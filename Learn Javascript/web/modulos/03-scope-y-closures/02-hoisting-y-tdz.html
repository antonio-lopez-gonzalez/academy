Hoisting y TDZ (Temporal Dead Zone)

Módulo 3 · Scope, closures y PF ⏱ 25 minutos

1 · Introducción

JavaScript parece ejecutarse línea por línea, pero el motor hace algo antes de empezar: escanea todo el código en busca de declaraciones y las "eleva" (hoisting) al principio de su scope. Este comportamiento invisible es la causa de algunos de los comportamientos más desconcertantes del lenguaje — y también de algunas de sus características más potentes.

El hoisting no mueve físicamente tu código. Es un modelo mental para entender que las declaraciones se procesan en la fase de compilación, antes de la ejecución. Y la Temporal Dead Zone (TDZ) es la zona de seguridad que let y const imponen para evitar que uses variables antes de que estén inicializadas.

2 · Teoría

Qué es el hoisting: las declaraciones suben, las inicializaciones NO

El motor de JavaScript ejecuta el código en dos fases:

  1. Fase de compilación (creación): escanea todas las declaraciones (var, let, const, function) y las registra en memoria.
  2. Fase de ejecución: ejecuta las instrucciones línea por línea, usando las variables ya registradas.

El hoisting es la manifestación de este proceso: las declaraciones "existen" desde el principio del scope, aunque las asignaciones ocurren en la línea donde están escritas.

Analogía: imagina que llegas a un teatro. El acomodador (fase de compilación) ya ha reservado todos los asientos (variables) y sabe exactamente dónde está cada uno. Pero los asientos están vacíos hasta que los ocupantes llegan durante la función (fase de ejecución). Puedes señalar un asiento vacío, pero no puedes usarlo hasta que su ocupante se siente.

Hoisting de var → undefined

var se eleva y se inicializa automáticamente a undefined. Por eso puedes usarlo antes de la declaración sin error (aunque obtengas undefined):

console.log(nombre); // undefined — no ReferenceError
var nombre = "Ana";
console.log(nombre); // "Ana"

// El motor ve esto como:
// var nombre;           ← declaración elevada, inicializada a undefined
// console.log(nombre);  ← undefined
// nombre = "Ana";       ← asignación en su sitio original
// console.log(nombre);  ← "Ana"

Hoisting de let/const → TDZ (Temporal Dead Zone)

let y const también se elevan, pero no se inicializan. Entran en la TDZ: el espacio entre el inicio del scope y la línea de declaración donde la variable es inaccesible. Cualquier intento de acceso lanza ReferenceError:

console.log(edad); // ReferenceError: Cannot access 'edad' before initialization
let edad = 28;
console.log(edad); // 28

// La TDZ existe para let y const:
// ┌─────────────────────────┐
// │ {                       │ ← inicio del scope
// │   // ZONA MUERTA (TDZ)  │    let ciudad existe pero no puede usarse
// │   console.log(ciudad);  │    ReferenceError
// │   let ciudad = "Madrid";│ ← fin de la TDZ, ciudad = "Madrid"
// │   console.log(ciudad);  │    "Madrid" — OK
// │ }                       │
// └─────────────────────────┘

Hoisting de funciones declaradas → completas

Las funciones declaradas con function nombre() {} se elevan completamente: tanto el nombre como el cuerpo están disponibles desde el principio del scope:

saludar(); // "¡Hola!" — la función ya existe

function saludar() {
  console.log("¡Hola!");
}

Arrow functions y funciones expresadas → NO tienen hoisting de función

Solo la variable se eleva (con las reglas de var, let o const). La función en sí no existe hasta la línea de asignación:

// Con var: la variable existe pero vale undefined
saludarVar(); // TypeError: saludarVar is not a function (undefined no es invocable)
var saludarVar = () => console.log("Hola");

// Con let/const: TDZ
saludarLet(); // ReferenceError: Cannot access 'saludarLet' before initialization
let saludarLet = () => console.log("Hola");

// Con function declaration: funciona perfectamente
saludarDeclarada(); // "Hola"
function saludarDeclarada() { console.log("Hola"); }

Temporal Dead Zone en acción con stack traces

La TDZ no distingue entre lectura y escritura. Cualquier referencia lanza error. El mensaje de error moderno es claro ("Cannot access before initialization"), pero en motores antiguos puede ser críptico:

function calcular() {
  // El parámetro por defecto se evalúa en la TDZ de 'x'
  // Esto es un error sutil: la TDZ de 'x' empieza aquí
  console.log(x); // ReferenceError
  let x = 10;
}

// TDZ con parámetros por defecto (error todavía más sutil)
function foo(a = b, b = 1) {
  console.log(a, b);
}
foo(); // ReferenceError: Cannot access 'b' before initialization
// Los parámetros se evalúan de izquierda a derecha en la misma TDZ

La TDZ con typeof (excepción interesante)

typeof es el único operador seguro con variables no declaradas (devuelve "undefined" sin error). Pero si la variable está declarada con let y estás en su TDZ, typeof también lanza error:

console.log(typeof noDeclarada); // "undefined" — la variable no existe, typeof es seguro

{
  console.log(typeof x); // ReferenceError — x está declarada con let pero en TDZ
  let x = 5;
}

3 · Ejemplo mínimo

// Hoisting desglosado: lo que escribes vs lo que ejecuta el motor

// ESTO ESCRIBES:
console.log(a); // undefined
var a = 1;
console.log(a); // 1

saludar(); // "Hola"
function saludar() { console.log("Hola"); }

// ESTO "VE" EL MOTOR:
// var a;            ← hoisting de la declaración
// function saludar() { console.log("Hola"); } ← hoisting completo
// console.log(a);   → undefined
// a = 1;            ← la asignación se queda aquí
// console.log(a);   → 1
// saludar();        → "Hola"

4 · Ejemplo real

Depurando un error común en un sistema de configuración:

// Archivo: config.js
// La intención: cargar configuración según entorno
// El bug: hoisting de funciones vs arrow functions

// Versión con bug (arrow function)
try {
  const config = cargarConfig(); // ReferenceError si cargarConfig usa let/const
} catch (e) {
  console.error("Error al cargar:", e.message);
}

const cargarConfig = () => {
  return { env: "production", debug: false };
};

// Stack trace típico:
// ReferenceError: Cannot access 'cargarConfig' before initialization
//   at <anonymous>:3:18   ← la línea de la llamada
// El error dice exactamente dónde falló

// Versión corregida (function declaration con hoisting)
// O simplemente mueve la llamada después de la definición:
const cargarConfig2 = () => ({ env: "development", debug: true });
const config = cargarConfig2(); // OK — definida antes de usar

6 · Errores habituales

1. Pensar que let no tiene hoisting

// ❌ CONCEPCIÓN ERRÓNEA: "let no tiene hoisting"
// En realidad sí lo tiene, pero entra en TDZ

let x = 10;
function test() {
  console.log(x); // ReferenceError, NO 10
  let x = 20;     // esta declaración causa shadowing y TDZ en todo el scope de la función
}
test();
// Si let no tuviera hoisting, vería la x=10 del scope exterior. Pero la ve, y está en TDZ.

2. Mezclar var y let en el mismo scope

// ❌ MAL: redeclaración ilegal (SyntaxError)
let a = 1;
var a = 2; // SyntaxError: Identifier 'a' has already been declared

// ❌ MAL: también ilegal
var b = 1;
let b = 2; // SyntaxError

3. TDZ en closures dentro de bucles

// ❌ MAL: la TDZ atrapa la variable antes del setTimeout
for (let i = 0; i < 3; i++) {
  setTimeout(() => {
    console.log(i); // funciona porque cada iteración tiene su propio 'i'
  }, 100);
}

// Con var: todas comparten la misma variable (clásico bug)
for (var j = 0; j < 3; j++) {
  setTimeout(() => {
    console.log(j); // 3, 3, 3 — al ejecutarse, j ya vale 3
  }, 100);
}

7 · Ejercicio guiado

Enunciado: Encuentra y explica todos los comportamientos de hoisting/TDZ en el siguiente código:

var tipo = "global";

function probarHoisting() {
  console.log("1:", tipo);   // ¿?
  console.log("2:", valor);  // ¿?

  if (true) {
    console.log("3:", bloque); // ¿?
    let bloque = "bloque";
    var valor = 42;
  }

  var tipo = "local";
  console.log("4:", tipo);   // ¿?

  function interna() {
    return "ok";
  }
}

probarHoisting();

Solución razonada:

  1. Línea "1:" — Imprime undefined. El var tipo = "local" de abajo se eleva al inicio de la función y sombrea al var tipo = "global" exterior. La declaración existe, pero la asignación "local" aún no ocurrió.

  2. Línea "2:" — Imprime undefined. var valor se eleva al scope de la función (ignora el bloque if). La declaración existe, la asignación no.

  3. Línea "3:" — ReferenceError. let bloque está en su TDZ dentro del bloque if. No se puede acceder antes de la declaración.

  4. Línea "4:" — Imprime "local". La asignación ya ocurrió.

8 · Reto

🎯 El detector de hoisting

Crea una función detectarHoisting(fn) que reciba una función como string y analice su comportamiento de hoisting sin ejecutarla.

  • Identifica todas las declaraciones (var, let, const, function) y su scope.
  • Para cada variable, determina si su uso antes de la declaración resultaría en undefined (var), ReferenceError (let/const en TDZ), o si es seguro (function declaration).
  • Devuelve un array de warnings: ["Línea 3: 'x' se usa antes de su declaración con let (TDZ)"].
  • No necesitas un parser completo; puedes usar regex para detectar patrones comunes.

9 · Resumen

  • Hoisting: las declaraciones se procesan antes de la ejecución. Las asignaciones se quedan en su sitio.
  • var: se eleva e inicializa a undefined. Usable antes de la declaración (con valor undefined).
  • let/const: se elevan pero entran en TDZ. No accesibles antes de la declaración → ReferenceError.
  • function declarada: se eleva completamente. Invocable desde el principio del scope.
  • Arrow / función expresada: solo se eleva la variable (con reglas de var/let/const). La función no existe hasta la línea de asignación.
  • TDZ: espacio entre el inicio del scope y la declaración de let/const. Atrapa accesos tempranos.
  • typeof en TDZ: también lanza ReferenceError. Es la única excepción a la seguridad de typeof.

10 · Preguntas frecuentes

¿Por qué se diseñó la TDZ en lugar de simplemente no elevar let/const?

Por consistencia del motor. Si let no se elevara, habría dos comportamientos distintos: variables que existen desde el principio del scope (var) y variables que aparecen mágicamente a mitad del bloque. La TDZ unifica el comportamiento: todas las declaraciones se procesan en la fase de compilación, pero let/const añaden una restricción de acceso. Es una decisión deliberada para hacer el lenguaje más predecible, no un efecto secundario.

¿El hoisting afecta al rendimiento?

No de forma significativa. Ocurre en la fase de compilación, una sola vez por script. El coste de registrar variables en memoria es despreciable comparado con la ejecución real del código. No evites declarar variables por miedo al hoisting.

¿Por qué class tiene TDZ pero function no?

Porque las clases pueden extender otras clases, y si la clase padre no estuviera en TDZ, podría crearse una clase hija con un padre que aún no existe, causando errores difíciles de depurar. La TDZ en clases es una protección. Las funciones declaradas no dependen de otras funciones para existir, así que pueden elevarse completamente sin riesgo.

¿Existe el hoisting en otros lenguajes?

Sí, pero con otros nombres. Python "compila" las funciones y clases al inicio del módulo. C/C++ requieren declarar antes de usar (forward declaration). Java no tiene hoisting porque es compilado: el compilador resuelve todas las referencias en tiempo de compilación. El hoisting de JavaScript es único en que eleva las declaraciones pero no las inicializaciones, lo que lo hace especialmente confuso para principiantes.
