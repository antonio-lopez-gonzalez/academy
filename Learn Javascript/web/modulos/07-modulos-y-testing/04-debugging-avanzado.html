Debugging avanzado: breakpoints, watch, call stack, performance

Módulo 7 · Módulos, tooling y testing ⏱ 30 minutos

1 · Introducción

En la lección Módulo 0 aprendiste lo básico de las DevTools: la consola, console.log y los paneles principales. Ahora vamos un paso más allá: el objetivo es que dejes de "adivinar" y empieces a observar. El debugging avanzado consiste en congelar la ejecución en el momento exacto en que ocurre el problema, examinar el estado interno y entender la secuencia de llamadas que te llevó hasta allí.

Veremos las herramientas que todo desarrollador senior usa a diario: breakpoints (puntos de interrupción) de varios tipos, watch expressions, el call stack (pila de llamadas), logpoints, depuración de Node.js desde VSCode y profiling de rendimiento. Aprenderlo bien convierte un error que tardaba una hora en resolverse en un problema de cinco minutos.

¿Por qué esto importa?

El 90% de tu tiempo como desarrollador lo pasas leyendo código y depurando, no escribiendo. Dominar el debugging no es un lujo: es la habilidad que determina tu velocidad real de producción.

2 · Teoría

¿Qué es un breakpoint?

Un breakpoint (punto de interrupción) es una marca que le dices al motor de JavaScript: "detente aquí, justo antes de ejecutar esta línea, y déjame mirar". Cuando la ejecución se detiene, tienes una sesión de depuración pausada: puedes inspeccionar variables, evaluar expresiones en la consola, saltar línea a línea y observar la pila de llamadas.

// Coloca un breakpoint en esta línea (F9 en VSCode, o clic en el número de línea en DevTools)
const total = calcularTotal(articulos);

// Cuando el breakpoint "salta", puedes:
//  - Pasar el ratón por encima de 'articulos' para ver su valor
//  - Escribir 'calcularTotal' en la consola para ver la función
//  - Avanzar con F10 (siguiente línea) o F11 (entrar en la función)

Tipos de breakpoints

TipoCómo se creaCuándo se detiene

El call stack (pila de llamadas)

JavaScript ejecuta el código en un hilo único y lleva un registro de qué función está ejecutándose y quién la llamó. Esa estructura de datos es la pila de llamadas. Cuando una función llama a otra, la nueva se apila encima; al terminar, se desapila y se reanuda la anterior.

# Pila de llamadas vista en DevTools (de arriba a abajo):
#   multiplicar    ← la función actual (donde estamos pausados)
#   calcularPrecio  ← quien llamó a multiplicar
#   crearPedido     ← quien llamó a calcularPrecio
#   (anonymous)     ← script principal
#   (index):42      ← archivo y línea de cada llamada
Analogía

Piensa en un restaurante: el jefe de cocina apila pedidos. Cuando llega un pedido especial, lo coloca encima y lo atiende primero; cuando termina, vuelve al que tenía debajo. El call stack funciona igual: las llamadas se apilan y se desapilan en orden LIFO (Last In, First Out).

Watch expressions y scope

Una watch expression es una expresión que le pides al depurador que reevalúe en cada paso de la ejecución. No tienes que escribirla en consola cada vez: se actualiza automáticamente mientras pausas y avanzas. El panel Scope muestra todas las variables visibles en el punto exacto de la pausa, agrupadas por alcance: Local, Closure, Global.

Depurar Node.js: el flujo moderno

Hoy en día no hace falta console.log a mansalva en Node. Puedes depurar con el inspector integrado (Chrome DevTools apuntando a Node) o, lo más cómodo, directamente desde VSCode con un archivo de configuración launch.json.

// .vscode/launch.json — perfil de depuración para Node.js en VSCode
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Depurar archivo actual",
      "type": "node",
      "request": "launch",
      "program": "${file}",           // ejecuta el archivo que tienes abierto
      "skipFiles": ["/**"], // no entres en el código interno de Node
      "runtimeArgs": ["--import=tsx"]  // solo si usas TypeScript
    },
    {
      "name": "Vitest (debug)",
      "type": "node",
      "request": "launch",
      "program": "${workspaceFolder}/node_modules/vitest/vitest.mjs",
      "args": ["run"],
      "console": "integratedTerminal",
      "autoAttachChildProcesses": true
    }
  ]
}

Profiling: ¿por qué es lento mi código?

El Performance panel de DevTools graba la actividad de la página y genera un flamegraph (gráfico de llamas). Cada barra es una función; el ancho indica cuánto tiempo tardó. La detección de cuellos de botella se reduce a buscar las barras más anchas y las funciones con self time alto (tiempo gastado dentro de sí mismas, sin contar sus llamadas internas).

3 · Ejemplo mínimo

Un ejemplo que parece inofensivo pero esconde un error clásico. Pausemos la ejecución y observemos qué ocurre:

// Código con un bug sutil: calcula el IVA de una lista de precios
function calcularIVA(precios, tasa) {
  let total = 0;
  for (let i = 0; i < precios.length; i++) {
    total += precios[i] * tasa;   // ← BREAKPOINT aquí: ¿qué valor tiene precios[i]?
  }
  return total;
}

const precios = [10.5, 25, 8.75, 99.99];
const resultado = calcularIVA(precios, 0.21); // 21% de IVA
console.log(resultado); // esperamos 30.17, ¿obtenemos eso?

Paso a paso con breakpoint + watch:

  1. Pon el breakpoint

    Haz clic en el número de la línea total += precios[i] * tasa; en el panel Sources. Aparece un círculo rojo: la ejecución se detendrá ahí.

  2. Añade una watch expression

    En la sección Watch, haz clic en + y escribe precios[i]. Ahora, cada vez que la ejecución se detenga en ese punto, verás el precio actual del elemento.

  3. Recorre la ejecución

    Pulsa F8 (continuar) varias veces. Observa cómo la watch expression precios[i] cambia: 10.5, 25, 8.75, 99.99. El cálculo se ve correcto.

  4. Inspecciona el resultado final

    Cuando la ejecución termine, el resultado 30.17 es correcto (10.5+25+8.75+99.99 = 144.24 · 0.21 = 30.29... revisa la precisión). Con el depurador comprobamos que el bug no estaba aquí.

4 · Ejemplo real

Una mini-aplicación de carrito que no suma bien. Depuraremos un bug real con logpoints y call stack.

// carrito.js — pequeño programa Node que simula una tienda
const carrito = [];

// Añade un artículo al carrito
function agregar(producto) {
  carrito.push(producto);         // mutamos el array global
  return carrito.length;          // devolvemos el nuevo tamaño
}

// Calcula el total, aplicando descuento y IVA
function calcularTotal(articulos) {
  // Si no hay artículos, devolvemos 0 rápido (early return)
  if (articulos.length === 0) return 0;

  const subtotal = articulos.reduce((suma, a) => suma + a.precio, 0);
  const descuento = subtotal > 100 ? 10 : 0;   // 10€ de descuento si supera 100
  const total = subtotal - descuento;
  return total;
}

// Simulamos una compra
agregar({ nombre: 'Teclado', precio: 59 });
agregar({ nombre: 'Ratón', precio: 29 });
agregar({ nombre: 'Alfombrilla', precio: 19 });

const total = calcularTotal(carrito);
console.log('Total a pagar:', total); // ¿Por qué no se aplica el IVA 21%?

Debugging con DevTools de Node:

  1. Arranca el inspector

    node --inspect carrito.js
# o con pausa automática en la primera línea:
node --inspect-brk carrito.js

  2. Conecta Chrome

    Abre chrome://inspect y haz clic en "inspect" junto a tu proceso Node. Se abre una instancia de DevTools dedicada.

  3. Usa un logpoint en el reduce

    Clic derecho sobre la línea del reduce → "Add logpoint" con suma, a.precio. Ahora, sin detener la ejecución, verás cada iteración en la consola: 0 59, 59 29, 88 19.

  4. Examina el call stack

    El logpoint muestra que el subtotal es 107. El descuento de 10 se aplica (107 > 100) y el total es 97. El bug está claro: falta el IVA. El descuento se resta, pero nunca se añade el impuesto. Fíjate en el call stack: calcularTotal ← (anonymous).

  5. Corrige

    // Versión corregida: subtotal con descuento, y después el IVA (21%)
function calcularTotal(articulos) {
  if (articulos.length === 0) return 0;

  const subtotal = articulos.reduce((suma, a) => suma + a.precio, 0);
  const descuento = subtotal > 100 ? 10 : 0;
  const subtotalConDescuento = subtotal - descuento;
  const iva = 0.21;                                   // tipo de IVA
  return subtotalConDescuento * (1 + iva);            // total con impuestos
}

console.log('Total a pagar:', calcularTotal(carrito).toFixed(2)); // 117.37
Clave del ejemplo

El console.log te dice el qué (el total es 97), pero el debugger te dice el cómo: qué valores exactos pasaron por cada paso. Esa es la diferencia entre adivinar y saber.

6 · Errores habituales

Error 1: Depurar una build de producción minificada

// ❌ MAL: Vite hace build minificado, los nombres de variables cambian
// pnpm build && sirve la carpeta dist/ y abres las DevTools...
// Verás variables como 'n' y 'e', el breakpoint "no funciona" o salta en sitios raros

// ✅ CORRECTO: depura en modo desarrollo
// pnpm dev   ← servidor de desarrollo de Vite, código fuente intacto
// O si debes depurar producción, activa los source maps en vite.config.js:
// build: { sourcemap: true }

Error 2: Romper el flujo asíncrono con breakpoints

// ❌ MAL: pones un breakpoint en la promesa y no entiendes el orden de ejecución
fetch('/api/datos').then((r) => r.json()).then((datos) => renderizar(datos));
console.log('después del fetch'); // ← este console.log se imprime ANTES que renderizar

// ✅ CORRECTO: activa "Async" en DevTools (await) para pausar tras la resolución
// Con la casilla 'async' marcada en Sources, el depurador te muestra también
// el contexto asíncrono: qué llamada lanzó esta promesa.

Error 3: Poner el breakpoint en la línea equivocada

function duplicar(n) {
  return n * 2;   // ← breakpoint aquí: se detiene ANTES de ejecutar el return
}                 // si pausas aquí, n aún no está duplicado; avanza (F10) para verlo

// Consejo: para ver el resultado de una función, pon el breakpoint en la
// línea DESPUÉS de la llamada:
const resultado = duplicar(21); // ← breakpoint aquí: resultado ya contiene 42

Error 4: Olvidar que la pila se limpia al continuar

// ❌ MAL: intentas "volver atrás" en el call stack de un lenguaje interpretado
// En JavaScript no puedes retroceder la ejecución; el call stack solo sube (hacia
// la función llamadora), nunca baja en el tiempo.

// ✅ CORRECTO: si necesitas ver un estado anterior, pon un breakpoint más arriba
// o usa "Restart frame" (reinicia el frame actual re-ejecutando esa función).

7 · Ejercicio guiado

Objetivo: depurar un bug real con breakpoint, watch y call stack. La función ordenarPedido no devuelve lo esperado.

  1. Paso 1: Código del ejercicio

    function aplicarDescuento(precio, cupon) {
  // Un cupón puede ser '10' (10%), '20' (20%) o null (sin descuento)
  if (cupon === null) return precio;
  return precio - (precio * cupon) / 100;
}

function calcularEnvio(pesoKg) {
  // Envío gratis si pesa menos de 5 kg, si no 5€
  if (pesoKg < 5) return 0;
  return 5;
}

function ordenarPedido(precio, cupon, pesoKg) {
  const conDescuento = aplicarDescuento(precio, cupon);
  const envio = calcularEnvio(pesoKg);
  return conDescuento + envio;
}

// Se espera: 100 con 20% = 80, + envío 5 = 85
console.log(ordenarPedido(100, '20', 7)); // ¿Qué devuelve realmente?

  2. Paso 2: Establece el punto de interrupción

    Pon un breakpoint en la línea const conDescuento = aplicarDescuento(...). Ejecuta. Al pausar, en el panel Scope verás: precio: 100, cupon: "20" (¡string!), pesoKg: 7.

  3. Paso 3: Añade la watch expression

    Añade typeof cupon a Watch. Verás "string". Ese es el bug: la función espera el número 20, pero recibe el string "20".

  4. Paso 4: Entra en la función (F11)

    Pulsa F11 para entrar en aplicarDescuento. Observa el call stack: ahora tiene dos entradas: aplicarDescuento ← ordenarPedido. Dentro, el cálculo precio - (precio * cupon) / 100 con cupon = "20".

  5. Paso 5: Comprueba el resultado

    El descuento con string: 100 - (100 * "20") / 100 = 100 - 2000/100 = 100 - 20 = 80. Resulta que JavaScript coerciona el string a número en la multiplicación... pero la resta final sí da 80. El resultado 85 parece correcto.

    Ahora cambia la llamada a ordenarPedido(100, '20', 7) y prueba con el cupón '10' y null para asegurarte. La lección: valida tipos en el límite, porque la coerción puede dar la respuesta correcta "por accidente" hoy y romper mañana.

  6. Paso 6: Solución defensiva

    // Normalizamos el cupón al principio: aceptamos número o string, y null/undefined
function aplicarDescuento(precio, cupon) {
  if (cupon == null) return precio;                 // null o undefined → sin descuento
  const porcentaje = Number(cupon);                 // conversión explícita y segura
  if (Number.isNaN(porcentaje) || porcentaje <= 0) return precio; // descuento inválido
  return precio - (precio * porcentaje) / 100;
}

8 · Reto

🎯 Caza el bug del rendimiento

Tienes una función que parece infinita: tarda segundos en procesar una lista pequeña. Usa el Performance panel para descubrir el cuello de botella.

// Reto: este código es lentísimo con listas de 200 elementos. ¿Por qué?
function aplanar(anidado) {
  let resultado = [];
  for (let i = 0; i < anidado.length; i++) {
    const item = anidado[i];
    if (Array.isArray(item)) {
      resultado = resultado.concat(aplanar(item)); // ¿concatenación repetida?
    } else {
      resultado.push(item);
    }
  }
  return resultado;
}

const listaAnidada = Array.from({ length: 200 }, (_, i) => [i, [i + 1, i + 2]]);
console.time('aplanar');
const plana = aplanar(listaAnidada);
console.timeEnd('aplanar');
console.log('Elementos:', plana.length);

Pistas: graba con el Performance panel, busca la barra más ancha, y piensa en qué hace concat en cada llamada recursiva (¿crea un array nuevo? ¿copias?). Cuando lo descubras, propón una versión O(n) que use un único array con push.

9 · Resumen

  • Los breakpoints congelan la ejecución para inspeccionar el estado; hay de línea, condicionales, logpoints, XHR, eventos y DOM.
  • El call stack muestra quién llamó a quién; el error real suele estar en un llamador anterior.
  • Las watch expressions se reevalúan automáticamente en cada paso, sin teclear en consola.
  • Los logpoints registran mensajes sin modificar el código y sin pausar la ejecución.
  • Node.js se depura con --inspect o directamente desde VSCode con launch.json.
  • El Performance panel genera flamegraphs: la barra más ancha es el cuello de botella.
  • Depura en modo desarrollo (código fuente), no sobre la build minificada.

10 · Preguntas frecuentes

¿Breakpoint o console.log?

Empieza con un logpoint o un breakpoint cuando no sabes qué está pasando y necesitas explorar. Usa console.log solo si quieres dejar un log permanente y significativo en producción (que no sea de depuración). Regla práctica: si vas a borrar el console.log al terminar, es depuración → usa breakpoint/logpoint.

¿Por qué mi breakpoint no se activa?

Causas habituales: (1) estás depurando una build minificada de producción; (2) la línea no se ejecuta realmente (código muerto o una rama no alcanzada); (3) el archivo se sirve desde caché — fuerza el recargo sin caché con Ctrl+Shift+R; (4) estás depurando código transformado sin source maps.

¿Cómo depuro código asíncrono y promesas?

Marca la opción async (await) en el panel Sources de DevTools. Así, al pausar en una promesa, podrás ver el contexto asíncrono que la originó. Para async/await, pon el breakpoint en la línea tras el await y avanza con F10; el estado anterior está disponible en la pila con "Async" activado.

¿Puedo depurar mi aplicación Vite desde VSCode?

Sí. Arranca Vite en modo watch y usa un perfil de Chrome de VSCode apuntando a http://localhost:5173, o usa la extensión "Debugger for Chrome" (o el depurador nativo integrado). El panel Run and Debug te permite poner breakpoints directamente en tu código fuente con source maps.
