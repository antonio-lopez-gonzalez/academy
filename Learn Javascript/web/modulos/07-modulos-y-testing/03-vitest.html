Introducción a Vitest: test, describe, expect, mocks

Módulo 7 · Módulos, tooling y testing ⏱ 35 minutos

1 · Introducción

Escribir código sin tests es como construir un puente y no comprobar si aguanta peso: puedes tener suerte durante meses, pero eventualmente algo se romperá en producción. El testing automatizado es la red de seguridad que te permite hacer cambios con confianza, refactorizar sin miedo y dormir tranquilo tras un deploy.

Vitest es un framework de testing moderno diseñado para proyectos Vite. Comparte la misma configuración, el mismo pipeline de transformación y los mismos plugins que Vite, por lo que integrarlo en un proyecto existente es casi instantáneo. Es compatible con la API de Jest (el framework más popular), así que si sabes Jest, sabes Vitest.

¿Por qué Vitest y no Jest?

Jest fue el estándar durante años, pero es lento en proyectos ESM y requiere configuración adicional para TypeScript y JSX. Vitest nació para Vite: es más rápido (usa esbuild para transformación), soporta ESM nativamente, y su watch mode es instantáneo gracias a HMR. En proyectos Vite, es la elección natural.

2 · Teoría

TDD vs BDD: dos filosofías de testing

  • TDD (Test-Driven Development): escribes el test PRIMERO, luego el código mínimo para que pase. Ciclo: Red (test falla) → Green (pasa) → Refactor. Fuerza a pensar en la API antes que en la implementación.
  • BDD (Behavior-Driven Development): escribes tests que describen el COMPORTAMIENTO del sistema desde la perspectiva del usuario. Usa lenguaje natural (describe, it). Enfocado en el "qué hace", no en el "cómo".

Vitest soporta ambos estilos, pero la API describe/it (estilo BDD) es la más usada y la que emplearemos.

Instalación y configuración

pnpm add -D vitest

Añade a tu package.json:

{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest",
    "test:coverage": "vitest run --coverage"
  }
}

Si tienes un vite.config.js, Vitest lo usa automáticamente. Puedes añadir configuración de test:

// vite.config.js
import { defineConfig } from 'vite';

export default defineConfig({
  test: {
    // Entorno: 'node' (por defecto), 'jsdom', 'happy-dom'
    environment: 'jsdom',
    // Archivos de test: por defecto **/*.test.js y **/*.spec.js
    include: ['src/**/*.test.js'],
    // Globals: si true, no necesitas importar describe/it/expect
    globals: true,
  },
});

La API fundamental: test, describe, it, expect

  • test(nombre, fn, opciones?) o su alias it(nombre, fn): define un único test. La función puede ser síncrona o async.
  • describe(nombre, fn): agrupa tests relacionados. Puede anidarse. Crea un contexto compartido para beforeEach, afterEach, etc.
  • expect(valor): crea una aserción. Devuelve un objeto con métodos (toBe, toEqual, etc.) para verificar el valor.

Lifecycle hooks (ciclo de vida)

  • beforeAll(fn): se ejecuta UNA vez antes de todos los tests del bloque describe.
  • beforeEach(fn): se ejecuta antes de CADA test. Ideal para resetear estado, limpiar mocks.
  • afterEach(fn): se ejecuta después de cada test. Limpiar recursos, restaurar mocks.
  • afterAll(fn): se ejecuta UNA vez después de todos los tests. Cerrar conexiones, limpiar archivos temporales.

Mocks con vi.fn() y vi.mock()

Testear código aislándolo de sus dependencias externas:

  • vi.fn(): crea una función mock. Puedes inspeccionar cuántas veces se llamó, con qué argumentos, y definir su valor de retorno.
  • vi.mock('modulo'): reemplaza un módulo entero por un mock automático.
  • vi.spyOn(objeto, 'metodo'): espía un método existente sin reemplazar su implementación.
// Mock de función
const mockFn = vi.fn();
mockFn('hola');
expect(mockFn).toHaveBeenCalled();     // fue llamada
expect(mockFn).toHaveBeenCalledTimes(1); // 1 vez
expect(mockFn).toHaveBeenCalledWith('hola'); // con 'hola'

// Mock de módulo completo
vi.mock('./api.js', () => ({
  getUsers: vi.fn().mockResolvedValue([{ id: 1, name: 'Ana' }]),
  getPosts: vi.fn().mockRejectedValue(new Error('Fallo de red')),
}));

// Spy: espía console.log sin eliminar su comportamiento
const spy = vi.spyOn(console, 'log');
miFuncion(); // Llama a console.log internamente
expect(spy).toHaveBeenCalledWith('Mensaje esperado');
spy.mockRestore(); // Restaurar comportamiento original

Test coverage

El coverage mide qué porcentaje de tu código está cubierto por tests. Se instala con pnpm add -D @vitest/coverage-v8 y se ejecuta con pnpm test:coverage. Vitest genera un reporte detallado por línea, función y rama de decisión. Apunta a >80% de cobertura en proyectos serios, pero no persigas el 100% a ciegas: mejor pocos tests buenos que muchos tests triviales.

3 · Ejemplo mínimo

// 🧪 src/sumar.js — La función a testear
export function sumar(a, b) {
  return a + b;
}
// 🧪 src/sumar.test.js — El test más simple posible
import { describe, it, expect } from 'vitest';
import { sumar } from './sumar.js';

describe('sumar()', () => {
  it('debe sumar dos números positivos', () => {
    const resultado = sumar(2, 3);
    expect(resultado).toBe(5);
  });

  it('debe sumar números negativos', () => {
    expect(sumar(-1, -2)).toBe(-3);
  });

  it('debe sumar cero correctamente', () => {
    expect(sumar(5, 0)).toBe(5);
  });
});

Ejecuta pnpm test y verás:

✓ src/sumar.test.js (3)
  ✓ sumar() (3)
    ✓ debe sumar dos números positivos
    ✓ debe sumar números negativos
    ✓ debe sumar cero correctamente

Tests  3 passed (3)

Desglose:

  1. describe('sumar()', fn) agrupa los tests de la función sumar.
  2. it('debe sumar...', fn) define un test individual con un nombre descriptivo.
  3. expect(valor) inicia una aserción.
  4. .toBe(valorEsperado) comprueba igualdad estricta (===).

4 · Ejemplo real

Testeando una función de utilidad pura

// 📁 src/validators.js — Código a testear
export function isValidEmail(email) {
  const regex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  return regex.test(email);
}

export function isValidPassword(password) {
  return password.length >= 8
    && /[A-Z]/.test(password)
    && /[a-z]/.test(password)
    && /[0-9]/.test(password);
}

export function capitalize(text) {
  if (typeof text !== 'string') return '';
  return text.charAt(0).toUpperCase() + text.slice(1).toLowerCase();
}
// 📁 src/validators.test.js — Tests exhaustivos
import { describe, it, expect } from 'vitest';
import { isValidEmail, isValidPassword, capitalize } from './validators.js';

describe('isValidEmail', () => {
  it('debe validar un email correcto', () => {
    expect(isValidEmail('test@example.com')).toBe(true);
    expect(isValidEmail('user+tag@domain.co.uk')).toBe(true);
  });

  it('debe rechazar emails sin @', () => {
    expect(isValidEmail('notanemail')).toBe(false);
  });

  it('debe rechazar emails sin dominio', () => {
    expect(isValidEmail('user@')).toBe(false);
    expect(isValidEmail('@domain.com')).toBe(false);
  });

  it('debe rechazar strings vacíos', () => {
    expect(isValidEmail('')).toBe(false);
  });
});

describe('isValidPassword', () => {
  it('debe aceptar una contraseña fuerte', () => {
    expect(isValidPassword('Abcd1234')).toBe(true);
  });

  it('debe rechazar contraseñas cortas', () => {
    expect(isValidPassword('Ab1')).toBe(false);
  });

  it('debe rechazar contraseñas sin mayúscula', () => {
    expect(isValidPassword('abcd1234')).toBe(false);
  });

  it('debe rechazar contraseñas sin número', () => {
    expect(isValidPassword('Abcdefgh')).toBe(false);
  });
});

describe('capitalize', () => {
  it('debe capitalizar un string en minúsculas', () => {
    expect(capitalize('hola')).toBe('Hola');
  });

  it('debe forzar minúsculas en el resto', () => {
    expect(capitalize('HOLA')).toBe('Hola');
  });

  it('debe manejar string vacío', () => {
    expect(capitalize('')).toBe('');
  });

  it('debe devolver string vacío para no-strings', () => {
    expect(capitalize(null)).toBe('');
    expect(capitalize(123)).toBe('');
  });
});

Testeando código que usa fetch con mocks

// 📁 src/api.js — Código a testear
export async function getUsers(page = 1) {
  const res = await fetch(
    `https://jsonplaceholder.typicode.com/users?_page=${page}&_limit=5`
  );
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}
// 📁 src/api.test.js — Test con mock de fetch global
import { describe, it, expect, vi, beforeEach } from 'vitest';
import { getUsers } from './api.js';

describe('getUsers', () => {
  beforeEach(() => {
    // Resetear el mock antes de cada test para evitar interferencias
    vi.restoreAllMocks();
  });

  it('debe devolver una lista de usuarios', async () => {
    const mockUsers = [{ id: 1, name: 'Ana' }, { id: 2, name: 'Luis' }];

    // Mock de fetch global
    globalThis.fetch = vi.fn().mockResolvedValue({
      ok: true,
      json: () => Promise.resolve(mockUsers),
    });

    const users = await getUsers();

    expect(users).toEqual(mockUsers);
    expect(users).toHaveLength(2);

    // Verificar que fetch se llamó con la URL correcta
    expect(fetch).toHaveBeenCalledTimes(1);
    expect(fetch).toHaveBeenCalledWith(
      expect.stringContaining('users')
    );
  });

  it('debe lanzar error si la respuesta no es ok', async () => {
    globalThis.fetch = vi.fn().mockResolvedValue({
      ok: false,
      status: 404,
      statusText: 'Not Found',
    });

    await expect(getUsers()).rejects.toThrow('HTTP 404');
  });

  it('debe incluir el parámetro de página en la URL', async () => {
    globalThis.fetch = vi.fn().mockResolvedValue({
      ok: true,
      json: () => Promise.resolve([]),
    });

    await getUsers(3);

    expect(fetch).toHaveBeenCalledWith(
      expect.stringContaining('_page=3')
    );
  });
});

5 · Buenas prácticas

HazEvitaPor qué
Nombra los tests describiendo el comportamiento esperado Nombres genéricos como 'test 1' o 'funciona' Un test fallido debe decirte exactamente qué se rompió sin necesidad de leer el código
Un test = una aserción lógica (o pocas muy relacionadas) Un solo it con 20 expect sin relación Si falla una aserción, las demás no se ejecutan; pierdes información sobre otros fallos
Usa beforeEach para resetear estado compartido Modificar variables globales en un test y asumir que el siguiente las ve limpias Los tests deben ser independientes; el orden de ejecución no debería afectar el resultado
Mockea solo lo que no controlas (fetch, APIs externas, Date) Mockear la propia función que estás testeando o funciones puras Si mockeas lo que quieres testear, no estás testeando nada real
Testea casos de error tanto como casos de éxito Solo testear el "happy path" Los bugs más graves suelen ocurrir en casos límite y situaciones de error

6 · Errores habituales

Error 1: Tests que dependen del orden de ejecución

// ❌ MAL: el test 2 depende de que el test 1 se ejecute primero
let contador = 0;

it('incrementa el contador', () => {
  contador++;
  expect(contador).toBe(1); // Pasa solo si se ejecuta primero
});

it('vuelve a incrementar', () => {
  contador++;
  expect(contador).toBe(2); // Falla si vitest ejecuta este test primero
});

// ✅ CORRECTO: resetear en beforeEach
let contador = 0;

beforeEach(() => {
  contador = 0; // Estado limpio en cada test
});

it('incrementa de 0 a 1', () => {
  contador++;
  expect(contador).toBe(1);
});

it('incrementa de 0 a 1 (independiente)', () => {
  contador++;
  expect(contador).toBe(1); // Ambos tests pasan sin importar el orden
});

Error 2: Aserción que nunca se ejecuta en código async

// ❌ MAL: el test termina antes de que se ejecute la aserción
it('debe cargar usuarios', () => {
  getUsers().then(users => {
    expect(users).toHaveLength(2); // Nunca se ejecuta: el test ya terminó
  });
}); // El test pasa siempre (no hay aserciones ejecutadas)

// ✅ CORRECTO: usar async/await o retornar la promesa
it('debe cargar usuarios', async () => {
  const users = await getUsers();
  expect(users).toHaveLength(2);
});

Error 3: Usar toBe en lugar de toEqual para objetos/arrays

// ❌ MAL: toBe compara por referencia (===)
expect({ a: 1 }).toBe({ a: 1 }); // FALLA: son objetos diferentes en memoria
expect([1, 2, 3]).toBe([1, 2, 3]); // FALLA: mismo motivo

// ✅ CORRECTO: toEqual compara por valor (deep equality)
expect({ a: 1 }).toEqual({ a: 1 }); // PASA
expect([1, 2, 3]).toEqual([1, 2, 3]); // PASA

Error 4: Olvidar limpiar mocks globales

// ❌ MAL: el mock de fetch contamina otros tests
it('test 1', async () => {
  globalThis.fetch = vi.fn().mockResolvedValue({ ok: true, json: () => [] });
  await getUsers();
  expect(fetch).toHaveBeenCalledTimes(1);
});

it('test 2', async () => {
  await getUsers(); // fetch sigue siendo el mock del test 1
  expect(fetch).toHaveBeenCalledTimes(1); // Falla: fue llamado 2 veces
});

// ✅ CORRECTO: limpiar en beforeEach
beforeEach(() => {
  vi.restoreAllMocks(); // Restaura fetch original entre tests
});

7 · Ejercicio guiado

Escribe tests para una mini librería de arrays

  1. Crea el código a testear. 
    // 📁 src/array-utils.js
export function uniq(arr) {
  return [...new Set(arr)];
}

export function groupBy(arr, keyFn) {
  return arr.reduce((acc, item) => {
    const key = keyFn(item);
    if (!acc[key]) acc[key] = [];
    acc[key].push(item);
    return acc;
  }, {});
}

export function chunk(arr, size) {
  if (size <= 0) return [];
  const result = [];
  for (let i = 0; i < arr.length; i += size) {
    result.push(arr.slice(i, i + size));
  }
  return result;
}

export function shuffle(arr) {
  const copy = [...arr];
  for (let i = copy.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [copy[i], copy[j]] = [copy[j], copy[i]];
  }
  return copy;
}
  2. Escribe el archivo de tests. 
    // 📁 src/array-utils.test.js
import { describe, it, expect } from 'vitest';
import { uniq, groupBy, chunk, shuffle } from './array-utils.js';

describe('uniq', () => {
  it('debe eliminar duplicados', () => {
    expect(uniq([1, 2, 2, 3, 3, 3])).toEqual([1, 2, 3]);
  });

  it('debe retornar array vacío si recibe array vacío', () => {
    expect(uniq([])).toEqual([]);
  });

  it('no debe modificar arrays sin duplicados', () => {
    expect(uniq([1, 2, 3])).toEqual([1, 2, 3]);
  });
});

describe('groupBy', () => {
  const usuarios = [
    { name: 'Ana', role: 'admin' },
    { name: 'Luis', role: 'user' },
    { name: 'Mia', role: 'admin' },
  ];

  it('debe agrupar por role', () => {
    const result = groupBy(usuarios, u => u.role);
    expect(result.admin).toHaveLength(2);
    expect(result.user).toHaveLength(1);
    expect(result.admin[0].name).toBe('Ana');
  });

  it('debe retornar objeto vacío para array vacío', () => {
    expect(groupBy([], x => x)).toEqual({});
  });
});

describe('chunk', () => {
  it('debe dividir en chunks del tamaño indicado', () => {
    expect(chunk([1, 2, 3, 4, 5], 2)).toEqual([[1, 2], [3, 4], [5]]);
  });

  it('debe devolver array vacío si size es 0 o negativo', () => {
    expect(chunk([1, 2, 3], 0)).toEqual([]);
    expect(chunk([1, 2, 3], -1)).toEqual([]);
  });
});

describe('shuffle', () => {
  it('debe devolver un array de la misma longitud', () => {
    const arr = [1, 2, 3, 4, 5];
    expect(shuffle(arr)).toHaveLength(5);
  });

  it('debe contener los mismos elementos', () => {
    const arr = [1, 2, 3, 4, 5];
    const shuffled = shuffle(arr);
    expect(shuffled.sort()).toEqual([1, 2, 3, 4, 5]);
  });

  it('no debe modificar el array original', () => {
    const arr = [1, 2, 3];
    const copy = [...arr];
    shuffle(arr);
    expect(arr).toEqual(copy); // Inmutabilidad
  });
});

8 · Reto

🎯 Implementa y testea un sistema de caché con TTL

Crea una clase Cache con estos métodos y escribe tests exhaustivos:

  • set(key, value, ttlMs): guarda un valor con tiempo de vida en ms.
  • get(key): devuelve el valor si existe y no ha expirado; si expiró, devuelve undefined.
  • has(key): true si la clave existe y no expiró.
  • delete(key): elimina una clave manualmente.
  • clear(): vacía toda la caché.
  • size: getter que devuelve el número de entradas no expiradas.

Escribe tests para: guardar y recuperar, expiración por TTL, eliminación manual, clear, size con entradas expiradas. Usa vi.useFakeTimers() para controlar el tiempo en los tests sin esperar realmente.

9 · Resumen

  • Vitest es el framework de testing para proyectos Vite: rápido, compatible con Jest, nativo ESM.
  • TDD: test primero, código después. BDD: describe comportamiento (describe/it).
  • describe agrupa tests; it/test define un test; expect hace aserciones.
  • Usa toBe para primitivos (comparación ===) y toEqual para objetos/arrays (deep equality).
  • Los lifecycle hooks (beforeEach, afterEach) preparan y limpian el entorno entre tests.
  • vi.fn() crea funciones mock; vi.mock() reemplaza módulos enteros; vi.spyOn() espía métodos sin eliminarlos.
  • El test coverage mide qué % del código está cubierto. Usa @vitest/coverage-v8 y apunta a >80%.
  • Los tests son independientes: no deben depender del orden de ejecución ni compartir estado mutable.

10 · Preguntas frecuentes

¿Cuándo debo usar toBe vs toEqual?

toBe usa Object.is (similar a ===). Úsalo para primitivos: números, strings, booleanos, null, undefined. toEqual hace comparación recursiva de propiedades. Úsalo para objetos, arrays, sets, maps. Si usas toBe con objetos, fallará aunque los objetos tengan las mismas propiedades, porque son referencias diferentes en memoria.

¿Los tests deben estar en la misma carpeta que el código?

Hay dos convenciones: (1) Colocated: sumar.js junto a sumar.test.js en la misma carpeta. Ventaja: fácil encontrar el test. (2) Carpeta __tests__ separada, reflejando la estructura de src. Ventaja: separación limpia. Vitest acepta ambas; en este curso usamos colocated por simplicidad.

¿Cuántos tests debo escribir?

No hay un número mágico. Una buena regla: testear el "happy path" (funcionamiento normal), un caso límite (vacío, cero, negativo), y un caso de error. Para funciones puras, esto suele ser suficiente. Para funciones que interactúan con el exterior (fetch, DOM, timers), añade tests con mocks para cada escenario posible. Prioriza testear la lógica de negocio sobre setters/getters triviales.

¿Debo mockear fetch siempre en los tests?

Sí, en tests unitarios. Las peticiones reales hacen los tests lentos, frágiles (dependes de una red externa) y no deterministas. Mockea fetch para controlar exactamente qué responde y testear cómo reacciona tu código a cada escenario: éxito, 404, 500, timeout, red caída. Para tests de integración (end-to-end), puedes usar peticiones reales contra un servidor de pruebas local.
