Módulos ES (import/export), CommonJS vs ESM

Módulo 7 · Módulos, tooling y testing ⏱ 30 minutos

1 · Introducción

Durante sus primeros 20 años, JavaScript no tuvo un sistema de módulos propio. Todo el código vivía en el ámbito global (window), compartiendo variables y colisionando nombres. Esto hacía imposible construir aplicaciones grandes sin patrones como IIFE o el Module Pattern.

La comunidad resolvió el problema con sistemas como CommonJS (Node.js) y AMD (navegadores). Finalmente, ECMAScript 2015 (ES6) introdujo el sistema de módulos nativos: ESM (ECMAScript Modules). Ya no necesitas librerías externas para organizar tu código; el propio lenguaje lo soporta.

¿Por qué módulos?

Los módulos resuelven tres problemas fundamentales: (1) encapsulación: cada archivo tiene su propio ámbito, sin contaminar el global; (2) dependencias explícitas: declaras qué importas y qué exportas, haciendo el código auto-documentado; (3) carga ordenada: el runtime sabe exactamente qué necesita cada módulo antes de ejecutarlo.

2 · Teoría

Historia: del caos global a los módulos

Antes de los módulos, el código JavaScript típico era:

<!-- Los scripts se cargaban en orden manual. Cada uno contaminaba el ámbito global. -->
<script src="jquery.js"></script>
<script src="utils.js"></script>
<script src="app.js"></script>
<!-- app.js asume que jquery.js y utils.js ya se cargaron y expusieron sus variables en window -->

Esto tenía graves problemas: orden de carga frágil, colisiones de nombres, dependencias implícitas, imposibilidad de tree-shaking.

La comunidad creó varios sistemas:

  • IIFE + Module Pattern: función autoejecutable que devuelve un objeto con la API pública. Encapsula variables privadas pero no gestiona dependencias.
  • CommonJS (CJS): require() y module.exports. Diseñado para Node.js. Síncrono: adecuado para servidor (archivos en disco), no para navegador (red).
  • AMD (Asynchronous Module Definition): para navegadores. define() con array de dependencias. Asíncrono pero verboso. RequireJS fue su implementación más popular.
  • UMD (Universal Module Definition): combinación de CJS y AMD en un mismo archivo, usando detección de entorno.
  • ESM (ECMAScript Modules): import y export. Estándar nativo desde ES2015. Soporte en navegadores desde 2018, en Node desde v12 (estable desde v14).

ESM: import y export

Named exports (exportaciones con nombre)

Cada archivo puede exportar múltiples valores con nombre. Se importan con llaves y el nombre exacto:

// 📁 math.js
export const PI = 3.14159;

export function sumar(a, b) {
  return a + b;
}

export function restar(a, b) {
  return a - b;
}

// También se pueden exportar todas juntas al final:
// export { PI, sumar, restar };

// 📁 app.js
import { PI, sumar } from './math.js'; // Importación selectiva
console.log(sumar(10, 5)); // 15
console.log(PI); // 3.14159

Alias en imports y exports

// Renombrar al importar (evitar colisiones de nombres)
import { sumar as add, PI as pi } from './math.js';
console.log(add(1, 2)); // 3

// Renombrar al exportar
const CONSTANTE_PI = 3.14;
export { CONSTANTE_PI as PI };

Default export

Cada módulo puede tener UNA exportación por defecto. Se importa sin llaves, con cualquier nombre:

// 📁 Calculadora.js
export default class Calculadora {
  sumar(a, b) { return a + b; }
  restar(a, b) { return a - b; }
}

// 📁 app.js
import Calculadora from './Calculadora.js'; // El nombre es libre, pero usa el original por convención
const calc = new Calculadora();
console.log(calc.sumar(5, 3)); // 8

Combinar default y named exports

// 📁 usuario.js
export default function crearUsuario(nombre) {
  return { nombre, id: crypto.randomUUID() };
}
export const ROLES = ['admin', 'editor', 'lector'];
export const MAX_USUARIOS = 100;

// 📁 app.js
import crearUsuario, { ROLES, MAX_USUARIOS } from './usuario.js';
// El default va primero (sin llaves), luego los named (con llaves)

Importar todo como namespace

import * as math from './math.js';
console.log(math.sumar(1, 2)); // 3
console.log(math.PI); // 3.14159
// math es un objeto Module que contiene todos los exports con nombre

Re-export (barril / barrel exports)

Patrón común para crear un punto de entrada que centralice las exportaciones de varios archivos:

// 📁 index.js — Archivo "barril"
export { sumar, restar } from './math.js';
export { default as Calculadora } from './Calculadora.js';
export * from './constantes.js'; // Re-exporta todo (cuidado con colisiones)
// export * as utils from './utils.js'; // Re-exporta todo como un namespace

import() dinámico — Code Splitting

import() como función devuelve una promesa. Permite carga perezosa (lazy loading) y división de código (code splitting):

// El módulo solo se descarga cuando se necesita
async function cargarEditor() {
  const { Editor } = await import('./editor.js');
  return new Editor();
}

document.querySelector('#btn-editar').addEventListener('click', async () => {
  const editor = await cargarEditor();
  editor.iniciar();
});

<script type="module"> en el navegador

<!-- Diferido por defecto (como defer). Se ejecuta tras parsear el HTML. -->
<script type="module">
  import { sumar } from './math.js';
  console.log(sumar(1, 2));
</script>

<!-- O enlazando a un archivo externo -->
<script type="module" src="app.js"></script>

Los scripts type="module" están en strict mode automáticamente y tienen su propio ámbito (las variables no van a window).

.mjs vs .js y package.json "type"

  • .mjs: extensión explícita para módulos ES. Node.js siempre lo trata como ESM.
  • .cjs: extensión explícita para CommonJS. Node.js siempre lo trata como CJS.
  • .js: depende de package.json. Si "type": "module", los .js son ESM. Si no, son CJS.

Diferencias clave ESM vs CommonJS

CaracterísticaESMCommonJS
Sintaxisimport / exportrequire() / module.exports
ResoluciónEstática (analizable sin ejecutar)Dinámica (require puede ir en un if)
CargaAsíncrona (navegador)Síncrona (Node)
Strict modeSiempreNo automático
this en top-levelundefinedmodule.exports
Tree-shakingSí (los bundlers eliminan exports no usados)Difícil (por ser dinámico)
Import/export vivasBindings vivos (si el exportador cambia el valor, el importador lo ve)Copia en el momento de require
ESM bindings vivos vs CJS copia

En ESM, cuando importas una variable, obtienes una referencia viva al valor del módulo exportador. Si el exportador actualiza esa variable, el importador ve el cambio automáticamente. En CJS, require() devuelve una copia del objeto en ese momento; cambios posteriores en el módulo no se reflejan. Esto hace que ESM sea más adecuado para patrones como módulos de estado compartido.

3 · Ejemplo mínimo

// 🧪 Módulo mínimo: un archivo exporta, otro importa

// 📁 saludador.js
export function saludar(nombre) {
  return `Hola, ${nombre}`;
}

export const VERSION = '1.0.0';

// 📁 app.js
import { saludar, VERSION } from './saludador.js';

console.log(saludar('Ana')); // 'Hola, Ana'
console.log(`App v${VERSION}`); // 'App v1.0.0'
<!-- index.html — cargar el entry point como módulo -->
<script type="module" src="app.js"></script>

Lo mínimo que necesitas saber:

  1. export hace que una variable, función o clase esté disponible para otros archivos.
  2. import { nombre } from './archivo.js' trae ese valor al archivo actual.
  3. Las rutas en import deben llevar extensión .js explícita en navegadores y Node ESM.
  4. En el HTML, usa <script type="module"> para indicar que es un módulo.

4 · Ejemplo real

Estructura de proyecto con barrel exports

// 📁 api/index.js — Archivo barril que centraliza todas las funciones de API
export { getUsers } from './users.js';
export { getPosts, createPost } from './posts.js';

// 📁 api/users.js
const BASE = 'https://jsonplaceholder.typicode.com';

export async function getUsers() {
  const res = await fetch(`${BASE}/users`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

// 📁 api/posts.js
const BASE = 'https://jsonplaceholder.typicode.com';

export async function getPosts(userId) {
  const url = `${BASE}/posts${userId ? `?userId=${userId}` : ''}`;
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

export async function createPost(postData) {
  const res = await fetch(`${BASE}/posts`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(postData),
  });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}
// 📁 ui/index.js — Otro barrel para componentes de UI
export { Card } from './card.js';
export { Spinner } from './spinner.js';

// 📁 ui/card.js
export function Card({ title, body }) {
  const el = document.createElement('article');
  el.className = 'card';
  el.innerHTML = `
${title}
${body}
`;
  return el;
}

// 📁 ui/spinner.js
export function Spinner() {
  const el = document.createElement('div');
  el.className = 'spinner';
  el.textContent = '⏳ Cargando...';
  return el;
}
// 📁 app.js — Entry point que consume los barrels
import { getUsers, getPosts } from './api/index.js';
import { Card, Spinner } from './ui/index.js';

async function renderDashboard() {
  const main = document.querySelector('main');
  main.appendChild(Spinner());

  try {
    const [users, posts] = await Promise.all([
      getUsers(),
      getPosts(),
    ]);

    main.innerHTML = ''; // Limpiar spinner
    users.slice(0, 5).forEach(user => {
      main.appendChild(Card({
        title: user.name,
        body: `${user.email} — ${user.company.name}`,
      }));
    });

    console.log(`📊 ${users.length} usuarios, ${posts.length} posts`);
  } catch (error) {
    main.innerHTML = `
❌ ${error.message}
`;
  }
}

renderDashboard();

Este ejemplo muestra un patrón profesional: separar la lógica de API y la UI en módulos con barrel exports. Cada archivo tiene una responsabilidad; los barrels (index.js) centralizan las exportaciones para que el consumidor (app.js) importe desde un solo punto.

6 · Errores habituales

Error 1: Olvidar que los módulos ES están en strict mode

// ❌ MAL: esto NO funciona en módulos ES (strict mode automático)
x = 42; // ReferenceError: x is not defined
console.log(x);

// ✅ CORRECTO: declarar variables
const x = 42;
console.log(x);

Error 2: Confundir export default con export con nombre

// ❌ MAL: intentar importar un default como named
// 📁 math.js
export default function sumar(a, b) { return a + b; }

// 📁 app.js
import { sumar } from './math.js'; // ❌ sumar es undefined (es default, no named)

// ✅ CORRECTO:
import sumar from './math.js'; // Sin llaves para default

Error 3: Mezclar require e import en el mismo archivo (Node)

// ❌ MAL: en Node ESM no existe require
import fs from 'fs';
const path = require('path'); // ReferenceError: require is not defined

// ✅ CORRECTO: todo con import o con createRequire
import fs from 'fs';
import path from 'path';

Error 4: Importar desde un módulo que tiene efectos secundarios sin darse cuenta

// ❌ MAL: este módulo ejecuta código al importarse (side effect)
// 📁 analytics.js
fetch('/api/track', { method: 'POST', body: JSON.stringify({ page: location.href }) });
export function trackEvent(name) { /* ... */ }

// Cada vez que alguien importa analytics, se dispara el fetch.

// ✅ CORRECTO: los módulos no deberían ejecutar side effects al importarse.
// El consumidor debería llamar explícitamente a una función init():
export function init() {
  fetch('/api/track', { method: 'POST', body: JSON.stringify({ page: location.href }) });
}
export function trackEvent(name) { /* ... */ }

7 · Ejercicio guiado

Construye una mini librería de utilidades con barrel exports

  1. Crea el módulo de strings. 
    // 📁 utils/string.js
export function capitalizar(texto) {
  return texto.charAt(0).toUpperCase() + texto.slice(1).toLowerCase();
}

export function truncar(texto, maxLength = 50) {
  if (texto.length <= maxLength) return texto;
  return texto.slice(0, maxLength - 3) + '...';
}

export function slugificar(texto) {
  return texto
    .toLowerCase()
    .trim()
    .replace(/[^\w\s-]/g, '')
    .replace(/[\s_]+/g, '-')
    .replace(/-+/g, '-');
}
  2. Crea el módulo de números. 
    // 📁 utils/number.js
export function formatearMoneda(cantidad, moneda = 'EUR') {
  return new Intl.NumberFormat('es-ES', {
    style: 'currency',
    currency: moneda,
  }).format(cantidad);
}

export function aleatorio(min, max) {
  return Math.floor(Math.random() * (max - min + 1)) + min;
}

export function clamp(valor, min, max) {
  return Math.min(Math.max(valor, min), max);
}
  3. Crea el archivo barril index.js. 
    // 📁 utils/index.js
export { capitalizar, truncar, slugificar } from './string.js';
export { formatearMoneda, aleatorio, clamp } from './number.js';
  4. Consume la librería desde app.js. 
    // 📁 app.js
import { capitalizar, slugificar, formatearMoneda, aleatorio } from './utils/index.js';

console.log(capitalizar('jAVASCRIPT')); // 'Javascript'
console.log(slugificar('¡Hola Mundo!')); // 'hola-mundo'
console.log(formatearMoneda(1234.56, 'USD')); // '1.234,56 US$'
console.log(`🎲 Dado: ${aleatorio(1, 6)}`);

8 · Reto

🎯 Crea un plugin de polyfills con carga condicional

Crea un módulo polyfills.js que exporte una función ensureSupport(features). Esta función debe comprobar si el navegador soporta ciertas APIs (Array.prototype.at, Promise.allSettled, String.prototype.replaceAll, etc.) y, si no las soporta, cargar dinámicamente con import() un módulo con el polyfill correspondiente. Si ya las soporta, la función resuelve inmediatamente.

Pistas:

  • Usa import() dinámico para cargar polyfills solo si son necesarios.
  • Cada polyfill debe estar en su propio archivo (ej: polyfills/array-at.js).
  • Usa detección de features, NO user-agent sniffing.

9 · Resumen

  • JavaScript no tuvo módulos nativos durante 20 años. CommonJS (Node) y AMD (navegadores) fueron soluciones comunitarias.
  • ESM (ES2015) aporta import / export como sistema de módulos nativo del lenguaje.
  • Named exports: múltiples por archivo. Default export: uno por archivo. Se pueden combinar.
  • Namespace imports (import * as ns) agrupan todas las exportaciones en un objeto.
  • Re-exports (export { x } from, export * from) permiten barriles (barrel exports).
  • import() dinámico devuelve una promesa; permite code splitting y lazy loading.
  • <script type="module"> activa ESM en el navegador con strict mode y ámbito propio.
  • .mjs = siempre ESM, .cjs = siempre CJS, .js = depende de "type" en package.json.
  • ESM es estático (analizable sin ejecutar, permite tree-shaking); CJS es dinámico.
  • Los bindings de ESM son vivos (referencias); CJS devuelve una copia.

10 · Preguntas frecuentes

¿Puedo usar import y require en el mismo proyecto Node.js?

Sí, pero no en el mismo archivo. Si tu package.json tiene "type": "module", todos los .js se interpretan como ESM y require no existe. Puedes usar .cjs para archivos CommonJS dentro de un proyecto ESM. Al revés, en un proyecto CJS puedes usar .mjs para archivos ESM. También existe createRequire(import.meta.url) para usar require dentro de ESM.

¿Por qué los imports de ESM llevan extensión .js?

Porque los navegadores y Node ESM no hacen "resolución de extensiones" como CommonJS. Especificar la extensión hace la resolución directa, rápida y predecible. Los bundlers (Vite, webpack) sí resuelven sin extensión durante el build, pero es buena práctica ponerla para compatibilidad con Node y navegadores en desarrollo.

¿Debo usar default export o named exports?

La comunidad se inclina hacia named exports para la mayoría de casos: son más fáciles de refactorizar, el autocompletado del editor funciona mejor, y permiten tree-shaking más efectivo. Usa default export cuando el módulo tiene un propósito único muy claro (ej: una clase principal, un componente React). Muchos equipos prohíben default exports por completo.

¿Los módulos ES se cachean?

Sí. Cada módulo se evalúa una sola vez, independientemente de cuántas veces se importe. La primera vez que se importa, se ejecuta y su resultado se cachea. Las importaciones posteriores devuelven la misma instancia del módulo. Esto es útil para singletons y estado compartido, pero peligroso si un módulo tiene side effects.
