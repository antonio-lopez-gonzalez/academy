Integración con API REST (Fetch, loading, errores)

Módulo 9 · Proyecto Final: TaskFlow Vanilla ⏱ 45 minutos

1 · Introducción

En la lección anterior TaskFlow guardaba las tareas en localStorage: la aplicación funciona, pero los datos viven en un solo navegador. Hoy vas a convertir TaskFlow en una aplicación conectada: los datos vivirán en una API REST remota, de modo que las tareas se compartan entre dispositivos y usuarios. Es el salto de "app de juguete" a "producto real".

Concretamente, en esta lección:

  • Construirás un módulo de API (src/api.js) que encapsula toda la comunicación HTTP con fetch: getTasks, createTask, updateTask, deleteTask.
  • Integrarás ese módulo con el store que ya tienes, para que las acciones (addTask, deleteTask…) sincronicen con el servidor.
  • Implementarás los estados de carga (loading), los optimistic updates (interfaz que responde al instante y se corrige si el servidor falla) y un manejo de errores robusto con reintentos y mensajes para el usuario.

Todo esto apoyándote en lo que ya viste en el Módulo 6 · Fetch API y en el async/await: ahora toca ponerlo todo junto en un proyecto real.

¿Por qué un módulo api.js separado?

Separar la "capa de red" de la "capa de estado" es una de las decisiones de arquitectura más importantes. Si un día cambias de backend (o el endpoint cambia), solo tocas api.js. El store y las vistas ni se enteran. Además, api.js se convierte en un candidato perfecto para testear con mocks (lo verás en la última lección).

2 · Teoría

Recordatorio: el contrato de una API REST

Una API REST expone recursos (aquí, /tasks) y usa los verbos HTTP para describir la operación:

Verbo HTTPEndpointAcciónFunción en TaskFlow
GET/tasksListar todas las tareasgetTasks()
POST/tasksCrear una tareacreateTask(data)
PUT / PATCH/tasks/:idActualizar una tareaupdateTask(id, updates)
DELETE/tasks/:idEliminar una tareadeleteTask(id)

Usaremos json-server como backend de desarrollo: monta una API REST real con un solo archivo db.json, perfecta para practicar sin escribir servidor. En producción lo reemplazarías por tu backend real; la interfaz de api.js no cambiaría.

El ciclo de vida de una petición: estados

Toda petición a red pasa por tres estados, y tu interfaz debe responder a cada uno:

   usuario hace clic
          │
          ▼
   ┌────────────────┐      ┌────────────────┐      ┌─────────────────┐
   │   LOADING      │ ───► │    SUCCESS     │      │     ERROR       │
   │ "Cargando..."  │      │  datos listos  │      │ "Algo falló"    │
   └────────────────┘      └────────────────┘      └─────────────────┘
          │                        │                       │
          └── spinner/skeleton ────┴── render de datos ────┴── mensaje + reintentar
  • Loading: la petición está en vuelo. Mostramos un indicador (spinner o skeleton). Sin esto, la UI "congela" y el usuario cree que se rompió.
  • Success: recibimos los datos. Los metemos en el store y renderizamos.
  • Error: la petición falló. Mostramos un mensaje claro y una opción de reintento. Nunca dejar la pantalla vacía o con datos falsos.

Optimistic updates: responder antes de que llegue el servidor

Si cada clic de "completar tarea" esperara la respuesta del servidor para actualizar la UI, la app se sentiría lenta (especialmente con latencias de red reales). La técnica profesional es el optimistic update:

  1. Actualizas el store al instante (la UI responde de inmediato, optimista).
  2. Envías la petición al servidor en segundo plano.
  3. Si el servidor confirma, no haces nada más (o reconcilas con la respuesta del servidor).
  4. Si el servidor falla, reviertes el cambio y muestras el error.

Es la técnica que usan Gmail, Todoist y Slack. Bien implementada, da una experiencia instantánea. El riesgo es la consistencia: tu UI y el servidor pueden divergir momentáneamente, así que la reversión debe ser fiable.

Manejo de errores en fetch: dos capas

Recuerda la trampa de fetch: solo rechaza la promesa en errores de red. Un 404 o 500 "resuelve" la promesa. Por eso necesitas una capa de validación:

// Capa 1: error de red (fetch rechaza) → no hay conexión, DNS, timeout
// Capa 2: error HTTP (response.ok es false) → 4xx, 5xx
// Ambas se normalizan en una excepción con mensaje legible

AbortController: cancelar peticiones

Si el usuario navega a otra vista mientras una petición está en vuelo, seguimos procesándola y quizá actualizando un store que ya no le interesa. Con AbortController puedes cancelar la petición (viste la teoría en el Módulo 6 · AbortController). Nuestro módulo API lo soportará desde el principio.

3 · Ejemplo mínimo

El núcleo de nuestra integración es un módulo api.js mínimo que envuelve fetch en helpers pequeños y reutilizables:

// src/api.js — Capa de red de TaskFlow (versión mínima)
const BASE_URL = 'http://localhost:3000';   // json-server escucha en el puerto 3000

// Helper: parsea la respuesta, lanzando un error si no es 2xx
async function handleResponse(response) {
  // fetch NO lanza errores en 404/500: lo comprobamos nosotros
  if (!response.ok) {
    // Intentamos extraer el mensaje del cuerpo, si lo hay
    const error = await response.json().catch(() => ({}));
    throw new Error(error.message || `Error ${response.status}: ${response.statusText}`);
  }
  return response.json(); // Parsear el cuerpo JSON y devolverlo
}

// GET /tasks → devuelve el array de tareas
export async function getTasks() {
  const response = await fetch(`${BASE_URL}/tasks`);
  return handleResponse(response);
}

// POST /tasks → crea una tarea y devuelve la creada (con id del servidor)
export async function createTask(taskData) {
  const response = await fetch(`${BASE_URL}/tasks`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(taskData),
  });
  return handleResponse(response);
}

// DELETE /tasks/:id → elimina la tarea
export async function deleteTask(id) {
  const response = await fetch(`${BASE_URL}/tasks/${id}`, { method: 'DELETE' });
  return handleResponse(response);
}

Fíjate en el patrón: cada función es async, delega en handleResponse y devuelve datos ya parseados. La función que llame a esto nunca ve Response ni código de estado: o recibe datos, o recibe una excepción.

¿Por qué devolver errores como excepciones?

Las excepciones propagan de forma natural: puedes try/catch en el store o en la vista, donde el usuario ve el mensaje. Si cada función devolviera {ok, data, error}, tendrías que comprobar ok en cada llamada: código repetitivo y fácil de olvidar.

4 · Ejemplo real

Versión completa de api.js con soporte de AbortController y función de utilidad para adjuntar un token de autenticación:

// src/api.js — Capa de red completa de TaskFlow
const BASE_URL = 'http://localhost:3000';

// Cabeceras por defecto: JSON y token de autorización si existe
function getHeaders() {
  return {
    'Content-Type': 'application/json',
    // Si más adelante añades login, aquí va el token:
    // Authorization: `Bearer ${localStorage.getItem('token')}`,
  };
}

// Petición genérica: recibe método, ruta, cuerpo y señal de cancelación
async function request(method, path, body, signal) {
  // fetch solo rechaza por error de red; los HTTP no-2xx se validan aquí
  const response = await fetch(`${BASE_URL}${path}`, {
    method,
    headers: getHeaders(),
    body: body ? JSON.stringify(body) : undefined, // undefined → fetch no envía body
    signal,                                        // permite cancelar desde fuera
  });

  // Respuestas 204 (sin contenido) como DELETE: no hay JSON que parsear
  if (response.status === 204) return null;

  const data = await response.json().catch(() => null);

  if (!response.ok) {
    throw new Error(data?.message || `Error ${response.status} al realizar la petición`);
  }
  return data;
}

// ===== API pública de TaskFlow =====
export function getTasks(signal) {
  return request('GET', '/tasks', null, signal);
}

export function createTask(taskData, signal) {
  return request('POST', '/tasks', taskData, signal);
}

export function updateTask(id, updates, signal) {
  return request('PATCH', `/tasks/${id}`, updates, signal);
}

export function deleteTask(id, signal) {
  return request('DELETE', `/tasks/${id}`, null, signal);
}

Integración con el store (sincronización con el servidor):

// src/store.js — Ahora las acciones sincronizan con la API
import * as api from './api.js';
import { generateId } from './utils/id.js';

function createStore(initialState = {}) {
  let state = {
    tasks: [],
    filter: 'all',
    loading: false,     // ← NUEVO: estado de carga global
    error: null,        // ← NUEVO: mensaje de error para la UI
    ...initialState,
  };

  const listeners = new Set();

  function notify() {
    listeners.forEach((fn) => fn(state));
  }

  return {
    getState() {
      return { ...state };
    },

    subscribe(fn) {
      listeners.add(fn);
      return () => listeners.delete(fn);
    },

    // Cargar todas las tareas desde el servidor (pantalla de loading)
    async loadTasks() {
      // Ponemos el estado de carga: la UI mostrará el spinner
      state = { ...state, loading: true, error: null };
      notify();

      try {
        const tasks = await api.getTasks();
        state = { ...state, tasks, loading: false };
      } catch (error) {
        // No rompemos la app: guardamos el error para mostrarlo y dejamos de cargar
        state = { ...state, loading: false, error: error.message };
      }
      notify();
    },

    // Crear tarea: optimista (aparece al instante) + confirmación del servidor
    async addTask(taskData) {
      const task = {
        id: generateId(),           // ID temporal mientras el servidor responde
        title: taskData.title,
        description: taskData.description || '',
        priority: taskData.priority || 'medium',
        completed: false,
        createdAt: new Date().toISOString(),
      };

      // 1) Update optimista: añadir YA a la UI
      state = { ...state, tasks: [...state.tasks, task], error: null };
      notify();

      try {
        // 2) Enviar al servidor; usar su respuesta como fuente de verdad
        const created = await api.createTask(task);
        state = {
          ...state,
          // Reemplazamos la tarea temporal por la real (id del servidor)
          tasks: state.tasks.map((t) => (t.id === task.id ? created : t)),
        };
      } catch (error) {
        // 3) Revertir: quitamos la tarea que no se pudo guardar
        state = {
          ...state,
          tasks: state.tasks.filter((t) => t.id !== task.id),
          error: `No se pudo guardar: ${error.message}`,
        };
      }
      notify();
    },

    // Completar/descompletar: también optimista
    async toggleTask(taskId) {
      const task = state.tasks.find((t) => t.id === taskId);
      if (!task) return;

      const optimista = { ...task, completed: !task.completed };

      state = {
        ...state,
        tasks: state.tasks.map((t) => (t.id === taskId ? optimista : t)),
      };
      notify();

      try {
        await api.updateTask(taskId, { completed: optimista.completed });
      } catch (error) {
        // Revertir al valor anterior si el servidor falla
        state = {
          ...state,
          tasks: state.tasks.map((t) => (t.id === taskId ? task : t)),
          error: error.message,
        };
        notify();
      }
    },

    // Eliminar: optimista con reversión
    async deleteTask(taskId) {
      const borrada = state.tasks.find((t) => t.id === taskId);

      state = { ...state, tasks: state.tasks.filter((t) => t.id !== taskId) };
      notify();

      try {
        await api.deleteTask(taskId);
      } catch (error) {
        // Si falla, recuperamos la tarea
        state = { ...state, tasks: [...state.tasks, borrada], error: error.message };
        notify();
      }
    },

    setFilter(filter) {
      state = { ...state, filter };
      notify();
    },
  };
}

const store = createStore();
export default store;

La vista con estados de carga y error:

// src/views/tasks.js — Vista de tareas con loading y error
import store from '../store.js';

function render() {
  const { tasks, filter, loading, error } = store.getState();

  // Estado 1: cargando
  if (loading) {
    return `
      <div class="tasks-loading" role="status" aria-live="polite">
        <span class="spinner" aria-hidden="true"></span>
        Cargando tus tareas…
      </div>`;
  }

  // Estado 2: error
  if (error) {
    return `
      <div class="tasks-error" role="alert">
        <p><strong>Ups, algo falló.</strong> <span>${error}</span></p>
        <button data-retry>Reintentar</button>
      </div>`;
  }

  // Estado 3: datos (filtrados)
  const visibles = tasks.filter((t) =>
    filter === 'all' ? true : filter === 'completed' ? t.completed : !t.completed
  );

  return `
    <ul class="task-list">
      ${visibles.map((t) => `
        <li class="task-item ${t.completed ? 'task-item--done' : ''}">
          <input type="checkbox" data-toggle="${t.id}" ${t.completed ? 'checked' : ''}>
          <span>${t.title}</span>
          <button data-delete="${t.id}" aria-label="Eliminar ${t.title}">🗑</button>
        </li>
      `).join('')}
    </ul>`;
}

// mount(): inserta la vista y conecta los eventos (una vez por visita)
export function mount(container) {
  container.innerHTML = render();

  // Delegación de eventos: un solo listener para toda la lista
  container.querySelector('.task-list')?.addEventListener('click', async (event) => {
    const toggle = event.target.closest('[data-toggle]');
    const del = event.target.closest('[data-delete]');

    if (toggle) {
      await store.toggleTask(toggle.dataset.toggle); // actualiza optimista + servidor
    } else if (del) {
      await store.deleteTask(del.dataset.delete);
    }
  });

  // Botón de reintento tras un error
  container.querySelector('[data-retry]')?.addEventListener('click', () => {
    store.loadTasks();
  });

  // Al cambiar el estado del store, volvemos a renderizar
  const unsubscribe = store.subscribe(() => {
    const next = render();
    if (container.innerHTML !== next) container.innerHTML = next;
  });

  // Primera carga de datos
  store.loadTasks();

  return unsubscribe; // el router cancela la suscripción al salir de la vista
}

Tu app (localhost:5173) pedirá datos a otra puerta (localhost:3000): eso es un cross-origin. json-server envía las cabeceras CORS necesarias por defecto, así que funciona sin configuración. Si usaras otro backend, tendrías que habilitar CORS allí (recuerda la lección de seguridad del Módulo 8).

6 · Errores habituales

Error 1: Olvidar que fetch no lanza en 404/500

// ❌ MAL: crees que un 404 lanzará una excepción
async function getTasks() {
  const response = await fetch('/tasks');
  return response.json(); // ¡404 también entra aquí! response.json() fallará
}

// ✅ CORRECTO: validar siempre
async function getTasks() {
  const response = await fetch('/tasks');
  if (!response.ok) throw new Error(`Error ${response.status}`);
  return response.json();
}

Error 2: Race conditions al cargar

// ❌ MAL: dos loadTasks simultáneos, el más lento gana con datos viejos
async function loadTasks() {
  const tasks = await api.getTasks();
  state = { ...state, tasks }; // ¿qué pasa si el usuario navegó y volvió?
}

// ✅ CORRECTO: usar un token de secuencia o el AbortController
let currentRequest = null;

async function loadTasks() {
  // Cancelamos la petición anterior antes de lanzar la nueva
  currentRequest?.abort();
  currentRequest = new AbortController();
  try {
    const tasks = await api.getTasks(currentRequest.signal);
    state = { ...state, tasks };
  } catch (error) {
    // Si fue por cancelación, no mostramos error
    if (error.name !== 'AbortError') state = { ...state, error: error.message };
  }
}

Error 3: No revertir un optimistic update fallido

// ❌ MAL: la tarea se elimina en la UI, pero el servidor la mantiene
async function deleteTask(id) {
  state = { ...state, tasks: state.tasks.filter((t) => t.id !== id) };
  notify();
  await api.deleteTask(id); // si esto lanza, la UI ya mintió
}

// ✅ CORRECTO: guardar el dato y revertir en el catch
async function deleteTask(id) {
  const borrada = state.tasks.find((t) => t.id === id);
  state = { ...state, tasks: state.tasks.filter((t) => t.id !== id) };
  notify();
  try {
    await api.deleteTask(id);
  } catch (error) {
    state = { ...state, tasks: [...state.tasks, borrada], error: error.message };
    notify();
  }
}

Error 4: Olvidar escapar el HTML de los datos del servidor

// ❌ MAL: interpolamos el título de una tarea sin escapar → vulnerabilidad XSS
// (recuerda la lección de seguridad del Módulo 8)
function renderTask(task) {
  return `<li>${task.title}</li>`; // si task.title contiene <img onerror="...">, se ejecuta
}

// ✅ CORRECTO: escapar antes de insertar en el DOM
function escapeHtml(text) {
  const div = document.createElement('div');
  div.textContent = text;          // el navegador escapa automáticamente
  return div.innerHTML;
}

function renderTask(task) {
  return `<li>${escapeHtml(task.title)}</li>`;
}

7 · Ejercicio guiado

Objetivo: añadir la vista de detalle de una tarea que carga su información desde la API (GET /tasks/:id), con loading y error.

  1. Paso 1: Añade la función a api.js

    // src/api.js — añadir junto al resto de la API pública
export function getTask(id, signal) {
  return request('GET', `/tasks/${id}`, null, signal);
}

  2. Paso 2: Crea la vista de detalle

    // src/views/task-detail.js — Muestra una tarea individual
import { getTask } from '../api.js';

export function mount(container, { id }) {
  let task = null;      // dato cargado
  let error = null;     // mensaje de error
  const controller = new AbortController(); // para cancelar al salir

  async function cargar() {
    error = null;
    task = null;                 // volvemos a estado de carga
    render();
    try {
      task = await getTask(id, controller.signal);
    } catch (e) {
      if (e.name !== 'AbortError') error = e.message;
    }
    render();
  }

  function render() {
    if (error) {
      container.innerHTML = `
        <div class="tasks-error" role="alert">
          <p>${error}</p>
          <button data-retry>Reintentar</button>
        </div>`;
      container.querySelector('[data-retry]')?.addEventListener('click', cargar);
      return;
    }
    if (!task) {
      container.innerHTML = `<p class="tasks-loading" role="status">Cargando detalle…</p>`;
      return;
    }
    container.innerHTML = `
      <article class="task-detail">
        <h2>${escapeHtml(task.title)}</h2>
        <p>${task.completed ? '✅ Completada' : '⬜ Pendiente'}</p>
        <p>${task.description ? escapeHtml(task.description) : 'Sin descripción'}</p>
        <small>Creada: ${new Date(task.createdAt).toLocaleDateString()}</small>
      </article>`;
  }

  cargar();

  // Al desmontar la vista, cancelamos la petición en vuelo
  return () => controller.abort();
}

  3. Paso 3: Conecta la ruta en el router

    // src/router.js — añadir la ruta de detalle con parámetro
import { mountTaskList } from './views/tasks.js';
import { mountTaskDetail } from './views/task-detail.js';

router.on('/tareas', () => ({
  mount(container) { return mountTaskList(container); }
}));

// Ruta con parámetro dinámico: #/tareas/abc123
router.on('/tareas/:id', (params) => ({
  mount(container) { return mountTaskDetail(container, { id: params.id }); }
}));

8 · Reto

🎯 Sincronización con reintentos y actualización en vivo

Amplía la integración de TaskFlow con estas tres mejoras profesionales:

  • Reintento con backoff: si createTask o updateTask fallan por error de red (no por 4xx), reintenta automáticamente hasta 3 veces con espera creciente (500ms → 1s → 2s). Pista: un helper retry(fn, attempts) que duplique la espera en cada intento.
  • Filtrar errores irreversibles: no reintentes errores 4xx (400, 404, 422) — son errores del cliente que nunca se resolverán reintentando. Solo reintenta 5xx y errores de red.
  • Refresco periódico: mientras la vista de tareas está montada, recarga las tareas cada 30 segundos para reflejar cambios de otros dispositivos. Pista: setInterval que llame a store.loadTasks(), y clearInterval al desmontar. Ten cuidado de no pisar ediciones locales: ¿deberías refrescar si el usuario está escribiendo?

Si lo consigues, habrás construido un cliente REST con tolerancia a fallos comparable al de productos reales.

9 · Resumen

  • Una API REST se consume con fetch: GET para leer, POST para crear, PATCH/PUT para actualizar, DELETE para borrar.
  • Aísla la red en un módulo api.js que devuelve datos o lanza excepciones legibles; las vistas nunca hablan HTTP directamente.
  • fetch no lanza en 404/500: siempre valida response.ok.
  • Toda petición pasa por tres estados — loading, success, error — y la UI debe responder a los tres.
  • Los optimistic updates dan UX instantánea: actualizar primero, enviar después y revertir si el servidor falla.
  • Usa AbortController para cancelar peticiones al cambiar de vista o evitar race conditions.
  • El servidor es la fuente de verdad: usa los ids y datos que devuelve, y escapa su contenido antes de insertarlo en el DOM.

10 · Preguntas frecuentes

¿json-server funciona para producción?

No. json-server es una herramienta de desarrollo para simular un backend real (guardar en un archivo local, sin seguridad, sin escalado). En producción usarás un backend real o un servicio Backend-as-a-Service (Supabase, Firebase, PocketBase). La gracia es que api.js no cambiaría: solo cambia BASE_URL y, quizá, las cabeceras de autenticación.

¿Cuándo conviene el update optimista y cuándo el "pessimistic"?

Optimista cuando la operación es rápida de revertir, local y de bajo riesgo (completar una tarea, dar like, mover un elemento). Pessimista (esperar al servidor) cuando la operación es crítica, irreversible o costosa de revertir (pagar, eliminar definitivamente, transferencias), o cuando necesitas los datos del servidor para continuar (crear un recurso y usar su id).

¿Cómo manejo la autenticación en las peticiones?

La práctica estándar es enviar un token en la cabecera Authorization: Bearer <token>. El token se guarda (localStorage o, mejor, una cookie HttpOnly) tras el login y getHeaders() lo adjunta automáticamente a cada petición. Ante un 401, la app suele redirigir al login. Con json-server puedes simularlo con el plugin json-server-auth.

¿Por qué mi petición falla en producción pero funciona en local?

Las causas más comunes: (1) CORS — el backend no permite tu dominio de producción; (2) la BASE_URL apunta a localhost y en producción debe ser la URL pública; (3) el backend no está desplegado o la ruta cambió; (4) el frontend se sirve desde un subdirectorio y las rutas relativas se rompen. Revisa la pestaña Network de las DevTools para ver el código de estado exacto y la cabecera CORS de la respuesta.
