Testeo, build de producción y despliegue

Módulo 9 · Proyecto Final: TaskFlow Vanilla ⏱ 50 minutos

1 · Introducción

TaskFlow ya es una SPA funcional con estado, CRUD e integración con API REST. Pero una aplicación no está terminada cuando funciona en tu máquina: está terminada cuando está verificada (los tests garantizan que no rompes nada al cambiar código) y está desplegada (los usuarios pueden acceder a ella en Internet).

Esta lección cierra el curso con el flujo profesional completo de entrega de software:

  • Testeo: escribir tests con Vitest para la lógica pura (store, api, utilidades) usando mocks para aislar la red.
  • Build de producción: entender qué hace Vite al compilar (pnpm build), qué optimiza y cómo inspeccionar el resultado.
  • Despliegue: publicar TaskFlow en una plataforma estática (Netlify o Vercel) y conectar el backend con la URL de producción.

Usarás todo lo aprendido en la lección de Vitest, en package.json y scripts, y en la lección de rendimiento. Es el momento de "vestir" el proyecto para salir a producción.

¿Por qué testear y desplegar "tanto esfuerzo"?

Un proyecto sin tests es una bomba de tiempo: cada nueva feature puede romper una antigua sin que nadie lo note. Y un proyecto sin deploy no es un proyecto, es un borrador. Este flujo — probar, compilar, desplegar — es exactamente lo que se hace en el trabajo real, y ahora tienes el control total del proceso.

2 · Teoría

¿Qué testeamos de una SPA vanilla?

La parte más valiosa de tu aplicación para testear es la lógica de datos pura: el store, las funciones de utilidad y las de la capa de API. Esta lógica no depende del DOM ni del navegador, así que se testea rápido y de forma fiable en Node. Por el contrario, el "pegado" al DOM (eventos, renderizado) se puede testear con librerías como jsdom o happy-dom, pero es más frágil y lento; lo haremos solo donde aporte valor.

CapaQué testearDónde
utils/Funciones puras (id, fechas, escapeHtml)Node (rápido, sin DOM)
store.jsAcciones: estado resultante, inmutabilidad, notificaciónNode (rápido, sin DOM)
api.jsPeticiones correctas, manejo de errores, headersNode con fetch mockeado
views/Renderizado y eventos (puntualmente)Node con happy-dom

Los tres tipos de pruebas

  • Unitarias: una función aislada (ej: escapeHtml). Es la base de la pirámide: rápidas, baratas, muchas.
  • Integración: varias piezas juntas (ej: store + api con fetch mockeado). Verifican que los módulos hablan bien entre sí.
  • E2E (end-to-end): la app completa en un navegador real (Playwright, Cypress). Poco frecuentes, caras y lentas, pero verifican el flujo completo del usuario.
              ▲
            E2E │      pocas, caras
          ┌─────┴──────┐
          │            │
        Integración    │   algunas
      ┌──┴─────────────┴──┐
      │  Unitarias (base)  │  muchas, rápidas
      └───────────────────┘
        ← Pirámide de testing →

Mocks y stubs: aislar la red

En los tests de api.js o del store no queremos hacer peticiones HTTP reales (serían lentas, frágiles y dependientes del servidor). En su lugar, mockeamos fetch: le decimos "cuando llamen a fetch, devuelve esto, sin tocar la red". Con Vitest se hace con vi.fn() y vi.stubGlobal.

Build de producción: qué hace Vite

El modo desarrollo sirve módulos sueltos tal cual para iterar rápido. El pnpm build produce la carpeta dist/ optimizada para producción:

  • Minificación: elimina espacios, comentarios y renombra variables a nombres cortos (esbuild/terser).
  • Tree shaking: elimina código que nunca se usa (si importaste una función y no la llamas, no va al bundle).
  • Code splitting: con los import() dinámicos del router, cada vista es un chunk separado que se descarga solo cuando se visita.
  • Cacheo: los archivos se nombran con hash de contenido (index-a1b2c3.js), de modo que el navegador reutiliza el caché hasta que el contenido cambie.

Despliegue: el pipeline completo

desarrollo ──► tests ──► build (dist/) ──► deploy (Netlify/Vercel)
   pnpm dev     pnpm test     pnpm build       pnpm deploy / git push

Al desplegar hay tres decisiones clave:

  • Hosting estático: TaskFlow es estática (HTML/CSS/JS), así que cualquier hosting de estáticos sirve: Netlify, Vercel, GitHub Pages. Eliges "raíz del proyecto" como base y carpeta de salida dist.
  • Variable de entorno: BASE_URL debe cambiar de localhost:3000 a la URL pública del backend. Lo correcto es usar variables de entorno (import.meta.env.VITE_API_URL) que se sustituyen en el build, no valores hardcodeados.
  • CORS: el backend debe permitir peticiones desde el dominio de producción. json-server no sirve para producción; en un backend real, configuras la lista de orígenes permitidos.

3 · Ejemplo mínimo

El test más pequeño que tiene sentido para TaskFlow: verificar una utilidad pura. Empezamos con escapeHtml, la función que evita XSS y que se usa en todas las vistas:

// src/utils/sanitize.js — nuestra función pura a testear
export function escapeHtml(text) {
  const div = document.createElement('div'); // en Node no existe document…
  div.textContent = text;                    // …así que este test necesitará happy-dom
  return div.innerHTML;
}
// tests/sanitize.test.js — el test
import { describe, it, expect } from 'vitest';
import { escapeHtml } from '../src/utils/sanitize.js';

describe('escapeHtml', () => {
  it('escapa etiquetas peligrosas', () => {
    expect(escapeHtml('<script>alert(1)</script>')).toBe(
      '&lt;script&gt;alert(1)&lt;/script&gt;'
    );
  });

  it('deja el texto normal intacto', () => {
    expect(escapeHtml('Compra pan y leche')).toBe('Compra pan y leche');
  });

  it('escapa comillas y apóstrofes', () => {
    expect(escapeHtml('"comillas" y \'apóstrofe\'')).toBe(
      '&quot;comillas&quot; y &#39;apóstrofe&#39;'
    );
  });
});

Este test usa document.createElement, así que Vitest debe ejecutarse en un entorno con DOM. Lo indicamos en el archivo de test o en la configuración:

# Instalar el entorno DOM y añadirlo a la config de Vitest
pnpm add -D happy-dom
// vite.config.js
import { defineConfig } from 'vite';

export default defineConfig({
  test: {
    environment: 'happy-dom',   // entornos: 'node' (por defecto), 'jsdom', 'happy-dom'
  },
});

4 · Ejemplo real

Tests de integración del store con el módulo API mockeado: comprobamos el comportamiento optimista y la reversión sin tocar la red.

1. Test del store: optimistic update y reversión

// tests/store.test.js — integración del store con la API mockeada
import { describe, it, expect, vi, beforeEach } from 'vitest';
import store from '../src/store.js';
import * as api from '../src/api.js';

// Mockeamos TODO el módulo api: ninguna llamada real a fetch
vi.mock('../src/api.js', () => ({
  getTasks: vi.fn(),
  createTask: vi.fn(),
  updateTask: vi.fn(),
  deleteTask: vi.fn(),
}));

describe('store.addTask (optimistic)', () => {
  beforeEach(() => {
    vi.clearAllMocks();
    // api.createTask por defecto devuelve la tarea con id de servidor
    api.createTask.mockResolvedValue({ id: 'server-1', title: 'Comprar pan', completed: false });
  });

  it('añade la tarea al instante (antes de que el servidor responda)', async () => {
    // Llamamos sin esperar aún la respuesta
    const promise = store.addTask({ title: 'Comprar pan' });

    // El estado YA contiene la tarea gracias al update optimista
    const tasks = store.getState().tasks;
    expect(tasks).toHaveLength(1);
    expect(tasks[0].title).toBe('Comprar pan');

    await promise; // ahora esperamos a que el servidor (mock) responda
  });

  it('reemplaza el id temporal por el id del servidor al confirmar', async () => {
    await store.addTask({ title: 'Comprar pan' });

    const [task] = store.getState().tasks;
    expect(task.id).toBe('server-1');
  });

  it('revierte la tarea si el servidor falla', async () => {
    // El servidor falla: la promesa se rechaza
    api.createTask.mockRejectedValue(new Error('Network down'));

    await store.addTask({ title: 'Tarea perdida' });

    // La tarea fue revertida: el estado vuelve a estar vacío
    expect(store.getState().tasks).toHaveLength(0);
    // Y guardamos el error para mostrarlo en la UI
    expect(store.getState().error).toBeTruthy();
  });
});

2. Test del api.js: headers y manejo de errores HTTP

// tests/api.test.js — api.js con fetch mockeado globalmente
import { describe, it, expect, vi, afterEach } from 'vitest';
import { getTasks, createTask } from '../src/api.js';

describe('api', () => {
  afterEach(() => {
    vi.unstubAllGlobals(); // limpia el fetch mockeado entre tests
  });

  it('getTasks hace GET a /tasks y devuelve los datos', async () => {
    // Sustituimos fetch global por un mock que devuelve una respuesta 200 con JSON
    vi.stubGlobal('fetch', vi.fn(() =>
      Promise.resolve({
        ok: true,
        json: () => Promise.resolve([{ id: '1', title: 'Tarea' }]),
      })
    ));

    const tasks = await getTasks();

    expect(fetch).toHaveBeenCalledWith(
      expect.stringContaining('/tasks'),
      expect.objectContaining({ method: 'GET' })
    );
    expect(tasks).toEqual([{ id: '1', title: 'Tarea' }]);
  });

  it('createTask envía JSON con Content-Type y body serializado', async () => {
    vi.stubGlobal('fetch', vi.fn(() =>
      Promise.resolve({ ok: true, status: 201, json: () => Promise.resolve({ id: '2' }) })
    ));

    await createTask({ title: 'Nueva' });

    const [, options] = fetch.mock.calls[0];
    expect(options.method).toBe('POST');
    expect(options.headers['Content-Type']).toBe('application/json');
    expect(JSON.parse(options.body)).toEqual({ title: 'Nueva' });
  });

  it('lanza un error claro si la respuesta no es ok (ej. 500)', async () => {
    vi.stubGlobal('fetch', vi.fn(() =>
      Promise.resolve({ ok: false, status: 500, statusText: 'Internal Server Error' })
    ));

    await expect(getTasks()).rejects.toThrow('Error 500');
  });
});

3. Build y despliegue con variable de entorno

Primero, que api.js use una variable de entorno en lugar de un valor fijo:

// src/api.js — URL configurable por entorno
// Vite sustituye import.meta.env.VITE_API_URL en el build
const BASE_URL = import.meta.env.VITE_API_URL || 'http://localhost:3000';

export function getTasks(signal) {
  return request('GET', '/tasks', null, signal);
}
// …el resto igual
# Archivo .env (raíz del proyecto) — valores locales de desarrollo
VITE_API_URL=http://localhost:3000

# Variables que empiezan por VITE_ son públicas y se incrustan en el build

Ahora el flujo completo desde la terminal:

4. Despliegue en Netlify (también sirve Vercel)

  1. Sube el código a GitHub (si no lo has hecho): git add . && git commit -m "TaskFlow v1.0" && git push.
  2. En Netlify (o Vercel), crea un "New site from Git" y conecta el repositorio.
  3. Configura el build: Build command: pnpm build, Publish directory: dist.
  4. Añade la variable de entorno VITE_API_URL con la URL pública de tu backend.
  5. Despliega. Cada git push a la rama principal re-ejecuta el build y publica automáticamente.

6 · Errores habituales

Error 1: Mockear mal — el mock "pasa" pero el código real falla

// ❌ MAL: mockear la implementación con una simplificación que no es realista
vi.mock('../src/api.js', () => ({
  getTasks: () => Promise.resolve([{ id: '1' }]), // simplista
}));
// Los tests pasan… pero no verifican el manejo de response.ok del código real

// ✅ CORRECTO: mockear SOLO fetch, dejando que api.js haga su trabajo real
vi.stubGlobal('fetch', vi.fn(() =>
  Promise.resolve({ ok: true, json: () => Promise.resolve([{ id: '1' }]) })
));
// Así testeas tu código real, no una copia idealizada de él

Error 2: Desplegar sin ejecutar los tests en CI

// ❌ MAL: solo hay "build" en el pipeline; los tests no se ejecutan
// Netlify config:  build command: pnpm build

// ✅ CORRECTO: encadenar tests + build (si los tests fallan, no se publica)
// Netlify config:  build command: pnpm test && pnpm build

Error 3: La app funciona en local pero en producción la API no responde

// ❌ MAL: BASE_URL hardcodeado a localhost

// ✅ CORRECTO: variable de entorno + fallback de desarrollo

// Y en Netlify/Vercel defines VITE_API_URL=https://api.tuapp.com

7 · Ejercicio guiado

Objetivo: añadir la cobertura de tests a la función filterTasks del store y ejecutar el flujo completo de build.

  1. Paso 1: Extrae la lógica de filtrado a una función pura

    En src/store.js, la vista filtraba las tareas en el render. Mejor extraerla a una función testeable en src/utils/filter.js:

    // src/utils/filter.js — filtrado puro, sin DOM
export function filterTasks(tasks, filter) {
  // Filtros válidos: 'all' | 'pending' | 'completed'
  switch (filter) {
    case 'pending':
      return tasks.filter((t) => !t.completed);   // solo sin completar
    case 'completed':
      return tasks.filter((t) => t.completed);    // solo completadas
    case 'all':
    default:
      return [...tasks];                            // copia, no mutamos el original
  }
}

  2. Paso 2: Escribe los tests

    // tests/filter.test.js
import { describe, it, expect } from 'vitest';
import { filterTasks } from '../src/utils/filter.js';

// Datos de ejemplo reutilizados
const tasks = [
  { id: '1', title: 'A', completed: true },
  { id: '2', title: 'B', completed: false },
  { id: '3', title: 'C', completed: false },
];

describe('filterTasks', () => {
  it('"all" devuelve todas las tareas', () => {
    expect(filterTasks(tasks, 'all')).toHaveLength(3);
  });

  it('"pending" devuelve solo las pendientes', () => {
    const result = filterTasks(tasks, 'pending');
    expect(result).toHaveLength(2);
    expect(result.every((t) => !t.completed)).toBe(true);
  });

  it('"completed" devuelve solo las completadas', () => {
    const result = filterTasks(tasks, 'completed');
    expect(result).toHaveLength(1);
    expect(result[0].id).toBe('1');
  });

  it('no muta el array original (inmutabilidad)', () => {
    const copia = [...tasks];
    filterTasks(tasks, 'pending');
    expect(tasks).toEqual(copia);
  });
});

8 · Reto

🎯 Pipeline completo y desplegado

Lleva TaskFlow a producción y añade cobertura de un caso real:

  • Despliega TaskFlow en Netlify o Vercel conectando tu repositorio, con build command pnpm test && pnpm build y la variable VITE_API_URL apuntando a tu backend desplegado (o a una API pública de prueba si no tienes backend).
  • Test de reintentos: escribe un test para tu helper retry(fn, attempts) del reto anterior (el de la lección de API REST): verifica que (a) con un fallo pasajero, reintenta y acaba teniendo éxito; (b) con fallos persistentes, agota los intentos y propaga el error; (c) no reintenta errores 4xx.
  • Inspecciona el bundle: tras pnpm build, mira la salida y comprueba que el import() dinámico del router generó chunks separados por vista. Carga la web desde una pestaña nueva, abre DevTools → Network, y verifica que solo se descargan los chunks de la vista visitada.

Cuando lo tengas desplegado, ¡tu enlace de producción es tu certificado de haber terminado el curso!

9 · Resumen

  • Pirámide de testing: muchas unitarias (rápidas), algunas de integración, pocas E2E. Testea la lógica pura donde hay más valor.
  • Mocks: aísla la red mockeando fetch con vi.fn()/vi.stubGlobal; así los tests son deterministas y rápidos.
  • El store y sus acciones optimistas son ideales para testear: se puede verificar que el estado cambia al instante y que revierte ante un fallo del servidor.
  • Build de producción: minificación, tree shaking, code splitting (chunks por import()) y hashing de cache. Lo genera pnpm build en dist/.
  • Variables de entorno: import.meta.env.VITE_API_URL configura la API por entorno sin tocar código.
  • Despliegue: hosting estático + build command pnpm test && pnpm build + dist como carpeta de publicación. Cada push vuelve a desplegar.
  • Este flujo (test → build → deploy) es el mismo ciclo profesional de entrega de software que usarás en tu carrera.

10 · Preguntas frecuentes

¿Necesito tests para TODO el código?

No. El criterio profesional es testear lo que aporta valor: lógica de negocio, funciones con condiciones y ramas, y comportamientos que se repiten o son críticos. El HTML "de plantilla" de una vista que solo interpola datos rara vez necesita tests. Un buen objetivo: alta cobertura en store, api y utils; cobertura mínima en vistas.

¿Por qué el build de producción a veces falla cuando dev funciona?

Causas típicas: (1) import.meta.env se usa fuera de Vite (p. ej. en un archivo que también se ejecuta en Node); (2) alguna dependencia se importa con una sintaxis incompatible con la minificación; (3) variables globales del navegador (window, document) que se evalúan al cargar el módulo en Node. El pnpm preview tras el build es tu red de seguridad para detectarlo antes de publicar.

¿Y si no tengo un backend real para el despliegue?

Puedes desplegar TaskFlow igualmente. Opciones: (1) usar una API de demo pública para practicar (ej. JSONPlaceholder o una similar), cambiando solo VITE_API_URL; (2) desplegar json-server en un servicio que admita Node (Render, Railway) — con cuidado de que no es seguro para datos reales; (3) migrar a un BaaS (Supabase, Firebase) que ofrece base de datos + API autogestionada. La arquitectura con api.js hace que el cambio sea mínimo.

¿Cada push de código debe re-desplegar?

En el flujo más habitual, sí: cada push a la rama principal dispara un "deploy de producción" automático. Es cómodo y rápido (los estáticos compilan en segundos). Para mayor control, se suele usar una rama main para producción y ramas feature/* con "deploy previews" (una URL temporal por PR). Esta es la práctica estándar en equipos pequeños y medianos.
