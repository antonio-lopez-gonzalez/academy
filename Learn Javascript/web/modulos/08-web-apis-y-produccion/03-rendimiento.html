Rendimiento: lazy loading, debounce/throttle, Web Workers

Módulo 8 · Web APIs y Producción ⏱ 30 minutos

1 · Introducción

JavaScript se ejecuta en un único hilo (el "main thread"). Esto significa que mientras tu código está haciendo algo — calcular, esperar, procesar — la página está congelada. El usuario no puede hacer scroll, no puede hacer clic, no puede interactuar. Literalmente congelada.

Analogía: JavaScript es como un camarero único en un restaurante. Si el camarero se pone a fregar platos durante 5 minutos, nadie puede pedir, nadie recibe su comida, y los clientes se van. El arte del rendimiento en JavaScript es asegurarse de que el camarero (el main thread) nunca esté bloqueado más de 50ms seguidos. Si una tarea va a llevar más tiempo, la delegas o la troceas en pedacitos.

En esta lección aprenderás las cuatro herramientas fundamentales del rendimiento frontend:

  • Lazy loading: no cargues lo que no se ve. Imágenes bajo demanda, componentes bajo demanda.
  • Debounce vs Throttle: controla la frecuencia con la que se ejecutan funciones disparadas por eventos rápidos (scroll, resize, input).
  • Web Workers: ejecuta JavaScript en hilos paralelos para no bloquear la interfaz.
  • Performance API: mide cuánto tardan las cosas para poder optimizarlas.

También hablaremos de requestAnimationFrame, code splitting con import() dinámico y Service Workers (una mención breve, porque merecen su propio curso).

2 · Teoría

Lazy Loading: paga solo por lo que usas

El principio es simple: si una imagen está fuera de la pantalla, ¿por qué descargarla? El lazy loading retrasa la carga de recursos hasta que el usuario está a punto de necesitarlos. Hay dos niveles:

NivelQué cargaCómo se implementa
Imágenes nativas Imágenes y iframes Atributo HTML loading="lazy" (soportado por todos los navegadores modernos desde 2022). El navegador decide cuándo cargar según la distancia al viewport.
Componentes / Contenido Secciones enteras, listas de productos, widgets Intersection Observer desde JavaScript: observas un elemento centinela y cuando entra en el viewport, cargas el contenido dinámicamente.
Código (code splitting) Módulos JavaScript completos import() dinámico: el bundler (Vite, webpack) separa el módulo en un chunk aparte que solo se descarga cuando realmente se necesita.

¿Por qué no cargar todo de golpe? Cada kilobyte de JavaScript que envías al usuario tiene un coste: tiempo de descarga (red), tiempo de parseo (CPU) y tiempo de ejecución (CPU). En móviles con conexiones lentas, cada KB adicional puede añadir decenas de milisegundos al tiempo de carga. Google descubrió que el 53% de los usuarios abandonan una web si tarda más de 3 segundos en cargar.

Debounce vs Throttle: el arte de ignorar eventos

Algunos eventos se disparan a una velocidad brutal: scroll puede dispararse cada 16ms (60 veces por segundo). resize se dispara en cada píxel que cambia la ventana. input se dispara con cada tecla pulsada. Si ejecutas lógica pesada en cada uno de estos eventos, tu app se arrastra.

Las dos técnicas para controlar esto son complementarias, NO intercambiables:

TécnicaComportamientoCuándo usarla
Debounce Espera a que el evento pare. Ejecuta la función una sola vez, cuando han pasado X ms desde la última llamada. Búsquedas en tiempo real: no quieres llamar a la API con cada tecla, solo cuando el usuario termina de escribir. Autoguardado de formularios. Validación de campos al perder el foco.
Throttle Ejecuta la función como máximo una vez cada X ms. Ignora las llamadas intermedias. Scroll: actualizar una barra de progreso o un header sticky. Resize: recalcular un layout. Movimiento del ratón: actualizar coordenadas en un canvas.

Analogía del ascensor: Debounce es como un ascensor que espera a que la gente deje de pulsar botones antes de cerrar las puertas. Si sigues pulsando, el temporizador se reinicia. Throttle es como un semáforo que cambia cada 30 segundos — da igual cuántos coches lleguen, el ritmo es fijo.

Web Workers: JavaScript multihilo

JavaScript es single-threaded... pero los Web Workers son la excepción diseñada para evitarlo. Un Worker es un archivo JavaScript que se ejecuta en un hilo del sistema operativo totalmente independiente del hilo principal. No comparten variables, no comparten scope — se comunican exclusivamente mediante mensajes (postMessage).

┌──────────────────────────────────────────────┐
│                   MAIN THREAD                 │
│  ┌─────────┐  ┌──────────┐  ┌─────────────┐  │
│  │ DOM API │  │ UI Events│  │ Renderizado  │  │
│  └─────────┘  └──────────┘  └─────────────┘  │
│          ▲                                    │
│          │ postMessage (copia de datos)       │
│          ▼                                    │
│  ┌───────────────────────────────────────┐    │
│  │            WEB WORKER                 │    │
│  │  • No puede tocar el DOM              │    │
│  │  • No puede acceder a window          │    │
│  │  • Tiene su propio scope global (self)│    │
│  │  • Puede hacer fetch, cálculos, etc.  │    │
│  └───────────────────────────────────────┘    │
└──────────────────────────────────────────────┘

Los Workers son ideales para: procesamiento de imágenes, parsing de CSV/JSON enormes, cálculos matemáticos intensivos, compresión/descompresión, cifrado, o cualquier tarea que bloquearía la UI más de 50ms.

Regla de los 50ms: Google y el estándar RAIL (Response, Animation, Idle, Load) dicen que ninguna tarea del hilo principal debe durar más de 50ms. Si tienes una tarea que tarda 120ms, muévela a un Worker. Tu usuario notará la diferencia entre una interfaz que responde instantáneamente y una que se congela durante una décima de segundo.

requestAnimationFrame (rAF)

Cuando necesitas hacer animaciones con JavaScript (no CSS), requestAnimationFrame es la herramienta correcta. A diferencia de setInterval o setTimeout, rAF se sincroniza con el ciclo de refresco de la pantalla (normalmente 60Hz = cada ~16.7ms). Si la pestaña está en segundo plano, el navegador pausa automáticamente rAF — ahorrando batería y CPU.

Performance API

No puedes optimizar lo que no mides. La Performance API te permite medir el tiempo que tardan las operaciones con precisión de microsegundos:

  • performance.now(): timestamp de alta precisión (a diferencia de Date.now(), no se ve afectado por cambios de hora del sistema).
  • performance.mark(): crea una marca con nombre en el timeline.
  • performance.measure(): calcula la distancia entre dos marcas.

3 · Ejemplo mínimo

Debounce

// Implementación desde cero: solo se ejecuta cuando los eventos paran
function debounce(fn, delay = 300) {
  let timerId;  // Guardamos el ID del timeout entre llamadas (closure)

  return function (...args) {
    // Cada vez que se llama, cancelamos el timeout anterior
    clearTimeout(timerId);
    // Y programamos uno nuevo. Si sigue llamándose, nunca llega a ejecutarse
    timerId = setTimeout(() => fn.apply(this, args), delay);
  };
}

// Uso: búsqueda que solo se dispara cuando el usuario deja de escribir
const searchInput = document.getElementById('search');
searchInput.addEventListener('input', debounce((event) => {
  console.log('Buscando:', event.target.value); // Solo se ejecuta 300ms después de la última tecla
}, 300));

Throttle

// Implementación: se ejecuta como máximo cada 'limit' ms
function throttle(fn, limit = 100) {
  let inThrottle = false; // Flag que bloquea las llamadas durante el periodo de espera

  return function (...args) {
    if (!inThrottle) {
      fn.apply(this, args);  // Ejecutar la función ahora
      inThrottle = true;     // Activar el bloqueo
      setTimeout(() => {
        inThrottle = false;  // Desbloquear tras 'limit' ms
      }, limit);
    }
    // Si inThrottle es true, simplemente ignoramos la llamada
  };
}

// Uso: actualizar posición de un elemento al hacer scroll (máx 60fps)
window.addEventListener('scroll', throttle(() => {
  console.log('Scroll position:', window.scrollY);
}, 100)); // Máximo 10 veces por segundo

Web Worker

// ===== main.js (hilo principal) =====
// Crear un worker pasándole la ruta al archivo del worker
const worker = new Worker('./heavy-task.worker.js');

// Enviar datos al worker
worker.postMessage({ numbers: [1, 2, 3, 4, 5 /* ... hasta 10 millones */] });

// Recibir el resultado (la UI sigue respondiendo mientras tanto)
worker.onmessage = (event) => {
  console.log('Resultado del worker:', event.data);
};

// ===== heavy-task.worker.js (hilo independiente) =====
self.onmessage = (event) => {
  const { numbers } = event.data;
  // Cálculo pesado que bloquearía la UI durante segundos
  const result = numbers.reduce((sum, n) => sum + n, 0);
  // Devolver resultado al hilo principal
  self.postMessage(result);
};

Performance API

// Medir cuánto tarda una operación
performance.mark('inicio-operacion');
tareaPesada(); // La función que quieres medir
performance.mark('fin-operacion');

const medida = performance.measure('duracion', 'inicio-operacion', 'fin-operacion');
console.log(`La operación tardó ${medida.duration.toFixed(2)} ms`);

// Limpiar marcas cuando ya no las necesitas
performance.clearMarks('inicio-operacion');
performance.clearMarks('fin-operacion');
performance.clearMeasures('duracion');

4 · Ejemplo real

Construyamos un buscador de productos con debounce, lazy loading de imágenes y un spinner mientras carga:

// Clase que gestiona la búsqueda con todas las técnicas de rendimiento
class ProductSearch {
  constructor(containerId) {
    this.container = document.getElementById(containerId);
    this.observer = null;     // IntersectionObserver para lazy loading
    this.controller = null;    // AbortController para cancelar peticiones
    this.setupSearchInput();
    this.setupLazyObserver();
  }

  // 1. BÚSQUEDA CON DEBOUNCE + ABORTCONTROLLER
  setupSearchInput() {
    const input = document.getElementById('search-input');
    input.addEventListener('input', this.debounce(async (event) => {
      const query = event.target.value.trim();

      if (query.length < 2) {
        this.clearResults();
        return;
      }

      // Cancelar la petición anterior si el usuario sigue escribiendo
      if (this.controller) {
        this.controller.abort(); // AbortController evita race conditions
      }
      this.controller = new AbortController();

      this.showSpinner();

      try {
        // Simulamos una API (3 segundos de latencia para ver el efecto)
        const products = await this.fetchProducts(query, this.controller.signal);
        this.renderResults(products);
      } catch (err) {
        if (err.name !== 'AbortError') {
          this.showError('Error al buscar productos');
          console.error(err);
        }
      } finally {
        this.hideSpinner();
      }
    }, 400)); // 400ms de debounce: suficiente para un escritor rápido
  }

  // 2. DEBOUNCE REUTILIZABLE
  debounce(fn, delay) {
    let timer;
    return function (...args) {
      clearTimeout(timer);
      timer = setTimeout(() => fn.apply(this, args), delay);
    };
  }

  // 3. LAZY LOADING DE IMÁGENES CON INTERSECTION OBSERVER
  setupLazyObserver() {
    this.observer = new IntersectionObserver(
      (entries) => {
        entries.forEach((entry) => {
          if (entry.isIntersecting) {
            const img = entry.target;
            // La imagen real está en data-src, no en src (ahorro de ancho de banda)
            img.src = img.dataset.src;
            img.classList.add('loaded'); // Para animación CSS de fade-in
            // Dejar de observar esta imagen — ya está cargada
            this.observer.unobserve(img);
          }
        });
      },
      {
        rootMargin: '200px', // Precarga: empieza a cargar 200px ANTES de que sea visible
        threshold: 0.01       // Basta con que un 1% sea visible
      }
    );
  }

  // 4. FETCH CON SEÑAL DE CANCELACIÓN
  async fetchProducts(query, signal) {
    const response = await fetch(
      `https://fakestoreapi.com/products?limit=10&q=${encodeURIComponent(query)}`,
      { signal } // Pasamos la señal al fetch
    );

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}: ${response.statusText}`);
    }

    return response.json();
  }

  // 5. RENDERIZADO CON LAZY IMAGES
  renderResults(products) {
    this.clearResults();

    products.forEach((product) => {
      const card = document.createElement('article');
      card.className = 'product-card';

      const img = document.createElement('img');
      img.className = 'product-image';
      img.dataset.src = product.image; // NO asignamos src aún (lazy)
      img.alt = product.title;
      img.width = 200;
      img.height = 200;
      // Placeholder mientras carga (CSS puede mostrar un fondo gris animado)
      img.src = 'data:image/svg+xml,...'; // SVG inline minúsculo como placeholder

      const title = document.createElement('h3');
      title.textContent = product.title; // textContent = seguro (anti-XSS)

      const price = document.createElement('span');
      price.textContent = `$${product.price.toFixed(2)}`;

      card.appendChild(img);
      card.appendChild(title);
      card.appendChild(price);
      this.container.appendChild(card);

      // Empezar a observar esta imagen para lazy loading
      this.observer.observe(img);
    });
  }

  showSpinner() {
    document.getElementById('spinner').style.display = 'block';
  }

  hideSpinner() {
    document.getElementById('spinner').style.display = 'none';
  }

  clearResults() {
    this.container.innerHTML = ''; // Limpiar resultados anteriores
  }

  showError(msg) {
    document.getElementById('error').textContent = msg;
  }
}

// Inicializar cuando el DOM esté listo
document.addEventListener('DOMContentLoaded', () => {
  new ProductSearch('search-results');
});

Puntos clave del ejemplo: (1) El debounce de 400ms evita llamadas a la API con cada tecla. (2) AbortController cancela la petición anterior si el usuario sigue escribiendo — evita que resultados viejos sobrescriban a los nuevos si llegan desordenados. (3) Intersection Observer con rootMargin: '200px' precarga imágenes antes de que sean visibles para que el usuario no vea un espacio en blanco. (4) Las imágenes usan data-src en lugar de src — el navegador no descarga nada hasta que el observer las activa.

5 · Buenas prácticas

HazEvitaPor qué
Debounce para búsquedas y autoguardado Disparar una petición fetch en cada evento input Con cada tecla harías una llamada a la API. Un usuario escribiendo "cafetera" generaría 8 peticiones — 7 de ellas inútiles. Con debounce, solo la última importa.
Throttle para scroll y resize Ejecutar lógica compleja en cada frame de scroll El evento scroll se dispara ~60 veces/segundo. Si tu callback tarda solo 10ms, ya estás bloqueando el 60% del tiempo de CPU solo en scroll.
Workers para cálculos > 50ms Procesar JSON de 10MB en el hilo principal Parsear o procesar datos grandes en el hilo principal congela la UI. El usuario no puede hacer scroll ni clic. Muévelo al worker y actualiza la UI solo cuando termine.
requestAnimationFrame para animaciones JS setInterval(fn, 16) para animar setInterval no se sincroniza con el refresco de pantalla, causa tearing visual y sigue ejecutándose cuando la pestaña no es visible. rAF soluciona ambos problemas.
Mide con performance.now() Medir con Date.now() o console.time Date.now() se ve afectado por cambios de hora del sistema y tiene precisión de milisegundos. performance.now() tiene precisión de microsegundos y es monotónico (siempre avanza).
Import dinámico para funcionalidad que no se usa siempre Importar todo en la cabecera del archivo Si un editor de texto enriquecido pesa 500KB y solo se usa en una vista, el 90% de los usuarios lo descargarán sin necesitarlo. const editor = await import('./editor.js') cuando el usuario haga clic en "editar".

6 · Errores habituales

Error 1: Confundir debounce con throttle

// ❌ MAL: usar debounce para scroll (nunca se ejecuta mientras el usuario scrollea)
window.addEventListener('scroll', debounce(updateProgressBar, 100));
// El debounce espera a que el evento PARE. Como el scroll nunca "para" realmente,
// la barra de progreso no se actualizará hasta que el usuario suelte el scroll.

// ✅ BIEN: throttle para scroll (actualización periódica garantizada)
window.addEventListener('scroll', throttle(updateProgressBar, 100));

// ❌ MAL: usar throttle para búsqueda (se envían peticiones mientras el usuario escribe)
searchInput.addEventListener('input', throttle(search, 300));
// Si el usuario escribe rápido, throttle enviará varias peticiones parciales.

// ✅ BIEN: debounce para búsqueda (espera a que termine de escribir)
searchInput.addEventListener('input', debounce(search, 300));

Error 2: No cancelar peticiones anteriores

// ❌ MAL: race condition — resultados pueden llegar desordenados
let currentQuery = '';
input.addEventListener('input', debounce(async (e) => {
  currentQuery = e.target.value;
  const results = await fetch(`/search?q=${currentQuery}`);
  // Si el usuario escribió "ca" → "caf" → "cafe" muy rápido, las 3 peticiones
  // se lanzan. Si la de "ca" tarda más en responder, sobrescribe los resultados correctos.
  renderResults(results);
}, 300));

// ✅ BIEN: cancelar con AbortController o verificar que la query sigue siendo la actual
let controller = null;
input.addEventListener('input', debounce(async (e) => {
  const query = e.target.value;
  controller?.abort(); // Cancelar petición anterior
  controller = new AbortController();
  try {
    const res = await fetch(`/search?q=${query}`, { signal: controller.signal });
    const results = await res.json();
    renderResults(results);
  } catch (err) {
    if (err.name !== 'AbortError') throw err; // Solo ignoramos AbortError
  }
}, 300));

Error 3: Crear un Worker por tarea pequeña

// ❌ MAL: crear un worker nuevo para cada tarea minúscula
// Crear un Worker tiene un coste de inicialización (~50-100ms). Si la tarea
// dura menos que la inicialización, estás perdiendo rendimiento.
data.forEach((item) => {
  const w = new Worker('./process.worker.js');
  w.postMessage(item);
});

// ✅ BIEN: reutilizar el mismo worker o usar un pool de workers
const worker = new Worker('./process.worker.js');
data.forEach((item) => worker.postMessage(item));

7 · Ejercicio guiado

Vamos a implementar un medidor de rendimiento para cualquier función usando la Performance API:

  1. Wrapper de medición de rendimiento:

    // Wrapper que mide cuánto tarda cualquier función en ejecutarse
function measurePerformance(fn, label = fn.name || 'anonymous') {
  return function (...args) {
    const startMark = `${label}-start`;
    const endMark = `${label}-end`;

    performance.mark(startMark);   // Marca de inicio
    const result = fn.apply(this, args);  // Ejecutar la función real
    performance.mark(endMark);     // Marca de fin

    // Medir la distancia entre marcas
    const measure = performance.measure(label, startMark, endMark);
    console.log(`⏱ ${label}: ${measure.duration.toFixed(3)} ms`);

    // Limpiar para no llenar el buffer de rendimiento
    performance.clearMarks(startMark);
    performance.clearMarks(endMark);
    performance.clearMeasures(label);

    return result;
  };
}

// Uso: envuelves cualquier función y automáticamente mides su rendimiento
const heavyCalculation = measurePerformance(function processData(n) {
  let result = 0;
  for (let i = 0; i < n; i++) {
    result += Math.sqrt(i);
  }
  return result;
}, 'heavyCalculation');

heavyCalculation(10000000); // ⏱ heavyCalculation: 45.231 ms

  2. Detector de tareas que se pasan de los 50ms:

    // Higher-order function que lanza una advertencia si la función tarda > 50ms
function warnIfSlow(fn, maxMs = 50) {
  const measured = measurePerformance(fn);

  return function (...args) {
    const start = performance.now();
    const result = measured.apply(this, args);
    const elapsed = performance.now() - start;

    if (elapsed > maxMs) {
      console.warn(
        `⚠️ ${fn.name || 'anonymous'} tardó ${elapsed.toFixed(1)}ms ` +
        `(máximo recomendado: ${maxMs}ms). Considera moverlo a un Web Worker.`
      );
    }

    return result;
  };
}

8 · Reto

🎯 Sistema de infinite scroll con métricas

Crea un componente de "feed infinito" que:

  1. Cargue elementos de una API paginada (puedes simularla con setTimeout) de 20 en 20.
  2. Use Intersection Observer para detectar cuándo el último elemento está cerca del viewport.
  3. Use throttle (no debounce) para no disparar múltiples cargas seguidas.
  4. Mida el tiempo de cada carga (performance.now()) y lo muestre en la consola.
  5. Muestre un esqueleto (skeleton screen) mientras carga la siguiente página.
  6. Si la página tarda más de 3 segundos en cargar, muestre un mensaje de "La conexión es lenta...".
  7. Permita cancelar la carga si el usuario llega al final y no hay más datos.

Pista: Combina Intersection Observer para DETECTAR cuándo cargar, throttle para LIMITAR las cargas, y AbortController para CANCELAR cargas obsoletas.

9 · Resumen

  • Lazy loading: no cargues lo que no se ve. Usa loading="lazy" para imágenes nativas e Intersection Observer para componentes bajo demanda.
  • Debounce: espera a que los eventos paren. Perfecto para búsquedas y autoguardado. La función solo se ejecuta cuando han pasado X ms sin nuevas llamadas.
  • Throttle: ejecuta como máximo cada X ms. Perfecto para scroll, resize y eventos continuos. Garantiza ejecuciones periódicas.
  • Web Workers: hilos separados para tareas pesadas. No pueden tocar el DOM. Se comunican con postMessage. Ideales para procesamiento de datos, compresión, cifrado.
  • requestAnimationFrame: para animaciones JS. Se sincroniza con el refresco de pantalla y se pausa en pestañas de fondo.
  • Performance API: performance.now() para medir tiempo con precisión. performance.mark() y performance.measure() para medir secciones de código.
  • Code splitting: import() dinámico para cargar módulos solo cuando se necesitan. Vite los separa automáticamente en chunks.
  • AbortController: cancela peticiones fetch obsoletas. Evita race conditions en búsquedas y evita trabajo innecesario.

10 · Preguntas frecuentes

¿Debounce de 300ms es siempre lo correcto?

No hay un número mágico. Depende del contexto: para búsquedas, 300-500ms es un buen equilibrio entre capacidad de respuesta y ahorro de peticiones. Para autoguardado de formularios, 1000-2000ms es aceptable. Para eventos de arrastre (drag & drop), necesitas algo mucho más bajo (16ms para 60fps) — y ahí throttle es mejor que debounce. La clave es probar con usuarios reales.

¿Cuándo NO debo usar Web Workers?

No uses Workers si: la tarea dura menos de 50ms (la creación del Worker cuesta más que la tarea), necesitas acceso al DOM (los Workers no pueden tocarlo), necesitas acceso a APIs del navegador como localStorage o cookies (no disponibles en Workers), o la tarea depende de variables del scope principal (los Workers no comparten scope).

¿Service Workers y Web Workers son lo mismo?

No. Un Service Worker es un tipo especial de Worker que actúa como proxy de red entre tu página y el servidor. Permite cacheo offline, notificaciones push y sincronización en segundo plano. Un Web Worker es para cómputo paralelo. Ambos se ejecutan en hilos separados, pero tienen propósitos y ciclos de vida completamente diferentes.

¿Vite hace code splitting automáticamente con import()?

Sí. Cuando Vite encuentra un import('./modulo.js') dinámico, automáticamente separa ese módulo (y sus dependencias no compartidas) en un chunk independiente. Ese chunk solo se descarga cuando el import() se ejecuta realmente. No necesitas configuración adicional — funciona out of the box.
