Callbacks y el problema del callback hell

Módulo 6 · Asincronía y APIs ⏱ 30 minutos

1 · Introducción

JavaScript es un lenguaje single-threaded (un solo hilo de ejecución). Esto significa que solo puede hacer una cosa a la vez. Sin embargo, el navegador y Node.js pueden realizar operaciones como leer archivos, hacer peticiones HTTP o esperar temporizadores sin bloquear el hilo principal.

La asincronía es el mecanismo que permite a JavaScript delegar tareas largas al entorno (navegador, Node) y seguir ejecutando código mientras espera. Cuando la tarea delegada termina, JavaScript recoge el resultado y lo procesa.

¿Por qué existe la asincronía en JavaScript?

Imagina que cada vez que haces una petición HTTP la página se congela durante 2 segundos. Sería una experiencia de usuario horrible. La asincronía permite que la UI siga respondiendo mientras se esperan datos del servidor.

En esta lección aprenderás el mecanismo más básico de asincronía: los callbacks. Entenderás cómo funciona el event loop, por qué surgió el temido "callback hell" y cómo usar setTimeout, setInterval y clearTimeout.

2 · Teoría

El Event Loop: la analogía del restaurante

El event loop es el mecanismo que orquesta la ejecución asíncrona en JavaScript. Vamos a entenderlo con una analogía:

🍽 La cocina de un restaurante

Imagina un restaurante con un solo cocinero (el Call Stack). El cocinero prepara platos uno a uno, sin interrupciones. Cuando un cliente pide algo que tarda mucho (como un soufflé que necesita 20 minutos de horno), el cocinero no se queda mirando el horno. Le pasa la receta al camarero (las Web APIs) y sigue con el siguiente plato. Cuando el temporizador del horno suena, el camarero pone el plato en la mesa de pedidos listos (Callback Queue). El cocinero, cuando termina lo que está haciendo, recoge el siguiente pedido de esa mesa y lo emplata.

En JavaScript esto se traduce así:

  • Call Stack: pila de ejecución. Aquí vive todo el código síncrono. Se ejecuta LIFO (Last In, First Out).
  • Web APIs / Node APIs: funciones que delega el runtime como setTimeout, fetch, fs.readFile. No son parte de JavaScript en sí, las proporciona el entorno.
  • Callback Queue (también llamada Task Queue o Macrotask Queue): cola donde las Web APIs depositan los callbacks cuando terminan su trabajo.
  • Microtask Queue: cola de prioridad más alta donde van las promesas (.then, .catch). El event loop vacía TODA la microtask queue antes de tomar una macrotask.
  • Event Loop: el bucle infinito que comprueba si el call stack está vacío. Si lo está, toma la primera tarea de la microtask queue (si hay) o de la callback queue, y la empuja al call stack.

     ┌───────────────────────────┐
     │       Call Stack          │ ← Ejecuta código síncrono (LIFO)
     │  (función actual)         │
     └──────────┬────────────────┘
                │ si está vacío...
                ▼
     ┌───────────────────────────┐
     │      Event Loop           │ ← ¿Hay algo en las colas?
     │  (bucle infinito)         │
     └───┬───────────────────┬───┘
         │                   │
         ▼                   ▼
┌─────────────────┐  ┌─────────────────┐
│ Microtask Queue │  │ Callback Queue  │ ← Macrotasks
│ (.then/catch)   │  │ (setTimeout,    │
│ (máx prioridad) │  │  eventos DOM,   │
└─────────────────┘  │  fetch resp.)   │
                     └─────────────────┘

¿Qué es un callback?

Un callback es simplemente una función que se pasa como argumento a otra función, para que esta la ejecute ("la llame de vuelta") en el momento adecuado. JavaScript nació siendo asíncrono y los callbacks fueron el primer mecanismo para manejar esa asincronía.

Los callbacks no son exclusivos de la asincronía: los métodos de arrays como map, filter y forEach también reciben callbacks, pero son síncronos. La diferencia está en cuándo se ejecuta el callback:

  • Callback síncrono: se ejecuta inmediatamente dentro de la misma función que lo recibe. Ej: [1,2,3].forEach(n => console.log(n)).
  • Callback asíncrono: se registra y se ejecuta más tarde, cuando ocurre un evento o termina una operación. Ej: setTimeout(() => console.log('tarde'), 1000).

Inversión de control (Inversion of Control)

Cuando pasas un callback a una función de terceros (una librería, una API, setTimeout), estás cediendo el control sobre cuándo y cuántas veces se ejecutará tu código. Esto se llama inversión de control y es uno de los problemas fundamentales del patrón de callbacks:

  • No sabes si el callback se ejecutará alguna vez.
  • No sabes si se ejecutará más de una vez.
  • No sabes si se ejecutará demasiado pronto o demasiado tarde.
  • No tienes control sobre el manejo de errores dentro de esa función externa.

Callback hell (Pyramid of Doom)

Cuando necesitas encadenar varias operaciones asíncronas que dependen del resultado de la anterior, los callbacks se anidan, creando una estructura indentada que recuerda a una pirámide:

// ❌ Callback hell / Pyramid of doom
obtenerUsuario(id, (error, usuario) => {
  if (error) return console.error(error);
  obtenerPedidos(usuario.id, (error, pedidos) => {
    if (error) return console.error(error);
    obtenerDetalles(pedidos[0].id, (error, detalles) => {
      if (error) return console.error(error);
      enviarEmail(usuario.email, detalles, (error, ok) => {
        if (error) return console.error(error);
        console.log('¡Todo completado!');
      });
    });
  });
});

Este patrón tiene tres problemas graves:

  1. Legibilidad: el código se hunde hacia la derecha con cada nivel de anidamiento.
  2. Manejo de errores: hay que comprobar error en cada nivel, duplicando lógica.
  3. Mantenibilidad: añadir un paso en medio o cambiar el orden requiere reindentar todo.

setTimeout y setInterval

setTimeout(callback, ms) ejecuta una función una sola vez después de que pasen los milisegundos indicados. setInterval(callback, ms) la ejecuta repetidamente cada cierto intervalo. Ambos devuelven un ID que se puede cancelar con clearTimeout(id) o clearInterval(id).

Nota importante sobre setTimeout

El tiempo indicado en setTimeout es un mínimo, no una garantía. Si el call stack está ocupado ejecutando código síncrono, el callback esperará hasta que el stack se libere. Un setTimeout(fn, 0) no ejecuta fn inmediatamente; la difiere al próximo ciclo del event loop.

3 · Ejemplo mínimo

// 🧪 Ejemplo mínimo de callback asíncrono con setTimeout

console.log('1: Inicio'); // (1) Se ejecuta primero, síncrono

setTimeout(() => {
  // (3) Este callback se ejecuta DESPUÉS de que el call stack esté vacío
  console.log('3: Han pasado al menos 2 segundos');
}, 2000);

console.log('2: Fin del código síncrono'); // (2) Se ejecuta segundo, síncrono

// Salida en consola:
// 1: Inicio
// 2: Fin del código síncrono
// 3: Han pasado al menos 2 segundos

Vamos a desglosar qué ocurre línea por línea:

  1. console.log('1: Inicio') se ejecuta inmediatamente. Se añade al call stack y se saca.
  2. setTimeout(cb, 2000) registra el callback en la Web API de temporizadores. La Web API empieza a contar 2 segundos. Mientras tanto, JavaScript sigue ejecutando lo siguiente.
  3. console.log('2: Fin...') se ejecuta inmediatamente. El call stack queda vacío.
  4. Pasan 2 segundos. La Web API empuja el callback a la Callback Queue.
  5. El event loop ve que el call stack está vacío, saca el callback de la Callback Queue y lo empuja al stack para ejecutarlo.
  6. Se ejecuta console.log('3: Han pasado...').
// Ejemplo mínimo de callback como argumento (versión síncrona)
function saludar(nombre) {
  console.log('Hola, ' + nombre);
}

function procesarUsuario(nombre, callback) {
  const nombreMayus = nombre.toUpperCase();
  callback(nombreMayus); // El callback se ejecuta de vuelta
}

procesarUsuario('ana', saludar); // → 'Hola, ANA'

4 · Ejemplo real

Simulador de descarga de archivos con callbacks

/**
 * Simula la descarga de un archivo desde un servidor.
 * Usa callbacks al estilo Node.js: el primer argumento es el error (o null).
 * Este patrón se conoce como "error-first callback".
 */
function descargarArchivo(url, callback) {
  console.log(`⬇ Iniciando descarga desde ${url}...`);

  const tiempoDescarga = Math.floor(Math.random() * 2000) + 500;

  setTimeout(() => {
    // Simulamos un 20% de probabilidad de error
    if (Math.random() < 0.2) {
      callback(new Error(`Fallo de red al descargar ${url}`), null);
      return;
    }
    const datos = `Contenido de ${url} (${tiempoDescarga}ms)`;
    callback(null, datos);
  }, tiempoDescarga);
}

/**
 * Descarga secuencial de 3 archivos con callbacks anidados.
 * Observa cómo crece la indentación — es el inicio del callback hell.
 */
function descargarTresArchivos() {
  console.log('📦 Iniciando descarga de 3 archivos...');

  descargarArchivo('/api/fotos/perfil.png', (error, archivo1) => {
    if (error) {
      console.error('❌ Fallo en archivo 1:', error.message);
      return;
    }
    console.log('✅ Archivo 1:', archivo1);

    descargarArchivo('/api/fotos/portada.png', (error, archivo2) => {
      if (error) {
        console.error('❌ Fallo en archivo 2:', error.message);
        return;
      }
      console.log('✅ Archivo 2:', archivo2);

      descargarArchivo('/api/fotos/avatar.png', (error, archivo3) => {
        if (error) {
          console.error('❌ Fallo en archivo 3:', error.message);
          return;
        }
        console.log('✅ Archivo 3:', archivo3);
        console.log('🎉 Todas las descargas completadas');
      });
    });
  });
}

descargarTresArchivos();

Este ejemplo muestra el patrón "error-first callback" típico de Node.js: la función asíncrona recibe un callback donde el primer parámetro es el error (si lo hay) y el segundo los datos. En las próximas lecciones verás cómo las promesas resuelven exactamente este problema.

Contador con setInterval y clearInterval

// Contador regresivo que se detiene automáticamente
let segundos = 10;

const id = setInterval(() => {
  console.log(`⏰ ${segundos}...`);
  segundos--;

  if (segundos < 0) {
    clearInterval(id);
    console.log('🔥 ¡Tiempo terminado!');
  }
}, 1000);

// Si quieres cancelarlo manualmente antes:
// clearInterval(id);

6 · Errores habituales

Error 1: Esperar que setTimeout sea preciso

// ❌ MAL: asumir que setTimeout(0) ejecuta el callback inmediatamente
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
// Salida real: A, C, B (no A, B, C)

// ✅ CORRECTO: entender que setTimeout(0) solo difiere
// el callback al próximo ciclo del event loop.

Error 2: Olvidar el manejo de errores en cada nivel

// ❌ MAL: error silencioso porque no se comprueba el error
leerArchivo('datos.json', (error, contenido) => {
  const datos = JSON.parse(contenido); // ¡Si error existe, contenido es undefined!
  console.log(datos.nombre);
});

// ✅ CORRECTO: comprobar siempre el error primero
leerArchivo('datos.json', (error, contenido) => {
  if (error) {
    console.error('No se pudo leer el archivo:', error.message);
    return;
  }
  const datos = JSON.parse(contenido);
  console.log(datos.nombre);
});

Error 3: Crear intervalos sin límite ni limpieza

// ❌ MAL: setInterval sin fin, nunca se limpia
setInterval(() => {
  document.querySelector('.reloj').textContent = new Date().toISOString();
}, 1000);

// ✅ CORRECTO: guardar el ID y limpiarlo cuando no sea necesario
const relojId = setInterval(() => {
  document.querySelector('.reloj').textContent = new Date().toISOString();
}, 1000);

// En un SPA, limpiarías al destruir el componente:
// window.addEventListener('beforeunload', () => clearInterval(relojId));

Error 4: Confundir callback síncrono con asíncrono

// ❌ ERROR DE CONCEPTO: pensar que forEach espera operaciones asíncronas
[1, 2, 3].forEach(async (id) => {
  const data = await fetch('/api/' + id); // ¡forEach no espera al await!
  console.log(data);
});
console.log('Terminó'); // Se imprime ANTES que los fetch terminen

// ✅ CORRECTO: usar for...of si necesitas await secuencial en bucle
async function procesarIds() {
  for (const id of [1, 2, 3]) {
    const data = await fetch('/api/' + id);
    console.log(data);
  }
  console.log('Terminó'); // Ahora sí, después de todos los fetch
}

7 · Ejercicio guiado

Crea un simulador de semáforo con callbacks y setTimeout

Vamos a construir paso a paso un semáforo que cicla entre verde (4s), amarillo (1s) y rojo (3s) usando solo callbacks y setTimeout.

  1. Define los estados del semáforo. 
    const estados = [
  { color: 'verde', duracion: 4000 },
  { color: 'amarillo', duracion: 1000 },
  { color: 'rojo', duracion: 3000 },
];
  2. Crea la función que muestra un color y programa el siguiente. 
    function mostrarColor(estado, siguienteIndice) {
  console.log(`🟢🔴🟡 Semáforo: ${estado.color.toUpperCase()}`);
  console.log(`   Esperando ${estado.duracion / 1000} segundos...`);

  // Programamos el siguiente cambio pasando el callback
  setTimeout(() => {
    const indice = siguienteIndice % estados.length;
    mostrarColor(estados[indice], indice + 1);
  }, estado.duracion);
}
  3. Inicia el semáforo. 
    // Arrancamos con el primer estado (verde)
mostrarColor(estados[0], 1);
  4. Añade la capacidad de detener el semáforo. 
    let timeoutId = null;

function mostrarColorConControl(estado, siguienteIndice) {
  console.log(`🚦 ${estado.color.toUpperCase()}`);

  timeoutId = setTimeout(() => {
    const indice = siguienteIndice % estados.length;
    mostrarColorConControl(estados[indice], indice + 1);
  }, estado.duracion);
}

function detenerSemaforo() {
  if (timeoutId !== null) {
    clearTimeout(timeoutId);
    console.log('🛑 Semáforo detenido');
  }
}

mostrarColorConControl(estados[0], 1);

// Tras 12 segundos, detenemos el semáforo
setTimeout(detenerSemaforo, 12000);

8 · Reto

🎯 Sistema de cola de tareas con rate limiting

Crea una función ejecutarEnCola(tareas, intervaloMs) que reciba un array de funciones callback y las ejecute una por una, esperando intervaloMs milisegundos entre cada una (como un rate limiter). Cada tarea debe recibir un callback que debe llamar cuando termine para pasar a la siguiente. Si una tarea falla, debe detenerse la cola y notificar el error.

Pistas:

  • Necesitarás llevar un índice de la tarea actual.
  • Cada tarea recibe un callback (error) => {} que debe invocar para señalar que terminó.
  • Usa setTimeout para esperar el intervalo entre tareas.

9 · Resumen

  • JavaScript es single-threaded pero el entorno (navegador, Node) ofrece APIs asíncronas.
  • El Event Loop coordina el Call Stack, las Web APIs, la Microtask Queue y la Callback Queue.
  • Un callback es una función que se pasa como argumento para ser ejecutada más tarde.
  • La inversión de control es el riesgo de ceder la ejecución de tu código a una función externa sin garantías de cuándo o cuántas veces se ejecutará.
  • El callback hell ocurre al anidar callbacks asíncronos secuenciales, haciendo el código ilegible y difícil de mantener.
  • setTimeout(cb, ms) ejecuta una vez; setInterval(cb, ms) ejecuta repetidamente. Ambos devuelven un ID cancelable.
  • El patrón error-first callback unifica el manejo de errores: (error, resultado) => {}.
  • Las promesas (próxima lección) nacieron para resolver los problemas del callback hell.

10 · Preguntas frecuentes

¿Por qué setTimeout(fn, 0) no ejecuta fn inmediatamente?

Porque setTimeout(fn, 0) no ejecuta el callback en el momento actual; lo registra en la Callback Queue. El event loop solo tomará ese callback cuando el call stack esté completamente vacío. Es útil para diferir código al próximo "tick" del event loop — por ejemplo, para esperar a que el DOM se haya renderizado antes de hacer una medición de layout.

¿Los callbacks siempre son asíncronos?

No. array.forEach(cb), array.map(cb) y array.filter(cb) ejecutan sus callbacks de forma síncrona. Son funciones de orden superior que iteran inmediatamente. Solo son asíncronos los callbacks que se pasan a APIs asíncronas como setTimeout, fetch, addEventListener, fs.readFile (Node), etc.

¿Debo seguir usando callbacks en código nuevo?

En general, no. Las promesas y async/await ofrecen una experiencia mucho mejor: encadenamiento plano, manejo de errores centralizado con .catch() y try/catch, y mejor legibilidad. Sin embargo, hay APIs que aún usan callbacks (como fs.readFile en Node si no usas la versión fs/promises) o addEventListener. Conócelos porque los verás en código legacy, en APIs del navegador y en entrevistas técnicas.

¿Qué diferencia hay entre la Callback Queue y la Microtask Queue?

La Microtask Queue (promesas con .then(), .catch(), .finally(), queueMicrotask(), MutationObserver) tiene mayor prioridad. El event loop vacía TODA la microtask queue antes de tomar UNA sola tarea de la Callback Queue. Esto significa que si dentro de un .then() encadenas otro .then(), ambos se ejecutarán antes que cualquier setTimeout pendiente.
