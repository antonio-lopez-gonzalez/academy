Glosario de AI-DLC

Referencia 📖 vocabulario del curso

Metodología

AI-DLC
AI-Driven Development Life Cycle. Metodología y motor de AWS Labs que convierte una petición en un ciclo de vida estructurado, con fases, etapas, agentes, gates y auditoría.
Fase
Gran división del ciclo: Initialization, Ideation, Inception, Construction y Operation. Cada fase agrupa etapas que producen artefactos relacionados.
Etapa (stage)
Unidad de trabajo dentro de una fase. Define qué se hace, qué agente lo hace, qué artefactos produce y qué revisión o gate lo cierra.
Workflow profile (scope)
Ruta predefinida de etapas para un tipo de trabajo. “Perfil” es el nombre de cara al usuario; “scope” es el nombre interno que guarda el motor. Ejemplos: classic, express, feature, enterprise, mvp, poc, bugfix, refactor, infra, security-patch, workshop.
Depth
Profundidad de la ceremonia: minimal, standard o comprehensive. Ajusta cuánto detalle y cuántas comprobaciones se exigen, sin convertir un perfil en otro.
Test strategy
Estrategia de pruebas asociada al perfil: minimal, standard o comprehensive. Determina el nivel de verificación esperado en Construction.
Review cap
Techo de revisión: adversarial, advisory o none. Limita cuánta revisión automática se ejecuta; nunca eleva una etapa por encima de lo que declara.
Adaptive composer
Agente que propone una ruta de etapas a medida cuando ningún perfil estándar encaja. La propuesta se confirma antes de empezar.

Ejecución y control

Harness
Herramienta que ejecuta el motor: Claude Code, Cursor, Kiro, Codex, opencode o Copilot. El core es el mismo; cambia el shell.
Conductor
Orquestador de AI-DLC dentro del harness. Pregunta al motor cuál es el siguiente paso, coordina a los agentes y reporta el resultado. No decide la ruta.
Agente
Rol especializado que ejecuta una etapa: product, design, delivery, architect, aws-platform, compliance, devsecops, developer, quality, pipeline-deploy, operations, más dos revisores y el composer.
Gate
Punto de decisión humana al final de una etapa. El humano aprueba, pide cambios, salta o rechaza. La decisión queda registrada; el agente no se autoaprueba.
Plan approval
Gate específico de Construction: el humano aprueba el plan de una unidad antes de que se genere el código.
Checkpoint
Verificación intermedia durante Construction. Puede incluir un comando de verificación registrado que se reutiliza en cada unidad o lote.
Unit
Unidad de trabajo en Construction. Puede construirse en orden unit-major (una unidad completa cada vez) o stage-major (todas las unidades por etapa).
Swarm
Ejecución en fan-out de varios lotes de Code Generation mediante el tool de tareas del harness. No existe un “Workflow tool” mágico: es paralelismo controlado.
Skeleton
Primera unidad construida como rebanada mínima integrada. Si está activo, se aprueba antes de continuar con las demás unidades.

Calidad y seguridad

Sensor
Check determinista sobre un artefacto: secciones requeridas, fuentes citadas, cobertura upstream, trazabilidad, linter o type-check. Es advisory salvo que el equipo lo haga bloqueante en un gate.
Guard
Comprobación determinista sobre una acción del agente, no sobre el mensaje del humano. Su rechazo nombra el siguiente paso exacto.
Guard policy
Configuración que decide cuánto se apartan los guards: strict, relaxed u off. Se puede fijar por intent o por equipo.
Fence
Barrera declarativa que limita una acción (por ejemplo, un revisor solo puede leer los artefactos de su unidad).
Human presence
Registro de que un turno proviene de una persona real. Sin presencia, un gate no puede aprobarse.
Evidencia source-bound
Hallazgo de revisión ligado a una fuente concreta del artefacto. Permite discutir el hallazgo sin depender de la memoria del agente.
Learnings
Ciclo por el que una corrección hecha durante una etapa se convierte en regla o sensor para las siguientes. Se puede activar o desactivar por perfil.

Estado y trazabilidad

Space
Espacio de trabajo lógico dentro de `aidlc/`. El espacio por defecto es `default`; se pueden crear otros y cambiar con `/aidlc space`.
Intent
Una pieza de trabajo concreta (una feature, un bugfix, una PoC). Cada intent tiene su carpeta, su estado y su auditoría.
Artifact
Documento producido por una etapa: intent statement, stakeholder map, requisitos, diseño, plan, review, etc.
aidlc-state.md
Archivo que dice dónde está el trabajo: fase, etapa, scope, aprobaciones y siguiente paso.
Audit trail
Registro de eventos del ciclo: preguntas, respuestas, aprobaciones, cambios y transiciones. Permite reconstruir qué pasó y por qué.
Review receipt
Recibo que acredita que una revisión se hizo y qué encontró. Se usa para congelar el estado revisado antes de avanzar.
Version skew
Desajuste entre la versión del motor instalada y la del proyecto. `aidlc doctor` lo detecta; `aidlc config` refresca el proyecto.

Harnesses del curso

Claude Code
Harness CLI de Anthropic. AI-DLC se instala con `aidlc config --harness claude`, vive en `.claude/` y se invoca con `/aidlc`. Tiene línea de estado propia.
Cursor
Harness IDE (y CLI `agent`). AI-DLC vive en `.cursor/`, con reglas `.mdc`, hooks y subagentes nativos. Se invoca con `/aidlc`; no tiene línea de estado, se usa `/aidlc-status`.
Config
Comando `aidlc config` que proyecta el runtime de AI-DLC en el proyecto: archivos del harness, `aidlc/`, `AGENTS.md` y `.gitignore`. Preserva lo que es del usuario.
Doctor
Comando `aidlc doctor` que comprueba instalación, proyecto, hooks y integridad. Los warnings son advisory; un `fail` trae su corrección.
Native install
Canal recomendado: instalador oficial que trae el comando `aidlc` y todos los runtimes de harness. No requiere Bun ni Node.js.
Copy channel
Canal manual: descargar el runtime versionado y copiar `runtime//` al proyecto. Requiere Bun y no instala el comando nativo.
