Instalar AI-DLC para Cursor

Módulo 3 · Cursor 🕐 35 minutos

1 · Introducción

Instalar AI-DLC en Cursor es, sobre todo, un ejercicio de respetar el orden. Primero el repositorio, después la confianza del workspace y al final la configuración. Si alteras ese orden, el sistema arranca y parece funcionar: el agente responde, las etapas se ejecutan, los artefactos se escriben. Lo que no funciona es lo invisible —el registro de aprobaciones— y eso no lo descubres hasta que necesitas reanudar el trabajo.

La proyección de Cursor es la más «nativa» de todas las que soporta AI-DLC: no usa una carpeta oculta partida ni un adaptador exótico, sino que aprovecha lo que Cursor ya entiende —reglas, agentes, skills y hooks— y coloca al lado los directorios del motor como datos inertes. Entender esa decisión te dice exactamente qué archivo es de quién.

Por qué existe esta lección

Porque el error clásico de Cursor —«apruebo y sigue pendiente»— no se arregla con un prompt, sino volviendo a la raíz: un repositorio Git, un IDE reiniciado y una carpeta de confianza. Y porque saber qué se commitea evita que el equipo reciba un .cursor/ con rutas locales.

2 · Teoría

Antes de configurar: los tres prerrequisitos

PrerrequisitoComprobaciónConsecuencia si falta
Repositorio Gitgit rev-parse --is-inside-work-treeCursor puede omitir hooks; las aprobaciones no se registran
Workspace confiadoAviso de confianza al abrir la carpetaEl agente no ejecuta herramientas del proyecto
Cursor reiniciado tras git initCerrar y volver a abrir el IDEEl proceso mantiene el estado anterior y sigue sin hooks

El tercero es el que más se olvida. git init cambia el directorio; Cursor, si ya estaba abierto, no lo detecta hasta que reinicias. La documentación de solución de problemas lo dice de forma explícita: reinicia por completo, no solo recargues la ventana.

Configurar

cd ~/proyectos/inventario
git init                      # solo si aún no es un repo
aidlc config --harness cursor --dry-run
aidlc config --harness cursor
aidlc doctor

El comando proyecta el framework dentro de .cursor/, crea o actualiza aidlc/ y escribe AGENTS.md en la raíz. Como en Claude Code, es transaccional e idempotente: puedes repetirlo tras actualizar el motor y conserva lo que hayas editado en las capas de método.

Qué escribe en .cursor/

.cursor/
├── rules/
│   ├── aidlc-onboarding.mdc      ← onboarding siempre aplicado
│   ├── <una regla permanente>    ← método base
│   └── <cuatro phase rules>      ← punteros por fase
│
├── agents/                       ← los 14 roles como subagentes nativos
├── skills/                       ← orquestador, atajos y runners de etapa
│
├── hooks.json                    ← cableado de hooks
├── hooks/                        ← adaptador que Cursor ejecuta
├── cli.json                      ← permisos de la CLI
├── mcp.json                      ← servidores MCP, si los añades
│
├── tools/                        ← datos inertes para Cursor
├── aidlc-common/
├── knowledge/
├── sensors/
└── scopes/

Cursor solo interpreta algunas subcarpetas como semántica nativa: rules/, agents/, skills/, hooks.json, hooks/, cli.json y mcp.json. Las demás —tools/, knowledge/, sensors/, scopes/— son datos que el motor lee y que Cursor ignora. Por eso conviven sin conflicto en el mismo directorio.

Reglas: el onboarding y las cuatro fases

.cursor/rules/aidlc-onboarding.mdc es la puerta de entrada. Se aplica siempre y explica al agente que existe un ciclo, dónde está el estado y cómo se invoca. Las otras cinco reglas —una permanente y cuatro de fase— son punteros: no contienen el método completo, indican dónde está y qué aplica en cada momento.

Esa economía es deliberada. Cursor carga reglas en el contexto de cada petición; meter el manual entero en una regla encarece todas las conversaciones y diluye lo importante. Si quieres añadir una práctica del equipo, va a aidlc/spaces/default/memory/team.md, que el motor lee cuando toca, no a una regla siempre activa.

hooks.json y el adaptador

Cada harness tiene su modelo de hooks. Claude Code ejecuta scripts en eventos; Cursor ofrece su propio sistema. AI-DLC resuelve la diferencia con un adaptador: hooks.json declara qué eventos interesan y hooks/ contiene el código que traduce el evento de Cursor a una operación del motor.

{
  "hooks": {
    "postToolUse": [
      { "command": "… adaptador de AI-DLC …" }
    ]
  }
}

El contenido exacto depende de la versión; lo que importa es que no lo escribas a mano. Si un hook falta o se rompe, el doctor lo detecta y aidlc config lo restaura.

Sin hooks no hay registro

El gate seguirá apareciendo en la conversación y podrás elegir «aprobar». Pero si el hook que registra la decisión no se ejecuta, el estado no avanza. Ese es el fallo silencioso que hay que saber reconocer: la aprobación se ve, no se guarda.

cli.json: permisos de la CLI

Define qué puede hacer agent sin preguntar: comandos permitidos, rutas de escritura, ejecución de herramientas. Es el equivalente al settings.json de Claude Code, con el formato de Cursor. Una política demasiado laxa convierte el agente en un proceso con permisos de shell; una demasiado estricta interrumpe cada etapa con confirmaciones.

PolíticaEfectoCuándo

EquilibradaLectura libre; escritura y comandos con aprobaciónProyectos reales con tests y revisión
RestrictivaTodo requiere confirmaciónRepositorios de terceros o auditorías

Qué comprueba el doctor en Cursor

El diagnóstico añade verificaciones específicas del harness a las generales:

  • Repositorio Git: si falla, el mensaje pide git init y reiniciar Cursor.
  • Hooks cableados: que cada hook declarado en hooks.json exista en hooks/.
  • Estructura: presencia de rules/, agents/, skills/ y del onboarding.
  • Registros: cambios sin commitear bajo aidlc/, que impiden que el equipo vea el estado.
  • Integridad: versión de la distribución frente al motor instalado.

3 · Ejemplo mínimo

De carpeta vacía a proyecto configurado, con el orden correcto.

mkdir ~/laboratorio/cursor-aidlc
cd ~/laboratorio/cursor-aidlc
git init
printf '# Laboratorio Cursor\n' > README.md
git add . && git commit -m "Initial commit"

aidlc config --harness cursor
aidlc doctor

Después, abre la carpeta en Cursor, acepta la confianza y comprueba que el agente encuentra el ciclo:

> /aidlc --status
  Espacio: default
  Intent:  (ninguno)
  Estado:  listo para inicializar

Ese «listo para inicializar» confirma tres cosas a la vez: Cursor lee las reglas, el motor encuentra el estado y el harness está correctamente proyectado.

Si /aidlc no aparece en el menú

Comprueba que estás en la raíz del workspace y que .cursor/skills/ existe. En Cursor los comandos se descubren como skills nativas; si la carpeta falta, la proyección no se completó y toca repetir aidlc config --harness cursor.

4 · Ejemplo real

El equipo de inventario ya tiene AI-DLC funcionando en Claude Code. Ahora quieren que las personas de producto, que viven en Cursor, puedan revisar y aprobar las mismas etapas. El objetivo no es duplicar el proyecto: es que aidlc/ sea el mismo.

git checkout -b chore/aidlc-cursor
aidlc config --harness cursor --dry-run
aidlc config --harness cursor
aidlc doctor
git add .cursor aidlc .gitignore aidlc.settings.json AGENTS.md
git commit -m "Set up AI-DLC para Cursor"

Lo que cambia en el repositorio:

AntesDespués
.claude/.claude/ + .cursor/
CLAUDE.mdCLAUDE.md + AGENTS.md
aidlc/ con un espacioEl mismo aidlc/, sin duplicar
Estado de una iniciativaEl mismo estado, leído por dos harnesses

La revisión del pull request se centra en dos archivos y no en cincuenta:

git diff --stat .cursor/rules .cursor/cli.json
git diff aidlc.settings.json

El primero dice qué reglas se aplican siempre y qué permisos tiene la CLI. El segundo, qué modelo usarán las etapas en ambos harnesses. Si el equipo usa modelos distintos según la herramienta, esto se convierte en una decisión que hay que escribir, no en un detalle.

La analogía del idioma compartido

Claude Code y Cursor son dos idiomas para el mismo proyecto. .claude/ y .cursor/ son los diccionarios de cada uno; aidlc/ es el acta común. Traducir el acta a cada idioma sería absurdo: se escribe una vez y cada herramienta la lee.

5 · Buenas prácticas

HazEvitaPor qué
Verificar Git, confianza y reinicio antes de configurar. Configurar y luego investigar por qué no se registra nada. Los tres prerrequisitos son baratos de comprobar y caros de diagnosticar después.
Commitear .cursor/ completo, incluidos agentes y skills. Commitear solo rules/ «porque es lo importante». Sin agentes ni skills, los subagentes y los atajos no existen en la máquina del compañero.
Revisar cli.json como parte del pull request. Aceptar la política por defecto sin mirarla. Define qué puede hacer el agente sin preguntar: es una decisión de seguridad.
Mantener un solo aidlc/ para todos los harnesses. Crear un aidlc-cursor/ aparte. Duplicar el estado rompe la trazabilidad y garantiza que las dos copias divergan.
Repetir aidlc config tras actualizar el motor. Actualizar solo el binario. La proyección y el motor deben ser de la misma release; el doctor avisa si no.

6 · Errores habituales

1. Configurar sin repositorio Git

Mal — carpeta sin git init 
cd ~/proyectos/inventario
aidlc config --harness cursor
# el doctor avisa: project is in a git repository
Bien — repositorio primero, reinicio después 
cd ~/proyectos/inventario
git init
git add . && git commit -m "Initial commit"
aidlc config --harness cursor
# cerrar Cursor por completo y volver a abrirlo

El aviso del doctor no es cosmético: sin el repositorio, los hooks pueden omitirse y las aprobaciones no quedan registradas. El síntoma aparece semanas después, cuando nadie entiende por qué el estado no avanza.

2. Copiar .cursor/ de otro proyecto

Mal — clonar la carpeta a mano 
cp -r ../otro-proyecto/.cursor .
Bien — proyectar desde el motor 
aidlc config --harness cursor

La carpeta contiene rutas, versiones y referencias al estado del otro proyecto. Copiada, produce errores que parecen del agente y son de procedencia. La proyección se genera, no se hereda.

3. Editar las reglas de .cursor/rules/ para el equipo

Mal — método en una regla siempre activa 
# .cursor/rules/aidlc-onboarding.mdc
+ Todos los cambios requieren dos aprobadores.
+ Nunca generes tests de integración.
Bien — prácticas en memory/ 
# aidlc/spaces/default/memory/team.md
- Los cambios en `src/pagos/` requieren dos aprobadores.
- Los tests de integración se escriben cuando la unidad toca la base de datos.

La regla de onboarding se reescribe al refrescar y además se carga en cada petición. Las prácticas del equipo tienen su sitio y se leen cuando corresponde.

4. Ignorar cli.json hasta que el agente hace algo inesperado

Mal — permisos implícitos 
# nadie sabe qué comandos puede ejecutar `agent`
# hasta que borra un directorio en una etapa
Bien — política escrita y revisada 
{
  "permissions": {
    "allow": ["read", "edit"],
    "ask": ["shell"]
  }
}

El formato exacto depende de la versión, pero el principio no: la política debe estar en el repositorio, revisada por alguien y alineada con lo que el equipo considera aceptable.

7 · Ejercicio guiado

Objetivo: configurar Cursor en un repositorio nuevo, verificar la estructura y comprobar que los hooks se ejecutan.

  1. Paso 1 — Repositorio y commit inicial. 
    mkdir ~/laboratorio/aidlc-cursor
cd ~/laboratorio/aidlc-cursor
git init
printf '# Lab\n' > README.md
git add . && git commit -m "Initial commit"
git rev-parse --is-inside-work-tree
  2. Paso 2 — Previsualiza y configura. 
    aidlc config --harness cursor --dry-run
aidlc config --harness cursor

    Acepta MCP solo si tienes un servidor concreto que usar. La status line no existe en Cursor, así que esa pregunta no aparecerá.

  3. Paso 3 — Inspecciona la estructura. 
    find .cursor -maxdepth 2 | sort
ls .cursor/rules
head -20 .cursor/hooks.json

    Localiza aidlc-onboarding.mdc, la carpeta agents/ y el adaptador de hooks.

  4. Paso 4 — Abre Cursor y confía. Cierra cualquier ventana previa, abre la carpeta, acepta el aviso y espera a que el agente termine de indexar. Si acabas de hacer git init, el reinicio es obligatorio.
  5. Paso 5 — Comprueba los hooks con una sesión mínima. 
    > /aidlc --status
> /aidlc --doctor

    Vuelve a ejecutar aidlc doctor en la terminal: el aviso de «hooks have not run» debe haber desaparecido.

  6. Paso 6 — Commit y verificación en limpio. 
    git add .cursor aidlc .gitignore aidlc.settings.json AGENTS.md
git commit -m "Set up AI-DLC para Cursor"
git status --short

    No debe quedar ningún *.local.json ni cursor local en el índice.

Resultado esperado

Un .cursor/ completo y versionado, /aidlc disponible en el menú y un doctor que ya no avisa de hooks sin ejecutar. Si el aviso persiste, revisa que abriste la raíz del repo y no una subcarpeta.

8 · Reto

🎯 La política de permisos del equipo

Escribe la política de cli.json que usará tu equipo y justifica cada permiso: qué puede hacer el agente sin preguntar, qué requiere confirmación y qué está prohibido. Ten en cuenta que el mismo archivo se aplica cuando alguien revisa un artefacto y cuando alguien genera código en una zona sensible.

Después simula el fallo: si mañana un agente borra un archivo de src/ sin preguntar, ¿qué regla lo permitió? ¿Cómo lo detectarías antes de que llegue a la rama principal?

Pista: no empieces por lo que quieres permitir, sino por lo irreversible. Escrituras fuera del repo, borrados, pushes y despliegues son los cuatro que necesitan respuesta explícita.

9 · Resumen

  • Orden obligatorio: Git → confianza → reinicio → aidlc config.
  • .cursor/ contiene reglas, agentes, skills, hooks, permisos y MCP; los directorios del motor conviven como datos inertes.
  • .cursor/rules/aidlc-onboarding.mdc se aplica siempre; las prácticas del equipo van a memory/.
  • hooks.json cablea los eventos y hooks/ traduce al motor: sin ellos, las aprobaciones no se registran.
  • cli.json define qué puede hacer agent sin preguntar: es una decisión de seguridad y se revisa en el PR.
  • Se commitea .cursor/, aidlc/, AGENTS.md, aidlc.settings.json y .mcp.json; nunca los *.local.json.

10 · Preguntas frecuentes

¿Puedo configurar Cursor y Claude Code en el mismo repositorio?

Sí, y es lo habitual en equipos híbridos. Cada harness tiene su carpeta de motor y ambos comparten aidlc/. Configura uno, verifica con el doctor, y luego el otro. El estado y las reglas de equipo son únicos.

¿Por qué hay carpetas dentro de .cursor/ que Cursor ignora?

Porque el motor necesita sus datos —sensores, scopes, conocimiento— y la proyección de Cursor es directa, sin una carpeta oculta separada. Cursor solo interpreta reglas, agentes, skills, hooks y permisos; el resto son datos que AI-DLC lee cuando ejecuta una etapa.

¿Debo editar hooks.json para añadir un hook propio?

Puedes, pero hazlo con cuidado y documentado: el doctor comprueba que cada hook declarado exista y aidlc config puede reescribir el archivo. Si necesitas un comportamiento nuevo, valora si corresponde a una regla de memory/ antes de tocar el cableado.

¿Qué pasa si clono el repo en otro ordenador?

Debes tener el motor instalado y Cursor autenticado. El resto viaja en el repositorio. Abre la carpeta, acepta la confianza y ejecuta aidlc doctor; si hay version skew, aidlc config --harness cursor lo resuelve.
