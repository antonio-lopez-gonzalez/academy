Estado y gates

Módulo 8 · Proyecto final 🕐 45 minutos

1 · Introducción

El corazón de aidlc-lite cabe en dos archivos: state.mjs, que decide cómo se mueve una intención, y gates.mjs, que traduce una decisión humana en avance o retención. Todo lo demás —el CLI, la auditoría, las reglas— existe alrededor de esa máquina. Si el estado se corrompe o el gate se salta, el resto del proyecto da igual.

La máquina es deliberadamente pequeña: una intención tiene un perfil con etapas, un índice de etapa actual y un estado global in_progress o completed. Aprobar avanza; rechazar mantiene la etapa y registra el motivo. No hay hilos, no hay base de datos y no hay reintentos automáticos. Esa simplicidad permite ver con claridad las decisiones que en un motor grande quedan enterradas bajo capas de abstracción.

El gate no es un booleano. gates.mjs define cuatro decisiones: approve, request_changes, skip y reject. Dos avanzan y dos retienen. El CLI solo expone approve y reject; las otras dos existen en la política y en los tests, y esa asimetría es una lección en sí misma: lo que el motor soporta y lo que la interfaz ofrece no siempre coinciden.

Por qué el estado es puro

state.mjs no lee ni escribe archivos. Recibe un objeto, lo transforma y lo devuelve. Esa pureza permite probar todos los casos límite con fechas fijas y sin tocar disco. La persistencia vive en engine.mjs, que decide cuándo guardar y cuándo auditar. Separar ambas cosas es lo que hace testeable la máquina.

La máquina en cuatro funciones

// src/state.mjs (extracto real)
export function createIntent({ profile, intent, now = new Date() }) {
  const definition = getProfile(profile);
  if (!intent || !intent.trim()) {
    throw new Error("la intención no puede estar vacía");
  }
  const timestamp = now.toISOString();
  return {
    version: 1,
    intent: intent.trim(),
    profile,
    createdAt: timestamp,
    updatedAt: timestamp,
    currentStage: 0,
    status: "in_progress",
    stages: definition.stages.map((stage, index) => ({
      ...stage,
      status: index === 0 ? "in_progress" : "pending",
      approvedAt: null,
      note: null,
    })),
    history: [],
  };
}

Crear una intención valida dos cosas antes de construir el objeto: que el perfil exista —getProfile lanza si no— y que la intención no esté vacía. El resto es derivar: la primera etapa queda in_progress, las demás pending, y el historial arranca vacío. No hay estado «inicial» separado: la primera etapa ya está activa.

export function approveCurrent(state, { note = "", now = new Date() } = {}) {
  if (state.status === "completed") {
    throw new Error("la intención ya está completada");
  }
  const stage = state.stages[state.currentStage];
  if (!stage) throw new Error("no hay una etapa activa");

  stage.status = "approved";
  stage.approvedAt = now.toISOString();
  stage.note = note || null;
  state.history.push({
    at: now.toISOString(), type: "gate.approved",
    stage: stage.id, note: note || null,
  });

  state.currentStage += 1;
  if (state.currentStage >= state.stages.length) {
    state.currentStage = state.stages.length - 1;
    state.status = "completed";
    state.stages[state.currentStage].status = "approved";
  } else {
    state.stages[state.currentStage].status = "in_progress";
  }
  state.updatedAt = now.toISOString();
  return state;
}

La aprobación tiene un caso límite importante: al aprobar la última etapa, el índice no puede avanzar fuera del array. El código lo deja en la última posición, marca el estado global como completed y vuelve a marcar la etapa como aprobada. Esa segunda marca es redundante, pero evita que un lector encuentre una etapa «aprobada» con estado global completado y otra «in_progress» residual.

export function rejectCurrent(state, { note = "", now = new Date() } = {}) {
  if (state.status === "completed") {
    throw new Error("la intención ya está completada");
  }
  const stage = state.stages[state.currentStage];
  if (!stage) throw new Error("no hay una etapa activa");

  stage.note = note || null;
  state.history.push({
    at: now.toISOString(), type: "gate.rejected",
    stage: stage.id, note: note || null,
  });
  state.updatedAt = now.toISOString();
  return state;
}

Rechazar no cambia currentStage ni el estado de la etapa: la deja activa y guarda el motivo en note. Esa es la diferencia operativa entre aprobar y rechazar en este motor: una mueve el cursor, la otra lo deja donde estaba y añade información para la siguiente iteración.

Las cuatro decisiones del gate

// src/gates.mjs (completo)
export const GATE_DECISIONS = ["approve", "request_changes", "skip", "reject"];
const ADVANCE = new Set(["approve", "skip"]);
const HOLD = new Set(["request_changes", "reject"]);

export function applyGate(state, decision, { note = "", now = new Date() } = {}) {
  if (ADVANCE.has(decision)) {
    return { state: approveCurrent(state, { note, now }), advanced: true };
  }
  if (HOLD.has(decision)) {
    return { state: rejectCurrent(state, { note, now }), advanced: false };
  }
  throw new Error(
    `decisión de gate desconocida: ${decision}. Válidas: ${GATE_DECISIONS.join(", ")}`
  );
}
DecisiónEfectoHistorialUso previsto
approveAvanza a la siguiente etapa.gate.approvedEl artefacto es aceptable.
request_changesMantiene la etapa y guarda el motivo.gate.rejectedFalta algo concreto; se corrige y se reintenta.
skipAvanza sin el artefacto.gate.approvedLa etapa no aplica o ya existe fuera del ciclo.
rejectMantiene la etapa y guarda el motivo.gate.rejectedLa propuesta no sigue por este camino.

Hay una simplificación que conviene ver: skip se registra como gate.approved y request_changes como gate.rejected. El estado distingue el efecto —avanzar o no— pero la auditoría no distingue el matiz. Si el equipo necesita saber si una etapa se aprobó o se saltó, la nota debe decirlo. Es una deuda consciente del motor didáctico que la lección de audit trail permite discutir.

El CLI solo expone dos de las cuatro

Los comandos reales son approve y reject. No hay un comando request-changes ni skip, aunque applyGate los soporte y los tests los cubran. Esa asimetría no es un olvido: el CLI prioriza el flujo más común y deja las otras decisiones como API para una extensión. Si quieres usarlas desde la terminal, tendrías que añadir el comando y su test; el motor ya está preparado.

node src/cli.mjs approve --dir .demo --note "revisado"
node src/cli.mjs reject  --dir .demo --note "faltan NFRs"
# no existe: node src/cli.mjs skip
# no existe: node src/cli.mjs request-changes

Persistencia: state.json y audit.jsonl

engine.mjs añade el evento con appendAudit y guarda el estado con saveState. El orden real es:

// src/engine.mjs (extracto de approve)
const state = loadState(dir);
const before = currentStage(state);
const result = applyGate(state, "approve", { note });
appendAudit(dir, {
  type: "gate.approved",
  intent: result.state.intent,
  stage: before?.id ?? null,
  note: note || null,
  status: result.state.status,
});
saveState(dir, result.state);
return result.state;

Se escribe primero el evento y después el estado. Si el proceso muere entre ambas operaciones, la auditoría conserva la decisión y el estado puede reconstruirse a mano; el motor didáctico no lo hace automáticamente. Un motor de producción añadiría transacción o un evento de recuperación; aquí la ventana queda visible para razonar sobre ella.

{"at":"2026-11-06T10:01:00.000Z","type":"intent.started","intent":"API de inventario","profile":"express","stages":3}
{"at":"2026-11-06T10:12:44.018Z","type":"gate.approved","intent":"API de inventario","stage":"intent","note":"ok","status":"in_progress"}
{"at":"2026-11-06T10:20:00.000Z","type":"gate.rejected","intent":"API de inventario","stage":"build","note":"faltan pruebas"}

La auditoría no tiene seq: el orden es el de las líneas. Para el proyecto didáctico es suficiente, pero significa que no puedes detectar un borrado ni ordenar eventos de forma independiente del archivo. La lección 07/04 propone cómo añadir secuencia y verificación sin cambiar el resto del motor.

Estado, historial y auditoría: tres registros

RegistroDónde viveQué guardaSe puede reconstruir
state.aidlc-lite/state.jsonFoto actual y etapas.Sí, desde historia/auditoría.
historyDentro del estadoDecisiones de esta intención.Se pierde si se edita el estado.
audit.aidlc-lite/audit.jsonlEventos append-only del proyecto.No; es la fuente.

El historial duplica parte de la auditoría. Esa duplicación es cómoda para leer el estado sin abrir dos archivos, pero también es un riesgo: si alguien edita history y no la auditoría, los dos registros discrepan. El doctor actual no compara ambos; solo valida la forma del estado. Saber qué comprueba y qué no es parte de entender el motor.

Qué valida validateState

  • Que el estado sea un objeto y tenga intent, profile, stages y currentStage.
  • Que stages sea un array no vacío y currentStage un número dentro de rango.
  • No valida que las etapas coincidan con el perfil, ni que haya una sola in_progress, ni que el historial sea coherente.

Esa validación parcial es suficiente para detectar un archivo corrupto o un índice fuera de rango, pero no para garantizar la consistencia semántica. Un motor real añadiría comprobaciones de perfil, estados permitidos por etapa y relación con la auditoría. El proyecto didáctico deja esas mejoras como extensión.

Rechazar no es retroceder

En aidlc-lite, reject mantiene la etapa actual: no vuelve a la anterior ni reinicia el perfil. Si el equipo necesita volver a una etapa previa, tendrá que crear una intención nueva o editar el estado con un evento que lo justifique. Confundir «rechazar» con «retroceder» es el error más común al leer la máquina.

3 · Ejemplo mínimo

Crear una intención express, aprobar la primera etapa y rechazar la segunda. Tres llamadas y un estado resultante.

import { createIntent } from "./src/state.mjs";
import { applyGate } from "./src/gates.mjs";

const now = new Date("2026-11-06T10:00:00Z");
const state = createIntent({ profile: "express", intent: "demo", now });

applyGate(state, "approve", { note: "ok", now });
applyGate(state, "reject", { note: "faltan pruebas", now });

console.log(state.currentStage); // 1
console.log(state.status);       // in_progress
console.log(state.stages.map((s) => s.status));
// [ "approved", "in_progress", "pending" ]
console.log(state.history.map((h) => h.type));
// [ "gate.approved", "gate.rejected" ]

Qué ha pasado:

  • createIntent dejó la etapa 0 en in_progress y las demás en pending.
  • approve marcó la etapa 0 como approved y movió el cursor a la 1.
  • reject no movió el cursor: la etapa 1 sigue in_progress y guarda la nota.
  • El historial tiene dos entradas, una por decisión, con la fecha inyectada.

Si apruebas la última etapa, el estado pasa a completed y un segundo approve lanza la intención ya está completada. Esa excepción es la garantía de que no se puede seguir avanzando después del final.

4 · Ejemplo real

El flujo completo con el CLI real sobre un perfil feature. Observa que run no ejecuta etapas: solo crea la intención y la deja en la primera. Cada aprobación es un comando humano.

node src/cli.mjs run --dir .demo --profile feature --intent "API de inventario"

# Perfil    : feature
# Estado    : in_progress
# Etapa     : intent — Intent capture (1/7)

node src/cli.mjs reject --dir .demo --note "faltan NFRs"

# Etapa     : requirements — Requirements (2/7)

node src/cli.mjs approve --dir .demo --note "NFRs añadidos"

# Etapa     : design — Design (3/7)

La auditoría correspondiente mantiene el orden real de los comandos:

{"at":"...","type":"intent.started","intent":"API de inventario","profile":"feature","stages":7}
{"at":"...","type":"gate.approved","intent":"API de inventario","stage":"intent","note":"alcance revisado","status":"in_progress"}

Hay dos detalles que un revisor atento debería ver. El primero: el evento gate.rejected no lleva status, porque reject no cambia el estado global. El segundo: la etapa rechazada conserva la nota hasta que se vuelve a aprobar; entonces approveCurrent la sobrescribe con la nueva nota. La historia completa queda en history y en la auditoría, pero la foto actual solo muestra la última nota.

La analogía del semáforo

El estado es el semáforo: dice si puedes avanzar. El gate es la mano que pulsa el botón. approve pone verde y mueve el cursor; reject deja el rojo y escribe por qué. El semáforo no decide por ti ni cambia solo porque haya pasado el tiempo.

6 · Errores habituales

1. Tratar «rechazar» como «volver atrás»

Mal — se espera retroceder 
rejectCurrent(state, { note: "faltan NFRs" });
// ❌ se asume que currentStage vuelve a 0
assert.equal(state.currentStage, 0); // el test falla si estaba en 1
Bien — rechazar mantiene la etapa 
rejectCurrent(state, { note: "faltan NFRs" });
assert.equal(state.currentStage, 1);       // sigue en requirements
assert.equal(state.status, "in_progress");
assert.equal(state.history.at(-1).type, "gate.rejected");

El motor no tiene una operación de retroceso. Si el equipo necesita volver a una etapa anterior, debe crear un intento nuevo o añadir una operación explícita con su evento. Asumir que rechazar rebobina produce tests que fallan y expectativas equivocadas.

2. Avanzar el índice sin pasar por el gate

Mal — el estado se mueve solo 
// ❌ no hay decisión, no hay historial, no hay evento
state.currentStage += 1;
state.stages[state.currentStage].status = "in_progress";
Bien — una función, un registro 
const result = applyGate(state, "approve", { note: "ok" });
appendAudit(dir, { type: "gate.approved", stage: before.id, note: "ok" });
saveState(dir, result.state);

Mutar el estado a mano rompe la relación con history y con la auditoría. Aunque el resultado parezca correcto, la decisión desaparece del registro. La regla es simple: si avanza, pasa por applyGate; si se guarda, pasa por engine.

3. Suponer que skip y request_changes quedan diferenciados en la auditoría

Mal — el tipo de evento no basta 
{"type":"gate.approved","stage":"design","note":null}
// ¿se aprobó o se saltó? La auditoría no lo dice.
Bien — la nota explicita la decisión 
{"type":"gate.approved","stage":"design","note":"skip: el diseño ya existe en ADR-07"}
{"type":"gate.rejected","stage":"build","note":"request_changes: añadir test de 409"}

El motor didáctico colapsa skip en gate.approved y request_changes en gate.rejected. Si el equipo necesita distinguirlos, la nota debe hacerlo explícito o el esquema debe evolucionar con un campo decision. Ignorar esa limitación hace que la auditoría pierda matiz.

7 · Ejercicio guiado

Objetivo: recorrer la máquina con un perfil corto, provocar los casos límite y comprobar cómo quedan el estado y la auditoría.

  1. Paso 1 — Crea una intención poc: 
    cd proyectos/aidlc-lite
node src/cli.mjs init --dir .lab
node src/cli.mjs run --dir .lab --profile poc --intent "prueba de estado"

    poc tiene tres etapas: intent, build y test. La etapa 1/3 debe ser intent.

  2. Paso 2 — Aprueba dos veces: 
    node src/cli.mjs approve --dir .lab --note "primera"
node src/cli.mjs approve --dir .lab --note "segunda"

    Tras la segunda, la etapa es test (3/3) y el estado sigue in_progress. Abre .lab/.aidlc-lite/state.json y comprueba que currentStage es 2.

  3. Paso 3 — Rechaza la última etapa: 
    node src/cli.mjs reject --dir .lab --note "falta el test de regresión"

    El estado no cambia de etapa; la nota aparece en stages[2].note y en el último elemento de history. La auditoría añade un gate.rejected sin status.

  4. Paso 4 — Aprueba la última etapa: 
    node src/cli.mjs approve --dir .lab --note "regresión añadida"
node src/cli.mjs status --dir .lab

    Ahora status debe mostrar Estado: completed y Etapa: test — Build and test (3/3). Un approve más debe fallar con «la intención ya está completada».

  5. Paso 5 — Inspecciona la auditoría: 
    cat .lab/.aidlc-lite/audit.jsonl

    Cuenta los eventos: project.initialized, intent.started, tres gate.approved y un gate.rejected. Comprueba que el orden coincide con los comandos.

  6. Paso 6 — Escribe un test de caso límite: 
    test("aprobar una intención completada falla", () => {
  const state = createIntent({ profile: "poc", intent: "demo" });
  for (let i = 0; i < state.stages.length; i += 1) approveCurrent(state);
  assert.equal(state.status, "completed");
  assert.throws(() => approveCurrent(state), /completada/);
});

Resultado esperado

Un estado con completed, un historial con las cuatro decisiones y una auditoría con el mismo orden. Si el número de eventos no cuadra con los comandos, revisa si algún comando falló antes de escribir.

8 · Reto

🎯 El gate que se puede auditar

El estado actual no guarda quién aprobó ni qué decisión exacta se tomó: solo el tipo gate.approved o gate.rejected. skip y request_changes se confunden con las decisiones principales. El equipo quiere poder responder «quién aprobó la etapa 3, cuándo y con qué decisión» sin abrir el historial del chat.

Diseña el cambio: ¿añades actor, decision y gateId al historial, a la auditoría o a ambos? ¿Cómo migras los estados existentes sin romper validateState? ¿Qué pasa con los eventos antiguos que no tienen esos campos? ¿Cómo evitas que el CLI acepte un --actor inventado? ¿Qué test demuestra que skip y request_changes ya no se confunden?

Pista: el actor no puede ser un flag libre; si el CLI lo acepta, cualquiera puede escribir cualquier nombre. En un motor real vendría de la identidad del proceso o de una configuración firmada. Para el proyecto didáctico, al menos haz que sea obligatorio, que no pueda ser «agent» y que quede en el evento además de en el estado.

9 · Resumen

  • state.mjs es una máquina pura: crea, aprueba, rechaza y valida sin tocar disco.
  • El estado guarda intención, perfil, índice de etapa, estado global, etapas e historial.
  • approveCurrent avanza; en la última etapa marca completed y no permite avanzar más.
  • rejectCurrent mantiene la etapa activa y registra el motivo; no retrocede.
  • gates.mjs define cuatro decisiones: approve, request_changes, skip y reject; el CLI solo expone dos.
  • skip se registra como aprobación y request_changes como rechazo: el matiz debe ir en la nota.
  • validateState comprueba forma y rango, no la coherencia semántica con el perfil ni la auditoría.

createIntentCrea la intención y activa la primera etapa.intent.started
approveCurrentAvanza o completa.gate.approved
rejectCurrentMantiene la etapa y guarda nota.gate.rejected

10 · Preguntas frecuentes

¿Por qué el CLI no tiene un comando para skip?

Porque el flujo más común es aprobar o rechazar, y el proyecto prefiere una interfaz pequeña a una completa. applyGate ya soporta skip y los tests lo cubren; añadir el comando es una extensión de una línea en el switch y su test. Lo importante es que el motor no confunda «saltar» con «aprobar» al registrar.

¿Se puede reanudar después de cerrar la terminal?

Sí. El estado está en .aidlc-lite/state.json y la auditoría en audit.jsonl. Al ejecutar status o approve, el motor lee el archivo y continúa desde la etapa actual. No hay estado en memoria que se pierda.

¿Qué pasa si el estado y la auditoría no coinciden?

El motor actual no lo detecta automáticamente: doctor valida la forma del estado y cuenta eventos, pero no compara la secuencia. Si sospechas una inconsistencia, revisa state.json y audit.jsonl a mano. Una mejora razonable es añadir un seq y una comprobación de continuidad, como se propone en la lección de audit trail.
