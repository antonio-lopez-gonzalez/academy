Pruebas y operación

Módulo 8 · Proyecto final 🕐 40 minutos

1 · Introducción

aidlc-lite tiene cuarenta tests y ningún framework. Se ejecutan con node --test, usan node:test y node:assert/strict, y cubren desde la máquina de estados hasta el CLI como proceso. Esa elección no es minimalismo por moda: es la forma de que el proyecto se pueda ejecutar y entender sin instalar nada.

Las pruebas de este proyecto no comprueban que el código «parezca correcto». Fijan el contrato: qué pasa al aprobar la última etapa, qué devuelve doctor cuando falta una proyección, qué código de salida tiene sensors cuando encuentra hallazgos. Son la especificación ejecutable de la mecánica que has estudiado en los seis módulos anteriores.

La operación también es parte del proyecto. Un motor que solo funciona en la máquina de quien lo escribió no enseña nada: hay que poder inicializarlo en un directorio limpio, ejecutar el flujo, diagnosticarlo y recuperarlo. Eso es lo que separa un ejercicio de un artefacto que otra persona puede usar.

Los tests son la documentación que no miente

Un README puede quedar desactualizado; un test que pasa fija el comportamiento actual. Si mañana alguien cambia reject para que retroceda, el test de state.mjs fallará y la discusión será sobre el contrato, no sobre una impresión. En un motor de proceso, esa precisión es el producto.

2 · Teoría

Qué cubre cada archivo de test

ArchivoQué fijaTipo
test/state.test.mjsCreación, avance, rechazo, fin de intención y validación.Unitario puro
test/gates.test.mjsLas cuatro decisiones y el error ante una desconocida.Unitario puro
test/profiles.test.mjsLos once perfiles, sus etapas y el error de perfil desconocido.Unitario puro
test/rules.test.mjsFusión, orden, fuentes, valores por defecto y validación.Integración con disco
test/projection.test.mjsMarcadores, idempotencia, contenido del usuario y frontmatter.Integración con disco
test/sensors.test.mjsSecciones, placeholders y longitud mínima.Unitario puro
test/engine.test.mjsInit, run, status, approve, reject, sync y doctor.Integración con directorio temporal
test/cli.test.mjsAyuda, perfiles, flujo completo y errores de uso.Extremo a extremo con proceso

La proporción es sana: la mayor parte de las pruebas son unitarias y rápidas; las de integración usan directorios temporales; solo el CLI se lanza como proceso. Si todas fueran extremo a extremo, la suite tardaría y los fallos serían difíciles de localizar. Si todas fueran unitarias, nadie probaría que las piezas encajan.

Tres niveles, tres costes

unitario puro          state · gates · profiles · sensors
   │                    sin disco, sin proceso, milisegundos
   ▼
integración            rules · projection · engine
   │                    mkdtemp + fs real, decenas de milisegundos
   ▼
extremo a extremo      cli con execFileSync
                        proceso Node, salida y exit code

El nivel no es una jerarquía de calidad: es una herramienta. Un test unitario de createIntent no demuestra que el CLI arranque; un test de CLI no demuestra que la máquina de estados maneje la última etapa. Cada nivel cubre lo que el otro no puede ver.

Determinismo: reloj, disco y rutas

Los tres enemigos de una suite estable son el reloj, el estado compartido y las rutas relativas. El proyecto los ataca así:

  • Reloj inyectado — createIntent, approveCurrent, rejectCurrent y applyGate aceptan now. Los tests pasan una fecha fija y no comparan contra Date.now().
  • Directorios temporales — cada test de integración crea su propio mkdtempSync(path.join(os.tmpdir(), "aidlc-...")). Nada se escribe en el repositorio ni se comparte entre pruebas.
  • Rutas absolutas — los tests de CLI resuelven projectRoot desde import.meta.url y pasan cwd explícito a execFileSync.
// test/engine.test.mjs (extracto real)
function tempDir() {
  return fs.mkdtempSync(path.join(os.tmpdir(), "aidlc-engine-"));
}

test("run crea una intención y status la muestra", () => {
  const dir = tempDir();
  initProject(dir, { harnesses: "claude" });
  startIntent(dir, { profile: "feature", intent: "API de inventario" });
  const current = status(dir);
  assert.equal(current.profile, "feature");
  assert.equal(current.stage, "intent");
  assert.equal(current.done, 0);
  assert.equal(current.total, 7);
  assert.equal(current.pendingGate, true);
});

Ese test crea un proyecto completo en un directorio temporal, arranca una intención y consulta el estado. No toca el .aidlc-lite/ del repositorio ni depende de que exista una demo previa. Es la diferencia entre una prueba y una receta que solo funciona en una máquina.

El contrato de códigos de salida

CódigoSignificadoEjemplo
0Éxito.status, approve, doctor sin problemas.
1Error de uso, validación o diagnóstico.Perfil desconocido, falta --intent, doctor con problemas.
2Los sensores encontraron hallazgos.sensors --artifact con secciones ausentes.

El código 2 es deliberado: un hallazgo de sensor no es un fallo del programa, es un resultado que el pipeline debe poder distinguir de un error de configuración. Si el CI trata cualquier código distinto de cero como «roto», perderá esa distinción. Lo correcto es decidir por código: 0 sigue, 1 falla, 2 revisa o falla según la política del equipo.

// src/cli.mjs (extracto real)
case "sensors": {
  const report = runSensors(path.resolve(flags.artifact));
  for (const finding of report.findings) {
    console.log(`  ! ${finding.code}: ${finding.message}`);
  }
  console.log(`${report.ok ? "✓" : "!"} sensors: ${report.findings.length} hallazgos`);
  return report.ok ? 0 : 2;
}

Cómo se prueba el CLI

El test de extremo a extremo no importa main ni simula process.argv: lanza el proceso real con execFileSync. Eso incluye el parseo de argumentos, la salida y el código de salida, que es exactamente lo que usa una persona o un pipeline.

// test/cli.test.mjs (extracto real)
const projectRoot = path.resolve(path.dirname(fileURLToPath(import.meta.url)), "..");
const cli = path.join(projectRoot, "src", "cli.mjs");

function run(args, cwd = projectRoot) {
  return execFileSync(process.execPath, [cli, ...args], {
    cwd,
    encoding: "utf8",
    stdio: ["ignore", "pipe", "pipe"],
  });
}

test("flujo init -> run -> status -> approve -> doctor", () => {
  const dir = tempDir();
  run(["init", "--dir", dir, "--harness", "both"]);
  run(["run", "--dir", dir, "--profile", "express", "--intent", "demo"]);
  assert.match(run(["status", "--dir", dir]), /intent — Intent capture/);
  run(["approve", "--dir", dir, "--note", "ok"]);
  assert.match(run(["status", "--dir", dir]), /build — Code generation/);
  assert.match(run(["doctor", "--dir", dir]), /0 problemas/);
});

El test usa un directorio temporal y pasa --dir en cada comando. No depende del directorio de trabajo del proceso ni de un estado previo. La comprobación de la salida es por expresión regular, no por igualdad exacta: así el test no se rompe si cambia un espacio, pero sí si cambia la etapa.

Ejecutar la suite

cd proyectos/aidlc-lite
npm test
# ✔ crea una intención con la primera etapa en curso
# ✔ aprobar avanza a la siguiente etapa
# ...
# tests 40 · pass 40 · fail 0

npm test ejecuta node --test, que descubre los archivos *.test.mjs bajo test/. No hay configuración de Jest, Vitest ni ts-node. Si un test falla, el runner muestra el archivo, la línea y la aserción; no hay que interpretar una salida de framework.

Operación del motor: el runbook mínimo

  1. Instalar — Node.js 22 LTS. No hay npm install porque no hay dependencias.
  2. Inicializar — node src/cli.mjs init --dir <proyecto> --harness both. Crea configuración, reglas y proyecciones.
  3. Arrancar una intención — run --profile <perfil> --intent "<texto>". El perfil debe existir; profiles los lista.
  4. Operar — status para leer, approve o reject para decidir. Cada decisión es un comando humano.
  5. Reproyectar — tras editar rules/, ejecutar sync. Sin sync, las proyecciones quedan obsoletas.
  6. Diagnosticar — doctor antes de cerrar una sesión y en CI. Código 1 si hay problemas.
  7. Comprobar artefactos — sensors --artifact <ruta>. Código 2 si hay hallazgos.

El runbook no menciona ningún servicio externo, ninguna credencial y ningún despliegue. Es un motor local: su operación es ejecutarlo, leer su estado y reparar su estructura. Si algo falla, el diagnóstico está en state.json, audit.jsonl y la salida de doctor.

Diagnóstico rápido

SíntomaCausa probableAcción

Backup, versionado y migración

El estado y la auditoría viven en .aidlc-lite/. En el proyecto didáctico ese directorio está en .gitignore, porque cada demo empieza limpia. En un proyecto real se versionaría o se respaldaría antes de cambiar de versión del motor.

# Copia antes de actualizar el motor
cp -r .aidlc-lite .aidlc-lite.bak-2026-11-06
node src/cli.mjs doctor

# En Windows PowerShell
Copy-Item .aidlc-lite .aidlc-lite.bak-2026-11-06 -Recurse

El estado tiene version: 1. Si el esquema cambia, un motor nuevo debe leer la versión y migrar o rechazar el archivo con un mensaje claro. No debe asumir que el JSON siempre tiene la forma actual: un state.json antiguo puede tener etapas sin note o sin approvedAt.

Los límites también son contrato

aidlc-lite no tiene escritura atómica, no usa seq en la auditoría, no registra el actor y no detecta proyecciones obsoletas. No son bugs ocultos: son límites conocidos. Si los necesitas, extiende el motor con tests; no finjas que ya están resueltos.

3 · Ejemplo mínimo

Dos tests que fijan dos contratos: el perfil classic tiene seis etapas y una intención vacía no se puede crear.

// test/profiles.test.mjs
import test from "node:test";
import assert from "node:assert/strict";
import { getProfile } from "../src/profiles.mjs";

test("classic incluye plan y test", () => {
  const ids = getProfile("classic").stages.map((stage) => stage.id);
  assert.deepEqual(ids, ["intent", "requirements", "design", "plan", "build", "test"]);
});

test("classic tiene seis etapas", () => {
  assert.equal(getProfile("classic").stages.length, 6);
});
// test/state.test.mjs
import test from "node:test";
import assert from "node:assert/strict";
import { createIntent } from "../src/state.mjs";

test("crear una intención vacía falla", () => {
  assert.throws(
    () => createIntent({ profile: "classic", intent: "   " }),
    /vacía/
  );
});

Qué fijan estos tests:

  • El orden de las etapas de classic no es accidental: si alguien reordena el perfil, el test falla.
  • Una intención vacía es un error de uso, no un estado válido con intent: "".
  • No hay mocks, no hay beforeEach y no hay configuración global: cada test es una función.

La suite completa añade los casos de avance, rechazo, fin de intención, perfiles desconocidos, fusión de reglas, proyección idempotente, sensores y CLI. Cuarenta tests no son muchos para un motor; son los justos para que cada contrato tenga una prueba y ninguna prueba dependa de otra.

4 · Ejemplo real

El test de extremo a extremo del CLI, completo, y el flujo que ejecuta. Es el que más se acerca a lo que hará una persona en la terminal.

// test/cli.test.mjs (extracto real)
import test from "node:test";
import assert from "node:assert/strict";
import fs from "node:fs";
import os from "node:os";
import path from "node:path";
import { execFileSync } from "node:child_process";
import { fileURLToPath } from "node:url";

const projectRoot = path.resolve(path.dirname(fileURLToPath(import.meta.url)), "..");
const cli = path.join(projectRoot, "src", "cli.mjs");

function run(args, cwd = projectRoot) {
  return execFileSync(process.execPath, [cli, ...args], {
    cwd, encoding: "utf8", stdio: ["ignore", "pipe", "pipe"],
  });
}

function tempDir() {
  return fs.mkdtempSync(path.join(os.tmpdir(), "aidlc-cli-"));
}

test("flujo init -> run -> status -> approve -> doctor", () => {
  const dir = tempDir();
  run(["init", "--dir", dir, "--harness", "both"]);
  run(["run", "--dir", dir, "--profile", "express", "--intent", "demo"]);
  assert.match(run(["status", "--dir", dir]), /intent — Intent capture/);
  run(["approve", "--dir", dir, "--note", "ok"]);
  assert.match(run(["status", "--dir", dir]), /build — Code generation/);
  assert.match(run(["doctor", "--dir", dir]), /0 problemas/);
});

Lo que este test demuestra y lo que no:

DemuestraNo demuestra
El CLI arranca con Node y parsea --dir.Que la estética de la salida sea buena.
init crea lo necesario para que doctor pase.Que las reglas sean coherentes entre capas.
run respeta el perfil express y su primera etapa.Que el perfil sea el adecuado para el trabajo.
approve avanza a build.Que el humano haya leído el artefacto.

El test no necesita un servidor, una base de datos ni un modelo. Su única dependencia es Node y el sistema de archivos. Por eso puede ejecutarse en cualquier CI sin configuración y en menos de un segundo.

Un pipeline mínimo podría ser:

# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm test
      - run: node src/cli.mjs init --dir .ci --harness both
      - run: node src/cli.mjs doctor --dir .ci

El paso de doctor sobre un proyecto recién inicializado comprueba que la estructura, las reglas y las proyecciones se crean bien en un entorno limpio. No sustituye a los tests, pero detecta problemas de rutas o de permisos que un test en local puede ocultar.

La analogía del simulacro

Los tests son simulacros de incendio: no apagan fuegos reales, pero demuestran que cada pieza sabe qué hacer y que la salida está despejada. El día que hay un cambio en el motor, la suite te dice si la evacuación sigue funcionando. Un simulacro que nunca falla porque nadie lo ejecuta no protege a nadie.

6 · Errores habituales

1. Tests que escriben en el repositorio

Mal — estado compartido entre pruebas 
// ❌ usa el directorio del proyecto y deja .aidlc-lite/ sucio
initProject(".", { harnesses: "claude" });
startIntent(".", { profile: "classic", intent: "demo" });
Bien — directorio temporal por test 
const dir = fs.mkdtempSync(path.join(os.tmpdir(), "aidlc-engine-"));
initProject(dir, { harnesses: "claude" });
startIntent(dir, { profile: "classic", intent: "demo" });

Escribir en el repositorio hace que los tests dependan del orden y dejen basura. Un test que pasa en local porque ya existe .aidlc-lite/ puede fallar en CI, donde el directorio está limpio. El directorio temporal elimina esa clase de fallo.

2. Depender del reloj real

Mal — la fecha cambia en cada ejecución 
const state = createIntent({ profile: "express", intent: "demo" });
const expected = new Date().toISOString().slice(0, 10);
assert.equal(state.createdAt.slice(0, 10), expected);
Bien — fecha inyectada 
const now = new Date("2026-11-06T10:00:00Z");
const state = createIntent({ profile: "express", intent: "demo", now });
assert.equal(state.createdAt, "2026-11-06T10:00:00.000Z");

La comparación con new Date() puede fallar si el test cruza la medianoche o si el runner está en otro huso. La inyección hace que la prueba sea una función pura del input, no del momento en que se ejecuta.

3. Comprobar la salida sin comprobar el código de salida

Mal — el mensaje parece correcto 
const output = run(["doctor", "--dir", dir]);
assert.match(output, /doctor/);
// ❌ no se comprueba si el proceso terminó con 1
Bien — salida y código 
const result = spawnSync(process.execPath, [cli, "doctor", "--dir", dir], {
  encoding: "utf8",
});
assert.equal(result.status, 0);
assert.match(result.stdout, /0 problemas/);

execFileSync lanza una excepción si el proceso termina con código distinto de cero; por eso el test del camino feliz no necesita comprobarlo. Para probar un fallo, usa spawnSync o assert.throws y verifica el código. La salida sin el código puede ocultar que el comando falló.

7 · Ejercicio guiado

Objetivo: ejecutar la suite, añadir un test de diagnóstico y montar un smoke test de operación.

  1. Paso 1 — Ejecuta la suite completa: 
    cd proyectos/aidlc-lite
npm test

    Salida esperada: tests 40 · pass 40 · fail 0. Si algún test falla, anota el archivo y la aserción antes de tocar nada.

  2. Paso 2 — Ejecuta solo un archivo: 
    node --test test/state.test.mjs
node --test test/cli.test.mjs

    El runner acepta rutas. Úsalo para iterar sin esperar la suite completa cuando estés cambiando una pieza.

  3. Paso 3 — Añade un test de doctor sin proyección: 
    test("doctor detecta una proyección ausente", () => {
  const dir = tempDir();
  initProject(dir, { harnesses: "claude" });
  fs.rmSync(path.join(dir, ".claude", "CLAUDE.md"));
  const report = doctor(dir);
  assert.equal(report.ok, false);
  assert.ok(report.problems.some((p) => p.includes("proyección")));
});

    El test debe fallar si el doctor deja de comprobar hasManagedBlock. Si pasa siempre, no está probando lo que crees.

  4. Paso 4 — Prueba un fallo de uso: ejecuta run sin --intent y comprueba el código 1. 
    node src/cli.mjs run --dir .lab
echo $?   # 1
# error: run requiere --intent "<texto>"
  5. Paso 5 — Prueba los sensores con un artefacto incompleto: crea un Markdown de dos líneas y ejecuta sensors. Debe devolver 2 y enumerar los hallazgos. 
    printf '# X\n' > /tmp/incompleto.md
node src/cli.mjs sensors --artifact /tmp/incompleto.md
echo $?   # 2
  6. Paso 6 — Escribe el smoke test de operación: un script que inicialice en un directorio temporal, cree una intención, apruebe y pase el doctor. 
    DIR=$(mktemp -d)
node src/cli.mjs init --dir "$DIR" --harness both
node src/cli.mjs run --dir "$DIR" --profile express --intent "smoke"
node src/cli.mjs approve --dir "$DIR" --note "smoke"
node src/cli.mjs doctor --dir "$DIR"

    Si el script termina con 0, la operación básica funciona en un entorno limpio. Es el mismo flujo que pondrías en CI.

Resultado esperado

La suite en verde, un test nuevo que falla si se rompe el diagnóstico y un smoke test que recorre init → run → approve → doctor sin tocar el repositorio. Si el smoke test deja archivos fuera del directorio temporal, no es un smoke test: es una demo.

8 · Reto

🎯 El comando report

El equipo quiere un comando report que imprima, en una sola pasada, el estado de la intención, los últimos cinco eventos de auditoría y el resultado de los sensores sobre el artefacto de la etapa actual. Debe funcionar con --json para un panel, devolver 0 si todo está bien, 1 si el estado es inválido y 2 si hay hallazgos de sensores.

Diseña la extensión: ¿la lógica vive en cli.mjs, en engine.mjs o en un módulo nuevo? ¿Cómo reutilizas status, readAudit y runSensors sin duplicarlos? ¿Qué pasa si no hay intención activa? ¿Cómo pruebas la salida JSON y el código 2 sin depender de un artefacto real? ¿Qué parte del contrato belongs al CLI y qué parte al motor?

Pista: el comando es una composición de lecturas, no una nueva máquina de estados. Si empiezas a mutar el estado para generar el informe, has convertido un comando de solo lectura en una operación que necesita gate. Mantenlo puro y testea la composición con un directorio temporal.

9 · Resumen

  • La suite tiene 40 tests y se ejecuta con node --test, sin framework ni dependencias.
  • Los tests unitarios usan now inyectado; los de integración usan directorios temporales; el CLI se prueba como proceso.
  • Los códigos de salida son contrato: 0 éxito, 1 error o diagnóstico, 2 hallazgos de sensores.
  • El runbook del motor es init → run → status → approve/reject → sync → doctor → sensors.
  • El estado y la auditoría viven en .aidlc-lite/; se respaldan antes de migrar de versión.

10 · Preguntas frecuentes

¿Por qué no hay cobertura medida?

Porque la cobertura mide líneas ejecutadas, no contratos verificados. Los cuarenta tests cubren los comportamientos que el motor promete; añadir una métrica sin un objetivo claro solo invita a escribir tests vacíos para subir el número. Si quieres medirla, node --test --experimental-test-coverage existe, pero úsala como señal, no como meta.

¿Cómo se prueba un fallo de disco o un JSON corrupto?

Creando un directorio temporal, escribiendo un state.json inválido y llamando a doctor o status. El test debe comprobar que el error es claro y que el proceso no sigue como si nada. Para un fallo de escritura, necesitarías inyectar el sistema de archivos o usar permisos; el proyecto no lo hace porque añadiría complejidad al motor.

¿Los tests pueden ejecutarse en paralelo?

Sí, porque cada test de integración usa su propio directorio temporal y los unitarios no comparten estado. El runner de Node puede ejecutar archivos en paralelo; si añades un test que escriba en una ruta fija, romperás esa propiedad. La regla es simple: nada fuera de mkdtempSync.
