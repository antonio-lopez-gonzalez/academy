Arquitectura de aidlc-lite

Módulo 8 · Proyecto final 🕐 40 minutos

1 · Introducción

Has usado AI-DLC durante seis módulos. Ahora toca mirar debajo del capó con aidlc-lite, un motor didáctico en Node.js 22 que reproduce en pequeño la mecánica del ciclo: perfiles de workflow, una máquina de estados, gates humanos, auditoría append-only, reglas por capas y proyección a Claude Code y Cursor. No usa APIs de IA, no genera código y no despliega nada.

El proyecto no es un clon de AI-DLC. Es un laboratorio para entender por qué el estado y la auditoría están separados, por qué el gate es un comando explícito y no una respuesta del modelo, por qué las reglas se proyectan en lugar de copiarse y por qué un sensor determinista vale más que una segunda opinión. Cada módulo tiene una responsabilidad pequeña y un test que la fija.

Se ejecuta con node src/cli.mjs <comando>, no tiene dependencias externas y se prueba con node --test. Todo ocurre en local: un state.json, un audit.jsonl, tres archivos de reglas y dos proyecciones generadas. Esa simplicidad es deliberada; cualquier pieza extra tendría que justificar qué enseña.

Por qué un motor y no otro documento

Porque las reglas del proceso solo se entienden cuando se implementan. Un gate parece trivial hasta que tienes que decidir quién puede aprobar y qué pasa si se rechaza. Un sensor parece trivial hasta que descubres que su valor está en el fixture que demuestra que detecta algo. aidlc-lite convierte esas preguntas en código ejecutable.

Los once perfiles

Las rutas son deliberadamente cortas para que se puedan leer y testear. Cada perfil declara solo las etapas que necesita para contar su historia.

classic (6 etapas: requisitos, diseño, plan, construcción y pruebas), express y poc (3: intent, build, test), feature (7, con despliegue), enterprise (10, con NFRs, seguridad y operación), mvp (5, sin operación), bugfix (3, con regresión), refactor (4), infra (6), security-patch (3) y workshop (4, ruta guiada). El motor real usa 30 etapas después del setup; aquí cada ruta declara solo lo necesario. test/profiles.test.mjs fija, entre otras cosas, que PROFILES.classic.stages.length sea 6.

// src/profiles.mjs (extracto)
export const PROFILES = {
  classic: {
    title: "Classic",
    description: "Ceremonia clásica: requisitos, diseño, plan, construcción y pruebas.",
    stages: route(["intent", "requirements", "design", "plan", "build", "test"]),
  },
  enterprise: {
    title: "Enterprise",
    description: "Trabajo regulado con NFRs, seguridad y operación.",
    stages: route([
      "intent", "requirements", "nfr", "design", "security",
      "plan", "build", "test", "deploy", "operate",
    ]),
  },
};

Las etapas se reutilizan desde un diccionario STAGES y se copian con route(); así una etapa se define una vez y se referencia por identificador.

Flujo de una ejecución

init
 ├─ escribe .aidlc-lite/config.json
 ├─ crea rules/org.md, team.md, project.md
 ├─ proyecta .claude/CLAUDE.md y .cursor/rules/aidlc-team.mdc
 └─ audita project.initialized

run --profile feature --intent "API de inventario"
 ├─ carga config y perfil
 ├─ createIntent()
 ├─ audita intent.started
 └─ guarda state.json

status
 └─ lee state.json y calcula progreso (no muta nada)

approve --note "revisado"
 ├─ loadState
 ├─ applyGate(state, "approve")
 ├─ audita gate.approved
 └─ saveState

reject --note "faltan NFRs"
 ├─ applyGate(state, "reject")
 ├─ audita gate.rejected (la etapa sigue activa)
 └─ saveState

sync
 ├─ loadRules → merge textual org → team → project
 └─ projectAll → sobrescribe solo el bloque gestionado

El CLI no tiene un bucle interactivo que pregunta «¿apruebas?». La presencia humana se modela con un comando separado: run deja la intención en la primera etapa y approve o reject son actos explícitos de una persona. Es una decisión de diseño distinta de la de un harness, pero conserva la propiedad importante: el motor nunca avanza sin que alguien ejecute la aprobación.

Estado y auditoría: dos archivos, dos preguntas

state.json responde «dónde estamos»: intención, perfil, etapa actual, estado de cada etapa e historial. audit.jsonl responde «qué pasó»: una línea por evento, sin reescritura. La auditoría es la fuente y el estado, una proyección; en un motor completo el estado se reconstruye desde los eventos, aunque aidlc-lite todavía no lo hace de forma automática.

{
  "version": 1,
  "intent": "API de inventario",
  "profile": "feature",
  "createdAt": "2026-11-06T10:00:00.000Z",
  "updatedAt": "2026-11-06T10:12:44.018Z",
  "currentStage": 1,
  "status": "in_progress",
  "stages": [
    { "id": "intent", "title": "Intent capture", "status": "approved",
      "approvedAt": "2026-11-06T10:12:44.018Z", "note": "revisado" },
    { "id": "requirements", "title": "Requirements", "status": "in_progress",
      "approvedAt": null, "note": null }
  ],
  "history": [
    { "at": "2026-11-06T10:12:44.018Z", "type": "gate.approved",
      "stage": "intent", "note": "revisado" }
  ]
}

La auditoría usa un formato más plano, sin secuencia numérica: cada evento lleva at, type y los campos propios del evento. Es suficiente para el proyecto didáctico y fácil de leer con jq o Node. En la lección 07/02 veremos qué se gana y qué se pierde frente a una auditoría con seq.

Decisiones de diseño

aidlc-lite no usa IA

No llama a ningún modelo, no genera código y no decide por ti. Es un motor de proceso: registra, valida y proyecta. Si necesitas un modelo para que funcione, has salido del alcance y probablemente has convertido una comprobación determinista en una opinión.

4 · Ejemplo real

Una sesión completa sobre un directorio de demo, con las salidas reales del motor. El estado y la auditoría viven en .demo/.aidlc-lite/.

node src/cli.mjs init --dir .demo --harness both
# ✓ proyecto inicializado en .../.demo
#   harnesses: claude, cursor
#   → .claude/CLAUDE.md
#   → .cursor/rules/aidlc-team.mdc

node src/cli.mjs run --dir .demo --profile feature --intent "API de inventario"
# ✓ intención creada
# Intención : API de inventario
# Perfil    : feature
# Estado    : in_progress
# Etapa     : intent — Intent capture (1/7)
# Gate      : pendiente (approve | reject)

node src/cli.mjs approve --dir .demo --note "alcance revisado"
# ✓ gate aprobado
# Intención : API de inventario
# Perfil    : feature
# Estado    : in_progress
# Etapa     : requirements — Requirements (2/7)
# Gate      : pendiente (approve | reject)

La traza de auditoría correspondiente, en el formato real de audit.mjs:

{"at":"2026-11-06T10:00:00.000Z","type":"project.initialized","harnesses":["claude","cursor"],"files":[".claude/CLAUDE.md",".cursor/rules/aidlc-team.mdc"]}
{"at":"2026-11-06T10:01:00.000Z","type":"intent.started","intent":"API de inventario","profile":"feature","stages":7}
{"at":"2026-11-06T10:02:00.000Z","type":"gate.approved","intent":"API de inventario","stage":"intent","note":"alcance revisado","status":"in_progress"}

Qué ha hecho cada capa:

  1. init creó configuración, reglas y proyecciones; engine.mjs orquestó y audit.mjs registró el evento.
  2. run cargó config.json, resolvió el perfil con getProfile, creó el estado con createIntent, auditó el inicio y lo guardó.
  3. status solo leyó: no hay mutación ni evento.
  4. approve aplicó applyGate, añadió el evento con la nota humana y guardó el estado.

La analogía del reloj

El CLI es la esfera, engine el mecanismo, state la cuerda y audit la bitácora. Si la esfera intentara mover las agujas por su cuenta, el reloj se rompería. Cada pieza hace una cosa y la hace completa.

6 · Errores habituales

1. Poner un modelo en el camino del gate

Mal — la decisión se delega 
// ❌ el motor pide al modelo que apruebe
const verdict = await llm.ask(`¿Apruebas este plan? ${plan}`);
if (verdict === "sí") approve(dir, { note: "auto" });
Bien — comando humano explícito 
node src/cli.mjs approve --dir .demo --note "revisado por ana"
# el actor es quien ejecuta el comando; no hay auto-aprobación

Un modelo puede redactar, resumir o proponer. No puede aprobar. Si el motor incluye una llamada a un modelo en el gate, el proyecto deja de enseñar AI-DLC y empieza a enseñar autoaprobación con pasos extra.

2. Guardar el estado solo en memoria

Mal — el proceso es el estado 
// ❌ al salir, todo se pierde
let currentStage = 0;
run(); // no hay state.json ni auditoría
Bien — estado y auditoría persistidos 
const state = createIntent({ profile, intent, now });
saveState(dir, state);
appendAudit(dir, { type: "intent.started", intent, profile, stages: state.stages.length });

Sin persistencia no hay reanudación, no hay auditoría y no hay forma de enseñar qué pasa al cerrar la terminal. El estado en memoria es útil dentro de una función; fuera, es una promesa que se rompe con el proceso.

3. Acoplar las reglas a un solo harness

Mal — la fuente es el archivo generado 
// ❌ se escribe directamente el formato de Claude
const claude = rules.map((rule) => `- ${rule}`).join("\n");
fs.writeFileSync(".claude/CLAUDE.md", claude);
Bien — fuente, render y proyección 
const { merged } = loadRules(dir);
const written = projectAll(dir, merged, config.harnesses);
// writeDefaultRules crea la fuente; projectAll genera las salidas

Si el único formato es el del harness, cambiar de harness obliga a reescribir las reglas. La fuente debe ser neutra y las proyecciones, derivadas. Esa separación permite que Cursor y Claude compartan la misma política.

7 · Ejercicio guiado

Objetivo: recorrer el proyecto real, entender los perfiles y ver cómo se guardan el estado y la auditoría.

  1. Paso 1 — Entra en el proyecto y ejecuta la ayuda: 
    cd proyectos/aidlc-lite
node src/cli.mjs --help
node src/cli.mjs profiles

    Salida esperada: once líneas, de classic a workshop, cada una con su número de etapas y descripción.

  2. Paso 2 — Inicializa una demo con ambos harnesses: 
    node src/cli.mjs init --dir .demo --harness both
find .demo -maxdepth 3 -type f   # o Get-ChildItem en Windows

    Comprueba que existen .demo/.aidlc-lite/config.json, .demo/rules/*.md, .demo/.claude/CLAUDE.md y .demo/.cursor/rules/aidlc-team.mdc.

  3. Paso 3 — Crea una intención con el perfil classic: 
    node src/cli.mjs run --dir .demo --profile classic --intent "API de inventario"
node src/cli.mjs status --dir .demo

    La etapa 1/6 es intent — Intent capture. El estado está en .demo/.aidlc-lite/state.json; ábrelo y localiza currentStage y stages.

  4. Paso 4 — Aprueba y rechaza: 
    node src/cli.mjs approve --dir .demo --note "requisitos claros"
node src/cli.mjs reject --dir .demo --note "faltan NFRs"

    Tras aprobar, la etapa avanza a requirements. Tras rechazar, la etapa sigue siendo requirements y el motivo queda en history y en la auditoría.

  5. Paso 5 — Lee la auditoría: 
    cat .demo/.aidlc-lite/audit.jsonl

    Deben aparecer project.initialized, intent.started, gate.approved y gate.rejected. No hay seq: el orden es el orden de las líneas y la fecha at.

  6. Paso 6 — Diagnostica: 
    node src/cli.mjs sync --dir .demo
node src/cli.mjs doctor --dir .demo
node src/cli.mjs sensors --dir .demo --artifact examples/intent.md

    doctor debe terminar con 0 problemas y varios eventos de auditoría. sensors debe devolver 0 hallazgos con el ejemplo incluido; si devuelve 2, el artefacto no cumple las secciones requeridas.

Resultado esperado

Una demo con estado, auditoría y proyecciones reales, y la capacidad de explicar qué archivo es fuente y cuál es salida. Si confundes rules/ con CLAUDE.md, vuelve al paso 2: la fuente es rules/, la proyección es CLAUDE.md.

8 · Reto

🎯 El perfil que no existe

El equipo quiere un perfil hotfix con tres etapas: intent, build y test, pero con una diferencia: en build debe exigir una nota de incidente y en test debe declarar el comando de regresión. El CLI actual no tiene forma de exigir esa nota ni de guardar el comando.

Diseña la extensión sin romper los once perfiles existentes: ¿la exigencia vive en el perfil, en el gate o en un sensor? ¿Qué campos añadirías a la etapa y al estado? ¿Cómo migras un state.json existente? ¿Qué tests demuestran que los perfiles antiguos siguen funcionando? ¿Qué parte es configuración y qué parte es código?

Pista: un perfil es una ruta de etapas, no un lugar para reglas de negocio arbitrarias. Si la exigencia es «toda build de hotfix necesita nota de incidente», probablemente es una regla del proyecto o un sensor, no un campo nuevo del perfil. Añadir campos a la etapa obliga a migrar el estado y a tocar todos los perfiles.

9 · Resumen

  • aidlc-lite es un motor didáctico en Node.js 22 ESM, sin APIs de IA y sin dependencias.
  • Incluye once perfiles con rutas simplificadas de 3 a 10 etapas; classic es el perfil por defecto.
  • Las capas están separadas: CLI, engine, profiles, state, gates, audit, rules, projection, sensors y config.
  • El estado vive en .aidlc-lite/state.json y la auditoría en .aidlc-lite/audit.jsonl.
  • approve y reject son comandos humanos explícitos; el motor no tiene auto-aprobación.
  • Las reglas se escriben en rules/ y se proyectan a .claude/CLAUDE.md y .cursor/rules/aidlc-team.mdc.
  • El alcance pequeño es una decisión de diseño, no una limitación temporal.

10 · Preguntas frecuentes

¿Por qué no usar TypeScript?

Porque añade compilación y configuración que no enseñan nada sobre el ciclo de vida. El proyecto usa ESM, tests y validaciones explícitas. Si el objetivo fuera producción, TypeScript sería razonable; para un motor didáctico, el ruido supera el beneficio.

¿Puedo usar aidlc-lite en un proyecto real?

Puedes usarlo como referencia o para prototipos, pero no sustituye a AI-DLC: no tiene sus 33 etapas, sus 14 agentes ni sus perfiles completos. Está pensado para entender la mecánica. Si lo usas en un proyecto real, hazlo con un alcance pequeño y sabiendo que las garantías son las que tú implementes.

¿Qué pasa si el proceso se interrumpe a mitad de una etapa?

Al reanudar, status lee el estado y muestra la etapa actual. Si el evento se escribió pero el estado no, la auditoría conserva la decisión; el proyecto didáctico no reconstruye el estado automáticamente, pero el evento permite hacerlo a mano. La lección 07/02 cubre los casos límite y el orden de escritura que usaría un motor más robusto.
