Reglas y proyección

Módulo 7 · Proyecto final 🕐 40 minutos

1 · Introducción

Un equipo no trabaja igual que otro, y un proyecto no trabaja igual que la organización que lo contiene. aidlc-lite modela esa realidad con tres capas de reglas: org.md, team.md y project.md. La organización impone lo que no se negocia, el equipo añade su forma de trabajar y el proyecto concreta lo que necesita ese repositorio.

El problema no es escribirlas: es que Cursor y Claude las lean sin duplicarlas. Si el equipo mantiene un archivo para cada harness, en dos semanas habrá dos políticas distintas y nadie sabrá cuál es la buena. aidlc-lite resuelve eso con una proyección: una fuente en rules/ y dos archivos generados, .claude/CLAUDE.md y .cursor/rules/aidlc-team.mdc.

La implementación real es más sencilla de lo que parece: no hay parser de reglas ni identificadores con severidad. Hay lectura de tres archivos, una fusión textual en orden y una sustitución de un bloque delimitado por marcadores. Esa simplicidad tiene ventajas —se lee, se diffea y se explica— y también límites que conviene conocer antes de confiar en ella.

Una fuente, dos salidas

Si editas CLAUDE.md a mano, el siguiente sync sobrescribe el bloque gestionado. Si editas rules/project.md, ambas proyecciones se actualizan. La regla es simple: la fuente es rules/; los archivos de harness son artefactos generados.

2 · Teoría

Las tres capas y su orden

CapaArchivoQué debe contenerQuién la cambia
Organizaciónrules/org.mdPolíticas no negociables: gates, secretos, cumplimiento.Seguridad, plataforma o dirección técnica.
Equiporules/team.mdConvenciones de revisión, responsable humano, definición de terminado.El equipo.

El orden de lectura es org → team → project. La fusión es textual: cada archivo se antepone con un comentario de fuente y se concatenan en ese orden. No hay un motor que elimine una regla anterior porque otra capa la contradiga; la precedencia es una convención de lectura, no una operación del programa.

<!-- source: org.md -->
# Reglas de la organización

- Todo cambio pasa por un gate humano.
- Ningún agente se autoaprueba.
- Los secretos no se escriben en artefactos ni en reglas.

<!-- source: team.md -->
# Reglas del equipo

- Una intención, un responsable humano.
- Los artefactos se revisan antes de aprobar.
- Las decisiones se registran en el audit trail.

Esa salida es exactamente lo que produce mergeRules. Si el proyecto necesita una regla más específica, se añade al final; el lector ve primero la política general y después la concreción. Pero si el proyecto dice lo contrario que la organización, ambas frases siguen ahí: el conflicto no se resuelve solo.

El formato: Markdown sin esquema

No hay frontmatter, identificadores ni severidad. Cada archivo es un documento Markdown con título y viñetas. Esa decisión hace que cualquiera pueda contribuir sin aprender un DSL, pero traslada al revisor la responsabilidad de detectar contradicciones y reglas muertas.

# Reglas del proyecto

- Node.js 22, ESM y sin dependencias en aidlc-lite.
- Los tests se ejecutan con `node --test`.
- La proyección a Cursor y Claude se regenera con `sync`.
- No se editan a mano los bloques gestionados de `.claude/` ni `.cursor/`.

Una regla útil es concreta y verificable. «Escribir código limpio» no se puede comprobar; «los tests se ejecutan con node --test» sí. El motor no valida el contenido, así que la calidad de las reglas depende de la revisión humana. Los sensores pueden cubrir una parte, pero no sustituyen esa revisión.

Carga, fusión y escritura por defecto

// src/rules.mjs (extracto real)
export const RULE_FILES = ["org.md", "team.md", "project.md"];

export function loadRules(dir) {
  const sources = [];
  for (const file of RULE_FILES) {
    const full = path.join(rulesDir(dir), file);
    if (!fs.existsSync(full)) continue;
    sources.push({ file, text: fs.readFileSync(full, "utf8").trim() });
  }
  return { sources, merged: mergeRules(sources) };
}

export function mergeRules(sources) {
  return sources
    .map(({ file, text }) => `<!-- source: ${file} -->\n${text}`)
    .join("\n\n");
}

loadRules ignora los archivos que no existen en lugar de fallar. Eso permite trabajar con una capa ausente —por ejemplo, un proyecto sin reglas de equipo— y fusionar solo lo que hay. validateRules es más estricto: exige que exista rules/ y las tres capas. La separación es intencionada: cargar es tolerante, diagnosticar es exigente.

export function writeDefaultRules(dir) {
  fs.mkdirSync(rulesDir(dir), { recursive: true });
  for (const file of RULE_FILES) {
    const full = path.join(rulesDir(dir), file);
    if (!fs.existsSync(full)) {
      fs.writeFileSync(full, DEFAULT_RULES[file], "utf8");
    }
  }
}

init llama a writeDefaultRules. La comprobación existsSync es la parte importante: si el archivo ya existe, no se toca. Puedes ejecutar init varias veces sin perder tus reglas. Esa propiedad —idempotencia sin sobrescritura— es la que permite usar init como reparación de estructura.

Proyección: marcadores y propiedad

La proyección no reescribe el archivo entero: sustituye un bloque entre marcadores. Todo lo que el usuario escriba fuera se conserva.

<!-- aidlc-lite:start -->
<!-- source: org.md -->
# Reglas de la organización
...
<!-- aidlc-lite:end -->
// src/projection.mjs (extracto real)
export const START = "<!-- aidlc-lite:start -->";
export const END = "<!-- aidlc-lite:end -->";

export function replaceManagedBlock(existing, block) {
  const start = existing.indexOf(START);
  const end = existing.indexOf(END);
  if (start !== -1 && end !== -1 && end > start) {
    return existing.slice(0, start) + block + existing.slice(end + END.length);
  }
  const separator = existing.endsWith("\n") || existing === "" ? "" : "\n";
  return `${existing}${separator}\n${block}\n`;
}

El bloque es propiedad de aidlc-lite. El resto del archivo es del usuario. Esa frontera es lo que permite tener instrucciones propias del proyecto en CLAUDE.md sin que sync las borre. Si editas dentro del bloque, el cambio se pierde en la siguiente proyección; si editas fuera, se conserva.

El contenido de las reglas es idéntico en ambos; cambia el envoltorio que cada harness espera. Esa es la ventaja de proyectar en lugar de duplicar: una regla se escribe una vez y se lee en los dos entornos. Si un harness necesita una regla específica —por ejemplo, algo sobre la status line de Claude—, se marca en la regla y se documenta; el motor no la separa automáticamente.

El flujo de sync

// src/engine.mjs (extracto real)
export function syncProjections(dir) {
  const config = loadConfig(dir);
  const { sources, merged } = loadRules(dir);
  const written = projectAll(dir, merged, config.harnesses);
  appendAudit(dir, {
    type: "rules.projected",
    sources: sources.map((source) => source.file),
    files: written.map((file) => path.relative(dir, file).replaceAll("\\", "/")),
  });
  return { written, sources };
}

sync lee la configuración, carga las reglas presentes, proyecta a los harnesses configurados y audita qué fuentes y qué archivos se escribieron. Si el proyecto se inicializó solo con claude, no aparecerá .cursor/. Para añadir Cursor después, cambia harnesses en .aidlc-lite/config.json o vuelve a inicializar en un directorio limpio con --harness both.

Qué valida doctor y qué no

  • Valida que exista config.json, que los harnesses sean válidos y que cada proyección tenga los dos marcadores.
  • Valida que existan las tres capas de reglas y que el estado tenga la forma mínima.
  • No compara el contenido del bloque con las reglas actuales: si editas rules/ y no ejecutas sync, el doctor no lo detecta como problema.
  • No detecta contradicciones entre capas: dos reglas opuestas conviven en el texto fusionado.

Esa última carencia es la más importante para un equipo. El doctor te dice que la estructura está bien, no que la política sea coherente. La revisión de reglas sigue siendo humana, igual que la revisión de código.

Las reglas se proyectan a ambos harnesses

No escribas secretos, tokens, rutas personales ni datos de clientes en rules/. Todo lo que pongas ahí acabará en dos archivos versionados y potencialmente en el contexto de un agente. Si una regla necesita un dato sensible, referencia el lugar donde se obtiene, no el dato.

Conflicto real: el proyecto contradice a la organización

Imagina que org.md dice «ninguna dependencia externa sin aprobación de seguridad» y project.md dice «usar Zod para validar». La fusión contiene las dos frases. No hay un error de sintaxis ni un fallo del doctor: hay una decisión pendiente. El equipo debe resolverla antes de que un agente lea las reglas y elija la que le convenga.

<!-- source: org.md -->
- Ninguna dependencia externa sin aprobación de seguridad.

<!-- source: project.md -->
- Usar Zod para validar los payloads.

La forma correcta de resolverlo no es borrar la regla de la organización, sino concretar la excepción: «Zod está aprobado por seguridad el 2026-11-01, referencia SEC-42». Así la política sigue siendo trazable y el proyecto puede avanzar. Si el conflicto no se resuelve, el agente recibirá instrucciones contradictorias y elegirá una sin autoridad para hacerlo.

Qué observar:

  • El orden es el de RULE_FILES: organización, equipo, proyecto.
  • Cada bloque lleva un comentario con su fuente, para que el lector sepa de dónde viene.

Si alguien edita el bloque de CLAUDE.md a mano y luego ejecuta sync, el cambio desaparece. Si edita fuera del bloque, se conserva. Esa es toda la regla de propiedad: el bloque es del motor, el resto es del proyecto.

La analogía de la plantilla y el documento

Las reglas son la plantilla; las proyecciones son documentos generados. Puedes escribir notas en los márgenes del documento, pero si vuelves a generar desde la plantilla, el cuerpo se reemplaza y los márgenes se conservan. Editar el cuerpo generado y llamarlo fuente es como corregir la fotocopia y esperar que cambie el original.

6 · Errores habituales

1. Editar la proyección y perder el cambio en el siguiente sync

Mal — la fuente y la salida se confunden 
# .claude/CLAUDE.md (editado a mano)
<!-- aidlc-lite:start -->
- Usar siempre PostgreSQL.
<!-- aidlc-lite:end -->
Bien — la regla vive en rules/ 
# rules/project.md
- La base de datos del proyecto es PostgreSQL 16.

El primer cambio desaparece en la siguiente proyección porque el bloque se sustituye entero. El segundo se conserva y se propaga a ambos harnesses. Si necesitas una instrucción que no debe gestionar el motor, escríbela fuera de los marcadores.

2. Poner secretos o datos personales en las reglas

Mal — el secreto se proyecta dos veces 
# rules/team.md
- La API key de producción es sk-live-abc123.
- El email del cliente principal es ana@cliente.com.
Bien — referencia, no dato 
# rules/team.md
- Las credenciales se leen de `.env`, nunca de reglas ni artefactos.
- Los datos de clientes se referencian por identificador interno.

Las reglas se copian a .claude/CLAUDE.md y .cursor/rules/aidlc-team.mdc, se versionan y acaban en el contexto del agente. Un secreto ahí es una fuga con dos copias. La regla correcta no es «no compartir», sino «no escribir el dato».

3. Creer que project.md sobrescribe a org.md

Mal — se asume un merge semántico 
# org.md
- Ninguna dependencia externa sin aprobación de seguridad.

# project.md
- Usar Zod para validar.
# ❌ el resultado contiene las dos reglas; nadie las reconcilió.
Bien — excepción explícita y trazable 
# project.md
- Zod está aprobado por seguridad el 2026-11-01 (SEC-42).
- Cualquier otra dependencia requiere aprobación previa.

La fusión no tiene lógica de override. El orden solo hace que la última capa se lea después. Si hay conflicto, el equipo debe resolverlo en el texto y dejar la referencia que lo justifica. Confiar en una precedencia automática produce políticas contradictorias que el agente interpretará a su manera.

4. Inicializar solo un harness y olvidar el otro

Mal — dos equipos con políticas distintas 
node src/cli.mjs init --dir .demo --harness claude
# más tarde, alguien usa Cursor y no encuentra reglas
# .cursor/rules/aidlc-team.mdc no existe
Bien — configurar ambos desde el inicio 
node src/cli.mjs init --dir .demo --harness both
# harnesses: claude, cursor
# .claude/CLAUDE.md
# .cursor/rules/aidlc-team.mdc

La configuración vive en .aidlc-lite/config.json. Si el proyecto se inicializó con un solo harness, sync no crea el otro. Añadirlo después exige editar la configuración y volver a proyectar; si no, cada harness tendrá una política distinta y la comparación del curso dejará de tener sentido.

Objetivo: comprobar la propiedad del bloque, la idempotencia y el efecto de una regla nueva en ambos harnesses.

Resultado esperado

Dos proyecciones con el mismo contenido, una instrucción propia que sobrevive y una regla nueva presente en ambos harnesses. Si el doctor falla, revisa que config.json incluya los dos harnesses y que los marcadores estén intactos.

8 · Reto

🎯 Detectar la proyección obsoleta

El doctor actual comprueba que los marcadores existen, pero no que el contenido proyectado coincida con las reglas actuales. Un equipo edita rules/team.md, olvida ejecutar sync y sigue trabajando con una política vieja en ambos harnesses. No hay ningún aviso: el doctor dice que todo está bien.

Diseña una comprobación de deriva: ¿guardas un hash en config.json, en el propio bloque o en un archivo aparte? ¿Qué pasa con el contenido del usuario fuera del bloque? ¿Cómo distingues «proyección obsoleta» de «proyección editada a mano»? ¿Qué comando devuelve error y con qué código de salida? ¿Cómo se integra en doctor sin convertirlo en un gate?

Pista: el bloque gestionado ya es una unidad verificable. Puedes calcular un hash de las reglas fusionadas y compararlo con el que dejaste la última vez dentro de un comentario del bloque. Si el archivo se editó a mano, el hash del contenido no coincide; si las reglas cambiaron, el hash esperado no coincide. Son dos estados distintos y conviene nombrarlos distinto.

9 · Resumen

  • La fusión es textual y en orden; no hay override automático ni detección de conflictos.
  • writeDefaultRules crea las capas que faltan y nunca sobrescribe las existentes.
  • La proyección sustituye solo el bloque entre aidlc-lite:start y aidlc-lite:end.
  • Claude recibe .claude/CLAUDE.md; Cursor recibe .cursor/rules/aidlc-team.mdc con frontmatter.
  • sync reproyecta según config.json y audita fuentes y archivos escritos.
  • doctor valida estructura y presencia de marcadores, no frescura ni coherencia semántica.

10 · Preguntas frecuentes

¿Puedo tener reglas distintas para Cursor y Claude?

El motor proyecta el mismo contenido a ambos. Si una regla solo aplica a un harness, puedes marcarla en el texto —por ejemplo, «solo Claude: mostrar la status line»— y documentar por qué. Lo que no hace el motor es separar automáticamente las reglas por harness; si lo necesitas, es una extensión del proyecto, no una capacidad actual.

¿Qué pasa si borro una de las tres capas?

loadRules la ignora y fusiona las que quedan, pero validateRules y doctor la reportan como problema. Esa separación permite que el motor funcione en un proyecto incompleto y que el diagnóstico te avise. Si quieres restaurarla, init vuelve a crear el archivo por defecto sin tocar los otros dos.

¿Por qué no hay identificadores de regla?

Porque el proyecto prioriza la legibilidad y la revisión en Markdown sobre la automatización. Con identificadores podrías detectar duplicados, overrides y reglas sin dueño, pero también añadirías un esquema que mantener. Para un motor didáctico, el texto plano enseña mejor el problema; la lección de sensores muestra cómo añadir comprobaciones sin convertirlo en un DSL.
