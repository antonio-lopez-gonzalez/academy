Instalar AI-DLC para Claude

Módulo 1 · Claude Code 🕐 35 minutos

1 · Introducción

Hay dos instalaciones distintas con nombres parecidos, y confundirlas cuesta una tarde. La primera es el binario aidlc: un ejecutable que sabe qué es un stage, un gate y un perfil. La segunda es la proyección en el proyecto: los archivos que Claude Code necesita para que /aidlc exista y para que los hooks puedan registrar aprobaciones.

El binario se instala una vez por máquina. La proyección se instala una vez por repositorio y se versiona en Git. Esta lección hace las dos, en ese orden, y termina con un commit limpio que cualquier compañero puede clonar.

Un detalle que sorprende: el instalador nativo incluye los runtimes de todos los harnesses. No instalas «AI-DLC para Claude» y luego «AI-DLC para Cursor» como si fueran programas distintos. Instalas el motor una vez y configuras cada proyecto para el harness que uses. aidlc config --harness claude no descarga nada nuevo: copia y adapta la distribución al repositorio.

Por qué existe esta lección

El 90 % de los problemas del primer día son de proyección, no de metodología: el comando no aparece, los hooks no se ejecutan, el estado no se guarda o el equipo recibe archivos locales en el diff. Todos se evitan sabiendo qué escribe aidlc config y qué se commitea.

2 · Teoría

Las dos capas

CapaQué esAlcanceCómo se instala
MotorEl binario aidlc con el core y los runtimes de harnessMáquinaInstalador nativo oficial
ProyecciónArchivos del harness y del espacio de trabajo dentro del repoProyectoaidlc config --harness <nombre>

El motor se actualiza con el instalador; la proyección se refresca con aidlc config, que es transaccional e idempotente: si vuelves a ejecutarlo, actualiza lo que falte y respeta lo que hayas editado. Esa propiedad es la que permite actualizar AI-DLC sin perder las reglas del equipo.

Instalar el motor

macOS, Linux y WSL:

curl -fsSL https://github.com/awslabs/aidlc-workflows/releases/latest/download/install.sh | sh

Windows, en PowerShell:

irm https://github.com/awslabs/aidlc-workflows/releases/latest/download/install.ps1 | iex

El instalador descarga la última release estable, verifica su checksum e instala el comando aidlc junto con los runtimes de harness. En una instalación nativa no necesitas Bun ni Node.js para el motor; sí los necesitarás para tu proyecto si es Node, que es el caso del curso.

aidlc version

Si el comando no aparece, abre una terminal nueva: el instalador modifica el PATH del usuario y las sesiones ya abiertas no lo ven. En Windows, el binario suele quedar en una ruta de usuario que PowerShell añade al perfil; si usas otra shell, compruébalo.

Configurar el proyecto: qué hace exactamente

cd ~/proyectos/inventario
aidlc config --harness claude --dry-run   # ver qué cambiaría
aidlc config --harness claude

Sin --harness, el comando abre una configuración interactiva cuando hay terminal. Con el flag, va directo. --dry-run imprime el plan sin escribir nada: úsalo la primera vez y en repositorios con cambios sin commitear.

Durante la configuración, el asistente puede preguntarte por:

  • Servidores MCP: si quieres conectar herramientas externas. Si dices que no, no se escribe .mcp.json.
  • Status line: si aceptas que AI-DLC muestre el avance en la barra inferior del terminal. Sustituye la que tuvieras, así que es una decisión tuya y se puede cambiar después.
  • Preset de modelo: el modelo por defecto para las etapas, guardado en aidlc.settings.json.

La configuración es transaccional

Si algo falla a mitad, no deja el proyecto en un estado intermedio. Puedes volver a ejecutarla sin miedo: es la forma recomendada de refrescar los archivos tras actualizar el motor.

Qué queda escrito

RutaContenido¿Commitear?
.claude/El motor del harness: skill /aidlc, agentes, stages, hooks, tools y settings.json con permisos y hooksSí
aidlc/Los registros: spaces/default/memory/ con las reglas, knowledge/ y intents/ con el trabajoSí
.gitignoreUn bloque marcado por AI-DLC con el estado local que no debe viajarSí
.mcp.jsonServidores MCP, solo si los elegisteSí
aidlc.settings.jsonPreset de modelo y ajustes compartidosSí

El commit recomendado por la documentación es exactamente este:

git add .claude aidlc .gitignore .mcp.json aidlc.settings.json
git commit -m "Set up AI-DLC"

Si .mcp.json no existe porque rechazaste MCP, git add se quejará de una ruta inexistente. Añade solo lo que exista; el resto del comando sigue siendo válido.

Qué se proyecta dentro de .claude/

.claude/
├── skills/aidlc/        ← el comando /aidlc y su orquestación
├── agents/              ← los 14 roles como subagentes
├── stages/              ← definiciones de etapa que lee el motor
├── hooks/               ← hooks en TypeScript; registran gates y estado
├── tools/               ← utilidades del motor (estado, auditoría, doctor)
└── settings.json        ← permisos, hooks cableados, mensaje de bienvenida

Esta carpeta es el motor del harness, no una carpeta de trabajo. No la edites a mano salvo que sepas exactamente qué estás cambiando: la siguiente ejecución de aidlc config puede reescribir lo que toques. Las reglas del equipo van en aidlc/spaces/default/memory/, que sí está pensada para editarse.

Motor y método no se mezclan

.claude/ es infraestructura; aidlc/ es el proyecto. Si metes decisiones de negocio en .claude/, las perderás en la primera actualización y nadie sabrá por qué cambió el comportamiento.

El estado local que no viaja

AI-DLC ignora deliberadamente una lista de archivos por máquina: el espacio activo, el intent activo, el identificador de clon, las sesiones en curso y los artefactos derivados en tiempo de ejecución. La razón es simple: si dos personas comparten el «intent activo», una pisa el trabajo de la otra sin querer.

Lo que sí viaja es la verdad compartida: las reglas de memory/, el conocimiento de knowledge/ y el estado y los artefactos de cada intent. Esa división es la que hace que el mismo repositorio funcione en dos harnesses y en tres máquinas sin conflictos constantes.

3 · Ejemplo mínimo

De cero a un proyecto configurado, en cuatro comandos.

# 1. Motor (una vez por máquina)
curl -fsSL https://github.com/awslabs/aidlc-workflows/releases/latest/download/install.sh | sh

# 2. Proyección (una vez por proyecto)
cd ~/proyectos/inventario
aidlc config --harness claude

# 3. Verificación
aidlc doctor

# 4. Primer vistazo
ls -a .claude aidlc

El doctor debe terminar con algo parecido a esto:

AI-DLC doctor

Machine
  ok    9 checks passed

Project (.claude, Claude Code)
  warn  AIDLC hooks have not run in this project yet
  ok    49 checks passed

Framework integrity
  ok    all 12 checks passed

0 problems, 1 warning.

El aviso de hooks es el esperado antes de la primera conversación: los hooks se ejecutan cuando Claude Code arranca en esa carpeta y procesa un evento. No hay nada que arreglar; desaparecerá tras el primer /aidlc.

Comprueba el diff antes de commitear

git status --short debe mostrar .claude/, aidlc/, .gitignore y, si aceptaste, .mcp.json y aidlc.settings.json. Si aparece un settings.local.json, el bloque de .gitignore no se aplicó: revísalo antes del commit.

4 · Ejemplo real

El equipo de inventario ya tiene el repositorio con código y tests. Ana configura AI-DLC en una rama para que el resto pueda revisar qué entra antes de mezclarlo.

git checkout -b chore/aidlc-setup
aidlc config --harness claude --dry-run
# revisa la lista: .claude/, aidlc/, bloque en .gitignore, aidlc.settings.json
aidlc config --harness claude
# responde: sin MCP por ahora, status line sí, preset por defecto
aidlc doctor
git add .claude aidlc .gitignore .mcp.json aidlc.settings.json
git commit -m "Set up AI-DLC para Claude Code"

En el pull request, el equipo revisa tres cosas y no cincuenta:

Qué se revisaPor qué
aidlc/spaces/default/memory/team.mdEs donde el equipo escribirá sus prácticas. Debe empezar vacío o con lo acordado, no con invenciones.
.claude/settings.jsonPermisos y hooks cableados: determina qué puede hacer el agente sin preguntar.
El bloque añadido a .gitignoreSi falta, cada persona commiteará su estado local y el repo se llenará de ruido.

Al día siguiente, Bruno clona y no configura nada:

git clone git@github.com:equipo/inventario.git
cd inventario
claude
> /aidlc --status
  Perfil: — (sin workflow activo)
  Espacio: default
  Estado: listo para inicializar

Ese es el objetivo de la lección: que la configuración sea del repositorio, no de la persona. Bruno no instala AI-DLC «para Claude» otra vez; solo tiene el motor y el proyecto ya sabe qué hacer.

La analogía del kit de obra

El motor es la caja de herramientas que llevas en el coche. La proyección es el plano y las normas de seguridad de esta obra concreta, colgados en la pared. Si el plano vive en tu casa, el siguiente operario trabaja a ciegas aunque tenga las mismas herramientas.

5 · Buenas prácticas

HazEvitaPor qué
Ejecutar --dry-run antes de configurar un repo existente. Lanzar aidlc config y descubrir el alcance en el diff. La configuración escribe decenas de archivos; saber cuáles antes evita sustos y conflictos.
Commitear .claude/ y aidlc/ juntos en un commit dedicado. Mezclar la instalación con un cambio de producto. Facilita el review y permite revertir la configuración sin tocar código.
Escribir las reglas en memory/team.md y project.md. Editar los archivos de .claude/. Lo de .claude/ se reescribe al refrescar; lo de memory/ es tuyo y se respeta.
Dejar MCP fuera hasta que haya una necesidad concreta. Conectar cinco servidores «por si acaso». Cada servidor añade superficie, permisos y ruido de contexto en cada etapa.
Revisar que .gitignore cubre *.local.json y el estado por sesión. Asumir que el bloque se añadió correctamente. Un archivo local commiteado genera conflictos en cada rama y filtra información de máquina.

6 · Errores habituales

1. Configurar en la carpeta equivocada

Mal — home como proyecto 
cd ~
aidlc config --harness claude
Bien — la raíz del repositorio 
cd ~/proyectos/inventario
git rev-parse --show-toplevel
aidlc config --harness claude

Configurar en el home crea un aidlc/ gigante que mezcla todos tus proyectos y un .claude/ que no se versiona en ningún sitio. El comando no adivina: usa el directorio actual.

2. Commitear el estado local

Mal — el diff con archivos de máquina 
git add -A
# incluye aidlc/active-space, aidlc/.aidlc-sessions/,
# .claude/settings.local.json, aidlc.settings.local.json
Bien — añadir rutas explícitas 
git add .claude aidlc .gitignore .mcp.json aidlc.settings.json
git status --short   # revisar que no haya *.local.json

El estado local describe tu sesión: qué espacio tienes activo, qué intent estás mirando. Si viaja, el compañero que clone aparecerá dentro de tu trabajo a medias.

3. Editar .claude/ para cambiar el comportamiento

Mal — parchear el motor 
# editar .claude/skills/aidlc/SKILL.md para cambiar las preguntas
# editar .claude/hooks/*.ts para relajar un gate
Bien — usar las capas de método 
# aidlc/spaces/default/memory/team.md
- Cada etapa de diseño debe comparar al menos dos alternativas.
- Los tests de concurrencia son obligatorios en escrituras compartidas.

El primer camino funciona hasta la siguiente actualización, y entonces nadie recuerda qué se cambió ni por qué. El segundo es el mecanismo previsto: reglas del equipo que se suman a las del framework.

4. Instalar «AI-DLC para Claude» y luego «para Cursor» como si fueran paquetes

Mal — dos instalaciones del motor 
curl .../install-claude.sh | sh
curl .../install-cursor.sh | sh
Bien — un motor, dos proyecciones 
# el instalador oficial ya trae todos los runtimes
aidlc config --harness claude    # en este repo
aidlc config --harness cursor    # en el repo donde uses Cursor

No existen instaladores por harness. Si alguien te ofrece uno, está describiendo mal el producto: lo que cambia por harness es la proyección dentro del proyecto, no el binario.

7 · Ejercicio guiado

Objetivo: configurar AI-DLC en un repositorio, entender cada archivo escrito y dejarlo listo para que otro lo clone.

  1. Paso 1 — Prepara el repositorio. 
    mkdir ~/laboratorio/aidlc-claude
cd ~/laboratorio/aidlc-claude
git init
printf '# Laboratorio AI-DLC\n' > README.md
git add README.md && git commit -m "Initial commit"
  2. Paso 2 — Previsualiza. 
    aidlc config --harness claude --dry-run

    Anota cuántos archivos propone crear y en qué rutas. Si el número te sorprende, es normal: son ~50 comprobaciones y decenas de archivos de motor.

  3. Paso 3 — Configura. 
    aidlc config --harness claude

    Responde que no a MCP (lo añadirás cuando lo necesites) y que sí a la status line. Si te pregunta por el preset de modelo, acepta el valor por defecto.

  4. Paso 4 — Lee lo escrito. 
    find .claude -maxdepth 2 -type d | sort
find aidlc -maxdepth 4 -type d | sort
cat aidlc.settings.json

    Localiza skills/aidlc/, agents/, hooks/ y, en aidlc/, la carpeta spaces/default/memory/.

  5. Paso 5 — Verifica el aislamiento. 
    cat .gitignore
git status --short

    Debe aparecer un bloque marcado por AI-DLC y ningún *.local.json en el listado de cambios.

  6. Paso 6 — Commit y clonación limpia. 
    git add .claude aidlc .gitignore aidlc.settings.json
git commit -m "Set up AI-DLC"
cd ..
git clone aidlc-claude copia
cd copia && aidlc doctor

    El clon debe pasar el doctor casi entero: la configuración viajó con el repositorio. Solo faltará el estado local, que es exactamente lo que debe faltar.

Resultado esperado

Un commit con cinco rutas, un aidlc doctor sin problemas y un clon que funciona sin volver a configurar. Si el clon pide configuración, algo se quedó fuera del commit.

8 · Reto

🎯 La decisión de MCP y status line

Antes de configurar el repositorio real, decide qué servidores MCP va a usar el equipo y si la status line de AI-DLC sustituye a la que ya tenéis. Escribe el criterio: qué información aporta cada servidor a una etapa concreta, qué permisos concede y quién lo mantiene.

Después diseña el caso contrario: qué pasaría si mañana hay que retirar un MCP que llevaba un mes configurado. ¿Qué artefactos dependen de él? ¿Cómo se detecta que una etapa dejó de tener la información que creía tener?

Pista: un servidor MCP sin dueño y sin etapa asignada es superficie de ataque con mantenimiento. Si no puedes nombrar la etapa que lo usa, no lo instales todavía.

9 · Resumen

  • Hay dos capas: el motor (binario, por máquina) y la proyección (archivos, por proyecto).
  • El instalador nativo ya incluye los runtimes de todos los harnesses; no hay instaladores separados.
  • aidlc config --harness claude es transaccional e idempotente; --dry-run previsualiza.
  • Escribe .claude/, aidlc/, un bloque en .gitignore y, si aceptas, .mcp.json y aidlc.settings.json.
  • Se commitea todo salvo los *.local.json y el estado por sesión.
  • Las reglas del equipo van en aidlc/spaces/default/memory/, no en .claude/.

10 · Preguntas frecuentes

¿Tengo que reinstalar el motor si actualizo AI-DLC?

El binario se actualiza con el instalador. Después conviene ejecutar aidlc config en cada proyecto para refrescar la proyección. El comando conserva lo que hayas editado y actualiza lo que falte, así que es seguro repetirlo.

¿Puedo tener Claude Code y Cursor configurados en el mismo repositorio?

Sí. Cada harness tiene su carpeta de motor —.claude/ y .cursor/— y ambos comparten aidlc/. Esa es la base de los equipos híbridos, que se tratan en el módulo 3. Configura uno, verifica, y luego el otro.

¿Qué pasa si aidlc config dice que no hay release disponible?

El comando es transaccional y funciona desde la release que ya está en la máquina; solo descarga si aceptas en el prompt o pasas la opción correspondiente. Si no hay red, revisa que el binario esté instalado y que la versión sea coherente con la del proyecto.

¿Debo commitear aidlc/spaces/default/knowledge/documents/?

Los documentos originales que el equipo necesita para trabajar sí forman parte de la verdad compartida. Lo que no se commitea es el catálogo derivado ni los índices generados con rutas locales. El bloque de .gitignore ya distingue ambos casos.

¿La status line es obligatoria?

No. Es una comodidad de Claude Code que muestra el avance del ciclo en la barra inferior. Si ya tienes una status line propia, puedes rechazarla y consultar el estado con /aidlc --status. En Cursor no existe: allí el equivalente siempre es el comando.
