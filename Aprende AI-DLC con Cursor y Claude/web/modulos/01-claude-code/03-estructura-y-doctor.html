Estructura del proyecto y doctor

Módulo 1 · Claude Code 🕐 35 minutos

1 · Introducción

Después de aidlc config, el repositorio tiene dos carpetas nuevas y un archivo con nombre de persona. La tentación es ignorarlas hasta que algo falle. El problema es que cuando algo falla —un gate que no se registra, una etapa que no encuentra su entrada, un compañero que ve otro estado— el diagnóstico exige saber qué hay dentro.

La estructura tiene una lógica muy simple: .claude/ es el motor, aidlc/ es el registro, CLAUDE.md es el contexto ambiental. Todo lo demás se deduce. Si confundes las tres capas, acabarás editando el motor para cambiar una regla o metiendo decisiones de negocio en un archivo que el agente lee en cada turno.

El segundo protagonista es aidlc doctor: el comando que responde «¿puede este proyecto ejecutar el ciclo?». No es un linter de tu código, es un diagnóstico de la instalación. Sus tres bloques —máquina, proyecto, integridad del framework— cubren el 90 % de los problemas de puesta en marcha.

Por qué existe esta lección

Porque un warn mal interpretado se convierte en una hora de depuración. Y porque saber qué archivo es «tuyo» y cuál es «del motor» evita el error más caro: personalizar la infraestructura y perder los cambios en la siguiente actualización.

Dos carpetas, dos propósitos. .claude/ se reescribe al refrescar; aidlc/ es tuya y se conserva. Las marcas de «cursor» —active-space, active-intent— son locales por diseño: si viajaran, el clon de un compañero aparecería dentro de tu trabajo a medias.

.claude/: el motor

Contiene la implementación de AI-DLC para Claude Code. Los elementos que más te van a importar:

RutaQué hace¿Lo tocas?
skills/aidlc/Define el comando /aidlc, sus flags y el flujo de conversaciónNo
agents/Los 14 roles: 11 domain experts, 2 reviewers, 1 composerNo
stages/Qué preguntas hace cada etapa y qué artefacto produceNo
hooks/Se ejecutan en eventos del harness; registran aprobaciones y estadoNo
tools/Utilidades que invocan los hooks y el propio cicloNo
settings.jsonPermisos, hooks cableados y mensaje de bienvenidaSolo con criterio

Los hooks son la pieza que más gente subestima. Sin ellos, un gate puede aprobarse en la conversación pero no quedar registrado, y entonces el estado y la auditoría divergen. Por eso el doctor comprueba que cada hook declarado en settings.json existe de verdad y que no están desactivados globalmente.

aidlc/: el registro

Es la parte que se lee, se revisa y se discute. Tres zonas:

  1. memory/: las reglas. org.md son los defaults del framework; team.md y project.md se suman a ellos. phases/ permite reglas por fase y templates/ sobrescribe el formato de un artefacto concreto.
  2. knowledge/: el dominio. documents/ guarda tus originales —PDFs, Word, Markdown— tal cual; documentkb/ es el catálogo derivado que el motor indexa. Nunca reorganices los originales para que «encajen»: el índice se reconstruye.
  3. intents/: el trabajo. Cada iniciativa tiene su carpeta con aidlc-state.md, audit/ y los artefactos de cada etapa. intents.json es el registro global con alcance y estado.

Un intent no es una rama

Puede haber varias iniciativas en intents/ a la vez, cada una en una fase distinta. Git sigue siendo el que decide qué código está en qué rama; AI-DLC registra el trabajo y sus decisiones. Mezclar ambos modelos mentales produce carpetas de intent que no corresponden con ninguna rama.

El archivo de estado

aidlc-state.md es el corazón de cada intent. Es Markdown legible y contiene, como mínimo:

CampoQué responde
ScopeQué perfil se aplicó y con qué overrides
Phase / StageDónde está el trabajo ahora mismo
Depth / Test strategyCon cuánto detalle y cuántas pruebas
Review overrideSi el techo de revisión se cambió para esta ejecución
DecisionesQué se aprobó, cuándo y quién lo hizo
PlanUnidades y orden, con las etapas saltadas marcadas

Si alguna vez dudas de qué está pasando, este archivo es la respuesta. No hace falta preguntar al agente: /aidlc --status es una vista de este documento.

CLAUDE.md: contexto ambiental

Claude Code lo lee al arrancar en el proyecto. Es el sitio para lo que quieres que el agente sepa siempre: cómo se arranca, cómo se prueban las cosas, qué convenciones son innegociables y qué archivos no debe tocar. No es el sitio para el método de AI-DLC: eso vive en memory/, que es neutral y lo leen también otros harnesses.

# inventario

API REST de inventario en Node.js 22, módulos ESM, sin build.

## Comandos
- `node --test` — suite completa
- `node src/cli.mjs --help` — CLI

## Convenciones
- Errores de dominio con códigos estables; nunca mensajes como contrato.
- Sin dependencias nuevas sin ADR en `docs/adr/`.
- No editar `dist/` ni `aidlc/` a mano.

## Zonas sensibles
- `src/pagos/` — revisar con dos personas.

La regla práctica: si otra persona lo necesita para trabajar, va en CLAUDE.md o en el README; si es una regla de cómo AI-DLC debe comportarse, va en memory/; si es una preferencia tuya, no va a ningún sitio versionado.

aidlc doctor: leer el diagnóstico

El comando agrupa las comprobaciones en tres bloques. Cada uno responde a una pregunta distinta:

BloquePreguntaQué mira
Machine¿El motor puede ejecutarse desde aquí?Ruta del binario, PATH del sistema frente al de la shell, runtime
Project (.claude, Claude Code)¿La proyección está completa y activa?Hooks presentes, hooks habilitados, estructura, registros sin commitear, estado
Framework integrity¿Los archivos del motor están íntegros y son coherentes?Versión y checksum de la distribución

Añade --verbose para ver todas las comprobaciones, incluidas las que pasan. El veredicto final separa problems de warnings: los primeros bloquean, los segundos son avisos que puedes ignorar si todo funciona.

Los tres avisos que verás siempre al principio

AvisoPor qué apareceQué hacer
Runtime hook PATH: aidlc is on this shell's PATH but not on the system-wide PATH Instalaste en tu usuario. Claude Code hereda el PATH de la terminal, así que funciona; solo fallaría si lo lanzas desde un icono o un servicio. Nada si arrancas desde terminal. Si lo lanzas desde el escritorio, añade la ruta al PATH del sistema.
AIDLC hooks have not run in this project yet Los hooks se ejecutan al arrancar Claude Code en esa carpeta; todavía no ha pasado. Nada. Desaparece tras la primera sesión.
Workspace records: N uncommitted change(s) under aidlc/ Los registros viajan por Git; si no los commiteas, tus compañeros no los ven. git add aidlc/ && git commit && git push

Un aviso que sí es un problema

Si el doctor dice que disableAllHooks está resuelto a true, los hooks existen pero no se ejecutan: los gates se aprobarán sin registrarse. Recorre las capas de configuración que indica el mensaje —gestión empresarial, settings.local.json, settings.json del proyecto, configuración global— y corrige la que gane.

Version skew: cuando el proyecto y el motor no son de la misma release

Cada proyecto guarda la versión con la que se generó. Si el binario instalado es más nuevo o más viejo, las etapas pueden no coincidir con los artefactos esperados. El doctor compara el sello del proyecto con el motor que lo sirve y avisa si hay desajuste: un warn del tipo «Project stamp 2.3.0 · engine 2.4.1» con la sugerencia de ejecutar aidlc config --harness claude.

La solución casi siempre es refrescar la proyección. Lo que no conviene es ignorarlo durante semanas: un archivo de etapa actualizado puede esperar un campo que el artefacto antiguo no tiene, y el fallo aparecerá como «sensor que no encuentra la sección» en lugar de como desajuste de versión.

3 · Ejemplo mínimo

Tres comandos para saber si el proyecto está sano y qué contiene.

aidlc doctor
find aidlc -maxdepth 4 -type d | sort
sed -n '1,40p' aidlc/spaces/default/memory/team.md

Y la salida que quieres ver en un proyecto bien configurado:

AI-DLC doctor

Machine
  ok    9 checks passed

Project (.claude, Claude Code)
  ok    49 checks passed

Framework integrity
  ok    all 12 checks passed

0 problems, 0 warnings.

Ese «0 warnings» solo es estable después de la primera sesión y de un commit. Antes, los tres avisos de la sección anterior son la firma de un proyecto nuevo, no de un proyecto roto.

El doctor no revisa tu código

No ejecuta tests ni compila. Comprueba que AI-DLC puede trabajar: hooks, versiones, estructura. Si tu suite falla, el doctor dirá que todo está en orden porque el problema está en otra capa.

4 · Ejemplo real

Bruno se incorpora al equipo de inventario y clona el repositorio. Su primer aidlc doctor no está limpio, y eso es una oportunidad para ver los diagnósticos en contexto.

$ aidlc doctor
AI-DLC doctor

Machine
  warn  Runtime hook PATH: aidlc is on this shell's PATH
        but not on the system-wide PATH
  ok    9 checks passed

Project (.claude, Claude Code)
  warn  AIDLC hooks have not run in this project yet
  warn  Workspace records: 12 uncommitted change(s) under aidlc/
  ok    49 checks passed

Framework integrity
  warn  Project stamp 2.3.0 · engine 2.4.1
  ok    all 12 checks passed

0 problems, 3 warnings.

Qué hace Bruno, en orden:

  1. PATH: no hace nada. Arranca Claude Code desde la terminal, que hereda su PATH. Si algún día lo lanza desde una aplicación de escritorio y los hooks no se ejecutan, ya sabe dónde mirar.
  2. Hooks sin ejecutar: abre claude en la carpeta, ejecuta /aidlc --status y sale. El aviso desaparece porque los hooks ya corrieron una vez.
  3. Registros sin commitear: aquí hay una decisión. Los 12 cambios pueden ser del trabajo de Ana, que aún no ha subido, o de la propia configuración. Bruno mira el diff antes de tocar nada.
  4. Version skew: ejecuta aidlc config --harness claude para refrescar la proyección a 2.4.1 y revisa el diff: no debería cambiar reglas, solo archivos del motor.
git log --oneline -5
git status --short aidlc/
git diff --stat aidlc/ | tail -3

El diff le dice que los 12 cambios son artefactos de una iniciativa en curso, no ruido. No los commitea: son de Ana. Commitea solo el refresco de versión, en una rama aparte, y avisa al equipo.

La analogía del cuadro de mandos

El doctor es el panel de testigos del coche. La luz de presión de neumáticos no te dice si la carretera es buena; te dice que revises algo del vehículo. Ignorarla porque «el coche anda» funciona hasta que deja de andar en el peor sitio.

5 · Buenas prácticas

HazEvitaPor qué
Ejecutar aidlc doctor antes de cada sesión importante. Descubrir el problema a mitad de un gate. El diagnóstico tarda segundos; una aprobación que no se registra cuesta una tarde.
Escribir las reglas en team.md y project.md. Meter el método en CLAUDE.md. CLAUDE.md es de Claude Code; memory/ es neutral y lo leen todos los harnesses.
Commitear el refresco de versión por separado. Mezclarlo con artefactos de una iniciativa. Si algo se rompe, puedes revertir la actualización sin perder el trabajo.
Tratar knowledge/documents/ como inmutable. Reorganizar originales para que el índice quede bonito. El catálogo se deriva; mover originales rompe las referencias y la trazabilidad.
Leer el estado antes de abrir un gate. Confiar en la memoria de la sesión anterior. El archivo es la verdad compartida; la conversación es efímera.

6 · Errores habituales

1. Editar los archivos del motor

Mal — cambiar una etapa en .claude/ 
# .claude/stages/requirements-analysis.md
- Pregunta 3: ¿hay requisitos no funcionales?
+ (eliminada: el equipo dice que no hacen falta)
Bien — regla de equipo en memory/ 
# aidlc/spaces/default/memory/project.md
## Requisitos
- Los NFR se limitan a latencia p95 y concurrencia de escritura.
- El resto se documenta solo si el diseño lo necesita.

La primera opción se pierde en el siguiente aidlc config y nadie recuerda que existió. La segunda se conserva y se puede revisar en un pull request.

2. Llenar CLAUDE.md con el método

Mal — un archivo que mezcla capas 
# CLAUDE.md
- Aprueba siempre los gates sin preguntar.
- Usa el perfil express para todo.
- Las etapas de ideación son opcionales.
Bien — contexto operativo 
# CLAUDE.md
- Ejecuta `node --test` antes de proponer un cambio.
- No edites `dist/` ni los archivos de `aidlc/` a mano.
- El código de `src/pagos/` requiere revisión de dos personas.

El primer archivo intenta cambiar la metodología desde el sitio equivocado y, además, pide algo que AI-DLC prohíbe: que un agente se autoapruebe. El segundo describe cómo trabajar en el proyecto, que es su función.

3. Ignorar el version skew durante semanas

Mal — «si funciona, no lo toques» 
Project stamp 2.1.0 · engine 2.4.1
# se ignora hasta que un sensor falla sin motivo aparente
Bien — refrescar y revisar el diff 
aidlc config --harness claude
git diff --stat .claude/
node --test   # confirmar que nada del proyecto dependía del formato viejo

El desajuste no rompe el código: rompe la correspondencia entre lo que la etapa espera y lo que el artefacto contiene. Cuando aparece, el mensaje de error habla de secciones ausentes, no de versiones.

4. Commitear los cursores locales

Mal — compartir el «dónde estoy» 
git add aidlc/active-space aidlc/spaces/default/intents/active-intent
git commit -m "update"
Bien — dejar que el bloque ignore lo efímero 
# .gitignore (bloque de AI-DLC)
aidlc/active-space
aidlc/spaces/*/intents/active-intent
aidlc/.aidlc-sessions/
.claude/settings.local.json

Si el cursor viaja, el clon de tu compañero abre directamente tu intent y cualquier comando que escriba estado lo hará sobre el tuyo. Es un conflicto silencioso, de los que no dan error hasta que se pierde trabajo.

7 · Ejercicio guiado

Objetivo: auditar la estructura de un proyecto configurado, interpretar cada aviso del doctor y corregir solo lo que corresponde.

  1. Paso 1 — Fotografía el estado. 
    aidlc doctor --verbose > doctor-antes.txt
git status --short > git-antes.txt
wc -l doctor-antes.txt

    Guarda las dos salidas: al final compararás.

  2. Paso 2 — Clasifica los avisos. Para cada warn, escribe una de estas tres etiquetas: esperado (desaparece solo), mío (lo arreglo yo) o del equipo (lo hablo con alguien). No actúes todavía.
  3. Paso 3 — Recorre el árbol. 
    find .claude -maxdepth 2 -type d | sort
find aidlc/spaces/default -maxdepth 3 -type d | sort

    Localiza memory/, knowledge/ e intents/. Abre team.md y comprueba si está vacío o tiene reglas reales.

  4. Paso 4 — Lee un estado completo. 
    find aidlc -name aidlc-state.md
cat <ruta-encontrada>

    Identifica scope, fase, etapa y la última decisión. Si no hay ningún intent todavía, crea uno mínimo con /aidlc y vuelve a leerlo.

  5. Paso 5 — Corrige lo tuyo. Commitea los registros pendientes si son tuyos, refresca la proyección si hay skew y ejecuta una sesión corta si faltan hooks por correr. No toques lo que sea de otra persona.
  6. Paso 6 — Compara. 
    aidlc doctor --verbose > doctor-despues.txt
diff doctor-antes.txt doctor-despues.txt

    Deberías ver menos avisos y ningún problema nuevo. Si aparece uno, has tocado algo que no debías: revisa el diff con git diff.

Resultado esperado

Una tabla con tres columnas —aviso, etiqueta, acción— y un doctor con menos ruido. Lo importante no es llegar a cero avisos, sino saber cuáles puedes ignorar con motivo.

8 · Reto

🎯 El team.md mínimo útil

Escribe las primeras diez reglas del equipo en aidlc/spaces/default/memory/team.md. Cada regla debe cumplir tres condiciones: es comprobable, cambia una decisión concreta y no repite algo que ya hace el framework.

Después clasifícalas: ¿cuáles son de estilo, cuáles de riesgo y cuáles de proceso? Si más de la mitad son de estilo, probablemente estás usando el archivo para gustos personales en lugar de para acuerdos del equipo.

Pista: una buena regla suena a «en escrituras compartidas, test de concurrencia obligatorio», no a «escribe código limpio». La segunda no se puede comprobar y, por tanto, no se puede saltar con criterio.

9 · Resumen

  • .claude/ es el motor; aidlc/ es el registro; CLAUDE.md es el contexto ambiental.
  • Dentro de aidlc/: memory/ son las reglas, knowledge/ el dominio e intents/ el trabajo.
  • Cada intent tiene su aidlc-state.md, su audit/ y sus artefactos por etapa.
  • Los cursores active-space y active-intent son locales y no se versionan.
  • aidlc doctor revisa máquina, proyecto e integridad del framework; los avisos no bloquean, los problemas sí.
  • El version skew se corrige refrescando la proyección con aidlc config, no editando archivos.

10 · Preguntas frecuentes

¿Puedo borrar audit/ para empezar limpio?

Puedes, pero pierdes exactamente lo que hace valioso el ciclo: la capacidad de reconstruir por qué se decidió algo. Si el objetivo es empezar una iniciativa nueva, crea un intent nuevo; si el objetivo es reducir ruido, archiva el anterior. Borrar el rastro y conservar el estado deja un proyecto que dice «aprobado» sin poder demostrarlo.

¿El doctor arregla los problemas que encuentra?

No. Informa y, en algunos avisos, sugiere el comando concreto. Las correcciones son decisiones: commitear registros, refrescar la proyección o cambiar una capa de configuración. Automatizarlas sin leer sería justo lo contrario de lo que AI-DLC propone.

¿Qué diferencia hay entre aidlc doctor y /aidlc --doctor?

El primero es el comando del binario y comprueba la instalación y el proyecto desde fuera del harness. El segundo se ejecuta dentro de la sesión y añade comprobaciones específicas del harness, como la presencia de cada hook cableado o la estructura del proyecto. Si algo falla dentro de Claude Code, empieza por el segundo.

¿Debo versionar knowledge/documents/ con PDFs grandes?

Si el equipo los necesita para trabajar, sí: son parte de la verdad compartida. Para documentos muy pesados, una alternativa es referenciarlos y mantenerlos en un almacén externo, pero entonces pierdes la ventaja de que el agente los lea sin configuración adicional. Decide según tamaño y frecuencia de cambio, no por defecto.
