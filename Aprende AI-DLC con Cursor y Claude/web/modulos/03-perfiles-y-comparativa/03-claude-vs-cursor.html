Claude Code vs Cursor

Módulo 3 · Perfiles y comparativa 🕐 35 minutos

1 · Introducción

La pregunta «¿cuál es mejor?» no tiene respuesta porque no compiten en lo mismo. Claude Code es una terminal con un agente dentro; Cursor es un editor con un agente al lado. Para AI-DLC, ambos ejecutan el mismo ciclo y escriben en el mismo sitio. La decisión útil no es cuál elegir para siempre, sino cuál usar en cada momento.

Hay una trampa frecuente: comparar prestaciones aisladas —«Cursor tiene diffs más bonitos», «Claude Code tiene status line»— y concluir que uno gana. En un ciclo con gates, lo que importa es dónde se revisa, quién decide y qué se puede automatizar. Ahí las diferencias son reales y estables.

Esta lección pone las dos herramientas en la misma tabla, con lo que es idéntico, lo que difiere y lo que decide el uso. Sin favoritos.

Por qué existe esta lección

Porque los equipos acaban discutiendo de herramientas en lugar de discutir de riesgo. Una tabla honesta convierte la discusión en una política: «las etapas con revisión de diseño, en Cursor; la construcción y la automatización, en Claude Code».

2 · Teoría

Lo que es idéntico

  • El core: fases, etapas, perfiles, agentes, sensores y gates.
  • El estado: aidlc/ con sus espacios, intents, artefactos y auditoría.
  • Los 14 roles: 11 domain experts, 2 reviewers y 1 composer.
  • El significado de un gate: aprobar, cambiar, saltar o rechazar; nunca lo decide un agente.
  • Los sensores deterministas: secciones, fuentes, cobertura, trazabilidad, linter, type-check.
  • La portabilidad: una iniciativa puede empezar en un harness y continuar en el otro.

Todo lo que no esté en esa lista es una diferencia de superficie, y las diferencias de superficie importan mucho menos de lo que parece cuando el estado está en el repositorio.

Las tres diferencias que sí deciden

1. Dónde vive la revisión

En Cursor, el artefacto y el código están en el mismo editor: puedes abrir el diseño a la izquierda y el handler a la derecha, y el revisor ancla sus hallazgos a líneas concretas. En Claude Code, la revisión es textual y cambiando de ventana. Para etapas de diseño con varios revisores humanos, el IDE ahorra fricción real.

2. Qué se puede automatizar

Claude Code está pensado para la terminal y se integra bien en scripts. Cursor tiene agent -p para modo headless, pero con un límite duro: no puede presentar ni aprobar un gate. Si tu automatización necesita recorrer el ciclo, no puedes hacerlo en ninguno de los dos sin una persona; si solo necesita consultar o preparar, ambos sirven.

3. Qué se rompe si falta Git

En Cursor, un proyecto sin repositorio puede perder los hooks y, con ellos, el registro de aprobaciones. En Claude Code el riesgo es menor, pero el historial sigue siendo la red de seguridad del ciclo. La conclusión práctica es la misma para ambos: Git no es opcional.

Comparar precios de lista sin más es engañoso, porque el coste real lo determina el perfil y el número de etapas. Un equipo que usa feature para todo paga mucho más que uno que clasifica bien, con cualquiera de las dos herramientas.

Qué no cambia al cambiar de harness

Vale la pena tenerlo escrito, porque es lo que permite cambiar sin miedo: el número de etapas lo decide el perfil, no la herramienta; los sensores son los mismos programas; un gate rechazado en Cursor se ve rechazado en Claude Code porque el evento está en la auditoría; y la versión del motor es la misma para ambos, porque se instala una vez.

La consecuencia práctica es que la comparación honesta no se hace entre interfaces, sino entre dos ejecuciones del mismo scope sobre el mismo proyecto. Todo lo demás es preferencia.

Hay tres cosas que sí conviene verificar cuando cambias, porque son las que pueden dar una falsa sensación de continuidad:

  • Que el segundo harness lee la misma versión de la proyección (aidlc doctor).
  • Que el gate pendiente es el mismo y no se ha duplicado.
  • Que el modelo configurado es el que el equipo acordó, no el que trae tu cuenta por defecto.

La analogía del taller y la oficina

Cursor es la mesa de dibujo: ves el plano y la pieza juntos, y puedes señalar con el dedo. Claude Code es el banco de trabajo: herramientas en fila, espacio para martillar y un script para repetir lo que ya sabes. Ninguno sustituye al otro; el equipo cambia de sitio según lo que toca.

3 · Ejemplo mínimo

La misma etapa, dos sitios. Solo cambia cómo se pide y cómo se ve.

# Claude Code
cd ~/proyectos/inventario
claude
> /aidlc --status
> /aidlc --stage design
# Cursor (CLI)
cd ~/proyectos/inventario
agent
> /aidlc-status
> /aidlc-jump --stage design

Y en el IDE de Cursor, lo mismo desde el panel del agente. El artefacto que se produce es idéntico, en la misma ruta, con los mismos sensores y el mismo gate.

aidlc/spaces/default/intents/260302-reserva-stock/
└── inception/design/design.md      ← el mismo archivo en ambos casos

Si abres ese archivo después de ejecutar la etapa en cada harness, no podrás distinguir cuál lo escribió. Esa es la prueba de que el harness es sustituible y el estado, no.

Compara artefactos, no interfaces

Si quieres saber qué herramienta funciona mejor para tu equipo, ejecuta la misma etapa en ambas y compara el artefacto, el número de preguntas y el tiempo hasta el gate. La interfaz te dirá cuál te gusta más; el artefacto te dirá cuál produce mejor trabajo.

4 · Ejemplo real

El equipo de inventario adopta una política mixta tras dos meses de uso. No es una preferencia: es el resultado de medir dónde se atascaban.

FaseHarnessMotivo observado
Ideation e InceptionCursorProducto revisa el artefacto al lado del código y aprueba con contexto
ConstructionClaude CodeSesiones largas, comandos, tests; menos cambios de ventana
Revisión finalCursorDiff completo con el artefacto de requisitos abierto
Consultas y scriptsCLI de Cursoragent -p para informes sin abrir nada
OperationClaude CodeDespliegue y logs en terminal

El cambio de harness ocurre en gates, no a mitad de etapa. El procedimiento que acordaron:

1. /aidlc-status en el harness actual
2. si hay gate pendiente: resolverlo antes de cambiar
3. commit del estado y los artefactos
4. abrir el otro harness en la misma raíz
5. /aidlc --status y confirmar que coincide
6. continuar

El paso 3 es el que más discusiones evitó. Sin commit, el segundo harness ve un estado a medias y la tentación es «arreglarlo» a mano.

Lo que no funcionó

Intentaron usar el agente en segundo plano de Cursor para avanzar Construction mientras el equipo comía. Se detuvo en el primer gate y dejó una etapa a medias que nadie sabía si estaba aprobada. La conclusión fue unánime: el trabajo sin gates se automatiza; el trabajo con gates se conduce.

5 · Buenas prácticas

HazEvitaPor qué
Elegir harness por tipo de etapa, no por persona. Que cada uno use el que le gusta y el estado se bifurque. La política compartida hace comparables los costes y los resultados.
Resolver los gates pendientes antes de cambiar de harness. Cambiar a mitad de decisión. Un gate abierto en dos sitios es una invitación a la incoherencia.
Commitear estado y artefactos antes de cambiar. Dejar cambios sin commitear en el árbol. El segundo harness no distingue lo tuyo de lo del ciclo.
Mantener un solo aidlc.settings.json si queréis modelos comparables. Configurar modelos distintos sin registrarlo. Si los resultados difieren, no sabrás si es la herramienta o el modelo.
Documentar la política en el README del proyecto. Dejarla en la cabeza del tech lead. Una persona nueva debe saber dónde empezar sin preguntar.

6 · Errores habituales

1. Declarar un ganador absoluto

Mal — la discusión de hinchas 
"Cursor es mejor porque ves el diff."
"Claude Code es mejor porque es más rápido."
Bien — decidir por etapa 
"Diseño y revisión → Cursor.
 Construcción y operación → Claude Code.
 Automatización de lectura → CLI de Cursor."

Ninguna de las dos frases del primer bloque es falsa, y ninguna sirve para decidir. La segunda sí: nombra el trabajo y el criterio.

2. Duplicar la configuración por harness

Mal — dos métodos 
aidlc-cursor/spaces/default/memory/team.md
aidlc-claude/spaces/default/memory/team.md
Bien — un registro, dos proyecciones 
aidlc/spaces/default/memory/team.md     ← único
.claude/                                 ← proyección
.cursor/                                 ← proyección

Dos copias del método divergen en una semana. Cuando eso pasa, el equipo deja de saber cuál es la regla vigente y empieza a ignorarlas todas.

3. Esperar paridad exacta de funciones

Mal — asumir que todo existe en ambos 
"En Cursor también hay status line, ¿no?"
Bien — comprobar por harness 
Claude Code: status line opcional
Cursor:      /aidlc-status y línea de progreso en cada gate

Cada harness proyecta el mismo motor con sus propias capacidades. Lo que no existe en uno se sustituye con un comando, no se inventa.

4. Automatizar un ciclo completo en headless

Mal — el pipeline que aprueba solo 
agent -p "/aidlc --scope feature implementa y aprueba los gates"
Bien — automatizar la preparación 
agent -p "resume los gates pendientes y el estado de cada intent"
# la decisión se toma en una sesión interactiva

Ningún harness permite que un agente se autopruebe un gate. El intento no acelera: deja el ciclo detenido en un sitio donde nadie lo ve.

7 · Ejercicio guiado

Objetivo: comparar los dos harnesses con la misma etapa y decidir la política del equipo con datos.

  1. Paso 1 — Configura ambos en el mismo repo de laboratorio. 
    aidlc config --harness claude
aidlc config --harness cursor
aidlc doctor

    Verifica que aidlc/ es único y que ambos settings apuntan a la misma versión.

  2. Paso 2 — Ejecuta una etapa en Claude Code. Elige requirements-analysis con --scope express --depth minimal. Anota: tiempo hasta el gate, número de preguntas y longitud del artefacto.
  3. Paso 3 — Ejecuta la misma etapa en Cursor. Abre una iniciativa nueva con el mismo scope y el mismo enunciado. Anota los mismos tres números.
  4. Paso 4 — Compara los artefactos. 
    diff aidlc/spaces/default/intents/<claude>/inception/requirements-analysis/requirements.md \
     aidlc/spaces/default/intents/<cursor>/inception/requirements-analysis/requirements.md

    Ignora el formato. Busca diferencias de contenido: supuestos, casos límite, requisitos no funcionales.

  5. Paso 5 — Prueba el cambio de harness. Resuelve el gate en Claude Code, commitea, abre Cursor y ejecuta /aidlc-status. Debe mostrar el mismo estado. Continúa una etapa en Cursor y vuelve.
  6. Paso 6 — Escribe la política. Tres líneas: qué etapa en qué harness y por qué. Añádela al README y pruébala durante una semana antes de darle categoría de norma.

Resultado esperado

Dos artefactos comparables, un cambio de harness sin pérdida de estado y una política escrita. Si los artefactos difieren mucho en contenido con el mismo scope, el factor no es la herramienta: es el modelo configurado o el contexto del proyecto.

8 · Reto

🎯 El cuadro de mando de la decisión

Diseña una tabla de una página que permita a cualquier persona del equipo decidir en qué harness empieza un trabajo, sin consultarte. Debe partir de dos o tres preguntas sobre el trabajo —no sobre la herramienta— y terminar en una recomendación con su motivo.

Después añade la columna que casi nadie pone: «qué se pierde si empiezo en el otro». Si esa columna está vacía en todas las filas, tu tabla no está decidiendo nada.

Pista: la pregunta que más discrimina es «¿quién va a mirar el artefacto y desde dónde?». Si la respuesta es una persona de producto que vive en el editor, la recomendación se cae sola.

9 · Resumen

  • El core, el estado, los agentes y los gates son idénticos; cambia la superficie.
  • Claude Code: terminal, status line, construcción y automatización.
  • Cursor: IDE, diffs con contexto, revisión de diseño y trabajo de producto.
  • Cursor necesita Git para que los hooks registren aprobaciones.
  • Ninguno permite aprobar gates en headless; la decisión es siempre humana.
  • La política se define por etapa, se escribe en el README y se mide.
  • Un solo aidlc/: duplicarlo rompe la trazabilidad.

10 · Preguntas frecuentes

¿Puedo trabajar con los dos a la vez en la misma rama?

Puedes, pero con cuidado: cada uno tiene su intent activo local, y dos sesiones simultáneas sobre la misma iniciativa pueden escribir artefactos distintos. Lo recomendable es alternar, no solapar. Si necesitas paralelismo, usa intents separados.

¿Los artefactos son exactamente iguales en ambos?

El formato lo define el motor y las plantillas del equipo, así que deberían ser comparables. Pueden variar en detalle porque el modelo y el contexto no son idénticos. Esa variación es la que conviene medir si te importa la consistencia.

¿Cuál es más barato?

Depende del plan y del perfil, no del harness. El coste dominante es el número de etapas y el contexto leído. Un equipo que usa express con criterio gasta menos que uno que usa feature para todo, con cualquiera de los dos.

¿Cursor puede hacer todo lo que hace Claude Code?

Casi todo lo que importa para el ciclo, con dos límites claros: no tiene status line y su modo headless no puede aprobar gates. A cambio ofrece revisión visual y atajos propios. La pregunta útil no es de paridad, sino de encaje con la etapa.

¿Puedo medir cuál me conviene con datos?

Sí: ejecuta el mismo scope y el mismo enunciado en ambos, y compara tiempo hasta el primer gate, número de preguntas, longitud del artefacto y número de cambios pedidos. Con dos o tres repeticiones tendrás una señal más fiable que cualquier opinión, y además sabrás si la diferencia viene del harness o del modelo configurado.
