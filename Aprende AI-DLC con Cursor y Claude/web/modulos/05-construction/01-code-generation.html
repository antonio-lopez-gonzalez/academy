Code generation

Módulo 5 · Construction 🕐 40 minutos

1 · Introducción

Construction empieza con una comprobación que parece trivial y que evita la mitad de los desastres: ¿el plan está aprobado y sigue siendo el mismo que se aprobó? Si la huella no coincide, no se genera código. Si coincide, el agente sabe exactamente qué unidad le toca, qué archivos puede tocar y qué comando demostrará que terminó.

Generar código con un agente no es pedir «hazme la API». Es ejecutar una unidad de trabajo con contexto acotado, restricciones explícitas y una verificación definida de antemano. El agente lee el diseño, la unidad, las reglas del equipo y el código vecino; propone un diff; lo escribe; ejecuta el comando de verificación; y se detiene en el checkpoint. Nada de eso ocurre «de una vez»: ocurre dentro de un bucle con límites.

La diferencia entre un agente útil y un agente peligroso no está en el modelo. Está en el contexto que recibe y en lo que se le permite hacer. Un agente con acceso a todo el repositorio y sin fences tomará decisiones que nadie revisó: cambiará una dependencia, tocará una migración, renombrará una tabla «para que quede más limpio». Un agente con una unidad, un alcance y un test hace exactamente lo pedido, y cuando no puede, se detiene y lo dice.

El plan es el contrato de generación

La calidad del código generado depende menos del prompt que del plan que lo precede. Si la unidad tiene un criterio de aceptación verificable y un alcance claro, el agente tiene un objetivo. Si el plan dice «implementar stock», el agente improvisará la arquitectura, el modelo y los errores. Code generation no arregla un plan malo; lo amplifica.

2 · Teoría

Precondiciones: lo que debe ser cierto antes de escribir

CondiciónCómo se compruebaSi falla
Plan aprobadoExiste un gate plan con decisión approved.No se genera código; se vuelve al gate.
Huella vigenteEl hash del plan y el diseño coincide con el aprobado.Re-aprobación del plan.
Unidad seleccionadaLa unidad existe, está desbloqueada y tiene verificación.Se elige otra unidad o se corrige el plan.
Fences definidosLa unidad declara rutas permitidas y acciones prohibidas.Se completan antes de generar.
Reglas cargadasLas reglas de org, equipo y proyecto están proyectadas al harness.Se ejecuta sync antes de empezar.

Estas comprobaciones no son ceremonia: son las que impiden que el agente «empiece por algo» mientras el plan sigue en revisión. Si el workflow permite generar sin plan aprobado, el gate de plan deja de tener sentido y todo Inception se convierte en documentación decorativa.

Contexto: lo justo, no todo

Un agente con demasiado contexto se distrae; con demasiado poco, inventa. La ventana útil para una unidad suele incluir:

  • La unidad — requisitos, alcance, aceptación y comando de verificación.
  • El diseño relevante — modelo de datos, contrato del endpoint y ADR que afecten a la unidad.
  • Las reglas del equipo — estilo, errores, seguridad, convenciones de nombres.
  • El código vecino — el módulo más parecido ya construido, para imitar patrones en lugar de inventarlos.
  • Los tests existentes — el estilo de prueba y las utilidades disponibles.

Lo que no hace falta: el repositorio entero, el historial de commits de tres años ni la documentación de todas las integraciones. El agente no necesita «saberlo todo»; necesita saber qué se espera de esta unidad y qué límites tiene.

Anatomía de una instrucción de etapa

AI-DLC no ejecuta una etapa con un prompt libre. Ejecuta una instrucción con seis partes. El texto exacto cambia entre versiones, pero la estructura es estable:

ParteQué contieneEjemplo
ObjetivoUna capacidad, no una lista.Implementar U1: consultar disponibilidad por SKU.
ContextoDiseño, requisitos y código vecino.FR-01, contrato GET /stock/:sku, módulo movements.
RestriccionesFences, reglas y prohibiciones.Solo tres archivos; sin dependencias nuevas; sin tocar migraciones.
AceptaciónCriterios observables.10 físicas y 3 reservadas → 7; SKU inexistente → 404.
VerificaciónComando exacto y salida esperada.node --test test/availability.test.mjs
ParadaCuándo detenerse en vez de improvisar.Si falta el contrato, no inventarlo: preguntar.

Fences: el alcance como restricción ejecutable

Un fence no es una recomendación en un comentario. Es una lista que el harness puede comprobar antes o después de escribir:

## Alcance permitido
- src/stock/availability.mjs
- src/http/routes/stock.mjs
- test/availability.test.mjs

## Prohibido sin aprobación
- package.json y dependencias.
- migrations/ y cambios de esquema.
- .env, secretos y configuración de despliegue.
- Cualquier archivo fuera de src/stock y src/http/routes.

Los fences resuelven un problema real: el agente «arregla» cosas que no le pediste. A veces el arreglo es correcto, pero rompe el alcance de la unidad y mezcla cambios que deberían revisarse por separado. Un diff de tres archivos se revisa; un diff de veintitrés se aprueba con la esperanza de que no explote.

El bucle de generación

leer unidad + diseño + reglas
        │
        ▼
proponer plan de cambios (archivos, orden)
        │
        ▼
escribir diff acotado ──▶ ejecutar verificación
        │                        │
        │                   falla ──▶ diagnosticar
        │                        │        │
        │                        │        └──▶ ¿requisito ambiguo? → parar
        │                        ▼
        └────────────────── pasa ──▶ checkpoint humano

El bucle no es infinito. Si la verificación falla tres veces por la misma causa, el agente debe parar y explicar qué no puede resolver. Si el problema es un requisito ambiguo, no debe elegir la interpretación más conveniente: debe devolver la pregunta al humano.

Revisar el diff: qué mirar

El humano no revisa línea a línea como en un examen. Revisa las decisiones:

  • ¿Hace lo que la unidad pide, ni más ni menos? Archivos tocados, endpoints añadidos, campos inventados.
  • ¿Los errores son los del contrato? Códigos, mensajes y estados HTTP.
  • ¿Hay cambios de comportamiento no cubiertos por tests? Validaciones nuevas, defaults, orden de operaciones.
  • ¿Se ha colado una dependencia, un secreto o una migración? El fence lo detecta; el ojo humano lo confirma.
  • ¿El test prueba el comportamiento o la implementación? Un test que verifica que se llamó a una función interna no demuestra el criterio de aceptación.
  • ¿El diff es revisable? Si no cabe en una pantalla, la unidad estaba mal cortada.

Cuándo parar en lugar de generar

Un agente bien configurado tiene condiciones de parada explícitas. Las más útiles:

  1. El contrato o el requisito no existe o se contradice con el diseño.
  2. La implementación requiere una dependencia nueva o un cambio de esquema no previsto.
  3. El test de aceptación no se puede escribir con la información disponible.
  4. El cambio excede el alcance de archivos permitido.
  5. La verificación falla por una causa que el agente no puede diagnosticar con la evidencia disponible.

Parar no es fracasar. Es la conducta correcta cuando el plan no cubre la realidad. Lo que no se debe hacer es rellenar el hueco con una decisión inventada y seguir, porque esa decisión acabará en el diff sin que nadie la haya discutido.

Claude Code y Cursor: mismo trabajo, distinto cristal

En Claude Code el diff se revisa en la terminal, con el comando de verificación ejecutándose en la misma sesión. En Cursor el diff aparece en el editor, con aceptación por archivo o por bloque. La diferencia importante es de supervisión: Cursor permite revisar visualmente y editar antes de aceptar; Claude Code favorece un flujo de texto y comandos. En ambos, el fence y el checkpoint son los mismos, y en ambos el agente debe detenerse antes de que un humano cierre la unidad.

3 · Ejemplo mínimo

Una instrucción de etapa completa para U1, sin prosa alrededor. Esta es la unidad de trabajo que el agente recibe; todo lo demás es ruido.

# Etapa · U1 Consultar disponibilidad

## Objetivo
Implementar el cálculo de disponibilidad y el endpoint GET /stock/:sku.

## Contexto
- Requisito: FR-01 (10 físicas, 3 reservadas → 7; SKU inexistente → 404).
- Diseño: disponible = movimientos − reservas activas. No se almacena.
- Vecino: src/stock/movements.mjs ya expone `sumBySku(sku)`.
- ADR-01: stock calculado; caché de 5 s permitida.

## Alcance
- src/stock/availability.mjs
- src/http/routes/stock.mjs
- test/availability.test.mjs

## Prohibido
Dependencias nuevas, migraciones, cambios en movements.mjs.

## Verificación
node --test test/availability.test.mjs

## Parada
Si `sumBySku` no devuelve el almacén, no lo añadas por tu cuenta:
pregunta si el filtro por warehouse entra en U1 o en U4.

El diff esperado es pequeño y legible:

// src/stock/availability.mjs
export function calculateAvailability({ physical, reserved }) {
  if (!Number.isInteger(physical) || !Number.isInteger(reserved)) {
    throw new TypeError("physical and reserved must be integers");
  }
  if (physical < 0 || reserved < 0) {
    throw new RangeError("stock values cannot be negative");
  }
  return Math.max(0, physical - reserved);
}
// test/availability.test.mjs
import test from "node:test";
import assert from "node:assert/strict";
import { calculateAvailability } from "../src/stock/availability.mjs";

test("descuenta las reservas del stock físico", () => {
  assert.equal(calculateAvailability({ physical: 10, reserved: 3 }), 7);
});

test("nunca devuelve disponibilidad negativa", () => {
  assert.equal(calculateAvailability({ physical: 2, reserved: 5 }), 0);
});

Lo relevante no es el código: es que el agente sabía qué archivos tocar, qué no tocar, qué probar y cuándo parar. Si el diff hubiera incluido un cambio en movements.mjs, el fence lo habría señalado. Si el test no hubiera cubierto el caso negativo, el checkpoint lo habría detectado.

El humano revisa el diff en la terminal y detecta algo que el test no cubre: el endpoint devuelve 200 con physical: null cuando el SKU existe pero no tiene movimientos. No es un fallo del test de la unidad; es un caso que el requisito no especificó. La decisión correcta no es «arreglarlo sobre la marcha»: es registrar la ambigüedad y decidir si entra en U1 o se abre un requisito nuevo.

Checkpoint · U1

  FR-01 no define el caso. ¿Entra en U1 o se difiere?

2) Cambiar U1 para devolver 200 con ceros

> 2

[agente corrige availability.mjs y añade test]
✔ 3 tests passed
Checkpoint cerrado. Evidencia adjunta a reviews/checkpoint-u1.md.

Este es el valor real del checkpoint: no es un «ok» al final, es el punto donde una observación del diff se convierte en una decisión. Si el agente hubiera decidido por su cuenta devolver ceros, el contrato habría cambiado sin que nadie lo supiera. Si el humano hubiera aprobado sin mirar, el cambio habría llegado a producción como un comportamiento sorpresa.

La analogía del encargo a un artesano

No le pides «hazme un mueble» y le dejas el taller entero. Le das las medidas, la madera, el acabado y el plazo; le dices qué herramientas puede usar y qué no debe tocar. Luego revisas el mueble antes de que salga del taller. El agente es el artesano: cuanto mejor sea el encargo, menos sorpresas en la entrega.

5 · Buenas prácticas

HazEvitaPor qué
Generar una unidad por ejecución.«Genera toda la API de inventario».Una unidad produce un diff revisable y un checkpoint con sentido; un proyecto entero produce un diff que nadie lee.
Dar el código vecino como ejemplo de patrón.Pedir que «siga las convenciones» sin mostrar ninguna.El agente imita lo que ve; si no ve nada, inventa un estilo nuevo que el equipo tendrá que mantener.
Declarar el comando de verificación antes de generar.Improvisar el test después del código.El test escrito después tiende a describir lo que el código hace, no lo que el requisito pide.
Revisar el diff por decisiones, no por líneas.Aprobar porque «los tests pasan».Los tests solo cubren lo que alguien pensó; el diff muestra lo que nadie pensó.
Parar y preguntar cuando falta el contrato.Rellenar el hueco con una suposición razonable.La suposición se convierte en comportamiento y el comportamiento se convierte en contrato de facto.
Mantener el fence actualizado si el plan cambia.Ampliar el alcance «porque hacía falta».Un fence obsoleto produce violaciones legítimas que el equipo aprende a ignorar.

El diff que cabe en una revisión

Si el diff de una unidad supera las doscientas líneas, pregúntate si la unidad estaba bien cortada. No es una regla absoluta —hay refactors legítimos—, pero en un proyecto nuevo casi siempre indica que se mezclaron varias capacidades. Divide antes de generar, no después de revisar.

6 · Errores habituales

1. Empezar a generar antes de aprobar el plan

Mal — código antes de la decisión 
# ❌ el plan sigue en revisión, pero ya hay archivos
aidlc run --skip-plan-gate
git status
# modified: src/stock/availability.mjs
Bien — comprobar huella y gate 
# ✅ Construction solo si el plan está aprobado
node src/cli.mjs status
# phase: construction
# plan: approved · fingerprint 4c1e9a0b…
# next: U1

node src/cli.mjs run
# gate pendiente: plan → resolver antes de generar

El código escrito antes de la aprobación es el peor de los mundos: ya existe, pero nadie acordó construirlo. Si el plan cambia, el trabajo se tira o se adapta a la fuerza. La precondición no es un formalismo; es lo que protege el tiempo del equipo.

2. Un prompt gigante que mezcla unidades

Mal — una sola ejecución para todo 
Implementa la API de inventario completa: consulta, reserva, liberación,
sincronización con el ERP, métricas, tests y documentación. Usa las
mejores prácticas y añade lo que falte.
Bien — una unidad, un alcance, una verificación 
U1 · Consultar disponibilidad
Alcance: availability.mjs, routes/stock.mjs, availability.test.mjs
Aceptación: 10/3 → 7; SKU inexistente → 404; valores negativos → error.
Verificación: node --test test/availability.test.mjs
Parada: si falta el filtro por almacén, preguntar.

«Añade lo que falte» es una invitación a que el agente decida el alcance. La segunda versión deja claro qué se construye, qué se verifica y qué se hace cuando algo no encaja. La primera produce un diff que hay que reescribir para poder revisarlo.

3. Aceptar el diff porque los tests pasan

Mal — el test como única evidencia 
✔ 2 tests passed
[aceptar diff sin mirar]
# el diff añade una dependencia y cambia el orden de los movimientos
Bien — tests + revisión de decisiones 
✔ 2 tests passed
Diff: 3 archivos, +64 −0
- availability.mjs: cálculo y validación ✓
- routes/stock.mjs: contrato y 404 ✓
- test/availability.test.mjs: caso feliz y negativo ✓
- package.json: sin cambios ✓
- movements.mjs: sin cambios ✓

Los tests verifican lo que alguien escribió. No verifican que no se haya añadido una dependencia, que no se haya tocado una migración o que el contrato siga siendo el acordado. El diff es la evidencia de alcance; los tests son la evidencia de comportamiento. Se necesitan las dos.

4. Dejar que el agente añada dependencias en silencio

Mal — una librería nueva sin decisión 
{
  "dependencies": {
    "express": "^5.0.0",
    "zod": "^3.23.0",
    "pino": "^9.0.0"
  }
}
Bien — dependencia como cambio de plan 
El agente detecta que necesita validación de esquema.
No modifica package.json.
Propone: "Añadir zod como dependencia de runtime; justificación y
alternativa con validación manual en docs/adr/ADR-03.md".
El humano decide en gate; si se aprueba, se actualiza el plan.

Cada dependencia es una obligación de mantenimiento, seguridad y licencia. Un agente que la añade porque le resulta cómodo está tomando una decisión de arquitectura sin ADR. El fence de package.json convierte esa comodidad en una conversación.

7 · Ejercicio guiado

Objetivo: ejecutar una unidad de generación con fences, revisar el diff y cerrar un checkpoint con evidencia.

  1. Paso 1 — Comprueba las precondiciones: 
    node src/cli.mjs status
# Esperado: plan approved, fingerprint vigente, next U1

    Si el estado no muestra un plan aprobado, no sigas. Vuelve al gate de plan de la lección anterior.

  2. Paso 2 — Escribe la instrucción de etapa: copia la estructura de la sección 3 y ajústala a tu unidad. Incluye objetivo, contexto, alcance, prohibiciones, verificación y parada. 
    ## Verificación
node --test test/availability.test.mjs

## Parada
Si el repositorio no tiene `sumBySku`, no implementes la consulta
completa: pregunta si U1 incluye el repositorio o solo el cálculo.
  3. Paso 3 — Genera y observa el plan de cambios: antes de escribir, el agente debe proponer qué archivos tocará. Rechaza el plan si incluye archivos fuera del fence. 
    Plan propuesto:
1. src/stock/availability.mjs
2. src/http/routes/stock.mjs
3. test/availability.test.mjs
¿Aplico? [sí / no / editar]
  4. Paso 4 — Revisa el diff con una lista: 
    [ ] Solo aparecen los archivos del fence
[ ] No hay dependencias nuevas
[ ] No hay migraciones ni cambios de esquema
[ ] Los errores coinciden con el contrato
[ ] El test cubre caso feliz y caso infeliz
[ ] El diff cabe en una revisión
  5. Paso 5 — Ejecuta la verificación registrada: no un comando parecido; exactamente el de la unidad. 
    node --test test/availability.test.mjs
# ✔ 2 tests passed · 0 failed

    Guarda la salida en reviews/checkpoint-u1.md con la fecha y el resultado. Esa es la evidencia que el checkpoint adjuntará al estado.

  6. Paso 6 — Cierra el checkpoint con una decisión: aprueba, cambia o rechaza. Si detectas un caso no cubierto, conviértelo en observación y decide si entra en la unidad o se difiere. Un checkpoint sin decisión no está cerrado.

Resultado esperado

Un diff de tres archivos, la salida del comando de verificación y una nota de checkpoint con la decisión. Si el diff toca más archivos de los previstos, el fence funcionó: te avisó antes de que el cambio se mezclara con el resto.

8 · Reto

🎯 El middleware que toca todo

La unidad U4 necesita autenticación. El equipo descubre que no hay middleware y que añadirlo afecta a todas las rutas, incluidas las de U1, U2 y U3, que ya están cerradas. El cambio cabe en un archivo nuevo, pero también requiere modificar el arranque del servidor y los tests existentes. El plan aprobado no lo previó.

Decide cómo se ejecuta: ¿una unidad nueva U6 con su propio gate, una ampliación de U4 con re-aprobación del plan, o un cambio transversal que se aplica en todas las unidades? ¿Qué fences usas para que el agente no reescriba los tests de las unidades cerradas? ¿Cómo verificas que las rutas antiguas siguen funcionando?

Pista: un cambio transversal no es una unidad vertical. Si afecta a todas las rutas, necesita una estrategia de verificación distinta —tests de contrato sobre las rutas existentes— y probablemente un ADR. No lo metas en U4 solo porque U4 lo necesite primero.

9 · Resumen

  • Construction solo empieza con plan aprobado y huella vigente; si el plan cambia, vuelve el gate.
  • Se genera una unidad por ejecución, con contexto acotado y código vecino como referencia.
  • La instrucción de etapa tiene objetivo, contexto, restricciones, aceptación, verificación y parada.
  • Los fences limitan archivos y acciones; una dependencia nueva o una migración son cambios de plan, no detalles de implementación.
  • El humano revisa decisiones en el diff, no solo el resultado de los tests.
  • Si falta el contrato, el agente para y pregunta; no rellena el hueco con una suposición.
  • El checkpoint cierra la unidad con evidencia y una decisión registrada.

10 · Preguntas frecuentes

¿Puedo generar varias unidades en paralelo?

Sí, si son independientes y no comparten archivos. Es lo que AI-DLC llama swarm y se explica en la lección de unidades. Si comparten el modelo de datos o el mismo módulo, el paralelismo produce conflictos de merge y decisiones contradictorias. En ese caso, secuencial es más rápido que reconciliar después.

¿El agente puede modificar los tests existentes?

Solo si la unidad lo autoriza explícitamente. Cambiar un test para que pase es una forma de falsificar la evidencia. Si el test existente ya no representa el comportamiento acordado, el cambio se discute en el gate y se registra como cambio de requisito o de plan.

¿Qué hago si el agente propone un diseño distinto al aprobado?

Parar y decidir. Puede tener razón, pero no tiene autoridad para cambiar el diseño. Se compara la propuesta con el ADR, se documenta la alternativa y se lleva al gate correspondiente. Si se acepta, se actualiza el diseño y se recalcula la huella; si no, se le indica que implemente lo aprobado.

¿Cuánto contexto debe recibir el agente?

El necesario para la unidad: requisito, contrato, ADR relevante, reglas y código vecino. Más contexto no mejora automáticamente la calidad; a veces introduce patrones obsoletos o decisiones de otras partes del sistema. El plan y la unidad son la fuente de verdad, no el repositorio entero.

¿Code generation incluye escribir documentación?

La documentación que la unidad declare como entregable, sí. La documentación de operación y el runbook suelen ser unidades propias. Lo que no debe hacer el agente es generar documentación no pedida para «compensar» un cambio: eso infla el diff y aleja la revisión de lo importante.
