Tests y checkpoints

Módulo 5 · Construction 🕐 35 minutos

1 · Introducción

Un agente puede escribir código que compila, pasa un test y no hace lo que el requisito pide. Puede escribir un test que comprueba que se llamó a una función interna, en lugar de comprobar que el stock disponible es siete. Puede ejecutar los tests en un entorno distinto al del equipo y declarar «verde» sin que nadie sepa qué se ejecutó. Los tests y los checkpoints existen para cerrar esas grietas.

El checkpoint es el cierre verificable de una unidad: no basta con que el agente diga que terminó. Hay un comando registrado, una salida, un código de salida, una evidencia adjunta y una decisión humana. Si el comando falla, la unidad no está terminada. Si el comando no existe, la unidad no estaba bien definida. Si el humano no mira la evidencia, el checkpoint es una firma en blanco.

La estrategia de pruebas no se improvisa por unidad. Viene del perfil de workflow y del riesgo: un MVP puede vivir con pruebas de integración sobre los flujos principales; un cambio en el cálculo de stock necesita pruebas de concurrencia. Lo importante no es la cantidad de tests, sino que cada uno demuestre un comportamiento que alguien pidió y que el conjunto se pueda ejecutar de forma determinista.

Los tests son evidencia, no decoración

En AI-DLC un test no existe para subir un número de cobertura. Existe para que el checkpoint pueda afirmar «esto cumple el criterio de aceptación» con una salida reproducible. Si el test se puede borrar sin que nadie note que el comportamiento desapareció, no era evidencia: era relleno.

2 · Teoría

Qué demuestra cada tipo de test

TipoQué demuestraCosteCuándo usarlo
UnitarioUna función o módulo cumple una regla aislada.Bajo y rápido.Cálculos, validaciones, máquinas de estado.
IntegraciónVarias piezas colaboran contra una base de datos o un servicio real.Medio; requiere entorno.Repositorios, transacciones, migraciones.
ContratoLa forma de entrada y salida coincide con lo acordado.Bajo.APIs, eventos, integraciones externas.
Extremo a extremoUn flujo completo funciona desde el borde.Alto y frágil.Rutas críticas de negocio, humo post-despliegue.
ConcurrenciaDos operaciones simultáneas no corrompen el estado.Medio; difícil de estabilizar.Reservas, contadores, colas, idempotencia.

La estrategia del perfil decide el reparto. Un proyecto con `depth: standard` suele pedir unitarios para la lógica y una integración por flujo; uno con `depth: thorough` añade contrato y concurrencia en las unidades de riesgo alto. Lo que no cambia es la regla: cada criterio de aceptación debe tener al menos un test que lo demuestre.

Probar comportamiento, no implementación

Un test de comportamiento describe qué observa el usuario del sistema. Un test de implementación describe cómo está construido por dentro. El primero sobrevive a un refactor; el segundo se rompe aunque el comportamiento siga siendo correcto.

Mal (implementación)Bien (comportamiento)
Comprueba que se llamó a repository.find una vez.Comprueba que la respuesta contiene available: 7.
Verifica que el método privado validate devuelve true.Verifica que un SKU inexistente produce 404 con SKU_NOT_FOUND.
Asume que la reserva usa una transacción concreta.Lanza 20 reservas concurrentes y comprueba que el stock nunca es negativo.

La prueba de fuego: si cambias la implementación sin cambiar el contrato, ¿el test debería seguir pasando? Si la respuesta es no, el test está acoplado a una decisión interna. Eso no siempre es malo —a veces quieres fijar una decisión—, pero debe ser una elección consciente, no un accidente.

Nota: se añadió test de 20 reservas concurrentes; ver NFR-02.

El checkpoint no es un log: es un registro con decisión. La evidencia demuestra qué se ejecutó; la decisión demuestra que alguien lo aceptó. Sin la segunda parte, el checkpoint es un evento automático, no un punto de control.

El comando registrado no se sustituye

La unidad declara un comando exacto. El agente debe ejecutar ese comando, no uno equivalente. La diferencia importa: node --test ejecuta todos los tests del proyecto; node --test test/reservations.test.mjs ejecuta solo los de la unidad. Si el comando registrado es el segundo y el agente ejecuta el primero, puede pasar por razones ajenas a la unidad. Si ejecuta un subconjunto aún más pequeño, puede ocultar un fallo.

{
  "scripts": {
    "test": "node --test",
    "test:unit": "node --test test/*.test.mjs",
    "test:u2": "node --test test/reservations.test.mjs"
  }
}

El comando registrado en la unidad es npm run test:u2 o el node --test directo; ambos son válidos si están escritos. Lo que no es válido es que el agente invente un comando nuevo en el checkpoint porque el registrado falla.

Cuando un test falla: clasificar antes de tocar

CausaSeñalAcción
Bug de productoEl comportamiento observado no coincide con el criterio.Corregir el código; el test se queda.
Bug del testEl test asume un estado o un formato incorrecto.Corregir el test y justificar por qué sigue representando el requisito.
EntornoFalta una variable, una base de datos o un servicio.Arreglar el entorno; no cambiar el test para que no lo necesite.
Flojo (flaky)Pasa y falla sin cambios, a menudo por tiempo o concurrencia.Estabilizar con reloj inyectado, esperas deterministas o aislamiento; nunca reintentar hasta que pase.

La clasificación no es burocracia: determina qué se puede tocar. Un bug de producto se arregla en el código; un test mal escrito se arregla en el test. Confundirlos lleva a la práctica más destructiva del oficio: cambiar la expectativa hasta que el código actual la cumpla.

Determinismo: el test debe poder repetirse

Un test que depende del reloj real, de la red o del orden de un Map no es evidencia: es una lotería. Las tres herramientas más útiles en Node.js son:

  • Reloj inyectado — pasar now como función o parámetro en lugar de llamar a Date.now() dentro de la lógica.
  • Fixtures explícitas — datos creados por el test, no un estado global compartido entre pruebas.
  • Aislamiento — cada test crea su base de datos temporal o su repositorio en memoria; nada depende del orden de ejecución.
export function isExpired(reservation, now = () => Date.now()) {
  return reservation.expiresAt.getTime() <= now();
}

// En el test, el tiempo es una entrada más:
test("una reserva caducada se considera expirada", () => {
  const reservation = { expiresAt: new Date("2026-11-07T10:00:00Z") };
  assert.equal(isExpired(reservation, () => Date.parse("2026-11-07T10:00:01Z")), true);
});

Evidencia: qué se guarda y dónde

La evidencia mínima de un checkpoint es la salida del comando, el código de salida y la fecha. Si el proyecto lo permite, se añade el hash del diff para que la evidencia no se pueda separar del código que la produjo. En AI-DLC la evidencia se liga a fuentes: el log del test, el archivo revisado y la línea concreta, no una frase «funciona».

reviews/
├── checkpoint-u1.log      ← salida de node --test
├── checkpoint-u1.md       ← decisión y notas
├── review-02.md           ← hallazgos del revisor
└── load-01.md             ← informe del NFR de latencia

La carpeta reviews/ no es un archivo muerto: es lo que permite que un checkpoint se audite meses después sin depender de la memoria de quien lo cerró.

El checkpoint como gate

El checkpoint de unidad es un gate más, con las mismas cuatro opciones. Aprobar marca la unidad como verificada y desbloquea las que dependen de ella. Cambiar devuelve la unidad al agente con instrucciones. Saltar permite seguir con una unidad no verificada, registrando la deuda. Rechazar devuelve al plan o al diseño si el problema es de fondo.

Verde no significa terminado

Un test verde demuestra que se cumple lo que el test comprueba. No demuestra que se cumpla todo el requisito, que no haya cambios colaterales ni que el NFR se haya medido. El checkpoint combina tests, sensores, revisión y decisión; ninguno de los cuatro basta por separado.

3 · Ejemplo mínimo

Un test, un comando y un checkpoint. La unidad más pequeña verificable tiene exactamente estos tres elementos.

// test/availability.test.mjs
import test from "node:test";
import assert from "node:assert/strict";
import { calculateAvailability } from "../src/stock/availability.mjs";

test("descuenta las reservas del stock físico", () => {
  assert.equal(calculateAvailability({ physical: 10, reserved: 3 }), 7);
});

test("el stock disponible nunca es negativo", () => {
  assert.equal(calculateAvailability({ physical: 2, reserved: 5 }), 0);
});
node --test test/availability.test.mjs
# ✔ descuenta las reservas del stock físico
# ✔ el stock disponible nunca es negativo
# tests 2 · pass 2 · fail 0 · duration_ms 41
# Checkpoint · U1

Comando: node --test test/availability.test.mjs
Exit code: 0 · 2 passed · 0 failed
Evidencia: reviews/checkpoint-u1.log
Diff: 3 archivos, +64 −0
Decisión: approved · ana.ruiz · 2026-11-07T09:15:00Z
Nota: caso de SKU inexistente se difiere a U3 (FR-09).

Por qué esto es suficiente para una unidad pequeña:

  • El test describe comportamiento observable, no una llamada interna.
  • El comando está registrado y se ejecutó tal cual.
  • La evidencia tiene salida, fecha y decisión.
  • La nota registra lo que queda fuera, para que no se pierda.

Si la unidad hubiera incluido la ruta HTTP, el checkpoint necesitaría además un test de contrato para el 404 y el formato de la respuesta. La regla es simple: cada criterio de aceptación de la unidad debe tener una evidencia asociada.

4 · Ejemplo real

U2 es la unidad de mayor riesgo: reservar unidades sin dejar stock negativo. El plan le asigna una verificación de concurrencia y una revisión de arquitectura. El test no comprueba que se usó un SELECT FOR UPDATE; comprueba el efecto observable.

// test/reservations.test.mjs (extracto)
test("20 reservas concurrentes no dejan stock negativo", async () => {
  const repo = await createTempRepository({ sku: "SKU-1", physical: 10 });
  const attempts = Array.from({ length: 20 }, (_, i) =>
    reserve({ repo, sku: "SKU-1", qty: 1, orderId: `P-${i}` })
  );

  const results = await Promise.allSettled(attempts);
  const ok = results.filter((r) => r.status === "fulfilled").length;
  const conflict = results.filter(
    (r) => r.status === "rejected" && r.reason.code === "INSUFFICIENT_STOCK"
  ).length;

  assert.equal(ok, 10);
  assert.equal(conflict, 10);
  assert.equal(await repo.available("SKU-1"), 0);
});

El test es determinista porque cada ejecución crea su repositorio temporal, no depende de un reloj externo y no comparte estado con otros tests. La concurrencia real se produce con Promise.allSettled, y el resultado esperado es exacto: diez reservas exitosas, diez conflictos, cero disponibles.

$ node --test test/reservations.test.mjs
✔ reserva 3 con 7 disponibles deja 4
✔ con 2 disponibles, 409 y stock intacto
✔ 20 reservas concurrentes no dejan stock negativo
✔ una reserva expirada libera unidades
tests 6 · pass 6 · fail 0 · duration_ms 318

El checkpoint adjunta además la revisión de arquitectura, que detectó un índice que faltaba en la consulta de reservas. Sin esa revisión, el test habría pasado igual y el problema habría aparecido con carga real. Esa es la razón por la que el checkpoint combina evidencias distintas: el test demuestra corrección funcional; la revisión detecta riesgos que el test no ve.

EvidenciaQué demuestraQué no demuestra
Test de concurrenciaNo se vende stock inexistente en el escenario probado.Que aguante 500 req/s ni que el índice sea suficiente.
Revisión de arquitecturaEl diseño y el índice son coherentes con NFR-02.Que el código no tenga un bug de lógica.
Sensor de trazabilidadCada requisito tiene unidad y test.Que el test sea bueno.
Decisión humanaAlguien aceptó el riesgo residual.Que el riesgo desaparezca.

La analogía del control de calidad

En una fábrica, el control de calidad no es «la pieza parece bien». Es una medición con un instrumento calibrado, un registro y una firma. El test es el instrumento; el log es el registro; la decisión es la firma. Si falta uno de los tres, la pieza sale sin trazabilidad.

Cobertura como señal, no como objetivo

Una cobertura alta con tests triviales es peor que una cobertura media con tests de comportamiento. Usa la cobertura para encontrar ramas sin probar, no para fijar una meta que se alcanza escribiendo tests vacíos. En AI-DLC la pregunta no es «¿cuánto cubrimos?», sino «¿qué criterio de aceptación no tiene evidencia?».

6 · Errores habituales

1. Cambiar el test para que pase

Mal — la expectativa se adapta al bug 
test("20 reservas concurrentes", async () => {
  const available = await repo.available("SKU-1");
  // ❌ el test fallaba con 0; se relaja la expectativa
  assert.ok(available >= -2);
});
Bien — el test fija el comportamiento acordado 
test("20 reservas concurrentes", async () => {
  const available = await repo.available("SKU-1");
  // ✅ NFR-02: el stock nunca puede ser negativo
  assert.equal(available, 0);
  assert.equal(await repo.reserved("SKU-1"), 10);
});

El primer test sigue pasando con un stock de −2, que es exactamente el bug que la unidad debía evitar. El segundo falla hasta que la implementación es correcta. Un test que se relaja para pasar no es un test: es una justificación.

2. Reintentar un test flojo hasta que pase

Mal — la lotería como estrategia 
for i in 1 2 3 4 5; do
  node --test test/reservations.test.mjs && break
done
Bien — estabilizar la causa 
// El test dependía del reloj real para la expiración.
const clock = () => Date.parse("2026-11-07T10:00:00Z");
const reservation = createReservation({ ttlSeconds: 60, now: clock });
assert.equal(isExpired(reservation, () => clock() + 61_000), true);

Reintentar oculta la no determinación y enseña al equipo a ignorar los rojos. Si un test es flojo, el problema es del test o del código, no de la suerte. La solución es aislar el tiempo, los datos y la concurrencia, no repetir hasta que salga bien.

3. Probar la implementación en lugar del comportamiento

Mal — el test se rompe al refactorizar 
// ❌ verifica que se llamó al repositorio una vez
assert.equal(repo.findCalls.length, 1);
assert.equal(repo.findCalls[0].sku, "SKU-1");
Bien — verifica el resultado observable 
// ✅ verifica la respuesta que el contrato promete
const response = await getStock({ sku: "SKU-1" });
assert.equal(response.status, 200);
assert.deepEqual(response.body, {
  sku: "SKU-1",
  physical: 10,
  reserved: 3,
  available: 7,
});

El primer test impide cambiar la caché, el repositorio o la estrategia de consulta aunque el contrato siga siendo correcto. El segundo permite refactorizar sin romper la evidencia. Los dobles de prueba son útiles para aislar, pero no deben convertirse en el objeto de la afirmación.

4. Declarar terminado sin ejecutar el comando registrado

Mal — «en mi máquina pasa» 
El agente dice: "He implementado la reserva y los tests deberían pasar.
No he ejecutado node --test porque el entorno no tiene base de datos."
Bien — entorno reproducible y evidencia 
# El test usa un repositorio temporal, sin base de datos externa
node --test test/reservations.test.mjs
# exit code 0 · 6 passed
# salida guardada en reviews/checkpoint-u2.log

«Deberían pasar» no es evidencia. Si el entorno no permite ejecutar el comando, el checkpoint no se puede cerrar: se arregla el entorno o se cambia el diseño del test para que sea ejecutable. Un test que solo corre en la máquina de alguien no protege a nadie.

7 · Ejercicio guiado

Objetivo: escribir tests de comportamiento para una unidad, ejecutar el comando registrado y cerrar un checkpoint con evidencia y decisión.

  1. Paso 1 — Elige una unidad y extrae sus criterios: por ejemplo U3, liberar una reserva. Escribe los criterios como casos observables. 
    1. Liberar 3 unidades devuelve disponibles +3.
2. Liberar dos veces la misma reserva devuelve 409.
3. Una reserva expirada se libera automáticamente al consultar.
  2. Paso 2 — Escribe un test por criterio: sin mocks innecesarios y con datos creados por el test. 
    test("liberar una reserva devuelve las unidades", async () => {
  const repo = await createTempRepository({ sku: "SKU-1", physical: 10 });
  const { reservationId } = await reserve({ repo, sku: "SKU-1", qty: 3, orderId: "P-1" });
  await release({ repo, reservationId });
  assert.equal(await repo.available("SKU-1"), 10);
});
  3. Paso 3 — Ejecuta el comando exacto: 
    node --test test/release.test.mjs
# ✔ liberar una reserva devuelve las unidades
# ✔ liberar dos veces devuelve 409
# ✔ una reserva expirada libera al consultar
# tests 3 · pass 3 · fail 0
  4. Paso 4 — Rompe el código a propósito: cambia release para que no devuelva las unidades y vuelve a ejecutar. El test debe fallar. Si sigue pasando, el test no está probando lo que crees. Restaura el código.
  5. Paso 5 — Guarda la evidencia: redirige la salida a reviews/checkpoint-u3.log y escribe el checkpoint con comando, exit code, fecha, diff y decisión. 
    # Checkpoint · U3
Comando: node --test test/release.test.mjs
Exit code: 0 · 3 passed
Diff: 3 archivos, +91 −4
Decisión: approved · ana.ruiz · 2026-11-08T11:02:00Z
  6. Paso 6 — Clasifica un fallo real: si algún test falla, escribe primero la causa —producto, test, entorno o flaky— y la acción asociada. No toques código hasta haber clasificado. La clasificación evita el reflejo de cambiar la expectativa.

Resultado esperado

Tres tests que fallen si el comportamiento desaparece, la salida del comando registrado y un checkpoint con decisión. La prueba de calidad: rompe la implementación y comprueba que la suite se entera. Si no se entera, no era evidencia.

8 · Reto

🎯 El test de concurrencia que pasa siempre

U2 tiene un test de 20 reservas concurrentes que pasa en local y falla una de cada diez veces en CI. El equipo sospecha que la causa es el pool de conexiones, pero no está seguro. Alguien propone subir el timeout y añadir un reintento; otro propone ejecutar el test en serie para que no compita consigo mismo.

Diseña una estrategia que produzca evidencia útil: ¿cómo reproduces el fallo de forma determinista? ¿Qué aíslas —tiempo, conexiones, orden— para saber qué depende de qué? ¿Qué haces si el fallo solo aparece con carga real y no en el test? ¿Cómo registras la decisión de aceptar un riesgo residual sin convertir el rojo en verde artificial?

Pista: un test de concurrencia que depende del planificador del sistema operativo nunca será completamente determinista. La salida no es hacerlo perfecto, sino hacerlo reproducible: controla el punto de interacción —por ejemplo, una barrera antes de la escritura— y verifica la invariante, no el orden exacto de las operaciones.

9 · Resumen

  • La estrategia de pruebas se deriva del perfil y del riesgo; no se improvisa unidad a unidad.
  • Cada criterio de aceptación necesita al menos un test que lo demuestre.
  • Se prueba comportamiento observable, no implementación interna.
  • El checkpoint une comando registrado, salida, evidencia, sensores, revisión y decisión humana.
  • El comando registrado se ejecuta tal cual; si falla, se clasifica la causa antes de tocar nada.
  • Un test flojo se estabiliza con reloj inyectado, fixtures y aislamiento; nunca con reintentos hasta que pase.
  • Verde no significa terminado: significa que lo comprobado se cumple.

10 · Preguntas frecuentes

¿Qué hago si el comando registrado tarda demasiado?

Primero mide: un test lento puede ser una señal de diseño —base de datos compartida, falta de aislamiento— más que un problema de herramienta. Si el coste es inevitable, separa la suite rápida de la lenta y registra ambas en la unidad. Lo que no hagas es cambiar el comando por uno más rápido que no demuestre el criterio.

¿Puedo cerrar un checkpoint con un test marcado como skip?

Solo si el skip está justificado y registrado como deuda, con dueño y fecha. Un skip silencioso es una evidencia falsa: el checkpoint afirma que se verificó algo que no se ejecutó. Si el criterio no se puede probar todavía, es mejor saltar la unidad completa con motivo que fingir que se verificó.

¿Los tests los escribe el agente o el humano?

El agente puede escribirlos, pero el humano define el criterio y revisa que el test lo represente. Un test generado a partir del código tiende a describir la implementación; un test generado a partir del requisito tiende a describir el comportamiento. La diferencia está en el contexto que recibe, no en quién lo escribe.

¿Necesito cobertura del 100 %?

No. La cobertura mide líneas ejecutadas, no comportamientos verificados. Un 100 % con aserciones triviales puede ser peor que un 70 % con casos de error bien probados. Usa la cobertura para encontrar ramas olvidadas y la trazabilidad para encontrar requisitos sin evidencia.

¿Qué diferencia hay entre checkpoint y gate de etapa?

El checkpoint cierra una unidad de Construction y desbloquea las siguientes; el gate de etapa cierra una fase completa de Inception o el plan. Ambos son decisiones humanas, pero el checkpoint se apoya en evidencia de ejecución —tests, sensores, revisión— y el gate de etapa se apoya en artefactos de diseño y requisitos.
