Configurar el proyecto

Módulo 1 · Initialization 🕐 35 minutos

1 · Introducción

aidlc config es el comando que convierte un repositorio cualquiera en un proyecto AI-DLC. No instala el motor: eso lo hace el instalador nativo una vez por máquina. Lo que hace es proyectar el runtime instalado dentro del repositorio, con la forma que espera el harness elegido, y crear el registro neutral donde vivirá el trabajo.

Es un comando aburrido y por eso mismo conviene dominarlo. Escribe decenas de archivos, toca archivos que ya son tuyos y añade bloques gestionados en .gitignore y en el contexto del agente. Si no sabes qué va a cambiar, el diff se convierte en una sorpresa; si lo sabes, el diff es una revisión de dos minutos.

Hay dos propiedades que hacen que puedas ejecutarlo sin miedo. La primera: es transaccional, no deja el proyecto a medias si algo falla. La segunda: es idempotente y respeta lo que editaste en las capas que son tuyas, así que repetirlo es la forma prevista de refrescar la proyección tras actualizar el motor.

Por qué existe esta lección

Porque la configuración decide tres cosas que luego nadie revisa: qué puede hacer el agente sin preguntar, qué archivos viajan al equipo y qué versión del framework cree el proyecto que está usando. Un error aquí no rompe el primer día; aparece cuando alguien clona, cuando se aprueba un gate o cuando se actualiza la release.

2 · Teoría

Qué hace exactamente

motor instalado (una vez por máquina)
        │
        │  aidlc config --harness 
        ▼
repositorio
├── .claude/  o  .cursor/     ← runtime del harness (del motor)
├── aidlc/                    ← registro neutral (tuyo)
├── CLAUDE.md  o  AGENTS.md   ← contexto ambiental (bloque gestionado)
├── .gitignore                ← bloque gestionado con estado local
├── aidlc.settings.json       ← preset de modelo compartido
└── .mcp.json                 ← servidores MCP, solo si los aceptas

El comando no adivina el harness cuando no hay terminal. Si lo lanzas desde un script, un contenedor o CI, tienes que nombrarlo. En una terminal interactiva abre un asistente que pregunta por MCP, status line y preset de modelo; con --harness va directo a la parte que importa.

Las opciones que se usan de verdad

Hay una diferencia importante entre --yes y --mcp. --yes confirma lo que el comando ya iba a hacer; no decide por ti si quieres servidores MCP. Si tu script quiere MCP, tiene que decirlo con --mcp defaults. Si no lo dice, la respuesta es no.

Si configuras los dos harnesses en el mismo repositorio, aidlc/ es uno solo y cada harness tiene su carpeta. Ese es el modelo de los equipos híbridos, que se desarrolla en Claude Code vs Cursor.

Bloques gestionados: cómo respeta lo tuyo

En CLAUDE.md, AGENTS.md y .gitignore, AI-DLC no reescribe el archivo entero. Añade un bloque delimitado por marcas:

<!-- BEGIN AI-DLC:agents -->
…contenido que el motor mantiene…
<!-- END AI-DLC:agents -->

Todo lo que está fuera de las marcas se conserva byte a byte. Por eso puedes tener tu contexto de proyecto en AGENTS.md y seguir refrescando sin perderlo. Si las marcas están duplicadas o mal formadas, el comando se niega a tocar el archivo: es mejor un error explícito que un archivo corrupto.

Lo de dentro del bloque no es tuyo

El bloque gestionado se reemplaza en cada refresco. Las reglas del equipo van a aidlc/spaces/<space>/memory/, que sí es una capa editable y se conserva. Si escribes una norma dentro del bloque, la perderás en la siguiente actualización y nadie sabrá por qué cambió el comportamiento.

Interactivo frente a sin preguntas

En una terminal con prompt, el asistente pregunta por MCP, status line y preset de modelo. En CI, en un contenedor o en cualquier terminal sin prompt, no hay asistente: tienes que nombrar el harness. La forma canónica de configurar sin preguntas es esta:

aidlc config --harness claude --mcp none --yes
aidlc config --harness cursor --mcp none --yes

La status line solo existe en Claude Code y se controla aparte, con aidlc config --statusline on|off. En Cursor no hay línea de estado: el equivalente es /aidlc --status o el atajo /aidlc-status.

Refresco y desfase de versiones

Cada proyección queda ligada a la release con la que se configuró. Cuando actualizas el motor, el proyecto puede quedar por detrás; el doctor lo detecta y lo llama skew. El refresco es el mismo comando:

aidlc config --harness claude
aidlc doctor

Qué ocurre en ese refresco:

  • Los archivos del framework se actualizan a la versión instalada.
  • Lo que editaste en memory/, knowledge/ y los artefactos de los intents se conserva.
  • Los bloques gestionados se sustituyen por los de la nueva release.
  • Si un archivo del framework fue modificado a mano, el comando avisa; --force lo reemplaza, pero solo deberías usarlo después de leer qué se pierde.

Si la máquina no tiene la release que el proyecto necesita, --download la trae y la verifica. Si trabajas con una release local —por ejemplo, un tar.gz con su .sha256—, --from apunta a ella. En ambos casos, el objetivo es que la proyección y el motor hablen la misma versión.

3 · Ejemplo mínimo

Configurar un repositorio nuevo, sin asistente y sin MCP, en dos comandos y una comprobación.

cd ~/proyectos/inventario
aidlc config --harness claude --mcp none --yes
aidlc doctor

La salida resume lo que hizo y cuál es el siguiente paso:

configured /home/ana/proyectos/inventario for Claude Code 2.x.y
next: open Claude Code in this project (restart it if it is already open
in this folder) and run `/aidlc --doctor`

El diff debería contener exactamente esto:

git status --short
# ?? .claude/
# ?? aidlc/
# ?? .gitignore
# ?? aidlc.settings.json

Si aparece .mcp.json cuando pediste --mcp none, algo no cuadra: revisa el comando antes de seguir. Si aparece un *.local.json, el bloque de .gitignore no se aplicó y hay que mirarlo antes del commit.

El dry run también sirve para revisar el pasado

aidlc config --show te dice qué configuración cree el comando que hay, sin escribir nada. Es la forma rápida de comprobar el preset de modelo o las secciones activas cuando heredas un repositorio que no configuraste tú.

4 · Ejemplo real

El equipo de inventario configuró Claude Code hace un mes. Marta, de producto, trabaja en Cursor y quiere revisar los artefactos sin pedir capturas de pantalla. La decisión es añadir la segunda proyección al mismo repositorio, no crear un repositorio paralelo.

git checkout -b chore/aidlc-cursor
aidlc config --harness cursor --dry-run
# revisa: .cursor/, AGENTS.md, bloque en .gitignore,
#         aidlc.settings.json (sin cambios si ya existe)
aidlc config --harness cursor --mcp none --yes
aidlc doctor

El doctor ahora informa de dos proyectos:

Project (.claude, Claude Code)      ok  49 checks passed
Project (.cursor, Cursor)          ok  47 checks passed
Framework integrity                ok  all 12 checks passed

El diff del pull request se revisa con tres preguntas:

Qué se miraQué se espera
.cursor/Reglas, agentes, skills y hooks de la proyección; nada editado a mano
AGENTS.mdUn bloque gestionado nuevo; el contenido previo del equipo intacto
.gitignoreEl bloque de AI-DLC sigue siendo uno solo y cubre los locales

Un mes después, el motor pasa a una versión nueva. Ana refresca las dos proyecciones en una rama:

aidlc config --harness claude --mcp none --yes
aidlc config --harness cursor --mcp none --yes
aidlc doctor
git diff --stat .claude .cursor AGENTS.md CLAUDE.md aidlc.settings.json

El diff es aburrido: cambios en archivos del framework, ninguna línea de memory/. Ese es el síntoma de un refresco sano. Si apareciera un cambio en team.md, sería una señal de alarma: esa capa no la toca el comando.

Configurar no es adoptar

Tener .cursor/ y .claude/ en el repositorio no obliga a nadie a usar los dos. La configuración crea la posibilidad; la política del equipo decide qué etapas se hacen en cada harness. La configuración es infraestructura; la adopción es una decisión organizativa.

5 · Buenas prácticas

HazEvitaPor qué
Ejecutar --dry-run antes de configurar un repo con historia. Lanzar el comando y leer el diff después. El plan te dice qué rutas toca y cuáles ya existen; el diff te lo dice cuando ya es tarde para elegir.
Un commit dedicado solo a la configuración. Mezclarlo con un cambio de producto. Se revisa mejor y se revierte sin arrastrar código.
Nombrar --harness, --mcp y --yes en CI. Confiar en el asistente interactivo. Sin terminal no hay asistente; el comando necesita decisiones explícitas.
Editar reglas en aidlc/spaces/<space>/memory/. Tocar .claude/ o .cursor/. El motor se reescribe al refrescar; la capa de método se conserva.
Refrescar con aidlc config tras actualizar el motor. Actualizar solo el binario y dejar la proyección vieja. El desfase de versiones produce hooks y skills que no encajan entre sí.
Leer qué se pierde antes de usar --force. Usarlo como botón de «arreglar». Reemplaza archivos del framework que alguien modificó; a veces esa modificación era la única copia de una decisión.

6 · Errores habituales

1. Configurar en el directorio equivocado

Mal — el home como proyecto 
cd ~
aidlc config --harness claude
Bien — la raíz del repositorio 
cd ~/proyectos/inventario
git rev-parse --show-toplevel
aidlc config --harness claude

El comando usa el directorio actual, no busca el repositorio hacia arriba. Configurar en el home crea un aidlc/ que mezcla todos tus proyectos y una proyección que no se versiona en ningún sitio.

2. Commitear todo con git add -A

Mal — el diff con archivos de máquina 
git add -A
# entran aidlc/active-space, aidlc/active-memory/,
# .claude/settings.local.json, aidlc.settings.local.json
Bien — rutas explícitas 
git add .claude aidlc .gitignore aidlc.settings.json AGENTS.md
git status --short   # ningún *.local.json

El estado local describe tu sesión. Si viaja, cada compañero hereda tu espacio activo y aparecen conflictos en archivos que nadie debería estar mergeando.

3. Usar --force para resolver un aviso del doctor

Mal — borrar la evidencia 
aidlc config --harness claude --force
# el aviso desaparece, pero también la modificación que lo causaba
Bien — entender la modificación 
aidlc doctor --verbose
git diff .claude/
# si era una prueba, se descarta a propósito; si era una regla,
# se mueve a aidlc/spaces/default/memory/team.md

--force es una herramienta de migración, no de limpieza. Su función es descartar cambios en archivos que pertenecen al framework; si el cambio era una regla del equipo, el sitio correcto es memory/.

4. Ejecutar la configuración en CI sin decisiones explícitas

Mal — esperar un asistente que no existe 
- run: aidlc config
# sin TTY no hay preguntas; el comando no sabe qué harness
Bien — flags completos y deterministas 
- run: aidlc config --harness claude --mcp none --yes
- run: aidlc doctor

En un pipeline no hay nadie para responder. Nombrar el harness, decidir MCP y confirmar el destino convierte la configuración en un paso reproducible, que es lo único que un pipeline puede verificar.

7 · Ejercicio guiado

Objetivo: configurar un repositorio con contexto propio, revisar el plan antes de aplicarlo y comprobar que un refresco no toca tus reglas.

  1. Paso 1 — Prepara un repositorio con contenido previo. 
    mkdir ~/laboratorio/aidlc-config
cd ~/laboratorio/aidlc-config
git init
printf '# Inventario\n\nAPI en Node.js 22.\n' > README.md
printf '# Contexto del equipo\n\n- Tests con node --test\n' > AGENTS.md
git add README.md AGENTS.md && git commit -m "Base"

    El AGENTS.md previo es la prueba de que el bloque gestionado no debe borrarlo.

  2. Paso 2 — Lee el plan en JSON. 
    aidlc config --harness claude --dry-run --json > plan.json
node -e "const p=require('./plan.json'); console.log(p.counts, p.data.notes)"

    Anota el planToken. Ese token identifica exactamente el plan que acabas de revisar.

  3. Paso 3 — Aplica el plan revisado. 
    aidlc config --harness claude --plan-token <token> --mcp none --yes

    Si el plan cambió entre la revisión y la aplicación, el token deja de valer: es la garantía de que aplicas lo que leíste.

  4. Paso 4 — Comprueba la fusión del contexto. 
    cat AGENTS.md

    Deben convivir tu texto y el bloque BEGIN/END AI-DLC. Tu texto, intacto y fuera de las marcas.

  5. Paso 5 — Añade una regla del equipo y refresca. 
    printf '\n- Los endpoints nuevos requieren test de contrato.\n' >> aidlc/spaces/default/memory/team.md
aidlc config --harness claude --mcp none --yes
git diff aidlc/spaces/default/memory/team.md

    El diff debe estar vacío: el refresco no toca la capa de método.

  6. Paso 6 — Revisa y commitea. 
    git status --short
git add .claude aidlc .gitignore AGENTS.md aidlc.settings.json
git commit -m "Configura AI-DLC"

    No debe aparecer ningún *.local.json. Si aparece, revisa el bloque de .gitignore antes de commitear.

Resultado esperado

Un plan aplicado con token, un AGENTS.md que conserva tu contexto, una regla de equipo que sobrevive al refresco y un commit sin archivos locales. Si el bloque gestionado se comió tu texto, tienes un problema de marcas, no de configuración.

8 · Reto

🎯 El contrato de revisión del diff de configuración

Diseña el procedimiento con el que un equipo revisa cualquier cambio producido por aidlc config: una actualización del motor, la adición de un harness o un refresco de rutina. Debe decir qué archivos son territorio del framework y no se revisan línea a línea, qué archivos son decisiones del equipo y requieren aprobación, y qué señales obligan a parar el merge.

Incluye el caso incómodo: alguien modificó un archivo de .claude/ hace tres semanas para «arreglar» un gate. El refresco quiere reemplazarlo. ¿Quién decide, con qué información y cómo se registra la decisión para que no vuelva a pasar?

Pista: el diff no distingue intención. Lo que sí la distingue es una lista corta de rutas con dueño y una pregunta obligatoria en el PR: «¿este cambio viene de la release o de una persona?».

9 · Resumen

  • aidlc config proyecta el runtime en el repositorio; el motor se instala una vez por máquina.
  • Es transaccional e idempotente: repetirlo es la forma de refrescar.
  • --dry-run previsualiza; --plan-token aplica exactamente el plan revisado.
  • --yes confirma, pero no activa MCP: para eso hace falta --mcp defaults.
  • Escribe el motor del harness, aidlc/, el contexto ambiental, el bloque de .gitignore y el preset de modelo.
  • Se commitea todo salvo *.local.json, cursores y estado por sesión.
  • Las reglas del equipo van a memory/; el bloque gestionado se reemplaza en cada refresco.

10 · Preguntas frecuentes

¿Tengo que volver a ejecutar aidlc config cada vez que abro el proyecto?

No. Se ejecuta al configurar y al refrescar tras una actualización del motor. Abrir el harness no configura nada: lee lo que ya está en el repositorio. Si necesitas configurar cada mañana, la proyección no está versionada o estás abriendo otra carpeta.

¿--yes acepta también los servidores MCP?

No. --yes confirma un destino no reconocido o una mutación de sección; no sustituye tu decisión sobre MCP. Si quieres las entradas que trae la release, añade --mcp defaults. Si no las quieres, --mcp none lo deja explícito y evita sorpresas en el diff.

¿Puedo configurar Cursor y Claude Code en el mismo repositorio?

Sí, y es el caso normal de un equipo híbrido. Cada harness escribe su carpeta —.cursor/ y .claude/— y ambos comparten aidlc/. Configura uno, verifica con el doctor y luego el otro; no los lances a la vez sobre el mismo árbol sin commitear.

¿Qué hago si el doctor avisa de un desfase de versiones?

Refrescar la proyección con aidlc config --harness <nombre>. Si la máquina no tiene la release que el proyecto espera, --download la trae y la verifica. El objetivo es que el binario y los archivos proyectados sean de la misma versión; mezclarlos produce fallos difíciles de leer.

¿El bloque gestionado de AGENTS.md puede convivir con el mío?

Sí. AI-DLC solo reemplaza el texto entre sus marcas BEGIN y END; lo de fuera se conserva byte a byte. El límite es claro: lo que escribas dentro del bloque se perderá en el siguiente refresco. Las prácticas del equipo van a memory/.
