Dunders y protocolos (duck typing)

Módulo 5 · Programación orientada a objetos ⏱ 35 minutos

1 · Introducción

¿Por qué len("hola") funciona, for x in lista funciona, y x in coleccion también? Porque esos objetos implementan unos métodos de nombre raro rodeado de dobles guiones bajos —los dunders (double underscores)— que Python llama internamente para cada operación. Son el mecanismo que hace que tus objetos se comporten como los de la biblioteca estándar.

Esta lección cierra el módulo enseñando los dunders esenciales (__repr__, __str__, __eq__, __lt__, __len__, __iter__, __contains__) y el concepto de protocolo y duck typing: si un objeto implementa los métodos de un protocolo, sirve, sin importar de qué clase herede. Terminaremos con por qué un buen __repr__ es tu mejor herramienta de depuración.

¿Por qué Python usa dunders en vez de interfaces? Porque el lenguaje prefiere el duck typing: «si camina como pato y grazna como pato, es un pato». No hace falta declarar implements Iterable; basta con implementar __iter__. Eso hace que for, len, in y sorted funcionen con cualquier objeto que siga el protocolo, incluido el tuyo. Es la razón por la que la biblioteca estándar se siente tan cohesiva.

2 · Teoría

Dunders: los métodos que Python llama por ti

Nunca los llamas directamente; los invoca el intérprete cuando usas la sintaxis correspondiente. Esta tabla es el mapa que da sentido a todo lo demás:

__repr__ y __str__

Son dos representaciones con propósitos distintos. __repr__ es la oficial y sin ambigüedad: idealmente, el texto que al evaluarlo recrearía el objeto. __str__ es la informal y legible. Si solo defines __repr__, str() lo reutiliza; si defines __str__, tiene prioridad para print.

class Item:
    def __init__(self, id, title):
        self.id = id
        self.title = title

    def __repr__(self):
        # Para el desarrollador: muestra la clase y los campos entre comillas.
        return f"Item(id={self.id!r}, title={self.title!r})"

    def __str__(self):
        # Para el usuario: frase legible.
        return f"{self.title} (ref. {self.id})"


item = Item("1", "1984")
print(repr(item))     # Item(id='1', title='1984')
print(str(item))      # 1984 (ref. 1)
print(item)           # 1984 (ref. 1)   <- print usa __str__
print([item])         # [Item(id='1', title='1984')]  <- ¡dentro de una lista usa __repr__!

¿Por qué __repr__ es esencial para depurar? Porque los depuradores, los logs, las trazas de error, los print(lista) y el REPL usan __repr__, no __str__. Si no lo defines, verás <__main__.Item object at 0x7f…>: un montón de memoria hexadecimal que no dice nada del contenido. Un buen __repr__ convierte cada depuración en un vistazo instantáneo al estado del objeto. Regla: define siempre __repr__; __str__ solo si necesitas una versión de cara al usuario.

El detalle de !r. f"{self.title!r}" aplica repr() al valor, de modo que el string se muestra entre comillas: title='1984'. Sin !r sería title=1984 y no distinguirías el string "42" del entero 42 al depurar. En __repr__, usa !r para los campos.

__eq__ y __hash__

Por defecto == entre objetos compara identidad (como is). Para comparar por valor, define __eq__. Y recuerda la regla: si defines __eq__, Python pone __hash__ = None y el objeto deja de ser hashable, salvo que definas __hash__ coherente.

class Item:
    def __init__(self, id, title):
        self.id = id
        self.title = title

    def __eq__(self, other):
        # Devolver NotImplemented (no False) si no sabemos comparar.
        if not isinstance(other, Item):
            return NotImplemented
        return (self.id, self.title) == (other.id, other.title)


a = Item("1", "1984")
b = Item("1", "1984")
print(a == b)       # True   (antes era False: comparaba identidad)
print(a is b)       # False  (siguen siendo objetos distintos)
print(a != b)       # False  (Python deriva != de __eq__)

Devuelve NotImplemented, no False. Cuando el otro objeto no es comparable, devolver False afirma «no son iguales» cuando en realidad «no sé compararlo». NotImplemented permite a Python probar el __eq__ del otro objeto. Es una diferencia sutil que evita comparaciones incorrectas en jerarquías y con tipos reflexivos.

__lt__ y el orden

Para que sorted(), min() o max() funcionen con tus objetos, implementa __lt__ (menor que). Python no genera los otros operadores automáticamente en una clase normal (en dataclasses order=True sí lo hace, lección 4).

class Item:
    def __init__(self, title, year):
        self.title = title
        self.year = year

    def __lt__(self, other):
        # Ordenamos por año (y desempatamos por título).
        return (self.year, self.title) < (other.year, other.title)

    def __repr__(self):
        return f"Item({self.title!r}, {self.year})"


items = [Item("Dune", 1965), Item("1984", 1949)]
print(sorted(items))   # [Item('1984', 1949), Item('Dune', 1965)]

__len__, __iter__ y __contains__: el protocolo de colección

Estos tres convierten tu objeto en una colección de la que se puede pedir tamaño, iterar y comprobar pertenencia.

class Catalog:
    def __init__(self, items):
        self._items = list(items)

    def __len__(self):
        # Habilita len(catalog) y la truthiness: un catálogo vacío es falsy.
        return len(self._items)

    def __iter__(self):
        # Habilita "for item in catalog".
        return iter(self._items)

    def __contains__(self, title):
        # Habilita "title in catalog".
        return any(item.title == title for item in self._items)


catalog = Catalog([Item("1984", 1949), Item("Dune", 1965)])
print(len(catalog))            # 2
for item in catalog:           # __iter__ en acción
    print(item.title)
print("Dune" in catalog)       # True   (__contains__)
print("Neuromante" in catalog) # False
print(bool(Catalog([])))       # False  (len == 0 -> falsy)

¿Por qué __len__ también da truthiness? Porque sin __bool__, Python usa __len__: un objeto con longitud 0 se considera False en un if. Es el mismo principio que hace que if lista: compruebe si está vacía. Consistencia total con los tipos integrados.

Duck typing y protocolos

Un protocolo es un conjunto de métodos que define un comportamiento. No es una clase que heredas: es un contrato implícito. Si un objeto implementa __iter__, es iterable. Punto. No importa su tipo.

# Función que solo exige el protocolo iterable: funciona con LISTA y con
# cualquier objeto que tenga __iter__, sin comprobar el tipo.
def describe_all(collection):
    return [f"- {item}" for item in collection]

print(describe_all([1, 2, 3]))          # ['- 1', '- 2', '- 3']
print(describe_all("abc"))              # ['- a', '- b', '- c']  (un str es iterable)

Cuando una función no comprueba el tipo y solo usa el comportamiento, es duck typing. Python ofrece además la clase collections.abc.Iterable y el módulo typing.Protocol para expresar estos contratos al verificador de tipos (Módulo 7), pero en ejecución el contrato es puramente estructural: lo que importa es tener los métodos, no la ascendencia.

Duck typing ≠ sin control. Duck typing no significa «confía a ciegas». Cuando un objeto no cumple el protocolo, el error salta al usarlo (TypeError: 'Item' object is not iterable). La defensa correcta es EAFP (Módulo 6): intentar y capturar, en vez de comprobar tipos por adelantado (LBYL). En Módulo 7, typing.Protocol + mypy te avisan en desarrollo de que no cumples el contrato, sin coste en ejecución.

3 · Ejemplo mínimo

Una caja de un solo valor que se comporta como un número: implementa __repr__, __eq__ y __lt__. Es el dunder más pequeño con valor real.

box.py
class Box:
    def __init__(self, value):
        self.value = value

    def __repr__(self):
        # Indispensable: sin esto verías Box object at 0x...
        return f"Box({self.value!r})"

    def __eq__(self, other):
        if not isinstance(other, Box):
            return NotImplemented
        return self.value == other.value

    def __lt__(self, other):
        return self.value < other.value


b = Box(3)
c = Box(5)
print(b)                 # Box(3)  -> usa __repr__
print(b == Box(3))       # True    -> __eq__ por valor
print(b < c)             # True    -> __lt__
print(sorted([c, b]))    # [Box(3), Box(5)]

Línea por línea: __repr__ hace que print(b) sea informativo (si no, verías la dirección de memoria). __eq__ compara por value, comprobando antes que el otro sea Box. __lt__ habilita el orden, y sorted lo usa. Con solo esos tres dunders, la caja ya se comporta como un tipo integrado.

4 · Ejemplo real

Damos a nuestro modelo de Biblioteca los dunders que lo hacen de primera clase: Item con representación e igualdad, y un Catalog que se comporta como una colección (iterable, con longitud y pertenencia).

biblioteca/models.py (versión de esta lección)
from dataclasses import dataclass, field


@dataclass
class Item:
    """Ítem del catálogo con dunders propios."""

    id: str
    title: str = ""
    kind: str = "book"
    year: int = 0
    borrowed: bool = field(default=False, compare=False)

    def __post_init__(self):
        self.title = self.title.strip()
        if not self.title:
            raise ValueError("title no puede estar vacío")

    def __repr__(self):
        # Representación inequívoca: útil en logs y depuración.
        return (f"Item(id={self.id!r}, title={self.title!r}, "
                f"kind={self.kind!r}, year={self.year}, borrowed={self.borrowed})")

    def __str__(self):
        # Representación para el usuario de la CLI.
        state = "prestado" if self.borrowed else "disponible"
        year = self.year if self.year else "s/a"
        return f"{self.title} ({year}) — {state}"

    def __len__(self):
        # Longitud "útil": los años de antigüedad si hay año, si no 0.
        # (Ejemplo didáctico; lo natural sería un método con nombre.)
        return self.year

    def __lt__(self, other):
        # Orden por año y, a igualdad, por título.
        return (self.year, self.title) < (other.year, other.title)


class Catalog:
    """Colección de ítems que implementa el protocolo de colección."""

    def __init__(self, items=None):
        self._items = list(items) if items else []

    @property
    def items(self):
        # Copia defensiva: quien lo use no muta el catálogo por accidente.
        return list(self._items)

    def add(self, item):
        self._items.append(item)

    def __len__(self):
        return len(self._items)

    def __iter__(self):
        # Iterar el catálogo delega en la lista interna.
        return iter(self._items)

    def __contains__(self, title):
        # "title in catalog": búsqueda por título.
        return any(item.title == title for item in self._items)

    def __repr__(self):
        return f"Catalog({self._items!r})"


# --- Uso ---
catalog = Catalog()
catalog.add(Item("1", "1984", "book", 1949))
catalog.add(Item("2", "Dune", "book", 1965, borrowed=True))
catalog.add(Item("3", "Blade Runner", "movie", 1982))

# __repr__ y __str__
print(repr(catalog.items[0]))  # Item(id='1', title='1984', kind='book', year=1949, borrowed=False)
print(catalog.items[0])        # 1984 (1949) — disponible

# __len__ y truthiness
print(len(catalog))            # 3
print(bool(catalog))           # True

# __iter__: for directo sobre el catálogo (sin .items)
for item in catalog:
    print(str(item))
# 1984 (1949) — disponible
# Dune (1965) — prestado
# Blade Runner (1982) — disponible

# __contains__
print("Dune" in catalog)       # True
print("Neuromante" in catalog) # False

# __lt__ manual para el orden + __eq__ que genera la propia dataclass
print(catalog.items[0] < catalog.items[1])   # True (1949 < 1965)
print(catalog.items[0] == Item("1", "1984", "book", 1949))  # True

Decisiones explicadas:

  • Item usa @dataclass, que genera __eq__ por valor. El orden (__lt__) lo escribimos a mano para personalizarlo: en un catálogo queremos ordenar por año y, a igualdad, por título. La dataclass con order=True (lección 4) lo generaría automáticamente, pero entonces no podrías comparar por un criterio propio. Aquí demostramos la firma real del dunder; no mezcles order=True con un __lt__ manual, porque Python 3.14 lanza TypeError al detectar el conflicto.
  • borrowed tiene compare=False: el estado de préstamo no define la identidad del ítem (un mismo libro prestado o no sigue siendo el mismo libro).
  • Catalog.__contains__ busca por título, no por identidad. Es una decisión de dominio: "Dune" in catalog se lee mejor que catalog.find_by_title("Dune") is not None. Documentar el protocolo es clave cuando su semántica no es obvia.
  • items devuelve una copia de la lista interna: evita que el llamador mutile el catálogo. La mutación legítima pasa por add().

El __repr__ de Catalog delega en la lista. f"Catalog({self._items!r})" aplica repr() a la lista, que a su vez llama al __repr__ de cada Item. Así, un solo print(repr(catalog)) muestra todo el contenido de forma legible. Esto es lo que hace que los contenedores integrados de Python sean tan cómodos de depurar: cada nivel implementa su __repr__.

6 · Errores habituales

No definir __repr__: objetos ilegibles

# ❌ Sin __repr__, depurar una lista es inservible.
class Item:
    def __init__(self, title):
        self.title = title

items = [Item("1984"), Item("Dune")]
print(items)   # [<__main__.Item object at 0x7f...>, <__main__.Item object at 0x7f...>]

# ✅ Con __repr__, el estado aparece ante tus ojos.
class Item:
    def __init__(self, title):
        self.title = title

    def __repr__(self):
        return f"Item({self.title!r})"

print([Item("1984"), Item("Dune")])   # [Item('1984'), Item('Dune')]

Definir __eq__ y perder la hashabilidad sin darse cuenta

# ❌ __eq__ por valor, pero el objeto deja de ser hashable.
class Item:
    def __init__(self, id):
        self.id = id

    def __eq__(self, other):
        return isinstance(other, Item) and self.id == other.id

# {Item("1")}   # TypeError: unhashable type: 'Item'

# ✅ Define __hash__ coherente si lo necesitas (y hazlo inmutable).
class Item:
    def __init__(self, id):
        self.id = id

    def __eq__(self, other):
        return isinstance(other, Item) and self.id == other.id

    def __hash__(self):
        # Debe depender de los MISMOS campos que __eq__.
        return hash(self.id)

print({Item("1"), Item("1")})   # {<__main__.Item object at ...>} -> un solo ítem

Si el objeto va a cambiar, no es buena idea hacerlo hashable: si su estado cambia, el hash también y la tabla hash se corrompe. En la práctica, o es inmutable y hashable, o no lo metas en un set.

__eq__ que devuelve False en lugar de NotImplemented

# ❌ Afirma "no son iguales" para cualquier tipo, impidiendo la comparación reflexiva.
class Item:
    def __init__(self, id):
        self.id = id

    def __eq__(self, other):
        if not isinstance(other, Item):
            return False          # debería ser NotImplemented
        return self.id == other.id

# ✅ NotImplemented deja que Python pruebe el __eq__ del otro tipo.
class Item:
    def __init__(self, id):
        self.id = id

    def __eq__(self, other):
        if not isinstance(other, Item):
            return NotImplemented
        return self.id == other.id

Llamar a los dunders directamente

# ❌ Feo y frágil: no es la API pública.
item.__repr__()
item.__len__()
item.__eq__(otro)

# ✅ Usa las funciones y operadores para los que existen.
repr(item)

item == otro

Olvidar que __str__ cae en __repr__ (y viceversa no)

class Item:
    def __str__(self):          # solo __str__
        return "legible"

item = Item()
print(str(item))    # legible
print(repr(item))   # <__main__.Item object at 0x...>  <- sigue ilegible en depuración
# Moraleja: define __repr__ (y str solo si quieres una versión de usuario).

8 · Reto

🎯 Un catálogo indexable y comparable

Amplía Catalog para que soporte indexación y slicing: catalog[0] y catalog[0:2] deben funcionar como en una lista. Necesitarás el dunder __getitem__ (no visto en la teoría; investiga su firma y qué debe devolver para el slicing). Después añade __eq__ al Catalog para que dos catálogos sean iguales si contienen los mismos ítems en el mismo orden.

Pista: __getitem__(self, index) recibe el índice o un slice; puedes delegar directamente en self._items[index] y listo. Ojo con __eq__: debe devolver NotImplemented si el otro no es un Catalog, y comparar las listas internas. Y pregúntate: si añades __getitem__, ¿tu Catalog pasa a ser también iterable por sí solo? (Pista: Python puede iterar un objeto con __getitem__ aunque no tenga __iter__; experimenta eliminando __iter__ y observa.) 9 · Resumen

  • Los dunders son métodos que Python invoca internamente al usar la sintaxis (==, <, len, for, in…).
  • __repr__ es para el desarrollador y es imprescindible para depurar; __str__ es para el usuario. Si solo defines uno, que sea __repr__.
  • __eq__ compara por valor; devuelve NotImplemented con tipos ajenos. Definir __eq__ anula __hash__ salvo que lo definas coherente.
  • __lt__ habilita sorted/min/max; en dataclasses, order=True lo genera.
  • __len__, __iter__ y __contains__ implementan el protocolo de colección: len(), for e in.
  • Duck typing: si implementas los métodos del protocolo, sirves, sin importar de qué clase heredes.

10 · Preguntas frecuentes

¿Cuál es la diferencia real entre __repr__ y __str__?

__repr__ es la representación oficial, para el desarrollador: sin ambigüedad, idealmente recreable evaluando el texto. __str__ es la informal, para el usuario final. En una consola, repr; en print(), str. Dentro de un contenedor ([obj], un dict, un log), Python usa __repr__. Por eso siempre se define __repr__ y __str__ solo cuando el usuario necesita una frase distinta.

¿Por qué mi __eq__ debería devolver NotImplemented y no False?

«No son iguales» (False) y «no sé compararlo» (NotImplemented) son cosas distintas. Devolver NotImplemented le dice a Python que pruebe el __eq__ del otro operando (comparación reflexiva). Si devuelves False, bloqueas esa posibilidad y puedes dar respuestas incorrectas en jerarquías o con tipos de terceros. Python interpreta NotImplemented en ambos lados como «no iguales», pero sin robar la oportunidad al otro tipo.

¿Qué es el duck typing exactamente?

Es la idea de que el comportamiento importa más que el tipo declarado. Si una función hace for x in coleccion, no le importa si coleccion es una list, un set o tu Catalog: solo le importa que sea iterable (que tenga __iter__). Esto hace a las funciones más flexibles y reutilizables. El precio es que el error, si el objeto no cumple el protocolo, aparece en ejecución; se mitiga con tests y con typing.Protocol + mypy (Módulo 7).

¿Puedo sobrecargar operadores como + o *?

Sí: __add__, __mul__, __sub__… Pero con criterio. La sobrecarga de operadores debe coincidir con la intuición de quien lee el código. En el dominio Biblioteca, len(catalog) o "Dune" in catalog se entienden; item1 + item2 no significa nada obvio y confundiría. Regla: sobrecarga solo si la operación resulta natural para el tipo (vectores que se suman, dinero que se suma), no porque se pueda.

¿Implementar __len__ hace mi objeto iterable, o __iter__ lo hace contable?

No: cada protocolo es independiente. __len__ da len() y truthiness; __iter__ da iteración; __contains__ da pertenencia. Si defines __iter__ pero no __contains__, Python puede calcular in iterando (más lento). Si defines __getitem__, Python también puede iterar aunque no tengas __iter__ (protocolo heredado de las secuencias). Por eso conviene implementar explícitamente los que tengan sentido y no depender de los caminos alternativos, que además pueden ser más lentos.
