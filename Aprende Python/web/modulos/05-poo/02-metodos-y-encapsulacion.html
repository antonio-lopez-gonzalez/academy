Métodos, propiedades y encapsulación

Módulo 5 · Programación orientada a objetos ⏱ 30 minutos

1 · Introducción

En la lección anterior nuestra clase Item expone sus atributos tal cual: item.year = 99999 es perfectamente posible y nadie lo impide. Un catálogo real no puede aceptar eso. Necesitamos que el objeto valide lo que se le asigna y que ofrezca operaciones derivadas (por ejemplo, un label calculado) sin que quien lo use tenga que llamar a un método.

Esta lección enseña el sistema de métodos de Python y sus tres tipos (instance, @classmethod, @staticmethod), el mecanismo de encapsulación real de Python (que no es private de Java), y cómo convertir un atributo en una propiedad con @property y su setter para validar sin cambiar la forma de usarlo.

¿Por qué Python no tiene private? Porque la filosofía de Python es «somos adultos responsables»: no hay barreras infranqueables, hay convenciones claras. Un atributo con guion bajo (_year) significa «es interno, no lo toques desde fuera»; la comunidad lo respeta y las herramientas lo señalan. Esto evita la rigidez de getters/setters obligatorios y permite empezar simple y endurecer después sin romper a quien ya usa la clase.

Al terminar sabrás escribir un setter que rechace años imposibles, entenderás por qué una @property es mejor que un get_year(), y distinguirás cuándo usar cada tipo de método.

2 · Teoría

Tres tipos de métodos

Ya conoces los métodos de instancia. Python ofrece dos decoradores más para casos concretos. La diferencia está en qué reciben como primer argumento:

TipoPrimer parámetroSe llama sobre…Cuándo usarlo
Instanciaself (la instancia)item.describe()Necesita leer/escribir estado del objeto. El caso normal.
@classmethodcls (la clase)Item.from_dict(d)Constructores alternativos; trabajar con la clase, no con una instancia.
@staticmethodningunoItem.is_valid_kind(k)Utilidad que lógicamente pertenece a la clase pero no necesita estado.
 
class Item:
    # 1) Método de INSTANCIA: recibe self.
    def describe(self):
        return f"{self.title}"

    # 2) @classmethod: recibe la CLASE (cls), no una instancia.
    @classmethod
    def build_default(cls, title):
        # cls es Item (o la subclase que lo invoque).
        return cls(id="?", title=title, kind="book")

    # 3) @staticmethod: no recibe ni self ni cls.
    @staticmethod
    def is_valid_kind(kind):
        return kind in {"book", "movie"}

¿Por qué existe @classmethod? Porque a veces quieres construir un ítem desde otro formato sin instanciar a mano. Item.from_dict({...}) lee mejor que una función externa parse_item() y queda asociado a la clase correcta: si existe class Book(Item), Book.from_dict(...) creará un Book porque cls es dinámico. Un @staticmethod, en cambio, no sabe de qué clase se llamó.

Encapsulación en Python: convención, no candado

Python tiene tres «niveles» que son solo acuerdos de nomenclatura:

FormaNombreQué significa
yearPúblicoParte de la API de la clase. Úsalo desde fuera.
_yearProtegido (convención)Interno. Puedes mirarlo, pero no deberías depender de él: puede cambiar.
__yearPrivado (name mangling)Python lo renombra a _Item__year. Evita colisiones en herencia; no es privacidad real.
 
class Item:
    def __init__(self):
        self.public = "todos"
        self._internal = "convención"
        self.__mangled = "renombrado"


item = Item()
print(item.public)              # todos
print(item._internal)           # convención (funciona, pero no lo hagas)
# print(item.__mangled)         # AttributeError: no existe ese nombre
print(item._Item__mangled)      # renombrado  <- el nombre real tras el mangling
print(item.__dict__)            # {'public':..., '_internal':..., '_Item__mangled':...}

El name mangling no protege nada: solo cambia el nombre para evitar que una subclase pise por accidente el atributo de la base. Sirve para decir «esto es mío, no lo heredes ni lo toques». Si de verdad necesitas aislamiento, la respuesta en Python no es __, es no exponer API innecesaria y documentar.

No abuses del doble guion bajo. __x activa el mangling incluso dentro de la misma clase y complica la depuración y el testing. La convención mayoritaria es un solo guion bajo (_x) para lo interno. Reserva __ para evitar colisiones deliberadas en jerarquías.

@property: atributo de aspecto, método por dentro

Una propiedad permite que algo calculado o validado se use como un atributo. Se lee item.label (sin paréntesis), pero por dentro se ejecuta un método. Y con @nombre.setter interceptamos la asignación item.year = 1949 para validar.

class Item:
    def __init__(self, title, year=None):
        self.title = title
        self.year = year              # pasa por el setter (ver abajo)

    @property
    def year(self):
        # GETTER: se ejecuta al leer item.year
        return self._year

    @year.setter
    def year(self, value):
        # SETTER: se ejecuta al asignar item.year = value
        if value is not None and not isinstance(value, int):
            raise TypeError("year debe ser int o None")
        if value is not None and not (0 < value < 3000):
            raise ValueError(f"año fuera de rango: {value}")
        self._year = value             # guardamos en el atributo interno


item = Item("1984", 1949)
print(item.year)      # 1949   (getter)
item.year = 2000      # setter valida
print(item.year)      # 2000
# item.year = 99999   # ValueError: año fuera de rango: 99999

¿Por qué usar @property en vez de get_year()/set_year()? Porque mantiene la sintaxis de atributo (item.year), que es lo natural en Python, y a la vez te permite añadir lógica. La gran ventaja: puedes empezar con self.year = year como atributo plano y, el día que necesites validar, convertir year en propiedad sin que cambie una sola línea del código que lo usa. Es evolución sin ruptura.

Propiedades calculadas (solo getter)

class Item:
    def __init__(self, title, kind, year):
        self.title = title
        self.kind = kind
        self.year = year

    @property
    def label(self):
        # No hay setter: es de solo lectura, se calcula al vuelo.
        return f"{self.title} · {self.year}"

item = Item("1984", "book", 1949)
print(item.label)          # 1984 · 1949
# item.label = "x"         # AttributeError: can't set attribute

Una propiedad sin setter es de solo lectura: intentar asignarla lanza AttributeError. Perfecto para valores derivados que no deben fijarse a mano.

3 · Ejemplo mínimo

La propiedad más pequeña con sentido: una temperatura que nunca baja de un mínimo absoluto. Es el patrón «validar en el setter» reducido a lo esencial.

temperature.py
class Temperature:
    # El cero absoluto es el mínimo físico: lo validamos siempre.
    ZERO = -273.15

    def __init__(self, celsius):
        # Asignamos a la propiedad: pasa por el setter y valida ya.
        self.celsius = celsius

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < Temperature.ZERO:
            raise ValueError(f"por debajo del cero absoluto: {value}")
        self._celsius = value


t = Temperature(20)
print(t.celsius)          # 20
t.celsius = -40
print(t.celsius)          # -40
# Temperature(-300)       # ValueError: por debajo del cero absoluto: -300

Por qué funciona: en __init__ escribimos self.celsius = celsius (no self._celsius), de modo que incluso el valor inicial pasa por la validación. El dato real vive en _celsius; celsius es solo la puerta de entrada. Así es imposible crear una Temperature inválida.

4 · Ejemplo real

Endurecemos nuestro Item de Biblioteca: year validado con rango, kind validado contra una lista cerrada, un label calculado y un constructor alternativo from_dict (típico para leer del JSON más adelante).

biblioteca/models.py (versión de esta lección)
class Item:
    """Ítem del catálogo, con datos validados."""

    # Constantes de clase: inmutables, compartidas, documentan las reglas.
    VALID_KINDS = frozenset({"book", "movie"})   # frozenset: inmutable
    MIN_YEAR = 0
    MAX_YEAR = 3000

    def __init__(self, id, title, kind, year=None):
        self.id = id
        self.title = title
        self.kind = kind            # pasa por el setter (valida)
        self.year = year            # pasa por el setter (valida)
        self.borrowed = False

    # ---------- PROPERTY: kind ----------
    @property
    def kind(self):
        return self._kind

    @kind.setter
    def kind(self, value):
        if value not in Item.VALID_KINDS:
            raise ValueError(f"kind inválido: {value!r}")
        self._kind = value

    # ---------- PROPERTY: year ----------
    @property
    def year(self):
        return self._year

    @year.setter
    def year(self, value):
        # None es válido: significa "año desconocido".
        if value is not None:
            if not isinstance(value, int):
                raise TypeError(f"year debe ser int o None, no {type(value).__name__}")
            if not (Item.MIN_YEAR <= value <= Item.MAX_YEAR):
                raise ValueError(f"año fuera de rango: {value}")
        self._year = value

    # ---------- PROPERTY calculada, solo lectura ----------
    @property
    def label(self):
        year = self.year if self.year is not None else "s/a"
        return f"{self.title} ({year})"

    # ---------- @classmethod: constructor alternativo ----------
    @classmethod
    def from_dict(cls, data):
        """Crea un Item desde un dict (p. ej. leído del JSON)."""
        return cls(
            id=str(data["id"]),
            title=data["title"],
            kind=data.get("kind", "book"),
            year=data.get("year"),
        )

    # ---------- @staticmethod: utilidad sin estado ----------
    @staticmethod
    def is_valid_kind(kind):
        return kind in Item.VALID_KINDS


# --- Uso ---
book = Item("1", "1984", "book", 1949)
print(book.label)              # 1984 (1949)
print(book.kind)               # book

data = {"id": 2, "title": "Blade Runner", "kind": "movie", "year": 1982}
movie = Item.from_dict(data)   # constructor alternativo
print(movie.label)             # Blade Runner (1982)

print(Item.is_valid_kind("book"))    # True
print(Item.is_valid_kind("cd"))      # False

# Los setters protegen invariantes:
# Item("3", "X", "cd")        # ValueError: kind inválido: 'cd'
# book.year = 99999           # ValueError: año fuera de rango: 99999

Decisiones explicadas:

  • VALID_KINDS es un frozenset, no una list: es inmutable y la comprobación in es O(1). Como constante de clase, no hay riesgo de mutación accidental (el bug de la lección 1).
  • El orden en __init__ importa: self.year = year pasará por el setter, y el setter consulta Item.MIN_YEAR en la clase, no en la instancia.
  • from_dict usa cls(...), no Item(...): así, si mañana hay class Movie(Item), Movie.from_dict(...) devolverá un Movie. Ese polimorfismo se explica en la lección 3.
  • is_valid_kind no necesita ni self ni cls: @staticmethod evita instanciar solo para preguntar algo.

Los errores de validación usan excepciones con tipo correcto: ValueError cuando el valor es del tipo esperado pero fuera de rango, TypeError cuando el tipo es incorrecto. Distinguirlas importa porque el manejo de errores (Módulo 6) capturará cada una por separado. En Módulo 6 definiremos una jerarquía propia (BibliotecaError).

5 · Buenas prácticas

HazEvitaPor qué
Empieza con atributos públicos simples Escribir get_/set_ para todo «por si acaso» En Python acceder a item.title es lo idiomático. Añade @property solo cuando haga falta lógica.
Valida en el setter, incluido el valor inicial Validar solo al asignar desde fuera Si __init__ escribe el atributo interno directamente, puedes crear objetos inválidos.
Un solo guion bajo (_year) para lo interno Doble guion (__year) «para hacerlo private» El mangling complica depuración y testing; no aporta privacidad real.

6 · Errores habituales

Olvidar el _ y provocar recursión infinita en el setter

# ❌ El setter se asigna a sí mismo: recursión sin fin.
class Item:
    @property
    def year(self):
        return self.year          # RecursionError: se llama a sí misma

    @year.setter
    def year(self, value):
        self.year = value         # ¡vuelve a llamar al setter!

# ✅ El dato real va en el atributo interno _year.
class Item:
    @property
    def year(self):
        return self._year

    @year.setter
    def year(self, value):
        self._year = value

Es el error nº 1 al introducir propiedades: confundir el nombre de la propiedad con el del almacenamiento. La propiedad year intercepta item.year; por dentro hay que escribir en otro nombre, típicamente _year.

Validar solo en el setter y saltárselo en __init__

# ❌ El constructor escribe el interno: se salta la validación.
class Item:
    def __init__(self, year):
        self._year = year         # no pasa por el setter

    @property
    def year(self):
        return self._year

    @year.setter
    def year(self, value):
        if value < 0:
            raise ValueError("año negativo")
        self._year = value

bad = Item(-5)                    # ningún error: objeto inválido creado
print(bad.year)                   # -5

# ✅ El constructor asigna a la PROPIEDAD, no al interno.
class Item:
    def __init__(self, year):
        self.year = year          # dispara el setter

    @property
    def year(self):
        return self._year

    @year.setter
    def year(self, value):
        if value < 0:
            raise ValueError("año negativo")
        self._year = value

# Item(-5)                        # ValueError: año negativo

Creer que __x (mangling) es privado de verdad

# ❌ "Lo hice private con __, nadie puede tocarlo desde fuera".
class Item:
    def __init__(self):
        self.__secret = "valor"

item = Item()
# print(item.__secret)      # AttributeError
print(item._Item__secret)   # valor   <- accesible si conoces el mangling

# ✅ Si es interno, nómbralo _secret y documenta que no es API.
#    Si es API, déjalo público. No hay candados, hay acuerdos.

Usar @staticmethod cuando hace falta self

# ❌ staticmethod intenta leer estado de la instancia: no lo recibe.
class Item:
    def __init__(self, title):
        self.title = title

    @staticmethod
    def describe():
        return f"{self.title}"     # NameError: name 'self' is not defined

# ✅ Si necesita el estado del objeto, es método de instancia.
class Item:
    def __init__(self, title):
        self.title = title

    def describe(self):
        return f"{self.title}"

Robar el nombre del atributo con la propiedad

# ❌ La propiedad "borrowed" no puede convivir con un atributo del mismo nombre.
class Item:
    @property
    def borrowed(self):
        return self._borrowed

    @borrowed.setter
    def borrowed(self, value):
        self._borrowed = value

# Al instanciar, self.borrowed = False llama al setter -> sin problema.
# Pero este patrón es válido SOLO si el almacenamiento interno es _borrowed.
# Si escribieras self.borrowed = value dentro del setter, recursión.

9 · Resumen

  • Hay tres tipos de métodos: de instancia (self), @classmethod (cls) y @staticmethod (ninguno).
  • La encapsulación en Python es una convención: _x = interno, __x = renombrado (mangling) para evitar colisiones, no privacidad real.
  • @property convierte un método en un atributo de lectura; @nombre.setter intercepta la asignación para validar.
  • El dato real de una propiedad se guarda en un atributo con otro nombre (_year); asignarse a sí misma causa RecursionError.
  • Valida también el valor inicial: __init__ debe asignar a la propiedad, no al atributo interno.
  • Las propiedades calculadas (solo getter) son de solo lectura y nunca se desincronizan.

10 · Preguntas frecuentes

¿Cuándo convierto un atributo en @property?

Cuando necesitas lógica al leer o escribir: validar, normalizar, calcular o impedir el acceso. Mientras el atributo sea un simple contenedor de datos, déjalo público. Lo bonito es que no tienes que decidirlo desde el principio: puedes empezar con self.year = year y, cuando aparezca la necesidad, reescribirlo como propiedad sin cambiar a quien ya usaba item.year. Esa evolución sin ruptura es la razón de ser de las propiedades.

¿Un @classmethod es como un constructor de Java/C#?

Se parece: Item.from_dict(d) es un «constructor alternativo» que devuelve una instancia. La diferencia conceptual es que en Python no hay overloading de constructores; en su lugar, se añaden factory methods con nombre descriptivo (from_dict, from_row, empty). Recibe cls en vez de self y, al hacer cls(...), respeta la subclase desde la que se llama.

¿Por qué mi setter da RecursionError?

Porque dentro del setter escribiste self.year = value en vez de self._year = value. self.year = … vuelve a invocar el setter, que se vuelve a llamar a sí mismo… hasta que Python corta con RecursionError: maximum recursion depth exceeded. Regla: la propiedad es la puerta; el almacén es _year.

¿Puedo tener una propiedad con el mismo nombre que el parámetro de __init__?

Sí, y es lo normal: def __init__(self, year): self.year = year. El parámetro year es local al método; self.year = year pasa por el setter de la propiedad year. No hay conflicto. Lo que sí sería un problema es querer tener a la vez un atributo de instancia year y una propiedad year: la propiedad siempre gana, porque vive en la clase.

¿@staticmethod no es lo mismo que una función normal del módulo?

Funcionalmente sí; la diferencia es organizativa. Item.is_valid_kind(k) deja claro que esa validación pertenece al dominio del ítem y la mantiene junto a él. Además participa de la herencia y del autocompletado. Una función suelta is_valid_kind(k) en el módulo también funciona, pero se pierde la asociación. Úsala cuando la lógica esté conceptualmente atada a la clase aunque no necesite su estado.
