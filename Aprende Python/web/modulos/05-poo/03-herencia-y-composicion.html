Herencia y composición

Módulo 5 · Programación orientada a objetos ⏱ 35 minutos

1 · Introducción

Un catálogo mezcla libros y películas. Ambos comparten lo esencial (id, título, año, si están prestados) pero difieren en detalles: un libro tiene autor y páginas; una película, director y duración. Hasta ahora tendríamos un solo Item con un montón de campos opcionales que a veces aplican y a veces no. Eso es frágil: nadie impide crear una película con autor o un libro con duración.

La herencia resuelve esto declarando un tipo base Item con lo común y dos subtipos Book y Movie que añaden lo suyo. La composición es la alternativa: en vez de «ser un», un objeto «tiene un» colaborador. Esta lección enseña ambas, cuándo preferir cada una (spoiler: favor composition over inheritance) y cómo definir contratos con clases abstractas (abc).

¿Por qué importa el diseño? Porque la herencia crea un acoplamiento fuerte: un cambio en la clase base se propaga a todas las subclases. Usada mal, genera jerarquías profundas e inmanejables. Python la soporta, pero la comunidad prefiere composición para el comportamiento variable y reserva la herencia para relaciones «es un» genuinas y estables. Entender esto es lo que separa a quien escribe clases de quien modela dominios.

2 · Teoría

Herencia: «es un»

Una clase puede heredar de otra. La subclase recibe todos sus atributos y métodos, y puede añadir o sobrescribir. La relación debe leerse «Book es un Item».

class Item:                        # clase BASE (o superclase)
    def __init__(self, id, title):
        self.id = id
        self.title = title

    def describe(self):
        return f"[{self.id}] {self.title}"


class Book(Item):                  # subclase: hereda de Item
    def __init__(self, id, title, author):
        super().__init__(id, title)  # delega la parte común en la base
        self.author = author         # añade lo propio

    def describe(self):             # sobrescribe (override)
        return f"{super().describe()} — {self.author}"


book = Book("1", "1984", "George Orwell")
print(book.describe())   # [1] 1984 — George Orwell
print(isinstance(book, Book))   # True
print(isinstance(book, Item))   # True  <- un Book ES un Item

super(): no es «la clase padre», es «el siguiente en el MRO»

super() devuelve un objeto que delega la llamada al método siguiente en el orden de resolución de métodos (MRO). Con herencia simple parece «la clase padre», pero la definición exacta importa en la herencia múltiple.

class A:
    def hello(self):
        return "A"

class B(A):
    def hello(self):
        # super() -> sigue la cadena a partir de B: encuentra A
        return "B+" + super().hello()

class C(B):
    def hello(self):
        return "C+" + super().hello()

print(C().hello())   # C+B+A

¿Por qué super() y no Item.__init__(self, ...)? Porque nombrar la clase explícitamente se rompe en cuanto hay herencia múltiple o se reordena la jerarquía: llamarías al método equivocado o duplicarías inicialización. super() sigue el MRO calculado por Python, de modo que la cadena de colaboración es coherente. Es la forma correcta y la única que coopera en jerarquías en las que varias bases llaman a super().

MRO: el orden de resolución de métodos

El MRO (Method Resolution Order) es el orden en que Python busca un método o atributo: primero la instancia, luego su clase, luego las bases, según el algoritmo C3 linealization. Lo puedes consultar con Clase.__mro__ o Clase.mro().

class Item: describe() ^ | class Media(Item): ... ^ | class Movie(Media): describe() -> override Movie.__mro__ = (Movie, Media, Item, object) 1º 2º 3º 4º Buscar "describe" en Movie(): si no está -> Media -> Item -> object 
class Item:
    pass

class Media(Item):
    pass

class Movie(Media):
    pass

print([c.__name__ for c in Movie.__mro__])
# ['Movie', 'Media', 'Item', 'object']

El MRO siempre termina en object, la raíz de todo en Python. Cuando hay class C(A, B), C3 garantiza que una clase aparece antes que sus bases y que el orden es coherente; si es imposible, Python lanza TypeError: Cannot create a consistent method resolution order.

isinstance e issubclass

movie = Movie("2", "Blade Runner")

print(isinstance(movie, Movie))    # True
print(isinstance(movie, Media))    # True (por herencia)
print(isinstance(movie, Item))     # True
print(isinstance(movie, str))      # False

print(issubclass(Movie, Item))     # True  (relación de clases)
print(issubclass(Item, Movie))     # False

isinstance es la comprobación correcta cuando trabajas con jerarquías. Prefiere isinstance(x, T) a type(x) is T: el primero respeta la herencia (y duck typing con ABCs, lección 5); el segundo exige el tipo exacto.

Composición: «tiene un»

En lugar de heredar, un objeto contiene a otro y delega en él. Si mañana los ítems pueden tener un Loan (préstamo) con fecha y prestatario, no decimos «Item es un Loan», sino «Item tiene un Loan».

class Loan:
    """Un préstamo activo."""
    def __init__(self, borrower, days):
        self.borrower = borrower
        self.days = days

    def summary(self):
        return f"{self.borrower} ({self.days} días)"


class Item:
    def __init__(self, id, title):
        self.id = id
        self.title = title
        self.loan = None            # TIENE UN préstamo (o ninguno)

    def borrow(self, borrower, days):
        if self.loan is not None:
            raise ValueError("ya está prestado")
        self.loan = Loan(borrower, days)   # composición

    def status(self):
        # Delegamos en el colaborador cuando existe.
        return "disponible" if self.loan is None else self.loan.summary()


item = Item("1", "1984")
item.borrow("Ana", 14)
print(item.status())    # Ana (14 días)

¿Herencia o composición? Favor composition

CriterioHerenciaComposición
Relación«es un» (Book es un Item)«tiene un» (Item tiene un Loan)
AcoplamientoFuerte: la base afecta a todas las subclasesDébil: el colaborador se puede cambiar
ReutilizaciónTodo lo heredado queda expuestoSolo delegas lo que necesitas
RiesgoJerarquías profundas, método equivocado (frágil base class)Más código de delegación, pero más claro
CuándoJerarquía estable y relación genuinaComportamiento variable, cambio frecuente

Analogía — el coche: un coche tiene un motor, no es un motor. Podrías heredar de Motor para reutilizar su método start(), pero entonces un coche «sería» un motor y quedarías atado a esa jerarquía; cambiar a motor eléctrico obligaría a reescribir la clase. Con composición, el coche contiene un motor y puedes sustituirlo sin tocar el coche. Lo mismo en biblioteca: un Item tiene metadatos, no es un Metadata.

Clases abstractas con abc

A veces queremos declarar un contrato: «todo Item debe saber describirse», pero no hay una implementación única. Para eso está el módulo abc (Abstract Base Classes): define métodos abstractos que las subclases están obligadas a implementar. Intentar instanciar la base abstracta falla.

from abc import ABC, abstractmethod


class Item(ABC):                        # hereda de ABC
    def __init__(self, id, title):
        self.id = id
        self.title = title

    @abstractmethod
    def describe(self):
        """Cada ítem concreto DEBE implementarlo."""
        ...


class Book(Item):
    def __init__(self, id, title, author):
        super().__init__(id, title)
        self.author = author

    def describe(self):                 # cumple el contrato
        return f"{self.title} — {self.author}"


# Item("1", "x")       # TypeError: Can't instantiate abstract class Item
book = Book("1", "1984", "Orwell")
print(book.describe())  # 1984 — Orwell

# class Bad(Item): pass   # tampoco se puede instanciar: describe() sin implementar

¿Por qué existe abc? Porque Python no hace comprobación estática de contratos como Java. Sin ABC, olvidar implementar describe daría error solo al llamarlo, tarde y lejos. Con @abstractmethod, el error salta al instanciar, en el momento y lugar donde importa. Es además la base de los protocolos para duck typing que verás en la lección 5.

3 · Ejemplo mínimo

Una jerarquía de dos niveles con super(), lo más pequeño posible, para ver cómo se construye de abajo arriba.

animals.py
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return "..."

class Dog(Animal):
    def speak(self):
        # Recupera el ".speak()" de la clase base y lo enriquece.
        return "guau (" + super().speak() + ")"


a = Animal("genérico")
d = Dog("Rex")
print(a.speak())                     # ...
print(d.speak())                     # guau (...)
print(isinstance(d, Animal))         # True

Línea por línea: Dog hereda __init__ tal cual de Animal (por eso Dog("Rex") funciona sin definir constructor). Dog.speak sobrescribe el de la base y llama a super().speak() para reutilizar su resultado. La instancia d pasa los dos isinstance por la relación de herencia.

4 · Ejemplo real

Modelamos Book y Movie como subclases de un Item abstracto, y usamos composición para el préstamo. Este es el esqueleto que el proyecto final irá refinando.

biblioteca/models.py (versión de esta lección)
from abc import ABC, abstractmethod


class Loan:
    """Colaborador que representa un préstamo activo."""

    def __init__(self, borrower, days):
        self.borrower = borrower
        self.days = days

    def summary(self):
        return f"{self.borrower} ({self.days} días)"


class Item(ABC):
    """Base abstracta: todo ítem del catálogo."""

    def __init__(self, id, title, year=None):
        self.id = id
        self.title = title
        self.year = year                 # validación simplificada aquí
        self.loan = None                 # COMPOSICIÓN: tiene un Loan o None

    @abstractmethod
    def describe(self):
        """Contrato: cada subtipo describe A SU MANERA."""
        ...

    def borrow(self, borrower, days):
        if self.loan is not None:
            raise ValueError(f"{self.id} ya está prestado")
        self.loan = Loan(borrower, days)

    def return_item(self):
        self.loan = None

    @property
    def borrowed(self):
        return self.loan is not None


class Book(Item):
    def __init__(self, id, title, author, pages=None, year=None):
        super().__init__(id, title, year)
        self.author = author
        self.pages = pages

    def describe(self):
        extra = f", {self.pages} págs." if self.pages else ""
        return f"[{self.id}] {self.title} — {self.author}{extra}"


class Movie(Item):
    def __init__(self, id, title, director, duration=None, year=None):
        super().__init__(id, title, year)
        self.director = director
        self.duration = duration         # minutos

    def describe(self):
        extra = f", {self.duration} min" if self.duration else ""
        return f"[{self.id}] {self.title} — dir. {self.director}{extra}"


# --- Uso: polimorfismo en acción ---
catalog = [
    Book("1", "1984", "George Orwell", pages=328, year=1949),
    Movie("2", "Blade Runner", "Ridley Scott", duration=117, year=1982),
]

# Un único bucle trata ambos subtipos igual: polimorfismo.
for item in catalog:
    print(item.describe())
# [1] 1984 — George Orwell, 328 págs.
# [2] Blade Runner — dir. Ridley Scott, 117 min

catalog[0].borrow("Ana", 14)
print(catalog[0].borrowed)      # True
print(catalog[0].loan.summary())  # Ana (14 días)
catalog[0].return_item()
print(catalog[0].borrowed)      # False

# isinstance respeta la jerarquía:
print(isinstance(catalog[0], Book))   # True
print(isinstance(catalog[0], Item))   # True
print(isinstance(catalog[1], Book))   # False

Decisiones explicadas:

  • Item es abstracta: no se puede crear «un ítem genérico», siempre es libro o película. Eso evita estados ambiguos y obliga a implementar describe.
  • Las subclases llaman a super().__init__(id, title, year) y luego añaden sus campos. Nunca repiten la inicialización de la base.
  • Loan se compone: un Item tiene un préstamo. Podríamos haber hecho class Item(Loan) pero sería un modelado falso; además, cambiar las reglas del préstamo no obligaría a tocar la clase del ítem.
  • El bucle final es polimorfismo: el mismo item.describe() ejecuta el código de Book o de Movie según el objeto. Es la razón práctica de usar herencia aquí.

Regla práctica: usa herencia cuando la lista de subtipos es corta y estable y el «es un» no admite discusión (Book/Movie son Item). Si el comportamiento varía con frecuencia o el subtipo podría cambiar en tiempo de ejecución, compón. Y cuando dudes, empieza con composición: es más fácil convertir composición en herencia que al contrario.

6 · Errores habituales

No llamar a super().__init__()

# ❌ La subclase define __init__ pero no inicializa la base.
class Item:
    def __init__(self, id, title):
        self.id = id
        self.title = title

class Book(Item):
    def __init__(self, id, title, author):
        self.author = author     # faltan self.id y self.title

book = Book("1", "1984", "Orwell")
print(book.author)               # Orwell
# print(book.title)              # AttributeError: 'Book' object has no attribute 'title'

# ✅ Delega la parte común en la base.
class Book(Item):
    def __init__(self, id, title, author):
        super().__init__(id, title)
        self.author = author

Heredar por reutilizar, no por ser

# ❌ Item hereda de Loan solo para tener sus métodos. Item NO ES un préstamo.
class Loan:
    def __init__(self, borrower, days):
        self.borrower = borrower
        self.days = days

class Item(Loan):                 # modelado falso
    def __init__(self, id, title):
        super().__init__(None, 0)  # truco para contentar a la base
        self.id = id
        self.title = title

# ✅ Item TIENE un préstamo (composición).
class Item:
    def __init__(self, id, title):
        self.id = id
        self.title = title
        self.loan = None           # colaborador opcional

Usar type(x) is T y romper la herencia

class Item: ...
class Book(Item): ...

book = Book()

# ❌ Falla para cualquier subclase de Item.
print(type(book) is Item)          # False  (es Book, no Item)
# ✅ Respeta la jerarquía.
print(isinstance(book, Item))      # True

Instanciar una clase abstracta

from abc import ABC, abstractmethod

class Item(ABC):
    @abstractmethod
    def describe(self): ...

# ❌ TypeError: Can't instantiate abstract class Item with abstract method describe
# item = Item()

# ❌ Tampoco una subclase que olvida implementarlo:
class Book(Item):
    pass
# Book()   # TypeError: abstract method describe

# ✅ Implementa todos los abstractos.
class Movie(Item):
    def describe(self):
        return "una película"
Movie()   # ok

Herencia múltiple sin entender el MRO

# ❌ Ambigüedad: ¿qué __init__ gana? Depende del MRO, no del orden que imaginas.
class A:
    def __init__(self):
        self.name = "A"
class B:
    def __init__(self):
        self.name = "B"
class C(A, B):
    pass

print(C().name)      # A  (C -> A -> B: gana A)

# ✅ Si necesitas combinar, hazlo explícito y coopera con super()
#    (o mejor: usa composición y evita la herencia múltiple).

9 · Resumen

  • La herencia modela «es un»; la composición, «tiene un». Prefiere composición salvo relación de tipo genuina y estable.
  • super() no llama a «la clase padre»: llama al siguiente método en el MRO.
  • El MRO (C3) es el orden de búsqueda de atributos y métodos; termina siempre en object.
  • isinstance(x, Base) respeta la herencia; type(x) is Base no. Usa issubclass para clases.
  • Las ABC (abc.ABC + @abstractmethod) definen contratos: no se pueden instanciar si falta implementar algo.
  • El polimorfismo permite tratar Book y Movie igual a través de Item.

10 · Preguntas frecuentes

¿Por qué «favor composition over inheritance»?

Porque la herencia crea un acoplamiento fuerte: un cambio en la base afecta a todas las subclases y cualquier método heredado queda expuesto aunque no tenga sentido. La composición acopla débilmente: el objeto contiene un colaborador con una interfaz concreta y lo puedes sustituir, envolver o simular. La máxima viene del libro Design Patterns (GoF, 1994) y Python la aplica con naturalidad. Hereda cuando el «es un» sea indiscutible y el conjunto de subtipos sea estable; en el resto, compón.

¿Qué es exactamente el MRO y por qué importa si solo uso una base?

El MRO es la lista ordenada de clases por la que Python busca un atributo: Movie.__mro__ es (Movie, Media, Item, object). Aunque uses una sola base, importa porque define a quién llama super() y qué método «gana» al sobrescribir. Con herencia múltiple es esencial: class C(A, B) resuelve en el orden que C3 considera consistente, no en el orden en que escribiste los métodos. Consúltalo con Clase.__mro__ cuando algo no se comporte como esperas.

¿Cuándo uso ABC y cuándo un protocolo (duck typing)?

ABC introduce acoplamiento explícito: la subclase debe heredar. Úsala cuando controles toda la jerarquía y quieras forzar el contrato. Los protocolos (o simplemente duck typing: «si camina como pato y grazna como pato…») no exigen herencia, solo que el objeto tenga los métodos; son más flexibles y se ven en la lección 5 con __iter__, __len__, etc. Como regla: ABC para contratos cerrados y jerarquías propias; protocolos/duck typing para interfaces abiertas de la biblioteca estándar.

¿Puedo sobrescribir un método y llamar al original?

Sí, y es lo recomendado: def describe(self): return super().describe() + " extra". Así amplías el comportamiento en lugar de reemplazarlo. Evita copiar y pegar el código de la base en la subclase: duplicar crea dos fuentes de verdad que se desincronizan. Si no quieres conservar nada del original, entonces no llames a super(), pero sé consciente de que estás rompiendo el comportamiento heredado (y puede violar el principio de sustitución de Liskov).

¿Un Book es también un Item a efectos de type()?

type(book) devuelve Book, no Item. Pero isinstance(book, Item) es True porque Book hereda de Item. La confusión típica es usar type(...) is Item y creer que una subclase no «es» un Item. Para comprobaciones de pertenencia a una jerarquía, isinstance siempre.
