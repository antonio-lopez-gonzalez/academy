Arquitectura del paquete

Módulo 9 · Proyecto final ⏱ 30 minutos

1 · Introducción

Durante ocho módulos Biblioteca creció de script suelto a sistema con clases, JSON, tests, tipos y logging. Todo funciona, pero aún vive «en el repositorio»: hay que estar en la carpeta correcta y ejecutar python -m. El último paso profesional es convertir esos archivos en un paquete instalable con un comando propio: bib.

Esta lección no escribe lógica de negocio: define el plano. Qué carpetas existen, qué responsabilidad tiene cada módulo, en qué dirección pueden importarse y cuál es el manifiesto (pyproject.toml) que describe el proyecto.

Por qué separar en capas antes de escribir código

El error típico de un proyecto que crece es mezclarlo todo: la CLI abriendo ficheros, la validación dentro del print, las reglas repartidas. Cuando algo falla no sabes dónde mirar. Al fijar las capas primero, cada línea futura tiene un sitio obvio.

Al terminar tendrás: la estructura src/biblioteca/ creada, un pyproject.toml real con el comando bib y el diagrama de capas.

Plan del Módulo 9. Cuatro pasos hasta la entrega:

  1. Arquitectura y paquete (esta lección).
  2. Implementar el núcleo: models, store y service.
  3. Tests y calidad: pytest, mypy y ruff.
  4. Empaquetar y entregar: entry point, build y verificación end-to-end.

2 · Teoría

Una arquitectura en capas reparte el sistema por responsabilidad y fija la dirección de las dependencias. En Biblioteca son cuatro, de dentro hacia fuera:

MóduloResponsabilidadConoce aNo conoce a
models.pyQué es un ítem (datos)—store, service, cli
store.pyCómo se guarda/lee en JSONmodelsservice, cli
service.pyReglas: add, list_items, search, borrow, return_itemmodels, storecli
cli.pyHablar con la persona (argparse)service, store, models— (es el borde)

La regla de oro es la dirección de las dependencias: las flechas apuntan hacia dentro. cli puede importar service, pero service jamás importa cli. ¿Por qué? Porque la CLI es un detalle reemplazable: mañana una API web podría llamar al mismo service sin tocar las reglas.

                       ┌──────────────────────────────┐
    borde / interfaz   │        cli.py (bib)          │  argparse · print · exit
                       └───────────────┬──────────────┘
                                       │ usa
                       ┌───────────────▼──────────────┐
    negocio            │    service.py (funciones)    │  add · list_items · search · borrow · return_item
                       └───────────────┬──────────────┘
                                       │ usa
                       ┌───────────────▼──────────────┐
    persistencia       │           store.py           │  load · save
                       └───────────────┬──────────────┘
                                       │ usa
                       ┌───────────────▼──────────────┐
    dominio            │  models.py (Item/Book/Movie) │  dataclasses · item_from_dict
                       └──────────────────────────────┘

Layout src/. Si pones biblioteca/ en la raíz (flat layout), al ejecutar desde ahí Python añade el directorio actual a sys.path y encuentra la carpeta aunque el paquete no esté instalado. Eso esconde fallos de empaquetado. Con src/, para que import biblioteca funcione el paquete debe estar instalado: el layout fuerza a probar la realidad.

pyproject.toml. Es el manifiesto estándar (PEP 621): metadatos, versión de Python, dependencias, dónde está el código y qué comandos expone. Sustituye al viejo setup.py. El build-system elige el backend; usamos hatchling.

Entry point. En [project.scripts] se declara bib = "biblioteca.cli:main": al instalar, el instalador genera un ejecutable que llama a esa función. No escribimos el script: lo crea a partir del manifiesto.

3 · Ejemplo mínimo

Un paquete saludo con src layout, en su forma más pequeña:

saludo/
├── pyproject.toml
└── src/saludo/
    ├── __init__.py
    └── __main__.py
# src/saludo/__init__.py — marca el paquete y expone su versión.
__version__ = "0.1.0"

# src/saludo/__main__.py — lo ejecuta `python -m saludo`.
print("¡Hola desde el paquete saludo!")

$ pip install -e .          # instala en modo editable (enlaza al código)
$ python -m saludo
¡Hola desde el paquete saludo!

Línea por línea: __init__.py marca saludo/ como paquete; __main__.py es lo que Python ejecuta con -m saludo; pip install -e . lee el manifiesto, enlaza src/saludo y deja el paquete importable desde cualquier carpeta (editable: el código no se copia).

El manifiesto, código real para copiar tal cual:

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "biblioteca"
version = "1.0.0"
description = "Biblioteca — catálogo personal de libros y películas (proyecto del curso de Python)"
readme = "README.md"
requires-python = ">=3.12"
license = { text = "UNLICENSED" }
authors = [{ name = "Academy" }]
dependencies = []                       # solo biblioteca estándar

[project.scripts]
bib = "biblioteca.cli:main"             # entry point → comando `bib`

[project.optional-dependencies]
dev = ["pytest", "mypy", "ruff"]

[tool.hatch.build.targets.wheel]
packages = ["src/biblioteca"]           # el código vive en src/

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q"
pythonpath = ["src"]                    # los tests importan sin instalar

[tool.mypy]
python_version = "3.12"
strict = true

[tool.ruff]
line-length = 88
target-version = "py312"

Y __init__.py, deliberadamente ligero: marca el paquete, reexporta los modelos y resuelve la versión (la lógica llega en la lección 2):

# src/biblioteca/__init__.py — identidad del paquete; sin lógica de negocio.
from importlib.metadata import PackageNotFoundError, version

from .models import BibliotecaError, Book, Item, Movie

try:
    __version__ = version("biblioteca")
except PackageNotFoundError:      # paquete no instalado (se ejecuta desde el repo)
    __version__ = "1.0.0"

__all__ = ["BibliotecaError", "Item", "Book", "Movie", "__version__"]
Por qué los errores viven en models.py

BibliotecaError es parte del dominio y models.py no depende de nadie: definirlo ahí evita ciclos y permite que store, service y cli hagan from .models import BibliotecaError. El __init__ se limita a reexportarlo para que from biblioteca import BibliotecaError siga siendo cómodo.

Por qué los errores viven en __init__.py

Todas las capas necesitan lanzarlos y la jerarquía es identidad del paquete. Al tenerlos aquí, store, service y cli hacen from biblioteca import BibliotecaError sin dependencias cruzadas ni ciclos.

6 · Errores habituales

1. Paquete en la raíz: el import funciona «de casualidad».

❌ Incorrecto 
biblioteca/          ← el código en la raíz
├── pyproject.toml
└── biblioteca/__init__.py

Ejecutar desde la raíz funciona aunque no esté instalado, porque el directorio actual está en sys.path. El día del pip install, un archivo no incluido pasa desapercibido.

✅ Correcto 
biblioteca/
├── pyproject.toml
└── src/biblioteca/__init__.py

2. Lógica en un if __name__ == "__main__" gigante. Parsing, ficheros y reglas mezclados en un archivo: no se puede testear ni reutilizar. La CLI debe delegar en service.

3. Import circular por un __init__.py tragón. Si __init__ importa cli y cli importa del paquete, puedes acabar con media API cargada. Solución: __init__ ligero.

4. Olvidar [build-system]. Sin él, uv build o pip install no saben con qué backend construir. pyproject.toml siempre lo necesita para ser construible.

7 · Ejercicio guiado

Crea el esqueleto de Biblioteca y comprueba que el paquete es importable como instalado.

  1. Crea y activa el entorno virtual. 
    # Linux / macOS
python3 -m venv .venv && source .venv/bin/activate
# Windows (PowerShell)
py -m venv .venv
.venv\Scripts\Activate.ps1
  2. Crea carpetas y archivos con los comandos de la sección 4.
  3. Copia el pyproject.toml y el __init__.py de la sección 4.
  4. Instala en editable. 
    $ pip install -e .
Successfully installed biblioteca-1.0.0
  5. Comprueba import y versión (funciona incluso desde otra carpeta). 
    $ python -c "import biblioteca; print(biblioteca.__version__)"
1.0.0
$ python -c "from biblioteca import BibliotecaError; print(BibliotecaError.__name__)"
BibliotecaError
Cómo saber que lo has hecho bien

Si el paso 5 imprime 1.0.0 desde tu carpeta personal, el paquete está realmente instalado. Si solo funciona desde la raíz, revisa el src layout y la instalación editable.

8 · Reto

Empaqueta el esquema como dato del paquete

Hoy schema/library.schema.json vive fuera del paquete. Muévelo a src/biblioteca/schema/library.schema.json y haz que el código lo localice aunque el paquete esté instalado en otra máquina, sin depender del directorio de trabajo.

Pista: investiga importlib.resources (files("biblioteca") / "schema" / "library.schema.json") y el ajuste include de [tool.hatch.build.targets.wheel] para que hatchling copie los .json. Al terminar, la ruta debe resolverse sin os.getcwd().

9 · Resumen

  • Un proyecto instalable se organiza en capas con dependencias hacia dentro.
  • El src layout obliga a instalar/construir de verdad.
  • pyproject.toml es el manifiesto único: metadatos, build, deps y comandos.
  • [project.scripts] declara el entry point que genera bib.
  • __init__.py ligero: versión y reexportación de los modelos, nunca negocio.
ArchivoQué hace
models.pyDefine Item, Book y Movie (datos) y BibliotecaError.
store.pyLee y escribe data/library.json en JSON.
service.pyReglas: add, list_items, search, borrow, return_item.
cli.pyInterfaz bib con argparse; delega en el servicio.
pyproject.tomlManifiesto: build, metadatos, deps y entry point bib.

10 · Preguntas frecuentes

¿Puedo usar setuptools en vez de hatchling?

Sí. [build-system] admite setuptools con [tool.setuptools.packages.find] where = ["src"]. Usamos hatchling porque necesita menos configuración con src layout; el resto del manifiesto es idéntico.

¿Necesito src/ para un script pequeño?

No. Para un archivo que no vas a publicar, un .py basta. El src layout paga su coste cuando el proyecto se instala, se testea y se comparte.

¿Por qué los errores van en models.py y no en un errors.py?

Seguimos el contrato del curso: los cinco módulos son __init__, models, store, service y cli. BibliotecaError es parte del dominio, así que vive junto a los modelos y evita un módulo extra; el __init__ se limita a reexportarlo.

¿Diferencia entre python -m biblioteca.cli y bib?

python -m biblioteca.cli ejecuta el módulo, que acaba en raise SystemExit(main()); bib es el ejecutable del entry point que llama a biblioteca.cli:main. Ambos acaban en el mismo main().

¿El data/library.json va dentro del paquete?

No: son datos del usuario, no código. Si estuviera dentro del paquete instalado se sobreescribiría al actualizar. Vive en una carpeta de trabajo, configurable con --store.
