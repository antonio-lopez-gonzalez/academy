Pattern matching (match/case)

Módulo 8 · Python moderno y asincronía ⏱ 30 minutos

1 · Introducción

Un if/elif largo que va comprobando la forma de un dato —«¿es una tupla de dos?», «¿es un dict con clave kind?», «¿la lista empieza por "add"?»— se vuelve un laberinto de índices y isinstance. Python 3.10 añadió structural pattern matching: match/case, una forma de describir la forma del dato y extraer sus partes en el mismo paso.

Aprenderás patrones literales, de captura y comodín _, desestructuración de secuencias y diccionarios, guardas con if, y —igual de importante— cuándo match es la herramienta correcta y cuándo un if/elif se lee mejor. No es un switch; es reconocimiento de estructura.

¿Por qué no es solo un switch? Porque un switch clásico compara un valor con constantes. match va mucho más allá: puede desestructurar una lista, un dict o un objeto y ligar sus partes a nombres si el patrón encaja. Eso elimina montañas de if len(x) == 2 and isinstance(x[0], str)… y hace explícita la forma que esperas.

2 · Teoría

Anatomía de un match

match evalúa un sujeto (una expresión) y prueba cada case de arriba abajo. El primer patrón que encaja ejecuta su bloque y sale. Si ninguno encaja, no pasa nada (no hay error). El orden importa muchísimo, porque algunos patrones encajan con casi todo.

match subject:                 # se evalúa el sujeto UNA vez
    case 0:                    # patrón literal
        print("cero")
    case [x, y]:               # patrón de secuencia: extrae x e y
        print(f"par: {x}, {y}")
    case {"kind": kind}:       # patrón de mapping: extrae la clave
        print(f"tipo {kind}")
    case _:                    # comodín: lo pilla todo (siempre al final)
        print("otra cosa")

Tipos de patrón

PatrónEjemploQué hace
Literalcase "book":Compara por igualdad con constantes: números, strings, True, None.
Comodíncase _:Encaja con cualquier cosa; no liga nombre. Va al final.
Capturacase name:Encaja con todo y liga el valor a name.
ORcase "book" | "movie":Encaja si encaja cualquiera de las alternativas.

La trampa nº 1 — un nombre desnudo es CAPTURA, no comparación. case book: no pregunta «¿vale "book"?»: captura cualquier valor en una variable llamada book y siempre encaja. Para comparar con una constante, usa literales (case "book":) o una referencia con punto (case Color.RED:). Un case de captura mal colocado deja muertos todos los siguientes.

Orden y alcance del case

match value: case [x]: ── sólo lista/tupla de 1 elemento │ case [x, y]: ── exactamente 2 │ case [x, *rest]: ── 1 o más (rest = lista del resto) │ case _: ── comodín: DEBE ir al final Regla: lo específico ARRIBA, lo general ABAJO. Si pones "case name:" antes, captura todo y los demás nunca corren.

Guardas (if)

Una guarda es un if al final del case que añade una condición. El patrón debe encajar y la guarda ser verdadera. La guarda no liga nombres nuevos: solo usa los ya capturados por el patrón.

match point:
    case (0, 0):
        print("origen")
    case (x, 0) if x > 0:      # liga x y exige x > 0
        print(f"eje X positivo en {x}")
    case (x, y):
        print(f"punto ({x}, {y})")

Desestructurar sin miedo a las claves ausentes

Los patrones de mapping no necesitan todas las claves: solo comprueban que las mencionadas están presentes. Esto los hace perfectos para validar datos heterogéneos (como un ítem de Biblioteca):

match item:
    case {"kind": "book", "title": title, "year": year}:
        print(f"Libro {title} ({year})")
    case {"kind": "movie", "title": title}:
        print(f"Película {title}")           # year es opcional

3 · Ejemplo mínimo

El caso que mejor muestra el valor de match: reconocer la forma de un comando representado como tupla, algo típico de una CLI.

def run_command(command):
    """Interpreta un comando como tupla y despacha según su forma."""
    match command:
        case ["add", title]:                    # 2 elementos: add + título
            return f"Añadiría: {title}"
        case ["search", query, kind]:           # 3 elementos
            return f"Buscaría '{query}' en {kind}"
        case ["list"]:                          # 1 elemento exacto
            return "Listaría todo el catálogo"
        case ["list", *filters]:                # 1 o más: resto como filtros
            return f"Listaría con filtros: {filters}"
        case _:
            return "Comando desconocido"

print(run_command(["add", "1984"]))
print(run_command(["search", "orwell", "book"]))
print(run_command(["list"]))
print(run_command(["list", "--kind", "movie"]))
print(run_command("hola"))
        
Añadiría: 1984
Buscaría 'orwell' en book
Listaría todo el catálogo
Listaría con filtros: ['--kind', 'movie']
Comando desconocido

Línea por línea: match command evalúa la tupla; cada case describe una forma concreta. ["add", title] exige dos elementos y liga el segundo a title. ["list", *filters] usa «estrella» para capturar el resto en una lista. case _ atrapa lo que no encaje: en el último ejemplo, un str no es una list, así que cae al comodín. Todo esto sin un solo len() ni un if command[0] == ....

4 · Ejemplo real

En Biblioteca, match brilla en dos sitios: interpretar el payload que llega al servicio (que puede ser un dict incompleto o de tipo inesperado) y clasificar eventos del dominio antes de persistir. Fíjate en las guardas y en la validación de forma.

biblioteca/service.py
def normalize_item(payload):
    """Valida y normaliza un ítem entrante según su ESTRUCTURA.
    Devuelve un dict listo para el store, o lanza ValueError."""
    match payload:
        # Un libro necesita título; el año es opcional.
        case {"kind": "book", "title": title, **extra}:
            year = extra.get("year")
            if not title.strip():
                raise ValueError("el título no puede estar vacío")
            return {"kind": "book", "title": title, "year": year}

        # Una película necesita título y, si viene, año entero >= 1888.
        case {"kind": "movie", "title": title, "year": year} if isinstance(year, int) and year >= 1888:
            return {"kind": "movie", "title": title, "year": year}

        # Película sin año.
        case {"kind": "movie", "title": title}:
            return {"kind": "movie", "title": title, "year": None}

        # Un ítem ya normalizado que llega de un test o del store.
        case {"id": id_, "title": title, "kind": kind} if kind in ("book", "movie"):
            return {"id": id_, "title": title, "kind": kind}

        # Cualquier otra cosa: error explícito, nunca silencio.
        case _:
            raise ValueError(f"payload inválido: {payload!r}")


# --- Comprobación ---
print(normalize_item({"kind": "book", "title": "1984", "year": 1949}))
print(normalize_item({"kind": "movie", "title": "Blade Runner", "year": 1982}))
print(normalize_item({"kind": "movie", "title": "Dune"}))
try:
    normalize_item({"kind": "book", "title": "  "})
except ValueError as exc:
    print("Error controlado:", exc)
        
{'kind': 'book', 'title': '1984', 'year': 1949}
{'kind': 'movie', 'title': 'Blade Runner', 'year': 1982}
{'kind': 'movie', 'title': 'Dune', 'year': None}
Error controlado: el título no puede estar vacío

Decisiones que vale la pena entender:

  • El patrón de mapping solo exige las claves que menciona. {"kind": "book", "title": title, **extra} liga extra con el resto de claves, así que un libro con campos de más sigue encajando.
  • La guarda valida el año solo en el caso de película: if isinstance(year, int) and year >= 1888. Si el año es una cadena, ese case no encaja y cae al siguiente.
  • El orden importa: la película con año y la película sin año se distinguen porque el caso más específico va antes.
  • case _ con raise: ante una forma desconocida, fallamos con contexto en vez de devolver None.

¿Por qué match aquí y no if/elif? Porque la lógica es «según la forma del diccionario»: qué claves existen y de qué tipo son. Con if/elif necesitarías isinstance(payload, dict) and payload.get("kind") == "book" and "title" in payload repetido cuatro veces, más los get. El match hace visible la forma esperada de un vistazo. (Nota: la validación definitiva contra el esquema sigue viviendo en store.py, Módulo 6.)

6 · Errores habituales

Creer que un nombre desnudo compara

KIND = "book"

match "movie":
    case KIND:              # ❌ NO compara con "book": captura y SIEMPRE encaja
        print("es un libro/a")   # se ejecuta aunque el sujeto sea "movie"

# ✅ Compara con un literal o con una referencia con punto
match "movie":
    case "book":
        print("libro")
    case "movie":
        print("película")

Poner la captura antes que los casos específicos

def describe(seq):
    match seq:
        case values:            # ❌ captura TODO: lo de abajo nunca corre
            return "cualquier cosa"
        case [x, y]:
            return "par"        # código inalcanzable

# ✅ Lo específico primero, la captura/comodín al final
def describe_fixed(seq):
    match seq:
        case [x, y]:
            return f"par {x},{y}"
        case [x, *rest]:
            return f"el primero {x}, resto {rest}"
        case _:
            return "otra cosa"

Patrón de mapping con claves literales esperando tipos

item = {"kind": "book", "title": "1984"}

# ❌ Se espera que valide tipos, pero solo comprueba presencia de claves
match item:
    case {"kind": "book", "title": title, "year": year}:
        print("con año")
    case {"kind": "book", "title": title}:
        print(f"libro sin año: {title}")   # <-- cae aquí (year no está)

7 · Ejercicio guiado

Objetivo: escribir una función describe_point que use match para clasificar puntos en el plano: origen, sobre los ejes, cuadrantes y entradas que no sean un par de números.

  1. Paso 1 — Escribe la función con patrones y guardas.
    points.py
    def describe_point(point):
    """Clasifica un punto (x, y) usando pattern matching."""
    match point:
        case (0, 0):
            return "origen"
        case (x, 0):
            return f"eje X en {x}"
        case (0, y):
            return f"eje Y en {y}"
        case (x, y) if x > 0 and y > 0:
            return "cuadrante I"
        case (x, y) if x < 0 < y:
            return "cuadrante II"
        case (x, y) if x < 0 and y < 0:
            return "cuadrante III"
        case (x, y):
            return "cuadrante IV"
        case _:
            return "no es un punto válido"

for p in [(0, 0), (3, 0), (0, -2), (1, 1), (-1, 1), (-2, -3), (2, -1), "hola"]:
    print(p, "->", describe_point(p))
  2. Paso 2 — Ejecuta y comprueba la salida esperada. 
    python points.py
# Salida esperada:
# (0, 0) -> origen
# (3, 0) -> eje X en 3
# (0, -2) -> eje Y en -2
# (1, 1) -> cuadrante I
# (-1, 1) -> cuadrante II
# (-2, -3) -> cuadrante III
# (2, -1) -> cuadrante IV
# hola -> no es un punto válido
  3. Paso 3 — Razona el orden. El origen va primero porque (0, 0) también encajaría en «eje X». Los ejes van antes que los cuadrantes por la misma razón. El último case (x, y) es una captura que solo alcanza lo que no cumplió ninguna guarda anterior: puntos como (2, -1). Es válido ponerlo al final, justo antes del comodín.
  4. Paso 4 — Verificación. Cambia el orden y coloca case (x, y) antes que los cuadrantes: verás que (1, 1) pasa a decir cuadrante IV. Eso demuestra que el orden decide el resultado y que la captura no pregunta nada.

Cómo comprobarlo: añade un caso que no sea par numérico, como (1, "a") o [1, 2, 3]. El comodín debe decirlo. Y usa case (x, _) si quieres ignorar explícitamente la segunda coordenada: el comodín dentro de un patrón también comunica intención.

8 · Reto

🎯 Un match para los eventos de la CLI

Modela los eventos de la CLI bib como tuplas y usa un único match para clasificarlos y validarlos: ("add", title, kind), ("add", title) (kind por defecto "book"), ("borrow", id), ("return", id), ("list",), ("list", *filters) y cualquier otra cosa como error. Además, exige con guardas que kind sea "book" o "movie" y que el título no esté vacío. Devuelve una tupla normalizada o lanza ValueError.

Pista 1: el patrón case ("add", title, kind) if kind in ("book", "movie") combina desestructuración y guarda. Pista 2: coloca el caso de 3 elementos antes que el de 2 para que ("add", "x") no capture mal. Pista 3: usa _ para la rama de error y lanza desde ahí. Bonus: extrae la clasificación a una dataclass y devuélvela.

9 · Resumen

  • match/case es reconocimiento estructural: describe la forma del dato y extrae sus partes.
  • Prueba los case de arriba abajo y ejecuta el primero que encaja; sin coincidencia no pasa nada.
  • Un nombre desnudo es captura (siempre encaja); para comparar usa literales o referencias con punto.
  • Desestructura secuencias ([a, b], [*rest]) y mappings ({"kind": k}); el mapping no exige todas las claves.
  • Las guardas (case p if cond) añaden una condición al patrón.
  • Ordena lo específico arriba y cierra con case _.
  • Si solo comparas constantes, un if/elif o un dict se leen mejor.
PatrónPara qué sirve
case 0: / case "book":Comparar con un literal.
case "book" | "movie":Alternativas (OR).
case [x, y]:Desestructurar secuencias por posición.
case {"kind": k}:Comprobar claves y ligar valores.
case Book(title=t):Comprobar tipo y extraer atributos.
case n if n > 0:Guarda: condición extra sobre lo capturado.
case _:Comodín final: cubre lo inesperado.

10 · Preguntas frecuentes

¿match es más rápido que if/elif?

No es su objetivo y la diferencia es despreciable. match existe por claridad estructural, no por rendimiento. Para una comparación sencilla de valores, un if/elif o un dict de funciones (handlers[key]()) puede ser incluso más directo. Elige match cuando la forma del dato sea lo relevante.

¿Por qué case "book" | "movie" funciona pero case kind no compara?

"book" es un patrón literal y "book" | "movie" es un patrón OR de literales: comparan por igualdad. kind es un patrón de captura: liga el sujeto a una variable y encaja siempre. La sintaxis es parecida, la semántica es opuesta. Regla mental: en un case, un nombre crea una variable, no la consulta.

¿Qué pasa si ningún case encaja y no pongo _?

Nada: el bloque match termina sin ejecutar ningún cuerpo y el programa sigue. No hay excepción ni else obligatorio. Por eso se recomienda cerrar casi siempre con case _: que o bien devuelva un valor por defecto, o bien lance un error explícito. Un match sin comodín sobre datos externos es un bug latente.

¿_ «no liga nada» o es una variable más?

El comodín _ es un patrón especial que encaja con cualquier cosa y no liga ningún nombre (no crea ni reasigna _ en el ámbito). Dentro de patrones compuestos (case (x, _)) sirve para decir explícitamente «esta parte no me interesa». Es una herramienta de intención legible tanto como de control de flujo.
