datetime y logging

Módulo 8 · Python moderno y asincronía ⏱ 30 minutos

1 · Introducción

Dos bibliotecas de la stdlib convierten un script en una herramienta operable: datetime para trabajar con fechas y horas (y no romperse con zonas horarias), y logging para dejar rastro de lo que hace el programa (niveles, formato, destino) en lugar de salpicar print().

En Biblioteca las necesitamos juntas: cuando un usuario hace bib borrow <id>, queremos registrar la fecha de préstamo y su vencimiento (30 días después) con zona horaria correcta, y emitir un log con nivel adecuado. Verás datetime/date/timedelta, zoneinfo para UTC, formato ISO 8601, y el sistema de logging (niveles, getLogger, handlers y formatters) aplicado a la CLI real.

¿Por qué logging y no print? Porque print no tiene nivel (no puedes silenciar lo informativo y conservar los errores), ni origen (qué módulo lo dijo), ni destino configurable (fichero, consola, sistema externo), ni fecha. logging te da todo eso sin cambiar el código de negocio: configuras una vez y el qué se muestra y dónde se decide fuera.

2 · Teoría

Los tres tipos de datetime

TipoRepresentaEjemplo
dateFecha sin horadate(1949, 6, 8)
timeHora sin fechatime(14, 30)
datetimeFecha y horadatetime.now()
timedeltaUna duracióntimedelta(days=30)

La aritmética es intuitiva: datetime + timedelta da datetime; datetime − datetime da timedelta. Todo objeto datetime tiene .year, .month, .day, .hour… y métodos como .date() y .strftime().

El error clásico: «naive» vs «aware»

Un datetime sin zona (naive) no sabe si es UTC, Madrid o Tokio. Uno con zona (aware) lo sabe, y comparar/mover entre zonas es correcto. El consejo profesional: guarda en UTC, muestra en la zona local. En Python 3.9+ la stdlib trae zoneinfo (base de datos IANA), así que no necesitas pytz.

from datetime import datetime, timezone
from zoneinfo import ZoneInfo

now_utc = datetime.now(timezone.utc)                 # aware, en UTC
madrid = now_utc.astimezone(ZoneInfo("Europe/Madrid"))  # mismo instante, otra zona
print(now_utc.isoformat())
print(madrid.isoformat())
        
2026-03-14T09:26:53.123456+00:00
2026-03-14T10:26:53.123456+01:00

Mismo instante, distinta hora local. Las dos líneas representan el mismo momento: una en UTC (+00:00) y otra en Madrid (+01:00). El sufijo de offset es la parte «aware». Si restas dos aware obtienes la diferencia real; si restas naive con aware, Python lanza TypeError (y hace bien: comparar peras con manzanas).

Windows y zoneinfo: Linux y macOS ya traen la base IANA del sistema, pero Windows no, así que allí necesitas el paquete de datos tzdata (py -m pip install tzdata dentro del venv). Sin él, ZoneInfo("Europe/Madrid") lanza ZoneInfoNotFoundError. Es el único caso de este curso en que una utilidad de la stdlib necesita un paquete de datos en Windows.

Formatear y parsear: ISO 8601

Para guardar fechas en JSON, el formato estándar es ISO 8601 (2026-03-14T09:26:53+00:00): ordenado, sin ambigüedad y reconocido por todos. .isoformat() lo produce y datetime.fromisoformat() lo lee (en 3.11+ acepta también el sufijo Z de UTC). Para formatos propios usa strftime/strptime.

logging: la jerarquía de niveles

Cada mensaje tiene un nivel. Un logger tiene un nivel mínimo: lo que esté por debajo se descarta. Los niveles, de menor a mayor gravedad:

NivelCuándo usarlo
DEBUGDetalle de depuración (variables, pasos).
INFOEvento normal esperado («ítem añadido»).
WARNINGAlgo raro pero no fatal (campo ausente, se usa default).
ERRORLa operación falló (no se pudo guardar).
CRITICALEl programa no puede continuar.

Cómo viaja un mensaje por logging

código LOGGER HANDLERS FORMATTER ────── ────── ──────── ───────── log.info( ──▶ getLogger( ──▶ StreamHandler ──▶ "%(asctime)s "añadido") __name__) (consola) %(levelname)s FileHandler %(name)s: (fichero) %(message)s" filtra por distribuye da forma nivel el registro al texto Un logger puede tener VARIOS handlers: el MISMO log va a consola y a fichero. La configuración (nivel, handlers, formato) se decide UNA vez, fuera del código.

Regla de oro: en cada módulo crea un logger con logging.getLogger(__name__) y emite con logger.info(...). La configuración global (nivel, handlers, formato) se hace una vez en el punto de entrada de la aplicación (el main de la CLI), no repartida por los módulos.

3 · Ejemplo mínimo

El mínimo de ambos conceptos en un solo programa: calcular el vencimiento de un préstamo (30 días) y registrar dos mensajes con niveles distintos.

import logging
from datetime import datetime, timedelta, timezone

# 1) Configuración global UNA vez: consola, nivel INFO, con formato.
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
)

# 2) Logger del módulo actual (buena práctica: __name__)
logger = logging.getLogger(__name__)

# 3) Un préstamo: ahora (UTC) + 30 días
now = datetime.now(timezone.utc)
due = now + timedelta(days=30)

logger.info("Préstamo registrado: vence %s", due.isoformat())
logger.debug("Esto NO se verá: el nivel mínimo es INFO")
logger.warning("Cuidado: ejemplo de aviso")

# 4) Guardar en formato ISO y recuperarlo
stored = due.isoformat()
recovered = datetime.fromisoformat(stored)
print("Recuperado:", recovered.isoformat())
print("¿Mismo instante?", recovered == due)
        
2026-03-14 09:26:53,123 [INFO] __main__: Préstamo registrado: vence 2026-04-13T09:26:53.123456+00:00
2026-03-14 09:26:53,123 [WARNING] __main__: Cuidado: ejemplo de aviso
Recuperado: 2026-04-13T09:26:53.123456+00:00
¿Mismo instante? True

Línea por línea: basicConfig fija nivel, formato y destino por defecto (consola); el DEBUG se descarta porque el nivel mínimo es INFO; logger.info("… %s", due.isoformat()) usa formateo perezoso (los argumentos se expanden solo si el mensaje se va a emitir, más eficiente que una f-string). timedelta(days=30) suma exactamente 30 días y fromisoformat reconstruye el instante sin pérdida.

4 · Ejemplo real

Así se registra un préstamo en Biblioteca: calculamos vencimiento con zona horaria, lo guardamos en ISO y dejamos rastro con el nivel adecuado. La configuración de logging vive en la CLI; los módulos solo piden su logger.

biblioteca/service.py
import logging
from datetime import datetime, timedelta, timezone

# El logger del módulo: NO se configura aquí (eso es cosa de la CLI).
logger = logging.getLogger(__name__)

LOAN_DAYS = 30

def borrow(item: dict) -> dict:
    """Marca un ítem como prestado y devuelve la info del préstamo."""
    if item.get("borrowed"):
        # Antes era un print; ahora un log con nivel y contexto.
        logger.warning("Intento de prestar un ítem ya prestado: %s", item["id"])
        raise ValueError(f"{item['id']} ya está prestado")

    now = datetime.now(timezone.utc)          # instante exacto, en UTC
    due = now + timedelta(days=LOAN_DAYS)     # vencimiento

    item["borrowed"] = True
    item["borrowed_at"] = now.isoformat()     # ISO 8601 para el JSON
    item["due_at"] = due.isoformat()

    logger.info("Ítem %s prestado; vence el %s",
                item["id"], due.strftime("%d/%m/%Y"))
    return item


# --- Punto de entrada (así lo haría cli.py) ---
def configure_logging(verbose=False):
    """Configuración ÚNICA de logging para la CLI Biblioteca."""
    logging.basicConfig(
        level=logging.DEBUG if verbose else logging.INFO,
        format="%(levelname)-8s %(name)s | %(message)s",
    )

if __name__ == "__main__":
    configure_logging(verbose=False)

    book = {"id": "b1", "title": "1984", "kind": "book", "borrowed": False}
    print("Antes:", book["borrowed"])
    updated = borrow(book)
    print("Después:", updated["borrowed"], "vence:", updated["due_at"])

    # Segundo intento: debe avisar y fallar sin romper el formato de logs
    try:
        borrow(updated)
    except ValueError as exc:
        print("Error esperado:", exc)
        
Antes: False
INFO     biblioteca.service | Ítem b1 prestado; vence el 13/04/2026
Después: True vence: 2026-04-13T09:26:53.123456+00:00
WARNING  biblioteca.service | Intento de prestar un ítem ya prestado: b1
Error esperado: b1 ya está prestado

Decisiones que importan aquí:

  • timezone.utc al crear el instante: guardamos en UTC y mostramos en formato local con strftime. Así el almacén JSON es consistente aunque cambie el huso del equipo.
  • Dos formatos con propósitos distintos: isoformat() para persistir (lo lee la máquina), strftime("%d/%m/%Y") para el humano en el log.
  • Niveles con criterio: un préstamo normal es INFO; un intento sobre un ítem ya prestado es WARNING (no fatal, pero anómalo).
  • El logger no se configura en service.py: solo getLogger(__name__). Quien decide el nivel y el destino es configure_logging en la CLI. Si algún día quieres volcar a fichero, cambias un sitio.

Añadir un fichero de log sin tocar el servicio:

handler = logging.FileHandler("biblioteca.log", encoding="utf-8")
handler.setFormatter(logging.Formatter("%(levelname)s %(message)s"))
logging.getLogger().addHandler(handler)   # ahora TODO log INFO+ va al fichero

Ese es el poder de la separación: el código emite; la configuración decide dónde acaba.

5 · Buenas prácticas

HazEvitaPor qué
logging.getLogger(__name__) en cada módulo print() para mensajes de operación Los logs tienen nivel, origen y destino configurable; print no se puede silenciar ni redirigir sin tocar el código.
Configura logging una vez en el main basicConfig() repartido por varios módulos La configuración es global; llamarla desde cualquier sitio produce handlers duplicados y resultados impredecibles.
Formateo perezoso: logger.info("x=%s", x) logger.info(f"x={x}") siempre Con %s el texto solo se construye si el mensaje se emite; con f-string se construye aunque el nivel lo descarte.
Guarda fechas en UTC aware con ISO 8601 Guardar datetime.now() naive o timestamps crudos Sin zona, dos equipos de husos distintos interpretan la misma fecha de forma diferente; ISO con offset elimina la ambigüedad.

No logees datos sensibles (contraseñas, tokens) ni en DEBUG. Y no uses logging dentro de una excepción esperada como sustituto de controlar el flujo: los logs informan, no deciden. La lógica sigue en try/except.

6 · Errores habituales

Comparar naive con aware

from datetime import datetime, timezone

naive = datetime(2026, 1, 1, 12, 0)          # sin zona
aware = datetime(2026, 1, 1, 12, 0, tzinfo=timezone.utc)

# ❌ Mezclar naive y aware revienta
# naive - aware   -> TypeError: can't subtract offset-naive and offset-aware datetimes

# ✅ Hazlo aware (asume UTC si el dato es UTC)
naive_utc = naive.replace(tzinfo=timezone.utc)
print((aware - naive_utc).total_seconds())   # 0.0

Configurar logging varias veces o sin global

import logging

# ❌ basicConfig llamado en varios módulos: handlers duplicados,
#    el mismo mensaje se imprime dos veces.
def a():
    logging.basicConfig(level=logging.INFO)
    logging.info("desde a")

def b():
    logging.basicConfig(level=logging.INFO)   # no hace nada tras el primero
    logging.info("desde b")                    # pero puede duplicar en otros casos

# ✅ Configura UNA vez en el punto de entrada y usa getLogger en los módulos
def configure_logging():
    logging.basicConfig(level=logging.INFO,
                        format="%(levelname)s %(name)s: %(message)s")

logger = logging.getLogger(__name__)            # en cada módulo

7 · Ejercicio guiado

Objetivo: calcular la fecha de vencimiento de un préstamo y formatearla de tres maneras, comprobando que la aritmética de fechas y el logging funcionan como esperas.

  1. Paso 1 — Escribe el programa.
    loan_dates.py
    import logging
from datetime import datetime, timedelta, timezone
from zoneinfo import ZoneInfo

logging.basicConfig(level=logging.INFO,
                    format="%(levelname)s: %(message)s")
logger = logging.getLogger("biblioteca.loans")

# Fecha fija para que la salida sea reproducible
borrowed = datetime(2026, 1, 31, 10, 0, tzinfo=timezone.utc)
due = borrowed + timedelta(days=30)          # 31 ene + 30 días

print("Prestado (UTC):  ", borrowed.isoformat())
print("Vence (UTC):     ", due.isoformat())
print("Vence (Madrid):  ", due.astimezone(ZoneInfo("Europe/Madrid")).isoformat())
print("Legible:         ", due.strftime("%d/%m/%Y"))

days_left = (due - borrowed).days
logger.info("Días de préstamo: %d", days_left)
  2. Paso 2 — Ejecuta y comprueba. 
    python loan_dates.py
# Salida esperada:
# INFO: Días de préstamo: 30
# Prestado (UTC):   2026-01-31T10:00:00+00:00
# Vence (UTC):      2026-03-02T10:00:00+00:00
# Vence (Madrid):   2026-03-02T11:00:00+01:00
# Legible:          02/03/2026
  3. Paso 3 — Entiende el resultado. 31 de enero + 30 días cae en el 2 de marzo (2026 no es bisiesto: febrero tiene 28 días; 31 ene → 28 feb es +28, +2 = 2 mar). timedelta hace la aritmética de calendario, no una suma de «31 + 30». La versión Madrid muestra 11:00+01:00: el mismo instante, una hora más por el huso, y el offset cambia en verano (+02:00).
  4. Paso 4 — Verificación. Imprime (due - borrowed).days (30) y comprueba que due > borrowed es True. Luego cambia timedelta(days=30) por timedelta(weeks=4): obtendrás un vencimiento distinto (28 días), lo que demuestra que timedelta es una duración, no una fecha.

9 · Resumen

  • datetime combina fecha y hora; timedelta es una duración. Sumar/restar es aritmética de calendario.
  • Distingue naive (sin zona) de aware (con zona). Guarda en UTC, muestra en local.
  • Usa zoneinfo.ZoneInfo (stdlib) para husos; evita depender de pytz en código nuevo.
  • Persiste fechas en ISO 8601 (isoformat/fromisoformat); usa strptime solo para formatos propios.
  • logging aporta niveles, origen, formato y destino; print no.
  • getLogger(__name__) en cada módulo; configura una sola vez en el punto de entrada.
  • Un logger puede tener varios handlers (consola + fichero); el código no cambia.

10 · Preguntas frecuentes

¿Por qué guardar en UTC y no en la hora local del usuario?

Porque UTC es un único instante sin ambigüedad, mientras que «hora local» depende de dónde y cuándo. Un mismo evento guardado como 2026-03-02T10:00 sin zona es interpretable de muchas formas; guardado como 2026-03-02T10:00+00:00 no. Cuando necesites mostrar la hora del usuario, conviertes con astimezone(ZoneInfo(...)) en el borde de la aplicación (CLI/UI).

¿Cuándo uso logging y cuándo print?

print es para salida del programa para el usuario (el resultado de bib list en la terminal). logging es para diagnóstico del programa para quien lo opera (qué pasó, con qué nivel). Una CLI puede usar ambos: imprime la tabla de libros y registra INFO «listados 3 ítems» y ERROR si el almacén está corrupto.

¿logging es oficial? ¿Dónde está la documentación?

Sí, datetime, zoneinfo y logging son parte de la biblioteca estándar y su documentación está en docs.python.org (páginas «datetime», «zoneinfo» y «logging» / «logging.config»). logging permite configurar por código o por diccionario/fichero (logging.config.dictConfig), útil cuando quieres cambiar el comportamiento sin recompilar nada.
