Concurrencia: GIL, threading y asyncio

Módulo 8 · Python moderno y asincronía ⏱ 40 minutos

1 · Introducción

Hasta ahora el código corría de principio a fin, una instrucción tras otra. Pero hay tareas que esperan: descargar un fichero, leer de disco, consultar una API. Mientras esperas, la CPU está ociosa. La concurrencia consiste en aprovechar esa espera para hacer otras cosas —y en Python tiene una particularidad que confunde a todo el mundo: el GIL.

En esta lección desmontamos el mito «los hilos en Python no sirven para nada», entendemos qué es el GIL y qué implica de verdad, y aprendemos los tres modelos de concurrencia de la stdlib: threading (I/O-bound), multiprocessing (CPU-bound) y asyncio (muchas I/O concurrentes en un solo hilo). Terminaremos importando datos a Biblioteca en paralelo con asyncio.gather.

¿Por qué existe el GIL? El Global Interpreter Lock es un candado que garantiza que un solo hilo ejecute bytecode de Python a la vez. Existe para simplificar la gestión de memoria de CPython (recuento de referencias) y de las estructuras internas: sin él, cada operación tendría que ser thread-safe. El precio es que los hilos no aceleran el código que calcula… pero sí el que espera, porque el GIL se libera durante las operaciones de I/O.

2 · Teoría

Concurrencia no es paralelismo

TérminoSignificaEjemplo
ConcurrenciaVarias tareas progresan entrelazadas (puede ser en un solo núcleo).Un camarero atiende 6 mesas alternando.
ParalelismoVarias tareas se ejecutan a la vez en varios núcleos.Seis camareros, una mesa cada uno.

La clave para elegir modelo es la naturaleza de la tarea: ¿pasa el tiempo esperando (I/O-bound) o calculando (CPU-bound)?

El GIL, en un diagrama

Dos hilos, un GIL (un solo hilo ejecuta bytecode a la vez): Hilo A [====GIL====]..............[====GIL====]..... Hilo B .............[====GIL====]..............[====GIL====] ↑ Cuando A hace I/O (leer socket/fichero), LIBERA el GIL y B puede ejecutar. Si A solo CALCULA, no lo suelta hasta su «turno» (sys.setswitchinterval). Consecuencia: - CPU-bound (math pura): los hilos NO paralelizan; el GIL serializa. -> multiprocessing - I/O-bound (red/disco): los hilos SÍ solapan la espera. -> threading / asyncio

Matiz importante: existe una propuesta (free-threaded / PEP 703) que en versiones recientes de Python permite compilar sin GIL como modo experimental. En el Python estándar que usas en este curso (3.12/3.13, build por defecto) el GIL sigue presente. Aunque desapareciera, el criterio I/O vs CPU seguiría guiando la elección de modelo.

Modelo 1 — threading: hilos para I/O

Los hilos comparten memoria (cuidado con las condiciones de carrera) y son ideales cuando la tarea espera. Para lanzar varios y esperar a todos, la forma cómoda es concurrent.futures.ThreadPoolExecutor, que gestiona el pool y devuelve futures:

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(descargar, url) for url in urls]
    resultados = [f.result() for f in futures]   # espera y recoge

El GIL se libera al hacer la llamada de red, así que los cuatro hilos se solapan. Con CPU pura, en cambio, se turnarían sin ganar tiempo.

Modelo 2 — multiprocessing: procesos para CPU

Cada proceso tiene su propio intérprete y su propio GIL, así que sí hay paralelismo real entre núcleos. El precio: no comparten memoria (los datos se serializan al pasar de uno a otro, con pickle) y arrancar un proceso es caro. Se usa para cálculo intensivo: comprimir imágenes, procesar millones de filas, hashing pesado.

from concurrent.futures import ProcessPoolExecutor

if __name__ == "__main__":        # OBLIGATORIO en Windows/macOS
    with ProcessPoolExecutor() as pool:
        resultados = list(pool.map(calcular_pesado, datos))

En Windows y macOS (spawn): el punto de entrada debe estar protegido por if __name__ == "__main__":. Sin esa guarda, al crear cada proceso se reimporta el módulo y se vuelven a lanzar procesos en cascada (bucle infinito de procesos). Es el error clásico de multiprocessing en Windows.

Modelo 3 — asyncio: un hilo, muchas esperas

Con asyncio una sola hebra de ejecución maneja miles de operaciones de I/O. La idea: cuando una tarea va a esperar, cede el control cooperativamente al event loop, que ejecuta otra. No hay hilos ni carreras de datos entre tareas, pero debe haber una sola tarea ejecutando a la vez y todo el camino debe ser cooperativo (async/await).

asyncio.run(main()) -> crea el EVENT LOOP y ejecuta main() Event Loop (un solo hilo): ├─ tareaA: fetch(url1) ──await──▶ cede .......... listo → sigue ├─ tareaB: fetch(url2) ──await──▶ cede ..... listo → sigue └─ tareaC: fetch(url3) ──await──▶ cede ........... listo → sigue Mientras una espera, el loop avanza las demás. Un solo hilo puede tener decenas de miles de conexiones abiertas. Regla: si haces algo BLOQUEANTE (time.sleep, requests, open pesado) dentro de una corrutina, BLOQUEAS TODO el loop.
ConceptoQué es
async defDeclara una corrutina (no se ejecuta al llamarla; devuelve un objeto awaitable).
await exprCede el control hasta que expr esté listo. Solo dentro de async def.
asyncio.run(coro)Punto de entrada: crea el loop, ejecuta la corrutina y lo cierra.
asyncio.gather(*coros)Ejecuta varias corrutinas concurrentemente y espera a todas.
asyncio.create_task(coro)Agenda una corrutina para que corra «por detrás».
asyncio.to_thread(func)Ejecuta en un hilo una función bloqueante sin congelar el loop.

La alternativa moderna a gather es asyncio.TaskGroup (Python 3.11+), un context manager que cancela las tareas hermanas si una falla y agrupa sus errores. Es más seguro que gather para código nuevo; en esta lección usamos gather por ser el más difundido y el que verás por todas partes.

¿Cuál uso? La decisión en una tabla

EscenarioModeloPor qué
Descargar 50 URLsasyncio o threadingI/O-bound; espera solapada. asyncio escala a muchísimas más.
Operaciones de disco locales sencillasthreadingI/O-bound; simple y suficiente. No fuerces async si no hay beneficio.
Comprimir 10 000 imágenesmultiprocessingCPU-bound; necesita paralelismo real entre núcleos.
Servidor con miles de conexionesasyncioUn hilo escala mejor que miles de hilos.
Llamar a una librería bloqueante desde asyncasyncio.to_threadEvita congelar el event loop con código que no es async.

Por qué asyncio no es «mejor»: no acelera el cálculo (sigue siendo un hilo), obliga a que todo el camino sea async y hace más difícil depurar una pila de corrutinas. Se elige cuando hay muchas operaciones de I/O y quieres evitar la sobrecarga de miles de hilos. Para dos descargas, threading es más simple; para pura CPU, multiprocessing es la única que paraleliza.

3 · Ejemplo mínimo

El asyncio más pequeño posible: dos corrutinas que «esperan» (simulando I/O de red con asyncio.sleep) y se ejecutan concurrentemente con gather. Fíjate en que el tiempo total es ~1 s, no ~2 s.

import asyncio
import time

async def fetch(name, seconds):
    """Simula una descarga que tarda 'seconds' (I/O, NO CPU)."""
    print(f"  inicio {name}")
    await asyncio.sleep(seconds)        # cede el control al loop mientras espera
    print(f"  fin    {name}")
    return f"{name}:ok"

async def main():
    start = time.perf_counter()
    # gather lanza las dos corrutinas A LA VEZ y espera a ambas
    results = await asyncio.gather(
        fetch("A", 1),
        fetch("B", 1),
    )
    elapsed = time.perf_counter() - start
    print("resultados:", results)
    print(f"tiempo total: {elapsed:.1f}s  (no 2.0s)")

asyncio.run(main())                     # punto de entrada
        
  inicio A
  inicio B
  fin    A
  fin    B
resultados: ['A:ok', 'B:ok']
tiempo total: 1.0s  (no 2.0s)

Línea por línea: async def define corrutinas que no se ejecutan al llamarlas; asyncio.gather las agenda en el loop, que las va avanzando mientras esperan; await asyncio.sleep libera el control (a diferencia de time.sleep, que bloquearía todo). asyncio.run(main()) arranca el loop. Ambas «descargas» se solapan: el total es el máximo, no la suma.

4 · Ejemplo real

Biblioteca importa ítems desde varias fuentes (un fichero local lento, un servicio remoto…). Hacerlo secuencialmente tardaría la suma de todos; con asyncio.gather tarda el máximo. La descarga real usa urllib (bloqueante), así que la aislamos con asyncio.to_thread para no congelar el loop.

biblioteca/importer.py
import asyncio
import json
import time
from urllib.request import urlopen

# --- Fuentes ficticias (en producción serían rutas/servicios reales) ---
# Cada función "descarga" es BLOQUEANTE: por eso va en un hilo aparte.
def _fetch_local(path: str) -> list:
    time.sleep(0.5)                       # simula lectura lenta de disco
    return [{"id": "b1", "title": "1984", "kind": "book"}]

def _fetch_remote(url: str) -> list:
    time.sleep(0.5)                       # simula latencia de red
    return [{"id": "m1", "title": "Dune", "kind": "movie"}]

async def fetch_async(func, arg):
    """Ejecuta una función BLOQUEANTE en un hilo, sin bloquear el loop."""
    return await asyncio.to_thread(func, arg)

async def import_catalog() -> list:
    """Importa de varias fuentes EN PARALELO y combina los resultados."""
    start = time.perf_counter()

    # gather: las dos "descargas" progresan a la vez
    local, remote = await asyncio.gather(
        fetch_async(_fetch_local, "data/local.json"),
        fetch_async(_fetch_remote, "https://example.com/items"),
    )

    elapsed = time.perf_counter() - start
    print(f"Importadas {len(local) + len(remote)} fuentes en {elapsed:.1f}s")
    return local + remote

def main():
    items = asyncio.run(import_catalog())     # punto de entrada
    for item in items:
        print(f"  {item['id']}: {item['title']} ({item['kind']})")

if __name__ == "__main__":
    main()
        
Importadas 2 fuentes en 0.5s
  b1: 1984 (book)
  m1: Dune (movie)

Decisiones que vale la pena entender:

  • asyncio.to_thread para código bloqueante: urlopen y las lecturas de disco no son async. Ejecutarlas directamente dentro de una corrutina bloquearía el loop entero (ninguna otra tarea avanzaría). to_thread las mueve a un hilo y devuelve un awaitable.
  • gather sobre las dos fuentes: el tiempo total es ~0.5 s (el máximo), no ~1.0 s (la suma). Ese es el ahorro real de la concurrencia en I/O.
  • asyncio.run solo en el punto de entrada: se llama una vez, en main. Nunca dentro de código que ya corre en un loop.
  • La lógica de combinación es síncrona: una vez tenemos los datos, unir dos listas no necesita async. La concurrencia se aplica solo a la espera, no a todo el programa.

La versión threading (más simple si no quieres async): con ThreadPoolExecutor(max_workers=2) envías _fetch_local y _fetch_remote a dos hilos y recoges con f.result(); también tarda ~0.5 s. Para dos operaciones, threading es más directo; asyncio brilla con decenas o miles de operaciones simultáneas.

5 · Buenas prácticas

HazEvitaPor qué
Elige por naturaleza: I/O → threading/asyncio; CPU → multiprocessing Usar hilos para cálculo puro esperando que vaya más rápido El GIL serializa el bytecode: con CPU-bound, los hilos no ganan nada y añaden complejidad.
Usa asyncio.to_thread para código bloqueante dentro de async Llamar time.sleep/requests dentro de una corrutina Una llamada bloqueante congela el event loop entero: ninguna otra tarea avanza.
asyncio.run una sola vez, en el main Llamar asyncio.run dentro de código que ya corre en un loop Lanza RuntimeError: asyncio.run() cannot be called from a running event loop y además duplica loops.
Protege el entrypoint con if __name__ == "__main__": en multiprocessing Crear procesos a nivel de módulo en Windows/macOS Con el arranque «spawn», el módulo se reimporta en cada proceso: sin la guarda, se lanzan procesos en cascada.

Async contagia. Una función async solo puede llamar con await a otras async; si necesitas una síncrona pesada, la envuelves con to_thread. Por eso migrar a asyncio afecta a toda la cadena de llamadas: decide pronto y con criterio, no «por moda».

6 · Errores habituales

Creer que los hilos aceleran el cálculo (CPU-bound)

import threading, time

def cpu_task():
    total = 0
    for i in range(20_000_000):       # solo CPU, sin I/O
        total += i
    return total

# ❌ Dos hilos NO terminan en la mitad de tiempo: el GIL los serializa.
start = time.perf_counter()
threads = [threading.Thread(target=cpu_task) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(f"hilos: {time.perf_counter() - start:.2f}s")   # ~ similar a secuencial

# ✅ Para CPU, usa procesos: paralelismo real entre núcleos.
# from concurrent.futures import ProcessPoolExecutor
# if __name__ == "__main__":

#         pool.submit(cpu_task).result()

7 · Ejercicio guiado

Objetivo: medir de verdad la diferencia entre secuencial y concurrente en una tarea I/O-bound, y comprobar que el tiempo total baja del orden de la suma al orden del máximo.

  1. Paso 1 — Escribe el comparador.
    concurrency_bench.py
    import asyncio
import time

async def fetch(name, seconds):
    """Simula una fuente que tarda 'seconds' en responder."""
    await asyncio.sleep(seconds)
    return f"{name}:ok"

async def sequential(sources):
    """Versión 1: una detrás de otra (await dentro del bucle)."""
    start = time.perf_counter()
    results = []
    for name, secs in sources:
        results.append(await fetch(name, secs))   # espera cada una entera
    return results, time.perf_counter() - start

async def concurrent(sources):
    """Versión 2: todas a la vez con gather."""
    start = time.perf_counter()
    results = await asyncio.gather(*(fetch(name, secs) for name, secs in sources))
    return list(results), time.perf_counter() - start

async def main():
    sources = [("A", 0.4), ("B", 0.4), ("C", 0.4)]

    _, t_seq = await sequential(sources)
    _, t_con = await concurrent(sources)

    print(f"secuencial: {t_seq:.1f}s")   # ~1.2s (suma)
    print(f"concurrente: {t_con:.1f}s")  # ~0.4s (máximo)

asyncio.run(main())
  2. Paso 2 — Ejecuta y comprueba. 
    python concurrency_bench.py
# Salida esperada:
# secuencial: 1.2s
# concurrente: 0.4s
  3. Paso 3 — Interpreta. La versión secuencial espera cada fetch completo antes de empezar el siguiente: 0.4 + 0.4 + 0.4 = 1.2 s. La concurrente lanza las tres y espera a que terminen a la vez: 0.4 s, el máximo. Ese es exactamente el patrón que hace eficiente importar de varias fuentes o llamar a varias APIs.
  4. Paso 4 — Verificación. Cambia los tiempos a ("A", 0.1), ("B", 0.5), ("C", 0.2). El secuencial dará ~0.8 s y el concurrente ~0.5 s (el mayor). Si el concurrente te diera la suma, sería señal de que algo está bloqueando el loop en serie (por ejemplo, un time.sleep en lugar de asyncio.sleep).

Cómo comprobarlo: si al pasar a gather el tiempo no baja, sospecha de bloqueo. Sustituye await asyncio.sleep por time.sleep (sin await) y verás que el «concurrente» vuelve a tardar la suma: la corrutina bloquea el loop y gather no puede solapar nada.

8 · Reto

🎯 Importador con límite de concurrencia y errores

Amplía el importador de Biblioteca para descargar 20 fuentes con asyncio, pero con dos requisitos: (1) como máximo 5 descargas simultáneas a la vez, y (2) si una fuente falla, las demás deben completarse igualmente y devolver la lista de las que fallaron. Además, mide el tiempo total y demuestra que con límite 5 es más lento que sin límite (si las fuentes tardan lo mismo).

Pista 1: asyncio.Semaphore es el patrón clásico para limitar concurrencia: async with sem: dentro de cada tarea. Pista 2: asyncio.gather(..., return_exceptions=True) no aborta por la primera excepción: las devuelve en la lista. Pista 3: asyncio.TaskGroup (3.11+) es la alternativa moderna, pero cancela las hermanas al fallar una: para «seguir pese a fallos», gather(return_exceptions=True) es más directo. Bonus: limita también el número de hilos con ThreadPoolExecutor(max_workers=5) si usas to_thread.

9 · Resumen

  • La concurrencia solapa esperas; el paralelismo ejecuta en varios núcleos. No son lo mismo.
  • El GIL deja que un solo hilo ejecute bytecode a la vez; se libera durante la I/O.
  • I/O-bound → threading o asyncio; CPU-bound → multiprocessing.
  • threading comparte memoria (ojo con las carreras); usa ThreadPoolExecutor.
  • multiprocessing paraleliza de verdad, pero serializa datos y exige if __name__ == "__main__":.
  • asyncio: un hilo + event loop; async/await, gather, asyncio.run en el borde, to_thread para bloquear sin congelar.
  • No bloquees el loop: asyncio.sleep sí, time.sleep no.

10 · Preguntas frecuentes

¿El GIL significa que los hilos son inútiles en Python?

No. Es un mito muy extendido. Los hilos son muy útiles para I/O, porque el GIL se libera mientras se espera una respuesta de red o de disco, y otro hilo aprovecha ese hueco. Lo que el GIL impide es paralelizar cálculo puro con hilos; para eso están los procesos. La frase correcta es «los hilos no aceleran el código CPU-bound», no «no sirven».

¿asyncio usa varios hilos?

Por defecto, no: asyncio corre en un solo hilo con un event loop cooperativo. La concurrencia viene de que las tareas ceden el control al esperar, no de tener varios hilos. Si necesitas ejecutar algo bloqueante, asyncio.to_thread sí usa un hilo del pool interno, pero el loop sigue siendo uno. Eso es lo que le permite manejar miles de conexiones con poca memoria.

¿Cuándo uso threading y cuándo asyncio para I/O?

Regla práctica: si la tarea es puntual y el código ya es síncrono, threading (o ThreadPoolExecutor) es más simple. Si necesitas miles de operaciones concurrentes, o tu stack ya es async (por ejemplo, un framework web async), usa asyncio. También importa el ecosistema: si dependes de librerías síncronas, async te obligará a envolverlas con to_thread constantemente.

¿Por qué await solo funciona dentro de async def?

Porque await necesita un event loop en marcha para suspender y reanudar la corrutina. Fuera de una función async no hay loop, y Python lo prohíbe con un SyntaxError. El puente entre el mundo síncrono y el async es asyncio.run(...), que se llama una sola vez desde el punto de entrada. Si partís de una librería síncrona y quieres «llamar a async», ese asyncio.run es el borde.

¿Y los free-threaded builds de Python 3.13?

Son una modalidad experimental que compila CPython sin GIL. Prometen hilos con paralelismo real, pero tienen costes (rendimiento en un solo hilo, compatibilidad de extensiones) y aún no son el modo por defecto. Para este curso, asume GIL en el intérprete estándar; si en el futuro se generaliza, el criterio de elegir modelo según I/O vs CPU seguirá siendo válido. Consulta la documentación oficial si necesitas detalles actualizados.
