Ámbito LEGB y closures

Módulo 2 · Control de flujo y funciones ⏱ 35 minutos

1 · Introducción

Cuando usas un nombre dentro de una función, Python tiene que decidir a qué objeto te refieres. Esa decisión la resuelve el ámbito (scope): el conjunto de nombres visibles en un punto del programa. Python sigue un orden fijo y memorizable: LEGB (Local → Enclosing → Global → Built-in).

Y cuando una función interna «recuerda» variables de la función que la contiene, incluso después de que esta termine, tienes un closure. Esta lección explica por qué existen, cómo se relacionan con nonlocal y global, y por qué son la maquinaria oculta de los decoradores del Módulo 8.

¿Por qué existe esta lección? Porque casi todos los UnboundLocalError y los bugs de «estado que se recuerda» vienen de no entender el ámbito. Saber que asignar dentro de una función vuelve local ese nombre —aunque exista fuera— te ahorra confusión y te da una herramienta potentísima: funciones que llevan su propio estado sin necesidad de una clase.

2 · Teoría

Asignar dentro de una función la vuelve local

Aquí está la clave que sorprende a todo el mundo: si en algún punto de una función asignas a un nombre, Python lo considera local en toda la función, aunque exista uno con el mismo nombre fuera. Leer un nombre global sin asignarlo sí funciona; asignarlo crea una local nueva.

count = 10

def read():
    print(count)          # leer un global: OK, LEGB llega hasta Global

def broken():
    print(count)          # ❌ UnboundLocalError
    count = 0             # esta asignación declara 'count' local en toda la función

read()                     # 10

def good():
    count = 0             # local explícita: no toca el global
    count += 1
    return count

print(good())              # 1
print(count)               # 10  (el global no cambió)

El error UnboundLocalError casi nunca es un fallo de LEGB: es la consecuencia de asignar y leer el mismo nombre dentro de la misma función. Si quieres modificar el de fuera, necesitas global o nonlocal… o, mejor, evitarlo.

global: declarar que el nombre vive en el módulo

global nombre dentro de una función hace que las asignaciones afecten a la variable del módulo. Funciona, pero se considera mala práctica: crea estado compartido difícil de seguir y de testear. Casi siempre es mejor pasar el valor como argumento y devolver el nuevo.

total = 0

def add_to_total(amount):
    global total          # permiso explícito para escribir el global
    total += amount

add_to_total(5)
add_to_total(7)
print(total)              # 12

# Alternativa limpia: sin estado global
def add(a, b):
    return a + b
print(add(5, 7))          # 12

nonlocal: escribir en la función externa

nonlocal es a la variable enclosing lo que global es a la del módulo. Solo tiene sentido en funciones anidadas: permite que la función interna modifique una variable de la externa. Sin él, count += 1 dentro de la interna crearía una local y fallaría.

def counter():
    count = 0                  # variable de la función externa (enclosing)
    def increment():
        nonlocal count         # escribe en 'count' de counter, no en una local
        count += 1
        return count
    return increment           # devolvemos la función interna

tick = counter()
print(tick())                  # 1
print(tick())                  # 2
print(tick())                  # 3

# Salida esperada:
# 1
# 2
# 3

Closures: funciones que recuerdan su entorno

Cuando devuelves una función interna y esta usa variables de la externa, Python conserva esas variables aunque counter() ya haya terminado. Ese paquete «función + entorno capturado» es un closure. Es la forma de tener estado privado sin escribir una clase.

def counter():                 tick = counter()
    count = 0                  # count vive en una "celda" que la
    def increment():           # función interna captura
        nonlocal count         #
        count += 1             tick()  -> 1   (count = 1)
        return count           tick()  -> 2   (count = 2)
    return increment           # cada tick() recuerda el mismo count

¿Por qué existen los closures? Porque permiten configurar una función en el momento de crearla. Un generador de identificadores con prefijo, un validador con un límite, un decorador que envuelve: todos son funciones «preconfiguradas» que recuerdan datos de su creación.

3 · Ejemplo mínimo

El ejemplo más pequeño que muestra la resolución LEGB: el mismo nombre en tres niveles.

message = "global"          # ámbito Global

def outer():
    message = "enclosing"   # ámbito Enclosing
    def inner():
        message = "local"   # ámbito Local
        print(message)      # encuentra el LOCAL primero
    inner()
    print(message)          # aquí ya no hay local: encuentra el ENCLOSING

outer()
print(message)              # en el módulo: encuentra el GLOBAL

# Salida esperada:
# local
# enclosing
# global

Línea por línea:

  1. Hay tres variables llamadas message, una por ámbito. No se pisan: cada función tiene su propio espacio.
  2. Dentro de inner(), LEGB encuentra primero la local.
  3. De vuelta en outer(), la local de inner ya no es visible; se usa la de outer.
  4. En el módulo, solo existe la global.

4 · Ejemplo real

En Biblioteca necesitamos generar identificadores como book-001, book-002… sin una variable global que todos compartan (dos catálogos distintos deben tener contadores independientes). Un closure lo resuelve: cada generador lleva su propio contador.

def make_id_generator(prefix):
    """Devuelve una función que genera ids incrementales con ese prefijo."""
    counter = 0                          # estado privado de ESTE generador
    def next_id():
        nonlocal counter                 # incrementa el contador capturado
        counter += 1
        return f"{prefix}-{counter:03d}" # formato 001, 002...
    return next_id                       # el closure recuerda prefix y counter

books = make_id_generator("book")
movies = make_id_generator("movie")

print(books())    # book-001
print(books())    # book-002
print(movies())   # movie-001  (contador independiente)
print(books())    # book-003

# Salida esperada:
# book-001
# book-002
# movie-001
# book-003

Decisiones de diseño:

  • counter vive dentro de make_id_generator; nadie fuera puede verlo ni tocarlo. Es encapsulación sin clase.
  • Cada llamada a make_id_generator crea un counter nuevo, así que books y movies no comparten estado. Un global counter habría mezclado ambos.
  • nonlocal es imprescindible: sin él, counter += 1 declararía una local y daría UnboundLocalError.
  • La función devuelta (next_id) es el closure: captura prefix y counter de su creador.

6 · Errores habituales

UnboundLocalError por asignar y leer el mismo nombre

total = 0

# ❌ Asignar a 'total' la vuelve local en TODA la función, luego leerla falla
def increase():
    # total += 1        # UnboundLocalError: 'total' no está ligada
    ...
# increase()

# ✅ Pasa, modifica y devuelve; sin estado global
def increase(value):
    return value + 1

total = increase(total)
print(total)             # 1

Captura tardía en un bucle (late binding)

# ❌ Las lambdas capturan la variable 'i', no su valor de cada vuelta.
# Cuando se llaman, el bucle ya terminó y 'i' vale 2.
funcs = []
for i in range(3):
    funcs.append(lambda: i)
print([f() for f in funcs])     # [2, 2, 2]  <- ¡sorpresa!

# ✅ Fija el valor actual con un parámetro por defecto (se evalúa en cada vuelta)
funcs = []
for i in range(3):
    funcs.append(lambda i=i: i)  # el default captura el valor de AHORA
print([f() for f in funcs])     # [0, 1, 2]

7 · Ejercicio guiado

Objetivo: construir un contador con umbral usando nonlocal, y comprobar que dos contadores no comparten estado.

  1. Paso 1: escribe la fábrica de contadores. 
    def make_counter(limit):
    """Devuelve una función que cuenta hasta 'limit' y luego se detiene."""
    count = 0
    def tick():
        nonlocal count
        if count < limit:
            count += 1
        return count
    return tick
  2. Paso 2: crea dos contadores con límites distintos y hazlos avanzar. 
    low = make_counter(2)
high = make_counter(5)

print(low())     # 1
print(low())     # 2
print(low())     # 2   (ya llegó al límite)
print(high())    # 1   (contador independiente)
  3. Paso 3 (verificación): la salida esperada es: 
    # 1
# 2
# 2
# 1

    Si low y high compartieran el contador, las cifras no cuadrarían. Que sean independientes demuestra que el estado vive en el closure, no en un global.

  4. Paso 4: guarda como counters.py y ejecútalo con python3 counters.py (o py counters.py en Windows). Inspecciona el closure con print(low.__closure__): verás las celdas que capturó.

8 · Reto

🎯 Un memoizador con closure

Escribe memoize(func) que devuelva una versión de func que recuerde los resultados ya calculados: si la llama otra vez con los mismos argumentos, devuelve el resultado guardado sin recalcular. Pruébalo con una función que imprime «calculando…» para ver cuándo se ejecuta de verdad.

Pista: dentro de memoize crea un diccionario cache = {} y una función wrapper(*args). Consulta cache antes de llamar a func; guárdalo después. Como cache es mutable, no necesitas nonlocal: mutar un objeto capturado sí se refleja; solo necesitarías nonlocal si reasignaras la variable cache.

9 · Resumen

  • Python resuelve nombres en orden LEGB: Local → Enclosing → Global → Built-in.
  • Asignar a un nombre dentro de una función lo hace local en toda la función (origen del UnboundLocalError).
  • global permite escribir el módulo; se considera mala práctica salvo casos justificados.
  • nonlocal permite escribir la variable de la función externa (closures).
  • Un closure es una función que conserva su entorno de creación; da estado privado sin clase.
  • Los closures capturan por referencia: cuidado con el late binding en bucles.

10 · Preguntas frecuentes

¿Por qué me da UnboundLocalError si la variable existe fuera?

Porque en algún punto asignas a ese nombre dentro de la función. Python decide el ámbito de cada nombre al compilar la función: si ve una asignación, lo marca como local para todas las líneas. La solución no es global a ciegas, sino pasar el valor y devolver el nuevo, o usar global/nonlocal si de verdad quieres modificarlo.

¿Cuándo uso global y cuándo nonlocal?

global apunta a la variable del módulo; nonlocal, a la de la función externa que envuelve a la actual. Si estás dentro de una función anidada y quieres modificar algo de la función de fuera, es nonlocal. Si quieres modificar el nivel del archivo, global. En la práctica: evita global; usa nonlocal en closures.

¿Por qué el cierre tardío devuelve [2, 2, 2]?

Porque las funciones del bucle capturan la variable i, no su valor en ese instante. Cuando por fin se llaman, el bucle ya acabó y i vale 2. Fijar el valor con lambda i=i: i (default evaluado en cada vuelta) o con functools.partial resuelve el problema.

¿Los closures pueden modificar listas sin nonlocal?

Sí. La distinción es mutar vs rebindear. cache[k] = v o items.append(x) mutan el objeto capturado y se ven fuera sin declarar nada. count += 1 o cache = {} reasignan el nombre, y eso requiere nonlocal. Es la misma diferencia entre mutabilidad y asignación que viste en el Módulo 1.
