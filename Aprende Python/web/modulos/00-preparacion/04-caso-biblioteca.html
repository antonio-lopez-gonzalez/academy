1 · Introducción

Aprender sintaxis suelta no convierte a nadie en ingeniero. Por eso este curso no enseña conceptos aislados: los aplica, módulo a módulo, a un único proyecto real. Se llama Biblioteca y es un catálogo personal de libros y películas con el que añadirás, listarás, buscarás y prestarás ítems desde la terminal.

La gracia es que verás el mismo sistema evolucionar: en el módulo 0 es un script de juguete; en el módulo 9 será un paquete Python instalable con tests, tipos y una CLI llamada bib. Cada herramienta que aprendas (colecciones, funciones, clases, ficheros, pytest, uv…) tendrá un sitio concreto en Biblioteca. Esta lección es el mapa del viaje: qué construiremos, con qué arquitectura y por qué.

¿Por qué existe esta lección? Porque un hilo conductor da sentido a todo lo demás. Cuando en el módulo 6 escribas persistencia JSON, no será un ejercicio abstracto: será el almacén de Biblioteca. Saber dónde vas evita que cada lección parezca inconexa.

2 · Teoría

Qué es Biblioteca, en una frase

Un catálogo de libros y películas que vive en un fichero JSON y se gestiona desde una CLI de línea de comandos llamada bib, construida con la biblioteca estándar de Python y acompañada de una suite de tests. Nada de frameworks: solo Python idiomático, como querrías en una herramienta interna real.

Las tres piezas del sistema

  1. El modelo: qué es un «ítem» (un libro o una película) y qué campos tiene.
  2. El almacén: dónde y cómo se guardan los ítems (un JSON validado por un esquema).
  3. La interfaz: cómo el usuario manda comandos (bib add, bib list…) y ve resultados.
  ┌─────────────────────────────────────────────────────────────┐
  │                         USUARIO                              │
  │        $ bib add "1984" --kind book --year 1949             │
  └───────────────────────────┬─────────────────────────────────┘

3 · Ejemplo mínimo

El germen de todo el curso, en 6 líneas: el catálogo como lista de diccionarios y un bucle que lo imprime. Es feo comparado con lo que vendrá, y precisamente por eso sirve de punto de partida.

# catalog_v0.py — el catálogo antes de tener clases, ficheros o CLI.
CATALOG = [                                    # una lista de diccionarios
    {"id": "b-001", "title": "1984",         "kind": "book",  "borrowed": False},
    {"id": "b-002", "title": "Dune",         "kind": "book",  "borrowed": True },
    {"id": "m-001", "title": "Blade Runner", "kind": "movie", "borrowed": False},
]

for item in CATALOG:                            # iteramos directo sobre la lista
    status = "prestado" if item["borrowed"] else "disponible"   # ternario
    print(f"{item['id']}  {item['title']:<14} [{item['kind']}]  {status}")

Salida esperada (ejecuta con python3 catalog_v0.py):

b-001  1984           [book]  disponible
b-002  Dune           [book]  prestado
m-001  Blade Runner   [movie] disponible

Línea por línea:

  1. CATALOG = [ ... ]: una lista de diccionarios. Cada diccionario es un ítem con las claves del contrato.
  2. {"id": ...}: los diccionarios usan cadenas como claves y cualquier valor como contenido.
  3. for item in CATALOG: iteramos los elementos, no los índices. Idiomático en Python.
  4. "prestado" if ... else "disponible": expresión condicional, útil para valores pequeños.
  5. {item['title']:<14}: alineación a la izquierda en 14 caracteres para que las columnas queden rectas. Este tipo de formato es parte de las f-strings.

4 · Ejemplo real

Así se verá Biblioteca al final del curso. Este NO es código que puedas ejecutar aún —llegaremos aquí paso a paso—, es la meta. Tenerla delante desde el principio le da sentido a cada módulo.

La experiencia desde la terminal

# Añadir un libro (el ID se genera solo: "b-003")
$ bib add "El nombre del viento" --kind book --year 2007
Añadido: b-003 · El nombre del viento (2007)

# Listar solo películas
$ bib list --kind movie
m-001  Blade Runner (1982)  disponible

# Buscar por texto
$ bib search "orwell"
b-001  1984 (1949)  disponible

# Prestar y devolver (cambian el estado persistido)
$ bib borrow b-001
b-001 ahora está prestado.
$ bib return b-001
b-001 devuelto y disponible.

Cómo se organizará el proyecto

  proyectos/biblioteca/
  ├── pyproject.toml          ← metadatos + entry point "bib"      (M4, M9)
  ├── src/
  │   └── biblioteca/
  │       ├── __init__.py     ← expone la API pública             (M4)
  │       ├── models.py       ← Item / Book / Movie (dataclass)   (M5)
  │       ├── store.py        ← lee/escribe library.json          (M6)
  │       ├── service.py      ← add/list/search/borrow/return     (M2–M6)
  │       └── cli.py          ← argparse, subcomandos             (M4)
  ├── tests/
  │   ├── test_models.py      ├── test_store.py    └── test_cli.py (M7)
  ├── data/library.json       ← el almacén                        (M6)
  └── schema/library.schema.json ← validación del almacén         (M6)

Por qué esta arquitectura

  • Separar cli de service y store: la lógica no depende de la terminal. Podrás testear add o borrow sin teclear comandos; y mañana podrías poner una web delante sin tocar el núcleo.
  • data/library.json fuera del código: los datos son del usuario, no del programa. El código se actualiza; los datos se conservan.
  • Errores propios (BibliotecaError): mejor que lanzar Exception a pelo, para poder capturar exactamente lo que esperas (módulo 6).
  • La stdlib y nada más: argparse, json, pathlib, dataclasses… todo viene con Python. Las herramientas externas (pytest, ruff, mypy, uv) llegan cuando aportan valor, no antes.

Los author/director aparecerán en el módulo 5, cuando el modelo madure con clases. Hasta entonces el contrato base (id, title, kind, year, borrowed) es suficiente y mantiene las lecciones enfocadas.

6 · Errores habituales

Sobre-ingeniería antes de tiempo

# ❌ Empezar con base de datos, ORM, inyección de dependencias y 12 capas
#    para un catálogo de 3 ítems. Es abrumador y no enseña Python.

# ✅ Empezar simple (lista de dicts) y crecer cuando duela:
CATALOG = [{"id": "b-001", "title": "1984", "kind": "book", "borrowed": False}]
#    El dolor de mantener esto a mano justificará las dataclasses en M5.

Estado global que nadie controla

# ❌ Variables sueltas que se modifican desde cualquier sitio
counter = 0
CATALOG = []

def add_item(title):
    global counter, CATALOG      # mutación global difícil de testear
    counter += 1
    CATALOG.append({"id": f"b-{counter:03d}", "title": title})

# ✅ El estado vive en estructuras pasadas explícitamente a las funciones
def add_item(items: list[dict], title: str) -> dict:
    new_id = f"b-{len(items) + 1:03d}"          # derivado, no global
    item = {"id": new_id, "title": title, "kind": "book", "borrowed": False}
    items.append(item)                           # el llamador decide dónde guardar
    return item

8 · Reto

🎯 Diseña el contrato antes de programarlo

Sin escribir código todavía, redacta dos cosas en un archivo NOTAS.md dentro de proyectos/biblioteca/: (1) la lista definitiva de campos de un ítem con su tipo, y (2) qué debería hacer cada comando add, list, search, borrow y return ante entradas válidas y ante errores (por ejemplo, prestar un ítem ya prestado o buscar un ID inexistente). Para cada caso decidirás qué salida o error es razonable.

Pista: piensa primero en el modelo (¿qué distingue un libro de una película?), después en los casos límite (año desconocido, título duplicado, préstamo repetido). Ese hábito —diseñar el contrato antes de teclear— es justo lo que separará tu módulo 9 del típico script improvisado. Guarda NOTAS.md: lo revisarás en el módulo 4.

9 · Resumen

  • Biblioteca es el hilo conductor: catálogo de libros y películas con CLI bib y almacén data/library.json.
  • Arquitectura en capas: cli → service → store, con models compartido. Testeable y mantenible.
  • El contrato base de un ítem: id, title, kind, year, borrowed; author/director llegan con la madurez del modelo (M5).
  • Comandos: bib add, list, search, borrow, return.
  • El proyecto evoluciona sin tirar código: script → paquete → dataclasses → JSON → tests → empaquetado.
  • Se prioriza la biblioteca estándar; las herramientas externas llegan cuando aportan.

10 · Preguntas frecuentes

¿Por qué un proyecto y no ejercicios sueltos?

Porque en un ejercicio suelto todo es descartable y nada encaja. Un proyecto que crece obliga a tomar decisiones reales: cómo modelar, cómo separar capas, cómo testear, cómo empaquetar. Ver el mismo sistema evolucionar es la forma más rápida de interiorizar por qué existe cada herramienta.

¿Puedo usar mi propio proyecto en lugar de Biblioteca?

Puedes, pero te perderás la continuidad: cada lección referencia ítems concretos (1984, Dune, Blade Runner) y comandos concretos (bib add). Si cambias el dominio, mantén al menos la arquitectura y el contrato; la pedagogía es la misma.

¿Por qué separar cli.py de service.py desde tan pronto?

Porque es lo que hace testeable el proyecto. Si la lógica de «prestar un ítem» vive dentro del parser de argumentos, solo puedes probarla lanzando la CLI completa. Separada en service.py, la pruebas con una simple llamada a función. Es una decisión de arquitectura que pagará dividendos en el módulo 7.
