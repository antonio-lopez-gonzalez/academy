uv: el gestor moderno

Módulo 4 · Módulos, paquetes y entornos ⏱ 30 minutos

1 · Introducción

venv + pip son la vía estándar y funcionan perfectamente. Pero arrastran dos limitaciones: son lentos en proyectos con muchas dependencias y no tienen un lockfile que garantice reproducibilidad exacta. Ahí entra uv, un gestor escrito en Rust por Astral (los creadores de ruff) que unifica en una sola herramienta: creación de entornos, instalación de paquetes, resolución de dependencias, lockfile y gestión de versiones de Python.

En esta lección verás qué es, por qué es tan rápido, los comandos esenciales (uv venv, uv add, uv run, uv sync) y, sobre todo, una comparación honesta con venv/pip: cuándo merece la pena uv y cuándo no.

¿Por qué existe esta lección? Porque uv se ha vuelto el estándar de facto en muchos equipos y aparece en la documentación de proyectos modernos. Debes saber usarlo y saber qué resuelve de verdad, sin adoptarlo por moda. Aprenderás ambos caminos; el criterio lo pones tú.

2 · Teoría

Qué es uv exactamente

uv es un ejecutable único que reemplaza funcionalmente a varias herramientas del ecosistema Python:

Herramienta clásicaEquivalente en uvQué aporta
venvuv venvCrea entornos en milisegundos
pipuv add / uv pipInstala y resuelve dependencias mucho más rápido
pip-toolsuv lockLockfile reproducible de serie
pyenvuv pythonInstala y fija versiones de Python
pipxuv tool / uvxEjecuta herramientas aisladas

¿Por qué es tan rápido? Porque está escrito en Rust, usa un cache global de paquetes (no descarga dos veces el mismo wheel) y resuelve las dependencias con un algoritmo concurrente. Eso no lo hace «mágico»: instala exactamente los mismos paquetes de PyPI, solo que de forma más eficiente. La ganancia real se nota en proyectos grandes y en CI.

El lockfile: la clave de la reproducibilidad

Cuando haces uv add, uv escribe dos cosas:

  • pyproject.toml: lo que declaras, con rangos de versión (igual que en la lección 02).
  • uv.lock: lo que uv resolvió, con versiones y hashes exactos de todas las dependencias (directas y transitivas).
pyproject.toml                 uv.lock
(rangos, intención)   ---->    (versiones y hashes exactos)
     "requests>=2.31"              requests 2.32.3
                                   urllib3  2.2.3
                                   idna     3.10
                                   ...
        ↑ versión el lockfile (uv lock)
        ↑ sincroniza el entorno con el lockfile (uv sync)

La diferencia con pip freeze > requirements.txt es que el lockfile es multiplataforma: resuelve también para otros sistemas operativos y versiones de Python, así que el mismo uv.lock sirve en tu portátil y en el servidor. Es la misma idea que package-lock.json de npm o poetry.lock.

Documentación oficial: consulta docs.astral.sh/uv para la lista de comandos y opciones vigentes. La herramienta evoluciona rápido y es la fuente que debes mirar antes de confiar en un flag concreto.

Instalar uv (multiplataforma)

Linux / macOS:

# Instalador oficial (deja uv en ~/.local/bin)
curl -LsSf https://astral.sh/uv/install.sh | sh

Windows (PowerShell):

# Instalador oficial para Windows
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

Alternativa común (si ya tienes pip):

python -m pip install uv
uv --version

uv es un binario: no vive dentro de un venv. Se instala una vez en el sistema y gestiona los entornos de cada proyecto.

Activar a mano (opcional): si prefieres activar el entorno que crea uv, los scripts son idénticos a venv: source .venv/bin/activate en Linux/macOS y .venv\Scripts\Activate.ps1 en Windows. Con uv run no lo necesitas.

Los comandos esenciales

ComandoQué hace
uv initCrea la estructura base: pyproject.toml, .python-version, README.md…
uv venvCrea el entorno virtual .venv/
uv add requestsAñade una dependencia a pyproject.toml, actualiza uv.lock e instala
uv add --dev pytestAñade una dependencia de desarrollo a un grupo aparte
uv remove requestsElimina una dependencia y actualiza entorno y lockfile
uv syncSincroniza el entorno con el uv.lock (crea el venv si falta)
uv lockRecalcula el lockfile sin tocar el entorno
uv run python script.pyEjecuta un comando dentro del entorno del proyecto (lo sincroniza antes)
uv run bib listEjecuta el comando de consola del paquete instalado
uv treeMuestra el árbol de dependencias resuelto
uv python install 3.12Descarga e instala una versión de Python gestionada por uv
uv python pin 3.12Fija la versión del proyecto en .python-version
uv pip install requestsInterfaz compatible con pip (sin pyproject ni lockfile)

uv run es tu amigo: sincroniza el entorno según el lockfile y ejecuta el comando, todo en uno. Si el entorno no existe, lo crea. Eso elimina el paso «¿habré activado el venv?», el error más habitual de la lección anterior.

venv/pip vs uv: comparación honesta

¿Cuándo usar cada uno? Usa venv + pip cuando trabajes en un entorno restrictivo (sin permiso para instalar binarios), cuando el proyecto ya lo usa, o cuando quieras ceñirte solo a la biblioteca estándar. Usa uv en proyectos nuevos con varias dependencias, monorepos, CI, o cuando quieras reproducibilidad con lockfile y no te importe instalar un binario. No hay «ganador absoluto»: hay contexto. Este curso enseña los dos precisamente para que elijas con criterio.

3 · Ejemplo mínimo

Un proyecto nuevo con uv, de cero a ejecutar algo, en tres comandos.

# 1) Crea el proyecto (genera pyproject.toml, README y .python-version)
uv init demo-uv
cd demo-uv

# 2) Añade una dependencia: actualiza pyproject.toml, uv.lock e instala en .venv
uv add requests

# 3) Ejecuta código dentro del entorno, sin activar nada
uv run python -c "import requests; print('requests', requests.__version__)"

# Salida esperada (la versión puede variar)
requests 2.32.3

Qué ocurrió por detrás, comando a comando:

  1. uv init: crea pyproject.toml mínimo, un .python-version con la versión de Python a usar y un README.md.
  2. uv add requests: resuelve la última versión compatible, la escribe en pyproject.toml, congela todo en uv.lock y lo instala en .venv.
  3. uv run …: comprueba que el entorno coincide con el lockfile y ejecuta el comando. No necesitaste activate.

4 · Ejemplo real

Montamos el proyecto Biblioteca con uv. Fíjate en que no hay ni un activate: todo pasa por uv run.

# 1) Inicializa el proyecto (si aún no tiene pyproject.toml)
uv init --package biblioteca     # el flag --package crea el layout con src/
cd biblioteca

# 2) Fija la versión de Python del proyecto y deja que uv la instale si falta
uv python install 3.12
uv python pin 3.12               # escribe la versión en .python-version

# 3) Dependencia de ejecución (el paquete la necesita para funcionar)
uv add platformdirs

# 4) Dependencias de desarrollo (pytest, ruff, mypy)
uv add --dev pytest ruff mypy

# 5) Sincroniza el entorno con el lockfile (crea .venv y los enlaces del paquete)
uv sync

# 6) Ejecuta la CLI del paquete tal como la usará el usuario final
uv run bib list
uv run bib add "1984" --kind book --year 1949

# Salida esperada (la CLI real se detalla en la lección 05)
(catálogo vacío)
añadido: it_9f3a1c7b  1984 (1949)  [disponible]

# 7) Árbol de dependencias resuelto (útil para auditar qué entra)
uv tree

# 8) En otra máquina o en CI, basta con esto para reproducir el entorno exacto:
uv sync --frozen                 # usa uv.lock sin recalcularlo

# Árbol esperado (fragmento)
biblioteca v0.1.0
└── platformdirs v4.3.6

Decisiones y su porqué:

  • uv init --package: genera la estructura con src/ y un [project.scripts] vacío, alineada con la lección 02.
  • uv python pin 3.12: deja la versión en .python-version, de modo que todo el equipo use la misma sin discusión.
  • uv add --dev: separa las herramientas de desarrollo, igual que hacíamos con [project.optional-dependencies], pero de forma automática.
  • uv sync --frozen: en CI no quieres que uv «reconsidere» versiones; quieres exactamente las del lockfile. Si algo no cuadra, falla en vez de instalar algo distinto.

¿Y si abres el proyecto un día y el entorno está roto? No lo arregles a mano: borra .venv y ejecuta uv sync. Reconstruye todo desde uv.lock en segundos. Esa es la ventaja del lockfile.

6 · Errores habituales

Mezclar uv add con pip install a mano

# ❌ Instalas con pip algo que NO queda en pyproject ni en uv.lock
uv add requests          # bien, gestionado por uv
python -m pip install flask   # ¡el entorno y el lockfile se desincronizan!

# ✅ Si el proyecto lo gestiona uv, usa uv para todo
uv add flask             # actualiza pyproject.toml, uv.lock y el entorno a la vez

El «por qué» es que uv no sabe qué has instalado por fuera; al siguiente uv sync eliminará lo que no esté en el lockfile y tu flask desaparecerá sin avisar. Un proyecto, un gestor.

Editar uv.lock a mano

# ❌ No toques el lockfile: tiene hashes y estructura interna
# uv.lock
[[package]]
name = "requests"
version = "2.32.3"
# ... (uv lo regenera; editarlo lo invalida)

# ✅ Cambia la intención en pyproject y deja que uv resuelva
uv add "requests>=2.32"
uv lock

Olvidar que uv no está en todas partes

# ❌ Asumir que el servidor de producción tiene uv instalado
# (fallará si el entorno no permite descargar binarios)
uv sync

# ✅ Ten una vía de respaldo con la stdlib documentada en el README
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

No entender qué hace uv run con el argumento

# ❌ Pasar la ruta de un fichero que no existe en el entorno
uv run script.py            # funciona si está en el cwd, pero…

# ✅ Recuerda que uv run ejecuta comandos; el comando por defecto es "python"
uv run python script.py
uv run bib list             # el comando de consola instalado

7 · Ejercicio guiado

Objetivo: crear un proyecto con uv, añadir y quitar una dependencia, y comprobar que el lockfile la refleja.

  1. Paso 1: crea el proyecto e inspecciona lo que genera: 
    uv init demo-uv --python 3.12
cd demo-uv
ls -a                # verás pyproject.toml, .python-version, README.md…
  2. Paso 2: añade una dependencia y observa el lockfile: 
    uv add attrs
ls uv.lock            # el lockfile ya existe
grep -n "name = \"attrs\"" uv.lock   # Windows: Select-String "attrs" uv.lock
  3. Paso 3: añade una dependencia de desarrollo: 
    uv add --dev pytest
uv tree               # pytest aparece en el grupo de desarrollo
  4. Paso 4: ejecuta código dentro del entorno, sin activar: 
    uv run python -c "import attrs; print('attrs', attrs.__version__)"

    # Salida esperada (versión orientativa)
attrs 24.2.0
  5. Paso 5: elimina una dependencia y comprueba que desaparece del lockfile: 
    uv remove attrs
grep -c "name = \"attrs\"" uv.lock   # debe dar 0

    # Salida esperada
0
  6. Paso 6 (verificación): borra el entorno y reconstruye desde el lockfile: 
    rm -rf .venv            # Windows: Remove-Item -Recurse -Force .venv
uv sync
uv run python -c "import pytest; print('pytest', pytest.__version__)"

    # Salida esperada (versión orientativa)
pytest 8.3.3

8 · Reto

🎯 Reproducir el mismo proyecto con uv y con venv/pip

Toma un proyecto pequeño con tres dependencias (por ejemplo requests, rich y, como desarrollo, pytest). Créalo una vez con uv (usando uv.lock) y otra vez en una carpeta aparte con venv + pip (usando un requirements.txt). Compara: ¿qué ficheros genera cada enfoque? ¿Qué pasa si borras el entorno en cada caso y reproduces? ¿Cuál de los dos lockfiles es más portable y por qué?

Pista: en el proyecto uv, borra .venv y ejecuta uv sync; en el de pip, borra .venv y ejecuta python -m pip install -r requirements.txt. Fíjate en que el uv.lock incluye hashes y resolución para varias plataformas, mientras el requirements.txt congela solo lo que quedó en tu máquina. Escribe tus conclusiones honestas: ninguno es «mejor» sin contexto.

9 · Resumen

  • uv es un gestor todo-en-uno (entornos, paquetes, versiones de Python y lockfile), escrito en Rust.
  • uv init crea el proyecto; uv add añade dependencias y actualiza uv.lock; uv run ejecuta sin activar nada.
  • uv sync reconstruye el entorno desde el lockfile; en CI usa uv sync --frozen.
  • uv python install / uv python pin gestionan la versión de Python del proyecto.
  • El lockfile (uv.lock) garantiza reproducibilidad multiplataforma; se versiona en Git.
  • No mezcles uv add con pip install manual: desincronizas el entorno.
  • venv + pip siguen siendo la vía estándar y la mejor en entornos restringidos.

uv add X / uv add --dev XAñade dependencia de ejecución / desarrollo

10 · Preguntas frecuentes

¿uv reemplaza a pip del todo?

Funcionalmente sí: uv add, uv pip install y uv sync cubren lo que hacías con pip. Pero pip sigue siendo la herramienta estándar que encontrarás en cualquier entorno, así que conviene conocer ambas. uv incluso ofrece una interfaz compatible (uv pip) para transiciones graduales.

¿Necesito activar el entorno con uv?

No es necesario si usas uv run: él localiza el entorno del proyecto y ejecuta dentro. Puedes activar .venv como siempre si lo prefieres, pero uv run evita depender de que el PATH esté bien configurado.

¿Qué diferencia hay entre uv.lock y requirements.txt?

uv.lock es un lockfile estructurado, con hashes y resolución para varias plataformas y versiones de Python; lo genera uv automáticamente. Un requirements.txt congelado con pip freeze captura solo lo instalado en tu máquina, sin hashes ni resolución multiplataforma. Para reproducibilidad estricta, el lockfile es más completo.

¿Puedo usar uv si el proyecto ya usa venv/pip?

Sí. Puedes añadir uv poco a poco: usa uv pip install sobre el entorno existente o deja que uv gestione el proyecto con uv add/uv sync. Eso sí, no mezcles ambos flujos sobre el mismo entorno a la vez, o el lockfile y lo instalado se desincronizarán.

¿Por qué uv puede instalar versiones de Python que no tengo?

Porque incluye un gestor de versiones: descarga builds de Python gestionadas por el equipo de Astral y las pone a disposición del proyecto. Eso unifica la versión entre desarrolladores y CI sin depender de pyenv o de lo que traiga el sistema operativo.
