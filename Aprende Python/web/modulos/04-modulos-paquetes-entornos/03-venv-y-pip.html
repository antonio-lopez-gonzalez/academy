Entornos virtuales: venv y pip

Módulo 4 · Módulos, paquetes y entornos ⏱ 35 minutos

1 · Introducción

Si instalas paquetes con pip install sin más, van a parar a los site-packages globales de tu instalación de Python: la carpeta compartida por todos tus proyectos. Eso crea un problema tan común que tiene nombre: la dependency hell. El proyecto A necesita requests==2.28 y el B necesita requests==2.32; en un entorno global no pueden convivir.

La solución es el entorno virtual (venv): una carpeta con su propio Python y sus propios paquetes, aislada del resto. En esta lección aprenderás a crearlo, activarlo y desactivarlo en Linux/macOS y Windows, a instalar y congelar dependencias con pip, y las buenas prácticas que evitarán que tu proyecto se vuelva irrecuperable.

¿Por qué existe esta lección? Porque el 90 % de los errores de «a mí no me funciona» en Python vienen de tener el entorno equivocado o paquetes mal instalados. Dominar venv es la frontera entre usar Python como juguete y usarlo como profesional.

2 · Teoría

El problema: un único espacio global

Cada instalación de Python tiene una carpeta de paquetes (site-packages) y un único ejecutable. Cuando haces pip install, se escribe ahí. Con varios proyectos, las versiones chocan:

SIN ENTORNO VIRTUAL                  CON ENTORNOS VIRTUALES
Python 3.12 (una instalación)        Python 3.12 (el intérprete base)
└── site-packages/                   ├── venv-proyecto-A/
    ├── requests 2.28  <-- A quiere  │   └── site-packages/  (requests 2.28)
    └── requests 2.32  <-- B quiere  └── venv-proyecto-B/
                                             └── site-packages/  (requests 2.32)
   (imposible: solo cabe una)                        (cada uno, lo suyo)

Un entorno virtual es una carpeta con: un enlace (o copia) al intérprete de Python, un site-packages propio, y scripts de activación. Los paquetes que instales dentro no afectan a los demás proyectos.

Analogía: el entorno global es una nevera compartida por todo el edificio: si dos vecinos compran leche de marcas distintas, una acaba fuera. Un entorno virtual es tu propia nevera: cada piso guarda exactamente lo que necesita, sin peleas.

Crear un entorno: python -m venv .venv

venv es un módulo de la biblioteca estándar: no hay que instalar nada. Se ejecuta como módulo con -m (recuerda la lección de ejecución) para garantizar que usas el Python correcto:

# Crea un entorno virtual en la carpeta .venv (nombre por convención)
# Linux / macOS
python3 -m venv .venv

# Windows: el launcher "py" elige el intérprete registrado
py -m venv .venv

El nombre .venv es solo una convención muy extendida (y añadida al .gitignore), pero puede ser cualquiera. Dentro se crea una estructura así:

.venv/                          <- el entorno (NUNCA se versiona)
├── bin/            (Linux/macOS)   o   Scripts/   (Windows)
│   ├── python          <- ejecutable del entorno
│   ├── pip
│   └── activate        <- script de activación (bash)
├── lib/python3.12/site-packages/   <- AQUÍ caen los paquetes instalados
└── pyvenv.cfg                     <- marca el intérprete base del entorno

¿Por qué python -m venv y no venv a secas? Porque -m garantiza que usas el módulo venv del intérprete que acabas de invocar. Si tuvieras varios Pythons instalados, así no hay ambigüedad. Es el mismo motivo por el que conviene python -m pip en lugar de pip.

Activar y desactivar: los comandos cambian por sistema

«Activar» significa poner el python y el pip del entorno por delante en el PATH. Así, cuando escribes python, usas el del entorno. La sintaxis depende de tu shell:

Linux / macOS (bash o zsh):

source .venv/bin/activate      # activa
# el prompt cambia a: (.venv) usuario@maquina:~/proyecto$
deactivate                     # desactiva

Windows — PowerShell:

.venv\Scripts\Activate.ps1     # activa
# si da error de permisos, ejecuta una vez:
# Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
deactivate                     # desactiva

Windows — Símbolo del sistema (cmd):

.venv\Scripts\activate.bat     # activa
deactivate                     # desactiva

Truco que evita activar nada: invoca el Python del entorno directamente. Funciona igual en los tres sistemas y es ideal para scripts y CI:

# Linux/macOS
.venv/bin/python -m pip install requests
# Windows
.venv\Scripts\python -m pip install requests

Al ejecutar así, el entorno se detecta por la ubicación del propio ejecutable, sin tocar el PATH.

pip: instalar, listar y congelar

pip es el instalador de paquetes. La regla de oro: siempre dentro del entorno activado y siempre vía python -m pip para no equivocarte de instalación.

ComandoQué hace
python -m pip install requestsInstala el paquete (y sus dependencias) en el entorno actual
python -m pip install "requests>=2.31,<3"Instala respetando un rango de versiones
python -m pip install -e .Instala tu proyecto en modo editable (desarrollo)
python -m pip listLista los paquetes instalados en el entorno
python -m pip show requestsMuestra versión, autor y de quién depende un paquete
python -m pip uninstall requestsDesinstala un paquete
python -m pip freezeImprime todas las versiones exactas instaladas
python -m pip install -r requirements.txtInstala a partir de un fichero congelado
python -m pip install --upgrade pipActualiza el propio pip dentro del entorno
 
# Congela las dependencias exactas y guarda el resultado en un fichero
python -m pip freeze > requirements.txt

# Contenido típico de requirements.txt (versiones exactas, con ==)
certifi==2024.8.30
charset-normalizer==3.4.0
idna==3.10
requests==2.32.3
urllib3==2.2.3

¿Por qué == exacto al congelar? Porque freeze captura un entorno tal como funciona hoy. Sirve para reproducirlo en otra máquina o en producción. No sirve como declaración del paquete: para eso está dependencies en pyproject.toml con rangos flexibles. Deja de congelar si lo que quieres es permitir actualizaciones compatibles.

3 · Ejemplo mínimo

Crear un entorno, comprobar que está aislado y verlo con pip list. El ejemplo usa bash; cambia la activación en Windows con el callout de arriba.

# 1) Crear el entorno en la carpeta actual
python3 -m venv .venv                # Windows: py -m venv .venv

# 2) Activar el entorno
source .venv/bin/activate            # Windows PowerShell: .venv\Scripts\Activate.ps1

# 3) ¿Qué Python estamos usando ahora? Debe apuntar al del entorno (.venv)
which python                         # Windows: where python

# 4) Ver los paquetes instalados (un entorno nuevo trae muy pocos)
python -m pip list

# Salida esperada (rutas y versiones pueden variar)
/home/ada/proyecto/.venv/bin/python

Package    Version
---------- -------
pip        24.2

Fíjate en dos cosas: el which python apunta a dentro de .venv, y la lista de paquetes está casi vacía (solo pip). Ese aislamiento es el objetivo. Al escribir deactivate, el python vuelve a ser el global.

4 · Ejemplo real

Montamos el entorno del proyecto Biblioteca desde cero, instalamos el paquete en editable con sus dependencias de desarrollo y congelamos. Este es el flujo que repetirás cada vez que clones un proyecto.

# 1) Crear y activar el entorno (Linux/macOS)
python3 -m venv .venv
source .venv/bin/activate

# 2) Actualizar pip dentro del entorno (recomendado al empezar)
python -m pip install --upgrade pip

# 3) Instalar el proyecto en editable con el extra "dev"
#    Las comillas evitan que la shell interprete los corchetes.
python -m pip install -e ".[dev]"

# 4) Verificar la instalación: pytest queda disponible y el comando bib también
python -m pytest --version
bib --help

# Salida esperada (versiones orientativas)
pytest 8.3.3
usage: bib [-h] {add,list,search,borrow,return} ...

# 5) Congelar el entorno de trabajo para poder reproducirlo
python -m pip freeze > requirements.txt

# 6) En otra máquina (o más tarde), recrear todo desde el fichero:
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

Nota sobre -e ".[dev]": el punto es «este proyecto»; los corchetes indican el extra declarado en [project.optional-dependencies] del pyproject.toml (lección anterior). Sin el extra, solo instalarías las dependencias de ejecución.

El «por qué» del orden: primero aíslas (venv), luego actualizas pip, después instalas y por último congelas. Si congelas antes de instalar, el fichero sale incompleto. Si instalar antes de activar el entorno, ensucias el Python global.

6 · Errores habituales

Instalar sin activar el entorno

# ❌ No activaste: esto instala en el Python GLOBAL del sistema
pip install requests
# Salida (a veces): "Defaulting to user installation..."

# ✅ Activa y confirma con which/where antes de instalar
source .venv/bin/activate       # Windows: .venv\Scripts\Activate.ps1
which python                    # Windows: where python  -> debe ser .venv
python -m pip install requests

Usar sudo pip install

# ❌ Nunca instales paquetes en el Python del sistema con sudo
sudo pip install requests

Puede sobrescribir paquetes que usa tu sistema operativo y dejarlo en un estado inconsistente. En Linux/macOS, el Python del sistema a menudo no debe tocarse. La solución es siempre un venv.

Cometer el error de creer que el venv se activa «en un comando»

# ❌ Las variables de entorno de un script no afectan a tu shell actual
.venv/bin/activate              # en Linux: se ejecuta la primera vez, pero
                                # si el PATH es relativo, se rompe al cambiar de carpeta

En bash se activa con source .venv/bin/activate (o . .venv/bin/activate); ejecutarlo con .venv/bin/activate en un script separado no cambia el shell padre. Ese es el motivo del source.

Rutas de Windows con la activación de Linux

# ❌ Esto no existe en Windows: no hay carpeta bin/ ni slash
source .venv/bin/activate       # en PowerShell da "no such file or directory"

# ✅ En PowerShell usa la ruta con barra invertida y el script .ps1
.venv\Scripts\Activate.ps1

Congelar dentro del entorno equivocado

Un pip freeze hecho con el global activo produce un requirements.txt con cientos de paquetes ajenos al proyecto. Siempre: activa, comprueba con which python/where python, y luego congela.

7 · Ejercicio guiado

Objetivo: montar de cero el entorno de un proyecto, instalar una dependencia, congelarla y reproducirla.

  1. Paso 1: crea la carpeta del proyecto y entra: 
    mkdir demo-venv && cd demo-venv
  2. Paso 2: crea y activa el entorno (elige tu sistema): 
    # Linux / macOS
python3 -m venv .venv && source .venv/bin/activate

    # Windows PowerShell
py -m venv .venv
.venv\Scripts\Activate.ps1
  3. Paso 3: confirma que el entorno está activo y actualiza pip: 
    which python            # Windows: where python  -> debe contener ".venv"
python -m pip install --upgrade pip
  4. Paso 4: instala una dependencia y compruébala: 
    python -m pip install "requests>=2.31,<3"
python -m pip show requests

    # Salida esperada (fragmento; la versión puede variar)
Name: requests
Version: 2.32.3
  5. Paso 5: congela y guarda el fichero: 
    python -m pip freeze > requirements.txt
cat requirements.txt            # Windows: type requirements.txt
  6. Paso 6 (verificación): borra el entorno, créalo de nuevo y reinstala desde el fichero. La versión de requests debe coincidir. 
    deactivate
rm -rf .venv                    # Windows: Remove-Item -Recurse -Force .venv
python3 -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip show requests     # misma versión que antes

8 · Reto

🎯 Dos entornos, dos versiones, cero conflicto

Crea un proyecto con dos entornos virtuales (.venv-a y .venv-b) en el mismo directorio. En el A instala una versión concreta de requests (por ejemplo requests==2.31.0) y en el B otra distinta (requests==2.32.3). Demuestra, sin activarlos a la vez, que cada uno ve su propia versión usando la ruta directa al ejecutable (.venv-a/bin/python -m pip show requests). Escribe en un párrafo por qué los entornos no entran en conflicto aunque compartan el mismo Python base.

Pista: no necesitas activar nada para usar cada entorno; basta con invocar su Python por ruta. Fíjate en que solo existe un intérprete global pero cada entorno tiene su propio site-packages.

9 · Resumen

  • Un entorno virtual aísla las dependencias de cada proyecto del Python global.
  • Se crea con python -m venv .venv (Windows: py -m venv .venv).
  • Se activa con source .venv/bin/activate (Linux/macOS) o .venv\Scripts\Activate.ps1 (PowerShell).
  • Se desactiva con deactivate; también puedes invocar el Python del entorno por ruta sin activarlo.
  • Instala siempre con python -m pip, nunca con sudo pip.
  • pip freeze > requirements.txt captura versiones exactas para reproducir el entorno.
  • Añade .venv/ al .gitignore: nunca se versiona.

10 · Preguntas frecuentes

¿Por qué el entorno se llama .venv y no venv?

Es una convención: el punto delante lo oculta en listados y deja claro que es una carpeta de trabajo interna, no código fuente. Muchas herramientas (editores, VSCode) detectan .venv automáticamente. El nombre no es obligatorio, pero ayuda a que todos los proyectos se vean igual.

¿Puedo activar dos entornos virtuales a la vez?

No de forma útil: activar uno reemplaza el PATH del anterior. Si necesitas herramientas de dos entornos, actívalos por separado o invoca cada Python por su ruta absoluta. Un proceso usa un solo entorno.

¿venv copia Python entero dentro de la carpeta?

No. Crea un enlace (symlink) o una copia ligera al intérprete base y una carpeta site-packages propia. Por eso los entornos son pequeños y por eso no son portables entre sistemas operativos ni entre versiones de Python.

¿Diferencia entre pyproject.toml, requirements.txt y pip freeze?

pyproject.toml declara lo que tu paquete necesita, con rangos. pip freeze es un comando que imprime lo que hay instalado, con versiones exactas. requirements.txt es el fichero donde guardas ese freeze para reproducir un entorno concreto. Los tres conviven: declaras con el primero, reproduces con los otros dos.

¿Qué hago si PowerShell bloquea Activate.ps1?

Windows aplica una política de ejecución de scripts. Puedes permitir scripts locales firmados una vez con Set-ExecutionPolicy -Scope CurrentUser RemoteSigned. Como alternativa, usa .venv\Scripts\activate.bat en cmd, o invoca el Python del entorno por ruta sin activar nada.
