Type hints y mypy

Módulo 7 · Testing y calidad ⏱ 35 minutos

1 · Introducción

Python es de tipado dinámico: el tipo vive en el objeto, no en el nombre, y el intérprete no comprueba nada hasta que el código se ejecuta. Eso da una libertad enorme, pero también significa que un error de tipos se descubre en producción, cuando ya es tarde: TypeError: can only concatenate str (not "int") to str.

Los type hints (anotaciones de tipo) son anotaciones opcionales que documentan qué espera y devuelve cada función. No cambian lo que Python hace en tiempo de ejecución, pero permiten que una herramienta externa, mypy, analice el código sin ejecutarlo y detecte incoherencias antes de que salgan de tu máquina. En esta lección aprenderás la sintaxis moderna (list[str], X | None, Protocol, TypedDict) y a leer los errores de mypy.

¿Por qué existe esta lección? Porque los tests comprueban ejemplos concretos que tú escribes, mientras que mypy comprueba todos los caminos posibles del código. Son complementarios: pytest dice «esta entrada concreta funciona», mypy dice «ninguna llamada pasa un int donde esperas un str». Juntos convierten la calidad en algo verificable por máquina.

2 · Teoría

La anotación no se ejecuta: es documentación verificable

Cuando escribes def add(a: int, b: int) -> int:, Python guarda las anotaciones en add.__annotations__ pero no las aplica. Puedes llamar a esa función con strings y no protestará:

def add(a: int, b: int) -> int:
    return a + b

print(add(2, 3))          # 5 -> correcto
print(add("2", "3"))      # "23" -> ¡sin error! Python no mira las anotaciones

Esto desconcierta a quien viene de Java o C#: allí el compilador rechaza el segundo caso. En Python la anotación es una promesa escrita que mypy sí comprueba, pero el intérprete ignora. Por eso el Módulo 7 insiste: los hints no son runtime; son contrato para las herramientas y para las personas.

Analogía: los hints son como el etiquetado de las cajas de una mudanza. El etiquetado no cambia lo que hay dentro, pero quien carga el camión (mypy) detecta al instante si un paquete «frágil» va debajo de un piano. Si no etiquetas, todo viaja igual… hasta que algo se rompe.

Tipos genéricos con la sintaxis moderna (3.9+)

Desde Python 3.9 los contenedores de la stdlib son genéricos directamente, sin importar de typing. Usa la forma moderna, no la heredada:

Anotación modernaSignificaEvita (heredado)
list[str]Lista de stringsList[str]
dict[str, int]Diccionario string → enteroDict[str, int]
tuple[str, int]Tupla fija de dos camposTuple[str, int]

Nada: X | None y Optional

Un valor que puede ser «de este tipo o nada» se anota con la unión X | None (operador |, desde 3.10). La forma clásica, Optional[X] (requiere from typing import Optional), es equivalente; el curso prefiere la nueva por su lectura. Así, int | None es un int o None.

Optional[int] NO significa «parámetro opcional». Significa «int o None». Un parámetro con valor por defecto es opcional aunque su tipo no incluya None. Confundir las dos ideas es uno de los malentendidos más frecuentes con los hints.

Callable: anotar funciones

Las funciones son objetos, así que pueden pasarse como argumentos. Para anotarlas se usa Callable[[args], retorno] (en Python 3.12 vive en collections.abc, también disponible en typing):

from collections.abc import Callable

def apply_twice(fn: Callable[[int], int], value: int) -> int:
    return fn(fn(value))

print(apply_twice(lambda x: x + 1, 10))   # 12

Protocol: duck typing verificable

Python no exige herencia para usar un objeto: si tiene los métodos que necesitas, vale. Es el duck typing («si camina como un pato…»). Protocol permite expresar ese contrato ante mypy sin obligar a heredar de una clase base:

from typing import Protocol


class Readable(Protocol):
    """Cualquier cosa con un metodo read() que devuelva texto."""
    def read(self, size: int = -1) -> str: ...


def load_header(source: Readable) -> str:
    return source.read(10)          # mypy acepta cualquier objeto con read()

Así puedes pasar un io.StringIO, un archivo abierto o tu propia clase: no hay que declarar «implemento Readable», basta con tener el método. Es herencia estructural.

TypedDict: diccionarios con forma

Los datos JSON de Biblioteca son diccionarios con claves conocidas. En memoria el modelo son @dataclass (Book/Movie), pero en la frontera —el JSON crudo que consume item_from_dict— TypedDict describe la forma para que mypy avise si escribes mal una clave o el tipo de un valor:

from typing import TypedDict


class ItemDict(TypedDict):
    id: str
    title: str
    kind: str
    year: int | None
    borrowed: bool


def title_of(item: ItemDict) -> str:
    return item["title"]      # mypy conoce las claves válidas

Ejecutar mypy

mypy es también una dependencia de desarrollo. Se instala y se ejecuta sobre archivos o carpetas:

pip install mypy            # o: uv add --dev mypy
mypy src/biblioteca         # analiza el paquete
mypy --strict src/biblioteca  # el modo mas exigente (recomendado a largo plazo)

Un error típico se lee así: archivo:línea:columna: nivel: mensaje [código].

3 · Ejemplo mínimo

Una función con un hint equivocado. El intérprete no se queja; mypy sí:

# demo.py

def greet(name: str) -> str:
    """Devuelve un saludo; 'name' debe ser texto."""
    return "Hola, " + name


print(greet("Ada"))     # Hola, Ada
print(greet(42))        # ¡Ejecuta igual! Las anotaciones no se comprueban

Salida real al ejecutar (sin error, aunque el hint miente):

Hola, Ada
TypeError: can only concatenate str (not "int") to str

Ahora pasamos mypy. Fíjate en que detecta el problema sin ejecutar nada:

mypy demo.py

demo.py:8: error: Argument 1 to "greet" has incompatible type "int"; expected "str"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

Ese es todo el valor: el error se descubre en el editor, antes del TypeError en producción.

En «errores habituales» verás el error de tipos que mypy detectó durante el desarrollo (un path: str cuyo valor por defecto es un Path): el proyecto ya lo trae corregido con str | Path.

Dos lentes complementarias. pytest dice «este caso concreto funciona»; mypy dice «esta firma no es coherente». Puedes tener verde en pytest y rojo en mypy: los tests pasan porque en ejecución un Path funciona igual que una ruta de texto, pero el hint path: str miente sobre su valor por defecto. Se arregla declarando path: str | Path y anotando _format(item: Item) -> str en cli.py.

6 · Errores habituales

❌ Creer que los hints se comprueban en tiempo de ejecución

def add(a: int, b: int) -> int:
    return a + b

# ❌ No lanza TypeError: Python ignora las anotaciones
print(add("2", "3"))      # "23"

# ✅ Si quieres validacion en runtime, hazla explicita con isinstance
def add_safe(a: int, b: int) -> int:
    if not isinstance(a, int) or not isinstance(b, int):
        raise TypeError("se esperaban enteros")
    return a + b

❌ Hints que mienten

from pathlib import Path

from . import store
from .models import Item


# ❌ El hint dice 'str', pero el valor por defecto es un Path:
#    mypy dara «Incompatible default for parameter "path"» [assignment]
#    en cada función del servicio.
def search(term: str, path: str = store.DEFAULT_STORE) -> list[Item]:
    ...


# ✅ el hint dice la verdad: acepta la ruta como texto o como Path
def search_ok(term: str, path: str | Path = store.DEFAULT_STORE) -> list[Item]:
    ...

8 · Reto

🎯 Un protocolo para el almacén

El módulo store.py usa funciones (load/save) y recibe una ruta. Diseña un Protocol mínimo, StoreLike, con dos métodos —load(self) -> list[Item] y save(self, items: Sequence[Item]) -> None— e implementa un InMemoryStore en memoria. Escribe una función que opere contra el protocolo y comprueba con mypy que el fake lo satisface sin heredar de él.

Pista: declara fake: StoreLike = InMemoryStore(): si le falta un método o el tipo no encaja, mypy lo señala con [assignment]. Observa que el protocolo no menciona rutas: describe «algo que sabe cargar y guardar ítems», no una implementación concreta ni una firma de funciones.

9 · Resumen

  • Los type hints documentan el contrato; no se comprueban al ejecutar.
  • mypy es quien verifica los hints de forma estática, sin correr el programa.
  • Sintaxis moderna: list[str], dict[str, int], tuple[int, ...].
  • X | None (o Optional[X]) significa «tipo o nada», no «parámetro opcional».
  • Callable[[int], str] anota funciones; Protocol modela duck typing estático.
  • TypedDict da forma a los diccionarios (y por tanto al JSON de Biblioteca).
  • El error de mypy se lee: archivo, línea, columna, mensaje y [código].

10 · Preguntas frecuentes

¿Los type hints hacen Python más lento?

En tiempo de ejecución, prácticamente no. Las anotaciones se evalúan una vez (al definir la función) y se guardan; no se comprueban en cada llamada. El coste real lo asume mypy al analizar, no tu programa.

¿Son obligatorios para ejecutar Python?

No, en absoluto. Python funciona sin un solo hint. Son una herramienta para que tú, tu editor y mypy entendáis el código; opcional pero muy recomendable en proyectos que van a crecer, como Biblioteca.

¿Por qué mypy marca un error si el código funciona?

Porque mypy analiza todos los caminos, no los datos concretos que probaste. Puede que hoy solo le pases enteros, pero el hint dice que espera otro tipo: eso es una bomba para el próximo cambio. Corrige el hint o el código; no lo tapes con # type: ignore salvo caso justificado.

¿Protocol o herencia?

Usa herencia cuando compartes implementación; usa Protocol cuando solo necesitas un contrato. Con Protocol, cualquier objeto que tenga los métodos correctos encaja sin declarar nada, lo que mantiene el código desacoplado y sigue siendo verificable por mypy.
