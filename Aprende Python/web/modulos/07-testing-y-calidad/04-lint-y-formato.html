PEP 8, ruff y black

Módulo 7 · Testing y calidad ⏱ 30 minutos

1 · Introducción

En las tres lecciones anteriores hemos verificado qué hace el código (pytest) y qué tipos usa (mypy). Falta la tercera pata de la calidad: que el código sea uniforme y legible. Dos programas idénticos con sangrías distintas, imports desordenados o nombres arbitrarios obligan a quien revisa a leer el estilo en vez de la lógica. La buena noticia es que esto no se decide a mano: se delega en herramientas.

Veremos PEP 8 (la guía de estilo oficial), ruff (linter y formateador extremadamente rápido, que hoy reemplaza a flake8, isort y buena parte de pylint), black (el formateador clásico) y pre-commit (automatización para que nada de esto dependa de tu memoria).

¿Por qué existe esta lección? Porque el estilo no es estética: es ancho de banda mental. Cuando el formato es automático y consistente, las revisiones de código se centran en los bugs y el diseño, no en si había dos espacios o cuatro. Adoptar un estilo común es lo que permite que un equipo (o tu yo de dentro de seis meses) lea el código sin fricción.

2 · Teoría

PEP 8: la guía de estilo de Python

Un PEP (Python Enhancement Proposal) es un documento de diseño del ecosistema. El PEP 8 describe el estilo recomendado. No es una ley que el intérprete imponga, pero es la base que siguen la stdlib y casi todo el ecosistema. Lo esencial:

TemaReglaEjemplo
Sangría4 espacios por nivel, nunca tabuladores mezcladosdef f(): + 4 espacios
Longitud de línea79 clásico; la comunidad moderna usa 88ruff/black por defecto: 88
Variables y funcionessnake_casefind, sample_items
ClasesPascalCaseclass Book, class Movie
ConstantesUPPER_SNAKE_CASEDEFAULT_STORE
ImportsAl principio: stdlib, terceros, locales; sin comodinesgrupos separados por línea en blanco
EspaciosAlrededor de operadores, tras comas; no dentro de paréntesisa = 1, f(a, b)
Líneas en blanco2 entre funciones y clases de nivel superiorsepara bloques

¿Por qué hay imports con orden obligatorio? Porque sigue una regla de dependencia: la biblioteca estándar no puede depender de terceros, y los terceros no deben depender de tu paquete. Agrupar en ese orden (stdlib → terceros → locales) hace visible cuándo estás rompiendo esa dirección.

ruff: linter y formateador en una sola herramienta

ruff está escrito en Rust y es decenas de veces más rápido que las herramientas que reemplaza. Hace dos trabajos distintos, y conviene no confundirlos:

  • Lint (ruff check): detecta problemas: imports sin usar, variables sin usar, comparaciones raras, imports mal ordenados, malas prácticas. Muchos son corregibles con --fix.
  • Formato (ruff format): reescribe el código para que tenga un formato idéntico, como black. No pregunta.
pip install ruff             # o: uv add --dev ruff

ruff check .                 # analiza todo el proyecto (no modifica)
ruff check --fix .           # aplica las correcciones seguras automaticamente
ruff format .                # formatea el codigo (equivalente a black)
ruff format --check .        # solo comprueba, sin escribir (util en CI)

ruff incluye un formateador compatible con black. Por eso el curso lo adopta como herramienta única. Aun así, enseñamos black porque sigue siendo el formateador clásico y lo encontrarás en proyectos existentes; el resultado es prácticamente el mismo.

black: el formateador «sin opiniones»

black se define como the uncompromising formatter: no discute estilo, lo impone. Su lema resume el porqué: «cualquier color quieres, mientras sea negro». Al no ser configurable en lo esencial, elimina las discusiones de estilo del equipo.

pip install black
black .                      # formatea todos los .py del proyecto
black --check .              # comprueba sin modificar (CI)
black --diff .               # muestra que cambiaria, sin escribirlo

pre-commit: que la calidad no dependa de la memoria

Correr ruff y mypy a mano funciona… hasta el día que te olvidas. pre-commit engancha hooks de Git que se ejecutan automáticamente antes de cada commit: si el código no pasa, el commit se aborta. Así, el repositorio nunca recibe código que no pase las comprobaciones.

pip install pre-commit
pre-commit install           # instala el hook en .git/hooks/
pre-commit run --all-files   # ejecuta los hooks sobre todo el repo ahora mismo

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9                       # fija una version concreta del hook
    hooks:
      - id: ruff                      # lint (con --fix)
        args: [--fix]
      - id: ruff-format               # formateo
  - repo: https://github.com/psf/black
    rev: 24.8.0
    hooks:
      - id: black

Fija la versión (rev) de cada hook. Un pre-commit sin versión fija se rompe «un día cualquiera» cuando el proyecto remoto cambia. Actualizar es una decisión deliberada (pre-commit autoupdate), no una sorpresa.

3 · Ejemplo mínimo

Un archivo desordenado a propósito: import sin usar, comparación con == None, espacios irregulares. Los errores que verás son clásicos del lint.

# demos/desordenado.py
import os                                     # importado y sin usar
import json


def  calcular ( a,b ):                         # espacios raros en el nombre
    if a == None:                              # debe ser 'is None'
        return 0
    return a+b

Ejecutamos el lint:

ruff check demos/desordenado.py

demos/desordenado.py:1:8: F401 [*] `os` imported but unused
demos/desordenado.py:2:1: F811 Redefinition of unused `json` from line 1
demos/desordenado.py:5:5: E712 [*] Comparison to `None` should be `cond is None`
Found 3 errors.
[*] 2 fixable with the `--fix` option.

Cada línea es archivo:línea:columna: código mensaje. Los [*] indican que ruff puede arreglarlos solo:

ruff check --fix demos/desordenado.py     # arregla imports y 'is None'
ruff format demos/desordenado.py          # normaliza espacios y saltos

# demos/desordenado.py (resultado ya limpio)
import json


def calcular(a, b):
    if a is None:
        return 0
    return a + b

Observa que ruff no arregló la lógica: quitó el import muerto, cambió == None por is None y dejó el formato impecable. Eso es exactamente lo que quieres: decisiones automáticas fuera, pensamiento para ti.

4 · Ejemplo real

Configuramos la calidad de Biblioteca en el pyproject.toml, que es el único lugar donde se declaran herramientas (Módulo 4). Así cualquiera que clone el repo obtiene el mismo comportamiento con solo ejecutar los comandos.

# pyproject.toml (fragmento real)
[tool.mypy]
python_version = "3.12"
strict = true                          # el modo más exigente

[tool.ruff]
line-length = 88                       # límite de línea (coherente con black)
target-version = "py312"

El lint de ruff funciona con valores por defecto, pero puedes fijar qué reglas corre. Esta es la selección explícita que usaremos como referencia:

# pyproject.toml (ampliación opcional)
[tool.ruff.lint]
# E/W: estilo PEP 8 - F: errores lógicos - I: orden de imports
# UP: sintaxis moderna - B: bugbear - ANN: anotaciones
select = ["E", "W", "F", "I", "UP", "B", "ANN"]
ignore = ["E501"]                      # la longitud la decide el formateador

[tool.ruff.format]
quote-style = "double"                 # comillas dobles, como black

Supongamos que añadimos a service.py un helper con los típicos deslices: el import local pegado al bloque estándar y el parámetro sin anotar.

# src/biblioteca/service.py (helper nuevo, antes)
import json
from biblioteca import store


def borrowed_titles(path):
    items = store.load(path)
    return json.dumps([item.title for item in items if item.borrowed], ensure_ascii=False, indent=2)

Pasamos el lint y el formato (el tipado estático, con mypy, lo dejamos estable en la lección anterior):

ruff check src/biblioteca
ruff format src/biblioteca

src/biblioteca/service.py:2:1: I001 [*] Import block is un-sorted or un-formatted
src/biblioteca/service.py:5:1: ANN001 Missing type annotation for function argument 'path'
Found 2 errors.
[*] 1 fixable with the `--fix` option.
1 file reformatted.

Tras ruff check --fix y ruff format, el helper queda así (la línea larga se reflowa a varias líneas):

# src/biblioteca/service.py (helper nuevo, después)
import json

from biblioteca import store


def borrowed_titles(path: str) -> str:
    """Títulos actualmente prestados, serializados a JSON."""
    items = store.load(path)
    return json.dumps(
        [item.title for item in items if item.borrowed],
        ensure_ascii=False,
        indent=2,
    )

Un detalle que enseña el lint: I001 no mira solo espacios: detecta que el import local quedó pegado al bloque de la biblioteca estándar. Esa línea en blanco no es estética, hace visible la dirección de dependencias (stdlib → local). Y ANN001 te recuerda anotar la firma, justo lo que mypy agradece.

Documentación oficial: reglas y configuración completas en docs.astral.sh/ruff; el formateador clásico, en black.readthedocs.io; pre-commit, en pre-commit.com.

La regla E501 en el config. Desactivamos el aviso de «línea demasiado larga» en el lint porque el formateador ya garantiza que las líneas caben; avisar dos veces por lo mismo es ruido. Es un ejemplo de cómo ruff y el formato se reparten el trabajo.

6 · Errores habituales

❌ Confundir lint con formateo

# ❌ 'ruff format' no arregla un import sin usar ni un bug logico
ruff format src/

# ✅ son dos trabajos: primero el lint (con --fix), luego el formato
ruff check --fix src/
ruff format src/

❌ Comparar con None usando ==

# ❌ E711: 'None' es un singleton, se compara por identidad
if item.year == None:
    ...

# ✅ 'is None' expresa identidad y es lo que PEP 8 recomienda
if item.year is None:
    ...

❌ Imports desordenados o comodín

# ❌ I001: import local antes que stdlib; y comodín que contamina el namespace
from biblioteca.models import Book
import json
from os import *

# ✅ grupos en orden y nombres explícitos
import json

from biblioteca.models import Book

❌ Silenciar el linter en bloque

# ❌ Apaga TODAS las reglas en todo el archivo: deja de protegerte
# ruff: noqa

# ✅ ignora una regla puntual, con motivo
import os  # noqa: F401  (se usa en runtime via eval del plugin)

7 · Ejercicio guiado

Objetivo: dejar el paquete Biblioteca limpio de lint y bien formateado, y automatizarlo con pre-commit.

  1. Instala las herramientas en el entorno de desarrollo: 
    pip install ruff black pre-commit
# equivalencia moderna: uv add --dev ruff black pre-commit
  2. Añade la configuración al pyproject.toml: el fragmento real [tool.ruff] con line-length = 88 y target-version = "py312". Deja el bloque opcional [tool.ruff.lint] para más adelante: fijar la selección de reglas es una decisión aparte.
  3. Pasa el lint y aplica las correcciones automáticas: 
    ruff check --fix src/biblioteca tests
ruff format src/biblioteca tests
ruff check src/biblioteca tests        # ahora debe salir limpio

    Resultado esperado: tras el --fix y el formato, el último ruff check responde All checks passed!. Si quedan errores, no los corrijas a ciegas: lee el código de la regla (E7xx, F4xx…) y decide.

  4. Crea .pre-commit-config.yaml con los hooks de ruff y black del ejemplo de teoría. Luego instálalos y pruébalos: 
    pre-commit install
pre-commit run --all-files

    Resultado esperado: cada hook aparece como Passed (o Failed la primera vez, si había algo que arreglar; en ese caso los hooks modifican los archivos y basta con volver a añadirlos a Git).

  5. Comprueba la automatización: edita un archivo a propósito e introduce import os sin usar. Haz git add y git commit. Resultado esperado: el commit se aborta; ruff marca F401 y te ofrece el arreglo. Corrige con ruff check --fix, vuelve a añadir y commitea: ahora pasa.

Windows (PowerShell): los comandos ruff, black y pre-commit se ejecutan igual que en Linux o macOS una vez activado el entorno (.venv\Scripts\Activate.ps1). Si tu shell no encuentra el ejecutable, usa python -m ruff, python -m black y python -m pre_commit.

8 · Reto

🎯 Un hook que también comprueba tests y tipos

Amplía .pre-commit-config.yaml para que, además de ruff y black, el commit ejecute pytest y mypy sobre el paquete. Investiga cómo declarar un hook que corra un comando local (repo: local) o usa el hook mantenido en pre-commit.com/hooks.html. Después decide, con argumentos, en qué casos no conviene meter tests en pre-commit (por ejemplo, si la suite tarda mucho) y qué alternativa usarías.

Pista: para un comando propio, el hook se declara con repo: local, language: system, entry: pytest -q, pass_filenames: false y types: [python]. La pregunta de diseño —pre-commit rápido para lint/formato, tests y tipos en CI— es más importante que el YAML.

9 · Resumen

  • PEP 8 es la guía de estilo: snake_case, PascalCase, imports ordenados y 4 espacios.
  • ruff hace dos trabajos: lint (ruff check) y formato (ruff format).
  • black es el formateador clásico «sin opiniones»; ruff-format es compatible.
  • El lint arregla semántica; el formato arregla presentación. No los confundas.
  • pre-commit ejecuta las comprobaciones antes de cada commit y fija la versión de los hooks.
  • Configura las herramientas en pyproject.toml: una sola fuente para todo el equipo.
  • Los docstrings explican el por qué; el linter nunca lo sustituye.

10 · Preguntas frecuentes

¿ruff reemplaza a black, isort y flake8?

En la práctica, sí para la mayoría de proyectos: ruff implementa las reglas de flake8, el orden de imports de isort (regla I) y un formateador compatible con black. Puedes quedarte solo con ruff. En este curso mostramos black porque lo encontrarás en proyectos existentes y entender ambos te hace versátil.

¿79 u 88 caracteres por línea?

El PEP 8 clásico recomienda 79; la comunidad moderna, liderada por black, usa 88, que es el valor por defecto de ruff y black. Lo importante no es el número, sino elegir uno y que el formateador lo garantice. En Biblioteca usamos 88.

¿Debo arreglar todos los avisos del linter?

Casi todos, sí. Un aviso es una señal, pero no una orden divina: algunos casos justifican un # noqa puntual con un comentario que explique el porqué. Lo que nunca es aceptable es un # ruff: noqa a nivel de archivo que apague todo.

¿pre-commit sustituye a la CI?

No. pre-commit te da feedback local y rápido antes del commit; la CI es la barrera final en el servidor, donde nadie puede saltarse los hooks. Se complementan: lint y formato en pre-commit, suite completa y mypy también en CI.
