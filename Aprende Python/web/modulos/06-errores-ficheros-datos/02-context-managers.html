Context managers y with

Módulo 6 · Errores, ficheros y datos ⏱ 30 minutos

1 · Introducción

Cada vez que abrimos un fichero, una conexión de red o un lock, adquirimos un recurso que hay que devolver. Y el recurso no se libera «al final de la función»: hay que liberarlo explícitamente, pase lo que pase. La sentencia with es la respuesta de Python a ese problema, y es una de las construcciones más elegantes del lenguaje.

En esta lección verás por qué with garantiza el cierre aunque salte una excepción, cómo funciona por dentro el protocolo de contexto (__enter__/__exit__), cómo escribir el tuyo con contextlib.contextmanager y dónde se usa de verdad en Biblioteca: escribir el data/library.json de forma segura para no dejarlo corrupto si el programa muere a mitad.

¿Por qué existe esta lección? Porque el 90% de las «pérdidas de recursos» y de los ficheros corruptos vienen de abrir algo y no cerrarlo, sobre todo cuando hay un error en medio. with convierte ese cierre en imposible de olvidar. Es el mismo principio que un try/finally, pero expresado en una línea y sin ruido.

2 · Teoría

El problema: los recursos no se cierran solos

Un objeto fichero en Python mantiene abierto un file descriptor del sistema operativo. El recolector de basura suele cerrarlo cuando el objeto desaparece, pero (1) no sabes cuándo ocurrirá, y (2) en Windows un fichero abierto no se puede borrar ni renombrar. El patrón manual sería:

# ❌ Sin try/finally, si read() lanza, el fichero NO se cierra.
f = open("data/library.json", encoding="utf-8")
text = f.read()          # si esto falla…
f.close()                # …esta línea nunca se ejecuta

# ✅ Versión manual correcta: try/finally garantiza el cierre.
f = open("data/library.json", encoding="utf-8")
try:
    text = f.read()
finally:
    f.close()            # se ejecuta siempre, haya o no excepción

Funciona, pero es verboso y fácil de olvidar. La sentencia with es azúcar sintáctico exactamente para ese patrón:

# ✅ Idiomático: el cierre se garantiza y no queda código de limpieza suelto.
with open("data/library.json", encoding="utf-8") as f:
    text = f.read()
# aquí 'f' ya está cerrado, incluso si read() lanzó una excepción

Multiplataforma: en Linux/macOS un fichero abierto aún se puede borrar o renombrar; en Windows no, y obtendrás PermissionError. Y pasa siempre encoding="utf-8" para que los acentos no se corrompan al mover ficheros entre Windows (cp1252) y Linux/macOS.

Analogía: with es como entrar a una sala con torno de salida. Da igual cómo salgas —andando, corriendo o por una emergencia— el torno te obliga a pasar y registra tu salida. Ese torno es __exit__.

El protocolo: __enter__ y __exit__

Un context manager es cualquier objeto que cumpla el protocolo definido por dos métodos especiales. Cuando escribes with expr as var:, Python hace esto:

with obj as var:
    BLOQUE

equivale a:

var = obj.__enter__()        # 1) entrar: devuelve lo que recibe 'as'
try:
    BLOQUE                   # 2) ejecutar el cuerpo
except BaseException as exc: # 3) si hay error…
    if not obj.__exit__(exc.__class__, exc, exc.__traceback__):
        raise                #    …__exit__ decide si se traga (True) o sube (False)
else:
    obj.__exit__(None, None, None)   # 4) sin error: notificar cierre normal

El método __exit__(self, exc_type, exc, tb) recibe tres argumentos. En el camino feliz los tres son None; si hubo excepción, contiene el tipo, el objeto y el traceback. Y su valor de retorno importa:

  • return False (o no devolver nada): la excepción se propaga. Es lo correcto casi siempre.
  • return True: la excepción se suprime. Solo tiene sentido en context managers cuyo trabajo es gestionar ese error (como contextlib.suppress).

⚠️ Devolver True sin querer es un bug clásico. Si tu __exit__ acaba con return True por descuido, te comerás cualquier excepción del bloque y el programa seguirá con estado inconsistente. Devuelve False explícito o simplemente no devuelvas nada.

Escribir el tuyo: clase o contextlib.contextmanager

Tienes dos caminos. Con una clase, implementas los dos protocolos; cómodo si guardas estado. Con el decorador @contextmanager de contextlib, escribes una función generadora: todo lo anterior al yield es __enter__ y lo posterior es __exit__.

from contextlib import contextmanager

# --- Versión con clase ---
class Tag:
    def __init__(self, label: str) -> None:
        self.label = label
    def __enter__(self):
        print(f"[{self.label}] inicio")
        return self
    def __exit__(self, exc_type, exc, tb):
        print(f"[{self.label}] fin")
        return False                    # dejamos subir cualquier excepción

# --- Versión con generador (menos código) ---
@contextmanager
def tag(label: str):
    print(f"[{label}] inicio")          # __enter__
    try:
        yield label                     # el valor que recibe 'as'
    finally:
        print(f"[{label}] fin")         # __exit__ (¡envuelto en finally!)

¿Por qué el try/finally alrededor del yield? Porque si el bloque del with lanza una excepción, esta se inyecta en el punto del yield. El finally se asegura de que la limpieza ocurre igual. contextmanager gestiona el resto y decide no suprimir el error.

La biblioteca estándar ya trae varios útiles: contextlib.suppress(FileNotFoundError) (ignora un error concreto), contextlib.nullcontext() (no hace nada, útil para sustituir un with en tests) y contextlib.ExitStack() cuando el número de recursos no se conoce hasta el runtime.

3 · Ejemplo mínimo

Un context manager que marca el inicio y el fin de un paso, y que se cierra incluso cuando el bloque falla:

from contextlib import contextmanager

@contextmanager
def paso(nombre: str):
    print(f"→ inicio {nombre}")      # equivale a __enter__
    try:
        yield nombre                 # aquí se ejecuta el with
    finally:
        print(f"← fin {nombre}")     # equivale a __exit__, SIEMPRE

with paso("cargar catálogo"):
    print("  trabajando")

# Salida esperada:
# → inicio cargar catálogo
#   trabajando
# ← fin cargar catálogo

Línea por línea: al entrar, la función se ejecuta hasta el yield e imprime «inicio». El with recibe el valor nombre (aunque no usemos as). El cuerpo imprime «trabajando». Al salir, la ejecución continúa tras el yield: el finally imprime «fin». El por qué de yield: marca la frontera entre empezar y terminar; todo lo que hay antes es «adquirir» y lo que hay después es «liberar».

4 · Ejemplo real

En Biblioteca, guardar el catálogo con path.write_text(json.dumps(...)) tiene un peligro: si el programa se interrumpe a mitad de la escritura (Ctrl+C, corte de luz, disco lleno), library.json queda truncado y corrupto, y lo perdiste todo. La solución profesional es la escritura atómica: escribir en un temporal y renombrar al final, que en el mismo sistema de archivos es una operación atómica.

# Patrón general: escritura atómica con un context manager
import json
import os
import tempfile
from contextlib import contextmanager
from pathlib import Path

@contextmanager
def atomic_write(path: Path, encoding: str = "utf-8"):
    """Escribe un fichero de forma atómica.

    Crea un temporal en el MISMO directorio (para que os.replace no
    cruce dispositivos) y solo lo mueve al destino si todo fue bien.
    Si el bloque lanza, el temporal se borra y el original queda intacto.
    """
    path.parent.mkdir(parents=True, exist_ok=True)   # asegura el directorio
    fd, tmp_name = tempfile.mkstemp(dir=path.parent, suffix=".tmp")
    tmp = Path(tmp_name)
    try:
        with os.fdopen(fd, "w", encoding=encoding) as handle:
            yield handle                      # el with de dentro escribe aquí
        os.replace(tmp, path)                 # ✅ renombrado atómico (solo si OK)
    except BaseException:
        tmp.unlink(missing_ok=True)           # ❌ algo falló: no dejamos basura
        raise                                 # y propagamos el error

# Uso desde el servicio de guardado
with atomic_write(Path("data/library.json")) as f:
    json.dump(items, f, ensure_ascii=False, indent=2)

# Salida esperada (data/library.json escrito al completo o no tocado):
# [nada por stdout; el fichero aparece de golpe, nunca a medias]

Decisiones: (1) el temporal vive en path.parent para que os.replace sea atómico (renombrar entre discos no lo es); (2) except BaseException aquí sí es correcto porque queremos limpiar ante cualquier interrupción, incluida Ctrl+C, y volvemos a lanzar con raise; (3) el yield entrega el handle abierto, así el código de fuera escribe normal. Este patrón es el que haría fiable el store.py: el proyecto, de momento, escribe con write_text directo (lo verás en la lección 4), y adoptar la escritura atómica es precisamente el reto de esa lección.

Conexión: este patrón es el hermano de open(). open es un context manager que cierra el fichero; atomic_write es un context manager que publica el fichero. En la lección 4 verás cómo se combinan json.loads/json.dumps con Path.read_text/write_text y por qué la escritura atómica evita el temido «JSON corrupto».

6 · Errores habituales

No usar with y fiarse del recolector

# ❌ En Windows no podrás renombrar/borrar el fichero hasta que el GC
#    decida cerrarlo; en el peor caso, se pierden escrituras en el buffer.
f = open("data/library.json", "w", encoding="utf-8")
f.write("texto que quizá nunca llegue al disco")   # buffer sin vaciar

# ✅ with cierra (y hace flush) al salir del bloque, sin excepciones que lo impidan.
with open("data/library.json", "w", encoding="utf-8") as f:
    f.write("texto garantizado")

__exit__ que se traga todo sin querer

class Silencio:
    def __enter__(self):
        return self
    def __exit__(self, exc_type, exc, tb):
        return True          # ❌ suprime CUALQUIER excepción del bloque

# ✅ Sé explícito: no suprimas salvo que sea tu trabajo.
class NoSuprime:
    def __enter__(self):
        return self
    def __exit__(self, exc_type, exc, tb):
        return False         # la excepción sube

Olvidar liberar en el contextmanager casero

@contextmanager
def mal():
    print("adquiero recurso")
    yield
    print("libero")           # ❌ si el with lanza, esto NO se ejecuta

# ✅ La limpieza va en finally.
@contextmanager
def bien():
    print("adquiero recurso")
    try:
        yield
    finally:
        print("libero")

Usar with con algo que no es un context manager

# ❌ TypeError: 'list' object does not support the context manager protocol
with [1, 2, 3] as datos:
    pass

# ✅ 'with' espera __enter__/__exit__. Para datos sueltos, no aplica;
#    si quieres un no-op, contextlib.nullcontext() es la herramienta.
from contextlib import nullcontext
with nullcontext([1, 2, 3]) as datos:
    print(len(datos))        # 3

7 · Ejercicio guiado

Objetivo: escribir un context manager que presta temporalmente un ítem y lo deja como estaba al salir, incluso si el bloque falla. Así demostrarás de primera mano que __exit__ siempre corre.

  1. Paso 1 — el modelo: una dataclass mínima con el estado borrowed. 
    from dataclasses import dataclass

@dataclass
class Book:
    id: str
    title: str
    borrowed: bool = False
  2. Paso 2 — el context manager: adquiere antes del yield, libera en un finally. 
    from contextlib import contextmanager

@contextmanager
def prestado_temporalmente(item):
    item.borrowed = True          # __enter__: adquiere el recurso (estado)
    try:
        yield item
    finally:
        item.borrowed = False     # __exit__: SIEMPRE restaura
  3. Paso 3 — camino feliz y con error: comprueba que el estado se restaura en ambos. 
    libro = Book("b1", "1984")

with prestado_temporalmente(libro):
    print("dentro:", libro.borrowed)     # True
print("después:", libro.borrowed)        # False

try:
    with prestado_temporalmente(libro):
        raise RuntimeError("fallo simulado")
except RuntimeError as exc:
    print("capturado:", exc)
print("tras el error:", libro.borrowed)  # False — ¡el finally corrió!
  4. Paso 4 — resultado esperado: 
    dentro: True
después: False
capturado: fallo simulado
tras el error: False
    La cuarta línea es la prueba: aunque el bloque lanzó RuntimeError, el finally restauró borrowed = False. Sin with (o sin finally), el ítem habría quedado «prestado» para siempre.

Por qué funciona: la excepción se inyecta en el yield, el finally se ejecuta y, como @contextmanager no la suprime, vuelve a propagarse hasta tu except RuntimeError. Si quisieras suprimirla (rara vez), el generador tendría que capturarla y return, en vez de dejarla salir.

8 · Reto

🎯 Escritura atómica del catálogo

Implementa tu propio atomic_write(path) como context manager sin mirar el de la teoría. Requisitos: crear el directorio padre si falta, escribir en un temporal del mismo directorio, renombrar atómicamente solo si el bloque termina bien, y borrar el temporal si hubo cualquier excepción (¡incluido Ctrl+C!). Después pruébalo: escribe una lista de libros y, en un segundo intento, lanza un RuntimeError a propósito tras escribir algo; comprueba que el fichero bueno anterior sigue intacto.

Pista: tempfile.mkstemp(dir=path.parent) te da un descriptor y una ruta; usa os.fdopen(fd, "w", encoding="utf-8") para obtener un handle de texto. Para el renombrado atómico, os.replace(tmp, path). En el except, limpia con tmp.unlink(missing_ok=True) y vuelve a lanzar. Piensa por qué el temporal debe vivir en el mismo directorio que el destino.

9 · Resumen

  • Los recursos (ficheros, locks, conexiones) deben liberarse siempre, también cuando hay errores.
  • with es try/finally expresado de forma segura y concisa: imposible olvidar el cierre.
  • Un context manager cumple el protocolo __enter__/__exit__; as recibe lo que devuelve __enter__.
  • __exit__(exc_type, exc, tb) recibe el error si lo hubo; devolver True lo suprime (cuidado), False lo propaga.
  • @contextmanager convierte una función generadora: antes del yield es la entrada, el finally posterior es la salida.
  • La escritura atómica (temporal + os.replace) evita ficheros a medias; es la base de un almacén fiable.

10 · Preguntas frecuentes

¿with y try/finally son exactamente lo mismo?

En esencia, sí: with se apoya en el protocolo de contexto, que internamente equivale a un try/finally. La diferencia es de expresividad y seguridad: with encapsula la limpieza en el objeto, se reutiliza en todo el programa y no puedes olvidarla. Además, un context manager puede suprimir excepciones (devolviendo True), algo que try/finally no hace por sí solo.

¿Cuándo devo devolver True desde __exit__?

Casi nunca. Un context manager debe suprimir una excepción solo si forma parte de su contrato gestionarla, como contextlib.suppress. Ejemplo legítimo: un CM «reintenta» que captura un error transitorio y lo resuelve. Si devuelves True y el error era un bug, lo habrás ocultado. En caso de duda, devuelve False.

¿Puedo usar varias cosas en un solo with?

Sí: with open(a) as f, open(b) as g: o, si son muchas y dinámicas, contextlib.ExitStack. Los recursos se cierran en orden inverso al que se abrieron (el último en entrar es el primero en salir), igual que una pila. Esto importa cuando un recurso depende de otro.

¿Por qué la escritura atómica usa un fichero temporal y no escribe directamente?

Porque una escritura directa puede dejar el fichero a medias si el proceso muere. Escribir en un temporal y renombrar con os.replace hace que el destino pase de golpe de la versión antigua a la nueva: quien lo lea verá una u otra, nunca una mezcla. Requisito clave: el temporal debe estar en el mismo sistema de archivos que el destino, o el renombrado deja de ser atómico (suele cruzar dispositivos).

¿Un context manager puede devolver algo distinto de sí mismo en __enter__?

Sí, y es lo normal. open(...) devuelve un objeto fichero distinto de sí mismo; @contextmanager devuelve lo que pongas tras yield. La regla es: as var recibe el resultado de __enter__, que no tiene por qué ser el objeto del with. Muchos context managers devuelven self por comodidad, pero no es obligatorio.
