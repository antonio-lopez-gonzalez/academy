SQL vs NoSQL

Módulo 2 · Datos 🕐 35 minutos

1 · Introducción

Elegir base de datos es una de las decisiones que más cuesta revertir en un sistema. Cambiar de motor con datos en producción es carísimo: migrar esquemas, reescribir consultas, rehacer índices y garantizar que no se pierde ni un registro. Por eso esta lección no va de "cuál es mejor" (no existe), sino de cómo se decide con criterio.

La respuesta corta, que iremos desmontando: elige por patrón de acceso, no por moda. Un sistema se rompe cuando se elige el motor por lo que "usa todo el mundo" y luego resulta que las consultas reales necesitan joins, transacciones o agregaciones que ese motor no da bien.

¿Por qué existe esta lección?

Porque "SQL vs NoSQL" se presenta casi siempre como una guerra de religiones, cuando en realidad es una decisión de ingeniería: qué accesos vas a hacer, qué garantías necesitas y a qué escala. Vamos a convertir la pregunta "¿qué motor uso?" en la pregunta correcta: "¿cómo accedo a mis datos?".

Errores típicos que verás una y otra vez:

  • Elegir NoSQL "porque escala" cuando el cuello de botella real está en otro sitio (o no existe todavía).
  • Meter todo en un solo motor relacional cuando un cache KV o un índice de búsqueda lo resolverían mejor.
  • Modelar en documento como si fuera una tabla relacional (o al revés), perdiendo la ventaja de cada modelo.
  • Confundir NoSQL con "sin transacciones" (muchos motores modernos sí las ofrecen, aunque con matices).

2 · Teoría

Qué significa "relacional" de verdad

Un motor relacional (PostgreSQL, MySQL, SQL Server, Oracle) organiza los datos en tablas con filas y columnas, con un esquema que se define antes de escribir. Su superpoder no es "usar SQL": es que puede combinar datos de varias tablas (joins), mantener invariantes (claves foráneas, unicidad) y ejecutar transacciones con ACID:

ConsistenciaLas invariantes se respetan antes y despuésNunca queda una fila con user_id inexistente
AislamientoTransacciones concurrentes no se pisan de forma incorrectaDos compras simultáneas no venden el mismo stock una sola vez
DurabilidadLo confirmado sobrevive a un falloTras el COMMIT, el dato está en disco

BASE y el otro extremo

Frente a ACID, los motores distribuidos de NoSQL suelen abrazar BASE (Basically Available, Soft state, Eventual consistency): priorizan estar disponibles y responder rápido, aceptando que las réplicas converjan con el tiempo. Esto no es "peor": es un trade-off deliberado que verás a fondo en Réplicas y consistencia y en El teorema CAP. Lo importante ahora: esquema flexible y consistencia eventual son el precio de la escala horizontal.

La pregunta correcta: el patrón de acceso

Antes de mirar motores, escribe los accesos. Por cada uno: qué entidades toca, por qué clave filtra, cuántos registros devuelve, qué forma tiene la respuesta y cuánta frecuencia tiene.

ACCESO 1: "dado un user_id, dame su perfil y sus 3 últimos pedidos"
  → clave: user_id        → devuelve: ~1 perfil + 3 pedidos   → forma: jerárquica
ACCESO 2: "dame el top 10 de productos por ventas de la semana"
  → filtro: rango de fechas  → devuelve: agregado          → necesidad: agregación
ACCESO 3: "¿qué amigos de mis amigos ya compraron X?"
  → recorrido: grafo a 2 saltos                          → necesidad: relaciones
ACCESO 4: "busca 'zapatilla roja talla 42' y ordena por relevancia"
  → texto + filtros                                       → necesidad: búsqueda
Regla de oro

El motor se elige al final, no al principio. Primero se escribe cómo se consulta; después se busca el motor cuya forma de indexar y almacenar encaje con esos accesos. Si necesitas varios patrones muy distintos, quizá necesites varios motores (poliglot persistence) y sincronizarlos.

¿Puede un relacional hacer esto a escala?

Sí, muchas veces. Un PostgreSQL bien indexado y con réplicas de lectura aguanta perfectamente decenas de miles de QPS para un sistema típico. El relacional deja de ser cómodo cuando: (1) el volumen de escritura supera lo que un nodo (o una partición primaria) puede absorber; (2) el modelo es tan flexible que un esquema fijo duele (catálogos con atributos infinitos); (3) el acceso dominante es por clave y necesitas latencias de milisegundos a escala planetaria; o (4) el acceso principal es un recorrido de grafo profundo. La lección Particionado y sharding explica el cuándo de la escala horizontal.

3 · Ejemplo mínimo

Tomemos un pedido con sus líneas. En relacional son dos tablas con una clave foránea; en documento es un único objeto anidado. Fíjate en cuántas operaciones necesita cada modelo para reconstruir lo mismo.

Opción A — relacional (normalizado)

schema.sql
-- Dos tablas: el pedido y sus líneas, unidas por la clave foránea
CREATE TABLE orders (
  id          bigserial PRIMARY KEY,
  customer_id bigint NOT NULL,
  total_cents int    NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  id         bigserial PRIMARY KEY,
  order_id   bigint NOT NULL REFERENCES orders(id),
  sku        text   NOT NULL,
  qty        int    NOT NULL,
  price_cents int   NOT NULL
);

CREATE INDEX idx_items_order ON order_items(order_id);

-- Reconstruir un pedido = un JOIN
SELECT o.id, o.customer_id, o.total_cents,
       i.sku, i.qty, i.price_cents
FROM orders o
JOIN order_items i ON i.order_id = o.id
WHERE o.id = 1042;

Opción B — documento (anidado)

order-1042.json
{
  "_id": 1042,
  "customer_id": 77,
  "total_cents": 4599,
  "created_at": "2026-10-11T09:14:00Z",
  "items": [
    { "sku": "ZAP-ROJO-42", "qty": 1, "price_cents": 3999 },
    { "sku": "CORD-001",    "qty": 2, "price_cents": 300 }
  ]
}

En el motor de documentos, leer el pedido es un solo acceso por clave (GET order:1042): todo lo que necesitas para pintar la pantalla viene ya junto. En el relacional es un JOIN que el planificador resuelve con un índice, pero sigue siendo trabajo de dos estructuras.

Analogía: la carpeta vs. los archivadores

El documento es una carpeta con todo el expediente dentro: la coges y lo tienes entero. El relacional es una biblioteca con fichas cruzadas: cada dato vive una sola vez y puedes combinarlos de mil maneras, pero reconstruir un expediente requiere ir a varios cajones. Ninguno es "mejor": depende de si prefieres leer rápido un expediente entero o cruzar datos de muchos expedientes.

El número que decide

Supón 10 000 pedidos/segundo de escritura y lecturas "dame este pedido". Con documento, la escritura es una sola operación sobre un nodo (documento entero). Con relacional, la misma operación son 2 inserts + gestión de transacción; sigue funcionando, pero consume más I/O y coordinación. Si en cambio el negocio pregunta "¿cuánto ha vendido cada SKU por región este trimestre?", el relacional lo hace con un GROUP BY; el documento te obliga a agregar en la aplicación o duplicar datos. Mismo sistema, dos preguntas, dos veredictos.

4 · Ejemplo real

El caso clásico URL shortener (Módulo 6) es el ejemplo canónico del trade-off. Requisitos con supuestos explícitos:

  • 100 M URLs creadas por mes ⇒ ~40 escrituras/segundo de media.
  • Tasa de lectura:escritura 100:1 ⇒ ~4 000 lecturas/segundo (picos ×5 ⇒ 20 000 QPS).
  • Acceso: siempre por clave (el slug corto); nunca por "todas las URLs de un día".
  • Latencia objetivo: p99 < 20 ms en la redirección.

El patrón de acceso manda

La operación dominante es GET /{slug} → url_larga: una lectura por clave, sin joins ni agregaciones. Ese es exactamente el patrón de un almacén clave-valor. Meterlo en un relacional funciona, pero es usar un camión para llevar una carta: pagas índices, transacciones y un esquema más rico del que necesitas, a cambio de nada.

        ESCRITURA (40/s)                         LECTURA (hasta 20k/s)
   ┌──────────────┐                         ┌──────────────────────┐
   │  crear URL   │──► genera slug ──► PUT  │  GET /{slug}         │
   └──────────────┘     (base62)     key=slug│  ──► KV store ──► 302 │
                                        val=url                     │
                                    ┌──────────────┐                │
                                    │  KV store    │◄───────────────┘
                                    │  slug→url    │   (una lectura por clave)
                                    └──────────────┘
                                     caché delante (ver Módulo 3)

Dónde el relacional sigue siendo la elección

Ahora cambia el requisito: el sistema necesita analítica de negocio (URLs por dominio, por cliente, por país, con filtros combinados) y consistencia fuerte en la creación (un slug nunca puede duplicarse). Un KV puro te obliga a resolver la unicidad con un segundo sistema; un relacional te la da con un índice UNIQUE y ejecuta la analítica con SQL. En ese escenario, muchas arquitecturas reales usan relacional como fuente de verdad y un KV/caché como capa de lectura rápida delante (exactamente el patrón que verás en Estrategias de caché).

No es "uno u otro"

La decisión final del URL shortener de un sistema grande combina dos motores: KV para el camino caliente de lectura y relacional (o un motor transaccional) como fuente de verdad y para analítica. Elegir por patrón de acceso no significa elegir un solo motor; significa asignar cada acceso al motor que mejor lo sirve.

6 · Errores habituales

Trasladar el esquema relacional 1-a-1 al documento

El error número uno al pasar a documento: crear una colección por tabla y hacer "joins" en la aplicación.

Así no
// ❌ Colecciones separadas que obligan a unir en código (dos lecturas + lógica)
// colección "orders"          colección "order_items"
{ "_id": 1042, "customer": 77 }  { "order_id": 1042, "sku": "ZAP-ROJO-42", "qty": 1 }
Así sí
// ✅ El documento refleja el acceso real: leer el pedido = una lectura
{ "_id": 1042, "customer": 77, "items": [ { "sku": "ZAP-ROJO-42", "qty": 1 } ] }

Asumir que NoSQL no tiene transacciones

Creencia incorrecta
❌ "En NoSQL no hay transacciones, así que no puedo usar un motor
    distribuido para pagos."  → Falso hoy: varios motores ofrecen
    transacciones (aunque a menudo con límites de alcance y coste).
Cómo razonarlo
✅ Pregunta en su lugar: ¿necesito transacciones que crucen MUCHAS
    entidades y particiones? Si la respuesta es "sí, a menudo", el
    relacional (o un motor con transacciones fuertes) encaja mejor.
    Si las "transacciones" son por clave, un KV las hace triviales.

Elegir por escala hipotética

Así no
❌ "Vamos a montar Cassandra porque el feed puede tener millones
    de usuarios."  → Y la consulta real de la pantalla necesita un
    JOIN con la tabla de usuarios y un filtro por fecha variable.
Así sí
✅ "La escritura del feed es un append por usuario (FAN-OUT ON WRITE,
    ~50k/s) y la lectura es por clave de usuario. Ese patrón justifica
    un columnar. La tabla de usuarios (baja escala, joins) se queda en
    el relacional."  → Decisión con número y con acceso explícito.
⚠️ "Escala" no es una palabra mágica

Ningún motor "escala" por sí solo. Escala el conjunto: motor + clave de partición + caché + réplicas + modelo de datos. Elegir NoSQL sin pensar la clave de partición es tan mala idea como un relacional sin índices. La clave de partición se estudia en Particionado y sharding.

7 · Ejercicio guiado

Objetivo: decidir el motor de cada pieza de un pequeño e-commerce aplicando el método "primero los accesos".

  1. Paso 1 — enumera los accesos. Escribe cada operación con su clave y su volumen: 
    A) Crear pedido y cobrar: transacción sobre order + stock + pago.
   → volumen: 50/s (pico 300/s). Necesita atomicidad fuerte.
B) Ver catálogo por categoría con filtros: por categoría, marca, precio.
   → volumen: 5 000/s. Filtros combinables → consultas variadas.
C) Buscar "zapatilla roja 42": texto libre + filtros.
   → volumen: 2 000/s. Relevancia y autocompletar.
D) Recomendar "quien compró X compró Y": recorrido de co-compra.
   → volumen: 500/s. Relaciones entre productos.
E) Carrito de sesión (usuario logueado o no): leer y escribir rápido.
   → volumen: 20 000/s. Solo por clave de sesión.
  2. Paso 2 — clasifica cada acceso por patrón. 
    A) Transaccional multi-entidad  → RELACIONAL (ACID, joins)
B) Filtros variados sobre atributos → RELACIONAL (índices) o BÚSQUEDA
C) Texto + relevancia            → BÚSQUEDA (índice invertido)
D) Relaciones multi-salto        → GRAFO
E) Clave → valor, altísimo QPS   → CLAVE-VALOR (con TTL)
  3. Paso 3 — decide y justifica cada elección. La conclusión esperada: cinco accesos, cinco patrones, arquitectura políglota, con el relacional como fuente de verdad del pedido y del stock, y el resto como proyecciones/capas especializadas.
  4. Paso 4 — resuelve la coherencia entre motores. El catálogo (relacional) debe reflejarse en el buscador; el carrito (KV) puede perderse sin drama. Anota el trade-off: el buscador tendrá un pequeño retraso respecto al relacional (consistencia eventual, Módulo 3), y eso es aceptable para catálogo pero no para el cobro.
  5. Paso 5 — reflexiona. ¿Podrías haberlo hecho todo con PostgreSQL? Sí para empezar (con búsqueda full-text nativa y una tabla de aristas). ¿A qué volumen dejaría de bastar? Cuando el QPS de E o el volumen de C lo exijan. Anota ese umbral: es tu ADR.
Resultado esperado

Un párrafo por acceso del tipo: "El carrito es solo GET/PUT session_id a 20 000 QPS; un KV con TTL lo sirve en <1 ms, y su pérdida ocasional es tolerable. Por eso va a KV, no a relacional." Decisión + número + trade-off aceptado. Ese es el formato de un ADR.

8 · Reto

🎯 El motor que lo hace todo (y por qué a veces basta)

Diseña un sistema de reseñas de productos con estos accesos: (1) crear reseña (única por usuario y producto); (2) listar las últimas 20 reseñas de un producto; (3) calcular la media de puntuación por producto; (4) buscar reseñas que contengan una palabra; (5) detectar usuarios que reseñan en círculo (A reseña lo de B, B lo de A, mismo patrón).

Primero propón una arquitectura con varios motores justificando cada uno. Después, responde: ¿puede un único PostgreSQL cubrir los cinco accesos? Si sí, ¿a partir de qué volumen (reseñas/segundo y tamaño total) dejaría de ser cómodo, y por qué acceso rompería primero?

Pista: para el acceso 3 piensa si una media se calcula ON READ (caro a escala) u ON WRITE (contador mantenido). Para el 5, un grafo recorre relaciones; un relacional lo hace con recursive CTEs, pero cada salto extra multiplica el coste. El umbral no lo fija el dato, lo fija tu SLO de latencia.

9 · Resumen

  • No existe "mejor" motor: existe un motor que encaja con tu patrón de acceso y tus garantías.
  • El relacional aporta joins, invariantes y ACID; empieza por él salvo que un acceso concreto pida otra cosa.
  • NoSQL son varias familias (documento, clave-valor, columnar, grafo, búsqueda), cada una óptima para un patrón.
  • Escribe los accesos primero: clave, forma, volumen, frecuencia. El motor se deduce después.
  • BASE (disponibilidad + consistencia eventual) es el trade-off de la escala horizontal, no un defecto.
  • Un sistema grande suele ser políglota: varios motores con una fuente de verdad clara.

10 · Preguntas frecuentes

¿Entonces NoSQL no es mejor para escalar?

Es mejor para escalar ciertos patrones (acceso por clave, escritura masiva) porque nace pensado para repartirse en muchos nodos. Pero "escalar" incluye el modelo y la operación: un relacional con réplicas y particionado bien hechos escala muchísimo más de lo que la gente cree. La pregunta útil no es "¿qué escala más?" sino "¿cuál encaja con mis accesos y mi equipo?".

¿Puedo empezar con un relacional y migrar después?

Sí, y suele ser lo sensato. Migrar de relacional a un motor especializado para un acceso es un proyecto acotado (crear una proyección, sincronizarla, leer de ella). Lo difícil es migrar de vuelta si te metiste en un modelo rígido que no soporta requisitos nuevos. Por eso: complejidad solo cuando un número la justifique.

¿Qué es eso de "polyglot persistence"?

Usar varios motores en un mismo sistema, cada uno para el patrón donde destaca (p. ej. relacional para pedidos, KV para carrito, búsqueda para catálogo). Es potente pero tiene coste: hay que sincronizar los motores y decidir cuál es la fuente de verdad. Si no puedes decir en una frase "el dato X vive en el motor Y y se copia a Z", no lo hagas todavía.

¿Un motor de búsqueda puede ser mi base de datos principal?

Normalmente no. Los motores de búsqueda están optimizados para consultar, no para ser la fuente de verdad transaccional: históricamente han tenido garantías de durabilidad y transacción más débiles y unos costes de indexación altos. El patrón habitual es: relacional (verdad) → se sincroniza → buscador (consulta). Así el buscador puede reconstruirse entero en cualquier momento.

¿Cómo sé cuándo debo añadir un segundo motor?

Cuando un acceso concreto incumple tu SLO y el motor actual no puede arreglarlo de forma sencilla: la consulta es de otro tipo (texto, grafo), el QPS de lectura es enorme y solo por clave, o el volumen de escritura satura. Si el problema se resuelve con un índice, una caché o una réplica de lectura, casi siempre es mejor eso que añadir un motor entero al sistema.
