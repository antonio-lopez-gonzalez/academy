Skills: el cómo reutilizable

Módulo 3 · Specs para agentes ⏱ 30 minutos
Curso relacionado

Para ver las skills construyendo agentes (MCP, tools, evals), el curso Aprende IA dedica su módulo 6 a la extensibilidad: «Skills (SKILL.md)».

1 · Introducción

Si AGENTS.md es la puerta del repo, una skill es el manual del oficio colgado junto a ella: una spec reutilizable de cómo se hace una clase entera de tareas («cómo se diseña una API», «cómo se construye un curso Academy», «cómo se escribe SDD»). La escribes una vez y cada hilo la invoca cuando la necesita.

En esta lección aprenderás qué es un SKILL.md, cómo se relaciona con la spec del producto (el qué) y con AGENTS.md (la puerta), y escribirás una skill mínima de verdad.

¿Por qué existe esta pieza? Porque sin skills cada hilo reinventa el oficio: un día el agente documenta APIs de una forma, al día siguiente de otra. La skill fija el cómo una sola vez, versionado en Git, y deja que cada spec se concentre en el qué de su funcionalidad.

Errores típicos: confundir skill con spec de producto, escribir skills gigantes que nadie invoca, o activar skills irrelevantes que contaminan el contexto (ver lección 03).

2 · Teoría

Un SKILL.md tiene una cabecera (name + description) que sirve para activarlo: el agente lee la descripción y decide si la tarea de hoy encaja. El cuerpo es la spec del oficio: vocabulario, plantillas, pasos, anti-patrones. Piensa en la diferencia así:

Analogía: la spec del producto es la receta de esta cena (qué plato, para quién, sin gluten); la skill es el manual de técnica culinaria (cómo se hace un sofrito, cómo se templa chocolate) que sirve para cien cenas. AGENTS.md es el cartel de la puerta que dice dónde están los manuales.

El flujo en un hilo real: el prompt de hoy dice «implementa etiquetas según la delta-spec» (el qué concreto); AGENTS.md ordena leer la spec y la skill SDD; la skill aporta cómo se escribe una delta-spec y cómo se verifica. Ninguno de los tres sobra.

Las skills de este curso son el ejemplo vivo: academy-course (cómo construir la web: mapa, anatomía HTML, SITE_BASE), spec-driven-development (qué enseñar: vocabulario, ciclo, plantillas) y documentation (cómo consultar docs oficiales). AGENTS.md las lista en su orden de lectura: la puerta apunta a los manuales.

3 · Ejemplo mínimo

La skill más pequeña que funciona: 15 líneas que fijan cómo escribir mensajes de commit en un repo.

---
name: commit-style
description: Use when writing a git commit message in this repo.
---

# Commit style


Format: `<type>: <short imperative summary>` (max 72 chars).


Allowed types: feat, fix, docs, refactor, test, chore.


Body (optional): explain WHY, not what — the diff already shows what.


Never commit secrets, `data/*.json` stores, or auto-generated files.

Línea por línea: la cabecera dice cuándo activarla («al escribir un commit»); el formato elimina variación inútil; los tipos cerrados evitan inventos («update», «misc»); el cuerpo exige el porqué porque el qué ya lo muestra el diff; y el anti-patrón protege lo irreversible (secretos versionados). Quince líneas que valen para mil commits.

4 · Ejemplo real

La skill spec-driven-development de este curso es una skill real de oficio: define el vocabulario SDD, el ciclo specify → plan → implement → verify y las plantillas de spec, criterios, ADR y delta-spec. Las lecciones la obedecen; este es su núcleo (extracto fiel, no inventado):

---
name: spec-driven-development
description: Use when writing lesson content or the Lumen sample project.
---

## Core vocabulary

- **Spec**: versioned document stating *what* and *why*, with acceptance criteria.
  It is NOT a prompt, a ticket, a README, or a design doc.
- **Skill (`SKILL.md`)**: reusable *how-to-work* spec for a class of tasks.
  Product spec = *what*; skill = *how*.
- **Verify**: checking the implementation *against the spec*, not "it compiles".

Y esta es la spec de producto con la que se combina: el contrato del CLI de Lumen (estable en todas las lecciones):

## CLI contract (spec/lumen.md)

- `node src/cli.js add "comprar pan"` crea una nota `{ id, title, done, createdAt }`.
- `node src/cli.js list` lista las notas abiertas.
- `node src/cli.js close <id>` marca una nota como cerrada.

El prompt que une ambas en el hilo de hoy:

Siguiendo la skill spec-driven-development (plantilla de spec + estilo
Dado/Cuando/Entonces) y la spec `spec/lumen.md` (contrato CLI de arriba),
escribe la delta-spec del comando `tag`: estado actual, estado deseado
con criterios verificables, impacto y migración.

Observa el reparto: la skill aporta cómo se escribe una delta-spec (plantilla, estilo de criterios); la spec aporta qué existe hoy (contrato CLI); el prompt solo dice qué pieza toca. El prompt no sustituye a ninguno de los dos: sin la skill, cada delta-spec saldría con otro formato; sin la spec, el agente inventaría el CLI.

6 · Errores habituales

Skill que en realidad es una spec de producto

# ❌ Disfrazada: habla de UNA funcionalidad, no de una clase de trabajo
# "Cómo implementar el botón de exportar de Lumen paso a paso…"
# Esto es una spec (o un plan). Morirá con la funcionalidad.

# ✅ Skill de verdad: sirve para cien botones, no para uno
# "Cómo exponer un comando del CLI: nombre en inglés, --help,
#  código de salida 0/1, criterio Dado/Cuando/Entonces por comando."

Descripción de activación inútil

# ❌ El agente no sabe cuándo invocarla
description: Utilidades varias para el desarrollo del proyecto.

# ✅ Gatillo concreto: tarea + artefacto
description: Use when writing a git commit message in this repo.

Skill gigante que compite con la puerta

# ❌ 150 líneas mezclando convenciones del repo, requisitos del
# producto y tutorial de git. Nadie la mantiene entera.

# ✅ Partir en tres: puerta (AGENTS.md, 20 líneas) + skill de oficio
# (esta clase de tarea) + spec del producto (esta funcionalidad).
# Cada pieza cambia a un ritmo distinto; júntalas y todo se pudre a la
# velocidad de lo que más cambia.

7 · Ejercicio guiado

Objetivo: escribir una skill mínima cli-command que fije cómo se añade un comando al CLI de Lumen.

  1. Paso 1: crea .agents/skills/cli-command/SKILL.md con cabecera name: cli-command y descripción «Use when adding a command to the Lumen CLI».
  2. Paso 2: escribe la plantilla: nombre en inglés, ficha en --help, salida por stdout, errores por stderr con código 1.
  3. Paso 3: exige un criterio Dado/Cuando/Entonces por comando, demostrable con node src/cli.js ….
  4. Paso 4: añade un anti-patrón: prohibido romper el formato { id, title, done, createdAt } sin delta-spec.
  5. Paso 5: referencia la skill desde el AGENTS.md de Lumen (una línea en el orden de lectura).

Resultado esperado: un SKILL.md de 20–30 líneas que, invocado con «añade el comando reopen según la skill cli-command y la spec», produce un comando con ayuda, criterio verificable y formato de nota intacto. Prueba de fuego: dos comandos escritos en hilos distintos con la misma skill deben parecerse entre sí sin que nadie lo pida en el chat.

8 · Reto

🎯 Skill de review de specs

Escribe la skill spec-review: checklist para revisar cualquier spec antes de implementar (ambigüedad, no-verificable, alcance hinchado, secreto colado). Debe caber en 30 líneas y funcionar aplicada a la spec de Lumen y a otra spec cualquiera de tu trabajo.

Pista: cada ítem del checklist debe terminar en una pregunta que se responda con sí/no mirando solo la spec; si necesita preguntar al autor, el ítem está mal redactado.

9 · Resumen

  • Una skill es una spec del cómo para una clase entera de tareas; la spec de producto es el qué de una funcionalidad.
  • Cabecera name + description = gatillo de activación; cuerpo = vocabulario + plantillas + anti-patrones.
  • AGENTS.md apunta a las skills; el prompt del hilo las invoca para la tarea de hoy.
  • Una skill por clase de tarea, corta, versionada y con dueño; lo puntual vive en specs, no en skills.

10 · Preguntas frecuentes

¿En qué se diferencia una skill de un prompt guardado?

El prompt guardado congela una petición («haz X con estos ficheros»); la skill fija el oficio para cualquier petición de esa clase (plantilla, vocabulario, criterios). El prompt envejece con la tarea; la skill amortiza en todas las futuras.

¿Cuántas skills debe tener un repo?

Pocas: una por clase de trabajo que se repita (commits, comandos CLI, reviews, diseño de API…). Si tienes veinte skills, la mayoría son specs disfrazadas o granularidad inventada. Empieza con una y parte solo cuando duela.

¿Quién escribe las skills, el humano o el agente?

El agente puede proponer el borrador observando cómo trabajas; el humano la aprueba y es su dueño. Igual que con la spec: el agente redacta, el humano posee. Una skill sin dueño se pudre.

¿Las skills sustituyen a la documentación oficial?

No: la complementan. La skill dice cómo trabajamos aquí (nuestra plantilla, nuestro estilo); la doc oficial dice qué permite la herramienta. Por eso AGENTS.md lista también la skill documentation: antes de afirmar un flag, se consulta la fuente.

¿Cómo sé que una skill se ha quedado obsoleta?

Dos síntomas: los hilos la invocan y luego hay que corregir lo mismo a mano (la plantilla ya no describe el trabajo real), o nadie la invoca en semanas (la clase de tarea murió o cambió de nombre). En ambos casos se actualiza o se archiva con fecha, nunca se deja pudrirse en silencio.
