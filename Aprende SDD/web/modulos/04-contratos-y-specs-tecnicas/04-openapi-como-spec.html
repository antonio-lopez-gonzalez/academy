OpenAPI como spec en una lección

Módulo 4 · Contratos y specs técnicas ⏱ 30 minutos

1 · Introducción

En esta lección entenderás OpenAPI como lo que es para SDD: un contrato de API que genera clientes, valida peticiones y documenta sin esfuerzo extra. No es un tutorial completo de OpenAPI: es la comparativa que te permite decidir cuándo un esquema JSON ya no basta y necesitas un contrato de API.

Lo usarás cuando Lumen (o cualquier producto) exponga su inbox por HTTP: el CLI y la web dejan de compartir un fichero y pasan a hablar por una API cuya forma promete OpenAPI.

¿Por qué existe esta lección? Porque las APIs acordadas «de palabra» se rompen en silencio: alguien renombra un campo, el cliente sigue pidiendo lo viejo y el error aparece en el usuario, no en el verify. OpenAPI pone la promesa por escrito y la ejecuta: valida, genera código y delata divergencias antes del despliegue.

Errores típicos de esta pieza: tratar OpenAPI como «documentación que se escribe al final», inventarse campos de memoria, o usarlo para una CLI local que no lo necesita.

2 · Teoría

OpenAPI es un formato estándar para describir una API HTTP: qué rutas existen, qué recibe cada una y qué devuelve. Piénsalo como JSON Schema con superpoderes de API: donde el esquema valida un dato, OpenAPI valida una conversación entera (petición + respuesta + rutas).

Analogía: si JSON Schema es el contrato de cómo es una carta (papel, idioma, firma), OpenAPI es el contrato de la oficina de correos: qué ventanillas hay (paths), qué formulario pide cada una y qué resguardo devuelve. Con la carta sola no montas el servicio; con el servicio descrito, cualquiera puede enviar cartas sin preguntar.

El patrón estable (lo único que afirmamos aquí)

Un documento OpenAPI gira siempre alrededor de tres bloques estables, presentes en todas las versiones:

  • openapi: qué versión del formato usa el documento (la portada que dice «esto es OpenAPI»).
  • info: título y descripción humana de la API (qué servicio es y para qué).
  • paths: las rutas (/notes, /notes/{id}…) con sus operaciones y sus datos.

Todo lo demás (componentes reutilizables, seguridad, validaciones finas) existe y es útil, pero cambia entre versiones y herramientas. Si dudas de un campo concreto, consulta la documentación oficial antes de ponerlo en tu spec: esta lección enseña el patrón, no la sintaxis de memoria.

OpenAPI en el ciclo SDD: se escribe en specify (la API se diseña antes de codificarse), genera esqueletos en implement y valida peticiones reales en verify. Y cuando cambia, cambia con delta-spec: una ruta nueva es un cambio con impacto y migración, no un commit silencioso.

Lo que OpenAPI no promete (a propósito)

El contrato garantiza forma, no fondo: que GET /notes existe y devuelve una lista con forma de notas, no que las notas sean las correctas ni que cerrar funcione. Esa capa semántica vive en los criterios de aceptación y los escenarios BDD (lección 03). Por eso un VERIFY completo combina ambos: validador de API en verde + criterios de producto en verde. Uno sin el otro es media verificación con confianza entera.

Tres usos ejecutables del contrato

  • Generar clientes: la web obtiene su cliente HTTP desde el contrato, sin copiar rutas a mano.
  • Validar peticiones y respuestas: cada llamada real se comprueba contra lo prometido en paths.
  • Burlar (mock) la API: el frontend avanza con un doble generado mientras el servidor aún no existe.

Los tres usan el mismo documento: por eso el contrato es fuente de verdad y no «documentación».

3 · Ejemplo mínimo

El contrato de API más pequeño que dice algo: existe una ruta /notes en una API llamada Lumen. Solo el patrón estable, nada más:

{
  // openapi: declara que este documento es un contrato OpenAPI
  "openapi": "3.1.0",
  // info: título humano de la API (para quién la lee, no para la máquina)
  "info": { "title": "Lumen API", "version": "1.0.0" },
  // paths: las rutas que la API promete servir (aquí, solo listar notas)
  "paths": {
    "/notes": {}
  }
}

Línea por línea:

  1. openapi: la portada. Dice a las herramientas «trátame como contrato OpenAPI», no como JSON cualquiera.
  2. info: el nombre del servicio. Parece decorativo, pero es lo que el cliente generado mostrará: la spec también se lee.
  3. paths: el corazón: cada clave es una promesa de que esa ruta existe. Vacía aún, pero la promesa ya está firmada.

Por qué funciona: hasta este esqueleto ya ordena el trabajo: el agente no puede «inventar» que la ruta se llama /note en singular sin contradecir el contrato. La discusión «¿cómo se llama la ruta?» muere aquí, no en el código.

4 · Ejemplo real

Lumen crece: la web ya no lee el fichero directamente, sino una API con dos rutas. El contrato promete listar y crear notas con la misma forma del esquema de la lección 01:

{
  // openapi: versión del formato del documento (portada del contrato)
  "openapi": "3.1.0",
  // info: qué API es y en qué versión va su promesa
  "info": { "title": "Lumen API", "version": "1.0.0" },
  // paths: las dos promesas de esta versión: listar y crear notas
  "paths": {
    // GET /notes: devuelve la lista de notas (las de schema/note.schema.json)
    "/notes": {},
    // POST /notes: crea una nota a partir de un título
    "/notes/create": {}
  }
}

Decisiones explicadas:

  • ¿Por qué solo dos rutas? Porque la spec actual de Lumen solo necesita listar y crear por API; close sigue siendo CLI. Cada ruta es una promesa de mantenimiento: no se prometen rutas «por si acaso».
  • ¿Por qué el contrato cita la Nota de la lección 01? Porque los datos de la API son las notas { id, title, done, createdAt }. Reutilizar el mismo esquema evita dos verdades paralelas (la del fichero y la de la API) que divergen en una semana.
  • ¿Por qué no detallamos aquí cada campo y código de estado? Porque esta lección es comparativa, no un tutorial completo: el patrón (openapi / info / paths) te orienta; los detalles se consultan en la documentación oficial y se fijan en tu spec con su versión declarada.

Y el valor ejecutable, en una línea: desde este contrato se generan clientes y se validan peticiones reales. El criterio de aceptación ya no dice «la API funciona», dice:

# el contrato genera y comprueba: si la API se desvía, el VERIFY lo pilla
# generate: crea el cliente a partir del contrato (sin escribirlo a mano)
# validate: comprueba una petición real contra lo prometido en paths
npx openapi-generator-cli generate -i lumen.openapi.json -o clients/web
node scripts/validate-api.mjs lumen.openapi.json

6 · Errores habituales

❌ OpenAPI como documentación póstuma

# ❌ flujo invertido: el código manda, el contrato transcribe
# 1. el agente implementa rutas inventadas (/note, /getNotes, ...)
# 2. alguien "documenta" lo que salió escribiendo el openapi a posteriori
# resultado: el contrato bendice el caos en vez de ordenarlo

✅ Contrato primero, código después

# ✅ flujo spec-first: el contrato dirige, el VERIFY comprueba
# 1. se acuerda lumen.openapi.json (paths: /notes, /notes/create)
# 2. el agente implementa contra el contrato y genera el cliente
# 3. validate-api.mjs comprueba que lo servido coincide con lo prometido
node scripts/validate-api.mjs lumen.openapi.json

Por qué estaba mal: el contrato póstumo no decide nada: solo congela decisiones ya tomadas sin criterio. El valor de OpenAPI está en prometer antes para poder verificar después.

❌ Usar OpenAPI donde basta JSON Schema

# ❌ sobrediseño: Lumen local (CLI + fichero) no tiene rutas ni clientes HTTP
# Un contrato OpenAPI para "add/list/close" locales añade ceremonia
# sin counterparts: no hay peticiones que validar ni clientes que generar.
# ✅ ahí basta schema/note.schema.json (lección 01).

7 · Ejercicio guiado

Objetivo: escribir el contrato mínimo de la API de Lumen y decidir qué promete.

  1. Paso 1: crea lumen.openapi.json con los tres bloques del ejemplo mínimo (openapi, info, paths).
  2. Paso 2: añade a paths exactamente dos entradas: /notes (listar) y /notes/create (crear). Nada de close por API: sigue siendo CLI.
  3. Paso 3: en info, pon título «Lumen API» y versión «1.0.0». Anota en un comentario qué significa esa versión (la de la promesa, no la del código).
  4. Paso 4: escribe un criterio de aceptación: «Dado el contrato, cuando se genera el cliente, entonces el cliente expone listar y crear contra esas rutas».

Resultado esperado: un lumen.openapi.json con los tres bloques y dos rutas, más un criterio que nombra el comando de generación/validación. Si tu contrato promete rutas que la spec no pide, recorta: cada ruta es deuda de compatibilidad.

JSON o YAML, sin dogma: ambos describen el mismo patrón (openapi / info / paths). Aquí usamos JSON para comparar lado a lado con el esquema de la Nota. Lo importante es versionarlo en Git y validarlo en CI, no la extensión.

8 · Reto

🎯 Diseña la delta de `close` por API

Escribe una delta-spec de una página: ¿qué ruta prometerías para cerrar notas por API, qué impacto tiene en los clientes actuales (que hoy solo listan y crean) y qué estrategia de compatibilidad usarías? No implementes nada.

Pista: el Módulo 5 te dará la plantilla (estado actual → deseado → impacto → migración); adelanta su espíritu: ¿rompe a alguien lo que propones?

9 · Resumen

  • OpenAPI es el contrato de una API HTTP: promete rutas y valida la conversación (petición + respuesta).
  • El patrón estable es openapi + info + paths; los detalles se consultan en la documentación oficial, no se inventan.
  • Su valor ejecutable: genera clientes y valida peticiones reales en el VERIFY.
  • Se diseña en specify, no se transcribe al final; cada ruta nueva es una delta con impacto.
  • Para datos en disco basta JSON Schema; para APIs con clientes, OpenAPI; para decisiones, ADR.

10 · Preguntas frecuentes

¿Esta lección me enseña OpenAPI completo?

No, a propósito: es una comparativa, no un tutorial. Te llevas el patrón (contrato de API que genera y valida), el criterio de cuándo usarlo y la disciplina de consultar la documentación oficial para la sintaxis exacta. Un tutorial completo ocuparía un curso entero y envejecería con cada versión.

¿Lumen necesita OpenAPI?

El Lumen actual (CLI + fichero local), no: le basta JSON Schema. OpenAPI entra cuando la inbox se expone por HTTP a varios clientes. La lección usa esa evolución hipotética para que compares: elegir el contrato adecuado es una decisión de diseño, digna de ADR.

¿Qué versión de OpenAPI uso?

La estable que soporten tus herramientas (validador y generador), declarada en el campo openapi y en tu spec. No la afirmes de memoria: compruébala en la documentación oficial el día que la uses. El patrón de esta lección no depende de la versión menor.

¿OpenAPI sustituye a los criterios de aceptación?

No. OpenAPI garantiza que la conversación tiene la forma prometida; los criterios garantizan que el producto hace lo debido. Una API puede validar perfecta y devolver notas equivocadas. Contrato válido más criterios verdes: eso es VERIFY completo.

¿Cómo le pido al agente que implemente contra el contrato?

Mostrándole el contrato, no contándoselo: «implementa el servidor según lumen.openapi.json (rutas /notes y /notes/create); verifica con el generador y el validador del criterio». El prompt cita la spec de la que sale, como exige el curso: el prompt no sustituye al contrato, lo invoca.
