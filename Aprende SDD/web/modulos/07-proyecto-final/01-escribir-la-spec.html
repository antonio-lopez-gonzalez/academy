Escribir la spec de Lumen

Módulo 7 · Proyecto final ⏱ 35 minutos

1 · Introducción

En esta lección vas a escribir la spec completa de Lumen: una bandeja de notas mínima (inbox) con una CLI en Node.js que crea, lista y cierra notas sobre un almacén JSON local. Es el mismo producto que has visto evolucionar en los módulos 0–6; ahora lo cierras de punta a punta.

Existe porque es la primera fase del ciclo specify → plan → implement → verify: sin una spec que otro agente pueda implementar sin adivinar, todo lo demás (plan, código, verificación) se apoya en aire.

Se utiliza al inicio de cualquier pieza de trabajo, y se revisa por un humano antes de planificar. Errores típicos: escribir la solución en vez del problema, olvidar los no-objetivos, y redactar criterios que no se pueden demostrar con un comando.

Por qué empezar por la spec y no por el código

El código registra qué se hizo; la spec registra qué se quería y cómo se demuestra. Cuando el agente de turno (o tú dentro de tres meses) dude, la spec gana la discusión. Por eso la spec es la fuente de verdad, no el chat ni el código.

2 · Teoría

Una spec es un documento versionado que dice qué se quiere y por qué, con criterios de aceptación observables. No es un prompt (una instrucción de usar y tirar en un chat), ni un ticket (una tarea con dueño y fecha), ni un README (una explicación para el lector futuro).

La anatomía que usamos en este curso —y que Lumen sigue— tiene seis piezas:

  • Objetivo: 1–2 frases con verbos observables. Qué y para qué.
  • No-objetivos: lo que queda fuera explícitamente. Es la pieza más barata contra la invención del agente.
  • Glosario: lenguaje ubicuo. Si “cerrar” y “borrar” se confunden, habrá bugs.
  • Restricciones: stack, compatibilidad, presupuesto (técnico o de negocio).
  • Supuestos: lo que damos por hecho, escrito para poder rebatirlo.
  • Criterios de aceptación: frases Dado / Cuando / Entonces demostrables sin leerle la mente al implementador.
┌──────────┐ ┌──────┐ ┌───────────┐ ┌────────┐ │ SPECIFY │───▶│ PLAN │───▶│ IMPLEMENT │───▶│ VERIFY │ │ intention│ │ path │ │ code │ │ vs spec│ └──────────┘ └──────┘ └───────────┘ └────────┘ ▲ │ └────────── diverge? update the SPEC ─────────┘
Analogía: el plano del edificio

Decirle al albañil en el pasillo “hazme una cocina práctica” es un prompt. El plano con medidas, materiales y cotas de entrega es una spec: dos equipos distintos construyen la misma cocina. Lumen es nuestra cocina: pequeña, pero con plano completo.

Restricciones y supuestos también deciden

Las restricciones (“Node.js LTS + JavaScript vanilla, sin frameworks”) impiden que el agente proponga React para un inbox. Los supuestos (“un solo usuario, sin concurrencia”) hacen explícito lo que se da por hecho para que alguien pueda rebatirlo. Sin ambas secciones, el agente decide la arquitectura por ti.

Dónde vive la spec de Lumen

En el repo del producto: proyectos/lumen/spec/lumen.md. La spec vive en Git, junto al código, y evoluciona con él. Referencia además el contrato schema/note.schema.json y el ADR spec/adr/0001-almacen-json.md.

3 · Ejemplo mínimo

La spec más pequeña posible que sigue siendo spec: objetivo, un no-objetivo y un criterio demostrable.

# Inbox de notas (mini)

## Objetivo
Guardar ideas con un comando y listarlas después.

## No-objetivos
- No hay sincronización entre máquinas.

## Criterios de aceptación
- [ ] Dado el almacén vacío, cuando ejecuto `add`, entonces `list` muestra la nota.

Línea por línea:

  • # Inbox… — el título nombra la pieza, no la tecnología.
  • ## Objetivo — verbos observables: guardar, listar. Nada de “práctico” o “bonito”.
  • ## No-objetivos — cierra la puerta más tentadora (sincronizar) antes de que el agente la imagine.
  • Criterios… — contexto (almacén vacío) + acción (add) + resultado observable (list la muestra). Se demuestra con comandos, no con opiniones.

4 · Ejemplo real

La spec completa de Lumen que usarás en el proyecto final. Cada decisión está explicada debajo. Este es el documento que el plan (lección 02) y la implementación (lección 03) deben obedecer.

proyectos/lumen/spec/lumen.md
# Lumen — bandeja de notas mínima (inbox)

## Objetivo
Lumen guarda ideas rápidas desde la terminal y permite
listarlas y cerrarlas. Una nota es `{ id, title, done, createdAt }`.

## No-objetivos
- Sin sincronización ni red: solo almacén local.
- Sin edición de texto enriquecido ni adjuntos.
- Sin autenticación ni multiusuario.
- Sin interfaz web en esta versión (solo CLI).

## Glosario
- nota: una idea con `id`, `title`, `done` y `createdAt`.
- cerrar: marcar `done = true`. No borra la nota.
- almacén: fichero `data/notes.json` con un array de notas.

## Restricciones
- Node.js (LTS) + JavaScript vanilla, sin frameworks.
- El almacén se valida contra `schema/note.schema.json`.
- Rutas de ejemplo en formato Linux (`data/notes.json`).

## Supuestos
- Un solo usuario por almacén; no hay concurrencia.
- Los `id` son únicos y estables (nunca se reutilizan).

## CLI
- `node src/cli.js add "texto"` — crea una nota.
- `node src/cli.js list` — lista las notas.
- `node src/cli.js close <id>` — cierra una nota por su id.
- `node src/cli.js --help` — muestra la ayuda.

## Criterios de aceptación
- [ ] Dado el almacén vacío, cuando ejecuto `add "comprar pan"`,
      entonces `list` muestra una nota con ese título y `done = false`.
- [ ] Dado que existe una nota abierta, cuando ejecuto `close <id>`
      con su id, entonces `list` la muestra con `done = true`.
- [ ] Dado un `id` inexistente, cuando ejecuto `close <id>`,
      entonces el CLI falla con un error y no modifica el almacén.
- [ ] Dado cualquier estado, cuando ejecuto `--help`,
      entonces se muestran los cuatro comandos con ejemplos.
- [ ] Dado el almacén tras cualquier comando, cuando lo valido contra
      `schema/note.schema.json`, entonces la validación pasa.

## Fuera de alcance del plan
- Etiquetas y búsqueda (delta posterior, ver lección 04).
- UI web: solo lectura del mismo almacén, fuera de esta spec.

Decisiones clave y su porqué:

  • Cerrar ≠ borrar: el glosario lo fija porque es la ambigüedad que más bugs produce. Cerrar marca done; borrar eliminaría la fila y rompería la auditoría del inbox.
  • Contrato validable: el último criterio convierte el esquema JSON en juez automático. Por eso la spec cita schema/note.schema.json: lo que una máquina puede comprobar no depende de opiniones.
  • El error es criterio: el tercer criterio especifica el comportamiento ante un id inexistente. Sin él, cada implementador inventa el suyo (silencio, crash, nota fantasma).
  • tags no aparece: las etiquetas son el delta de la lección 04. Adelantarlas aquí contaminaría la spec base y rompería el contrato estable { id, title, done, createdAt }.
Por qué cada criterio cita comandos reales

Si un criterio no se puede demostrar con un comando o un fichero en el repo de Lumen, hay que reescribirlo. “El CLI es usable” no es verificable; “close <id> marca done = true” sí.

Por qué la spec cita el esquema y el ADR

La spec de Lumen no describe el JSON campo por campo: apunta a schema/note.schema.json (contrato máquina-comprobable) y al ADR spec/adr/0001-almacen-json.md (por qué JSON local y no SQLite). Cada artefacto responde una pregunta distinta; duplicarlos en la spec garantiza que diverjan.

6 · Errores habituales

❌ Mal “Lumen es un inbox de notas fácil de usar con sincronización futura y buen diseño.”

Está mal porque: “fácil”, “buen diseño” y “futura” no se pueden demostrar con ningún comando; además diseña de más (sincronización) sin comprometerse.

✅ Bien “Dado el almacén vacío, cuando ejecuto add "comprar pan", entonces list muestra la nota con done = false.”

Otras trampas clásicas al escribir esta spec:

  • ❌ Prompt disfrazado: pegar el historial del chat y llamarlo spec. No tiene no-objetivos ni criterios. ✅ Reescribirlo con la plantilla de seis piezas.
  • ❌ Diseño prematuro: “usar una clase NoteManager con singleton”. ✅ La spec dice qué; el plan y el código deciden el cómo.
  • ❌ Secretos en la spec: incluir rutas absolutas personales o tokens “para probar”. ✅ La spec solo contiene rutas relativas al repo (data/notes.json); los secretos nunca se versionan.
  • ❌ Filtrar tags antes de tiempo: añadir el campo en la spec base “por si acaso”. ✅ El contrato estable es { id, title, done, createdAt }; las etiquetas llegan como delta versionado.

7 · Ejercicio guiado

Escribe tú la spec de Lumen en proyectos/lumen/spec/lumen.md y comprueba que un compañero (o un agente) puede implementarla sin preguntar.

  1. Copia la plantilla de seis piezas (objetivo, no-objetivos, glosario, restricciones, supuestos, criterios) en spec/lumen.md.
  2. Redacta el objetivo en 1–2 frases con verbos observables (guardar, listar, cerrar).
  3. Añade 4 no-objetivos como mínimo: red, adjuntos, multiusuario, UI web.
  4. Fija el glosario: define “cerrar” explícitamente como marcar done sin borrar.
  5. Escribe 5 criterios en formato Dado/Cuando/Entonces, uno por cada comando más la validación contra el esquema.
  6. Auto-revisión: por cada criterio, escribe el comando que lo demuestra. Si alguno no tiene comando, reescríbelo.

Resultado esperado: un fichero spec/lumen.md de unas 40–60 líneas donde cada criterio se puede verificar con node src/cli.js add "texto" | list | close <id> | --help más la validación contra schema/note.schema.json. Sin la palabra tags en todo el documento.

8 · Reto

Endurece la spec sin engordarla

Añade a tu spec los criterios de aceptación para estos dos casos límite: título vacío en add y almacén corrupto (JSON inválido en data/notes.json). Máximo 6 líneas nuevas en total, sin contradecir ningún criterio existente.

Pista: piensa en “falla con un error y no modifica el almacén” como patrón reutilizable, y decide si el caso merece criterio o no-objetivo.

9 · Resumen

  • La spec es la fuente de verdad: versionada en Git, anterior al plan y al código.
  • Seis piezas: objetivo, no-objetivos, glosario, restricciones, supuestos y criterios verificables.
  • Cada criterio debe demostrarse con un comando o un fichero; si no, se reescribe.
  • El contrato de Lumen es estable: { id, title, done, createdAt }; tags solo llega como delta.

10 · Preguntas frecuentes

¿No es más rápido empezar por el código si Lumen es tan pequeño?

Es más rápido la primera tarde y más lento el primer cambio. Sin spec, cada decisión (“¿cerrar borra?”) se re-discute en cada sesión. La spec de Lumen cabe en una página; su coste es minutos y su ahorro es cada futura discusión con un agente.

¿Quién escribe la spec: yo o el agente?

El agente puede redactar el borrador, pero el humano es el dueño: revisa y aprueba antes del plan. Un agente no puede decidir no-objetivos de negocio por ti.

¿Dónde va la ayuda (--help) en la spec?

En la sección CLI y en un criterio propio: “cuando ejecuto --help, entonces se muestran los cuatro comandos con ejemplos”. La ayuda es comportamiento observable, no decoración.

¿Por qué la spec prohíbe la UI web en vez de simplemente no mencionarla?

Porque “no mencionado” lo lee un agente como “permitido si sobra tiempo”. Un no-objetivo explícito cierra la puerta; el silencio la entreabre. Por eso los no-objetivos nombran malentendidos plausibles.

¿Cómo sé que mi spec está terminada?

Pasa el test del comando: cada criterio tiene un comando que lo demuestra, cada no-objetivo nombra algo que alguien pediría de verdad, y un agente distinto al que la escribió puede implementarla sin hacer preguntas. Si falla alguna de las tres, la spec sigue en borrador.
