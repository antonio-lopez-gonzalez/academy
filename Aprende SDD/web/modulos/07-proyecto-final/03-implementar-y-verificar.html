Implementar y verificar

Módulo 7 · Proyecto final ⏱ 35 minutos

1 · Introducción

En esta lección vas a implementar el CLI de Lumen siguiendo la spec y el plan, y a verificar cada criterio con comandos reales. Implementar sin verificar es solo escribir; verificar sin spec es solo opinar.

Existe porque la definition of done vive en la spec, no en “compila” ni en “parece funcionar”. Verificar significa demostrar cada criterio Dado/Cuando/Entonces con un comando y su salida.

Se utiliza al final de cada implementación y antes de dar nada por terminado. Errores típicos: probar solo el camino feliz, verificar leyendo el código en vez de ejecutarlo, y parchear el código cuando lo que está mal es la spec.

Por qué verificar contra la spec y no contra tu intuición

Tu intuición recuerda lo que querías; la spec recuerda lo que pediste. Solo la spec permite que otra persona (o un agente) compruebe lo mismo que tú con los mismos comandos. Por eso “terminado” significa “cada criterio demostrado”, nada menos.

2 · Teoría

Implementar es escribir código obedeciendo spec + plan, en el orden que el plan fijó. Verificar es comprobar el resultado contra cada criterio de la spec, con comandos reales y salidas observables. Son dos fases distintas: mezclarlas produce código que “casi cumple” sin que nadie sepa qué falta.

El bucle de divergencia manda:

  • Si el código no cumple la spec y la spec tiene razón → se corrige el código.
  • Si el código no cumple la spec y la spec estaba mal → se corrige primero la spec (en Git, con motivo) y luego el código. Nunca se parchea el código a ciegas.
IMPLEMENT (spec + plan) ──▶ VERIFY (criterio × criterio) cumple ──▶ hecho diverge ──▶ ¿quién tiene razón? spec ──▶ fix código código ──▶ fix spec primero
Analogía: la entrega del edificio

El plano decía tres enchufes por habitación: la entrega consiste en contarlos, no en admirar la pintura. Verificar Lumen es igual: ejecutar cada comando de la spec y contar los resultados, incluido el que debe fallar.

El camino feliz no basta

Los criterios de error (id inexistente) y de contrato (validación contra el esquema) son los que distinguen una demo de una entrega. Si solo pruebas add y list, no has verificado: has hecho turismo.

Por qué el orden del plan protege la implementación

Si implementas close antes de que add funcione, no puedes probarlo sin inventar datos a mano. El orden esquema → almacén → add → list → close garantiza que cada paso se prueba con la salida real del anterior, no con fixtures imaginarios.

3 · Ejemplo mínimo

Implementar y verificar en su forma más pequeña: un comando y su comprobación.

# Implemento el paso 3 del plan (comando add) y lo verifico:
node src/cli.js add "pan"   # creo la nota
node src/cli.js list         # compruebo: "pan" aparece con done = false

Línea por línea:

  • add "pan" — ejecuta el comportamiento que la spec promete (crear).
  • list — demuestra el resultado observable (la nota existe y está abierta).
  • El criterio queda marcado solo si la salida coincide con lo esperado; si no, hay divergencia y se decide quién tiene razón (spec o código).

El almacén (extracto de src/cli.js)

La implementación de referencia lo mantiene todo en un único src/cli.js (módulos ESM, cero dependencias); estas son sus funciones de almacén:

proyectos/lumen/src/cli.js — loadNotes / saveNotes
// Lee y escribe data/notes.json; toda escritura valida el contrato.
import fs from "node:fs";
import path from "node:path";

// Relativo al directorio de trabajo (donde se ejecuta el CLI).
const STORE_PATH = path.join("data", "notes.json");

// Lee el almacén; si no existe, devuelve el inbox vacío.
function loadNotes() {
  if (!fs.existsSync(STORE_PATH)) return [];
  const raw = fs.readFileSync(STORE_PATH, "utf8");
  return JSON.parse(raw); // JSON corrupto → error claro, sin sobrescribir
}

// Guarda las notas; si alguna rompe el esquema, falla sin escribir.
function saveNotes(notes) {
  assertValid(notes); // valida contra schema/note.schema.json
  fs.writeFileSync(STORE_PATH, JSON.stringify(notes, null, 2) + "\n");
}

El CLI (extracto del mismo src/cli.js)

proyectos/lumen/src/cli.js — main / addNote / closeNote
// Punto de entrada del CLI de Lumen: interpreta el comando y delega.
// Usa loadNotes/saveNotes del mismo fichero (definidas arriba).

function main(args) {
  const [command, ...rest] = args;
  if (command === "add") return addNote(rest.join(" "));
  if (command === "list") return listNotes();
  if (command === "close") return closeNote(rest[0]);
  if (command === "--help" || !command) return showHelp();
  fail(`comando desconocido: ${command}`); // falla sin tocar el almacén
}

// Crea una nota con id único y done = false.
function addNote(title) {
  if (!title) fail("el título no puede estar vacío");
  const notes = loadNotes(); // lee data/notes.json
  const note = { id: makeId(), title, done: false, createdAt: new Date().toISOString() };
  notes.push(note);
  saveNotes(notes); // valida contra el esquema al guardar
  console.log(`nota creada: ${note.id}`);
}

// Marca done = true; con id inexistente falla sin modificar nada.
function closeNote(id) {
  const notes = loadNotes();
  const note = notes.find((n) => n.id === id);
  if (!note) fail(`nota no encontrada: ${id}`);
  note.done = true;
  saveNotes(notes);
  console.log(`nota cerrada: ${id}`);
}

Verificación: cada criterio, su comando, su salida

# Criterio 1 — crear y listar:
node src/cli.js add "comprar pan"
# salida esperada: nota creada: <id>
node src/cli.js list
# salida esperada: la nota "comprar pan" con done = false

# Criterios 2 y 3 — cerrar y error ante id inexistente:
node src/cli.js close <id>
# salida esperada: nota cerrada: <id> (y list la muestra con done = true)
node src/cli.js close no-existe
# salida esperada: error "nota no encontrada" y data/notes.json sin cambios

# Criterio 4 — ayuda:
node src/cli.js --help
# salida esperada: describe add, list, close y --help con ejemplos

# Criterio 5 — contrato (el almacén sigue siendo JSON válido):
node --input-type=module -e "import fs from 'node:fs'; JSON.parse(fs.readFileSync('data/notes.json','utf8')); console.log('almacén válido')"
# salida esperada: almacén válido

Por qué esta verificación es suficiente: cubre los cinco criterios sin excepción, incluye el caso de error, y termina con la validación máquina-comprobable del contrato. Si un comando diverge de su salida esperada, el bucle decide: ¿está mal el código o estaba mal la spec?

6 · Errores habituales

❌ Mal “Funciona: he creado una nota y se ve bien.”

Está mal porque: no cita ningún criterio, no muestra comandos ni salidas, y “se ve bien” no es observable. ¿Y el close? ¿Y el id inexistente? ¿Y el esquema?

✅ Bien “Criterio 3: node src/cli.js close no-existe falla con ‘nota no encontrada’ y data/notes.json queda intacto. ✅”

  • ❌ “Compila, luego está hecho”: el CLI arranca pero nadie ejecutó los cinco criterios. ✅ Hecho = cinco ✅, uno por criterio.
  • ❌ Inventar tags al implementar: “ya que estoy, añado etiquetas”. ✅ Fuera de alcance: el contrato es { id, title, done, createdAt } hasta el delta de la lección 04.

7 · Ejercicio guiado

Implementa el CLI y verifica los cinco criterios sin saltarte ninguno.

  1. Prepara el repo: crea schema/note.schema.json y src/cli.js (comandos + funciones de almacén) según el plan.
  2. Implementa en orden: esquema → almacén → add → list → close → --help.
  3. Verifica el criterio 1: node src/cli.js add "comprar pan" y confirma en list que aparece con done = false.
  4. Verifica los criterios 2 y 3: cierra la nota con su id; luego prueba con un id inexistente y confirma el error sin cambios en el almacén.
  5. Verifica los criterios 4 y 5: ejecuta --help y valida data/notes.json contra el esquema.
  6. Registra el resultado: marca cada criterio con ✅ o ❌ y anota la salida real de cada comando.

Resultado esperado: cinco ✅ con sus cinco evidencias (salidas de add, list, close, --help y la validación del esquema), más un data/notes.json que valida sin errores. Si hay un ❌, el informe dice si se corrige código o spec.

8 · Reto

Escribe el informe de verificación

Redacta un verify.md de una página: tabla criterio → comando → salida → ✅/❌, más la decisión ante cada ❌ (fix código o fix spec). No lo resolvemos aquí.

Pista: el formato que cuesta leer es el que nadie relee; una tabla de 5 filas con comandos copiables vale más que tres párrafos.

9 · Resumen

  • Implementar = obedecer spec + plan en orden; verificar = demostrar cada criterio ejecutando.
  • Hecho significa todos los criterios en ✅, incluido el error y el contrato.
  • Ante divergencia: si la spec tiene razón se arregla el código; si estaba mal, se arregla primero la spec en Git.

10 · Preguntas frecuentes

¿Puedo verificar con tests automatizados en vez de comandos a mano?

Sí, y es recomendable: los tests son specs ejecutables. Pero deben mapear 1:1 con los criterios de la spec; un test que no cita su criterio es tan opaco como “se ve bien”.

¿Qué hago si un criterio es imposible de demostrar?

Reescribirlo. Un criterio sin comando ni fichero que lo demuestre no es un criterio, es un deseo. Vuelve a la spec, reformúlalo en observable y versiona el cambio.

¿Y si el agente implementa algo mejor que la spec?

Si es mejor de verdad, se promociona: se actualiza la spec en Git con el motivo y luego se acepta el código. Lo que nunca se hace es aceptar la mejora en silencio y dejar la spec mintiendo.

¿La UI web opcional cuenta como verificación?

No en esta versión: la spec la declara no-objetivo. Si la construyes, verifica solo que lee el mismo almacén sin modificarlo; no sustituye a ninguno de los cinco criterios del CLI.

¿Dónde anoto la evidencia de cada criterio?

En un verify.md junto a la spec: tabla de criterio → comando → salida → ✅/❌. Es la prueba de que “terminado” significa algo comprobable por terceros, no tu recuerdo de la sesión.
