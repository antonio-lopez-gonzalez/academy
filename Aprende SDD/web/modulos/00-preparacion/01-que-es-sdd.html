Qué es Spec-Driven Development

Módulo 0 · Preparación ⏱ 30 minutos

1 · Introducción

Piensa en tu última sesión con un agente de código: le pediste algo en el chat, generó código que funcionaba… y una semana después nadie recuerda por qué el código hace lo que hace. El chat se evaporó, el código quedó, la intención se perdió. Si ahora le pides un cambio al mismo agente (o a otro distinto), tiene que adivinar lo que ya se decidió una vez.

Ese es el problema que resuelve Spec-Driven Development (SDD): la intención del proyecto —qué se quiere, qué queda fuera, cómo se demuestra que está hecho— vive en un artefacto versionado (la spec), no en un hilo de chat que nadie puede recuperar. En esta lección entenderás qué es una spec, qué es SDD, por qué importa justo ahora que los agentes escriben código, y cuál es el ciclo de trabajo que usaremos en todo el curso.

¿Por qué existe esta lección? Porque todo el curso cuelga de una sola idea: la spec es la fuente de verdad. Si no interiorizas qué es una spec y por qué el chat no puede serlo, cada lección posterior (planes, contratos, ADRs, deltas) parecerá burocracia. Esta base te ahorra el error más caro del curso: tratar la spec como «documentación que se escribe después».

2 · Teoría

El problema: el chat se evapora

El chat con un agente tiene tres defectos estructurales como memoria del proyecto:

  • Es efímero: se pierde entre sesiones, no tiene historial revisable y no se puede enlazar desde el código.
  • Es ambiguo por diseño: mezcla decisiones, intentos fallidos, correcciones y contexto pegado a toda prisa. Nada dice qué parte sigue vigente.
  • No se puede verificar: «lo hablamos» no es un criterio contra el que comprobar nada. Nadie puede demostrar que el código cumple «lo que se dijo».

El resultado: cada cambio nuevo empieza de cero, el agente rellena los huecos inventando comportamiento, y el humano corrige a mano lo que «yo no pedí». Eso tiene un nombre en este curso: under-spec (lo verás a fondo en el módulo 6).

La definición: qué es una spec

Una spec (especificación) es un documento versionado que declara qué se quiere y por qué, con criterios de aceptación observables. Tres matices importan desde el día uno:

  • Versionada: vive en el repo, junto al código, con historial de Git. Cada decisión tiene fecha, autor y motivo.
  • Observable: usa verbos que se pueden demostrar («el CLI lista las notas abiertas ordenadas por fecha») y no adjetivos que no se pueden demostrar («que quede bonito», «rápido» sin números).
  • Fuente de verdad: es el artefacto que gana las discusiones. Ni el chat, ni «lo que el código hace hoy», ni la memoria de nadie.

Analogía: planos frente a instrucciones de pasillo. Construir con SDD es construir con planos: un documento que el arquitecto firma, el constructor ejecuta y el inspector verifica. Pedir cosas en el chat es darle instrucciones al albañil de palabra, en el pasillo: funciona para colgar un cuadro, pero no para levantar un edificio. Cuando algo sale mal, con planos sabes quién decidió qué; de palabra, cada uno recuerda una conversación distinta.

Qué es SDD, en una frase

SDD = la intención vive en un artefacto versionado que un humano y un agente pueden ejecutar. «Ejecutar» aquí tiene dos sentidos, y ambos importan: un humano puede leerla y saber qué hacer sin adivinar, y un agente puede recibirla como contexto y producir código que la cumple sin inventar. Si una spec no sirve para ninguno de los dos, no es una spec: es prosa.

Por qué ahora: el código lo escribe (a menudo) un agente

Antes, la especificación informal «vivía» en la cabeza del programador mientras escribía el código: la intención y la implementación nacían juntas. Con un agente de código en medio, esa cadena se rompe: quien decide (tú) ya no es quien teclea (el agente). Y un agente sin spec no se detiene a preguntar lo importante: rellena los huecos con lo más probable, que rara vez es lo que querías. La spec es el contrato que vuelve a unir intención e implementación cuando hay una máquina en medio.

El ciclo SDD: specify → plan → implement → verify

SDD no es «escribir un documento y olvidarse». Es un ciclo de cuatro fases que recorrerás en cada lección del curso:

┌──────────┐    ┌──────┐    ┌───────────┐    ┌────────┐
│ SPECIFY  │───▶│ PLAN │───▶│ IMPLEMENT │───▶│ VERIFY │
│ intención│    │ camino│    │ código    │    │ vs spec│
└──────────┘    └──────┘    └───────────┘    └────────┘
      ▲                                            │
      └────── ¿diverge? actualiza la SPEC ─────────┘
  • Specify: se escribe la spec. El agente puede redactar un borrador, pero el humano es el dueño.
  • Plan: se propone el camino (pasos, ficheros, riesgos, fuera de alcance) antes de escribir código. Saltarse el plan es el modo de fallo número uno.
  • Implement: se escribe el código siguiendo la spec y el plan.
  • Verify: se comprueba cada criterio de aceptación. Si la spec estaba mal, se corrige primero la spec: nunca se parchea el código a ciegas.

Nota: este ciclo es el esqueleto del módulo 2, donde lo diseccionaremos fase por fase. Por ahora quédate con la forma: un bucle, no una cascada. La flecha de vuelta («¿diverge? actualiza la spec») es lo que mantiene la spec viva cuando el producto cambia.

3 · Ejemplo mínimo

La spec más pequeña que sigue siendo una spec: 14 líneas que describen una única capacidad. Léela línea por línea y fíjate en qué hace cada pieza.

# Recordar una nota                    
                                           
## Objetivo                               
Lumen guarda una nota con un título      
para no depender de la memoria del chat. 
                                           
## No-objetivos                           
- Sin etiquetas ni búsqueda              
- Sin sincronización entre máquinas      
                                           
## Criterios de aceptación               
- [ ] Dado un almacén vacío, cuando      
  ejecuto `lumen add "comprar pan"`,      
  entonces `lumen list` muestra la nota

¿Por qué esto sí es una spec y un mensaje de chat no? Porque tiene las tres propiedades de la definición: está pensada para versionarse (vive en spec/ con historial), todo en ella es observable (hay comandos que la demuestran), y puede actuar como fuente de verdad (si el agente añade búsqueda, la spec dice que no: estaba en no-objetivos).

4 · Ejemplo real

Mira el viaje completo de la misma idea en sus dos formas. Primero, como nace casi siempre: un párrafo en un chat.

# ❌ La intención atrapada en el chat (no es una spec)
hazme una app de notas sencilla, con CLI en node,
que guarde en un json o algo así, y que se puedan
cerrar las notas. Que quede limpia, porfa.

¿Qué pierde esta petición? Todo lo que un implementador necesita: ¿qué es «sencilla» (qué queda fuera)? ¿Qué forma tiene una nota? ¿Qué significa «cerrar»? ¿Cómo demuestro que «quedó limpia»? Cada hueco lo rellenará quien implemente, inventando. Y dentro de una semana, ni tú recordarás qué pediste exactamente.

Ahora la misma intención, convertida en spec versionada (extracto de la spec de Lumen, el caso de estudio de todo el curso, que conocerás en la lección 4):

# ✅ La misma intención, como artefacto versionado (spec/lumen.md)
## Objetivo
Lumen es una bandeja de notas mínima: capturar ideas rápido
y cerrarlas cuando dejan de estar pendientes.

## No-objetivos
- Sin etiquetas ni búsqueda (llegan como cambio en el módulo 5)
- Sin multiusuario ni sincronización en red
- Sin interfaz web obligatoria (el CLI es el producto; la web es opcional)

## Criterios de aceptación
- [ ] Dado un almacén vacío, cuando ejecuto `lumen add "comprar pan"`,
  entonces `lumen list` muestra una nota abierta con ese título
- [ ] Dada una nota abierta con id abc123, cuando ejecuto
  `lumen close abc123`, entonces `lumen list` ya no la muestra
  como abierta

Las decisiones clave de esta transformación:

  • «Sencilla» se volvió no-objetivos concretos: en vez de un adjetivo, hay una lista de lo que no se hará. Cada elemento es algo que un agente ambicioso habría añadido por su cuenta.
  • «Guardar en un json o algo así» se volvió criterio demostrable: no prescribe el formato interno (eso es diseño, y tiene su sitio: un ADR), pero exige un comportamiento que se puede ejecutar y comprobar.
  • «Que quede limpia» desapareció: y hace bien en desaparecer. No se puede demostrar, así que no puede estar en una spec. Lo que sí está es la lista exacta de comportamientos esperados.
  • Vive en spec/lumen.md, versionada con Git: dentro de tres meses, git log spec/lumen.md contará la historia de cada decisión. Ningún chat puede hacer eso.

5 · Buenas prácticas

HazEvitaPor qué
Escribir la spec antes de pedir código al agente Generar código y «documentarlo después» La spec guía las decisiones; escrita después solo describe lo que salió, incluidos los errores
Guardar la spec en el repo (spec/) con el código Dejarla en un wiki, un doc suelto o el historial del chat Spec y código evolucionan juntos: el diff de Git muestra cuándo divergieron y por qué
Usar verbos observables y criterios demostrables Adjetivos sin número («rápido», «limpio», «intuitivo») Solo lo observable se puede verificar; lo demás es una opinión que el agente interpretará a su manera
Declarar no-objetivos desde la primera versión Asumir que «lo obvio» no hace falta escribirlo Lo obvio para ti es invisible para el agente: los no-objetivos son la barandilla más barata
Recorrer el ciclo completo, incluido verify Parar en «compila y parece funcionar» «Compila» no es «cumple la spec»: verificar es lo que convierte código en entrega

6 · Errores habituales

Confundir «documentar» con «especificar»

# ❌ Esto es un README, no una spec: describe, no compromete
# Lumen es una app de notas hecha con Node.js.
# Usa un archivo JSON para guardar los datos.
# Ejecuta `lumen --help` para ver las opciones.

# ✅ Esto es una spec: declara qué DEBE pasar y cómo se demuestra
## Criterios de aceptación
- [ ] Dado un almacén vacío, cuando ejecuto `lumen add "comprar pan"`,
  entonces el almacén contiene una nota abierta con ese título

El README cuenta lo que hay; la spec declara lo que debe haber. Por eso el README se escribe después (describe el producto) y la spec antes (decide el producto). Las diferencias finas entre ambos las verás en la lección 2.

Pegar el chat y llamarlo spec

# ❌ Historial del chat pegado en un .md: prompt disfrazado de spec
# Usuario: hazme una app de notas sencilla...
# Agente: ¡Claro! He creado add, list, close y además search
#          con etiquetas porque me pareció útil...
# Usuario: vale, pero quita lo de etiquetas de momento

# ✅ Spec real: sin historia, sin intentos, solo decisiones vigentes
## Objetivo
Lumen es una bandeja de notas mínima: capturar y cerrar pendientes.

## No-objetivos
- Sin etiquetas ni búsqueda

El chat pegado conserva los intentos fallidos, las correcciones y las decisiones revertidas sin marcar qué sigue vigente. Fíjate además en el detalle revelador: el agente ya inventó etiquetas «porque le pareció útil». Eso es under-spec en estado puro, y es exactamente lo que una lista de no-objetivos habría impedido.

Escribir una spec que nadie puede verificar

# ❌ Criterios que no se pueden demostrar (¿cómo los compruebas?)
- [ ] El CLI es fácil de usar
- [ ] El código queda limpio y mantenible
- [ ] Funciona rápido con muchas notas

# ✅ El mismo spirito, en criterios demostrables
- [ ] `lumen --help` lista los comandos add, list y close con un
  ejemplo de uso para cada uno
- [ ] `lumen list` con 1000 notas responde en menos de 1 segundo
  en una máquina de desarrollo típica

Regla de oro de todo el curso: si no puedes escribir el comando que lo demuestra, reescribe el criterio. «Fácil de usar» se convierte en ayuda documentada con ejemplos; «rápido» se convierte en un número con un contexto de medida.

7 · Ejercicio guiado

Objetivo: convertir un párrafo de chat en una mini-spec versionada que otro agente podría implementar sin adivinar.

  1. Paso 1: crea la carpeta y el fichero donde vivirá la spec. Las specs viven en el repo, junto al código: 
    # Desde la raíz de tu proyecto de prueba
mkdir -p spec              # spec/ es la casa de las specs (ver lección 4)
git init 2>/dev/null; git status   # confirma que estás en un repo Git
  2. Paso 2: parte de este párrafo (típico mensaje de chat) y subraya cada hueco: ¿qué es ambiguo? ¿qué falta? ¿qué sobra por no demostrable? 
    # Párrafo de partida (NO lo copies como spec)
Quiero un comando que me diga cuántas notas tengo abiertas.
Que sea rápido y que se vea bien.
  3. Paso 3: escribe spec/count.md con objetivo (qué + porqué), 2 no-objetivos y 2 criterios de aceptación con formato Dado/Cuando/Entonces. Modelo de solución: 
    # Contar notas abiertas

## Objetivo
El comando `count` informa cuántas notas siguen abiertas
para saber de un vistazo si la bandeja está al día.

## No-objetivos
- Sin filtros por fecha ni por texto (eso es búsqueda, fuera de alcance)
- Sin formato decorado: salida de una sola línea legible por scripts

## Criterios de aceptación
- [ ] Dadas 3 notas abiertas y 2 cerradas, cuando ejecuto
  `lumen count`, entonces la salida es `3`
- [ ] Dado un almacén vacío, cuando ejecuto `lumen count`,
  entonces la salida es `0`
  4. Paso 4: versiona la spec y comprueba que Git la recuerda: 
    git add spec/count.md        # registra la intención, igual que el código
git commit -m "spec: comando count de Lumen"
git log --oneline -- spec/  # el historial de la intención, separado del código
  5. Paso 5 (verificación): resultado esperado comprobable — existe spec/count.md con las tres secciones (Objetivo, No-objetivos, Criterios), cada criterio nombra un comando exacto y una salida exacta, y git log -- spec/ muestra tu commit. Pásale tu spec a un compañero (o a un agente) y pregunta: «¿podrías implementarlo sin hacerme ninguna pregunta?». Si la respuesta es sí, la spec funciona.

8 · Reto

🎯 Rescata una intención perdida

Busca en tu propio historial (un chat con un agente, un ticket viejo, un mensaje de tu equipo) una petición de código de más de dos semanas. Sin mirar el código resultante, escribe su spec en spec/rescate.md: objetivo, 3 no-objetivos y 3 criterios Dado/Cuando/Entonces. Después compara tu spec con el código que realmente se escribió: marca cada divergencia (¿el código hace algo que tu spec prohíbe? ¿le falta algo que tu spec exige?) y decide, para cada una, si habría que corregir el código o la spec.

Pista: las divergencias donde «el código inventó algo útil» son las más instructivas — casi siempre revelan un no-objetivo que faltaba o un criterio que pedía existir.

9 · Resumen

  • El chat se evapora, el código queda, la intención se pierde: ese es el problema que SDD resuelve.
  • Una spec es intención en un artefacto versionado: qué + por qué + criterios observables.
  • SDD = trabajar con la spec como fuente de verdad, la que gana las discusiones.
  • Importa ahora porque el agente que escribe el código rellena huecos inventando: la spec cierra esos huecos por escrito.
  • El ciclo es specify → plan → implement → verify, con vuelta a la spec cuando hay divergencia.
  • Planos frente a pasillo: la spec se firma, se ejecuta y se verifica; el chat solo se recuerda (mal).
ArtefactoPara qué sirve
spec.md (la spec)Declara qué se quiere, qué queda fuera y cómo se demuestra; fuente de verdad
El planOrdena el camino de la spec al código antes de escribirlo (módulo 2)
Criterios de aceptaciónDefinen «hecho» de forma demostrable, sin leerle la mente a nadie
No-objetivosImpiden que el agente (o el humano) invente funcionalidad
El repo GitVersiona la intención junto al código: cada decisión tiene historia

10 · Preguntas frecuentes

¿No es SDD simplemente «escribir documentación antes de programar»?

No. La documentación describe lo que ya existe; la spec decide lo que debe existir y cómo se demuestra. Además la spec es ejecutable en un sentido en que la documentación no lo es: un agente puede recibirla como contexto y producir código que la cumple, y un humano puede verificar criterio por criterio. Si un documento no sirve para implementar ni para verificar, por bien escrito que esté, no es una spec.

¿SDD significa que ya no puedo programar de forma exploratoria?

Al contrario: SDD distingue explorar de entregar. Prototipa libremente en el chat todo lo que quieras (eso se llama vibe coding y tiene su lugar), pero antes de llevarlo a producción escribe la spec que el prototipo debería haber tenido. La regla del curso es: prototipo libre, spec antes de ship. Lo verás a fondo en el módulo 6.

¿Quién escribe la spec si el agente puede redactarla?

El agente puede redactar el borrador, pero el humano es el dueño: decide, firma y responde de ella. Delegar la redacción es eficiente; delegar la propiedad es abdicar. Si aceptas una spec generada sin leerla criterio por criterio, has vuelto al chat con pasos extra.

¿Vale cualquier formato para la spec o tiene que ser Markdown?

En este curso, Markdown en el repo: es texto plano (difiere bien en Git), lo lee cualquier editor y lo consume cualquier agente sin herramientas especiales. El formato exacto lo aprenderás en el módulo 1 (objetivo, no-objetivos, glosario, restricciones, criterios). Lo importante no es la sintaxis, sino las propiedades: versionada, observable, fuente de verdad.

¿Y si la spec está mal? ¿No es peor que no tener spec?

Una spec mala a la vista es mejor que una intención invisible: al menos se puede discutir, corregir y versionar. Por eso el ciclo tiene flecha de vuelta: cuando la implementación diverge porque la spec estaba mal, se corrige primero la spec y luego el código. El módulo 5 enseña exactamente ese gesto: actualizar la spec en Git con motivo, en vez de parchear a ciegas.
