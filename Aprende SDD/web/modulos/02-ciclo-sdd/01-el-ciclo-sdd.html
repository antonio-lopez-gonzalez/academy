Las cuatro fases del ciclo

Módulo 2 · El ciclo SDD ⏱ 30 minutos

1 · Introducción

Ya sabes escribir una spec (Módulo 1): objetivo, no-objetivos, glosario, restricciones y criterios de aceptación. Ahora viene la pregunta que decide si esa spec sirve de algo: ¿cómo se trabaja con ella? La respuesta es un ciclo de cuatro fases — specify → plan → implement → verify — que se repite en cada funcionalidad y en cada cambio.

En esta lección aprenderás qué hace cada fase, quién decide qué en cada una (humano o agente), por qué el ciclo es un bucle con retorno a la spec (no una cascada de una sola pasada) y por qué saltarse el plan es el modo de fallo nº 1 cuando se trabaja con agentes de código.

¿Por qué existe esta lección? Porque la mayoría de fracasos con agentes no son problemas del modelo: son problemas de proceso. Pedir código directamente en el chat equivale a construir sin planos. El ciclo SDD existe para que la intención quede escrita antes de codificar, el camino se revise antes de ejecutarse y el resultado se compruebe contra lo escrito — no contra lo que cada uno recuerda haber pedido.

2 · Teoría

El bucle completo

┌──────────┐    ┌──────┐    ┌───────────┐    ┌────────┐
│ SPECIFY  │───▶│ PLAN │───▶│ IMPLEMENT │───▶│ VERIFY │
│ intention│    │ path │    │ code      │    │ vs spec│
└──────────┘    └──────┘    └───────────┘    └────────┘
      ▲                                            │
      └────────── diverge? update the SPEC ─────────┘

Cada vuelta del bucle transforma intención en código verificado. La flecha de retorno es lo que lo distingue de una cascada: si al verificar descubres que la spec estaba mal, actualizas la spec primero y vuelves a girar. Nunca se parchea el código a ciegas contra una spec que ya sabes que está equivocada.

Quién decide qué en cada fase

FasePregunta que respondeQuién proponeQuién decide
Specify¿Qué queremos y por qué?El humano, o el agente como borradorEl humano (es el dueño del producto)
Plan¿En qué orden, con qué riesgos, qué queda fuera?El agenteEl humano (revisa y aprueba el plan)
Implement¿Cómo se escribe el código?El agente (o el humano)La spec + el plan aprobado
Verify¿Cumple cada criterio de la spec?El agente con checklist, o el humanoLa spec (es el árbitro)

La regla de oro: el agente nunca es el product owner. Puede redactar, proponer y ejecutar, pero las decisiones de qué se quiere y de si el plan es aceptable las toma un humano. El agente tampoco es el árbitro final: el árbitro es la spec escrita.

Analogía: construir una casa. Specify son los planos visados (qué se construye). Plan es el plan de obra (orden de gremios, materiales, qué no se toca). Implement es la obra. Verify es la inspección final contra los planos. Nadie aceptaría «dile al albañil en el pasillo lo que quieres y cruza los dedos»: eso es pedir código en el chat sin spec ni plan.

Por qué no se salta el plan (modo de fallo nº 1)

Pasar de la spec al código sin plan es el error más caro y más común. ¿Por qué? Porque la spec dice qué, pero no dice en qué orden tocar los ficheros, qué riesgos hay (migraciones, compatibilidad, secretos), ni qué queda explícitamente fuera. Sin plan, el agente toma esas decisiones solo — y las toma de la forma más probable estadísticamente, no de la forma correcta para tu proyecto.

  • El plan hace visibles los malentendidos baratos: corregir un paso del plan cuesta segundos; corregir código ya escrito cuesta horas y deja deuda.
  • El plan acota el blast radius: dice qué ficheros se tocan y cuáles no. Sin esa lista, un cambio pequeño se derrama por todo el repo.
  • El plan ordena el riesgo: lo irreversible y lo incierto van primero (o se aíslan), no se descubren a mitad de la implementación.
  • El plan es revisable por un humano en 5 minutos; un diff de 800 líneas generado sin plan, no.

Síntoma de que te saltaste el plan: el agente entrega algo que «casi» es lo pedido, con dos o tres decisiones inventadas («añadí también…», «asumí que querías…»). Cada «asumí» es un paso del plan que nadie escribió ni revisó. La cura no es un mejor prompt: es un plan aprobado antes del código.

El ciclo no es cascada: cuándo se vuelve atrás

Se vuelve a specify cuando la verificación revela que la spec estaba mal (un criterio imposible, un supuesto falso, un no-objetivo que sí hacía falta). Se vuelve a plan cuando la implementación revela un riesgo no contemplado (un fichero acoplado, una migración olvidada). Volver atrás no es fracasar: es el mecanismo que impide que el error se congele en código. Lo que está prohibido es volver atrás de memoria, sin dejar constancia en la spec.

3 · Ejemplo mínimo

El ciclo entero, en miniatura, para una funcionalidad trivial: un comando ping en el CLI. Fíjate en que cada fase produce un artefacto distinto.

# SPECIFY → spec/ping.md (qué se quiere)
## Objetivo
# El CLI responde "pong" al comando ping.
## Criterios de aceptación
- [ ] Dado el CLI instalado, cuando ejecuto `ping`,
      entonces imprime `pong` y sale con código 0.

# PLAN → plan/ping.md (cómo se hará, sin código aún)
1. Añadir subcomando `ping` en `src/cli.js` (solo lectura).
2. Riesgo: ninguno (no toca el almacén).
3. Fuera de alcance: banderas, red, telemetría.

# IMPLEMENT → código (sigue spec + plan)
# VERIFY → `node src/cli.js ping` imprime `pong` (criterio ☑ / ☐)

Línea por línea: la spec ocupa 5 líneas y ya contiene un criterio comprobable; el plan ocupa 3 líneas y ya declara orden, riesgo y fuera de alcance; la implementación aún no existe (el plan se revisa antes); la verificación es un comando concreto, no una opinión («creo que funciona»).

Por qué este ejemplo importa: demuestra que el ciclo no es burocracia para proyectos grandes. Incluso para 5 líneas de spec, separar qué (spec), cómo y en qué orden (plan) y cómo lo compruebo (verify) evita que el agente invente banderas, telemetría o formatos de salida que nadie pidió.

4 · Ejemplo real

El mismo ciclo aplicado a Lumen, la bandeja de notas del curso: el comando close, que marca una nota como hecha. Aquí el plan ya no es trivial, porque toca el almacén compartido data/notes.json.

# spec/lumen-close.md (extracto)
## Objetivo
# Cerrar una nota existente por su id sin borrarla.
## Criterios de aceptación
- [ ] Dado el almacén con la nota `abc123` abierta,
      cuando ejecuto `close abc123`, entonces `done` pasa a `true`.
- [ ] Dado un id inexistente, cuando ejecuto `close zzz`,
      entonces falla con mensaje a stderr y código distinto de 0.

# plan/lumen-close.md (extracto)
1. Leer `data/notes.json` y localizar la nota por `id` (fallar si no existe).
2. Poner `done=true` y reescribir el fichero (escritura atómica).
3. Verificar con `list`: la nota sigue existiendo y aparece como cerrada.
Riesgos: escritura concurrente (fuera de alcance v1, documentar supuesto).
Fuera de alcance: borrar notas, cerrar varias a la vez, confirmación interactiva.

Decisiones explicadas: el plan fija la semántica de error (stderr + código ≠ 0) antes de que el agente elija una al azar; declara la escritura atómica como requisito porque el almacén es un fichero compartido; y deja la concurrencia como supuesto explícito en vez de fingir que está resuelta. Todo eso se revisa en 2 minutos sobre el plan; descubrirlo en el diff sería 10 veces más caro.

Conexión con el Módulo 1: la spec de close usa objetivo, criterios Dado/Cuando/Entonces y supuestos explícitos — las piezas que aprendiste en las lecciones de anatomía. El ciclo de este módulo es cómo se usa esa anatomía.

6 · Errores habituales

❌ Spec → código, sin plan

# ❌ El modo de fallo nº 1: del "qué" al código sin camino revisado
# chat> "aquí tienes la spec, impleméntala"

# ✅ Spec → plan (revisado) → código
# chat> "aquí tienes la spec; propón el plan: pasos, ficheros,
#          riesgos y fuera de alcance. No escribas código aún."

Por qué está mal: el agente decide el orden, el alcance y los riesgos sin supervisión. La versión correcta inserta una revisión humana barata (el plan) antes del trabajo caro (el código).

❌ Verificar con «compila y parece funcionar»

# ❌ "Compila, lo doy por bueno"
# node src/cli.js close abc123   # ¿y? ¿qué criterio demuestra esto?

# ✅ Cada criterio, una comprobación concreta
# node src/cli.js close abc123 && node src/cli.js list | grep abc123
# → la nota existe y aparece como cerrada (criterio 1 ☑)
# node src/cli.js close zzz; echo $?   # → código ≠ 0 (criterio 2 ☑)

Por qué está mal: «compila» no es un criterio de la spec. La versión correcta ejecuta una comprobación por criterio y deja constancia del resultado.

❌ Tratar el ciclo como cascada de una sola pasada

Escribir la spec, implementar, y negarse a tocar la spec cuando la verificación revela que estaba mal («la spec ya está aprobada»). Por qué está mal: congela el error en código. La versión correcta: si la spec estaba mal, se corrige la spec primero (con su commit y su motivo) y se vuelve a girar el ciclo.

7 · Ejercicio guiado

Objetivo: recorrer el ciclo completo para una funcionalidad mínima de Lumen: el comando list con filtro de abiertas.

  1. Specify (5 min): escribe spec/lumen-list-open.md con 1 objetivo y 2 criterios: (a) list --open muestra solo notas con done=false; (b) con el almacén vacío, sale con código 0 e imprime lista vacía, sin error.
  2. Plan (5 min): escribe plan/lumen-list-open.md con 3 pasos (leer almacén, filtrar, imprimir), 1 riesgo (formato de salida: decide tabla o JSON y fíjalo) y 1 fuera de alcance (paginación).
  3. Revisión del plan (2 min): relee tu plan buscando un «asumí»: ¿fijaste el formato de salida? ¿el orden? Si hay algo implícito, escríbelo antes de seguir.
  4. Implement (10 min): implementa (tú o con un agente) siguiendo solo spec + plan. Si surge algo no contemplado, anótalo: no lo decidas en silencio.
  5. Verify (5 min): ejecuta una comprobación por criterio y marca ☑/☐ en la spec.

Resultado esperado: dos ficheros versionables (spec/lumen-list-open.md con 2 criterios ☑ y plan/lumen-list-open.md con pasos + riesgo + fuera de alcance) y dos comandos de verificación ejecutados, uno por criterio. Si algún criterio queda ☐, el resultado esperado incluye además la decisión escrita: ¿se corrige el código o se corrige la spec?

8 · Reto

🎯 Detecta un ciclo saltado

Busca en tu historial reciente (un chat con un agente, una PR, un ticket) un caso donde se pasó del «qué» al código sin plan escrito. Reconstruye a posteriori: escribe en 10 líneas el plan que debería haberse aprobado (pasos, un riesgo, un fuera de alcance) y señala qué decisión inventada sobre la marcha te habría ahorrado.

Pista: busca las palabras «asumí», «también añadí» o «pensé que querías» — cada una es un paso del plan que faltó.

9 · Resumen

  • El ciclo SDD es specify → plan → implement → verify, con retorno a la spec cuando hay divergencia.
  • Specify: el humano decide el qué; plan: el agente propone y el humano aprueba; implement: se sigue spec + plan; verify: la spec arbitra.
  • Saltarse el plan es el modo de fallo nº 1: el agente decide orden, alcance y riesgos sin revisión.
  • El plan es el último punto barato para corregir; el código ya escrito es caro.
  • Volver atrás (a spec o a plan) no es fracasar: es el mecanismo que impide congelar errores en código.
ArtefactoPara qué sirve
Spec (spec/*.md)Fija el qué y el porqué; es la fuente de verdad y el árbitro final
Plan (plan/*.md)Fija pasos, orden, riesgos y fuera de alcance; se revisa antes del código
Código (src/)Implementa spec + plan, nada más

10 · Preguntas frecuentes

¿El ciclo no es demasiado proceso para cambios pequeños?

No: el ciclo se escala al tamaño del cambio. Para un ping son 8 líneas de spec + plan (lo viste en el ejemplo mínimo). El coste del ciclo es proporcional; el coste de no hacerlo — decisiones inventadas, re-trabajo — aparece incluso en cambios pequeños. Ciclos pequeños, frecuentes y baratos.

¿Quién escribe la spec, el humano o el agente?

El agente puede redactar el borrador, pero el humano es el dueño: decide el qué, aprueba la spec y responde del porqué. Un agente no puede ser product owner porque no conoce el negocio ni asume las consecuencias. Delega la redacción, nunca la decisión.

¿Plan mode significa que el agente no toca código?

Exacto durante la fase de plan: propone pasos, ficheros, riesgos y fuera de alcance, y espera aprobación. Puede leer el repo para informar el plan, pero no escribir código hasta que el humano apruebe. Lo verás en detalle en la lección 03.

¿Cuándo termina un ciclo? ¿Cuándo puedo decir «hecho»?

Cuando todos los criterios de aceptación están verificados con comprobaciones concretas (lección 04). «Compila», «parece funcionar» o «el agente dice que está listo» no terminan un ciclo: solo la checklist ☑ contra la spec.
