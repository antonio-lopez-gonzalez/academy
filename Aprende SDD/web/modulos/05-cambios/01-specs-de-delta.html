Specs de delta: estado actual → deseado

Módulo 5 · Cambios ⏱ 30 minutos

1 · Introducción

Casi todo el trabajo real de un desarrollador no es crear algo de cero, sino cambiar algo que ya existe: añadir etiquetas, cambiar un formato, soportar un caso nuevo. En esta lección aprenderás a escribir una spec de delta: una spec pequeña que describe un cambio sobre un sistema vivo, sin reescribir la spec completa del producto.

Por qué existe: porque el cambio sin contexto es la primera fuente de regresiones. Cuando pides a un agente «añade etiquetas» sin decirle cómo es el sistema hoy, qué debe seguir funcionando y cómo migran los datos viejos, el agente inventa. La delta-spec cierra esas tres puertas.

La usarás cada vez que toques un sistema en producción: una funcionalidad nueva, un ajuste de contrato, una migración de datos. Error típico de esta pieza: reescribir la spec entera para un cambio de veinte líneas, o al revés, describir solo lo nuevo y olvidar lo que ya existe.

En el repo, cada delta vive en su propio fichero numerado dentro de spec/changes/ (por ejemplo 0001-tags.md) y se anuncia con una línea en spec/changelog.md. ¿Por qué un fichero por cambio y no un apéndice creciente? Porque cada cambio se revisa, se aprueba, se revierte y se entiende por separado: el fichero es la unidad de decisión, igual que el commit lo es en Git.

2 · Teoría

Una spec de producto describe cómo debe ser el sistema. Una delta-spec describe cómo pasar de A a B: parte del estado actual (verificable hoy), define el estado deseado (verificable mañana) y documenta el camino (impacto + migración). Es como la diferencia entre el plano de un edificio terminado y el plano de una reforma: la reforma necesita mostrar qué paredes ya existen, cuáles se tiran y dónde duermen los inquilinos mientras dura la obra.

Por qué no basta con reescribir la spec completa

Reescribir el mundo para cada cambio tiene tres costes: pierdes el historial de por qué cambió cada cosa, obligas al revisor a releerlo todo para encontrar el cambio real, y le das al agente una superficie enorme donde desviarse. La delta-spec es un parche con contexto: apunta a la spec base, cambia solo lo necesario y deja rastro en Git. El ciclo sigue siendo el mismo (specify → plan → implement → verify), pero el specify es incremental.

La plantilla de una delta-spec tiene cuatro bloques (skill de SDD, §6):

BloqueQué contienePor qué importa
Estado actualCómo se comporta el sistema hoy, con referencias a ficheros y comandosEl agente (y el revisor) parten de hechos, no de recuerdos
Estado deseadoCómo debe comportarse, con criterios de aceptaciónSin esto no hay forma de verificar el cambio
Impacto y compatibilidadQué se rompe, qué migra, qué sigue compatibleAquí viven las regresiones si no se escriben
MigraciónPasos, orden y vuelta atrás (rollback)Un cambio sin plan de vuelta atrás es una apuesta

Guárdala siempre en la misma plantilla para que cualquier lector (humano o agente) sepa dónde mirar:

# Cambio: <título del cambio, no del producto>

## Estado actual
<cómo se comporta hoy, con ficheros y comandos>

## Estado deseado
<cómo debe comportarse, con criterios de aceptación>

## Impacto y compatibilidad
<qué se rompe / migra / sigue compatible>

## Migración
<pasos, orden y vuelta atrás>
Analogía: la receta que ya estás cocinando

Una spec greenfield es una receta desde cero. Una delta-spec es una nota pegada en la nevera: «la sopa de ayer (estado actual) + añade jengibre y sirve en dos cuencos (estado deseado); los cuencos viejos siguen valiendo (compatibilidad); si queda sosa, añade caldo, no sal (migración y rollback)».

3 · Ejemplo mínimo

La delta-spec más pequeña posible: doce líneas que cambian un comportamiento sin reescribir nada más.

# Cambio: `list` muestra las abiertas primero

## Estado actual
- `node src/cli.js list` lista las notas en orden de creación (ver `spec/lumen.md` §4).

## Estado deseado
- [ ] Dado 3 notas (2 abiertas, 1 cerrada), cuando ejecuto `list`, entonces las abiertas salen primero.

## Impacto y compatibilidad
- Ninguna rotura: el formato de salida no cambia, solo el orden.

## Migración
- Sin migración de datos. Desplegar y verificar con `list` sobre `data/notes.json` de ejemplo.

Línea por línea: el título nombra el cambio, no el producto. El estado actual cita la spec base (§4) para que cualquiera pueda comprobarlo. El estado deseado es un solo criterio verificable (Dado/Cuando/Entonces). El impacto declara explícitamente que no hay rotura —ese «nada se rompe» escrito vale más que el silencio—. La migración dice «no hace falta», que también es una decisión documentada.

4 · Ejemplo real

El caso de esta lección: añadir etiquetas (tags) a Lumen. Hoy una nota es { id, title, done, createdAt } y el CLI solo sabe add, list y close <id>. Queremos etiquetar notas y filtrar por etiqueta, sin romper ni una sola nota existente. 

# Cambio: etiquetas y filtrado en Lumen

## Estado actual
- Nota: `{ id, title, done, createdAt }` (ver `schema/note.schema.json`).
- `node src/cli.js add "comprar pan"` crea una nota sin etiquetas.
- `node src/cli.js list` lista todas las notas, sin filtros.

## Estado deseado
- [ ] Dado `add "comprar pan" --tags compra,casa`, cuando listo, entonces la nota guarda `tags: ["compra", "casa"]`.
- [ ] Dado notas con y sin etiquetas, cuando ejecuto `list --tag compra`, entonces solo salen las de esa etiqueta.
- [ ] Dado un `data/notes.json` antiguo (notas sin `tags`), cuando ejecuto cualquier comando, entonces funciona como antes.

## Impacto y compatibilidad
- `tags` es opcional: las notas viejas siguen válidas (el esquema lo marca como no requerido).
- `list` sin `--tag` se comporta exactamente igual que antes.
- Sin cambios en `close` ni en el formato del fichero.

## Migración
1. Ampliar `schema/note.schema.json` con `tags` opcional.
2. Añadir `--tags` a `add` y `--tag` a `list` (ver `src/cli.js`).
3. No migrar datos: las notas sin `tags` se leen como «sin etiquetas».
4. Vuelta atrás: revertir el commit; los datos nunca se reescriben con `tags` obligatorios.

Decisiones explicadas: tags es opcional porque obligarlo rompería todas las notas existentes (más sobre esto en la próxima lección). El tercer criterio protege explícitamente el almacén viejo: es el criterio que el agente olvidaría si no lo escribes. La migración dice «no migrar datos» a propósito —la ausencia de migración también se especifica—. Y la vuelta atrás es trivial porque el cambio es aditivo: nada irreversible.

El prompt sale de la spec, no al revés

Con esta delta-spec, el prompt al agente es de una línea: «implementa spec/changes/0001-tags.md siguiendo el plan habitual». Si el agente propone algo raro, la discusión vuelve a la spec, no al chat.

Y cuando la delta se verifica, la spec base se pone al día: lumen.md pasa a describir notas con tags opcional y cita 0001-tags.md como origen. Así la base siempre describe el presente y spec/changes/ conserva el pasado.

6 · Errores habituales

❌ Solo describir lo nuevo. «Añadir --tags a add» sin decir qué pasa con las notas viejas. El agente decide por ti: quizá reescribe el fichero y corrompe datos. ✅ Añade siempre el criterio «con datos antiguos, todo funciona como antes».

❌ Reescribir la spec entera para un cambio pequeño. Copias lumen.md, editas dos líneas y nadie sabe qué cambió. ✅ Una delta-spec que apunta a la base: el diff es el cambio.

❌ Migración mágica. «Actualizar el esquema» sin decir en qué orden, ni qué pasa si falla a mitad. ✅ Pasos numerados, orden explícito y rollback de una línea.

❌ Delta sin estado actual. Empezar directamente en «quiero que…» porque «todos sabemos cómo funciona Lumen». El agente nuevo del equipo no lo sabe, y el de dentro de seis meses tampoco. ✅ Dos líneas de contexto con referencias verificables, siempre.

❌ Guardar la delta solo en el chat. Discutir el cambio en el hilo del agente y no dejar fichero. Cuando el hilo se evapora, el motivo del cambio se pierde. ✅ La delta vive en spec/changes/000N-nombre.md y el changelog la cita.

7 · Ejercicio guiado

Escribe la delta-spec del cambio «búsqueda por texto en Lumen» (list --search pan). Sigue estos pasos:

  1. Describe el estado actual en dos líneas: qué hace list hoy y dónde está especificado.
  2. Escribe dos criterios con Dado/Cuando/Entonces: uno para búsqueda con resultados y otro para búsqueda sin resultados (¿qué debe pasar: lista vacía o error?).
  3. Declara el impacto: ¿cambia el formato de salida? ¿afecta a close? Escríbelo aunque la respuesta sea «nada».
  4. Cierra con la migración: ¿hay que tocar datos? ¿cuál es la vuelta atrás? Guárdalo como spec/changes/0002-search.md.
  5. Regístralo en el changelog: añade una línea a spec/changelog.md con la fecha y el motivo. Una delta sin entrada en el changelog es una carta sin sello: existe pero nadie la encuentra.

Resultado esperado: un fichero spec/changes/0002-search.md de unas 20 líneas con las cuatro secciones, dos criterios verificables con comandos reales (node src/cli.js list --search pan), impacto «sin roturas: list sin --search no cambia» y migración «sin migración de datos».

8 · Reto

Cambio con migración real

Escribe la delta-spec de «renombrar title a text en las notas de Lumen». Este sí rompe el esquema y exige migrar data/notes.json. Incluye el script o pasos de migración y el rollback.

Pista: piensa qué pasa con un fichero a medio migrar si el proceso se interrumpe; tu sección de migración debe decirlo.

9 · Resumen

  • El 90 % del trabajo real son cambios sobre sistemas vivos: se especifican con delta-specs, no reescribiendo el mundo.
  • Toda delta-spec tiene cuatro bloques: estado actual, estado deseado, impacto/compatibilidad y migración.
  • El impacto «ninguno» también se escribe: distingue lo compatible de lo no pensado.
  • Cada delta se guarda numerada en spec/changes/: el historial es la memoria del producto.
ArtefactoPara qué sirve
Delta-specEspecificar un cambio incremental con contexto, impacto y migración
Estado actual / deseadoAnclar el «antes» verificable y el «después» con criterios de aceptación
Sección de migraciónOrden de pasos y vuelta atrás para aplicar el cambio con seguridad

10 · Preguntas frecuentes

¿Cuándo escribo una delta-spec y cuándo edito la spec base directamente?

Si el cambio tiene impacto, migración o necesita revisión separada, delta-spec. Si es una errata o una aclaración que no cambia comportamiento, edita la base directamente. En caso de duda, delta: el rastro en Git siempre ayuda.

¿La delta-spec sustituye al plan?

No. La delta-spec dice qué cambia y por qué es seguro; el plan dice en qué orden tocar el código. Para cambios triviales el plan puede ser de tres líneas, pero sigue existiendo.

¿Dónde viven las delta-specs en el repo?

En spec/changes/ numeradas (0001-tags.md, 0002-search.md) más una línea en spec/changelog.md. La spec base se actualiza después para reflejar el nuevo estado, citando la delta.

¿Qué tamaño debe tener una delta-spec?

La más pequeña que elimine la ambigüedad: normalmente 20–40 líneas. Si supera una página, probablemente mezcla varios cambios: divídela.

¿Actualizo la spec base después del cambio?

Sí: cuando la delta se implementa y verifica, la spec base refleja el nuevo estado y cita la delta que lo produjo. La delta queda como historia; la base, como presente.
