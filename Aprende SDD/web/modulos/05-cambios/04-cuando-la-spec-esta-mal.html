Cuando la spec está mal

Módulo 5 · Cambios ⏱ 25 minutos

1 · Introducción

Tarde o temprano te pasará: el código cumple la spec… y el resultado está mal. La tentación es parchear el código a ciegas y seguir. En esta lección aprenderás por qué cuando la spec está mal, se corrige primero la spec, y cómo el historial Git de la spec se convierte en la memoria del producto.

Por qué existe: porque una spec errónea con código parcheado encima produce dos fuentes de (des)verdad que se contradicen. El siguiente agente —o tú dentro de tres meses— leerá la spec, implementará lo que dice y reintroducirá el bug que el parche había tapado. Corregir la spec primero mantiene una sola verdad.

Lo aplicarás cada vez que la verificación falle y el código «haga lo que dice el papel». Error típico: el parche rápido en el código con la promesa de «ya actualizo la spec luego» —ese luego no llega nunca—.

Hay una señal inconfundible de que la spec (y no el código) es la culpable: el implementador —humano o agente— puede señalar la línea exacta que siguió y esa línea, leída literalmente, produce el comportamiento incorrecto. Si hay que «interpretar» la spec para defender el código, el código se desvió; si basta leerla, la spec está mal.

2 · Teoría

Cuando verificación y spec discrepan, solo hay dos culpables posibles: el código se desvió de la spec, o la spec describía algo incorrecto. El protocolo SDD es: 1) decide cuál de los dos está mal, 2) si es la spec, corrígela en Git con su motivo, 3) re-planifica si hace falta, 4) y solo entonces toca el código. Parchear el código sin tocar la spec es mentirle al futuro.

Por qué la spec se corrige primero (siempre)

La spec es la fuente de verdad: gana las discusiones por definición. Si el código la contradice en silencio, ya no tienes fuente de verdad, tienes dos versiones en guerra y ningún árbitro. Cada corrección de spec, además, deja una entrada en el historial Git con el por qué del cambio —esa es la memoria del producto—. Dentro de un año, git log spec/ contará la historia de cada decisión; git log src/ solo contará qué líneas se movieron.

Así se ve esa memoria en la práctica: cada entrada cuenta una decisión con su motivo, sin necesidad de preguntar a nadie.

git log --oneline spec/
# a1b2c3d spec: --tag insensible a mayúsculas (las etiquetas son de humanos)
# e4f5g6h spec: delta 0003 acepta espacios en --tags (evidencia del piloto)

Analogía: el plano y la obra

Si el plano dice «puerta de 60 cm» y por ahí debe pasar una camilla, el error está en el plano, no en el albañil que lo siguió al milímetro. Regañar al albañil (parchear el código) deja el plano mal para la próxima obra. Se corrige el plano, se anota por qué (normativa de accesibilidad), y luego se ensancha la puerta.

3 · Ejemplo mínimo

El ritual completo cabe en cuatro comandos: diagnosticar, corregir la spec, dejar rastro, y después tocar código.

# 1. Reproduzco contra la spec (¿quién está mal?)
node src/cli.js list --tag Casa   # no encuentra "casa": la spec no definió mayúsculas

# 2. Corrijo la SPEC primero, con motivo
git commit -m "spec: --tag insensible a mayúsculas (las etiquetas son de humanos)" spec/changes/0001-tags.md

# 3. Ahora sí, implemento contra la spec corregida… y verifico
node src/cli.js list --tag casa   # OK

Línea por línea: el primer comando reproduce el fallo con hechos, no con opiniones —sin reproducción no hay diagnóstico—. El commit toca solo la spec y su mensaje explica el por qué (las etiquetas las escriben humanos, los humanos mezclan mayúsculas). Solo después se implementa, ya con la verdad actualizada. El último comando verifica contra la spec nueva, cerrando el bucle.

Separa los commits aunque vayan en el mismo cambio

Aunque el parche y la spec viajen juntos por prisa, haz dos commits: primero la spec («qué verdad cambia y por qué»), después el código («qué implementación la cumple»). El revisor verá la decisión antes que su consecuencia, y git log spec/ seguirá contando una historia limpia aunque el cambio fuera urgente.

4 · Ejemplo real

Caso Lumen: la delta de etiquetas especificó --tags compra,casa con comas, pero los usuarios escriben --tags "compra casa" con espacios y el CLI falla. El código cumple la spec al pie de la letra. La spec está mal: describió la sintaxis cómoda para el implementador, no la natural para el usuario. 

# Delta 0003: separador de etiquetas (corrige 0001)

## Estado actual
- `add --tags` solo acepta comas (`spec/changes/0001-tags.md`).
- Evidencia: 3 de 5 usuarios del piloto escriben espacios y fallan.

## Estado deseado
- [ ] Dado `add "pan" --tags "compra casa"`, cuando listo, entonces guarda `["compra", "casa"]`.
- [ ] Dado `--tags "compra,casa"` (comas), cuando añado, entonces sigue funcionando (compatibilidad con 0001).

## Impacto y compatibilidad
- Sin roturas: se aceptan ambos separadores; el almacenamiento (`tags: [...]`) no cambia.

## Migración
- Sin migración de datos. Actualizar `0001-tags.md` y el ejemplo de `--help`.

Decisiones explicadas: la corrección es una nueva delta que cita a la anterior (0003 corrige 0001), no una edición silenciosa: el historial muestra el aprendizaje. La evidencia del piloto justifica el cambio con datos, no con gusto personal. Se mantiene la sintaxis vieja (comas) funcionando: corregir la spec no es excusa para romper a los que ya la usaban. Y el --help se actualiza porque también es spec visible.

No reescribas la historia para esconder el error

Puede tentar editar 0001-tags.md como si siempre hubiera aceptado espacios, para que el historial «quede limpio». No lo hagas: el historial limpio miente y el honesto enseña. Quien lea 0001 → 0003 entenderá por qué existen dos separadores; quien lea una 0001 retocada creerá que el diseño nació perfecto y repetirá el mismo error en el próximo cambio.

El historial como memoria

Dentro de un año, git log spec/changes/ contará: «0001 introdujo etiquetas con comas → 0003 aceptó espacios por el piloto». Esa es la memoria del producto: cada decisión con su contexto y su motivo, inmune a la rotación del equipo y al olvido del chat.

5 · Buenas prácticas

Corregir la spec no es admitir un fracaso: es el ciclo funcionando. Estas reglas hacen que cada corrección deje el producto más inteligente que antes.

6 · Errores habituales

❌ Culpar al agente. «El agente lo implementó mal» cuando el agente siguió fielmente una spec errónea. ✅ El agente ejecuta; el humano posee la intención. Si la intención estaba mal escrita, el defecto es de la spec.

❌ Editar la spec a posteriori para que cuadre con el parche. Reescribir la verdad para que coincida con el código ya escrito invierte el ciclo: la spec deja de dirigir y pasa a justificar. ✅ Spec primero, código después, también al corregir.

❌ Borrar la delta errónea del historial. Reescribir Git para fingir que 0001 siempre tuvo espacios. ✅ La delta que se equivocó se queda: el error documentado enseña; el error borrado se repite.

❌ Corregir la spec y no re-verificar a los vecinos. Cambiar el separador de --tags sin volver a probar list --tag ni el esquema. ✅ Toda corrección de spec re-ejecuta la verificación completa: las líneas de una spec se sostienen entre sí.

7 · Ejercicio guiado

Practica el protocolo completo con un fallo real de Lumen:

  1. Reproduce: la spec dice que close con id inexistente «falla con error» (sintaxis: close <id>). Ejecuta node src/cli.js close no-existo: ¿código de salida? ¿mensaje? Anota el comportamiento real.
  2. Diagnostica: ¿el código se desvió o la spec es vaga? («falla con error» no define ni código de salida ni mensaje: veredicto probable, la spec está mal).
  3. Corrige la spec primero: escribe el criterio exacto (código de salida distinto de 0 + mensaje con el id) y commitea solo la spec con motivo.
  4. Implementa y re-verifica todos los criterios vecinos de close, no solo el nuevo.
  5. Lee tu historial: ejecuta git log --oneline spec/ y comprueba que un extraño entendería la historia solo con los mensajes. Si no, reescribe el mensaje (del commit, no la historia) antes de seguir.

Resultado esperado: un commit de spec («spec: define el error de close con id inexistente: salida 1 + mensaje con el id») anterior al commit de código, más una verificación que muestra los tres criterios de close en verde.

El orden de los commits es el resultado tanto como su contenido: si un revisor ve primero el commit de código, el ejercicio está suspenso aunque el mensaje sea perfecto. La spec manda, también en el historial.

8 · Reto

Autopsia de una spec muerta

Busca en un proyecto tuyo un parche que contradiga lo que la documentación dice. Escribe la delta que habría hecho falta: estado actual (lo que dice el papel), estado deseado (lo que hace el código), y el motivo que el historial debería haber guardado.

Pista: si no encuentras ningún caso, es que tu documentación ya es la spec… o que lleva tiempo sin leerse. Ambas son respuestas interesantes.

9 · Resumen

  • Si el código cumple la spec y el resultado está mal, la spec está mal: se corrige primero la spec.
  • Protocolo: reproducir → diagnosticar → corregir spec en Git con motivo → re-planificar → implementar → re-verificar.
  • Commits de spec separados y con motivo: git log spec/ es la memoria del producto.
  • Las deltas erróneas no se borran: se corrigen con nuevas deltas que las citan.
  • Incluso urgente, el cambio trae su spec: la deuda de spec no se paga sola.
  • La prueba literal («¿un implementador fiel llega a este resultado?») decide si la culpa es de la spec o del código.
  • Corregir hacia adelante con deltas que citan el error: el historial honesto enseña, el retocado miente.

10 · Preguntas frecuentes

¿De verdad paro una urgencia para actualizar la spec?

Sí, pero sin burocracia: el commit de spec puede ser de dos líneas junto al parche, en el mismo cambio. Lo que no vale es solo el parche. Cinco minutos hoy ahorran la regresión de dentro de tres meses.

¿Cómo distingo «spec mal» de «código mal»?

Reproduce con un comando y lee la spec literalmente: si un implementador fiel llega a este resultado, la spec está mal. Si la spec pedía otra cosa, el código se desvió. La lectura literal es el test.

¿Puedo reescribir el historial para limpiar una spec errónea?

No: el error documentado enseña y el borrado se repite. Corrige hacia adelante con una delta que cite la anterior. Reserva la reescritura para secretos filtrados, nunca para decisiones.

¿Qué pongo en el mensaje del commit de spec?

Qué cambia y por qué: «spec: --tag insensible a mayúsculas (el piloto muestra que los humanos mezclan)». El por qué es lo único que el diff no dice solo.

¿Y si la spec está mal pero el código ya funciona bien?

Entonces tienes deuda de spec: el sistema funciona por accidente y la próxima implementación seguirá el papel equivocado. Actualiza la spec para que describa lo que el código hace (con su motivo) y verifica que nada más dependía del texto viejo.
