Modo server (SSR) e hidratación bajo demanda

Módulo 5 · Datos y Endpoints 🕐 35 minutos

1 · Introducción

Hasta ahora todo tu sitio se generaba en build time: rápido, barato y estático. Pero hay casos en los que el HTML no puede nacer antes: un panel con sesión de usuario, un carrito personalizado, un buscador que lee ?q=, una página con datos que cambian cada minuto. Ahí entra el SSR (render en servidor, bajo demanda).

Astro no te obliga a elegir entre estático y dinámico para todo el sitio: puedes decidir por ruta. Y hay una tercera vía, las server islands, que combinan lo mejor de ambos: una página estática con una pequeña parte renderizada en el servidor bajo demanda.

¿Por qué existe esta lección? Porque el renderizado no es una propiedad del framework sino una decisión arquitectónica. Elegir bien entre estático, SSR y server islands decide el coste, la velocidad y la complejidad de tu aplicación. Quien domina esta elección, en lugar de aplicarla a ciegas, construye webs que escalan sin arruinarse.

2 · Teoría

Los tres modos de renderizado

ModoCuándo se genera el HTMLCosteFrescura
Estático (static)En el build, uno por páginaMínimo (se sirve un fichero)La del último build
SSR (server)En cada peticiónUn proceso por peticiónInmediata
Server islandsLa página en build, la isla en cada peticiónProceso solo para la islaInmediata para la isla

Analogía: el modo estático es un periódico impreso (rápido de leer, pero de ayer). El SSR es un chef cocinando cada plato al pedido (fresco, pero hay que esperar y tener cocina). Las server islands son un restaurante con menú impreso y un postre que se prepara al momento: la carta ya está, solo el postre se hace al pedir.

Adaptadores: cómo entra Astro en un servidor

Astro genera un sitio, pero para SSR necesita saber en qué entorno se ejecuta: un servidor Node, Vercel, Netlify, Cloudflare… Eso es un adaptador. Sin adaptador no hay SSR: el output 'server' requiere uno.

PlataformaAdaptadorComando
Node (servidor propio)@astrojs/nodepnpm astro add node
Vercel@astrojs/vercelpnpm astro add vercel
Netlify@astrojs/netlifypnpm astro add netlify
Cloudflare@astrojs/cloudflarepnpm astro add cloudflare
src/pages/api/tasks.ts (necesita SSR para POST)
// Este endpoint hace POST: sin SSR no puede ejecutarse en produccion.
// Con el adaptador de Node + output 'server', ya funciona.
import type { APIRoute } from 'astro';
export const POST: APIRoute = async ({ request }) => {
  const data = await request.json();
  return Response.json({ ok: true, data }, { status: 201 });
};
astro.config.mjs (SSR con Node)
import { defineConfig } from 'astro/config';
import node from '@astrojs/node';

export default defineConfig({
  // 'server': todas las rutas se renderizan bajo demanda por defecto.
  output: 'server',
  // mode 'standalone': Astro levanta su propio servidor Node.
  // mode 'middleware': exporta un handler para tu servidor Express/Fastify.
  adapter: node({ mode: 'standalone' }),
});

Con mode: 'standalone', tras pnpm build ejecutas node dist/server/entry.mjs y tienes un servidor completo.

prerender: la decisión por ruta

La clave de Astro 5 es que puedes mezclar. Cada archivo puede declarar si se pre-renderiza:

  • En output: 'static' (por defecto), todo es estático salvo las rutas con export const prerender = false (requiere adapter).
  • En output: 'server', todo es dinámico salvo las rutas con export const prerender = true.

Historia: Astro 3/4 tenían un tercer valor, output: 'hybrid'. En Astro 5 se eliminó: su comportamiento se absorbió en 'static', que ahora admite rutas bajo demanda con prerender = false. Si ves tutoriales antiguos con 'hybrid', están desactualizados.

src/pages/dashboard.astro (bajo demanda)
---
// En output 'static', esta linea hace que la pagina sea SSR.
// Requiere un adaptador instalado.
export const prerender = false;

// Datos especificos de la peticion: fijate en que NO se podrian
// pre-renderizar, porque dependen del usuario que hace la peticion.
const user = Astro.locals.user; // inyectado por un middleware (Modulo 8)
---

<h1>Hola, {user?.name ?? 'invitado'}</h1>
src/pages/sobre-nosotros.astro (estatica)
---
// Nada que declarar: en 'static' (por defecto) o en server con
// prerender = true, esta pagina se genera una vez en el build.
export const prerender = true;
---

<h1>Sobre nosotros</h1>
<p>Contenido que no cambia: perfecto para el build.</p>

Server islands: estático por fuera, dinámico por dentro

Imagina una portada de comercio: el 95 % es contenido cacheable, pero una esquina muestra «Hola, Ana» y el número de artículos del carrito. No quieres hacer toda la página dinámica por esa esquina. Ahí entran las server islands: la página se genera en build y la isla se renderiza en el servidor bajo demanda, rellenando un hueco.

PAGINA (estatica, cacheable)             SERVIDOR
+---------------------------------+      +-------------------------+
| Header, hero, contenido         |      |  Renderiza SOLO la      |
|                                 | <--- |  server island al vuelo |
|  +---------------------------+  |      |  (carrito, usuario...)  |
|  |  server island: carrito   |  |      +-------------------------+
|  |  (fallback mientras carga)|  |
|  +---------------------------+  |
+---------------------------------+
src/pages/tienda.astro
---
import Cart from '../components/Cart.astro';
---

<html lang="es">
  <body>
    <!-- Contenido estatico y cacheable de la tienda. -->
    <h1>Tienda</h1>

    <!-- server:defer renderiza este componente en el servidor bajo
         demanda; el slot "fallback" es lo que se ve mientras llega. -->
    <Cart server:defer>
      <p slot="fallback">Cargando carrito…</p>
    </Cart>
  </body>
</html>

Las server islands necesitan un adaptador y que la página se sirva desde el servidor. No confundas server:defer (renderizado en servidor bajo demanda) con client:visible (hidratación en el navegador tras hacerse visible). Son ejes distintos: dónde se renderiza el HTML vs cuándo se hidrata en el cliente.

La elección, resumida

Si el contenido…Usa
Es igual para todos y no cambia a menudoEstático (build)
Depende del usuario, la sesión o cambia por segundoSSR (prerender = false)
Es mayormente estático con una pieza dinámicaServer island (server:defer)

3 · Ejemplo mínimo

Activar SSR en un proyecto y comprobar que una página se genera en cada petición.

Terminal
# Instala el adaptador de Node: modifica astro.config.mjs por ti.
pnpm astro add node
astro.config.mjs
import { defineConfig } from 'astro/config';
import node from '@astrojs/node';

export default defineConfig({
  output: 'server',                       // HTML en cada peticion
  adapter: node({ mode: 'standalone' }),  // servidor Node propio
});
src/pages/hora.astro
---
// Si el output es 'server', esta pagina se genera en CADA peticion.
// La hora cambia: prueba a recargar y veras un valor distinto.
const now = new Date().toLocaleTimeString('es-ES');
---

<html lang="es">
  <body>
    <h1>La hora en el servidor es {now}</h1>
  </body>
</html>

Cómo verificarlo:

  1. Build y arranque: pnpm build y luego node dist/server/entry.mjs.
  2. Recarga varias veces: la hora cambia en cada recarga, porque el HTML se genera en el servidor bajo demanda.
  3. Contrasta: si añades export const prerender = true; al frontmatter y vuelves a construir, la hora quedará congelada en el valor del build. Esa es la diferencia entre los dos modos, visible en una línea.

4 · Ejemplo real

Arquitectura mixta para un panel de administración: la landing pública es estática y cacheable; el panel es SSR; la portada muestra un saludo personalizado con una server island.

astro.config.mjs
import { defineConfig } from 'astro/config';
import node from '@astrojs/node';

export default defineConfig({
  // Estatico por defecto; las rutas concretas se activan con prerender = false.
  // Requiere adaptador para poder renderizar bajo demanda.
  output: 'static',
  adapter: node({ mode: 'standalone' }),
});
src/pages/index.astro (portada, mayormente estatica)
---
import Greeting from '../components/Greeting.astro';
// No declaramos prerender: en 'static' esta pagina es estatica por defecto.
---

<html lang="es">
  <body>
    <h1>Bienvenido</h1>
    <p>Contenido indexable y cacheable en el CDN.</p>

    <!-- Saludo personalizado: se renderiza en el servidor bajo demanda,
         sin volver dinamica toda la portada. -->
    <Greeting server:defer>
      <span slot="fallback">Hola</span>
    </Greeting>
  </body>
</html>
src/components/Greeting.astro (server island)
---
// Este componente se ejecuta en el servidor en cada peticion.
// Aqui SI podemos leer cookies/sesion (Modulo 8).
const name = Astro.cookies.get('name')?.value ?? 'invitado';
---

<span>Hola, <strong>{name}</strong></span>
src/pages/admin/panel.astro (SSR puro)
---
// Depende por completo de la sesion: NO se puede pre-renderizar.
export const prerender = false;

// Astro.request existe en SSR; Astro.cookies lee las cookies del usuario.
const session = Astro.cookies.get('session')?.value;
if (!session) {
  // Redirigimos si no hay sesion (Auth en detalle, Modulo 8).
  return Astro.redirect('/login');
}
const stats = await fetch('https://api.example.com/stats').then((r) => r.json());
---

<h1>Panel</h1>
<ul>
  {Object.entries(stats).map(([k, v]) => <li>{k}: {String(v)}</li>)}
</ul>

Decisiones explicadas:

  • La portada sigue estática: máxima velocidad y cache en el CDN para el contenido que ve casi todo el tráfico.
  • Solo el saludo es dinámico, como server island: la página entera no paga el coste de render por petición.
  • El panel es SSR puro con prerender = false: depende de sesión y datos privados, no hay nada que cachear.
  • Astro.redirect: redirección del lado del servidor, ideal para control de acceso.

Regla de oro del coste: el SSR consume CPU en cada petición. Cuanta más página hagas dinámica, más servidor necesitas. Empuja todo lo posible al build y deja en el servidor solo lo que de verdad lo requiere. Un sitio bien diseñado suele ser 80-95 % estático.

5 · Buenas prácticas

HazEvitaPor qué
Estático por defecto; SSR solo en rutas que lo necesitan Activar output: 'server' en todo el sitio «por comodidad» El SSR multiplica el coste de servidor; lo cacheable debe quedarse en build
Usar server islands para piezas dinámicas en páginas estáticas Volver dinámica toda la página por una sola esquina Mantienes el CDN y la velocidad, y solo pagas por la isla
Elegir el adaptador según el destino de despliegue Usar el adaptador de Node para desplegar en Vercel Cada plataforma tiene su runtime; el adaptador equivocado rompe el build o el despliegue
Marcar prerender = true en todo lo posible bajo output: 'server' Dejar todo dinámico en modo server Las rutas estáticas se sirven como ficheros: más rápidas y más baratas
Depurar los fallos de SSR con los logs del servidor Buscar el error en DevTools del navegador El render ocurre en el servidor; los errores salen en su terminal/logs

6 · Errores habituales

Activar output: 'server' sin adaptador

✗ Incorrecto

// SSR sin adaptador: Astro no sabe donde ejecutarse. Error de build.
export default defineConfig({
  output: 'server',   // y ningun adapter definido
});

✓ Correcto

import node from '@astrojs/node';
export default defineConfig({
  output: 'server',
  adapter: node({ mode: 'standalone' }), // imprescindible
});

El renderizado bajo demanda necesita un entorno de ejecución. El adaptador se lo da.

Usar output: 'hybrid' (eliminado en Astro 5)

✗ Incorrecto

// Valor eliminado en Astro 5: rompe el build o avisa con deprecacion.
export default defineConfig({ output: 'hybrid' });

✓ Correcto

// En Astro 5: 'static' por defecto + rutas con prerender = false.
export default defineConfig({
  output: 'static',
  adapter: node({ mode: 'standalone' }),
});

La mezcla estático/dinámico ahora se expresa ruta por ruta, no con un modo global intermedio.

Hacer dinámico lo que podría ser estático

✗ Incorrecto

---
// Página de blog idéntica para todos: NO necesita SSR.
export const prerender = false;
const posts = await (await fetch(apiUrl)).json();
---

✓ Correcto

---
// Pre-renderizamos en build: más rápido y cacheable en el CDN.
export const prerender = true;
const posts = await (await fetch(apiUrl)).json();
---

Si el contenido es el mismo para todos, generar en build ahorra CPU por petición y permite cachear. El SSR no es «mejor»: es solo necesario cuando los datos son por usuario o en tiempo real.

Confundir server islands con hidratación

✗ Incorrecto

<!-- server:defer NO hidrata en el cliente: es render en el servidor. -->
<Cart server:defer />   <!-- no esperes un onClick funcionando -->

✓ Correcto

<!-- Contenido dinamico sin interactividad: server island. -->
<Cart server:defer><p slot="fallback">Cargando…</p></Cart>

<!-- Interactividad real (clics, estado): isla de framework con client:*. -->
<CartWidget client:visible />

server:defer controla dónde se genera el HTML (servidor, al vuelo). client:* controla cuándo se hidrata en el navegador. Son ejes independientes y complementarios.

7 · Ejercicio guiado

Objetivo: convertir un sitio estático en una arquitectura mixta: landing estática, una ruta SSR y una página con server island.

  1. Activa el adaptador y el modo mixto: 
    pnpm astro add node

    // astro.config.mjs
import node from '@astrojs/node';
export default defineConfig({
  output: 'static',
  adapter: node({ mode: 'standalone' }),
});
  2. Deja la portada estática (src/pages/index.astro): contenido, hero y textos. No declares nada.
  3. Crea una ruta SSR src/pages/hora.astro que muestre la hora del servidor: 
    ---
export const prerender = false; // esta ruta se genera bajo demanda
const now = new Date().toLocaleTimeString('es-ES');
---
<h1>Hora del servidor: {now}</h1>
  4. Crea una server island src/components/VisitorInfo.astro que lea una cabecera y la muestre, y anídala en la portada con server:defer y un slot="fallback".
  5. Construye y arranca: 
    pnpm build
node dist/server/entry.mjs
  6. Verifica:
    • Recarga /hora varias veces: la hora cambia (SSR).
    • Inspecciona el HTML de / con «Ver código fuente»: el contenido estático está completo en el fichero, y el hueco del visitante se rellena al vuelo.
    • Mira los logs del servidor: aparecen las peticiones de la isla, pero no de la portada entera.

8 · Reto

🎯 Decide el modo de cada ruta (y justifícalo)

Te dan una web con estas páginas. Para cada una, decide si debe ser estática, SSR o llevar una server island, y explica por qué en una frase:

  • / — portada con hero, últimas noticias (globales) y un saludo «Hola, {nombre}».
  • /precio — precio de una criptomoneda actualizado al segundo.
  • /blog/[slug] — artículo de un CMS.
  • /checkout — resumen del carrito del usuario con su sesión.
  • /docs — documentación que casi nunca cambia.

Después, impleméntalo: monta la portada estática con una server island para el saludo, y haz SSR solo donde toque. Ejecuta pnpm build y comprueba cuántas rutas se generaron como ficheros en dist/ y cuántas quedaron dinámicas.

Pista: pregúntate siempre dos cosas: «¿este HTML es igual para todos los usuarios?» y «¿cuánto cambia este dato?». Si la respuesta es «sí» y «poco», es estático. Si es «no» y «mucho», es SSR. Si es «casi todo igual, salvo una esquina», usa una server island. Fíjate: el precio de la cripto cambia al segundo pero podría ser una server island dentro de una página estática; el checkout, en cambio, es SSR de arriba a abajo.

9 · Resumen

  • Estático: HTML en build, rápido y cacheable. SSR: HTML por petición, fresco y personalizado. Server islands: mezcla de ambos.
  • El SSR requiere un adaptador (@astrojs/node, Vercel, Netlify, Cloudflare).
  • Astro 5 decidió por ruta: output: 'static' (por defecto) con prerender = false, o output: 'server' con prerender = true.
  • output: 'hybrid' ya no existe: su lógica se movió a 'static'.
  • server:defer renderiza una isla en el servidor bajo demanda; client:* la hidrata en el navegador. Son ejes distintos.
  • La regla de coste: estático por defecto, dinámico solo cuando los datos son por usuario o en tiempo real.

10 · Preguntas frecuentes

¿SSR significa que pierdo las ventajas de Astro?

No. Astro sigue siendo Astro: MPA, HTML en servidor y islands. El SSR solo cambia cuándo se genera ese HTML, no el modelo. Además, en Astro 5 el SSR es por ruta: puedes tener el 90 % del sitio estático y una sola sección dinámica. La mejor arquitectura casi siempre mezcla ambos.

¿server:defer sustituye a client:load?

No, cubren cosas distintas. Con server:defer, el HTML de la isla se genera en el servidor bajo demanda (útil para contenido personalizado). Con client:load, un componente se hidrata en el navegador para volverse interactivo. Puedes combinar ambos conceptos: contenido dinámico servido desde el servidor y luego hidratado si necesita clics.

¿Qué adaptador debo elegir?

El de la plataforma donde despliegas: @astrojs/vercel en Vercel, @astrojs/netlify en Netlify, @astrojs/cloudflare en Cloudflare y @astrojs/node si gestionas tu propio servidor. Elegir mal el adaptador es una causa clásica de build roto o de funciones que no arrancan en producción. Lo verás con detalle en el Módulo 8.

¿Puedo cachear páginas SSR para que no cueste tanto?

Sí. Las cabeceras HTTP (Cache-Control) permiten cachear respuestas SSR en el CDN durante X segundos o hasta que cambien (con stale-while-revalidate). También puedes cachear los datos y no la página, o usar ISR en plataformas que lo soportan. La idea: si una página «dinámica» cambia poco, no hace falta renderizarla en cada petición.

¿Sirve SSR para una API que consumirá una app móvil?

Sí. Un endpoint en src/pages/api/ con SSR es exactamente una API REST normal: la app móvil hace fetch a tus rutas como a cualquier backend. De hecho, Astro es una forma cómoda de montar APIs pequeñas o medianas sin sacar un framework de servidor aparte, compartiendo tipos con el front si usas TypeScript.
