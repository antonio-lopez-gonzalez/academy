Proyecto: blog con API y SSR

Módulo 5 · Datos y Endpoints 🕐 45 minutos

1 · Introducción

En este proyecto vas a construir un blog completo que reúne todo lo aprendido en el módulo: consume una API externa en build time para listar y detallar artículos, expone su propio endpoint para los comentarios y los muestra con una isla React que se hidrata solo cuando es visible.

Es, en miniatura, la arquitectura de muchísimos sitios reales: contenido estático y cacheable (los artículos) + una zona dinámica (los comentarios) que vive en el servidor. Aprenderás a decidir qué parte es estática, qué parte es SSR y cómo se comunican sin fricción.

¿Por qué este proyecto? Porque integra las tres lecciones del módulo en un solo artefacto coherente: fetch en build, endpoints y SSR. Además te obliga a tomar la decisión arquitectónica más importante de Astro: separar lo estático de lo dinámico. Cuando termines, tendrás una plantilla reutilizable para cualquier web con datos externos.

2 · Teoría

La arquitectura objetivo

              +------------------------------------------+
              |             NAVEGADOR                    |
              |  /blog  /blog/[slug]   (HTML estatico)   |
              |  + isla React de comentarios (fetch)     |
              +-------------------+----------------------+
                                  |
             HTML pre-renderizado |  GET/POST /api/comments
                                  v
              +------------------------------------------+
              |               SERVIDOR / BUILD           |
              |  - build: fetch externo -> articulos     |
              |  - SSR:   endpoint /api/comments         |
              |  - (persistencia en memoria para el demo)|
              +------------------------------------------+

Observa la separación de responsabilidades:

  • Los artículos vienen de una API externa y no cambian por usuario: se resuelven en build time y se sirven como HTML estático.
  • Los comentarios los escribe el usuario y deben persistir y leerse en caliente: van por un endpoint SSR.
  • La isla React solo gestiona la caja de comentarios: lee y publica contra el endpoint.

Dos orígenes de datos, dos estrategias

DatoOrigenEstrategiaMotivo
Lista de artículosAPI externaFetch en buildIgual para todos, cambia poco, cacheable
Cuerpo de un artículoAPI externaFetch en getStaticPathsUna página por artículo, generadas de antemano
ComentariosNuestro endpointSSR + islaCambian con cada usuario y cada momento

Analogía: los artículos son una revista impresa (se imprime una vez y se reparte a todos). Los comentarios son un tablón de anuncios en la puerta: cualquiera clava un papel en cualquier momento y todos lo leen al pasar. Mezclar ambos modelos en la misma página, sin volver dinámico lo que no lo necesita, es la esencia de la arquitectura islands aplicada a los datos.

Persistencia del demo: en memoria, pero con contrato real

Un blog real guardaría los comentarios en una base de datos. Para no depender de infraestructura en este módulo, usaremos un almacén en memoria (un Map), como en la lección de endpoints. Lo importante: el contrato del endpoint (rutas, métodos, validación, códigos de estado) es idéntico al de producción; solo cambiará la implementación interna cuando llegue la base de datos.

3 · Ejemplo mínimo

Antes del proyecto, la pieza más pequeña: un endpoint de comentarios que solo sabe listar y añadir.

src/pages/api/comments.ts
import type { APIRoute } from 'astro';

// Almacen en memoria: se reinicia al reiniciar el servidor.
interface Comment { id: number; slug: string; author: string; text: string; }
const store = new Map<string, Comment[]>();

// GET /api/comments?slug=mi-post -> comentarios de ese articulo.
export const GET: APIRoute = ({ url }) => {
  const slug = url.searchParams.get('slug') ?? '';
  return Response.json(store.get(slug) ?? []);
};

// POST /api/comments -> añade un comentario al articulo indicado.
export const POST: APIRoute = async ({ request }) => {
  let body: { slug?: string; author?: string; text?: string };
  try {
    body = await request.json();
  } catch {
    return Response.json({ error: 'JSON invalido' }, { status: 400 });
  }

  // Validacion de servidor: imprescindible.
  if (!body.slug || !body.author?.trim() || !body.text?.trim()) {
    return Response.json({ error: 'Faltan campos' }, { status: 422 });
  }

  // Creamos y guardamos el comentario.
  const list = store.get(body.slug) ?? [];
  const comment: Comment = {
    id: Date.now(),
    slug: body.slug,
    author: body.author.trim(),
    text: body.text.trim(),
  };
  list.push(comment);
  store.set(body.slug, list);

  return Response.json(comment, { status: 201 });
};

Es el corazón dinámico del proyecto. Todo lo demás lo irás montando alrededor: la lista estática de artículos, las páginas individuales y la isla que consume este endpoint.

4 · Ejemplo real

El proyecto completo, pieza a pieza.

1) Configuración: estático por defecto, adapter para el endpoint

astro.config.mjs
import { defineConfig } from 'astro/config';
import react from '@astrojs/react';   // isla de comentarios
import node from '@astrojs/node';     // necesario para el endpoint POST

export default defineConfig({
  // Los articulos se generan en build; el endpoint puede correr bajo demanda.
  output: 'static',
  integrations: [react()],
  adapter: node({ mode: 'standalone' }),
});

2) Capa de datos: un helper tipado y con manejo de errores

src/lib/posts.ts
// Un solo lugar para hablar con la API externa de articulos.
// Reutilizar esto evita repetir fetch y manejo de errores por doquier.
export interface Post {
  id: number;
  slug: string;
  title: string;
  body: string;
}

const API = 'https://jsonplaceholder.typicode.com/posts';

// Trae todos los articulos. En build time.
export async function getPosts(): Promise<Post[]> {
  try {
    const res = await fetch(API);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (error) {
    console.error('No se pudieron cargar los posts:', error);
    return []; // fallback: el build no se cae
  }
}

// Trae un articulo por slug (en el demo el slug es el id).
export async function getPost(slug: string): Promise<Post | null> {
  try {
    const res = await fetch(`${API}/${slug}`);
    if (!res.ok) return null;
    return await res.json();
  } catch (error) {
    console.error(`No se pudo cargar el post ${slug}:`, error);
    return null;
  }
}

5) La isla de comentarios

src/components/CommentSection.tsx
import { useEffect, useState } from 'react';

interface Comment {
  id: number;
  slug: string;
  author: string;
  text: string;
}

export default function CommentSection({ slug }: { slug: string }) {
  const [comments, setComments] = useState<Comment[]>([]);
  const [author, setAuthor] = useState('');
  const [text, setText] = useState('');
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState('');

  // Cargamos los comentarios al montar la isla.
  useEffect(() => {
    let active = true; // evita setState si la isla se desmonta antes
    fetch(`/api/comments?slug=${slug}`)
      .then((r) => r.json())
      .then((data) => {
        if (active) setComments(data);
      })
      .catch(() => {
        if (active) setError('No se pudieron cargar los comentarios.');
      })
      .finally(() => {
        if (active) setLoading(false);
      });
    return () => {
      active = false;
    };
  }, [slug]);

  async function submit(e: React.FormEvent) {
    e.preventDefault();
    if (!author.trim() || !text.trim()) return;

    const res = await fetch('/api/comments', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ slug, author, text }),
    });

    if (!res.ok) {
      const err = await res.json();
      setError(err.error ?? 'Error al publicar');
      return;
    }

    const created: Comment = await res.json();
    setComments((prev) => [...prev, created]); // añadimos el confirmado
    setText('');
    setError('');
  }

  return (
    <section>
      <h2>Comentarios</h2>

      {loading && <p>Cargando comentarios…</p>}
      {error && <p role="alert">{error}</p>}

      <ul>
        {comments.map((c) => (
          <li key={c.id}><strong>{c.author}</strong>: {c.text}</li>
        ))}
      </ul>

      <form onSubmit={submit}>
        <input
          value={author}
          onChange={(e) => setAuthor(e.target.value)}
          placeholder="Tu nombre"
          aria-label="Tu nombre"
        />
        <textarea
          value={text}
          onChange={(e) => setText(e.target.value)}
          placeholder="Escribe un comentario"
          aria-label="Comentario"
        />
        <button type="submit">Publicar</button>
      </form>
    </section>
  );
}

Decisiones explicadas:

  • Helper src/lib/posts.ts: centraliza el acceso a la API externa y su manejo de errores. Las páginas quedan limpias.
  • getStaticPaths con una sola llamada: no repetimos el fetch por artículo.
  • Artículos estáticos, comentarios dinámicos: la separación exacta de la teoría. La página del artículo es HTML; solo la caja de comentarios se hidrata.
  • client:visible en la sección de comentarios: suele estar al final de la página, así que no tiene sentido hidratarla antes.
  • active en el useEffect: patrón para evitar actualizar estado tras desmontar la isla (una fuga de memoria clásica).
  • La isla añade el comentario que el servidor confirmó (201), en lugar de recargar toda la lista. Consistencia inmediata sin peticiones extra.

6 · Errores habituales

Renderizar los artículos en el cliente

✗ Incorrecto

// Traer los articulos con una isla React: spinner y datos no indexables.
useEffect(() => {
  fetch('/api/posts').then((r) => r.json()).then(setPosts);
}, []);

✓ Correcto

---
// Datos globales y estables: se resuelven en build, sin JS en cliente.
const posts = await getPosts();
---
{posts.map((p) => <article><a href={`/blog/${p.id}`}>{p.title}</a></article>)}

Si el contenido es igual para todos, renderizarlo en el cliente añade latencia, rompe el SEO y gasta datos sin motivo.

Olvidar el adaptador para el endpoint dinámico

✗ Incorrecto

// output: 'static' pero SIN adapter: el POST /api/comments no correra
// en produccion (solo funciona en pnpm dev).
export default defineConfig({ output: 'static' });

✓ Correcto

import node from '@astrojs/node';
export default defineConfig({
  output: 'static',
  adapter: node({ mode: 'standalone' }), // habilita el endpoint dinamico
});

El endpoint es dinámico; sin adaptador solo funciona en desarrollo. Es el error más común al desplegar por primera vez.

Repetir el fetch en cada página de artículo

✗ Incorrecto

---
// getStaticPaths pide TODA la lista, y luego cada pagina pide el post:
// dos fetches por ruta. Con 100 posts, 200 peticiones.
export async function getStaticPaths() { /* fetch posts */ }
const post = await getPost(Astro.params.slug);
---

✓ Correcto

---
// getStaticPaths resuelve las props; la pagina las recibe hechas.
export async function getStaticPaths() {
  const posts = await getPosts(); // una sola vez
  return posts.map((p) => ({ params: { slug: String(p.id) }, props: { post: p } }));
}
const { post } = Astro.props; // ya lo tenemos
---

Pide los datos una vez y reparte las props. Evitas multiplicar peticiones y aceleras el build.

Objetivo: montar el blog completo y verificar cada capa por separado.

8 · Reto

🎯 Búsqueda, paginación y contador de vistas

Amplía el blog con tres mejoras que combinan lo estático y lo dinámico:

  • Búsqueda: una isla que filtre los artículos por título sin recargar (ya tienes el patrón del Módulo 4). Decide si el filtrado es en cliente sobre datos pre-cargados o una consulta a un endpoint de búsqueda; justifica la elección.
  • Paginación: páginas /blog/page/[n] generadas con getStaticPaths a partir de los mismos datos. Debe ser estática.
  • Contador de vistas: un endpoint POST /api/views/[slug] que incremente un contador, y una server island que muestre el número actual al vuelo dentro de la página estática del artículo.

Requisitos: validación de servidor en el endpoint de vistas, códigos de estado correctos, y ninguna ruta que sea dinámica sin justificación. Ejecuta pnpm build y demuestra cuántos ficheros estáticos se generan.

Pista: la búsqueda sobre 20 artículos puede ser en cliente (datos ya presentes como props). No todo necesita un endpoint; añadir red solo porque puedes es un mal criterio. El contador de vistas sí es dinámico (cambia con cada visita), así que ahí brilla server:defer: la página permanece estática y solo el numerito se renderiza en el servidor. Recuerda: en memoria, los contadores se reinician al reiniciar; el «contrato» es lo que importa.

9 · Resumen

  • Un blog real mezcla contenido estático (artículos) y zona dinámica (comentarios).
  • Los artículos se resuelven en build time con un helper centralizado y getStaticPaths.
  • Los comentarios viven en un endpoint SSR (GET/POST) con validación de servidor.
  • La isla React gestiona loading, error y actualiza la UI con el recurso confirmado.
  • Sin adaptador, el endpoint dinámico solo funciona en desarrollo.
  • La persistencia en memoria es temporal: la base de datos llega en módulos posteriores.

10 · Preguntas frecuentes

¿Por qué los comentarios no persisten al reiniciar?

Porque el demo usa un Map en memoria del proceso. Al reiniciar el servidor, ese estado desaparece. Es intencional para no depender de infraestructura en este módulo. En producción se sustituye por una base de datos (PostgreSQL, SQLite, un servicio serverless…) manteniendo el mismo contrato del endpoint: rutas, métodos, validación y códigos de estado no cambian.

¿Por qué los artículos son estáticos y los comentarios no?

Los artículos son los mismos para todos y cambian poco: perfectos para generar en build, cachear en el CDN y servir al instante. Los comentarios dependen del usuario y del momento: deben leerse y escribirse en caliente. Esa asimetría es la clave de la arquitectura: no dinamizas toda la página por una parte que lo necesita.

¿Debería la isla cargar los comentarios o traerlos ya del servidor?

Depende del caso. Aquí la isla los carga porque el endpoint es la fuente viva y queremos simplicidad. Una alternativa es renderizar los comentarios iniciales en el servidor como HTML (mejor primera pintura y SEO) y usar la isla solo para publicar. Es un patrón excelente: HTML para leer, isla para escribir. Puedes probarlo en el reto.

¿Cómo evito que cualquiera publique comentarios machacando mi API?

Con las defensas habituales: autenticación (que solo usuarios válidos publiquen), limitación de tasa (rate limiting), validación robusta del contenido y, si hace falta, moderación. La autenticación con cookies y middleware se trata en el Módulo 8. Por ahora, recuerda que un endpoint sin protección es público de verdad.

¿Puedo desplegar este blog en Vercel o Netlify?

Sí. Cambia el adaptador por el de la plataforma (@astrojs/vercel o @astrojs/netlify) y el resto del código se queda igual. El adaptador le enseña a Astro en qué entorno ejecutarse; el contrato de tu aplicación no cambia. El despliegue completo por plataforma se ve en el Módulo 8.
