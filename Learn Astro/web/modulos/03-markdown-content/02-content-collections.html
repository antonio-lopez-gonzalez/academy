Content Collections y esquemas Zod

Módulo 3 · Markdown y Content 🕐 35 minutos

1 · Introducción

En la lección anterior listamos Markdown con import.meta.glob. Funciona, pero tiene un agujero: nadie comprueba que el frontmatter de cada post sea correcto. Si un post escribe pubdate en minúsculas, o se olvida el title, el error aparece en tiempo de ejecución o, peor, en producción. Y todo está tipado como any: el editor no te ayuda.

Las content collections resuelven esto: agrupan contenido (Markdown, MDX, JSON, YAML) bajo un esquema tipado definido con Zod. Si un fichero incumple el esquema, el build falla con un mensaje claro indicando qué fichero y qué campo. Es la diferencia entre «espero que esté bien» y «el sistema garantiza que está bien».

¿Por qué existe esto? Porque el contenido es código, pero se escribe sin pensar en tipos. Un blog con 300 posts escritos por varias personas necesita un contrato: «todo post tiene title, description, pubDate y author». Ese contrato es el esquema. Zod lo verifica en build time y TypeScript propaga los tipos al editor. Es la misma idea que un esquema de base de datos o un validador de JSON: el error se caza lo antes posible.

Novedad de Astro 5 — la Content Layer: las colecciones ya no están atadas a carpetas fijas de Markdown. Ahora se definen con un loader (glob, file, o uno propio) en src/content.config.ts, lo que permite traer contenido de donde sea (ficheros locales, una API, un CMS) manteniendo el mismo esquema y la misma API.

Errores típicos: poner la config en src/content/config.ts en lugar de src/content.config.ts (en Astro 5 la nueva ubicación es la raíz de src), olvidar que getCollection es asíncrona (falta el await), usar entry.slug cuando en la Content Layer el identificador es entry.id, y no llamar a render() para pintar el cuerpo.

2 · Teoría

Colecciones, loaders y esquemas

Una colección es un grupo de contenido homogéneo: todos los posts, o todos los autores, o todos los productos. Cada colección se define con dos piezas:

  • Un loader: de dónde salen las entradas. glob() lee ficheros por patrón; file() lee un único fichero JSON/YAML con un array.
  • Un schema (Zod): qué forma tiene cada entrada (sus campos y tipos).
src/content.config.ts
   ┌────────────────────────────────────────────────┐
   │ const blog = defineCollection({                │
   │   loader: glob({ pattern, base }),  ← DE DÓNDE │
   │   schema: z.object({ title, pubDate, … }) ← FORMA│
   │ });                                            │
   │ export const collections = { blog };           │
   └────────────────────────────────────────────────┘
                     │
        getCollection('blog')  ─▶  entradas VALIDADAS y TIPADAS
                     │
        render(entry)          ─▶  { Content, headings }  → <Content />

Analogía: una colección es una biblioteca con normas de catalogación. El loader es la estantería de donde recoges los libros; el esquema es la ficha obligatoria (título, autor, año…). Si un libro llega sin ficha, la bibliotecaria (Zod) lo rechaza en la puerta y te dice exactamente qué le falta. Nada entra sin cumplir el contrato.

La Content Layer API (Astro 5)

El fichero de configuración vive en src/content.config.ts. Fíjate en la ruta: en Astro 5 la config va en la raíz de src/, no dentro de src/content/ (esa era la ubicación antigua de las colecciones «legacy»). El contenido en sí puede vivir donde quieras, porque lo declara el loader.

src/content.config.ts
// defineCollection y el re-export de Zod vienen de 'astro:content'.
import { defineCollection, z } from 'astro:content';
// glob y file son los loaders de la Content Layer.
import { glob } from 'astro/loaders';

const blog = defineCollection({
  // 1) DE DÓNDE: todos los .md/.mdx dentro de src/content/blog/
  loader: glob({ pattern: '**/*.{md,mdx}', base: './src/content/blog' }),

  // 2) QUÉ FORMA: el contrato que debe cumplir el frontmatter de cada post
  schema: z.object({
    title: z.string(),                                  // obligatorio
    description: z.string(),                            // obligatorio (SEO)
    pubDate: z.coerce.date(),                           // string → Date automáticamente
    author: z.string().default('Anónimo'),              // opcional con valor por defecto
    tags: z.array(z.string()).default([]),              // lista, por defecto vacía
    draft: z.boolean().default(false),                  // borrador oculto por defecto
  }),
});

// Cada colección exportada queda disponible para getCollection/getEntry.
export const collections = { blog };

Tipos generados: cuando cambias la config, Astro ejecuta astro sync (automático en dev y build) y genera los tipos en .astro/. Así el editor conoce la forma exacta de entry.data. Si añades una colección y no ves los tipos, ejecuta pnpm astro sync a mano.

Leer contenido: getCollection, getEntry

La API es pequeña y toda asíncrona (en Astro 5 los loaders pueden ser lentos: leer un CMS, descargar datos…):

import { getCollection, getEntry } from 'astro:content';

// Todas las entradas de una colección (await obligatorio)
const posts = await getCollection('blog');

// El mismo dato, pero filtrado en el propio getCollection
const publicados = await getCollection('blog', ({ data }) => !data.draft);

// Una sola entrada por su id
const uno = await getEntry('blog', 'hola-astro');

Cada entrada tiene esta forma: entry.id (identificador, derivado de la ruta del fichero), entry.data (el frontmatter ya validado y tipado) y entry.body (el Markdown en crudo).

Pintar el cuerpo: render()

Para convertir el cuerpo Markdown en un componente que puedas colocar, usa render (en Astro 5 es la forma recomendada; el antiguo entry.render() está desaconsejado):

import { render } from 'astro:content';

const { Content, headings } = await render(post);
// Content  → componente con el HTML del Markdown → <Content />
// headings → títulos, para construir un índice

Relaciones entre colecciones

Con reference() puedes enlazar entradas tipadas: un post apunta a un autor de otra colección, y Astro valida que la referencia exista.

// En el schema del blog:
author: reference('authors'),   // debe existir una colección 'authors'
// Al resolver:
const autor = await getEntry(post.data.author);  // objeto autor completo

3 · Ejemplo mínimo

Una colección de una sola entrada y una página que la muestra. Primero la config y el contenido:

src/content.config.ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

// Colección mínima: solo un título obligatorio.
const blog = defineCollection({
  loader: glob({ pattern: '**/*.md', base: './src/content/blog' }),
  schema: z.object({
    title: z.string(),
  }),
});

export const collections = { blog };
src/content/blog/hola.md
---
title: Mi primer post de colección
---

Este texto es el **cuerpo** del post, en Markdown.
src/pages/blog/index.astro
---
import { getCollection, render } from 'astro:content';

// getCollection es ASÍNCRONA → await obligatorio.
const posts = await getCollection('blog');
// De momento solo pintamos el primero.
const { Content } = await render(posts[0]);
---

<html lang="es">
  <head><meta charset="UTF-8" /><title>Blog</title></head>
  <body>
    <h1>{posts[0].data.title}</h1>
    <!-- <Content /> pinta el Markdown convertido a HTML -->
    <Content />
  </body>
</html>

Línea por línea: la config declara la colección blog con su loader (glob sobre src/content/blog) y su esquema. El fichero hola.md aporta el frontmatter (title) y el cuerpo. En la página, await getCollection('blog') devuelve las entradas validadas; post.data.title es el frontmatter tipado; y render(post) produce el componente Content, que pintamos con <Content />. Si quitas el title del frontmatter, el build falla señalando src/content/blog/hola.md: ese es el valor del esquema.

4 · Ejemplo real

Migraciones del blog del Módulo 2 a content collections. La arquitectura no cambia: cambia de dónde salen los datos.

La configuración de la colección

src/content.config.ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const blog = defineCollection({
  // Todos los Markdown/MDX bajo src/content/blog (incluidas subcarpetas)
  loader: glob({ pattern: '**/*.{md,mdx}', base: './src/content/blog' }),
  schema: z.object({
    title: z.string(),
    description: z.string(),
    pubDate: z.coerce.date(),          // '2026-01-10' se convierte en Date
    author: z.string().default('Anónimo'),
    tags: z.array(z.string()).default([]),
    draft: z.boolean().default(false),
  }),
});

export const collections = { blog };

El detalle, ahora como ruta comodín por id

src/pages/blog/[...id].astro
---
import { getCollection, render } from 'astro:content';
import type { CollectionEntry } from 'astro:content';
import BlogLayout from '../../layouts/BlogLayout.astro';

// Una ruta por cada entrada de la colección.
export async function getStaticPaths() {
  const posts = await getCollection('blog');
  return posts.map((post) => ({
    // El identificador de una entrada de la Content Layer es `id`.
    // Usamos [...id] (rest) para admitir ids con subcarpetas: '2026/hola'.
    params: { id: post.id },
    props: { post },
  }));
}

interface Props {
  post: CollectionEntry<'blog'>;  // tipo generado automáticamente
}
const { post } = Astro.props;

// render() convierte el cuerpo Markdown en componente.
const { Content, headings } = await render(post);
---

<BlogLayout
  title={post.data.title}
  description={post.data.description}
  pubDate={post.data.pubDate}
  author={post.data.author}
>
  <Content />
</BlogLayout>

El listado, filtrado y ordenado

src/pages/blog/index.astro
---
import { getCollection } from 'astro:content';
import BaseLayout from '../../layouts/BaseLayout.astro';
import PostCard from '../../components/PostCard.astro';

// Filtramos los borradores en la propia consulta: nunca llegan a la página.
const posts = await getCollection('blog', ({ data }) => !data.draft);

// Orden descendente por fecha.
const ordered = posts.sort(
  (a, b) => b.data.pubDate.getTime() - a.data.pubDate.getTime()
);
---

<BaseLayout title="Blog">
  <h1>Blog</h1>
  {ordered.map((post) => (
    <article>
      <h2><a href={`/blog/${post.id}`}>{post.data.title}</a></h2>
      <p>{post.data.description}</p>
      <p>Etiquetas: {post.data.tags.join(', ')}</p>
    </article>
  ))}
</BaseLayout>

Qué ha cambiado respecto al Módulo 2: ya no hay posts.ts a mano ni getStaticPaths que recorra un array local: los posts son ficheros Markdown validados. El identificador pasó de slug a id, y el cuerpo se pinta con <Content />. La ventaja inmediata: si un post olvida description, el build lo avisa antes de publicar. El componente PostCard puede adaptarse para recibir CollectionEntry<'blog'> en lugar del tipo Post manual.

Depuración: si el build falla con «does not match the schema», el mensaje indica el fichero y el campo. Abre ese Markdown y corrige el frontmatter. Para inspeccionar los datos en runtime de desarrollo, imprime {JSON.stringify(post.data)} temporalmente en un post.

6 · Errores habituales

Error 1 — Ubicación equivocada de la config

Mal — ubicación de las colecciones «legacy» 
src/content/config.ts     ← en Astro 5 la config vive en src/content.config.ts
Bien 
src/content.config.ts     ← raíz de src/
src/content/blog/*.md     ← el contenido puede estar donde diga el loader

Error 2 — Olvidar el await

Mal — getCollection devuelve una Promise 
const posts = getCollection('blog');   // posts es una Promise, no un array
posts.map(...);                        // TypeError: posts.map is not a function
Bien 
const posts = await getCollection('blog');

Error 3 — Usar entry.slug en vez de entry.id

Mal 
params: { id: post.slug },   // undefined en la Content Layer
Bien 
params: { id: post.id },

Error 4 — Frontmatter que incumple el esquema

---
title: Post sin fecha
description: Le falta pubDate, que es obligatorio
---

El build fallará con un mensaje del estilo «pubDate: Required» señalando el fichero. Esto es una virtud, no un estorbo: el error se caza en build, no en producción. Corrige el frontmatter añadiendo el campo que falta.

Error 5 — No renderizar el cuerpo

---
const posts = await getCollection('blog');
---
<h1>{posts[0].data.title}</h1>
<!-- Falta render + <Content />: el cuerpo no se ve -->

El frontmatter (data) y el cuerpo (body) son cosas distintas. Para ver el cuerpo, hay que render() y colocar <Content />.

8 · Reto

👥 Relaciona posts con autores con reference()

Crea una colección authors (con loader file() sobre un JSON) con campos id, name y bio. Modifica la colección blog para que author sea una referencia a authors en lugar de un string. En el detalle del post, resuelve la referencia con getEntry(post.data.author) y muestra el nombre y la bio del autor.

Pista: el loader file() se importa de astro/loaders y espera un JSON con un array de objetos que incluyan un id. En el esquema, author: reference('authors') valida que la referencia exista; si un post apunta a un autor inexistente, el build falla. Para resolverla: const autor = await getEntry(post.data.author);.

9 · Resumen

  • Una colección agrupa contenido bajo un esquema Zod validado en build time.
  • En Astro 5 se define en src/content.config.ts con dos piezas: loader (de dónde) y schema (qué forma).
  • Loaders: glob() para ficheros por patrón y file() para un JSON/YAML único.
  • getCollection() y getEntry() son asíncronos y devuelven entradas tipadas.
  • Cada entrada tiene id, data (frontmatter validado) y body.
  • render(entry) produce <Content /> y headings.
  • El tipo CollectionEntry<'blog'> se genera solo; no hay que escribirlo a mano.

10 · Preguntas frecuentes

¿Content collections o import.meta.glob?

Colecciones, siempre que puedas. Te dan validación de esquema, tipos automáticos y una API estable. import.meta.glob sigue siendo útil para casos muy concretos (leer ficheros arbitrarios), pero pierdes la validación y el tipado. La lección anterior lo mostró solo para entender el mecanismo subyacente.

¿Dónde guardo el contenido con la Content Layer?

Donde tú quieras: lo decide el base del loader. Lo habitual es src/content/<coleccion>/, pero puedes tener src/data/posts/ o incluso traer entradas de una API con un loader propio. La carpeta deja de ser una convención obligatoria y pasa a ser una elección.

¿Qué pasa con las colecciones «legacy» de mi proyecto antiguo?

Siguen funcionando en Astro 5: el fichero src/content/config.ts con type: 'content' | 'data' es compatible. Aun así, para proyectos nuevos usa la Content Layer. Migrar suele ser mover la config a src/content.config.ts, añadir un loader y cambiar slug por id y entry.render() por render(entry).

¿Puedo validar el frontmatter con campos condicionales?

Sí. Zod permite construcciones avanzadas: .refine(), uniones, .superRefine()… Por ejemplo, exigir draftNote solo cuando draft sea true. Empieza simple y añade refinamientos cuando el contenido real lo pida.

¿Las colecciones funcionan con SSR?

Sí. La Content Layer es independiente del modo de render: en build time se conoce el contenido y getCollection funciona igual en SSR. La diferencia es cuándo se ejecuta el renderizado, no cómo se leen las entradas.
