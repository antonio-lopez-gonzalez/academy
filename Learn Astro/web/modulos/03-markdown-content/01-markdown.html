Markdown y MDX en Astro

Módulo 3 · Markdown y Content 🕐 30 minutos

1 · Introducción

En el Módulo 2 escribíamos el contenido de cada post como una propiedad body: string dentro de posts.ts. Eso funciona para demostrar el routing, pero es una barbaridad para escribir: el contenido de verdad es texto largo con títulos, listas, enlaces y código. Para eso existe Markdown: un formato de texto plano, legible por humanos, que se convierte en HTML.

Astro integra Markdown de serie, y de una forma muy elegante: un fichero .md dentro de src/pages/ es una página, igual que un .astro. Y si el Markdown se te queda corto, existe MDX: Markdown + componentes, para incrustar interactividad o piezas de UI dentro del texto. En esta lección aprendes ambos, el frontmatter y, sobre todo, cuándo usar cada uno.

¿Por qué Astro apuesta por Markdown? Porque el contenido y el código tienen ciclos de vida distintos: un artículo lo escribe una persona sin tocar el diseño, y el diseño lo cambia alguien sin tocar el texto. Separar formato (Markdown) de presentación (layout) permite que cada uno trabaje sin pisar al otro. Y como Astro lo compila a HTML en build time, el resultado es un sitio estático rapidísimo.

Cuándo lo usarás: páginas de contenido (blog, docs, legales, changelog). Markdown para texto; MDX cuando ese texto necesite componentes vivos.

Errores típicos: escribir HTML a mano dentro del Markdown (rompe el propósito), olvidar el layout en el frontmatter (la página sale sin <html> estilo), equivocar la sintaxis YAML del frontmatter (una coma de más tumba el build) y usar MDX cuando bastaría Markdown (más dependencias y complejidad sin motivo).

2 · Teoría

Qué es Markdown y por qué es tan útil

Markdown es un lenguaje de marcado ligero: escribes # Título y obtienes un <h1>; **negrita** produce <strong>. La clave es que el fichero se lee bien sin renderizar: un editor de texto plano basta para trabajar. Astro lo compila a HTML en build time mediante la librería unified (remark para Markdown, rehype para HTML), que conoceremos a fondo en la lección 3.

GFM de serie: Astro activa GitHub-flavored Markdown por defecto (tablas, tachado ~~texto~~, listas de tareas - [ ], autolinks) y también smartypants (comillas tipográficas y guiones largos). El resaltado de bloques de código lo hace Shiki en build time: cero JavaScript en el navegador.

Frontmatter: los datos de la página

Todo fichero Markdown puede empezar con un bloque YAML entre ---. Ese bloque es el frontmatter, y sus claves llegan al layout como datos:

src/pages/aviso-legal.md
---
layout: ../layouts/BaseLayout.astro   # qué layout envuelve esta página
title: Aviso legal                    # datos propios, libres
updatedAt: 2026-04-01
---

Este párrafo es el contenido. Nada de HTML.

La clave reservada más importante es layout: le dice a Astro con qué componente envolver el HTML generado (esto lo viste en la lección de layouts). Todas las demás claves son tuyas: las inventas según necesites.

El layout recibe el frontmatter y los títulos

Cuando un Markdown usa un layout, ese layout recibe unas props especiales en Astro.props:

// Dentro del layout que envuelve un Markdown:
const { frontmatter, headings, url } = Astro.props;
// frontmatter → las claves del bloque YAML
// headings    → array de títulos { depth, slug, text } (ideal para un TOC)
// url         → la URL de la página

MDX: Markdown que sabe usar componentes

MDX es Markdown con superpoderes: puedes importar y usar componentes dentro del texto. Se instala con la integración oficial @astrojs/mdx:

# Añade la integración MDX al proyecto (actualiza astro.config y package.json)
pnpm astro add mdx
src/pages/demo.mdx
---
layout: ../layouts/BaseLayout.astro
title: Demo con componentes
---

import Callout from '../components/Callout.astro';

# Documento MDX

Esto es Markdown normal, pero además puedo incrustar componentes:

<Callout type="tip">
  Este bloque lo pinta un componente .astro importado.
</Callout>

¿Cuándo usar MDX y cuándo Markdown? Regla simple: si el contenido se puede escribir sin componentes, usa .md. Usa .mdx solo cuando necesites un componente concreto dentro del texto (un gráfico, un vídeo embebido, un aviso reutilizable o una isla interactiva). MDX añade dependencia y complejidad; no lo conviertas en el formato por defecto.

Lo diferencial de Astro no es «tener Markdown» (todos lo tienen), sino tenerlo integrado con el mismo sistema de layouts y componentes, sin peajes de configuración.

3 · Ejemplo mínimo

Una página Markdown con frontmatter y un layout. Primero el layout mínimo que la envolverá:

src/layouts/BaseLayout.astro
---
// Propiedades que recibe un layout que envuelve Markdown.
interface Props {
  frontmatter: { title?: string };  // las claves del bloque YAML
}
const { frontmatter } = Astro.props;
---

<!DOCTYPE html>
<html lang="es">
  <head>
    <meta charset="UTF-8" />
    <!-- El título sale del frontmatter del Markdown -->
    <title>{frontmatter.title}</title>
  </head>
  <body>
    <main>
      <!-- Aquí entra el HTML que Astro genera desde el Markdown -->
      <slot />
    </main>
  </body>
</html>
src/pages/about.md
---
layout: ../layouts/BaseLayout.astro
title: Sobre mí
---

# Sobre mí

Soy desarrolladora y este es mi blog. Escribo en **Markdown**,
que Astro convierte a HTML en build time.

- Sin framework de UI
- Sin JavaScript en el navegador
- Con `pnpm dev` para ver los cambios al instante

[Aprende Astro](https://astro.build)

Línea por línea: el frontmatter declara layout (ruta relativa desde el fichero Markdown) y title. Astro compila el Markdown a HTML y lo inyecta en el <slot /> del layout. El layout lee Astro.props.frontmatter.title para el <title>. El resultado es dist/about/index.html, exactamente igual que si lo hubieras escrito en un .astro, pero con texto mucho más cómodo de mantener. El bloque de código con lenguaje se resalta automáticamente con Shiki.

4 · Ejemplo real

Convertimos el blog del Módulo 2 a contenido Markdown: los posts viven en src/pages/blog/ como ficheros .md, con un layout de artículo y un listado que los descubre automáticamente.

El layout de artículo (reutiliza el chasis del módulo anterior)

src/layouts/BlogLayout.astro
---
import BaseLayout from './BaseLayout.astro';

interface Props {
  frontmatter: {
    title: string;
    description?: string;
    pubDate: Date;
    author: string;
  };
  headings: Array<{ depth: number; slug: string; text: string }>;
}
const { frontmatter, headings } = Astro.props;

// Construimos un índice (TOC) solo con los h2 de nivel 2.
const toc = headings.filter((h) => h.depth === 2);
---

<BaseLayout title={`${frontmatter.title} — Bitácora`}>
  <article>
    <header>
      <h1>{frontmatter.title}</h1>
      <p>Por {frontmatter.author} · {frontmatter.pubDate.toLocaleDateString('es-ES')}</p>
    </header>

    <!-- Índice generado desde los títulos reales del Markdown -->
    {toc.length > 0 && (
      <nav>
        <ol>{toc.map((h) => <li><a href={`#${h.slug}`}>{h.text}</a></li>)}</ol>
      </nav>
    )}

    <!-- El Markdown compilado entra aquí -->
    <slot />
  </article>
</BaseLayout>

El listado que descubre los posts automáticamente

src/pages/blog/index.astro
---
import BaseLayout from '../../layouts/BaseLayout.astro';

// import.meta.glob es una función de Vite: importa TODOS los ficheros
// que casen con el patrón. Con eager:true los importa al instante.
// Cada módulo expone su `frontmatter` y su `url`.
const modules = import.meta.glob('./*.md', { eager: true });

// Normalizamos a un array tipado y ordenamos por fecha (más nuevo primero).
const posts = Object.entries(modules)
  .map(([path, mod]: any) => ({
    url: mod.url,                       // p. ej. '/blog/hola-astro/'
    ...mod.frontmatter,                 // title, description, pubDate...
  }))
  .sort((a, b) => new Date(b.pubDate).getTime() - new Date(a.pubDate).getTime());
---

<BaseLayout title="Blog">
  <h1>Blog</h1>
  <ul>
    {posts.map((post) => (
      <li>
        <a href={post.url}>{post.title}</a> — {post.description}
      </li>
    ))}
  </ul>
</BaseLayout>

Aviso honesto: import.meta.glob funciona, pero es la vía «manual». La forma recomendada y tipada de listar contenido en Astro 5 son las content collections, que verás en la siguiente lección. Con ellas, getCollection('blog') te da los posts ya validados contra un esquema. Este ejemplo sirve para entender que el listado no «sabe» de antemano qué posts hay: los descubre del sistema de archivos.

6 · Errores habituales

Error 1 — HTML incrustado en Markdown

Mal — mezclas formato con contenido 
---
title: Post
---

<div class="post">
  <h1>Título</h1>
  <p>Texto</p>
</div>
Bien — Markdown puro; la estructura la pone el layout 
---
title: Post
layout: ../layouts/BlogLayout.astro
---

# Título

Texto

Error 2 — Frontmatter YAML mal formado

Mal — falta cerrar y hay comas de más 
---
title: Hola
pubDate: 2026-01-10,
tags: [astro, mpa,
---

Contenido
Bien — YAML válido 
---
title: Hola
pubDate: 2026-01-10
tags: [astro, mpa]
---

Contenido

El frontmatter es YAML: sin comas finales, con las listas bien cerradas y el bloque --- abierto y cerrado. Un fallo aquí tumba el build con un error de parseo.

Error 3 — Usar MDX sin necesidad

Mal — MDX para texto plano 
---
title: Aviso legal
layout: ../layouts/BaseLayout.astro
---
# Aviso legal

Texto sin ningún componente.

Si no hay componentes, .mdx solo añade dependencia y tiempo de build. Renómbralo a .md.

Error 4 — El layout olvida el <slot />

<body>
  <h1>{frontmatter.title}</h1>
  <!-- Falta <slot />: el contenido del Markdown desaparece -->
</body>

Mismo síntoma que en los layouts del Módulo 2: la página se ve con el chasis pero sin cuerpo. Los layouts de Markdown son layouts normales; necesitan su <slot />.

8 · Reto

📑 Índice de contenidos automático

Añade al BlogLayout un índice (TOC) que se genere automáticamente a partir de los títulos del Markdown (las props headings). Debe listar solo los h2, enlazar a cada sección por su slug y ocultarse si el post no tiene subtítulos. Después, escribe un post con al menos tres h2 para probarlo.

Pista: ya tienes el array headings en Astro.props; filtra por h.depth === 2 y solo pinta el <nav> si toc.length > 0. Los slug ya están generados por Astro, así que los <a href={`#${h.slug}`}> funcionan sin configurar nada.

9 · Resumen

  • Un .md en src/pages/ es una página: Astro lo compila a HTML en build time.
  • El frontmatter (YAML entre ---) lleva los datos; la clave layout decide su envoltorio.
  • El layout recibe frontmatter, headings y url en Astro.props.
  • MDX (@astrojs/mdx) permite usar componentes dentro del texto; úsalo solo cuando lo necesites.
  • Astro trae GFM y smartypants de serie y resalta el código con Shiki sin JavaScript.
  • Para listar Markdown existe import.meta.glob, pero lo recomendado son las content collections (lección siguiente).

10 · Preguntas frecuentes

¿Puedo usar Markdown fuera de src/pages/?

Sí. Fuera de pages/ el Markdown no es una página, sino contenido que se importa. Es exactamente como funcionan las content collections: ficheros Markdown en src/content/ que luego lees con getCollection. La diferencia es que en pages/ la ruta es automática.

¿Necesito una extensión de VSCode para Markdown?

No es obligatoria, pero ayuda: el soporte nativo de Markdown de VSCode ya previsualiza los ficheros, y la extensión del lenguaje Astro añade soporte para frontmatter y MDX. Para MDX, la extensión oficial de Astro es lo más cómodo.

¿Qué pasa con el HTML que escribo a mano dentro del Markdown?

Markdown permite HTML incrustado y Astro lo respeta, pero rompe la separación contenido/forma y a menudo complica el mantenimiento. Prefiere Markdown puro y deja la estructura al layout o a componentes. Cuando de verdad necesites algo más, MDX con un componente es más limpio que HTML suelto.

¿El resaltado de código añade JavaScript al navegador?

No. Astro usa Shiki en build time: el HTML sale ya con los colores aplicados mediante <span> clasificados. En el navegador no se ejecuta nada para resaltar. Puedes personalizar el tema en astro.config.mjs (markdown.shikiConfig), como verás en la lección 3.

¿Puedo tener Markdown con componentes sin instalar MDX?

No de forma nativa: el Markdown puro no admite componentes. La vía limpia es MDX. La alternativa pobre sería HTML incrustado, que ya hemos desaconsejado. Instalar MDX es un comando (pnpm astro add mdx) y no afecta al resto del proyecto.
