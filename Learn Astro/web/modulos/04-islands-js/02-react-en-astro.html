Componentes React como islands

Módulo 4 · Islands e Interactividad 🕐 35 minutos

1 · Introducción

Ya sabes qué es una isla. Ahora toca lo práctico: escribir componentes React y convertirlos en islas dentro de Astro. React es la integración más usada y, bien entendida, la más potente: te da estado, hooks y todo el ecosistema de librerías, pero solo donde de verdad hace falta.

El reto no es solo configurar la integración. El reto de fondo es desarrollar criterio: saber cuándo un componente debe ser React y cuándo debe quedarse como .astro. Un equipo que mete React en todo termina con un SPA disfrazado y pierde las ventajas de Astro; un equipo que no lo usa nunca se queda sin interactividad. Esta lección te da la frontera exacta.

¿Por qué existe esta lección? Porque la mayoría de tutoriales de Astro asumen que vienes de React y cometen el error inverso: meter React hasta en el layout. Aquí aprendes a usarlo como una herramienta quirúrgica. Entender la frontera Astro/React es entender Astro.

2 · Teoría

Qué aporta la integración @astrojs/react

Astro no trae React de fábrica: es agnóstico de framework. La integración @astrojs/react le enseña a Astro tres cosas:

  1. Renderizar componentes .jsx/.tsx a HTML en el servidor, igual que hace un componente .astro.
  2. Hidratarlos en el cliente cuando reciben una directiva client:*, cargando el runtime de React solo para esas islas.
  3. Configurar Vite para compilar JSX/TSX con el transform correcto.

Instalación en un paso. El comando pnpm astro add react instala el paquete, añade la integración a astro.config.mjs y actualiza tsconfig.json automáticamente. Prefierelo a instalar a mano: evita olvidar la configuración de JSX.

Terminal
# Instala y configura la integracion de React en un solo comando.
pnpm astro add react
astro.config.mjs (resultado)
// Importamos la integracion oficial de React.
import { defineConfig } from 'astro/config';
import react from '@astrojs/react';

export default defineConfig({
  // Registramos React como integracion: habilita las islands React.
  integrations: [react()],
});

La frontera: cuándo React y cuándo .astro

La regla es simple y se deriva directamente de la lección anterior: React solo donde haya estado o eventos que cambien en el cliente. Todo lo demás es .astro.

Necesitas…UsaPor qué
Layout, cabecera, pie, texto, listas estáticas.astroCero JavaScript; se renderiza a HTML y listo
Renderizar datos en build time.astroEl frontmatter puede hacer await y acceder a APIs del servidor
Un formulario con validación interactivaReact (isla)Necesita estado y manejo de eventos en el cliente
Filtros, pestañas, carruseles, modalesReact (isla)UI que cambia sin recargar la página
Un widget con una librería solo-navegadorReact + client:onlyNo puede pre-renderizarse en el servidor

Analogía: un componente .astro es una fotografía: se toma una vez (en el build) y se entrega impresa. Un componente React hidratado es una pizarra viva: se entrega con un dibujo (el HTML pre-renderizado) pero además alguien puede escribir en ella (el cliente). Si no necesitas que nadie escriba, la fotografía es más barata y suficiente.

Pasar props: la frontera de serialización

Cuando Astro pasa props a una isla, esos datos se serializan a JSON y se incrustan en la página para que el cliente los reconstruya. Esto impone una regla dura:

  • Solo cruzan la frontera datos serializables: strings, números, booleanos, arrays, objetos planos, fechas (ISO), etc.
  • No cruzan funciones, clases con métodos, instancias de Date complejas, símbolos ni objetos de terceros con lógica.
  • Sí puedes pasar objetos definidos en el frontmatter .astro (y tipados con TypeScript) como si fueran constantes.

Error clásico: pasar onClick={handler} desde un .astro a una isla React. No funciona: una función no se puede serializar. Los manejadores de eventos se definen dentro del componente React (que sí vive en el cliente), nunca se pasan desde Astro.

Estado y ciclo de vida: React normal, aislado

Dentro de una isla, React funciona exactamente como lo conoces: useState, useEffect, useReducer, etc. La única diferencia es que cada isla es un árbol de React independiente:

Pagina Astro (HTML estatico)
+-------------------------------------------------------+
|  <Header />            estatico, sin React            |
|                                                       |
|  +---------------------+   +---------------------+    |
|  | ISLA React A        |   | ISLA React B        |    |
|  | root React propio   |   | root React propio   |    |
|  | estado aislado      |   | estado aislado      |    |
|  +---------------------+   +---------------------+    |
|                                                       |
|  <Footer />            estatico, sin React            |
+-------------------------------------------------------+
   A y B NO comparten estado por defecto: son dos roots.

Si dos islas necesitan compartir estado (por ejemplo un carrito que se refleja en la cabecera y en el resumen), las opciones son: pasarlo como props desde la página (si es estático), usar un store externo mínimo como nanostores, o fusionarlas en una única isla. En el proyecto del módulo lo verás en la práctica.

3 · Ejemplo mínimo

Un componente React con una prop tipada y un poco de estado. Explicado línea a línea:

src/components/Greeting.tsx
// useState es la unica API de React que necesitamos aqui.
import { useState } from 'react';

// Definimos el tipo de las props con TypeScript. Al ser una isla,
// estas props llegan serializadas desde el .astro que la usa.
interface GreetingProps {
  name: string;        // obligatoria: quien te saluda
  initialCount?: number; // opcional: valor de arranque
}

export default function Greeting({ name, initialCount = 0 }: GreetingProps) {
  // Estado local de la isla, inicializado con la prop (o 0 por defecto).
  const [count, setCount] = useState(initialCount);

  return (
    <div>
      <p>Hola, {name}. Llevas {count} saludos.</p>
      {/* El listener se define AQUI, en el cliente, nunca en el .astro. */}
      <button onClick={() => setCount(count + 1)}>Saludar</button>
    </div>
  );
}
src/pages/index.astro
---
// Importamos el componente React como cualquier otro componente.
import Greeting from '../components/Greeting.tsx';
---

<html lang="es">
  <body>
    <h1>Demo de isla React</h1>

    <!-- Astro renderiza Greeting a HTML en el build y, ademas,
         hidrata el componente en el cliente (client:load). -->
    <!-- Las props name y initialCount son serializables (string y number). -->
    <Greeting name="Ada" initialCount={3} client:load />
  </body>
</html>

Claves del ejemplo:

  1. Props tipadas: la interfaz GreetingProps documenta y valida en compilación qué recibe la isla.
  2. Valor por defecto: initialCount = 0 en la desestructuración evita undefined si no se pasa.
  3. Estado vs props: initialCount solo inicializa el estado. Los clics cambian count, no la prop. React no «escucha» cambios de prop salvo que lo programes.
  4. Listener dentro del componente: el onClick vive en el cliente. Astro nunca lo serializa.

4 · Ejemplo real

Un patrón muy habitual: una página que renderiza en build time una lista de artículos y ofrece una isla React para filtrarlos por categoría sin recargar. La página sigue siendo estática; solo el filtro es isla.

src/components/ArticleFilter.tsx
import { useMemo, useState } from 'react';

// Tipamos un articulo simplificado. Debe ser serializable (objeto plano).
export interface Article {
  slug: string;
  title: string;
  category: string;
}

interface Props {
  articles: Article[]; // llegan pre-renderizados desde el .astro
}

export default function ArticleFilter({ articles }: Props) {
  // Estado: la categoria activa. Un estado = un filtro controlado.
  const [category, setCategory] = useState('todas');

  // Derivamos las categorias unicas de los datos (se recalcula al vuelo).
  const categories = useMemo(
    () => ['todas', ...new Set(articles.map((a) => a.category))],
    [articles]
  );

  // Lista filtrada: pura derivacion del estado actual, sin estado extra.
  const visible =
    category === 'todas'
      ? articles
      : articles.filter((a) => a.category === category);

  return (
    <section>
      {/* Botones de filtro: cada uno fija el estado 'category'. */}
      <div role="group" aria-label="Filtrar por categoria">
        {categories.map((c) => (
          <button
            key={c}
            onClick={() => setCategory(c)}
            aria-pressed={c === category}
          >
            {c}
          </button>
        ))}
      </div>

      {/* Renderizamos solo lo filtrado. */}
      <ul>
        {visible.map((a) => (
          <li key={a.slug}><strong>{a.title}</strong> — {a.category}</li>
        ))}
      </ul>
    </section>
  );
}
src/pages/articulos.astro
---
// Este codigo corre en build time (servidor). Podriamos incluso hacer fetch.
import ArticleFilter, { type Article } from '../components/ArticleFilter.tsx';

// Datos de ejemplo; en el Modulo 5 vendran de una API o content collection.
const articles: Article[] = [
  { slug: 'astro-islands', title: 'Islands', category: 'arquitectura' },
  { slug: 'finetuning', title: 'Ajuste fino', category: 'rendimiento' },
  { slug: 'tailwind-tips', title: 'Tailwind util', category: 'estilos' },
];
---

<html lang="es">
  <body>
    <h1>Articulos</h1>

    <!-- El HTML con los articulos se pre-renderiza y ademas la isla
         los recibe como props (array serializable) para poder filtrar. -->
    <ArticleFilter articles={articles} client:visible />
  </body>
</html>

Decisiones explicadas:

  • Datos en el frontmatter: los artículos se preparan en build time. En un caso real vendrían de Markdown, Content Collections o una API (Módulo 5).
  • Props serializables: un array de objetos planos cruza la frontera sin problema.
  • El filtrado es estado de cliente: no requiere volver al servidor. Por eso es una isla y no una página nueva por categoría.
  • client:visible: el filtro está a media página; no bloquea la primera carga.

Alternativa estática: si el filtrado fuera por enlaces (/articulos/arquitectura), no necesitarías JavaScript en absoluto: serían páginas estáticas generadas con getStaticPaths. La isla solo se justifica cuando quieres filtrar sin navegar. Que exista React no significa que debas usarlo.

6 · Errores habituales

Pasar un manejador de eventos desde el .astro

✗ Incorrecto

---
import Button from '../components/Button.tsx';
// Una funcion NO se puede serializar hacia el cliente.
const handleClick = () => alert('hola');
---
<Button onClick={handleClick} client:load />

✓ Correcto

// El manejador se define DENTRO del componente que vive en el cliente.
export default function Button() {
  return <button onClick={() => alert('hola')}>Pulsar</button>;
}

La frontera servidor/cliente serializa props a JSON. Las funciones no cruzan; los eventos se declaran dentro de la isla.

Usar React para contenido estático

✗ Incorrecto

<!-- Componente React puramente presentacional e hidratado: JS innecesario. -->
<Hero client:load />
<Features client:load />
<Testimonials client:load />

✓ Correcto

<!-- En Astro, la presentacion estatica se escribe en .astro (cero JS). -->
<Hero />
<Features />
<Testimonials />

Si un componente no tiene estado ni eventos, .astro lo hace mejor y más barato. React aporta valor solo cuando hay interactividad real.

Olvidar la directiva client:*

✗ Incorrecto

<!-- Se renderiza, pero el onClick no se engancha: isla inerte. -->
<Counter />

✓ Correcto

<!-- La directiva aporta la hidratacion y, con ella, los eventos. -->
<Counter client:load />

Es el error más frecuente: el componente «se ve» pero no responde. Casi siempre falta la directiva client:*.

Compartir estado entre islas «a lo loco»

✗ Incorrecto

<!-- Dos islas que "deberian" compartir estado, pero son roots distintos. -->
<AddToCart client:load />
<CartIcon client:load />   <!-- no se enteran la una de la otra -->

✓ Correcto

<!-- Opcion A: una sola isla que contiene ambos. Opcion B: un store
     externo (nanostores) que ambos importan y comparten. -->
<Cart client:load />

Por defecto no hay estado compartido entre islas. Hay que diseñarlo explícitamente con un store o fusionando componentes.

7 · Ejercicio guiado

Objetivo: crear una isla React de pestañas (tabs) que cambia el panel visible sin recargar la página, dentro de una página Astro estática.

  1. Instala la integración si no la tienes: 
    pnpm astro add react
  2. Crea el componente React con estado en src/components/Tabs.tsx: 
    import { useState } from 'react';

interface Tab { id: string; label: string; content: string; }
interface Props { tabs: Tab[]; }

export default function Tabs({ tabs }: Props) {
  // Estado: id de la pestana activa. Arrancamos en la primera.
  const [active, setActive] = useState(tabs[0]?.id);

  return (
    <div>
      <!-- Botonera: aria-selected comunica el estado a lectores de pantalla. -->
      <div role="tablist">
        {tabs.map((t) => (
          <button
            key={t.id}
            role="tab"
            aria-selected={active === t.id}
            onClick={() => setActive(t.id)}
          >
            {t.label}
          </button>
        ))}
      </div>
      <!-- Panel activo: derivado del estado, sin estado redundante. -->
      <div role="tabpanel">{tabs.find((t) => t.id === active)?.content}</div>
    </div>
  );
}
  3. Úsalo como isla desde una página .astro, pasando los datos como prop serializable: 
    ---
import Tabs from '../components/Tabs.tsx';
const tabs = [
  { id: 'a', label: 'Resumen', content: 'Vista general del producto.' },
  { id: 'b', label: 'Detalles', content: 'Especificaciones tecnicas.' },
];
---
<h2>Ficha de producto</h2>
<Tabs tabs={tabs} client:visible />
  4. Verifica la hidratación: arranca pnpm dev, abre la página y pulsa las pestañas. El panel cambia sin recargar.
  5. Comprueba el HTML pre-renderizado: en DevTools, desactiva JavaScript (Settings → Debugger → Disable JavaScript) y recarga. Debes seguir viendo el contenido de la primera pestaña: es el HTML que vino del servidor. Esto demuestra que la isla no es una SPA.

8 · Reto

🎯 Dos islas que comparten un contador

Crea una página con dos islas React separadas: un botón «Añadir al carrito» y un icono de carrito que muestra el número de artículos. Al principio no se comunicarán (cada una tiene su propio estado y su propio root). Haz que compartan estado usando nanostores más el paquete @nanostores/react, sin fusionarlas en un solo componente.

Después responde: ¿por qué importa que el estado viva fuera de los componentes para que dos islas lo compartan? ¿Qué ventaja tiene frente a meter todo en una única isla gigante?

Pista: un store es un objeto con get(), set() y subscribe(). El hook useStore() suscribe el componente React al store y lo re-renderiza cuando cambia. Recuerda: solo props serializables cruzan desde Astro; el store se importa dentro de cada isla, en el cliente.

9 · Resumen

  • @astrojs/react enseña a Astro a renderizar e hidratar componentes React como islas.
  • Instala con pnpm astro add react; la integración se registra en astro.config.mjs.
  • React va solo donde hay estado o eventos; lo presentacional se queda en .astro.
  • Las props cruzan la frontera serializadas: nada de funciones ni clases con métodos.
  • Cada isla es un root de React independiente: el estado no se comparte por defecto.
  • Para compartir estado entre islas: props desde Astro, un store externo (nanostores) o fusionar componentes.
  • Una directiva client:* es obligatoria para que la isla sea interactiva.

10 · Preguntas frecuentes

¿React se envía al navegador si no uso ninguna isla?

No. Si no hay ninguna directiva client:*, Astro renderiza los componentes React a HTML y no envía el runtime de React. El framework solo se descarga cuando hay al menos una isla hidratada en la página, y en ese caso se comparte entre todas las islas de esa página.

¿Puedo usar React Context para compartir estado entre islas?

No a través de islas separadas: cada isla es un root distinto de React, por lo que un Provider en una isla no alcanza a otra. Solo puedes usar Context dentro de una misma isla (con sus subcomponentes). Para compartir entre islas necesitas un store externo como nanostores o props desde la página.

¿Por qué mi isla «se ve» pero no reacciona a los clics?

Casi siempre falta la directiva client:*. Sin ella, Astro entrega el HTML pre-renderizado pero no hidrata: no hay listeners. Añade client:load, client:idle o client:visible según la urgencia. Otra causa menos común es un desajuste entre el HTML del servidor y el del cliente, que hace fallar la hidratación: revisa la consola de DevTools.

¿Puedo pasar un objeto que definí en el frontmatter como prop?

Sí, siempre que sea serializable (objeto plano, array, primitivos, fechas en ISO). Lo que creas en el frontmatter vive en el servidor, se serializa a JSON y se reconstruye en el cliente. No cruzarán funciones, clases con comportamiento ni objetos con referencias circulares. Tiparlo con TypeScript te avisará si te sales del contrato.

¿Merece la pena React si solo necesito un acordeón?

A veces no. Un acordeón simple puede resolverse con el elemento nativo <details>/<summary>, que es accesible y no necesita JavaScript. React tiene sentido cuando hay comportamiento que el HTML nativo no cubre (estado complejo, sincronización, efectos). El criterio es: usa la herramienta más simple que resuelva el problema.
