Proyecto: zona privada con auth

Módulo 8 · Auth y Despliegue 🕐 45 minutos

1 · Introducción

En este proyecto cierras el Módulo 8 construyendo una zona privada completa: una página de login, una sesión con cookie HttpOnly, un middleware que protege las rutas privadas, un área de usuario que lee datos por sesión, un logout que invalida, y el despliegue a producción con variables de entorno. Todo, de principio a fin.

Es el patrón que reaparecerá en casi cualquier aplicación real: una parte pública que cualquiera ve y una parte privada que solo ve quien ha demostrado quién es.

¿Por qué este proyecto? Porque la autenticación se aprende montándola entera, no leyendo piezas. Aquí unirás cookies, middleware, endpoints, SSR, variables de entorno y despliegue en un solo artefacto funcional. Y lo harás con la seguridad en su sitio desde el minuto uno, no como parche al final: cookie HttpOnly, guardia en servidor, secretos fuera del repositorio.

2 · Teoría

El mapa de la zona privada

Antes de escribir código, dibujamos la frontera. A la izquierda, lo público; a la derecha, lo privado. El middleware es la puerta.

  PUBLICO                                    PRIVADO
  +--------------------+        +-----------------------------------+
  | / (landing)        |        | /login  (form, publica)            |
  | /precios           |        |                                    |
  | /blog/[slug]       |        | --- puerta: middleware ---         |
  | /api/login (POST)  |        | /dashboard   (requiere sesion)     |
  +--------------------+        | /dashboard/perfil (idem)           |
                                | /api/logout  (POST)                |
                                +-----------------------------------+

Reglas de oro que aplicaremos

  • La cookie es HttpOnly: imposible de leer desde JavaScript.
  • La cookie lleva solo un id opaco (aleatorio), nunca el email ni el rol.
  • El servidor es la autoridad: las páginas privadas se renderizan tras la guardia; el cliente no decide nada.
  • Los secretos van en variables de entorno del servidor y no al repositorio.
  • La zona privada no se cachea en el CDN: cada petición se renderiza para su usuario.

Analogía: piensa en un edificio de oficinas. La planta baja es pública (landing), el ascensor es el middleware (comprueba tu tarjeta), y cada planta privada solo se abre si la tarjeta es válida y tiene permiso para esa planta. La tarjeta (cookie) no dice tu nombre completo: solo un número que el guardia consulta en su registro (el almacén de sesiones).

El esqueleto ejecutable: sin estilos, sin base de datos, sin almacén sofisticado. Solo el flujo login → cookie → guardia → panel → logout, en versión mínima.

src/pages/api/login.ts
import type { APIRoute } from 'astro';

export const POST: APIRoute = async ({ request, cookies, redirect }) => {
  const form = await request.formData();
  const email = String(form.get('email') ?? '');
  const password = String(form.get('password') ?? '');

  // Credenciales de prueba (en el proyecto real: base de datos + hash).
  if (email !== 'ana@example.com' || password !== 'secreto123') {
    return redirect('/login?error=1');
  }

  cookies.set('session', crypto.randomUUID(), {
    path: '/', httpOnly: true, secure: true, sameSite: 'lax', maxAge: 60 * 60 * 24,
  });
  return redirect('/dashboard');
};
src/middleware.ts
import { defineMiddleware } from 'astro:middleware';

export const onRequest = defineMiddleware(async (context, next) => {
  const id = context.cookies.get('session')?.value;
  context.locals.user = id ? { id, name: 'Ana' } : null;

  if (context.url.pathname.startsWith('/dashboard') && !context.locals.user) {
    return context.redirect('/login');
  }
  return next();
});

Con esto ya funciona el flujo básico. El resto del proyecto consiste en endurecerlo: un almacén de sesiones real, un módulo de auth reutilizable, el formulario maquetado, la destrucción de sesión al salir y el despliegue.

Paso 1 — El almacén de sesiones

src/lib/session.ts
// Almacen de sesiones en memoria. Sirve para practicar y para un servidor
// unico; en produccion con varias instancias usarias Redis o base de datos.
type Session = { userId: string; email: string; name: string; expiresAt: number };

const store = new Map<string, Session>();

// Duracion de la sesion: 7 dias.
const TTL = 60 * 60 * 24 * 7 * 1000;

// Crea una sesion opaca: el id es un UUID aleatorio, sin datos dentro.
export function createSession(user: { id: string; email: string; name: string }): string {
  const id = crypto.randomUUID();
  store.set(id, { userId: user.id, email: user.email, name: user.name, expiresAt: Date.now() + TTL });
  return id;
}

// Devuelve la sesion solo si existe y no ha caducado.
export function getSession(id: string | undefined): Session | null {
  if (!id) return null;
  const s = store.get(id);
  if (!s) return null;
  if (s.expiresAt < Date.now()) {
    store.delete(id); // limpia la caducada
    return null;
  }
  // Renovacion deslizante: cada uso extiende la vida de la sesion.
  s.expiresAt = Date.now() + TTL;
  return s;
}

// Invalida la sesion en el servidor (no basta con borrar la cookie).
export function destroySession(id: string | undefined): void {
  if (id) store.delete(id);
}

Paso 3 — La guardia centralizada

src/middleware.ts
import { defineMiddleware } from 'astro:middleware';
import { getSession } from './lib/session';

// Cualquier ruta bajo estos prefijos exige sesion.
const PROTECTED = ['/dashboard'];

export const onRequest = defineMiddleware(async (context, next) => {
  const sessionId = context.cookies.get('session')?.value;
  const session = getSession(sessionId);

  // Resolvemos identidad una vez y la dejamos en locals para las paginas.
  context.locals.sessionId = session ? sessionId : undefined;
  context.locals.user = session
    ? { id: session.userId, email: session.email, name: session.name }
    : null;

  const isPrivate = PROTECTED.some((p) => context.url.pathname.startsWith(p));
  if (isPrivate && !context.locals.user) {
    // Sesion inexistente o caducada: fuera.
    return context.redirect('/login');
  }

  // Las paginas privadas no deben cachearse en el CDN.
  const response = await next();
  if (isPrivate) {
    response.headers.set('Cache-Control', 'private, no-store');
  }
  return response;
});

Paso 4 — Login y logout

src/pages/api/login.ts
import type { APIRoute } from 'astro';
import { createSession } from '../../lib/session';

export const POST: APIRoute = async ({ request, cookies, redirect }) => {
  const form = await request.formData();
  const email = String(form.get('email') ?? '').trim().toLowerCase();
  const password = String(form.get('password') ?? '');

  // En un proyecto real: buscar el usuario y comprobar el HASH de la contrasena.
  const valid = email === 'ana@example.com' && password === 'secreto123';
  if (!valid) {
    // Respuesta uniforme: no revelamos si el fallo fue email o contrasena.
    return redirect('/login?error=1');
  }

  const sessionId = createSession({ id: 'u_1', email, name: 'Ana' });
  cookies.set('session', sessionId, {
    path: '/',
    httpOnly: true,                  // JavaScript del navegador no la lee
    secure: import.meta.env.PROD,    // HTTPS obligatorio en produccion
    sameSite: 'lax',                 // mitigacion de CSRF
    maxAge: 60 * 60 * 24 * 7,        // 7 dias
  });

  return redirect('/dashboard');
};
src/pages/api/logout.ts
import type { APIRoute } from 'astro';
import { destroySession } from '../../lib/session';

export const POST: APIRoute = async ({ cookies, redirect }) => {
  // Invalidamos la sesion en el servidor...
  destroySession(cookies.get('session')?.value);
  // ...y borramos la cookie del navegador.
  cookies.delete('session', { path: '/' });
  return redirect('/login');
};

Decisiones explicadas:

  • Sesión opaca en un módulo aparte: session.ts aísla la lógica (crear, leer, caducar, destruir) para que el middleware y los endpoints no repitan código.
  • Renovación deslizante: cada uso alarga la vida de la sesión; el usuario activo no se ve expulsado a mitad de tarea.
  • Logout que invalida de verdad: no basta con borrar la cookie del navegador; la sesión se elimina también en el servidor.
  • El middleware corta y añade cabeceras: protege /dashboard y marca esas respuestas como no-store para que el CDN no sirva la página de un usuario a otro.
  • La cookie usa secure solo en producción: en local (HTTP) no bloquearía el login.
  • Respuesta de login uniforme: el mismo mensaje para cualquier fallo, para no filtrar qué emails existen.

Limitación consciente: el Map en memoria se pierde al reiniciar el servidor y no se comparte entre varias instancias. Es perfecto para aprender y para un despliegue de una sola instancia. En producción real, sustituye session.ts por Redis o una tabla de base de datos manteniendo la misma interfaz: el resto del proyecto no cambia.

6 · Errores habituales

El panel se cachea y muestra datos de otro usuario

✗ Incorrecto

// El CDN puede guardar esta respuesta y servirla a otro usuario.
return next();

✓ Correcto

const response = await next();
if (isPrivate) response.headers.set('Cache-Control', 'private, no-store');
return response;

Las páginas con datos personales no deben cachearse compartidamente. Sin no-store, un proxy o CDN puede servir el panel de Ana a quien pida la misma URL.

Confundir «autenticado» con «autorizado»

✗ Incorrecto

// Basta estar logueado para ver el panel de administracion: grave.
if (!context.locals.user) return context.redirect('/login');
// ...y ya esta, cualquiera con cuenta entra en /admin

✓ Correcto

// Autenticacion (quien eres) y autorizacion (que puedes hacer) son dos pasos.
if (context.url.pathname.startsWith('/admin') && context.locals.user?.role !== 'admin') {
  return new Response('Acceso denegado', { status: 403 });
}

Estar logueado no significa tener permiso. Separa ambos conceptos y comprueba el rol para cada zona sensible.

Perder la sesión al recargar una página estática

✗ Incorrecto

<!-- Pagina del panel pre-renderizada: NO puede leer la cookie. -->
<!-- export const prerender = true;  (o no declararlo en modo static) -->

✓ Correcto

---
// La ruta privada DEBE renderizarse por peticion.
export const prerender = false;
---

Una página privada estática se genera en el build sin sesión. Marcar prerender = false (con adaptador) es obligatorio para leer la cookie del usuario.

Guardar el mensaje de error del login de forma demasiado detallada

✗ Incorrecto

/login?error=email-no-existe
/login?error=password-incorrecta

✓ Correcto

// Un unico error generico: no ayudamos a enumerar usuarios.
return redirect('/login?error=1');

Distinguir «email no existe» de «contraseña mal» permite a un atacante descubrir qué cuentas existen. Un mensaje único evita la enumeración.

Usar una clave de sesión prevista para firma como texto plano

✗ Incorrecto

// Si en algun momento firmas cookies/tokens, esta clave NUNCA va con PUBLIC_.
PUBLIC_SESSION_SECRET=clave-corta

✓ Correcto

# Sin PUBLIC_: solo el servidor la ve. Larga y aleatoria.
SESSION_SECRET=una-cadena-larga-y-aleatoria-generada-con-crypto

Un secreto de firma con prefijo PUBLIC_ queda en el bundle y cualquiera podría falsificar sesiones. Sin prefijo, y generado de forma aleatoria.

8 · Reto

🎯 Convierte la zona privada en un sistema con roles, registro y CSRF

Lleva el proyecto a un nivel de producción sobre tres ejes:

  • Registro real: añade una página /registro con validación en servidor, y guarda usuarios con la contraseña hasheada (bcrypt o argon2). Nada de texto plano.
  • Roles y autorización: distingue user y admin; crea un /admin accesible solo a administradores (403 para el resto). Recuerda: autenticación ≠ autorización.
  • Protección CSRF: genera un token por sesión, inclúyelo como campo oculto en los formularios y verifícalo en los endpoints POST. Piensa cómo se combina con SameSite=lax.
  • Almacén externo: sustituye el Map por un almacén que sobreviva a reinicios (Redis en Docker, o una tabla SQLite). Mantén la misma interfaz de session.ts para no tocar el resto.
  • Recuperación de contraseña: diseña (aunque sea sin enviar email) el flujo de «olvidé mi contraseña» con un token de un solo uso y caducidad corta.

Pista: diseña primero las tablas (users, sessions, password_resets) y luego traduce cada endpoint a operaciones sobre ellas. Para el CSRF, el token debe ser impredecible, ligado a la sesión y verificado en cada POST; un atacante que no puede leerlo —porque la cookie es HttpOnly— no puede falsificarlo. Piensa también qué pasa si el usuario está logueado pero su sesión caduca a mitad de un formulario: la revalidación en servidor debe detectarlo y responder con un error claro, no con un 500.

9 · Resumen

  • Una zona privada separa lo público (landing, login) de lo protegido (panel, APIs de sesión).
  • La sesión es una cookie HttpOnly con un id opaco; los datos viven en el servidor.
  • El middleware resuelve la identidad una vez, protege rutas y añade Cache-Control: private, no-store.
  • El logout invalida la sesión en servidor y borra la cookie.
  • Las rutas privadas necesitan prerender = false y un adaptador.
  • El despliegue usa el adaptador de la plataforma y define los secretos en el panel, nunca en el repo.

10 · Preguntas frecuentes

¿Por qué el logout es un POST y no un enlace?

Porque cambia estado. Un enlace (GET) puede dispararse desde una imagen o un iframe en otra web (CSRF), cerrando tu sesión sin que lo quieras. Un <form method="POST"> requiere una acción deliberada y, combinado con SameSite, complica muchísimo ese ataque. La regla general: todo lo que modifica estado va por POST (o DELETE/PUT), nunca por un enlace navegable.

¿Puedo usar el Map en producción?

Para una demo de una sola instancia, sí. Pero se pierde al reiniciar y no se comparte entre réplicas: con dos instancias, el usuario logueado en una puede aparecer deslogueado en la otra. Si tu despliegue escala horizontalmente (lo normal en serverless), necesitas un almacén compartido: Redis, una base de datos o el almacén KV de tu plataforma. La buena noticia es que, gracias a session.ts, cambiar el almacén es cambiar un fichero.

¿Cómo pruebo el flujo sin montar una base de datos?

Con usuarios de prueba en memoria y credenciales fijas, como en el ejemplo. Lo importante es que la forma del código sea la definitiva: verificar → crear sesión → fijar cookie → proteger. Cuando llegue la base de datos, solo cambias la comprobación de credenciales y el almacén de sesiones; el resto del flujo (middleware, rutas, logout) no se toca.

¿Necesito HTTPS en local para las cookies secure?

En local sirves por http://localhost, y los navegadores tratan localhost como contexto seguro, así que las cookies secure suelen funcionar. Por eso en el ejemplo usamos secure: import.meta.env.PROD: activo en producción (HTTPS real) y relajado en desarrollo. Nunca lo desactives en producción: ahí secure es obligatorio.

¿Y la autorización por roles, dónde va?

Primero autenticas (quién eres) en el middleware, y luego autorizas (qué puedes hacer) por ruta. El rol es un dato del usuario que vive en el servidor, no en la cookie. Una forma limpia es comparar context.locals.user.role contra el permiso requerido para esa zona, devolviendo 403 cuando no coincide. Nunca confíes en un rol que venga del cliente.
