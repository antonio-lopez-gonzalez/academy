Variables de entorno y secretos

Módulo 8 · Auth y Despliegue 🕐 30 minutos

1 · Introducción

Toda aplicación real necesita datos que no pueden estar en el código: la URL de la API, la clave de un servicio de correo, el secreto con el que firmas sesiones, la cadena de conexión a la base de datos. Son las variables de entorno. En Astro se leen con import.meta.env, y la gran pregunta es siempre la misma: ¿esto puede verlo el navegador o debe quedarse en el servidor?

Confundir ambas cosas es una de las fugas de seguridad más comunes y más fáciles de cometer: basta con ponerle a una clave un prefijo de más.

¿Por qué existe esta lección? Porque existe una frontera invisible pero tajante: el código que corre en el servidor es privado y puede guardar secretos; el código que llega al navegador es público, aunque esté minificado. Entender esa frontera —y cómo Astro la materializa con el prefijo PUBLIC_ y con astro:env— te evita filtrar credenciales a producción sin darte cuenta.

2 · Teoría

Dos mundos: servidor y navegador

Astro tiene dos lugares donde se ejecuta tu código: el build/servidor y el navegador. Las variables de entorno viven, por defecto, solo en el mundo del servidor. Para que una variable llegue al navegador hay que pedirlo explícitamente, y Astro lo hace con un convenio de nombres.

  SERVIDOR / BUILD                      NAVEGADOR
  +--------------------------+          +----------------------------+
  |  import.meta.env.SECRET  |          |  solo llega lo PUBLIC_*    |
  |  import.meta.env.DB_URL  |          |  (queda en el bundle JS)   |
  |  import.meta.env.PUBLIC_*|  ----->  |  import.meta.env.PUBLIC_*  |
  +--------------------------+          +----------------------------+
        segreto (privado)                  publico (visible por todos)

Analogía: el servidor es la trastienda de una tienda y el navegador es el escaparate. Puedes tener la caja fuerte en la trastienda (variables sin prefijo). Si pones algo en el escaparate (PUBLIC_), prepárate para que todo el mundo lo vea, porque cualquiera puede mirar el código fuente de tu web.

El prefijo PUBLIC_: la decisión que lo cambia todo

Astro expone al cliente únicamente las variables que empiezan por PUBLIC_. Las demás son undefined en el navegador (y en el build estático). Es un convenio sencillo, y precisamente por eso hay que respetarlo con disciplina.

Variable¿Servidor?¿Navegador?¿Secreto?
PUBLIC_API_URL✓✓No, es visible
PUBLIC_SITE_NAME✓✓No
DATABASE_URL✓✗Sí, jamás al cliente
SESSION_SECRET✓✗Sí, crítico
EMAIL_API_KEY✓✗Sí

Poner PUBLIC_ a un secreto lo publica. No es «más cómodo», no es «por si acaso»: cualquiera que abra DevTools → Sources verá el valor embebido en el JavaScript. Si alguna vez pusiste una clave con PUBLIC_ y la desplegaste, rótala: ya está comprometida, incluso si cambias el nombre después.

De dónde salen los valores: .env

Astro carga variables desde ficheros .env en la raíz del proyecto, usando Vite por debajo. Hay varios según el modo:

FicheroCuándo se carga
.envSiempre
.env.localSiempre, pero no se sube al repo (local)
.env.productionEn builds de producción
.env.developmentEn pnpm dev

Los secretos de producción no van en .env. En producción las variables se definen en el panel de la plataforma (Vercel, Netlify, Cloudflare…) donde despliegas. El .env es para desarrollo local. Lo verás a fondo en la lección de despliegue.

astro:env: variables tipadas y separadas por contexto

Astro 5 trae el módulo virtual astro:env, que mejora este modelo en dos direcciones: tipado (sabes que una variable existe y de qué tipo es) y separación por contexto (server o client). Se declaran en astro.config.mjs con un esquema:

astro.config.mjs
import { defineConfig, envField } from 'astro/config';

export default defineConfig({
  env: {
    schema: {
      // Accesible en el cliente: nombre publico de la web.
      PUBLIC_SITE_NAME: envField.string({ context: 'client', access: 'public' }),

      // Solo en el servidor: nunca llega al navegador.
      DATABASE_URL: envField.string({ context: 'server', access: 'secret' }),
      SESSION_SECRET: envField.string({ context: 'server', access: 'secret' }),
    },
  },
});

// Import DESDE 'astro:env', no desde import.meta.env.
import { PUBLIC_SITE_NAME, DATABASE_URL } from 'astro:env/server';

// PUBLIC_SITE_NAME tambien puede importarse en cliente:
// import { PUBLIC_SITE_NAME } from 'astro:env/client';

¿Para qué sirve el esquema? Para que el build falle si falta una variable o si intentas leer un secreto en el cliente. Con import.meta.env un nombre mal escrito es simplemente undefined y el bug aparece en producción; con astro:env lo cazas al construir. En proyectos serios, esto compensa con creces el pequeño coste de configurarlo.

3 · Ejemplo mínimo

Una variable pública y una privada, y comprobar dónde llega cada una.

.env
# Visible en el navegador (bundle JS).
PUBLIC_SITE_NAME=Mi Blog Astro
# Solo en el servidor: NUNCA lleva PUBLIC_.
GREETING_SECRET=shhh-no-lo-cuenten
src/pages/index.astro
---
// PUBLIC_* esta disponible en servidor y cliente.
const siteName = import.meta.env.PUBLIC_SITE_NAME;

// Sin PUBLIC_: disponible SOLO en el frontmatter (servidor/build).
// En el <script> del navegador seria undefined.
const secret = import.meta.env.GREETING_SECRET;
---
<h1>{siteName}</h1>
<p>El secreto empieza por: {secret?.slice(0, 4)}…</p>

<script>
  // Esto corre en el NAVEGADOR.
  console.log(import.meta.env.PUBLIC_SITE_NAME);   // "Mi Blog Astro"
  console.log(import.meta.env.GREETING_SECRET);   // undefined (esta bien!)
</script>

Abre DevTools → Console y verás el nombre público impreso y el secreto como undefined. Ese undefined es la frontera funcionando. Si GREETING_SECRET tuviera prefijo PUBLIC_, aparecería el valor real: fuga.

4 · Ejemplo real

Una newsletter: el cliente necesita la URL de la API (pública), pero la clave del servicio de email es un secreto que solo usa el servidor en un endpoint.

.env (desarrollo local)
# --- PUBLICAS: pueden ir al navegador ---
PUBLIC_API_URL=http://localhost:4321
PUBLIC_SITE_NAME=Academy News

# --- SECRETAS: solo servidor ---
EMAIL_API_KEY=ma_key_de_prueba_local
EMAIL_FROM=news@example.com
src/pages/api/subscribe.ts (usa el secreto en el servidor)
import type { APIRoute } from 'astro';

export const POST: APIRoute = async ({ request }) => {
  const { email } = await request.json();

  // La clave secreta se lee AQUI, en el servidor. Nunca se envia al cliente.
  const apiKey = import.meta.env.EMAIL_API_KEY;

  const res = await fetch('https://api.emailservice.example/subscribers', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      // Autenticacion con el proveedor: el secreto viaja cliente -> servidor
      // del proveedor, pero NUNCA navegador -> nuestro usuario.
      Authorization: `Bearer ${apiKey}`,
    },
    body: JSON.stringify({ email }),
  });

  if (!res.ok) {
    return Response.json({ error: 'No se pudo suscribir' }, { status: 502 });
  }
  return Response.json({ ok: true }, { status: 201 });
};
src/components/NewsletterForm.tsx (isla que llama a nuestro endpoint)
import { useState } from 'react';

// En el cliente usamos PUBLIC_API_URL (visible): es solo una URL, no un secreto.
const API_URL = import.meta.env.PUBLIC_API_URL;

export default function NewsletterForm() {
  const [email, setEmail] = useState('');
  const [status, setStatus] = useState('idle');

  async function onSubmit(e) {
    e.preventDefault();
    setStatus('sending');
    // Llamamos a NUESTRO endpoint: la clave secreta la pone el servidor.
    const res = await fetch(`${API_URL}/api/subscribe`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ email }),
    });
    setStatus(res.ok ? 'ok' : 'error');
  }

  return (
    <form onSubmit={onSubmit}>
      <input
        type="email"
        value={email}
        onChange={(e) => setEmail(e.target.value)}
        placeholder="tu@email.com"
      />
      <button disabled={status === 'sending'}>Suscribirme</button>
      {status === 'error' && <span role="alert">Error, intentalo de nuevo</span>}
    </form>
  );
}

Decisiones explicadas:

  • PUBLIC_API_URL es pública y no pasa nada: es una URL, no da acceso a nada por sí sola. Lo que protege la operación es el secreto del servidor.
  • EMAIL_API_KEY vive solo en el endpoint: el navegador nunca la ve. Así, aunque alguien inspeccione el bundle, no puede usar tu cuenta del proveedor de email.
  • El cliente habla con nosotros, no con el proveedor: patrón habitual para no exponer claves de terceros.
  • La respuesta de error es genérica: no filtramos detalles internos del proveedor al usuario.

Regla mental: si un valor permite gastar dinero, leer datos privados o actuar en tu nombre, es un secreto y va sin PUBLIC_. Las URLs, nombres de sitio, IDs de analytics y claves públicas (como la publishable key de un servicio de pagos) pueden ser PUBLIC_, porque su diseño asume que son visibles.

6 · Errores habituales

Publicar un secreto con PUBLIC_

✗ Incorrecto

# La clave queda embebida en el JS: cualquiera la ve en DevTools.
PUBLIC_EMAIL_API_KEY=sk_live_1234567890

✓ Correcto

# Sin PUBLIC_: solo accesible en el servidor.
EMAIL_API_KEY=sk_live_1234567890

El prefijo es la única cosa que separa un secreto de un dato público. No hay minificado ni ofuscación que lo salve: PUBLIC_ significa visible.

Leer process.env en el navegador

✗ Incorrecto

// En un <script> del navegador. process no existe en el cliente: ReferenceError,
// y si existiera, filtraria el entorno del servidor.
const key = process.env.SESSION_SECRET;

✓ Correcto

// En el cliente solo existe import.meta.env, y solo con PUBLIC_*.
const url = import.meta.env.PUBLIC_API_URL;
// Los secretos se usan en endpoints/acciones del servidor.

El navegador no tiene acceso al entorno del servidor; solo ve lo que Astro decide inyectar, y eso es solo PUBLIC_*.

Commitear el .env

✗ Incorrecto

git add .env && git commit -m "config"
# El secreto queda en el historial: borrarlo despues no lo elimina de ahi.

✓ Correcto

# .gitignore
.env
.env.local
.env.*.local

# Y versionar un fichero de ejemplo SIN valores:
# .env.example
# EMAIL_API_KEY=

Si ya lo commiteaste, no basta con borrar el fichero: hay que rotar el secreto, porque el valor sigue en el historial.

Fiar el tipado a la memoria

✗ Incorrecto

// Si escribes mal el nombre, es undefined: el bug salta en produccion.
const url = import.meta.env.PUBLIC_API_ULR; // typo silencioso

✓ Correcto

// Declarado con envField: el build falla si falta o esta mal escrito.
import { PUBLIC_API_URL } from 'astro:env/client';

Con esquema, los errores de configuración aparecen en el build, no cuando ya está todo en producción.

7 · Ejercicio guiado

Objetivo: configurar variables públicas y secretas, comprobar la frontera en el navegador y blindar la config con astro:env.

  1. Crea el .env con una pública y una secreta: 
    PUBLIC_SITE_NAME=Mi Blog
SECRET_GREETING=hola-mundo
  2. Ignora el fichero: asegúrate de que .env está en .gitignore y crea un .env.example con los nombres y valores vacíos.
  3. Úsalas en una página src/pages/index.astro: muestra PUBLIC_SITE_NAME en el HTML y registra ambas en un <script> del navegador.
  4. Verifica la frontera: pnpm dev, abre DevTools → Console. Debes ver el nombre del sitio y undefined para el secreto. Luego abre DevTools → Sources y busca SECRET_GREETING: no debe aparecer.
  5. Prueba el error clásico: renombra temporalmente la secreta a PUBLIC_SECRET_GREETING, recarga y comprueba que el valor ahora sí aparece en el bundle. Después vuelve a quitarle el prefijo. Esto fija el concepto.
  6. Blinda con astro:env: añade el env.schema al astro.config.mjs con PUBLIC_SITE_NAME como client/public y SECRET_GREETING como server/secret, y cambia los imports a astro:env/client y astro:env/server.
  7. Comprueba que falla bien: borra una de las líneas del .env y ejecuta pnpm build. El build debe quejarse de que falta una variable definida en el esquema. Eso es exactamente lo que quieres en producción.

8 · Reto

🎯 Un módulo de configuración tipado para todo el proyecto

Ahora mismo las variables se leen sueltas por el código. Crea un único punto de entrada, src/config.ts, que:

  • Valide toda la configuración al arrancar con un esquema (Zod o el envField de astro:env) y falle rápido si algo es inválido (por ejemplo, una URL mal formada o un número que no lo es).
  • Separe con claridad la parte pública (importable desde el cliente) de la privada (solo servidor), y provoque un error de tipos si intentas usar la privada en un componente de isla.
  • Ofrezca defaults sensatos para desarrollo, pero exija valores explícitos en producción.
  • Documente cada variable con un comentario: qué es, si es secreta y un ejemplo de valor.

Pista: la clave es que el compilador te proteja. Si desde el cliente solo puedes importar config.public, es imposible que un secreto se cuele por descuido. Piensa también cómo distinguir el entorno (import.meta.env.PROD/.DEV) para no exigir valores de producción al desarrollar. Bonus: usa una función de validación que reciba el objeto crudo y devuelva un objeto tipado, en vez de leer las variables dispersas por todo el código.

9 · Resumen

  • Las variables se leen con import.meta.env; por defecto viven en el servidor.
  • Solo las variables con prefijo PUBLIC_ llegan al navegador, y por tanto son públicas.
  • Los secretos jamás llevan PUBLIC_: si se filtraron, hay que rotarlos.
  • El .env es para desarrollo; en producción los valores van en el panel de la plataforma.
  • .env va en .gitignore; se versiona un .env.example sin valores.
  • astro:env añade tipado y hace fallar el build si falta una variable o si un secreto intenta cruzar al cliente.

10 · Preguntas frecuentes

¿Una variable PUBLIC_ es insegura por definición?

No necesariamente: es visible. La clave está en que eso sea intencionado. Un nombre de sitio, una URL de API o una clave de analytics son públicos por diseño. Lo que nunca debe ir con PUBLIC_ es algo que otorgue privilegios: claves de servicio, contraseñas, tokens de administración. La prueba: «si un atacante tuviera este valor, ¿qué podría hacer?». Si la respuesta es «nada relevante», puede ser pública.

¿Puedo usar process.env en Astro?

En el servidor y en el build suele funcionar (Node), pero la forma recomendada y portable es import.meta.env (o astro:env). En el cliente process.env no existe. Además, import.meta.env aísla el cliente de las variables sin prefijo, cosa que process.env no garantiza. Usa siempre la API de Astro.

¿Y si mi plataforma solo permite definir variables sin prefijo?

El prefijo forma parte del nombre de la variable, así que defines PUBLIC_API_URL tal cual en el panel de la plataforma. No es un mecanismo aparte: es el nombre. Lo mismo en local en el .env. Donde debes tener cuidado es en no añadir ni quitar el prefijo por descuido entre entornos.

¿astro:env sustituye a import.meta.env?

Los complementa. import.meta.env sigue ahí y es la base; astro:env añade validación en build y separación por contexto. Para proyectos pequeños puede bastar con import.meta.env y disciplina. En cuanto participa un equipo y hay secretos críticos, el esquema de astro:env evita errores caros.

Olvidé añadir una variable en producción, ¿qué pasa?

Depende de cómo lo gestiones. Sin esquema, la variable será undefined y el fallo aparecerá en tiempo de ejecución (a veces solo cuando un usuario concreto usa una ruta). Con astro:env y un esquema, el build falla en el despliegue, así que te enteras antes de que llegue tráfico. Esa es la principal razón para usar el esquema: convertir un bug de producción en un error de build.
