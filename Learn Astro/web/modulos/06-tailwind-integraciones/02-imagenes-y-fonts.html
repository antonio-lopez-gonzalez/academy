Optimización de imágenes y fuentes

Módulo 6 · Tailwind e Integraciones 🕐 30 minutos

1 · Introducción

Imágenes y fuentes son, casi siempre, lo más pesado de una página web. Una foto sin optimizar puede pesar 3 MB; una familia tipográfica mal cargada puede añadir 500 KB y provocar saltos de maquetación. En esta lección aprenderás a que Astro se encargue de estas dos cosas por ti: redimensionar, convertir a formatos modernos y precargar fuentes de forma automática y tipada.

Astro trae dos herramientas para esto:

  • astro:assets: los componentes <Image> y <Picture>, que optimizan imágenes locales y remotas en build time.
  • La Fonts API (más reciente) y, como alternativa sencilla, Fontsource: ambas gestión de fuentes con foco en rendimiento y privacidad.

¿Por qué existe esta lección? Porque puedes escribir el HTML más limpio del mundo y seguir teniendo una web lenta si no cuidas imágenes y fuentes. El rendimiento es una decisión de arquitectura, no un retoque final. Astro mete esta disciplina por defecto: si usas sus componentes, la optimización deja de depender de que te acuerdes.

Errores típicos que veremos: meter imágenes gigantes en public/ y referenciarlas con un <img> pelado; no poner width/height y provocar layout shift; cargar cinco pesos de la misma fuente «por si acaso»; o usar fuentes de Google por <link> enviando datos del usuario a terceros.

2 · Teoría

Por qué una imagen puede hundir tu web

Una imagen se descarga, se decodifica y se pinta. Cada una de esas fases cuesta tiempo y memoria. Los tres problemas clásicos:

ProblemaQué provocaCómo lo resuelve Astro
Peso excesivoDescargas lentas, mala métrica LCPConvierte a WebP/AVIF y redimensiona
Sin dimensionesLayout shift (CLS) al cargarwidth/height obligatorios y correctos
Formato inadecuadoJPEG/PNG enormes e innecesarios<Picture> negocia formato por navegador

La clave de Astro es que la optimización ocurre en build time. Tu máquina (o CI) procesa las imágenes una vez con un motor de imagen (por defecto Sharp) y genera los archivos optimizados. El usuario recibe la versión ya lista, no una imagen cruda que su navegador tenga que arreglar.

Analogía: es la diferencia entre un restaurante que sirve la verdura sin pelar y otro que ya la sirve preparada. Astro es el segundo: la «cocina» (build) hace el trabajo pesado una vez, y cada comensal (visitante) recibe el plato listo. Cocinar al gusto de cada visitante en el navegador sería carísimo.

Imágenes locales vs remotas

Una imagen local vive en tu proyecto (normalmente src/assets/) y la importas. Astro la analiza y conoce sus dimensiones reales. Una imagen remota vive en otra URL; Astro no puede leer sus dimensiones, así que debes dárselas tú y autorizar el dominio.

AspectoLocal (src/assets)Remota (URL externa)
Cómo se usaimport foto from '../assets/foto.jpg'<Image src="https://.../foto.jpg" ...>
DimensionesSe detectan solasHay que pasarlas a mano
AutorizaciónNo necesitaSí: image.domains o image.remotePatterns
OptimizaciónCompleta en buildSe descarga y optimiza en build

Para imágenes remotas, primero autorizas los dominios en el config:

astro.config.mjs
import { defineConfig } from 'astro/config';

export default defineConfig({
  image: {
    // Lista blanca de dominios permitidos para <Image>/<Picture>.
    // Sin esto, Astro rechaza las imagenes remotas por seguridad.
    domains: ['images.example.com'],
    // remotePatterns permite comodines mas finos (subcarpetas, etc.).
    remotePatterns: [{ protocol: 'https', hostname: '**.cdn.example.com' }],
  },
});

<Image> y <Picture>: cuándo usar cada uno

  • <Image>: genera un único <img> optimizado. Es la opción por defecto y la más sencilla.
  • <Picture>: genera un <picture> con varios <source>, ofreciendo varios formatos (AVIF y WebP) y dejando que el navegador elija el mejor que soporte. Tiene un fallback obligatorio.
  <Image>                        <Picture>
  +---------------------+        +-------------------------------+
  | <img                |        | <picture>                     |
  |   src="hero.webp"   |        |   <source avif>               |
  |   width/height      |        |   <source webp>               |
  |   loading="lazy"    |        |   <img src="hero.jpg" ...>    |
  | >                   |        | </picture>                    |
  +---------------------+        +-------------------------------+
   Un formato, simple            Varios formatos, max compatibilidad

Regla práctica: usa <Image> el 90 % de las veces y reserva <Picture> para imágenes grandes y destacadas (un héroe a pantalla completa) donde merece la pena negociar AVIF vs WebP. AVIF comprime mejor, pero WebP tiene soporte universal: con <Picture> ofreces ambos y ganas en cualquier navegador.

Fuentes: el coste oculto y cómo domarlo

Una fuente web se descarga como archivo (.woff2), y hasta que llega el navegador usa una fuente de respaldo. Si las dos son muy distintas, el texto «salta» de sitio (layout shift). Las tres palancas son:

  1. Menos archivos: carga solo los pesos que usas (normal y quizá bold, no nueve).
  2. Formato correcto: .woff2 es el más eficiente.
  3. Precarga y ajuste: preload para la fuente del hero, y size-adjust para que el respaldo mida igual que la principal.

Astro ofrece dos caminos. El primero, sencillo y manual, con Fontsource: instalas la fuente como paquete y la importas.

Terminal
# Instala solo el peso que necesitas, en formato variable o concreta.
pnpm add @fontsource-variable/inter
src/layouts/Layout.astro
---
// Importa la fuente: Astro/Vite la procesa, la hashea y la sirve
// desde tu dominio. No hay peticiones a Google.
import '@fontsource-variable/inter';
---

El segundo camino es la Fonts API de Astro (a partir de 5.7), que descarga, cachea y precarga fuentes con una configuración tipada, además de generar fallbacks optimizados para evitar el salto de maquetación:

astro.config.mjs
import { defineConfig, fontProviders } from 'astro/config';

export default defineConfig({
  fonts: [
    {
      // El proveedor Fontsource evita peticiones a terceros:
      // Astro descarga y sirve la fuente desde tu propio sitio.
      provider: fontProviders.fontsource(),
      name: 'Inter',
      cssVariable: '--font-inter',
      weights: [400, 600],        // solo los pesos usados
      styles: ['normal'],
      subsets: ['latin'],
      fallbacks: ['sans-serif'],  // genera un respaldo a medida
    },
  ],
});

Y en el <head> de tu layout insertas el componente <Font>:

src/layouts/Layout.astro
---
import { Font } from 'astro:assets';
---
<html lang="es">
  <head>
    <!-- preload = carga esta fuente cuanto antes (solo el hero). -->
    <Font cssVariable="--font-inter" preload />
  </head>
  <body>
    <slot />
  </body>
</html>

<style>
  /* Aplica la fuente mediante la variable cssVariable. */
  body {
    font-family: var(--font-inter), ui-sans-serif, system-ui, sans-serif;
  }
</style>

Con Tailwind v4: registra la fuente como token para obtener utilidades (font-sans) apuntando a tu variable. En global.css: @theme inline { --font-sans: var(--font-inter); }. Así tus clases usan la fuente sin CSS adicional.

3 · Ejemplo mínimo

La imagen optimizada más pequeña posible, con una imagen local:

src/pages/index.astro
---
// 1) Importamos el componente de astro:assets.
import { Image } from 'astro:assets';
// 2) Importamos la imagen local: Astro lee sus dimensiones reales.
//    La ruta es relativa al propio archivo .astro.
import hero from '../assets/hero.jpg';
---

<!-- 3) <Image> genera un <img> optimizado: formato moderno y
     dimensiones correctas (evita el layout shift). -->
<Image src={hero} alt="Persona programando en su portatil" />

Explicado línea a línea:

  1. import { Image } from 'astro:assets': astro:assets es un módulo integrado de Astro; no hay que instalar nada.
  2. import hero from '../assets/hero.jpg': al importar la imagen obtienes un objeto con metadatos (ancho, alto, formato). Astro, además, sabe dónde está el archivo para procesarlo.
  3. <Image src={hero} alt="...">: Astro genera un <img> con src apuntando a la versión optimizada, y width/height derivados del original.
  4. El atributo alt sigue siendo obligatorio por accesibilidad; Astro te obliga a pensar en él.

Si la imagen está «above the fold» (visible nada más cargar), añade loading="eager" y fetchpriority="high" para que no se cargue con pereza. Para todas las demás, deja el loading="lazy" por defecto.

4 · Ejemplo real

Un componente de hero profesional: imagen destacada con <Picture> (AVIF + WebP + fallback), srcset responsive, prioridad de carga y fuente Inter con la Fonts API.

Autorizamos las imágenes de un CDN remoto:

astro.config.mjs
import { defineConfig, fontProviders } from 'astro/config';

export default defineConfig({
  image: {
    // Permite optimizar imagenes servidas desde este CDN.
    remotePatterns: [{ protocol: 'https', hostname: 'images.unsplash.com' }],
  },
  fonts: [
    {
      provider: fontProviders.fontsource(),
      name: 'Inter',
      cssVariable: '--font-inter',
      weights: [400, 600, 700],
      styles: ['normal'],
      subsets: ['latin'],
      fallbacks: ['sans-serif'],
    },
  ],
});

El componente del hero:

src/components/Hero.astro
---
import { Picture } from 'astro:assets';
// Imagen local: Astro detecta sus dimensiones reales.
import cover from '../assets/hero-cover.jpg';

interface Props {
  title: string;
  subtitle: string;
}

const { title, subtitle } = Astro.props;
---

<section class="relative isolate overflow-hidden">
  <!-- Picture ofrece AVIF y WebP, con un fallback obligatorio.
       Los navegadores eligen el primer formato que soportan. -->
  <Picture
    src={cover}
    formats={['avif', 'webp']}
    fallbackFormat="jpg"
    alt=""
    loading="eager"
    fetchpriority="high"
    widths={[480, 960, 1440, 1920]}
    sizes="100vw"
    class="absolute inset-0 -z-10 h-full w-full object-cover"
  />

  <div class="mx-auto max-w-3xl px-6 py-32 text-center">
    <h1 class="text-5xl font-bold tracking-tight text-white">{title}</h1>
    <p class="mt-6 text-xl text-slate-200">{subtitle}</p>
  </div>
</section>

Y el layout que precarga la fuente del hero:

src/layouts/Layout.astro
---
import { Font } from 'astro:assets';
import '../styles/global.css';

const { title = 'Mi sitio' } = Astro.props;
---
<html lang="es">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>{title}</title>
    <!-- Preload solo de la fuente principal. -->
    <Font cssVariable="--font-inter" preload />
  </head>
  <body class="font-sans antialiased">
    <slot />
  </body>
</html>

Decisiones profesionales detrás de este ejemplo:

  • <Picture> con formats: ofrece AVIF (más pequeño) y WebP (universal). El navegador elige; tú no decides por él.
  • widths + sizes: genera un srcset. Un móvil no descarga la versión de 1920 px. sizes="100vw" indica que ocupa todo el ancho de la ventana.
  • loading="eager" y fetchpriority="high": el hero debe pintarse cuanto antes (es el LCP). El resto de imágenes irán lazy.
  • alt="" aquí es correcto: la imagen es decorativa (hay un h1 con el texto). Un alt vacío es válido solo si la imagen no aporta información; para imágenes de contenido, descríbelas.
  • <Font ... preload />: solo se precarga la fuente del texto visible. Precargar todo sería contraproducente.

Verifica en DevTools: abre la pestaña Network, filtra por imagen y recarga con «Disable cache». Verás las distintas variantes generadas (por ejemplo hero-cover.avif con varios anchos). Cambia el tamaño de la ventana y observa cómo se pide otra variante del srcset. En Elements, el <img> tendrá width/height y un srcset largo.

6 · Errores habituales

Usar <img> crudo con imágenes de public/

✗ Incorrecto

<!-- Se sirve el archivo tal cual: sin redimensionar ni convertir.
     Ademas, sin width/height -> layout shift. -->
<img src="/hero.jpg" alt="Hero">

✓ Correcto

---
import { Image } from 'astro:assets';
import hero from '../assets/hero.jpg'; // desde src/assets, no public/
---
<Image src={hero} alt="Hero" />

public/ es para archivos que deben servirse sin procesar (favicons, PDFs). Las imágenes que aparecen en la web deben vivir en src/assets/ para que Astro las optimice.

Imagen remota sin autorizar el dominio

✗ Incorrecto

---
// Astro rechaza esta imagen: el dominio no esta autorizado.
import { Image } from 'astro:assets';
---
<Image src="https://images.unsplash.com/foto.jpg" width={800} height={600} alt="Foto" />

✓ Correcto

// astro.config.mjs: autoriza el dominio primero.
export default defineConfig({
  image: { remotePatterns: [{ protocol: 'https', hostname: 'images.unsplash.com' }] },
});

Es una medida de seguridad: evita que un tercero pueda hacer que tu servidor procese imágenes arbitrarias. Las remotas también requieren width/height, porque Astro no puede leerlas.

Cargar cinco pesos de fuente

✗ Incorrecto

<!-- Cinco archivos que casi nadie usara: peso muerto. -->
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Inter:wght@100;200;300;400;500;600;700;800;900&display=swap">

✓ Correcto

// astro.config.mjs: solo los pesos que la web usa de verdad.
fonts: [{
  provider: fontProviders.fontsource(),
  name: 'Inter',
  cssVariable: '--font-inter',
  weights: [400, 700],
  styles: ['normal'],
  subsets: ['latin'],
}]

Cada peso es una descarga. Si tu diseño solo usa normal y bold, cargar nueve pesos es tirar ancho de banda y retrasar el render del texto.

Poner loading="lazy" a la imagen del hero

✗ Incorrecto

<!-- La imagen principal (LCP) empieza a cargarse tarde. -->
<Image src={hero} alt="Hero" loading="lazy" />

✓ Correcto

<!-- Prioriza el elemento mas importante de la primera pantalla. -->
<Image src={hero} alt="Hero" loading="eager" fetchpriority="high" />

Lazy significa «carga cuando haga falta». La imagen de arriba del todo hace falta ya: aplazándola, empeoras la métrica LCP (Largest Contentful Paint).

7 · Ejercicio guiado

Objetivo: construir una galería de tarjetas con imágenes locales optimizadas y una fuente de display aplicada solo a los títulos.

  1. Crea la carpeta src/assets/gallery/ y coloca dentro dos o tres imágenes (.jpg o .png). Que una sea claramente más grande que las demás para notar la diferencia de peso.
  2. Define el array de imágenes importando cada una (así Astro conoce sus dimensiones) en src/pages/galeria.astro: 
    ---
import { Image } from 'astro:assets';
import foto1 from '../assets/gallery/foto1.jpg';
import foto2 from '../assets/gallery/foto2.jpg';

const fotos = [
  { src: foto1, alt: 'Atardecer en la montaña' },
  { src: foto2, alt: 'Calle de una ciudad antigua' },
];
---
  3. Renderiza la galería pidiendo anchos concretos y dejando el lazy por defecto: 
    <section class="grid gap-6 sm:grid-cols-2">
  {fotos.map((foto) => (
    <figure class="overflow-hidden rounded-xl">
      <Image
        src={foto.src}
        alt={foto.alt}
        widths={[320, 640, 960]}
        sizes="(min-width: 640px) 50vw, 100vw"
        class="h-64 w-full object-cover"
      />
    </figure>
  ))}
</section>
  4. Añade una fuente de display con Fontsource y aplícala solo a los h2: 
    pnpm add @fontsource-variable/playfair-display

    ---
import '@fontsource-variable/playfair-display';
---
<style>
  h2 { font-family: 'Playfair Display Variable', serif; }
</style>
  5. Verifica en DevTools: en Network comprueba que se descargan variantes del srcset según el tamaño de ventana y que las fuentes salen de tu dominio, no de Google. En Lighthouse, revisa que no hay layout shift por imágenes.

8 · Reto

🎯 Página de artículo a prueba de rendimiento

Construye /blog/[slug] (puedes usar datos de ejemplo) con estas exigencias:

  • Una imagen de portada con <Picture>: formatos AVIF y WebP, widths y sizes correctos, y prioridad de carga por ser el LCP.
  • Al menos dos imágenes dentro del cuerpo del artículo, lazy y con alt descriptivo.
  • Una imagen remota desde un CDN autorizado en astro.config.mjs.
  • Una fuente de titulares distinta de la del cuerpo, cargando solo los pesos usados.

Mide el resultado con pnpm build && pnpm preview y Lighthouse en modo móvil. Objetivo: imágenes con properly size images en verde y CLS cercano a 0.

Pista: recuerda que las imágenes decorativas llevan alt="" y las de contenido un texto real. Y ojo: widths y sizes solo tienen sentido cuando el navegador puede elegir; si no, deja que Astro use el tamaño natural.

9 · Resumen

  • astro:assets trae <Image> y <Picture>, que optimizan imágenes en build time.
  • Las imágenes locales (importadas de src/assets/) no necesitan dimensiones; las remotas sí, y hay que autorizar el dominio.
  • <Image> = un formato; <Picture> = varios formatos (AVIF/WebP) con fallback.
  • El LCP se marca con loading="eager" y fetchpriority="high"; el resto va lazy.
  • Las fuentes se gestionan con Fontsource o la Fonts API, cargando solo los pesos usados y sirviéndolas desde tu dominio.
  • El preload de fuentes se reserva a lo imprescindible arriba del todo.

10 · Preguntas frecuentes

¿Por qué mi imagen de public/ no se optimiza?

Porque todo lo que está en public/ se sirve «tal cual», sin pasar por el pipeline de Astro. Para que se optimice, muévela a src/assets/ e impórtala. Reserva public/ para archivos que no deben transformarse: favicons, robots.txt, PDFs.

¿Puedo usar una imagen remota sin autorizar el dominio?

No con <Image>/<Picture>: Astro exige autorizar el dominio en image.domains o image.remotePatterns. La alternativa es un <img> normal, pero entonces pierdes toda la optimización (redimensionado, conversión de formato).

¿<Image> funciona en SSR o en el cliente?

La optimización de astro:assets está pensada para build time (SSG), que es el modo por defecto. En modo servidor necesitas configurar un image service (por ejemplo Sharp o un servicio de imágenes en el edge) para procesar en tiempo de petición. Para el 90 % de los casos, SSG cubre la optimización.

¿Fontsource o la Fonts API de Astro?

Fontsource es sencillo y directo: instalas un paquete e importas. La Fonts API (Astro 5.7+) añade descarga, caché, <Font>, generación de respaldos ajustados y precarga tipada. Si quieres control fino del rendimiento de fuentes con menos trabajo manual, la Fonts API compensa; si prefieres mínima configuración, Fontsource es perfecta.

¿Cargar AVIF siempre es mejor que WebP?

AVIF suele comprimir mejor (archivos más pequeños a igual calidad), pero es más lento de codificar y el soporte, aunque amplio, no es tan universal como WebP. Por eso <Picture> ofrece ambos: el navegador elige el mejor que soporta. Si usas <Image> y quieres un único formato, WebP es el compromiso seguro.
