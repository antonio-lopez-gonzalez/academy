Integraciones oficiales (Sitemap, RSS, etc.)

Módulo 6 · Tailwind e Integraciones 🕐 30 minutos

1 · Introducción

Un sitio web profesional no es solo lo que se ve: también son los archivos que consumen los buscadores y los lectores de noticias. Un sitemap.xml ayuda a Google a descubrir tus páginas; un rss.xml permite que la gente siga tu blog. Astro los genera con integraciones oficiales, sin escribir el XML a mano.

En esta lección aprenderás el patrón astro add —cómo se instalan y configuran las integraciones— y verás tres de las más útiles en la práctica: Sitemap, RSS y MDX.

¿Por qué existe esta lección? Porque «tener la web» y «tener una web que la gente encuentre» son cosas distintas. Las integraciones son el puente. Además, entender el patrón astro add te da una llave maestra: casi todo lo que añadas a Astro (React, Tailwind, MDX, adaptadores) se instala igual. Es la mecánica de extensibilidad del framework.

Errores típicos que veremos: integrar el sitemap y olvidar la opción site (sin ella, las URLs salen relativas y quedan inservibles); añadir @astrojs/rss a integrations cuando en realidad es una librería que usas en un endpoint; o duplicar archivos index.md y index.mdx creando rutas en conflicto.

2 · Teoría

Qué es una integración y qué hace astro add

Una integración es un paquete que extiende Astro enganchándose a su ciclo de build. Puede aportar código a la página, generar archivos, transformar Markdown o añadir un renderer de framework. Hay tres tipos frecuentes:

TipoPara quéEjemplos
UI frameworkRenderizar componentes de otros frameworks@astrojs/react, @astrojs/vue, @astrojs/svelte
FuncionalGenerar archivos o activar funciones@astrojs/sitemap, @astrojs/mdx
AdaptadorDesplegar en un entorno concreto (SSR)@astrojs/vercel, @astrojs/netlify

El comando pnpm astro add <nombre> automatiza la instalación: detecta el paquete, lo instala con tu gestor, edita el astro.config.mjs por ti y, si necesita archivos de apoyo, los crea. Si por algún motivo no puede modificar el config, te imprime las líneas exactas para hacerlo a mano.

Analogía: astro add es como un fontanero que no solo trae la pieza, sino que además la conecta a la instalación y comprueba que no gotea. Si el acceso es complicado, te deja las instrucciones para que lo hagas tú, pero nunca te deja a medias sin avisar.

Sitemap: para que los buscadores te encuentren

Un sitemap.xml es un índice de todas tus URLs. Google no lo necesita para indexarte, pero acelera el descubrimiento. La integración @astrojs/sitemap lo genera automáticamente recorriendo tus páginas construidas.

Requisito imprescindible: define la opción site en tu config. Un sitemap necesita URLs absolutas (https://tudominio.com/pagina). Sin site, Astro no sabe cuál es tu dominio y el resultado es inutilizable.

Integrar un sitemap.xml encaja con la sección de SEO del Módulo 7: aquí generamos el archivo, allí lo acompañamos de metadatos y datos estructurados.

RSS: un canal para seguir tu contenido

RSS es un formato XML que los lectores de noticias consultan para saber cuándo publicas algo nuevo. Atención al matiz: @astrojs/rss no es una integración que se añada al config, sino una librería que usas dentro de un endpoint para devolver el XML. Es decir: creas un archivo de ruta que genera el RSS, y la librería te ayuda a construirlo.

Esta distinción confunde a mucha gente. @astrojs/sitemap se registra en integrations: [...]. @astrojs/rss se importa en src/pages/rss.xml.js. Mismo prefijo «@astrojs/», mecánicas distintas.

MDX: Markdown con superpoderes

Ya conoces Markdown (Módulo 3). MDX es ese mismo Markdown pero con la posibilidad de importar y usar componentes dentro del contenido. La integración @astrojs/mdx habilita los archivos .mdx, que Astro trata como páginas o entradas de colección.

Aspecto.md.mdx
ContenidoMarkdown puroMarkdown + componentes
Importar componentesNoSí
InteractividadNoSí (con islas client:*)
Uso típicoArtículos sencillosContenido con gráficos, demos, avisos a medida

Regla de oro: no conviertas todo a MDX. Markdown es más simple y portable; MDX solo cuando el contenido de verdad necesita componentes. Un .mdx innecesario es complejidad añadida sin beneficio.

3 · Ejemplo mínimo

El primer paso, siempre el mismo: definir el dominio y añadir el sitemap.

Terminal
# Instala @astrojs/sitemap y edita el config automaticamente.
pnpm astro add sitemap

Revisa el config resultante. La pieza clave es site:

astro.config.mjs
import { defineConfig } from 'astro/config';
// La integracion se importa y se pone en el array integrations.
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  // OBLIGATORIO para el sitemap: URL absoluta del sitio.
  site: 'https://mi-blog.example.com',

  integrations: [sitemap()],
});

Tras pnpm build, aparece en dist/:

dist/
├── index.html
├── blog/
│   └── index.html
└── sitemap-index.xml      ← generado por la integracion
    └── (apunta a sitemap-0.xml con las URLs)

Explicado paso a paso:

  1. pnpm astro add sitemap: instala el paquete y escribe la integración en el config.
  2. site: la URL base. Sin ella, el sitemap tendría rutas relativas y los buscadores no sabrían interpretarlas.
  3. integrations: [sitemap()]: registra la integración. Al construir, Astro recorre las rutas generadas y emite el XML.
  4. sitemap-index.xml: el índice. Si tienes muchas URLs, Astro reparte el sitemap en varios archivos y este índice los agrupa (así respeta el límite de 50.000 URLs por sitemap).

Para comprobar que funciona, tras pnpm build abre el XML generado en dist/sitemap-index.xml. No debe contener rutas relativas ni {{placeholders}} sin sustituir: eso suele significar que site está mal o ausente.

4 · Ejemplo real

Un blog completo: sitemap, RSS generado desde una colección y MDX para un artículo con un componente a medida.

Primero, el config con sitemap y MDX:

astro.config.mjs
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';
import mdx from '@astrojs/mdx';

export default defineConfig({
  site: 'https://mi-blog.example.com',
  integrations: [sitemap(), mdx()],
});

El RSS se escribe en un endpoint, leyendo tus colecciones de contenido. Esta es la clave: no mantienes el feed a mano; se genera a partir de los mismos datos del blog.

src/config.ts
// Metadatos centralizados: una sola fuente para el site y el RSS.
export const SITE = {
  title: 'Mi Blog de Astro',
  description: 'Articulos sobre Astro, MPA e islands.',
  url: 'https://mi-blog.example.com',
} as const;
src/pages/rss.xml.js
// @astrojs/rss es una LIBRERIA, no una integracion del config.
import rss from '@astrojs/rss';
import { getCollection } from 'astro:content';
import { SITE } from '../config';

// Endpoint GET: Astro lo ejecuta en build y emite rss.xml.
export async function GET(context) {
  // Leemos las entradas publicadas de la coleccion "blog".
  const posts = await getCollection('blog', ({ data }) => !data.draft);

  return rss({
    title: SITE.title,
    description: SITE.description,
    // context.site viene de la opcion `site` del config: otra razon
    // para tenerla siempre definida.
    site: context.site,
    items: posts.map((post) => ({
      title: post.data.title,
      pubDate: post.data.pubDate,
      description: post.data.description,
      // Enlace relativo; rss() lo convierte en absoluto con `site`.
      link: `/blog/${post.id}/`,
    })),
    // Datos extra del canal, como el idioma.
    customData: '<language>es-es</language>',
  });
}

Y un enlace al feed en el <head> de tu layout, para que los navegadores y lectores lo descubran:

src/layouts/Layout.astro
<head>
  <meta charset="utf-8" />
  <!-- Con esto los lectores RSS detectan el feed automaticamente. -->
  <link rel="alternate" type="application/rss+xml" title="RSS" href="/rss.xml" />
</head>

Ahora, un artículo en MDX que usa un componente propio. Creamos un componente de aviso:

src/components/Callout.astro
---
interface Props {
  type?: 'info' | 'warning';
}
const { type = 'info' } = Astro.props;
---
<aside class:list={['rounded-lg border p-4', type === 'warning' ? 'border-amber-500/40 bg-amber-500/10' : 'border-sky-500/40 bg-sky-500/10']}>
  <slot />
</aside>

Y lo usamos dentro del Markdown, cosa imposible en un .md normal:

src/content/blog/primer-post.mdx
---
title: 'Primeros pasos con islands'
pubDate: 2026-01-15
description: 'Que son las islands y por que cambian el rendimiento.'
---

# Primeros pasos con islands

Las **islands** son piezas interactivas aisladas dentro de HTML estatico.

{/* Importamos un componente y lo usamos como etiqueta. */}
import Callout from '../../components/Callout.astro';

<Callout type="warning">
  Recuerda: sin una directiva `client:*`, este componente no se hidrata.
</Callout>

Como ves, en MDX el contenido narrativo y los componentes viven juntos.

Decisiones profesionales detrás de este ejemplo:

  • Metadatos centralizados (src/config.ts): el título y la URL del sitio se definen una vez y se reutilizan en el RSS y en el SEO del Módulo 7.
  • RSS desde la fuente de verdad: el feed se genera de las colecciones, así que nunca se desincroniza de los artículos publicados.
  • Filtrado de borradores: !data.draft evita publicar en el feed artículos sin terminar.
  • MDX solo donde aporta: el artículo necesita un componente, así que es .mdx. Los artículos simples se quedan en .md.

Verifica el RSS en DevTools: abre /rss.xml en el navegador. Algunos navegadores lo muestran con un visor de feeds; si no, verás el XML crudo. Revisa que los <link> sean URLs absolutas y que las fechas <pubDate> estén en formato RFC 822. Pega el XML en un validador de feeds si quieres asegurarte.

5 · Buenas prácticas

HazEvitaPor qué
Definir site antes de cualquier integración que genere URLs Integrar el sitemap y olvidar site Sin site las URLs son relativas y los buscadores no las resuelven
Distinguir integración (config) de librería (endpoint) Meter rss() en integrations @astrojs/rss es una librería que se importa en un endpoint, no un plugin

Reservar MDX para contenido que usa componentes Convertir todo el Markdown a MDX «por costumbre» Markdown es más simple y portable; MDX añade complejidad

Revisar los archivos generados en dist/ Asumir que la integración «habrá funcionado» Ver el XML real revela site mal configurado o rutas perdidas

6 · Errores habituales

Integrar el sitemap sin site

✗ Incorrecto

// Falta `site`: el sitemap saldra con URLs relativas e inservibles.
export default defineConfig({
  integrations: [sitemap()],
});

✓ Correcto

export default defineConfig({
  site: 'https://mi-blog.example.com', // dominio absoluto, obligatorio
  integrations: [sitemap()],
});

El sitemap exige URLs completas. Sin site, Astro no puede construirlas y el XML no sirve para los buscadores.

Tratar el RSS como una integración del config

✗ Incorrecto

// @astrojs/rss NO es una integracion: esto no compila/funciona.
import rss from '@astrojs/rss';
export default defineConfig({ integrations: [rss()] });

✓ Correcto

// src/pages/rss.xml.js — se importa dentro de un endpoint.
import rss from '@astrojs/rss';
export async function GET(context) {
  return rss({ title: 'Mi blog', site: context.site, items: [] });
}

El nombre engaña: la «integración» RSS es en realidad una librería que usas en un endpoint. Se importa en un archivo de ruta, no en el config.

Duplicar rutas en .md y .mdx

✗ Incorrecto

src/pages/guia.md     -> /guia
src/pages/guia.mdx    -> /guia   ← dos paginas para la misma ruta

✓ Correcto

src/pages/guia.mdx    -> /guia   (una sola: la que necesita componentes)

Astro generará un error de ruta duplicada, o peor, una de las dos sobrescribirá a la otra de forma confusa. Un contenido, un archivo.

Feed RSS con fechas o enlaces mal formados

✗ Incorrecto

// pubDate como Date sin serializar y link relativo sin `site`:
// el feed no valida y los lectores lo ignoran.
items: posts.map((p) => ({ title: p.data.title, link: `/blog/${p.id}` })),

✓ Correcto

// rss() usa `site` para convertir el link en absoluto y
// serializa pubDate al formato correcto.
return rss({
  site: context.site,
  items: posts.map((p) => ({
    title: p.data.title,
    pubDate: p.data.pubDate,      // Date -> RFC 822 automaticamente
    link: `/blog/${p.id}/`,       // se vuelve absoluto con `site`
  })),
});

Un feed inválido no da error visible: simplemente nadie lo usa. Por eso conviene validarlo.

7 · Ejercicio guiado

Objetivo: añadir sitemap y RSS a un blog de ejemplo, y publicar un artículo en MDX con un componente propio.

  1. Define el dominio y añade las integraciones: 
    pnpm astro add sitemap
pnpm astro add mdx

    // astro.config.mjs — comprueba que quedan asi:
export default defineConfig({
  site: 'https://ejemplo.test',
  integrations: [sitemap(), mdx()],
});
  2. Instala la librería de RSS y crea el endpoint: 
    pnpm add @astrojs/rss

    // src/pages/rss.xml.js
import rss from '@astrojs/rss';
import { getCollection } from 'astro:content';

export async function GET(context) {
  const posts = await getCollection('blog');
  return rss({
    title: 'Mi blog',
    description: 'Un blog de ejemplo en Astro.',
    site: context.site,
    items: posts.map((p) => ({
      title: p.data.title,
      pubDate: p.data.pubDate,
      link: `/blog/${p.id}/`,
    })),
  });
}
  3. Enlaza el feed en el <head> de tu layout: 
    <link rel="alternate" type="application/rss+xml" title="RSS" href="/rss.xml" />
  4. Crea un componente src/components/Note.astro y úsalo en un artículo src/content/blog/mdx-demo.mdx importándolo dentro del propio MDX.
  5. Verifica con pnpm build: revisa dist/sitemap-index.xml y dist/rss.xml. Comprueba que ambos contienen tu dominio absoluto. Luego abre /rss.xml en el navegador durante pnpm dev.

8 · Reto

🎯 Un blog con descubrimiento completo y feed filtrado

Amplía el ejercicio hasta tener un blog profesionalmente «descubrible»:

  • Sitemap con exclusión: configura @astrojs/sitemap para omitir ciertas rutas (por ejemplo /privacidad o páginas de borradores) usando su opción de filtrado.
  • Dos feeds RSS: uno general (/rss.xml) y otro solo de una categoría (/blog/astro/rss.xml, por ejemplo). Ambos generados desde la misma colección con distintos filtros.
  • Contenido mixto: al menos un artículo .md y otro .mdx que use un componente interactivo (aunque sea una isla sencilla).

Comprueba en dist/ que solo aparecen las páginas deseadas en el sitemap y que ambos feeds se generan correctamente con URLs absolutas.

Pista: la opción de filtrado del sitemap recibe cada URL y devuelve un booleano; úsala para decidir qué entra. Para los dos feeds, monta el items con .filter() sobre la colección. Y recuerda: un feed por archivo de ruta, no un archivo con ramas.

9 · Resumen

  • Una integración extiende Astro y se registra en integrations: [...] del config.
  • pnpm astro add <nombre> instala y configura automáticamente; si no puede, te da las instrucciones.
  • Sitemap genera sitemap-index.xml y requiere site con el dominio absoluto.
  • RSS (@astrojs/rss) es una librería que se usa en un endpoint (rss.xml.js), no en el config.
  • MDX es Markdown con componentes; se usa solo cuando el contenido los necesita.
  • Conviene verificar los archivos generados en dist/ en lugar de asumir que todo salió bien.

10 · Preguntas frecuentes

¿astro add modifica mi config sin avisar?

Lo modifica, pero de forma controlada: añade el import y la entrada en integrations (o en vite.plugins, según el caso). Verás el cambio en tus diff de Git antes de cometer nada. Si no puede editar el archivo, astro add te imprime exactamente las líneas que debes pegar.

¿El sitemap es obligatorio para posicionar en Google?

No es obligatorio, pero ayuda. Google puede descubrir tus páginas siguiendo enlaces, así que un sitio bien enlazado se indexa sin sitemap. Aun así, un sitemap acelera el descubrimiento, especialmente en sitios nuevos o con páginas poco enlazadas, y es una señal de buena higiene SEO.

¿Puedo tener RSS sin usar Content Collections?

Sí. El endpoint rss() solo necesita un array de items. Puedes construirlo desde un fetch a una API, desde un JSON local o desde cualquier fuente. Las colecciones son el caso más común, pero no el único.

¿MDX sustituye a Markdown?

No, lo complementa. Markdown sigue siendo preferible para contenido sencillo por su simplicidad y portabilidad. MDX es la herramienta cuando necesitas insertar componentes. Un proyecto sano suele tener ambos.

¿Qué diferencia hay entre integración y adaptador?

Una integración extiende el build (renderizado, archivos generados). Un adaptador le dice a Astro dónde se ejecuta en producción (Vercel, Netlify, Cloudflare…), habilitando SSR y funciones serverless. Los adaptadores se cubren en el Módulo 8 (despliegue).
