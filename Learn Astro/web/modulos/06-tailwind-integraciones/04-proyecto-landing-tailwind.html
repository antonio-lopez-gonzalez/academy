Proyecto: landing con Tailwind y Astro

Módulo 6 · Tailwind e Integraciones 🕐 45 minutos

1 · Introducción

Vamos a construir, de principio a fin, una landing page con Astro y Tailwind v4: héroe, características, precios y llamada a la acción. Es el proyecto de cierre del módulo y reúne todo lo aprendido: componentes .astro, props tipadas, Tailwind, imágenes optimizadas con astro:assets y fuentes.

Una landing es el mejor banco de pruebas para Astro porque es casi todo contenido estático: perfecto para HTML pre-renderizado, sin apenas JavaScript. Añadiremos interacción solo si de verdad aporta, respetando la filosofía islands.

¿Por qué este proyecto? Porque una landing profesional no es «HTML con clases». Es una arquitectura: componentes reutilizables, un sistema de diseño coherente (tipografía, espaciado, color), contenido data-driven (precios desde un array) e imágenes optimizadas. Lo que practiques aquí se traduce directamente a un trabajo real.

Errores típicos que evitaremos: repetir el mismo botón con clases distintas en cada sección; hardcodear el mismo texto varias veces; olvidar las imágenes optimizadas; y, el más caro, meter JavaScript de cliente donde no hace falta.

2 · Teoría

Anatomía de una landing

Casi todas las landings siguen el mismo esqueleto, porque funciona: captar atención, explicar el valor, resolver dudas y pedir una acción. Lo traducimos a secciones:

  +-------------------------------------------------------+
  |  Navbar    (logo + enlaces + CTA)      sticky          |
  +-------------------------------------------------------+
  |  HERO      (titular grande + subtitulo + botones)      |
  |            + imagen de fondo optimizada (LCP)          |
  +-------------------------------------------------------+
  |  FEATURES  (grid de 3-4 caracteristicas)               |
  +-------------------------------------------------------+
  |  PRICING   (3 planes, uno destacado)                   |
  +-------------------------------------------------------+
  |  CTA final (una accion clara y grande)                 |
  +-------------------------------------------------------+
  |  FOOTER    (enlaces, copyright)                        |
  +-------------------------------------------------------+

Cada bloque se convierte en un componente .astro. El nav, el hero, la tarjeta de feature, la tarjeta de precio, el CTA y el footer. La página solo los compone.

Datos como fuente de verdad

Los textos de features y precios no deben estar repartidos por el HTML. Viven en arrays y se recorren con map(). Así, cambiar un precio o añadir una feature es editar un objeto, no buscar y reemplazar en diez sitios. Es la misma mentalidad content-driven del curso, aplicada a la UI.

Analogía: una landing con el contenido disperso es como una tienda donde cada cartel de precio está escrito a mano en su estantería: cambiar uno implica recordar dónde está. Con datos centralizados es como un sistema de etiquetas electrónicas: cambias el precio en el sistema y todas se actualizan.

El sistema de diseño mínimo

Para que la landing se vea coherente y no como un collage, definimos tres cosas en @theme:

  • Color de marca: una escala (50, 500, 700) que da identidad a botones y acentos.
  • Fuente de display: un tipo de letra para titulares, distinto del cuerpo.
  • Espaciado y contenedor: un ancho máximo (una «columna» de contenido) reusable en todas las secciones.

Todo eso se define una vez; las clases de Tailwind lo reutilizan. Es lo que separa una landing amateur de una profesional.

Regla del contenedor: elige un patrón único, por ejemplo mx-auto max-w-6xl px-6, y repítelo en cada sección. La coherencia del margen horizontal es lo que hace que una página se sienta «diseñada».

Rendimiento: por qué casi no hace falta JavaScript

Una landing estática con Astro puede cargar cero JavaScript propio. El navbar móvil, si es un simple enlace, no necesita scripts. Solo si quieres un menú desplegable interactivo plantearías una isla. Y aun así, usarías client:visible para no cargarla hasta que haga falta. Recuerda el Módulo 4: hidratación selectiva, no por defecto.

3 · Ejemplo mínimo

Antes de la landing completa, la pieza mínima: una sección de features data-driven que ya usaremos en el proyecto.

src/components/FeatureGrid.astro
---
// El contenido vive aqui, no en el HTML. Cambiar una feature
// es editar un objeto de este array.
interface Feature {
  icon: string;
  title: string;
  description: string;
}

const features: Feature[] = [
  { icon: '⚡', title: 'Rapido', description: 'HTML estatico servido al instante.' },
  { icon: '🧩', title: 'Islands', description: 'Solo se hidrata lo que lo necesita.' },
  { icon: '🎨', title: 'Tailwind', description: 'Estilos con utilidades coherentes.' },
];
---

<section class="mx-auto max-w-6xl px-6 py-24">
  <div class="grid gap-8 md:grid-cols-3">
    {features.map((feature) => (
      <article class="rounded-2xl border border-slate-800 bg-slate-900/50 p-8">
        <span class="text-3xl" aria-hidden="true">{feature.icon}</span>
        <h3 class="mt-4 text-lg font-semibold text-white">{feature.title}</h3>
        <p class="mt-2 text-slate-400">{feature.description}</p>
      </article>
    ))}
  </div>
</section>

Explicado línea a línea:

  1. La interface Feature: describe la forma de cada elemento. Si te falta un campo, TypeScript avisa antes de compilar.
  2. El array features: la fuente de verdad del contenido de la sección.
  3. features.map(...): genera una tarjeta por elemento. Añadir una feature es añadir un objeto.
  4. Las clases de Tailwind: grid gap-8 md:grid-cols-3 crea tres columnas en pantallas medianas y una en móvil, sin media queries escritas a mano.
  5. aria-hidden="true" en el icono: es decorativo; que los lectores de pantalla no lo anuncien.

Decisiones profesionales detrás del proyecto:

  • Todo es un componente: el navbar, el hero, features, pricing y el CTA son piezas independientes y reutilizables.
  • Contenido data-driven: features y planes viven en arrays. Cambiar el producto es editar datos.
  • Sistema de diseño en @theme: el color y la tipografía se definen una vez. La coherencia visual es automática.
  • Imagen LCP priorizada: el fondo del hero es loading="eager" con fetchpriority="high"; el resto de imágenes serían lazy.
  • Cero JavaScript de cliente: ninguna interacción necesita hidratación. La página es HTML + CSS puro: máxima velocidad.

Verifica en DevTools: abre la pestaña Network y refresca. Con esta landing no debería haber ningún archivo JavaScript de framework: solo el CSS de Tailwind y las fuentes. Si ves JS de un framework, has añadido una isla que no necesitas. En Lighthouse (modo móvil), apunta a puntuaciones de rendimiento superiores a 95.

6 · Errores habituales

Copiar el mismo botón con clases distintas

✗ Incorrecto

<!-- Tres botones "iguales" con clases que ya no coinciden. -->
<a href="/a" class="rounded bg-blue-500 px-4 py-2 text-white">Empezar</a>
<a href="/b" class="rounded-lg bg-blue-600 px-4 py-3 text-white">Empezar</a>
<a href="/c" class="rounded bg-blue-500 px-4 py-2 text-white font-medium">Empezar</a>

✓ Correcto

---
// Un componente Button.astro con la clase en un sitio.
const { href = '#', variant = 'primary' } = Astro.props;
---
<a href={href} class:list={['rounded-lg px-4 py-2 font-medium', variant === 'primary' ? 'bg-brand-500 text-white' : 'bg-slate-800 text-slate-100']}>
  <slot />
</a>

Cuando reutilizas estilos copiando clases, en tres iteraciones ya tienes botones que se ven distintos. Un componente centraliza el estilo.

Hardcodear el contenido repetido

✗ Incorrecto

<!-- El precio 19€ esta escrito en cinco sitios distintos. -->
<p>19€/mes</p>
...
<p>Solo 19€ al mes</p>

✓ Correcto

---
const plans = [{ name: 'Pro', price: 19 }]; // una sola fuente
---
{plans.map((p) => <p>{p.price}€/mes</p>)}

El contenido repetido escrito a mano se desincroniza en cuanto cambias un dato. Los arrays son la fuente de verdad.

Imagen de hero sin optimizar

✗ Incorrecto

<!-- JPG de 2 MB, sin srcset, sin lazy/eager controlado. -->
<img src="/hero.jpg" class="absolute inset-0 w-full" alt="">

✓ Correcto

---
import { Picture } from 'astro:assets';
import backdrop from '../assets/hero-backdrop.jpg';
---
<Picture src={backdrop} formats={['avif', 'webp']} fallbackFormat="jpg" alt="" loading="eager" fetchpriority="high" widths={[768, 1280, 1920]} sizes="100vw" />

El hero es la imagen que más impacta el rendimiento percibido. Optimizarla (formato, tamaño, prioridad) es la mejora de mayor retorno.

Añadir una isla que no hace falta

✗ Incorrecto

<!-- Componente React solo para mostrar texto estatico: JS inutil. -->
<Headline client:load />

✓ Correcto

<!-- Es texto: un elemento .astro, cero JavaScript. -->
<h1 class="text-5xl font-bold">Titular</h1>

Hidratar un componente que no tiene interacción es enviar JavaScript para nada. En una landing, la respuesta por defecto es «sin isla».

8 · Reto

🎯 Landing multilingüe con tema claro/oscuro

Lleva la landing a un nivel de producción real:

  • Modo claro y oscuro: un tema alternable sin recargar, gestionado con una isla mínima (por ejemplo, un componente Preact/React con client:idle) que guarde la preferencia. Aquí sí se justifica JavaScript: es una interacción real.
  • Internacionalización: dos idiomas (español e inglés) con las rutas / y /en/, reaprovechando los mismos componentes con textos distintos.
  • Sección de FAQ con un acordeón accesible (puede resolverse con <details>, sin JavaScript, o con una isla).
  • Sitemap: integra @astrojs/sitemap para que todas las rutas queden indexables.

Mide el resultado con Lighthouse en modo móvil y compáralo con el de la versión sin isla. Analiza cuánto cuesta en rendimiento el JavaScript que añadiste «de verdad».

Pista: para el tema, hidrata con client:idle y aplica la clase en un <html> o <body>. Para i18n, evita duplicar componentes: pasa los textos como props. Y plantéate si el acordeón con <details> hace innecesaria otra isla.

9 · Resumen

  • Una landing se descompone en componentes: navbar, hero, features, pricing, CTA y footer.
  • El contenido vive en arrays tipados, no disperso por el HTML.
  • Un sistema de diseño mínimo (@theme: marca, fuente, contenedor) da coherencia visual.
  • La imagen del hero es el LCP: se optimiza con <Picture> y prioridad de carga.
  • Las landing estáticas no necesitan JavaScript de cliente: cero islas por defecto.
  • Tailwind y los componentes se combinan: las utilidades no sustituyen a la componentización.

10 · Preguntas frecuentes

¿La landing necesita alguna isla para ser «moderna»?

No. «Moderna» es que cargue rápido y sea mantenible, no que tenga JavaScript. Esta landing no necesita ninguna isla y ese es su punto fuerte. Añade una isla solo cuando exista una interacción que no puedas resolver con HTML/CSS (un menú complejo, un alternador de tema con persistencia…).

¿Cómo hago un menú móvil sin JavaScript?

Puedes usar un <details> con un <summary> como botón (funciona sin JS) o, si quieres animación y control fino, una isla pequeña con client:visible. Empieza por la opción sin JS; solo si la experiencia lo exige, hidrata.

¿Merece la pena separar el contenido en un archivo de datos?

Para una sola página, un array en el frontmatter basta. Si el contenido crece o se reutiliza entre páginas, muévelo a src/data/ o a una Content Collection (Módulo 3). El criterio es la reutilización: un dato que vive en un sitio no debe copiarse en dos.

¿Puedo reutilizar estos componentes en otra página del sitio?

Sí, ese es justo el objetivo de los componentes .astro. Navbar, CtaFinal o Pricing funcionan en cualquier página. Si un componente tiene que verse distinto según la página, pásale props en lugar de duplicarlo.

¿Cómo garantizo que los precios estén en un solo sitio?

Extrayendo el array de planes a src/data/plans.ts e importándolo donde haga falta (la sección de precios y, si los mencionas en el hero, también allí). Un dato, un origen.
