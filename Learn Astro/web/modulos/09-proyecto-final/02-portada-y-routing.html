Portada, routing y colecciones

Módulo 9 · Proyecto Final: Blog Profesional 🕐 40 minutos

1 · Introducción

Con la arquitectura y los cimientos listos, toca levantar las paredes: la portada, el listado de artículos, la página de detalle de cada post y las páginas de etiqueta. Todo generado en build a partir de la colección, con URLs limpias y sin un solo kilobyte de JavaScript innecesario.

Esta lección es, sobre todo, sobre routing: cómo el sistema de ficheros de Astro se convierte en URLs, cómo getStaticPaths genera una página por cada post, y cómo organizamos las rutas para que crezcan sin desorden.

¿Por qué existe esta lección? Porque el routing es donde más se nota si entendiste el modelo de Astro o solo copiaste ejemplos. Un blog tiene una forma de URLs muy concreta (/blog, /blog/post, /tags/react) y cada una se genera de una manera distinta. Dominar getStaticPaths, los layouts y la reutilización de componentes convierte cien artículos en cien páginas sin escribir cien ficheros.

2 · Teoría

El fichero es la URL: el routing por sistema de ficheros

En Astro no hay un fichero de rutas que declarar. La ruta es la ubicación del fichero en src/pages/. Esto se llama routing basado en ficheros (file-based routing) y es compartido con Next.js y Nuxt.

FicheroURL generada
src/pages/index.astro/
src/pages/blog/index.astro/blog
src/pages/blog/[slug].astro/blog/cualquier-cosa (una por cada slug)
src/pages/tags/[tag].astro/tags/react, /tags/astro…
src/pages/rss.xml.ts/rss.xml (endpoint que devuelve XML)

Los corchetes indican un segmento dinámico: [slug].astro no genera una URL, sino todas las URLs que le digas. ¿Cómo se lo dices? Con getStaticPaths. Es la pieza central de esta lección.

getStaticPaths: una página, muchos posts

Cuando el build encuentra [slug].astro, necesita saber qué valores tomará slug. Se lo pides con getStaticPaths, que devuelve una lista de combinaciones { params, props }: una por página a generar.

  Build de Astro encuentra blog/[slug].astro
        |
        v
  llama a getStaticPaths()
        |
        v
  [ { params: { slug: 'primer-post' }, props: { entry } },
    { params: { slug: 'segundo-post' }, props: { entry } } ]
        |
        +--> genera dist/blog/primer-post/index.html
        +--> genera dist/blog/segundo-post/index.html

Dos consecuencias importantes: primero, todo se genera en build time (no hay servidor). Segundo, los datos del post viajan como props, así que la página no vuelve a consultar la colección.

Analogía: [slug].astro es una plantilla de imprenta. getStaticPaths es la orden de trabajo: «imprime una copia por cada uno de estos artículos, poniendo este título y este texto en cada una». La plantilla es la misma; los datos cambian. Al final tienes todas las copias ya impresas, listas para repartir.

Los layouts: una estructura, muchas páginas

Un blog repite la misma estructura en todas las páginas: cabecera, contenido, pie, metadatos. En Astro eso se encapsula en layouts, que son componentes .astro con un <slot /> donde cada página inyecta su contenido.

LayoutResponsabilidad
BaseLayout.astro<html>, <head>, SEO, header/footer globales
PostLayout.astroEstructura del artículo: título, fecha, tags, contenido, navegación prev/next
BlogLayout.astroListados: título de sección, rejilla, paginación (si la hay)

Componente, no copia-pega: en cuanto ves la misma tarjeta de post en la portada, en el listado y en la página de tag, tienes un componente. Un PostCard significa que cambiar el diseño del listado es tocar un solo fichero.

El id de una entrada como slug

En Astro 5, cada entrada de una colección tiene un id (antes slug) derivado de la ruta del fichero. Un fichero src/content/blog/mi-articulo.md genera el id mi-articulo. Es ese id el que usamos como slug en las rutas dinámicas y en los enlaces.

Ficheroid de la entradaURL
content/blog/astro-islands.mdastro-islands/blog/astro-islands
content/blog/2026/reflexiones.md2026/reflexiones/blog/2026/reflexiones

3 · Ejemplo mínimo

La página de detalle más pequeña posible: genera una URL por post y muestra su título y su contenido.

src/pages/blog/[slug].astro
---
import { getCollection } from 'astro:content';

// Astro llama a esta funcion en el BUILD para saber que paginas crear.
export async function getStaticPaths() {
  const posts = await getCollection('blog');

  // Una entrada por cada post: params.slug forma la URL, props lleva los datos.
  return posts.map((post) => ({
    params: { slug: post.id },
    props: { post },
  }));
}

// Astro inyecta las props que devolvio getStaticPaths.
const { post } = Astro.props;

// Renderizamos el Markdown de la entrada como componente.
const { Content } = await post.render();
---
<html lang="es">
  <body>
    <h1>{post.data.title}</h1>
    <Content />
  </body>
</html>

Verifica:

  1. Build: ejecuta pnpm build y mira dist/blog/: hay una carpeta por cada post, cada una con su index.html.
  2. Prueba una URL: abre /blog/primer-post; el HTML ya trae el contenido, sin consultar nada.
  3. Prueba una URL inexistente: /blog/no-existe no se generó, así que da 404. Solo existen las páginas que getStaticPaths declaró.

La página de detalle, completa

src/pages/blog/[slug].astro
---
import { getCollection } from 'astro:content';
import PostLayout from '../../layouts/PostLayout.astro';

export async function getStaticPaths() {
  // Solo posts publicados, de mas reciente a mas antiguo.
  const posts = (await getCollection('blog', ({ data }) => !data.draft))
    .sort((a, b) => b.data.pubDate.valueOf() - a.data.pubDate.valueOf());

  return posts.map((post, i) => ({
    params: { slug: post.id },
    // Calculamos prev/next AQUI (en build), no en la pagina.
    props: {
      post,
      next: posts[i - 1], // el mas reciente (i menor = mas nuevo)
      prev: posts[i + 1], // el mas antiguo
    },
  }));
}

const { post, prev, next } = Astro.props;
const { Content } = await post.render();
---
<PostLayout post={post} prev={prev} next={next}>
  <Content />
</PostLayout>

src/pages/tags/[tag].astro
---
import BaseLayout from '../../layouts/BaseLayout.astro';
import PostCard from '../../components/PostCard.astro';
import { getPosts, getTags } from '../../lib/posts';

export async function getStaticPaths() {
  const tags = await getTags(); // [{ tag, count }, ...]

  // Una pagina por etiqueta; los posts se calculan en build y viajan como props.
  const posts = await getPosts();
  return tags.map(({ tag }) => ({
    params: { tag },
    props: { tag, posts: posts.filter((p) => p.data.tags.includes(tag)) },
  }));
}

const { tag, posts } = Astro.props;
---
<BaseLayout title={`#${tag}`} description={`Articulos etiquetados con ${tag}`}>
  <h1>Articulos con #{tag}</h1>
  <p>{posts.length} articulos.</p>
  <div class="grid">
    {posts.map((post) => <PostCard post={post} />)}
  </div>
  <a href="/tags">← Todas las etiquetas</a>
</BaseLayout>

Decisiones explicadas:

  • Toda la lógica de datos se calcula en getStaticPaths: prev/next, filtrado por etiqueta… Es el punto donde ya tienes la colección cargada; la página solo pinta.
  • Reutilización vía PostCard: portada, listado y tag comparten la misma tarjeta. Consistencia y mantenimiento.
  • Layouts anidados: PostLayout usa BaseLayout; cada nivel añade su parte sin duplicar el <head> ni el SEO.
  • Fechas legibles y <time datetime>: el usuario ve la fecha formateada y las máquinas reciben un ISO válido (bueno para SEO).

6 · Errores habituales

Olvidar getStaticPaths en una ruta dinámica

✗ Incorrecto

---
// Escribes blog/[slug].astro pero no declaras que paginas generar.
// El build falla: no sabe que URLs crear.
const { post } = Astro.props;
---

✓ Correcto

---
export async function getStaticPaths() {
  const posts = await getCollection('blog');
  return posts.map((post) => ({ params: { slug: post.id }, props: { post } }));
}
const { post } = Astro.props;
---

En modo estático, una ruta dinámica sin getStaticPaths no tiene nada que generar. Es el error número uno al empezar con blogs.

Consultar la colección otra vez dentro de la página

✗ Incorrecto

---
export async function getStaticPaths() {
  const posts = await getCollection('blog');
  return posts.map((post) => ({ params: { slug: post.id }, props: { post } }));
}
const { post } = Astro.props;
// Volvemos a cargar TODA la coleccion para algo que ya teniamos.
const all = await getCollection('blog');
---

✓ Correcto

---
export async function getStaticPaths() {
  const posts = await getCollection('blog');
  return posts.map((post, i) => ({
    params: { slug: post.id },
    // Lo que necesitemos, lo pasamos como props ya calculado.
    props: { post, prev: posts[i + 1], next: posts[i - 1] },
  }));
}
---

La colección ya está en memoria durante getStaticPaths. Volver a consultarla es trabajo duplicado y hace el código más confuso.

Duplicar el <head> y el SEO en cada página

✗ Incorrecto

<!-- Copiar y pegar metadatos en cada pagina: se desincronizan. -->
<meta name="description" content="..." />
<meta property="og:title" content="..." />

✓ Correcto

---
// El layout genera todos los metadatos a partir de estas props.
---
<BaseLayout title={post.data.title} description={post.data.description}>
  <Content />
</BaseLayout>

El SEO repetido se desincroniza y genera metadatos inconsistentes. Encapsúlalo en el layout.

Construir URLs a mano

✗ Incorrecto

<!-- Suele quedar un slash de mas o apuntar a un formato antiguo. -->
<a href="/blog/post/primer-post.html">{post.data.title}</a>

✓ Correcto

<!-- Una unica forma de construir la URL del post. -->
<a href={`/blog/${post.id}`}>{post.data.title}</a>

Escribir URLs a mano garantiza enlaces rotos. Deriva siempre la URL de los datos (post.id).

8 · Reto

🎯 Paginación y un feed RSS

Amplía el routing con dos piezas de un blog de verdad:

  • Paginación: en lugar de listar todos los posts en /blog, crea /blog/2, /blog/3… con un número fijo de posts por página y enlaces «anterior/siguiente». Decide cuántos por página y cómo se comporta la última.
  • Feed RSS: crea un endpoint src/pages/rss.xml.ts que devuelva el feed XML con los últimos artículos (título, descripción, fecha y URL absoluta). Recuerda que las URLs absolutas necesitan site configurado.
  • Bonus de accesibilidad: añade un enlace <link rel="alternate" type="application/rss+xml"> en el <head> del layout, para que los lectores de feeds descubran el RSS.

Pista: la paginación se resuelve con getStaticPaths generando { params: { page: '2' } }, y otra ruta blog/[...page].astro para que /blog (sin número) sea la página 1. Para el RSS, Astro tiene la integración oficial @astrojs/rss y un rss() helper que te evita escribir el XML a mano. Piensa qué campos del esquema necesita el feed y si tu description es lo bastante buena como resumen. Y cuidado: el enlace de RSS debe estar en el <head>, donde lo buscan los lectores, no en el footer.

9 · Resumen

  • El routing es basado en ficheros: la ruta es la ubicación en src/pages/.
  • Los segmentos dinámicos ([slug], [tag]) generan muchas URLs desde un fichero.
  • getStaticPaths devuelve { params, props } y es donde se calcula todo lo que necesita cada página.
  • El id de una entrada de colección es su slug natural en Astro 5.
  • Los layouts encapsulan estructura y SEO; PostCard encapsula la tarjeta reutilizable.
  • Todo se genera en build: las páginas estáticas ya contienen el contenido, sin servidor.

10 · Preguntas frecuentes

¿Qué diferencia hay entre id y slug en Astro 5?

En el Content Layer de Astro 5, cada entrada tiene un id derivado de la ruta del fichero (por ejemplo mi-articulo o 2026/notas). En versiones anteriores se hablaba de slug. A efectos prácticos, usamos post.id como el segmento de la URL. Si necesitas una URL distinta a la del fichero, puedes añadir un campo slug propio al esquema y usarlo en getStaticPaths.

¿Puedo hacer la página de detalle sin getStaticPaths?

Solo si activas SSR (prerender = false + adaptador), porque entonces la ruta se resuelve en cada petición en vez de generarse en build. Para un blog estático, casi siempre quieres getStaticPaths: genera HTML de antemano y no necesita servidor. Usa SSR solo si tu contenido cambia constantemente y no puedes reconstruir, algo raro en un blog.

¿Cómo evito repetir el código de las tarjetas?

Extrayéndolo a un componente: PostCard.astro. Regla práctica: en cuanto el mismo bloque de marcado aparece en dos sitios, es un componente. En Astro, los componentes no tienen coste en tiempo de ejecución: se renderizan a HTML en el build. Así que extraer no solo mejora el mantenimiento, no cuesta nada al usuario.

¿Los borradores aparecen en las páginas de etiqueta?

No, si sigues el patrón de esta lección: getPosts() ya filtra los borradores y tanto el listado como las etiquetas lo usan. Ese es exactamente el beneficio de centralizar las consultas: el filtro se aplica en todas partes sin repetirlo. Si un borrador apareciera, el bug estaría en una página que consultó la colección directamente en vez de usar el helper.

¿Cuántos posts puede manejar este enfoque?

Miles sin problema. El build genera un HTML por ruta, y el tiempo de build crece linealmente con el número de páginas. A partir de decenas de miles de artículos, plantéate paginación, generación incremental o pasar el catálogo a un CMS con búsqueda del lado servidor. Para un blog personal o profesional normal, el enfoque estático es el adecuado durante muchísimo tiempo.
