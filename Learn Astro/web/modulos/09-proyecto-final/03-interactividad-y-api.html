Islands, API y formularios

Módulo 9 · Proyecto Final: Blog Profesional 🕐 40 minutos

1 · Introducción

El blog ya tiene portada, listado, detalle y etiquetas, todo estático. Pero le faltan las dos piezas que necesitan JavaScript: un buscador/filtro de artículos y un formulario de newsletter. Aquí es donde la arquitectura de islas de Astro demuestra su valor: añadimos interactividad sin convertir el blog en una SPA y sin hidratar todo lo demás.

Veremos también los endpoints: cuándo un formulario debe hablar con el servidor, cómo recibir datos y devolver respuestas, y por qué a veces conviene no tener servidor en absoluto (un índice de búsqueda pre-generado).

¿Por qué existe esta lección? Porque la diferencia entre un blog bonito y un blog profesional está, muchas veces, en dos cosas: que la búsqueda funcione al instante y que suscribirse sea fácil. Y porque la tentación de «hacerlo todo React» es enorme. Aquí aprenderás a dibujar la frontera: HTML estático por defecto, una isla pequeña y bien delimitada para lo interactivo, y un endpoint solo cuando de verdad hace falta un servidor.

2 · Teoría

La frontera de la interactividad

Antes de escribir una isla, pregúntate qué parte exacta de la página necesita JavaScript. Casi siempre es mucho menos de lo que parece.

Elemento del blog¿Necesita JS?Por qué
Portada, artículo, listadosNoContenido estático: HTML puro
Enlaces de navegaciónNoUn <a> no hidrata nada
Buscador/filtro en vivoSíResponde a la escritura sin recargar
Formulario de newsletterSíEstado de envío y feedback
Índice de etiquetasNoSon enlaces estáticos

Analogía: una isla en el océano es exactamente esto: una porción pequeña de terreno dinámico rodeada de océano estático. El océano (el blog entero) se sirve como HTML que ya funciona; la isla (el buscador) carga su JavaScript cuando hace falta. Si mañana quitas la isla, la página sigue viva.

Dos formas de hacer la búsqueda

Hay dos arquitecturas para un buscador de blog, y elegir bien es una decisión de arquitectura:

EnfoqueCómo funcionaCosteFrescura
Índice pre-generado Un endpoint estático /search.json que se genera en build; la isla lo carga una vez y filtra en el cliente Cero servidor; un JSON que crece con los posts La del último build (suficiente para un blog)
API dinámica Una ruta SSR que recibe ?q= y busca (en DB o servicio externo) Un servidor por petición Inmediata

Regla de oro: para un blog con miles de artículos como máximo, el índice pre-generado gana. Es un blog: su contenido cambia cuando publicas, no por segundo. Un JSON estático filtrado en el cliente es instantáneo, gratis y sin servidor. Reserva la API dinámica para catálogos enormes o datos que cambian en vivo.

Endpoints en Astro: la misma carpeta, otro tipo de fichero

Un endpoint es un fichero en src/pages/ que, en vez de devolver HTML, devuelve datos. Se exportan funciones con el nombre del método HTTP (GET, POST…) y reciben un contexto.

src/pages/api/search.json.ts (endpoint ESTATICO: se genera en build)
import type { APIRoute } from 'astro';
import { getPosts } from '../../lib/posts';

// Un endpoint pre-renderizado: produce un JSON estatico en el build.
export const prerender = true;

// Astro infiere el content-type .json por la extension del fichero.
export const GET: APIRoute = async () => {
  const posts = await getPosts();

  // Solo lo minimo para buscar: id, titulo, descripcion, tags.
  const index = posts.map((p) => ({
    id: p.id,
    title: p.data.title,
    description: p.data.description,
    tags: p.data.tags,
  }));

  return new Response(JSON.stringify(index), {
    headers: { 'Content-Type': 'application/json' },
  });
};

Fíjate en la elegancia: search.json es un endpoint, pero se genera en build como un fichero. No hay servidor. La isla lo descarga como cualquier otro recurso estático y filtra en memoria. Es la mejor de ambas vías combinada.

Enviar un formulario: isla + endpoint

El formulario de newsletter sí necesita un servidor (enviar el email a tu proveedor, guardar el suscriptor). El patrón es: la isla gestiona los estados y hace fetch al endpoint; el endpoint hace el trabajo y responde. Es exactamente lo que viste en el Módulo 8 con las variables de entorno, pero aplicado a un formulario.

  [isla React]                    [endpoint POST]
  estado: idle/submitting/...      recibe { email }
        |                          valida en servidor
        | fetch('/api/newsletter') verifica el secreto (servidor)
        +------------------------> llama al proveedor
        |                          |
        |<-------- 200 / 4xx ------+
        v
  estado: success / error

src/components/ReactFilter.tsx
import { useState } from 'react';

// La isla recibe los datos ya listos; no consulta nada.
export default function ReactFilter({ posts }) {
  const [query, setQuery] = useState('');

  // Filtrado derivado: no es estado, se calcula en cada render.
  const filtered = posts.filter((p) =>
    p.title.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <div>
      <input
        type="search"
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Buscar articulos…"
        aria-label="Buscar articulos"
      />
      <ul>
        {filtered.map((p) => (
          <li key={p.id}><a href={`/blog/${p.id}`}>{p.title}</a></li>
        ))}
      </ul>
    </div>
  );
}

Con client:visible, el JavaScript de la isla solo se descarga cuando el bloque entra en pantalla. Antes de eso, no hay coste. Y si el usuario no llega ahí, no se hidrata nunca.

4 · Ejemplo real

El buscador completo (con índice pre-generado) y el formulario de newsletter con su endpoint. Son las dos islas del blog.

El índice de búsqueda

src/pages/api/search.json.ts
import type { APIRoute } from 'astro';
import { getPosts } from '../../lib/posts';

// Pre-renderizado: el JSON se genera en el build, no hay servidor.
export const prerender = true;

export const GET: APIRoute = async () => {
  const posts = await getPosts();
  const index = posts.map((p) => ({
    id: p.id,
    title: p.data.title,
    description: p.data.description,
    // Incluimos tags y autor para poder filtrar tambien por ellos.
    tags: p.data.tags,
    author: p.data.author,
  }));
  return new Response(JSON.stringify(index), {
    headers: { 'Content-Type': 'application/json' },
  });
};

El buscador como isla

src/components/SearchBox.tsx
import { useEffect, useMemo, useState } from 'react';

// Tipo del indice que sirve /api/search.json.
type PostIndex = {
  id: string;
  title: string;
  description: string;
  tags: string[];
  author: string;
};

export default function SearchBox() {
  // El indice se carga UNA vez al montar la isla.
  const [index, setIndex] = useState<PostIndex[]>([]);
  const [query, setQuery] = useState('');
  const [tag, setTag] = useState<string | null>(null);

  useEffect(() => {
    // Descarga unica del indice estatico; luego todo es local e instantaneo.
    fetch('/api/search.json')
      .then((r) => r.json())
      .then(setIndex)
      .catch(() => setIndex([]));
  }, []);

  // Lista de tags derivada del indice cargado.
  const allTags = useMemo(
    () => [...new Set(index.flatMap((p) => p.tags))].sort(),
    [index]
  );

  // Resultados derivados de query + tag seleccionado. Sin estado extra.
  const results = useMemo(() => {
    const q = query.trim().toLowerCase();
    return index.filter((p) => {
      const matchesText =
        !q ||
        p.title.toLowerCase().includes(q) ||
        p.description.toLowerCase().includes(q);
      const matchesTag = !tag || p.tags.includes(tag);
      return matchesText && matchesTag;
    });
  }, [index, query, tag]);

  return (
    <section aria-label="Buscador de articulos">
      <input
        type="search"
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Buscar por titulo o descripcion…"
        aria-label="Buscar articulos"
      />

      <div role="group" aria-label="Filtrar por etiqueta">
        <button onClick={() => setTag(null)} aria-pressed={tag === null}>Todas</button>
        {allTags.map((t) => (
          <button key={t} onClick={() => setTag(t)} aria-pressed={tag === t}>
            #{t}
          </button>
        ))}
      </div>

      {/* aria-live anuncia el numero de resultados a lectores de pantalla. */}
      <p aria-live="polite">{results.length} resultados</p>

      <ul>
        {results.map((p) => (
          <li key={p.id}>
            <a href={`/blog/${p.id}`}>{p.title}</a>
            <small>{p.description}</small>
          </li>
        ))}
      </ul>
    </section>
  );
}

Comentarios en JSX: dentro del JSX no se pueden usar comentarios HTML con <!-- -->; se escriben como expresiones {/* … */}, como en el código anterior. Es una diferencia con los ficheros .astro, donde los comentarios HTML sí son válidos fuera del frontmatter.

El formulario de newsletter

src/pages/api/newsletter.ts
import type { APIRoute } from 'astro';

export const POST: APIRoute = async ({ request }) => {
  const { email } = await request.json<{ email?: string }>();

  // Revalidacion en servidor: el cliente no es de fiar.
  if (!email || !/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email)) {
    return Response.json({ error: 'Email no valido' }, { status: 400 });
  }

  // El secreto vive en el servidor (Modulo 8); el cliente nunca lo ve.
  const apiKey = import.meta.env.NEWSLETTER_API_KEY;

  const res = await fetch('https://api.newsletter.example/subscribers', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${apiKey}` },
    body: JSON.stringify({ email }),
  });

  if (!res.ok) {
    // No filtramos detalles internos del proveedor.
    return Response.json({ error: 'No se pudo suscribir' }, { status: 502 });
  }
  return Response.json({ ok: true }, { status: 201 });
};
src/components/NewsletterForm.tsx
import { useState, type FormEvent } from 'react';

type Status = 'idle' | 'submitting' | 'success' | 'error';

export default function NewsletterForm() {
  const [email, setEmail] = useState('');
  const [status, setStatus] = useState<Status>('idle');

  async function handleSubmit(e: FormEvent) {
    e.preventDefault();
    setStatus('submitting');
    try {
      const res = await fetch('/api/newsletter', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ email }),
      });
      setStatus(res.ok ? 'success' : 'error');
    } catch {
      setStatus('error');
    }
  }

  if (status === 'success') {
    return <p role="status">¡Gracias! Revisa tu correo para confirmar.</p>;
  }

  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="nl-email">Tu email</label>
      <input
        id="nl-email"
        type="email"
        value={email}
        onChange={(e) => setEmail(e.target.value)}
        required
        aria-invalid={status === 'error'}
      />
      <button type="submit" disabled={status === 'submitting'}>
        {status === 'submitting' ? 'Enviando…' : 'Suscribirme'}
      </button>
      {status === 'error' && <p role="alert">No se pudo suscribir. Intentalo de nuevo.</p>}
    </form>
  );
}

src/pages/blog/index.astro

import NewsletterForm from '../../components/NewsletterForm.tsx';
---
<BaseLayout title="Blog" description="Busca y filtra todos los articulos">
  <h1>Blog</h1>
  <!-- El listado estatico puede seguir aqui, o dejar solo el buscador. -->
  <SearchBox client:visible />

    <h2>Suscribete</h2>
    <!-- El formulario esta arriba: lo hidratamos al cargar. -->
    <NewsletterForm client:load />
  </section>
</BaseLayout>

Decisiones explicadas:

  • Índice pre-generado: cero servidor para la búsqueda; el JSON se construye en el build y se descarga una vez.
  • Filtrado derivado con useMemo: los resultados no son estado, se calculan de query y tag. Menos estado, menos bugs.
  • client:visible para el buscador y client:load para el formulario: el buscador está abajo y espera; el formulario, si es un CTA, conviene cargarlo ya.
  • El endpoint revalida: la validación del cliente es UX; la del servidor es seguridad.
  • Secreto en servidor: la clave del proveedor de newsletter nunca llega al navegador.
  • Accesibilidad: aria-live en el número de resultados y role="alert" en los errores.

6 · Errores habituales

Mandar todo el contenido al navegador

✗ Incorrecto

// El indice incluye el cuerpo COMPLETO de cada post: megas al cliente.
const index = posts.map((p) => ({ id: p.id, body: p.body }));

✓ Correcto

// Solo lo necesario para buscar y mostrar resultados.
const index = posts.map((p) => ({
  id: p.id, title: p.data.title, description: p.data.description, tags: p.data.tags,
}));

El índice de búsqueda se descarga entero en el cliente. Incluir el contenido completo hace que crezca sin control. Busca por título, descripción y tags; el cuerpo se lee en la página del post.

Guardar los resultados del filtro en estado

✗ Incorrecto

// Estado duplicado: se desincroniza de query y tag.
const [results, setResults] = useState([]);
useEffect(() => setResults(filter(query, tag)), [query, tag]);

✓ Correcto

// Derivado: siempre coherente con las entradas.
const results = useMemo(() => filter(query, tag), [query, tag]);

Duplicar el resultado en estado añade una sincronización que puede fallar. Derívalo de las entradas y elimina la clase de bug entera.

Confiar en el cliente para validar

✗ Incorrecto

// El endpoint guarda lo que llegue, sin comprobar nada.
export const POST: APIRoute = async ({ request }) => {
  const { email } = await request.json();
  await saveSubscriber(email); // confia ciegamente en el cliente
};

✓ Correcto

export const POST: APIRoute = async ({ request }) => {
  const { email } = await request.json();
  if (!email || !/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email)) {
    return Response.json({ error: 'Email no valido' }, { status: 400 });
  }
  await saveSubscriber(email);
};

El formulario puede saltarse con una petición manual. El endpoint debe validar siempre, pase lo que pase en el cliente.

Hidratar el buscador con client:load sin motivo

✗ Incorrecto

<!-- Descarga React al cargar la pagina, aunque el buscador este abajo. -->
<SearchBox client:load />

✓ Correcto

<!-- Solo hidrata cuando el usuario llega al buscador. -->
<SearchBox client:visible />

El buscador suele estar al final del listado. client:visible retrasa la descarga hasta que se necesita, mejorando la carga inicial sin perder funcionalidad.

Objetivo: añadir al blog un buscador con índice pre-generado y un formulario de newsletter funcional.

  5. Construye el endpoint de newsletter src/pages/api/newsletter.ts que valide el email en servidor y (simulando) llame al proveedor usando una variable secreta.
  6. Construye la isla del formulario src/components/NewsletterForm.tsx con los cuatro estados (idle, submitting, success, error) y móntala con client:load.

    pnpm dev

8 · Reto

🎯 Búsqueda con puntuación, historial y estados vacíos

Convierte el buscador en algo que se sienta profesional. Debe:

  • Ordenar los resultados por relevancia: una coincidencia en el título debe pesar más que en la descripción o en las etiquetas. Diseña una función de puntuación pura.
  • Mostrar un mensaje claro de «sin resultados» con sugerencias (por ejemplo, las etiquetas más usadas), en vez de una lista vacía.
  • Sincronizar la búsqueda con la URL (?q=react&tag=astro) para que se pueda compartir y el botón «atrás» funcione.
  • Guardar un historial de búsquedas recientes (máximo 5) y ofrecer «limpiar historial».
  • Mantener la accesibilidad: el número de resultados con aria-live y navegación con teclado por los resultados.

Pista: para la puntuación, recorre cada campo con distinto peso (título ×3, tags ×2, descripción ×1) y suma. Para la URL, lee los parámetros al montar y usa history.replaceState al cambiar la búsqueda, para no generar una entrada de historial por cada tecla. El «sin resultados» es donde más se nota el cuidado: un buscador que responde «nada» sin más se siente roto, aunque funcione. Y decide bien qué va en el historial: guardar cada tecla es ruido; guardar la búsqueda cuando el usuario la «confirma» es lo correcto.

9 · Resumen

  • La interactividad va en islas pequeñas; el resto del blog sigue siendo HTML estático.
  • Para un blog, la búsqueda se hace mejor con un índice pre-generado (JSON estático) que con un servidor.
  • Los datos se pasan a las islas como props desde el build, no consultando la colección en el cliente.
  • Los endpoints son ficheros en src/pages/ que devuelven datos; pueden ser estáticos (prerender = true) o dinámicos.
  • Los formularios hablan con un endpoint que revalida en servidor y usa secretos que el cliente nunca ve.
  • Elegir client:visible o client:load es una decisión de rendimiento, no un detalle.

10 · Preguntas frecuentes

¿La búsqueda con índice estático aguanta muchos posts?

Para un blog típico, sin problema. Un índice ligero (título, descripción, tags) de mil artículos pesa poco y se filtra en milisegundos en el cliente. El problema aparece si incluyes el cuerpo completo o si tienes decenas de miles de entradas. En ese momento valora cargar el índice por partes, usar un servicio de búsqueda o pasar a una API. Para el 99 % de los blogs, el índice estático es la respuesta correcta.

¿Por qué no hago la búsqueda con un endpoint SSR que reciba ?q=?

Puedes, pero para un blog estás pagando un servidor por algo que el cliente puede hacer más rápido y gratis. Con SSR, cada tecla es una petición de red y una ejecución de función. Con el índice estático, cada tecla es un filtrado en memoria. El SSR tiene sentido si el catálogo es enorme o si los datos cambian constantemente (inventario, productos), no para artículos que solo cambian cuando publicas.

¿Necesito el adaptador para un endpoint estático?

No. Un endpoint con prerender = true se genera en build como un fichero; no necesita runtime. Solo necesitas adaptador si el endpoint es dinámico (por ejemplo, el POST de newsletter con SSR). Es posible tener un blog 100 % estático si tu formulario delega en un servicio externo directamente; en cuanto quieres proteger un secreto, necesitas la función del servidor y, con ella, el adaptador.

¿Cómo evito que el formulario se envíe dos veces?

Con el estado submitting: el botón se deshabilita mientras la petición está en vuelo. Es el mismo patrón del Módulo 4. Además, en el servidor puedes añadir idempotencia (si llega el mismo email dos veces seguidas, no duplicar la suscripción). La combinación de ambos —UI que evita el doble clic y servidor que tolera reintentos— es la forma robusta.

¿Reacciono a cada tecla o espero?

Con un índice en memoria, reaccionar a cada tecla es instantáneo y no supone coste, así que hazlo. Si en el futuro usas un endpoint remoto, ahí sí conviene un debounce (esperar ~250 ms tras la última tecla) para no disparar una petición por pulsación. Como el filtrado local no tiene coste de red, el buscador se siente inmediato: esa inmediatez es, en gran parte, lo que hace que se perciba como «profesional».
