Arquitectura del blog profesional

Módulo 9 · Proyecto Final: Blog Profesional 🕐 45 minutos

1 · Introducción

Este es el proyecto final del curso: un blog profesional construido de principio a fin, y el primero en el que tú tomas las decisiones de arquitectura en vez de seguir una receta. La diferencia entre un blog de tutorial y uno profesional no está en las líneas de código, sino en las decisiones previas: dónde vive el contenido, qué es estático y qué es dinámico, cómo se estructura el SEO, qué se hidrata y qué no.

En esta primera lección no escribiremos aún el blog: diseñaremos su plano. Trazar bien la arquitectura al principio ahorra refactorizaciones dolorosas después y, sobre todo, hace que cada pieza encaje por una razón.

¿Por qué empezar por la arquitectura? Porque un blog es el ejemplo canónico de Astro: contenido en colecciones, rutas que se generan en build, islas para búsqueda, SEO como ciudadano de primera. Si entiendes por qué cada decisión es la correcta aquí, la aplicarás a cualquier proyecto content-driven. Y si empiezas escribiendo páginas sin mapa, acabarás con rutas duplicadas, contenido desorganizado y un SEO que no rinde.

2 · Teoría

Qué hace «profesional» a un blog

Un blog es, en esencia, una base de datos de artículos presentada de varias formas (portada, listado, detalle, por etiqueta). Lo que lo diferencia de un juguete son seis dimensiones que decidimos antes de escribir código:

DimensiónPregunta que respondeDecisión del proyecto
Contenido¿Dónde y cómo viven los artículos?Content Collections (Markdown + frontmatter validado con Zod)
Renderizado¿Qué se genera en build y qué en servidor?Todo estático por defecto; SSR solo para la API de búsqueda
Interactividad¿Qué necesita JavaScript?Islands: buscador/filtro y formulario de newsletter
Rutas¿Qué URLs existen?Portada, listado, detalle, tags, autor, RSS
SEO¿Cómo nos encuentran?Metadatos, canónicas, Open Graph, sitemap, JSON-LD
Rendimiento¿Qué tan rápido carga?Cero JS donde no hace falta; imágenes y fuentes optimizadas

Por qué Content Collections y no ficheros sueltos

Podrías poner los posts en src/pages/blog/*.md y listo. Pero entonces el contenido y las rutas están mezclados, no hay validación del frontmatter, y listar todos los posts exige leer el sistema de ficheros a mano. Las Content Collections separan contenido de presentación y añaden un esquema Zod que garantiza que cada post tiene los campos que esperas.

  src/content/blog/*.md          ->  contenido (una entrada por post)
        |  schema.zod valida frontmatter
        v
  getCollection('blog')          ->  datos tipados en build
        |
        +--> portada (ultimos 3)
        +--> listado (/blog)
        +--> detalle (/blog/[slug])
        +--> tags (/tags/[tag])

Analogía: las Content Collections son como una biblioteca con fichas normalizadas. Cada libro (post) trae una ficha (frontmatter) con campos obligatorios: título, fecha, autor, etiquetas. El bibliotecario (el esquema Zod) rechaza cualquier libro cuya ficha esté incompleta. Sin esa normalización, buscar «todos los libros de este autor» sería un caos.

Estático por defecto: la decisión que lo define todo

El contenido de un blog es igual para todos y cambia de vez en cuando (cuando publicas). Eso es exactamente el caso ideal para el renderizado estático: HTML pre-generado, servido desde el CDN, sin coste de cómputo por visita. La única ruta que necesita servidor es la API de búsqueda, si decides hacerla dinámica; incluso la búsqueda puede resolverse en el cliente con un índice pre-generado.

Regla de arquitectura: en un blog, el 100 % debería ser estático, con la posible excepción de la búsqueda y los formularios. Esto significa despliegue baratísimo, tiempo de respuesta mínimo y una superficie de ataque diminuta. Guarda el SSR para aplicaciones con datos por usuario.

Islands: solo lo que de verdad lo necesita

En un blog, casi nada necesita JavaScript. Las dos excepciones típicas:

  • Buscador/filtro: filtra el listado en vivo sin recargar. Puede ser una isla que reciba los posts como props (pre-generados) y filtre en el cliente.
  • Formulario de newsletter: necesita estado de envío y feedback.

Todo lo demás —portada, artículo, lista de tags— es HTML puro, sin hidratación.

Astro 5: las colecciones se definen en src/content.config.ts (en la raíz de src), no dentro de src/content/. Es uno de los cambios de la Content Layer de Astro 5; si ves tutoriales con src/content/config.ts, son de versiones anteriores. Los ficheros de contenido siguen viviendo en src/content/.

La frontera datos/presentación: lib/posts.ts

Un detalle de arquitectura que marca la diferencia: en lugar de importar getCollection en cada página, centraliza las consultas en src/lib/posts.ts. Así la lógica de «qué posts se publican», «cómo se ordenan», «cómo se agrupan por tag» vive en un solo sitio.

Sin lib/posts.tsCon lib/posts.ts
Cada página repite el filtro de borradoresEl filtro vive en un único sitio
Cambiar el orden exige tocar N ficherosCambias una función
Difícil de testearFunciones puras, fáciles de probar

3 · Ejemplo mínimo

El esqueleto arquitectónico mínimo y ya correcto: una colección con esquema, un helper y una ruta que la usa. Es la semilla del blog entero.

src/content.config.ts
import { defineCollection, z } from 'astro:content';

// El esquema es la ley: cada post DEBE cumplir estos campos.
const blog = defineCollection({
  type: 'content', // Markdown/MDX del Content Layer
  schema: z.object({
    title: z.string(),
    description: z.string(),
    pubDate: z.coerce.date(),
    draft: z.boolean().default(false),
  }),
});

// Registramos la coleccion para poder usar getCollection('blog').
export const collections = { blog };
src/lib/posts.ts
import { getCollection } from 'astro:content';

// Publicados y ordenados de mas reciente a mas antiguo.
// Esta es LA funcion que usaran todas las paginas.
export async function getPosts() {
  const posts = await getCollection('blog', ({ data }) => !data.draft);
  return posts.sort((a, b) => b.data.pubDate.valueOf() - a.data.pubDate.valueOf());
}
src/pages/index.astro (portada minima)
---
import { getPosts } from '../lib/posts';
const posts = await getPosts(); // se ejecuta en BUILD time
---
<h1>Mi blog</h1>
<ul>
  {posts.map((post) => (
    <li><a href={`/blog/${post.id}`}>{post.data.title}</a></li>
  ))}
</ul>

Fíjate: aún no hay ni una página de detalle, ni estilos, ni islas. Pero la columna vertebral ya está: contenido validado, consulta centralizada, página que consume. Todo lo que construiremos en las siguientes lecciones crece sobre esta base sin rehacerla.

El esquema de contenido, completo

src/content.config.ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const blog = defineCollection({
  // Content Layer de Astro 5: cargador glob sobre una carpeta.
  loader: glob({ pattern: '**/*.md', base: './src/content/blog' }),
  schema: ({ image }) => z.object({
    title: z.string().max(70),               // titulos de SEO razonables
    description: z.string().max(160),        // meta description
    pubDate: z.coerce.date(),
    updatedDate: z.coerce.date().optional(), // para mostrar "actualizado"
    author: z.string().default('Redaccion'),
    tags: z.array(z.string()).default([]),
    cover: image().optional(),               // imagen validada y optimizada
    coverAlt: z.string().optional(),         // accesibilidad
    draft: z.boolean().default(false),
  }),
});

// Coleccion de autores: permite pagina de autor.
const authors = defineCollection({
  loader: glob({ pattern: '**/*.json', base: './src/content/authors' }),
  schema: z.object({
    name: z.string(),
    bio: z.string(),
    avatar: image().optional(),
  }),
});

export const collections = { blog, authors };

Los helpers de contenido

src/lib/posts.ts
import { getCollection, type CollectionEntry } from 'astro:content';

export type Post = CollectionEntry<'blog'>;

// Publicados, de mas reciente a mas antiguo.
export async function getPosts(): Promise<Post[]> {
  const posts = await getCollection('blog', ({ data }) => !data.draft);
  return posts.sort((a, b) => b.data.pubDate.valueOf() - a.data.pubDate.valueOf());
}

// Un post por su id (slug).
export async function getPostById(id: string): Promise<Post | undefined> {
  const posts = await getPosts();
  return posts.find((p) => p.id === id);
}

// Todos los tags con su numero de posts, ordenados por frecuencia.
export async function getTags(): Promise<{ tag: string; count: number }[]> {
  const posts = await getPosts();
  const counts = new Map<string, number>();
  for (const post of posts) {
    for (const tag of post.data.tags) {
      counts.set(tag, (counts.get(tag) ?? 0) + 1);
    }
  }
  return [...counts.entries()]
    .map(([tag, count]) => ({ tag, count }))
    .sort((a, b) => b.count - a.count);
}

// Posts de un tag concreto.
export async function getPostsByTag(tag: string): Promise<Post[]> {
  const posts = await getPosts();
  return posts.filter((p) => p.data.tags.includes(tag));
}

Decisiones explicadas:

  • El esquema vive aparte del contenido: añadir un campo (por ejemplo updatedDate) obliga a actualizar los posts, y el build avisa si falta. Es el equivalente a una migración de base de datos.
  • Los helpers forman una capa: las páginas piden «posts publicados» o «posts por tag», no saben cómo se obtienen. Cambiar la fuente (un CMS remoto, por ejemplo) no afecta a las páginas.
  • BaseLayout encapsula el SEO: cada página pasa su título y descripción; los metadatos se generan igual en todo el sitio. Consistencia gratis.
  • site configurado: sin él, las URL canónicas y el sitemap salen mal. Es la primera línea de la configuración por una razón.
  • React solo donde hará falta: se instala la integración, pero las islas concretas llegarán en la lección de interactividad.

6 · Errores habituales

Definir las colecciones en el fichero antiguo

✗ Incorrecto

// src/content/config.ts  <- ubicacion de Astro 4, no de Astro 5.
export const collections = { blog };

✓ Correcto

// src/content.config.ts  <- en la raiz de src (Astro 5).
import { defineCollection, z } from 'astro:content';
export const collections = { blog };

En Astro 5 el fichero de colecciones se movió a src/content.config.ts. Si lo pones en el sitio viejo, las colecciones no se registran.

Duplicar la lógica de consulta en cada página

✗ Incorrecto

---
// Un filtro distinto (y facil de olvidar) en cada pagina.
const posts = (await getCollection('blog')).filter((p) => !p.data.draft);
posts.sort((a, b) => b.data.pubDate - a.data.pubDate);
---

✓ Correcto

---
// Una unica fuente de verdad para "posts publicados y ordenados".
import { getPosts } from '../lib/posts';
const posts = await getPosts();
---

La lógica dispersa se desincroniza: un día una página muestra borradores y nadie se entera. Centraliza.

Frontmatter sin validación

✗ Incorrecto

// Esquema vacio: cualquier post con cualquier frontmatter "valida".
schema: z.object({})

✓ Correcto

schema: z.object({
  title: z.string().max(70),
  description: z.string().max(160),
  pubDate: z.coerce.date(),
  tags: z.array(z.string()).default([]),
})

El esquema es la red de seguridad. Sin campos obligatorios, un post sin fecha romperá el orden y el SEO sin avisar en el build.

Hidratar listados que no lo necesitan

✗ Incorrecto

<!-- Un listado de posts no necesita React ni hidratacion. -->
<PostsGrid posts={posts} client:load />

✓ Correcto

<!-- Listado en HTML puro, generado en build. -->
<ul>{posts.map((p) => <li><PostCard post={p} /></li>)}</ul>

<!-- Solo lo interactivo (buscador) es isla. -->
<SearchBox posts={index} client:visible />

Hidratar contenido estático es enviar JavaScript que no sirve para nada: peor rendimiento y peor SEO sin ninguna ganancia.

7 · Ejercicio guiado

Objetivo: montar los cimientos del blog: proyecto, colección con esquema, helpers y portada que lista los posts.

  1. Crea el proyecto e instala las integraciones base: 
    pnpm create astro@latest blog-profesional
cd blog-profesional
pnpm astro add react tailwind
  2. Configura site en astro.config.mjs con una URL absoluta (aunque sea de ejemplo) y las integraciones react y tailwind.
  3. Define la colección en src/content.config.ts con un esquema que incluya title, description, pubDate, tags (con default) y draft (con default).
  4. Crea tres posts en src/content/blog/ (por ejemplo primer-post.md), cada uno con su frontmatter completo. Marca uno como draft: true.
  5. Comprueba la validación: borra la pubDate de un post y ejecuta pnpm build. Debe fallar indicando el post y el campo. Restáurala. Ese fallo controlado es exactamente lo que buscas.
  6. Escribe los helpers src/lib/posts.ts con getPosts y getTags.
  7. Crea la portada src/pages/index.astro que liste los posts publicados (el borrador no debe aparecer) enlazando a /blog/{post.id}.
  8. Verifica el build estático: 
    pnpm build
    Inspecciona dist/: la portada debe ser un index.html con los posts ya dentro. Confirma que el borrador no está en el HTML. Eso demuestra que todo se resolvió en build, sin servidor.

8 · Reto

🎯 Una decisión de arquitectura documentada y una colección nueva

Actúa como el arquitecto del proyecto y resuelve dos cosas:

  • Escribe un ADR breve (registro de decisión de arquitectura, 15 líneas) titulado «Content Collections frente a Markdown en pages». Incluye: el contexto, las opciones que consideraste, la decisión, y las consecuencias (buenas y malas). Un buen ADR reconoce los costes de lo elegido.
  • Añade una segunda colección coherente: authors (autores), projects (proyectos del portfolio) o series (series de artículos). Defínela con su esquema, añade datos de ejemplo, y enlaza el blog con ella (por ejemplo, un post referencia un autor, y la página de autor lista sus posts).
  • Justifica técnicamente: ¿tu colección nueva debería ser content (Markdown/MDX) o data (JSON/YAML)? Razona la respuesta según si el contenido es prosa o estructura.

Pista: para el ADR, la parte más valiosa es la de consecuencias. «Elegimos Content Collections porque validan el frontmatter» es un beneficio; «y aceptamos que añadir un campo obliga a tocar todos los posts» es la consecuencia honesta. Para la segunda colección, piensa primero qué relación tiene con blog: 1-a-muchos (un autor, muchos posts) es el caso más didáctico. Decide el tipo de colección preguntándote si el contenido se lee como prosa (content) o se consume como datos (data).

9 · Resumen

  • Un blog profesional es contenido en colecciones presentado en varias rutas; la arquitectura decide cómo.
  • Las Content Collections separan contenido y presentación y validan el frontmatter con Zod.
  • En Astro 5 las colecciones se definen en src/content.config.ts con la Content Layer (loader).
  • Un blog debe ser estático por defecto; las islas se reservan para búsqueda y formularios.
  • Centralizar las consultas en lib/posts.ts evita duplicar lógica y facilita cambiar la fuente de datos.
  • El site configurado y un Seo.astro reutilizable son cimientos, no extras.

10 · Preguntas frecuentes

¿Content Collections o Markdown en pages/?

Para un blog, Content Collections sin dudarlo. Las páginas Markdown obligan a mezclar contenido y rutas, no validan el frontmatter y hacen incómodo listar todos los posts. Las colecciones cuestan un poco más de configuración inicial y lo devuelven con creces en tipado, validación y consultas. La excepción: páginas sueltas como «Sobre mí» o «Contacto», que perfectamente pueden ser un .astro o un .md sin colección.

¿Por qué no hago todo dinámico con SSR?

Porque el contenido de un blog no depende del usuario. Hacerlo dinámico solo añade coste de servidor por visita, latencia y puntos de fallo, sin ninguna ventaja. El estático con CDN es más rápido, más barato y más seguro. Reserva el SSR para lo que de verdad varía por usuario (auth, paneles, datos en vivo).

¿Necesito el adaptador si el blog es estático?

No, si no hay ninguna ruta dinámica. Generas dist/ y cualquier CDN lo sirve. Solo necesitas adaptador si añades SSR o server islands, por ejemplo para una API de búsqueda on-demand. Recuerda que la búsqueda también puede ser estática (un índice JSON pre-generado) y evitar el adaptador del todo.

¿Cuándo debería empezar a escribir las páginas?

Cuando la columna vertebral —esquema, helpers, layout base— funcione con un post de prueba. Es tentador crear rutas antes de tener claro el modelo de contenido, pero entonces cada cambio de esquema obliga a tocar muchas páginas. Diseña el contenido, valida con un post, y luego multiplica las vistas. Es el orden que seguiremos en las próximas lecciones.

¿Los borradores se sirven en local pero no en producción?

Es una decisión de diseño habitual, y muy útil. Puedes usar import.meta.env.DEV para que el filtro de draft excluya borradores solo en producción: en desarrollo ves todo, en el build publicas solo lo terminado. La clave es tenerlo centralizado en getPosts(), para que la regla sea una sola y no dependa de cada página.
