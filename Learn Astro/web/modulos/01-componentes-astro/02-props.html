Props, tipos y valores por defecto

Módulo 1 · Componentes Astro 🕐 30 minutos

1 · Introducción

Un componente reutilizable no vale nada si no puedes pasarle datos: una tarjeta necesita el título, un botón necesita el texto y el color, un avatar necesita la imagen. Esos datos que van desde quien usa el componente hacia dentro se llaman props (propiedades), y en Astro se leen desde el objeto global Astro.props.

En esta lección aprenderás a declarar props, a tiparlas con TypeScript (interfaz Props), a darles valores por defecto y a distinguir las props normales del contenido que se pasa «por dentro» con slots. Sobre esto último hay un malentendido muy común: quien viene de React busca un prop children; en Astro ese prop no existe y en su lugar se usan slots (que veremos en detalle en la lección siguiente).

🎯 Por qué existe esta lección

Porque unas props bien tipadas son la diferencia entre un componente que se puede reutilizar con confianza y uno que se rompe cada vez que alguien cambia una llamada. TypeScript en Astro no es decoración: el editor te avisa antes de ejecutar si te falta un dato o le pasas algo del tipo equivocado.

2 · Teoría

Qué es Astro.props

Cuando usas un componente con atributos, Astro los recoge en un objeto y lo pone a tu disposición como Astro.props dentro del frontmatter. Es, literalmente, un objeto con los atributos que te han pasado:

Cómo fluyen las props
<!-- Quien USA el componente pasa atributos… -->
<Badge texto="Nuevo" color="verde" />

<!-- …que dentro del componente llegan así: -->
---
const { texto, color } = Astro.props;
// Astro.props = { texto: 'Nuevo', color: 'verde' }
---
<span class={`badge badge--${color}`}>{texto}</span>

La forma habitual es desestructurar Astro.props en el frontmatter: obtienes las variables de golpe y el resto del componente las ve. Pero recuerda que todo esto ocurre en el servidor: no hay re-render, no hay observación de cambios. Las props llegan, se usan y se convierten en HTML.

📌 Props estáticas, de una sola dirección

En Astro las props se resuelven en el render, una vez. A diferencia de React, no existe el flujo «estado → re-render → nuevas props» en el navegador. Si necesitas algo que cambie tras un clic, eso es una isla (Módulo 4), no una prop.

Tipar las props con la interfaz Props

Astro tiene una convención (no magia): si declaras una interfaz llamada Props en el frontmatter, Astro la usa para validar y dar autocompletado a tus props. Es la recomendación oficial y la usaremos siempre.

src/components/Button.astro
---
// El nombre exacto "Props" es lo que Astro detecta para tipar.
interface Props {
  label: string;                 // obligatoria
  variant?: 'primary' | 'ghost'; // opcional (el ? lo indica)
  disabled?: boolean;
}

const { label, variant = 'primary', disabled = false } = Astro.props;
---

<button class={`btn btn--${variant}`} disabled={disabled}>
  {label}
</button>

Beneficios concretos del tipado:

  • Autocompletado: al escribir <Button en otro archivo, el editor te sugiere label, variant…
  • Errores tempranos: si omites label o pones variant="azul" cuando solo se permite 'primary' | 'ghost', el editor y pnpm astro check te lo señalan.
  • Documentación viva: la interfaz es la documentación de qué acepta el componente.
  • Uniones de literales: 'primary' | 'ghost' restringe los valores válidos; mucho mejor que un string cualquiera.

Valores por defecto

Se aplican al desestructurar: si la propiedad llega undefined, se usa el valor por defecto. Es el mismo mecanismo que en JavaScript moderno, y es la forma idiomática en Astro.

Valores por defecto al desestructurar
---
interface Props {
  title: string;
  subtitle?: string;
  featured?: boolean;
  tags?: string[];
}
// "=" define el fallback cuando la prop no se pasa o es undefined.
const {
  title,
  subtitle = 'Sin subtítulo',
  featured = false,
  tags = [],
} = Astro.props;
---

⚠️ Los valores por defecto solo actúan sobre undefined

Si alguien pasa tags={null}, el valor por defecto no se aplica (porque null no es undefined). Con TypeScript estricto, además, tipar tags?: string[] impide pasar null. Es una razón más para tipar las props.

Props frente a slots: el mito de children

En React, todo lo que pones entre las etiquetas de un componente llega como un prop especial llamado children. En Astro no existe ese prop: el contenido interior se inserta con un slot. Es una decisión de diseño coherente: Astro es HTML primero, y en HTML el contenido anidado es la forma natural de pasar marcado.

NecesidadEn ReactEn Astro
Pasar datos (texto, números, opciones)propsprops (Astro.props)
Pasar HTML o componentes anidadosprop children<slot />
Varios huecos de contenidoprops de render / composiciónslots con nombre (slot="x")
Slot: el «children» de Astro
<!-- Card.astro -->
<div class="card">
  <slot />  <!-- aquí entra el contenido que se anida al usarlo -->
</div>

<!-- Uso: el contenido entre etiquetas viaja al slot -->
<Card>
  <h2>Hola</h2>
  <p>Esto es el contenido anidado.</p>
</Card>

La lección siguiente está dedicada a los slots (simples, con nombre y con fallback). Aquí solo queremos que te quede claro: datos → props; marcado → slots. Si intentas pasar HTML por una prop, casi siempre estás usando mal la herramienta.

Un caso especial: props en componentes de framework

Cuando usas React como isla, ese componente sí tiene children, porque sigue las reglas de React. Es decir: el «prop children» existe en el mundo React, no en Astro. Distinguir el mundo de cada componente evita más de un dolor de cabeza.

Isla React: aquí sí hay children
// Widget.tsx — componente REACT (no Astro)
type Props = { children: React.ReactNode };
export default function Widget({ children }: Props) {
  return <div className="widget">{children}</div>;
}

3 · Ejemplo mínimo

El componente más simple que recibe una prop tipada y le da valor por defecto.

src/components/Greeting.astro
---
// Definimos el "contrato" del componente.
interface Props {
  name: string;
  greeting?: string; // opcional: puede no venir
}
// greeting tiene valor por defecto "Hola"; name es obligatorio.
const { greeting = 'Hola', name } = Astro.props;
---
<p>{greeting}, {name}!</p>

Usos válidos y su resultado:

src/pages/index.astro
---
import Greeting from '../components/Greeting.astro';
---
<Greeting name="Ana" />                     <!-- Hola, Ana! -->
<Greeting name="Luis" greeting="Buenas" />  <!-- Buenas, Luis! -->
<!-- Si omitiéramos name, TypeScript avisaría: falta una prop obligatoria. -->

Línea por línea, lo esencial:

  • interface Props: el nombre exacto que Astro reconoce para tipar.
  • greeting?: el signo de interrogación indica opcional; puede llegar undefined.
  • greeting = 'Hola': el valor de reserva cuando no se pasa.
  • name: sin ? ni valor por defecto, es obligatorio; si falta, error de tipos.

4 · Ejemplo real

Un componente de badge de estado, del tipo que aparece en cualquier panel: recibe un estado, deriva un color, permite personalizar texto y puede no tener contenido (usa un slot con fallback). Es un buen ejemplo porque combina props tipadas y slot en un solo componente.

src/components/StatusBadge.astro
---
// Unión de literales: solo estos estados son válidos.
type Estado = 'activo' | 'pausado' | 'error';

interface Props {
  estado: Estado;
  label?: string;     // texto opcional; si no viene, se usa el estado
  size?: 'sm' | 'md';
}

const { estado, label, size = 'md' } = Astro.props;

// Mapa de estado → color. Vive en el servidor y se resuelve una vez.
const colores: Record<Estado, string> = {
  activo: '#16a34a',
  pausado: '#d97706',
  error: '#dc2626',
};
const color = colores[estado];
---

<span class={`badge badge--${size}`} style={`--dot:${color}`}>
  <span class="badge__dot"></span>
  <!-- Fallback del slot: si no se pasa contenido, muestra label o estado -->
  <slot>{label ?? estado}</slot>
</span>

<style>
  .badge { display: inline-flex; align-items: center; gap: 6px; }
  .badge__dot {
    width: 10px; height: 10px; border-radius: 50%;
    background: var(--dot); /* variable CSS inyectada por style= */
  }
  .badge--sm { font-size: 0.8rem; }
</style>

Usos realistas, incluidos los casos raros:

src/pages/panel.astro
---
import StatusBadge from '../components/StatusBadge.astro';
---
<StatusBadge estado="activo" />
<!-- muestra el dot verde y el texto "activo" (fallback) -->

<StatusBadge estado="error" label="Fallo de conexión" size="sm" />
<!-- dot rojo, texto personalizado, tamaño pequeño -->

<StatusBadge estado="pausado">En mantenimiento</StatusBadge>
<!-- contenido anidado: el slot lo pinta y el fallback no se usa -->

Decisiones y por qué:

  • type Estado + Record<Estado, string> garantiza que el mapa cubre todos los estados: si añades uno nuevo, TypeScript te obliga a añadir su color.
  • label ?? estado: el operador ?? usa el estado como texto si no hay label (solo si es undefined/null).
  • El slot con fallback convierte el componente en flexible: sirve con texto automático o con contenido HTML a medida.
  • style con variable CSS: pasamos el color como variable; es una forma limpia de parametrizar estilos desde props sin escribir CSS inline por todas partes.

📋 Analogía: el formulario de un trámite

La interfaz Props es el formulario oficial de tu componente: dice qué campos son obligatorios (sin ?), cuáles opcionales (con ?) y qué valores se admiten (las uniones). El valor por defecto es lo que pone la ventanilla si dejas el campo en blanco. Y el slot es el anexo donde adjuntas documentos libres.

5 · Buenas prácticas

Qué hacerQué evitarPor qué
Declarar siempre interface Props Usar Astro.props sin tipos El tipado da autocompletado y errores antes de ejecutar; documenta el componente
Marcar opcional (?) lo que puede faltar y darle valor por defecto Convertir todo en opcional «para que no falle» Si todo es opcional, el componente puede acabar mostrando huecos; el contrato pierde sentido

6 · Errores habituales

1. Buscar el prop children que no existe

Mal — mentalidad React aplicada a Astro 
---
// ❌ children NO existe en Astro: siempre será undefined.
const { children } = Astro.props;
---
<div>{children}</div>
Bien — slot para el contenido anidado 
<div>
  <slot />  <!-- ✅ aquí llega el contenido que se anida al usar el componente -->
</div>

Lo que en React es children, en Astro es un <slot />. No es un capricho: es que Astro es HTML primero y el contenido anidado ya es la forma natural de pasar marcado.

2. Dar por hecho que el valor por defecto cubre null

Mal — pasar null salta el valor por defecto 
<Card title={null} />
<!-- El componente: const { title = 'Sin título' } = Astro.props;
     ❌ title llega null, no undefined; el fallback NO se aplica. -->
Bien — tipar para impedir null y omitir la prop si no hay valor 
---
interface Props { title?: string; } // string | undefined, nunca null
const { title = 'Sin título' } = Astro.props;
---
<!-- Uso correcto: se omite title en lugar de pasar null -->
<Card /> <!-- ✅ title es undefined → se aplica 'Sin título' -->

3. Confundir atributos HTML nativos con props

Mal — esperar que cualquier atributo sea una prop 
<Button data-testid="cta" aria-label="Enviar" />
<!-- ❌ Si la interfaz Props no los declara, TS los marca como error
     …a menos que se propaguen al HTML. Hay que decidirlo a conciencia. -->
Bien — extender los atributos nativos del elemento 
---
// HTMLAttributes permite pasar class, id, aria-*, data-*… al elemento real.
interface Props extends astroHTML.JSX.ButtonHTMLAttributes {
  label: string;
  variant?: 'primary' | 'ghost';
}
const { label, variant = 'primary', ...rest } = Astro.props;
---
<button class={`btn btn--${variant}`} {...rest}>{label}</button>
<!-- ✅ aria-label, data-*, disabled… viajan al <button> real. -->

7 · Ejercicio guiado

Objetivo: crear un componente Precio.astro bien tipado, con valores por defecto y con un slot para contenido adicional, y usarlo desde una página con varios casos.

  1. Paso 1 — diseña el contrato. El componente recibe amount (número, obligatorio), currency (opcional, por defecto 'EUR') y highlight (booleano, por defecto false). Escribe la interface Props con esos tipos.
  2. Paso 2 — formatea en el servidor. Usa Intl.NumberFormat('es-ES', { style: 'currency', currency }) en el frontmatter para obtener el precio formateado. Es cálculo de servidor, no del navegador.
  3. Paso 3 — pinta con clases condicionales. En el template, aplica una clase extra si highlight es verdadero usando una plantilla de texto o class:list.
  4. Paso 4 — añade un slot con fallback. Coloca un <slot>...</slot> que muestre «IVA incluido» por defecto y permita sustituirlo.
  5. Paso 5 — úsalo en tres variantes. En la página, pásale solo amount; luego con currency="USD" y highlight; luego con contenido anidado propio.
  6. Paso 6 — rompe el contrato a propósito. Intenta usar <Precio /> sin amount y comprueba que tu editor/CLI avisa del error. Luego arréglalo.

Solución paso a paso.

src/components/Precio.astro
---
interface Props {
  amount: number;                 // obligatorio
  currency?: string;              // opcional
  highlight?: boolean;            // opcional
}
const { amount, currency = 'EUR', highlight = false } = Astro.props;

// Formateo en el servidor: el navegador recibe el texto ya resuelto.
const format = new Intl.NumberFormat('es-ES', { style: 'currency', currency });
const text = format.format(amount);
---
<p class:list={['precio', { 'precio--destacado': highlight }]}>
  {text}
  <!-- Fallback: si nadie anida contenido, se muestra el aviso por defecto. -->
  <slot><small>IVA incluido</small></slot>
</p>
src/pages/tienda.astro
---
import Precio from '../components/Precio.astro';
---
<Precio amount={1999} />
<Precio amount={29.9} currency="USD" highlight />
<Precio amount={9.99}><small>¡Oferta del día!</small></Precio>

✅ Resultado esperado

Tres precios formateados correctamente, el segundo destacado, y solo el tercero sustituye el texto «IVA incluido» por el suyo. Al quitar amount, el editor (o pnpm astro check) debe marcar un error de tipo: ese es el contrato funcionando.

8 · Reto

🎯 Un componente «con todas las letras»

Diseña un componente Avatar.astro que combine props tipadas y un slot: recibe src (imagen), alt, un size restringido a 'xs' | 'sm' | 'md' | 'lg', un status opcional ('online' | 'offline' | 'busy') que pinte un puntito de color, y un slot que permita añadir contenido junto al nombre (por ejemplo, una etiqueta «Admin»). Además, haz que el componente propague atributos HTML nativos (title, data-*, aria-*) al elemento raíz usando ...rest.

Pista: para el status necesitas una unión de literales y un mapa a colores, como en el ejemplo de StatusBadge. Para propagar atributos, extiende astroHTML.JSX.HTMLAttributes y desestructura ...rest. Pregúntate: ¿qué pasa si alguien pasa un size inválido? ¿Lo atrapa TypeScript o necesitas validación en runtime? Razónalo antes de mirar el Módulo 6.

9 · Resumen

  • Las props llegan al componente en Astro.props, que se desestructura en el frontmatter.
  • Declarar interface Props da tipado, autocompletado y errores tempranos; es la convención oficial.
  • Los valores por defecto se aplican al desestructurar y solo cubren undefined.
  • Las uniones de literales ('sm' | 'md') restringen las variantes válidas.
  • En Astro no hay prop children: el contenido anidado se inserta con <slot />. El prop children sí existe, pero en componentes de framework (React) usados como islas.
  • Datos → props; marcado → slots. Esa es la regla que gobierna la composición en Astro.

10 · Preguntas frecuentes

¿Es obligatorio llamar Props a la interfaz?

Es la convención que Astro reconoce para tipar automáticamente las props: si declaras interface Props en el frontmatter, Astro la usa. Puedes exportarla o renombrarla en otros contextos, pero para el tipado automático de un componente, usa exactamente Props.

¿Puedo pasar una función como prop?

Técnicamente sí (es JavaScript), pero casi nunca tiene sentido en un componente .astro, porque no hay runtime en el cliente donde llamarla: la función se ejecutaría en el servidor. Las funciones y los callbacks pertenecen a las islas de framework, que sí viven y ejecutan en el navegador (Módulo 4).

¿Cómo hago una prop «opcional pero obligatoria si se cumple X»?

Se modela con uniones discriminadas en TypeScript. Por ejemplo, un componente que o tiene href o tiene onClick, pero no ambos ni ninguno. Es unión de tipos ({ href: string } | { onClick: () => void }) y TypeScript lo comprueba solo. Es un patrón profesional muy común; lo usaremos cuando aparezcan casos reales.

¿Los valores por defecto funcionan con arrays y objetos?

Sí, pero cuidado con la mutación. Asignar tags = [] crea un array nuevo cada render (bien). Si en cambio pones un array/objeto compartido en el ámbito del módulo y lo mutas, puedes arrastrar estado entre renders. Regla: los valores por defecto de tipos compuestos se escriben inline (= [], = {}) para que sean frescos.

¿Puedo pasar HTML por una prop en lugar de usar un slot?

Se puede con set:html, pero es la excepción y conlleva riesgo de inyección de HTML si el contenido no es de confianza. Para estructura y marcado, usa slots: son la vía segura, idiomática y auto-escapan. Reserva set:html para contenido que tú controlas por completo (por ejemplo, HTML de un Markdown ya procesado).
