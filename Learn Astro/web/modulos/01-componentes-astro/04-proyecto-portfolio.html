Proyecto: portfolio con componentes

Módulo 1 · Componentes Astro 🕐 45 minutos

1 · Introducción

Es hora de unir todo lo aprendido en el módulo. En este proyecto construirás un portfolio personal hecho solo con componentes .astro: un layout base, una cabecera, un pie, una tarjeta de proyecto reutilizable y su sección contenedora. Nada de JavaScript de cliente: la gracia es demostrar cuánto se puede lograr con HTML, props y slots bien usados.

El objetivo no es solo que la web se vea bien, sino que su arquitectura sea la correcta: cada pieza con una sola responsabilidad, las props tipadas con TypeScript y los slots usados para el marcado flexible. Es el mismo patrón que repetirás en todos los proyectos del curso, así que hazlo con calma.

🎯 Por qué existe esta lección

Porque leer sobre componentes no es lo mismo que componerlos. Este proyecto te obliga a decidir dónde va cada dato, cuándo usar props y cuándo un slot, y a encadenar un layout con sus secciones. Es la prueba práctica de que el Módulo 1 ha calado.

📌 Requisitos de partida

Necesitas un proyecto Astro funcionando (Módulo 0) con TypeScript estricto. Para los avatares e imágenes usarás imports desde src/assets/. Si no tienes imágenes, puedes usar un SVG de marcador de posición o una URL externa; el proyecto funciona igual.

2 · Teoría

Qué vas a construir

Un portfolio de una sola página de inicio con estas piezas, todas componentes .astro:

src/
├── layouts/
│   └── BaseLayout.astro     ← esqueleto: <head>, header, slot, footer
├── components/
│   ├── Header.astro         ← cabecera con navegación
│   ├── Footer.astro         ← pie con año y redes
│   ├── Section.astro        ← sección con título + slot (reutilizable)
│   ├── ProjectCard.astro    ← tarjeta de un proyecto (props tipadas)
│   ├── Hero.astro           ← presentación personal
│   └── SkillList.astro      ← lista de habilidades (render de array)
└── pages/
    └── index.astro          ← compone todas las piezas

Árbol de composición en la página:
  BaseLayout
   ├── Header
   ├── Hero
   ├── Section ("Proyectos")
   │    └── ProjectCard × N
   ├── Section ("Habilidades")
   │    └── SkillList
   └── Footer

Las tres decisiones de diseño

Antes de escribir código, conviene razonar las reglas que seguirás (y por qué):

DecisiónReglaPor qué
¿Dónde va la estructura común? En un layout (BaseLayout) con un <slot /> El <head>, la cabecera y el pie se escriben una sola vez
¿Props o slot? Datos → props; marcado → slot El título de una tarjeta es una prop; su descripción enriquecida puede ser un slot
¿Cómo recorro listas? map() en el frontmatter o en el template El HTML se genera en el servidor; no hay runtime que actualice la lista

El orden de construcción importa

Construiremos de fuera hacia dentro: primero el layout (el andamio), luego las piezas básicas (Header, Footer), después las de contenido (Section, ProjectCard, Hero, SkillList) y, por último, la página que las une. Este orden evita el clásico «import no encontrado» que aparece si construyes la página antes que sus componentes.

🏗️ Analogía: montar un mueble

Primero la estructura (las piezas grandes del esqueleto), luego los cajones y puertas (componentes), y al final el montaje (la página). Si empiezas por la decoración sin tener el armazón, acabas con piezas sueltas sin sitio. Y una vez montado, cambiar la puerta de un cajón (el componente) la cambia en todas las copias.

3 · Ejemplo mínimo

Antes del proyecto completo, el «mínimo viable» de composición: dos componentes y una página. Fíjate en el esqueleto de layout + slot + página, porque ese es el patrón que replicarás a lo grande.

src/layouts/BaseLayout.astro
---
// Layout mínimo: el <head> y el <slot /> donde encaja cada página.
---
<!DOCTYPE html>
<html lang="es">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Mi portfolio</title>
  </head>
  <body>
    <slot />  <!-- aquí entra el contenido de cada página -->
  </body>
</html>

---
interface Props {
  title: string;
  url: string;
}
const { title, url } = Astro.props;
---
<a class="card" href={url}>
  <h3>{title}</h3>
</a>
src/pages/index.astro
---

import ProjectCard from '../components/ProjectCard.astro';
---

  <h1>Mis proyectos</h1>
  <ProjectCard title="Tienda online" url="https://ejemplo.dev" />

Con esto ya tienes el patrón: layout → slot → página → componente con props. Todo lo demás del proyecto es refinar y multiplicar esta idea.

Ahora las piezas de contenido. El Section es un componente reutilizable que combina una prop (id) con un slot (el contenido):

src/components/Section.astro
---
interface Props {
  id: string;        // ancla para la navegación
  title: string;
  subtitle?: string;
}
const { id, title, subtitle } = Astro.props;
---
<section id={id} class="section">
  <h2>{title}</h2>
  {subtitle && <p class="section__subtitle">{subtitle}</p>}
  <!-- El contenido de la sección se pasa por slot -->
  <slot />
</section>

<style>

  .section__subtitle { color: #666; }
</style>

Y por último, la página que lo une todo. Aquí se ve la composición real: el layout envuelve, las secciones agrupan y las tarjetas se generan con map().

import Section from '../components/Section.astro';
import ProjectCard from '../components/ProjectCard.astro';

// Datos del portfolio. En el Módulo 3 esto vendrá de Content Collections.
const proyectos = [
  {
    title: 'Tienda online',
    description: 'E-commerce con carrito y checkout.',
    url: 'https://ejemplo.dev/tienda',
    tags: ['Astro', 'Stripe', 'Tailwind'],
  },
  {
    title: 'App de notas',
    description: 'Notas con Markdown y sincronización.',
    url: 'https://ejemplo.dev/notas',
    tags: ['Astro', 'TypeScript'],
  },
];
---
<BaseLayout title="Ana Torres — Portfolio">
  <!-- Hero: presentación -->
  <header class="hero">
    <h1>Ana Torres</h1>
    <p>Desarrolladora frontend. Construyo webs rápidas con Astro.</p>
  </header>

  <!-- Sección de proyectos: una tarjeta por proyecto -->
  <Section id="proyectos" title="Proyectos" subtitle="Una selección de mi trabajo">
    {proyectos.map((p) => (
      <ProjectCard
        title={p.title}
        description={p.description}
        url={p.url}
        tags={p.tags}
      />
    ))}
  </Section>

  <!-- Sección de contacto -->
  <Section id="contacto" title="Contacto">
    <p>Escríbeme a <a href="mailto:hola@ejemplo.dev">hola@ejemplo.dev</a></p>
  </Section>
</BaseLayout>

Decisiones y por qué:

  • Un solo layout con <slot />: el <head> y la estructura se definen una vez.
  • Título sobrescribible como prop con valor por defecto: cada página puede personalizarlo.
  • Section con prop id y slot: reutilizable en toda la web; el contenido concreto lo pone quien la usa.
  • ProjectCard con tags opcional y valor por defecto []: si no hay etiquetas, no se pinta la lista (tags.length > 0).
  • Los datos viven en el frontmatter, no en el cliente: cero JavaScript, cero hydration.

💡 DevTools: comprueba la promesa

Abre la página y pulsa «Ver código fuente». Verás el HTML de las tarjetas, los <li> de las etiquetas y el año del pie: todo generado en el servidor. En la pestaña Network no hay bundles de framework. Ese es el portfolio de un proyecto Astro bien hecho.

5 · Buenas prácticas

Qué hacerQué evitarPor qué
Tipar cada componente con su interface Props Componentes sin contrato, con props «a ver qué llega» El proyecto crece; el tipado evita que una tarjeta se rompa al cambiar su uso
Un componente = una responsabilidad Un index.astro con todo el HTML dentro Componer facilita reutilizar, cambiar y entender; el monolito es una trampa
Datos en el frontmatter y map() para las listas Duplicar HTML a mano por cada proyecto Duplicar datos garantiza inconsistencias; una lista + un map es una sola fuente
Valores por defecto en props opcionales (tags = []) Suponer que siempre llegan todas las props Los componentes robustos no fallan cuando falta un dato opcional
Estilos con scope dentro de cada componente Un CSS global gigante que toca todo El scope evita colisiones y mantiene el estilo junto a su componente

6 · Errores habituales

1. Construir la página antes que los componentes

Mal — el import apunta a un archivo que aún no existe 
---
import ProjectCard from '../components/ProjectCard.astro';
// ❌ Si el archivo no existe todavía, el dev server falla:
//    "Failed to resolve import ... ProjectCard.astro"
---
Bien — de fuera hacia dentro 
1. layouts/BaseLayout.astro
2. components/Header.astro, Footer.astro
3. components/Section.astro, ProjectCard.astro
4. pages/index.astro   ← este último, cuando ya todo existe

2. Duplicar HTML en lugar de recorrer con map()

Mal — cada proyecto copia y pega el bloque 
<article class="project"><h3><a href="/a">Tienda</a></h3><p>E-commerce</p></article>
<article class="project"><h3><a href="/b">Notas</a></h3><p>Notas</p></article>
<!-- ❌ cambiar el diseño obliga a editar cada bloque; se desincronizan. -->
Bien — una lista de datos y un map 
{proyectos.map((p) => (
  <ProjectCard title={p.title} description={p.description} url={p.url} />
))}
<!-- ✅ el diseño vive en ProjectCard; la lista, en los datos. -->

3. Usar el slot para lo que era una prop

Mal — texto simple por slot cuando es un dato 
<Section id="x">
  <h2>Proyectos</h2> <!-- ❌ el título duplica el rol del componente -->
  <p>…</p>
</Section>
<!-- Si el título es un dato, debería ser una PROP, no marcado. -->
Bien — datos por props, marcado por slot 
<Section id="proyectos" title="Proyectos" subtitle="Mi trabajo">
  <!-- ✅ título y subtítulo son props; aquí solo va el marcado propio -->
  {proyectos.map((p) => <ProjectCard ... />)}
</Section>

8 · Reto

🎯 Portfolio multi-página con layout anidado

Amplía el portfolio de una sola página a tres páginas (/, /proyectos, /sobre-mi) usando el routing por sistema de archivos. Crea además un layout anidado: un MarketingLayout que derive de BaseLayout y añada su propia barra de sección, reenviando los slots con name + slot. Muévete entre páginas verificando que comparten cabecera y pie. Documenta en un comentario por qué has puesto el CSS global donde lo pusiste.

Pista: para el layout anidado, recuerda que el intermedio debe reenviar los slots explícitamente (lección 3). Y para el enrutado, un archivo por ruta en src/pages/. Pregúntate: si dos páginas comparten una sección, ¿qué reutilizas, el layout o un componente Section? Hay una respuesta mejor que la otra según si la sección cambia de contenido o de posición.

9 · Resumen

  • Un portfolio completo se compone con layout + componentes + props + slots, sin JavaScript de cliente.
  • El layout concentra la estructura común y cede el contenido con <slot />; el título es una prop opcional con valor por defecto.
  • Los componentes de contenido (Section, ProjectCard) son reutilizables y tipados; los datos viven en el frontmatter.
  • Las listas se generan con map(); nunca se duplica HTML a mano.
  • Se verifica con pnpm astro check (tipos) y pnpm build + pnpm preview (producción).
  • Regla que se repite en todos los proyectos: datos → props, marcado → slots, lógica → servidor.

10 · Preguntas frecuentes

¿Los datos del portfolio deberían estar en un archivo aparte?

Para este tamaño, tenerlos en el frontmatter de la página está bien. Cuando crezcan (o quieras editarlos sin tocar el HTML), el paso natural es un archivo .json/.ts en src/data/ y, más adelante, Content Collections con esquemas Zod (Módulo 3), que además te dan tipado y validación del contenido.

¿Cómo hago que el portfolio se vea bien en móvil sin framework CSS?

Con CSS moderno y un diseño responsivo básico: max-width en el contenedor, flex-wrap para las rejillas y clamp() para tipografías fluidas. En el Módulo 6 añadirás Tailwind, pero no es obligatorio: Astro funciona perfectamente con CSS propio. La ventaja de no usar framework es que envías exactamente el CSS que necesitas.

¿Debería añadir un <script> para el menú móvil?

Solo si de verdad lo necesitas: un menú desplegable sí requiere interactividad y sería un buen candidato a un pequeño <script> (o a una isla, si se complica). Pero pregúntate primero si puedes resolverlo con HTML/CSS puro (por ejemplo, un <details> o un checkbox). Cada script que evites es peso y complejidad que te ahorras.

¿Cómo organizo los estilos: global o por componente?

Regla práctica: global para lo verdaderamente transversal (reset, variables de color, tipografía base) y con scope para todo lo que pertenece a un componente concreto. Así evitas un CSS global inmanejable y "fugas" de estilo. En el proyecto, global.css se importa una vez en el layout; cada componente lleva lo suyo en su <style>.

¿Puedo reutilizar este portfolio como plantilla para otros proyectos?

Sí, y de hecho es una buena idea: el patrón layout + componentes + slots se repite en casi toda web de contenido. Copia la estructura, sustituye los componentes de contenido por los tuyos y ajusta los estilos. La arquitectura no cambia; solo cambia el contenido, que es exactamente la ventaja de haberlo hecho con componentes.
