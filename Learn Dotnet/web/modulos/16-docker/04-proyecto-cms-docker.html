Proyecto CMS: Docker Compose + CI/CD

Módulo 16 · Docker y despliegue50 min

1. Introducción

En este proyecto integraremos todo lo aprendido en el módulo para contenerizar y automatizar el despliegue del CMS que venimos construyendo. Crearemos un Dockerfile optimizado para el proyecto Cms.Api, un docker-compose.yml que incluye PostgreSQL, Redis y la API, y un workflow de GitHub Actions que compile, testee y publique la imagen Docker.

Al finalizar tendrás un CMS que puedes levantar en cualquier máquina con Docker, con una pipeline que verifica automáticamente cada cambio.

Objetivo del proyecto: empaquetar el CMS como una imagen Docker, orquestarla con PostgreSQL y Redis mediante Docker Compose, y configurar CI/CD básico para que cada push a main publique una nueva imagen.

2. Teoría

Arquitectura del CMS en contenedores

El CMS está organizado en cuatro capas: Domain, Application, Infrastructure y Api. Docker se encarga de la capa de presentación y despliegue, sin modificar la lógica de negocio.

Consideraciones de producción

En desarrollo usamos Docker Compose para levantar todo rápidamente. En producción, las opciones más comunes para una aplicación .NET containerizada son:

  • Railway: plataforma sencilla que detecta el Dockerfile y despliega automáticamente. Ideal para proyectos personales y MVPs.
  • Azure Container Apps: servicio gestionado de Microsoft con autoescalado, revisiones y secretos integrados. Muy adecuado para .NET.
  • AWS ECS / Fargate: orquestación de contenedores sin servidor de Amazon. Requiere más configuración pero ofrece gran flexibilidad.
  • Kubernetes (AKS, EKS, GKE): para aplicaciones grandes que necesitan alta disponibilidad, múltiples réplicas y pipelines complejas.

Imagen final vs desarrollo

El mismo Dockerfile sirve para desarrollo y producción. La diferencia está en los valores de configuración inyectados mediante variables de entorno y en el entorno ASP.NET Core (Development, Docker, Production).

Orden de despliegue seguro

En producción nunca debe ejecutarse dotnet ef database update automáticamente al arrancar la API. El despliegue correcto aplica primero las migraciones de forma controlada y luego arranca la nueva versión de la aplicación. En desarrollo con Docker Compose podemos usar un contenedor de inicialización o ejecutar el comando manualmente.

3. Ejemplo mínimo

El núcleo del proyecto es el Dockerfile del CMS. Empezamos con la versión mínima multi-stage.

# proyecto-final/src/Cms.Api/Dockerfile

# Etapa de build
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

COPY src/Cms.Api/Cms.Api.csproj Cms.Api/
COPY src/Cms.Application/Cms.Application.csproj Cms.Application/
COPY src/Cms.Domain/Cms.Domain.csproj Cms.Domain/
COPY src/Cms.Infrastructure/Cms.Infrastructure.csproj Cms.Infrastructure/

RUN dotnet restore Cms.Api/Cms.Api.csproj

COPY src/Cms.Api/ Cms.Api/
COPY src/Cms.Application/ Cms.Application/
COPY src/Cms.Domain/ Cms.Domain/
COPY src/Cms.Infrastructure/ Cms.Infrastructure/

RUN dotnet publish Cms.Api/Cms.Api.csproj \
    -c Release \
    -o /app/publish \
    --no-restore

# Etapa de runtime
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
EXPOSE 8080
USER app
ENTRYPOINT ["dotnet", "Cms.Api.dll"]

# proyecto-final/docker-compose.yml
# Orquesta la API del CMS con PostgreSQL y Redis.

services:
  cms-api:
    build:
      context: .
      dockerfile: src/Cms.Api/Dockerfile
    container_name: cms-api
    ports:
      - "8080:8080"
    environment:
      - ASPNETCORE_ENVIRONMENT=Docker
      - ConnectionStrings__Cms=Host=postgres;Port=5432;Database=cms;Username=postgres;Password=${POSTGRES_PASSWORD:-postgres}
      - ConnectionStrings__Redis=redis:6379
      - Jwt__Issuer=${JWT_ISSUER:-CmsApi}
      - Jwt__Audience=${JWT_AUDIENCE:-CmsClient}
      - Jwt__Key=${JWT_KEY:-EstaEsUnaClaveSuperSecretaDe32Caracteres!}
      - Serilog__MinimumLevel__Default=Information
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    networks:
      - cms-network
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 60s

  postgres:
    image: postgres:16-alpine
    container_name: cms-postgres
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD:-postgres}
      - POSTGRES_DB=cms
    ports:
      - "5432:5432"
    volumes:
      - cms-postgres-data:/var/lib/postgresql/data
    networks:
      - cms-network
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d cms"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s

  redis:
    image: redis:7-alpine
    container_name: cms-redis
    ports:
      - "6379:6379"
    volumes:
      - cms-redis-data:/data
    networks:
      - cms-network
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 5s

volumes:
  cms-postgres-data:
  cms-redis-data:

networks:
  cms-network:
    driver: bridge

  },
  "Serilog": {

      "Default": "Information"
    },
    "WriteTo": [
      { "Name": "Console" }
    ]
  },

}
// Program.cs (fragmentos relevantes para Docker)
// Configuración de EF Core con PostgreSQL
builder.Services.AddDbContext<CmsDbContext>(options =>
    options.UseNpgsql(
        builder.Configuration.GetConnectionString("Cms"),
        b => b.MigrationsAssembly("Cms.Infrastructure")));

// Caché distribuida con Redis
builder.Services.AddStackExchangeRedisCache(options =>
    options.Configuration = builder.Configuration.GetConnectionString("Redis"));

// Healthchecks para PostgreSQL y Redis
builder.Services.AddHealthChecks()
    .AddNpgSql(builder.Configuration.GetConnectionString("Cms")!)
    .AddRedis(builder.Configuration.GetConnectionString("Redis")!);

var app = builder.Build();

app.MapHealthChecks("/health");
app.MapControllers();
app.Run();
# .github/workflows/cms-deploy.yml
# CI/CD del CMS: build, test, Docker build/push y despliegue.

name: CMS CI/CD

on:
  push:
    branches: [main]
    paths:
      - 'proyecto-final/**'
  pull_request:
    branches: [main]
    paths:
      - 'proyecto-final/**'

env:
  DOTNET_VERSION: '8.0.x'
  IMAGE_NAME: ${{ secrets.DOCKER_USERNAME }}/cms-api

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./proyecto-final

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Cache NuGet
        uses: actions/cache@v4
        with:
          path: ~/.nuget/packages
          key: ${{ runner.os }}-nuget-${{ hashFiles('proyecto-final/**/*.csproj') }}
          restore-keys: |
            ${{ runner.os }}-nuget-

      - name: Restore
        run: dotnet restore src/Cms.sln

      - name: Build
        run: dotnet build src/Cms.sln --no-restore --configuration Release

      - name: Test
        run: dotnet test src/Cms.sln --no-build --verbosity normal

      - name: Publish
        run: dotnet publish src/Cms.Api/Cms.Api.csproj --no-build --configuration Release --output ./publish

      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: cms-api-publish
          path: ./proyecto-final/publish
          retention-days: 5

  docker-build:
    needs: build-and-test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Docker meta
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=main-
            type=raw,value=main

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: ./proyecto-final
          file: ./proyecto-final/src/Cms.Api/Dockerfile
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy-railway:
    needs: docker-build
    runs-on: ubuntu-latest
    environment: production
    if: github.ref == 'refs/heads/main'

    steps:
      - name: Deploy to Railway
        run: echo "Aquí se conecta el CLI de Railway con RAILWAY_TOKEN"
        env:
          RAILWAY_TOKEN: ${{ secrets.RAILWAY_TOKEN }}

5. Buenas prácticas

  • Mantén el Dockerfile cerca del proyecto de entrada. En nuestro caso está en src/Cms.Api/Dockerfile y el contexto de build es la raíz de proyecto-final.
  • Usa un .dockerignore exhaustivo. Excluye tests, documentación, configuración local y carpetas de compilación.
  • Define un appsettings.Docker.json para valores por defecto seguros en contenedores.
  • Configura variables de entorno en el docker-compose.yml y usa .env para secretos. No versiones el .env.
  • Añade healthcheck a todos los servicios con tiempos de arranque.
  • Usa depends_on: condition: service_healthy para que la API espere a que PostgreSQL y Redis estén listos.
  • El workflow debe ejecutar tests antes de build Docker. Usa needs para encadenar los jobs.
  • Etiqueta la imagen con el SHA del commit. Permite rastrear exactamente qué código se desplegó.
  • No ejecutes migraciones automáticas en el arranque de la API. En desarrollo sí puedes, pero en producción usa un job o contenedor de inicialización.
  • Documenta los comandos de arranque en el README. Un nuevo desarrollador debe poder levantar todo con docker compose up -d.

6. Errores habituales

Error 1: el contexto de build no incluye todos los proyectos

# ❌ MAL: ejecutar build desde dentro de src/Cms.Api
# El Dockerfile no encuentra los proyectos de otras capas
docker build -t cms-api -f src/Cms.Api/Dockerfile src/Cms.Api

Problema: el contexto se limita a src/Cms.Api y no incluye Cms.Application, Cms.Domain ni Cms.Infrastructure.

# ✅ BIEN: contexto desde la raíz del proyecto final
docker build -t cms-api -f src/Cms.Api/Dockerfile .

Error 2: olvidar el archivo de entorno

# ❌ MAL: levantar sin .env
# POSTGRES_PASSWORD se usa con el valor por defecto "postgres"
docker compose up -d

Problema: en producción se usa la contraseña por defecto. Siempre crea un .env con valores fuertes.

Error 3: exponer puertos de base de datos en producción

# ❌ MAL: en producción no mapees el puerto 5432 al host
services:
  postgres:
    ports:
      - "5432:5432"

Problema: expone la base de datos al exterior. En desarrollo está bien, en producción elimina la sección ports de PostgreSQL y Redis.

Error 4: no invalidar el cache de Docker cuando cambia la configuración

Si cambias un ENV en el Dockerfile pero el contexto no cambia, Docker puede usar capas cacheadas. Usa docker build --no-cache o modifica un archivo que invalide la capa relevante.

Error 5: desplegar imágenes sin tests

En el workflow, si el job de Docker no depende del job de tests, una imagen con tests fallidos puede llegar a producción. Usa needs: build-and-test siempre.

Conteneriza el CMS que has construido en los módulos anteriores.

  1. Crea el archivo proyecto-final/src/Cms.Api/Dockerfile multi-stage.
  2. Crea proyecto-final/.dockerignore excluyendo bin, obj, .git, *.md y archivos de configuración local.
  3. Crea proyecto-final/docker-compose.yml con los servicios cms-api, postgres y redis.
  4. Crea proyecto-final/src/Cms.Api/appsettings.Docker.json con las cadenas de conexión apuntando a los nombres de servicio.
  5. Añade healthchecks a PostgreSQL y Redis, y haz que la API dependa de ellos.
  6. Crea un .env con POSTGRES_PASSWORD, JWT_KEY y otros secretos.
  7. Ejecuta docker compose up -d desde proyecto-final.
  8. Aplica las migraciones de EF Core dentro del contenedor.
  9. Verifica que /health y los endpoints de la API responden.
  10. Crea el workflow .github/workflows/cms-deploy.yml con build, test y Docker push.

8. Reto

Añade un servicio de reverse proxy con Caddy o nginx al docker-compose.yml. El proxy debe:

  • Terminar HTTPS con un certificado autofirmado en local.
  • Redirigir el tráfico del puerto 443 al puerto 8080 de la API.
  • Añadir cabeceras de seguridad básicas (X-Content-Type-Options, Referrer-Policy).

Además, configura el workflow de GitHub Actions para que publique la imagen solo cuando la cobertura de tests sea mayor al 60%. No resuelvas el reto todavía; inténtalo primero.

9. Resumen

  • El CMS se empaqueta en una imagen Docker multi-stage usando sdk:8.0 para compilar y aspnet:8.0 para ejecutar.
  • Docker Compose levanta la API junto con PostgreSQL y Redis, conectados mediante una red virtual.
  • El appsettings.Docker.json adapta la configuración de la API al entorno de contenedores.
  • Los secretos se gestionan con variables de entorno y un archivo .env no versionado.
  • GitHub Actions compila, testea y publica la imagen Docker automáticamente en cada push a main.
  • En producción se despliega en plataformas gestionadas como Railway, Azure Container Apps o AWS ECS.
  • Las migraciones de base de datos deben aplicarse de forma controlada, no automáticamente al arrancar la API.

10. Preguntas frecuentes

¿Puedo usar el mismo Dockerfile para desarrollo y producción?

Sí. El Dockerfile empaqueta el código compilado. La diferencia entre entornos viene de las variables de entorno y el archivo appsettings.Docker.json. Para optimizar aún más, en producción puedes usar una imagen alpine o jammy-chiseled.

¿Cómo aplico migraciones en producción?

La forma más segura es crear un job de despliegue o un contenedor de inicialización que ejecute dotnet ef database update antes de arrancar la nueva versión de la API. También puedes generar un idempotent SQL script con dotnet ef migrations script y ejecutarlo manualmente.

¿Qué plataforma es mejor para desplegar un CMS .NET?

Para aprender y proyectos pequeños, Railway o Azure Container Apps son muy sencillos. Para empresas con requisitos estrictos de seguridad y escalado, Azure Container Apps, AWS ECS o AKS son más adecuados.

¿Necesito Kubernetes para un proyecto pequeño?

No. Kubernetes añade complejidad significativa. Empieza con Docker Compose en local, luego pasa a una plataforma gestionada como Azure Container Apps, y considera Kubernetes solo cuando necesites múltiples microservicios, alta disponibilidad y control total.

¿Cómo gestiono secretos en GitHub Actions?

Ve a Settings → Secrets and variables → Actions del repositorio. Añade DOCKER_USERNAME, DOCKER_PASSWORD, JWT_KEY, POSTGRES_PASSWORD y cualquier otro valor sensible. Accede a ellos con ${{ secrets.NOMBRE }}.

¿Por qué no usar latest en la imagen de Docker?

latest es mutable: hoy apunta a una versión y mañana a otra. Si necesitas hacer rollback o rastrear un bug, no sabrás qué imagen exacta estaba corriendo. Usa etiquetas basadas en SHA, versión o rama.

¿Cómo comparto el .env con el equipo?

No compartas el archivo .env real. Crea un .env.example con valores de ejemplo y documentación de cada variable. Cada desarrollador y el pipeline de CI/CD crean su propio .env a partir de ese ejemplo.
