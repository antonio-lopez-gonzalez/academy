Docker Compose: API + PostgreSQL + Redis

Módulo 16 · Docker y despliegue35 min

1. Introducción

En esta lección aprenderemos a orquestar varios contenedores con Docker Compose. Una aplicación .NET real rara vez vive sola: necesita una base de datos, una caché distribuida, a veces una cola de mensajes y otras piezas. Docker Compose permite definir todos esos servicios en un solo archivo y levantarlos con un comando.

El problema que resolvemos es el siguiente: en desarrollo cada desarrollador instala PostgreSQL y Redis de forma distinta. En CI/CD y en producción queremos que esas dependencias se levanten de la misma manera. Docker Compose convierte la infraestructura de apoyo en código.

Objetivo: crear un docker-compose.yml que levante la API del CMS junto con PostgreSQL y Redis, configurar redes y volúmenes persistentes, usar variables de entorno y conectar la aplicación con appsettings.Docker.json.

2. Teoría

¿Qué es Docker Compose?

Docker Compose es una herramienta para definir y ejecutar aplicaciones multi-contenedor. Se configura con un archivo YAML (docker-compose.yml o compose.yaml) y se gestiona con el comando docker compose.

Conceptos clave:

  • Services: cada contenedor que forma parte de la aplicación (API, PostgreSQL, Redis).
  • Networks: redes virtuales que permiten la comunicación entre contenedores por nombre de servicio.
  • Volumes: almacenamiento persistente fuera del ciclo de vida del contenedor.
  • Environment: variables de entorno inyectadas en los contenedores.
  • depends_on: controla el orden de inicio, aunque no garantiza que el servicio esté listo.
  • healthcheck: verifica que un servicio está realmente saludable antes de que otros dependan de él.

Comunicación entre contenedores

En Docker Compose, cada servicio se puede resolver por su nombre. Si definimos un servicio llamado postgres, la API puede conectarse a Host=postgres en la cadena de conexión. Docker inserta automáticamente registros DNS para cada servicio dentro de la misma red.

┌─────────────────────────────────────────────────────────────┐
│                     Docker network: cms                       │
│                                                             │
│  ┌─────────────┐      ┌─────────────┐      ┌─────────────┐   │
│  │   cms-api   │──────│   postgres  │      │    redis    │   │
│  │   :8080     │      │   :5432     │      │   :6379     │   │
│  └─────────────┘      └─────────────┘      └─────────────┘   │
│        │                                                    │
│        ▼                                                    │
│   http://localhost:8080 (puerto expuesto al host)            │
└─────────────────────────────────────────────────────────────┘

Configuración por entorno

ASP.NET Core usa una jerarquía de configuración: variables de entorno tienen prioridad sobre appsettings.json. Para Docker creamos un appsettings.Docker.json que se carga cuando el entorno es Docker, y variables de entorno para valores sensibles como contraseñas.

Healthchecks

depends_on solo espera a que el contenedor arranque, no a que el servicio esté listo. Un healthcheck en PostgreSQL permite que la API se inicie solo cuando la base de datos acepte conexiones.

Importante: en producción se usa un orquestador como Kubernetes, que sí gestiona readiness probes de forma nativa. Docker Compose es ideal para desarrollo, pruebas y despliegues pequeños.

3. Ejemplo mínimo

Un docker-compose.yml básico con la API y una base de datos PostgreSQL.

# docker-compose.yml básico
services:
  api:
    build:
      context: .
      dockerfile: src/Cms.Api/Dockerfile
    ports:
      - "8080:8080"
    environment:
      - ASPNETCORE_ENVIRONMENT=Docker
      - ConnectionStrings__Cms=Host=postgres;Port=5432;Database=cms;Username=postgres;Password=postgres
    depends_on:
      - postgres

  postgres:
    image: postgres:16-alpine
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=postgres
      - POSTGRES_DB=cms
    ports:
      - "5432:5432"
    volumes:
      - postgres-data:/var/lib/postgresql/data

volumes:
  postgres-data:

Para levantar y probar:

# Levantar todos los servicios en segundo plano
docker compose up -d

# Ver logs de la API
docker compose logs -f api

# Detener y eliminar contenedores
docker compose down

# Detener y eliminar contenedores incluyendo volúmenes
docker compose down -v
Tip: usa docker compose up --build para forzar la reconstrucción de la imagen cuando cambies el código. Sin --build Docker reutiliza la imagen existente.

4. Ejemplo real

Ampliamos el ejemplo añadiendo Redis, healthchecks, una red personalizada, volúmenes con nombres descriptivos y un appsettings.Docker.json.

# docker-compose.yml profesional para el CMS
# Ubicación: proyecto-final/docker-compose.yml

services:
  cms-api:
    build:
      context: .
      dockerfile: src/Cms.Api/Dockerfile
    container_name: cms-api
    ports:
      - "8080:8080"
    environment:
      # Entorno de ASP.NET Core. Activa appsettings.Docker.json.
      - ASPNETCORE_ENVIRONMENT=Docker
      # Variables de conexión separadas para facilitar la configuración.
      - ConnectionStrings__Cms=Host=postgres;Port=5432;Database=cms;Username=postgres;Password=${POSTGRES_PASSWORD:-postgres}
      - ConnectionStrings__Redis=redis:6379
      # Variables de JWT (en producción usa un gestor de secretos)
      - Jwt__Issuer=${JWT_ISSUER:-CmsApi}
      - Jwt__Audience=${JWT_AUDIENCE:-CmsClient}
      - Jwt__Key=${JWT_KEY:-EstaEsUnaClaveSuperSecretaDe32Caracteres!}
      # Logging
      - Serilog__MinimumLevel__Default=Information
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    networks:
      - cms-network
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s

  postgres:
    image: postgres:16-alpine
    container_name: cms-postgres
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD:-postgres}
      - POSTGRES_DB=cms
    ports:
      - "5432:5432"
    volumes:
      - cms-postgres-data:/var/lib/postgresql/data
    networks:
      - cms-network
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d cms"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s

  redis:
    image: redis:7-alpine
    container_name: cms-redis
    ports:
      - "6379:6379"
    volumes:
      - cms-redis-data:/data
    networks:
      - cms-network
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 5s

volumes:
  cms-postgres-data:
    driver: local
  cms-redis-data:
    driver: local

networks:
  cms-network:
    driver: bridge
// appsettings.Docker.json
// Se carga cuando ASPNETCORE_ENVIRONMENT=Docker
// Sobreescribe appsettings.json con valores apropiados para contenedor.
{
  "ConnectionStrings": {
    "Cms": "Host=postgres;Port=5432;Database=cms;Username=postgres;Password=postgres",
    "Redis": "redis:6379"
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "Serilog": {
    "MinimumLevel": {
      "Default": "Information"
    },
    "WriteTo": [
      {
        "Name": "Console"
      }
    ]
  },
  "AllowedHosts": "*"
}
// Program.cs (fragmento): configurar Redis y EF Core para Docker
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = builder.Configuration.GetConnectionString("Redis");
});

builder.Services.AddDbContext<CmsDbContext>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("Cms")));

// Añadir healthchecks para la base de datos y Redis
builder.Services.AddHealthChecks()
    .AddNpgSql(builder.Configuration.GetConnectionString("Cms")!)
    .AddRedis(builder.Configuration.GetConnectionString("Redis")!);

Archivo .env opcional para no escribir secretos en el compose:

# .env en la raíz del proyecto (NO versionar en git)
POSTGRES_PASSWORD=SuperSecreto123!
JWT_ISSUER=CmsApi
JWT_AUDIENCE=CmsClient
JWT_KEY=EstaEsUnaClaveSuperSecretaDe32Caracteres!
# Levantar con variables del archivo .env
docker compose --env-file .env up -d

# Escalar la API a dos réplicas (solo en Compose Standalone)
docker compose up -d --scale cms-api=2

# Ver estado de los healthchecks
docker compose ps

# Ejecutar migraciones de EF Core dentro del contenedor
docker compose exec cms-api dotnet ef database update \
  --project src/Cms.Infrastructure/Cms.Infrastructure.csproj \
  --startup-project src/Cms.Api/Cms.Api.csproj
Recuerda: en producción no ejecutes migraciones automáticamente al arrancar la API. Usa un job de despliegue o un contenedor de init que aplique las migraciones antes de que arranque la aplicación.

5. Buenas prácticas

  • Usa un archivo .env para secretos y valores que cambian entre entornos. Nunca versiones contraseñas en docker-compose.yml.
  • Define redes explícitas para aislar la comunicación entre servicios y evitar depender de la red por defecto.
  • Usa volúmenes con nombres para que los datos de PostgreSQL y Redis sobrevivan a docker compose down.
  • Añade healthcheck a servicios con tiempos de arranque (PostgreSQL, Redis, API). Combina con depends_on: condition: service_healthy.
  • Configura restart: unless-stopped para que los servicios se recuperen automáticamente tras un reinicio del host.
  • Evita exponer puertos de base de datos a menos que necesites conectarte desde el host. En producción, solo la API debe acceder a PostgreSQL.
  • Crea un appsettings.Docker.json para valores por defecto razonables en contenedores.
  • Usa imágenes Alpine o Slim para reducir tamaño y superficie de ataque.
  • Limita recursos con deploy.resources cuando sea posible.
  • Versiona docker-compose.yml y .dockerignore, pero no el archivo .env.

6. Errores habituales

Error 1: la API falla porque PostgreSQL aún no está listo

# ❌ MAL: depends_on solo espera que el contenedor arranque
services:
  api:
    depends_on:
      - postgres

Problema: el contenedor de PostgreSQL puede estar en ejecución sin que el servidor acepte conexiones todavía.

# ✅ BIEN: usar condition: service_healthy
services:
  api:
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d cms"]
      interval: 10s
      retries: 5

Error 2: conexión a localhost desde el contenedor

// ❌ MAL: localhost dentro del contenedor es el propio contenedor
{
  "ConnectionStrings": {
    "Cms": "Host=localhost;Port=5432;..."
  }
}

Problema: dentro del contenedor localhost apunta a sí mismo, no al host ni a otros contenedores.

// ✅ BIEN: usa el nombre del servicio
{
  "ConnectionStrings": {
    "Cms": "Host=postgres;Port=5432;..."
  }
}

Error 3: persistir datos dentro del contenedor

# ❌ MAL: sin volumen, los datos se pierden al eliminar el contenedor
services:
  postgres:
    image: postgres:16-alpine

Problema: al ejecutar docker compose down se elimina el contenedor y los datos almacenados dentro.

# ✅ BIEN: montar un volumen
services:
  postgres:
    image: postgres:16-alpine
    volumes:
      - postgres-data:/var/lib/postgresql/data

volumes:
  postgres-data:

Error 4: exponer secretos en el compose

# ❌ MAL: contraseña en texto plano en el archivo versionado
services:
  api:
    environment:
      - ConnectionStrings__Cms=...;Password=secreto123

Problema: el archivo docker-compose.yml forma parte del repositorio y queda expuesto.

# ✅ BIEN: usar interpolación de variables
services:
  api:
    environment:
      - ConnectionStrings__Cms=...;Password=${POSTGRES_PASSWORD}

7. Ejercicio guiado

Levanta una aplicación .NET 8 con PostgreSQL y Redis usando Docker Compose.

  1. Crea una API con dotnet new webapi -n ComposeDemo y añade un endpoint /health que devuelva 200 OK.
  2. Crea un Dockerfile multi-stage para la API.
  3. Crea un docker-compose.yml con tres servicios: api, postgres y redis.
  4. Añade healthchecks a PostgreSQL y Redis. Haz que la API dependa de ellos.
  5. Configura la API para que se conecte a postgres:5432 y redis:6379.
  6. Crea un .env con al menos POSTGRES_PASSWORD.
  7. Ejecuta docker compose up -d y verifica que http://localhost:8080/health responde.

8. Reto

Añade un servicio de pgAdmin (dpage/pgadmin4) al docker-compose.yml del ejercicio para poder explorar la base de datos desde el navegador. Configúralo para que se conecte automáticamente a PostgreSQL y asegúrate de que no se exponga en producción. No lo resuelvas todavía; inténtalo primero.

9. Resumen

  • Docker Compose orquesta varios contenedores con un solo archivo YAML.
  • Los servicios se comunican por nombre dentro de una red definida por el usuario.
  • Los volúmenes persisten datos fuera del contenedor.
  • Los healthcheck y depends_on condicionales mejoran el arranque ordenado.
  • Los secretos deben ir en .env, no en el archivo docker-compose.yml.
  • El appsettings.Docker.json adapta la configuración de la API al entorno de contenedores.

10. Preguntas frecuentes

¿Cuál es la diferencia entre docker-compose.yml y compose.yaml?

La especificación moderna de Docker Compose recomienda compose.yaml. Ambos nombres funcionan, pero compose.yaml es el preferido desde la versión 2 del formato.

¿Por qué la API no puede usar localhost para conectarse a PostgreSQL?

Porque cada contenedor tiene su propio stack de red. localhost dentro del contenedor de la API apunta a la propia API. Usa el nombre del servicio (postgres) que Docker resuelve como DNS.

¿Qué pasa si borro el volumen con docker compose down -v?

Se eliminan los datos persistentes. Úsalo solo cuando quieras empezar de cero. Sin -v, los volúmenes se conservan y se reutilizan al volver a levantar los servicios.

¿Puedo usar Docker Compose en producción?

Para entornos pequeños y simples, sí. Para alta disponibilidad, autoescalado, rolling updates y gestión de secretos avanzada, usa Kubernetes o un servicio gestionado como Azure Container Apps, AWS ECS o Railway.

¿Cómo paso la configuración de JWT sin hardcodearla?

Define variables en un archivo .env y usa la interpolación ${JWT_KEY} en el docker-compose.yml. En producción, el pipeline de CI/CD inyecta esos valores desde un gestor de secretos.

¿Cómo ejecuto migraciones de EF Core en Docker?

La forma más segura es crear un contenedor de init o un job que ejecute dotnet ef database update antes de arrancar la API. Nunca ejecutes migraciones automáticamente dentro del Program.cs de una API expuesta a internet.
