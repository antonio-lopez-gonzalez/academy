Dockerfile multi-stage para .NET

Módulo 16 · Docker y despliegue35 min

1. Introducción

En esta lección aprenderemos a crear un Dockerfile multi-stage para una aplicación ASP.NET Core 8. Docker nos permite empaquetar la aplicación junto con todas sus dependencias en una imagen portable que se ejecuta igual en desarrollo, en CI/CD y en producción.

El problema que resolvemos es simple: en un equipo de desarrollo todos tienen versiones distintas de SDK, runtime y herramientas. En producción queremos una imagen pequeña, segura y reproducible. Un Dockerfile multi-stage compila el código en una imagen con el SDK completo y luego copia solo lo necesario a una imagen mínima de runtime.

Objetivo: construir una imagen Docker optimizada para .NET 8, entender por qué se usa multi-stage, cómo cachear capas de dependencias y cómo ejecutar el contenedor con un usuario no root.

2. Teoría

¿Qué es una imagen Docker?

Una imagen Docker es un paquete inmutable que contiene el sistema de archivos, las bibliotecas, el runtime y la configuración necesarios para ejecutar una aplicación. A diferencia de una máquina virtual, un contenedor comparte el kernel del host, por lo que es mucho más ligero.

En .NET una imagen puede partir de varias bases oficiales:

  • mcr.microsoft.com/dotnet/sdk:8.0: incluye el SDK completo con dotnet CLI, compilador y herramientas. Ocupa ~700 MB. Se usa para compilar y publicar.
  • mcr.microsoft.com/dotnet/aspnet:8.0: incluye solo el runtime de ASP.NET Core. Ocupa ~220 MB. Se usa para ejecutar la aplicación publicada.
  • mcr.microsoft.com/dotnet/runtime:8.0: runtime para aplicaciones de consola sin ASP.NET Core.
Tip: nunca uses la imagen sdk para ejecutar en producción. Tiene herramientas de compilación que aumentan la superficie de ataque y el tamaño de la imagen.

Multi-stage builds

Un Dockerfile puede tener varias etapas (stages). Cada etapa es una imagen temporal. La última etapa es la que se guarda como resultado final. Las etapas anteriores se descartan, pero se pueden copiar archivos entre ellas.

Para .NET 8 el patrón estándar es:

┌─────────────────────┐      ┌─────────────────────┐      ┌─────────────────────┐
│   base (runtime)    │◀─────│      build          │      │      publish        │
│   imagen final      │      │   compilar código   │─────▶│   publicar app      │
│   ~220 MB           │      │   con SDK           │      │   con SDK           │
└─────────────────────┘      └─────────────────────┘      └─────────────────────┘
         ▲                                                          │
         │              copiar binarios publicados                   │
         └──────────────────────────────────────────────────────────┘

Optimización de capas

Docker construye imágenes en capas. Si una capa cambia, todas las capas posteriores se vuelven a construir. Por eso copiamos primero los archivos .csproj y ejecutamos dotnet restore antes de copiar el resto del código fuente. Así, los paquetes NuGet solo se restauran cuando cambian las dependencias, no en cada cambio de código.

Usuario no root

Por seguridad, la aplicación dentro del contenedor no debe ejecutarse como root. Las imágenes de .NET 8 incluyen un usuario predefinido app con UID 1654. Podemos usarlo directamente para reducir el impacto de una posible vulnerabilidad.

.dockerignore

El archivo .dockerignore evita que archivos innecesarios (como bin, obj, .git o archivos locales de configuración) se copien al contexto de build. Menos archivos significan un contexto más pequeño y menos invalidaciones de caché.

3. Ejemplo mínimo

Supongamos una API minimal llamada HelloApi. Creamos un Dockerfile multi-stage básico.

# Etapa 1: compilar y publicar con el SDK
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# Copiamos solo el proyecto para cachear restore
COPY HelloApi.csproj .
RUN dotnet restore HelloApi.csproj

# Copiamos el resto del código y publicamos
COPY . .
RUN dotnet publish HelloApi.csproj -c Release -o /app/publish

# Etapa 2: imagen final de runtime
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .

EXPOSE 8080
ENTRYPOINT ["dotnet", "HelloApi.dll"]

Para construir y ejecutar:

# Construir la imagen desde la raíz del proyecto
# El punto final indica el contexto de build (carpeta actual)
docker build -t hello-api:1.0 -f src/HelloApi/Dockerfile .

# Ejecutar el contenedor
# -p 8080:8080 mapea el puerto del host al puerto del contenedor
docker run -d -p 8080:8080 --name hello-api hello-api:1.0

# Verificar que responde
curl http://localhost:8080
Nota: en .NET 8 la imagen de ASP.NET runtime expone por defecto el puerto 8080, no el 80 de versiones anteriores. La variable de entorno ASPNETCORE_URLS ya no es necesaria si usas el puerto por defecto.

4. Ejemplo real

Vamos a mejorar el Dockerfile para un proyecto profesional con varios proyectos, usuario no root, imagen alpine para reducir tamaño y un .dockerignore completo.

# Dockerfile para una API ASP.NET Core 8 con Clean Architecture
# Ubicación: src/Cms.Api/Dockerfile

# -------------------------------------------------
# Etapa 1: build
# Usamos el SDK de .NET 8 para compilar y publicar
# -------------------------------------------------
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# Copiamos los archivos de proyecto de todas las capas.
# El orden importa: si cambia un .csproj, se invalida el cache de restore.
COPY src/Cms.Api/Cms.Api.csproj Cms.Api/
COPY src/Cms.Application/Cms.Application.csproj Cms.Application/
COPY src/Cms.Domain/Cms.Domain.csproj Cms.Domain/
COPY src/Cms.Infrastructure/Cms.Infrastructure.csproj Cms.Infrastructure/

# Restore solo del proyecto de entrada.
# El SDK descarga todos los paquetes transitivos necesarios.
RUN dotnet restore Cms.Api/Cms.Api.csproj

# Copiamos todo el código fuente de las capas.
COPY src/Cms.Api/ Cms.Api/
COPY src/Cms.Application/ Cms.Application/
COPY src/Cms.Domain/ Cms.Domain/
COPY src/Cms.Infrastructure/ Cms.Infrastructure/

# Compilamos y publicamos en Release.
# -o /app/publish coloca los binarios en esa carpeta.
# --no-restore reutiliza los paquetes ya descargados.
RUN dotnet publish Cms.Api/Cms.Api.csproj \
    -c Release \
    -o /app/publish \
    --no-restore

# -------------------------------------------------
# Etapa 2: runtime
# Imagen final ligera con solo ASP.NET Core runtime.
# -------------------------------------------------
FROM mcr.microsoft.com/dotnet/aspnet:8.0-alpine AS runtime

# En Alpine necesitamos globalization solo si la app la usa.
# Para la mayoría de APIs en inglés/español básico la desactivamos.
ENV DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1

# Creamos el directorio de trabajo.
WORKDIR /app

# Copiamos los binarios publicados desde la etapa de build.
COPY --from=build /app/publish .

# Configuramos la aplicación para escuchar en 8080.
ENV ASPNETCORE_URLS=http://+:8080

# Exponemos el puerto. Es documentación; el puerto real lo controla el runtime.
EXPOSE 8080

# Ejecutamos como usuario no root incluido en la imagen oficial.
USER app

# Punto de entrada: arranca la API.
ENTRYPOINT ["dotnet", "Cms.Api.dll"]
# .dockerignore en la raíz del repositorio
# Evita copiar archivos innecesarios al contexto de Docker.

# Carpetas de compilación
**/bin/
**/obj/

# Configuración local y secretos
**/appsettings.Development.json
**/appsettings.Local.json
**/secrets.json
*.env
.env.*

# Herramientas y dependencias locales
.vs/
.vscode/
.idea/
*.user
*.suo

# Control de versiones
.git/
.gitignore

# Tests y documentación que no se necesitan en la imagen
tests/
*.md
docs/

# Docker mismo
Dockerfile*
docker-compose*.yml
.dockerignore

Construcción y verificación de tamaño:

# Construir desde la raíz del repositorio
docker build -t cms-api:1.0 -f src/Cms.Api/Dockerfile .

# Comparar tamaño de imagen con y sin optimizaciones
docker images cms-api

# REPOSITORY   TAG       IMAGE ID       CREATED          SIZE
# cms-api      1.0       abc123...      10 seconds ago   115MB

# Inspeccionar las capas del Dockerfile
# Útil para detectar capas grandes o cambios innecesarios
docker history cms-api:1.0
Variante Alpine: la imagen aspnet:8.0-alpine es más pequeña que la estándar. Si tu aplicación no necesita culturas complejas (fechas, monedas, ordenación específica) o System.Drawing, Alpine es una excelente opción.

5. Buenas prácticas

  • Usa SDK solo para build, runtime para ejecutar. Nunca expongas el compilador en producción.
  • Copia .csproj antes que el código. Así dotnet restore se cachea entre builds si no cambian las dependencias.
  • Usa --no-restore en publish. Acelera la etapa de publicación porque los paquetes ya están descargados.
  • Ejecuta como usuario no root. USER app es suficiente en las imágenes oficiales de .NET 8.
  • Mantén un .dockerignore completo. Reduce el contexto de build y evita invalidar caché por archivos locales.
  • Prefiere imágenes alpine o jammy-chiseled si no necesitas funcionalidades de cultura complejas. Son más pequeñas y seguras.
  • Usa una sola instrucción COPY por carpeta. Cada instrucción crea una capa; agrupar reduce el número de capas.
  • No guardes secretos en la imagen. Usa variables de entorno, Docker secrets o un gestor de configuración en tiempo de ejecución.
  • Etiqueta las imágenes con versiones semánticas. Evita siempre usar latest en producción.
  • Escanea la imagen con docker scout o Trivy. Detecta vulnerabilidades en las dependencias de la imagen base.

6. Errores habituales

Error 1: compilar y ejecutar en la misma imagen

# ❌ MAL: imagen final incluye SDK completo
FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /app
COPY . .
RUN dotnet publish -c Release -o out
EXPOSE 8080
ENTRYPOINT ["dotnet", "out/Cms.Api.dll"]

Problema: la imagen final pesa más de 700 MB y expone herramientas de compilación innecesarias.

# ✅ BIEN: separar build y runtime
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
...
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
...
COPY --from=build /app/publish .

Error 2: copiar todo antes de restore

# ❌ MAL: restore se ejecuta en cada cambio de código
COPY . .
RUN dotnet restore

Problema: cualquier cambio en un archivo .cs invalida el cache de restore y vuelve a descargar todos los paquetes.

Error 3: ejecutar como root

# ❌ MAL: no se especifica USER, por defecto es root
FROM mcr.microsoft.com/dotnet/aspnet:8.0
...
ENTRYPOINT ["dotnet", "Cms.Api.dll"]

Problema: si un atacante explota la aplicación, obtiene privilegios de root dentro del contenedor.

Error 4: exponer secretos en el Dockerfile

# ❌ MAL: secretos en la imagen
ENV ConnectionStrings__Cms="Host=prod;Password=secreto123"

Problema: cualquiera con acceso a la imagen puede leer las variables ENV con docker inspect o docker history. Pasa secretos en tiempo de ejecución mediante variables de entorno del host.

7. Ejercicio guiado

Crea un Dockerfile multi-stage para una API minimal de .NET 8.

  1. Crea una nueva API con dotnet new webapi -n DockerDemo -o ejemplos/m16-docker/DockerDemo.
  2. En la raíz del proyecto crea un .dockerignore que excluya bin, obj, .git, *.md y appsettings.Development.json.
  3. Crea un Dockerfile en la raíz del proyecto con dos etapas: build con sdk:8.0 y runtime con aspnet:8.0.
  4. Copia primero el .csproj, ejecuta dotnet restore, luego copia el resto del código y ejecuta dotnet publish.
  5. Usa USER app en la etapa final y expón el puerto 8080.
  6. Construye la imagen: docker build -t docker-demo:1.0 .
  7. Ejecuta el contenedor: docker run -d -p 8080:8080 --name docker-demo docker-demo:1.0.
  8. Verifica que responde en http://localhost:8080/weatherforecast.

8. Reto

Optimiza el Dockerfile del ejercicio usando la imagen base aspnet:8.0-alpine y añade un HEALTHCHECK que consulte el endpoint /health de la API. Investiga cómo Docker usa el HEALTHCHECK para decidir si el contenedor está sano. No lo resuelvas todavía; inténtalo primero.

9. Resumen

  • Un Dockerfile multi-stage separa la compilación (SDK) de la ejecución (runtime).
  • La imagen mcr.microsoft.com/dotnet/aspnet:8.0 es la base correcta para ejecutar APIs en producción.
  • Copiar .csproj antes que el código fuente permite cachear dotnet restore.
  • El usuario app de las imágenes oficiales permite ejecutar el contenedor sin privilegios de root.
  • El archivo .dockerignore reduce el contexto de build y protege contra la inclusión accidental de archivos locales.
  • Los secretos y la configuración de entorno deben inyectarse en tiempo de ejecución, no en la imagen.

10. Preguntas frecuentes

¿Puedo usar docker build desde cualquier carpeta?

Sí, pero el punto (.) al final del comando define el contexto de build. Si tu Dockerfile está en una subcarpeta, usa -f para indicar la ruta del Dockerfile pero el contexto debe ser la raíz del proyecto: docker build -t cms-api:1.0 -f src/Cms.Api/Dockerfile ..

¿Por qué el puerto predeterminado es 8080 en .NET 8?

Microsoft cambió el puerto por defecto para permitir que las imágenes oficiales se ejecuten como usuario no root. En Linux, los puertos menores a 1024 requieren privilegios especiales; el 8080 evita ese problema.

¿Qué diferencia hay entre COPY . . y copiar solo el proyecto?

COPY . . copia todo el contexto de build. Si incluye archivos que cambian frecuentemente (como el código fuente), invalida el cache de Docker. Copiar primero solo el .csproj permite que dotnet restore se ejecute solo cuando cambien las dependencias.

¿Debo usar dotnet build antes de dotnet publish?

No es necesario. dotnet publish ya realiza la compilación. Usar --no-restore tras un dotnet restore previo es más eficiente.

¿Cuándo debo usar alpine y cuándo jammy?

Alpine es más pequeña y segura, ideal para APIs sin dependencias de cultura complejas. Jammy (Ubuntu) es más compatible con bibliotecas nativas que requieren glibc. Si usas bibliotecas como SkiaSharp, ImageMagick o drivers nativos específicos, prueba Jammy primero.

¿Cómo veo el tamaño de mi imagen?

Ejecuta docker images nombre-imagen. Para ver el desglose por capas usa docker history nombre-imagen:tag. Para optimizar más, usa docker scout quickview si tienes Docker Desktop o dive como herramienta externa.
