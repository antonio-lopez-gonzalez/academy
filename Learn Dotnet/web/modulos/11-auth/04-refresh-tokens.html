Refresh Tokens: rotation y revocación

Módulo 11 · Autenticación y autorización35 min

1 · Introducción

Un access token de corta duración es seguro pero incómodo: si expira cada 15 minutos, el usuario tendría que iniciar sesión constantemente. Los refresh tokens resuelven este problema: permiten obtener un nuevo access token sin volver a pedir la contraseña.

En esta lección aprenderemos la estrategia de rotation (cada refresh token se usa una sola vez), la revocación y cómo almacenar refresh tokens de forma segura.

¿Qué problema resuelve?

Mantener sesiones largas sin aumentar el riesgo de un access token comprometido. El access token es corto; el refresh token es largo y puede invalidarse en el servidor.

Errores típicos

  • Usar un único refresh token largo sin rotation ni expiración.
  • Almacenar refresh tokens en localStorage del navegador.
  • No revocar tokens en logout o cambio de contraseña.
  • Generar refresh tokens predecibles (por ejemplo, GUIDs sin hash).
  • Permitir múltiples refresh tokens por usuario sin límite.
  • Ignorar la detección de reutilización de refresh tokens robados.

2 · Teoría

Access token vs refresh token

CaracterísticaAccess tokenRefresh token
DuraciónCorta (minutos)Larga (días/semanas)
UsoAcceder a recursosObtener nuevos access tokens
FormatoJWT autocontenidoOpaco (string aleatorio largo)
RevocaciónImposible hasta expirarPosible en servidor
AlmacenamientoClienteCliente + servidor

Rotation

Cada vez que se usa un refresh token, se genera un nuevo par de tokens y el refresh token anterior se invalida. Esto reduce el impacto de un token robado: si un atacante lo usa, el usuario legítimo notará que su token ya no funciona.

Revocación

El servidor debe poder invalidar refresh tokens en eventos como:

  • Logout del usuario.
  • Cambio de contraseña.
  • Detección de uso sospechoso.
  • Revocación administrativa.

Detección de reutilización

La estrategia más robusta guarda el refresh token actual en la base de datos. Si llega un refresh token que no coincide con el actual, se asume que fue robado y se revocan todos los tokens de la sesión.

Almacenamiento en cliente

  • HttpOnly cookie: protegida contra XSS, accesible solo por el servidor.
  • Secure cookie: solo se envía por HTTPS.
  • SameSite: mitiga CSRF en ciertos escenarios.
  • localStorage: no usar para refresh tokens; es vulnerable a XSS.

Refresh tokens opacos

Los refresh tokens no deben ser JWTs. Deben ser strings largos y aleatorios almacenados en la base de datos. Así puedes revocarlos y detectar reutilización.

3 · Ejemplo mínimo

Simularemos el flujo de login, refresh y logout con un servicio en memoria.

# Crear proyecto de consola
dotnet new console -n RefreshTokensDemo -o RefreshTokensDemo
cd RefreshTokensDemo
# No necesitamos paquetes externos; usamos solo BCL.
dotnet run
using System.Security.Cryptography;

// ----------------------------------------------------------------
// MODELOS
// ----------------------------------------------------------------
public sealed record UserSession(Guid UserId, string Email, string[] Roles);
public sealed class RefreshToken
{
    public required string Token { get; init; }
    public required Guid UserId { get; init; }
    public required DateTime ExpiresAt { get; init; }
    public required bool IsRevoked { get; set; }
    public required string? ReplacedBy { get; set; }
}

// ----------------------------------------------------------------
// SERVICIO EN MEMORIA
// ----------------------------------------------------------------
public sealed class RefreshTokenService
{
    private readonly List _tokens = new();
    private readonly TimeProvider _timeProvider;

    public RefreshTokenService(TimeProvider timeProvider)
    {
        _timeProvider = timeProvider;
    }

    public RefreshToken Create(UserSession session)
    {
        var token = new RefreshToken
        {
            Token = Convert.ToBase64String(RandomNumberGenerator.GetBytes(64)),
            UserId = session.UserId,
            ExpiresAt = _timeProvider.GetUtcNow().AddDays(7).DateTime,
            IsRevoked = false,
            ReplacedBy = null
        };

        _tokens.Add(token);
        return token;
    }

    public RefreshToken Rotate(string oldToken, UserSession session)
    {
        var stored = _tokens.FirstOrDefault(t => t.Token == oldToken);
        if (stored is null || stored.IsRevoked || stored.ExpiresAt < _timeProvider.GetUtcNow())
        {
            throw new InvalidOperationException("Refresh token inválido.");
        }

        // Detectar reutilización: si el token usado ya fue reemplazado, revocamos toda la sesión.
        if (stored.ReplacedBy is not null)
        {
            RevokeAllUserTokens(stored.UserId);
            throw new InvalidOperationException("Posible robo de token. Sesión revocada.");
        }

        var newToken = Create(session);
        stored.IsRevoked = true;
        stored.ReplacedBy = newToken.Token;
        return newToken;
    }

    public void Revoke(string token)
    {
        var stored = _tokens.FirstOrDefault(t => t.Token == token);
        if (stored is not null)
        {
            stored.IsRevoked = true;
        }
    }

    public void RevokeAllUserTokens(Guid userId)
    {
        foreach (var token in _tokens.Where(t => t.UserId == userId))
        {
            token.IsRevoked = true;
        }
    }
}

// ----------------------------------------------------------------
// USO
// ----------------------------------------------------------------
var service = new RefreshTokenService(TimeProvider.System);
var session = new UserSession(Guid.NewGuid(), "ana@example.com", ["Author"]);

var refreshToken = service.Create(session);
Console.WriteLine($"Refresh token creado: {refreshToken.Token[..20]}...");

var newToken = service.Rotate(refreshToken.Token, session);
Console.WriteLine($"Nuevo refresh token: {newToken.Token[..20]}...");

// Reutilizar el antiguo debería fallar.
try
{
    service.Rotate(refreshToken.Token, session);
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"Error esperado: {ex.Message}");
}

Cryptographically secure

RandomNumberGenerator.GetBytes genera bytes criptográficamente seguros. Nunca uses Guid.NewGuid().ToString() como refresh token.

4 · Ejemplo real

En una API real, el refresh token se guarda en PostgreSQL, se envía al cliente como HttpOnly cookie y se valida en el endpoint /auth/refresh.

// RefreshToken.cs (entidad EF Core)
public sealed class RefreshToken
{
    public required Guid Id { get; init; }
    public required string TokenHash { get; init; } // SHA-256 del token para búsqueda rápida.
    public required Guid UserId { get; init; }
    public required DateTime ExpiresAt { get; init; }
    public bool IsRevoked { get; set; }
    public string? ReplacedByTokenHash { get; set; }
    public DateTime CreatedAt { get; init; }
}

// IRefreshTokenRepository.cs
public interface IRefreshTokenRepository
{
    Task GetByTokenHashAsync(string tokenHash, CancellationToken ct);
    Task AddAsync(RefreshToken token, CancellationToken ct);
    Task UpdateAsync(RefreshToken token, CancellationToken ct);
    Task RevokeAllForUserAsync(Guid userId, CancellationToken ct);
}

// IJwtService.cs
public interface IJwtService
{
    string GenerateAccessToken(User user);
    string GenerateRefreshToken();
}

// AuthService.cs
public sealed class AuthService(
    IUserRepository userRepository,
    IRefreshTokenRepository refreshTokenRepository,
    IJwtService jwtService,
    IPasswordHasher passwordHasher,
    TimeProvider timeProvider) : IAuthService
{
    public async Task LoginAsync(LoginRequest request, CancellationToken ct)
    {
        var user = await userRepository.GetByEmailAsync(request.Email, ct);
        if (user is null)
        {
            return AuthResult.Failure("Credenciales inválidas.");
        }

        var result = passwordHasher.VerifyHashedPassword(user, user.PasswordHash, request.Password);
        if (result == PasswordVerificationResult.Failed)
        {
            return AuthResult.Failure("Credenciales inválidas.");
        }

        if (result == PasswordVerificationResult.SuccessRehashNeeded)
        {
            user.PasswordHash = passwordHasher.HashPassword(user, request.Password);
        }

        var accessToken = jwtService.GenerateAccessToken(user);
        var refreshTokenValue = jwtService.GenerateRefreshToken();
        var refreshToken = new RefreshToken
        {
            Id = Guid.NewGuid(),
            TokenHash = HashToken(refreshTokenValue),
            UserId = user.Id,
            ExpiresAt = timeProvider.GetUtcNow().AddDays(7).DateTime,
            CreatedAt = timeProvider.GetUtcNow().DateTime
        };

        await refreshTokenRepository.AddAsync(refreshToken, ct);
        return AuthResult.Success(accessToken, refreshTokenValue);
    }

    public async Task RefreshAsync(string refreshTokenValue, CancellationToken ct)
    {
        var tokenHash = HashToken(refreshTokenValue);
        var token = await refreshTokenRepository.GetByTokenHashAsync(tokenHash, ct);

        if (token is null || token.IsRevoked || token.ExpiresAt < timeProvider.GetUtcNow())
        {
            return AuthResult.Failure("Refresh token inválido.");
        }

        // Detección de reutilización.
        if (token.ReplacedByTokenHash is not null)
        {
            await refreshTokenRepository.RevokeAllForUserAsync(token.UserId, ct);
            return AuthResult.Failure("Sesión comprometida. Revocada.");
        }

        var user = await userRepository.GetByIdAsync(token.UserId, ct);
        if (user is null)
        {
            return AuthResult.Failure("Usuario no encontrado.");
        }

        var newAccessToken = jwtService.GenerateAccessToken(user);
        var newRefreshTokenValue = jwtService.GenerateRefreshToken();
        var newRefreshToken = new RefreshToken
        {
            Id = Guid.NewGuid(),
            TokenHash = HashToken(newRefreshTokenValue),
            UserId = user.Id,
            ExpiresAt = timeProvider.GetUtcNow().AddDays(7).DateTime,
            CreatedAt = timeProvider.GetUtcNow().DateTime,
            ReplacedByTokenHash = null
        };

        token.IsRevoked = true;
        token.ReplacedByTokenHash = newRefreshToken.TokenHash;

        await refreshTokenRepository.AddAsync(newRefreshToken, ct);
        await refreshTokenRepository.UpdateAsync(token, ct);

        return AuthResult.Success(newAccessToken, newRefreshTokenValue);
    }

    public async Task LogoutAsync(string refreshTokenValue, CancellationToken ct)
    {
        var token = await refreshTokenRepository.GetByTokenHashAsync(HashToken(refreshTokenValue), ct);
        if (token is not null)
        {
            token.IsRevoked = true;
            await refreshTokenRepository.UpdateAsync(token, ct);
        }
    }

    private static string HashToken(string token)
    {
        var bytes = SHA256.HashData(Encoding.UTF8.GetBytes(token));
        return Convert.ToHexString(bytes);
    }
}

Los endpoints de /auth/login y /auth/refresh reciben el servicio, generan tokens y devuelven el refresh token como cookie HttpOnly, Secure y SameSite=Strict.

Hash del refresh token

Guarda el hash del refresh token en la base de datos, no el token en texto plano. Si la base de datos se filtra, el atacante no puede usar los tokens directamente.

5 · Buenas prácticas

  • Usa access tokens cortos (15 minutos) y refresh tokens largos (7 días).
  • Implementa rotation: cada refresh genera un nuevo refresh token.
  • Detecta reutilización de refresh tokens y revoca toda la sesión.
  • Almacena refresh tokens como HttpOnly Secure cookies.
  • Guarda el hash del refresh token, no el token original.
  • Revoca tokens en logout, cambio de contraseña y comportamiento sospechoso.
  • Usa TimeProvider para que los tests controlen el tiempo.

6 · Errores habituales

Incorrecto: refresh token sin expiración

// ❌ Mal: refresh token eterno.
ExpiresAt = DateTime.MaxValue

Correcto: refresh token con expiración

// ✅ Bien: expiración razonable.
ExpiresAt = timeProvider.GetUtcNow().AddDays(7).DateTime

Incorrecto: refresh token en localStorage

// ❌ Mal: vulnerable a XSS.
localStorage.setItem("refreshToken", token);

Correcto: HttpOnly Secure cookie

// ✅ Bien: cookie no accesible por JavaScript.
context.Response.Cookies.Append("refreshToken", token, new CookieOptions
{
    HttpOnly = true,
    Secure = true,
    SameSite = SameSiteMode.Strict
});

Incorrecto: permitir reutilización sin detección

// ❌ Mal: el token antiguo sigue siendo válido.
if (stored.IsRevoked) return Invalid;
return CreateNewToken();

Correcto: rotation con detección

// ✅ Bien: invalidar el antiguo y detectar si ya fue usado.
if (stored.ReplacedByTokenHash is not null)
{
    RevokeAllUserTokens(stored.UserId);
    return Compromised;
}
stored.IsRevoked = true;
// emitir nuevo token...

9 · Resumen

  • El access token es corto y autocontenido; el refresh token es largo y opaco.
  • La rotation invalida el refresh token anterior al emitir uno nuevo.
  • La revocación permite cerrar sesiones y responder ante compromisos.
  • La detección de reutilización protege contra tokens robados.
  • Almacena refresh tokens como HttpOnly Secure cookies, guarda su hash en la base de datos y genera valores con RandomNumberGenerator.

10 · Preguntas frecuentes

¿Por qué no usar un JWT como refresh token?

Porque no podrías revocarlo hasta que expire. Los refresh tokens opacos permiten invalidación inmediata y detección de reutilización.

¿Cuánto debe durar un refresh token?

Depende del riesgo. Entre 7 días y 30 días es común. Aplicaciones bancarias pueden usar duraciones más cortas y reautenticación frecuente.

¿Qué hago si el refresh token expira?

El usuario debe volver a iniciar sesión con usuario y contraseña. No extiendas automáticamente la expiración de refresh tokens sin justificación.

¿Debo almacenar el refresh token o su hash?

Hash. Si alguien accede a la base de datos, no podrá usar los tokens directamente. Aunque SHA-256 es rápido, el token ya es aleatorio y largo, por lo que el hash añade defensa en profundidad.
