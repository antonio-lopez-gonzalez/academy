Proyecto CMS: JWT + roles

Módulo 11 · Proyecto50 min

1. Introducción

En esta lección aplicamos todo lo aprendido sobre autenticación y autorización al proyecto CMS. Añadiremos autenticación JWT, roles (Admin, Editor, Author), protección de endpoints y refresh tokens. También sembraremos usuarios iniciales con contraseñas hasheadas mediante BCrypt.

Al finalizar, la API del CMS tendrá un sistema completo de login, endpoints protegidos por roles y políticas, y un flujo de refresh tokens seguro.

Objetivos del proyecto

  • Configurar autenticación JWT en Cms.Api.
  • Definir roles Admin, Editor y Author.
  • Proteger endpoints CRUD según el rol requerido.
  • Implementar un servicio de autenticación custom con JWT.
  • Implementar refresh tokens con rotation y revocación.
  • Sembrar usuarios iniciales con contraseñas hasheadas con BCrypt.
  • Verificar que los tests de integración pasan.

2. Teoría

2.1. Arquitectura del CMS

Seguimos Clean Architecture con cuatro capas:

  • Cms.Domain: entidades User, Role y value objects.
  • Cms.Application: casos de uso, interfaces de servicios de autenticación.
  • Cms.Infrastructure: EF Core, repositorios, implementación de IJwtService.
  • Cms.Api: configuración de autenticación, endpoints, seeding.

2.2. Autenticación en capas

La infraestructura conoce los detalles de JWT (claves, claims, emisor). La aplicación define las interfaces. La API solo configura el middleware y protege endpoints. El dominio no conoce JWT.

2.3. Roles del CMS

  • Admin: gestiona usuarios, categorías y cualquier post.
  • Editor: puede editar y publicar cualquier post, gestionar categorías.
  • Author: solo puede crear y editar sus propios posts.

2.4. Refresh tokens

Usamos el patrón de lección anterior: tokens opacos de 64 bytes, rotación, detección de reutilización y almacenamiento como HttpOnly Secure cookie.

Consejo del proyecto

Define los secretos de JWT en user-secrets o variables de entorno. Nunca incluyas una clave real en appsettings.Development.json que pueda subirse a Git.

public interface IAuthService

// Cms.Application/Contracts/AuthResult.cs
public sealed class AuthResult
{
    public bool IsSuccess { get; init; }
    public string? AccessToken { get; init; }
    public string? RefreshToken { get; init; }
    public string? Error { get; init; }

    public static AuthResult Success(string accessToken, string refreshToken) =>
        new() { IsSuccess = true, AccessToken = accessToken, RefreshToken = refreshToken };

    public static AuthResult Failure(string error) =>
        new() { IsSuccess = false, Error = error };
}

4.2. Entidades de dominio

Añadimos tres entidades al dominio del CMS:

  • User: Id, Email, Name, PasswordHash y una colección de Role.
  • Role: Id y Name, con valores predefinidos Admin, Editor y Author.
  • RefreshToken: Id, TokenHash, UserId, ExpiresAt, IsRevoked y ReplacedByTokenHash.

El repositorio IRefreshTokenRepository ofrece operaciones para buscar por hash, añadir, actualizar y revocar todos los tokens de un usuario.

4.3. Configuración JWT

La configuración de JWT (JwtSettings) y el servicio (JwtService) siguen el mismo patrón visto en la lección 1: generan un token con claims de sub, email, name, roles y jti, y generan refresh tokens aleatorios de 64 bytes. El secreto se lee desde variables de entorno o dotnet user-secrets.

4.4. Servicio de autenticación

// Cms.Infrastructure/Services/AuthService.cs
public sealed class AuthService(
    IUserRepository userRepository,
    IRefreshTokenRepository refreshTokenRepository,
    IJwtService jwtService,
    TimeProvider timeProvider) : IAuthService
{
    public async Task LoginAsync(LoginCommand command, CancellationToken ct)
    {
        var user = await userRepository.GetByEmailAsync(command.Email, ct);
        if (user is null)
        {
            return AuthResult.Failure("Credenciales inválidas.");
        }

        if (!BCrypt.Net.BCrypt.Verify(command.Password, user.PasswordHash))
        {
            return AuthResult.Failure("Credenciales inválidas.");
        }

        return await GenerateTokensAsync(user, ct);
    }

    public async Task RefreshAsync(string refreshTokenValue, CancellationToken ct)
    {
        var tokenHash = JwtService.HashToken(refreshTokenValue);
        var token = await refreshTokenRepository.GetByTokenHashAsync(tokenHash, ct);

        if (token is null || token.IsRevoked || token.ExpiresAt < timeProvider.GetUtcNow())
        {
            return AuthResult.Failure("Refresh token inválido.");
        }

        if (token.ReplacedByTokenHash is not null)
        {
            await refreshTokenRepository.RevokeAllForUserAsync(token.UserId, ct);
            return AuthResult.Failure("Sesión comprometida.");
        }

        var user = await userRepository.GetByIdAsync(token.UserId, ct);
        if (user is null)
        {
            return AuthResult.Failure("Usuario no encontrado.");
        }

        var result = await GenerateTokensAsync(user, ct);
        token.Revoke(JwtService.HashToken(result.RefreshToken!));
        await refreshTokenRepository.UpdateAsync(token, ct);
        return result;
    }

    public async Task LogoutAsync(string refreshTokenValue, CancellationToken ct)
    {
        var token = await refreshTokenRepository.GetByTokenHashAsync(JwtService.HashToken(refreshTokenValue), ct);
        if (token is not null)
        {
            token.Revoke();
            await refreshTokenRepository.UpdateAsync(token, ct);
        }
    }

    private async Task GenerateTokensAsync(User user, CancellationToken ct)
    {
        var accessToken = jwtService.GenerateAccessToken(user);
        var refreshTokenValue = jwtService.GenerateRefreshToken();
        var refreshToken = RefreshToken.Create(
            JwtService.HashToken(refreshTokenValue),
            user.Id,
            timeProvider.GetUtcNow().AddDays(7).DateTime);

        await refreshTokenRepository.AddAsync(refreshToken, ct);
        return AuthResult.Success(accessToken, refreshTokenValue);
    }
}

4.5. Configuración en Cms.Api

// Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.Configure(builder.Configuration.GetSection("JwtSettings"));

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        var settings = builder.Configuration.GetSection("JwtSettings").Get()!;
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidIssuer = settings.Issuer,
            ValidAudience = settings.Audience,
            IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(settings.Secret))
        };
    });

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanCreatePosts", policy =>
        policy.RequireRole("Admin", "Editor", "Author"));

    options.AddPolicy("CanEditAnyPost", policy =>
        policy.RequireRole("Admin", "Editor"));

    options.AddPolicy("CanManageCategories", policy =>
        policy.RequireRole("Admin", "Editor"));

    options.AddPolicy("CanManageUsers", policy =>
        policy.RequireRole("Admin"));
});

// Registro de servicios.
builder.Services.AddScoped();
builder.Services.AddScoped();

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

// Endpoints de autenticación.
app.MapPost("/api/v1/auth/login", LoginAsync);
app.MapPost("/api/v1/auth/refresh", RefreshAsync);
app.MapPost("/api/v1/auth/logout", LogoutAsync);

// Endpoints protegidos por policies.
app.MapPost("/api/v1/posts", [Authorize(Policy = "CanCreatePosts")] async (CreatePostCommand command, IMediator mediator, CancellationToken ct) =>
{
    var result = await mediator.Send(command, ct);
    return result.IsSuccess
        ? Results.Created($"/api/v1/posts/{result.Value}", result.Value)
        : Results.BadRequest(result.Errors);
});

app.MapDelete("/api/v1/posts/{id:guid}", [Authorize(Policy = "CanEditAnyPost")] async (Guid id, IMediator mediator, CancellationToken ct) =>
{
    var result = await mediator.Send(new DeletePostCommand(id), ct);
    return result.IsSuccess ? Results.NoContent() : Results.NotFound();
});

app.Run();

// Métodos de endpoint extraídos para claridad.
static async Task LoginAsync(LoginCommand command, IAuthService authService, HttpContext context)
{
    var result = await authService.LoginAsync(command, context.RequestAborted);
    if (!result.IsSuccess) return Results.Unauthorized();
    AppendRefreshTokenCookie(context, result.RefreshToken!);
    return Results.Ok(new { result.AccessToken });
}

static async Task RefreshAsync(IAuthService authService, HttpContext context)
{
    if (!context.Request.Cookies.TryGetValue("refreshToken", out var refreshToken))
        return Results.Unauthorized();

    var result = await authService.RefreshAsync(refreshToken, context.RequestAborted);
    if (!result.IsSuccess) return Results.Unauthorized();

    AppendRefreshTokenCookie(context, result.RefreshToken!);
    return Results.Ok(new { result.AccessToken });
}

static async Task LogoutAsync(IAuthService authService, HttpContext context)
{
    if (context.Request.Cookies.TryGetValue("refreshToken", out var refreshToken))
        await authService.LogoutAsync(refreshToken, context.RequestAborted);

    context.Response.Cookies.Delete("refreshToken");
    return Results.Ok();
}

static void AppendRefreshTokenCookie(HttpContext context, string refreshToken)
{
    context.Response.Cookies.Append("refreshToken", refreshToken, new CookieOptions
    {
        HttpOnly = true,
        Secure = true,
        SameSite = SameSiteMode.Strict,
        Expires = DateTime.UtcNow.AddDays(7)
    });
}

4.6. Seeding de usuarios

El seeder crea tres usuarios iniciales con roles distintos y contraseñas hasheadas con BCrypt. Las contraseñas son solo para desarrollo.

// Cms.Infrastructure/Persistence/Seeders/UserSeeder.cs
public static class UserSeeder
{
    public static async Task SeedAsync(ApplicationDbContext context)
    {
        if (await context.Users.AnyAsync()) return;

        var admin = User.Create("admin@cms.local", "Administrador",
            BCrypt.Net.BCrypt.HashPassword("Admin123!", workFactor: 12),
            [Role.Admin, Role.Editor]);

        var editor = User.Create("editor@cms.local", "Editor Principal",
            BCrypt.Net.BCrypt.HashPassword("Editor123!", workFactor: 12),
            [Role.Editor]);

        var author = User.Create("author@cms.local", "Autor Invitado",
            BCrypt.Net.BCrypt.HashPassword("Author123!", workFactor: 12),
            [Role.Author]);

        context.Users.AddRange(admin, editor, author);
        await context.SaveChangesAsync();
    }
}

5. Buenas prácticas

  • Configura JWT desde una sección dedicada y lee el secreto de variables de entorno.
  • Define policies con nombres descriptivos en lugar de hardcodear roles en endpoints.
  • Usa BCrypt o PasswordHasher para hashear contraseñas.
  • Almacena refresh tokens como HttpOnly Secure cookies.
  • Implementa rotation y revocación de refresh tokens.
  • Guarda el hash del refresh token en la base de datos.
  • Testea los endpoints protegidos con y sin token, y con roles incorrectos.

6. Errores habituales

Incorrecto: secretos en appsettings sin protección

// ❌ Mal: nunca subas esto.
{
  "JwtSettings": {
    "Secret": "mi-clave-secreta"
  }
}

Correcto: user-secrets o variables de entorno

# ✅ Bien: user-secrets en desarrollo.
dotnet user-secrets init --project Cms.Api
dotnet user-secrets set --project Cms.Api "JwtSettings:Secret" "clave-secreta-de-32-bytes-min!"

Incorrecto: refresh token en body de la respuesta

// ❌ Mal: expuesto a XSS si el cliente lo guarda en localStorage.
return Results.Ok(new { AccessToken, RefreshToken });

Correcto: HttpOnly Secure cookie

// ✅ Bien: cookie inaccesible desde JavaScript.
context.Response.Cookies.Append("refreshToken", refreshToken, new CookieOptions
{
    HttpOnly = true,
    Secure = true,
    SameSite = SameSiteMode.Strict
});

Implementa un endpoint GET /api/v1/users/me que devuelva el perfil del usuario autenticado. Luego, añade un endpoint PUT /api/v1/users/me/password que permita cambiar la contraseña propia. 9. Resumen

  • El CMS ahora tiene autenticación JWT con roles Admin, Editor y Author.
  • La infraestructura implementa IJwtService y IAuthService; la API solo configura el middleware.
  • Las policies centralizan la autorización y evitan roles hardcodeados.
  • Los refresh tokens usan rotation, revocación y HttpOnly Secure cookies.
  • Se sembraron usuarios con contraseñas hasheadas mediante BCrypt.
  • Los endpoints críticos están protegidos por rol y por policy.

10. Preguntas frecuentes

¿Dónde conviene guardar el secreto JWT en el CMS?

En producción, en Azure Key Vault, AWS Secrets Manager o variables de entorno. En desarrollo, dotnet user-secrets es suficiente.

¿Por qué no usamos Identity en el CMS?

El CMS es una API headless con un modelo de dominio propio. Custom JWT nos da más control sobre usuarios, roles y refresh tokens sin arrastrar las tablas de Identity.

¿Cómo pruebo endpoints protegidos en integración?

Con WebApplicationFactory: crea un token de prueba con JwtService usando la misma clave configurada en el test, y envíalo en el header Authorization: Bearer ....
