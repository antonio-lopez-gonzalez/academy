JWT: estructura, firma y expiración

Módulo 11 · Autenticación y autorización35 min

1 · Introducción

Un JSON Web Token (JWT) es un estándar abierto (RFC 7519) para representar claims de forma compacta y segura entre dos partes. Es la forma más común de transportar identidad en APIs REST modernas.

En esta lección aprenderemos a crear y validar JWTs desde cero con .NET 8, entendiendo exactamente qué hay dentro de cada token y por qué la firma es indispensable.

¿Qué problema resuelve?

Permite que un cliente demuestre su identidad ante la API sin enviar usuario y contraseña en cada request. El servidor firma la información y el cliente la presenta en cada llamada.

Errores típicos

  • Guardar secretos en código fuente o appsettings.json sin cifrar.
  • Tokens que nunca expiran o con expiraciones de varios días.
  • Enviar información sensible (tarjetas, contraseñas) en los claims.
  • Validar solo la firma pero no el emisor, audiencia o expiración.
  • Usar algoritmo none o claves débiles.

2 · Teoría

Estructura de un JWT

Un JWT tiene tres partes separadas por puntos:

xxxxx.yyyyy.zzzzz
│      │      └──── Firma (Signature)
│      └─────────── Payload (Claims)
└────────────────── Header

Cada parte se codifica en Base64Url, una variante de Base64 segura para URLs (sin =, + ni /).

Header

Indica el algoritmo y el tipo de token:

{
  "alg": "HS256",
  "typ": "JWT"
}

Payload (Claims)

Contiene declaraciones sobre el usuario y el token. Existen claims registrados, públicos y privados.

  • sub (subject): identificador del usuario.
  • name: nombre del usuario.
  • role: rol del usuario (o roles en .NET).
  • email: correo electrónico.
  • iss (issuer): quién emitió el token.
  • aud (audience): para quién está destinado.
  • iat (issued at): momento de emisión.
  • nbf (not before): momento a partir del cual es válido.
  • exp (expiration): momento de expiración en segundos desde epoch.
  • jti (JWT ID): identificador único del token.

Firma

La firma garantiza que el token no ha sido modificado. Se calcula concatenando header y payload codificados, y aplicando HMAC-SHA256 con un secreto compartido:

HMACSHA256(base64Url(header) + "." + base64Url(payload), secret)

El secreto es la clave del reino

Cualquiera que conozca el secreto puede emitir tokens válidos. Nunca lo subas a GitHub. En producción usa variables de entorno, Azure Key Vault o AWS Secrets Manager.

JWT vs sesión

Sesión server-sideJWT
Estado almacenado en servidorEstado autocontenido en el token
Requiere buscar sesión en cada requestEl servidor solo valida firma y claims
Invalidación inmediataInvalidación más compleja (revocación, TTL corto)
Escalabilidad limitadaEscalabilidad horizontal natural

3 · Ejemplo mínimo

Crearemos un proyecto de consola que genera y valida un JWT con HMAC-SHA256.

# Crear proyecto de consola
mkdir ejemplos/m11-auth && cd ejemplos/m11-auth
dotnet new console -n JwtBasics -o JwtBasics
cd JwtBasics

# Instalar paquete para manejo de JWT
dotnet add package System.IdentityModel.Tokens.Jwt --version 7.5.1

# Ejecutar
dotnet run
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.IdentityModel.Tokens;

// ----------------------------------------------------------------
// 1. CONFIGURAR LA CLAVE DE FIRMA
// ----------------------------------------------------------------
// En producción este secreto viene de una variable de entorno.
const string secretKey = "una-clave-super-secreta-de-32bytes!";

// SecurityKey representa la clave simétrica usada para HMAC-SHA256.
var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secretKey));

// ----------------------------------------------------------------
// 2. DEFINIR LOS CLAIMS
// ----------------------------------------------------------------
// Los claims son afirmaciones sobre el usuario. Nunca guardes datos
// sensibles como contraseñas o tarjetas aquí.
var claims = new[]
{
    new Claim(JwtRegisteredClaimNames.Sub, "user-123"),
    new Claim(JwtRegisteredClaimNames.Name, "Ana García"),
    new Claim(JwtRegisteredClaimNames.Email, "ana@example.com"),
    new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
    new Claim(ClaimTypes.Role, "Author"),
    new Claim("permissions", "posts:read posts:write")
};

// ----------------------------------------------------------------
// 3. CREAR LAS CREDENCIALES DE FIRMA
// ----------------------------------------------------------------
var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

// ----------------------------------------------------------------
// 4. CONSTRUIR EL TOKEN
// ----------------------------------------------------------------
var tokenDescriptor = new SecurityTokenDescriptor
{
    Subject = new ClaimsIdentity(claims),
    Expires = DateTime.UtcNow.AddHours(2),
    Issuer = "MiApiDotNet",
    Audience = "MiClienteSpa",
    SigningCredentials = credentials
};

var handler = new JwtSecurityTokenHandler();
var token = handler.CreateToken(tokenDescriptor);
var tokenString = handler.WriteToken(token);

Console.WriteLine("Token JWT generado:");
Console.WriteLine(tokenString);

// ----------------------------------------------------------------
// 5. VALIDAR EL TOKEN
// ----------------------------------------------------------------
var validationParameters = new TokenValidationParameters
{
    ValidateIssuer = true,
    ValidateAudience = true,
    ValidateLifetime = true,
    ValidateIssuerSigningKey = true,
    ValidIssuer = "MiApiDotNet",
    ValidAudience = "MiClienteSpa",
    IssuerSigningKey = key,
    ClockSkew = TimeSpan.Zero // Sin tolerancia por defecto; prueba ajustarlo.
};

try
{
    var principal = handler.ValidateToken(tokenString, validationParameters, out var validatedToken);
    Console.WriteLine("Token válido. Claims:");
    foreach (var claim in principal.Claims)
    {
        Console.WriteLine($"  {claim.Type}: {claim.Value}");
    }
}
catch (SecurityTokenException ex)
{
    Console.WriteLine($"Token inválido: {ex.Message}");
}

¿Por qué ClockSkew?

Por defecto, .NET permite 5 minutos de desfase para compensar diferencias de reloj entre servidores. En tests locales puedes ponerlo a TimeSpan.Zero, pero en producción deja el valor por defecto.

4 · Ejemplo real

En una API profesional no generamos el token en un console. El secreto se lee de configuración, se inyecta un servicio y se expone un endpoint POST /auth/login.

// JwtSettings.cs
public sealed class JwtSettings
{
    public required string Secret { get; init; }
    public required string Issuer { get; init; }
    public required string Audience { get; init; }
    public int ExpirationHours { get; init; } = 2;
}

// IJwtService.cs
public interface IJwtService
{
    string GenerateToken(Guid userId, string email, string name, string[] roles);
}

// JwtService.cs
public sealed class JwtService(IOptions options) : IJwtService
{
    private readonly JwtSettings _settings = options.Value;

    public string GenerateToken(Guid userId, string email, string name, string[] roles)
    {
        var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_settings.Secret));
        var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

        var claims = new List
        {
            new(JwtRegisteredClaimNames.Sub, userId.ToString()),
            new(JwtRegisteredClaimNames.Email, email),
            new(JwtRegisteredClaimNames.Name, name),
            new(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString())
        };

        foreach (var role in roles)
        {
            claims.Add(new Claim(ClaimTypes.Role, role));
        }

        var tokenDescriptor = new SecurityTokenDescriptor
        {
            Subject = new ClaimsIdentity(claims),
            Expires = DateTime.UtcNow.AddHours(_settings.ExpirationHours),
            Issuer = _settings.Issuer,
            Audience = _settings.Audience,
            SigningCredentials = credentials
        };

        var handler = new JwtSecurityTokenHandler();
        return handler.WriteToken(handler.CreateToken(tokenDescriptor));
    }
}
// Program.cs
using Microsoft.AspNetCore.Authentication.JwtBearer;

var builder = WebApplication.CreateBuilder(args);

// Lee la configuración de JWT desde appsettings.
builder.Services.Configure(builder.Configuration.GetSection("JwtSettings"));

// Configura autenticación JWT.
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        var settings = builder.Configuration.GetSection("JwtSettings").Get()!;
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidIssuer = settings.Issuer,
            ValidAudience = settings.Audience,
            IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(settings.Secret))
        };
    });

builder.Services.AddAuthorization();
builder.Services.AddScoped();

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

app.MapPost("/auth/login", (LoginRequest request, IJwtService jwtService) =>
{
    // En una app real, validarías hash de contraseña.
    var token = jwtService.GenerateToken(Guid.NewGuid(), request.Email, request.Name, ["Author"]);
    return Results.Ok(new { Token = token });
});

app.MapGet("/admin-only", [Authorize(Roles = "Admin")] () => "Secreto");

app.Run();

public record LoginRequest(string Email, string Name, string Password);
// appsettings.json (solo desarrollo)
{
  "JwtSettings": {
    "Secret": "clave-32-bytes-minimo-requerida!",
    "Issuer": "CmsApi",
    "Audience": "CmsSpa",
    "ExpirationHours": 2
  }
}

Longitud mínima de la clave

Para HMAC-SHA256 la clave debe tener al menos 256 bits (32 bytes). Si la clave es más corta, JwtSecurityTokenHandler lanzará una excepción.

5 · Buenas prácticas

  • Almacena el secreto en variables de entorno o un vault, nunca en el código fuente.
  • Usa claves de 32 bytes o más para HMAC-SHA256.
  • Establece expiraciones cortas: 15 minutos para access tokens, 2 horas como máximo.
  • Valida siempre issuer, audience, lifetime y signing key.
  • No incluyas datos sensibles en los claims: el payload es legible tras decodificar Base64Url.
  • Usa ClaimTypes.Role si vas a usar [Authorize(Roles = "...")]; alternativamente, configura RoleClaimType.
  • Asigna un jti único por token para facilitar auditoría y revocación.
  • Usa HTTPS siempre; nunca envíes JWT por HTTP en producción.
  • Prefiere refresh tokens para mantener sesiones largas sin aumentar el tiempo de vida del access token.

6 · Errores habituales

Incorrecto: clave corta en appsettings

// ❌ Mal: clave de 10 bytes y en configuración sin cifrar.
{
  "JwtSettings": {
    "Secret": "12345"
  }
}

Correcto: clave de 32+ bytes desde entorno

// ✅ Bien: leer de variable de entorno o user-secrets.
var secret = builder.Configuration["JwtSettings:Secret"]
    ?? throw new InvalidOperationException("JWT secret no configurado.");

if (Encoding.UTF8.GetBytes(secret).Length < 32)
{
    throw new InvalidOperationException("El secreto JWT debe tener al menos 32 bytes.");
}

Incorrecto: token sin expiración

// ❌ Mal: token que nunca expira.
new SecurityTokenDescriptor
{
    Expires = null
};

Correcto: token con expiración explícita

// ✅ Bien: access token de corta duración.
Expires = DateTime.UtcNow.AddMinutes(15)

Incorrecto: no validar issuer ni audience

// ❌ Mal: aceptar cualquier token firmado.
TokenValidationParameters = new()
{
    ValidateIssuer = false,
    ValidateAudience = false,
    ValidateLifetime = false
};

Correcto: validar todo

// ✅ Bien: validar issuer, audience, lifetime y clave.
TokenValidationParameters = new()
{
    ValidateIssuer = true,
    ValidateAudience = true,
    ValidateLifetime = true,
    ValidateIssuerSigningKey = true,
    ValidIssuer = settings.Issuer,
    ValidAudience = settings.Audience,
    IssuerSigningKey = key
};

9 · Resumen

  • Un JWT está compuesto por header, payload y firma, separados por puntos.
  • El payload contiene claims: identidad, roles, expiración, emisor y audiencia.
  • La firma usa HMAC-SHA256 con un secreto compartido; el receptor debe validarla.
  • JwtSecurityTokenHandler permite crear y validar tokens en .NET.
  • La clave debe tener al menos 32 bytes y almacenarse fuera del código fuente.
  • Los tokens deben expirar y no contener datos sensibles.
  • En ASP.NET Core, AddJwtBearer configura automáticamente la validación.

10 · Preguntas frecuentes

¿JWT es cifrado?

No. El payload es legible tras decodificar Base64Url. Es firmado, no cifrado. Si necesitas ocultar datos, usa JWE (JSON Web Encryption) en lugar de JWT.

¿Qué longitud debe tener el secreto?

Para HMAC-SHA256, al menos 32 bytes (256 bits). Para HMAC-SHA384, 48 bytes; para HMAC-SHA512, 64 bytes.

¿Dónde almaceno el secreto en producción?

En variables de entorno, Azure Key Vault, AWS Secrets Manager, HashiCorp Vault o similar. Nunca en el repositorio ni en appsettings.json desprotegido.

¿Puedo usar RSA o ECDsa en lugar de HMAC?

Sí. HMAC es simétrico y rápido para el mismo emisor/receptor. RSA/ECDs son asimétricos y útiles cuando el emisor y el validador son servidores distintos (por ejemplo, Identity Server).

¿Por qué usar ClaimTypes.Role?

ASP.NET Core busca roles por defecto en el claim http://schemas.microsoft.com/ws/2008/06/identity/claims/role, que es lo que representa ClaimTypes.Role. Si usas un claim personalizado como "role", debes configurar RoleClaimType = "role".
