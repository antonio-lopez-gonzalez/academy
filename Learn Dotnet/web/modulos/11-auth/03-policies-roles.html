Policies, roles y claims

Módulo 11 · Autenticación y autorización30 min

1 · Introducción

Autenticar a un usuario es solo la mitad del problema. La otra mitad es decidir qué puede hacer una vez dentro. .NET 8 ofrece tres mecanismas de autorización: roles, claims y policies. Entender cuándo usar cada uno es clave para diseñar sistemas seguros y mantenibles.

En esta lección veremos cómo proteger endpoints con [Authorize], cómo crear policies basadas en claims y cómo evaluar autorización imperativamente desde código.

¿Qué problema resuelve?

Restringir el acceso a recursos y operaciones según la identidad del usuario. Roles son simples; claims y policies permiten reglas más finas y expresivas.

Errores típicos

  • Usar roles para todo, creando decenas de roles híbridos como AdminEditor.
  • Ignorar que los claims son más flexibles que los roles.
  • Hardcodear comprobaciones de permisos en controllers.
  • No proteger endpoints sensibles porque "solo lo usan admins".
  • Mezclar autenticación y autorización en el mismo middleware.

2 · Teoría

Autenticación vs autorización

  • Autenticación: ¿quién eres? (login, JWT, cookie).
  • Autorización: ¿qué puedes hacer? (roles, claims, policies).

En ASP.NET Core, UseAuthentication debe ejecutarse antes que UseAuthorization. Sin autenticación, no hay usuario contra quien autorizar.

Roles

Un rol es un grupo lógico de usuarios. Es fácil de entender pero rígido:

[Authorize(Roles = "Admin")]

Claims

Un claim es una afirmación sobre el usuario. Puede representar cualquier cosa: email, fecha de nacimiento, permisos, departamento, etc. Los claims son más flexibles que los roles.

new Claim("permission", "posts:write")
new Claim("department", "engineering")
new Claim("country", "ES")

Policies

Una policy agrupa uno o varios requisitos. Puede exigir claims, roles, requisitos personalizados o una combinación. Es el mecanismo más limpio y extensible.

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanEditPosts", policy =>
        policy.RequireClaim("permission", "posts:write")
              .RequireRole("Editor", "Admin"));
});

Handlers de autorización personalizados

Cuando la lógica no depende solo de claims, implementamos un IAuthorizationHandler. Por ejemplo: "solo el autor del post puede editarlo".

Autorización imperativa

A veces no podemos decidir la autorización hasta que consultamos la base de datos. Usamos IAuthorizationService en el controller o handler.

Preferencia

Prefiere policies sobre roles hardcodeados. Los roles son útiles para grupos grandes; los claims y policies son mejores para permisos granulares y cambiantes.

3 · Ejemplo mínimo

Protegeremos un endpoint con roles, claims y policies en una API mínima.

# Crear API con autenticación JWT
dotnet new web -n PoliciesDemo -o PoliciesDemo
cd PoliciesDemo
dotnet add package Microsoft.AspNetCore.Authentication.JwtBearer --version 8.0.0
dotnet run
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.AspNetCore.Authorization;
using System.Security.Claims;
using System.Text;

var builder = WebApplication.CreateBuilder(args);

var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes("clave-de-32-bytes-minimo-req!!"));

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = false,
            ValidateAudience = false,
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = key,
            ValidateLifetime = true,
            ClockSkew = TimeSpan.Zero
        };
    });

builder.Services.AddAuthorization(options =>
{
    // Policy basada en claim.
    options.AddPolicy("CanReadPosts", policy =>
        policy.RequireClaim("permission", "posts:read"));

    // Policy basada en claim y rol.
    options.AddPolicy("CanDeletePosts", policy =>
        policy.RequireRole("Admin")
              .RequireClaim("permission", "posts:delete"));
});

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

// Endpoint abierto.
app.MapGet("/", () => "Público");

// Endpoint que requiere autenticación.
app.MapGet("/profile", [Authorize] (ClaimsPrincipal user) =>
    $"Hola {user.FindFirst(ClaimTypes.Name)?.Value}");

// Endpoint basado en roles.
app.MapGet("/admin", [Authorize(Roles = "Admin")] () => "Solo Admin");

// Endpoint basado en policies.
app.MapGet("/posts", [Authorize(Policy = "CanReadPosts")] () => "Lista de posts")
   .RequireAuthorization("CanReadPosts");

app.MapDelete("/posts/{id}", [Authorize(Policy = "CanDeletePosts")] (Guid id) =>
    $"Post {id} eliminado");

app.Run();

ClaimsPrincipal

Después de la autenticación, ASP.NET Core construye un ClaimsPrincipal a partir de los claims del token. Puedes inyectarlo como parámetro o usar User en un controller.

4 · Ejemplo real

En el CMS necesitamos una regla especial: un autor puede editar sus propios posts, pero un editor o admin puede editar cualquier post. Esto requiere un handler de autorización personalizado.

// IAuthorizationRequirement vacío; sirve como marcador.
public sealed class IsAuthorRequirement : IAuthorizationRequirement
{
}

// Handler que consulta el autor del post.
public sealed class IsAuthorHandler(IHttpContextAccessor httpContextAccessor, IPostRepository postRepository)
    : AuthorizationHandler
{
    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        IsAuthorRequirement requirement)
    {
        // El usuario debe estar autenticado.
        var userIdClaim = context.User.FindFirst(ClaimTypes.NameIdentifier);
        if (userIdClaim is null || !Guid.TryParse(userIdClaim.Value, out var userId))
        {
            return;
        }

        // Extraemos el id del post desde la ruta.
        var httpContext = httpContextAccessor.HttpContext;
        if (httpContext is null)
        {
            return;
        }

        if (!httpContext.Request.RouteValues.TryGetValue("id", out var idValue)
            || !Guid.TryParse(idValue?.ToString(), out var postId))
        {
            return;
        }

        var post = await postRepository.GetByIdAsync(postId, httpContext.RequestAborted);
        if (post is null)
        {
            return;
        }

        if (post.AuthorId == userId || context.User.IsInRole("Admin") || context.User.IsInRole("Editor"))
        {
            context.Succeed(requirement);
        }
    }
}
// Program.cs
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("IsAuthorOrAdmin", policy =>
        policy.Requirements.Add(new IsAuthorRequirement()));
});

builder.Services.AddSingleton();
builder.Services.AddHttpContextAccessor();

// ...

app.MapPut("/api/v1/posts/{id:guid}", async (
    Guid id,
    UpdatePostCommand command,
    IMediator mediator,
    CancellationToken ct) =>
{
    // La autorización ya se validó por la policy.
    var result = await mediator.Send(command with { Id = id }, ct);
    return result.IsSuccess ? Results.NoContent() : Results.NotFound();
})
.WithName("UpdatePost")
.RequireAuthorization("IsAuthorOrAdmin");

Autorización imperativa

public async Task DeletePost(
    Guid id,
    IAuthorizationService authorizationService,
    HttpContext httpContext,
    IPostRepository postRepository,
    CancellationToken ct)
{
    var post = await postRepository.GetByIdAsync(id, ct);
    if (post is null)
    {
        return Results.NotFound();
    }

    var authorizationResult = await authorizationService.AuthorizeAsync(
        httpContext.User,
        post,
        "CanDeletePost");

    if (!authorizationResult.Succeeded)
    {
        return Results.Forbid();
    }

    await postRepository.DeleteAsync(post, ct);
    return Results.NoContent();
}

No dupliques autorización

Si ya proteges un endpoint con [Authorize(Policy = "...")], no repitas la misma lógica dentro del handler. La duplicación es un riesgo de inconsistencias.

5 · Buenas prácticas

  • Usa policies en lugar de roles hardcodeados para reglas reutilizables.
  • Prefiere claims sobre roles cuando necesitas permisos granulares.
  • Centraliza la configuración de policies en Program.cs o un método de extensión.
  • Usa handlers personalizados para reglas que dependen de datos del request o de la base de datos.
  • Protege todos los endpoints por defecto y abre explícitamente los públicos.
  • No confíes en claims sin firmar; siempre autentica antes de autorizar.
  • Usa [AllowAnonymous] con cuidado y solo en endpoints realmente públicos.
  • Testea las policies con unit tests o integration tests.

6 · Errores habituales

Incorrecto: comprobar roles manualmente en el controller

// ❌ Mal: lógica dispersa y difícil de testear.
if (!User.IsInRole("Admin"))
{
    return Results.Forbid();
}

Correcto: declarar la policy en el endpoint

// ✅ Bien: la autorización vive en el pipeline, no en el handler.
app.MapDelete("/posts/{id}", [Authorize(Policy = "CanDeletePosts")] (Guid id) => ...);

Incorrecto: olvidar UseAuthentication

// ❌ Mal: Authorization sin Authentication no tiene usuario contra quien autorizar.
app.UseAuthorization();
app.UseAuthentication();

Correcto: orden correcto

// ✅ Bien: primero autenticamos, luego autorizamos.
app.UseAuthentication();
app.UseAuthorization();

Incorrecto: roles para permisos muy granulares

// ❌ Mal: explosión de roles.
[Authorize(Roles = "AdminPostEditorCommentModerator")]

Correcto: claims con policy

// ✅ Bien: claims granulares y policies descriptivas.
options.AddPolicy("CanModerateComments", policy =>
    policy.RequireClaim("permission", "comments:moderate"));

Implementa un handler de autorización que permita editar un recurso solo si el usuario es el propietario o si pertenece al departamento Legal. El handler debe recibir el recurso como parámetro de contexto y usar IAuthorizationService para evaluarlo imperativamente. No lo resuelvas ahora; inténtalo primero.

9 · Resumen

  • Autenticación determina quién es el usuario; autorización determina qué puede hacer.
  • Los roles son grupos simples pero rígidos.
  • Los claims permiten afirmaciones flexibles sobre el usuario.
  • Las policies agrupan requisitos y son el mecanismo más limpio.
  • Los handlers personalizados permiten reglas basadas en datos del request.
  • IAuthorizationService permite autorización imperativa en código.
  • El orden correcto del pipeline es UseAuthentication antes que UseAuthorization.

10 · Preguntas frecuentes

¿Puedo combinar roles y claims en una policy?

Sí. Una policy puede exigir roles, claims, requisitos personalizados o combinaciones de todos ellos.

¿Qué pasa si pongo [Authorize] sin parámetros?

Exige que el usuario esté autenticado, sin importar roles o claims. Es útil para endpoints que solo necesitan saber quién es el usuario.

¿Cómo accedo a los claims en un Minimal API?

Inyecta ClaimsPrincipal como parámetro del endpoint o usa HttpContext.User.

¿Qué diferencia hay entre RequireClaim y RequireAssertion?

RequireClaim exige un claim con un valor específico. RequireAssertion permite evaluar una expresión lambda sobre el ClaimsPrincipal, por ejemplo, para comparar fechas o múltiples claims.

¿Puedo usar [Authorize] en un Minimal API?

Sí, como atributo en el método lambda o con RequireAuthorization("PolicyName") en el endpoint.
