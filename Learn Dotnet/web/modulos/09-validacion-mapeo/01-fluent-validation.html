FluentValidation

Módulo 9 · Validación y mapeo35 min

1. Introducción

En esta lección aprenderemos a usar FluentValidation, la librería más popular de .NET para validar reglas de negocio de forma declarativa, mantenible y testable.

Veremos por qué la validación debe vivir en la capa de aplicación y no en los modelos de dominio ni en los controladores, cómo construir validadores con AbstractValidator, cómo encadenar reglas con RuleFor, cómo integrarlo con ASP.NET Core y cómo devolver errores de validación al cliente en un formato profesional.

Objetivos de la lección

  • Entender por qué la validación cruzada de reglas de negocio no debe vivir en Data Annotations.
  • Construir validadores con AbstractValidator<T>.
  • Usar reglas condicionales con When y Unless.
  • Validar propiedades anidadas con SetValidator.
  • Integrar FluentValidation con MediatR y ASP.NET Core.

2. Teoría

2.1. ¿Dónde debe vivir la validación?

En ASP.NET Core existe System.ComponentModel.DataAnnotations. Es útil para validaciones superficiales: campo requerido, longitud máxima, rango numérico. Sin embargo, las validaciones de negocio reales rara vez se limitan a eso:

  • Verificar que un email no esté duplicado en la base de datos.
  • Validar que un post no tenga un slug repetido.
  • Comprobar que un autor tenga permisos para publicar en una categoría.

Data Annotations no puede acceder a servicios inyectados, no es testable unitariamente de forma limpia y mezcla reglas de API con reglas de negocio. FluentValidation resuelve todo esto:

  • Validadores desacoplados que reciben dependencias por constructor.
  • Reglas expresivas, encadenadas y reutilizables.
  • Integración con MediatR para ejecutar validación antes de cada handler.
  • Separación clara entre la capa de aplicación y la de presentación.

2.2. Conceptos clave

ConceptoDescripción
AbstractValidator<T>Clase base de todo validador. Define las reglas para un tipo de request.
RuleFor(x => x.Propiedad)Selecciona la propiedad a validar y devuelve un builder encadenable.
NotEmpty, MaximumLength, EmailAddressReglas predefinidas de la librería.
Must(expr) / MustAsync(expr)Reglas personalizadas con funciones o funciones asíncronas.
When(predicado) / Unless(predicado)Reglas condicionales que solo se ejecutan si se cumple una condición.
SetValidator(child)Valida una propiedad anidada usando otro validador.
ValidationResultResultado de la validación con IsValid y Errors.

2.3. Comparación con otras tecnologías

En Node.js se usa frecuentemente Joi o Zod. En Java se usa Jakarta Bean Validation con anotaciones. FluentValidation es similar a Joi en su estilo encadenable, pero se integra de forma nativa con el contenedor de DI de .NET, lo que permite resolver servicios dentro de las validaciones.

Consejo profesional

La validación de entrada es una regla de aplicación, no de API. Usa FluentValidation en el handler de MediatR o en un pipeline de comportamiento. El controlador solo debe recibir el resultado y devolverlo al cliente.

3. Ejemplo mínimo

Crearemos un validador para un DTO de creación de categoría. Necesitamos:

  1. Instalar el paquete FluentValidation.
  2. Crear una clase que herede de AbstractValidator<T>.
  3. Definir las reglas en el constructor.
  4. Validar una instancia.
dotnet add package FluentValidation --version 11.9.0
using FluentValidation;

// DTO de entrada que representa la solicitud de creación de una categoría.
public sealed class CreateCategoryRequest
{
    public string Name { get; set; } = string.Empty;
    public string? Description { get; set; }
}

// Validador que contiene las reglas de negocio para el DTO.
public sealed class CreateCategoryRequestValidator : AbstractValidator<CreateCategoryRequest>
{
    public CreateCategoryRequestValidator()
    {
        // El nombre es obligatorio y tiene longitud limitada.
        RuleFor(x => x.Name)
            .NotEmpty().WithMessage("El nombre de la categoría es obligatorio.")
            .MaximumLength(100).WithMessage("El nombre no puede superar los 100 caracteres.");

        // La descripción es opcional, pero si se envía no debe superar los 500 caracteres.
        RuleFor(x => x.Description)
            .MaximumLength(500).WithMessage("La descripción no puede superar los 500 caracteres.")
            .When(x => !string.IsNullOrEmpty(x.Description));
    }
}

class Program
{
    static async Task Main(string[] args)
    {
        var validator = new CreateCategoryRequestValidator();

        var request = new CreateCategoryRequest
        {
            Name = "",
            Description = new string('a', 501)
        };

        var result = await validator.ValidateAsync(request);

        if (!result.IsValid)
        {
            foreach (var error in result.Errors)
            {
                Console.WriteLine($"{error.PropertyName}: {error.ErrorMessage}");
            }
        }
    }
}

Este ejemplo compila y ejecuta con dotnet run. La salida mostrará dos errores: uno por el nombre vacío y otro por la descripción demasiado larga.

4. Ejemplo real

En una aplicación profesional usamos MediatR y un pipeline de comportamiento para ejecutar la validación antes de cada handler. Así, el propio handler se mantiene libre de validaciones.

4.1. Comando y validador

using FluentValidation;

public sealed record CreatePostCommand(
    string Title,
    string Slug,
    string? Content,
    Guid AuthorId,
    Guid CategoryId,
    IEnumerable<string> Tags) : IRequest<Result<Guid>>;

public sealed class CreatePostCommandValidator : AbstractValidator<CreatePostCommand>
{
    public CreatePostCommandValidator(ICategoryRepository categoryRepository)
    {
        RuleFor(x => x.Title)
            .NotEmpty().WithMessage("El título es obligatorio.")
            .MaximumLength(200).WithMessage("El título no puede superar los 200 caracteres.");

        RuleFor(x => x.Slug)
            .NotEmpty().WithMessage("El slug es obligatorio.")
            .Matches("^[a-z0-9]+(?:-[a-z0-9]+)*$")
            .WithMessage("El slug solo puede contener letras minúsculas, números y guiones.");

        RuleFor(x => x.AuthorId)
            .NotEmpty().WithMessage("El autor es obligatorio.");

        RuleFor(x => x.CategoryId)
            .NotEmpty().WithMessage("La categoría es obligatoria.");

        // Regla asíncrona que consulta el repositorio para verificar que la categoría existe.
        RuleFor(x => x.CategoryId)
            .MustAsync(async (categoryId, cancellation) =>
                await categoryRepository.ExistsAsync(categoryId, cancellation))
            .WithMessage("La categoría seleccionada no existe.");

        // Validación condicional: solo se aplica si hay contenido.
        RuleFor(x => x.Content)
            .MaximumLength(50000)
            .WithMessage("El contenido no puede superar los 50000 caracteres.")
            .When(x => !string.IsNullOrEmpty(x.Content));

        // Regla personalizada sobre la colección de tags.
        RuleFor(x => x.Tags)
            .Must(tags => tags.Distinct(StringComparer.OrdinalIgnoreCase).Count() == tags.Count())
            .WithMessage("No se permiten tags duplicados.")
            .When(x => x.Tags is not null);
    }
}

4.2. Pipeline de validación con MediatR

using FluentValidation;
using MediatR;

public sealed class ValidationBehavior<TRequest, TResponse> : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
    where TResponse : class
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public ValidationBehavior(IEnumerable<IValidator<TRequest>> validators)
    {
        _validators = validators;
    }

    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken cancellationToken)
    {
        if (!_validators.Any())
        {
            return await next();
        }

        var context = new ValidationContext<TRequest>(request);

        var validationResults = await Task.WhenAll(
            _validators.Select(v => v.ValidateAsync(context, cancellationToken)));

        var failures = validationResults
            .SelectMany(r => r.Errors)
            .Where(f => f is not null)
            .ToList();

        if (failures.Any())
        {
            throw new ValidationException(failures);
        }

        return await next();
    }
}

El pipeline intercepta cada request antes de llegar al handler. Si hay errores, lanza una ValidationException. Un middleware global de excepciones la captura y la convierte en un ValidationProblemDetails con código 400.

4.3. Integración con ASP.NET Core

using FluentValidation;

var builder = WebApplication.CreateBuilder(args);

// Registra automáticamente todos los AbstractValidator del assembly.
builder.Services.AddValidatorsFromAssembly(typeof(Program).Assembly);

builder.Services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssembly(typeof(Program).Assembly);
    cfg.AddBehavior(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));
});

var app = builder.Build();

app.MapPost("/api/v1/posts", async (CreatePostCommand command, IMediator mediator) =>
{
    var result = await mediator.Send(command);
    return result.IsSuccess
        ? Results.Created($"/api/v1/posts/{result.Value}", result.Value)
        : Results.BadRequest(result.Errors);
});

app.Run();

5. Buenas prácticas

  • Valida en la capa de aplicación. No dejes que la validación de negocio viva en el controlador o en los modelos de dominio.
  • Usa mensajes claros en español. El consumidor de la API debe entender inmediatamente qué ha fallado.
  • No accedas a la base de datos si las reglas triviales ya fallan. En FluentValidation se ejecutan las reglas en orden, pero evita consultas innecesarias cuando las reglas simples ya han fallado.
  • Usa validadores anidados para DTOs complejos. Esto mantiene cada validador enfocado y testable.
  • Testea tus validadores unitariamente. Son puras funciones de entrada-salida y muy fáciles de probar.
  • Prefiere ValidationException + middleware global para centralizar la respuesta de errores de validación.

Evita

No mezcles validación de entrada con lógica de negocio. Validar que una categoría existe es una regla de aplicación. Decidir que un post se publique automáticamente si el autor es editor es lógica de dominio y debe vivir en el handler.

6. Errores habituales

6.1. No usar ValidateAsync cuando hay reglas asíncronas

// MAL: Validate() ignora las reglas asíncronas.
var result = validator.Validate(request);

// BIEN:
var result = await validator.ValidateAsync(request);

6.2. Validar en el controlador

// MAL: el controlador se llena de lógica de validación.
app.MapPost("/posts", (CreatePostCommand command, IValidator<CreatePostCommand> validator) =>
{
    var result = validator.Validate(command);
    if (!result.IsValid) return Results.BadRequest(result.Errors);
    // ...
});

// BIEN: el pipeline se encarga automáticamente.
app.MapPost("/posts", async (CreatePostCommand command, IMediator mediator) =>
{
    var result = await mediator.Send(command);
    return result.Match(
        onSuccess: id => Results.Created($"/posts/{id}", id),
        onFailure: errors => Results.BadRequest(errors));
});

6.3. Mensajes genéricos sin contexto

// MAL:
RuleFor(x => x.Title).NotEmpty();

// BIEN: mensajes descriptivos y traducidos.
RuleFor(x => x.Title)
    .NotEmpty().WithMessage("El título es obligatorio.")
    .MaximumLength(200).WithMessage("El título no puede superar los {MaxLength} caracteres.");

7. Ejercicio guiado

Crea un validador para un comando de registro de usuario con las siguientes reglas:

  • Email: obligatorio, formato válido, máximo 150 caracteres.
  • Password: obligatorio, mínimo 8 caracteres, al menos una mayúscula, una minúscula y un número.
  • ConfirmPassword: debe coincidir con Password.
  • DisplayName: opcional, máximo 50 caracteres.
public sealed class RegisterUserCommandValidator : AbstractValidator<RegisterUserCommand>
{
    public RegisterUserCommandValidator()
    {
        RuleFor(x => x.Email)
            .NotEmpty().WithMessage("El email es obligatorio.")
            .EmailAddress().WithMessage("El formato del email no es válido.")
            .MaximumLength(150).WithMessage("El email no puede superar los 150 caracteres.");

        RuleFor(x => x.Password)
            .NotEmpty().WithMessage("La contraseña es obligatoria.")
            .MinimumLength(8).WithMessage("La contraseña debe tener al menos 8 caracteres.")
            .Matches(@"[A-Z]").WithMessage("La contraseña debe contener al menos una mayúscula.")
            .Matches(@"[a-z]").WithMessage("La contraseña debe contener al menos una minúscula.")
            .Matches(@"[0-9]").WithMessage("La contraseña debe contener al menos un número.");

        RuleFor(x => x.ConfirmPassword)
            .Equal(x => x.Password).WithMessage("Las contraseñas no coinciden.");

        RuleFor(x => x.DisplayName)
            .MaximumLength(50).WithMessage("El nombre visible no puede superar los 50 caracteres.")
            .When(x => !string.IsNullOrEmpty(x.DisplayName));
    }
}

Prueba el validador con un test unitario xUnit enviando un email vacío, una contraseña corta y contraseñas que no coincidan.

9. Resumen

  • FluentValidation permite expresar reglas de validación de forma limpia, declarativa y testable.
  • La validación de negocio debe vivir en la capa de aplicación, no en controladores ni en modelos de dominio.
  • Usa RuleFor, Must, MustAsync, When y SetValidator para cubrir casos reales.
  • MediatR + pipeline de validación centraliza la ejecución de validadores y mantiene los handlers limpios.
  • Los mensajes de error deben ser claros, traducidos y útiles para el cliente.

10. Preguntas frecuentes

¿Puedo usar FluentValidation junto con Data Annotations?

Sí, pero no es recomendable. Mezclar ambos dificulta el mantenimiento y divide las reglas entre dos sitios. Usa solo FluentValidation para la lógica de negocio.

¿Cómo se integra con Minimal APIs?

Manualmente inyectando el validador o, preferiblemente, usando MediatR. En Minimal APIs no existe el filtro de validación automática de MVC, por lo que el pipeline de MediatR es la solución más limpia.

¿Qué pasa con las reglas asíncronas?

Debes usar ValidateAsync. Si llamas a Validate síncrono, las reglas MustAsync se ignoran y pasarán desapercibidas.

¿Cómo traduzco los mensajes de error?

FluentValidation admite localización. Puedes usar WithMessage con una clave de recurso o configurar un LanguageManager personalizado. Para cursos en español, mantén los mensajes directamente en español en el código.

¿Debo validar también en el frontend?

La validación del frontend mejora la experiencia de usuario, pero nunca sustituye a la del backend. El servidor es la única fuente de verdad de las reglas de negocio.
