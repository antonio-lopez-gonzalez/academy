Result<T> con errores de validación

Módulo 9 · Validación y mapeo30 min

1 · Introducción

En esta lección aprenderemos a modelar el resultado de una operación de negocio sin usar excepciones para el flujo normal. Usaremos un tipo Result<T> que representa explícitamente si una operación fue exitosa o falló, y por qué.

Veremos cómo combinar errores de validación, cómo devolverlos desde handlers de MediatR, cómo mapearlos a ProblemDetails y cuándo preferir este patrón sobre lanzar excepciones.

Objetivos de la lección

  • Implementar un tipo Result<T> básico.
  • Modelar errores de validación como datos, no como excepciones.
  • Combinar múltiples errores en una sola respuesta.
  • Devolver Result<T> desde handlers de MediatR.
  • Comparar el patrón con el manejo de excepciones.

2 · Teoría

2.1. ¿Por qué usar Result?

En muchas aplicaciones, los errores de validación se lanzan como excepciones. Esto funciona, pero tiene problemas:

  • Las excepciones rompen el flujo de control y son costosas.
  • Con las excepciones, el tipo de retorno no expresa que puede fallar.
  • Es difícil acumular varios errores sin una estructura explícita.

El patrón Result<T> convierte el fallo en un valor más. El tipo de retorno del método dice explícitamente: "esto puede devolver un error". Esto mejora la legibilidad y el testing.

2.2. Diseño de Result<T>

La implementación mínima consta de dos estados: éxito y fallo. Cada uno contiene el valor correspondiente. Un error contiene un código y una descripción, lo que facilita la traducción y la depuración.

public sealed class Result<T>
{
    public bool IsSuccess { get; }
    public bool IsFailure => !IsSuccess;
    public T? Value { get; }
    public List<Error> Errors { get; }

    private Result(T value)
    {
        IsSuccess = true;
        Value = value;
        Errors = new List<Error>();
    }

    private Result(List<Error> errors)
    {
        IsSuccess = false;
        Errors = errors;
        Value = default;
    }

    public static Result<T> Success(T value) => new(value);
    public static Result<T> Failure(List<Error> errors) => new(errors);
    public static Result<T> Failure(Error error) => new(new List<Error> { error });
}

public sealed record Error(string Code, string Message);

2.3. Comparación con excepciones

AspectoExcepcionesResult<T>
Flujo esperadoRompe el flujoContinúa normalmente
TestabilidadRequiere Assert.ThrowsDevuelve un valor
Errores múltiplesDifícil de acumularFácil de combinar
ExpresividadEl tipo no indica falloEl tipo indica fallo
Errores técnicos gravesIdealNo usar

Regla de oro

Usa Result<T> para errores de dominio esperados: validación, reglas de negocio, autorización, recursos no encontrados. Reserva las excepciones para casos excepcionales: base de datos caída, errores de red imprevistos, bugs.

3 · Ejemplo mínimo

Implementaremos un validador que devuelve errores acumulados como un Result<T>.

public sealed class CreateCategoryRequest
{
    public string Name { get; set; } = string.Empty;
}

public sealed class CreateCategoryRequestValidator
{
    public Result<CreateCategoryRequest> Validate(CreateCategoryRequest request)
    {
        var errors = new List<Error>();

        if (string.IsNullOrWhiteSpace(request.Name))
        {
            errors.Add(new Error("Category.Name.Empty", "El nombre de la categoría es obligatorio."));
        }
        else if (request.Name.Length > 100)
        {
            errors.Add(new Error("Category.Name.TooLong", "El nombre no puede superar los 100 caracteres."));
        }

        return errors.Count == 0
            ? Result<CreateCategoryRequest>.Success(request)
            : Result<CreateCategoryRequest>.Failure(errors);
    }
}

class Program
{
    static void Main()
    {
        var validator = new CreateCategoryRequestValidator();
        var result = validator.Validate(new CreateCategoryRequest { Name = "" });

        if (result.IsFailure)
        {
            foreach (var error in result.Errors)
            {
                Console.WriteLine($"[{error.Code}] {error.Message}");
            }
        }
    }
}

Este ejemplo se ejecuta con dotnet run y muestra cómo los errores se modelan como datos, no como excepciones.

4 · Ejemplo real

4.1. Result pattern integrado con FluentValidation

En una aplicación profesional no renunciamos a FluentValidation. Lo que hacemos es adaptar sus errores a nuestro Result<T>.

using FluentValidation;
using FluentValidation.Results;

public static class ValidationResultExtensions
{
    // Convierte un FluentValidation.ValidationResult en un Result<T> fallido.
    public static Result<T> ToResult<T>(this ValidationResult validationResult, T value)
    {
        if (validationResult.IsValid)
        {
            return Result<T>.Success(value);
        }

        var errors = validationResult.Errors
            .Select(f => new Error(f.ErrorCode, f.ErrorMessage))
            .ToList();

        return Result<T>.Failure(errors);
    }
}

public sealed class CreatePostCommandHandler : IRequestHandler<CreatePostCommand, Result<Guid>>
{
    private readonly IPostRepository _postRepository;
    private readonly IValidator<CreatePostCommand> _validator;

    public CreatePostCommandHandler(
        IPostRepository postRepository,
        IValidator<CreatePostCommand> validator)
    {
        _postRepository = postRepository;
        _validator = validator;
    }

    public async Task<Result<Guid>> Handle(
        CreatePostCommand request,
        CancellationToken cancellationToken)
    {
        var validationResult = await _validator.ValidateAsync(request, cancellationToken);
        if (!validationResult.IsValid)
        {
            return validationResult.ToResult(Guid.Empty);
        }

        var slugExists = await _postRepository.ExistsBySlugAsync(request.Slug, cancellationToken);
        if (slugExists)
        {
            return Result<Guid>.Failure(
                new Error("Post.Slug.Duplicated", "Ya existe un post con ese slug."));
        }

        var post = new Post
        {
            Id = Guid.NewGuid(),
            Title = request.Title,
            Slug = request.Slug,
            Content = request.Content,
            CategoryId = request.CategoryId,
            AuthorId = request.AuthorId
        };

        await _postRepository.AddAsync(post, cancellationToken);
        return Result<Guid>.Success(post.Id);
    }
}

4.2. Mapeo a ProblemDetails

En la API, convertimos los errores de Result<T> en un ValidationProblemDetails con código 400, siguiendo el RFC 9457.

public static class ResultExtensions
{
    public static IResult ToHttpResult<T>(this Result<T> result)
    {
        if (result.IsSuccess)
        {
            return TypedResults.Ok(result.Value);
        }

        var errorsByProperty = result.Errors
            .GroupBy(e => e.Code.Split('.')[0])
            .ToDictionary(
                g => g.Key,
                g => g.Select(e => e.Message).ToArray());

        var problemDetails = new ValidationProblemDetails(errorsByProperty)
        {
            Status = StatusCodes.Status400BadRequest,
            Title = "Uno o más errores de validación han ocurrido.",
            Type = "https://tools.ietf.org/html/rfc7231#section-6.5.1"
        };

        return TypedResults.BadRequest(problemDetails);
    }
}

4.3. Endpoint limpio

app.MapPost("/api/v1/posts", async (
    CreatePostCommand command,
    IMediator mediator,
    CancellationToken cancellationToken) =>
{
    var result = await mediator.Send(command, cancellationToken);
    return result.ToHttpResult();
});

El endpoint no sabe nada de validación. Solo recibe un Result<Guid> y lo convierte en respuesta HTTP.

5 · Buenas prácticas

  • Modela los errores con código y mensaje. El código permite identificar el error y el mensaje es lo que verá el usuario.
  • Acumula errores de validación. Devolver un solo error por request frustra al usuario. Recopila todos los errores posibles antes de fallar.
  • No uses Result<T> para errores técnicos. Bases de datos caídas, errores de red o bugs deben lanzar excepciones.
  • Devuelve Result<T> desde handlers. Esto mantiene la lógica de negocio testable y expresiva.
  • Mapea los errores a ProblemDetails en la capa de API. La capa de aplicación no debe conocer HTTP.
  • Documenta los códigos de error. En OpenAPI, enumera los posibles errores de cada endpoint.

Evita

No lances excepciones para errores de validación esperados. Cada excepción capturada es un evento costoso. Si el usuario envía un email duplicado, eso es un flujo de negocio esperado, no un fallo del sistema.

6 · Errores habituales

6.1. Usar excepciones para errores de negocio

// MAL: rompe el flujo y dificulta los tests.
if (slugExists)
    throw new InvalidOperationException("Ya existe un post con ese slug.");

// BIEN: devuelve un resultado.
if (slugExists)
    return Result<Guid>.Failure(new Error("Post.Slug.Duplicated", "Ya existe un post con ese slug."));

6.2. No agrupar errores

// MAL: devuelve un error genérico sin detalles.
return Result<Guid>.Failure(new Error("ValidationError", "La solicitud no es válida."));

// BIEN: devuelve cada error con su propiedad y mensaje.
return Result<Guid>.Failure(errors);

6.3. Llamar a .Value sin comprobar IsSuccess

// PELIGROSO: puede devolver null o un valor por defecto.
var id = result.Value;

// BIEN:
if (result.IsSuccess)
    var id = result.Value;
else
    // manejar errores

6.4. Mezclar Result con excepciones en el mismo handler sin criterio

Define una política clara: Result<T> para errores de negocio esperados, excepciones para errores técnicos inesperados. No alternes ambos sin un patrón definido.

7 · Ejercicio guiado

Implementa un handler que registra un usuario y devuelve Result<Guid>. Debe acumular errores:

  • Email vacío o con formato incorrecto.
  • Contraseña con menos de 8 caracteres.
  • Email ya registrado en la base de datos.
public async Task<Result<Guid>> Handle(
    RegisterUserCommand request,
    CancellationToken cancellationToken)
{
    var errors = new List<Error>();

    if (string.IsNullOrWhiteSpace(request.Email))
        errors.Add(new Error("User.Email.Empty", "El email es obligatorio."));
    else if (!request.Email.Contains('@'))
        errors.Add(new Error("User.Email.Invalid", "El formato del email no es válido."));

    if (request.Password is null || request.Password.Length < 8)
        errors.Add(new Error("User.Password.TooShort", "La contraseña debe tener al menos 8 caracteres."));

    var existing = await _repository.FindByEmailAsync(request.Email, cancellationToken);
    if (existing is not null)
        errors.Add(new Error("User.Email.Duplicated", "Ya existe un usuario con ese email."));

    if (errors.Any())
        return Result<Guid>.Failure(errors);

    var user = new User(Guid.NewGuid(), request.Email, request.Password);
    await _repository.AddAsync(user, cancellationToken);

    return Result<Guid>.Success(user.Id);
}

Prueba el handler con xUnit verificando los tres casos de error y el caso de éxito.

8 · Reto

Extiende el Result<T> para que soporte:

  1. Un operador Map que transforme el valor si es exitoso.
  2. Un operador Bind que encadene otro Result<T>.
  3. Un método Match para manejar éxito y fallo en una sola expresión.

Aplica estos métodos en el proyecto CMS para encadenar validación de comando, validación de dominio y persistencia en una sola tubería.

9 · Resumen

  • Result<T> modela el éxito y el fallo como un valor, mejorando la claridad y testabilidad.
  • Usa Result<T> para errores de negocio esperados, no para errores técnicos.
  • Acumula todos los errores de validación posibles antes de devolver un fallo.
  • La capa de aplicación devuelve Result<T>; la capa de API lo convierte en ProblemDetails.
  • El patrón es complementario con FluentValidation: se puede convertir ValidationResult a Result<T>.

10 · Preguntas frecuentes

¿Result<T> reemplaza a las excepciones?

No. Reemplaza las excepciones para errores de negocio esperados. Las excepciones siguen siendo adecuadas para fallos técnicos, bugs y situaciones realmente excepcionales.

¿Result<T> es lo mismo que el tipo Result de Functional Programming?

Conceptualmente sí. En C# puedes implementar uno básico o usar librerías como FluentResults, LanguageExt o ErrorOr. Para la mayoría de proyectos, una implementación propia simple es suficiente.

¿Cómo combino Result con async/await?

Devuelve Task<Result<T>>. Puedes crear helpers como BindAsync o MapAsync para encadenar operaciones asíncronas.

¿Cómo devuelvo errores de múltiples validadores?

Acumula todos los Error en una lista y devuelve Result<T>.Failure(errors) si la lista tiene elementos. FluentValidation ya proporciona una lista de ValidationFailure que puedes proyectar.

¿Qué problema resuelve ProblemDetails?

Proporciona un formato estándar para errores HTTP, con campos como type, title, status, detail y errors. Esto facilita que los clientes consuman tu API de forma predecible.
