Proyecto CMS: validación con FluentValidation

Módulo 9 · Proyecto45 min

1 · Introducción

En esta lección aplicamos todo lo aprendido sobre validación y mapeo al proyecto CMS. Añadiremos validadores FluentValidation para los comandos de creación de posts, categorías y tags, los integraremos en un pipeline de MediatR y devolveremos los errores de validación como ProblemDetails.

Al final, la API rechazará automáticamente cualquier comando inválido antes de que llegue al handler, y el código de los handlers quedará limpio y enfocado en la lógica de negocio.

Objetivos del proyecto

  • Instalar y configurar FluentValidation en el proyecto CMS.
  • Crear validadores para CreatePostCommand, CreateCategoryCommand y CreateTagCommand.
  • Implementar un pipeline de validación con MediatR.
  • Configurar un middleware global que convierta ValidationException en ProblemDetails.
  • Verificar que los tests de integración fallan con 400 cuando los datos son inválidos.

2 · Teoría

2.1. Arquitectura del proyecto CMS

El proyecto CMS sigue Clean Architecture:

  • Cms.Domain: entidades, value objects e interfaces de repositorio.
  • Cms.Application: commands, queries, handlers, validadores y DTOs.
  • Cms.Infrastructure: EF Core, repositorios, servicios externos.
  • Cms.Api: Minimal APIs, middleware, configuración.

Los validadores viven en Cms.Application porque conocen las reglas de negocio y pueden depender de abstracciones de repositorio. La API solo expone los resultados.

2.2. Pipeline de validación

MediatR permite añadir comportamientos que se ejecutan antes y después de cada handler. Usaremos un IPipelineBehavior para ejecutar todos los validadores registrados para un request. Si hay fallos, lanzamos ValidationException y el middleware global la convierte en 400.

2.3. Middleware de excepciones

En .NET 8 preferimos IExceptionHandler sobre UseExceptionHandler. Es más explícito, testable y permite controlar la respuesta de forma precisa.

Consejo del proyecto

Registra los validadores con AddValidatorsFromAssembly pasando el assembly de la capa de aplicación. Así, la API no necesita conocer los validadores individualmente.

3 · Ejemplo mínimo

Antes de integrar todo, veamos un validador sencillo para CreateTagCommand. Un tag solo tiene un nombre y un slug.

using FluentValidation;

public sealed record CreateTagCommand(string Name, string Slug) : IRequest<Result<Guid>>;

public sealed class CreateTagCommandValidator : AbstractValidator<CreateTagCommand>
{
    public CreateTagCommandValidator()
    {
        RuleFor(x => x.Name)
            .NotEmpty().WithMessage("El nombre del tag es obligatorio.")
            .MaximumLength(50).WithMessage("El nombre no puede superar los 50 caracteres.");

        RuleFor(x => x.Slug)
            .NotEmpty().WithMessage("El slug es obligatorio.")
            .Matches("^[a-z0-9]+(?:-[a-z0-9]+)*$")
            .WithMessage("El slug solo puede contener letras minúsculas, números y guiones.");
    }
}

Este validador se ejecuta automáticamente cuando registramos el pipeline de validación. No hay que tocar el endpoint.

4.2. Validadores para el CMS

// CreateCategoryCommandValidator.cs
using FluentValidation;

public sealed class CreateCategoryCommandValidator : AbstractValidator<CreateCategoryCommand>
{
    public CreateCategoryCommandValidator(ICategoryRepository categoryRepository)
    {
        RuleFor(x => x.Name)
            .NotEmpty().WithMessage("El nombre de la categoría es obligatorio.")
            .MaximumLength(100).WithMessage("El nombre no puede superar los 100 caracteres.");

        RuleFor(x => x.Description)
            .MaximumLength(500).WithMessage("La descripción no puede superar los 500 caracteres.")
            .When(x => !string.IsNullOrEmpty(x.Description));

        // Regla asíncrona que verifica unicidad del nombre.
        RuleFor(x => x.Name)
            .MustAsync(async (name, cancellation) =>
                !await categoryRepository.ExistsByNameAsync(name, cancellation))
            .WithMessage("Ya existe una categoría con ese nombre.");
    }
}

// CreatePostCommandValidator.cs
public sealed class CreatePostCommandValidator : AbstractValidator<CreatePostCommand>
{
    public CreatePostCommandValidator(
        ICategoryRepository categoryRepository,
        IPostRepository postRepository)
    {
        RuleFor(x => x.Title)
            .NotEmpty().WithMessage("El título es obligatorio.")
            .MaximumLength(200).WithMessage("El título no puede superar los 200 caracteres.");

        RuleFor(x => x.Slug)
            .NotEmpty().WithMessage("El slug es obligatorio.")
            .Matches("^[a-z0-9]+(?:-[a-z0-9]+)*$")
            .WithMessage("El slug solo puede contener letras minúsculas, números y guiones.");

        RuleFor(x => x.Slug)
            .MustAsync(async (slug, cancellation) =>
                !await postRepository.ExistsBySlugAsync(slug, cancellation))
            .WithMessage("Ya existe un post con ese slug.");

        RuleFor(x => x.CategoryId)
            .NotEmpty().WithMessage("La categoría es obligatoria.");

        RuleFor(x => x.CategoryId)
            .MustAsync(async (categoryId, cancellation) =>
                await categoryRepository.ExistsAsync(categoryId, cancellation))
            .WithMessage("La categoría seleccionada no existe.");

        RuleFor(x => x.AuthorId)
            .NotEmpty().WithMessage("El autor es obligatorio.");

        RuleFor(x => x.Content)
            .MaximumLength(50000).WithMessage("El contenido no puede superar los 50000 caracteres.")
            .When(x => !string.IsNullOrEmpty(x.Content));

        RuleFor(x => x.Tags)
            .Must(tags => tags.Distinct(StringComparer.OrdinalIgnoreCase).Count() == tags.Count())
            .WithMessage("No se permiten tags duplicados.")
            .When(x => x.Tags is not null);

        RuleForEach(x => x.Tags)
            .MaximumLength(30).WithMessage("Cada tag no puede superar los 30 caracteres.")
            .Matches("^[a-z0-9-]+$")
            .WithMessage("Los tags solo pueden contener letras minúsculas, números y guiones.")
            .When(x => x.Tags is not null);
    }
}

4.3. Pipeline de validación

using FluentValidation;
using MediatR;

public sealed class ValidationBehavior<TRequest, TResponse> : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
    where TResponse : IResult
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public ValidationBehavior(IEnumerable<IValidator<TRequest>> validators)
    {
        _validators = validators;
    }

    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken cancellationToken)
    {
        if (!_validators.Any())
        {
            return await next();
        }

        var context = new ValidationContext<TRequest>(request);

        var validationResults = await Task.WhenAll(
            _validators.Select(v => v.ValidateAsync(context, cancellationToken)));

        var failures = validationResults
            .SelectMany(r => r.Errors)
            .Where(f => f is not null)
            .ToList();

        if (failures.Any())
        {
            throw new ValidationException(failures);
        }

        return await next();
    }
}

4.4. Configuración en Program.cs

using FluentValidation;

var builder = WebApplication.CreateBuilder(args);

// Registra todos los validadores del assembly de aplicación.
builder.Services.AddValidatorsFromAssembly(typeof(CreatePostCommand).Assembly);

builder.Services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssembly(typeof(CreatePostCommand).Assembly);
    cfg.AddBehavior(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));
});

// Handler global de excepciones.
builder.Services.AddExceptionHandler<ValidationExceptionHandler>();
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();
app.UseStatusCodePages();

app.MapPost("/api/v1/categories", async (CreateCategoryCommand command, IMediator mediator) =>
{
    var result = await mediator.Send(command);
    return result.IsSuccess
        ? Results.Created($"/api/v1/categories/{result.Value}", result.Value)
        : Results.BadRequest(result.Errors);
});

app.Run();

4.5. Handler de excepciones

using FluentValidation;
using Microsoft.AspNetCore.Diagnostics;
using Microsoft.AspNetCore.Mvc;

public sealed class ValidationExceptionHandler : IExceptionHandler
{
    private readonly IProblemDetailsService _problemDetailsService;

    public ValidationExceptionHandler(IProblemDetailsService problemDetailsService)
    {
        _problemDetailsService = problemDetailsService;
    }

    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        if (exception is not ValidationException validationException)
        {
            return false;
        }

        var errors = validationException.Errors
            .GroupBy(f => f.PropertyName)
            .ToDictionary(
                g => g.Key,
                g => g.Select(f => f.ErrorMessage).ToArray());

        httpContext.Response.StatusCode = StatusCodes.Status400BadRequest;

        var problemDetails = new ValidationProblemDetails(errors)
        {
            Status = StatusCodes.Status400BadRequest,
            Title = "Uno o más errores de validación han ocurrido.",
            Type = "https://tools.ietf.org/html/rfc7231#section-6.5.1"
        };

        await _problemDetailsService.WriteAsync(new ProblemDetailsContext
        {
            HttpContext = httpContext,
            ProblemDetails = problemDetails
        });

        return true;
    }
}

Con esta configuración, cualquier ValidationException se convierte automáticamente en una respuesta 400 con ValidationProblemDetails.

5 · Buenas prácticas

  • Registra los validadores desde el assembly de aplicación. Mantiene la API desacoplada de los validadores concretos.
  • Usa IExceptionHandler en lugar de middlewares imperativos para manejar excepciones.
  • Centraliza los mensajes de error. Si repites el mismo mensaje, considera constantes o un servicio de localización.
  • Testea los validadores de forma aislada. Son clases puras, ideales para tests unitarios.
  • Testea el pipeline de validación. Envía un comando inválido y verifica que no llega al handler y que la respuesta es 400.
  • No repitas validaciones en el handler. Si el validador ya lo comprueba, el handler debe confiar en que el comando es válido.

6 · Errores habituales

6.1. Registrar los validadores del assembly equivocado

// MAL: registra desde la API, donde no están los validadores.
builder.Services.AddValidatorsFromAssembly(typeof(Program).Assembly);

// BIEN: registra desde el assembly de aplicación.
builder.Services.AddValidatorsFromAssembly(typeof(CreatePostCommand).Assembly);

6.2. No añadir el pipeline de MediatR

Si solo registras los validadores pero no añades el ValidationBehavior, los validadores nunca se ejecutan. MediatR no los invoca automáticamente.

6.3. Usar Validate en lugar de ValidateAsync

// MAL: las reglas MustAsync se ignoran.
var result = validator.Validate(request);

// BIEN:
var result = await validator.ValidateAsync(request);

6.4. Devolver 500 para errores de validación

Si no registras el handler de excepciones o no capturas ValidationException, el middleware por defecto devolverá 500. Los errores de validación siempre deben ser 400.

7 · Ejercicio guiado

Completa la validación del CMS añadiendo un validador para UpdatePostCommand:

  • Id no puede ser vacío.
  • Title obligatorio y máximo 200 caracteres.
  • Slug obligatorio y con formato correcto.
  • La categoría debe existir, excepto si no se proporciona.
public sealed class UpdatePostCommandValidator : AbstractValidator<UpdatePostCommand>
{
    public UpdatePostCommandValidator(ICategoryRepository categoryRepository)
    {
        RuleFor(x => x.Id)
            .NotEmpty().WithMessage("El identificador del post es obligatorio.");

        RuleFor(x => x.Title)
            .NotEmpty().WithMessage("El título es obligatorio.")
            .MaximumLength(200).WithMessage("El título no puede superar los 200 caracteres.");

        RuleFor(x => x.Slug)
            .NotEmpty().WithMessage("El slug es obligatorio.")
            .Matches("^[a-z0-9]+(?:-[a-z0-9]+)*$")
            .WithMessage("El slug solo puede contener letras minúsculas, números y guiones.");

        RuleFor(x => x.CategoryId)
            .MustAsync(async (categoryId, cancellation) =>
                await categoryRepository.ExistsAsync(categoryId!.Value, cancellation))
            .WithMessage("La categoría seleccionada no existe.")
            .When(x => x.CategoryId.HasValue);
    }
}

Escribe un test de integración que envíe un UpdatePostCommand inválido y verifique que el handler no se ejecuta y que la respuesta contiene errors.Title.

8 · Reto

En el proyecto CMS, implementa un pipeline de validación que devuelva Result<T> en lugar de lanzar ValidationException. Esto requiere:

  1. Que el pipeline no lance excepciones, sino que devuelva un Result<T> fallido.
  2. Que los handlers devuelvan Result<T>.
  3. Que los endpoints mapeen Result<T> a ProblemDetails sin depender de un handler de excepciones.

Implementa esta versión en una rama alternativa y compara la legibilidad y testabilidad con la versión basada en excepciones.

9 · Resumen

  • Los validadores del CMS viven en la capa de aplicación y dependen de abstracciones de repositorio.
  • FluentValidation permite expresar reglas complejas: formato, unicidad, existencia, condiciones y validaciones anidadas.
  • El pipeline de MediatR ejecuta validación automáticamente antes de cada handler.
  • Un IExceptionHandler global convierte ValidationException en ValidationProblemDetails.
  • La API queda limpia: los endpoints solo envían comandos y mapean resultados.

10 · Preguntas frecuentes

¿Dónde deben vivir los validadores en Clean Architecture?

En la capa de aplicación. Conocen los comandos y pueden depender de interfaces de repositorio del dominio. No deben conocer detalles de EF Core ni HTTP.

¿Cómo testeo el pipeline de validación?

Crea un test de integración con WebApplicationFactory que envíe un comando inválido. Verifica que la respuesta es 400 y que los endpoints no persisten datos.

¿Puedo usar validadores asíncronos en el pipeline?

Sí, siempre que el pipeline llame a ValidateAsync. MediatR invoca el pipeline de forma asíncrona, así que no hay problema.

¿Qué hago si un validador necesita un servicio transaccional?

Prefiere consultas de solo lectura. Si necesitas lógica transaccional compleja, muévela al handler. El validador debe ser rápido y idempotente.

¿Cómo evito que la validación acceda a la base de datos innecesariamente?

Coloca las reglas triviales primero. FluentValidation las ejecuta en orden, pero incluso así, si hay muchas reglas, considera un validador en dos pasos: primero reglas puras, luego reglas de existencia.
