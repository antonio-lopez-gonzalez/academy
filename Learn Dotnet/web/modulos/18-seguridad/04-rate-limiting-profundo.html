Rate Limiting en profundidad

Módulo 18 · Seguridad en APIs (OWASP)30 min

1. Introducción

En esta lección profundizamos en rate limiting, una de las mitigaciones más efectivas contra A04 (Unrestricted Resource Consumption) y A06 (Unrestricted Access to Sensitive Business Flows). Veremos los algoritmos disponibles en ASP.NET Core, cómo aplicarlos por cliente y cómo escalarlos con Redis.

¿Qué problema resuelve? Limita la cantidad de peticiones que un cliente puede hacer en un periodo de tiempo, protegiendo contra abuso, scraping, ataques de denegación de servicio y automatización de flujos de negocio.

¿Cuándo se utiliza? En cualquier API pública, especialmente en endpoints de autenticación, creación de recursos, operaciones costosas y flujos sensibles como pagos o reservas.

Errores típicos: aplicar un único límite global, no distinguir entre usuarios autenticados y anónimos, no devolver Retry-After cuando se excede el límite, o ignorar que el rate limiting en memoria no funciona bien con múltiples instancias.

2. Teoría

ASP.NET Core 8 incluye rate limiting nativo en el namespace System.Threading.RateLimiting. Soporta varios algoritmos, cada uno con características diferentes:

  • Fixed Window: divide el tiempo en ventanas fijas. Simple pero permite picos al inicio de cada ventana. Es fácil de implementar y entender.
  • Sliding Window: similar al fijo, pero distribuye el permiso a lo largo de la ventana, suavizando los picos. Es el más equilibrado para APIs generales.
  • Token Bucket: permite ráfagas controladas hasta un tamaño de bucket, útil para APIs con picos ocasionales pero límites medios a largo plazo.
  • Concurrency: limita el número de peticiones simultáneas, no por unidad de tiempo. Útil para proteger recursos limitados como conexiones de base de datos.

Comparación de algoritmos
─────────────────────────
Fixed Window    →  fácil, picos al cambio de ventana
Sliding Window  →  más justo, evita picos de ventana
Token Bucket    →  permite ráfagas, bueno para APIs interactivas
Concurrency     →  limita peticiones paralelas, no frecuencia

Por defecto, el rate limiter de ASP.NET Core almacena los contadores en memoria. Para aplicaciones escaladas horizontalmente, necesitamos un almacén distribuido como Redis. Aunque ASP.NET Core no incluye un rate limiter distribuido por defecto, existen paquetes como AspNetCoreRateLimit o implementaciones personalizadas sobre IDistributedCache.

Claves de rate limiting

El rate limiter necesita una clave para agrupar peticiones. Las claves comunes son:

  • IP del cliente (anónimos).
  • Identificador de usuario autenticado (ClaimTypes.NameIdentifier).
  • Combinación de IP + endpoint.
  • API key.

Para proxies o balanceadores, la IP real suele venir en X-Forwarded-For. ASP.NET Core puede configurarse para leer correctamente estas cabeceras con ForwardedHeadersOptions.

Retry-After

La respuesta 429 Too Many Requests debe incluir el header Retry-After para indicar al cliente cuándo puede reintentar. Esto mejora la experiencia de usuario y permite a clientes respetuosos backoff correctamente.

3. Ejemplo mínimo

Configuramos un rate limiter global con ventana deslizante y lo aplicamos a toda la aplicación.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddRateLimiter(options =>
{
    options.AddSlidingWindowLimiter("general", slidingOptions =>
    {
        slidingOptions.PermitLimit = 100;         // 100 peticiones
        slidingOptions.Window = TimeSpan.FromMinutes(1); // por minuto
        slidingOptions.SegmentsPerWindow = 4;     // 4 segmentos de 15s
        slidingOptions.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
        slidingOptions.QueueLimit = 2;            // 2 peticiones en cola
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

var app = builder.Build();
app.UseRateLimiter();
app.MapControllers();
app.Run();

Con esta configuración, un cliente puede hacer hasta 100 peticiones por minuto, distribuidas de forma más uniforme gracias a la ventana deslizante. Las peticiones excedentes pueden esperar en cola si hay espacio.

4. Ejemplo real

En una API profesional queremos políticas diferenciadas: una para usuarios anónimos, otra para autenticados y otra más estricta para endpoints sensibles como login o creación de posts.

builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("authenticated", context =>
    {
        // Usamos el claim de usuario como clave de rate limiting
        var userId = context.User.FindFirstValue(ClaimTypes.NameIdentifier)
                     ?? context.Connection.RemoteIpAddress?.ToString()
                     ?? "anonymous";

        return RateLimitPartition.GetSlidingWindowLimiter(
            userId,
            _ => new SlidingWindowRateLimiterOptions
            {
                PermitLimit = 200,
                Window = TimeSpan.FromMinutes(1),
                SegmentsPerWindow = 4
            });
    });

    options.AddFixedWindowLimiter("strict", fixedOptions =>
    {
        fixedOptions.PermitLimit = 5;
        fixedOptions.Window = TimeSpan.FromMinutes(1);
    });

    options.AddTokenBucketLimiter("burst", tokenOptions =>
    {
        tokenOptions.TokenLimit = 20;
        tokenOptions.ReplenishmentPeriod = TimeSpan.FromSeconds(10);
        tokenOptions.TokensPerPeriod = 5;
        tokenOptions.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
        tokenOptions.QueueLimit = 0;
    });

    options.OnRejected = async (context, token) =>
    {
        context.HttpContext.Response.StatusCode = StatusCodes.Status429TooManyRequests;
        context.HttpContext.Response.ContentType = "application/json";

        if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter))
        {
            context.HttpContext.Response.Headers.RetryAfter =
                ((int)retryAfter.TotalSeconds).ToString(NumberFormatInfo.InvariantInfo);
        }

        await context.HttpContext.Response.WriteAsJsonAsync(
            new { message = "Demasiadas peticiones. Inténtalo más tarde." },
            token);
    };
});

Aplicamos las políticas a los endpoints:

// Todos los endpoints usan la política "general" por defecto
app.UseRateLimiter();

app.MapPost("/api/auth/login", (LoginRequest request) => Results.Ok())
   .RequireRateLimiting("strict")
   .AllowAnonymous();

app.MapPost("/api/v1/posts", async (CreatePostRequest request, IMediator mediator) =>
{
    var postId = await mediator.Send(request);
    return Results.Created($"/api/v1/posts/{postId}", postId);
})
.RequireRateLimiting("authenticated")
.RequireAuthorization();

app.MapPost("/api/v1/media/upload", async (IFormFile file) =>
{
    // Procesar archivo...
    return Results.Ok();
})
.RequireRateLimiting("burst")
.RequireAuthorization();

La política strict protege contra fuerza bruta en login. La política authenticated limita por usuario. La política burst permite ráfagas cortas pero controladas, útil para subida de archivos.

5. Buenas prácticas

  • Diferencia usuarios autenticados de anónimos: los anónimos tienen límites más bajos porque no puedes identificarlos de forma fiable.
  • Usa la IP como fallback: si no hay usuario autenticado, la dirección IP es la mejor clave disponible (ten cuidado con proxies).
  • Devuelve Retry-After: los clientes respetuosos sabrán cuándo reintentar.
  • Combina rate limiting con paginación: nunca permitas listados ilimitados.
  • Escalabilidad: en producción con múltiples instancias, usa Redis u otro almacén distribuido.
  • No dependas solo del rate limiting: es una capa más, no la única defensa contra abuso.
  • Monitorea los rechazos: alerta si hay picos de 429, puede indicar un ataque o un cliente mal configurado.
  • Prueba los límites: incluye tests que verifiquen que se devuelve 429 tras superar el límite.
Consejo: para endpoints críticos (login, registro, recuperación de contraseña), usa límites muy bajos (5 intentos/minuto) para mitigar ataques de fuerza bruta. Considera también bloquear temporalmente la cuenta tras varios intentos fallidos.

6. Errores habituales

IncorrectoPor qué está malCorrecto
Un solo límite global para toda la API Endpoint barato y endpoint costoso tienen el mismo límite Políticas por endpoint o grupo funcional

No devolver Retry-After El cliente no sabe cuándo reintentar Incluir el header en la respuesta 429

Ignorar proxies al leer la IP El rate limiter agrupa por IP del proxy, no del cliente Configurar ForwardedHeadersOptions

7. Ejercicio guiado

Vamos a implementar rate limiting por usuario para el endpoint de creación de posts del CMS.

  1. Registra AddRateLimiter en Program.cs.
  2. Crea una política "create-post" con TokenBucketRateLimiter: 10 tokens, recarga de 2 tokens cada 10 segundos.
  3. Usa el NameIdentifier del usuario como clave.
  4. Aplica la política al endpoint POST /api/v1/posts.
  5. Verifica que al superar el límite recibes 429 con Retry-After.
  6. Registra los rechazos en el log para auditoría.
options.AddPolicy("create-post", context =>
{
    var userId = context.User.FindFirstValue(ClaimTypes.NameIdentifier)
                 ?? "anonymous";

    return RateLimitPartition.GetTokenBucketLimiter(
        userId,
        _ => new TokenBucketRateLimiterOptions
        {
            TokenLimit = 10,
            QueueProcessingOrder = QueueProcessingOrder.OldestFirst,
            QueueLimit = 0,
            ReplenishmentPeriod = TimeSpan.FromSeconds(10),
            TokensPerPeriod = 2,
            AutoReplenishment = true
        });
});

Registro del endpoint:

app.MapPost("/api/v1/posts", async (CreatePostRequest request, IMediator mediator) =>
{
    var postId = await mediator.Send(request);
    return Results.Created($"/api/v1/posts/{postId}", postId);
})
.RequireRateLimiting("create-post")
.RequireAuthorization();

8. Reto

Implementa un rate limiter distribuido con Redis para el CMS. El desafío es:

  • Implementar IRateLimiterPolicy<T> o un middleware personalizado.
  • Almacenar los contadores en Redis con expiración (IDistributedCache).
  • Hacer que funcione correctamente cuando la API se ejecuta en múltiples contenedores.
  • Considerar la atomicidad de las operaciones de Redis para evitar condiciones de carrera.

No resuelvas el reto todavía. Piensa en las operaciones atómicas de Redis y la serialización de los contadores. Investiga AspNetCoreRateLimit como alternativa probada.

9. Resumen

  • El rate limiting protege contra abuso y consumo descontrolado de recursos.
  • ASP.NET Core 8 soporta Fixed Window, Sliding Window, Token Bucket y Concurrency.
  • Debes diferenciar usuarios autenticados y anónimos, y usar claves estables.
  • Devuelve siempre Retry-After en respuestas 429.
  • En producción escalada, usa un almacén distribuido como Redis.
  • Los endpoints de autenticación deben tener los límites más estrictos.

10. Preguntas frecuentes

¿Qué algoritmo elijo?

Sliding Window para la mayoría de endpoints. Token Bucket si esperas ráfagas legítimas. Concurrency para limitar peticiones paralelas. Fixed Window solo si necesitas simplicidad y puedes aceptar picos de ventana.

¿El rate limiter de ASP.NET Core es distribuido?

No por defecto; trabaja en memoria. Para escalar horizontalmente necesitas Redis o una implementación personalizada.

¿Cómo identifico a un usuario anónimo?

Usa la dirección IP como clave, pero ten en cuenta que puede estar detrás de proxies. Revisa X-Forwarded-For si aplica.

¿El rate limiting reemplaza la autenticación?

No. Es una capa adicional. Un endpoint sensible debe estar protegido por autenticación, autorización y rate limiting.

¿Cómo pruebo el rate limiting?

Lanza múltiples peticiones consecutivas desde un script o herramienta como bombardier o wrk, y verifica que tras superar el límite recibes 429.

¿Qué pasa si coloco el rate limiter después de autenticación?

El rate limiter suele ir antes de autenticación para proteger endpoints de login. Sin embargo, para políticas basadas en usuario, debe ir después de UseAuthentication.
