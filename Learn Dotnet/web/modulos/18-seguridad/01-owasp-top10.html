OWASP Top 10 para APIs .NET

Módulo 18 · Seguridad en APIs (OWASP)45 min

1 · Introducción

En esta lección vamos a aprender el OWASP Top 10 para APIs, el estándar de facto para entender los riesgos de seguridad más críticos que enfrentan las APIs modernas. Veremos cada riesgo desde la perspectiva de .NET 8 y ASP.NET Core, y aprenderemos a mitigarlo con las herramientas que ya conocemos del ecosistema.

¿Por qué existe OWASP? Las APIs son la capa de entrada de casi todas las aplicaciones. Un atacante no necesita romper el firewall si puede enviar una petición HTTP bien construida que explote una autorización mal implementada. OWASP organiza y prioriza estos riesgos para que los equipos de desarrollo sepan dónde enfocar sus esfuerzos.

¿Qué problema resuelve? Proporciona un lenguaje común y un checklist técnico para diseñar, implementar y auditar APIs seguras. Nos ayuda a clasificar los fallos y comunicarlos a otros equipos.

¿Cuándo se utiliza? Desde el diseño de un endpoint hasta la auditoría de seguridad previa a producción. También es útil durante code reviews y planificación de arquitectura.

Errores típicos: pensar que "usar HTTPS ya es suficiente", ignorar la autorización a nivel de objeto, exponer campos internos en los DTOs, o confiar en que el cliente validará los datos. También es común tratar OWASP como una lista a memorizar en lugar de una forma de pensar sobre el diseño seguro.

2 · Teoría

OWASP publica una lista de los 10 riesgos más críticos para APIs. La versión actual (2023) reorganiza los clásicos problemas de las web tradicionales y los adapta a las particularidades de las APIs: uso masivo de JSON, autenticación stateless con JWT, microservicios y consumo de APIs de terceros.

En .NET 8 contamos con mecanismos nativos para mitigar casi todos estos riesgos: middleware de autorización, IAuthorizationService, rate limiting, validación de modelos, HttpClientFactory con Polly, configuración jerárquica, OpenTelemetry y logging estructurado.

Cada riesgo representa una categoría de errores. No basta con aplicar una sola medida; hay que pensar en defensa en profundidad: múltiples capas de protección que hagan más difícil la explotación. Un atacante debe encontrar y saltar varias barreras para conseguir su objetivo.

A01 — Broken Object Level Authorization (BOLA)

Es el riesgo más frecuente y peligroso. Ocurre cuando un endpoint recibe un identificador de recurso y no verifica que el usuario autenticado tenga permiso sobre ese recurso. En .NET lo resolvemos con IAuthorizationService, AuthorizationHandler<TRequirement, TResource> y políticas personalizadas.

A02 — Broken Authentication

Incluye JWT mal configurados, tokens sin expiración, algoritmos débiles, credenciales débiles y gestión inadecuada de sesiones. Usamos Microsoft.AspNetCore.Authentication.JwtBearer con validación completa de emisor, audiencia, firma y expiración.

A03 — Broken Object Property Level Authorization

Se produce cuando un endpoint devuelve más datos de los necesarios o permite modificar campos que no deberían ser editables. La solución son DTOs específicos para cada operación y proyecciones en las consultas.

A04 — Unrestricted Resource Consumption

Permite que un cliente agote CPU, memoria, red o base de datos. La mitigación incluye rate limiting, paginación, límites de tamaño de payload y timeouts.

A05 — Broken Function Level Authorization

Surge cuando un rol o claim puede acceder a una función administrativa. Lo resolvemos con policies, roles y claims bien definidos, y nunca confiando solo en el rol indicado por el cliente.

A06 — Unrestricted Access to Sensitive Business Flows

Automatización masiva de flujos de negocio sensibles: compras, reservas, creación de contenido. Rate limiting avanzado y detección de patrones anómalos son las mitigaciones principales.

A07 — Server Side Request Forgery (SSRF)

El servidor realiza peticiones a URLs controladas por el atacante. Ocurre al integrar APIs de terceros o al descargar recursos. Usamos listas blancas de hosts, esquemas y puertos permitidos.

A08 — Security Misconfiguration

Headers de seguridad ausentes, CORS abierto, trazas de error detalladas, dependencias vulnerables. En .NET configuramos middleware de headers, CORS restrictivo y mantenemos las dependencias actualizadas.

A09 — Improper Inventory Management

APIs no documentadas, versiones antiguas sin mantenimiento, endpoints deprecados accesibles. Mitigación: versionado explícito, deprecación y documentación actualizada con Swagger/Scalar.

A10 — Unsafe Consumption of APIs

Consumimos APIs de terceros sin validar ni limitar el impacto de sus fallos. Usamos validación estricta, timeouts, retries con Polly y nunca confiamos en la respuesta externa.

3 · Ejemplo mínimo

Veamos el ejemplo más pequeño posible de un endpoint vulnerable a BOLA (A01) y su versión segura. Es importante entender que el problema no es el framework; el problema es asumir que "estar autenticado" implica "estar autorizado".

// ❌ VULNERABLE: cualquier usuario autenticado puede ver cualquier pedido
app.MapGet("/api/orders/{id:guid}", async (Guid id, CmsDbContext db) =>
{
    var order = await db.Orders.FindAsync(id);
    return order is null ? Results.NotFound() : Results.Ok(order);
}).RequireAuthorization();

// ✅ SEGURO: verificamos que el recurso pertenezca al usuario actual
app.MapGet("/api/orders/{id:guid}", async (
    Guid id,
    ClaimsPrincipal user,
    IOrderAuthorizationService auth,
    CmsDbContext db) =>
{
    var order = await db.Orders.FindAsync(id);
    if (order is null) return Results.NotFound();

    // Autorización a nivel de objeto: ¿es el dueño o es admin?
    var authorized = await auth.AuthorizeAsync(user, order, Operations.Read);
    if (!authorized.Succeeded) return Results.Forbid();

    return Results.Ok(order);
}).RequireAuthorization();

La diferencia es sutil pero crítica: RequireAuthorization solo valida que exista un token válido. La segunda llamada a IAuthorizationService valida que el usuario tenga derecho sobre ese recurso concreto. En .NET, un endpoint puede tener dos capas de autorización: autenticación y autorización de recurso.

4 · Ejemplo real

A continuación implementamos protecciones contra A01, A03, A04 y A05 en un endpoint real del CMS. Supongamos que tenemos un endpoint para obtener un post por su identificador.

// Configuración de autorización en Program.cs
builder.Services.AddAuthorization(options =>
{
    // A05: políticas por función/rol
    options.AddPolicy("CanEditPosts", policy =>
        policy.RequireRole("Admin", "Editor")
              .RequireClaim("permissions", "posts:write"));
});

// Endpoint con múltiples mitigaciones
app.MapGet("/api/v1/posts/{id:guid}", async (
    Guid id,
    [FromServices] IPostService posts,
    [FromServices] IAuthorizationService authorization,
    ClaimsPrincipal user,
    CancellationToken cancellationToken) =>
{
    // A04: paginación/validación de recursos se hace en capas inferiores
    var post = await posts.GetByIdAsync(id, cancellationToken);
    if (post is null) return Results.NotFound();

    // A01: autorización a nivel de objeto
    var authResult = await authorization.AuthorizeAsync(user, post, Operations.Read);
    if (!authResult.Succeeded) return Results.Forbid();

    // A03: devolvemos un DTO, nunca la entidad completa
    return Results.Ok(post.ToResponseDto());
})
.RequireAuthorization("CanEditPosts")  // A05
.WithName("GetPostById")
.WithOpenApi();

El DTO de respuesta es clave para A03. Si la entidad Post contuviera un InternalNotes o un AuthorSalary, nunca debería exponerse directamente.

// Entidad de dominio (campos internos que no deben salir al cliente)
public class Post
{
    public Guid Id { get; set; }
    public string Title { get; set; } = string.Empty;
    public string Content { get; set; } = string.Empty;
    public string Status { get; set; } = "draft";
    public Guid AuthorId { get; set; }
    public string InternalNotes { get; set; } = string.Empty; // sensible
    public decimal AuthorSalary { get; set; }                  // sensible
}

// DTO de respuesta (solo campos públicos)
public record PostResponseDto(
    Guid Id,
    string Title,
    string Content,
    string Status,
    Guid AuthorId);

Además, para A04, la capa de aplicación debe imponer límites. Por ejemplo, el servicio de listado de posts nunca devolverá todos los registros sin paginación:

public async Task<PagedResult<PostResponseDto>> ListPostsAsync(
    ListPostsRequest request,
    CancellationToken cancellationToken)
{
    // Límite máximo de página para evitar consumo excesivo
    const int MaxPageSize = 100;
    var pageSize = Math.Min(request.PageSize, MaxPageSize);

    var query = _dbContext.Posts
        .AsNoTracking()
        .OrderByDescending(p => p.PublishedAt);

    var total = await query.CountAsync(cancellationToken);
    var items = await query
        .Skip((request.Page - 1) * pageSize)
        .Take(pageSize)
        .Select(p => p.ToResponseDto())
        .ToListAsync(cancellationToken);

    return new PagedResult<PostResponseDto>(items, total, request.Page, pageSize);
}

5 · Buenas prácticas

  • Defensa en profundidad: nunca confíes en una sola capa de seguridad. Autenticación + autorización + validación + rate limiting + logging.
  • Principio del mínimo privilegio: cada endpoint debe exigir solo los claims/roles estrictamente necesarios. No otorgues permisos de administrador por defecto.
  • DTOs específicos por operación: usar PostCreateDto, PostUpdateDto, PostResponseDto. Evitar reciclar la entidad.
  • Never trust the client: validar todo en el servidor, incluso si el frontend parece hacerlo bien. Un atacante puede saltarse cualquier validación del cliente.
  • Auditoría: registrar quién accede a recursos sensibles. Usa Serilog con Enrich.WithClientIp() o similar.
  • Pruebas de seguridad: incluye tests que intenten acceder a recursos ajenos y esperen 403. Los tests de seguridad son tan importantes como los funcionales.
  • Revisión de dependencias: ejecuta dotnet list package --vulnerable regularmente para detectar librerías con problemas conocidos.
  • Documentación de APIs: mantén Swagger/Scalar actualizado y elimina endpoints deprecados que no se usen.
  • Seguridad por diseño: plantea cada endpoint como si fuera público. Pregúntate siempre "¿qué pasa si un atacante envía esta petición?".
Consejo: crea un helper AuthorizationPolicies centralizado para que todas las políticas estén definidas en un solo lugar y sean fáciles de auditar. Evita dispersar RequireRole por toda la aplicación.

7 · Ejercicio guiado

Vamos a crear un AuthorizationHandler que verifique que el usuario actual es autor de un post o tiene rol Admin. Este handler se aplica a un recurso concreto, no solo al endpoint.

  1. Crea una clase PostAuthorizationRequirement : IAuthorizationRequirement.
  2. Crea PostAuthorizationHandler : AuthorizationHandler<PostAuthorizationRequirement, Post>.
  3. En el handler, compara context.User.FindFirstValue(ClaimTypes.NameIdentifier) con resource.AuthorId.
  4. Registra la política en AddAuthorization.
  5. Aplica la política en el endpoint con RequireAuthorization("PostOwnerOrAdmin").
public class PostAuthorizationRequirement : IAuthorizationRequirement { }

public class PostAuthorizationHandler
    : AuthorizationHandler<PostAuthorizationRequirement, Post>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        PostAuthorizationRequirement requirement,
        Post resource)
    {
        var userId = context.User.FindFirstValue(ClaimTypes.NameIdentifier);
        var isAdmin = context.User.IsInRole("Admin");

        if (isAdmin || userId == resource.AuthorId.ToString())
        {
            context.Succeed(requirement);
        }

        return Task.CompletedTask;
    }
}

// Registro en Program.cs
builder.Services.AddSingleton<IAuthorizationHandler, PostAuthorizationHandler>();

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("PostOwnerOrAdmin", policy =>
        policy.Requirements.Add(new PostAuthorizationRequirement()));
});

En el endpoint, primero obtenemos el post, luego llamamos a AuthorizeAsync pasando el recurso como segundo parámetro. Si falla, devolvemos Results.Forbid().

8 · Reto

Implementa una protección contra A06 — Unrestricted Access to Sensitive Business Flows en el endpoint de publicación de posts del CMS. El objetivo es evitar que un usuario automático cree cientos de posts en pocos segundos.

Requisitos:

  • Limitar a 5 creaciones de post por minuto por usuario.
  • Devolver 429 Too Many Requests con un header Retry-After.
  • Usar rate limiting de ASP.NET Core (no un contador manual).
  • Registrar en el log cada intento bloqueado para auditoría.

9 · Resumen

  • OWASP Top 10 para APIs es una guía esencial para desarrolladores backend.
  • En .NET 8 disponemos de herramientas nativas para mitigar cada riesgo: autorización, rate limiting, headers, validación y logging.
  • La autorización a nivel de objeto (BOLA) es el error más común y costoso. Siempre verifica la propiedad del recurso.
  • Los DTOs específicos previenen la exposición accidental de datos sensibles (A03).
  • Rate limiting, headers de seguridad, gestión de secretos y versionado son obligatorios en producción.
  • La seguridad es un proceso: revisa, testea y actualiza constantemente.

10 · Preguntas frecuentes

¿Es suficiente con HTTPS?

No. HTTPS protege la confidencialidad en tránsito, pero no la autorización ni la validación de datos. Es una capa necesaria pero no suficiente. Necesitas también autenticación, autorización y validación de entrada.

¿Debo implementar todos los controles yo mismo?

No. Usa lo que ofrece ASP.NET Core: AddAuthentication, AddAuthorization, AddRateLimiter, etc. Tu trabajo es configurarlos correctamente y no omitirlos. No reinventes la rueda.

¿Cómo priorizo qué arreglar primero?

Empieza por autorización (A01, A03, A05) y autenticación (A02), ya que son los más explotables. Luego rate limiting (A04, A06) y configuración (A08). Finalmente, gestión de secretos y dependencias.

¿OWASP cambia cada año?

La lista para APIs se actualiza periódicamente (última versión 2023). Los principios, sin embargo, son estables: validar entrada, autorizar acceso y minimizar la superficie de ataque.

¿Qué diferencia hay entre roles y claims?

Los roles son claims de tipo role. Los claims son más flexibles y pueden expresar permisos granulares (por ejemplo, posts:write), preferencia de UI o datos de identidad. En APIs modernas, los claims suelen ser preferibles a los roles.

¿Cómo se audita una API en producción?

Combina logs estructurados (Serilog), trazas distribuidas (OpenTelemetry), alertas sobre patrones de error (muchos 401/403/429) y revisiones periódicas de dependencias y configuración.
