SQL Injection y cómo EF Core la previene

Módulo 18 · Seguridad en APIs (OWASP)30 min

1 · Introducción

La inyección SQL sigue siendo uno de los vectores de ataque más peligrosos y comunes. En esta lección veremos por qué ocurre, cómo Entity Framework Core la previene de forma automática y qué errores podemos cometer al usar SQL crudo.

¿Qué problema resuelve? Evita que un atacante ejecute comandos SQL arbitrarios enviando input malicioso por la API.

¿Cuándo se utiliza? Siempre que escribas consultas contra una base de datos relacional, ya sea con EF Core, Dapper o ADO.NET.

Errores típicos: concatenar strings para formar SQL, usar FromSqlRaw sin parámetros, o pensar que "usar un ORM" garantiza seguridad automáticamente. También es peligroso confiar en validaciones del cliente para sanitizar SQL.

2 · Teoría

SQL Injection ocurre cuando el input del usuario se interpola directamente en una consulta SQL. El motor de base de datos no puede distinguir entre código y datos, por lo que ejecuta el input como si fuera parte de la consulta.

El mecanismo de defensa es siempre el mismo: consultas parametrizadas. Los parámetros se envían por separado al motor, que los trata como valores, no como código. EF Core genera consultas parametrizadas automáticamente cuando usas LINQ.


Sin parametrizar (vulnerable)
─────────────────────────────
SELECT * FROM Posts WHERE Title = 'user input'

Input malicioso: ' OR '1'='1
Resultado: SELECT * FROM Posts WHERE Title = '' OR '1'='1'
→ Devuelve todos los posts.

Con parametrización (seguro)
────────────────────────────
SELECT * FROM Posts WHERE Title = @p0
@p0 = ' OR '1'='1   ← el motor lo trata como un string literal
→ No se ejecuta la condición OR, se busca un título exacto.

En .NET 8, EF Core utiliza SqlParameter (o el equivalente de Npgsql para PostgreSQL) internamente. Eso significa que cualquier consulta LINQ está protegida por diseño. El peligro aparece cuando el desarrollador decide escribir SQL manualmente de forma incorrecta.

¿Cómo funciona internamente EF Core?

Cuando escribes una consulta LINQ, EF Core la traduce a un árbol de expresiones, luego a una consulta SQL relacional y finalmente envía los parámetros de forma separada al motor de base de datos. El motor conoce la estructura de la consulta y los valores, por lo que nunca puede confundir datos con código.

ORMs y falsos positivos

Algunos desarrolladores creen que usar un ORM les libera de pensar en SQL Injection. Es cierto solo si usamos LINQ. Tan pronto como usamos FromSqlRaw, ExecuteSqlRaw o consultas ad hoc, recuperamos la responsabilidad de parametrizar manualmente.

ADON.NET y Dapper

En ADO.NET, los SqlParameter o NpgsqlParameter son la forma segura de ejecutar consultas. Dapper hace esto casi automáticamente si pasamos objetos anónimos con propiedades como parámetros. Solo se vuelve vulnerable si concatenamos strings o usamos DynamicParameters de forma incorrecta.

3 · Ejemplo mínimo

Veamos la diferencia entre una consulta LINQ segura y una consulta cruda vulnerable. Ambas devuelven posts por título, pero la segunda permite inyección SQL.

// ✅ SEGURO: EF Core parametriza automáticamente
app.MapGet("/api/posts", async (string title, CmsDbContext db) =>
{
    var posts = await db.Posts
        .Where(p => p.Title.Contains(title))
        .ToListAsync();

    return Results.Ok(posts);
});

// ❌ VULNERABLE: concatenación directa de SQL
app.MapGet("/api/posts-unsafe", async (string title, CmsDbContext db) =>
{
    var sql = $"SELECT * FROM Posts WHERE Title LIKE '%{title}%'";
    var posts = await db.Posts.FromSqlRaw(sql).ToListAsync();
    return Results.Ok(posts);
});

Si un atacante envía title='; DROP TABLE Posts; --, la consulta insegura podría destruir datos. La primera consulta simplemente buscará un título con esos caracteres y no devolverá nada. La inyección más peligrosa no es solo leer datos; es modificar o eliminar el esquema.

4 · Ejemplo real

En una aplicación profesional usamos búsquedas dinámicas, filtros opcionales y, a veces, SQL crudo por rendimiento. Veamos cómo hacerlo de forma segura con FromSqlInterpolated, SqlParameter y Dapper.

// ✅ FromSqlInterpolated: parametriza automáticamente
app.MapGet("/api/posts/search", async (string? title, CmsDbContext db) =>
{
    var term = $"%{title ?? string.Empty}%";

    var posts = await db.Posts
        .FromSqlInterpolated($"""
            SELECT * FROM "Posts" WHERE "Title" LIKE {term}
            """)
        .AsNoTracking()
        .ToListAsync();

    return Results.Ok(posts);
});

FromSqlInterpolated convierte las expresiones interpoladas en parámetros. Es equivalente a escribir manualmente SqlParameter. La clave es que la expresión entre llaves nunca se interpola directamente; se convierte en un parámetro nombrado.

// ✅ SQL crudo seguro con parámetros explícitos
app.MapGet("/api/posts/by-author", async (Guid authorId, CmsDbContext db) =>
{
    var parameter = new SqlParameter("@authorId", authorId);

    var posts = await db.Posts
        .FromSqlRaw("""
            SELECT * FROM "Posts" WHERE "AuthorId" = @authorId
            """, parameter)
        .AsNoTracking()
        .ToListAsync();

    return Results.Ok(posts);
});

Si usas Dapper, el comportamiento es el mismo: siempre parametriza con objetos anónimos o DynamicParameters.

// ✅ Dapper con parámetros
public class PostRepository : IPostRepository
{
    private readonly string _connectionString;

    public PostRepository(IConfiguration configuration)
    {
        _connectionString = configuration.GetConnectionString("Default")!;
    }

    public async Task<IReadOnlyList<Post>> SearchByAuthorAsync(Guid authorId)
    {
        const string sql = """
            SELECT * FROM "Posts" WHERE "AuthorId" = @authorId
            """;

        using var connection = new NpgsqlConnection(_connectionString);
        var posts = await connection.QueryAsync<Post>(sql, new { authorId });
        return posts.ToList();
    }
}

Para búsquedas dinámicas con filtros opcionales, podemos construir la consulta de forma programática pero siempre parametrizando:

public async Task<IReadOnlyList<Post>> SearchAsync(PostSearchCriteria criteria)
{
    var sql = new StringBuilder("SELECT * FROM \"Posts\" WHERE 1 = 1");
    var parameters = new DynamicParameters();

    if (!string.IsNullOrWhiteSpace(criteria.Title))
    {
        sql.Append(" AND \"Title\" LIKE @title");
        parameters.Add("title", $"%{criteria.Title}%");
    }

    if (criteria.AuthorId.HasValue)
    {
        sql.Append(" AND \"AuthorId\" = @authorId");
        parameters.Add("authorId", criteria.AuthorId.Value);
    }

    if (criteria.Status is not null)
    {
        sql.Append(" AND \"Status\" = @status");
        parameters.Add("status", criteria.Status);
    }

    using var connection = new NpgsqlConnection(_connectionString);
    var posts = await connection.QueryAsync<Post>(sql.ToString(), parameters);
    return posts.ToList();
}

Observa que la consulta SQL se concatena, pero los valores nunca se concatenan. Los valores siempre van en DynamicParameters. Esta es la regla de oro.

Detección de SQL Injection en tests y revisión de código

Además de parametrizar, debemos revisar el código y escribir tests que verifiquen que no se pueden inyectar payloads. Un test típico envía un string malicioso y verifica que la respuesta no contenga más datos de los esperados o que la consulta SQL generada contenga parámetros.

[Fact]
public async Task Search_ByTitle_WithSqlInjectionPayload_ReturnsNoExtraResults()
{
    // Arrange
    var maliciousTitle = "test' OR '1'='1";
    await SeedPostsAsync(title: "test");

    // Act
    var response = await _client.GetAsync($"/api/posts?title={Uri.EscapeDataString(maliciousTitle)}");

    // Assert
    response.EnsureSuccessStatusCode();
    var posts = await response.Content.ReadFromJsonAsync<List<PostResponseDto>>();
    posts.Should().BeEmpty("porque el payload se trata como un literal, no como SQL");
}

El test fallará si la consulta es vulnerable: en ese caso, el payload devolvería todos los posts. Si la consulta está parametrizada, devolverá cero resultados porque ningún título coincide exactamente con el literal malicioso.

5 · Buenas prácticas

  • Prefiere LINQ: EF Core parametriza automáticamente y abstrae las diferencias entre motores de base de datos.
  • Si usas SQL crudo, usa parámetros: nunca concatenes input del usuario. Usa FromSqlInterpolated o SqlParameter.
  • Valida el input antes de tocar la base de datos: longitudes, caracteres permitidos y rangos. Aunque la parametrización protege, una validación previa reduce la superficie de ataque.
  • Principio de mínimo privilegio: el usuario de la base de datos de la aplicación no debe poder ejecutar DROP TABLE ni acceder a tablas que no necesite.
  • Auditoría: loguea consultas SQL inusuales o errores de sintaxis que puedan indicar intentos de inyección.
  • Tests de seguridad: incluye tests que envíen payloads de inyección SQL y verifiquen que no se ejecuten. Un payload clásico es ' OR '1'='1.
  • Stored procedures: son seguras si se llaman con parámetros. Si el procedimiento almacenado concatena internamente, sigue siendo vulnerable.
  • Evita SQL dinámico en el cliente: nunca construyas consultas SQL en el frontend y las envíes al backend para ejecutar.
Consejo: configura EF Core para loguear las consultas SQL en desarrollo con EnableSensitiveDataLogging(), pero desactívalo en producción para no exponer datos reales en los logs.

7 · Ejercicio guiado

Vamos a convertir un endpoint vulnerable en uno seguro. El endpoint busca posts por slug (cadena de URL amigable).

  1. Crea un endpoint GET /api/posts/by-slug/{slug}.
  2. Usa FromSqlInterpolated para consultar por el slug.
  3. Valida que el slug solo contenga letras, números, guiones y guiones bajos.
  4. Escribe un test que envíe slug="test' OR '1'='1" y verifique que no se devuelvan todos los posts.
  5. Escribe otro test que envíe un slug válido y verifique que la consulta funciona.
app.MapGet("/api/posts/by-slug/{slug}", async (string slug, CmsDbContext db) =>
{
    // Validación de formato adicional
    if (!SlugRegex().IsMatch(slug))
        return Results.BadRequest("Slug con formato inválido.");

    var post = await db.Posts
        .FromSqlInterpolated($"""
            SELECT * FROM "Posts" WHERE "Slug" = {slug}
            """)
        .AsNoTracking()
        .FirstOrDefaultAsync();

    return post is null ? Results.NotFound() : Results.Ok(post);
});

[GeneratedRegex(@"^[a-z0-9\-_]+$", RegexOptions.IgnoreCase)]
private static partial Regex SlugRegex();

El test de seguridad envía un payload clásico de inyección. La respuesta debe ser 400 por la validación del slug o, si llegara a la consulta, 404 porque EF Core parametriza el input. Nunca debe devolver todos los posts.

8 · Reto

Implementa un buscador avanzado de posts con múltiples filtros opcionales (título, autor, fecha, estado) usando SQL crudo de forma segura. Debe:

  • Construir la consulta SQL dinámicamente según los filtros recibidos.
  • Usar siempre parámetros, nunca concatenación.
  • Devolver resultados paginados.
  • Validar que los filtros tengan formatos esperados (GUID, fechas, enumeraciones).

No resuelvas el reto todavía. Inténtalo primero; veremos una posible solución más adelante.

9 · Resumen

  • SQL Injection ocurre cuando el input del usuario se interpola como código SQL.
  • EF Core protege automáticamente las consultas LINQ.
  • El peligro aparece al usar SQL crudo sin parametrizar.
  • Usa FromSqlInterpolated, SqlParameter o Dapper con parámetros.
  • Valida el input y aplica el principio de mínimo privilegio en la base de datos.
  • Los stored procedures también deben parametrizar internamente.

10 · Preguntas frecuentes

¿Las consultas LINQ de EF Core son 100% seguras?

Sí, contra SQL Injection, porque EF Core genera parámetros. El riesgo aparece cuando usas FromSqlRaw o consultas ad hoc mal construidas.

¿Puedo usar string.Format en SQL?

No. Cualquier forma de concatenar strings con input del usuario es vulnerable. Usa siempre parámetros.

¿Dapper es seguro?

Sí, si usas parámetros en el objeto anónimo o DynamicParameters. Nunca concatenes.

¿Los stored procedures protegen contra inyección SQL?

Solo si se llaman con parámetros. Un stored procedure que concatene internamente sigue siendo vulnerable.

¿Es seguro usar FromSqlInterpolated con cualquier tipo?

Sí, siempre que los valores vengan dentro de las llaves. No uses FromSqlRaw con strings interpolados.

¿Debo desactivar EnableSensitiveDataLogging en producción?

Sí. En producción solo se recomienda mostrar consultas SQL sin valores. Los datos sensibles nunca deben aparecer en logs.
