Proyecto CMS: auditoría de seguridad

Módulo 18 · Seguridad en APIs (OWASP)55 min

1 · Introducción

En esta lección final del módulo vamos a auditar el CMS que hemos construido a lo largo del curso. Revisaremos cada endpoint, cada servicio y cada pieza de configuración a la luz del OWASP Top 10 para APIs. Al terminar, el CMS contará con cabeceras de seguridad, rate limiting, autorización a nivel de objeto, gestión segura de secretos y un checklist de auditoría.

¿Qué problema resuelve? Evita que vulnerabilidades comunes lleguen a producción aplicando una revisión sistemática. La auditoría no es un evento único; es una práctica continua.

¿Cuándo se utiliza? Antes de cada despliegue importante, tras cambios en autenticación/autorización, o como parte de un pipeline de CI/CD. También es recomendable hacer auditorías trimestrales.

Errores típicos: hacer la auditoría solo al final del proyecto, no automatizarla, confiar en que "el framework ya lo hace", o no revisar endpoints deprecados y dependencias antiguas.

2 · Teoría

Una auditoría de seguridad no es solo un checklist; es un proceso que combina revisión manual, análisis estático, pruebas automatizadas y revisión de configuración. Para el CMS nos centraremos en los puntos más críticos:


Checklist de auditoría de seguridad para el CMS
───────────────────────────────────────────────
☐ Autenticación: JWT bien configurado, expiración, refresh tokens
☐ Autorización: BOLA resuelto en todos los endpoints con recursos
☐ Autorización funcional: policies y roles correctos
☐ Propiedades sensibles: DTOs específicos, nunca entidades completas
☐ Rate limiting: por usuario, por endpoint, con Retry-After
☐ SQL Injection: LINQ o SQL parametrizado
☐ XSS/CSRF: cabeceras de seguridad, JSON como salida
☐ SSRF: validación de URLs externas
☐ Secretos: user-secrets/env vars/Key Vault, nada en el repo
☐ Logs: no filtran secretos ni datos sensibles
☐ CORS: orígenes restringidos
☐ Versionado: endpoints versionados y deprecados documentados
☐ Dependencias: sin paquetes con vulnerabilidades conocidas
☐ Headers de seguridad: middleware global configurado
☐ Health checks: no exponen información sensible
☐ Errores: respuestas genéricas en producción, detalles en desarrollo

El objetivo no es alcanzar la seguridad perfecta, sino reducir la superficie de ataque y aplicar defensa en profundidad. Cada punto del checklist es una capa adicional de protección.

Enfoque práctico

Para el CMS, seguiremos un enfoque iterativo: primero revisaremos autenticación y autorización, luego configuración y headers, después rate limiting y finalmente dependencias y secretos. Este orden prioriza los riesgos más críticos y explotables.

3 · Ejemplo mínimo

Veamos un fragmento mínimo de la configuración segura del CMS en Program.cs. Este código combina autenticación, autorización, rate limiting y cabeceras de seguridad.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ClockSkew = TimeSpan.Zero
        };
    });

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("PostOwnerOrAdmin", policy =>
        policy.Requirements.Add(new PostOwnerOrAdminRequirement()));

    options.AddPolicy("CanEditPosts", policy =>
        policy.RequireRole("Admin", "Editor"));
});

builder.Services.AddRateLimiter(options =>
{
    options.AddSlidingWindowLimiter("general", opts =>
    {
        opts.PermitLimit = 100;
        opts.Window = TimeSpan.FromMinutes(1);
        opts.SegmentsPerWindow = 4;
    });
});

var app = builder.Build();

app.UseMiddleware<SecurityHeadersMiddleware>();
app.UseRateLimiter();
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();
app.Run();

4 · Ejemplo real

A continuación aplicamos las correcciones más importantes en los endpoints del CMS.

4.1 Autorización a nivel de objeto (A01)

app.MapPut("/api/v1/posts/{id:guid}", async (
    Guid id,
    UpdatePostRequest request,
    IMediator mediator,
    IAuthorizationService authorization,
    ClaimsPrincipal user,
    CancellationToken cancellationToken) =>
{
    var post = await mediator.Send(new GetPostQuery(id), cancellationToken);
    if (post is null) return Results.NotFound();

    var auth = await authorization.AuthorizeAsync(user, post, Operations.Update);
    if (!auth.Succeeded) return Results.Forbid();

    await mediator.Send(request with { Id = id }, cancellationToken);
    return Results.NoContent();
})
.RequireAuthorization("CanEditPosts");

4.2 Rate limiting en endpoints sensibles (A04, A06)

app.MapPost("/api/v1/posts", async (CreatePostRequest request, IMediator mediator) =>
{
    var postId = await mediator.Send(request);
    return Results.Created($"/api/v1/posts/{postId}", postId);
})
.RequireAuthorization("CanEditPosts")
.RequireRateLimiting("create-post");

app.MapPost("/api/auth/login", (LoginRequest request) => Results.Ok())
   .RequireRateLimiting("strict")
   .AllowAnonymous();

4.3 Middleware de cabeceras de seguridad (A08)

public class SecurityHeadersMiddleware(RequestDelegate next)
{
    public Task InvokeAsync(HttpContext context)
    {
        var headers = context.Response.Headers;

        headers.Append("X-Frame-Options", "DENY");
        headers.Append("X-Content-Type-Options", "nosniff");
        headers.Append("X-XSS-Protection", "0");
        headers.Append("Referrer-Policy", "strict-origin-when-cross-origin");
        headers.Append("Strict-Transport-Security", "max-age=31536000; includeSubDomains");
        headers.Append("Content-Security-Policy", "default-src 'none'; frame-ancestors 'none'");
        headers.Append("Permissions-Policy", "accelerometer=(), camera=(), geolocation=(), gyroscope=(), magnetometer=(), microphone=(), payment=(), usb=()");

        return next(context);
    }
}

4.4 Gestión de secretos

// appsettings.json: nunca incluyas secretos
{
  "Jwt": {
    "Issuer": "CmsApi",
    "Audience": "CmsClients"
  },
  "ConnectionStrings": {
    "Default": "Host=localhost;Database=cms;Username=cms_user"
  }
}

// Program.cs: obtener secreto desde configuración
var jwtSecret = builder.Configuration["Jwt:SecretKey"]
    ?? throw new InvalidOperationException("Jwt:SecretKey no configurado.");

// Validación de longitud mínima para JWT HMAC
if (jwtSecret.Length < 32)
    throw new InvalidOperationException("Jwt:SecretKey debe tener al menos 32 caracteres.");

4.5 CORS restrictivo

builder.Services.AddCors(options =>
{
    options.AddPolicy("CmsCorsPolicy", policy =>
    {
        policy.WithOrigins("https://cms.example.com", "https://admin.example.com")
              .WithMethods("GET", "POST", "PUT", "DELETE")
              .WithHeaders("Authorization", "Content-Type", "X-Requested-With")
              .AllowCredentials();
    });
});

app.UseCors("CmsCorsPolicy");

5 · Buenas prácticas

  • Auditoría periódica: repasa el checklist antes de cada release y trimestralmente.
  • Automatiza lo que puedas: dotnet list package --vulnerable, secret scanning en GitHub, análisis estático.
  • Prueba la seguridad: escribe tests que intenten acceder a recursos ajenos y esperen 403/404.
  • Documenta las decisiones: un ADR de seguridad ayuda a mantener el conocimiento.
  • Principio de mínimo privilegio: cada servicio, usuario de BD y API key debe tener solo los permisos necesarios.
  • Monitorea: usa OpenTelemetry y Serilog para detectar patrones de ataque (muchos 401/429/403).
  • Respuestas de error controladas: en producción, nunca devuelvas stack traces ni detalles internos.
  • Endpoints deprecados: desactívalos o documenta claramente que no deben usarse.
  • Health checks seguros: no expongan información sensible sobre la infraestructura.
  • Revisión de roles: asegúrate de que cada rol tenga exactamente los permisos que necesita.
Consejo: crea un proyecto de tests de seguridad separado con escenarios de ataque: BOLA, inyección SQL, fuerza bruta y SSRF. Estos tests deben ejecutarse en cada pull request.

7 · Ejercicio guiado

Vamos a completar la auditoría del CMS paso a paso.

  1. Revisa autenticación: verifica que el JWT tiene expiración corta (15 min) y refresh tokens rotan.
  2. Revisa autorización: asegúrate de que todos los endpoints con {id} verifican propiedad del recurso.
  3. Revisa DTOs: ningún endpoint debe devolver la entidad EF completa.
  4. Añade cabeceras de seguridad: registra el middleware global.
  5. Configura rate limiting: políticas generales y estrictas para auth/creación.
  6. Revisa secretos: mueve Jwt:SecretKey y connection strings a user-secrets/env vars.
  7. Configura CORS: restringe a orígenes conocidos y métodos necesarios.
  8. Ejecuta dotnet list package --vulnerable y actualiza paquetes vulnerables.
  9. Escribe tests de seguridad: un usuario no debe poder editar el post de otro.
  10. Revisa health checks: no expongan información sensible.
# Comando para detectar paquetes vulnerables
dotnet list package --vulnerable --include-transitive

# Ejecutar tests de seguridad
dotnet test tests/Cms.Api.SecurityTests

# Verificar cabeceras de seguridad
curl -I https://localhost:5001/api/v1/posts

8 · Reto

Implementa un pipeline de seguridad en CI/CD para el CMS. El pipeline debe:

  • Ejecutar dotnet list package --vulnerable y fallar si hay vulnerabilidades de alto severity.
  • Activar secret scanning de GitHub y revisar los alertas.
  • Correr los tests de seguridad antes de permitir el merge.
  • Generar un reporte de cabeceras de seguridad con curl -I contra el entorno de staging.
  • Implementar un scan de puertos o vulnerabilidades básico en la imagen Docker.

No resuelvas el reto todavía. Diseña primero el workflow de GitHub Actions y luego implementa cada paso.

9 · Resumen

  • La auditoría de seguridad del CMS combina autorización, rate limiting, headers y gestión de secretos.
  • Cada endpoint con recursos propios debe verificar BOLA.
  • Los DTOs y el mapeo manual/AutoMapper previenen la exposición accidental de datos.
  • Rate limiting, headers de seguridad y gestión de secretos son obligatorios en producción.
  • Automatiza la seguridad en CI/CD para mantenerla en el tiempo.
  • La seguridad del CMS es un proceso continuo, no un evento puntual.

10 · Preguntas frecuentes

¿Con esto el CMS es 100% seguro?

No. La seguridad es un proceso continuo. Esta auditoría cubre los riesgos más comunes, pero siempre pueden aparecer nuevos vectores. Mantén la vigilancia y actualiza controles.

¿Debo auditar también dependencias de frontend?

Si tu API sirve SPA o documentación, sí. En este curso nos centramos en el backend, pero un despliegue real requiere auditar todo el stack.

¿Con qué frecuencia ejecuto dotnet list package --vulnerable?

Como mínimo una vez por sprint y siempre en el pipeline de CI/CD. Las dependencias nuevas también deben revisarse antes de añadirse.

¿Dónde almaceno los tests de seguridad?

En un proyecto de tests separado, por ejemplo Cms.Api.SecurityTests, usando WebApplicationFactory para pruebas de integración.

¿Qué hago si el secret scanning detecta un secreto histórico?

Considera el secreto comprometido. Rótalo, revoca accesos y borra el secreto del historial si es posible. En GitHub, usa el mecanismo de revocación asistida.

¿Debo desactivar Swagger en producción?

Depende del caso. Si Swagger expone detalles internos de la API, es mejor desactivarlo en producción o protegerlo con autenticación. Considera usarlo solo en entornos internos.
