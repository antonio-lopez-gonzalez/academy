Secret scanning y gestión de secretos

Módulo 18 · Seguridad en APIs (OWASP)25 min

1 · Introducción

En esta lección aprenderemos a gestionar secretos en aplicaciones .NET: contraseñas de base de datos, claves de API, tokens de JWT, credenciales de servicios cloud. Veremos cómo almacenarlos de forma segura durante el desarrollo y en producción, y cómo evitar que terminen accidentalmente en el repositorio.

¿Qué problema resuelve? Evita que credenciales sensibles se filtren en el código fuente, los logs o el control de versiones. Una vez que un secreto está en un repositorio público o incluso privado, debe considerarse comprometido.

¿Cuándo se utiliza? Desde el primer día del proyecto. Cualquier valor que no deba ser público debe gestionarse como secreto: connection strings, claves de firma JWT, API keys, certificados, etc.

Errores típicos: hardcodear connection strings en appsettings.json, subir certificados al repositorio, pensar que "es solo un entorno de desarrollo", o loguear secretos por descuido.

2 · Teoría

En .NET 8, la configuración sigue una jerarquía de fuentes. Cuanto más específica es la fuente, mayor prioridad tiene:

  1. appsettings.json (valores por defecto, seguros de compartir)
  2. appsettings.{Environment}.json (valores por entorno)
  3. User secrets (desarrollo local)
  4. Variables de entorno (contenedores, CI/CD)
  5. Argumentos de línea de comandos
  6. Proveedores cloud (Azure Key Vault, AWS Secrets Manager)

La regla de oro es: los secretos nunca van al código fuente. Ni en appsettings.json, ni en comentarios, ni en scripts de prueba, ni en documentación.


Jerarquía de configuración en .NET
──────────────────────────────────
appsettings.json
  ↓
appsettings.Development.json
  ↓
User Secrets (desarrollo local)
  ↓
Variables de entorno (Docker, K8s, CI/CD)
  ↓
Azure Key Vault / AWS Secrets Manager (producción)

Además, debemos protegernos contra la filtración accidental. Las herramientas de secret scanning analizan el código y detectan patrones que parecen claves, tokens o contraseñas. GitHub, Azure DevOps y muchas herramientas locales ofrecen esta capacidad.

User secrets

Es el mecanismo recomendado para desarrollo local. Los secretos se almacenan fuera del repositorio en la carpeta de perfil del usuario. Funciona con IConfiguration sin cambios de código.

Variables de entorno

Es la forma estándar de inyectar secretos en contenedores y servidores. En .NET, las variables de entorno con doble guión bajo se mapean a jerarquías de configuración: ConnectionStrings__Default se convierte en ConnectionStrings:Default.

Proveedores cloud

Azure Key Vault, AWS Secrets Manager y HashiCorp Vault ofrecen almacenamiento centralizado, rotación, acceso basado en identidad y auditoría. Son la opción recomendada para producción.

3 · Ejemplo mínimo

Veamos cómo usar dotnet user-secrets para guardar una connection string local sin tocar appsettings.json.

# Inicializar user secrets en el proyecto de la API
dotnet user-secrets init --project src/Cms.Api/Cms.Api.csproj

# Establecer un secreto
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Database=cms;Username=cms_user;Password=supersecreta" --project src/Cms.Api/Cms.Api.csproj

# Listar secretos (valores ofuscados)
dotnet user-secrets list --project src/Cms.Api/Cms.Api.csproj

# Eliminar un secreto si es necesario
dotnet user-secrets remove "ConnectionStrings:Default" --project src/Cms.Api/Cms.Api.csproj

# Limpiar todos los secretos del proyecto
dotnet user-secrets clear --project src/Cms.Api/Cms.Api.csproj

En el código, accedemos a la connection string de la forma habitual. El proveedor de user secrets se carga automáticamente en entorno de desarrollo:

var connectionString = builder.Configuration
    .GetConnectionString("Default");

4 · Ejemplo real

En producción, los secretos deben venir de un almacén seguro. A continuación configuramos Azure Key Vault como fuente de configuración. El ejemplo es análogo para AWS Secrets Manager con su paquete correspondiente.

// Program.cs: cargar Key Vault solo en producción
if (builder.Environment.IsProduction())
{
    var keyVaultUrl = builder.Configuration["Azure:KeyVault:Url"];
    var credential = new DefaultAzureCredential();

    builder.Configuration.AddAzureKeyVault(
        new Uri(keyVaultUrl!),
        credential,
        new AzureKeyVaultConfigurationOptions
        {
            // Prefijo opcional para organizar secretos
            Manager = new KeyVaultSecretManager()
        });
}

En appsettings.json solo guardamos valores no secretos y la URL del almacén:

{
  "Azure": {
    "KeyVault": {
      "Url": "https://curso-dotnet-kv.vault.azure.net/"
    }
  },
  "Jwt": {
    "Issuer": "CmsApi",
    "Audience": "CmsClients"
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information"
    }
  }
}

En Docker o Kubernetes, usamos variables de entorno:

# docker-compose.yml (solo ejemplo, nunca en producción real)
services:
  cms-api:
    image: cms-api:latest
    environment:
      - ASPNETCORE_ENVIRONMENT=Production
      - ConnectionStrings__Default=Host=postgres;Database=cms;Username=cms_user;Password=${DB_PASSWORD}
      - Jwt__SecretKey=${JWT_SECRET_KEY}
    env_file:
      - .env
    depends_on:
      - postgres
      - redis

El archivo .env debe estar en .gitignore y nunca subirse al repositorio. En CI/CD, los secretos se inyectan desde GitHub Secrets, Azure DevOps Variables o el gestor de secretos del proveedor cloud. Nunca escribas secretos en los logs del pipeline, ni siquiera con echo para depurar.

Enmascarar secretos en logs

Serilog y otros loggers pueden escribir accidentalmente valores sensibles si un objeto de configuración se serializa completo. Podemos usar destructuring policies para evitarlo:

// Marcar propiedades sensibles para no loguearse
public class SensitiveSettings
{
    public string DatabasePassword { get; set; } = string.Empty;
    public string JwtSecretKey { get; set; } = string.Empty;

    public override string ToString()
    {
        return "[SensitiveSettings - valores enmascarados]";
    }
}

// O usar Serilog.Exceptions sin exponer datos
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Information()
    .WriteTo.Console()
    .Destructure.With<SensitiveDataDestructuringPolicy>()
    .CreateLogger();

En producción, nunca loguees la connection string completa ni el token. Si necesitas depurar, loguea solo el emisor o el hash de una clave.

GitHub Actions:

# .github/workflows/deploy.yml (fragmento)
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Build Docker image
        run: docker build -t cms-api:latest .
        env:
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
          JWT_SECRET_KEY: ${{ secrets.JWT_SECRET_KEY }}

5 · Buenas prácticas

  • Nunca hardcodees secretos: ni en desarrollo, ni en tests, ni en scripts.
  • Usa dotnet user-secrets en local: es la forma estándar en .NET para desarrollo.
  • Variables de entorno en contenedores: inyecta secretos en runtime, nunca en la imagen.
  • Usa un gestor de secretos cloud en producción: Azure Key Vault, AWS Secrets Manager, HashiCorp Vault.
  • Activa secret scanning en GitHub: detecta tokens y claves comprometidos automáticamente.
  • Rota secretos periódicamente: las claves de JWT, connection strings y API keys deben cambiar cada cierto tiempo.
  • No loguees secretos: configura Serilog para enmascarar valores sensibles.
  • Audita el acceso: los gestores de secretos cloud registran quién leyó qué y cuándo.
  • Limita el alcance: un secreto de desarrollo no debe funcionar en producción, y viceversa.
  • Revisa .gitignore: asegúrate de que archivos de credenciales, .env y certificados no se suban.
Consejo: añade siempre .env, *.pfx, secrets.json, *.pem, *.key y archivos de credenciales a tu .gitignore. Si un secreto se filtra, considera el repositorio comprometido y rótalo inmediatamente.

7 · Ejercicio guiado

Vamos a configurar user secrets para el CMS y verificar que no se filtran.

  1. Inicializa user secrets en el proyecto Cms.Api.
  2. Guarda un secreto llamado Jwt:SecretKey con un valor aleatorio de 32 caracteres.
  3. Lee el secreto en Program.cs y úsalo para configurar JWT.
  4. Verifica que el valor no aparece en appsettings.json.
  5. Revisa el archivo .gitignore del proyecto.
  6. Simula una filtración: escribe un secreto en un comentario de código y verifica que el secret scanning lo detecta.
// Program.cs: usar el secreto para JWT
var jwtSecret = builder.Configuration["Jwt:SecretKey"]
    ?? throw new InvalidOperationException("Jwt:SecretKey no está configurado.");

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(jwtSecret)),
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ClockSkew = TimeSpan.Zero
        };
    });

Para generar una clave segura en PowerShell:

# Generar 32 bytes aleatorios y convertir a Base64
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
[System.Convert]::ToBase64String($bytes)

8 · Reto

Configura Azure Key Vault o AWS Secrets Manager para el proyecto final del CMS. El reto incluye:

  • Crear el almacén de secretos en la nube.
  • Configurar la identidad administrada o credenciales necesarias.
  • Cargar los secretos como proveedor de configuración en producción.
  • Implementar rotación automática o manual del secreto de JWT.
  • Configurar Serilog para enmascarar valores sensibles en los logs.

No resuelvas el reto todavía. Investiga primero la documentación oficial de tu proveedor cloud.

9 · Resumen

  • Los secretos nunca deben estar en el código fuente.
  • .NET ofrece user secrets para desarrollo local y proveedores cloud para producción.
  • Las variables de entorno son la forma estándar de inyectar secretos en contenedores.
  • El secret scanning detecta filtraciones accidentales en el repositorio.
  • Configura correctamente .gitignore y evita loguear valores sensibles.
  • La rotación periódica y la separación por entorno reducen el impacto de una filtración.

10 · Preguntas frecuentes

¿Dónde se guardan los user secrets?

En un archivo JSON fuera del directorio del proyecto, en la carpeta de perfil del usuario. No se incluye en el control de versiones.

¿Puedo usar variables de entorno en desarrollo?

Sí, pero dotnet user-secrets es más cómodo porque persiste entre sesiones y está integrado con IConfiguration.

¿Qué hago si un secreto se filtra?

Revoquelo inmediatamente, rótelo y revisa los logs de acceso. Activa alertas de secret scanning para detectarlo pronto.

¿Es seguro pasar secretos por variables de entorno?

Más seguro que hardcodearlos, pero las variables de entorno pueden filtrarse en logs o dumps. Para máxima seguridad, usa un gestor de secretos con inyección en runtime.

¿Debo enmascarar secretos en Serilog?

Sí. Configura destructuring policies para evitar que propiedades como Password, Token, SecretKey o ConnectionString se escriban en los logs.

¿Qué herramientas de secret scanning existen?

GitHub ofrece secret scanning nativo. Otras opciones: truffleHog, git-secrets, GitGuardian, detect-secrets y análisis estático en CI/CD.
