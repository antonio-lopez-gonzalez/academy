Quartz.NET: alternativa enterprise

Módulo 15 · Background Jobs30 min

1. Introducción

En esta lección veremos Quartz.NET, una librería de planificación de tareas muy usada en entornos empresariales. Aunque Hangfire es más sencillo y viene con dashboard, Quartz.NET brinda un control mucho mayor sobre calendarios, triggers, jobs stateful y clustering.

Es la opción preferida cuando necesitas expresiones Cron complejas, múltiples triggers por job, clustering con varios nodos o ejecución sin almacenamiento de colas tipo "fire-and-forget".

Comparación rápida: Hangfire es ideal para jobs encolados, reintentos y dashboard visual. Quartz.NET es ideal para planificación cron, clustering y control fino de triggers.

2. Teoría

Conceptos de Quartz.NET

  • Job: la unidad de trabajo. Implementa IJob y contiene el código a ejecutar.
  • Trigger: define cuándo se ejecuta un job. Puede ser sencillo (SimpleTrigger) o basado en Cron (CronTrigger).
  • Scheduler: el orquestador que asocia jobs con triggers y los ejecuta.
  • JobDetail: metadatos del job, como su identificador, grupo y datos asociados.
  • JobDataMap: diccionario de datos que se pasa al job en cada ejecución.

Clustering

Quartz.NET puede configurarse con un job store JDBC o ADO.NET compartido. Cuando varias instancias apuntan al mismo almacén, solo una de ellas ejecuta cada trigger, logrando alta disponibilidad sin duplicar trabajos.

Expresiones Cron

Una expresión Cron tiene 6 o 7 campos: segundos, minutos, horas, día del mes, mes, día de la semana y opcionalmente año.

0 30 8 ? * MON-FRI  → de lunes a viernes a las 8:30
0 0/15 * * * ?       → cada 15 minutos
0 0 3 ? * 1          → todos los domingos a las 3:00

Job stores persistentes

Para producción, Quartz.NET debe configurarse con un jobStore persistente. El más común es AdoJobStore, que usa tablas en SQL Server o PostgreSQL. La configuración requiere especificar el delegate adecuado según el motor de base de datos:

builder.Services.AddQuartz(q =>
{
    q.UsePersistentStore(store =>
    {
        store.UsePostgres(connectionString);
        store.UseJsonSerializer();
    });
    q.UseClustering();
});

Con esta configuración, varios nodos pueden compartir el mismo scheduler y evitar la ejecución duplicada de triggers.

Listeners

Quartz.NET permite registrar listeners que reaccionan ante eventos del scheduler, de los jobs o de los triggers. Son útiles para logging centralizado, métricas o notificaciones.

public class LoggingJobListener : IJobListener
{
    public string Name => "LoggingJobListener";

    public Task JobToBeExecuted(IJobExecutionContext context, CancellationToken ct)
    {
        // Se ejecuta justo antes del job
        return Task.CompletedTask;
    }

    public Task JobWasExecuted(
        IJobExecutionContext context,
        JobExecutionException? jobException,
        CancellationToken ct)
    {
        // Se ejecuta después del job, incluso si falló
        return Task.CompletedTask;
    }
}

3. Ejemplo mínimo

Configuraremos Quartz.NET con un job recurrente que escribe un mensaje en los logs.

# Instalamos el paquete principal
dotnet add package Quartz.Extensions.Hosting
// HelloJob.cs
[DisallowConcurrentExecution] // Evita que dos instancias del mismo job se solapen
public class HelloJob(ILogger<HelloJob> logger) : IJob
{
    public Task Execute(IJobExecutionContext context)
    {
        logger.LogInformation("Hola desde Quartz.NET a las {Time}", DateTime.Now);
        return Task.CompletedTask;
    }
}
// Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddQuartz(q =>
{
    // Registramos el job con un identificador único
    var jobKey = new JobKey("hello-job", "demo");
    q.AddJob<HelloJob>(jobKey, j => j.WithDescription("Job de saludo"));

    // Configuramos el trigger: cada minuto
    q.AddTrigger(t => t
        .ForJob(jobKey)
        .WithIdentity("hello-trigger", "demo")
        .WithCronSchedule("0 * * ? * *")); // cada minuto
});

// Arranca el scheduler junto con el host
builder.Services.AddQuartzHostedService(q => q.WaitForJobsToComplete = true);

var app = builder.Build();
app.Run();
Tip: WaitForJobsToComplete = true hace que el host espere a que los jobs activos terminen antes de cerrar la aplicación.

4. Ejemplo real

Vamos a programar un job que genera un sitemap del CMS cada noche a las 2:00. El job recibe datos a través de JobDataMap y es stateful para evitar ejecuciones solapadas.

// ISitemapGenerator.cs
public interface ISitemapGenerator
{
    Task GenerateAsync(string outputPath, CancellationToken ct);
}
// GenerateSitemapJob.cs
[DisallowConcurrentExecution]
[PersistJobDataAfterExecution] // Guarda los datos del job entre ejecuciones
public class GenerateSitemapJob(
    ILogger<GenerateSitemapJob> logger,
    ISitemapGenerator generator) : IJob
{
    public async Task Execute(IJobExecutionContext context)
    {
        // Recuperamos parámetros del JobDataMap
        var outputPath = context.JobDetail.JobDataMap.GetString("OutputPath")!;
        var lastRun = context.JobDetail.JobDataMap.GetDateTime("LastRun");

        logger.LogInformation("Generando sitemap en {Path}. Última ejecución: {LastRun}",
            outputPath, lastRun);

        await generator.GenerateAsync(outputPath, context.CancellationToken);

        // Persistimos el momento de la última ejecución
        context.JobDetail.JobDataMap.Put("LastRun", DateTime.UtcNow);
    }
}
// Registro en Program.cs
builder.Services.AddQuartz(q =>
{
    var jobKey = new JobKey("sitemap-job", "cms");

    q.AddJob<GenerateSitemapJob>(jobKey, j =>
        j.WithDescription("Genera el sitemap del CMS")
         .UsingJobData("OutputPath", "wwwroot/sitemap.xml"));

    q.AddTrigger(t => t
        .ForJob(jobKey)
        .WithIdentity("sitemap-trigger", "cms")
        .WithCronSchedule("0 0 2 * * ?", x => x.InTimeZone(TimeZoneInfo.Utc))
        .WithDescription("Todos los días a las 2:00 UTC"));
});

builder.Services.AddQuartzHostedService(q => q.WaitForJobsToComplete = true);
Atributos clave: [DisallowConcurrentExecution] impide que el mismo job se ejecute dos veces simultáneamente. [PersistJobDataAfterExecution] guarda cambios en JobDataMap tras cada ejecución.

5. Buenas prácticas

  • Usa [DisallowConcurrentExecution]: evita que un job largo se solape consigo mismo si el trigger dispara antes de que termine.
  • Respeta context.CancellationToken: permite que Quartz cancele el trabajo si el scheduler se detiene.
  • No inyectes scoped services directamente: los jobs se crean por el scheduler; usa IServiceScopeFactory para crear scopes.
  • Documenta los triggers: usa WithDescription para saber qué hace cada Cron sin tener que descifrarlo.
  • Usa job store persistente en producción: ADO.NET con SQL Server o PostgreSQL permite clustering y recuperación ante caídas.
  • Configura misfire instructions: indica qué debe pasar si un trigger no se dispara a tiempo (ej. WithMisfireHandlingInstructionFireAndProceed).

6. Errores habituales

Error 1: no registrar el job en el scheduler

// ❌ MAL: solo añadimos el trigger sin asociarlo al job
q.AddTrigger(t => t.WithCronSchedule("0 * * ? * *"));

Solución: usa .ForJob(jobKey) o AddJob correctamente.

Error 2: inyectar DbContext en el job

// ❌ MAL: el DbContext es scoped
public class BadJob(DbContext context) : IJob { ... }
// ✅ BIEN: scope manual
public async Task Execute(IJobExecutionContext context)
{
    await using var scope = _scopeFactory.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<DbContext>();
}

Error 3: Cron incorrecto

Quartz.NET usa 6 campos obligatorios (con segundos). Una expresión de 5 campos dará error. Usa herramientas online para validar tus expresiones Cron.

Error 4: olvidar AddQuartzHostedService

Si solo llamas a AddQuartz, el scheduler no se arranca automáticamente con el host. Siempre añade AddQuartzHostedService.

7. Ejercicio guiado

Crea un job Quartz que cada 30 segundos compruebe si un archivo existe y escriba el resultado en el log.

  1. Crea un proyecto web: dotnet new web -n QuartzDemo.
  2. Instala Quartz.Extensions.Hosting.
  3. Crea FileCheckJob implementando IJob.
  4. Lee la ruta del archivo desde JobDataMap.
  5. Registra el job con un trigger cada 30 segundos: 0/30 * * ? * *.
  6. Añade AddQuartzHostedService.
  7. Ejecuta y observa los logs.

8. Reto

Configura Quartz.NET con un job store persistente en PostgreSQL y dos nodos de la misma aplicación. Comprueba que, aunque lances dos instancias, solo una ejecuta cada trigger. Investiga cómo configurar quartz.jobStore.clustered y quartz.jobStore.driverDelegateType.

9. Resumen

  • Quartz.NET es un scheduler enterprise con soporte para Cron, triggers complejos y clustering.
  • Un job implementa IJob; un trigger define cuándo se ejecuta.
  • AddQuartzHostedService arranca el scheduler junto con la aplicación.
  • Usa [DisallowConcurrentExecution] para jobs que no deben solaparse.
  • Elige Quartz.NET cuando necesites planificación avanzada; Hangfire para jobs encolados con dashboard.

10. Preguntas frecuentes

¿Puedo usar Quartz.NET sin ASP.NET Core?

Sí. El paquete Quartz.Extensions.Hosting funciona en cualquier proyecto que use IHost, incluyendo worker services.

¿Qué es un misfire?

Ocurre cuando un trigger no se dispara a tiempo porque el servidor estaba caído o porque otro job bloqueaba el thread pool. Quartz.NET permite configurar la política de recuperación.

¿Cómo testeo un job?

Crea una instancia del job inyectando mocks. Para IJobExecutionContext usa un mock de Moq o una implementación fake con los datos que necesites.

¿Qué job store uso en producción?

Para clustering usa ADO.NET con SQL Server o PostgreSQL. Para una sola instancia sencilla puedes usar RAMJobStore, pero perderás los triggers al reiniciar.

¿Puedo tener varios triggers para el mismo job?

Sí. Un mismo job puede tener múltiples triggers con diferentes horarios. Esto es útil cuando el mismo proceso debe ejecutarse en horarios distintos.

¿Cómo configuro el scheduler en múltiples nodos?

Usa q.UsePersistentStore(...) con PostgreSQL o SQL Server y llama a q.UseClustering(). Cada nodo usará el mismo job store y Quartz coordinará quién ejecuta cada trigger.
