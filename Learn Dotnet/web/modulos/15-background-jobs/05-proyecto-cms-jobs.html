Proyecto CMS: publicación automática + emails

Módulo 15 · Background Jobs50 min

1 · Introducción

En este proyecto integraremos todo lo aprendido en el módulo dentro del CMS que venimos construyendo. Implementaremos dos funcionalidades en segundo plano:

  • Un job programado que publica automáticamente los posts cuyo ScheduledAt ya ha llegado.
  • Un servicio de emails con Channel<T> que notifique a los suscriptores cuando un post se publique.

Usaremos Hangfire para el job programado y Channel<T> para el procesamiento de emails. También veremos cómo encadenar ambos sistemas de forma limpia.

Escenario real: un editor programa un post para las 9:00 del lunes. El job recurrente lo detecta, cambia su estado a Published y encola un email de notificación que el consumidor envía en segundo plano.

2 · Teoría

Arquitectura del flujo

┌─────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  Scheduler  │────▶│  Hangfire Job   │────▶│  PostPublisher  │
│  (cron)     │     │  cada minuto    │     │  publica posts  │
└─────────────┘     └─────────────────┘     └────────┬────────┘
                                                     │
                                                     ▼
                                            ┌─────────────────┐
                                            │  Channel<T>     │
                                            │  de notificaciones
                                            └────────┬────────┘
                                                     │
                                                     ▼
                                            ┌─────────────────┐
                                            │ EmailConsumer   │
                                            │ BackgroundService
                                            └─────────────────┘

Decisiones de diseño

  • Hangfire para publicación: necesitamos persistencia y reintentos si la base de datos no está disponible.
  • Channel<T> para emails: los emails son tareas rápidas, no críticas y toleran perderse si el proceso reinicia. Un canal en memoria es suficiente y muy eficiente.
  • Separación de responsabilidades: el job solo orquesta; la lógica de publicación y envío está en servicios testeables.

Idempotencia en la publicación

El job puede ejecutarse varias veces si hay reintentos. Por eso la consulta de posts programados debe filtrar solo aquellos que aún no están publicados. Así, ejecutar el job dos veces seguidas no publicará dos veces el mismo post.

Desacoplamiento con eventos de dominio

En lugar de que el job llame directamente al servicio de emails, publicaremos un evento de dominio PostPublishedEvent. Un handler encolará el email. Esto mantiene el dominio independiente de la infraestructura.

3 · Ejemplo mínimo

El núcleo del sistema es el job recurrente que consulta y publica posts. Veamos su versión más simple.

// IPostPublishingJob.cs
public interface IPostPublishingJob
{
    Task PublishScheduledPostsAsync();
}
// PostPublishingJob.cs
public class PostPublishingJob(
    ILogger<PostPublishingJob> logger,
    IPostRepository repository,
    IEventBus eventBus) : IPostPublishingJob
{
    [AutomaticRetry(Attempts = 3)]
    public async Task PublishScheduledPostsAsync()
    {
        var posts = await repository.GetScheduledToPublishAsync(DateTime.UtcNow);

        foreach (var post in posts)
        {
            post.Publish();
            await repository.UpdateAsync(post);

            await eventBus.PublishAsync(new PostPublishedEvent(
                post.Id, post.Title, post.AuthorEmail));

            logger.LogInformation("Post publicado: {Title}", post.Title);
        }
    }
}
// Registro del job recurrente
RecurringJob.AddOrUpdate<IPostPublishingJob>(
    "cms-publish-scheduled-posts",
    job => job.PublishScheduledPostsAsync(),
    Cron.Minutely);

4 · Ejemplo real

Ampliamos el ejemplo con el canal de emails, el consumidor como BackgroundService y la integración completa en Program.cs.

// Post.cs (modelo de dominio)
public class Post
{
    public Guid Id { get; private set; }
    public string Title { get; private set; } = string.Empty;
    public string AuthorEmail { get; private set; } = string.Empty;
    public PostStatus Status { get; private set; }
    public DateTime? ScheduledAt { get; private set; }

    public void Schedule(DateTime scheduledAt)
    {
        ScheduledAt = scheduledAt;
        Status = PostStatus.Scheduled;
    }

    public void Publish()
    {
        if (Status != PostStatus.Scheduled)
            throw new InvalidOperationException("Solo se pueden publicar posts programados");

        Status = PostStatus.Published;
        ScheduledAt = null;
    }
}

public enum PostStatus { Draft, Scheduled, Published, Archived }
// PostPublishedEvent.cs
public sealed record PostPublishedEvent(
    Guid PostId,
    string Title,
    string AuthorEmail);
// IEventBus.cs
public interface IEventBus
{
    Task PublishAsync<TEvent>(TEvent evt, CancellationToken ct = default) where TEvent : class;
}
// InMemoryEventBus.cs (versión simple para este módulo)
public class InMemoryEventBus(IServiceProvider provider) : IEventBus
{
    public async Task PublishAsync<TEvent>(TEvent evt, CancellationToken ct = default)
        where TEvent : class
    {
        var handlers = provider.GetServices<IEventHandler<TEvent>>();
        foreach (var handler in handlers)
        {
            await handler.HandleAsync(evt, ct);
        }
    }
}
// IEventHandler.cs
public interface IEventHandler<in TEvent> where TEvent : class
{
    Task HandleAsync(TEvent evt, CancellationToken ct);
}
// EnqueueEmailOnPostPublishedHandler.cs
public class EnqueueEmailOnPostPublishedHandler(
    IEmailChannel channel,
    ILogger<EnqueueEmailOnPostPublishedHandler> logger) : IEventHandler<PostPublishedEvent>
{
    public async Task HandleAsync(PostPublishedEvent evt, CancellationToken ct)
    {
        var message = new EmailMessage(
            evt.AuthorEmail,
            $"Tu post '{evt.Title}' ha sido publicado",
            "El post programado ya está disponible en el CMS.");

        await channel.Writer.WriteAsync(message, ct);
        logger.LogInformation("Email encolado para {Email}", evt.AuthorEmail);
    }
}
// EmailChannel.cs y EmailConsumerService.cs
public interface IEmailChannel
{
    ChannelWriter<EmailMessage> Writer { get; }
    ChannelReader<EmailMessage> Reader { get; }
}

public class EmailChannel : IEmailChannel
{
    private readonly Channel<EmailMessage> _channel =
        Channel.CreateBounded<EmailMessage>(new BoundedChannelOptions(500)
        {
            FullMode = BoundedChannelFullMode.Wait,
            SingleReader = true,
            SingleWriter = false
        });

    public ChannelWriter<EmailMessage> Writer => _channel.Writer;
    public ChannelReader<EmailMessage> Reader => _channel.Reader;
}

public class EmailConsumerService(
    ILogger<EmailConsumerService> logger,
    IEmailChannel channel,
    IEmailSender sender) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var message in channel.Reader.ReadAllAsync(stoppingToken))
        {
            try
            {
                await sender.SendAsync(message, stoppingToken);
                logger.LogInformation("Notificación enviada a {To}", message.To);
            }
            catch (Exception ex)
            {
                logger.LogError(ex, "Error enviando notificación a {To}", message.To);
            }
        }
    }
}
// Program.cs (fragmentos clave)
var builder = WebApplication.CreateBuilder(args);

// Base de datos del CMS
builder.Services.AddDbContext<CmsDbContext>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("Cms")));

// Hangfire con PostgreSQL
builder.Services.AddHangfire(config => config
    .SetDataCompatibilityLevel(CompatibilityLevel.Version_180)
    .UseSimpleAssemblyNameTypeSerializer()
    .UseRecommendedSerializerSettings()
    .UsePostgreSqlStorage(builder.Configuration.GetConnectionString("Hangfire")));

builder.Services.AddHangfireServer(options => options.WorkerCount = 2);

// Canal de emails en memoria
builder.Services.AddSingleton<IEmailChannel, EmailChannel>();
builder.Services.AddHostedService<EmailConsumerService>();

// Eventos y handlers
builder.Services.AddSingleton<IEventBus, InMemoryEventBus>();
builder.Services.AddSingleton<IEventHandler<PostPublishedEvent>, EnqueueEmailOnPostPublishedHandler>();

// Jobs y servicios
builder.Services.AddScoped<IPostPublishingJob, PostPublishingJob>();
builder.Services.AddScoped<IPostRepository, PostRepository>();
builder.Services.AddSingleton<IEmailSender, FakeEmailSender>();

var app = builder.Build();

app.UseHangfireDashboard("/hangfire", new DashboardOptions
{
    Authorization = [new HangfireAuthorizationFilter()]
});

// Registramos jobs recurrentes
RecurringJob.AddOrUpdate<IPostPublishingJob>(
    "cms-publish-scheduled-posts",
    job => job.PublishScheduledPostsAsync(),
    Cron.Minutely,
    new RecurringJobOptions { TimeZone = TimeZoneInfo.Utc });

app.MapControllers();
app.Run();
Importante: en un módulo posterior reemplazaremos el InMemoryEventBus por una solución más robusta. Por ahora nos sirve para entender el flujo sin añadir infraestructura extra.

5 · Buenas prácticas

  • El job no conoce al canal: solo publica un evento de dominio. El handler decide si encolar un email, una notificación push, etc.
  • Filtra por estado en la consulta: la publicación solo debe afectar a posts Scheduled con ScheduledAt <= ahora.
  • Usa transacciones: si el job actualiza varios posts, envuélvelo en una transacción para mantener la consistencia.
  • Protege el dashboard: nunca expongas /hangfire sin autenticación.
  • Monitoriza el canal: añade métricas de mensajes encolados y enviados para detectar cuellos de botella.
  • Jobs idempotentes: asegúrate de que publicar dos veces el mismo post no duplique emails ni cambie el estado incorrectamente.

6 · Errores habituales

Error 1: el job publica posts ya publicados

// ❌ MAL: podría devolver posts ya publicados
var posts = await repository.GetScheduledToPublishAsync(DateTime.UtcNow);

Solución: asegúrate de que el repositorio filtre por Status == Scheduled.

Error 2: el handler bloquea la publicación

// ❌ MAL: enviar el email de forma síncrona retrasa el job
await _smtpClient.SendAsync(email);

Solución: encola el email en Channel<T> y deja que un consumidor lo envíe después.

Error 3: no gestionar el cierre del canal

Si la aplicación se reinicia, los emails pendientes en el canal se pierden. Decide si esto es aceptable; si no, usa Hangfire también para emails.

Error 4: registrar handlers como scoped incorrectamente

En este ejemplo usamos un bus en memoria. Si el handler necesita DbContext, crea un scope manual dentro de HandleAsync.

9 · Resumen

  • El proyecto CMS ahora incluye publicación automática de posts con Hangfire.
  • Los eventos de dominio desacoplan la publicación del envío de notificaciones.
  • Channel<T> procesa los emails en segundo plano de forma eficiente.
  • Los jobs deben ser idempotentes y los handlers no deben bloquear la lógica principal.
  • El dashboard de Hangfire debe protegerse en producción.

10 · Preguntas frecuentes

¿Por qué no usar Hangfire también para los emails?

Podrías hacerlo. Sin embargo, Channel<T> es más ligero para notificaciones de alta frecuencia que toleran pérdida ocasional. Hangfire añade latencia por la persistencia en base de datos.

¿Cada cuánto debe ejecutarse el job de publicación?

Depende de la precisión que necesites. Cron.Minutely es suficiente para la mayoría de CMS. Si necesitas precisión de segundos, considera un job más frecuente o un servicio dedicado.

¿Qué pasa si el job falla a mitad de publicar varios posts?

Hangfire reintentará el job completo. Por eso la publicación debe ser idempotente: los posts ya publicados no deben volver a cambiar de estado.

¿Puedo separar el consumidor de emails en otro proceso?

Sí. En un sistema más grande, el consumidor puede ser un worker service independiente. El canal de memoria solo funciona dentro del mismo proceso; para separarlos necesitarías una cola externa.
