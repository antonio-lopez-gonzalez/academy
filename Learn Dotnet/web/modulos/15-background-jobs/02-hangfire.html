Hangfire: trabajos programados

Módulo 15 · Background Jobs35 min

1. Introducción

En esta lección aprenderemos a usar Hangfire, una librería muy popular en .NET para ejecutar tareas en segundo plano de forma persistente. A diferencia de un BackgroundService casero, Hangfire almacena los trabajos en una base de datos, los reintenta automáticamente si fallan y ofrece un panel de administración web.

Es útil cuando necesitas procesos que sobrevivan a reinicios de la aplicación, como enviar un email de bienvenida, generar informes nocturnos o sincronizar datos con sistemas externos.

Diferencia clave: BackgroundService vive en memoria; si el proceso se reinicia, el trabajo se pierde. Hangfire persiste los trabajos en SQL Server, PostgreSQL o Redis.

2. Teoría

Componentes principales de Hangfire

  • Client: es el código que encola un trabajo. Puede ser un endpoint de la API, un handler de MediatR o un servicio.
  • Server: es el proceso que lee trabajos de la cola y los ejecuta. En ASP.NET Core suele ser la misma aplicación, pero también puede ser un worker aparte.
  • Storage: el almacén persistente donde se guardan los trabajos, estados y métricas. PostgreSQL y SQL Server son los más comunes.
  • Dashboard: interfaz web para monitorizar trabajos, reintentos y colas.

Tipos de trabajos

  • Fire-and-forget: se ejecuta una sola vez, lo antes posible. BackgroundJob.Enqueue.
  • Delayed: se ejecuta una sola vez en el futuro. BackgroundJob.Schedule.
  • Recurring: se ejecuta periódicamente con una expresión Cron. RecurringJob.AddOrUpdate.
  • Continuation: se ejecuta después de que otro trabajo termine. BackgroundJob.ContinueJobWith.

Idempotencia

Un trabajo puede ejecutarse más de una vez si hay reintentos o si varios servidores lo intentan. Por eso los jobs deben ser idempotentes: ejecutarlos una o varias veces debe dejar el sistema en el mismo estado final.

Serialización de jobs

Hangfire serializa el nombre del tipo y los argumentos del método. No puede ejecutar métodos anónimos o lambdas que capturen variables locales complejas. El método debe ser público y pertenecer a una clase concreta.

Colas y prioridades

Hangfire permite organizar trabajos en colas. Por defecto existe la cola default, pero puedes crear colas como emails, reports o imports. Cada servidor puede configurarse para procesar colas específicas, aislando cargas pesadas de las urgentes.

[Queue("emails")]
public class EmailJob : IEmailSender { ... }

Reintentos y políticas

Hangfire reintenta automáticamente los jobs fallidos con un backoff exponencial: 10 segundos, 1 minuto, 10 minutos, etc. Puedes personalizar el número de intentos o desactivar los reintentos para errores de validación.

3. Ejemplo mínimo

Configuraremos Hangfire con almacenamiento en PostgreSQL y encolaremos un trabajo de ejemplo.

# Añadimos los paquetes necesarios
dotnet add package Hangfire.AspNetCore
dotnet add package Hangfire.PostgreSql
// Program.cs
var builder = WebApplication.CreateBuilder(args);

// Configuramos Hangfire con PostgreSQL
builder.Services.AddHangfire(config => config
    .SetDataCompatibilityLevel(CompatibilityLevel.Version_180)
    .UseSimpleAssemblyNameTypeSerializer()
    .UseRecommendedSerializerSettings()
    .UsePostgreSqlStorage(
        builder.Configuration.GetConnectionString("Hangfire")));

// Arrancamos el servidor que procesa los trabajos
builder.Services.AddHangfireServer();

var app = builder.Build();

// Habilitamos el dashboard en /hangfire
app.UseHangfireDashboard();

app.MapGet("/welcome", (IBackgroundJobClient jobs) =>
{
    // Encolamos un trabajo fire-and-forget
    jobs.Enqueue<IEmailSender>(sender => sender.SendWelcomeEmail("alumno@dotnet.es"));
    return Results.Accepted();
});

app.Run();
// IEmailSender.cs
public interface IEmailSender
{
    Task SendWelcomeEmail(string email);
}

public class EmailSender(ILogger<EmailSender> logger) : IEmailSender
{
    public Task SendWelcomeEmail(string email)
    {
        logger.LogInformation("Enviando email de bienvenida a {Email}", email);
        return Task.CompletedTask;
    }
}
Tip: usa interfaces para los jobs. Hangfire serializa la expresión sender => sender.SendWelcomeEmail(...), pero el contenedor resuelve la implementación real al ejecutar.

4. Ejemplo real

Construiremos un sistema que publica automáticamente artículos programados cada día a las 8:00. Incluye un job recurrente, configuración de reintentos y un job encolado cuando un usuario programa una publicación.

// IPostPublisher.cs
public interface IPostPublisher
{
    Task PublishScheduledPostsAsync();
}

public class PostPublisher(
    ILogger<PostPublisher> logger,
    IPostRepository repository,
    IEmailSender emailSender) : IPostPublisher
{
    [AutomaticRetry(Attempts = 3, LogEvents = true)]
    public async Task PublishScheduledPostsAsync()
    {
        logger.LogInformation("Buscando posts programados para publicar");

        var posts = await repository.GetScheduledPostsAsync(DateTime.UtcNow);

        foreach (var post in posts)
        {
            post.Publish();
            await repository.UpdateAsync(post);

            // Encolamos un email como continuación del proceso
            BackgroundJob.Enqueue<IEmailSender>(
                sender => sender.NotifyPublication(post.AuthorEmail, post.Title));
        }

        logger.LogInformation("{Count} posts publicados", posts.Count);
    }
}
// Registro del job recurrente al arrancar
public static class HangfireJobRegistration
{
    public static void RegisterRecurringJobs()
    {
        // Cron diario a las 08:00 UTC
        RecurringJob.AddOrUpdate<IPostPublisher>(
            "publish-scheduled-posts",
            publisher => publisher.PublishScheduledPostsAsync(),
            Cron.Daily(8, 0),
            new RecurringJobOptions
            {
                TimeZone = TimeZoneInfo.Utc
            });
    }
}
// Program.cs (fragmento relevante)
builder.Services.AddHangfire(config => config
    .UsePostgreSqlStorage(builder.Configuration.GetConnectionString("Hangfire")));

builder.Services.AddHangfireServer(options =>
{
    // Número de trabajos concurrentes por servidor
    options.WorkerCount = 2;
});

var app = builder.Build();

app.UseHangfireDashboard("/hangfire", new DashboardOptions
{
    Authorization = [new BasicAuthAuthorizationFilter("admin", "P@ssw0rd!")]
});

// Registramos los jobs recurrentes una vez construida la aplicación
HangfireJobRegistration.RegisterRecurringJobs();

app.Run();
Seguridad: en producción protege el dashboard con autenticación real o deshabilítalo. Nunca expongas /hangfire sin autorización.

5. Buenas prácticas

  • Haz los jobs idempotentes: verifica el estado actual antes de actuar para evitar efectos duplicados.
  • Mantén los jobs cortos: si un trabajo es muy largo, divídelo en subtareas o usa un job recurrente que procese lotes.
  • Usa transacciones: si el job actualiza base de datos, envuelve la lógica en una transacción.
  • Configura reintentos con criterio: no reintices errores de validación; sí reintenta fallos transitorios de red.
  • Monitoriza el dashboard: revisa trabajos fallidos y ajusta colas y workers.
  • Extrae la lógica a servicios: el job solo debe orquestar; la lógica de negocio debe estar en servicios testeables.

6. Errores habituales

Error 1: ejecutar jobs sin storage persistente

// ❌ MAL: en memoria los trabajos desaparecen al reiniciar
builder.Services.AddHangfire(config => config.UseInMemoryStorage());

Solución: usa PostgreSQL, SQL Server o Redis para cualquier entorno que no sea una demo local.

Error 2: lambdas con variables capturadas

// ❌ MAL: la lambda captura una variable local
var postId = 42;
BackgroundJob.Enqueue(() => publisher.Publish(postId)); // puede funcionar, pero es frágil

Mejor opción: pasa los argumentos directamente en la expresión de la interfaz.

Error 3: no proteger el dashboard

El dashboard permite ver y reencolar trabajos. En producción configura autenticación y autorización adecuadas.

Error 4: jobs no idempotentes

// ❌ MAL: si se ejecuta dos veces, se envían dos emails
public async Task SendWelcomeEmail(string email)
{
    await _smtpClient.SendAsync(email);
}
// ✅ BIEN: comprobamos si ya se envió
public async Task SendWelcomeEmail(string email)
{
    if (await _repository.WasEmailSentAsync(email)) return;
    await _smtpClient.SendAsync(email);
    await _repository.MarkEmailAsSentAsync(email);
}

9. Resumen

  • Hangfire permite ejecutar trabajos en segundo plano de forma persistente y monitorizable.
  • Soporta trabajos fire-and-forget, delayed, recurring y continuation.
  • Necesita un storage persistente como PostgreSQL, SQL Server o Redis.
  • El dashboard facilita la monitorización, pero debe protegerse en producción.
  • Los jobs deben ser idempotentes para evitar efectos colaterales en reintentos.

10. Preguntas frecuentes

¿Puedo ejecutar Hangfire en un worker service sin ASP.NET Core?

Sí. Añade AddHangfireServer a un proyecto de tipo worker y usa BackgroundJob.Enqueue desde cualquier sitio donde tengas acceso al client.

¿Hangfire es gratuito?

La versión open source es gratuita e incluye la mayoría de funcionalidades. Existen extensiones de pago como Hangfire Pro para batches y queues avanzadas.

¿Cómo escalo Hangfire?

Simplemente lanza más instancias de la aplicación apuntando al mismo storage. Hangfire usa locking a nivel de base de datos para evitar que dos servidores ejecuten el mismo trabajo.

¿Puedo usar Redis como storage?

Sí, mediante Hangfire.Redis.StackExchange. Redis es más rápido para colas muy activas, pero PostgreSQL es más sencillo de mantener y respaldar.

¿Cómo configuro colas separadas?

Usa el atributo [Queue("nombre")] en el job y configura AddHangfireServer(options => options.Queues = ["emails", "default"]) para indicar qué colas procesa cada servidor.

¿Qué pasa si un job nunca termina?

Hangfire usa un heartbeat y un tiempo de expiración (SlidingInvisibilityTimeout). Si un servidor desaparece, el trabajo vuelve a estar disponible para otro servidor tras el timeout configurado.
