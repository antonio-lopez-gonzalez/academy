Channel<T> para productor/consumidor

Módulo 15 · Background Jobs30 min

1 · Introducción

En esta lección aprenderemos a usar System.Threading.Channels.Channel<T>, una cola asíncrona y de alto rendimiento incluida en .NET. Es la herramienta ideal para implementar el patrón productor/consumidor dentro de un mismo proceso.

Un channel permite que un hilo escriba tareas mientras otro las procesa, sin bloqueos innecios y con control de backpressure si la cola tiene límite. Es útil para encolar emails, eventos de dominio o trabajos que no necesitan persistencia entre reinicios.

Cuándo usar Channel<T>: cuando necesitas una cola en memoria rápida, ligera y sin dependencias externas, y puedes permitirte perder los mensajes no procesados al reiniciar.

2 · Teoría

¿Qué es un channel?

Un Channel<T> es una estructura de datos que conecta un writer (productor) con uno o varios readers (consumidores). Es similar a BlockingCollection<T> pero completamente asíncrono y optimizado para async/await.

Canales ilimitados y limitados

  • Unbounded: no tiene límite de capacidad. El productor nunca espera, pero puede consumir memoria ilimitada.
  • Bounded: tiene un tamaño máximo. Si la cola está llena, el productor espera hasta que haya espacio (backpressure).

API principal

  • Channel.CreateUnbounded<T>() y Channel.CreateBounded<T>(capacity).
  • ChannelWriter<T>: escribe con WriteAsync, completa con Complete.
  • ChannelReader<T>: lee con ReadAllAsync o TryRead/WaitToReadAsync.

Backpressure

Con un canal limitado, el productor puede esperar o descartar mensajes. Esto protege al consumidor de ser saturado. Es especialmente útil cuando el productor es mucho más rápido que el consumidor.

Advertencia: los datos de un Channel<T> residen en memoria. Si el proceso se reinicia, los mensajes pendientes se pierden. Para durabilidad usa Hangfire, Quartz persistente o una cola como RabbitMQ.

¿Cuándo prefiero Channel<T> sobre otras colas?

  • Channel<T>: mismo proceso, alta frecuencia, baja latencia, no necesitas operaciones.
  • Hangfire/Quartz: persistencia, reintentos, planificación y monitorización.
  • RabbitMQ / Azure Service Bus: comunicación entre procesos o máquinas, mayor durabilidad.

3 · Ejemplo mínimo

Creamos un canal ilimitado, un productor que escribe números y un consumidor que los imprime.

// Program.cs
using var cts = new CancellationTokenSource();
Console.CancelKeyPress += (_, e) =>
{
    e.Cancel = true;
    cts.Cancel();
};

// Creamos un canal de enteros sin límite
var channel = Channel.CreateUnbounded<int>();

// Tarea productora
var producer = Task.Run(async () =>
{
    for (var i = 1; i <= 10; i++)
    {
        await channel.Writer.WriteAsync(i, cts.Token);
        Console.WriteLine($"Producido: {i}");
        await Task.Delay(200, cts.Token);
    }

    // Indicamos que no habrá más mensajes
    channel.Writer.Complete();
});

// Tarea consumidora
var consumer = Task.Run(async () =>
{
    await foreach (var item in channel.Reader.ReadAllAsync(cts.Token))
    {
        Console.WriteLine($"Consumido: {item}");
    }
});

await Task.WhenAll(producer, consumer);
Console.WriteLine("Fin");

Para ejecutarlo:

dotnet new console -n ChannelDemo
dotnet run --project ChannelDemo
Tip: await foreach con ReadAllAsync es la forma más limpia de consumir un canal. El bucle termina automáticamente cuando el writer llama a Complete.

4 · Ejemplo real

Vamos a integrar Channel<T> en una API que recibe solicitudes de envío de email y las procesa en segundo plano. Usaremos un canal limitado para aplicar backpressure y un BackgroundService como consumidor.

// EmailMessage.cs
public sealed record EmailMessage(string To, string Subject, string Body);
// IEmailChannel.cs
public interface IEmailChannel
{
    ValueTask TryWriteAsync(EmailMessage message, CancellationToken ct);
    ValueTask<EmailMessage> ReadAsync(CancellationToken ct);
}
// EmailChannel.cs
public class EmailChannel : IEmailChannel
{
    private readonly Channel<EmailMessage> _channel =
        Channel.CreateBounded<EmailMessage>(new BoundedChannelOptions(100)
        {
            FullMode = BoundedChannelFullMode.Wait,
            SingleReader = true,
            SingleWriter = false
        });

    public ValueTask TryWriteAsync(EmailMessage message, CancellationToken ct)
        => _channel.Writer.TryWrite(message);

    public ValueTask<EmailMessage> ReadAsync(CancellationToken ct)
        => _channel.Reader.ReadAsync(ct);
}
// EmailConsumerService.cs
public class EmailConsumerService(
    ILogger<EmailConsumerService> logger,
    IEmailChannel channel,
    IEmailSender sender) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        logger.LogInformation("Consumidor de emails arrancado");

        await foreach (var message in channel.ReadAsync(stoppingToken))
        {
            try
            {
                await sender.SendAsync(message, stoppingToken);
                logger.LogInformation("Email enviado a {To}", message.To);
            }
            catch (Exception ex)
            {
                logger.LogError(ex, "Error enviando email a {To}", message.To);
            }
        }
    }
}

// Extensión para permitir await foreach sobre IEmailChannel
public static class EmailChannelExtensions
{
    public static IAsyncEnumerable<EmailMessage> ReadAllAsync(
        this IEmailChannel channel, CancellationToken ct)
    {
        // Implementación simplificada para el ejemplo
        return ReadAllCore(channel, ct);
    }

    private static async IAsyncEnumerable<EmailMessage> ReadAllCore(
        IEmailChannel channel, [EnumeratorCancellation] CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            yield return await channel.ReadAsync(ct);
        }
    }
}
// Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSingleton<IEmailChannel, EmailChannel>();
builder.Services.AddHostedService<EmailConsumerService>();
builder.Services.AddSingleton<IEmailSender, FakeEmailSender>();

var app = builder.Build();

app.MapPost("/send-email", async (EmailMessage message, IEmailChannel channel) =>
{
    var written = await channel.TryWriteAsync(message, default);
    return written
        ? Results.Accepted(value: new { status = "encolado" })
        : Results.Problem("La cola de emails está saturada", statusCode: 503);
});

app.Run();
Patrón productor/consumidor: el endpoint actúa como productor rápido; el BackgroundService actúa como consumidor lento. El canal desacopla ambos y protege al sistema contra picos de carga.

5 · Buenas prácticas

  • Prefiere canales limitados: evitan que la memoria crezca indefinidamente bajo carga.
  • Define una política de cola llena: Wait, DropNewest, DropOldest o DropWrite según el caso.
  • Completa el writer al cerrar: llama a Writer.Complete() para que los consumidores terminen su await foreach.
  • Usa CancellationToken en lecturas y escrituras: permite un cierre limpio.
  • No captures excepciones del canal: las operaciones canceladas lanzan OperationCanceledException; trátala como señal de cierre.
  • Considera múltiples consumidores: configura SingleReader = false si varios servicios van a leer del mismo canal.

6 · Errores habituales

Error 1: canal ilimitado bajo carga alta

// ❌ MAL: puede agotar la memoria
var channel = Channel.CreateUnbounded<EmailMessage>();

Solución: usa CreateBounded con una capacidad razonable y una política de cola llena.

Error 2: no completar el writer

// ❌ MAL: el consumidor quedará esperando para siempre
await foreach (var item in channel.Reader.ReadAllAsync(ct)) { ... }

Solución: llama a channel.Writer.Complete() cuando el productor termine.

Error 3: mezclar single reader/writer incorrectamente

Si configuras SingleReader = true pero lees desde varios consumidores, el comportamiento puede ser incorrecto o ineficiente. Ajusta las opciones a tu arquitectura real.

Error 4: usar Channel<T> como cola persistente

Los mensajes se pierden al reiniciar. Para durabilidad usa Hangfire, Quartz persistente o un broker de mensajería.

7 · Ejercicio guiado

Crea un canal limitado de capacidad 5 con política DropOldest. Un productor escribe 20 números rápidamente y un consumidor los procesa cada segundo. Comprueba cuántos mensajes se descartan.

  4. El consumidor espera 1 segundo entre lecturas.

8 · Reto

Implementa un sistema con dos consumidores leyendo del mismo canal. Asegúrate de que cada mensaje solo se procese una vez. Para ello tendrás que ajustar SingleReader y gestionar la competencia entre consumidores.

9 · Resumen

  • Channel<T> es una cola asíncrona en memoria ideal para el patrón productor/consumidor.
  • Puede ser ilimitada o limitada; las limitadas aplican backpressure.
  • ChannelWriter<T> produce; ChannelReader<T> consume.
  • Integra el canal con BackgroundService para procesar mensajes en segundo plano.
  • No es una cola persistente; reiniciar el proceso pierde los mensajes pendientes.

10 · Preguntas frecuentes

¿Channel<T> reemplaza a Queue<T>?

No exactamente. Queue<T> es síncrona y no está pensada para escenarios async/await. Channel<T> está optimizada para concurrencia asíncrona.

¿Es thread-safe?

Sí. Múltiples productores y consumidores pueden escribir y leer concurrentemente si las opciones del canal lo permiten.

¿Puedo usar Channel<T> entre procesos?

No. Es solo para comunicación dentro de un proceso. Para procesos distintos usa un broker como RabbitMQ, Azure Service Bus o Redis Streams.

¿Qué diferencia hay entre TryWrite y WriteAsync?

TryWrite intenta escribir inmediatamente y devuelve false si no puede. WriteAsync espera hasta que haya espacio en canales limitados.
