Middleware personalizado

Módulo 10 · Middleware y pipelines30 min

1. Introducción

ASP.NET Core incluye middlewares útiles de serie, pero casi siempre necesitas algo propio: añadir una cabecera de trazabilidad, medir tiempos, loguear el body, transformar la respuesta o normalizar la cultura. En esta lección aprenderemos a crear middlewares profesionales, registrarlos con métodos de extensión y decidir cuándo usar clases que implementan IMiddleware frente a middlewares inline.

¿Qué problema resuelve?

Permite encapsular comportamiento transversal de forma testable y reutilizable. En lugar de repetir lógica en cada endpoint, la colocas en un middleware que se aplica a todas las peticiones o a un subconjunto.

Errores típicos

  • Crear un middleware inline gigante en Program.cs que no se puede testear.
  • Implementar IMiddleware pero registrarlo como singleton, perdiendo el scope y generando captive dependencies.
  • Leer el body de la petición sin habilitar el rewind (el endpoint se queda sin datos).
  • Olvidar liberar recursos que el middleware reserva, como MemoryStream temporales.

2. Teoría

Dos formas de crear middleware

Podemos escribir middleware de dos maneras:

  • Inline: con app.Use(async (context, next) => ...). Es rápido para pruebas o middleware muy simples.
  • Clase: heredando de IMiddleware o siguiendo la convención de InvokeAsync. Es la forma profesional: permite inyección de dependencias, testing unitario y reutilización.

Convención de middleware por clase

Una clase middleware puede seguir dos convenciones:

  • Método public async Task InvokeAsync(HttpContext context, RequestDelegate next). La clase debe instanciarse manualmente o registrarse con una fábrica.
  • Implementar IMiddleware con Task InvokeAsync(HttpContext context, RequestDelegate next). El runtime la instancia a través de DI.

¿Cuál elegir?

Usa IMiddleware cuando necesites inyección de dependencias y quieras que la instancia se resuelva desde el contenedor. Es la forma más limpia y testable. Usa la convención InvokeAsync si necesitas crear el middleware sin depender de DI.

Extensión del pipeline

Para que Program.cs sea legible, se crean métodos de extensión UseXxx:

public static class MiddlewareExtensions
{
    public static IApplicationBuilder UseRequestTiming(this IApplicationBuilder app)
    {
        return app.UseMiddleware();
    }
}

Así en Program.cs escribimos:

app.UseRequestTiming();

Bifurcación del pipeline

app.Map crea una rama nueva que no vuelve a la principal. app.UseWhen añade middleware condicional que sí vuelve. Esto es útil para aplicar comportamiento solo a APIs, a archivos estáticos o a rutas de administración.

API¿Vuelve?Uso típico
app.MapNoSubaplicaciones: /api, /health
app.UseWhenSíMiddleware condicional para un subconjunto de rutas

3. Ejemplo mínimo

Crearemos un middleware con IMiddleware que mide el tiempo de respuesta y lo expone como cabecera.

dotnet new web -n CustomMiddleware -o CustomMiddleware
cd CustomMiddleware
dotnet run --project .
// Middleware/RequestTimingMiddleware.cs
using System.Diagnostics;

public sealed class RequestTimingMiddleware : IMiddleware
{
    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        var stopwatch = Stopwatch.StartNew();
        await next(context);
        stopwatch.Stop();

        context.Response.Headers.Append("X-Response-Time-ms", stopwatch.ElapsedMilliseconds.ToString());
    }
}
// Middleware/MiddlewareExtensions.cs
public static class MiddlewareExtensions
{
    public static IApplicationBuilder UseRequestTiming(this IApplicationBuilder app)
        => app.UseMiddleware();
}
// Program.cs
var builder = WebApplication.CreateBuilder(args);

// Registramos el middleware como transient; IMiddleware se resuelve por DI
builder.Services.AddTransient();

var app = builder.Build();

app.UseRequestTiming();

app.MapGet("/", () => "Hola");

app.Run();

¿Qué ocurre aquí?

La clase implementa IMiddleware, por lo que ASP.NET Core la instancia desde DI. El método de extensión UseRequestTiming hace que el pipeline sea legible y permite reutilizar el middleware en otros proyectos.

4. Ejemplo real

Un middleware común en producción es el que loguea el cuerpo de las peticiones y respuestas. Es útil para debugging, pero hay que hacerlo con cuidado porque el body de la petición solo se puede leer una vez y el de la respuesta no siempre es re-escribible.

// Middleware/RequestResponseLoggingMiddleware.cs
public sealed class RequestResponseLoggingMiddleware : IMiddleware
{
    private readonly ILogger _logger;

    public RequestResponseLoggingMiddleware(ILogger logger)
    {
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        context.Request.EnableBuffering();
        var requestBody = await ReadStreamAsync(context.Request.Body);
        context.Request.Body.Position = 0;

        _logger.LogInformation("Request {Method} {Path}: {Body}",
            context.Request.Method,
            context.Request.Path,
            requestBody);

        var originalResponseBody = context.Response.Body;
        using var responseBody = new MemoryStream();
        context.Response.Body = responseBody;

        await next(context);

        context.Response.Body.Position = 0;
        var responseText = await ReadStreamAsync(context.Response.Body);
        context.Response.Body.Position = 0;

        await responseBody.CopyToAsync(originalResponseBody);

        _logger.LogInformation("Response {StatusCode}: {Body}",
            context.Response.StatusCode,
            responseText);
    }

    private static async Task ReadStreamAsync(Stream stream)
    {
        using var reader = new StreamReader(stream, leaveOpen: true);
        return await reader.ReadToEndAsync();
    }
}
// Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddTransient();

var app = builder.Build();

// Solo en desarrollo para no ralentizar producción ni filtrar datos sensibles
if (app.Environment.IsDevelopment())
    app.UseRequestResponseLogging();

app.MapPost("/echo", (EchoRequest request) => request with { Text = $"Eco: {request.Text}" });

app.Run();

public record EchoRequest(string Text);

Advertencia de seguridad

No loguees contraseñas, tokens, datos médicos o financieros. Si usas este middleware, enmascara o excluye campos sensibles. En producción, considera activarlo solo para un porcentaje de tráfico o con un nivel de log muy alto.

Bifurcación con UseWhen

app.UseWhen(
    context => context.Request.Path.StartsWithSegments("/api"),
    api => api.UseMiddleware());

// Middleware fuera de /api no se ejecuta

5. Buenas prácticas

  • Prefiere clases sobre middleware inline. Son más fáciles de testear, reutilizar y mantener.
  • Registra IMiddleware como transient. Así se puede inyectar servicios scoped (como DbContext) si el middleware se crea dentro de un scope.
  • Devuelve el control siempre. Si un middleware corta la petición, asegúrate de devolver un status code claro (400, 401, 404, etc.).
  • Usa HttpRequest.EnableBuffering() para leer el body de la petición y volver a posicionarlo para los siguientes middlewares y endpoints.
  • Documenta el middleware en el pipeline. Escribe comentarios que expliquen qué hace y qué dependencias requiere.

6. Errores habituales

6.1. Middleware inline no testeable

// ❌ MAL: lógica grande dentro de Program.cs
app.Use(async (context, next) =>
{
    // ... 40 líneas de lógica ...
    await next();
});

La solución es extraerlo a una clase IMiddleware.

6.2. No reponer el body de la petición

// ❌ MAL: leer el body sin EnableBuffering
var body = await new StreamReader(context.Request.Body).ReadToEndAsync();
// El endpoint posterior no puede leer el body
// ✅ CORRECTO
context.Request.EnableBuffering();
var body = await new StreamReader(context.Request.Body).ReadToEndAsync();
context.Request.Body.Position = 0;

6.3. Registrar IMiddleware como singleton con dependencias scoped

// ❌ MAL: captura dependencias scoped
builder.Services.AddSingleton();
// ✅ CORRECTO
builder.Services.AddTransient();

7. Ejercicio guiado

Crea un middleware que añada una cabecera X-Api-Gateway solo a las peticiones que pasan por /api. Usa UseWhen.

// Middleware/ApiGatewayMiddleware.cs
public sealed class ApiGatewayMiddleware : IMiddleware
{
    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        context.Response.Headers.Append("X-Api-Gateway", "Curso-DotNet");
        await next(context);
    }
}
// Program.cs
builder.Services.AddTransient();

app.UseWhen(
    context => context.Request.Path.StartsWithSegments("/api"),
    branch => branch.UseMiddleware());

app.MapGet("/api/values", () => new[] { "a", "b" });
app.MapGet("/", () => "Página pública");

app.Run();

Prueba con curl -i http://localhost:5000/api/values (verás la cabecera) y curl -i http://localhost:5000/ (no la verás).

8. Reto

Implementa un middleware que rechace peticiones con un User-Agent vacío o que contenga la palabra bot. Debe devolver 400 Bad Request y un ProblemDetails. No lo apliques a las rutas de /health.

Intenta resolverlo antes de ver la solución. Pista: context.Request.Headers.TryGetValue("User-Agent", out var userAgent).

9. Resumen

  • Los middlewares personalizados encapsulan comportamiento transversal.
  • IMiddleware es la forma más limpia: permite DI y testing.
  • Los métodos de extensión UseXxx mejoran la legibilidad de Program.cs.
  • Para leer el body de una petición, usa EnableBuffering y reposiciónalo a 0.
  • app.UseWhen aplica middleware a un subconjunto de rutas y devuelve el control.
  • Evita loguear datos sensibles y no dejes lógica de middleware inline en producción.

10. Preguntas frecuentes

¿Puedo inyectar un DbContext en un middleware?

Sí, pero con IMiddleware registrado como transient. Si lo registras como singleton, el DbContext (que es scoped) no se podrá inyectar y obtendrás un error de captura de dependencias. En middleware inline, el middleware se ejecuta en el contexto de la petición, pero sigue siendo más limpio pedir el DbContext dentro del scope de la petición.

¿Cuál es la diferencia entre Invoke y InvokeAsync?

La convención clásica acepta un método llamado Invoke o InvokeAsync con firma public async Task InvokeAsync(HttpContext context, RequestDelegate next). IMiddleware exige InvokeAsync. Usa siempre InvokeAsync por claridad y consistencia.

¿Cómo testeo un middleware?

Crea un DefaultHttpContext, monta un RequestDelegate que simule el siguiente middleware o el endpoint, y llama a InvokeAsync. Luego inspecciona HttpContext.Response.

¿Puedo anidar middlewares dentro de otros?

El pipeline ya es anidado: cada await next(context) invoca al siguiente middleware. No necesitas crear clases anidadas, solo encadenar app.Use o app.UseMiddleware.

¿Es mejor app.UseMiddleware<T> o app.Use?

Para código profesional, app.UseMiddleware<T> con IMiddleware. Para prototipos o una sola línea de traza, app.Use es aceptable. Evita mezclar ambos estilos sin criterio.
