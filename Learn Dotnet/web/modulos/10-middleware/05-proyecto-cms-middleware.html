Proyecto CMS: middleware + rate limiting

Módulo 10 · Proyecto45 min

1 · Introducción

En esta lección aplicamos todo lo aprendido sobre middleware al proyecto CMS. Añadiremos un middleware de correlation ID, un middleware de logging de peticiones, configuraremos rate limiting por IP y por usuario, y añadiremos health checks para la base de datos y un check básico de liveness.

Al final, la API del CMS tendrá una capa transversal profesional: trazabilidad, protección contra abuso y visibilidad del estado del sistema.

Objetivos del proyecto

  • Crear un middleware CorrelationIdMiddleware que respete el ID entrante o genere uno nuevo.
  • Crear un middleware RequestLoggingMiddleware que loguee método, path, status code y tiempo de respuesta.
  • Configurar rate limiting SlidingWindow para rutas /api, excluyendo /health.
  • Añadir CORS para el frontend del CMS.
  • Añadir health checks: /health/live, /health/ready y /health detallado.
  • Verificar que todo compila y que los tests de integración respetan el correlation ID.

2 · Teoría

2.1. Arquitectura del CMS

El CMS sigue Clean Architecture:

  • Cms.Domain: entidades y reglas de negocio.
  • Cms.Application: commands, queries, handlers, validadores y DTOs.
  • Cms.Infrastructure: EF Core, repositorios, servicios externos.
  • Cms.Api: endpoints, middleware, configuración y health checks.

Los middleware y los health checks viven en Cms.Api porque son infraestructura de la aplicación web. El middleware de logging puede depender de ILogger, que es un servicio transversal.

2.2. Pipeline objetivo del CMS

ExceptionHandler / IExceptionHandler
HSTS / HTTPS
CORS
Correlation ID
Request Logging
Rate Limiting
Authentication
Authorization
Endpoints / Controllers

El correlation ID se registra antes del logging para que todas las trazas incluyan el ID. El rate limiting se coloca antes de autenticación para proteger incluso endpoints anónimos, pero excluimos /health para no afectar a los orquestadores.

2.3. Decisiones de diseño

  • Middleware como clases IMiddleware: permiten inyección de dependencias y testing unitario.
  • Rate limiting por IP: protección general contra abuso. Más adelante se añadirá por usuario autenticado.
  • Health checks separados: /health/live para Kubernetes (siempre vive), /health/ready para dependencias (base de datos), /health para detalles internos.

Consejo del proyecto

Registra todos los middlewares con métodos de extensión UseXxx. Así el Program.cs del CMS se lee como un libro de configuración.

3 · Ejemplo mínimo

Antes de integrar todo, veamos el middleware de correlation ID para el CMS.

// Cms.Api/Middleware/CorrelationIdMiddleware.cs
public sealed class CorrelationIdMiddleware : IMiddleware
{
    public const string HeaderKey = "X-Correlation-ID";

    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        var correlationId = GetOrCreateCorrelationId(context);
        context.Response.Headers.Append(HeaderKey, correlationId);

        using (LogContext.PushProperty("CorrelationId", correlationId))
        {
            await next(context);
        }
    }

    private static string GetOrCreateCorrelationId(HttpContext context)
    {
        if (context.Request.Headers.TryGetValue(HeaderKey, out var value) &&
            !string.IsNullOrWhiteSpace(value))
        {
            return value.ToString();
        }

        return Guid.NewGuid().ToString("N");
    }
}

// Cms.Api/Middleware/MiddlewareExtensions.cs
public static class MiddlewareExtensions
{
    public static IApplicationBuilder UseCorrelationId(this IApplicationBuilder app)
        => app.UseMiddleware();
}

En Program.cs usaremos app.UseCorrelationId(), manteniendo el archivo principal limpio.

4 · Ejemplo real

4.1. Middleware de logging de peticiones

// Cms.Api/Middleware/RequestLoggingMiddleware.cs
using System.Diagnostics;

public sealed class RequestLoggingMiddleware : IMiddleware
{
    private readonly ILogger _logger;

    public RequestLoggingMiddleware(ILogger logger)
    {
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        var stopwatch = Stopwatch.StartNew();
        _logger.LogInformation(
            "Request {Method} {Path} started",
            context.Request.Method,
            context.Request.Path);

        await next(context);

        stopwatch.Stop();
        _logger.LogInformation(
            "Request {Method} {Path} completed with {StatusCode} in {ElapsedMs}ms",
            context.Request.Method,
            context.Request.Path,
            context.Response.StatusCode,
            stopwatch.ElapsedMilliseconds);
    }
}

// Cms.Api/Middleware/MiddlewareExtensions.cs
public static IApplicationBuilder UseRequestLogging(this IApplicationBuilder app)
    => app.UseMiddleware();

4.2. Configuración de CORS, Rate Limiting y Health Checks

// Cms.Api/Program.cs
var builder = WebApplication.CreateBuilder(args);

// Capa de aplicación e infraestructura
builder.Services.AddApplication();
builder.Services.AddInfrastructure(builder.Configuration);
builder.Services.AddControllers();

builder.Services.AddTransient();
builder.Services.AddTransient();

builder.Services.AddCors(options =>
{
    options.AddPolicy("CmsFrontend", policy =>
    {
        var allowedOrigins = builder.Configuration.GetSection("Cors:AllowedOrigins").Get() ?? [];
        policy.WithOrigins(allowedOrigins)
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials();
    });
});

builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = 429;
    options.OnRejected = (context, token) =>
    {
        context.Response.StatusCode = 429;
        return context.Response.WriteAsync("Too many requests. Please retry later.", token);
    };

    options.AddPolicy("cms-api", context =>
    {
        var remoteIp = context.Connection.RemoteIpAddress?.ToString() ?? "unknown";
        return RateLimitPartition.GetSlidingWindowLimiter(remoteIp, _ => new SlidingWindowRateLimiterOptions
        {
            PermitLimit = 60,
            Window = TimeSpan.FromMinutes(1),
            SegmentsPerWindow = 6,
            QueueLimit = 0
        });
    });
});

builder.Services.AddHealthChecks()
    .AddDbContextCheck("database", tags: new[] { "ready" })
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: new[] { "live" });

var app = builder.Build();

if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler();
    app.UseHsts();
}

app.UseHttpsRedirection();
app.UseCors("CmsFrontend");

app.UseCorrelationId();
app.UseRequestLogging();

app.UseRateLimiter();

app.UseAuthentication();
app.UseAuthorization();

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

app.MapHealthChecks("/health", new HealthCheckOptions
{
    Predicate = _ => true,
    ResponseWriter = async (context, report) =>
    {
        var response = new
        {
            Status = report.Status.ToString(),
            Duration = report.TotalDuration,
            Checks = report.Entries.Select(e => new
            {
                Name = e.Key,
                Status = e.Value.Status.ToString(),
                e.Value.Duration
            })
        };

        await context.Response.WriteAsJsonAsync(response);
    }
}).DisableRateLimiting();

app.MapControllers();

app.Run();

¿Qué ocurre aquí?

El pipeline del CMS aplica CORS, correlation ID, logging y rate limiting antes de autenticación. Los endpoints de salud no están limitados. El health check de base de datos forma parte del readiness; el self check forma parte del liveness.

4.4. Controlador con rate limiting

// Cms.Api/Controllers/PostsController.cs (extracto)
using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.RateLimiting;

[ApiController]
[Route("api/v1/[controller]")]
[EnableRateLimiting("cms-api")]
public class PostsController : ControllerBase
{
    [HttpGet]
    public async Task GetAll([FromServices] IMediator mediator)
    {
        var posts = await mediator.Send(new GetAllPostsQuery());
        return Ok(posts);
    }
}

Logging en producción

En producción, el middleware de logging debe ser ligero: no leas el body completo de cada petición. Para debugging de body, usa un middleware separado y activo solo en desarrollo o para un porcentaje de tráfico.

5 · Buenas prácticas

  • Orden de middleware documentado. Añade comentarios en Program.cs que expliquen por qué cada middleware va en ese lugar.
  • Rate limiting realista. 60 peticiones/minuto por IP es razonable para un CMS; ajusta según el uso real.
  • Excepciones de salud. Nunca apliques rate limiting a endpoints que usan los balanceadores o Kubernetes para decidir si el pod está vivo.
  • Correlation ID en tests. En tests de integración, envía un X-Correlation-ID de prueba y verifica que la respuesta lo repite.
  • Configuration de CORS externa. No hardcodees orígenes; usa appsettings.json o variables de entorno.

6 · Errores habituales

6.1. Middleware de logging sin respetar el correlation ID

// ❌ MAL: logging antes de UseCorrelationId
app.UseRequestLogging();
app.UseCorrelationId();
// ✅ CORRECTO
app.UseCorrelationId();
app.UseRequestLogging();

6.2. Health check limitado por rate limiting

// ❌ MAL: el balanceador puede recibir 429 y marcar el pod como no sano
app.MapHealthChecks("/health");
app.UseRateLimiter();
// ✅ CORRECTO
app.UseRateLimiter();
app.MapHealthChecks("/health").DisableRateLimiting();

6.3. CORS después de autenticación

// ❌ MAL
app.UseAuthentication();
app.UseCors("CmsFrontend");

// ✅ CORRECTO
app.UseCors("CmsFrontend");
app.UseAuthentication();

6.4. Middleware sin registrar en DI

// ❌ MAL: UseMiddleware requiere que IMiddleware esté registrado
app.UseMiddleware();
// ✅ CORRECTO
builder.Services.AddTransient();
app.UseCorrelationId();

7 · Ejercicio guiado

Añade un middleware que añada una cabecera de versión de la API a todas las respuestas de /api/v1/*.

// Cms.Api/Middleware/ApiVersionHeaderMiddleware.cs
public sealed class ApiVersionHeaderMiddleware : IMiddleware
{
    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        if (context.Request.Path.StartsWithSegments("/api/v1"))
        {
            context.Response.Headers.Append("X-Api-Version", "v1");
        }

        await next(context);
    }
}

// Cms.Api/Middleware/MiddlewareExtensions.cs
public static IApplicationBuilder UseApiVersionHeader(this IApplicationBuilder app)
    => app.UseMiddleware();

// Program.cs
builder.Services.AddTransient();

app.UseCorrelationId();
app.UseApiVersionHeader();
app.UseRequestLogging();

Prueba con curl -i http://localhost:5000/api/v1/posts y verifica que aparece X-Api-Version: v1 en la respuesta.

8 · Reto

Implementa un middleware que rechace peticiones POST a /api/v1/posts cuya cabecera Content-Type no sea application/json. Debe devolver 415 Unsupported Media Type con un ProblemDetails. El middleware debe ser testable y registrarse con UseContentTypeValidation. No lo apliques a /api/v1/media/upload.

9 · Resumen

  • El CMS ahora tiene un pipeline profesional: CORS, correlation ID, logging, rate limiting, autenticación y autorización.
  • Los middlewares son clases IMiddleware registrados como transient y expuestos mediante métodos de extensión UseXxx.
  • El rate limiting protege las rutas /api con SlidingWindow por IP; los endpoints de salud están excluidos.
  • Los health checks separan liveness y readiness, y el endpoint /health devuelve detalles útiles para operadores.
  • El orden del pipeline es crítico: correlation ID antes de logging, CORS antes de autenticación, salud fuera del rate limiting.

10 · Preguntas frecuentes

¿Dónde deben vivir los middleware en Clean Architecture?

En el proyecto Cms.Api, junto con la configuración de la aplicación web. Son parte de la infraestructura de presentación, no de la lógica de negocio.

¿Por qué no usamos middleware inline en el CMS?

Porque queremos testearlos unitariamente, reutilizarlos y mantener Program.cs legible. Las clases IMiddleware son la forma profesional.

¿Cómo verificamos que el correlation ID funciona en tests?

En un test de integración con WebApplicationFactory, envía la cabecera X-Correlation-ID, haz una petición y comprueba que la respuesta incluye el mismo valor. También puedes verificar que el logger captura el ID.

¿El rate limiting afecta a los tests de integración?

Sí, si no lo desactivas. En tests, registra una política permisiva o desactiva el middleware para evitar tests flaky por límites.

¿Deberíamos añadir un health check de Redis ya?

Sí, en el módulo de caching. Por ahora, el readiness verifica la base de datos. Cuando añadamos Redis, registraremos un .AddRedis o un check personalizado.
