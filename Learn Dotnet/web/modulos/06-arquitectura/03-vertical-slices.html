Vertical Slices vs Clean Architecture

Módulo 6 · Arquitectura y organización30 min

1 · Introducción

Hasta ahora hemos organizado el código en capas horizontales: Domain, Application, Infrastructure, Presentation. Eso funciona muy bien, pero tiene un inconveniente: una funcionalidad cualquiera está dispersa entre cuatro carpetas distintas.

Vertical Slices es una alternativa donde organizamos el código por feature o funcionalidad. Todo lo necesario para crear un post vive en una sola carpeta: request, handler, validador, mapper, respuesta y tests.

¿Cuándo usar cada una?

Clean Architecture es ideal para sistemas grandes con muchas reglas de negocio compartidas. Vertical Slices brilla en APIs medianas donde cada feature es independiente y se quiere alta velocidad de desarrollo.

Errores típicos

  • Mezclar carpetas por capa y por feature sin criterio.
  • Crear slices que comparten todo entre sí, perdiendo el beneficio del bajo acoplamiento.
  • Ignorar el dominio compartido y duplicar conceptos en cada slice.

2 · Teoría

Organización horizontal vs vertical

En la organización horizontal (Clean Architecture), agrupamos cosas del mismo tipo:

src/
├── Controllers/
├── Services/
├── Repositories/
├── Dtos/
└── Entities/

En Vertical Slices agrupamos todo lo relacionado con una funcionalidad:

src/
├── Features/
│   ├── Posts/
│   │   ├── CreatePost/
│   │   │   ├── CreatePostCommand.cs
│   │   │   ├── CreatePostHandler.cs
│   │   │   ├── CreatePostValidator.cs
│   │   │   └── CreatePostEndpoint.cs
│   │   ├── GetPostById/
│   │   └── ListPosts/
│   └── Categories/
│       └── ...

Alta cohesión

Cuando modificas "crear post", casi todo el código que tocas está en Features/Posts/CreatePost. No saltas entre Controllers, Services y Repositories.

¿Es incompatible con Clean Architecture?

No. Puedes combinarlas: mantener los proyectos/límites de Clean Architecture, pero dentro de Application o Presentation organizar por slices. En .NET moderno es muy común usar Vertical Slices + CQRS + MediatR.

Ventajas e inconvenientes

CaracterísticaClean ArchitectureVertical Slices
Escalabilidad cognitivaBuena en equipos grandesBuena en equipos pequeños/medios
CohesiónBaja dentro de una capaAlta dentro de una feature
AcoplamientoDesacoplamiento por capaDesacoplamiento por feature
Curva de aprendizajeMás formalMás intuitiva
ReutilizaciónFácil de compartir abstraccionesRiesgo de duplicar lógica compartida

3 · Ejemplo mínimo

Crearemos un proyecto pequeño con una slice para crear tareas usando MediatR.

dotnet new web -n VerticalSlicesMini -o VerticalSlicesMini
cd VerticalSlicesMini
dotnet add package MediatR --version 12.2.0

// Program.cs
using MediatR;
using VerticalSlicesMini.Features.Todos.Create;
using VerticalSlicesMini.Features.Todos.List;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddMediatR(cfg => cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));

var app = builder.Build();

app.MapPost("/todos", async (CreateTodoCommand command, ISender sender) =>
{
    var id = await sender.Send(command);
    return Results.Created($"/todos/{id}", id);
});

app.MapGet("/todos", async (ISender sender) =>
    Results.Ok(await sender.Send(new ListTodosQuery())));

app.Run();

// Features/Todos/Create/CreateTodoCommand.cs
namespace VerticalSlicesMini.Features.Todos.Create;

public sealed record CreateTodoCommand(string Title) : IRequest<Guid>;

// Features/Todos/Create/CreateTodoHandler.cs
namespace VerticalSlicesMini.Features.Todos.Create;

public sealed class CreateTodoHandler : IRequestHandler<CreateTodoCommand, Guid>
{
    private static readonly List<Todo> Store = new();

    public Task<Guid> Handle(CreateTodoCommand request, CancellationToken cancellationToken)
    {
        var todo = new Todo(Guid.NewGuid(), request.Title, false);
        Store.Add(todo);
        return Task.FromResult(todo.Id);
    }
}

public sealed record Todo(Guid Id, string Title, bool IsCompleted);

// Features/Todos/List/ListTodosQuery.cs
namespace VerticalSlicesMini.Features.Todos.List;

public sealed record ListTodosQuery : IRequest<List<TodoDto>>;

public sealed record TodoDto(Guid Id, string Title, bool IsCompleted);

// Features/Todos/List/ListTodosHandler.cs
using VerticalSlicesMini.Features.Todos.Create;

namespace VerticalSlicesMini.Features.Todos.List;

public sealed class ListTodosHandler : IRequestHandler<ListTodosQuery, List<TodoDto>>
{
    public Task<List<TodoDto>> Handle(ListTodosQuery request, CancellationToken cancellationToken)
    {
        var todos = CreateTodoHandler.Store
            .Select(t => new TodoDto(t.Id, t.Title, t.IsCompleted))
            .ToList();
        return Task.FromResult(todos);
    }
}

Store estático solo para el ejemplo

En producción usarías un DbContext o repositorio inyectado. Aquí lo hacemos estático para enfocarnos en la estructura por slices.

4 · Ejemplo real

En un CMS real con Clean Architecture + Vertical Slices, los handlers viven en Application y los endpoints en Api. Cada feature es autocontenida.

src/Cms.Application/
└── Features/
    └── Posts/
        ├── CreatePost/
        │   ├── CreatePostCommand.cs
        │   ├── CreatePostHandler.cs
        │   ├── CreatePostValidator.cs
        │   └── CreatePostResponse.cs
        ├── GetPostById/
        │   ├── GetPostByIdQuery.cs
        │   ├── GetPostByIdHandler.cs
        │   └── PostDto.cs
        └── PublishPost/
            ├── PublishPostCommand.cs
            └── PublishPostHandler.cs

// Cms.Application/Features/Posts/CreatePost/CreatePostCommand.cs
namespace Cms.Application.Features.Posts.CreatePost;

public sealed record CreatePostCommand(
    string Title,
    string Content,
    Guid CategoryId
) : IRequest<Guid>;

// Cms.Application/Features/Posts/CreatePost/CreatePostHandler.cs
using Cms.Domain.Entities;
using Cms.Domain.Repositories;

namespace Cms.Application.Features.Posts.CreatePost;

public sealed class CreatePostHandler(IPostRepository posts, IUnitOfWork unitOfWork)
    : IRequestHandler<CreatePostCommand, Guid>
{
    public async Task<Guid> Handle(CreatePostCommand request, CancellationToken cancellationToken)
    {
        var post = Post.Create(request.Title, request.Content);
        await posts.AddAsync(post);
        await unitOfWork.SaveChangesAsync(cancellationToken);
        return post.Id;
    }
}

// Cms.Api/Features/Posts/PostsEndpoints.cs
using Cms.Application.Features.Posts.CreatePost;
using Cms.Application.Features.Posts.GetPostById;
using MediatR;

namespace Cms.Api.Features.Posts;

public static class PostsEndpoints
{
    public static IEndpointRouteBuilder MapPostEndpoints(this IEndpointRouteBuilder app)
    {
        app.MapPost("/api/posts", async (CreatePostCommand command, ISender sender) =>
        {
            var id = await sender.Send(command);
            return Results.Created($"/api/posts/{id}", id);
        });

        app.MapGet("/api/posts/{id:guid}", async (Guid id, ISender sender) =>
        {
            var post = await sender.Send(new GetPostByIdQuery(id));
            return post is null ? Results.NotFound() : Results.Ok(post);
        });

        return app;
    }
}

// Cms.Api/Program.cs
using Cms.Api.Features.Posts;
using Cms.Application;
using Cms.Infrastructure;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddApplication();
builder.Services.AddInfrastructure(builder.Configuration);

var app = builder.Build();
app.MapPostEndpoints();
app.Run();

5 · Buenas prácticas

  • Una slice por feature: No mezcles comandos, queries y endpoints de distintas funcionalidades.
  • Compartir lo común: Extrae a Shared o Common solo lo verdaderamente reutilizable (paginación, validadores genéricos, etc.).
  • No dependas de otras slices: Si una slice necesita datos de otra, usa la interfaz de repositorio o un query público, no accedas a su store interno.
  • Mantén los límites de arquitectura: Incluso con slices, respeta que Domain no depende de Application ni de Infrastructure.
  • Usa MediatR para desacoplar: Los endpoints envían mensajes; los handlers los procesan. La capa de presentación no conoce la implementación.

6 · Errores habituales

❌ Slices que se conocen entre sí

// Mal: desde CreatePost accedemos al handler de GetPostById
public async Task Handle(CreatePostCommand request, ...)
{
    ...
    var other = await new GetPostByIdHandler(_posts).Handle(...);
}

Esto acopla slices. Si necesitas verificar existencia, usa el repositorio o un servicio de dominio.

❌ Todo en un solo archivo

Por facilidad, algunos ponen command, handler, validator y DTOs en un solo archivo. Para proyectos pequeños está bien, pero en producción separa en archivos con nombres claros.

✅ Correcto

Divide por responsabilidad dentro de la carpeta de la feature. Así es más fácil encontrar y testear cada pieza.

7 · Ejercicio guiado

Convierte el mini ejemplo de tareas en una estructura con dos features: MarkTodoComplete y DeleteTodo.

  1. Crea Features/Todos/MarkComplete/MarkTodoCompleteCommand.cs y su handler.
  2. Crea Features/Todos/Delete/DeleteTodoCommand.cs y su handler.
  3. Registra los endpoints PUT /todos/{id}/complete y DELETE /todos/{id}.
  4. Asegúrate de que cada slice solo toca el store a través de una interfaz común ITodoRepository.

Pista de estructura

Features/Todos/
├── Create/
├── List/
├── MarkComplete/
└── Delete/

8 · Reto

Diseña una estructura híbrida para el CMS: mantén los proyectos de Clean Architecture, pero dentro de Cms.Application organiza todo por Vertical Slices. Define al menos tres features (CreatePost, PublishPost, GetPostById) y un proyecto Cms.Shared para paginación y validadores genéricos.

No resuelvas el reto todavía. Usa la lección 6 del módulo (proyecto CMS) como guía cuando llegues a ella.

9 · Resumen

  • Clean Architecture organiza por capas horizontales; Vertical Slices organiza por features verticales.
  • Las slices aumentan la cohesión de una funcionalidad y reducen el salto entre carpetas.
  • No son excluyentes: se pueden combinar dentro de los límites de Clean Architecture.
  • MediatR facilita la separación entre endpoints (presentación) y handlers (aplicación).
  • Cuidado con el acoplamiento entre slices: comparte abstracciones, no implementaciones.

10 · Preguntas frecuentes

¿Debo elegir una sola arquitectura?

No necesariamente. Muchos proyectos .NET usan Clean Architecture para las capas Domain/Application/Infrastructure y Vertical Slices dentro de Application. Es una combinación muy productiva.

¿Dónde van los tests con Vertical Slices?

Idealmente junto a cada slice (Features/Posts/CreatePost/CreatePostTests.cs) o en un proyecto de tests con la misma estructura de carpetas.

¿Vertical Slices escala en equipos grandes?

Sí, pero requiere disciplina. Es útil definir convenciones claras sobre qué puede compartirse y qué no. De lo contrario, cada slice se convierte en un mini sistema con duplicación.

¿Y Minimal APIs?

Encajan perfectamente. Cada slice expone sus endpoints desde un método de extensión (MapXxxEndpoints) o directamente en Program.cs.
