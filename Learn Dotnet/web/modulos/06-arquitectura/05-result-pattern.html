Result<T> pattern y manejo de errores

Módulo 6 · Arquitectura y organización30 min

1 · Introducción

En C# tradicional solemos usar excepciones para cualquier error. Sin embargo, las excepciones son costosas y semánticamente representan situaciones excepcionales, no resultados esperados como "email duplicado" o "categoría no encontrada".

El Result<T> pattern devuelve explícitamente éxito o error, obligando al llamador a manejar ambos casos. Es especialmente útil en la capa de aplicación y en APIs.

¿Qué resolveremos?

Evitar el uso de excepciones para flujos de control normales. Queremos que el compilador nos obligue a considerar el caso de error.

Errores típicos

  • Lanzar ArgumentException desde Application para errores de dominio esperados.
  • Devolver null cuando falla una operación, perdiendo información del error.
  • Mezclar códigos HTTP en la capa de aplicación.
  • No distinguir entre errores de validación, no encontrado y conflictos.

2 · Teoría

Result vs excepciones

AspectoExcepcionesResult<T>
Caso de usoErrores excepcionalesErrores esperados del dominio
RendimientoCostoso (stack trace)Ligero (objeto simple)
Seguridad de tiposNo obliga a manejarObliga a verificar IsSuccess
LegibilidadFlujo interrumpidoFlujo explícito
Información del errorMensaje + stackCódigo, mensaje, detalles tipados

Railway-oriented programming

El Result pattern se asocia al railway-oriented programming: las operaciones se encadenan como vías de tren. Si una falla, el tren sigue por la vía de error sin necesidad de try/catch intermedio.

Éxito ──▶ Paso 1 ──▶ Paso 2 ──▶ Resultado final
                          │
                          ▼
                        Error (se propaga sin romper el flujo)

Tipos de error

Un buen diseño de errores incluye al menos:

  • Código: identificador único del error (p. ej. Post.NotFound).
  • Mensaje: descripción legible.
  • Tipo: validación, no encontrado, conflicto, autorización...

¿Cuándo usar excepciones?

Usa excepciones para bugs, fallos de infraestructura inesperados o violaciones de invariantes que nunca deberían ocurrir. Usa Result para errores de negocio previsibles.

3 · Ejemplo mínimo

Implementaremos un Result<T> desde cero, sin dependencias externas.

dotnet new console -n ResultPatternMini -o ResultPatternMini
cd ResultPatternMini

// Result.cs
namespace ResultPatternMini;

public sealed class Result<T>
{
    public bool IsSuccess { get; }
    public bool IsFailure => !IsSuccess;
    public T Value { get; }
    public Error Error { get; }

    private Result(T value)
    {
        IsSuccess = true;
        Value = value;
        Error = Error.None;
    }

    private Result(Error error)
    {
        IsSuccess = false;
        Error = error;
        Value = default!;
    }

    public static Result<T> Success(T value) => new(value);
    public static Result<T> Failure(Error error) => new(error);

    // Permite encadenar operaciones (railway)
    public Result<TOut> Map<TOut>(Func<T, TOut> mapper) =>
        IsSuccess ? Result<TOut>.Success(mapper(Value)) : Result<TOut>.Failure(Error);
}

public sealed record Error(string Code, string Message, ErrorType Type)
{
    public static readonly Error None = new(string.Empty, string.Empty, ErrorType.Failure);
    public static Error NotFound(string code, string message) => new(code, message, ErrorType.NotFound);
    public static Error Validation(string code, string message) => new(code, message, ErrorType.Validation);
    public static Error Conflict(string code, string message) => new(code, message, ErrorType.Conflict);
}

public enum ErrorType
{
    Failure,
    Validation,
    NotFound,
    Conflict,
    Unauthorized
}

// UserService.cs
namespace ResultPatternMini;

public sealed class UserService
{
    private readonly List<string> _emails = new() { "juan@example.com" };

    public Result<Guid> Register(string email)
    {
        if (string.IsNullOrWhiteSpace(email))
            return Result<Guid>.Failure(Error.Validation("User.EmailRequired", "El email es obligatorio."));

        if (_emails.Contains(email))
            return Result<Guid>.Failure(Error.Conflict("User.EmailExists", "El email ya está registrado."));

        _emails.Add(email);
        return Result<Guid>.Success(Guid.NewGuid());
    }
}

// Program.cs
using ResultPatternMini;

var service = new UserService();
var result = service.Register("juan@example.com");

if (result.IsFailure)
{
    Console.WriteLine($"Error [{result.Error.Type}]: {result.Error.Code} - {result.Error.Message}");
    return;
}

Console.WriteLine($"Usuario creado: {result.Value}");

4 · Ejemplo real

En el CMS usaremos Result<T> en los handlers de MediatR. La API convierte el error en el status code adecuado.

// Application/Abstractions/Result.cs
namespace Cms.Application.Abstractions;

public sealed class Result<T>
{
    public bool IsSuccess { get; }
    public bool IsFailure => !IsSuccess;
    public T Value { get; }
    public Error Error { get; }

    private Result(T value) { IsSuccess = true; Value = value; Error = Error.None; }
    private Result(Error error) { IsSuccess = false; Error = error; Value = default!; }

    public static Result<T> Success(T value) => new(value);
    public static Result<T> Failure(Error error) => new(error);
}

public sealed record Error(string Code, string Message, ErrorType Type)
{
    public static readonly Error None = new(string.Empty, string.Empty, ErrorType.Failure);
    public static Error NotFound(string code, string message) => new(code, message, ErrorType.NotFound);
    public static Error Validation(string code, string message) => new(code, message, ErrorType.Validation);
    public static Error Conflict(string code, string message) => new(code, message, ErrorType.Conflict);
}

public enum ErrorType { Failure, Validation, NotFound, Conflict, Unauthorized }

// Application/Features/Posts/GetPostById/GetPostByIdQuery.cs
using Cms.Application.Abstractions;
using MediatR;

namespace Cms.Application.Features.Posts.GetPostById;

public sealed record GetPostByIdQuery(Guid Id) : IRequest<Result<PostDto>>;

public sealed record PostDto(Guid Id, string Title, string Content, bool IsPublished);

// Application/Features/Posts/GetPostById/GetPostByIdHandler.cs
using Cms.Application.Abstractions;
using Cms.Domain.Repositories;
using MediatR;

namespace Cms.Application.Features.Posts.GetPostById;

public sealed class GetPostByIdHandler(IPostRepository posts)
    : IRequestHandler<GetPostByIdQuery, Result<PostDto>>
{
    public async Task<Result<PostDto>> Handle(GetPostByIdQuery request, CancellationToken cancellationToken)
    {
        var post = await posts.GetByIdAsync(request.Id);
        if (post is null)
            return Result<PostDto>.Failure(Error.NotFound("Post.NotFound", $"Post {request.Id} no encontrado."));

        return Result<PostDto>.Success(new PostDto(post.Id, post.Title, post.Content, post.IsPublished));
    }
}

// Api/Features/Posts/PostsEndpoints.cs
using Cms.Application.Abstractions;
using Cms.Application.Features.Posts.GetPostById;
using MediatR;

namespace Cms.Api.Features.Posts;

public static class PostsEndpoints
{
    public static IEndpointRouteBuilder MapPostEndpoints(this IEndpointRouteBuilder app)
    {
        app.MapGet("/api/posts/{id:guid}", async (Guid id, ISender sender) =>
        {
            var result = await sender.Send(new GetPostByIdQuery(id));

            return result.IsSuccess
                ? Results.Ok(result.Value)
                : result.Error.Type switch
                {
                    ErrorType.NotFound => Results.NotFound(),
                    ErrorType.Validation => Results.BadRequest(result.Error.Message),
                    _ => Results.Problem(result.Error.Message)
                };
        });

        return app;
    }
}

Evita exponer errores técnicos

En producción no devuelvas el stack trace ni mensajes internos. Usa Problem Details con códigos de error públicos.

5 · Buenas prácticas

  • Usa Result para errores esperados: validaciones, duplicados, no encontrados, conflictos de negocio.
  • Usa excepciones para lo inesperado: fallos de red, null reference, bugs.
  • Códigos de error únicos: Post.NotFound, Category.DuplicatedName.
  • No mezcles HTTP en Application: La API decide el status code; Application solo devuelve el tipo de error.
  • Testea el caso de error: Asegúrate de que los handlers devuelven el Error correcto.

6 · Errores habituales

❌ Lanzar excepción para un error esperado

public async Task<PostDto> Handle(GetPostByIdQuery request, ...)
{
    var post = await _posts.GetByIdAsync(request.Id);
    if (post is null)
        throw new NotFoundException($"Post {request.Id} no encontrado"); // Mal
    ...
}

✅ Correcto

if (post is null)
    return Result<PostDto>.Failure(Error.NotFound("Post.NotFound", $"Post {request.Id} no encontrado."));

❌ Llamar .Value sin verificar IsSuccess

var result = await sender.Send(query);
return Results.Ok(result.Value); // Puede lanzar si falló

✅ Correcto

if (result.IsFailure)
    return MapError(result.Error);
return Results.Ok(result.Value);

8 · Reto

Integra el Result pattern con MediatR. Crea un behavior ResultMappingBehavior<TRequest, TResponse> que, si el handler devuelve un Result<T> con error, convierta automáticamente la respuesta HTTP a Problem Details. La API no debería necesitar un switch manual.

No resuelvas el reto todavía. Piensa en cómo un endpoint podría devolver Results<Ok<T>, ProblemHttpResult> de forma genérica.

9 · Resumen

  • Result<T> modela éxito o error de forma explícita y segura en tipos.
  • Usa Result para errores de negocio esperados; excepciones para situaciones excepcionales.
  • Un buen error incluye código, mensaje y tipo.
  • La capa Application devuelve errores; la API los convierte en status codes.
  • El railway-oriented programming permite encadenar operaciones de forma limpia.

10 · Preguntas frecuentes

¿No es esto lo mismo que OneOf o FluentResults?

Son librerías que resuelven el mismo problema con más funcionalidades. OneOf usa discriminated unions; FluentResults añade logging y metadatos. Nuestra implementación desde cero sirve para entender el concepto.

¿Debo implementar Result desde cero en producción?

Puedes, pero librerías como Ardalis.Result, FluentResults o ErrorOr ahorran tiempo y añaden funcionalidades. Evalúa si tu equipo prefiere una librería madura.

¿Cómo convierto errores en Problem Details?

Mapea ErrorType a status code (400 validación, 404 not found, 409 conflict) y genera un ProblemDetails con el código y mensaje.

¿Puedo devolver Result desde Domain?

Sí, aunque en Domain suele usarse excepciones para invariantes rotas o un tipo de resultado más ligero. Depende de si quieres que el dominio sea totalmente libre de excepciones.
