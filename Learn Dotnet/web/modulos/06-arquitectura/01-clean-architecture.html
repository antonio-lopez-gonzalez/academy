Clean Architecture

Módulo 6 · Arquitectura y organización40 min

1 · Introducción

En este módulo dejamos de lado los detalles del lenguaje y empezamos a diseñar aplicaciones que puedan crecer sin dolor durante años. Clean Architecture es una de las formas más populares de organizar un proyecto .NET profesional.

Aprenderemos qué es, por qué Robert C. Martin la propuso, qué problema resuelve y cómo aplicarla en .NET 8 con una separación física real en proyectos .csproj.

¿Qué resolveremos?

Evitar que la capa de presentación (ASP.NET Core) dependa directamente de Entity Framework, de detalles de base de datos o de librerías externas. Queremos que el dominio de negocio sea independiente y testeable.

Errores típicos

  • Poner DbContext y controladores en el mismo proyecto.
  • Depender de NuGet de infraestructura (SQL Server, Redis) desde la capa de dominio.
  • Mezclar reglas de negocio con código de ASP.NET Core.

2 · Teoría

Clean Architecture organiza el software en capas concéntricas. La regla más importante es la Regla de Dependencia: las dependencias apuntan siempre hacia el centro.

          ┌─────────────────────────────┐
          │     Presentation (API)      │  ← ASP.NET Core, Minimal APIs, Controllers, Swagger
          │  usa abstracciones de App     │
          ├─────────────────────────────┤
          │    Infrastructure             │  ← EF Core, PostgreSQL, Redis, JWT, HttpClient, Email
          │  implementa abstracciones     │  ← referencia a Application
          │  definidas en Application     │
          ├─────────────────────────────┤
          │    Application                │  ← casos de uso, comandos, queries, DTOs, interfaces
          │  orquesta el dominio          │  ← referencia a Domain
          │  define contratos de infra    │
          ├─────────────────────────────┤
          │       Domain                  │  ← entidades, value objects, reglas de negocio puras
          │  no depende de nadie          │  ← cero referencias externas
          └─────────────────────────────┘

Capas en .NET 8

CapaProyectoResponsabilidad
DomainCms.DomainEntidades, value objects, reglas de negocio, excepciones de dominio.
ApplicationCms.ApplicationCasos de uso, comandos, queries, DTOs, interfaces de repositorios y servicios.
InfrastructureCms.InfrastructureImplementaciones concretas: EF Core, PostgreSQL, Redis, JWT, email, almacenamiento.
PresentationCms.ApiASP.NET Core, Minimal APIs, controllers, middleware, Swagger, configuración.

Comparación con Onion y Hexagonal

Tres nombres, misma idea central:

  • Clean Architecture: Robert C. Martin. Énfasis en capas concéntricas y regla de dependencia.
  • Onion Architecture: Jeffrey Palermo. Similar, usa términos de Domain Services, Application Services e Infrastructure.
  • Hexagonal Architecture: Alistair Cockburn. Enfocada en puertos y adaptadores; el dominio está en el centro y todo lo externo es un adaptador.

En la práctica .NET se usan indistintamente. Nosotros usaremos el nombre Clean Architecture porque es el más común en la comunidad de .NET.

¿Por qué separar en proyectos físicos?

Separar por carpetas es fácil de romper con un using incorrecto. Separar en proyectos .csproj hace que el compilador de .NET impida dependencias prohibidas. Es una barrera que protege tu arquitectura.

3 · Ejemplo mínimo

Crearemos cuatro proyectos de consola/classlib para ilustrar la separación de capas. No hace falta ASP.NET Core para entender la regla de dependencia.

# Crear solución y proyectos de capas
dotnet new sln -n CleanArchitectureMini -o CleanArchitectureMini
cd CleanArchitectureMini

dotnet new classlib -n Domain -o src/Domain
dotnet new classlib -n Application -o src/Application
dotnet new classlib -n Infrastructure -o src/Infrastructure
dotnet new console -n Presentation -o src/Presentation

# Agregar referencias según la regla de dependencia
dotnet add src/Application reference src/Domain
dotnet add src/Infrastructure reference src/Application
dotnet add src/Presentation reference src/Application
dotnet add src/Presentation reference src/Infrastructure

// src/Domain/Order.cs
namespace Domain;

public class Order
{
    public Guid Id { get; private set; } = Guid.NewGuid();
    public List<OrderLine> Lines { get; private set; } = new();

    public void AddLine(string product, int quantity, decimal unitPrice)
    {
        if (quantity <= 0)
            throw new ArgumentException("La cantidad debe ser mayor que cero.");

        Lines.Add(new OrderLine(product, quantity, unitPrice));
    }

    public decimal Total => Lines.Sum(l => l.Total);
}

public record OrderLine(string Product, int Quantity, decimal UnitPrice)
{
    public decimal Total => Quantity * UnitPrice;
}

// src/Application/IOrderRepository.cs
using Domain;

namespace Application;

// La capa Application define el contrato. No sabe nada de SQL.
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(Guid id);
    Task AddAsync(Order order);
}

// src/Application/CreateOrderUseCase.cs
using Domain;

namespace Application;

public class CreateOrderUseCase(IOrderRepository repository)
{
    public async Task<Order> ExecuteAsync(string product, int quantity, decimal unitPrice)
    {
        var order = new Order();
        order.AddLine(product, quantity, unitPrice);
        await repository.AddAsync(order);
        return order;
    }
}

// src/Infrastructure/InMemoryOrderRepository.cs
using Application;
using Domain;

namespace Infrastructure;

// Implementación concreta. La infraestructura depende de Application.
public class InMemoryOrderRepository : IOrderRepository
{
    private readonly List<Order> _orders = new();

    public Task<Order?> GetByIdAsync(Guid id) =>
        Task.FromResult(_orders.FirstOrDefault(o => o.Id == id));

    public Task AddAsync(Order order)
    {
        _orders.Add(order);
        return Task.CompletedTask;
    }
}

// src/Presentation/Program.cs
using Application;
using Infrastructure;

// La capa de presentación ensambla el sistema concreto.
var repository = new InMemoryOrderRepository();
var useCase = new CreateOrderUseCase(repository);

var order = await useCase.ExecuteAsync("Libro .NET 8", 2, 29.99m);
Console.WriteLine($"Pedido {order.Id} creado con total {order.Total:C}");

Compilación y ejecución

dotnet build
dotnet run --project src/Presentation

La API es la única que conoce a todas

Cms.Api referencia Cms.Application e Cms.Infrastructure. El contenedor de DI resuelve las interfaces de Application con las implementaciones de Infrastructure. Ningún otro proyecto puede referenciar Infrastructure.

5 · Buenas prácticas

  • Domain sin dependencias externas: No debe tener referencias a Entity Framework, JSON, ni HttpClient.
  • Application define interfaces: Repositorios, servicios de dominio, unit of work. Infrastructure las implementa.
  • Infrastructure no expone detalles: Los DbContext no deben ser usados directamente desde controllers.
  • Presentation es fina: Solo transforma HTTP en comandos y viceversa. No contiene lógica de negocio.
  • Usa proyectos físicos: Facilita el análisis de arquitectura con dotnet y evita violaciones.

¿Puede un proyecto de tests referenciar Domain?

Sí, los tests unitarios deben referenciar únicamente Domain y Application. Los tests de integración pueden referenciar también Infrastructure y API.

6 · Errores habituales

❌ Violación de la regla de dependencia

// src/Domain/Entities/Post.cs
using Microsoft.EntityFrameworkCore; // ¡PROHIBIDO en Domain!

El dominio no debe conocer detalles de persistencia. Si el compilador permite esto, revisa las referencias del proyecto.

❌ Repositorio con lógica de negocio

// Mal: el repositorio valida reglas de negocio
public async Task CreatePostAsync(Post post)
{
    if (post.Title.Length < 5)
        throw new InvalidOperationException("Título demasiado corto");
    await _context.Posts.AddAsync(post);
}

✅ Correcto

public async Task CreatePostAsync(Post post)
{
    await _context.Posts.AddAsync(post);
    await _context.SaveChangesAsync();
}

La validación de reglas pertenece al dominio o al caso de uso (Application), no al repositorio.

7 · Ejercicio guiado

Vamos a crear la estructura de capas para un mini sistema de inventario.

  1. Crea la solución InventoryMini.
  2. Crea cuatro proyectos: Inventory.Domain, Inventory.Application, Inventory.Infrastructure y Inventory.Api.
  3. En Domain crea Product con Id, Name y Stock, y un método IncreaseStock(int amount) que valide amount > 0.
  4. En Application define IProductRepository y AddStockUseCase.
  5. En Infrastructure implementa InMemoryProductRepository.
  6. En Api registra todo en DI y expón un endpoint POST /products/{id}/stock.

Solución parcial

// Domain/Product.cs
namespace Inventory.Domain;

public class Product
{
    public Guid Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public int Stock { get; private set; }

    public void IncreaseStock(int amount)
    {
        if (amount <= 0) throw new ArgumentException("Debe ser positivo", nameof(amount));
        Stock += amount;
    }
}

9 · Resumen

  • Clean Architecture organiza el código en capas concéntricas: Domain, Application, Infrastructure, Presentation.
  • La regla de dependencia apunta siempre hacia el centro; Domain no depende de nadie.
  • Separar en proyectos físicos protege la arquitectura en tiempo de compilación.
  • Application define abstracciones; Infrastructure implementa detalles.
  • Presentation es un adaptador fino que transforma HTTP en comandos.

10 · Preguntas frecuentes

¿Clean Architecture es overkill para un API pequeño?

Para un CRUD sencillo de pocas tablas puede ser excesivo. Sin embargo, para un CMS que crecerá durante el curso, es una inversión que paga dividendos. Puedes empezar con Vertical Slices y luego migrar a Clean Architecture si el proyecto crece.

¿Puedo usar Minimal APIs con Clean Architecture?

Sí. Los Minimal APIs funcionan como adaptadores de presentación. En lugar de controllers, usas MapGet/MapPost que invocan handlers de Application.

¿Dónde van los DTOs?

En Application o Presentation, nunca en Domain. Los DTOs son contratos de la API, no parte del modelo de negocio.

¿Y los servicios de aplicación?

En .NET moderno suelen reemplazarse por handlers de MediatR (ver lección 4 de este módulo). Son más desacoplados y fáciles de probar.
