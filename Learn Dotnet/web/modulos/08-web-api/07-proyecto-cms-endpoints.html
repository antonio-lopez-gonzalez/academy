Proyecto CMS: endpoints CRUD

Módulo 8 · ASP.NET Core Web API55 min

1. Introducción

En esta lección integraremos todo lo aprendido en el módulo 8 para construir la capa de presentación del CMS. Crearemos endpoints CRUD para posts, categorías, tags y usuarios, conectando los controllers con la capa de aplicación que ya construimos en módulos anteriores.

El objetivo es una API REST limpia, versionada, documentada con Swagger y lista para crecer con validación, autenticación y pruebas.

¿Qué lograremos?

Una API funcional con operaciones CRUD, respuestas HTTP semánticas (200, 201, 204, 404, 422), DTOs como contratos, manejo global de excepciones y documentación OpenAPI.

Errores típicos

  • Exponer entidades de EF Core directamente en los endpoints.
  • Mezclar lógica de aplicación en los controllers.
  • No manejar casos de recurso no encontrado ni errores de validación.
  • Olvidar configurar el versionado, Swagger o el manejo global de excepciones.

2. Teoría

Arquitectura del CMS hasta ahora

Hemos construido la base del CMS en módulos anteriores:

  • Cms.Domain: entidades y excepciones de dominio.
  • Cms.Application: casos de uso, comandos, queries, DTOs e interfaces de repositorios.
  • Cms.Infrastructure: EF Core, PostgreSQL, implementación de repositorios.
  • Cms.Api: ASP.NET Core, controllers, middleware, configuración (nuevo en este módulo).

El proyecto Cms.Api debe ser la capa más delgada posible. Su responsabilidad es recibir peticiones HTTP, delegar en la capa de aplicación y devolver respuestas HTTP correctas.

Flujo de una petición

Cliente HTTP → Cms.Api Controller → MediatR/Service → Cms.Application → Cms.Infrastructure → PostgreSQL
                    ↑_____________________________________________________|
                                     Respuesta HTTP + DTO

Patrones que aplicaremos

PatrónDóndePropósito
Controller-based APICms.ApiOrganizar endpoints por dominio.
CQRS con MediatRCms.ApplicationSeparar comandos y queries.
Result PatternCms.ApplicationEvitar excepciones para flujo normal.
Global Exception HandlerCms.ApiRespuestas de error consistentes.
API VersioningCms.ApiPermitir evolución del contrato.
Swagger/ScalarCms.ApiDocumentación interactiva.

Los controllers deben ser delgados

Un controller profesional contiene solo: validación de entrada básica, llamada a la capa de aplicación y conversión del resultado en respuesta HTTP. La lógica de negocio vive en Cms.Application.

3. Ejemplo mínimo

Antes de construir el CMS completo, veamos un controller mínimo que sigue estas reglas.

// Cms.Api/Controllers/v1/PostsController.cs
using Microsoft.AspNetCore.Mvc;

namespace Cms.Api.Controllers.v1;

[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
[ApiVersion("1.0")]
public class PostsController : ControllerBase
{
    private readonly ISender _mediator;

    public PostsController(ISender mediator)
    {
        _mediator = mediator;
    }

    [HttpGet("{id:guid}")]
    public async Task GetById(Guid id, CancellationToken ct)
    {
        var result = await _mediator.Send(new GetPostByIdQuery(id), ct);
        return result.IsSuccess ? Ok(result.Value) : NotFound();
    }
}

Observa que el controller recibe ISender (de MediatR) y envía un Query. No conoce EF Core, repositorios ni detalles de infraestructura.

4. Ejemplo real

Paso 1: Configurar Program.cs

// Cms.Api/Program.cs
using Cms.Api.Middleware;
using Cms.Application;
using Cms.Infrastructure;
using Scalar.AspNetCore;

var builder = WebApplication.CreateBuilder(args);

// Capas inferiores
builder.Services.AddApplication(builder.Configuration);
builder.Services.AddInfrastructure(builder.Configuration);

// API
builder.Services.AddControllers()
    .AddJsonOptions(options =>
    {
        options.JsonSerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase;
        options.JsonSerializerOptions.DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull;
        options.JsonSerializerOptions.ReferenceHandler = ReferenceHandler.IgnoreCycles;
    });

builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new Asp.Versioning.ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;
    options.ApiVersionReader = new Asp.Versioning.UrlSegmentApiVersionReader();
})
.AddMvc()
.AddApiExplorer(options =>
{
    options.GroupNameFormat = "'v'VVV";
    options.SubstituteApiVersionInUrl = true;
});

builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
    app.MapScalarApiReference();
}

app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseAuthorization();
app.MapControllers();

app.Run();

Paso 2: Global exception handler

// Cms.Api/Middleware/GlobalExceptionHandler.cs
using Cms.Domain.Exceptions;
using Microsoft.AspNetCore.Diagnostics;

namespace Cms.Api.Middleware;

public class GlobalExceptionHandler : IExceptionHandler
{
    private readonly ILogger _logger;

    public GlobalExceptionHandler(ILogger logger)
    {
        _logger = logger;
    }

    public async ValueTask TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        _logger.LogError(exception, "Error no controlado en la API");

        var problemDetails = exception switch
        {
            DomainException domain => new ProblemDetails
            {
                Status = domain.StatusCode,
                Title = GetTitle(domain.StatusCode),
                Detail = domain.Message,
                Instance = httpContext.Request.Path
            },
            _ => new ProblemDetails
            {
                Status = StatusCodes.Status500InternalServerError,
                Title = "Error interno del servidor",
                Detail = "Ocurrió un error inesperado. Inténtalo más tarde.",
                Instance = httpContext.Request.Path
            }
        };

        httpContext.Response.StatusCode = problemDetails.Status!.Value;
        await httpContext.Response.WriteAsJsonAsync(problemDetails, cancellationToken);
        return true;
    }

    private static string GetTitle(int statusCode) => statusCode switch
    {
        StatusCodes.Status404NotFound => "Recurso no encontrado",
        StatusCodes.Status409Conflict => "Conflicto de negocio",
        StatusCodes.Status422UnprocessableEntity => "Error de validación",
        _ => "Error"
    };
}

Paso 3: Controllers CRUD

// Cms.Api/Controllers/v1/PostsController.cs
using Cms.Application.Posts.Commands.CreatePost;
using Cms.Application.Posts.Commands.DeletePost;
using Cms.Application.Posts.Commands.UpdatePost;
using Cms.Application.Posts.Queries.GetPostById;
using Cms.Application.Posts.Queries.ListPosts;
using Microsoft.AspNetCore.Mvc;

namespace Cms.Api.Controllers.v1;

[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
[ApiVersion("1.0")]
public class PostsController : ControllerBase
{
    private readonly ISender _mediator;

    public PostsController(ISender mediator)
    {
        _mediator = mediator;
    }

    [HttpGet]
    public async Task List([FromQuery] ListPostsQuery query, CancellationToken ct)
    {
        var result = await _mediator.Send(query, ct);
        return Ok(result);
    }

    [HttpGet("{id:guid}")]
    public async Task GetById(Guid id, CancellationToken ct)
    {
        var result = await _mediator.Send(new GetPostByIdQuery(id), ct);
        return result.IsSuccess ? Ok(result.Value) : NotFound();
    }

    [HttpPost]
    public async Task Create([FromBody] CreatePostCommand command, CancellationToken ct)
    {
        var result = await _mediator.Send(command, ct);

        if (result.IsFailure)
            return UnprocessableEntity(new { error = result.Error.Message });

        return CreatedAtAction(
            nameof(GetById),
            new { id = result.Value.Id, version = "1.0" },
            result.Value);
    }

    [HttpPut("{id:guid}")]
    public async Task Update(
        Guid id,
        [FromBody] UpdatePostCommand command,
        CancellationToken ct)
    {
        if (id != command.Id)
            return BadRequest(new { error = "El id de ruta no coincide con el del body" });

        var result = await _mediator.Send(command, ct);

        return result.Match(
            success => NoContent(),
            notFound => NotFound(),
            validationError => UnprocessableEntity(new { error = validationError.Message }),
            conflict => Conflict(new { error = conflict.Message })
        );
    }

    [HttpDelete("{id:guid}")]
    public async Task Delete(Guid id, CancellationToken ct)
    {
        var result = await _mediator.Send(new DeletePostCommand(id), ct);
        return result.IsSuccess ? NoContent() : NotFound();
    }
}

Repite la misma estructura para CategoriesController, TagsController y UsersController, adaptando los commands y queries.

Validación con FluentValidation

En el módulo 9 añadiremos FluentValidation con un pipeline de MediatR. Por ahora, la validación básica de entrada (IDs coincidentes, campos requeridos) la hace el controller; la validación de negocio la hace la capa de aplicación.

5. Buenas prácticas

  • Controllers delgados: solo orquestan, no contienen lógica de negocio.
  • DTOs de entrada y salida: nunca expongas entidades de EF Core.
  • Status codes semánticos: 200, 201, 204, 400, 404, 409, 422 según corresponda.
  • Manejo global de errores: un único IExceptionHandler para consistencia.
  • Versionado desde el día uno: aunque solo tengas v1, configura el versionado para facilitar futuros cambios.
  • Documentación: Swagger y Scalar en desarrollo ayudan a probar y entender la API.
  • CancellationToken: siempre en endpoints asíncronos.
  • Configuración de JSON: camelCase, ignorar nulos, evitar ciclos.

6. Errores habituales

Incorrecto: controller con lógica de negocio

// ❌ Mal: el controller valida duplicados y accede a DbContext
[HttpPost]
public async Task Create([FromBody] CreatePostRequest dto)
{
    var exists = await _db.Posts.AnyAsync(p => p.Slug == dto.Slug);
    if (exists)
        return Conflict();

    var post = new Post { ... };
    _db.Posts.Add(post);
    await _db.SaveChangesAsync();
    return Created(...);
}

Correcto: delegar en la capa de aplicación

// ✅ Bien: el controller solo delega y convierte el resultado
[HttpPost]
public async Task Create([FromBody] CreatePostCommand command, CancellationToken ct)
{
    var result = await _mediator.Send(command, ct);
    return result.IsSuccess
        ? CreatedAtAction(nameof(GetById), new { id = result.Value.Id }, result.Value)
        : UnprocessableEntity(new { error = result.Error.Message });
}

Incorrecto: exponer entidades de dominio

// ❌ Mal: devuelve la entidad con navegaciones y campos internos
[HttpGet("{id:guid}")]
public async Task GetById(Guid id)
{
    var post = await _db.Posts.Include(p => p.Author).FirstOrDefaultAsync(p => p.Id == id);
    return post is null ? NotFound() : Ok(post);
}

Correcto: devolver DTO de respuesta

// ✅ Bien: proyección a DTO plano
[HttpGet("{id:guid}")]
public async Task GetById(Guid id, CancellationToken ct)
{
    var result = await _mediator.Send(new GetPostByIdQuery(id), ct);
    return result.IsSuccess ? Ok(result.Value) : NotFound();
}

9. Resumen

  • La capa Cms.Api es la más delgada del CMS.
  • Los controllers delegan en la capa de aplicación mediante MediatR.
  • Usamos DTOs de entrada y salida, nunca entidades de EF Core.
  • Configuramos manejo global de excepciones con IExceptionHandler y ProblemDetails.
  • Versionamos la API por URL path desde el inicio.
  • Documentamos con Swagger y Scalar para facilitar pruebas.
  • Devolvemos status codes semánticos y respuestas consistentes.

10. Preguntas frecuentes

¿Por qué usar MediatR desde el controller?

Desacopla el controller de los handlers de aplicación. El controller no necesita conocer la implementación de cada caso de uso, solo envía un mensaje y recibe un resultado.

¿Dónde va la validación?

La validación de formato y entrada básica puede ir en el controller. La validación de negocio pertenece a la capa de aplicación o dominio. En el módulo 9 usaremos FluentValidation con un pipeline de MediatR.

¿Puedo usar Minimal APIs para el CMS?

Sí, pero dada la cantidad de entidades y operaciones, controllers resultan más organizados. Podrías combinar Minimal APIs para endpoints de salud o diagnóstico.

¿Cómo evito referencias circulares en JSON?

Configura ReferenceHandler.IgnoreCycles y, lo más importante, proyecta a DTOs planos sin navegaciones mutuas.

¿Qué paquetes necesito?

MediatR, Asp.Versioning.Mvc.ApiExplorer, Swashbuckle.AspNetCore, Scalar.AspNetCore y los proyectos de referencia Cms.Application e Cms.Infrastructure.
