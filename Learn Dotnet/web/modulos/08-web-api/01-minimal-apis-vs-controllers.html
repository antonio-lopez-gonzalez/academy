Minimal APIs vs Controller-based

Módulo 8 · ASP.NET Core Web API35 min

1 · Introducción

ASP.NET Core ofrece dos formas de construir APIs HTTP: Minimal APIs y Controllers. Ambas comparten el mismo runtime, el mismo model binding, el mismo routing y el mismo middleware. La diferencia está en la forma de organizar el código.

En esta lección aprenderemos cuándo usar cada una, sus ventajas, sus limitaciones y cómo combinarlas en un mismo proyecto .NET 8.

¿Qué problema resuelven?

Permiten exponer lógica de negocio a través de HTTP sin tener que escribir un servidor web manual. ASP.NET Core se encarga del routing, parsing, serialización, logging, seguridad y mucho más.

Errores típicos

  • Elegir Minimal APIs para un API grande con muchas reglas de negocio y terminar con Program.cs de miles de líneas.
  • Usar controllers para un microservicio pequeño con pocas operaciones y añadir ceremonia innecesaria.
  • Mezclar ambos estilos sin convención clara, confundiendo al equipo.

2 · Teoría

Una API Web en .NET 8 recibe una petición HTTP, la transforma en objetos C#, ejecuta lógica y devuelve una respuesta HTTP. Eso ocurre dentro del pipeline de ASP.NET Core, independientemente de si usas Minimal APIs o Controllers.

Controllers (ControllerBase)

Estilo clásico. Agrupas endpoints en clases que heredan de ControllerBase. El framework se encarga de la instanciación, el model binding, la validación automática y la serialización.

  • Separan claramente rutas, acciones y modelos.
  • Integran filtros, [ApiController], ModelState y helpers como Ok(), NotFound().
  • Son ideales cuando el API crece y necesitas organización por dominio.

Minimal APIs

Introducidas en .NET 6. Permiten mapear directamente una ruta a un delegado o a un método sin clases de controlador. Reducen la ceremonia y el consumo de memoria.

  • Perfectas para microservicios, funciones pequeñas, proxies o APIs con pocas operaciones.
  • Permiten inyección de dependencias directamente en los parámetros del delegado.
  • Consumen menos recursos en el arranque porque no necesitan el pipeline de descubrimiento de controllers.

Decisión práctica

Para el CMS usaremos Controllers porque tendremos CRUD de múltiples entidades (posts, categorías, tags, usuarios) y conviene organizar por dominio. Sin embargo, endpoints de diagnóstico o salud pueden ser Minimal APIs.

3 · Ejemplo mínimo

Crearemos un proyecto web que contenga tanto Minimal API como Controller en el mismo Program.cs.

# Crear un proyecto de API vacío
# --template webapi-empty evita la estructura de controllers por defecto
dotnet new web -n MinimalVsControllers -o MinimalVsControllers
cd MinimalVsControllers

dotnet run --project .
# Probar: http://localhost:5000/api/hello
#         http://localhost:5000/minimal/hello

// Program.cs
using Microsoft.AspNetCore.Mvc;

var builder = WebApplication.CreateBuilder(args);

// Registramos los controllers para la parte clásica
builder.Services.AddControllers();

var app = builder.Build();

// Minimal API: ruta simple sin clase de controlador
app.MapGet("/minimal/hello", () => new { message = "Hola desde Minimal API" });

// Controller-based: mapeamos la ruta base de controllers
app.MapControllers();

app.Run();

// Controllers/HelloController.cs
[ApiController]
[Route("api/[controller]")]
public class HelloController : ControllerBase
{
    [HttpGet]
    public IActionResult Get() =>
        Ok(new { message = "Hola desde Controller" });
}

[ApiController] activa comportamientos automáticos: model binding más estricto, respuesta 400 automática cuando la validación falla, y routing por atributos obligatorio.

¿Qué ocurre aquí?

El mismo WebApplication aloja dos formas de responder. Minimal API usa el pipeline de endpoints; Controller usa el pipeline de ControllerBase. No comparten filtros, pero sí comparten DI, configuración, logging y middleware.

4 · Ejemplo real

En un proyecto profesional conviene agrupar endpoints. Minimal APIs ofrecen MapGroup para aplicar prefijos, filtros y configuraciones comunes.

// Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllers();

var app = builder.Build();

// Grupo de Minimal APIs para endpoints de salud y diagnóstico
var diagnostics = app.MapGroup("/diag")
    .WithTags("Diagnostics")
    .WithOpenApi();

diagnostics.MapGet("/health", () => Results.Ok(new { status = "Healthy" }));
diagnostics.MapGet("/version", (IConfiguration config) =>
    Results.Ok(new { version = config["AppVersion"] ?? "1.0.0" }));

// Controllers para el dominio de negocio
app.MapControllers();

app.Run();

// Controllers/PostsController.cs
using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("api/v1/[controller]")]
public class PostsController : ControllerBase
{
    private readonly IPostService _postService;

    public PostsController(IPostService postService)
    {
        _postService = postService;
    }

    [HttpGet]
    public async Task GetAll(CancellationToken cancellationToken)
    {
        var posts = await _postService.GetAllAsync(cancellationToken);
        return Ok(posts);
    }

    [HttpGet("{id:guid}")]
    public async Task GetById(Guid id, CancellationToken cancellationToken)
    {
        var post = await _postService.GetByIdAsync(id, cancellationToken);
        return post is null ? NotFound() : Ok(post);
    }
}

Cuidado con los ciclos de vida

En Minimal APIs, el parámetro IPostService postService se resuelve desde DI por cada petición. Si tu servicio es Scoped, el endpoint se ejecuta dentro del scope de la petición. Eso es correcto. Si declaras un servicio como Singleton e inyectas un Scoped dentro, tendrás una captive dependency.

5 · Buenas prácticas

  • Usa Controllers para APIs grandes con muchas entidades, filtros, validaciones y separación por dominio.
  • Usa Minimal APIs para endpoints simples: salud, diagnóstico, webhooks, proxies o APIs muy pequeñas.
  • No mezcles estilos sin criterio. Documenta qué partes del API usan cada estilo y por qué.
  • Extrae la lógica de negocio de los endpoints/controladores a servicios de aplicación. Los endpoints deben ser delgados.
  • Usa MapGroup en Minimal APIs para aplicar rutas comunes, tags de OpenAPI y filtros.
  • Activa [ApiController] siempre que uses controllers de API. Aporta validación automática y convenciones.
  • Evita lógica de negocio en Program.cs. Mantén la configuración de servicios y la configuración del pipeline separadas.

6 · Errores habituales

Incorrecto: Program.cs monolítico con Minimal APIs

// ❌ Mal: todo el API en Program.cs
app.MapPost("/posts", async (CreatePostRequest dto, CmsDbContext db) => {
    var post = new Post { Title = dto.Title, Content = dto.Content };
    db.Posts.Add(post);
    await db.SaveChangesAsync();
    return Results.Created($"/posts/{post.Id}", post);
});
app.MapGet("/posts", async (CmsDbContext db) => await db.Posts.ToListAsync());
app.MapPut("/posts/{id}", async (Guid id, UpdatePostRequest dto, CmsDbContext db) => { ... });
// ...cientos de líneas más

Correcto: extraer handlers a métodos estáticos o clases

// ✅ Bien: endpoints delegan en métodos con nombre
var posts = app.MapGroup("/api/v1/posts");
posts.MapGet("/", PostHandlers.GetAll);
posts.MapPost("/", PostHandlers.Create);

public static class PostHandlers
{
    public static async Task GetAll(IPostService service, CancellationToken ct)
    {
        var posts = await service.GetAllAsync(ct);
        return Results.Ok(posts);
    }

    public static async Task Create(CreatePostRequest dto, IPostService service, CancellationToken ct)
    {
        var post = await service.CreateAsync(dto, ct);
        return Results.Created($"/api/v1/posts/{post.Id}", post);
    }
}

Incorrecto: controller sin [ApiController]

// ❌ Mal: falta el atributo, se pierde validación automática y model binding estricto
public class PostsController : ControllerBase
{
    [HttpPost]
    public IActionResult Create(CreatePostRequest dto) { ... }
}

Correcto: controller con [ApiController]

// ✅ Bien: [ApiController] habilita el comportamiento API moderno
[ApiController]
[Route("api/v1/[controller]")]
public class PostsController : ControllerBase
{
    [HttpPost]
    public async Task Create(CreatePostRequest dto) { ... }
}

7 · Ejercicio guiado

Crea un proyecto ASP.NET Core vacío que exponga dos endpoints de lectura de productos: uno con Minimal API y otro con Controller.

  1. Crea el proyecto: dotnet new web -n ProductApi.
  2. Registra controllers en Program.cs.
  3. Crea un ProductController con GET /api/v1/products y GET /api/v1/products/{id}.
  4. Crea un grupo Minimal API en /api/v1/mini-products con las mismas dos operaciones.
  5. Inyecta IProductRepository en ambos estilos.
  6. Ejecuta y prueba con curl o navegador.
// ProductRepository.cs (en memoria para el ejercicio)
public interface IProductRepository
{
    IEnumerable GetAll();
    Product? GetById(int id);
}

public record Product(int Id, string Name, decimal Price);

public class InMemoryProductRepository : IProductRepository
{
    private static readonly List Products = new()
    {
        new Product(1, "Laptop", 1200),
        new Product(2, "Ratón", 25)
    };

    public IEnumerable GetAll() => Products;
    public Product? GetById(int id) => Products.FirstOrDefault(p => p.Id == id);
}

8 · Reto

Extiende el ejercicio anterior para que ambos estilos (Controller y Minimal API) compartan un MapGroup o un prefijo común. Añade un IEndpointFilter o un IActionFilter que registre el tiempo de ejecución de cada petición en el log. Compara la verbosidad de ambas soluciones.

9 · Resumen

  • ASP.NET Core soporta Minimal APIs y Controllers en el mismo proyecto.
  • Controllers son mejores para APIs grandes con muchas entidades y validación automática.
  • Minimal APIs reducen ceremonia y son ideales para microservicios, diagnóstico y endpoints simples.
  • [ApiController] activa validación automática, model binding estricto y routing por atributos.
  • MapGroup permite organizar Minimal APIs por dominio.
  • La lógica de negocio debe vivir fuera de los endpoints/controladores.

10 · Preguntas frecuentes

¿Puedo usar Minimal APIs y Controllers en el mismo proyecto?

Sí. Llama builder.Services.AddControllers() y app.MapControllers() para controllers, y usa app.MapGet/Post/Put/Delete para Minimal APIs. Comparten DI, middleware, configuración y logging.

¿Minimal API es más rápido que Controller?

En la mayoría de casos la diferencia es despreciable. Minimal APIs tienen menos overhead en el arranque y menor consumo de memoria para proyectos pequeños. En APIs grandes, el cuello de botella suele estar en la base de datos o la serialización.

¿Puedo usar ModelState en Minimal APIs?

No. ModelState es parte del pipeline de controllers. En Minimal APIs la validación se hace manualmente, con FluentValidation o con IEndpointFilter.

¿Qué es [ApiController] exactamente?

Es un atributo que aplica convenciones a los controllers: responde 400 ante modelos inválidos, infiere el parámetro [FromBody] para objetos complejos, requiere routing por atributos y devuelve ProblemDetails en errores.

¿Qué pasa si no uso [ApiController]?

El controller sigue funcionando, pero pierdes la validación automática, el model binding estricto y la inferencia de fuentes de parámetros. Tendrás que validar manualmente y escribir más código.
