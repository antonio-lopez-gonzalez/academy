Global Exception Handling y Problem Details

Módulo 8 · ASP.NET Core Web API30 min

1 · Introducción

Toda aplicación falla eventualmente. La diferencia entre una API amateur y una profesional está en cómo gestiona los errores: mensajes útiles para el cliente, logs detallados para el equipo y sin fugas de información sensible.

En esta lección veremos el manejo global de excepciones en .NET 8 con IExceptionHandler, UseExceptionHandler y ProblemDetails siguiendo el estándar RFC 9457.

¿Qué problema resuelve?

Evitar que cada endpoint necesite bloques try/catch repetidos. Centraliza la conversión de excepciones en respuestas HTTP consistentes y seguras.

Errores típicos

  • Poner try/catch en cada controller y devolver mensajes inconsistentes.
  • Exponer stack traces al cliente en producción.
  • Devolver 500 sin más contexto, obligando al cliente a adivinar.
  • Registrar la excepción en el controller en lugar de en el middleware global.

2 · Teoría

El pipeline de ASP.NET Core

El middleware se ejecuta en orden. Cuando ocurre una excepción en un endpoint, el control viaja hacia atrás por el pipeline hasta encontrar un middleware que la capture. Si nadie la captura, ASP.NET Core devuelve un 500 genérico.

Request → ExceptionHandler → Routing → Endpoint → ❗ Excepción
                                     ↑___________________|

IExceptionHandler (.NET 8)

Es la forma moderna y extensible de manejar excepciones. Puedes registrar varios handlers y ASP.NET Core los ejecutará en orden hasta que uno indique que manejó la excepción.

  • Implementa IExceptionHandler.
  • Regístralo con builder.Services.AddExceptionHandler<THandler>().
  • Activa el middleware con app.UseExceptionHandler().
  • Activa ProblemDetails con builder.Services.AddProblemDetails().

ProblemDetails y RFC 9457

ProblemDetails es un formato estándar para errores HTTP. Antes se conocía como RFC 7807; .NET 8 sigue RFC 9457. La respuesta incluye campos como type, title, status, detail, instance y extensiones personalizadas.

Orden importa

Registra AddProblemDetails y AddExceptionHandler en Program.cs y luego usa app.UseExceptionHandler() lo más temprano posible en el pipeline, antes de UseRouting y MapControllers.

3 · Ejemplo mínimo

# Crear proyecto y ejecutar
dotnet new web -n ExceptionHandlingDemo -o ExceptionHandlingDemo
cd ExceptionHandlingDemo
dotnet run --project .
# Probar: GET /api/error          → 500 mapeado a ProblemDetails
#         GET /api/not-found      → 404 mapeado a ProblemDetails
#         GET /api/validation     → 422 mapeado a ProblemDetails

// Program.cs
using Microsoft.AspNetCore.Diagnostics;
using Microsoft.AspNetCore.Mvc;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler();

var app = builder.Build();

app.UseExceptionHandler();
app.MapControllers();

app.Run();

// GlobalExceptionHandler.cs
public class GlobalExceptionHandler : IExceptionHandler
{
    private readonly ILogger _logger;

    public GlobalExceptionHandler(ILogger logger)
    {
        _logger = logger;
    }

    public async ValueTask TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        _logger.LogError(exception, "Excepción no controlada capturada");

        var problemDetails = exception switch
        {
            NotFoundException nf => new ProblemDetails
            {
                Status = StatusCodes.Status404NotFound,
                Title = "Recurso no encontrado",
                Detail = nf.Message,
                Instance = httpContext.Request.Path
            },
            ValidationException ve => new ValidationProblemDetails(ve.Errors)
            {
                Status = StatusCodes.Status422UnprocessableEntity,
                Title = "Error de validación",
                Instance = httpContext.Request.Path
            },
            _ => new ProblemDetails
            {
                Status = StatusCodes.Status500InternalServerError,
                Title = "Error interno del servidor",
                Detail = "Ocurrió un error inesperado. Contacta con soporte.",
                Instance = httpContext.Request.Path
            }
        };

        httpContext.Response.StatusCode = problemDetails.Status!.Value;
        await httpContext.Response.WriteAsJsonAsync(problemDetails, cancellationToken);
        return true;
    }
}

// Excepciones personalizadas de dominio
public class NotFoundException : Exception
{
    public NotFoundException(string message) : base(message) { }
}

public class ValidationException : Exception
{
    public IDictionary Errors { get; }

    public ValidationException(IDictionary errors)
        : base("La solicitud contiene errores de validación")
    {
        Errors = errors;
    }
}

Observa

El handler devuelve true para indicar que manejó la excepción. Si devolviera false, ASP.NET Core pasaría al siguiente handler registrado.

4 · Ejemplo real

En el CMS queremos que excepciones de dominio específicas se conviertan en respuestas HTTP adecuadas, mientras que errores inesperados se oculten al cliente pero se registren con detalle.

// Controllers/PostsController.cs
[ApiController]
[Route("api/v1/[controller]")]
public class PostsController : ControllerBase
{
    private readonly IPostService _postService;

    public PostsController(IPostService postService)
    {
        _postService = postService;
    }

    [HttpGet("{id:guid}")]
    public async Task GetById(Guid id, CancellationToken ct)
    {
        // Sin try/catch: el middleware global se encarga
        var post = await _postService.GetByIdAsync(id, ct);
        return Ok(post);
    }
}

// Domain/Exceptions/DomainException.cs
public abstract class DomainException : Exception
{
    protected DomainException(string message) : base(message) { }
    public abstract int StatusCode { get; }
}

public class PostNotFoundException : DomainException
{
    public PostNotFoundException(Guid id) : base($"Post {id} no encontrado") { }
    public override int StatusCode => StatusCodes.Status404NotFound;
}

public class DuplicateSlugException : DomainException
{
    public DuplicateSlugException(string slug) : base($"El slug '{slug}' ya existe") { }
    public override int StatusCode => StatusCodes.Status409Conflict;
}

// Actualizamos el handler para DomainException
public async ValueTask TryHandleAsync(
    HttpContext httpContext,
    Exception exception,
    CancellationToken cancellationToken)
{
    if (exception is DomainException domainException)
    {
        var problemDetails = new ProblemDetails
        {
            Status = domainException.StatusCode,
            Title = GetTitleForStatus(domainException.StatusCode),
            Detail = domainException.Message,
            Instance = httpContext.Request.Path
        };

        httpContext.Response.StatusCode = problemDetails.Status.Value;
        await httpContext.Response.WriteAsJsonAsync(problemDetails, cancellationToken);
        return true;
    }

    _logger.LogError(exception, "Excepción no controlada");

    var fallback = new ProblemDetails
    {
        Status = StatusCodes.Status500InternalServerError,
        Title = "Error interno del servidor",
        Detail = "Ocurrió un error inesperado.",
        Instance = httpContext.Request.Path
    };

    httpContext.Response.StatusCode = fallback.Status.Value;
    await httpContext.Response.WriteAsJsonAsync(fallback, cancellationToken);
    return true;
}

No expongas detalles internos

En producción, nunca devuelvas stack traces, nombres de servidores o cadenas de conexión. Usa logs para el diagnóstico y ProblemDetails genéricos para el cliente.

5 · Buenas prácticas

  • Centraliza el manejo de excepciones en un IExceptionHandler o middleware.
  • Usa excepciones de dominio específicas para casos conocidos (no encontrado, conflicto, validación).
  • Devuelve ProblemDetails siguiendo RFC 9457.
  • Registra siempre la excepción con ILogger antes de responder.
  • No devuelvas stack traces al cliente en producción.
  • Usa ValidationProblemDetails para errores de validación por campo.
  • Prueba el handler con integration tests usando WebApplicationFactory.

6 · Errores habituales

Incorrecto: try/catch en cada controller

// ❌ Mal: código repetido y respuestas inconsistentes
[HttpGet("{id:guid}")]
public async Task GetById(Guid id)
{
    try
    {
        var post = await _service.GetByIdAsync(id);
        return Ok(post);
    }
    catch (PostNotFoundException ex)
    {
        return NotFound(ex.Message);
    }
    catch (Exception ex)
    {
        return StatusCode(500, ex.Message);
    }
}

Correcto: dejar que el middleware global maneje

// ✅ Bien: el controller solo orquesta, no maneja excepciones
[HttpGet("{id:guid}")]
public async Task GetById(Guid id, CancellationToken ct)
{
    var post = await _service.GetByIdAsync(id, ct);
    return Ok(post);
}

Incorrecto: exponer ex.Message en 500

// ❌ Mal: fugas de información sensible
var problem = new ProblemDetails
{
    Status = 500,
    Detail = exception.Message
};

Correcto: mensaje genérico en 500

// ✅ Bien: detalle genérico al cliente, detalle completo en logs
var problem = new ProblemDetails
{
    Status = 500,
    Title = "Error interno del servidor",
    Detail = "Ocurrió un error inesperado."
};
_logger.LogError(exception, "Error interno: {Message}", exception.Message);

7 · Ejercicio guiado

Implementa un manejador global de excepciones en un proyecto nuevo.

  1. Crea dotnet new web -n ErrorHandlingApi.
  2. Registra AddProblemDetails y AddExceptionHandler<GlobalExceptionHandler>.
  3. Implementa GlobalExceptionHandler que mapee:
    • ArgumentException → 400
    • KeyNotFoundException → 404
    • InvalidOperationException → 409
    • Otras → 500 con mensaje genérico
  4. Crea un controller que lance cada tipo de excepción.
  5. Prueba que devuelva ProblemDetails correctamente.

8 · Reto

Añade un segundo IExceptionHandler especializado en errores de validación de FluentValidation. Haz que convierta ValidationException en ValidationProblemDetails con los errores por campo. Asegúrate de que se ejecute antes que el handler genérico y que el handler genérico sea el último recurso.

9 · Resumen

  • El manejo global de excepciones evita try/catch repetidos y unifica las respuestas de error.
  • IExceptionHandler es la forma moderna en .NET 8.
  • AddProblemDetails habilita respuestas estándar RFC 9457.
  • Usa excepciones de dominio para casos conocidos y un handler genérico para lo inesperado.
  • Nunca expongas stack traces o información sensible al cliente.
  • Registra siempre el error completo en logs para diagnóstico interno.

10 · Preguntas frecuentes

¿Puedo tener varios IExceptionHandler?

Sí. Se ejecutan en orden de registro. Un handler puede devolver false para delegar al siguiente. El último suele ser un handler genérico que siempre devuelve true.

¿Qué diferencia hay entre UseExceptionHandler y IExceptionHandler?

UseExceptionHandler captura excepciones y reejecuta el request en un pipeline de error. IExceptionHandler es un servicio inyectado que decide qué respuesta devolver. En .NET 8 puedes combinar ambos.

¿Qué es ValidationProblemDetails?

Es una especialización de ProblemDetails que incluye un diccionario errors con los errores por campo. Es ideal para respuestas 400/422 de validación.

¿Debo lanzar excepciones para flujo de negocio normal?

Dependerá del patrón que elijas. Result<T> es mejor para flujo controlado. Las excepciones deben reservarse para casos excepcionales o errores que deben detener la operación.

¿Cómo evito fugas de información en producción?

No incluyas exception.Message, stack traces ni datos internos en ProblemDetails. Usa ASPNETCORE_ENVIRONMENT para mostrar más detalle solo en desarrollo si lo necesitas.
