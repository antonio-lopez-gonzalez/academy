Swagger/Scalar y API Versioning

Módulo 8 · ASP.NET Core Web API35 min

1 · Introducción

Una API profesional necesita documentación interactiva y una estrategia de versionado que permita evolucionar sin romper a los clientes existentes. En .NET 8, Swagger sigue siendo la opción más popular, pero Scalar está ganando terreno como alternativa moderna y ligera.

Veremos cómo configurar Swagger y Scalar, cómo versionar una API por URL, query, header y media type, y cómo marcar versiones como obsoletas.

¿Por qué versionar?

Cuando cambias un contrato público (nombres de campos, comportamientos, rutas) los clientes antiguos dejarían de funcionar. El versionado permite introducir cambios en una nueva versión mientras mantienes la anterior.

Errores típicos

  • No documentar la API y obligar a los clientes a adivinar los endpoints.
  • Cambiar endpoints existentes sin mantener compatibilidad.
  • Mezclar versiones en la misma ruta sin convención.
  • Olvidar marcar versiones antiguas como deprecadas.

2 · Teoría

OpenAPI y Swagger

OpenAPI es la especificación. Swagger es el conjunto de herramientas que permite generar, visualizar y probar documentación OpenAPI. En ASP.NET Core, Swashbuckle.AspNetCore genera automáticamente el documento a partir de los endpoints.

Scalar

Scalar es una interfaz moderna para OpenAPI. Es una alternativa a Swagger UI con mejor diseño, soporte para temas oscuros y menos dependencias. Se integra fácilmente con Microsoft.AspNetCore.OpenApi.

Estrategias de versionado

EstrategiaEjemploVentajasInconvenientes
URL path/api/v1/productsExplícita, fácil de cachearRompe REST purista; URLs cambian
Query string/api/products?api-version=1.0URLs limpiasMenos visible, problemas con cache
Headerx-api-version: 1.0URLs establesMenos descubrible
Media typeAccept: application/json; v=1.0REST puroCompleja para clientes

Para el CMS usaremos versionado por URL path porque es el más simple y visible para los clientes.

Atributos de versionado

  • [ApiVersion("1.0")]: declina qué versiones soporta un controller o endpoint.
  • [MapToApiVersion("2.0")]: asigna una acción específica a una versión.
  • [ApiVersion("1.0", Deprecated = true)]: marca la versión como obsoleta.

Convención recomendada

Usa versionado semántico 1.0, 2.0. Mantén al menos una versión estable mientras deprecas la anterior. Documenta claramente la fecha de fin de vida de cada versión.

3 · Ejemplo mínimo

# Crear proyecto
dotnet new webapi -n VersionedApi -o VersionedApi
cd VersionedApi

# Instalar paquetes necesarios
dotnet add package Asp.Versioning.Http
dotnet add package Asp.Versioning.Mvc.ApiExplorer
dotnet add package Swashbuckle.AspNetCore

dotnet run --project .
# Navegar a: http://localhost:5000/swagger

// Program.cs
using Asp.Versioning;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();

// Configurar versionado por URL path
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;
    options.ApiVersionReader = new UrlSegmentApiVersionReader();
})
.AddMvc()
.AddApiExplorer(options =>
{
    options.GroupNameFormat = "'v'VVV";
    options.SubstituteApiVersionInUrl = true;
});

builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI(options =>
    {
        options.SwaggerEndpoint("/swagger/v1/swagger.json", "v1");
        options.SwaggerEndpoint("/swagger/v2/swagger.json", "v2");
    });
}

app.UseHttpsRedirection();
app.UseAuthorization();
app.MapControllers();
app.Run();

// Controllers/v1/ProductsController.cs
using Asp.Versioning;
using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
[ApiVersion("1.0")]
public class ProductsController : ControllerBase
{
    [HttpGet]
    public IActionResult Get() => Ok(new { version = "v1", products = new[] { "laptop", "ratón" } });
}

// Controllers/v2/ProductsController.cs
[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
[ApiVersion("2.0")]
public class ProductsControllerV2 : ControllerBase
{
    [HttpGet]
    public IActionResult Get() => Ok(new { version = "v2", products = new[] { "laptop", "ratón", "teclado" } });
}

Observa

La ruta api/v{version:apiVersion}/[controller] permite que el versionado lea el segmento v1 o v2. SubstituteApiVersionInUrl = true hace que Swagger genere correctamente las URLs.

4 · Ejemplo real

Configuramos Swagger para mostrar múltiples versiones y añadimos Scalar como alternativa. También marcamos la v1 como deprecada.

// Program.cs
builder.Services.AddSwaggerGen(options =>
{
    options.SwaggerDoc("v1", new OpenApiInfo
    {
        Title = "CMS API",
        Version = "v1",
        Description = "Versión 1 del API del CMS. Obsoleta, usa v2."
    });

    options.SwaggerDoc("v2", new OpenApiInfo
    {
        Title = "CMS API",
        Version = "v2",
        Description = "Versión actual del API del CMS."
    });
});

// Scalar como alternativa a Swagger UI
builder.Services.AddScoped();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
    app.MapScalarApiReference(); // Requiere Scalar.AspNetCore
}

// Controller con versión deprecada y acción específica
[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
[ApiVersion("1.0", Deprecated = true)]
[ApiVersion("2.0")]
public class PostsController : ControllerBase
{
    [HttpGet]
    [MapToApiVersion("1.0")]
    public IActionResult GetV1() => Ok(new { message = "Respuesta de v1 (obsoleta)" });

    [HttpGet]
    [MapToApiVersion("2.0")]
    public IActionResult GetV2() => Ok(new { message = "Respuesta mejorada de v2" });
}

Cuidado con los breaking changes

Una nueva versión no debe cambiar el comportamiento de la anterior. Si eliminas un campo, hazlo en una nueva versión y mantén la compatibilidad en la versión anterior durante el período de deprecación.

5 · Buenas prácticas

  • Documenta siempre la API con Swagger o Scalar, al menos en desarrollo.
  • Elige una estrategia de versionado y aplícala de forma consistente.
  • Usa versionado por URL path para APIs públicas de tamaño medio.
  • Mantén compatibilidad en versiones antiguas mientras están soportadas.
  • Marca versiones como obsoletas con Deprecated = true y comunica fechas de fin de vida.
  • Incluye ejemplos y descripciones en los DTOs para enriquecer la documentación.
  • No expongas información sensible en la documentación pública (claves, URLs internas).

6 · Errores habituales

Incorrecto: versionado inconsistente

// ❌ Mal: algunos controllers usan v1, otros /api/products/version2
[Route("api/v1/products")]
public class ProductsV1Controller : ControllerBase { ... }

[Route("api/products/version2")]
public class ProductsV2Controller : ControllerBase { ... }

Correcto: convención unificada

// ✅ Bien: todos siguen el mismo patrón
[Route("api/v{version:apiVersion}/products")]
[ApiVersion("1.0")]
public class ProductsV1Controller : ControllerBase { ... }

[Route("api/v{version:apiVersion}/products")]
[ApiVersion("2.0")]
public class ProductsV2Controller : ControllerBase { ... }

Incorrecto: no configurar ApiExplorer

// ❌ Mal: Swagger no genera documentos por versión
builder.Services.AddApiVersioning();

Correcto: añadir ApiExplorer

// ✅ Bien: necesario para que Swagger descubra versiones
builder.Services.AddApiVersioning()
    .AddMvc()
    .AddApiExplorer(options =>
    {
        options.GroupNameFormat = "'v'VVV";
        options.SubstituteApiVersionInUrl = true;
    });

7 · Ejercicio guiado

Configura un API versionado con dos versiones de un endpoint de usuarios.

  1. Crea dotnet new webapi -n UsersVersionedApi.
  2. Instala Asp.Versioning.Mvc.ApiExplorer y Swashbuckle.AspNetCore.
  3. Configura versionado por URL path con v1 y v2 por defecto.
  4. Crea UsersController con GET /api/v1/users devolviendo { users: [...] }.
  5. En v2, añade paginación: { users: [...], page: 1, total: 100 }.
  6. Configura Swagger para mostrar ambas versiones.
  7. Marca v1 como obsoleta.

8 · Reto

Implementa versionado por header x-api-version para una versión interna del CMS. Configura Swagger para permitir seleccionar la versión desde el header. Luego, combina versionado por URL path para clientes públicos y por header para clientes internos.

9 · Resumen

  • Swagger/Scalar generan documentación interactiva a partir de OpenAPI.
  • El versionado permite evolucionar la API sin romper clientes antiguos.
  • Las estrategias principales son URL path, query string, header y media type.
  • Para el CMS usaremos versionado por URL path.
  • Usa [ApiVersion], [MapToApiVersion] y Deprecated para gestionar versiones.
  • Configura AddApiExplorer para que Swagger descubra correctamente las versiones.

10 · Preguntas frecuentes

¿Swagger UI sigue siendo la opción recomendada?

Sigue siendo la más usada, pero Scalar está creciendo rápidamente por su diseño moderno. Puedes ofrecer ambas en desarrollo.

¿Qué estrategia de versionado es mejor?

URL path es la más sencilla y explícita para APIs públicas. Header es más limpia pero menos descubrible. Query string es menos común en APIs modernas.

¿Cómo marco una versión como obsoleta?

Usa [ApiVersion("1.0", Deprecated = true)]. Swagger mostrará un indicador de deprecación y el header api-deprecated-versions se incluirá en las respuestas.

¿Puedo tener varias versiones en un mismo controller?

Sí, usando [ApiVersion("1.0")] y [ApiVersion("2.0")] en el controller, y [MapToApiVersion] en cada acción.

¿Scalar reemplaza a Swagger completamente?

No, es una interfaz alternativa para documentos OpenAPI. Sigue necesitando generar el documento OpenAPI, ya sea con Swashbuckle o con Microsoft.AspNetCore.OpenApi.
