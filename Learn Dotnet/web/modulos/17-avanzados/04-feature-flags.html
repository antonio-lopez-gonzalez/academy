Feature Flags

Módulo 17 · Temas avanzados25 min

1. Introducción

En esta lección aprenderemos a controlar el comportamiento de nuestra aplicación sin redeployar código. La técnica se llama feature flags (o feature toggles): variables de configuración que activan o desactivan funcionalidades en tiempo de ejecución.

Veremos Microsoft.FeatureManagement, la librería oficial de .NET, que permite habilitar características para todos los usuarios, para un porcentaje, para usuarios concretos o por grupos.

Objetivo de aprendizaje: configurar feature flags en .NET 8, usar IFeatureManager, implementar despliegues progresivos y proteger endpoints con FeatureGate.

2. Teoría

¿Qué es un feature flag?

Un feature flag es una condición en el código que decide si una funcionalidad está activa. En lugar de ramas de código que se despliegan por separado, despliegas el código completo y luego enciendes la funcionalidad cuando esté lista.

Escenarios comunes:

  • Release control: ocultar una función hasta el día del lanzamiento.
  • Canary release: activar una función para el 5% de usuarios y monitorizar.
  • A/B testing: mostrar dos versiones diferentes y comparar métricas.
  • Kill switch: desactivar rápidamente una función que falla en producción.

Microsoft.FeatureManagement

Microsoft.FeatureManagement es el paquete oficial de .NET para trabajar con feature flags. Se integra con IConfiguration, por lo que los flags pueden leerse de appsettings.json, variables de entorno, Azure App Configuration o cualquier otro proveedor.

Tipos de filtros

  • AlwaysOn / AlwaysOff: activado o desactivado globalmente.
  • Percentage: activado para un porcentaje aleatorio de llamadas.
  • Targeting: activado para usuarios, grupos o porcentajes por grupo.
  • TimeWindow: activado solo en un rango de fechas.
  • Custom: filtro personalizado con lógica propia.

Configuración por entorno

Como los feature flags se integran con IConfiguration, puedes definir valores distintos por entorno. Por ejemplo, en appsettings.Development.json puedes activar todos los flags para que los desarrolladores prueben la nueva funcionalidad, mientras que en appsettings.Production.json permanecen desactivados hasta el lanzamiento.

Feature flags en pruebas

Para tests unitarios, inyecta IFeatureManager con un mock o usa una implementación fija. Para tests de integración, puedes establecer un valor fijo en IConfiguration para evitar que tests fallen por aleatoriedad de un filtro porcentual.

Recuerda: un feature flag es una deuda técnica temporal. Cada flag debe tener un propietario, una fecha de caducidad y un plan de eliminación. De lo contrario, acumulan complejidad y hacen imposible saber qué código realmente se ejecuta en producción.

3. Ejemplo mínimo

Activamos una funcionalidad simple desde appsettings.json.

# Instalamos el paquete
dotnet add package Microsoft.FeatureManagement.AspNetCore
// appsettings.json
{
  "FeatureManagement": {
    "NewDashboard": true,
    "BetaSearch": false
  }
}
// Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddFeatureManagement();

var app = builder.Build();

app.MapGet("/", async (IFeatureManager featureManager) =>
{
    if (await featureManager.IsEnabledAsync("NewDashboard"))
    {
        return Results.Ok("Nuevo dashboard activado");
    }

    return Results.Ok("Dashboard clásico");
});

app.Run();

Para ejecutarlo:

dotnet run --project ejemplos/m17-avanzados/FeatureFlagsDemo
Tip: cambia el valor en appsettings.json y observa cómo cambia la respuesta sin recompilar.

4. Ejemplo real

Configuramos un despliegue progresivo por porcentaje y targeting por usuario, y protegemos un endpoint con FeatureGate.

// appsettings.json
{
  "FeatureManagement": {
    "BetaSearch": {
      "EnabledFor": [
        {
          "Name": "Percentage",
          "Parameters": {
            "Value": 25
          }
        }
      ]
    },
    "PremiumReports": {
      "EnabledFor": [
        {
          "Name": "Targeting",
          "Parameters": {
            "Audience": {
              "Users": [ "alice@example.com", "bob@example.com" ],
              "Groups": [ "beta-testers" ],
              "DefaultRolloutPercentage": 10
            }
          }
        }
      ]
    }
  }
}
// Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddFeatureManagement()
    .AddFeatureFilter<PercentageFilter>()
    .AddFeatureFilter<TargetingFilter>();

// Targeting necesita un contexto de usuario
builder.Services.AddHttpContextAccessor();

var app = builder.Build();

app.MapGet("/search", async (IFeatureManager featureManager) =>
{
    if (await featureManager.IsEnabledAsync("BetaSearch"))
    {
        return Results.Ok("Resultados de búsqueda beta");
    }

    return Results.Ok("Resultados de búsqueda clásica");
});

// Bloquea el endpoint si el flag está desactivado
app.MapGet("/reports/premium", [FeatureGate("PremiumReports")]
    () => Results.Ok("Reporte premium generado"));

app.Run();
// TargetingContextAccessor.cs (contexto de usuario para TargetingFilter)
public class TargetingContextAccessor(IHttpContextAccessor httpContextAccessor) : ITargetingContextAccessor
{
    public ValueTask<TargetingContext> GetContextAsync()
    {
        var user = httpContextAccessor.HttpContext?.User;
        var userId = user?.Identity?.Name ?? "anonymous";
        var groups = user?.Claims
            .Where(c => c.Type == ClaimTypes.Role)
            .Select(c => c.Value)
            .ToList() ?? new List<string>();

        return new ValueTask<TargetingContext>(new TargetingContext
        {
            UserId = userId,
            Groups = groups
        });
    }
}
// Filtro personalizado que activa el flag solo en horario de oficina
public class BusinessHoursFilter : IFeatureFilter
{
    public Task<bool> EvaluateAsync(FeatureFilterEvaluationContext context)
    {
        var now = DateTime.UtcNow;
        var isBusinessHours = now.DayOfWeek is not DayOfWeek.Saturday
            and not DayOfWeek.Sunday
            && now.Hour is >= 8 and < 18;

        return Task.FromResult(isBusinessHours);
    }
}

// Registro en Program.cs
builder.Services.AddFeatureManagement()
    .AddFeatureFilter<PercentageFilter>()
    .AddFeatureFilter<TargetingFilter>()
    .AddFeatureFilter<BusinessHoursFilter>();
// appsettings.json con filtro de horario de oficina
{
  "FeatureManagement": {
    "PremiumReports": {
      "EnabledFor": [
        { "Name": "BusinessHours" }
      ]
    }
  }
}
Observación: FeatureGate devuelve 404 si el flag está desactivado. En una API REST sería más claro devolver 403; puedes personalizarlo implementando tu propio filtro o middleware.

5. Buenas prácticas

  • Mantén los flags temporales: cuando un feature se estabiliza, elimina el flag y el código muerto.
  • Nombra los flags por funcionalidad: NewDashboard es mejor que FlagA.
  • Usa targeting para pruebas controladas: activa primero para tu equipo y luego para beta testers.
  • Monitoriza los flags en producción: asegúrate de saber qué flags están activos y en qué porcentaje.
  • Evita anidar muchos flags: demasiados feature flags crean combinaciones imposibles de probar.
  • Documenta el propósito de cada flag: indica cuándo debe eliminarse.
  • Usa Azure App Configuration para flags dinámicos: permite cambiar flags sin reiniciar la aplicación.

6. Errores habituales

Feature flags sin límite de vida

// MAL: flag que nunca se elimina, acumulando deuda técnica
if (await featureManager.IsEnabledAsync("NewDashboard2019"))

Solución: cada flag debe tener un dueño y una fecha de eliminación planificada.

Usar flags para lógica de autorización

// MAL: controlar permisos con feature flags
if (await featureManager.IsEnabledAsync("AdminFeature"))

Solución: la autorización debe usarse con [Authorize], policies y claims. Los feature flags controlan disponibilidad, no permisos.

No registrar el filtro

// MAL: se usa PercentageFilter pero no se registra
builder.Services.AddFeatureManagement();

Solución: registra explícitamente los filtros que uses: .AddFeatureFilter<PercentageFilter>().

7. Ejercicio guiado

Añade un feature flag que active una versión beta del endpoint de posts.

  1. Crea un proyecto web API con dotnet new webapi -n FeatureFlagsExercise.
  2. Instala Microsoft.FeatureManagement.AspNetCore.
  3. Define un flag PostsV2 en appsettings.json con PercentageFilter al 50%.
  4. Crea dos implementaciones de IPostService: PostServiceV1 y PostServiceV2.
  5. En el endpoint GET /posts, usa IFeatureManager para decidir qué servicio inyectar o qué respuesta devolver.
  6. Llama varias veces al endpoint y observa que aproximadamente la mitad de las respuestas son V2.
// Endpoint condicional
app.MapGet("/posts", async (
    IFeatureManager features,
    IPostService v1,
    IPostService v2) =>
{
    var service = await features.IsEnabledAsync("PostsV2") ? v2 : v1;
    return Results.Ok(await service.ListAsync());
});

9. Resumen

  • Los feature flags permiten activar o desactivar funcionalidades sin redeployar.
  • Microsoft.FeatureManagement se integra con IConfiguration.
  • Los filtros incluyen porcentaje, targeting, ventana de tiempo y filtros personalizados.
  • FeatureGate protege endpoints completos.
  • Los flags deben ser temporales y no reemplazar la autorización.

10. Preguntas frecuentes

¿Puedo cambiar un flag en caliente?

Depende del proveedor de configuración. Con appsettings.json el archivo se recarga automáticamente. Con Azure App Configuration puedes cambiar flags desde el portal sin reiniciar.

¿Los flags afectan al rendimiento?

Normalmente no. IFeatureManager cachea los resultados. En escenarios de alto tráfico, monitoriza el tiempo de evaluación.

¿Qué pasa si un flag no está definido?

IsEnabledAsync devuelve false de forma segura. Si usas FeatureGate, el endpoint queda inaccesible.

¿Puedo usar feature flags en librerías de clase?

Sí, inyectando IFeatureManager. Asegúrate de registrar AddFeatureManagement en la aplicación que consume la librería.

¿Feature flags es lo mismo que A/B testing?

No exactamente. Los feature flags son la infraestructura. A/B testing usa feature flags para mostrar variaciones y comparar métricas. Puedes combinarlos.

¿Cómo pruebo un endpoint con FeatureGate?

En tests de integración, usa WebApplicationFactory y configura la sección FeatureManagement en la configuración de prueba. La acción del endpoint se ejecuta solo si el flag está activo.

¿Puedo anidar filtros?

Sí, un flag puede tener varios filtros en EnabledFor. Se evalúan en orden hasta que uno devuelva true (si está configurado con RequirementType predeterminado). También puedes exigir que todos los filtros coincidan con "RequirementType": "All".

¿Cómo hago un filtro personalizado?

Implementa IFeatureFilter y registra el filtro con AddFeatureFilter<MiFiltro>(). El filtro recibe un FeatureFilterEvaluationContext con el nombre del flag y sus parámetros.
