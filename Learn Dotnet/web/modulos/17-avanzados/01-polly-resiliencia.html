Resiliencia con Polly

Módulo 17 · Temas avanzados40 min

1 · Introducción

En esta lección aprenderemos a hacer que nuestras aplicaciones .NET sobrevivan a fallos transitorios: bases de datos que no responden durante 200 ms, APIs externas que devuelven 503, redes inestables. La herramienta que usaremos es Polly, la librería de resiliencia más popular del ecosistema .NET.

No se trata solo de "intentarlo de nuevo". Se trata de decidir cuándo reintentar, cuántas veces, cuánto esperar entre intentos, y qué hacer cuando el fallo deja de ser transitorio.

Veremos retry, circuit breaker, timeout, bulkhead, fallback y cómo combinarlo todo con IHttpClientFactory.

Objetivo de aprendizaje: comprender las políticas de Polly, saber combinarlas en un policy wrap e integrarlas con HttpClient para llamadas externas resilientes.

2 · Teoría

¿Qué es la resiliencia?

La resiliencia es la capacidad de un sistema para recuperarse de fallos sin que el usuario lo note. En una aplicación distribuida, los fallos son inevitables: un nodo de Redis se reinicia, un servicio externo hace despliegue, la red tiene un pico de latencia.

Sin resiliencia, un único error transitorio puede propagarse y provocar un error 500 al cliente. Con resiliencia, la aplicación reintenta, espera o devuelve una respuesta degradada.

Políticas de Polly

Polly organiza el comportamiento de resiliencia en políticas (policies). Cada política responde a excepciones o resultados específicos. Las más importantes son:

  • Retry: vuelve a intentar la operación un número de veces.
  • Circuit Breaker: corta temporalmente las llamadas si hay demasiados fallos seguidos.
  • Timeout: limita el tiempo máximo de una operación.
  • Bulkhead: limita la concurrencia y la cola de operaciones.
  • Fallback: devuelve un valor alternativo cuando todo falla.

Retry fijo vs backoff exponencial

Un retry con intervalo fijo espera siempre lo mismo. Es simple pero puede saturar el servicio caído si todos los clientes reintentan al mismo tiempo.

El backoff exponencial aumenta el tiempo de espera entre intentos (1 s, 2 s, 4 s, 8 s...). Da tiempo a que el servicio se recupere y reduce la carga. Suele añadirse jitter (aleatoriedad) para evitar sincronización de picos.

Retry fijo:          1s  1s  1s  1s  1s
Backoff exponencial: 1s  2s  4s  8s 16s
Backoff con jitter:  0.8s 1.9s 3.5s 9.2s 15.1s

Circuit breaker

Imagina una puerta automática de un supermercado: si detecta que mucha gente tropieza a la entrada, se cierra temporalmente. El circuit breaker funciona igual: si se producen N fallos en un tiempo determinado, las llamadas fallan inmediatamente durante un tiempo de enfriamiento (cooldown). Luego deja pasar una llamada de prueba.

Esto evita saturar un servicio ya sobrecargado y permite recuperarse.

Policy wrap

Las políticas se pueden apilar. El orden importa. Normalmente se usa:

  1. Fallback (última línea de defensa).
  2. Circuit Breaker (protege al servicio).
  3. Retry (reintentos ante fallos transitorios).
  4. Timeout (corta operaciones colgadas).

3 · Ejemplo mínimo

Creamos un retry simple que intenta una operación hasta 3 veces si lanza una HttpRequestException.

# Añadimos el paquete de Polly
dotnet add package Polly

# Versión compatible con IHttpClientFactory
dotnet add package Microsoft.Extensions.Http.Polly
// Program.cs de una aplicación de consola
using Polly;
using Polly.Retry;

// Definimos la política: reintentar hasta 3 veces con espera fija de 1 segundo
var retryPolicy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(
        retryCount: 3,
        sleepDurationProvider: retryAttempt =>
            TimeSpan.FromSeconds(Math.Pow(2, retryAttempt - 1)),
        onRetry: (exception, duration, attempt, context) =>
        {
            Console.WriteLine($"Reintento {attempt} tras {duration.TotalSeconds}s. Error: {exception.Message}");
        });

await retryPolicy.ExecuteAsync(async () =>
{
    using var client = new HttpClient();
    // Esta llamada fallará si el servidor no responde
    var response = await client.GetAsync("https://httpbin.org/status/503");
    response.EnsureSuccessStatusCode();
    return await response.Content.ReadAsStringAsync();
});

Para ejecutarlo:

dotnet run --project ejemplos/m17-avanzados/PollyRetryDemo
Cuidado: new HttpClient() se usa aquí solo para el ejemplo mínimo. En producción usa IHttpClientFactory con PolicyHttpMessageHandler.

4 · Ejemplo real

Configuramos un HttpClient con Polly integrado en ASP.NET Core: retry con backoff exponencial + jitter, circuit breaker y timeout.

// Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddHttpClient<IExternalCatalogService, ExternalCatalogService>(client =>
{
    client.BaseAddress = new Uri("https://api.catalog.example.com/");
    client.Timeout = TimeSpan.FromSeconds(30);
})
.AddPolicyHandler(GetRetryPolicy())
.AddPolicyHandler(GetCircuitBreakerPolicy());

static IAsyncPolicy<HttpResponseMessage> GetRetryPolicy()
{
    return HttpPolicyExtensions
        .HandleTransientHttpError() // 5xx y excepciones de red
        .WaitAndRetryAsync(
            retryCount: 3,
            sleepDurationProvider: retryAttempt =>
                TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)) +
                TimeSpan.FromMilliseconds(Random.Shared.Next(0, 1000)),
            onRetry: (outcome, duration, attempt, context) =>
            {
                // En producción usa ILogger en lugar de Console
                Console.WriteLine($"Reintento {attempt} tras {duration.TotalSeconds:F1}s. Status: {outcome.Result?.StatusCode}");
            });
}

static IAsyncPolicy<HttpResponseMessage> GetCircuitBreakerPolicy()
{
    return HttpPolicyExtensions
        .HandleTransientHttpError()
        .CircuitBreakerAsync(
            handledEventsAllowedBeforeBreaking: 5,
            durationOfBreak: TimeSpan.FromSeconds(30),
            onBreak: (outcome, breakDelay) =>
                Console.WriteLine($"Circuito abierto durante {breakDelay.TotalSeconds}s"),
            onReset: () => Console.WriteLine("Circuito cerrado"),
            onHalfOpen: () => Console.WriteLine("Circuito medio abierto: prueba en curso"));
}
// ExternalCatalogService.cs
public interface IExternalCatalogService
{
    Task<CatalogItem?> GetItemAsync(Guid id, CancellationToken ct = default);
}

public class ExternalCatalogService(HttpClient httpClient, ILogger<ExternalCatalogService> logger)
    : IExternalCatalogService
{
    public async Task<CatalogItem?> GetItemAsync(Guid id, CancellationToken ct = default)
    {
        // Polly ya está aplicado al HttpClient; la llamada es transparente
        var response = await httpClient.GetAsync($"items/{id}", ct);

        if (response.StatusCode == HttpStatusCode.NotFound)
        {
            logger.LogWarning("Item {ItemId} no encontrado", id);
            return null;
        }

        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<CatalogItem>(ct);
    }
}

public sealed record CatalogItem(Guid Id, string Name, decimal Price);

Policy wrap completo

Si queremos controlar el orden exacto de las políticas, usamos Policy.WrapAsync:

// Combinamos fallback, circuit breaker, retry y timeout
var fallback = Policy<HttpResponseMessage>
    .Handle<Exception>()
    .FallbackAsync(
        fallbackValue: new HttpResponseMessage(HttpStatusCode.OK)
        {
            Content = JsonContent.Create(new CatalogItem(Guid.Empty, "Default", 0))
        },
        onFallbackAsync: (result, context) =>
        {
            logger.LogWarning("Fallback activado");
            return Task.CompletedTask;
        });

var timeout = Policy.TimeoutAsync<HttpResponseMessage>(TimeSpan.FromSeconds(10));
var retry = GetRetryPolicy();
var circuitBreaker = GetCircuitBreakerPolicy();

var resilienceStrategy = Policy
    .WrapAsync(fallback, circuitBreaker, retry, timeout);
Tip: el orden en WrapAsync es de fuera hacia dentro. El fallback envuelve al circuit breaker, que envuelve al retry, que envuelve al timeout.

5 · Buenas prácticas

  • Reintenta solo errores transitorios: un 400 por datos inválidos no debe reintentarse.
  • Usa backoff exponencial con jitter: evita que todos los clientes golpeen el servicio al mismo tiempo.
  • Limita el número de reintentos: más de 3-5 reintentos suelen ser contraproducentes.
  • Añade timeout fuera del retry: el timeout total debe controlar el tiempo máximo independientemente de los reintentos.
  • No ocultes errores permanentes: un fallback no debe devolver datos incorrectos silenciosamente.
  • Registra cada reintento: usa ILogger o los callbacks de Polly para observabilidad.
  • Usa bulkhead para recursos críticos: limita cuántas llamadas concurrentes pueden entrar a un servicio externo.

6 · Errores habituales

Reintentar operaciones no idempotentes

// MAL: POST que cobra dinero o crea recursos
await retryPolicy.ExecuteAsync(() => httpClient.PostAsJsonAsync("/orders", order));

Problema: si la solicitud llegó al servidor pero la respuesta se perdió, reintentar puede duplicar el pedido.

Solución: usa idempotency keys o reintenta solo operaciones seguras (GET, PUT con idempotencia).

Retry dentro de un circuit breaker mal ordenado

// MAL: el retry envuelve al circuit breaker
var wrong = Policy.WrapAsync(retry, circuitBreaker);

Problema: los reintentos aumentan el contador de fallos del circuit breaker, abriéndolo antes de tiempo.

Solución: el circuit breaker debe envolver al retry: Policy.WrapAsync(circuitBreaker, retry).

Ignorar HttpClient.Timeout

// MAL: timeout del cliente mayor que el timeout de Polly
client.Timeout = TimeSpan.FromMinutes(5);

Problema: HttpClient.Timeout lanza TaskCanceledException antes de que Polly pueda actuar.

Solución: configura HttpClient.Timeout como infinito o muy alto cuando uses políticas de timeout de Polly.

// WeatherService.cs
public class WeatherService(HttpClient client)
{
    public async Task<WeatherResponse?> GetAsync(string city, CancellationToken ct = default)

        var response = await client.GetAsync($"forecast/{city}", ct);

9 · Resumen

  • La resiliencia protege a la aplicación de fallos transitorios.
  • Polly ofrece retry, circuit breaker, timeout, bulkhead y fallback.
  • El retry debe usar backoff exponencial con jitter.
  • El circuit breaker evita saturar un servicio ya caído.
  • Las políticas se combinan con Policy.WrapAsync y el orden importa.
  • La integración con IHttpClientFactory se hace mediante AddPolicyHandler.

10 · Preguntas frecuentes

¿Polly reemplaza a try/catch?

No. Polly encapsula la estrategia de reintentos, pero sigues necesitando manejar errores que no cubre la política o errores de lógica de negocio.

¿Debo reintentar errores 404?

No. El 404 indica que el recurso no existe, no un fallo transitorio. Usa HandleTransientHttpError() o filtra explícitamente 5xx y excepciones de red.

¿Cómo pruebo un circuit breaker?

Simula varios fallos consecutivos y verifica que la política pasa al estado Open. Luego espera el tiempo de cooldown y comprueba que una llamada de prueba se permite en estado Half-Open.

¿Qué alternativas existen a Polly?

En .NET 8 también puedes usar Microsoft.Extensions.Http.Resilience, que incluye estrategias de resiliencia oficiales inspiradas en Polly. Polly sigue siendo más maduro y flexible.

¿El bulkhead limita por instancia o globalmente?

Por instancia de política. Si tienes múltiples pods en Kubernetes, cada uno tendrá su propio bulkhead. Para límites globales necesitas un componente centralizado como API Gateway o Redis.
