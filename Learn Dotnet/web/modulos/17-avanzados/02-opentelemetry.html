OpenTelemetry: trazas y métricas

Módulo 17 · Temas avanzados40 min

1. Introducción

En esta lección aprenderemos a observar nuestra aplicación .NET de forma estandarizada: trazas distribuidas que siguen una petición de un endpoint a otro, métricas que miden el rendimiento y el estado, y exportadores que envían esa información a sistemas como Jaeger, Zipkin o Prometheus.

El estándar que usamos es OpenTelemetry, soportado por .NET 8 de forma nativa. No dependeremos de librerías propietarias para instrumentar nuestro código.

Objetivo de aprendizaje: instrumentar manualmente con ActivitySource y Meter, integrar ASP.NET Core, EF Core y HttpClient, y exportar a herramientas de observabilidad.

2. Teoría

¿Qué es OpenTelemetry?

OpenTelemetry es un estándar abierto para recopilar telemetría: trazas, métricas y logs. Funciona como un intermediario: tu código genera datos de telemetría, y los exportadores los envían a la herramienta que prefieras (Jaeger, Prometheus, Grafana, Datadog, etc.).

En .NET 8, OpenTelemetry se integra con el sistema de Activities (antes System.Diagnostics.Activity) y con System.Diagnostics.Metrics.

Traces, spans y baggage

Una trace representa la vida completa de una operación: desde que el usuario hace clic hasta que la base de datos devuelve datos. Cada paso es un span. Los spans se relacionan en árbol: un span padre contiene spans hijos.

El baggage permite propagar datos de contexto entre spans, como un tenantId o un correlationId.

Trace: GET /api/posts
├── Span: ASP.NET Core HTTP GET /api/posts (500ms)
│   ├── Span: EF Core query (80ms)
│   ├── Span: HttpClient GET a auth-service (40ms)
│   └── Span: Redis cache lookup (5ms)
└── Span: envío de respuesta (1ms)

ActivitySource

ActivitySource es la fábrica de spans. Tienes que crear una instancia estática y luego usar StartActivity para crear spans. El span debe ser Disposed para cerrarse correctamente.

Meter, Counter y Histogram

Meter es la fábrica de métricas. A partir de un Meter creas:

  • Counter: valor que solo aumenta (número de peticiones, errores).
  • Histogram: muestras que se agrupan en buckets (tiempos de respuesta, tamaños de payload).
  • ObservableCounter / ObservableGauge: valores leídos periódicamente (memoria, CPU).

3. Ejemplo mínimo

Creamos un programa de consola que genera trazas y métricas personalizadas.

# Paquetes necesarios
dotnet add package OpenTelemetry
dotnet add package OpenTelemetry.Exporter.Console
// Program.cs
using System.Diagnostics;
using System.Diagnostics.Metrics;
using OpenTelemetry;
using OpenTelemetry.Metrics;
using OpenTelemetry.Trace;

// 1. Definimos un ActivitySource y un Meter
var activitySource = new ActivitySource("Demo.Telemetry");
var meter = new Meter("Demo.Telemetry");

// 2. Contador y histograma
var requestCounter = meter.CreateCounter<long>("demo.requests");
var responseTimeHistogram = meter.CreateHistogram<double>("demo.response_time_ms");

// 3. Configuramos OpenTelemetry para exportar a consola
using var tracerProvider = Sdk.CreateTracerProviderBuilder()
    .AddSource("Demo.Telemetry")
    .AddConsoleExporter()
    .Build();

using var meterProvider = Sdk.CreateMeterProviderBuilder()
    .AddMeter("Demo.Telemetry")
    .AddConsoleExporter()
    .Build();

// 4. Generamos un span y una métrica
using var activity = activitySource.StartActivity("ProcessOrder");
activity?.SetTag("order.id", Guid.NewGuid().ToString());
activity?.SetTag("order.amount", 123.45m);

requestCounter.Add(1, new KeyValuePair<string, object?>("method", "POST"));
responseTimeHistogram.Record(42.5);

Console.WriteLine("Telemetría enviada a consola");

Para ejecutarlo:

dotnet run --project ejemplos/m17-avanzados/OpenTelemetryDemo
Tip: los ActivitySource y Meter suelen declararse como static readonly para evitar crear instancias repetidas.

4. Ejemplo real

Instrumentamos una API ASP.NET Core con trazas y métricas, integrando automáticamente ASP.NET Core, EF Core y HttpClient.

// Program.cs
using OpenTelemetry.Resources;
using OpenTelemetry.Trace;
using OpenTelemetry.Metrics;

var builder = WebApplication.CreateBuilder(args);

var serviceName = "Cms.Api";

builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource
        .AddService(serviceName)
        .AddAttributes(new Dictionary<string, object>
        {
            ["deployment.environment"] = builder.Environment.EnvironmentName,
            ["service.namespace"] = "cms"
        }))
    .WithTracing(tracing =>
    {
        tracing
            .AddSource("Cms.Api")
            .AddAspNetCoreInstrumentation()
            .AddHttpClientInstrumentation()
            .AddEntityFrameworkCoreInstrumentation()
            .AddOtlpExporter(options =>
            {
                // Envía a un collector OTLP (por defecto http://localhost:4317)
                options.Endpoint = new Uri("http://localhost:4317");
            });
            // También puedes añadir .AddConsoleExporter() para depurar
    })
    .WithMetrics(metrics =>
    {
        metrics
            .AddAspNetCoreInstrumentation()
            .AddHttpClientInstrumentation()
            .AddRuntimeInstrumentation()
            .AddPrometheusExporter();
    });

builder.Services.AddControllers();
builder.Services.AddHttpClient();

var app = builder.Build();

app.UseOpenTelemetryPrometheusScrapingEndpoint(); // Endpoint /metrics
app.MapControllers();
app.Run();
// Telemetry.cs (definición de ActivitySource y Meter)
namespace Cms.Api.Telemetry;

public static class CmsTelemetry
{
    public static readonly ActivitySource ActivitySource = new("Cms.Api");
    public static readonly Meter Meter = new("Cms.Api");

    public static readonly Counter<long> PostsCreated =
        Meter.CreateCounter<long>("cms.posts_created", "posts", "Número de posts creados");

    public static readonly Histogram<double> PostPublishDuration =
        Meter.CreateHistogram<double>("cms.post_publish_duration_ms", "ms", "Tiempo de publicación de posts");
}
// PostsController.cs (fragmento)
[ApiController]
[Route("api/v1/[controller]")]
public class PostsController : ControllerBase
{
    [HttpPost]
    public async Task<ActionResult<PostResponse>> Create(
        [FromBody] CreatePostRequest request,
        [FromServices] IPostService service,
        CancellationToken ct)
    {
        // Iniciamos un span personalizado
        using var activity = CmsTelemetry.ActivitySource.StartActivity("CreatePost");
        activity?.SetTag("post.title", request.Title);

        var stopwatch = Stopwatch.StartNew();
        var result = await service.CreateAsync(request, ct);
        stopwatch.Stop();

        CmsTelemetry.PostsCreated.Add(1,
            new KeyValuePair<string, object?>("category", request.CategoryId.ToString()));
        CmsTelemetry.PostPublishDuration.Record(stopwatch.Elapsed.TotalMilliseconds);

        return CreatedAtAction(nameof(GetById), new { id = result.Id }, result);
    }
}
Observación: al llamar a un servicio externo con HttpClient, OpenTelemetry añade automáticamente un span hijo con la URL, el método HTTP y el status code. Si el servicio externo también está instrumentado, los spans se unen en una traza distribuida gracias a los headers de propagación.

5. Buenas prácticas

  • Usa un ActivitySource y un Meter por assembly o servicio: facilita filtrar y controlar qué instrumentación está activa.
  • No inventes nombres de atributos: usa los estándares semánticos de OpenTelemetry (por ejemplo http.method, db.system).
  • Evita spans muy pequeños: instrumentar cada línea de código genera ruido. Instrumenta operaciones significativas.
  • No pongas datos sensibles en tags: emails, contraseñas o tokens no deben viajar en trazas.
  • Usa histogramas para tiempos: los promedios son engañosos; los histogramas muestran percentiles reales.
  • Exporta a OTLP en producción: es el estándar unificado y desacopla la aplicación de la herramienta final.
  • Configura sampling si hay mucho tráfico: enviar el 100% de trazas puede ser costoso. Usa head-based o tail-based sampling.

6. Errores habituales

No disposear el span

// MAL: el span no se cierra si hay una excepción
var activity = CmsTelemetry.ActivitySource.StartActivity("Operation");
await DoWorkAsync();
activity?.Dispose();

Solución: usa using var activity = ... para garantizar el dispose.

Registrar el ActivitySource sin añadirlo al provider

// MAL: se crea ActivitySource pero no se registra
var source = new ActivitySource("MyService");

// En Program.cs:
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddAspNetCoreInstrumentation()); // Falta .AddSource("MyService")

Solución: siempre incluye .AddSource("NombreDeTuAssembly") para que los spans personalizados se exporten.

Usar métricas sin unidades

// MAL: métrica sin unidad ni descripción
var counter = meter.CreateCounter<int>("things");

Solución: incluye unidades y descripciones claras: "requests", "ms", "bytes".

9. Resumen

  • OpenTelemetry permite recopilar trazas, métricas y logs de forma estandarizada.
  • ActivitySource crea spans; Meter crea contadores, histogramas y gauges.
  • ASP.NET Core, EF Core y HttpClient se instrumentan automáticamente con paquetes NuGet.
  • OTLP es el exportador recomendado para producción.
  • Evita exponer datos sensibles y no generes spans excesivamente pequeños.

10. Preguntas frecuentes

¿OpenTelemetry reemplaza a Serilog?

No. Serilog es un logging framework. OpenTelemetry puede exportar logs a través de OTLP, pero sigues pudiendo usar Serilog como generador. En .NET 8 la integración entre ILogger y OpenTelemetry es cada vez más directa.

¿Por qué no veo mis spans personalizados?

Probablemente olvidaste .AddSource("Nombre.Del.Source") en el TracerProvider. Verifica también que el ActivitySource se crea con el mismo nombre.

¿Qué diferencia hay entre OTLP y Jaeger?

OTLP es un protocolo de envío. Jaeger es un backend que recibe datos (puede recibir OTLP) y los muestra. Tu aplicación envía a OTLP; Jaeger almacena y visualiza.

¿Cómo mido un contador con tags?

Usa el overload de Add que acepta ReadOnlySpan<KeyValuePair<string, object?>>. Los tags permiten segmentar las métricas.

¿Puedo usar OpenTelemetry en BackgroundService?

Sí, pero debes crear el span dentro del scope de trabajo. Si el servicio procesa mensajes de una cola, inicia un nuevo span por mensaje y añade el traceparent si el mensaje lo incluye.
