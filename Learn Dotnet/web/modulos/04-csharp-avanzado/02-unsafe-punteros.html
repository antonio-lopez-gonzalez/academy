unsafe y punteros

Módulo 4 · C# Avanzado30 min

1 · Introducción

En esta lección exploramos el código no seguro (unsafe) de C#: punteros, direcciones de memoria, pinning de objetos gestionados y la interoperabilidad con código nativo. Veremos cuándo tiene sentido usarlo y cuándo es mejor evitarlo.

¿Por qué existe? Porque el runtime de .NET gestiona automáticamente la memoria, mueve objetos en el heap durante las compactaciones del GC y verifica límites. El código unsafe permite saltarse esas protecciones para obtener rendimiento máximo o interactuar con bibliotecas nativas (C/C++, drivers, GPU).

¿Cuándo se utiliza? Solo cuando:

  • Procesas millones de elementos y el overhead de bounds checking es inaceptable.
  • Interoperas con código nativo (P/Invoke, COM, drivers).
  • Trabajas con hardware o redes a bajo nivel.
  • Implementas algoritmos de criptografía, compresión o procesamiento de imágenes.

Errores típicos: olvidar el bloque fixed, usar punteros con objetos que el GC puede mover, acceder a memoria liberada, confundir aritmética de punteros.

2 · Teoría

2.1. El contexto unsafe

Para usar punteros en C# debes marcar el bloque, método o proyecto con unsafe. Además, el proyecto debe permitir código no seguro en el .csproj:

<PropertyGroup>
  <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
</PropertyGroup>

Un puntero es una variable que almacena una dirección de memoria. El tipo T* significa "puntero a T". El operador &x obtiene la dirección de x, y *p obtiene el valor almacenado en esa dirección.

2.2. Pinning con fixed

Los objetos gestionados (arrays, strings) pueden ser movidos por el GC. Si necesitas pasar su dirección a código nativo o trabajar con punteros, debes "fijarlos" con fixed. Dentro del bloque fixed, el objeto no se moverá.

2.3. Marshalling

Marshal.AllocHGlobal reserva memoria no gestionada desde el heap nativo. Debes liberarla manualmente con Marshal.FreeHGlobal. Si olvidas liberarla, hay memory leak real (el GC no lo limpia).

2.4. Function pointers

C# 9 introdujo function pointers (delegate*) para pasar punteros a funciones nativas sin crear un delegado gestionado. Son más ligeros que los delegates normales, pero menos seguros.

2.5. Diagrama: managed vs unmanaged memory

┌────────────────────────────────────────────────────────────────────┐
│                         MANAGED HEAP (.NET GC)                       │
│  ┌─────────────────┐                                               │
│  │  byte[] buffer  │  ← el GC puede mover este array durante        │
│  │  [0,1,2,3,4,...]│    la compactación                             │
│  └────────┬────────┘                                               │
│           │                                                         │
│  fixed {  │  }  ← bloqueo temporal: el array no se mueve            │
│           │                                                         │
└───────────┼─────────────────────────────────────────────────────────┘
            │
            │  &buffer[0]  ← puntero a la dirección fija
            │
┌───────────┼─────────────────────────────────────────────────────────┐
│           │              UNMANAGED HEAP (AllocHGlobal)              │
│  ┌────────┴────────┐                                              │
│  │  IntPtr native  │  ← memoria reservada manualmente               │
│  │  0x7F...        │    debes liberarla con FreeHGlobal             │
│  └─────────────────┘                                              │
│                                                                    │
│  STACK: stackalloc byte[64] ← memoria rápida, liberada al salir    │
└────────────────────────────────────────────────────────────────────┘

2.6. Comparación con C/C++

En C/C++ todo el código es "unsafe" por defecto: no hay GC, no hay bounds checking, no hay type safety. En C# el código unsafe es una zona especial que debes habilitar explícitamente. El resto del código sigue siendo seguro. Esto permite escribir el 5% crítico en punteros y el 95% restante con la seguridad habitual de .NET.

3 · Ejemplo mínimo

Creamos un proyecto de consola con AllowUnsafeBlocks.

dotnet new console -n UnsafeDemo -o ejemplos/m04-csharp-avanzado/unsafe-demo/src/UnsafeDemo

Modificamos el .csproj:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
    <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
  </PropertyGroup>
</Project>

Program.cs:

// Ejemplo mínimo de punteros y fixed en C#
using System;
using System.Runtime.InteropServices;

int number = 42;

// 1. Obtener dirección de una variable local de pila
unsafe
{
    int* p = &number;
    Console.WriteLine($"Valor: {*p}, Dirección: {(nint)p:X}");
}

// 2. Recorrer un array con punteros usando fixed
int[] values = [1, 2, 3, 4, 5];
unsafe
{
    fixed (int* ptr = values)
    {
        for (int i = 0; i < values.Length; i++)
        {
            Console.WriteLine($"values[{i}] = {ptr[i]}");
        }
    }
}

// 3. Memoria no gestionada con AllocHGlobal
IntPtr native = Marshal.AllocHGlobal(64);
try
{
    unsafe
    {
        byte* p = (byte*)native;
        for (int i = 0; i < 64; i++)
        {
            p[i] = (byte)i;
        }
        Console.WriteLine($"Byte 10 en memoria nativa: {p[10]}");
    }
}
finally
{
    Marshal.FreeHGlobal(native);
}

Explicación:

  • int* p = &number;: declara un puntero a entero y le asigna la dirección de number.
  • *p: dereferencia el puntero para leer el valor.
  • fixed (int* ptr = values): fija el array en memoria para que el GC no lo mueva durante el bloque.
  • ptr[i]: indexación de punteros sin bounds checking.
  • Marshal.AllocHGlobal: reserva memoria nativa. Siempre liberamos con FreeHGlobal en un finally.

4 · Ejemplo real

Implementamos una función que invierte un array de bytes in-place usando punteros. Luego la comparamos con la versión segura.

public static class ByteReverser
{
    // Versión segura con Span (recomendada)
    public static void ReverseSafe(Span<byte> data)
    {
        for (int i = 0, j = data.Length - 1; i < j; i++, j--)
        {
            (data[i], data[j]) = (data[j], data[i]);
        }
    }

    // Versión unsafe con punteros (solo para benchmarking/educativo)
    public static unsafe void ReverseUnsafe(byte[] data)
    {
        fixed (byte* start = data)
        {
            byte* left = start;
            byte* right = start + data.Length - 1;
            while (left < right)
            {
                byte temp = *left;
                *left = *right;
                *right = temp;
                left++;
                right--;
            }
        }
    }
}

Function pointer: llamar a una función nativa simulada.

public static class NativeInterop
{
    // Simulamos un callback nativo con function pointer
    public static unsafe int ApplyToEach(int* values, int length, delegate* managed<int, int> transform)
    {
        int sum = 0;
        for (int i = 0; i < length; i++)
        {
            values[i] = transform(values[i]);
            sum += values[i];
        }
        return sum;
    }
}

// Uso
int[] nums = [1, 2, 3, 4, 5];
unsafe
{
    fixed (int* p = nums)
    {
        int sum = NativeInterop.ApplyToEach(p, nums.Length, &DoubleValue);
        Console.WriteLine(sum); // 30
    }
}

static int DoubleValue(int x) => x * 2;

En la práctica, para interop real usarías [LibraryImport] (source-generated P/Invoke en .NET 7+) en lugar de punteros manuales, pero entender los punteros te ayuda a depurar problemas de marshalling.

5 · Buenas prácticas

  • Usa unsafe solo cuando el rendimiento sea crítico y no haya alternativa segura.
  • Prefiere Span<T> y Memory<T> antes de saltar a punteros.
  • Limita el tamaño del bloque fixed para no penalizar al GC.
  • Libera siempre la memoria no gestionada con FreeHGlobal o VirtualFree.
  • Usa [LibraryImport] para P/Invoke en .NET 8; reduce marshalling y mejora performance.
  • Documenta claramente qué métodos contienen código unsafe.

6 · Errores habituales

6.1. Olvidar fixed

// ❌ MAL: el array puede moverse por el GC
unsafe
{
    int* p = values; // Error de compilación si values es managed
}

Correcto:

// ✅ BIEN: fijar el array antes de obtener su dirección
unsafe
{
    fixed (int* p = values)
    {
        // usar p
    }
}

6.2. No liberar memoria nativa

// ❌ MAL: memory leak
IntPtr p = Marshal.AllocHGlobal(1024);
// uso...
// ¡nunca se libera!

Correcto:

// ✅ BIEN: try/finally garantiza la liberación
IntPtr p = Marshal.AllocHGlobal(1024);
try
{
    // uso...
}
finally
{
    Marshal.FreeHGlobal(p);
}

6.3. Aritmética de punteros incorrecta

// ❌ MAL: accede más allá del array
unsafe
{
    fixed (int* p = values)
    {
        int x = p[values.Length]; // fuera de rango
    }
}

Correcto:

// ✅ BIEN: validar siempre los límites
unsafe
{
    fixed (int* p = values)
    {
        for (int i = 0; i < values.Length; i++)
        {
            Console.WriteLine(p[i]);
        }
    }
}

7 · Ejercicio guiado

Implementa un método unsafe que sume todos los elementos de un int[] usando un puntero. Asegúrate de usar fixed.

Solución:

public static unsafe int SumWithPointer(int[] values)
{
    if (values.Length == 0) return 0;

    fixed (int* p = values)
    {
        int sum = 0;
        int* end = p + values.Length;
        for (int* current = p; current < end; current++)
        {
            sum += *current;
        }
        return sum;
    }
}

Observa cómo el bucle avanza el puntero en lugar de usar índices. Es más eficiente porque evita recalcular la dirección base + índice en cada iteración.

9 · Resumen

  • El código unsafe permite usar punteros y omitir comprobaciones del runtime.
  • Requiere AllowUnsafeBlocks en el proyecto.
  • Los objetos managed deben fijarse con fixed antes de obtener su dirección.
  • La memoria nativa reservada con AllocHGlobal debe liberarse manualmente.
  • Los function pointers permiten callbacks nativos sin delegados gestionados.
  • Usa unsafe solo cuando sea necesario; Span<T> suele ser suficiente.

10 · Preguntas frecuentes

¿El código unsafe rompe la seguridad de tipos?
No rompe la seguridad de tipos del resto de la aplicación, pero dentro del bloque unsafe sí puedes cometer errores de memoria. Es una zona de menor seguridad.
¿Puedo usar unsafe en ASP.NET Core?
Sí, siempre que el proyecto lo permita, pero es raro necesitarlo en una API web normal. Aparece en librerías de bajo nivel, criptografía, networking o procesamiento de imágenes.
¿fixed es costoso?
Fijar un objeto le dice al GC que no lo mueva. No es costoso en sí, pero si fijas muchos objetos grandes durante mucho tiempo puedes fragmentar el heap. Mantén los bloques fixed cortos.
¿Qué alternativa tengo a Marshal.AllocHGlobal?
Para buffers temporales pequeños, usa stackalloc o ArrayPool<T>. Para interop nativo, NativeMemory (.NET 6+) es más moderno y seguro que Marshal.AllocHGlobal.
