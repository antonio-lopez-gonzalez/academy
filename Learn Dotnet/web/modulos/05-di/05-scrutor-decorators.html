Decorators con Scrutor y Open Generics

Módulo 5 · Inyección de Dependencias30 min

1 · Introducción

El contenedor DI de .NET cubre los casos básicos, pero la industria profesional necesita patrones avanzados: decorar servicios, escanear assemblies y registrar genéricos abiertos. Ahí entra Scrutor y la capacidad de registrar typeof(IRepository<>).

  • Qué vamos a aprender: el patrón Decorator, Scrutor para decoración automática, assembly scanning, open generic registration y cómo comparar con la decoración manual.
  • Problema que resuelve: añadir comportamiento transversal (logging, cache, retry, métricas) sin modificar el servicio original.
  • Cuándo se utiliza: cuando necesitas cachear, loguear, medir o validar llamadas a un servicio sin ensuciar su implementación.
Errores típicos: crear manualmente un Decorator para cada servicio, registrar decoradores en orden incorrecto, escanear assemblies sin filtros o usar open generics para tipos que no comparten semántica.

2 · Teoría

2.1. Patrón Decorator

El Decorator es un patrón estructural que envuelve un objeto con otro que comparte la misma interfaz. El cliente no distingue entre el original y el decorado. Es ideal para añadir responsabilidades de forma dinámica.

Patrón Decorator:

  ┌──────────────┐
  │   IService   │◀──────────── Cliente
  └──────┬───────┘
         │
    ┌────┴────┐
    │         │
    ▼         ▼
┌────────┐ ┌─────────────┐
│Service │ │  Decorator  │──contiene──▶ Service
│(real)  │ │  (logging)  │              (real)
└────────┘ └─────────────┘

El cliente usa IService. El Decorator intercepta las llamadas,
añade comportamiento (logging, cache, métricas) y delega al servicio real.

2.2. Decoración manual

Consiste en crear una clase que implemente la misma interfaz, reciba la implementación real por constructor y delegue los métodos. Funciona pero no escala si tienes muchas interfaces.

2.3. Scrutor

Scrutor es un paquete NuGet que extiende IServiceCollection con:

  • Assembly scanning: registrar automáticamente todas las implementaciones de una interfaz.
  • Decoration: envolver servicios con decoradores sin crear clases manualmente.

2.4. Open Generic Registration

Permite registrar un servicio genérico abierto (IRepository<T>) contra una implementación genérica abierta (Repository<T>). Una sola línea cubre todos los tipos concretos.

2.5. Orden de decoradores

Cuando aplicas varios decoradores, el orden importa. Si decoras primero con cache y luego con logging, las llamadas se medirán y loguearán antes de consultar la caché. Si inviertes el orden, primero se usa la caché y solo los misses se loguean.

3 · Ejemplo mínimo

Decoración manual de un servicio de pedidos.

public interface IOrderService
{
    Task<Order?> GetByIdAsync(int id);
}

public class OrderService : IOrderService
{
    public Task<Order?> GetByIdAsync(int id)
    {
        return Task.FromResult<Order?>(new Order { Id = id, Total = 99.99m });
    }
}

public class LoggingOrderService(IOrderService inner, ILogger<LoggingOrderService> logger) : IOrderService
{
    public async Task<Order?> GetByIdAsync(int id)
    {
        logger.LogInformation("Obteniendo pedido {Id}", id);
        var result = await inner.GetByIdAsync(id);
        logger.LogInformation("Pedido {Id} obtenido", id);
        return result;
    }
}

// Registro manual
services.AddSingleton<IOrderService, OrderService>();
services.AddSingleton<IOrderService>(provider =>
{
    var inner = new OrderService();
    var logger = provider.GetRequiredService<ILogger<LoggingOrderService>>();
    return new LoggingOrderService(inner, logger);
});

// Problema: la segunda AddSingleton reemplaza la primera
// Necesitamos registrar el servicio real con un nombre distinto o usar Scrutor
Observación: registrar el mismo servicio dos veces hace que la última implementación "gane". Scrutor resuelve esto con el concepto de Decorate.

4 · Ejemplo real

Usamos Scrutor para decorar automáticamente y escanear assemblies. También registramos un repositorio genérico abierto.

// Instalar Scrutor:
// dotnet add package Scrutor

var builder = WebApplication.CreateBuilder(args);

// 1. Assembly scanning: registrar todos los servicios que terminan en "Service" contra sus interfaces
builder.Services.Scan(scan => scan
    .FromAssemblyOf<Program>()
    .AddClasses(classes => classes.Where(c => c.Name.EndsWith("Service")))
    .AsImplementedInterfaces()
    .WithScopedLifetime());

// 2. Open generic registration: IRepository -> EfRepository
builder.Services.AddScoped(typeof(IRepository<>), typeof(EfRepository<>));

// 3. Decorar IOrderService con logging
builder.Services.Decorate<IOrderService, LoggingOrderService>();

// 4. Decorar también con cache (logging será el más externo)
builder.Services.Decorate<IOrderService, CachingOrderService>();

var app = builder.Build();

app.MapGet("/orders/{id}", async (int id, IOrderService service) =>
    await service.GetByIdAsync(id));

app.Run();

// Interfaces y servicios
public interface IOrderService
{
    Task<Order?> GetByIdAsync(int id);
}

public class OrderService : IOrderService
{
    public Task<Order?> GetByIdAsync(int id) =>
        Task.FromResult<Order?>(new Order { Id = id, Total = 99.99m });
}

public class LoggingOrderService(IOrderService inner, ILogger<LoggingOrderService> logger) : IOrderService
{
    public async Task<Order?> GetByIdAsync(int id)
    {
        logger.LogInformation("Inicio: GetByIdAsync({Id})", id);
        var result = await inner.GetByIdAsync(id);
        logger.LogInformation("Fin: GetByIdAsync({Id})", id);
        return result;
    }
}

public class CachingOrderService(IOrderService inner, IMemoryCache cache) : IOrderService
{
    public async Task<Order?> GetByIdAsync(int id)
    {
        var key = $"order:{id}";
        if (cache.TryGetValue(key, out Order? cached))
        {
            return cached;
        }

        var result = await inner.GetByIdAsync(id);
        if (result is not null)
        {
            cache.Set(key, result, TimeSpan.FromMinutes(5));
        }

        return result;
    }
}

public interface IRepository<T> where T : class
{
    Task<T?> GetByIdAsync(Guid id);
}

public class EfRepository<T>(DbContext context) : IRepository<T> where T : class
{
    public Task<T?> GetByIdAsync(Guid id) =>
        context.Set<T>().FindAsync(id).AsTask();
}

public class Order
{
    public int Id { get; set; }
    public decimal Total { get; set; }
}
Orden de decoración: en el ejemplo, la cadena es CachingOrderService → LoggingOrderService → OrderService. El cliente llama a Caching, que si no hay cache delega a Logging, que delega a OrderService. Scrutor aplica los decoradores en el orden de llamada a Decorate.

6 · Errores habituales

Error 1: Registrar el decorador sin el servicio base

// INCORRECTO: decorate necesita que el servicio base ya esté registrado
builder.Services.Decorate<IOrderService, LoggingOrderService>();

// CORRECTO: primero la implementación, luego el decorador
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.Decorate<IOrderService, LoggingOrderService>();

Error 2: Decorar sin respetar el lifetime

// INCORRECTO: Singleton envolviendo un Scoped
services.AddScoped<IOrderService, OrderService>();
services.AddSingleton<IOrderService, LoggingOrderService>(); // Captive Dependency

// CORRECTO: el decorador debe tener el mismo lifetime que el servicio base
services.AddScoped<IOrderService, OrderService>();
services.Decorate<IOrderService, LoggingOrderService>(); // Scrutor respeta el lifetime

Error 3: Escanear assembly sin filtros

// INCORRECTO: escanea todo y registra clases no deseadas
builder.Services.Scan(scan => scan
    .FromAssemblyOf<Program>()
    .AddClasses()
    .AsImplementedInterfaces()
    .WithScopedLifetime());

// CORRECTO: filtra por namespace o sufijo
builder.Services.Scan(scan => scan
    .FromAssemblyOf<Program>()
    .AddClasses(classes => classes.InNamespaces("Cms.Application.Services"))
    .AsImplementedInterfaces()
    .WithScopedLifetime());

Error 4: Decorador con dependencia Scoped dentro de Singleton

// INCORRECTO: el decorador Singleton captura un servicio Scoped
public class SingletonDecorator(IScopedService scoped) : IOrderService { ... }

// CORRECTO: usa IServiceScopeFactory o haz el decorador Scoped
public class LoggingOrderService(IOrderService inner, IServiceScopeFactory scopeFactory) : IOrderService
{
    public async Task<Order?> GetByIdAsync(int id)
    {
        using var scope = scopeFactory.CreateScope();
        var scoped = scope.ServiceProvider.GetRequiredService<IScopedService>();
        // ...
        return await inner.GetByIdAsync(id);
    }
}

7 · Ejercicio guiado

Crea una aplicación de consola que use Scrutor para decorar un servicio de pedidos con métricas.

  1. Instala Scrutor.
  2. Crea IOrderService y OrderService.
  3. Crea MetricsOrderService que mida el tiempo de cada operación con Stopwatch.
  4. Registra el servicio base y añade el decorador con Decorate.
  5. Resuelve IOrderService y observa que las métricas se ejecutan.
var services = new ServiceCollection();

services.AddScoped<IOrderService, OrderService>();
services.Decorate<IOrderService, MetricsOrderService>();

var provider = services.BuildServiceProvider();

using var scope = provider.CreateScope();
var service = scope.ServiceProvider.GetRequiredService<IOrderService>();
await service.GetByIdAsync(1);

public interface IOrderService
{
    Task<Order?> GetByIdAsync(int id);
}

public class OrderService : IOrderService
{
    public Task<Order?> GetByIdAsync(int id) =>
        Task.FromResult<Order?>(new Order { Id = id, Total = 100m });
}

public class MetricsOrderService(IOrderService inner) : IOrderService
{
    public async Task<Order?> GetByIdAsync(int id)
    {
        var sw = Stopwatch.StartNew();
        var result = await inner.GetByIdAsync(id);
        sw.Stop();
        Console.WriteLine($"GetByIdAsync({id}) tomó {sw.ElapsedMilliseconds} ms");
        return result;
    }
}

public class Order
{
    public int Id { get; set; }
    public decimal Total { get; set; }
}

9 · Resumen

  • El patrón Decorator añade comportamiento transversal sin modificar el servicio original.
  • La decoración manual funciona para pocos servicios; Scrutor escala para muchos.
  • Decorate<TInterface, TDecorator> envuelve automáticamente la implementación registrada.
  • El orden de los decoradores determina el orden de ejecución del comportamiento.
  • El assembly scanning de Scrutor automatiza el registro masivo de servicios.
  • La open generic registration registra typeof(IRepository<>) contra typeof(EfRepository<>) de una sola vez.
  • Los decoradores deben respetar el lifetime del servicio base para evitar Captive Dependencies.

10 · Preguntas frecuentes

¿Scrutor es oficial de Microsoft?

No, Scrutor es un paquete de la comunidad mantenido por Kristian Hellang. Es muy estable y ampliamente usado en producción. No es parte de Microsoft.Extensions.DependencyInjection, pero extiende su API de forma natural.

¿Puedo decorar sin Scrutor?

Sí, manualmente registrando una factory que construya el decorador con la implementación interna. El problema es que debes hacerlo por cada interfaz, y el orden de registro importa. Scrutor simplifica el proceso y mantiene el lifetime correcto.

¿Qué es un open generic?

Es un tipo genérico sin tipos concretos cerrados, como IRepository<> en lugar de IRepository<Post>. Permite registrar una sola abstracción para todos los tipos T que se usen en la aplicación.

¿Puedo decorar un servicio registrado como open generic?

Sí, pero la sintaxis de Scrutor para decorar genéricos abiertos es ligeramente diferente. Puedes usar Decorate(typeof(IRepository<>), typeof(LoggingRepository<>)). Asegúrate de que el decorador también sea un open generic con la misma firma.

¿Puedo tener múltiples decoradores para el mismo servicio?

Sí, llamando a Decorate varias veces. Cada llamada envuelve la implementación anterior. El orden de las llamadas define la cadena de ejecución. Piensa en ello como capas de una cebolla.
