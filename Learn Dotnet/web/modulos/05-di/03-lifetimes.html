Singleton, Scoped, Transient + Captive Dependencies

Módulo 5 · Inyección de Dependencias35 min

1 · Introducción

El contenedor DI no solo crea objetos: también decide cuánto vive cada objeto. Esa decisión es el lifetime y es la causa más común de bugs sutiles en aplicaciones .NET.

  • Qué vamos a aprender: Singleton, Scoped, Transient, cuándo usar cada uno y por qué mezclarlos mal crea Captive Dependencies.
  • Problema que resuelve: controlar el ciclo de vida de los servicios para compartir recursos, aislar estados y evitar fugas de memoria o datos compartidos entre requests.
  • Cuándo se utiliza: en cada registro de servicio. La elección de lifetime es tan importante como la elección de la interfaz.
Errores típicos: usar Singleton para todo, inyectar Scoped dentro de Singleton, usar Transient para servicios costosos o compartir estado mutable en Singleton.

2 · Teoría

2.1. Los tres lifetimes

Lifetime¿Cuántas instancias?¿Cuándo se destruye?Uso típico
SingletonUna en toda la aplicaciónAl cerrar la aplicaciónConfiguración, cachés, conexiones compartidas, logging
ScopedUna por scopeAl cerrar el scopeDbContext, servicios de un request HTTP
TransientUna nueva cada vez que se pideCuando se deja de usarServicios ligeros sin estado, factorías

2.2. ¿Qué es un scope?

Un scope es un contexto de vida. En ASP.NET Core, cada request HTTP crea un scope. Cuando el request termina, se eliminan las instancias Scoped. Puedes crear scopes manualmente con IServiceScopeFactory.

Lifetimes en ASP.NET Core:

┌─────────────────────────────────────────┐
│           Aplicación (root)              │
│  Singleton:   [Config] [Cache] [Logger]   │
│                                          │
│  ┌─────────────────────────────┐        │
│  │      Request HTTP 1         │        │
│  │  Scoped: [DbContext]        │        │
│  │  Transient: [A] [B] [C]     │        │
│  └─────────────────────────────┘        │
│                                          │
│  ┌─────────────────────────────┐        │
│  │      Request HTTP 2         │        │
│  │  Scoped: [DbContext]        │        │
│  │  Transient: [A] [B] [C]     │        │
│  └─────────────────────────────┘        │
└─────────────────────────────────────────┘

Singleton: compartido entre todos los requests.
Scoped: compartido solo dentro de un request.
Transient: nuevo en cada resolución.

2.3. Captive Dependencies

Una Captive Dependency ocurre cuando un servicio de lifetime largo (por ejemplo, Singleton) depende de uno de lifetime corto (por ejemplo, Scoped). El servicio corto se "captura" y vive más de lo debido.

Ejemplo clásico: un Singleton que contiene un DbContext registrado como Scoped. El DbContext debería morir al terminar el request, pero como el Singleton vive toda la aplicación, el DbContext nunca se descarta.

2.4. ValidateScopes y ValidateOnBuild

.NET puede detectar Captive Dependencies al construir el provider o al resolver servicios. Se activa con ValidateScopes y ValidateOnBuild. En desarrollo ASP.NET Core está activado por defecto.

3 · Ejemplo mínimo

Este programa demuestra la diferencia entre los tres lifetimes.

using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection();

services.AddSingleton<SingletonService>();
services.AddScoped<ScopedService>();
services.AddTransient<TransientService>();

var provider = services.BuildServiceProvider();

for (int i = 1; i <= 2; i++)
{
    Console.WriteLine($"--- Scope {i} ---");
    using var scope = provider.CreateScope();
    var sp = scope.ServiceProvider;

    var s1 = sp.GetRequiredService<SingletonService>();
    var s2 = sp.GetRequiredService<SingletonService>();
    var sc1 = sp.GetRequiredService<ScopedService>();
    var sc2 = sp.GetRequiredService<ScopedService>();
    var t1 = sp.GetRequiredService<TransientService>();
    var t2 = sp.GetRequiredService<TransientService>();

    Console.WriteLine($"Singleton:    {s1.Id} == {s2.Id}  => {s1.Id == s2.Id}");
    Console.WriteLine($"Scoped:       {sc1.Id} == {sc2.Id}  => {sc1.Id == sc2.Id}");
    Console.WriteLine($"Transient:    {t1.Id} == {t2.Id}  => {t1.Id == t2.Id}");
}

public class SingletonService
{
    public Guid Id { get; } = Guid.NewGuid();
}

public class ScopedService
{
    public Guid Id { get; } = Guid.NewGuid();
}

public class TransientService
{
    public Guid Id { get; } = Guid.NewGuid();
}
Salida esperada: Singleton siempre igual; Scoped igual dentro del mismo scope, diferente entre scopes; Transient siempre diferente.

4 · Ejemplo real

En una aplicación ASP.NET Core con Entity Framework Core, la elección de lifetime es crítica.

var builder = WebApplication.CreateBuilder(args);

// Singleton: compartido, sin estado, seguro para hilos
builder.Services.AddSingleton<IPostCache, PostCache>();

// Scoped: una instancia por request HTTP. Ideal para DbContext.
builder.Services.AddDbContext<CmsDbContext>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("Default")!),
    ServiceLifetime.Scoped);

// Transient: nuevo cada vez. Útil para servicios ligeros sin estado.
builder.Services.AddTransient<IEmailFormatter, EmailFormatter>();

// Scoped: lógica de negocio que debe compartir DbContext dentro del request
builder.Services.AddScoped<IPostService, PostService>();

var app = builder.Build();

app.MapGet("/posts", async (IPostService service) =>
    Results.Ok(await service.GetAllAsync()));

app.Run();

public class PostService(IPostCache cache, CmsDbContext dbContext, IEmailFormatter formatter)
{
    public async Task<IReadOnlyList<Post>> GetAllAsync()
    {
        // PostService es Scoped; dbContext es Scoped; ambos viven el mismo request.
        var posts = await dbContext.Posts.ToListAsync();
        return posts;
    }
}
Regla: los servicios que dependen de un Scoped (como DbContext) también deben ser Scoped o Transient. Nunca Singleton.

6 · Errores habituales

Error 1: Scoped dentro de Singleton

// INCORRECTO: Captive Dependency
public class PostCache(CmsDbContext dbContext) : IPostCache
{
    // dbContext es Scoped, pero el cache es Singleton.
    // El DbContext se queda vivo toda la vida de la aplicación.
}

builder.Services.AddSingleton<IPostCache, PostCache>();
builder.Services.AddDbContext<CmsDbContext>(o => o.UseNpgsql("..."));

// CORRECTO: el cache es Singleton, pero usa IServiceScopeFactory para crear scopes
public class PostCache(IServiceScopeFactory scopeFactory) : IPostCache
{
    public Post? Get(Guid id)
    {
        using var scope = scopeFactory.CreateScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<CmsDbContext>();
        return dbContext.Posts.Find(id);
    }
}

Error 2: Usar Transient para todo

// INCORRECTO: crea una instancia de todo en cada resolución. Ineficiente.
services.AddTransient<IMapper, Mapper>();
services.AddTransient<IConfigurationReader, ConfigurationReader>();

// CORRECTO: Mapper sin estado puede ser Singleton; config también Singleton
services.AddSingleton<IMapper, Mapper>();
services.AddSingleton<IConfigurationReader, ConfigurationReader>();

Error 3: Singleton con estado mutable

// INCORRECTO: estado mutable compartido entre requests sin sincronización
public class RequestCounter
{
    public int Count { get; set; } // Race condition potencial
}

// CORRECTO: stateless o inmutable, o usar ConcurrentDictionary/Interlocked
public class RequestCounter
{
    private long _count;
    public long Increment() => Interlocked.Increment(ref _count);
}

Error 4: No validar scopes en tests

// INCORRECTO: container sin validación
var provider = services.BuildServiceProvider();

// CORRECTO: detecta Captive Dependencies al construir
var provider = services.BuildServiceProvider(new ServiceProviderOptions
{
    ValidateScopes = true,
    ValidateOnBuild = true
});

7 · Ejercicio guiado

Crea una aplicación de consola que demuestre Captive Dependencies y cómo detectarlas.

  1. Registra ScopedService como Scoped.
  2. Registra SingletonService como Singleton que reciba ScopedService por constructor.
  3. Construye el provider con ValidateScopes = true.
  4. Intenta resolver SingletonService desde el scope. ¿Qué excepción obtienes?
  5. Corrige el problema usando IServiceScopeFactory dentro del Singleton.
var services = new ServiceCollection();
services.AddScoped<ScopedService>();
services.AddSingleton<SingletonService>();

var provider = services.BuildServiceProvider(new ServiceProviderOptions
{
    ValidateScopes = true,
    ValidateOnBuild = true
});

using var scope = provider.CreateScope();
try
{
    var singleton = scope.ServiceProvider.GetRequiredService<SingletonService>();
    Console.WriteLine(singleton.GetMessage());
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"Error detectado: {ex.Message}");
}

public class ScopedService
{
    public string GetMessage() => "Soy scoped";
}

public class SingletonService
{
    public SingletonService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    private readonly IServiceScopeFactory _scopeFactory;

    public string GetMessage()
    {
        using var scope = _scopeFactory.CreateScope();
        var scoped = scope.ServiceProvider.GetRequiredService<ScopedService>();
        return scoped.GetMessage();
    }
}
Consejo: en ASP.NET Core Development, ValidateScopes ya está activado. Si ves Cannot resolve scoped service from root provider, es porque un Singleton está pidiendo un Scoped directamente.

9 · Resumen

  • Singleton: una sola instancia para toda la aplicación. Ideal para configuración, caches y servicios sin estado.
  • Scoped: una instancia por scope. Ideal para DbContext y lógica de negocio de un request.
  • Transient: nueva instancia en cada resolución. Ideal para servicios ligeros y sin estado.
  • Las dependencias deben tener un lifetime igual o más corto que su consumidor.
  • Una Captive Dependency ocurre cuando un servicio largo captura uno corto. Se detecta con ValidateScopes.
  • Para que un Singleton use un Scoped, debe crear un scope con IServiceScopeFactory.
  • Evita estado mutable en Singleton; si es necesario, usa primitivas thread-safe.

10 · Preguntas frecuentes

¿Qué lifetime debo usar por defecto?

Como punto de partida, usa Scoped para servicios de aplicación y acceso a datos, Singleton para servicios sin estado compartidos y Transient para factorías o servicios muy ligeros. No hay un default universal: depende de si el servicio tiene estado, si es seguro para concurrencia y si depende de otros servicios.

¿Por qué DbContext debe ser Scoped?

DbContext mantiene estado de seguimiento de entidades. Si fuera Singleton, se compartiría entre requests y causaría errores de concurrencia y datos incorrectos. Si fuera Transient, cada resolución tendría su propio contexto y perderías la coherencia transaccional dentro de un mismo request.

¿Puede un Transient depender de un Scoped?

Sí, dentro del mismo scope. El Transient se creará dentro del scope activo y recibirá la misma instancia Scoped. El problema aparece cuando un Transient resuelto desde el provider raíz intenta obtener un Scoped: el scope no existe y se comporta como singleton o lanza excepción según la configuración.

¿Qué es exactamente Cannot resolve scoped service from root provider?

Significa que estás intentando obtener un servicio Scoped desde el ServiceProvider raíz (sin scope) o desde un Singleton. El provider raíz no tiene un scope asociado, así que un servicio Scoped no tiene contexto de vida válido. La solución es crear un scope con IServiceScopeFactory o cambiar el lifetime.

¿HttpClient debe ser Singleton o Transient?

No uses HttpClient directamente con DI. Usa IHttpClientFactory (registrado como Singleton) y resuelve HttpClient como Transient a través de la factory. IHttpClientFactory gestiona los sockets y evita agotar los puertos del sistema. Lo veremos en el módulo de HTTP avanzado.
