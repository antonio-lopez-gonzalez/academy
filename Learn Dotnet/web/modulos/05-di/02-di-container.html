El contenedor de DI de .NET por dentro

Módulo 5 · Inyección de Dependencias35 min

1 · Introducción

En la lección anterior aprendimos qué es DI y por qué importa. Ahora vamos a abrir el capó del contenedor de inyección de dependencias que incluye .NET.

  • Qué vamos a aprender: IServiceCollection, ServiceDescriptor, ServiceProvider, BuildServiceProvider, IServiceScopeFactory y cómo se resuelven los servicios.
  • Problema que resuelve: automatizar la composición de objetos sin perder el control ni caer en la magia negra.
  • Cuándo se utiliza: en cualquier aplicación .NET que use ASP.NET Core, worker services, tests o aplicaciones de consola.
Errores típicos: llamar BuildServiceProvider en medio de ConfigureServices, no entender la diferencia entre IServiceCollection y IServiceProvider, o confiar en que el contenedor resuelva automáticamente ciclos sin configurarlos.

2 · Teoría

2.1. Los tres actores principales

TipoRepresentaAnalogía
IServiceCollectionEl catálogo de servicios registradosEl menú de un restaurante
ServiceDescriptorCada registro: qué servicio, qué implementación, qué lifetimeUn plato del menú
IServiceProviderEl resolvedor de instanciasEl cocinero que prepara el plato

2.2. IServiceCollection

Es una lista de ServiceDescriptor. El WebApplicationBuilder expone builder.Services como una implementación concreta. Aquí es donde ocurre el registro de servicios.

2.3. ServiceDescriptor

Cada descriptor contiene:

  • ServiceType: la abstracción (interfaz o clase base).
  • ImplementationType: la clase concreta que se instanciará.
  • ImplementationInstance: una instancia ya existente (modo singleton manual).
  • ImplementationFactory: una factory para crear el servicio.
  • Lifetime: Singleton, Scoped o Transient.

2.4. IServiceProvider

Es el objeto que resuelve servicios. Se obtiene al llamar BuildServiceProvider() sobre la colección. Expone métodos como GetService<T>() y GetRequiredService<T>().

2.5. IServiceScopeFactory y scopes

Los servicios con lifetime Scoped se crean una vez por scope. En ASP.NET Core cada request HTTP crea un scope. El IServiceScopeFactory permite crear scopes explícitos en background services o tests.

Flujo de resolución:

┌─────────────────────┐
│   IServiceCollection │  ← Registro de servicios
│   (ServiceDescriptors) │
└──────────┬────────────┘
           │ BuildServiceProvider()
           ▼
┌─────────────────────┐
│   IServiceProvider   │  ← Motor de resolución
└──────────┬────────────┘
           │ GetService<IOrderService>()
           ▼
┌─────────────────────┐
│   IOrderService      │
│   (OrderService)     │
└──────────┬────────────┘
           │ Constructor necesita IOrderRepository
           ▼
┌─────────────────────┐
│   IOrderRepository   │
│   (SqlOrderRepository)│
└─────────────────────┘

2.6. Activación de constructores

El contenedor selecciona el constructor público con más parámetros que pueda resolver. Si hay ambigüedad o múltiples constructores, lanza una excepción.

3 · Ejemplo mínimo

Construimos un contenedor desde cero en una aplicación de consola.

using Microsoft.Extensions.DependencyInjection;

// 1. Crear la colección de servicios
var services = new ServiceCollection();

// 2. Registrar servicios con su lifetime
services.AddSingleton<IGreetingService, GreetingService>();
services.AddTransient<IUserRepository, UserRepository>();
services.AddScoped<UserGreeter>();

// 3. Construir el ServiceProvider
var provider = services.BuildServiceProvider();

// 4. Resolver servicios
var greeter = provider.GetRequiredService<UserGreeter>();
greeter.Greet(1);

public interface IGreetingService
{
    string SayHello(string name);
}

public class GreetingService : IGreetingService
{
    public string SayHello(string name) => $"Hola, {name}";
}

public interface IUserRepository
{
    string? GetName(int id);
}

public class UserRepository : IUserRepository
{
    public string? GetName(int id) => id == 1 ? "Ana" : null;
}

public class UserGreeter(IGreetingService greetingService, IUserRepository userRepository)
{
    public void Greet(int id)
    {
        var name = userRepository.GetName(id) ?? "desconocido";
        Console.WriteLine(greetingService.SayHello(name));
    }
}
Salida: Hola, Ana. El contenedor resolvió IGreetingService e IUserRepository y los inyectó en UserGreeter.

4 · Ejemplo real

En ASP.NET Core el contenedor se configura en Program.cs. Veamos un ejemplo más completo con registros explícitos, factory y resolución manual de un scope.

var builder = WebApplication.CreateBuilder(args);

// Registro tipo-interfaz
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();

// Registro con factory para leer configuración
builder.Services.AddSingleton<IShippingCalculator>(provider =>
{
    var configuration = provider.GetRequiredService<IConfiguration>();
    var flatRate = configuration.GetValue<decimal>("Shipping:FlatRate");
    return new ShippingCalculator(flatRate);
});

// Registro de instancia existente
builder.Services.AddSingleton(new EmailTemplateEngine("es-ES"));

// Registro de clase concreta sin interfaz
builder.Services.AddScoped<OrderService>();

var app = builder.Build();

// Crear un scope explícito para resolver servicios scoped
app.MapPost("/orders/{id}/ship", async (int id, IServiceScopeFactory scopeFactory) =>
{
    using var scope = scopeFactory.CreateScope();
    var service = scope.ServiceProvider.GetRequiredService<OrderService>();
    var result = await service.ShipAsync(id);
    return result ? Results.Ok() : Results.NotFound();
});

app.Run();

public class OrderService(IOrderRepository repository, IShippingCalculator shipping)
{
    public async Task<bool> ShipAsync(int id)
    {
        var order = await repository.GetByIdAsync(id);
        if (order is null) return false;

        order.ShippingCost = shipping.Calculate(order.Total);
        await repository.SaveAsync(order);
        return true;
    }
}
Decisión: usa factories cuando necesites datos de configuración u otras dependencias para construir el servicio. Si la construcción es trivial, usa el registro tipo-interfaz directo.

6 · Errores habituales

Error 1: Llamar BuildServiceProvider en Program.cs antes de tiempo

// INCORRECTO: crea un contenedor parcial y luego continúa registrando
var tempProvider = builder.Services.BuildServiceProvider();
var config = tempProvider.GetRequiredService<IConfiguration>();
builder.Services.AddSingleton(new MyService(config));

// CORRECTO: usa la configuración ya disponible o una factory
builder.Services.AddSingleton<IMyService>(provider =>
{
    var config = provider.GetRequiredService<IConfiguration>();
    return new MyService(config);
});

Error 2: Resolver servicios scoped desde el provider raíz

// INCORRECTO: provider raíz no tiene scope
var provider = services.BuildServiceProvider();
var scoped = provider.GetRequiredService<MyScopedService>(); // Funciona, pero es un singleton captivo

// CORRECTO: crear un scope
using var scope = provider.CreateScope();
var scoped = scope.ServiceProvider.GetRequiredService<MyScopedService>();

Error 3: Registrar múltiples implementaciones sin propósito claro

// INCORRECTO: si hay varias implementaciones, GetRequiredService devuelve la última
services.AddTransient<IValidator, EmailValidator>();
services.AddTransient<IValidator, PhoneValidator>();

// CORRECTO: usa IEnumerable<IValidator> cuando necesitas todas
public class ValidationService(IEnumerable<IValidator> validators) { /* ... */ }

Error 4: No registrar una dependencia indirecta

// INCORRECTO: se registró OrderService pero no IOrderRepository
services.AddScoped<OrderService>();
// Falta: services.AddScoped<IOrderRepository, SqlOrderRepository>();

// Al resolver: InvalidOperationException: no hay registro para IOrderRepository

7 · Ejercicio guiado

Crea una aplicación de consola .NET 8 que use el contenedor DI manualmente. Pasos:

  1. Crea una interfaz ILogger con void Log(string message).
  2. Crea ConsoleLogger y FileLogger como implementaciones.
  3. Crea PaymentService que reciba ILogger por constructor.
  4. Registra todo en ServiceCollection, construye ServiceProvider y resuelve PaymentService.
  5. Prueba ambas implementaciones cambiando solo el registro.
var services = new ServiceCollection();
services.AddTransient<ILogger, ConsoleLogger>();
services.AddTransient<PaymentService>();

var provider = services.BuildServiceProvider();
var paymentService = provider.GetRequiredService<PaymentService>();

paymentService.ProcessPayment(100m);

public interface ILogger
{
    void Log(string message);
}

public class ConsoleLogger : ILogger
{
    public void Log(string message) => Console.WriteLine($"[LOG] {message}");
}

public class PaymentService(ILogger logger)
{
    public void ProcessPayment(decimal amount)
    {
        logger.Log($"Procesando pago de {amount:C}");
    }
}

8 · Reto

Reto: Implementa un contenedor DI mínimo

Crea una mini-librería de inyección de dependencias sin usar Microsoft.Extensions.DependencyInjection:

  • Permite registrar un tipo de servicio contra una implementación.
  • Soporta solo Transient y Singleton.
  • Resuelve el constructor público con más parámetros.
  • Resuelve recursivamente las dependencias del constructor.
  • Implementa GetService<T>().

Al terminar, pruébalo con OrderService e IOrderRepository. Entenderás por qué el contenedor de .NET es un autómata que hace lo mismo que harías manualmente.

9 · Resumen

  • IServiceCollection es el catálogo de registros. ServiceDescriptor describe cada registro.
  • BuildServiceProvider convierte el catálogo en un motor de resolución.
  • IServiceProvider resuelve servicios mediante GetService o GetRequiredService.
  • El contenedor elige el constructor con más parámetros resolvibles.
  • Los servicios se pueden registrar por tipo, factory o instancia existente.
  • Los servicios Scoped se deben resolver dentro de un IServiceScope.
  • Evita construir un ServiceProvider intermedio durante la configuración.

10 · Preguntas frecuentes

¿Qué diferencia hay entre GetService y GetRequiredService?

GetService devuelve null si el servicio no está registrado. GetRequiredService lanza InvalidOperationException. Usa GetRequiredService para dependencias obligatorias y GetService para opcionales.

¿Puedo tener varios constructores?

El contenedor selecciona el constructor público con más parámetros que pueda resolver. Si hay varios constructores con la misma cantidad de parámetros resolvibles, lanzará una excepción. La recomendación es tener un solo constructor público.

¿Qué pasa si no registro una dependencia indirecta?

El contenedor falla al resolver el servicio que la necesita. Por ejemplo, si registras OrderService pero no IOrderRepository, al pedir OrderService obtendrás InvalidOperationException indicando que no hay registro para la interfaz.

¿Cuándo usar AddSingleton con instancia?

Cuando ya tienes una instancia construida antes de configurar el contenedor y quieres compartirla. Útil para objetos de configuración, caches precargados o conexiones ya inicializadas. Cuidado: si la instancia depende de otros servicios, usa una factory en su lugar.

¿Puedo usar el contenedor DI fuera de ASP.NET Core?

Sí. El paquete Microsoft.Extensions.DependencyInjection es independiente. Puedes usarlo en aplicaciones de consola, workers, tests o cualquier proyecto .NET. Solo necesitas crear un ServiceCollection, registrar servicios y llamar BuildServiceProvider.
