¿Qué es DI? El problema que resuelve

Módulo 5 · Inyección de Dependencias30 min

1 · Introducción

En esta lección vamos a entender qué es la Inyección de Dependencias (DI), por qué nació y qué problema resuelve antes de siquiera abrir el contenedor de .NET.

  • Qué vamos a aprender: el concepto de dependencia, acoplamiento, inversión de control, Poor Man's DI y la primera toma de contacto con IServiceCollection.
  • Problema que resuelve: evitar que las clases se construyan unas a otras con new, dificultando los tests, el cambio de implementaciones y la mantenibilidad.
  • Cuándo se utiliza: siempre que una clase necesite colaborar con otra para cumplir su responsabilidad.
Errores típicos: crear dependencias con new dentro de los constructores, usar static para compartir servicios, mezclar lógica de negocio con creación de objetos, o pensar que DI es solo una librería en lugar de un principio de diseño.

2 · Teoría

2.1. ¿Qué es una dependencia?

Una clase A depende de una clase B cuando necesita una instancia de B para funcionar. Si A crea a B con new, ambas están fuertemente acopladas.

2.2. Acoplamiento vs cohesión

ConceptoBuenoMalo
AcoplamientoBajo (dependo de abstracciones)Alto (dependo de implementaciones concretas)
CohesiónAlta (cada clase hace una sola cosa)Baja (una clase hace de todo)

2.3. Inversión de Control (IoC)

Normalmente una clase controla la creación de sus dependencias. Con Inversión de Control, el control se invierte: alguien externo (el contenedor DI) crea y proporciona las dependencias.

Sin IoC:
┌──────────────┐
│  OrderService │──new──▶ SqlOrderRepository
└──────────────┘

Con IoC:
┌──────────────┐
│  OrderService │◀────── IOrderRepository
└──────────────┘           ▲
                           │
                 ┌─────────┴─────────┐
                 │   DI Container    │
                 └─────────┬─────────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
   SqlOrderRepository   MockRepository   MemoryRepository

2.4. Inyección de Dependencias vs IoC

DI es una forma concreta de aplicar IoC: las dependencias se inyectan desde fuera. Existen tres formas principales:

  1. Constructor injection: la más recomendada. Obligatoria, documenta claramente las dependencias.
  2. Property/Setter injection: opcional, útil para dependencias no esenciales.
  3. Method injection: se pasa la dependencia como parámetro de un método.

2.5. Poor Man's DI

Antes de usar un contenedor, podemos hacer DI manualmente. Es conocido como Poor Man's DI o Pure DI. El código es simple, pero no escala en aplicaciones grandes.

3 · Ejemplo mínimo

Partimos de un servicio que crea su propia dependencia (alto acoplamiento) y lo convertimos a inyección por constructor.

Versión acoplada (antes)

// INCORRECTO: la clase crea su dependencia concreta
public class OrderService
{
    private readonly SqlOrderRepository _repository;

    public OrderService()
    {
        _repository = new SqlOrderRepository(); // Acoplamiento fuerte
    }

    public decimal CalculateTotal(int orderId)
    {
        var order = _repository.GetById(orderId);
        return order.Total;
    }
}

Versión con inyección por constructor

// CORRECTO: depende de una abstracción, no de una implementación
public interface IOrderRepository
{
    Order? GetById(int orderId);
}

public class OrderService
{
    private readonly IOrderRepository _repository;

    // La dependencia la recibe desde fuera
    public OrderService(IOrderRepository repository)
    {
        _repository = repository;
    }

    public decimal CalculateTotal(int orderId)
    {
        var order = _repository.GetById(orderId);
        return order?.Total ?? 0m;
    }
}

public class SqlOrderRepository : IOrderRepository
{
    public Order? GetById(int orderId) => new Order { Id = orderId, Total = 99.99m };
}

public class MemoryOrderRepository : IOrderRepository
{
    public Order? GetById(int orderId) => new Order { Id = orderId, Total = 49.99m };
}

public class Order
{
    public int Id { get; set; }
    public decimal Total { get; set; }
}

Poor Man's DI manual

// Composición manual en la aplicación (console, test, web...)
var repository = new SqlOrderRepository();
var service = new OrderService(repository);

var total = service.CalculateTotal(1);
Console.WriteLine($"Total: {total}");

// En un test podemos sustituir fácilmente la implementación
var fakeRepository = new MemoryOrderRepository();
var serviceForTest = new OrderService(fakeRepository);
Consejo: haz el ejercicio de componer manualmente primero. Si entiendes Poor Man's DI, entenderás por qué el contenedor de .NET es solo un automatismo de lo mismo.

4 · Ejemplo real

En una aplicación ASP.NET Core usamos el contenedor DI integrado. Registramos abstracciones e implementaciones, y el runtime resuelve automáticamente los constructores.

// Program.cs de una aplicación .NET 8
var builder = WebApplication.CreateBuilder(args);

// 1. Registramos la abstracción y su implementación
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();

// 2. Registramos el servicio que depende de esa abstracción
builder.Services.AddScoped<OrderService>();

var app = builder.Build();

// 3. El contenedor resuelve OrderService inyectando automáticamente IOrderRepository
app.MapGet("/orders/{id}/total", (int id, OrderService service) =>
{
    var total = service.CalculateTotal(id);
    return Results.Ok(total);
});

app.Run();

Lo que ocurre internamente:

  1. El contenedor ve que OrderService necesita IOrderRepository.
  2. Busca en su catálogo una implementación registrada: SqlOrderRepository.
  3. Crea el SqlOrderRepository y lo pasa al constructor de OrderService.
  4. Devuelve el OrderService listo para usar.
Registrar: decirle al contenedor qué implementación devolver para cada abstracción.
Resolver: pedirle al contenedor una instancia construida con todas sus dependencias.

6 · Errores habituales

Error 1: Dependencia concreta en el constructor

// INCORRECTO: depende de la implementación concreta
public class OrderService
{
    private readonly SqlOrderRepository _repository;
    public OrderService(SqlOrderRepository repository) => _repository = repository;
}

// CORRECTO: depende de la abstracción
public class OrderService
{
    private readonly IOrderRepository _repository;
    public OrderService(IOrderRepository repository) => _repository = repository;
}

Error 2: Crear dependencias con new dentro de métodos

// INCORRECTO: no se puede testar ni cambiar la implementación
public decimal CalculateTotal(int orderId)
{
    var repository = new SqlOrderRepository(); // new es un code smell
    var order = repository.GetById(orderId);
    return order?.Total ?? 0m;
}

// CORRECTO: la dependencia se recibe por constructor
public class OrderService(IOrderRepository repository)
{
    public decimal CalculateTotal(int orderId)
    {
        var order = repository.GetById(orderId);
        return order?.Total ?? 0m;
    }
}

Error 3: Usar Service Locator para ocultar dependencias

// INCORRECTO: no se ve qué depende la clase
public class OrderService
{
    public decimal CalculateTotal(int orderId)
    {
        var repository = ServiceLocator.Get<IOrderRepository>();
        var order = repository.GetById(orderId);
        return order?.Total ?? 0m;
    }
}

Error 4: Programar contra clases estáticas

// INCORRECTO: estático = imposible de mockear, acoplamiento global
public static class OrderRepository
{
    public static Order? GetById(int id) { /* ... */ }
}

// CORRECTO: interfaz + inyección por constructor
public class OrderService(IOrderRepository repository) { /* ... */ }

7 · Ejercicio guiado

Crea una aplicación de consola .NET 8 que calcule el precio de un producto aplicando impuestos. Sigue estos pasos:

  1. Crea una interfaz ITaxCalculator con un método decimal CalculateTax(decimal amount).
  2. Crea dos implementaciones: StandardTaxCalculator (21%) y ReducedTaxCalculator (10%).
  3. Crea ProductPriceService que reciba ITaxCalculator por constructor y calcule el precio final.
  4. En Program.cs usa Poor Man's DI para crear el servicio y muestra el precio final.
// ITaxCalculator.cs
public interface ITaxCalculator
{
    decimal CalculateTax(decimal amount);
}

public class StandardTaxCalculator : ITaxCalculator
{
    public decimal CalculateTax(decimal amount) => amount * 0.21m;
}

public class ProductPriceService(ITaxCalculator taxCalculator)
{
    public decimal GetFinalPrice(decimal basePrice)
    {
        var tax = taxCalculator.CalculateTax(basePrice);
        return basePrice + tax;
    }
}

// Program.cs
var taxCalculator = new StandardTaxCalculator();
var service = new ProductPriceService(taxCalculator);

var finalPrice = service.GetFinalPrice(100m);
Console.WriteLine($"Precio final: {finalPrice:C}"); // 121,00 €
Extra: cambia a ReducedTaxCalculator sin modificar ProductPriceService. ¿Cómo se siente el cambio? Eso es el principio Open/Closed en acción.

9 · Resumen

  • DI es un principio de diseño: las dependencias se proporcionan desde fuera, no se crean dentro.
  • IoC invierte el control de la creación de objetos al runtime o a un compositor.
  • La inyección por constructor es la forma preferida porque documenta y obliga a las dependencias.
  • Programar contra abstracciones (interfaces) permite sustituir implementaciones sin cambiar el consumidor.
  • Poor Man's DI es la composición manual: útil para aprender y para aplicaciones pequeñas.
  • El contenedor DI de .NET automatiza la composición a partir de un catálogo de servicios registrados.
  • Evita new interno, static y Service Locator para mantener el código desacoplado y testable.

10 · Preguntas frecuentes

¿DI es lo mismo que IoC?

No exactamente. IoC es un principio más amplio: invertir el control de la ejecución o la creación. DI es una forma específica de IoC donde las dependencias se inyectan desde fuera. Otra forma de IoC sería el patrón Template Method o los eventos.

¿Por qué constructor injection y no setter injection?

La inyección por constructor obliga a que la dependencia exista antes de crear el objeto. Con setter injection la dependencia es opcional y el objeto puede quedar en un estado inválido. Además, constructor injection hace las dependencias explícitas y evita sorpresas.

¿Siempre debo usar interfaces?

No siempre. Para clases simples, utilidades o DTOs que no cambian, una dependencia concreta puede ser suficiente. La regla práctica es: usa interfaces cuando haya más de una implementación, cuando quieras testar con mocks, o cuando esperes cambiar la implementación en el futuro.

¿Cómo se relaciona DI con SOLID?

DI es la puerta de entrada al DIP (Dependency Inversion Principle). DIP dice que los módulos de alto nivel no deben depender de los de bajo nivel, sino de abstracciones. DI es la técnica que hace cumplir ese principio inyectando abstracciones.

¿Es DI un patrón de diseño o una librería?

DI es un patrón de diseño. El contenedor de .NET (también llamado IoC container) es una librería/framework que automatiza el patrón. Puedes hacer DI sin un contenedor, como demostramos con Poor Man's DI.
