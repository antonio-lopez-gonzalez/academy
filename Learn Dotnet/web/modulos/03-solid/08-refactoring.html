Refactoring aplicando SOLID

Módulo 3 · SOLID en C# 50 minutos

1 · Introducción

Pongamos en práctica todo lo aprendido: partiremos de una clase problemática y la transformaremos paso a paso, aplicando SRP, OCP, LSP, ISP, DIP, composición y Dependency Injection.

Objetivo

Refactorizar una god class en un diseño desacoplado y cohesivo.

2 · Teoría

La clase problemática

OrderService ├── valida pedido ├── calcula precio ├── aplica descuentos ├── guarda en SQL Server ├── genera factura ├── envía email └── registra logs
// Incorrecto: una god class acoplada a todo
class OrderService
{
    private readonly SqlServerOrderRepository _repo = new();

    public void Procesar(Order order)
    {
        // Valida (SRP roto)
        if (order.Items.Count == 0) throw new ArgumentException("Pedido vacío");

        // Calcula precio y descuentos (SRP + OCP rotos)
        decimal total = 0;
        foreach (var item in order.Items) total += item.Precio;
        if (order.EsVip) total *= 0.8m;
        else if (order.EsCliente) total *= 0.95m;

        order.Total = total;

        // Guarda en SQL Server (DIP roto)
        _repo.Guardar(order);

        // Genera factura, envía email y loggea (SRP roto)
        var factura = "Factura de " + order.Id;
        Console.WriteLine($"Enviando: {factura}");     // email simulado
        Console.WriteLine($"[LOG] Pedido {order.Id} procesado");
    }
}

El diseño objetivo

OrderService │ ├── IOrderRepository ├── IDiscountStrategy ├── IInvoiceGenerator ├── IEmailService └── ILogger

Paso 1: extraer abstracciones (DIP)

interface IOrderRepository { void Guardar(Order order); }
interface IInvoiceGenerator { string Generar(Order order); }
interface IEmailService { void Enviar(string destino, string mensaje); }
interface ILogger { void Log(string mensaje); }

// OCP: los descuentos como estrategias
interface IDiscountStrategy { decimal Apply(decimal total); }

class VipDiscount : IDiscountStrategy { public decimal Apply(decimal t) => t * 0.8m; }
class ClientDiscount : IDiscountStrategy { public decimal Apply(decimal t) => t * 0.95m; }
class NoDiscount : IDiscountStrategy { public decimal Apply(decimal t) => t; }

Paso 2: extraer la validación (SRP)

class OrderValidator
{
    public void Validar(Order order)
    {
        if (order.Items.Count == 0)
            throw new ArgumentException("Pedido vacío");
    }
}

Paso 3: componer el servicio orquestador

class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IInvoiceGenerator _invoice;
    private readonly IEmailService _email;
    private readonly ILogger _logger;
    private readonly OrderValidator _validator;

    // DIP + Constructor Injection: dependencias explícitas por constructor
    public OrderService(
        IOrderRepository repository,
        IInvoiceGenerator invoice,
        IEmailService email,
        ILogger logger,
        OrderValidator validator)
    {
        _repository = repository;
        _invoice = invoice;
        _email = email;
        _logger = logger;
        _validator = validator;
    }

    public void Procesar(Order order, IDiscountStrategy descuento)   // OCP: la estrategia llega de fuera
    {
        _validator.Validar(order);                       // SRP
        order.Total = descuento.Apply(order.CalcularTotal());  // OCP
        _repository.Guardar(order);                      // DIP
        string factura = _invoice.Generar(order);
        _email.Enviar(order.Cliente.Email, factura);
        _logger.Log($"Pedido {order.Id} procesado");
    }
}

// Distintos descuentos sin modificar OrderService (OCP)

9 · Resumen

  • Identifica las responsabilidades y extráelas (SRP).
  • Abstrae lo que varía (OCP + DIP).
  • Inyecta dependencias por constructor (DI).
  • El orquestador coordina; los colaboradores ejecutan.

10 · Preguntas frecuentes

¿Cuánto debería durar un refactor?

En pasos pequeños y continuos (como deuda técnica). Refactoriza siempre que añadas funcionalidad a código con code smells.

¿Cómo sé que el refactor no cambió el comportamiento?

Con tests: si tienes pruebas que cubren el comportamiento, un refactor correcto las mantiene en verde.

¿El orquestador viola SRP?

No: su única responsabilidad es coordinar el flujo. Los detalles concretos viven en los colaboradores.
