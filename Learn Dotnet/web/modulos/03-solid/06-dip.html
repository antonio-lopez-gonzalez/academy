D — Dependency Inversion Principle

Módulo 3 · SOLID en C# 45 minutos

1 · Introducción

Es el principio que conecta SOLID con la Inyección de Dependencias del .NET profesional. Dice: los módulos de alto nivel no deben depender de módulos de bajo nivel; ambos deben depender de abstracciones.

Objetivo

Invertir dependencias hacia abstracciones y distinguir DIP de Dependency Injection.

2 · Teoría

El problema: dependencias rígidas

// Incorrecto: PedidoService depende directamente de la implementación concreta
class PedidoService
{
    private readonly SqlServerRepository _repository = new SqlServerRepository();
    // ↑ acoplado a SQL Server: difícil de cambiar o testear
}

Aquí el módulo de alto nivel (PedidoService) depende de un detalle de bajo nivel (SqlServerRepository).

La solución: depender de abstracciones

// La abstracción (contrato)
interface IPedidoRepository
{
    void Guardar(Pedido pedido);
}

// El módulo de alto nivel depende de la abstracción
class PedidoService
{
    private readonly IPedidoRepository _repository;

    public PedidoService(IPedidoRepository repository)
    {
        _repository = repository;
    }
}

Ahora PedidoService no sabe ni le importa si guarda en SQL Server, MySQL o memoria. Depende del contrato, no del detalle.

Dependency Inversion vs Dependency Injection

  • DIP (principio): "depende de abstracciones, no de concreciones". Es la idea de diseño.
  • DI (técnica): suministrar las dependencias desde fuera (por constructor) en vez de crearlas dentro. Es la forma de aplicar DIP.
No confundir

DIP es el "qué" (principio); DI es el "cómo" (técnica). El patrón más común es la Constructor Injection: recibir las dependencias en el constructor.

Constructor Injection

class PedidoService
{
    private readonly IPedidoRepository _repository;

    // Constructor Injection: las dependencias llegan por el constructor
    public PedidoService(IPedidoRepository repository)
    {
        _repository = repository;
    }
}

IoC y Service Locator

  • IoC (Inversion of Control): el principio general de ceder el control de la creación de objetos a un contenedor.
  • Service Locator: un registro global del que se piden dependencias. Funciona, pero es un anti-patrón por ocultar las dependencias.
Service Locator: problemas

Oculta las dependencias (no se ven en la firma), acopla todo al localizador y dificulta las pruebas. Prefiere siempre Constructor Injection.

3 · Ejemplo mínimo

// Evitar
class Servicio { private readonly SqlRepository _r = new(); }

// Preferir
class Servicio
{
    private readonly IRepository _r;
    public Servicio(IRepository r) => _r = r;
}

4 · Ejemplo real

Un servicio que envía notificaciones, desacoplado del proveedor concreto:

interface INotificador
{
    void Enviar(string destinatario, string mensaje);
}

class NotificadorEmail : INotificador
{
    public void Enviar(string destino, string mensaje) =>
        Console.WriteLine($"Email a {destino}: {mensaje}");
}

class NotificadorSms : INotificador
{
    public void Enviar(string destino, string mensaje) =>
        Console.WriteLine($"SMS a {destino}: {mensaje}");
}

// El consumidor depende de la abstracción
class ServicioPedidos
{
    private readonly INotificador _notificador;

    public ServicioPedidos(INotificador notificador) => _notificador = notificador;

    public void Avisar(string cliente)
    {
        _notificador.Enviar(cliente, "Tu pedido está listo");
    }
}

// El día de mañana cambias Email por Sms sin tocar ServicioPedidos
var servicio = new ServicioPedidos(new NotificadorSms());
servicio.Avisar("ana@mail.com");

9 · Resumen

  • DIP: depende de abstracciones, no de concreciones.
  • DI (constructor injection) es la técnica para aplicarlo.
  • IoC es el principio general de ceder el control.
  • Evita Service Locator.

10 · Preguntas frecuentes

¿Qué es Constructor Injection?

Pasar las dependencias de una clase a través de su constructor, en lugar de crearlas dentro. Es la forma más común y recomendada de DI.

¿Por qué Service Locator es un anti-patrón?

Porque oculta las dependencias (no se ven en la firma), acopla el código a un registro global y dificulta las pruebas unitarias.

¿DIP es lo mismo que IoC?

No. DIP es un principio específico sobre dependencias. IoC es un concepto más amplio: ceder el control del flujo/creación a un framework o contenedor.
