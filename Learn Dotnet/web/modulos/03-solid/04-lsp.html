L — Liskov Substitution Principle

Módulo 3 · SOLID en C# 45 minutos

1 · Introducción

Formulado por Barbara Liskov: una clase derivada debe poder sustituir a su clase base sin romper el comportamiento esperado. Si heredas, la derivada debe comportarse como su base en todos los contextos donde se use la base.

Objetivo

Detectar jerarquías de herencia incorrectas y entender los contratos (pre/post condiciones e invariantes).

2 · Teoría

Sustituibilidad

Si un código funciona con una Base, debe funcionar igual con cualquier Derivada. Cuando la derivada se comporta de forma distinta e inesperada, se viola LSP.

Contratos

  • Precondiciones: lo que debe cumplirse antes de llamar. La derivada no debe endurecerlas.
  • Postcondiciones: lo que se garantiza después. La derivada no debe debilitarlas.
  • Invariantes: propiedades que siempre deben ser ciertas.

El problema clásico: Square / Rectangle

En geometría, un cuadrado "es un" rectángulo. Pero modelarlo por herencia rompe LSP:

class Rectangle
{
    public virtual double Ancho { get; set; }
    public virtual double Alto { get; set; }

    public double Area() => Ancho * Alto;
}

class Square : Rectangle
{
    public override double Ancho
    {
        set { base.Ancho = value; base.Alto = value; }   // fuerzo igualdad
    }

    public override double Alto
    {
        set { base.Ancho = value; base.Alto = value; }
    }
}
// Código que funciona con Rectangle falla con Square:
void Redimensionar(Rectangle r)
{
    r.Ancho = 5;
    r.Alto = 10;
    Console.WriteLine(r.Area());   // Rectangle: 50. Square: ¡100! (inesperado)
}

Redimensionar(new Rectangle());   // 50
Redimensionar(new Square());      // 100 (viola la expectativa)
¿Qué pasó?

El Square no cumple el contrato del Rectangle (ancho y alto independientes). Al sustituirlo, rompe el comportamiento esperado. La herencia era incorrecta.

Excepciones inesperadas

Otra violación típica: la derivada lanza excepciones que la base no lanza, o deja métodos sin implementar correctamente.

class Ave
{
    public virtual void Volar() => Console.WriteLine("Volando");
}

class Pinguino : Ave
{
    public override void Volar() => throw new NotSupportedException("¡No puedo volar!");
    // Violación: un Pinguino no puede sustituir a un Ave sin romper el contrato
}

Cuándo NO usar herencia

Si la relación "es un" no es sólida o la derivada no puede cumplir el contrato, no heredes. Usa composición.

3 · Ejemplo mínimo

class Ave
{
    public virtual void Volar() => Console.WriteLine("Volando");
}
class Pinguino : Ave
{
    // public override void Volar() => throw new NotSupportedException();
    // ↑ viola LSP: no sustituye correctamente a Ave
}

4 · Ejemplo real

Rediseñar la jerarquía de aves para cumplir LSP, separando lo que vuela de lo que no:

interface IVolador
{
    void Volar();
}

class Aguila : IVolador
{
    public void Volar() => Console.WriteLine("Volando alto");
}

class Pinguino
{
    // no implementa IVolador: no puede volar
    public void Nadar() => Console.WriteLine("Nadando");
}

// Ahora cada tipo cumple su contrato sin excepciones inesperadas

9 · Resumen

  • LSP: la derivada debe sustituir a su base sin romper el comportamiento.
  • Contratos: precondiciones, postcondiciones e invariantes.
  • Square/Rectangle es el ejemplo clásico de herencia incorrecta.
  • Si no hay sustituibilidad, usa composición/interfaces.

10 · Preguntas frecuentes

¿Por qué Square/Rectangle viola LSP?

Porque Square fuerza ancho = alto, cambiando el comportamiento esperado de Rectangle (donde ancho y alto son independientes). Un código que usa Rectangle se rompe al recibir un Square.

¿Qué es una precondición?

Una condición que debe cumplirse antes de invocar un método. La derivada no debe exigir más que la base (endurecerla) porque rompería a los clientes.

¿LSP se aplica solo a herencia?

Principalmente, pero la idea de sustituibilidad también aplica a interfaces y a cualquier contrato entre tipos.
