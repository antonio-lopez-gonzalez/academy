Proyecto final de POO + SOLID

1 · Introducción

Es el momento de integrar todo: diseña un sistema de pedidos completo aplicando POO y SOLID. Aquí no hay código a copiar: hay un diseño que debes construir tú, justificando cada decisión.

Objetivo

Diseñar una aplicación con clases, encapsulación, composición, interfaces, polimorfismo y SOLID.

2 · Especificación

Entidades del dominio

La aplicación gestiona:

  • Clientes
  • Productos
  • Pedidos
  • Líneas de pedido
  • Pagos
  • Facturas
  • Notificaciones

Modelo inicial

Orders ├── Order ├── OrderItem ├── Customer └── Product
class Customer
{
    public string Nombre { get; set; } = "";
    public string Email { get; set; } = "";
}

class Product
{
    public string Nombre { get; set; } = "";
    public decimal Precio { get; set; }
}

class OrderItem
{
    public Product Producto { get; set; } = new();
    public int Cantidad { get; set; }
    public decimal Subtotal => Producto.Precio * Cantidad;
}

class Order
{
    public Customer Cliente { get; set; } = new();
    public List<OrderItem> Items { get; set; } = new();
    public decimal Total { get; private set; }

    public decimal CalcularTotal()
    {
        Total = Items.Sum(i => i.Subtotal);
        return Total;
    }
}

Abstracciones (contratos)

interface IOrderRepository { void Guardar(Order order); }
interface IProductRepository { Product? Buscar(int id); }
interface IPaymentService { bool Procesar(Order order); }
interface IEmailService { void Enviar(string destino, string mensaje); }
interface IInvoiceGenerator { string Generar(Order order); }
interface IDiscountStrategy { decimal Apply(decimal total); }

Servicios

class OrderService { /* orquesta la creación de pedidos */ }
class PaymentService : IPaymentService { /* procesa pagos */ }
class EmailService : IEmailService { /* envía notificaciones */ }
class InvoiceService : IInvoiceGenerator { /* genera facturas */ }
class DiscountService { /* calcula descuentos (estrategias) */ }

Qué aplicar

  • Crear clases y encapsular el estado.
  • Utilizar composición e interfaces.
  • Utilizar polimorfismo (ej. distintos métodos de pago).
  • Aplicar SRP, OCP, LSP, ISP y DIP.
  • Evitar clases gigantes y acoplamiento.
  • Utilizar Dependency Injection.
  • Diseñar código extensible.

4 · Criterios de evaluación

  • SRP: ¿cada clase tiene una sola responsabilidad?
  • OCP: ¿puedes añadir un nuevo tipo de pago o descuento sin modificar lo existente?
  • LSP: ¿las implementaciones de IPaymentService sustituyen correctamente?
  • ISP: ¿las interfaces son pequeñas y específicas?
  • DIP: ¿los servicios dependen de abstracciones, no de concreciones?

6 · Errores habituales

Error 1: una sola clase que lo hace todo

// class Sistema { /* clientes + pedidos + pagos + ... */ }  ← god class

Error 2: dependencias new dentro de los servicios

// private readonly Repo _r = new Repo();   ← acoplamiento rígido

Error 3: interfaces gigantes

// interface ITodo { ... 15 métodos ... }   ← viola ISP

7 · Plan de trabajo

  1. Modela las entidades con encapsulación.
  2. Define las interfaces (contratos).
  3. Implementa los servicios con inyección de dependencias.
  4. Añade un sistema de descuentos extensible (OCP).
  5. Añade varios métodos de pago polimórficos.
  6. Revisa que se cumplan los cinco principios.

10 · Preguntas frecuentes

¿Por dónde empiezo?

Por el dominio (entidades) y las interfaces. Luego los servicios que las consumen, inyectando dependencias por constructor.

¿Debo usar herencia o composición?

Composición + interfaces en casi todo. Herencia solo donde haya una relación "es un" sólida y LSP se cumpla.

¿Cuál es el siguiente paso?

Con C# + .NET + POO + SOLID ya puedes entrar en el desarrollo profesional: Dependency Injection de .NET, ASP.NET Core, EF Core, testing y arquitectura.
