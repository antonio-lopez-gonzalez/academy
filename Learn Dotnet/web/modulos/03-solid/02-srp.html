S — Single Responsibility Principle

Módulo 3 · SOLID en C# 40 minutos

1 · Introducción

Es el principio más intuitivo y el que más se viola. Dice: una clase debe tener una única razón para cambiar. Cuando una clase hace demasiadas cosas, cualquier cambio la toca y se convierte en un punto frágil.

Objetivo

Detectar responsabilidades mezcladas y separarlas en clases cohesivas.

2 · Teoría

¿Qué significa "responsabilidad"?

Una responsabilidad es una razón de cambio. Si una clase tiene que cambiar por motivos de validación Y de persistencia Y de notificaciones, tiene tres responsabilidades (y tres razones para cambiar).

El ejemplo clásico: la "god class"

Una clase que lo hace todo:

User ├── valida usuario ├── guarda en BD ├── envía email ├── genera PDF └── registra logs
// Incorrecto: demasiadas responsabilidades
class User
{
    public void Validar() { /* ... */ }
    public void GuardarEnBd() { /* ... */ }
    public void EnviarEmail() { /* ... */ }
    public void GenerarPdf() { /* ... */ }
    public void RegistrarLog() { /* ... */ }
}

La solución: separar responsabilidades

UserValidator → valida usuario UserRepository → guarda en BD EmailService → envía email PdfGenerator → genera PDF Logger → registra logs
class UserValidator
{
    public void Validar(User user) { /* solo valida */ }
}

class UserRepository
{
    public void Guardar(User user) { /* solo persiste */ }
}

class EmailService
{
    public void Enviar(User user) { /* solo notifica */ }
}

class PdfGenerator
{
    public void Generar(User user) { /* solo genera PDF */ }
}

class Logger
{
    public void Log(string mensaje) { /* solo loggea */ }
}

Cohesión

Al separar, cada clase tiene alta cohesión: todo lo que contiene está relacionado con una única responsabilidad.

Cómo detectar violaciones

  • La clase tiene "y" en su descripción: "valida Y guarda Y notifica".
  • Cambiar una funcionalidad te obliga a tocar código no relacionado.
  • Métodos que usan campos de partes distintas de la clase.

3 · Ejemplo mínimo

// Antes: una clase que valida y persiste
class ProductoService
{
    public void Guardar(Producto p)
    {
        if (p.Precio < 0) throw new ArgumentException();   // validación
        // ... guardar en BD                                    // persistencia
    }
}

// Después: dos responsabilidades separadas
class ProductoValidator { public void Validar(Producto p) { /* ... */ } }
class ProductoRepository { public void Guardar(Producto p) { /* ... */ } }

4 · Ejemplo real

Un PedidoService refactorizado aplicando SRP:

// Incorrecto
class PedidoService
{
    public void Crear(Pedido pedido)
    {
        // valida
        if (pedido.Items.Count == 0) throw new ArgumentException("Pedido vacío");
        // guarda
        _db.Pedidos.Add(pedido); _db.SaveChanges();
        // notifica
        _email.Enviar(pedido.Cliente.Email, "Pedido creado");
        // loggea
        Console.WriteLine($"Pedido {pedido.Id} creado");
    }
}

// Correcto: orquesta servicios especializados
class PedidoService
{
    private readonly IValidadorPedido _validador;
    private readonly IPedidoRepository _repositorio;
    private readonly INotificador _notificador;

    public PedidoService(IValidadorPedido v, IPedidoRepository r, INotificador n)
    {
        _validador = v; _repositorio = r; _notificador = n;
    }

    public void Crear(Pedido pedido)
    {
        _validador.Validar(pedido);
        _repositorio.Guardar(pedido);
        _notificador.Notificar(pedido.Cliente, "Pedido creado");
    }
}

9 · Resumen

  • SRP: una clase, una única razón de cambio.
  • Responsabilidad = razón de cambio.
  • Separar en clases cohesivas y especializadas.
  • Detecta "god classes" y métodos demasiado grandes.

10 · Preguntas frecuentes

¿Qué es una "god class"?

Una clase que concentra demasiadas responsabilidades no relacionadas. Es el anti-patrón por excelencia de SRP.

¿Cómo sé si violo SRP?

Si al explicar qué hace la clase dices "hace esto Y esto Y esto", o si un cambio en una funcionalidad te obliga a tocar código de otra.

¿SRP se aplica solo a clases?

No. También a métodos, módulos y funciones: cada uno debería tener una única responsabilidad.
