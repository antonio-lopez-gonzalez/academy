I — Interface Segregation Principle

Módulo 3 · SOLID en C# 35 minutos

1 · Introducción

Dice: los clientes no deberían depender de métodos que no usan. Una interfaz enorme obliga a las clases a implementar cosas que no necesitan, creando acoplamiento y código muerto.

Objetivo

Detectar interfaces demasiado grandes y dividirlas en interfaces pequeñas y cohesivas.

2 · Teoría

El problema: una interfaz gigante

// Incorrecto: una interfaz que mezcla responsabilidades
interface IWorker
{
    void Work();
    void Eat();
    void Sleep();
    void Drive();
}

// Un robot debe "implementar" Eat() y Sleep() aunque no los necesite
class Robot : IWorker
{
    public void Work() { /* ... */ }
    public void Eat() { throw new NotSupportedException(); }   // no tiene sentido
    public void Sleep() { throw new NotSupportedException(); }
    public void Drive() { /* ... */ }
}

El robot depende de métodos que no usa, y los implementa lanzando excepciones. Mal diseño.

La solución: interfaces pequeñas

interface IWork { void Work(); }
interface IEat { void Eat(); }
interface ISleep { void Sleep(); }
interface IDrive { void Drive(); }

// Cada clase implementa solo lo que necesita
class Robot : IWork, IDrive
{
    public void Work() { /* ... */ }
    public void Drive() { /* ... */ }
}

class Humano : IWork, IEat, ISleep
{
    public void Work() { /* ... */ }
    public void Eat() { /* ... */ }
    public void Sleep() { /* ... */ }
}
IWorker (gigante) │ ▼ IWork · IEat · ISleep · IDrive ← pequeñas y cohesivas

Interfaces orientadas al cliente

Cada interfaz debe reflejar lo que un cliente concreto necesita, no todo lo que una clase puede hacer.

Cohesión de interfaces

Una interfaz cohesiva agrupa métodos relacionados. Si ves métodos que no tienen relación entre sí, es señal de que deberías dividirla.

ISP vs interfaces genéricas

ISP no significa "una interfaz por método". Busca el equilibrio: interfaces coherentes que agrupen métodos relacionados, evitando las omnipotentes.

3 · Ejemplo mínimo

// Antes
interface IMultifuncion { void Imprimir(); void Escanear(); void EnviarFax(); }

// Después
interface IPrinter { void Imprimir(); }
interface IScanner { void Escanear(); }
interface IFax { void EnviarFax(); }

4 · Ejemplo real

Separar un contrato de repositorio para que cada cliente dependa solo de lo que usa:

// Incorrecto: una interfaz con operaciones de lectura Y escritura
interface IRepositorio
{
    Producto Buscar(int id);
    void Guardar(Producto p);
    void Eliminar(int id);
    IEnumerable<Producto> Listar();
}

// Correcto: separar por capacidad
interface IRepositorioLectura<T>
{
    T? Buscar(int id);
    IEnumerable<T> Listar();
}

interface IRepositorioEscritura<T>
{
    void Guardar(T entidad);
    void Eliminar(int id);
}

Así, una vista de solo lectura no se ve obligada a implementar escritura.

8 · Reto

Reto

Diseña las interfaces de un sistema de pagos donde hay métodos de tarjeta, PayPal y transferencia. Asegúrate de que cada proveedor implementa solo lo que necesita (ningún NotSupportedException).

9 · Resumen

  • ISP: no depender de métodos que no se usan.
  • Divide interfaces grandes en pequeñas y cohesivas.
  • Diseña desde la perspectiva del cliente.
  • Evita implementaciones con NotSupportedException.

10 · Preguntas frecuentes

¿Cuántos métodos debe tener una interfaz?

No hay número mágico. La clave es la cohesión: los métodos deben estar relacionados. Si algunos sobran para algunos clientes, divídela.

¿ISP y SRP son lo mismo?

Están relacionados pero no son idénticos. SRP habla de la clase; ISP, de la interfaz. Una interfaz con métodos incoherentes suele reflejar una clase con múltiples responsabilidades.

¿Qué es una interfaz orientada al cliente?

Una interfaz diseñada pensando en las necesidades concretas de quien la consume, en lugar de agrupar todo lo que una clase puede hacer.
