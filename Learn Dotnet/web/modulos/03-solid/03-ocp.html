O — Open/Closed Principle

Módulo 3 · SOLID en C# 40 minutos

1 · Introducción

Dice: las entidades deben estar abiertas a la extensión, pero cerradas a la modificación. En otras palabras: deberías poder añadir nuevas funcionalidades sin tocar el código existente.

Objetivo

Detectar el problema de los if/switch crecientes y extender comportamiento con polimorfismo.

2 · Teoría

El problema: if/else y switch crecientes

Cada vez que añades un caso, debes modificar el método existente. Con el tiempo se vuelve un monstruo:

// Incorrecto: cada tipo nuevo obliga a MODIFICAR esta clase
class GeneradorDocumentos
{
    public void Generar(string tipo, string contenido)
    {
        if (tipo == "PDF")
        {
            // genera PDF
        }
        else if (tipo == "Excel")
        {
            // genera Excel
        }
        else if (tipo == "Word")
        {
            // genera Word
        }
        // ... cada formato nuevo = modificar aquí
    }
}

La solución: polimorfismo + interfaces

Defines una abstracción y cada variante es una implementación nueva. Añadir un formato = crear una clase, sin tocar las demás:

interface IDocumentGenerator
{
    void Generar(string contenido);
}

class PdfGenerator : IDocumentGenerator
{
    public void Generar(string contenido) => Console.WriteLine($"PDF: {contenido}");
}

class ExcelGenerator : IDocumentGenerator
{
    public void Generar(string contenido) => Console.WriteLine($"Excel: {contenido}");
}

class WordGenerator : IDocumentGenerator
{
    public void Generar(string contenido) => Console.WriteLine($"Word: {contenido}");
}
IDocumentGenerator ├── PdfGenerator ├── ExcelGenerator └── WordGenerator ← añadir uno nuevo NO modifica el resto
// El código cliente no cambia al añadir formatos
void GenerarDocumento(IDocumentGenerator generator, string contenido)
{
    generator.Generar(contenido);
}

GenerarDocumento(new PdfGenerator(), "mi informe");
GenerarDocumento(new ExcelGenerator(), "datos");

Strategy Pattern

Este diseño es el Strategy Pattern: encapsulas un comportamiento intercambiable detrás de una interfaz. Es la aplicación práctica del OCP.

OCP mediante composición

En lugar de heredar para especializar, compones. Combinar OCP con composición da diseños muy flexibles.

3 · Ejemplo mínimo

interface IDescuento { decimal Aplicar(decimal precio); }

class SinDescuento : IDescuento { public decimal Aplicar(decimal p) => p; }
class Descuento10 : IDescuento { public decimal Aplicar(decimal p) => p * 0.9m; }

4 · Ejemplo real

Un sistema de descuentos que se puede extender sin modificar el código existente:

interface IDiscountStrategy
{
    decimal Apply(decimal precio);
}

class RegularDiscount : IDiscountStrategy
{
    public decimal Apply(decimal p) => p * 0.95m;   // 5% de descuento
}

class VipDiscount : IDiscountStrategy
{
    public decimal Apply(decimal p) => p * 0.80m;   // 20% de descuento
}

class CalculadoraPrecios
{
    public decimal Calcular(decimal precio, IDiscountStrategy strategy)
    {
        return strategy.Apply(precio);
    }
}

var calc = new CalculadoraPrecios();
Console.WriteLine(calc.Calcular(100, new RegularDiscount()));   // 95
Console.WriteLine(calc.Calcular(100, new VipDiscount()));       // 80

6 · Errores habituales

Error 1: switch de tipos para extender

// Cada tipo nuevo = modificar el switch (viola OCP)

Error 2: abstraer absolutamente todo

// No crees interfaces para cosas que nunca cambiarán. YAGNI.

Error 3: violar OCP por miedo a "complicar"

// Un if/else pequeño hoy se vuelve un monstruo mañana. Abstrae lo que varía.

Reto

9 · Resumen

  • OCP: abierto a extensión, cerrado a modificación.
  • Los if/switch crecientes violan OCP.
  • Soluciones: polimorfismo, interfaces y Strategy Pattern.
  • Extiende creando clases, no editando las existentes.

10 · Preguntas frecuentes

¿Qué es el Strategy Pattern?

Un patrón que encapsula algoritmos intercambiables detrás de una interfaz común, permitiendo elegir la estrategia en tiempo de ejecución.

¿OCP es siempre posible al 100%?

No. Es un ideal. Busca minimizar las modificaciones del código existente al añadir funcionalidad, no eliminarlas siempre.

¿Cómo sé si debo abstraer algo?

Si ya has modificado un if/switch dos veces para añadir casos, es señal de que deberías abstraerlo con polimorfismo.
