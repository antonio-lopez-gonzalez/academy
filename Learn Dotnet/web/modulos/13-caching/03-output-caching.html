Output Caching y Response Caching

Módulo 13 · Caching y rendimiento30 min

1 · Introducción

En las lecciones anteriores vimos cómo cachear datos internos con IMemoryCache y IDistributedCache. Ahora veremos cómo cachear respuestas HTTP completas: el middleware de Output Caching de .NET 8 y el más antiguo Response Caching. Esto evita que ASP.NET Core ejecute endpoints de lectura costosos una y otra vez para la misma petición.

Veremos las diferencias, cuándo usar cada uno, cómo configurar políticas, variar el caché por query string, headers o clave personalizada, y cómo devolver 304 Not Modified con ETags.

Output Caching vs Response Caching: Output Caching es el middleware moderno de .NET 7+. Permite políticas, almacenamiento en Redis, invalidación por tags y variación por clave personalizada. Response Caching es el antiguo atributo [ResponseCache] basado en cabeceras HTTP (Cache-Control), más limitado y pensado para caché en navegadores o proxies.

Al terminar sabrás aplicar Output Caching en Minimal APIs y controllers, configurar cache profiles y añadir soporte para If-None-Match.

2 · Teoría

2.1 Response Caching

Se activa con el atributo [ResponseCache] y el middleware app.UseResponseCaching(). No almacena respuestas en el servidor, sino que añade cabeceras HTTP (Cache-Control, Pragma, Vary) para que navegadores, proxies y CDNs decidan si cachean.

Es útil para:

  • APIs públicas de lectura con datos que cambian poco.
  • Activar caché en el cliente o en un CDN.
  • Compatibilidad con aplicaciones antiguas.

Limitaciones:

  • No permite almacenamiento en el servidor.
  • No soporta variación por usuario autenticado.
  • La configuración está dispersa en atributos.

2.2 Output Caching

Output Caching almacena la respuesta generada en el servidor (memoria, Redis o almacenamiento personalizado) y la devuelve directamente para peticiones futuras. Se activa con builder.Services.AddOutputCache() y app.UseOutputCache().

Ventajas:

  • Políticas centralizadas: builder.Services.AddOutputCache(options => { options.AddPolicy(...); }).
  • Variación por ruta, query, headers, autenticación y clave personalizada.
  • Almacenamiento en Redis para múltiples instancias.
  • Tags para invalidación por grupo.
  • Ignora peticiones con cuerpo, métodos no idempotentes o que no devuelven 200 OK.

2.3 ETags y 304 Not Modified

Un ETag es una firma de la respuesta (normalmente un hash). El cliente envía If-None-Match con el ETag que ya tiene. Si el servidor decide que la respuesta no ha cambiado, devuelve 304 Not Modified sin cuerpo, ahorrando ancho de banda.

Output Caching no genera ETags automáticamente, pero puedes combinarlo con HttpResponse.Headers.ETag y lógica personalizada.

2.4 Cache profiles

Los cache profiles permiten definir configuraciones con nombre y aplicarlas por endpoint o controller. Son útiles para mantener tiempos y reglas consistentes en toda la API.

3 · Ejemplo mínimo

Creamos una Minimal API con Output Caching.

dotnet new web -n OutputCacheDemo -o ejemplos/m13-caching/OutputCacheDemo/src/OutputCacheDemo
dotnet add ejemplos/m13-caching/OutputCacheDemo/src/OutputCacheDemo package Microsoft.AspNetCore.OutputCaching
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("Long", policy =>
        policy.Expire(TimeSpan.FromMinutes(5)));

    options.AddPolicy("Short", policy =>
        policy.Expire(TimeSpan.FromSeconds(30)));
});

var app = builder.Build();

app.UseOutputCache();

app.MapGet("/time", () => Results.Ok(DateTime.UtcNow.ToString("O")))
   .CacheOutput("Short");

app.MapGet("/weather/{city}", (string city) =>
    Results.Ok(new { City = city, Temperature = 22.5m, Time = DateTime.UtcNow }))
   .CacheOutput(policy =>
   {
       policy.Expire(TimeSpan.FromMinutes(1));
       policy.VaryByQuery("unit"); // distinto caché para ?unit=c y ?unit=f
   });

app.Run();

Prueba:

curl http://localhost:5000/time
curl http://localhost:5000/weather/Madrid?unit=c
curl http://localhost:5000/weather/Madrid?unit=f

Verás que /time devuelve el mismo valor durante 30 segundos, mientras que /weather/Madrid tiene entradas separadas para cada unit.

Tip: el orden de middleware importa. UseOutputCache() debe ir después de UseRouting() y antes de UseEndpoints() (o simplemente después de UseRouting() en Minimal APIs).

4 · Ejemplo real

En el CMS queremos cachear la lista pública de posts publicados y la respuesta de categorías, pero no los endpoints de administración.

using Microsoft.AspNetCore.OutputCaching;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOutputCache(options =>
{
    options.AddBasePolicy(policy =>
        policy.NoCache()); // por defecto, no cachear

    options.AddPolicy("PublicPosts", policy =>
    {
        policy.Expire(TimeSpan.FromMinutes(2));
        policy.VaryByQuery("page", "pageSize");
        policy.VaryByRouteValue("slug");
        policy.Tag("posts");
    });

    options.AddPolicy("PublicCategories", policy =>
    {
        policy.Expire(TimeSpan.FromMinutes(10));
        policy.Tag("categories");
    });
});

builder.Services.AddStackExchangeRedisOutputCache(options =>
{
    options.Configuration = "localhost:6379";
    options.InstanceName = "CmsOutput_";
});

var app = builder.Build();

app.UseOutputCache();

app.MapGet("/api/v1/posts", async (IPostService posts, int page, int pageSize, CancellationToken ct) =>
{
    var result = await posts.GetPublishedAsync(page, pageSize, ct);
    return Results.Ok(result);
}).CacheOutput("PublicPosts");

app.MapGet("/api/v1/posts/{slug}", async (string slug, IPostService posts, CancellationToken ct) =>
{
    var post = await posts.GetBySlugAsync(slug, ct);
    return post is null ? Results.NotFound() : Results.Ok(post);
}).CacheOutput("PublicPosts");

app.MapGet("/api/v1/categories", async (ICategoryService categories, CancellationToken ct) =>
{
    var result = await categories.GetAllAsync(ct);
    return Results.Ok(result);
}).CacheOutput("PublicCategories");

// Endpoint de administración: sin caché por la política base.
app.MapPost("/api/v1/posts", async (CreatePostRequest request, IPostService posts, CancellationToken ct) =>
{
    var id = await posts.CreateAsync(request, ct);

    // Invalidamos el caché de posts públicos tras crear uno nuevo.
    var outputCache = app.Services.GetRequiredService<IOutputCacheStore>();
    await outputCache.EvictByTagAsync("posts", ct);

    return Results.Created($"/api/v1/posts/{id}", id);
});

app.Run();

Observa:

  • La política base NoCache() obliga a activar el caché explícitamente por endpoint.
  • VaryByQuery y VaryByRouteValue crean entradas separadas según parámetros.
  • Tag permite invalidar grupos de respuestas con EvictByTagAsync.
  • Redis almacena las respuestas, por lo que todas las instancias del CMS comparten el mismo caché de salida.
Variación por usuario: Output Caching no cachea respuestas con autenticación por defecto, para evitar filtrar datos de un usuario a otro. Si necesitas variación por usuario, usa VaryByValue con el identificador del usuario o reconsidera el diseño de seguridad.

5 · Buenas prácticas

  • Prefiere Output Caching sobre Response Caching: es más flexible, permite almacenamiento en servidor y políticas nombradas.
  • Define una política base segura: NoCache() o tiempos muy cortos, y activa el caché explícitamente.
  • Usa tags para invalidación: agrupa respuestas por dominio (posts, categories, users) y evítalas tras mutaciones.
  • Varía correctamente: incluye query strings, headers o valores que afectan a la respuesta. Si olvidas una variación, distintos usuarios pueden recibir la misma respuesta.
  • No cachees métodos mutadores: Output Caching ignora POST, PUT, DELETE por defecto, pero verifica que no añadas manualmente políticas de salida a endpoints de escritura.
  • Considera Redis para producción: con varias instancias, el caché de salida en memoria daría respuestas distintas por servidor.
  • Monitoriza hit rate: muchos misses indican variación excesiva o TTL demasiado corto.
  • Combina con ETag: para reducir ancho de banda, añade ETag y lógica de 304 además de Output Caching.

6 · Errores habituales

6.1 Aplicar Output Caching a endpoints autenticados

// ❌ Mal: datos personales podrían compartirse entre usuarios
app.MapGet("/api/v1/me", [Authorize] (ClaimsPrincipal user) =>
    Results.Ok(user.Identity!.Name))
   .CacheOutput("Long");

// ✅ Bien: no cachear o variar por identificador de usuario
app.MapGet("/api/v1/me", [Authorize] (ClaimsPrincipal user) =>
    Results.Ok(user.Identity!.Name))
   .CacheOutput(policy =>
   {
       policy.VaryByValue(ctx =>
           new KeyValuePair<string, string>("user", ctx.User.Identity!.Name!));
   });

6.2 Olvidar invalidar el caché

// ❌ Mal: los lectores nunca ven el nuevo post
app.MapPost("/api/v1/posts", async (CreatePostRequest r, IPostService s, CancellationToken ct) =>
{
    var id = await s.CreateAsync(r, ct);
    return Results.Created($"/api/v1/posts/{id}", id);
});

// ✅ Bien: invalidar las tags afectadas
app.MapPost("/api/v1/posts", async (
    CreatePostRequest r,
    IPostService s,
    IOutputCacheStore cache,
    CancellationToken ct) =>
{
    var id = await s.CreateAsync(r, ct);
    await cache.EvictByTagAsync("posts", ct);
    return Results.Created($"/api/v1/posts/{id}", id);
});

6.3 Variación insuficiente

// ❌ Mal: ?page=1 y ?page=2 devuelven el mismo caché
policy.Expire(TimeSpan.FromMinutes(2));

// ✅ Bien: variar por query string relevante
policy.VaryByQuery("page", "pageSize");
policy.Expire(TimeSpan.FromMinutes(2));

6.4 Usar Response Caching esperando almacenamiento en servidor

// ❌ Mal: [ResponseCache] no cachea en el servidor ASP.NET Core
[ResponseCache(Duration = 60)]
public IActionResult Get() => Ok(...);

// ✅ Bien: Output Caching almacena la respuesta en el servidor
[OutputCache(Duration = 60)]
public IActionResult Get() => Ok(...);

7 · Ejercicio guiado

Ampliaremos el ejemplo mínimo para añadir ETag manual y variación por header.

Paso 1: endpoint con ETag

app.MapGet("/api/v1/categories", async (ICategoryService categories, CancellationToken ct, HttpContext ctx) =>
{
    var result = await categories.GetAllAsync(ct);

    var json = JsonSerializer.Serialize(result);
    var etag = Convert.ToBase64String(SHA256.HashData(Encoding.UTF8.GetBytes(json)));

    ctx.Response.Headers.ETag = etag;

    if (ctx.Request.Headers.TryGetValue("If-None-Match", out var incoming) &&
        incoming.ToString() == etag)
    {
        return Results.StatusCode(304);
    }

    return Results.Ok(result);
}).CacheOutput("PublicCategories");

Paso 2: prueba con curl

curl -v http://localhost:5000/api/v1/categories
# Guarda el ETag de la respuesta

curl -v -H 'If-None-Match: ' http://localhost:5000/api/v1/categories
# Debería devolver 304 Not Modified

Paso 3: variación por header

options.AddPolicy("Localized", policy =>
{
    policy.Expire(TimeSpan.FromMinutes(2));
    policy.VaryByHeader("Accept-Language");
});

Añade un endpoint /api/v1/greeting que devuelva un saludo en distintos idiomas según Accept-Language y cachea con la política Localized.

Implementa un endpoint /api/v1/posts/search que acepte ?q=termino y ?sort=date|relevance:

  • Cachea la respuesta con variación por ambos parámetros.
  • Asigna la tag posts.
  • Invalida el caché cuando se crea un nuevo post.
  • Añade ETag basado en un hash del resultado y devuelve 304 cuando sea posible.

9 · Resumen

  • Output Caching es el middleware moderno de .NET para cachear respuestas HTTP en el servidor.
  • Response Caching es el mecanismo basado en cabeceras HTTP para clientes y proxies.
  • Output Caching soporta políticas, tags, variación por query/header/route, Redis y autenticación.
  • Invalida respuestas con IOutputCacheStore.EvictByTagAsync.
  • Usa ETags y If-None-Match para devolver 304 y reducir ancho de banda.
  • No cachees endpoints autenticados sin variar por usuario; no cachees endpoints de escritura.

10 · Preguntas frecuentes

¿Output Caching almacena respuestas en memoria?

Por defecto sí, en memoria del proceso. Puedes cambiar a Redis con AddStackExchangeRedisOutputCache para compartir caché entre instancias.

¿Cachea peticiones POST?

No, Output Caching solo considera métodos seguros e idempotentes (GET, HEAD). Si intentas aplicarlo a POST, será ignorado.

¿Qué devuelve el cliente si hay un caché hit?

El mismo cuerpo y cabeceras que se guardaron. La primera petición generó la respuesta; las siguientes la devuelven desde el middleware sin ejecutar el endpoint.

¿Output Caching funciona con controllers?

Sí, usa el atributo [OutputCache(Duration = 60, VaryByQueryKeys = new[] { "page" })]. También puedes usar nombres de políticas definidas en Program.cs.

¿Response Caching está obsoleto?

No está obsoleto, pero es menos potente. Sigue siendo útil para controlar cabeceras Cache-Control en clientes y CDNs. Para caché en servidor, usa Output Caching.

¿Cómo invalido una sola entrada?

Output Caching no expone una API directa para eliminar una clave específica por URL. El mecanismo recomendado es EvictByTagAsync o redefinir la política para incluir una clave de variación que puedas invalidar.
