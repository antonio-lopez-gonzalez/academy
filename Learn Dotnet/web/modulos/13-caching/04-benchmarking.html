Benchmarking con BenchmarkDotNet

Módulo 13 · Caching y rendimiento35 min

1. Introducción

Cuando optimizamos código es fácil caer en la trampa de "mejorar" algo sin medir si realmente mejora. El benchmarking es la disciplina de medir el rendimiento de forma reproducible, controlada y estadísticamente significativa.

En esta lección aprenderemos a usar BenchmarkDotNet, la biblioteca estándar de .NET para benchmarks de métodos. Veremos cómo decorar benchmarks, configurar el entorno, comparar algoritmos, interpretar resultados y por qué no debemos usar Stopwatch para comparaciones serias.

¿Por qué no usar Stopwatch? Stopwatch mide una sola ejecución y es sensible a JIT, recolección de basura, otros procesos, frecuencia variable de CPU y optimizaciones del compilador. BenchmarkDotNet ejecuta múltiples rondas, calienta el JIT, aísla el benchmark en un proceso separado y calcula promedios, medianas y desviaciones.

Al terminar sabrás diseñar benchmarks confiables, evitar errores comunes y decidir cuándo una optimización merece la pena.

2. Teoría

2.1 ¿Qué mide BenchmarkDotNet?

BenchmarkDotNet mide principalmente:

  • Mean: tiempo medio de ejecución.
  • Median: valor central, menos sensible a outliers.
  • Allocated: memoria asignada en el montón (heap) por operación.
  • Gen 0/1/2: número de recolecciones de basura provocadas.
  • Ratio: comparación frente al benchmark baseline.

2.2 Atributos principales

  • [Benchmark]: marca un método como escenario de medición.
  • [Benchmark(Baseline = true)]: establece el método de referencia para comparar ratios.
  • [GlobalSetup]: código que se ejecuta una vez antes de todos los benchmarks de la clase (crear datos, conectar a BD).
  • [IterationSetup]: código que se ejecuta antes de cada iteración.
  • [Params]: permite ejecutar el mismo benchmark con varios valores de entrada.
  • [MemoryDiagnoser]: añade columnas de memoria asignada.
  • [RPlotExporter], [MarkdownExporter]: genera gráficos y tablas.

2.3 Cómo funciona internamente

BenchmarkDotNet genera un proyecto independiente con tu benchmark, lo compila en modo Release, ejecuta iteraciones piloto para determinar cuántas iteraciones necesita, calienta el JIT, ejecuta las mediciones y aplica análisis estadístico. El resultado es una tabla Markdown o HTML lista para publicar.

2.4 Reglas de oro del benchmarking

  • Ejecuta siempre en Release.
  • Evita depuradores, logs excesivos o operaciones de red en el benchmark.
  • El trabajo a medir debe ser lo suficientemente largo para que el tiempo sea significativo, pero no tanto que una sola ejecución domine.
  • No compares JIT-debug con JIT-optimized.
  • Repite benchmarks y descarta outliers causados por tareas en segundo plano.

3. Ejemplo mínimo

Creamos un benchmark que compara tres formas de concatenar strings.

dotnet new console -n BenchmarkDemo -o ejemplos/m13-caching/BenchmarkDemo/src/BenchmarkDemo
dotnet add ejemplos/m13-caching/BenchmarkDemo/src/BenchmarkDemo package BenchmarkDotNet
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;
using System.Text;

namespace BenchmarkDemo;

[MemoryDiagnoser]
public class StringConcatenationBenchmark
{
    private const int Count = 1000;
    private readonly List<string> _words = new();

    [GlobalSetup]
    public void Setup()
    {
        // Datos de entrada compartidos para todos los benchmarks.
        for (int i = 0; i < Count; i++)
            _words.Add($"palabra-{i}");
    }

    [Benchmark(Baseline = true)]
    public string ConcatWithPlus()
    {
        var result = "";
        foreach (var word in _words)
            result += word; // Crea un string nuevo en cada iteración.
        return result;
    }

    [Benchmark]
    public string ConcatWithStringBuilder()
    {
        var sb = new StringBuilder();
        foreach (var word in _words)
            sb.Append(word);
        return sb.ToString();
    }

    [Benchmark]
    public string ConcatWithStringBuilderCapacity()
    {
        // Reservamos capacidad estimada para reducir realocaciones.
        var sb = new StringBuilder(Count * 10);
        foreach (var word in _words)
            sb.Append(word);
        return sb.ToString();
    }
}

class Program
{
    static void Main(string[] args) =>
        BenchmarkRunner.Run<StringConcatenationBenchmark>(args: args);
}

Ejecuta:

dotnet run --project ejemplos/m13-caching/BenchmarkDemo/src/BenchmarkDemo --configuration Release

Salida típica:

|              Method |     Mean |    Error |   StdDev | Ratio | RatioSD |    Gen0 |    Gen1 |   Gen2 | Allocated |
|-------------------- |---------:|---------:|---------:|------:|--------:|--------:|--------:|-------:|----------:|
|        ConcatWithPlus | 142.3 us |  2.81 us |  3.01 us |  1.00 |    0.00 | 109.3750 | 109.3750 | 0.0000 |  682.3 KB |
| ConcatWithStringBuilder |  3.2 us | 0.06 us | 0.05 us |  0.02 |    0.00 |   1.9531 |       - |     - |   12.1 KB |
| ConcatWithStringBuilderCapacity |  2.1 us | 0.04 us | 0.04 us |  0.01 |    0.00 |   1.1368 |       - |     - |    7.0 KB |
Tip: la columna Ratio compara contra el baseline. En este ejemplo, StringBuilderCapacity es ~68 veces más rápido y asigna ~100 veces menos memoria que la concatenación con +.

4. Ejemplo real

En el CMS queremos comparar dos formas de recuperar posts publicados: una con seguimiento de EF Core y otra con AsNoTracking, y también medir el impacto de la proyección a DTOs.

using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.DependencyInjection;

namespace Cms.Benchmarks;

[MemoryDiagnoser]
public class PostRetrievalBenchmark
{
    private CmsDbContext _context = null!;

    [GlobalSetup]
    public async Task Setup()
    {
        var services = new ServiceCollection();
        services.AddDbContext<CmsDbContext>(options =>
            options.UseNpgsql("Host=localhost;Database=cms_benchmark;Username=cms;Password=cms_secret"));

        var provider = services.BuildServiceProvider();
        _context = provider.GetRequiredService<CmsDbContext>();
        await _context.Database.MigrateAsync();
        await SeedDataAsync();
    }

    private async Task SeedDataAsync()
    {
        if (_context.Posts.Any()) return;

        var posts = Enumerable.Range(1, 10_000)
            .Select(i => new Post
            {
                Title = $"Post {i}",
                Content = $"Contenido del post {i}",
                Status = PostStatus.Published,
                PublishedAt = DateTime.UtcNow.AddDays(-i)
            });

        _context.Posts.AddRange(posts);
        await _context.SaveChangesAsync();
    }

    [Benchmark(Baseline = true)]
    public async Task<List<Post>> GetAll_Tracked()
    {
        return await _context.Posts
            .Where(p => p.Status == PostStatus.Published)
            .Take(100)
            .ToListAsync();
    }

    [Benchmark]
    public async Task<List<Post>> GetAll_AsNoTracking()
    {
        return await _context.Posts
            .AsNoTracking()
            .Where(p => p.Status == PostStatus.Published)
            .Take(100)
            .ToListAsync();
    }

    [Benchmark]
    public async Task<List<PostSummaryDto>> GetAll_Projected()
    {
        return await _context.Posts
            .AsNoTracking()
            .Where(p => p.Status == PostStatus.Published)
            .OrderByDescending(p => p.PublishedAt)
            .Take(100)
            .Select(p => new PostSummaryDto(p.Id, p.Title, p.PublishedAt!.Value))
            .ToListAsync();
    }
}

public class Program
{
    public static void Main(string[] args) =>
        BenchmarkRunner.Run<PostRetrievalBenchmark>(args: args);
}

public sealed record PostSummaryDto(Guid Id, string Title, DateTime PublishedAt);

Resultado esperado:

  • AsNoTracking es más rápido porque EF no crea el snapshot de cambios.
  • Projected suele ser el más rápido y con menos asignaciones porque solo trae las columnas necesarias.
Entorno: los benchmarks de base de datos son sensibles al estado de la BD, caché del sistema operativo y disco. Úsalos para comparar estrategias en tu entorno, no como métrica absoluta. Para benchmarks puros de CPU, evita I/O.

5. Buenas prácticas

  • Siempre Release: BenchmarkDotNet lo fuerza, pero nunca ejecutes benchmarks desde el depurador.
  • Un concepto por benchmark: si comparas algoritmos, asegúrate de que hacen exactamente lo mismo. Diferencias sutiles invalidan la comparación.
  • Usa baseline: marca el método actual o más simple como Baseline = true para ver ratios claros.
  • Evita side effects: un benchmark no debe modificar datos que afecten a otra iteración.
  • Configura iteraciones si es necesario: para operaciones muy rápidas o muy lentas, usa [MinIterationCount], [MaxIterationCount], [WarmupCount].
  • Mide memoria con [MemoryDiagnoser]: a veces un código más rápido asigna mucha más memoria, lo que genera presión al GC.
  • Documenta el hardware: incluye CPU, RAM y versión de .NET cuando compartas resultados.
  • Automatiza con criterios: no optimices por un 1% de mejora si el código es más complejo. La regla del 80/20 también aplica al rendimiento.

6. Errores habituales

6.1 Benchmark en Debug

# ❌ Mal: el JIT de Debug no optimiza
 dotnet run

# ✅ Bien: modo Release
 dotnet run --configuration Release

6.2 Usar Stopwatch para comparar librerías

// ❌ Mal: una sola medida, sin calentamiento, con GC impredecible
var sw = Stopwatch.StartNew();
RunAlgorithmA();
sw.Stop();
Console.WriteLine(sw.Elapsed);

// ✅ Bien: BenchmarkDotNet ejecuta múltiples rondas, aisla el proceso
// y calcula estadísticas confiables.
BenchmarkRunner.Run<MyBenchmark>();

6.3 No inicializar datos compartidos

// ❌ Mal: cada iteración genera datos, contaminando la medición
[Benchmark]
public int SumList()
{
    var list = Enumerable.Range(1, 1000).ToList(); // generación dentro
    return list.Sum();
}

// ✅ Bien: datos preparados en GlobalSetup
private List<int> _list = null!;

[GlobalSetup]
public void Setup() => _list = Enumerable.Range(1, 1000).ToList();

[Benchmark]
public int SumList() => _list.Sum();

6.4 Comparar resultados de máquinas distintas

// ❌ Mal: "en mi portátil tarda 2 ms, así que en producción tardará 2 ms"
// ✅ Bien: ejecuta benchmarks en un entorno lo más parecido posible a producción,
// con CPU estable, sin cargas de fondo y repitiendo varias veces.

7. Ejercicio guiado

Vamos a benchmarkar la búsqueda de un elemento en una lista frente a un HashSet.

Paso 1: crea el proyecto

dotnet new console -n SearchBenchmark -o ejemplos/m13-caching/SearchBenchmark/src/SearchBenchmark
dotnet add ejemplos/m13-caching/SearchBenchmark/src/SearchBenchmark package BenchmarkDotNet

Paso 2: implementa el benchmark

using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

namespace SearchBenchmark;

[MemoryDiagnoser]
public class SearchBenchmarkClass
{
    private List<int> _list = null!;
    private HashSet<int> _set = null!;

    [Params(100, 10_000, 1_000_000)]
    public int N { get; set; }

    [GlobalSetup]
    public void Setup()
    {
        _list = Enumerable.Range(0, N).ToList();
        _set = new HashSet<int>(_list);
    }

    [Benchmark(Baseline = true)]
    public bool ListContains() => _list.Contains(N - 1);

    [Benchmark]
    public bool HashSetContains() => _set.Contains(N - 1);
}

class Program
{
    static void Main(string[] args) =>
        BenchmarkRunner.Run<SearchBenchmarkClass>(args: args);
}

Paso 3: ejecuta y analiza

dotnet run --project ejemplos/m13-caching/SearchBenchmark/src/SearchBenchmark --configuration Release

Observa cómo el ratio entre ListContains y HashSetContains cambia drásticamente con el tamaño. ¿Por qué? Reflexiona sobre complejidad algorítmica: O(n) vs O(1).

9. Resumen

  • BenchmarkDotNet es la herramienta estándar de .NET para medir rendimiento de forma rigurosa.
  • Usa [Benchmark], [GlobalSetup] y [MemoryDiagnoser] para diseñar benchmarks confiables.
  • Marca un método como Baseline para comparar ratios de mejora.
  • No uses Stopwatch para comparaciones serias; JIT, GC y otros procesos distorsionan los resultados.
  • Ejecuta siempre en Release y en un entorno estable.
  • Mide antes y después de optimizar; la intuición sobre rendimiento suele ser mala.

10. Preguntas frecuentes

¿BenchmarkDotNet funciona con .NET 8?

Sí, es compatible con .NET 6, 7, 8 y versiones posteriores. Asegúrate de usar la última versión estable del paquete.

¿Puedo benchmarkar métodos asíncronos?

Sí. Los benchmarks pueden devolver Task o Task<T>. BenchmarkDotNet espera la tarea correctamente.

¿Por qué mis benchmarks varían entre ejecuciones?

Por carga del sistema operativo, turbo boost de CPU, caché de CPU, GC y otros procesos. Ejecuta varias veces, cierra aplicaciones innecesarias y considera usar un entorno dedicado.

¿Debo incluir benchmarks en CI?

No como gates de build, porque los entornos de CI son inestables. Sí puedes ejecutarlos manualmente o en máquinas dedicadas y almacenar resultados históricos para detectar regresiones.

¿Qué significa la columna Allocated?

Es la cantidad de memoria asignada en el heap por cada operación del benchmark. Menor es mejor, especialmente si reduce presión al GC.

¿Puedo benchmarkar consultas a base de datos?

Sí, pero considera que estás midiendo también la BD, el disco y la red. Es útil para comparar estrategias de consulta, no para obtener cifras absolutas de CPU.
