Integration Tests con WebApplicationFactory

Módulo 12 · Testing40 min

1 · Introducción

Los tests unitarios aíslan una clase. Los tests de integración comprueban que varias partes funcionan juntas: la API, la serialización JSON, el middleware, el enrutamiento y, en muchos casos, la base de datos real.

En .NET 8, ASP.NET Core proporciona WebApplicationFactory<TEntryPoint>, que lanza la aplicación en memoria sin abrir un puerto real de red. Con ella podemos hacer peticiones HTTP contra nuestra API usando un HttpClient de prueba.

¿Cuándo usar integration tests? Cuando necesitas validar que una request completa recorre correctamente controllers, filtros, validación, mapeo, EF Core y base de datos. Son más lentos que los unitarios, pero detectan problemas que los unitarios no ven.

Al final de esta lección serás capaz de escribir un test de integración que levante la API, cree un post y devuelva 201 Created con la ubicación correcta.

2 · Teoría

2.1 WebApplicationFactory

WebApplicationFactory<TEntryPoint> utiliza como entry point la clase Program del proyecto de API. Desde el test puedes:

  • Configurar servicios de DI (por ejemplo, sustituir la base de datos por PostgreSQL en TestContainers).
  • Modificar IConfiguration para apuntar a una cadena de conexión temporal.
  • Crear un HttpClient que envía peticiones al pipeline de la aplicación.

2.2 IClassFixture

El factory es costoso de crear. Para compartirlo entre todos los tests de una clase usamos IClassFixture<WebApplicationFactory<Program>>. xUnit lo crea una vez y lo inyecta en el constructor.

2.3 TestContainers

TestContainers levanta contenedores Docker desde el código del test. Nos permite usar PostgreSQL real o Redis real sin depender de una instancia externa. La base de datos se destruye al finalizar los tests, garantizando aislamiento.

2.4 Patrón Arrange-Act-Assert

En tests de integración el patrón AAA sigue siendo válido:

  • Arrange: preparar el payload, autorizar si es necesario, configurar el factory.
  • Act: enviar la petición HTTP.
  • Assert: comprobar status code, headers y cuerpo de respuesta.

3 · Ejemplo mínimo

Crea una Minimal API y un proyecto de test:

dotnet new web -n MiniApi -o IntegrationMini/src/MiniApi
dotnet new xunit -n MiniApi.Tests -o IntegrationMini/tests/MiniApi.Tests
dotnet add IntegrationMini/tests/MiniApi.Tests package Microsoft.AspNetCore.Mvc.Testing

Program.cs:

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/health", () => Results.Ok(new { Status = "Healthy" }));

app.Run();

public partial class Program { }

La clase Program parcial es necesaria para que el test pueda referenciarla desde WebApplicationFactory<Program>.

Test de integración:

using FluentAssertions;
using Microsoft.AspNetCore.Mvc.Testing;
using System.Net;
using System.Net.Http.Json;
using Xunit;

namespace MiniApi.Tests;

public class HealthEndpointTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public HealthEndpointTests(WebApplicationFactory<Program> factory)
    {
        _client = factory.CreateClient();
    }

    [Fact]
    public async Task GetHealth_WhenAppIsRunning_ReturnsOkWithHealthyStatus()
    {
        // Act
        var response = await _client.GetAsync("/health");

        // Assert
        response.StatusCode.Should().Be(HttpStatusCode.OK);

        var body = await response.Content.ReadFromJsonAsync<HealthResponse>();
        body.Should().NotBeNull();
        body!.Status.Should().Be("Healthy");
    }

    private sealed record HealthResponse(string Status);
}

Ejecuta:

dotnet test IntegrationMini/tests/MiniApi.Tests
Tip: el HttpClient creado por CreateClient no hace una petición real por red; el mensaje viaja directamente por el pipeline de la aplicación en memoria.

4 · Ejemplo real

Supongamos una API de posts con PostgreSQL. Usaremos TestContainers para levantar una base de datos real y EF Core.

dotnet add Cms.Api.Tests package Testcontainers.PostgreSql
dotnet add Cms.Api.Tests package Microsoft.AspNetCore.Mvc.Testing

Custom factory:

using Microsoft.AspNetCore.Mvc.Testing;
using Microsoft.EntityFrameworkCore;
using Testcontainers.PostgreSql;

namespace Cms.Api.Tests;

public class CmsApiFactory : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder()
        .WithDatabase("cms_test")
        .WithUsername("cms")
        .WithPassword("cms_secret")
        .Build();

    public string ConnectionString => _postgres.GetConnectionString();

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.ConfigureServices(services =>
        {
            // Elimina la registración real de DbContext
            var descriptor = services.SingleOrDefault(
                d => d.ServiceType == typeof(DbContextOptions<CmsDbContext>));
            if (descriptor is not null)
                services.Remove(descriptor);

            // Registra el DbContext apuntando al contenedor de pruebas
            services.AddDbContext<CmsDbContext>(options =>
                options.UseNpgsql(_postgres.GetConnectionString()));
        });
    }

    public async Task InitializeAsync()
    {
        await _postgres.StartAsync();
        using var scope = Services.CreateScope();
        var context = scope.ServiceProvider.GetRequiredService<CmsDbContext>();
        await context.Database.MigrateAsync();
    }

    public async Task DisposeAsync()
    {
        await _postgres.DisposeAsync();
    }
}

Test de creación de posts:

using FluentAssertions;
using System.Net;
using System.Net.Http.Json;
using Xunit;

namespace Cms.Api.Tests.Posts;

public class CreatePostTests : IClassFixture<CmsApiFactory>
{
    private readonly HttpClient _client;
    private readonly CmsApiFactory _factory;

    public CreatePostTests(CmsApiFactory factory)
    {
        _factory = factory;
        _client = factory.CreateClient();
    }

    [Fact]
    public async Task CreatePost_WhenRequestIsValid_ReturnsCreatedWithLocation()
    {
        // Arrange
        var request = new { Title = "Mi primer post", Content = "Contenido", AuthorId = Guid.NewGuid() };

        // Act
        var response = await _client.PostAsJsonAsync("/api/v1/posts", request);

        // Assert
        response.StatusCode.Should().Be(HttpStatusCode.Created);
        response.Headers.Location.Should().NotBeNull();

        var created = await response.Content.ReadFromJsonAsync<PostResponse>();
        created.Should().NotBeNull();
        created!.Title.Should().Be("Mi primer post");

        // Verificación adicional: el post existe en la BD
        using var scope = _factory.Services.CreateScope();
        var context = scope.ServiceProvider.GetRequiredService<CmsDbContext>();
        var postInDb = await context.Posts.SingleOrDefaultAsync(p => p.Id == created.Id);
        postInDb.Should().NotBeNull();
    }

    private sealed record PostResponse(Guid Id, string Title, string Content);
}

Observa que:

  • La factory se encarga del ciclo de vida del contenedor Docker.
  • Las migraciones se aplican automáticamente al inicializar.
  • El test valida tanto la respuesta HTTP como el estado persistente.

5 · Buenas prácticas

  • Comparte la factory, no el HttpClient: la factory es costosa; el cliente es barato. Crea un cliente por test si manipulas cookies o headers de autorización.
  • Aísla la base de datos: usa TestContainers o una base de datos por test runner. Nunca apuntes a la base de datos de desarrollo o producción.
  • Ejecuta migraciones en InitializeAsync: garantiza un esquema limpio antes de correr tests.
  • Limpia datos entre tests: borra filas de las tablas afectadas o reinicia el contenedor si el test lo requiere.
  • Desactiva servicios externos: reemplaza envío de emails, colas y pagos por mocks o no-ops en la factory.
  • Usa autorización de test: si la API requiere JWT, configura un emisor de tokens fake para los tests de integración.
  • Mantén los tests deterministas: no uses DateTime.Now en aserciones; inyecta TimeProvider.
Atención: los tests de integración requieren Docker. Asegúrate de que el daemon de Docker esté en ejecución antes de lanzarlos; de lo contrario TestContainers fallará.

6 · Errores habituales

6.1 No exponer Program como parcial

// ❌ Mal: WebApplicationFactory no puede acceder a Program interno
var app = builder.Build();
app.Run();
// ✅ Bien: declarar Program como parcial
public partial class Program { }

6.2 No sustituir la base de datos de producción

// ❌ Mal: el test usaría la cadena de conexión real del appsettings
services.AddDbContext<CmsDbContext>();
// ✅ Bien: reemplazar el DbContextOptions registrado
var descriptor = services.SingleOrDefault(d => d.ServiceType == typeof(DbContextOptions<CmsDbContext>));
if (descriptor is not null) services.Remove(descriptor);

services.AddDbContext<CmsDbContext>(options => options.UseNpgsql(connectionString));

6.3 No aplicar migraciones

// ❌ Mal: la base de datos está vacía y las peticiones fallan por falta de tablas
// ✅ Bien: migrar antes de los tests
public async Task InitializeAsync()
{
    await _postgres.StartAsync();
    using var scope = Services.CreateScope();
    var context = scope.ServiceProvider.GetRequiredService<CmsDbContext>();
    await context.Database.MigrateAsync();
}

6.4 Testear muchos escenarios en una sola petición

// ❌ Mal: crear, actualizar, borrar y listar en el mismo test
var create = await client.PostAsync(...);
var update = await client.PutAsync(...);
var delete = await client.DeleteAsync(...);
// ✅ Bien: un test por comportamiento (Create, Update, Delete, List)

7 · Ejercicio guiado

Vamos a testear un endpoint de validación de email.

Paso 1: API

app.MapPost("/validate-email", (string email) =>
{
    if (string.IsNullOrWhiteSpace(email) || !email.Contains('@'))
        return Results.BadRequest(new { Error = "Email inválido" });

    return Results.Ok(new { Valid = true });
});

Paso 2: Test

[Theory]
[InlineData("hola@example.com", HttpStatusCode.OK)]
[InlineData("no-es-email", HttpStatusCode.BadRequest)]
[InlineData("   ", HttpStatusCode.BadRequest)]
public async Task ValidateEmail_WithVariousInputs_ReturnsExpectedStatus(
    string email, HttpStatusCode expected)
{
    var response = await _client.PostAsJsonAsync("/validate-email", new { Email = email });
    response.StatusCode.Should().Be(expected);
}

Paso 3: ejecuta

dotnet test IntegrationMini/tests/MiniApi.Tests

Añade un test que compruebe que la respuesta OK contiene Valid = true.

8 · Reto

Extiende la API de posts con:

  • GET /api/v1/posts/{id}
  • DELETE /api/v1/posts/{id}

Escribe tests de integración que:

  • Creen un post.
  • Lo recuperen por GET y comprueben el title.
  • Lo eliminen y devuelvan 204.
  • Al volver a buscarlo devuelvan 404.

Utiliza TestContainers para PostgreSQL. No resuelvas el reto ahora.

9 · Resumen

  • WebApplicationFactory<Program> levanta la API en memoria para tests.
  • IClassFixture comparte la factory entre tests de la misma clase.
  • TestContainers permite usar PostgreSQL, Redis y otros servicios reales en Docker.
  • Reemplaza el DbContext real por la versión de prueba en ConfigureWebHost.
  • Aplica migraciones en InitializeAsync y limpia datos entre tests.

10 · Preguntas frecuentes

¿Los tests de integración necesitan Docker?

Solo si usas TestContainers. Si apuntas a una base de datos local o en memoria, no. Pero TestContainers es la opción más fiable porque garantiza aislamiento y reproducibilidad.

¿Puedo usar SQLite en memoria para los tests?

Podrías, pero esconde diferencias de comportamiento con PostgreSQL (tipos de datos, funciones SQL, límite de identificadores). Para tests que validen EF Core, TestContainers con PostgreSQL es mucho más fiel.

¿Cómo autorizo requests en tests de integración?

Puedes registrar un handler de autenticación de test que acepte cualquier token y añada los claims que necesites. También puedes crear un token JWT con una clave compartida.

¿Cómo comparto la factory entre varias clases de tests?

Usa ICollectionFixture<T> en lugar de IClassFixture<T>. xUnit creará una única instancia por toda la colección.

¿Por qué no veo logs de la API en la consola del test?

El factory redirige el logging. Para verlo, añade builder.ConfigureLogging(l => l.AddConsole().SetMinimumLevel(LogLevel.Debug)) en ConfigureWebHost.
