Proyecto CMS: suite completa de tests

Módulo 12 · Testing55 min

1. Introducción

En esta lección aplicamos todo lo aprendido en el módulo de testing al proyecto del CMS. Vamos a construir una suite de tests completa que cubra validadores, servicios de aplicación, handlers de MediatR, endpoints de la API y un pequeño benchmark de rendimiento.

El objetivo no es solo tener tests, sino tener tests que nos den confianza para refactorizar, añadir funcionalidades y desplegar con seguridad.

Proyecto del módulo: crearemos una solución de tests separada en la carpeta proyectos/m12-cms-testing o dentro de proyecto-final/tests, según la estructura del curso. La importante es que sea independiente y ejecutable con dotnet test.

Al terminar tendrás tests unitarios con xUnit + Moq + FluentAssertions, tests de integración con WebApplicationFactory y TestContainers, y un benchmark con BenchmarkDotNet para medir la recuperación de posts.

2. Teoría

2.1 Estrategia de testing en capas

Una arquitectura limpia se presta a testear cada capa por separado:

  • Domain: pocos tests, generalmente de value objects e invariantes. No tiene dependencias externas.
  • Application: tests unitarios de handlers y servicios. Mockeamos repositorios, unidad de trabajo, publicador de eventos, etc.
  • Infrastructure: tests de integración de repositorios contra base de datos real.
  • API: tests de integración de endpoints con WebApplicationFactory.

2.2 Pirámide de tests

        /
       / \   E2E (pocos, lentos)
      /   \  
     /-----\  Integration (moderados)
    /       \ 
   /---------\ Unit (muchos, rápidos)

En el CMS priorizamos tests unitarios para reglas de negocio y tests de integración para flujos críticos: crear post, login, publicar post programado, etc.

2.3 Test data builders

Para evitar repetir la creación de entidades en cada test, usamos builders o métodos de fábrica. Por ejemplo, PostBuilder.CreateDraft() devuelve un post válido por defecto.

2.4 Anticorrupción de tests

Los tests no deben depender de detalles internos de la implementación. Si mañana cambiamos EF Core por Dapper, los tests de aplicación no deberían romperse.

4. Ejemplo real

4.1 Test unitario de validador

using FluentAssertions;
using FluentValidation.TestHelper;
using Xunit;

namespace Cms.Tests.Application.Validators;

public class CreatePostValidatorTests
{
    private readonly CreatePostValidator _sut = new();

    [Fact]
    public void Validate_WhenTitleIsEmpty_ShouldHaveValidationError()
    {
        var command = new CreatePostCommand("", "Contenido", Guid.NewGuid());
        var result = _sut.TestValidate(command);
        result.ShouldHaveValidationErrorFor(x => x.Title);
    }

    [Theory]
    [InlineData("A")]
    [InlineData("Este título es demasiado largo porque supera los cincuenta caracteres permitidos")]
    public void Validate_WhenTitleHasInvalidLength_ShouldHaveValidationError(string title)
    {
        var command = new CreatePostCommand(title, "Contenido", Guid.NewGuid());
        var result = _sut.TestValidate(command);
        result.ShouldHaveValidationErrorFor(x => x.Title);
    }
}

4.2 Test unitario de handler

using FluentAssertions;
using Moq;
using Xunit;

namespace Cms.Tests.Application.Handlers;

public class CreatePostHandlerTests
{
    private readonly Mock<IPostRepository> _repoMock;
    private readonly Mock<IUnitOfWork> _uowMock;
    private readonly CreatePostHandler _sut;

    public CreatePostHandlerTests()
    {
        _repoMock = new Mock<IPostRepository>();
        _uowMock = new Mock<IUnitOfWork>();
        _sut = new CreatePostHandler(_repoMock.Object, _uowMock.Object);
    }

    [Fact]
    public async Task Handle_WhenCommandIsValid_CreatesPostAndSavesChanges()
    {
        // Arrange
        var command = new CreatePostCommand("Título", "Contenido", Guid.NewGuid());
        _repoMock.Setup(r => r.AddAsync(It.IsAny<Post>(), It.IsAny<CancellationToken>()))
                 .Returns(Task.CompletedTask);
        _uowMock.Setup(u => u.SaveChangesAsync(It.IsAny<CancellationToken>()))
                .ReturnsAsync(1);

        // Act
        var result = await _sut.Handle(command, CancellationToken.None);

        // Assert
        result.IsSuccess.Should().BeTrue();
        result.Value.Title.Should().Be("Título");

        _repoMock.Verify(r => r.AddAsync(It.IsAny<Post>(), It.IsAny<CancellationToken>()), Times.Once);
        _uowMock.Verify(u => u.SaveChangesAsync(It.IsAny<CancellationToken>()), Times.Once);
    }
}

4.3 Factory de integración

using Microsoft.AspNetCore.Mvc.Testing;
using Testcontainers.PostgreSql;

namespace Cms.Tests.Api.Factories;

public class CmsApiFactory : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder()
        .WithDatabase("cms_tests")
        .WithUsername("cms")
        .WithPassword("cms_secret")
        .Build();

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.ConfigureServices(services =>
        {
            var descriptor = services.SingleOrDefault(d => d.ServiceType == typeof(DbContextOptions<CmsDbContext>));
            if (descriptor is not null) services.Remove(descriptor);

            services.AddDbContext<CmsDbContext>(options =>
                options.UseNpgsql(_postgres.GetConnectionString()));

            // Sustituye servicios externos por no-ops
            services.AddSingleton<IEmailSender, NoOpEmailSender>();
        });
    }

    public async Task InitializeAsync()
    {
        await _postgres.StartAsync();
        using var scope = Services.CreateScope();
        var context = scope.ServiceProvider.GetRequiredService<CmsDbContext>();
        await context.Database.MigrateAsync();
    }

    public async Task DisposeAsync() => await _postgres.DisposeAsync();
}

4.4 Test de endpoint

using FluentAssertions;
using System.Net;
using System.Net.Http.Json;
using Xunit;

namespace Cms.Tests.Api.Endpoints;

public class PostsEndpointTests : IClassFixture<CmsApiFactory>
{
    private readonly HttpClient _client;

    public PostsEndpointTests(CmsApiFactory factory)
    {
        _client = factory.CreateClient();
    }

    [Fact]
    public async Task CreatePost_WhenRequestIsValid_ReturnsCreated()
    {
        var request = new { Title = "Nuevo post", Content = "Body", AuthorId = Guid.NewGuid() };
        var response = await _client.PostAsJsonAsync("/api/v1/posts", request);

        response.StatusCode.Should().Be(HttpStatusCode.Created);

        var body = await response.Content.ReadFromJsonAsync<PostResponse>();
        body.Should().NotBeNull();
        body!.Title.Should().Be("Nuevo post");
    }

    [Fact]
    public async Task GetPost_WhenPostDoesNotExist_ReturnsNotFound()
    {
        var response = await _client.GetAsync($"/api/v1/posts/{Guid.NewGuid()}");
        response.StatusCode.Should().Be(HttpStatusCode.NotFound);
    }

    private sealed record PostResponse(Guid Id, string Title, string Content);
}

4.5 Benchmark de recuperación de posts

using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;
using Microsoft.Extensions.DependencyInjection;

namespace Cms.Tests.Benchmarks;

[MemoryDiagnoser]
public class PostRetrievalBenchmark
{
    private CmsDbContext _context = null!;

    [GlobalSetup]
    public async Task Setup()
    {
        var services = new ServiceCollection();
        services.AddDbContext<CmsDbContext>(options =>
            options.UseNpgsql("Host=localhost;Database=cms_benchmark;Username=cms;Password=cms_secret"));

        var provider = services.BuildServiceProvider();
        _context = provider.GetRequiredService<CmsDbContext>();
        await _context.Database.MigrateAsync();
        await SeedDataAsync();
    }

    private async Task SeedDataAsync()
    {
        if (_context.Posts.Any()) return;

        var posts = Enumerable.Range(1, 10_000)
            .Select(i => new Post($"Post {i}", $"Contenido {i}", Guid.NewGuid()));

        _context.Posts.AddRange(posts);
        await _context.SaveChangesAsync();
    }

    [Benchmark(Baseline = true)]
    public async Task<List<Post>> GetAll_Posts()
    {
        return await _context.Posts.AsNoTracking().ToListAsync();
    }

    [Benchmark]
    public async Task<List<Post>> GetAll_WithPagination()
    {
        return await _context.Posts.AsNoTracking()
            .OrderBy(p => p.Id)
            .Take(50)
            .ToListAsync();
    }
}

public class Program
{
    public static void Main(string[] args) =>
        BenchmarkRunner.Run<PostRetrievalBenchmark>(args: args);
}
Tip: los benchmarks no son tests, pero forman parte de la estrategia de calidad. Ejecútalos en un entorno estable, nunca en CI compartido con carga variable.

5. Buenas prácticas

  • Tests unitarios rápidos: no dependan de red, disco ni base de datos.
  • Tests de integración enfocados: un flujo crítico por test; no reemplacen a los unitarios.
  • Builders de datos: crea datos de prueba con valores por defecto sensibles.
  • Separar proyectos si es necesario: un proyecto de unit tests y otro de integration/benchmarks para tiempos de ejecución distintos.
  • Seed mínimo: en integración, inserta solo los datos que necesita el test.
  • Nombres descriptivos: CreatePost_WhenTitleIsEmpty_ReturnsValidationError.
  • Medir rendimiento base: antes de optimizar, corre benchmarks. Después de optimizar, compara.
  • Cobertura realista: configura Coverlet en CI con un umbral sensato y excluye migrations.

6. Errores habituales

6.1 Compartir base de datos entre tests

// ❌ Mal: todos los tests modifican la misma tabla sin limpiar
public class Tests1 { ... }
public class Tests2 { ... } // falla por datos de Tests1
// ✅ Bien: limpiar en InitializeAsync o usar transacciones por test
public async Task DisposeAsync()
{
    using var scope = Services.CreateScope();
    var context = scope.ServiceProvider.GetRequiredService<CmsDbContext>();
    context.Posts.RemoveRange(context.Posts);
    await context.SaveChangesAsync();
}

6.2 Mockear el DbContext

// ❌ Mal: DbSet<T> es difícil de simular y los tests no son fiables
var mockSet = new Mock<DbSet<Post>>();
// ✅ Bien: depende de repositorios con interfaz; el repositorio se testea contra BD real

6.3 Tests que validan implementación en lugar de comportamiento

// ❌ Mal: verificar que se llamó a un método interno
mediatorMock.Verify(m => m.Send(It.IsAny<InternalCommand>(), It.IsAny<CancellationToken>()));
// ✅ Bien: verificar el resultado observable
result.IsSuccess.Should().BeTrue();
result.Value.Status.Should().Be(PostStatus.Draft);

6.4 Benchmarks sin baseline

// ❌ Mal: dos benchmarks sin baseline dificultan comparar
[Benchmark] public async Task VersionA() { ... }
[Benchmark] public async Task VersionB() { ... }
// ✅ Bien: marca la versión actual como baseline
[Benchmark(Baseline = true)] public async Task Current() { ... }
[Benchmark] public async Task Optimized() { ... }

7. Ejercicio guiado

Vamos a añadir un test de integración para el login del CMS.

Paso 1: endpoint de login

app.MapPost("/api/v1/auth/login", async (
    LoginRequest request,
    IAuthService auth,
    CancellationToken ct) =>
{
    var result = await auth.AuthenticateAsync(request.Email, request.Password, ct);
    return result.IsSuccess
        ? Results.Ok(result.Value)
        : Results.Unauthorized();
});

Paso 2: test de integración

[Fact]
public async Task Login_WhenCredentialsAreInvalid_ReturnsUnauthorized()
{
    var request = new { Email = "noexiste@example.com", Password = "wrong" };
    var response = await _client.PostAsJsonAsync("/api/v1/auth/login", request);

    response.StatusCode.Should().Be(HttpStatusCode.Unauthorized);
}

Paso 3: ejecuta

dotnet test proyecto-final/tests/Cms.Tests --filter "FullyQualifiedName~Auth"

Añade un test que valide un login exitoso. Necesitarás insertar un usuario con hash de contraseña en el seed de la factory.

9. Resumen

  • El CMS se testea por capas: unitarios en Application, integración en Infrastructure y API.
  • Usa Moq para dependencias externas y FluentAssertions para aserciones legibles.
  • WebApplicationFactory + TestContainers levanta la API y PostgreSQL en los tests de integración.
  • Los builders de datos reducen duplicación y hacen los tests más mantenibles.
  • BenchmarkDotNet mide el rendimiento de consultas críticas antes de optimizar.
  • Coverlet y ReportGenerator nos ayudan a identificar zonas poco protegidas sin obsesionarnos con el 100%.

10. Preguntas frecuentes

¿Dónde coloco los tests del CMS?

En la carpeta proyecto-final/tests o proyectos/m12-cms-testing. Lo importante es que estén en la misma solución y se ejecuten con dotnet test.

¿Debo testear la capa Domain?

Sí, pero de forma ligera. Testea value objects, invariantes y reglas de negocio puras. Si la capa Domain solo tiene DTOs, no necesitas tests.

¿Cómo limpio datos entre tests de integración?

Puedes eliminar entidades en DisposeAsync, envolver cada test en una transacción y hacer rollback, o usar contenedores efímeros por clase.

¿Puedo ejecutar solo los tests unitarios?

Sí, con traits de xUnit. Añade [Trait("Category", "Unit")] y [Trait("Category", "Integration")], luego filtra con --filter Category=Unit.

¿Los benchmarks deben ejecutarse en CI?

No como parte del build habitual porque los entornos de CI no son estables. Ejecútalos manualmente o en una máquina dedicada y almacena los resultados históricos.

¿Qué hago si un test de integración falla solo en CI?

Revisa la disponibilidad de Docker, la configuración de red, el orden de ejecución y los datos compartidos. Añade logs de Serilog al output del test para diagnosticar.
