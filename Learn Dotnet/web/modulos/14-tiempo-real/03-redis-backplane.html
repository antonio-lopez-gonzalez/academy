Escalar SignalR con Redis Backplane

Módulo 14 · Tiempo real35 min

1 · Introducción

SignalR por defecto mantiene en memoria el mapa de conexiones y grupos. Esto funciona perfectamente con un solo servidor, pero en producción casi siempre tendrás múltiples instancias de tu API detrás de un balanceador de carga.

En esta lección aprenderemos qué es un backplane, por qué Redis es la opción estándar en .NET 8 y cómo configurar AddStackExchangeRedis para que los mensajes de SignalR se repliquen entre todos los servidores.

¿Qué problema resuelve?

Sin backplane, un cliente conectado al servidor A no recibe mensajes enviados desde el servidor B. El backplane actúa como una "radio común" a la que todos los servidores se suscriben y retransmiten.

Errores típicos

  • Desplegar SignalR a Kubernetes sin backplane y descubrir que los mensajes no llegan a todos los usuarios.
  • Usar Redis solo para cache y olvidar configurarlo también para SignalR.
  • Asumir que Clients.All funciona entre servidores sin backplane.
  • Compartir la misma conexión de Redis para cache y SignalR sin revisar límites de timeout.

2 · Teoría

¿Qué es un backplane?

En una arquitectura horizontalmente escalable, cada instancia de la aplicación conoce solo las conexiones que ella misma mantiene. El backplane es un componente central que recibe los mensajes de cada instancia y los propaga al resto. Así, cuando el servidor A llama a Clients.Group("editores").SendAsync(...), el mensaje también llega a los clientes conectados al servidor B y C.

┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐ │ Servidor A │ │ Servidor B │ │ Servidor C │ │ conexiones 1,2 │ │ conexiones 3,4 │ │ conexiones 5,6 │ └────────┬────────┘ └────────┬────────┘ └────────┬────────┘ │ │ │ └───────────────────────┼───────────────────────┘ │ ┌────────────▼────────────┐ │ Redis Backplane │ │ pub/sub de mensajes │ └──────────────────────────┘

¿Cómo funciona internamente?

SignalR usa el mecanismo de pub/sub de Redis. Cuando un servidor quiere enviar un mensaje a un grupo, publica el mensaje en un canal de Redis. Los demás servidores están suscritos a ese canal y reenvían el mensaje a sus conexiones locales. El backplane no procesa la lógica de negocio; solo replica los mensajes.

Consideraciones de rendimiento

  • Redis añade latencia de red: el mensaje debe ir al Redis y volver. Suele ser sub-milisegundo en la misma región.
  • Si tienes muchos mensajes pequeños, considera MessagePack en lugar de JSON para reducir el tamaño.
  • La latencia del backplane no afecta al envío al cliente local; el servidor A sigue enviando a sus clientes inmediatamente.

¿Cuándo no necesito backplane?

Si tu aplicación corre en una sola instancia (desarrollo, pruebas o una app pequeña con un solo pod), el backplane no es necesario. En producción con más de una instancia, es prácticamente obligatorio.

3 · Ejemplo mínimo

Añadimos Redis a un proyecto web con SignalR. Necesitamos un servidor Redis local; puedes levantarlo con Docker.

# Levantamos Redis localmente con Docker
docker run -d -p 6379:6379 --name redis-signalr redis:7-alpine

# Creamos el proyecto y añadimos el backplane
dotnet new web -n BackplaneDemo -o BackplaneDemo
cd BackplaneDemo
dotnet add package Microsoft.AspNetCore.SignalR.StackExchangeRedis --version 8.0.0
dotnet run --project .
Program.cs
using Microsoft.AspNetCore.SignalR;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSignalR()
    .AddStackExchangeRedis("localhost:6379", options =>
    {
        // Nombre de instancia útil para ver en logs de Redis
        options.Configuration.ChannelPrefix = "BackplaneDemo";
    });

var app = builder.Build();
app.UseStaticFiles();
app.MapHub("/chatHub");
app.Run();

public sealed class ChatHub : Hub
{
    public async Task Broadcast(string message)
    {
        // Este mensaje se replicará a todos los servidores gracias a Redis
        await Clients.All.SendAsync("ReceiveMessage", Context.ConnectionId, message);
    }
}

¿Qué ocurre aquí?

SignalR usa Redis como intermediario. Si lanzas dos instancias en puertos distintos y un cliente se conecta a cada una, ambos recibirán el mensaje cuando uno de ellos invoque Broadcast.

4 · Ejemplo real

En producción no conectamos con una cadena hardcodeada. Leemos la configuración, configuramos reintentos y añadimos health checks para Redis. También registramos un servicio que envía mensajes desde fuera del hub.

appsettings.json
{
  "ConnectionStrings": {
    "Redis": "localhost:6379,abortConnect=false,connectTimeout=5000"
  }
}
Program.cs
using Microsoft.AspNetCore.SignalR;
using StackExchange.Redis;

var builder = WebApplication.CreateBuilder(args);

var redisConnectionString = builder.Configuration
    .GetConnectionString("Redis") ?? throw new InvalidOperationException("Redis connection string is missing.");

builder.Services.AddHealthChecks()
    .AddRedis(redisConnectionString, name: "redis-signalr");

builder.Services.AddSignalR()
    .AddStackExchangeRedis(redisConnectionString, options =>
    {
        // Prefijo para evitar colisiones con otras apps que usen el mismo Redis
        options.Configuration.ChannelPrefix = "CmsRealtime";

        // Puedes añadir configuración de reintentos si es necesario
        options.Configuration.ConnectTimeout = 5000;
        options.Configuration.SyncTimeout = 5000;
    });

// IHubContext permite enviar desde cualquier servicio inyectado
builder.Services.AddSingleton();

var app = builder.Build();
app.UseStaticFiles();
app.MapHub("/hubs/notifications");
app.MapHealthChecks("/health/ready");
app.Run();

public sealed class NotificationHub : Hub
{
    public async Task JoinProject(string projectId)
    {
        await Groups.AddToGroupAsync(Context.ConnectionId, projectId);
    }

    public async Task LeaveProject(string projectId)
    {
        await Groups.RemoveFromGroupAsync(Context.ConnectionId, projectId);
    }
}

public interface INotificationClient
{
    Task ProjectUpdated(string projectId, string status);
}

public interface INotificationService
{
    Task NotifyProjectUpdatedAsync(string projectId, string status);
}

public sealed class NotificationService : INotificationService
{
    private readonly IHubContext _hubContext;

    public NotificationService(IHubContext hubContext)
    {
        _hubContext = hubContext;
    }

    public async Task NotifyProjectUpdatedAsync(string projectId, string status)
    {
        await _hubContext.Clients.Group(projectId).ProjectUpdated(projectId, status);
    }
}

Conexión compartida

El paquete de SignalR crea su propia conexión multiplexada a Redis. Si usas IDistributedCache con el mismo Redis, no es necesario que compartas la conexión de SignalR; cada servicio gestiona la suya. Solo asegúrate de que el servidor Redis soporte el número de conexiones esperado.

5 · Buenas prácticas

  • Usa un ChannelPrefix por aplicación. Si varias apps comparten Redis, el prefijo evita que reciban mensajes ajenos.
  • Configura timeouts razonables. Redis caído no debe bloquear indefinidamente los envíos de SignalR.
  • Monitoriza la conexión. Añade un health check de Redis y alerta si el backplane está caído.
  • Considera Azure SignalR Service. Si usas Azure, te evitas gestionar Redis y obtienes escalado automático.
  • Usa MessagePack para payloads grandes. Reduce ancho de banda y latencia en el backplane.
  • Prueba en multi-instancia localmente. Lanza dos puertos con dotnet run --urls y verifica que los mensajes cruzan.

Prueba local multi-instancia

# Terminal A
dotnet run --project MiApi --urls "http://localhost:5001"

# Terminal B
dotnet run --project MiApi --urls "http://localhost:5002"

# Conecta clientes a ambos puertos y verifica que Clients.All funciona

6 · Errores habituales

6.1. Olvidar el backplane en producción

Incorrecto
// Funciona en local con 1 instancia; falla en producción con 2+
builder.Services.AddSignalR();
Correcto
builder.Services.AddSignalR()
    .AddStackExchangeRedis(redisConnectionString, options =>
    {
        options.Configuration.ChannelPrefix = "CmsRealtime";
    });

6.2. Cadena de conexión hardcodeada

Incorrecto
.AddStackExchangeRedis("localhost:6379")
Correcto
.AddStackExchangeRedis(builder.Configuration.GetConnectionString("Redis")!)

6.3. Confundir backplane con persistencia

El backplane replica mensajes entre servidores, pero no los almacena. Si un cliente se reconecta después de un corte, no recibirá los mensajes que perdió durante la desconexión. Para persistencia, usa una cola de mensajes o un servicio gestionado como Azure SignalR Service.

7 · Ejercicio guiado

Despliega dos instancias de la misma API con Redis y comprueba que un mensaje enviado desde una instancia llega a un cliente conectado a la otra.

  1. Levanta Redis: docker run -d -p 6379:6379 redis:7-alpine
  2. Crea un proyecto web con SignalR + Redis como en el ejemplo mínimo.
  3. Lanza la instancia A en http://localhost:5001.
  4. Lanza la instancia B en http://localhost:5002.
  5. Conecta un cliente JS a la instancia A.
  6. Desde un cliente conectado a la instancia B, envía un mensaje con Clients.All.
  7. Verifica que el cliente conectado a la instancia A recibe el mensaje.
Comando para lanzar la instancia B
dotnet run --project BackplaneDemo --urls "http://localhost:5002"

¿Por qué es importante esta prueba?

Es la prueba de fuego de un backplane. Si los mensajes no cruzan, tus usuarios verán notificaciones incompletas cuando el balanceador los mande a un servidor distinto.

9 · Resumen

  • El backplane permite que varias instancias de SignalR compartan conexiones y grupos.
  • Redis es el backplane estándar en .NET 8 con AddStackExchangeRedis.
  • SignalR usa pub/sub de Redis para replicar mensajes entre servidores.
  • Configura ChannelPrefix para evitar colisiones entre aplicaciones.
  • El backplane no reemplaza la persistencia ni las colas de mensajes.
  • Azure SignalR Service es una alternativa gestionada sin necesidad de Redis.

10 · Preguntas frecuentes

¿Necesito Redis si uso Azure SignalR Service?

No. Azure SignalR Service actúa como backplane y gestiona las conexiones por ti. Es la opción recomendada si despliegas en Azure.

¿Puedo usar Redis Sentinel o Cluster?

Sí. StackExchange.Redis soporta configuraciones de alta disponibilidad. Pasa la cadena de conexión con los endpoints de Sentinel/Cluster y el cliente se encarga del failover.

¿El backplane afecta al rendimiento?

Añade una pequeña latencia de red, pero es despreciable comparado con la latencia del cliente. Si tienes miles de mensajes por segundo, monitoriza el uso de CPU y red de Redis.

¿Los grupos se sincronizan entre servidores?

La pertenencia a un grupo se sincroniza mediante el backplane. Cuando un servidor añade una conexión a un grupo, el cambio se propaga para que los envíos a ese grupo funcionen en todos los servidores.

¿Puedo tener un backplane por entorno?

Sí, y deberías. Usa prefijos de canal distintos o instancias de Redis separadas para desarrollo, staging y producción.
