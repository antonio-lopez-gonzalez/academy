Proyecto CMS: notificaciones en tiempo real

Módulo 14 · Proyecto50 min

1 · Introducción

En el CMS que estamos construyendo a lo largo del curso, varios usuarios pueden estar editando simultáneamente. Queremos que cuando un autor publique un nuevo post o un lector añada un comentario, los editores y otros usuarios relevantes reciban una notificación inmediata sin tener que recargar la página.

En esta lección integraremos SignalR en el proyecto final del CMS. Crearemos un NotificationHub, usaremos grupos para segmentar por roles, configuraremos Redis como backplane para producción y conectaremos un cliente JavaScript de prueba.

Objetivos del proyecto

  • Crear un NotificationHub en Cms.Api con métodos tipados.
  • Enviar notificaciones cuando se publique un nuevo post o un comentario.
  • Notificar a los roles Author, Editor y Admin.
  • Permitir que un cliente JS se suscriba a notificaciones con autenticación JWT.
  • Integrar el envío desde un handler de MediatR para mantener la arquitectura limpia.
  • Configurar Redis como backplane en el entorno de producción.

Errores típicos

  • Colocar la lógica de notificaciones directamente en el controlador en lugar de un handler.
  • Enviar notificaciones a Clients.All sin segmentar por rol o por suscripción.
  • Olvidar el token JWT en la conexión SignalR y que Context.User esté vacío.
  • No usar backplane en producción, causando notificaciones perdidas en despliegues multi-instancia.

2 · Teoría

2.1. Arquitectura del CMS

Recordamos la estructura del proyecto final:

  • Cms.Domain: entidades como Post, Comment, User.
  • Cms.Application: commands, queries, handlers, validadores y DTOs.
  • Cms.Infrastructure: EF Core, repositorios, Redis, email.
  • Cms.Api: hubs, endpoints, middleware, configuración.

Los hubs y la configuración de SignalR viven en Cms.Api. Sin embargo, el envío de notificaciones desde la lógica de negocio se hace a través de un servicio de aplicación o un handler de MediatR que inyecta IHubContext. Así respetamos la regla de dependencias de Clean Architecture.

2.2. Flujo de una notificación

2.3. Decisiones de diseño

  • Hub tipado: NotificationHub : Hub<INotificationClient> para detectar errores en tiempo de compilación.
  • Grupos por rol: al conectarse, el usuario se une automáticamente a grupos como authors, editors y admins.
  • Notificaciones selectivas: los comentarios en un post notifican a los autores de ese post; los posts publicados notifican a editores y admins.
  • Backplane condicional: en desarrollo usamos la memoria interna; en producción añadimos Redis.

Consejo del proyecto

Define un contrato de notificaciones claro en Cms.Application (por ejemplo, una interfaz INotificationService) e implementa el envío real en Cms.Infrastructure usando IHubContext. La capa de aplicación no debe depender de SignalR.

3 · Ejemplo mínimo

Antes de integrar todo, veamos el hub más pequeño del CMS: un método que se une a grupos por rol y recibe un mensaje de bienvenida.

Cms.Api/Hubs/INotificationClient.cs
namespace Cms.Api.Hubs;

public interface INotificationClient
{
    Task PostPublished(Guid postId, string title, string authorName);
    Task CommentAdded(Guid postId, string commentAuthor, string excerpt);
    Task SystemMessage(string message);
}
Cms.Api/Hubs/NotificationHub.cs
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.SignalR;

namespace Cms.Api.Hubs;

[Authorize]
public sealed class NotificationHub : Hub
{
    public override async Task OnConnectedAsync()
    {
        // Nos unimos a grupos basados en roles de claims
        if (Context.User?.IsInRole("Author") == true)
            await Groups.AddToGroupAsync(Context.ConnectionId, "authors");

        if (Context.User?.IsInRole("Editor") == true)
            await Groups.AddToGroupAsync(Context.ConnectionId, "editors");

        if (Context.User?.IsInRole("Admin") == true)
            await Groups.AddToGroupAsync(Context.ConnectionId, "admins");

        await Clients.Caller.SystemMessage($"Conectado como {Context.User?.Identity?.Name}");
        await base.OnConnectedAsync();
    }

    public override async Task OnDisconnectedAsync(Exception? exception)
    {
        // SignalR elimina automáticamente la conexión de los grupos,
        // pero podemos hacer limpieza adicional si fuera necesario.
        await base.OnDisconnectedAsync(exception);
    }
}

¿Qué ocurre aquí?

El hub está protegido con [Authorize], por lo que el cliente debe enviar un JWT válido. Al conectarse, el usuario se une a los grupos que corresponden a sus roles. Esto permite enviar notificaciones dirigidas más tarde.

4 · Ejemplo real

Integramos SignalR con el resto del CMS: configuración de JWT para WebSockets, registro del hub, servicio de notificaciones en infraestructura y handler de MediatR.

4.1. Configuración de autenticación para SignalR

Cms.Api/Program.cs (extracto)
using Cms.Api.Hubs;
using Cms.Application;
using Cms.Infrastructure;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddApplication();
builder.Services.AddInfrastructure(builder.Configuration);

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = JwtTokenValidation.BuildParameters(builder.Configuration);

        // SignalR no puede enviar cabeceras en el handshake WebSocket
        options.Events = new JwtBearerEvents
        {
            OnMessageReceived = context =>
            {
                var accessToken = context.Request.Query["access_token"];
                if (!string.IsNullOrEmpty(accessToken))
                    context.Token = accessToken;
                return Task.CompletedTask;
            }
        };
    });

builder.Services.AddAuthorization();

var signalRBuilder = builder.Services.AddSignalR();

// En producción, activamos el backplane de Redis
if (builder.Environment.IsProduction())
{
    var redis = builder.Configuration.GetConnectionString("Redis")
        ?? throw new InvalidOperationException("Redis connection string is missing in production.");

    signalRBuilder.AddStackExchangeRedis(redis, options =>
    {
        options.Configuration.ChannelPrefix = "CmsSignalR";
    });
}

builder.Services.AddControllers();

var app = builder.Build();

if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler();
    app.UseHsts();
}

app.UseHttpsRedirection();
app.UseCors("CmsFrontend");

app.UseAuthentication();
app.UseAuthorization();

app.MapHub("/hubs/notifications")
   .RequireAuthorization();

app.MapControllers();
app.Run();

4.2. Servicio de notificaciones en infraestructura

Cms.Application/Interfaces/INotificationService.cs
namespace Cms.Application.Interfaces;

public interface INotificationService
{
    Task NotifyPostPublishedAsync(Guid postId, string title, string authorName, CancellationToken cancellationToken = default);
    Task NotifyCommentAddedAsync(Guid postId, string commentAuthor, string excerpt, CancellationToken cancellationToken = default);
}
Cms.Infrastructure/Realtime/SignalRNotificationService.cs
using Cms.Api.Hubs;
using Cms.Application.Interfaces;
using Microsoft.AspNetCore.SignalR;

namespace Cms.Infrastructure.Realtime;

public sealed class SignalRNotificationService : INotificationService
{
    private readonly IHubContext _hubContext;
    private readonly ILogger _logger;

    public SignalRNotificationService(
        IHubContext hubContext,
        ILogger logger)
    {
        _hubContext = hubContext;
        _logger = logger;
    }

    public async Task NotifyPostPublishedAsync(Guid postId, string title, string authorName, CancellationToken cancellationToken = default)
    {
        _logger.LogInformation("Notificando publicación del post {PostId}", postId);

        // Editores y admins reciben notificación de nuevos posts pendientes de revisión
        await _hubContext.Clients.Groups("editors", "admins")
            .PostPublished(postId, title, authorName);
    }

    public async Task NotifyCommentAddedAsync(Guid postId, string commentAuthor, string excerpt, CancellationToken cancellationToken = default)
    {
        _logger.LogInformation("Notificando comentario en el post {PostId}", postId);

        // Autores del post reciben notificación de nuevos comentarios
        await _hubContext.Clients.Groups("authors")
            .CommentAdded(postId, commentAuthor, excerpt);
    }
}

4.3. Handler de MediatR que dispara la notificación

Cms.Application/Posts/Commands/PublishPost/PublishPostCommandHandler.cs
using Cms.Application.Interfaces;
using Cms.Domain.Entities;
using Cms.Domain.Interfaces;
using MediatR;

namespace Cms.Application.Posts.Commands.PublishPost;

public sealed record PublishPostCommand(Guid PostId) : IRequest;

public sealed class PublishPostCommandHandler : IRequestHandler
{
    private readonly IPostRepository _postRepository;
    private readonly INotificationService _notifications;
    private readonly ILogger _logger;

    public PublishPostCommandHandler(
        IPostRepository postRepository,
        INotificationService notifications,
        ILogger logger)
    {
        _postRepository = postRepository;
        _notifications = notifications;
        _logger = logger;
    }

    public async Task Handle(PublishPostCommand request, CancellationToken cancellationToken)
    {
        var post = await _postRepository.GetByIdAsync(request.PostId, cancellationToken)
            ?? throw new NotFoundException($"Post {request.PostId} no encontrado");

        post.Publish();
        await _postRepository.SaveChangesAsync(cancellationToken);

        _logger.LogInformation("Post {PostId} publicado", request.PostId);

        // Notificación en tiempo real a editores y admins
        await _notifications.NotifyPostPublishedAsync(
            post.Id,
            post.Title,
            post.AuthorName,
            cancellationToken);
    }
}

    ¿Qué ocurre aquí?

    El handler de publicación cambia el estado del post, guarda y luego notifica. La infraestructura envía el mensaje a través del hub. El cliente JS recibe el mensaje si pertenece a los grupos editors o admins. En producción, Redis replica el mensaje entre instancias.

    5 · Buenas prácticas

    • Abstrae SignalR detrás de una interfaz de aplicación. La capa de aplicación no debe depender de ASP.NET Core SignalR.
    • Notifica después de persistir. No envíes notificaciones antes de confirmar que la operación de negocio fue exitosa.
    • Usa grupos en lugar de listas de connectionIds. SignalR gestiona los grupos de forma eficiente y los sincroniza con el backplane.
    • Segmenta las notificaciones. No envíes todo a Clients.All; envía solo a quienes necesitan la información.
    • Protege el hub con autorización. Las notificaciones suelen contener datos sensibles.
    • Configura Redis en producción. Un solo servidor en memoria no escala.
    • Registra las notificaciones enviadas. Útil para debugging y auditoría.

    No envíes todo el DTO

    Envía solo los datos necesarios en la notificación (id, título, autor). Si el cliente necesita más detalle, puede hacer una petición REST al API. Esto reduce el tamaño de los mensajes y mantiene el contrato estable.

    6 · Errores habituales

    6.1. Notificar desde el controlador

    Incorrecto
    [HttpPost("posts/{id}:publish")]
public async Task Publish(Guid id, [FromServices] IHubContext hub)
{
    await _mediator.Send(new PublishPostCommand(id));
    await hub.Clients.All.SendAsync("PostPublished", id);
    return NoContent();
}
    Correcto
    [HttpPost("posts/{id}:publish")]
public async Task Publish(Guid id)
{
    await _mediator.Send(new PublishPostCommand(id));
    return NoContent();
}

// La notificación se dispara desde el handler de aplicación a través de INotificationService

    6.2. Enviar a todos sin segmentar

    Incorrecto
    await _hubContext.Clients.All.PostPublished(postId, title, authorName);
    Correcto
    await _hubContext.Clients.Groups("editors", "admins")
    .PostPublished(postId, title, authorName);

    6.3. Olvidar el token en la conexión SignalR

    Incorrecto
    const connection = new signalR.HubConnectionBuilder()
    .withUrl("/hubs/notifications")
    .build();
    Correcto
    const connection = new signalR.HubConnectionBuilder()
    .withUrl("/hubs/notifications?access_token=" + encodeURIComponent(token))
    .build();

    6.4. No usar backplane en producción

    El siguiente código funciona en local pero fallará en Kubernetes con múltiples pods:

    Incorrecto
    builder.Services.AddSignalR(); // sin Redis

    La solución es la configuración condicional del ejemplo real.

{
    await _hubContext.Clients.User(authorId)
        .CommentAdded(postId, commentAuthor, excerpt);

    Cms.Application/Comments/Commands/AddComment/AddCommentCommandHandler.cs
    public async Task Handle(AddCommentCommand request, CancellationToken cancellationToken)
{
    var post = await _postRepository.GetByIdAsync(request.PostId, cancellationToken)
        ?? throw new NotFoundException("Post no encontrado");

    var comment = post.AddComment(request.Content, request.AuthorId, request.AuthorName);
    await _postRepository.SaveChangesAsync(cancellationToken);

    await _notifications.NotifyCommentAddedAsync(
        post.Id,
        request.AuthorName,
        request.Content[..Math.Min(100, request.Content.Length)],
        cancellationToken);

    await _notifications.NotifyAuthorOfCommentAsync(
        post.AuthorId,
        post.Id,
        request.AuthorName,
        request.Content[..Math.Min(100, request.Content.Length)],
        cancellationToken);

    return comment.Id;
}

    ¿Por qué usar Clients.User para el autor?

    El autor del post puede tener cualquier rol o incluso estar desconectado. Al usar el userId basado en NameIdentifier, SignalR envía la notificación a todas las conexiones activas de ese usuario, independientemente de sus roles.

    8 · Reto

    Reto: panel de actividad en tiempo real

    Implementa un hub adicional llamado ActivityHub que envíe a los administradores un resumen de actividad cada vez que se publica un post, se añade un comentario o se registra un usuario. El resumen debe incluir el tipo de evento, el timestamp y el usuario responsable. Asegúrate de que el backplane de Redis lo propague entre instancias y de que solo los usuarios con rol Admin reciban estos eventos.

    9 · Resumen

    • Integrar SignalR en el CMS mantiene la arquitectura limpia usando INotificationService en aplicación y SignalRNotificationService en infraestructura.
    • El hub se protege con [Authorize] y el token JWT se envía por query string en WebSockets.
    • Los usuarios se unen a grupos según sus roles para recibir notificaciones segmentadas.
    • Los handlers de MediatR disparan notificaciones después de persistir la operación.
    • Redis actúa como backplane en producción para escalar horizontalmente.
    • El cliente JavaScript se reconecta automáticamente y escucha eventos tipados.

    10 · Preguntas frecuentes

    ¿Por qué no poner el hub en la capa de aplicación?

    El hub es infraestructura web de ASP.NET Core. La capa de aplicación define la interfaz INotificationService y la infraestructura la implementa. Esto mantiene la regla de dependencias de Clean Architecture.

    ¿Qué pasa si el handler de MediatR notifica antes de guardar?

    El cliente podría recibir una notificación de un post que aún no existe en base de datos. Por eso notificamos después de SaveChangesAsync.

    ¿Cómo pruebo el hub sin un navegador?

    Puedes usar el cliente .NET de SignalR o escribir tests de integración con WebApplicationFactory y un cliente de SignalR. También puedes invocar directamente IHubContext en tests unitarios usando un TestHubContext mock.

    ¿Necesito un endpoint REST para obtener el historial?

    Sí. SignalR es para eventos en tiempo real; el historial debe consultarse por REST o GraphQL. No intentes reconstruir el historial a partir de notificaciones perdidas.

    ¿Puedo usar SignalR desde Minimal APIs?

    Sí, con app.MapHub<T>("/ruta"). La autenticación y autorización funcionan igual que con controladores.
