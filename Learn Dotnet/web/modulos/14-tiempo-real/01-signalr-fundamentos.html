SignalR: WebSockets en .NET

Módulo 14 · Tiempo real35 min

1 · Introducción

Hasta ahora nuestra API solo respondía cuando el cliente preguntaba. Pero muchas aplicaciones modernas necesitan que el servidor avise al cliente: un chat, un tablero en vivo, una notificación de nuevo pedido o un CMS que avise cuando alguien publica un artículo.

En esta lección aprenderemos SignalR, la librería de ASP.NET Core para comunicación en tiempo real. Veremos qué transportes usa (WebSockets, Server-Sent Events y Long Polling), cómo funciona un Hub y cómo enviar mensajes desde el servidor hacia los clientes conectados.

¿Qué problema resuelve?

SignalR abstrae la complejidad de mantener una conexión persistente entre navegador y servidor. En lugar de que el cliente haga polling cada segundo, el servidor empuja datos cuando ocurre algo. Es como pasar de "¿ya llegó?" cada cinco segundos a recibir un mensaje cuando el paquete realmente llega.

Errores típicos

  • Crear un HttpClient que hace polling constante en lugar de usar una conexión persistente.
  • Ignorar que SignalR elige el transporte automáticamente si WebSockets no está disponible.
  • Llamar a métodos del hub sin await, perdiendo errores de conexión.
  • Esperar que los mensajes persistan: SignalR es en tiempo real, no una cola de mensajes.

2 · Teoría

¿Qué es SignalR?

SignalR es una librería de ASP.NET Core que permite añadir funcionalidad en tiempo real a aplicaciones web. Soporta tres transportes y elige el mejor disponible automáticamente:

  • WebSockets: conexión bidireccional persistente sobre TCP. Es el más eficiente y el preferido.
  • Server-Sent Events (SSE): el servidor envía datos al cliente sobre una conexión HTTP persistente, pero el cliente no puede responder por ese canal.
  • Long Polling: el cliente mantiene una petición HTTP abierta hasta que el servidor tiene datos. Es el fallback más compatible pero menos eficiente.

Cómo negocia el transporte

Cuando un cliente de SignalR se conecta a /hubUri, el servidor y el cliente negocian qué transporte usar. El orden por defecto es WebSockets → SSE → Long Polling. Puedes forzar uno concreto, pero lo normal es dejar que SignalR decida.

El concepto de Hub

Un Hub es una clase que expone métodos que los clientes pueden llamar y que puede llamar a métodos en los clientes. Es el punto central de la comunicación.

  • Los clientes invocan métodos del hub como si fueran métodos remotos.
  • El hub usa Clients.All.SendAsync(...) para enviar un mensaje a todos los clientes.
  • Clients.Caller.SendAsync(...) responde solo al cliente que hizo la llamada.
  • Clients.Others.SendAsync(...) envía a todos menos al que llamó.

Regla mnemotécnica

SignalR es la opción por defecto en .NET para tiempo real en navegadores. Si necesitas control total del protocolo, usa WebSockets directamente. Si la comunicación es solo servidor → cliente y unidireccional, SSE puede ser más simple.

3 · Ejemplo mínimo

Crearemos una aplicación web con un hub de chat. El servidor reenviará cada mensaje a todos los clientes conectados.

# Creamos un proyecto web vacío
dotnet new web -n SignalRChatDemo -o SignalRChatDemo
cd SignalRChatDemo

# SignalR viene incluido en ASP.NET Core; no necesitamos NuGet extra
dotnet run --project .
Program.cs
using Microsoft.AspNetCore.SignalR;

var builder = WebApplication.CreateBuilder(args);

// Registramos SignalR en el contenedor de DI
builder.Services.AddSignalR();

var app = builder.Build();

// Servimos el HTML estático que contendrá el cliente JS
app.UseStaticFiles();
app.UseDefaultFiles();

// Mapeamos el hub en la ruta /chatHub
app.MapHub("/chatHub");

app.Run();

// Hub sencillo que recibe un mensaje y lo retransmite a todos
public sealed class ChatHub : Hub
{
    public async Task SendMessage(string user, string message)
    {
        // Clients.All apunta a todas las conexiones activas
        await Clients.All.SendAsync("ReceiveMessage", user, message);
    }
}

    ¿Qué ocurre aquí?

    El cliente establece una conexión persistente con /chatHub. Cuando escribe un mensaje, invoca SendMessage en el servidor. El hub llama a Clients.All.SendAsync("ReceiveMessage", ...) y todos los navegadores conectados reciben el mensaje.

    4 · Ejemplo real

    En una aplicación profesional no basta con retransmitir: necesitas logging, manejo de errores, contexto de usuario y opciones de serialización. Veamos un hub más realista.

    Program.cs
    using System.Text.Json;
using System.Text.Json.Serialization;
using Microsoft.AspNetCore.SignalR;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSignalR(options =>
{
    // Reintentos automáticos en el servidor si falla el envío
    options.EnableDetailedErrors = builder.Environment.IsDevelopment();
    options.MaximumReceiveMessageSize = 64 * 1024; // 64 KB
    options.StreamBufferCapacity = 50;
})
.AddJsonProtocol(options =>
{
    // Usamos System.Text.Json con camelCase para que el cliente JS sea coherente
    options.PayloadSerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase;
    options.PayloadSerializerOptions.DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull;
});

builder.Services.AddSingleton();

var app = builder.Build();
app.UseStaticFiles();
app.UseAuthentication();
app.UseAuthorization();

app.MapHub("/hubs/notifications")
   .RequireAuthorization();

app.Run();

// Proveedor que identifica usuarios por claim "sub" (email o id)
public sealed class EmailBasedUserIdProvider : IUserIdProvider
{
    public string? GetUserId(HubConnectionContext connection)
        => connection.User?.FindFirst("sub")?.Value;
}

public sealed class NotificationHub : Hub
{
    private readonly ILogger _logger;

    public NotificationHub(ILogger logger)
    {
        _logger = logger;
    }

    public override async Task OnConnectedAsync()
    {
        _logger.LogInformation("Conexión {ConnectionId} establecida", Context.ConnectionId);
        await Clients.Caller.ReceiveNotification("Bienvenido", "Conectado al hub de notificaciones.");
        await base.OnConnectedAsync();
    }

    public override async Task OnDisconnectedAsync(Exception? exception)
    {
        _logger.LogInformation("Conexión {ConnectionId} cerrada: {Reason}",
            Context.ConnectionId, exception?.Message ?? "sin error");
        await base.OnDisconnectedAsync(exception);
    }

    public async Task Broadcast(string title, string body)
    {
        await Clients.All.ReceiveNotification(title, body);
    }
}

// Interfaz tipada que define los métodos disponibles en el cliente
public interface INotificationClient
{
    Task ReceiveNotification(string title, string body);
}

    Hub tipado

    Usar Hub<T> con una interfaz de cliente permite que el compilador verifique los métodos que envías al cliente. Es más seguro que las cadenas mágicas de SendAsync.

    5 · Buenas prácticas

    • No hagas trabajo pesado dentro del hub. El hub debe recibir, validar y reenviar. La lógica de negocio debe estar en servicios de aplicación o en handlers de MediatR.
    • Usa Hub<T> tipado para detectar errores en los métodos del cliente en tiempo de compilación.
    • Configura límites de tamaño de mensaje para evitar ataques de memoria.
    • Registra conexiones y desconexiones con ILogger; facilita mucho el debugging.
    • Autoriza los hubs si la información es sensible. Un hub sin autorización expone datos a cualquiera que se conecte.
    • Maneja errores del cliente con connection.onclose y reintentos (withAutomaticReconnect).

    SignalR no es una base de datos

    Nunca uses SignalR como único mecanismo de entrega de mensajes críticos. Si un cliente está desconectado, no recibirá nada. Para garantías de entrega, combina con una cola (RabbitMQ, Azure Service Bus, Hangfire, etc.).

    6 · Errores habituales

    6.1. Olvidar que los métodos del hub son asíncronos

    Incorrecto
    public void SendMessage(string user, string message)
{
    Clients.All.SendAsync("ReceiveMessage", user, message);
}
    Correcto
    public async Task SendMessage(string user, string message)
{
    await Clients.All.SendAsync("ReceiveMessage", user, message);
}

    El problema: si no haces await, los errores se pierden y la tarea puede no completarse antes de que el servidor libere la conexión.

    6.2. Mapear el hub antes de UseStaticFiles sin importar

    El orden entre UseStaticFiles y MapHub no es crítico porque operan en rutas distintas, pero sí lo es respecto a autenticación: si pones MapHub antes de UseAuthentication, Context.User estará vacío.

    6.3. Cliente JS sin manejo de errores

    Incorrecto
    connection.start();
    Correcto
    async function start() {
    try {
        await connection.start();
        console.log("Conectado");
    } catch (err) {
        console.error("Error de conexión:", err);
        setTimeout(start, 5000);
    }
}
connection.onclose(start);
start();

    7 · Ejercicio guiado

    Crea un hub de "estado del sistema" que envíe la hora del servidor a todos los clientes cada 5 segundos mientras haya al menos un cliente conectado.

    TimeHub.cs
    using Microsoft.AspNetCore.SignalR;

public sealed class TimeHub : Hub
{
    private static int _connectedCount;

    public override async Task OnConnectedAsync()
    {
        Interlocked.Increment(ref _connectedCount);
        await Clients.Caller.ShowTime($"Conectado. Clientes activos: {_connectedCount}");
        await base.OnConnectedAsync();
    }

    public override async Task OnDisconnectedAsync(Exception? exception)
    {
        Interlocked.Decrement(ref _connectedCount);
        await base.OnDisconnectedAsync(exception);
    }
}

public interface ITimeClient
{
    Task ShowTime(string message);
}
    TimeHostedService.cs
    public sealed class TimeHostedService : BackgroundService
{
    private readonly IServiceProvider _provider;

    public TimeHostedService(IServiceProvider provider)
    {
        _provider = provider;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);

            // IHubContext permite enviar mensajes desde fuera de un hub
            using var scope = _provider.CreateScope();
            var hubContext = scope.ServiceProvider.GetRequiredService>();
            await hubContext.Clients.All.ShowTime($"Hora del servidor: {DateTime.UtcNow:O}");
        }
    }
}

    ¿Por qué IHubContext?

    Los servicios en segundo plano no son hubs, pero pueden inyectar IHubContext<THub, TClient> para enviar mensajes a los clientes conectados. Recuerda crear un scope si tu servicio es singleton.

    9 · Resumen

    • SignalR permite comunicación en tiempo real entre servidor y clientes.
    • Soporta WebSockets, Server-Sent Events y Long Polling; elige el mejor disponible automáticamente.
    • El Hub es la clase central que recibe llamadas del cliente y envía mensajes a los clientes.
    • Clients.All, Clients.Caller y Clients.Others son los selectores básicos.
    • Usa Hub<T> tipado para seguridad en tiempo de compilación.
    • IHubContext permite enviar mensajes desde servicios que no son hubs.

    10 · Preguntas frecuentes

    ¿SignalR siempre usa WebSockets?

    No. Intenta WebSockets primero; si no está disponible (proxy antiguo, firewall, etc.) usa SSE o Long Polling. Puedes forzar uno con .withTransport(signalR.HttpTransportType.WebSockets).

    ¿Puedo usar SignalR con clientes que no sean navegadores?

    Sí. Existen clientes oficiales para .NET, Java y JavaScript. También puedes consumir el protocolo de SignalR desde cualquier lenguaje, aunque es más trabajo.

    ¿SignalR escala horizontalmente?

    Sí, pero necesitas un backplane (Redis, Azure SignalR Service) para que los mensajes lleguen a todos los servidores. Sin backplane, un cliente en el servidor A no recibe mensajes enviados desde el servidor B.

    ¿Los mensajes de SignalR se pierden si el cliente está offline?

    Sí, por defecto no hay persistencia. Si necesitas garantía de entrega, usa una cola de mensajes o el modo persistente de Azure SignalR Service.

    ¿Puedo pasar objetos complejos en los métodos?

    Sí, siempre que sean serializables con System.Text.Json (por defecto) o MessagePack (si instalas el paquete correspondiente). Evita ciclos de referencia.
