Code-First y migraciones

Módulo 7 · Entity Framework Core35 min

1. Introducción

Code-First nos permite diseñar el dominio en C# y dejar que EF Core genere y evolucione el esquema de la base de datos. Las migraciones son el mecanismo que transforma esos cambios en scripts SQL versionados.

En esta lección veremos:

  • Configuración de entidades con Fluent API y Data Annotations.
  • El ciclo de vida de OnModelCreating.
  • Comandos de migraciones: add, update, remove, script, bundle.
  • Estrategias para aplicar migraciones en producción.

2. Teoría

2.1 Configuración de entidades

EF Core ofrece dos formas de configurar el mapeo objeto-relacional:

  • Data Annotations: atributos sobre las propiedades de la entidad. Rápidas, pero ensucian el dominio.
  • Fluent API: configuración en OnModelCreating. Más completa y mantiene las entidades limpias.
Recomendación del curso: usar Fluent API en el DbContext y dejar las entidades de dominio libres de dependencias de infraestructura.

2.2 Data Annotations (para prototipos rápidos)

public class Post
{
    [Key]
    public int Id { get; set; }

    [Required]
    [MaxLength(200)]
    public string Title { get; set; } = string.Empty;

    [Column("body", TypeName = "text")]
    public string Content { get; set; } = string.Empty;
}

2.3 Fluent API (recomendado para producción)

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Post>(entity =>
    {
        entity.ToTable("posts", "cms");
        entity.HasKey(p => p.Id);
        entity.Property(p => p.Title)
              .HasColumnName("title")
              .HasMaxLength(200)
              .IsRequired();
        entity.Property(p => p.Content)
              .HasColumnName("body")
              .HasColumnType("text");
        entity.Property(p => p.CreatedAt)
              .HasDefaultValueSql("now()");
    });
}

2.4 ¿Qué es una migración?

Una migración es una clase de C# que contiene dos métodos:

  • Up(): aplica los cambios al esquema.
  • Down(): revierte los cambios.

EF Core compara el modelo actual con el snapshot de la última migración y genera las diferencias. También genera un archivo SQL con script.

2.5 Comandos esenciales

ComandoPropósito
dotnet ef migrations add InitialCreateCrea una migración con los cambios actuales.
dotnet ef database updateAplica las migraciones pendientes a la base de datos.
dotnet ef migrations removeElimina la última migración si no se ha aplicado.
dotnet ef migrations scriptGenera un script SQL con todas las migraciones.
dotnet ef migrations bundleCrea un ejecutable que aplica las migraciones.

2.6 Producción: migraciones seguras vs peligrosas

Aplicar migraciones directamente desde la aplicación (context.Database.Migrate()) es conveniente para desarrollo, pero en producción puede causar problemas:

  • La aplicación necesita permisos de DDL (CREATE, ALTER, DROP).
  • Varias instancias pueden intentar migrar simultáneamente.
  • Los despliegues automatizados se vuelven difíciles de auditar.

La práctica profesional es generar un script idempotente o un bundle y ejecutarlo en el pipeline de despliegue antes de iniciar la aplicación.

3. Ejemplo mínimo

Partimos de un proyecto con un modelo mínimo. Instalamos la herramienta CLI de EF Core y creamos la primera migración.

# Instalar la herramienta global de EF Core (si no la tienes)
dotnet tool install --global dotnet-ef

# Asegurar que está actualizada
dotnet tool update --global dotnet-ef

# Crear una migración inicial
dotnet ef migrations add InitialCreate --project src/MiApp --startup-project src/MiApp

# Aplicar la migración
dotnet ef database update --project src/MiApp --startup-project src/MiApp

# Ver el SQL generado
dotnet ef migrations script --project src/MiApp --startup-project src/MiApp
// MiApp.csproj
<ItemGroup>
  <PackageReference Include="Npgsql.EntityFrameworkCore.PostgreSQL" Version="8.0.0" />
  <PackageReference Include="Microsoft.EntityFrameworkCore.Design" Version="8.0.0">
    <PrivateAssets>all</PrivateAssets>
    <IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>
  </PackageReference>
</ItemGroup>

4. Ejemplo real

Configuramos un proyecto ASP.NET Core con EF Core y PostgreSQL. Separamos la cadena de conexión en appsettings.json y usamos un bundle idempotente para producción.

// Program.cs
var connectionString = builder.Configuration
    .GetConnectionString("Default")!;

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseNpgsql(connectionString, npgsql =>
        npgsql.MigrationsAssembly("MiApp")));

// appsettings.json
{
  "ConnectionStrings": {
    "Default": "Host=localhost;Database=cmsdb;Username=cms;Password=secret"
  }
}

// Data/DesignTimeDbContextFactory.cs
// Necesario si el DbContext no está en el assembly de inicio o requiere parámetros complejos.
public class DesignTimeDbContextFactory : IDesignTimeDbContextFactory<AppDbContext>
{
    public AppDbContext CreateDbContext(string[] args)
    {
        var optionsBuilder = new DbContextOptionsBuilder<AppDbContext>();
        optionsBuilder.UseNpgsql("Host=localhost;Database=cmsdb;Username=cms;Password=secret");
        return new AppDbContext(optionsBuilder.Options);
    }
}
# Crear una migración para añadir un índice
dotnet ef migrations add AddPostIndex --project src/MiApp

# Generar un script idempotente desde la migración cero hasta la última
dotnet ef migrations script 0 AddPostIndex --idempotent --output migrate.sql

# Crear un bundle ejecutable (ideal para pipelines de CI/CD)
dotnet ef migrations bundle --self-contained -r linux-x64 --output efbundle

# Ejecutar el bundle en producción
./efbundle --connection "Host=prod;Database=cmsdb;Username=cms;Password=secret"

5. Buenas prácticas

  • Usa Fluent API para todo el mapeo real: es más completo y mantenible que Data Annotations.
  • Revisa las migraciones antes de aplicarlas: abre el archivo generado y verifica que los cambios sean correctos.
  • No modifiques archivos de migración ya aplicados: crea una nueva migración con los ajustes.
  • Genera scripts idempotentes para producción: permiten ejecutar la migración varias veces sin duplicar objetos.
  • Usa bundles cuando no puedas confiar en el SDK: en producción basta con el ejecutable.
  • Especifica el MigrationsAssembly si separas el DbContext del proyecto de inicio.
  • Versiona los archivos de migración: forman parte del código fuente.

6. Errores habituales

Error 1: Aplicar migraciones desde el código de la aplicación en producción

// ❌ Riesgoso: la app necesita permisos DDL y puede competir con otras instancias.
app.Services.CreateScope().ServiceProvider
    .GetRequiredService<AppDbContext>().Database.Migrate();

En su lugar, ejecuta el script o el bundle como paso del despliegue.

Error 2: Eliminar una migración ya aplicada

Si la base de datos ya conoce la migración, dotnet ef migrations remove fallará o dejará el estado inconsistente. En ese caso, crea una nueva migración que revierta los cambios.

Error 3: Mezclar Data Annotations y Fluent API sin coherencia

Ambos se combinan, pero si configuras lo mismo en ambos lugares con valores distintos, gana Fluent API. Prefere un solo estilo para evitar sorpresas.

Error 4: Olvidar el paquete de diseño

El paquete Microsoft.EntityFrameworkCore.Design es necesario para que los comandos de la CLI generen migraciones. No se despliega en producción si se configura con PrivateAssets.

7. Ejercicio guiado

Crea un proyecto de consola con un modelo Customer y un Order:

  1. Define Customer con Id, Name y Email.
  2. Define Order con Id, OrderDate y Total.
  3. Configura ambos con Fluent API: nombres de tabla, longitudes máximas y tipos de columna.
  4. Agrega el paquete de PostgreSQL y el paquete de diseño.
  5. Crea una migración llamada InitialSchema.
  6. Genera el script SQL idempotente y revisa el contenido.
modelBuilder.Entity<Customer>(entity =>
{
    entity.ToTable("customers", "sales");
    entity.HasKey(c => c.Id);
    entity.Property(c => c.Name).HasMaxLength(150).IsRequired();
    entity.Property(c => c.Email).HasMaxLength(255).IsRequired();
    entity.HasIndex(c => c.Email).IsUnique();
});

modelBuilder.Entity<Order>(entity =>
{
    entity.ToTable("orders", "sales");
    entity.HasKey(o => o.Id);
    entity.Property(o => o.Total).HasPrecision(18, 2);
    entity.Property(o => o.OrderDate).HasDefaultValueSql("now()");
});

8. Reto

Añade una propiedad Phone a Customer y una migración llamada AddCustomerPhone. Después crea un bundle de migraciones para Linux x64 y un script SQL que solo incluya las migraciones desde InitialSchema hasta AddCustomerPhone.

Investiga qué es un script idempotente y cuándo es obligatorio usarlo.

9. Resumen

  • Code-First define el dominio en C# y evoluciona el esquema con migraciones.
  • Fluent API es preferible a Data Annotations para mantener el dominio limpio.
  • dotnet ef migrations add crea el código de migración; update lo aplica.
  • En producción se usan scripts SQL o bundles, no EnsureCreated ni Migrate() desde la app.
  • Revisar siempre las migraciones generadas antes de versionarlas.

10. Preguntas frecuentes

¿Qué pasa si dos desarrolladores crean migraciones simultáneamente?

EF Core genera un snapshot del modelo. Si hay conflictos, se resuelven en el control de versiones. El orden de las migraciones importa, así que hay que coordinar las ramas.

¿Puedo usar migraciones sin conexión a la base de datos?

Para crear migraciones no necesitas conexión. Para aplicar update o generar script sí necesitas la cadena de conexión.

¿Cómo hago una migración vacía para datos iniciales?

Usa dotnet ef migrations add SeedData y escribe SQL o usa migrationBuilder.Sql("...") en los métodos Up y Down.

¿Qué es un bundle de migraciones?

Es un ejecutable autocontenido que aplica las migraciones. Útil cuando no se quiere instalar el SDK en el servidor de destino.

¿Puedo renombrar una migración?

Sí, pero no es recomendable si ya está aplicada. Renombrar cambia la clase y el archivo, pero la fila en la tabla __EFMigrationsHistory sigue con el nombre original, lo que puede causar inconsistencias.
