Transacciones y concurrencia optimista

Módulo 7 · Entity Framework Core30 min

1 · Introducción

Cuando varios usuarios o procesos trabajan sobre los mismos datos, aparecen dos problemas: cómo garantizar que un conjunto de operaciones se aplique de forma atómica y cómo evitar que una actualización sobrescriba los cambios de otro usuario sin saberlo. En esta lección aprenderemos transacciones y concurrencia optimista.

Veremos:

  • SaveChanges como transacción implícita.
  • Transacciones explícitas con IDbContextTransaction.
  • Interceptores de EF Core.
  • Concurrencia optimista con RowVersion o Timestamp.
  • Manejo de DbUpdateConcurrencyException.

2 · Teoría

2.1 SaveChanges como transacción

Por defecto, SaveChanges envuelve todas las operaciones en una única transacción. Si alguna falla, se hace ROLLBACK. Esto es fundamental para mantener la integridad.

context.Posts.Add(post1);
context.Posts.Add(post2);
await context.SaveChangesAsync(); // Todo o nada.

2.2 Transacciones explícitas

A veces necesitas agrupar varios SaveChanges, ejecutar SQL directo o coordinar operaciones externas. Para eso usa BeginTransactionAsync.

await using var transaction = await context.Database.BeginTransactionAsync();

try
{
    context.Posts.Add(post);
    await context.SaveChangesAsync();

    await context.Database.ExecuteSqlRawAsync(
        "INSERT INTO audit_log (entity, action) VALUES ({0}, {1})",
        "Post", "Created");

    await transaction.CommitAsync();
}
catch
{
    await transaction.RollbackAsync();
    throw;
}
Importante: no mantengas transacciones abiertas durante operaciones de red o largas esperas. Bloqueas recursos y reduces la escalabilidad.

2.3 Interceptores

Los interceptores permiten ejecutar código antes o después de operaciones de EF Core de forma transversal. Ejemplos: auditoría, lógica de tenancy, enriquecimiento de consultas.

public class AuditingInterceptor : SaveChangesInterceptor
{
    public override async ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        var context = eventData.Context;
        if (context is null) return result;

        foreach (var entry in context.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State == EntityState.Added)
                entry.Entity.CreatedAt = DateTime.UtcNow;

            if (entry.State == EntityState.Modified)
                entry.Entity.UpdatedAt = DateTime.UtcNow;
        }

        return await base.SavingChangesAsync(eventData, result, cancellationToken);
    }
}

// Registro en Program.cs
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseNpgsql(connectionString)
           .AddInterceptors(new AuditingInterceptor()));

2.4 Concurrencia optimista

La concurrencia optimista asume que los conflictos son poco frecuentes. En lugar de bloquear filas, se añade una columna de versión. Al guardar, EF Core verifica que la versión no haya cambiado. Si cambió, lanza DbUpdateConcurrencyException.

public class Post
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;

    [Timestamp]
    public byte[] RowVersion { get; set; } = null!;
}
// Fluent API
modelBuilder.Entity<Post>()
    .Property(p => p.RowVersion)
    .IsRowVersion();

En PostgreSQL, el equivalente a rowversion de SQL Server es una columna de tipo xid o una propiedad de control manual. Npgsql usa ConcurrencyCheck o una columna de timestamp generada.

// PostgreSQL con Npgsql: usa una propiedad de versión que el proveedor maneja.
modelBuilder.Entity<Post>()
    .Property(p => p.RowVersion)
    .IsConcurrencyToken()
    .ValueGeneratedOnAddOrUpdate();

2.5 Manejo de DbUpdateConcurrencyException

Cuando ocurre un conflicto, debes decidir: recargar los valores del cliente, del servidor o abortar la operación.

public async Task UpdatePostAsync(int id, PostUpdateDto dto)
{
    var post = await _context.Posts.FindAsync(id);
    if (post is null) throw new NotFoundException();

    post.Title = dto.Title;

    try
    {
        await _context.SaveChangesAsync();
    }
    catch (DbUpdateConcurrencyException ex)
    {
        var entry = ex.Entries.Single();
        var databaseValues = await entry.GetDatabaseValuesAsync();

        if (databaseValues is null)
        {
            // La entidad fue eliminada por otro usuario.
            throw new ConflictException("El post fue eliminado por otro usuario.");
        }

        // Recargar valores del servidor y perder los del cliente.
        entry.OriginalValues.SetValues(databaseValues);
        entry.Reload();

        // O bien: fusionar cambios manualmente.
        throw new ConflictException("El post fue modificado por otro usuario. Recarga y vuelve a intentarlo.");
    }
}

3 · Ejemplo mínimo

Transacción explícita que actualiza un post y registra en auditoría.

await using var transaction = await context.Database.BeginTransactionAsync();

try
{
    var post = await context.Posts.FindAsync(1);
    post!.Title = "Nuevo título";
    await context.SaveChangesAsync();

    await context.Database.ExecuteSqlRawAsync(
        "INSERT INTO audit_log (action, entity_id) VALUES ('update', 1)");

    await transaction.CommitAsync();
    Console.WriteLine("Transacción confirmada.");
}
catch (Exception ex)
{
    await transaction.RollbackAsync();
    Console.WriteLine($"Error: {ex.Message}");
}

4 · Ejemplo real

Implementación de un interceptor de auditoría y un handler CQRS con control de concurrencia para el CMS.

// Domain/IAuditable.cs
public interface IAuditable
{
    DateTime CreatedAt { get; set; }
    DateTime? UpdatedAt { get; set; }
}

// Domain/Post.cs
public class Post : IAuditable
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;
    public string Content { get; set; } = string.Empty;
    public DateTime CreatedAt { get; set; }
    public DateTime? UpdatedAt { get; set; }
    public byte[] RowVersion { get; set; } = null!;
}

// Data/Configurations/PostConfiguration.cs
public void Configure(EntityTypeBuilder<Post> entity)
{
    entity.Property(p => p.RowVersion)
          .IsConcurrencyToken()
          .ValueGeneratedOnAddOrUpdate();
}

// Data/Interceptors/AuditingInterceptor.cs
public class AuditingInterceptor : SaveChangesInterceptor
{
    public override async ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        var context = eventData.Context;
        if (context is null) return result;

        var now = DateTime.UtcNow;
        foreach (var entry in context.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State == EntityState.Added)
                entry.Entity.CreatedAt = now;

            if (entry.State == EntityState.Modified)
                entry.Entity.UpdatedAt = now;
        }

        return await base.SavingChangesAsync(eventData, result, cancellationToken);
    }
}

// Application/Handlers/UpdatePostHandler.cs
public async Task Handle(UpdatePostCommand request, CancellationToken cancellationToken)
{
    var post = await _context.Posts.FindAsync(new object[] { request.Id }, cancellationToken);
    if (post is null) throw new NotFoundException();

    post.Title = request.Title;
    post.Content = request.Content;

    try
    {
        await _context.SaveChangesAsync(cancellationToken);
    }
    catch (DbUpdateConcurrencyException)
    {
        throw new ConflictException("El post fue modificado o eliminado por otro usuario.");
    }
}

5 · Buenas prácticas

  • Confía en SaveChanges para transacciones simples: no uses transacciones explícitas si no las necesitas.
  • Mantén las transacciones cortas: no invoques servicios externos ni hagas I/O dentro de una transacción.
  • Usa interceptores para cross-cutting concerns: auditoría, tenancy, soft deletes, etc.
  • Implementa concurrencia optimista en entidades críticas: evita sobrescrituras silenciosas.
  • Decide una política ante conflictos: ¿recargas, ganas el cliente, gana el servidor o notificas al usuario?
  • Loggea los conflictos de concurrencia: son indicadores de diseño o de carga inesperada.

6 · Errores habituales

Error 1: Llamar a SaveChanges dentro de una transacción sin necesidad

Varios SaveChanges en una transacción explícita son válidos cuando coordinas operaciones, pero intenta agrupar todo en uno si es posible.

Error 2: Mantener transacciones abiertas durante I/O

Una transacción abierta mientras llamas a un servicio externo bloquea la fila o la tabla. Esto degrada el rendimiento y aumenta el riesgo de deadlocks.

Error 3: No capturar DbUpdateConcurrencyException

Si usas tokens de concurrencia, cualquier conflicto lanzará una excepción. Si no la manejas, el usuario verá un error 500 genérico.

Error 4: Usar RowVersion con PostgreSQL como en SQL Server

SQL Server tiene rowversion nativo. PostgreSQL no. Con Npgsql usa IsConcurrencyToken + ValueGeneratedOnAddOrUpdate, típicamente con una columna de timestamp o xid.

7 · Ejercicio guiado

Implementa un interceptor que registre automáticamente el usuario que crea o modifica una entidad.

  1. Crea una interfaz IUserAuditable con CreatedBy y UpdatedBy.
  2. Implementa un interceptor que reciba el usuario actual por constructor.
  3. En SavingChangesAsync, rellena los campos según el estado de la entidad.
  4. Registra el interceptor en el contenedor de DI.
public class UserAuditingInterceptor : SaveChangesInterceptor
{
    private readonly ICurrentUser _currentUser;
    public UserAuditingInterceptor(ICurrentUser currentUser) => _currentUser = currentUser;

    public override async ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        var context = eventData.Context;
        if (context is null) return result;

        var userId = _currentUser.UserId;
        foreach (var entry in context.ChangeTracker.Entries<IUserAuditable>())
        {
            if (entry.State == EntityState.Added)
                entry.Entity.CreatedBy = userId;

            if (entry.State == EntityState.Modified)
                entry.Entity.UpdatedBy = userId;
        }

        return await base.SavingChangesAsync(eventData, result, cancellationToken);
    }
}

8 · Reto

Implementa un endpoint que permita publicar un post solo si no ha sido modificado por otro usuario desde que se cargó. Añade un token de concurrencia y devuelve un 409 Conflict con los valores actuales del servidor cuando haya un conflicto.

9 · Resumen

  • SaveChanges es una transacción implícita: todo o nada.
  • Las transacciones explícitas permiten coordinar múltiples operaciones.
  • Los interceptores ejecutan lógica transversal antes o después de guardar.
  • La concurrencia optimista detecta conflictos sin bloquear filas.
  • DbUpdateConcurrencyException debe manejarse con una política clara.

10 · Preguntas frecuentes

¿Puedo usar transacciones entre múltiples DbContext?

Sí, compartiendo la misma conexión y transacción de ADO.NET. Usa context.Database.UseTransaction con la transacción del primer contexto.

¿SaveChanges siempre crea una transacción?

Sí, a menos que desactives el cambio de tracking o llames a SaveChanges sin entidades pendientes. También puedes controlar el nivel de aislamiento.

¿Qué pasa si no manejo DbUpdateConcurrencyException?

La excepción se propagará y normalmente se convertirá en un error 500. Deberías transformarla en un 409 Conflict con un mensaje útil.

¿La concurrencia optimista es suficiente para todos los casos?

No. Para operaciones críticas con alta contención, considera concurrencia pesimista (locks) o patrones de colas.

¿Puedo usar interceptores con DI?

Sí, los interceptores pueden recibir dependencias por constructor. Regístralos como instancias o resuélvelos desde el service provider.
