¿Qué es un ORM? DbContext y DbSet

Módulo 7 · Entity Framework Core30 min

1. Introducción

En esta lección aprenderemos qué es un ORM (Object-Relational Mapper) y por qué Entity Framework Core es la opción más usada en el ecosistema .NET. No solo veremos cómo escribir consultas; entenderemos qué papel juegan DbContext y DbSet<T> en el diseño de una aplicación profesional.

Veremos:

  • El problema de mapear objetos a tablas relacionales.
  • La diferencia entre ADO.NET clásico y EF Core.
  • DbContext como unidad de trabajo y DbSet como repositorio de entidades.
  • Code-First vs Database-First y una primera visión de las migraciones.
Objetivo: al terminar, serás capaz de crear un DbContext, configurar un DbSet y entender el ciclo de vida básico de EF Core.

2. Teoría

2.1 ¿Qué es un ORM?

Las bases de datos relacionales almacenan datos en filas y columnas. Los programas orientados a objetos trabajan con clases, propiedades y relaciones. Esa diferencia de modelos se llama impedancia objeto-relacional.

Un ORM es una capa de software que traduce automáticamente entre ambos mundos. Permite:

  • Definir modelos como clases de C#.
  • Consultar datos con LINQ en lugar de SQL manual.
  • Rastrear cambios y persistirlos con SaveChanges.
Importante: EF Core no reemplaza SQL. Es una capa de abstracción, pero saber SQL sigue siendo imprescindible para optimizar y depurar.

2.2 ADO.NET vs EF Core

ADO.NET es la API de acceso a datos de .NET. Trabaja con SqlConnection, SqlCommand, SqlDataReader y requiere escribir SQL manualmente, abrir conexiones y mapear filas a objetos.

// ADO.NET: todo manual, propenso a errores y SQL injection si no se parametriza.
using var connection = new SqlConnection(connectionString);
await connection.OpenAsync();
using var command = new SqlCommand("SELECT * FROM Posts WHERE Id = @id", connection);
command.Parameters.AddWithValue("@id", id);
using var reader = await command.ExecuteReaderAsync();
while (await reader.ReadAsync())
{
    var post = new Post
    {
        Id = reader.GetInt32(0),
        Title = reader.GetString(1)
    };
    posts.Add(post);
}

EF Core automatiza ese mapeo, genera SQL parametrizado y abstrae la conexión. No obstante, sigue usando ADO.NET por debajo.

2.3 DbContext: la unidad de trabajo

DbContext es el corazón de EF Core. Sus responsabilidades son:

  • Administración de la conexión a la base de datos.
  • Configuración del modelo (OnModelCreating).
  • Seguimiento de cambios en las entidades (change tracking).
  • Coordinación de la persistencia con SaveChanges.
  • Resolución de DbSet<T> como puertas de entrada para consultas.

Conceptualmente, DbContext implementa el patrón Unit of Work: agrupa un conjunto de operaciones y las aplica de forma atómica.

// Un DbContext es una unidad de trabajo: agrupa operaciones y las guarda juntas.
public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Post> Posts => Set<Post>();
    public DbSet<Category> Categories => Set<Category>();
}

2.4 DbSet: repositorio de entidades

DbSet<T> representa una tabla o vista. Expone una colección de entidades que se puede consultar con LINQ. Aunque suene trivial, es importante entender que un DbSet no es una lista en memoria: es una consulta parametrizable que se traduce a SQL en el momento de ejecución.

2.5 Code-First vs Database-First

EnfoqueDescripciónCuándo usarlo
Code-FirstDefinimos las entidades en C# y EF Core genera el esquema de la base de datos.Proyectos nuevos, control total del dominio, equipos que dominan C#.
Database-FirstPartimos de una base de datos existente y generamos las entidades con Scaffold-DbContext.Bases de datos legadas, DBA externos, evolución controlada por SQL.

En este curso usamos Code-First porque queremos un dominio limpio y evolucionar el esquema con migraciones controladas por código.

3. Ejemplo mínimo

Creamos un proyecto de consola que usa EF Core en memoria. No requiere PostgreSQL ni SQL Server y sirve para entender los conceptos.

# 1. Crear un proyecto de consola
mkdir m07-ejemplo-orm
cd m07-ejemplo-orm
dotnet new console

# 2. Agregar EF Core en memoria
dotnet add package Microsoft.EntityFrameworkCore.InMemory --version 8.0.0

# 3. Ejecutar
dotnet run
// Program.cs
using Microsoft.EntityFrameworkCore;

var builder = new DbContextOptionsBuilder<AppDbContext>();
builder.UseInMemoryDatabase("DemoDb");

await using var context = new AppDbContext(builder.Options);

context.Posts.Add(new Post { Id = 1, Title = "Hola EF Core" });
await context.SaveChangesAsync();

var post = await context.Posts.FirstAsync(p => p.Id == 1);
Console.WriteLine($"Post: {post.Title}");

public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions options) : base(options) { }
    public DbSet<Post> Posts => Set<Post>();
}

public class Post
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;
}

Este ejemplo:

  • Crea un DbContext con una base de datos en memoria.
  • Agrega una entidad y la persiste con SaveChangesAsync.
  • Consulta la entidad con LINQ y materialización asíncrona.

4. Ejemplo real

Ahora usamos PostgreSQL con Npgsql, separando el modelo de la configuración. La estructura refleja lo que usaremos en el CMS.

# Agregar el proveedor de PostgreSQL
dotnet add package Npgsql.EntityFrameworkCore.PostgreSQL --version 8.0.0
// Domain/Post.cs
// Entidad de dominio con propiedades básicas. Sin dependencias de EF Core.
public class Post
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;
    public string Content { get; set; } = string.Empty;
    public DateTime PublishedAt { get; set; }
    public int CategoryId { get; set; }
    public Category Category { get; set; } = null!;
}

public class Category
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public List<Post> Posts { get; set; } = new();
}

// Data/AppDbContext.cs
// DbContext del proyecto real. Separa la configuración del modelo en OnModelCreating.
public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Post> Posts => Set<Post>();
    public DbSet<Category> Categories => Set<Category>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Post>(entity =>
        {
            entity.ToTable("posts", "cms");
            entity.HasKey(p => p.Id);
            entity.Property(p => p.Title).HasMaxLength(200).IsRequired();
            entity.Property(p => p.Content).HasColumnType("text");
            entity.HasOne(p => p.Category)
                  .WithMany(c => c.Posts)
                  .HasForeignKey(p => p.CategoryId);
        });

        modelBuilder.Entity<Category>(entity =>
        {
            entity.ToTable("categories", "cms");
            entity.HasKey(c => c.Id);
            entity.Property(c => c.Name).HasMaxLength(100).IsRequired();
        });
    }
}

// Program.cs
var connectionString = "Host=localhost;Database=demo;Username=postgres;Password=secret";
var builder = new DbContextOptionsBuilder<AppDbContext>();
builder.UseNpgsql(connectionString);

await using var context = new AppDbContext(builder.Options);
await context.Database.EnsureCreatedAsync();

var category = new Category { Name = "Tecnología" };
context.Categories.Add(category);
await context.SaveChangesAsync();

context.Posts.Add(new Post
{
    Title = "Introducción a EF Core",
    Content = "Contenido del post...",
    PublishedAt = DateTime.UtcNow,
    CategoryId = category.Id
});
await context.SaveChangesAsync();

var posts = await context.Posts
    .Include(p => p.Category)
    .Where(p => p.Category.Name == "Tecnología")
    .ToListAsync();

foreach (var p in posts)
    Console.WriteLine($"{p.Title} en {p.Category.Name}");

5. Buenas prácticas

  • Separar dominio de persistencia: las entidades de dominio no deben depender de atributos de EF Core si el proyecto lo permite. Usa Fluent API en OnModelCreating.
  • Usar Code-First para proyectos nuevos: mantienes el control del esquema y evolucionas con migraciones.
  • Registrar el DbContext con el lifetime adecuado: normalmente Scoped en ASP.NET Core.
  • Evitar EnsureCreatedAsync en producción: es útil para prototipos, pero en producción se usan migraciones.
  • Preferir SaveChangesAsync: las operaciones de E/S deben ser asíncronas para no bloquear hilos.
  • Parametrizar las entidades: usa DbSet<Post> Posts => Set<Post>() en lugar de propiedades auto-inicializadas.

6. Errores habituales

Error 1: Pensar que DbSet es una lista

// ❌ Mal: asumir que todos los datos están en memoria.
var all = context.Posts.ToList(); // Esto ejecuta SQL. Puede ser enorme.
var filtered = all.Where(p => p.IsPublished); // Filtra en memoria, no en SQL.
// ✅ Bien: filtra en el servidor antes de materializar.
var filtered = await context.Posts
    .Where(p => p.IsPublished)
    .ToListAsync();

Error 2: Usar EnsureCreatedAsync en producción

EnsureCreatedAsync crea el esquema sin migraciones. No actualiza bien un esquema existente y dificulta el despliegue controlado.

Error 3: No configurar el proveedor de base de datos

Si olvidas UseNpgsql o UseSqlServer, el contexto no sabe a dónde conectar. El error suele ser "No database provider has been configured".

Error 4: Instanciar DbContext con new en toda la aplicación

El contexto debe recibirse por inyección de dependencias para controlar su lifetime, permitir testing y compartir transacciones.

  3. Define Book con Id, Title y AuthorId.
  4. Crea LibraryDbContext con dos DbSet.

author.Books.Add(new Book { Title = "Cien años de soledad" });

9. Resumen

  • Un ORM elimina la fricción entre objetos y tablas relacionales.
  • EF Core usa ADO.NET internamente pero genera SQL automáticamente.
  • DbContext es la unidad de trabajo; DbSet es la puerta de entrada a las tablas.
  • Code-First es ideal para proyectos nuevos con dominio en C#.
  • Las migraciones permiten evolucionar el esquema de forma controlada.

10. Preguntas frecuentes

¿Puedo usar EF Core sin migraciones?

Sí, con EnsureCreated o con Database.ExecuteSqlRaw. No obstante, esas opciones son limitadas y no recomendadas para producción.

¿EF Core solo funciona con SQL Server?

No. Existen proveedores para PostgreSQL, MySQL, SQLite, Oracle, SQL Server, Cosmos DB y otros. En este curso usamos Npgsql.EntityFrameworkCore.PostgreSQL.

¿Debo exponer DbSet como público?

Sí, si quieres consultar desde otras capas. Pero en arquitecturas limpias suele ocultarse detrás de repositorios o servicios de aplicación.

¿Qué pasa si llamo a SaveChangesAsync sin await?

Se devuelve un Task que no se observa. Pueden perderse excepciones y causar problemas de concurrencia. Usa siempre await.

¿Es EF Core más lento que ADO.NET?

Para operaciones simples, sí, porque tiene change tracking, materialización y generación de SQL. Sin embargo, el overhead suele ser insignificante frente a la latencia de red. La clave está en escribir consultas correctas.
