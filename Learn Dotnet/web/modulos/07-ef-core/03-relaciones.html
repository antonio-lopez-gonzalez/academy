Relaciones y cascading deletes

Módulo 7 · Entity Framework Core35 min

1 · Introducción

Las relaciones son el punto donde el modelo de objetos choca con el modelo relacional. Una entrada de blog tiene una categoría, una categoría tiene muchas entradas, y una entrada puede tener muchas etiquetas. EF Core nos permite expresar esas relaciones de forma natural, pero debemos entender cómo se traducen a claves foráneas y qué ocurre cuando borramos un registro padre.

En esta lección cubriremos:

  • Relaciones 1:1, 1:N y N:N.
  • Propiedades de navegación y claves foráneas.
  • Entidades propiedad (Owned).
  • Herencia: TPH, TPT y TPC.
  • Comportamientos de eliminación en cascada.
  • Relaciones obligatorias vs opcionales.

2 · Teoría

2.1 Relaciones 1:N

La relación más común. Un lado tiene una clave foránea; el otro lado tiene una colección.

public class Category
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public List<Post> Posts { get; set; } = new();
}

public class Post
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;
    public int CategoryId { get; set; }
    public Category Category { get; set; } = null!;
}

En Fluent API:

modelBuilder.Entity<Post>(entity =>
{
    entity.HasOne(p => p.Category)
          .WithMany(c => c.Posts)
          .HasForeignKey(p => p.CategoryId)
          .OnDelete(DeleteBehavior.Cascade);
});

2.2 Relaciones 1:1

Usan una clave foránea que también es clave primaria en la entidad dependiente, o una clave foránea única.

public class Author
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public AuthorProfile? Profile { get; set; }
}

public class AuthorProfile
{
    public int AuthorId { get; set; } // PK + FK
    public string Bio { get; set; } = string.Empty;
    public Author Author { get; set; } = null!;
}

modelBuilder.Entity<AuthorProfile>(entity =>
{
    entity.HasKey(ap => ap.AuthorId);
    entity.HasOne(ap => ap.Author)
          .WithOne(a => a.Profile)
          .HasForeignKey<AuthorProfile>(ap => ap.AuthorId);
});

2.3 Relaciones N:N

EF Core 5+ permite relaciones N:N sin tabla de unión explícita. También podemos configurar la tabla intermedia con campos adicionales.

public class Post
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;
    public List<Tag> Tags { get; set; } = new();
}

public class Tag
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public List<Post> Posts { get; set; } = new();
}

// Tabla intermedia implícita (EF Core la genera automáticamente).
modelBuilder.Entity<Post>()
    .HasMany(p => p.Tags)
    .WithMany(t => t.Posts);

Tabla intermedia explícita con metadatos:

public class PostTag
{
    public int PostId { get; set; }
    public int TagId { get; set; }
    public DateTime AssignedAt { get; set; }
    public Post Post { get; set; } = null!;
    public Tag Tag { get; set; } = null!;
}

modelBuilder.Entity<PostTag>(entity =>
{
    entity.HasKey(pt => new { pt.PostId, pt.TagId });
    entity.HasOne(pt => pt.Post).WithMany().HasForeignKey(pt => pt.PostId);
    entity.HasOne(pt => pt.Tag).WithMany().HasForeignKey(pt => pt.TagId);
});

2.4 Entidades propiedad (Owned)

Los value objects del dominio no tienen identidad propia. En EF Core se mapean como entidades propiedad, compartiendo tabla con el propietario.

public class Address
{
    public string Street { get; set; } = string.Empty;
    public string City { get; set; } = string.Empty;
    public string ZipCode { get; set; } = string.Empty;
}

public class Office
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public Address Address { get; set; } = new();
}

modelBuilder.Entity<Office>().OwnsOne(o => o.Address, address =>
{
    address.Property(a => a.Street).HasColumnName("address_street");
    address.Property(a => a.City).HasColumnName("address_city");
    address.Property(a => a.ZipCode).HasColumnName("address_zip");
});

2.5 Herencia: TPH, TPT y TPC

EstrategiaDescripciónCuándo usarla
TPHUna tabla para toda la jerarquía, con una columna discriminadora.Es la predeterminada. Buena cuando las subclases tienen pocos campos distintos.
TPTUna tabla base y una tabla por subclase.Cuando las subclases tienen muchos campos propios y pocos registros.
TPCUna tabla por subclase sin tabla base.Cuando cada subclase es independiente y no se consulta la jerarquía completa.
 
// TPH por defecto: EF Core añade una columna Discriminator.
modelBuilder.Entity<BillingDetail>()
    .HasDiscriminator<string>("BillingType")
    .HasValue<BankAccount>("BA")
    .HasValue<CreditCard>("CC");

// TPT
modelBuilder.Entity<BankAccount>().ToTable("bank_accounts");
modelBuilder.Entity<CreditCard>().ToTable("credit_cards");

// TPC (.NET 7+)
modelBuilder.Entity<BankAccount>().UseTpcMappingStrategy();
modelBuilder.Entity<CreditCard>().UseTpcMappingStrategy();

2.6 Cascading deletes

Define qué ocurre con los registros dependientes cuando se elimina el principal. Los valores principales son:

ComportamientoEfecto
CascadeBorra los dependientes automáticamente.
RestrictImpide borrar el principal si tiene dependientes.
SetNullPone la FK a null (solo en relaciones opcionales).
ClientSetNullEl cliente pone la FK a null; la base de datos no aplica nada.
NoActionNo realiza ninguna acción en el lado de la base de datos.

2.7 Relaciones obligatorias vs opcionales

Una relación es obligatoria cuando la clave foránea no acepta null. En ese caso, el borrado en cascada suele ser el comportamiento por defecto. Si la clave foránea es nullable, la relación es opcional y el borrado por defecto es ClientSetNull.

3 · Ejemplo mínimo

Modelo de blog con autor, posts y etiquetas.

public class BlogContext : DbContext
{
    public BlogContext(DbContextOptions options) : base(options) { }
    public DbSet<Author> Authors => Set<Author>();
    public DbSet<Post> Posts => Set<Post>();
    public DbSet<Tag> Tags => Set<Tag>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Author>(entity =>
        {
            entity.HasMany(a => a.Posts)
                  .WithOne(p => p.Author)
                  .HasForeignKey(p => p.AuthorId)
                  .OnDelete(DeleteBehavior.Cascade);
        });

        modelBuilder.Entity<Post>()
            .HasMany(p => p.Tags)
            .WithMany(t => t.Posts);
    }
}

public class Author { public int Id { get; set; } public string Name { get; set; } = ""; public List<Post> Posts { get; set; } = new(); }
public class Post { public int Id { get; set; } public string Title { get; set; } = ""; public int AuthorId { get; set; } public Author Author { get; set; } = null!; public List<Tag> Tags { get; set; } = new(); }
public class Tag { public int Id { get; set; } public string Name { get; set; } = ""; public List<Post> Posts { get; set; } = new(); }

4 · Ejemplo real

Configuración completa del CMS con esquema, índices, relaciones N:N explícitas y entidades propiedad.

// Domain/Post.cs
public class Post
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;
    public string Slug { get; set; } = string.Empty;
    public string Content { get; set; } = string.Empty;
    public PostStatus Status { get; set; }
    public DateTime CreatedAt { get; set; }
    public DateTime? PublishedAt { get; set; }

    public int AuthorId { get; set; }
    public User Author { get; set; } = null!;

    public int CategoryId { get; set; }
    public Category Category { get; set; } = null!;

    public List<PostTag> PostTags { get; set; } = new();
}

// Domain/PostTag.cs (tabla intermedia explícita)
public class PostTag
{
    public int PostId { get; set; }
    public Post Post { get; set; } = null!;
    public int TagId { get; set; }
    public Tag Tag { get; set; } = null!;
    public DateTime AssignedAt { get; set; }
}

// Data/Configurations/PostConfiguration.cs
public class PostConfiguration : IEntityTypeConfiguration<Post>
{
    public void Configure(EntityTypeBuilder<Post> entity)
    {
        entity.ToTable("posts", "cms");
        entity.HasKey(p => p.Id);
        entity.HasIndex(p => p.Slug).IsUnique();
        entity.Property(p => p.Title).HasMaxLength(200).IsRequired();
        entity.Property(p => p.Status).HasConversion<string>().HasMaxLength(20);
        entity.Property(p => p.CreatedAt).HasDefaultValueSql("now()");

        entity.HasOne(p => p.Author)
              .WithMany(u => u.Posts)
              .HasForeignKey(p => p.AuthorId)
              .OnDelete(DeleteBehavior.Restrict);

        entity.HasOne(p => p.Category)
              .WithMany(c => c.Posts)
              .HasForeignKey(p => p.CategoryId)
              .OnDelete(DeleteBehavior.SetNull);
    }
}

// Data/Configurations/PostTagConfiguration.cs
public class PostTagConfiguration : IEntityTypeConfiguration<PostTag>
{
    public void Configure(EntityTypeBuilder<PostTag> entity)
    {
        entity.ToTable("post_tags", "cms");
        entity.HasKey(pt => new { pt.PostId, pt.TagId });
        entity.Property(pt => pt.AssignedAt).HasDefaultValueSql("now()");
    }
}
Decisión: usamos Restrict para el autor porque no queremos borrar posts al eliminar un usuario; usamos SetNull para la categoría porque un post puede quedar sin categoría temporalmente.

5 · Buenas prácticas

  • Configura todas las relaciones explícitamente: las convenciones son útiles, pero la configuración explícita evita sorpresas.
  • Usa IEntityTypeConfiguration<T>: divide el OnModelCreating en archivos pequeños y cohesionados.
  • Prefiere TPH por defecto: es la estrategia más eficiente en la mayoría de los casos.
  • Define claves compuestas para tablas de unión N:N: mejora el rendimiento y la integridad.
  • Revisa el comportamiento de eliminación: un Cascade mal configurado puede borrar más datos de los esperados.
  • Usa DeleteBehavior.Restrict en datos críticos: obliga a borrar primero los dependientes de forma explícita.

6 · Errores habituales

Error 1: Dejar la eliminación en cascada por defecto sin revisar

El borrado en cascada puede eliminar toda una jerarquía de datos sin avisar. Siempre configura OnDelete de forma consciente.

Error 2: Propiedad de navegación sin clave foránea

// ❌ Mal: EF Core puede crear una sombra FK, pero el modelo es menos explícito.
public class Post
{
    public int Id { get; set; }
    public Category Category { get; set; } = null!;
}

// ✅ Bien: clave foránea explícita.
public class Post
{
    public int Id { get; set; }
    public int CategoryId { get; set; }
    public Category Category { get; set; } = null!;
}

Error 3: Tabla intermedia N:N con datos que no se persisten

Si la tabla intermedia necesita metadatos, define una entidad explícita. Las relaciones HasMany(...).WithMany(...) implícitas solo soportan las dos claves foráneas.

Error 4: Configurar DeleteBehavior.SetNull en una FK no nullable

SQL no puede poner null en una columna NOT NULL. El error aparece al aplicar la migración o al intentar borrar.

7 · Ejercicio guiado

Diseña el modelo de una biblioteca universitaria:

  1. Student puede tener muchos Loan.
  2. Book puede aparecer en muchos Loan.
  3. Loan es una tabla intermedia con LoanDate y ReturnDate.
  4. Configura OnDelete(DeleteBehavior.Restrict) para evitar borrar libros con préstamos activos.
  5. Agrega una entidad propiedad Address a Student.
modelBuilder.Entity<Loan>(entity =>
{
    entity.HasKey(l => new { l.StudentId, l.BookId, l.LoanDate });
    entity.HasOne(l => l.Student).WithMany(s => s.Loans).HasForeignKey(l => l.StudentId);
    entity.HasOne(l => l.Book).WithMany(b => b.Loans).HasForeignKey(l => l.BookId).OnDelete(DeleteBehavior.Restrict);
});

8 · Reto

Implementa una jerarquía de pagos con TPH: Payment, CardPayment y BankTransferPayment. Configura la columna discriminadora con nombres cortos y añade una migración. Luego, prueba las tres estrategias (TPH, TPT, TPC) y compara el SQL generado para una consulta que devuelva todos los pagos.

9 · Resumen

  • Las relaciones en EF Core se definen con claves foráneas y propiedades de navegación.
  • 1:N es la relación más común; 1:N requiere una clave foránea explícita y una propiedad de navegación.
  • Las relaciones N:N pueden ser implícitas o explícitas mediante una entidad intermedia.
  • Las entidades propiedad comparten tabla con su propietario y representan value objects.
  • TPH, TPT y TPC son estrategias de herencia con distintos compromisos de rendimiento y normalización.
  • El comportamiento de eliminación en cascada debe configurarse conscientemente.

10 · Preguntas frecuentes

¿Puedo tener una relación N:N con campos adicionales?

Sí, pero debes crear una entidad intermedia explícita y configurar las dos claves foráneas con HasOne(...).WithMany(...).HasForeignKey(...).

¿Qué pasa si no configuro OnDelete?

EF Core aplica convenciones. Para relaciones obligatorias suele ser Cascade; para opcionales, ClientSetNull. Revisa siempre la migración generada.

¿Es obligatorio tener propiedades de navegación en ambos lados?

No. Puedes tener una relación unidireccional. Sin embargo, las propiedades bidireccionales facilitan las consultas y el materializado.

¿Cuál es la mejor estrategia de herencia?

TPH es la más rápida para la mayoría de las consultas. TPT es mejor para subclases con muchos campos. TPC es útil cuando cada subclase vive de forma independiente.

¿Puedo usar Owned en colecciones?

Sí, con OwnsMany, aunque requiere una tabla separada. Es útil para colecciones de value objects dentro de una entidad raíz.
