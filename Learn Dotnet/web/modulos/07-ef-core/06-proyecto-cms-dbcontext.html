Proyecto CMS: DbContext + repositorios

Módulo 7 · Entity Framework Core50 min

1 · Introducción

En esta lección del proyecto práctico vamos a dar el salto definitivo a la persistencia. Construiremos el DbContext del CMS, configuraremos todas las relaciones entre entidades, crearemos las migraciones iniciales y conectaremos las interfaces de repositorio que diseñamos en el Módulo 6 con implementaciones reales basadas en EF Core.

Veremos:

  • Cómo estructurar el CmsDbContext en el proyecto de infraestructura.
  • Configuración de entidades con archivos IEntityTypeConfiguration<T>.
  • Modelo de dominio: Post, Category, Tag, User, PostTag.
  • Implementación de repositorios EF Core.
  • Registro del contexto en el contenedor de DI.
  • Generación y aplicación de la migración inicial.
Arquitectura: seguimos Clean Architecture. El DbContext y los repositorios concretos viven en Cms.Infrastructure. Las interfaces de repositorio viven en Cms.Domain o Cms.Application.

2 · Teoría

2.1 Ubicación del DbContext en Clean Architecture

En Clean Architecture, la capa de infraestructura depende de la capa de aplicación y dominio, pero no al revés. El DbContext es un detalle de infraestructura: pertenece al proyecto Cms.Infrastructure.

Cms.Api
    │
    ▼
Cms.Application  ← interfaces de repositorio (IRepository, IUnitOfWork)
    │
    ▼
Cms.Domain     ← entidades puras y contratos de dominio
    │
    ▼
Cms.Infrastructure  ← CmsDbContext, EF Core, repositorios concretos

2.2 Separación de configuración

En lugar de poner todo en OnModelCreating, creamos una clase de configuración por entidad. Esto mejora la mantenibilidad y permite que cada entidad evolucione de forma independiente.

// Cms.Infrastructure/Data/Configurations/PostConfiguration.cs
public class PostConfiguration : IEntityTypeConfiguration<Post>
{
    public void Configure(EntityTypeBuilder<Post> entity)
    {
        entity.ToTable("posts", "cms");
        entity.HasKey(p => p.Id);
        entity.HasIndex(p => p.Slug).IsUnique();
        entity.Property(p => p.Title).HasMaxLength(200).IsRequired();
        entity.Property(p => p.Slug).HasMaxLength(200).IsRequired();
        entity.Property(p => p.Content).HasColumnType("text");
        entity.Property(p => p.Status).HasConversion<string>().HasMaxLength(20);
        entity.Property(p => p.CreatedAt).HasDefaultValueSql("now()");
        entity.Property(p => p.RowVersion).IsConcurrencyToken().ValueGeneratedOnAddOrUpdate();

        entity.HasOne(p => p.Author)
              .WithMany(u => u.Posts)
              .HasForeignKey(p => p.AuthorId)
              .OnDelete(DeleteBehavior.Restrict);

        entity.HasOne(p => p.Category)
              .WithMany(c => c.Posts)
              .HasForeignKey(p => p.CategoryId)
              .OnDelete(DeleteBehavior.SetNull);
    }
}

2.3 Relaciones del CMS

El modelo del CMS tiene las siguientes relaciones:

  • User 1:N Post: un autor tiene muchos posts. Usamos Restrict para no borrar posts al eliminar un usuario.
  • Category 1:N Post: una categoría tiene muchos posts. Usamos SetNull porque un post puede quedar sin categoría.
  • Post N:N Tag mediante PostTag: tabla intermedia explícita con metadatos.

2.4 Repositorios con EF Core

Los repositorios encapsulan el acceso a datos. Reciben el DbContext por constructor y exponen métodos orientados al dominio. No exponen IQueryable para evitar que la lógica de filtrado se disperse.

public interface IPostRepository
{
    Task<Post?> GetByIdAsync(int id, CancellationToken cancellationToken = default);
    Task<IReadOnlyList<Post>> GetPublishedAsync(int page, int pageSize, CancellationToken cancellationToken = default);
    Task AddAsync(Post post, CancellationToken cancellationToken = default);
    Task UpdateAsync(Post post, CancellationToken cancellationToken = default);
    Task DeleteAsync(Post post, CancellationToken cancellationToken = default);
}

public class EfPostRepository : IPostRepository
{
    private readonly CmsDbContext _context;
    public EfPostRepository(CmsDbContext context) => _context = context;

    public async Task<Post?> GetByIdAsync(int id, CancellationToken cancellationToken = default)
    {
        return await _context.Posts
            .AsNoTracking()
            .Include(p => p.Category)
            .Include(p => p.Author)
            .Include(p => p.PostTags)
            .ThenInclude(pt => pt.Tag)
            .FirstOrDefaultAsync(p => p.Id == id, cancellationToken);
    }

    public async Task<IReadOnlyList<Post>> GetPublishedAsync(int page, int pageSize, CancellationToken cancellationToken = default)
    {
        return await _context.Posts
            .AsNoTracking()
            .Where(p => p.Status == PostStatus.Published)
            .OrderByDescending(p => p.PublishedAt)
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Include(p => p.Category)
            .Include(p => p.Author)
            .ToListAsync(cancellationToken);
    }

    public async Task AddAsync(Post post, CancellationToken cancellationToken = default)
    {
        await _context.Posts.AddAsync(post, cancellationToken);
    }

    public Task UpdateAsync(Post post, CancellationToken cancellationToken = default)
    {
        _context.Posts.Update(post);
        return Task.CompletedTask;
    }

    public Task DeleteAsync(Post post, CancellationToken cancellationToken = default)
    {
        _context.Posts.Remove(post);
        return Task.CompletedTask;
    }
}

2.5 Unidad de trabajo con DbContext

En lugar de llamar a SaveChanges dentro de cada repositorio, el DbContext actúa como unidad de trabajo. Los handlers CQRS llaman a SaveChangesAsync tras coordinar las operaciones de los repositorios.

public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken cancellationToken = default);
}

// CmsDbContext implementa IUnitOfWork directamente.
public class CmsDbContext : DbContext, IUnitOfWork
{
    public CmsDbContext(DbContextOptions<CmsDbContext> options) : base(options) { }

    public DbSet<Post> Posts => Set<Post>();
    public DbSet<Category> Categories => Set<Category>();
    public DbSet<Tag> Tags => Set<Tag>();
    public DbSet<User> Users => Set<User>();
    public DbSet<PostTag> PostTags => Set<PostTag>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(CmsDbContext).Assembly);
        base.OnModelCreating(modelBuilder);
    }
}

2.6 Configuración en DI

Registramos el DbContext, los repositorios y la unidad de trabajo en el contenedor de DI de la aplicación.

// Program.cs
builder.Services.AddDbContext<CmsDbContext>((provider, options) =>
{
    var connectionString = builder.Configuration.GetConnectionString("CmsDatabase")!;
    options.UseNpgsql(connectionString, npgsql =>
    {
        npgsql.MigrationsAssembly("Cms.Infrastructure");
        npgsql.MigrationsHistoryTable("__EFMigrationsHistory", "cms");
    });
});

builder.Services.AddScoped<IPostRepository, EfPostRepository>();
builder.Services.AddScoped<ICategoryRepository, EfCategoryRepository>();
builder.Services.AddScoped<ITagRepository, EfTagRepository>();
builder.Services.AddScoped<IUnitOfWork, CmsDbContext>();

// appsettings.json
{
  "ConnectionStrings": {
    "CmsDatabase": "Host=localhost;Database=cmsdb;Username=cms;Password=secret;SearchPath=cms,public"
  }
}
Nota: especificamos el MigrationsAssembly porque el DbContext está en Cms.Infrastructure, pero el proyecto de inicio es Cms.Api.

3 · Ejemplo mínimo

El DbContext mínimo del CMS con dos entidades y una relación.

public class CmsDbContext : DbContext
{
    public CmsDbContext(DbContextOptions<CmsDbContext> options) : base(options) { }
    public DbSet<Post> Posts => Set<Post>();
    public DbSet<Category> Categories => Set<Category>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Post>(entity =>
        {
            entity.ToTable("posts", "cms");
            entity.HasKey(p => p.Id);
            entity.Property(p => p.Title).HasMaxLength(200).IsRequired();
        });

        modelBuilder.Entity<Category>(entity =>
        {
            entity.ToTable("categories", "cms");
            entity.HasKey(c => c.Id);
            entity.Property(c => c.Name).HasMaxLength(100).IsRequired();
        });
    }
}

// Cms.Infrastructure/Data/Configurations/PostTagConfiguration.cs
public class PostTagConfiguration : IEntityTypeConfiguration<PostTag>
{
    public void Configure(EntityTypeBuilder<PostTag> entity)
    {
        entity.ToTable("post_tags", "cms");
        entity.HasKey(pt => new { pt.PostId, pt.TagId });
        entity.Property(pt => pt.AssignedAt).HasDefaultValueSql("now()");

        entity.HasOne(pt => pt.Post)
              .WithMany(p => p.PostTags)
              .HasForeignKey(pt => pt.PostId)
              .OnDelete(DeleteBehavior.Cascade);

        entity.HasOne(pt => pt.Tag)
              .WithMany(t => t.PostTags)
              .HasForeignKey(pt => pt.TagId)
              .OnDelete(DeleteBehavior.Cascade);
    }
}

4.4 Repositorios

// Cms.Infrastructure/Data/Repositories/EfCategoryRepository.cs
public class EfCategoryRepository : ICategoryRepository
{
    private readonly CmsDbContext _context;
    public EfCategoryRepository(CmsDbContext context) => _context = context;

    public async Task<Category?> GetByIdAsync(int id, CancellationToken cancellationToken = default)
    {
        return await _context.Categories
            .AsNoTracking()
            .FirstOrDefaultAsync(c => c.Id == id, cancellationToken);
    }

    public async Task<Category?> GetBySlugAsync(string slug, CancellationToken cancellationToken = default)
    {
        return await _context.Categories
            .AsNoTracking()
            .FirstOrDefaultAsync(c => c.Slug == slug, cancellationToken);
    }

    public async Task<IReadOnlyList<Category>> GetAllAsync(CancellationToken cancellationToken = default)
    {
        return await _context.Categories
            .AsNoTracking()
            .OrderBy(c => c.Name)
            .ToListAsync(cancellationToken);
    }

    public async Task AddAsync(Category category, CancellationToken cancellationToken = default)
    {
        await _context.Categories.AddAsync(category, cancellationToken);
    }

    public Task UpdateAsync(Category category, CancellationToken cancellationToken = default)
    {
        _context.Categories.Update(category);
        return Task.CompletedTask;
    }

    public Task DeleteAsync(Category category, CancellationToken cancellationToken = default)
    {
        _context.Categories.Remove(category);
        return Task.CompletedTask;
    }
}

4.5 Handler CQRS que usa repositorios

public class CreatePostHandler : IRequestHandler<CreatePostCommand, Result<int>>
{
    private readonly IPostRepository _postRepository;
    private readonly ICategoryRepository _categoryRepository;
    private readonly IUnitOfWork _unitOfWork;

    public CreatePostHandler(
        IPostRepository postRepository,
        ICategoryRepository categoryRepository,
        IUnitOfWork unitOfWork)
    {
        _postRepository = postRepository;
        _categoryRepository = categoryRepository;
        _unitOfWork = unitOfWork;
    }

    public async Task<Result<int>> Handle(CreatePostCommand request, CancellationToken cancellationToken)
    {
        var category = await _categoryRepository.GetByIdAsync(request.CategoryId, cancellationToken);
        if (category is null)
            return Result<int>.Failure("Category.NotFound", "La categoría no existe.");

        var post = new Post
        {
            Title = request.Title,
            Slug = request.Slug,
            Content = request.Content,
            AuthorId = request.AuthorId,
            CategoryId = category.Id,
            Status = PostStatus.Draft
        };

        await _postRepository.AddAsync(post, cancellationToken);
        await _unitOfWork.SaveChangesAsync(cancellationToken);

        return Result<int>.Success(post.Id);
    }
}

5 · Buenas prácticas

  • Organiza las configuraciones en archivos separados: una clase por entidad mejora la legibilidad y reduce conflictos en el control de versiones.
  • Usa esquemas de base de datos: el esquema cms agrupa las tablas del proyecto y evita colisiones con otros módulos.
  • Implementa las interfaces de dominio en infraestructura: la capa de aplicación no debe conocer EF Core.
  • Evita llamar a SaveChanges dentro de los repositorios: deja que el handler o la unidad de trabajo coordinen la transacción.
  • Usa AsNoTracking en consultas de solo lectura: mejora el rendimiento.
  • Configura índices y claves únicas: Slug y Email son buenos candidatos.
  • Genera migraciones en la capa de infraestructura: el modelo pertenece a esa capa.
  • No uses Database.EnsureCreated en producción: usa migraciones o scripts idempotentes.

6 · Errores habituales

Error 1: Referenciar EF Core desde la capa de aplicación

// ❌ Mal: Application conoce EF Core.
public class CreatePostHandler : IRequestHandler<CreatePostCommand, int>
{
    private readonly CmsDbContext _context; // Dependencia de infraestructura.
}
// ✅ Bien: Application depende de abstracciones.
public class CreatePostHandler : IRequestHandler<CreatePostCommand, int>
{
    private readonly IPostRepository _postRepository;
}

Error 2: SaveChanges dentro del repositorio

Si el repositorio llama a SaveChanges, no puedes coordinar varias operaciones en una misma transacción. Usa una unidad de trabajo.

Error 3: Olvidar MigrationsAssembly

Si el DbContext está en Cms.Infrastructure pero el proyecto de inicio es Cms.Api, las migraciones deben especificar el ensamblado correcto.

Error 4: Materializar todo y filtrar en memoria

Los repositorios deben exponer consultas que EF Core traduzca a SQL, no listas materializadas que luego se filtren en memoria.

9 · Resumen

  • El DbContext del CMS vive en Cms.Infrastructure siguiendo Clean Architecture.
  • Las configuraciones se separan con IEntityTypeConfiguration<T>.
  • El modelo incluye Post, Category, Tag, User y PostTag.
  • Los repositorios concretos usan EF Core pero exponen abstracciones del dominio.
  • El DbContext actúa como unidad de trabajo.
  • Las migraciones se generan en la capa de infraestructura y se aplican con la CLI de EF Core.

10 · Preguntas frecuentes

¿Por qué el DbContext no está en Cms.Application?

Porque EF Core es un detalle de infraestructura. La capa de aplicación solo depende de interfaces para mantener la arquitectura limpia.

¿Por qué no llamar a SaveChanges en el repositorio?

Para que un handler CQRS pueda coordinar varias operaciones (por ejemplo, crear un post y registrar auditoría) en una misma transacción.

¿Cómo decido entre IQueryable y Listas en repositorios?

Los repositorios del dominio suelen devolver Task<IReadOnlyList<T>> o Task<T?>. No exponen IQueryable para evitar lógica de filtrado dispersa entre capas.

¿Puedo tener varios DbContext en la misma aplicación?

Sí, y es común en aplicaciones grandes. Cada contexto gestiona su propio modelo y cadena de conexión.

¿Dónde coloco las migraciones si el DbContext está en Infrastructure?

Usa MigrationsAssembly("Cms.Infrastructure") en la configuración de Npgsql y ejecuta los comandos con --project src/Cms.Infrastructure y --startup-project src/Cms.Api.

¿Es necesario un repository pattern con EF Core?

No es obligatorio. Para aplicaciones pequeñas, DbContext puede actuar como unidad de trabajo y repositorio. En proyectos grandes, el patrón repositorio mejora el testing y la separación de responsabilidades.
