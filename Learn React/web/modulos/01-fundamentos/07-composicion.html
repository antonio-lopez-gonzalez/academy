Composición

Módulo 1 · Fundamentos ⏱ 30 minutos

1 · Introducción

Llegamos a la lección que cierra el modelo mental del Módulo 1. La composición es la técnica con la que React resuelve casi todos los problemas de diseño de interfaces: construir componentes complejos combinando componentes simples, en lugar de crear componentes gigantes con decenas de props o de «heredar» comportamiento.

Si vienes de la programación orientada a objetos, esta lección requiere un ajuste mental importante: en React no existe la herencia entre componentes. Ni la necesitas. Todo lo que la herencia resolvía (reutilización, especialización) se resuelve mejor con composición. La documentación oficial de React lo dice sin ambages: «no hemos encontrado ningún caso en el que recomendaríamos crear jerarquías de herencia de componentes».

2 · Teoría

Composición vs herencia: el cambio de paradigma

🧱 Analogía: coches personalizados

Herencia: para tener un coche deportivo, fabricas un «CocheDeportivo» que hereda de «Coche». ¿Y si luego quieres uno deportivo Y descapotable Y eléctrico? Explosión de subclases: CocheDeportivoDescapotableElectrico…

Composición: fabricas piezas (motor, techo, alerón) y ENSAMBLAS el coche que necesitas: <Coche><MotorElectrico /><TechoDescapotable /></Coche>. Infinitas combinaciones, piezas finitas.

Las tres técnicas de composición en React

1. Contención (children): el componente «hueco»

Ya la conoces: componentes como Card, Modal o Layout que reciben contenido por children sin conocerlo.

2. Especialización: configurar un genérico

Un componente «especializado» es simplemente uno que usa al genérico con una configuración concreta: 

// Genérico
function Dialog({ title, children }) { … }

// Especializados: NO heredan; USAN al genérico
function WelcomeDialog() {
  return (
    <Dialog title="Bienvenido">
      <p>Gracias por registrarte.</p>
    </Dialog>
  );
}

function DeleteDialog({ onConfirm }) {
  return (
    <Dialog title="Eliminar">
      <p>¿Seguro?</p>
      <button onClick={onConfirm}>Sí, eliminar</button>
    </Dialog>
  );
}

3. Props de elementos («slots» con nombre)

Cuando un contenedor necesita varios huecos concretos, pasas elementos como props: 

function SplitPane({ left, right }) {
  return (
    <div className="split-pane">
      <div className="split-pane__left">{left}</div>
      <div className="split-pane__right">{right}</div>
    </div>
  );
}

// Uso: cada "zona" recibe su contenido
<SplitPane
  left={<ContactList />}
  right={<ChatWindow />}
/>
💡 El superpoder oculto de la composición: evitar renders

Cuando un padre pasa elementos YA CREADOS como children/props, React puede re-renderizar el contenedor sin volver a crear los hijos (son el mismo elemento, con la misma identidad). Es la técnica de optimización «lift content up» que retomaremos en el Módulo 11. La composición no solo organiza: también optimiza.

La guía de decisión profesional

SituaciónTécnica

3 · Ejemplo mínimo

src/components/Panel.jsx
// Contenedor genérico con children
export default function Panel({ title, children }) {
  return (
    <section className="panel">
      <h3 className="panel__title">{title}</h3>
      {children}
    </section>
  );
}
src/components/StatsPanel.jsx — especialización por composición
import Panel from "./Panel.jsx";

// Un panel CONCRETO, construido USANDO el genérico (sin herencia)
export default function StatsPanel() {
  return (
    <Panel title="Estadísticas">
      <p>Visitas hoy: 128</p>
    </Panel>
  );
}

Línea por línea:

  1. Panel es agnóstico: título + hueco. Sirve para todo.
  2. StatsPanel no extiende nada: envuelve a Panel con una configuración concreta (título fijo + contenido propio).
  3. Si mañana Panel añade una prop collapsible, StatsPanel la puede aprovechar sin cambiar su estructura — o ignorarla. Independencia total.

4 · Ejemplo real

El layout de una aplicación completa con zonas múltiples — la estructura que usaremos en el proyecto final (TaskFlow):

src/components/AppLayout.jsx
// Layout con TRES zonas: header y sidebar por props (slots),
// contenido principal por children.
export default function AppLayout({ header, sidebar, children }) {
  return (
    <div className="app-layout">
      <header className="app-layout__header">{header}</header>
      <div className="app-layout__body">
        <aside className="app-layout__sidebar">{sidebar}</aside>
        <main className="app-layout__main">{children}</main>
      </div>
    </div>
  );
}
src/App.jsx — la página compone el layout
import AppLayout from "./components/AppLayout.jsx";
import TopBar from "./components/TopBar.jsx";
import ProjectNav from "./components/ProjectNav.jsx";
import TaskBoard from "./components/TaskBoard.jsx";

export default function App() {
  return (
    <AppLayout
      header={<TopBar />}        // slot header
      sidebar={<ProjectNav />}    // slot sidebar
    >
      <TaskBoard />               {/* children: el contenido */}
    </AppLayout>
  );
}

Decisiones explicadas:

  • El layout no importa a sus hijos: AppLayout no sabe qué es TopBar ni TaskBoard. Puedes probar el layout con contenido de mentira y cada pieza por separado. Desacoplamiento total.
  • Quién compone es la página (App): la «raíz» decide qué va en cada zona. Cambiar la página de «tareas» a «ajustes» es cambiar los elementos que se pasan, no el layout.
  • children para el contenido principal porque es la zona «natural» que cambia en cada página; props para las zonas estructurales (header/sidebar) porque son huecos con nombre.
  • Esta es EXACTAMENTE la arquitectura que React Router formalizará en el Módulo 8 con rutas anidadas: un layout + un hueco donde aparece la página actual.

5 · Buenas prácticas

HazEvitaPor qué
Componer: envolver genéricos y configurarlos Intentar heredar componentes (class A extends B) React no está diseñado para ello: rompe el modelo de funciones puras y la reconciliación.
Componentes pequeños ensamblados Componentes de 40 props booleanas (hasHeader, isBlue, showFooter…) La «explosión de props» es el síntoma de un componente que debería dividirse y componerse.
Layouts agnósticos que reciben zonas Layouts que importan componentes concretos de negocio Si el layout importa TaskBoard, ya no sirve para la página de ajustes.
Extraer lógica compartida a custom hooks (Módulo 6) Duplicar lógica entre componentes «especializados» La composición comparte UI; los hooks comparten lógica. Son complementarios.

6 · Errores habituales

Error 1: simular herencia con «componente base» + props de configuración infinitas

✘ Incorrecto 
// Un "ButtonBase" que pretende ser clase base de todo:
<ButtonBase
  isIconButton
  hasTooltip
  tooltipText="Guardar"
  iconPosition="left"
  usePrimaryStyle
  /* …12 props más… */
/>
✔ Correcto 
// Piezas pequeñas que se componen:
<Tooltip text="Guardar">
  <Button variant="primary">
    <SaveIcon /> Guardar
  </Button>
</Tooltip>

Error 2: el contenedor que conoce a sus hijos

✘ Incorrecto 
function PageLayout({ showTasks, showSettings }) {
  return (
    <div>
      {showTasks && <TaskBoard />}       {/* ✘ el layout importa */}
      {showSettings && <SettingsPanel />} {/*    componentes de negocio */}
    </div>
  );
}
✔ Correcto 
function PageLayout({ children }) {   // ✔ agnóstico: recibe lo que sea
  return <div className="page">{children}</div>;
}

<PageLayout><TaskBoard /></PageLayout>     // quien USA decide

Error 3: composición prematura de todo

Por qué está mal: crear 6 componentes-slot para una pantalla que se usa una vez es sobre-ingeniería. La flexibilidad tiene un coste (más archivos, más indirección).

Versión correcta: empieza simple (un componente concreto); refactoriza a composición cuando aparezca el SEGUNDO uso real. La regla del tres: al tercer copia-pega, abstrae.

7 · Ejercicio guiado

Vamos a refactorizar un componente rígido hacia composición:

  1. Punto de partida (el típico componente rígido):

    function UserCard() {
  return (
    <div className="card">
      <img src="ana.png" alt="Ana" />
      <h3>Ana García</h3>
      <p>Frontend Dev</p>
    </div>
  );
}

  2. Refactor a contenedor: extrae la caja visual a Card (con children) y deja que UserCard solo aporte el contenido:

    function Card({ children }) {
  return <div className="card">{children}</div>;
}

function UserCard({ user }) {
  return (
    <Card>
      <img src={user.avatar} alt={user.name} />
      <h3>{user.name}</h3>
      <p>{user.role}</p>
    </Card>
  );
}

  3. Comprueba la ganancia: crea ahora un ProductCard que reutilice el mismo Card con contenido distinto. Cero CSS duplicado, cero copia de estructura.

  4. Reflexiona: ¿qué habría costado esto con herencia? Tendrías class UserCard extends Card… y ¿qué pasa cuando una tarjeta necesite además comportamiento de Clickable? La composición no tiene ese techo.

8 · Reto

🎯 Mini biblioteca de layout

Crea estos 4 componentes de layout, todos agnósticos:

  • <Stack gap={…}> — apila hijos verticalmente con separación.
  • <Row gap={…} align="start|center|end"> — fila horizontal.
  • <Center> — centra su contenido.
  • <Container maxWidth={…}> — ancho máximo centrado.

Y construye una página de «Perfil» usándolos SOLO a ellos (sin divs con clase propios): avatar centrado, nombre, una fila de 3 estadísticas y una pila de 2 botones. Pista: las props de estilo se traducen a style={{ gap: gap + "px" }} o a clases dinámicas.

9 · Resumen

  • Composición = construir UI combinando componentes. Es EL mecanismo de reutilización de React.
  • React no usa herencia entre componentes: todo lo que la herencia resuelve, la composición lo resuelve mejor y sin rigidez.
  • Tres técnicas: contención (children), especialización (envolver y configurar), slots (props de elementos).
  • Los contenedores deben ser agnósticos: no importar componentes de negocio.
  • Para compartir lógica: custom hooks (Módulo 6). Para compartir estado lejano: Context (Módulo 10). La composición comparte UI.
  • No abstraigas antes de tiempo: la segunda o tercera repetición justifica la abstracción.

10 · Preguntas frecuentes

¿Composición es lo mismo que anidar componentes?

Anidar (un componente usa a otro) es la base; la composición es el patrón de diseño que la aprovecha: contenedores agnósticos, slots, especialización por configuración. Toda app React anida; las bien diseñadas componen.

¿Y si necesito que el contenedor «controle» a sus hijos?

Los hijos reciben props del padre como siempre: quien compone (la página) conecta ambos. El contenedor nunca necesita «saber» qué hijo tiene; la comunicación la hace el que los ensambla. Para casos avanzados (Tabs, Menús) se usa Context entre padre e hijos (Módulo 10).

¿Pasar JSX por props no es «raro»?

Es totalmente idiomático en React: los elementos son valores como cualquier otro (recuerda: objetos). <Layout header={<TopBar />} /> es tan normal como pasar un número. Las librerías profesionales lo usan constantemente.

¿Cómo se relaciona composición con «prop drilling»?

La composición es la PRIMERA solución al prop drilling (pasar datos por muchos niveles): en lugar de pasar los datos hacia abajo, pasas el COMPONENTE YA CONSTRUIDO hacia abajo. Si ni eso basta, entra Context (Módulo 10).
