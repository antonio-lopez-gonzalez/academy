Server Components: contexto y futuro

Módulo 13 · Proyecto Final: TaskFlow ⏱ 40 minutos

1 · Introducción

Durante todo el curso hemos trabajado con una SPA clásica: todo el JavaScript se descarga en el navegador y la aplicación se renderiza completamente en el cliente. Este modelo funciona muy bien, pero tiene limitaciones: el bundle crece, el SEO es complejo y el acceso a datos requiere llamadas HTTP que exponen la lógica.

React Server Components (RSC) cambian el paradigma: permiten que ciertos componentes se ejecuten exclusivamente en el servidor, generen HTML/streaming y nunca envíen su JavaScript al cliente. No es una característica menor: es el cambio arquitectónico más importante desde que React existe.

Qué problema resuelven: las SPAs tradicionales envían demasiado JavaScript al cliente, incluso código que solo debería ejecutarse en el servidor (consultas a DB, lógica sensible, transformaciones pesadas). RSC permiten decidir qué se ejecuta dónde, reduciendo el bundle drásticamente (a veces un 30–50 %) y mejorando el rendimiento percibido.

Cuándo se utiliza: siempre que tengas componentes que necesiten acceder a datos del servidor (base de datos, API interna, sistema de archivos) y que no requieran interactividad del usuario. Next.js App Router ya lo usa por defecto; el ecosistema avanza hacia esta arquitectura.

Errores típicos: pensar que RSC reemplazan a las SPAs (conviven), usar hooks dentro de Server Components (no tienen estado), o poner "use client" en todo el árbol (pierdes el beneficio).

2 · Teoría

¿Qué es un Server Component?

Un React Server Component es un componente que se ejecuta una única vez en el servidor durante la petición, genera su salida (una descripción serializable del árbol React) y nunca se envía su código JavaScript al cliente. 

// ServerComponent.jsx — ESTO NO TIENE "use client"
// Se ejecuta EN EL SERVIDOR. El cliente nunca ve este archivo.

import db from './database'

export default function ProjectList() {
  // Acceso directo a la base de datos — sin API REST
  const projects = db.query('SELECT * FROM projects ORDER BY created_at DESC')

  return (
    <ul>
      {projects.map(p => (
        <li key={p.id}>{p.name}</li>
      ))}
    </ul>
  )
}

Diferencia fundamental: Server vs Client

Característica Server Component Client Component
Se ejecuta en Servidor (una vez) Cliente (cada render)
Envía JS al cliente No Sí
Acceso a DB / sistema Directo Solo vía fetch
useState / useEffect No Sí
Eventos (onClick, etc.) No Sí
Bundle JS 0 bytes Su código sí

"use client" — la frontera

La directiva "use client" marca el límite entre el servidor y el cliente. Todo componente que importe un módulo con "use client" se convierte en Client Component. 

// ClientComponent.jsx — primera línea obligatoria
'use client'

import { useState } from 'react'

export default function LikeButton({ projectId }) {
  const [liked, setLiked] = useState(false)

  return (
    <button onClick={() => setLiked(!liked)}>
      {liked ? '❤️' : '🤍'}
    </button>
  )
}

// Parent.server.jsx — Server Component que usa el Client
import LikeButton from './LikeButton' // ← aquí se cruza la frontera

export default function Page({ projectId }) {
  return (
    <div>
      <h1>Proyecto {projectId}</h1>
      <LikeButton projectId={projectId} /> {/* ← se renderiza en cliente */}
    </div>
  )
}

¿Cómo se comunican?

Los Server Components pueden pasar props serializables (strings, números, objetos planos, arrays) a Client Components. No pueden pasar funciones (no se serializan). Los Client Components, a su vez, pueden renderizar Server Components como hijos mediante children. 

Petición HTTP
    │
    ▼
Servidor ejecuta Server Components
    │
    ├── Consulta DB / API interna
    ├── Genera descripción del árbol (serializada)
    └── Envía al cliente
        │
        ▼
Cliente recibe el árbol pre-renderizado
        │
        ├── Hidrata los Client Components (usa JS)
        └── El HTML Server Component ya está listo (0 JS)

RSC NO es SSR

Server-Side Rendering (SSR) renderiza componentes en el servidor para generar HTML que se envía al cliente, pero todo el JavaScript del componente se sigue enviando y se hidrata en el cliente. RSC, en cambio, no envía nada de JavaScript del Server Component. SSR + RSC pueden combinarse (Next.js lo hace).

Streaming y Suspense

Los Server Components pueden hacerse streaming: el servidor envía fragmentos del árbol conforme los va produciendo, y el cliente los muestra con Suspense. Esto mejora el Time To First Byte y la experiencia de carga. 

import { Suspense } from 'react'
import ProjectList from './ProjectList.server'

export default function Dashboard() {
  return (
    <Suspense fallback={<p>Cargando proyectos…</p>}>
      <ProjectList /> {/* Se streamea cuando la DB responde */}
    </Suspense>
  )
}

3 · Ejemplo mínimo

El ejemplo más pequeño que muestra la esencia de RSC: un Server Component que lee datos y un Client Component que añade interactividad. 

// Note.server.jsx — Server Component
// No tiene 'use client'. Se ejecuta en el servidor.

import db from './db'
import LikeButton from './LikeButton.client'

export default function Note({ id }) {
  const note = db.query('SELECT * FROM notes WHERE id = ?', [id])

  return (
    <article>
      <h2>{note.title}</h2>
      <p>{note.body}</p>
      <LikeButton noteId={note.id} />
    </article>
  )
}

// LikeButton.client.jsx — Client Component
'use client'

import { useState } from 'react'

export default function LikeButton({ noteId }) {
  const [likes, setLikes] = useState(0)
  return <button onClick={() => setLikes(l => l + 1)}>{likes} ❤️</button>
}

Línea por línea: Note lee directamente de la base de datos (no necesita fetch), renderiza el título y el cuerpo, e inserta LikeButton. LikeButton tiene "use client" porque necesita estado (useState) y eventos (onClick). El servidor serializa la UI de Note; LikeButton se marca como un agujero que el cliente debe hidratar.

4 · Ejemplo real

Imaginemos que TaskFlow necesita una página de dashboard que muestre estadísticas, proyectos recientes y un panel de tareas rápidas. Con la arquitectura actual (SPA), todo se resuelve con fetch y useEffect. Con RSC, el servidor haría las consultas directamente. 

// DashboardPage.server.jsx — Server Component
import db from '@/lib/db'
import { Suspense } from 'react'
import StatsCard from './StatsCard.client'
import RecentProjects from './RecentProjects.server'
import QuickActions from './QuickActions.client'

export default async function DashboardPage({ userId }) {
  // Consultas directas a la base de datos
  const stats = await db.query(`
    SELECT
      COUNT(*) as total,
      SUM(CASE WHEN status = 'done' THEN 1 ELSE 0 END) as completed
    FROM tasks WHERE user_id = ?
  `, [userId])

  return (
    <div className="dashboard">
      <StatsCard stats={stats} />

      <Suspense fallback={<div>Cargando proyectos…</div>}>
        <RecentProjects userId={userId} />
      </Suspense>

      <QuickActions userId={userId} />
    </div>
  )
}

// RecentProjects.server.jsx — Server Component (hijo)
import db from '@/lib/db'
import Card from './Card.client'

export default async function RecentProjects({ userId }) {
  const projects = await db.query(
    'SELECT * FROM projects WHERE user_id = ? ORDER BY updated_at DESC LIMIT 5',
    [userId]
  )

  return (
    <div className="grid">
      {projects.map(p => (
        <Card key={p.id} title={p.name} description={p.description} />
      ))}
    </div>
  )
}

// QuickActions.client.jsx — Client Component
'use client'

import { useState } from 'react'

export default function QuickActions({ userId }) {
  const [open, setOpen] = useState(false)

  return (
    <div>
      <button onClick={() => setOpen(!open)}>
        Acción rápida
      </button>
      {open && (
        <div className="menu">
          <button>Nueva tarea</button>
          <button>Nuevo proyecto</button>
        </div>
      )}
    </div>
  )
}

// Card.client.jsx — Componente puramente visual (podría ser server,
// pero si tiene animaciones, mejor client)
'use client'

export default function Card({ title, description }) {
  return (
    <div className="card">
      <h3>{title}</h3>
      <p>{description}</p>
    </div>
  )
}

Decisiones del ejemplo: DashboardPage y RecentProjects son Server Components porque solo leen datos y renderizan. QuickActions es Client Component porque necesita estado. StatsCard recibe datos ya procesados (stats) y podría ser Server, pero lo marcamos Client porque suele tener gráficos animados. Card es Client porque podría tener micro-interacciones.

5 · Buenas prácticas

Qué hacer

  • Server Component por defecto: si un componente no necesita interactividad, hazlo Server Component. Reduce el bundle automáticamente.
  • Mover "use client" lo más abajo posible: no pongas la directiva en un layout entero; solo en las hojas del árbol que realmente necesitan estado o efectos.
  • Pasar datos serializables: asegúrate de que las props que cruzan la frontera servidor→cliente sean JSON-serializables. Nada de funciones, clases ni símbolos.
  • Usar Suspense con Server Components: el streaming permite mostrar UI parcial mientras llegan los datos más lentos.
  • Extraer lógica de datos en capas: aunque tengas acceso directo a DB, mantén una función getProjects(userId) que sea reutilizable y testeable independientemente del componente.

Qué evitar

  • No uses "use client" en el componente raíz: perderías todos los beneficios de RSC en toda la app.
  • No intentes usar hooks en Server Components: no existen useState, useEffect, useContext en el servidor. Da error de compilación.
  • No serialices objetos complejos: Map, Set, Date (sí, Date se serializa a string), funciones… no pasan la frontera.
  • No asumas que el código Server es seguro si filtras en el cliente: la lógica sensible (permisos, autorización) debe validarse en el servidor siempre.

Por qué

Los Server Components no son una optimización cosmética: cambian el modelo mental. En una SPA clásica, el servidor es solo una API de datos; el cliente decide qué renderizar. Con RSC, el servidor vuelve a tener control sobre el HTML inicial, igual que en los días de PHP o Rails, pero manteniendo la riqueza interactiva de React. Es lo mejor de ambos mundos.

6 · Errores habituales

✘ Error
'use client'  // ← puesto en el layout principal (mal)

import { useEffect } from 'react'
import { Suspense } from 'react'
import ProjectList from './ProjectList'

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <Suspense>
          <ProjectList />  {/* podría ser server, pero todo es client */}
        </Suspense>
      </body>
    </html>
  )
}

Por qué está mal: al marcar el layout como "use client", todo el árbol de componentes se convierte en Client Component. Ningún componente dentro de RootLayout puede ser Server Component. Se pierde el beneficio principal de RSC.

✔ Correcto
// RootLayout.server.jsx — NO tiene 'use client'
import { Suspense } from 'react'
import ProjectList from './ProjectList.server'

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <Suspense>
          <ProjectList />  {/* Server Component */}
        </Suspense>
        {children}
      </body>
    </html>
  )
}

// Solo las hojas interactivas tienen 'use client'
// LikeButton.client.jsx, FilterPanel.client.jsx, etc.
✘ Error
// ProfilePage.server.jsx
export default function ProfilePage({ userId }) {
  const [editing, setEditing] = useState(false)  // ← ERROR: useState no existe aquí

  return <div>...</div>
}

Por qué está mal: los Server Components se ejecutan en Node.js (o similar), donde no hay useState, useEffect ni ningún hook de React. El servidor genera el árbol una vez y termina. El estado es cosa del cliente.

✔ Correcto
// ProfilePage.server.jsx
import ProfileEditor from './ProfileEditor.client'

export default function ProfilePage({ userId }) {
  return (
    <div>
      <ProfileEditor userId={userId} />
    </div>
  )
}

// ProfileEditor.client.jsx
'use client'
import { useState } from 'react'

export default function ProfileEditor({ userId }) {
  const [editing, setEditing] = useState(false)
  return <div>...</div>
}
✘ Error
// DateCard.server.jsx
export default function DateCard({ date }) {
  // Date se serializa a string automáticamente
  return <time>{date.toLocaleDateString()}</time>  // ← ERROR si date es objeto Date
}

// Uso:
<DateCard date={new Date()} />

Por qué está mal: aunque Date se serializa a string al cruzar la frontera servidor→cliente, dentro del Server Component sigue siendo un objeto Date del servidor y toLocaleDateString() funciona. El problema real aparece si intentas pasar el Date a un Client Component: el cliente recibe un string, no un objeto Date. Serializa siempre antes de pasar la frontera.

✔ Correcto
// DateCard.server.jsx
export default function DateCard({ dateString }) {
  return <time>{new Date(dateString).toLocaleDateString()}</time>
}

// Uso:
<DateCard dateString={new Date().toISOString()} />

7 · Ejercicio guiado

Vamos a refactorizar un componente de TaskFlow que actualmente es un Client Component para dividirlo en Server + Client. Partimos de esto: 

// TaskList.jsx — SPA actual: todo en cliente
import { useEffect, useState } from 'react'
import { taskService } from '../services/taskService'

export default function TaskList({ projectId }) {
  const [tasks, setTasks] = useState([])
  const [loading, setLoading] = useState(true)

  useEffect(() => {
    taskService.getByProject(projectId)
      .then(setTasks)
      .finally(() => setLoading(false))
  }, [projectId])

  if (loading) return <p>Cargando tareas…</p>

  return (
    <ul>
      {tasks.map(t => (
        <li key={t.id}>
          <span>{t.title}</span>
          <button onClick={() => taskService.toggleDone(t.id)}>
            {t.done ? '✅' : '⬜'}
          </button>
        </li>
      ))}
    </ul>
  )
}

Paso 1: Separar la lógica de datos

El Server Component se encargará de obtener los datos. Creamos TaskList.server.jsx: 

// TaskList.server.jsx
import db from '@/lib/db'
import TaskItem from './TaskItem.client'

export default async function TaskList({ projectId }) {
  const tasks = await db.query(
    'SELECT * FROM tasks WHERE project_id = ? ORDER BY position',
    [projectId]
  )

  return (
    <ul>
      {tasks.map(t => (
        <TaskItem key={t.id} task={t} />
      ))}
    </ul>
  )
}

Paso 2: El Client Component solo para la interactividad

// TaskItem.client.jsx
'use client'

import { taskService } from '../services/taskService'

export default function TaskItem({ task }) {
  async function handleToggle() {
    await taskService.toggleDone(task.id)
  }

  return (
    <li>
      <span>{task.title}</span>
      <button onClick={handleToggle}>
        {task.done ? '✅' : '⬜'}
      </button>
    </li>
  )
}

Paso 3: Comparación

Antes (SPA) Después (RSC)
2 estados + 1 efecto 0 estados en servidor
Fetch desde el cliente (latencia extra) Query directa a DB (0 ms de red)
Bundle: ~3 KB de JS Bundle: ~1 KB (solo botón toggle)
Renderizado: cliente espera datos Servidor envía HTML listo

El ejercicio muestra que la mayoría del código no necesitaba estar en el cliente. Solo el botón toggle requiere interactividad; la lista entera puede ser Server Component.

8 · Reto

Dado el siguiente componente SPA de TaskFlow que muestra un panel de actividad reciente con un filtro por tipo de evento: 

// ActivityPanel.jsx — SPA actual
import { useEffect, useState } from 'react'
import { activityService } from '../services/activityService'

export default function ActivityPanel({ projectId }) {
  const [events, setEvents] = useState([])
  const [filter, setFilter] = useState('all')

  useEffect(() => {
    activityService.getRecent(projectId).then(setEvents)
  }, [projectId])

  const filtered = filter === 'all'
    ? events
    : events.filter(e => e.type === filter)

  return (
    <div>
      <select onChange={e => setFilter(e.target.value)}>
        <option value="all">Todas</option>
        <option value="comment">Comentarios</option>
        <option value="status">Cambios de estado</option>
      </select>
      <ul>
        {filtered.map(e => (
          <li key={e.id}>
            <strong>{e.user}</strong> — {e.description}
          </li>
        ))}
      </ul>
    </div>
  )
}

Reto: refactoriza este componente para usar la arquitectura RSC, separando la parte de servidor (obtener datos) de la parte de cliente (el filtro interactivo). Piensa qué debe ir en cada lado y cómo pasar los datos serializados a través de la frontera.

Pista: el filtro por tipo podría hacerse en el servidor si es parte de la URL, pero aquí es interactivo (caja select) → debe estar en el cliente.

No lo resuelvas todavía. Inténtalo por tu cuenta antes de buscar la solución en la siguiente lección.

9 · Resumen

  • React Server Components se ejecutan una vez en el servidor y no envían JavaScript al cliente.
  • "use client" marca la frontera: los componentes que necesitan estado, efectos o eventos deben declararlo.
  • Beneficios: bundle reducido (a veces 30–50 %), acceso directo a datos, seguridad (la lógica sensible no llega al cliente), streaming con Suspense.
  • Limitaciones: no hay hooks, no hay eventos, no hay estado. Solo renderizado puro basado en props.
  • Next.js App Router usa RSC por defecto; el ecosistema React se mueve hacia esta arquitectura.
  • Nuestra app con Vite es una SPA clásica. El concepto RSC es crucial para entender hacia dónde va React, aunque nuestro proyecto no lo implemente directamente.
  • Migración futura: separar lógica de datos en capas (servicios/consultas) y mantener los componentes de UI lo más puros posible prepara el camino para adoptar RSC cuando el proyecto migre a Next.js u otro framework con soporte RSC.

10 · Preguntas frecuentes

¿Puedo usar Server Components en Vite?

Vite (sin framework adicional) no soporta RSC de forma nativa. Necesitas un meta-framework como Next.js (App Router) o Remix. Hay experimentos como vite-plugin-react-server pero no son estables. Si empiezas un proyecto nuevo que quieras que use RSC, elige Next.js.

¿RSC reemplaza a las SPAs?

No. RSC es una herramienta complementaria. Las SPAs (como nuestra app TaskFlow) siguen siendo excelentes para aplicaciones con mucha interactividad. RSC brilla en páginas con mucho contenido y poca interactividad (dashboards, landing pages, e-commerce). Muchas aplicaciones usarán una mezcla de ambos.

¿Qué pasa con el SEO?

RSC mejora el SEO drásticamente porque el servidor envía HTML completo (no un div vacío que luego se hidrata). Los crawlers ven el contenido real desde la primera petición, sin necesidad de SSR adicional. Combinado con SSR, es la mejor solución actual para SEO en React.

¿Puedo tener componentes React puros (solo props, sin estado) en el cliente aunque no necesiten interactividad?

Sí, perfectamente. No todos los componentes sin estado necesitan ser Server Components. Un componente que solo recibe props y renderiza puede vivir en el cliente sin problemas; simplemente no estás aprovechando la reducción de bundle de RSC. La decisión depende de si ese componente accede a datos del servidor o no.

¿Cómo manejo la autenticación con RSC?

La autenticación se verifica en el servidor (leyendo cookies/tokens) y se pasa como prop serializable a los Client Components. El servidor puede decidir qué renderizar según el rol del usuario sin exponer la lógica de permisos al cliente. Es más seguro que la SPA tradicional donde la lógica de autorización vive en JavaScript visible.

¿Qué es el "React Flight Protocol"?

Es el formato de serialización que React usa para enviar Server Components al cliente. No es JSON plano: es un formato de streaming que intercala referencias a módulos del cliente con fragmentos de UI serializada. Se llama "Flight" porque los datos "vuelan" del servidor al cliente. No necesitas conocer los detalles para usar RSC, pero es interesante saber que existe.

Si uso RSC, ¿sigue teniendo sentido React Query o SWR?

Sí, pero su rol cambia. En una app con RSC, las consultas iniciales se hacen en el servidor (sin necesidad de React Query). Las consultas posteriores (refetch, mutaciones, revalidación) siguen siendo responsabilidad del cliente. React Query se usa entonces para caching y sincronización de datos del lado del cliente, no para la carga inicial. Siguen siendo herramientas complementarias.

¿Debo reescribir TaskFlow con RSC?

No necesariamente. TaskFlow es una SPA construida con Vite, y funciona perfectamente así. Si el proyecto creciera y necesitaras mejor SEO, rendimiento de carga inicial o acceso directo a DB, podrías considerar migrar a Next.js progresivamente. Muchas aplicaciones profesionales mantienen partes en SPA y partes con RSC según las necesidades de cada página. Lo importante es entender el concepto para tomar buenas decisiones en el futuro.
