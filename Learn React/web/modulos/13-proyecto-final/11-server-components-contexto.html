Server Components: contexto y futuro

Módulo 13 · Proyecto final: TaskFlow 🕐 40 minutos

1 · Introducción

Hemos construido TaskFlow como una SPA clásica: todo el JavaScript se descarga en el navegador y la aplicación se renderiza por completo en el cliente. Este modelo es sólido y sigue siendo el más común, pero tiene límites: el bundle crece, el SEO se complica y acceder a datos exige exponer lógica de acceso a través de la API.

Qué vamos a aprender hoy: React Server Components (RSC), el cambio arquitectónico más profundo de React en años. No vamos a migrar TaskFlow (Vite no lo soporta de forma nativa), pero entenderlo es imprescindible: es el modelo hacia el que apunta el ecosistema.

Qué problema resuelve: las SPAs envían demasiado JavaScript, incluso código que solo tiene sentido en un servidor (consultas a base de datos, transformaciones pesadas, secretos). RSC permiten decidir qué se ejecuta dónde, moviendo al servidor los componentes que no necesitan interactividad.

Cuándo se utiliza: cuando tienes componentes que solo leen datos y no necesitan estado ni eventos. Next.js (App Router) lo usa por defecto, y la mayoría de frameworks del ecosistema avanza hacia ahí.

Errores típicos: pensar que RSC reemplazan a las SPAs (conviven), usar hooks dentro de un Server Component (no existen), o poner "use client" en el nivel raíz y tirar por la borda todo el beneficio.

2 · Teoría

¿Qué es un Server Component?

Un React Server Component es un componente que se ejecuta una sola vez en el servidor durante la petición, produce una descripción serializable de su UI y nunca envía su JavaScript al cliente. Su código muere en el servidor.

ProjectList.server.jsx — se ejecuta en el servidor
// NO tiene "use client". Este archivo jamás llega al navegador.
import db from "./database.js";

export default function ProjectList() {
  // Acceso DIRECTO a la base de datos: sin API REST intermedia.
  const projects = db.query("SELECT * FROM projects ORDER BY created_at DESC");

  return (
    <ul>
      {projects.map((p) => (
        <li key={p.id}>{p.name}</li>
      ))}
    </ul>
  );
}

La frontera: "use client"

La directiva "use client" marca el límite entre servidor y cliente. A partir del componente que la declara, él y todo su subárbol pasan a ser Client Components. Es como una frontera aduanera: al cruzarla, tu código empieza a viajar al navegador.

src/components/LikeButton.jsx — Client Component
// Primera línea OBLIGATORIA para marcar la frontera.
"use client";

import { useState } from "react";

export default function LikeButton({ projectId }) {
  const [liked, setLiked] = useState(false);

  return (
    <button onClick={() => setLiked((v) => !v)}>
      {liked ? "❤️" : "🤍"}
    </button>
  );
}
src/app/ProjectPage.server.jsx — Server que usa el Client
import LikeButton from "./LikeButton.jsx"; // ← aquí se cruza la frontera

export default function ProjectPage({ projectId }) {
  return (
    <div>
      <h1>Proyecto {projectId}</h1>
      <LikeButton projectId={projectId} /> {/* se hidrata en cliente */}
    </div>
  );
}

Cómo se comunican: props serializables

Los Server Components pasan a los Client Components props serializables (strings, números, booleanos, arrays y objetos planos). No pueden pasar funciones, clases, Map, Set ni símbolos. Los Client Components, a su vez, pueden recibir Server Components como children.

Petición HTTP │ ▼ Servidor ejecuta los Server Components │ ├── Consulta la base de datos / servicios internos ├── Genera una descripción serializada del árbol (protocolo "Flight") └── La envía al cliente │ ▼ Cliente recibe el árbol pre-renderizado │ ├── El HTML de los Server Components ya está listo (0 JS) └── Hidrata SOLO los Client Components (los que tienen interactividad)

RSC no es lo mismo que SSR

Es la confusión más frecuente. SSR (Server-Side Rendering) genera HTML en el servidor para que se vea rápido, pero sigue enviando el JavaScript del componente al cliente para hidratarlo. RSC no envía nada de JavaScript del Server Component. SSR y RSC se combinan: SSR da HTML rápido; RSC decide qué componentes no necesitan viajar al cliente.

SSRRSC
Genera HTML en servidorSíSí
Envía el JS del componenteSí (para hidratar)No
Acceso directo a la DBPosible pero no es el focoSí, es su esencia
Puede ser interactivoSí (tras hidratar)No (no tiene estado)

Streaming con Suspense

El servidor puede enviar el árbol por fragmentos a medida que lo produce. Con Suspense, las partes lentas (una consulta pesada) se streamean cuando están listas, mientras el resto ya se muestra. Mejora el Time To First Byte y la percepción de velocidad.

streaming de una parte lenta
import { Suspense } from "react";
import ProjectList from "./ProjectList.server.jsx";

export default function Dashboard() {
  return (
    <Suspense fallback={<p>Cargando proyectos…</p>}>
      <ProjectList /> {/* se streamea cuando la DB responde */}
    </Suspense>
  );
}

3 · Ejemplo mínimo

La esencia de RSC en el menor código posible: un Server Component que lee datos y un Client Component que añade un botón interactivo.

Note.server.jsx — lee datos (servidor)
// Sin "use client": vive en el servidor.
import db from "./db.js";
import LikeButton from "./LikeButton.jsx";

export default function Note({ id }) {
  const note = db.query("SELECT * FROM notes WHERE id = ?", [id]);

  return (
    <article>
      <h2>{note.title}</h2>
      <p>{note.body}</p>
      <LikeButton noteId={note.id} />
    </article>
  );
}
LikeButton.jsx — interactividad (cliente)
"use client";

import { useState } from "react";

export default function LikeButton({ noteId }) {
  const [likes, setLikes] = useState(0);
  return (
    <button onClick={() => setLikes((n) => n + 1)}>{likes} ❤️</button>
  );
}

Línea por línea:

  1. Note lee de la base de datos directamente: nada de fetch a una API intermedia.
  2. Renderiza título y cuerpo como HTML estático (su JavaScript nunca llega al cliente).
  3. LikeButton necesita estado y un evento, así que lleva "use client": se convierte en un «agujero» que el cliente hidrata.
  4. El servidor serializa la UI de Note; el cliente solo descarga el código del botón.

4 · Ejemplo real

Imaginemos que TaskFlow migrara a un framework con RSC. El dashboard sería un caso de estudio perfecto: la mayoría son datos (estadísticas, proyectos recientes) y solo unos pocos botones son interactivos.

DashboardPage.server.jsx — orquesta datos en el servidor
// Server Component
import db from "@/lib/db.js";
import { Suspense } from "react";
import StatsCard from "./StatsCard.jsx";
import RecentProjects from "./RecentProjects.server.jsx";
import QuickActions from "./QuickActions.jsx";

export default async function DashboardPage({ userId }) {
  // Consulta directa a la base de datos (no hay API intermedia).
  const stats = await db.query(
    `SELECT COUNT(*) AS total,
            SUM(CASE WHEN status = 'done' THEN 1 ELSE 0 END) AS completed
       FROM tasks WHERE user_id = ?`,
    [userId]
  );

  return (
    <div className="dashboard">
      <StatsCard stats={stats} />

      <Suspense fallback={<div>Cargando proyectos…</div>}>
        <RecentProjects userId={userId} />
      </Suspense>

      <QuickActions userId={userId} />
    </div>
  );
}
RecentProjects.server.jsx — Server Component hijo
import db from "@/lib/db.js";
import ProjectCard from "./ProjectCard.jsx";

export default async function RecentProjects({ userId }) {
  const projects = await db.query(
    "SELECT * FROM projects WHERE user_id = ? ORDER BY updated_at DESC LIMIT 5",
    [userId]
  );

  return (
    <div className="grid">
      {projects.map((p) => (
        <ProjectCard key={p.id} name={p.name} description={p.description} />
      ))}
    </div>
  );
}
QuickActions.jsx — el único Client Component
"use client";

import { useState } from "react";

export default function QuickActions({ userId }) {
  const [open, setOpen] = useState(false);

  return (
    <div>
      <button onClick={() => setOpen((v) => !v)}>Acción rápida</button>
      {open && (
        <div className="menu">
          <button>Nueva tarea</button>
          <button>Nuevo proyecto</button>
        </div>
      )}
    </div>
  );
}

Decisiones del ejemplo: DashboardPage y RecentProjects son Server Components porque solo leen datos y renderizan. QuickActions es Client porque tiene estado. StatsCard recibe estadísticas ya calculadas y podría ser Server, pero lo consideraríamos Client si tuviera gráficos animados. ProjectCard sería Client únicamente si necesitara micro-interacciones; si es puramente visual, mejor Server.

5 · Buenas prácticas

Qué hacer

  • Server Component por defecto: si un componente no necesita estado ni eventos, mantenlo en el servidor. Reduce el bundle sin esfuerzo.
  • Bajar "use client" lo más posible: no marques un layout o una página entera; solo las hojas que de verdad son interactivas.
  • Props serializables: al cruzar la frontera, solo datos JSON-ables.
  • Usar Suspense para streaming: muestra UI parcial mientras llegan los datos lentos.
  • Extraer el acceso a datos a funciones: aunque el Server Component pueda consultar la DB, envuelve las consultas en funciones reutilizables y testeables (getProjects(userId)).

Qué evitar

  • "use client" en la raíz: convierte todo el árbol en cliente y pierdes el beneficio principal.
  • Hooks en Server Components: useState, useEffect y useContext no existen ahí; dan error.
  • Objetos no serializables: Map, Set, funciones y clases no cruzan la frontera.
  • Confiar la autorización al cliente: la lógica de permisos va en el servidor, siempre.

Por qué importa (aunque TaskFlow sea una SPA)

RSC no es una optimización cosmética: cambia el modelo mental. En una SPA, el servidor es «solo» una API y el cliente decide todo. Con RSC, el servidor vuelve a controlar el HTML inicial (como en la época de PHP o Rails) sin renunciar a la interactividad de React. Es lo mejor de ambos mundos, y hacia ahí va el ecosistema. Aunque hoy tu proyecto con Vite no lo use, entenderlo te prepara para el mañana.

6 · Errores habituales

Error 1: "use client" en el layout raíz

✘ Incorrecto 
// RootLayout.jsx
"use client";   // ← convierte TODO el árbol en Client Components

import { Suspense } from "react";
import ProjectList from "./ProjectList.jsx";

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <Suspense>
          <ProjectList />  {/* ya NO puede ser Server Component */}
        </Suspense>
        {children}
      </body>
    </html>
  );
}
✔ Correcto 
// RootLayout.server.jsx — SIN "use client"
import { Suspense } from "react";
import ProjectList from "./ProjectList.server.jsx";

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <Suspense>
          <ProjectList />   {/* sigue siendo Server Component */}
        </Suspense>
        {children}
      </body>
    </html>
  );
}
// "use client" SOLO en las hojas interactivas: LikeButton, FilterPanel…

Error 2: usar useState en un Server Component

✘ Incorrecto 
// ProfilePage.server.jsx
import { useState } from "react";

export default function ProfilePage({ userId }) {
  const [editing, setEditing] = useState(false); // ← error: no hay hooks aquí
  return <div>…</div>;
}
✔ Correcto 
// ProfilePage.server.jsx (servidor: solo datos)
import ProfileEditor from "./ProfileEditor.jsx";

export default function ProfilePage({ userId }) {
  return <div><ProfileEditor userId={userId} /></div>;
}

// ProfileEditor.jsx (cliente: sí tiene estado)
"use client";

export default function ProfileEditor({ userId }) {

}

Error 3: pasar una función como prop a través de la frontera

✘ Incorrecto 
// El Server Component intenta pasar un callback (no serializable).
<ClientWidget onSave={() => db.save()} />
// Error: "Functions cannot be passed to Client Components".
✔ Correcto 
// Pasa DATOS; la acción la define el propio Client Component.
<ClientWidget projectId={project.id} initialName={project.name} />

// Y en el cliente, la acción hace su propio fetch al servidor:
"use client";
function ClientWidget({ projectId, initialName }) {
  async function save(name) {
    await fetch(`/api/projects/${projectId}`, { method: "PUT", body: name });
  }
  // …
}

7 · Ejercicio guiado

Refactoriza un componente de TaskFlow que actualmente es un Client Component para dividirlo en Server + Client. Partimos de la versión SPA:

TaskList.jsx — versión SPA (todo en cliente)
import { useEffect, useState } from "react";
import { taskService } from "../services/taskService.js";

export default function TaskList({ projectId }) {
  const [tasks, setTasks] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    taskService.getByProject(projectId)
      .then(setTasks)
      .finally(() => setLoading(false));
  }, [projectId]);

  if (loading) return <p>Cargando tareas…</p>;

  return (
    <ul>
      {tasks.map((t) => (
        <li key={t.id}>
          <span>{t.title}</span>
          <button onClick={() => taskService.toggleDone(t.id)}>
            {t.done ? "✅" : "⬜"}
          </button>
        </li>
      ))}
    </ul>
  );
}

  1. Paso 1 — Lógica de datos al servidor. El Server Component lee de la base de datos; el cliente no necesita estado de carga ni efecto.

    // TaskList.server.jsx
import db from "@/lib/db.js";
import TaskItem from "./TaskItem.jsx";

export default async function TaskList({ projectId }) {
  const tasks = await db.query(
    "SELECT * FROM tasks WHERE project_id = ? ORDER BY position",
    [projectId]
  );

  return (
    <ul>
      {tasks.map((t) => (
        <TaskItem key={t.id} task={t} />
      ))}
    </ul>
  );
}

  2. Paso 2 — Client Component solo para la interactividad. El botón que marca completada sí necesita cliente.

    // TaskItem.jsx
"use client";

import { taskService } from "../services/taskService.js";

export default function TaskItem({ task }) {
  async function handleToggle() {
    await taskService.toggleDone(task.id);
  }

  return (
    <li>
      <span>{task.title}</span>
      <button onClick={handleToggle}>{task.done ? "✅" : "⬜"}</button>
    </li>
  );
}

  3. Paso 3 — Compara. Antes: 2 estados + 1 efecto + fetch desde el cliente. Después: 0 estados en el servidor, una consulta directa y un bundle mucho menor (solo el botón). La mayoría del componente no necesitaba estar en el cliente.

Fetch desde el cliente (latencia extra)Consulta directa a la DB (sin red extra)

8 · Reto

🎯 De SPA a RSC: el panel de actividad

Dado este componente SPA de TaskFlow, que muestra la actividad reciente con un filtro por tipo de evento: 

// ActivityPanel.jsx — SPA actual
import { useEffect, useState } from "react";
import { activityService } from "../services/activityService.js";

export default function ActivityPanel({ projectId }) {
  const [events, setEvents] = useState([]);
  const [filter, setFilter] = useState("all");

  useEffect(() => {
    activityService.getRecent(projectId).then(setEvents);
  }, [projectId]);

  const filtered = filter === "all"
    ? events
    : events.filter((e) => e.type === filter);

  return (
    <div>
      <select onChange={(e) => setFilter(e.target.value)}>
        <option value="all">Todas</option>
        <option value="comment">Comentarios</option>
        <option value="status">Cambios de estado</option>
      </select>
      <ul>
        {filtered.map((e) => (
          <li key={e.id}><strong>{e.user}</strong> — {e.description}</li>
        ))}
      </ul>
    </div>
  );
}

El reto:

  1. Divide el componente en un Server Component que obtiene los eventos (consulta directa) y un Client Component que aporta el filtro interactivo (el <select>).
  2. Decide qué cruza la frontera y cómo: los eventos son datos serializables, así que el servidor puede pasarlos como prop.
  3. Modo avanzado: explica cómo harías que el filtro no necesitara cliente: poniendo el filtro en la URL (search params) y filtrando en el servidor con cada navegación. ¿Qué ganas y qué pierdes frente a la versión con estado local?
  4. Justifica, componente por componente, cuál va en cada lado y por qué.

Pista: el filtro es interactivo (un <select>), así que el control vive en el cliente. Pero la lista filtrada podría calcularse en el servidor si el filtro formara parte de la URL.

No lo resuelvas todavía. Piensa primero la frontera; el código es la parte fácil.

9 · Resumen

  • React Server Components se ejecutan una vez en el servidor y no envían JavaScript al cliente.
  • "use client" marca la frontera: los componentes que necesitan estado, efectos o eventos deben declararlo.
  • Beneficios: bundle más pequeño, acceso directo a datos, seguridad (la lógica sensible no sale del servidor) y streaming con Suspense.
  • Limitaciones: sin hooks, sin eventos, sin estado. Solo renderizado puro basado en props serializables.
  • RSC ≠ SSR: SSR genera HTML pero envía el JS; RSC no envía el JS del Server Component.
  • TaskFlow es una SPA y funciona perfectamente así. Conocer RSC importa para entender hacia dónde va React y para migrar con criterio cuando convenga.
  • Preparación: separar el acceso a datos en funciones y mantener los componentes de UI puros allana el camino a RSC en el futuro.

10 · Preguntas frecuentes

¿Puedo usar Server Components con Vite, como en TaskFlow?

Vite por sí solo no soporta RSC de forma nativa. Necesitas un meta-framework como Next.js (App Router) o Remix. Existen experimentos, pero no son estables. Nuestra app con Vite es una SPA y seguirá siéndolo; RSC es aquí conocimiento de contexto y futuro.

¿RSC reemplaza a las SPAs?

No. Son complementarios. Las SPAs siguen siendo ideales para aplicaciones con mucha interactividad (como un tablero Kanban completo). RSC brilla en páginas con mucho contenido y poca interacción (dashboards de solo lectura, e-commerce, blogs). Muchas apps combinarán ambos modelos.

¿Por qué no puedo usar useState en un Server Component?

Porque el Server Component se ejecuta una vez, en el servidor, y termina. No hay «re-render» que gestionar, ni interacción del usuario que dispare cambios. El estado es, por definición, cosa del cliente. Para interactividad, delega en un Client Component.

¿Qué es el «React Flight Protocol»?

Es el formato con el que React envía los Server Components al cliente. No es JSON plano: es un formato de streaming que mezcla fragmentos de UI serializada con referencias a módulos del cliente. Se llama «Flight» porque los datos «vuelan» del servidor al navegador. No necesitas conocerlo para usarlo, pero saber que existe ayuda a entender que RSC no es «SSR con otro nombre».

¿Debo reescribir TaskFlow con RSC?

No. TaskFlow es una SPA con Vite y cumple su propósito. Si el proyecto creciera y necesitaras mejor SEO, carga inicial más rápida o acceso directo a la base de datos, podrías migrar a Next.js gradualmente, página por página. Mantener el acceso a datos en funciones y la UI pura te lo pondrá fácil. Lo importante hoy es entender el concepto para decidir bien en cada proyecto.
