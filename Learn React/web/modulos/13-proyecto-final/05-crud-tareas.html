CRUD de tareas, etiquetas y prioridades

Módulo 13 · Proyecto final: TaskFlow 🕐 60 minutos

1 · Introducción

Con los proyectos listos llega el corazón de TaskFlow: las tareas. Igual que Trello, mostraremos las tareas en un tablero con columnas por estado (Por hacer, En progreso, Hechas), y cada tarea llevará etiquetas y una prioridad.

Qué vamos a aprender hoy: a modelar y manipular tareas con el CRUD completo, a moverlas entre columnas, a asignarles etiquetas y prioridad, y a construir un drag & drop nativo sin librerías externas.

Qué problema resuelve: un tablero no es solo «una lista dividida por columnas». El reto real es que mover una tarea se sienta instantáneo (optimista), que el cambio de estado se refleje en la columna correcta y que un fallo del servidor revierta sin romper la interfaz.

Cuándo se utiliza: los tableros Kanban son el patrón dominante para gestionar trabajo por estados (Trello, Jira, Linear, GitHub Projects). Entenderlo por dentro te permite adaptarlo a cualquier dominio.

Errores típicos: guardar las tareas «dentro» de cada tarea de columna (estado duplicado), derivar la columna a partir de un índice en lugar del estado real, o actualizar solo la UI y olvidarse de persistir.

2 · Teoría

Modelo de una tarea

Definir el modelo bien es media batalla. Una tarea de TaskFlow tiene identidad (id), pertenencia (projectId), contenido (title, description), y varios ejes de clasificación (status, priority, labels, position).

modelo (contrato con la API)
{
  "id": "b1f0…",
  "projectId": "a7c2…",
  "title": "Diseñar la pantalla de login",
  "description": "Wireframe + estados de error",
  "status": "todo",            // "todo" | "inProgress" | "done"
  "priority": "high",          // "low" | "medium" | "high" | "urgent"
  "labels": [
    { "id": "l1", "name": "diseño", "color": "#f78c6c" },
    { "id": "l2", "name": "frontend", "color": "#61dafb" }
  ],
  "position": 1000,            // orden dentro de la columna
  "dueDate": "2026-11-02",
  "createdAt": "2026-10-11T09:00:00Z"
}

El tablero: una columna no es un array aparte

El error más común al construir un Kanban es modelar las columnas como tres arrays de tareas (todo[], inProgress[], done[]). Eso duplica la verdad: la columna de una tarea es su status. La forma correcta es tener un solo array de tareas y derivar las columnas en el render.

ESTADO (una sola fuente de verdad) tasks = [ {id, status:"todo"}, {id, status:"done"}, {id, status:"todo"} ] │ render (derivado, no almacenado) ▼ ┌───────────────┬──────────────────┬───────────────┐ │ POR HACER │ EN PROGRESO │ HECHAS │ │ task A │ (ninguna) │ task B │ │ task C │ │ │ └───────────────┴──────────────────┴───────────────┘ Mover A de "todo" a "done" = cambiar tasks[0].status. Las columnas se recalculan solas. Imposible desincronizarse.

Etiquetas: muchos-a-muchos

Una etiqueta puede estar en muchas tareas y una tarea puede tener muchas etiquetas (relación muchos-a-muchos). En el frontend las representamos como un array de objetos dentro de la tarea. Streamlit, Notion y Trello las muestran como «chips» coloreados. En la API, la relación se gestiona en el backend (tabla intermedia), pero al cliente le llega el array ya resuelto.

Tarea ────< TaskLabel >──── Etiqueta │ │ └── labels: [{id,name,color}] ─┘ (lo que recibe el cliente)

Drag & drop nativo del navegador

No hace falta una librería para arrastrar tareas entre columnas. La API HTML5 de drag and drop es suficiente y usa tres eventos: onDragStart (en la tarjeta), onDragOver (en la columna, para permitir soltar) y onDrop (en la columna, para recibir la tarjeta).

onDragStart (tarjeta) → guardamos el id de la tarea que se arrastra │ ▼ onDragOver (columna) → event.preventDefault() para PERMITIR el drop │ ▼ onDrop (columna) → leemos el id y actualizamos su status

3 · Ejemplo mínimo

Empecemos por la operación más característica del tablero: mover una tarea de estado. Es una actualización parcial (PATCH) optimista.

src/services/taskService.js
import { request } from "./apiClient.js";

export const taskService = {
  // GET /api/projects/{projectId}/tasks?status=&priority=&label=&search=
  listByProject: (projectId, filters = {}) => {
    const params = new URLSearchParams(filters);
    return request(`/projects/${projectId}/tasks?${params}`);
  },

  // POST /api/projects/{projectId}/tasks → { task }
  create: (projectId, data) =>
    request(`/projects/${projectId}/tasks`, { method: "POST", body: data }),

  // PUT /api/tasks/{id} → { task }
  update: (taskId, data) =>
    request(`/tasks/${taskId}`, { method: "PUT", body: data }),

  // PATCH /api/tasks/{id}/status → { task }  (cambio parcial: solo el estado)
  changeStatus: (taskId, status) =>
    request(`/tasks/${taskId}/status`, { method: "PATCH", body: { status } }),

  // DELETE /api/tasks/{id} → 204
  remove: (taskId) => request(`/tasks/${taskId}`, { method: "DELETE" }),
};
src/hooks/useTasks.js — mover con actualización optimista
import { useState } from "react";
import { taskService } from "../services/taskService.js";

// Hook que encapsula el estado de una lista de tareas y sus mutaciones.
export function useTasks(initial = []) {
  const [tasks, setTasks] = useState(initial);

  // Mueve una tarea a otro estado de forma optimista, con rollback.
  async function moveTask(taskId, status) {
    const snapshot = tasks; // guardamos para poder deshacer

    // 1) UI instantánea: cambiamos el status en el array.
    setTasks((current) =>
      current.map((t) => (t.id === taskId ? { ...t, status } : t))
    );

    try {
      // 2) Persistimos en el servidor y reconciliamos con su respuesta.
      const { task } = await taskService.changeStatus(taskId, status);
      setTasks((current) => current.map((t) => (t.id === task.id ? task : t)));
    } catch (err) {
      // 3) Rollback: si falla, volvemos al estado anterior.
      setTasks(snapshot);
      throw err;
    }
  }

  return { tasks, setTasks, moveTask };
}

Línea por línea:

  1. snapshot = tasks — aunque el array es inmutable, guardar la referencia nos permite restaurarla tal cual.
  2. Primer setTasks — cambio optimista: la tarjeta salta de columna al instante.
  3. changeStatus devuelve la tarea actualizada; la reemplazamos por la del servidor por si el backend ajustó algo (p. ej. updatedAt).
  4. throw err — dejamos que quien llamó decida cómo avisar (un toast, un mensaje…).

4 · Ejemplo real

El tablero completo: columnas derivadas, tarjetas con etiquetas y prioridad, drag & drop nativo y un panel para crear/editar tareas.

src/components/tasks/Board.jsx
import { useState } from "react";
import TaskColumn from "./TaskColumn.jsx";

// Definimos las columnas UNA vez. El orden y la etiqueta viven aquí.
const COLUMNS = [
  { id: "todo", title: "Por hacer" },
  { id: "inProgress", title: "En progreso" },
  { id: "done", title: "Hechas" },
];

export default function Board({ tasks, onMove, onOpenTask }) {
  // Id de la tarea que se está arrastrando (estado del drag & drop).
  const [draggingId, setDraggingId] = useState(null);

  // Derivamos las tareas de cada columna: NO se almacenan por separado.
  function tasksOf(status) {
    return tasks
      .filter((t) => t.status === status)
      .sort((a, b) => a.position - b.position);
  }

  function handleDrop(status) {
    if (!draggingId) return;
    const task = tasks.find((t) => t.id === draggingId);
    setDraggingId(null);
    // Solo movemos si de verdad cambia de columna.
    if (task && task.status !== status) onMove(draggingId, status);
  }

  return (
    <div className="board">
      {COLUMNS.map((col) => (
        <TaskColumn
          key={col.id}
          column={col}
          tasks={tasksOf(col.id)}
          onDragStartTask={setDraggingId}
          onDropTask={handleDrop}
          onOpenTask={onOpenTask}
        />
      ))}
    </div>
  );
}
src/components/tasks/TaskColumn.jsx
import TaskCard from "./TaskCard.jsx";

export default function TaskColumn({
  column,
  tasks,
  onDragStartTask,
  onDropTask,
  onOpenTask,
}) {
  // onDragOver DEBE llamar a preventDefault: es lo que autoriza el drop.
  function handleDragOver(event) {
    event.preventDefault();
  }

  function handleDrop(event) {
    event.preventDefault();
    onDropTask(column.id);
  }

  return (
    <section
      className="board__column"
      onDragOver={handleDragOver}
      onDrop={handleDrop}
    >
      <header className="board__column-header">
        <h3>{column.title}</h3>
        <span className="board__count">{tasks.length}</span>
      </header>

      <div className="board__column-body">
        {tasks.length === 0 && (
          <p className="board__empty">Suelta una tarea aquí</p>
        )}
        {tasks.map((task) => (
          <TaskCard
            key={task.id}
            task={task}
            onDragStart={() => onDragStartTask(task.id)}
            onOpen={() => onOpenTask(task)}
          />
        ))}
      </div>
    </section>
  );
}

src/components/tasks/TaskPanel.jsx — crear/editar con etiquetas y prioridad
import { useState } from "react";

const ALL_LABELS = [
  { id: "l1", name: "diseño", color: "#f78c6c" },
  { id: "l2", name: "frontend", color: "#61dafb" },
  { id: "l3", name: "backend", color: "#c3e88d" },
  { id: "l4", name: "bug", color: "#ff5370" },
];

export default function TaskPanel({ task, onSave, onClose }) {
  const [form, setForm] = useState({
    title: task?.title ?? "",
    description: task?.description ?? "",
    priority: task?.priority ?? "medium",
    dueDate: task?.dueDate ?? "",
    // Guardamos solo los IDs de las etiquetas seleccionadas.
    labelIds: task?.labels.map((l) => l.id) ?? [],
  });
  const [saving, setSaving] = useState(false);

  function setField(name, value) {
    setForm((current) => ({ ...current, [name]: value }));
  }

  // Alterna una etiqueta en el array de seleccionadas.
  function toggleLabel(labelId) {
    setForm((current) => ({
      ...current,
      labelIds: current.labelIds.includes(labelId)
        ? current.labelIds.filter((id) => id !== labelId)
        : [...current.labelIds, labelId],
    }));
  }

  async function handleSubmit(event) {
    event.preventDefault();
    if (form.title.trim() === "") return;

    setSaving(true);
    try {
      // Traducimos labelIds a los objetos completos que espera la API.
      const labels = ALL_LABELS.filter((l) => form.labelIds.includes(l.id));
      await onSave({
        title: form.title.trim(),
        description: form.description,
        priority: form.priority,
        dueDate: form.dueDate || null,
        labels,
      });
    } finally {
      setSaving(false);
    }
  }

  return (
    <aside className="panel" role="dialog" aria-label="Detalle de la tarea">
      <form className="panel__form" onSubmit={handleSubmit}>
        <h2>{task ? "Editar tarea" : "Nueva tarea"}</h2>

        <label>
          Título
          <input
            value={form.title}
            onChange={(e) => setField("title", e.target.value)}
            autoFocus
          />
        </label>

        <label>
          Descripción
          <textarea
            rows={4}
            value={form.description}
            onChange={(e) => setField("description", e.target.value)}
          />
        </label>

        <label>
          Prioridad
          <select
            value={form.priority}
            onChange={(e) => setField("priority", e.target.value)}
          >
            <option value="low">Baja</option>
            <option value="medium">Media</option>
            <option value="high">Alta</option>
            <option value="urgent">Urgente</option>
          </select>
        </label>

        <label>
          Fecha límite
          <input
            type="date"
            value={form.dueDate ?? ""}
            onChange={(e) => setField("dueDate", e.target.value)}
          />
        </label>

        <fieldset className="labels-picker">
          <legend>Etiquetas</legend>
          {ALL_LABELS.map((label) => (
            <label key={label.id} className="label-option">
              <input
                type="checkbox"
                checked={form.labelIds.includes(label.id)}
                onChange={() => toggleLabel(label.id)}
              />
              <span className="label-chip" style={{ background: label.color }}>
                {label.name}
              </span>
            </label>
          ))}
        </fieldset>

        <footer className="panel__actions">
          <button type="button" onClick={onClose} disabled={saving}>Cancelar</button>
          <button type="submit" disabled={saving}>
            {saving ? "Guardando…" : "Guardar"}
          </button>
        </footer>
      </form>
    </aside>
  );
}

Decisiones del ejemplo: (1) las columnas se derivan de tasks con filter, nunca se almacenan; (2) el drag & drop usa la API nativa del navegador—cero dependencias—; (3) moveTask es optimista con rollback; (4) la prioridad se resuelve con un mapa de objeto (PRIORITY[task.priority]) en lugar de una cadena de if; (5) en el formulario guardamos labelIds (solo strings) y traducimos a objetos completos al enviar, para que el estado sea ligero.

5 · Buenas prácticas

HazEvitaPor qué
Un único array tasks y columnas derivadas Tres arrays (todo, inProgress, done) Evitas duplicar la verdad y las tareas «en dos sitios a la vez».
PATCH para cambios parciales (estado) PUT enviando la tarea completa solo para mover Menos datos, menos riesgo de sobrescribir campos con valores viejos.
Optimista con rollback para mover Esperar la respuesta para pintar el movimiento El tablero se siente instantáneo; si falla, la UI no miente.
preventDefault() en onDragOver Olvidarlo y que el drop no funcione «sin motivo» Sin llamarlo, el navegador cancela el evento de soltar.
Etiquetas como datos ({ id, name, color }) Clases CSS hardcodeadas por etiqueta El usuario podrá crear etiquetas nuevas sin tocar el código.
Guardar labelIds en el formulario Guardar objetos enteros en el estado local Estado ligero y comparaciones triviales (includes).

6 · Errores habituales

Error 1: duplicar el estado en tres arrays de columna

✘ Incorrecto 
const [todo, setTodo] = useState([]);
const [inProgress, setInProgress] = useState([]);
const [done, setDone] = useState([]);
// Mover una tarea obliga a quitarla de un array y añadirla a otro:
// tres estados que pueden desincronizarse entre sí.
✔ Correcto 
const [tasks, setTasks] = useState([]);
// La columna es un VALOR DERIVADO del campo "status":
const todo = tasks.filter((t) => t.status === "todo");

Error 2: mutar la tarea al moverla

✘ Incorrecto 
const task = tasks.find((t) => t.id === id);
task.status = "done";         // muta el objeto dentro del estado
setTasks(tasks);              // misma referencia de array → no re-render
✔ Correcto 
setTasks((current) =>
  current.map((t) => (t.id === id ? { ...t, status: "done" } : t))
);

Error 3: usar el índice de la columna como estado

✘ Incorrecto 
// La columna depende de la POSICIÓN, no del dato real.
{tasks.map((task, index) => (
  <TaskColumn title={["Todo", "Doing", "Done"][index]} task={task} />
))}
✔ Correcto 
// La columna la determina el dato task.status (una única verdad).
tasksOf("todo").map((task) => <TaskCard key={task.id} task={task} />)

8 · Reto

🎯 Reordenar dentro de la columna (frac index)

Hoy se puede mover una tarea entre columnas, pero no reordenarla dentro de una misma columna. Impleméntalo con el campo position:

  1. Permite soltar una tarjeta entre otras dos. Detecta la posición de inserción comparando la posición vertical del puntero con el punto medio de cada tarjeta.
  2. Al soltar, calcula la nueva position como el punto medio entre las posiciones de la tarjeta anterior y la siguiente (frac index). Si va al principio o al final, suma/resta un delta.
  3. Persiste con PATCH /api/tasks/{id}/position enviando solo { position } (optimista con rollback).
  4. Muestra un placeholder (una línea o hueco) en la posición donde caerá la tarjeta mientras arrastras.

Pista: el frac index evita renumerar toda la lista en cada movimiento: solo cambias una tarea. Cuida la precisión: con muchos movimientos los float pueden acercarse; una buena API «renormaliza» la columna cada cierto número de reordenamientos.

No lo resuelvas todavía. Reordenar con frac index es el patrón que usan Trello, Notion y Linear; dominarlo es un salto de nivel.

9 · Resumen

  • Una tarea tiene identidad, pertenencia, contenido, estado, prioridad, etiquetas y posición. Definir el modelo bien ahorra problemas.
  • En un Kanban, las columnas son valores derivados de status: nunca arrays separados.
  • PATCH para cambios parciales (mover estado), evita sobrescribir campos con datos viejos.
  • Optimista + rollback: el tablero se siente instantáneo y nunca miente.
  • Drag & drop nativo con draggable, onDragStart, onDragOver + preventDefault y onDrop.
  • Etiquetas como datos ({ id, name, color }) y prioridad como enum con mapa de presentación.

10 · Preguntas frecuentes

¿Por qué no uso una librería de drag & drop como dnd-kit?

Para columnas simples, la API nativa del navegador es suficiente y no añade dependencias. dnd-kit o react-beautiful-dnd brillan cuando necesitas reordenar dentro de listas largas, accesibilidad completa por teclado y animaciones complejas. Como reto, implementamos el reordenamiento a mano; en un producto real, valorar una librería es perfectamente sensato.

¿Cómo hago accesible el tablero por teclado?

El arrastre nativo no es accesible. Añade alternativas: que la tarjeta sea enfocable (tabIndex={0}) y que, desde el panel de detalle, se pueda cambiar el status con un <select>. Así, quien no puede arrastrar, puede mover igualmente.

¿La position la genera el cliente o el servidor?

La calcula el cliente (punto medio entre vecinas) porque él conoce la posición visual donde soltó el usuario. El servidor solo la persiste. Si dos usuarios mueven a la vez (tiempo real, lección 9), el servidor puede renormalizar la columna para evitar colisiones.

¿Por qué las etiquetas no son solo un array de strings?

Porque necesitan color y, en un producto real, un id estable para renombrarlas o reutilizarlas. Un array de objetos { id, name, color } permite todo eso y se serializa sin problema a JSON.

¿Qué pasa si el servidor devuelve la tarea con un status distinto al que envié?

Por eso reconciliamos con la respuesta del servidor en moveTask: si el backend aplicó una regla (p. ej. «una tarea done se archiva»), la UI refleja su verdad, no la nuestra. El servidor siempre tiene la última palabra.
