React vs Vanilla, Angular, Vue y Solid

Módulo 0 · Preparación ⏱ 30 minutos

1 · Introducción

«¿Por qué React y no Vue? ¿Y ese Solid del que hablan? ¿No es mejor hacerlo con JavaScript puro?» Son las preguntas correctas, y un profesional debe saber responderlas con argumentos, no con fe.

En esta lección comparamos React con sus alternativas reales del mercado. El objetivo NO es coronar un ganador: es que entiendas qué decisiones de diseño toma cada herramienta y cuándo cada una es la elección acertada. Comprender las alternativas, además, es la mejor forma de entender el propio React: cada comparación ilumina una decisión que React tomó y por qué.

2 · Teoría

React vs JavaScript Vanilla

Ya lo hemos intuido en las lecciones anteriores, pero fijémoslo. JavaScript vanilla es imperativo y manual: tú buscas elementos, tú los modificas, tú recuerdas qué depende de qué. React es declarativo y automático: describes la UI como función del estado y React sincroniza el DOM.

Vanilla JSReact
EstiloImperativo (cómo)Declarativo (qué)
Sincronización datos↔UIManual (tu responsabilidad)Automática (reconciliación)
ReutilizaciónCopiar/pegar o funciones ad hocComponentes (sistema formal)
Escala bien a…Widgets puntuales, páginas simplesApps grandes con mucho estado
Coste de entradaCero (es el navegador)Tooling (Vite, npm, build)
Velocidad máxima teóricaMayor (cero intermediarios)Muy buena (VDOM + batching)

Regla profesional: ¿un acordeón en una landing? Vanilla (o ni eso: HTML <details>). ¿Una aplicación con decenas de pantallas y estado compartido? React. La complejidad de React se amortiza con el tamaño del proyecto.

React vs Angular

Angular (Google, 2016; el sucesor completo de AngularJS) es la respuesta opuesta en filosofía: un framework completo y opinado. Trae de fábrica router, cliente HTTP, formularios, inyección de dependencias y TypeScript obligatorio.

ReactAngular
TipoBiblioteca de UIFramework completo
LenguajeJavaScript (TS opcional)TypeScript obligatorio
PlantillasJSX (HTML dentro de JS)HTML + directivas (*ngIf, *ngFor)
ReactividadRe-render + diffing de VDOMSignals (actualización granular) + Zone.js histórico
ArquitecturaLa decides túImpuesta (módulos, servicios, DI)
CurvaConceptos pocos, libertad altaMuchos conceptos (RxJS, DI…), todo guiado
Típico en…Startups, producto, todo tipo de empresasGrandes corporaciones y sector público

Si vienes de .NET, Angular te resultará familiar por su parecido con ASP.NET: inyección de dependencias, decoradores (parecidos a los atributos de C#), TypeScript con clases… React es más libre y más «JavaScript puro»: menos estructura impuesta, más decisiones tuyas. Ninguna es superior en abstracto: Angular brilla con equipos enormes que necesitan uniformidad; React brilla con equipos que quieren flexibilidad y velocidad de producto.

React vs Vue

Vue (Evan You, 2014, ex-Google) es el competidor más parecido en espíritu: biblioteca centrada en la vista, progresiva y con gran comunidad. Las diferencias están en el cómo:

ReactVue
PlantillasJSX: «todo es JavaScript»Templates HTML con directivas (v-if, v-for) o JSX opcional; SFC (Single File Components: template+script+style en un archivo)
ReactividadRe-ejecutar el componente y comparar VDOMSistema de proxies: sabe QUÉ dato cambió y actualiza solo eso
Estado en componenteuseState devuelve [valor, setter]ref()/reactive() con mutación directa (count.value++)
MutabilidadEstado INMUTABLE (creas nuevos objetos)Mutas directamente, Vue lo detecta
EcosistemaEl mayor del mercadoGrande, más cohesionado (router y store oficiales)

La diferencia profunda es filosófica: React re-renderiza e inmutabilidad; Vue rastrea y muta. Cuando en el Módulo 4 sufras creando copias de objetos ({ ...task, done: true }), recuerda que es una decisión de diseño deliberada: la inmutabilidad hace los cambios detectables por comparación y el tiempo depurable.

React vs Solid

Solid (Ryan Carniato, 2021) es el «y si React no tuviera Virtual DOM». Copia el modelo de JSX y componentes de React, pero con reactividad granular por signals:

  • En React, cambiar un estado re-ejecuta todo el componente y el VDOM decide qué cambió.
  • En Solid, el componente se ejecuta una sola vez; cada dato (signal) está conectado directamente a los puntos exactos del DOM que lo usan, y los actualiza sin volver a ejecutar nada.
CAMBIO DE UN DATO… ────────────────── REACT: setState → re-ejecutar componente → nuevo VDOM → diffing → tocar DOM donde difiera SOLID: setSignal → los nodos suscritos a ese signal se actualizan directamente. Sin re-ejecutar nada.

Resultado: Solid es de lo más rápido que existe en benchmarks. ¿Y por qué el mundo sigue con React? Porque el rendimiento de React es suficiente para el 99 % de las apps reales, y su ecosistema (librerías, empleo, documentación, IA que lo conoce bien) es inalcanzable hoy por hoy. Solid es excelente para aprender qué hay «después» del VDOM.

¿Y Blazor? (la mirada .NET)

Si vienes del mundo Microsoft: Blazor es la apuesta de .NET para escribir SPAs en C# con WebAssembly (o vía servidor con SignalR). Su modelo de componentes (Razor) es sorprendentemente parecido al de React: parámetros = props, renderizado declarativo, árbol de componentes. Si aprendes React en profundidad, Blazor te resultará trivial, y viceversa. React gana en madurez del ecosistema de UI y mercado; Blazor en no salir de C#.

3 · Ejemplo mínimo

El mismo contador en los cuatro mundos. No necesitas entenderlo todo aún: aprecia las diferencias de estilo.

Vanilla JavaScript:

counter.js
let count = 0;
const span = document.querySelector("#count");
document.querySelector("#btn").addEventListener("click", () => {
  count++;
  span.textContent = count; // sincronización manual
});

React:

Counter.jsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

Vue (SFC):

Counter.vue
<script setup>
import { ref } from "vue";
const count = ref(0);
</script>

<template>
  <button @click="count++">{{ count }}</button>
</template>

Solid:

Counter.jsx
function Counter() {
  const [count, setCount] = createSignal(0); // signal, no estado de re-render
  return <button onClick={() => setCount(count() + 1)}>{count()}</button>;
}

Fíjate: React y Solid parecen gemelos (JSX), pero count() en Solid es una función que lee el signal y suscribe ese punto del DOM; en React count es un valor congelado de ese render. Vue y Angular separan template y lógica; React los funde en JavaScript. Cuatro respuestas legítimas a la misma pregunta.

4 · Ejemplo real

Caso práctico: tu empresa va a construir tres productos y tú debes recomendar tecnología.

  1. Un panel de administración interno (50 pantallas, formularios complejos, 6 desarrolladores .NET que apenas saben frontend).

    Análisis: sin SEO que perder y con equipo .NET, dos candidatos serios: Blazor (no salen de C#) o React (mayor ecosistema de componentes de tablas/formularios y más perfiles disponibles para contratar después). Angular también encajaría por su parecido con .NET. Recomendación razonada: React si piensan contratar frontend a futuro; Blazor si el equipo será siempre .NET puro.

  2. La web pública de marketing (landing, blog, SEO crítico).

    Análisis: aquí una SPA pura (cualquiera) es mala idea por SEO y tiempo de primera carga. Toca generador estático/SSR: Astro (con islas React si hace falta) o Next.js. Nota cómo «React» sigue presente, pero renderizado en servidor.

  3. Un visualizador de datos en tiempo real (miles de puntos actualizándose 60 veces por segundo).

    Análisis: caso límite de rendimiento. Candidatos: Solid (granular, sin re-renders) o React con técnicas del Módulo 11 + canvas/WebGL para la parte caliente. Decisión: si el equipo es pequeño y el rendimiento es EL requisito, Solid; si forma parte de un producto mayor ya en React, React bien optimizado es suficiente.

La lección: no existe «la mejor herramienta», existe el mejor análisis. Y para analizar hay que conocer las alternativas.

6 · Errores habituales

Error 1: «React es el más rápido»

Por qué está mal: en benchmarks finos, Solid, Svelte o incluso vanilla superan a React. La velocidad de React es «suficiente y predecible», no «máxima».

Versión correcta: React se elige por ecosistema, modelo mental consolidado y mercado, no por ganar benchmarks.

Error 2: «Vue/Angular son peores» (tribalismo)

Por qué está mal: los tres son herramientas maduras usadas por empresas gigantes (Vue: Alibaba, GitLab; Angular: Google, Santander). Despreciar una tecnología sin conocerla es una señal de junior.

Versión correcta: «para ESTE equipo, ESTOS requisitos y ESTE plazo, React encaja mejor porque…».

Error 3: mezclar conceptos entre frameworks

Por qué está mal: preguntar «¿cómo hago two-way binding en React?» o «¿dónde está el v-if?» revela traer los vicios de otro framework. React tiene SUS respuestas (estado + onChange, &&/ternario), y forzar las de otros genera código antinatural.

Versión correcta: aprender «the React way»: este curso traduce cada concepto a su equivalente idiomático en React.

7 · Ejercicio guiado

Vamos a construir una tabla de equivalencias conceptuales (tu futura «chuleta mental»):

  1. Estado local: React useState ↔ Vue ref() ↔ Angular signal() ↔ Solid createSignal().

  2. Renderizar una lista: React {items.map(i => <li>…)} ↔ Vue v-for ↔ Angular *ngFor ↔ Solid <For>.

  3. Condicional: React {ok && <p>…} ↔ Vue v-if ↔ Angular *ngIf.

  4. Efecto colateral: React useEffect ↔ Vue watchEffect ↔ Angular effect().

  5. Conclusión que debes anotar: los conceptos (estado, listas, condicionales, efectos) existen en TODOS. Quien entiende los conceptos en React, aprende cualquier otro framework en semanas.

9 · Resumen

  • Vanilla: control total, sincronización manual. Perfecto para cosas pequeñas; inviable para apps grandes.
  • Angular: framework completo, TS obligatorio, opinionado. Brilla en grandes corporaciones.
  • Vue: templates o JSX, reactividad por proxies y mutación. Cohesivo y amable.
  • Solid: JSX como React pero sin VDOM (signals). El más rápido; ecosistema pequeño.
  • React: biblioteca de UI, JSX, inmutabilidad, re-render + diffing. El mayor ecosistema y mercado.
  • La elección profesional se hace con requisitos (SEO, equipo, escala), nunca con tribalismo.
  • Los conceptos (estado, listas, condicionales, efectos) son universales: dominar React te da todos los demás casi gratis.

10 · Preguntas frecuentes

¿React está «muerto» o «pasado de moda»?

Llevan anunciándolo desde 2015. Mientras tanto: es el framework más usado del mundo (State of JS, Stack Overflow Survey), Meta, Microsoft, Netflix y Shopify lo mantienen, y React 19 (2024) demuestra desarrollo activísimo. Aprender React es una de las inversiones más seguras del sector.

¿Debería aprender Vue «por si acaso»?

No de forma preventiva. Domina React primero (incluidos sus conceptos profundos); si un trabajo pide Vue, lo aprenderás en 2-3 semanas gracias a la tabla de equivalencias. Dos frameworks a medias valen menos que uno en profundidad.

¿Qué pasa con los micro-frontends?

Arquitectura donde distintos equipos despliegan partes independientes de la UI (pueden ser hasta de frameworks distintos). Es una solución organizativa para empresas enormes, no algo que necesites al empezar. Con React bien estructurado llegas muy lejos antes de necesitarla.

Vengo de Angular, ¿qué me costará más de React?

Dos cosas: (1) la libertad —en Angular el framework decide; en React decides tú (router, estructura de carpetas, estado global)— y (2) la inmutabilidad del estado: en Angular mutas propiedades; en React SIEMPRE creas objetos nuevos. El Módulo 4 te curará la segunda.

¿Y los signals que Angular y Vue ahora copian? ¿React se queda atrás?

React respondió con el React Compiler (2024/25): un compilador que optimiza los re-renders automáticamente, acercándose a la eficiencia granular sin cambiar el modelo mental. Lo veremos en el Módulo 11. El VDOM + compilador es la apuesta de React frente a los signals.
