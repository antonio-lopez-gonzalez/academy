El modelo mental de componentes

Módulo 0 · Preparación ⏱ 25 minutos

1 · Introducción

Todo lo que existe en React es un componente. Botones, tarjetas, formularios, páginas enteras: componentes. Entender profundamente qué es un componente —no solo «una pieza reutilizable de UI», que es la definición de manual— es lo que separa a quien escribe React de quien piensa en React.

Qué aprenderás en esta lección:

  • Qué es un componente de verdad (una función pura de props y estado).
  • Cómo las aplicaciones se organizan en árboles de componentes.
  • El flujo de datos en un solo sentido (one-way data flow).
  • Cómo descomponer una interfaz real en componentes (la habilidad nº 1 del desarrollador React).
  • Convenciones profesionales de nombres y archivos.

Error típico que evitaremos: creer que un componente es «un trozo de HTML copiable». Esa idea lleva a componentes gigantes e imposibles de mantener.

2 · Teoría

Un componente es una función (literalmente)

En React moderno, un componente es una función de JavaScript que recibe datos de entrada (las props) y devuelve una descripción de la interfaz (JSX):

props (datos de entrada) │ ▼ ┌─────────────────┐ │ COMPONENTE │ = una función de JavaScript │ function(props)│ └─────────────────┘ │ ▼ descripción de la UI (JSX → Virtual DOM)

Si recuerdas la fórmula de la lección 1 (UI = f(estado)), aquí está su materialización: el componente ES esa función. Mismos datos de entrada → misma descripción de salida. Como las funciones matemáticas.

La pureza: la regla de oro del modelo mental

React asume que tus componentes son funciones puras durante el renderizado:

  • Misma entrada → misma salida: con las mismas props, el componente describe la misma UI.
  • Sin efectos colaterales al renderizar: renderizar no puede cambiar variables externas, hacer peticiones HTTP ni modificar el DOM. Esas cosas existen, pero viven en su sitio (eventos y useEffect), no durante el render.
💡 ¿Por qué React exige pureza?

Porque React necesita poder ejecutar tus componentes cuando quiera y las veces que quiera: varias veces en desarrollo (StrictMode), pausar a medias (renderizado concurrente), reintentar… Si renderizar tuviera efectos colaterales, cada una de esas ejecuciones provocaría caos (peticiones duplicadas, contadores corruptos). La pureza es lo que hace el renderizado predecible y reintentable. Cuando en el Módulo 6 aprendas useEffect, esta regla cobrará todo su sentido.

La aplicación es un ÁRBOL de componentes

Los componentes se anidan unos dentro otros formando un árbol, como las muñecas rusas o las piezas de LEGO: piezas pequeñas que se combinan para construir piezas mayores, hasta formar la aplicación completa.

App ├── Header │ ├── Logo │ ├── SearchBar │ └── UserMenu │ ├── Avatar │ └── Dropdown ├── MainContent │ ├── Sidebar │ │ └── NavItem × 6 │ └── Feed │ └── PostCard × N │ ├── PostHeader │ ├── PostBody │ └── PostActions (Like, Comment, Share) └── Footer

Fíjate en dos cosas: (1) la raíz es App, un componente como cualquier otro; (2) los elementos del DOM (<button>, <img>…) son las hojas del árbol: componentes «primitivos» que ya trae el navegador.

El flujo de datos: un solo sentido, siempre hacia abajo

Los datos entran en un componente a través de las props, que le entrega su padre. Y solo su padre. Un componente no puede recibir datos de su abuelo directamente, ni de un hermano, ni (¡jamás!) modificar las props que recibe.

FLUJO DE DATOS UNIDIRECCIONAL ───────────────────────────── App (dueña del estado) │ props ↓ ┌─────┴─────┐ ▼ ▼ Sidebar Feed │ props ↓ ▼ PostCard ← solo RECIBE datos; │ nunca modifica sus props ▼ button (DOM) Para que algo «suba», el padre pasa una FUNCIÓN (callback) como prop, y el hijo la llama: PostCard ──onLike()──► Feed ──setState()──► nuevo render

Esta regla —los datos bajan, los eventos suben— es la que mantiene las aplicaciones grandes comprensibles: siempre puedes responder «¿de dónde viene este dato?» mirando hacia arriba en el árbol. Los frameworks antiguos con binding bidireccional (AngularJS) permitían que cualquier cosa cambiara cualquier cosa: depurar era una pesadilla. React eligió la disciplina del único sentido.

Composición: la única «herencia» de React

En programación orientada a objetos (vienes de .NET o Java) la reutilización se logra con herencia: class AdminUser : User. React prohíbe mentalmente ese camino: los componentes no heredan, se componen. Un AdminPanel no «extiende» un Panel: contiene un Panel configurado con props. Es el principio «composición sobre herencia» llevado a la UI, y le dedicaremos una lección entera en el Módulo 1.

3 · Ejemplo mínimo

El componente más pequeño del mundo:

Greeting.jsx
// Un componente = una función que devuelve una descripción de UI
function Greeting() {
  return <h1>Hola, mundo</h1>;
}

export default Greeting;

Línea por línea:

  1. function Greeting() — una función normal de JavaScript. Su nombre empieza en mayúscula: así React sabe que es un componente y no una etiqueta HTML.
  2. return <h1>…</h1>; — devuelve la descripción de lo que debe verse (JSX, Módulo 1). No devuelve un nodo del DOM: devuelve un elemento virtual.
  3. export default — lo hace disponible para que otros archivos lo usen con import Greeting from "./Greeting.jsx".

Y usarlo es como inventar tu propia etiqueta HTML:

App.jsx
import Greeting from "./Greeting.jsx";

function App() {
  return (
    <div>
      <Greeting />   <!-- como si "Greeting" fuera una etiqueta HTML nueva -->
      <Greeting />   <!-- reutilizable: dos instancias independientes -->
    </div>
  );
}

4 · Ejemplo real

La habilidad más valorada en un desarrollador React es mirar una interfaz y ver el árbol de componentes. Practiquemos con la tarjeta de una red social:

LO QUE VES (una tarjeta de post) LO QUE UN REACT DEV VE (árbol) ──────────────────────────────── ────────────────────────────── ┌───────────────────────────┐ PostCard │ @ana_dev · hace 2 h │ ├── PostHeader │ Aprendiendo React 19 🚀 │ │ ├── Avatar │ ❤ 24 💬 8 ↗ Compartir │ │ ├── AuthorName └───────────────────────────┘ │ └── Timestamp ├── PostBody (el texto) └── PostActions ├── LikeButton (❤ 24) ├── CommentButton (💬 8) └── ShareButton

Decisiones de diseño, explicadas:

  • PostCard recibe un solo objeto post como prop y reparte los trozos hacia abajo (post.author al header, post.likes a las acciones). Es la composición en acción.
  • LikeButton es componente propio porque tiene comportamiento (marcar like, animar el corazón). La regla práctica: si tiene su propio estado o lógica, merece ser componente.
  • Avatar se extrae porque se reutiliza en comentarios, cabecera, mensajes… La regla práctica: si se repite con distintos datos, merece ser componente.

¿Cuándo parar de dividir? Cuando dividir ya no aporta ni reutilización, ni claridad, ni estado propio. Un <span> con estilo no necesita ser componente.

6 · Errores habituales

Error 1: nombrar componentes en minúscula

✘ Incorrecto 
function userCard() {          // minúscula inicial
  return <article>…</article>;
}

// Al usarlo:
<userCard />   // React lo trata como una ETIQUETA HTML desconocida
                // y pinta… nada. Sin error visible. El peor tipo de bug.
✔ Correcto 
function UserCard() {          // PascalCase
  return <article>…</article>;
}

<UserCard />   // React lo reconoce como componente y lo ejecuta

Por qué: en JSX, la mayúscula inicial es la señal que distingue «componente mío» de «etiqueta del navegador». No es estética: es cómo funciona el compilador.

Error 2: un componente que devuelve «varias cosas sueltas»

✘ Incorrecto 
function Header() {
  return (
    <Logo />
    <Nav />      // ✘ dos elementos sueltos: una función solo puede
  );             //   devolver UN valor
}
✔ Correcto 
function Header() {
  return (
    <>           <!-- Fragment: un único envoltorio invisible -->
      <Logo />
      <Nav />
    </>
  );
}

Por qué: un componente es una función y las funciones devuelven un valor. El Fragment (lección dedicada en el Módulo 1) agrupa sin añadir nodos extra al DOM.

Error 3: definir un componente DENTRO de otro

✘ Incorrecto 
function Profile() {
  // ✘ Definir Avatar aquí dentro parece cómodo…
  function Avatar() {
    return <img src="ana.png" alt="Ana" />;
  }
  return <Avatar />;   // …pero en CADA render de Profile, Avatar
}                       //   es una función NUEVA → React lo destruye
                        //   y lo recrea (pierde estado y foco)
✔ Correcto 
function Avatar() {           // definido FUERA, a nivel de módulo
  return <img src="ana.png" alt="Ana" />;
}

function Profile() {
  return <Avatar />;         // misma identidad en todos los renders
}

7 · Ejercicio guiado

Vamos a descomponer en árbol la pantalla de un reproductor de música (tipo Spotify). Sigue los pasos:

  1. Identifica las zonas grandes: barra lateral (playlists), lista de canciones central, barra de reproducción inferior.

    App ├── Sidebar ├── SongList └── PlayerBar

  2. Divide cada zona por responsabilidad:

    App ├── Sidebar │ └── PlaylistItem × N ├── SongList │ ├── SearchInput │ └── SongRow × N └── PlayerBar ├── SongInfo (portada + título) ├── PlaybackControls (⏮ ▶ ⏭) └── ProgressBar

  3. Aplica las reglas prácticas: SongRow se repite → componente. PlaybackControls tiene estado (play/pausa) → componente. ProgressBar tiene estado y lógica de tiempo → componente.

  4. Decide el flujo de datos: ¿quién es dueño de «canción actual sonando»? El componente App (porque la necesitan tanto SongList —para marcarla— como PlayerBar —para tocarla—). El estado vive en el ancestro común más cercano: se llama lifting state up y la practicaremos en el Módulo 4.

9 · Resumen

  • Un componente es una función: props entran, descripción de UI sale. Es la materialización de UI = f(estado).
  • Los componentes deben ser puros durante el render: misma entrada → misma salida, sin efectos colaterales. Así React puede ejecutarlos cuando quiera.
  • La aplicación es un árbol: componentes dentro de componentes; las hojas son elementos del DOM.
  • Los datos fluyen en un solo sentido (padre → hijo vía props); los eventos suben mediante callbacks.
  • Reutilización por composición, nunca por herencia.
  • Convenciones: PascalCase, un componente por archivo, identificadores en inglés.
  • Diseña el árbol en papel antes de escribir código: es la práctica senior por excelencia.

10 · Preguntas frecuentes

¿Qué tamaño debe tener un componente?

No hay número mágico de líneas. Pregunta mejor: ¿tiene una única responsabilidad explicable en una frase? ¿se repite en otra pantalla? ¿tiene estado propio? Si respondes sí a alguna, la división está justificada. Como guía práctica: cuando un componente supera las ~150-200 líneas, suele estar haciendo demasiado.

¿Y los componentes de clase (class Component)?

Son la forma antigua (pre-2019, antes de los hooks). Todo el código nuevo se escribe con funciones; las clases solo las verás en código legado o en documentación vieja. Este curso usa exclusivamente componentes de función, el estándar actual.

¿Un componente puede devolver null?

Sí, y es muy útil: return null significa «no renderices nada» (pero el componente sigue existiendo en el árbol). Es la base del renderizado condicional que veremos en el Módulo 2.

¿Por qué no puedo modificar las props dentro del componente?

Porque las props pertenecen al padre: son su forma de configurarte. Si el hijo las cambiara, dos componentes que reciben la misma prop podrían ver valores distintos y la trazabilidad («¿de dónde viene este dato?») se rompería. Si necesitas cambiar un dato, necesitas estado (Módulo 4) o pedirle al padre que lo cambie (callback).

¿Qué diferencia hay entre componente e «instancia» de componente?

El componente es la función (la definición, como una clase en OOP). Cada vez que aparece <UserCard /> en la UI hay una instancia: con sus propias props y su propio estado. <UserCard /> tres veces = tres instancias independientes de la misma función.
