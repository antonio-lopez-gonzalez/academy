🛠 Proyecto: lista de tareas

Proyecto del Módulo 4 ⏱ 60 minutos

1 · Introducción

Cuarto proyecto del curso: una lista de tareas completa con añadir, marcar como completada, borrar, filtrar (todas/pendientes/completadas), estadísticas derivadas y botón «Limpiar completadas». Es el proyecto perfecto para este módulo porque TODO es estado: un array de objetos que cambia con el tiempo, operaciones inmutables, valores derivados y formularios controlados.

Además, es la base de TaskFlow, la app tipo Trello que construiremos en el Módulo 13. Aquí aprendes los fundamentos; allí añadiremos backend, autenticación, WebSockets y despliegue. Pero el corazón —estado inmutable, componentes modulares, flujo unidireccional— es exactamente el mismo.

📌 Qué vas a practicar
  • useState con arrays de objetos (lección 1 y 3).
  • Operaciones inmutables: spread, filter, map (lección 3 y 4).
  • Estado derivado: contadores y filtros calculados en el render (lección 1).
  • Formularios controlados: input con value + onChange (adelanto del Módulo 5).
  • Eventos con parámetros: callbacks que avisan al padre con el id (Módulo 3).
  • Renderizado condicional: lista vacía, botón que aparece/desaparece (Módulo 2).

2 · Diseño

LA APP ÁRBOL DE COMPONENTES ──────── ────────────────────── ┌─────────────────────────┐ App (estado + lógica) │ Lista de tareas │ ├── TaskForm (input controlado) │ │ ├── TaskStats (derivados + filtros) │ [input] [Añadir] │ └── TaskList (lista "tonta") │ │ └── TaskItem × N (toggle, delete) │ 2 pendientes · 1/3 │ │ [Todas] [Pend] [Comp] │ Lógica: funciones puras en App │ [Limpiar completadas] │ (addTask, toggleTask, deleteTask, clearCompleted) │ │ │ ✔ Repasar useState 🗑 │ Estado: │ ○ Terminar M4 🗑 │ tasks: [{ id, text, done }] │ ○ Leer inmutabilidad🗑 │ filter: "all" | "pending" | "done" └─────────────────────────┘

Decisiones de arquitectura:

  • El estado vive en App (el ancestro común): tasks y filter. Los hijos reciben datos por props y avisan con callbacks. Flujo unidireccional del Módulo 0, aplicado.
  • Componentes «tontos» abajo: TaskList y TaskItem no tienen estado propio; solo pintan y avisan. Son reutilizables y fáciles de testear.
  • Componentes con estado local donde tiene sentido: TaskForm tiene su propio text (el input que escribes), pero la tarea añadida vive en el padre. Separación de responsabilidades.
  • Valores derivados, no estado: visibleTasks, doneCount, pendingCount se calculan en cada render. Crear useState para ellos sería duplicar verdad y arriesgar desincronización.
  • Ids con crypto.randomUUID(): único, estable, nativo en navegadores modernos. Alternativas: contador global (nextId++), Date.now() (menos robusto si añades dos tareas en el mismo milisegundo).

3 · El código clave

src/App.jsx — el cerebro (estado + lógica)
import { useState } from "react";
import TaskForm from "./components/TaskForm.jsx";
import TaskList from "./components/TaskList.jsx";
import TaskStats from "./components/TaskStats.jsx";

export default function App() {
  // Estado principal: array de objetos { id, text, done }
  const [tasks, setTasks] = useState([
    { id: 1, text: "Repasar useState", done: true },
    { id: 2, text: "Terminar el proyecto del Módulo 4", done: false },
    { id: 3, text: "Leer sobre inmutabilidad", done: false },
  ]);

  // Estado de filtro: "all" | "pending" | "done"
  const [filter, setFilter] = useState("all");

  // ---- ACCIONES (todas INMUTABLES) ----

  function addTask(text) {
    const newTask = { id: crypto.randomUUID(), text, done: false };
    setTasks((current) => [...current, newTask]);
  }

  function toggleTask(id) {
    setTasks((current) =>
      current.map((task) =>
        task.id === id ? { ...task, done: !task.done } : task
      )
    );
  }

  function deleteTask(id) {
    setTasks((current) => current.filter((task) => task.id !== id));
  }

  function clearCompleted() {
    setTasks((current) => current.filter((task) => !task.done));
  }

  // ---- VALORES DERIVADOS ----

  const visibleTasks = tasks.filter((task) => {
    if (filter === "pending") return !task.done;
    if (filter === "done") return task.done;
    return true;
  });

  const doneCount = tasks.filter((t) => t.done).length;
  const pendingCount = tasks.length - doneCount;

  return (
    <main className="app">
      <header className="app-header">
        <h1>Lista de tareas</h1>
        <p className="app-subtitle">Proyecto del Módulo 4</p>
      </header>

      <TaskForm onAdd={addTask} />

      <TaskStats
        total={tasks.length}
        done={doneCount}
        pending={pendingCount}
        filter={filter}
        onFilterChange={setFilter}
        onClearCompleted={clearCompleted}
      />

      <TaskList tasks={visibleTasks} onToggle={toggleTask} onDelete={deleteTask} />
    </main>
  );
}
src/components/TaskForm.jsx — formulario controlado
import { useState } from "react";

export default function TaskForm({ onAdd }) {
  const [text, setText] = useState("");

  function handleSubmit(e) {
    e.preventDefault();
    const trimmed = text.trim();
    if (trimmed === "") return;
    onAdd(trimmed);
    setText("");
  }

  return (
    <form className="task-form" onSubmit={handleSubmit}>
      <input
        type="text"
        value={text}
        onChange={(e) => setText(e.target.value)}
        placeholder="¿Qué hay que hacer?"
        aria-label="Nueva tarea"
        autoFocus
      />
      <button type="submit" disabled={text.trim() === ""}>
        Añadir
      </button>
    </form>
  );
}
src/components/TaskItem.jsx — una tarea (toggle + delete)
export default function TaskItem({ task, onToggle, onDelete }) {
  return (
    <li className={task.done ? "task task--done" : "task"}>
      <label className="task__label">
        <input
          type="checkbox"
          checked={task.done}
          onChange={() => onToggle(task.id)}
          aria-label={`Marcar "${task.text}" como ${task.done ? "pendiente" : "completada"}`}
        />
        <span className="task__text">{task.text}</span>
      </label>
      <button
        className="task__delete"
        onClick={() => onDelete(task.id)}
        aria-label={`Borrar "${task.text}"`}
      >
        🗑
      </button>
    </li>
  );
}

4 · Decisiones profesionales aplicadas

  • Los manejadores viven en App: el estado está ahí, así que la lógica que lo modifica también. Los hijos solo avisan (onToggle(id), onDelete(id)). Flujo unidireccional del Módulo 0, aplicado.
  • Forma funcional setTasks(current => ...): aunque en este caso no es estrictamente necesaria (no encadenamos setters), es buena práctica cuando el nuevo valor depende del anterior. La usamos consistentemente para reforzar el hábito.
  • crypto.randomUUID() para ids: nativo en navegadores modernos, genera ids únicos y estables. Alternativa didáctica: let nextId = 4 fuera del componente (como en los ejemplos).
  • Filtros como estado, no como lógica hardcoded: filter es un string ("all", "pending", "done") que controla qué tareas se muestran. Si mañana añadimos «Prioritarias», solo añadimos un valor más al filtro y la lógica en visibleTasks.
  • Renderizado condicional en TaskList: si no hay tareas (tras filtrar), muestra un mensaje vacío. Es el patrón del Módulo 2: if (tasks.length === 0) return <EmptyState />.
  • Clases condicionales en TaskItem: task--done se añade si task.done es true. El CSS se encarga del estilo (tachado, opacidad). Separación de concerns: la lógica decide la clase, el CSS decide el estilo.
  • Accesibilidad: aria-label en checkboxes y botones, role="group" en los filtros. La app es navegable con teclado y compatible con lectores de pantalla.

5 · Buenas prácticas demostradas

  • Estado mínimo: solo tasks y filter. Todo lo demás (contadores, tareas visibles) se deriva en el render.
  • Inmutabilidad consistente: todas las operaciones usan spread, filter o map. Ninguna muta el array del estado.
  • Keys estables por id: key={task.id} en TaskList. Si reordenáramos las tareas, React mantendría la pista de cada una.
  • Guard clauses: if (trimmed === "") return en TaskForm. Las reglas de negocio (no añadir vacías) van en los manejadores, no en la UI.
  • Componentes pequeños y enfocados: cada componente hace UNA cosa. TaskItem pinta una tarea; TaskStats muestra estadísticas. Son fáciles de entender, testear y reutilizar.
  • Props con nombres claros: onAdd, onToggle, onDelete para callbacks; tasks, filter para datos. La convención on* para eventos viene del Módulo 3.
  • Responsive: el CSS usa flexbox y media queries para adaptarse a móviles. No es un curso de CSS, pero la app se ve bien en cualquier pantalla.

6 · Errores que este proyecto evita

  • Mutar el array con push: tasks.push(newTask); setTasks(tasks) no funciona (misma referencia). Usamos setTasks([...tasks, newTask]).
  • Mutar objetos con task.done = !task.done: el objeto es el mismo, React no detecta el cambio. Usamos map + spread: task.id === id ? { ...task, done: !task.done } : task.
  • Estado duplicado para contadores: const [doneCount, setDoneCount] = useState(0) se desincronizaría con tasks. Lo derivamos: tasks.filter(t => t.done).length.
  • Índice como key: key={index} rompería la reconciliación si reordenáramos. Usamos key={task.id}.
  • Leer el DOM con querySelector: el input vive en el estado (text), no en el DOM. Nunca hacemos document.querySelector("input").value.
  • Lógica de negocio en la UI: la validación «no añadir vacías» va en handleSubmit, no en un if dentro del JSX.

7 · Ejercicio guiado

  1. Arranca el proyecto: cd proyectos/m04-lista-tareas && pnpm dev. Añade 3 tareas, marca una como completada, filtra por «Pendientes», bórrala. Observa cómo los contadores se actualizan solos (son derivados).
  2. Añade un campo de prioridad: cada tarea tendrá priority: "low" | "medium" | "high". Modifica TaskForm para incluir un <select> y App para guardarla. Pista: el estado del formulario ahora es un objeto {'[{ text, priority }]'}.
  3. Ordena por prioridad: añade un botón «Ordenar por prioridad» que use toSorted (o [...tasks].sort) con un comparador que ponga high primero. Recuerda: inmutable.
  4. Edita en línea: doble-click en el texto de una tarea lo convierte en un input editable. Al pulsar Enter o perder el foco, guarda el cambio. Pista: necesitas un estado editingId en App y renderizado condicional en TaskItem.
  5. Persiste en localStorage: usa useEffect (adelanto del Módulo 6) para guardar tasks en localStorage cada vez que cambie, y cargarlas al iniciar. Pista: const [tasks, setTasks] = useState(() => JSON.parse(localStorage.getItem("tasks")) || []).

8 · Reto

🎯 Subtareas (estado anidado)

Cada tarea puede tener subtareas: un array de objetos {'[{ id, text, done }]'} anidado dentro de la tarea. Añade:

  1. Un botón «+ Subtarea» en cada TaskItem que abra un input inline.
  2. Renderiza las subtareas debajo del texto de la tarea (indentadas).
  3. Checkbox para marcar subtareas como completadas (inmutable: map en el array de tareas, map en el array de subtareas, spread en cada nivel).
  4. Borrar subtareas.
  5. Estadísticas derivadas: «2 de 5 subtareas completadas» en cada tarea.

Este es el primer paso hacia TaskFlow (Módulo 13), donde las tareas tendrán comentarios, etiquetas y más. La inmutabilidad anidada es la clave.

9 · Resumen

  • La lista de tareas es el «Hello World» de las apps reales: estado, eventos, formularios, renderizado condicional.
  • Arquitectura: estado en el ancestro común (App), componentes «tontos» abajo, flujo unidireccional.
  • Inmutabilidad consistente: spread, filter, map. Nunca push, sort directo o task.done = true.
  • Valores derivados: contadores y filtros se calculan en el render, no son estado.
  • Formularios controlados: el input es un espejo del estado local.
  • Este proyecto es la base de TaskFlow (Módulo 13): aquí aprendes los fundamentos; allí añadimos backend, auth, WebSockets.

10 · Preguntas frecuentes

¿Por qué el estado vive en App y no en TaskList?

Porque TaskStats también necesita acceder a las tareas (para los contadores). Si el estado viviera en TaskList, tendríamos que «elevarlo» (lifting state up) al ancestro común. Es más simple ponerlo ahí desde el principio.

¿Por qué TaskForm tiene su propio estado local?

Porque el texto que escribes en el input es temporal: solo importa cuando pulsas «Añadir». No tiene sentido que viva en App (que se re-renderizaría en cada tecla). Separación de responsabilidades: el formulario gestiona su input; App gestiona las tareas.

¿Por qué usar crypto.randomUUID() y no Date.now()?

Date.now() devuelve milisegundos desde 1970. Si añades dos tareas en el mismo milisegundo (poco probable pero posible), tendrían el mismo id. crypto.randomUUID() genera un UUID v4: prácticamente imposible de colisionar. Es nativo en navegadores modernos.

¿Y si quiero persistir las tareas (que no se pierdan al recargar)?

Usa localStorage con useEffect (Módulo 6). Guarda el array serializado (JSON.stringify(tasks)) cada vez que cambie, y cárgalo al iniciar con useState(() => JSON.parse(...)). El ejercicio guiado (paso 5) lo hace.

¿Por qué no usar useReducer en vez de useState?

useReducer (Módulo 10) es mejor cuando la lógica de actualización es compleja (muchas acciones, estado anidado). Aquí tenemos 4 acciones simples (añadir, toggle, borrar, limpiar); useState es suficiente. Si añadiéramos subtareas, etiquetas, prioridades… entonces useReducer sería más claro.
