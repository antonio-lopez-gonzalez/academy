useState: la memoria del componente

Módulo 4 · Estado ⏱ 40 minutos

1 · Introducción

Llegamos a LA lección más importante del curso. Todo lo anterior —JSX, componentes, props, eventos— eran los músculos y los sentidos de React. El estado es su memoria: lo que permite que una interfaz cambie con el tiempo recordando cosas (el texto que escribes, el contador, si el menú está abierto…).

Y aquí está el dato clave que ya sospechas desde el Módulo 3: una variable normal no sirve como memoria, porque cuando cambia, React no se entera y no repinta. El hook useState resuelve exactamente eso: te da un valor que persiste entre renders y cuya actualización dispara un nuevo render.

2 · Teoría

Por qué una variable normal NO sirve

function Counter() {
  let count = 0;                  // ✘ variable normal

  function handleClick() {
    count++;                      // la variable SÍ cambia…
    console.log(count);           // …en consola se ve: 1, 2, 3…
  }

  return <button onClick={handleClick}>{count}</button>;
  // …pero la pantalla SIEMPRE muestra 0 😶
}

Dos razones profundas:

  1. React no se entera del cambio: nadie le avisa de que debe re-renderizar. Cambiar una variable no dispara nada.
  2. Aunque re-renderizara, la variable se reinicia: let count = 0 vive DENTRO de la función; cada render la crearía de nuevo en 0. Las variables locales no sobreviven al render.

El estado necesita, pues, dos superpoderes: persistir entre renders y avisar a React al cambiar. Eso es exactamente lo que useState proporciona.

Anatomía de useState

import { useState } from "react";

const [count, setCount] = useState(0);
//      │        │               │
//      │        │               └─ valor INICIAL (solo se usa en el 1er render)
//      │        └─ la FUNCIÓN para cambiarlo (el "setter")
//      └─ el VALOR actual en este render
  • useState(0) crea una «celda de memoria» gestionada por React y la inicializa a 0 (solo la primera vez).
  • Devuelve un array de dos posiciones que desestructuramos: el valor actual y su setter. Los nombres son libres, pero la convención es sagrada: [algo, setAlgo].
  • setCount(5) hace DOS cosas: actualiza el valor Y programa un re-render del componente. En el siguiente render, count valdrá 5.
  • Entre renders, React «guarda» el valor por ti: la función componente se vuelve a ejecutar, pero el estado sobrevive.

¿Qué es un hook, exactamente?

Un hook (gancho) es una función especial de React que «engancha» tu componente a las capacidades internas de React (memoria, efectos, referencias…). useState es el primero; en el Módulo 6 verás useEffect, useRef, useMemo… Todos empiezan por use y todos obedecen las Reglas de los Hooks:

⚠ Las dos Reglas de los Hooks (inquebrantables)
  1. Solo en el nivel superior del componente: nunca dentro de ifs, bucles, returns tempranos ni funciones anidadas. ¿Por qué? React identifica cada hook por su orden de llamada (el 1er useState es la celda 1, el 2º la celda 2…). Un if saltaría ese orden y descuadraría todas las celdas.
  2. Solo dentro de componentes de React (o custom hooks): no en funciones normales, clases, o callbacks sueltos.
CÓMO REACT IDENTIFICA CADA useState: POR ORDEN DE LLAMADA ────────────────────────────────────────────────────────── Render 1: Render 2 (mismo orden): useState("Ana") → celda 1 useState("Ana") → celda 1 ✔ useState(0) → celda 2 useState(0) → celda 2 ✔ useState(false) → celda 3 useState(false) → celda 3 ✔ Si pones uno en un if que a veces no se ejecuta, la celda 2 sería a veces "0" y a veces "false": caos.

Múltiples estados y tipos de estado

const [name, setName] = useState("");        // string
const [age, setAge] = useState(0);            // número
const [isOpen, setIsOpen] = useState(false);  // booleano
const [items, setItems] = useState([]);       // array (lección 3)
const [user, setUser] = useState(null);       // objeto o null (lección 3)

Puedes tener tantos useState como necesites. ¿Uno por dato o un objeto grande? Regla práctica: un estado por dato independiente; agrupa solo lo que cambia junto (un formulario complejo, por ejemplo). Lo desarrollamos en la lección 3.

Estado = instantánea del render (el concepto que más cuesta)

Presta mucha atención a este experimento mental:

function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);   // pedimos count + 1
    console.log(count);    // ¿qué imprime? → 0 (¡no 1!)
  }
  …
}

¿Por qué imprime 0? Porque count es una constante de ESTE render: una fotografía del estado en el momento en que se ejecutó la función. setCount no modifica esa foto: programa un nuevo render con el valor nuevo. En el render actual, count seguirá siendo 0 hasta el final de la función. El estado en React no es una variable que mutas: es una serie de instantáneas inmutables, una por render. La próxima lección entera es sobre esto (batching incluido).

3 · Ejemplo mínimo

src/components/Counter.jsx
import { useState } from "react";   // 1. importamos el hook

export default function Counter() {
  const [count, setCount] = useState(0);   // 2. creamos el estado (valor inicial 0)

  function handleIncrement() {
    setCount(count + 1);   // 3. el setter cambia el valor Y repinta
  }

  // 4. el JSX LEE el estado: cada render muestra el valor actual
  return <button onClick={handleIncrement}>Contador: {count}</button>;
}

Línea por línea:

  1. import { useState } from "react" — el hook vive en el paquete react (no en react-dom).
  2. const [count, setCount] = useState(0) — crea la memoria: valor actual + setter. El 0 solo vale en el primer render.
  3. setCount(count + 1) — calcula el nuevo valor a partir del actual y lo establece. React re-renderiza.
  4. {count} — el JSX es una función del estado: en cada render, el botón muestra el valor nuevo. Ese es el ciclo entero de React funcionando.

4 · Ejemplo real

Un interruptor de tema claro/oscuro para una tarjeta (booleano) + un campo de nombre con eco en vivo (string) — los dos usos más comunes de useState:

src/components/ProfileWidget.jsx
import { useState } from "react";

export default function ProfileWidget() {
  // Estado 1: booleano para el tema
  const [isDark, setIsDark] = useState(true);
  // Estado 2: string para el nombre (input controlado)
  const [name, setName] = useState("");

  return (
    <div className={isDark ? "widget widget--dark" : "widget widget--light"}>
      {/* Toggle: invertimos el booleano actual */}
      <button onClick={() => setIsDark(!isDark)}>
        Cambiar a tema {isDark ? "claro ☀️" : "oscuro 🌙"}
      </button>

      {/* Input controlado: el valor ES el estado, y el estado se
          actualiza en cada tecla. Círculo perfecto. (Módulo 5 a fondo) */}
      <input
        value={name}
        onChange={(e) => setName(e.target.value)}
        placeholder="Tu nombre…"
      />

      {/* La UI siempre refleja el estado: sin sincronización manual */}
      {name && <p>Hola, {name} 👋</p>}
    </div>
  );
}

Decisiones explicadas:

  • Dos estados independientes = dos useState: el tema y el nombre no tienen relación; cada uno tiene su celda.
  • setIsDark(!isDark): el toggle clásico: leer el actual e invertirlo. (En la próxima lección veremos la forma aún más robusta: setIsDark(d => !d).)
  • Input controlado: value={name} + onChange que actualiza. El estado es la única fuente de verdad del input: lo que escribes viaja al estado y el estado repinta el input. Es el patrón de formularios del Módulo 5.
  • El saludo aparece/desaparece solo gracias al cortocircuito del Módulo 2: la UI es una proyección del estado, sin código de sincronización.

5 · Buenas prácticas

HazEvitaPor qué
Nombres [algo, setAlgo] [algo, cambiarAlgo], [data, setData] genérico La convención hace el código reconocible al instante; data no dice nada.
Estado mínimo necesario Guardar en estado lo que se puede CALCULAR (derivados) Estado duplicado = estados que se desincronizan. Si puedes calcularlo en el render, no es estado.
Estado lo más abajo posible en el árbol (cerca de quien lo usa) Todo el estado en App «por si acaso» Menos re-renders, componentes más independientes y reutilizables.
Pensar «qué eventos cambian este estado» al definirlo Crear estados «por si los necesito luego» El estado sin eventos que lo modifiquen es ruido (o debería ser una constante).
useState siempre en el nivel superior useState dentro de ifs, loops o returns tempranos Rompe el orden de los hooks: estados corruptos y bugs rarísimos.

6 · Errores habituales

Error 1: mutar el estado directamente

✘ Incorrecto 
count = count + 1;      // 💥 "count" es una CONSTANTE (error)
// o peor, con variables:
let [count] = useState(0);
count++;                // cambia el valor pero React NO se entera:
                        // no hay re-render. La pantalla no cambia.
✔ Correcto 
setCount(count + 1);    // el setter es la ÚNICA vía de cambio

Error 2: esperar que el estado cambie «en el acto»

✘ Incorrecto 
function handleClick() {
  setCount(count + 1);
  console.log(count);   // imprime el valor VIEJO: el estado de este
}                       // render es una foto fija hasta que termina
✔ Correcto 
function handleClick() {
  const next = count + 1;   // calcula el nuevo valor en una variable tuya
  setCount(next);
  console.log(next);        // si lo necesitas ya, usa tu variable
}

Error 3: useState dentro de un if

✘ Incorrecto 
function Profile({ isVip }) {
  if (isVip) {
    const [points, setPoints] = useState(0);  // 💥 orden de hooks roto
  }
  const [name, setName] = useState("");
}
✔ Correcto 
function Profile({ isVip }) {
  const [points, setPoints] = useState(0);   // siempre, nivel superior
  const [name, setName] = useState("");
  // …y la condición, en el JSX o en la lógica, nunca en los hooks
}

Error 4: estado para un valor derivado

✘ Incorrecto 
const [price, setPrice] = useState(100);
const [priceWithTax, setPriceWithTax] = useState(121);  // ✘ duplicado:
// si price cambia, ¿quién actualiza priceWithTax? Se desincronizan.
✔ Correcto 
const [price, setPrice] = useState(100);
const priceWithTax = price * 1.21;   // ✔ DERIVADO: se calcula en el render
// price cambia → re-render → priceWithTax se recalcula solo. Siempre sincronizado.

7 · Ejercicio guiado

Contador con botones de +1, −1 y reset:

  1. Crea el estado const [count, setCount] = useState(0); y muéstralo en un <h2>.

  2. Botón «+1»: onClick={() => setCount(count + 1)}. Comprueba que funciona.

  3. Botón «−1» con una regla: no puede bajar de 0 (usa Math.max(0, count - 1)).

  4. Botón «Reset»: setCount(0).

  5. Reto extra: muestra «Número par» / «Número impar» junto al contador — sin crear otro estado (derivado con ternario: count % 2 === 0).

  6. Abre React DevTools → Components → selecciona tu componente: verás la sección «hooks» con el valor del estado EN VIVO. Edítalo ahí y mira cómo la UI responde. Esa es tu nueva forma de depurar.

9 · Resumen

  • El estado es la memoria del componente: persiste entre renders y al cambiar dispara un re-render.
  • const [valor, setValor] = useState(inicial) — el valor inicial solo se usa en el primer render.
  • Una variable normal no sirve: no persiste y React no se entera de sus cambios.
  • El estado se cambia SOLO con el setter; es una instantánea inmutable por render (no cambia «en el acto»).
  • Reglas de los hooks: nivel superior, solo en componentes. React los identifica por ORDEN de llamada.
  • Estado mínimo: lo que se puede derivar, se deriva en el render.
  • El ciclo: estado → UI → evento → setter → re-render. Es TODA React.

10 · Preguntas frecuentes

¿El estado se pierde al re-renderizar?

No: React lo conserva mientras el componente siga montado en el mismo sitio del árbol. Se pierde al desmontar (salir de la página, ocultarlo con un condicional) o al cambiar su key.

¿Cada instancia del componente tiene su propio estado?

Sí: <Counter /> tres veces = tres contadores independientes. El estado es de la instancia (su posición en el árbol), no de la función.

¿Puedo llamar setCount durante el render?

No directamente en el cuerpo del componente: provocaría un render tras render infinito (React lo detecta y lanza error). Los setters se llaman en eventos, efectos o callbacks — nunca «en frío» durante el render (con una excepción avanzada: el patrón «derive state during render», que no necesitas ahora).

¿Cuántos useState son «demasiados»?

No hay límite técnico. Si superas ~6-7, probablemente el componente hace demasiado (divídelo) o los datos están relacionados (agrúpalos en un objeto o pasa a useReducer, Módulo 10).

¿useState es lento?

No: es la operación más optimizada de React. Los re-renders que provoca son baratos (recuerda: render ≠ repintar). El rendimiento solo se optimiza cuando hay un problema medido (Módulo 11).
