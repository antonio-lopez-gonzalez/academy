Inputs controlados

Módulo 5 · Formularios ⏱ 35 minutos

1 · Introducción

Hasta ahora hemos visto cómo React renderiza datos y responde a eventos. Pero cuando el usuario escribe en un input, ocurre algo especial: el DOM tiene su propio estado interno (el texto que ves en pantalla) y React tiene el suyo (el estado del componente). ¿Quién manda? ¿De dónde sacamos el valor cuando el usuario pulsa "Enviar"?

React resuelve esto con el patrón de componentes controlados: el estado de React es la única fuente de verdad del input. El input lee su valor del estado y, cuando el usuario escribe, un handler actualiza el estado. Es un círculo perfecto: estado → input → evento → estado → re-render → input…

Este patrón es la base de todos los formularios en React. Dominarlo ahora te ahorrará horas de confusión más adelante.

2 · Teoría

El problema: dos fuentes de verdad

En HTML puro, un <input> mantiene su propio estado interno. Cuando escribes "Ana", el DOM sabe que el valor es "Ana". Si quieres leerlo, usas document.querySelector('input').value.

Pero en React, queremos que el estado del componente sea la fuente de verdad. Si tienes const [name, setName] = useState(""), quieres que name refleje siempre lo que el usuario escribe. El problema: el input tiene su propio estado interno y React tiene el suyo. ¿Cuál es el verdadero?

La solución: el componente controlado

React impone su autoridad: el input no tiene estado propio. Su valor viene SIEMPRE del estado de React. Cuando el usuario escribe, el evento onChange dispara un handler que actualiza el estado. React re-renderiza y el input muestra el nuevo valor.

EL CÍRCULO DEL INPUT CONTROLADO ──────────────────────────────── ┌──────────────────────────────┐ │ ESTADO (name = "Ana") │ └──────────────┬───────────────┘ │ value={name} ▼ ┌──────────────────────────────┐ │ <input value="Ana" /> │ ← el input NO tiene estado propio └──────────────┬───────────────┘ │ el usuario escribe "Anabel" ▼ ┌──────────────────────────────┐ │ onChange(e) │ │ setName(e.target.value) │ ← "Anabel" └──────────────┬───────────────┘ │ setter → re-render ▼ ┌──────────────────────────────┐ │ ESTADO (name = "Anabel") │ ← vuelta arriba └──────────────────────────────┘

Anatomía de un input controlado

const [name, setName] = useState("");

<input
  value={name}                          // 1. el valor VIENE del estado
  onChange={(e) => setName(e.target.value)}  // 2. el evento ACTUALIZA el estado
  placeholder="Tu nombre…"
/>
  • value={name}: el input muestra SIEMPRE lo que dice el estado. No importa qué escriba el usuario: si el estado no cambia, el input no cambia.
  • onChange: se dispara en cada tecla. e.target.value es el nuevo valor que el usuario acaba de escribir.
  • setName(e.target.value): actualiza el estado. React re-renderiza y el input muestra el nuevo valor.

¿Por qué no "uncontrolled" (lo veremos al final)?

Existe otra forma: dejar que el input mantenga su propio estado y leerlo con useRef cuando necesites el valor (patrón "no controlado"). Es válido en casos simples, pero pierdes las ventajas del control total: validación en tiempo real, formateo automático, deshabilitar botones según el valor, resetear el formulario con un botón… Por eso el patrón controlado es el estándar profesional.

El estado es la única fuente de verdad

Este principio (Single Source of Truth) es sagrado en React. Si el valor de un input está en el estado, el input NO puede tener su propio estado interno. Por eso value={name} es obligatorio: sin él, el input tendría su propio estado y React perdería el control.

3 · Ejemplo mínimo

src/components/NameInput.jsx
import { useState } from "react";

export default function NameInput() {
  const [name, setName] = useState("");   // estado inicial: string vacío

  return (
    <div>
      <input
        value={name}                          // el valor VIENE del estado
        onChange={(e) => setName(e.target.value)}  // cada tecla actualiza el estado
        placeholder="Escribe tu nombre…"
      />
      {name && <p>Hola, {name} 👋</p>}      // saludo condicional (Módulo 2)
    </div>
  );
}

Línea por línea:

  1. useState("") — creamos el estado con un string vacío. Podría ser cualquier valor inicial.
  2. value={name} — el input muestra SIEMPRE lo que dice name. Sin esto, el input tendría su propio estado interno.
  3. onChange={(e) => setName(e.target.value)} — en cada tecla, actualizamos el estado con el nuevo valor del input.
  4. {name && <p>...</p>} — cortocircuito del Módulo 2: si name no está vacío, muestra el saludo.

4 · Ejemplo real

Un buscador en vivo: el usuario escribe y los resultados se filtran al instante. Es el patrón de input controlado aplicado a un caso real (el proyecto del Módulo 6 será un buscador de películas).

src/components/LiveSearch.jsx
import { useState } from "react";

const FRUITS = ["manzana", "plátano", "naranja", "fresa", "kiwi", "mango", "uva"];

export default function LiveSearch() {
  const [query, setQuery] = useState("");   // el texto del input

  // Filtramos en cada render: la lista es una FUNCIÓN del estado
  const filtered = FRUITS.filter((fruit) =>
    fruit.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <div>
      <input
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Busca una fruta…"
      />
      <ul>
        {filtered.length > 0 ? (
          filtered.map((fruit) => <li key={fruit}>{fruit}</li>)
        ) : (
          <li>No se encontraron resultados</li>
        )}
      </ul>
    </div>
  );
}

Decisiones explicadas:

  • El filtrado ocurre en el render: no es estado, es un valor derivado. Cada vez que query cambia, React re-renderiza y filtered se recalcula. Sin efectos, sin sincronización manual.
  • toLowerCase() en ambos: hace la búsqueda case-insensitive. El usuario puede escribir "MANZANA" o "manzana" y encontrará la fruta.
  • Renderizado condicional: si no hay resultados, mostramos un mensaje. Es el patrón del Módulo 2 aplicado a un caso real.
  • El input es controlado: podríamos resetear el buscador con setQuery("") en un botón, y el input se limpiaría al instante. Eso es el poder del control total.

5 · Buenas prácticas

HazEvitaPor qué
Siempre value + onChange juntos value sin onChange (input de solo lectura) Sin onChange, el usuario no puede escribir. Si quieres solo lectura, usa readOnly explícito.
Estado inicial coherente con el tipo de input useState(null) para un input de texto null en value se comporta como "no controlado". Usa "" para strings.
Un estado por campo independiente Un objeto gigante con todos los campos Más fácil de entender y actualizar. (Veremos excepciones en validaciones.)
Nombres descriptivos: email, password input1, field, data El código se lee solo. email dice qué es; data no dice nada.
Derivar valores en el render (búsquedas, cálculos) Guardar en estado lo que se puede calcular Estado duplicado = desincronización. Si puedes calcularlo, no es estado.

6 · Errores habituales

Error 1: olvidar el onChange

✘ Incorrecto 
<input value={name} />   // input de solo lectura: el usuario NO puede escribir
// React muestra una warning en consola: "You provided a `value` prop but no `onChange`"
✔ Correcto 
<input value={name} onChange={(e) => setName(e.target.value)} />

Error 2: usar null como valor inicial

✘ Incorrecto 
const [name, setName] = useState(null);
<input value={name} onChange={…} />
// React trata null como "no controlado": el input tiene su propio estado interno
// y value={null} se ignora. Comportamiento impredecible.
✔ Correcto 
const [name, setName] = useState("");   // string vacío = controlado desde el inicio

Error 3: no usar e.target.value

✘ Incorrecto 
<input value={name} onChange={() => setName("algo")} />
// siempre que escribas, el valor será "algo". No lees lo que el usuario escribe.
✔ Correcto 
<input value={name} onChange={(e) => setName(e.target.value)} />
// lees el valor ACTUAL del input (lo que el usuario acaba de escribir)

Error 4: guardar en estado lo que se puede derivar

✘ Incorrecto 
const [query, setQuery] = useState("");
const [filtered, setFiltered] = useState(FRUITS);   // ✘ estado duplicado

<input value={query} onChange={(e) => {
  setQuery(e.target.value);
  setFiltered(FRUITS.filter(f => f.includes(e.target.value)));  // desincronización
}} />
✔ Correcto 
const [query, setQuery] = useState("");
const filtered = FRUITS.filter(f => f.includes(query));   // derivado en el render

<input value={query} onChange={(e) => setQuery(e.target.value)} />
// query cambia → re-render → filtered se recalcula. Siempre sincronizado.

7 · Ejercicio guiado

Input controlado con contador de caracteres:

  1. Crea el estado const [text, setText] = useState("");

  2. Añade un <textarea> controlado: value={text} y onChange={(e) => setText(e.target.value)}.

  3. Muestra el número de caracteres: <p>{text.length} caracteres</p>. Actualízate en cada tecla.

  4. Añade un límite de 100 caracteres: si text.length >= 100, deshabilita el textarea (disabled) o muestra un mensaje de error.

  5. Añade un botón "Limpiar" que haga setText(""). Comprueba que el textarea se vacía al instante (el poder del control total).

  6. Abre React DevTools → Components → selecciona tu componente. Verás el estado text en vivo. Edítalo ahí y mira cómo el textarea responde.

9 · Resumen

  • Un input controlado es aquel cuyo valor viene SIEMPRE del estado de React.
  • Patrón: value={estado} + onChange={(e) => setEstado(e.target.value)}.
  • El estado es la única fuente de verdad: el input no tiene estado propio.
  • Ventajas: validación en tiempo real, resetear con un botón, deshabilitar según el valor, formateo automático.
  • Errores típicos: olvidar onChange, usar null como valor inicial, no leer e.target.value.
  • Lo que se puede derivar (búsquedas, cálculos), se deriva en el render: no es estado.

10 · Preguntas frecuentes

¿Qué pasa si pongo value sin onChange?

El input se vuelve de solo lectura: el usuario no puede escribir. React muestra una warning en consola. Si quieres solo lectura intencionadamente, usa readOnly en lugar de value sin onChange.

¿Puedo usar defaultValue en lugar de value?

Sí, pero entonces el input es "no controlado": tiene su propio estado interno y solo usa defaultValue en el primer render. Pierdes el control total (no puedes resetearlo con un botón, no puedes validarlo en tiempo real…). Solo útil en formularios muy simples.

¿Por qué no usar useRef para leer el valor?

Puedes, pero entonces el input es "no controlado". useRef te da acceso al DOM, pero React no se entera de los cambios hasta que tú leas el ref. Pierdes la reactividad: no puedes filtrar en tiempo real, no puedes deshabilitar botones según el valor… El patrón controlado es más reactivo y más "React".

¿El onChange se dispara en cada tecla o al perder el foco?

En cada tecla (o cada cambio, en el caso de checkboxes). Es diferente del evento nativo change de HTML, que en algunos inputs se dispara al perder el foco. React normaliza esto con Synthetic Events (Módulo 3).

¿Puedo formatear el valor mientras el usuario escribe?

Sí: en el onChange, transforma el valor antes de guardarlo en el estado. Por ejemplo, para convertir a mayúsculas: onChange={(e) => setName(e.target.value.toUpperCase())}. El input mostrará el valor formateado en el siguiente render.
