React Testing Library

Módulo 12 · Testing

Introducción

React Testing Library (RTL) es una librería para testear componentes React enfocándose en el comportamiento del usuario, no en los detalles de implementación.

Filosofía principal:

"Cuanto más se parezcan tus tests a cómo se usa tu software, más confianza te darán"

¿Qué significa esto?

  • Testea lo que el usuario ve y hace, no el estado interno
  • Usa queries similares a como un usuario buscaría elementos
  • Evita testear detalles de implementación (estado, métodos, etc.)
  • Tests más robustos: no se rompen con refactorizaciones

Instalación

pnpm add -D @testing-library/react @testing-library/jest-dom @testing-library/user-event

Configuración en src/test/setup.js:

import '@testing-library/jest-dom'

Tu primer test de componente

// src/components/Button.jsx
export default function Button({ children, onClick }) {
  return <button onClick={onClick}>{children}</button>
}

// src/components/__tests__/Button.test.jsx
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import Button from '../Button'

describe('Button', () => {
  it('should render with text', () => {
    render(<Button>Click me</Button>)
    
    // Busca el botón por su texto
    const button = screen.getByText('Click me')
    expect(button).toBeInTheDocument()
  })

  it('should call onClick when clicked', async () => {
    const handleClick = vi.fn()
    const user = userEvent.setup()
    
    render(<Button onClick={handleClick}>Click me</Button>)
    
    const button = screen.getByText('Click me')
    await user.click(button)
    
    expect(handleClick).toHaveBeenCalledOnce()
  })
})

Queries: cómo buscar elementos

RTL proporciona queries ordenadas por prioridad:

1. Queries por accesibilidad (preferidas)

// Por rol ARIA
screen.getByRole('button', { name: /submit/i })
screen.getByRole('heading', { name: /welcome/i })
screen.getByRole('textbox', { name: /email/i })

// Por label
screen.getByLabelText(/email/i)

// Por placeholder
screen.getByPlaceholderText(/enter your email/i)

// Por texto alt
screen.getByAltText(/profile picture/i)

// Por título
screen.getByTitle(/close modal/i)

2. Queries por texto

// Por texto visible
screen.getByText(/welcome/i)

// Por display value (inputs)
screen.getByDisplayValue(/john/i)

3. Queries por test id (último recurso)

// Componente
<div data-testid="custom-element">...</div>

// Test
screen.getByTestId('custom-element')

Variantes: getBy, queryBy, findBy

// getBy: espera que exista, throw si no
screen.getByText('Hello')

// queryBy: devuelve null si no existe (útil para testear ausencia)
expect(screen.queryByText('Error')).not.toBeInTheDocument()

// findBy: espera asíncronamente (para elementos que aparecen después)
const message = await screen.findByText('Success')

Simular interacciones con userEvent

import userEvent from '@testing-library/user-event'

describe('User interactions', () => {
  it('should handle user events', async () => {
    const user = userEvent.setup()
    
    render(<LoginForm />)
    
    // Escribir en inputs
    const emailInput = screen.getByLabelText(/email/i)
    await user.type(emailInput, 'test@example.com')
    
    // Click
    const submitButton = screen.getByRole('button', { name: /submit/i })
    await user.click(submitButton)
    
    // Keyboard
    await user.keyboard('{Enter}')
    
    // Clear input
    await user.clear(emailInput)
    
    // Hover
    await user.hover(screen.getByText('Hover me'))
    
    // Select option
    await user.selectOptions(
      screen.getByRole('combobox'),
      'option-value'
    )
  })
})

Testear formularios

// src/components/LoginForm.jsx
export default function LoginForm({ onSubmit }) {
  const [email, setEmail] = useState('')
  const [password, setPassword] = useState('')

  function handleSubmit(e) {
    e.preventDefault()
    onSubmit({ email, password })
  }

  return (
    <form onSubmit={handleSubmit}>
      <label>
        Email
        <input
          type="email"
          value={email}
          onChange={(e) => setEmail(e.target.value)}
          required
        />
      </label>
      <label>
        Password
        <input
          type="password"
          value={password}
          onChange={(e) => setPassword(e.target.value)}
          required
        />
      </label>
      <button type="submit">Login</button>
    </form>
  )
}

// Test
describe('LoginForm', () => {
  it('should submit form with email and password', async () => {
    const user = userEvent.setup()
    const handleSubmit = vi.fn()
    
    render(<LoginForm onSubmit={handleSubmit} />)
    
    await user.type(screen.getByLabelText(/email/i), 'test@example.com')
    await user.type(screen.getByLabelText(/password/i), 'password123')
    await user.click(screen.getByRole('button', { name: /login/i }))
    
    expect(handleSubmit).toHaveBeenCalledWith({
      email: 'test@example.com',
      password: 'password123'
    })
  })

  it('should show validation errors', async () => {
    const user = userEvent.setup()
    
    render(<LoginForm onSubmit={vi.fn()} />)
    
    await user.click(screen.getByRole('button', { name: /login/i }))
    
    // Los inputs required muestran validación nativa del navegador
    const emailInput = screen.getByLabelText(/email/i)
    expect(emailInput).toBeInvalid()
  })
})

Testear asíncrono

// src/components/UserProfile.jsx
export default function UserProfile({ userId }) {
  const [user, setUser] = useState(null)
  const [loading, setLoading] = useState(true)

  useEffect(() => {
    fetchUser(userId).then(data => {
      setUser(data)
      setLoading(false)
    })
  }, [userId])

  if (loading) return <div>Loading...</div>
  
  return <div>{user.name}</div>
}

// Test
describe('UserProfile', () => {
  it('should load and display user', async () => {
    // Mock de fetchUser
    vi.mock('../api', () => ({
      fetchUser: vi.fn().mockResolvedValue({ name: 'John Doe' })
    }))
    
    render(<UserProfile userId={1} />)
    
    // Espera a que aparezca el nombre
    const userName = await screen.findByText('John Doe')
    expect(userName).toBeInTheDocument()
  })

  it('should show loading state', () => {
    vi.mock('../api', () => ({
      fetchUser: vi.fn().mockImplementation(() => new Promise(() => {}))
    }))
    
    render(<UserProfile userId={1} />)
    
    expect(screen.getByText('Loading...')).toBeInTheDocument()
  })
})

Custom render

// src/test/test-utils.jsx
import { render } from '@testing-library/react'
import { ThemeProvider } from '../contexts/ThemeContext'
import { AuthProvider } from '../contexts/AuthContext'

function AllProviders({ children }) {
  return (
    <AuthProvider>
      <ThemeProvider>
        {children}
      </ThemeProvider>
    </AuthProvider>
  )
}

function customRender(ui, options) {
  return render(ui, { wrapper: AllProviders, ...options })
}

// Re-exportar todo
export * from '@testing-library/react'
export { customRender as render }

// Uso en tests
import { render, screen } from '../test/test-utils'

it('should use theme context', () => {
  render(<ThemedButton />)
  // ...
})

Mejores prácticas

  • Testea comportamiento, no implementación: qué hace el componente, no cómo lo hace
  • Usa queries accesibles: getByRole, getByLabelText antes que getByTestId
  • Evita selectores CSS: son frágiles y dependen de la implementación
  • No testees estados internos: testea lo que el usuario ve
  • Usa userEvent: simula interacciones reales del usuario
  • Tests independientes: cada test debe ser autónomo
  • Nombres descriptivos: describe qué hace el test, no cómo

Resumen

  • React Testing Library testea comportamiento, no implementación
  • Queries por accesibilidad: getByRole, getByLabelText
  • userEvent para simular interacciones reales
  • findBy para elementos asíncronos
  • Custom render para providers globales
  • Tests robustos que no se rompen con refactorizaciones
