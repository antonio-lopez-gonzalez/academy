React Testing Library

Módulo 12 · Testing 🕐 40 minutos

1 · Introducción

React Testing Library (RTL) es la librería oficial recomendada para probar componentes React. Su objetivo no es comprobar cómo está hecho un componente, sino qué hace desde el punto de vista de la persona que lo usa.

¿Por qué existe? Las primeras librerías de testing para React exponían los detalles internos: accedías al estado del componente, a sus props o a sus métodos para comprobar cosas. Eso hacía que cualquier refactor rompiera cientos de tests sin que el comportamiento de la app hubiera cambiado. RTL nació como reacción a ese problema.

¿Qué problema resuelve? Tests frágiles acoplados a la implementación. RTL te obliga a interactuar como lo haría un usuario: buscar elementos por su rol o su texto, escribir, hacer clic, esperar a que aparezca algo en pantalla.

¿Cuándo se usa? Siempre que pruebes un componente o un hook de React. Combinada con Vitest (el runner) y con userEvent (las interacciones), es el estándar de la industria.

Errores típicos: llenar el código de data-testid, usar selectores CSS de implementación, llamar a fireEvent en lugar de userEvent, u olvidar el await en las interacciones asíncronas.

2 · Teoría

La filosofía de RTL

Analogía: la prueba de usabilidad

Imagina que contratas a una persona para probar tu app. No le explicas cómo está programada; le dices "regístrate" y observas qué hace. Si necesita saber los nombres de tus variables internas para usarla, algo va mal. RTL te obliga a escribir tests como esa persona: texto visible, roles, etiquetas.

La regla de oro, citada en la propia documentación, es: "cuanto más se parezcan tus tests a cómo se usa tu software, más confianza te darán".

render, screen y el DOM

RTL funciona sobre jsdom, una implementación del DOM en JavaScript que ejecuta el navegador dentro de Node. Vitest arranca jsdom gracias a environment: "jsdom". Los tres conceptos básicos son:

  • render(ui) — monta el componente en un contenedor y devuelve utilidades de consulta.
  • screen — acceso global al DOM renderizado. Es la forma preferida de buscar elementos.
  • Cleanup automático — RTL desmonta el componente después de cada test, así no se filtran nodos entre pruebas.

Prioridad de las queries

No todas las formas de buscar un elemento son igual de buenas. RTL propone este orden, de más accesible a menos:

PrioridadQuerySirve para
1getByRoleBotones, enlaces, headings, inputs: la forma más parecida a como ve un usuario (y un lector de pantalla) la UI.
2getByLabelTextCampos de formulario asociados a un <label>.
3getByPlaceholderTextInputs sin label (peor, pero aceptable).
4getByTextTexto visible: párrafos, spans, botones simples.
5getByDisplayValueValor actual de un input o select.
6getByTestIdÚltimo recurso, cuando nada de lo anterior encaja.
Por qué importa la accesibilidad

Si tu componente se puede probar con getByRole, estás demostrando que es accesible: tiene roles y nombres correctos. Escribir buenos tests con RTL mejora la accesibilidad de la app casi sin esfuerzo extra.

getBy, queryBy y findBy

VarianteComportamientoCuándo usarla
getBy…Lanza error si no encuentra el elemento.Cuando el elemento debe estar presente.
queryBy…Devuelve null si no lo encuentra.Para comprobar que algo no está (ausencia).
findBy…Espera de forma asíncrona (por defecto 1000 ms).Para elementos que aparecen tras una operación asíncrona.

userEvent frente a fireEvent

fireEvent dispara un evento crudo del DOM. userEvent simula la interacción completa de una persona: al escribir, dispara focus, keydown, keypress, input y keyup. Por eso siempre debe preferirse.

  • Se inicializa una vez: const user = userEvent.setup().
  • Todos sus métodos son asíncronos: await user.click(...), await user.type(...).
No olvides el await

Los métodos de userEvent devuelven promesas. Si no las esperas, el test puede hacer la aserción antes de que el estado se actualice y dar un falso negativo (o un falso positivo más peligroso todavía).

3 · Ejemplo mínimo

El componente más pequeño que podemos probar: un botón que recibe un callback.

src/components/Button.jsx
export default function Button({ children, onClick }) {
  return (
    <button type="button" onClick={onClick}>
      {children}
    </button>
  );
}
src/components/Button.test.jsx
import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import Button from "./Button";

describe("Button", () => {
  it("muestra el texto que recibe", () => {
    render(<Button>Guardar</Button>);

    // getByRole es la query prioritaria: "como lo haría un usuario"
    expect(screen.getByRole("button", { name: "Guardar" })).toBeInTheDocument();
  });

  it("llama a onClick al pulsar", async () => {
    const handleClick = vi.fn();
    const user = userEvent.setup();

    render(<Button onClick={handleClick}>Guardar</Button>);

    await user.click(screen.getByRole("button", { name: "Guardar" }));

    expect(handleClick).toHaveBeenCalledOnce();
  });
});

Línea por línea:

  1. render(<Button>Guardar</Button>): monta el componente en jsdom.
  2. screen.getByRole("button", { name: "Guardar" }): busca por rol de accesibilidad y por su nombre accesible (el texto).
  3. toBeInTheDocument(): matcher extra que aporta @testing-library/jest-dom; comprueba que el nodo está en el DOM.
  4. vi.fn(): una función simulada que registra si fue llamada. Esto conecta RTL con la siguiente lección (mocks).
  5. await user.click(...): simula el clic real y espera a que React procese la actualización.

4 · Ejemplo real

Probemos un componente con estado propio: un formulario para añadir tareas en TaskFlow. Aquí veremos queries de label, user.type y validación.

src/components/TaskForm.jsx
import { useState } from "react";

export default function TaskForm({ onSubmit }) {
  const [title, setTitle] = useState("");

  function handleSubmit(event) {
    event.preventDefault();
    const trimmed = title.trim();
    if (trimmed === "") return; // no enviamos títulos vacíos
    onSubmit(trimmed);
    setTitle("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="task-title">Título de la tarea</label>
      <input
        id="task-title"
        value={title}
        onChange={(event) => setTitle(event.target.value)}
        placeholder="Nueva tarea"
      />
      <button type="submit">Añadir tarea</button>
    </form>
  );
}
src/components/TaskForm.test.jsx
import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import TaskForm from "./TaskForm";

describe("TaskForm", () => {
  it("envía el título recortado y limpia el input", async () => {
    const user = userEvent.setup();
    const onSubmit = vi.fn();

    render(<TaskForm onSubmit={onSubmit} />);

    // getByLabelText conecta con el <label htmlFor>
    const input = screen.getByLabelText("Título de la tarea");
    await user.type(input, "  Comprar pan  ");
    await user.click(screen.getByRole("button", { name: "Añadir tarea" }));

    expect(onSubmit).toHaveBeenCalledWith("Comprar pan");
    expect(input).toHaveValue("");
  });

  it("no envía si el título está vacío", async () => {
    const user = userEvent.setup();
    const onSubmit = vi.fn();

    render(<TaskForm onSubmit={onSubmit} />);
    await user.click(screen.getByRole("button", { name: "Añadir tarea" }));

    expect(onSubmit).not.toHaveBeenCalled();
  });
});

Decisiones explicadas:

  • getByLabelText: buscamos el input por su etiqueta, exactamente como lo localizaría una persona con un lector de pantalla.
  • user.type con espacios: comprobamos que el componente recorta (trim) antes de enviar. El test documenta el comportamiento real.
  • Dos aserciones con sentido: una sobre el callback (onSubmit) y otra sobre el estado visible (input vacío). Ambas son observables por el usuario.
  • Función simulada como prop: no nos interesa qué hace el padre; solo que el hijo invoca el contrato correcto.

Renderizado con providers

En una app real, los componentes suelen necesitar contexto (tema, autenticación, router). En lugar de envolver cada test, creamos un render personalizado.

src/test/test-utils.jsx
import { render } from "@testing-library/react";
import { ThemeProvider } from "../contexts/ThemeContext";
import { AuthProvider } from "../contexts/AuthContext";

// Envuelve cualquier UI con los providers globales de la app
function AllProviders({ children }) {
  return (
    <AuthProvider>
      <ThemeProvider>{children}</ThemeProvider>
    </AuthProvider>
  );
}

function customRender(ui, options) {
  return render(ui, { wrapper: AllProviders, ...options });
}

// Reexportamos todo y sobrescribimos render
export * from "@testing-library/react";
export { customRender as render };
Un único punto de entrada

Todos los tests importan render desde test/test-utils. El día que añadas un provider nuevo, lo tocas en un solo sitio y toda la suite queda cubierta.

6 · Errores habituales

Error 1: abusar de data-testid

✘ Incorrecto 
// El componente se llena de atributos solo para los tests
<button data-testid="submit-btn">Enviar</button>

// El test ignora la accesibilidad
screen.getByTestId("submit-btn"); // 💥 frágil y poco expresivo
✔ Correcto 
// Sin atributos extra: el texto ya es un nombre accesible
<button type="submit">Enviar</button>

screen.getByRole("button", { name: "Enviar" }); // ✅

Error 2: fireEvent en lugar de userEvent

✘ Incorrecto 
// Dispara un único evento input, sin foco ni teclado
fireEvent.change(input, { target: { value: "hola" } }); // 💥 irreal
✔ Correcto 
// Simula la escritura real, evento a evento
const user = userEvent.setup();
await user.type(input, "hola"); // ✅

Error 3: comprobar el estado interno en vez de la UI

✘ Incorrecto 
// Nos acoplamos al nombre interno del estado
expect(wrapper.state("count")).toBe(1); // 💥 se rompe al refactorizar
✔ Correcto 
// Comprobamos lo que el usuario ve
expect(screen.getByText("Contador: 1")).toBeInTheDocument(); // ✅

7 · Ejercicio guiado

Vamos a probar un componente Counter que muestra un número y tiene dos botones.

  1. Crea src/components/Counter.jsx con un useState(0), un párrafo que muestre el texto Contador: 0 y dos botones: "+1" y "Reiniciar".

  2. Crea src/components/Counter.test.jsx e importa render, screen y userEvent.

  3. Escribe un test que compruebe que al montar se muestra Contador: 0.

  4. Añade un test que haga dos clics en "+1" y espere ver Contador: 2.

  5. Añade un test que, tras subir el contador, pulse "Reiniciar" y espere ver Contador: 0.

  6. Ejecuta pnpm vitest run y revisa el reporte.

Solución:

src/components/Counter.jsx
import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Contador: {count}</p>
      <button type="button" onClick={() => setCount((c) => c + 1)}>+1</button>
      <button type="button" onClick={() => setCount(0)}>Reiniciar</button>
    </div>
  );
}
src/components/Counter.test.jsx
import { describe, it, expect } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import Counter from "./Counter";

describe("Counter", () => {
  it("muestra 0 al montar", () => {
    render(<Counter />);
    expect(screen.getByText("Contador: 0")).toBeInTheDocument();
  });

  it("incrementa al pulsar +1", async () => {
    const user = userEvent.setup();
    render(<Counter />);

    await user.click(screen.getByRole("button", { name: "+1" }));
    await user.click(screen.getByRole("button", { name: "+1" }));

    expect(screen.getByText("Contador: 2")).toBeInTheDocument();
  });

  it("vuelve a 0 al reiniciar", async () => {
    const user = userEvent.setup();
    render(<Counter />);

    await user.click(screen.getByRole("button", { name: "+1" }));
    await user.click(screen.getByRole("button", { name: "Reiniciar" }));

    expect(screen.getByText("Contador: 0")).toBeInTheDocument();
  });
});

8 · Reto

🎯 Render personalizado, router y accesibilidad

Escribe los tests de un componente que navega a otra ruta tras enviar un formulario. El reto tiene cuatro partes; no lo resuelvas todavía:

  1. Render con Router: adapta test/test-utils.jsx para envolver la UI en un MemoryRouter con rutas iniciales configurables.
  2. Navegación: verifica que tras un envío válido el componente navega a /dashboard y que en la nueva pantalla aparece un heading esperado.
  3. Accesibilidad: asegúrate de que puedes localizar todos los campos con getByRole/getByLabelText sin usar ningún data-testid.
  4. Ausencia: añade un test que compruebe con queryBy… que el mensaje de error no está presente cuando ya se ha enviado correctamente.

Pista: la opción { wrapper } de render acepta cualquier componente. Para las rutas iniciales del MemoryRouter usa initialEntries.

9 · Resumen

  • RTL prueba el comportamiento observable, no la implementación.
  • render monta el componente en jsdom y screen da acceso al DOM.
  • Prioriza getByRole y getByLabelText; deja getByTestId como último recurso.
  • getBy exige presencia, queryBy comprueba ausencia, findBy espera lo asíncrono.
  • userEvent simula interacciones reales; recuerda siempre el await.
  • Un render personalizado centraliza los providers de la app.

10 · Preguntas frecuentes

¿De dónde salen matchers como toBeInTheDocument?

Los aporta @testing-library/jest-dom. Se importa una vez en src/test/setup.js con import "@testing-library/jest-dom" y queda disponible en toda la suite.

¿Cuándo uso findBy en lugar de getBy?

Siempre que el elemento aparezca tras una operación asíncrona: una petición de red, una animación, un setTimeout antes de actualizar el DOM. findBy reintenta hasta encontrarlo o hasta agotar el tiempo (1000 ms por defecto).

¿Cómo pruebo un custom hook?

Con renderHook de RTL. Devuelve un objeto result cuya propiedad current expone lo que devuelve el hook. Para actualizarlo se usa act. Lo veremos en el proyecto del módulo.

¿Necesito React DevTools para testear?

No es obligatorio, pero ayuda mucho. Con React DevTools inspeccionas el árbol de componentes en el navegador y descubres los roles y textos reales para escribir tus queries correctamente.

¿Por qué no debo comprobar el estado interno?

Porque el estado es un detalle de implementación. Podrías renombrarlo, moverlo a un hook o a Context sin cambiar nada de lo que ve el usuario, y tus tests no deberían romperse. Prueba siempre el resultado visible.
