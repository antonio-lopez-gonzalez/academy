Mocks y spies

Módulo 12 · Testing 🕐 35 minutos

1 · Introducción

Hasta ahora hemos probado código autocontenido: funciones puras y componentes que no dependen del exterior. Pero una app real habla con una API, lee del localStorage, usa setTimeout o navega con React Router. En un test no queremos que esas dependencias hagan peticiones de red reales ni que dependan del reloj del sistema.

Los mocks y spies (término en inglés, "espías") son las herramientas que nos permiten sustituir o vigilar esas dependencias. Vitest las ofrece a través del objeto global vi.

¿Qué problema resuelven? Aíslan la unidad bajo prueba: un test debe fallar solo cuando tu código falla, no cuando el servidor está caído. Además permiten controlar escenarios imposibles de provocar a mano, como un error 500 o un temporizador de 10 segundos.

¿Cuándo se usan? Cuando la unidad depende de algo externo: red, tiempo, módulos de terceros, navegación o APIs del navegador.

Errores típicos: mockear tanto que el test ya no prueba nada real, olvidar limpiar los mocks entre tests, o intentar usar una variable declarada fuera de vi.mock (Vitest la "eleva" al principio del archivo y falla).

2 · Teoría

Spy, stub y mock: tres palabras que se confunden

TérminoQué haceHerramienta en Vitest
Spy (espía) Envuelve una función real para registrar cómo se llamó, sin cambiar su comportamiento. vi.spyOn(objeto, "metodo")
Stub (sustituto) Reemplaza una función por otra con un retorno fijo. vi.fn().mockReturnValue(...)
Mock (simulación) Reemplaza módulos o funciones enteras con implementaciones controladas. vi.fn(), vi.mock()

vi.fn: la función simulada

vi.fn() crea una función que no hace nada pero recuerda todo: cuántas veces se llamó, con qué argumentos y qué devolvió. Es la base de todo lo demás.

src/utils/format.js
// Una función que recibe callbacks: ideal para probar con vi.fn()
export function processItems(items, onEach) {
  return items.map((item) => {
    onEach(item);
    return item.toUpperCase();
  });
}

Comportamientos que puedes programar en una función simulada:

  • mockReturnValue(v) — devuelve siempre v.
  • mockReturnValueOnce(v) — devuelve v solo la primera vez.
  • mockImplementation(fn) — usa fn como implementación.
  • mockResolvedValue(v) — para funciones async, resuelve con v.
  • mockRejectedValue(err) — para funciones async, rechaza con err.

vi.spyOn: espiar sin destruir

A diferencia de vi.fn, spyOn conserva la implementación original salvo que la sobrescribas. Es perfecto para comprobar que se llamó a una función real.

src/utils/logger.js
export function log(message) {
  console.log(`[TaskFlow] ${message}`); // efecto secundario real
}
Restaura siempre los spies

Un spy cambia una función global durante el test. Si no lo restauras con spy.mockRestore(), el siguiente test heredará ese spy. Configurar restoreMocks: true en vite.config.js lo hace automáticamente.

vi.mock: reemplazar un módulo entero

vi.mock("ruta/al/modulo") sustituye un módulo por completo. Vitest lo eleva (hoisting) al inicio del archivo, antes de cualquier import. Por eso no puede referenciar variables declaradas más abajo con const. 

// Reemplaza ../api/tasks por una versión falsa controlada
vi.mock("../api/tasks", () => ({
  fetchTasks: vi.fn(),
  createTask: vi.fn(),
}));
Por qué se eleva el mock

Los import de JavaScript se resuelven antes de ejecutar el cuerpo del módulo. Para poder interceptar un import, Vitest debe registrar el mock antes de que se evalúe el import. De ahí la elevación y la limitación de no usar variables externas.

Mock de fetch (red)

Para probar código que usa la Fetch API, sustituimos global.fetch por una función simulada que devuelve una respuesta controlada. 

beforeEach(() => {
  global.fetch = vi.fn();
});

it("carga las tareas", async () => {
  fetch.mockResolvedValueOnce({
    ok: true,
    json: async () => [{ id: 1, title: "Tarea" }],
  });

  const tasks = await fetchTasks();
  expect(tasks).toHaveLength(1);
});

Fake timers (tiempo)

Los fake timers toman el control de setTimeout, setInterval y Date. Así pruebas temporizadores sin esperar de verdad. 

vi.useFakeTimers();

const callback = vi.fn();
setTimeout(callback, 1000);

expect(callback).not.toHaveBeenCalled(); // aún no
vi.advanceTimersByTime(1000);            // adelantamos el reloj
expect(callback).toHaveBeenCalled();     // ahora sí

vi.useRealTimers(); // devolvemos el control
Métodos de limpieza

mockClear() borra el historial de llamadas; mockReset() además borra la implementación; mockRestore() devuelve la función original (en spies). vi.clearAllMocks() aplica clear a todos.

3 · Ejemplo mínimo

Empecemos con lo más simple: comprobar que una función llama a su callback.

src/utils/format.test.js
import { describe, it, expect, vi } from "vitest";
import { processItems } from "./format";

describe("processItems", () => {
  it("llama al callback por cada elemento y transforma el array", () => {
    // vi.fn(): no hace nada, pero registra las llamadas
    const onEach = vi.fn();

    const result = processItems(["a", "b"], onEach);

    // Comprobamos el resultado visible
    expect(result).toEqual(["A", "B"]);
    // Comprobamos que el callback se invocó por cada elemento
    expect(onEach).toHaveBeenCalledTimes(2);
    expect(onEach).toHaveBeenNthCalledWith(1, "a");
    expect(onEach).toHaveBeenNthCalledWith(2, "b");
  });
});

Línea por línea:

  1. const onEach = vi.fn(): crea la función simulada. Al principio no devuelve nada.
  2. processItems(["a", "b"], onEach): pasamos el mock como dependencia.
  3. expect(result).toEqual(["A", "B"]): verificamos el comportamiento real de la función.
  4. toHaveBeenCalledTimes(2): comprobamos el contrato con el callback.
  5. toHaveBeenNthCalledWith(1, "a"): verificamos el argumento exacto en la primera llamada.

4 · Ejemplo real

En TaskFlow, un componente carga tareas desde una capa de servicios. Vamos a mockear ese módulo para que el componente se pruebe de forma aislada y determinista.

src/api/tasks.js
// Capa de acceso a la API real
export async function fetchTasks() {
  const response = await fetch("/api/tasks");
  if (!response.ok) throw new Error("Failed to fetch tasks");
  return response.json();
}
src/components/TaskList.jsx
import { useEffect, useState } from "react";
import { fetchTasks } from "../api/tasks";

export default function TaskList() {
  const [tasks, setTasks] = useState([]);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetchTasks()
      .then(setTasks)
      .catch((err) => setError(err.message));
  }, []);

  if (error) return <p role="alert">{error}</p>;

  return (
    <ul>
      {tasks.map((task) => (
        <li key={task.id}>{task.title}</li>
      ))}
    </ul>
  );
}
src/components/TaskList.test.jsx
import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import TaskList from "./TaskList";
import { fetchTasks } from "../api/tasks";

// Reemplazamos el módulo real por uno con funciones simuladas.
// Vitest eleva este mock al inicio del archivo.
vi.mock("../api/tasks", () => ({
  fetchTasks: vi.fn(),
}));

describe("TaskList", () => {
  it("renderiza las tareas que devuelve la API", async () => {
    // Programamos el retorno del mock
    fetchTasks.mockResolvedValue([
      { id: 1, title: "Diseñar el login" },
      { id: 2, title: "Escribir tests" },
    ]);

    render(<TaskList />);

    // findBy espera a que la promesa se resuelva y el DOM se actualice
    expect(await screen.findByText("Diseñar el login")).toBeInTheDocument();
    expect(screen.getByText("Escribir tests")).toBeInTheDocument();
    expect(fetchTasks).toHaveBeenCalledOnce();
  });

  it("muestra un error si la petición falla", async () => {
    fetchTasks.mockRejectedValue(new Error("Failed to fetch tasks"));

    render(<TaskList />);

    expect(await screen.findByRole("alert")).toHaveTextContent("Failed to fetch tasks");
  });
});

Decisiones explicadas:

  • vi.mock del módulo de API: el componente usa el módulo real en producción, pero en el test importa la versión simulada.
  • Importar fetchTasks después del mock: así obtenemos la función simulada y podemos programarla.
  • mockResolvedValue / mockRejectedValue: controlamos los dos caminos (éxito y error) sin red real.
  • findByRole("alert"): tras el rechazo, el componente pinta el error de forma asíncrona; esperamos con findBy.
Mock de módulo auto

Si solo necesitas simular todas las funciones de un módulo, existe el atajo vi.mock("../api/tasks") sin fábrica: Vitest lo genera automáticamente. La fábrica explícita es más clara y deja por escrito el contrato que se simula.

5 · Buenas prácticas

HazEvitaPor qué
Mockea solo dependencias externas (red, tiempo, terceros) Mockear tu propio código interno Si mockeas tu lógica, el test ya no prueba tu app.
Limpia los mocks entre tests Dejar mocks con estado de un test a otro El historial de llamadas se acumula y provoca fallos fantasma.
Restaura los spies Modificar funciones globales sin restaurarlas Un spy global contamina el resto de la suite.
Verifica argumentos concretos Comprobar solo toHaveBeenCalled() Llamar de cualquier manera no es lo mismo que llamar bien.
Configura clearMocks/restoreMocks en Vite Limpiar a mano en cada archivo Una sola configuración evita repetición y olvidos.
El peligro del over-mock

Un test lleno de mocks que solo comprueba que se llamaron funciones no verifica que la app funcione: verifica que llamas a los mocks. Si dudas, reduce el número de mocks y deja que entre más código real en la prueba.

6 · Errores habituales

Error 1: referenciar variables externas dentro de vi.mock

✘ Incorrecto 
const fakeTasks = [{ id: 1 }]; // declarada después de la elevación

vi.mock("../api/tasks", () => ({
  fetchTasks: vi.fn(() => fakeTasks), // 💥 ReferenceError: se eleva antes
}));
✔ Correcto 
// Los datos van DENTRO de la fábrica del mock
vi.mock("../api/tasks", () => ({
  fetchTasks: vi.fn(() => Promise.resolve([{ id: 1 }])), // ✅
}));

Error 2: estado de mocks que se filtra entre tests

✘ Incorrecto 
it("primer test", () => {
  myMock("a");
});

it("segundo test", () => {
  // 💥 toHaveBeenCalledOnce falla: el historial del test anterior sigue ahí
  expect(myMock).toHaveBeenCalledOnce();
});
✔ Correcto 
afterEach(() => {
  vi.clearAllMocks(); // ✅ historial limpio entre tests
});

Error 3: dejarse una petición de red real

✘ Incorrecto 
it("carga usuarios", async () => {
  // 💥 fetch real: el test depende de internet y de un servidor vivo
  const users = await fetchUsers();
  expect(users.length).toBeGreaterThan(0);
});
✔ Correcto 
it("carga usuarios", async () => {
  fetch.mockResolvedValueOnce({ ok: true, json: async () => [userMock] }); // ✅
  const users = await fetchUsers();
  expect(users).toEqual([userMock]);
});

7 · Ejercicio guiado

Vamos a probar una utilidad de debounce (retardo) con fake timers, y un spy sobre console.log.

  1. Crea src/utils/debounce.js con debounce(fn, delay) que devuelva una función que solo ejecute fn si pasa delay ms sin volver a llamarse.

  2. Crea src/utils/debounce.test.js e importa debounce.

  3. En beforeEach activa los fake timers con vi.useFakeTimers(); en afterEach restáuralos con vi.useRealTimers().

  4. Escribe un test que compruebe que fn no se llama antes de delay y sí después, con vi.advanceTimersByTime(delay).

  5. Añade un test que llame al debounce varias veces seguidas y compruebe que solo se ejecuta una vez.

  6. Ejecuta pnpm vitest run y verifica que todo pasa.

Solución:

src/utils/debounce.js
export function debounce(fn, delay) {
  let timerId;
  return function (...args) {
    clearTimeout(timerId);               // cancela la llamada pendiente
    timerId = setTimeout(() => fn(...args), delay);
  };
}
src/utils/debounce.test.js
import { describe, it, expect, vi, beforeEach, afterEach } from "vitest";
import { debounce } from "./debounce";

describe("debounce", () => {
  beforeEach(() => {
    vi.useFakeTimers();      // controlamos el tiempo
  });

  afterEach(() => {
    vi.useRealTimers();      // devolvemos el reloj real
  });

  it("ejecuta la función pasado el retardo", () => {
    const fn = vi.fn();
    const debounced = debounce(fn, 200);

    debounced("hola");
    expect(fn).not.toHaveBeenCalled();   // todavía no

    vi.advanceTimersByTime(200);         // adelantamos 200 ms
    expect(fn).toHaveBeenCalledWith("hola");
  });

  it("solo ejecuta una vez aunque se llame varias seguidas", () => {
    const fn = vi.fn();
    const debounced = debounce(fn, 200);

    debounced();
    debounced();
    debounced();
    vi.advanceTimersByTime(200);

    expect(fn).toHaveBeenCalledOnce();
  });
});

8 · Reto

🎯 Error 500, navegación simulada y fecha fija

Amplía la suite de TaskFlow con estos escenarios. No lo resuelvas todavía:

  1. Error de red: haz que un componente muestre un botón "Reintentar" cuando la API responde con ok: false, y prueba que al pulsarlo vuelve a llamar a la API (usa mockResolvedValueOnce dos veces).
  2. React Router simulado: mockea react-router-dom para comprobar que, tras guardar, el componente llama a navigate("/dashboard").
  3. Fecha fija: usa vi.setSystemTime para que un componente que muestra "hace 2 días" sea determinista, sin depender de la fecha del sistema.
  4. Reset parcial: consigue que el spy de console.error siga existiendo entre tests pero con el historial limpio, y explica la diferencia entre mockClear, mockReset y mockRestore.

Pista: para mockear useNavigate recuerda que Link también está en ese módulo; mockea solo lo necesario e importa el módulo real donde no haga falta simularlo.

9 · Resumen

  • vi.fn() crea funciones simuladas que registran llamadas y permiten programar retornos.
  • vi.spyOn() vigila funciones reales sin cambiar su comportamiento; restáuralas con mockRestore().
  • vi.mock() reemplaza módulos enteros y se eleva al inicio del archivo (no admite variables externas).
  • Para la red, se simula global.fetch con mockResolvedValueOnce / mockRejectedValue.
  • Los fake timers controlan setTimeout, setInterval y Date.
  • Limpia con clearMocks/restoreMocks o vi.clearAllMocks() entre tests.
  • Mockea solo lo externo: el over-mocking destruye el valor del test.

10 · Preguntas frecuentes

¿Cuál es la diferencia entre mockClear, mockReset y mockRestore?

mockClear() borra el historial de llamadas pero deja la implementación. mockReset() borra el historial y la implementación (el mock vuelve a no hacer nada). mockRestore() devuelve la función original; se usa con spyOn.

¿Por qué mi vi.mock no funciona y da ReferenceError?

Porque Vitest eleva vi.mock al principio del archivo y la fábrica del mock se ejecuta antes de que se declaren tus variables. Solución: define los datos dentro de la propia fábrica, o usa vi.hoisted() para declararlos en el ámbito elevado.

¿Debo mockear siempre las llamadas a la API?

Sí, en tests unitarios y de integración. Nunca quieres que tu suite dependa de un servidor real. Para probar el backend de verdad están los tests end-to-end, que se ejecutan aparte con un entorno desplegado.

¿Los fake timers afectan a userEvent?

Pueden interferir: userEvent usa temporizadores internos. Si combinas ambos, configura userEvent.setup({ advanceTimers: vi.advanceTimersByTime }) para que la escritura avance el reloj simulado de forma coherente.
