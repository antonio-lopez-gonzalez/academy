🛠 Proyecto: suite de tests

Módulo 12 · Testing 🕐 60 minutos Proyecto

1 · Introducción

Llegó el proyecto del módulo. Vamos a construir una suite de tests completa para la funcionalidad de tareas de TaskFlow, aplicando todo lo aprendido: Vitest, React Testing Library y mocks. No vamos a probar "un ejemplo suelto", sino una porción real de la app con su capa de servicios, su hook y sus componentes.

La funcionalidad bajo prueba incluye:

  • Servicios: taskService, la capa que habla con la API.
  • Lógica pura: taskFilters para filtrar y resumir.
  • Hook: useTasks, que orquesta cargar, añadir, alternar y eliminar.
  • Componentes: TaskList, TaskItem y TaskForm.

El objetivo no es alcanzar un 100% de cobertura porque sí, sino documentar y proteger el comportamiento que nos importa con tests rápidos y fiables.

2 · Teoría

Arquitectura de la suite

Probar no es "escribir tests por escribir". Antes de empezar conviene decidir qué se prueba en cada capa. En TaskFlow seguimos esta separación:

taskFilters.js (lógica pura) → Vitest, sin DOM, datos => datos ▲ │ la usa useTasks.js (hook de estado) → renderHook + mock del servicio ▲ │ la usa taskService.js (acceso a red) → mock de global.fetch ▲ │ la usan Componentes (UI) → RTL + userEvent + mock del servicio

Cada capa se prueba en su nivel: la lógica pura no necesita React; el hook no necesita pintar nada; los componentes no necesitan la API real. Así cada test falla solo por un motivo.

Qué se prueba y qué no

CapaSí se pruebaNo se prueba
taskService Que construye la URL, el método HTTP y el cuerpo correctos; que lanza error si !ok. El servidor real (es E2E).
taskFilters Filtros por estado y texto, cálculo del resumen. Nada más: es pura.
useTasks Estados de carga/error, añadir, alternar, eliminar. El render de la UI.
Componentes Lo que el usuario ve y hace; callbacks invocados. El estado interno o los nombres de las variables.
La regla del "cinturón"

Escribe tests donde hay riesgo: lógica con condiciones, transformaciones de datos, flujos con estados. No gastes esfuerzo probando que un <div> es un <div>.

src/features/tasks/taskFilters.js
export function filterTasks(tasks, { status = "all", query = "" } = {}) {
  const normalized = query.trim().toLowerCase();

  return tasks.filter((task) => {
    const matchesStatus =
      status === "all" ||
      (status === "completed" && task.completed) ||
      (status === "pending" && !task.completed);

    const matchesQuery =
      normalized === "" || task.title.toLowerCase().includes(normalized);

    return matchesStatus && matchesQuery;
  });
}

export function taskStats(tasks) {
  const completed = tasks.filter((t) => t.completed).length;
  return { total: tasks.length, completed, pending: tasks.length - completed };
}

  { id: 2, title: "Escribir tests", completed: true },
];

4 · Paso 2: servicios, hook y componentes

Ahora el núcleo de la suite: probamos la capa de servicios (con fetch simulado), el hook (con renderHook) y los componentes (con RTL).

Servicios: mock de fetch

src/api/taskService.js
const API_URL = "/api/tasks";

export const taskService = {
  async getAll() {
    const response = await fetch(API_URL);
    if (!response.ok) throw new Error("Failed to fetch tasks");
    return response.json();
  },

  async create(task) {
    const response = await fetch(API_URL, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(task),
    });
    if (!response.ok) throw new Error("Failed to create task");
    return response.json();
  },

  async remove(id) {
    const response = await fetch(`${API_URL}/${id}`, { method: "DELETE" });
    if (!response.ok) throw new Error("Failed to delete task");
    return response.json();
  },
};
src/api/taskService.test.js
import { describe, it, expect, vi, beforeEach } from "vitest";
import { taskService } from "./taskService";

describe("taskService", () => {
  beforeEach(() => {
    global.fetch = vi.fn(); // sustituimos fetch por un mock
  });

  it("getAll pide la URL correcta y devuelve las tareas", async () => {
    const mockTasks = [{ id: 1, title: "Tarea", completed: false }];
    fetch.mockResolvedValueOnce({ ok: true, json: async () => mockTasks });

    const tasks = await taskService.getAll();

    expect(fetch).toHaveBeenCalledWith("/api/tasks");
    expect(tasks).toEqual(mockTasks);
  });

  it("getAll lanza error si la respuesta no es ok", async () => {
    fetch.mockResolvedValueOnce({ ok: false, status: 500 });

    await expect(taskService.getAll()).rejects.toThrow("Failed to fetch tasks");
  });

  it("create envía un POST con el cuerpo en JSON", async () => {
    const newTask = { title: "Nueva", completed: false };
    fetch.mockResolvedValueOnce({ ok: true, json: async () => ({ id: 1, ...newTask }) });

    await taskService.create(newTask);

    expect(fetch).toHaveBeenCalledWith("/api/tasks", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(newTask),
    });
  });
});

Hook: renderHook y mock del servicio

src/hooks/useTasks.js
import { useState, useEffect } from "react";
import { taskService } from "../api/taskService";

export function useTasks() {
  const [tasks, setTasks] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  async function loadTasks() {
    try {
      setLoading(true);
      setTasks(await taskService.getAll());
      setError(null);
    } catch (err) {
      setError(err.message);
    } finally {
      setLoading(false);
    }
  }

  async function addTask(title) {
    const created = await taskService.create({ title, completed: false });
    setTasks((prev) => [...prev, created]);
  }

  async function removeTask(id) {
    await taskService.remove(id);
    setTasks((prev) => prev.filter((t) => t.id !== id));
  }

  useEffect(() => {
    loadTasks();
  }, []);

  return { tasks, loading, error, addTask, removeTask, reload: loadTasks };
}
src/hooks/useTasks.test.js
import { describe, it, expect, vi } from "vitest";
import { renderHook, waitFor } from "@testing-library/react";
import { useTasks } from "./useTasks";
import { taskService } from "../api/taskService";

// Mock automático del módulo completo de servicios
vi.mock("../api/taskService");

describe("useTasks", () => {
  it("carga las tareas y apaga el loading", async () => {
    const mockTasks = [{ id: 1, title: "Tarea", completed: false }];
    taskService.getAll.mockResolvedValueOnce(mockTasks);

    const { result } = renderHook(() => useTasks());

    expect(result.current.loading).toBe(true); // estado inicial

    await waitFor(() => expect(result.current.loading).toBe(false));

    expect(result.current.tasks).toEqual(mockTasks);
    expect(taskService.getAll).toHaveBeenCalledOnce();
  });

  it("guarda el mensaje cuando la carga falla", async () => {
    taskService.getAll.mockRejectedValueOnce(new Error("Network error"));

    const { result } = renderHook(() => useTasks());

    await waitFor(() => expect(result.current.error).toBe("Network error"));
  });

  it("añade una tarea a la lista", async () => {
    taskService.getAll.mockResolvedValueOnce([]);
    const created = { id: 1, title: "Nueva", completed: false };
    taskService.create.mockResolvedValueOnce(created);

    const { result } = renderHook(() => useTasks());
    await waitFor(() => expect(result.current.loading).toBe(false));

    await result.current.addTask("Nueva");

    expect(taskService.create).toHaveBeenCalledWith({ title: "Nueva", completed: false });
    expect(result.current.tasks).toContainEqual(created);
  });
});

Ejecuta y observa

Lanza pnpm test y deja la terminal abierta. Escribe un test, guárdalo y verás cómo se re-ejecuta solo. Ese ciclo rápido es lo que hace productivo a Vitest.

5 · Buenas prácticas

HazEvitaPor qué
Prueba cada capa en su nivel Probar la lógica pura a través de un componente Los tests directos son más rápidos y con mensajes de error más claros.
Mockea solo en los bordes (red, tiempo, módulos externos) Mockear tus propios componentes internos Si simulas lo tuyo, ya no estás probando lo tuyo.
Nombra los tests con frases de comportamiento Nombres como "test 1" El nombre es la documentación viva de lo que la app garantiza.
Cubre los caminos de error Probar solo el caso feliz Los bugs viven en los bordes: fallos de red, listas vacías, datos raros.
Mantén la suite rápida (unitarios + integración) Meter E2E en el mismo comando Los E2E son lentos; sepáralos para que el ciclo de desarrollo siga siendo ágil.
Cobertura como brújula, no como meta

La cobertura te dice qué no estás probando. Perseguir el 100% produce tests vacíos. Fíjate un umbral razonable (por ejemplo 80% en líneas) y revisa qué queda fuera antes de escribir más tests.

6 · Errores habituales

Error 1: no esperar a que el hook resuelva

✘ Incorrecto 
const { result } = renderHook(() => useTasks());
// 💥 el efecto asíncrono aún no ha terminado
expect(result.current.tasks).toHaveLength(1);
✔ Correcto 
const { result } = renderHook(() => useTasks());
// ✅ esperamos a que el loading termine
await waitFor(() => expect(result.current.loading).toBe(false));
expect(result.current.tasks).toHaveLength(1);

Error 2: reutilizar mocks sin limpiarlos

✘ Incorrecto 
// Sin clearMocks, el historial de un test contamina el siguiente
vi.mock("../api/taskService");
// 💥 toHaveBeenCalledOnce falla porque cuenta llamadas de tests previos
✔ Correcto 
// En vite.config.js, dentro de test:
test: {
  clearMocks: true, // ✅ historial limpio entre tests
}

Error 3: probar la implementación de los componentes

✘ Incorrecto 
// Nos acoplamos al nombre de la clase CSS interna
const item = container.querySelector(".task-item--done"); // 💥 frágil
expect(item).toBeTruthy();
✔ Correcto 
// Comprobamos el estado observable por el usuario
expect(screen.getByRole("checkbox")).toBeChecked(); // ✅

7 · Ejercicio guiado

Completa la suite con los tests del flujo de eliminación y del estado vacío del hook.

  1. Añade en useTasks.test.js un test "elimina una tarea de la lista".

  2. Dentro del test: simula taskService.getAll con una tarea y taskService.remove con {}.

  3. Espera a que loading sea false con waitFor.

  4. Llama a await result.current.removeTask(1).

  5. Comprueba que taskService.remove se llamó con 1 y que result.current.tasks quedó vacío.

  6. Ejecuta pnpm test:coverage y observa qué líneas de useTasks.js siguen sin cubrirse.

Solución (añadido a useTasks.test.js):

src/hooks/useTasks.test.js (nuevo test)
it("elimina una tarea de la lista", async () => {
  const mockTasks = [{ id: 1, title: "Tarea", completed: false }];
  taskService.getAll.mockResolvedValueOnce(mockTasks);
  taskService.remove.mockResolvedValueOnce({});

  const { result } = renderHook(() => useTasks());
  await waitFor(() => expect(result.current.loading).toBe(false));

  await result.current.removeTask(1);

  expect(taskService.remove).toHaveBeenCalledWith(1);
  expect(result.current.tasks).toEqual([]);
});

El informe HTML que genera --coverage se abre en coverage/index.html. Las líneas en rojo son las que no se ejecutaron nunca durante los tests: suelen revelar caminos de error o ramas que has olvidado.

8 · Reto

🎯 Suite lista para producción

Lleva la suite al siguiente nivel. No lo resuelvas todavía; inténtalo y luego compara:

  1. Umbral de cobertura: configura coverage.thresholds con 80% en líneas y 70% en ramas, y añade un script test:ci que falle si no se alcanza.
  2. Test de integración: monta TaskList dentro de un componente contenedor que use useTasks y prueba el flujo completo: añadir → aparecer en la lista → eliminar → desaparecer.
  3. Accesibilidad automatizada: instala jest-axe (o vitest-axe) y añade una comprobación de que TaskForm no tiene violaciones de accesibilidad.
  4. CI: crea un workflow que ejecute pnpm install --frozen-lockfile, pnpm test:ci y pnpm build en cada push.
  5. Fixture factory: refactoriza los datos de prueba a un makeTask(overrides) en src/test/factories.js para no repetir objetos por toda la suite.

Pista: para el test de integración reutiliza el render personalizado con providers del ejemplo real de la lección anterior.

9 · Resumen

  • Has construido una suite completa organizada por capas: lógica pura, servicios, hook y componentes.
  • Servicios: fetch simulado para probar URL, método, cuerpo y errores.
  • Hook: renderHook + waitFor con el módulo de servicios mockeado.
  • Componentes: RTL y userEvent, comprobando comportamiento, no implementación.
  • Configuración centralizada en vite.config.js y src/test/setup.js.
  • La cobertura es una brújula para encontrar lo no probado, no una meta absoluta.

10 · Preguntas frecuentes

¿Cuántos tests debo escribir por componente?

No hay un número fijo. Escribe un test por comportamiento relevante: qué muestra al montar, qué hace al interactuar y cómo reacciona en los casos límite (vacío, error, extremos). Si un test no añade confianza nueva, es ruido.

¿Los tests forman parte del build de producción?

No. Los archivos *.test.js(x) se excluyen del bundle de Vite. En vite.config.js los incluimos solo para el coverage y para ejecutarlos; el build de la app no los toca.

¿Debo llegar al 100% de cobertura?

Normalmente no. El 100% obliga a escribir tests artificiales para líneas triviales. Un umbral del 80% suele ser un buen equilibrio. Lo importante es cubrir bien la lógica con ramas y los caminos de error.

¿Cómo pruebo el flujo con el backend real?

Eso son pruebas end-to-end (E2E) con herramientas como Playwright, que arrancan la app y el backend de verdad. Se mantienen separadas de la suite de Vitest por su coste. Aquí probamos cada pieza de forma aislada y determinista.
