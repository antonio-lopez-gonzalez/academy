Zustand

Módulo 10 · Estado global 🕐 30 minutos

1 · Introducción

En las lecciones anteriores resolvimos el estado global con tres herramientas distintas: Context API (estado compartido sin librerías), useReducer (lógica compleja dentro de un componente) y Redux Toolkit (un contenedor global predecible y muy potente). Todas funcionan, pero ninguna es gratuita: Context obliga a envolver la app en un <Provider> y a vigilar los re-renderizados, y Redux Toolkit, aunque simplifica mucho el Redux clásico, todavía arrastra slice, store, Provider y dos hooks.

Zustand es una cuarta vía: una librería de estado global minimalista. La palabra es alemana y significa literalmente "estado". Su filosofía es justo esa: crear un estado global sin ceremonia. No hay Provider, no hay action types, no hay reducers obligatorios, y el componente que consume el estado se parece muchísimo a usar useState, solo que el valor vive fuera y lo comparten todos.

¿Qué problema resuelve? El dolor de cabeza típico: "quiero estado global, pero Context me re-renderiza medio árbol y Redux me parece demasiado para esta app". Zustand se coloca en ese hueco: tan simple como Context, con selección granular de estado (como Redux, solo re-renderiza quien consume lo que cambi) y una API de una sola función, create().

¿Cuándo lo usamos? En aplicaciones pequeñas y medianas con estado global compartido (carrito, usuario, tema, filtros, preferencias), cuando queremos persistencia automática en localStorage y cuando trabajamos con estado que también debe leerse desde fuera de React (por ejemplo, dentro de un manejador de eventos global o una utilidad).

📍 Antes de seguir

Si todavía no has leído la lección de Context API, hazlo primero: casi todos los conceptos de esta lección se explican por contraste con Context y con Redux Toolkit.

2 · Teoría

La diferencia fundamental: dónde vive el estado

En Context y en Redux el estado vive dentro del árbol de React, y por eso necesitas un <Provider> que lo inyecte hacia abajo. Zustand rompe esa idea: crea una store que vive fuera de React, en un módulo JavaScript normal. Es una simple variable con datos y funciones. Los componentes se suscriben a ella mediante un hook que la propia store genera.

create() ─► store (fuera del árbol de React) │ ┌───────────┼───────────┐ ▼ ▼ ▼ Componente Componente Componente useStore() useStore() useStore() │ ▼ (selector: "dame solo esto") re-render SOLO si cambia lo seleccionado

Ese último punto es la clave del rendimiento: no re-renderiza por suscripción global. Cada componente declara qué trozo del estado le interesa, y Zustand compara ese trozo con el anterior. Si no cambió, el componente no se vuelve a dibujar.

🧠 Analogía: la pizarra compartida

Imagina una pizarra en la sala común de una oficina. Cualquiera puede acercarse y leer lo que le interesa (no toda la pizarra, solo su mesa), y cualquiera puede escribir en ella. Nadie tiene que repartir fotocopias de la pizarra a cada despacho (eso sería el <Provider>): la pizarra está ahí y quien la necesita la consulta. Zustand es esa pizarra.

Las piezas de Zustand

  • create(): crea la store. Recibe una función que recibe set y get y devuelve un objeto con el estado y las acciones.
  • set: actualiza el estado. Acepta un objeto con los campos a cambiar o una función (state) => partial.
  • get: lee el estado actual desde dentro de una acción. Útil para lógica que depende de valores actuales.
  • Hook generado: create() devuelve un hook (useCounterStore) que los componentes usan para leer y actuar.
  • Selectores: useStore((state) => state.campo) para suscribirse solo a una parte.
  • Middlewares: persist (guarda en localStorage), devtools (Redux DevTools), immer (permitir mutación estilo RTK).

Instalación

terminal
pnpm add zustand

Un solo paquete, cero dependencias obligatorias. Nada de react-redux ni @reduxjs/toolkit: Zustand trae el binding de React incluido.

Anatomía de una store

src/store/counterStore.js
import { create } from "zustand";

export const useCounterStore = create((set, get) => ({
  // ---- estado ----
  count: 0,

  // ---- acciones ----
  // set recibe un objeto parcial: Zustand lo fusiona con el estado actual
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
  reset: () => set({ count: 0 }),

  // get permite leer el estado actual dentro de una acción
  double: () => set({ count: get().count * 2 }),
}));
⚠️ set fusiona, no reemplaza

En el nivel superior, set hace una fusión superficial (shallow merge). Es decir, set({ count: 0 }) cambia count y conserva el resto de campos y acciones. Esto es distinto de useState, donde pasar un objeto lo reemplaza entero. Pero cuidado: la fusión es solo del primer nivel; si tu estado es anidado, tú debes crear las copias necesarias.

💡 ¿Por qué a Zustand le importa tanto el selector?

Porque en React, "re-renderizar" es volver a ejecutar tu función de componente. Si un componente se suscribe a la store completa y cualquier parte cambia, se re-ejecuta sin necesidad. El selector es el contrato que le dice a Zustand: "avísame solo si este pedacito concreto cambia". Cuanto más fino el selector, menos trabajo para React.

3 · Ejemplo mínimo

El ejemplo más pequeño posible: un contador global. Fíjate en que no hay Provider ni acción que despachar; el componente usa la store como si fuera un useState compartido.

src/store/counterStore.js
import { create } from "zustand";

// create() devuelve un hook: useCounterStore
export const useCounterStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
  reset: () => set({ count: 0 }),
}));
src/components/Counter.jsx
import { useCounterStore } from "../store/counterStore";

export default function Counter() {
  // Un selector por cada valor/acción que necesitamos.
  // El componente solo se re-renderiza cuando "count" cambia.
  const count = useCounterStore((state) => state.count);
  const increment = useCounterStore((state) => state.increment);
  const decrement = useCounterStore((state) => state.decrement);
  const reset = useCounterStore((state) => state.reset);

  return (
    <div>
      <p>Contador: {count}</p>
      <button onClick={decrement}>-</button>
      <button onClick={increment}>+</button>
      <button onClick={reset}>Reset</button>
    </div>
  );
}
src/App.jsx
import Counter from "./components/Counter";

// ¡No hay Provider! La store ya existe por sí sola.
export default function App() {
  return <Counter />;
}

Línea por línea, lo importante:

  • create((set) => ({...})): la función recibe set y devuelve el estado inicial mezclado con las acciones. Todo en un solo objeto.
  • set((state) => ({ count: state.count + 1 })): usamos la forma de función para leer el valor más reciente del estado y evitar problemas si hay varias actualizaciones seguidas.
  • useCounterStore((state) => state.count): el selector. Solo nos suscribimos a count.
  • <button onClick={increment}>: la acción ya es una función del estado; no hay que envolverla en dispatch(...).

4 · Ejemplo real

Ahora algo cercano a producción: un carrito de compra con selección granular, totales derivados y persistencia automática en localStorage usando el middleware persist. Verás que varios componentes consumen la misma store sin pasarles nada por props.

src/store/cartStore.js
import { create } from "zustand";
import { persist } from "zustand/middleware";

export const useCartStore = create(
  // persist envuelve la store y sincroniza el estado con localStorage.
  persist(
    (set, get) => ({
      items: [],

      // Añadir producto: si ya existe, sube la cantidad; si no, lo añade.
      addItem: (product) => {
        const exists = get().items.find((item) => item.id === product.id);
        if (exists) {
          set({
            items: get().items.map((item) =>
              item.id === product.id
                ? { ...item, quantity: item.quantity + 1 }
                : item
            ),
          });
        } else {
          set({ items: [...get().items, { ...product, quantity: 1 }] });
        }
      },

      // Quitar un producto por id
      removeItem: (id) =>
        set({ items: get().items.filter((item) => item.id !== id) }),

      // Fijar una cantidad concreta (mínimo 1)
      setQuantity: (id, quantity) =>
        set({
          items: get().items.map((item) =>
            item.id === id ? { ...item, quantity: Math.max(1, quantity) } : item
          ),
        }),

      // Vaciar el carrito
      clear: () => set({ items: [] }),
    }),
    {
      name: "react19-cart", // clave bajo la que se guarda en localStorage
      // Solo persistimos "items"; las funciones no se guardan.
      partialize: (state) => ({ items: state.items }),
    }
  )
);
🧩 ¿Por qué derivamos el total y no lo guardamos?

El total (price × quantity sumado) es estado derivado: se puede calcular a partir de items. Si lo guardáramos en la store, tendríamos dos fuentes de verdad que podrían desincronizarse. Mejor calcularlo en un selector. Esta misma idea ya la aprendiste con Redux Toolkit.

src/store/cartStore.js (continuación)
// Selectores: funciones puras que derivan datos del estado.
// Se definen fuera del componente para no recrearlas en cada render.
export const selectItemCount = (state) =>
  state.items.reduce((count, item) => count + item.quantity, 0);

export const selectTotal = (state) =>
  state.items.reduce((total, item) => total + item.price * item.quantity, 0);
src/components/ProductList.jsx
import { useCartStore } from "../store/cartStore";

const products = [
  { id: 1, name: "Camiseta", price: 20 },
  { id: 2, name: "Pantalón", price: 40 },
  { id: 3, name: "Zapatos", price: 60 },
];

export default function ProductList() {
  // Suscripción a UNA sola acción: este componente no se re-renderiza
  // cuando el carrito cambia de contenido.
  const addItem = useCartStore((state) => state.addItem);

  return (
    <ul>
      {products.map((product) => (
        <li key={product.id}>
          {product.name} — ${product.price}
          <button onClick={() => addItem(product)}>Añadir</button>
        </li>
      ))}
    </ul>
  );
}
src/components/CartBadge.jsx
import { useCartStore, selectItemCount } from "../store/cartStore";

export default function CartBadge() {
  // Selector derivado: el badge solo se re-renderiza si cambia el número.
  const count = useCartStore(selectItemCount);
  return <span className="badge">🛒 {count}</span>;
}
src/components/Cart.jsx
import { useCartStore, selectTotal } from "../store/cartStore";

export default function Cart() {
  // Seleccionamos items (array) y las acciones que necesitamos.
  const items = useCartStore((state) => state.items);
  const removeItem = useCartStore((state) => state.removeItem);
  const setQuantity = useCartStore((state) => state.setQuantity);
  const clear = useCartStore((state) => state.clear);
  const total = useCartStore(selectTotal);

  if (items.length === 0) {
    return <p>El carrito está vacío</p>;
  }

  return (
    <div>
      <ul>
        {items.map((item) => (
          <li key={item.id}>
            {item.name} — ${item.price} ×
            <input
              type="number"
              min="1"
              value={item.quantity}
              onChange={(e) => setQuantity(item.id, Number(e.target.value))}
            />
            <button onClick={() => removeItem(item.id)}>Eliminar</button>
          </li>
        ))}
      </ul>

      <h3>Total: ${total.toFixed(2)}</h3>
      <button onClick={clear}>Vaciar carrito</button>
    </div>
  );
}

Decisiones de diseño que merece la pena destacar:

  • Todos los componentes leen la misma store sin recibir props ni estar dentro de un Provider. ProductList, CartBadge y Cart comparten estado sin conocerse.
  • partialize evita persistir las funciones: solo guardamos items. Si guardáramos todo, localStorage contendría acciones inútiles.
  • Estado derivado en selectores: selectTotal y selectItemCount se calculan al vuelo; nada de duplicar datos.
  • Solo actualizamos con set. La inmutabilidad se respeta creando arrays nuevos con map y filter.

🔧 Lógica asíncrona sin complicaciones

En Zustand las acciones son funciones normales, así que pueden ser async. No necesitas createAsyncThunk: declara la acción como async, haz el await fetch(...) y llama a set con el resultado.

src/store/usersStore.js
export const useUsersStore = create((set) => ({
  users: [],
  loading: false,
  error: null,

  fetchUsers: async () => {
    set({ loading: true, error: null });          // estado de carga
    try {
      const res = await fetch("https://api.example.com/users");
      if (!res.ok) throw new Error("Error al cargar usuarios");
      const users = await res.json();
      set({ users, loading: false });             // éxito
    } catch (error) {
      set({ error: error.message, loading: false }); // error
    }
  },
}));

6 · Errores habituales

Error 1: desestructurar la store completa

Mal — se re-renderiza por cualquier cambio 
function Cart() {
  // ✘ Al suscribirnos al objeto ENTERO, cualquier cambio en la store
  //   (aunque sea una acción o un campo que no usamos) re-renderiza.
  const { items, total, removeItem } = useCartStore();
  return <h3>{total}</h3>;
}
Bien — un selector por valor 
function Cart() {
  // ✔ Cada valor tiene su propia suscripción granular.
  const items = useCartStore((state) => state.items);
  const removeItem = useCartStore((state) => state.removeItem);
  return <h3>{items.length}</h3>;
}

Error 2: mutar el estado directamente

Mal — mutación, sin re-render fiable 
addItem: (product) => {
  // ✘ Zustand no detecta bien las mutaciones: referencia sin cambiar.
  get().items.push({ ...product, quantity: 1 });
}
Bien — crear un array nuevo 
addItem: (product) => {
  // ✔ Un array nuevo provoca el cambio de referencia que Zustand espera.
  set({ items: [...get().items, { ...product, quantity: 1 }] });
}

Error 3: selector que devuelve un objeto o array nuevo

Este es el error más traicionero: si el selector construye cada vez un array/objeto nuevo, Zustand cree que "cambió" en cada render y provoca un bucle infinito de re-renderizados.

Mal — bucle infinito 
// ✘ Cada llamada devuelve un array NUEVO (map crea otro array).
const names = useCartStore((state) => state.items.map((i) => i.name));
// React: "cambió" → re-render → "cambió" → re-render → ...
Bien — comparación superficial con useShallow 
import { useShallow } from "zustand/react/shallow";

// ✔ useShallow compara el contenido del array, no su referencia.
const names = useCartStore(
  useShallow((state) => state.items.map((i) => i.name))
);

Error 4: crear la store dentro de un componente

Mal — store dentro del render 
function Cart() {
  // ✘ Se recrea en cada render: se pierde el estado constantemente.
  const useStore = create(() => ({ items: [] }));
  // ...
}
Bien — store en un módulo, fuera de React 
// src/store/cartStore.js
import { create } from "zustand";

// ✔ Se crea UNA sola vez, al importar el módulo.
export const useCartStore = create(() => ({ items: [] }));

7 · Ejercicio guiado

Vas a construir una store de tema (claro/oscuro) con Zustand y persistencia, y un botón que lo alterne. Es el caso de uso clásico de estado global: algo que muchos componentes leen y que queremos recordar entre visitas.

  1. Instala Zustand con pnpm add zustand (si no lo hiciste antes).
  2. Crea src/store/themeStore.js con create(). El estado tendrá theme ("light" o "dark") y una acción toggleTheme.
  3. Envuelve la store con el middleware persist y dale un name propio, por ejemplo "react19-theme-store".
  4. Crea src/components/ThemeToggle.jsx con un botón. El componente debe leer solo theme (con su selector) y la acción toggleTheme.
  5. En el botón, muestra el tema actual y cambia el texto entre "Activar claro" y "Activar oscuro".
  6. Comprueba en el navegador: al recargar la página, el tema debe mantenerse (persistencia). Abre DevTools → Application → Local Storage y busca la clave.
Ver solución paso a paso
src/store/themeStore.js
import { create } from "zustand";
import { persist } from "zustand/middleware";

export const useThemeStore = create(
  persist(
    (set) => ({
      theme: "dark", // tema por defecto

      // Cambia entre "dark" y "light"
      toggleTheme: () =>
        set((state) => ({
          theme: state.theme === "dark" ? "light" : "dark",
        })),
    }),
    { name: "react19-theme-store" } // clave en localStorage
  )
);
src/components/ThemeToggle.jsx
import { useThemeStore } from "../store/themeStore";

export default function ThemeToggle() {
  // Selector granular: solo nos interesa el tema.
  const theme = useThemeStore((state) => state.theme);
  // Y solo nos interesa la acción de alternar.
  const toggleTheme = useThemeStore((state) => state.toggleTheme);

  return (
    <button onClick={toggleTheme}>
      Tema actual: {theme} — {theme === "dark" ? "Activar claro" : "Activar oscuro"}
    </button>
  );
}
src/App.jsx
import ThemeToggle from "./components/ThemeToggle";

export default function App() {
  // Sin Provider: la store ya vive fuera de React.
  return <ThemeToggle />;
}

Qué comprobar: al recargar, el tema elegido sigue ahí porque persist lo guardó en localStorage bajo react19-theme-store. Si abres React DevTools verás que al pulsar el botón solo se re-renderiza ThemeToggle: ningún otro componente se entera.

8 · Reto

🎯 Lista de favoritos con "deshacer"

Crea una store useFavoritesStore con Zustand que gestione una lista de favoritos (por ejemplo, películas o productos) y que incluya:

  • Estado items con los favoritos y acciones add, remove y toggle.
  • Un selector derivado selectCount que devuelva cuántos hay.
  • Persistencia con persist (para que sobrevivan a un refresco).
  • Una función "deshacer" que recupere el estado anterior a la última modificación.

Pista: no necesitas middlewares exóticos para el "deshacer". Guarda dentro de la propia store una copia del array anterior (por ejemplo en lastSnapshot) antes de cada set, y crea una acción undo que restaure esa copia. Piensa con cuidado qué acciones deben guardar snapshot: normalmente add y remove, no undo.

9 · Resumen

  • Zustand es una librería de estado global minimalista: la store vive fuera del árbol de React y no necesita <Provider>.
  • create() devuelve un hook; el estado y las acciones conviven en el mismo objeto y se actualizan con set (que fusiona superficialmente).
  • Selección granular: useStore((s) => s.campo). Esto es lo que evita re-renderizados innecesarios; nunca desestructures la store entera.
  • La inmutabilidad sigue siendo tu responsabilidad: crea copias con map/filter, no mutes.
  • El middleware persist sincroniza la store con localStorage de forma automática; usa partialize para elegir qué guardar.
  • El estado derivado (totales, contadores) va en selectores, no en el estado.
  • Es ideal para apps pequeñas y medianas; Redux Toolkit sigue teniendo ventaja en apps muy grandes con equipos y flujos complejos.

10 · Preguntas frecuentes

¿Zustand reemplaza a Context API y a Redux?
No exactamente. Zustand cubre el mismo nicho (estado global compartido) con menos ceremonia, y en muchos proyectos pequeños/medianos sustituye cómodamente a ambos. Pero Context sigue siendo la opción nativa cuando no quieres dependencias (por ejemplo, para el tema o el idioma), y Redux Toolkit sigue brillando en aplicaciones grandes con lógica compleja, time-travel debugging y equipos que necesitan convenciones estrictas.
¿Necesito un Provider con Zustand?
No. La store se crea una vez en un módulo y cualquier componente puede importarla. Solo usarías un contexto de React como envoltorio si necesitas múltiples instancias aisladas de la misma store (por ejemplo, una por test o por widget embebido).
¿Por qué se me dispara un bucle infinito de re-renderizados?
Casi siempre porque tu selector devuelve un objeto o array nuevo en cada llamada (state.items.map(...), ({ a, b })). Zustand compara por referencia y cree que el valor cambió siempre. La solución es devolver valores primitivos o envolver el selector con useShallow.
¿Cómo puedo ver la store en Redux DevTools?
Usa el middleware devtools de Zustand: create(devtools((set) => ({...}))). Puedes combinarlo con persist: create(devtools(persist((set) => ({...}), { name }))). Así podrás inspeccionar cada cambio igual que con Redux.
¿Zustand funciona fuera de React?
Sí, y es una de sus ventajas. Toda store expone métodos como useCartStore.getState(), useCartStore.setState(...) y useCartStore.subscribe(...). Eso permite leer y escribir el estado desde utilidades, pruebas o código que no es un componente.
