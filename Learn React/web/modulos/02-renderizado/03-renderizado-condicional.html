Renderizado condicional

Módulo 2 · Renderizado ⏱ 30 minutos

1 · Introducción

«Muestra el spinner mientras carga», «muestra el error si falló», «muestra el botón de admin solo si eres admin», «muestra "lista vacía" si no hay datos»… La mitad de la UI de una aplicación real es condicional: aparecer o no según el estado.

En React no hay directivas v-if o *ngIf: el renderizado condicional se hace con JavaScript normal — ternarios, cortocircuitos, ifs antes del return, returns tempranos. Esta lección te da el catálogo completo de técnicas y, sobre todo, cuándo usar cada una.

2 · Teoría

La caja de herramientas completa

Hay cinco técnicas. Cada una brilla en una situación distinta:

Técnica 1 — Cortocircuito && («mostrar u ocultar»)

{error && <p className="error">{error}</p>}

Si error es falsy, JavaScript devuelve el propio valor falsy (que React no pinta); si es truthy, devuelve el elemento. Úsala para: elementos que aparecen o no (avisos, badges, secciones opcionales). Recuerda la regla de oro de la lección de expresiones: a la izquierda, un booleano (o cuidado con el 0 fantasma).

Técnica 2 — Ternario («una cosa U otra»)

{isLoggedIn ? <UserMenu /> : <LoginButton />}

Úsala para: elegir entre DOS alternativas (conectado/desconectado, cargando/datos, modo lectura/edición). Es una expresión: cabe en cualquier hueco de JSX.

Técnica 3 — If + variable antes del return («lógica que no cabe en una línea»)

function StatusBadge({ status }) {
  let badge;
  if (status === "paid") {
    badge = <span className="ok">Pagado</span>;
  } else if (status === "pending") {
    badge = <span className="warn">Pendiente</span>;
  } else {
    badge = <span className="bad">Fallido</span>;
  }
  return <div>Estado: {badge}</div>;
}

Úsala para: 3+ casos o lógica con varias líneas. Los ifs viven FUERA del JSX, produciendo elementos que luego interpolas.

Técnica 4 — Return temprano («cortar el render por completo»)

function UserProfile({ user }) {
  if (!user) {
    return <p>Cargando perfil…</p>;   // corta AQUÍ: nada más se evalúa
  }
  return <h1>{user.name}</h1>;        // solo se ejecuta si hay user
}

Úsala para: casos en los que el resto del componente no tiene sentido (datos ausentes, sin permisos). Mantiene el JSX principal limpio y plano (sin anidar todo en un ternario gigante). Y return null pinta literalmente nada.

Técnica 5 — Mapa de elementos («switch» declarativo)

const ICONS = {
  success: <CheckIcon />,
  warning: <AlertIcon />,
  error: <CrossIcon />,
};

function Toast({ type, message }) {
  return (
    <div className={`toast toast--${type}`}>
      {ICONS[type]} {message}
    </div>
  );
}

Úsala para: elegir entre variantes fijas por clave (iconos por tipo, componentes por paso de un wizard). Añadir un caso = añadir una línea al mapa.

⚠ Condicional ≠ display:none

{show && <Modal />} destruye el modal del DOM (y su estado interno) cuando show es falso. style={{display:"none"}} lo mantiene montado pero invisible (conserva su estado: scroll, texto escrito…). Elige según necesites: ¿debe conservar su estado al ocultarse? Entonces CSS. ¿Debe desaparecer del todo? Entonces condicional. En el 90 % de los casos, condicional.

3 · Ejemplo mínimo

src/components/Notification.jsx
export default function Notification({ count }) {
  return (
    <div>
      <h1>Bandeja de entrada</h1>

      {/* Cortocircuito: solo aparece si hay notificaciones */}
      {count > 0 && <span className="badge">{count} nuevas</span>}

      {/* Ternario: mensaje distinto según haya o no */}
      <p>{count > 0 ? "Tienes cosas pendientes 📬" : "Todo leído 🎉"}</p>
    </div>
  );
}

Línea por línea:

  1. count > 0 && … — condición booleana explícita: si count es 0, la condición es false y no se pinta nada (ni el temido «0»).
  2. El ternario elige el mensaje: las dos ramas producen un string, ambos válidos como expresión.

4 · Ejemplo real: los 4 estados de una pantalla de datos

Toda pantalla que carga datos tiene cuatro estados posibles: cargando, error, vacía y con datos. El patrón profesional con returns tempranos:

src/components/ProductList.jsx
export default function ProductList({ products, isLoading, error }) {
  // 1. Return temprano por CARGA: la pantalla principal no tiene sentido aún
  if (isLoading) {
    return <p className="state">⏳ Cargando productos…</p>;
  }

  // 2. Return temprano por ERROR
  if (error) {
    return <p className="state state--error">❌ Error: {error}</p>;
  }

  // 3. Return temprano por VACÍO (¡la gente lo olvida siempre!)
  if (products.length === 0) {
    return <p className="state">No hay productos que mostrar.</p>;
  }

  // 4. Camino feliz: aquí SABEMOS que hay datos
  return (
    <ul className="product-list">
      {products.map((product) => (
        <li key={product.id}>
          {product.name} — {product.price} €
        </li>
      ))}
    </ul>
  );
}

Decisiones explicadas:

  • Escalera de returns tempranos: cada caso excepcional se resuelve y «sale»; el código principal queda al final, sin anidación. Se lee de arriba abajo como una checklist.
  • El orden importa: carga → error → vacío → datos. ¿Por qué vacío antes de los datos? Porque una lista vacía no es un error: es un estado legítimo que merece mensaje propio («tu búsqueda no tuvo resultados»).
  • Alternativa que NO usamos: un ternario gigante anidado en el JSX. Ilegible. Los returns tempranos son la forma profesional.

Este patrón volverá exactamente igual en el Módulo 9 (APIs) y en el proyecto final. Apréndetelo: cargando / error / vacío / datos.

5 · Buenas prácticas

HazEvitaPor qué
Condiciones booleanas explícitas (count > 0, items.length > 0) Truthy/falsy implícitos con números El 0 fantasma: {count && …} pinta «0» cuando count es 0.
Returns tempranos para estados excepcionales Ternarios anidados de varios niveles La anidación de ternarios es el código menos legible que existe.
Nombres de variables booleanas con is/has/can (isAdmin, hasError) admin, error2, flag La condición se lee como una frase: {isAdmin && …}.
Considerar SIEMPRE el caso vacío Asumir que la lista tendrá datos Pantalla en blanco = parece rota. «Sin resultados» = información.
Extraer sub-componentes cuando una rama crece Un solo componente con 5 ramas de 40 líneas Si cada estado es grande, <LoadingState />, <EmptyState />… son componentes propios.

6 · Errores habituales

Error 1: el 0 fantasma (vuelve, y volverá)

✘ Incorrecto 
{unreadCount && <Badge>{unreadCount}</Badge>}
// unreadCount = 0 → se evalúa como 0 → React PINTA "0" en pantalla 👻
✔ Correcto 
{unreadCount > 0 && <Badge>{unreadCount}</Badge>}
// false no se pinta. Problema resuelto para siempre.

Error 2: ternarios anidados ilegibles

✘ Incorrecto 
{loading ? <Spinner /> : error ? <Error /> : empty ? <Empty /> : <List />}
// Nadie, ni tú dentro de 2 semanas, sabe qué rama es cuál
✔ Correcto 
if (loading) return <Spinner />;
if (error) return <Error />;
if (empty) return <Empty />;
return <List />;

Error 3: dos elementos «opuestos» con dos && en lugar de ternario

✘ Frágil 
{isVip && <p>Descuento VIP</p>}
{!isVip && <p>Precio normal</p>}
// Funciona… hasta que alguien cambia UNA de las dos condiciones
// y quedan desincronizadas (o ambas visibles, o ninguna)
✔ Correcto 
{isVip ? <p>Descuento VIP</p> : <p>Precio normal</p>}
// Una sola condición, dos ramas: imposible desincronizar

7 · Ejercicio guiado

Componente TicketStatus con las cuatro técnicas:

  1. Props: status ("open" | "in-progress" | "closed"), priority ("high" | "normal"), assignee (string o null).

  2. Mapa de elementos: icono por status (open: 🔵, "in-progress": 🟡, closed: 🟢).

  3. Cortocircuito: si priority es "high", muestra «🔥 Urgente».

  4. Ternario: si hay assignee, «Asignado a {assignee}»; si no, «Sin asignar».

  5. Return temprano: si status no es ninguno de los tres válidos, return null (no pintes nada).

  6. Prueba todas las combinaciones desde App (4-5 instancias del componente).

8 · Reto

🎯 El semáforo de pedidos

Construye OrderDashboard que reciba orders (array), y pinte:

  1. Si orders es null → «Cargando…» (return temprano).
  2. Si está vacío → «Aún no hay pedidos hoy» con un icono 📭.
  3. Un resumen: «X pedidos · Y pendientes · Z entregados» calculado con filter.
  4. La lista, pero: los pedidos con delayed: true llevan un borde rojo y la etiqueta «⚠ Retrasado»; los entregados se muestran con opacidad reducida y tachado.
  5. Bonus: un mapa STATUS_STYLES que centralice icono + clase por estado.

9 · Resumen

  • El renderizado condicional es JavaScript normal: no hay directivas especiales.
  • && para mostrar/ocultar; ternario para elegir entre dos; if + variable para 3+ casos; return temprano para cortar el render; mapa de elementos para variantes por clave.
  • Condiciones booleanas explícitas: nunca dejes un número a la izquierda del &&.
  • Patrón de pantallas de datos: cargando → error → vacío → datos.
  • Condicional destruye del DOM; display:none solo oculta (conserva estado). Elige con criterio.

10 · Preguntas frecuentes

¿Puedo usar switch en el renderizado?

Sí, pero FUERA del JSX (es un statement): una función renderStep() con switch que devuelve JSX, y en el marcado {renderStep()}. En la práctica, el mapa de elementos es más limpio para casos fijos.

¿Es malo tener muchos condicionales en un componente?

Es señal de que el componente tiene varias responsabilidades. Si superas 3-4 condicionales, plantéate dividir: <AdminPanel /> vs <UserPanel /> como componentes propios, y UNA condición en el padre.

¿Qué es mejor para animar apariciones: condicional o display:none?

Las animaciones de salida son difíciles con renderizado condicional (el elemento desaparece al instante). Para transiciones de entrada/salida se usan librerías (Framer Motion) o se mantiene montado con CSS. Detalle avanzado que no cambia la regla general.

¿{false && <Component />} ejecuta el componente?

No: el elemento ni siquiera se crea como tal en el VDOM (la expresión devuelve false antes de evaluar el JSX… en realidad el JSX SÍ se evalúa como creación del elemento virtual, que es baratísimo, pero React no lo monta ni ejecuta la función componente). Lo que nunca pasa es el render de Component.
