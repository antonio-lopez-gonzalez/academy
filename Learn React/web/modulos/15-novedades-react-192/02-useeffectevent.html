useEffectEvent: eventos dentro de efectos

Módulo 15 · Novedades de React 19.2 ⏱ 40 minutos

1 · Introducción

En la lección de useEffect viste el concepto de sincronización con el exterior y las dependencias. Pero hay un caso que siempre ha sido incómodo: cuando tu efecto necesita leer el valor actual de una prop o estado, pero no quiere volver a ejecutarse cuando ese valor cambia.

Imagina un chat: te conectas a una sala cuando cambia roomId. Dentro del efecto, cuando llega un mensaje, quieres mostrar una notificación con el theme actual. Si pones theme en las dependencias, el efecto se reconecta cada vez que cambias de tema (¡mal!). Si no lo pones, el efecto se queda con el theme "congelado" del momento en que se ejecutó (stale closure).

React 19.2 resuelve esto con useEffectEvent: un hook que crea funciones que siempre ven los últimos props y estado, pero que NO son dependencias del efecto. Son los "event handlers" de los efectos.

¿Qué problema resuelve? El famoso dilema de las dependencias: o reconectas de más, o lees valores obsoletos. Antes se "arreglaba" con useRef para guardar la última versión de una función; ahora React te da una primitiva clara.

2 · Teoría

La firma del hook

import { useEffectEvent } from "react";

const onEvent = useEffectEvent((arg) => {
  // Aquí puedes leer los últimos props y estado
});

useEffect(() => {
  // ... 
  onEvent(valor);   // ✅ se puede llamar desde el efecto
}, [deps]);          // onEvent NO va en las dependencias

Reglas importantes

  • Solo se puede llamar desde dentro de efectos (o de otros Effect Events). No es un manejador de eventos de usuario ni una función que pases a otros componentes.
  • NO se añade a las dependencias. El linter (eslint-plugin-react-hooks v6+) lo entiende y no te avisará.
  • Siempre ve los últimos valores de props y estado, como un handler de eventos de DOM.
  • Se declara en el mismo componente/hook que su efecto. No se puede "pasar" de un componente a otro.
EL PROBLEMA (antes de useEffectEvent) ───────────────────────────────────── theme cambia │ ▼ useEffect se ejecuta de nuevo (porque theme es dependencia) │ ▼ chat se desconecta y reconecta 💥 innecesario LA SOLUCIÓN (useEffectEvent) ──────────────────────────── const onConnected = useEffectEvent(() => { showNotification("Conectado", theme); // ✅ ve el theme actual }); useEffect(() => { connect(roomId); connection.on("connected", onConnected); // ✅ sin reconectar }, [roomId]); // ✅ solo roomId dispara el efecto

3 · Ejemplo mínimo

src/components/ChatRoom.jsx
import { useEffect, useEffectEvent, useState } from "react";

export default function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    console.log(`Conectado a ${roomId} (tema: ${theme})`);
  });

  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on("connected", onConnected);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]);   // ✅ theme NO es dependencia

  return <h1>Sala {roomId}</h1>;
}

Línea por línea:

  1. onConnected = useEffectEvent(() => ...): una función que siempre lee el theme actual.
  2. connection.on("connected", onConnected): la usamos como callback del evento externo.
  3. }, [roomId]): el efecto solo se reconecta cuando cambia la sala. Cambiar el tema ya no lo reinicia.
  4. Resultado: si el usuario cambia de tema a "claro", la próxima notificación mostrará el tema claro sin reconectar el chat.

4 · Ejemplo real

Un panel de pedidos que escucha eventos del servidor (via WebSocket) y usa el filtro activo más reciente para decidir qué notificar, sin reconectarse cuando el filtro cambia:

src/components/OrdersMonitor.jsx
import { useEffect, useEffectEvent, useState } from "react";

export default function OrdersMonitor({ userId, activeFilter, onNotify }) {
  // "Evento de efecto": usa los últimos valores sin ser dependencia
  const handleOrder = useEffectEvent((order) => {
    if (order.status === activeFilter || activeFilter === "all") {
      onNotify(`Nuevo pedido: ${order.id}`);
    }
  });

  useEffect(() => {
    const socket = new WebSocket(`wss://api.example.com/orders/${userId}`);
    socket.onmessage = (event) => {
      const order = JSON.parse(event.data);
      handleOrder(order);   // ✅ ve el activeFilter más reciente
    };
    return () => socket.close();
  }, [userId]);   // ✅ activeFilter no reconecta el socket

  return (
    <div>
      <p>Monitor de pedidos activo para el usuario {userId}</p>
      <p>Filtro actual: {activeFilter}</p>
    </div>
  );
}

Decisiones explicadas:

  • handleOrder como Effect Event: lee activeFilter y onNotify actuales sin reconectar el WebSocket.
  • Dependencia solo userId: la conexión se mantiene estable; cambiar el filtro no la interrumpe.
  • onNotify también es seguro: si el padre la cambia, no reconectamos; el Effect Event siempre llama a la última versión.

5 · Buenas prácticas

HazEvitaPor qué
Usar useEffectEvent para lógica "de evento" disparada por un efecto Envolver todo el efecto en useEffectEvent Effect Event es para callbacks invocados desde un efecto (subscripciones, timers), no para la lógica reactiva del efecto.
Dejar el Effect Event fuera de las dependencias Silenciar el linter con eslint-disable por costumbre El linter actual entiende useEffectEvent; si te avisa, revisa si el uso es correcto.
Declararlo justo antes del efecto que lo usa Crearlo dentro del propio efecto La regla de hooks exige que esté en el cuerpo del componente/hook, no anidado.
Migrar los usos de useRef como "lastestValue" Mantener refs manuales para leer valores frescos useEffectEvent expresa la intención mejor y evita el patrón de ref como "workaround".

6 · Errores habituales

Error 1: llamar a un Effect Event desde un evento de usuario

✘ Incorrecto 
const onSave = useEffectEvent(() => { /* ... */ });

return <button onClick={onSave}>Guardar</button>;   // 💥 no se llama fuera de efectos
✔ Correcto 
// Para eventos de usuario, usa una función normal:
function handleSave() { /* ... */ }
return <button onClick={handleSave}>Guardar</button>;   // ✅

Error 2: meter el Effect Event en las dependencias

✘ Incorrecto 
const onConnected = useEffectEvent(() => { /* ... */ });

useEffect(() => {
  connection.on("connected", onConnected);
  return () => connection.disconnect();
}, [roomId, onConnected]);   // 💥 onConnected NO es una dependencia
✔ Correcto 
useEffect(() => {
  connection.on("connected", onConnected);
  return () => connection.disconnect();
}, [roomId]);   // ✅ onConnected siempre es "la última versión"

Error 3: usar useEffectEvent para lógica puramente reactiva

✘ Incorrecto 
const compute = useEffectEvent(() => count * 2);   // 💥 no es un "evento"
useEffect(() => { console.log(compute()); }, []);
✔ Correcto 
// Cálculos reactivos deben ser dependencias normales o useMemo:
useEffect(() => { console.log(count * 2); }, [count]);   // ✅

7 · Ejercicio guiado

Crea un temporizador que no se reinicie al cambiar un valor:

  1. Crea un componente PomodoroTimer con un estado secondsLeft.

  2. Añade una prop label (el nombre de la tarea actual).

  3. Con setInterval en un useEffect que solo se ejecute una vez (deps vacías).

  4. En cada tick, quieres loguear `Tick de ${label} - ${secondsLeft}s`.

  5. Sin useEffectEvent, verás que label se congela (stale closure). Pruébalo.

  6. Refactoriza con useEffectEvent: un Effect Event que lea label y secondsLeft actuales, llamado desde el intervalo.

  7. Comprueba que cambiar label no reinicia el temporizador y que el log muestra el label correcto.

8 · Reto

🎯 Sincronización de documentos con efectos

Implementa un editor colaborativo mínimo:

  1. Documento: un useState con el texto del documento.
  2. Subscripción: un useEffect que se conecta una vez a un "servidor" simulado y recibe cambios remotos.
  3. Conflictos: cuando llega un cambio remoto, quieres decidir si aplicar o no según una prop readOnly y el estado actual del cursor.
  4. useEffectEvent: encapsula la lógica "cuando llega un cambio remoto" en un Effect Event que lea los valores actuales sin reconectarse.
  5. Bonus: añade un contador de palabras y demuestra que cambiar el tema de la UI no interrumpe la conexión.

9 · Resumen

  • useEffectEvent crea "eventos de efecto": funciones que siempre ven los últimos props/estado pero no son dependencias.
  • Resuelve el dilema de las dependencias: ni reconectas de más ni lees valores obsoletos.
  • Solo se llama desde efectos (o desde otros Effect Events) y no se añade a las dependencias.
  • Reemplaza al patrón de useRef para leer valores frescos dentro de efectos.

10 · Preguntas frecuentes

¿Puedo llamar a un Effect Event desde un onClick?

No. Los Effect Events solo deben llamarse desde dentro de efectos (o de otros Effect Events). Para eventos de usuario usa funciones normales. El linter te avisará si lo haces mal.

¿Y si necesito pasar la función a otro componente?

No lo hagas. Si otro componente necesita el callback, pasa una prop normal (una función que tú definas con useCallback si hace falta). Los Effect Events viven en el mismo componente que su efecto.

¿Necesito actualizar el plugin de ESLint?

Sí. eslint-plugin-react-hooks v6+ entiende useEffectEvent: no te pedirá añadirlo a las dependencias y te avisará si lo llamas en el lugar incorrecto.

¿useEffectEvent es lo mismo que useCallback?

No. useCallback devuelve una función estable pero que sigue siendo una dependencia "reactiva". useEffectEvent devuelve una función que se actualiza con los últimos valores SIN ser reactiva (no dispara el efecto al cambiar). Son primitivas con propósitos distintos.
