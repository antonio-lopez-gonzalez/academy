PPR, prerender y cacheSignal

Módulo 15 · Novedades de React 19.2 ⏱ 40 minutos

1 · Introducción

En el Módulo 13 viste los Server Components y su contexto. React 19.2 lleva la arquitectura de servidor un paso más allá con tres conceptos que se complementan:

  • Partial Pre-rendering (PPR) — mezclar HTML estático y dinámico en una sola petición.
  • prerender / resume — las APIs para generar HTML estático y luego "reanudarlo" de forma dinámica.
  • cacheSignal — saber cuándo una cache() deja de ser válida en Server Components.

¿Qué problema resuelve? Una página estática es rapidísima pero no puede mostrar datos del usuario. Una página 100% dinámica es lenta de generar. PPR permite un shell estático (header, footer, nav) servido instantáneamente desde el CDN, mientras los huecos dinámicos (carrito, nombre del usuario) se rellenan y se hacen streaming al llegar la petición.

¿Cuándo se usa? En despliegues con renderizado en servidor (SSR/SSG) cuando quieres lo mejor de ambos mundos: caché estática + contenido personalizado.

2 · Teoría

PPR: el modelo mental

PARTIAL PRE-RENDERING (PPR) ─────────────────────────── PETICIÓN DEL USUARIO │ ▼ ┌───────────────────────────────────┐ │ HTML estático (pre-renderizado) │ ◄── servido al instante desde el CDN │ - header, footer, nav │ (no depende de datos del usuario) │ - texto, layout, estilos │ └───────────────┬───────────────────┘ │ ▼ Huecos dinámicos (Suspense) ┌───────────────────────────────────┐ │ carrito, nombre, recomendaciones │ ◄── se genera y hace stream │ (dependen de cookies/datos) │ cuando llega la petición └───────────────────────────────────┘

La idea clave: las partes de la página que NO dependen de la petición se pre-renderizan a HTML estático. Las que sí dependen (Suspense) se "aplazan" y se renderizan de forma dinámica. PPR las combina en un único HTML.

prerender y resume

React 19 ya traía prerender y prerenderToNodeStream (SSG). React 19.2 añade las APIs de reanudación: 

import { prerender } from "react-dom/static";
import { resume } from "react-dom/server";

// 1. Genera el HTML estático y el estado "postponed"
const { html, postponed } = await prerender(<App />);

// 2. En tiempo de petición, reanuda el prerender para los huecos dinámicos
const { html: finalHtml } = await resume(html, postponed, <App />);
  • prerender — genera HTML completo (estático) y devuelve un estado postponed con la información de qué se aplazó.
  • resume (nuevo en 19.2) — reanuda el prerender a partir del postponed para renderizar los huecos dinámicos en streaming.

cacheSignal

En Server Components, cache() memoiza los resultados de funciones (por ejemplo, consultas a la base de datos) para una petición. cacheSignal te avisa cuándo esa caché deja de ser válida, lo que permite cancelar trabajo obsoleto (como un fetch que ya no se necesita): 

import { cache, cacheSignal } from "react";

const getOrders = cache(async (userId) => {
  // consulta a la DB...
  return orders;
});

async function OrdersSection({ userId }) {
  const signal = cacheSignal();
  const orders = await getOrders(userId);

  // Si la caché se invalida, no seguimos con trabajo obsoleto
  if (signal.aborted) return null;

  return <OrderList orders={orders} />;
}

En la práctica, cacheSignal se usa dentro de librerías y frameworks (como enrutadores) para evitar renderizar respuestas desactualizadas cuando la caché se ha invalidado mientras se resolvía una Promise.

3 · Ejemplo mínimo

server/app.server.jsx
import { prerender } from "react-dom/static";
import { resume } from "react-dom/server";

// Componentes: el shell es estático, el carrito es dinámico
function App() {
  return (
    <html>
      <head><title>Mi tienda</title></head>
      <body>
        <Header />               {/* estático: siempre igual */}
        <Suspense fallback={<CartSkeleton />}>
          <Cart />              {/* dinámico: lee cookies del usuario */}
        </Suspense>
        <Footer />               {/* estático */}
      </body>
    </html>
  );
}

// Fase de build (SSG): genera el HTML estático
const { html, postponed } = await prerender(<App />);

// Fase de petición: reanuda solo el carrito
async function handleRequest(request) {
  const { html: finalHtml } = await resume(html, postponed, <App />);
  return new Response(finalHtml);
}

Línea por línea:

  1. prerender(<App />): genera el HTML con todo lo estático y marca el Suspense del carrito como "postponed".
  2. postponed: el "estado" de lo que quedó pendiente para reanudar después.
  3. resume(html, postponed, <App />): en tiempo de petición, reanuda y renderiza el carrito dinámico, enviándolo por streaming.

4 · Ejemplo real

Un servidor de Node que sirve una página de producto con PPR: descripción estática (SEO) y precio/stock dinámicos por usuario:

server/product.server.js
import { prerender } from "react-dom/static";
import { resume } from "react-dom/server";
import { ProductPage } from "./ProductPage.jsx";

// ---- Fase de build ---------------------------------------------------
// Generamos UNA vez el HTML estático de cada producto y el estado postponed
const prerenderCache = new Map();

export async function prerenderProduct(slug) {
  if (!prerenderCache.has(slug)) {
    const { html, postponed } = await prerender(
      <ProductPage slug={slug} />
    );
    prerenderCache.set(slug, { html, postponed });
  }
  return prerenderCache.get(slug);
}

// ---- Fase de petición ------------------------------------------------
export async function renderProductPage(slug, cookies) {
  const { html, postponed } = await prerenderProduct(slug);

  // Reanudamos el prerender: solo las partes que dependen del usuario
  // (precio con descuento, stock, recomendaciones) se generan aquí.
  const { html: finalHtml } = await resume(
    html,
    postponed,
    <ProductPage slug={slug} user={cookies.user} />
  );

  return finalHtml;
}

Decisiones explicadas:

  • Prerender cacheado por slug: el HTML estático se genera una vez y se reutiliza para todos los usuarios.
  • resume en cada petición: solo se re-renderizan los huecos dinámicos (precio/stock personalizado).
  • Ventaja: la descripción, imágenes y meta (críticas para SEO) salen instantáneas del CDN; lo personal llega por streaming.

5 · Buenas prácticas

HazEvitaPor qué
Envolver en Suspense las partes dinámicas Dejar dinámico todo el árbol sin boundaries PPR necesita límites de Suspense para saber qué aplazar y qué pre-renderizar.
Usar la caché de prerender para contenido no personalizado Prerenderizar contenido que depende de cookies o sesión Eso rompe la seguridad y la personalización; lo personal debe ir en huecos dinámicos.
Comprobar signal.aborted tras esperar una cache() Renderizar con datos obsoletos tras una invalidación cacheSignal evita mostrar respuestas de una caché ya invalidada.
Actualizar a las versiones 19.2 de React y react-dom Mezclar prerender viejo con resume en versiones antiguas resume y el estado postponed son de 19.2.

6 · Errores habituales

Error 1: asumir que PPR hace todo estático

✘ Incorrecto 
// Si no hay Suspense, PPR no puede aplazar nada:
prerender(<Page con datos de cookies SIN Suspense />);
// 💥 No podrá separar estático de dinámico correctamente
✔ Correcto 
// Envuelve lo dinámico en Suspense para crear el límite:
prerender(
  <Page>
    <Suspense fallback={<Skeleton />}>
      <UserData />
    </Suspense>
  </Page>
);   // ✅

Error 2: ignorar la invalidación de cache() con cacheSignal

✘ Incorrecto 
const data = await getCachedData(userId);
// 💥 Si la caché se invalidó mientras esperábamos, usamos datos viejos
return <UserPanel data={data} />;
✔ Correcto 
const signal = cacheSignal();
const data = await getCachedData(userId);
if (signal.aborted) return null;   // ✅ descartamos datos obsoletos
return <UserPanel data={data} />;

Error 3: usar PPR en entornos sin streaming

✘ Incorrecto 
// PPR y resume dependen de streaming y de un runtime de servidor que lo soporte
const html = renderToString(<App />);   // 💥 renderToString no reanuda PPR
resume(html, postponed, <App />);
✔ Correcto 
// Usa resume (web streams) o resumeToPipeableStream (Node streams)
const { html } = await resume(html, postponed, <App />);   // ✅

8 · Reto

🎯 Tienda con PPR y cacheSignal

Implementa una tienda con renderizado híbrido:

  1. Shell estático: header con logo, menú, footer, siempre igual para todos.
  2. Huecos dinámicos: el carrito (cookies) y las recomendaciones (datos del usuario).

9 · Resumen

  • PPR combina HTML estático (instantáneo) con huecos dinámicos (streaming) en una sola petición.
  • prerender genera el HTML estático y un estado postponed.
  • resume (19.2) reanuda el prerender para los huecos dinámicos.
  • cacheSignal avisa cuando una cache() se invalida, evitando renderizar datos obsoletos.
  • El límite entre estático y dinámico lo marcan los Suspense.

10 · Preguntas frecuentes

¿PPR funciona sin un framework como Next.js?

PPR se construye sobre las APIs de React DOM server (prerender + resume), así que puedes montarlo con un servidor Node propio. Los frameworks (Next.js) lo exponen de forma más declarativa a nivel de ruta.

¿Qué diferencia hay entre SSG y PPR?

SSG genera TODO el HTML estático. PPR genera un shell estático y deja huecos que se rellenan dinámicamente por petición. PPR es "SSG con partes dinámicas" en una sola respuesta.

¿Puedo usar cacheSignal fuera de Server Components?

cache() y cacheSignal() están pensados para Server Components. En el cliente, la caché y su invalidación las gestionan librerías de fetching (React Query, SWR).

¿Resume re-renderiza todo el árbol?

No. resume retoma desde el estado postponed: solo re-renderiza los huecos que se aplazaron. El resto del HTML ya está generado y se envía tal cual.
