onChange y onSubmit

Módulo 3 · Eventos ⏱ 30 minutos

1 · Introducción

El clic es el evento de las acciones, pero los formularios tienen sus dos eventos propios: onChange (el usuario está escribiendo/eligiendo) y onSubmit (el formulario se envía). Son la puerta de entrada al Módulo 5 (formularios completos) y esconden dos sorpresas importantes:

  1. El onChange de React no es el evento change del DOM (se parece más a input): se dispara en CADA tecla.
  2. El onSubmit necesita preventDefault() o el navegador recargará la página — comportamiento heredado de 1995 que sigue activo.

Vamos a dominar ambos con sus trampas incluidas.

2 · Teoría

onChange en React ≠ change en el DOM

DOM nativoReact
¿Cuándo salta en un <input> de texto? Al PERDER EL FOCO si el valor cambió En CADA pulsación de tecla (como el evento input nativo)
¿Por qué? Diseño original de HTML React lo normaliza: quieres reaccionar al valor a medida que se escribe (búsquedas, validaciones en vivo, contadores)

Decisión de diseño deliberada de React: unificar input y change en un solo onChange que siempre significa «el valor acaba de cambiar». Para ti, desarrollador: cada vez que el usuario toca el control, tu manejador se ejecuta con el nuevo valor disponible.

Leer el valor: event.target.value

El SyntheticEvent del onChange trae en target el elemento que cambió, y cada tipo de control expone su valor de forma ligeramente distinta:

ControlQué leerTipo
<input type="text">, <textarea>e.target.valuestring
<input type="number">e.target.value (¡string! hay que convertir: Number(…))string ⚠
<input type="checkbox">e.target.checkedboolean
<input type="radio">e.target.value + e.target.checkedstring/boolean
<select>e.target.valuestring
<input type="file">e.target.filesFileList
⚠ La trampa del type="number"

e.target.value es SIEMPRE un string, incluso en inputs numéricos: "5" + "5" = "55". Convierte con Number(e.target.value) antes de calcular. Este bug ha costado horas a medio mundo.

onSubmit y el preventDefault obligatorio

Cuando envías un <form> HTML clásico, el navegador hace una petición HTTP y recarga la página (así funcionaba la web en los 90). En una SPA eso destruiría tu aplicación: hay que cancelarlo con e.preventDefault() y gestionar el envío con JavaScript. 

function handleSubmit(e) {
  e.preventDefault();   // ← SIN esto, el navegador recarga la página
  // …aquí procesas los datos (validar, enviar a la API…)
}

¿Dónde va el onSubmit? En la etiqueta <form>, no en el botón. Así el formulario se envía tanto al pulsar el botón como al pulsar Enter en un input (comportamiento nativo que el usuario espera). Poner onClick en el botón de enviar pierde el Enter.

💡 ¿Por qué React no hace preventDefault automático?

Porque onSubmit es simplemente un evento más: React no asume qué quieres hacer. Quizá tu formulario SÍ debe enviarse de forma clásica (raro en una SPA, pero posible). La filosofía de React: darte el control explícito, no decisiones ocultas.

Vista previa: por qué estos eventos necesitan estado

Ya intuyes el problema: en onChange lees el nuevo valor… ¿y dónde lo guardas? En el Módulo 4 aprenderás useState y con él los inputs controlados (el valor vive en el estado de React y el input lo refleja). Hoy practicamos la lectura del evento; en dos lecciones cerraremos el círculo.

3 · Ejemplo mínimo

src/App.jsx
export default function App() {
  function handleChange(e) {
    // Se ejecuta en CADA tecla. e.target.value = el texto actual
    console.log("Escribiendo:", e.target.value);
  }

  function handleSubmit(e) {
    e.preventDefault(); // cancela la recarga de la página
    console.log("Formulario enviado");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input type="text" onChange={handleChange} placeholder="Escribe algo…" />
      <button type="submit">Enviar</button>
    </form>
  );
}

Línea por línea:

  1. onChange={handleChange} — cada tecla ejecuta el manejador con el SyntheticEvent.
  2. e.target.value — el valor ACTUAL del input tras esa tecla (ya incluye el carácter nuevo).
  3. <form onSubmit={handleSubmit}> — el submit se escucha en el form, no en el botón: funciona con clic y con Enter.
  4. e.preventDefault() — sin esta línea, la página recargaría y perderías tu SPA.

4 · Ejemplo real

Un buscador con filtrado en vivo (muestra resultados mientras escribes, usando una lista local y lo aprendido del Módulo 2):

src/components/SearchBox.jsx
const frameworks = [
  "React", "Angular", "Vue", "Svelte", "Solid", "Qwik", "Preact",
];

export default function SearchBox() {
  // Pequeño truco didáctico: guardamos el texto en una variable de
  // módulo SOLO para este ejemplo (en el Módulo 4 será useState)
  let query = "";

  function handleChange(e) {
    query = e.target.value;
    console.log("Buscando:", query);

    // Filtramos la lista con lo escrito (expresión pura de arrays)
    const results = frameworks.filter((fw) =>
      fw.toLowerCase().includes(query.toLowerCase())
    );
    console.log("Resultados:", results);
    // En el Módulo 4, "results" será lo que se RENDERIZA en pantalla
  }

  function handleSubmit(e) {
    e.preventDefault(); // sin recarga
    alert(`Búsqueda confirmada: ${query}`);
  }

  return (
    <form onSubmit={handleSubmit} className="search-box">
      <input
        type="search"
        onChange={handleChange}
        placeholder="Buscar framework…"
        aria-label="Buscar framework"
      />
      <button type="submit">Buscar</button>
    </form>
  );
}

Decisiones explicadas:

  • Búsqueda en vivo con onChange: el filtrado ocurre en cada tecla. Con datos locales es instantáneo; con API remota añadiremos debounce y AbortController (Módulo 9).
  • type="search" y aria-label: semántica y accesibilidad reales desde ya.
  • La variable de módulo es una chapuza didáctica deliberada: funciona para loggear, pero no repinta la pantalla y se compartiría entre instancias. La lección de useState la sustituirá — y entenderás exactamente QUÉ problema resuelve.

6 · Errores habituales

Error 1: esperar el onChange al perder el foco

Síntoma: «Mi manejador se ejecuta demasiado». Es al revés: en React, onChange salta en cada tecla por diseño. Si de verdad necesitas «al terminar», usa onBlur.

Error 2: leer el valor con document.querySelector

✘ Incorrecto 
function handleSubmit(e) {
  e.preventDefault();
  const valor = document.querySelector("#email").value; // ✘ estilo vanilla
}
✔ Correcto 
// Opción 1 (hoy): leer del evento con FormData (nativo y elegante)
function handleSubmit(e) {
  e.preventDefault();
  const data = new FormData(e.target);     // e.target = el <form>
  const email = data.get("email");         // por el atributo name=""
}
// Opción 2 (Módulo 4-5): inputs controlados con useState — la forma React

Error 3: botón sin type dentro de un form

✘ Incorrecto 
<form onSubmit={handleSubmit}>
  <button onClick={borrarTodo}>Limpiar</button>
  {/* ✘ type por defecto es "submit": ¡envía el formulario! */}
</form>
✔ Correcto 
<button type="button" onClick={borrarTodo}>Limpiar</button>
<button type="submit">Enviar</button>

  2. Unifica los tres manejadores en uno solo usando el atributo name de cada input:

  3. En el submit, usa new FormData(e.target) para recuperar los tres valores por su name y muéstralos en un alert formateado.

9 · Resumen

  • onChange en React salta en CADA cambio (cada tecla), no al perder el foco.
  • El valor se lee del evento: e.target.value (texto), e.target.checked (checkbox), e.target.files (archivos). Los numéricos llegan como string: convierte.
  • onSubmit va en el <form> (funciona con Enter y con el botón) y exige e.preventDefault() para no recargar.
  • FormData permite leer todos los campos por su name sin estado (camino válido para formularios simples).
  • Estos eventos + useState (Módulo 4) = inputs controlados, la forma canónica de React.

10 · Preguntas frecuentes

¿onChange o onInput?

En React, onChange ya se comporta como el input nativo. Existe onInput por compatibilidad, pero la convención universal en React es onChange.

¿Cómo hago «buscar al dejar de escribir» (debounce)?

Con setTimeout + limpieza en un useEffect, o con un custom hook useDebouncedValue. Es un patrón del Módulo 6 (hooks) y lo aplicaremos con APIs en el Módulo 9.

¿Qué pasa si tengo 20 inputs? ¿20 onChange?

Un solo manejador genérico con e.target.name (como en el ejercicio) o inputs controlados con un objeto de estado (Módulo 5 lo enseña a fondo). Nunca 20 funciones.

¿FormData o useState para formularios?

FormData (no controlado) para formularios simples de «leer al enviar». useState (controlado) cuando necesitas el valor en vivo: validación instantánea, botones deshabilitados condicionalmente, búsquedas en vivo. El Módulo 5 compara ambos en profundidad.
