onClick y Synthetic Events

Módulo 3 · Eventos ⏱ 35 minutos

1 · Introducción

Hasta ahora nuestras interfaces eran estatuas: se veían, pero no respondían. En este módulo cobran vida. Empezamos por el evento más importante: el clic, y por entender cómo maneja React los eventos por dentro (los Synthetic Events), que es diferente del DOM clásico en varios detalles que importan.

Qué problema resuelve el sistema de eventos de React: los eventos del navegador son inconsistentes entre browsers, verbosos de registrar (addEventListener, removeEventListener, limpiezas…) y fáciles de liar con fugas de memoria. React los unifica, los optimiza y los conecta con el ciclo de renderizado: evento → cambio de estado → nueva UI. Ese ciclo es la respiración de toda app React.

Errores típicos: llamar la función en lugar de pasarla (onClick={fn()}), usar atributos HTML (onclick minúsculo), y no entender por qué un alert sí funciona pero el estado «no cambia» (eso es el Módulo 4).

2 · Teoría

Eventos en el DOM clásico vs en React

// DOM clásico (imperativo): buscas el nodo y te suscribes
const button = document.querySelector("#save");
button.addEventListener("click", handleSave);
// …y recuerda quitarlo: button.removeEventListener("click", handleSave)

// React (declarativo): el manejador vive EN la descripción de la UI
<button onClick={handleSave}>Guardar</button>

Diferencias clave:

  1. camelCase: onClick, onChange, onSubmit (en HTML serían onclick…). Es JSX: propiedades de objetos JS, no atributos HTML.
  2. Pasas la FUNCIÓN, no un string: onClick={handleSave} es una referencia a la función; en HTML clásico, onclick="handleSave()" era un string con código (malísima práctica).
  3. React gestiona el ciclo de vida: al desmontar el componente, los manejadores se limpian solos. Adiós fugas de memoria por listeners huérfanos.

La regla de oro: pasa la función, NO la llames

El error nº 1 de todo principiante:

// ✘ INCORRECTO: estás EJECUTANDO la función durante el render
<button onClick={handleSave()}>Guardar</button>
// handleSave() se ejecuta AHORA (al renderizar) y onClick recibe
// el RESULTADO (undefined). El botón no hace nada… y peor: si la
// función cambiara estado, render infinito.

// ✔ CORRECTO: pasas la función SIN llamar; React la llamará
//   CUANDO ocurra el clic
<button onClick={handleSave}>Guardar</button>
📞 Analogía del número de teléfono

onClick={handleSave} es darle tu número al botón: «cuando te pulsen, llámame». onClick={handleSave()} es hacer la llamada tú ahora y entregarle al botón la conversación terminada. El botón necesita el número (la referencia), no la llamada ya hecha (el resultado).

Synthetic Events: los eventos «envueltos» de React

Cuando tu manejador se ejecuta, NO recibe el evento nativo del navegador: recibe un SyntheticEvent, un objeto envoltorio que React crea con la misma API (target, preventDefault(), stopPropagation(), currentTarget…) pero normalizada entre navegadores. 

function handleClick(event) {
  event.preventDefault();     // igual que en el DOM clásico
  console.log(event.target);  // el elemento real que recibió el clic
  console.log(event.type);    // "click"
  // event.nativeEvent        // el evento original del navegador (rara vez lo necesitas)
}

¿Por qué existe esta capa?

  • Compatibilidad: mismos nombres y comportamiento en Chrome, Firefox, Safari… (históricamente los eventos diferían entre browsers).
  • Rendimiento: React registra los listeners en la raíz (delegación de eventos) en lugar de uno por elemento. Miles de onClick = un solo listener real.
  • Integración con el render: los eventos se procesan dentro del sistema de prioridades de React (un clic interrumpe renders no urgentes).
Nota histórica: el «event pooling» ya no existe

Antes de React 17, el SyntheticEvent se «reciclaba» y no podías usarlo de forma asíncrona sin event.persist(). Eso se eliminó: desde React 17 puedes guardar el evento y usarlo cuando quieras. Si lo lees en un tutorial viejo, ignóralo.

Burbujeo y propagación en React

Los eventos en React burbujean como los del DOM: un clic en un botón dentro de un <div onClick={…}> dispara AMBOS manejadores (primero el del botón, luego el del div). event.stopPropagation() lo detiene: 

<div onClick={() => console.log("clic en el div")}>
  <button onClick={(e) => {
    e.stopPropagation();   // el div NO se entera de este clic
    console.log("clic en el botón");
  }}>
    Solo botón
  </button>
</div>

Caso de uso real: el modal de la lección de children (clic en el overlay cierra; clic dentro del modal no). Caso de uso a evitar: stopPropagation por todas partes «por si acaso» — rompe patrones legítimos como cerrar menús al hacer clic fuera.

3 · Ejemplo mínimo

src/App.jsx
export default function App() {
  // 1. El manejador: una función normal de JavaScript
  function handleClick() {
    alert("¡Botón pulsado!");
  }

  // 2. Se la pasamos al botón SIN llamarla (sin paréntesis)
  return <button onClick={handleClick}>Púlsame</button>;
}

Línea por línea:

  1. function handleClick() — el manejador (o handler). Convención: prefijo handle + evento (handleClick, handleSubmit).
  2. onClick={handleClick} — pasamos la REFERENCIA. React la guarda y la invoca cuando llegue el clic, pasándole el SyntheticEvent.

Versión con función anónima (la más común cuando el manejador es corto):

<button onClick={() => alert("¡Pulsado!")}>Púlsame</button>

4 · Ejemplo real

Un botón de «confirmar borrado» con cuenta atrás visual… usando solo lo que sabemos (sin estado todavía — con la API de DOM del navegador como trampolín didáctico, y en la próxima lección del Módulo 4 lo haremos «the React way»):

src/components/DeleteButton.jsx
export default function DeleteButton({ itemName, onDelete }) {
  // El manejador recibe el SyntheticEvent (lo llamamos "e" o "event")
  function handleConfirm(e) {
    // ¿Quién disparó el evento? El botón (e.target)
    console.log("Clic en:", e.target.textContent);

    // confirm() es del navegador: válido para demos; en producción
    // usarías tu propio Modal (como el del Módulo 1)
    const confirmed = confirm(`¿Eliminar "${itemName}"?`);

    if (confirmed) {
      // Avisamos al PADRE mediante la prop callback.
      // El botón no sabe borrar; solo NOTIFICA. (Inversión de control)
      onDelete();
    }
  }

  return (
    <button className="btn btn--danger" onClick={handleConfirm}>
      🗑 Eliminar
    </button>
  );
}

Decisiones explicadas:

  • El componente no borra nada: recibe onDelete (una prop-función) y la llama cuando corresponde. El padre decide qué significa «borrar». Así el mismo botón sirve para borrar una foto, un usuario o un pedido.
  • La lógica de confirmación vive en el manejador, no en el JSX: los eventos son el lugar natural de la lógica imperativa (alerts, confirms, logs).
  • Convención de nombres: handle* para funciones internas, on* para las props-callback. Cuando veas onDelete como prop y handleDelete como función, siempre sabrás quién es quién.
El ciclo completo (que cerrará el Módulo 4)

Este botón ya hace la mitad del trabajo: detectar la intención del usuario. La otra mitad —que la interfaz CAMBIE como consecuencia— necesita estado: onClick → setState → re-render → nueva UI. Es literalmente la primera lección del próximo módulo.

6 · Errores habituales

Error 1: llamar la función en el render

✘ Incorrecto 
<button onClick={handleDelete()}>Borrar</button>
// Se ejecuta AL RENDERIZAR (inmediatamente), no al hacer clic.
✔ Correcto 
<button onClick={handleDelete}>Borrar</button>
// …y si necesitas pasar argumentos:
<button onClick={() => handleDelete(id)}>Borrar</button>
// (la arrow ENVUELVE la llamada: se ejecuta solo cuando hay clic)

Error 2: onclick minúsculo (o comillas)

✘ Incorrecto 
<button onclick="handleSave()">Guardar</button>   // HTML viejo, no JSX
<button onClick="handleSave">Guardar</button>      // string, no función
✔ Correcto 
<button onClick={handleSave}>Guardar</button>

Error 3: esperar que el evento «haga algo» con la UI por arte de magia

✘ No funciona como esperas 
let count = 0;   // variable normal, fuera de React

function handleClick() {
  count++;       // la variable CAMBIA…
  console.log(count); // …pero React NO se entera: no hay re-render
}
// La pantalla sigue mostrando el valor viejo.

Por qué: React solo repinta cuando cambia el ESTADO (useState) o las props. Una variable normal es invisible para él. Es LA razón de ser del Módulo 4.

7 · Ejercicio guiado

  1. Crea un componente con tres botones que muestren un alert distinto cada uno («Perfil», «Ajustes», «Salir») con manejadores con nombre propio (handleProfile…).

  2. Refactoriza a UN solo manejador con parámetro: onClick={() => handleMenu("perfil")}. Comprueba que sigue funcionando igual.

  3. Añade al manejador un console.log(e.target.textContent, e.currentTarget) (recibiendo e) y explora el SyntheticEvent en la consola.

  4. Envuelve los botones en un <div onClick={() => console.log("burbuja")}> y observa el orden de los logs al pulsar un botón. Luego añade e.stopPropagation() a UNO de los botones y compara.

  5. Provoca el error 1: escribe onClick={handleMenu("perfil")} en un botón y observa que el alert salta AL CARGAR la página, no al hacer clic. La sensación de «¡ah, claro!» es el objetivo del ejercicio.

8 · Reto

🎯 El botón tramposo

Crea un componente TrickyButton que: muestre «Púlsame si puedes»; al pasar el ratón por encima (onMouseEnter), escriba en la consola «¡Casi!»; y al hacer clic por fin, muestre un alert «Lo conseguiste tras X intentos», donde X es el número de veces que el ratón entró en el botón.

Pista: necesitas contar eventos entre renders… pero aún no sabemos estado. Hazlo con una variable let del módulo (fuera del componente) SOLO para este reto, y anota en un comentario por qué en el Módulo 4 esto se haría con useState (pista: con let de módulo, dos instancias del botón compartirían contador).

9 · Resumen

  • Eventos en React: props camelCase que reciben una FUNCIÓN (onClick={fn}), nunca un string ni una llamada.
  • Regla de oro: pasa la referencia; React la llamará cuando ocurra el evento.
  • El manejador recibe un SyntheticEvent: misma API que el nativo (target, preventDefault, stopPropagation), normalizada entre navegadores.
  • React usa delegación de eventos en la raíz: miles de handlers = un listener real.
  • Los eventos burbujean como en el DOM; stopPropagation() lo corta (úsalo con criterio).
  • Convención: handleX funciones internas, onX props-callback.
  • Un evento no cambia la UI por sí solo: necesita estado (Módulo 4).

10 · Preguntas frecuentes

¿Puedo seguir usando addEventListener en React?

Para elementos que React controla: no (usa las props on*). Para cosas fuera del árbol (eventos de window como resize, scroll, keydown global): sí, dentro de un useEffect con limpieza (Módulo 6).

¿El SyntheticEvent es más lento que el nativo?

Al contrario: la delegación de eventos reduce miles de listeners a uno. La envoltura es un objeto ligero; el coste es irrelevante en la práctica.

¿Cómo paso parámetros al manejador?

Envuelve con arrow function: onClick={() => handleDelete(id)}. O si el manejador ES la arrow, el evento sigue disponible: onClick={(e) => handleDelete(id, e)}. Toda la próxima lección (03) trata de esto.

¿Qué eventos soporta React?

Prácticamente todos los del DOM: onClick, onDoubleClick, onMouseEnter/Leave, onKeyDown/Up, onFocus/Blur, onChange, onSubmit, onScroll, onDragStart… Misma convención camelCase en todos.

¿Por qué mi botón dentro de un formulario recarga la página?

Porque un <button> dentro de <form> es type="submit" por defecto y envía el formulario (recarga). Ponle type="button" si es solo un clic, o gestiona el submit con onSubmit + preventDefault (próxima lección).
