Validación y manejo de errores

Módulo 14 · Backend con .NET 8 🕐 40 minutos

1 · Introducción

Una API se juzga por cómo se comporta cuando algo va mal. Un cliente que envía un título vacío, un identificador que ya existe, un usuario que pide un proyecto ajeno, un fallo inesperado de la base de datos… Todos esos casos necesitan una respuesta clara, consistente y segura.

Hay dos preguntas que resolver en esta lección: ¿cómo validamos lo que entra? (datos del DTO) y ¿cómo devolvemos los errores? (códigos y cuerpo de la respuesta). Nuestro objetivo: que el frontend de React reciba siempre el mismo formato de error, con 400, 401, 403, 404 o 500, y que nunca se filtre un stack trace al cliente.

¿Por qué existe esta lección? Porque sin un formato de error unificado, el frontend acaba con quince maneras distintas de leer un fallo: a veces { message }, a veces un texto plano, a veces un HTML de error. Centralizar la validación y los errores hace que el código de la API sea más pequeño y que el cliente sea trivial de escribir: lee siempre el mismo campo y muestra el mismo toast.

Errores típicos:

  • Devolver el stack trace o el mensaje de una excepción SQL al cliente.
  • Validar a mano dentro de cada controlador, con ifs repetidos y mensajes distintos.
  • Devolver un formato de error distinto en cada endpoint.
  • Usar 500 para errores del cliente (400) o 200 con { "success": false }.
  • No registrar el error en el servidor: un 500 sin traza en logs es indepurable.

2 · Teoría

Validación declarativa con DataAnnotations

En lugar de escribir if (dto.Name == "") en cada endpoint, marcamos el DTO con atributos. ASP.NET Core los evalúa automáticamente antes de que entre al controlador. Es la diferencia entre validar por convención y validar a mano en cada sitio.

AtributoCompruebaEjemplo
[Required]Que el valor no sea nulo ni vacío[Required] public string Name
[StringLength(max, MinimumLength = min)]Longitud de un texto[StringLength(120, MinimumLength = 2)]
[MinLength] / [MaxLength]Longitud mínima / máxima[MinLength(8)]
[EmailAddress]Formato de correo[EmailAddress] public string Email
[Range(a, b)]Valor numérico en un rango[Range(0, 100)]
[RegularExpression]Coincidencia con un patrón[RegularExpression("todo|done")]

Validar el formato, no el negocio. DataAnnotations brilla con reglas de forma («obligatorio», «máximo 120 caracteres», «formato de email»). Las reglas de negocio («no puedes tener dos proyectos con el mismo nombre si eres el mismo usuario») pertenecen a un servicio que consulta la base de datos, y se resuelven con Conflict, BadRequest o NotFound explícitos.

[ApiController] y la validación automática

Cuando decoras un controlador con [ApiController], ASP.NET Core activa el comportamiento de API: si el modelo no es válido, devuelve 400 Bad Request automáticamente y no entra al método. No hace falta un if (!ModelState.IsValid) en cada acción. El cuerpo del 400 es un ProblemDetails (RFC 9457) con la lista de errores por campo.

  POST /api/projects  { "name": "" }
          │
          ▼
  [ApiController]  ──►  ModelState.IsValid == false
          │                      │
          │                      └──►  400 Bad Request
          │                            (ProblemDetails con errores por campo)
          ▼ (si todo fuera válido)
     Create(CreateProjectDto dto)   ← el método NO se ejecuta si hay errores

ProblemDetails: un formato de error estándar

ProblemDetails es el formato que ASP.NET Core usa para errores. Es un JSON con campos estándar (title, status, detail) y, si hay validación, errors por campo. Usar el estándar significa que el frontend tiene siempre la misma forma que leer.

Respuesta de error estándar (ejemplo)
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Name": ["El nombre es obligatorio"]
  },
  "traceId": "00-9f3c1e…-01"
}

El traceId es oro: identifica la petición concreta en los logs del servidor. Cuando un usuario reporta un error, con ese id localizas la traza exacta.

Errores no controlados: el middleware de excepciones

Los errores «esperados» (validación, no encontrado, sin permiso) se resuelven devolviendo un código concreto. Pero una excepción inesperada (NullReferenceException, fallo de conexión…) burbujearía hasta el cliente como un 500 con la traza completa: un regalo para quien busca vulnerabilidades. La solución es un middleware que capture todo lo que no manejamos, registre el error y devuelva un 500 genérico.

   Petición
      │
      ▼
  ┌─────────────────────────────┐
  │ ExceptionHandlerMiddleware  │  try { … pipeline … }
  │                             │  catch (Exception ex)
  │                             │    · log.Error(ex)
  │                             │    · 500 + ProblemDetails SIN traza
  └─────────────────────────────┘
      │              │
      ▼              ▼
   respuesta     respuesta de error
   normal        (segura y uniforme)

En .NET 8 existe IExceptionHandler y app.UseExceptionHandler(), la forma moderna y recomendada. También vale un middleware propio como el del ejemplo real, que es más explícito didácticamente. Usa UseExceptionHandler en proyectos nuevos; entender el mecanismo con un middleware te ayuda con cualquier framework.

Logging: para el servidor, no para el cliente

La regla es simple: el cliente recibe un mensaje útil; el servidor registra el detalle técnico. Un error de validación no necesita log (es culpa del cliente). Un 500 siempre se registra con la excepción completa. Un 401/403 conviene registrarlo a nivel warning para detectar intentos de acceso indebido.

3 · Ejemplo mínimo

Lo mínimo: un DTO con una regla y la comprobación automática de [ApiController].

TaskFlow.Core/DTOs/CreateProjectDto.cs
using System.ComponentModel.DataAnnotations;

namespace TaskFlow.Core.DTOs;

public class CreateProjectDto
{
    // Obligatorio y con longitud acotada: dos reglas, cero líneas de código
    [Required(ErrorMessage = "El nombre es obligatorio")]
    [StringLength(120, MinimumLength = 2, ErrorMessage = "Entre 2 y 120 caracteres")]
    public string Name { get; set; } = string.Empty;

    [StringLength(1000, ErrorMessage = "Máximo 1000 caracteres")]
    public string Description { get; set; } = string.Empty;
}
TaskFlow.Api/Controllers/ProjectsController.cs (fragmento)
[Authorize]
[ApiController]                       // ← activa la validación automática
[Route("api/projects")]
public class ProjectsController : ControllerBase
{
    [HttpPost]
    public async Task<ActionResult<Project>> Create(CreateProjectDto dto)
    {
        // NO hace falta comprobar dto.Name: si es inválido, ASP.NET ya
        // devolvió 400 ANTES de llegar aquí. Este código solo corre con datos válidos.
        var project = new Project { Name = dto.Name, Description = dto.Description };
        _context.Projects.Add(project);
        await _context.SaveChangesAsync();
        return CreatedAtAction(nameof(GetById), new { id = project.Id }, project);
    }
}

Pruébalo enviando un nombre vacío:

Terminal
curl -s -X POST http://localhost:5000/api/projects \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":""}' -w "\nHTTP %{http_code}\n"
# -> 400 con un ProblemDetails cuyo campo "errors.Name" explica el problema
  1. [Required] hace que un null o "" invalide el modelo.
  2. [StringLength(..., MinimumLength = 2)] añade el límite inferior y superior en una sola regla.
  3. ErrorMessage: personaliza el mensaje que verá el cliente. Sin él, el mensaje por defecto es correcto pero genérico.
  4. El método nunca se ejecuta si hay errores: no hay que «defenderse» dentro del controlador.

4 · Ejemplo real

Ahora el manejo de errores de TaskFlow: un middleware que captura lo inesperado, excepciones de dominio y respuestas uniformes para el frontend.

1) Excepciones de dominio

En lugar de devolver códigos a mano por todas partes, lanzamos excepciones concretas que el middleware traduce a respuestas HTTP. Esto mantiene los controladores legibles.

TaskFlow.Core/Exceptions/AppExceptions.cs
namespace TaskFlow.Core.Exceptions;

// Excepción base de la aplicación: todo error "esperado" hereda de aquí
public abstract class AppException(string message) : Exception(message);

// 404: el recurso no existe (o el usuario no puede verlo)
public class NotFoundException(string message = "Recurso no encontrado")
    : AppException(message);

// 400: los datos son sintácticamente válidos pero violan una regla de negocio
public class ValidationException(string message) : AppException(message);

// 409: conflicto con el estado actual (email duplicado, nombre repetido…)
public class ConflictException(string message) : AppException(message);

// 403: autenticado, pero sin permiso para esta operación
public class ForbiddenException(string message = "No tienes permiso")
    : AppException(message);

2) El middleware de excepciones

TaskFlow.Api/Middleware/ErrorHandlingMiddleware.cs
using System.Net;
using Microsoft.AspNetCore.Mvc;
using TaskFlow.Core.Exceptions;

namespace TaskFlow.Api.Middleware;

// Middleware de una sola pieza: captura TODO lo que no se haya manejado
public class ErrorHandlingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ErrorHandlingMiddleware> _logger;
    private readonly IHostEnvironment _env;

    public ErrorHandlingMiddleware(RequestDelegate next, ILogger<ErrorHandlingMiddleware> logger,
                                   IHostEnvironment env)
    {
        _next = next;
        _logger = logger;
        _env = env;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);          // deja continuar el pipeline
        }
        catch (AppException ex)            // error ESPERADO: sabemos qué código devolver
        {
            var status = ex switch
            {
                NotFoundException => HttpStatusCode.NotFound,        // 404
                ValidationException => HttpStatusCode.BadRequest,    // 400
                ConflictException => HttpStatusCode.Conflict,        // 409
                ForbiddenException => HttpStatusCode.Forbidden,      // 403
                _ => HttpStatusCode.BadRequest
            };

            _logger.LogWarning("AppException {Type}: {Message}", ex.GetType().Name, ex.Message);
            await WriteProblemAsync(context, (int)status, ex.Message, detail: null);
        }
        catch (Exception ex)               // error INESPERADO: 500 y log completo
        {
            // Aquí SÍ registramos la traza entera, pero solo en los logs del servidor
            _logger.LogError(ex, "Error no controlado en {Path}", context.Request.Path);

            // El detalle solo se expone en desarrollo; en producción, mensaje genérico
            var detail = _env.IsDevelopment() ? ex.Message : null;
            await WriteProblemAsync(context, 500, "Error interno del servidor", detail);
        }
    }

    // Escribe una respuesta ProblemDetails coherente con el estándar
    private static async Task WriteProblemAsync(HttpContext context, int status,
                                                string title, string? detail)
    {
        var problem = new ProblemDetails
        {
            Status = status,
            Title = title,
            Detail = detail,
            Instance = context.Request.Path
        };

        // El traceId permite cruzar esta respuesta con la línea del log del servidor
        problem.Extensions["traceId"] = context.TraceIdentifier;

        context.Response.StatusCode = status;
        context.Response.ContentType = "application/problem+json";
        await context.Response.WriteAsJsonAsync(problem);
    }
}

Fíjate en el detalle: en el caso 500 solo devolvemos ex.Message cuando _env.IsDevelopment(). En producción, null. Ese if de una línea es la diferencia entre depurar cómodamente y filtrar la estructura interna de tu base de datos a cualquier atacante. Nunca lo quites «porque en local es útil».

3) Registro del middleware

El orden importa: debe ser lo primero tras crear la app, para envolver todo lo demás.

TaskFlow.Api/Program.cs (fragmento)
using TaskFlow.Api.Middleware;
using TaskFlow.Core.Exceptions;

var app = builder.Build();

// PRIMERO el manejo de errores: envuelve todo lo que venga después.
// Alternativa moderna en .NET 8: app.UseExceptionHandler() + IExceptionHandler.
app.UseMiddleware<ErrorHandlingMiddleware>();

app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();

4) Controladores limpios

Con el middleware en su sitio, los controladores lanzan excepciones de dominio en lugar de construir respuestas de error a mano. Mucho menos código repetido:

TaskFlow.Api/Controllers/ProjectsController.cs (fragmento)
using TaskFlow.Core.Exceptions;

[HttpPut("{id:guid}")]
public async Task<IActionResult> Update(Guid id, CreateProjectDto dto)
{
    var project = await _context.Projects.FindAsync(id);
    if (project is null) throw new NotFoundException("Proyecto no encontrado");
    if (project.OwnerId != CurrentUserId) throw new ForbiddenException();

    // Regla de negocio: un usuario no puede tener dos proyectos con el mismo nombre
    var duplicated = await _context.Projects.AnyAsync(p =>
        p.Id != id && p.OwnerId == CurrentUserId && p.Name == dto.Name);
    if (duplicated) throw new ConflictException("Ya tienes un proyecto con ese nombre");

    project.Name = dto.Name;
    project.Description = dto.Description;
    await _context.SaveChangesAsync();
    return NoContent();
}

La respuesta al cliente, sin que el controlador sepa nada de HTTP más allá de la excepción lanzada:

Respuesta 409 (ProblemDetails)
{
  "status": 409,
  "title": "Ya tienes un proyecto con ese nombre",
  "detail": null,
  "instance": "/api/projects/3f1c…",
  "traceId": "00-4b2a…-01"
}

Un solo lugar, un solo formato. El frontend ahora sabe que cualquier error llega con { status, title, detail, errors?, traceId }. En React basta un helper que lea title para el mensaje y errors para resaltar campos del formulario. Fin de los casos especiales.

5) Validación de negocio dentro del flujo

A veces la validación depende de la base de datos. La comprobación de duplicados de arriba es un ejemplo. Otra: validar que las etiquetas de una tarea están dentro de un catálogo permitido. Siempre que consultes la base de datos, hazlo con AnyAsync (barato) y lanza la excepción de dominio apropiada.

6 · Errores habituales

Devolver la traza al cliente

✗ Incorrecto
// ❌ expone la estructura interna, nombres de tablas y rutas del servidor
catch (Exception ex)
{
    return StatusCode(500, ex.ToString());   // ¡stack trace completo al cliente!
}
✓ Correcto
// ✅ log detallado en el servidor, mensaje genérico al cliente
_logger.LogError(ex, "Error no controlado en {Path}", context.Request.Path);
return StatusCode(500, new { title = "Error interno del servidor" });

Validar a mano en cada controlador

✗ Incorrecto
// ❌ Validación manual, repetida y con mensajes que divergen
if (string.IsNullOrWhiteSpace(dto.Name))
    return BadRequest("Falta el nombre");
if (dto.Name.Length > 120)
    return BadRequest("Nombre demasiado largo");
if (!Regex.IsMatch(dto.Status, "todo|in-progress|done"))
    return BadRequest("Estado inválido");
✓ Correcto
// ✅ Un atributo por regla en el DTO; ASP.NET devuelve el 400 por ti
[Required, StringLength(120, MinimumLength = 2)]
public string Name { get; set; } = string.Empty;

[RegularExpression("todo|in-progress|done")]
public string Status { get; set; } = "todo";

Usar 200 con «success: false»

✗ Incorrecto
// ❌ HTTP 200 para un fallo: proxies, cachés y clientes creen que todo fue bien
return Ok(new { success = false, message = "No encontrado" });
✓ Correcto
// ✅ El código de estado ES la señal; el cuerpo añade contexto
return NotFound(new { title = "No encontrado" });   // 404

Registrar el middleware de errores en mal orden

✗ Incorrecto
// ❌ Si el middleware de errores va DESPUÉS, no captura lo anterior
app.UseAuthorization();
app.UseMiddleware<ErrorHandlingMiddleware>();
app.MapControllers();
✓ Correcto
// ✅ Lo primero: envuelve todo el pipeline
app.UseMiddleware<ErrorHandlingMiddleware>();
app.UseAuthorization();
app.MapControllers();

8 · Reto

🎯 Migra a IExceptionHandler y estandariza los errores del frontend

Dos mejoras que acercan TaskFlow a producción:

  1. Reescribe el manejo de errores usando la API moderna de .NET 8: un IExceptionHandler registrado con builder.Services.AddExceptionHandler<ApiExceptionHandler>() y app.UseExceptionHandler(), con soporte nativo de ProblemDetails (AddProblemDetails()). El comportamiento debe ser idéntico al middleware actual.
  2. Añade en el ProblemDetails un campo code legible por máquina (por ejemplo "project_not_found", "email_already_exists") además del title humano, y escribe en el frontend un helper que traduzca ese code a un mensaje de la interfaz.

Pista: para el handler, crea una clase que implemente public async ValueTask<bool> TryHandleAsync(HttpContext httpContext, Exception exception, CancellationToken ct) y devuelva true si ha gestionado la excepción. Reutiliza la misma tabla de AppException → código HTTP. Para el campo code, usa problem.Extensions["code"] = "…". En React, un mapa { project_not_found: 'Ese proyecto ya no existe' } evita mostrar jerga técnica al usuario y centraliza los textos.

9 · Resumen

  • DataAnnotations validan la forma del DTO de forma declarativa; [ApiController] devuelve el 400 automáticamente.
  • ProblemDetails es el formato estándar de error: status, title, detail, errors y traceId.
  • Las excepciones de dominio (NotFoundException, ConflictException…) mantienen los controladores limpios.
  • Un middleware (o IExceptionHandler en .NET 8) captura lo inesperado y devuelve un 500 sin traza.
  • La regla de oro: detalle en el log del servidor, mensaje útil y genérico al cliente.
  • El traceId conecta la queja del usuario con la línea exacta del log.
  • 401 (no autenticado) y 403 (sin permiso) son distintos y el frontend reacciona distinto.

10 · Preguntas frecuentes

¿Qué es exactamente ProblemDetails y por qué debería usarlo?

Es un formato estándar (especificado en la RFC 9457) para describir errores en APIs HTTP. Define campos como type, title, status, detail e instance. Su valor está en la uniformidad: cualquier cliente —no solo el tuyo— entiende dónde mirar. ASP.NET Core lo genera de serie en la validación automática, así que adoptarlo en tu propio middleware mantiene una única forma de error en toda la API.

¿Valido con DataAnnotations o con FluentValidation?

Ambas son válidas. DataAnnotations viene integrada en ASP.NET Core, no requiere paquetes y cubre el 90 % de los casos. FluentValidation es más expresiva para reglas complejas o condicionales y separa la validación del DTO, pero añade una dependencia y un paso de registro. Para TaskFlow empezamos con DataAnnotations por simplicidad; si las reglas crecen, migrar a FluentValidation es un camino natural.

¿Cómo hago que el cliente muestre los errores por campo de un formulario?

El 400 automático incluye un objeto errors donde la clave es el nombre de la propiedad y el valor, un array de mensajes. En React, tras el fetch, lees data.errors y lo asignas al estado de errores del formulario: cada input consulta su propia clave. Como la clave es el nombre de la propiedad C# (en PascalCase), tenlo en cuenta al mapearla al campo del formulario (que suele ser camelCase).

¿Debo devolver detail en el 500 en producción?

No. El detail de un 500 suele contener el mensaje de la excepción, que puede revelar nombres de tablas, rutas del servidor o incluso fragmentos de la consulta SQL. En producción devuelve un title genérico («Error interno del servidor») y un traceId, y busca el detalle en los logs. En desarrollo, exponer el detalle acelera el trabajo: por eso el if (_env.IsDevelopment()) del ejemplo real.

¿Qué registro en los logs: todos los errores?

Con criterio. Los errores de validación (400) son culpa del cliente y no se registran. Un 404 normalmente tampoco. Los 401/403, a nivel warning, porque varios seguidos pueden indicar un intento de acceso indebido. Los 409 y 400 de reglas de negocio, a nivel information o warning. Los 500 nunca se omiten: siempre error con la excepción completa. Así los logs son útiles en lugar de ruidosos.
