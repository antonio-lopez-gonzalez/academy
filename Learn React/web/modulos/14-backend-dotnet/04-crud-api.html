CRUD completo de la API

Módulo 14 · Backend con .NET 8 🕐 60 minutos

1 · Introducción

Tenemos el modelo de datos (lección 2) y la autenticación (lección 3). Falta lo que el frontend de React va a llamar de verdad: los endpoints. CRUD son las cuatro operaciones sobre un recurso: Create (crear), Read (leer), Update (actualizar) y Delete (borrar).

En esta lección construimos los endpoints de proyectos, tareas, subtareas y comentarios de TaskFlow. Todos siguen el mismo patrón: leer del DbContext, comprobar que el usuario tiene permiso, modificar y guardar. Una vez interiorices el patrón, escribirlos es casi mecánico; el trabajo real está en respetar los permisos y devolver los códigos de estado correctos.

¿Por qué existe esta lección? Porque una API no es solo «devolver datos»: es un contrato con el frontend. Cada endpoint tiene un verbo HTTP, una ruta, un cuerpo de entrada y una respuesta con un significado. Si ese contrato es incoherente, el frontend se llena de workarounds. Aquí lo dejamos limpio y REST.

Errores típicos:

  • Devolver 200 OK para una creación (debería ser 201 Created).
  • No comprobar permisos: cualquier usuario autenticado vería los proyectos de todos.
  • Usar GET para modificar o borrar datos (rompe la semántica HTTP).
  • Devolver la entidad de EF Core con sus ciclos de navegación (JSON infinito).
  • No validar que el recurso padre existe antes de crear el hijo (tareas huérfanas).

2 · Teoría

REST: recursos, no acciones

En REST, una URL identifica un recurso (un sustantivo) y el verbo HTTP indica la operación. No hay endpoints como /crearProyecto o /borrarTarea: hay recursos (/projects, /tasks) sobre los que actúas con los verbos estándar.

VerboRutaAcciónRespuesta esperada
GET/api/projectsListar200 + array JSON
GET/api/projects/{id}Obtener uno200 o 404
POST/api/projectsCrear201 + cabecera Location
PUT/api/projects/{id}Actualizar completo200 o 204
DELETE/api/projects/{id}Borrar204 (sin cuerpo)

Códigos de estado que usaremos: 200 OK (todo bien, con cuerpo), 201 Created (se creó algo, con su ubicación), 204 No Content (todo bien, sin cuerpo — típico en borrados), 400 Bad Request (datos inválidos), 401 Unauthorized (sin token), 403 Forbidden (sin permiso), 404 Not Found (no existe).

El mapa de endpoints de TaskFlow

/api/auth
  POST   /register                 crear cuenta, devuelve token

/api/projects/{projectId}/tasks                                  [auth]
  GET    /                         tareas del proyecto
  POST   /                         crear tarea en el proyecto
  PUT    /{taskId}                 actualizar tarea
  DELETE /{taskId}                 borrar tarea

/api/tasks/{taskId}/subtasks                                     [auth]
  POST   /                         crear subtarea
  PUT    /{subtaskId}              marcar como hecha / editar

/api/tasks/{taskId}/comments                                     [auth]
  GET    /                         listar comentarios
  POST   /                         añadir comentario

Dos decisiones de diseño clave

  1. Recursos anidados. Las tareas pertenecen a un proyecto, así que su ruta lo refleja: /api/projects/{projectId}/tasks. Esto hace el contrato explícito: para crear una tarea ya sabes a qué proyecto pertenece.
  2. El identificador del usuario sale del token, nunca del cuerpo. Si el cliente pudiera enviar ownerId, cualquiera crearía proyectos a nombre de otro. El servidor lo extrae del claim sub: es el único dato en el que puede confiar.

Regla de oro de la autorización: comprueba los permisos en cada operación, no solo en el GET de la lista. Un despiste habitual es filtrar bien en GET /projects y olvidar la comprobación en PUT y DELETE. Esa omisión permite editar o borrar recursos ajenos adivinando un identificador.

DTOs de entrada vs entidades de salida

El mismo patrón que en la lección 2, ahora aplicado a la escritura. Los DTOs de entrada (CreateProjectDto) definen qué acepta el cliente; las entidades solo se persisten. Separarlos evita que un cliente envíe un Id o un OwnerId que no le corresponde.

3 · Ejemplo mínimo

El CRUD completo de un solo recurso, en su versión más corta. Fíjate en los cuatro verbos y en cómo cada uno devuelve el estado correcto.

TaskFlow.Api/Controllers/ProjectsController.cs
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using TaskFlow.Core.Entities;

namespace TaskFlow.Api.Controllers;

[Authorize]                       // todos los endpoints exigen token válido
[ApiController]
[Route("api/projects")]
public class ProjectsController : ControllerBase
{
    private readonly TaskFlowDbContext _context;
    public ProjectsController(TaskFlowDbContext context) => _context = context;

    // READ (lista)
    [HttpGet]
    public async Task<ActionResult<List<Project>>> GetAll() =>
        await _context.Projects.AsNoTracking().ToListAsync();

    // READ (uno)
    [HttpGet("{id:guid}")]
    public async Task<ActionResult<Project>> GetById(Guid id)
    {
        var project = await _context.Projects.AsNoTracking().FirstOrDefaultAsync(p => p.Id == id);
        return project is null ? NotFound() : Ok(project);
    }

    // CREATE
    [HttpPost]
    public async Task<ActionResult<Project>> Create(CreateProjectDto dto)
    {
        var project = new Project { Name = dto.Name, Description = dto.Description };
        _context.Projects.Add(project);
        await _context.SaveChangesAsync();
        // 201 + cabecera Location apuntando al recurso recién creado
        return CreatedAtAction(nameof(GetById), new { id = project.Id }, project);
    }

    // UPDATE
    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(Guid id, CreateProjectDto dto)
    {
        var project = await _context.Projects.FindAsync(id);
        if (project is null) return NotFound();

        project.Name = dto.Name;                 // EF Core detecta el cambio…
        project.Description = dto.Description;
        await _context.SaveChangesAsync();       // …y genera el UPDATE
        return NoContent();
    }

    // DELETE
    [HttpDelete("{id:guid}")]
    public async Task<IActionResult> Delete(Guid id)
    {
        var project = await _context.Projects.FindAsync(id);
        if (project is null) return NotFound();

        _context.Projects.Remove(project);
        await _context.SaveChangesAsync();
        return NoContent();                      // 204: borrado, sin cuerpo
    }
}

Línea por línea de los detalles que importan:

  1. [Route("api/projects")] y [HttpPost] se combinan: el endpoint final es POST /api/projects.
  2. {id:guid} aplica una restricción de ruta: si el segmento no es un GUID válido, ASP.NET ni siquiera entra al método; devuelve 404.
  3. CreatedAtAction construye la respuesta 201 y calcula la cabecera Location llamando al método GetById.
  4. FindAsync(id) busca por clave primaria y usa la caché del change tracker: si ya está cargado, no ejecuta SQL.
  5. SaveChangesAsync() persiste todos los cambios pendientes del contexto en una transacción.
  6. NoContent() devuelve 204, la respuesta correcta para un PUT o DELETE que no tiene nada que contar.

    [RegularExpression("todo|in-progress|done")]
    public string Status { get; set; } = "todo";

    public string Status { get; set; } = string.Empty;

[RegularExpression] como validación barata: en lugar de aceptar cualquier texto para Status, restringimos los valores válidos en el propio DTO. ASP.NET Core devolverá 400 automáticamente si llega otra cosa. En la lección 6 veremos cómo formatear esa respuesta de error.

2) Proyectos, con permisos

TaskFlow.Api/Controllers/ProjectsController.cs
using System.IdentityModel.Tokens.Jwt;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using TaskFlow.Core.DTOs;
using TaskFlow.Core.Entities;

namespace TaskFlow.Api.Controllers;

[Authorize]
[ApiController]
[Route("api/projects")]
public class ProjectsController : ControllerBase
{
    private readonly TaskFlowDbContext _context;
    public ProjectsController(TaskFlowDbContext context) => _context = context;

    // Propiedad derivada: el Id del usuario autenticado, leído del claim "sub".
    // Nunca aceptamos el userId desde el cliente: viaja dentro del token firmado.
    private Guid CurrentUserId =>
        Guid.Parse(User.FindFirst(JwtRegisteredClaimNames.Sub)!.Value);

    // GET /api/projects -> solo los proyectos donde soy dueño o miembro
    [HttpGet]
    public async Task<ActionResult<List<Project>>> GetAll()
    {
        var projects = await _context.Projects
            .AsNoTracking()
            .Where(p => p.OwnerId == CurrentUserId ||
                        p.Members.Any(m => m.UserId == CurrentUserId))
            .OrderByDescending(p => p.CreatedAt)
            .ToListAsync();

        return Ok(projects);
    }

    // GET /api/projects/{id} -> con sus tareas
    [HttpGet("{id:guid}")]
    public async Task<ActionResult<Project>> GetById(Guid id)
    {
        var project = await _context.Projects
            .AsNoTracking()
            .Include(p => p.Tasks)          // evita el problema N+1
            .FirstOrDefaultAsync(p => p.Id == id);

        // Un proyecto ajeno se trata como "no existe": no revelamos su existencia
        if (project is null || !await CanAccessAsync(project.Id)) return NotFound();

        return Ok(project);
    }

    // POST /api/projects
    [HttpPost]
    public async Task<ActionResult<Project>> Create(CreateProjectDto dto)
    {
        var project = new Project
        {
            Name = dto.Name,
            Description = dto.Description,
            OwnerId = CurrentUserId             // el dueño es siempre quien crea
        };

        _context.Projects.Add(project);
        await _context.SaveChangesAsync();

        return CreatedAtAction(nameof(GetById), new { id = project.Id }, project);
    }

    // PUT /api/projects/{id} -> solo el dueño puede editar
    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(Guid id, CreateProjectDto dto)
    {
        var project = await _context.Projects.FindAsync(id);
        if (project is null || project.OwnerId != CurrentUserId) return NotFound();

        project.Name = dto.Name;
        project.Description = dto.Description;
        await _context.SaveChangesAsync();
        return NoContent();
    }

    // DELETE /api/projects/{id} -> solo el dueño puede borrar
    [HttpDelete("{id:guid}")]
    public async Task<IActionResult> Delete(Guid id)
    {
        var project = await _context.Projects.FindAsync(id);
        if (project is null || project.OwnerId != CurrentUserId) return NotFound();

        _context.Projects.Remove(project);   // la cascada borra tareas, subtareas…
        await _context.SaveChangesAsync();
        return NoContent();
    }

    // Comprueba pertenencia: dueño o miembro del proyecto
    private Task<bool> CanAccessAsync(Guid projectId) =>
        _context.Projects.AnyAsync(p =>
            p.Id == projectId &&
            (p.OwnerId == CurrentUserId || p.Members.Any(m => m.UserId == CurrentUserId)));
}

¿404 o 403 para un recurso ajeno? Ambos son defendibles. Devolver 404 no revela que el recurso existe (buena práctica de seguridad: no filtrar información). Devolver 403 es más expresivo para el cliente («existe, pero no es tuyo»). En TaskFlow optamos por 404 para proyectos ajenos por consistencia y privacidad; documenta tu elección y sé coherente.

3) Tareas anidadas bajo su proyecto

TaskFlow.Api/Controllers/TasksController.cs
using System.IdentityModel.Tokens.Jwt;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using TaskFlow.Core.DTOs;
using TaskFlow.Core.Entities;

namespace TaskFlow.Api.Controllers;

[Authorize]
[ApiController]
[Route("api/projects/{projectId:guid}/tasks")]
public class TasksController : ControllerBase
{
    private readonly TaskFlowDbContext _context;
    private readonly IHubContext<TasksHub> _hub;   // SignalR (lección 5)

    public TasksController(TaskFlowDbContext context, IHubContext<TasksHub> hub)
    {
        _context = context;
        _hub = hub;
    }

    private Guid CurrentUserId =>
        Guid.Parse(User.FindFirst(JwtRegisteredClaimNames.Sub)!.Value);

    // GET /api/projects/{projectId}/tasks
    [HttpGet]
    public async Task<ActionResult<List<TaskItem>>> GetByProject(Guid projectId)
    {
        if (!await CanAccessProjectAsync(projectId)) return NotFound();

        var tasks = await _context.Tasks
            .AsNoTracking()
            .Where(t => t.ProjectId == projectId)
            .Include(t => t.Subtasks)
            .Include(t => t.Comments)
            .OrderBy(t => t.CreatedAt)
            .ToListAsync();

        return Ok(tasks);
    }

    // POST /api/projects/{projectId}/tasks
    [HttpPost]
    public async Task<ActionResult<TaskItem>> Create(Guid projectId, CreateTaskDto dto)
    {
        // No se puede crear una tarea en un proyecto que no es tuyo (o no existe)
        if (!await CanAccessProjectAsync(projectId)) return NotFound();

        var task = new TaskItem
        {
            ProjectId = projectId,
            Title = dto.Title,
            Description = dto.Description,
            Status = dto.Status,
            Priority = dto.Priority,
            Labels = dto.Labels,
            DueDate = dto.DueDate
        };

        _context.Tasks.Add(task);
        await _context.SaveChangesAsync();

        return CreatedAtAction(nameof(GetByProject), new { projectId }, task);
    }

    // PUT /api/projects/{projectId}/tasks/{taskId}
    [HttpPut("{taskId:guid}")]
    public async Task<IActionResult> Update(Guid projectId, Guid taskId, CreateTaskDto dto)
    {
        if (!await CanAccessProjectAsync(projectId)) return NotFound();

        var task = await _context.Tasks
            .FirstOrDefaultAsync(t => t.Id == taskId && t.ProjectId == projectId);
        if (task is null) return NotFound();

        task.Title = dto.Title;
        task.Description = dto.Description;
        task.Status = dto.Status;
        task.Priority = dto.Priority;
        task.Labels = dto.Labels;
        task.DueDate = dto.DueDate;

        await _context.SaveChangesAsync();
        return NoContent();
    }

    // DELETE /api/projects/{projectId}/tasks/{taskId}
    [HttpDelete("{taskId:guid}")]
    public async Task<IActionResult> Delete(Guid projectId, Guid taskId)
    {
        if (!await CanAccessProjectAsync(projectId)) return NotFound();

        var task = await _context.Tasks
            .FirstOrDefaultAsync(t => t.Id == taskId && t.ProjectId == projectId);
        if (task is null) return NotFound();

        _context.Tasks.Remove(task);
        await _context.SaveChangesAsync();
        return NoContent();
    }

    private Task<bool> CanAccessProjectAsync(Guid projectId) =>
        _context.Projects.AnyAsync(p =>
            p.Id == projectId &&
            (p.OwnerId == CurrentUserId || p.Members.Any(m => m.UserId == CurrentUserId)));
}

Doble comprobación en recursos anidados. Fíjate en el Update y Delete: filtramos por Id y por ProjectId. Si solo filtrásemos por taskId, cualquiera podría modificar una tarea pasando el proyecto correcto en la URL aunque la tarea viviera en otro. El filtro compuesto garantiza que el recurso y su padre coinciden con la ruta.

4) Subtareas y comentarios

TaskFlow.Api/Controllers/SubtasksController.cs
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

[Authorize]
[ApiController]
[Route("api/tasks/{taskId:guid}/subtasks")]
public class SubtasksController : ControllerBase
{
    private readonly TaskFlowDbContext _context;
    public SubtasksController(TaskFlowDbContext context) => _context = context;

    // POST /api/tasks/{taskId}/subtasks
    [HttpPost]
    public async Task<IActionResult> Create(Guid taskId, CreateSubtaskDto dto)
    {
        // Verificamos que la tarea padre existe antes de crear el hijo
        if (!await _context.Tasks.AnyAsync(t => t.Id == taskId)) return NotFound();

        var subtask = new Subtask { TaskItemId = taskId, Content = dto.Content };
        _context.Subtasks.Add(subtask);
        await _context.SaveChangesAsync();
        return CreatedAtAction(nameof(List), new { taskId }, subtask);
    }

    // GET /api/tasks/{taskId}/subtasks
    [HttpGet]
    public async Task<IActionResult> List(Guid taskId) =>
        Ok(await _context.Subtasks
            .AsNoTracking()
            .Where(s => s.TaskItemId == taskId)
            .ToListAsync());

    // PUT /api/tasks/{taskId}/subtasks/{subtaskId} -> marcar como hecha
    [HttpPut("{subtaskId:guid}")]
    public async Task<IActionResult> ToggleDone(Guid taskId, Guid subtaskId, UpdateSubtaskDto dto)
    {
        var subtask = await _context.Subtasks
            .FirstOrDefaultAsync(s => s.Id == subtaskId && s.TaskItemId == taskId);
        if (subtask is null) return NotFound();

        subtask.Content = dto.Content ?? subtask.Content;
        subtask.Done = dto.Done;
        await _context.SaveChangesAsync();
        return NoContent();
    }
}
TaskFlow.Api/Controllers/CommentsController.cs (fragmento)
// GET /api/tasks/{taskId}/comments -> comentarios con su autor
[HttpGet]
public async Task<IActionResult> List(Guid taskId) =>
    Ok(await _context.Comments
        .AsNoTracking()
        .Where(c => c.TaskItemId == taskId)
        .Select(c => new { c.Id, c.Content, c.CreatedAt, Author = c.Author.Name })
        .OrderBy(c => c.CreatedAt)
        .ToListAsync());

// POST /api/tasks/{taskId}/comments -> el autor es SIEMPRE quien envía el token
[HttpPost]
public async Task<IActionResult> Create(Guid taskId, CreateCommentDto dto)
{
    if (!await _context.Tasks.AnyAsync(t => t.Id == taskId)) return NotFound();

    var comment = new Comment
    {
        TaskItemId = taskId,
        Content = dto.Content,
        AuthorId = CurrentUserId        // del token, nunca del cuerpo
    };
    _context.Comments.Add(comment);
    await _context.SaveChangesAsync();
    return Ok(comment);
}

Select antes de materializar: en la lista de comentarios proyectamos solo los campos necesarios (Id, Content, Author.Name). EF Core traduce ese Select a un SQL que solo lee esas columnas: menos datos por la red y ningún ciclo de navegación al serializar a JSON.

5 · Buenas prácticas

HazEvitaPor qué
Delega la lógica repetida en métodos privados (CanAccessAsync) Copiar la comprobación de permisos en cada endpoint Un solo sitio donde corregir; menos probabilidad de olvidarla
CreatedAtAction para crear return Ok(entity) tras un POST El cliente recibe 201 y la URL del recurso recién creado
AsNoTracking() en lecturas Tracking en GET que no modifican nada Menos memoria y CPU; es el 80 % de las peticiones de una API
DTOs de entrada separados de las entidades Aceptar la entidad como parámetro del POST Evita mass assignment: el cliente no puede fijar Id, OwnerId…
Filtrar por Id y parentId en recursos anidados Filtrar solo por el id del hijo Impide operar sobre un recurso pasando un padre que no le corresponde
Métodos y rutas en inglés, consistentes Mezclar /getProjects con /api/tasks API predecible: el frontend adivina la ruta de un recurso nuevo

6 · Errores habituales

No comprobar permisos en la escritura

✗ Incorrecto
// ❌ Cualquier usuario autenticado puede borrar CUALQUIER proyecto
[HttpDelete("{id:guid}")]
public async Task<IActionResult> Delete(Guid id)
{
    var project = await _context.Projects.FindAsync(id);
    if (project is null) return NotFound();
    _context.Projects.Remove(project);
    await _context.SaveChangesAsync();
    return NoContent();
}
✓ Correcto
// ✅ Solo el dueño puede borrarlo
var project = await _context.Projects.FindAsync(id);
if (project is null || project.OwnerId != CurrentUserId) return NotFound();

Aceptar el OwnerId desde el cliente

✗ Incorrecto
// ❌ El cliente decide de quién es el proyecto: suplantación trivial
var project = new Project { Name = dto.Name, OwnerId = dto.OwnerId };
✓ Correcto
// ✅ El dueño sale del token firmado, nunca del cuerpo
var project = new Project { Name = dto.Name, OwnerId = CurrentUserId };

Crear hijos sin comprobar el padre

✗ Incorrecto
// ❌ Tarea huérfana: el projectId puede no existir ni ser tuyo
_context.Tasks.Add(new TaskItem { ProjectId = projectId, Title = dto.Title });
✓ Correcto
// ✅ Verifica existencia y permiso ANTES de crear el hijo
if (!await CanAccessProjectAsync(projectId)) return NotFound();

Devolver entidades con ciclos de navegación

✗ Incorrecto
// ❌ Project referencia TaskItem y cada TaskItem referencia Project:
// System.Text.Json entra en bucle -> error en tiempo de ejecución
return Ok(await _context.Tasks.Include(t => t.Project).ToListAsync());
✓ Correcto
// ✅ Proyecta a un objeto sin ciclos (o usa DTOs de salida)
.Select(t => new { t.Id, t.Title, t.Status, t.Priority })

Verificación completa: un CRUD está bien probado cuando compruebas, para cada verbo, el caso feliz y tres casos tristes: sin token (401), con token de otro usuario (404/403) y con datos inválidos (400). Si esos cuatro escenarios responden lo que esperas, el endpoint es sólido.

8 · Reto

🎯 Paginación, filtros y borrado en cascada controlado

Tres mejoras sobre el CRUD actual, pensadas para el tablero de TaskFlow:

  1. Añade paginación a GET /api/projects/{projectId}/tasks con parámetros ?page=1&pageSize=20, devolviendo en la respuesta el total de elementos y el número de páginas.
  2. Añade filtros por estado, prioridad y etiqueta a ese mismo endpoint, más una búsqueda por texto en el título.
  3. Configura el borrado en cascada a nivel de modelo (que borrar un proyecto elimine sus tareas, subtareas y comentarios) sin borrar los usuarios autores, y demuéstralo con una consulta.

Pista: para la paginación, pagina en la base de datos con .Skip((page - 1) * pageSize).Take(pageSize) y CountAsync() por separado. Para los filtros opcionales, encadena .Where(...) solo cuando el parámetro viene no vacío: if (!string.IsNullOrEmpty(status)) query = query.Where(t => t.Status == status);. Para la cascada, actívala por relación en OnModelCreating con .OnDelete(DeleteBehavior.Cascade) (los hijos) y DeleteBehavior.Restrict para el autor de un comentario, de modo que nunca se borre un usuario por borrar una tarea.

9 · Resumen

  • REST usa recursos (sustantivos) y verbos HTTP; nunca verbos en la URL.
  • Los códigos honestos son parte del contrato: 201 al crear, 204 al borrar, 404 si no existe.
  • La autorización se comprueba en cada operación, no solo al listar.
  • El id del usuario sale siempre del token (claim sub), jamás del cuerpo de la petición.
  • Los recursos anidados (/projects/{id}/tasks) reflejan la jerarquía y se filtran por Id y padre.
  • CreatedAtAction, AsNoTracking() e Include son los tres detalles que distinguen un CRUD amateur de uno profesional.

10 · Preguntas frecuentes

¿Por qué usar PATCH o PUT en lugar de un solo POST para todo?

Porque los verbos describen intención y garantías. GET es seguro (no modifica nada) y se puede cachear; PUT reemplaza un recurso completo; PATCH modifica parte; DELETE borra. Si usaras POST para todo, el frontend y los proxies no sabrían cuándo una petición es segura ni cuándo cachearla. Además, el código se vuelve autoexplicativo: ver [HttpDelete] ya te dice qué hace el método.

Un recurso que no es mío, ¿devuelve 404 o 403?

Es una decisión de diseño, no un dogma. 404 no revela que el recurso exista y es lo más común en APIs públicas. 403 es más informativo («existe, pero no es tuyo») y puede ser útil en herramientas internas. Lo importante es ser coherente en toda la API y documentarlo, para que el frontend no tenga que adivinar. En TaskFlow usamos 404 para recursos ajenos.

¿Cómo evito que un DELETE de proyecto borre también los usuarios autores de los comentarios?

Configurando el comportamiento de borrado por relación en OnModelCreating. La cascada debe propagarse a lo que depende del proyecto (tareas → subtareas → comentarios) pero no a entidades independientes como User. Para la relación Comment.Author, usa DeleteBehavior.Restrict: la base de datos impedirá borrar un usuario con comentarios, protegiéndolo. Es el tema del reto.

¿Devuelvo la entidad o un DTO de salida?

Siempre un DTO de salida (o una proyección con Select). La entidad acopla el contrato de la API al esquema de la base de datos: si añades una columna interna o dejas una navegación a otro recurso, rompes el JSON o expones datos. El DTO de salida es tu contrato público y solo cambia cuando tú quieres.

¿Debería usar un repositorio genérico en vez del DbContext directo?

Es una discusión clásica. Un IRepository<T> genérico abstrae el acceso a datos, pero DbContext ya es una unidad de trabajo y un repositorio de facto. Para muchos equipos, envolver EF Core en un repositorio genérico añade capa sin aportar nada. En TaskFlow usamos el DbContext directamente en los controladores por claridad didáctica, y dejamos los repositorios específicos (como ProjectRepository de la lección 2) para lógica de consulta reutilizable. Si el proyecto crece y quieres testear controladores sin base de datos, la abstracción pasa a tener sentido.
