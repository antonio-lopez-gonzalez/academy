Docker: PostgreSQL y stack completo

Módulo 14 · Backend con .NET 8 🕐 45 minutos

1 · Introducción

Hasta ahora, para trabajar en TaskFlow hacían falta tres cosas instaladas a mano: la SDK de .NET 8, un PostgreSQL corriendo y, si querías probar el frontend, pnpm con Node. Cada persona del equipo tiene otra versión, otra configuración, otro «a mí me funciona». Ese es, literalmente, el problema que resuelve Docker: empaquetar cada pieza con todo lo que necesita y arrancar el sistema completo con un solo comando.

En esta lección contenerizamos el backend y orquestamos el stack completo (PostgreSQL + API + frontend) con Docker Compose. Al terminar, un compañero nuevo podrá clonar el repositorio, ejecutar docker compose up y tener TaskFlow funcionando sin instalar .NET, PostgreSQL ni Node.

¿Por qué existe esta lección? Porque el entorno de desarrollo que no se puede reproducir es deuda técnica desde el día uno. Docker convierte «instálate el PostgreSQL 16, crea el usuario y ejecuta las migraciones» en «descarga el repo y arranca». Es además la misma imagen que desplegarás en producción (lección 8): lo que pruebas en tu portátil es lo que corre en el servidor.

Errores típicos:

  • Usar localhost dentro de un contenedor para referirse a otro servicio: cada contenedor tiene su propio localhost.
  • Guardar los datos de PostgreSQL dentro del contenedor, sin volumen: se borran al recrearlo.
  • Arrancar la API antes de que PostgreSQL esté listo (la conexión falla y el contenedor muere).
  • Construir la imagen copiando bin/ y obj/ de la máquina anfitriona.
  • Usar docker-compose (v1, obsoleto) en lugar de docker compose (v2, integrado).

2 · Teoría

Imagen vs contenedor vs Compose

TérminoQué esEn TaskFlow
ImagenPlantilla inmutable construida a partir de un Dockerfiletaskflow-api:latest
ContenedorUna ejecución concreta de una imagenEl proceso de la API corriendo
VolumenAlmacenamiento que sobrevive al contenedorLos datos de PostgreSQL
RedCanal por el que se hablan los contenedores por nombreapi llama a postgres:5432
Docker ComposeDefine y arranca varios contenedores como un conjuntoPostgreSQL + API + frontend

Analogía: una imagen es la receta; un contenedor es el plato cocinado; un volumen es la despensa que sigue ahí aunque tires el plato. Y Docker Compose es el menú del restaurante: describe qué platos se sirven juntos, en qué orden y cómo se comunican. Tú abres el menú («menú del día») y el restaurante sirve todo coordinado.

El stack completo de TaskFlow

   navegador (http://localhost:3000)

   ┌─────────────────────────┐        red interna de Compose
   │ frontend (nginx)        │  ──►  /api  … reenvía a la API
   │ puerto 3000 -> 80       │

   │ api (.NET 8)            │  ────► │ postgres (PostgreSQL 16)│
   │ puerto 8080             │        │ puerto 5432 (interno)   │
   │ Host=postgres           │        │ volumen: pgdata         │
   └─────────────────────────┘        └─────────────────────────┘

Dos reglas que resuelven el 90 % de las confusiones con Docker:

  1. Dentro de la red de Compose, cada servicio se llama por su nombre. La API no conecta a localhost:5432, conecta a postgres:5432. El servicio se llama postgres en el compose.yaml, así que ese es su hostname.
  2. Los puertos publicados son para el anfitrión. ports: "8080:8080" expone el 8080 del contenedor al 8080 de tu máquina. Entre contenedores no hacen falta ports: se ven por la red interna.

¿Por qué un Dockerfile multi-stage?

El SDK de .NET pesa más de 800 MB; el runtime, unos 200 MB. Si usáramos el SDK como imagen final, cada despliegue arrastraría compiladores y herramientas que no se usan en ejecución. Un Dockerfile multi-stage separa dos fases: build (con SDK, compila y publica) y runtime (con solo el runtime, ejecuta). La imagen final es mucho más pequeña y más segura (menos superficie de ataque).

   Etapa BUILD (imagen SDK, grande)          Etapa RUNTIME (imagen aspnet, pequeña)
   ┌───────────────────────────────┐         ┌───────────────────────────────┐
   │ mcr.microsoft.com/dotnet/    │  COPY   │ mcr.microsoft.com/dotnet/    │
   │ sdk:8.0                       │ ──────► │ aspnet:8.0                    │
   │ restore · build · publish     │  /app/  │ solo los binarios publicados  │
   └───────────────────────────────┘ publish └───────────────────────────────┘
   (se descarta al terminar)                   (esta es la imagen final)

Arranque ordenado: depends_on y healthcheck

depends_on solo garantiza el orden de arranque, no que el servicio esté listo. PostgreSQL tarda uno o dos segundos en aceptar conexiones; si la API arranca antes, falla. La solución es un healthcheck sobre PostgreSQL y depends_on: condition: service_healthy: Compose espera a que la base de datos responda antes de levantar la API.

   docker compose up
      │
      ▼
   arranca postgres ──► healthcheck (pg_isready) ──► healthy
                                                        │
                                                        ▼
                                              arranca api (ya puede conectar)
                                                        │
                                                        ▼
                                              arranca frontend

3 · Ejemplo mínimo

Antes del stack completo, lo más pequeño: un compose.yaml que levanta solo PostgreSQL con un volumen. Es exactamente el contenedor que usábamos a mano en la lección 2, ahora declarado en un archivo.

compose.yaml (mínimo)
# Compose v2 lee 'compose.yaml' en la raíz del proyecto por convención
services:
  postgres:
    image: postgres:16-alpine        # imagen oficial, variante ligera
    environment:
      POSTGRES_DB: taskflow
      POSTGRES_USER: taskflow
      POSTGRES_PASSWORD: taskflow-dev   # solo desarrollo
    ports:
      - "5432:5432"                  # anfitrión:contenedor
    volumes:
      - pgdata:/var/lib/postgresql/data  # los datos sobreviven al contenedor

# Los volúmenes con nombre se declaran aparte
volumes:
  pgdata:
Terminal
# Arranca en segundo plano
docker compose up -d

# Comprueba estado y logs
docker compose ps
docker compose logs -f postgres

# Detiene (el volumen pgdata SE CONSERVA)
docker compose down

Línea por línea:

  1. services: cada clave hija es un contenedor. El nombre (postgres) es también su hostname en la red interna.
  2. image: usamos una imagen ya construida. Variante alpine por tamaño.
  3. environment: variables que la imagen oficial de PostgreSQL lee al inicializarse: crea la base taskflow y su usuario.
  4. ports: "5432:5432" publica el puerto para poder conectarte con psql desde tu máquina. Podrías quitarlo y seguiría funcionando entre contenedores.
  5. volumes: los datos van a pgdata; el contenedor puede recrearse sin perder nada.

4 · Ejemplo real

Ahora el stack completo de TaskFlow. Empezamos por el Dockerfile multi-stage del backend.

proyecto-final/backend/Dockerfile
# ============ Etapa 1: BUILD (imagen con SDK) ============
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# Copiamos primero SOLO los .csproj y restauramos.
# Así, mientras no cambien las dependencias, Docker reutiliza la capa de restore
# aunque el código cambie: builds mucho más rápidos.
COPY TaskFlow.Api/TaskFlow.Api.csproj TaskFlow.Api/
COPY TaskFlow.Core/TaskFlow.Core.csproj TaskFlow.Core/
COPY TaskFlow.Infrastructure/TaskFlow.Infrastructure.csproj TaskFlow.Infrastructure/
RUN dotnet restore TaskFlow.Api/TaskFlow.Api.csproj

# Ahora copiamos el resto del código y publicamos en Release
COPY . .
RUN dotnet publish TaskFlow.Api/TaskFlow.Api.csproj -c Release -o /app/publish /p:UseAppHost=false

# ============ Etapa 2: RUNTIME (imagen sin SDK) ============
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app

# Puerto en el que escuchará Kestrel dentro del contenedor
ENV ASPNETCORE_URLS=http://+:8080
EXPOSE 8080

# Copiamos SOLO los binarios publicados desde la etapa de build
COPY --from=build /app/publish .

# Usuario no root (la imagen aspnet:8.0 trae el usuario 'app')
USER app

# ENTRYPOINT en forma exec (array): el proceso recibe las señales correctamente
ENTRYPOINT ["dotnet", "TaskFlow.Api.dll"]

Configuración en contenedor: dentro del contenedor, UseHttpsRedirection() provocará redirecciones al puerto HTTPS que no publicamos. En el Program.cs, envuelve esa línea en if (!app.Environment.IsDevelopment() && !app.Environment.IsEnvironment("Docker")) o simplemente ponla condicional cuando exista ASPNETCORE_URLS con http. En el ejemplo del stack verás cómo lo resolvemos con ASPNETCORE_ENVIRONMENT: Docker.

El compose.yaml completo

proyecto-final/compose.yaml
# Levanta el stack completo de TaskFlow: base de datos + API + frontend
services:

  # ------------------------------------------------ PostgreSQL
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: taskflow
      POSTGRES_USER: taskflow
      POSTGRES_PASSWORD: taskflow-dev
      # Crea la base con esta codificación desde el primer arranque
      POSTGRES_INITDB_ARGS: "--encoding=UTF8"
    volumes:
      - pgdata:/var/lib/postgresql/data
    # El healthcheck permite que la API espere a que la BD esté LISTA
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U taskflow -d taskflow"]
      interval: 5s
      timeout: 3s
      retries: 10
    # No publicamos el 5432: nadie fuera del stack necesita conectarse

  # ------------------------------------------------ API .NET 8
  api:
    build:
      context: ./backend          # carpeta donde está el Dockerfile
      dockerfile: Dockerfile
    environment:
      ASPNETCORE_ENVIRONMENT: Docker
      # Doble guion bajo = nivel de configuración. Apunta a 'postgres', no a localhost
      ConnectionStrings__Default: "Host=postgres;Port=5432;Database=taskflow;Username=taskflow;Password=taskflow-dev"
      Jwt__Key: "clave-de-desarrollo-32-caracteres-minimo-cambiame"
      Jwt__Issuer: "TaskFlow"
      Jwt__Audience: "TaskFlow"
    ports:
      - "8080:8080"              # para probar Swagger desde el anfitrión
    depends_on:
      postgres:
        condition: service_healthy  # espera a que la BD responda
    restart: unless-stopped

  # ------------------------------------------------ Frontend (nginx)
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    ports:
      - "3000:80"                # TaskFlow en http://localhost:3000
    depends_on:
      - api
    restart: unless-stopped

volumes:
  pgdata:                        # persiste entre 'down' y 'up'

Jwt__Key en el compose es solo para desarrollo. En producción (lección 8) nunca escribimos la clave en un archivo versionado: se inyecta como secret o variable de entorno del proveedor. Aquí la dejamos fija para que el stack arranque «de fábrica» en un portátil.

Aplicar migraciones al arrancar

El contenedor no tiene la CLI de EF Core (solo el runtime). Dos opciones: ejecutar las migraciones con dotnet ef desde un contenedor con SDK, o aplicarlas automáticamente al arrancar la API en un entorno de desarrollo. Esta última es la más cómoda:

TaskFlow.Api/Program.cs (fragmento)
var app = builder.Build();

// En desarrollo/Docker aplicamos migraciones AL ARRANCAR para que el stack
// funcione con un solo 'docker compose up'. En producción NO se hace así:
// las migraciones se aplican como paso controlado del despliegue (lección 8).
if (app.Environment.IsDevelopment() || app.Environment.IsEnvironment("Docker"))
{
    using var scope = app.Services.CreateScope();
    var db = scope.ServiceProvider.GetRequiredService<TaskFlowDbContext>();
    await db.Database.MigrateAsync();   // aplica las migraciones pendientes
}

app.UseMiddleware<ErrorHandlingMiddleware>();
app.UseAuthentication();
app.UseAuthorization();
app.MapHub<TasksHub>("/hubs/tasks");
app.MapControllers();
app.Run();

El frontend también va en un contenedor

El frontend de TaskFlow es una SPA de Vite: se compila a estáticos y se sirven con nginx. El Dockerfile también es multi-stage.

proyecto-final/frontend/Dockerfile
# ============ Etapa 1: BUILD con pnpm ============
FROM node:22-alpine AS build
WORKDIR /app

# corepack activa la versión de pnpm fijada por el proyecto
RUN corepack enable
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

COPY . .
RUN pnpm build            # genera /app/dist con HTML, CSS y JS optimizados

# ============ Etapa 2: nginx sirve los estáticos ============
FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
proyecto-final/frontend/nginx.conf
server {
    listen 80;

    # Sirve la SPA: cualquier ruta cae en index.html (React Router)
    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
    }

    # Proxy de la API y del hub de SignalR hacia el servicio 'api' de Compose
    location /api/ {
        proxy_pass http://api:8080/api/;
    }
    location /hubs/ {
        proxy_pass http://api:8080/hubs/;
        # Cabeceras necesarias para el upgrade a WebSocket
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}

Por qué el proxy importa: con esta configuración el frontend llama a /api/… y /hubs/… en su mismo origen. No hay CORS y el WebSocket de SignalR funciona atravesando nginx. Es la forma más limpia de servir una SPA con API en producción.

6 · Errores habituales

Conectar a localhost desde el contenedor

✗ Incorrecto
# ❌ Dentro del contenedor, 'localhost' es el PROPIO contenedor, no PostgreSQL
environment:
  ConnectionStrings__Default: "Host=localhost;Port=5432;Database=taskflow;Username=taskflow;Password=taskflow-dev"
✓ Correcto
# ✅ El hostname es el nombre del servicio en Compose
environment:
  ConnectionStrings__Default: "Host=postgres;Port=5432;Database=taskflow;Username=taskflow;Password=taskflow-dev"

Arrancar la API antes que PostgreSQL

✗ Incorrecto
# ❌ depends_on no espera a que la BD esté LISTA: la API puede morir al conectar
depends_on:
  - postgres
✓ Correcto
# ✅ Espera a 'service_healthy' (requiere healthcheck en postgres)
depends_on:
  postgres:
    condition: service_healthy

Sin volumen: la base de datos se borra

✗ Incorrecto
# ❌ Al recrear el contenedor, PostgreSQL se inicializa de cero
services:
  postgres:
    image: postgres:16-alpine
    # sin 'volumes'
✓ Correcto
# ✅ Los datos viven en un volumen que sobrevive
services:
  postgres:
    image: postgres:16-alpine
    volumes:
      - pgdata:/var/lib/postgresql/data

Usar la v1 de Compose

✗ Incorrecto
# ❌ Comando v1 (obsoleto), con guion y sin espacio
docker-compose up
✓ Correcto
# ✅ Compose v2, integrado en el CLI de Docker
docker compose up

7 · Ejercicio guiado

Objetivo: levantar PostgreSQL y la API a partir del stack, comprobar que la API esperó a la base de datos y que los datos persisten entre reinicios.

  1. Paso 1 — escribe el Dockerfile del backend. Copia el multi-stage del ejemplo real y añade el .dockerignore. Comprueba que useHttpsRedirection no rompe el contenedor (usa ASPNETCORE_ENVIRONMENT: Docker).
  2. Paso 2 — escribe el compose.yaml con postgres (con healthcheck y volumen) y api (con depends_on: service_healthy y las variables ConnectionStrings__Default y Jwt__*).
  3. Paso 3 — arranca y observa el orden. 
    docker compose up --build
# Observa los logs: postgres primero, 'database system is ready to accept
# connections', y SOLO ENTONCES arranca la API. Luego, las migraciones.
  4. Paso 4 — siembra un dato y reinicia. Crea un proyecto por la API y luego reinicia el stack. El proyecto debe seguir ahí porque vive en el volumen. 
    # Registro + creación rápida (con jq para extraer el token)
TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"name":"Demo","email":"demo@taskflow.dev","password":"demo1234"}' | jq -r .token)
curl -s -X POST http://localhost:8080/api/projects -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"name":"Persistente"}'

docker compose restart api
curl -s http://localhost:8080/api/projects -H "Authorization: Bearer $TOKEN"
# -> el proyecto sigue listado: el volumen pgdata hizo su trabajo
  5. Paso 5 — verificación final. Ejecuta docker compose ps y confirma que los tres servicios están Up (y postgres como healthy). Si usaste los tres servicios, abre http://localhost:3000 y comprueba que el frontend responde y habla con la API a través del proxy.

Si algo falla: docker compose logs api para la API, docker compose logs postgres para la base de datos. El 90 % de los errores son la cadena de conexión (localhost en vez de postgres) o intentar conectar antes de que la BD esté lista.

8 · Reto

🎯 Imagen de producción optimizada y secretos fuera del compose

Tres mejoras para llevar el stack más cerca de producción:

  1. Añade un healthcheck a la API usando el endpoint /api/health que creamos en la lección 1, y haz que el frontend dependa de api con condition: service_healthy.
  2. Elimina la Jwt__Key del compose.yaml y sácala a un archivo .env (que no se versiona) usando ${JWT_KEY} en el compose. Documenta en un .env.example qué variables hacen falta.
  3. Reduce aún más la imagen final: usa el chiseled mcr.microsoft.com/dotnet/aspnet:8.0-jammy-chiseled como etapa de runtime y comprueba que el tamaño baja. Investiga por qué ese tag no incluye shell.

Pista: para el healthcheck de la API, test: ["CMD", "curl", "-f", "http://localhost:8080/api/health"] — ojo, la imagen de runtime puede no tener curl; usa la variante que sí lo incluye o un pequeño healthcheck con wget. Para los secretos, docker compose lee automáticamente un archivo .env de la carpeta del compose y expone las variables con ${NOMBRE}. Añade .env al .gitignore. Para el chiseled, el tamaño de la imagen y la ausencia de shell son consecuencias de su filosofía minimalista: no puedes hacer docker exec sh y tampoco lo necesitas en producción.

9 · Resumen

  • Docker empaqueta cada pieza con sus dependencias; Compose arranca el conjunto.
  • Dentro de la red de Compose, los servicios se llaman por su nombre (postgres), no por localhost.
  • Multi-stage separa el build (SDK) del runtime (aspnet): imagen final mucho más pequeña.
  • Copiar primero los .csproj y restaurar aprovecha la caché de capas.
  • Los datos van a un volumen; los contenedores son efímeros.
  • healthcheck + depends_on: condition: service_healthy garantizan el orden real de arranque.
  • El proxy inverso (nginx) sirve la SPA y enruta /api y /hubs, evitando CORS y habilitando WebSockets.

10 · Preguntas frecuentes

¿Por qué el build es lentísimo la primera vez y rápido después?

Docker construye por capas y las cachea. La primera vez descarga las imágenes base y restaura todos los paquetes NuGet: puede tardar minutos. En los siguientes builds, si solo has cambiado código C#, Docker reutiliza la capa de dotnet restore (porque los .csproj no cambiaron) y solo recompila. Ese es el motivo de copiar los .csproj antes que el código: maximiza el reaprovechamiento de la caché.

¿Puedo usar la base de datos del contenedor con pgAdmin o psql desde mi máquina?

Sí, si publicas el puerto. En el stack no lo publicamos (la API la ve por la red interna), pero puedes añadir temporalmente ports: ["5432:5432"] al servicio postgres y conectar con psql o pgAdmin usando localhost:5432, usuario taskflow y la contraseña de desarrollo. Recuerda retirar ese ports si no lo necesitas: cada puerto publicado es una superficie más expuesta.

¿Aplico las migraciones al arrancar el contenedor?

Solo en desarrollo, y lo hacemos para que docker compose up deje todo listo en un paso. En producción es mala idea: si se despliegan dos réplicas a la vez, ambas intentarían migrar en paralelo y podrían colisionar; y un cambio de esquema debería ser un paso explícito y verificable, no un efecto colateral del arranque. En la lección 8 lo tratamos como una etapa controlada del despliegue.

¿Cómo veo qué está pasando si la API no conecta con PostgreSQL?

Con docker compose logs api. El error típico es Npgsql.NpgsqlException: Connection refused, que casi siempre significa una de dos cosas: la cadena usa localhost en lugar de postgres, o la API arrancó antes que la base de datos (falta el condition: service_healthy). Otra comprobación útil: docker compose exec postgres psql -U taskflow -d taskflow -c "\dt" para ver si las tablas existen.

¿Docker es también lo que usaré en producción?

Sí: la misma imagen que construyes con docker build es la que publicas en un registro (Docker Hub, GHCR) y la que despliegas en el servidor. Esa continuidad —«lo que probé es lo que despliego»— es la mayor ventaja de Docker. En la lección 8 veremos dónde ejecutar esa imagen (App Service, Railway, VPS…) y cómo configurar los secretos por variables de entorno en cada plataforma.
