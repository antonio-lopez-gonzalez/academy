Despliegue del backend

Módulo 14 · Backend con .NET 8 🕐 40 minutos

1 · Introducción

Tenemos la API completa: capas, base de datos, autenticación, CRUD, tiempo real, manejo de errores y un stack de Docker que arranca en tu portátil. Falta el último paso: que funcione en internet, accesible desde el frontend desplegado y con datos reales.

Desplegar un backend no es «subir el binario». Hay que decidir dónde corre, cómo llegan las credenciales (cadena de conexión, clave JWT), cómo se aplican las migraciones, quién puede llamar a la API (CORS), y cómo saber que está viva cuando algo falle a las 3 de la mañana. Esta lección es la lista de comprobaciones para no olvidar nada.

¿Por qué existe esta lección? Porque el 80 % de los incidentes de un primer despliegue son siempre los mismos: secretos mal inyectados, migraciones no aplicadas, CORS bloqueando al frontend o HTTP en lugar de HTTPS. Conocerlos de antemano convierte un fin de semana de sudor en una tarde tranquila.

Errores típicos:

  • Subir appsettings.Production.json con secretos reales al repositorio.
  • No aplicar las migraciones y descubrir que «todos los endpoints dan 500».
  • Configurar CORS con AllowAnyOrigin() «para que funcione».
  • Servir la API por HTTP y dejar los tokens de acceso viajando en claro.
  • No tener endpoint de salud ni logs: el servidor cae y nadie se entera.

2 · Teoría

¿Dónde desplegar una API .NET con PostgreSQL?

PlataformaCómo funcionaVentaja / inconveniente
Azure App Service PaaS con runtime .NET integrado; subes código o una imagen Integración nativa, escalado y certificados gestionados; algo más caro
Railway / Render / Fly.io Despliegue desde Dockerfile + PostgreSQL gestionado Muy simples y con planes gratuitos; menos control fino
VPS + Docker Un servidor propio con docker compose y un proxy inverso Control total y barato; tú te encargas de TLS, backups y monitorización
Kubernetes Clúster con Deployment, Service e Ingress Escalado y resiliencia de nivel enterprise; complejidad alta

Recomendación del curso: para TaskFlow, Railway o Render es el mejor punto de partida: conectas el repositorio, detecta el Dockerfile, te da un PostgreSQL gestionado y un dominio con TLS automático. El VPS es el siguiente paso cuando quieras aprender la parte de operación.

La configuración es jerárquica

ASP.NET Core construye la configuración por capas: cada fuente puede sobrescribir la anterior. Entender el orden evita sorpresas.

   appsettings.json                 ← valores comunes, sin secretos (versionado)
        │ (se puede sobrescribir por)
        ▼
   appsettings.{Environment}.json   ← por entorno (Development / Production)
        │
        ▼
   user-secrets (solo Development)  ← secretos locales fuera del repo
        │
        ▼
   variables de entorno             ← ★ lo que se usa en producción
        │
        ▼
   argumentos de línea de comandos  ← máxima prioridad

Por eso en el compose.yaml usábamos ConnectionStrings__Default y Jwt__Key: el doble guion bajo representa la jerarquía de : en el JSON. En la plataforma de despliegue, defines esas mismas variables y la app las lee sin cambiar una línea de código.

CORS: por qué tu frontend recibe un error «de red»

Cuando el frontend en https://taskflow.app llama a la API en https://api.taskflow.app, son orígenes distintos. El navegador, por seguridad, bloquea la respuesta a menos que la API lo permita explícitamente con cabeceras CORS. Y no basta con permitir el origen: en peticiones con Authorization hay un preflight (OPTIONS) que también debe autorizarse.

   navegador (origen A)                 API (origen B)
        │                                    │
        │  OPTIONS /api/projects             │  preflight
        │  Origin: https://taskflow.app      │
        ├───────────────────────────────────►│
        │◄───────────────────────────────────┤
        │  204 + Access-Control-Allow-Origin: https://taskflow.app
        │      + Access-Control-Allow-Headers: Authorization, Content-Type
        │
        │  GET /api/projects  (+ Authorization)
        ├───────────────────────────────────►│
        │◄───────────────────────────────────┤  200 con la misma cabecera

Nunca AllowAnyOrigin() en producción. Permitir cualquier origen deja que cualquier web llame a tu API en nombre del usuario. Configura una lista blanca con el dominio exacto del frontend. Si el frontend y la API se sirven en el mismo dominio (como en el stack con nginx de la lección 7), ni siquiera necesitas CORS.

Migraciones: un paso del despliegue, no del arranque

En Docker (desarrollo) migrábamos al arrancar para tener un one-command setup. En producción eso es peligroso: con varias réplicas arrancando a la vez, todas intentarían migrar en paralelo. La práctica correcta es aplicar las migraciones como un paso explícito y único antes de arrancar la nueva versión:

   Deploy del backend
      │
      ├─ 1. build de la imagen (con el SDK)
      ├─ 2. publicar la imagen en un registro
      ├─ 3. ⚙ aplicar migraciones (UN solo proceso, con EF tools o un bundle)
      ├─ 4. arrancar la nueva versión de la API
      └─ 5. comprobar /api/health  ──► si falla, rollback

EF Core permite generar un bundle de migraciones: un ejecutable autónomo que no necesita el SDK ni el código fuente.

Terminal — generar un bundle de migraciones
# Genera un binario que aplica las migraciones por sí solo
dotnet ef migrations bundle \
  --project TaskFlow.Infrastructure \
  --startup-project TaskFlow.Api \
  -o ./efbundle

# En el servidor de producción: una sola ejecución, con la cadena de conexión real
./efbundle --connection "Host=db;Database=taskflow;Username=…;Password=…"

Observabilidad: saber que está viva y por qué falla

Un despliegue sin observabilidad es una caja negra. Lo mínimo para no ir a ciegas:

  • Endpoint de salud (/api/health): la plataforma (o tú) lo consulta para saber si la app responde; también sirve para el balanceador.
  • Logs estructurados: ASP.NET Core escribe logs en JSON si lo configuras; la plataforma los recoge y permite buscarlos.
  • traceId: ya lo devolvemos en cada error (lección 6); con él, un reporte de usuario se cruza con la línea exacta del log.
  • Alertas: aviso cuando aumenta la tasa de 500 o cuando el healthcheck falla.

Trazas y errores de extremo a extremo: el Módulo de New Relic del Academy profundiza en observabilidad. Aquí nos quedamos con lo esencial: health + logs + traceId.

3 · Ejemplo mínimo

El despliegue más pequeño posible: publicar la API y ejecutarla fuera del entorno de desarrollo, leyendo la configuración de variables de entorno.

Terminal
# 1) Publica en Release: genera los binarios optimizados en ./publish
dotnet publish TaskFlow.Api -c Release -o ./publish

# 2) Hora de ejecutarla "como en producción": sin appsettings.Development
#    y con las credenciales por variables de entorno.
cd publish
ASPNETCORE_ENVIRONMENT=Production \
ASPNETCORE_URLS=http://localhost:8080 \
ConnectionStrings__Default="Host=localhost;Port=5432;Database=taskflow;Username=taskflow;Password=taskflow-dev" \
Jwt__Key="clave-de-al-menos-32-caracteres-aleatorios-aqui" \
Jwt__Issuer="TaskFlow" \
Jwt__Audience="TaskFlow" \
dotnet TaskFlow.Api.dll

Línea por línea:

  1. dotnet publish -c Release compila con optimizaciones y copia los binarios (más las dependencias) a ./publish. Es lo que va al servidor.
  2. ASPNETCORE_ENVIRONMENT=Production desactiva Swagger y los detalles de error; activa la configuración de producción.
  3. ASPNETCORE_URLS define en qué dirección escucha Kestrel. En la plataforma, esto lo controla el proveedor.
  4. ConnectionStrings__Default y Jwt__Key sobrescriben el appsettings.json: el doble guion bajo es la jerarquía.
  5. dotnet TaskFlow.Api.dll arranca el proceso. Sin SDK, solo el runtime.

Las variables con _ no funcionan. Debe ser doble guion bajo: Jwt__Key. Un solo Jwt_Key es una clave distinta y la app no la encontrará. Es el error de despliegue más común y el más difícil de ver (la app arranca, pero la configuración llega vacía).

4 · Ejemplo real

Un despliegue completo, paso a paso, en el estilo que vale para cualquier plataforma basada en Docker.

1) Prepara la app para producción

Tres ajustes en el arranque: CORS con lista blanca, HTTPS solo fuera de contenedor y sin migraciones automáticas.

TaskFlow.Api/Program.cs (fragmento)
// CORS con lista blanca: el dominio real del frontend, leído de configuración.
// En producción NO se usa AllowAnyOrigin().
var allowedOrigins = builder.Configuration
    .GetSection("Cors:AllowedOrigins").Get<string[]>() ?? Array.Empty<string>();

builder.Services.AddCors(options =>
    options.AddPolicy("TaskFlowFrontend", policy =>
        policy.WithOrigins(allowedOrigins)          // dominios exactos
              .AllowAnyHeader()                     // incluye Authorization
              .AllowAnyMethod()));

var app = builder.Build();

// Migraciones SOLO en desarrollo/Docker. En producción, paso explícito del deploy.
if (app.Environment.IsDevelopment() || app.Environment.IsEnvironment("Docker"))
{
    using var scope = app.Services.CreateScope();
    var db = scope.ServiceProvider.GetRequiredService<TaskFlowDbContext>();
    await db.Database.MigrateAsync();
}

app.UseMiddleware<ErrorHandlingMiddleware>();

// HTTPS: en la plataforma hay TLS en el borde; forzar la redirección aquí
// puede crear bucles si no se configuran las cabeceras de proxy. Lo activamos
// solo cuando no corremos en Docker (donde el TLS lo gestiona el borde).
if (!app.Environment.IsEnvironment("Docker"))
    app.UseHttpsRedirection();

app.UseCors("TaskFlowFrontend");   // ANTES de autenticación y de mapControllers
app.UseAuthentication();
app.UseAuthorization();
app.MapHub<TasksHub>("/hubs/tasks");
app.MapControllers();
app.Run();

Orden de CORS: UseCors debe ir antes de UseAuthentication y de MapControllers. Si lo pones después, el preflight OPTIONS no recibirá las cabeceras y el navegador bloqueará la petición real con un error genérico de red.

2) El endpoint de salud, listo para el balanceador

TaskFlow.Api/Controllers/HealthController.cs (fragmento)
[ApiController]
[Route("api/[controller]")]
public class HealthController : ControllerBase
{

    [HttpGet]

3) Configuración de producción sin secretos

TaskFlow.Api/appsettings.Production.json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",
      "Microsoft.EntityFrameworkCore.Database.Command": "Warning"
    }
  },
  "Cors": {
    "AllowedOrigins": [ "https://taskflow.app" ]
  }
}

Los secretos no aparecen aquí: llegan por variables de entorno del proveedor.

Variables de entorno en producción
# Nunca en un archivo versionado. Se definen en el panel del proveedor
# o se inyectan como secretos del orquestador.
ASPNETCORE_ENVIRONMENT=Production

# Cadena de conexión del PostgreSQL gestionado (host interno del proveedor)
ConnectionStrings__Default=Host=db.xxxx;Port=5432;Database=taskflow;Username=taskflow;Password=REEMPLAZAR

# Clave JWT fuerte, única por entorno, de ≥32 caracteres aleatorios
Jwt__Key=REEMPLAZAR-por-una-clave-aleatoria-de-32-o-mas-caracteres
Jwt__Issuer=TaskFlow
Jwt__Audience=TaskFlow

Genera la clave, no la inventes. Una frase como mi-clave-secreta-2026 es adivinable. Usa un generador aleatorio, por ejemplo openssl rand -base64 48. La clave va por entorno y nunca se comparte entre desarrollo, staging y producción: si se filtra una, el daño queda contenido.

4) Publica la imagen en un registro y despliega

Terminal — construir y publicar la imagen
# Etiqueta la imagen con el registro, el nombre y una versión inmutable.
# NUNCA despliegues con :latest en producción: no sabes qué hay dentro.
docker build -t ghcr.io/tu-usuario/taskflow-api:1.0.0 ./proyecto-final/backend

# Autenticarse en el registro (GitHub Container Registry en este ejemplo)
echo "$GITHUB_TOKEN" | docker login ghcr.io -u tu-usuario --password-stdin

# Subir la imagen
docker push ghcr.io/tu-usuario/taskflow-api:1.0.0

El proveedor construye desde esa imagen y, antes de arrancar la nueva versión, aplica las migraciones con el bundle. Si el despliegue es por Git (Railway/Render detectan el Dockerfile), ese paso se configura como release command: ./efbundle --connection "$ConnectionStrings__Default".

5) Un pipeline de despliegue, en YAML

La automatización mínima en GitHub Actions: pruebas, migraciones y despliegue como pasos ordenados.

.github/workflows/deploy.yml
name: Deploy TaskFlow API

on:
  push:
    branches: [ main ]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 1) Compilar y ejecutar los tests de la solución
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      - run: dotnet build TaskFlow.sln -c Release
      - run: dotnet test  TaskFlow.sln -c Release --no-build

      # 2) Aplicar migraciones contra la BD de producción (paso ÚNICO y explícito)
      - name: Apply migrations
        run: dotnet ef database update --project TaskFlow.Infrastructure --startup-project TaskFlow.Api
        env:
          ConnectionStrings__Default: ${{ secrets.CONNECTION_STRING }}

      # 3) Construir, publicar y desplegar la imagen
      - name: Build image
        run: docker build -t ${{ secrets.REGISTRY }}/taskflow-api:${{ github.sha }} ./proyecto-final/backend
      - name: Push image
        run: docker push ${{ secrets.REGISTRY }}/taskflow-api:${{ github.sha }}
      - name: Deploy
        run: echo "Aquí tu paso específico de despliegue (CLI del proveedor, kubectl apply…)"

Etiqueta con el SHA del commit. ${{ github.sha }} da una versión única y trazable: sabes exactamente qué código corre y puedes volver a una versión anterior con un clic. Los secretos (secrets.CONNECTION_STRING) viven en GitHub, no en el repositorio.

6) Smoke test tras el despliegue

Terminal
BASE="https://api.taskflow.app"

# 1) ¿Está viva?
curl -s -o /dev/null -w "health  %{http_code}\n" "$BASE/api/health"        # 200

# 2) ¿Registra y autentica?
curl -s "$BASE/api/auth/login" -H "Content-Type: application/json" \
  -d '{"email":"demo@taskflow.dev","password":"demo1234"}' \
  -w "\nlogin   %{http_code}\n"                                            # 200

# 3) ¿Protege lo que debe?
curl -s -o /dev/null -w "sin-auth %{http_code}\n" "$BASE/api/projects"     # 401

# 4) ¿Devuelve errores seguros? (a un recurso inexistente)
curl -s "$BASE/api/projects/00000000-0000-0000-0000-000000000000" \
  -H "Authorization: Bearer $TOKEN" | head -c 200                          # sin traza

Secretos en el repositorio

✗ Incorrecto
// appsettings.Production.json versionado en Git
{
  "ConnectionStrings": { "Default": "Host=db.prod;Username=admin;Password=Prod2026!" },
  "Jwt": { "Key": "clave-real-de-produccion" }
}
✓ Correcto

✗ Incorrecto
// ❌ "para que funcione" -> cualquier origen puede llamar a la API

// ✅ Solo el dominio del frontend
policy.WithOrigins("https://taskflow.app").AllowAnyHeader().AllowAnyMethod();

Migrar en el arranque de producción

✗ Incorrecto
// ❌ Dos réplicas arrancan a la vez y migran en paralelo: carrera garantizada

# ✅ Paso único y explícito antes de arrancar la nueva versión

7 · Ejercicio guiado

Objetivo: preparar la configuración de producción, simularla en local y ejecutar un smoke test como el que correrías tras desplegar.

  1. Paso 1 — crea appsettings.Production.json sin secretos, con el nivel de log adecuado y el array de CORS.
    TaskFlow.Api/appsettings.Production.json
    {
  "Logging": { "LogLevel": { "Default": "Information", "Microsoft.AspNetCore": "Warning" } },
  "Cors": { "AllowedOrigins": [ "https://taskflow.app" ] }
}
  2. Paso 2 — genera una clave JWT fuerte. 
    openssl rand -base64 48
# Copia el resultado: esa es tu Jwt__Key de producción (32+ caracteres aleatorios)
  3. Paso 3 — publica y arranca en modo producción localmente, con todas las credenciales por variables de entorno. 
    dotnet publish TaskFlow.Api -c Release -o ./publish
cd publish
ASPNETCORE_ENVIRONMENT=Production \
ASPNETCORE_URLS=http://localhost:8080 \
ConnectionStrings__Default="Host=localhost;Port=5432;Database=taskflow;Username=taskflow;Password=taskflow-dev" \
Jwt__Key="la-clave-que-generaste-en-el-paso-2" \
Jwt__Issuer=TaskFlow Jwt__Audience=TaskFlow \
dotnet TaskFlow.Api.dll

    Comprueba que Swagger no está disponible (http://localhost:8080/swagger devuelve 404): en Production no lo exponemos.

  4. Paso 4 — aplica las migraciones como paso separado. Detén la app, aplica el bundle y vuelve a arrancar. 
    dotnet ef migrations bundle --project TaskFlow.Infrastructure --startup-project TaskFlow.Api -o ./efbundle
./efbundle --connection "Host=localhost;Port=5432;Database=taskflow;Username=taskflow;Password=taskflow-dev"
  5. Paso 5 — smoke test. Ejecuta las cuatro comprobaciones del ejemplo real y anota los códigos esperados: health 200, login 200, sin token 401 y el error sin traza. Si los cuatro son correctos, la API está lista para producción.

Truco de verificación: revisa que en la salida de la app en Production no aparece la cadena de conexión ni la clave JWT en los logs. Si las ves, es que las estás registrando en algún sitio: corrígelo antes de desplegar.

8 · Reto

🎯 Despliegue real con HTTPS, monitorización y rollback

Lleva TaskFlow a internet de verdad y prepáralo para operar:

  1. Despliega la API y PostgreSQL en una plataforma real (Railway, Render o un VPS con docker compose + Caddy/nginx para TLS). Consigue un dominio con HTTPS y configura Cors:AllowedOrigins con el dominio del frontend desplegado.
  2. Añade logs estructurados (JSON) y una alerta que dispare si /api/health deja de responder o si la tasa de 500 sube por encima de un umbral.
  3. Documenta y ejecuta un rollback: despliega v1, luego v2, y vuelve a v1 apuntando a la etiqueta anterior de la imagen. Mide cuánto tardas.

Pista: para los logs JSON, configura el console logger con AddJsonConsole(). Para la alerta, la mayoría de PaaS ofrecen «uptime checks» y notificaciones por email/Slack sin escribir código. Para el rollback, la clave es que cada versión esté etiquetada de forma inmutable (SHA o semver) y que las migraciones sean compatibles hacia atrás: si v2 añadió una columna, v1 debe seguir funcionando con ella; por eso conviene desplegar primero el código tolerante y después el cambio de esquema.

9 · Resumen

  • La configuración de ASP.NET Core es jerárquica: las variables de entorno (doble guion bajo) sobrescriben los archivos JSON.
  • Los secretos viven en el proveedor, nunca en el repositorio ni en appsettings.json.
  • CORS se configura con lista blanca; AllowAnyOrigin() solo vale para desarrollo.
  • Las migraciones son un paso único y explícito del despliegue (efbundle), no un efecto del arranque.
  • La imagen se etiqueta con una versión inmutable (SHA o semver) para saber qué corre y poder volver atrás.
  • Sin healthcheck, logs y alertas el despliegue es una caja negra.
  • Un smoke test tras desplegar confirma que la app responde de verdad.

10 · Preguntas frecuentes

¿Puedo desplegar el backend y el frontend en dominios distintos?

Sí, y es lo más común (por ejemplo, frontend en Vercel y API en Railway). Requiere configurar CORS en la API con el dominio exacto del frontend y usar HTTPS en ambos. La alternativa —servir ambos desde el mismo dominio con un proxy inverso como en el stack de Docker— evita CORS por completo y suele ser más simple de operar para un proyecto propio.

¿Por qué la app funciona en local pero da 500 en producción por la base de datos?

Casi siempre por una de estas tres: (1) la cadena de conexión no llegó (nombre de variable mal escrito, guion simple en vez de doble); (2) el proveedor gestionado exige SSL Mode=Require en la cadena, que en local no hacías falta; (3) las migraciones no se aplicaron, así que las tablas no existen. Revisa los logs de la API: el mensaje de Npgsql te dirá exactamente cuál de las tres es.

¿Cómo hago rollback si un despliegue sale mal?

Vuelve a apuntar el proveedor a la etiqueta de imagen anterior (por eso nunca desplegamos :latest). En plataformas con «releases», casi todas tienen un botón de rollback que reapunta a la revisión previa. La parte delicada es el esquema: si la versión nueva ya cambió la base de datos, la anterior debe seguir siendo capaz de leerla. Estrategia segura: desplegar primero cambios compatibles hacia atrás (columnas opcionales, sin borrar nada) y retirar lo viejo en un despliegue posterior.

¿Necesito un servidor propio o basta un PaaS?

Para TaskFlow, un PaaS (Railway, Render, Fly.io, Azure App Service) es más que suficiente y te ahorra gestionar TLS, backups y sistema operativo. Un VPS propio tiene sentido cuando quieres control total, aprender la parte de operación, o reducir costes con cargas altas y predecibles. Como el despliegue es por Docker, la imagen es la misma en ambos mundos: puedes empezar en PaaS y mudarte a un VPS sin tocar la aplicación.

¿Dónde guardo la clave JWT y cómo la roto?

En el gestor de secretos del proveedor (variables de entorno cifradas, Key Vault, Secrets Manager) y nunca en el repositorio. Para rotarla: genera una nueva clave, despliégala y, si quieres una transición suave, acepta temporalmente la clave anterior además de la nueva en la validación de firmas. Al retirar la antigua, todos los tokens firmados con ella dejarán de ser válidos y los usuarios tendrán que volver a iniciar sesión: es el objetivo de una rotación de seguridad.
