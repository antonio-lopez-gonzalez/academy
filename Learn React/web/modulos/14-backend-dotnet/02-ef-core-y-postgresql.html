EF Core y PostgreSQL

Módulo 14 · Backend con .NET 8 🕐 55 minutos

1 · Introducción

Ya tenemos la solución con capas (lección anterior). Ahora hay que guardar datos de verdad. TaskFlow necesita usuarios, proyectos, tareas, subtareas, comentarios y etiquetas; todo eso vive en PostgreSQL, un motor relacional gratuito, robusto y el favorito de la comunidad .NET moderna.

Podríamos escribir SQL a mano, pero en C# usamos un ORM: Entity Framework Core (EF Core). Es el Object-Relational Mapper oficial de .NET: traduce clases C# a tablas, objetos a filas y LINQ a SQL. Y lo más importante: el esquema no se edita a mano, se describe en C# y se aplica con migraciones versionadas.

Esta lección responde a: ¿cómo represento el modelo de TaskFlow en C# y lo llevo a PostgreSQL sin perder el control?

¿Por qué existe esta lección? Porque el 100 % de los datos de una aplicación relacional viven detrás de este paso. Si entiendes las entidades, el DbContext y las migraciones, el CRUD de la lección 4 será mecánico. Si no, cada consulta se convertirá en un misterio de NullReferenceException y consultas N+1.

Errores típicos:

  • Editar la base de datos a mano y que la migración no refleje el estado real.
  • Olvidar las relaciones y cargar listas vacías sin darse cuenta (problema N+1).
  • Guardar contraseñas en claro porque «el hash es para después».
  • Usar DateTime.Now en lugar de DateTime.UtcNow: fechas incoherentes entre servidores.
  • Mezclar entidades de dominio con DTOs en el mismo tipo.

2 · Teoría

¿Qué es exactamente EF Core?

EF Core es una biblioteca que se sitúa entre tu C# y la base de datos. Tú trabajas con objetos y consultas LINQ; él genera el SQL, abre la conexión, lee las filas y las convierte en objetos. La diferencia clave con escribir SQL a mano es que el compilador te ayuda: si escribes context.Tasks.Where(t => t.Title) y Title no existe, no compila.

Analogía: EF Core es un traductor profesional. Tú hablas C#/LINQ; PostgreSQL habla SQL. En lugar de aprender SQL perfecto y escribirlo a mano cada vez, le dices al traductor lo que quieres y él lo redacta. Como todo traductor, a veces necesita que le des contexto: de ahí métodos como Include, que le indican «trae también los datos relacionados».

Code-first: el esquema vive en C#

Hay dos filosofías. Database-first: diseñas la base de datos y generas el C#. Code-first: diseñas las clases y generas la base de datos. Elegimos code-first porque el código es la fuente de verdad, está en Git y las migraciones aplican los cambios de forma reproducible en cualquier entorno (tu portátil, CI, producción, Docker).

   C# (Entities + DbContext)
            │  dotnet ef migrations add
            ▼
   Migración (código C# con Up/Down)
            │  dotnet ef database update
            ▼
   PostgreSQL  ──  tablas, índices, claves
            ▲
            │  dotnet ef migrations add (nuevo cambio)
            └── se repite: el esquema evoluciona SIN tocarlo a mano

Tracking: por qué AsNoTracking importa

El DbContext es un cambiador de cambios (change tracker): cuando lees entidades, las guarda en memoria y lleva un registro de lo que modificas para generar el UPDATE correcto en SaveChangesAsync(). Eso es cómodo para escribir, pero en consultas de solo lectura es coste puro: copia objetos y compara estados sin necesidad. La regla práctica:

  • Vas a modificar las entidades → deja el tracking por defecto (usa FindAsync, Single…).
  • Solo vas a leer y devolver datos → añade .AsNoTracking().

Rendimiento: en APIs que devuelven colecciones grandes, AsNoTracking() reduce memoria y tiempo de CPU de forma notable. En la lección 4 lo aplicaremos en cada endpoint de lectura.

El problema N+1, en un vistazo

❌ Sin Include (N+1 consultas: 1 por proyecto + 1 por cada lista)
   SELECT * FROM Projects;                 -- 1 consulta
   SELECT * FROM Tasks WHERE ProjectId=…; -- 1 por proyecto  ← ¡lentísimo!

✅ Con Include (1 sola consulta con JOIN)
   SELECT p.*, t.*
   FROM Projects p LEFT JOIN Tasks t ON t.ProjectId = p.Id;

PostgreSQL y Npgsql

EF Core no sabe hablar con cada motor por sí solo: usa un proveedor. Para PostgreSQL el oficial es Npgsql.EntityFrameworkCore.PostgreSQL. Empieza con UseNpgsql(…) y a partir de ahí todo es EF Core estándar. Antes de continuar, levanta PostgreSQL. La forma sencilla (sin instalar nada) es Docker:

Terminal
# Un contenedor PostgreSQL 16 para el desarrollo; el volumen conserva los datos
docker run --name taskflow-db \
  -e POSTGRES_DB=taskflow \
  -e POSTGRES_USER=taskflow \
  -e POSTGRES_PASSWORD=taskflow-dev \
  -p 5432:5432 \
  -v taskflow_pgdata:/var/lib/postgresql/data \
  -d postgres:16-alpine

Y la migración inicial, que crea la tabla en PostgreSQL:

Terminal
# --project: dónde vive el DbContext. --startup-project: de dónde lee la config.
dotnet ef migrations add InitialCreate \
  --project TaskFlow.Infrastructure \
  --startup-project TaskFlow.Api

dotnet ef database update \
  --project TaskFlow.Infrastructure \
  --startup-project TaskFlow.Api

Línea por línea de la migración:

  1. migrations add InitialCreate: EF Core compara tus entidades con las migraciones existentes y genera un fichero C# con los cambios (aquí, CREATE TABLE "Projects"). No toca la base de datos.
  2. database update: aplica todas las migraciones pendientes. La tabla __EFMigrationsHistory registra cuáles se han ejecutado.
  3. --startup-project: necesario porque la configuración (la cadena de conexión) se lee desde el proyecto que arranca, no desde la biblioteca.

Comprueba el resultado con docker exec -it taskflow-db psql -U taskflow -d taskflow -c "\dt": verás la tabla Projects y __EFMigrationsHistory.

El DbContext completo, con las reglas que no se deducen por convención:

TaskFlow.Infrastructure/Data/TaskFlowDbContext.cs
using Microsoft.EntityFrameworkCore;
using TaskFlow.Core.Entities;

namespace TaskFlow.Infrastructure.Data;

public class TaskFlowDbContext : DbContext
{
    public TaskFlowDbContext(DbContextOptions<TaskFlowDbContext> options)
        : base(options) { }

    public DbSet<User> Users => Set<User>();
    public DbSet<Project> Projects => Set<Project>();
    public DbSet<TaskItem> Tasks => Set<TaskItem>();
    public DbSet<Subtask> Subtasks => Set<Subtask>();
    public DbSet<Comment> Comments => Set<Comment>();

    // Fluent API: aquí van las reglas que no se pueden expresar con atributos
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // El email es único: dos usuarios no pueden registrarse con el mismo
        modelBuilder.Entity<User>()
            .HasIndex(u => u.Email)
            .IsUnique();

        // Clave compuesta para la tabla de unión (UserId + ProjectId)
        modelBuilder.Entity<ProjectMember>()
            .HasKey(pm => new { pm.UserId, pm.ProjectId });

        // Una lista de strings no es una columna relacional: la guardamos
        // como texto separado por comas y la reconstruimos al leer.
        modelBuilder.Entity<TaskItem>()
            .Property(t => t.Labels)
            .HasConversion(
                v => string.Join(",", v),                              // al guardar
                v => v.Split(",", StringSplitOptions.RemoveEmptyEntries).ToList() // al leer
            );
    }
}

¿Por qué HasConversion y no una tabla Label? Para un proyecto didáctico, guardar las etiquetas como texto es simple y suficiente. Si necesitases consultas por etiqueta, filtros por nombre o estadísticas, lo correcto sería una tabla Labels con relación N:M. La conversión es una decisión de diseño con un coste: no puedes indexar ni hacer WHERE label = 'urgent' de forma eficiente.

Ejecutar consultas con LINQ

TaskFlow.Infrastructure/Repositories/ProjectRepository.cs
using Microsoft.EntityFrameworkCore;
using TaskFlow.Core.Entities;
using TaskFlow.Infrastructure.Data;

namespace TaskFlow.Infrastructure.Repositories;

public class ProjectRepository
{
    private readonly TaskFlowDbContext _context;

    public ProjectRepository(TaskFlowDbContext context) => _context = context;

    // Solo lectura -> AsNoTracking (más rápido, no llena el change tracker)
    public Task<List<Project>> GetAllAsync() =>
        _context.Projects
            .AsNoTracking()
            .OrderByDescending(p => p.CreatedAt)
            .ToListAsync();

    // Lectura con datos relacionados -> Include evita el problema N+1
    public Task<Project?> GetWithTasksAsync(Guid id) =>
        _context.Projects
            .AsNoTracking()
            .Include(p => p.Tasks)
            .FirstOrDefaultAsync(p => p.Id == id);
}

Los métodos ...Async devuelven Task<…> porque la consulta se ejecuta en la base de datos y no bloquea el hilo del servidor. Es la versión .NET del await fetch(...) que ya usas en React: esperas sin congelar nada.

5 · Buenas prácticas

HazEvitaPor qué
Cambios de esquema siempre por migración Editar tablas con psql o pgAdmin La migración es el historial reproducible; sin ella, tu portátil y producción divergen
DateTime.UtcNow y columnas UTC DateTime.Now El servidor puede vivir en otra zona horaria; UTC es el único instante sin ambigüedad
.AsNoTracking() en lecturas Tracking en endpoints que solo devuelven datos Menos memoria y CPU; el cambio es gratis
Include solo de lo necesario Cargar toda la jerarquía «por si acaso» Cada Include es un JOIN; traer datos que no usas cuesta ancho de banda y memoria
Índices en columnas de búsqueda (Email, ProjectId) Consultas filtrando columnas sin índice Un índice convierte un escaneo completo en una búsqueda directa
Usuario de base de datos con permisos mínimos Conectar como superusuario postgres Limita el daño si las credenciales se filtran o hay un bug de seguridad

Ojo con Guid como clave y HasData: los datos sembrados deben tener IDs fijos, no Guid.NewGuid(). Si el ID cambia en cada generación de migración, la migración no es determinista y el database update fallará o duplicará filas.

6 · Errores habituales

Editar la base de datos a mano

✗ Incorrecto
-- ❌ Añades una columna directamente en PostgreSQL
ALTER TABLE "Projects" ADD COLUMN "Archived" boolean NOT NULL DEFAULT false;
-- Tu base de datos local ya la tiene, pero la de tu compañero y producción no.
-- La próxima migración generará un cambio duplicado o incoherente.
✓ Correcto
# ✅ Modificas la entidad C# y generas la migración
dotnet ef migrations add AddArchivedToProject \
  --project TaskFlow.Infrastructure --startup-project TaskFlow.Api
dotnet ef database update \
  --project TaskFlow.Infrastructure --startup-project TaskFlow.Api

Olvidar Include y asumir que las listas llegan llenas

✗ Incorrecto
// ❌ Tasks será una lista VACÍA (EF Core no carga relaciones por defecto)
var project = await _context.Projects.FindAsync(id);
return Ok(project.Tasks);   // siempre un array vacío: bug silencioso
✓ Correcto
// ✅ Pide explícitamente lo relacionado que vas a devolver
var project = await _context.Projects
    .Include(p => p.Tasks)
    .FirstOrDefaultAsync(p => p.Id == id);

Guardar la contraseña en claro

✗ Incorrecto
// ❌ Cualquiera con acceso a la base de datos conoce las contraseñas
user.PasswordHash = dto.Password;
✓ Correcto
// ✅ Hash unidireccional con BCrypt (lección 3): no se puede revertir
user.PasswordHash = BCrypt.Net.BCrypt.HashPassword(dto.Password);

Fechas con DateTime.Now

✗ Incorrecto
// ❌ Hora local del servidor: cambia según dónde se despliegue
public DateTime CreatedAt { get; set; } = DateTime.Now;
✓ Correcto
// ✅ UTC: el instante es el mismo en cualquier servidor
public DateTime CreatedAt { get; set; } = DateTime.UtcNow;

8 · Reto

🎯 Etiquetas como relación real (y un índice compuesto)

El reto es llevar las etiquetas del modelo «texto separado por comas» a un modelo relacional de verdad:

  1. Crea la entidad Label (con Name y Color) y configura la relación muchos-a-muchos con TaskItem.
  2. Añade una migración que cree las tablas nuevas y migre los datos existentes de la columna Labels a las filas de la tabla de unión.
  3. Configura un índice compuesto único (ProjectId, Title) en TaskItem para impedir dos tareas con el mismo nombre dentro de un proyecto.

Pista: para el N:M puedes dejar que EF Core genere la tabla de unión implícita o declararla explícita como hicimos con ProjectMember. Para migrar los datos, edita el método Up() de la migración generada y escribe el UPDATE/INSERT … SELECT a mano — es el único caso legítimo para tocar una migración, y siempre revisándola. Para el índice: modelBuilder.Entity<TaskItem>().HasIndex(t => new { t.ProjectId, t.Title }).IsUnique();

9 · Resumen

  • EF Core es el ORM oficial de .NET: clases C# ↔ tablas PostgreSQL, LINQ ↔ SQL.
  • Trabajamos code-first: las entidades son la fuente de verdad y las migraciones versionan el esquema.
  • Un DbSet<T> es una tabla; una propiedad es una columna; una navegación List<T> es una relación.
  • Las reglas que la convención no cubre se declaran con Fluent API en OnModelCreating (índices únicos, claves compuestas, conversiones).
  • Trae datos relacionados con Include, evita el problema N+1 y AsNoTracking() en lecturas.
  • Guarda siempre en UTC y nunca contraseñas en claro.
  • Los datos de ejemplo van en HasData con IDs fijos.

10 · Preguntas frecuentes

¿Entity Framework Core es lento? ¿No es mejor Dapper o SQL a mano?

Depende del caso. EF Core añade una capa de traducción y de seguimiento de cambios que en escenarios muy específicos cuesta microsegundos. Para un CRUD de aplicación como TaskFlow es perfectamente rápido y, sobre todo, mantenible. Cuando necesites control absoluto del SQL en una consulta pesada, puedes usar FromSqlRaw o Dapper dentro de EF Core: no son enemigos, coexisten.

¿Por qué mis listas relacionadas llegan siempre vacías?

Casi seguro porque falta un Include. EF Core no carga relaciones automáticamente (a diferencia de la lazy loading que existía en versiones antiguas con proxies). Debes pedir explícitamente cada navegación que vas a usar: .Include(p => p.Tasks). Es una decisión de diseño deliberada: obliga a ser consciente del SQL que se genera y evita el problema N+1.

¿Qué pasa si me equivoco en una migración ya aplicada?

Depende. Si ya está aplicada en producción, quedan las opciones honestas: añadir una migración que lo corrija (la favorita) o crear la migración inversa correspondiente. Si solo está en tu entorno local y no la has compartido, puedes revertir con dotnet ef database update NombreAnterior y luego dotnet ef migrations remove. Lo que nunca hay que hacer es borrar la fila de __EFMigrationsHistory a mano y seguir: dejarás el esquema y el historial desincronizados.

¿Puedo usar List<string> para las etiquetas en PostgreSQL sin conversión?

PostgreSQL soporta columnas text[] (arrays nativos) y Npgsql las mapea de serie a List<string>. Podrías usarlo directamente. Aun así, en esta lección mostramos HasConversion porque enseña un concepto transferible —cómo adaptar un tipo cuando el motor no lo soporta— y deja claro el coste: arrays y texto separado por comas no son relacionales y complican filtros e índices. La solución «correcta» y escalable es el reto: una tabla de etiquetas.

¿Cómo veo el SQL que EF Core está generando?

Con .ToQueryString() sobre cualquier consulta obtienes el SQL sin ejecutarlo: perfecto para depurar. Para verlo en vivo, registra el nivel Information para Microsoft.EntityFrameworkCore.Database.Command en appsettings.Development.json. En la lección 4 usaremos esta técnica para comprobar que un Include se traduce en un LEFT JOIN y no en consultas extra.
