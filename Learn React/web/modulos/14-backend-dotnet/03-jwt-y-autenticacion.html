JWT y autenticación

Módulo 14 · Backend con .NET 8 🕐 55 minutos

1 · Introducción

TaskFlow es una aplicación con cuentas de usuario: cada persona ve sus proyectos y no los de los demás. Esto plantea dos preguntas que toda API debe resolver: ¿quién eres? (autenticación) y ¿qué puedes hacer? (autorización).

La respuesta clásica es una sesión en el servidor: al iniciar sesión, el servidor guarda en memoria quién eres y te da una cookie. Funciona, pero no escala bien: si mañana tienes tres servidores, cada uno tiene que conocer la sesión. La respuesta moderna para APIs consumidas por un frontend (nuestro React) es el JSON Web Token (JWT): un token firmado que el cliente envía en cada petición y que el servidor puede validar sin consultar ninguna base de datos ni mantener estado.

En esta lección implementamos el flujo completo: registro, inicio de sesión, hash de contraseñas y protección de endpoints con [Authorize].

¿Por qué existe esta lección? Porque la autenticación es la puerta de entrada a cualquier aplicación real, y es también la parte donde más se falla. Un hash mal hecho o una clave JWT filtrada convierten tu proyecto en una brecha de seguridad. Aquí entenderás qué viaja dentro del token, por qué es seguro y, sobre todo, por qué no debe contener datos sensibles.

Errores típicos:

  • Guardar contraseñas en claro o con un hash reversible.
  • Firmar tokens con una clave débil, corta o escrita en el repositorio.
  • Meter datos sensibles (contraseña, datos personales) en el payload del token: es legible por cualquiera.
  • No validar el emisor, la audiencia y la caducidad en el servidor.
  • Devolver mensajes distintos para «email no existe» y «contraseña incorrecta»: eso ayuda a los atacantes.

2 · Teoría

La distinción importa: un 401 significa «no sé quién eres, identifícate»; un 403, «sé quién eres, pero no tienes permiso». En el frontend, un 401 suele llevar al login y un 403 a un mensaje de «no autorizado».

Anatomía de un JWT

Un JWT es una cadena con tres partes separadas por puntos:

eyJhbGciOiJIUzI1NiJ9  .  eyJzdWIiOiIxIiwibmFtZSI6IkFudG9uaW8ifQ  .  SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
└────────┬──────────┘     └──────────────┬───────────────┘     └──────────────┬───────────────┘
      HEADER                        PAYLOAD                          SIGNATURE
   {"alg":"HS256",            {"sub":"…","name":"…",              firma con la
    "typ":"JWT"}               "exp":1767225600}                   clave secreta
     (algoritmo)              (claims del usuario)                  del servidor

La parte más importante: el header y el payload van codificados en Base64URL, NO cifrados. Cualquiera puede leerlos: pega el token en jwt.io y verás todo su contenido. Lo único que el servidor garantiza es que la firma no se puede falsificar sin la clave secreta. Por eso: nunca metas contraseñas, emails completos ni datos personales de más en el payload.

Hash de contraseñas: por qué BCrypt

Una contraseña nunca se guarda tal cual. Se guarda su hash: el resultado de aplicar una función unidireccional. De la contraseña se obtiene el hash, pero del hash no se recupera la contraseña.

No sirve cualquier hash (MD5, SHA-256): son demasiado rápidos y permiten probar millones de contraseñas por segundo. BCrypt está diseñado para ser lento y añade un salt aleatorio por usuario, de forma que dos personas con la misma contraseña tienen hashes distintos. Verificar es igual de fácil; atacar por fuerza bruta es inviable.

Analogía: un hash rápido (SHA-256) es como una cerradura que se abre en un segundo: probar un millón de llaves es cuestión de horas. BCrypt es una cerradura que tarda 100 ms en abrirse: probar un millón de llaves son casi 28 horas por cada usuario. El mismo algoritmo, aplicado con un factor de coste, cambia por completo la seguridad.

3 · Ejemplo mínimo

Lo más pequeño que demuestra el concepto: hashear una contraseña con BCrypt y comprobar que dos hashes de la misma contraseña son distintos.

Terminal
# BCrypt.Net-Next es la librería de hashing que usaremos
dotnet add TaskFlow.Infrastructure package BCrypt.Net-Next --version 4.0.3
TaskFlow.Infrastructure/Identity/PasswordHasher.cs
namespace TaskFlow.Infrastructure.Identity;

public class PasswordHasher
{
    // HashPassword genera un SALT aleatorio interno y lo incluye en el resultado.
    // Por eso dos hashes de la misma contraseña son diferentes entre sí.
    public string Hash(string password) =>
        BCrypt.Net.BCrypt.HashPassword(password, workFactor: 11);

    // Verify recalcula internamente y compara de forma segura
    public bool Verify(string password, string hash) =>
        BCrypt.Net.BCrypt.Verify(password, hash);
}
Terminal
# Con un proyecto de consola rápido se ve el comportamiento
dotnet script
> var h = new PasswordHasher();
> h.Hash("demo1234");   // "$2a$11$…" (distinto cada vez)
> h.Verify("demo1234", hashAnterior);  // true
> h.Verify("otra", hashAnterior);      // false

Línea por línea:

  1. workFactor: 11: el «coste» del algoritmo. Cada unidad duplica el tiempo de cómputo. 11 es un buen equilibrio hoy: ~100 ms en hardware corriente, imperceptible para un login legítimo y letal para un ataque masivo. Súbelo con el tiempo si el hardware mejora.
  2. HashPassword devuelve el salt + hash juntos en una sola cadena (formato $2a$11$salt+hash). No necesitas guardar el salt por separado; va dentro.
  3. Verify(password, hash) extrae el salt del hash, recalcula y compara en tiempo constante para no filtrar información por tiempo de respuesta.

4 · Ejemplo real

Ahora el flujo completo de TaskFlow. Empezamos por el servicio que genera tokens.

TaskFlow.Infrastructure/Identity/JwtService.cs
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.Extensions.Configuration;
using Microsoft.IdentityModel.Tokens;
using TaskFlow.Core.Entities;

namespace TaskFlow.Infrastructure.Identity;

public class JwtService
{
    private readonly IConfiguration _configuration;

    public JwtService(IConfiguration configuration) => _configuration = configuration;

    public string GenerateToken(User user)
    {
        // La clave simétrica: debe tener al menos 32 bytes para HS256.
        // Se lee de configuración (user-secrets en local, variable de entorno en prod).
        var key = new SymmetricSecurityKey(
            Encoding.UTF8.GetBytes(_configuration["Jwt:Key"]!));

        // Credenciales de firma: algoritmo HS256 (HMAC + SHA-256)
        var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

        // Claims: la identidad que irá dentro del token
        var claims = new[]
        {
            new Claim(JwtRegisteredClaimNames.Sub, user.Id.ToString()),
            new Claim(JwtRegisteredClaimNames.Email, user.Email),
            new Claim(ClaimTypes.Name, user.Name)
        };

        var token = new JwtSecurityToken(
            issuer: _configuration["Jwt:Issuer"],
            audience: _configuration["Jwt:Audience"],
            claims: claims,
            expires: DateTime.UtcNow.AddDays(7), // caducidad: 7 días
            signingCredentials: credentials);

        // WriteToken serializa (header.payload.signature) en Base64URL
        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}

Caducidad: 7 días es cómodo para un proyecto didáctico, pero largo en producción. Lo habitual es un access token corto (15–60 min) más un refresh token largo que permite renovarlo sin volver a pedir la contraseña. Lo mencionamos en el reto.

Configurar el pipeline de autenticación

Registramos JwtService, configuramos el esquema Bearer y validamos cada token entrante.

TaskFlow.Api/Program.cs (fragmento)
using System.Text;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;
using TaskFlow.Infrastructure.Identity;

// Registramos el servicio de tokens como singleton (no guarda estado por petición)
builder.Services.AddSingleton<JwtService>();
builder.Services.AddSingleton<PasswordHasher>();

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        // Estas comprobaciones son OBLIGATORIAS: sin ellas, un token de otra
        // aplicación o caducado podría colarse.
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,            // el emisor debe ser el nuestro
            ValidateAudience = true,          // la audiencia también
            ValidateLifetime = true,          // debe estar vigente (no caducado)
            ValidateIssuerSigningKey = true,  // la firma debe coincidir con la clave
            ValidIssuer = builder.Configuration["Jwt:Issuer"],
            ValidAudience = builder.Configuration["Jwt:Audience"],
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(builder.Configuration["Jwt:Key"]!))
        };
    });

builder.Services.AddAuthorization();

var app = builder.Build();

app.UseAuthentication();   // 1º: ¿lleva un token válido? rellena User
app.UseAuthorization();    // 2º: ¿tiene permiso para este endpoint?
app.MapControllers();
app.Run();

El orden importa: UseAuthentication() va siempre antes de UseAuthorization(). La autenticación rellena HttpContext.User; la autorización lo consulta. Si los inviertes, todos tus [Authorize] devolverán 401 aunque el token sea perfecto.

El controlador de autenticación

Tres endpoints: registro, login y «quién soy».

TaskFlow.Api/Controllers/AuthController.cs
using System.IdentityModel.Tokens.Jwt;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using TaskFlow.Core.DTOs;
using TaskFlow.Core.Entities;
using TaskFlow.Infrastructure.Data;
using TaskFlow.Infrastructure.Identity;

namespace TaskFlow.Api.Controllers;

[ApiController]
[Route("api/[controller]")]
public class AuthController : ControllerBase
{
    private readonly TaskFlowDbContext _context;
    private readonly JwtService _jwt;
    private readonly PasswordHasher _hasher;

    public AuthController(TaskFlowDbContext context, JwtService jwt, PasswordHasher hasher)
    {
        _context = context;
        _jwt = jwt;
        _hasher = hasher;
    }

    // POST /api/auth/register
    [HttpPost("register")]
    public async Task<IActionResult> Register(RegisterDto dto)
    {
        // El email debe ser único (también hay índice único en la BD)
        if (await _context.Users.AnyAsync(u => u.Email == dto.Email))
            return Conflict(new { message = "El email ya está registrado" });

        var user = new User
        {
            Name = dto.Name,
            Email = dto.Email,
            PasswordHash = _hasher.Hash(dto.Password) // hash, NUNCA en claro
        };

        _context.Users.Add(user);
        await _context.SaveChangesAsync();

        return CreatedAtAction(nameof(Me), null, new
        {
            user = Map(user),
            token = _jwt.GenerateToken(user)
        });
    }

    // POST /api/auth/login
    [HttpPost("login")]
    public async Task<IActionResult> Login(LoginDto dto)
    {
        var user = await _context.Users.FirstOrDefaultAsync(u => u.Email == dto.Email);

        // Mensaje GENÉRICO: no revelamos si el email existe o la contraseña falló
        if (user is null || !_hasher.Verify(dto.Password, user.PasswordHash))
            return Unauthorized(new { message = "Credenciales inválidas" });

        return Ok(new
        {
            user = Map(user),
            token = _jwt.GenerateToken(user)
        });
    }

    // GET /api/auth/me  -> requiere token válido
    [Authorize]
    [HttpGet("me")]
    public async Task<IActionResult> Me()
    {
        // El claim "sub" lo depositó el middleware tras validar el token
        var sub = User.FindFirst(JwtRegisteredClaimNames.Sub)?.Value;
        if (sub is null) return Unauthorized();

        var user = await _context.Users.FindAsync(Guid.Parse(sub));
        return user is null ? NotFound() : Ok(Map(user));
    }

    // Proyección a un objeto anónimo: solo campos públicos, sin PasswordHash
    private static object Map(User u) => new { u.Id, u.Name, u.Email };
}

5 · Buenas prácticas

HazEvitaPor qué
BCrypt (o Argon2) con workFactor razonable MD5, SHA-256 o contraseñas en claro Los hashes rápidos se revientan por fuerza bruta; BCrypt está hecho para ser lento
Clave JWT ≥ 32 caracteres aleatorios, fuera del repo Claves cortas o escritas en appsettings.json Con la clave se pueden falsificar tokens; si se filtra, la autenticación se cae
Validar Issuer, Audience, Lifetime y firma Dejar las validaciones por defecto sin revisarlas Sin validación, tokens de otro entorno o caducados podrían aceptarse

HTTPS obligatorio Servir la API por HTTP en producción El token viaja en la cabecera: sin TLS, cualquiera en la red lo intercepta

6 · Errores habituales

Guardar la contraseña tal cual

✗ Incorrecto
// ❌ Cualquiera con acceso a la BD (o a un backup) conoce todas las contraseñas
var user = new User { Email = dto.Email, PasswordHash = dto.Password };
✓ Correcto
// ✅ Hash unidireccional con salt incluido (BCrypt)
var user = new User { Email = dto.Email, PasswordHash = _hasher.Hash(dto.Password) };

Poner datos sensibles en el payload del JWT

✗ Incorrecto
// ❌ El payload es Base64, NO cifrado: cualquiera lo lee
new Claim("password", user.PasswordHash),
new Claim("creditCard", user.CreditCard)
✓ Correcto
// ✅ Solo el identificador y datos no sensibles
new Claim(JwtRegisteredClaimNames.Sub, user.Id.ToString()),
new Claim(ClaimTypes.Name, user.Name)

Ordenar mal el middleware

✗ Incorrecto
// ❌ Authorization antes de Authentication: aún no hay usuario que autorizar
app.UseAuthorization();
app.UseAuthentication();
✓ Correcto
// ✅ Primero identificar, después autorizar
app.UseAuthentication();
app.UseAuthorization();

Revelar si el usuario existe

✗ Incorrecto
// ❌ Mensajes distintos -> permite enumerar emails registrados
if (user is null) return NotFound(new { message = "Ese email no existe" });
if (!_hasher.Verify(dto.Password, user.PasswordHash))
    return Unauthorized(new { message = "Contraseña incorrecta" });
✓ Correcto
// ✅ Mismo mensaje para ambos casos: no se filtra información
if (user is null || !_hasher.Verify(dto.Password, user.PasswordHash))
    return Unauthorized(new { message = "Credenciales inválidas" });

8 · Reto

🎯 Añade un refresh token y roles

Dos mejoras profesionales sobre el flujo actual:

  1. Crea un endpoint POST /api/auth/refresh que reciba un refresh token y devuelva un nuevo access token corto (por ejemplo 30 minutos). Guarda el refresh token en la base de datos con su fecha de expiración y permite revocarlo.
  2. Añade un claim de rol al token (admin / user) y protege un endpoint nuevo con [Authorize(Roles = "admin")]. Comprueba que un usuario normal recibe 403 (autenticado pero sin permiso) y no 401.

Pista: para el refresh, el access token se genera igual que ahora pero con AddMinutes(30); el refresh es un valor aleatorio largo (RandomNumberGenerator) que se persiste y se compara. Para los roles, añade new Claim(ClaimTypes.Role, "admin") al firmar y asegúrate de que en la firma está la colección de roles como array de claims. La diferencia entre 401 y 403 es exactamente la que viste en la teoría: 401 = no sé quién eres; 403 = sé quién eres pero no tienes el rol.

9 · Resumen

  • Autenticar es saber quién eres (401 si falla); autorizar es decidir qué puedes hacer (403 si no puedes).
  • Un JWT tiene tres partes: header, payload y firma. El payload es legible; solo la firma garantiza autenticidad.
  • Los claims (sub, email, rol…) son la identidad que viaja dentro del token.
  • Las contraseñas se guardan con BCrypt (lento, con salt), nunca en claro ni con hashes rápidos.
  • El pipeline necesita UseAuthentication() antes de UseAuthorization().
  • [Authorize] protege un endpoint; User dentro del controlador expone los claims ya validados.
  • La clave JWT vive en user-secrets o variables de entorno, jamás en el repositorio.

10 · Preguntas frecuentes

Si el payload del JWT es legible, ¿por qué es seguro?

Porque la seguridad no está en el secreto, sino en la firma. El servidor firma header + payload con una clave secreta que solo él conoce. Si alguien cambia un solo carácter del payload (por ejemplo, poniéndose rol «admin»), la firma deja de coincidir y el token se rechaza. La confidencialidad no forma parte del diseño de JWT: es un mecanismo de integridad y autenticidad, no de cifrado. Si necesitas ocultar el contenido, usa cifrado (JWE) o, mejor, mete en el token solo un identificador y consulta el resto en el servidor.

¿Dónde guardo el token en el frontend: localStorage o cookie?

Ambos tienen riesgos. localStorage es fácil de usar pero vulnerable a XSS: si un script malicioso corre en tu página, puede leer el token. Una cookie HttpOnly, Secure, SameSite es inmune a XSS (el JavaScript no la puede leer) pero reintroduce el riesgo de CSRF, que se mitiga con tokens anti-CSRF. En este curso seguimos con localStorage por simplicidad y porque el frontend se despliega aparte de la API, pero conviene conocer el compromiso y, en producción real, evaluar cookies HttpOnly.

¿Por qué el login devuelve el mismo mensaje si el email no existe o la contraseña falla?

Para evitar la enumeración de usuarios. Si el mensaje distingue ambos casos, un atacante puede averiguar qué emails están registrados probándolos uno a uno. Con un mensaje genérico, un intento solo confirma «algo está mal», sin decirte el qué. Es un principio de seguridad habitual: no dar pistas innecesarias a quien no está autenticado.

¿Qué pasa si se filtra la clave JWT?

Es un incidente grave: con la clave, cualquiera puede fabricar tokens válidos y hacerse pasar por cualquier usuario. Por eso vive fuera del repositorio (user-secrets, variables de entorno, gestor de secretos) y debe rotarse. Plan de respuesta: cambiar la clave en el servidor (invalida automáticamente todos los tokens firmados con la anterior), forzar un nuevo login y revisar accesos. Una clave larga y aleatoria de al menos 256 bits hace inviable adivinarla.

¿Puedo devolver más datos en el token para ahorrar consultas?

Sí, con moderación. Meter el nombre o el rol evita una consulta a la base de datos en cada petición. Pero el token es inmutable hasta que caduque: si actualizas el nombre del usuario, el token seguirá llevando el viejo hasta que expire. La regla práctica: mete en el token los identificadores y datos que cambian poco (ID, rol) y consulta en la base de datos lo que pueda cambiar con frecuencia o sea sensible.
