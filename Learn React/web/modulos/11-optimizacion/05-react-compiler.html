React Compiler

Módulo 11 · Optimización ⏱ 25 minutos

1 · Introducción

En las lecciones anteriores has aprendido a memorizar a mano: memo, useMemo, useCallback. Es eficaz, pero también tedioso y fácil de olvidar. El React Compiler (antes conocido como "React Forget") invierte el enfoque: en lugar de que tú decidas dónde memorizar, un compilador analiza tu código en tiempo de build y añade las memorizaciones automáticamente.

Está pensado para trabajar con React 19 (aunque soporta React 17 y 18) y ya es estable para producción. Tú escribes JavaScript limpio y React se encarga del rendimiento por defecto.

¿Por qué existe?

Porque optimizar a mano no escala. Mantener cientos de useMemo y useCallback es propenso a errores: se olvidan dependencias, se memoiza lo que no toca y se rompe la memorización con props inestables. El compilador hace ese trabajo de forma consistente y te devuelve código enfocado en la lógica.

Qué problema resuelve: elimina el boilerplate de memorización manual y aplica optimizaciones correctas en todo el proyecto sin que tengas que pensarlas.

Cuándo se usa: en proyectos React 19 nuevos y, de forma incremental, en código existente; necesario si dependes de la memorización automática para el rendimiento.

Errores típicos: esperar que arregle código que viola las reglas de React; mutar props o estado (rompe el compilador); y activarlo sin el lint que señala los componentes que no puede optimizar.

2 · Teoría

El problema: memorización manual

Este bloque es correcto, pero nadie quiere escribirlo ni mantenerlo: 

import { memo, useCallback, useMemo } from "react";

const List = memo(function List({ items, onPick }) {
  // Memorizamos el valor derivado…
  const ordered = useMemo(
    () => [...items].sort((a, b) => a.name.localeCompare(b.name)),
    [items]
  );

  // …y el callback, o `memo` no serviría de nada.
  const handlePick = useCallback((id) => onPick(id), [onPick]);

  return (
    <ul>
      {ordered.map((it) => (
        <li key={it.id} onClick={() => handlePick(it.id)}>
          {it.name}
        </li>
      ))}
    </ul>
  );
});

Con el compilador activo, escribes lo mismo sin la maquinaria, y él añade las memorizaciones equivalentes: 

function List({ items, onPick }) {
  const ordered = [...items].sort((a, b) => a.name.localeCompare(b.name));

  function handlePick(id) {
    onPick(id);
  }

  return (
    <ul>
      {ordered.map((it) => (
        <li key={it.id} onClick={() => handlePick(it.id)}>
          {it.name}
        </li>
      ))}
    </ul>
  );
}

Cómo funciona por dentro

El compilador es un plugin de Babel. Analiza cada componente y hook, entiende el flujo de datos y, sin cambiar la semántica, inserta cachés de valores por render a través de un runtime interno (react/compiler-runtime).

QUÉ HACE EL REACT COMPILER ────────────────────────── Tu código fuente (JSX limpio) │ ▼ Análisis del flujo de datos y de las dependencias │ ▼ Inserción automática de cachés por render (equivalente a useMemo / useCallback / memo) │ ▼ Código compilado que llama a react/compiler-runtime │ ▼ En React DevTools: badge "Memo ✨" en el componente

Así se ve, simplificado, un componente compilado:

import { c as _c } from "react/compiler-runtime";

export default function MyApp() {
  const $ = _c(1); // reserva un hueco de caché
  let t0;
  if ($[0] === Symbol.for("react.memo_cache_sentinel")) {
    t0 = <div>Hello World</div>; // se calcula una sola vez
    $[0] = t0;
  } else {
    t0 = $[0]; // en renders posteriores se reutiliza
  }
  return t0;
}

Las reglas de React: el contrato del compilador

Para poder optimizar con seguridad, el compilador asume que tu código cumple las Reglas de React. Si no las cumples, simplemente omite ese componente (no rompe la app).

ReglaQué significaConsecuencia si la violas
Componentes puros Mismo input (props/estado) → mismo output; sin efectos secundarios en el render. Ese componente no se optimiza.
Inmutabilidad No mutar props ni estado directamente; crear copias. Cachés incorrectas o componente omitido.
Hooks en el nivel superior No llamar hooks dentro de condiciones o bucles. No optimizable (y bug real en React).
Sin efectos en el render Los efectos van en useEffect o en manejadores. Comportamiento impredecible al memorizar.
Adopción incremental y opt-out

Puedes aplicar el compilador por carpetas para no tocar todo un código heredado de golpe. Y si un componente concreto se comporta mal, se excluye temporalmente con la directiva "use no memo" en su cuerpo, arreglas la causa y la quitas.

3 · Ejemplo mínimo

src/components/Contador.jsx
import { useState } from "react";

// Sin memo, sin useCallback: código "de libro".
// Con el compilador activo, React añade la memorización que haga falta.
export default function Contador() {
  const [count, setCount] = useState(0);

  // Si esta función se pasara a un hijo, el compilador la estabilizaría solo.
  const incrementar = () => setCount((c) => c + 1);

  return <button onClick={incrementar}>Clics: {count}</button>;
}

Línea por línea:

  1. Sin memo: no envolvemos el componente a mano; el compilador decide si hace falta.
  2. incrementar como función normal: no necesitamos useCallback; el compilador la cachea si su referencia debe ser estable.
  3. La lógica es la misma: el compilador no cambia qué hace el componente, solo cuándo se recalcula.

4 · Ejemplo real

Un buscador con resultados: lo difícil a mano sería estabilizar el onSelect que pasamos a cada fila. Con el compilador, desaparece.

src/components/Buscador.jsx
import { useMemo, useState } from "react";

// Recibe el catálogo por props. El compilador memorizará el filtrado
// derivado y la función `seleccionar` sin que escribamos useMemo/useCallback.
export default function Buscador({ catalogo, onSelect }) {
  const [texto, setTexto] = useState("");

  // Este valor derivado se cachea automáticamente según sus dependencias reales.
  const resultados = catalogo.filter((p) =>
    p.name.toLowerCase().includes(texto.toLowerCase())
  );

  // Esta función mantiene una referencia estable entre renders.
  function seleccionar(id) {
    onSelect(id);
  }

  return (
    <>
      <input value={texto} onChange={(e) => setTexto(e.target.value)} />
      <ul>
        {resultados.map((p) => (
          <li key={p.id} onClick={() => seleccionar(p.id)}>
            {p.name}
          </li>
        ))}
      </ul>
    </>
  );
}

Decisiones explicadas:

  • Sin useMemo para resultados: el compilador detecta que depende de catalogo y texto y lo cachea.
  • Sin useCallback para seleccionar: el compilador le da una referencia estable mientras su lógica no dependa de valores cambiantes.
  • Mismo comportamiento, menos ruido: el código se lee como lógica de negocio, no como una coreografía de hooks.
El compilador no arregla una mala arquitectura

Si el estado está mal colocado o un componente depende de datos que cambian sin parar, el compilador no puede hacer magia. Sigue siendo imprescindible el diagnóstico de las lecciones 01 y 04: medir primero, y usar el compilador como red de seguridad automática del rendimiento.

6 · Errores habituales

Error 1: mutar props o estado

✘ Incorrecto 
function Lista({ items }) {
  // 💥 Mutar una prop: el compilador no puede razonar sobre los cambios
  // y omite la optimización (o produce cachés incorrectas).
  items.sort((a, b) => a.name.localeCompare(b.name));
  return <ul>{items.map((i) => <li key={i.id}>{i.name}</li>)}</ul>;
}
✔ Correcto 
function Lista({ items }) {
  // ✅ Crea una copia y ordena la copia: entrada inmutable, salida estable.
  const ordenados = [...items].sort((a, b) => a.name.localeCompare(b.name));
  return <ul>{ordenados.map((i) => <li key={i.id}>{i.name}</li>)}</ul>;
}

Error 2: hooks condicionales

✘ Incorrecto 
function Panel({ visible }) {
  // 💥 Hook dentro de un condicional: viola las Reglas y rompe el análisis.
  if (visible) {
    const [x] = useState(0);
  }
  return null;
}
✔ Correcto 
function Panel({ visible }) {
  // ✅ El hook se llama siempre, en el nivel superior.
  const [x] = useState(0);
  if (!visible) return null;
  return <p>{x}</p>;
}

Error 3: efectos secundarios durante el render

✘ Incorrecto 
function Perfil({ id }) {
  // 💥 Escribir en el DOM o enviar analítica durante el render es un efecto.
  document.title = `Perfil ${id}`;
  return <h1>Perfil</h1>;
}
✔ Correcto 
function Perfil({ id }) {
  // ✅ El título se declara con metadata (Módulo 11, lección 07):
  //    React lo sube al <head> sin efectos imperativos.
  return (
    <>
      <title>Perfil {id}</title>
      <h1>Perfil</h1>
    </>
  );
}

7 · Ejercicio guiado

Instala y verifica el React Compiler en un proyecto Vite con React 19.

  1. Crea el proyecto e instala el plugin del compilador. 
    pnpm create vite@latest m11-compiler --template react
cd m11-compiler
pnpm install
pnpm add -D babel-plugin-react-compiler@latest
  2. Configura Vite. Con @vitejs/plugin-react 6 o superior se usa el preset del compilador:
    vite.config.js
    import { defineConfig } from "vite";
import react, { reactCompilerPreset } from "@vitejs/plugin-react";
import babel from "@rolldown/plugin-babel";

export default defineConfig({
  plugins: [
    react(),
    // El compilador debe ejecutarse PRIMERO en el pipeline de Babel.
    babel({ presets: [reactCompilerPreset()] }),
  ],
});

    En versiones anteriores del plugin, la opción va dentro de react(): 

    import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [
    react({
      babel: { plugins: ["babel-plugin-react-compiler"] },
    }),
  ],
});
  3. Instala el lint de reglas del compilador. 
    pnpm add -D eslint-plugin-react-hooks@latest

    Activa el preset recommended-latest en tu configuración de ESLint para que señale los componentes no optimizables.

  4. Verifica con DevTools. Ejecuta pnpm dev y abre React DevTools: los componentes optimizados muestran el badge "Memo ✨".
  5. Provoca una violación. Escribe un componente que mute una prop (como en el Error 1) y comprueba que el lint lo señala y que DevTools deja de mostrar el badge en ese componente.

8 · Reto

🎯 Migrar una app a memorización automática

Toma la app del proyecto del módulo (o una tuya) y adóptala al React Compiler de forma incremental y medida:

  1. Baseline: registra el rendimiento actual (Profiler, lección 04) de una interacción concreta antes de tocar nada.
  2. Activa el compilador por carpetas. Empieza por una sola feature y resuelve todos los avisos del lint eslint-plugin-react-hooks en ella.
  3. Retira memorizaciones redundantes (memo, useMemo, useCallback) de esa feature, pero solo después de comprobar que el badge "Memo ✨" aparece y que las métricas no empeoran.
  4. Extiende y compara. Repite para el resto de la app y presenta el antes/después: tiempo de commit, nº de renders y tamaño del bundle.

Pista: para excluir temporalmente un componente problemático usa "use no memo" en su cuerpo; pero recuerda que es un parche: arregla la causa y quita la directiva.

9 · Resumen

  • El React Compiler memoriza automáticamente valores, funciones y componentes en tiempo de build.
  • Sustituye (o vuelve innecesarios) los useMemo, useCallback y memo manuales.
  • Se instala como babel-plugin-react-compiler (devDependency) y debe correr primero en Babel.
  • Optimiza solo componentes que cumplen las Reglas de React (puros, inmutables, hooks en el nivel superior).
  • El lint eslint-plugin-react-hooks y el badge "Memo ✨" verifican su efecto.
  • La adopción es incremental; el compilador no sustituye al diagnóstico de rendimiento.

10 · Preguntas frecuentes

¿Tengo que quitar todos mis useMemo y useCallback?

No es obligatorio. El compilador convive con ellos. Puedes retirarlos poco a poco en las zonas ya optimizadas, midiendo para confirmar que no empeora nada.

¿Qué pasa si mi componente viola las Reglas de React?

El compilador lo omite (no lo optimiza) y sigue con el resto. El lint te avisa de por qué. A diferencia de un error de ejecución, no rompe la app: simplemente ese componente se comporta como antes.

¿Funciona con React 18?

Sí, el compilador soporta React 17 y 18, aunque está diseñado para rendir al máximo con React 19. En versiones anteriores puede requerir algo de configuración extra.

¿Sigue siendo necesario React.memo?

En un proyecto con el compilador activo, normalmente no: añade esa memorización por ti. memo sigue siendo útil para leer y mantener código que no usa el compilador, y para entender qué está haciendo por debajo.

¿El compilador hace mi app más rápida siempre?

Reduce trabajo evitable en los renders, que es la mayoría de los casos. Pero no arregla cuellos de botella de arquitectura (estado mal colocado, DOM gigante) ni el coste de red. Sigue midiendo (lecciones 01 y 04).
