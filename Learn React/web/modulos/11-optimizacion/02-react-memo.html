React.memo

Módulo 11 · Optimización ⏱ 30 minutos

1 · Introducción

En la lección anterior vimos que cuando un componente se re-renderiza, todo su subárbol lo hace con él. React.memo es la herramienta que rompe esa cascada para un hijo concreto: le dice a React "si las props de este componente no han cambiado, reutiliza el último resultado y no vuelvas a llamarlo".

Piénsalo como un envoltorio (higher-order component): tomas un componente y obtienes otro componente equivalente que, además, se salta renders cuando sus props no cambian.

¿Por qué existe?

Porque la cascada del padre es muy habitual y muchas veces el hijo recibe props que no han cambiado. Sin memo no habría forma de decirle a React "este hijo en concreto es caro, no lo rehagas si no hace falta". React no compara props por defecto porque esa comparación también cuesta.

Qué problema resuelve: evita re-renders de componentes costosos cuyas props permanecen iguales entre renders del padre.

Cuándo se usa: en componentes pesados (tablas grandes, gráficos, listas largas) que se re-renderizan por culpa de un padre que cambia por otro motivo.

Errores típicos: envolver todo en memo; pasarle objetos, arrays o funciones creadas en el render (que siempre son "nuevas"); y usarlo en componentes triviales donde el coste de comparar supera al de renderizar.

2 · Teoría

Qué hace exactamente memo

memo(Componente) devuelve un componente nuevo. Antes de renderizar compara las props anteriores con las nuevas usando una comparación superficial (una por una, con Object.is). Si todas son iguales, React reutiliza el resultado anterior y no ejecuta tu función.

REACT.MEMO: DECISIÓN EN CADA RENDER DEL PADRE ───────────────────────────────────────────── Padre renderiza │ ▼ <MemoizedComp prop={...} /> │ ▼ ¿propsAnteriores ≈ propsNuevas? (comparación superficial) │ ├── SÍ → se reutiliza el árbol anterior (0 trabajo de render) │ └── NO → se ejecuta la función del componente de nuevo
"Superficial" significa un nivel

memo compara cada prop con Object.is. Para primitivos (números, strings, booleanos) esto es exacto. Para objetos, arrays y funciones, Object.is pregunta ¿es la misma referencia?, no "¿tiene el mismo contenido?". Por eso {'{ color: "red" }'} recién creado nunca es igual al anterior.

La tabla de la verdad de memo

Prop¿Cambió de referencia?¿Renderiza?Comentario
count={5}NoNoPrimitivo: comparación exacta.
count={6}SíSíEl valor cambió: hay que re-renderizar.
style={'{'} color: "red" {'}'} creado en el renderSí (nuevo objeto)SíMismo contenido, nueva referencia: memo no ayuda.
onClick={'() => …'} creado en el renderSí (nueva función)SíNecesita useCallback.

El patrón memo + children

A veces el componente que quieres saltarte recibe como hijos JSX que tú recreas. Truco muy útil: si pasas JSX como children desde un padre memorizado, los hijos no se re-renderizan aunque el estado cambie dentro. Lo veremos en el ejemplo real.

React 19 y el React Compiler

React 19 introduce el React Compiler, que añade estas memorizaciones de forma automática (lo estudiaremos en la lección 05). Mientras lo adoptas, memo sigue siendo la herramienta manual y entender por qué funciona es requisito para entender lo que el compilador hace por ti.

3 · Ejemplo mínimo

src/components/Etiqueta.jsx
import { memo } from "react";

// Componente "caro" (imagina que hace un cálculo pesado).
function Etiqueta({ texto }) {
  console.log("Etiqueta renderiza");
  return <span className="etiqueta">{texto}</span>;
}

// memo devuelve un componente equivalente que se salta renders
// cuando `texto` no cambia.
export default memo(Etiqueta);

Línea por línea:

  1. function Etiqueta({ texto }): un componente normal. El console.log nos deja ver cuándo se ejecuta.
  2. memo(Etiqueta): lo envuelve. React recordará las props del último render (aquí, texto) y las comparará con las nuevas.
  3. export default memo(...): se exporta el envoltorio, no el componente original; quien lo importe ya obtiene la versión memorizada.
displayName en DevTools

Al envolver con memo, el nombre en React DevTools puede aparecer como anónimo. Define Etiqueta.displayName = "Etiqueta" (o usa una función con nombre dentro de memo) para que el árbol sea legible.

4 · Ejemplo real

Un panel de productos: al escribir en el buscador, el padre se re-renderiza, pero queremos que la tabla (cara) solo lo haga cuando cambien sus datos o el callback de selección.

src/components/ProductTable.jsx
import { memo } from "react";

// Componente caro: se memoiza. Recibe dos props: los datos y un callback.
function ProductTable({ products, onSelect }) {
  console.log("ProductTable renderiza", products.length);

  return (
    <table>
      <tbody>
        {products.map((p) => (
          <tr key={p.id} onClick={() => onSelect(p.id)}>
            <td>{p.name}</td>
            <td>{p.price} €</td>
          </tr>
        ))}
      </tbody>
    </table>
  );
}

export default memo(ProductTable);
src/App.jsx
import { useCallback, useMemo, useState } from "react";
import ProductTable from "./components/ProductTable.jsx";

export default function App() {
  const [search, setSearch] = useState("");
  const [selectedId, setSelectedId] = useState(null);
  const [products] = useState(() => [
    { id: 1, name: "Camiseta", price: 19 },
    { id: 2, name: "Sudadera", price: 39 },
    { id: 3, name: "Gorra", price: 15 },
  ]);

  // ✅ products se filtra y se memoiza: su referencia solo cambia si
  //    cambian `products` o `search`.
  const visible = useMemo(
    () => products.filter((p) => p.name.toLowerCase().includes(search.toLowerCase())),
    [products, search]
  );

  // ✅ El callback se estabiliza: su referencia NO cambia entre renders.
  const handleSelect = useCallback((id) => setSelectedId(id), []);

  return (
    <>
      <input value={search} onChange={(e) => setSearch(e.target.value)} />
      {/* selectedId cambia en cada clic: ahí SÍ queremos re-render de la tabla. */}
      <p>Seleccionado: {selectedId ?? "—"}</p>
      <ProductTable products={visible} onSelect={handleSelect} />
    </>
  );
}

Decisiones explicadas:

  • useMemo para visible: sin él, cada render crearía un array nuevo y memo vería "prop cambiada" aunque el contenido fuera igual.
  • useCallback para handleSelect: una función recreada en cada render es, para memo, una prop que siempre cambia.
  • El estado selectedId sigue provocando renders de la tabla: es correcto, porque queremos reflejar la selección. memo no es "no renderizar nunca", es "no renderizar si no hace falta".
Regla de oro

memo solo funciona si todas las props son estables. Si una sola (objeto, array o función) se recrea en cada render, el memo se cae entero y no gana nada. Por eso memo casi siempre va acompañado de useMemo y useCallback.

5 · Buenas prácticas

HazEvitaPor qué
Memoiza componentes medidos como caros Envolver cada componente en memo Cada memo añade una comparación de props y complejidad de lectura.
Estabiliza props con useMemo / useCallback Pasar objetos y funciones nuevas cada render Una prop inestable invalida toda la memorización.
Usa constantes de módulo para datos que no cambian Crear {'{ color: "red" }'} dentro del componente Una constante definida fuera del componente es la misma referencia siempre.
Prefiere colocar mejor el estado antes que memoizar Resolver todo con memo Menos altura de estado = menos renders, sin añadir nada.
Usa el patrón memo + children cuando aplique Recrear JSX dentro del componente caro El JSX pasado como children mantiene su referencia.

6 · Errores habituales

Error 1: prop objeto creada en el render

✘ Incorrecto 
const Fila = memo(function Fila({ style }) {
  console.log("Fila renderiza");
  return <div style={style}>Hola</div>;
});

function Padre() {
  const [n, setN] = useState(0);
  // 💥 `style` es un objeto nuevo en cada render: memo no sirve de nada.
  const style = { color: "tomate" };
  return (
    <>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Fila style={style} />
    </>
  );
}
✔ Correcto 
import { memo, useMemo, useState } from "react";

// ✅ Opción A: constante de módulo si el estilo no depende del estado.
const STYLE = { color: "tomate" };

// ✅ Opción B: si depende del estado, memoízalo.
function Padre() {
  const [n, setN] = useState(0);
  const style = useMemo(() => ({ color: n > 3 ? "tomate" : "azul" }), [n]);
  return (
    <>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Fila style={style} />
    </>
  );
}

Error 2: comparador personalizado que compara a fondo

✘ Incorrecto 
// 💥 Comparar con JSON.stringify es frágil, lentísimo y sensible al orden de claves.
const Fila = memo(FilaBase, (prev, next) => {
  return JSON.stringify(prev.data) === JSON.stringify(next.data);
});
✔ Correcto 
// ✅ Compara solo el dato que importa, con igualdad barata.
const Fila = memo(
  FilaBase,
  (prev, next) => prev.data.id === next.data.id && prev.data.updatedAt === next.data.updatedAt
);

Error 3: memoizar componentes triviales

✘ Incorrecto 
// 💥 Comparar props cuesta más que renderizar un span.
const Etiqueta = memo(function Etiqueta({ children }) {
  return <span>{children}</span>;
});
✔ Correcto 
// ✅ Sin memo: es tan barato que no importa re-renderizarlo.
function Etiqueta({ children }) {
  return <span>{children}</span>;
}

7 · Ejercicio guiado

Vas a construir una lista pesada, romperla con una prop inestable y arreglarla paso a paso.

  1. Crea un componente de fila costoso (con un console.log) y un componente Lista que lo renderice 200 veces.
  2. Comprueba el escenario "malo": añade un contador en el padre. Al pulsarlo, verás 200 logs de Fila aunque los datos no cambien.
  3. Envuelve Fila con memo. Vuelve a pulsar el contador. Si el log sigue apareciendo 200 veces, es porque Fila recibe una prop inestable; si desaparece, felicidades. 
    import { memo } from "react";

const Fila = memo(function Fila({ item, onPick }) {
  console.log("Fila renderiza", item.id);
  return (
    <li onClick={() => onPick(item.id)}>
      {item.name}
    </li>
  );
});
  4. Estabiliza las props. Pasa onPick con useCallback y los datos como constante de módulo o con useMemo. Verifica que Fila ya no renderiza al pulsar el contador.
  5. Mide. Graba con el Profiler antes y después (lección 04) y anota la diferencia en el tiempo de commit al pulsar el contador.
Pista de verificación

Si al poner memo el componente sigue renderizando, ya sabes que el problema no era React: era una prop inestable. Ese es exactamente el 90 % de los casos en los que "memo no me funciona".

8 · Reto

🎯 Lista de chat con memorización fina

Construye una lista de mensajes de chat donde el rendimiento importa:

  1. Renderiza 500 mensajes. Cada mensaje muestra autor, texto y hora.
  2. Añade un input de "escribiendo…". Al teclear, el borrador cambia de estado en el padre en cada pulsación. Consigue, con memo + useCallback, que ningún mensaje se re-renderice al teclear.
  3. Comparador personalizado: marca como "no leído" solo algunos mensajes. Usa el segundo argumento de memo para que un mensaje se re-renderice únicamente cuando cambien su id, su texto o su estado de lectura.
  4. Demuéstralo con números: graba con el Profiler antes y después. Adjunta una captura del ranked chart mostrando que los mensajes ya no aparecen como re-renderizados al teclear.

Pista: el borrador y la lista deben ser componentes hermanos; si el input controlado vive dentro del mismo componente que la lista y no separas nada, ninguna memoización te salvará de la cascada.

9 · Resumen

  • React.memo envuelve un componente y se salta el render si sus props no cambian.
  • Usa comparación superficial (Object.is prop a prop), un solo nivel.
  • Solo es útil si todas las props son estables: objetos, arrays y funciones necesitan useMemo / useCallback.
  • El segundo argumento permite un comparador propio, pero casi nunca es necesario.
  • No lo uses en componentes triviales ni para "arreglar" un estado mal colocado.
  • Con React 19, el React Compiler puede automatizar estas memorizaciones (lección 05).

10 · Preguntas frecuentes

¿memo evita que un componente se re-renderice si cambia su propio estado?

No. memo solo mira las props. Si el componente tiene estado propio y lo actualiza, renderiza igualmente. Para eso no hay atajo: el estado es del componente y debe reflejarse.

¿Por qué memo no funciona cuando recibo una función como prop?

Porque cada render del padre crea una función nueva (una referencia nueva). memo ve "la prop cambió". Estabilízala con useCallback.

¿Uso memo o useMemo?

Son cosas distintas: memo memoriza un componente (evita renders); useMemo memoriza un valor dentro de un componente (evita recálculos). Se combinan: useMemo estabiliza la prop que memo necesita.

¿Pongo memo en el componente raíz de la lista o en cada ítem?

Normalmente en el ítem, que es el que se repite cientos de veces. Memorizar la lista entera evita un solo render; memorizar el ítem evita cientos. Y recuerda pasar key estable en el map.

¿memo sirve de algo si uso React Compiler?

El compilador añade memorizaciones equivalentes automáticamente, así que en un proyecto con el compilador activo memo suele ser redundante. Aun así, entenderlo es imprescindible para saber qué está haciendo el compilador por ti y para leer código legado.
