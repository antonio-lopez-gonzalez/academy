Re-renders y cómo diagnosticarlos

Módulo 11 · Optimización ⏱ 35 minutos

1 · Introducción

Antes de optimizar nada hay que responder una pregunta incómoda: ¿qué es exactamente lo que va lento? React re-renderiza componentes constantemente y, en la inmensa mayoría de los casos, eso es correcto y barato. El rendimiento solo se convierte en un problema cuando hay re-renders innecesarios en componentes costosos.

Esta lección es la base de todo el módulo. Aquí aprenderás qué dispara un render, por qué un re-render en un componente arrastra a sus hijos, cómo instrumentarlo con console.log y cómo usar React DevTools para medir antes de tocar. Las técnicas concretas (memo, useMemo, code splitting…) llegan en las siguientes lecciones; aquí solo diagnosticamos.

¿Por qué existe esta lección?

La primera causa de aplicaciones React lentas no es React: es un equipo que optimiza por intuición, envuelve todo en memo "por si acaso" y termina con un código más difícil de leer y igual de lento. Sin saber leer un render, cualquier optimización es un disparo a ciegas.

Qué problema resuelve: te da un método para pasar de "la app va lenta" a "el componente ProductRow de la tabla se re-renderiza 500 veces al escribir y tarda 40 ms por render". Ese salto, de la sensación al dato, es todo.

Cuándo se usa: siempre que notes lag al escribir, al hacer scroll, al filtrar o al navegar. Es el paso 1 obligatorio de cualquier trabajo de optimización.

Errores típicos: confundir "se re-renderiza" con "es lento"; leer mal el doble render que introduce <StrictMode> en desarrollo; y no medir nunca el resultado de una optimización.

2 · Teoría

Render y commit: dos fases distintas

Cuando React trabaja, lo hace en dos fases. En la fase de render llama a tus funciones de componente para calcular qué debería haber en pantalla (produce elementos, no toca el DOM). En la fase de commit compara esos elementos con los anteriores y aplica al DOM real únicamente los cambios necesarios.

Un "re-render" es, por tanto, volver a llamar a tu función. Que React calcule no significa que escriba en el DOM: si el resultado es idéntico, el commit es casi gratis. Ahí está la clave del diagnóstico: un re-render solo duele si dentro de la función pasa algo caro (recorrer 1.000 elementos, ordenar, crear objetos grandes…).

FLUJO DE UN RENDER EN REACT 19 ────────────────────────────── setState / setCount / dispatch / useContext cambia │ ▼ ┌─────────────────────── FASE DE RENDER ────────────────────────┐ │ React llama a la función del componente y a sus hijos │ │ → produce un árbol de elementos (objetos en memoria) │ │ → es PURO: no toca el DOM │ └───────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────── FASE DE COMMIT ────────────────────────┐ │ Diff (reconciliación) contra el árbol anterior │ │ → escribe en el DOM SOLO lo que cambió │ │ → ejecuta useEffect / useLayoutEffect │ └───────────────────────────────────────────────────────────────┘ │ ▼ PANTALLA ACTUALIZADA

¿Qué dispara un re-render?

Solo hay tres motivos por los que React vuelve a renderizar un componente:

DisparadorQué ocurre¿Se puede evitar?
Estado propio (useState, useReducer) Actualizas el estado con setX y el componente se vuelve a renderizar. No (es su propósito). Sí puedes colocar el estado más cerca de donde se usa.
Props que cambian (el padre se re-renderiza) Si el padre renderiza, todos sus hijos renderizan, aunque sus props sean iguales. Sí: memo + referencias estables (lecciones 02 y 03).
Contexto consumido (useContext) Si el value del proveedor cambia, todos los que lo consumen renderizan. Sí: dividir contextos y estabilizar el value.
Analogía: la receta y el plato

La fase de render es leer la receta y calcular mentalmente cómo quedará el plato. La fase de commit es cocinarlo de verdad. Un re-render es "volver a leer la receta": si el plato no cambia, no has malgastado ingredientes. Pero si la receta incluye "picar 1.000 cebollas", releerla sí cuesta tiempo. Por eso el problema nunca es el re-render en sí, sino lo que hay dentro de la función que se re-ejecuta.

La cascada del padre

Este es el concepto que más confunde. React no compara props automáticamente para decidir si un hijo debe renderizar. Cuando el estado de un componente cambia, React renderiza ese componente y todo su subárbol, salvo que algún hijo esté memorizado. Por eso "subir demasiado" un estado provoca que medio árbol se recalcule cuando el usuario solo escribe una letra.

Igualdad referencial

Esta es la frase que debes memorizar: en JavaScript, dos objetos con el mismo contenido no son iguales ({} !== {}, [] !== [], () => {} !== () => {}). Cada render crea objetos y funciones nuevas, y esos valores "nuevos" son los que rompen memorizaciones que parecían razonables.

3 · Ejemplo mínimo

El instrumento de diagnóstico más simple es un console.log en el cuerpo del componente. Ese log se ejecuta una vez por render.

src/components/Contador.jsx
import { useState } from "react";

export default function Contador() {
  const [count, setCount] = useState(0);

  // Se ejecuta en CADA render del componente.
  // No es un efecto: es código que corre durante la fase de render.
  console.log("Contador renderiza. count =", count);

  return (
    <button onClick={() => setCount((c) => c + 1)}>
      Clics: {count}
    </button>
  );
}

Línea por línea:

  1. useState(0): declara un estado local. Cambiarlo es el primer disparador de un render.
  2. console.log(...): corre en cada render. Si haces clic 3 veces y ves 4 líneas (el montaje + 3 cambios), el componente se está re-renderizando como esperas.
  3. onClick con actualización funcional c => c + 1: encola el cambio de estado. React renderiza y luego, al hacer commit, actualiza el texto del botón.

Para no ensuciar la lógica con logs, encapsúlalo en un pequeño hook de desarrollo. Es lo que usaremos en el resto de la lección:

src/hooks/useRenderCount.js
import { useRef } from "react";

// Hook SOLO para desarrollo: cuenta y registra cuántas veces renderiza un componente.
export function useRenderCount(label) {
  // useRef guarda un valor entre renders sin provocar nuevos renders.
  const renders = useRef(0);
  renders.current += 1;

  console.log(`[render] ${label}: ${renders.current}`);
  return renders.current;
}
Mutación durante el render

renders.current += 1 muta un ref durante el render, lo cual no es "puro". Es aceptable en una herramienta de diagnóstico que se elimina del código de producción, pero nunca debería formar parte de la lógica real.

4 · Ejemplo real

Recuperamos el hilo conductor del curso: un panel de productos con buscador. El síntoma es que escribir en el buscador se nota lento. Instrumentamos el árbol para ver qué se re-renderiza.

src/App.jsx
import { useState } from "react";
import { useRenderCount } from "./hooks/useRenderCount.js";
import Header from "./components/Header.jsx";
import Sidebar from "./components/Sidebar.jsx";
import ProductTable from "./components/ProductTable.jsx";

export default function App() {
  useRenderCount("App");

  // ⚠️ El estado vive en la RAÍZ: cualquier letra re-renderiza todo el árbol.
  const [search, setSearch] = useState("");

  return (
    <div className="app">
      <Header />
      <Sidebar />

      <input
        value={search}
        onChange={(e) => setSearch(e.target.value)}
        placeholder="Buscar productos…"
      />

      <ProductTable search={search} />
    </div>
  );
}

Cómo se diagnostica:

  1. Añade useRenderCount("Nombre") a cada componente sospechoso. Al escribir, verás en la consola líneas de Header, Sidebar y ProductTable en cada pulsación de tecla.
  2. Lee el patrón. Si Header y Sidebar no dependen de search, esos re-renders son innecesarios: se debe a que el estado está demasiado arriba.
  3. Confírmalo con el Profiler y Highlight updates. La lección 04 entra a fondo; aquí basta con ver qué componentes se iluminan.
  4. Anota los números. "Escribir 'camiseta' (8 letras) = 8 renders de todo el árbol". Ese es tu punto de partida medible.
Primer arreglo: colocar bien el estado

Antes de memoizar nada, mueve el estado search a un componente SearchSection que solo contenga el input y la tabla. Así Header y Sidebar dejan de re-renderizarse sin escribir ni un solo memo. Colocar el estado suele ser la optimización más barata y la más olvidada.

6 · Errores habituales

Error 1: interpretar mal el doble render de StrictMode

En desarrollo, <StrictMode> monta, desmonta y vuelve a montar cada componente, y llama a las funciones de render dos veces, para detectar efectos impuros. Ver el log dos veces no es un problema de rendimiento.

✘ Incorrecto 
// main.jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import App from "./App.jsx";

// Quitar StrictMode "porque renderiza dos veces" es esconder el síntoma.
createRoot(document.getElementById("root")).render(<App />);
✔ Correcto 
// main.jsx: se conserva StrictMode y se compara contra la build de producción.
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import App from "./App.jsx";

// Compara nº de renders en `pnpm dev` vs `pnpm build && pnpm preview`.
createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>
);

Error 2: medir solo con la app "a ojo"

✘ Incorrecto 
// "Creo que va lento cuando escribo" → me pongo a envolver todo en memo.
// No hay dato, no hay baseline, no hay forma de saber si mejoró.
✔ Correcto 
// 1) Reproduce el problema: escribe "camiseta" con el Profiler grabando.
// 2) Anota el commit más lento y el componente que lo domina.
// 3) Optimiza SOLO eso.
// 4) Repite la grabación y compara los mismos números.

Error 3: confundir re-render con lentitud

✘ Incorrecto 
function Badge({ label }) {
  // Renderiza mucho, pero es trivial: un <span>. Envolverlo en memo
  // solo añade complejidad y una comparación de props por render.
  return <span className="badge">{label}</span>;
}
✔ Correcto 
// Optimiza lo que de verdad cuesta: aquí sí tiene sentido mirar.
function ProductTable({ products }) {
  // Recorrer 1.000 productos y ordenarlos es lo caro.
  const rows = [...products].sort((a, b) => a.name.localeCompare(b.name));
  return <ul>{rows.map((p) => <li key={p.id}>{p.name}</li>)}</ul>;
}

7 · Ejercicio guiado

Vas a construir un escenario con pnpm y medir qué se re-renderiza al escribir en un formulario.

  1. Crea el proyecto. 
    pnpm create vite@latest m11-renders --template react
cd m11-renders
pnpm install
pnpm dev
  2. Añade el hook de diagnóstico en src/hooks/useRenderCount.js (el de la sección 3).
  3. Monta este árbol en src/App.jsx: un Header estático, un input controlado y una Lista que recibe el texto. 
    import { useState } from "react";
import { useRenderCount } from "./hooks/useRenderCount.js";

function Header() {
  useRenderCount("Header");
  return <h1>Mi tienda</h1>;
}

function Lista({ texto }) {
  useRenderCount("Lista");
  const items = Array.from({ length: 500 }, (_, i) => `Producto ${i}`);
  return <ul>{items.map((it) => <li key={it}>{it}</li>)}</ul>;
}

export default function App() {
  useRenderCount("App");
  const [texto, setTexto] = useState("");
  return (
    <>
      <Header />
      <input value={texto} onChange={(e) => setTexto(e.target.value)} />
      <Lista texto={texto} />
    </>
  );
}
  4. Observa el escenario "malo". Escribe 5 letras y cuenta las líneas de cada componente en la consola. Nota que Header se re-renderiza 5 veces sin necesitarlo.
  5. Consulta la lección 04 y graba una sesión con el Profiler. Identifica cuál es el componente que domina el tiempo de commit.
  6. Aplica solo el arreglo de colocación del estado. Mueve texto a un componente SearchSection que envuelva input + Lista. Verifica que Header ya no renderiza al escribir. Anota el antes y el después.
Cierre del ejercicio

Deberías terminar con un número medible: por ejemplo, "8 pulsaciones → antes 8 renders de todo, después 8 renders de SearchSection y Lista, 0 de Header". Eso ya es un diagnóstico completo.

8 · Reto

🎯 Panel de diagnóstico de renders

Construye una herramienta propia que convierta el diagnóstico en un dato visible en pantalla, sin depender del Profiler:

  1. Un hook useRenderStats(name) que registre en un "store" externo (un Map a nivel de módulo) cuántos renders ha hecho cada componente y cuánto tardó el último render (mide con performance.now() alrededor del cálculo del componente).
  2. Una vista <RenderMonitor /> que lea ese store y muestre una tabla ordenada por "más renders" y por "mayor tiempo acumulado".
  3. Detección de estabilidad de props: para un componente elegido, guarda las props del render anterior y muestra en rojo las que cambiaron de referencia aunque tuvieran el mismo contenido.
  4. Antes y después: monta el escenario del ejercicio, captura los números, aplica la colocación del estado y vuelve a capturarlos. Muestra la mejora en pantalla.

Pista: para no provocar renders en el monitor cada vez que se registra un render, mantén el store fuera de React y suscríbete desde la vista con useSyncExternalStore.

9 · Resumen

  • Un re-render es volver a llamar a la función del componente; solo duele si dentro hay trabajo caro.
  • React tiene dos fases: render (puro, calcula) y commit (escribe el DOM).
  • Un componente re-renderiza si cambia su estado, si su padre renderiza o si cambia un contexto que consume.
  • La cascada del padre hace que todo el subárbol renderice: colocar bien el estado es la optimización más barata.
  • La igualdad referencial ({} !== {}) es la raíz de casi toda optimización que "no funciona".
  • Mide antes y después: console.log estratégico, useRenderCount, React DevTools y la build de producción.

10 · Preguntas frecuentes

¿Cada render toca el DOM?

No. React primero calcula el árbol nuevo en memoria (fase de render) y solo en el commit escribe en el DOM las diferencias respecto al árbol anterior. Un re-render sin cambios reales termina en un commit mínimo o incluso vacío.

¿Por qué veo cada log dos veces en desarrollo?

Por <StrictMode>. En desarrollo React monta y desmonta los componentes una vez extra para detectar efectos impuros. Ocurre solo en desarrollo; no es un problema de rendimiento. Compara con pnpm build && pnpm preview.

Si el padre renderiza, ¿el hijo siempre renderiza?

Sí, salvo que el hijo esté memorizado con memo o que React pueda saltarse la rama por otra razón. Esta cascada es intencionada: React no compara props por defecto porque hacerlo costaría más que re-renderizar en muchos casos. Lo veremos en detalle en la lección 02.

¿Merece la pena medir en desarrollo si todo es más lento?

Sirve para localizar la causa (qué componente renderiza de más y por qué). Para decidir si una optimización merece la pena, mide siempre sobre la build de producción, donde los tiempos reflejan lo que verá el usuario.

¿Debo usar console.log o useEffect para contar renders?

Usa código durante el render (un console.log o un ref). Un useEffect sin dependencias cuenta commits, no renders, y no se ejecuta si el render termina en un commit vacío. Para diagnosticar "¿cuántas veces se llama mi función?", quieres el cuerpo del render.
