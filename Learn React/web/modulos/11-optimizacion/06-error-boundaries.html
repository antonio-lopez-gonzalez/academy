Error Boundaries

Módulo 11 · Optimización

1. Introducción

Un Error Boundary es un componente de React que captura errores de JavaScript en cualquier parte de su árbol de hijos, registra esos errores y muestra una interfaz de fallback en lugar del componente que falló.

¿Qué problema resuelve? En React, si un componente lanza una excepción durante el renderizado, el método lifecycle o el constructor, todo el árbol se desmonta. Sin un Error Boundary, un error en un widget insignificante puede romper la aplicación completa y mostrar una pantalla en blanco.

¿Cuándo se utiliza? En puntos de integración de la UI: layouts, paneles independientes, widgets de terceros, secciones de una página que pueden fallar sin afectar al resto.

Error típico: Pensar que un try/catch en el JSX captura errores de render. No es así. try/catch solo funciona en código imperativo, no en el renderizado declarativo de React.

2. Teoría

Los Error Boundaries son componentes de clase que implementan uno o ambos métodos:

  • static getDerivedStateFromError(error) — se ejecuta durante la fase de renderizado. Recibe el error y debe devolver un nuevo estado. Se usa para actualizar el estado y mostrar el fallback.
  • componentDidCatch(error, info) — se ejecuta durante la fase de commit. Recibe el error y un objeto info con componentStack (traza del árbol de componentes). Se usa para logging o reporte de errores.

¿Cómo funciona internamente? Durante el renderizado, React recorre el árbol de componentes. Si un componente lanza una excepción, React busca hacia arriba el Error Boundary más cercano que haya implementado estos métodos. Si lo encuentra, React llama a getDerivedStateFromError para obtener el nuevo estado y luego renderiza el fallback. Si no encuentra ningún Error Boundary, React desmonta todo el árbol y el error se propaga al entorno (console.error o ventana blanca).

React 19: Los Error Boundaries ahora también capturan errores lanzados desde Suspense durante la carga de datos asíncrona. Además, la comunidad está explorando un hook useErrorBoundary() para componentes funcionales, pero aún no es parte del API estable.

3. Ejemplo mínimo

El Error Boundary más pequeño posible. Es un componente de clase que implementa ambos métodos y muestra un mensaje genérico cuando algo falla. 

import { Component } from 'react';

class ErrorBoundary extends Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  // Se ejecuta durante el renderizado: actualiza el estado para mostrar el fallback
  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  // Se ejecuta después del commit: ideal para logging
  componentDidCatch(error, info) {
    console.error('Error capturado:', error, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return <h1>Algo salió mal.</h1>;
    }
    return this.props.children;
  }
}

// Uso
function App() {
  return (
    <ErrorBoundary>
      <BuggyComponent />
    </ErrorBoundary>
  );
}

Línea por línea: El constructor inicializa hasError en false. getDerivedStateFromError recibe el error y devuelve un nuevo estado que marca hasError: true. En el render, si hay error mostramos un mensaje; si no, renderizamos los hijos normalmente.

4. Ejemplo real

Creamos un dashboard con varios widgets independientes. Cada widget está envuelto en su propio Error Boundary. Si un widget de clima falla, el resto del dashboard sigue funcionando. 

import { Component } from 'react';

// Error Boundary reutilizable
class WidgetErrorBoundary extends Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, info) {
    // Enviar el error a un servicio de monitoreo
    console.error('Widget falló:', error.message, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="widget-error">
          <h3>{this.props.fallbackTitle || 'Widget no disponible'}</h3>
          <p>{this.props.fallbackMessage || 'Ocurrió un error al cargar este widget.'}</p>
          <button onClick={() => this.setState({ hasError: false, error: null })}>
            Reintentar
          </button>
        </div>
      );
    }
    return this.props.children;
  }
}

// Componente que puede fallar (simula una API que falla)
function WeatherWidget({ city }) {
  // Lanza error si la ciudad está vacía
  if (!city) {
    throw new Error('Ciudad no especificada');
  }

  return <div>Clima en {city}: 22°C, soleado</div>;
}

// Componente que siempre funciona
function ClockWidget() {
  return <div>{new Date().toLocaleTimeString()}</div>;
}

// Dashboard con múltiples widgets
function Dashboard() {
  return (
    <div className="dashboard">
      <h1>Mi Dashboard</h1>

      <div className="dashboard__grid">
        <WidgetErrorBoundary
          fallbackTitle="Error en el clima"
          fallbackMessage="No pudimos cargar la información del clima."
        >
          <WeatherWidget city="" />
        </WidgetErrorBoundary>

        <WidgetErrorBoundary
          fallbackTitle="Error en el reloj"
        >
          <ClockWidget />
        </WidgetErrorBoundary>
      </div>
    </div>
  );
}

¿Qué pasa aquí? Cuando WeatherWidget recibe una ciudad vacía, lanza un error. El WidgetErrorBoundary lo captura y muestra un mensaje con un botón de reintentar. ClockWidget sigue funcionando porque está en su propio Error Boundary.

5. Buenas prácticas

Qué hacer

  • Usar Error Boundaries en puntos de integración: layouts, secciones independientes, widgets de terceros, paneles del dashboard.
  • Incluir un botón de reintentar: permite al usuario recuperarse del error sin recargar la página.
  • Reportar errores: usa componentDidCatch para enviar la traza a un servicio de monitoreo (Sentry, Datadog, etc.).
  • Personalizar el fallback: muestra un mensaje amigable y útil, no solo "Algo salió mal".
  • Combinar con Suspense: en React 19, los Error Boundaries capturan errores de datos asíncronos dentro de Suspense.

Qué evitar

  • NO usar Error Boundaries para manejo de flujo: no son sustitutos de try/catch para eventos o llamadas asíncronas. Solo capturan errores durante renderizado, lifecycle y constructores.
  • NO envolver todo en un solo Error Boundary: si un error en un widget pequeño oculta toda la app, pierdes el propósito.
  • NO abusar de ellos: cada Error Boundary añade overhead. Úsalos solo donde tengan sentido.
  • NO olvidar el estado inicial: siempre inicializa hasError en false en el constructor.

¿Por qué?

Los Error Boundaries son una red de seguridad, no una muleta. Un buen diseño de componentes debería minimizar los errores de renderizado. Los Error Boundaries existen para asegurar que cuando algo falla inesperadamente, la aplicación no se rompa por completo y el usuario tenga una experiencia controlada.

6. Errores habituales

Error 1: Usar Error Boundaries para capturar errores de eventos

// ❌ Incorrecto: Error Boundary NO captura errores de eventos
function Button() {
  function handleClick() {
    throw new Error('Error en click');
  }

  return <button onClick={handleClick}>Click</button>;
}

// ✅ Correcto: usar try/catch en el manejador
function Button() {
  function handleClick() {
    try {
      // código que puede fallar
      throw new Error('Error en click');
    } catch (error) {
      console.error('Error en evento:', error);
    }
  }

  return <button onClick={handleClick}>Click</button>;
}

Error 2: Envolver toda la app en un solo Error Boundary

// ❌ Incorrecto: un error en cualquier parte oculta toda la app
<ErrorBoundary>
  <App />
</ErrorBoundary>

// ✅ Correcto: Error Boundaries en cada sección independiente
<div>
  <ErrorBoundary>
    <Sidebar />
  </ErrorBoundary>

  <ErrorBoundary>
    <MainContent />
  </ErrorBoundary>

  <ErrorBoundary>
    <WidgetPanel />
  </ErrorBoundary>
</div>

// ❌ Incorrecto: los functional components NO pueden ser Error Boundaries

Error 4: Olvidar resetear el estado del Error Boundary

// ❌ Incorrecto: una vez en error, no hay forma de recuperarse
class ErrorBoundary extends Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  render() {
    if (this.state.hasError) {
      return <h1>Error</h1>;  // No hay botón de reintentar
    }
    return this.props.children;
  }
}

// ✅ Correcto: permitir reintentar
class ErrorBoundary extends Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  handleRetry = () => {
    this.setState({ hasError: false });
  };

  render() {
    if (this.state.hasError) {
      return (
        <div>
          <h1>Error</h1>
          <button onClick={this.handleRetry}>Reintentar</button>
        </div>
      );
    }
    return this.props.children;
  }
}

7. Ejercicio guiado

Vamos a crear un perfil de usuario que carga datos desde una API. Si la API falla, queremos mostrar un mensaje de error sin romper el resto de la aplicación.

Paso 1: Crear el Error Boundary

import { Component } from 'react';

class ProfileErrorBoundary extends Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, info) {
    console.group('Error en perfil');
    console.error('Error:', error.message);
    console.error('Component stack:', info.componentStack);
    console.groupEnd();
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="profile-error">
          <h2>No pudimos cargar el perfil</h2>
          <p>{this.state.error.message}</p>
          <button onClick={() => this.setState({ hasError: false, error: null })}>
            Reintentar
          </button>
        </div>
      );
    }
    return this.props.children;
  }
}

Paso 2: Crear el componente que puede fallar

function UserProfile({ userId }) {
  // Simula una API que falla si el userId es inválido
  if (!userId || userId < 0) {
    throw new Error('ID de usuario inválido: ' + userId);
  }

  const user = {
    id: userId,
    name: 'Ana García',
    email: 'ana@ejemplo.com',
    role: 'Desarrolladora'
  };

  return (
    <div className="profile">
      <h2>{user.name}</h2>
      <p>Email: {user.email}</p>
      <p>Rol: {user.role}</p>
    </div>
  );
}

Paso 3: Usarlo en la aplicación

function App() {
  return (
    <div className="app">
      <header>
        <h1>Mi Aplicación</h1>
        <nav>{/* Navegación que siempre funciona */}</nav>
      </header>

      <main>
        <ProfileErrorBoundary>
          <UserProfile userId={-1} />
        </ProfileErrorBoundary>

        <section className="other-content">
          <h2>Otra sección</h2>
          <p>Este contenido no se ve afectado por el error del perfil.</p>
        </section>
      </main>
    </div>
  );
}

Paso 4: Probar

  1. Renderiza la app — verás el perfil fallar pero el resto intacto.
  2. Haz clic en "Reintentar" — el Error Boundary resetea su estado y React vuelve a renderizar UserProfile, que volverá a fallar (porque userId sigue siendo -1).
  3. Cambia userId a 1 — ahora el perfil se carga correctamente.

8. Reto

Crea un componente ApiErrorBoundary genérico que reciba una prop onReset y un fallback personalizado (un componente React). El componente debe:

  1. Capturar errores de componentes hijos.
  2. Usar componentDidCatch para logging.
  3. Renderizar el fallback recibido como prop cuando haya error, pasándole el error y una función onRetry.
  4. Al hacer clic en reintentar, llamar a onReset (si existe) y resetear el estado.

Bonus: Úsalo con Suspense y un componente lazy que falle intencionalmente (simula un chunk que no se carga). Observa que en React 19 el Error Boundary captura el error asíncrono de Suspense.

9. Resumen

  • Error Boundary: componente de clase que captura errores en su árbol hijo durante renderizado, lifecycle y constructores.
  • Métodos clave: static getDerivedStateFromError(error) (actualiza estado) y componentDidCatch(error, info) (logging).
  • Solo clase: los componentes funcionales no pueden ser Error Boundaries de forma nativa. Alternativa: react-error-boundary.
  • React 19: los Error Boundaries también capturan errores de Suspense (data fetching asíncrono).
  • Buenas prácticas: envolver secciones independientes, incluir botón de reintentar, reportar errores, personalizar fallback.
  • No abusar: solo en puntos de integración. No sustituyen try/catch para eventos ni manejo de flujo normal.

10. Preguntas frecuentes

¿Puedo usar un Error Boundary para capturar errores en eventos (onClick, onChange)?
No. Los Error Boundaries solo capturan errores durante renderizado, lifecycle y constructores. Los errores en eventos debes manejarlos con try/catch.
¿Por qué los Error Boundaries tienen que ser componentes de clase?
Porque React expone getDerivedStateFromError y componentDidCatch solo en el API de clases. No hay equivalente en hooks. Existe la librería react-error-boundary que provee un wrapper funcional.
¿Cuántos Error Boundaries debería tener en mi aplicación?
Depende del tamaño. Como regla general, uno por layout, uno por sección independiente del dashboard, y uno global como red de seguridad. Normalmente entre 3 y 10 en una app mediana.
¿Un Error Boundary puede capturar errores de sí mismo?
No. Solo captura errores de sus hijos. Si el propio Error Boundary lanza un error, ese error se propaga al Error Boundary padre (o se rompe la app si no hay ninguno).
¿Qué pasa con los errores asíncronos (fetch, setTimeout)?
Los Error Boundaries no los capturan directamente. Sin embargo, en React 19, si un error ocurre dentro de un componente Suspense durante la carga de datos (por ejemplo, una promesa que se rechaza), el Error Boundary sí lo captura.
¿Hay alguna alternativa para componentes funcionales?
Sí, la librería react-error-boundary proporciona un componente ErrorBoundary que funciona con functional components y hooks. También se está explorando un hook useErrorBoundary() en React 19, pero aún no es estable.
¿Debo enviar todos los errores capturados a un servicio externo?
Sí, es buena práctica. Usa componentDidCatch para enviar el error y el componentStack a servicios como Sentry, Datadog o LogRocket. Esto te permite monitorizar errores en producción.
¿Qué datos contiene info.componentStack?
Contiene la traza del árbol de componentes desde el Error Boundary hasta el componente que falló. Es útil para identificar dónde ocurrió el error, pero no incluye el stack trace de JavaScript (eso está en error.stack).
