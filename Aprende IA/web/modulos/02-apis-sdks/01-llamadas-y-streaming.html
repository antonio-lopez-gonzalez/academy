Llamadas y streaming

Módulo 2 · APIs y SDKs 🕐 30 minutos

1 · Introducción

Una llamada a un LLM parece trivial: le mandas un texto, te devuelve otro. Pero entre esas dos cosas hay una petición HTTP, una cola de tokens que el modelo genera uno a uno y una respuesta que puede tardar segundos. Si tu interfaz se queda congelada esperando la respuesta completa, la sensación es de lentitud aunque el modelo vaya rápido. El streaming es la técnica que convierte esa espera en texto que aparece en pantalla.

En esta lección verás la anatomía de una llamada (modelo, mensajes, options), cómo funciona el streaming token a token, cómo cancelar una generación a medias y cómo poner timeouts para no colgar tu programa. Es la base sobre la que se apoya todo lo demás del módulo: sin entender la llamada, el resto es copiar y pegar.

¿Por qué existe esta lección? Porque casi todas las decisiones raras de las apps de IA («¿por qué tarda?», «¿por qué se queda colgado?», «¿por qué el usuario cree que no funciona?») se explican aquí. Latencia, cancelación y timeouts son ingeniería, no detalles.

Local primero: todos los ejemplos corren contra Ollama en tu máquina, sin API key. Donde el código cambie para OpenAI/Anthropic lo verás indicado con un callout.

2 · Teoría

Anatomía de una llamada

Toda llamada a un LLM, sea local o en la nube, tiene la misma forma lógica. Cambia el nombre del campo, pero no la idea:

ParámetroQué esPor qué importa
modelQué modelo usas (p. ej. llama3.2)Determina calidad, velocidad, coste y si cabe en tu máquina
messagesLista de turnos con role (system, user, assistant)Es el contexto que ve el modelo en cada llamada
optionsControles de sampling: temperature, num_predict, etc.Ajustan creatividad y longitud máxima de la respuesta
streamSi quieres la respuesta completa o troceadaCambia la experiencia de usuario y cómo consumes la API

Analogía: una llamada sin streaming es pedir una pizza y esperar sentado hasta que esté entera para comer. Una llamada con streaming es comer por raciones que te van saliendo de la cocina. Tarda lo mismo en total, pero la experiencia es completamente distinta.

El modelo no «responde de golpe»

Por dentro, un LLM genera la respuesta token a token: predice el siguiente fragmento, lo añade, y con eso predice el siguiente. La API normalmente acumula todo y te lo devuelve al final. El streaming expone ese goteo tal cual ocurre.

  petición ──► [ modelo genera token 1 ] ──► token 2 ──► token 3 ──► … ──► done
                    │
       sin stream  │  esperas… esperas… esperas… y recibes TODO de golpe
       con stream  │  recibes: "La" → " respuesta" → " es" → … según se generan

Por eso hay dos latencias distintas que conviene no confundir (lo mediremos en la lección 4):

  • TTFT (Time To First Token): cuánto tardas en ver el primer trozo. Depende sobre todo de la carga del modelo y del tamaño del prompt.
  • Latencia total: cuánto tardas en tener toda la respuesta. Depende del número de tokens generados.

Por qué el streaming mejora la percepción

Con TTFT de 600 ms y una respuesta de 8 segundos, la interfaz bloqueada parece «colgada» 8 segundos. Con streaming, a los 600 ms ya hay texto y el usuario percibe inmediatez. La velocidad real no cambió; cambió lo que el usuario ve.

En una CLI o una web, el primer token es tu mejor indicador de salud. Si aparece rápido, el usuario confía; si no aparece nada, piensa que se rompió. El streaming no es estética: es gestión de expectativas.

Cancelación y timeouts: que tu programa no se quede colgado

Un stream es un iterador: tú decides cuándo dejas de leerlo. Salir del bucle cancela la generación (dejas de consumir). Además, conviene poner un timeout de conexión y un deadline propio por si el modelo se atasca:

  • Timeout de socket: corta si no hay bytes durante demasiado tiempo.
  • Deadline lógico: «no quiero esperar más de N segundos en total», lo compruebas tú con un reloj.

No confundas num_predict (cuántos tokens puede generar como máximo) con un timeout. Un modelo lento puede tardar 30 s en 50 tokens; un límite de tokens no te protege del tiempo, y un timeout no te protege del coste.

3 · Ejemplo mínimo

El ejemplo más pequeño que demuestra el streaming contra Ollama. Fíjate en stream=True y en que la respuesta ya no es un objeto único, sino un iterador.

ejemplos/stream_minimo.py
# stream_minimo.py — la llamada más pequeña con streaming.
from ollama import Client

client = Client()  # por defecto apunta a http://localhost:11434

# stream=True NO devuelve una respuesta, devuelve un iterador de fragmentos.
stream = client.chat(
    model="llama3.2",
    messages=[{"role": "user", "content": "Explica en dos frases qué es un token."}],
    options={"temperature": 0.2},   # 0 = determinista, valores altos = más variado
    stream=True,
)

# Iteramos: cada 'part' trae un trocito de texto en part.message.content.
for part in stream:
    print(part.message.content or "", end="", flush=True)  # sin salto, sin esperar

print()  # un salto final al terminar la respuesta

Salida esperada (varía según el modelo): el texto aparece poco a poco en la terminal.

Un token es la unidad mínima de texto que procesa un modelo: puede ser una palabra, parte de ella o un signo. El modelo no lee letras, lee tokens.

Línea por línea:

  1. Client(): crea el cliente apuntando al servidor local. No hay clave de API porque el modelo corre en tu máquina.
  2. stream=True: cambia el contrato. En vez de esperar la respuesta completa, recibes un iterador de fragmentos.
  3. options={"temperature": 0.2}: controla el sampling. Baja temperatura = respuestas más estables y repetibles (útil para tareas técnicas).
  4. for part in stream: aquí está la magia. Cada iteración bloquea solo hasta el siguiente trocito, no hasta el final.
  5. end="", flush=True: evita el salto de línea y fuerza a Python a volcar el texto al instante. Sin flush, puede quedar en un búfer y parecer que no se escribe nada.
  6. or "": el fragmento final a veces trae contenido vacío (None); lo normalizamos para no imprimir None.

Nube como alternativa: con OpenAI el patrón es el mismo, cambia el nombre. client.chat.completions.create(..., stream=True) y dentro del bucle chunk.choices[0].delta.content or "".

4 · Ejemplo real

El Copiloto (el asistente que responde sobre los cursos de la Academy) muestra la respuesta en una CLI. Queremos tres cosas: ver el primer token cuanto antes, mostrar cuánto tardó, y poder cortar con un deadline. Todo con código determinista alrededor de la inferencia.

src/copiloto/llm.py — stream_response()
# src/copiloto/llm.py
from __future__ import annotations

import time
from dataclasses import dataclass

from ollama import Client

DEFAULT_MODEL = "llama3.2"


@dataclass
class StreamStats:
    """Métricas de una generación. Medir siempre, aunque sea barato."""

    ttft_ms: float          # tiempo hasta el primer token
    total_ms: float         # tiempo total de la respuesta
    chunks: int             # nº de fragmentos recibidos (≈ tokens generados)
    cancelled: bool         # ¿cortamos antes de terminar?


def stream_response(
    messages: list[dict[str, str]],
    *,
    model: str = DEFAULT_MODEL,
    max_seconds: float = 30.0,   # deadline lógico propio
) -> StreamStats:
    """Genera una respuesta por streaming con deadline y métricas."""
    client = Client()
    t0 = time.perf_counter()
    first: float | None = None
    chunks = 0
    cancelled = False

    stream = client.chat(model=model, messages=messages, stream=True)
    for part in stream:
        # 1) Deadline: código nuestro, NO del modelo. Cortamos si nos pasamos.
        if time.perf_counter() - t0 > max_seconds:
            cancelled = True
            break   # salir del bucle deja de consumir el stream (cancela)

        text = part.message.content or ""
        if not text:
            continue

        # 2) Medimos solo la primera vez: ahí está el TTFT.
        if first is None:
            first = time.perf_counter() - t0

        chunks += 1
        print(text, end="", flush=True)   # la UI reacciona ya

    total = time.perf_counter() - t0
    print()
    return StreamStats(
        ttft_ms=(first or 0.0) * 1000,
        total_ms=total * 1000,
        chunks=chunks,
        cancelled=cancelled,
    )

Decisiones y porqués:

  • Deadline con time.perf_counter(): es un reloj monótono, ideal para medir intervalos. El deadline es nuestra lógica determinista; el modelo no lo conoce.
  • break = cancelar: dejar de iterar el stream corta la generación. No necesitas una llamada especial de cancelación en el caso simple.
  • Medir TTFT y total: son las dos cifras que explicarás en la lección 4. Aquí solo las capturamos.
  • @dataclass: agrupar métricas evita pasar cinco variables sueltas y hace el resultado inspeccionable y testeable.

El Copiloto imprimirá cada token según llega (percepción de velocidad) y devolverá un StreamStats que luego se registra y se evalúa. Esta mezcla —UI reactiva + métricas— es exactamente lo que separa un juguete de una herramienta.

5 · Buenas prácticas

HazEvitaPor qué
Usar stream=True en cualquier UI interactiva Bloquear la interfaz hasta la respuesta completa El primer token es tu mejor señal de que todo va bien
flush=True en cada escritura Confiar en el búfer por defecto Sin flush, el texto puede quedar retenido y parecer «colgado»
Poner un deadline propio además del timeout de red Un único timeout enorme «por si acaso» Proteges tiempo y coste con dos límites distintos
Medir TTFT y total desde el principio Optimizar «a ojo» sin números Sin medir no sabes si el problema es el modelo, la red o tu código
Normalizar fragmentos vacíos (or "") Asumir que content siempre es str El chunk final suele venir vacío o None
Guardar la respuesta ensamblada para evaluar/log Desechar el texto porque solo lo «pintaste» Necesitas la respuesta completa para trazas y evals

6 · Errores habituales

Esperar la respuesta completa «porque es más simple»

Mal
antipatron/blocking.py
# ❌ Sin streaming: la UI no muestra NADA hasta que termina.
response = client.chat(model="llama3.2", messages=messages)
print(response.message.content)   # aparece de golpe tras 8 segundos
Bien
correcto/streaming.py
# ✅ Con streaming: el texto aparece desde el primer token.
for part in client.chat(model="llama3.2", messages=messages, stream=True):
    print(part.message.content or "", end="", flush=True)
print()

Olvidar flush y creer que no funciona

Mal 
# ❌ Sin flush, Python puede acumular en búfer. En scripts largos
#    parece que la respuesta no llega aunque el modelo ya generó texto.
for part in stream:
    print(part.message.content or "", end="")
Bien 
# ✅ flush=True fuerza a escribir en pantalla en cada fragmento.
for part in stream:
    print(part.message.content or "", end="", flush=True)

Usar un timeout gigante en vez de uno razonable

Mal 
# ❌ "timeout": 9999 no protege: si algo se atasca, esperas 2h47m.
client = Client(host="http://localhost:11434", timeout=9999)
Bien 
# ✅ Timeout corto de red + deadline lógico de negocio separados.
client = Client(host="http://localhost:11434", timeout=5.0)  # seg de socket

deadline = time.monotonic() + 30.0   # tope de negocio
for part in stream:
    if time.monotonic() > deadline:
        break

Capturar una excepción a mitad de stream y perder lo ya escrito

Mal 
# ❌ Si algo falla a mitad, tiramos TODO el texto parcial a la basura.
buffer = ""
for part in stream:
    buffer += part.message.content or ""
print(buffer)   # si el bucle peta, no se ha mostrado nada
Bien 
# ✅ Acumula Y muestra según llega; el parcial nunca se pierde.
buffer = ""
try:
    for part in stream:
        text = part.message.content or ""
        buffer += text
        print(text, end="", flush=True)
except Exception as exc:
    print(f"\n[interrumpido tras {len(buffer)} caracteres: {exc}]")

7 · Ejercicio guiado

Objetivo: medir el TTFT y la latencia total de una respuesta con streaming, con tu propio código.

  1. Paso 1 — Entorno. Confirma que Ollama está corriendo y tienes un modelo: 
    ollama list
ollama run llama3.2 "hola"   # si no lo tienes: ollama pull llama3.2
  2. Paso 2 — Crea el script. Guarda esto como medir_stream.py: 
    import time
from ollama import Client

client = Client()
messages = [{"role": "user", "content": "Cuenta del 1 al 20, solo los números."}]

t0 = time.perf_counter()
first = None
n = 0
texto = []
for part in client.chat(model="llama3.2", messages=messages, stream=True):
    piece = part.message.content or ""
    if not piece:
        continue
    if first is None:
        first = time.perf_counter() - t0
    n += 1
    texto.append(piece)
    print(piece, end="", flush=True)

total = time.perf_counter() - t0
print()
print(f"TTFT: {first*1000:.0f} ms | total: {total*1000:.0f} ms | chunks: {n}")
print(f"tokens/s ≈ {n / total:.1f}")
  3. Paso 3 — Ejecuta y observa. 
    uv run medir_stream.py

    Resultado esperado: el texto aparece progresivamente y al final una línea con TTFT, total, número de fragmentos y tokens por segundo aproximados. El TTFT suele ser bastante mayor que el tiempo por token: por eso el streaming «se siente» rápido.

  4. Paso 4 — Compara. Cambia el prompt por uno de 200 palabras y repite. Observa que el TTFT apenas cambia pero el total crece: estás generando más tokens.
  5. Paso 5 — Verificación. Añade max_seconds=3.0 (o un if time.perf_counter() - t0 > 3: break) y confirma que la generación se corta y no esperas indefinidamente.

8 · Reto

🎯 Streaming cancelable desde el teclado

Construye una pequeña CLI del Copiloto que haga streaming de la respuesta, imprima el TTFT al primer token y permita cancelar la generación pulsando Ctrl+C sin perder lo ya generado. Al cancelar debe imprimir un resumen con los caracteres recibidos y si la cancelación fue del usuario o por deadline.

Pista: captura KeyboardInterrupt alrededor del bucle y guarda el texto acumulado antes de salir. Para no bloquear el hilo principal, mira cómo leer la entrada en otro hilo o usa una señal simple; no necesitas nada sofisticado, solo que el bucle pueda detenerse de forma limpia.

9 · Resumen

  • Una llamada a un LLM siempre lleva modelo, mensajes y opciones; el streaming solo cambia cómo recibes la respuesta.
  • El modelo genera token a token; el streaming expone ese goteo y mejora la latencia percibida.
  • Hay dos latencias: TTFT (hasta el primer token) y total (hasta el último). Mídelas, no las adivines.
  • Cancelar es dejar de iterar el stream; un deadline propio protege el tiempo de negocio y un timeout de red protege la conexión.
  • flush=True es obligatorio en cualquier salida interactiva: sin él, puede parecer que no se escribe nada.
  • Siempre acumula el texto completo aunque lo muestres por trozos: lo necesitarás para trazas y evals.

10 · Preguntas frecuentes

¿El streaming hace que el modelo responda más rápido?

No. Tarda lo mismo en generar la respuesta completa. Lo que cambia es cuándo ves el resultado: empiezas a ver texto desde el primer token en vez de esperar al último. Mejora la latencia percibida, no la real.

¿Puedo hacer streaming y a la vez pedir salida estructurada (JSON)?

Sí, pero combínalo con cuidado: el JSON solo es válido cuando termina. Puedes mostrar el progreso crudo y, al acabar, validar el texto completo con pydantic. Si la salida debe ser JSON estricto, a menudo interesa más la respuesta completa que el streaming (lo verás en el módulo 1, lección de salida estructurada).

¿Cómo cancelo de verdad una generación en la nube?

Salir del iterador cierra la conexión y el servidor deja de enviarte datos. Los SDKs suelen exponer un gestor de contexto (with client.chat.completions.stream(...) en OpenAI) que al salir cierra el stream de forma ordenada. Para cancelación cooperativa desde otra parte de tu app, guarda una referencia al stream y ciérralo o rompe el bucle.

¿Qué timeout elijo?

Depende de la tarea, pero un punto de partida sano: timeout de red corto (5-10 s) para detectar conexiones muertas y un deadline de negocio (15-60 s) según cuánto estás dispuesto a esperar. Mídelo con datos reales antes de fijarlo.

¿num_predict es lo mismo que un límite de tiempo?

No. num_predict limita cuántos tokens puede generar el modelo como máximo. Ahorra coste y evita respuestas eternas, pero no garantiza tiempo: 50 tokens de un modelo cargado pueden tardar mucho. Para el tiempo necesitas timeout y/o deadline.
