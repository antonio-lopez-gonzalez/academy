Tool / function calling

Módulo 2 · APIs y SDKs 🕐 35 minutos

1 · Introducción

Un LLM solo predice texto. No puede consultar tu base de datos, mirar la hora ni ejecutar código. Pero hay un truco que cambia todo: le enseñas una lista de herramientas («funciones») y, cuando cree que necesita una, no la ejecuta; en su lugar responde con un nombre de función y unos argumentos. Tu código lee esa propuesta, ejecuta la función de verdad y le devuelve el resultado. El modelo continúa la conversación con información nueva.

Esto es tool calling (o function calling). Es el puente entre la inferencia (lo que el modelo decide) y la lógica determinista (lo que tu código hace). Sin él no hay agentes, ni RAG con búsqueda, ni nada que toque el mundo real.

¿Por qué existe esta lección? Porque el malentendido más común es creer que «el modelo ejecuta funciones». No lo hace, y no puede. El modelo propone; tú ejecutas. Tener clarísimo ese reparto es lo que te permite construir, depurar y asegurar agentes.

Local primero: los ejemplos usan Ollama con un modelo que soporte tools (p. ej. llama3.2 o qwen2.5). El mismo patrón, con otro nombre de campo, aplica a OpenAI y Anthropic.

2 · Teoría

El reparto de responsabilidades

Grábate esto: el modelo decide, tú haces. El ciclo tiene cuatro piezas:

PiezaQuiénQué hace
Declaración de toolsTu códigoDescribe nombre, propósito y esquema de argumentos en JSON Schema
Propuesta de llamadaEl modeloDevuelve tool_calls: nombre + argumentos (en texto/JSON)
EjecuciónTu códigoValida los argumentos y llama a la función real
ResultadoTu códigoAñade un mensaje role="tool" con el resultado y vuelve a llamar

Analogía: el modelo es un cliente en un restaurante que pide «un solomillo al punto». El camarero (tu código) es quien va a la cocina, comprueba que hay solomillo y lo trae. El cliente no entra en la cocina: solo elige del menú. La carta es el JSON Schema: define qué se puede pedir.

El esquema: la carta de herramientas

Cada tool se describe con JSON Schema. Lo mínimo es un nombre, una descripción y los parámetros con sus tipos. La descripción es para el modelo, así que escríbela pensando en él:

tools_example.json
{
  "type": "function",
  "function": {
    "name": "search_lessons",
    "description": "Busca lecciones del curso por una consulta de texto y devuelve las más relevantes.",
    "parameters": {
      "type": "object",
      "properties": {
        "query": {
          "type": "string",
          "description": "Términos de búsqueda, en lenguaje natural."
        },
        "limit": {
          "type": "integer",
          "description": "Número máximo de resultados (1-10).",
          "minimum": 1,
          "maximum": 10
        }
      },
      "required": ["query"]
    }
  }
}

Fíjate en required y en minimum/maximum: los límites en el esquema guían al modelo, pero no lo obligan. Validarás los argumentos en tu código de todos modos (esa es la parte determinista).

El bucle mínimo de una herramienta

La conversación crece en cada vuelta. Este es el ciclo, con los mensajes que se van añadiendo:

  messages = [ user: "¿Cuántas lecciones tiene el módulo 2?" ]
        │
        ▼
  [ modelo ] ──► assistant.tool_calls = [ { name: "search_lessons",
                                             arguments: { "query": "módulo 2 lecciones" } } ]
        │
        ▼  TU CÓDIGO: valida argumentos → ejecuta → obtiene "4 lecciones"
        │
  messages += assistant(tool_calls)
  messages += { role: "tool", content: "4 lecciones", tool_name: "search_lessons" }
        │
        ▼
  [ modelo ] ──► assistant.content = "El módulo 2 tiene 4 lecciones."
        │
        ▼
      FIN (stop_reason sin tool_calls)

El bucle es lo que hace un agente. Aquí verás una sola herramienta y pocas vueltas. En el módulo 5 el bucle se generaliza (varias tools, memoria, límite de iteraciones) y en el 6 se expone por MCP. El corazón, sin embargo, es este.

3 · Ejemplo mínimo

La forma más corta en Ollama: defines una función Python con anotaciones de tipo y docstring estilo Google, y la librería la convierte en tool. Tú ejecutas la función cuando el modelo la pide.

ejemplos/tool_minimo.py
# tool_minimo.py — una sola herramienta, un solo turno de ejecución.
from ollama import Client


def add_two_numbers(a: int, b: int) -> int:
    """Suma dos números.

    Args:
        a: Primer número.
        b: Segundo número.

    Returns:
        La suma de a y b.
    """
    return int(a) + int(b)


client = Client()

# 1) Enviamos la pregunta Y la herramienta disponible.
response = client.chat(
    model="llama3.2",
    messages=[{"role": "user", "content": "¿Cuánto es 30 + 12?"}],
    tools=[add_two_numbers],   # la función se convierte en tool (JSON Schema)
)

# 2) El modelo NO ha sumado: ha PROPUESTO llamar a la herramienta.
if response.message.tool_calls:
    call = response.message.tool_calls[0]
    name = call.function.name                 # "add_two_numbers"
    args = call.function.arguments            # {"a": 30, "b": 12}
    print(f"El modelo propone: {name}({args})")

    # 3) La ejecución la hacemos NOSOTROS (código determinista).
    result = add_two_numbers(**args)
    print(f"Resultado real: {result}")
else:
    print("El modelo respondió directamente:", response.message.content)

Salida esperada:

El modelo propone: add_two_numbers({'a': 30, 'b': 12})
Resultado real: 42

Línea por línea:

  1. def add_two_numbers(a: int, b: int) -&gt; int: las anotaciones de tipo definen los tipos del esquema (integer).
  2. Docstring Google: la sección Args: describe cada parámetro. Todo eso se convierte en la carta que ve el modelo.
  3. tools=[add_two_numbers]: pasamos la función, no una llamada. La librería la traduce a JSON Schema.
  4. response.message.tool_calls: si viene lleno, el modelo quiere ejecutar algo. Puede venir vacío y responder en texto.
  5. call.function.arguments: un diccionario ya parseado. En otros SDKs llega como string JSON y debes hacer json.loads.
  6. add_two_numbers(**args): aquí está la verdad. Lo que suma es tu código, no el modelo.

Este ejemplo muestra una vuelta: no devolvemos el resultado al modelo para que responda con palabras. El siguiente ejemplo añade ese paso y ya tienes el bucle completo.

4 · Ejemplo real

En el Copiloto, la primera herramienta útil es search_lessons: dado un texto, devuelve las lecciones más relevantes de la Academy. Aquí usamos el esquema explícito y un dispatcher, porque tener el control total del JSON Schema es lo que harás en producción.

src/copiloto/tools.py
# src/copiloto/tools.py
from __future__ import annotations

import json
from collections.abc import Callable
from typing import Any

# Catálogo simulado de lecciones (en el módulo 4 será un índice real con embeddings).
LESSONS = [
    {"id": "02-01", "title": "Llamadas y streaming", "module": "02"},
    {"id": "02-02", "title": "Tool / function calling", "module": "02"},
    {"id": "02-03", "title": "Multiproveedor y errores", "module": "02"},
    {"id": "02-04", "title": "Coste, latencia y tokens", "module": "02"},
]


def search_lessons(query: str, limit: int = 5) -> list[dict[str, str]]:
    """Devuelve lecciones cuyo título contenga algún término de la query."""
    terms = [t.lower() for t in query.split() if t]
    hits = [ls for ls in LESSONS if any(t in ls["title"].lower() for t in terms)]
    return hits[: max(1, min(limit, 10))]


# El esquema que ve el modelo. Descripción clara = mejores llamadas.
SEARCH_LESSONS_SCHEMA: dict[str, Any] = {
    "type": "function",
    "function": {
        "name": "search_lessons",
        "description": "Busca lecciones del curso por texto y devuelve las más relevantes.",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "Términos de búsqueda."},
                "limit": {
                    "type": "integer",
                    "description": "Máximo de resultados (1-10).",
                    "minimum": 1,
                    "maximum": 10,
                },
            },
            "required": ["query"],
        },
    },
}

# El dispatcher: nombre → función Python real. Es nuestro, no del modelo.
HANDLERS: dict[str, Callable[..., Any]] = {
    "search_lessons": search_lessons,
}


def run_tool(name: str, arguments: str | dict[str, Any]) -> str:
    """Ejecuta una tool propuesta por el modelo y devuelve el resultado como texto."""
    if name not in HANDLERS:
        return json.dumps({"error": f"tool desconocida: {name}"})

    args = json.loads(arguments) if isinstance(arguments, str) else arguments
    try:
        result = HANDLERS[name](**args)          # validación + ejecución
        return json.dumps(result, ensure_ascii=False)
    except (TypeError, ValueError) as exc:
        # Devolvemos el ERROR al modelo para que pueda corregir su llamada.
        return json.dumps({"error": str(exc)})
src/copiloto/agent.py — bucle con una tool
# src/copiloto/agent.py
from __future__ import annotations

from ollama import Client

from copiloto.tools import SEARCH_LESSONS_SCHEMA, run_tool

MODEL = "llama3.2"
MAX_STEPS = 4   # cinturón de seguridad: nunca dejamos el bucle sin límite


def answer_with_tools(question: str) -> str:
    client = Client()
    messages: list[dict] = [
        {"role": "system", "content": "Eres el Copiloto de la Academy. Usa las tools cuando aporten datos."},
        {"role": "user", "content": question},
    ]

    for _ in range(MAX_STEPS):
        response = client.chat(model=MODEL, messages=messages, tools=[SEARCH_LESSONS_SCHEMA])
        msg = response.message

        # Caso A: ya no pide tools → respuesta final en lenguaje natural.
        if not msg.tool_calls:
            return msg.content or ""

        # Caso B: pidió tools → las ejecutamos TODAS y devolvemos los resultados.
        messages.append({"role": "assistant", "content": msg.content or "", "tool_calls": msg.tool_calls})
        for call in msg.tool_calls:
            result = run_tool(call.function.name, call.function.arguments)
            messages.append({
                "role": "tool",
                "content": result,
                "tool_name": call.function.name,
            })

    return "No pude cerrar la respuesta dentro del límite de pasos."

Decisiones y porqués:

  • Esquema explícito + HANDLERS: en producción casi nunca pasas la función cruda; prefieres el esquema a la vista y un mapa nombre→función. Así controlas qué es ejecutable y qué no.
  • run_tool devuelve texto, incluso el error: el modelo necesita leer el resultado. Devolverle un error útil (no lanzar la excepción) le permite corregir sus argumentos.
  • MAX_STEPS: nunca un bucle while True. Un límite de iteraciones te salva de bucles infinitos, de coste desbocado y de cuelgues.
  • Se ejecutan todas las tool_calls: los modelos modernos pueden pedir varias a la vez; ignorar la segunda rompería el protocolo.

Nube como alternativa: en OpenAI el esquema es el mismo pero envuelto en tools=[{"type": "function", "function": …}] y los argumentos llegan como string en tool_call.function.arguments; en Anthropic se llama input_schema y el resultado se devuelve en un bloque tool_result con tool_use_id.

5 · Buenas prácticas

HazEvitaPor qué
Descripciones claras y en imperativo («Busca…», «Devuelve…») Nombres crípticos o descripciones vacías El modelo elige la tool por la descripción; es documentación para él
Pocas tools, bien separadas Una tool «haz_cualquier_cosa» Demasiadas opciones solapadas confunden la selección
Validar los argumentos en tu código Confiar en que el modelo acierta el esquema El esquema orienta, no garantiza; tú eres la última línea
Devolver el resultado como texto/JSON pequeño Volcar 10 MB de datos en content Todo lo que devuelves entra en el contexto y cuesta tokens
Límite de iteraciones + timeout while True hasta que el modelo pare Un bucle sin tope es una factura y un cuelgue esperando a pasar
Devolver errores útiles al modelo Lanzar la excepción y matar la conversación El modelo puede reintentar con argumentos corregidos

6 · Errores habituales

Creer que el modelo ejecuta la función

Mal 
# ❌ "El modelo ya habrá sumado; leo el resultado del texto."
response = client.chat(model="llama3.2", messages=messages, tools=[add_two_numbers])
# ...y si tool_calls existe, NO sumó: solo propuso. Además, sin ejecutar nada,
# el modelo no sabe el resultado y puede inventárselo (alucinación).
Bien 
# ✅ El modelo propone; tú ejecutas y devuelves el resultado.
if response.message.tool_calls:
    call = response.message.tool_calls[0]
    result = add_two_numbers(**call.function.arguments)
    # ... y devuelves 'result' al modelo en un mensaje role="tool".

No devolver el resultado al modelo

Mal 
# ❌ Ejecutas la tool pero cortas el bucle: el usuario no ve la respuesta.
for call in response.message.tool_calls:
    run_tool(call.function.name, call.function.arguments)
print(response.message.content)   # vacío: el modelo aún no ha hablado
Bien 
# ✅ Añades el resultado y vuelves a llamar para que el modelo redacte.
messages.append(result_as_tool_message)
final = client.chat(model=model, messages=messages, tools=[schema])
print(final.message.content)

Bucle sin límite

Mal 
# ❌ El modelo puede pedir tools indefinidamente: factura y cuelgue.
while True:
    response = client.chat(model=model, messages=messages, tools=tools)
    if not response.message.tool_calls:
        break
    # ...
Bien 
# ✅ Tope duro de iteraciones, siempre.
for _ in range(MAX_STEPS):
    response = client.chat(model=model, messages=messages, tools=tools)
    if not response.message.tool_calls:
        break
    # ...
else:
    return "No pude cerrar la respuesta dentro del límite de pasos."

Comparar argumentos del modelo sin validarlos

Mal 
# ❌ Confías en el esquema y usas los argumentos tal cual.
#    El modelo puede mandar limit=99 o query=123 aunque no toque.
hits = search_lessons(**call.function.arguments)
Bien 
# ✅ Valida (pydantic o a mano) antes de tocar tu sistema.
from pydantic import BaseModel, Field

class SearchArgs(BaseModel):
    query: str = Field(min_length=1)
    limit: int = Field(default=5, ge=1, le=10)

hits = search_lessons(**SearchArgs.model_validate(call.function.arguments).model_dump())

7 · Ejercicio guiado

Objetivo: cerrar el bucle completo —el modelo pide una tool, tú la ejecutas y devuelves el resultado— partiendo del ejemplo mínimo.

  1. Paso 1 — Punto de partida. Guarda el tool_minimo.py de la sección 3 y confirma que el modelo propone las tools (no que responde en texto). Si tu modelo no soporta tools, cambia a qwen2.5 o llama3.2.
  2. Paso 2 — Añade el resultado y vuelve a llamar. Completa el script así: 
    import json
from ollama import Client

def add_two_numbers(a: int, b: int) -> int:
    """Suma dos números.

    Args:
        a: Primer número.
        b: Segundo número.

    Returns:
        La suma de a y b.
    """
    return int(a) + int(b)

client = Client()
messages = [{"role": "user", "content": "¿Cuánto es 30 + 12? Después explica el resultado."}]
tools = [add_two_numbers]

for step in range(4):
    response = client.chat(model="llama3.2", messages=messages, tools=tools)
    msg = response.message

    if not msg.tool_calls:
        print("FINAL:", msg.content)
        break

    messages.append({"role": "assistant", "content": msg.content or "", "tool_calls": msg.tool_calls})
    for call in msg.tool_calls:
        args = call.function.arguments
        result = add_two_numbers(**args)
        messages.append({
            "role": "tool",
            "content": json.dumps({"result": result}),
            "tool_name": call.function.name,
        })
        print(f"[tool] {call.function.name}({args}) -> {result}")
  3. Paso 3 — Ejecuta. 
    uv run tool_loop.py

    Resultado esperado: una línea [tool] add_two_numbers({'a': 30, 'b': 12}) -&gt; 42 y, después, una línea FINAL: con una frase del modelo que usa el 42. Si el modelo no llama a la tool y responde «42» de memoria, plantéale una operación que no pueda calcular bien de cabeza (p. ej. 3847 * 2911) para forzar la llamada.

  4. Paso 4 — Rompe a propósito. Llama a add_two_numbers con un argumento inválido (p. ej. a="hola") desde run_tool y comprueba que devuelves el error al modelo en vez de romper el programa.
  5. Paso 5 (verificación): confirma que, en cada vuelta, messages crece con un mensaje de assistant con tool_calls y uno o más mensajes role="tool". Ese es el protocolo correcto.

8 · Reto

🎯 Dos tools y elección autónoma

Añade al Copiloto una segunda herramienta, count_progress(module: str), que devuelva cuántas lecciones completadas hay en un módulo (inventa una pequeña tabla en memoria). Deja que el modelo reciba ambas tools y responde con la más adecuada sin que tú se la indiques. Prueba con preguntas que requieran una, la otra y quizá las dos («¿en qué módulo del 2 al 3 hay más lecciones completadas?»).

Pista: no cambies el bucle; solo amplía el HANDLERS y la lista de esquemas. El mérito del reto es comprobar que el modelo elige según las descripciones, y entender por qué una descripción ambigua provoca la tool equivocada. Añade un registro de qué tool se llamó en cada paso para estudiarlo.

9 · Resumen

  • En tool calling, el modelo propone una llamada (nombre + argumentos) y tu código la ejecuta: nunca al revés.
  • Las tools se declaran con JSON Schema; la descripción es la documentación que el modelo lee para elegir.
  • El bucle es: llamar → si hay tool_calls, ejecutar y añadir un mensaje role="tool" → repetir hasta que tool_calls esté vacío.
  • Los argumentos del modelo llegan como texto/JSON: valídalos siempre antes de tocar tus sistemas.
  • Pon un límite de iteraciones y devuelve errores útiles al modelo para que pueda corregirse.
  • Este bucle mínimo es la semilla del agente del módulo 5 y del servidor MCP del módulo 6.

10 · Preguntas frecuentes

¿El modelo «ve» mi código cuando le paso una tool?

No ve el código, solo el esquema que generas a partir de él (nombre, descripción y parámetros). Puede llamar a la tool, pero la ejecución ocurre siempre en tu proceso. Si tu función hace algo peligroso, el riesgo no es que el modelo lo ejecute: es que tú lo ejecutes sin validar.

¿Por qué mi modelo responde en texto en vez de llamar a la tool?

Tres causas típicas: el modelo no soporta tools (usa uno que sí, p. ej. llama3.2/qwen2.5), la descripción es ambigua o no deja claro cuándo usarla, o la pregunta se puede responder sin datos externos (el modelo prefiere contestar de memoria). Refuerza la descripción y, si hace falta, instruye en el system que use las tools para datos concretos.

¿Cuántas tools puedo declarar?

Técnicamente muchas; en la práctica, pocas y bien diferenciadas. Cada esquema ocupa contexto (cuesta tokens) y demasiadas opciones solapadas empeoran la elección. Si tienes decenas, agrúpalas en «namespaces» o usa varias llamadas, en lugar de volcar el catálogo entero.

¿Los argumentos son seguros de usar directamente?

No. Son una propuesta del modelo y pueden traer tipos raros, valores fuera de rango o inyección. Valídalos con pydantic y aplica el principio de mínima confianza: tu función debe comprobar sus precondiciones aunque el esquema diga que el dato es un entero entre 1 y 10.

¿En qué se diferencia esto de un agente?

En nada esencial, solo en escala. Un agente es este bucle con más pasos, varias tools, memoria de conversación y, a veces, planificación. El tool calling es el ladrillo; el agente es la construcción. Lo verás en el módulo 5.
