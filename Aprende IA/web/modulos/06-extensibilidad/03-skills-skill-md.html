Skills (SKILL.md)

Módulo 6 · Extensibilidad: MCP, skills y plugins 🕐 30 minutos
Curso relacionado

Las skills también se tratan desde la metodología en el curso Aprende SDD: mira su módulo 3, lección «Skills: el cómo reutilizable».

1 · Introducción

Hasta aquí has dado al agente capacidades: tools que puede ejecutar, resources que puede leer, prompts que el usuario lanza. Pero hay algo que las tres primitivas no cubren bien: el saber hacer. Cuando el trabajo tiene pasos, criterios y trampas que repetimos siempre igual («así es como añadimos una lección en este repo», «así evaluamos el RAG», «así publicamos una versión»), no quieres un ejecutor: quieres un manual de procedimiento que el agente lea justo cuando el trabajo lo pida.

Una skill es exactamente eso: una carpeta con un fichero SKILL.md que enseña al agente cómo hacer un tipo de trabajo. La descubres por su name y su description, y el agente carga su contenido completo solo cuando la tarea encaja. Dicho de otro modo: las tools son capacidades, las skills son procedimientos.

Esta lección responde a tres preguntas: qué es una skill, cuándo merece la pena crear una (trabajo reutilizable, no cualquier cosa) y cómo se escribe un SKILL.md que funcione. Y como este mismo repositorio ya las usa, tienen un ejemplo real a mano de distancia.

¿Por qué existe esta lección? Porque el conocimiento procedimental es el que más se repite y el que más se olvida. Sin skills, o lo repites en cada conversación, o lo embutes en un AGENTS.md que crece hasta ser ruido. Una skill es la forma de tener un manual grande sin pagar su coste en tokens hasta que hace falta.

2 · Teoría

La analogía: la ficha de procedimiento

Imagina que entra un compañero nuevo al equipo. No le recitas de memoria todo lo que sabes; le das un manual de procedimientos con fichas por tarea: «cómo desplegar», «cómo investigar un incidente», «cómo añadir una migración». Cada ficha solo se lee cuando toca. Las skills son esas fichas: la descripción está en el lomo (para saber qué contiene la ficha) y el cuerpo solo se abre cuando la tarea lo pide. Y si dentro de una ficha necesitas el detalle de una tabla, hay un anexo aparte que solo lees si te hace falta.

Anatomía de una skill

Una skill es una carpeta. Dentro, SKILL.md es obligatorio; el resto es opcional:

  skill-name/
  ├── SKILL.md            ← OBLIGATORIO
  │   ├── frontmatter YAML (name, description)
  │   └── cuerpo Markdown  (instrucciones, pasos, ejemplos)
  └── (opcional)
      ├── scripts/        ← codigo para tareas repetitivas o deterministas
      ├── references/      ← documentos que se cargan solo cuando hacen falta
      └── assets/          ← plantillas y ficheros que se usan en la salida

El SKILL.md tiene dos partes. Arriba, un frontmatter YAML con dos campos obligatorios:

  • name: identificador unico, en minusculas y con guiones, igual que el nombre de la carpeta.
  • description: qué hace la skill y cuándo usarla. Es lo que el agente lee para decidir si la carga, así que es la parte más importante del fichero.

Debajo, el cuerpo Markdown: las instrucciones, los pasos, los ejemplos y las advertencias. Es lo que el agente sigue cuando la skill está activa.

.agents/skills/copiloto-evals/SKILL.md (esqueleto)
---
name: copiloto-evals
description: Escribe y ejecuta evaluaciones del Copiloto. Usala al anadir o
  cambiar un eval del pipeline de RAG, o al revisar una regresion.
---

# Evaluaciones del Copiloto

## Cuando usar esta skill
Cuando haya que anadir un caso de evaluacion o investigar una regresion.

## Pasos
1. Escribe el caso en `evals/dataset.jsonl` con pregunta y respuesta esperada.
2. Ejecuta `uv run copiloto eval --case <id>`.
3. Compara con el resultado anterior; si empeora, no hagas merge.

## Reglas
- Un eval mide algo concreto: no mezcles fidelidad y formato en el mismo caso.
- Nunca cambies el dataset para que pase: cambia el codigo.

La description no es un eslogan: es un disparador. «Una skill sobre RAG» no ayuda; «escribe evaluaciones del pipeline de RAG del Copiloto, úsala al añadir un eval o al revisar una regresión» sí. Si el agente no entiende cuándo cargarla, la skill nunca se activa.

Divulgación progresiva: por qué una skill no infla el contexto

La razón de que las skills existan es el contexto limitado. Si metieras todos los manuales en el prompt, gastarías la ventana y distraerías al modelo. Las skills se cargan en tres niveles:

NivelQué se cargaCuándo
1. MetadataNombre + descripción (~100 palabras)Siempre: es el catálogo que el agente ve
2. CuerpoEl SKILL.md completo (idealmente <500 líneas)Cuando la skill se activa para una tarea
3. RecursosFicheros de references/, scripts/, assets/Solo si el cuerpo los señala y hacen falta

Así puedes tener veinte skills instaladas: solo pagas las ~100 palabras de descripción de cada una. El resto se carga bajo demanda. Si el cuerpo crece demasiado, se parte en más referencias con punteros claros («para el formato exacto, lee references/formato.md»).

Regla de tamaño: si tu SKILL.md se acerca a las 500 líneas, no lo estires: crea una capa más de referencias y deja en el cuerpo solo el índice y los punteros. El agente lee el anexo cuando lo necesita, no antes.

Skill frente a tool, prompt y AGENTS.md

Es fácil confundirlas. La tabla las separa:

Qué esCuándo se cargaQuién lo controla
Tool Una capacidad: ejecutar una acción El modelo la invoca cuando la necesita El modelo
Prompt (MCP) Una plantilla de mensajes El usuario la lanza El usuario
Skill Un procedimiento: cómo hacer un tipo de trabajo El agente la activa cuando la tarea encaja El agente (por relevancia)
AGENTS.md Reglas del proyecto, siempre vigentes Siempre (o al abrir el proyecto) El proyecto

Skill ↔ AGENTS.md: la frontera es siempre frente a bajo demanda. AGENTS.md son las leyes del país: pocas, permanentes y de obligado cumplimiento (idioma, convenciones, dónde vive cada cosa). Las skills son los manuales de oficio: muchos y específicos, y solo abres el que la tarea requiere. Si una regla se aplica a todo lo que haces en el repo, va en AGENTS.md. Si solo se aplica cuando haces ese tipo de trabajo, es una skill.

Cuándo crear una skill

No todo merece una skill. Crear una de más es tan malo como no tener la que hace falta: añade mantenimiento y ruido de descubrimiento. Merece la pena cuando se cumplen estas señales:

  • Reutilizable: el mismo tipo de trabajo se repite (no es un caso único).
  • Con pasos: tiene procedimiento (si es una frase, es un prompt o una regla, no una skill).
  • Con trampas: hay errores fáciles que quieres evitar explícitamente.
  • Estable: el procedimiento cambia poco; una skill desactualizada es peor que ninguna.

No conviertas en skill cualquier gusto o preferencia efímera. Las skills se cargan como instrucciones y el agente las sigue: una skill con criterios obsoletos o contradictorios produce errores difíciles de rastrear. Si la regla es permanente y universal, es AGENTS.md; si es puntual, no es nada.

3 · Ejemplo mínimo

La skill más pequeña posible: un SKILL.md con frontmatter válido y un cuerpo de tres pasos. Nada de scripts ni referencias. Con esto ya es una skill funcional.

.agents/skills/contar-lecciones/SKILL.md
---
name: contar-lecciones
description: Cuenta las lecciones de un curso de la Academy y resume su progreso.
  Usala cuando haya que reportar cuantas lecciones tiene un curso o modulo.
---

# Contar lecciones

## Cuando usar esta skill
Cuando se pida saber cuantas lecciones (o modulos) tiene un curso.

## Pasos
1. Localiza `Aprende <Curso>/web/assets/js/course-data.js`.
2. Cuenta los objetos de `modules[].lessons[]`.
3. Devuelve el total y el desglose por modulo.

## Salida esperada
Una linea por modulo con su numero de lecciones y el total al final.

Fíjate en lo esencial:

  • El frontmatter es lo único obligatorio. name coincide con la carpeta (contar-lecciones); description dice qué y, sobre todo, cuándo.
  • El cuerpo es Markdown normal. No hay sintaxis especial: se escribe para que lo entienda un lector (el agente).
  • No hay código. Una skill no ejecuta: instruye. Si necesitas ejecutar, el cuerpo dice qué comando lanzar (o usa una tool).

Aquí está la diferencia clave frente a un script: este SKILL.md no «cuenta» nada por sí mismo. Le dice al agente cómo contar. La skill es conocimiento; la ejecución la hace el agente con sus herramientas.

4 · Ejemplo real

El Copiloto. Un equipo que mantiene el Copiloto repite siempre la misma tarea delicada: añadir o cambiar un eval sin romper las métricas. Eso es un procedimiento con pasos y trampas. Lo convertimos en una skill que el agente carga solo cuando el trabajo es de evaluación.

La carpeta completa. El SKILL.md es corto y apunta a un anexo con el formato exacto del dataset (nivel 3, cargado solo si hace falta):

  .agents/skills/copiloto-evals/
  ├── SKILL.md                 ← indice + pasos (nivel 2)
  └── references/
      └── dataset-formato.md   ← detalle del formato (nivel 3)
.agents/skills/copiloto-evals/SKILL.md
---
name: copiloto-evals
description: Escribe, ejecuta y revisa evaluaciones del Copiloto. Usala cuando
  haya que anadir un caso al dataset, cambiar el juez, o investigar una regresion
  de calidad en el pipeline de RAG.
---

# Evaluaciones del Copiloto

## Cuando usar esta skill
- Anadir o modificar un caso en `evals/dataset.jsonl`.
- Investigar por que una metrica (recall, faithfulness) bajo.
- Cambiar el juez automatico o su rubrica.

## Antes de empezar
1. Ejecuta la suite completa para tener una linea base:
   `uv run copiloto eval`
2. Anota las metricas actuales. Sin linea base, no hay regresion que detectar.

## Pasos para anadir un caso
1. Elige una pregunta que el Copiloto **deberia** responder con el corpus.
2. Escribe el caso con el formato de `references/dataset-formato.md`.
3. Anade la respuesta esperada y las fuentes que la respaldan.
4. Ejecuta solo ese caso: `uv run copiloto eval --case <id>`.
5. Ejecuta la suite completa y compara con la linea base.

## Reglas
- Un caso mide **una** cosa: no mezcles fidelidad con formato.
- Nunca relajes una asercion para que pase: corrige el codigo o el corpus.
- Un caso que siempre pasa o siempre falla no aporta: revisalo.

## Anexos
- Formato exacto del dataset: lee `references/dataset-formato.md`.

Y el anexo que el cuerpo referencia (se carga solo si el agente llega al paso 2):

.agents/skills/copiloto-evals/references/dataset-formato.md
# Formato de un caso de evaluacion

Cada linea de `evals/dataset.jsonl` es un objeto JSON:

```json
{
  "id": "rag-citas-01",
  "question": "¿Como reduce RAG la alucinacion?",
  "expected_sources": ["04-rag/01-pipeline-rag"],
  "assertions": ["cita al menos una fuente", "no inventa datos fuera del contexto"]
}
```

Reglas:
- `id` unico, en minusculas y con guiones.
- `expected_sources` son rutas `modulo/leccion` del corpus.
- `assertions` son comprobaciones concretas, no opiniones.

Decisiones y porqués:

  • La skill describe un procedimiento, no una capacidad. No buscas ni descargas nada: enseñas la secuencia y las reglas.
  • Línea base antes de tocar nada: es el equivalente a «mide antes de optimizar». La skill impone el rigor que el prompt suelto no garantiza.
  • El detalle vive en references/: el cuerpo se mantiene legible y solo se carga el anexo cuando el paso 2 lo pide.
  • Reglas explícitas («no relajes una aserción para que pase»): las trampas que quieres blindar van escritas, no implícitas.

Este mismo repositorio es un ejemplo vivo: las skills de la Academy (academy-course, python-course, spec-driven-development…) siguen exactamente esta anatomía —frontmatter con name y description, y un cuerpo con reglas y pasos—. Ábrelas y compáralas con lo que acabas de leer: son la mejor plantilla.

6 · Errores habituales

6.1. Descripción que no dice cuándo activarse

La skill existe, es perfecta… y nunca se usa, porque el agente no sabe cuándo encaja. El fallo está en el frontmatter.

Incorrecto
---
name: evals
description: Skill sobre evaluaciones.
---
Correcto
---
name: copiloto-evals
description: Escribe y ejecuta evaluaciones del Copiloto. Usala al anadir o
  cambiar un caso del dataset, o al investigar una regresion de calidad.
---

6.2. Confundir una skill con un script

Una skill instruye; no ejecuta. Si escribes el procedimiento como si el fichero fuese a correr solo, el agente no sabe que debe ejecutar los comandos por su cuenta.

Incorrecto
## Pasos
dataset.add(case)          # ❌ esto parece codigo que se ejecuta solo
metric = run_eval()
Correcto
## Pasos
1. Anade el caso a `evals/dataset.jsonl` (formato en `references/dataset-formato.md`).
2. Ejecuta `uv run copiloto eval --case <id>`.
3. Compara el resultado con la linea base.

6.3. Meter reglas universales en una skill

Si la regla se aplica a todo el proyecto, no es una skill: es una ley que debe estar siempre presente en AGENTS.md. Esconderla en una skill hace que a veces se cumpla y a veces no.

Incorrecto
# skill: formato-del-proyecto
## Reglas
- Todo el contenido y la UI van en espanol.   # ❌ esto es universal: va en AGENTS.md
- Los identificadores van en ingles.
Correcto
# AGENTS.md (siempre presente)
- Contenido, comentarios y UI en espanol; identificadores y comandos en ingles.

# skill: copiloto-evals (solo cuando se evalua)
- Un caso mide una sola cosa: no mezcles fidelidad y formato.

7 · Ejercicio guiado

Objetivo: crear desde cero una skill real para el Copiloto, decidir su frontera con AGENTS.md y comprobar que su descripción permite activarla en el momento correcto.

  1. Paso 1 — elige un trabajo repetible. Piensa en algo que el equipo del Copiloto hace siempre igual. Proponemos: añadir una lección nueva a un curso de la Academy. Tiene pasos, reglas y trampas (actualizar course-data.js, la portada, el contador…). Es un buen candidato a skill.
  2. Paso 2 — crea la carpeta y el frontmatter. La carpeta debe llamarse como el name: 
    mkdir -p .agents/skills/nueva-leccion
    .agents/skills/nueva-leccion/SKILL.md
    ---
name: nueva-leccion
description: Anade una leccion a un curso de la Academy siguiendo el contrato
  de la web estatica. Usala cuando haya que crear o registrar una leccion nueva.
---

# Anadir una leccion

## Cuando usar esta skill
Cuando se pida crear una leccion o registrarla en el indice del curso.

## Pasos
1. Crea `web/modulos/<modulo>/<archivo>.html` con las 10 secciones exactas.
2. Anade la leccion a `web/assets/js/course-data.js` (unica fuente de verdad).
3. Verifica: `node --check` del JS y comprobacion estructural de ids y atributos.
4. Levanta el servidor estatico y comprueba HTTP 200.

## Reglas
- El `reto` nunca se resuelve en el HTML.
- El pie de pagina lleva siempre los tres scripts y `SITE_BASE`.
- Si falta una leccion en el mapa o sobra un archivo, no termines: no puede haber huerfanos.
  3. Paso 3 — decide la frontera con AGENTS.md. ¿Alguna regla del borrador se aplica a todo el repo? Si sí, muévela a AGENTS.md y quítala de la skill. Prueba: «¿esto debe cumplirse aunque hoy no toque añadir una lección?». Las convenciones de idioma, por ejemplo, irían a AGENTS.md.
  4. Paso 4 — añade un anexo si crece. El detalle del «contrato de la web» (las 10 secciones, clases, etc.) es largo: extráelo a references/contrato-web.md y referencia desde el cuerpo. Así el SKILL.md se mantiene corto. 
    mkdir -p .agents/skills/nueva-leccion/references
  5. Paso 5 — comprueba la activación. Lee solo el frontmatter y pregúntate: si pido «añade una lección de X», ¿la descripción encaja sin ambigüedad? Si pido «explica qué es un token», ¿la skill se activaría por error? Ajusta la description hasta que la respuesta sea «sí» y «no», respectivamente.

Prueba de humo: borra mentalmente el cuerpo y quédate solo con la description. Si con eso ya sabes cuándo cargarla, el frontmatter está bien escrito. Si no, el problema no está en los pasos: está en la descripción.

8 · Reto

🎯 Una skill que se comprueba sola

Diseña una skill para el trabajo que tú repites más en el Copiloto, con una condición extra: que su cumplimiento sea verificable. Requisitos:

  • Un SKILL.md con frontmatter válido y pasos numerados; separa en references/ todo lo que pase de ~50 líneas.
  • Incluye en la skill un paso de verificación determinista: un comando que devuelva éxito o fracaso (un test, un ruff, una comprobación de estructura). Una skill que no se puede verificar se erosiona.
  • Escribe una tabla de frontera: qué de esta skill es universal (candidato a AGENTS.md) y qué es específico de este trabajo (se queda en la skill).
  • Documenta en un README.md junto a la skill por qué no es una tool, ni un prompt, ni una regla de AGENTS.md.

Pista: el paso de verificación suele ser el mismo que usarías en CI. Si el procedimiento termina con «y comprueba que…», ese «comprueba» debe ser un comando concreto, no una intención. Para la frontera, aplica la pregunta clave: ¿se aplica siempre (AGENTS.md) o solo cuando haces este trabajo (skill)?

9 · Resumen

  • Una skill enseña cómo hacer un tipo de trabajo; las tools son capacidades y los prompts, plantillas. Skill = procedimiento.
  • Es una carpeta con SKILL.md: frontmatter obligatorio (name + description) y un cuerpo Markdown. Opcional: scripts/, references/, assets/.
  • La descripción es el disparador: debe decir qué y cuándo. Sin eso, la skill nunca se activa.
  • Divulgación progresiva en tres niveles: metadata (siempre), cuerpo (al activarse), recursos (bajo demanda). Por eso no inflan el contexto.
  • Skill ↔ AGENTS.md: AGENTS.md = leyes siempre vigentes; skill = manual de oficio bajo demanda.
  • Crea una skill solo si el trabajo es reutilizable, con pasos, con trampas y estable. Si no, no es una skill.

10 · Preguntas frecuentes

¿Una skill puede ejecutar código?

Ella sola no: una skill es texto que instruye. Pero puede incluir scripts/ que el agente lance, o pedir en sus pasos que se ejecute un comando. La diferencia es sutil pero importante: la skill describe el procedimiento; la ejecución la hace el agente con sus herramientas (o las que ofrece por MCP). Si el trabajo es pura ejecución y no tiene «saber hacer», probablemente sea una tool, no una skill.

¿Cuándo una regla va a AGENTS.md y cuándo a una skill?

La pregunta mágica: «¿esto debe cumplirse aunque hoy no haga ese tipo de trabajo?». Si la respuesta es sí, es AGENTS.md (siempre presente). Si solo aplica cuando haces ese trabajo concreto, es una skill. Así evitas dos extremos: un AGENTS.md gigante que se lee en cada turno, y skills que esconden leyes universales que a veces se incumplen.

¿Cargar muchas skills no llena el contexto?

No, gracias a la divulgación progresiva. De cada skill solo está siempre su metadata (~100 palabras: nombre + descripción). El cuerpo se carga al activarse y los recursos, solo si el cuerpo los pide. Puedes tener decenas de skills instaladas pagando muy poco hasta que una se usa. El coste aparece cuando activas varias a la vez: entonces importa que sus cuerpos sean concisos.

¿En qué se diferencia de un prompt MCP?

Un prompt MCP es una plantilla de mensajes de un solo disparo que el usuario lanza. Una skill es conocimiento procedimental más rico —pasos, criterios, anexos— que el agente carga por relevancia. Un prompt puede ser «resume este módulo»; una skill es «así es como se escribe un eval del Copiloto, paso a paso, con sus reglas». Y no compiten: un prompt puede invocar una skill, y una skill puede usar tools de un servidor MCP.

¿Cómo sé que una skill está bien escrita?

Tres pruebas. (1) Descripción: borra el cuerpo y comprueba que solo con la description sabes cuándo activarla. (2) Verificación: el procedimiento termina en un paso comprobable (un comando, un test), no en una intención. (3) Mantenimiento: si cambia el proceso, hay que actualizarla; si esto pasa mucho, quizá no era una skill estable sino algo que debería vivir en código.
