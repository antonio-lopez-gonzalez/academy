Servidores MCP

Módulo 6 · Extensibilidad: MCP, skills y plugins 🕐 40 minutos

1 · Introducción

Hasta ahora las tools del Copiloto vivían encerradas en su propio proceso: tú declarabas el esquema, el modelo elegía una tool y tu código la ejecutaba. Funciona, pero tiene dos problemas. El primero: esa tool solo existe para tu agente. Si mañana quieres usar search_lessons desde tu editor, desde otro agente o desde una app distinta, tienes que volver a escribir la lógica y el esquema. El segundo: si quieres usar una tool que ya existe en otro sitio (leer un repositorio Git, consultar Postgres, navegar la web), tienes que copiarla dentro de tu proyecto.

Esto es el clásico problema N×M: cada aplicación (N) necesita conectar con cada herramienta (M) y acabas escribiendo N×M integraciones distintas, todas incompatibles entre sí. Es exactamente lo que pasó con los cargadores de móvil antes del USB-C.

MCP (Model Context Protocol) es el estándar abierto que resuelve ese problema para las herramientas de los LLM. Define cómo un servidor expone capacidades (tools, y alguna cosa más) y cómo un cliente las descubre y las llama, con un protocolo común. Con MCP, la misma tool la puede usar cualquier host que hable el protocolo, y tu agente puede usar cualquier servidor que hable el protocolo. Es «USB-C para las herramientas del modelo».

En esta lección montamos un servidor MCP real en Python que expone las tools del Copiloto y lo ejecutamos por stdio, que es el transporte local por defecto. La idea central es sencilla: tus tools dejan de ser código privado de tu agente y pasan a ser un servicio interoperable.

¿Por qué existe esta lección? Porque «darle tools a un agente» y «saber empaquetarlas» son dos cosas distintas. El tool calling del módulo 2 te enseña a ejecutar una tool; MCP te enseña a publicar esa tool para que la consuman otros. Separar qué hace la tool de quién la usa es lo que convierte una app cerrada en un ecosistema: integras una vez, reutilizas en todas partes.

2 · Teoría

La analogía: el enchufe universal

Antes del USB-C, cada dispositivo tenía su conector y cada cable servía para un solo aparato: cargar el móvil, conectar el monitor, pasar fotos… eran tres cables. El USB-C impone un contrato físico común: mientras un extremo sea USB-C, da igual quién fabricó el cable ni quién fabricó el aparato. MCP hace eso mismo con las herramientas: el servidor es el aparato que ofrece capacidades y el cliente es el aparato que las usa; el «conector» es el protocolo. No importa quién escribió el servidor: si habla MCP, tu agente lo entiende. Y no importa quién es el agente: si habla MCP, puede usar tu servidor.

El problema N×M y la solución MCP

  SIN MCP (N apps × M tools, cada una con su integracion)

   agente A ──┐   ┌── tool Git
   editor B ──┼───┼── tool Postgres      → N×M conectores a medida
   app C    ──┘   └── tool web

  CON MCP (N + M conectores, todos iguales)

   agente A ──┐                    ┌── servidor Git
   editor B ──┼── protocolo MCP ───┼── servidor Postgres
   app C    ──┘                    └── servidor web

En el primer esquema cada flecha es código nuevo, acoplado y frágil. En el segundo, un cliente MCP habla con cualquier servidor MCP, y un servidor MCP sirve a cualquier cliente. El número de integraciones baja de N×M a N+M: escritas una vez, reutilizadas siempre.

Host, cliente y servidor

MCP se apoya en tres roles. Conviene no confundirlos:

  • Host: la aplicación con IA (el Copiloto, un IDE, un chat). Es dueño de la conversación y decide qué consiente.
  • Cliente: la mitad que habla MCP dentro del host. Se conecta a un servidor, descubre sus capacidades y las invoca. Un host puede tener varios clientes, uno por servidor.
  • Servidor: lo que tú construyes. Expone capacidades (tools, resources, prompts) y las ejecuta. No sabe nada del modelo ni de la conversación: solo responde peticiones.

Regla mnemotécnica: el host es la app, el cliente es su intérprete de MCP y el servidor es tu código. En esta lección escribimos el tercero; el host y su cliente ya existen (tu editor, el Copiloto, un SDK).

El protocolo: JSON-RPC

Por debajo, MCP no es más que mensajes JSON-RPC 2.0: peticiones con un method, unos params y una respuesta con result o error. Métodos que verás una y otra vez: initialize (negociar versión y capacidades), tools/list y tools/call, resources/list y resources/read, prompts/list y prompts/get. Cada capacidad se anuncia en el initialize: el cliente solo pide lo que el servidor declara. Si tu servidor no expone resources, el cliente ni intenta listarlos.

El SDK crea todo el JSON por ti. Tú escribes funciones Python con tipos y docstrings; el SDK deriva de ahí el nombre, la descripción y el JSON Schema de los argumentos. Nunca escribas JSON-RPC a mano salvo para depurar.

Transportes: stdio y HTTP

El protocolo es el mismo, pero viaja por canales distintos según dónde viva el servidor:

TransporteCómo funcionaCuándo usarlo
stdio El host lanza el servidor como subproceso y habla por su stdin/stdout Servidores locales, una sola sesión, procesos de confianza. Es el defecto y lo que usamos aquí.
Streamable HTTP El servidor escucha en una URL; varios clientes se conectan por HTTP Servidores remotos, compartidos, con autenticación
SSE HTTP con server-sent events Variante heredada de HTTP; prefiere Streamable HTTP en proyectos nuevos

Con stdio no hay puertos, ni red, ni autenticación: el host controla el ciclo de vida del proceso. Por eso es el transporte ideal para el Copiloto, que corre en la misma máquina. Su gran trampa la veremos en Errores habituales: stdout es el canal del protocolo, así que cualquier print() tuyo lo corrompe.

MCP frente a llamar tools «a mano»

No son excluyentes: el Copiloto puede seguir usando sus tools internas en el bucle y, además, exponerlas por MCP para que otros hosts las consuman. MCP es una capa de interoperabilidad, no un sustituto del bucle agentic.

3 · Ejemplo mínimo

El servidor MCP más pequeño posible: una sola tool que suma dos números. No tiene lógica de negocio; lo importante es ver que publicar una tool es declarar una función con tipos y un docstring.

server.py
# server.py — un servidor MCP minimo con una sola tool.
# Instalacion:  uv init mcp-demo && cd mcp-demo && uv add "mcp>=2"
from mcp.server import MCPServer   # en la v1 del SDK esto se llamaba FastMCP


mcp = MCPServer("demo")            # el nombre identifica el servidor


@mcp.tool()                        # el decorador publica `add` como tool
def add(a: int, b: int) -> int:
    """Suma dos enteros."""        # el docstring es la descripcion que ve el modelo
    return a + b


if __name__ == "__main__":
    mcp.run()                      # transporte por defecto: stdio

Eso es todo. Fíjate en que no escribimos JSON, ni esquemas, ni rutas: el SDK lee de la función el nombre (add), la descripción (add two numbers… aquí, el docstring) y el esquema de argumentos a partir de los type hints (a: int, b: int). La función se convierte en una tool MCP.

Ahora la probamos en memoria, sin arrancar ningún subproceso ni puerto. El cliente se conecta directamente al objeto servidor:

test_demo.py
# test_demo.py — conecta un cliente al servidor en memoria y llama a la tool.
import asyncio

from mcp import Client
from server import mcp


async def main() -> None:
    async with Client(mcp) as client:           # sesion MCP lista
        tools = await client.list_tools()        # descubrimiento
        print("tools:", [t.name for t in tools.tools])
        result = await client.call_tool("add", {"a": 2, "b": 3})
        print("resultado:", result.content)


asyncio.run(main())

Salida esperada:

tools: ['add']
resultado: [TextContent(type='text', text='5')]

Línea por línea:

  • @mcp.tool(): registra la función como tool. El cliente la descubrirá con tools/list.
  • Type hints + docstring: de ahí salen el esquema y la descripción. Sin ellos, el modelo no sabría qué argumentos pasar ni para qué sirve la tool.
  • mcp.run(): arranca el bucle del servidor por stdio. Cuando escribimos «el host lanza el servidor como subproceso», esto es el servidor esperando peticiones por su entrada estándar.
  • Client(mcp): un cliente en memoria. Perfecto para tests y para entender el protocolo sin la fricción de arrancar procesos.
  • tools.tools: la respuesta viene envuelta; las tools están en .tools. Lo mismo pasa con resources y prompts.

Si tu versión del SDK aún es la v1, el mismo código funciona cambiando la importación: from mcp.server.fastmcp import FastMCP y mcp = FastMCP("demo"). Todo lo demás (decoradores, cliente) es idéntico. En la v2 el nombre FastMCP se renombró a MCPServer.

4 · Ejemplo real

El Copiloto. Ahora exponemos las tools que ya construimos en los módulos 2 y 5 como un servidor MCP, para que cualquier host —el editor, un IDE, otro agente— pueda usarlas. El servidor no reimplementa nada: reutiliza las funciones de copiloto.tools que ya conocemos.

proyectos/copiloto/src/copiloto/mcp_server.py
"""Servidor MCP del Copiloto.

Expone las tools del Copiloto a cualquier host que hable MCP.
No contiene logica de negocio: reutiliza `copiloto.tools`.
"""
from mcp.server import MCPServer          # v2; en v1 era `from mcp.server.fastmcp import FastMCP`

from copiloto.tools import buscar_lecciones, abrir_modulo, contar_progreso

mcp = MCPServer("copiloto")


@mcp.tool()
def search_lessons(query: str, k: int = 4) -> list[dict]:
    """Busca fragmentos relevantes en las lecciones de la Academy."""
    return buscar_lecciones(query, k=k)


@mcp.tool()
def open_module(course: str, module: str) -> str:
    """Devuelve el indice de lecciones de un modulo de un curso."""
    return abrir_modulo(course, module)


@mcp.tool()
def count_progress(course: str) -> dict:
    """Cuenta lecciones completadas y pendientes de un curso."""
    return contar_progreso(course)


def main() -> None:
    # stdio: el host lanza este proceso y habla por su stdin/stdout.
    mcp.run()


if __name__ == "__main__":
    main()

Y así lo registra un host. El host no importa Python: solo sabe que debe lanzar un comando que habla MCP. Este es el fichero de configuración típico (adaptado del que usan los IDEs y los clientes MCP):

mcp.json
{
  "mcpServers": {
    "copiloto": {
      "command": "uv",
      "args": ["run", "--directory", "proyectos/copiloto", "copiloto-mcp"]
    }
  }
}

Con "command": "uv" y esos argumentos, el host ejecuta el servidor como subproceso y se comunica por stdio. copiloto-mcp es un console script que declaras en pyproject.toml:

proyectos/copiloto/pyproject.toml (fragmento)
[project.scripts]
copiloto = "copiloto.cli:main"
copiloto-mcp = "copiloto.mcp_server:main"

Decisiones y porqués:

  • Reutilizar copiloto.tools: una sola fuente de verdad para la lógica. Si mejoras buscar_lecciones, mejora a la vez el agente y el servidor MCP.
  • Docstrings claros: son la documentación que el modelo lee al elegir tool. Un docstring vago («busca cosas») produce malas llamadas.
  • -> list[dict] y -> dict: tipos serializables. Devolver objetos raros (una conexión, un objeto con estado) rompería la conversión a respuesta MCP.
  • stdio: servidor local en la misma máquina, sin auth ni puertos. El host controla el proceso.
  • Punto de entrada separado (copiloto-mcp): el host no necesita saber nada del resto del Copiloto; solo ejecuta ese comando.

En el módulo 5 el Copiloto llamaba a estas tools desde dentro de su bucle. Aquí las sacamos a un proceso aparte. Son dos formas del mismo concepto: una tool es una capacidad; MCP es su envoltorio para compartirla. Puedes tener las dos cosas a la vez.

6 · Errores habituales

6.1. Escribir en stdout y corromper el protocolo

El error número uno de stdio. Un print() de depuración se mezcla con el JSON-RPC y el host recibe basura; el síntoma es un error de parseo incomprensible que no menciona tu print.

Incorrecto
# ❌ print() escribe en stdout, el mismo canal del protocolo.
@mcp.tool()
def search_lessons(query: str) -> list[dict]:
    print(f"Buscando {query}...")      # corrompe la respuesta JSON-RPC
    return buscar_lecciones(query)
Correcto
# ✅ Los logs van a stderr: el protocolo se queda limpio en stdout.
import sys

@mcp.tool()
def search_lessons(query: str) -> list[dict]:
    print(f"Buscando {query}...", file=sys.stderr)
    return buscar_lecciones(query)

6.2. Argumentos sin tipo (esquema vacío)

Si no declaras los tipos, el SDK no puede construir el JSON Schema y el modelo no sabe cómo llamar la tool. La tool «existe», pero es inutilizable.

Incorrecto
# ❌ Sin type hints, el esquema de argumentos queda vacio.
@mcp.tool()
def search_lessons(query, k=4):
    """Busca lecciones."""
    return buscar_lecciones(query, k)
Correcto
# ✅ Los tipos generan el esquema; el docstring, la descripcion.
@mcp.tool()
def search_lessons(query: str, k: int = 4) -> list[dict]:
    """Busca fragmentos relevantes en las lecciones de la Academy."""
    return buscar_lecciones(query, k=k)

6.3. Devolver objetos no serializables

La respuesta MCP viaja como contenido serializable. Devolver una conexión a base de datos o un generador produce un error en tiempo de ejecución.

Incorrecto
# ❌ Un objeto con estado no se puede serializar a la respuesta MCP.
@mcp.tool()
def db_connection() -> object:
    """Devuelve la conexion abierta."""
    return get_connection()            # conexion viva = fallo
Correcto
# ✅ Devuelve datos serializables; la conexion es un detalle interno.
@mcp.tool()
def db_status() -> dict:
    """Devuelve el estado de la base de datos."""
    return {"ok": True, "tables": 12}

7 · Ejercicio guiado

Objetivo: crear un servidor MCP con una tool que cuenta las lecciones de la Academy, probarlo en memoria y, después, conectarte a él por stdio como lo haría un host real.

  1. Paso 1 — prepara el proyecto. Crea una carpeta y añade el SDK: 
    uv init copiloto-mcp && cd copiloto-mcp
uv add "mcp>=2"
  2. Paso 2 — el servidor. Una tool que recibe un directorio raíz y cuenta los archivos .html de lecciones: 
    # server.py — servidor MCP que cuenta lecciones de la Academy.
from pathlib import Path

from mcp.server import MCPServer

mcp = MCPServer("academy-index")


@mcp.tool()
def count_lessons(root: str) -> int:
    """Cuenta las lecciones (.html) bajo <root>/Aprende */web/modulos/."""
    base = Path(root)
    lessons = list(base.glob("Aprende */web/modulos/*/*.html"))
    return len(lessons)


if __name__ == "__main__":
    mcp.run()          # stdio
  3. Paso 3 — pruébalo en memoria. Antes de tocar el host, confirma que la tool responde: 
    # test_server.py
import asyncio
from mcp import Client
from server import mcp

async def main() -> None:
    async with Client(mcp) as client:
        print("tools:", [t.name for t in (await client.list_tools()).tools])
        result = await client.call_tool("count_lessons", {"root": ".."})
        print("lecciones:", result.content)

asyncio.run(main())

    Ejecuta uv run test_server.py. Esperado: tools: ['count_lessons'] y un número (según los cursos presentes).

  4. Paso 4 — conéctate por stdio. Ahora levanta el servidor como subproceso, igual que un host: 
    # cliente.py — lanza el servidor por stdio y llama a la tool.
import asyncio

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client


async def main() -> None:
    params = StdioServerParameters(command="uv", args=["run", "server.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()                 # negocia capacidades
            tools = await session.list_tools()
            print("tools:", [t.name for t in tools.tools])
            result = await session.call_tool("count_lessons", {"root": ".."})
            print("lecciones:", result.content)


asyncio.run(main())

    Ejecuta uv run cliente.py. La diferencia con el paso 3 es enorme: ahora hay un proceso aparte hablando JSON-RPC por stdin/stdout. Esto es exactamente lo que hace un IDE al conectar tu servidor.

  5. Paso 5 — provoca el error de stdout. Añade un print("debug") dentro de count_lessons, vuelve a correr cliente.py y observa cómo se rompe. Quita el print y comprueba que se arregla. Acabas de ver, en carne propia, por qué los logs van a stderr.

Si tu host no ve la tool, la primera comprobación es siempre la misma: ejecuta el paso 3 (cliente en memoria). Si ahí funciona, el problema está en la configuración del host (comando, ruta o argumentos), no en tu servidor.

8 · Reto

🎯 El servidor del Copiloto, por HTTP y con token

Parte del servidor del ejemplo real (las tres tools del Copiloto) y da el salto de local a remoto. Requisitos:

  • Arranca el servidor con transporte Streamable HTTP (parámetro transport de run()) en lugar de stdio.
  • Conéctate con el cliente MCP a la URL del servidor y llama a search_lessons desde un proceso aparte.
  • Añade un token compartido: el servidor rechaza cualquier petición sin él. Piensa dónde va el token (cabecera, entorno) y por qué nunca debe ir en el repositorio.
  • Explica en un comentario por qué print() deja de ser peligroso con HTTP pero el token introduce un riesgo nuevo.

Pista: mcp.run(transport="streamable-http") y el cliente se conecta con la URL (Client("http://localhost:8000/mcp")). Para el token, consulta las opciones de autenticación del SDK y guárdalo en una variable de entorno; en la v1 el mismo cambio se hace pasando transport="streamable-http" a FastMCP.run(). No lo dejes «para que funcione»: decide explícitamente qué endpoints quedan expuestos.

9 · Resumen

  • MCP es un protocolo abierto que estandariza cómo un servidor expone capacidades y cómo un cliente las descubre y las usa. Resuelve el problema N×M bajándolo a N+M.
  • Tres roles: host (la app con IA), cliente (su mitad MCP) y servidor (tu código, lo que construyes).
  • Por debajo es JSON-RPC: initialize, tools/list, tools/call… El SDK lo genera todo a partir de tus funciones.
  • El SDK deriva nombre, descripción y esquema del nombre de la función, el docstring y los type hints. Escribir tipos no es opcional.
  • stdio es el transporte local por defecto: el host lanza el servidor como subproceso y habla por stdin/stdout. Nunca escribas a stdout; usa stderr para logs.
  • El Copiloto expone sus tools con un punto de entrada separado (copiloto-mcp) que reutiliza copiloto.tools: una sola fuente de verdad.

10 · Preguntas frecuentes

¿MCP sustituye al tool calling que vi en el módulo 2?

No. El tool calling es cómo un modelo pide que se ejecute una función; MCP es cómo publicas esa función para que la consuma cualquier host. Son complementarias: por dentro, el agente sigue usando tool calling; MCP es la capa estándar que permite que la misma tool la usen otros. El modelo nunca «habla MCP»: habla el host, que traduce.

¿stdio o Streamable HTTP?

stdio cuando el servidor corre en tu máquina, en una sola sesión y es de confianza (el caso del Copiloto). HTTP cuando el servidor es remoto, lo comparten varios usuarios o necesitas autenticación. Empieza por stdio: menos partes móviles, sin puertos ni red. Migrar después es cambiar el transporte de run() y la forma de conectar el cliente.

¿Por qué mi host dice que el servidor «falló al iniciar»?

Casi siempre es una de estas tres: (1) el command no existe en el PATH del host; (2) la ruta del proyecto en args es incorrecta; (3) hay un print() en stdout corrompiendo el protocolo. Aísla ejecutando el cliente en memoria: si ahí funciona, el fallo está en la configuración del host, no en el servidor.

¿Puedo exponer la misma tool interna y por MCP?

Sí, y es lo recomendable. La lógica vive una sola vez en copiloto.tools; el bucle del agente la importa directamente y el servidor MCP la envuelve con @mcp.tool(). Así el Copiloto sigue siendo autónomo y, además, otras apps pueden usar sus capacidades sin duplicar código.

¿Qué versión del SDK debo instalar?

La v2 estable del SDK de Python (uv add "mcp>=2"), donde la clase de alto nivel se llama MCPServer (importada de mcp.server). En la v1 se llamaba FastMCP (from mcp.server.fastmcp import FastMCP); muchos tutoriales siguen usando ese nombre. Consulta siempre la documentación oficial antes de fijar una versión, porque la API de transporte y de tipos cambió entre ambas.
