Tools, resources y prompts

Módulo 6 · Extensibilidad: MCP, skills y plugins 🕐 35 minutos

1 · Introducción

En la lección anterior montamos un servidor MCP, pero solo usamos una de sus capacidades: las tools. MCP tiene en realidad tres primitivas —tools, resources y prompts— y elegir bien cuál usar es una decisión de diseño, no un detalle. La pregunta que las separa es siempre la misma:

¿Quién tiene el control: el modelo, la aplicación o el usuario?

  • Las tools las decide el modelo: son acciones que el LLM puede invocar cuando cree que le ayudan.
  • Los resources los decide la aplicación: son datos de solo lectura que la app inyecta como contexto.
  • Los prompts los decide el usuario: son plantillas que una persona elige explícitamente (un comando, un botón).

Cuando confundes las primitivas, todo funciona «más o menos» pero mal: conviertes en tool algo que debería ser un resource, dejas que el modelo decida datos que el usuario debería elegir, o expones como resource algo que tiene efectos secundarios. Esta lección te da el criterio para decidir, y muestra cómo un cliente descubre y consume cada primitiva.

¿Por qué existe esta lección? Porque MCP no es «un protocolo de tools». Si tratas las tres primitivas como una sola, pierdes lo mejor del estándar: separar acciones (con efectos), datos (solo lectura) y rutinas (elegidas por la persona) es lo que hace un servidor predecible, seguro y fácil de consentir.

2 · Teoría

La analogía: acciones, estantería y recetas

Piensa en una cocina profesional. Las tools son los electrodomésticos: se encienden cuando hace falta y hacen algo (cambian el estado del mundo). La estantería de ingredientes son los resources: están ahí, se leen, pero nadie los «usa» en el sentido de provocar un cambio. Y las recetas impresas son los prompts: no se ejecutan solas, las elige un cocinero y las sigue. El modelo es el cocinero: pide encender un electrodoméstico (tool), lee un ingrediente (resource), pero la receta la pone el dueño del restaurante (el usuario).

Tools: lo que el modelo puede hacer

Es la primitiva que ya conoces del módulo 2. Una tool es una función con efectos: buscar, escribir, enviar, calcular. El modelo la invoca cuando decide que le ayuda a completar la tarea. Como puede cambiar el mundo, es la primitiva que exige más cuidado (permisos, sandbox, aprobación: lo veremos en la lección 04). El SDK construye su esquema desde los type hints y su descripción desde el docstring.

@mcp.tool()
def search_lessons(query: str, k: int = 4) -> list[dict]:
    """Busca fragmentos relevantes en las lecciones de la Academy."""
    ...

Resources: lo que la aplicación puede leer

Un resource es solo lectura y se identifica por una URI (copiloto://lecciones/04). Es el equivalente a un GET: leer un documento, una tabla, una configuración. No tiene efectos secundarios, así que no necesita aprobación ni sandbox. Como la URI puede llevar parámetros, existe el resource template: una plantilla con huecos (copiloto://lecciones/{module}) que el cliente puede rellenar. El cliente lo lista por separado de los resources concretos.

@mcp.resource("copiloto://lecciones/{module}")
def read_module(module: str) -> str:
    """Devuelve el indice de lecciones de un modulo."""
    ...

Un resource no «busca»: devuelve el contenido de una URI que ya conoces. Si lo que necesitas es encontrar algo sin saber la URI exacta, eso es una tool (búsqueda), no un resource. Confundir esto es el error más común.

Prompts: lo que el usuario elige

Un prompt es una plantilla reutilizable que devuelve uno o varios mensajes listos para el modelo. No lo dispara el modelo ni la app «por su cuenta»: lo elige una persona, normalmente desde un comando o un menú (piensa en «/resumir-módulo»). Sirve para codificar rutinas: «revisa este módulo con estas instrucciones y este formato».

@mcp.prompt()
def review_module(course: str, module: str) -> str:
    """Pide un resumen del modulo con puntos clave y posibles mejoras."""
    return f"Resume el modulo {module} de {course} en 5 puntos y sugiere mejoras."

Descubrimiento y capacidades

El cliente no adivina: pregunta. En el initialize, el servidor declara qué primitivas soporta («capacidades»), y el cliente solo pide lo que está declarado. Después descubre la lista concreta. El flujo típico de arranque es:

  cliente                          servidor
     │  initialize ─────────────────▶│   negocian version + capacidades
     │◀──────────────── capabilities │   (tools? resources? prompts?)
     │                               │
     │  tools/list ─────────────────▶│   solo si el server declaro tools
     │◀──────────────── [tools]      │
     │                               │
     │  resources/list ─────────────▶│   solo si declaro resources
     │◀──────────── [resources]      │
     │  resources/templates/list ───▶│   plantillas con {param}
     │◀──────────────── [templates]  │
     │                               │
     │  prompts/list ───────────────▶│   solo si declaro prompts
     │◀──────────────── [prompts]    │

Esta negociación es lo que hace que MCP sea extensible sin romper nada: un cliente antiguo ignora las capacidades que no conoce, y un servidor minimal solo declara las que ofrece.

Cómo lo consume un agente

Aquí está la clave de por qué las tres primitivas importan al diseñar un agente. El host las trata de forma distinta:

  • Tools → se convierten en el esquema de tools que se pasa al modelo en cada turno. El modelo decide cuándo llamarlas; el host ejecuta y devuelve el resultado al bucle.
  • Resources → el host los inyecta como contexto cuando cree que vienen al caso (o cuando el usuario los selecciona). No pasan por «decisión del modelo»: son datos.
  • Prompts → se exponen como comandos que el usuario elige; el host convierte la plantilla en mensajes y arranca el turno con ellos.

Un resource puede contener datos sensibles (configuración, registros, secretos por descuido). Como se inyecta como contexto, todo lo que expongas se le puede mostrar al modelo y quedar en la traza. Antes de publicar un resource, pregúntate: «¿esto puede acabar en el prompt o en un log?».

3 · Ejemplo mínimo

Un servidor con las tres primitivas a la vez y un cliente que descubre y usa cada una. Es el ejemplo más pequeño que muestra la diferencia entre ellas.

server.py
# server.py — las tres primitivas de MCP en un solo servidor.
from mcp.server import MCPServer

mcp = MCPServer("tres-primitivas")

NOTES: dict[str, str] = {"rag": "RAG = recuperar y luego generar."}


@mcp.tool()                                   # el MODELO decide: accion con efecto
def add_note(key: str, text: str) -> str:
    """Guarda una nota nueva (efecto secundario)."""
    NOTES[key] = text
    return f"nota '{key}' guardada"


@mcp.resource("notes://{key}")                # la APP decide: dato de solo lectura
def read_note(key: str) -> str:
    """Lee una nota existente por su clave."""
    return NOTES.get(key, "(no existe)")


@mcp.prompt()                                 # el USUARIO decide: plantilla
def explain(topic: str) -> str:
    """Plantilla para pedir una explicacion breve."""
    return f"Explica {topic} en tres frases y da un ejemplo."


if __name__ == "__main__":
    mcp.run()

Ahora un cliente que recorre las tres: lista, lee y comprueba.

client.py
# client.py — descubre y consume las tres primitivas.
import asyncio

from mcp import Client
from server import mcp


async def main() -> None:
    async with Client(mcp) as client:
        # 1) Tools: el modelo las invocaria. Aqui las llamamos nosotros.
        tools = await client.list_tools()
        print("tools:", [t.name for t in tools.tools])
        print(await client.call_tool("add_note", {"key": "evals", "text": "mide antes de optimizar"}))

        # 2) Resources: datos de solo lectura, por URI.
        resources = await client.list_resources()
        print("resources:", [str(r.uri) for r in resources.resources])
        note = await client.read_resource("notes://rag")     # rellena {key} = rag
        print("nota:", note.contents[0].text)

        # 3) Prompts: plantilla que elige el usuario.
        prompts = await client.list_prompts()
        print("prompts:", [p.name for p in prompts.prompts])
        filled = await client.get_prompt("explain", {"topic": "embeddings"})
        print("mensaje:", filled.messages[0].content.text)


asyncio.run(main())

Salida esperada (recortada):

tools: ['add_note']
resources: ['notes://rag', 'notes://evals']
nota: RAG = recuperar y luego generar.
prompts: ['explain']
mensaje: Explica embeddings en tres frases y da un ejemplo.

Fíjate en las diferencias de forma de invocación, que reflejan la diferencia de naturaleza:

  • La tool se llama con un dict de argumentos: call_tool("add_note", {"key": ..., "text": ...}). Su esquema lo genera el SDK.
  • El resource se lee por una URI: read_resource("notes://rag"). La plantilla notes://{key} se rellenó con key = "rag".
  • El prompt se instancia con argumentos nombrados y devuelve mensajes: get_prompt("explain", {"topic": "embeddings"}).

Los resources concretos (notes://rag) aparecen en resources/list porque existen; la plantilla (notes://{key}) se lista aparte, con resources/templates/list. Un cliente que quiere «todos los resources» combina las dos listas.

4 · Ejemplo real

El Copiloto. Ampliamos el servidor de la lección 01 para que no sea solo tools: añadimos un resource template con los índices de los módulos y un prompt de revisión. Así cualquier host puede usar el Copiloto de tres formas distintas, cada una con su nivel de control.

proyectos/copiloto/src/copiloto/mcp_server.py
"""Servidor MCP del Copiloto: tools, resources y prompts."""
from mcp.server import MCPServer

from copiloto.index import list_lessons         # metadatos de las lecciones
from copiloto.tools import buscar_lecciones, abrir_modulo, contar_progreso

mcp = MCPServer("copiloto")


# --- Tools: acciones que decide el MODELO -------------------------------
@mcp.tool()
def search_lessons(query: str, k: int = 4) -> list[dict]:
    """Busca fragmentos relevantes en las lecciones de la Academy."""
    return buscar_lecciones(query, k=k)


@mcp.tool()
def count_progress(course: str) -> dict:
    """Cuenta lecciones completadas y pendientes de un curso."""
    return contar_progreso(course)


# --- Resources: datos de solo lectura que aporta la APP -----------------
@mcp.resource("copiloto://curso/{course}/modulo/{module}")
def module_index(course: str, module: str) -> str:
    """Indice de lecciones de un modulo, en texto plano.

    URI: copiloto://curso/Aprende IA/modulo/04
    """
    lessons = list_lessons(course=course, module=module)
    return "\n".join(f"- {l['file']}: {l['title']}" for l in lessons)


# --- Prompts: plantillas que elige el USUARIO ---------------------------
@mcp.prompt()
def review_module(course: str, module: str) -> str:
    """Rutina de revision de un modulo: resumen + mejoras."""
    return (
        f"Lee las lecciones del modulo {module} de {course} y devuelve "
        "5 puntos clave y 3 mejoras concretas."
    )


def main() -> None:
    mcp.run()


if __name__ == "__main__":
    main()

Decisiones y porqués:

  • search_lessons es una tool, no un resource: encuentra contenido aunque no conozcas la URI. Devolver «lo que busque» es una acción; por eso el modelo la decide.
  • module_index es un resource: un documento estable, identificado por una URI, sin efectos. La app lo inyecta cuando hace falta (por ejemplo, al abrir un módulo).
  • review_module es un prompt: una rutina que a nadie le apetece reescribir. El usuario la lanza como «/revisar-módulo»; el modelo no la dispara solo.
  • La URI es legible (copiloto://curso/…/modulo/04): encodifica qué es el dato. Una URI críptica hace que ni el host ni tú sepáis qué se está leyendo.

Cómo lo consume el bucle del agente (módulo 5). Solo las tools entran en el esquema que ve el modelo:

proyectos/copiloto/src/copiloto/agent.py (fragmento)
async def build_tool_schemas(client: Client) -> list[dict]:
    """Convierte las tools MCP al esquema que espera el LLM."""
    listed = await client.list_tools()
    return [
        {
            "type": "function",
            "function": {
                "name": t.name,
                "description": t.description,
                "parameters": t.inputSchema,     # JSON Schema, cortesia del SDK
            },
        }
        for t in listed.tools
    ]


async def load_module_context(client: Client, course: str, module: str) -> str:
    """La APP (no el modelo) decide inyectar el indice del modulo."""
    uri = f"copiloto://curso/{course}/modulo/{module}"
    result = await client.read_resource(uri)
    return result.contents[0].text

Este fragmento enseña el corazón del diseño: las tools van al modelo; los resources los inyecta tu código. Si un dato debe estar «siempre» en el contexto, no lo conviertas en tool: léelo como resource y añádelo tú. Así el modelo no gasta un turno pidiendo algo que la app ya sabía que hacía falta.

6 · Errores habituales

6.1. Un resource que en realidad busca

La app no puede «leer un recurso» sin saber su URI; «búscame lo que hable de X» no es una lectura, es una acción. Como resource, ni el modelo ni el host sabrían cuándo usarlo.

Incorrecto
# ❌ "Buscar" no es leer una URI: eso es una accion.
@mcp.resource("copiloto://buscar")
def search_lessons(query: str) -> str:
    """Busca lecciones que hablen de muestra query."""
    return "\n".join(buscar_lecciones(query))
Correcto
# ✅ Buscar es una tool (el modelo decide); el resource solo lee.
@mcp.tool()
def search_lessons(query: str, k: int = 4) -> list[dict]:
    """Busca fragmentos relevantes en las lecciones."""
    return buscar_lecciones(query, k=k)

6.2. Un resource con efectos secundarios

Los resources se leen sin consentimiento ni aprobación. Si «leer» cambia algo, rompes el contrato: la app cree que solo está mirando.

Incorrecto
# ❌ Leer un resource incrementa un contador: efecto oculto.
@mcp.resource("copiloto://curso/{course}")
def course_stats(course: str) -> str:
    VIEWS[course] += 1                 # el "GET" no deberia mutar nada
    return json.dumps(VIEWS[course])
Correcto
# ✅ El resource solo lee; si hay que registrar algo, es otra pieza.
@mcp.resource("copiloto://curso/{course}")
def course_stats(course: str) -> str:
    return json.dumps(contar_progreso(course))

6.3. Exponer de más en un resource

El resource acaba como contexto del modelo y en las trazas. Volcar configuración, rutas internas o secretos «por comodidad» es una fuga esperando a ocurrir.

Incorrecto
# ❌ Vuelca todo el entorno, incluidos secretos, al contexto.
@mcp.resource("copiloto://config")
def config() -> str:
    return json.dumps(dict(os.environ))        # API keys incluidas
Correcto
# ✅ Expone solo lo necesario y no sensible.
@mcp.resource("copiloto://config")
def config() -> str:
    return json.dumps({"model": MODEL, "top_k": 4})

  1. Paso 1 — parte del servidor de la lección 01. Añade un estado en memoria y las tres primitivas: 
    # server.py — tools + resource template + prompt.
from mcp.server import MCPServer

mcp = MCPServer("academy")

MODULES: dict[str, list[str]] = {
    "06": ["01-mcp-servidores", "02-tools-resources-prompts", "03-skills-skill-md", "04-plugins-y-permisos"],
}


@mcp.tool()                                   # accion: el MODELO decide
def add_lesson(module: str, lesson: str) -> str:
    """Anade una leccion a un modulo (efecto secundario)."""
    MODULES.setdefault(module, []).append(lesson)
    return f"{module} ahora tiene {len(MODULES[module])} lecciones"


@mcp.resource("academy://modulo/{module}")    # dato: la APP decide
def list_module(module: str) -> str:
    """Lista las lecciones de un modulo."""
    return "\n".join(f"- {l}" for l in MODULES.get(module, []))


@mcp.prompt()                                 # rutina: el USUARIO decide
def plan_module(module: str) -> str:
    """Planifica el estudio de un modulo."""
    return f"Propon un plan de estudio de 3 dias para el modulo {module}."


if __name__ == "__main__":
    mcp.run()

8 · Reto

🎯 Un cuaderno de apuntes MCP completo

Diseña y programa un servidor «cuaderno de apuntes» que use las tres primitivas con criterio y dialoga con un agente que lo consuma. Requisitos:

  • Una tool append_note(topic, text) que añade texto a un tema (acción, con efecto).
  • Un resource template notes://{topic} que devuelve todas las notas de un tema (solo lectura).
  • Un prompt summarize_notes(topic) que devuelve una plantilla para resumir ese tema en 5 puntos.
  • En el cliente/agente: las tools van al esquema del modelo; del resource se inyecta como contexto el tema activo; el prompt se ofrece como comando que el usuario lanza a propósito.
  • Documenta en README.md por qué cada capacidad es la primitiva que es. Si alguna te obliga a «hacer trampas», cambia de primitiva.

Pista: el tema activo es estado de la aplicación, no del modelo: guárdalo en el host y léelo con read_resource antes de montar el contexto. Para agrupar recursos por tema, usa una plantilla notes://{topic} y deja que el host decida qué topic leer. Si empiezas a necesitar «buscar notas por palabra», eso ya no es un resource: es una tool de búsqueda.

9 · Resumen

  • MCP tiene tres primitivas y se distinguen por quién las controla: tools (modelo), resources (aplicación), prompts (usuario).
  • Tools: acciones con efectos, con esquema derivado de los type hints. Se descubren con tools/list y se invocan con tools/call.
  • Resources: datos de solo lectura identificados por URI. resources/list + resources/templates/list; se leen con resources/read.
  • Prompts: plantillas de mensajes que elige el usuario. prompts/list y prompts/get.
  • El arranque negocia capacidades: el cliente solo pide lo que el servidor declara. Eso hace el estándar extensible sin romper clientes antiguos.
  • En un agente: las tools van al modelo, los resources los inyecta la app como contexto, y los prompts se ofrecen como comandos.
  • Resource que «busca», resource con efectos y resources que filtran secretos: los tres errores que hay que evitar.

10 · Preguntas frecuentes

¿Por qué no convertir todo en tools? Es lo que el modelo maneja.

Porque pagas dos costes. Primero, cada tool ocupa espacio en el esquema que ve el modelo en cada turno: más tools, más tokens y más confusión. Segundo, un dato que la app ya sabe que necesita no debería depender de que el modelo decida pedirlo. Los resources permiten inyectar contexto de forma determinista; los prompts dan rutinas que el usuario controla sin gastar turnos del modelo.

¿Cómo distingo un resource template de un resource normal?

El template lleva parámetros en la URI, entre llaves: notes://{topic}. El normal es una URI fija: copiloto://config. Los clientes los listan por separado (resources/list frente a resources/templates/list), pero ambos se leen igual, con resources/read sobre una URI concreta.

Los prompts, ¿no son lo mismo que un system prompt?

No. El system prompt es la instrucción base de la conversación; un prompt MCP es una plantilla que el usuario elige para iniciar un flujo (tipo «/resumir»). El prompt MCP genera mensajes que el host añade a la conversación; tú sigues teniendo tu system prompt. Uno es política permanente; el otro, una rutina a demanda.

¿Un cliente soporta obligatoriamente las tres primitivas?

No. El cliente solo usa lo que el servidor declara y él mismo soporta. Un servidor puede exponer solo tools; un cliente puede entender solo tools y resources. El initialize existe precisamente para negociar esto: si falta una capacidad en cualquier lado, simplemente no se usa. Esa tolerancia es lo que permite que el ecosistema crezca sin coordinación central.

¿Dónde encaja esto con las skills de la próxima lección?

Perfectamente. Un prompt es una rutina de un solo disparo; una skill es conocimiento procedimental más rico (varios pasos, criterios, recursos) que el agente carga cuando el trabajo lo pide. Muchas veces una skill usa tools y resources de un servidor MCP: la skill dice cómo hacer el trabajo; MCP aporta las capacidades que ese trabajo necesita.
