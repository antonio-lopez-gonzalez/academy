Primera llamada al modelo

Módulo 0 · Preparación 🕐 35 minutos

1 · Introducción

Ha llegado el momento. Vamos a hacer la primera llamada real a un LLM, en local con Ollama, midiendo lo que tarda y manejando lo que puede salir mal. Al terminar esta lección tendrás la puerta llm.py del Copiloto funcionando de verdad, con streaming, métricas y errores controlados.

La harás dos veces, a propósito:

  • una vez por HTTP directo con la biblioteca estándar, para que veas exactamente qué viaja por la red;
  • una vez con el SDK de Python, que es lo cómodo para el código del día a día.

Entender las dos capas te evita la caja negra: cuando algo falle, sabrás si el problema es del modelo, de la red o de tu código. Y nada de secretos: la configuración va por variables de entorno y un .env que nunca se sube al repositorio.

¿Por qué esta lección existe? Porque la primera llamada es donde se junta todo: endpoint, payload, streaming, errores y latencia. Si esto queda claro desde el principio, los módulos siguientes (prompting, tools, RAG) son solo capas sobre una base sólida.

Requisitos: haber completado la lección 3 (tener uv, Ollama en marcha y el modelo llama3.2 descargado). Si aún no, vuelve a ella; esta lección la aprovecha al 100%.

2 · Teoría

Qué viaja por la red: el contrato de la llamada

Toda llamada a un LLM, sea local o en la nube, se reduce a un POST con un JSON y una respuesta JSON. En Ollama el endpoint de conversación es POST /api/chat. Este es el contrato:

petición (JSON)
{
  "model": "llama3.2",
  "messages": [
    { "role": "system", "content": "Respondes en español, de forma breve." },
    { "role": "user",   "content": "¿Qué es un token?" }
  ],
  "stream": false
}
respuesta (JSON)
{
  "model": "llama3.2",
  "message": { "role": "assistant", "content": "Un token es una unidad de texto." },
  "done": true,
  "done_reason": "stop",
  "prompt_eval_count": 37,
  "eval_count": 14,
  "total_duration": 1870000000
}

Fíjate en que la respuesta es la misma pieza de información que ya conoces: texto generado más métricas (prompt_eval_count, eval_count, total_duration) y motivo de parada (done_reason). Es tu instrumento de observación.

El SDK no es magia: internamente hace exactamente el POST que acabamos de ver. Por eso empezamos por HTTP.

Streaming: por qué el texto aparece a trozos

En modo stream: false, el servidor espera a generar toda la respuesta y luego la devuelve. En modo stream: true, envía cada token en cuanto se produce, como una secuencia de objetos JSON. La diferencia para el usuario es enorme: con streaming, la primera palabra aparece casi al instante aunque la respuesta completa tarde más.

  stream:false                     stream:true
  [==================]  espera     [=][=][=][=][=][=]  va saliendo
  0s ----------------- 3s            0.2s ------------- 3s

  (todo de golpe al final)         (sensacion de inmediatez)

Analogía: sin streaming es contar un chiste entero antes de reírte; con streaming, te ríes según cae cada gracia. El resultado final es el mismo, pero la experiencia cambia por completo. Medirás la latencia al primer token, no solo el total.

Configuración sin secretos: .env y variables de entorno

La regla es simple: el código no contiene URLs de servicios secretos ni claves. Lee del entorno; en local, carga el entorno desde un archivo .env que está en .gitignore. Y versiona un .env.example con las claves vacías, para documentar qué variables existen sin filtrar nada.

Nunca subas un .env al repositorio. Una clave filtrada en el historial de Git sigue ahí aunque borres el archivo después. Este curso no usa claves para el núcleo, pero el hábito se coge desde la primera llamada.

3 · Ejemplo mínimo

La llamada más pequeña posible, con la biblioteca estándar: sin dependencias, viendo el JSON crudo.

primera_llamada.py
# primera_llamada.py — primera llamada a Ollama usando solo la stdlib.
# Asi ves EXACTAMENTE que viaja por la red.
import json
import urllib.request

payload = {
    "model": "llama3.2",
    "messages": [{"role": "user", "content": "Di hola en una sola palabra."}],
    "stream": False,
}

req = urllib.request.Request(
    "http://localhost:11434/api/chat",
    data=json.dumps(payload).encode("utf-8"),
    headers={"Content-Type": "application/json"},
)

with urllib.request.urlopen(req, timeout=60) as resp:
    data = json.loads(resp.read().decode("utf-8"))

print("respuesta:", data["message"]["content"])
print("tokens salida:", data["eval_count"])
print("duracion (s):", round(data["total_duration"] / 1e9, 2))

Salida esperada:

respuesta: Hola
tokens salida: 2
duracion (s): 0.83

Línea por línea:

  1. payload: el diccionario que se convertirá en JSON. messages es la conversación; stream: False pide todo de golpe.
  2. json.dumps(...).encode("utf-8"): convierte el dict a bytes UTF-8. Sin el encode, urllib no acepta el cuerpo.
  3. headers={"Content-Type": "application/json"}: le dice al servidor que el cuerpo es JSON. Omitirlo provoca errores crípticos.
  4. urlopen(req, timeout=60): siempre con timeout. Una llamada sin timeout puede colgar tu programa indefinidamente.
  5. data["message"]["content"]: el texto generado vive en message.content; las métricas, en la raíz.

La puerta al modelo, completa:

proyectos/copiloto/src/copiloto/llm.py
# src/copiloto/llm.py — puerta unica al modelo: streaming, metricas y errores.
import os
import time
from dataclasses import dataclass, field

from ollama import Client, ResponseError

OLLAMA_HOST = os.environ.get("OLLAMA_HOST", "http://localhost:11434")
DEFAULT_MODEL = os.environ.get("COPILOTO_MODEL", "llama3.2")


@dataclass
class Reply:
    text: str
    prompt_tokens: int = 0
    output_tokens: int = 0
    done_reason: str = "stop"
    seconds_to_first_token: float = 0.0
    total_seconds: float = 0.0


def _client() -> Client:
    return Client(host=OLLAMA_HOST)


def ask(prompt: str, *, model: str = DEFAULT_MODEL,
        temperature: float = 0.0) -> Reply:
    """Pide una respuesta completa (sin streaming) y devuelve metricas."""
    try:
        started = time.perf_counter()
        r = _client().chat(
            model=model,
            messages=[{"role": "user", "content": prompt}],
            options={"temperature": temperature},
            stream=False,
        )
    except ConnectionError as e:
        raise RuntimeError(
            f"Ollama no responde en {OLLAMA_HOST}. ¿Está arrancado?"
        ) from e
    except ResponseError as e:
        raise RuntimeError(f"Error del modelo ({e.status_code}): {e.error}") from e

    return Reply(
        text=r.message.content,
        prompt_tokens=r.prompt_eval_count,
        output_tokens=r.eval_count,
        done_reason=r.done_reason,
        total_seconds=time.perf_counter() - started,
    )


def ask_stream(prompt: str, *, model: str = DEFAULT_MODEL):
    """Genera la respuesta token a token y mide la latencia al primer token."""
    started = time.perf_counter()
    first = None
    for chunk in _client().chat(
        model=model,
        messages=[{"role": "user", "content": prompt}],
        stream=True,
    ):
        piece = chunk.message.content
        if piece and first is None:
            first = time.perf_counter() - started
        yield piece, first

Y la CLI que lo usa:

proyectos/copiloto/src/copiloto/cli.py
# src/copiloto/cli.py — "copiloto ask" y "copiloto stream".
import typer

from copiloto.llm import ask, ask_stream

app = typer.Typer(help="Copiloto: asistente sobre los cursos de la Academy.")


@app.command()
def ask(prompt: str, stream: bool = True) -> None:
    """Pregunta algo al modelo local."""
    if not stream:
        reply = ask(prompt)
        print(reply.text)
        print(f"· {reply.output_tokens} tokens en {reply.total_seconds:.2f}s")
        return

    for piece, first in ask_stream(prompt):
        print(piece, end="", flush=True)          # flush: sin el, nada se ve
    print()
    if first is not None:
        print(f"· primer token en {first:.2f}s")


if __name__ == "__main__":
    app()

Decisiones y porqués:

  • OLLAMA_HOST y COPILOTO_MODEL por entorno: mismo binario, distinta configuración. Sin tocar el código.
  • ask vs ask_stream: dos usos reales. ask para cuando quieres la respuesta completa y sus métricas; ask_stream para la experiencia interactiva.
  • Errores traducidos: ConnectionError y ResponseError se convierten en RuntimeError con un mensaje accionable. El usuario no ve un stack trace de red.
  • flush=True: sin él, Python podría acumular la salida y arruinar el efecto del streaming.
  • Medición desde el día uno: seconds_to_first_token y total_seconds son las dos cifras que definen la sensación de velocidad de tu app.

Este llm.py crecerá en el módulo 2 (reintentos con backoff, tool calling, multiproveedor), pero el contrato —una función que entra texto y sale un Reply con métricas— ya no cambia. La buena arquitectura consiste en acertar la frontera temprano.

6 · Errores habituales

Guardar el .env en el repositorio

Mal — secretos versionados 
# ❌ El .env con claves reales viaja al repo y queda en el historial para siempre.
git add .env
git commit -m "config"
Bien — ignorado y con ejemplo 
# ✅ .env en .gitignore; se versiona solo el .env.example sin valores.
grep -q '^.env$' .gitignore || echo '.env' >> .gitignore
git add .gitignore .env.example

No poner timeout ni manejar la caída del servidor

Mal — sin timeout ni control 
# ❌ Si Ollama esta apagado o tarda, esto cuelga o revienta sin contexto.
r = client.chat(model="llama3.2", messages=msgs)
Bien — timeout y error traducido 
# ✅ El cliente admite timeout; y traducimos la excepcion a algo util.
try:
    client = Client(host=OLLAMA_HOST, timeout=60.0)
    r = client.chat(model=model, messages=msgs)
except ConnectionError as e:
    raise RuntimeError("Ollama no responde; ¿esta arrancado?") from e

Olvidar flush=True al streamear

Mal — salida "a saltos" 
# ❌ Sin flush, el texto puede bufferease: el usuario no ve el streaming.
for chunk in stream:
    print(chunk.message.content, end="")
Bien — vaciar el buffer 
# ✅ flush fuerza a mostrar cada trozo en cuanto llega.
for chunk in stream:
    print(chunk.message.content, end="", flush=True)

Tratar la salida como si fuera determinista

Mal — parsear sin validar 
# ❌ parsear texto libre del modelo y confiar en que el formato es el esperado.
data = json.loads(reply.text)     # puede no ser JSON valido
Bien — pedir formato y validar 
# ✅ Pide JSON al modelo y valida con pydantic; si falla, reintenta (modulo 1).
from pydantic import ValidationError
try:
    invoice = Invoice.model_validate_json(reply.text)
except ValidationError:
    reply = ask(prompt + "\nDevuelve SOLO JSON valido.")   # reintento controlado

No medir la latencia

Mal — a ciegas 
# ❌ "Creo que va rapido": sin medir no hay ingenieria ni decision posible.
reply = ask(prompt)
print(reply.text)
Bien — medir y registrar 
# ✅ Anota tokens y tiempos; son tus constantes para el modulo de coste.
reply = ask(prompt)
print(f"{reply.output_tokens} tok en {reply.total_seconds:.2f}s "
      f"({reply.output_tokens / reply.total_seconds:.1f} tok/s)")

8 · Reto

🎯 Streaming cancelable con métricas

Mejora ask_stream para que: (1) sea cancelable —si el usuario pulsa Ctrl+C, se detiene limpiamente sin dejar el programa colgado—; (2) acumule la respuesta completa y, al terminar, devuelva un Reply con el texto entero, el número de tokens y los dos tiempos (al primer token y total); (3) funcione también como generador asíncrono con AsyncClient para integrarlo más adelante en una API. Escribe además una prueba que verifique que cancelar tras el primer token no lanza excepciones raras.

Pista: envuelve el bucle en try/except KeyboardInterrupt y cierra el generador con .close() si hace falta. Para lo asíncrono, el SDK ofrece AsyncClient y async for. Para acumular, concatena los chunk.message.content en una lista y únelos al final con "".join(...). Piensa qué métrica debería devolver cada modo, sin inventar datos que no tengas.

9 · Resumen

  • Toda llamada a un LLM es un POST con JSON (/api/chat en Ollama) y una respuesta JSON con texto + métricas.
  • Puedes hablar por HTTP directo (útil para entender y depurar) o por el SDK de Python (cómodo para la app). El SDK hace lo mismo por dentro.
  • El streaming reduce la latencia percibida: mide la latencia al primer token, no solo la total.
  • Maneja ConnectionError y ResponseError con mensajes accionables, y pon siempre un timeout.
  • Configura por variables de entorno; en local desde .env (ignorado) y documenta con .env.example. Cero claves en el repositorio.
  • El Copiloto concentra el acceso al modelo en llm.py, con una respuesta normalizada (Reply) que ya incluye tokens y tiempos.

10 · Preguntas frecuentes

¿Uso HTTP directo o el SDK?

En el código de la aplicación, el SDK: es más corto y ya resuelve streaming y errores. Usa HTTP directo para aprender y para depurar: ver el JSON crudo aclara qué espera el servidor y qué devuelve. Saber hacer las dos cosas te da independencia del SDK de turno.

¿Por qué me llega la respuesta a trozos aunque no pida streaming?

Si no pides stream: false, el valor por defecto de /api/chat es true. Muchos clientes acumulan los trozos y te los dan «enteros», pero por debajo está llegando por partes. Si no quieres streaming, indícalo explícitamente.

¿Por qué veo un ResponseError con código 404?

Casi siempre significa que el modelo no está descargado. Ejecuta ollama pull llama3.2 y comprueba con ollama list. Es un error de configuración, no del código: tu llamada es correcta, falta el modelo.

¿Cómo pruebo sin arrancar Ollama cada vez?

Separa el cliente en una función (llm.ask) y en los tests sustitúyela por un doble que devuelva un Reply fijo. Así la lógica determinista se testea sin tocar el modelo. En el módulo 2 y en el de evals profundizaremos en cómo aislar el modelo para testear.

¿Qué hago si el primer token tarda muchísimo la primera vez?

Es normal: la primera llamada carga el modelo en memoria (load_duration). Las siguientes son más rápidas porque el modelo se queda cargado un tiempo. Puedes controlar ese tiempo con keep_alive. Mide siempre la llamada «en caliente» si comparas modelos.
