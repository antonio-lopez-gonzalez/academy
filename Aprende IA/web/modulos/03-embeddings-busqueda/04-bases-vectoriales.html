Bases vectoriales

Módulo 3 · Embeddings y búsqueda semántica 🕐 35 minutos

1 · Introducción

En la lección 2 buscamos vecinos con un array de numpy y un argsort. Funciona… mientras el corpus viva en memoria y quepa en un proceso. Pero Copiloto necesita persistencia (los vectores sobreviven al reinicio), filtros («busca solo en el módulo 4»), actualizaciones incrementales (cambió una lección) y, algún día, quizá millones de vectores. Eso es una base vectorial.

Buenas noticias: no siempre necesitas una base vectorial dedicada. Con PostgreSQL (pgvector) o SQLite (sqlite-vec) tienes vectores, metadatos y SQL en el mismo sitio. Esta lección te da el criterio para elegir, el SQL concreto y el patrón que casi siempre gana en calidad: la búsqueda híbrida (vectorial + BM25).

¿Por qué existe esta lección? Porque aquí es donde se decide «qué motor» y mucha gente salta directo a una base vectorial de moda para un corpus de 5.000 chunks, añadiendo infra que no aporta nada. Queremos que elijas por datos y por restricciones, no por hype.

Definición: una base vectorial es un almacén que guarda vectores junto a metadatos y responde a consultas del tipo «los k vectores más cercanos a este», con opción de filtrar por campos. Por debajo usa un índice vectorial (o búsqueda plana) para acelerar.

2 · Teoría

Índices vectoriales: exacto vs. aproximado

Buscar los k vecinos más cercanos de verdad, comparando contra todos, es la búsqueda exacta (flat / fuerza bruta): O(N·d). Es perfecta y simple; solo se vuelve lenta cuando N es enorme. Los índices aproximados (ANN, Approximate Nearest Neighbors) sacrifican un poco de exactitud a cambio de mucha velocidad y menos memoria:

ÍndiceCómo funcionaVentajaCoste
Flat (exacto) Compara contra todos los vectores 100% de recall; cero parámetros O(N·d): lento e inviable a gran escala
HNSW Grafo navegable por capas (estilo «saltos») Excelente recall y latencia; el estándar Más memoria; construcción más lenta; parámetros (m, ef)
IVF Agrupa vectores en «listas» y busca solo en las cercanas Poca memoria; rápido de construir Hay que «entrenarlo»; recall depende de las listas visitadas

La idea que hay que llevarse: flat cuando el corpus cabe; HNSW cuando crece. El Copiloto, con unos miles de chunks, funciona de sobra con flat dentro de pgvector o sqlite-vec (que también indexan sin índice ANN).

Analogía: buscar en un diccionario. Flat es leerlo entero hasta encontrar la palabra: infalible y lento. HNSW es un índice con «saltos»: abres por la letra y afinas: casi siempre llegas a la palabra correcta en unos pocos pasos, pero en casos raros te pasas de largo. La aproximación no es un defecto: es un intercambio deliberado.

pgvector: vectores dentro de PostgreSQL

pgvector es una extensión de PostgreSQL que añade el tipo vector(n) y operadores de distancia. Su gran baza: vives en una sola base de datos para vectores, metadatos, filtros, joins y transacciones. Define los operadores (¡ojo, devuelven distancia: menor es mejor!):

OperadorDistanciaÍndice
<->Euclídea (L2)vector_l2_ops
<=>Cosenovector_cosine_ops
<#>Producto interno negativovector_ip_ops
copiloto/sql/schema.sql
-- 1. Habilitar la extension (una vez por base de datos).
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Tabla de chunks: vector + metadatos en la misma fila.
CREATE TABLE chunks (
    chunk_id     text PRIMARY KEY,          -- p. ej. '03-04::s2::c1'
    lesson_id    text NOT NULL,             -- '03-04'
    module_id    text NOT NULL,             -- '03'
    section      text,                      -- titulo de la seccion
    source_path  text NOT NULL,
    model        text NOT NULL,             -- con que modelo se genero
    content      text NOT NULL,             -- el texto del chunk
    embedding    vector(384) NOT NULL       -- la dimension debe coincidir con el modelo
);

-- 3. Indice HNSW para distancia coseno (omitelo si usas busqueda plana).
--    Opera sobre vecores normalizados -> la distancia coseno es la que queremos.
CREATE INDEX chunks_embedding_idx ON chunks
    USING hnsw (embedding vector_cosine_ops);

-- 4. Indice de metadatos para filtros rapidos por modulo/leccion.
CREATE INDEX chunks_module_idx ON chunks (module_id);

Y así se busca desde Python con psycopg y pgvector. La consulta devuelve los vecinos ordenados por distancia coseno ascendente:

copiloto/src/copiloto/store_pg.py (fragmento)
# store_pg.py — insertar y buscar chunks en PostgreSQL + pgvector.
import psycopg
from pgvector import Vector
from pgvector.psycopg import register_vector

def connect(dsn: str) -> psycopg.Connection:
    conn = psycopg.connect(dsn)               # dsn desde el entorno, NUNCA en el repo
    register_vector(conn)                     # ensena a psycopg el tipo vector
    return conn

def upsert_chunk(conn, *, chunk_id, content, embedding, **meta) -> None:
    conn.execute(
        """
        INSERT INTO chunks (chunk_id, lesson_id, module_id, section,
                            source_path, model, content, embedding)
        VALUES (%s, %s, %s, %s, %s, %s, %s, %s)
        ON CONFLICT (chunk_id) DO UPDATE SET
            content = EXCLUDED.content,
            embedding = EXCLUDED.embedding
        """,
        (chunk_id, meta["lesson_id"], meta["module_id"], meta["section"],
         meta["source_path"], meta["model"], content, Vector(embedding)),
    )
    conn.commit()

def search(conn, query_embedding, k: int = 5, module_id: str | None = None):
    # El patron importante: FILTRAR por metadato + ordenar por distancia.
    # <=> es distancia coseno; ASC porque en distancia MENOR es mejor.
    sql = """
        SELECT chunk_id, lesson_id, section, content,
               1 - (embedding <=> %s) AS similarity
        FROM chunks
        WHERE (%s::text IS NULL OR module_id = %s)
        ORDER BY embedding <=> %s
        LIMIT %s
    """
    rows = conn.execute(sql, (Vector(query_embedding), module_id, module_id,
                              Vector(query_embedding), k)).fetchall()
    return rows

Detalles que importan:

  • Distancia, no similitud: ORDER BY embedding <=> q ASC. La columna similarity se calcula como 1 - distancia solo para mostrarla.
  • ON CONFLICT ... DO UPDATE: reindexar una lección cambiada es un upsert por chunk_id, no un borrado masivo. La persistencia y la clave estable (lección 3) se combinan.
  • Filtro + índice: WHERE module_id = ... reduce candidatos antes del ranking. Con el índice HNSW, PostgreSQL combina el filtro con la búsqueda vectorial.
  • La dimensión vector(384) es fija: debe casar con el modelo. Cambiar de modelo implica migración y reindexado.

sqlite-vec: el más pequeño posible

sqlite-vec lleva la búsqueda vectorial a SQLite: un solo archivo, cero servidores, perfecto para el Copiloto local o para tests. Usa «tablas virtuales» vec0 que declaras con la dimensión y columnas de metadato, y responde con MATCH + k.

copiloto/sql/sqlite.sql
-- Tabla virtual vec0: vector + metadatos declarados como columnas.
CREATE VIRTUAL TABLE chunks USING vec0(
    chunk_id    text PRIMARY KEY,
    embedding   float[384],
    module_id   text,
    lesson_id   text,
    section     text
);

-- Busqueda KNN: MATCH (vector) + k = N, ordenada por distance (menor = mejor).
-- Los filtros de metadato van en el mismo WHERE y se aplican durante la busqueda.
SELECT chunk_id, section, distance
FROM chunks
WHERE embedding MATCH :query_vector
  AND k = 5
  AND module_id = '03'
ORDER BY distance;

Dos alcances distintos en sqlite-vec: el MATCH ... k = N hace la búsqueda KNN, y las condiciones de metadato filtran los resultados. Pero para un filtrado verdaderamente selectivo (poca proporción del corpus) conviene usar una partition key o filtrar antes en una tabla normal. Con un WHERE module_id = '03' que deja fuera el 90% del corpus, un índice plano puede visitar miles de vectores «inútiles». Lo verás al medir.

copiloto/src/copiloto/store_sqlite.py (fragmento)
# store_sqlite.py — cargar la extension y buscar con sqlite-vec.
import sqlite3, struct
import sqlite_vec

def connect(path: str = "copiloto.db") -> sqlite3.Connection:
    db = sqlite3.connect(path)
    db.enable_load_extension(True)
    sqlite_vec.load(db)                     # registra las funciones vec_* y el tipo vec0
    db.enable_load_extension(False)
    return db

def to_blob(vector) -> bytes:
    # Compacto: N floats empaquetados, mejor que JSON para vectores grandes.
    return struct.pack(f"{len(vector)}f", *vector)

def search(db, query_vector, k: int = 5):
    rows = db.execute(
        """
        SELECT chunk_id, section, distance
        FROM chunks
        WHERE embedding MATCH ? AND k = ?
        ORDER BY distance
        """,
        (to_blob(query_vector), k),
    ).fetchall()
    return rows

Fíjate en los paralelismos y en las diferencias:

  • distance, no similitud: igual que en pgvector, menor es mejor. La similitud coseno de una búsqueda es 1 - distance (si indexaste con coseno).
  • to_blob: pasar vectores como bytes empaquetados (struct.pack) es mucho más rápido y compacto que JSON. Acepta ambas formas, pero prefiere el blob.
  • Sin servidor: la base es un archivo. Copias, versionas o borras el índice sin infraestructura. Ideal para el desarrollo y los tests del Copiloto.

Filtrado por metadato: dónde se aplica es la pregunta

«Busca en el módulo 4» puede implementarse de dos maneras, y la diferencia es enorme:

EstrategiaCómoCuándo conviene
Pre-filtrado (filter-then-search) Reduce el conjunto y busca solo dentro Filtro selectivo (deja poco corpus). Más preciso.
Post-filtrado (search-then-filter) Busca top-k global y descarta los que no cumplen Filtro poco selectivo. Sencillo, pero puede devolver menos de k.

El problema clásico es el post-filtrado: pides top-10, filtras a «módulo 4», y solo sobreviven 2. Si filtras antes, garantizas k resultados relevantes. Por eso las bases vectoriales serias ofrecen operadores de filtro durante la búsqueda (como el WHERE de vec0 o el índice parcial de pgvector).

Búsqueda híbrida: vectorial + BM25

Recordemos el límite de la lección 1: los embeddings capturan tema, no exactitud. «uv sync --frozen» o «data-module="03"» se recuperan mejor con búsqueda léxica por palabra clave. La familia clásica es BM25 (una versión ponderada de «cuenta cuántas palabras de la consulta aparecen, penalizando las frecuentes»); en SQLite se implementa con FTS5.

   consulta
      |
      +-- vectorial (embeddings) ---> ranking por significado
      |
      +-- lexica   (BM25/FTS5)  ---> ranking por palabras exactas
      |
      v
   FUSION (RRF: 1/(60+rank) sumado)  ---> ranking final
copiloto/sql/hybrid.sql
-- Tabla FTS5 (indice invertido) con el texto de los chunks.
CREATE VIRTUAL TABLE chunks_fts USING fts5(
    chunk_id UNINDEXED,
    content,
    tokenize = 'unicode61'
);

-- Fusion RRF: combina el ranking vectorial y el lexico sin calibrar escalas.
-- Cada rama aporta 1/(RRF_K + posicion); sumamos y ordenamos de mayor a menor.
WITH vector AS (
    SELECT chunk_id, ROW_NUMBER() OVER (ORDER BY distance) AS rank
    FROM chunks
    WHERE embedding MATCH :query_vector AND k = 20
),
lexical AS (
    SELECT chunk_id, ROW_NUMBER() OVER (ORDER BY bm25(chunks_fts)) AS rank
    FROM chunks_fts
    WHERE chunks_fts MATCH :query_text
    LIMIT 20
)
SELECT chunk_id, SUM(1.0 / (60 + rank)) AS rrf_score
FROM (SELECT chunk_id, rank FROM vector
      UNION ALL
      SELECT chunk_id, rank FROM lexical)
GROUP BY chunk_id
ORDER BY rrf_score DESC
LIMIT 5;

Dos ideas que hacen que esto funcione:

  • RRF (Reciprocal Rank Fusion): en vez de sumar puntuaciones de escalas incompatibles (similitud coseno 0–1 vs. BM25 sin cota), se combinan posiciones. Cada lista aporta 1/(60 + rank). Simple, robusto y sin parámetros que calibrar. 60 es la constante habitual.
  • Consultas distintas por rama: la vectorial usa el embedding de la pregunta; la léxica usa el texto de la pregunta (o palabras clave extraídas). Ambas contribuyen al mismo ranking final.

¿Cuál elijo? Criterio, no moda

EscenarioElección recomendada
Prototipo, demo, tests, app de escritorio, un solo usuariosqlite-vec (+ FTS5 para híbrida)
Ya tienes PostgreSQL en producción; quieres metadatos, joins y transaccionespgvector
Pocos miles de chunks, quieres cero infraestructuranumpy en memoria (lección 2) o sqlite-vec plano
Miles de millones de vectores, servidores dedicados, multi-tenantBase vectorial dedicada (Qdrant, Milvus…)
Necesitas lo exacto (comandos, versiones) además de lo semánticoHíbrida vectorial + BM25 sobre cualquiera de las anteriores

Regla del curso: empieza con SQLite + sqlite-vec (local, sin servidor) y deja pgvector listo como camino de producción. Ambas hablan el mismo «modelo mental» (vector + metadatos + filtro + distancia), así que migrar entre ellas es cambiar el driver, no la arquitectura. Y en las dos, añade la rama léxica si tu dominio tiene identificadores y comandos — el nuestro los tiene.

3 · Ejemplo mínimo

Todo el ciclo con sqlite-vec: crear la tabla, insertar tres vectores y buscar el más cercano. Sin servidor ni dependencias de red.

vector-lab/src/vec_min.py
# vec_min.py — sqlite-vec mas pequeno posible.
import sqlite3, struct
import sqlite_vec

def to_blob(vec: list[float]) -> bytes:
    return struct.pack(f"{len(vec)}f", *vec)

db = sqlite3.connect(":memory:")              # en memoria: no deja archivo
db.enable_load_extension(True)
sqlite_vec.load(db)                           # carga la extension vec0
db.enable_load_extension(False)

# 1. Tabla virtual con una columna vectorial de 3 dimensiones (juguete).
db.execute("CREATE VIRTUAL TABLE items USING vec0(item_id text PRIMARY KEY, v float[3])")

# 2. Insertamos tres vectores normalizados.
rows = [("a", [1.0, 0.0, 0.0]), ("b", [0.0, 1.0, 0.0]), ("c", [0.707, 0.707, 0.0])]
for item_id, vec in rows:
    db.execute("INSERT INTO items(item_id, v) VALUES (?, ?)", (item_id, to_blob(vec)))

# 3. KNN: el vector de consulta mira hacia a y c.
query = struct.pack("3f", 0.9, 0.2, 0.0)
for item_id, distance in db.execute(
    "SELECT item_id, distance FROM items WHERE v MATCH ? ORDER BY distance LIMIT 2",
    (query,),
):
    print(item_id, round(distance, 4))

Salida esperada:

a 0.0243
c 0.2187

Lo que demuestra, paso a paso:

  1. sqlite_vec.load(db): activa el tipo vec0 y las funciones de distancia. Es lo único «especial» respecto a SQLite normal.
  2. CREATE VIRTUAL TABLE ... vec0: declara la dimensión (float[3]) al crear la tabla. La dimensión queda fijada como en pgvector.
  3. to_blob: los vectores viajan como bytes empaquetados, la forma más rápida para el motor.
  4. MATCH ... ORDER BY distance: la búsqueda KNN. El resultado trae la distance: menor es más cercano. a gana porque su dirección es la más parecida a la consulta.

4 · Ejemplo real

El almacén del Copiloto: sqlite-vec para los vectores y FTS5 para la rama léxica, fusionadas con RRF. Este es el «motor de búsqueda» que el pipeline de RAG (Módulo 4) consultará.

copiloto/src/copiloto/store.py (fragmento)
# store.py — indexado y busqueda hibrida (vectorial + BM25) sobre SQLite.
from __future__ import annotations
import sqlite3, struct
import numpy as np
import sqlite_vec

SCHEMA = """
CREATE VIRTUAL TABLE IF NOT EXISTS chunks USING vec0(
    chunk_id text PRIMARY KEY,
    embedding float[384],
    module_id text,
    lesson_id text
);
CREATE VIRTUAL TABLE IF NOT EXISTS chunks_fts USING fts5(
    chunk_id UNINDEXED, content
);
"""

def connect(path: str = "copiloto.db") -> sqlite3.Connection:
    db = sqlite3.connect(path)
    db.enable_load_extension(True)
    sqlite_vec.load(db)
    db.enable_load_extension(False)
    db.executescript(SCHEMA)
    db.execute("PRAGMA journal_mode=WAL")     # mejor concurrencia lectura/escritura
    return db

def _blob(vec) -> bytes:
    return struct.pack(f"{len(vec)}f", *vec)

def index_chunks(db, chunks, embeddings) -> None:
    """Indexa en transaccion: vectores en vec0 y texto en FTS5."""
    with db:                                   # commit/rollback automatico
        for chunk, vec in zip(chunks, embeddings, strict=True):
            db.execute("DELETE FROM chunks WHERE chunk_id = ?", (chunk.chunk_id,))
            db.execute("DELETE FROM chunks_fts WHERE chunk_id = ?", (chunk.chunk_id,))
            db.execute(
                "INSERT INTO chunks(chunk_id, embedding, module_id, lesson_id) VALUES (?, ?, ?, ?)",
                (chunk.chunk_id, _blob(vec), chunk.module_id, chunk.lesson_id),
            )
            db.execute(
                "INSERT INTO chunks_fts(chunk_id, content) VALUES (?, ?)",
                (chunk.chunk_id, chunk.text),
            )

def _vector_candidates(db, query_vector, k: int) -> list[str]:
    rows = db.execute(
        "SELECT chunk_id FROM chunks WHERE embedding MATCH ? AND k = ? ORDER BY distance",
        (_blob(query_vector), k),
    ).fetchall()
    return [r[0] for r in rows]

def _lexical_candidates(db, query_text: str, k: int) -> list[str]:
    # bm25(): menor es mejor. Escapamos comillas para evitar inyeccion en FTS.
    safe = query_text.replace('"', '""')
    rows = db.execute(
        "SELECT chunk_id FROM chunks_fts WHERE chunks_fts MATCH ? ORDER BY bm25(chunks_fts) LIMIT ?",
        (f'"{safe}"', k),
    ).fetchall()
    return [r[0] for r in rows]

def hybrid_search(db, query_vector, query_text, k: int = 5, rrf_k: int = 60):
    """Reciprocal Rank Fusion de los rankings vectorial y lexico."""
    vec_rank = {cid: i for i, cid in enumerate(_vector_candidates(db, query_vector, k=20))}
    lex_rank = {cid: i for i, cid in enumerate(_lexical_candidates(db, query_text, k=20))}
    scores: dict[str, float] = {}
    for cid in set(vec_rank) | set(lex_rank):
        score = 0.0
        if cid in vec_rank:
            score += 1.0 / (rrf_k + vec_rank[cid])
        if cid in lex_rank:
            score += 1.0 / (rrf_k + lex_rank[cid])
        scores[cid] = score
    ranked = sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:k]
    return ranked

Decisiones y porqués:

  • Dos índices, un almacén: chunks (vec0) para la búsqueda semántica y chunks_fts (FTS5) para la léxica. Comparten chunk_id, así que fusionar es trivial.
  • Indexado por transacción: with db: garantiza que vectores y texto entren juntos o no entren. Nada de índices a medias.
  • Borrado por chunk_id antes de insertar: indexado incremental idempotente (el reto de la lección 3 encaja aquí).
  • RRF: no comparamos la distance de sqlite-vec con bm25() (escalas distintas); combinamos posiciones. Robusto y sin calibración.
  • Candidatos amplios (20) y resultado corto (5): cada rama aporta su «pool» y la fusión devuelve lo mejor de ambos. Súbelo si mides que falta recall.
  • WAL: permite leer mientras se escribe; útil si la CLI indexa en segundo plano.

Seguridad en FTS5: el texto de la consulta entra en MATCH, que tiene su propia sintaxis. Escapar comillas y no interpolar a lo bruto evita que una pregunta del usuario rompa la consulta (o peor). Es el mismo principio que la seguridad de prompt (Módulo 1): desconfía de la entrada.

5 · Buenas prácticas

HazEvitaPor qué
Elige el motor por restricciones reales (escala, infra, equipo) Adoptar una base vectorial dedicada para 5.000 chunks Infra que no aporta precisión es coste y superficie de fallo. SQLite/pgvector cubren el caso típico.
Empieza con búsqueda flat; añade HNSW cuando midas latencia Meter HNSW desde el día uno «por si acaso» Un índice ANN añade memoria, parámetros y pérdida de recall. No lo necesitas hasta que lo necesitas.
Filtra antes cuando el filtro es selectivo Post-filtrar un top-k global y quedarte sin resultados El post-filtrado puede devolver menos de k o candidatos irrelevantes. Pre-filtrar garantiza k útiles.
Combina vectorial + BM25 (RRF) cuando haya términos exactos Confiar solo en embeddings para comandos y versiones Lo léxico cubre lo que el vector no distingue: identificadores, flags y nombres de API.
Normaliza y fija la dimensión alineada con el modelo Mezclar modelos o dimensiones en la misma columna La columna guarda una dimensión fija; comparar vectores de espacios distintos no significa nada.
Indexa en transacción y por chunk_id estable Recrear la tabla entera en cada arranque Upserts incrementales son seguros y rápidos; recrear arriesga estados a medias y pierde datos.
Mide recall y latencia con tu corpus Suponer que «el índice mágico lo ordena bien» La calidad del retrieval se mide (Módulo 4); los parámetros del índice (ef, listas) afectan al recall.

6 · Errores habituales

Tratar la distancia como similitud (otra vez, ahora con SQL)

❌ Incorrecto
-- <=> devuelve DISTANCIA coseno: el mejor es el MENOR.
SELECT chunk_id FROM chunks ORDER BY embedding <=> :query DESC LIMIT 5;   -- peores!
✅ Correcto
SELECT chunk_id, 1 - (embedding <=> :query) AS similarity
FROM chunks
ORDER BY embedding <=> :query ASC                                       -- menor distancia
LIMIT 5;

Si ordenas con DESC, devuelves los más lejanos. El error es idéntico al de la lección 2, pero un motor de base no te avisa: devuelve resultados.

Indice ANN sin medir el recall

❌ Incorrecto
-- HNSW con parametros por defecto... en un corpus donde flat seria instantaneo.
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
✅ Correcto
-- Con pocos miles de chunks: busca plana y mide. Si hace falta ANN, ajusta y MIDE el recall.
-- SELECT ... ORDER BY embedding <=> :q LIMIT 10;   (sin indice ANN)
-- CREATE INDEX ... USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

Un índice aproximado puede no devolver el vecino exacto. Está bien, siempre que lo sepas y lo midas. Añadirlo cuando no lo necesitas solo introduce una fuente de error.

Post-filtrar y quedarte con dos resultados

❌ Incorrecto
hits = search(db, q, k=10)                 # top-10 global
module4 = [h for h in hits if h.module_id == "04"]
# module4 puede tener 0, 1 o 2 elementos: el filtro se aplico DESPUES.
✅ Correcto
# Filtra DENTRO de la busqueda para garantizar k resultados del modulo 4.
hits = search(db, q, k=10, module_id="04")

Mezclar embeddings de modelos distintos en una tabla

❌ Incorrecto
# Un dia reindexas con otro modelo SIN vaciar: conviven espacios vectoriales.
db.execute("INSERT INTO chunks(embedding) VALUES (?)", (_blob(new_model_vec),))
✅ Correcto
# Cambiar de modelo = migracion completa: nueva tabla/columna y reindexado total.
# Guarda 'model' como columna y valida que todos los vectores son del mismo modelo.

Buscar solo con vectores en un dominio lleno de identificadores

❌ Incorrecto
query: "flag --frozen de uv sync"
# Solo vectorial: puede devolver "que es uv" y perderse el comentario exacto.
✅ Correcto
# Hibrida: la rama BM25 rescata el match exacto de "--frozen" y "uv sync"
# y la rama vectorial aporta el contexto semantico. Fusion con RRF.

CORPUS = [
    ("d1", "Para instalar dependencias de forma reproducible usa uv sync --frozen."),
    ("d2", "La similitud coseno mide el angulo entre dos vectores."),
    ("d3", "uv es un gestor de proyectos y entornos de Python."),
    ("d4", "BM25 es una funcion de ranking lexico clasica."),
]

def blob(v): return struct.pack(f"{len(v)}f", *v)

db = sqlite3.connect(":memory:")
db.enable_load_extension(True); sqlite_vec.load(db); db.enable_load_extension(False)
db.execute("CREATE VIRTUAL TABLE c USING vec0(id text PRIMARY KEY, e float[384])")
db.execute("CREATE VIRTUAL TABLE cfts USING fts5(id UNINDEXED, content)")

vecs = np.array(list(model.embed([t for _, t in CORPUS])))
for (cid, text), vec in zip(CORPUS, vecs, strict=True):
    db.execute("INSERT INTO c(id, e) VALUES (?, ?)", (cid, blob(vec)))
    db.execute("INSERT INTO cfts(id, content) VALUES (?, ?)", (cid, text))

def vector_search(q, k=3):
    v = np.array(next(iter(model.query_embed([q]))))
    return [r[0] for r in db.execute(
        "SELECT id FROM c WHERE e MATCH ? AND k = ? ORDER BY distance", (blob(v), k))]

def lexical_search(q, k=3):
    safe = q.replace('"', '""')
    return [r[0] for r in db.execute(
        "SELECT id FROM cfts WHERE cfts MATCH ? ORDER BY bm25(cfts) LIMIT ?", (f'"{safe}"', k))]

def rrf(q, k=3, rrf_k=60):
    ranks = {}
    for i, cid in enumerate(vector_search(q, 20)):  ranks.setdefault(cid, []).append(i)
    for i, cid in enumerate(lexical_search(q, 20)): ranks.setdefault(cid, []).append(i)
    scored = {cid: sum(1/(rrf_k + r) for r in rs) for cid, rs in ranks.items()}
    return sorted(scored, key=scored.get, reverse=True)[:k]

q = "uv sync --frozen"
print("vectorial:", vector_search(q))
print("lexica   :", lexical_search(q))
print("hibrida  :", rrf(q))

9 · Resumen

  • Una base vectorial guarda vectores + metadatos y responde a «los k más cercanos», con filtros.
  • Índices: flat (exacto), HNSW e IVF (aproximados). Flat hasta que la escala obligue a ANN, y entonces mide el recall.
  • pgvector: vectores dentro de PostgreSQL (vector(n), <=> coseno, HNSW). Ideal si ya tienes Postgres.
  • sqlite-vec: un archivo, sin servidor; tablas vec0, MATCH ... k, filtros por metadato. Ideal para el Copiloto local.
  • Siempre distancia (menor es mejor) en SQL; similitud = 1 - distancia.
  • Filtrado por metadato: pre-filtrar cuando es selectivo; el post-filtrado puede dejar menos de k.
  • Híbrida (vectorial + BM25 con RRF): cubre lo semántico y lo exacto; el patrón que mejor funciona con comandos y versiones.

10 · Preguntas frecuentes

¿Necesito una base vectorial dedicada (Qdrant, Milvus…)?

Para el Copiloto, no. Con miles de chunks, sqlite-vec o pgvector bastan y te dan metadatos y filtros sin infraestructura extra. Una base dedicada brilla con millones/miles de millones de vectores, multi-tenant o requisitos de latencia muy estrictos; entonces su complejidad se paga sola.

¿HNSW siempre es mejor que la búsqueda plana?

No. HNSW es más rápido a gran escala pero aproximado (puede no devolver el vecino exacto) y consume más memoria. Con corpus pequeños, flat es instantáneo y exacto. Añade HNSW cuando midas que la latencia lo pide, y entonces verifica el recall.

¿pgvector o sqlite-vec para el proyecto del curso?

Ambos: empieza con sqlite-vec (local, sin servidor, perfecto para desarrollo y tests) y deja pgvector como camino de producción. Comparten el mismo modelo mental, así que cambiar de uno a otro es cambiar el driver y el SQL, no rediseñar. El curso usa las dos: una principal y otra comparativa.

¿Qué es exactamente la búsqueda híbrida?

Combinar una búsqueda semántica (embeddings) con una léxica (BM25/FTS) y fusionar los rankings. Captura tanto paráfrasis como términos exactos, que es justo lo que necesita un corpus técnico. La fusión habitual, sencilla y robusta, es RRF, porque combina posiciones y evita calibrar escalas incompatibles.

¿Cómo sé si el filtro por metadato está bien aplicado?

Pruébalo con un filtro selectivo. Si pides k=5 filtrando por un módulo y recibes menos de 5 resultados, estás post-filtrando (mal): el filtro debería aplicarse dentro de la búsqueda para garantizar k candidatos que cumplan. En vec0 y en pgvector el filtro va en el mismo WHERE; verifícalo midiendo resultados devueltos.
