Observabilidad y trazas

Módulo 7 · Evals, calidad y producción 🕐 35 minutos

1 · Introducción

Hasta ahora evaluamos el comportamiento en lote: corremos el dataset y miramos los números. Pero en producción los fallos llegan de uno en uno, con entradas que no anticipaste, y una pregunta aparece en la cabeza: «¿por qué esta respuesta salió mal?». Sin un registro de lo que pasó por dentro, esa pregunta no tiene respuesta.

La observabilidad es registrar cada paso del sistema para poder reconstruirlo después. En una app con IA, un «paso» es mucho más que un log: es una traza con todas las llamadas encadenadas y sus números.

  • Registrar cada llamada: prompt, tokens, latencia, coste, modelo, motivo de parada.
  • Trazar el pipeline: retrieval → reranking → generación → tools, como un árbol de pasos.
  • Reproducir una mala respuesta: con las entradas, versiones y semilla que la produjeron.
  • OpenTelemetry: el estándar para exportar trazas sin atarte a un proveedor.

¿Por qué existe esta lección? Porque no puedes arreglar lo que no puedes ver. El módulo 2 te enseñó a medir una llamada; esta lección te enseña a guardar esas medidas para toda la vida del sistema y a reconstruir cualquier incidente. Es lo que separa «creo que el retrieval falló» de «el retrieval devolvió 0 fragmentos porque el índice estaba vacío: aquí está la traza».

2 · Teoría

Del log a la traza: el árbol de pasos

Un log es una línea suelta. Una traza es un árbol: una raíz (la petición del usuario) con hijos (cada paso), cada uno con su duración y sus datos. Un span es un nodo del árbol.

  TRACE  run_id=7f3a…  (pregunta: "¿qué es el chunking?")
  │
  ├─ span  retrieve          42 ms   fragmentos=4
  ├─ span  rerank            18 ms   top=3
  ├─ span  llm.chat         980 ms   in=1240 out=180  $0.0021
  ├─ span  tool.search_lessons  85 ms  ok
  └─ span  llm.chat          610 ms   in=980  out=95   $0.0014

Con ese árbol, un fallo se localiza en segundos: si retrieve devuelve 0 fragmentos, el problema es de índice, no del modelo; si llm.chat tardó 12 s, es latencia del proveedor.

Una traza es como el registro de una consulta médica: no solo la conclusión («tienes X»), sino qué pruebas se hicieron, en qué orden, cuánto tardaron y qué salió en cada una. Con la conclusión sola, un segundo médico no puede reproducir el diagnóstico; con el registro completo, sí.

Guarda el hash del prompt y del contexto, no el texto entero, si el volumen o la privacidad lo piden. Un hash te dice «mismo prompt que ayer» sin almacenar el contenido. Cuando necesites reproducir, guardas el texto completo solo de los casos muestreados o de los fallos.

Los tres pilares: trazas, métricas y logs

Se complementan; no pongas todo en el mismo sitio:

  • Trazas: el detalle de una petición (esta respuesta concreta). Para depurar.
  • Métricas: agregados en el tiempo (latencia p95, coste/día, tasa de abstención). Para vigilar.
  • Logs: eventos sueltos y errores (un timeout, un reintento). Para contexto puntual.

Un incidente se investiga así: una métrica se dispara («la latencia p95 subió»), entras en los logs, coges un run_id, y abres su traza para ver qué paso se salió de madre.

Reproducir una mala respuesta

Reproducir es recrear el fallo exacto. Necesitas capturar todo lo que influyó:

  • La entrada: la pregunta y el contexto recuperado (las mismas lecciones).
  • Las versiones: modelo, versión del prompt, versión del índice, parámetros de sampling.
  • La semilla: si el proveedor la soporta, para acercarte al mismo muestreo.

Los modelos no garantizan reproducibilidad bit a bit ni con temperatura 0. «Reproducir» significa acercarse lo suficiente para diagnosticar, no obtener el carácter exacto. Por eso la traza guarda también el output original: aunque no puedes recrearlo, sí puedes analizarlo.

OpenTelemetry: el estándar para no atarte

Podrías inventar tu propio formato de trazas. Pero OpenTelemetry (OTel) ya resuelve el modelo de datos, la propagación de contexto y los exportadores (a Jaeger, Grafana, Datadog, etc.). Adoptarlo te da:

  • Vendor-neutral: cambias de backend sin tocar el código.
  • Spans anidados con context manager (with tracer.start_as_current_span(...)).
  • Convenciones semánticas para IA generativa: nombres de atributos como gen_ai.* que las herramientas ya entienden.
  • Correlación con el resto de tu sistema (HTTP, base de datos) en la misma traza.

No necesitas OTel el primer día: una versión propia con dataclasses y un run_id ya aporta el 80%. Pero si el sistema va a producción de verdad, OTel evita reinventar y te conecta con el ecosistema de observabilidad que ya usa tu equipo para el resto de servicios.

Cuidado con la PII en las trazas

Las trazas guardan prompts y respuestas, que pueden contener datos personales. Trátalas como datos sensibles: redacta antes de almacenar, controla el acceso y define retención. La lección 04 amplía el tema de PII; aquí basta la regla: si no lo guardarías en un log, no lo guardes en la traza.

3 · Ejemplo mínimo

Una traza sin dependencias: spans anidados con dataclasses y un run_id. Es la idea de OTel en treinta líneas, para ver la mecánica antes de usar el SDK.

trace_minimo.py
# trace_minimo.py — trazas propias para entender spans anidados.
import time
import uuid
from contextlib import contextmanager
from dataclasses import dataclass, field


@dataclass
class Span:
    name: str
    attrs: dict[str, object] = field(default_factory=dict)
    start: float = 0.0
    end: float = 0.0
    children: list["Span"] = field(default_factory=list)

    @property
    def ms(self) -> float:
        return (self.end - self.start) * 1000


class Tracer:
    def __init__(self) -> None:
        self.run_id = uuid.uuid4().hex[:8]
        self.root: Span | None = None
        self._stack: list[Span] = []

    @contextmanager
    def span(self, name: str, **attrs: object):
        s = Span(name=name, attrs=attrs, start=time.perf_counter())
        if self._stack:
            self._stack[-1].children.append(s)
        else:
            self.root = s
        self._stack.append(s)
        try:
            yield s
        finally:
            s.end = time.perf_counter()
            self._stack.pop()

    def render(self, span: Span | None = None, depth: int = 0) -> None:
        span = span or self.root
        if span is None:
            return
        attrs = " ".join(f"{k}={v}" for k, v in span.attrs.items())
        print(f"{'  ' * depth}├─ {span.name:<18} {span.ms:6.0f} ms  {attrs}")
        for child in span.children:
            self.render(child, depth + 1)


if __name__ == "__main__":
    t = Tracer()
    with t.span("run", question="¿qué es el chunking?"):
        with t.span("retrieve"):
            time.sleep(0.04)
        with t.span("llm.chat", model="llama3.1:8b", tokens=1420):
            time.sleep(0.12)
    print(f"run_id={t.run_id}")
    t.render()

Salida esperada:

run_id=7f3a91c2
├─ run                question=¿qué es el chunking?
  ├─ retrieve          42 ms
  ├─ llm.chat         120 ms  model=llama3.1:8b tokens=1420

Ya tienes lo esencial: un árbol con tiempos y atributos, anidado con un context manager. El run_id es la llave para encontrar la traza cuando un usuario reporta un problema. OTel hará lo mismo, pero exportable y con convenciones.

4 · Ejemplo real

El Copiloto. Instrumentamos el pipeline con OpenTelemetry: un span raíz por pregunta, spans hijos por paso y atributos gen_ai.* en las llamadas al modelo. Añadimos un envoltorio traced_chat que registra tokens, latencia y coste.

proyectos/copiloto/src/copiloto/telemetry.py
"""Configuración de OpenTelemetry para el Copiloto."""
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor


def setup_tracing(endpoint: str = "http://localhost:4318/v1/traces") -> trace.Tracer:
    """Registra un TracerProvider y devuelve un tracer listo para usar."""
    resource = Resource.create({"service.name": "copiloto"})
    provider = TracerProvider(resource=resource)
    provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(endpoint=endpoint)))
    trace.set_tracer_provider(provider)
    return trace.get_tracer("copiloto")


tracer = setup_tracing()
proyectos/copiloto/src/copiloto/llm.py (instrumentado)
"""Llamada al modelo envuelta en un span con tokens, latencia y coste."""
import time

from copiloto.telemetry import tracer

# Precio en USD por 1M tokens (ejemplo local: 0; nube: precios reales).
PRICE = {"in": 0.15 / 1_000_000, "out": 0.60 / 1_000_000}


def traced_chat(messages: list[dict], model: str, temperature: float = 0.0) -> dict:
    with tracer.start_as_current_span("llm.chat") as span:
        span.set_attribute("gen_ai.system", "ollama")
        span.set_attribute("gen_ai.request.model", model)
        span.set_attribute("gen_ai.request.temperature", temperature)

        start = time.perf_counter()
        response = _call_model(messages, model, temperature)   # SDK real
        latency_ms = (time.perf_counter() - start) * 1000

        usage = response["usage"]
        cost = usage["input_tokens"] * PRICE["in"] + usage["output_tokens"] * PRICE["out"]
        span.set_attribute("gen_ai.usage.input_tokens", usage["input_tokens"])
        span.set_attribute("gen_ai.usage.output_tokens", usage["output_tokens"])
        span.set_attribute("gen_ai.response.finish_reasons", [response["finish_reason"]])
        span.set_attribute("copiloto.latency_ms", latency_ms)
        span.set_attribute("copiloto.cost_usd", cost)
        return response

El pipeline completo como traza: cada paso abre su propio span hijo y queda anidado bajo el run.

proyectos/copiloto/src/copiloto/agent.py (instrumentado)
from copiloto.llm import traced_chat
from copiloto.retrieval import retrieve
from copiloto.telemetry import tracer


def run_agent(question: str) -> "Answer":
    with tracer.start_as_current_span("run") as root:
        root.set_attribute("copiloto.question", question)

        with tracer.start_as_current_span("retrieve") as s:
            fragments = retrieve(question)
            s.set_attribute("copiloto.fragments", len(fragments))   # ¡clave! si es 0, es el índice

        context = "\n\n".join(f.text for f in fragments)
        with tracer.start_as_current_span("generate") as s:
            answer = traced_chat(build_messages(question, context), model="llama3.1:8b")
            s.set_attribute("copiloto.answered", bool(answer["content"]))

        return Answer(text=answer["content"], fragments=fragments)

Contrato para reproducir cualquier mala respuesta: la traza guarda las entradas y las versiones; un comando las vuelve a ejecutar.

proyectos/copiloto/src/copiloto/replay.py
"""Reproduce una traza pasada para diagnosticar una mala respuesta."""
from copiloto.agent import run_agent

# El `run.json` se guarda por caso muestreado/fallido: entrada + versiones.
def replay(run: dict) -> None:
    print("versiones:", run["model"], run["prompt_version"], run["index_version"])
    fresh = run_agent(run["question"])
    print("respuesta original:", run["answer"][:200])
    print("respuesta actual  :", fresh.text[:200])
    # Compara: ¿cambió el retrieval? ¿el prompt? ¿el modelo?

Ejemplo de traza exportada (vista de árbol en Jaeger/Grafana):

run                                      1.24 s
├─ retrieve            fragments=0       3 ms     ← ¡aquí está el fallo!
├─ generate            answered=true   1.10 s
│  └─ llm.chat  in=210 out=140  $0.0001  1.05 s

retrieve devolvió 0 fragmentos: el modelo respondió sin contexto y por eso alucinó. La traza te ahorró horas de conjeturas. Decisiones y porqués:

  • Span raíz por pregunta (run): un run_id que liga todos los pasos, correlacionable con la sesión del usuario.
  • Spans hijos por paso: retrieve, generate, llm.chat; el árbol localiza el fallo al instante.
  • Atributos gen_ai.*: convención que las herramientas de observabilidad entienden sin configuración extra.
  • Tokens, latencia y coste por llamada: alimentan las métricas y el presupuesto de la lección 04.
  • Bandera de fragmentos: el atributo más usado en el día a día; distingue fallo de retrieval de fallo de generación.
  • Replay con versiones: sin la versión del prompt y del índice, «reproducir» es imposible.

Fíjate en cómo encajan las lecciones: el módulo 2 medía una llamada (coste_usd, latency_ms); aquí esos números se guardan en cada span. La observabilidad es la memoria del sistema; las evals son sus exámenes.

6 · Errores habituales

6.1. Guardar solo la respuesta final

Si no registras los pasos intermedios, un fallo es un misterio.

Incorrecto
# ❌ Log único: no sabes si falló el retrieval o el modelo.
print("respuesta:", run_agent(q).text)
Correcto
# ✅ Span por paso: fragmentos, tokens y latencia quedan registrados.
with tracer.start_as_current_span("retrieve") as s:
    fragments = retrieve(q)
    s.set_attribute("copiloto.fragments", len(fragments))   # 0 => fallo de índice

6.2. No guardar las versiones

El sistema cambia a diario; sin versión, el «replay» reproduce otra cosa y confunde más que ayuda.

Incorrecto
# ❌ Reejecutar con el prompt de hoy una traza de ayer.
replay(run)                 # ¿qué prompt usó ayer? no lo sabes
Correcto
# ✅ La traza lleva la versión; el replay la usa.
run = {"question": q, "prompt_version": "v3", "index_version": "2026-10-01", "model": "llama3.1:8b"}

6.3. Volcar el prompt completo sin redactar

Las trazas acaban en un backend externo; el prompt puede llevar datos personales.

Incorrecto
# ❌ Guardar el texto con datos del usuario tal cual.
span.set_attribute("copiloto.prompt", full_prompt_with_pii)
Correcto
# ✅ Hash para correlacionar; el texto solo en casos muestreados y redactado.
span.set_attribute("copiloto.prompt_hash", sha256(full_prompt))

7 · Ejercicio guiado

Objetivo: instrumentar el Copiloto con OpenTelemetry, localizar un fallo real por su traza y reproducirlo. Al terminar podrás responder «¿por qué salió mal esta respuesta?» con evidencia, no con opiniones.

  1. Paso 1 — levanta un backend y configura el tracer. Un contenedor con Jaeger o Grafana Tempo es suficiente: 
    docker run -d --name jaeger -p 16686:16686 -p 4318:4318 jaegertracing/all-in-one:latest
uv add opentelemetry-sdk opentelemetry-exporter-otlp-proto-http

    Importa setup_tracing() al arrancar el Copiloto y comprueba que aparece el servicio copiloto en el panel.

  2. Paso 2 — instrumenta los pasos. Envuelve retrieve, generate y cada llamada en un span con sus atributos. Añade como mínimo fragments, input_tokens, output_tokens y latency_ms: 
    with tracer.start_as_current_span("retrieve") as s:
    frags = retrieve(q)
    s.set_attribute("copiloto.fragments", len(frags))
  3. Paso 3 — provoca y localiza un fallo. Borra el índice vectorial (o apunta a uno vacío) y haz una pregunta. Abre la traza en el panel: 
    run                                   1.1 s
├─ retrieve          fragments=0       2 ms   ← el retrieval no devolvió nada
└─ generate          answered=true   1.0 s

    Esperado: ves fragments=0 y entiendes que el problema es de índice, no del modelo. Repuebla el índice y repite: ahora fragments=4.

  4. Paso 4 — reproduce una respuesta mala. Fuerza una respuesta infiel (prompt sin contexto, o temperatura alta) y guarda el run.json con entrada y versiones. Ejecuta el replay: 
    uv run python -m copiloto.replay runs/7f3a91c2.json
# versiones: llama3.1:8b prompt=v3 index=2026-10-01
# original: "El chunking divide en trozos de 512 tokens de Borges..."   (inventado)
# actual  : "El chunking trocea documentos con solape [03-chunking]."

    Compara: el original alucinó porque el retrieve vino vacío. Documenta la causa raíz con la traza delante.

  5. Paso 5 — convierte el fallo en métrica y en caso. Añade una métrica (contador de fragments=0) para vigilar el índice, y un caso de eval (lección 01) para la regresión. Cierra el bucle: observar → diagnosticar → reproducir → vigilar.

    Resultado esperado: un Copiloto que exporta trazas con tokens, latencia y coste; un fallo localizado por su traza; un replay con versiones; y una métrica que vigila la causa raíz. Acabas de hacer el sistema observable.

8 · Reto

🎯 Un panel de coste y latencia por versión

Convierte las trazas en un panel que te diga, de un vistazo, cómo va el sistema en producción. Requisitos:

  • Una métrica de coste acumulado por día y por modelo, a partir de los atributos de los spans.
  • Una métrica de latencia p50/p95 desglosada por paso (retrieve vs llm.chat): quieres saber si la lentitud es de tu código o del proveedor.
  • Un desglose por versión de prompt (usando prompt_hash): ¿la v3 es más cara o más lenta que la v2?
  • Una alerta cuando la tasa de fragments=0 supera un umbral (índice roto o desincronizado).

Pista: OTel también exporta métricas (no solo trazas); o agrega los spans en tu backend. Para el desglose por versión, basta con agrupar por el atributo prompt_hash. Recuerda redactar PII antes de agregar y muestrear si el volumen es alto. No resuelvas el reto con un print en cada llamada: el objetivo es una señal agregada y duradera, no ruido. Y cuidado con optimizar el coste a costa de la calidad: compáralo con las evals de las lecciones 01 y 02.

9 · Resumen

  • Una traza es un árbol de spans: cada paso del sistema con su duración y sus datos.
  • Registra por llamada: modelo, tokens, latencia, coste, hash del prompt y motivo de parada.
  • Los tres pilares: trazas (una petición), métricas (agregados) y logs (eventos).
  • Reproducir exige capturar entrada, versiones (prompt, modelo, índice) y parámetros de sampling.
  • OpenTelemetry da spans anidados, atributos gen_ai.* y exportación vendor-neutral.
  • Un fragments=0 en el span de retrieval distingue un fallo de índice de un fallo de modelo.
  • Redacta PII y muestrea: la traza es un dato sensible, no un vertedero.

10 · Preguntas frecuentes

¿En qué se diferencia una traza de un log normal?

Un log es una línea suelta; una traza es un árbol de pasos relacionados por un mismo run_id, con duración y jerarquía. El log te dice «ocurrió un evento»; la traza te dice «esta petición pasó por retrieve (3 ms), generate (1 s) y esta llamada tardó 980 ms». Para depurar un pipeline con IA, la jerarquía es imprescindible: necesitas saber en qué paso se rompió.

¿Necesito OpenTelemetry o me vale un formato propio?

Un formato propio con dataclasses y un run_id cubre la mayoría de las necesidades locales y es un buen punto de partida. Pero en producción, OTel aporta exportadores, convenciones (gen_ai.*), correlación con HTTP/base de datos y neutralidad de proveedor. Si vas a integrarte con el equipo de plataforma, usa OTel desde el principio. Si estás aprendiendo, empieza por lo propio y migra cuando duela.

¿Puedo reproducir exactamente la misma respuesta?

No de forma garantizada. Ni con temperature=0 los proveedores aseguran reproducibilidad bit a bit (batching, hardware, versiones del modelo). «Reproducir» aquí significa recrear el contexto suficiente para diagnosticar: mismas entradas, versiones y parámetros, y comparar salidas. Por eso la traza guarda también el output original: aunque no puedas regenerarlo idéntico, sí puedes analizarlo.

¿Cuánto texto debo guardar en las trazas?

Depende de tu privacidad y presupuesto. Estrategia pragmática: guarda siempre los atributos numéricos (tokens, latencia, coste) y los hashes; guarda el texto completo solo de una muestra y de los casos fallidos, con PII redactada y una política de retención clara. Así puedes reproducir los incidentes que importan sin almacenar todo el tráfico.

¿Las trazas afectan al coste o a la latencia del producto?

Diseñadas bien, no. El exportador usa batching: los spans se acumulan y se envían en lote en segundo plano, sin bloquear la petición. El impacto es mínimo si evitas serializar textos enormes en el hilo de respuesta. Ojo con el muestreo: en volumen alto, exportar el 100% de las trazas puede costar en el backend y en ancho de banda, aunque no en el modelo.
