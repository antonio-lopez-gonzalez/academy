Tools y handlers

Módulo 5 · Agentes y tools 🕐 35 minutos

1 · Introducción

Un agente sin tools es un modelo que solo puede hablar. Las tools son las manos del agente: lo que le permite buscar, calcular, leer archivos o consultar una base de datos. Pero una tool no es «una función que llamas»: es un contrato con dos caras que deben encajar perfectamente. Por un lado, el esquema que ve el modelo (nombre, descripción, parámetros) para decidir cuándo y con qué argumentos usarla. Por otro, el handler, el código Python que realmente la ejecuta y produce el resultado.

Casi todos los agentes que «van mal» fallan aquí, no en el modelo. El modelo elige mal la tool porque su descripción era ambigua; o el handler explota con una excepción porque los argumentos venían sin validar; o la tool devuelve 4 KB de texto que el modelo no puede aprovechar y contamina el resto del bucle. Ninguno de esos fallos es de «inteligencia»: son fallos de diseño del contrato. Y son, precisamente, los que tú controlas.

En esta lección aprendemos a diseñar ese contrato bien: un nombre que el modelo entienda, un esquema que acote lo que puede pedir, una descripción que le diga cuándo usar la tool, una validación que proteja al handler y una respuesta útil que el modelo pueda leer y seguir con el bucle. Todo sobre las tools reales del Copiloto: buscar lecciones, abrir un módulo y contar progreso.

¿Por qué existe esta lección? Porque el eslabón que más se descuida de un agente es el más barato de mejorar. Reescribir una descripción o validar un argumento no cuesta GPU ni tokens, pero arregla más fallos que cambiar de modelo. Antes de escalar el modelo, diseña bien la tool.

2 · Teoría

La analogía: el formulario del mostrador

Una tool es como un formulario de mostrador con ventanilla. Tú (el desarrollador) diseñas el formulario: qué casillas hay, cuáles son obligatorias y cómo se llama cada una. El modelo (el cliente) lo rellena. Si la casilla «fecha» no dice qué formato espera, el cliente escribirá «mañana» y el empleado de detrás (el handler) no sabrá qué hacer. Si el formulario tiene un campo llamado «dato» sin explicación, nadie sabrá qué poner. Y si el empleado, al recibir un formulario incompleto, se va a casa (excepción), se corta toda la cola. Diseñar tools es diseñar buenos formularios y un mostrador que no se cierra ante un error.

El esquema de una tool: las tres piezas que ve el modelo

Cada tool se declara con un esquema JSON. De todo él, el modelo usa tres piezas para decidir:

  • name: el identificador. Debe ser un verbo o frase corta en snake_case que diga qué hace (buscar_lecciones, contar_progreso). Nada de tool1 o hacer_cosa.
  • description: la frase que le dice al modelo cuándo usarla y qué devuelve. Es la pieza más importante y la que más se descuida. Es documentación que se ejecuta.
  • parameters: el esquema JSON de los argumentos (tipos, cuáles son obligatorios, valores permitidos). Es un contrato: limita lo que el modelo puede pedir y te da algo que validar.
{
  "type": "function",
  "function": {
    "name": "buscar_lecciones",
    "description": "Busca un tema en las lecciones de la Academy y devuelve las lecciones donde aparece, con su curso, modulo y archivo. Usala cuando el usuario pregunte DONDE se explica algo. NO la uses para contar lecciones (para eso usa contar_progreso).",
    "parameters": {
      "type": "object",
      "properties": {
        "consulta": {
          "type": "string",
          "description": "Tema o frase a buscar, en lenguaje natural. Ejemplo: 'bucle agentic', 'chunking'."
        },
        "limite": {
          "type": "integer",
          "description": "Numero maximo de resultados. Por defecto 5.",
          "default": 5
        }
      },
      "required": ["consulta"]
    }
  }
}

La descripción: el prompt que no escribiste

El modelo no ve tu código del handler. Solo ve el nombre, la descripción y el esquema. Por eso la descripción es un prompt: le dice al modelo cuándo usar la tool y cuándo no. Una buena descripción responde a tres preguntas:

PreguntaQué incluirEjemplo de fragmento
¿Qué hace? Acción concreta y resultado «Devuelve las lecciones donde aparece un tema»
¿Cuándo usarla? La intención del usuario que la dispara «Úsala cuando pregunte dónde se explica algo»
¿Cuándo NO usarla? La tool parecida con la que se confunde «No la uses para contar lecciones; para eso, contar_progreso»

La tercera fila es la que casi nadie escribe y la que más arregla. Cuando tienes dos tools parecidas, la desambiguación explícita («para X usa A; para Y usa B») reduce drásticamente las elecciones equivocadas. El modelo no «debería saberlo»: díselo.

El handler: validar antes de ejecutar

El handler es la función Python que se ejecuta cuando el modelo pide la tool. Aunque el esquema acote los tipos, nunca confíes en los argumentos sin validar. Los motivos son dos: el modelo puede equivocarse (el esquema guía, no obliga), y el esquema JSON es más pobre que tus tipos reales (no conoce tus Enum, tus rangos, tus rutas). La herramienta de validación natural en el curso es pydantic: describes el modelo de argumentos una vez y pydantic valida, convierte y da errores legibles.

# Validar es la frontera entre "el modelo pidio algo" y "ejecuto algo".
from pydantic import BaseModel, Field


class BuscarArgs(BaseModel):
    consulta: str = Field(min_length=2)
    limite: int = Field(default=5, ge=1, le=20)      # entre 1 y 20


def buscar_lecciones(consulta: str, limite: int = 5) -> str:
    args = BuscarArgs(consulta=consulta, limite=limite)   # lanza si algo no cuadra
    ...  # aqui ya trabajamos con tipos garantizados

Validar no es solo por seguridad: convierte valores «casi correctos» en correctos. Si el modelo pide limite="5" (texto), pydantic lo coerciona a 5 (entero). Si pedía limite=999, la validación lo rechaza y tú decides qué hacer: recortar, avisar o devolver un error útil (lo vemos abajo).

Errores de tool: el bucle no debe morir

Un handler puede fallar: una ruta que no existe, una base caída, un argumento fuera de rango. ¿Qué debe pasar? Que el bucle siga vivo y que el modelo se entere del fallo. La regla es simple: una excepción del handler no debe propagarse hasta tumbar el agente; se convierte en una observación de error que vuelve al transcript. Así el modelo puede reaccionar —corregir un argumento, probar otra tool, o decirle al usuario que no pudo— en lugar de que el programa muera sin explicación.

   modelo pide tool
        │
        ▼
   handler lanza excepcion ──▶ ¿capturamos? ── sí ──▶ observacion "ERROR: ..." ──▶ vuelve al modelo
                                            └─ no ──▶ 💥 el agente entero se cae

Hay un matiz importante: un error recuperable (argumento inválido, no encontrado) es información útil para el modelo. Un error fatal (falta la API key, la base no existe) no lo es: reintentar no ayudará. Distinguirlos evita que el agente dé vueltas corrigiendo algo que no tiene arreglo. La distinción se implementa con un mensaje claro en la observación («no encontrado» vs «error de configuración, no reintentes»).

Resultados útiles: lo que devuelves es lo que el modelo verá

El resultado de una tool entra en el transcript tal cual. Un volcado de 4 KB llena el contexto, cuesta tokens y diluye la señal. Un resultado útil es corto, estructurado y concluyente: exactamente lo que el modelo necesita para decidir si ya puede responder. Tres principios:

  • Corto: devuelve solo los campos relevantes, no el objeto entero. Si hay una lista larga, recorta y di cuántos elementos quedaron fuera.
  • Estructurado: usa JSON o un formato estable por líneas. Es más fácil de «leer» por el modelo y de depurar por ti.
  • Concluyente: incluye el resultado y su interpretación. «0 resultados» es más útil que una lista vacía; «no encontrado» es más útil que una cadena vacía.
  ❌   {"rows": [ ... 40 objetos con todos sus campos ... ]}     (ruido, tokens)

  ✅   "3 lecciones encontradas:
        1. Aprende IA > Modulo 5 > 01-bucle-agentic (relevancia 0.91)
        2. Aprende IA > Modulo 4 > 01-pipeline-rag (relevancia 0.88)
        ... (+2 omitidas)"                                   (senal util)

Nunca metas en el resultado de una tool credenciales, rutas internas, SQL crudo con datos sensibles ni contenido de ficheros sin filtrar. Todo lo que devuelve una tool termina en el transcript y, potencialmente, en la respuesta final. La tool es una frontera de confianza (lo veremos a fondo en la lección 03 de seguridad y en el módulo 7).

El ciclo completo de una tool

  ESQUEMA (lo ve el modelo)          HANDLER (lo ejecuta tu codigo)
  ┌─────────────────────────┐        ┌──────────────────────────────┐
  │ name: buscar_lecciones  │        │ 1. valida args (pydantic)    │
  │ description: cuando...  │──────▶ │ 2. ejecuta la accion         │
  │ parameters: {...}       │        │ 3. captura errores -> obs     │
  └─────────────────────────┘        │ 4. formatea resultado corto  │
                                     └───────────────┬──────────────┘
                                                     ▼
                                     observacion -> transcript -> modelo decide

Este ciclo es el contrato entero. Diséñalo bien y el modelo parecerá «más listo»; diséñalo mal y ningún modelo lo arreglará.

3 · Ejemplo mínimo

Una única tool, buscar_lecciones, con las tres piezas del contrato: esquema claro, validación con pydantic y resultado corto. Ejecútala directamente (sin LLM): así ves que el handler es código normal y que la validación hace su trabajo antes de tocar nada.

tool_minima.py
# tool_minima.py — el contrato de UNA tool: esquema + validacion + resultado corto.
# Instalacion:  uv add pydantic
from pydantic import BaseModel, Field, ValidationError

# --- El universo de datos (en el Copiloto serian las lecciones indexadas) ---
LECCIONES = {
    "bucle agentic": "Aprende IA > Modulo 5 > 01-bucle-agentic",
    "chunking": "Aprende IA > Modulo 3 > 03-chunking",
    "pipeline de rag": "Aprende IA > Modulo 4 > 01-pipeline-rag",
    "embeddings": "Aprende IA > Modulo 3 > 01-que-son-los-embeddings",
}


# --- 1. El modelo de argumentos: el contrato que validamos ---
class BuscarArgs(BaseModel):
    consulta: str = Field(min_length=2, description="Tema a buscar")
    limite: int = Field(default=3, ge=1, le=10)


# --- 2. El handler: valida, ejecuta y formatea ---
def buscar_lecciones(consulta: str, limite: int = 3) -> str:
    """Devuelve un resultado CORTO y util: solo las coincidencias y el recuento."""
    try:
        args = BuscarArgs(consulta=consulta, limite=limite)     # valida
    except ValidationError as exc:
        # El error se devuelve como texto: es la observacion que vera el modelo.
        return f"ERROR: argumentos invalidos -> {exc.errors()[0]['msg']}"

    hits = [(k, v) for k, v in LECCIONES.items() if args.consulta.lower() in k]
    if not hits:
        return f"0 lecciones encontradas para '{args.consulta}'."   # concluyente

    lineas = [f"{i}. {ruta}" for i, (_, ruta) in enumerate(hits[: args.limite], 1)]
    extra = len(hits) - args.limite
    resumen = f"{len(hits)} leccion(es) encontrada(s):\n" + "\n".join(lineas)
    return resumen + (f"\n(+{extra} omitidas)" if extra > 0 else "")


if __name__ == "__main__":
    print(buscar_lecciones("rag"))              # -> 1 leccion encontrada
    print(buscar_lecciones("x"))                # -> ERROR: cadena demasiado corta
    print(buscar_lecciones("leccion", limite=99))  # -> ERROR: fuera de rango

Salida esperada:

1 leccion(es) encontrada(s):
1. Aprende IA > Modulo 4 > 01-pipeline-rag
ERROR: argumentos invalidos -> String should have at least 2 characters
ERROR: argumentos invalidos -> Input should be less than or equal to 10

Fíjate en lo esencial: incluso llamada «a mano», la tool no revienta con argumentos malos: devuelve un mensaje de error claro. Cuando esta misma función la invoque el agente, ese ERROR: entrará en el transcript y el modelo decidirá qué hacer. Eso es lo que mantiene vivo el bucle.

Fíjate también en el formato: líneas numeradas y un recuento. El modelo puede «leer» esto y citarlo. Si la tool devolviera {...} con 40 campos, ni el modelo ni tú sacaríais nada en claro.

4 · Ejemplo real

El Copiloto. Sus tools viven en proyectos/copiloto/src/copiloto/tools.py, y son tres: buscar_lecciones, abrir_modulo y contar_progreso. Lo importante del archivo no es la lógica (es sencilla) sino cómo está organizado el contrato: cada tool tiene su esquema, su modelo pydantic de argumentos, su handler con errores capturados y un despachador único dispatch() que el bucle del agente llama en cada vuelta.

proyectos/copiloto/src/copiloto/tools.py
"""Las tools del Copiloto: esquema + validacion + handler + despachador."""
import json
from pathlib import Path

from pydantic import BaseModel, Field, ValidationError

LECCIONES = {                                  # indice minimo (el real lo da rag.py)
    "bucle agentic": ("Aprende IA", "Modulo 5", "01-bucle-agentic"),
    "pipeline de rag": ("Aprende IA", "Modulo 4", "01-pipeline-rag"),
}
MODULOS = {"05": ("Agentes y tools", 4), "04": ("RAG", 4)}


# --- Modelos de argumentos (una clase por tool) ---------------------------
class BuscarArgs(BaseModel):
    consulta: str = Field(min_length=2)
    limite: int = Field(default=5, ge=1, le=20)


class ModuloArgs(BaseModel):
    modulo: str = Field(pattern=r"^0[0-8]$")     # solo ids validos: "00".."08"


class ProgresoArgs(BaseModel):
    modulo: str = Field(default="05", pattern=r"^0[0-8]$")


# --- Handlers --------------------------------------------------------------
def _buscar(args: BuscarArgs) -> str:
    hits = [(l, m, a) for tema, (l, m, a) in LECCIONES.items()
            if args.consulta.lower() in tema]
    if not hits:
        return f"0 lecciones encontradas para '{args.consulta}'."
    out = [f"{l} > {m} > {a}" for l, m, a in hits[: args.limite]]
    return f"{len(hits)} resultado(s):\n" + "\n".join(out)


def _abrir_modulo(args: ModuloArgs) -> str:
    if args.modulo not in MODULOS:
        return f"No existe el modulo '{args.modulo}'."
    titulo, n = MODULOS[args.modulo]
    return f"Modulo {args.modulo}: {titulo} ({n} lecciones)."


def _contar_progreso(args: ProgresoArgs) -> str:
    # En el Copiloto real lee la clave 'ia-progress' del navegador del usuario;
    # aqui simulamos para mostrar el contrato.
    total = MODULOS.get(args.modulo, ("?", 0))[1]
    hechas = min(total, 2)
    return f"Modulo {args.modulo}: {hechas}/{total} lecciones completadas."


# --- Registro: esquema (lo ve el modelo) + handler (lo ejecutas tu) --------
REGISTRY = {
    "buscar_lecciones": (BuscarArgs, _buscar),
    "abrir_modulo": (ModuloArgs, _abrir_modulo),
    "contar_progreso": (ProgresoArgs, _contar_progreso),
}

TOOLS = [
    {"type": "function", "function": {
        "name": "buscar_lecciones",
        "description": ("Busca un tema en las lecciones de la Academy y devuelve "
                        "curso > modulo > archivo. Usala cuando pregunte DONDE se "
                        "explica algo, no para contar lecciones."),
        "parameters": {"type": "object",
                       "properties": {"consulta": {"type": "string"},
                                      "limite": {"type": "integer", "default": 5}},
                       "required": ["consulta"]}}},
    {"type": "function", "function": {
        "name": "abrir_modulo",
        "description": ("Devuelve el titulo y el numero de lecciones de un modulo. "
                        "Usala cuando pregunten por un modulo concreto."),
        "parameters": {"type": "object",
                       "properties": {"modulo": {"type": "string"}},
                       "required": ["modulo"]}}},
    {"type": "function", "function": {
        "name": "contar_progreso",
        "description": ("Cuenta las lecciones completadas del usuario en un modulo. "
                        "Usala solo si preguntan por SU progreso, no por el temario."),
        "parameters": {"type": "object",
                       "properties": {"modulo": {"type": "string", "default": "05"}},
                       "required": []}}},
]


def dispatch(name: str, raw_arguments: dict | str) -> str:
    """Punto unico de entrada del bucle: valida, ejecuta y NUNCA propaga excepciones."""
    if name not in REGISTRY:                              # tool desconocida
        return f"ERROR: no existe la tool '{name}'."
    model, handler = REGISTRY[name]
    try:
        args = model(**raw_arguments)                     # 1. valida
    except ValidationError as exc:                        # 2. error -> observacion
        return f"ERROR: argumentos invalidos -> {exc.errors()[0]['msg']}"
    try:
        return handler(args)                              # 3. ejecuta
    except Exception as exc:                              # 4. cualquier fallo -> observacion
        return f"ERROR: la tool '{name}' fallo: {exc}"

Y así lo consume el bucle del agente (lección 01):

from copiloto.tools import TOOLS, dispatch

for call in msg.message.tool_calls:
    args = call.function.arguments
    if isinstance(args, str):                 # algunos SDKs entregan JSON en texto
        args = json.loads(args)
    result = dispatch(call.function.name, args)   # siempre devuelve texto, nunca lanza
    messages.append({"role": "tool", "content": result, "tool_name": call.function.name})

Uso desde la CLI del Copiloto:

uv run copiloto ask "¿Dónde se explica el bucle agentic y cuántas lecciones tiene el Módulo 5?"

Decisiones y porqués:

  • Un modelo pydantic por tool: la validación vive junto al contrato, no desperdigada por el handler. Cambiar una restricción es cambiar una línea del modelo.
  • pattern=r"^0[0-8]$": el argumento modulo solo admite ids válidos. Es mucho más fuerte que "type": "string": descarta de raíz "9", "modulo 5" o "abc".
  • Un único dispatch(): el bucle no conoce handlers concretos, solo el nombre. Añadir una tool es registrarla; el bucle no cambia. Esta indirección es la que hace que el módulo 6 (MCP) pueda enchufar tools externas casi sin tocar el agente.
  • Nunca propaga excepciones: dispatch() captura todo y lo convierte en texto. El bucle del agente no necesita try: por contrato, dispatch siempre devuelve una cadena.
  • Descripciones con desambiguación: «no para contar lecciones», «solo si preguntan por SU progreso». Le dicen al modelo cuándo no usar cada tool, que es lo que evita elegir la equivocada.

Este archivo es la frontera de confianza del agente. Todo lo que entra (argumentos del modelo) y lo que sale (resultado) pasa por aquí. Por eso el dispatch es también el lugar natural para registrar qué tool se llamó y con qué, y para recortar o filtrar el resultado antes de que llegue al transcript.

5 · Buenas prácticas

HazEvitaPor qué
Nombre en verbo snake_case (buscar_lecciones) tool1, fn_do_thing, nombres ambiguos El modelo elige por el nombre; que sea autoexplicativo
Descripción con qué hace, cuándo y cuándo no Una línea vaga como «busca cosas» La descripción es el prompt que decide la elección de tool
Esquema con tipos, obligatorios y valores permitidos parameters vacío o un único "object" Un contrato pobre deja al modelo adivinar los argumentos
Validar con pydantic en el handler Confiar en que «el modelo siempre acierta» El esquema guía, no obliga; valida antes de ejecutar
Capturar errores y devolverlos como observación Dejar que la excepción tumbe el agente El modelo debe poder reaccionar al fallo, no el programa morir
Resultados cortos, estructurados y concluyentes Volcar el objeto entero o listas de cientos de filas El resultado va al transcript: cada carácter cuesta tokens y atención
Un despachador único (dispatch) Un if name == ... por todo el bucle Centraliza validación, errores y registro; facilita enchufar tools

6 · Errores habituales

6.1. Descripciones vagas

El modelo no puede adivinar el matiz que no escribiste.

Incorrecto
# ❌ "Gestiona lecciones": no dice cuando usarla frente a las otras.
{"name": "lecciones", "description": "Gestiona lecciones",
 "parameters": {"type": "object", "properties": {"q": {"type": "string"}}}}
Correcto
# ✅ Dice que hace, cuando usarla y cuando NO.
{"name": "buscar_lecciones",
 "description": ("Devuelve curso > modulo > archivo donde aparece un tema. "
                 "Usala para preguntas de DONDE se explica algo. "
                 "No la uses para contar lecciones (usa contar_progreso)."),
 "parameters": {"type": "object",
                "properties": {"consulta": {"type": "string"}},
                "required": ["consulta"]}}

6.2. Confiar en argumentos sin validar

El modelo puede pedir limite=1000 o enviar "5" como texto. Si el handler no valida, el fallo aparece tarde y lejos del origen.

Incorrecto
# ❌ Sin validacion: un argumento raro explota dentro de la logica.
def buscar(consulta: str, limite: int = 5) -> str:
    return ">".join(LECCIONES[consulta][:limite])   # IndexError si no existe
Correcto
# ✅ Valida en la frontera; el resto del handler trabaja con tipos garantizados.
class BuscarArgs(BaseModel):
    consulta: str = Field(min_length=2)
    limite: int = Field(default=5, ge=1, le=20)

def buscar(consulta: str, limite: int = 5) -> str:
    args = BuscarArgs(consulta=consulta, limite=limite)
    hit = LECCIONES.get(args.consulta)
    return hit if hit else f"0 resultados para '{args.consulta}'."

6.3. Dejar que la excepción tumbe el bucle

Una tool que lanza encima del bucle mata al agente entero, justo cuando el modelo podía haberse recuperado.

Incorrecto
# ❌ La excepcion sube por todo el bucle y revienta el agente.
result = HANDLERS[name](**args)
messages.append({"role": "tool", "content": result})
Correcto
# ✅ El fallo se convierte en observacion: el modelo decide como seguir.
try:
    result = HANDLERS[name](**args)
except Exception as exc:
    result = f"ERROR: la tool '{name}' fallo: {exc}"
messages.append({"role": "tool", "content": result})

6.4. Devolver volcados gigantes

Una tool que devuelve todo el dataset llena el contexto, sube el coste y diluye la señal que el modelo necesitaba.

Incorrecto
# ❌ 200 filas con todos sus campos: ruido puro en el transcript.
return json.dumps(all_rows)
Correcto
# ✅ Recorta, resume y di cuantos quedaron fuera.
top = all_rows[:5]
return f"{len(all_rows)} resultados, top {len(top)}:\n" + "\n".join(
    f"{r['leccion']} ({r['score']:.2f})" for r in top)

7 · Ejercicio guiado

Objetivo: añadir una tercera tool al Copiloto de forma completa (esquema + validación + handler + registro) y probar sus errores sin que el programa se caiga. Al terminar tendrás el patrón exacto que se repite por cada tool nueva.

  1. Paso 1 — crea el archivo de trabajo. 
    uv init copiloto-tools && cd copiloto-tools
uv add pydantic
  2. Paso 2 — parte del dispatch mínimo. Copia la estructura del ejemplo real: registro de (modelo, handler) y un único punto de entrada que nunca lanza: 
    # tools.py — base con una tool ya registrada.
from pydantic import BaseModel, Field, ValidationError

class BuscarArgs(BaseModel):
    consulta: str = Field(min_length=2)
    limite: int = Field(default=5, ge=1, le=20)

def _buscar(args: BuscarArgs) -> str:
    return f"buscando '{args.consulta}' (top {args.limite})..."

REGISTRY = {"buscar_lecciones": (BuscarArgs, _buscar)}

def dispatch(name: str, raw: dict | str) -> str:
    if name not in REGISTRY:
        return f"ERROR: no existe la tool '{name}'."
    model, handler = REGISTRY[name]
    try:
        args = model(**raw)
    except ValidationError as exc:
        return f"ERROR: argumentos invalidos -> {exc.errors()[0]['msg']}"
    try:
        return handler(args)
    except Exception as exc:
        return f"ERROR: la tool '{name}' fallo: {exc}"
  3. Paso 3 — añade la tool abrir_leccion. Debe recibir un archivo y devolver el título real, validando el formato del nombre: 
    # Añade al final de tools.py (antes del REGISTRY) y registra la tool.
TITULOS = {"01-bucle-agentic": "El bucle agentic",
           "02-tools-y-handlers": "Tools y handlers"}

class LeccionArgs(BaseModel):
    archivo: str = Field(pattern=r"^\d{2}-[a-z-]+$")   # p. ej. 01-bucle-agentic

def _abrir_leccion(args: LeccionArgs) -> str:
    titulo = TITULOS.get(args.archivo)
    return f"{args.archivo}: {titulo}" if titulo else f"No encontrada: {args.archivo}."

REGISTRY["abrir_leccion"] = (LeccionArgs, _abrir_leccion)
  4. Paso 4 — prueba los tres casos. Ninguno debe lanzar; todos deben devolver texto: 
    print(dispatch("abrir_leccion", {"archivo": "01-bucle-agentic"}))   # titulo
print(dispatch("abrir_leccion", {"archivo": "EXISTE?"}))            # ERROR de patron
print(dispatch("abrir_leccion", {"archivo": "99-nada"}))           # No encontrada
print(dispatch("tool_fantasma", {}))                               # ERROR: no existe

    Resultado esperado: cuatro líneas, todas cadenas de texto. La segunda empieza por ERROR: argumentos invalidos (el patrón rechazó EXISTE?); la tercera por No encontrada; la cuarta por ERROR: no existe la tool. Acabas de blindar la frontera de confianza del agente.

  5. Paso 5 — describe la tool para el modelo. Añade su esquema a una lista TOOLS con una descripción que incluya cuándo no usarla: 
    TOOLS = [{"type": "function", "function": {
    "name": "abrir_leccion",
    "description": ("Devuelve el titulo de una leccion por su archivo "
                    "(p. ej. '01-bucle-agentic'). Usala cuando ya sepas el archivo. "
                    "Si solo tienes un tema, usa antes buscar_lecciones."),
    "parameters": {"type": "object",
                   "properties": {"archivo": {"type": "string"}},
                   "required": ["archivo"]}}}]

    Resultado esperado: un esquema completo con las tres piezas (nombre, descripción con desambiguación, parámetros). Compáralo con el del paso 3: uno es el contrato que ve el modelo; el otro, la validación que lo protege. Los dos deben estar en sintonía.

Reutiliza este patrón por cada tool nueva: modelo pydantic → handler → registro → entrada en TOOLS. Cuando tengas 20 tools, seguirá siendo el mismo ritual de cuatro pasos.

8 · Reto

🎯 Un catálogo de tools que se defiende solo

Convierte el registro de tools en un catálogo autodescriptivo y a prueba de errores. Requisitos:

  • Cada tool se declara una sola vez (nombre, descripción y modelo pydantic) y de ahí se generan tanto el esquema JSON de TOOLS como el registro de handlers. No debe haber dos sitios donde escribir el nombre.
  • dispatch() debe rellenar un informe por llamada: tool, argumentos normalizados, duración en milisegundos y si fue éxito o error.
  • El resultado debe pasar por un recorte: si supera N caracteres, truncar y añadir … (+X caracteres omitidos).
  • Distingue en la observación los errores recuperables (ERROR_RECUPERABLE: ..., el modelo puede reintentar) de los fatales (ERROR_FATAL: ... no reintentes).
  • Prueba con una tool que reciba un argumento fuera de rango y otra que intente leer por encima del límite de limite; ninguna debe lanzar.

Pista: en Python puedes guardar el modelo pydantic junto al handler en un dataclass Tool y generar el JSON Schema con Model.model_json_schema(). Para el informe, mide con time.perf_counter() alrededor de la ejecución. No busques «la tool perfecta»: busca que añadir la siguiente tool no obligue a tocar el bucle ni a repetir nombres.

9 · Resumen

  • Una tool es un contrato de dos caras: el esquema (que ve el modelo) y el handler (que ejecutas tú). Deben encajar.
  • El esquema tiene tres piezas decisivas: nombre, descripción y parámetros. La descripción es un prompt: di qué hace, cuándo usarla y cuándo no.
  • Valida los argumentos (pydantic) en la frontera, antes de ejecutar. El esquema guía; la validación protege.
  • Una excepción del handler no debe tumbar el agente: se convierte en observación de error y el modelo reacciona.
  • Devuelve resultados cortos, estructurados y concluyentes: lo que sale de la tool entra tal cual en el transcript.
  • Centraliza en un dispatch() único: validación, errores, registro y recorte en un solo sitio.

10 · Preguntas frecuentes

¿Cuántas tools debería darle a un agente?

Las mínimas que cubran las tareas, y no muchas más. Cuantas más tools, más fácil que el modelo elija la equivocada o se invente una; además, cada esquema ocupa tokens en cada llamada. Empieza con 3–5 y crece solo cuando falte cobertura real. Si dos tools se pisan, fusíonalas o desambigua sus descripciones.

¿El esquema de la tool ya valida? ¿Por qué validar otra vez con pydantic?

El esquema guía, no obliga. El modelo puede producir argumentos que no encajen con el JSON Schema (tipos raros, valores fuera de rango), y el esquema no conoce tus tipos reales (un Enum, un rango, un patrón). La validación con pydantic es tu última línea: garantiza que el handler recibe tipos y valores seguros, y te da errores legibles para devolver al modelo.

¿Qué hago si una tool falla? ¿Dejo que el agente pare?

No. Convierte el fallo en una observación y devuélvela al transcript. En la mayoría de errores recuperables (argumento inválido, no encontrado), el modelo corrige y reintenta solo. Para errores fatales (falta configuración), dile explícitamente que no reintente, para que no desperdicie pasos. Lo que nunca debes hacer es dejar que la excepción suba y mate el bucle.

¿Cuánto puede devolver una tool?

Lo mínimo que permita al modelo decidir. Unas pocas líneas o un JSON corto. El resultado entra en el transcript y se reenvía en cada vuelta posterior, así que un volcado grande se paga muchas veces y además diluye la señal. Recorta, resume e indica cuántos elementos quedaron fuera (+N omitidas).

¿Ejecuta el modelo mi código? ¿Es peligroso?

No: el modelo solo pide ejecutar una tool; quien la ejecuta eres tú. Por eso el peligro está en qué tools expones y qué permites. Una tool que ejecuta código arbitrario o borra archivos es peligrosa por diseño, no por el modelo. La regla: expón solo lo que necesites y trata cada argumento como entrada no confiable (validación + sandboxing, tema de la lección 04).
