El agente con tools

Módulo 8 · Proyecto final: Copiloto 🕐 45 minutos

1 · Introducción

El Copiloto ya sabe buscar en las lecciones. Pero una sola pregunta «busca y responde» tiene techo: no puede listar las lecciones de un módulo, ni consultar el progreso del alumno, ni encadenar dos búsquedas. Para eso necesita algo más que recuperar: necesita poder hacer cosas. Eso son las tools, y un modelo que las usa en un bucle es un agente.

En esta lección el Copiloto deja de ser un buscador con generación y pasa a ser un asistente que decide: ante «¿qué lecciones tiene el módulo de agentes?» entenderá que debe llamar a open_module; ante «¿cuánto he avanzado en el curso de IA?» llamará a count_progress; ante «¿cómo se trocea un documento?» llamará a search_lessons. Y encadenará varias tools cuando la pregunta lo exija.

Construiremos la capa tools.py —tres herramientas con esquema, validación y manejo de errores— y la capa agent.py: el bucle pensar → actuar → observar con límite de iteraciones y memoria de conversación para que el Copiloto recuerde lo dicho antes.

¿Por qué existe esta lección? Porque «darle tools al modelo» es fácil de romper: sin esquemas claros el modelo inventa argumentos, sin límite de iteraciones entra en bucles que cuestan dinero, y sin memoria cada turno olvida el anterior. Aquí montamos el agente con las defensas que lo hacen usable y explicamos cuándo un agente aporta y cuándo es un RAG con pasos extra.

2 · Teoría

La analogía: el becario con acceso a las herramientas

Un becario brillante pero que solo puede mirar la pantalla de su ordenador no sirve para mucho. Si además tiene un catálogo de herramientas —el buscador del catálogo, la ficha de cada curso, el contador de avances—, puede resolver tareas de varios pasos solo. Pero necesita un manual que diga qué hace cada herramienta y cómo se usa (el esquema), y alguien que le ponga un límite de pasos para que no se quede girando en círculos. Las tools son el catálogo; el esquema, el manual; el bucle agentic, la jornada de trabajo; el límite de iteraciones, el «hoy es lunes, no te eternices».

Qué es una tool (y qué no)

Una tool es una función tuya, determinista, que el modelo puede pedir que se ejecute. El modelo no ejecuta nada: solo emite una intención («llama a search_lessons con query="chunking"»). Tú validas, ejecutas y le devuelves el resultado. Esta separación es fundamental:

Lo hace el modelo (probabilístico)Lo haces tú (determinista)
Decidir si usa una toolComprobar que la tool existe
Elegir cuál y con qué argumentosValidar los argumentos contra el esquema
Interpretar el resultadoEjecutar la función y capturar errores
Redactar la respuesta finalImponer el límite de iteraciones y el coste

Nunca confíes en los argumentos que propone el modelo: valídalos siempre. Un agente con una tool read_file(path) puede recibir ../../etc/passwd. Las tools tienen que ser seguras por diseño: parámetros acotados (por ejemplo, solo nombres de curso/módulo, nunca rutas arbitrarias) y validación con pydantic antes de ejecutar.

Las tres tools del Copiloto

  • search_lessons(query, k): búsqueda semántica sobre las lecciones (usa index.search). Devuelve fragmentos con su referencia. Es la tool que el Copiloto usa el 80 % del tiempo.
  • open_module(course, module): lista las lecciones de un módulo, con título y minutos. Sirve para navegar («¿qué hay en el módulo 5?») sin depender de la similitud semántica.
  • count_progress(course): devuelve cuántas lecciones hay y cuántas se han completado. Es el estado del alumno.

El progreso del alumno vive en el navegador (localStorage['ia-progress']). La CLI no puede leerlo directamente, así que count_progress lee un archivo .data/progress.json que el alumno (o una futura exportación desde la web) deja ahí. Es una decisión de diseño explícita: separar el estado del navegador del estado del Copiloto, no mezclarlos.

El bucle agentic: pensar → actuar → observar

El agente no responde en una sola llamada. Itera:

   ┌───────────────────────────────────────────────┐
   │  1. PENSAR   el modelo ve los mensajes y decide│
   │              ¿respondo o llamo a una tool?     │
   └───────────────┬───────────────────────────────┘
                   ▼  (si decide llamar)
   ┌───────────────────────────────────────────────┐
   │  2. ACTUAR   TÚ ejecutas la tool con los args  │
   │              validados y obtienes un resultado │
   └───────────────┬───────────────────────────────┘
                   ▼
   ┌───────────────────────────────────────────────┐
   │  3. OBSERVAR devuelves el resultado al modelo  │
   │              como mensaje de role "tool"       │
   └───────────────┬───────────────────────────────┘
                   │  vuelve a 1 con el nuevo estado
                   ▼   (si ya no pide tools → respuesta final)

Cada vuelta es una llamada al modelo más. Por eso el bucle necesita dos frenos: un máximo de iteraciones (para que no sea infinito) y, si hay coste, un presupuesto de tokens. Un agente sin frenos es una factura esperando a ocurrir.

Condiciones de parada

El bucle termina por una de estas razones, y distinguirlas importa:

  1. Respuesta final: el modelo deja de pedir tools y devuelve texto. Es el final feliz.
  2. Límite de iteraciones: se alcanzó max_iterations sin respuesta. Hay que devolver algo honesto («no he podido completarlo»), no dejar que se corte en seco.
  3. Error irrecuperable: una tool falla de forma que no se puede continuar. En este caso, el error se le devuelve al modelo como observación para que decida otra estrategia (normalmente probar otra tool); solo si insiste se aborta.

Memoria: que el Copiloto recuerde el turno anterior

La «memoria» de un agente es, casi siempre, el historial de mensajes. Añades los turnos previos al messages y el modelo ve la conversación. El problema es que el historial crece y la ventana de contexto es finita. Tres estrategias:

EstrategiaCómoCuándo
Ventana deslizanteConservar sistema + últimos N turnosConversaciones cortas; lo más simple
ResumenResumir los turnos viejos con el propio LLMConversaciones largas; cuesta una llamada
Estado estructuradoGuardar hechos clave («curso=IA», «nivel=avanzado») aparteCuando hay datos que no deben perderse

Para el Copiloto, la ventana deslizante más un pequeño estado (el curso en el que está el alumno) es suficiente y barato.

3 · Ejemplo mínimo

Un agente sin LLM: simulamos un modelo que «decide» llamar a una tool y ejecutamos el bucle de verdad. Así ves la mecánica pensar → actuar → observar sin ruido probabilístico. El proveedor real llega en el ejemplo real.

agente_minimo.py
# agente_minimo.py — el bucle agentic con un "modelo" simulado (determinista).
from dataclasses import dataclass


@dataclass
class ToolCall:
    name: str
    args: dict


# --- Catálogo de tools: nombre -> función determinista ---
def search_lessons(query: str, k: int = 4) -> list[str]:
    data = {"chunking": ["chunking: divide un documento en fragmentos con solape"],
            "rag": ["rag: recupera contexto y lo pasa al modelo"]}
    return data.get(query.lower(), [])[:k]


def count_progress(course: str) -> dict:
    return {"course": course, "done": 12, "total": 36}


TOOLS = {"search_lessons": search_lessons, "count_progress": count_progress}


# --- "Modelo" simulado: devuelve una secuencia fija de decisiones ---
class FakeModel:
    def __init__(self, scripted):
        self.scripted = list(scripted)            # lista de ToolCall o de None

    def step(self, messages):
        return self.scripted.pop(0) if self.scripted else None


def run_agent(model, question: str, max_iterations: int = 6) -> str:
    messages = [{"role": "user", "content": question}]
    for _ in range(max_iterations):              # ← freno: nunca infinito
        decision = model.step(messages)          # PENSAR (aquí decide el "LLM")
        if decision is None:                     # no pide tool -> respuesta final
            return f"respuesta final para: {question}"
        fn = TOOLS.get(decision.name)            # ACTUAR (validar + ejecutar)
        result = fn(**decision.args) if fn else {"error": "tool desconocida"}
        messages.append({"role": "tool", "content": result})   # OBSERVAR
    return "límite de iteraciones alcanzado sin respuesta final"


# El "modelo" decide buscar el progreso y luego responde.
model = FakeModel([ToolCall("count_progress", {"course": "Aprende IA"})])
print(run_agent(model, "¿Cuánto he avanzado en IA?"))

Salida esperada:

respuesta final para: ¿Cuánto he avanzado en IA?

Fíjate en las piezas: un catálogo (TOOLS), una decisión (model.step), la ejecución validada y el mensaje de observación. El bucle real solo cambia FakeModel por un LLM de verdad; la estructura es idéntica.

4 · Ejemplo real

El Copiloto. Primero las tools con su esquema y validación; después el bucle con el modelo real, con memoria de conversación y con límite de pasos.

proyectos/copiloto/src/copiloto/tools.py
"""Capa tools: acciones deterministas que el agente puede solicitar."""
from __future__ import annotations

import json
from pathlib import Path

from pydantic import BaseModel, Field

from copiloto.config import settings
from copiloto.index import search


# --- Esquemas: lo que el modelo ve y con lo que debe cumplir ---
class SearchArgs(BaseModel):
    query: str = Field(description="Pregunta o términos a buscar en las lecciones.")
    k: int = Field(default=4, ge=1, le=20, description="Número de fragmentos a devolver.")


class OpenModuleArgs(BaseModel):
    course: str = Field(description='Curso, p. ej. "Aprende IA".')
    module: str = Field(description='Módulo, p. ej. "05" o "agentes".')


class ProgressArgs(BaseModel):
    course: str = Field(description='Curso del que contar el progreso, p. ej. "Aprende IA".')


def search_lessons(args: SearchArgs) -> list[dict]:
    """Busca fragmentos relevantes en las lecciones (búsqueda semántica)."""
    return [
        {"score": round(score, 3), "course": c.course, "module": c.module,
         "lesson": c.lesson, "section": c.section, "text": c.text}
        for score, c in search(args.query, k=args.k)
    ]


def open_module(args: OpenModuleArgs) -> list[dict]:
    """Lista las lecciones de un módulo leyendo los ficheros del curso en disco."""
    base = settings.academy_root / args.course / "web" / "modulos"
    lessons: list[dict] = []
    for folder in sorted(base.glob(f"{args.module}*")):
        for html in sorted(folder.glob("*.html")):
            lessons.append({"module": folder.name, "lesson": html.stem})
    return lessons


def count_progress(args: ProgressArgs) -> dict:
    """Cuenta lecciones totales y completadas (progreso exportado a .data/progress.json)."""
    path = Path(".data/progress.json")
    done = json.loads(path.read_text(encoding="utf-8")).get(args.course, []) if path.exists() else []
    base = settings.academy_root / args.course / "web" / "modulos"
    total = len(list(base.glob("*/*.html")))
    return {"course": args.course, "done": len(done), "total": total}


# --- Registro: esquema para el modelo + handler para ejecutar ---
TOOL_SCHEMAS = [
    {"type": "function", "function": {
        "name": "search_lessons",
        "description": "Busca en las lecciones los fragmentos más relevantes a la consulta.",
        "parameters": SearchArgs.model_json_schema()}},
    {"type": "function", "function": {
        "name": "open_module",
        "description": "Lista las lecciones que contiene un módulo de un curso.",
        "parameters": OpenModuleArgs.model_json_schema()}},
    {"type": "function", "function": {
        "name": "count_progress",
        "description": "Devuelve el progreso (lecciones hechas y totales) de un curso.",
        "parameters": ProgressArgs.model_json_schema()}},
]

HANDLERS = {
    "search_lessons": (SearchArgs, search_lessons),
    "open_module": (OpenModuleArgs, open_module),
    "count_progress": (ProgressArgs, count_progress),
}


def execute(name: str, raw_args: dict) -> dict:
    """Valida los argumentos con pydantic y ejecuta la tool. Nunca lanza: informa."""
    if name not in HANDLERS:
        return {"error": f"tool desconocida: {name}"}
    model, fn = HANDLERS[name]
    try:
        args = model.model_validate(raw_args)           # ← validación obligatoria
    except Exception as exc:                             # argumentos inválidos
        return {"error": f"argumentos inválidos: {exc}"}
    try:
        return {"ok": fn(args)}
    except Exception as exc:                             # fallo controlado, no excepción
        return {"error": f"la tool {name} falló: {exc}"}
proyectos/copiloto/src/copiloto/agent.py
"""Capa agent: el bucle pensar -> actuar -> observar con memoria y límite."""
from __future__ import annotations

import json

from copiloto.config import settings
from copiloto.llm import LLM, get_llm, llm_chat_tools
from copiloto.tools import TOOL_SCHEMAS, execute

SYSTEM_PROMPT = """\
Eres el Copiloto, un asistente que ayuda a navegar los cursos de la Academy.
Usa las herramientas cuando necesites datos reales (buscar lecciones, listar un
módulo, contar progreso). No inventes contenido de lecciones: cita curso, módulo
y lección. Si una tool devuelve un error, prueba otra estrategia o explícalo."""


def _trim(messages: list[dict], keep_turns: int = 8) -> list[dict]:
    """Memoria: conserva el sistema + los últimos N mensajes (ventana deslizante)."""
    system = [m for m in messages if m["role"] == "system"]
    rest = [m for m in messages if m["role"] != "system"]
    return system + rest[-keep_turns:]


def run(question: str, memory: list[dict] | None = None,
        llm: LLM | None = None, max_iterations: int | None = None) -> tuple[str, list[dict]]:
    """Ejecuta el agente sobre una pregunta. Devuelve (respuesta, memoria actualizada)."""
    llm = llm or get_llm()
    max_iterations = max_iterations or settings.max_iterations
    messages = (memory or [{"role": "system", "content": SYSTEM_PROMPT}]).copy()
    messages.append({"role": "user", "content": question})

    for step in range(max_iterations):                  # ← freno del bucle
        reply = llm_chat_tools(llm, _trim(messages), TOOL_SCHEMAS)
        messages.append(reply)
        calls = reply.get("tool_calls") or []
        if not calls:                                   # no pide tools -> respuesta final
            return reply.get("content", ""), messages
        for call in calls:                              # ACTUAR: validar + ejecutar
            result = execute(call["name"], call["args"])
            messages.append({"role": "tool", "tool_call_id": call["id"],
                             "content": json.dumps(result, ensure_ascii=False)})

    return ("No he podido completarlo en el número de pasos permitido. "
            "Prueba a reformular la pregunta."), messages

def llm_chat_tools(llm: LLM, messages: list[dict], tools: list[dict]) -> dict:
    """Pide al modelo una respuesta que puede incluir tool_calls (normalizado)."""
    raw = llm.chat(messages, tools=tools)               # cada proveedor lo adapta
    return {
        "role": "assistant",
        "content": raw.get("content"),
        "tool_calls": [{"id": c["id"], "name": c["name"], "args": c["args"]}
                       for c in raw.get("tool_calls", [])],
    }

Uso: una conversación con memoria entre turnos.

uv run copiloto agent
# Tú: ¿qué lecciones tiene el módulo 5?
#   ↳ tool open_module(course="Aprende IA", module="05")
# Copiloto: El módulo 5 (Agentes y tools) tiene 4 lecciones: el bucle agentic,
#           tools y handlers, planificación y memoria, y sandboxing y coste.
# Tú: ¿y cuánto he avanzado en ese curso?
#   ↳ tool count_progress(course="Aprende IA")
# Copiloto: En Aprende IA has completado 12 de 36 lecciones (33 %).

Decisiones y porqués:

  • Esquemas con pydantic (model_json_schema()): la descripción que ve el modelo y la validación que aplicas tú nacen de la misma fuente. No pueden divergir.
  • execute() nunca lanza excepción: convierte cualquier fallo en {"error": ...}. Así el agente ve el error y puede reaccionar en lugar de romperse.
  • Argumentos acotados: k tiene ge=1, le=20; course y module son nombres, no rutas. La tool no puede leer archivos arbitrarios.
  • _trim() (ventana deslizante): la memoria no crece sin fin; el sistema nunca se recorta.
  • max_iterations desde settings: el freno del bucle es configuración, no un número mágico escondido.
  • Devolver la memoria actualizada: permite continuar la conversación en el siguiente turno sin recalcular el historial.

Cuando el agente no necesita tools (una pregunta directa), el coste es el de una sola llamada. El coste extra aparece solo cuando decide actuar: cada tool añade una vuelta. Por eso el bucle se mide (módulo 7) y se acota.

6 · Errores habituales

6.1. Ejecutar los argumentos del modelo sin validar

El modelo propone argumentos plausibles, no correctos. Sin validación, un k gigante o una ruta maliciosa entran de lleno.

Incorrecto
# ❌ Los args del modelo van directos a la función.
result = HANDLERS[name](**call["args"])       # sin tipos, sin rangos, sin control
Correcto
# ✅ Valida con el esquema y captura el fallo como resultado.
args = SearchArgs.model_validate(call["args"])   # k acotado, query obligatoria
result = {"ok": search_lessons(args)}

6.2. Bucle sin límite de iteraciones

Un agente que se equivoca puede pedir tools una y otra vez. Sin freno, es un bucle caro.

Incorrecto
# ❌ while True hasta que el modelo decida parar.
while True:
    reply = llm.chat(messages, tools=TOOL_SCHEMAS)
    if not reply.tool_calls:
        break
Correcto
# ✅ Tope explícito y salida honesta al alcanzarlo.
for _ in range(settings.max_iterations):
    …
return "No he podido completarlo en el número de pasos permitido."

6.3. Volcar el resultado crudo entero (o perder la referencia)

Devolver una lección entera infla el contexto y diluye; devolver solo puntuaciones impide citar.

Incorrecto
# ❌ La tool devuelve el HTML entero de las 10 secciones.
return [{"html": open(path).read()} for path in all_lessons]
Correcto
# ✅ Fragmentos acotados con su referencia citable.
return [{"score": s, "lesson": c.lesson, "section": c.section, "text": c.text}
        for s, c in search(query, k=k)]

8 · Reto

🎯 Una tool nueva y un presupuesto de coste del bucle

Amplía el agente con una tool nueva y protégelo con un presupuesto, no solo con un contador de pasos. Requisitos:

  • Añade la tool compare_lessons(course_a, course_b) que devuelva en qué se parecen y en qué difieren dos cursos (por ejemplo, comparando los títulos de sus módulos). Diseña su esquema, su handler y su validación.
  • Implementa un presupuesto de tokens en el bucle: suma los tokens de cada llamada y detén el agente si supera un límite, devolviendo una respuesta honesta y las tools ya ejecutadas.
  • Registra una traza por conversación: lista de (paso, tool, args, tokens, ms) y el total. Muestra cómo varía el coste entre una pregunta simple y una que encadena tres tools.
  • Decide y justifica: ¿qué haces si el presupuesto se agota a mitad de una tarea multi-paso? ¿Abortar, pedir más presupuesto o degradar?

Pista: en Ollama y en los SDKs, cada respuesta trae el uso de tokens (prompt_eval_count, eval_count en Ollama). Acumúlalos en el bucle. Mide de verdad con tu dataset del módulo 7 antes de fijar el límite: no pongas un número «a ojo» ni uno tan bajo que el agente nunca termine. El objetivo es un freno medido, no arbitrario.

9 · Resumen

  • Una tool es una función tuya determinista; el modelo solo pide ejecutarla. Tú validas, ejecutas y devuelves el resultado.
  • El bucle agentic es pensar → actuar → observar, repetido hasta una respuesta final o un freno.
  • Frenos imprescindibles: máximo de iteraciones (y, con coste, presupuesto de tokens). Sin ellos, el agente es una factura esperando.
  • Los errores de tool se devuelven como observación (no se lanzan) para que el agente pueda recuperarse.
  • La memoria es el historial de mensajes, acotado por ventana deslizante, resumen o estado estructurado.
  • Un agente aporta cuando hay tareas multi-paso o dependientes del estado; para una sola pregunta, un RAG simple basta y cuesta menos.

10 · Preguntas frecuentes

¿Cuándo quiero un agente y cuándo un RAG simple basta?

Si cada pregunta se responde con una recuperación y una generación, no necesitas agente: un RAG directo es más barato y más predecible. Un agente aporta cuando la tarea es multi-paso («lista el módulo y luego explícame la lección 3»), depende del estado (el progreso del alumno) o requiere decidir entre acciones. Empieza simple; añade el bucle cuando la pregunta lo justifique.

¿El modelo ejecuta el código de las tools?

No. El modelo solo emite una intención (nombre de tool + argumentos). Tu código valida y ejecuta. Es una frontera de seguridad esencial: el modelo nunca toca el sistema directamente. Por eso todas las tools deben ser seguras por diseño, con parámetros acotados y sin acceso a rutas o comandos arbitrarios.

¿Cómo evito que el agente entre en un bucle infinito?

Con un máximo de iteraciones (settings.max_iterations) y una salida honesta al alcanzarlo. Si hay coste, añade un presupuesto de tokens. Además, ayuda mucho que las tools devuelvan errores claros: si el agente «ve» que falló, suele cambiar de estrategia en lugar de repetir. Un bucle que se repite casi siempre es señal de que una tool no está devolviendo información útil.

¿Qué memoria necesita el Copiloto?

Para uso normal, una ventana deslizante (el sistema + los últimos turnos) es suficiente y barata. Si las conversaciones son largas, añade un resumen de los turnos antiguos (cuesta una llamada). Y para datos que no deben perderse (el curso activo, el nivel), guárdalos como estado estructurado aparte, no dentro del texto. No metas el historial entero en cada llamada: la ventana es finita y cada token cuesta.

¿Cuánto cuesta una conversación con agente frente a una pregunta simple?

Una pregunta directa que no usa tools cuesta una llamada. Cada tool ejecutada añade una vuelta (una llamada más con el resultado acumulado), así que una tarea de tres tools puede costar cuatro o cinco llamadas. Por eso se mide con trazas (módulo 7): el coste no está en la pregunta, está en cuántas vueltas decide dar el modelo. El límite de iteraciones y el presupuesto son tus herramientas para acotarlo.
