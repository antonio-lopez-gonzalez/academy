Discriminated unions exhaustivos

Modulo 4 · Unions y narrowing 🕐 30 minutos

1 · Introduccion

Con las discriminated unions ya sabes modelar estados. Ahora llega el paso que las vuelve indispensables: hacer que TypeScript te obligue a tratar cada variante. El patron del switch exhaustivo convierte "olvidar un caso" en un error de compilacion. Cuando tu union crezca, el compilador te perseguira hasta que el codigo este completo.

2 · Teoria

El objetivo: la exhaustividad

Una union discriminada tiene N variantes. Decimos que un bloque de codigo es exhaustivo cuando cubre las N. Si cubre N-1 y alguien añade una variante nueva, el codigo se queda "cojo" sin que nadie avise. La exhaustividad lo impide.

El patron basico

type Resultado =
  | { estado: "ok"; datos: string[] }
  | { estado: "error"; mensaje: string }
  | { estado: "cargando" };

function pintar(r: Resultado): string {
  switch (r.estado) {
    case "ok":       return `Listo: ${r.datos.length} elementos`;
    case "error":    return `Error: ${r.mensaje}`;
    case "cargando": return "Cargando...";
  }
  // Al llegar aqui, r es NEVER: no queda ninguna variante.
  // La linea siguiente "no se alcanza" pero protege el futuro:
  const imposible: never = r;  // si alguien añade una variante, aqui falla
  return imposible;
}

Anatomia del guard:

  1. El switch estrecha por el discriminante (estado).
  2. Tras el switch, r tiene tipo never (no quedan opciones).
  3. Asignar never a la variable imposible es la "bomba de humo": si alguien añade { estado: "cancelado" }, entonces r ya no es never, y la asignacion falla → el compilador te dice DÓNDE falta el caso.
Por que el "check never"

Un switch que no cubre todo compila igualmente; el bug se manifiesta en runtime. La linea const imposible: never = r hace que la omision falle en compilacion. Es un guard de bajo coste y altisimo valor: tu union puede crecer sin miedo a olvidar un caso.

Una funcion util: la que lanza

function assertNever(x: never): never {
  throw new Error(`Caso inesperado: ${JSON.stringify(x)}`);
}

function pintar2(r: Resultado): string {
  switch (r.estado) {
    case "ok":       return `OK (${r.datos.length})`;
    case "error":    return `Error: ${r.mensaje}`;
    default:         return assertNever(r); // si r no es never, no compila
  }
}

assertNever es una funcion auxiliar reutilizable: si llega algo que no deberia, lanza. Si el compilador dice que r aun tiene una variante posible, la llamada falla.

Mas alla del switch: guardas exhaustivas con if

function evaluar(r: Resultado): number {
  if (r.estado === "ok") return r.datos.length;
  if (r.estado === "error") return -1;
  // OJO: el tercer caso (cargando) no esta cubierto...
  // ... pero no hay error porque el retorno de la funcion no lo exige.
  return 0; // decision explicita: el resto
}

El truco never brilla en switches; con if la exhaustividad se vigila con el tipo de retorno union o con un assertNever al final.

3 · Ejemplo minimo

exhaustivo-minimo.ts
// Union discriminada.
type Opcion =
  | { tipo: "sumar"; a: number; b: number }
  | { tipo: "restar"; a: number; b: number };

function calcular(o: Opcion): number {
  switch (o.tipo) {
    case "sumar":  return o.a + o.b;
    case "restar": return o.a - o.b;
    default: {
      // nunca llega, pero protege el futuro de la union.
      const imposible: never = o;
      throw new Error("Opcion inesperada");
    }
  }
}

console.log(calcular({ tipo: "sumar", a: 2, b: 3 }));  // 5

4 · Ejemplo real

Un reducer de un estado (patron de React/Redux o cualquier maquina de estados). Cada accion es una variante y el exhaustivo nos obliga a tratarla:

reducer.ts
// Estado que maneja el reducer.
type Estado = { contador: number; ultimoCambio: string };

// Cada accion: variante con su discriminante "tipo".
type Accion =
  | { tipo: "incrementar"; paso: number }
  | { tipo: "decrementar"; paso: number }
  | { tipo: "resetear" }
  | { tipo: "cambiarACero" }; // añadir aqui y el switch dejara de compilar

function reducer(estado: Estado, accion: Accion): Estado {
  switch (accion.tipo) {
    case "incrementar":
      return { contador: estado.contador + accion.paso, ultimoCambio: "+" };
    case "decrementar":
      return { contador: estado.contador - accion.paso, ultimoCambio: "-" };
    case "resetear":
      return { contador: 0, ultimoCambio: "reset" };
    default: {
      // Guard exhaustivo: si "cambiarACero" se añade sin tratarlo, falla aqui.
      const comprobar: never = accion;
      return estado; // en la practica nunca llega
    }
  }
}

console.log(reducer({ contador: 5, ultimoCambio: "init" }, { tipo: "incrementar", paso: 2 }));

Decisiones:

  • Cada accion es una variante de la union: el reducer es un switch exhaustivo.
  • El default con never convierte cualquier accion no cubierta en un error de compilacion.
  • Añadir cambiarACero te obliga a decidir su logica — el compilador te persigue, que es justo lo que queremos.

5 · Buenas practicas

  • Siempre usa switch con un default que asigne a never (o llame a assertNever).
  • Define assertNever una vez en tu proyecto y reusala.
  • Cuando añadas una variante a una union, deja que el compilador te diga que codigo falta: no lo busques a mano.
  • Si el codigo no necesita lanzar, la asignacion a never ya es suficiente como guard.
  • Mantén el discriminante con literal UNICO (revisa leccion del modulo 2).

Que evitar

  • Un default vacio que "no hace nada": es exactamente el hueco por el que se cuela un caso sin tratar.
  • Usar default para la logica real de un caso: cada caso debe tener su case.
  • Confiar en que "no van a añadir variantes": los estados crecen, la proteccion es barata.

6 · Errores habituales

Mal — default vacio que silencia el error futuro 
function pintar(r: Resultado): string {
  switch (r.estado) {
    case "ok": return "ok";
    case "error": return "error";
    case "cargando": return "cargando";
    default: break; // ❌ si añaden una variante, este hueco no avisa
  }
  return "";
}
Bien — default con guard never 
function pintar(r: Resultado): string {
  switch (r.estado) {
    case "ok": return "ok";
    case "error": return "error";
    case "cargando": return "cargando";
    default: {
      const imposible: never = r; // si falta un caso, aqui falla
      return "";
    }
  }
}
Mal — olvidar el case y que compile "por suerte"

Si solo cubres 2 de 3 casos y el switch no retorna (cae en default), el codigo compila. El guard nunca lo detecta.

Bien — obligar a retornar en TODAS las ramas 
// sin default y con retorno en todos los cases + default never: 
// el compilador avisa si falta cualquier variante.

9 · Resumen

  • Union discriminada: variantes con discriminante literal unico.
  • Switch exhaustivo: un case por variante + default con guard never.
  • La asignacion a never (o assertNever) hace que añadir una variante rompa la compilacion hasta tratarla.
  • Es el mecanismo "se cierra solo" que vuelve a TypeScript ideal para maquinas de estados y reducers.

10 · Preguntas frecuentes

¿Por que la linea "const imposible: never = r" es necesaria?

Porque sin ella el default no comprueba nada: cualquier valor valido "caeria" ahi y se ignoraria. La asignacion a never falla si el valor NO es nunca, exponiendo el caso no cubierto.

¿Puedo usar if/else en vez de switch?

Si, pero la exhaustividad con never es mas natural en switch. En if/else, el equivalente es terminar con assertNever y un retorno por defecto.

¿Esto funciona con unions de objetos grandes?

Perfectamente: cuantas mas variantes, mas valor tiene el guard. El compilador gestiona decenas de casos sin esfuerzo y te indica la variante exacta que falta.

¿Y si mi union no tiene discriminante?

Entonces no hay un campo unico para estrechar. Dificil hacer exhaustivo; la solucion profesional es añadir un discriminante (aunque sea sintetico) o usar guards con in + assertNever al final.

¿Este patron tiene coste en runtime?

No. El switch y el throw del assertNever se quedan en runtime (poca cosa), pero la comprobacion de exhaustividad ocurre SOLO en el compilador. Lo que compila es codigo JS normal.
