Declaration files .d.ts

Modulo 7 · Modulos y configuracion 🕐 30 minutos

1 · Introduccion

Los archivos .d.ts describen la forma de un modulo JavaScript SIN contener su implementacion. Son el "catalogo de tipos" que las librerias publican para que tu codigo pueda consumirlas con seguridad total.

El problema que resuelven: cuando importas lodash, express o jquery (JavaScript puro), TypeScript no tiene forma de saber sus tipos. Los .d.ts — generados por la propia libreria o por la comunidad — llenan ese vacío. Tambien son la via para tipar librerias sin tipado: creas un shim con declare module.

Cuando se utilizan
  • Publicar una libreria (generas los .d.ts con declaration: true).
  • Tipar un modulo JS sin tipos (archivo de env externo).
  • Declarar variables globales, funciones nativas o flags de entorno.
  • Comunicar un paquete de JS con el resto del codigo TS.

2 · Teoria

La analogia: el indice del libro sin el libro

Imagin a una biblioteca que guarda solo el indice de un libro, no el libro. El indice te dice "capitulo 3 empieza en la pagina 40, tiene 3 tablas" — es decir, la estructura sin el contenido. Un .d.ts es el indice de un modulo: define sus funciones, interfaces y tipos, sin implementarlos.

libro.ts libro.d.ts bundle JS implementacion solo tipos (cargado por Node) funct greet(){ export function greet(name: string): void; console.log(name) │ } │ solo "forma" ▼ los .ts importan el .d.ts para saber la forma, y en runtime usan el JS real

Declaraciones puramente ambient (sin implementacion)

// modelo.d.ts — solo la forma, sin cuerpo.
export interface Usuario { id: number; nombre: string; }
export declare function crearUsuario(nombre: string): Usuario;
export type Sesion = { token: string };
// (Nada de "function crearUsuario(...) {...}" — solo la firma)

La palabra declare aparece en la funcion porque no hay cuerpo: estamos declarando.

Generar .d.ts a partir de tu codigo

// tsconfig.json (libreria)
{
  "compilerOptions": {
    "declaration": true,      // genera foo.d.ts junto al JS
    "declarationMap": true,   // para ir del .d.ts al .ts en el editor
    "emitDeclarationOnly": true
  }
}

TypeScript deriva los .d.ts automaticamente de tus fuentes. No los escribes a mano: los genera el compilador.

Tipar un modulo JS sin tipos: declare module

// env.d.ts (o un shim propio)
declare module "mi-paquete-js" {
  export function saludar(nombre: string): string;
  export const version: string;
}

Asi, cuando importes mi-paquete-js, TypeScript ya conoce su forma aunque el paquete sea JS puro. Tambien puedes declarar módulos glob de los que "no hay ni idea":

// ultima carta: tipar como any controlado
declare module "mi-paquete-js";
// import "mi-paquete-js" ahora es any: util como parche temporal, mejor tiparlo.

Variables globales y entorno

// Un .d.ts puede declarar variables globales del navegador o de tu runtime:
declare const API_URL: string;
declare function hashPassword(pw: string): string;
// (Sin import/export, el archivo es "global" — afecta a todo el programa)
¿El archivo es un modulo o un script?

Si un .d.ts tiene import/export, es un modulo: sus declaraciones son locales y se accede via imports. Si no tiene ninguno, es un script (ambiente global). Para forzar que sea un modulo puedes anadir un export {} vacío.

Tipos de la libreria en npm

  • Las librerias TS publican sus .d.ts (campo "types" o exports).
  • Las de JS pueden publicar @types/lo-que-sea (DefinitelyTyped).
  • Si no hay ninguno, veras "Could not find a declaration file for module 'x'".

3 · Ejemplo minimo

math-utils.d.ts
// Un .d.ts minimo que declara un modulo JS.
declare module "matematica-js" {
  export function sumar(a: number, b: number): number;
  export function restar(a: number, b: number): number;
}
app.ts
import { sumar } from "matematica-js"; // ✅ tipado gracias al .d.ts

const total: number = sumar(1, 2);   // number
// sumar("1", 2); // ✖ es un numero

Linea a linea:

  • declare module "matematica-js" abre un espacio de declaracion para ese nombre de import.
  • Las export function son firmas sin cuerpo.
  • Cuando TypeScript resuelve import ... from "matematica-js", busca el .d.ts.
  • En runtime no existe nada de esto: sigue usando el JS real de la libreria.

4 · Ejemplo real

Tipamos un mini-paquete JS de terceros con un .d.ts y ademas declaramos el entorno de la app:

types/analytics.d.ts
// Shims de la libreria "analytics-js" (JS sin tipos).
declare module "analytics-js" {
  export interface TrackOptions {
    userId?: string;
    locale?: string;
  }
  export function track(evento: string, opciones?: TrackOptions): void;
  export function page(nombre: string, url: string): void;
}
types/env.d.ts
// Variables de entorno que Vite u otro runtime inyecta.
declare const VITE_API_URL: string;
declare const import_meta_env: { MODE: string }; // ilustrativo
src/main.ts
import { track, page } from "analytics-js";

track("registro", { userId: "u-1", locale: "es" }); // ✅ opciones tipadas
page("home", "/");

// VITE_API_URL es un string global tipado:
console.log(VITE_API_URL);

Decisiones:

  • Los declare module se agrupan en archivos dentro de types/ (incluidos a mano en el tsconfig).
  • No tocamos el codigo de la libreria JS: solo describimos su API.
  • Las vars globales (env) van en un env.d.ts separate para no ensuciar el codigo.
  • Si la libreria publicara ya sus tipos, este shim sobraria (no se duplica).

5 · Buenas practicas

  • Prefiere los .d.ts generados con declaration: true para tus propias librerias.
  • Usa declare module solo en el puente con JS sin tipos; no reinventes lo que librerias ya tipan (busca @types/... primero).
  • Separa declaraciones globales (env) en env.d.ts.
  • Cuando definas tipos para un paquete, especifica interfaces para opciones: autocompletado y menos fallos.
  • Escribe .d.ts con el minimo de imports para mantener la claridad.

Que evitar

  • declare const x: any; a diestra y sin razon: pierdes todo el tipado que querias ganar.
  • Declarar dos veces el mismo modulo (conflicto si la libreria SI trae tipos).
  • Meter variables de entorno con firma sin validacion.
  • Poner declare module dentro de archivos con imports que lo transformen en modulo sin querer.

6 · Errores habituales

Mal — declarar any para todo 
declare module "totally-js" {
  const c: any; // ✖ perdemos el tipado del paquete
}
Bien — tipos reales 
declare module "totally-js" {
  export const config: { url: string; retries: number };
  export function run(id: number): Promise<string>;
}
Mal — mezclar ambient con implementacion 
// .d.ts NO lleva cuerpos:
export function hola() { return "mundo"; } // ✖ con cuerpo en .d.ts = error
Bien — solo firma 
export declare function hola(): string; // ✅
Mal — global accident via imports 
// Un .d.ts con un import "de relleno" se convierte en modulo y
// tus declare globales dejan de ser globales:
import {} from "x";
declare const API: string; // ya no es global para los demas
Bien — separar 
// env.d.ts sin imports: api global;
// shims con declare module aparte (con imports si necesitan.)

7 · Ejercicio guiado

Vamos a tipar el mini-paquete "formatter-legacy" (JS sin tipos).

  1. Crea types/formatter.d.ts con declare module "formatter-legacy".
  2. Declara export function formatear(valor: unknown): string.
  3. Anade export const locale: "es" | "en".
  4. Importa en un main.ts y usa ambos con tipos.
  5. Incluye types/ en el tsconfig (include o files).

Solucion paso a paso:

types/formatter.d.ts
declare module "formatter-legacy" {
  export function formatear(valor: unknown): string;
  export const locale: "es" | "en";
}
src/main.ts
import { formatear, locale } from "formatter-legacy";

const etiqueta: string = formatear(42);   // ✅
const idioma: "es" | "en" = locale;       // ✅
// locale = "fr"; // ✖ no es "es" | "en"

8 · Reto

Reto

La libreria "storage-promise" expone get(key): Promise<unknown> y set(key, value): Promise<void>. Escribe su .d.ts con un tipo generico Storage<T> para que get devuelva Promise<T | undefined> y set acepte T. Despues consume un Storage<number[]> correctamente tipado. No mires la solucion.

9 · Resumen

  • .d.ts: la forma de un modulo sin implementacion.
  • Se generan con declaration: true para librerias.
  • declare module tipea JS sin tipos (shims).
  • Sin import/export un .d.ts es global; con import/export es un modulo.
  • Preferencia: @types/... > shims propios > declare module any.

10 · Preguntas frecuentes

¿Cuando se generan los .d.ts?

Cuando compilas tu libreria con declaration: true (y emitDeclarationOnly si solo quieres los tipos). Para apps no hacen falta en local.

¿Que hago si un paquete no trae tipos y no hay @types?

Escribe un declare module en un archivo de tipos propio, o usa un shim catch-all con any (como último recurso). Es frecuente en paquetes JS viejos o sin mantenimiento.

¿Los .d.ts de DefinitelyTyped (@types) están vigentes?

Si, es el repositorio comunidad que aporta tipos a miles de paquetes JS. Mas moderno es que la libreria integre sus tipos, pero los @types siguen siendo la red de seguridad habitual.

¿Puedo tipar objetos globales ya definidos?

Si: con interface Window { ... } (augmentación de modulo global) o declare global en un archivo que sea modulo. Es util para variables y API propias del runtime.

¿El editor distingue un .d.ts de un .ts?

Si; los .d.ts son "invisibles" a efectos de codigo: solo aportan tipos. El editor los usa para autocompletado y errores sin mostrarlos en el arbol de soluciones.

¿Debo escribir .d.ts a mano para mi propio proyecto?

Normalmente no: generar res resultados es mas fiable. Escribelos solo para el puente con JS externo, o para declarar APIs muy concretas de esferas globales (env, window).
