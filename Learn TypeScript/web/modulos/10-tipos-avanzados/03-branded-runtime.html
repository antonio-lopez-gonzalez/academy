Branded types con validacion en runtime

Modulo 10 · Tipos avanzados 🕐 35 minutos

1 · Introduccion

En el Modulo 6 viste la marca simple: number & { [simbolo]: "USER" }. Esta leccion va un paso mas alla del "truco de tipos": la marca generica Brand<T, B>, los validadores que parsean en el borde (un JSON, un formulario, una fila de base de datos) y la composicion de marcas para representar varios invariantes a la vez.

La marca solo existe en tiempo de compilacion: en runtime, un UserId no es mas que un number. Por eso la puerta de entrada siempre debe ser un validador que, ademas de asegurar el tipo, compruebe el dominio: entero positivo, formato de email, rango de temperatura...

Cuando se utilizan
  • IDs con dominio propio (userId, orderId, facturaId) que no deben cruzarse.
  • Unidades (EUR vs USD, Celsius vs Fahrenheit) y cantidades con invariantes (positivas).
  • Strings con formato (slugs, emails, tokens) que llegan validados desde fuera.
  • Datos que cruzan un borde de confianza: de unknown/JSON a valores marcados.

2 · Teoria

La analogia: el control de acceso en la puerta de un avion

En un aeropuerto no validas la tarjeta de embarque constantemente: la validas una vez, en la puerta de embarque, y a partir de ahi el pasajero lleva un "sello" (la marca) que todos los demas puntos confian. Con los branded types pasa igual: validas en el borde y el resto del sistema opera con valores ya marcados. El sello no existe fisicamente (es un truco de tipos), pero la confianza esta en que solo la puerta sabe crearlo.

La marca generica: Brand<T, B>

brand-helper.ts
// Marca generica: marca CUALQUIER tipo base con una etiqueta literal.
declare const marca: unique symbol;

type Brand<T, B extends string> = T & { readonly [marca]: B };

type UserId = Brand<number, "UserId">;
type OrderId = Brand<number, "OrderId">;
type Email = Brand<string, "Email">;

Antes duplicabas number & { [marca]: "X" } por cada id. Con el helper, un solo Brand<T, B> marca cualquier base (number, string, objetos, tuples) con la etiqueta que necesites. El unique symbol declarado con declare garantiza que ninguna marca colisiona con otras.

El validador: de unknown a valor marcado

validator.ts
// Validador con type predicate: "si esto pasa, el valor ES UserId".
function isUserId(valor: unknown): valor is UserId {
  return typeof valor === "number"
    && Number.isInteger(valor)
    && valor > 0;
}

// Parser en el borde: devuelve el valor marcado o null.
function parseUserId(crudo: unknown): UserId | null {
  if (typeof crudo !== "number" || !Number.isInteger(crudo) || crudo <= 0) return null;
  return crudo as UserId; // asercion controlada: unica puerta a la marca
}
Predicate vs parser

valor is UserId funciona como guard en un if; el parser (parseUserId) devuelve UserId | null y encaja mejor como punto unico de entrada. Usa el que te resulte mas natural, pero mantiene UN solo lugar donde se hace el as.

Composicion de marcas: varios invariantes a la vez

composicion.ts
type Positivo = Brand<number, "Positivo">;
type Euro = Brand<number, "Euro">;

// Interseccion: la base es number, y las marcas se suman.
type Precio = Positivo & Euro;

// Solo este validador sabe que otorga AMBAS marcas.
function parsePrecio(crudo: unknown): Precio | null {
  if (typeof crudo !== "number" || crudo <= 0) return null;
  return crudo as Precio; // garantiza: numero, mayor que cero, en euros
}

// Marcas en capas: una marca sobre un valor ya marcado.
type Verificado = Brand<UserId, "Verificado">;
type UsuarioVerificado = UserId & Verificado;

function borrarUsuario(usuario: UsuarioVerificado): void {
  // aqui sabes que es un UserId Y que paso la verificacion
}

La composicion exige que las marcas compartan la misma base: number & string seria never. Por eso las unidades y las cantidades se marcan sobre number, y los dominios compuestos se cruzan cuando quieres dos invariantes.

La marca no viaja por la red

Al serializar (JSON.stringify) la marca desaparece: es un truco de tipos, se borra en runtime. Por eso debes revalidar en cada borde: quien recibe un JSON no puede confiar en que el remitente marco los datos correctamente.

3 · Ejemplo minimo

borde-minimo.ts
declare const marca: unique symbol;
type Brand<T, B extends string> = T & { readonly [marca]: B };

type UserId = Brand<number, "UserId">;

// El borde: de unknown (lo que llega de fuera) a UserId.
function parseUserId(crudo: unknown): UserId | null {
  if (typeof crudo !== "number" || !Number.isInteger(crudo) || crudo <= 0) return null;
  return crudo as UserId;
}

// Los datos cruzan la frontera como unknown.
const datos: unknown = JSON.parse('{"id": 42}');
const objeto = datos as Record<string, unknown>;

const id = parseUserId(objeto["id"]); // UserId | null

if (id !== null) {
  console.log(`Usuario ${id} cargado`); // aqui id ya es UserId garantizado
}

Linea a linea:

  • Brand<number, "UserId"> marca cualquier number; la puerta es el validador.
  • Las tres comprobaciones (typeof, entero, positivo) garantizan el dominio antes del as.
  • El JSON se tipa como unknown: el compilador te obliga a validar antes de usar, el dato nunca entra "de gratis".

4 · Ejemplo real

Cliente de cobros: una respuesta de API llega como unknown, se parsea en dominios marcados y la logica de negocio solo acepta valores compuestos (importe en euros y positivo).

api-cobros.ts
declare const marca: unique symbol;
type Brand<T, B extends string> = T & { readonly [marca]: B };

type Euro = Brand<number, "Euro">;
type USD = Brand<number, "USD">;
type Positivo = Brand<number, "Positivo">;
type FacturaId = Brand<string, "FacturaId">;

// Validadores por dominio, todos en el borde:
function parseEuro(crudo: unknown): Euro | null {
  return typeof crudo === "number" ? (crudo as Euro) : null;
}

function parsePositivo(crudo: unknown): Positivo | null {
  return typeof crudo === "number" && crudo > 0 ? (crudo as Positivo) : null;
}

function parseFactura(crudo: unknown): FacturaId | null {
  return typeof crudo === "string" && /^F-\d+$/.test(crudo) ? (crudo as FacturaId) : null;
}

// Composicion: euros Y positivos en un solo valor.
type ImporteEur = Euro & Positivo;

function parseImporte(crudo: unknown): ImporteEur | null {
  if (parseEuro(crudo) === null || parsePositivo(crudo) === null) return null;
  return crudo as ImporteEur; // ambas validaciones pasaron
}

// La logica de negocio pide el dominio exacto:
function cobrar(factura: FacturaId, importe: ImporteEur): string {
  return `Factura ${factura} cobrada por ${importe} EUR`;
}

// Ayudante para re-narrow el JSON a un registro.
function esRegistro(v: unknown): v is Record<string, unknown> {
  return typeof v === "object" && v !== null;
}

// Simula la respuesta de la API:
const respuesta: unknown = JSON.parse('{"facturaId":"F-7","importe":199}');

if (esRegistro(respuesta)) {
  const factura = parseFactura(respuesta["facturaId"]);
  const importe = parseImporte(respuesta["importe"]);
  if (factura !== null && importe !== null) {
    cobrar(factura, importe); // ✅ ambos valores validados y marcados
  }
}

Decisiones:

  • Cada dominio tiene su validador reutilizable; parseImporte compone dos de ellos sin duplicar logica.
  • La asercion as aparece solo dentro de los validadores: fuera de ellos es imposible crear un valor marcado sin mentir al compilador.
  • El negocio (cobrar) firma con ImporteEur: las marcas documentan las invariantes en el propio tipo.
  • esRegistro es un type predicate generico que convierte el unknown en un mapa accesible por clave para poder validar cada campo.

5 · Buenas practicas

  • Valida en el borde (API, JSON, formulario, fila de BD) y marca ahi; no en mitad de la logica de negocio.
  • Un validador por dominio (parseUserId, parseOrderId...), reutilizable y comprobable de forma aislada.
  • Centraliza la asercion as: el unico lugar del proyecto donde se crea una marca.
  • Tipa la entrada como unknown y valida; nunca uses any en el borde, porque desactiva la exigencia del compilador.
  • Compone marcas con interseccion cuando la base es compatible: cada marca representa un invariante verificable.
  • Usa marcas para IDs, unidades, strings con formato y estados verificados; no para datos planos donde "string" basta.

Que evitar

  • Brandear sin validar: la marca vacia es mentira silenciosa.
  • Crear valores marcados con as fuera del validador (rompe la invitacion del dominio).
  • Intentar comprobar la marca en runtime (in, instanceof): no existe en runtime.
  • Componer marcas sobre bases distintas (number & string = never).

6 · Errores habituales

Mal — marca sin validacion 
type UserId = Brand<number, "UserId">;
const id = 7 as UserId; // ✖ nunca comprobaste el dominio: 0, -3 o 9999 pasan igual
Bien — la marca nace tras validar 
function parseUserId(crudo: unknown): UserId | null {
  return typeof crudo === "number" && Number.isInteger(crudo) && crudo > 0
    ? (crudo as UserId) // unico punto de asercion, tras validar
    : null;
}
Mal — any en el borde 
const datos = JSON.parse(respuesta); // any: puedes usar campos sin validar
const id: number = datos.id;         // compila, pero si viene undefined → runtime crash
Bien — unknown obliga a validar 
const datos: unknown = JSON.parse(respuesta);
if (esRegistro(datos) && typeof datos["id"] === "number") {
  const userId = parseUserId(datos["id"]); // UserId | null
}
Mal — comprobar la marca en runtime 
if (marca in valor) { /* ✖ marca es un unique symbol de TIPOS: no existe en runtime */ }
Bien — la verificacion vive en el validador 
// Compruebas con la funcion, no con el valor:
parseUserId(valor) !== null;
Mal — marcar fuera del validador 
function anular(idCrudo: number): void {
  const userId = idCrudo as UserId; // ✖ la marca se cita sin pasar por el borde
  // ... el dominio no se verifico jamas
}
Bien — el borde entrega el marcado 
function anular(idCrudo: unknown): void {
  const userId = parseUserId(idCrudo);
  if (userId === null) return; // aqui userId ya es UserId garantizado
}

7 · Ejercicio guiado

Queremos anular pedidos con marcas separadas: un UserId y un OrderId que salen de un payload JSON y no pueden mezclarse.

  1. Define Brand<T, B> con declare const marca: unique symbol.
  2. Crea type UserId = Brand<number, "UserId"> y type OrderId = Brand<number, "OrderId">.
  3. Escribe parseUserId(crudo: unknown): UserId | null que valide entero positivo.
  4. Escribe parseOrderId con la misma validacion.
  5. Define anularPedido(userId: UserId, orderId: OrderId): void y llama con los valores parseados de un JSON tipado como unknown.

Solucion paso a paso:

ejercicio-runtime.ts
// 1) La marca generica.
declare const marca: unique symbol;
type Brand<T, B extends string> = T & { readonly [marca]: B };

// 2) Los dominios.
type UserId = Brand<number, "UserId">;
type OrderId = Brand<number, "OrderId">;

// 3 y 4) Validadores en el borde.
function parseUserId(crudo: unknown): UserId | null {
  if (typeof crudo !== "number" || !Number.isInteger(crudo) || crudo <= 0) return null;
  return crudo as UserId;
}

function parseOrderId(crudo: unknown): OrderId | null {
  if (typeof crudo !== "number" || !Number.isInteger(crudo) || crudo <= 0) return null;
  return crudo as OrderId;
}

// 5) Logica que exige los dominios por separado.
function anularPedido(userId: UserId, orderId: OrderId): void {
  console.log(`Anulando pedido ${orderId} del usuario ${userId}`);
}

function esRegistro(v: unknown): v is Record<string, unknown> {
  return typeof v === "object" && v !== null;
}

const payload: unknown = JSON.parse('{"userId": 3, "orderId": 91}');

if (esRegistro(payload)) {
  const userId = parseUserId(payload["userId"]);
  const orderId = parseOrderId(payload["orderId"]);
  if (userId !== null && orderId !== null) {
    anularPedido(userId, orderId); // ✅ llamada segura: los dominios no se cruzan
  }
}

8 · Reto

Reto

Compone marcas para unidades fisicas: type Positivo = Brand<number, "Positivo"> y type Celsius = Brand<number, "Celsius">. Escribe una funcion sumarTemperaturas(a: Celsius & Positivo, b: Celsius & Positivo): Celsius & Positivo que retorne siempre un valor positivo (piensa en Math.max(0, a + b) como el constructor del resultado), y un parseTemp(crudo: unknown): Celsius & Positivo | null que valide rango y positividad. No mires la solucion: el resultado de la suma es un valor de runtime que debe pasar por una funcion constructora para recuperar las marcas.

9 · Resumen

  • Brand<T, B> es la marca generica: cualquier tipo base + etiqueta literal con unique symbol.
  • El validador es la unica puerta: comprueba el dominio y crea la marca con un as controlado.
  • El borde de confianza (JSON, formularios, APIs) se tipa como unknown; el validador lo re-narrow con type predicates.
  • Las marcas se componen con interseccion mientras la base coincida: cada marca es un invariante.
  • La marca no existe en runtime: revalida en cada borde y nunca la compruebes con in o instanceof.
  • Usa marcas cuando haya cruce real de dominios: IDs, unidades, formatos y estados verificados.

10 · Preguntas frecuentes

¿La marca sobrevive a JSON.stringify?

No. Es un truco de tipos: se borra en runtime (type erasure). Por eso se revalida en cada borde: el que recibe un JSON no puede confiar en las marcas del que lo envio.

¿Por que unique symbol?

Cada unique symbol es un tipo unico: dos marcas declaradas en nodos const/declare distintos nunca colisionan, y el compilador las distingue con seguridad.

¿Puedo componer marcas con bases distintas?

No de forma util: number & string se reduce a never. Compone solo cuando las bases coinciden, como unidades y cantidades sobre number.

¿Es normal tener tantos validadores?

Si. Un validador por dominio (parseUserId, parseOrderId, parseEmail...) es barato, comprobable y se reutiliza en todas las entradas de ese dominio.

¿Zod u otras librerias sustituyen esto?

Zod parsea y deriva el tipo a partir del schema, y su safeParse devuelve el valor ya tipado. El brand manual te da el mismo patron sin dependencias, con control total del momento de la validacion.

¿Puedo marcar tipos no primitivos?

Si: Brand<T, B> acepta con T objetos y tuples. La marca se superpone a la base; la composicion y las invarianzas se mantienen igual de claras.
