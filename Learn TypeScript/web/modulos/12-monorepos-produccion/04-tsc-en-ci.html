TypeScript en produccion y CI

Modulo 12 · Monorepos y produccion 🕐 35 minutos

1 · Introduccion

El editor te avisa de los tipos en vivo, pero no es una garantia: nadie puede cazar cada combinacion de ramas y archivos en local. La garantia real vive en CI: un paso que comprueba los tipos de TODO el proyecto y falla el pipeline si algo esta roto. Esta leccion monta ese paso: que comando usar (tsc --noEmit vs tsc -b), como cachear el trabajo incremental, donde dibujar la linea entre tsc y ESLint, y como medir el rendimiento del chequeo.

El problema que resuelve: en produccion, un error de tipos se paga carisimo (el build explode o, peor, sale a runtime). En CI, el coste es un commit rechazado. La diferencia entre los dos mundos es un pipeline que sepa que los tipos son parte del contrato, no un adorno.

Cuando se utiliza
  • En cada PR y en cada push a la rama principal.
  • En monorepos (leccion 1): tsc -b desde la raiz chequea el grafo entero.
  • Antes de publicar (leccion 3): los .d.ts se validan, no solo se emiten.
  • Cuando el equipo quiere metrics de cuanto tarda el chequeo y por que.

2 · Teoria

La analogia: el portero del concierto

El editor es el guia que te aconseja en el camino; CI es el portero de la puerta del concierto: sin entrada no pasas. A nadie le importa que el guia haya sido amable: si el portero (un tsc estricto, de punta a punta) encuentra que tu "entrada" (el codigo) no es valida, el espectaculo (el despliegue) no ocurre. El portero nunca se cansa ni "se le escapa".

Chequeo en CI: tsc --noEmit o tsc -b

Dos contextos, dos comandos naturales:

# Proyecto unico: comprueba tipos sin emitir nada.
tsc --noEmit --pretty false

# Monorepo (leccion 1): el grafo entero, en orden, con cache.
tsc -b . --pretty false
  • --noEmit solo quiere la respuesta "¿hay errores?". No hay artefactos que limpiar.
  • -b (build mode) respeta references, ordena y reutiliza tsbuildinfo: en un monorepo es la unica forma de chequear el conjunto sin compilar el mundo dos veces.
  • --pretty false produce salida parseable en CI (lineas de error normales).
El build del bundler NO es un chequeo de tipos

Vite (esbuild) transpila archivo a archivo: borra los tipos sin comprobarlos. Un vite build en verde con un as any sospechoso te da falsa seguridad. El paso de tsc es el unico que verifica el sistema de tipos completo. Por eso el pipeline lleva AMBOS: typecheck + build.

incremental y tsBuildInfoFile: cache del chequeo

// apps/client/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "noEmit": true,
    "incremental": true,        // en composite viene implicito
    "tsBuildInfoFile": "./node_modules/.tmp/tsconfig.client.tsbuildinfo"
  }
}

incremental guarda la huella de cada archivo en tsbuildinfo; en la siguiente ejecucion, TypeScript reutiliza el resultado de lo que no cambio. En CI, restaurar ese fichero (cache del runner) hace el chequeo de tipos notablemente mas rapido en PRs que repiten trabajo. Tips:

  • Reubica el fichero (tsBuildInfoFile) fuera del paquete para cachearlo de un solo sitio.
  • No lo comitees; restauralo desde el cache de tu CI (por ejemplo, actions/cache).
  • En monorepo, el cache cubre el grafo: si contracts no cambio, sus consumidores no se recomprueban.

tsc y ESLint: dos roles, no un sustituto

Herramienta Comprueba Ejemplos
tsc El sistema de tipos: asignaciones, genericos, narrowing, referencias. type error, as any no detectado, referencia rota entre paquetes.
ESLint Estilo y patrones: nombrado, ramas, importacion, accesibilidad, seguridad. no-unused-vars, reglas de @typescript-eslint.

Ambos son complementarios: ESLint no puede validar que tu Generico<T> sea correcto, y tsc no te obliga a nombrar bien las funciones. Un pipeline sano ejecuta los dos, y una regla de ESLint "type-aware" (@typescript-eslint/no-unsafe-assignment) refuerza a tsc sin reemplazarlo.

skipLibCheck: que se salta y cuando mirarlo

// tsconfig.base.json (raiz)
{
  "compilerOptions": {
    "skipLibCheck": true
    // ^ no chequear los .d.ts de node_modules (rendimiento)
  }
}

skipLibCheck: true salta la validacion de los .d.ts de node_modules (bibliotecas ajenas): enorme ahorro de tiempo y la opcion sana por defecto en apps. Cuando publicas una libreria (leccion 3), conviene validarlo a false en la build para cazar declaraciones tuyas mal generadas (o usar un validador de API como api-extractor).

Aislamiento: isolatedModules y verbatimModuleSyntax

Vite, esbuild y el compilador nativo transpilan archivo a archivo, sin ver el proyecto entero. Un archivo debe poder transpilarse solo: por eso isolatedModules te obliga a marcar los import type explicitos, y verbatimModuleSyntax mantiene esa distincion en el codigo emitido. Ya lo viste en detalle en el Modulo 7; aqui es politica de CI:

  • Activalos en la config base: lo que vale en local vale en el build de produccion.
  • Atrapan errores que tsc a veces perdona y el transpilador rompe (por ejemplo, const enum inlineado).
  • Preparan el terreno para el type-stripping del futuro (tsgo/TS natal): codigo que se puede ejecutar sin una pasada de compilacion completa.

Telemetria de rendimiento: tsgo y tsserver

# Cuanto tarda y quien consume:
tsc -b . --extendedDiagnostics     # tiempos por fase (program, bind, check, emit)
tsc -b . --listFiles               # que archivos entran al programa
tsc --explainFiles                 # por que entra cada archivo
tsc --generateTrace ./trace        # grafo puro para @typescript/trace-analyzer

# Compilador nativo (TS 7): mismo tsconfig, ~10x mas rapido.
tsgo -b . --pretty false

Medir es decidir: si el chequeo tarda 4 minutos, primero mira --extendedDiagnostics (¿check o emit?) y --listFiles (¿se colo un directorio gigante?). El tsgo (port nativo en Go, linea TypeScript 6/7) acelera el mismo pipeline sin cambiar tsconfig. El tsserver (lenguaje del editor) comparte config; si el editor va lento, el mismo perfil sirve para diagnosticarlo.

3 · Ejemplo minimo

package.json (script de tipo)
{
  "scripts": {
    "typecheck": "tsc -b . --pretty false"
  }
}
.github/workflows/ci.yml (minimo)
name: CI
on: [push, pull_request]
jobs:
  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm typecheck   # falla el PR si hay errores de tipos

Linea a linea:

  • tsc -b . --pretty false: grafo completo, salida parseable; nada de emit intermedio en el job de tipos.
  • actions/setup-node con cache: pnpm reutiliza el store de paquetes.
  • --frozen-lockfile: la instalacion debe reproducir exactamente el lockfile commiteado.
  • Si el job falla, el PR se bloquea: los tipos pasan a ser parte del contrato del equipo.

4 · Ejemplo real

Pipeline de monorepo (leccion 1) con typecheck, lint, build y cache del chequeo incremental:

.github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile

      # Cache de los tsbuildinfo: el chequeo incremental no repite trabajo.
      - uses: actions/cache@v4
        with:
          path: node_modules/.tmp
          key: tsbuildinfo-${{ runner.os }}-${{ hashFiles('**/tsconfig*.json') }}

      - run: pnpm typecheck   # tsc -b . --pretty false

  lint:
    runs-on: ubuntu-latest
    needs: typecheck          # si hay errores de tipos, no llegamos aqui
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint        # ESLint: estilo y reglas, roles separados

  build:
    runs-on: ubuntu-latest
    needs: [typecheck, lint]
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm build       # compila/empaqueta lo que se ira a produccion

Decisiones:

  • Jobs separados = fallos claros y paralelismo: typecheck, lint y build tienen responsabilidad unica.
  • needs encadena: un tipo roto detiene el pipeline antes de gastar tiempo en lint/build.
  • El cache de node_modules/.tmp guarda los tsbuildinfo (clave por estado de tsconfigs); la cache del paquete (pnpm) ya la gestiona setup-node.
  • Typecheck y build son pasos distintos a proposito: verificar tipos (tsc) y empaquetar (Vite) no son lo mismo, y ambos fallan por razones distintas.
  • Con tsgo este job se declara igual: mismo tsconfig, mismo resultado, menos tiempo.

5 · Buenas practicas

  • Comprueba tipos en CI con tsc (nunca confies en el build del bundler para validar tipos).
  • En monorepo, un solo tsc -b . --pretty false desde la raiz cubre todo el grafo.
  • Activa incremental y cachea los tsbuildinfo; rebonde la clave si cambian los tsconfigs.
  • Separa tsc y ESLint en jobs (o en pasos) con responsabilidad explicita.
  • skipLibCheck: true en apps; revisa las declaraciones propias con la build de libreria (leccion 3).
  • Activa isolatedModules y verbatimModuleSyntax en la base: protegen frente a transpiladores archivo a archivo.
  • Registra la duracion del typecheck (--extendedDiagnostics) y considera tsgo si el tiempo empieza a doler.

Que evitar

  • Confundir "build verde" con "tipos sanos": esbuild no comprueba el sistema de tipos.
  • Correr tsc sin --noEmit (o -b) en CI y ensuciar el workspace con emisiones.
  • Cachear mal: tsbuildinfo restaurado con codigo nuevo (clave poco especifica) invalida el proposito.
  • Relajar skipLibCheck a false en una app solo por "rigor": pagas minutos por archivos que no controlas.
  • Comiteos de *.tsbuildinfo: son cache, se regeneran.

6 · Errores habituales

Mal — validar tipos con el build del bundler 
# "build": "vite build" (o "tsup", "esbuild")
# ✖ el transpilador borra los tipos sin COMPROBARLOS:
#    un "as any" o un generico roto pasan en verde.
Bien — chequeo aparte con tsc 
# "typecheck": "tsc -b . --pretty false"
# ✅ comprueba el sistema de tipos completo; luego construye el bundler.
Mal — emitir en CI donde no hace falta 
tsc -p apps/client        # ✖ escribe JS junto a los tipos, sin -b ni noEmit
Bien — solo respuesta, sin artefactos 
tsc -b . --pretty false    # ✅ grafo en orden; apps con noEmit no escriben nada
Mal — cache del tsbuildinfo con clave ambigua 
# ✖ misma clave siempre: restaura tsbuildinfo de otro codigo
key: tsbuildinfo
Bien — clave ligada a la config 
# ✅ invalida cuando cambian los tsconfigs
key: tsbuildinfo-${{ hashFiles('**/tsconfig*.json') }}
Mal — codigo que transpila pero no tipa (const enum) 
const enum Moneda { EUR, USD }   // ✖ con isolatedModules no puede transpilarse
// tsc lo alinea en un proyecto; esbuild (archivo a archivo) no puede resolverlo
Bien — enums reales o unions de literales 
type Moneda = "EUR" | "USD";      // ✅ transpila y tipa en cualquier tool

7 · Ejercicio guiado

Pon un chequeo de tipos en CI para tu monorepo (leccion 1).

  1. Anade el script typecheck al package.json raiz: tsc -b . --pretty false.
  2. Verifica en local que falla cuando introduces un error de tipos (cambia un nombre de funcion).
  3. Configura el job typecheck de GitHub Actions con checkout, pnpm, node y pnpm install --frozen-lockfile.
  4. Anade cache de node_modules/.tmp con clave ligada a los tsconfigs.
  5. Ejecuta el typecheck y comprueba que el job en verde pasa y que un error de tipos bloquea.

Solucion paso a paso:

package.json
{
  "scripts": {
    "typecheck": "tsc -b . --pretty false"
  }
}
.github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - uses: actions/cache@v4
        with:
          path: node_modules/.tmp
          key: tsbuildinfo-${{ runner.os }}-${{ hashFiles('**/tsconfig*.json') }}
      - run: pnpm install --frozen-lockfile
      - run: pnpm typecheck

Puebalo a fondo: rompe un tipo a proposito (doble("texto")), sube la rama, y verifica que el job falla con la linea exacta del error. Esa es la garantia que el editor no puede darte sola.

8 · Reto

Reto

Mide el typecheck actual con tsc -b . --extendedDiagnostics y anota los tiempos de Program, Bind y Check. Luego ejecuta el mismo chequeo con tsgo -b . --pretty false (el compilador nativo) y compara. Si tienes un paquete publicable (leccion 3), valida sus declaraciones con skipLibCheck: false: ¿aparece algun error en tus propios .d.ts? Anade el resultado como job de PR. Pista: la telemetria te dice donde duelen los segundos; el fix casi nunca es "afinar el tsconfig".

9 · Resumen

  • El editor aconseja; CI garantiza: un job tsc que falla el pipeline es la linea roja de tipos.
  • tsc --noEmit para proyectos unicos; tsc -b . para monorepos (grafo, orden, cache).
  • incremental/tsBuildInfoFile + cache del runner abaratan el chequeo repetido.
  • tsc y ESLint tienen roles distintos; el build del bundler NO chequea tipos.
  • skipLibCheck, isolatedModules y verbatimModuleSyntax son politica de CI tanto como de tsconfig.
  • Mide con --extendedDiagnostics/--listFiles y acelera con tsgo si hace falta.

10 · Preguntas frecuentes

¿Por que no sirve "vite build" como chequeo de tipos?

Vite usa esbuild, que transpila archivo a archivo: elimina los tipos sin comprobarlos. Un generico roto o un as que esconde un bug pasan el build. Solo tsc valida el sistema de tipos completo; por eso el pipeline lleva typecheck + build.

¿--noEmit y -b son intercambiables?

No exactamente: --noEmit chequea un proyecto sin emitir; -b (build mode) respeta references, ordena el grafo y usa tsbuildinfo. En un proyecto solo, tsc --noEmit basta; en un monorepo, tsc -b es la herramienta (y respeta los noEmit de sus projects).

¿Que es tsgo y por que deberia importarme?

Es el compilador nativo de TypeScript (linea 6/7, portado a Go): da el mismo resultado que tsc (mismo tsconfig) con tiempos del orden de 10x menores. En CI significa menos minutos por pipeline; en local, menos espera al salvar. Codigo compatible con 5.9+ corre igual en ambos.

¿Vale la pena cachear los tsbuildinfo en CI?

Para proyectos medianos/grandes, si: es el ahorro mas grande del chequeo incremental. Si tu chequeo dura segundos, el cache puede no compensar el overhead de restaurar. Mide antes de complicar.

¿Cuando desactivo skipLibCheck?

Cuando publicas librerias: quieres validar tus propios .d.ts y los de tus dependencias de tipos (p. ej. paquetes de tipos flojos). En apps, manten true: revisar cada .d.ts de node_modules cuesta y casi nunca aporta.

¿ESLint con reglas de tipos reemplaza a tsc?

No. Las reglas type-aware de @typescript-eslint se apoyan en el type checker para opiniones (no-misused-promises, no-unsafe-assignment), pero no sustituyen la comprobacion completa de tipos. tsc valida; ESLint opina. Ejecuta ambos.
