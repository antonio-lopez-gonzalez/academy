Contratos end-to-end tipados

Modulo 12 · Monorepos y produccion 🕐 40 minutos

1 · Introduccion

El mito mas caro del desarrollo web es "el backend me manda un JSON y ya se como es". No: quien lo dice define a mano un interface en front y otro en back, y cuando uno cambia, el otro se entera por un crash en produccion. Esta leccion construye un contrato end-to-end: un solo paquete contracts que comparten front y back, con validacion en runtime en el borde (con zod) y tipos derivados del schema con z.infer.

El problema que resuelve: los tipos no cruzan la red. En el motor de tu app, TypeScript te protege; en la frontera de la API, el dato llega como string o unknown y ninguna promesa del compilador le aplica. Un schema es la unica fuente de verdad: valida ahi, deriva los tipos para todos, y elimina los interface Pedido duplicados.

Cuando se utiliza
  • APIs propias donde controlas front y back (monorepo o no).
  • Contratos de red, payloads de eventos, respuestas de endpoints.
  • Cuando el JSON del exterior no se puede confiar para "tiparlo con as".
  • Equipos que quieren un unico punto de verdad y romper en CI, no en runtime.

2 · Teoria

La analogia: el contrato de obra y el formulario de aduanas

Front y back son dos paises que hablan idiomas distintos (navegador y servidor). El contrato es el documento que ambos firman: como se llama cada campo, que valores admite. Pero un contrato firmado no basta: en la aduana hay que revisar cada paquete que cruza la frontera antes de dejarlo entrar, porque cualquiera puede decir "esto es un Pedido" sin serlo. El schema es el contrato; parse/safeParse son la aduana.

El problema: tipos duplicados y deriva (drift)

Sin contrato compartido: apps/server/src/pedido.ts apps/client/src/api.ts ┌─────────────────────────┐ ┌──────────────────────────┐ │ interface Pedido { │ │ interface Pedido { │ │ id: string; │ │ id: string; │ │ total: number; │ │ total: number; │ │ } │ ✖ │ } │ │ // back anade "envio" │ ─────▶ │ // front no se entera │ └─────────────────────────┘ └──────────────────────────┘ ✖ dos copias de la verdad

Dos interfaces con el mismo nombre, mantenidas a mano, en repositorios (o carpetas) distintos. Cuando el back anade envio, el front no se entera hasta que un undefined explota en pantalla. Eso es drift: la deriva entre lo que el servidor produce y lo que el cliente cree que produce.

El borde de confianza: el JSON llega como unknown

const res = await fetch("/api/pedidos/1");
const pedido = await res.json(); // tipo: any 😱 nada te protege

// Lo "tipamos" a mano, pero es una mentira:
const pedido = (await res.json()) as Pedido; // ✖ asercion sin comprobar
// si el back cambio el contrato, esto no falla en compilacion:
// pedido.envio.metodo -> undefined.envio en runtime

La asercion as sobre un JSON no validado es una mentira que el compilador te cree. El JSON cruza la red sin tipos; "prometer" con as no convierte el dato, solo silencia al compilador. El problema se ve tarde: donde usas el campo, no donde llego.

zod: el schema como fuente de verdad

Un schema de zod es una descripcion ejecutable del dato: define la forma, la valida en runtime y, de paso, deriva el tipo estatico con z.infer. Un solo objeto gobierna dos mundos: el mundo real (verificacion) y el mundo de tipos (compilador). 

import { z } from "zod";

// El schema: fuente de verdad unica.
export const PedidoSchema = z.object({
  id: z.string(),
  total: z.number().nonnegative(),
  estado: z.enum(["creado", "pagado", "enviado"]),
});

// El tipo DERIVADO: no se escribe a mano, sale del schema.
export type Pedido = z.infer<typeof PedidoSchema>;
// => { id: string; total: number; estado: "creado" | "pagado" | "enviado" }
Por que derivar el tipo y no escribirlo

Si escribes el tipo a mano ademas del schema, tienes DOS fuentes de verdad otra vez: schema y tipo pueden divergir. Al derivar con z.infer, cualquier cambio en el schema actualiza el tipo en todo el proyecto de forma automatica. El schema es el hecho; el tipo, una consecuencia.

El patron: validar en el borde, tipar dentro

// 1) En el borde de entrada (server): parse antes de tocar la logica.
const body = PedidoSchema.safeParse(req.body);

if (!body.success) {
  // ✖ dato invalido: ni entra al dominio de negocio.
  return res.status(400).json({ error: body.error.flatten() });
}

// 2) Dentro del dominio, body.data YA es Pedido (validado).
registrar(body.data); // body.data: Pedido — no hay "as", hay prueba

La clave es donde se valida: en el borde, la primera linea del handler. A partir de ahi, el dato validado se mueve por el sistema con su tipo derivado. El resto del codigo nunca vuelve a dudar.

Comparativa de estrategias

Estrategia Seguridad en runtime Tipos en compilacion Fuente de verdad
as Pedido sobre el JSON Ninguna Si, pero mentirosa Dos copias manuales
Solo interface compartido Ninguna Si Una, pero no comprueba
Schema zod + z.infer Si (parse en el borde) Si, derivado Una, ejecutable

3 · Ejemplo minimo

schema-minimo.ts
import { z } from "zod";

// Schema: la unica fuente de verdad.
const UsuarioSchema = z.object({
  nombre: z.string().min(1),
  edad: z.number().int().positive(),
});

// Tipo derivado (no escrito a mano):
type Usuario = z.infer<typeof UsuarioSchema>;

// Validacion en el borde:
const resultado = UsuarioSchema.safeParse({ nombre: "Ana", edad: 30 });

if (resultado.success) {
  const u: Usuario = resultado.data; // ✅ data es Usuario de verdad
  console.log(u.nombre.toUpperCase());
} else {
  console.log("Dato invalido:", resultado.error.issues);
}

Linea a linea:

  • z.object describe la forma; los campos admiten restricciones (min, int, positive).
  • z.infer convierte el schema en el tipo Usuario estatico.
  • safeParse valida en runtime y devuelve un union: exito (con data) o fallo (con error.issues).
  • Tras safeParse, data esta validado: eliminaste la necesidad del as.

4 · Ejemplo real

Contrato de pedidos compartido entre un server (Node) y un client, dentro del monorepo del Modulo 12.

packages/contracts/package.json
{
  "name": "@acme/contracts",
  "dependencies": {
    "zod": "^4.0.0"
  }
}
packages/contracts/src/pedido.ts
import { z } from "zod";

// El contrato entero: entradas, salidas y errores.
export const EstadoSchema = z.enum(["creado", "pagado", "enviado"]);

export const PedidoSchema = z.object({
  id: z.string(),
  total: z.number().nonnegative(),
  estado: EstadoSchema,
  envio: z.object({
    metodo: z.enum(["correos", "agencia"]),
    seguimiento: z.string().optional(),
  }),
});

export const CrearPedidoSchema = z.object({
  total: z.number().positive(),
  metodo: z.enum(["correos", "agencia"]),
});

export const ErrorApiSchema = z.object({
  error: z.string(),
});

// Tipos derivados: los consumidores nunca los re-escriben.
export type Pedido = z.infer<typeof PedidoSchema>;
export type CrearPedido = z.infer<typeof CrearPedidoSchema>;
export type ErrorApi = z.infer<typeof ErrorApiSchema>;
apps/server/src/rutas.ts
import {
  CrearPedidoSchema,
  PedidoSchema,
} from "@acme/contracts";

// El borde: TODO lo externo pasa por safeParse antes de tocar negocio.
export async function crearPedido(req: Request): Promise<Response> {
  const cuerpo = await req.json(); // unknown, no confiable
  const entrada = CrearPedidoSchema.safeParse(cuerpo);

  if (!entrada.success) {
    // Dato invalido: se rechaza aqui, con detalle util.
    return new Response(JSON.stringify({
      error: entrada.error.issues.map(i => i.message),
    }), { status: 400 });
  }

  // entrada.data ya es CrearPedido validado.
  const pedido = { id: crypto.randomUUID(), estado: "creado", ...entrada.data };
  return new Response(JSON.stringify(pedido), {
    headers: { "content-type": "application/json" },
  });
}

export function validarPedidoEntrante(data: unknown): Pedido | null {
  const r = PedidoSchema.safeParse(data);
  return r.success ? r.data : null; // cargo completo, parseado
}
apps/client/src/api.ts
import type { CrearPedido, Pedido } from "@acme/contracts";

// El client importa solo TIPOS: sin codigo de validacion.
export async function crearPedido(input: CrearPedido): Promise<Pedido> {
  const res = await fetch("/api/pedidos", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(input),
  });

  const json = await res.json();
  // El client confia en el contrato: el server ya valido (o rechazo 4xx).
  return json as Pedido;
}

Decisiones:

  • El schema vive en contracts, el unico punto de verdad; front y back lo importan.
  • El server valida en runtime (aduana): nada externo entra sin safeParse.
  • Los tipos (Pedido, CrearPedido) se derivan con z.infer: nadie los escribe a mano, impossible el drift.
  • El client importa import type (cero peso en el bundle) y usa los mismos tipos.
  • Cambiar el contrato rompe en compilacion a ambos lados: descubres la rotura en CI, no en pantalla.

5 · Buenas practicas

  • Valida en el borde: primera linea del handler; que el dato invalido no cruce hacia el dominio.
  • Deriva SIEMPRE los tipos con z.infer; prohibido escribir a mano el interface paralelo.
  • En el client usa import type de los contratos (tipos borrados, cero bundle).
  • Rechaza con 400 y detalles utiles (error.issues) en lugar de romper con 500.
  • Combina con el monorepo de la leccion 1: contracts como paquete composite y referenciado.
  • Para schemas grandes, compone schemas pequenos (EstadoSchema dentro de PedidoSchema) y reutilizalos.

Que evitar

  • (await res.json()) as Pedido sin validar: una promesa sin prueba.
  • Validar en el interior y no en el borde: el dato malo ya toco logica de negocio.
  • Duplicar el schema en front y back: vuelves al drift con dos aduanas distintas.
  • Confiar en json() as T solo porque "el API es nuestro": los bugs de versiones y el cache rompen esa confianza.

6 · Errores habituales

Mal — asercion sin validar sobre JSON externo 
const res = await fetch("/api/pedidos/1");
const p = (await res.json()) as Pedido; // ✖ no se ha comprobado nada
console.log(p.envio.seguimiento.toUpperCase()); // puede explotar
Bien — safeParse en el borde 
const r = PedidoSchema.safeParse(await res.json());
if (!r.success) return; // o lanza un error manejable
console.log(r.data.envio.seguimiento?.toUpperCase()); // ✅ data es Pedido
Mal — escribir el tipo a mano ademas del schema 
const PedidoSchema = z.object({ id: z.string(), total: z.number() });

// ✖ dos fuentes de verdad: schema y tipo pueden divergir
interface Pedido {
  id: string;
  total: number;
}
Bien — tipo derivado del schema 
const PedidoSchema = z.object({ id: z.string(), total: z.number() });

// ✅ una sola fuente; si el schema cambia, el tipo cambia solo
type Pedido = z.infer<typeof PedidoSchema>;
Mal — validar dentro de la logica, tarde 
function procesar(pedido: Pedido): void {
  // ✖ el dato ya "toco" el sistema sin ser comprobado
  if (typeof pedido.total !== "number") { /* casi nunca llega aqui */ }
  cobrar(pedido.total);
}
Bien — validar en el borde 
export async function handler(req: Request): Promise<Response> {
  const r = PedidoSchema.safeParse(await req.json());
  if (!r.success) return new Response("400", { status: 400 });
  return procesar(r.data); // ✅ procesar recibe Pedido validado
}

7 · Ejercicio guiado

Construye un contrato de Producto y su handler de creacion.

  1. Instala zod en packages/contracts: pnpm --filter @acme/contracts add zod.
  2. Define ProductoSchema con nombre: z.string().min(1) y precio: z.number().nonnegative().
  3. Exporta type Producto = z.infer<typeof ProductoSchema>.
  4. En el server, crea un handler que haga safeParse del body y devuelva 400 si falla.
  5. En el client, importa import type { Producto } y escribe una funcion que reciba y devuelva Producto.

Solucion paso a paso:

packages/contracts/src/producto.ts
import { z } from "zod";

export const ProductoSchema = z.object({
  nombre: z.string().min(1),
  precio: z.number().nonnegative(),
});

export type Producto = z.infer<typeof ProductoSchema>;
apps/server/src/productos.ts
import { ProductoSchema } from "@acme/contracts";

export async function crearProducto(req: Request): Promise<Response> {
  const entrada = ProductoSchema.safeParse(await req.json());

  if (!entrada.success) {
    // Rechazo util en el borde: nombre o precio invalidos.
    return new Response(
      JSON.stringify({ error: entrada.error.issues.map(i => i.message) }),
      { status: 400, headers: { "content-type": "application/json" } },
    );
  }

  const guardado = { id: crypto.randomUUID(), ...entrada.data };
  return new Response(JSON.stringify(guardado), {
    headers: { "content-type": "application/json" },
  });
}
apps/client/src/api.ts
import type { Producto } from "@acme/contracts";

export async function crearProducto(p: Producto): Promise<Producto> {
  const res = await fetch("/api/productos", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(p),
  });
  return (await res.json()) as Producto; // el server ya valido
}

8 · Reto

Reto

Extiende el contrato con una union discriminada: PedidoSchema con un campo tipo igual a "digital" o "fisico", donde el fisico requiere envio y el digital requiere enlaceDescarga. Usa z.discriminatedUnion para que la union sea exhaustiva, y comprueba que en el server puedes distinguir ambos casos sin as. Pista: el discriminador debe aparecer como literal en cada rama del schema.

9 · Resumen

  • Los tipos no cruzan la red: el JSON llega como unknown y hay que validarlo, no "prometerlo" con as.
  • Un schema (zod) es la fuente de verdad: valida en runtime y deriva tipos con z.infer.
  • Validar en el borde: primera linea del handler, antes de la logica de negocio.
  • Compartir el paquete contracts entre front y back elimina el drift de interfaces duplicadas.
  • Un cambio de contrato rompe en compilacion en los dos lados: el error aparece en CI, no en produccion.

10 · Preguntas frecuentes

¿No basta con compartir solo los tipos con import type?

Compartir tipos quita el drift, pero los tipos desaparecen en runtime: alguien puede mandarte un JSON que no cumple el contrato y tu codigo lo tratara como valido. El schema anade la verificacion real en el borde. Lo ideal es schema + tipos derivados.

¿Cuando uso parse y cuando safeParse?

parse lanza una excepcion ZodError si falla; util en pruebas o cuando el fallo debe abortar el flujo. safeParse devuelve un union ({ success: true, data } | { success: false, error }) sin lanzar; la opcion recomendada en handlers y bordes.

¿Y si el client tambien quiere validar la respuesta del server?

Puedes: pasas la respuesta por PedidoSchema.safeParse en el client. Es una capa extra de seguridad ante proxies, caches o versiones desplegadas. El coste es pequeno comparado con diagnosticar un dato corrupto.

¿zod anade mucho peso al bundle del client?

Si importas el schema en el client, si: zod tiene coste. Solucion: en el client importa solo los tipos (import type) y deja la validacion en el server. Si necesitas validar en ambos lados, busca alternativas sin peso (o subdivide schemas por paquete).

¿Que pasa con fetch y el runtime fuera del browser (Node)?

Node 18+ trae fetch, Request y Response nativos, asi que el patron de esta leccion funciona igual en el server. El borde es el mismo: parsear antes de usar.

¿Puedo generar los contratos desde el schema en un solo paso?

Existen herramientas que derivan clientes tipados desde schemas (p. ej. tRPC, o generadores de clientes desde OpenAPI). Aqui aprendes el patron manual con zod: suficiente para la mayoria de APIs propias y la base sobre la que construyen esas herramientas.
