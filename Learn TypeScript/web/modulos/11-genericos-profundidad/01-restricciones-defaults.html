Restricciones, defaults e inferencia contextual

Modulo 11 · Genericos en profundidad 🕐 30 minutos

1 · Introduccion

En el modulo 5 viste genericos por primera vez: <T> captura un tipo y lo propaga por la firma. Pero un generico "sin control" acepta cualquier tipo, y a veces eso es demasiado: queremos decir "cualquier tipo que tenga id", o "cualquier tipo y si no lo dices, usa string". Esta leccion afina el control sobre T con cuatro tecnicas:

  • Restricciones (extends): el contrato minimo que todo tipo debe cumplir.
  • Defaults: el valor por defecto cuando el tipo no se declara ni se infiere.
  • Inferencia contextual: TypeScript llena T solo, mirando el contexto (callbacks, objetos, genericos de arrays).
  • Diferir la resolucion: el truco de no querer que se infiera, para que el tipo se decida en el punto de llamada.
Cuando se utilizan
  • extends: APIs que exigen una forma minimo (entidades con id, datos con nombre).
  • Defaults: utilidades muy genericas donde casi siempre vale lo mismo (K = string, E = Error).
  • Inferencia contextual: tecleas menos y el compilador tipa por ti en usos naturales.
  • Diferir: cargas, factorias y "fabricas de tipos" donde el dato llega despues del tipo.

2 · Teoria

extends como contrato

T extends Algo es una restriccion (constraint): no limita a un tipo concreto, limita al conjunto de tipos que cumplen una forma minima. Piensa en un trabajo de practicante: no piden "Ana" ni "Luis", piden "alguien que sepa JavaScript". Cualquier tipo que cumpla el contrato puede entrar, y ademas TypeScript lo recuerda: dentro de la funcion puedes usar las propiedades del contrato sin aserciones. 

// El contrato: minimo una propiedad id de tipo string.
function tieneId<T extends { id: string }>(entidad: T): string {
  return entidad.id; // ✅ el contrato garantiza que id existe
}

tieneId({ id: "u1", nombre: "Ana", rol: "admin" }); // ✅ tipo extra: permitido
// tieneId({ nombre: "Ana" }); // ✖ falta la propiedad id
Por que contratos y no tipos concretos

Si firmaras la funcion con { id: string; nombre: string } exacto, rechazarias el objeto del ejemplo (le sobra rol) y perderias el tipo real al devolver T. Con extends ganas en ambos lados: aceptas lo que cumpla el minimo y conservas el tipo completo en el retorno. El contrato se paga solo cuando el generico aporta algo; si nunca devuelves T, planteate si el generico sobra.

Parametros genericos con defaults

Igual que los parametros de funcion pueden tener un valor por defecto, los parametros de tipo pueden tener un tipo por defecto. Se aplican cuando quien usa la utilidad no los declara. Reglas: los parametros con default van al final y, si hay restriccion, el default debe cumplirla. 

// K tiene default: quien use Cache sin segundo argumento obtiene K = string.
interface Cache<T, K extends string = string> {
  guardar(clave: K, valor: T): void;
  leer(clave: K): T | undefined;
}

declare const numeros: Cache<number>; // K = string (default)
declare const simbolos: Cache<number, "a" | "b">; // K limitado a dos claves

// El default debe satisfacer la restriccion:
type Entorno<T extends string = "produccion"> = {
  entorno: T;
  debug: boolean;
};
declare const prod: Entorno;                    // entorno: "produccion"
declare const dev: Entorno<"desarrollo">;       // entorno: "desarrollo"
// type Mal = Entorno<number>; // ✖ number no cumple extends string
El default "never" como centinela

Un truco frecuente es usar = never como default: el parametro es opcional, pero si nadie lo rellena, la rama que depende de el se vuelve inalcanzable (condicionales que resuelven a never). Es la forma elegante de decir "este parametro existe para quien lo quiera usar, y si no, no molesta".

Inferencia contextual

Muchas veces no hace falta declarar T: TypeScript lo infiere del argumento. La inferencia contextual va un paso mas alla: cuando el generico ya esta fijado por un sitio, los otros lugares se tipan desde ese contexto sin anotarlos. El ejemplo clasico es el callback de map: no anotas el parametro, el tipo llega del array. 

const numeros = [1, 2, 3];
// n es number: el generico de map ya esta fijado por el array.
const dobles = numeros.map((n) => n * 2);

// T se infiere de "valor", y entonces el callback se tipa contextualmente:
function ajustar<T>(valor: T, fn: (v: T) => T): T {
  return fn(valor);
}
const resultado = ajustar(5, (n) => n + 1); // n: number, sin anotar nada

Un detalle importante: cuando hay varias fuentes de inferencia, TypeScript busca una solucion comun. Si dos sitios piden tipos incompatibles, el compilador se queja; ese error es util porque delata una firma mal disenada.

Diferir la resolucion: no querer inferir

A veces el generico no debe inferirse en la llamada, sino decidirse por el autor del codigo. El patron base es que T aparezca solo en el retorno (o en posiciones "fantasma"): sin argumentos que lo fijen, la unica forma de darle valor es declararlo explicito. 

// T no aparece en ningun argumento: nadie puede inferirlo.
// La resolucion se "difiere" al punto de llamada.
declare function consultar<T>(sql: string): Promise<T>;

interface Usuario {
  id: number;
  nombre: string;
}

async function cargarUsuarios() {
  const usuarios = await consultar<Usuario[]>("SELECT * FROM usuarios");
  // const v = await consultar("SELECT 1"); // ✖ sin argumento de tipo: T = unknown
  console.log(usuarios[0]?.nombre);
}
Analogia: el pedido con destinatario

consultar es como una empresa de paqueteria que puede llevar cualquier cosa (T), pero de quien firma el pedido depende que llegue "un paquete de discos" y no "una caja vacia". Si no escribes el destinatario (<Usuario[]>), TypeScript entrega un paquete unknown: lo recibes, pero no puedes abrirlo sin verificarlo.

Otra variante es el argumento fantasma: un parametro que solo existe para fijar el tipo, sin valor util en runtime. Tambien es comun usar satisfies para diferir: compruebas que un objeto cumple una forma sin que el objeto se ensanche ni se reduzca.

3 · Ejemplo minimo

ajustes-minimos.ts
// 1) extends: contrato minimo.
function inicial<T extends { nombre: string }>(x: T): string {
  return x.nombre.charAt(0);
}

// 2) Default: K vale "id" si no lo dices.
interface Almacen<T, K extends string = "id"> {
  guardar(clave: K, valor: T): void;
}
interface Usuario { id: string; nombre: string }
declare const almacen: Almacen<Usuario>; // K = "id"

// 3) Inferencia contextual: el callback se tipa solo.
declare const personas: Array<{ nombre: string; edad: number }>;
const nombres = personas.map((p) => p.nombre); // p ya esta tipado

// 4) Diferir: T se declara en la llamada, no se infiere.
declare function fabricar<T>(): T;
const numero = fabricar<number>();

Linea a linea:

  • <T extends { nombre: string }>: cualquier objeto con nombre entra; el retorno conserva T.
  • K extends string = "id": restriccion y default combinados; el default cumple la restriccion.
  • personas.map((p) => ...): nada de anotar p; el contexto lo aporta.
  • fabricar<number>(): sin argumentos no hay de donde inferir; el tipo se difiere al autor de la llamada.

4 · Ejemplo real

Un repositorio de datos con cache que combina las cuatro tecnicas: contrato, default, inferencia contextual en el constructor y carga diferida en las consultas.

repositorio-tipado.ts
// Contrato minimo: toda entidad persistible tiene id.
interface ConId {
  id: string;
}

// K tiene default. Quien use Repositorio solo declara la entidad.
class Repositorio<T extends ConId, K extends string = string> {
  private cache = new Map<K, T>();

  // El callback que decide la clave se tipa por inferencia contextual:
  // f es T, aunque quien construye no anota nada.
  constructor(private hashCode: (entidad: T) => K) {}

  guardar(entidad: T): void {
    this.cache.set(this.hashCode(entidad), entidad); // K y T ya casan
  }

  total(): number {
    let suma = 0;
    for (const entidad of this.cache.values()) {
      suma += (entidad as { importe?: number }).importe ?? 0;
    }
    return suma;
  }
}

// Consulta diferida: el tipo de datos se declara donde se consume.
declare function consultar<T>(sql: string): Promise<T>;

interface Factura extends ConId {
  importe: number;
}

async function cerrarDia() {
  const repo = new Repositorio<Factura>((f) => f.id); // f: Factura (contextual)
  repositoryEnUso(repo);

  const facturas = await consultar<Factura[]>("SELECT * FROM facturas");
  return facturas.reduce((acc, f) => acc + f.importe, 0);
}

function repositoryEnUso(repo: Repositorio<Factura>): void {
  repo.guardar({ id: "f-1", importe: 120 });
  repo.guardar({ id: "f-2", importe: 40 });
}

Decisiones:

  • extends ConId es el contrato: solo entidades con id entran, y dentro de la clase siempre puedes leer entidad.id.
  • El default K = string hace que new Repositorio<Factura>(...) compile sin declara K; si un dia necesitas claves por UUID, puedes declarar K = "uuid-...".
  • El callback del constructor se tipa contextualmente: (f) => f.id ya sabe que f es Factura.
  • consultar<Factura[]> difiere el tipo: la funcion de consulta es reutilizable, el significado lo pone el consumidor.
  • Quien llama una vez obtiene tipos exactos en cadena: sin any ni aserciones repetidas.

5 · Buenas practicas

  • Haz restricciones minimas: pide solo lo que la funcion necesita, no "todo el objeto". Un contrato pequeno es un contrato utilizable.
  • Pon los defaults al final de la lista de parametros genericos y verifica que cumplan la restriccion.
  • Prefiere la inferencia contextual: anota <T> cuando el tipo salga de los argumentos y deja el cafe para el punto de llamada.
  • Diferi la resolucion solo cuando el tipo dependa del que llama, no del argumento (cargas, factorias, decodificadores).
  • Explica el contrato en el @param o en un comentario de cabecera; el contrato es tu documentacion ejecutable.

Que evitar

  • Restricciones con object si tambien quieres primitivos: object rechaza string y number.
  • Defaults "por si acaso" que enmascaran el error de haber olvidado el tipo; un default que no se usa es ruido.
  • Diferir tipos que si tienen inferencia clara, obligando a anotar a mano lo que ya se sabe.
  • Cambiar la restriccion entre versiones sin revisar los puntos de llamada: un contrato mas estricto rompe consumidores silenciosamente.

6 · Errores habituales

Mal — default que no cumple la restriccion 
type Entorno<T extends string = number> = T; // ✖ number no cumple extends string
Bien — default valido, restriccion y default al final 
type Entorno<T extends string = "produccion"> = T; // ✅
Mal — restriccion tan amplia que no protege nada 
function largo<T extends any>(x: T): number { // any no aporta negocio
  return x.length; // ✖ any permite esto aunque no exista length
}
Bien — contrato con lo que la funcion usa 
function largo<T extends { length: number }>(x: T): number {
  return x.length; // ✅ el contrato garantiza length
}
Mal — olvidar el tipo en una llamada diferida 
declare function consultar<T>(): Promise<T>;
const datos = await consultar(); // ✖ T = unknown: uso inseguro despues
Bien — declarar el tipo en el punto de consumo 
interface Pedido { total: number }
const pedido = await consultar<Pedido>(); // ✅ T esta decidido

7 · Ejercicio guiado

Queremos una funcion procesarCola que acepte cualquier dato con id, una cache con default de clave, y una carga diferida para llenarla.

  1. Declara interface ConId { id: string }.
  2. Define class Cola<T extends ConId, K extends string = "id"> con un Map<K, T> y metodos agregar y leer.
  3. Haz que agregar extraiga la clave de una funcion pasada al constructor (inferencia contextual).
  4. Declara declare function cargar<T>(): Promise<T>.
  5. Usa la cola con cacheDePedidos = new Cola<Pedido>(...) y rellenala con await cargar<Pedido[]>().

Solucion paso a paso:

ejercicio-restricciones.ts
interface ConId {
  id: string;
}

class Cola<T extends ConId, K extends string = "id"> {
  private datos = new Map<K, T>();

  constructor(private claveDe: (entidad: T) => K) {}

  agregar(entidad: T): void {
    this.datos.set(this.claveDe(entidad), entidad);
  }

  leer(clave: K): T | undefined {
    return this.datos.get(clave);
  }
}

declare function cargar<T>(): Promise<T>;

interface Pedido extends ConId {
  total: number;
}

async function iniciar() {
  // El callback se tipa contextualmente: p es Pedido.
  const cacheDePedidos = new Cola<Pedido>((p) => p.id);

  const pedidos = await cargar<Pedido[]>();
  for (const p of pedidos) {
    cacheDePedidos.agregar(p);
  }

  const primero = cacheDePedidos.leer("p-1");
  console.log(primero?.total ?? 0); // total existe porque T extends ConId y Pedido lo tiene
}

8 · Reto

Reto

Escribe una funcion esperar<T, R = T>(proceso: () => Promise<T>) que devuelva un objeto con resultado: () => Promise<T> y transformar: (fn: (x: T) => R) => ..., de forma que el tipo de R se infiera del callback y el de T se difiera a la llamada inicial (pista: solo el retorno original menciona T; el transformador anade R con un segundo generico por defecto).

9 · Resumen

  • T extends Contrato es una restriccion: acepta todo tipo que cumpla la forma minima y conserva el tipo completo en el retorno.
  • Los defaults (K = string) van al final y deben satisfacer la restriccion; = never sirve de centinela.
  • La inferencia contextual tipa callbacks y objetos desde el contexto ya fijado, sin anotaciones redundantes.
  • Diferir la resolucion (= dejar T solo en el retorno) obliga a declarar el tipo donde se consume, ideal para cargas y factorias.
  • Contrato, default, contexto y diferimiento son cuatro perillas para decir exactamente cuanto control quieres sobre T.

10 · Preguntas frecuentes

¿extends sustituye a la genericidad?

No: lo contrario. extends recorta el conjunto de tipos aceptados pero sigue siendo generico: acepta cualquier tipo que cumpla el contrato, no solo un tipo fijo. Lo comprobas porque el retorno sigue siendo T, no el contrato.

¿Un default oculta errores de tipado?

Puede. Si el default se aplica silenciosamente, un olvido del autor de la llamada pasa desapercibido. Por eso los defaults deben tener sentido "por defecto" (string, Error, unknown) y las restricciones deben ser lo bastante precisas para que el contrato siga protegiendo.

¿Cuando conviene no inferir y anotar a mano?

Cuando la inferencia daria un tipo equivocado o demasiado amplio. Ejemplos: cargas (consultar<T>), decodificadores ("este JSON es un Usuario") y APIs donde el tipo lo define el consumidor, no el argumento.

¿Por que los defaults van siempre al final?

Porque los genericos se rellenan en orden posicional: si un parametro con default estuviera antes de uno obligatorio, no habria forma de omitir el del medio sin usar undefined. La regla mantiene las llamadas legibles.

¿La inferencia contextual funciona con objetos?

Si. Cuando declaras un objeto con un tipo anotado, las propiedades que faltan se tipan desde el tipo anotado, y los callbacks dentro del objeto reciben contexto. Es el mismo mecanismo que en los argumentos: el tipo ya esta "fijado" y el resto del codigo se ajusta a el.

¿Puedo combinar extends, default y diferimiento en una firma?

Si, y es comun. Por ejemplo function cargar<T extends ConId, K extends string = "id">(): Promise<T[]> tiene contrato, default y tipo diferido a la vez. Solo respeta el orden: primero obligatorios, luego defaults.
