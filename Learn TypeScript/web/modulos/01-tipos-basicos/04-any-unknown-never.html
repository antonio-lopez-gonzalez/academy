any, unknown, never y modo strict

Modulo 1 · Tipos basicos 🕐 30 minutos

1 · Introduccion

TypeScript tiene tres tipos "especiales" que marcan el contorno de su tipado: any (sin control), unknown (control seguro de lo desconocido) y never (lo imposible). Dominarlos es entender los limites del sistema, y todo esto cobra sentido dentro del modo strict, que es como vamos a trabajar siempre.

Al terminar sabras responder a una de las preguntas mas importantes de TypeScript: "¿recibo algo de fuera que no se que es, como lo trato sin abrir la puerta a cualquier cosa?".

2 · Teoria

any: el tipo que apaga el compilador

let dato: any = "hola";
dato = 42;            // ✅ cualquiera vale
dato = { x: 1 };      // ✅ cualquiera vale
dato.estoNoExiste();  // ✅ no da error de compilacion... hasta runtime

any es "se acepta todo y no se comprueba nada". Util para migraciones puntuales y para prototipos, es la puerta que vuelves a abrir a JavaScript sin tipos. Su riesgo: el error que evita TypeScript justo no se detecta. Ademas, any se propaga: si una funcion recibe any, su resultado suele ser any, y el "sin tipos" contagia todo tu codigo.

unknown: el "no se, comprueba antes"

unknown admite cualquier valor, pero obliga a estrechar antes de usar:

let dato: unknown = JSON.parse('{"precio": 9}');

// dato.precio;               // ✖ error: el tipo es unknown
// dato.toUpperCase();        // ✖ error: unknown no tiene metodos

// Para usarlo hay que comprobar su forma:
if (typeof dato === "object" && dato !== null && "precio" in dato) {
  // aqui "dato" ya tiene forma de objeto y "precio" existe
  console.log("vi precio");
}

La diferencia con any es filosofica: any dice "no me lo preguntes"; unknown dice "preguntame, pero no prometas". Todo lo que llega del exterior (JSON.parse, fetch, eventos, inputs) deberia aterrizar en unknown y validarse.

never: el tipo del "que no puede pasar"

never es el conjunto vacio: cero valores posibles. Aparece en:

// Funcion que siempre lanza: su retorno es "never".
function lanzarError(mensaje: string): never {
  throw new Error(mensaje);
}

// Ramas que TypeScript sabe que son imposibles.
function correjir(x: string | number) {
  if (typeof x === "string") {
    // aqui x: string
  } else {
    // aqui x: number  (ya se quedo sin opciones)
  }
}

never es esencial para el "exhaustive check": cuando un switch cubre todos los casos de una union, la rama default queda never. Si añades un caso nuevo al tipo y olvidas tratarlo, el switch deja de ser exhaustivo y el compilador avisa. Lo practicaras a fondo en el modulo 4.

El modo strict

strict activa ~6-10 comprobaciones. Las dos que mas nos importan ahora:

  • strictNullChecks: null/undefined no entran en los tipos por defecto.
  • noImplicitAny: una funcion con parametro sin tipo da error (en vez de asumir any silenciosamente).
// Con noImplicitAny, este codigo DA ERROR:
// function saludar(nombre) { ... }  // ✖ Parametro 'nombre' tiene tipo implicito any

// La intencion te obliga a decidir el tipo:
function saludar(nombre: string): void {
  console.log(`Hola ${nombre}`);
}
Por que strict SIEMPRE

La mayoria de los bugs que TypeScript evita dependen de strict. Trabajar sin el es como llevar casco sin abrochar: parece que protege. La comunidad profesional lo da por hecho: todo proyecto serio lo activa desde el primer dia.

Aserciones cuando TU sabes mas que el compilador

// as: "confia en mi, esto es un number". Solo si estas SEGURO.
const edad = document.getElementById("edad") as HTMLInputElement;
edad.value = "30"; // el DOM en tipado no sabe que existe; tu se lo dices

// ! (non-null): "se que esto NO es null/undefined en este punto".
const contenedor = document.getElementById("app")!;

Las aserciones no cambian el valor en runtime: solo convencen al compilador. Usalas con criterio: si te equivocas, el error aparecera en runtime. Son un negativo de any hecho a medida.

3 · Ejemplo minimo

especiales.ts
// unknown: el valor "caido del cielo" exige comprobacion.
const entrada: unknown = "42";

// No puedes sumarlo ni llamar metodos sin estrechar antes.
// const numero = entrada + 1;  // ✖ "entrada" es unknown

// Estrechamos en runtime con typeof:
let valorNumerico: number | null = null;
if (typeof entrada === "number") {
  valorNumerico = entrada; // aqui TS sabe que "entrada" es number
}

// never: la rama imposible se usa para avisar en el futuro.
function checkNunca(x: never): void {
  console.log("Esto es imposible: " + x);
}

4 · Ejemplo real

Leer la respuesta de una API sin saber si es exito o error — el caso clasico de unknown:

api.ts
interface Usuario {     // forma esperada del dato de exito
  nombre: string;
  email: string;
}

// Recibe lo que sea y devuelve un Usuario SOLO si la forma cuadra.
// Si no encaja, devuelve null en vez de romper silenciosamente.
function parsearUsuario(datos: unknown): Usuario | null {
  // Comprobacion estructurada: objeto no nulo con nombre y email strings.
  if (
    typeof datos === "object" &&
    datos !== null &&
    "nombre" in datos &&
    "email" in datos
  ) {
    // Tras las comprobaciones, "datos" es object con esas claves.
    // Como TS no conoce aun las formas, extraemos de forma segura:
    const { nombre, email } = datos as Record<string, unknown>;
    if (typeof nombre === "string" && typeof email === "string") {
      return { nombre, email }; // Conversion EXPLICITA y vigilada
    }
  }
  return null; // No cumple la forma: devolvemos ausencia, no `any`
}

// Un JSON real desde una red: JSON.parse devuelve "any".
const crudo: unknown = JSON.parse('{"nombre":"Ada","email":"ada@dev.ts"}');

const usuario = parsearUsuario(crudo);
if (usuario) {
  console.log(`Bienvenida, ${usuario.nombre}`);
} else {
  console.log("El JSON no tenia la forma esperada.");
}

Decisiones:

  • El dato externo aterriza en unknown, no en any: nadie puede usarlo sin pasar por la validacion.
  • La funcion no lanza si los datos son malos: devuelve null y el flujo decide. Menos codigo de excepciones, mas prediccion.
  • La escritura usa unknown como "canal de entrada" y la funcion como "aduana" que solo deja pasar lo que cumple la forma.

5 · Buenas practicas

  • Entrada unknown, salida validada: nunca devuelvas any desde tus funciones publicas.
  • Evita any: su sitio legitimo es escaso (parches, scripts de migracion).
  • Usa never en ramas imposibles y para el exhaustive check del modulo 4.
  • Usa void como retorno de funciones que solo hacen efectos.
  • Las aserciones (as, !) las justo donde el DOM o librerias tipan de menos; documenta el por que.

Que evitar

  • any como "tipo por defecto" de variables de entrada.
  • Aserciones as para saltarte problemas de tipos sin comprobar.
  • Desactivar strict para que los errores desaparezcan.

6 · Errores habituales

Mal — JSON.parse directamente como string 
const datos = JSON.parse(respuesta); // tipo: any
console.log(datos.precio);           // any: compila, pero "precio" puede no existir
Bien — pasar por unknown y validar 
const datos: unknown = JSON.parse(respuesta); // obliga a comprobar
// validacion antes de usar datos.precio...
Mal — asercion para apagar el compilador 
const total = valor as number; // si valor es "abc", total sera la cadena
total.toFixed(2);              // 💥 Typeerror en runtime
Bien — validacion real antes de la asercion 
if (typeof valor === "number") {
  valor.toFixed(2); // TS sabe que es number, sin asercion
}
Mal — retornar any desde funciones publicas 
function obtener() { return JSON.parse(d); } // retorna any
Bien — retorno tipado o unknown_validado 
function obtener(): Producto | null {
  const crudo: unknown = JSON.parse(d);
  return parsearProducto(crudo); // validado dentro
}

Por que estan mal: any y las aserciones perezosas mueven el error del compilador al runtime, que es exactamente lo que el curso intenta que nunca pase.

8 · Reto

Reto

Escribe una funcion generica de "aduana" esArea(lista, valor) que compruebe si un unknown pertenece a una readonly string[] de estados validos. Despues, usala para convertir un unknown de localStorage en uno de tus estados tipados sin nunca usar as. (Idealmente reutiliza el ejercicio de la leccion de enums).

9 · Resumen

  • any: sin comprobacion, se propaga, evítalo fuera de parches/migraciones.
  • unknown: admite todo pero obliga a estrechar antes de usar; es el canal seguro de entrada.
  • never: el conjunto vacio; para throw y para el exhaustive check.
  • void: funciones que no devuelven valor util.
  • strict activa strictNullChecks y noImplicitAny, entre otros.
  • Aserciones as y !: cuando tu sabes mas, pero con responsabilidad.

10 · Preguntas frecuentes

¿Hay algun momento en que any sea la opcion correcta?

Migraciones graduales de JS a TS, y al interactuar con codigo legacy con tipado imposible. Pero siempre acotado, documentado y con intencion de eliminarlo.

¿Por que JSON.parse devuelve any y no unknown?

Historia: any fue el tipo elegido en su dia. El idioma correcto hoy es asignar el resultado a un unknown y validar. No dejes que el any "borre" tu validacion.

¿Puedo asignar any a unknown? ¿Y al reves?

any → unknown siempre es seguro. unknown → cualquier tipo requiere comprobacion o asercion. Esa asimetria es la proteccion.

¿Que diferencia hay entre as y !?

as convence al compilador del tipo de un valor. ! solo elimina null/undefined de un tipo que puede serlo. Ambos no cambian nada en runtime.

¿never y void son lo mismo?

No. void = "devuelve sin valor". never = "no puede devolver" (la ejecucion no llega al final: lanza o no termina).
