Enums y const assertions

Modulo 1 · Tipos basicos 🕐 30 minutos

1 · Introduccion

Cuando un dato solo puede tomar unos pocos valores (estado: pendiente/enviado/entregado; rol: admin/usuario), JavaScript usa cadenas magicas o numeros. En TypeScript tienes dos herramientas: los enum (introducidos en el lenguaje) y las const assertions con as const sobre objetos (el patron moderno recomendado).

Aqui no solo aprenderas la sintaxis de ambos, sino la discusion de fondo que todavia divide opiniones: cuando un enum es una buena idea y cuando conviene evitarlo. Esta leccion te da criterio, no solo recetas.

2 · Teoria

El problema de fondo: constantes sin tipo

// JavaScript puro: el estado es un string suelto. Errores tipograficos
// o valores inventados no generan ninguna alerta.
const estado = "enviado";

function cambiarEstado(nuevo: string) {
  // ¿que impide pasar "enviado " (con espacio) o "borrado"?
  console.log(`Cambiando a ${nuevo}`);
}

El valor "enviado" no esta conectado con el conjunto de estados validos. La idea de enum y de union de literales es hacer finito y conocido ese conjunto.

Enum numerico

enum Estado {
  Pendiente,   // 0 (auto)
  Enviado,     // 1
  Entregado,   // 2
}
console.log(Estado.Pendiente); // 0
console.log(Estado[1]);        // "Enviado" (mapeo inverso)

Por defecto los miembros se numeran 0,1,2... Puedes forzar valores, e incluso mezclar: 

enum CodigoError {
  OK = 200,
  NoEncontrado = 404,
  ErrorInterno = 500,
}

Enum de strings

enum Rol {
  Admin = "ADMIN",
  Usuario = "USUARIO",
  Invitado = "INVITADO",
}
console.log(Rol.Admin); // "ADMIN"

Los enums de string son mas legibles que los numericos (el valor se ve en logs y en la base de datos) y no tienen el mapeo inverso (que en numericos es una curiosidad y una trampa).

El problema de los enums: existen en runtime

Un enum "normal" genera JavaScript real en tu bundle. Eso significa:

  • Añade codigo que se ejecuta (aunque en tree-shaking moderno se pueda eliminar en parte).
  • Su mapeo inverso numerico permite hacer Estado[0], rompiendo el tipado.
  • No se puede usar const enum con isolatedModules (que Vite requiere), porque el compilador "inline" los valores y los transpiladores por fichero no pueden hacerlo.
const enum: ojo con Vite

const enum Estado { ... } desaparece en runtime (los valores se inline). Pero al compilar fichero a fichero (aislado, como hace Vite) no siempre es posible. La recomendacion actual de la comunidad es: no usar const enum salvo que sepas exactamente lo que haces.

La alternativa moderna: union de literales + as const

La recomendacion predominante hoy en dia es representar los valores con union types:

// 1. Union de literales: el tipo del dato.
type Estado = "pendiente" | "enviado" | "entregado";

// 2. Objeto "as const": las constantes con sus valores reales.
// "as const" vuelve cada propiedad un LITERAL inmutable.
export const ESTADOS = {
  Pendiente: "pendiente",
  Enviado: "enviado",
  Entregado: "entregado",
} as const;

// ESTADOS.Enviado tiene el tipo literal "enviado", no string.
const estado: Estado = ESTADOS.Enviado; // ✅
// const mal: Estado = "volando";       // ✖ no es un estado valido

Ventajas: no genera runtime (el objeto ya existe), no tiene mapeo inverso, funciona perfectamente con Vite, y el compilador valida cada valor contra la union. Es el patron que usaremos en este curso como opcion por defecto.

Que es "as const" exactamente

as const es una afirmacion que le dice al compilador: "trata este valor con la maxima estrechez posible". Sus tres efectos: 

// Sin as const: propiedades amplian a string/number.
const config = { puerto: 3000, entorno: "dev" };
// config.puerto: number, config.entorno: string

// Con as const: todo queda como literal.
const configFija = { puerto: 3000, entorno: "dev" } as const;
// configFija.puerto: 3000 (literal), configFija.entorno: "dev" (literal)
  1. Las propiedades de objetos pasan a ser literales.
  2. Los arrays pasan a readonly tuplas.
  3. Toda la estructura queda readonly.

3 · Ejemplo minimo

estado-minimo.ts
// PATRON RECOMENDADO: union + as const
type EstadoPedido = "pendiente" | "enviado" | "entregado";

export const ESTADOS_PEDIDO = {
  Pendiente: "pendiente",
  Enviado: "enviado",
  Entregado: "entregado",
} as const;

// Funcion que SOLO acepta estados validos.
function actualizarEstado(nuevo: EstadoPedido): void {
  console.log(`Estado actualizado a: ${nuevo}`);
}

actualizarEstado(ESTADOS_PEDIDO.Enviado);   // ✅
// actualizarEstado("pagado");              // ✖ error TS2345

4 · Ejemplo real

Un sistema de envio que valida transiciones de estado. Compara los dos enfoques:

Con enum (funciona, pero... 
enum EstadoEnvio {
  Pendiente = "PENDIENTE",
  Enviado = "ENVIADO",
  Entregado = "ENTREGADO",
}

// La validacion manual es necesaria porque cualquier string podria colarse.
function transicionar(estado: EstadoEnvio): void {
  console.log(`Procesando: ${estado}`);
}
// transicionar(EstadoEnvio[1]); // con numericos podrias romper el tipado
Con union + as const (recomendado) 
// Los tres estados posibles del envio.
export type EstadoEnvio = "PENDIENTE" | "ENVIADO" | "ENTREGADO";

// Las constantes reales, derivadas de la union. "as const" las estrecha.
export const EstadoEnvio = {
  Pendiente: "PENDIENTE",
  Enviado: "ENVIADO",
  Entregado: "ENTREGADO",
} as const;

// Transiciones permitidas: clave = estado actual, valor = siguientes.
export const TRANSICIONES = {
  PENDIENTE: ["ENVIADO"],
  ENVIADO: ["ENTREGADO"],
  ENTREGADO: [], // terminal
} as const;

// Valida que un cambio sea legal, todo con tipos.
function puedeTransicionar(actual: EstadoEnvio, siguiente: EstadoEnvio): boolean {
  // el acceso con el estado actual da el array de destinos permitidos.
  return (TRANSICIONES[actual] as readonly string[]).includes(siguiente);
}

console.log(puedeTransicionar("PENDIENTE", "ENVIADO"));   // true
console.log(puedeTransicionar("ENTREGADO", "ENVIADO"));   // false

Decisiones: el objeto EstadoEnvio exportado es a la vez el tipo y el conjunto de constantes (mismo nombre, algo habitual con este patron). La union garantiza que nadie invente estados; el objeto evita cadenas magicas repartidas por el codigo.

5 · Buenas practicas

  • Por defecto, usa union de literales + as const en vez de enum. Es el patron dominante hoy.
  • Los enums de strings son la opcion "oficial" si prefieres enum: sus valores son auto-descriptivos.
  • Prefiere Estado["X"]... no: accede siempre por clave (EstadoEnvio.Enviado) y nunca por mapeo inverso.
  • Mantén la union y el objeto de constantes juntos y en el mismo fichero, para que no divergan.
  • Si usas enums de verdad (necesidades de compatibilidad), activa siempre isolatedModules y evita const enum.

Que evitar

  • const enum en proyectos Vite/modernos.
  • Enums numericos para estados que veras en logs o BD: numeros sin nombre (0,1,2) son imposibles de depurar.
  • Depender del mapeo inverso Estado[0]: invita a romper el tipado.

6 · Errores habituales

Mal — asignar un string "valido" a un enum 
enum Estado { Pendiente = "PENDIENTE" }
let e: Estado = "PENDIENTE"; // ✖ "PENDIENTE" no es Estado (aunque el valor coincida)
Bien — con union y as const si funciona 
type Estado = "PENDIENTE";
const Estado = { Pendiente: "PENDIENTE" } as const;
let e: Estado = Estado.Pendiente; // ✅
Mal — numerico para estados reales 
enum Estado { Pendiente, Enviado } // 0 y 1: ininterpretables en logs
console.log(Estado.Enviado);        // 1 — ¿de que estado hablo?
Bien — strings auto-descriptivos 
const Estado = { Pendiente: "pendiente", Enviado: "enviado" } as const;
console.log(Estado.Enviado); // "enviado" — legible en logs

Por que estan mal: el enum y sus valores son "tipos nominales" (no intercambiables con sus valores string); los numericos pierden semantica al leer el codigo y en la base de datos.

9 · Resumen

  • enum crea un tipo con un conjunto de miembros: numericos o de strings, con (o sin) mapeo inverso.
  • Los enums existen en runtime y el const enum choca con el compilado aislado de Vite.
  • Patron recomendado: union de literales + objeto as const — sin runtime extra, con validacion total.
  • as const estrecha propiedades a literales, arrays a readonly y toda la estructura a readonly.
  • Para estados/roles usa siempre valores strings auto-descriptivos, nunca numeros sin nombre.

10 · Preguntas frecuentes

¿Estan "desaconsejados" los enums en TypeScript?

No por el lenguaje, pero la comunidad los usa cada vez menos. Los problemas (runtime, mapeo inverso, const enum con isolatedModules) se resuelven con union + as const, que es mas simple y seguro. Usa enums cuando tu ecosistema o librerias los necesiten.

¿Que es el mapeo inverso y por que es peligroso?

En enums numericos, Estado[0] devuelve "Pendiente" (mapeo nombre→valor y valor→nombre). Permite accesos no tipados (Estado[5] compila y da undefined en runtime).

¿Puedo iterar los valores de un enum?

Con enums de strings puedes con Object.values. Con union + as const tambien, y con el beneficio de que el objeto y el tipo son la misma fuente de verdad.

¿Por que as const hace los arrays readonly?

Porque as const impone la maxima estrechez y la inmutabilidad: las tuplas y propiedades pasan a ser de solo lectura. Es coherente con su filosofia de "no cambies lo que declaro".

¿Que pasa si necesito un valor "libre" ademas de los fijos?

Usa una union mas amplia: type Estado = "pendiente" | "enviado" | string... cuidado, eso se reduce a string. Mejor: type Estado = EstadoConocido | (string & {}) si realmente lo necesitas (es un truco avanzado; por defecto, evita el "abierto").
