Template literals y branded types

Modulo 6 · Utility Types 🕐 30 minutos

1 · Introduccion

Dos grupos de tecnicas que dan semantica a los strings y a los numeros:

  • Template literal types avanzados: no solo rutas; construyen tipos a partir de cadenas, reescriben prefijos, y pueden extraer infer de partes de la cadena.
  • Branded types: una marca nominal sobre un tipo base para distinguir "un id de usuario" de "un id de pedido", aunque ambos sean number.

El problema: string y number son demasiado genericos. Un id de usuario y un id de pedido son ambos number, y TypeScript (estructural) no los distingue. Los branded types crean identidades nominales para que el compilador los separe.

Cuando se utilizan
  • IDs con dominio propio (userId, orderId, projectId).
  • Tokens, slugs, colores validados con formato.
  • Rutas tipadas con parametros interpolados.
  • Capas donde quieres diferenciar datos "crudos" de datos "validados".

2 · Teoria

La analogia: el DNI con tipo de documento

Tanto un usuario como un pedido tienen un "numero". En JavaScript, ambos son number y puedes mezclarlos por error: guardar el id de un pedido donde iba el id del usuario. El branded type es como el numero de identidad que lleva impreso el tipo de documento: UsuarioId, PedidoId. Son el MISMO numero, pero viene etiquetado con su dominio. TypeScript no te deja cruzar las marcas.

Template literal types: sintaxis y casos

type Prefijo = `api:${string}`;
const a: Prefijo = "api:usuarios"; // ✅

// En unions:
type Recurso = "users" | "orders";
type RutaCon = `/v1/${Recurso}`; // "/v1/users" | "/v1/orders"

// Extraer la parte dinamica con infer:
type ExtraeParam<S extends string> = S extends `api:${infer R}` ? R : never;
type Param = ExtraeParam<"api:usuarios">; // "usuarios"
Por que uppersnake keys y parsing

Los template literals no solo construyen strings tipados; con infer tambien los parens. TypeScript puede reconocer un "patron" y extraer el trozo variable. Esto permite tipar rutas parametrizadas, claves i18n o prefijos de eventos con una sola utilidad.

Branded types: la marca

// Una marca: un campo simbolico que no existe en runtime.
declare const marca: unique symbol;

type UsuarioId = number & { [marca]: "UsuarioId" };
type PedidoId = number & { [marca]: "PedidoId" };

number & { ... } es un "number, pero con una marca que solo se crea al validar". Te obliga a pasar por una funcion constructora para obtener un valor marcado: 

// Constructores seguros: solo aqui se pueden crear valores marcados.
function usuarioId(n: number): UsuarioId {
  return n as UsuarioId; // asercion controlada en el punto unico
}

function pedidoId(n: number): PedidoId {
  return n as PedidoId;
}

function obtenerUsuario(id: UsuarioId): void { /* ... */ }

const uid = usuarioId(7);
obtenerUsuario(uid);            // ✅
// obtenerUsuario(pedidoId(5)); // ✖ PedidoId no es UsuarioId

La marca con symbol

El patron moderno usa un unique symbol como marca (declarado con declare) para que la interseccion sea nominal:

// La marca queda "inferida" en el tipo.
declare const marcaPedido: unique symbol;

type IDPedido = number & { readonly [marcaPedido]: "IDPedido" };

function validarPedido(crudo: number): IDPedido | null {
  return crudo > 0 ? (crudo as IDPedido) : null; // validacion real del id
}

La marca no existe en runtime: es un truco de tipos (el compilador lo borra con type erasure). Por eso la funcion constructora/validadora es crucial: es la unica puerta para crear valores marcados sin hacer trampa.

Combinacion con genericos y utilidades

// La marca generica reutilizable (branding moderno):
declare const marcaGenerica: unique symbol;

type MonedaM<M extends string> = number & { readonly [marcaGenerica]: M };

type ValorEuropeo = MonedaM<"EUR">;
type ValorDolar = MonedaM<"USD">;

function sumarEUR(a: ValorEuropeo, b: ValorEuropeo): ValorEuropeo {
  return (a + b) as ValorEuropeo;
}
// sumarEUR(eur, usd) ✖ falla: marcas distintas

3 · Ejemplo minimo

brand-minimo.ts
// 1) Template: rutas tipadas con parametro.
type Ruta = `/pedidos/${number}`;
const r: Ruta = "/pedidos/42"; // ✅
// const bad: Ruta = "/pedidos/abc"; // ✖ "abc" no es un numero
// const bad2: Ruta = "/usuarios/42"; // ✖ falta el prefijo "/pedidos/"

// 2) Branded: ids con marca.
declare const marca: unique symbol;
type Euro = number & { readonly [marca]: "EUR" };
type Dolar = number & { readonly [marca]: "USD" };

const eur = (n: number) => n as Euro;
const usd = (n: number) => n as Dolar;

const total: Euro = eur(10);
// total = usd(5); // ✖ marcas distintas

Linea a linea:

  • type Ruta = `/pedidos/${number}`: template literal restringido a un segmento numerico.
  • La marca cruza number con un objeto cuyo simbolo solo TypeScript distingue.
  • Los "constructores" eur/usd crean los valores marcados; fuera de ahi no hay marca.
  • Sumar/mezclar tipos con marcas distintas produce error en compilacion.

4 · Ejemplo real

Servicio de pagos donde Euros y Dolares no pueden mezclarse, y un endpoint con rutas tipadas:

pagos-branded.ts
// Marca generica para numeros.
declare const marca: unique symbol;
type Moneda<M extends string> = number & { readonly [marca]: M };

type EUR = Moneda<"EUR">;
type USD = Moneda<"USD">;

// Constructores: la unica puerta.
function euros(n: number): EUR { return n as EUR; }
function dolares(n: number): USD { return n as USD; }

// Operaciones seguras por moneda.
function sumarEUR(a: EUR, b: EUR): EUR {
  return (a + b) as EUR;
}

// Rutas tipadas de la API.
type RutaPago = `/pagos/${string}/${"eur" | "usd"}`;
const cobrarRuta: RutaPago = "/pagos/123/eur"; // ✅

// Servicio:
function cobrar(importe: EUR, ruta: RutaPago): boolean {
  console.log(`Cobro ${importe} en ${ruta}`);
  return true;
}

const a = euros(100);
const b = euros(30);

cobrar(sumarEUR(a, b), cobrarRuta); // ✅ tipos correctos
// cobrar(dolares(5), cobrarRuta);  // ✖ USD no es EUR

Decisiones:

  • Una sola marca generica Moneda<M> en vez de duplicar tipos.
  • Los constructores centralizan la asercion; fuera de ellos es imposible crear monedas.
  • El template literal con union de divisas válidas tipa la ruta real.
  • Los errores del tipo documentan el dominio: USD y EUR no se cruzan.

5 · Buenas practicas

  • Centraliza la construccion de valores marcados en funciones validadoras (un solo as).
  • Usa unique symbol con declare para que ninguna marca colisione entre tipos.
  • Prefiere genericos (Moneda<M>) para marcas reutilizables.
  • Los template literal types para rutas, prefijos, identificadores con formato.
  • Extrae la parte variable con infer cuando necesites parsear el segmento.

Que evitar

  • Crear valores marcados con as fuera del constructor (rompes la invariante).
  • Abusar de marcas en datos simples donde "string" basta.
  • Template literals demasiado abiertos (`${string}${number}`) que no validan nada.
  • Mezclar marcas con herencia de clases: la marca es estructural, no de herencia.

6 · Errores habituales

Mal — usar asi un "brand" sin pasar por el constructor 
type ID = number & { __marca: "ID" };
function f(id: ID): void {}
// f(5); // ✖ el 5 no tiene la marca (bien)
// const fake = { __marca: "ID" } as ID; // ✖ puedes hacerlo, pero...
Bien — constructores unicos 
declare const m: unique symbol;
type ID = number & { readonly [m]: "ID" };
function newId(n: number): ID { return n as ID; } // punto unico
Mal — template literal que no restringe nada 
type Slugg = `${string}`; // equivale a string: no aporta restriccion
Bien — plantilla real con segmento variable 
type Slugg = `slug/${string}`; // obliga al prefijo, string libre despues
Mal — usar la marca en runtime 
// Los tipos no existen en runtime:
const val: EUR = euros(5);
// if ('marca' in val) ... // ✖ la marca es un symbol de tipos, no existe en runtime
Bien — la marca es solo en el tipado 
// La validacion real (n > 0) la haces en el constructor:
function euros(n: number): EUR | null {
  return n > 0 ? (n as EUR) : null;
}

7 · Ejercicio guiado

Queremos una marca UserID que no se pueda confundir con un OrderID.

  1. Declara declare const m: unique symbol;.
  2. Define type UserID = number & { readonly [m]: "USER" }.
  3. Define type OrderID = number & { readonly [m]: "ORDER" }.
  4. Crea funcion orderId(n: number): OrderID.
  5. Comprueba que no puedes pasar un UserID a una funcion que pide OrderID.

Solucion paso a paso:

ejercicio-branded.ts
declare const m: unique symbol;

type UserID = number & { readonly [m]: "USER" };
type OrderID = number & { readonly [m]: "ORDER" };

function orderId(n: number): OrderID { return n as OrderID; }
function pedirById(id: OrderID): void { console.log(id); }

const uid = 3 as UserID; // (constructora de usuario omitida)
const oid = orderId(10);

pedirById(oid);   // ✅
// pedirById(uid); // ✖ UserID no es OrderID

8 · Reto

Reto

Generaliza el concepto con un tipo Marca<T, M> que marque cualquier tipo (Marca<string, "Slug">, Marca<number, "Celsius">). Luego escribe una funcion sumarTemperaturas que solo acepte grados Celsius y devuelva Celsius. No mires la solucion: piensa en la interseccion con una marca symbol tipica.

9 · Resumen

  • Template literals construyen y parsean tipos de string con infer.
  • Branded types: number & { readonly [simbolo]: "..."; } crean identidades nominales.
  • Los constructores o validadores son la unica puerta a crear valores marcados.
  • TypeScript (estructural) no distingue dos numbers; las marcas lo hacen a nivel de tipos (solo compilacion, se borran en el artefacto).

10 · Preguntas frecuentes

¿Los branded types existen en runtime?

No. La marca es un truco de tipos (compilacion). En runtime seguirá siendo un number normal. Por eso la validacion real (rangos, formatos) vive en el constructor/validador.

¿Por que unique symbol?

Porque cada unique symbol es un tipo unico: dos marcas declaradas con nodos let/const distintos no colisionan, y el compilador puede diferenciarlas.

¿Se pueden hacer operaciones aritmeticas sobre un numero marcado?

Si: el numero sigue siendo number (con la marca). El resultado debe volver a pasarse por su marca si quieres mantener la semantica, o quedará como number puro.

¿Los template literals permiten unions grandes?

Si, pero cuidado con la explosion combinatoria: `/x/${"a"|"b"}/${"1"|"2"}` genera 4 rutas. Con unions enormes (decenas de combinaciones) el compilador puede costar. Usalos para dominios pequenos.

¿Cuando es excesivo usar branded types?

Cuando el coste de validacion supera el beneficio: para un prototype simple, para datos sin cruce de dominios, o cuando solo hay un tipo de id. Empieza con ellos cuando tengas cruces reales (usuario, pedido, proyecto).

¿Los branded types funcionan con JSON serializado?

En runtime sos numbers. Para validar en el borde de la API, usa el validador que reconstruye la marca al recibir el dato (parsing + marca). Eso evita que la marca entre "falsa" desde fuera.
