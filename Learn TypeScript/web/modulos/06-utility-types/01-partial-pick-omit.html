Partial, Required, Pick, Omit

Modulo 6 · Utility Types 🕐 30 minutos

1 · Introduccion

Los utility types son transformaciones preconstruidas que TypeScript te da para derivar tipos a partir de otros sin tener que escribirlos a mano. Son los esqueletos de los mapped types del modulo 5, convertidos en herramientas de un solo uso.

Resuelven el problema mas comun del dia a dia: tu modelo de datos no cambia (Usuario), pero los momentos de su vida si — para crear necesitas que todo sea opcional (formulario parcial), para persistir necesitas todo obligatorio, para listas necesitas solo un subconjunto de campos.

Cuando se utilizan
  • Partial: formularios, updates parciales, "puede faltar algo".
  • Required: completion forzada de optional, payloads que llegan por API.
  • Pick: vistas que solo usan una parte del modelo (listas, selectores).
  • Omit: "igual pero sin este campo" (por ejemplo sin id o sin password).

2 · Teoria

La analogia: la plantilla del formulario

Tienes un formulario impreso con tres campos: Nombre, Email, Edad. Dependiendo de la vista, quieres distintas copias de esa misma plantilla:

  • Vista "crear": los campos pueden estar vacios → todos opcionales (Partial).
  • Vista "enviar": todos deben estar llenos → todos obligatorios (Required).
  • Vista "resumen": solo muestro Nombre y Email → solo esas columnas (Pick).
  • Vista "no mostrar el Email" → todo menos Email (Omit).

En lugar de definir cuatro tipos a mano (que se desincronizan cuando el modelo cambia), derivas de uno solo.

Partial <T>

interface Usuario {
  id: number;
  nombre: string;
  email: string;
  activo: boolean;
}

// "El mismo usuario, pero cada propiedad puede faltar".
type UsuarioParcial = Partial<Usuario>;
// { id?: number; nombre?: string; email?: string; activo?: boolean }

// Implementacion interna (mapped type, modulo 5):
// { [P in keyof T]?: T[P] }

Perfecto para un formulario de edicion: el usuario puede enviar solo los campos que cambio.

Required <T>

// Operacion inversa: quita el "?" de todas las propiedades.
type UsuarioCompleto = Required<UsuarioParcial>;
// { id: number; nombre: string; email: string; activo: boolean }

// Internamente: { [P in keyof T]-?: T[P] }   ("-?" elimina el opcional)

Pick <T, K>

// Se queda solo con las claves que digas (K debe estar en keyof T).
type Resumen = Pick<Usuario, "id" | "nombre">;
// { id: number; nombre: string }

// Internamente: { [P in K]: T[P] }

Ideal para construir vistas y tipos DTO sin arrastrar campos que no se usan.

Omit <T, K>

// "Todo menos K". Perfecto para excluir campos sensibles.
type UsuarioSinEmail = Omit<Usuario, "email">;
// { id: number; nombre: string; activo: boolean }

// Omit esta implementado como Pick de TODO excepto K:
// type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;

Pick vs Omit: cuando usar cada uno

  • Pick: conocido el subconjunto exacto de campos que quieres.
  • Omit: conocido el campo (o campos) que quieres excluir; util cuando la lista a quitar es corta.
T = { id, nombre, email, activo } │ Pick<T,"nombre"> ──► { nombre } Omit<T,"email"> ──► { id, nombre, activo }

Componer utility types

// Formulario de edicion: opcional PERO sin id (no puedes cambiar el id).
type EditarUsuario = Partial<Omit<Usuario, "id">>;
// { nombre?: string; email?: string; activo?: boolean }

// La composicion se lee de dentro hacia fuera:
// 1. Omit quita "id"
// 2. Partial hace opcional el resto
Por que los utility types no son magia

Cada uno es un mapped type (o un condicional) que tu podrias escribir a mano (modulo 5, leccion 3). Los utility types lo hacen mas legible, con nombres estandar que todos los developers conocen. Tus tipos derivados quedan auto-sincronizados con el modelo fuente.

3 · Ejemplo minimo

utility-minimo.ts
interface Punto { x: number; y: number; }

const p1: Partial<Punto> = { x: 10 };    // solo x, falta y (ok)
// const p2: Required<Punto> = { x: 10 }; // ✖ falta y
const p3: Pick<Punto, "x"> = { x: 10 };  // solo x, y no existe (ok)
const p4: Omit<Punto, "x"> = { y: 20 };  // solo y

Linea a linea:

  • Partial<Punto>: { x?: number; y?: number }, asignar solo x es valido.
  • Required<Punto>: los dos obligatorios, {x:10} falla.
  • Pick<Punto, "x">: un objeto con una sola clave x.
  • Omit<Punto, "x">: un objeto con y solamente.

4 · Ejemplo real

Un CRUD de usuarios donde cada operacion usa un subtipo distinto derivado del modelo central:

crud-utility.ts
// El modelo fuente: una sola fuente de verdad.
interface Usuario {
  id: number;
  nombre: string;
  email: string;
  activo: boolean;
  creadoEn: Date;
}

// 1) Crear: todo opcional menos el id y la fecha (el sistema los genera).
type CrearUsuario = Omit<Usuario, "id" | "creadoEn">;
// { nombre: string; email: string; activo: boolean }

// 2) Editar: opcional y sin campos inmutables.
type EditarUsuario = Partial<Omit<Usuario, "id" | "creadoEn">>;
// { nombre?: string; email?: string; activo?: boolean }

// 3) Vista de listado: solo los campos que se muestran en la tabla.
type UsuarioLista = Pick<Usuario, "id" | "nombre" | "activo">;

// 4) Forzar datos de interes: email es obligatorio para validar.
type UsuarioConEmail = Required<Pick<Usuario, "email">>;

// Uso en APIs:
async function crear(datos: CrearUsuario): Promise<Usuario> { /* ... */ }
function editar(datos: EditarUsuario): Usuario { /* ... */ }

Decisiones:

  • Todos los tipos derivan de Usuario: si el modelo cambia, las firmas se actualizan solas en las llamadas.
  • Omit<Usuario, "id" | "creadoEn"> acepta varias claves separadas por union.
  • La composicion Partial<Omit<...>> expresa claramente "opcional, pero sin estos campos".
  • No se duplica codigo de tipos; se define la intencion y TypeScript la mantiene.

5 · Buenas practicas

  • Deriva los DTOs y vistas del modelo central; no los redefinas a mano.
  • Usa Pick cuando sepas el conjunto exacto de campos que quieres.
  • Usa Omit cuando quieras excluir pocos campos y el resto te de igual.
  • Componelos: Partial<Omit<T, K>>, Readonly<Pick<...>>, son expresiones idiomaticas.
  • Que el tipo "fuente" sea la interfaz completa; los derivados, siempre en funcion de el.

Que evitar

  • Definir tipos duplicados donde un utility bastaria (rompe la sincronizacion).
  • Omit del revés (con claves que quieres mantener en vez de excluir).
  • Usar any para los derivados: destruye la relacion.
  • Anidar utility types sin entender el orden (lee de dentro hacia fuera).

6 · Errores habituales

Mal — Pick con una clave inexistente 
type Usuario = { id: number; nombre: string };
type Malo = Pick<Usuario, "apellidos">; // ✖ "apellidos" no existe en keyof
Bien — solo claves reales 
type Usuario = { id: number; nombre: string };
type Bueno = Pick<Usuario, "id">; // ✅
Mal — confundir Pick y Omit 
// Queria "quitar el id":
type Res = Pick<Usuario, "nombre">; // ✅ esto ES quitar id, pero...
// Si solo conocia "quitame id" pero no quiero listar todos los demas:
type Res2 = Omit<Usuario, "id">; // más legible cuando son pocas a quitar
Bien — elegir segun lo que conozcas 
type Usuario = { id: number; nombre: string; email: string };
type SinId = Omit<Usuario, "id">; // { nombre; email } ✅
Mal — Required sobre algo que no quieres forzar 
interface Cfg { a?: string; b?: string }
type Obligado = Required<Cfg>; // a y b obligatorias
// No le pidas a Required "quitar solo una" — quita el ? de TODAS
Bien — si solo quieres una, usa composicion 
type SoloA = Required<Pick<Cfg, "a">> // a: string (sin b)

7 · Ejercicio guiado

Retomando el CRUD anterior, vamos a definir una vista de API externa que no debe exponer id.

  1. Define type UsuarioPublico = Omit<Usuario, "id">.
  2. Haz despues type UsuarioPublicoParcial = Partial<Omit<Usuario, "id">>.
  3. Compara: Omit<Usuario, "id"> vs Omit<Usuario, "id" | "email">.
  4. Comprueba que Pick<Usuario, "email"> devuelve solo el email.

Solucion paso a paso:

ejercicio-utility.ts
type UsuarioPublico = Omit<Usuario, "id">;
// { nombre; email; activo; creadoEn }

type UsuarioPublicoParcial = Partial<Omit<Usuario, "id">>;
// { nombre?; email?; activo?; creadoEn? }

type SoloEmail = Pick<Usuario, "email">;
// { email: string }

// Si tambien queremos quitar email a la vez:
type UsuarioClean = Omit<Usuario, "id" | "email">;
// { nombre; activo; creadoEn }

8 · Reto

Reto

Define un tipo EditarConCamposObligatorios<T, K extends keyof T> que sea como Partial<T> pero donde las claves de K sean OBLIGATORIAS. Es decir, para los campos en K se aplica Required y para el resto Partial. Intenta implementarlo con Pick, Omit, Required y Partial antes de mirar nada mas.

9 · Resumen

  • Partial<T>: todo opcional.
  • Required<T>: todo obligatorio (quita el ?).
  • Pick<T, K>: solo las claves de K.
  • Omit<T, K>: todo excepto K.
  • Compone: Partial<Omit<T, "id">> y derivas del modelo central, sin duplicar.

10 · Preguntas frecuentes

¿Por que no usar una interfaz duplicada y quitar un campo?

Porque se desincroniza: si el modelo central cambia, la copia queda obsoleta y el error aparece en runtime o en otro punto. Derivar con utility types mantiene la coherencia en compilacion.

¿Puedo aplicar Partial a un tipo con metodos?

Si. Aunque los metodos se mantienen como opcionales, lo cual rara vez quieres. Para solo los datos, combinelo con Omit<T, keyof Metodos> o restrinja al shape de datos.

¿Omit y Pick sirven para claves numericas?

Si: K extends keyof T puede ser cualquier clave, incluidos indices numericos de arrays y tuplas.

¿Hay diferencias de rendimiento entre derivar y definir a mano?

El rendimiento en compilacion es el mismo orden. En runtime no hay diferencia porque los tipos se borran. La ventaja es mantenibilidad, no velocidad.

¿Por que Omit<T, ...> no funciona con genericos no resueltos?

Porque Omit necesita saber keyof T para excluir; si T es generico sin instanciar, Exclude se queda diferido. Se resuelve cuando se le da un tipo concreto. En enterfaces, se suele resolver directamente.

¿Puedo combinar Omit y Pick para un DTO muy concreto?

Si: type MiDTO = Pick<Omit<Usuario, "password">, "id" | "nombre"> primero quita lo sensible y despues elige lo que expones.
