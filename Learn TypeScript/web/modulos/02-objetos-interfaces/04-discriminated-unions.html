Discriminated unions y literales

Modulo 2 · Objetos e interfaces 🕐 30 minutos

1 · Introduccion

Esta leccion es el corazon de TypeScript. Los tipos literales (valores exactos como tipos), las unions de varias formas de objeto y, sobre todo, las discriminated unions: la combinacion de una union con un campo discriminante que le permite a TypeScript saber exactamente con que variante estas trabajando en cada momento.

Si dominas esto, lees el tipado de las librerias mas famosas y escribes codigo con una seguridad que JavaScript puro solo puede sonar. Muchas lecciones del modulo 4 profundizan en este terreno.

2 · Teoria

Tipos literales

Un tipo literal es un valor concreto usado como tipo:

let estado: "activo" = "activo";   // solo puede valer "activo"
// estado = "pausado";             // ✖ TS2322: "pausado" no es "activo"

Los literales no son solo strings: 42 es un tipo literal numerico, true un literal booleano. Combinados con unions forman conjuntos finitos: 

type Nivel = "bajo" | "medio" | "alto"; // 3 valores posibles
type Port = 3000 | 3001 | 3002;          // 3 numeros posibles
type Binario = 0 | 1;                    // 2 valores

Recuerda de la leccion 1: const puerto = 3000 ya tiene el tipo literal 3000.

Union de formas de objeto

type Cargando = { estado: "cargando" };
type Exito = { estado: "exito"; datos: string[] };
type Error = { estado: "error"; mensaje: string };

// La union: el valor puede ser cualquiera de las tres.
type EstadoPeticion = Cargando | Exito | Error;

Un union type acepta valores que cumplan al menos una de las variantes. Con objetos, el acceso a propiedades comunes esta permitido; el acceso a propiedades de una sola variante da error hasta que el compilador sepa cual es.

El discriminante

La clave: cada variante tiene un campo literal distinto con el mismo nombre (estado). Ese campo es el discriminante. Cuando comparamos el valor del discriminante, TypeScript estrecha la union a la variante correspondiente: 

function describe(peticion: EstadoPeticion): string {
  if (peticion.estado === "exito") {
    // AQUI peticion ES Exito: tiene "datos".
    return `Listo, ${peticion.datos.length} elementos`;
  }
  // Si no es "exito"... podria ser cargando o error.
  return peticion.estado; // "cargando" | "error"
}
EstadoPeticion │ ├── { estado: "cargando" } ← cargando ├── { estado: "exito", datos } ← exito └── { estado: "error", mensaje } ← error ▲ comparar "estado" elimina las demas ramas (narrowing)

El discriminante suele llamarse type, kind, estado o tipo. No importa el nombre; importa que sea un literal distinto por variante.

Por que es tan util

El patron "peticion que puede ser exito/error/cargando" es la vida real: lo mismo en APIs, UI, formularios, sockets. Con la discriminated union, TypeScript te obliga a tratar cada caso y actualiza tus ramas cuando añades uno nuevo. El código "se cierra solo".

Switch exhaustivo

function mensajeDe(p: EstadoPeticion): string {
  switch (p.estado) {
    case "cargando": return "Cargando...";
    case "exito":    return `OK (${p.datos.length})`;
    case "error":    return `Error: ${p.mensaje}`;
  }
}
// Si añadieramos { estado: "cancelado" } a la union, esta funcion
// dejaría de cubrir todos los casos → con never lo hacemos fallar.

En el modulo 4 completamos la tecnica con el caso default que asigna a never, convirtiendo "olvidar un caso" en un error de compilacion.

3 · Ejemplo minimo

union-minima.ts
// Literales + union de objetos con discriminante "tipo".
type Circulo = { tipo: "circulo"; radio: number };
type Rectangulo = { tipo: "rectangulo"; ancho: number; alto: number };

type Forma = Circulo | Rectangulo;

// La funcion estrecha por el discriminante.
function area(f: Forma): number {
  if (f.tipo === "circulo") {
    // f es Circulo: solo "radio" disponible.
    return Math.PI * f.radio ** 2;
  }
  // f es Rectangulo.
  return f.ancho * f.alto;
}

console.log(area({ tipo: "circulo", radio: 2 }));     // 12.566...
console.log(area({ tipo: "rectangulo", ancho: 3, alto: 4 })); // 12

4 · Ejemplo real

Un feed de notificaciones con varios tipos. Cada variante lleva sus propios datos:

notificaciones.ts
// Discriminante "tipo" con un literal distinto en cada variante.
type Notificacion =
  | { tipo: "mensaje"; de: string; texto: string }
  | { tipo: "alerta"; nivel: "info" | "warning" | "critico"; asunto: string }
  | { tipo: "sistema"; version: string };

// La UI puede renderizar cada una con su plantilla.
function renderizar(n: Notificacion): string {
  switch (n.tipo) {
    case "mensaje":
      // aqui n es la variante mensaje: "de" y "texto" disponibles.
      return `💬 ${n.de}: ${n.texto}`;

    case "alerta":
      // aqui n es la variante alerta: "nivel" y "asunto".
      return `⚠️ [${n.nivel}] ${n.asunto}`;

    case "sistema":
      // aqui n es la variante sistema: "version".
      return `⚙️ Nueva version ${n.version} disponible`;
  }
}

console.log(renderizar({ tipo: "mensaje", de: "Ada", texto: "Hola" }));
console.log(renderizar({ tipo: "alerta", nivel: "critico", asunto: "Servidor caido" }));
console.log(renderizar({ tipo: "sistema", version: "2.0.1" }));

Decisiones:

  • Las tres variantes viven en el mismo type: el renderizado conoce todas las formas y el autocompletado sugiere cada campo segun la rama.
  • El switch por tipo es la "maquina de estados" del tipo: cada case garantiza la forma exacta.
  • Añadir un nuevo tipo ({ tipo: "evento"; ... }) rompe el switch hasta que lo trates: el sistema te guia a completar.

5 · Buenas practicas

  • Usa el mismo nombre de discriminante en todas las variantes y literal distinto en cada una.
  • Prefiere discriminated unions a "objeto con opcional everywhere": son mas seguras y mas legibles.
  • Convierte los campos que solo aplican a ciertos casos en variantes separadas, no en opcionales.
  • Mantén el switch exhaustivo (con never en default) para que el compilador avise al crecer la union.
  • Nombra las variantes de forma narrativa: Mensaje, Alerta...

Que evitar

  • Discriminantes con valores no literales (dos variantes con el mismo tipo: string rompen el estrechado).
  • Duplicar el campo discriminante con valores iguales.
  • Mezclar discriminated unions con any: se pierde toda la magia.

6 · Errores habituales

Mal — discriminante no literal 
type A = { tipo: string; x: number };
type B = { tipo: string; y: string };  // ambos "string" → no se estrecha
Bien — literal unico por variante 
type A = { tipo: "a"; x: number };
type B = { tipo: "b"; y: string };     // "a" | "b" → estrecha perfecto
Mal — acceder a la propiedad de una variante sin estrechar 
function ver(f: Forma): number {
  return f.radio; // ✖ error: la propiedad "radio" no existe en Rectangulo
}
Bien — estrechar por el discriminante primero 
function ver(f: Forma): number {
  if (f.tipo === "circulo") return f.radio;   // ✅ solo en esa rama
  return f.alto;
}

Por que estan mal: sin literal unico el compilador no puede eliminar variantes, y sin estrechar el codigo pretende usar datos que podrian no existir. Ambas son las causas tipicas de los "undefined" en runtime.

9 · Resumen

  • Tipos literales: un valor exacto como tipo ("exito", 42).
  • Union de objetos: el valor cumple una de las variantes.
  • Discriminated union: union + campo literal unico (discriminante) por variante.
  • Con el discriminante, TypeScript estrecha y te da las propiedades de la variante exacta.
  • El switch exhaustivo (+ never en el default) protege cuando la union crece.

10 · Preguntas frecuentes

¿Puedo usar el discriminante con numeros?

Si. Un discriminante numerico (1 | 2 | 3) tambien estrecha. Aunque para legibilidad en logs, los strings son mas recomendables.

¿Que pasa si dos variantes comparten el mismo valor literal en el discriminante?

TypeScript no puede distinguirlas y el estrechado no funciona bien. Cada variante debe tener un discriminante UNICO.

¿La discriminated union tiene coste en runtime?

No. Es puro tipado: en runtime tus objetos son exactamente los que ya escribes. Todo el poder desaparece al compilar a JS.

¿Puedo anidar discriminated unions?

Si. Variantes pueden contener otras uniones con su propio discriminante. Es comun en protocolos y ASTs. TypeScript las estrecha por niveles.

¿Cuando usar discriminated union y cuando opcionales?

Cuando hay 2+ "modos" excluyentes → discriminated union. Cuando solo alguna propiedad puntual puede faltar → opcional. La union es la regla profesional para estados.
