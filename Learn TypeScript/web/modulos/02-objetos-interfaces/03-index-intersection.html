Index signatures e intersection

Modulo 2 · Objetos e interfaces 🕐 30 minutos

1 · Introduccion

Hasta ahora las interfaces listaban claves fijas. Pero el mundo real tiene objetos "abiertos": diccionarios, mapas con claves dinamicas, caches... Para eso existen las index signatures ([clave: string]: Valor). Y cuando necesitas "una forma Y otra forma" al mismo tiempo, llegan los intersection types con &.

Son dos herramientas que aparecen constantemente en librerias y en datos tipo mapa. Tambien es donde TypeScript muestra sus limites: hay que usarlas con criterio para no perder seguridad.

2 · Teoria

Index signature: claves dinamicas

Permite declarar que un objeto puede tener CUALQUIER clave (del tipo indicado) apuntando a un valor:

// Un diccionario: cualquier palabra clave → numero (recuento).
interface Contador {
  [palabra: string]: number;
}

const visitas: Contador = {
  inicio: 120,
  producto: 45,
  // cualquier clave string es valida, siempre que el valor sea number
};

console.log(visitas.inicio);  // 120
console.log(visitas["carrito"]); // undefined (no existe) — cuidado

La sintaxis [nombre: string]: Valor declara que TODAS las claves son del tipo dado y sus valores de Valor. Puede haber claves de string, number o symbol.

El precio de la index signature

Acepta "cualquier clave", asi que visitas.carrito compila aunque no exista, y devuelve undefined en runtime. Es una herramienta para datos con estructura abierta, no para objetos con claves conocidas. Para claves conocidas, lista las propiedades.

Record<K, V>: la alternativa comoda

Record es un utility type de TypeScript (modulo 6): Record<K, V> es "objeto con claves de tipo K y valores V":

type Dias = "L" | "M" | "X";
const horario: Record<Dias, number> = { L: 8, M: 8, X: 7 };
// horario.L === 8

Si usas union de claves en K, Record exige que todas existan (mas seguro que la index signature). La regla: si las claves son conocidas y finitas → Record o lista de propiedades; si son desconocidas → index signature.

Index signatures y el "undefined"

Con strict, acceder a una clave que puede no existir da number | undefined (con noUncheckedIndexedAccess activado):

const visitas: Record<string, number> = {};
// con noUncheckedIndexedAccess:
// visitas.inicio es number | undefined → hay que comprobar
if (visitas.inicio !== undefined) {
  console.log(visitas.inicio);
}

Intersection types con &

La interseccion une dos tipos: el resultado tiene las propiedades de ambos:

interface ConId { id: number }
interface ConNombre { nombre: string }

type Entidad = ConId & ConNombre; // tiene id Y nombre

const e: Entidad = { id: 1, nombre: "Ada" }; // ✅
ConId = { id } ConNombre = { nombre } ConId & ConNombre = { id, nombre } (interseccion de propiedades)

La interseccion es el equivalente type de extends. Se usa mucho para combinar props de componentes, opciones de configuracion, etc. Como vimos, con claves en conflicto puede producir never: usala con claves distintas o tipos compatibles.

Mix: index signature + propiedades fijas

interface Config {
  nombre: string;               // propiedad fija tipada
  [clave: string]: string;      // resto: claves string → string
}
// Correcto: "nombre" es string y coincide con la firma.

Cuidado: las propiedades fijas deben ser compatibles con la firma. Si declaras [clave: string]: number y luego nombre: string, el compilador se queja (string no es number).

3 · Ejemplo minimo

index-minimo.ts
// Index signature para un diccionario generico de numeros.
type Contador = { [clave: string]: number };

const recuento: Contador = { a: 1, b: 2 };
recuento.c = 3;   // ✅ nueva clave permitida en runtime y en tipos

// Intersection: junta las dos formas.
type ConId = { id: number };
type ConEmail = { email: string };
type UsuarioBasico = ConId & ConEmail;

const u: UsuarioBasico = { id: 1, email: "a@d.ts" }; // ✅ ambas props

4 · Ejemplo real

Un sistema de cache de peticiones con claves dinamicas y metadatos fijos, y la combinacion de configuraciones:

cache.ts
// La cache: clave = URL (string) → respuesta (string).
// Index signature porque las claves llegan en runtime y son infinitas.
type CacheRespuestas = Record<string, string>;

const cache: CacheRespuestas = {};
cache["/api/usuarios"] = JSON.stringify([{ id: 1, nombre: "Ada" }]);

function obtener(url: string): string | undefined {
  // con noUncheckedIndexedAccess, el acceso puede ser undefined.
  return cache[url];
}

// ------------------ Intersection para configuracion ------------------
interface Red { protocolo: "http" | "https"; }
interface Seguridad { apikey: string; }

// La config final combina ambas.
type ConfigRed = Red & Seguridad;

const configuracion: ConfigRed = {
  protocolo: "https",
  apikey: "secreto-solo-en-variables-de-entorno",
};

// Interesante: las props de la interseccion se ven juntas.
function conectar(cfg: ConfigRed): string {
  return `${cfg.protocolo}://${cfg.apikey}`;
}
console.log(conectar(configuracion));

Decisiones:

  • Record<string, string> para la cache: claves desconocidas al tipar, valores homogeneos.
  • El acceso devuelve string | undefined: el codigo decide que hacer cuando la clave no existe.
  • Red & Seguridad compone dos contratos separados y reutilizables; cualquier cambio en Red se refleja en ConfigRed.

5 · Buenas practicas

  • Usa Record con claves finitas (uniones) para exigir todas; index signature solo para claves desconocidas.
  • Activa noUncheckedIndexedAccess en proyectos estrictos: te obliga a manejar el "no existe".
  • Con intersecciones, manten las claves distintas o tipos compatibles para evitar never.
  • Preferí Map (el objeto nativo) cuando necesites claves de tipos no string, o borrado frecuente.
  • Documenta cuando usas index signatures: son la unica puerta a "undefined silencioso".

Que evitar

  • Index signatures en objetos con claves conocidas: pierdes el autocompletado y la comprobacion de errores tipograficos.
  • Intersections con la misma clave con tipos incompatibles.
  • Creer que un objeto con index signature "valida" que la clave exista: no existe validacion de presencia.

6 · Errores habituales

Mal — index signature para claves conocidas 
interface Usuario {
  [clave: string]: string; // cualquiera
}
// ahora "email" tipa string pero "edad" tambien... y pierdes nombres
Bien — claves fijas con propiedades 
interface Usuario {
  email: string;
  edad: number;
}
Mal — propiedad fija incompatible con la firma 
interface Malo {
  edad: number;            // ✖ number no es string
  [clave: string]: string;
}
Bien — firma compatible (o union de valores) 
interface Bien {
  edad: number;
  [clave: string]: number | string; // firma incluye ambos
}
Mal — interseccion con clave en conflicto 
type A = { v: number };
type B = { v: string };
type AB = A & B; // v: number & string → never. Imposible de construir.
Bien — claves distintas o extends 
type A = { a: number };
type B = { b: string };
type AB = A & B; // a: number, b: string → ✅

8 · Reto

Reto

Escribe una funcion agruparPor(lista, clave) que agrupe un array de objetos por el valor de una propiedad dada, devolviendo un Record<string, Objeto[]>. Tipala con genericos (si te atreves con <T extends object>) o con un tipo concreto. La funcion deberia soportar agrupar Producto[] por categoria.

9 · Resumen

  • Index signature: [clave: string]: Valor para objetos con claves dinamicas.
  • Record<K, V>: la variante con claves tipadas, ideal para uniones finitas.
  • Acceso a claves puede dar undefined: activa noUncheckedIndexedAccess.
  • Intersection &: combina dos tipos (propiedades de ambos).
  • Evita firma con propiedades fijas incompatibles, y evitá intersecciones con claves en conflicto (never).

10 · Preguntas frecuentes

¿Cuando index signature vs Map?

Index signature/Record: datos planos JSON, caches por string, tablas de config. Map: si necesitas claves no-string (objetos, numeros), borrado, o tamaños grandes con inserciones/borrados frecuentes.

¿Record<string, X> e index signature son identicos?

Practicamente si: Record<string, X> se expande a { [clave: string]: X }. La ventaja de Record es que admite unions de claves finitas de forma natural.

¿Por que a veces accedo a una index y el tipo es "number | undefined"?

Con noUncheckedIndexedAccess, el acceso a una clave que podria no existir devuelve el valor | undefined. Es una mejora de seguridad: te obliga a comprobar.

¿Como compongo mas de dos interfaces?

Encadenando: type Total = A & B & C o con interfaces interface C extends A, B {}. La interseccion es asociativa y conmutativa en tipos.

¿Que pasa con las propiedades opcionales en intersecciones?

Se combinan bien: { a?: number } & { b: string } da { a?: number; b: string }. Los conflictos aparecen cuando una clave es obligatoria y la otra opcional con tipo distinto.
