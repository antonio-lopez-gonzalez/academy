Flujo de trabajo

Modulo 0 · Preparacion 🕐 25 minutos

1 · Introduccion

Ya tienes TypeScript instalado. Ahora aprendemos como se trabaja con el cada dia: el bucle editar → comprobar → arreglar, el famoso --watch, como leer un error de compilacion con su codigo (TS2345, TS2304...) y como integrar todo con VSCode para que el editor sea tu aliado, no tu verdugo.

Este es el momento en que la herramienta deja de ser "algo que se instala" y pasa a ser parte de tu ritmo de trabajo. Al final podras desarrollar sin miedo a romper nada en silencio.

2 · Teoria

El bucle TypeScript

1. EDITA ──► 2. COMPRUEBA ──► 3. CORRE / CONTESTA │ │ (tsc o el │ └────────4. ARREGLA ◄─ editor) │ ▲ ▼ └──── errores de tipo ◄─┘

Todo el flujo se puede resumir en una frase: TypeScript no te deja avanzar hasta que tienes razon.

Dos formas de comprobar

  • Manual: pnpm exec tsc --noEmit en un proyecto Vite, o pnpm exec tsc en un proyecto que emite JS.
  • Automatica: pnpm exec tsc --watch (o tsc -w). Vigila tus ficheros y re-compila al guardar. En Vite, el dev server (relacionado en el build) ya lo hace.

Como leer un error de TypeScript

Un error tsc sigue una plantilla fija:

terminalerror
src/usuario.ts:12:20 - error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'. la columna 20 señala el argumento culpable

Anatomia:

ParteSignificado
src/usuario.ts:12:20Fichero, linea 12, columna 20.
error TS2345Codigo unico del error (buscalo en Google/official docs).
MensajeExplica el problema concreto.

La clave profesional: lee como si te hablara un poli que ya sabe la respuesta. "Argument of type X is not assignable to parameter of type Y" se traduce como: "le esta entrando una X donde yo esperaba una Y".

VSCode + TypeScript

VSCode usa el propio compilador de TypeScript como motor de inteligencias: el subrayado rojo, el autocompletado, el F2 para renombrar y el menu de refactor (CTRL/CMD+.). Para cambiar la version de TS que usan un proyecto concreto, usa la barra de estado → "Use Workspace Version".

3 · Ejemplo minimo

Reproducimos el ciclo completo con un fichero suelto:

flujo.ts
const anios: number = 30;

// Error intencional para ver el bucle de trabajo.
// const incremental = anios + "invitaciones"; // Argument of type 'string'
                                               // is not assignable to 'number'

En terminal

pnpm exec tsc flujo.ts --noEmit          # 0 errores → OK
pnpm exec tsc flujo.ts --noEmit --watch   # se queda vigilando cambios

En --noEmit, tsc no genera flujo.js: se limita a comprobar tipos. Al descomentar la linea problematica, el watch escribe el error al guardar el fichero.

4 · Ejemplo real

Un flujo realista de fix de un bug tipico de JavaScript migrado a TypeScript:

JavaScript original — el bug vive innocentemente 
function totalPedidos(pedidos) {
  return pedidos.reduce((suma, pedido) => {
    return suma + pedido.subtotal;
  }, 0);
}
// Nadie avisa de que un pedido puede no tener "subtotal" o que
// "subtotal" puede llegarnos como string desde la API.
TypeScript — el mismo bug se hace visible 
// interface declara la forma esperada del dato.
interface Pedido {
  id: number;           // identificador numerico del pedido
  subtotal: number;     // subtotal en euros
}

// Pedido[]: array de objetos que cumplen la forma Pedido.
function totalPedidos(pedidos: Pedido[]): number {
  return pedidos.reduce((suma, pedido) => suma + pedido.subtotal, 0);
}

// En el punto de entrada del sistema (por ejemplo, al recibir datos
// de la API), INTERFAZ MUY MUCHO MAS ESTRICTA:
const datosTramposos: Pedido[] = [{ id: 1, subtotal: "9.99" }]; // ✖ error TS2322
// string no es asignable a number → el bug aparece en desarrollo, no en produccion.

Por que es tan util este flujo: el error aparece en el punto donde el dato entra (el "limite" con el mundo exterior), y no en un punto oscuro de la funcion o de la UI. Los limites son lo mas rentable de tipar.

De donde venia el dato

El valor "9.99" este viene de un JSON de una API. Al tipar la variable que lo recibe, TypeScript nos obliga a decidir donde se convierte a numero. Decidir donde ocurre la conversion es precision; dejarlo flotando es el clasico bug "suma de cadenas".

5 · Buenas practicas

  • Compila con frecuencia: tsc --noEmit dos veces por hora te ahorra depuraciones nocturnas.
  • Usa --watch en desarrollo para tener feedback continuo sin gestos manuales.
  • Aprende a leer el codigo TSxxxx: es la "voz de la maquina"; con 6-7 codigos ya lees casi todo.
  • Configura VSCode: extension typescript de ms (la integra por defecto), formato Prettier opcional, y "use workspace version".
  • Comenta los limites del sistema: cuando un dato cruza una API o un JSON, tipalo explicitamente.

Que evitar

  • Ignorar un error "porque ya se que funciona": cada warning es una decision que difieres.
  • Convertir el código a any para silenciar un error en vez de entender el tipo esperado.
  • Compilar JS antes de revisar tipos (build con errores de tipos = tiempo perdido).

6 · Errores habituales

Mal — ignorar el subrayado rojo del editor 
const n: number = "texto";  // ✖ error visible en el editor
console.log(n.toFixed(2));   // en runtime, toFixed no existe en string
Bien — dejar que el compilador decida el tipo 
const n = 5;          // inferido: number (no necesita anotacion)
console.log(n.toFixed(2)); // "5.00"
Mal — compilar con watch pero sin ver la salida

El watch escribe en la terminal; si la ocultas, es como apagar el subtitulo del error.

Bien — salida visible + atajos 
pnpm exec tsc --watch        # ver salida en una terminal dedicada
# o abre la "Terminal del problema" en VSCode (panel PROBLEMAS)

Por que estan mal: un error visible pero ignorado es un bug confirmado que esperara en produccion; la mayoria de estos casos TypeScript los desambiguaba en una linea.

7 · Ejercicio guiado

Vamos a reproducir el ciclo completo con un mini-proyecto:

  1. Crea pedidos.ts con la interface Pedido y totalPedidos del ejemplo real.
  2. Compila: pnpm exec tsc pedidos.ts --noEmit → debe decir que no hay errores.
  3. Introduce un pedido con subtotal: "x" y mira el error TS2322. Lee el mensaje e identifica fichero, linea y columna.
  4. Corrige al tipo correcto y verifica que compila otra vez.

8 · Reto

Reto

Crea una funcion que reciba un string con el contenido de un JSON de un producto (ejemplo: '{"nombre":"Tecla","precio":1.5}'), la valide contra una interface Producto usando JSON.parse y devuelva la suma del precio. La trampa: JSON.parse devuelve any. Convertirlo de forma SEGURA al tipo deseado y haz fallar el programa (con un error de tipos o una validacion manual) si el JSON no cumple la forma.

9 · Resumen

  • El flujo es editar → comprobar → correr, con tsc --noEmit y --watch.
  • Lee los errores con su anatomía: fichero:linea:col - TSxxxx - mensaje.
  • Tipar los limites del sistema (API, JSON, variables recibidas) es donde mas valor tiene.
  • VSCode usa el propio compilador: subrayado, autocompletar, renombrar con F2.
  • Nunca silencies errores con any: entiende la expectativa, no la evites.

10 · Preguntas frecuentes

¿Cada cuanto deberia compilar?

Con --watch no lo piensas: el error aparece al guardar. Sin watch, compila tras cada change logico (no por cada linea).

¿Que diferencia hay entre tsc --noEmit y tsc normal?

--noEmit solo comprueba tipos (no genera JS). El normal emite .js. Para revisar tipos en cualquier proyecto usa siempre --noEmit si ya tienes otra herramienta que emite (Vite, esbuild).

¿Por que VSCode marca un error que tsc no marca (o al reves)?

VSCode usa la version de TS del proyecto ("Use Workspace Version"). Si difieren de la global, veras diferencias. Fija la version en package.json y activa siempre workspace version.

¿Que hago si el error TSxxxx no me dice nada?

Busca "typescript TS2345" en la doc oficial. Casi siempre es un fallo de asignabilidad: el dato real no cumple el contrato.

¿Puedo usar Node mismo sin build para ejecutar TS?

Si, con node --experimental-strip-types fichero.ts (Node 22.6+). Para el curso usaremos tsc y los buenos motores de build, pero saberlo ayuda en prototipos rapidos.
