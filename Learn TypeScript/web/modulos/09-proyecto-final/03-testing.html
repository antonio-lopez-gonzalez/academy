Testing con Vitest tipado

Modulo 9 · Proyecto final 🕐 40 minutos Proyecto

1 · Introduccion

Los tests protegen el comportamiento de tu CRUD frente a cambios futuros. Con Vitest (el corredor de tests nativo de Vite) escribes tests en TypeScript puro que comprueban las funciones de dominio y el almacen de datos, todo tipado.

El problema que resuelve: sin tests, un cambio en el CRUD puede romper una regla silenciosamente y nadie se da cuenta hasta produccion. Con tests, cada funcion pura se verifica en cada cambio; y al ser funciones puras y tipadas, testearlas es directo.

Cuando se utiliza
  • Funciones puras del dominio (CRUD, filtros, calculos).
  • Almacen de datos (mock de localStorage).
  • Regresiones tras refactors.
  • Comprobacion de que los tipos derivados funcionan como esperas.

2 · Teoria

La analogia: el banco de pruebas

Antes de enviar un coche a la carretera, la fabrica lo mete en un banco de pruebas: acelera, frena, gira mil veces, y si algo falla, no sale. Nuestros tests son ese banco: cada funcion del CRUD pasa por escenarios controlados. Si algo se rompe, no se "despliega".

Configurar Vitest

pnpm add -D vitest

// package.json scripts
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  }
}

Vitest reutiliza vite.config.ts; no necesita config extra para TypeScript (transpila con esbuild). Los tipos de los tests van en archivos .test.ts.

La API de Vitest: describe/it/expect

import { describe, it, expect } from "vitest";
import { crearTarea } from "../domain/operaciones";

describe("crearTarea", () => {
  it("crea una tarea pendiente con id propio", () => {
    const tarea = crearTarea({ titulo: "Comprar pan" });

    expect(tarea.titulo).toBe("Comprar pan");
    expect(tarea.estado).toBe("pendiente");
    expect(tarea.id).toMatch(/^[0-9a-f-]{36}$/); // formato UUID
  });
});
  • describe: agrupa tests de una unidad.
  • it: un caso concreto. expect: las aserciones.
  • Los tests son TS: el tipado del dominio esta presente.

Testear el CRUD (funciones puras)

import { describe, it, expect } from "vitest";
import {
  crearTarea,
  actualizarTarea,
  eliminarTarea,
  porEstado,
} from "../domain/operaciones";

describe("CRUD de tareas", () => {
  const t1 = crearTarea({ titulo: "A" });
  const t2 = crearTarea({ titulo: "B", descripcion: "detalle" });
  const base = [t1, t2];

  it("actualiza solo la tarea con el id indicado", () => {
    const resultado = actualizarTarea(base, t1.id, { estado: "completada" });

    expect(resultado).toHaveLength(2);
    expect(resultado[0].estado).toBe("completada");
    expect(resultado[1].estado).toBe("pendiente"); // la otra intacta
  });

  it("no muta el array original (inmutabilidad)", () => {
    const antes = JSON.stringify(base);
    actualizarTarea(base, t1.id, { titulo: "Z" });
    eliminarTarea(base, t2.id);
    expect(JSON.stringify(base)).toBe(antes);
  });

  it("borra por id y filtra por estado", () => {
    const sinT2 = eliminarTarea(base, t2.id);
    expect(sinT2).toHaveLength(1);

    const completadas = actualizarTarea(base, t1.id, { estado: "completada" });
    expect(porEstado(completadas, "completada")).toHaveLength(1);
    expect(porEstado(completadas, "completada")[0].id).toBe(t1.id);
  });
});

Mock de localStorage

En Vitest (entorno node), localStorage no existe. Lo simulamos con un mock simple:

// tests/setup.ts — mock del localStorage para el entorno de Node.
const store = new Map<string, string>();

(globalThis as any).localStorage = {
  getItem: (k: string) => store.get(k) ?? null,
  setItem: (k: string, v: string) => { store.set(k, v); },
  removeItem: (k: string) => { store.delete(k); },
};

// vite.config.ts — añade el setup:
export default defineConfig({
  plugins: [react()],
  test: {
    setupFiles: ["./tests/setup.ts"],
  },
});

Testear el almacen

import { beforeEach, describe, it, expect } from "vitest";
import { guardarTareas, leerTareas } from "../data/tareasStore";
import { crearTarea } from "../domain/operaciones";

describe("tareasStore", () => {
  beforeEach(() => localStorage.clear());

  it("guarda y recupera tareas de localStorage", () => {
    const tarea = crearTarea({ titulo: "Recuperar" });
    guardarTareas([tarea]);

    const leidas = leerTareas();
    expect(leidas).toHaveLength(1);
    expect(leidas[0].titulo).toBe("Recuperar");
  });

  it("devuelve array vacio si no hay nada", () => {
    expect(leerTareas()).toEqual([]);
  });
});

Comprobar tipos en los tests

Vitest no comprueba tipos (eso lo hace tsc). Pero puedes verificar que una inferencia es la esperada con aserciones de tipos manuales:

// Asercion de tipos: solo compila si la igualdad es correcta.
type Expect<T extends true> = T;
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;

const resultado = leerTareas(); // inferido: Tarea[]
const chequeo: Expect<Equal<typeof resultado, Tarea[]>> = true;
Por que tsc y vitest son complementarios

tsc --noEmit valida los tipos en todo el proyecto; Vitest valida el comportamiento runtime. Un test puede pasar aunque el tipo este mal inferido, y viceversa. Por eso el build usa tsc -b y los tests usan vitest run: dos redes distintas.

3 · Ejemplo minimo

__tests__/contador.test.ts
import { describe, it, expect } from "vitest";

// La funcion que vamos a testear.
function incrementar(n: number, pasos = 1): number {
  return n + pasos;
}

describe("incrementar", () => {
  it("incrementa en 1 por defecto", () => {
    expect(incrementar(0)).toBe(1);
  });

  it("incrementa en el numero de pasos", () => {
    expect(incrementar(0, 5)).toBe(5);
  });
});

Linea a linea:

  • Tests en TypeScript con tipos: n: number.
  • describe agrupa, it cada caso, expect las aserciones.
  • pnpm test ejecuta la suite y da el reporte.

4 · Ejemplo real

La suite de tests del proyecto final: CRUD, filtros y almacen, todo tipado.

src/__tests__/operaciones.test.ts
import { describe, it, expect } from "vitest";
import {
  crearTarea,
  actualizarTarea,
  eliminarTarea,
  aplicarFiltro,
} from "../domain/operaciones";
import type { Tarea } from "../domain/modelo";

function construir(): Tarea[] {
  const a = crearTarea({ titulo: "Backlog" });
  const b = crearTarea({ titulo: "En progreso" });
  const c = crearTarea({ titulo: "Hecho" });
  const enProgreso = actualizarTarea([a, b, c], b.id, { estado: "en-progreso" });
  const completado = actualizarTarea(enProgreso, c.id, { estado: "completada" });
  return completado;
}

describe("operaciones del dominio", () => {
  it("crea tareas con ids unicos", () => {
    const [x, y] = [crearTarea({ titulo: "X" }), crearTarea({ titulo: "Y" })];
    expect(x.id).not.toBe(y.id);
  });

  it("aplica el filtro correctamente", () => {
    const tareas = construir();
    expect(aplicarFiltro(tareas, "pendientes")).toHaveLength(1);
    expect(aplicarFiltro(tareas, "completadas")).toHaveLength(1);
    expect(aplicarFiltro(tareas, "todas")).toHaveLength(3);
  });

  it("actualiza respetando la inmutabilidad", () => {
    const tareas = construir();
    const antes = JSON.stringify(tareas);
    const modificadas = actualizarTarea(tareas, tareas[0].id, { titulo: "Cambiado" });
    expect(JSON.stringify(tareas)).toBe(antes);
    expect(modificadas[0].titulo).toBe("Cambiado");
  });

  it("elimina por id", () => {
    const tareas = construir();
    const sinPrimera = eliminarTarea(tareas, tareas[0].id);
    expect(sinPrimera.find((t) => t.id === tareas[0].id)).toBeUndefined();
  });
});

Decisiones:

  • Los tests usan funciones puras, no la UI: rapidos y deterministicos.
  • Los escenarios se construyen con las mismas funciones que la app (DRY incluso en tests).
  • La inmutabilidad se verifica comparando el JSON antes y despues.
  • Vitest corre en Node: no hay que levantar el navegador.

5 · Buenas practicas

  • Testea funciones puras del dominio (CRUD, filtros) antes que componentes.
  • Mockea el limite (localStorage) con un setup limpio y beforeEach.
  • Una asercion fuerte por caso: legible y diagnostica el fallo rapido.
  • Usa vitest run en CI y vitest (watch) en local.
  • Complementa con tsc --noEmit: tipos y comportamiento son dos redes distintas.

Que evitar

  • Testear implementacion (que funcion interna se llamo) en vez de comportamiento.
  • Depender del orden de los tests: cada test debe ser autonomo.
  • Snapshots gigantes que cambian por ruido de la UI.
  • Olvidar el beforeEach que limpia el estado entre tests.

6 · Errores habituales

Mal — testear la implementacion en vez del comportamiento 
it("usa spread para crear", () => {
  const t = crearTarea({ titulo: "x" });
  expect(JSON.stringify(t)).toContain("titulo"); // ✖ detalles internos
});
Bien — comportamiento real 
it("crea una tarea pendiente", () => {
  const t = crearTarea({ titulo: "x" });
  expect(t.estado).toBe("pendiente"); // ✅
});
Mal — estado compartido entre tests 
let base: Tarea[]; // ✖ puede contaminar el siguiente test
Bien — construir y limpiar por test 
beforeEach(() => localStorage.clear()); // ✅ aislamiento
Mal — no limpiar localStorage 
it("guarda tareas", () => {
  guardarTareas([x]);   // ✓ pasa
});
it("devuelve vacio", () => {
  expect(leerTareas()).toEqual([]); // ✖ hereda lo guardado antes
});
Bien — setup limpio 
beforeEach(() => localStorage.clear()); // ✅ estado limpio cada test

7 · Ejercicio guiado

Vamos a testear la funcion contarPendientes del dominio.

  1. Escribe src/__tests__/dominio.test.ts con describe/it/expect.
  2. Construye un array con crearTarea y estados variados.
  3. Comprueba que contarPendientes da el numero correcto.
  4. Anade un caso de array vacio.

Solucion paso a paso:

src/__tests__/dominio.test.ts
import { describe, it, expect } from "vitest";
import { crearTarea, actualizarTarea, contarPendientes } from "../domain/operaciones";

describe("contarPendientes", () => {
  it("cuenta solo las pendientes", () => {
    const t1 = crearTarea({ titulo: "A" });
    const t2 = crearTarea({ titulo: "B" });
    const t3 = crearTarea({ titulo: "C" });

    const conEstados = actualizarTarea([t1, t2, t3], t2.id, { estado: "en-progreso" });
    const final = actualizarTarea(conEstados, t3.id, { estado: "completada" });

    expect(contarPendientes(final)).toBe(1);
  });

  it("devuelve 0 para un array vacio", () => {
    expect(contarPendientes([])).toBe(0);
  });
});

Reto

9 · Resumen

  • Vitest corre tests de TypeScript en Node, con describe/it/expect.
  • Testea funciones puras del dominio: rapido, deterministico, legible.
  • Mockea el limite (localStorage) y limpia con beforeEach.
  • Cada test es autonomo y valida comportamiento, no implementacion.
  • Complementa con tsc --noEmit y ejecuta pnpm test en CI.

10 · Preguntas frecuentes

¿Vitest necesita config special para TypeScript?

No: transpila con esbuild automaticamente. Si quieres coverage, instala @vitest/coverage-v8. Los tipos se validan aparte con tsc.

¿Testeo componentes React con Vitest?

Si, con @testing-library/react y jsdom. En este modulo nos centramos en las funciones puras, que son la base; probar la UI requiere mas setup.

¿Como mido coverage?

vitest run --coverage con el provider instalado. El reporte te muestra que funciones, ramas y lineas estan cubiertas y donde faltan tests.

¿Por que los tests en __tests__ y no junto al codigo?

Es una convencion. En monorepos grandes se suele poner el test junto a su modulo (operaciones.test.ts al lado de operaciones.ts). Ambas son validas; elige una y mantenla.

¿Vitest corre en CI sin problemas?

Si: vitest run es no interactivo y devuelve exit code distinto de 0 si algo falla. Anade pnpm test antes del build en el pipeline.

¿Las aserciones de tipos como Equal son necesarias?

Son opcionales, pero documentan lo que esperas del tipado derivado. La comprobacion real de tipos la hace tsc; estas aserciones son una confirmacion extra en los propios tests.
