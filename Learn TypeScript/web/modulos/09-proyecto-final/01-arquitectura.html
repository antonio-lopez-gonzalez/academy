Arquitectura del proyecto final

Modulo 9 · Proyecto final 🕐 45 minutos Proyecto

1 · Introduccion

El proyecto final es una app de tareas (todo manager) completa: CRUD tipado, testing con Vitest y build de produccion desplegable. Esta leccion define la arquitectura: la columna vertebral de tipos y capas sobre la que montaremos todo.

El problema que resuelve: antes de escribir codigo hay que decidir donde vive cada cosa. Una arquitectura clara evita el "codigo espagueti" cuando la app crece, hace visible el flujo de datos y permite testear cada capa por separado.

Que vas a construir (las 4 lecciones)
  • 01·Arquitectura (esta): tipos de dominio, capas y estructura.
  • 02·CRUD tipado: crear, leer, actualizar y borrar tareas con localStorage.
  • 03·Testing con Vitest: test de tipos y de logica tipada.
  • 04·Build y despliegue: produccion y publicacion.

2 · Teoria

La analogia: el organigrama del restaurante

Un restaurante no cocina, sirve y limpia todo en la misma mesa: tiene cocina (logica), sala (presentacion) y almacen (datos). Cada area tiene su recinto, su gente y su "contrato" con las demas. Nuestra app es igual:

DOM (vistas React) │ presenta y pide acciones ▼ capa de dominio (estado + reglas: create/update/delete) │ usa el almacen ▼ capa de datos (localStorage / API) ← 64 "contratos" de tipos

Los tipos de dominio (el contrato central)

// domain/modelo.ts — la union que da sentido a toda la app.
export type EstadoTarea = "pendiente" | "en-progreso" | "completada";

export interface Tarea {
  id: string;
  titulo: string;
  descripcion: string;
  estado: EstadoTarea;
  creadaEn: string; // ISO date
}

Un solo tipo central Tarea alimenta toda la app: el estado, los componentes, el almacen y los tests. Todo deriva de ahi (modulo 6: utility types).

Inversion de dependencias: datos como servicio

// data/tareasStore.ts — abstrae "de donde vienen las tareas".
import type { Tarea } from "../domain/modelo";
import { useLocalStorage } from "../hooks/useLocalStorage";

// El modulo de datos es agnostico de la UI:
export function leerTareas(): Tarea[] {
  const crudo = localStorage.getItem("tareas");
  return crudo ? (JSON.parse(crudo) as Tarea[]) : [];
}

export function guardarTareas(tareas: Tarea[]): void {
  localStorage.setItem("tareas", JSON.stringify(tareas));
}

Si mañana cambias localStorage por una API, solo tocas data/. El resto de la app no se entera.

El flujo de datos (una direccion)

TareaItem ──onToggle──► useTareas ──update──► tareasStore ▲ │ └─────────────── estado ────────────┘ Los eventos del DOM suben; el estado baja por props. Nunca el DOM modifica el almacen directamente.

Por que la arquitectura se decide antes

  • Los tipos de dominio son la "moneda comun": TODAS las capas los importan.
  • Separar data/hooks/components permite testear cada pieza (leccion 03).
  • El flujo "una direccion" hace el estado predecible.
  • Cambiar de almacen (localStorage → API) no toca la UI.

3 · Ejemplo minimo

domain/modelo.ts
// El minimo absoluto de arquitectura: el tipo de dominio y el cambio de estado.
export type EstadoTarea = "pendiente" | "en-progreso" | "completada";

export interface Tarea {
  id: string;
  titulo: string;
  estado: EstadoTarea;
}

// Funcion de dominio pura (se puede testear):
export function cambiarEstado(tarea: Tarea, estado: EstadoTarea): Tarea {
  return { ...tarea, estado };
}

Linea a linea:

  • EstadoTarea: union cerrada de estados validos.
  • Tarea: el modelo minimo de datos.
  • cambiarEstado: funcion pura (sin efectos) del dominio → facil de testear.
  • Toda la app importa estos tipos; el resto se deriva.

4 · Ejemplo real

La arquitectura completa en accion: el hook que orquesta el CRUD y el estado global de la app:

src/hooks/useTareas.ts
import { useState } from "react";
import type { Tarea, EstadoTarea } from "../domain/modelo";
import { leerTareas, guardarTareas } from "../data/tareasStore";

export function useTareas() {
  const [tareas, setTareas] = useState<Tarea[]>(leerTareas);

  function crear(titulo: string, descripcion = ""): void {
    const nueva: Tarea = {
      id: crypto.randomUUID(),
      titulo,
      descripcion,
      estado: "pendiente",
      creadaEn: new Date().toISOString(),
    };
    const siguientes = [...tareas, nueva];
    setTareas(siguientes);
    guardarTareas(siguientes);
  }

  function actualizarEstado(id: string, estado: EstadoTarea): void {
    const siguientes = tareas.map((t) => (t.id === id ? { ...t, estado } : t));
    setTareas(siguientes);
    guardarTareas(siguientes);
  }

  function eliminar(id: string): void {
    const siguientes = tareas.filter((t) => t.id !== id);
    setTareas(siguientes);
    guardarTareas(siguientes);
  }

  return { tareas, crear, actualizarEstado, eliminar };
}

Decisiones:

  • El hook no sabe que la UI existe: solo maneja Tarea[] y el almacen.
  • Cada operacion es inmutable (map/filter/spread): el state cambia en copia tipada.
  • crypto.randomUUID() genera ids unicos tipados como string.
  • Almacen siempre sincronizado despues de cada mutacion.
  • Los tests de la leccion 03 podran usar directamente leerTareas/guardarTareas.

5 · Buenas practicas

  • Define los tipos de dominio primero: son la columna vertebral.
  • Separa data / hooks / components en capas con responsabilidad unica.
  • Manten el flujo en una direccion: DOM sube eventos, props bajan estado.
  • Usa funciones puras de dominio (cambiarEstado) faciles de testear.
  • Cubre el acceso a datos detrás de funciones (store), no de fetch disperso.

Que evitar

  • Que la UI escriba directamente en localStorage (acopla presentacion con datos).
  • Tipos duplicados en cada capa (derivalos del dominio).
  • Mutaciones directas del estado (usa inmutabilidad).
  • Hooks gigantes con logica de UI y de datos mezclada.

6 · Errores habituales

Mal — mutar el estado directamente 
function eliminar(id: string) {
  tareas.splice(tareas.findIndex((t) => t.id === id), 1); // ✖ muta
  setTareas(tareas); // React puede no rerender correctamente
}
Bien — inmutabilidad 
const siguientes = tareas.filter((t) => t.id !== id);
setTareas(siguientes);
Mal — UI tocando el almacen 
// El componente recibe localStorage.set directamente:
function Boton() {
  return <button onClick={() => localStorage.setItem("t", "x")} />; // ✖ acoplado
}
Bien — pasar por el hook/capa de datos 
function Boton({ onAccion }: { onAccion: () => void }) {
  return <button onClick={onAccion} />; // ✅ la accion viene de arriba
}
Mal — tipar el estado del dominio con string suelto 
let estado: string = "pendiente"; // ✖ admite "cualquier-cosa"
Bien — union cerrada 
let estado: EstadoTarea = "pendiente"; // ✅ solo los 3 valores

7 · Ejercicio guiado

Vamos a completar el modelo de dominio con una funcion de filtrado.

  1. Anade un campo opcional etiquetas?: string[] a Tarea.
  2. Escribe function porEstado(tareas: Tarea[], estado: EstadoTarea): Tarea[].
  3. Escribe function pendientes(tareas: Tarea[]): number (cuenta las pendientes).

Solucion paso a paso:

domain/modelo.ts (ampliado)
export interface Tarea {
  id: string;
  titulo: string;
  descripcion: string;
  estado: EstadoTarea;
  creadaEn: string;
  etiquetas?: string[];
}

export function porEstado(tareas: Tarea[], estado: EstadoTarea): Tarea[] {
  return tareas.filter((t) => t.estado === estado);
}

export function contarPendientes(tareas: Tarea[]): number {
  return tareas.filter((t) => t.estado === "pendiente").length;
}

8 · Reto

Reto

Anade al dominio un tipo Filtro = "todas" | "pendientes" | "completadas" y una funcion aplicarFiltro(tareas: Tarea[], filtro: Filtro): Tarea[]. Despues, en el almacen, valida al leer que las tareas cumplen el contrato (filtra las mal formadas). No mires la solucion.

9 · Resumen

  • Tipos de dominio centrales: Tarea, EstadoTarea.
  • Capas: domain (reglas) → data (almacen) → hooks (logica) → components (UI).
  • Flujo en una direccion: DOM sube eventos, props bajan estado.
  • Funciones puras de dominio (testables) y acceso a datos encapsulado.
  • Inmutabilidad siempre que se actualice el estado.

10 · Preguntas frecuentes

¿Por que separar tantas capas en una app pequena?

Porque el proyecto final crece con testing y despliegue. Separar desde el principio hace cada pieza testeable y sustituible, y las bases que aprendas aqui se escalan a proyectos grandes.

¿Que pasa si quiero usar una API en vez de localStorage?

Solo cambia data/tareasStore.ts: leer/guardar pasan a fetch. La UI y los hooks no necesitan tocarse (ese es el beneficio de la inversión de dependencias).

¿LocalStorage es seguro para datos reales?

No: es local, sincrono y sensible a XSS. Para una demo esta perfecto. La leccion 04 menciona API y autentificacion para produccion.

¿Necesito un state manager global?

No. Con una sola fuente de estado (useTareas en App) y props, es suficiente. Los managers globales aportan valor cuando la logica compartida es compleja o distribuida.

¿Por que funciones puras de dominio?

Porque reciben datos tipados y devuelven datos tipados sin efectos: son trivialmente testeables, deterministicas y componibles. Son la parte "matematica" de tu app.

¿La arquitectura se aplica solo a React?

No: separar dominio/datos/presentacion vale para Angular, Vue, vanilla o backend. TypeScript hace visible el contrato entre capas, y React es solo una capa de presentacion.
