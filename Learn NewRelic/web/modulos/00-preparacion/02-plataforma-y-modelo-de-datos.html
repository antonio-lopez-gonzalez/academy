La plataforma New Relic y el modelo de datos

Módulo 0 · Observabilidad y New Relic ⏱ 35 minutos

1 · Introducción

New Relic no es «una pantalla de métricas»: es una base de datos de series temporales (NRDB) con una interfaz encima. Si entiendes su modelo de datos —eventos con atributos que se facetasan—, cualquier consulta, dashboard o alerta deja de ser magia.

En esta lección verás cómo viaja la telemetría desde tu agente hasta el Query Builder, qué son los tipos de eventos (Transaction, Span, Log, Metric, custom events) y por qué «evento» es la palabra clave de todo lo demás.

2 · Teoría

El viaje de un dato

Tú (agente .NET / OTel)                New Relic
───────────────────────────────────────────────────────────────
 +--------------------+   HTTPS    +--------------+
 | Transaction/Log/   | ─────────▶ │ Collector    │
 | /Span/Métrica/Event|            │ (valida,     │
 +--------------------+            │  muestrea)   │
                                   +──────┬───────+
                                          ▼
                                   +------------+   NRQL   +----------------+
                                   │    NRDB    │ ◀──────── │ Query Builder  │
                                   │ (timeboxed)│          │ Dashboards     │
                                   +------------+          │ Alertas        │
                                                            +----------------+

Tu app (con el agente APM o el SDK de OTel) envía datos por HTTPS a un collector de New Relic. Ahí se validan, se aplican límites y muestreo, y se escriben como eventos en NRDB. Todo lo que ves en la UI (tablas, gráficas, dashboards, alertas) es una consulta NRQL sobre esa base.

El evento: la unidad fundamental

Un evento es un registro con una marca de tiempo y un conjunto de atributos (pares clave/valor tipados). Cuando haces SELECT count(*) FROM Transaction FACET appName estás contando eventos y agrupándolos por el valor de un atributo.

Tipo de eventoQué representaAtributos típicos
TransactionUna petición atendidaappName, name, duration, http.statusCode, traceId
TransactionErrorUn error dentro de una transacciónerror.class, error.message, transactionName
SpanUna unidad de trabajo del tracetraceId, guid, parentId, name, duration.ms
LogUn registro de log estructuradolevel, message, trace.id, span.id
MetricSeries temporales numéricasmetricName, metricTimeslice
Custom eventsHechos de negocio propiosLos que tú definas (máx. 64)

Entities: de qué hablas cuando hablas de «tu app»

New Relic agrupa los datos de tu aplicación en una entidad (APM). Cada entidad tiene un entity.guid y nombre (el appName). Los appName mal configurados (múltiples apps con el mismo nombre, nombre cambiado) son causa clásica de datos «que faltan»: estás mirando la entidad equivocada.

La interfaz: one.newrelic.com

  • All capabilities: el launcher con todos los productos (APM & services, Logs, Distributed tracing, Errors inbox, Alerts, Dashboards…).
  • Query Builder: consola NRQL para escribir y guardar consultas.
  • Dashboards: widgets hechos de consultas guardadas, con variables.

Consejo: casi todo lo que ves en APM es una consulta NRQL precocinada. Cuando aprendas NRQL (Módulo 7) podrás ver debajo del capó.

3 · Ejemplo mínimo

Un evento Transaction que generaría tu agente al atender GET /health. Abre el Query Builder, escribe esto y observa los atributos:

SELECT timestamp, appName, name, duration, http.statusCode
FROM Transaction
WHERE appName = 'NotificadorWebSocket'
SINCE 15 minutes ago
LIMIT 5

Cada fila es un evento. La columna duration es un atributo. Agrupar por una columna es un facet. Ya estás hablando el idioma de New Relic.

6 · Errores habituales

Buscar datos en la entidad equivocada

Si cambiaste appName a mitad de proyecto, los datos viejos están bajo la entidad anterior. Verifica: SELECT uniques(appName) FROM Transaction SINCE 30 days ago.

Usar dobles comillas en NRQL

-- ❌ Comillas dobles: las etiquetas y strings van con comillas simples
SELECT count(*) FROM Transaction WHERE appName = "api"    -- error

-- ✅ Comillas simples
SELECT count(*) FROM Transaction WHERE appName = 'api'

Pensar que los datos «desaparecen»

Los eventos de mayor detalle tienen retención acotada (trazas ~8 días por defecto); las métricas van a retención mayor y los eventos pagados más. Si necesitas historia larga, guarda agregaciones, no el detalle.

7 · Ejercicio guiado

  1. Paso 1: Abre tu cuenta (o crea una gratis) y ve a All capabilities → Query Builder.
  2. Paso 2: Ejecuta SHOW EVENT TYPES SINCE 1 day ago. Anota 5 tipos que existan.
  3. Paso 3: Ejecuta SELECT count(*) FROM Transaction FACET appName SINCE 7 days ago. Identifica qué entidades tienes y si alguna esperabas y no aparece.

8 · Reto

🎯 Atributos al detalle

Consulta un solo evento Transaction de tu app y estudia su timestamp y duration. Después respóndete: ¿qué atributo no está presente que te gustaría usar en un FACET? Escríbelo como candidato para la instrumentación custom del Módulo 3.

9 · Resumen

  • New Relic = NRDB (eventos/métricas) + UI sobre consultas NRQL.
  • El evento (tiempo + atributos) es la unidad fundamental; facetear es agrupar por atributo.
  • Tipos clave: Transaction, TransactionError, Span, Log, Metric y custom events.
  • Tu app es una entidad identificada por appName.
  • El camino es: agente → collector → NRDB → revisado con NRQL.

10 · Preguntas frecuentes

¿NRDB es una base de datos SQL?

No exactamente. Es una base de series temporales optimizada por columnas, con un lenguaje parecido a SQL (NRQL) pero orientado a agregaciones por tiempo.

¿Las métricas y los eventos se guardan igual?

No. Las métricas (Metric/`metricTimeslice`) son series agregadas de tamaño predecible; los eventos guardan cada muestra (más caros). Elegir métricas vs. eventos es una decisión de coste y de preguntas.

¿Puedo consultar logs y trazas a la vez?

Sí, correlacionando por trace.id. En NRQL se consultan por separado (FROM Log, FROM Span), y la UI (logs in context) los une por ti.
