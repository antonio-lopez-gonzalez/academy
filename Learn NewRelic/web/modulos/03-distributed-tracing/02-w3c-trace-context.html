W3C Trace Context: traceparent y tracestate

Módulo 3 · Distributed Tracing y traceId ⏱ 35 minutos

1 · Introducción

Para que una traza sobreviva de un servicio a otro hace falta pasar el contexto por el canal. El estándar W3C Trace Context define dos headers: traceparent (el esencial) y tracestate (metadatos del proveedor). New Relic lo implementa, junto a su header legado newrelic para compatibilidad.

Entender los campos de traceparent es la base para poder propagar el contexto por el WebSocket en el siguiente módulo, porque ahí no hay headers.

2 · Teoría

traceparent

Formato version-traceid-parentid-flags:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │_││_______________32 hex________││________16 hex_______││_│
             │ │ traceId (traza completa)      │ parentId (span del     │
             │ │                               │ emisor / padre)        │
             │ └───────────────────────────────┘                         │
             └── versión (00)                                           └ sampled flags
  • version: 00 en la implementación estándar.
  • traceId: 32 hex — el mismo que ves en NRDB.
  • parentId (spanId): 16 hex — el guid del span de origen; será el parentId del receptor.
  • flags: el bit 1 (0x01) es sampled: la decisión de muestreo que se respetará aguas abajo.

tracestate

Lista de pares vendor=value separados por comas, donde cada proveedor guarda su información (New Relic guarda account/trust-key, sampling priority, etc.). Se propaga tal cual: tracestate: newrelic=1-...-... Los proveedores deben aceptar entradas desconocidas sin romperse.

El header newrelic (legado)

New Relic sigue enviando su header propietario newrelic por defecto (excludeNewrelicHeader="false") para interoperar con agentes antiguos. Si tu frontera es 100% OTel/W3C puedes desactivarlo.

Flujo de propagación

Servicio A                                Servicio B
  │  crea traceId + spanId (guid)              │
  │  traceparent = 00-<traceId>-<guid>-<sample>│
  │────────────────────► request HTTP ────────►│ acepta (AcceptDistributedTraceHeaders)
  │                                            │   traceId ← traceparent.traceId
  │                                            │   parentId ← traceparent.parentId
  │                                            │   crea su entry span (guid nuevo)
  │                     response ◄─────────────│

Analogía: traceparent es el pasaporte con tu identidad y a quién vas (tu última parada). tracestate es la página de sellos de otros países que no debes borrar.

3 · Ejemplo mínimo

El agente hace la mayoría sola: si instrumentas ambos servicios con distributed tracing activo, los headers se inyectan/aceptan automáticamente en HttpClient. Comprueba el comportamiento con una llamada de salida:

using HttpClient client = new();
// El agente añade traceparent/tracestate automáticamente a esta request
var resp = await client.GetAsync("https://api.precio.example/prices/9421");

En el span del servicio de precios verás parentId = guid del span emisor de CallPriceApi.

4 · Ejemplo real

Tu WebSocket no tiene headers por mensaje, así que "traduces" el contexto W3C al JSON del mensaje (el carrier). Patrón (detallado en M3-04):

{
  "type": "trade",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "tracestate": "newrelic=1-21-...-...",
  "timestamp": "...", "payload": { }
}

El receptor los leerá y llamará a AcceptDistributedTraceHeaders, que entiende W3C y el header newrelic. Así tu cadena WebSocket ↔ API queda como una sola traza aunque no haya headers HTTP.

6 · Errores habituales

Incumplir el orden/longitud de traceparent

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01   ✅ 55 chars
traceparent: 4bf92f3577b34da6a3ce929d0e0e4736                         ❌ le falta parentId/flags

Usar dobles espacios o mayúsculas en hex

El hex de traceId/parentId va en minúsculas por especificación; algunos agentes son estrictos. No "corrija" los IDs: propágalos tal cual vienen del trazador.

7 · Ejercicio guiado

  1. Paso 1: En una traza de tu app, localiza el header traceparent (en Trace details / atributos del span emisor).
  2. Paso 2: Sepáralo con / o mentalmente en sus 4 campos y anota traceId, parentId y flags.
  3. Paso 3: Ejecuta SELECT count(*) FROM Span WHERE traceId = '<tu traceId>' y observa cuántos spans comparten el traceId.

8 · Reto

🎯 Construye tu carrier

Diseña las reglas de tu «carrier» para el WebSocket: qué campos llevarás en el JSON (traceparent completo vs. traceId+tracestate separados), cómo sanearás los valores y qué harás si un mensaje viene sin contexto (¿empezar traza nueva o errarlo?).

9 · Resumen

  • traceparent = version-traceId-parentId-flags; el pasaporte de la traza.
  • tracestate = metadatos por proveedor; se propaga sin borrar.
  • New Relic añade además el header newrelic (legado, configurable).
  • En WebSocket, el JSON es el carrier: modelas los mismos campos.

10 · Preguntas frecuentes

¿Puedo quitar el header newrelic?

Sí con excludeNewrelicHeader="true"; hazlo si toda tu cadena es OTel/W3C y quieres exactamente estándar.

¿Qué pasa si el traceparent es inválido?

El receptor ignora el contexto y comienza una traza nueva (con su traceId). Por eso conviene sanear/validar en tu carrier WS.

¿AcceptDistributedTraceHeaders acepta otel?

Sí, acepta W3C (traceparent/tracestate) y el formato newrelic; es la API de «traducción» oficial.
