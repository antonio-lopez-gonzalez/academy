Propagación manual del traceId sin HTTP

Módulo 3 · Distributed Tracing y traceId ⏱ 40 minutos

1 · Introducción

En HTTP el agente propaga los headers él solo. Pero en canales que no instrumenta —tu WebSocket, una cola custom— tú decides cómo viaja el contexto. New Relic te da dos llamadas para eso: InsertDistributedTraceHeaders (al enviar) y AcceptDistributedTraceHeaders (al recibir).

Esta es la pieza que convierte a tu WebSocket en un participante de pleno derecho del distributed tracing, con el traceId viajando dentro del propio JSON del mensaje.

¿Por qué importa? Porque ahora mismo, un mensaje que entra por tu WebSocket y dispara una llamada HTTP pierde su contexto: el traceId del HTTP no tendrá relación con el mensaje que lo provocó. Con esta lección lo «cosemos» para hilar un solo trace.

2 · Teoría

El patrón manual

Fíjate en el requisito clave: ambas llamadas necesitan estar dentro de una transacción.

EMISOR (dentro de una transacción)              RECEPTOR (dentro de una transacción)
   │                                                │
   │ InsertDistributedTraceHeaders(carrier, setter) │
   │   → escribe traceparent/tracestate/newrelic    │
   │     en el carrier del mensaje                  │
   │ ──────────── mensaje (cola/WS) ───────────────► │
   │                                                │ AcceptDistributedTraceHeaders(
   │                                                │    carrier, getter, transportType)
   │                                                │   → enlaza su entry span como hijo
   │                                                ▼
   │                              el traceId del receptor = el del emisor

El carrier

El carrier es «el lugar donde escribes claves/valores del mensaje»: propiedades de un mensaje de cola, un Dictionary<string,string>, o el propio objeto de tu mensaje WebSocket con un campo TraceContext. El setter y el getter son las funciones que adaptan la llamada de la API a TU tipo de objeto.

transportType

Al aceptar, indicas cómo viajó (enum TransportType): valores reales HTTP, HTTPS, Queue, AMQP, Kafka, JMS, IronMQ… y Other (para tu WebSocket). Ayuda a la UI a tipar bien el salto entre procesos.

Alternativa ligera: GetLinkingMetadata()

Si no necesitas saltar de proceso pero sí «declarar» el traceId (por ejemplo, en un log o en un evento custom), IAgent.GetLinkingMetadata() te devuelve un diccionario con trace.id, span.id, entity.guid… sin fabricar headers.

3 · Ejemplo mínimo

Con un Dictionary<string,string> como carrier (patrón universal para probar):

using NewRelic.Api.Agent;

IAgent agent = NewRelic.Api.Agent.NewRelic.GetAgent();

// ───── EMISOR ───── (dentro de una transacción)
var carrier = new Dictionary<string, string>();
agent.CurrentTransaction.InsertDistributedTraceHeaders(
    carrier,
    static (props, key, value) => props[key] = value);

EnqueueMessage(new Message { Type = "trade", TraceContext = carrier });

// ───── RECEPTOR ───── (dentro de una transacción recién creada)
Message msg = DequeueMessage();

agent.CurrentTransaction.AcceptDistributedTraceHeaders(
    msg.TraceContext,
    static (props, key) =>
        props.TryGetValue(key, out var v) ? [v] : [],
    TransportType.Queue);

AcceptDistributedTraceHeaders lee W3C (traceparent/tracestate) o el header newrelic según lo que encuentre.

4 · Ejemplo real

En tu WebSocket el carrier es el propio JSON. Definimos una bolsa de contexto en el envoltorio:

// El payload JSON del mensaje tiene estos campos además de payload/business:
//   "type", "timestamp", "traceId", "tracestate", "messageId"

// Al enviar un mensaje hacia un worker (dentro de una transacción existente):
var env = new MessageEnvelope(type: "trade", timestamp: now, messageId: id);
txn.InsertDistributedTraceHeaders(env.TraceContext, WriteTraceHeader);

static void WriteTraceHeader(MessageEnvelope env, string key, string value)
    => env.TraceContext[key] = value;

// Al recibirlo, dentro del [Transaction] que creas para el mensaje (M4):
agent.CurrentTransaction.AcceptDistributedTraceHeaders(
    env.TraceContext,
    ReadTraceHeader,
    TransportType.Other);   // no existe "WebSocket"; usa Other

static IEnumerable<string> ReadTraceHeader(MessageEnvelope env, string key)
    => env.TraceContext.TryGetValue(key, out var v) ? [v] : [];

Y el TraceContext se serializa dentro del JSON:

{
  "type": "trade",
  "timestamp": "2026-08-31T10:15:00.123Z",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "tracestate": "newrelic=1-21-...-...",
  "messageId": "887",
  "payload": { }
}

Así, el traceId del mensaje es el traceId de la traza: de recibirlo a procesarlo y a llamar a la API de precios, todo queda hilado.

6 · Errores habituales

Aceptar el contexto ANTES de crear la transacción del mensaje

// ❌ No hay transacción todavía: Accept no enlaza nada
AcceptTrace(msg);
Process(msg);

// ✅ Primero el [Transaction]/transacción del mensaje, después Accept
[Transaction]
public void Dispatch(MessageEnvelope msg)
{
    agent.CurrentTransaction.AcceptDistributedTraceHeaders(...);
    Process(msg);
}

Leer/escribir claves que no están

// ❌ El getter hace fallar si la clave no existe
static IEnumerable<string> BadGetter(MessageEnvelope e, string k) => [e.TraceContext[k]];

// ✅ Devuelve vacío si no existe (la API lo trata como «sin contexto»)

7 · Ejercicio guiado

  1. Paso 1: En tu Dispatch [Transaction], añade la llamada AcceptDistributedTraceHeaders con un getter tolerante.
  2. Paso 2: Envía mensajes SIN contexto: verás traces «nuevas» (traceId generado).
  3. Paso 3: Envía mensajes que incluyan un traceparent falso/válido en sus campos de contexto y comprueba que el entry span hereda ese traceId.
  4. Paso 4: Consulta SELECT traceId FROM Span WHERE name LIKE '%Dispatch%' y verifica el enlace.

8 · Reto

🎯 Extremo a extremo

Diseña el flujo donde tu servidor recibe un trade, lo procesa y llama a una API interna; y donde un worker recoge el resultado y lo guarda. Escribe las 4 llamadas (Insert/Accept) que harían falta y dibuja el árbol que esperas (usuario→WS→API→cola→worker). Aplica lo dibujado en el Módulo 8.

9 · Resumen

  • InsertDistributedTraceHeaders escribe el contexto en el carrier; AcceptDistributedTraceHeaders lo enlaza.
  • Ambas requieren una transacción en curso; el transportType califica la frontera.
  • En WebSocket, el carrier es el propio JSON con campos de contexto.
  • GetLinkingMetadata() es la versión ligera para logs/eventos.

10 · Preguntas frecuentes

¿Y si el cliente no manda contexto?

No pasa nada: el receptor empieza una traza nueva. La decisión de diseño es tuya: al filtrar «mensajes sin contexto» puedes medir qué % de tus mensajes no provienen de un extremo trazado.

¿InsertDistributedTraceHeaders e Inyección automática de HttpClient se pisan?

No. Para HttpClient el agente ya lo hace solo; Insert/Accept es para canales que él no conoce. Solo una de las dos debe escribir el contexto por canal.

¿Puedo propagar sin W3C, solo con traceId?

Puedes llevar solo el traceId como atributo (para correlacionar logs), pero para que New Relic reconstruya trazas unidas necesitas el contexto W3C/NewRelic completo. Lleva el contexto.
