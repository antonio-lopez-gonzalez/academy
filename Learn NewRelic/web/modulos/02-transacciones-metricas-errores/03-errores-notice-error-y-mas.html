Errores: NoticeError, esperados vs. no esperados

Módulo 2 · Transacciones, Métricas y Errores ⏱ 30 minutos

1 · Introducción

Un error no registrado es un incidente silencioso. Pero un error esperado (como un 404 o una validación de negocio) sin marcar, contamina tu error rate y tus alertas. Este equilibrio —capturar todo pero clasificar bien— es el corazón de esta lección.

Aprenderás a usar NoticeError, a marcar errores como esperados y a entender cómo el error rate alimenta alertas y Errors inbox.

2 · Teoría

Cómo captura errores el agente

El agente detecta automáticamente excepciones sin capturar en transacciones web y errores HTTP. Eso genera TransactionError (evento) y un error trace. Además, tienes NoticeError para casos «no automáticos»: manejo con try/catch dentro de tu WebSocket, validaciones, errores de cola…

Cuatro sobre-cargas útiles de NoticeError

NewRelic.Api.Agent.NewRelic.NoticeError(Exception ex);
NewRelic.Api.Agent.NewRelic.NoticeError(Exception ex, IDictionary<string, string> attrs);
NewRelic.Api.Agent.NewRelic.NoticeError(string mensaje, IDictionary<string, string> attrs);
NewRelic.Api.Agent.NewRelic.NoticeError(string mensaje, IDictionary<string, string> attrs, bool isExpected);

La última es la clave para clasificar: con isExpected: true el error no afecta al error rate ni al Apdex, pero sigue apareciendo en Error analytics/Errors inbox para que lo rastrees.

Expected vs. no-expected

TipoEjemplo en tu WebSocket¿Afecta el error rate?
Esperado (expected)Mensaje malformado que rechazas, 404, validación de negocioNo
No esperadoNullReference en el processor, timeout de un external, DB caídaSí → dispara alertas y Apdex

El error rate y las alertas

Las alertas de «error rate» se basan en el error.expected=false normalmente. El Errors inbox agrupa errores por similitud (error.class, error.message) para que priorices los grupos, no las líneas.

3 · Ejemplo mínimo

try
{
    var order = ParseOrder(msg.Payload);              // puede lanzar JsonException
    ProcessOrder(order);
}
catch (JsonException ex)
{
    // Error ESPERADO: malformado, no infla tu error rate
    NewRelic.Api.Agent.NewRelic.NoticeError(
        ex,
        new Dictionary<string, string> {
            { "messageType", msg.Type },
            { "messageId", msg.MessageId },
        },
        isExpected: true);
}
catch (Exception ex)
{
    // Error NO esperado: debe saltar la alerta
    NewRelic.Api.Agent.NewRelic.NoticeError(ex);
    throw;
}

Con atributos como messageType podrás facetear errores por tipo y responder «¿qué tipos de mensaje fallan más?».

4 · Ejemplo real

En un servidor WebSocket con varios tipos de mensaje:

// Middleware por tipo: tratamos errores esperados por tipo de mensaje
if (msg.Type == "ping")
{
    // Si el ping va mal, es un problema de salud del nodo → NO esperado
    NewRelic.Api.Agent.NewRelic.NoticeError("Ping procesado con errores", null);
}
else if (msg.Type == "trade" && !IsValidTrade(msg))
{
    // Rechazo de negocio → esperado
    NewRelic.Api.Agent.NewRelic.NoticeError("Trade inválido", attrs, isExpected: true);
}

La consulta que separa claramente la clasificación en el Query Builder:

SELECT count(*) FROM TransactionError
WHERE appName = 'NotificadorWebSocket'
FACET error.class, error.expected, error.messageType
SINCE 24 hours ago

6 · Errores habituales

Reportar errores en loops de alto volumen

// ❌ Un NoticeError (evento) por cada mensaje fallido en un batch de 10k
// ✅ Captura 1 error sampleado + una métrica de contador:
//    IncrementCounter("Custom/ProcessErrors") y marca pocos detalles
//    (o usa muestreo y atributos de cardinalidad baja)

Llamar NoticeError fuera de una transacción

Sin transacción, el agente crea un error trace suelto pero no contribuye al error rate de una transacción. Si quieres que cuente, hazlo dentro del contexto de la transacción (en M4 verás cómo crear la transacción del mensaje).

Confundir «403» con esperado/inesperado

Un 403 de seguridad es un fallo de seguridad: normalmente no lo marques como esperado aunque «lo esperes». La etiqueta «expected» implica «irrelevante para SLA», que no es lo mismo.

  1. Paso 1: En tu handler de mensajes, envía con un helper «parsea y marca error esperado en invalid JSON» y «error no esperado en cualquier otra excepción», como en el ejemplo mínimo.
  2. Paso 2: Envía 10 mensajes válidos y 3 con JSON roto.
  3. Paso 3: Consulta: 
    SELECT count(*) FROM TransactionError FACET error.class, error.expected SINCE 15 minutes ago
  4. Paso 4: Comprueba que los esperados no afectan tu error rate de la transacción.

8 · Reto

🎯 Errors inbox que no ahoga

Define una revisión de errores: qué campos (error.class, message, messageType, appName) consultarías para decidir qué grupo atender primero cada semana. Escribe la consulta NRQL y un «SLA» razonable para cada grupo.

9 · Resumen

  • NoticeError declara errores manualmente, con atributos y opción isExpected.
  • Los esperados no inflan error rate ni Apdex; los no esperados deben disparar alertas.
  • Faceta con FACET error.expected, error.class para separar ruido y señal.
  • En bucles de alto volumen: métricas + muestreo > evento por error.

10 · Preguntas frecuentes

¿Cuándo uso isExpected en un WebSocket?

Para "circunstancias normales del negocio": mensajes malformados, validaciones, tipos desconocidos. NO para fallos de infraestructura.

¿Qué pasa con los 500 de mi API?

Por defecto cuentan como error (no esperado). Puedes configurar errorCollector y excepciones ignoradas/esperadas en newrelic.config.

¿Errors inbox necesita configuración?

No; agrupa por similitud automáticamente. El SetErrorGroupCallback existe si quieres controlar los grupos con tu propia lógica.
