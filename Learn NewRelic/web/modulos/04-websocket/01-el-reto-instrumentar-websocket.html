El reto: por qué el agente no ve los WebSocket

Módulo 4 · Instrumentar WebSocket ⏱ 30 minutos

1 · Introducción

Ya sabes que «instalar el agente» no cubre tu WebSocket. Ahora vamos a entender por qué a nivel de mecánica del agente, y qué es lo que sí captura (para aprovecharlo) frente a lo que no (para instrumentarlo).

Este análisis previo es el que te permitirá decidir sin miedo qué instrumentar y qué no, en lugar de crear ruido.

2 · Teoría

Qué ve el agente en un WebSocket

Un WebSocket empieza como HTTP (handshake de upgrade). El agente instrumenta ASP.NET Core, así que verá:

  • La transacción de la petición de upgrade (WS /ws con status 101).
  • Todo lo que ocurra durante esa transacción antes de que termine.
  • Llamadas HTTP salientes, bases de datos, etc., si se ejecutan dentro de esa transacción.

Pero la conexión queda «abierta»: el agente no crea una transacción por cada frame que llega después. Esa es la clave del problema.

Por qué no hay transacciones por mensaje

Cliente            Servidor .NET (agente)
   │  handshake GET /ws (101)  │ ← transacción "corta" del upgrade
   ├─► mensaje 1 ─────────────►│  (solo enmarcado como parte del upgrade)
   ├─► mensaje 2 ─────────────►│  The agent no inicia nada nuevo
   ├─► mensaje 3 ─────────────►│  ──► sin duración, sin atributos, sin trace por mensaje
   │  ...                      │
   └─► close                   │

La razón de diseño: WebSocket es long-lived y de mensajería arbitraria; el agente no conoce la «unidad de trabajo» de tus mensajes (eso solo lo sabes tú: qué es un trade, cuándo termina). Por eso la instrumentación de ese nivel es responsabilidad de la app.

Qué ganas si lo instrumentas

AntesDespués

Mentalidad: no intentes que el agente «entienda tu protocolo». Instrumenta ¿qué es una unidad de trabajo para tu negocio? y deja que el agente provea el transporte (métricas, headers, spans) de esa unidad.

3 · Ejemplo mínimo

El núcleo del handler que verás en las próximas lecciones: una transacción por mensaje con sus atributos.

[Transaction]                              // 1 mensaje = 1 transacción
public void OnMessage(MessageEnvelope msg)
{
    var txn = NewRelic.Api.Agent.NewRelic.GetAgent().CurrentTransaction;
    txn.AddCustomAttribute("messageType", msg.Type);
    txn.AddCustomAttribute("messageId", msg.MessageId);

    // ... el resto del procesado ...
}

Métricas y eventos para completar el cuadro. La toma de decisiones instrumentación:

Regla de oro del coste: la transacción por mensaje ya te da count+duration+errors con un precio contenido (muestreo de trazas). No añadas un custom event por mensaje: guarda los eventos para caras de negocio relevantes.

6 · Errores habituales

Esperar transacciones WebSocket automáticas

# ❌ "Instalé el agente, ¿por qué no veo los mensajes?"
# ✅ Algo ya ves (el upgrade HTTP). Los mensajes se instrumentan
#    con [Transaction] + atributos (M4-02, M4-03).

Instrumentar el hilo/ loop completo de la conexión

// ❌ Una transacción que abarca toda la conexión (minutos)
[Transaction]
public async Task HandleConnection(WebSocket socket)
{
    while (socket.State == WebSocketState.Open)
    {
        var msg = await ReceiveAsync(socket);
        Process(msg);
    }
}

// ✅ Transacción por mensaje, dentro del loop
public async Task HandleConnection(WebSocket socket)
{
    while (socket.State == WebSocketState.Open)
    {
        var msg = await ReceiveAsync(socket);
        OnMessage(msg);   // [Transaction] por mensaje
    }
}

Poner todo el tráfico en eventos

10k mensajes/min × evento = factura alta. Métrica/transacción para el volumen; eventos para lo que merece la pena.

8 · Reto

🎯 El upgrade como primer eslabón

Investiga cómo recuperar el traceId de la transacción del upgrade (pista: GetLinkingMetadata() o un atributo) y diseña cómo lo pasarías al primer mensaje de la conexión. Escríbelo como cola de tu proyecto (lo aplicamos en M8).

9 · Resumen

  • El agente ve el handshake HTTP, no la mensajería posterior.
  • La unidad de trabajo del WebSocket la define el negocio → instrumentación tuya.
  • Una transacción por mensaje + atributos + [Trace] en fases clave.
  • Volumen en métricas/transacciones; eventos solo para hechos valiosos.

10 · Preguntas frecuentes

¿SignalR cambia esto?

La mecánica es la misma: el transporte es socket; el agente instrumenta HTTP/ASP.NET. Los hubs y la lógica de negocio se instrumentan igual con atributos/API.

Y si el volumen es enorme, ¿la transacción por mensaje es viable?

Sí, con muestreo. Las transacciones (eventos) se generan en cliente, pero el tracing de spans va muestreado. Para contadores masivos sin trazas, usa métricas IncrementCounter.

¿La transacción por mensaje incluye el tiempo en el socket?

No por defecto: el ReceiveAsync bloqueante esperaría el próximo mensaje. Mide el «tiempo de espera» del loop aparte (métricas) y la duración del procesado en la transacción.
