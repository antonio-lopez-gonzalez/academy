Caso práctico: servidor WebSocket instrumentado

Módulo 4 · Instrumentar WebSocket ⏱ 45 minutos

1 · Introducción

Reunimos todo: un servidor WebSocket en .NET 8 que instrumenta cada mensaje con transacción, atributos, spans, errores y propagación W3C, más una Minimal API. Es la semilla del proyecto proyectos/newrelic-ws-demo.

Este documento es el «código completo comentado» que podrás ejecutar ya (dotnet run) y, con tu licencia, ver en New Relic.

2 · Teoría

Arquitectura deseada:

Program.cs (Minimal API + WebSocket)
   ├── GET  /api/status        ──► transacción automática
   ├── POST /api/broadcast     ──► transacción + atributo audience
   └── WS   /ws                ──► upgrade automático
            └── WsServer.Handle
                 └── [Transaction] MessageDispatcher.OnMessage
                      ├── AcceptDistributedTraceHeaders(W3C del JSON)
                      ├── atributos (messageType, messageId, userId)
                      ├── dispatch → [Trace] por tipo (Validate/Apply/Broadcast)
                      └── NoticeError (expected/non-expected)
   └── meters de datos: RecordMetric (QueueLatency, BroadcastMs)
   └── logs estructurados con ILogger (M5 los enriquecerá)

División de responsabilidades por archivos, testable y clara.

3 · Ejemplo mínimo

Primer corte funcional, un único archivo:

// ConsoleRun.cs — compilable con dotnet run en un proyecto web
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton(NR.Agent());   // lazy IAgent (M2-04)
builder.Services.AddSingleton<MessageDispatcher>();
var app = builder.Build();

app.MapGet("/api/status", () =>
{
    NewRelic.Api.Agent.NewRelic.GetAgent().CurrentTransaction
        .AddCustomAttribute("version", Environment.GetEnvironmentVariable("APP_VERSION") ?? "dev");
    return Results.Ok(new { status = "ok" });
});

app.UseWebSockets();
app.Map("/ws", async (HttpContext ctx, MessageDispatcher dispatcher) =>
{
    if (!ctx.WebSockets.IsWebSocketRequest) return Results.BadRequest();

    // El upgrade toma el control de la conexión; el endpoint la acompaña
    using var socket = await ctx.WebSockets.AcceptWebSocketAsync();
    await new WsServer(socket, dispatcher).HandleAsync();
    return Results.Empty;
});

app.Run();

static class NR
{
    public static NewRelic.Api.Agent.IAgent Agent() =>
        NewRelic.Api.Agent.NewRelic.GetAgent();     // lazy: se resuelve al usarse
}

4 · Ejemplo real

El proyecto completo comentado (idéntico al de proyectos/newrelic-ws-demo, versión reducida):

// ─────────── Messages.cs ───────────
public sealed record MessageEnvelope(
    string Type, DateTimeOffset Timestamp, string MessageId,
    Dictionary<string, string> TraceContext, JsonElement Payload);

// ─────────── MessageDispatcher.cs ───────────
public sealed class MessageDispatcher(ILogger<MessageDispatcher> logger)
{
    private readonly IAgent _agent = NewRelic.Api.Agent.NewRelic.GetAgent();

    [Transaction]                       // 1 mensaje = 1 transacción (OtherTransaction)
    public void OnMessage(MessageEnvelope msg)
    {
        var txn = _agent.CurrentTransaction;
        txn.AddCustomAttribute("messageType", msg.Type)
           .AddCustomAttribute("messageId", msg.MessageId);

        // Acepta el contexto W3C que viaja en el JSON (M3-04)
        txn.AcceptDistributedTraceHeaders(msg.TraceContext,
            static (env, k) => env.TraceContext.TryGetValue(k, out var v) ? [v] : [],
            TransportType.Other);   // el enum real no tiene "WebSocket"

        try { Dispatch(msg); }
        catch (Exception ex)
        {
            var expected = IsBusinessError(msg, ex);
            NewRelic.Api.Agent.NewRelic.NoticeError(ex,
                new Dictionary<string, string> { { "messageType", msg.Type } },
                expected );
            logger.LogError(ex, "Fallo procesando {Type} {MessageId}", msg.Type, msg.MessageId);
        }
    }

    private void Dispatch(MessageEnvelope msg) => msg.Type switch
    {
        "trade" => _trade.ProcessTrade(msg),
        "ping"  => _ping.Respond(msg),
        _ => logger.LogWarning("Desconocido {Type}", msg.Type),
    };
}

// ─────────── TradeProcessor.cs ───────────
public sealed class TradeProcessor
{
    [Trace]
    public void ProcessTrade(MessageEnvelope msg)
    {
        _agent.CurrentSpan.AddCustomAttribute("symbol", GetSymbol(msg));
        Validate(msg);                       // [Trace]
        Apply(msg);                          // [Trace] + métrica de latencia
    }
}

// ─────────── WsServer.cs ───────────
public sealed class WsServer(WebSocket socket, MessageDispatcher dispatcher)
{
    public async Task HandleAsync()
    {
        var buffer = new byte[4 * 1024];
        while (socket.State == WebSocketState.Open)
        {
            var result = await socket.ReceiveAsync(buffer, CancellationToken.None);
            if (result.MessageType == WebSocketMessageType.Close) break;

            var env = JsonSerializer.Deserialize<MessageEnvelope>(
                Encoding.UTF8.GetString(buffer, 0, result.Count));
            if (env is null) continue;

            dispatcher.OnMessage(env);      // transacción aquí
        }
    }
}

Con tu licencia puesta, esto produce: transacciones OtherTransaction, spans, errores y, si activas logs, correlación. Es el MVP del proyecto final.

6 · Errores habituales

Transacción en el async loop completo (otra vez el clásico)

// ❌ Recibe + transacción juntos: la duración mide la espera del siguiente
[Transaction]
public async Task HandleAsync() { while(...) await socket.ReceiveAsync(...); }

// ✅ Transacción solo en OnMessage (procesado)

Deserializar con la transacción activa y fallar en parseo

Si el JSON viene roto y lo parseas dentro de la transacción, el error de parseo será del mensaje (correcto). Si lo evitas con `?`/`!`, pierdes ese contexto. Manejalo con try/catch alrededor del dispatch.

Olvidar que el TraceContext viaja en JSON, no en headers

En el cliente y en cualquier proxy debe propagarse el JSON completo; si un proxy descarta campos, pierdes el context. No te apoyes en headers del WS.

8 · Reto

🎯 Completa tu arquitectura

Añade al caso práctico: (1) una llamada HttpClient a un endpoint tuyo dentro del ProcessTrade; (2) una métrica Custom/BroadcastMs; (3) un log con el traceId. Deja preparadas las queries para comprobar cada uno. Esto es prácticamente el Módulo 8.

9 · Resumen

  • Patrón completo: transporte → [Transaction] → Accept(mensaje) → dispatch → [Trace] → errores.
  • Separa socket de negocio; la transacción mide el trabajo.
  • Con este MVP ya tienes transactions, spans, errores y trazas del WebSocket.

10 · Preguntas frecuentes

¿Este código cubre también el consumo?

Sí, en parte: las transacciones por mensaje y sus eventos cuentan. Ajusta el sampling y usa métricas si el volumen es brutal (M2-02).

¿Puedo ver el WebSocket en «APM» como tal?

Sí: verás la entidad con sus transacciones (upgrade + OtherTransaction por mensaje), traces y errors. El «WebSocket» como concepto se construye con tus atributos.

¿Y la conexión que se mantiene abierta?

La conexión en sí (long-lived) la vigila la infraestructura, no necesariamente necesita transacción; el upgrade da su métrica y la persistencia del socket puedes medirla aparte.
