Instalación y consola web

Módulo 0 · Fundamentos 🕐 30 minutos

1 · Introducción

Levantar MinIO son dos comandos. Operarlo sin perder datos es otra conversación. La diferencia está en tres decisiones que se toman en el primer minuto: dónde vive el dato (un volumen, no la capa escribible del contenedor), con qué credenciales arranca (root solo para el arranque, nunca en la aplicación) y qué puertos expones (API y consola son superficies distintas).

En esta lección montamos un MinIO de un solo nodo con Docker, comprobamos su salud, recorremos la consola web y demostramos que los objetos sobreviven a un reinicio del contenedor. También veremos qué es exactamente lo que se guarda en /data y por qué no debes tocarlo a mano.

El objetivo no es «tener MinIO corriendo», sino tener un entorno reproducible que puedas destruir y recrear sin miedo. Ese entorno será la base del almacén de documentos durante todo el curso.

El error de los primeros cinco minutos

El fallo más caro de esta lección es arrancar sin volumen. Todo funciona, subes documentos, haces docker compose down y al volver la nada. El segundo es commitear las credenciales root en docker-compose.yml. Los dos se evitan con la configuración que viene a continuación.

2 · Teoría

Qué hace el contenedor

La imagen oficial contiene un único binario, minio, y un punto de entrada. El comando server /data le dice que sirva almacenamiento desde ese directorio. MinIO no necesita una base de datos externa: los metadatos de buckets y objetos viven en el propio volumen, en una estructura interna que no debes editar.

+----------------------------- docker -----------------------------+
|                                                                  |
|  quay.io/minio/minio                                             |
|  ┌────────────────────────────────────────────────────────────┐  |
|  │  proceso minio                                             │  |
|  │    :9000  API S3          :9001  consola                   │  |
|  │       │                      │                             │  |
|  │       └──────────┬───────────┘                             │  |
|  │                  v                                         │  |
|  │              /data  ──────────────────────────────┐        │  |
|  └───────────────────────────────────────────────────┼────────┘  |
|                                                      │           |
+------------------------------------------------------┼-----------+
                                                       v
                                        volumen minio-data
                                        (persiste fuera del contenedor)

Sin volumen, /data vive en la capa escribible del contenedor. Esa capa desaparece cuando el contenedor se elimina, y además está pensada para cambios efímeros, no para E/S intensiva. Un volumen de Docker (o un bind mount a una carpeta del host) separa el ciclo de vida del dato del ciclo de vida del proceso.

Las variables que importan

Variable / flagQué controlaRecomendación
MINIO_ROOT_USERUsuario root inicialNo usar minioadmin; es público y conocido
MINIO_ROOT_PASSWORDContraseña root inicialMínimo 8 caracteres; secreto real, fuera de Git
server /dataDirectorio de datosDebe apuntar a un volumen persistente
--console-address ":9001"Puerto interno de la consolaFijarlo evita puertos aleatorios
-p 9000:9000Publicación de la API S3Cambiar solo el puerto del host si está ocupado
-p 9001:9001Publicación de la consolaNo exponerla a Internet en producción

Las credenciales root se leen al arrancar. Si cambias la contraseña en el entorno y reinicias, MinIO actualiza el usuario root; si las pierdes, no hay un «recuperar contraseña»: hay que restaurar el acceso con el procedimiento de recuperación y, en el peor caso, recrear el despliegue. Por eso el módulo 3 insiste en crear un usuario de aplicación y guardar el root en un gestor de secretos.

Endpoints de salud

EndpointQué respondeUso
/minio/health/live200 si el proceso está vivoLiveness probe; no valida credenciales
/minio/health/ready200 si puede atender peticionesReadiness probe
/minio/health/cluster200 si hay quórum de escrituraClúster; 503 si no puede escribir

Un 200 en live no significa que tus credenciales sean correctas ni que el bucket exista. Solo dice que hay un proceso escuchando. Para comprobar el acceso real, el cliente debe autenticarse con una operación S3.

Un nodo no es un clúster

Este Compose levanta un servidor con un volumen. Es el entorno de desarrollo y también puede servir cargas pequeñas con las precauciones adecuadas, pero es un punto único de fallo: si el disco muere, el servicio muere. No hay erasure coding entre discos ni réplica entre nodos.

MinIO no soporta Docker Compose para despliegues distribuidos. Un clúster multi-nodo multi-disco se despliega con el Kubernetes Operator o sobre máquinas con volúmenes locales preparados. Añadir réplicas en Compose no crea un clúster: crea contenedores aislados que no comparten datos.

Qué hay dentro de /data

/data
├── .minio.sys/          metadatos internos del despliegue
├── documentos/          un directorio por bucket
│   ├── 2026/
│   │   └── informes/
│   │       └── acme/
│   │           └── informe.pdf/
│   │               └── xl.meta
│   └── ...
└── .minio.sys/tmp/      temporales de operaciones en curso

La estructura real depende de la versión y del modo (single drive o erasure set). Lo importante: no es una carpeta de ficheros legible. No copies objetos con cp, no edites xl.meta y no borres directorios para «limpiar». Para mover datos se usa mc mirror o la API; para copiar el volumen, se para el servicio o se usa una instantánea coherente.

3 · Ejemplo mínimo

Primero las credenciales. Crea un .env local a partir de un ejemplo que sí se puede versionar:

# .env.example  (sí se versiona)
MINIO_ROOT_USER=minioadmin
MINIO_ROOT_PASSWORD=cambiar-esta-clave

# .env  (NO se versiona)
cp .env.example .env

Ahora el contenedor, con un volumen con nombre:

docker run -d \
  --name minio \
  -p 9000:9000 \
  -p 9001:9001 \
  -v minio-data:/data \
  --env-file .env \
  quay.io/minio/minio server /data --console-address ":9001"

Flag a flag:

  • -d lo deja en segundo plano; sin esto, la terminal queda ocupada por los logs.
  • --name minio da un nombre estable para docker logs, docker stop y docker exec.
  • -p 9000:9000 publica la API S3. El primer número es el puerto del host; el segundo, el del contenedor.
  • -p 9001:9001 publica la consola.
  • -v minio-data:/data monta un volumen gestionado por Docker. El dato sobrevive a docker rm.
  • --env-file .env inyecta las credenciales sin escribirlas en el historial del shell.
  • server /data --console-address ":9001" es el comando del servidor y fija la consola en el puerto esperado.

Comprueba que responde:

curl -i http://localhost:9000/minio/health/live
docker logs minio --tail 20
HTTP/1.1 200 OK
...
API: http://172.18.0.2:9000  http://127.0.0.1:9000
WebUI: http://172.18.0.2:9001  http://127.0.0.1:9001

Abre http://localhost:9001, inicia sesión con las credenciales del .env y crea un bucket llamado documentos. Si la consola de tu versión no muestra alguna sección, no es un fallo del servidor: las funciones de administración han ido migrando a mc. El comando equivalente siempre existe.

4 · Ejemplo real

Para el proyecto del curso usamos Compose porque describe el entorno en un fichero versionado y se levanta con un comando. Este es el docker-compose.yml del almacén de documentos:

services:
  minio:
    image: quay.io/minio/minio
    container_name: document-store-minio
    command: server /data --console-address ":9001"
    ports:
      - "9000:9000"
      - "9001:9001"
    env_file:
      - .env
    volumes:
      - minio-data:/data
    restart: unless-stopped

volumes:
  minio-data:

Y el .env.example que acompaña al repositorio:

MINIO_ROOT_USER=minioadmin
MINIO_ROOT_PASSWORD=cambiar-esta-clave

# Usuario de aplicación (se crea en el módulo 3)
APP_ACCESS_KEY=app-documentos
APP_SECRET_KEY=cambiar-tambien

# Endpoint que usan los servicios
S3_ENDPOINT=http://localhost:9000
S3_REGION=us-east-1

Arranque y comprobación:

docker compose up -d
docker compose ps
curl -fsS http://localhost:9000/minio/health/live && echo " API OK"
curl -fsS http://localhost:9001 > /dev/null && echo " consola OK"

En PowerShell, el equivalente para la segunda comprobación es Invoke-WebRequest http://localhost:9001 -UseBasicParsing | Select-Object StatusCode. Para detener sin perder datos usa docker compose down; el volumen se conserva. docker compose down -v elimina también el volumen y con él todos los objetos: es el comando que separa un reinicio de un borrado.

La consola es útil para explorar y para una operación puntual, pero no es la vía de automatización. Todo lo que hagas allí debe tener su reflejo en un comando o en un fichero versionado; si no, el entorno de staging y el de producción divergen sin que nadie lo note.

La consola Community no es la de AIStor

Las imágenes Community recientes han ido recortando funciones de gestión en la consola. Si una pantalla no aparece en tu versión, no está rota: usa mc, que es la interfaz canónica del curso. En producción, además, la consola no debería ser el camino de operación.

Persistencia: la prueba que hay que hacer siempre

# Sube un objeto (consola o mc)
mc cp ./informe.pdf local/documentos/2026/informes/acme/informe.pdf

# Reinicia el servicio sin borrar el volumen
docker compose restart

# El objeto sigue ahí
mc stat local/documentos/2026/informes/acme/informe.pdf

# Ahora destruye el contenedor, pero no el volumen
docker compose down
docker compose up -d
mc ls local/documentos/2026/informes/acme/

Si el objeto desaparece en el segundo bloque, el volumen no está montado donde crees. Revisa docker compose config y docker volume inspect antes de seguir.

5 · Buenas prácticas

HazEvitaPor qué
Montar un volumen nombrado o un bind mount explícito Dejar /data en la capa del contenedor La capa se borra con el contenedor y no está pensada para E/S.
Versionar .env.example y ignorar .env Commitear credenciales root Un secreto en Git está comprometido aunque lo borres después.
Fijar la etiqueta de la imagen Usar latest en un entorno compartido Un pull puede cambiar comportamiento sin que toques nada.
Comprobar live y autenticación por separado Interpretar un 200 como «todo listo» El health check no valida credenciales, buckets ni permisos.
Guardar el root en un gestor de secretos Reutilizar la misma contraseña en todos los entornos El radio de impacto de una filtración debe ser un entorno, no todos.
Probar un ciclo de restauración Suponer que el volumen es un backup Un volumen en el mismo host no protege de un fallo del host.

6 · Errores habituales

1. Arrancar sin volumen

Mal — el dato vive y muere con el contenedor 
docker run -d --name minio \
  -p 9000:9000 -p 9001:9001 \
  --env-file .env \
  quay.io/minio/minio server /data --console-address ":9001"
Bien — volumen explícito 
docker run -d --name minio \
  -p 9000:9000 -p 9001:9001 \
  -v minio-data:/data \
  --env-file .env \
  quay.io/minio/minio server /data --console-address ":9001"

El síntoma es brutal: docker rm minio y todos los objetos desaparecen. No hay mensaje de error, porque para MinIO era un directorio normal.

2. Root por defecto o en el repositorio

Mal — credenciales conocidas y versionadas 
# ❌ minioadmin/minioadmin es público; el .env no va a Git
environment:
  MINIO_ROOT_USER: minioadmin
  MINIO_ROOT_PASSWORD: minioadmin
Bien — secreto inyectado y ejemplo sin valor real 
env_file:
  - .env            # ignorado por Git

# .env.example:
# MINIO_ROOT_USER=minioadmin
# MINIO_ROOT_PASSWORD=cambiar-esta-clave

Además del .gitignore, comprueba el historial si ya lo subiste: cambiar el valor en un commit nuevo no borra el anterior. Rota la credencial.

3. Puerto ocupado

Mal — cambiar el puerto interno y romper la documentación 
# ❌ El contenedor sigue escuchando en 9000; esto no arregla el conflicto.
docker run -p 9100:9100 ... quay.io/minio/minio server /data
Bien — cambiar solo el puerto del host y actualizar el endpoint 
netstat -ano | findstr :9000     # Windows
lsof -i :9000                    # macOS / Linux

docker run -p 9100:9000 -p 9101:9001 ...
export S3_ENDPOINT=http://localhost:9100

La regla es: el puerto interno del contenedor no cambia; cambia el mapeo del host. Si cambias el de la consola, actualiza también la URL del navegador.

4. Confundir down con down -v

Mal — borrar el volumen «para reiniciar limpio» 
docker compose down -v   # ❌ elimina el volumen y todos los objetos
Bien — reiniciar conservando el dato 
docker compose restart
# o
docker compose down
docker compose up -d

No hay papelera. Si el bucket tiene versionado y object lock, el volumen sigue siendo la única copia; si lo borras, no hay versiones que recuperar.

7 · Ejercicio guiado

Objetivo: levantar MinIO, crear un bucket, subir un objeto y demostrar que sobrevive a un reinicio y a la recreación del contenedor.

  1. Prepara el entorno. 
    mkdir laboratorio-minio
cd laboratorio-minio
cp .env.example .env
docker compose up -d
docker compose ps

    Salida esperada: el servicio minio en estado running y los puertos 0.0.0.0:9000->9000/tcp y 9001->9001/tcp.

  2. Comprueba salud y autenticación por separado. 
    curl -i http://localhost:9000/minio/health/live
curl -i http://localhost:9000/minio/health/cluster

    Ambos deben devolver 200. Después configura el alias y ejecuta mc admin info local: si esto falla, el problema es de credenciales, no de red.

  3. Crea el bucket y un objeto desde la consola. Entra en http://localhost:9001, crea documentos y sube un PDF pequeño a 2026/informes/acme/. Si tu consola no permite subir, hazlo con mc cp; el resultado es el mismo.
  4. Verifica el objeto por la API. 
    mc ls --recursive local/documentos
mc stat local/documentos/2026/informes/acme/informe.pdf

    Debe aparecer la clave completa y un Content-Type coherente con el fichero.

  5. Reinicia y recrea. 
    docker compose restart
mc ls local/documentos/2026/informes/acme/

docker compose down
docker compose up -d
mc ls local/documentos/2026/informes/acme/

    El objeto debe seguir en ambos casos. Si no, revisa el volumen antes de continuar.

  6. Inspecciona el volumen y los logs. 
    docker volume inspect laboratorio-minio_minio-data
docker logs document-store-minio --tail 30

    Anota el Mountpoint. Ese directorio es el dato real; el contenedor es solo el proceso que lo sirve.

8 · Reto

🎯 Migrar de bind mount a volumen sin perder nada

Tienes un MinIO funcionando con -v ./data:/data y quieres pasar a un volumen nombrado minio-data. El servicio no puede perder objetos y solo puedes tener una caída breve. Diseña el procedimiento completo: cómo congelar la escritura, cómo copiar los datos de forma coherente, cómo arrancar el nuevo volumen y cómo verificar que el recuento y los ETag coinciden.

Compara dos estrategias: copiar el directorio con el servicio parado y migrar los objetos con mc mirror entre dos instancias. ¿Cuál elegirías si el volumen pesa 2 TB y solo puedes parar cinco minutos? Justifica la decisión.

Pista: copiar ficheros de /data con el servidor escribiendo puede producir una copia inconsistente. Y recuerda que mc mirror puede ejecutarse con el servicio antiguo todavía en marcha, seguido de una pasada final en delta.

9 · Resumen

  • MinIO se ejecuta con server /data; los datos deben vivir en un volumen, no en la capa del contenedor.
  • Las credenciales root se inyectan por entorno. minioadmin/minioadmin es solo para pruebas aisladas.
  • 9000 publica la API S3 y 9001 la consola; son superficies separadas.
  • /minio/health/live, ready y cluster miden cosas distintas; ninguno valida permisos.
  • Compose sirve para un nodo. Un clúster distribuido va con Kubernetes Operator o baremetal preparado.
  • docker compose down conserva el volumen; down -v lo destruye.
  • La consola es para explorar; la automatización y la operación repetible van por mc o la API.

10 · Preguntas frecuentes

¿Puedo cambiar la contraseña root después?

Sí: cambia MINIO_ROOT_PASSWORD en el entorno y reinicia el servicio. MinIO actualiza la credencial del usuario root al arrancar. Hazlo con el servicio accesible y actualiza también los secretos de tus herramientas. Si la pierdes y no puedes reiniciar, el acceso se recupera con el procedimiento de recuperación del despliegue; no hay una pregunta secreta.

¿Por qué la consola no muestra una sección que sí aparece en la documentación?

Porque la consola Community ha ido perdiendo funciones de administración en versiones recientes y la documentación puede corresponder a AIStor o a una versión anterior. Comprueba la versión del servidor con mc admin info y usa el comando equivalente de mc. En este curso la consola es una ayuda visual, no la fuente de verdad.

¿Cómo actualizo MinIO sin perder datos?

Fija la nueva etiqueta de imagen, haz una copia de seguridad verificada —no solo un docker commit— y recrea el contenedor con el mismo volumen. MinIO aplica migraciones de formato al arrancar; por eso conviene leer las notas de la versión y no saltar demasiadas releases a la vez. En producción, prueba primero en staging con una copia de los datos.

¿Puedo usar el puerto 80 para la API?

Sí, publicando -p 80:9000. El puerto interno no cambia; solo el mapeo. Ten en cuenta que el endpoint que configures en las aplicaciones debe incluir el puerto si no es el estándar. Para TLS, lo habitual es terminar en un proxy inverso o configurar certificados en MinIO, no cambiar el puerto a ciegas.

¿Este Compose sirve para producción?

Puede servir para una carga pequeña y no crítica, pero es un único punto de fallo y no incluye TLS, backups ni monitorización. Producción implica decidir durabilidad (erasure coding o réplica), TLS, usuarios de mínimo privilegio, alertas y un plan de restauración probado. El curso va construyendo esas piezas; el Compose de esta lección es el punto de partida, no el destino.
