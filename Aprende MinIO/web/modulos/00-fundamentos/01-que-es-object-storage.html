Qué es el almacenamiento de objetos

Módulo 0 · Fundamentos 🕐 30 minutos

1 · Introducción

Tu aplicación guarda los PDF de los clientes en una carpeta del servidor. Funciona durante meses. Un día hay dos servidores, luego cuatro, y el balanceador envía cada petición a uno distinto: la mitad de las descargas devuelven 404. Copias la carpeta a mano, montas NFS y aparece el siguiente problema: dos procesos escriben el mismo archivo y uno pisa al otro. Después llega el backup de 8 TB y ya no sabes ni cuánto tarda en restaurarse.

El almacenamiento de objetos existe para ese momento. No es un sistema de ficheros más rápido ni un disco de red: es un modelo distinto, diseñado para guardar blobs completos, identificados por una clave, con metadatos y acceso por HTTP. Su unidad de trabajo no es «abrir un archivo y escribir en el byte 4 096», sino «guardar este objeto entero» o «dame este objeto entero».

Ese cambio parece una limitación y en realidad es la fuente de su escalabilidad. En esta lección veremos qué es exactamente un objeto, en qué se diferencia de un fichero y de un bloque, por qué es inmutable, cuándo conviene usarlo y cuándo es la herramienta equivocada. Es la base de todo el curso: si confundes objeto con carpeta, los prefijos, el versionado y el lifecycle se convertirán en comandos memorizados sin modelo detrás.

Por qué empezar aquí

MinIO implementa la API S3, y S3 es un almacén de objetos, no un disco. Muchas decisiones que parecen rarezas —no hay rename, no puedes modificar un byte, borrar no siempre borra— se explican por este modelo. Entenderlo evita diseñar claves que luego no se pueden listar y evita usar object storage para cosas que pedían una base de datos.

2 · Teoría

La definición que importa

Un objeto es la terna datos + metadatos + clave. Nada más. Los datos son una secuencia de bytes opaca: a MinIO le da igual que sea un PDF, un vídeo o un Parquet. Los metadatos describen esos bytes: tipo de contenido, tamaño, fecha, checksum y pares clave-valor que tú aportas. La clave es el nombre único dentro de un bucket y, a diferencia de una ruta de fichero, es una cadena plana que puede contener barras.

+-------------------------------------------------------------+
| OBJETO                                                      |
|                                                             |
|  clave     2026/informes/acme/informe-anual-2026.pdf        |
|  datos     [ 2 411 233 bytes binarios, opacos para MinIO ]  |
|  metadatos Content-Type: application/pdf                    |
|            x-amz-meta-tenant: acme                          |
|            x-amz-meta-sha256: 4f9c...                       |
|            ETag: "9f2c1b..."                                |
+-------------------------------------------------------------+
| bucket: documentos                                          |
+-------------------------------------------------------------+

El bucket es el contenedor de primer nivel. Agrupa objetos, define políticas, versionado, lifecycle y cifrado. No hay buckets dentro de buckets. Un objeto pertenece a exactamente un bucket y se identifica por la pareja bucket + clave.

Tres formas de guardar bytes

ModeloUnidad de accesoOrganizaciónEncaja en
Fichero (NFS, SMB, ext4) Abrir, leer y escribir rangos; bloquear; renombrar Árbol de directorios con permisos POSIX Compartir documentos entre humanos, código, configuraciones
Bloque (EBS, iSCSI, SAN) Bloques de tamaño fijo, sin semántica de archivo Un dispositivo que el sistema operativo formatea Bases de datos, sistemas transaccionales, baja latencia
Objeto (S3, MinIO, GCS) PUT y GET del objeto completo (o rangos de bytes) Espacio plano: bucket + clave + metadatos Documentos, backups, imágenes, logs, data lakes, artefactos

La diferencia clave no es el tamaño: es la unidad de mutación. En un fichero puedes cambiar el byte 100 sin tocar el resto. En un objeto, cualquier cambio produce una versión nueva del objeto completo. MinIO sí permite leer un rango con una petición Range, pero no escribir un rango: no existe un PUT parcial.

Espacio plano, no árbol

Cuando subes 2026/informes/acme/informe.pdf, MinIO no crea tres directorios. Guarda un objeto cuya clave contiene barras. La consola y mc ls las muestran como carpetas porque es cómodo para humanos, pero esa jerarquía es una vista que se calcula al listar con un delimitador.

LO QUE VES                         LO QUE HAY
documentos/                        bucket documentos
├── 2026/                          ├── clave 2026/informes/acme/informe.pdf
│   ├── informes/                  ├── clave 2026/informes/globex/q1.pdf
│   │   ├── acme/                  ├── clave 2026/facturas/acme/f-001.pdf
│   │   │   └── informe.pdf        └── clave 2027/informes/acme/informe.pdf
│   │   └── globex/
│   │       └── q1.pdf
│   └── facturas/
│       └── acme/
│           └── f-001.pdf
└── 2027/

Consecuencia inmediata: no existe renombrar una carpeta. Renombrar 2026/ a 2025/ significaría copiar y borrar cada objeto, uno por uno. Lo veremos con detalle en Buckets y prefijos.

Inmutabilidad: reemplazar, no editar

Un objeto publicado no se modifica. Un PUT sobre una clave existente crea una nueva versión lógica que sustituye a la anterior como «actual». Los lectores ven la versión antigua o la nueva, nunca una mezcla a medio escribir. Esa atomicidad es gratuita y es la razón por la que object storage encaja tan bien con réplicas, cachés y CDNs.

PUT informe.pdf (v1)        PUT informe.pdf (v2)
        |                           |
        v                           v
   [ bytes v1 ]   <----------  [ bytes v2 ]   <- la clave apunta aquí
        |                           |
        +---- lectores ven v1       +---- lectores ven v2
              o v1 completo              o v2 completo, nunca mitad y mitad

Sin versionado, la versión anterior se vuelve inalcanzable en cuanto termina el PUT. Con versionado, MinIO conserva ambas y puedes recuperar la primera por su version ID. Lo veremos en Versionado y object locking.

Por qué escala

  • Sin jerarquía que bloquear: no hay inodos, directorios ni locks distribuidos. Cada objeto es independiente.
  • Metadatos separados de los datos: listar un prefijo no requiere abrir los objetos.
  • Paralelismo natural: cien clientes pueden escribir cien claves distintas sin coordinarse.
  • Durabilidad por software: MinIO usa erasure coding y réplica para sobrevivir a discos muertos, no un RAID del sistema operativo.
  • HTTP de por medio: cualquier lenguaje, cualquier contenedor y cualquier CDN hablan el mismo protocolo.

Los límites también existen y conviene saberlos desde el principio: la clave puede medir hasta 1 024 bytes y cada segmento entre barras hasta 255; un listado devuelve como máximo 1 000 claves por página; un PUT simple admite hasta 5 TiB en MinIO, y los objetos mayores requieren multipart. En AWS S3 el tamaño máximo de objeto es 5 TiB, así que si diseñas para la nube, ese es el techo portable.

Objeto no significa «solo para cosas enormes»

Puedes guardar un objeto de 10 bytes. Lo que no puedes es consultarlo por su contenido ni actualizarlo parcialmente. La pregunta correcta no es «¿es grande?», sino «¿lo leo y escribo entero, y me sirve identificarlo por una clave?».

3 · Ejemplo mínimo

Vamos a comprobar el modelo con un objeto real. Necesitas el MinIO de la lección Instalación y consola web y mc configurado como en mc y el primer bucket; si aún no los tienes, lee el ejemplo y vuelve después.

mc mb --ignore-existing local/documentos

mc cp ./informe-anual-2026.pdf \
  local/documentos/2026/informes/acme/

mc stat local/documentos/2026/informes/acme/informe-anual-2026.pdf

Línea a línea:

  • mc mb crea el bucket. --ignore-existing hace el comando idempotente: si ya existe, no falla.
  • mc cp copia un fichero local a un bucket. Como el destino termina en /, conserva el nombre del fichero y lo añade a la clave. Las «carpetas» intermedias se crean implícitamente: no hay ninguna llamada para crearlas.
  • mc stat pide los metadatos con un HEAD. No descarga los 2,4 MB.

Salida típica:

Name      : 2026/informes/acme/informe-anual-2026.pdf
Date      : 2026-02-11 09:14:22 CET
Size      : 2.4 MiB
ETag      : 9f2c1b7d4a0e5c63f8a1d2e3b4c5d6e7
Type      : file
Metadata  :
  Content-Type: application/pdf

Fíjate en tres cosas. La clave incluye toda la ruta, no solo el nombre. El Content-Type lo dedujo mc de la extensión, y es un metadato, no parte del fichero. Y el ETag identifica esa versión concreta: si vuelves a subir el mismo contenido, se repite; si cambias un byte, cambia.

Ahora sustituye el objeto por una versión corregida:

mc cp ./informe-anual-2026-corregido.pdf \
  local/documentos/2026/informes/acme/informe-anual-2026.pdf

mc stat local/documentos/2026/informes/acme/informe-anual-2026.pdf

El ETag es distinto y el tamaño puede serlo. No ha habido una «edición»: hay un objeto nuevo ocupando la misma clave. Si el bucket no tiene versionado, la versión anterior ya no se puede recuperar.

4 · Ejemplo real

El hilo conductor del curso es un almacén de documentos para un copiloto interno. La empresa recibe contratos, informes y facturas en PDF; un millón doscientos mil documentos al año, unos 8 TB, con picos de 40 subidas por segundo. Los usuarios buscan por cliente y por fecha, y el sistema debe conservar los contratos siete años sin posibilidad de alterarlos.

El diseño inicial que muchos equipos escriben es este:

/var/documentos/
├── acme/
│   ├── contrato.pdf
│   ├── contrato-final.pdf
│   ├── contrato-final-bueno.pdf
│   └── factura.pdf
└── globex/

Es un árbol de ficheros con nombres que mienten. No hay forma fiable de saber qué versión es la válida, la fecha no está en ningún sitio consultable y dos servidores no comparten el volumen. La traducción a objetos separa lo que identifica de lo que describe:

ElementoDiseño
Bucketdocumentos
Clave2026/contratos/acme/CTR-2026-0142.pdf
Metadatos de sistemaContent-Type: application/pdf
Metadatos de negociotenant=acme, sha256=…, doc-id=CTR-2026-0142
VersionadoActivado: cada corrección conserva la anterior
Object lockRetención COMPLIANCE de 7 años para contratos
LifecycleBorradores a 90 días; versiones antiguas a 1 año

Con esa estructura, las preguntas del negocio se convierten en listados:

  • «¿Qué contratos de acme hay en 2026?» → listar el prefijo 2026/contratos/acme/.
  • «Dame el informe anual» → GET de una clave exacta.
  • «¿Se modificó el contrato después de firmarse?» → versiones y ETag; con object lock, ni siquiera es posible.
  • «Borra los borradores de hace tres meses» → regla de lifecycle, no un script que alguien recuerda ejecutar.

El almacén no sustituye a la base de datos. En PostgreSQL viven usuarios, permisos y el índice de documentos con su doc-id, su tenant y su estado. En MinIO viven los bytes y una copia de los metadatos imprescindibles. Esa separación es deliberada: la base de datos consulta, el object store guarda.

La analogía del guardarropa

Un sistema de ficheros es un armario con cajones: puedes abrir un cajón y cambiar una camiseta. Object storage es un guardarropa con ticket: entregas un paquete cerrado y recibes un número (la clave). Para cambiar algo, entregas un paquete nuevo con el mismo número. Nunca abres el paquete por la mitad, y por eso puedo tener mil empleados atendiendo a la vez sin que se pisen.

6 · Errores habituales

1. «Los prefijos son carpetas»

Mal — renombrar una carpeta existente 
# ❌ No existe un rename de prefijo.
# ❌ Esto copia y borra objeto a objeto, y puede tardar horas.
mc mv local/documentos/2026/ local/documentos/2025/
Bien — copiar a las claves nuevas y verificar 
mc cp --recursive \
  local/documentos/2026/ \
  local/documentos/2025/

mc ls --recursive local/documentos/2025/ | wc -l
# Solo cuando el recuento cuadra:
mc rm --recursive --force local/documentos/2026/

El «rename» de un prefijo es una copia completa seguida de un borrado. Si el bucket tiene versionado, el borrado deja delete markers y el espacio no se libera. Diseña las claves para no tener que renombrar.

2. «Puedo editar el objeto en su sitio»

Mal — abrir, parchear y esperar que sea atómico 
// ❌ S3 no ofrece escritura por rangos ni append.
await client.putObject('documentos', key, Buffer.from('nuevo pie de página'))
Bien — descargar, transformar y volver a subir el objeto completo 
const original = await client.getObject('documentos', key)
const pdf = await renderWithFooter(original)

await client.putObject('documentos', key, pdf, pdf.length, {
  'Content-Type': 'application/pdf',
})

El segundo ejemplo sustituye el objeto entero y es atómico para los lectores. Aun así, dos procesos que hagan lo mismo se pisarán: para eso están el versionado y el bloqueo optimista, que veremos más adelante.

3. «Sirve como base de datos»

Mal — buscar por metadatos como si fuera SQL 
# ❌ Listar 1,2 millones de objetos para filtrar por tenant
mc ls --recursive local/documentos/ | grep acme
Bien — consultar en la base de datos y pedir la clave exacta 
SELECT object_key
FROM documents
WHERE tenant = 'acme' AND created_at >= '2026-01-01';

El listado de S3 no filtra por metadatos de usuario; solo por prefijo. Si necesitas consultas por atributos, mantén un índice en PostgreSQL y usa MinIO para los bytes.

4. «Borrar es reversible»

Mal — borrado recursivo sin versionado ni copia 
# ❌ Sin versionado, esto es definitivo.
mc rm --recursive --force local/documentos/2026/
Bien — versionado, object lock o réplica antes de borrar 
mc version enable local/documentos
mc ls --versions local/documentos/2026/
mc rm --recursive local/documentos/2026/   # deja delete markers

Con versionado, el borrado crea marcadores y los datos siguen ahí; con object lock, ni siquiera se pueden borrar hasta que expire la retención. La reversibilidad se decide antes del incidente, no después.

7 · Ejercicio guiado

Objetivo: clasificar los datos de un proyecto real y traducirlos a buckets, claves y metadatos antes de escribir código.

  1. Inventaria lo que guardas hoy. Crea una tabla con nombre, tamaño medio, frecuencia de escritura, frecuencia de lectura y si necesitas conservar versiones. 
    documento          tamaño   escribe   lee      versiones
contrato.pdf       1,8 MB   una vez   a veces  sí (7 años)
factura.pdf        300 KB   una vez   a veces  sí (7 años)
borrador.docx      2,1 MB   muchas    a veces  no
miniatura.jpg      80 KB    una vez   siempre  no
export.csv         40 MB    diaria    a veces  no
  2. Decide el bucket. Un bucket por dominio funcional, no uno por cliente ni uno por año: documentos para lo jurídico, media para miniaturas. Los clientes y los años van en la clave, no en el bucket.
  3. Diseña tres claves candidatas y elige una. 
    A) acme/2026/contrato/CTR-2026-0142.pdf
B) 2026/contratos/acme/CTR-2026-0142.pdf
C) CTR-2026-0142.pdf

    B permite listar «todos los contratos de 2026» y «los contratos de acme en 2026». A prioriza al cliente. C impide cualquier listado útil. La elección depende de la consulta dominante: en este curso usaremos B.

  4. Sube un objeto con metadatos de negocio y compruébalo. 
    mc cp --attr "tenant=acme;doc-id=CTR-2026-0142;sha256=4f9c" \
  ./contrato.pdf \
  local/documentos/2026/contratos/acme/CTR-2026-0142.pdf

mc stat local/documentos/2026/contratos/acme/CTR-2026-0142.pdf
    Name      : 2026/contratos/acme/CTR-2026-0142.pdf
Size      : 1.8 MiB
ETag      : 2b7e...
Metadata  :
  Content-Type: application/pdf
  X-Amz-Meta-Tenant: acme
  X-Amz-Meta-Doc-Id: CTR-2026-0142
  5. Comprueba qué operación no puedes hacer. Intenta renombrar el prefijo 2026/ a 2025/ sin copiar, y explica por qué no existe el comando. Después mide cuánto tarda un listado de 1 000 objetos con mc ls --recursive | Measure-Object (PowerShell) o | wc -l (bash).
  6. Escribe la política de borrado. Para cada fila del inventario, decide: versionado sí/no, retención, y si el borrado debe ser reversible. Los contratos van a COMPLIANCE siete años; los borradores expiran a 90 días; las miniaturas se pueden regenerar.

Criterio de éxito

Si puedes responder «¿qué clave pido para el contrato de acme de 2026?» sin listar el bucket, el diseño es correcto. Si necesitas recorrer objetos para encontrar uno, la clave está mal pensada.

8 · Reto

🎯 El informe que se reescribe cada noche

Un proceso genera cada noche un PDF de 400 páginas (unos 60 MB) a partir de 400 plantillas HTML. Solo cambian dos o tres páginas al día, pero el PDF completo se regenera y se sube con la misma clave. El equipo se queja de que el almacenamiento crece sin control y de que descargar el informe tarda demasiado.

Diseña una estructura de objetos que permita: (a) servir el informe completo, (b) servir una página suelta sin descargar 60 MB, (c) conservar el histórico sin duplicar 60 MB por noche, y (d) saber qué páginas cambiaron entre dos versiones. No hace falta implementarlo: escribe las claves, los metadatos y qué operación usarías para cada caso.

Pista: un objeto no tiene que coincidir con un fichero. Piensa en granularidad: ¿qué unidad cambia de verdad? Y recuerda que el versionado guarda objetos completos, no diferencias.

9 · Resumen

  • Un objeto es bytes + metadatos + clave, dentro de un bucket. No hay jerarquía real: las barras son parte de la clave.
  • La unidad de mutación es el objeto completo: PUT sustituye, no edita; los lectores ven una versión íntegra.
  • Object storage brilla con documentos, backups, media, data lakes y artefactos; no sirve para transacciones ni para escritura parcial.
  • Escala porque no hay locks ni inodos: cada clave es independiente y el acceso es HTTP.
  • Sin versionado, sobrescribir o borrar es definitivo. La reversibilidad se diseña antes del incidente.
  • La clave es una decisión de producto: determina qué listados puedes hacer y cuánto cuesta cambiar de idea.

10 · Preguntas frecuentes

¿Puedo montar MinIO como una unidad de red y trabajar con él?

Existen herramientas como s3fs o rclone mount, pero no convierten S3 en un sistema de ficheros POSIX. No hay bloqueos, el rendimiento es irregular y una aplicación que espera fsync o escritura por rangos fallará. Úsalo para copiar ficheros, no para ejecutar una base de datos ni para editar documentos en sitio.

Si es inmutable, ¿cómo corrijo un documento?

Descargas el objeto, lo modificas en memoria o en disco y subes el resultado con la misma clave. Eso crea una versión nueva. Si el bucket tiene versionado, la anterior sigue accesible por su version ID; si no, se pierde. La inmutabilidad se refiere al objeto ya escrito, no a que no puedas publicar otra versión.

¿MinIO es fuertemente consistente?

Sí: las operaciones de lectura ven la última escritura confirmada, incluidas las de listado, sin el retardo que S3 tuvo históricamente. Eso simplifica mucho el código, pero no convierte dos escrituras concurrentes en una transacción: la última gana. Para evitar perder cambios necesitas versionado, claves únicas o bloqueo optimista.

¿Merece la pena para muchos archivos pequeños?

Funciona, pero cada objeto tiene un coste fijo de metadatos y de petición. Miles de ficheros de 1 KB con muchas lecturas aleatorias suelen rendir mejor en una base de datos o empaquetados en un archivo mayor (un ZIP, un Parquet, un tar). Si los necesitas sueltos, al menos agrúpalos por prefijo para que los listados sean baratos.

¿Sustituye a mi base de datos?

No. Sustituye al disco donde guardabas los blobs. La base de datos sigue siendo el lugar para usuarios, permisos, estados y consultas por atributos. La arquitectura habitual es una fila en PostgreSQL con la clave del objeto y los metadatos consultables, y los bytes en MinIO.
