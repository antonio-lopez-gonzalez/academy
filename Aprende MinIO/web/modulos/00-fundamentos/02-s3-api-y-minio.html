La API S3 y MinIO

Módulo 0 · Fundamentos 🕐 35 minutos

1 · Introducción

La pregunta que más se repite al empezar es «¿MinIO es lo mismo que S3?». La respuesta corta es no: S3 es una API, un contrato HTTP con operaciones, firmas y códigos de error. Amazon S3 es el servicio original que la define; MinIO es una implementación independiente de ese contrato. Igual que «SQL» no es un producto sino un lenguaje, «S3» no es un producto sino un protocolo.

Esa distinción tiene una consecuencia enorme para tu código: si usas la API S3 y evitas las extensiones propietarias, la misma aplicación funciona contra MinIO en tu portátil, contra MinIO en tu centro de datos y contra AWS en la nube. Cambiar de proveedor debería ser cambiar un endpoint y unas credenciales, no reescribir la capa de almacenamiento.

En esta lección veremos qué piezas componen el modelo —bucket, objeto, región, endpoint—, por qué existen dos formas de construir la URL (path-style y virtual-host), qué significa exactamente «compatible con S3», qué diferencia hay entre MinIO Community y AIStor, y por qué el curso insiste en un detalle tan aburrido como el forcePathStyle.

Por qué existe esta lección

La mayoría de los errores al conectar una aplicación con MinIO no son de MinIO: son de configuración del cliente. Un endpoint con https cuando el servidor es HTTP, una región que no coincide con la firma o un cliente que intenta documentos.localhost producen errores crípticos. Entender el contrato te permite leerlos.

2 · Teoría

El contrato: recursos y verbos

S3 es una API REST. Todo se reduce a dos tipos de recurso y unos pocos verbos HTTP:

RecursoURIOperaciones habituales
ServicioGET /Listar buckets
Bucket/{bucket}Crear, borrar, consultar versión, listar objetos
Objeto/{bucket}/{key}PUT, GET, HEAD, DELETE, multipart

Los parámetros de consulta cambian la operación: ?list-type=2 lista objetos, ?uploads inicia una subida multipart, ?versioning gestiona el versionado. Las cabeceras llevan metadatos y la autenticación. La firma SigV4 incluye método, ruta, cabeceras y hash del cuerpo, de modo que una petición no se puede alterar sin invalidarla.

PUT /documentos/2026/informes/acme/informe.pdf HTTP/1.1
Host: localhost:9000
Authorization: AWS4-HMAC-SHA256 Credential=.../20260211/us-east-1/s3/aws4_request, ...
Content-Type: application/pdf
x-amz-meta-tenant: acme
x-amz-content-sha256: 4f9c...

Las cinco palabras del modelo

TérminoQué esDónde vive
EndpointURL base del servicioConfiguración del cliente: http://localhost:9000
RegiónÁmbito geográfico usado en la firmaConfiguración del cliente; MinIO usa una región propia
BucketContenedor de objetos y políticasServidor
ClaveNombre único del objeto dentro del bucketServidor, dentro de la URL
CredencialesAccess key + secret keyCliente, nunca en el código ni en el repositorio

La región merece un comentario. En AWS el bucket pertenece a una región concreta y el cliente debe firmar para ella. MinIO se despliega normalmente como una región lógica (por defecto us-east-1) y valida la firma contra la región configurada. Si tu cliente dice eu-west-1 y el servidor espera us-east-1, la firma puede fallar con AuthorizationHeaderMalformed. La solución no es «probar regiones»: es alinear la configuración.

Path-style frente a virtual-host

Hay dos formas de poner el bucket en la URL:

PATH-STYLE
http://localhost:9000/documentos/2026/informes/acme/informe.pdf
                      ^^^^^^^^^^ bucket en la ruta

VIRTUAL-HOST
http://documentos.localhost:9000/2026/informes/acme/informe.pdf
       ^^^^^^^^^^ bucket como subdominio

AWS (virtual-host obligatorio en la práctica)
https://documentos.s3.eu-west-1.amazonaws.com/2026/informes/acme/informe.pdf

Virtual-host permite balancear por DNS y repartir buckets entre servidores, pero exige un registro DNS comodín (*.midominio.com) y un certificado que cubra los subdominios. En local, documentos.localhost no resuelve por defecto y el cliente falla con getaddrinfo ENOTFOUND. Por eso MinIO y la mayoría de clientes usan path-style en desarrollo: el bucket va en la ruta y todo apunta a un único host.

La regla práctica

Contra MinIO en local o en una IP: path-style activado. Contra AWS: virtual-host (o path-style si el SDK lo permite y el bucket no tiene puntos). En AWS SDK v3 se controla con forcePathStyle: true; en mc, con mc alias set --path on.

Qué significa «compatible con S3»

No existe un certificado único. «Compatible» suele significar que las operaciones del núcleo funcionan igual: buckets, objetos, multipart, versionado, lifecycle, políticas, presigned URLs y notificaciones. Las diferencias aparecen en los bordes:

ÁreaAWS S3MinIO Community

Tamaño máximo de objeto5 TiB50 TiB (multipart); 5 TiB por PUT simple
ACLsModelo completo, junto con políticasSoporte limitado; se prefieren políticas IAM

Para el curso, la regla es: usa el núcleo S3 y trata las funciones exclusivas como optimizaciones opcionales. Si tu aplicación necesita Object Lambda para funcionar, no es portable; si solo usa PutObject, GetObject, versionado y lifecycle, cambiar de proveedor es configuración.

Un servidor, dos puertos

                     :9000                         :9001
  Aplicación  -------------->  +-------------+  <--------------  Navegador
  mc / SDK    API S3 (HTTP)    |    MinIO    |   Consola web (HTTP)
  curl / AWS CLI               +------+------+
                                      |
                                      v
                               /data (volumen)
                            objetos + metadatos

El puerto 9000 habla S3 y es el que usan las aplicaciones, mc y los SDK. El 9001 sirve la consola web. Son procesos y superficies distintas: puedes cerrar la consola al exterior y mantener la API accesible, y es lo recomendable en producción.

Sobre el despliegue: Docker Compose sirve para un solo nodo, que es lo que necesitas para desarrollar. Un clúster distribuido de MinIO no se monta con Compose; se despliega con el Kubernetes Operator o sobre máquinas con los volúmenes locales correctamente preparados. Lo veremos en Modo distribuido.

3 · Ejemplo mínimo

El cliente más pequeño posible con AWS SDK v3 contra MinIO. Instala las dos dependencias:

npm install @aws-sdk/client-s3
npm pkg set type=module

Y este es el programa completo:

import { S3Client, ListBucketsCommand } from '@aws-sdk/client-s3'

const s3 = new S3Client({
  endpoint: 'http://localhost:9000',
  region: 'us-east-1',
  forcePathStyle: true,
  credentials: {
    accessKeyId: process.env.MINIO_ROOT_USER,
    secretAccessKey: process.env.MINIO_ROOT_PASSWORD,
  },
})

const { Buckets } = await s3.send(new ListBucketsCommand({}))
console.log(Buckets?.map((b) => b.Name))

Línea a línea:

  • endpoint sustituye a la URL de AWS. Debe incluir esquema y puerto, y coincidir con lo que escucha el servidor.
  • region no elige un centro de datos en MinIO: entra en la firma SigV4. Usa la misma que configuraste en el servidor.
  • forcePathStyle: true construye http://localhost:9000/documentos/… en lugar de http://documentos.localhost:9000/…. Sin esto, el cliente intenta resolver un subdominio que no existe.
  • credentials se leen del entorno. En esta fase son las root del arranque; en el módulo 3 las sustituiremos por un usuario de mínimo privilegio.
  • ListBucketsCommand es una operación de servicio: GET /. Devuelve los buckets a los que esas credenciales tienen acceso.

Salida esperada:

[ 'documentos' ]

Si obtienes ENOTFOUND, revisa forcePathStyle. Si obtienes SignatureDoesNotMatch, revisa credenciales y región. Si obtienes ECONNREFUSED, el contenedor no está escuchando en ese puerto. Casi todos los problemas iniciales están en esas tres cosas.

4 · Ejemplo real

El almacén de documentos debe poder ejecutarse en local con MinIO y desplegarse en AWS sin tocar el código. La clave es aislar la construcción del cliente en un único módulo y leer todo de variables de entorno:

// lib/s3.mjs
import { S3Client } from '@aws-sdk/client-s3'

export function createS3Client(env = process.env) {
  const endpoint = env.S3_ENDPOINT || undefined

  return new S3Client({
    endpoint,
    region: env.S3_REGION || 'us-east-1',
    forcePathStyle: env.S3_FORCE_PATH_STYLE !== 'false',
    credentials: {
      accessKeyId: env.S3_ACCESS_KEY,
      secretAccessKey: env.S3_SECRET_KEY,
    },
  })
}

El .env.example del proyecto documenta los dos escenarios:

# Local con MinIO
S3_ENDPOINT=http://localhost:9000
S3_REGION=us-east-1
S3_FORCE_PATH_STYLE=true
S3_ACCESS_KEY=app-documentos
S3_SECRET_KEY=cambiar-en-local

# AWS (sin endpoint: el SDK usa el de la región)
# S3_ENDPOINT=
# S3_REGION=eu-west-1
# S3_FORCE_PATH_STYLE=false

Path-styletruefalseSin DNS comodín en local

La prueba de portabilidad no es «compila en local»: es ejecutar la misma suite contra los dos backends. Un test que sube un objeto, lo lee, comprueba su ETag y lo borra debería pasar sin cambios. Si necesita un comportamiento especial para cada uno, tienes acoplamiento escondido.

El nombre del bucket también es portable… con matices

En AWS los nombres son únicos globalmente y no pueden contener puntos si usas TLS virtual-host. En MinIO basta con que sean únicos en tu despliegue. Si eliges documentos.prod, funcionará en local y puede fallar en AWS por el certificado. Usa nombres simples, en minúsculas y sin puntos.

6 · Errores habituales

1. Virtual-host contra localhost

Mal — el cliente busca un subdominio que no existe 
const s3 = new S3Client({
  endpoint: 'http://localhost:9000',
  forcePathStyle: false,   // ❌ intenta documentos.localhost
  region: 'us-east-1',
})
Bien — path-style en local 
const s3 = new S3Client({
  endpoint: 'http://localhost:9000',
  forcePathStyle: true,
  region: 'us-east-1',
})

El error típico es getaddrinfo ENOTFOUND documentos.localhost. No es un fallo de MinIO: el cliente está pidiendo otro host. En AWS ocurre lo contrario; allí virtual-host es el modo normal.

2. Mezclar HTTP y HTTPS

Mal — el servidor habla HTTP y el cliente espera TLS 
# ❌ El contenedor escucha en http://localhost:9000
export S3_ENDPOINT=https://localhost:9000
Bien — el esquema debe coincidir con el servidor 
export S3_ENDPOINT=http://localhost:9000   # desarrollo
# En producción: https://minio.example.com, con certificado válido

El síntoma es un error de TLS (ERR_SSL_WRONG_VERSION_NUMBER o unable to verify the first certificate). MinIO no habla HTTPS porque sí: hay que darle certificados. Lo veremos en TLS y cifrado.

3. Suponer paridad total con AWS

Mal — usar una función que MinIO no implementa 
// ❌ S3 Object Lambda / Inventory no forman parte del núcleo portable
await s3.send(new SelectObjectContentCommand({ /* ... */ }))
Bien — núcleo S3 y pruebas contra ambos 
await s3.send(new GetObjectCommand({ Bucket, Key }))
await s3.send(new PutObjectCommand({ Bucket, Key, Body }))

Antes de adoptar una función, comprueba si es del núcleo o del producto. Si solo existe en AWS, tu arquitectura deja de ser portable y debe ser una decisión consciente, no un descubrimiento en el despliegue.

4. Montar un clúster con Compose

Mal — escalar réplicas de Compose y llamarlo distribuido 
# ❌ Esto no es un clúster MinIO soportado.
services:
  minio:
    image: quay.io/minio/minio
    deploy:
      replicas: 4
Bien — Compose para un nodo; Operator para un clúster 
services:
  minio:
    image: quay.io/minio/minio
    command: server /data --console-address ":9001"
    volumes:
      - minio-data:/data

Cuatro contenedores con cuatro volúmenes independientes no comparten erasure coding ni quorum: son cuatro servidores sueltos. El modo distribuido real se despliega con el Kubernetes Operator o con volúmenes locales preparados en cada nodo.

7 · Ejercicio guiado

Objetivo: comprobar el contrato S3 con tres clientes distintos —curl, mc y el SDK— contra el mismo servidor.

  1. Comprueba que la API está viva, sin credenciales. 
    curl -i http://localhost:9000/minio/health/live
    HTTP/1.1 200 OK
Server: MinIO
...

    El health check no demuestra que puedas autenticarte; solo que el proceso responde.

  2. Configura el alias con path-style explícito. 
    mc alias set local http://localhost:9000 \
  "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD" --path on

mc alias list local

    La salida incluye Path: on. Ese ajuste es el equivalente a forcePathStyle: true.

  3. Pregunta al servidor por su estado. 
    mc admin info local
    ●  localhost:9000
   Uptime: 3 hours
   Version: RELEASE.2025-...
   Network: 1/1 OK
   Drives: 1/1 OK

1 node, 1 drive online

    Es una operación administrativa, no S3 puro. Con un usuario sin permisos de admin fallará aunque pueda leer objetos.

  4. Ejecuta el listado con SDK y captura la petición. Guarda el ejemplo mínimo en list-buckets.mjs y ejecútalo con node --env-file=.env list-buckets.mjs. Después repite con depuración para ver la URL construida: 
    DEBUG=@aws-sdk/* node list-buckets.mjs 2>&1 | Select-String "localhost"

    Debes ver http://localhost:9000/, no un subdominio por bucket.

  5. Cambia solo el endpoint y comprueba que el cliente se adapta. Apunta S3_ENDPOINT a un MinIO en otro puerto (por ejemplo, el 9100 de un segundo contenedor) y vuelve a listar. El código no cambia; la configuración sí. Ese es el objetivo de la lección.

8 · Reto

🎯 Un arnés de portabilidad

Escribe una suite de pruebas que se ejecute contra MinIO y, sin modificar el código, contra AWS S3. Debe cubrir: crear un bucket con nombre único, subir un objeto con Content-Type y metadatos, leerlo, comprobar el ETag, listar por prefijo y borrarlo. Cada backend se selecciona solo con variables de entorno.

Además, documenta qué pruebas has tenido que marcar como opcionales y por qué. El objetivo no es que todo pase en ambos, sino descubrir dónde empieza la incompatibilidad y dejarlo escrito.

Pista: usa un prefijo con timestamp para no chocar con ejecuciones anteriores, y no borres el bucket hasta que la suite termine. Para el ETag, recuerda que un objeto subido en varias partes no devuelve un MD5 simple.

9 · Resumen

  • S3 es una API REST, no un producto. MinIO la implementa y añade su propia operación.
  • El modelo se reduce a endpoint + región + bucket + clave + credenciales.
  • Path-style pone el bucket en la ruta y es lo práctico en local; virtual-host lo pone en el subdominio y es lo habitual en AWS.
  • La compatibilidad cubre el núcleo; las funciones gestionadas de AWS no son portables.
  • MinIO Community es AGPLv3; AIStor es la edición comercial. El curso usa Community.
  • 9000 es la API S3; 9001 es la consola. En producción, la consola no se expone.
  • Compose es para un nodo; un clúster distribuido va con Kubernetes Operator o baremetal preparado.

10 · Preguntas frecuentes

¿Puedo usar la AWS CLI contra MinIO?

Sí. La AWS CLI es un cliente S3 más: configura --endpoint-url http://localhost:9000, una región y credenciales. Para uso diario en el curso preferimos mc porque sus comandos son más directos para administración, pero la CLI de AWS es una buena forma de comprobar que el comportamiento es el estándar.

Si MinIO es AGPLv3, ¿tengo que publicar mi aplicación?

No por usarlo como servicio. La obligación de la AGPL aparece si modificas MinIO y distribuyes esa versión o la ofreces como servicio de red: en ese caso debes facilitar el código de la versión modificada. Tu aplicación, que habla con MinIO por HTTP, es un programa separado. Es un resumen divulgativo; consulta la licencia completa y a tu equipo legal si el uso es comercial.

¿Qué región debo poner si no uso AWS?

La que tenga configurada el servidor, normalmente us-east-1 por defecto. En MinIO la región no elige ubicación física: forma parte de la firma. Usa una constante en la configuración y no la cambies entre cliente y servidor. Si despliegas varias regiones reales, cada una tendrá su endpoint y su valor.

¿Por qué hay dos puertos y no uno?

Porque la API S3 y la consola son superficies distintas con modelos de autenticación distintos. La API usa firma SigV4 por petición; la consola usa sesión de navegador. Separarlas permite cerrar la consola al exterior, ponerla detrás de una VPN y dejar solo la API accesible para las aplicaciones.

¿Necesito Internet para usar MinIO?

No. MinIO funciona completamente en local o en una red aislada. Solo necesitas Internet para descargar la imagen y las dependencias. Esto es una ventaja frente a la nube y una razón por la que encaja en entornos regulados, siempre que asumas la operación: backups, actualizaciones y monitorización son tu responsabilidad.
