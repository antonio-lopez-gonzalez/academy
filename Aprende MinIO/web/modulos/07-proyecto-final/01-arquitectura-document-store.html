Arquitectura del document store

Módulo 7 · Proyecto final 🕐 40 minutos

1 · Introducción

Un almacén de documentos no es una carpeta compartida con una API delante. Es un sistema donde el objeto, sus metadatos y el catálogo evolucionan por separado; donde una subida puede fallar a medias; donde un borrado debe poder deshacerse; y donde el coste de equivocarse en la clave se paga durante años.

En este módulo construimos documentos, el almacén que hemos ido preparando: subida directa con presigned URLs, catálogo de metadatos, versionado, lifecycle, eventos y pruebas. El proyecto ejecutable vive en proyectos/document-store/ y se levanta con un solo docker compose up más npm run api.

Esta primera lección no escribe la API: toma las decisiones. Qué buckets existen, cómo se llama cada objeto, qué guarda el catálogo, qué garantiza MinIO y qué tenemos que garantizar nosotros. El resto del módulo implementa ese contrato.

Por qué existe esta lección

Porque el 80 % de los problemas de un almacén vienen del modelo de datos, no del SDK. Una clave que depende del nombre original, un catálogo que se cree la fuente de verdad o un bucket público por comodidad se arreglan mal y tarde. Diseñarlo antes cuesta una hora; corregirlo en producción cuesta una migración.

Modelo de claves: el contrato más duradero

La clave es el identificador permanente del objeto. Debe ser única, estable, segura y fácil de listar por prefijo. El modelo canónico que buscamos es:

{tenant}/{año}/{tipo}/{id}-{nombre-seguro}
acme/2026/factura/7f2c9a1e-informe.pdf

El proyecto de referencia simplifica un nivel: usa el mes en lugar del tipo y guarda el tipo en el catálogo, porque un documento puede tener varios tipos de negocio y no queremos duplicar la fuente de verdad:

{tenant}/{AAAA}/{MM}/{uuid}-{nombre-seguro}
acme/2026/11/7f2c9a1e-4b2d-4f7a-9c1e-3d5a6b7c8d9e-informe.pdf

Ambos cumplen los mismos principios: el tenant delimita el espacio, la fecha permite lifecycle y listados, el id lo genera el servidor y el nombre se sanea. El tipo es un atributo consultable, no una carpeta.

ComponenteReglaPor qué
tenant^[a-z0-9][a-z0-9-]{1,30}$Evita mayúsculas, barras y traversal.
año/mesUTC, dos dígitos el mesListados estables y lifecycle por prefijo.
idUUID generado por el servidorEl cliente no elige la ruta ni puede adivinarla.
nombreNFD, sin acentos, [a-zA-Z0-9._-], 120 caracteresCompatible, legible y sin sorpresas.
prefijo tmp/Reservado para restos y pruebasLifecycle lo expira sin tocar documentos reales.

Un prefijo no es una carpeta: es una convención sobre cadenas. No hay renombrado ni movimiento atómico; «mover» un objeto es copiar y borrar. Diseña la clave para que nunca necesites renombrarla.

Buckets y prefijos

bucket: documentos
├── acme/2026/11/7f2c…-informe.pdf
├── acme/2026/11/9a1b…-contrato.pdf
├── globex/2026/10/3c4d…-factura.pdf
└── tmp/                      <- lifecycle: expira en 1 día

Un solo bucket simplifica políticas, réplica y backup. Los tenants se separan por prefijo y las políticas IAM pueden limitar el acceso a arn:aws:s3:::documentos/acme/*. Un bucket por tenant solo se justifica si necesitas cuotas, cifrado o retención radicalmente distintos, o si el número de tenants es pequeño y estable.

Para cuarentena o derivados, añade buckets separados (documentos-cuarentena, documentos-derivados) con sus propias políticas. No mezcles contenido aprobado con contenido sin escanear en el mismo prefijo público.

El catálogo del proyecto es un JSON con escritura atómica y una cola de mutaciones; es didáctico y suficiente para el curso. En producción sería PostgreSQL, con índices por tenant, estado y fecha. MinIO no sustituye a una base de datos: listar millones de objetos para filtrar por tipo es lento y caro.

  "etag": "9f3c2ab1c4d5e6f708192a3b4c5d6e7f",

El flujo completo

POST /documents            API: valida, genera id y clave, crea catálogo (pending)
                           devuelve presigned PUT
        |
        v
PUT uploadUrl              navegador -> MinIO (sin credenciales)
        |
        v
POST /documents/:id/complete
                           API: statObject, valida tamaño real,
                           catálogo -> stored, webhook document.stored
        |
        v
GET /documents/:id         API: ficha + presigned GET
DELETE /documents/:id      API: removeObject -> delete marker, catálogo -> deleted

Hay dos momentos de verdad: el objeto existe cuando MinIO responde al PUT, y el documento está «stored» cuando el catálogo lo confirma tras statObject. Entre ambos, el estado es pending y la descarga no debe anunciarse como disponible.

Consistencia y reconciliación

MinIO es fuertemente consistente para las operaciones de objeto: un PUT confirmado se lee después. El catálogo, en cambio, es otro sistema y puede fallar entre la escritura del objeto y la del registro. Por eso el estado pending es explícito y el reconciliador compara:

  • Documentos pending con objeto existente y tamaño válido → completar.
  • Documentos stored sin objeto → marcar missing y alertar.
  • Objetos en el bucket sin registro → crear un registro huérfano para investigar.

Esta rutina es la que convierte un sistema «que funciona cuando todo va bien» en uno operable. Se ejecuta al arrancar y periódicamente; nunca borra datos por su cuenta.

3 · Ejemplo mínimo

El proyecto ya trae el bucket, el versionado y el lifecycle. Levántalo y comprueba el estado con tres órdenes:

cd proyectos/document-store
docker compose up -d
npm install
npm run bootstrap

bucket documentos listo en 127.0.0.1:9000
versionado: Enabled
reglas de lifecycle: expire-tmp, expire-noncurrent

Ese resultado confirma las tres decisiones estructurales: un bucket, versionado activo y dos reglas de lifecycle. Puedes verlo también con mc:

mc alias set local http://localhost:9000 minioadmin minioadmin123
mc version info local/documentos
mc ilm rule ls local/documentos

Y una clave de ejemplo, generada con las reglas del proyecto, se ve así:

import { documentKey } from "./src/keys.mjs";

documentKey({
  tenant: "acme",
  filename: "../../Informe Año.pdf",
  id: "7f2c9a1e-4b2d-4f7a-9c1e-3d5a6b7c8d9e",
  date: new Date("2026-11-05T12:00:00Z"),
});
// acme/2026/11/7f2c9a1e-4b2d-4f7a-9c1e-3d5a6b7c8d9e-Informe-Ano.pdf

Fíjate en lo que desapareció: ../../, los acentos y los espacios. La clave no puede escapar del prefijo del tenant aunque el nombre original lo intente.

4 · Ejemplo real

Así se ve un documento recorriendo el sistema desde que el usuario lo elige hasta que otro usuario lo descarga. Los estados del catálogo son la columna vertebral:

MomentoObjeto en MinIOCatálogoQué puede hacer la API
Se crea la fichaNo existependingDevolver la URL de subida; no descargar.
El navegador subeExiste, aún sin validarpendingNada nuevo; la URL de subida ya se usó.

Se restauraVersión recuperadastoredDescarga de nuevo.

La API del proyecto separa las operaciones en dos grupos: las que hablan con el catálogo y las que hablan con MinIO. Esa separación permite probar la validación sin servidor y sustituir el catálogo sin tocar el almacenamiento.

src/keys.mjs      reglas puras: tenant, nombre, tipo, tamaño, clave
src/catalog.mjs   persistencia del catálogo (JSON atómico)
src/storage.mjs   MinIO: bucket, versionado, lifecycle, presign, stat
src/api.mjs       HTTP: rutas, estados, errores
test/*.test.mjs   node --test, sin MinIO

Un detalle que marca la diferencia en operación: la API nunca confía en el tamaño declarado por el cliente. Al completar hace statObject y compara el tamaño real con el máximo. Si el objeto no existe, devuelve 409; si supera el límite, 413. El cliente puede mentir en el JSON, pero no en los bytes que MinIO almacenó.

Para el tenant acme, la política de producción debería permitir solo su prefijo. En el curso se usa root por comodidad; el README lo advierte y la lección Usuarios y políticas explica cómo crear el usuario acotado. El código no cambia: cambian las credenciales del entorno.

El tipo, en el catálogo

El proyecto no incluye el tipo en la clave porque un mismo documento puede clasificarse de varias formas con el tiempo. Si tu dominio exige que el tipo sea parte de la ruta (por ejemplo, para lifecycle por tipo), usa {tenant}/{año}/{tipo}/{id}-{nombre} y asume que cambiar de tipo implica una nueva clave.

6 · Errores habituales

1. Usar el nombre original como clave

Mal — colisiones y traversal 
const key = `${tenant}/${body.filename}`;
// acme/../../etc/passwd
// acme/informe.pdf  (dos tenants suben el mismo nombre y se pisan)
Bien — id del servidor y nombre saneado 
const id = crypto.randomUUID();
const key = documentKey({ tenant, filename, id });
// acme/2026/11/7f2c…-informe.pdf

El nombre visible para el usuario se guarda en el catálogo; la clave es un identificador, no una ruta de confianza.

2. Suponer que prefijo es carpeta

Mal — «mover» renombrando 
# ❌ no existe un rename de objetos
mc mv local/documentos/acme/2026/11/informe.pdf local/documentos/acme/2026/11/final.pdf
Bien — copiar y borrar, o mejor: no renombrar 
mc cp local/documentos/acme/2026/11/informe.pdf \
      local/documentos/acme/2026/11/final.pdf
mc rm local/documentos/acme/2026/11/informe.pdf

Cada «movimiento» crea una versión nueva y deja la anterior. Si el nombre puede cambiar, guarda el nombre de presentación en el catálogo y deja la clave estable.

3. Confiar en el tamaño que declara el cliente

Mal — validar solo el JSON de entrada 
assertSize(body.size, MAX); // el cliente puede decir 1024 y subir 2 GB
Bien — verificar el objeto real al completar 
const stat = await statObject(client, config, doc.key);
if (!stat) throw new HttpError(409, "objeto no subido");
if (stat.size > config.maxUploadBytes) throw new HttpError(413, "demasiado grande");

La validación de entrada evita trabajo inútil; la verificación de salida es la que protege el almacén.

4. Hacer público el bucket para descargar

Mal — permiso de lectura global 
mc anonymous set download local/documentos
# cualquiera con la clave puede leer todos los tenants
Bien — bucket privado y URL firmada por documento 
const url = await client.presignedGetObject("documentos", doc.key, 300);

La URL caduca y solo permite GET sobre esa clave. El bucket sigue cerrado y la política se puede auditar.

7 · Ejercicio guiado

Objetivo: levantar la infraestructura del proyecto, comprobar el modelo de claves y verificar que el bucket nace con versionado y lifecycle.

  1. Arranca MinIO y la API: 
    cd proyectos/document-store
docker compose up -d
npm install
npm run api

    La API escucha en http://localhost:7072. En otra terminal, curl http://localhost:7072/health debe devolver {"status":"ok","bucket":"documentos"}.

  2. Comprueba versionado y lifecycle: 
    mc alias set local http://localhost:9000 minioadmin minioadmin123
mc version info local/documentos
mc ilm rule ls local/documentos

    Espera Enabled y las reglas expire-tmp (1 día) y expire-noncurrent (30 días).

  3. Prueba las reglas de clave en Node: 
    node --input-type=module -e "
import { documentKey } from './src/keys.mjs';
console.log(documentKey({ tenant: 'acme', filename: '../Año.pdf', id: '123e4567-e89b-12d3-a456-426614174000', date: new Date('2026-11-05') }));
"

    Salida esperada: acme/2026/11/123e4567-e89b-12d3-a456-426614174000-Ano.pdf. No aparece .. ni el acento.

  4. Crea un documento y observa la clave: 
    curl -s -X POST http://localhost:7072/documents \
  -H "Content-Type: application/json" \
  -d '{"tenant":"acme","filename":"informe.pdf","contentType":"application/pdf","size":2048}'

    La respuesta incluye key con el patrón acme/2026/11/<uuid>-informe.pdf y una uploadUrl que caduca en 900 s.

  5. Lista el prefijo del tenant: 
    mc ls --recursive local/documentos/acme/

    Verás los objetos por año y mes. Ese es el único «árbol» que existe: una convención de prefijos, no carpetas reales.

  6. Revisa el catálogo: 
    cat data/catalog.json

    Comprueba que el documento está en pending hasta completar la subida. El catálogo y el bucket son dos sistemas: mantenerlos coherentes es el trabajo de la API y del reconciliador.

8 · Reto

🎯 Un modelo para dos negocios incompatibles

La empresa A necesita que los documentos se organicen por tipo (factura, contrato, informe) y que el lifecycle expire las facturas a los siete años. La empresa B necesita que el tipo cambie con el tiempo y que nada se borre antes de una auditoría. Diseña un único modelo de claves y catálogo que soporte ambos sin duplicar buckets ni romper el versionado.

Decide si el tipo va en la clave, en una etiqueta o solo en el catálogo; cómo aplicas lifecycle por tipo sin una regla por tenant; y qué pasa cuando un documento cambia de tipo. Justifica la respuesta con el coste de migración y con la reversibilidad de cada opción.

Pista: el lifecycle filtra por prefijo y por etiquetas, no por columnas de una base de datos. Si el tipo debe gobernar la retención, probablemente tenga que existir en el objeto, no solo en el catálogo.

9 · Resumen

  • La clave es un identificador permanente: tenant, fecha, UUID y nombre saneado.
  • Un prefijo no es una carpeta; no hay renombrado atómico ni movimiento.
  • El bucket es privado; las descargas usan presigned GET cortos.
  • El catálogo guarda lo que MinIO no puede consultar: tipo, estado, propietario y fechas.
  • El estado pending y el reconciliador cubren el hueco entre objeto y catálogo.
  • Versionado y lifecycle se configuran antes de la primera subida real.
  • Compose es un nodo; el modo distribuido va con Operator o baremetal.

10 · Preguntas frecuentes

¿Por qué no un bucket por tenant?

Porque multiplica políticas, réplica, backup y operación sin aportar aislamiento real en este caso. El prefijo permite políticas por tenant y el catálogo filtra por tenant. Un bucket por tenant se justifica si necesitas cuotas o retención legales muy distintas, o si el número de tenants es pequeño y estable.

¿Dónde guardo el tipo de documento?

En el catálogo, como atributo consultable. Si además debe gobernar lifecycle o políticas, añade una etiqueta o inclúyelo en la clave. La regla es no duplicar la verdad: elige una fuente principal y deriva el resto de forma controlada.

¿El catálogo JSON sirve para producción?

No. Es didáctico: escribe un archivo completo en cada cambio y no soporta consultas concurrentes serias. En producción usa PostgreSQL u otra base con transacciones, índices y backups. La API del proyecto está separada para que sustituirlo no afecte a MinIO.

¿Qué pasa si subo el objeto pero nunca llamo a /complete?

Queda pending y ocupa espacio. El lifecycle de tmp/ no lo limpia si está en el prefijo del tenant. Necesitas una regla o un reconciliador que detecte pending antiguos y decida expirarlos. Es una de las razones por las que conviene subir primero a un prefijo temporal.

¿Por qué no guardo los bytes en la API?

Porque la API tendría que recibir, bufferizar y reenviar cada archivo, consumiendo memoria y ancho de banda. Con presigned PUT el navegador habla directamente con MinIO y la API solo firma y verifica. Menos carga, menos timeouts y una ruta de subida más escalable.
