Metadatos, versionado y lifecycle

Módulo 7 · Proyecto final 🕐 40 minutos

1 · Introducción

Un documento no es solo su contenido. Es quién lo subió, cuándo, de qué tipo es, en qué estado está y qué versiones ha tenido. MinIO guarda una parte de esa información en el objeto; la aplicación guarda el resto en su catálogo. Y el tiempo —el lifecycle— decide cuánto vive cada cosa.

Las tres piezas se confunden con facilidad. Los metadatos de usuario no son un motor de búsqueda. Las etiquetas no son metadatos. El versionado no es un backup. El lifecycle no es «borrar lo viejo». Cada una tiene una semántica distinta y una forma distinta de equivocarse.

En esta lección conectamos las tres con el document store: qué metadatos escribe la API, cómo se recupera una versión borrada y cómo se declaran reglas que limpian temporales sin tocar documentos reales. El objetivo es que ninguna operación destructiva sea irreversible por accidente.

Por qué existe esta lección

Porque el lifecycle es la función más peligrosa del almacenamiento: una regla con el prefijo equivocado borra producción en silencio. Y porque el versionado solo protege lo que existía después de activarlo. Entender el modelo evita descubrirlo con una auditoría.

2 · Teoría

Tres capas que no son intercambiables

CapaDónde viveLímitePara qué sirve
Metadatos del sistemaCabeceras del objetoContent-Type, Cache-Control, Content-DispositionControlan cómo se sirve y se descarga.
Metadatos de usuariox-amz-meta-*~2 KB en totalContexto pequeño, se lee con HEAD.

CatálogoBase de datos o JSONLo que defina tu esquemaConsultas por tenant, tipo, estado y fecha.

La regla práctica: si necesitas buscar, va al catálogo; si necesitas filtrar una regla, va en etiquetas o prefijo; si necesitas servir mejor, va en metadatos del sistema. Guardar el mismo dato en tres sitios garantiza que se desincronicen.

Qué escribe la API al completar

await catalog.update(id, {
  status: "stored",
  size: stat.size,
  etag: stat.etag,
  versionId: stat.versionId ?? null,
  completedAt: new Date().toISOString(),
});

El versionId es la pieza que permite descargar exactamente la versión que el catálogo conoce, incluso si el objeto se sobrescribe después. Sin él, una descarga «del documento» puede devolver una versión distinta de la registrada.

Los metadatos de presentación se fijan en la subida, no después:

await client.putObject("documentos", key, stream, {
  "Content-Type": "application/pdf",
  "Content-Disposition": 'attachment; filename="informe.pdf"',
  "Cache-Control": "private, no-store",
  "X-Amz-Meta-Tenant": tenant,
  "X-Amz-Meta-Classification": "internal",
});

Con presigned PUT, esas cabeceras las envía el cliente. Si no están firmadas, la API debe leerlas al completar y decidir si las acepta; no puede confiar en que el navegador haya puesto las correctas.

Versionado: qué cambia exactamente

Con versionado activo, cada PUT sobre la misma clave crea una versión nueva y la anterior deja de ser actual. Un DELETE no borra: crea un delete marker, que es una versión especial que oculta las anteriores. La clave «desaparece» de un GET normal, pero los bytes siguen ahí.

clave: acme/2026/11/informe.pdf

v1  PUT   9f3c...   <- primera versión
v2  PUT   4d81...   <- actual
v3  DELETE (marker) <- GET devuelve 404; v1 y v2 siguen

si se elimina el marker -> v2 vuelve a ser actual
si se elimina v2      -> v1 pasa a ser actual
si se eliminan todas  -> el objeto desaparece de verdad
ComandoEfectoReversible
mc rm objetoCrea un delete marker si hay versionadoSí: elimina el marker.
mc rm --version-id IDBorra esa versión concretaNo, salvo backup o réplica.
mc rm --versionsBorra todas las versiones y markersNo: es destrucción permanente.
Lifecycle de versión no actualBorra versiones antiguas tras N díasNo; planifícalo con cuidado.

Versionado no es backup

Vive en el mismo bucket y en el mismo clúster. Si se pierde el despliegue, se pierden todas las versiones. El versionado protege de sobrescrituras y borrados lógicos; el backup y la réplica protegen de la pérdida del sistema. Son capas distintas y ninguna sustituye a la otra.

Lifecycle: corriente, no actual y multpart

Una regla de lifecycle tiene un filtro (prefijo, etiquetas o tamaño) y una acción (expirar, transicionar). En un bucket versionado, «expirar» el objeto corriente crea un delete marker; no borra las versiones. Para borrar versiones antiguas hay que decirlo explícitamente con la acción de versiones no actuales.

ReglaQué haceRiesgo si se mal configura
Expiration.DaysExpira la versión corriente (delete marker)Documentos activos desaparecen de los listados.
NoncurrentVersionExpirationBorra versiones antiguas tras N díasPierdes la recuperación que creías tener.
AbortIncompleteMultipartUploadLimpia subidas multipart sin terminarSin ella, los restos consumen espacio invisible.
ExpiredObjectDeleteMarkerElimina markers sin versiones detrásLimpieza útil; no borra datos vivos.

El proyecto declara dos reglas al arrancar: expire-tmp sobre tmp/ a un día y expire-noncurrent sobre todo el bucket a 30 días. La primera limpia restos; la segunda limita el crecimiento de versiones. Ninguna expira la versión corriente de un documento real.

mc ilm rule ls local/documentos
mc ilm rule export local/documentos > lifecycle.json
mc ilm rule add local/documentos --prefix "tmp/" --expire-days 1
mc ilm rule add local/documentos --noncurrent-expire-days 30 --expire-delete-marker

Exportar a un archivo y versionarlo convierte el lifecycle en configuración revisable. Aplicarlo a mano desde la consola es exactamente lo que el curso quiere evitar.

Object lock: cuando no se puede borrar

El bloqueo de objetos (WORM) exige un bucket creado con --with-lock; no se puede activar después. Hay dos modos: governance, que un usuario con permisos especiales puede acortar, y compliance, que nadie puede acortar hasta que expire el plazo. El versionado es obligatorio; el detalle está en Versionado y object locking.

mc mb --with-lock local/documentos-legales
mc retention set --default GOVERNANCE 30d local/documentos-legales
mc retention info local/documentos-legales

Úsalo solo si la ley o la política interna lo exigen: complica el borrado, el lifecycle y las pruebas. Un bucket con compliance y una retención mal calculada es inmutable durante años, incluido para ti.

La API no debe borrar versiones concretas salvo en una operación administrativa explícita. Su borrado es lógico: marca, no destruye. La destrucción real se reserva a políticas de retención y a un runbook con backup.

3 · Ejemplo mínimo

Comprueba con mc que un borrado normal no destruye nada. Usa el prefijo tmp/ para no mezclarlo con documentos del catálogo:

mc alias set local http://localhost:9000 minioadmin minioadmin123

echo "version 1" > nota.txt
mc cp nota.txt local/documentos/tmp/versionado.txt

echo "version 2" > nota.txt
mc cp nota.txt local/documentos/tmp/versionado.txt

mc ls --versions local/documentos/tmp/versionado.txt

[2026-11-05 10:30]  10B 4d81e07… v2 PUT versionado.txt
[2026-11-05 10:29]  10B 9f3c2ab… v1 PUT versionado.txt

Ahora borra y observa:

mc rm local/documentos/tmp/versionado.txt
mc ls --versions local/documentos/tmp/versionado.txt

[2026-11-05 10:31]   0B 7a2b1c9… v3 DELETE versionado.txt
[2026-11-05 10:30]  10B 4d81e07… v2 PUT versionado.txt
[2026-11-05 10:29]  10B 9f3c2ab… v1 PUT versionado.txt

La versión v3 es un delete marker: no tiene contenido. Recupera la v2 sin tocar el marker:

mc cp --version-id 4d81e07… local/documentos/tmp/versionado.txt ./recuperado.txt
cat ./recuperado.txt

El objeto «borrado» sigue siendo accesible por versión. Para restaurarlo como actual, elimina el marker con mc rm --version-id 7a2b1c9…; entonces v2 vuelve a ser la versión corriente.

4 · Ejemplo real

El document store declara su lifecycle en código, no en la consola. Estas son las reglas reales de src/storage.mjs:

await client.setBucketLifecycle(config.bucket, {
  Rule: [
    {
      ID: "expire-tmp",
      Status: "Enabled",
      Filter: { Prefix: "tmp/" },
      Expiration: { Days: 1 },
    },
    {
      ID: "expire-noncurrent",
      Status: "Enabled",
      Filter: { Prefix: "" },
      NoncurrentVersionExpiration: { NoncurrentDays: 30 },
    },
  ],
});

La primera regla solo toca tmp/. La segunda no expira documentos: borra versiones que llevan 30 días sin ser actuales. Un documento activo no se ve afectado; una versión reemplazada sí, lo que acota el crecimiento del bucket.

Falta una tercera regla que conviene añadir: abortar subidas multipart incompletas. Sin ella, un cliente que empieza una subida grande y desaparece deja partes que nadie ve y que consumen capacidad. Se declara en la misma llamada:

Rule: [
  // ... expire-tmp y expire-noncurrent
  {
    ID: "abort-multipart",
    Status: "Enabled",
    Filter: { Prefix: "" },
    AbortIncompleteMultipartUpload: { DaysAfterInitiation: 3 },
  },
]

Todo el lifecycle en un solo sitio

Mantener las tres reglas en setBucketLifecycle evita que una aplicación las pise al arrancar. Si las creas con mc ilm rule add por separado, el siguiente arranque de la API puede reemplazar la configuración completa y eliminar las que no conoce.

El ciclo completo de un documento con versionado y lifecycle:

DíaAcciónEstado
0Subida y completev1 actual, catálogo stored
10Nueva subida sobre la misma clavev2 actual, v1 no actual
20Borrado desde la APIDelete marker, catálogo deleted
21Restauración manualv2 actual, catálogo stored
40Lifecycle de no actualesv1 borrada; v2 intacta

La restauración no es automática: quitar el delete marker devuelve el objeto, pero el catálogo sigue en deleted hasta que un job o una persona lo actualice. Ese hueco es el motivo por el que existe la reconciliación.

Para documentos con retención legal, el bucket se crea aparte:

mc mb --with-lock local/documentos-legales
mc retention set --default COMPLIANCE 365d local/documentos-legales
mc retention info local/documentos-legales

No mezcles documentos legales con el bucket general: una regla de lifecycle o un borrado administrativo no debe poder afectar a un objeto inmutable por ley.

6 · Errores habituales

1. Expirar el bucket entero

Mal — una regla sin prefijo borra documentos reales 
mc ilm rule add local/documentos --expire-days 30
# dentro de 30 días, TODOS los objetos corrientes desaparecen de los listados
Bien — limitar a temporales y versiones no actuales 
mc ilm rule add local/documentos --prefix "tmp/" --expire-days 1
mc ilm rule add local/documentos --noncurrent-expire-days 30

La expiración de un objeto corriente en un bucket versionado crea un delete marker, pero el efecto para el usuario es el mismo: el documento deja de estar disponible.

2. Borrar todas las versiones para «limpiar»

Mal — destrucción permanente sin vuelta atrás 
mc rm --recursive --versions local/documentos/acme/
Bien — borrado lógico y lifecycle planificado 
mc rm local/documentos/acme/2026/11/informe.pdf   # delete marker
mc ls --versions local/documentos/acme/2026/11/
# y si hace falta espacio, una regla de no actuales con revisión

--versions elimina también los delete markers y todas las versiones. No es una limpieza: es un borrado definitivo que solo un backup puede deshacer.

3. Usar metadatos como base de datos

Mal — listar todo para filtrar por tipo 
// recorre millones de objetos y descarga metadatos para buscar facturas
for await (const obj of client.listObjectsV2("documentos", "", true)) {
  const stat = await client.statObject("documentos", obj.name);
  if (stat.metaData["x-amz-meta-type"] === "factura") { /* ... */ }
}
Bien — consultar el catálogo indexado 
const docs = await catalog.list({ tenant: "acme", type: "factura" });

Los metadatos de usuario tienen un límite de tamaño y no se indexan para búsquedas. El catálogo existe precisamente para eso.

7 · Ejercicio guiado

Objetivo: comprobar versiones, recuperar un borrado, revisar las reglas de lifecycle y etiquetar un objeto.

  1. Confirma el versionado del proyecto: 
    cd proyectos/document-store
docker compose up -d
mc alias set local http://localhost:9000 minioadmin minioadmin123
mc version info local/documentos
mc ilm rule ls local/documentos

    Espera Enabled y las reglas expire-tmp y expire-noncurrent.

  2. Crea dos versiones de un objeto de prueba: 
    echo "v1" > /tmp/v.txt
mc cp /tmp/v.txt local/documentos/tmp/ejercicio.txt
echo "v2" > /tmp/v.txt
mc cp /tmp/v.txt local/documentos/tmp/ejercicio.txt
mc ls --versions local/documentos/tmp/ejercicio.txt

    Anota los dos version-id. La versión actual es la de arriba.

  3. Borra y comprueba el delete marker: 
    mc rm local/documentos/tmp/ejercicio.txt
mc ls --versions local/documentos/tmp/ejercicio.txt
mc cat local/documentos/tmp/ejercicio.txt

    El último comando debe fallar con NoSuchKey; el listado debe mostrar una versión DELETE de 0 bytes.

  4. Recupera una versión concreta: 
    mc cp --version-id <version-id-v1> \
  local/documentos/tmp/ejercicio.txt /tmp/recuperado.txt
cat /tmp/recuperado.txt

    Debe imprimir v1. Después elimina el marker para que la versión vuelva a ser actual.

  5. Etiqueta el objeto y observa los límites: 
    mc tag set local/documentos/tmp/ejercicio.txt "clasificacion=interno&estado=revisado"
mc tag list local/documentos/tmp/ejercicio.txt

    Las etiquetas se pueden usar en filtros de lifecycle. No las uses para datos que necesites consultar por rango o fecha: eso es catálogo.

  6. Exporta el lifecycle y añade una regla segura: 
    mc ilm rule export local/documentos > /tmp/lifecycle.json
mc ilm rule add local/documentos --prefix "tmp/" --expire-days 2
mc ilm rule ls local/documentos

    Compara el JSON exportado con las reglas activas. Si añades una regla sin prefijo, vuelve a leer la sección 6: es el error más caro de esta lección.

8 · Reto

🎯 Retención distinta para cada tenant

Diseña una política de retención donde el tenant legal conserve todo durante siete años con object lock en modo compliance, acme conserve versiones 90 días y demo borre todo a los 7 días. Debes usar un solo bucket si es posible, explicar cómo lo consigues con prefijos, etiquetas y reglas, y qué limitaciones tiene object lock cuando se activa a nivel de bucket.

Incluye el orden de creación de las reglas, una prueba de que demo no puede afectar a legal y el procedimiento para cambiar la retención de un tenant sin destruir datos. Señala qué parte es reversible y qué parte no lo es nunca.

Pista: object lock se activa al crear el bucket y se aplica por objeto o por defecto. Si legal y demo comparten bucket, la retención por defecto afectaría a ambos; quizá el aislamiento no sea opcional.

9 · Resumen

  • Metadatos sirven para servir, etiquetas para filtrar y catálogo para consultar.
  • El versionId identifica la versión exacta que el catálogo registró.
  • Un borrado normal en un bucket versionado crea un delete marker, no destruye bytes.
  • El lifecycle de la versión corriente expira el documento; el de no actuales borra historia.
  • El proyecto limpia tmp/ a un día y versiones no actuales a 30 días.
  • Object lock exige crear el bucket con lock y no se puede deshacer en modo compliance.
  • Versionado no es backup: la pérdida del clúster se cubre con réplica y copias externas.

10 · Preguntas frecuentes

¿Cuántas versiones debo conservar?

Depende de la criticidad y del espacio. Una política habitual es conservar las versiones no actuales 30 o 90 días y mantener un backup externo para el largo plazo. Lo importante es que la política esté escrita y probada: el lifecycle no avisa cuando borra.

¿El delete marker ocupa espacio?

Es un objeto pequeño de metadatos, no una copia del contenido. Ocupa muy poco, pero puede acumularse si nunca se limpia. La acción ExpiredObjectDeleteMarker elimina los markers que ya no ocultan ninguna versión.

¿Puedo cambiar el modo de object lock después?

No se puede pasar de compliance a governance ni acortar una retención compliance. Governance permite a un usuario con permiso especial acortar el plazo; compliance no. Planifica la retención antes de crear el bucket y prueba con objetos de laboratorio.

¿El lifecycle se aplica a los objetos que ya existen?

Sí, MinIO evalúa las reglas sobre los objetos existentes además de los nuevos. La evaluación no es instantánea: puede tardar en ejecutarse. No uses el lifecycle como un cron exacto para acciones de negocio; úsalo para retención y limpieza.

¿Cómo recupero un documento borrado desde la API?

Localiza la clave en el catálogo, ejecuta mc ls --versions, elimina el delete marker con mc rm --version-id y actualiza el catálogo a stored. Si el documento tenía retención o el bucket es inmutable, el procedimiento cambia: consulta la política antes de tocar versiones.
