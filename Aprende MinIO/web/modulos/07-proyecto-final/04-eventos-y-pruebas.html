Eventos y pruebas

Módulo 7 · Proyecto final 🕐 40 minutos

1 · Introducción

El document store ya guarda, versiona y limpia. Lo que falta es que reaccione: avisar a otro sistema cuando un documento queda almacenado, escanearlo, indexarlo o generar una miniatura. Y falta lo que separa un proyecto de una demo: pruebas que demuestren que el flujo funciona y un runbook para cuando no.

Los eventos de MinIO son notificaciones HTTP o mensajes a una cola. No son transacciones. Llegan al menos una vez, pueden duplicarse, pueden perderse si el destino está caído y no garantizan orden. El receptor debe ser rápido, idempotente y capaz de delegar el trabajo pesado. Esta lección cierra el módulo con el receptor, una batería de pruebas con node --test y un runbook para operar el sistema, sobre el estado que dejó Metadatos, versionado y lifecycle.

Por qué existe esta lección

Porque un evento duplicado que devuelve 500 genera reintentos infinitos, y porque un test que necesita un bucket compartido se vuelve flaky en la primera semana. La diferencia entre un sistema operable y uno frágil está en estas dos cosas.

2 · Teoría

Del bucket al receptor

PUT en documentos/…            MinIO                         receptor
        |                        |                               |
        +----------------------->| evalúa reglas de notificación |
                                 | POST /webhooks/minio          |
                                 +------------------------------>| valida token
                                 |                              | deduplica
                                 |                              | encola
                                 |<------------------------------+ 204
                                 |                              |
                                 |  si falla: reintenta         | worker procesa

MinIO entrega el evento con formato compatible con S3: un objeto raíz con EventName y un array Records. Cada registro trae eventName, eventTime, s3.bucket.name, s3.object.key, size, eTag y sequencer.

{
  "EventName": "s3:ObjectCreated:Put",
  "Key": "documentos/acme/2026/11/7f2c-informe.pdf",
  "Records": [
    {
      "eventName": "s3:ObjectCreated:Put",
      "eventTime": "2026-11-05T10:00:00.000Z",
      "s3": {
        "bucket": { "name": "documentos" },
        "object": {
          "key": "acme/2026/11/7f2c-informe.pdf",
          "size": 204800,
          "eTag": "9f3c2ab1c4d5e6f708192a3b4c5d6e7f",
          "contentType": "application/pdf",
          "sequencer": "182178E8B3728CAC"
        }
      }
    }
  ]
}

La clave puede venir codificada si contiene espacios o caracteres especiales. Trátala como dato no confiable: decodifica, valida que empieza por el prefijo esperado y no la uses para construir rutas locales.

Configurar el destino

El proyecto usa variables de entorno porque el target se declara al arrancar MinIO. En Compose, con la API corriendo en el host, el bloque queda así:

services:
  minio:
    image: quay.io/minio/minio
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: minioadmin
      MINIO_ROOT_PASSWORD: minioadmin123
      MINIO_NOTIFY_WEBHOOK_ENABLE_PRIMARY: "on"
      MINIO_NOTIFY_WEBHOOK_ENDPOINT_PRIMARY: "http://host.docker.internal:7072/webhooks/minio"
      MINIO_NOTIFY_WEBHOOK_AUTH_TOKEN_PRIMARY: "dev-token"
    extra_hosts:
      - "host.docker.internal:host-gateway"

Después de reiniciar MinIO, se suscribe el bucket. La suscripción es independiente del target: si configuras el webhook pero no ejecutas mc event add, no llega nada.

mc event add local/documentos \
  arn:minio:sqs::primary:webhook \
  --event put --suffix ".pdf"
mc event list local/documentos

El ARN identifica el target (primary) y el tipo (webhook). --event put filtra altas; --suffix ".pdf" reduce ruido. Para el pipeline completo, querrás también s3:ObjectCreated:CompleteMultipartUpload.

Receptor: rápido, idempotente, con token

El receptor del proyecto registra el evento y devuelve 204. Es suficiente para observar el flujo, pero en producción debe además validar el token, deduplicar y encolar. El orden importa: responde antes de hacer trabajo pesado, porque MinIO tiene timeout y reintenta.

if (req.method === "POST" && url.pathname === "/webhooks/minio") {
  const auth = req.headers.authorization;
  if (auth !== `Bearer ${process.env.MINIO_WEBHOOK_TOKEN}`) {
    return send(res, 401, { error: "token inválido" });
  }

  const event = await readJson(req);
  for (const record of event.Records ?? []) {
    const key = decodeURIComponent(record.s3.object.key.replace(/\+/g, " "));
    const id = [record.s3.bucket.name, key, record.s3.object.eTag].join("/");
    if (seen.has(id)) continue;   // en memoria: usa una tabla en producción
    seen.add(id);
    queue.push({ id, key, size: record.s3.object.size });
  }
  return send(res, 204);
}

La clave de idempotencia combina bucket, clave y ETag: el mismo objeto notificado dos veces se procesa una. Si el objeto cambia, el ETag cambia y es un trabajo nuevo. sequencer ayuda a ordenar eventos del mismo objeto, pero no es un identificador global ni garantiza orden entre objetos.

ReglaMotivo
Validar AuthorizationEl endpoint está expuesto; sin token cualquiera puede inyectar eventos.
Responder 2xx rápidoUn timeout provoca reintentos y multiplica el trabajo.
Deduplicar antes de encolarLa entrega es al menos una vez.
No confiar en el ordenDos objetos pueden llegar invertidos.
Encolar, no procesar en el handlerEl trabajo pesado tiene su propio timeout y escala.

Eventos de aplicación y eventos de MinIO

El proyecto emite además un webhook propio, document.stored, al completar una subida. No es lo mismo que la notificación de MinIO: el primero lo controla tu API y puede incluir el id del catálogo; el segundo lo emite el servidor y refleja el objeto, no tu estado de negocio. Para procesos de negocio, usa el de la API; para reaccionar a cualquier escritura, el de MinIO.

En Node.js 22, node --test descubre *.test.mjs y ejecuta cada archivo en un proceso. El proyecto ya trae pruebas de claves y catálogo. Añadir una prueba de lifecycle exige extraer las reglas a una función pura, para no necesitar MinIO:

// src/lifecycle.mjs
export function lifecycleRules() {
  return [
    { ID: "expire-tmp", Status: "Enabled", Filter: { Prefix: "tmp/" }, Expiration: { Days: 1 } },
    { ID: "expire-noncurrent", Status: "Enabled", Filter: { Prefix: "" }, NoncurrentVersionExpiration: { NoncurrentDays: 30 } },
  ];
}

import test from "node:test";
import assert from "node:assert/strict";
import { lifecycleRules } from "../src/lifecycle.mjs";

test("el lifecycle solo expira tmp y versiones no actuales", () => {
  const rules = lifecycleRules();
  assert.deepEqual(rules.map((r) => r.ID), ["expire-tmp", "expire-noncurrent"]);
  assert.equal(rules[0].Filter.Prefix, "tmp/");
  assert.ok(!rules.some((r) => r.Filter.Prefix === "" && r.Expiration));
});

Prueba de integración con Compose

La prueba de integración se salta si no hay API, para que npm test siga funcionando sin Docker. Con BASE_URL definida, recorre el flujo real:

import test from "node:test";
import assert from "node:assert/strict";
const BASE = process.env.BASE_URL;

test("flujo completo de documento", { skip: !BASE }, async () => {
  const created = await fetch(`${BASE}/documents`, {
    method: "POST", headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ tenant: "test-acme", filename: "prueba.pdf",
      contentType: "application/pdf", size: 1024 }),
  });
  assert.equal(created.status, 201);
  const doc = await created.json();
  const put = await fetch(doc.uploadUrl, {
    method: "PUT", headers: { "Content-Type": "application/pdf" },
    body: "%PDF-1.4\nprueba\n",
  });
  assert.equal(put.status, 200);
  const completed = await fetch(`${BASE}/documents/${doc.id}/complete`, { method: "POST" });
  assert.equal(completed.status, 200);
  assert.equal((await completed.json()).status, "stored");
});

Reglas para que no sea flaky: usa un tenant de prueba, limpia al final, no dependas del orden de listados y no compartas claves entre ejecuciones. Si la prueba falla, debe dejar el sistema en un estado inspeccionable, no borrar la evidencia.

4 · Ejemplo real

El receptor real del proyecto es deliberadamente pequeño: registra el evento y responde. Así se observa el flujo sin introducir un worker en el curso:

if (req.method === "POST" && url.pathname === "/webhooks/minio") {
  const event = await readJson(req);
  console.log("[minio-event]", event.EventName ?? "evento sin nombre");
  for (const record of event.Records ?? []) {
    console.log("  objeto:", record.s3.bucket.name, record.s3.object.key);
  }
  return send(res, 204);
}

Al subir un PDF completado, la consola muestra algo así:

[minio-event] s3:ObjectCreated:Put
  objeto: documentos acme/2026/11/7f2c-informe.pdf

Y si el destino no responde, MinIO reintenta. El receptor no debe tardar: si tarda más que el timeout, el evento se considera fallido aunque el trabajo se haya hecho, y llegará otra vez. Esa es la razón de separar recepción y procesamiento.

Comprobaciones de operación que acompañan al receptor:

mc admin config get local notify_webhook:primary
mc event list local/documentos
curl -i -X POST http://localhost:7072/webhooks/minio \
  -H "Authorization: Bearer dev-token" \
  -H "Content-Type: application/json" \
  -d '{"EventName":"s3:ObjectCreated:Put","Records":[]}'

La última orden simula una entrega y debe devolver 204. Si devuelve 401, el token del entorno no coincide con el que envía MinIO. Si devuelve 500, el receptor está lanzando antes de responder y MinIO lo reintentará.

Un evento no confirma el negocio

Que el receptor reciba un PUT no significa que el documento esté completo o aprobado. El evento de MinIO refleja el objeto; el estado de negocio vive en el catálogo. Procesa solo cuando la ficha esté en stored, o usa el webhook de aplicación document.stored.

6 · Errores habituales

1. Devolver 500 ante un duplicado

Mal — el reintento se convierte en tormenta 
if (await alreadyProcessed(id)) {
  throw new Error("ya procesado"); // MinIO reintenta
}
Bien — idempotente y 2xx 
if (await alreadyProcessed(id)) {
  return send(res, 204); // nada que hacer, pero el evento se aceptó
}

Un duplicado no es un error: es una condición normal. Solo los fallos transitorios deben provocar reintento.

2. Hacer el trabajo pesado antes de responder

Mal — el webhook tarda minutos 
app.post("/webhooks/minio", async (req, res) => {
  await scanAndThumbnail(req.body); // 80 MB después...
  res.status(204).end();
});
Bien — encolar y responder 
app.post("/webhooks/minio", async (req, res) => {
  await queue.add("scan", req.body);
  res.status(204).end(); // el worker hará el trabajo
});

El receptor debe ser un portero, no un taller. Si el trabajo es largo, tiene su propio timeout, su propia escala y su propia cola de errores.

3. Confiar en el orden o en la clave cruda

Mal — asumir que el último evento es el estado actual 
const key = record.s3.object.key; // puede venir codificada
await process(key);              // sin comprobar el prefijo
Bien — decodificar, validar y verificar el objeto 
const key = decodeURIComponent(record.s3.object.key.replace(/\+/g, " "));
if (!key.startsWith(`${tenant}/`)) return;
const stat = await statObject(bucket, key); // el objeto manda

El evento es una pista; el objeto y el catálogo son la verdad. Antes de actuar, comprueba que el objeto sigue existiendo y que su ETag coincide.

4. Probar contra el bucket de todos

Mal — tests que se pisan entre sí 
await client.putObject("documentos", "informe.pdf", body);
// otro test sobrescribe la misma clave y el resultado es aleatorio
Bien — claves y tenants únicos, limpieza explícita 
const tenant = `test-${crypto.randomUUID().slice(0, 8)}`;
const key = `${tenant}/2026/11/${crypto.randomUUID()}-prueba.pdf`;
t.after(() => client.removeObject("documentos", key).catch(() => {}));

Un test que falla una de cada diez veces no es un test: es una fuente de desconfianza. Aísla los datos y limpia incluso cuando falla.

7 · Ejercicio guiado

Objetivo: conectar MinIO con el receptor, observar un evento real, comprobar la idempotencia y ejecutar la suite completa.

  1. Arranca el proyecto y la API: 
    cd proyectos/document-store
docker compose up -d
npm install
npm run api

    Añade al servicio de MinIO las tres variables MINIO_NOTIFY_WEBHOOK_* de la sección 2 y extra_hosts. Reinicia con docker compose up -d.

  2. Verifica el target y suscribe el bucket: 
    mc admin config get local notify_webhook:primary
mc event add local/documentos \
  arn:minio:sqs::primary:webhook \
  --event put --suffix ".pdf"
mc event list local/documentos

    Debe aparecer el ARN con el prefijo y el sufijo configurados. Si event add falla, el target no está habilitado.

  3. Sube un PDF por el flujo normal: crea el documento, haz el PUT a la URL firmada y llama a /complete. En la terminal de la API debe aparecer [minio-event] s3:ObjectCreated:Put con la clave del objeto.
  4. Simula una entrega duplicada: reenvía el mismo JSON al receptor con curl. Si tu versión deduplica, el segundo envío no debe encolar trabajo; si solo registra, anota por qué el proyecto de referencia no deduplica todavía y qué añadirías.
  5. Ejecuta la suite y hazla fallar: 
    npm test
BASE_URL=http://localhost:7072 node --test test/integration.test.mjs

    La primera orden no necesita MinIO. La segunda recorre el flujo completo; si no existe el archivo de integración, créalo con el código de la sección 2. Después cambia el prefijo esperado de tmp/ a temp/ y ejecuta npm test: debe fallar. Restaura el valor y confirma que vuelve a pasar. Una prueba que nunca falla no demuestra nada.

8 · Reto

🎯 Entrega fiable con reconciliación

Diseña el procesamiento de eventos para que un documento se escanee e indexe exactamente una vez desde el punto de vista del negocio, aunque el evento llegue duplicado, el worker muera a mitad o el target esté caído una hora. Debes incluir: cola con ack, deduplicación persistente, reintentos con backoff, cola de descartes y un job de reconciliación que detecte objetos sin estado.

Define las métricas que demostrarían que funciona (edad del evento más antiguo, pendientes, duplicados descartados, fallos por tipo) y escribe el runbook para los tres incidentes más probables. Explica qué parte es exactamente una vez y qué parte sigue siendo al menos una vez.

Pista: la exactitud de negocio se consigue con una operación idempotente en el destino, no con una cola mágica. El estado final del objeto o del catálogo es lo que decide si el trabajo ya se hizo.

9 · Resumen

  • MinIO notifica con formato S3 (Records con bucket, clave, tamaño, ETag y sequencer); el target se configura al arrancar y la suscripción con mc event add.
  • La entrega es al menos una vez, sin orden garantizado; el receptor valida token, deduplica, encola y responde 2xx rápido.
  • El evento de MinIO no confirma el estado de negocio: el catálogo sí; node --test cubre claves y reglas sin MinIO.
  • Un runbook y un checklist convierten el proyecto en algo operable.

10 · Preguntas frecuentes

¿MinIO garantiza que el evento llega una sola vez?

No. La entrega es al menos una vez y puede repetirse por reintentos o reinicios. El orden entre objetos tampoco está garantizado. Diseña el consumidor para que procesar dos veces el mismo objeto no cambie el resultado.

¿Puedo perder eventos?

Sí. Si el destino está caído y la cola interna se llena, MinIO puede descartar notificaciones. Por eso el sistema necesita reconciliación: listar objetos y comparar con el catálogo para detectar los que nunca se procesaron.

¿Qué diferencia hay entre el webhook de MinIO y el de la API?

El de MinIO lo emite el servidor cuando cambia un objeto y no conoce tu catálogo. El de la API lo emite tu código después de verificar y actualizar el estado. Para procesos de negocio, el segundo es más fiable; para reaccionar a cualquier escritura, el primero es más completo.

¿Qué debe contener el checklist final del proyecto?

Compose arranca con una orden; bucket versionado y lifecycle aplicados; política de mínimo privilegio; presigned uploads con expiración; validación de tipo y tamaño; complete idempotente; borrado recuperable; eventos configurados; suite en verde; runbook y backup probado. Si falta uno, el proyecto no está terminado: está en demo.
