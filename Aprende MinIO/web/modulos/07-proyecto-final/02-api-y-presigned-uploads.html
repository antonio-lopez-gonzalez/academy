API y presigned uploads

Módulo 7 · Proyecto final 🕐 45 minutos

1 · Introducción

La API del document store tiene una responsabilidad estrecha y crítica: decidir qué se puede subir, dónde se guarda y cuándo está disponible. Los bytes no pasan por ella. El navegador recibe una URL firmada, sube directo a MinIO y después pide a la API que verifique y registre el resultado.

Ese diseño elimina el cuello de botella de memoria y ancho de banda, pero introduce dos preguntas: ¿cómo impides que el cliente elija la clave? y ¿cómo sabes que lo que subió es lo que dijo? La respuesta es generar la clave en el servidor y verificar con statObject antes de dar el documento por bueno. Al terminar podrás subir un PDF con curl, completarlo, descargarlo y borrarlo de forma recuperable, igual que en Subidas directas.

Por qué existe esta lección

Porque una presigned URL mal emitida es una escritura arbitraria en tu bucket. El cliente no debe poder elegir la ruta, el tipo ni el tamaño efectivo. La firma limita el método y la clave; la verificación posterior limita la realidad.

No hay autenticación de usuario en el proyecto: es una simplificación docente. En producción, cada petición debe llevar identidad (sesión, token o mTLS) y el tenant debe derivarse de ella, no del cuerpo. Aceptar tenant del cliente sin comprobar permisos es una escalada horizontal.

Crear: la clave nace en el servidor

POST /documents
{ tenant, filename, contentType, size }
        |
        v
assertTenant -> sanitizeFilename -> assertContentType -> assertSize
        |
        v
id = randomUUID()          <- el cliente no lo elige
key = {tenant}/{año}/{mes}/{id}-{nombre}
        |
        v
catálogo: status=pending
uploadUrl = presignedPutObject(bucket, key, 900s)
        |
        v
201 { id, key, uploadUrl, expiresIn }

La URL firmada cubre el método PUT, el bucket, la clave y la expiración. No cubre un tamaño máximo: S3 no tiene una cabecera «no aceptes más de N bytes» en un PUT simple. Por eso el tamaño declarado se valida al crear y el tamaño real se valida al completar.

Content-Type no está garantizado por la firma

presignedPutObject de minio-js firma la operación y la clave; la cabecera Content-Type que envíe el cliente no queda necesariamente vinculada. Al completar, lee stat.metaData["content-type"], compara con el tipo declarado y rechaza si no coincide. Es un endurecimiento que el proyecto de referencia aún no aplica y que deberías añadir.

Completar: verificar antes de confiar

El paso /complete es el que convierte una subida en un documento. Debe ser idempotente: dos llamadas seguidas devuelven el mismo estado y no duplican efectos. La secuencia correcta es:

  1. Buscar la ficha; si no existe, 404.
  2. statObject; si no hay objeto, 409 (la subida no ocurrió o caducó).
  3. Comprobar tamaño real y tipo real; si no cuadra, 413 o 415.
  4. Actualizar el catálogo con size, etag y completedAt.
  5. Emitir el evento de aplicación solo si el estado anterior era pending.

El ETag se guarda como huella barata para detectar cambios y para reconciliar. No es una prueba criptográfica de integridad en objetos multipart o cifrados; para eso se usa un checksum propio.

Las funciones de keys.mjs lanzan Error genéricos para poder probarlas sin HTTP. En el borde de la API hay que traducirlos a errores de cliente: si el catch general los convierte en 500, el cliente recibe un fallo de servidor por algo que envió mal. Envuelve la validación en un HttpError(400/415/413) o usa una clase de error de dominio con su código.

La descarga sigue el mismo principio: el bucket es privado y la API firma una URL de GET con expiración corta. El proyecto usa los mismos 900 s que la subida; para descargas de un usuario concreto, 300 s es más prudente. La URL no debe registrarse en logs ni guardarse en el catálogo: es una credencial temporal.

3 · Ejemplo mínimo

El núcleo son dos llamadas al SDK: firmar y verificar. Así las implementa el proyecto en src/storage.mjs:

import * as Minio from "minio";
const client = new Minio.Client({
  endPoint: "127.0.0.1",
  port: 9000,
  useSSL: false,
  accessKey: process.env.MINIO_ACCESS_KEY,
  secretKey: process.env.MINIO_SECRET_KEY,
});
export function presignedPut(client, config, key) {
  return client.presignedPutObject(
    config.bucket,
    key,
    config.presignExpirySeconds, // 900 s
  );
}
export function statObject(client, config, key) {
  return client.statObject(config.bucket, key);
}

presignedPutObject devuelve una URL con X-Amz-Signature; no contacta con el servidor. statObject hace un HEAD y devuelve tamaño, ETag, fecha y metadatos. La primera crea capacidad de escritura; la segunda comprueba la realidad.

El cliente solo necesita hacer un PUT a esa URL:

curl -i -X PUT "<uploadUrl>" \
  -H "Content-Type: application/pdf" \
  --data-binary "@informe.pdf"

Si la URL caducó, MinIO responde 403 con AccessDenied o ExpiredToken. Si la clave no coincide, la firma falla. No hay forma de «arreglar» la URL: se pide otra.

4 · Ejemplo real

Estas son las dos rutas que sostienen el flujo, extraídas de src/api.mjs y simplificadas para la lección:

if (req.method === "POST" && url.pathname === "/documents") {
  const body = await readJson(req);
  const tenant = assertTenant(body.tenant);
  const filename = body.filename;
  const contentType = assertContentType(body.contentType);
  const size = assertSize(body.size, config.maxUploadBytes);
  const id = crypto.randomUUID();
  const key = documentKey({ tenant, filename, id });
  const doc = {
    id, tenant, filename, key, contentType, size,
    status: "pending", createdAt: new Date().toISOString(),
  };
  await catalog.create(doc);
  const uploadUrl = await presignedPut(client, config, key);
  return send(res, 201, {
    id, key, uploadUrl,
    expiresIn: config.presignExpirySeconds,
    next: `PUT ${uploadUrl} y luego POST /documents/${id}/complete`,
  });
}

Y la ruta de finalización:

if (req.method === "POST" && action === "/complete") {
  const doc = await catalog.get(id);
  if (!doc) throw new HttpError(404, "documento no encontrado");
  const stat = await statObject(client, config, doc.key).catch(() => null);
  if (!stat) throw new HttpError(409, "el objeto todavía no se ha subido");
  if (stat.size > config.maxUploadBytes) {
    throw new HttpError(413, "el objeto supera el tamaño máximo");
  }
  // Endurecimiento recomendado: el tipo real debe coincidir con el declarado.
  const realType = stat.metaData?.["content-type"];
  if (realType && realType !== doc.contentType) {
    throw new HttpError(415, "el tipo real no coincide con el declarado");
  }
  const updated = await catalog.update(id, {
    status: "stored",
    size: stat.size,
    etag: stat.etag,
    completedAt: new Date().toISOString(),
  });
  await notify({ event: "document.stored", id, key: doc.key, tenant: doc.tenant });
  return send(res, 200, updated);
}

El objeto rechazado no desaparece

Si la verificación falla después del PUT, el objeto ya está en MinIO. La API debe borrarlo o moverlo a un prefijo de rechazo, y el lifecycle debe expirar ese prefijo. Rechazar en el catálogo sin limpiar el bucket deja basura que nadie ve.

6 · Errores habituales

1. Aceptar la clave desde el cliente

Mal — el cliente decide dónde escribe 
const key = body.key; // "acme/../../otro-tenant/secreto.pdf"
const url = await client.presignedPutObject("documentos", key, 900);
Bien — clave derivada de datos validados 
const id = crypto.randomUUID();
const key = documentKey({ tenant, filename, id });
const url = await client.presignedPutObject("documentos", key, 900);

La URL firmada es capacidad de escritura. Si la clave la elige el cliente, también elige si sobrescribe un documento ajeno.

2. Dar por bueno el tamaño declarado

Mal — nunca se mira el objeto real 
if (body.size > MAX) throw new HttpError(413, "demasiado grande");
await catalog.update(id, { status: "stored", size: body.size });
Bien — el tamaño sale de statObject 
const stat = await statObject(client, config, doc.key);
if (!stat) throw new HttpError(409, "objeto no subido");
if (stat.size > MAX) throw new HttpError(413, "demasiado grande");
await catalog.update(id, { status: "stored", size: stat.size, etag: stat.etag });

La primera validación ahorra una subida inútil; la segunda es la que impide almacenar un archivo de 2 GB declarando 2 KB.

3. Devolver 500 ante un error del cliente

Mal — la validación se convierte en fallo de servidor 
try {
  const tenant = assertTenant(body.tenant);
} catch (error) {
  throw error; // el catch global responde 500
}
Bien — traducir a un error HTTP concreto 
try {
  assertTenant(body.tenant);
} catch (error) {
  throw new HttpError(400, error.message);
}

Un 500 dice «el servidor falló». Un 400 dice «tu petición está mal». La diferencia importa para clientes, métricas y alertas.

7 · Ejercicio guiado

Objetivo: completar el ciclo de vida de un documento con la API real, comprobar la validación y recuperar un borrado.

  1. Arranca el proyecto: 
    cd proyectos/document-store
docker compose up -d
npm install
npm run api

    Comprueba curl http://localhost:7072/health. Debe devolver 200 con el bucket documentos.

  2. Crea el documento y guarda la respuesta: 
    curl -s -X POST http://localhost:7072/documents \
  -H "Content-Type: application/json" \
  -d '{"tenant":"acme","filename":"informe.pdf","contentType":"application/pdf","size":204800}' \
  | tee /tmp/doc.json

    Extrae id y uploadUrl con jq o a mano. La clave debe contener un UUID, no el nombre original.

  3. Sube un PDF pequeño a la URL firmada: 
    printf '%%PDF-1.4\n%% documento de prueba\n' > /tmp/informe.pdf
curl -i -X PUT "$UPLOAD_URL" \
  -H "Content-Type: application/pdf" \
  --data-binary "@/tmp/informe.pdf"

    Espera 200 OK y un ETag. Si recibes 403, la URL caducó: vuelve a crear el documento.

  4. Completa y verifica: 
    curl -s -X POST http://localhost:7072/documents/$ID/complete
curl -s http://localhost:7072/documents/$ID

    El estado pasa a stored con size real y etag. Repite el complete: debe devolver 200 con el mismo resultado, no un error.

  5. Prueba los rechazos: 
    # tipo no permitido
curl -s -X POST http://localhost:7072/documents \
  -H "Content-Type: application/json" \
  -d '{"tenant":"acme","filename":"x.exe","contentType":"application/x-msdownload","size":10}'
# tenant con traversal
curl -s -X POST http://localhost:7072/documents \
  -H "Content-Type: application/json" \
  -d '{"tenant":"../etc","filename":"x.pdf","contentType":"application/pdf","size":10}'

    Espera un 4xx con un mensaje claro. Si recibes 500, aplica la traducción de errores de la sección 6.

  6. Borra y recupera: 
    curl -s -X DELETE http://localhost:7072/documents/$ID
mc ls --versions local/documentos/acme/2026/11/
mc rm --version-id <version-id-del-delete-marker> local/documentos/$KEY
curl -s http://localhost:7072/documents/$ID

    El DELETE crea un delete marker; al eliminarlo, la versión anterior vuelve a ser la actual. Actualiza el catálogo a stored si restauras manualmente: MinIO no avisa a tu base de datos.

8 · Reto

🎯 Subidas grandes, reanudables y verificadas

El límite de 25 MiB deja fuera vídeos y archivos comprimidos grandes. Diseña una extensión de la API para subidas multipart con presigned URLs por parte: iniciar, firmar cada parte, listar partes subidas, completar y abortar. Debe permitir reanudar tras una caída, verificar un checksum al final y caducar las subidas abandonadas.

Decide cuántas partes, de qué tamaño, cómo evitas que el cliente complete una subida con partes de otro documento y qué pasa si una parte se sube dos veces. Incluye los endpoints, el estado en el catálogo y una prueba de fallo a mitad de la subida.

Pista: cada parte tiene su propio ETag; la operación de completar recibe la lista ordenada. Un ListParts te dice qué falta, y el lifecycle de subidas multipart incompletas evita que los restos se acumulen.

9 · Resumen

  • La API valida, genera la clave y firma; los bytes van directos a MinIO.
  • La clave se deriva de datos validados; el cliente nunca la elige.
  • La presigned URL limita método, bucket, clave y tiempo, no el tamaño ni el tipo real.
  • statObject es la verificación que convierte una subida en un documento.
  • /complete debe ser idempotente y no repetir eventos en cada llamada.
  • Los errores de validación se traducen a 400, 413 o 415, no a 500.
  • Un objeto rechazado tras el PUT debe limpiarse o aislarse.

10 · Preguntas frecuentes

¿La URL presignada se puede reutilizar?

Sí, hasta que expira, y permite exactamente el método y la clave firmados. Si se filtra dentro de esa ventana, cualquiera puede subir a esa clave. Por eso la expiración es corta y la clave incluye un UUID no adivinable. Para subidas críticas, añade un token de un solo uso en la API que autorice el complete.

¿Puedo limitar el tamaño en la propia URL?

Con un PUT simple no hay una cabecera estándar para imponer un máximo. La alternativa es un presigned POST con una política que incluya content-length-range, o verificar después con statObject. El proyecto usa PUT y verificación posterior; si el tamaño es crítico, añade la comprobación antes de publicar el documento.

¿Qué pasa si el cliente sube dos veces a la misma URL?

La segunda escritura sobrescribe la primera. Con versionado, se crea una versión nueva y la anterior queda recuperable, pero el ETag y el tamaño del catálogo pueden quedar desfasados si el complete ya se ejecutó. Para evitarlo, el complete puede guardar el ETag esperado y rechazar si el objeto cambió, o usar claves únicas por intento.

¿Necesito autenticación en la API si las URLs ya están firmadas?

Sí. Las URLs firmadas protegen el acceso a MinIO, no a tu API. Sin autenticación, cualquiera puede crear documentos, listar tenants y pedir descargas. La identidad del usuario decide qué tenant puede usar; la firma solo decide qué operación de almacenamiento se permite.
