Credenciales root

Módulo 3 · Seguridad 🕐 30 minutos

1 · Introducción

Todo MinIO arranca con un usuario root: la identidad que existe antes de que existan usuarios, políticas o buckets. Es la llave con la que se abre la puerta por primera vez. El problema empieza cuando esa llave se queda puesta en la cerradura: la aplicación la usa para todo, el equipo la comparte por chat y acaba en un .env que alguien sube a Git.

Root no es «un usuario con todos los permisos». Es una identidad fuera del sistema de políticas: no hay forma de limitarla por prefijo, por acción ni por bucket, y no se puede deshabilitar ni borrar. Si se filtra, el atacante puede leer todos los objetos, borrar buckets, crear usuarios y cambiar políticas. No hay recuperación parcial; hay que rotar y auditar.

La postura correcta es sencilla de enunciar y fácil de romper: root se usa para el arranque y para tareas de plataforma puntuales; las aplicaciones usan usuarios con permisos acotados. Esta lección cubre cómo se define root, cómo se entrega el secreto, cómo se rota y qué señales indican que ya está comprometido.

El default es peor de lo que crees

Si no defines MINIO_ROOT_USER y MINIO_ROOT_PASSWORD, MinIO arranca con minioadmin:minioadmin. No es un ejemplo de la documentación: es el valor real. Un servidor con el puerto 9000 expuesto y credenciales por defecto no está «sin configurar», está abierto.

2 · Teoría

Qué es exactamente el usuario root

MinIO crea la identidad root al arrancar, leyendo estas dos variables:

MINIO_ROOT_USER=minio-root
MINIO_ROOT_PASSWORD=una-frase-larga-y-aleatoria-de-40-caracteres
PropiedadRootUsuario IAM
Quién lo creaEl servidor, al arrancarUn administrador con mc admin user add
PermisosTodos, siempreLos de sus políticas adjuntas
Se puede limitarNoSí, por acción y recurso
Se puede deshabilitarNoSí, con mc admin user disable
Cómo se cambiaVariables de entorno y reinicioComandos de administración en caliente
Uso previstoArranque y operación de plataformaAplicaciones y personas

La longitud mínima que exige MinIO es de 3 caracteres para el usuario y 8 para la contraseña. Eso es un suelo técnico, no una recomendación: una contraseña de 8 caracteres se rompe con fuerza bruta offline en muy poco tiempo. Usa cadenas aleatorias de 32 caracteres o más, generadas con un gestor de secretos.

Se leen al arrancar, no en cada petición

Cambiar la variable de entorno de un contenedor en marcha no cambia la contraseña: el proceso ya leyó el valor. La rotación siempre implica reiniciar el servidor (o todos los nodos, en un clúster).

Root frente a administrador delegado

Hay dos formas de «tener permisos de administración». Root es la identidad irreducible. consoleAdmin es una política integrada que puedes adjuntar a un usuario normal y que permite gestionar el servidor sin ser root. La diferencia práctica: al usuario consoleAdmin puedes deshabilitarlo, rotarle el secreto o quitarle la política; a root, no.

root  ------------------------------------------->  todo, sin límites
  |
  +-- se usa UNA vez: crear el primer admin delegado
        |
        +-- ops-admin (consoleAdmin) ------------->  administración diaria
              |
              +-- app-documentos (política propia) ->  solo su prefijo
                    |
                    +-- svcacct (opcional) --------->  credencial de un job

El objetivo es que, después del arranque, nadie necesite root para el día a día. Si tu aplicación tiene las credenciales root, cualquier error de código se convierte en un error con permisos totales.

Cómo se entrega el secreto

MétodoCuándoRiesgo
docker compose con env_fileDesarrollo localEl valor queda en docker inspect y en el entorno del proceso.
Fichero de entorno montado y MINIO_CONFIG_ENV_FILEServidor único, baremetal o contenedorHay que proteger permisos del fichero (0600) y no versionarlo.
Secret de Docker o KubernetesProducciónEl secreto sigue existiendo en el plano de control; controla quién lo lee.
Vault, AWS Secrets Manager, SOPSProducción con auditoríaRequiere integrar la inyección al arrancar; no lo metas en una imagen.

MinIO permite apuntar a un fichero de entorno con MINIO_CONFIG_ENV_FILE. Es la vía más limpia en contenedores: el secreto no aparece en la línea de comandos ni en la definición del servicio.

Rotación: qué cambia y qué deja de funcionar

Rotar root significa arrancar el servidor con un valor nuevo. No hay un comando «cambiar contraseña de root» en caliente. El procedimiento seguro tiene un orden:

  1. Antes: crea o verifica un usuario consoleAdmin con su propio secreto. Es tu red de seguridad si algo falla.
  2. Genera el nuevo secreto y guárdalo en el gestor de secretos, no en un ticket.
  3. Actualiza el fichero o el secret que lee el servidor.
  4. Reinicia MinIO. En un clúster, todos los nodos deben acabar con las mismas credenciales root.
  5. Verifica que el valor viejo falla y el nuevo funciona; comprueba también el admin delegado.
  6. Actualiza cualquier automatización que aún usara root. Revisa los logs de acceso de las últimas horas.

Consecuencias inmediatas de la rotación:

  • Las presigned URLs firmadas con el secreto anterior dejan de ser válidas, aunque no hayan expirado.
  • Los procesos que tenían root en memoria empiezan a recibir InvalidAccessKeyId o SignatureDoesNotMatch.
  • Las sesiones de consola abiertas con root se invalidan.

En un clúster, la rotación no es instantánea

Todos los nodos deben compartir las mismas credenciales root. Durante un reinicio escalonado conviven nodos con secretos distintos, y una petición firmada con el nuevo valor puede caer en un nodo que aún tiene el viejo. Planifica una ventana o actualiza todos los nodos a la vez; no lo hagas en horario de pico.

Qué puede hacer un root comprometido

AcciónImpacto
Leer cualquier objetoExfiltración completa de documentos, backups y secretos almacenados.
Borrar objetos y bucketsPérdida de datos; sin versionado, irreversible.
Crear usuarios y políticasPersistencia: el atacante se crea su propia puerta trasera.
Cambiar configuraciones del servidorDesactivar cifrado, cambiar CORS, alterar lifecycle.
Leer configuraciones y metadatosDescubrir otros servicios, endpoints y credenciales de terceros.

Por eso una filtración de root no se trata como «cambio de contraseña»: se trata como incidente. Rota, revisa usuarios creados, revisa políticas modificadas, revisa accesos y, si hay datos sensibles, asume exfiltración hasta que los logs demuestren lo contrario.

3 · Ejemplo mínimo

Un compose.yml que no pone el secreto en el YAML: lo lee de un fichero de entorno montado como secret.

services:
  minio:
    image: quay.io/minio/minio
    command: server /data --console-address ":9001"
    ports:
      - "9000:9000"
      - "9001:9001"
    environment:
      MINIO_CONFIG_ENV_FILE: /run/secrets/minio_env
    secrets:
      - minio_env
    volumes:
      - minio-data:/data

secrets:
  minio_env:
    file: ./secrets/minio.env

volumes:
  minio-data:
# secrets/minio.env — nunca se versiona
MINIO_ROOT_USER=minio-root
MINIO_ROOT_PASSWORD=K7f2pQ9xR4mT8vL3nB6cW1sH5jD0aZ2e
chmod 600 secrets/minio.env
docker compose up -d

Qué hace cada pieza:

  • MINIO_CONFIG_ENV_FILE le dice a MinIO que cargue variables desde ese fichero, con el mismo formato que un .env.
  • El secret de Compose monta el fichero en /run/secrets/minio_env, fuera del contexto de la imagen.
  • El YAML no contiene el valor: puede ir al repositorio sin filtrar nada.
  • chmod 600 limita la lectura al usuario que ejecuta Compose.

El secreto también está en el host

Un fichero montado sigue existiendo en el disco del servidor. Cifra el volumen, limita el acceso por SSH y rota si sospechas que alguien pudo leerlo. Un secret no es magia: es un secreto con mejor higiene.

4 · Ejemplo real

El arranque del almacén crea un administrador delegado y un usuario de aplicación. Root solo se usa en este script, que se ejecuta desde el pipeline de plataforma con el secreto inyectado.

#!/usr/bin/env bash
# scripts/bootstrap.sh — se ejecuta una vez por entorno
set -euo pipefail

: "${MINIO_URL:?falta MINIO_URL}"
: "${MINIO_ROOT_USER:?falta MINIO_ROOT_USER}"
: "${MINIO_ROOT_PASSWORD:?falta MINIO_ROOT_PASSWORD}"
: "${APP_USER:?falta APP_USER}"
: "${APP_SECRET:?falta APP_SECRET}"
: "${OPS_ADMIN_SECRET:?falta OPS_ADMIN_SECRET}"

mc alias set bootstrap "$MINIO_URL" "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD"

# 1. Administrador delegado para el equipo de plataforma
if ! mc admin user info bootstrap ops-admin >/dev/null 2>&1; then
  mc admin user add bootstrap ops-admin "$OPS_ADMIN_SECRET"
fi
mc admin policy attach bootstrap consoleAdmin --user ops-admin

# 2. Usuario de la aplicación, sin privilegios de administración
if ! mc admin user info bootstrap app-documentos >/dev/null 2>&1; then
  mc admin user add bootstrap app-documentos "$APP_SECRET"
fi
mc admin policy attach bootstrap documentos-rw --user app-documentos

echo "bootstrap completado: root ya no es necesario"

El script es idempotente: si el usuario existe, no falla; si la política ya está adjunta, el comando lo indica y continúa. Eso permite ejecutarlo en cada despliegue sin miedo.

La aplicación recibe solo APP_USER y APP_SECRET. Nunca MINIO_ROOT_*:

# .env.example de la aplicación — nombres, no valores
MINIO_ENDPOINT=minio
MINIO_PORT=9000
MINIO_USE_SSL=false
MINIO_ACCESS_KEY=app-documentos
MINIO_SECRET_KEY=cambia-esto-en-tu-gestor-de-secretos
MINIO_BUCKET=documentos
# .gitignore
.env
.env.*
!.env.example
secrets/
*.pem
*.key

Comprueba que root no se usa

Busca en tus despliegues la cadena MINIO_ROOT_. Debe aparecer solo en el servicio de MinIO y en el script de bootstrap. Si aparece en la API, en un job o en una imagen, tienes una credencial root fuera de su sitio.

6 · Errores habituales

1. Arrancar sin variables y creer que está «sin configurar»

Mal — credenciales por defecto en un puerto público 
services:
  minio:
    image: quay.io/minio/minio
    command: server /data
    ports: ["9000:9000"]   # ❌ minioadmin:minioadmin
Bien — root explícito desde el primer arranque 
    environment:
      MINIO_CONFIG_ENV_FILE: /run/secrets/minio_env
    secrets: [minio_env]

No hay ningún aviso visible: el servidor arranca correctamente. La única forma de detectarlo es saber que el default existe y comprobarlo en el checklist de despliegue.

2. Dar root a la aplicación

Mal — el servicio hereda todos los permisos 
MINIO_ACCESS_KEY=minio-root
MINIO_SECRET_KEY=$MINIO_ROOT_PASSWORD   # ❌ en el contenedor de la API
Bien — usuario con política acotada 
MINIO_ACCESS_KEY=app-documentos
MINIO_SECRET_KEY=$APP_SECRET            # permisos solo sobre documentos/*

Además de reducir el daño, el usuario acotado hace que los errores de código sean detectables: si la aplicación intenta borrar un bucket y recibe AccessDenied, es que estaba haciendo algo que no debía.

3. Rotar el valor sin reiniciar

Mal — el proceso sigue con el secreto viejo 
sed -i 's/^MINIO_ROOT_PASSWORD=.*/MINIO_ROOT_PASSWORD=nuevo/' secrets/minio.env
# ❌ nadie reinició MinIO; la contraseña antigua sigue activa
Bien — reiniciar y verificar ambos valores 
docker compose up -d --force-recreate minio
mc alias set check http://localhost:9000 minio-root 'nuevo-secreto'
mc admin info check

Y verifica también que el valor viejo falla. Si sigue funcionando, el proceso no releyó el fichero o estás hablando con otro nodo.

4. Confiar en .gitignore después de un commit

Mal — borrar el archivo no borra la historia 
git rm --cached .env      # ❌ el secreto sigue en el commit anterior
echo '.env' >> .gitignore
Bien — rotar, purgar y avisar 
git log --all -- .env      # localizar el commit
# rotar el secreto YA; después limpiar historia si el repo es público
# y revisar accesos desde la fecha de exposición

La rotación es lo urgente; la limpieza del historial es lo segundo. Un secreto publicado se considera comprometido aunque el repositorio sea privado.

7 · Ejercicio guiado

Objetivo: arrancar MinIO sin credenciales por defecto, crear un administrador delegado y rotar root comprobando que el valor anterior deja de funcionar.

  1. Genera un secreto largo: 
    openssl rand -base64 36
# en PowerShell:
# [Convert]::ToBase64String((1..36 | ForEach-Object { Get-Random -Max 256 }))

    Guarda el resultado en secrets/minio.env con MINIO_ROOT_USER=minio-root y el secreto en MINIO_ROOT_PASSWORD. Permisos 600.

  2. Levanta el servicio con el compose de la sección 3: 
    docker compose up -d
mc alias set local http://localhost:9000 minio-root 'el-secreto-generado'
mc admin info local
    ●  localhost:9000
   Uptime: 12 seconds
   Version: 2025-xx-xxTxx-xx-xxZ
   Network: 1/1 OK
  3. Comprueba que el default no funciona: intenta mc alias set bad http://localhost:9000 minioadmin minioadmin. Debe devolver AccessDenied o InvalidAccessKeyId. Si entra, el fichero de entorno no se cargó.
  4. Crea el administrador delegado: 
    mc admin user add local ops-admin 'otro-secreto-largo-y-distinto'
mc admin policy attach local consoleAdmin --user ops-admin
mc admin user info local ops-admin

    Comprueba que ops-admin puede ejecutar mc admin info sin usar root.

  5. Rota root: cambia MINIO_ROOT_PASSWORD en el fichero, ejecuta docker compose up -d --force-recreate minio y prueba: 
    mc alias set viejo http://localhost:9000 minio-root 'secreto-anterior'
mc alias set nuevo http://localhost:9000 minio-root 'secreto-nuevo'

    El primero debe fallar con InvalidAccessKeyId o SignatureDoesNotMatch; el segundo debe funcionar. ops-admin debe seguir funcionando.

  6. Busca fugas: ejecuta git log --all -p | grep -n 'MINIO_ROOT_PASSWORD' (en PowerShell, git log --all -p | Select-String MINIO_ROOT_PASSWORD) y revisa que no haya valores en el repositorio. Documenta en el README del proyecto dónde vive el secreto y quién puede leerlo.

Comprobación final

Después de la rotación, mc admin info local con el secreto viejo debe fallar y con el nuevo debe responder. Si el alias viejo sigue guardado en ~/.mc/config.json, bórralo con mc alias remove viejo: no dejes credenciales muertas en disco.

8 · Reto

🎯 Rotación sin caída y detección de uso de root

Diseña el runbook para rotar root en un clúster de cuatro nodos sin que ninguna petición legítima falle. Debe incluir el orden de reinicio, cómo comprobar la consistencia entre nodos, qué hacer si un nodo no arranca con el valor nuevo y cómo revertir sin volver al secreto comprometido.

Además, construye una alerta que detecte uso de root en el día a día: a partir de los logs de auditoría o de los request-id, identifica peticiones firmadas por la identidad root y distingue las del bootstrap de las que vienen de una aplicación mal configurada.

Pista: en un clúster, la credencial root debe ser idéntica en todos los nodos; el problema no es el reinicio, es la ventana en la que conviven secretos distintos. Para la alerta, empieza por saber qué campo del log identifica al firmante.

9 · Resumen

  • Root se define con MINIO_ROOT_USER y MINIO_ROOT_PASSWORD; sin ellas, el default es minioadmin:minioadmin.
  • Root está fuera del sistema de políticas: no se puede limitar, deshabilitar ni borrar.
  • La contraseña mínima son 8 caracteres; usa 32 o más aleatorios.
  • Se lee al arrancar: rotar exige reiniciar y, en clúster, coordinar todos los nodos.
  • La rotación invalida presigned URLs y sesiones firmadas con el secreto anterior.
  • El secreto va por fichero o gestor de secretos, nunca en el YAML, la imagen o el historial de Git.
  • Un root comprometido puede leer, borrar y crear accesos persistentes: trátalo como incidente.

10 · Preguntas frecuentes

¿Puedo deshabilitar o borrar el usuario root?

No. Root existe mientras exista el servidor y no pasa por el sistema de usuarios IAM. Lo que sí puedes hacer es no usarlo: crear un consoleAdmin, usarlo para la operación diaria y dejar root solo para el arranque y la rotación.

¿Qué pasa con las presigned URLs cuando roto root?

Dejan de funcionar inmediatamente, aunque su X-Amz-Expires no haya llegado a cero. La firma se valida con el secreto actual; si el secreto cambia, la firma ya no cuadra. Es una razón más para no firmar con root: al rotarlo rompes enlaces de todos tus clientes.

¿Puedo poner una política a root para limitarlo?

No. Las políticas se evalúan para identidades IAM; root las ignora por diseño. Si necesitas un administrador acotado, crea un usuario con la política consoleAdmin o una política personalizada. Si necesitas un usuario de aplicación, dale solo las acciones S3 sobre su prefijo.

¿Basta con cambiar la contraseña tras una filtración?

No. Un atacante con root pudo crear usuarios, adjuntar políticas o modificar la configuración. Rota, enumera usuarios y políticas, compara con la configuración esperada y revisa los accesos. Si el servidor estuvo expuesto, asume que los datos pudieron copiarse.

¿Root y consoleAdmin son lo mismo en la práctica?

Para muchas operaciones diarias, sí: ambos pueden administrar usuarios, políticas y buckets. La diferencia es el control: a consoleAdmin puedes quitarle la política, deshabilitarlo o rotarle el secreto sin reiniciar el servidor. Root no tiene ese interruptor.
