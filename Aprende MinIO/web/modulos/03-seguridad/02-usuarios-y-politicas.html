Usuarios y políticas

Módulo 3 · Seguridad 🕐 40 minutos

1 · Introducción

En la lección anterior dejamos root donde debe estar: en el arranque. Pero «no usar root» no es una política de seguridad, es una intención. La pregunta real es qué puede hacer cada proceso cuando ya no es root, y cómo lo demuestras antes de que ocurra en producción.

MinIO implementa un subconjunto de IAM: usuarios, grupos, políticas y service accounts. Una política es un documento JSON que dice quién puede hacer qué sobre qué recurso. Bien escrita, convierte un error de código en un AccessDenied inofensivo; mal escrita, convierte cualquier credencial filtrada en acceso total al bucket.

Esta lección construye el modelo mental de evaluación —deny explícito, allow, deny implícito—, escribe políticas por prefijo, distingue política de usuario de política de bucket y prueba el resultado con el mismo cliente que usará la aplicación. El objetivo no es memorizar acciones de S3, sino saber leer una política y predecir qué permitirá.

Mínimo privilegio no es «pocos permisos»

Es exactamente los permisos necesarios para la tarea, ni uno más. Un usuario que solo sube PDF a acme/ no necesita listar el bucket entero, ni borrar, ni tocar otros prefijos. Cada permiso extra es una capacidad que un atacante hereda si roba esa credencial.

2 · Teoría

El modelo de identidad

                 +-------------------+
                 |     política      |  JSON: acciones + recursos
                 +---------+---------+
                           |
          +----------------+----------------+
          |                                 |
     +----v----+                       +----v----+
     |  grupo  |                       | usuario |<---- service account
     +----+----+                       +----+----+      (credencial derivada)
          |                                 |
          +-----------+---------------------+
                      |
                 identidad efectiva
                      |
                 petición S3 firmada

Un usuario puede tener políticas adjuntas directamente y también heredarlas de sus grupos. Los permisos efectivos son la unión de todas sus políticas, menos lo que esté denegado explícitamente. Los service accounts son credenciales hijas de un usuario: no pueden tener más permisos que el padre, pero sí menos, y no sirven para entrar en la consola.

Anatomía de una política

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadWriteOwnPrefix",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": ["arn:aws:s3:::documentos/acme/*"]
    }
  ]
}

Bucket ARN frente a object ARN

Esta distinción explica la mitad de los AccessDenied que verás. Hay acciones que operan sobre el bucket y acciones que operan sobre objetos, y el Resource debe coincidir:

AcciónRecurso correctoQué hace
s3:ListBucketarn:aws:s3:::documentosListar claves del bucket
s3:GetBucketLocationarn:aws:s3:::documentosResolver la región (lo piden muchos SDK)
s3:GetObjectarn:aws:s3:::documentos/acme/*Leer un objeto
s3:PutObjectarn:aws:s3:::documentos/acme/*Escribir un objeto
s3:DeleteObjectarn:aws:s3:::documentos/acme/*Borrar un objeto
s3:AbortMultipartUploadarn:aws:s3:::documentos/acme/*Cancelar una subida multipart
s3:ListMultipartUploadPartsarn:aws:s3:::documentos/acme/*Ver las partes ya subidas

Si pones arn:aws:s3:::documentos/* en ListBucket, el comando falla aunque el usuario pueda leer cada objeto. El bucket y sus objetos son dos recursos distintos, no un prefijo y su contenido.

Cómo se evalúa una petición

petición firmada por una identidad
        |
        v
+---------------------------+
| ¿Hay algún Deny explícito? |---- sí ----> DENEGAR (sin excepciones)
+-------------+-------------+
              | no
              v
+---------------------------+
| ¿Hay algún Allow?         |---- no ----> DENEGAR (implícito)
+-------------+-------------+
              | sí
              v

El denegado implícito es la base del mínimo privilegio: todo lo que no está permitido, está prohibido. El Deny explícito existe para quitar algo que otra política concede; gana siempre, incluso si el usuario es administrador de ese bucket.

Para una aplicación, casi siempre quieres política de usuario. La política de bucket es la excepción: sirve para publicar un prefijo, permitir a otra cuenta o dar acceso sin credenciales. Si te ves escribiendo "Principal": "*" para que funcione una subida, probablemente estés resolviendo el problema equivocado.

Listar solo un prefijo

s3:ListBucket no se puede limitar con el Resource, porque el recurso es el bucket entero. Se limita con la condición s3:prefix, que compara el prefijo que envía la petición:

{
  "Sid": "ListOwnPrefix",
  "Effect": "Allow",
  "Action": ["s3:ListBucket"],
  "Resource": ["arn:aws:s3:::documentos"],
  "Condition": {
    "StringLike": { "s3:prefix": ["acme/*"] }
  }
}

Sin esa condición, el usuario puede enumerar todas las claves del bucket aunque no pueda leerlas. La enumeración filtra nombres, tamaños y fechas: es información, y a veces es suficiente para un ataque.

3 · Ejemplo mínimo

Una política que permite leer y escribir solo bajo acme/, y su usuario.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOwnPrefix",
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": ["arn:aws:s3:::documentos"],
      "Condition": { "StringLike": { "s3:prefix": ["acme/*"] } }
    },
    { "Sid": "Location", "Effect": "Allow", "Action": ["s3:GetBucketLocation"], "Resource": ["arn:aws:s3:::documentos"] },
    {
      "Sid": "ReadWriteOwnPrefix",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": ["arn:aws:s3:::documentos/acme/*"]
    }
  ]
}
mc admin user add local app-documentos 'un-secreto-largo-y-aleatorio'
mc admin policy create local documentos-rw ./policies/documentos-rw.json
mc admin policy attach local documentos-rw --user app-documentos
mc admin user info local app-documentos
AccessKey : app-documentos
Status    : enabled
Policy    : documentos-rw
  • user add crea la identidad con una clave y un secreto; el secreto no se puede recuperar después, solo rotar.
  • policy create registra el JSON en el servidor; si ya existe, lo reemplaza.
  • policy attach une la política al usuario; el cambio es efectivo en la siguiente petición, sin reiniciar.
  • user info muestra el estado y las políticas adjuntas, pero no el secreto.

4 · Ejemplo real

El almacén tiene tres roles: la API sube y lee, el analista solo lee, y nadie puede borrar documentos legales. Las políticas se versionan en proyectos/document-store/policies/ y se aplican con un script, no a mano en la consola.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListTenantPrefix",
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": ["arn:aws:s3:::documentos"],
      "Condition": { "StringLike": { "s3:prefix": ["acme/*"] } }
    },
    { "Sid": "Location", "Effect": "Allow", "Action": ["s3:GetBucketLocation"], "Resource": ["arn:aws:s3:::documentos"] },
    {
      "Sid": "ReadWriteTenant",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": ["arn:aws:s3:::documentos/acme/*"]
    },
    {
      "Sid": "ProtectLegal",
      "Effect": "Deny",
      "Action": ["s3:DeleteObject"],
      "Resource": ["arn:aws:s3:::documentos/acme/*/legal/*"]
    }
  ]
}

El Deny de ProtectLegal gana sobre el Allow de ReadWriteTenant, aunque el recurso esté incluido en el allow. Ese es el patrón para «todo el prefijo, excepto esta rama»: no se escribe una política gigante con exclusiones, se añade un deny quirúrgico.

# Un grupo para todas las aplicaciones del tenant
mc admin group add local apps-acme app-documentos
mc admin policy attach local documentos-rw --group apps-acme

# Un usuario de solo lectura para analítica
mc admin user add local analytics-acme 'otro-secreto-distinto'
mc admin policy attach local documentos-ro --user analytics-acme

# Comprobar quién tiene una política
mc admin policy entities local --policy documentos-rw
Policy: documentos-rw
  User: app-documentos
  Group: apps-acme

Los grupos simplifican la rotación: si mañana cambia el conjunto de permisos de las aplicaciones, editas una política y afectas a todos los miembros. Adjuntar políticas usuario por usuario garantiza que dentro de tres meses haya dos versiones distintas y nadie sepa cuál es la buena.

// La aplicación usa app-documentos: funciona en acme/,
// recibe AccessDenied en otro/ y al borrar en acme/2026/11/legal/.
await client.putObject('documentos', 'acme/2026/11/a.pdf', body, size)

6 · Errores habituales

1. Dar ListBucket sobre el ARN de los objetos

Mal — el recurso no coincide con la acción 
{
  "Action": ["s3:ListBucket"],
  "Resource": ["arn:aws:s3:::documentos/*"]
}
Bien — bucket para listar, objetos para leer 
{
  "Action": ["s3:ListBucket"],
  "Resource": ["arn:aws:s3:::documentos"]
}

El usuario puede leer un objeto concreto si conoce la clave, pero mc ls devuelve AccessDenied. No es un fallo del cliente: la acción de listar pertenece al bucket.

2. Resolver un 403 con s3:* sobre *

Mal — conviertes el usuario en root de facto 
{
  "Effect": "Allow",
  "Action": "s3:*",
  "Resource": ["*"]
}
Bien — la acción y el recurso que hacen falta 
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": ["arn:aws:s3:::documentos/acme/*"]
}

Ampliar permisos hasta que desaparezca el error es la forma más rápida de crear un problema mayor. Si no sabes qué acción falta, mira el AccessDenied con el request-id y reproduce la operación con mc --debug.

3. Olvidar las acciones multipart

Mal — solo PutObject 
"Action": ["s3:PutObject"]   // ❌ falla al completar una subida grande
Bien — incluir el ciclo multipart 
"Action": [
  "s3:PutObject",
  "s3:AbortMultipartUpload",
  "s3:ListMultipartUploadParts"
]

Con objetos pequeños nunca lo ves. El día que alguien sube un vídeo, el SDK parte el archivo, sube las partes y recibe AccessDenied al completar. El objeto no aparece y las partes quedan ocupando espacio hasta que se limpian.

4. Publicar el bucket para evitar firmar

Mal — lectura anónima para todo el mundo 
mc anonymous set download local/documentos   # ❌ todo el bucket es público
Bien — presigned GET acotado o bucket policy por prefijo 
const url = await client.presignedGetObject('documentos', key, 300)
// URL temporal, sin credenciales y con expiración

Un bucket público no distingue entre un enlace compartido y un rastreador que enumera claves. Si necesitas acceso sin credenciales, firma una URL por objeto o publica solo un prefijo con una política explícita y revisada.

7 · Ejercicio guiado

Objetivo: crear un usuario con mínimo privilegio, comprobar qué puede y qué no, y verificar que un Deny explícito gana.

  1. Crea el fichero de política de la sección 4: 
    mkdir -p policies
# guarda el JSON como policies/documentos-rw.json
mc admin policy create local documentos-rw ./policies/documentos-rw.json

    Salida esperada: Created policy documentos-rw successfully.

  2. Crea el usuario y adjunta la política: 
    mc admin user add local app-documentos 'secreto-de-laboratorio-2026'
mc admin policy attach local documentos-rw --user app-documentos
mc admin user info local app-documentos
  3. Prueba lo permitido: 
    mc alias set app http://localhost:9000 app-documentos 'secreto-de-laboratorio-2026'
printf 'hola\n' > nota.txt
mc cp nota.txt app/documentos/acme/2026/11/nota.txt
mc ls app/documentos/acme/2026/11/
    [2026-11-05 11:02:14 CET]     5B STANDARD nota.txt
  4. Prueba lo prohibido por prefijo: 
    mc cp nota.txt app/documentos/otro/2026/11/nota.txt
# mc: <ERROR> Unable to copy. Access Denied.

    Después intenta listar el bucket completo: mc ls app/documentos/ debe fallar por la condición s3:prefix.

  5. Comprueba el Deny explícito: 
    mc cp nota.txt app/documentos/acme/2026/11/legal/nota.txt   # permitido
mc rm app/documentos/acme/2026/11/legal/nota.txt            # denegado

    La escritura entra porque el allow cubre acme/*; el borrado falla porque ProtectLegal lo deniega. Anota el código: AccessDenied.

  6. Revisa la entidad efectiva y rota el secreto: 
    mc admin policy entities local --policy documentos-rw
mc admin user add local app-documentos 'nuevo-secreto-de-laboratorio'
mc alias set app http://localhost:9000 app-documentos 'nuevo-secreto-de-laboratorio'

    El usuario mantiene la política; lo que cambia es el secreto. Comprueba que el alias viejo deja de funcionar.

Comprobación final

Escribe en una tabla las cuatro operaciones probadas y su resultado esperado. Si alguna te sorprende, vuelve al diagrama de evaluación: casi siempre es un recurso con el ARN equivocado o un deny que no esperabas.

8 · Reto

🎯 Políticas como código, con pruebas

Diseña tres roles para el almacén —uploader, reader y auditor— con permisos disjuntos y por prefijo. El uploader no puede leer lo que sube; el reader no puede escribir; el auditor puede listar todo pero solo leer metadatos, no contenido.

Escribe un script de pruebas que, para cada rol, ejecute una lista de operaciones permitidas y denegadas y falle si el resultado no coincide con lo esperado. Debe poder ejecutarse contra un MinIO local y limpiar lo que cree. Añade una comprobación de que ningún rol puede borrar bajo legal/.

Pista: statObject es un HEAD y getObject es un GET; para el auditor necesitas permitir el primero y denegar el segundo. Piensa en qué acción S3 corresponde a cada uno.

9 · Resumen

  • Los permisos efectivos son la unión de las políticas del usuario y sus grupos.
  • Se evalúa en orden: deny explícito, allow, deny implícito. El deny gana siempre.
  • ListBucket se aplica al bucket; GetObject y PutObject, a los objetos.
  • s3:prefix limita el listado a un prefijo, no el Resource.
  • Política de usuario para identidades; política de bucket para acceso anónimo o entre cuentas.
  • Los grupos reducen la deriva y simplifican la rotación.
  • Las políticas se versionan y se prueban con el mismo cliente que usa la aplicación.

10 · Preguntas frecuentes

¿Las políticas se aplican al instante?

Sí. MinIO evalúa la política en cada petición; no hay que reiniciar ni refrescar una caché. Si un cambio no surte efecto, comprueba que adjuntaste la política correcta y que estás usando el alias y el usuario esperados.

¿Puedo impedir que un usuario vea los nombres de otros tenants?

Sí, con la condición s3:prefix en ListBucket. Sin ella, el usuario puede enumerar el bucket aunque reciba AccessDenied al leer los objetos. Los nombres, tamaños y fechas ya son información sensible en muchos contextos.

¿Por qué falla una subida grande si PutObject está permitido?

Porque el SDK usa multipart por encima de cierto tamaño. Necesitas s3:AbortMultipartUpload y s3:ListMultipartUploadParts, y a veces s3:ListBucketMultipartUploads para reanudar. Añádelas si tus objetos pueden superar el umbral de parte.

¿Necesito política de bucket si ya tengo política de usuario?

Para una aplicación con credenciales, no. La política de bucket añade acceso sin identidad (anónimo) o desde otra cuenta, y lleva Principal. Si no necesitas eso, una política de usuario es más fácil de razonar y de auditar.
