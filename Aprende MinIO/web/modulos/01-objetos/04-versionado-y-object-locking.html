Versionado y object locking

Módulo 1 · Objetos y buckets 🕐 35 minutos

1 · Introducción

Un script con un error de variable sobrescribe 4 000 contratos con un fichero vacío. Un `mc rm --recursive --force` mal copiado borra el prefijo del año en curso. Alguien sube una versión corregida de un informe y descubre que la anterior ya no existe. En object storage, sin protección adicional, cada PUT y cada DELETE son definitivos.

El versionado convierte cada escritura en una versión numerada y cada borrado en un marcador que oculta, pero no elimina. El object locking va un paso más allá: impide borrar o modificar versiones durante un periodo de retención, incluso para un administrador. Juntos son la base de la recuperación ante errores humanos y del cumplimiento normativo (WORM: write once, read many).

Esta lección explica cómo se comportan las versiones, qué es un delete marker, qué diferencia hay entre suspender y desactivar, cómo se activa la retención —y por qué solo se puede al crear el bucket—, y cuándo el versionado es una mala idea por coste. Al terminar podrás recuperar un documento borrado y bloquear un contrato durante siete años.

La diferencia entre «borrado» y «oculto»

En un bucket versionado, borrar sin especificar versión no borra datos: crea un marcador. El objeto desaparece de ls, pero sigue ahí. Esa distinción es la que permite deshacer un borrado accidental y la que explica por qué el espacio no baja después de «limpiar» un bucket.

2 · Teoría

Tres estados, no dos

EstadoUn PUT sobre una clave existenteUn DELETE sin versión
DesactivadoSustituye el objeto; no hay historialBorra el objeto de forma permanente
ActivadoCrea una versión nueva con ID únicoCrea un delete marker; las versiones siguen
SuspendidoCrea una versión con ID null y sobrescribe la anterior nullCrea un marcador con ID null

«Suspendido» no es «desactivado». Al suspender, MinIO deja de asignar IDs nuevos, pero conserva todas las versiones anteriores y sigue usando marcadores. Es útil para congelar el crecimiento sin perder el historial; no es una forma de volver al comportamiento simple.

Los objetos que existían antes de activar el versionado reciben el ID null. Si activas versionado después de un incidente, no recuperas lo borrado: solo proteges lo que venga a partir de ese momento.

Versiones y marcadores

PUT contrato.pdf          -> v1  (id 1a2b...)
PUT contrato.pdf          -> v2  (id 3c4d...)   <- latest
PUT contrato.pdf          -> v3  (id 5e6f...)   <- latest
DELETE contrato.pdf       -> delete marker (id 7g8h...)  <- latest
                              GET sin versión -> 404
                              GET versionId=5e6f -> 200 (v3)
DELETE versionId=7g8h     -> se elimina el marcador
                              GET sin versión -> 200 (v3)  <- restaurado

Un delete marker es un objeto de 0 bytes sin datos, con su propio version ID. Ocultar el objeto es su única función. Si borras el marcador, la versión anterior vuelve a ser la actual. Si borras una versión concreta con --version-id, esa versión desaparece para siempre y no se crea ningún marcador.

Dos operaciones que parecen iguales y no lo son

mc rm local/bucket/key sobre un bucket versionado oculta. mc rm --version-id <id> local/bucket/key destruye. Y mc rm --versions destruye todas las versiones. La primera es reversible; las otras dos, no.

Recuperar: dos caminos

SituaciónOperaciónResultado
Borrado accidental (hay marcador)Borrar el delete markerLa versión anterior vuelve a ser la actual
Quieres una versión antigua sin cambiar la actualmc cp --version-id <id> … nuevo-keyUna copia con otra clave
Quieres que una versión antigua sea la actualCopiar esa versión sobre la misma claveSe crea una versión nueva con el contenido antiguo
Quieres eliminar una versión concretamc rm --version-id <id>Irreversible

El tercer caso es el más seguro para «rollback»: no borras historia, publicas una versión nueva que restaura el contenido. La versión defectuosa sigue disponible para auditar qué pasó.

Object locking: WORM de verdad

El versionado protege de un borrado accidental, pero un usuario con permisos puede borrar todas las versiones. El object locking añade una retención que el servidor hace cumplir. Requiere versionado y solo se puede activar al crear el bucket:

mc mb --with-lock local/contratos

No hay un mc bucket lock enable para un bucket existente. Si no lo activaste al crearlo, la única vía es crear otro bucket y migrar los objetos. Esa es una decisión de arquitectura, no un flag que se añade después.

ModoQuién puede saltárseloUso típico
GOVERNANCE Un usuario con permiso s3:BypassGovernanceRetention, usando --bypass Protección operativa contra errores; un administrador puede corregir
COMPLIANCE Nadie, ni siquiera root, hasta que expire el plazo Retención legal, auditoría, contratos
Legal hold Se activa y desactiva con permiso; no tiene fecha Litigios, investigaciones, conservación indefinida

La retención se puede fijar por defecto en el bucket o por versión concreta:

# Retención por defecto para todo objeto nuevo
mc retention set --default GOVERNANCE 30d local/contratos
# Retención de una versión concreta
mc retention set --version-id "$VID" COMPLIANCE 7y local/contratos/2026/acme/CTR-2026-0142.pdf
# Legal hold: sin fecha, hasta que se retire
mc legalhold set local/contratos/2026/acme/CTR-2026-0142.pdf
mc legalhold clear local/contratos/2026/acme/CTR-2026-0142.pdf

COMPLIANCE no se puede acortar ni saltar. Si aplicas siete años en un entorno de pruebas, esos objetos serán imborrables durante siete años. Usa GOVERNANCE para pruebas y COMPLIANCE solo cuando la obligación legal esté clara.

Interacción con lifecycle

El lifecycle y la retención se complementan, pero no se pisan:

  • Lifecycle puede expirar versiones no actuales después de N días, pero no puede borrar una versión retenida antes de que expire su plazo.
  • Los delete markers también se pueden expirar, lo que revela la versión anterior si sigue existiendo.
  • El versionado no guarda diferencias: cada versión ocupa el tamaño completo del objeto. Un fichero de 1 GB reescrito diez veces ocupa 10 GB.
  • Para controlar el coste, define --noncurrent-expire-days y limita el número de versiones que conservas.
# En el bucket documentos: conservar versiones antiguas 90 días
mc ilm rule add --noncurrent-expire-days 90 --prefix "2026/" local/documentos
# Ver las reglas
mc ilm rule ls local/documentos

La retención tiene prioridad: si una versión está bloqueada, el lifecycle no la elimina aunque su regla diga que ya expiró. Cuando la retención termine, la siguiente evaluación del lifecycle podrá limpiarla.

Cuándo no usar versionado

SituaciónPor qué evitarloAlternativa
Temporales que se reescriben cada minutoMiles de versiones por objeto; el coste se disparaPrefijo temporal con lifecycle corto, sin versionado
Caché o artefactos regenerablesNo hay valor en recuperar versionesUn bucket sin versionado, con expiración
Objetos enormes con cambios frecuentesCada versión es una copia completaVersionado solo en la capa de negocio o snapshots
Datos que deben ser inmutables de por vidaEl versionado solo no impide borrar versionesObject lock en modo COMPLIANCE

El versionado no es gratis ni en espacio ni en complejidad operativa. Actívalo donde la recuperación tenga valor y acompáñalo siempre de una política de expiración de versiones no actuales.

3 · Ejemplo mínimo

Activar versionado, crear dos versiones, borrar y recuperar:

mc mb --ignore-existing local/documentos
mc version enable local/documentos
printf 'v1\n' > contrato.txt
mc cp ./contrato.txt local/documentos/2026/acme/contrato.txt
printf 'v2 corregida\n' > contrato.txt
mc cp ./contrato.txt local/documentos/2026/acme/contrato.txt
mc ls --versions local/documentos/2026/acme/
[2026-02-11 10:02:11 CET]    13B 8f3a... v2 2026/acme/contrato.txt
[2026-02-11 10:01:54 CET]     3B 1c9d... v1 2026/acme/contrato.txt

Ahora borra sin especificar versión:

mc rm local/documentos/2026/acme/contrato.txt
mc ls local/documentos/2026/acme/                 # no aparece
mc ls --versions local/documentos/2026/acme/      # aparece el marcador

Para restaurar, identifica el version ID del delete marker y bórralo:

MARKER=$(mc ls --versions --json local/documentos/2026/acme/contrato.txt \
  | jq -r 'select(.isDeleteMarker == true) | .versionId' | head -1)
mc rm --version-id "$MARKER" local/documentos/2026/acme/contrato.txt
mc cat local/documentos/2026/acme/contrato.txt
v2 corregida

Qué ha pasado en cada paso:

  • version enable hace que cada PUT cree una versión con ID único.
  • ls --versions muestra todas, incluidas las que ya no son actuales.
  • rm sin --version-id crea un marcador; no borra bytes.
  • Borrar el marcador revela de nuevo la versión anterior. El contenido no se ha movido.

Si en lugar de borrar el marcador quieres una copia con otro nombre:

mc cp --version-id "$VID" \
  local/documentos/2026/acme/contrato.txt \
  local/documentos/2026/acme/contrato-restaurado.txt

4 · Ejemplo real

El almacén de documentos tiene dos necesidades distintas y, por tanto, dos buckets. El object lock se activa por bucket, no por prefijo: si solo los contratos son WORM, no puedes bloquear documentos/2026/contratos/ sin bloquear también los borradores.

BucketVersionadoRetenciónLifecycle
documentos Activado Sin object lock Versiones no actuales: 90 días; temporales: 7 días
contratos Activado (lo exige el lock) COMPLIANCE 7 años por defecto Solo limpieza de subidas incompletas; no expira versiones retenidas

Creación del bucket inmutable:

mc mb --with-lock local/contratos
mc version info local/contratos
mc retention set --default COMPLIANCE 7y local/contratos
mc retention info local/contratos

Subida de un contrato y comprobación de su retención:

mc cp --attr "tenant=acme;doc-id=CTR-2026-0142" \
  ./contrato.pdf \
  local/contratos/2026/acme/CTR-2026-0142.pdf
VID=$(mc stat --json local/contratos/2026/acme/CTR-2026-0142.pdf | jq -r '.versionID')
mc retention info --version-id "$VID" \
  local/contratos/2026/acme/CTR-2026-0142.pdf
Mode      : COMPLIANCE
Retain Until: 2033-02-11 10:15:00 CET
Version   : 5e6f...

El contrato ya no se puede borrar ni sobrescribir de forma que desaparezca hasta 2033. Un PUT nuevo crea otra versión también retenida; el original sigue intacto. Eso es WORM: se añade, no se modifica.

Un borrado accidental, paso a paso

# El script mal configurado oculta todo el prefijo de 2026
mc rm --recursive local/documentos/2026/
# El listado normal está vacío
mc ls --recursive local/documentos/2026/
# Pero las versiones siguen ahí
mc ls --versions --recursive local/documentos/2026/ | head
# Restaurar un objeto concreto: borrar su marcador más reciente
MARKER=$(mc ls --versions --json local/documentos/2026/informes/acme/INF-2026-0007.pdf \
  | jq -r 'select(.isDeleteMarker == true) | .versionId' | head -1)
mc rm --version-id "$MARKER" local/documentos/2026/informes/acme/INF-2026-0007.pdf
mc stat local/documentos/2026/informes/acme/INF-2026-0007.pdf

Restaurar 4 000 objetos uno a uno no es un plan. Para eso existen los scripts de recuperación masiva o una réplica en otro sitio; el versionado te da la materia prima, no el botón de «deshacer todo». Diseña y prueba el procedimiento antes de necesitarlo.

Legal hold: cuando no hay fecha

mc legalhold set local/contratos/2026/acme/CTR-2026-0142.pdf
mc legalhold info local/contratos/2026/acme/CTR-2026-0142.pdf
mc legalhold clear local/contratos/2026/acme/CTR-2026-0142.pdf

El legal hold es independiente de la retención: un objeto puede tener retención de 30 días y legal hold indefinido. Mientras esté activo, no se puede borrar la versión aunque la retención haya expirado. Se usa para litigios y auditorías, no como sustituto de una política de retención.

Separar por bucket también separa permisos

La aplicación que sube documentos no debería poder borrar versiones de contratos. Al estar en otro bucket, la política se escribe una vez y el radio de impacto de un error queda acotado. Mezclar borradores y contratos en el mismo bucket obliga a políticas por prefijo, que son más frágiles.

5 · Buenas prácticas

HazEvitaPor qué
Activar versionado antes de la primera escritura Activarlo después de un borrado No recupera lo que ya no existe; solo protege lo nuevo.
Definir expiración de versiones no actuales Dejar que el historial crezca sin límite Cada versión ocupa el tamaño completo y se factura.

6 · Errores habituales

1. Activar versionado después del desastre

Mal — creer que recupera el pasado 
# ❌ Los objetos borrados ayer no vuelven por activar versionado hoy.
mc rm --recursive --force local/documentos/2025/
mc version enable local/documentos
Bien — activarlo antes y probar la recuperación 
mc version enable local/documentos
mc cp ./documento.pdf local/documentos/2026/documento.pdf
mc rm local/documentos/2026/documento.pdf
mc ls --versions local/documentos/2026/

El versionado es una decisión previa. Activarlo a posteriori solo cambia el comportamiento de las escrituras futuras; los datos que ya no están no se reconstruyen.

2. «He borrado el bucket y sigue ocupando espacio»

Mal — asumir que rm libera capacidad 
# ❌ En un bucket versionado, esto crea marcadores; el espacio sigue.
mc rm --recursive --force local/documentos/2026/
Bien — decidir explícitamente qué versiones se destruyen 
mc ls --versions --recursive local/documentos/2026/ | wc -l
mc rm --recursive --force --versions --older-than 90d \
  local/documentos/2026/

--versions borra todas las versiones, no solo la actual. Es irreversible. Úsalo con --dry-run y con un criterio de antigüedad, nunca como primer reflejo.

3. Confundir suspender con desactivar

Mal — esperar que suspender haga las escrituras simples 
# ❌ Las versiones antiguas siguen; las nuevas se escriben como "null"
#    y se sobrescriben entre sí. No es lo mismo que desactivar.
mc version suspend local/documentos
Bien — usar el estado que corresponde al objetivo 
mc version enable local/documentos     # historial completo
mc version suspend local/documentos    # congelar nuevas versiones con ID null
mc version info local/documentos

MinIO no permite «desactivar» un bucket que ya tuvo versiones: se suspende. Si necesitas volver al comportamiento simple, crea otro bucket y migra; no hay marcha atrás limpia.

7 · Ejercicio guiado

Objetivo: crear un bucket con object lock, comprobar la retención, borrar con marcador, restaurar y ver la diferencia entre GOVERNANCE y legal hold.

  1. Crea un bucket con lock y comprueba el estado. 
    mc mb --with-lock local/contratos-lab
mc version info local/contratos-lab
mc retention info local/contratos-lab

    El versionado debe aparecer como Enabled. El lock solo existe porque se activó al crear el bucket.

  2. Sube tres versiones del mismo contrato. 
    for v in 1 2 3; do
  printf 'contrato version %s\n' "$v" > contrato.txt
  mc cp ./contrato.txt local/contratos-lab/2026/acme/contrato.txt
done
mc ls --versions local/contratos-lab/2026/acme/

    Deben aparecer tres versiones con IDs distintos; la última es la actual.

  3. Aplica retención GOVERNANCE de un día. 
    mc retention set --default GOVERNANCE 1d local/contratos-lab
VID=$(mc stat --json local/contratos-lab/2026/acme/contrato.txt | jq -r '.versionID')
mc retention set --version-id "$VID" GOVERNANCE 1d local/contratos-lab/2026/acme/contrato.txt
mc retention info --version-id "$VID" local/contratos-lab/2026/acme/contrato.txt

    Anota la fecha Retain Until. Intenta borrar esa versión sin bypass: debe fallar con AccessDenied.

  4. Comprueba el bypass de GOVERNANCE. 
    mc rm --version-id "$VID" local/contratos-lab/2026/acme/contrato.txt
mc rm --bypass --version-id "$VID" local/contratos-lab/2026/acme/contrato.txt

    El primer comando falla; el segundo funciona porque root tiene el permiso de bypass. Con COMPLIANCE, el segundo también fallaría. No uses COMPLIANCE en este laboratorio.

  5. Prueba el legal hold. 
    mc legalhold set local/contratos-lab/2026/acme/contrato.txt
mc legalhold info local/contratos-lab/2026/acme/contrato.txt
mc rm local/contratos-lab/2026/acme/contrato.txt   # falla
mc legalhold clear local/contratos-lab/2026/acme/contrato.txt
mc rm local/contratos-lab/2026/acme/contrato.txt   # ahora crea marcador

    El legal hold no tiene fecha: mientras esté activo, la versión actual no se puede borrar. Retirarlo requiere permiso explícito.

  6. Restaura el borrado y limpia con criterio. 
    MARKER=$(mc ls --versions --json local/contratos-lab/2026/acme/contrato.txt \
  | jq -r 'select(.isDeleteMarker == true) | .versionId' | head -1)
mc rm --version-id "$MARKER" local/contratos-lab/2026/acme/contrato.txt
mc cat local/contratos-lab/2026/acme/contrato.txt
mc rm --recursive --force --versions local/contratos-lab/2026/acme/
mc ls --versions local/contratos-lab/2026/acme/

    Tras borrar el marcador, el contrato vuelve. La limpieza final destruye todas las versiones: es el paso irreversible y solo se hace en un bucket de laboratorio.

8 · Reto

🎯 Retención a siete años sin arruinar el presupuesto

Diseña la política de retención del archivo legal: contratos firmados durante siete años, borradores durante 90 días, versiones intermedias de un contrato durante un año y subidas incompletas durante tres días. El equipo quiere poder liberar un contrato antes si hay una orden judicial, pero no quiere que un administrador pueda borrarlo por error.

Define buckets, modos de retención, legal holds, reglas de lifecycle y permisos. Calcula el crecimiento esperado si cada contrato se reescribe tres veces antes de firmarse y explica cómo evitarías pagar siete años por las versiones intermedias. Incluye cómo verificarías que la política funciona sin esperar siete años.

Pista: COMPLIANCE no se puede acortar, así que la liberación anticipada no puede depender de borrar la versión. Piensa en qué se conserva, qué se puede expirar y cómo separar el original firmado de sus borradores. GOVERNANCE y legal hold responden a amenazas distintas.

9 · Resumen

  • El versionado convierte cada escritura en una versión con ID y cada borrado en un delete marker.
  • GET sin versión devuelve la última; con versionId, la que pidas, incluso detrás de un marcador.
  • Borrar el marcador restaura la versión anterior; borrar una versión concreta es permanente.
  • Suspender no es desactivar: las versiones antiguas siguen y las nuevas usan el ID null.
  • El object lock exige versionado y solo se activa al crear el bucket con mc mb --with-lock.
  • GOVERNANCE se puede saltar con permiso; COMPLIANCE no se puede saltar ni acortar; el legal hold no tiene fecha.
  • Lifecycle expira versiones no actuales, pero nunca antes de que termine la retención.
  • Cada versión ocupa el tamaño completo: sin política de expiración, el coste crece rápido.

10 · Preguntas frecuentes

¿El versionado protege contra ransomware?

Solo parcialmente. Si el atacante tiene credenciales que pueden borrar versiones, puede destruir el historial. Para una protección real necesitas object lock en modo COMPLIANCE, permisos de mínimo privilegio que impidan borrar versiones y una réplica en otro sistema. El versionado solo evita el borrado accidental de la versión actual; no es un plan de recuperación por sí mismo.

¿Cuánto ocupa una versión?

El tamaño completo del objeto. MinIO no guarda diferencias incrementales entre versiones. Un PDF de 2 MB con diez versiones ocupa unos 20 MB, más los metadatos. Por eso conviene expirar versiones no actuales y separar los objetos que se reescriben mucho de los que son inmutables por naturaleza.

¿Puedo desactivar el versionado por completo?

No en un bucket que ya lo tuvo: se suspende. Al suspender, las versiones existentes se conservan y las nuevas escrituras usan el ID null, sobrescribiéndose entre sí. Si necesitas un bucket sin historial, crea uno nuevo y migra solo la versión actual con mc mirror o mc cp.

¿Puedo activar object lock en un bucket existente?

No. El object lock se configura al crear el bucket, porque cambia el comportamiento de versionado y retención desde el primer objeto. Si no lo activaste, crea un bucket nuevo con mc mb --with-lock, copia los objetos y actualiza la aplicación. Planifica esta decisión antes de la primera escritura, no después de la auditoría.
