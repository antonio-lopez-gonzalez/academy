Kubernetes Operator

Módulo 6 · Integración 🕐 35 minutos

1 · Introducción

Docker Compose te dio un MinIO de un solo proceso para desarrollar. Pero un clúster distribuido no se levanta con un docker compose up: necesita varios nodos, discos independientes, arranque ordenado, certificados y una forma de crecer sin perder datos. En Kubernetes eso se hace con el MinIO Operator.

El Operator no es «MinIO en un pod». Es un controlador que entiende un recurso propio, el Tenant, y se encarga de crear los StatefulSets, los servicios, los PVC y la configuración de TLS para que el clúster exista y se repare. Tú declaras el estado deseado; el Operator lo reconcilia.

Esta lección explica el modelo, muestra un Tenant mínimo y otro realista, y deja claros los límites: el modo distribuido soportado es Kubernetes o baremetal, nunca Compose; y un tenant que nace de un solo servidor no se convierte en distribuido cambiando un número.

Por qué existe esta lección

Porque «tenemos Kubernetes» no significa «tenemos almacenamiento de objetos». El Operator es la pieza que convierte Kubernetes en una plataforma capaz de operar MinIO con erasure coding, actualizaciones controladas y certificados. Sin entender el CRD, un kubectl apply se convierte en una caja negra que nadie se atreve a tocar.

2 · Teoría

El patrón Operator en una frase

Un Operator es un controlador que ejecuta un bucle de reconciliación: lee el estado deseado de un recurso personalizado (CRD), compara con el estado real y actúa hasta que coinciden. En MinIO el recurso se llama Tenant, vive en el grupo minio.min.io/v2 y describe la imagen, las credenciales, los pools de servidores y el almacenamiento.

kubectl apply -f tenant.yaml
          |
          v
+----------------------+        +---------------------------+
| Kubernetes API       | <----> | MinIO Operator            |
| Tenant (minio.min.io)|        | reconcile loop            |
+----------------------+        +-------------+-------------+
                                             |
              +------------------------------+---------------------------+
              v                              v                           v
      StatefulSet minio            Services (S3, console, hl)     PVCs por servidor
      pods myminio-pool-0-{0..3}   myminio / myminio-console      4 por pod, RWO

Qué crea exactamente un Tenant

CampoQué controlaConsecuencia
spec.imageImagen y versión de MinIOCambiarla dispara una actualización gradual.
spec.configurationSecret con config.env (root, opciones)Sin él, el tenant no arranca con credenciales válidas.
spec.pools[].serversPods de MinIO en ese pool4 o más para distribuido; 1 es standalone.
spec.pools[].volumesPerServerDiscos por servidorMás discos, más erasure coding y más paralelismo.
spec.pools[].volumeClaimTemplateTamaño y StorageClass de cada PVCDefine capacidad, IOPS y tolerancia a fallos.
spec.mountPath / subPathDónde se montan los datosNo se cambian después: partirías los datos en dos rutas.

spec.features.bucketDNSAcceso bucket.tenant.ns.svcÚtil, pero exige DNS y comodines correctos.

Pools: la unidad de crecimiento

Un clúster MinIO se compone de uno o más pools. Cada pool aporta un conjunto de servidores y discos; los datos se distribuyen entre todos. Para crecer se añade un pool, no se redimensiona el existente. El nombre del pool debe ser único y conviene que sea secuencial (pool-0, pool-1).

Cada servidor de un pool debe tener al menos un volumen, y lo habitual son cuatro. Con servers: 4 y volumesPerServer: 4 tienes 16 discos; MinIO calcula la paridad sobre ellos. Si el StorageClass entrega discos del mismo nodo físico, la tolerancia teórica no te salva de perder ese nodo: la topología importa tanto como el número.

El modo no se cambia en caliente

El Operator no soporta convertir un tenant standalone (servers: 1) en distribuido. Si necesitas alta disponibilidad, crea el tenant desde el principio con cuatro o más servidores y migra los datos con mc mirror o réplica. Cambiar servers en un pool existente no es una operación de escalado válida.

Almacenamiento: el punto donde fallan los laboratorios

MinIO está diseñado para discos directos o volúmenes de bloque, con un sistema de archivos local (XFS recomendado). No uses NFS ni un volumen compartido entre pods para los datos: el erasure coding asume que cada disco falla de forma independiente, y compartir el mismo backend convierte un fallo en una pérdida global.

  • Cloud: StorageClass de bloque (EBS, PD, Azure Disk) con ReadWriteOnce.
  • Baremetal: discos locales con un provisioner como local-path o OpenEBS, y anti-affinity para repartir pods.
  • Laboratorio: local-path en un clúster de un nodo sirve para aprender, no para afirmar alta disponibilidad.

TLS, consola y acceso

Con requestAutoCert: true, el Operator solicita certificados al API de Kubernetes y los renueva. En producción es más común desactivarlo y usar cert-manager: creas un Certificate, y referencias el secret resultante en spec.externalCertSecret con tipo kubernetes.io/tls.

El tenant expone dos servicios: la API S3 y la consola. El Operator, además, tiene su propia consola para administrar tenants. Para un acceso puntual, kubectl port-forward es suficiente; para usuarios, publica la API detrás de un Ingress con TLS y no expongas la consola sin autenticación adicional.

Actualizaciones y capacidad

Cambiar spec.image inicia una actualización gradual de los pods. El Operator espera a que el clúster esté sano antes de continuar; aun así, una actualización es un cambio de versión de datos y merece backup, ventana y un plan de vuelta atrás. Añadir un pool es la forma soportada de ampliar capacidad; después puedes lanzar un rebalanceo para redistribuir datos antiguos. Cambiar mountPath o convertir un standalone en distribuido no son operaciones de escalado: son migraciones.

3 · Ejemplo mínimo

Instala el Operator y comprueba que el CRD existe. En producción fija una versión; aquí usamos la referencia principal para el laboratorio:

kubectl apply -k "github.com/minio/operator"
kubectl get pods -n minio-operator
kubectl get crd tenants.minio.min.io

NAME                              READY   STATUS    RESTARTS   AGE
minio-operator-7d9f8c6b5d-abcde   1/1     Running   0          42s
console-6f7c9d8b4f-xyz12          1/1     Running   0          42s

NAME                    CREATED AT
tenants.minio.min.io    2026-11-05T10:00:00Z

El Tenant más pequeño posible necesita credenciales y un pool. Este es el esqueleto, sin recursos ni TLS, para un laboratorio de un solo servidor:

apiVersion: v1
kind: Secret
metadata:
  name: storage-configuration
  namespace: storage
type: Opaque
stringData:
  config.env: |
    export MINIO_ROOT_USER=minioadmin
    export MINIO_ROOT_PASSWORD=cambia-esto
---
apiVersion: minio.min.io/v2
kind: Tenant
metadata:
  name: myminio
  namespace: storage
spec:
  image: quay.io/minio/minio:latest
  configuration:
    name: storage-configuration
  mountPath: /export
  requestAutoCert: true
  pools:
    - name: pool-0
      servers: 1
      volumesPerServer: 4
      volumeClaimTemplate:
        metadata:
          name: data
        spec:
          accessModes: ["ReadWriteOnce"]
          resources:
            requests:
              storage: 2Gi

Qué hace cada pieza:

  • config.env es el formato que espera MinIO para variables de entorno; el secret se monta en los pods.
  • namespace: storage debe existir antes de aplicar; el Operator no lo crea por ti.
  • servers: 1 produce un standalone: útil para probar el CRD, sin tolerancia a fallos.
  • volumesPerServer: 4 crea cuatro PVC por pod, aunque haya un solo pod.
  • requestAutoCert: true activa TLS automático; el cliente deberá confiar en el certificado o usar --insecure en el laboratorio.

4 · Ejemplo real

El almacén de documentos necesita un tenant distribuido, con discos separados, TLS de cert-manager y límites de recursos. Este manifiesto es el que llevarías a un clúster de producción (ajustando StorageClass, tamaños y dominios):

apiVersion: minio.min.io/v2
kind: Tenant
metadata:
  name: documentos
  namespace: storage
spec:
  image: quay.io/minio/minio:RELEASE.2025-04-22T22-12-26Z
  configuration:
    name: documentos-configuration
  mountPath: /export
  requestAutoCert: false
  externalCertSecret: [{ name: documentos-tls, type: kubernetes.io/tls }]
  pools:
    - name: pool-0
      servers: 4
      volumesPerServer: 4
      resources:
        requests: { cpu: "2", memory: 8Gi }
        limits: { memory: 8Gi }
      volumeClaimTemplate:
        spec:
          accessModes: ["ReadWriteOnce"]
          storageClassName: fast-block
          resources: { requests: { storage: 500Gi } }
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  v1.min.io/tenant: documentos
              topologyKey: kubernetes.io/hostname

Las decisiones importantes, una a una:

DecisiónPor qué
4 servidores × 4 discosDistribuido real, con paridad y tolerancia a fallos de disco y de pod.
Imagen fijadaUna actualización no ocurre por sorpresa; el cambio es explícito y revisable.
Anti-affinity por hostnameEvita que los cuatro pods caigan en el mismo nodo y compartan destino.
cert-managerRotación y emisión fuera del Operator, con el mismo flujo que el resto de servicios.
storageClassName: fast-blockEl rendimiento y la durabilidad dependen del disco, no del YAML.

El flujo de despliegue completo:

kubectl create namespace storage --dry-run=client -o yaml | kubectl apply -f -

kubectl create secret generic documentos-configuration \
  --namespace storage \
  --from-literal=config.env='export MINIO_ROOT_USER=admin-documentos
export MINIO_ROOT_PASSWORD=una-clave-larga-y-aleatoria'

kubectl apply -f documentos-tls.yaml
kubectl apply -f tenant.yaml
kubectl get tenant -n storage
kubectl get pods -n storage -l v1.min.io/tenant=documentos
kubectl get pvc -n storage

NAME         STATE     HEALTH   POOLS   AGE
documentos   ready     green    1       3m

NAME               READY   STATUS    RESTARTS
documentos-pool-0-0 1/1    Running   0
documentos-pool-0-1 1/1    Running   0
documentos-pool-0-2 1/1    Running   0
documentos-pool-0-3 1/1    Running   0

Con el tenant sano, configuras el alias y creas el bucket. Desde dentro del clúster usa el servicio; desde tu máquina, un port-forward temporal:

kubectl port-forward -n storage svc/documentos 9000:9000 &
mc alias set documentos https://localhost:9000 admin-documentos 'una-clave-larga-y-aleatoria' --insecure
mc mb documentos/documentos
mc admin info documentos

6 · Errores habituales

1. Escalar cambiando servers

Mal — de 1 a 4 en el mismo pool 
pools:
  - name: pool-0
    servers: 4   # antes 1; el Operator no soporta esta conversión
Bien — crear el tenant distribuido desde el inicio o migrar 
pools:
  - name: pool-0
    servers: 4
    volumesPerServer: 4

Si ya tienes datos en un standalone, crea otro tenant y copia con mc mirror --preserve o configura réplica. Intentar el cambio in-place deja el tenant en un estado que el Operator no garantiza.

2. Usar NFS o un volumen compartido

Mal — un único backend para todos los «discos» 
volumeClaimTemplate:
  spec:
    accessModes: ["ReadWriteMany"]
    storageClassName: nfs-slow
Bien — un volumen de bloque por servidor 
volumeClaimTemplate:
  spec:
    accessModes: ["ReadWriteOnce"]
    storageClassName: fast-block
    resources:
      requests:
        storage: 500Gi

Compartir el backend anula la premisa de fallos independientes. Además, el rendimiento de NFS suele ser incompatible con la carga de MinIO.

3. Desplegar sin límites ni anti-affinity

Mal — cuatro pods en el mismo nodo sin recursos 
pools:
  - servers: 4
    volumesPerServer: 4   # sin resources ni affinity
Bien — reservar recursos y repartir 
resources:
  requests: { cpu: "2", memory: 8Gi }
  limits: { memory: 8Gi }
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - topologyKey: kubernetes.io/hostname

Sin límites, un pico de MinIO puede provocar el desalojo de otros servicios; sin anti-affinity, la alta disponibilidad es solo un número en el YAML.

7 · Ejercicio guiado

Objetivo: desplegar un tenant distribuido de laboratorio, comprobar que el Operator crea los PVC y que el clúster sobrevive a la pérdida de un pod.

  1. Crea un clúster de laboratorio y el namespace: 
    kind create cluster --name minio-lab
kubectl create namespace storage
kubectl config set-context --current --namespace=storage

    Un solo nodo es suficiente para el ejercicio; recuerda que no representa alta disponibilidad real.

  2. Instala el Operator y espera a que esté listo: 
    kubectl apply -k "github.com/minio/operator"
kubectl wait --for=condition=available deployment/minio-operator -n minio-operator --timeout=180s
kubectl get crd tenants.minio.min.io
  3. Crea el secret y el tenant de 4 servidores × 2 discos: 
    kubectl create secret generic lab-configuration \
  --from-literal=config.env='export MINIO_ROOT_USER=labadmin
export MINIO_ROOT_PASSWORD=labadmin-secreto'

    Aplica un Tenant como el de la sección 4, cambiando servers: 4, volumesPerServer: 2, storage: 2Gi, storageClassName: standard y sin externalCertSecret (requestAutoCert: true).

  4. Observa los recursos creados: 
    kubectl get tenant,pods,pvc -n storage
kubectl get statefulset -n storage

    Espera 4 pods Running y 8 PVC Bound (4 servidores × 2 volúmenes). El número exacto de PVC es la primera comprobación de que entendiste el pool.

  5. Conecta, escribe y comprueba la recuperación: 
    kubectl port-forward svc/myminio 9000:9000 &
mc alias set lab https://localhost:9000 labadmin labadmin-secreto --insecure
mc mb lab/documentos
printf 'hola desde kubernetes\n' > nota.txt
mc cp nota.txt lab/documentos/pruebas/nota.txt
kubectl delete pod myminio-pool-0-1 -n storage
kubectl get pods -n storage -w
mc cat lab/documentos/pruebas/nota.txt

    El pod vuelve a arrancar y el objeto sigue disponible. Con mc admin info lab verás el estado de los discos y del pool. Si el objeto desapareciera, revisa que los PVC sean independientes y no un único volumen compartido.

Comprobación final

Borra el tenant con kubectl delete tenant myminio -n storage y observa qué recursos quedan. Los PVC pueden conservarse según la política de retención: entender qué sobrevive a un borrado es parte de operar el almacenamiento.

8 · Reto

🎯 Del Compose al clúster sin perder un byte

Diseña un plan de migración desde el MinIO de un solo nodo que usas en desarrollo hacia un tenant del Operator con cuatro servidores y TLS. El plan debe cubrir: creación del tenant, copia de buckets y objetos, usuarios y políticas, configuración de lifecycle y notificaciones, cambio de endpoint en la aplicación, verificación de integridad y vuelta atrás si algo falla.

Incluye una tabla de ventana y riesgos, y decide qué harías con las credenciales root y con las URLs presignadas que estén vivas durante el cambio. No escribas el resultado: deja el plan en un documento y critícalo como si fueras el revisor de guardia.

Pista: mc mirror --preserve copia objetos y metadatos, pero no copia políticas, usuarios ni configuración de eventos. Todo lo que no sea datos hay que recrearlo y probarlo por separado.

9 · Resumen

  • El Operator reconcilia un CRD Tenant y crea StatefulSets, servicios y PVC por ti.
  • pools[].servers y volumesPerServer definen la topología; 4 servidores es el mínimo razonable para distribuido.
  • El modo standalone no se convierte en distribuido: se migra a otro tenant.
  • Los datos necesitan discos de bloque independientes; NFS y volúmenes compartidos no valen.
  • TLS se resuelve con auto-certificados o con cert-manager y externalCertSecret.
  • Se crece añadiendo pools; se actualiza cambiando la imagen, con backup y ventana.
  • Compose sigue siendo solo para un nodo de desarrollo.

10 · Preguntas frecuentes

¿Puedo usar Docker Compose para un clúster distribuido?

No es un modo soportado. Compose sirve para un único proceso de MinIO en desarrollo. Para distribuido, usa el Operator en Kubernetes o la instalación baremetal con varios servidores y discos. Montar cuatro contenedores con Compose puede parecer que funciona, pero no tendrás las garantías ni el soporte de una topología validada.

¿Cuántos servidores y discos necesito para empezar?

El ejemplo canónico es 4 servidores × 4 discos, que da 16 discos y permite tolerar fallos. Menos discos reducen la protección; más discos aumentan el rendimiento y la capacidad pero también el coste. La decisión depende de la criticidad y del presupuesto, no de una fórmula única.

¿El Operator crea el namespace y el secret de credenciales?

El namespace lo creas tú. El secret de configuración también: el Tenant solo lo referencia por nombre. Así las credenciales no quedan escritas en el CRD y pueden gestionarse con tu flujo habitual de secretos.

¿Cómo actualizo MinIO sin downtime?

El Operator hace una actualización gradual, pero «sin downtime» depende de que haya réplicas sanas y de que la aplicación reintente. Antes de cambiar la imagen, prueba en staging, haz backup y verifica que la versión nueva es compatible con tus datos. Un clúster de un solo servidor no puede actualizarse sin interrupción.
