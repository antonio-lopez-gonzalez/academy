Compatibilidad con AWS SDK

Módulo 6 · Integración 🕐 35 minutos

1 · Introducción

Hasta ahora has usado minio-js y mc contra MinIO. Ambos hablan la misma API S3, pero si mañana el almacenamiento se contrata en AWS, se migra a otro proveedor compatible o la empresa exige un SDK con soporte corporativo, no quieres reescribir la aplicación. Quieres cambiar configuración, no código.

El SDK v3 de AWS para JavaScript es la otra mitad de esa promesa. Es modular, está escrito en TypeScript, funciona en Node.js 22 y firma cada petición con Signature Version 4 (SigV4). MinIO valida esa misma firma. La compatibilidad no es magia: es un contrato HTTP con un conjunto de operaciones y unos cuantos matices que conviene conocer antes de encontrarlos en producción.

En esta lección conectaremos @aws-sdk/client-s3 a MinIO, generaremos presigned URLs con @aws-sdk/s3-request-presigner y separaremos lo que es portable de lo que es propio de cada implementación. Los tres fallos clásicos —estilo de URL, región y checksums— aparecen casi siempre en la primera conexión, así que los trataremos con detalle.

Por qué existe esta lección

La API S3 es el estándar de facto del almacenamiento de objetos. Aprender un SDK propietario te ata a un proveedor; aprender el contrato S3 te permite usar MinIO en local, AWS en la nube y un tercero compatible en el mismo código. La diferencia está en cinco líneas de configuración y en una batería de pruebas de compatibilidad.

2 · Teoría

Qué viaja realmente por el cable

El SDK no envía «sube este archivo». Construye una petición HTTP con un método, una ruta, unas cabeceras y un cuerpo; después calcula una firma sobre todos esos elementos. En SigV4 la firma cubre, entre otros, el método, la ruta canónica, los parámetros de consulta, las cabeceras firmadas y el hash del cuerpo. Cambiar una barra en la ruta o el valor de Host invalida la firma.

PUT /documentos/2026/informe.pdf HTTP/1.1
Host: localhost:9000
x-amz-date: 20261105T101500Z
x-amz-content-sha256: e3b0c442...
Authorization: AWS4-HMAC-SHA256 Credential=documentos-app/20261105/us-east-1/s3/aws4_request,
               SignedHeaders=host;x-amz-content-sha256;x-amz-date,
               Signature=5f2c...

        firma = HMAC-SHA256(clave derivada, petición canónica)
        si un byte cambia -> SignatureDoesNotMatch

De ahí salen las tres constantes de configuración que veremos una y otra vez: endpoint (a qué host se envía), región (qué ámbito usa la firma) y estilo de ruta (cómo se coloca el bucket en la URL).

Path-style frente a virtual-hosted-style

AWS prefiere https://bucket.s3.amazonaws.com/key. MinIO, en local, no tiene DNS comodín para cada bucket, así que espera http://localhost:9000/bucket/key. Si el SDK usa el estilo virtual, intenta resolver documentos.localhost y falla antes de enviar nada.

VIRTUAL-HOSTED (AWS)                 PATH-STYLE (MinIO local)
+------------------------------+      +------------------------------+
| https://bucket.s3.../k       |      | http://localhost:9000/bucket/k|
| Host: bucket.s3.amazonaws.com|      | Host: localhost:9000          |
+------------------------------+      +------------------------------+
        requiere DNS por bucket            una sola entrada DNS

La opción forcePathStyle: true obliga al SDK a usar siempre la segunda forma. En un MinIO distribuido con features.bucketDNS o detrás de un proxy con comodín podrías usar virtual-host, pero para desarrollo y para la mayoría de instalaciones el path-style es la opción segura.

La región también forma parte de la firma: MinIO no tiene regiones reales, pero valida que el ámbito de la credencial sea coherente. Si firmas con eu-west-1 y el servidor espera us-east-1, verás SignatureDoesNotMatch. Fija region en el cliente y usa el mismo valor en el mc alias; us-east-1 es un buen valor por defecto y una variable de entorno (S3_REGION) permite cambiarlo al apuntar a AWS.

Checksums: la trampa moderna

Desde finales de 2024, el SDK v3 calcula checksums flexibles por defecto en muchas operaciones. Añade cabeceras como x-amz-checksum-crc32 y x-amz-sdk-checksum-algorithm. Las versiones recientes de MinIO las entienden, pero un servidor antiguo o un proxy que no las espere puede rechazar la petición con NotImplemented o un error de checksum. Para un cliente que debe hablar con cualquier S3 compatible, se configura explícitamente:

requestChecksumCalculation: "WHEN_REQUIRED",
responseChecksumValidation: "WHEN_REQUIRED",

Así el SDK solo envía checksums cuando la operación los exige, y tú puedes añadir los tuyos (SHA-256, CRC32C) donde aporten valor. No es un retroceso de seguridad: es controlar el contrato en lugar de heredar el de AWS.

Presigned URLs: firmar sin enviar

Un presigned URL es una petición futura con la firma ya calculada en los parámetros de consulta. El SDK no contacta con el servidor: deriva la firma de las credenciales que tengas en memoria. Por eso importa quién firma y para qué host.

  • El host firmado debe ser el host público por el que el cliente accederá. Firmar http://minio:9000 y enviar la URL al navegador produce un error de red, no de permisos.
  • La expiración máxima con credenciales de larga duración es de siete días; para subidas de usuario, quince minutos suele ser suficiente.
  • Firma con un usuario de mínimo privilegio, nunca con root. La URL hereda sus permisos y su ámbito.

Portabilidad real: un adaptador y un contrato

No repartas S3Client por toda la aplicación. Aísla el SDK en un módulo con cuatro o cinco funciones y prueba ese módulo contra MinIO y, si puedes, contra AWS. La aplicación no debe saber si debajo hay MinIO, AWS o un proveedor compatible: solo cambian las variables de entorno.

3 · Ejemplo mínimo

Vamos a listar buckets y subir un objeto contra el MinIO del curso usando el SDK de AWS. Crea el proyecto e instala solo los paquetes necesarios:

mkdir s3-portable
cd s3-portable
npm init -y
npm pkg set type=module
npm i @aws-sdk/client-s3@3 @aws-sdk/s3-request-presigner@3

El archivo .env.example documenta las variables; el .env real no se versiona:

S3_ENDPOINT=http://localhost:9000
S3_REGION=us-east-1
S3_ACCESS_KEY=documentos-app
S3_SECRET_KEY=cambia-esto-en-local
S3_BUCKET=documentos

Y este es el cliente mínimo, en client.mjs:

import {
  S3Client,
  ListBucketsCommand,
  PutObjectCommand,
} from "@aws-sdk/client-s3";

const client = new S3Client({
  endpoint: process.env.S3_ENDPOINT,
  region: process.env.S3_REGION ?? "us-east-1",
  forcePathStyle: true,
  credentials: {
    accessKeyId: process.env.S3_ACCESS_KEY,
    secretAccessKey: process.env.S3_SECRET_KEY,
  },
  requestChecksumCalculation: "WHEN_REQUIRED",
  responseChecksumValidation: "WHEN_REQUIRED",
});

const buckets = await client.send(new ListBucketsCommand({}));
console.log("buckets:", buckets.Buckets?.map((b) => b.Name));

await client.send(new PutObjectCommand({
  Bucket: process.env.S3_BUCKET,
  Key: "pruebas/hola.txt",
  Body: "hola desde el SDK de AWS\n",
  ContentType: "text/plain; charset=utf-8",
}));
console.log("objeto subido");

Ejecútalo con el cargador de entorno de Node.js 22:

node --env-file=.env client.mjs

buckets: [ 'documentos' ]
objeto subido

Línea a línea, lo importante:

  • endpoint apunta al servidor; sin él, el SDK resolvería s3.us-east-1.amazonaws.com.
  • forcePathStyle: true produce /documentos/pruebas/hola.txt en lugar de documentos.localhost.
  • region forma parte del ámbito de la firma; debe ser estable.
  • Los dos flags de checksum evitan cabeceras que servidores antiguos no entienden.
  • ContentType se firma y se guarda como metadato del sistema; no es un adorno.

4 · Ejemplo real

El almacén de documentos necesita firmar una subida y una descarga. Las encapsulamos en storage.mjs para que el resto de la aplicación no importe nada del SDK:

import { S3Client, GetObjectCommand, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const client = new S3Client({
  endpoint: process.env.S3_ENDPOINT,
  region: process.env.S3_REGION ?? "us-east-1",
  forcePathStyle: true,
  ...(process.env.S3_ACCESS_KEY
    ? {
        credentials: {
          accessKeyId: process.env.S3_ACCESS_KEY,
          secretAccessKey: process.env.S3_SECRET_KEY,
        },
      }
    : {}),
  requestChecksumCalculation: "WHEN_REQUIRED",
  responseChecksumValidation: "WHEN_REQUIRED",
});

const Bucket = process.env.S3_BUCKET;

export function presignPut(key, contentType, expiresIn = 900) {
  return getSignedUrl(
    client,
    new PutObjectCommand({ Bucket, Key: key, ContentType: contentType }),
    { expiresIn },
  );
}

export function presignGet(key, expiresIn = 300) {
  return getSignedUrl(
    client,
    new GetObjectCommand({ Bucket, Key: key }),
    { expiresIn },
  );
}

Fíjate en el detalle de las credenciales: si existen variables, se usan; si no, el SDK aplica su cadena de proveedores (rol de IAM, perfil, SSO). Eso permite el mismo archivo en local y en AWS sin un if repartido por la aplicación.

El cambio de entorno queda reducido a una tabla:

VariableMinIO localAWS
S3_ENDPOINThttp://localhost:9000Sin valor (endpoint por defecto) o el endpoint de la región
S3_REGIONus-east-1eu-west-1, us-east-2…
S3_ACCESS_KEYUsuario de la aplicaciónVacío si usas rol de IAM
S3_BUCKETdocumentosEl bucket real, único a nivel global

Para que la portabilidad sea una promesa y no una esperanza, escribe pruebas de contrato: subir, leer, listar, borrar y comprobar que un HeadObject de una clave inexistente devuelve NotFound. Esas pruebas deben pasar en los dos entornos. En el módulo 2 viste cómo normalizar errores; el adaptador es el lugar donde se aplica.

Un endpoint público para las URLs

Si la API corre dentro de Docker, el SDK puede hablar con http://minio:9000, pero el navegador no resuelve ese nombre. Configura un S3_PUBLIC_ENDPOINT (por ejemplo http://localhost:9000) y crea un segundo cliente solo para firmar URLs públicas. Es la causa número uno de «la URL se genera pero no funciona».

6 · Errores habituales

1. Olvidar el path-style

Mal — el SDK intenta resolver un subdominio que no existe 
const client = new S3Client({
  endpoint: "http://localhost:9000",
  region: "us-east-1",
  credentials,
}); // GET http://documentos.localhost:9000/ -> ENOTFOUND
Bien — bucket en la ruta 
const client = new S3Client({
  endpoint: "http://localhost:9000",
  region: "us-east-1",
  forcePathStyle: true,
  credentials,
});

El error puede aparecer como getaddrinfo ENOTFOUND documentos.localhost o como una redirección permanente. En ambos casos, mira la URL antes de tocar credenciales.

2. Heredar los checksums por defecto

Mal — cabeceras que el servidor antiguo no soporta 
x-amz-sdk-checksum-algorithm: CRC32
x-amz-checksum-crc32: ...
-> NotImplemented / XAmzContentChecksumMismatch
Bien — checksums solo cuando se piden 
new S3Client({
  endpoint, region, forcePathStyle: true,
  requestChecksumCalculation: "WHEN_REQUIRED",
  responseChecksumValidation: "WHEN_REQUIRED",
});

Y si tu dominio exige integridad, calcula el checksum en el adaptador y compáralo con el ETag o con el valor que devuelve HeadObject. No dependas de que el transporte lo haga por ti.

3. Generar la URL con el host interno o con root

Mal — URL inalcanzable y privilegios excesivos 
// dentro de Docker
const client = new S3Client({ endpoint: "http://minio:9000", ... });
const url = await getSignedUrl(client, new PutObjectCommand({
  Bucket: "documentos", Key: key,
})); // el navegador no resuelve "minio"
Bien — cliente público y usuario acotado 
const publicClient = new S3Client({
  endpoint: process.env.S3_PUBLIC_ENDPOINT, // http://localhost:9000
  region, forcePathStyle: true,
  credentials: appCredentials, // no root
});
const url = await getSignedUrl(publicClient, command, { expiresIn: 600 });

La URL hereda los permisos del firmante y el host firmado. Un error aquí no se arregla «regenerando la URL»: se arregla corrigiendo el cliente con el que se firma.

7 · Ejercicio guiado

Objetivo: conectar el SDK de AWS a MinIO con un usuario acotado, subir un objeto, firmar una URL y comprobar que el mismo código solo necesita configuración para cambiar de proveedor.

  1. Levanta MinIO y crea el alias: 
    docker run -d --name minio-sdk \
  -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=minioadmin \
  -e MINIO_ROOT_PASSWORD=minioadmin \
  -v minio-sdk-data:/data \
  quay.io/minio/minio server /data --console-address ":9001"

mc alias set local http://localhost:9000 minioadmin minioadmin
mc mb --ignore-existing local/documentos

    Salida esperada: Bucket created successfully `local/documentos`.

  2. Crea un usuario de aplicación con política acotada: 
    cat > documentos-app.json <<'JSON'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": ["arn:aws:s3:::documentos/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": ["arn:aws:s3:::documentos"]
    }
  ]
}
JSON

mc admin user add local documentos-app 'clave-local-segura'
mc admin policy create local documentos-app-policy documentos-app.json
mc admin policy attach local documentos-app-policy --user documentos-app

    El usuario no puede crear buckets ni cambiar políticas: solo operar sobre documentos.

  3. Crea el proyecto del ejemplo mínimo con las tres órdenes de la sección 3 y un .env con las credenciales del usuario recién creado. Ejecuta node --env-file=.env client.mjs.
  4. Firma una subida, úsala con curl y comprueba el objeto: 
    import { getSignedUrl } from "@aws-sdk/s3-request-presigner";
import { PutObjectCommand } from "@aws-sdk/client-s3";
// ... cliente igual que en storage.mjs
const url = await getSignedUrl(client, new PutObjectCommand({
  Bucket: "documentos",
  Key: "pruebas/firmado.txt",
  ContentType: "text/plain",
}), { expiresIn: 300 });
console.log(url);

    curl -i -X PUT -H "Content-Type: text/plain" \
  --data-binary "subido con presigned URL" "$URL"
mc stat local/documentos/pruebas/firmado.txt
mc cat local/documentos/pruebas/firmado.txt

    Espera HTTP/1.1 200 OK y un ETag. Si cambias el Content-Type en curl, la firma falla: la cabecera está firmada. mc debe ver el mismo objeto, tamaño y tipo.

  5. Rompe la configuración a propósito: elimina forcePathStyle y ejecuta de nuevo. Anota el error exacto. Restaura la opción y confirma que vuelve a funcionar. Repite con una región distinta y con requestChecksumCalculation en WHEN_SUPPORTED; documenta qué error produce cada cambio en tu versión de MinIO.

Comprobación final

Tu adaptador debe funcionar con dos configuraciones sin tocar una línea de JavaScript: MinIO local y un bucket de AWS (o un segundo MinIO con otra región). Si necesitas cambiar código para alternar, todavía no es portable.

8 · Reto

🎯 Una suite de contrato para dos proveedores

Diseña y ejecuta una suite de pruebas que valide el mismo adaptador contra MinIO y contra AWS S3 (o un segundo proveedor compatible al que tengas acceso). Debe cubrir: subida, lectura, HeadObject, listado por prefijo, copia, borrado, versionado y una presigned URL usada desde fuera del proceso. Registra las diferencias que encuentres y clasifícalas en «portable», «requiere configuración» y «no soportado».

Después, escribe una tabla de decisión: para cada diferencia, qué haría tu aplicación si mañana cambia de proveedor. No vale decir «usar siempre AWS»: el objetivo es que el contrato sobreviva al cambio.

Pista: empieza por las operaciones que ya usas en el document store y añade una prueba por operación. Las diferencias más probables aparecen en ACL, website, checksums y en la forma de configurar notificaciones, no en PutObject.

9 · Resumen

  • MinIO y AWS comparten la API S3 y SigV4; el mismo SDK sirve para ambos cambiando configuración.
  • forcePathStyle: true evita depender de DNS por bucket, imprescindible en local.
  • La región forma parte de la firma; debe ser coherente entre cliente, servidor y alias de mc.
  • Los checksums flexibles del SDK v3 se controlan con WHEN_REQUIRED para maximizar compatibilidad.
  • Las presigned URLs se firman con un usuario acotado y para el host público, no para el host interno.
  • La portabilidad se demuestra con un adaptador pequeño y pruebas de contrato contra los dos entornos.
  • ACL, website, analytics y logging no son portables tal cual: usa políticas, un proxy y las herramientas propias de MinIO.

10 · Preguntas frecuentes

¿MinIO implementa toda la API de S3?

Implementa el núcleo que usan las aplicaciones —objetos, buckets, multipart, versionado, object lock, lifecycle, réplica y notificaciones— y deja fuera operaciones de AWS que no aportan a un almacén privado, como el hosting de sitios web o las ACL. La documentación oficial de compatibilidad lista cada caso. Antes de migrar, prueba las operaciones concretas que usas.

¿Puedo usar minio-js y el SDK de AWS a la vez?

Sí, ambos hablan el mismo protocolo. Lo sensato es elegir uno por aplicación para no duplicar configuración y manejo de errores. minio-js es más directo para MinIO; el SDK de AWS es útil si necesitas portabilidad o ya está integrado en tu ecosistema. El adaptador permite cambiar sin tocar los casos de uso.

¿Por qué la presigned URL funciona en local pero no desde el navegador?

Porque se firmó con el host interno (minio:9000) o con localhost visto desde otro contenedor. La firma incluye el Host: no puedes reescribir la URL y esperar que siga siendo válida. Firma con un cliente cuyo endpoint sea exactamente el host público que usará el navegador.

¿La región de MinIO tiene algún efecto real?

MinIO usa la región como parte del ámbito de firma y para algunas validaciones. No cambia dónde se almacenan los datos ni ofrece aislamiento geográfico. Lo importante es que cliente y servidor coincidan; us-east-1 es un valor seguro por defecto.
