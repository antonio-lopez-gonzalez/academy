Errores, reintentos y checksums

Módulo 2 · SDK y aplicación 🕐 35 minutos

1 · Introducción

El código que sube documentos funciona en tu portátil y falla el día que la red se corta a mitad de un PDF, el servidor reinicia durante un despliegue o el proxy devuelve un 503. Ninguno de esos fallos es exótico: son el estado normal de un sistema distribuido. Lo que distingue a una aplicación robusta no es no tener errores, sino saber cuáles se reintentan, cuáles no, y cómo comprobar que lo que llegó es lo que se envió.

Reintentar a ciegas es peor que no reintentar. Un reintento sobre un error permanente multiplica la carga y esconde el problema. Un reintento sobre una operación no idempotente crea objetos duplicados. Y un reintento sin jitter sincroniza a todos los clientes para volver a golpear al servidor en el mismo instante.

Esta lección construye la taxonomía completa sobre el cliente de la lección anterior: códigos de error S3, política de reintento con backoff y jitter, idempotencia de las escrituras, y la diferencia entre ETag y checksum —la parte que más malentendidos genera cuando aparece un -3 al final de un hash.

Por qué importa más el «no reintentar»

Un 403 no se arregla esperando. Un 404 de clave no aparece por reintentar. Reintentar esos errores convierte un fallo claro en una tormenta de peticiones y retrasa el diagnóstico. La primera decisión de una política de reintentos es la lista de errores que no entran.

2 · Teoría

Dos capas de error que no coinciden

Una respuesta S3 trae un código HTTP y, en el cuerpo, un XML con un código propio. minio-js lo convierte en un Minio.S3Error con code, message y statusCode. No son lo mismo: NoSuchKey y NoSuchBucket comparten el 404, y AccessDenied agrupa varias causas (política, credencial deshabilitada, IP restringida).

petición HTTP
    |
    +-- falla antes de hablar con el servidor --> error de red (ECONNREFUSED, ETIMEDOUT…)
    |                                            no es S3Error
    |
    +-- el servidor responde 4xx/5xx ----------- S3Error
                                                 code      = NoSuchKey
                                                 statusCode = 404
                                                 amzRequestid = 17B9C2F4…

Captura las dos familias por separado. Un catch que solo mira err.message pierde el código y acaba tratando igual un fallo de red y un permiso denegado.

Idempotencia: qué se puede repetir sin daño

Operación¿Repetirla es seguro?Matiz

La regla práctica: un reintento debe reutilizar la misma clave y el mismo cuerpo. Si tu función genera un UUID dentro del bloque que se reintenta, cada intento crea un objeto nuevo y acabas con duplicados que nadie pidió.

Backoff con jitter

El backoff exponencial separa los intentos: 200 ms, 400 ms, 800 ms… El jitter rompe la sincronía entre clientes. Sin él, mil instancias que fallan a la vez reintentan a la vez, y el servidor recibe picos idénticos.

delay = random(0, min(cap, base * 2^(attempt-1)))     <- full jitter

attempt 1  |##                |  0–200 ms
attempt 2  |####              |  0–400 ms
attempt 3  |########          |  0–800 ms
attempt 4  |################  |  0–1600 ms, tope 5 s

Siempre con un deadline total: 4 intentos no pueden durar 10 minutos.

Añade tres límites además del número de intentos: un deadline por operación, un presupuesto de reintentos por petición de usuario y la cabecera Retry-After si el servidor la envía. Y registra cada reintento: un reintento silencioso es un incidente que no ves.

ETag no es un checksum (siempre)

En una subida simple, el ETag suele ser el MD5 del contenido. En una subida multipart, es el MD5 de la concatenación de los MD5 de cada parte, con el número de partes como sufijo. Y con SSE-KMS, el ETag deja de ser un hash del contenido.

Subida simple:
  ETag = MD5(objeto)                       9c1e0b2a4d5f60718293a4b5c6d7e8f9

Multipart (3 partes):
  ETag = MD5( MD5(p1) || MD5(p2) || MD5(p3) ) + "-3"
                                            ^^^ no es el MD5 del objeto

Por eso un ETag "abc…-3" nunca coincidirá con md5sum del fichero completo.
Qué mirasQué mideCuándo sirve
ETag simpleMD5 del contenido (normalmente)Comparar dos subidas del mismo tamaño en el mismo bucket
ETag multipartMD5 de los MD5 de las partesDetectar cambios entre versiones, no verificar el contenido
x-amz-checksum-sha256SHA-256 del objeto completoIntegridad de extremo a extremo si el cliente lo envía
Metadato propio sha256El hash que calculó tu aplicaciónVerificación explícita, independiente del ETag

No compares ETag con md5sum sin comprobar el formato

Si el ETag contiene un guion, es multipart. Si el objeto está cifrado con SSE-KMS, el ETag no es un hash del contenido. En esos casos la comparación falla siempre, y el equipo acaba desactivando la verificación «porque daba falsos positivos».

Verificación de integridad en la práctica

Verifica en tres momentos: al subir (SHA-256 como metadato y comparación de tamaño), al descargar (hash mientras escribes a disco) y en mantenimiento (un job que detecta objetos sin checksum o con tamaño cero).

MinIO verifica internamente los checksums que recibe y protege los datos con erasure coding, pero eso no sustituye a que tu aplicación compruebe que el PDF que guardó es el que el usuario envió. Son capas distintas.

3 · Ejemplo mínimo

Un put con reintento, jitter y checksum. El cuerpo se lee una vez y se reutiliza en todos los intentos: la clave y los bytes no cambian.

// subir-seguro.mjs
import * as Minio from 'minio'
import { readFile } from 'node:fs/promises'
import { createHash } from 'node:crypto'
import { setTimeout as delay } from 'node:timers/promises'

const client = new Minio.Client({ /* configuración de la lección 1 */ })
const RETRYABLE = new Set(['SlowDown', 'InternalError', 'ServiceUnavailable', 'RequestTimeout'])
const NETWORK = new Set(['ECONNRESET', 'ECONNREFUSED', 'ETIMEDOUT', 'EPIPE', 'EAI_AGAIN'])

function isRetryable(err) {
  if (err instanceof Minio.S3Error) {
    if ([408, 429, 500, 502, 503, 504].includes(err.statusCode)) return true
    return RETRYABLE.has(err.code)
  }
  return NETWORK.has(err.code)
}

async function withRetry(fn, { attempts = 4, baseMs = 200, capMs = 5000 } = {}) {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn()
    } catch (err) {
      if (attempt >= attempts || !isRetryable(err)) throw err
      const ceiling = Math.min(capMs, baseMs * 2 ** (attempt - 1))
      await delay(Math.random() * ceiling) // full jitter
      console.warn(`reintento ${attempt} tras ${err.code}`)
    }
  }
}
const bucket = 'documentos'
const key = 'acme/2026/11/informe.pdf'
const body = await readFile('./informe.pdf')
const sha256 = createHash('sha256').update(body).digest('hex')

const etag = await withRetry(() => client.putObject(
  bucket, key, body, body.length,
  { 'Content-Type': 'application/pdf', 'X-Amz-Meta-Sha256': sha256 },
))

const stat = await client.statObject(bucket, key)
console.log({ etag, sha256, size: stat.size, guardado: stat.metaData.sha256 })
if (stat.size !== body.length) throw new Error('tamaño distinto al enviado')
{ etag: '9c1e0b2a4d5f60718293a4b5c6d7e8f9',
  sha256: 'a3f1…',
  size: 20480,
  guardado: 'a3f1…' }
  • body se lee fuera del reintento: si lo leyeras dentro, un fichero modificado entre intentos cambiaría el contenido.
  • key también es constante. Generar el UUID dentro de fn rompería la idempotencia.
  • attempt >= attempts corta antes de dormir en el último intento.
  • Math.random() * ceiling es full jitter: el rango crece, pero el valor es aleatorio.
  • stat.metaData.sha256 confirma que el metadato viajó; el tamaño confirma que no se truncó.

4 · Ejemplo real

En el almacén, cada subida registra intentos y verifica el contenido. El logger estructurado permite responder «¿cuántos reintentos hubo a las 10:15?» sin buscar en texto libre.

// src/upload-verified.mjs
import * as Minio from 'minio'
import { createHash } from 'node:crypto'
import { createReadStream, statSync } from 'node:fs'
import { setTimeout as delay } from 'node:timers/promises'

const RETRYABLE_CODES = new Set(['SlowDown', 'InternalError', 'ServiceUnavailable'])
const RETRYABLE_STATUS = new Set([408, 429, 500, 502, 503, 504])

function classify(err) {
  if (!(err instanceof Minio.S3Error)) return 'network'
  if (err.code === 'NoSuchKey') return 'not_found'
  if (err.code === 'AccessDenied') return 'forbidden'
  if (err.code === 'PreconditionFailed') return 'conflict'
  if (RETRYABLE_STATUS.has(err.statusCode) || RETRYABLE_CODES.has(err.code)) return 'transient'
  return 'permanent'
}

export async function uploadVerified({ client, bucket, key, filePath, meta, logger }) {
  const { size } = statSync(filePath)
  const started = Date.now()

  for (let attempt = 1; ; attempt++) {
    try {
      const etag = await client.putObject(
        bucket, key, createReadStream(filePath), size, meta,
      )
      const stat = await client.statObject(bucket, key)
      if (stat.size !== size) throw new Error(`tamaño ${stat.size} != ${size}`)
      logger.info({ event: 's3.put.ok', bucket, key, etag, attempt, ms: Date.now() - started })
      return { etag, size }
    } catch (err) {
      const kind = classify(err)
      const retryable = kind === 'transient' || kind === 'network'
      logger.warn({ event: 's3.put.fail', bucket, key, attempt, kind,
        code: err.code, statusCode: err.statusCode, requestId: err.amzRequestid })

      if (!retryable || attempt >= 4) {
        err.attempts = attempt
        err.kind = kind
        throw err
      }
      const ceiling = Math.min(5000, 200 * 2 ** (attempt - 1))
      await delay(Math.random() * ceiling)
    }
  }
}

Observa el detalle de stat.size !== size: comprobar el tamaño tras la subida es barato y detecta un stream truncado o una discrepancia antes de que el documento entre en el catálogo.

Al descargar, recalcula el SHA-256 con un Transform dentro del pipeline y compáralo con el metadato. Si no coincide, no reintentes a ciegas: el objeto almacenado o el metadato están mal, y la solución es investigar o recuperar una versión anterior.

6 · Errores habituales

1. Reintentar un AccessDenied

Mal — el permiso no aparece esperando 
for (let i = 0; i < 5; i++) {
  try { return await client.getObject(bucket, key) }
  catch (err) { await delay(1000) } // ❌ también reintenta 403
}
Bien — solo lo transitorio 
if (!isRetryable(err)) throw err
// AccessDenied, NoSuchKey y 400 salen inmediatamente

Cinco reintentos de un 403 solo añaden cinco segundos y cinco líneas de ruido en los logs. La causa está en la política o en la credencial.

2. Generar la clave dentro del reintento

Mal — cada intento crea un objeto 
await withRetry(async () => {
  const key = `${prefix}/${randomUUID()}.pdf` // ❌ nuevo en cada intento
  return client.putObject(bucket, key, body, body.length)
})
Bien — la clave se decide una vez 
const key = `${prefix}/${randomUUID()}.pdf`
await withRetry(() => client.putObject(bucket, key, body, body.length))

Si el primer intento llegó a escribir y la respuesta se perdió, el reintento debe sobrescribir la misma clave. Con una clave nueva, el objeto original queda huérfano y el usuario ve dos documentos.

3. Comparar un ETag multipart con el MD5 del fichero

Mal — el sufijo -N lo delata 
md5sum grande.bin
# 8f14e45fceea167a5a36dedd4bea2543  grande.bin
mc stat local/documentos/grande.bin
# ETag: 4a2b7c1e9f0d3a6b8c5e2f1d0a9b8c7d-3
# ❌ "no coinciden, el archivo está corrupto"
Bien — entender qué representa cada valor 
ETag multipart = MD5(MD5(p1) || MD5(p2) || MD5(p3)) + "-3"
Para verificar el contenido, usa un checksum completo (SHA-256) o
recalcula el ETag multipart con el tamaño de parte correcto.

El ETag multipart es estable y útil para detectar cambios, pero no es el hash del objeto. Compararlo con md5sum produce un falso positivo garantizado.

4. Reintentar sin jitter ni deadline

Mal — todos los clientes a la vez 
while (true) {
  try { return await op() } catch { /* reintento inmediato */ }
}
Bien — backoff, jitter y un límite 
const ceiling = Math.min(5000, 200 * 2 ** (attempt - 1))
await delay(Math.random() * ceiling)
if (Date.now() > deadline) throw err

Sin jitter, un despliegue que reinicia cien pods provoca cien reintentos sincronizados. Sin deadline, una petición puede quedarse «viva» más que el timeout del proxy y el usuario nunca recibe respuesta.

7 · Ejercicio guiado

Objetivo: comprobar con datos reales la diferencia entre ETag simple y multipart, y ver una política de reintento en acción.

  1. Crea un fichero pequeño y súbelo: 
    printf 'contenido estable\n' > pequeno.txt
mc cp pequeno.txt local/documentos/acme/2026/11/pequeno.txt
mc stat local/documentos/acme/2026/11/pequeno.txt
    ETag: 8f9c0b1d2e3f4a5b6c7d8e9f0a1b2c3d

    Compara con md5sum pequeno.txt: debe coincidir.

  2. Genera un fichero de 100 MB y súbelo: 
    node -e "require('fs').writeFileSync('grande.bin', Buffer.alloc(100*1024*1024))"
mc cp grande.bin local/documentos/acme/2026/11/grande.bin
mc stat local/documentos/acme/2026/11/grande.bin

    El ETag termina en -N, con el número de partes según el tamaño de parte. Ese sufijo es la prueba de que fue multipart.

  3. Comprueba el falso negativo: ejecuta md5sum grande.bin y compara con el ETag. No coinciden. Ahora calcula el SHA-256 del fichero y guárdalo como metadato con mc cp --attr, o vuelve a subirlo con el script de la sección 3.
  4. Provoca un fallo transitorio: con una subida en marcha, ejecuta docker pause minio-sdk durante unos segundos y luego docker unpause minio-sdk. Observa los reintentos del SDK y el tiempo total. Repite sin pausa y compara.
  5. Prueba un fallo permanente: usa una clave en un bucket inexistente (local/no-existe/x.txt). Debe fallar con NoSuchBucket y sin reintentos. Añade el código a tu clasificador y comprueba que sale en el primer intento.
  6. Mide el jitter: ejecuta veinte veces una función que simule un fallo transitorio y registra los retardos. No deben ser todos iguales ni estrictamente crecientes: eso es el jitter haciendo su trabajo.

Comprobación final

Tu tabla de decisión debe tener tres columnas: código, ¿reintenta?, acción. Si un código no encaja en ninguna, trátalo como permanente y regístralo: es mejor fallar rápido que reintentar a ciegas.

8 · Reto

🎯 El verificador de integridad

Construye verify.mjs que recorra el prefijo acme/ y clasifique cada objeto en tres grupos: con metadato sha256, con ETag simple y con ETag multipart. Para los que tengan metadato, descarga en streaming y comprueba el hash sin cargar el objeto entero en memoria. Para los multipart, explica en la salida por qué no puedes comparar directamente con el MD5 del fichero.

Añade un modo --repair que vuelva a calcular el SHA-256 de los objetos que no lo tengan y actualice el metadato sin cambiar el contenido. Debe ser idempotente: ejecutarlo dos veces no debe producir escrituras innecesarias ni objetos nuevos.

Pista: para actualizar metadatos en S3 no existe un PATCH; se reescribe el objeto. Investiga copyObject con sustitución de metadatos y comprueba qué pasa con el ETag resultante.

9 · Resumen

  • Hay dos familias de error: red (sin respuesta) y S3 (S3Error con code y statusCode).
  • Solo se reintentan 408, 429, 5xx y fallos de transporte; los 4xx permanentes se propagan.
  • Un reintento debe repetir la misma clave y el mismo cuerpo; si no, no es idempotente.
  • Backoff exponencial con jitter, más un deadline total y un máximo de intentos.
  • El ETag simple suele ser MD5; el multipart es MD5 de MD5s con sufijo -N.
  • Para integridad real, usa un checksum completo (SHA-256) y guárdalo como metadato.
  • Registra intento, código y amzRequestid; nunca el cuerpo ni las credenciales.

10 · Preguntas frecuentes

Si PUT es idempotente, ¿puedo reintentar siempre?

Solo si repites la misma clave con los mismos bytes. Dos escrituras concurrentes a la misma clave son idempotentes en el sentido de que el resultado es un objeto completo, pero no deterministas: gana la última. Si el contenido puede cambiar entre intentos, no estás reintentando la misma operación.

¿Por qué minio-js ya reintenta y yo tengo que añadir otra capa?

Porque el SDK no conoce tu contexto: no sabe si la operación es idempotente, cuánto puede esperar el usuario ni qué errores de negocio quieres propagar. Su reintento es de transporte; el tuyo es de política. Además, el SDK no registra los intentos con tu formato de logs.

¿Sirve el ETag para detectar corrupción?

Como señal barata, a veces. Como verificación formal, no: en multipart no cubre el contenido completo y con SSE-KMS no es un hash. Para corrupción usa checksums completos o compara el tamaño y el hash calculado por tu aplicación.

¿Debo reintentar un 409 al crear el bucket?

Distingue el código. BucketAlreadyOwnedByYou significa que el bucket ya existe y es tuyo: es el resultado deseado. BucketAlreadyExists significa que el nombre está ocupado por otra cuenta: reintentar no lo va a liberar.
