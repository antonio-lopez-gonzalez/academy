Descargas y transformaciones

Módulo 2 · SDK y aplicación 🕐 35 minutos

1 · Introducción

Subir es solo la mitad del problema, como vimos en multipart y streaming. Un almacén de documentos se usa para leer: abrir un PDF en el navegador, pedir las primeras páginas de una vista previa, mostrar una miniatura o servir un vídeo que el usuario quiere adelantar. Cada uno de esos casos tiene un patrón distinto, y el patrón ingenuo —traer el objeto entero a memoria y responder— es el que convierte un servidor sano en un montón de procesos muertos por falta de memoria.

Un objeto puede pesar 5 KB o 5 GB. El código que lo maneja no debería cambiar por ello: los streams permiten tratar ambos con el mismo consumo acotado. Pero los streams tienen reglas —hay que consumirlos, hay que cerrarlos, hay que propagar errores— y las transformaciones añaden una pregunta nueva: ¿se hacen al vuelo en cada descarga o una vez al subir?

Esta lección cubre las descargas por streaming, las peticiones por rango (la base de un visor de PDF o de vídeo), la escritura a ficheros temporales, las miniaturas con sharp y las cabeceras de caché que deciden si el navegador vuelve a pedir el objeto.

La memoria es el recurso escaso

La CPU se puede repartir y el disco se puede ampliar; la memoria de un proceso Node es un límite duro. Todo lo que hagas con objetos debe funcionar con un objeto de 1 GB sin reservar 1 GB de RAM. Si tu código llama a readFile o a Buffer.concat, ese límite ya está roto.

2 · Teoría

Tres formas de leerlo

getObject pide el objeto completo; getPartialObject(bucket, key, offset, length) pide un rango; statObject hace un HEAD y devuelve metadatos sin descargar. Los dos primeros devuelven un Readable, y solo el segundo permite responder 206 Partial Content sin traer el resto.

Backpressure: el stream manda el ritmo

MinIO  ----chunk---->  Readable  ----chunk---->  Writable (disco o socket)
                          |                          |
                          |  si el destino va lleno, |
                          |  el stream pausa la      |
                          |  lectura del origen      |
                          +--------------------------+

Sin backpressure: el origen lee a 500 MB/s y el destino escribe a 50 MB/s
                 -> la diferencia se acumula en memoria -> OOM

Con pipeline:    el destino marca el ritmo; la memoria se mantiene acotada

pipeline de node:stream/promises conecta los extremos, propaga el error de cualquiera de ellos y destruye los demás. Es la única forma razonable de encadenar MinIO con disco, con una respuesta HTTP o con sharp.

Rangos: cómo se sirve un vídeo que se puede adelantar

El navegador pide Range: bytes=1048576-2097151 y espera un 206 con Content-Range: bytes 1048576-2097151/10485760. Si respondes 200 con el objeto completo, el reproductor descarga todo antes de saltar y la experiencia se rompe.

GET /video.mp4
Range: bytes=1000-1999

HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 1000-1999/500000
Content-Length: 1000

[1000 bytes del objeto, desde el offset 1000]

Tres detalles que se olvidan:

  • Accept-Ranges: bytes debe ir también en la respuesta completa, para que el cliente sepa que puede pedir rangos.
  • Un rango fuera del tamaño del objeto se responde 416 con Content-Range: bytes */tamaño.
  • El rango con sufijo (bytes=-500) significa «los últimos 500 bytes», no «desde el byte 500».

Ficheros temporales: el patrón que casi siempre funciona

Cuando el consumidor necesita un fichero —sharp, ffmpeg, un antivirus— escribe el objeto en un directorio temporal y trabaja sobre él. Ventajas: el consumo de memoria no depende del tamaño, las herramientas externas funcionan igual y puedes medir el tamaño resultante con stat antes de subirlo.

getObject ──pipeline──> /tmp/minio-xxxx/in.bin
                              |
                              +── sharp / ffmpeg / antivirus
                              |
                        /tmp/minio-xxxx/out.jpg
                              |
                        stat + putObject(size conocido)
                              |
                        rm -rf /tmp/minio-xxxx  (finally)

Un pico de descargas concurrentes puede llenar /tmp y tumbar el proceso: limita la concurrencia, comprueba el espacio libre y borra siempre en un finally.

¿Transformar al vuelo o al escribir?

CriterioAl vuelo (on read)Al escribir (on write)
CosteSe repite en cada descargaSe paga una vez
LatenciaAlta la primera vez, cacheable despuésBaja al leer
FlexibilidadParámetros infinitos (tamaño, formato, calidad)Solo las variantes que generaste
ConsistenciaDepende del originalHay que invalidar si el original cambia
Uso típicoRedimensionar a un tamaño pedido por el usuarioMiniaturas fijas, PDF normalizado, antivirus

La regla práctica: si la variante es finita y conocida, genérala al escribir y sirve el resultado como un objeto más. Si es arbitraria, genera al vuelo pero cachea por clave derivada.

Content-Type y caché se deciden al escribir

En S3, Content-Type, Content-Disposition y Cache-Control son metadatos del objeto. Se fijan en el putObject y se devuelven en cada GET. Cambiarlos después implica reescribir el objeto.

ClaveCabecera recomendadaMotivo
acme/2026/11/<uuid>.pdfprivate, max-age=60Contenido privado; se sirve por la API, no por CDN
thumbs/<uuid>.jpgpublic, max-age=31536000, immutableLa clave cambia cuando cambia el contenido
exports/informe-2026-11.pdfprivate, max-age=300Clave mutable: no se puede cachear para siempre

immutable solo es honesto si la clave nunca reutiliza contenido distinto. Si sobrescribes la misma clave, el navegador puede servir la versión vieja durante un año y ni siquiera preguntar.

Cuándo delegar a un worker

El proceso web debe responder rápido: si la transformación tarda o consume CPU que necesitan otras peticiones, publica { bucket, key, versionId } en una cola y responde 202. El worker descarga, transforma y sube el derivado con una clave idempotente, timeout y reintento acotado.

3 · Ejemplo mínimo

Descargar a disco sin cargar el objeto en memoria, y leer solo los primeros bytes.

// descargar.mjs
import * as Minio from 'minio'
import { pipeline } from 'node:stream/promises'
import { createWriteStream } from 'node:fs'

const client = new Minio.Client({ /* configuración de la lección 1 */ })
const bucket = 'documentos'
const key = 'acme/2026/11/informe.pdf'
const stat = await client.statObject(bucket, key)
const stream = await client.getObject(bucket, key)
await pipeline(stream, createWriteStream('./informe.pdf'))
console.log(`${stat.size} bytes, etag ${stat.etag}`)

Para comprobar el tipo real, pide los primeros bytes con getPartialObject(bucket, key, 0, 5) y compara con %PDF-; el tamaño del rango es cinco, no el del objeto.

20480 bytes, etag 9c1e0b2a4d5f60718293a4b5c6d7e8f9
%PDF-
  • statObject primero: sabes el tamaño antes de abrir el stream y puedes rechazar objetos absurdos.
  • pipeline cierra el stream de MinIO y el fichero aunque falle cualquiera de los dos.
  • getPartialObject con length = 5 pide un rango, no el objeto completo.

4 · Ejemplo real

El endpoint de descarga del almacén responde con rangos, valida la caché del navegador y nunca bufferiza el documento.

// src/download.mjs
import express from 'express'
import * as Minio from 'minio'
import { pipeline } from 'node:stream/promises'

const BUCKET = 'documentos'
const client = new Minio.Client({ /* configuración */ })
const app = express()

app.get('/api/documents/:id/content', async (req, res) => {
  const key = await resolveKey(req.params.id) // consulta a tu base de datos
  const stat = await client.statObject(BUCKET, key)
  const type = stat.metaData['content-type'] ?? 'application/octet-stream'

  const headers = {
    'Content-Type': type,
    'ETag': stat.etag,
    'Accept-Ranges': 'bytes',
    'Cache-Control': 'private, max-age=60',
  }

  const inm = req.headers['if-none-match']?.replaceAll('"', '')
  if (inm === stat.etag) return res.status(304).end()
  const range = req.headers.range
  if (!range) {
    res.writeHead(200, { ...headers, 'Content-Length': stat.size })
    return sendObject(key, res)
  }

  const [, rawStart, rawEnd] = /^bytes=(\d*)-(\d*)$/.exec(range) ?? []
  if (rawStart === undefined) return sendRangeError(res, stat.size)

  let start = rawStart === '' ? Math.max(0, stat.size - Number(rawEnd)) : Number(rawStart)
  let end = rawEnd === '' ? stat.size - 1 : Math.min(Number(rawEnd), stat.size - 1)
  if (!Number.isFinite(start) || start > end || start >= stat.size) {
    return sendRangeError(res, stat.size)
  }

  res.writeHead(206, {
    ...headers,
    'Content-Range': `bytes ${start}-${end}/${stat.size}`,
    'Content-Length': end - start + 1,
  })
  return sendObject(key, res, start, end - start + 1)
})

async function sendObject(key, res, offset, length) {
  try {
    const stream = offset === undefined
      ? await client.getObject(BUCKET, key)
      : await client.getPartialObject(BUCKET, key, offset, length)
    await pipeline(stream, res)
  } catch (err) {
    if (err.code === 'ERR_STREAM_PREMATURE_CLOSE') return // el cliente cortó
    throw err
  }
}

function sendRangeError(res, size) {
  res.writeHead(416, { 'Content-Range': `bytes */${size}` })
  res.end()
}

El orden importa: comprobar If-None-Match antes de abrir el stream evita trabajo y ancho de banda. El 304 no lleva cuerpo, pero sí debe llevar el ETag para que el cliente lo siga usando.

El Content-Length de un rango no es el tamaño del objeto

Es end - start + 1. Si envías el tamaño completo con un cuerpo parcial, el cliente espera bytes que no llegan y la descarga se queda colgada hasta el timeout.

Miniaturas con sharp, sin sorpresas de memoria

sharp usa libvips, que trabaja por franjas y no necesita cargar el bitmap completo. Aun así, el patrón más seguro es descargar a un temporal, transformar a otro fichero y subir con el tamaño ya conocido.

// src/thumbs.mjs
import sharp from 'sharp'
import { createReadStream, createWriteStream, statSync } from 'node:fs'
import { mkdtemp, rm } from 'node:fs/promises'
import { pipeline } from 'node:stream/promises'
import { tmpdir } from 'node:os'
import { join } from 'node:path'
export async function makeThumbnail(client, key) {
  const dir = await mkdtemp(join(tmpdir(), 'minio-thumb-'))
  const input = join(dir, 'input')
  const output = join(dir, 'output.jpg')
  try {
    const source = await client.statObject('documentos', key)
    const stream = await client.getObject('documentos', key)
    await pipeline(stream, createWriteStream(input))

    await sharp(input)
      .rotate()                                  // respeta la orientación EXIF
      .resize({ width: 480, withoutEnlargement: true })
      .jpeg({ quality: 82, mozjpeg: true })
      .toFile(output)

    const size = statSync(output).size
    const thumbKey = `thumbs/${source.etag}-${key.split('/').pop()}.jpg`
    await client.putObject(
      'documentos', thumbKey, createReadStream(output), size,
      {
        'Content-Type': 'image/jpeg',
        'Cache-Control': 'public, max-age=31536000, immutable',
        'X-Amz-Meta-Source-Key': key,
        'X-Amz-Meta-Source-Etag': source.etag,
      },
    )
    return { thumbKey, size }
  } finally {
    await rm(dir, { recursive: true, force: true })
  }
}

La clave de la miniatura incluye el ETag del original. Si el documento cambia, cambia la clave, y no hay que invalidar ninguna caché: la URL anterior simplemente deja de generarse. Ese es el mismo principio de content-addressed que usan los CDN.

6 · Errores habituales

1. Cargar el objeto entero para responderlo

Mal — el tamaño del objeto entra en RAM 
const stream = await client.getObject(bucket, key)
const chunks = []
for await (const chunk of stream) chunks.push(chunk)
res.send(Buffer.concat(chunks)) // ❌ 2 GB de RAM para un vídeo de 2 GB
Bien — del objeto a la respuesta, sin buffer intermedio 
res.writeHead(200, { 'Content-Type': 'video/mp4', 'Content-Length': stat.size })
await pipeline(await client.getObject(bucket, key), res)

El buffer intermedio no aporta nada si no vas a modificar el contenido. Si necesitas transformar, encadena un Transform en el pipeline.

2. Ignorar la cabecera Range

Mal — siempre 200 con el objeto completo 
app.get('/video', async (req, res) => {
  await pipeline(await client.getObject(bucket, key), res)
}) // ❌ el reproductor no puede adelantar
Bien — 206 con el tramo pedido 
res.writeHead(206, {
  'Content-Range': `bytes ${start}-${end}/${stat.size}`,
  'Content-Length': end - start + 1,
  'Accept-Ranges': 'bytes',
})
await pipeline(await client.getPartialObject(bucket, key, start, end - start + 1), res)

El reproductor del navegador pide rangos desde el primer segundo. Si respondes con todo el archivo, la reproducción funciona pero el salto de minutaje descarga de nuevo desde cero.

3. Cachear para siempre una clave mutable

Mal — mismo nombre, contenido nuevo 
await client.putObject(bucket, 'avatars/ana.jpg', body, size, {
  'Cache-Control': 'public, max-age=31536000, immutable', // ❌
})
Bien — clave nueva por versión 
const key = `avatars/ana-${sha256.slice(0, 12)}.jpg`
// nueva subida -> nueva clave -> caché inmutable honesta

Con immutable, el navegador no revalida durante un año. Si cambias el contenido bajo la misma URL, el usuario verá la foto antigua y no hay forma remota de arreglarlo salvo cambiar la URL.

7 · Ejercicio guiado

Objetivo: descargar con streaming, servir rangos correctamente y generar una miniatura idempotente.

  1. Genera una imagen de prueba y súbela: 
    npm install sharp@^0.35.5
node -e "require('sharp')({ create: { width: 2000, height: 1500, channels: 3, background: '#C72C48' } }).jpeg().toFile('foto.jpg')"
mc cp foto.jpg local/documentos/acme/2026/11/foto.jpg

    Salida esperada: foto.jpg: 42.1 KiB aproximadamente.

  2. Descarga con pipeline y compara el hash: 
    node --env-file=.env descargar.mjs
sha256sum foto.jpg
node -e "console.log(require('crypto').createHash('sha256').update(require('fs').readFileSync('informe.pdf')).digest('hex'))"

    Los dos hashes deben coincidir. Si no, el stream se cerró antes de tiempo.

  3. Pide un rango y comprueba el tamaño: 
    const s = await client.getPartialObject('documentos', key, 0, 1024)
let n = 0
for await (const chunk of s) n += chunk.length
console.log(n) // 1024
  4. Levanta el endpoint de la sección 4 y pide rangos con curl: 
    curl -i -H 'Range: bytes=0-1023' http://localhost:3000/api/documents/abc/content
    HTTP/1.1 206 Partial Content
Accept-Ranges: bytes

  5. Comprueba el 304: copia el ETag de la respuesta anterior y repite con -H 'If-None-Match: "..."'. Debe devolver 304 Not Modified sin cuerpo. Prueba también bytes=999999- y espera 416.
  6. Genera la miniatura dos veces: ejecuta makeThumbnail con la misma clave. La segunda ejecución debe reutilizar la misma clave de destino y no crear objetos nuevos. Comprueba con mc ls local/documentos/thumbs/ y mc stat que el Cache-Control es el esperado.

Comprobación final

Haz una descarga de un objeto de 100 MB mientras observas la memoria del proceso con docker stats o el monitor del sistema. Debe mantenerse plana. Si sube en escalera, hay un buffer escondido en algún punto del pipeline.

8 · Reto

🎯 Variantes bajo demanda con caché

Implementa un endpoint /api/documents/:id/thumb?w=240 que genere la miniatura al vuelo la primera vez, la guarde en thumbs/<etag>/<ancho>.jpg y la sirva desde ahí en las siguientes peticiones. Debe admitir tres anchos permitidos, rechazar el resto y no regenerar si el objeto ya existe.

Cuando llegue una versión nueva del documento, las miniaturas antiguas deben dejar de servirse sin borrar nada de inmediato. Añade una métrica de cache hit y explica qué harías para limpiar las variantes huérfanas sin recorrer el bucket entero cada noche.

Pista: el ETag del original ya está en la ruta. Para la limpieza, piensa en lifecycle por prefijo y en un índice de variantes generadas, no en un listado completo.

9 · Resumen

  • getObject y getPartialObject devuelven streams; consúmelos con pipeline o for await.
  • Los rangos se responden con 206, Content-Range y el Content-Length del tramo.
  • Un objeto que se reenvía no necesita buffer intermedio: del stream de MinIO al socket.
  • Los ficheros temporales acotan la memoria pero hay que borrarlos siempre y limitar la concurrencia.
  • sharp transforma por franjas, pero el patrón seguro es temporal de entrada y temporal de salida.
  • Content-Type y Cache-Control se fijan al escribir; las claves inmutables permiten caché agresiva.
  • Las transformaciones caras van a un worker idempotente, no al handler de la petición.

10 · Preguntas frecuentes

¿Puedo pedir varios rangos en una sola petición?

S3 no soporta multipart/byteranges. getPartialObject pide un único intervalo. Si necesitas varias partes, haz varias peticiones o descarga el objeto completo; para vídeo adaptativo se usan segmentos separados, no múltiples rangos en una respuesta.

¿Puedo pasar el stream de getObject directamente a putObject?

Sí, si conoces el tamaño de antemano y lo pasas como argumento; si no, el SDK no puede planificar la subida. Para copias dentro del mismo servidor es más eficiente copyObject, que no baja los bytes al cliente. Y si el origen y el destino están en servidores distintos, un stream con tamaño conocido funciona bien.

¿Por qué mi vídeo se ve pero no se puede adelantar?

Casi siempre porque el endpoint ignora Range y devuelve 200 con el objeto completo. El reproductor puede reproducir desde el principio, pero al buscar reinicia la descarga. Comprueba que devuelves 206, Accept-Ranges: bytes y un Content-Range correcto.

¿Es seguro usar sharp con archivos subidos por usuarios?

sharp delega en libvips y ha tenido CVEs, como cualquier parser de formatos complejos. Mantén la dependencia actualizada, limita el tamaño y las dimensiones de entrada, ejecuta el procesado con menos privilegios y, si el riesgo es alto, en un contenedor aislado. No confíes en la extensión del fichero.
