Notificaciones de eventos

Módulo 4 · Ciclo de vida 🕐 40 minutos

1 · Introducción

Cuando un documento llega al bucket, la aplicación necesita enterarse: extraer texto, generar un thumbnail, pasarlo por el antivirus, indexarlo o avisar al equipo. Hay dos formas de saberlo. La mala es preguntar cada pocos segundos con un LIST y comparar contra una base de datos. La buena es que el almacenamiento emita un evento cuando algo cambia.

MinIO implementa las notificaciones de eventos de S3: el servidor observa las operaciones sobre un bucket y publica un mensaje JSON en un destino configurado. El destino puede ser un webhook HTTP, una cola AMQP (RabbitMQ), Kafka, NATS, MQTT, Redis o una base de datos. La aplicación deja de hacer polling y reacciona a hechos.

El patrón parece simple —«sube un archivo, llega un JSON»— y esconde tres decisiones que separan una integración sólida de una que pierde documentos en silencio:

  • La entrega no es exactamente una vez. Un reintento puede duplicar un evento; tu consumidor tiene que ser idempotente.
  • La cola es finita. Si el destino está caído y la cola se llena, MinIO descarta eventos nuevos. La notificación no es un registro de auditoría.
  • El evento no es el dato. El mensaje dice «existe esta clave y esta versión»; el contenido hay que leerlo del bucket, y puede haber cambiado.

Por qué esta lección se conecta con RabbitMQ

MinIO emite eventos, pero no es un broker: no tiene enrutado por tópicos, ni colas duraderas por consumidor, ni dead letter queues. Cuando el pipeline crece, el patrón habitual es MinIO → RabbitMQ → workers. El curso Aprende RabbitMQ cubre la parte que MinIO deliberadamente no hace.

2 · Teoría

Qué eventos existen

MinIO agrupa los eventos por familia. Los nombres que se pasan a mc event add son cortos; el mensaje usa el nombre S3 completo.

Nombre cortoEvento S3Cuándo se emite
puts3:ObjectCreated:*Al crear o sobrescribir un objeto (incluye multipart completado y copia).
gets3:ObjectAccessed:GetAl leer un objeto. Genera mucho volumen; úsalo con cuidado.
deletes3:ObjectRemoved:*Al borrar una versión o crear un delete marker.
replicas3:Replication:*Cambios de estado de replicación.
ilms3:LifecycleTransitionCuando lifecycle transiciona o expira un objeto.
scans3:ObjectRestore:*Eventos del scanner/restauración, según versión.

Para un pipeline de documentos, put,delete es el 90 % de los casos. Añadir get multiplica el tráfico y suele ser una decisión de analítica, no de procesado.

Destinos: no todos sirven para lo mismo

DestinoConfigCuándo elegirlo
Webhook HTTPnotify_webhookPrototipos, servicios pequeños, integraciones sin broker.
AMQP 0-9-1 (RabbitMQ)notify_amqpEnrutado, colas duraderas, reintentos y DLQ gestionados por el broker.
Kafkanotify_kafkaAlto volumen, log particionado, varios consumidores independientes.
PostgreSQL / MySQLnotify_postgres / notify_mysqlRegistro transaccional en una base existente.

Todos comparten la misma mecánica: se declara un target con un identificador, se reinicia el servidor y se asocia el target a un bucket con un ARN. Cambiar de webhook a RabbitMQ no cambia el modelo, solo el destino y el consumidor. También existen destinos NATS, MQTT, Redis y Elasticsearch con el mismo esquema.

El ARN: cómo se conecta todo

configuración del servidor              asociación al bucket
+-----------------------------+         +--------------------------------------+
| notify_webhook:1            |         | mc event add myminio/documentos      |
|   endpoint=http://...       |  ARN    |   arn:minio:sqs::1:webhook           |
|   queue_dir=/opt/events     |-------->|   --event put,delete                 |
+-----------------------------+         +--------------------------------------+
         ^                                          |
         |                                          v
   identificador "1"                    eventos publicados en el endpoint

La forma del ARN es arn:minio:sqs::<ID>:<TIPO>. El identificador debe coincidir exactamente con el que pusiste tras los dos puntos en notify_webhook:1. Un desajuste es la causa número uno de «la configuración está puesta pero no llega nada».

El payload

El mensaje sigue el formato de notificaciones de S3. Un PUT produce algo así:

{
  "EventName": "s3:ObjectCreated:Put",
  "Key": "documentos/2026/acta.pdf",
  "Records": [{
    "eventTime": "2026-11-05T09:12:44.123Z",
    "s3": {
      "bucket": { "name": "documentos" },
      "object": {
        "key": "2026/acta.pdf", "size": 48213,
        "eTag": "9f2b1c4d8e7a...", "versionId": "01J9Z8K3M4N5...",
        "contentType": "application/pdf",
        "userMetadata": { "tenant": "acme" }
      }
    }
  }]
}

Qué mirar: EventName distingue creación de borrado; versionId es la clave de idempotencia natural (dos reintentos comparten versión); y eTag identifica contenido, pero en multipart no es el MD5 del archivo. El evento no lleva el PDF: el worker debe hacer getObject con clave y versión, y esa versión sigue siendo legible aunque el objeto se haya sobrescrito.

Entrega: al menos una vez, nunca exactamente una

MinIO mantiene una cola por destino. En modo asíncrono (el de por defecto) envía el evento y continúa; si el destino falla, reintenta. Ese diseño prioriza el rendimiento y produce dos efectos que debes asumir:

EfectoPor qué ocurreCómo se mitiga
DuplicadosEl destino recibió el evento pero el ACK se perdió; MinIO reintenta.Idempotencia por bucket + key + versionId + eventName.
PérdidasLa cola se llenó o el proceso se reinició sin queue_dir persistente.queue_dir en disco, queue_limit suficiente y reconciliación periódica.

La cola por defecto admite 100 000 eventos. Cuando se llena, MinIO descarta los nuevos. Subir el límite ayuda, pero no convierte la notificación en un log duradero. Si necesitas garantías fuertes, el patrón es:

MinIO --evento--> RabbitMQ/Kafka (durable, con DLQ) --> workers
   |                                                        |
   +---- queue_dir persistente (buffer ante caídas) --------+
                                                            |
              reconciliación periódica: LIST del bucket vs. índice de procesados

El modo síncrono (MINIO_API_SYNC_EVENTS=on o api.sync_events=on) espera el ACK antes de continuar. Reduce pérdidas a costa de bajar el ritmo de envío y llenar la cola antes. No lo actives «por seguridad» sin medir: puedes convertir un pico de subidas en un cuello de botella.

Idempotencia: el contrato del consumidor

Un consumidor correcto responde rápido (valida y encola; el trabajo pesado va a un worker), registra la clave de idempotencia antes de actuar (tabla con restricción única o Redis con TTL) y reconcilia una vez al día listando el bucket. Los eventos son la vía rápida, no la única fuente de verdad.

3 · Ejemplo mínimo

Un webhook local que imprime los eventos del prefijo documentos/. Primero el receptor en Node.js 22 ESM:

// webhook.mjs — receptor mínimo, sin dependencias
import { createServer } from "node:http";
createServer(async (req, res) => {
  if (req.method !== "POST") return res.writeHead(405).end();
  let body = "";
  for await (const chunk of req) body += chunk;
  const event = JSON.parse(body);
  const { key, versionId } = event.Records?.[0]?.s3?.object ?? {};
  console.log(event.EventName, key, versionId);
  res.writeHead(200).end("ok");
}).listen(8080, () => console.log("webhook escuchando en :8080"));

Ahora la configuración de MinIO:

mc admin config set myminio notify_webhook:1 \
  endpoint="http://127.0.0.1:8080/events" \
  auth_token="$WEBHOOK_TOKEN" \
  queue_dir="/opt/minio/events" \
  queue_limit="10000"
mc admin service restart myminio
mc event add myminio/documentos \
  arn:minio:sqs::1:webhook \
  --event put,delete \
  --prefix "documentos/"

Qué hace cada línea:

  • notify_webhook:1: declara el target con identificador 1. Ese 1 es el que aparece en el ARN.
  • endpoint: URL que recibirá los POST. Debe ser alcanzable desde el contenedor de MinIO; localhost dentro del contenedor no es tu máquina.
  • auth_token: token que MinIO envía para que el receptor distinga peticiones legítimas.
  • queue_dir: buffer en disco para eventos no entregados. Sin esto, un reinicio pierde la cola en memoria.
  • queue_limit: tamaño máximo. Si se llena, se descartan eventos nuevos.
  • mc admin service restart: los cambios de notify_* requieren reinicio. No lo omitas.
  • --prefix "documentos/": solo ese prefijo; el resto del bucket no genera mensajes.

Verifica y prueba:

mc event list myminio/documentos
printf 'contenido de prueba\n' | mc pipe myminio/documentos/documentos/2026/prueba.txt

s3:ObjectCreated:Put documentos/2026/prueba.txt 01J9Z8K3M4N5P6Q7R8S9T0V1W2

Si no llega nada, el orden de comprobación es siempre el mismo: target configurado → servidor reiniciado → ARN con el identificador correcto → endpoint alcanzable desde MinIO → prefijo coincide.

4 · Ejemplo real

El almacén de documentos necesita procesar cada PDF que llega: extraer texto, contar páginas y escribir un JSON derivado en derivados/. El pipeline es asíncrono y tolera reintentos.

PUT documentos/2026/acta.pdf
          |
          v
   MinIO --s3:ObjectCreated:Put--> webhook --200 OK--> cola
                                                        |
                                                        v
                                    worker PDF --escribe--> derivados/2026/acta.json

El receptor no procesa: valida, deduplica y encola.

// receptor.mjs — deduplicación persistente en un log append-only
import { createServer } from "node:http";
import { readFile, appendFile } from "node:fs/promises";

const RUTA = "./procesados.log";
const procesados = new Set(
  (await readFile(RUTA, "utf8").catch(() => "")).split("\n").filter(Boolean)
);

async function registrar(id) {
  if (procesados.has(id)) return false;
  procesados.add(id);
  await appendFile(RUTA, `${id}\n`);
  return true;
}

createServer(async (req, res) => {
  if (req.method !== "POST") return res.writeHead(405).end();
  let body = "";
  for await (const chunk of req) body += chunk;
  let event;
  try { event = JSON.parse(body); } catch { return res.writeHead(400).end("json inválido"); }
  const record = event.Records?.[0];
  const bucket = record?.s3?.bucket?.name;
  const object = record?.s3?.object;
  if (!bucket || !object?.key) return res.writeHead(400).end("evento incompleto");
  const id = `${bucket}/${object.key}@${object.versionId}:${event.EventName}`;
  if (!(await registrar(id))) return res.writeHead(200).end("duplicado");
  console.log("nuevo trabajo", id); // aquí solo se encola
  res.writeHead(200).end("aceptado");
}).listen(8080);

Un log sirve para un proceso, no para un clúster

El ejemplo evita dependencias y funciona con Node.js 22, pero el Set y el archivo no resisten varios receptores en paralelo. En producción usa una tabla con restricción UNIQUE sobre la clave de idempotencia o Redis con SET NX; la idea es la misma, la garantía es atómica.

El worker descarga siempre por versión, no por la clave actual. Si llegan dos eventos de la misma clave con versiones distintas, cada uno procesa su contenido; si llega el mismo evento dos veces, la tabla lo corta.

// worker.mjs — descarga la versión exacta del evento
import { Client } from "minio";
const minio = new Client({
  endPoint: process.env.MINIO_ENDPOINT, port: 9000, useSSL: true,
  accessKey: process.env.MINIO_ACCESS_KEY, secretKey: process.env.MINIO_SECRET_KEY,
});
export async function procesar({ bucket, key, versionId }) {
  const stream = await minio.getObject(bucket, key, versionId);
  // ...extraer texto, escribir derivados/<key>.json...
  return stream;
}

Depurar sin adivinar

mc watch myminio/documentos --prefix "documentos/" --event put,delete muestra los eventos que MinIO emite, sin depender de tu webhook. Si mc watch los ve y tu receptor no, el problema está en la configuración del target o en la red, no en el bucket.

Cuando el volumen crece, el webhook deja de ser el destino adecuado: no tiene ACK duradero, ni reintentos con backoff gestionados, ni DLQ. El salto natural es publicar en RabbitMQ y que los workers consuman de una cola durable. La lógica de idempotencia no cambia; solo cambia el transporte.

5 · Buenas prácticas

HazEvitaPor qué
Responder 200 en milisegundos y encolar Extraer el PDF dentro del handler HTTP El timeout de MinIO provoca reintentos y multiplica el trabajo.

6 · Errores habituales

1. El identificador del target no coincide con el ARN

Mal — configurar uno y suscribir otro 
mc admin config set myminio notify_webhook:primary endpoint="http://api:8080/events"
mc event add myminio/documentos arn:minio:sqs::1:webhook --event put
# ❌ El ARN apunta al target "1"; el configurado se llama "primary". Nunca llega nada.
Bien — el mismo identificador en ambos lados 
mc admin config set myminio notify_webhook:1 endpoint="http://api:8080/events"
mc admin service restart myminio
mc event add myminio/documentos arn:minio:sqs::1:webhook --event put,delete
mc event list myminio/documentos

2. Procesar en el handler y provocar duplicados

Mal — trabajo pesado dentro del webhook 
app.post("/events", async (req, res) => {
  await extraerTexto(req.body);   // ❌ 30 s; MinIO reintenta y llega otra vez
  await escribirDerivado(req.body);
  res.sendStatus(200);
});
Bien — aceptar, deduplicar y encolar 
app.post("/events", async (req, res) => {
  const id = idempotencyKey(req.body);
  const nuevo = await registro.insertarSiNoExiste(id);
  if (!nuevo) return res.sendStatus(200);
  await cola.publicar(req.body);  // vuelve en milisegundos
  res.sendStatus(202);
});

3. Apuntar el webhook a localhost desde el contenedor

Mal — mezclar el espacio de red del host y del contenedor 
mc admin config set myminio notify_webhook:1 endpoint="http://localhost:8080/events"
# ❌ Dentro del contenedor, localhost es el propio MinIO. Connection refused en bucle.
Bien — usar el nombre del servicio o el host alcanzable 
mc admin config set myminio notify_webhook:1 \
  endpoint="http://api:8080/events"   # nombre del servicio en la red de Compose

En local con Compose, el receptor y MinIO deben compartir red. Si el receptor corre en el host, usa host.docker.internal (Docker Desktop) o la IP del bridge.

7 · Ejercicio guiado

Objetivo: recibir eventos reales, comprobar el payload y verificar que un duplicado no se procesa dos veces.

  1. Arranca el receptor mínimo en una terminal y deja que escuche: 
    node webhook.mjs
# webhook escuchando en :8080

    Si usas Compose, copia webhook.mjs al servicio api y expón el puerto 8080.

  2. Configura el target y reinicia: 
    mc admin config set myminio notify_webhook:1 \
  endpoint="http://api:8080/events" \
  auth_token="dev-token" \
  queue_dir="/opt/minio/events" \
  queue_limit="10000"
mc admin service restart myminio
mc admin info myminio

    Salida esperada: el servidor vuelve a estar online y mc admin info responde.

  3. Suscribe el bucket a put y delete: 
    mc event add myminio/documentos \
  arn:minio:sqs::1:webhook \
  --event put,delete \
  --prefix "documentos/"
mc event list myminio/documentos

    Debe aparecer una línea con el ARN, los eventos y el prefijo.

  4. Genera un evento y lee el payload: 
    printf 'acta\n' | mc pipe myminio/documentos/documentos/2026/acta.txt
mc stat myminio/documentos/documentos/2026/acta.txt

    En la terminal del receptor verás s3:ObjectCreated:Put documentos/2026/acta.txt <versionId>. Compara el versionId con el de mc stat.

  5. Provoca un duplicado y limpia: envía dos veces el mismo JSON al receptor con curl; la segunda respuesta debe ser duplicado. Después retira la suscripción con mc event remove myminio/documentos arn:minio:sqs::1:webhook y comprueba que mc event list ya no muestra eventos.

Comprobación final

Ejecuta mc watch myminio/documentos --event put,delete en otra terminal y sube un objeto. Si mc watch lo muestra pero el webhook no, el fallo está en el target o en la red. Si tampoco lo muestra, revisa el prefijo y el nombre del evento.

8 · Reto

🎯 Un pipeline que sobrevive a la caída del consumidor

Construye un pipeline que procese los PDF de documentos/ y escriba un JSON en derivados/. Debe cumplir: el receptor responde en menos de 200 ms, mata el worker a mitad de un trabajo y no se pierde nada, y si el mismo evento llega tres veces solo se genera un derivado.

Después apaga el receptor durante dos minutos, sube diez documentos y vuelve a arrancarlo. ¿Cuántos derivados aparecen? ¿Qué habría pasado sin queue_dir? Documenta el resultado con evidencia, no con suposiciones.

Pista: separa aceptación, encolado y procesado. La clave de idempotencia debe vivir fuera de la memoria del proceso; el versionId del evento es tu mejor candidato.

9 · Resumen

  • El flujo tiene tres piezas: target (notify_*), ARN (arn:minio:sqs::ID:TIPO) y suscripción (mc event add).
  • Los eventos útiles para un pipeline son put y delete; get multiplica el volumen.
  • La entrega es al menos una vez en el mejor caso: puede duplicar, desordenar y —si la cola se llena— descartar. El consumidor debe ser idempotente.
  • versionId es la clave natural de idempotencia; el evento no contiene el objeto, solo sus metadatos.
  • queue_dir y queue_limit son la diferencia entre un buffer y una promesa falsa.
  • Para garantías fuertes, MinIO publica en RabbitMQ/Kafka y el broker aporta durabilidad, reintentos y DLQ.

10 · Preguntas frecuentes

¿MinIO garantiza entrega exactamente una vez?

No. En modo asíncrono puede reintentar tras un ACK perdido y puede descartar si la cola se llena; en modo síncrono reduce las pérdidas pero no elimina los duplicados. Diseña siempre consumidores idempotentes y añade una reconciliación periódica con el bucket.

¿Puedo tener varios destinos para el mismo bucket?

Sí. Puedes declarar varios targets y añadir varias suscripciones con ARN distintos. Cada una mantiene su propia cola y su propio consumo. Úsalo con criterio: cada destino multiplica el trabajo de emisión y el riesgo de configuraciones divergentes.

¿Los eventos incluyen los borrados por lifecycle?

Depende del tipo de evento que suscribas. Los eventos ilm cubren transiciones y expiraciones del ciclo de vida; delete cubre borrados iniciados por un cliente. Si necesitas reaccionar a limpiezas automáticas, suscribe ilm, no delete.

¿Por qué no simplemente hago polling con LIST?

Porque escala mal: cada consulta recorre claves y compites con el tráfico real. Además introduces latencia y necesitas estado para saber qué ya procesaste. El polling es aceptable como reconciliación diaria, no como mecanismo principal.
