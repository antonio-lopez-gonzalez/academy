Erasure coding

Módulo 5 · Operación 🕐 35 minutos

1 · Introducción

Hasta ahora el curso ha tratado el bucket como una caja negra: mc cp entra, mc cat sale. Pero debajo hay discos, y los discos fallan. La pregunta que responde el erasure coding es muy concreta: si se rompen varios discos a la vez, ¿puedo seguir leyendo y escribiendo, o he perdido el bucket?

La respuesta de MinIO no es RAID ni una copia completa del dato. Es Reed-Solomon: cada objeto se parte en shards, se calculan shards de paridad y se reparten entre discos. Con eso, un objeto se reconstruye aunque falten varios fragmentos. La misma idea que usan los CD, los códigos QR y los enlaces espaciales, aplicada a object storage.

Entender el modelo importa por tres razones prácticas:

  • Capacidad: la paridad consume espacio. Un clúster de 100 TB no ofrece 100 TB.
  • Tolerancia: el nivel de paridad decide cuántos discos puedes perder. No es un número mágico, es una decisión de diseño.
  • Operación: tras un fallo, el clúster queda degradado hasta que el healing termina. Ese periodo es el más peligroso.

Erasure coding no es backup

Protege de un fallo de hardware dentro del clúster. No protege de un borrado, de un error de aplicación ni de perder el centro de datos entero. Para eso están el versionado, la réplica y el backup de las lecciones anteriores. Son capas, no alternativas.

2 · Teoría

N = K + M

Tres letras que explican todo el mecanismo:

SímboloNombreQué representa
NErasure set sizeNúmero de discos del conjunto sobre el que se reparte un objeto (4 a 16).
KData shardsFragmentos con datos reales. Es el mínimo necesario para leer.
MParity shardsFragmentos calculados. Permiten reconstruir hasta M fragmentos perdidos.

La regla de oro: M nunca puede superar N/2. Como mínimo debe quedar tanta información útil como paridad; si no, el sistema sería más caro que una copia completa y no aportaría nada.

objeto: acta.pdf (48 MB)

                 D1  D2  D3 ... D12 | P1  P2  P3  P4      N = 16, K = 12, M = 4
                    |       |       |       |       |
        +-----------+-------+-------+-------+-------+-----------+
        |     |     |     |     |     |     |     |     |     |
      disk1 disk2 disk3 ... disk12 disk13 disk14 disk15 disk16
        D1    D2    D3      D12     P1     P2     P3     P4
  se puede perder CUALQUIER combinación de 4 discos y el objeto sigue completo

Dos matices que la analogía del RAID pierde:

  • No hay un disco «de paridad» dedicado ni un disco «principal». Todos los discos contienen shards de todos los objetos.
  • La pérdida tolerable no es «un disco por cada grupo», sino M discos del erasure set, sean cuales sean. Con M=4, puedes perder cuatro discos a la vez.

Paridad por defecto según el tamaño del set

Discos en el erasure setParidad por defectoSobrecosteFallos tolerados
1EC:01,00×0 (desarrollo, sin protección)
2 – 3EC:12,00× – 1,50×1
4 – 5EC:22,00× – 1,67×2
6 – 7EC:32,00× – 1,75×3
8 – 16EC:42,00× – 1,33×4

El sobrecoste se calcula como N / K. Con 16 discos y EC:4: 16 / 12 = 1,33×. Es decir, para almacenar 1 TB de datos necesitas 1,33 TB de disco bruto. Con EC:8 en 16 discos, 16 / 8 = 2×: la mitad del disco es paridad.

La paridad se decide al crear el pool

El tamaño del erasure set se fija cuando MinIO inicializa un server pool y no se puede cambiar después. La paridad sí se puede ajustar en caliente, pero solo afecta a objetos nuevos: los existentes conservan la paridad con la que se escribieron. Cambiar EC:4 por EC:2 no reescribe el pasado.

Quórum: leer y escribir necesitan K

MinIO necesita al menos K shards para leer un objeto y K discos disponibles para escribir uno nuevo. Con N=16 y K=12:

Discos caídosLecturaEscrituraEstado
0SíSíÓptimo.
1 – 4Sí, reconstruyendoSíDegradado pero operativo: aún quedan ≥ 12.
5 – 11Depende del objetoNoPérdida de quórum de escritura; algunos objetos con más de 4 shards perdidos son ilegibles.
12 – 16NoNoDatos perdidos para los objetos afectados.

«Depende del objeto» no es una evasiva: si un objeto tenía sus 16 shards en discos que siguen vivos, se lee; si perdió 5 o más, no. La tolerancia es por conjunto de shards, no una propiedad global mágica.

Qué pasa cuando falla un disco, paso a paso

t0  falla disk7
    - MinIO detecta el fallo y marca el disco offline
    - las lecturas siguen: se reconstruye desde los 15 shards restantes
    - las escrituras siguen: hay 15 >= K=12
    - el clúster queda DEGRADADO: queda margen para 3 fallos más
t1  healing automático
    - el scanner detecta shards que faltan
    - reconstruye los datos del disco perdido en los discos sanos
    - consume CPU, disco y red; puede tardar horas en un bucket grande
t2  healing completo
    - vuelve la redundancia completa (4 fallos tolerables)
    - hasta aquí, el riesgo era real: un segundo fallo reducía el margen

El periodo entre t0 y t2 es el que hay que vigilar. Un clúster degradado no es un clúster sano con una luz amarilla: es un clúster con menos margen del que fue diseñado para tener.

Healing: automático, pero no instantáneo

MinIO repara en lectura cuando detecta un shard corrupto y, en segundo plano, con el scanner. Para forzarlo o comprobar el estado:

mc admin heal myminio
mc admin heal -r myminio/documentos
mc admin heal -r myminio/documentos --dry-run
mc admin heal -r myminio/documentos --scan deep
FlagUso
-rRecursivo: recorre el bucket o prefijo.
--dry-runInforma de lo que repararía sin tocar nada. Útil para dimensionar.
--scan deepComprueba también la integridad de los shards, no solo su presencia. Más lento.
--removeElimina objetos corruptos irrecuperables. Es destructivo: úsalo con criterio.

Bit rot: el fallo silencioso

Un disco puede devolver datos distintos de los que se escribieron sin avisar: un bit que se voltea por desgaste, temperatura o firmware. MinIO calcula un hash HighwayHash por shard y lo verifica en cada lectura. Si no cuadra, reconstruye el shard desde la paridad y marca el disco para healing. Esa es la diferencia entre «el archivo se lee» y «el archivo se lee bien».

Storage class: pagar más o menos paridad

MinIO permite dos clases por defecto:

ClaseConfiguraciónUso
STANDARDParidad alta (por defecto, EC:4)Datos importantes, lecturas frecuentes.
REDUCED_REDUNDANCYParidad menor (por ejemplo, EC:2)Datos derivados, temporales, reproducible desde el original.
 
mc admin config get myminio storage_class
mc admin config set myminio storage_class \
  standard=EC:4 \
  reduced_redundancy=EC:2

El cliente elige la clase al escribir:

mc cp --storage-class REDUCED_REDUNDANCY \
  ./thumbnails/acta.jpg myminio/documentos/derivados/

La clase se guarda con el objeto; cambiarla en el servidor no reescribe lo ya almacenado. Y no es una forma de «ahorrar espacio» sin coste: reducir paridad reduce la tolerancia a fallos de esos objetos.

Límites que conviene saber

  • Un solo disco no tiene paridad: en el Compose de desarrollo verás EC:0. No es un clúster tolerante a fallos.
  • El erasure set no crece: si necesitas más capacidad o más discos por set, se añade un pool nuevo, no se estira el existente.
  • Objetos pequeños: cada uno genera N shards y metadatos; con millones de ficheros de 1 KB, el coste dominante no es el dato.
  • Healing compite con el tráfico: reconstruir un disco grande puede saturar la red; planifícalo.
  • No sustituye a RAID de forma automática: MinIO recomienda JBOD y gestiona la redundancia él mismo; poner RAID debajo suele duplicar la protección y complicar la operación.

3 · Ejemplo mínimo

Lo más pequeño que puedes hacer para entender tu despliegue es preguntarle a MinIO cómo está organizado:

mc admin info myminio

●  minio.local:9000
   Uptime: 3 hours
   Version: 2026-10-28T07:31:12Z
   Network: 1/1 OK
   Drives: 4/4 OK
   Pool: 1
Pools:
   1st, Erasure sets: 1, Drives per erasure set: 4
120 GiB Used, 3 Buckets, 1842 Objects
4 drives online, 0 drives offline, EC:2

Cómo leerlo:

  • Drives 4/4 OK: no hay discos caídos en este momento.
  • Erasure sets: 1: todos los discos forman un único conjunto. Con más de 16 discos verías varios sets.
  • Drives per erasure set: 4: N=4. Es el tamaño con el que se calculó la paridad.
  • EC:2: K=2, M=2. Con 4 discos, se toleran 2 fallos; el sobrecoste es 4/2 = 2×.

Y ahora la comprobación que casi nadie hace: ¿qué clase de almacenamiento está configurada?

mc admin config get myminio storage_class

storage_class standard=EC:4 reduced_redundancy=EC:2

Si el set tiene 4 discos y la clase estándar pide EC:4, MinIO no puede cumplirla: la paridad máxima es N/2 = 2. La configuración se acepta, pero la paridad efectiva se limita al máximo posible. Por eso conviene que standard y el tamaño del set sean coherentes.

4 · Ejemplo real

El almacén de documentos crece hasta necesitar 40 TB útiles. El equipo diseña un clúster de cuatro nodos con cuatro discos de 4 TB cada uno: 16 discos, 64 TB brutos.

Dimensionamiento

4 nodos × 4 discos × 4 TB = 64 TB brutos
erasure set: 16 discos (un solo set)
paridad estándar: EC:4  →  K=12, M=4
sobrecoste: 16/12 = 1,33×
capacidad útil: 64 TB / 1,33 ≈ 48 TB
tolerancia: 4 discos (o un nodo entero, si sus 4 discos fallan)
EscenarioDiscos disponiblesQué ocurre
Falla un disco15/16Lecturas y escrituras continúan; healing reconstruye.
Falla un nodo entero12/16Sigue operativo al límite: quedan exactamente K=12.
Falla un nodo y un disco de otro11/16Sin quórum de escritura; lecturas solo si el objeto conserva ≥12 shards.
Falla un segundo nodo8/16Muchos objetos ilegibles. Situación de pérdida parcial.

Un nodo no es un disco

Si los 4 discos de un nodo están en el mismo chasis y se cae la fuente, pierdes 4 discos de golpe. Con EC:4 estás en el límite exacto: cualquier fallo adicional te deja sin escrituras. Por eso los clústeres serios distribuyen discos entre nodos y añaden margen (EC:3 o EC:4 con más de 16 discos por pool).

Configurar la clase estándar

mc admin config set myminio storage_class \
  standard=EC:4 \
  reduced_redundancy=EC:2
mc admin service restart myminio
mc admin info myminio

Los objetos nuevos se escribirán con 12+4. Los antiguos, con la paridad que tuvieran. Si el equipo quiere cambiar la paridad de todo el bucket, necesita reescribirlo (copiar a un bucket nuevo), no basta con cambiar la configuración.

Operar un fallo

03:12  alerta: drive /data/disk3 offline en minio-2
03:13  mc admin info myminio
       → 15 drives online, 1 offline, EC:4
03:14  el tráfico de lectura sigue; las escrituras siguen (15 ≥ 12)
03:15  se sustituye el disco físicamente
03:40  MinIO detecta el disco nuevo y comienza el healing
05:10  healing completo: 16/16 online, redundancia restaurada
durante 1h 58m el clúster tuvo 3 fallos de margen en vez de 4

El error de operación típico no es el fallo del disco: es no reponerlo porque «el clúster sigue funcionando». Un clúster que lleva tres meses con un disco menos está a un fallo de quedarse sin margen, y nadie lo sabe porque los listados responden.

Comprobar el estado del healing

mc admin heal -r myminio/documentos --dry-run
mc admin heal -r myminio/documentos --scan deep

El --dry-run es la forma segura de saber cuánto queda por reparar sin lanzar carga adicional. El --scan deep verifica integridad; úsalo en una ventana de mantenimiento, no en hora punta.

6 · Errores habituales

1. Creer que un nodo con 4 discos tolera 4 fallos «de nodo»

Mal — confundir shards con hosts 
EC:4 sobre 4 nodos × 4 discos
❌ "Puedo perder 4 nodos"
   En realidad: 4 discos. Si caen 2 nodos, has perdido 8 discos.
Bien — razonar por discos y por dominio de fallo 
4 discos tolerados = 1 nodo completo (4 discos) y nada más.
Para tolerar 2 nodos con 4 discos cada uno: M ≥ 8
→ N=16, EC:8, sobrecoste 2×. Es una decisión de coste, no gratis.

2. Cambiar la paridad y suponer que reescribe los objetos

Mal — bajar EC para recuperar espacio 
mc admin config set myminio storage_class standard=EC:2
# ❌ Los objetos existentes siguen con EC:4 y el espacio no cambia.
Bien — cambiar la clase y reescribir si hace falta 
mc admin config set myminio storage_class standard=EC:2
mc mirror --overwrite myminio/documentos myminio/documentos-nuevo
# Solo los objetos nuevos usan la nueva paridad; migrar es una decisión aparte.

3. Ignorar el clúster degradado

Mal — «sigue respondiendo, lo miro luego» 
mc admin info myminio
# 15 drives online, 1 offline, EC:4
# ❌ Se deja así durante semanas; el margen es de 3 fallos, no de 4.
Bien — reponer y verificar el healing 
mc admin info myminio --offline
mc admin heal -r myminio --dry-run
# Reponer el disco y confirmar que vuelve a 16/16 y healing completo.

7 · Ejercicio guiado

Objetivo: leer la geometría real del clúster, calcular su capacidad útil y comprobar el estado del healing sin tocar datos.

  1. Inspecciona el clúster: 
    mc admin info myminio
mc admin info myminio --offline

    Anota: número de pools, erasure sets, discos por set, discos online/offline y el valor EC:N. En el Compose de desarrollo verás un solo disco y EC:0: es lo esperado.

  2. Lee la configuración de storage class: 
    mc admin config get myminio storage_class

    Si el set tiene 4 discos, la paridad máxima es EC:2. Comprueba si la configuración pide algo imposible y explica qué hará MinIO.

  3. Calcula a mano: para N=16 y EC:4, ¿cuál es K, cuántos fallos tolera y cuánto sobrecoste tiene? Para N=8 y EC:3, ¿cuánta capacidad útil queda de 32 TB brutos? Deja los números escritos antes de seguir.
  4. Escribe un objeto con clase reducida en un bucket de laboratorio: 
    mc mb --ignore-existing myminio/lab-ec
printf 'derivado reproducible\n' > derivado.txt
mc cp --storage-class REDUCED_REDUNDANCY \
  derivado.txt myminio/lab-ec/derivados/prueba.txt
mc ls --json myminio/lab-ec/derivados/

    Salida esperada: el objeto aparece con la clase REDUCED_REDUNDANCY. En un solo disco la paridad efectiva sigue siendo 0; lo que se demuestra es la etiqueta y el flujo.

  5. Comprueba el healing en seco y limpia: 
    mc admin heal -r myminio/lab-ec --dry-run
mc rb --force myminio/lab-ec

    Salida esperada: ningún objeto pendiente. Si cambiaste la storage class del clúster, vuelve a dejarla como estaba y reinicia.

Comprobación final

Vuelve a mc admin info y explica en una frase por qué la capacidad «usada» y la «disponible» no suman el tamaño bruto de los discos. Si no sabes responder, repasa la relación N/K antes de pasar al modo distribuido.

Calcula el coste bruto, el sobrecoste y el número de fallos que quedan disponibles tras perder un nodo.

Compara dos alternativas: una con 16 discos por pool y otra con varios pools de 8. ¿Cuál tolera mejor el fallo de un nodo? ¿Qué pasa con la capacidad si un pool queda inaccesible?

Pista: el erasure set nunca cruza pools. Un pool caído no se reconstruye desde otro pool; solo la réplica o el backup cubren ese escenario.

9 · Resumen

  • Erasure coding parte cada objeto en K datos + M paridad, repartidos por el erasure set.
  • Se toleran hasta M fallos de disco; M nunca supera N/2.
  • Leer requiere K shards; escribir requiere K discos disponibles.
  • El sobrecoste es N/K: EC:4 en 16 discos cuesta un 33 % de capacidad.
  • El tamaño del erasure set se fija al crear el pool; la paridad se puede cambiar, pero solo afecta a objetos nuevos.
  • Un fallo deja el clúster degradado hasta que el healing termina; ese es el periodo de riesgo.
  • Erasure coding protege del fallo de hardware, no de borrados ni de perder el sitio.

10 · Preguntas frecuentes

¿Erasure coding es lo mismo que RAID?

Comparten la idea de paridad, pero el nivel de abstracción es distinto. RAID protege discos y es transparente al sistema de archivos; el erasure coding de MinIO protege objetos, reparte shards entre nodos y reconstruye en lectura. MinIO recomienda JBOD y gestionar la redundancia en el servidor, no debajo.

¿Puedo cambiar la paridad de un bucket existente?

Puedes cambiar la configuración de storage class, pero solo se aplica a objetos nuevos. Los existentes conservan la paridad con la que se escribieron. Para cambiarlos hay que reescribirlos (copiar a un bucket nuevo y sustituir), lo que consume tiempo, red y espacio temporal.

¿Qué pasa si pierdo más shards de los que tolera un objeto?

Ese objeto es ilegible. Otros objetos que no tenían shards en los discos perdidos pueden seguir leyéndose. No hay una recuperación mágica: la única vía es restaurar desde réplica o backup. Por eso el healing y la reposición de discos no son opcionales.

¿Cuánta capacidad útil me queda realmente?

Capacidad bruta × K/N, menos el margen de seguridad que quieras dejar. Con 16 discos y EC:4, el 75 %. A eso réstale versiones, réplica y backups: el número que ves en mc admin info es capacidad usable del clúster, no espacio libre para datos nuevos después de todo.
