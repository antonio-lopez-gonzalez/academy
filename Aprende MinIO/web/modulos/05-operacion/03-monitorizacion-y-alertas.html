Monitorización y alertas

Módulo 5 · Operación 🕐 35 minutos

1 · Introducción

Un clúster MinIO puede estar fallando de tres formas distintas y las tres se parecen a «va lento»: un disco a punto de morir sube la latencia, un nodo sin quórum devuelve 503 a una de cada cuatro peticiones, y la capacidad baja hace que el siguiente upload grande bloquee las escrituras.

disco lento ────────┐
nodo sin quórum ────┼──> «va lento» ──> latencia, 503, escrituras bloqueadas
capacidad baja ─────┘

Ninguna se detecta mirando la consola web de vez en cuando. La monitorización existe para convertir esas señales en números, y las alertas para convertir los números en una persona que actúa antes de que sea tarde. Y una alerta sin runbook es solo un mensaje que alguien silenciará.

En esta lección montamos las tres capas: salud (¿responde?), métricas (¿cómo está?) y alertas con procedimiento (¿qué hacemos?).

La pregunta que ordena todo

No monitorices «todo lo que MinIO expone». Monitoriza lo que responde a: ¿puedo servir lecturas?, ¿puedo aceptar escrituras?, ¿voy a quedarme sin espacio?, ¿estoy perdiendo datos o redundancia? Todo lo demás es contexto para depurar.

Live no es «está sano»

/minio/health/live solo dice que el proceso responde. Un nodo sin quórum, con un disco muerto o con el healing atascado puede devolver 200 en live. Para el estado real necesitas cluster, mc admin info y las métricas de discos.

mc admin info: la foto que hay que saber leer

Métricas: Prometheus y el endpoint v3

MinIO expone métricas en formato Prometheus. La versión 3 las organiza por dominio y es la recomendada para despliegues nuevos:

Endpoint v3Contenido
/minio/metrics/v3/clusterCapacidad, uso, salud y erasure sets.
/minio/metrics/v3/system/driveDiscos: espacio, latencia, errores, inodos.
/minio/metrics/v3/api/requestsPeticiones S3, errores y latencia.
/minio/metrics/v3/replicationEstado de réplica y backlog.
/minio/metrics/v3/ilmTransiciones y expiraciones.
/minio/metrics/v3/notificationColas y entrega de eventos.

El scrape se genera con mc, que incluye el bearer token necesario:

mc admin prometheus generate cluster cluster --api-version v3

scrape_configs:
- job_name: minio-job-cluster
  bearer_token: eyJhbGciOiJIUzUxMiIsInR5cCI6IkpXVCJ9...
  metrics_path: /minio/metrics/v3/cluster
  static_configs: [{ targets: ['minio.example.net:9000'] }]

Para ver las métricas sin montar Prometheus:

mc admin prometheus metrics cluster --api-version v3 | head -40

El token caduca. Si el scrape empieza a devolver 401 de la noche a la mañana, casi siempre es eso: automatiza la rotación o usa credenciales de servicio con permisos de solo métricas.

El healing no siempre tiene una métrica única

El estado del healing se lee mejor con mc admin info y mc admin heal -r ALIAS --dry-run que con un número aislado. Si quieres alertar, hazlo sobre la causa —disco offline, errores de disco, objetos pendientes— y no sobre un contador cuyo significado cambia entre versiones.

Alertas: síntoma, no ruido

Una alerta útil tiene cuatro partes: condición, umbral, ventana y acción. Sin la cuarta, no es una alerta; es una notificación.

groups:
- name: minio
  rules:
  - alert: MinioNodeOffline
    expr: minio_cluster_health_nodes_offline_count > 0
    for: 2m
    labels:
      severity: critical
    annotations:
      summary: "Hay un nodo de MinIO offline"
      runbook: "https://runbooks.example.net/minio/node-offline"
  - alert: MinioCapacityLow
    expr: |
      minio_cluster_capacity_usable_free_bytes
        / minio_cluster_capacity_usable_total_bytes < 0.20
    for: 30m
    labels:
      severity: warning
    annotations:
      summary: "Menos del 20 % de capacidad usable"
      runbook: "https://runbooks.example.net/minio/capacity"

Criterios que evitan la fatiga:

  • Ventanas (for) de 2 a 10 minutos: un pico de un scrape no es un incidente.
  • Umbrales con margen: avisar al 70 % de capacidad deja tiempo para expandir; al 95 %, ya es tarde.
  • Síntomas antes que causas: «errores 5xx altos» es accionable; «CPU al 60 %» normalmente no.

Logs: el contexto que las métricas no dan

mc admin logs cluster --last 100
mc admin logs cluster --type application --last 50
mc admin logs cluster --type minio --last 50
mc support diag cluster

mc admin logs unifica los logs de los nodos; mc support diag genera un informe de diagnóstico para soporte. En Kubernetes, además, kubectl logs del pod concreto sigue siendo la vía para ver el arranque y los reinicios.

Runbook: qué hacer cuando suena

AlertaPrimera acciónDespués
Nodo offlinemc admin info --offline; comprobar red y proceso.Reincorporar; verificar healing; no borrar datos.
Disco offlineIdentificar la ruta y el nodo; revisar dmesg/SMART.Sustituir disco; confirmar healing completo.

3 · Ejemplo mínimo

La comprobación más pequeña que merece la pena automatizar: ¿el clúster puede aceptar escrituras ahora mismo?

#!/usr/bin/env bash
set -euo pipefail
URL="${MINIO_URL:?falta MINIO_URL}"
for probe in live ready cluster; do
  code="$(curl -sS -o /dev/null -w '%{http_code}' "$URL/minio/health/$probe")"
  printf '%-10s %s\n' "$probe" "$code"
  if [ "$code" != "200" ]; then
    echo "FALLO: $probe devolvió $code" >&2
    exit 1
  fi
done
echo "MinIO responde y tiene quórum de escritura"

Qué hace y por qué está ordenado así:

  • live: descarta que el proceso esté muerto. Si falla, no hay nada más que comprobar.
  • ready: descarta que el nodo esté arrancando o fuera de servicio.
  • cluster: comprueba el quórum. Es el que de verdad decide si un PUT va a funcionar.
  • set -euo pipefail: el script falla ante cualquier error, no solo ante el último comando.

Este script es un buen smoke test de despliegue, pero no sustituye a Prometheus: solo mira el instante en que se ejecuta. Las alertas necesitan series temporales.

4 · Ejemplo real

El almacén de documentos tiene un panel de control y cuatro alertas. El panel responde a «¿cómo estamos?»; las alertas, a «¿hay que actuar ya?».

Panel mínimo

Seis cifras bastan: capacidad usable (34,2 / 48 TiB, 71 %), nodos y discos (4/4 y 15/16), ratio de errores S3, latencia p95 del peor disco, peticiones por segundo y réplica pendiente. Debajo, healing, última ejecución de lifecycle y días hasta que caduque el certificado TLS.

Qué se alerta y qué no

SeñalAlertaMotivo
Nodo offlineSí, critical a los 2 minReduce quórum y redundancia de inmediato.
Disco offlineSí, critical a los 5 minEl healing no empieza hasta que alguien repone.
Capacidad < 20 %Sí, warning a los 30 minQueda tiempo para expandir sin urgencia.
Errores S3 > 1 %Sí, warning a los 10 minPuede ser cliente o servidor; el runbook separa.
CPU al 60 %NoNo es accionable por sí solo; va en el panel.
Un pico de latencia de 10 sNoRuido; se investiga si persiste.
Certificado TLS < 30 díasSí, warningUn fallo de TLS tumba el servicio igual que un disco.

Cómo se ve un incidente con estas piezas

A las 09:02 salta MinioDiskOffline en minio-3. El runbook confirma 15/16 discos y escrituras OK, se sustituye el disco a las 09:20, el healing termina a las 11:10 y se cierra con el RTO real anotado. Sin la alerta, el disco habría seguido offline durante semanas.

Consultas que se usan en el panel

100 * minio_cluster_capacity_usable_free_bytes / minio_cluster_capacity_usable_total_bytes
sum(rate(minio_s3_requests_errors_total[5m])) / sum(rate(minio_s3_requests_total[5m]))
max by (server, drive) (1 - minio_node_drive_free_bytes / minio_node_drive_total_bytes)
histogram_quantile(0.95, sum by (le) (rate(minio_node_drive_latency_us_bucket[5m])))

La última consulta asume que la métrica de latencia es un histograma en tu versión. Si no lo es, usa el valor directo y ajusta el umbral: lo importante es vigilar el peor disco, no la media del clúster, que esconde el problema.

5 · Buenas prácticas

HazEvitaPor qué
Monitorizar cluster, no solo live Confundir «proceso vivo» con «clúster sano» Un nodo sin quórum responde a live y falla los PUT.
Vigilar el peor disco y el peor nodo Mirar solo la media del clúster Un disco al 99 % basta para bloquear escrituras de su set.
Ventanas for y umbrales con margen Alertar al primer scrape que cruza un límite El ruido hace que se ignoren las alertas importantes.
Runbook con comandos y dueño Alertas que solo dicen «algo va mal» En un incidente, la claridad vale más que la telemetría.

6 · Errores habituales

1. Usar solo /minio/health/live como monitor

Mal — «devuelve 200, está sano» 
curl -f https://minio.example.net:9000/minio/health/live
# ❌ 200 aunque el clúster haya perdido quórum o tenga 3 discos caídos.
Bien — combinar live, ready y cluster 
curl -f https://minio.example.net:9000/minio/health/ready
curl -f https://minio.example.net:9000/minio/health/cluster
mc admin info cluster --offline

2. Alertar de capacidad con un número absoluto

Mal — un umbral que no significa nada 
# ❌ "Quedan menos de 5 TB": en un clúster de 400 TB es una emergencia;
# en uno de 8 TB, es el estado normal desde el primer mes.
expr: minio_cluster_capacity_usable_free_bytes < 5e12
Bien — porcentaje y tendencia 
expr: |
  minio_cluster_capacity_usable_free_bytes
    / minio_cluster_capacity_usable_total_bytes < 0.20
for: 30m

Añade al panel una proyección de días hasta llenarse con la pendiente de los últimos 30 días. Es la señal que permite planificar en vez de apagar fuegos.

3. Scrapear cada 5 segundos y alertar al instante

Mal — ruido garantizado 
# ❌ Cualquier micro-pico de latencia dispara una página a las 3 de la mañana.
expr: minio_node_drive_latency_us > 100000
for: 0m
Bien — ventana y percentil 
expr: |
  histogram_quantile(0.95,
    sum by (le) (rate(minio_node_drive_latency_us_bucket[5m]))
  ) > 500000
for: 10m

7 · Ejercicio guiado

Objetivo: montar la cadena completa salud → métricas → alerta → runbook, y comprobar que cada eslabón funciona.

  1. Comprueba los cuatro endpoints de salud: 
    for probe in live ready cluster; do
  curl -sS -o /dev/null -w "$probe: %{http_code}\n" \
    "http://localhost:9000/minio/health/$probe"
done
curl -sS -o /dev/null -w "maintenance: %{http_code}\n" \
  "http://localhost:9000/minio/health/cluster?maintenance=true"

    Salida esperada en el Compose de desarrollo: 200 en los tres primeros. maintenance puede devolver 412: con un solo nodo, apagarlo pierde el quórum.

  2. Lee el estado real: 
    mc admin info myminio
mc admin info myminio --offline

    Anota discos online/offline, nodos y EC:N. Compara lo que dice live con lo que dice info: no son la misma pregunta.

  3. Genera la configuración de scrape: 
    mc admin prometheus generate myminio cluster --api-version v3

    Guarda la salida en prometheus/minio-scrape.yml. Identifica el metrics_path, el bearer_token y el target.

  4. Lee métricas sin Prometheus: 
    mc admin prometheus metrics myminio --api-version v3 | \
  grep -E "minio_cluster_capacity_usable_(total|free)_bytes|minio_cluster_health_nodes_offline_count|minio_node_drive_offline_total"

    Calcula a mano el porcentaje libre: free / total × 100. Ese es el número que debe aparecer en el panel.

  5. Escribe las reglas de alerta y el runbook: una regla para nodo offline y otra para capacidad por debajo del 20 %, con for, severity, summary y runbook. Después escribe el runbook de «disco offline» en cinco pasos (confirmar, localizar, sustituir, verificar healing y cerrar con evidencia) e incluye el criterio de escalado.

Comprobación final

Fuerza la alerta de disco en un entorno de laboratorio (por ejemplo, con una métrica de prueba o un disco desmontado) y comprueba que llega, que el runbook se entiende y que el cierre deja evidencia. Una alerta que nunca se ha disparado no está probada.

8 · Reto

🎯 Detectar una degradación antes de que sea un incidente

Diseña una alerta que avise cuando el clúster esté perdiendo redundancia de forma lenta: por ejemplo, un disco con errores de timeout crecientes pero aún online. Debe dispararse antes de que el disco caiga, no después, y no debe saltar por un único error aislado.

Escribe la consulta PromQL, el umbral, la ventana y el runbook. Después explica cómo la probarías sin romper un disco de producción y qué harías si la alerta se dispara un viernes a las 18:00.

Pista: mira la derivada de los errores, no el valor absoluto, y combínala con la latencia del mismo disco. Un contador que sube en escalera es más informativo que un total acumulado.

9 · Resumen

  • live dice que el proceso vive; ready, que puede atender; cluster, que hay quórum de escritura.
  • mc admin info es la foto operativa; --offline aísla lo que falta.
  • Prometheus v3 organiza las métricas por dominio; mc admin prometheus generate produce el scrape con token.
  • Vigila capacidad usable, nodos y discos offline, latencia del peor disco y ratio de errores S3.
  • Alerta sobre síntomas accionables, con ventana y con runbook; evita el ruido de CPU y picos puntuales.
  • El healing se verifica con mc admin info y heal --dry-run, no solo con una métrica.

10 · Preguntas frecuentes

¿Necesito Prometheus o basta con la consola web?

La consola sirve para mirar, no para avisar. Sin series temporales no puedes ver tendencias, ni distinguir un pico de una degradación, ni alertar a las 3 de la mañana. Para producción, Prometheus (o un sistema compatible) y alertas con runbook son el mínimo.

¿Cada cuánto debo scrapear?

Cada 15 o 30 segundos es un buen equilibrio para MinIO: suficiente resolución y poco coste. Scrapear cada segundo multiplica el almacenamiento de series sin mejorar la detección, porque las alertas usan ventanas de minutos.

¿Qué hago si el token de Prometheus caduca?

Regenerarlo con mc admin prometheus generate y actualizar el scrape. Mejor aún: automatiza la rotación o usa credenciales de servicio con permisos mínimos. Un panel congelado es peor que un panel vacío, porque parece sano.

¿Cómo sé si el healing ha terminado?

Con mc admin info (todos los discos online) y mc admin heal -r ALIAS --dry-run (sin objetos pendientes). Si además quieres integridad, --scan deep en una ventana de mantenimiento. No te fíes solo de que el bucket responda.

¿Debo alertar de cada error 4xx?

No. Los 4xx suelen ser clientes con credenciales mal configuradas, claves inexistentes o firmas caducadas. Alerta sobre el ratio total de errores y separa 4xx de 5xx en el panel; los 5xx indican problemas del servidor y sí merecen atención inmediata.
