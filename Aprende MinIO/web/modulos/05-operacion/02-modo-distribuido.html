Modo distribuido

Módulo 5 · Operación 🕐 40 minutos

1 · Introducción

El docker compose up del curso levanta un MinIO de un solo proceso y un solo disco. Es perfecto para aprender la API, pero es un punto único de fallo: si el contenedor muere, el bucket muere con él. Producción empieza cuando el almacenamiento sobrevive a la caída de una máquina.

El modo distribuido de MinIO reparte los datos entre varios servidores y discos. No hay un nodo coordinador ni un disco maestro: todos los nodos son iguales, hablan entre sí y participan en cada escritura. Es un sistema server-side de erasure coding a escala de clúster.

Aquí hay una frontera que el curso repite porque se ignora mucho: Docker Compose no está soportado para un clúster distribuido. Compose sirve para desarrollo local de un nodo. Un despliegue distribuido real se hace con el Kubernetes Operator o sobre baremetal con systemd. El motivo no es burocracia: es que un clúster necesita nombres estables, discos locales dedicados y una orquestación que no recicle contenedores con datos dentro.

Qué vas a poder decidir al terminar

Cuántos nodos y discos necesita tu carga, qué tolerancia a fallos compras con cada topología, cómo se amplía sin downtime y por qué añadir un pool no es lo mismo que ampliar un pool existente.

2 · Teoría

Pools: la unidad de crecimiento

Un despliegue distribuido se compone de uno o más server pools. Cada pool es un grupo de nodos con sus discos, y dentro de cada pool MinIO crea uno o varios erasure sets.

MINIO_VOLUMES="https://minio{1...4}.example.net:9000/data/disk{1...4}"
                          POOL 1
        +-----------------------------------------------+
        |  minio1   minio2   minio3   minio4           |
        |  4 discos 4 discos 4 discos 4 discos          |
        |                                               |
        |  erasure set de 16 discos  →  EC:4            |
        +-----------------------------------------------+
  un pool puede tener más de un erasure set si supera los 16 discos

Reglas que no se negocian:

  • El tamaño de un pool se fija al crearlo. No se puede añadir un disco a un pool existente.
  • Para crecer se añade un pool nuevo, con sus propios nodos y discos.
  • Los erasure sets no cruzan pools. Un objeto vive en un pool; si ese pool cae, sus objetos no se reconstruyen desde otro pool.
  • Un pool con más de 16 discos se divide en varios erasure sets del tamaño que MinIO calcule al inicializar.

Topología mínima con alta disponibilidad

                        balanceador / DNS
                     :9000 (S3)   :9001 (consola)
                              |
        +----------+----------+----------+----------+
        |          |          |          |          |
     minio1     minio2     minio3     minio4
     d1 d2      d1 d2      d1 d2      d1 d2
     d3 d4      d3 d4      d3 d4      d3 d4
        |          |          |          |          |
        +----------+----------+----------+----------+
              16 discos, 1 erasure set, EC:4
              tolera 4 discos = 1 nodo completo

Esta es la topología de referencia del curso: 4 nodos × 4 discos. Tolera la caída de un nodo entero sin perder escrituras, porque quedan 12 discos y K=12. No tolera dos nodos: quedarían 8 discos y muchos objetos perderían más de 4 shards.

Por qué Compose no vale para distribuido

Compose es una herramienta de desarrollo: define contenedores en una sola máquina, con nombres y redes efímeras. Un clúster MinIO necesita exactamente lo contrario.

Lo que necesita el clústerLo que ofrece Compose
Hostnames estables por nodoNombres de servicio que cambian al recrear el contenedor.
Discos locales dedicados por nodoVolúmenes o bind mounts sobre el mismo host; un fallo de host se lleva todo.
Dominios de fallo independientesUna sola máquina: no hay tolerancia real a fallos de nodo.
Orquestación con rolling updatesRecreación manual; sin control de quórum ni de orden.
Escalado y reemplazo de nodosNo hay scheduler ni reconciliación de estado.

Puedes simular varios contenedores en Compose para aprender la sintaxis, pero no es un despliegue soportado ni prueba nada de alta disponibilidad: si el host cae, caen los cuatro «nodos». Para producción, Kubernetes Operator o baremetal.

Kubernetes Operator: el camino gestionado

El Operator declara un Tenant (un clúster MinIO) como recurso de Kubernetes. Él crea los StatefulSets, los volúmenes, los servicios y gestiona el ciclo de vida.

apiVersion: minio.min.io/v2
kind: Tenant
metadata:
  name: minio-documentos
  namespace: minio
spec:
  pools:
    - name: pool-0
      servers: 4
      volumesPerServer: 4
      size: 4Ti
      storageClassName: local-nvme
  mountPath: /export
  requestAutoCert: true

kubectl apply -f tenant.yaml
kubectl get tenants -n minio
kubectl rollout status statefulset/minio-documentos-pool-0 -n minio

La ventaja no es «Kubernetes porque sí»: el Operator aplica los cambios de forma ordenada, respeta el quórum y permite crecer añadiendo pools al spec. La contrapartida es que necesitas un clúster con volúmenes locales o de bloque y experiencia operando CRDs. Lo veremos en detalle en Kubernetes Operator.

Expansión: añadir un pool, no estirar el existente

Cuando la capacidad se acerca al umbral, se añade un pool nuevo. El procedimiento conceptual:

  1. Preparar nodos y discos nuevos, con la misma versión y configuración.
  2. Añadir el pool a MINIO_VOLUMES en todos los nodos, separado por un espacio.
  3. Reiniciar de forma rolling: un nodo a la vez, esperando a que vuelva sano.
  4. Verificar con mc admin info que aparecen los dos pools.
  5. Opcional: rebalancear para mover datos antiguos al pool nuevo.
# Antes: un pool
MINIO_VOLUMES="https://minio{1...4}.example.net:9000/data/disk{1...4}"
# Después: dos pools en una sola línea (EnvironmentFile no admite continuación)
MINIO_VOLUMES="https://minio{1...4}.example.net:9000/data/disk{1...4} https://minio{5...8}.example.net:9000/data/disk{1...4}"

El orden importa

Los pools deben aparecer en el mismo orden en todos los nodos. Un orden distinto hace que los nodos no se reconozcan como el mismo clúster. Y no se puede eliminar un pool del final sin decommission: quitar una línea de MINIO_VOLUMES no borra los datos, pero deja el clúster inconsistente.

Rebalance y decommission

OperaciónComandoQué haceRiesgo
Rebalancemc admin rebalance start ALIASRedistribuye objetos entre pools para equilibrar espacio.Consume red y disco; es online pero lento.
Estadomc admin rebalance status ALIASProgreso y velocidad.—

Ampliación no significa rebalanceo automático: los objetos nuevos se reparten, pero los antiguos se quedan donde estaban. Si el pool viejo está lleno y el nuevo vacío, el espacio no se equilibra solo. Planifica el rebalanceo o acepta que la distribución será desigual.

Alta disponibilidad: qué cubre y qué no

FalloCon 4 nodos × 4 discos, EC:4Cobertura
Un discoSigue todo; healing.Sí
Un nodoSigue al límite (12 discos).Sí, sin margen

El balanceador debe comprobar /minio/health/ready y repartir sin sesión pegajosa: S3 es stateless y cualquier nodo puede atender cualquier objeto. Si un nodo está caído, sacarlo del balanceador evita timeouts, pero no lo expulses del clúster: sigue siendo parte del erasure set y su healing importa.

3 · Ejemplo mínimo

El arranque de un clúster de cuatro nodos con cuatro discos cada uno, en baremetal con systemd. Cada nodo ejecuta exactamente el mismo comando:

export MINIO_VOLUMES="https://minio{1...4}.example.net:9000/data/disk{1...4}"
export MINIO_ROOT_USER="$MINIO_ROOT_USER"
export MINIO_ROOT_PASSWORD="$MINIO_ROOT_PASSWORD"
minio server $MINIO_VOLUMES --console-address :9001

Qué significa cada pieza:

  • minio{1...4}.example.net: notación de expansión. MinIO genera minio1, minio2, minio3 y minio4.
  • /data/disk{1...4}: cuatro rutas de disco por nodo. Deben ser discos físicos o volúmenes de bloque, no carpetas dentro del disco del sistema.
  • https://: TLS entre nodos. En producción no se usa HTTP plano, ni siquiera en la red interna.
  • --console-address :9001: la consola web; la API S3 escucha en :9000.

En el /etc/default/minio de cada nodo queda lo mismo, sin export:

MINIO_VOLUMES="https://minio{1...4}.example.net:9000/data/disk{1...4}"
MINIO_OPTS="--console-address :9001"
MINIO_ROOT_USER=minioadmin
MINIO_ROOT_PASSWORD=CAMBIA-ESTO-Y-USALO-DE-UN-GESTOR-DE-SECRETOS

Y se comprueba desde fuera:

mc alias set cluster https://minio.example.net:9000 "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD"
mc admin info cluster

●  minio.example.net:9000
   Uptime: 12 minutes
   Version: 2026-10-28T07:31:12Z
   Network: 4/4 OK
   Drives: 16/16 OK
   Pool: 1
Pools:
   1st, Erasure sets: 1, Drives per erasure set: 16
16 drives online, 0 drives offline, EC:4

Si ves Network: 4/4, Drives: 16/16 y un solo pool con 16 discos por set, el clúster está completo. Cualquier cifra menor indica un nodo o un disco que no se unió.

4 · Ejemplo real

El almacén de documentos empieza con 4 nodos × 4 discos de 4 TB (64 TB brutos, 48 TB útiles con EC:4). Al año, el uso llega al 70 % y el equipo planifica la expansión.

Situación de partida

Pool 1: 4 nodos × 4 discos × 4 TB = 64 TB brutos
EC:4  →  48 TB útiles
uso: 34 TB (70 % de 48 TB)
proyección: +18 TB en 12 meses → no cabe

Expansión con un segundo pool

Pool 1: minio1..4  × 4 discos × 4 TB  = 64 TB brutos
Pool 2: minio5..8  × 4 discos × 8 TB  = 128 TB brutos
                                       ---------------
                                       192 TB brutos
EC:4 en cada pool → 48 TB + 96 TB = 144 TB útiles
  pool 2 tiene su propio erasure set de 16 discos
  los objetos nuevos se reparten entre pools
  los antiguos siguen en el pool 1 hasta rebalancear
# 1. Actualizar MINIO_VOLUMES en los 8 nodos (mismo orden, una sola línea)
MINIO_VOLUMES="https://minio{1...4}.example.net:9000/data/disk{1...4} https://minio{5...8}.example.net:9000/data/disk{1...4}"
# 2. Rolling restart: un nodo a la vez
sudo systemctl restart minio
# esperar a que mc admin info vuelva a mostrar el nodo sano antes del siguiente
# 3. Verificar
mc admin info cluster
# 4. Opcional: equilibrar
mc admin rebalance start cluster
mc admin rebalance status cluster

Qué NO hacer al ampliar

ErrorConsecuencia
Reiniciar los 8 nodos a la vezSin quórum: el clúster no arranca y las escrituras fallan en bloque.
Añadir un disco suelto a un pool existenteNo está soportado; el pool es inmutable.
Usar un orden distinto de pools por nodoLos nodos no forman el mismo clúster.
Montar el pool nuevo con NFSLatencia y coherencia impredecibles; el healing se degrada.
Confiar en que el rebalance es automáticoEl pool viejo sigue lleno; el nuevo, vacío.

Alta disponibilidad en el día a día

cliente → balanceador (health: /minio/health/ready)
              |            |            |            |
           minio1       minio2       minio3       minio4
              \____________\____________/____________/
                       erasure set 16, EC:4
fallo de minio2:
  - el balanceador deja de enviarle tráfico
  - las escrituras siguen: 12 discos ≥ K=12
  - el healing reconstruye los shards del nodo caído
  - cuando vuelve, se reincorpora y termina de sincronizar

El balanceador no debe enviar tráfico a un nodo que no responde, pero el nodo sigue perteneciendo al clúster. Expulsarlo o borrar sus datos «para limpiar» es la forma más rápida de convertir un fallo recuperable en una pérdida de datos.

5 · Buenas prácticas

HazEvitaPor qué
Diseñar pools con un dominio de fallo claro Meter los 16 discos en un chasis Un fallo de energía no debe contar como 16 fallos simultáneos.
Usar discos locales XFS/ext4 en JBOD RAID, LVM o NFS debajo de MinIO MinIO necesita ver el fallo y gestionar la reconstrucción.
Rolling restart de un nodo a la vez Reiniciar el clúster completo Sin quórum no hay escrituras; el orden mantiene el servicio.
Añadir pools al final y con el mismo orden Reordenar o quitar pools de MINIO_VOLUMES El orden define la identidad del clúster.

6 · Errores habituales

1. Creer que Compose con varios contenedores es un clúster

Mal — cuatro contenedores en un portátil 
services:
  minio1: { image: quay.io/minio/minio, volumes: ["./d1:/data"] }
  minio2: { image: quay.io/minio/minio, volumes: ["./d2:/data"] }
  minio3: { image: quay.io/minio/minio, volumes: ["./d3:/data"] }
  minio4: { image: quay.io/minio/minio, volumes: ["./d4:/data"] }
# ❌ Un solo host, volúmenes locales y nombres efímeros: no hay alta disponibilidad.
Bien — Compose para desarrollo, Operator o baremetal para producción 
# Desarrollo: un nodo, sin pretensiones de HA
docker compose up -d
# Producción: Tenant con el Operator, o nodos baremetal con systemd
kubectl apply -f tenant.yaml

Compose no está soportado para distribuido. Puedes usarlo para entender la sintaxis, pero no para afirmar que tu servicio tolera fallos.

2. Añadir un disco a un pool existente

Mal — intentar estirar el pool 
# ❌ Añadir /data/disk5 a un pool ya creado no amplía su erasure set.
MINIO_VOLUMES="https://minio{1...4}:9000/data/disk{1...5}"
Bien — crear un pool nuevo 
MINIO_VOLUMES="https://minio{1...4}:9000/data/disk{1...4} https://minio{5...8}:9000/data/disk{1...4}"

El tamaño de un pool es inmutable. La ampliación se hace por adición de pools, no por mutación del existente.

3. Reiniciar todos los nodos a la vez

Mal — «reinicio el clúster y ya» 
for n in 1 2 3 4; do ssh minio$n "systemctl restart minio" & done
wait
# ❌ Sin quórum, las escrituras fallan y el clúster puede no volver a formar el set.
Bien — uno a uno, comprobando salud 
for n in 1 2 3 4; do
  ssh minio$n "systemctl restart minio"
  until mc admin info cluster >/dev/null 2>&1; do sleep 5; done
  mc admin info cluster | grep -E "Drives|Network"
done

7 · Ejercicio guiado

Objetivo: pasar de «funciona en mi portátil» a un diseño de clúster verificable, con números y con el comando de arranque correcto.

  1. Inspecciona el despliegue actual: 
    mc admin info myminio

    Anota pools, erasure sets, discos por set y EC:N. En el Compose del curso verás 1 pool, 1 set, 1 disco y EC:0. Escribe en una frase qué fallos tolera hoy: ninguno.

  2. Diseña una topología de 4 nodos × 4 discos de 2 TB: calcula TB brutos, TB útiles con EC:4 y fallos tolerados. Comprueba que 12 discos restantes tras perder un nodo siguen siendo ≥ K.
  3. Escribe el MINIO_VOLUMES exacto para esa topología con notación de expansión. Debe incluir TLS, el puerto 9000 y cuatro rutas de disco por nodo. Compáralo con el del ejemplo y explica cada símbolo.
  4. Simula la expansión: añade un segundo pool de 4 nodos × 4 discos de 4 TB al mismo MINIO_VOLUMES. Calcula la capacidad total y explica qué pasa con los objetos que ya existían. 
    Pool 1: 4 × 4 × 2 TB = 32 TB brutos  → 24 TB útiles (EC:4)
Pool 2: 4 × 4 × 4 TB = 64 TB brutos  → 48 TB útiles (EC:4)
Total: 96 TB brutos → 72 TB útiles
  5. Escribe el runbook de reinicio rolling y verifica el diseño: orden de nodos, comprobación entre nodos, comando de salud, criterio de parada y qué hacer si un nodo no vuelve. Después escribe qué salida esperarías de mc admin info con dos pools (líneas Pools:, Erasure sets y Drives).

Comprobación final

Si tu diseño tolera la caída de un nodo, dilo con precisión: «tolera 4 discos, que es un nodo de 4 discos, y solo mientras el healing no haya terminado». Si necesitas tolerar dos nodos, el número cambia y el coste también.

8 · Reto

🎯 Un plan de expansión sin downtime

El clúster de 4 nodos × 4 discos está al 78 % y la previsión dice que en cinco meses no cabrá. Diseña un plan que añada capacidad sin perder escrituras, sin degradar la latencia de forma inaceptable y sin tocar los datos existentes más de lo necesario. Incluye el orden exacto de reinicios, la comprobación entre pasos y el criterio para abortar.

Después responde: si el pool nuevo tiene 8 discos por nodo y el viejo 4, ¿qué pasa con la distribución de objetos? ¿Qué harías para que el pool viejo dejase de llenarse? ¿Y si el presupuesto solo alcanza para tres nodos nuevos?

Pista: el pool nuevo no hereda los datos del viejo. El rebalanceo es una operación aparte, y tres nodos con cuatro discos pueden no alcanzar el tamaño de erasure set que necesita tu paridad.

9 · Resumen

  • El modo distribuido reparte datos entre nodos y discos; no hay coordinador ni disco maestro.
  • La unidad de crecimiento es el server pool; su tamaño se fija al crearlo y no se estira.
  • Los erasure sets no cruzan pools: un pool caído no se reconstruye desde otro.
  • Compose es solo para desarrollo de un nodo; producción se despliega con Kubernetes Operator o baremetal.
  • Expandir es añadir un pool al final de MINIO_VOLUMES y reiniciar en rolling, un nodo a la vez.
  • La alta disponibilidad del clúster no cubre la pérdida del centro de datos: para eso, réplica.

10 · Preguntas frecuentes

¿Puedo montar un clúster distribuido con Docker Compose?

Técnicamente puedes arrancar varios contenedores, pero no es un despliegue soportado ni proporciona alta disponibilidad: todos comparten host, red y destino de fallo. MinIO documenta Kubernetes y baremetal para distribuido. Usa Compose solo para el nodo de desarrollo del curso.

¿Cuántos nodos necesito como mínimo?

El mínimo práctico son cuatro discos para tener paridad real. Para alta disponibilidad se recomiendan al menos cuatro nodos con discos repartidos, de modo que la caída de un nodo no deje el clúster sin margen. Menos nodos pueden funcionar, pero la tolerancia y el rendimiento se resienten.

¿Puedo añadir un disco a un nodo existente?

No para ampliar el pool actual: el tamaño de un pool es inmutable. Puedes añadir un pool nuevo con esos discos y nodos. Añadir una ruta a MINIO_VOLUMES de un pool existente no aumenta su erasure set y puede dejar el clúster inconsistente.

¿Qué pasa si cae un pool entero?

Los objetos almacenados en ese pool dejan de estar accesibles; los de otros pools siguen. No hay reconstrucción entre pools, porque cada uno tiene sus propios erasure sets. La única protección para ese escenario es la réplica a otro sitio o un backup.
