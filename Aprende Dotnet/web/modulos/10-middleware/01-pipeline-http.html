Pipeline HTTP de ASP.NET Core

Módulo 10 · Middleware y pipelines30 min

1 · Introducción

Cada petición HTTP que llega a una aplicación ASP.NET Core atraviesa una cadena de middleware antes de llegar al endpoint final. Esa cadena se llama pipeline HTTP. Es el equivalente en .NET a las cadenas de filtros de Express.js o a los interceptores de Spring.

En esta lección aprenderemos qué es un middleware, cómo se construye el pipeline, por qué el orden importa y qué hacen métodos como app.Use(), app.Run() y app.Map().

¿Qué problema resuelve?

El pipeline permite aplicar comportamiento transversal a todas las peticiones (logging, seguridad, compresión, rate limiting, tracing) sin ensuciar cada endpoint. Es como una línea de montaje donde cada operario hace una tarea y pasa el paquete al siguiente.

Errores típicos

  • Registrar el middleware de autenticación después del de autorización, dejando a los endpoints sin identidad.
  • Colocar app.Run() en medio del pipeline y cortar el flujo de todas las peticiones.
  • Invocar next() dos veces en el mismo middleware, duplicando el trabajo y alterando la respuesta.
  • Olvidar que el pipeline es bidireccional: el código que va hacia el endpoint se ejecuta en el orden de registro, pero el que vuelve se ejecuta al revés.

2 · Teoría

¿Qué es un middleware?

Un middleware es un componente que recibe un HttpContext, hace algo con él y decide si llama al siguiente componente de la cadena o no. Está representado por un delegado RequestDelegate con forma Func<HttpContext, Task>.

Conceptualmente es una cebolla: cada capa puede actuar antes de entrar, después de volver o ambas. Si una capa decide no llamar a next(), la petición se corta (short-circuit) y las capas interiores no se ejecutan.

Componentes del pipeline

  • app.Use(): añade un middleware que puede llamar a next() y continuar.
  • app.Run(): añade un middleware terminal que no llama a next(). Si se ejecuta, termina la cadena.
  • app.Map(): bifurca el pipeline según una ruta. No vuelve a la cadena principal; es un subpipeline.
  • app.UseWhen(): añade un middleware condicionalmente para un subconjunto de rutas pero sí vuelve.

El orden importa

El orden de registro en Program.cs es el orden de ejecución hacia el endpoint. Cuando la respuesta vuelve, el orden se invierte. Un middleware de excepciones debe ir al principio para capturar errores de todos los demás; un middleware de compresión debe ir después de los que escriben la respuesta.

Petición → [ExceptionHandler] → [HttpsRedirection] → [CORS] → [Authentication] → [Authorization] → [Endpoint] →
         ← [ExceptionHandler] ← [HttpsRedirection] ← [CORS] ← [Authentication] ← [Authorization] ← [Respuesta]

Regla mnemotécnica

Orden recomendado: Excepciones → HSTS → Redirección HTTPS → Static Files → Routing → CORS → Autenticación → Autorización → Endpoints. Si un middleware depende de algo, ese algo debe ir antes.

3 · Ejemplo mínimo

Crearemos un proyecto web que muestre el recorrido de la petición con trazas en consola.

# Creamos un proyecto web vacío (sin controllers por defecto)
dotnet new web -n PipelineDemo -o PipelineDemo
cd PipelineDemo

dotnet run --project .
# Probar: http://localhost:5000
// Program.cs
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

// Middleware A: antes y después de la siguiente etapa
app.Use(async (context, next) =>
{
    Console.WriteLine("A: antes de next");
    await next(); // cede el control al siguiente middleware
    Console.WriteLine("A: después de next");
});

// Middleware B
app.Use(async (context, next) =>
{
    Console.WriteLine("B: antes de next");
    await next();
    Console.WriteLine("B: después de next");
});

// Middleware terminal: no llama a next
app.Run(async context =>
{
    Console.WriteLine("Terminal: respondiendo");
    await context.Response.WriteAsync("Hola desde el pipeline");
});

app.Run();

Si llamas a la raíz, verás en consola:

A: antes de next
B: antes de next
Terminal: respondiendo
B: después de next
A: después de next

¿Qué ocurre aquí?

El await next() es el punto de inflexión. Todo lo que escribas antes se ejecuta al bajar hacia el endpoint; todo lo que escribas después se ejecuta al subir con la respuesta.

4 · Ejemplo real

En una API real el pipeline suele ser más largo. Vamos a simular un pipeline con excepciones, redirección HTTPS, CORS y endpoints.

// Program.cs
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

// 1. Captura de excepciones al inicio para cubrir todo lo demás
if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/error");
    app.UseHsts();
}

app.UseHttpsRedirection();

// 2. CORS antes de autenticación, porque el preflight OPTIONS no lleva credenciales
app.UseCors(policy =>
    policy.AllowAnyOrigin()
          .AllowAnyMethod()
          .AllowAnyHeader());

// 3. Autenticación y autorización en el orden correcto
app.UseAuthentication();
app.UseAuthorization();

// 4. Middleware personalizado de trazas
app.Use(async (context, next) =>
{
    var logger = app.Services.GetRequiredService>();
    logger.LogInformation("Request {Method} {Path} started", context.Request.Method, context.Request.Path);
    await next();
    logger.LogInformation("Request finished with status {StatusCode}", context.Response.StatusCode);
});

// 5. Endpoints
app.MapGet("/", () => "OK");
app.MapGet("/error", () => Results.Problem("Ocurrió un error inesperado."));

app.Run();

Cuidado con HSTS en desarrollo

UseHsts() añade la cabecera Strict-Transport-Security. En desarrollo no se aplica porque puede forzar a navegadores a recordar HTTPS para localhost, lo que dificulta las pruebas.

5 · Buenas prácticas

  • Ordena el pipeline con intención. Los middleware de cortocircuito (Map, UseStaticFiles) deben ir temprano si quieres evitar trabajo innecesario.
  • No bloquees. Siempre usa async/await en el pipeline; no llames a .Result o .Wait().
  • Evita duplicar trabajo. Si necesitas leer el body de la respuesta, usa Stream con cuidado porque los streams pueden no ser re-lectables.
  • Usa extensiones con nombre. Registra tus middlewares con métodos UseXxx para que Program.cs sea legible.
  • Documenta las dependencias. Si un middleware necesita autenticación, escribe un comentario indicando que UseAuthentication debe ir antes.

Consejo de rendimiento

El middleware de ExceptionHandler y el de StatusCodePages añaden overhead. En APIs de alto rendimiento, evalúa manejar errores con IExceptionHandler (a partir de .NET 8) para respuestas más ligeras y testables.

6 · Errores habituales

6.1. Llamar a next después de escribir en la respuesta

// ❌ MAL: escribe la respuesta y luego continúa
app.Use(async (context, next) =>
{
    await context.Response.WriteAsync("Primero");
    await next(); // siguiente middleware puede escribir y romper el body
});

El problema: si el siguiente middleware también escribe, la respuesta queda corrupta. Si escribes, generalmente no debes llamar a next.

6.2. app.Run() no es el último

// ❌ MAL: todo lo que va después de Run nunca se ejecuta
app.Run(async context => await context.Response.WriteAsync("A"));
app.Use(async (context, next) => await next()); // nunca llega

La versión correcta es usar app.Run() solo al final del pipeline o usar app.Use() si se necesita continuar.

6.3. Autenticación después de autorización

// ❌ MAL: sin identidad no se puede autorizar
app.UseAuthorization();
app.UseAuthentication();
// ✅ CORRECTO
app.UseAuthentication();
app.UseAuthorization();

7 · Ejercicio guiado

Crea un middleware que mida el tiempo de cada petición y lo añada como cabecera X-Response-Time-ms.

// Program.cs
using System.Diagnostics;

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.Use(async (context, next) =>
{
    var stopwatch = Stopwatch.StartNew();
    await next();
    stopwatch.Stop();

    var elapsedMs = stopwatch.ElapsedMilliseconds;
    context.Response.Headers.Append("X-Response-Time-ms", elapsedMs.ToString());
});

app.MapGet("/slow", async () =>
{
    await Task.Delay(120);
    return "Listo";
});

app.MapGet("/fast", () => "Rápido");

app.Run();

Prueba con curl -i http://localhost:5000/slow y observa la cabecera.

¿Por qué detenemos el Stopwatch después de next?

Porque queremos medir todo el tiempo de procesamiento, incluyendo la ejecución del endpoint y el middleware interiores. El await nos devuelve el control cuando la respuesta ya está lista.

8 · Reto

Construye un middleware de branching: si la petición va a /api/v2/*, añade una cabecera X-Api-Version: 2; si va a /api/v1/*, añade X-Api-Version: 1. Usa app.UseWhen para no duplicar el resto del pipeline.

Intenta resolverlo antes de ver la solución. Pistas: context.Request.Path.StartsWithSegments y app.UseWhen.

9 · Resumen

  • El pipeline HTTP es una cadena de middleware que procesa la petición y la respuesta.
  • app.Use() continúa, app.Run() termina, app.Map() bifurca.
  • El orden de registro determina el orden de ejecución; la vuelta es inversa.
  • El orden correcto de middleware comunes: excepciones, HSTS, HTTPS, estáticos, routing, CORS, autenticación, autorización, endpoints.
  • El pipeline es un patrón común a muchos frameworks, lo que facilita la comparación entre ecosistemas.

10 · Preguntas frecuentes

¿El middleware se ejecuta para cada petición o solo al arrancar?

El registro se hace al arrancar. El middleware se ejecuta para cada petición. La parte del constructor de un middleware personalizado se ejecuta al crear la instancia (singleton, scoped o transient según su registro).

¿Puedo modificar la respuesta una vez que el endpoint ha escrito?

Generalmente no. Si el endpoint ha empezado a enviar bytes al cliente, no puedes cambiar cabeceras. Si necesitas interceptar el body, reemplaza el Response.Body por un MemoryStream temporal, invoca next() y luego copias el resultado.

¿Qué pasa si no llamo a next() en un middleware?

La petición se corta (short-circuit). Ningún middleware posterior ni el endpoint se ejecutará. Es útil para devolver 401 o 404 antes de gastar recursos.

¿Es lo mismo app.Map que app.UseWhen?

No. Map crea una bifurcación que no vuelve a la rama principal. UseWhen añade un middleware condicional que, después de ejecutarse, devuelve el control a la cadena principal.

¿Puedo usar middleware en Minimal APIs y Controllers?

Sí. El pipeline es compartido por ambos. La diferencia es que Minimal APIs no tienen filtros de MVC como IActionFilter, pero sí IEndpointFilter.
