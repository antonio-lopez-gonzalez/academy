Correlation ID y Health Checks

Módulo 10 · Middleware y pipelines25 min

1 · Introducción

En sistemas distribuidos, una petición puede atravesar múltiples servicios, bases de datos, colas y caches. Sin una identidad única, es imposible seguir el rastro de una petición. El Correlation ID es un identificador que se propaga entre servicios y se incluye en los logs. Los Health Checks permiten a los orquestadores y balanceadores saber si la aplicación está sana.

En esta lección aprenderemos a implementar ambos con middleware de ASP.NET Core y a exponerlos de forma profesional.

¿Qué problema resuelven?

El Correlation ID permite correlacionar logs de distintos servicios y entender el flujo completo de una operación. Los Health Checks detectan problemas antes de que el usuario los experimente y permiten reinicios automáticos.

Errores típicos

  • Crear un nuevo correlation ID en cada servicio en lugar de respetar el que vino del cliente.
  • No propagar el correlation ID en llamadas HttpClient salientes.
  • Implementar un health check que consulta la base de datos en cada ping, saturándola.
  • Exponer información sensible en el endpoint /health.

2 · Teoría

Correlation ID

El correlation ID es simplemente un GUID o un identificador único que viaja en una cabecera HTTP, normalmente X-Correlation-ID o Correlation-Id. Si el cliente lo envía, el servidor lo respeta; si no, lo genera. El ID se propaga a:

  • Los logs estructurados (Serilog).
  • Las respuestas al cliente.
  • Las llamadas HTTP a otros servicios.
  • Los mensajes de cola o eventos.

Health Checks

ASP.NET Core incluye Microsoft.Extensions.Diagnostics.HealthChecks. Se registran con AddHealthChecks y se exponen con MapHealthChecks. Pueden ser:

  • Readiness: indica si la aplicación está lista para recibir tráfico. Puede depender de la base de datos.
  • Liveness: indica si la aplicación sigue viva. Suele ser muy ligero.

Health Checks con HealthCheckResult

Cada check devuelve Healthy, Degraded o Unhealthy. Puedes configurar qué checks forman parte de cada endpoint y personalizar el output.

Combinar con OpenTelemetry

En producción moderna, el correlation ID suele ser el traceparent de OpenTelemetry. Así unificas logs, trazas y métricas. En esta lección usamos X-Correlation-ID por simplicidad; en el módulo de telemetría profundizaremos.

3 · Ejemplo mínimo

Crearemos un middleware que lee o genera un correlation ID y lo expone en la respuesta.

dotnet new web -n CorrelationDemo -o CorrelationDemo
cd CorrelationDemo
dotnet run --project .
// Middleware/CorrelationIdMiddleware.cs
public sealed class CorrelationIdMiddleware : IMiddleware
{
    public const string HeaderKey = "X-Correlation-ID";

    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        var correlationId = GetOrCreateCorrelationId(context);
        context.Response.Headers.Append(HeaderKey, correlationId);

        using (LogContext.PushProperty("CorrelationId", correlationId))
        {
            await next(context);
        }
    }

    private static string GetOrCreateCorrelationId(HttpContext context)
    {
        if (context.Request.Headers.TryGetValue(HeaderKey, out var value) &&
            !string.IsNullOrWhiteSpace(value))
        {
            return value.ToString();
        }

        return Guid.NewGuid().ToString();
    }
}
// Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddTransient();

var app = builder.Build();

app.UseMiddleware();

app.MapGet("/", (ILogger logger) =>
{
    logger.LogInformation("Endpoint raíz");
    return Results.Ok(new { message = "Hola" });
});

app.Run();

¿Qué ocurre aquí?

Si el cliente envía X-Correlation-ID: abc-123, la respuesta lo repite. Si no envía nada, el middleware genera un GUID. El uso de LogContext (Serilog) permite incluir el ID en todos los logs de la petición.

4 · Ejemplo real

Añadimos health checks con una verificación de base de datos y un endpoint separado para liveness.

dotnet add package Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore
// Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("Default")!));

builder.Services.AddHealthChecks()
    .AddDbContextCheck("database", tags: new[] { "ready" })
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: new[] { "live" });

builder.Services.AddTransient();

var app = builder.Build();

app.UseMiddleware();

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

app.MapHealthChecks("/health", new HealthCheckOptions
{
    ResponseWriter = async (context, report) =>
    {
        var response = new
        {
            Status = report.Status.ToString(),
            Checks = report.Entries.Select(e => new
            {
                Name = e.Key,
                Status = e.Value.Status.ToString(),
                Duration = e.Value.Duration.ToString()
            })
        };

        await context.Response.WriteAsJsonAsync(response);
    }
});

app.MapGet("/", () => "OK");

app.Run();

UI de Health Checks

Para entornos de desarrollo puedes instalar AspNetCore.HealthChecks.UI, que muestra un panel visual. No lo incluyas en producción sin autenticación, ya que expone detalles internos.

Propagación de correlation ID en HttpClient

public class CorrelationIdDelegatingHandler : DelegatingHandler
{
    private readonly IHttpContextAccessor _httpContextAccessor;

    public CorrelationIdDelegatingHandler(IHttpContextAccessor httpContextAccessor)
    {
        _httpContextAccessor = httpContextAccessor;
    }

    protected override Task SendAsync(HttpRequestMessage request, CancellationToken cancellationToken)
    {
        var correlationId = _httpContextAccessor.HttpContext?.Request.Headers
            .TryGetValue(CorrelationIdMiddleware.HeaderKey, out var value) == true
            ? value.ToString()
            : Guid.NewGuid().ToString();

        request.Headers.TryAddWithoutValidation(CorrelationIdMiddleware.HeaderKey, correlationId);
        return base.SendAsync(request, cancellationToken);
    }
}
builder.Services.AddHttpContextAccessor();
builder.Services.AddHttpClient("Downstream")
    .AddHttpMessageHandler();

5 · Buenas prácticas

  • Respeta el correlation ID entrante. No generes uno nuevo si el cliente ya lo envió.
  • Devuélvelo en la respuesta. Así el cliente puede consultar sus logs propios.
  • Registra el correlation ID en todos los logs. Usa Serilog LogContext o LoggerMessage.
  • Separa liveness de readiness. Kubernetes usa /health/live para decidir si reinicia y /health/ready para decidir si enruta tráfico.
  • No abuses de los health checks pesados. Un ping de base de datos en cada /health puede saturarla. Considera caches o intervalos de sondeo largos.
  • No expongas detalles internos. El endpoint público debe ser mínimo; los detalles completos solo para administradores.

6 · Errores habituales

6.1. Generar siempre un correlation ID nuevo

// ❌ MAL: pierde la trazabilidad entre servicios
var correlationId = Guid.NewGuid().ToString();
// ✅ CORRECTO: reutiliza si existe
var correlationId = context.Request.Headers.TryGetValue(HeaderKey, out var value)
    ? value.ToString()
    : Guid.NewGuid().ToString();

6.2. Health check que no valida dependencias

// ❌ MAL: readiness siempre Healthy
app.MapHealthChecks("/health/ready");
// ✅ CORRECTO: readiness verifica dependencias críticas
builder.Services.AddHealthChecks()
    .AddDbContextCheck(tags: new[] { "ready" });

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

6.3. No usar IHttpContextAccessor correctamente

El HttpContext no se debe propagar a código fuera del request. Para HttpClient, usa un DelegatingHandler que acceda al IHttpContextAccessor en el momento de enviar la petición.

7 · Ejercicio guiado

Crea un health check personalizado que devuelva Degraded si el disco tiene menos de 1 GB libre.

public class DiskSpaceHealthCheck : IHealthCheck
{
    public Task CheckHealthAsync(HealthCheckContext context, CancellationToken cancellationToken = default)
    {
        var drive = new DriveInfo(Path.GetPathRoot(Environment.CurrentDirectory)!);
        var freeGb = drive.AvailableFreeSpace / (1024.0 * 1024.0 * 1024.0);

        if (freeGb < 1)
            return Task.FromResult(HealthCheckResult.Degraded($"Solo quedan {freeGb:F2} GB libres"));

        return Task.FromResult(HealthCheckResult.Healthy($"{freeGb:F2} GB libres"));
    }
}

// Program.cs
builder.Services.AddHealthChecks()
    .AddCheck("disk", tags: new[] { "ready" });

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

Prueba con curl http://localhost:5000/health/ready y observa el estado del disco.

8 · Reto

Implementa un middleware que, si la petición es un POST, PUT o DELETE, añada el correlation ID a un header de respuesta y también lo incluya en un archivo de log local. Luego, añade un health check que verifique que el archivo de log no ha crecido más de 100 MB en la última hora.

9 · Resumen

  • El correlation ID permite seguir una petición a través de servicios y logs.
  • Respeta el ID entrante, genera uno si falta, devuélvelo en la respuesta y propágalo en llamadas externas.
  • Los health checks separan liveness (vive) de readiness (lista para tráfico).
  • Usa AddHealthChecks, IHealthCheck y MapHealthChecks.
  • No expongas detalles sensibles en endpoints de salud públicos.

10 · Preguntas frecuentes

¿Correlation ID es lo mismo que Trace ID?

Conceptualmente son similares. Un correlation ID es un identificador de negocio. Un trace ID (como el de OpenTelemetry) es un identificador técnico de trazas distribuidas. En la práctica, muchos sistemas usan el mismo valor para ambos.

¿Qué pasa si un servicio downstream no acepta la cabecera?

Intenta usar un estándar como traceparent. Si no es posible, documenta la cabecera esperada y proporciona un adaptador en tu servicio.

¿Los health checks deben estar en el mismo puerto que la API?

Depende. Kubernetes y muchos balanceadores prefieren un endpoint en el puerto principal. Para mayor seguridad, puedes exponerlos en un puerto administrativo separado con MapHealthChecks en una segunda aplicación.

¿Debo usar HealthChecks.UI en producción?

Solo si lo proteges con autenticación y autorización. Exponer detalles de todos tus checks puede revelar información útil para un atacante.

¿Cómo propago el correlation ID en mensajes de cola?

Inclúyelo como propiedad o cabecera del mensaje. Cuando el consumidor lo procesa, extrae el ID y lo establece en su propio LogContext para mantener la trazabilidad.
