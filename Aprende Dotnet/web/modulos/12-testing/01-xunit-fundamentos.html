xUnit, Moq y FluentAssertions

Módulo 12 · Testing40 min

1 · Introducción

En esta lección aprenderemos el trío más común para escribir tests unitarios en .NET 8:

  • xUnit: el framework de test más usado en la comunidad .NET moderna.
  • Moq: biblioteca de mocks para simular dependencias.
  • FluentAssertions: biblioteca para escribir aserciones legibles y expresivas.

Un test unitario comprueba una única unidad de código (normalmente una clase o un método) de forma aislada. Para ello necesitamos sustituir las dependencias externas —repositorios, servicios de correo, relojes— por objetos controlados llamados mocks.

¿Por qué xUnit? Es el framework recomendado por Microsoft para ASP.NET Core, soporta bien async/await, paralelismo por defecto y una sintaxis limpia sin atributos heredados.

Al terminar esta lección sabrás escribir tests con [Fact], [Theory], datos parametrizados, mocks con verificación y aserciones tipo Should().Be(...).

2 · Teoría

2.1 xUnit: [Fact] vs [Theory]

En xUnit un método de test es un método público, sin valor de retorno, decorado con un atributo:

  • [Fact]: el test siempre se ejecuta con los mismos datos. Útil para comportamientos fijos.
  • [Theory]: el test se ejecuta una vez por cada conjunto de datos. Útil para probar reglas con múltiples entradas.

2.2 Datos parametrizados

xUnit ofrece tres formas principales de alimentar un [Theory]:

  • [InlineData(...)]: datos escritos directamente en el atributo. Ideal para pocos valores primitivos.
  • [MemberData(nameof(MiMetodo))]: datos devueltos por una propiedad o método estático. Útil para listas grandes.
  • [ClassData(typeof(MiClaseDeDatos))]: datos encapsulados en una clase que implementa IEnumerable<object[]>. Ideal para reutilizar entre tests.

2.3 Contexto compartido

Si varios tests necesitan el mismo objeto costoso (por ejemplo una base de datos en memoria o un HttpClient), usamos IClassFixture<TFixture> para compartirlo por clase de tests.

2.4 Moq: simulación de dependencias

Moq crea automáticamente una implementación de una interfaz o clase abstracta. Podemos:

  • Setup: definir qué devuelve un método para ciertos argumentos.
  • Returns / ReturnsAsync: especificar el valor de retorno síncrono o asíncrono.
  • Throws / ThrowsAsync: simular excepciones.
  • Callback: ejecutar código cuando se invoca el mock.
  • Verify: comprobar que un método fue llamado con los argumentos esperados.

Por defecto Moq usa MockBehavior.Loose: los miembros no configurados devuelven el valor por defecto de su tipo. Con MockBehavior.Strict cualquier llamada no configurada lanza excepción.

2.5 FluentAssertions

FluentAssertions convierte aserciones en frases casi naturales en inglés:

result.Should().Be(expected);
result.Should().NotBeNull();
list.Should().ContainEquivalentOf(expectedDto);
action.Should().Throw<ArgumentException>().WithMessage("*invalid*");

Para colecciones y objetos complejos, BeEquivalentTo compara valores miembro a miembro sin exigir la misma referencia.

2.6 Convención de nombres

Adopta la convención Method_Scenario_ExpectedResult:

[Fact]
public void Add_WhenSecondOperandIsZero_ReturnsFirstOperand() { ... }

Así, cuando un test falla, el nombre describe exactamente qué comportamiento se ha roto.

3 · Ejemplo mínimo

Creamos un proyecto de consola y su test:

# Crear solución y proyectos
dotnet new console -n Calculadora -o CalculadoraApp/src/Calculadora
dotnet new xunit -n Calculadora.Tests -o CalculadoraApp/tests/Calculadora.Tests
dotnet sln CalculadoraApp/CalculadoraApp.sln add CalculadoraApp/src/Calculadora/Calculadora.csproj
dotnet sln CalculadoraApp/CalculadoraApp.sln add CalculadoraApp/tests/Calculadora.Tests/Calculadora.Tests.csproj

# Añadir Moq y FluentAssertions
dotnet add CalculadoraApp/tests/Calculadora.Tests package Moq
dotnet add CalculadoraApp/tests/Calculadora.Tests package FluentAssertions

Calculadora simple:

namespace Calculadora;

public static class Calculadora
{
    public static int Sumar(int a, int b) => a + b;
    public static int Dividir(int a, int b) => b == 0
        ? throw new ArgumentException("El divisor no puede ser cero", nameof(b))
        : a / b;
}

Tests con xUnit:

using FluentAssertions;
using Xunit;

namespace Calculadora.Tests;

public class CalculadoraTests
{
    [Fact]
    public void Sumar_WhenBothOperandsArePositive_ReturnsCorrectSum()
    {
        // Act
        var result = Calculadora.Sumar(2, 3);

        // Assert
        result.Should().Be(5);
    }

    [Theory]
    [InlineData(10, 2, 5)]
    [InlineData(9, 3, 3)]
    [InlineData(0, 5, 0)]
    public void Dividir_WhenDivisorIsNotZero_ReturnsQuotient(int a, int b, int expected)
    {
        var result = Calculadora.Dividir(a, b);
        result.Should().Be(expected);
    }

    [Fact]
    public void Dividir_WhenDivisorIsZero_ThrowsArgumentException()
    {
        // Arrange
        Action act = () => Calculadora.Dividir(5, 0);

        // Act & Assert
        act.Should().Throw<ArgumentException>()
           .WithParameterName("b");
    }
}

Ejecutamos los tests:

dotnet test CalculadoraApp/tests/Calculadora.Tests
Tip: el patrón Arrange-Act-Assert (AAA) mantiene cada test ordenado y facilita la lectura. Separa los tres bloques con una línea en blanco.

4 · Ejemplo real

Imagina un servicio PostService que crea posts. Depende de IPostRepository y IEmailSender. Queremos testear la lógica sin tocar base de datos ni correo real.

using FluentAssertions;
using Moq;
using Xunit;

namespace Cms.Application.Tests.Posts;

public class PostServiceTests
{
    private readonly Mock<IPostRepository> _repositoryMock;
    private readonly Mock<IEmailSender> _emailSenderMock;
    private readonly PostService _sut;

    public PostServiceTests()
    {
        _repositoryMock = new Mock<IPostRepository>();
        _emailSenderMock = new Mock<IEmailSender>();
        _sut = new PostService(_repositoryMock.Object, _emailSenderMock.Object);
    }

    [Fact]
    public async Task CreateAsync_WhenPostIsValid_SavesAndNotifiesEditors()
    {
        // Arrange
        var command = new CreatePostCommand("Título", "Contenido", authorId: Guid.NewGuid());

        _repositoryMock
            .Setup(r => r.AddAsync(It.IsAny<Post>(), It.IsAny<CancellationToken>()))
            .Returns(Task.CompletedTask);

        _emailSenderMock
            .Setup(e => e.SendToEditorsAsync(It.IsAny<string>(), It.IsAny<CancellationToken>()))
            .Returns(Task.CompletedTask);

        // Act
        var result = await _sut.CreateAsync(command, CancellationToken.None);

        // Assert
        result.Should().NotBeNull();
        result.Title.Should().Be("Título");

        _repositoryMock.Verify(
            r => r.AddAsync(It.Is<Post>(p => p.Title == "Título"), It.IsAny<CancellationToken>()),
            Times.Once);

        _emailSenderMock.Verify(
            e => e.SendToEditorsAsync("Nuevo post pendiente de revisión", It.IsAny<CancellationToken>()),
            Times.Once);
    }

    [Theory]
    [InlineData(null)]
    [InlineData("")]
    [InlineData("   ")]
    public async Task CreateAsync_WhenTitleIsInvalid_ThrowsValidationException(string? invalidTitle)
    {
        // Arrange
        var command = new CreatePostCommand(invalidTitle!, "Contenido", Guid.NewGuid());

        // Act
        Func<Task> act = () => _sut.CreateAsync(command, CancellationToken.None);

        // Assert
        await act.Should().ThrowAsync<ValidationException>();

        _repositoryMock.Verify(
            r => r.AddAsync(It.IsAny<Post>(), It.IsAny<CancellationToken>()),
            Times.Never);
    }
}

Observa que:

  • El servicio bajo test se guarda en _sut (System Under Test).
  • Los mocks se crean en el constructor para reutilizarlos en todos los tests de la clase.
  • Usamos It.IsAny<T>() cuando el valor exacto no importa y It.Is<T>(...) cuando queremos comprobar una condición.
  • Con Verify nos aseguramos de que los colaboradores recibieron las llamadas esperadas.

5 · Buenas prácticas

  • AAA: organiza cada test en Arrange, Act y Assert.
  • Nombres descriptivos: usa Method_Scenario_ExpectedResult.
  • Un concepto por test: no mezcles la validación de éxito con la de errores en el mismo método.
  • No lógica en tests: evita if, bucles y cálculos complejos dentro de los tests. Si necesitas variaciones, usa [Theory].
  • Preferir FluentAssertions sobre Assert clásico: los mensajes de error son más claros y la sintaxis se lee mejor.
  • Mocks para dependencias externas: base de datos, servicios de correo, APIs de terceros, reloj.
  • Evita sobre-especificar: usa It.IsAny cuando un argumento no es relevante para el comportamiento que validas.
  • Limpia estado entre tests: si un mock guarda estado, recréalo en el constructor o usa IClassFixture con cuidado.
Cuidado con Strict: MockBehavior.Strict es útil para detectar llamadas inesperadas, pero hace los tests frágiles. Úsalo solo cuando realmente importe cada interacción.

6 · Errores habituales

6.1 Aserciones sin contexto

// ❌ Mal: si falla, no sabemos qué valor tenía
Assert.True(result == expected);
// ✅ Bien: mensaje descriptivo automático
result.Should().Be(expected);

6.2 No esperar tareas asíncronas

// ❌ Mal: puede provocar deadlocks o resultados inconsistentes
var result = _sut.CreateAsync(command).Result;
// ✅ Bien: test asíncrono
var result = await _sut.CreateAsync(command);

6.3 Compartir estado mutable entre tests

// ❌ Mal: _counter se acumula entre tests
private int _counter = 0;
// ✅ Bien: inicializar en el constructor
public MyTests() { _counter = 0; }

6.4 Verificar llamadas irrelevantes

// ❌ Mal: rompe el test si añadimos logging
_loggerMock.Verify(l => l.LogInformation("Iniciando"), Times.Once);
// ✅ Bien: verifica solo interacciones que afectan al comportamiento
_repositoryMock.Verify(r => r.AddAsync(...), Times.Once);

7 · Ejercicio guiado

Vamos a testear un pequeño servicio de descuentos.

Paso 1: crea el servicio

namespace Tienda;

public class DiscountService
{
    public decimal ApplyDiscount(decimal amount, string customerType)
    {
        if (amount < 0) throw new ArgumentException("El importe no puede ser negativo", nameof(amount));

        var discount = customerType switch
        {
            "VIP" => 0.20m,
            "PREMIUM" => 0.10m,
            _ => 0.00m
        };

        return amount * (1 - discount);
    }
}

Paso 2: añade tests

using FluentAssertions;
using Xunit;

namespace Tienda.Tests;

public class DiscountServiceTests
{
    private readonly DiscountService _sut = new();

    [Theory]
    [InlineData(100, "VIP", 80)]
    [InlineData(100, "PREMIUM", 90)]
    [InlineData(100, "REGULAR", 100)]
    public void ApplyDiscount_WithKnownCustomerType_ReturnsExpectedAmount(
        decimal amount, string type, decimal expected)
    {
        var result = _sut.ApplyDiscount(amount, type);
        result.Should().Be(expected);
    }

    [Fact]
    public void ApplyDiscount_WhenAmountIsNegative_ThrowsArgumentException()
    {
        Action act = () => _sut.ApplyDiscount(-10, "VIP");
        act.Should().Throw<ArgumentException>().WithParameterName("amount");
    }
}

Paso 3: ejecuta

dotnet test Tienda.Tests

Intenta añadir un caso para un customerType en mayúsculas y minúsculas mezcladas. ¿Qué debería pasar? Refactoriza el servicio para que ignore mayúsculas y vuelve a ejecutar los tests.

9 · Resumen

  • xUnit usa [Fact] para tests fijos y [Theory] para tests parametrizados.
  • [InlineData], [MemberData] y [ClassData] permiten reutilizar la lógica del test con distintos datos.
  • Moq simula dependencias con Mock<T>, Setup y Verify.
  • FluentAssertions hace las aserciones legibles y los errores comprensibles.
  • Organiza los tests con AAA y nombra con Method_Scenario_ExpectedResult.

10 · Preguntas frecuentes

¿Por qué xUnit y no NUnit o MSTest?

xUnit es más moderno, no obliga a heredar de una clase base y ejecuta tests de distintas clases en paralelo por defecto. Microsoft lo usa en ASP.NET Core y Entity Framework Core.

¿Cuándo uso [Fact] y cuándo [Theory]?

Usa [Fact] cuando el test no tiene variaciones de entrada. Usa [Theory] cuando quieres validar una regla con varios valores. Si empiezas a copiar y pegar el mismo test, es señal de que necesitas una Theory.

¿Moq o NSubstitute?

Ambos son excelentes. Moq es históricamente el más usado en proyectos .NET y tiene una sintaxis muy madura. NSubstitute es algo más legible. Elige uno y sé consistente en todo el proyecto.

¿Debo mockear DTOs o entidades de dominio?

No. Los DTOs, entidades y value objects son datos planos; créalos con new. Mock solo colaboradores con comportamiento (servicios, repositorios, adaptadores).

¿Cómo testeo métodos privados?

No los testees directamente. Si un método privado es complejo, probablemente seaconvierta en una clase interna con su propia interfaz. Los tests deben validar el comportamiento público.

¿Puedo usar async void en tests?

No. Usa siempre async Task; de lo contrario xUnit no podrá esperar la finalización y podrías perder excepciones.
