Code Coverage con Coverlet

Módulo 12 · Testing25 min

1 · Introducción

Escribir tests es necesario, pero no basta. Necesitamos saber qué partes del código están siendo ejecutadas por los tests. A eso se le llama code coverage o cobertura de código.

En .NET 8, el ecosistema más común es Coverlet para recoger la cobertura y ReportGenerator para generar un informe HTML legible. dotnet-coverage también es una alternativa oficial de Microsoft.

¿Qué mide Coverlet? Coverlet mide qué líneas y ramas (branches) del código fueron ejecutadas por los tests. No mide si los tests son correctos, solo si recorren el código.

Al terminar esta lección sabrás ejecutar Coverlet, generar un informe HTML y interpretar la métricas sin caer en la trampa del 100%.

2 · Teoría

2.1 ¿Qué es la cobertura?

La cobertura indica el porcentaje de código que los tests ejecutan. Se mide en varias dimensiones:

  • Line coverage: porcentaje de líneas ejecutadas. Es la métrica más intuitiva.
  • Branch coverage: porcentaje de ramas de decisión (if, switch, ?:) recorridas. Más estricta y útil.
  • Method coverage: porcentaje de métodos invocados.

2.2 Coverlet

Coverlet funciona como un data collector de dotnet test. Se añade como paquete NuGet al proyecto de tests y no requiere instrumentación manual. Funciona con xUnit, NUnit y MSTest.

2.3 ReportGenerator

ReportGenerator convierte los archivos XML generados por Coverlet (formatos Cobertura, OpenCover, etc.) en un sitio HTML con gráficos, líneas resaltadas y resumen por proyecto.

2.4 Cobertura en CI

En pipelines de integración continua podemos:

  • Generar cobertura en cada pull request.
  • Subir el informe a Azure DevOps, SonarCloud, Codecov o GitHub Actions artifacts.
  • Bloquear merges si la cobertura cae por debajo de un umbral.

2.5 La trampa del 100%

Un proyecto con 100% de cobertura no está libre de bugs. Puedes ejecutar código sin validar resultados, o escribir tests que no comprueben el comportamiento real. La cobertura es una herramienta, no un objetivo. Prioriza tests que documenten y validen comportamiento, no tests que solo recorran líneas.

3 · Ejemplo mínimo

Crea una librería y un proyecto de tests:

dotnet new classlib -n Calculator -o CoverageMini/src/Calculator
dotnet new xunit -n Calculator.Tests -o CoverageMini/tests/Calculator.Tests
dotnet add CoverageMini/tests/Calculator.Tests reference CoverageMini/src/Calculator

# Paquete de cobertura
dotnet add CoverageMini/tests/Calculator.Tests package coverlet.collector

Calculadora:

namespace Calculator;

public class BasicCalculator
{
    public int Add(int a, int b) => a + b;
    public int Max(int a, int b) => a > b ? a : b;
}

Tests (solo uno de los dos métodos):

using FluentAssertions;
using Xunit;

namespace Calculator.Tests;

public class BasicCalculatorTests
{
    private readonly BasicCalculator _sut = new();

    [Fact]
    public void Add_TwoNumbers_ReturnsSum()
    {
        _sut.Add(2, 3).Should().Be(5);
    }
}

Ejecuta con cobertura:

dotnet test CoverageMini/tests/Calculator.Tests \
  --collect:"XPlat Code Coverage" \
  --results-directory ./coverage-results

Coverlet generará un archivo XML con un GUID en coverage-results. Si solo testeamos Add, la cobertura de Max será cero.

3.1 Generar informe HTML

# Instalar reportgenerator como tool global
# --version no es obligatoria, pero fija la versión
dotnet tool install -g dotnet-reportgenerator-globaltool --version 5.2.0

# Generar informe HTML
reportgenerator \
  -reports:"coverage-results/**/*.cobertura.xml" \
  -targetdir:"coverage-report" \
  -reporttypes:"Html"

Abre coverage-report/index.html en el navegador. Verás líneas cubiertas en verde y no cubiertas en rojo.

Tip: para ejecutar reportgenerator global sin instalarlo, usa dotnet reportgenerator tras instalarlo como tool local.

4 · Ejemplo real

En el CMS, queremos excluir del informe el código que no aporta valor de negocio: atributos, DTOs anémicos, clases de configuración de EF, etc. Coverlet permite excluir con filtros o atributos.

Supongamos un servicio PostService y un validador PostValidator. Añadimos al proyecto de tests el colector:

<PackageReference Include="coverlet.collector" Version="6.0.0">
  <PrivateAssets>all</PrivateAssets>
  <IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>
</PackageReference>

Corrida con filtros:

dotnet test Cms/tests/Cms.Tests \
  --collect:"XPlat Code Coverage" \
  --results-directory ./coverage-results \
  -- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.Exclude="[Cms.Infrastructure.Migrations.*]*" \
  -- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.Format="cobertura" \
  -- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.Threshold="60" \
  -- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.ThresholdType="line"

En el .csproj también puedes configurar cobertura:

<PropertyGroup>
  <!-- Cobertura mínima que falla el build si no se alcanza -->
  <CoverletThreshold>70</CoverletThreshold>
  <CoverletThresholdType>line</CoverletThresholdType>
</PropertyGroup>

Para excluir código de cobertura, añade el atributo ExcludeFromCodeCoverage:

using System.Diagnostics.CodeAnalysis;

namespace Cms.Infrastructure;

[ExcludeFromCodeCoverage]
public class MigrationMarker { }

Mejor aún: configura el atributo de forma centralizada en programas de arranque, configuraciones de Swagger o configuración de DI.

5 · Buenas prácticas

  • Automatiza en CI: ejecuta cobertura en cada pull request y publica el informe.
  • Usa umbral mínimo con sentido: un 70% de line coverage y un 60% de branch coverage suele ser un buen punto de partida.
  • Excluye código no testeable: migraciones, modelos de EF puros, programas de arranque, proxies generados.
  • Revisa los archivos con cobertura baja: no solo el porcentaje global. Identifica clases críticas de negocio.
  • Combina métricas: line coverage + branch coverage + mutation testing (Stryker) para una imagen más real.
  • El informe es una conversación: no uses la cobertura para castigar; úsala para encontrar zonas poco protegidas.
  • No perseguir el 100%: puede generar tests triviales que no aportan seguridad y encarecen el mantenimiento.
Atención: un alto porcentaje de cobertura sin aserciones significativas es engañoso. Un test que llama a un método pero no verifica nada aumenta la cobertura sin aportar valor.

6 · Errores habituales

6.1 Usar cobertura como métrica de calidad

# ❌ Mal: exigir 100% sin contexto
-- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.Threshold=100
# ✅ Bien: umbral realista y por componente
-- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.Threshold=70

6.2 Generar tests triviales solo para subir cobertura

// ❌ Mal: test que no valida nada
[Fact]
public void Max_Runs()
{
    _sut.Max(1, 2); // sin aserción
}
// ✅ Bien: test que valida el comportamiento
[Fact]
public void Max_WhenFirstIsGreater_ReturnsFirst()
{
    _sut.Max(5, 2).Should().Be(5);
}

6.3 No filtrar archivos irrelevantes

# ❌ Mal: el informe incluye migrations y DTOs
reportgenerator -reports:"**/*.cobertura.xml" -targetdir:coverage-report
# ✅ Bien: excluir assemblies de infraestructura
reportgenerator \
  -reports:"coverage-results/**/*.cobertura.xml" \
  -targetdir:"coverage-report" \
  -assemblyfilters:"+Cms.Domain;+Cms.Application" \
  -reporttypes:"Html;Badges"

6.4 No archivar el informe en CI

# ❌ Mal: generar sin publicar artifact
- run: dotnet test --collect:"XPlat Code Coverage"
# ✅ Bien: subir el informe HTML como artifact
- run: dotnet test --collect:"XPlat Code Coverage" --results-directory coverage-results
- run: reportgenerator -reports:"coverage-results/**/*.cobertura.xml" -targetdir:coverage-report
- uses: actions/upload-artifact@v4
  with:
    name: coverage-report
    path: coverage-report

7 · Ejercicio guiado

Vamos a medir cobertura de la calculadora del ejemplo mínimo.

Paso 1: añade más tests

[Fact]
public void Max_WhenFirstIsGreater_ReturnsFirst()
{
    _sut.Max(5, 2).Should().Be(5);
}

[Fact]
public void Max_WhenSecondIsGreater_ReturnsSecond()
{
    _sut.Max(2, 5).Should().Be(5);
}

Paso 2: ejecuta cobertura

dotnet test CoverageMini/tests/Calculator.Tests \
  --collect:"XPlat Code Coverage" \
  --results-directory ./coverage-results

reportgenerator -reports:"coverage-results/**/*.cobertura.xml" -targetdir:"coverage-report" -reporttypes:"Html"

Paso 3: analiza

Abre el informe. Ahora deberías ver 100% de líneas y ramas. ¿Qué sucede si falta el test de Max con el segundo mayor? El branch coverage bajará porque no se recorre la rama del operador ternario.

8 · Reto

Configura el pipeline de CI del CMS para:

  • Instalar reportgenerator como tool local.
  • Generar cobertura con Coverlet.
  • Excluir el proyecto Cms.Infrastructure menos Cms.Infrastructure.Services.
  • Subir el informe HTML como artifact.
  • Establecer un umbral de 65% de branch coverage y hacer que el build falle si se baja.

No resuelvas el reto ahora. Inténtalo en tu repositorio y lo revisaremos.

9 · Resumen

  • Coverlet recoge cobertura de código durante dotnet test como data collector.
  • ReportGenerator convierte los XML en un informe HTML interactivo.
  • Line coverage mide líneas ejecutadas; branch coverage mide decisiones recorridas.
  • Excluye código no testeable con atributos o filtros.
  • La cobertura es una guía, no un objetivo absoluto. No persigas el 100% a cualquier precio.

10 · Preguntas frecuentes

¿Coverlet es el único collector?

No. Microsoft proporciona dotnet-coverage y herramientas como Visual Studio Enterprise incluyen IntelliTrace. Coverlet es la opción más popular en el ecosistema open source.

¿Puedo ver cobertura en Visual Studio Code?

Con la extensión de C# Dev Kit puedes ver cobertura de tests. También puedes abrir el informe HTML generado por ReportGenerator.

¿Por qué branch coverage es más estricta que line coverage?

Porque una sola línea con un if puede contener dos ramas. Line coverage puede marcar la línea como ejecutada si solo entra por una rama, mientras que branch coverage exige recorrer ambas.

¿Qué es mutation testing?

Es una técnica que introduce pequeños cambios (mutaciones) en el código y comprueba si los tests detectan la alteración. Stryker.NET es el tool más conocido en .NET.

¿Cómo excluyo un método concreto?

Con [System.Diagnostics.CodeAnalysis.ExcludeFromCodeCoverage] sobre el método, clase o ensamblado. En CI, también puedes usar filtros de Coverlet con expresiones como [AssemblyName.*]TypeName.
