Nullable: tipos que pueden ser null

Módulo 1 · Fundamentos de C# 35 minutos

1 · Introducción

null significa "no hay valor", y es la fuente del error más famoso de la programación: la NullReferenceException. C# distingue dos escenarios y te da herramientas para manejarlo de forma segura.

  • Nullable value types (int?): permiten que un tipo de valor sea "sin valor".
  • Nullable reference types (string?): avisos del compilador para no usar referencias nulas por error.
Objetivo

Distinguir ambos conceptos y usar ??, ??=, ?. y ! correctamente.

2 · Teoría

Nullable value types: int?

Un int siempre vale un número. Un int? puede valer un número o null. Es la abreviatura de Nullable<int>:

int? edad = null;          // sin valor
edad = 30;                 // con valor

int? a = 5;
int? b = null;

bool tieneValor = a.HasValue;   // true
int valor = a.Value;            // 5 (¡falla si es null!)

Propiedades útiles de Nullable<T>: HasValue (¿tiene valor?) y Value (el valor).

Nullable reference types: string?

Desde C# 8, con <Nullable>enable</Nullable> activado, el compilador distingue:

string nombre = "Ana";     // NO puede ser null (aviso si lo intentas)
string? apodo = null;      // SÍ puede ser null

// El compilador te avisa si usas una referencia anulable sin comprobar
// int longitud = apodo.Length;   // warning: puede ser null
¿Qué cambia en runtime?

Nada. string y string? compilan al mismo tipo. La diferencia es solo información para el compilador: te avisa (warnings) antes de que una referencia nula explote en producción.

El operador de perdón nulo (!)

string? posibleNulo = ObtenerNombre();

// Si TÚ sabes que no es null, se lo dices al compilador con !
string seguro = posibleNulo!;
Console.WriteLine(seguro.Length);
Usa ! con cuidado

! no comprueba nada: solo silencia el aviso. Si te equivocas, tendrás un NullReferenceException igualmente.

Los operadores de null (repaso aplicado)

string? nombre = null;

// ?.  : acceso seguro (devuelve null en vez de explotar)
int? longitud = nombre?.Length;     // null

// ??  : valor por defecto si es null
string final = nombre ?? "Anónimo"; // "Anónimo"

// ??= : asignar solo si es null
nombre ??= "Por defecto";           // nombre = "Por defecto"

#nullable

Puedes controlar el análisis de nullabilidad por archivo con la directiva #nullable:

#nullable enable   // activa avisos a partir de aquí
string? x = null;
#nullable disable  // desactiva avisos
string y = null;   // sin aviso

En proyectos modernos .NET 8, <Nullable>enable</Nullable> ya está activo por defecto.

3 · Ejemplo mínimo

string? nombre = null;

Console.WriteLine(nombre?.Length ?? 0);   // 0 (sin excepción)

4 · Ejemplo real

Leer datos de un formulario donde el campo "apellido" es opcional:

string? apellido = ObtenerApellido();   // puede ser null

// Forma segura de obtener longitud o 0
int longitud = apellido?.Length ?? 0;

// Forma segura de mostrar
Console.WriteLine($"Apellido: {apellido ?? "No indicado"}");

static string? ObtenerApellido() => null;

6 · Errores habituales

Error 1: acceder a .Value sin comprobar HasValue

int? x = null;
// Console.WriteLine(x.Value);   // InvalidOperationException

// Correcto
if (x.HasValue) Console.WriteLine(x.Value);

Error 2: abusar del operador !

string? nombre = null;
// nombre!.Length   // compila, pero explota en runtime
// Mejor: nombre?.Length ?? 0

Error 3: creer que string? es un tipo distinto en runtime

// string y string? son el mismo tipo; solo cambia el análisis del compilador

9 · Resumen

  • int? / Nullable<T>: tipo de valor que puede ser null (HasValue/Value).
  • string?: referencia anulable, analizada por el compilador.
  • Operadores: ?. (acceso seguro), ?? (default), ??= (asignar si null), ! (perdón nulo).

10 · Preguntas frecuentes

¿Cuál es la diferencia entre int? y string??

int? es un tipo de valor envuelto (cambia el tipo real a Nullable<int>). string? es solo una anotación: el tipo en runtime es el mismo string.

¿Por qué se llama "operador de perdón nulo"?

Porque con ! "perdonas" al compilador por avisarte y le aseguras que el valor no es null, aunque él no pueda verificarlo.

¿El compilador puede garantizar que no hay nulls?

No al 100% (datos externos siempre pueden ser null), pero el análisis de flujo reduce enormemente la probabilidad de NullReferenceException.
