Memoria y el Garbage Collector

Módulo 1 · Fundamentos de C# 45 minutos

1 · Introducción

Entender cómo .NET organiza la memoria y cómo el Garbage Collector (GC) la libera automáticamente es lo que te separa de "escribir código que funciona" a "escribir código que entiende lo que hace". Aquí cerramos el círculo de la distinción entre value types y reference types que vimos al principio.

Objetivo

Distinguir stack/heap, entender el GC y sus generaciones, y gestionar recursos con IDisposable/using.

2 · Teoría

Stack y Heap

STACK (rápido, pequeño) HEAP (grande, gestionado por el GC) ┌──────────────────────┐ ┌─────────────────────────┐ │ int x = 5 │ │ objeto (class) │ │ (value type, se copia)│ │ (reference type) │ └──────────────────────┘ └─────────────────────────┘ ▲ ▲ │ │ variables locales y structs objetos, arrays, strings
  • Stack: zona de memoria rápida, organizada como pila (LIFO). Aquí viven los value types (variables locales, structs). Se limpia automáticamente al salir del método.
  • Heap: zona más grande y flexible. Aquí viven los reference types (objetos, arrays, strings). No se limpia sola: lo hace el GC.

Referencias y copias

// Value type: se copia el valor
int a = 10;
int b = a;
b = 20;
Console.WriteLine(a);   // 10 (a no cambia)

// Reference type: se comparte la referencia
var lista1 = new List<int> { 1, 2, 3 };
var lista2 = lista1;      // misma referencia
lista2.Add(4);
Console.WriteLine(lista1.Count);   // 4 (¡cambió por la referencia compartida!)

Boxing y unboxing

Cuando metes un value type en un contexto de object, se encajona (boxing): se copia al heap. Sacarlo de vuelta es unboxing:

int numero = 42;
object caja = numero;      // BOXING: int → object (va al heap)

int recuperado = (int)caja; // UNBOXING: object → int (cast explícito)
El coste

El boxing asigna memoria en el heap y presiona al GC. Las colecciones genéricas (List<int>) existen precisamente para evitarlo (frente al viejo ArrayList que boxea todo).

El Garbage Collector

El GC es el componente del CLR que libera memoria automáticamente: detecta objetos en el heap que ya no son alcanzables desde ninguna referencia y los elimina. No tienes que llamar a delete ni a free (a diferencia de C/C++).

Generaciones

El GC agrupa los objetos por "antigüedad" para no escanear todo el heap en cada limpieza:

GeneraciónQué contieneRecolección
Gen 0Objetos nuevos y de vida cortaMuy frecuente y barata
Gen 1Objetos que sobrevivieron a Gen 0Menos frecuente
Gen 2Objetos longevosRara y costosa
LOHObjetos muy grandes (Large Object Heap, >85 KB)Aparte

Idea clave: los objetos de vida corta (la mayoría) se recogen rápido y barato en Gen 0. Por eso, crear muchos objetos temporales no es tan grave como parece, pero evitarlo ayuda.

Gestión de recursos: IDisposable

El GC gestiona memoria, pero no recursos externos: archivos, conexiones de red, bases de datos. Para esos recursos, la clase implementa IDisposable y libera explícitamente con Dispose().

using statement y using declaration

// using statement (clásico): libera al final del bloque
using (var reader = new StreamReader("archivo.txt"))
{
    string contenido = reader.ReadToEnd();
}   // Dispose() se llama aquí automáticamente

// using declaration (C# 8+): libera al final del ámbito
using var writer = new StreamWriter("salida.txt");
writer.WriteLine("Hola");
// Dispose() se llama al salir del método
using = liberar a tiempo

using garantiza que Dispose() se ejecute incluso si hay una excepción. Es la forma correcta de manejar cualquier recurso desechable.

IAsyncDisposable

Para recursos cuya liberación es asíncrona (verás asincronía en la próxima lección), existe IAsyncDisposable:

await using (var recurso = new RecursoAsync())
{
    // ...
}   // llama a DisposeAsync() al terminar

3 · Ejemplo mínimo

// Boxing
int numero = 42;
object caja = numero;        // boxing
int recuperado = (int)caja;  // unboxing

Console.WriteLine(recuperado);   // 42

4 · Ejemplo real

Un recurso que implementa IDisposable y se usa con using, simulando una conexión:

class Conexion : IDisposable
{
    public void Conectar() => Console.WriteLine("Conectado");
    public void Dispose() => Console.WriteLine("Conexión cerrada (recursos liberados)");
}

using (var conexion = new Conexion())
{
    conexion.Conectar();
}
// Al salir: "Conectado" y luego "Conexión cerrada"

6 · Errores habituales

Error 1: olvidar Dispose

// Incorrecto: el archivo queda abierto/bloqueado
// var reader = new StreamReader("x.txt");

// Correcto
using var reader = new StreamReader("x.txt");

Error 2: llamar GC.Collect() manualmente

// Incorrecto: casi nunca necesario, perjudica el rendimiento
// GC.Collect();

Error 3: creer que value types viven SIEMPRE en el stack

// Un int dentro de una clase vive en el heap (inline en el objeto).
// Un struct local vive en el stack. El "dónde" depende del contexto.

9 · Resumen

  • Stack (value types, rápido) vs Heap (reference types, GC).
  • Boxing/unboxing: value type ↔ object, con coste en el heap.
  • El GC libera memoria automáticamente, en generaciones (Gen 0/1/2) + LOH.
  • IDisposable + using para recursos externos; IAsyncDisposable para la versión asíncrona.

10 · Preguntas frecuentes

¿Puedo forzar al GC?

Técnicamente sí con GC.Collect(), pero casi nunca es buena idea: el GC ya sabe cuándo recolectar. Forzarlo suele reducir el rendimiento.

¿Qué es un "memory leak" en .NET?

Aunque el GC evita la mayoría, puede haber fugas si mantienes referencias a objetos que ya no necesitas, o si olvidas liberar recursos no gestionados (sin Dispose).

¿Un struct puede estar en el heap?

Sí. Si es un campo de una clase, se almacena inline dentro del objeto en el heap. La regla "struct = stack" es una simplificación didáctica.
