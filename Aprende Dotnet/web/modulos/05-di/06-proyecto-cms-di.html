Proyecto CMS: registro de servicios con DI

Módulo 5 · Inyección de Dependencias45 min

1 · Introducción

En esta lección aplicamos todo lo aprendido sobre Inyección de Dependencias al proyecto práctico del curso: un CMS headless que venimos construyendo poco a poco.

  • Qué vamos a aprender: cómo registrar repositorios, servicios de aplicación, validadores y utilidades del CMS usando extensiones de IServiceCollection, eligiendo lifetimes correctos y evitando Captive Dependencies.
  • Problema que resuelve: centralizar la composición de la aplicación para que la capa de API no conozca los detalles de implementación de infraestructura.
  • Cuándo se utiliza: en cualquier aplicación profesional que separe Domain, Application, Infrastructure y Api.
Errores típicos: registrar todo en Program.cs, mezclar lifetimes incorrectamente, exponer DbContext a capas superiores, o usar new para crear servicios en lugar de dejar que el contenedor los componga.

2 · Teoría

2.1. Arquitectura del CMS

Hasta ahora el CMS tiene la siguiente estructura:

  • Cms.Domain: entidades, value objects, interfaces de repositorio.
  • Cms.Application: servicios de aplicación, comandos, queries, DTOs.
  • Cms.Infrastructure: implementaciones de repositorios con EF Core, caching, email.
  • Cms.Api: endpoints ASP.NET Core Minimal API.
Capas del CMS y flujo de dependencias:

        ┌─────────────┐
        │   Cms.Api   │  ← Solo conoce Application
        └──────┬──────┘
               │ IServiceCollection
               ▼
        ┌─────────────┐
        │ Cms.Application│  ← Define abstracciones (interfaces de repositorio)
        └──────┬──────┘
               │
               ▼
        ┌─────────────┐
        │Cms.Infrastructure│  ← Implementa las abstracciones
        └──────┬──────┘
               │
               ▼
        ┌─────────────┐
        │  Cms.Domain │  ← No depende de nadie
        └─────────────┘

Regla: las flechas de dependencia apuntan hacia Domain.

2.2. Responsabilidad de registrar servicios

Cada capa debe exponer un método de extensión para registrar sus propios servicios. Así Program.cs permanece limpio y las capas inferiores no son referenciadas directamente desde la API.

2.3. Lifetimes del CMS

ServicioLifetimeMotivo
IPostRepository, ICategoryRepositoryScopedComparten DbContext dentro del request
IPostService, ICategoryServiceScopedUsan repositorios Scoped
CmsDbContextScopedLifetime de EF Core por defecto
IPostCacheSingletonCache en memoria compartida
IEmailServiceTransientSin estado, fácil de reciclar
FluentValidation validatorsSingletonReglas inmutables, recomendado por FluentValidation

2.4. Extensiones de IServiceCollection

En lugar de llenar Program.cs, cada proyecto expone un método AddXxx(this IServiceCollection services, IConfiguration configuration). Esto mejora la organización y permite testar el registro de servicios.

3 · Ejemplo mínimo

La API solo llama a dos métodos de extensión: uno de Application y otro de Infrastructure.

// Cms.Api/Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddCmsApplication()
    .AddCmsInfrastructure(builder.Configuration);

var app = builder.Build();

app.MapControllers();
app.Run();
// Cms.Application/DependencyInjection.cs
public static class DependencyInjection
{
    public static IServiceCollection AddCmsApplication(this IServiceCollection services)
    {
        services.AddScoped<IPostService, PostService>();
        services.AddScoped<ICategoryService, CategoryService>();

        services.AddValidatorsFromAssemblyContaining<CreatePostRequestValidator>();

        return services;
    }
}
// Cms.Infrastructure/DependencyInjection.cs
public static class DependencyInjection
{
    public static IServiceCollection AddCmsInfrastructure(
        this IServiceCollection services,
        IConfiguration configuration)
    {
        services.AddDbContext<CmsDbContext>(options =>
            options.UseNpgsql(configuration.GetConnectionString("Default")!));

        services.AddScoped<IPostRepository, EfPostRepository>();
        services.AddScoped<ICategoryRepository, EfCategoryRepository>();

        services.AddSingleton<IPostCache, PostCache>();
        services.AddTransient<IEmailService, EmailService>();

        return services;
    }
}
Resultado: la API no referencia Cms.Infrastructure directamente; solo conoce Cms.Application. La composición se delega a los métodos de extensión.

4 · Ejemplo real

En un CMS real necesitamos más servicios: notificaciones, búsqueda, cache distribuida, logging estructurado y options. Añadimos todo manteniendo la separación de capas.

// Cms.Infrastructure/DependencyInjection.cs
public static class DependencyInjection
{
    public static IServiceCollection AddCmsInfrastructure(
        this IServiceCollection services,
        IConfiguration configuration)
    {
        // 1. Options pattern para configuración tipada
        services.AddOptions<CmsOptions>()
            .Bind(configuration.GetSection(CmsOptions.SectionName))
            .ValidateDataAnnotations()
            .ValidateOnStart();

        // 2. Entity Framework Core
        services.AddDbContext<CmsDbContext>((provider, options) =>
        {
            var cmsOptions = provider.GetRequiredService<IOptions<CmsOptions>>().Value;
            options.UseNpgsql(cmsOptions.ConnectionString);
        });

        // 3. Repositorios: Scoped, comparten DbContext
        services.AddScoped<IPostRepository, EfPostRepository>();
        services.AddScoped<ICategoryRepository, EfCategoryRepository>();
        services.AddScoped<ITagRepository, EfTagRepository>();
        services.AddScoped<IUserRepository, EfUserRepository>();

        // 4. Open generic: cualquier IRepository no registrado explícitamente
        // (solo si queremos un fallback; los repositorios específicos se registran arriba)
        // services.AddScoped(typeof(IRepository<>), typeof(EfRepository<>));

        // 5. Servicios de infraestructura
        services.AddSingleton<IPostCache, PostCache>();
        services.AddSingleton<ISearchIndex, InMemorySearchIndex>();
        services.AddTransient<IEmailService, SmtpEmailService>();
        services.AddTransient<ISlugGenerator, SlugGenerator>();

        // 6. HttpClient con nombre para integraciones externas
        services.AddHttpClient("Analytics", client =>
        {
            client.BaseAddress = new Uri("https://analytics.example.com");
            client.Timeout = TimeSpan.FromSeconds(30);
        });

        // 7. Decorador de logging para repositorios (Scrutor)
        services.Decorate<IPostRepository, LoggingPostRepository>();
        services.Decorate<IPostRepository, CachingPostRepository>();

        return services;
    }
}

// Cms.Application/DependencyInjection.cs
public static class DependencyInjection
{
    public static IServiceCollection AddCmsApplication(this IServiceCollection services)
    {
        services.AddScoped<IPostService, PostService>();
        services.AddScoped<ICategoryService, CategoryService>();
        services.AddScoped<ITagService, TagService>();
        services.AddScoped<IUserService, UserService>();

        services.AddScoped<INotificationService, NotificationService>();

        // Validadores de FluentValidation (singleton, inmutables)
        services.AddValidatorsFromAssemblyContaining<CreatePostRequestValidator>();

        return services;
    }
}

// Cms.Api/Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddCmsApplication()
    .AddCmsInfrastructure(builder.Configuration);

builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

app.UseHttpsRedirection();
app.UseAuthorization();
app.MapControllers();

app.Run();
Nota: PostService depende de IPostRepository e IPostCache. Como el servicio es Scoped y la caché es Singleton, no hay Captive Dependency. Pero el decorador CachingPostRepository debe ser Scoped (Scrutor respeta el lifetime del servicio base).

6 · Errores habituales

Error 1: La API referencia Infrastructure directamente

// INCORRECTO: rompe Clean Architecture
using Cms.Infrastructure.Persistence;

builder.Services.AddDbContext<CmsDbContext>(...);
builder.Services.AddScoped<IPostRepository, EfPostRepository>();

// CORRECTO: delegar a la extensión de Infrastructure
builder.Services.AddCmsInfrastructure(builder.Configuration);

Error 2: Singleton que captura DbContext

// INCORRECTO: la caché captura el DbContext Scoped
public class PostCache(CmsDbContext dbContext) : IPostCache { ... }
services.AddSingleton<IPostCache, PostCache>();

// CORRECTO: Singleton usa IServiceScopeFactory para scopes cortos
public class PostCache(IServiceScopeFactory scopeFactory) : IPostCache
{
    public Post? Get(Guid id)
    {
        using var scope = scopeFactory.CreateScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<CmsDbContext>();
        return dbContext.Posts.Find(id);
    }
}

Error 3: Registrar validadores como Scoped

// INCORRECTO: los validadores no necesitan estado por request
services.AddScoped<IValidator<CreatePostRequest>, CreatePostRequestValidator>();

// CORRECTO: FluentValidation recomienda Singleton
services.AddValidatorsFromAssemblyContaining<CreatePostRequestValidator>();
// o manualmente:
services.AddSingleton<IValidator<CreatePostRequest>, CreatePostRequestValidator>();

Error 4: Llenar Program.cs de registros

// INCORRECTO: Program.cs crece sin control
builder.Services.AddDbContext<CmsDbContext>(...);
builder.Services.AddScoped<IPostRepository, EfPostRepository>();
builder.Services.AddScoped<ICategoryRepository, EfCategoryRepository>();
builder.Services.AddScoped<IPostService, PostService>();
builder.Services.AddSingleton<IPostCache, PostCache>();
// ... 30 registros más

// CORRECTO: agrupar en extensiones
builder.Services
    .AddCmsApplication()
    .AddCmsInfrastructure(builder.Configuration);

// Cms.Domain/Settings/CmsOptions.cs
public class CmsOptions
{
    public const string SectionName = "Cms";

    [Required]
    public string ConnectionString { get; set; } = string.Empty;

    [Range(1, 1440)]
    public int DefaultCacheExpirationMinutes { get; set; } = 5;

8 · Reto

Reto: Añade decorators y open generics al CMS

  • Instala Scrutor en Cms.Infrastructure.
  • Crea un decorador LoggingPostRepository que loguee cada operación.
  • Crea un decorador CachingPostRepository que use IPostCache.
  • Registra ambos decoradores en el orden correcto.
  • Define IRepository<T> como open generic y EfRepository<T> como implementación base para repositorios simples.
  • Asegúrate de que CachingPostRepository no capture CmsDbContext de forma incorrecta.

9 · Resumen

  • El proyecto CMS separa Domain, Application, Infrastructure y Api.
  • Cada capa expone un método de extensión de IServiceCollection para registrar sus servicios.
  • La API solo referencia Application y llama a AddCmsApplication e AddCmsInfrastructure.
  • Los repositorios y servicios de aplicación son Scoped; las cachés e índices son Singleton; utilidades sin estado son Transient.
  • Se usa Options Pattern para configuración tipada y validada.
  • Se evitan Captive Dependencies entre Singleton y Scoped.
  • Scrutor permite decorar repositorios con logging y cache sin modificar las implementaciones base.

10 · Preguntas frecuentes

¿Por qué la API no referencia Infrastructure?

Porque en Clean Architecture las dependencias apuntan hacia el centro (Domain). Si la API referenciara Infrastructure, rompería la regla de dependencia. La composición se realiza en runtime mediante DI, usando la extensión AddCmsInfrastructure sin referencia directa al proyecto (solo se añade la referencia en tiempo de compilación para poder usar la extensión, pero la API no depende de tipos concretos de Infrastructure).

¿Cómo se testea el registro de servicios?

Puedes crear un test de integración que construya el ServiceProvider y resuelva cada servicio público. También puedes activar ValidateScopes y ValidateOnBuild para detectar Captive Dependencies.

¿Puedo usar MediatR en este módulo?

MediatR se verá en el módulo de Arquitectura y CQRS, pero si ya lo conoces puedes registrar los handlers en AddCmsApplication con services.AddMediatR(cfg => cfg.RegisterServicesFromAssemblyContaining<CreatePostCommand>()).

¿Por qué los validadores son Singleton?

Los validadores de FluentValidation no tienen estado y sus reglas no cambian entre requests. Registrarles como Singleton reduce la presión de GC. FluentValidation lo recomienda por defecto con AddValidatorsFromAssemblyContaining.

¿Qué pasa si CmsDbContext es Singleton?

Sería una Captive Dependency masiva. El DbContext mantiene estado de seguimiento y no es seguro para concurrencia. Si fuera Singleton, todos los requests compartirían el mismo contexto, provocando errores de concurrencia, datos incorrectos y posibles fugas de memoria.
