CI/CD con GitHub Actions

Módulo 16 · Docker y despliegue35 min

1 · Introducción

En esta lección aprenderemos a automatizar la integración y entrega continua de una aplicación .NET 8 con GitHub Actions. CI/CD es la práctica de ejecutar automáticamente tests, compilaciones y despliegues cada vez que se modifica el código.

El problema que resolvemos es la inconsistencia manual: un desarrollador compila en su máquina, otro en una máquina distinta, y en producción se olvida de ejecutar los tests. Una pipeline de CI/CD garantiza que cada cambio pase por los mismos pasos automatizados antes de llegar a producción.

Objetivo: crear un workflow de GitHub Actions que compile, testee, publique y empaquete una aplicación .NET 8 en una imagen Docker, usando secretos y artefactos de forma segura.

2 · Teoría

¿Qué es CI/CD?

CI/CD son las siglas de Continuous Integration / Continuous Deployment (integración continua / despliegue continuo).

  • Integración continua (CI): cada vez que se sube código a un pull request o a la rama principal, se ejecutan automáticamente compilación, tests y análisis estático.
  • Despliegue continuo (CD): tras pasar CI, el artefacto se publica o despliega automáticamente en un entorno.

¿Qué es GitHub Actions?

GitHub Actions es el servicio de automatización integrado en GitHub. Se configura con archivos YAML dentro de .github/workflows/. Un workflow se ejecuta en respuesta a eventos del repositorio como push, pull_request o release.

Conceptos clave:

  • Workflow: el archivo YAML completo.
  • Job: un grupo de pasos que se ejecutan en el mismo runner. Los jobs pueden ejecutarse en paralelo o en secuencia.
  • Step: una tarea dentro de un job. Puede ejecutar un comando o una action reutilizable.
  • Runner: la máquina virtual donde se ejecuta el workflow. GitHub ofrece ubuntu-latest, windows-latest y macos-latest.
  • Action: tarea reutilizable publicada en el marketplace de GitHub, como actions/checkout o actions/setup-dotnet.
  • Matrix: estrategia para ejecutar el mismo job con distintas combinaciones (por ejemplo, varias versiones de .NET o varios sistemas operativos).
  • Secrets: variables sensibles configuradas en el repositorio y accesibles en el workflow mediante ${{ secrets.NOMBRE }}.
  • Artifacts: archivos generados por el workflow que se pueden descargar después, como binarios publicados o informes de tests.

Seguridad en pipelines

Nunca escribas contraseñas, tokens o claves de API directamente en el YAML. Usa GitHub Secrets y referéncialos con ${{ secrets.NOMBRE }}. También evita imprimir secretos en logs; GitHub enmascara automáticamente los valores de secrets cuando aparecen en la salida.

3 · Ejemplo mínimo

Un workflow básico que compila y testea una solución en cada push.

# .github/workflows/ci.yml
name: .NET CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    steps:
      # Descarga el código del repositorio
      - uses: actions/checkout@v4

      # Configura el SDK de .NET 8
      - name: Setup .NET 8
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'

      # Restaura dependencias de NuGet
      - name: Restore
        run: dotnet restore

      # Compila la solución en Release
      - name: Build
        run: dotnet build --no-restore --configuration Release

      # Ejecuta todos los tests del repositorio
      - name: Test
        run: dotnet test --no-build --verbosity normal

Este archivo debe guardarse en .github/workflows/ci.yml. GitHub lo detectará automáticamente en el siguiente push.

Tip: --no-restore en build y --no-build en test aceleran el workflow porque reutilizan la compilación anterior.

4 · Ejemplo real

Workflow completo con estrategia de matriz, publicación de artefactos, build de imagen Docker, push a Docker Hub y escaneo de vulnerabilidades.

# .github/workflows/cms-ci-cd.yml
name: CMS CI/CD

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]
  release:
    types: [published]

env:
  # Variables de entorno del workflow
  DOTNET_VERSION: '8.0.x'
  IMAGE_NAME: ${{ secrets.DOCKER_USERNAME }}/cms-api
  REGISTRY: docker.io

jobs:
  # ─────────────────────────────────────────────────────────
  # Job 1: build y test
  # ─────────────────────────────────────────────────────────
  build-and-test:
    runs-on: ubuntu-latest

    # Ejecuta con varias versiones del SDK (matrix strategy)
    strategy:
      matrix:
        dotnet-version: ['8.0.x']

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup .NET ${{ matrix.dotnet-version }}
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ matrix.dotnet-version }}

      - name: Cache NuGet packages
        uses: actions/cache@v4
        with:
          path: ~/.nuget/packages
          key: ${{ runner.os }}-nuget-${{ hashFiles('**/*.csproj') }}
          restore-keys: |
            ${{ runner.os }}-nuget-

      - name: Restore
        run: dotnet restore proyecto-final/src/Cms.sln

      - name: Build
        run: dotnet build proyecto-final/src/Cms.sln --no-restore --configuration Release

      - name: Test
        run: dotnet test proyecto-final/src/Cms.sln --no-build --verbosity normal

      - name: Publish
        run: dotnet publish proyecto-final/src/Cms.Api/Cms.Api.csproj --no-build --configuration Release --output ./publish

      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: cms-api-publish
          path: ./publish
          retention-days: 5

  # ─────────────────────────────────────────────────────────
  # Job 2: build y push de imagen Docker
  # ─────────────────────────────────────────────────────────
  docker-build:
    needs: build-and-test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Docker meta
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=sha

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: ./proyecto-final
          file: ./proyecto-final/src/Cms.Api/Dockerfile
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Scan image
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ env.IMAGE_NAME }}:main
          format: 'sarif'
          output: 'trivy-results.sarif'

  # ─────────────────────────────────────────────────────────
  # Job 3: despliegue (placeholder para Railway, Azure, etc.)
  # ─────────────────────────────────────────────────────────
  deploy:
    needs: docker-build
    runs-on: ubuntu-latest
    environment: production
    if: github.event_name == 'release'

    steps:
      - name: Deploy placeholder
        run: echo "Aquí se conecta con Railway, Azure Container Apps o AWS ECS"

Explicación de las decisiones:

  • Matrix: aunque usamos una sola versión de .NET, la matriz permite ampliar fácilmente a múltiples versiones o sistemas operativos.
  • Cache de NuGet: actions/cache acelera el restore usando el hash de los archivos .csproj como clave.
  • Artefactos: upload-artifact guarda el resultado de publish para descargas o despliegues posteriores.
  • Buildx: habilita cache avanzado, multiplataforma y mejores optimizaciones de build.
  • metadata-action: genera etiquetas como main, 1.2.3 y sha-abc123 automáticamente.
  • cache-from/to type=gha: cachea capas de Docker entre ejecuciones del workflow usando el caché de GitHub Actions.
  • Trivy: escanea la imagen en busca de vulnerabilidades en paquetes de la imagen base.
  • environment: production: permite añadir protecciones de despliegue, como revisores o secrets de entorno.
Seguridad: los valores DOCKER_USERNAME y DOCKER_PASSWORD deben configurarse en Settings → Secrets and variables → Actions del repositorio. Nunca los escribas en el YAML.

5 · Buenas prácticas

  • Usa runners de Ubuntu para .NET. Son más rápidos, baratos y compatibles con Docker que Windows o macOS.
  • Cachea NuGet y capas de Docker. Reduce drásticamente el tiempo de ejecución.
  • Compila en Release y ejecuta todos los tests. CI/CD sin tests no es CI/CD.
  • Publica artefactos incluso si no los despliegas. Permiten debuggear fallos y despliegues manuales de emergencia.
  • Etiqueta imágenes con semántica. Usa versiones, SHA y rama, nunca latest en producción.
  • Escanea imágenes antes de desplegar. Detecta vulnerabilidades en la imagen base y dependencias del sistema.
  • Usa needs para que el build de Docker solo ocurra si los tests pasan.
  • Limita permisos del workflow. Añade permissions: contents: read para repositorios públicos y reduce la superficie de ataque.
  • Versiona las actions. Usa versiones mayor como @v4 en lugar de @master para evitar cambios inesperados.
  • Configura un entorno de producción con protección de ramas y revisores manuales antes de desplegar.

6 · Errores habituales

Error 1: ejecutar restore, build y test sin reutilizar

# ❌ MAL: compilaciones redundantes
- run: dotnet restore
- run: dotnet build
- run: dotnet test

Problema: cada comando compila de nuevo. Pierdes tiempo y puede introducir inconsistencias.

# ✅ BIEN: reutilizar la compilación
- run: dotnet restore
- run: dotnet build --no-restore
- run: dotnet test --no-build

Error 2: hardcodear secretos

# ❌ MAL: secretos en texto plano
- run: docker login -u miusuario -p miPassword123

Problema: los secretos quedan en el historial del repositorio y en los logs.

# ✅ BIEN: usar GitHub Secrets
- uses: docker/login-action@v3
  with:
    username: ${{ secrets.DOCKER_USERNAME }}
    password: ${{ secrets.DOCKER_PASSWORD }}

Error 3: no usar cache

Sin cache de NuGet y Docker, cada ejecución descarga todo de cero. Las pipelines lentas desincentivan su uso. Añade actions/cache y type=gha en el build de Docker.

Error 4: usar latest como etiqueta

# ❌ MAL: imagen imposible de rastrear
- run: docker build -t ${{ secrets.DOCKER_USERNAME }}/cms-api:latest .

Problema: latest cambia con cada build y dificulta rollbacks. Usa versiones, SHA o nombres de rama.

Error 5: desplegar sin pasar tests

# ❌ MAL: build y deploy en paralelo
jobs:
  build:
    runs-on: ubuntu-latest
  deploy:
    runs-on: ubuntu-latest

Problema: el despliegue puede ocurrir aunque los tests fallen. Usa needs: build.

7 · Ejercicio guiado

Crea un workflow de CI/CD para un proyecto .NET 8.

  1. Crea un repositorio en GitHub y sube el código de una API .NET 8.
  2. Crea la carpeta .github/workflows/ en la raíz del repositorio.
  3. Crea un archivo ci.yml con los pasos: checkout, setup .NET 8, restore, build, test.
  4. Activa el workflow haciendo un push a la rama main.
  5. Ve a la pestaña Actions del repositorio y verifica que la ejecución termine en verde.
  6. Añade un paso de dotnet publish y sube el artefacto con actions/upload-artifact@v4.
  7. (Opcional) Si tienes cuenta en Docker Hub, añade los secrets y un job de build y push de imagen.

8 · Reto

Añade al workflow un job de code coverage usando coverlet y reportgenerator. El workflow debe generar un informe HTML de cobertura, subirlo como artefacto y fallar si la cobertura global es menor al 70%. No lo resuelvas todavía; inténtalo primero.

9 · Resumen

  • GitHub Actions automatiza CI/CD con workflows definidos en YAML.
  • Un pipeline de .NET debe restaurar, compilar, testear y publicar antes de crear la imagen Docker.
  • Los secretos se gestionan con secrets.NOMBRE y nunca se escriben en el YAML.
  • Cachear NuGet y capas de Docker acelera enormemente las ejecuciones.
  • Las imágenes Docker deben etiquetarse con versión, SHA o rama, nunca con latest.
  • Escanea imágenes y protege el despliegue a producción con entornos y revisores.

10 · Preguntas frecuentes

¿Cuánto cuesta usar GitHub Actions?

GitHub ofrece minutos gratuitos para repositorios públicos y privados según el plan. Para repositorios públicos, los minutos de runners de Linux son gratuitos con ciertos límites. Si necesitas más, puedes usar runners auto-hospedados.

¿Puedo usar GitHub Actions sin Docker?

Sí. Puedes publicar directamente en Azure App Service, Azure Functions, AWS, Railway u otros servicios sin crear una imagen Docker. Docker aporta portabilidad y consistencia entre entornos.

¿Cómo evito que se ejecute el workflow en cada push?

Configura la sección on con filtros de rama, path o eventos. Por ejemplo: on: push: branches: [main] paths: ['src/**'] ejecuta solo si cambia código dentro de src/.

¿Qué es el cache de capas de Docker con type=gha?

Es una forma de cachear las capas intermedias de un build de Docker usando el almacenamiento de GitHub Actions. Acelera builds posteriores porque no reconstruye capas que no han cambiado.

¿Cómo protejo un despliegue a producción?

Define un environment: production en el job. Después, en el repositorio, configura reglas de protección que requieran revisores manuales, ramas permitidas o tiempo de espera antes de desplegar.

¿Debo ejecutar migraciones de EF Core en el workflow?

En CI no, solo en CD. En el job de despliegue puedes ejecutar dotnet ef database update contra la base de datos de producción, o bien usar un contenedor de inicialización. En CI/CD contra bases de datos reales, asegúrate de que la cadena de conexión esté protegida como secret.
