XSS, CSRF y cabeceras de seguridad

Módulo 18 · Seguridad en APIs (OWASP)30 min

1 · Introducción

En esta lección veremos tres riesgos clásicos de la web tradicional adaptados a las APIs modernas: XSS (Cross-Site Scripting), CSRF (Cross-Site Request Forgery) y la protección mediante cabeceras de seguridad HTTP.

Las APIs que devuelven JSON son naturalmente más resistentes a XSS que las aplicaciones que renderizan HTML, pero no están exentas de riesgos. Además, el CSRF se comporta de forma diferente cuando usamos autenticación stateless con JWT.

¿Qué problema resuelven? Previenen la ejecución de scripts maliciosos, el abuso de sesiones autenticadas y la explotación de configuraciones inseguras del navegador.

¿Cuándo se utilizan? En toda aplicación web o API que sea consumida desde un navegador. Incluso APIs puras deben configurar cabeceras de seguridad y protegerse contra clickjacking.

Errores típicos: devolver HTML desde una API, no configurar cabeceras de seguridad, o añadir anti-forgery tokens innecesarios a una API stateless con JWT. También es común olvidar que Swagger/Scalar se ejecutan en un navegador y pueden verse afectados por XSS o clickjacking.

2 · Teoría

XSS ocurre cuando un atacante consigue que un navegador ejecute código JavaScript malicioso. En una API que devuelve JSON, el riesgo principal no está en el backend, sino en cómo el cliente renderiza esos datos. Si el frontend inserta userInput directamente en el DOM sin escapar, se produce XSS.

Hay tres tipos principales de XSS:

  • Stored XSS: el payload se almacena en la base de datos y se sirve a múltiples usuarios.
  • Reflected XSS: el payload viene en la URL o en una petición y se refleja inmediatamente en la respuesta.
  • DOM-based XSS: el payload se procesa completamente en el cliente sin intervención del servidor.

CSRF obliga a un usuario autenticado a ejecutar una acción no deseada en una aplicación web. Tradicionalmente se mitiga con tokens anti-forgery que el navegador no puede leer fácilmente. Sin embargo, en una API stateless con JWT almacenado en localStorage y enviado en el header Authorization, el navegador no añade ese header automáticamente, por lo que el CSRF clásico no aplica.

Las cabeceras de seguridad son directivas que el servidor envía al navegador para restringir comportamientos peligrosos: ejecutar scripts inline, cargar la página en un iframe, adivinar el tipo MIME, etc.


Cabeceras de seguridad esenciales
─────────────────────────────────
Content-Security-Policy    →  controla de dónde puede cargar recursos el navegador
X-Content-Type-Options     →  evita que el navegador adivine el tipo de contenido
X-Frame-Options            →  evita clickjacking (iframe)
Strict-Transport-Security  →  fuerza HTTPS durante un tiempo (HSTS)
Referrer-Policy            →  limita la información de referencia enviada
Permissions-Policy         →  desactiva APIs del navegador innecesarias

APIs JSON y XSS

Una API que devuelve JSON correctamente tipado no ejecuta JavaScript por sí sola. El problema aparece cuando el frontend usa innerHTML o cuando la API devuelve contenido HTML sin escapar. Por eso, en una API pura, el principal trabajo contra XSS es validar el input y devolver JSON correctamente codificado.

JWT y CSRF

CSRF se basa en que el navegador envía automáticamente ciertas credenciales (cookies de sesión) con cada petición. Si el token JWT se almacena en localStorage y se añade manualmente al header Authorization, el navegador no lo envía automáticamente. Esto elimina el riesgo de CSRF tradicional. Si usas cookies HttpOnly, sí necesitas anti-forgery tokens.

3 · Ejemplo mínimo

Veamos cómo configurar cabeceras de seguridad en ASP.NET Core con un middleware personalizado muy sencillo.

app.Use(async (context, next) =>
{
    var headers = context.Response.Headers;

    // Evita que el navegador cargue la página en un iframe
    headers.Append("X-Frame-Options", "DENY");

    // Evita sniffing de MIME type
    headers.Append("X-Content-Type-Options", "nosniff");

    // Fuerza HTTPS durante 1 año
    headers.Append("Strict-Transport-Security", "max-age=31536000; includeSubDomains");

    // Política de contenido restrictiva para APIs
    headers.Append("Content-Security-Policy", "default-src 'none'");

    await next();
});

Este middleware debe colocarse temprano en el pipeline, idealmente justo después de UseExceptionHandler y antes de UseRouting. Si lo colocas después de UseStaticFiles, los archivos estáticos no recibirán las cabeceras.

Orden del pipeline de seguridad


Orden recomendado del pipeline
──────────────────────────────
app.UseExceptionHandler()
app.UseMiddleware<SecurityHeadersMiddleware>()
app.UseHttpsRedirection()
app.UseCors()
app.UseAuthentication()
app.UseAuthorization()
app.UseRateLimiter()
app.MapControllers()
app.Run()

Las cabeceras de seguridad se aplican lo antes posible para que todas las respuestas, incluidas las de error, las incluyan. UseRateLimiter se coloca después de UseAuthentication cuando necesitamos identificar al usuario para limitar por claim.

4 · Ejemplo real

En una API profesional no configuramos cabeceras manualmente en cada endpoint. Usamos un middleware reutilizable, validamos la entrada y devolvemos siempre JSON con el Content-Type correcto.

// Middleware reutilizable para cabeceras de seguridad
public class SecurityHeadersMiddleware(RequestDelegate next)
{
    public Task InvokeAsync(HttpContext context)
    {
        var headers = context.Response.Headers;

        headers.Append("X-Frame-Options", "DENY");
        headers.Append("X-Content-Type-Options", "nosniff");
        headers.Append("X-XSS-Protection", "0");
        headers.Append("Referrer-Policy", "strict-origin-when-cross-origin");
        headers.Append("Strict-Transport-Security", "max-age=31536000; includeSubDomains; preload");
        headers.Append("Content-Security-Policy", "default-src 'none'; frame-ancestors 'none'");
        headers.Append("Permissions-Policy", "accelerometer=(), camera=(), geolocation=(), gyroscope=(), magnetometer=(), microphone=(), payment=(), usb=()");

        return next(context);
    }
}

Registro en Program.cs:

app.UseMiddleware<SecurityHeadersMiddleware>();

app.MapControllers();
app.Run();

Respecto a XSS, el backend debe validar y sanitizar la entrada, pero la responsabilidad final de no ejecutar scripts recae en el cliente. No obstante, podemos ayudar devolviendo siempre JSON y nunca HTML:

// ✅ Devuelve JSON con encoding correcto
app.MapGet("/api/comments/{id:guid}", async (Guid id, CmsDbContext db) =>
{
    var comment = await db.Comments.FindAsync(id);
    return comment is null
        ? Results.NotFound()
        : Results.Json(comment); // Content-Type: application/json; charset=utf-8
});

El tipo de contenido application/json no ejecuta JavaScript. El problema de XSS aparece cuando el frontend toma un string del JSON y lo inserta directamente en el DOM usando innerHTML o similares. Por eso, en APIs modernas, el backend debe minimizar la superficie de ataque validando la entrada y documentando claramente que el cliente debe escapar la salida.

Configuración de excepciones para no filtrar información

Las respuestas de error también pueden contribuir a problemas de seguridad si revelan información interna. En producción, un error no debe devolver stack traces ni detalles de la base de datos. El middleware de excepciones debe transformar todo en ProblemDetails genéricos:

if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler(errorApp =>
    {
        errorApp.Run(async context =>
        {
            context.Response.StatusCode = StatusCodes.Status500InternalServerError;
            context.Response.ContentType = "application/json";
            await context.Response.WriteAsJsonAsync(new ProblemDetails
            {
                Title = "Error interno",
                Detail = "Se ha producido un error inesperado. Contacte con soporte.",
                Status = StatusCodes.Status500InternalServerError
            });
        });
    });
}

Esta configuración es importante en A08 (Security Misconfiguration) y también reduce el riesgo de que un atacante utilice mensajes de error para montar ataques de XSS o ingeniería social.

Además, podemos validar el input para reducir la probabilidad de que un payload XSS se almacene. Si permitimos HTML en comentarios, deberíamos sanitizarlo con una librería como HtmlSanitizer:

public class CreateCommentRequest
{
    public Guid PostId { get; set; }

    [Required]
    [MaxLength(2000)]
    public string Content { get; set; } = string.Empty;
}

public class CreateCommentHandler
{
    public async Task<Guid> Handle(CreateCommentRequest request)
    {
        var sanitizer = new HtmlSanitizer();
        var cleanContent = sanitizer.Sanitize(request.Content);

        // Persistir cleanContent en la base de datos
    }
}

El sanitizer permite etiquetas seguras como <p> o <strong>, pero elimina <script>, eventos inline y otros vectores XSS.

5 · Buenas prácticas

  • Nunca devuelvas HTML desde una API que no esté pensada para ello. Si necesitas generar HTML, usa un motor de vistas dedicado y escapa la salida.
  • Configura cabeceras de seguridad globalmente con un middleware, no en cada endpoint.
  • Usa JWT en header Authorization para APIs stateless. No necesitas anti-forgery tokens en este caso.
  • Si usas cookies para autenticación, marca HttpOnly, Secure y SameSite=Strict, y sí usa anti-forgery tokens.
  • Valida y limita la entrada del usuario: longitudes, caracteres permitidos y sanitización si se va a reflejar.
  • Content Security Policy debe ser restrictiva y ajustarse al frontend que consumirá la API.
  • Sanitiza HTML si permites contenido enriquecido. Nunca confíes en el input tal cual.
  • Configura CORS de forma restrictiva: orígenes explícitos, métodos necesarios y headers permitidos.
  • Protege la documentación: Swagger/Scalar también se ejecutan en navegador y deben tener CSP y X-Frame-Options.
Consejo: usa NWebsec o NetEscapades.AspNetCore.SecurityHeaders si prefieres una librería madura en lugar de escribir el middleware a mano. Estas librerías facilitan la configuración y evitan errores tipográficos en los headers.

8 · Reto

Investiga cómo configurar Content Security Policy para una API que sirve también documentación Swagger/Scalar. La política debe:

  • Permitir scripts y estilos inline solo para la documentación.
  • Bloquear iframes y objetos.
  • NO aplicarse a los endpoints JSON (o aplicar una versión más restrictiva).
  • Usar nonces para scripts inline si es posible.

No resuelvas el reto todavía. Piensa en cómo condicionar las cabeceras según la ruta. Swagger/Scalar usan scripts inline, lo que complica una CSP estricta.

9 · Resumen

  • Las APIs JSON son menos vulnerables a XSS, pero deben configurar cabeceras de seguridad.
  • El CSRF clásico no aplica a APIs stateless con JWT en el header Authorization.
  • Las cabeceras X-Frame-Options, X-Content-Type-Options, HSTS y CSP reducen la superficie de ataque.
  • Usa un middleware global para aplicar las cabeceras en toda la aplicación.
  • Sanitiza el input si permite contenido HTML enriquecido.
  • Configura CORS de forma restrictiva y nunca uses * en producción.

10 · Preguntas frecuentes

¿Una API pura JSON puede tener XSS?

Directamente en el backend no, pero si el frontend renderiza los datos sin escapar, sí. El backend puede ayudar validando y nunca devolviendo HTML.

¿Necesito anti-forgery tokens con JWT?

No, si el token va en el header Authorization. Sí los necesitas si usas cookies de sesión.

¿Qué es HSTS?

HTTP Strict Transport Security. Indica al navegador que siempre use HTTPS para el dominio durante el tiempo indicado. Evita ataques de downgrade.

¿Dónde coloco el middleware de cabeceras?

Lo antes posible en el pipeline, normalmente después del exception handler y antes de routing/static files. Si está demasiado tarde, algunas respuestas no tendrán las cabeceras.

¿Qué es CSP?

Content Security Policy. Define de qué orígenes puede cargar scripts, estilos, imágenes y otros recursos el navegador. Es una de las mitigaciones más potentes contra XSS.

¿Debo usar cookies HttpOnly o localStorage?

Las cookies HttpOnly no son accesibles por JavaScript, lo que reduce XSS. Sin embargo, para APIs stateless con JWT, el header Authorization es más sencillo. Si eliges cookies, usa SameSite=Strict y anti-forgery tokens.
