Proyecto CMS: caching con Redis

Módulo 13 · Caching y rendimiento45 min

1 · Introducción

En este proyecto del módulo vamos a aplicar todo lo aprendido sobre caching al CMS. Añadiremos una capa de caché distribuido con Redis para las consultas de posts y categorías, invalidaremos las entradas cuando se modifiquen los datos y compararemos el rendimiento con y sin caché usando BenchmarkDotNet.

También configuraremos Redis en el docker-compose.yml del proyecto final para que el entorno de desarrollo sea reproducible.

Objetivo del proyecto: cachear las lecturas públicas de posts y categorías sin afectar la lógica de negocio. Las escrituras (crear, actualizar, eliminar) invalidarán el caché correspondiente. Usaremos Redis para que la solución funcione al escalar a múltiples instancias.

Al terminar tendrás el CMS con una capa de caché lista para producción, tests de integración que verifican la invalidación y benchmarks que demuestran la mejora.

2 · Teoría

2.1 Estrategia de caché en el CMS

El CMS tiene dos tipos de lecturas que benefician mucho del caché:

  • Categorías: lista pequeña, cambia raramente. TTL largo (10 minutos).
  • Posts publicados: lista grande, cambia con frecuencia moderada. TTL corto (2 minutos) y variación por paginación.
  • Post individual: consulta directa por id o slug. TTL medio (5 minutos).

Invalidaciones:

  • Al crear un post: invalidar lista de posts publicados y tags relacionadas.
  • Al actualizar un post: invalidar el post individual y la lista de publicados.
  • Al crear/actualizar/eliminar una categoría: invalidar lista de categorías.

2.2 Arquitectura

Colocamos el caché en la capa de aplicación, justo antes de los repositorios. Así la infraestructura no conoce de caché y la capa de aplicación decide qué cachear y cuándo invalidar.

API ──▶ Handler (Application)
           │
           ▼
        CachedService (Application)
           │
           ├─▶ IDistributedCache (Redis)
           │
           ▼

           │

        EF Core + PostgreSQL

2.3 Convención de claves

Usamos un generador central para evitar duplicar strings y errores:

  • cms:category:all
  • cms:post:published:page:{page}:size:{size}
  • cms:post:{id}
  • cms:post:slug:{slug}

3 · Ejemplo mínimo

Vamos a añadir Redis al proyecto final del CMS. Suponemos que ya tienes la estructura Clean Architecture con las capas Cms.Domain, Cms.Application, Cms.Infrastructure y Cms.Api.

Paso 1: instalar paquetes

dotnet add proyecto-final/src/Cms.Api package Microsoft.Extensions.Caching.StackExchangeRedis

dotnet add proyecto-final/tests/Cms.Tests package Microsoft.Extensions.Caching.StackExchangeRedis

4.1 Generador de claves

namespace Cms.Application.Caching;

public static class CacheKeys
{
    public const string Prefix = "cms";
    public const string CategoriesAll = "cms:category:all";

    public static string Post(Guid id) => $"cms:post:{id}";
    public static string PostBySlug(string slug) => $"cms:post:slug:{slug}";
    public static string PublishedPosts(int page, int pageSize) =>
        $"cms:post:published:page:{page}:size:{pageSize}";
}

4.2 Extensiones de IDistributedCache

using Microsoft.Extensions.Caching.Distributed;
using System.Text.Json;

namespace Cms.Application.Caching;

public static class DistributedCacheExtensions
{
    public static async Task<T?> GetAsync<T>(
        this IDistributedCache cache,
        string key,
        CancellationToken ct = default)
    {
        var data = await cache.GetAsync(key, ct);
        if (data is null) return default;
        return JsonSerializer.Deserialize<T>(data);
    }

    public static async Task SetAsync<T>(
        this IDistributedCache cache,
        string key,
        T value,
        TimeSpan absoluteExpiration,
        CancellationToken ct = default)
    {
        var data = JsonSerializer.SerializeToUtf8Bytes(value);
        await cache.SetAsync(key, data, new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = absoluteExpiration
        }, ct);
    }
}

4.3 Servicio de categorías cacheado

using Cms.Application.Caching;
using Microsoft.Extensions.Caching.Distributed;

namespace Cms.Application.Categories;

public sealed class CategoryService
{
    private readonly ICategoryRepository _repository;
    private readonly IDistributedCache _cache;
    private readonly ILogger<CategoryService> _logger;

    public CategoryService(
        ICategoryRepository repository,
        IDistributedCache cache,
        ILogger<CategoryService> logger)
    {
        _repository = repository;
        _cache = cache;
        _logger = logger;
    }

    public async Task<IReadOnlyList<CategoryDto>> GetAllAsync(CancellationToken ct)
    {
        var cached = await _cache.GetAsync<IReadOnlyList<CategoryDto>>(CacheKeys.CategoriesAll, ct);
        if (cached is not null)
        {
            _logger.LogInformation("Cache hit: categorías");
            return cached;
        }

        _logger.LogInformation("Cache miss: categorías");
        var categories = await _repository.GetAllAsync(ct);
        var dtos = categories.Select(c => new CategoryDto(c.Id, c.Name, c.Slug)).ToList();

        await _cache.SetAsync(CacheKeys.CategoriesAll, dtos, TimeSpan.FromMinutes(10), ct);
        return dtos;
    }

    public async Task InvalidateAsync(CancellationToken ct)
    {
        _logger.LogInformation("Invalidando caché de categorías");
        await _cache.RemoveAsync(CacheKeys.CategoriesAll, ct);
    }
}

public sealed record CategoryDto(Guid Id, string Name, string Slug);

public interface ICategoryRepository
{
    Task<IReadOnlyList<Category>> GetAllAsync(CancellationToken ct);
}

4.4 Servicio de posts cacheado

using Cms.Application.Caching;
using Microsoft.Extensions.Caching.Distributed;

namespace Cms.Application.Posts;

public sealed class CachedPostService
{
    private readonly IPostRepository _repository;
    private readonly IDistributedCache _cache;
    private readonly ILogger<CachedPostService> _logger;

    public CachedPostService(
        IPostRepository repository,
        IDistributedCache cache,
        ILogger<CachedPostService> logger)
    {
        _repository = repository;
        _cache = cache;
        _logger = logger;
    }

    public async Task<PostDto?> GetByIdAsync(Guid id, CancellationToken ct)
    {
        var key = CacheKeys.Post(id);
        var cached = await _cache.GetAsync<PostDto>(key, ct);
        if (cached is not null)
        {
            _logger.LogInformation("Cache hit: post {PostId}", id);
            return cached;
        }

        _logger.LogInformation("Cache miss: post {PostId}", id);
        var post = await _repository.GetByIdAsync(id, ct);
        if (post is null) return null;

        var dto = MapToDto(post);
        await _cache.SetAsync(key, dto, TimeSpan.FromMinutes(5), ct);
        return dto;
    }

    public async Task<IReadOnlyList<PostSummaryDto>> GetPublishedAsync(
        int page, int pageSize, CancellationToken ct)
    {
        var key = CacheKeys.PublishedPosts(page, pageSize);
        var cached = await _cache.GetAsync<IReadOnlyList<PostSummaryDto>>(key, ct);
        if (cached is not null)
        {
            _logger.LogInformation("Cache hit: posts publicados página {Page}", page);
            return cached;
        }

        _logger.LogInformation("Cache miss: posts publicados página {Page}", page);
        var posts = await _repository.GetPublishedAsync(page, pageSize, ct);
        var dtos = posts.Select(MapToSummary).ToList();

        await _cache.SetAsync(key, dtos, TimeSpan.FromMinutes(2), ct);
        return dtos;
    }

    public async Task InvalidateAsync(Guid id, CancellationToken ct)
    {
        await _cache.RemoveAsync(CacheKeys.Post(id), ct);

        // Invalidamos todas las páginas de posts publicados. En producción podríamos
        // usar un tag o un patrón de invalidación más sofisticado.
        for (int page = 1; page <= 10; page++)
        {
            for (int size = 10; size <= 50; size += 10)
            {
                await _cache.RemoveAsync(CacheKeys.PublishedPosts(page, size), ct);
            }
        }
    }

    private static PostDto MapToDto(Post post) =>
        new(post.Id, post.Title, post.Slug, post.Status, post.PublishedAt);

    private static PostSummaryDto MapToSummary(Post post) =>
        new(post.Id, post.Title, post.PublishedAt!.Value);
}

public sealed record PostDto(Guid Id, string Title, string Slug, string Status, DateTime? PublishedAt);
public sealed record PostSummaryDto(Guid Id, string Title, DateTime PublishedAt);

public interface IPostRepository
{
    Task<Post?> GetByIdAsync(Guid id, CancellationToken ct);
    Task<IReadOnlyList<Post>> GetPublishedAsync(int page, int pageSize, CancellationToken ct);
}

public sealed class Post(Guid id, string title, string slug, string status, DateTime? publishedAt)
{
    public Guid Id { get; } = id;
    public string Title { get; } = title;
    public string Slug { get; } = slug;
    public string Status { get; } = status;
    public DateTime? PublishedAt { get; } = publishedAt;
}

4.5 Invalidación en handlers de escritura

public sealed class CreateCategoryHandler(
    ICategoryRepository repository,
    CategoryService service,
    IUnitOfWork unitOfWork)
{
    public async Task<Result<Guid>> HandleAsync(CreateCategoryCommand command, CancellationToken ct)
    {
        var category = new Category(command.Name, command.Slug);
        await repository.AddAsync(category, ct);
        await unitOfWork.SaveChangesAsync(ct);

        await service.InvalidateAsync(ct);
        return Result<Guid>.Success(category.Id);
    }
}

public sealed class UpdatePostHandler(
    IPostRepository repository,
    CachedPostService service,
    IUnitOfWork unitOfWork)
{
    public async Task<Result> HandleAsync(UpdatePostCommand command, CancellationToken ct)
    {
        var post = await repository.GetByIdAsync(command.Id, ct);
        if (post is null) return Result.Failure("Post.NotFound", "Post no encontrado");

        post.Update(command.Title, command.Content);
        await unitOfWork.SaveChangesAsync(ct);

        await service.InvalidateAsync(command.Id, ct);
        return Result.Success();
    }
}

5 · Buenas prácticas

  • Capa de aplicación: el caché debe vivir en aplicación, no en infraestructura. Así el dominio sigue puro y la API no conoce detalles.
  • Claves centralizadas: usa una clase CacheKeys para evitar duplicar strings y errores de formato.
  • TTLs según el tipo de dato: categorías 10 minutos, posts individuales 5 minutos, listas 2 minutos.
  • Invalidación explícita: cada escritura debe invalidar las claves afectadas. Es preferible invalidar de más que servir datos obsoletos.
  • Evita invalidación en masa sin control: invalidar todas las páginas con bucles puede ser costoso. Considera tags o versiones cuando el número de claves sea grande.
  • Tests de integración: verifica que tras una escritura, la siguiente lectura no devuelve datos cacheados.
  • Benchmarks: mide consultas con y sin caché para demostrar la mejora y detectar regresiones.
  • Monitoreo: añade logs de Cache hit y Cache miss para calcular hit rate en producción.

6 · Errores habituales

6.1 Cachear endpoints de escritura

// ❌ Mal: POST nunca debe cachearse
app.MapPost("/api/v1/posts", ...)
   .CacheOutput("Default");

// ✅ Bien: solo cachear GET y HEAD, e invalidar en escritura
app.MapGet("/api/v1/posts", ...)
   .CacheOutput("PublicPosts");

6.2 No invalidar al actualizar

// ❌ Mal: el post modificado sigue apareciendo antiguo
public async Task HandleAsync(UpdatePostCommand command, CancellationToken ct)
{
    var post = await repository.GetByIdAsync(command.Id, ct);
    post.Update(command.Title, command.Content);
    await unitOfWork.SaveChangesAsync(ct);
}

// ✅ Bien: invalidar la caché del recurso
await service.InvalidateAsync(command.Id, ct);

6.3 Depender de Redis en tests sin contenedor

// ❌ Mal: los tests fallan si Redis no está corriendo
services.AddStackExchangeRedisCache(options =>
    options.Configuration = "localhost:6379");

// ✅ Bien: usar Testcontainers para Redis o un in-memory IDistributedCache en tests
services.AddDistributedMemoryCache();

6.4 TTL infinito

// ❌ Mal: sin expiración, un error de invalidación deja datos obsoletos para siempre
await _cache.SetAsync(key, dto, new DistributedCacheEntryOptions(), ct);

// ✅ Bien: siempre expiración absoluta como mínimo
await _cache.SetAsync(key, dto, TimeSpan.FromMinutes(5), ct);

9 · Resumen

  • El CMS ahora usa Redis como caché distribuido para posts y categorías.
  • La capa de aplicación contiene la lógica de caché, manteniendo el dominio puro.
  • Usamos un generador central de claves y TTLs según el tipo de dato.
  • Los handlers de escritura invalidan las claves afectadas para evitar datos obsoletos.
  • Configuramos Redis en Docker Compose para un entorno reproducible.
  • BenchmarkDotNet y tests de integración validan que el caché mejora el rendimiento y se invalida correctamente.

10 · Preguntas frecuentes

¿Dónde coloco la lógica de caché en Clean Architecture?

En la capa de aplicación, justo antes de los repositorios. Nunca en Domain (debe ser pura) ni en Infrastructure (la infra no debe decidir qué cachear).

¿Por qué no usar Output Caching en lugar de IDistributedCache?

Output Caching cachea respuestas HTTP completas; IDistributedCache cachea datos. Ambos se complementan. Output Caching evita ejecutar endpoints; el caché de datos evita consultar la BD. Puedes usar ambos en el mismo CMS.

¿Cómo invalido todas las páginas de posts sin bucles?

Usa un token de versión compartido: almacena cms:posts:version y varía las claves incluyendo la versión. Al cambiar la versión, todas las entradas antiguas quedan obsoletas y se rellenan con la nueva. También puedes usar tags de Output Caching con EvictByTagAsync.

¿Qué pasa si Redis cae en producción?

Con abortConnect=false la librería intenta reconectar. Rodea el caché de try/catch y cae a la base de datos. Considera un circuit breaker para no saturar la BD si Redis está caído mucho tiempo.

¿Debo cachear siempre los posts individuales?

No. Si los posts individuales se consultan poco, el coste de Redis puede superar el beneficio. Mide primero. Generalmente, listas y datos muy populados son mejores candidatos.

¿Cómo pruebo el caché en integración?

Registra AddDistributedMemoryCache en los tests de la factory para no depender de Redis, o usa Testcontainers para levantar un Redis real. Verifica que la primera lectura devuelve datos y que tras una escritura se invalidan.
