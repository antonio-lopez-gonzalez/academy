Caching en memoria: IMemoryCache

Módulo 13 · Caching y rendimiento30 min

1 · Introducción

En esta lección aprenderemos a usar IMemoryCache, el caché en memoria de ASP.NET Core. Es la solución más rápida para evitar repetir trabajo costoso: consultas a base de datos, cálculos complejos, respuestas de APIs externas o listados que cambian poco.

Veremos la diferencia entre la interfaz IMemoryCache y la implementación MemoryCache, cómo almacenar y recuperar valores, estrategias de expiración, prioridades y el patrón cache-aside.

¿Cuándo usarlo? Cuando tu aplicación corre en una sola instancia, los datos caben en RAM y pueden tolerar unos segundos de desfase respecto a la fuente real. Si escalas a varias máquinas, necesitarás caché distribuido (Redis), que veremos en la siguiente lección.

Al terminar sabrás configurar el caché, leer y escribir con GetOrCreate, invalidar entradas y evitar los errores más comunes como cache stampede o claves mal diseñadas.

2 · Teoría

2.1 IMemoryCache vs MemoryCache

ASP.NET Core separa la interfaz de la implementación siguiendo el principio de inversión de dependencias:

  • IMemoryCache: abstracción. La inyectas en constructores y la usas en tu código. Es la que debes preferir siempre.
  • MemoryCache: implementación concreta. Se registra en el contenedor de DI y gestiona el almacenamiento real, compresión, expiración y evicción por presión de memoria.

Registro típico en Program.cs:

builder.Services.AddMemoryCache();

2.2 Cómo funciona internamente

MemoryCache guarda los valores en un ConcurrentDictionary<object, CacheEntry>. Cada entrada tiene metadatos de expiración, prioridad, tokens de invalidación y callbacks. Cuando el sistema detecta presión de memoria, el MemoryCacheCompact elimina primero las entradas con menor prioridad y más antiguas.

Memoria compartida: el caché vive en el mismo proceso de la aplicación. Si reinicias el servidor, se pierde. Si escalas horizontalmente, cada instancia tiene su propia copia, lo que puede provocar inconsistencias.

2.3 Estrategias de expiración

  • Absolute expiration: la entrada desaparece transcurrido un tiempo fijo. Útil cuando sabes exactamente cuánto vale la pena conservarla.
  • Sliding expiration: el contador se reinicia cada vez que se accede a la entrada. Útil para datos populares, pero puede hacer que entradas poco útiles sobrevivan demasiado si se combinan con un acceso absoluto.
  • Expiration tokens: permiten invalidar un grupo de entradas de una sola vez (por ejemplo, cuando se publica un post).
  • Priority: define qué entradas se eliminan primero cuando hay presión de memoria.

2.4 Patrón cache-aside

Es el patrón más común: primero se consulta el caché; si no está, se calcula, se guarda y se devuelve. Así el caché "envuelve" la fuente de datos real.

Request ──▶ ¿En caché? ──Sí──▶ Devolver valor
              │
              No
              ▼
        Calcular valor
              │
              ▼
        Guardar en caché
              │
              ▼
        Devolver valor

3 · Ejemplo mínimo

Creamos una aplicación de consola que usa IMemoryCache para evitar repetir una operación lenta.

dotnet new console -n MemoryCacheDemo -o ejemplos/m13-caching/MemoryCacheDemo/src/MemoryCacheDemo
dotnet add ejemplos/m13-caching/MemoryCacheDemo/src/MemoryCacheDemo package Microsoft.Extensions.Caching.Memory
dotnet add ejemplos/m13-caching/MemoryCacheDemo/src/MemoryCacheDemo package Microsoft.Extensions.DependencyInjection
using Microsoft.Extensions.Caching.Memory;
using Microsoft.Extensions.DependencyInjection;

namespace MemoryCacheDemo;

class Program
{
    // Método que simula un trabajo costoso: 500 ms de espera.
    static async Task<string> GetSlowDataAsync(string key)
    {
        await Task.Delay(500);
        return $"Datos para {key} calculados a las {DateTime.Now:HH:mm:ss.fff}";
    }

    static async Task Main()
    {
        // Configuramos un contenedor de DI mínimo con el caché en memoria.
        var services = new ServiceCollection();
        services.AddMemoryCache();
        var provider = services.BuildServiceProvider();
        var cache = provider.GetRequiredService<IMemoryCache>();

        const string cacheKey = "slow:greeting";

        // --- Primera llamada: no está en caché, se ejecuta el trabajo lento.
        var first = await cache.GetOrCreateAsync(cacheKey, async entry =>
        {
            // Establecemos una expiración combinada para no mantener datos eternos.
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(10);
            entry.SlidingExpiration = TimeSpan.FromSeconds(3);
            entry.Priority = CacheItemPriority.High;

            return await GetSlowDataAsync(cacheKey);
        });

        Console.WriteLine($"Primera: {first}");

        // --- Segunda llamada: ya existe en caché, es instantánea.
        var second = await cache.GetOrCreateAsync(cacheKey, async entry =>
        {
            return await GetSlowDataAsync(cacheKey);
        });

        Console.WriteLine($"Segunda: {second}");

        // Invalidamos la entrada manualmente.
        cache.Remove(cacheKey);

        // --- Tercera llamada: el caché está vacío, vuelve a calcular.
        var third = await cache.GetOrCreateAsync(cacheKey, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(10);
            return await GetSlowDataAsync(cacheKey);
        });

        Console.WriteLine($"Tercera: {third}");
    }
}

Salida aproximada:

Primera: Datos para slow:greeting calculados a las 14:30:10.123
Segunda: Datos para slow:greeting calculados a las 14:30:10.123
Tercera: Datos para slow:greeting calculados a las 14:30:11.234
Tip: GetOrCreateAsync es la forma más segura de consultar y poblar el caché en un solo paso. Evita el clásico if (cache.TryGetValue(...)) seguido de un segundo acceso.

4 · Ejemplo real

En un servicio de posts del CMS podemos cachear el listado de categorías, que cambia poco, pero no un post individual en borrador, que evoluciona constantemente.

using Microsoft.Extensions.Caching.Memory;

namespace Cms.Application.Categories;

public interface ICategoryRepository
{
    Task<IReadOnlyList<Category>> GetAllAsync(CancellationToken ct);
}

public sealed class CategoryService
{
    private readonly ICategoryRepository _repository;
    private readonly IMemoryCache _cache;
    private readonly ILogger<CategoryService> _logger;

    private const string AllCategoriesKey = "categories:all";

    public CategoryService(
        ICategoryRepository repository,
        IMemoryCache cache,
        ILogger<CategoryService> logger)
    {
        _repository = repository;
        _cache = cache;
        _logger = logger;
    }

    public async Task<IReadOnlyList<Category>> GetAllAsync(CancellationToken ct)
    {
        var cached = await _cache.GetOrCreateAsync(
            AllCategoriesKey,
            async entry =>
            {
                _logger.LogInformation("Cache miss para categorías; consultando base de datos");

                // Expira en 5 minutos como máximo, pero se renueva si se usa.
                entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
                entry.SlidingExpiration = TimeSpan.FromMinutes(1);
                entry.Priority = CacheItemPriority.Normal;

                return await _repository.GetAllAsync(ct);
            });

        return cached ?? Array.Empty<Category>();
    }

    public void Invalidate()
    {
        _logger.LogInformation("Invalidando caché de categorías");
        _cache.Remove(AllCategoriesKey);
    }
}

public sealed record Category(Guid Id, string Name, string Slug);

Registro en DI:

builder.Services.AddMemoryCache();
builder.Services.AddScoped<CategoryService>();

Invalidación cuando se crea una categoría:

public class CreateCategoryHandler
{
    private readonly ICategoryRepository _repository;
    private readonly CategoryService _service;

    public CreateCategoryHandler(ICategoryRepository repository, CategoryService service)
    {
        _repository = repository;
        _service = service;
    }

    public async Task<Category> HandleAsync(CreateCategoryCommand command, CancellationToken ct)
    {
        var category = await _repository.CreateAsync(command, ct);
        _service.Invalidate();
        return category;
    }
}
Claves: usa nombres descriptivos y con prefijo de dominio, como categories:all o post:{id}. Nunca uses objetos complejos como clave: el caché internamente usa GetHashCode y eso puede causar colisiones inesperadas.

5 · Buenas prácticas

  • Prefiere IMemoryCache: inyecta la interfaz, no la implementación concreta.
  • Define claves centralizadas: evita duplicar strings literales en múltiples clases. Usa constantes o un generador de claves.
  • Combina expiraciones: usa AbsoluteExpirationRelativeToNow como tope y SlidingExpiration para datos populares. Sin absoluta, una entrada muy consultada podría vivir para siempre.
  • Invalida al mutar: siempre que guardes, actualices o elimines un recurso, invalida las entradas de caché afectadas. El caché sin invalidación es una fuente de bugs difíciles.
  • No almacenes objetos mutables: si guardas una lista y la modificas después, estás modificando el caché. Almacena copias de solo lectura o estructuras inmutables.
  • Prioriza correctamente: datos grandes y poco importantes deben tener CacheItemPriority.Low o Normal. Datos críticos y pequeños pueden ser High.
  • Mide antes de cachear: no añadas caché por intuición. Mide con logs o BenchmarkDotNet si la mejora justifica la complejidad.
  • Considera MemoryCacheEntryOptions reutilizables: para muchas entradas con la misma configuración, crea una instancia y pásala a Set o GetOrCreate.

6 · Errores habituales

6.1 Cache stampede

Cuando una entrada expira y muchas peticiones concurrentes llegan al mismo tiempo, todas calculan el mismo valor. Para evitarlo, usa siempre GetOrCreateAsync, que bloquea el cálculo para una misma clave.

// ❌ Mal: el trabajo costoso se ejecuta varias veces en paralelo
if (!_cache.TryGetValue(key, out var value))
{
    value = await GetExpensiveValueAsync();
    _cache.Set(key, value);
}

// ✅ Bien: GetOrCreateAsync asegura que solo un hilo calcula por clave
value = await _cache.GetOrCreateAsync(key, async entry =>
    await GetExpensiveValueAsync());

6.2 No invalidar

// ❌ Mal: el caché nunca se actualiza tras un cambio
public async Task UpdateAsync(Category category)
{
    await _repository.UpdateAsync(category);
}

// ✅ Bien: invalidar la clave afectada tras la modificación
public async Task UpdateAsync(Category category)
{
    await _repository.UpdateAsync(category);
    _cache.Remove($"category:{category.Id}");
    _cache.Remove("categories:all");
}

6.3 Claves frágiles

// ❌ Mal: concatenación manual dispersa por el código
var key = "categories";

// ✅ Bien: claves con prefijo y formato consistente
private static string CategoryKey(Guid id) => $"category:{id}";
private const string AllCategoriesKey = "categories:all";

6.4 Depender de caché en memoria en entornos multi-instancia

// ❌ Mal: cada instancia ve datos distintos
services.AddMemoryCache();

// ✅ Bien: usar caché distribuido en producción con varias réplicas
services.AddStackExchangeRedisCache(options =>
    options.Configuration = "localhost:6379");

7 · Ejercicio guiado

Vamos a cachear un cálculo de estadísticas de posts en una aplicación de consola.

Paso 1: crea el proyecto

dotnet new console -n StatsCache -o ejemplos/m13-caching/StatsCache/src/StatsCache
dotnet add ejemplos/m13-caching/StatsCache/src/StatsCache package Microsoft.Extensions.Caching.Memory
dotnet add ejemplos/m13-caching/StatsCache/src/StatsCache package Microsoft.Extensions.DependencyInjection

Paso 2: implementa el servicio

using Microsoft.Extensions.Caching.Memory;

namespace StatsCache;

public class PostStatsService(IMemoryCache cache)
{
    public async Task<int> CountPublishedAsync()
    {
        return await cache.GetOrCreateAsync(
            "stats:published-count",
            async entry =>
            {
                await Task.Delay(300); // simula consulta a BD
                entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(30);
                return 42;
            });
    }

    public void Invalidate() => cache.Remove("stats:published-count");
}

Paso 3: programa

using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection();
services.AddMemoryCache();
services.AddScoped<PostStatsService>();

var provider = services.BuildServiceProvider();
using var scope = provider.CreateScope();
var service = scope.ServiceProvider.GetRequiredService<PostStatsService>();

var a = await service.CountPublishedAsync();
var b = await service.CountPublishedAsync();
service.Invalidate();
var c = await service.CountPublishedAsync();

Console.WriteLine($"a={a}, b={b}, c={c}");

Verás que la segunda llamada es instantánea y la tercera vuelve a esperar 300 ms. ¿Puedes añadir una expiración deslizante de 10 segundos además de la absoluta?

8 · Reto

Añade a PostStatsService una invalidación por grupo usando ChangeToken:

  • Crea un CancellationTokenSource compartido como campo del servicio.
  • Usa entry.AddExpirationToken(new CancellationChangeToken(_tokenSource.Token)) al guardar.
  • Expón un método InvalidateAll() que llame a _tokenSource.Cancel() para expirar todas las entradas vinculadas a la vez.

9 · Resumen

  • IMemoryCache es el caché en memoria de ASP.NET Core, rápido pero limitado a un solo proceso.
  • Se registra con AddMemoryCache() y se usa con GetOrCreateAsync para evitar el patrón TryGetValue + Set.
  • Configura expiración absoluta, deslizante y prioridad según el tipo de dato.
  • Invalida entradas cuando los datos subyacentes cambian.
  • Usa claves con prefijo y evita objetos complejos como claves.
  • Para varias instancias o producción con escalado, considera Redis (IDistributedCache) que veremos a continuación.

10 · Preguntas frecuentes

¿Cuánto dura una entrada en IMemoryCache?

Tanto como indiques con AbsoluteExpiration o SlidingExpiration. Si no estableces ninguna, la entrada puede durar indefinidamente hasta que el proceso se cierre o haya presión de memoria.

¿Puedo usar IMemoryCache fuera de ASP.NET Core?

Sí, como vimos en el ejemplo mínimo. Solo necesitas instalar Microsoft.Extensions.Caching.Memory y configurar un ServiceCollection mínimo.

¿Es seguro almacenar objetos mutables?

No es recomendable. Si devuelves una lista mutable y el consumidor la modifica, estás modificando el valor cacheado. Devuelve siempre IReadOnlyList<T>, inmutables o copias.

¿Qué pasa si la memoria se llena?

MemoryCache compacta automáticamente entradas según prioridad y antigüedad. Las de prioridad NeverRemove solo desaparecen si se invalidan o se cierra el proceso.

¿GetOrCreateAsync realmente evita cálculos duplicados?

Sí, para una misma clave el caché internamente bloquea los hilos concurrentes hasta que el primero termina. Sin embargo, esto ocurre dentro de la misma instancia; entre instancias no hay bloqueo.

¿Puedo ver todas las claves del caché?

No directamente. IMemoryCache no expone un listado de claves por diseño. Si necesitas enumerar, deberás llevar tu propio registro de claves, aunque eso suele indicar un mal diseño.
