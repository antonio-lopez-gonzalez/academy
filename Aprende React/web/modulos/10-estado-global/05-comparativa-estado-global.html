Comparativa: cuándo usar cada uno

Módulo 10 · Estado global 🕐 30 minutos

1 · Introducción

Ya conoces las cuatro herramientas de este módulo: Context API, useReducer, Redux Toolkit y Zustand. La pregunta que todo el mundo se hace ahora es la más difícil de todas: ¿cuál uso en mi proyecto?

Y la respuesta honesta es: depende. No existe una "mejor" herramienta universal. Existe la herramienta adecuada para cada tipo de estado dentro de tu aplicación. La buena noticia es que aprender React como un profesional no es memorizar cuál es la "buena", sino saber leer el problema y elegir.

Una de las decisiones que más distingue a un desarrollador junior de uno senior es justamente esta: el junior elige la herramienta de moda (o la que ya conoce) y la aplica a todo; el senior analiza la frecuencia de cambio, el alcance del estado, el tamaño del equipo y el coste de mantenimiento, y elige en consecuencia. Esta lección es ese criterio.

🎯 El error de fondo: sobre-ingeniería

El pecado capital del estado global es sobre-ingenierizar: montar Redux para una app de tres pantallas, o envolver en un contexto un estado que solo usaba un componente. React ya trae useState y useReducer para el estado local. Antes de añadir una capa global, pregúntate siempre: ¿esto realmente es global?

2 · Teoría

Primero, clasifica el estado

Antes de mirar herramientas, mira el estado. En una app real conviven varios tipos, y cada uno tiene una herramienta natural:

Tipo de estadoEjemplosHerramienta natural
Local Valor de un input, si un menú está abierto useState
Local complejo Un formulario con 8 campos y validaciones useReducer
Compartido, cambia poco Tema, idioma, usuario autenticado Context API
Global, muchas actualizaciones Carrito, editor, tablero tipo Trello Redux Toolkit o Zustand
Del servidor Datos de una API, listados, detalle fetch + estado local (o una librería de datos)
De la URL Filtros, paginación, id de recurso React Router (search params)
💡 El estado del servidor no es estado global

Es tentador meter los datos que vienen de la API en Redux o Zustand, pero su naturaleza es distinta: viven en el servidor, tienen caché, se invalidan y hay que revalidarlos. Para eso existen librerías de data fetching. Este módulo se centra en estado de cliente.

El árbol de decisión

Este diagrama resume la conversación que deberías tener contigo mismo antes de elegir:

¿El estado lo usa más de un componente? │ ├─ NO ─► ¿La lógica de cambio es compleja (muchas acciones)? │ ├─ NO ─► useState │ └─ SÍ ─► useReducer │ └─ SÍ ─► ¿Cambia con poca frecuencia y hay pocos consumidores? ├─ SÍ ─► Context API (tema, idioma, usuario) │ └─ NO ─► ¿App grande, equipo grande, necesitas DevTools/middlewares? ├─ SÍ ─► Redux Toolkit └─ NO ─► Zustand

Complejidad frente a frecuencia de cambio

Otra forma de verlo es un mapa de dos ejes: cuánta gente lo usa (alcance) y cuánto cambia (frecuencia). Context se comporta peor cuanto más cambia el valor, porque cualquier cambio re-renderiza a todos los consumidores.

Cambia MUCHO │ Redux/Zustand │ Redux Toolkit (global vivo) │ (escala, devtools) ──────────────────┼────────────────── useState │ Context API (local) │ (global estable) │ Cambia POCO
🧭 Regla práctica

Empieza por lo más simple que funcione y escala solo cuando el dolor aparezca. Lo habitual en apps medianas: useState para lo local, un par de contextos para lo estable (tema, usuario) y Zustand o Redux para el estado global que cambia mucho y comparten muchos componentes.

3 · Ejemplo mínimo

Nada compara mejor que el mismo caso en las cuatro herramientas. El caso: un contador global que dos componentes pueden leer y modificar. Compara la cantidad de piezas de cada versión.

Context API

src/contexts/CounterContext.jsx
import { createContext, useContext, useState } from "react";

const CounterContext = createContext();

export function CounterProvider({ children }) {
  const [count, setCount] = useState(0);
  return (
    <CounterContext.Provider value={{ count, setCount }}>
      {children}
    </CounterContext.Provider>
  );
}

export function useCounter() {
  const ctx = useContext(CounterContext);
  if (!ctx) throw new Error("useCounter requiere CounterProvider");
  return ctx;
}

Piezas: contexto + Provider + hook + envolver la app.

useReducer

src/components/Counter.jsx
import { useReducer } from "react";

// Reducer puro: (state, action) => newState
function reducer(state, action) {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };
    case "decrement":
      return { count: state.count - 1 };
    default:
      return state;
  }
}

export default function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <div>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: "increment" })}>+</button>
    </div>
  );
}

Piezas: reducer + useReducer. Compartirlo exigiría además un contexto.

Redux Toolkit

src/store/counterSlice.js
import { createSlice } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { count: 0 },
  reducers: {
    increment: (state) => { state.count += 1; },
    decrement: (state) => { state.count -= 1; },
  },
});

export const { increment, decrement } = counterSlice.actions;
export default counterSlice.reducer;
src/components/Counter.jsx
import { useSelector, useDispatch } from "react-redux";
import { increment } from "../store/counterSlice";

export default function Counter() {
  const count = useSelector((state) => state.counter.count);
  const dispatch = useDispatch();
  return <button onClick={() => dispatch(increment())}>{count}</button>;
}

Piezas: slice + store + Provider + selector + dispatch.

Zustand

src/store/counterStore.js
import { create } from "zustand";

export const useCounterStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
}));
src/components/Counter.jsx
import { useCounterStore } from "../store/counterStore";

export default function Counter() {
  const count = useCounterStore((state) => state.count);
  const increment = useCounterStore((state) => state.increment);
  return <button onClick={increment}>{count}</button>;
}

Piezas: create() y un hook. Sin Provider, sin dispatch, sin slice.

📏 Analogía: coches con distintas mecánicas

Los cuatro te llevan al mismo sitio. Context es una bicicleta eléctrica: barata, sin permisos, perfecta para trayectos cortos. useReducer es una caja de cambios dentro de un mismo vehículo: no te saca de él, pero ordena el motor. Redux Toolkit es un camión: pesado de arrancar, pero mueve cargas enormes con seguridad. Zustand es un coche utilitario moderno: ligero, rápido y suficiente para el 80% de los viajes.

4 · Ejemplo real

Imagina una tienda online real. No tiene un tipo de estado: tiene varios, y lo profesional es asignar cada uno a la herramienta adecuada. Así se repartiría:

Estado de la tiendaAlcanceFrecuenciaHerramienta
Tema claro/oscuroToda la appCasi nuncaContext API
Usuario autenticadoToda la appCasi nunca (login/logout)Context API
Carrito de la compraVarias páginasMuy frecuenteRedux Toolkit / Zustand
Filtros y orden del catálogoPágina de catálogoFrecuenteURL (search params)
Lista de productosDel servidorPor peticiónfetch + estado local
Valor del buscadorUn componenteAl escribiruseState local

Fíjate en que ninguno de los cuatro es "el ganador": conviven. Vamos a ver cómo se monta esa convivencia en el código. Este es el main.jsx de una app que usa Context + Redux a la vez:

src/main.jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { Provider } from "react-redux";
import { store } from "./store";
import { ThemeProvider } from "./contexts/ThemeContext";
import { AuthProvider } from "./contexts/AuthContext";
import App from "./App.jsx";
import "./styles/global.css";

// Cada herramienta con su envoltorio, sin pisarse.
// Orden: primero lo más externo/estable (tema), luego el resto.
createRoot(document.getElementById("root")).render(
  <StrictMode>
    <ThemeProvider>
      <AuthProvider>
        <Provider store={store}>
          <App />
        </Provider>
      </AuthProvider>
    </ThemeProvider>
  </StrictMode>
);

Y ahora un componente que consume de los tres sitios a la vez, cada cosa de su herramienta:

src/components/TopBar.jsx
import { useAuth } from "../contexts/AuthContext";      // usuario (Context)
import { useTheme } from "../contexts/ThemeContext";    // tema (Context)
import { useSelector } from "react-redux";              // carrito (Redux)

export default function TopBar() {
  const { user } = useAuth();
  const { theme, toggleTheme } = useTheme();
  // Selector derivado y ligero: solo cuenta los artículos.
  const cartCount = useSelector((state) =>
    state.cart.items.reduce((n, item) => n + item.quantity, 0)
  );

  return (
    <header>
      <span>{user ? `Hola, ${user.name}` : "Invitado"}</span>
      <span>🛒 {cartCount}</span>
      <button onClick={toggleTheme}>{theme === "dark" ? "☀️" : "🌙"}</button>
    </header>
  );
}
⚠️ Mezclar herramientas no es gratis

Usar varias herramientas juntas es normal, pero cada una es una capa más que entender, depurar y mantener. La regla es una responsabilidad, una herramienta: el tema solo en Context, el carrito solo en Redux. Si el tema acabara duplicado en Context y en Redux, tendrías dos fuentes de verdad y un bug esperando.

Un caso de migración típico

Un escenario muy común en el mundo real: empezaste con Context para todo y la app creció. El contexto del carrito re-renderiza media aplicación cada vez que se añade un producto. La migración habitual es mover solo el carrito a Zustand (o Redux) y dejar el tema y el usuario en Context:

ANTES DESPUÉS ┌────────────────────────┐ ┌────────────────────────┐ │ Context: tema │ │ Context: tema │ │ Context: usuario │ ──► │ Context: usuario │ │ Context: CARRITO ✗ │ │ Zustand: CARRITO ✓ │ │ (re-render global) │ │ (selectores finos) │ └────────────────────────┘ └────────────────────────┘

5 · Buenas prácticas

HazEvita
Empezar con useState y subir de nivel solo cuando duela Montar Redux desde el primer día "por si acaso"
Elegir la herramienta por tipo de estado Usar la misma herramienta para todo
Guardar en la URL el estado navegable (filtros, página, id) Meter navegación en el store global
Un contexto por responsabilidad (tema, auth) Un "contexto dios" con todo metido

🤝 Y el factor humano: el equipo

La elección no es solo técnica. Si tu equipo de 20 personas ya conoce Redux, imponer Zustand "porque es más simple" tiene un coste de formación y de convenciones que quizá no compensa. La herramienta que tu equipo domina y puede mantener suele ganar a la teóricamente más elegante.

6 · Errores habituales

Error 1: Context para estado que cambia mucho

Mal — cada tecla re-renderiza todo el árbol 
// ✘ Un contexto con el texto del buscador: cambia en cada pulsación
//   y re-renderiza a TODOS los consumidores.
const SearchContext = createContext();

export function SearchProvider({ children }) {
  const [query, setQuery] = useState("");
  return (
    <SearchContext.Provider value={{ query, setQuery }}>
      {children}
    </SearchContext.Provider>
  );
}
Bien — el buscador es estado local 
// ✔ Si solo lo usa un componente, es estado LOCAL.
function SearchBox() {
  const [query, setQuery] = useState("");
  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}

Error 2: meter datos del servidor en el store global

Mal — el store acaba siendo una caché a medias 
// ✘ La lista de productos no es estado de cliente: está en el servidor.
export const useProductsStore = create((set) => ({
  products: [],
  fetchProducts: async () => {
    const res = await fetch("/api/products");
    set({ products: await res.json() });
  },
}));
Bien — cada tipo de estado, su herramienta 
// ✔ Los datos del servidor se piden donde se usan (o con una
//   librería de data fetching) y el store guarda solo estado de cliente.
function ProductList() {
  const [products, setProducts] = useState([]);

  useEffect(() => {
    fetch("/api/products")
      .then((res) => res.json())
      .then(setProducts);
  }, []);

  return <ul>{products.map((p) => <li key={p.id}>{p.name}</li>)}</ul>;
}

Error 3: cambiar de herramienta sin motivo

Mal — reescribir por moda 
Sprint 1: montamos Redux Toolkit para el carrito.
Sprint 3: "he leído que Zustand mola más". Reescritura completa.
Sprint 5: "Redux es el estándar". Otra reescritura. → deuda y bugs.
Bien — decidir una vez y justificar el cambio 
Elige según el problema, documenta por qué, y solo migra si hay
un motivo medible (rendimiento, mantenibilidad, onboarding del equipo).

Error 4: confundir estado global con estado compartido de dos componentes

Subir estado al componente padre (o a un hook común) suele ser mejor que crear un contexto para algo que solo comparten dos componentes hermanos.

Mal — contexto para dos hermanos 
// ✘ Crear un contexto solo para pasar un valor entre dos hijos.
const ValueContext = createContext();
function Parent() {
  const [value, setValue] = useState("");
  return (
    <ValueContext.Provider value={{ value, setValue }}>
      <Input />
      <Preview />
    </ValueContext.Provider>
  );
}
Bien — elevar el estado al padre común 
// ✔ El padre ya está ahí: pásalo por props.
function Parent() {
  const [value, setValue] = useState("");
  return (
    <>
      <Input value={value} onChange={setValue} />
      <Preview value={value} />
    </>
  );
}

7 · Ejercicio guiado

Este ejercicio no es de escribir código, sino de decidir: la habilidad más valiosa de esta lección. Después implementarás una de las decisiones.

  1. Lee estos cinco estados de una supuesta app de tareas y anota, para cada uno, la herramienta que elegirías y por qué (alcance + frecuencia):
    • (a) El texto que el usuario escribe en un input de nueva tarea.
    • (b) El tema claro/oscuro de la aplicación.
    • (c) La lista de tareas con sus etiquetas, prioridades y filtros (la comparten 6 componentes y cambia constantemente).
    • (d) El usuario logueado y su token.
    • (e) El filtro "solo completadas" que debe poder compartirse por enlace.
  2. Compara tus respuestas con la referencia: (a) useState local; (b) Context; (c) Redux Toolkit o Zustand; (d) Context (cambia poco); (e) estado en la URL (useSearchParams de React Router).
  3. Elige el estado (c), la lista de tareas global, e impleméntala con Zustand (o con el gestor que prefieras de los dos). Debe tener tasks y las acciones addTask, toggleTask y removeTask.
  4. Añade un selector derivado selectPendingCount que cuente las tareas no completadas, y otro selectByPriority(priority).
  5. Escribe dos componentes: uno que muestre el contador de pendientes y otro que permita alternar tareas. Comprueba con React DevTools que solo se re-renderiza el contador cuando cambia el número.
Ver solución de referencia (estado c con Zustand)
src/store/taskStore.js
import { create } from "zustand";

export const useTaskStore = create((set, get) => ({
  tasks: [],

  addTask: (title, priority = "media") =>
    set({
      tasks: [
        ...get().tasks,
        { id: crypto.randomUUID(), title, priority, done: false },
      ],
    }),

  toggleTask: (id) =>
    set({
      tasks: get().tasks.map((task) =>
        task.id === id ? { ...task, done: !task.done } : task
      ),
    }),

  removeTask: (id) =>
    set({ tasks: get().tasks.filter((task) => task.id !== id) }),
}));

// Selectores derivados, definidos fuera del componente.
export const selectPendingCount = (state) =>
  state.tasks.filter((task) => !task.done).length;

export const selectByPriority = (priority) => (state) =>
  state.tasks.filter((task) => task.priority === priority);
src/components/TaskCounter.jsx
import { useTaskStore, selectPendingCount } from "../store/taskStore";

export default function TaskCounter() {
  const pending = useTaskStore(selectPendingCount);
  return <p>Pendientes: {pending}</p>;
}
src/components/TaskList.jsx
import { useTaskStore } from "../store/taskStore";

export default function TaskList() {
  const tasks = useTaskStore((state) => state.tasks);
  const toggleTask = useTaskStore((state) => state.toggleTask);

  return (
    <ul>
      {tasks.map((task) => (
        <li key={task.id}>
          <input
            type="checkbox"
            checked={task.done}
            onChange={() => toggleTask(task.id)}
          />
          {task.title} ({task.priority})
        </li>
      ))}
    </ul>
  );
}

Lo que demuestra el ejercicio: decidir por tipo de estado, usar selectores para aislar re-renderizados, y usar estado derivado en lugar de duplicarlo. Con Redux Toolkit sería el mismo resultado con más piezas (slice + store + Provider).

8 · Reto

🎯 Especificación de estado de una app real

Elige una aplicación que conozcas bien (tu banco online, una red social, un reproductor de música, un gestor de tareas) e imagina que vas a reconstruirla como una SPA con React. Tu entregable es un documento de decisión de estado:

  • Una tabla con al menos 10 estados de la app, indicando para cada uno: descripción, alcance (local / compartido / global), frecuencia de cambio, y herramienta elegida.
  • Justifica en una frase por qué cada herramienta. Si algo puede confundir, explica por qué no usas la alternativa obvia.
  • Dibuja un diagrama ASCII con las capas de providers/stores que envolvías la app, en su orden correcto.
  • Señala qué estados van a la URL y por qué.

Pista: elige al menos un estado de cada tipo de la tabla "clasifica el estado" de la teoría, para que tu documento demuestre que sabes repartir, no solo elegir una herramienta para todo. Si te quedas sin ideas, pregúntate: ¿qué pasa si el usuario recarga la página en medio de esta pantalla? La respuesta te dirá si ese estado va a la URL, a un store persistente o no debe sobrevivir.

9 · Resumen

  • No hay una herramienta "mejor": hay una herramienta adecuada para cada tipo de estado.
  • Clasifica el estado primero: local, local complejo, compartido estable, global vivo, del servidor, o de la URL.
  • start simple: useState → useReducer → Context → Zustand/Redux, subiendo de nivel solo cuando aparece el dolor.
  • Context brilla con datos estables y pocos consumidores; sufre cuando el valor cambia mucho.
  • useReducer es para lógica local compleja (muchas acciones, un reducer claro).
  • Redux Toolkit gana en apps y equipos grandes: DevTools, middlewares, convenciones.
  • Zustand gana en simplicidad: sin Provider, selectores granulares y persistencia integrada.
  • Conviven: es normal usar Context para el tema y Redux/Zustand para el carrito en la misma app. Una responsabilidad, una herramienta.
  • El estado del servidor y el de la URL tienen sus propias herramientas; no los metas en el store global por defecto.

10 · Preguntas frecuentes

Si tengo dudas, ¿cuál elijo por defecto?
Para una app pequeña o mediana, Zustand es un excelente valor por defecto: es sencillo y cubre la mayoría de casos de estado global. Para una app grande con equipo numeroso y necesidad de convenciones, Redux Toolkit. Y si el estado es realmente simple y estable, no añadas nada: Context basta.
¿Puedo usar Context y Redux/Zustand a la vez?
Sí, es habitual. Un reparto típico: Context para el tema y el usuario (estable), un store para el carrito o el editor (cambia mucho). La clave es no duplicar la misma información en dos sitios: cada dato debe vivir en un único lugar.
¿Los filtros y la paginación van al store global o a la URL?
A la URL. Guardarlos como search params te da gratis tres cosas: enlaces compartibles, funcionan los botones atrás/adelante del navegador y recargar la página conserva el estado. El store global no te da nada de eso.
¿Y los datos de la API? ¿Redux o Zustand?
En principio, ni uno ni otro. Es estado del servidor: tiene caché, se invalida y se revalida. Usa fetch con estado local (como en el Módulo 9) o una librería de data fetching. Redux/Zustand son para estado de cliente. Si de verdad necesitas mezclarlos, mantén bien separada la "caché del servidor" del estado de UI.
¿Migramos a Zustand si ya tenemos Redux y funciona?
Solo si hay un motivo medible: el boilerplate de Redux te está frenando, el onboarding cuesta, o hay mucho código repetitivo. "Está de moda" no es un motivo. Si migras, hazlo incremental: mueve un dominio a la vez y documenta la decisión con un ADR.
