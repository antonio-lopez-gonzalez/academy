Vitest: fundamentos

Módulo 12 · Testing 🕐 35 minutos

1 · Introducción

Vitest es el framework de testing que nace dentro del ecosistema de Vite. Es la herramienta que usaremos durante todo el Módulo 12 para escribir y ejecutar pruebas. Su lema es sencillo: si tu código se ejecuta en Vite, tus tests deben ejecutarse en Vitest.

¿Por qué existe? Durante años, JavaScript testeó con Jest. El problema es que Jest trae su propio transformador: vuelve a compilar tu código con Babel o ts-jest, ignora la configuración de Vite y a menudo se atasca con ESM o con CSS importado. Vitest reutiliza el pipeline de Vite, así que no duplicas configuración ni mantienes dos sistemas de build distintos.

¿Qué problema resuelve? Pruebas que tardan demasiado, configuración duplicada, soporte de ESM roto y una experiencia de desarrollo (watch mode, HMR) que no reflejaba cómo se ejecuta la app real.

¿Cuándo se usa? Siempre que el proyecto use Vite (nuestro caso) o incluso en cualquier proyecto moderno de JavaScript/Node. Vitest es hoy una opción más que madura para tests unitarios e de integración.

Errores típicos antes de empezar: instalar dependencias con npm (nosotros usamos solo pnpm), olvidar environment: 'jsdom' cuando hay DOM, o creer que un test sirve para "comprobar la implementación" en lugar de documentar el comportamiento esperado.

2 · Teoría

Los tres niveles de pruebas

Antes de escribir un solo test, conviene saber qué estás probando. La pirámide clásica distingue tres niveles:

▲ ╱ ╲ E2E (Playwright/Cypress) → pocos, lentos, muy confiables ╱───╲ ╱ ╲ Integración → varios, medios ╱───────╲ ╱ ╲ Unitarios (Vitest) → muchos, rápidos, baratos ╱───────────╲ ─────────────── Vitest cubre los dos niveles de abajo. En este módulo nos centramos en unitarios (funciones) e integración (componentes + hooks).

¿Por qué Vitest y no Jest?

CriterioJestVitest
Transformación Babel / ts-jest (propia) Reutiliza Vite (esbuild)
Configuración Archivo jest.config.js aparte Bloque test dentro de vite.config.js
ESM nativo Con flags y fricción Sí, de serie
Velocidad Buena Muy alta (mismo motor que Vite)
API describe / it / expect Compatible con Jest
Analogía: el mismo motor

Es como probar un coche en el mismo circuito donde se va a conducir. Jest prueba tu código en un banco de pruebas ajeno al que realmente lo ejecuta; Vitest lo prueba con el motor real de Vite, así que lo que pasa en los tests es lo que pasa en producción.

Anatomía de un test

Vitest expone tres funciones globales (con globals: true) que puedes importar explícitamente o usar sin importar:

  • describe — agrupa tests relacionados. Se puede anidar.
  • it (alias de test) — define un caso concreto.
  • expect — construye la aserción mediante un matcher.

La estructura interna de un buen test sigue el patrón AAA: Arrange (preparar), Act (ejecutar) y Assert (comprobar).

Configuración en Vite

Vitest se configura en el mismo archivo que Vite. No necesitas nada más:

vite.config.js
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  test: {
    // Simula un navegador para poder renderizar React
    environment: "jsdom",
    // No hace falta importar describe/it/expect en cada archivo
    globals: true,
    // Se ejecuta antes de la suite (matchers extra, limpieza, etc.)
    setupFiles: ["./src/test/setup.js"],
    // Limpia los mocks entre tests automáticamente
    clearMocks: true,
  },
});

Ciclo de vida de la suite

Vitest ofrece hooks que se ejecutan en momentos concretos. Sirven para preparar y limpiar estado:

  • beforeAll / afterAll — una vez por suite.
  • beforeEach / afterEach — antes/después de cada test.
Aislamiento ante todo

Cada test debe poder ejecutarse solo y en cualquier orden. Si un test depende del estado que dejó otro, tienes un test frágil. Limpia en afterEach y usa beforeEach para partir siempre del mismo punto.

3 · Ejemplo mínimo

Empecemos por la prueba más pequeña posible: una función pura.

src/utils/math.js
// Una función pura: mismo input, mismo output, sin efectos secundarios
export function sum(a, b) {
  return a + b;
}

export function multiply(a, b) {
  return a * b;
}
src/utils/math.test.js
import { describe, it, expect } from "vitest";
import { sum, multiply } from "./math";

// describe agrupa los tests de una misma unidad
describe("sum", () => {
  it("suma dos números positivos", () => {
    // Arrange / Act: ejecutamos la función
    const result = sum(2, 3);
    // Assert: comprobamos el resultado esperado
    expect(result).toBe(5);
  });

  it("maneja números negativos", () => {
    expect(sum(-1, 1)).toBe(0);
  });
});

describe("multiply", () => {
  it("multiplica dos números", () => {
    expect(multiply(3, 4)).toBe(12);
  });
});

Línea por línea:

  1. import { describe, it, expect } from "vitest": aunque tengas globals: true, importarlos explícitamente hace el archivo autosuficiente.
  2. describe("sum", ...): agrupa los casos de la función sum. El nombre es solo documentación, aparece en el reporte.
  3. it("suma dos números positivos", ...): un caso concreto descrito en lenguaje natural.
  4. expect(result).toBe(5): la aserción. toBe usa ===, perfecto para números.
  5. Por qué funciona: sum es pura; no hay DOM, ni red, ni estado. Es el test ideal: rápido, determinista y sin mocks.

4 · Ejemplo real

En TaskFlow tenemos una capa de lógica pura que filtra y resume tareas. Vamos a probarla como lo haríamos en un proyecto profesional: con it.each, toEqual y una prueba asíncrona.

src/features/tasks/taskFilters.js
// Filtra tareas según el estado activo y un texto de búsqueda
export function filterTasks(tasks, { status = "all", query = "" } = {}) {
  const normalized = query.trim().toLowerCase();

  return tasks.filter((task) => {
    const matchesStatus =
      status === "all" ||
      (status === "completed" && task.completed) ||
      (status === "pending" && !task.completed);

    const matchesQuery =
      normalized === "" || task.title.toLowerCase().includes(normalized);

    return matchesStatus && matchesQuery;
  });
}

// Devuelve un resumen con el recuento por estado
export function taskStats(tasks) {
  return {
    total: tasks.length,
    completed: tasks.filter((t) => t.completed).length,
    pending: tasks.filter((t) => !t.completed).length,
  };
}
src/features/tasks/taskFilters.test.js
import { describe, it, expect } from "vitest";
import { filterTasks, taskStats } from "./taskFilters";

// Fixture: datos de ejemplo reutilizables en todos los tests
const tasks = [
  { id: 1, title: "Diseñar el login", completed: false },
  { id: 2, title: "Escribir tests de la API", completed: true },
  { id: 3, title: "Revisar el login social", completed: false },
];

describe("filterTasks", () => {
  it('devuelve todas las tareas con status "all"', () => {
    expect(filterTasks(tasks)).toHaveLength(3);
  });

  it("filtra por estado completed", () => {
    const result = filterTasks(tasks, { status: "completed" });
    // Comparamos objetos: hay que usar toEqual, no toBe
    expect(result).toEqual([tasks[1]]);
  });

  it("filtra por texto de búsqueda sin distinguir mayúsculas", () => {
    const result = filterTasks(tasks, { query: "LOGIN" });
    expect(result.map((t) => t.id)).toEqual([1, 3]);
  });

  // it.each genera un test por cada caso de la tabla
  it.each([
    [{ status: "all" }, 3],
    [{ status: "completed" }, 1],
    [{ status: "pending" }, 2],
  ])("con %o devuelve %i tareas", (filters, expected) => {
    expect(filterTasks(tasks, filters)).toHaveLength(expected);
  });
});

describe("taskStats", () => {
  it("calcula el resumen de tareas", () => {
    expect(taskStats(tasks)).toEqual({ total: 3, completed: 1, pending: 2 });
  });

  it("devuelve ceros para una lista vacía", () => {
    expect(taskStats([])).toEqual({ total: 0, completed: 0, pending: 0 });
  });
});

Decisiones explicadas:

  • Fixture compartida: el array tasks se declara una vez y todos los tests lo usan como referencia estable.
  • toEqual para arrays/objetos: compara estructura profunda; toBe fallaría porque son referencias distintas.
  • it.each: convierte una tabla de casos en varios tests, con nombres legibles (%o imprime el objeto, %i el número).
  • Solo lógica pura: no hay React ni red aquí. Este tipo de test es el más rápido y el que más veces escribirás.
El patrón que se repite

Toda la lógica de negocio (filtros, ordenaciones, cálculos, validaciones) debería vivir en funciones puras como estas y probarse con Vitest. Cuanto más saques la lógica fuera de los componentes, más fácil será probarla.

5 · Buenas prácticas

HazEvitaPor qué
Escribe el nombre del test en lenguaje natural ("calcula el total con IVA") Nombres crípticos como "test1" El reporte de Vitest es documentación: debe contarse en frases.
Un comportamiento por test Test gigantes con 20 aserciones Si falla, sabes exactamente qué rompió.
Usa toEqual para objetos/arrays toBe para comparar objetos toBe compara referencia; dos objetos iguales no son la misma referencia.
Aísla cada test (datos frescos en beforeEach) Compartir estado mutable entre tests Tests que dependen del orden son frágiles y difíciles de depurar.
Prueba el comportamiento observable Probar detalles internos de implementación Un test acoplado a la implementación se rompe con cada refactor sin aportar valor.
Por qué importa el aislamiento

Vitest puede ejecutar archivos en paralelo y en distinto orden. Si tus tests comparten estado, el resultado cambia de una ejecución a otra: aparecen los temidos flaky tests.

6 · Errores habituales

Error 1: usar toBe para comparar objetos

✘ Incorrecto 
// toBe compara la referencia, no el contenido
const result = { id: 1, title: "Tarea" };
expect(result).toBe({ id: 1, title: "Tarea" }); // 💥 Falla siempre
✔ Correcto 
// toEqual hace comparación profunda
expect(result).toEqual({ id: 1, title: "Tarea" }); // ✅

Error 2: olvidar el await en tests asíncronos

✘ Incorrecto 
it("carga las tareas", () => {
  // Sin await, el test termina antes de que la promesa se resuelva
  const tasks = fetchTasks();        // 💥 tasks es una Promise
  expect(tasks).toHaveLength(2);     // Falla o da falso positivo
});
✔ Correcto 
it("carga las tareas", async () => {
  const tasks = await fetchTasks();  // ✅ esperamos la promesa
  expect(tasks).toHaveLength(2);
});

Error 3: tests que dependen del orden de ejecución

✘ Incorrecto 
// Estado mutable compartido: el segundo test depende del primero
let counter = 0;

it("incrementa", () => {
  counter++;
  expect(counter).toBe(1); // 💥 falla si el orden cambia
});
✔ Correcto 
// Cada test parte del mismo estado inicial
let counter;

beforeEach(() => {
  counter = 0; // ✅ estado fresco en cada test
});

it("incrementa", () => {
  counter++;
  expect(counter).toBe(1);
});

7 · Ejercicio guiado

Vamos a probar una utilidad típica: convertir un título en un slug para URLs.

  1. Crea src/utils/slugify.js con una función slugify(text) que: pase a minúsculas, quite tildes, reemplace espacios por guiones y elimine caracteres no válidos.

  2. Crea src/utils/slugify.test.js e importa la función.

  3. Escribe un test para una cadena simple: slugify("Hola Mundo") debe ser "hola-mundo".

  4. Añade un test con tildes y mayúsculas: slugify("Programación en Español") debe ser "programacion-en-espanol".

  5. Añade un test para espacios múltiples y signos: slugify(" React 19!! ") debe ser "react-19".

  6. Ejecuta pnpm vitest run y comprueba que los tres pasan. Detecta si falta algún caso límite.

Solución:

src/utils/slugify.js
export function slugify(text) {
  return text
    .normalize("NFD")            // separa las tildes de la letra base
    .replace(/[\u0300-\u036f]/g, "") // elimina los signos diacríticos
    .toLowerCase()
    .trim()
    .replace(/[^a-z0-9\s-]/g, "")    // quita lo que no sea letra/número/espacio/guion
    .replace(/\s+/g, "-")            // espacios → guiones
    .replace(/-+/g, "-");            // colapsa guiones repetidos
}
src/utils/slugify.test.js
import { describe, it, expect } from "vitest";
import { slugify } from "./slugify";

describe("slugify", () => {
  it("convierte un título simple", () => {
    expect(slugify("Hola Mundo")).toBe("hola-mundo");
  });

  it("elimina tildes y pasa a minúsculas", () => {
    expect(slugify("Programación en Español")).toBe("programacion-en-espanol");
  });

  it("limpia espacios y signos de puntuación", () => {
    expect(slugify("  React 19!!  ")).toBe("react-19");
  });
});
Truco de depuración

Si un matcher falla, Vitest muestra el valor recibido y el esperado en un diff. Ejecuta en watch mode con pnpm vitest y el runner se re-ejecuta al guardar, así iteras sin salir del editor.

🎯 Matchers propios y cobertura

Amplía la utilidad slugify del ejercicio anterior con este reto (no lo resuelvas todavía; inténtalo y luego compara):

  1. Opción de longitud máxima: añade un segundo parámetro { maxLength } que trunque el slug sin cortar una palabra a medias.

9 · Resumen

  • Vitest es el runner de tests nativo de Vite: no duplica configuración y soporta ESM de serie.
  • Se configura en el bloque test de vite.config.js (environment, globals, setupFiles).
  • Anatomía: describe agrupa, it define un caso, expect verifica con matchers.
  • toBe para primitivos, toEqual para objetos y arrays.
  • it.each genera varios tests desde una tabla de casos.
  • Hooks beforeEach/afterEach garantizan aislamiento entre tests.
  • Ejecuta con pnpm test (watch) o pnpm test:run (una sola vez).

10 · Preguntas frecuentes

¿Necesito importar describe/it/expect si tengo globals: true?

No es obligatorio, pero importarlos explícitamente desde "vitest" hace el archivo autosuficiente, mejora el autocompletado y evita errores cuando copias un test a un proyecto sin globals. Es la práctica recomendada.

¿Dónde van los archivos de test?

Vitest detecta por defecto *.test.js(x) y *.spec.js(x). Puedes colocarlos junto al código (co-location) o en una carpeta __tests__. En el curso usaremos ambas según convenga; lo importante es ser consistente.

¿Qué diferencia hay entre prueba unitaria e integración?

La unitaria prueba una pieza aislada (una función pura). La de integración prueba varias piezas juntas (un componente con su estado y eventos). Vitest sirve para las dos; en la siguiente lección añadiremos React Testing Library para el nivel de integración.

¿Puedo probar código asíncrono con promesas?

Sí. Marca el test como async y usa await. Para esperar a que una promesa rechace se usa await expect(promise).rejects.toThrow(...), y para el camino feliz await expect(promise).resolves.toEqual(...).

¿Vitest reemplaza a Jest en todos los proyectos?

No es obligatorio, pero en proyectos Vite es claramente superior porque comparte el pipeline de build. Su API es compatible con Jest, así que migrar suele ser cuestión de mover la configuración al vite.config.js.
