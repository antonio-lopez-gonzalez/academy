Inmutabilidad: por qué es sagrada

Módulo 4 · Estado ⏱ 30 minutos

1 · Introducción

En la lección anterior aprendiste el cómo: spread, filter, map. Hoy entendemos el por qué profundo. ¿Por qué React es tan estricto con la inmutabilidad? ¿Por qué no puede simplemente «ver» que cambiaste el array? ¿Y por qué otros frameworks (Vue, Angular) no tienen esta restricción?

La respuesta está en cómo JavaScript maneja los datos y en cómo React decide si debe re-renderizar. Entender esto te dará una intuición sólida para predecir el comportamiento de React, no solo seguir reglas. Y te ahorrará horas de depuración de bugs sutiles donde «la pantalla no se actualiza aunque el estado cambió».

⚠ La regla de oro (repetida porque es sagrada)

NUNCA mutar el estado directamente. Ni push, ni sort, ni item.done = true. Siempre crear un array/objeto NUEVO. Esta lección explica por qué es tan importante.

2 · Teoría

Valores vs referencias (repaso rápido)

En JavaScript, los primitivos (number, string, boolean) se copian por valor: let b = a crea una copia independiente. Los objetos (arrays, objetos, funciones) se copian por referencia: let b = a hace que ambos apunten al MISMO objeto en memoria. 

// Primitivos: copias independientes
let a = 5;
let b = a;
b = 10;
console.log(a); // 5 (a no cambió)

// Objetos: referencias compartidas
let arr1 = [1, 2, 3];
let arr2 = arr1;      // arr2 apunta al MISMO array
arr2.push(4);
console.log(arr1);    // [1, 2, 3, 4] (¡arr1 también cambió!)
console.log(arr1 === arr2); // true (misma referencia)

Esto es fundamental: cuando haces items.push(x), estás modificando el array original. Si ese array es el estado de React, has mutado el estado.

Cómo React detecta cambios: comparación por referencia

Cuando llamas a setItems(newItems), React compara el valor anterior con el nuevo usando Object.is (similar a === pero maneja NaN correctamente). Si la referencia es la misma, React asume que nada cambió y no re-renderiza. 

function addItem() {
  items.push(newItem);      // muta el array del estado
  setItems(items);          // misma referencia → React no repinta
}

function addItemCorrect() {
  setItems([...items, newItem]);  // array nuevo → React re-renderiza
}
COMPARACIÓN DE REFERENCIAS EN REACT ──────────────────────────────────── Estado anterior: items = [1, 2, 3] (referencia A) Nuevo estado: items = [1, 2, 3] (referencia A, mutado) Object.is(A, A) → true → React asume "nada cambió" → NO re-render Estado anterior: items = [1, 2, 3] (referencia A) Nuevo estado: items = [1, 2, 3, 4] (referencia B, array nuevo) Object.is(A, B) → false → React detecta cambio → RE-RENDER

Por eso mutar es invisible para React: la referencia no cambia, aunque el contenido sí. React no inspecciona el contenido del array (sería caro); solo compara referencias.

¿Qué pasa cuando mutas? El bug clásico

Cuando mutas el estado, ocurren tres problemas:

  1. React no re-renderiza: la UI se queda congelada mostrando el estado viejo.
  2. El estado se corrompe en silencio: el array/objeto ha cambiado, pero React no lo sabe. Si luego haces una actualización inmutable, los cambios ocultos aparecen «de golpe».
  3. Los componentes hijos no se actualizan: si pasas el array mutado como prop, los hijos reciben la misma referencia y React.memo (Módulo 11) no los re-renderiza.

El demo MutationLab en ejemplos/m04-estado muestra esto en vivo: un botón muta (la pantalla no cambia) y el otro es inmutable (la pantalla se actualiza). Si pulsas el botón malo varias veces y luego el bueno, verás aparecer «de golpe» los valores corruptos.

«Copiar no es caro»: structural sharing

Una objeción común: «¿no es ineficiente copiar arrays grandes todo el tiempo?» No tanto como parece. Primero, copiar un array de 1000 elementos cuesta microsegundos (son referencias, no copias profundas). Segundo, React usa structural sharing: cuando haces [...items, newItem], solo copias las referencias a los elementos existentes, no los objetos completos.

STRUCTURAL SHARING (compartir estructura) ────────────────────────────────────────── items = [obj1, obj2, obj3] (referencias a objetos) [...items, obj4] crea: nuevoArray = [ref→obj1, ref→obj2, ref→obj3, ref→obj4] ↑ ↑ ↑ └───────────┴───────────┴─── MISMAS referencias (no se copian los objetos) Solo se crea un array nuevo; los objetos internos se comparten.

Por eso la inmutabilidad es barata en la práctica. Lo caro es tocar el DOM, y React solo toca lo que cambió (gracias al diffing del Virtual DOM).

Tabla de métodos: mutantes vs inmutables

JavaScript tiene métodos que mutan el array original y otros que devuelven uno nuevo. En React, solo usamos los segundos:

Operación✘ Mutante (prohibido)✔ Inmutable (seguro)
Añadir al final arr.push(x) [...arr, x]
Añadir al inicio arr.unshift(x) [x, ...arr]
Borrar por índice arr.splice(i, 1) arr.filter((_, idx) => idx !== i)
Ordenar arr.sort(fn) [...arr].sort(fn) o arr.toSorted(fn)
Invertir arr.reverse() [...arr].reverse() o arr.toReversed()
Rellenar arr.fill(x) Array(arr.length).fill(x)

Los métodos toSorted y toReversed (ES2023) son inmutables por diseño. Si tu entorno los soporta, úsalos. Si no, el patrón [...arr].sort() funciona siempre.

Spread es copia SUPERFICIAL (el gotcha de anidados)

El spread ({'{ ...obj }'}) copia solo el primer nivel. Si tienes objetos anidados, necesitas spread en cada nivel: 

const state = {
  user: { name: "Ada", address: { city: "London", zip: "12345" } },
};

// ✘ INCORRECTO: spread superficial no copia address
const newState = { ...state, user: { ...state.user, name: "Grace" } };
// newState.user.address === state.user.address (misma referencia)
// Si luego mutas newState.user.address.city, también cambias state.user.address.city

// ✔ CORRECTO: spread en cada nivel
const correctState = {
  ...state,
  user: {
    ...state.user,
    address: { ...state.user.address, city: "Paris" },
  },
};
// Ahora address es un objeto nuevo, independiente

Si tienes más de 2-3 niveles de anidación, el spread manual se vuelve verboso y propenso a errores. Considera aplanar el estado (normalizar) o usar useReducer (Módulo 10) con una librería como Immer.

Comparación con otros lenguajes

  • .NET (C#): los record types son inmutables por defecto. El operador with (var nuevo = persona with { Nombre = "Grace" }) es el equivalente al spread de JavaScript. La filosofía es la misma: datos inmutables = menos bugs.
  • Java: String es inmutable (cada operación crea uno nuevo). Las colecciones mutables (ArrayList) son la norma, pero hay librerías como Immutables o Vavr para colecciones persistentes.
  • Python: las tuplas son inmutables; las listas, mutables. No hay enforcement del lenguaje, pero las convenciones de «no mutar argumentos» son comunes en código funcional.
  • Rust: la inmutabilidad es el default (let x = 5 es inmutable; necesitas let mut x = 5 para mutar). El compilador te obliga a pensar en mutabilidad.

3 · Ejemplo mínimo

El laboratorio de mutación: dos botones que hacen «lo mismo», pero uno muta y el otro no. Ejecutable en ejemplos/m04-estado (sección 4):

src/components/MutationLab.jsx
import { useState } from "react";

export default function MutationLab() {
  const [numbers, setNumbers] = useState([1, 2, 3]);

  function nextValue() {
    return Math.max(...numbers) + 1;
  }

  function addMutating() {
    numbers.push(nextValue()); // ✘ MUTA el array actual
    setNumbers(numbers);       // ✘ MISMA referencia → React no repinta
  }

  function addImmutable() {
    // ✔ Array NUEVO con spread → referencia distinta → re-render
    setNumbers([...numbers, nextValue()]);
  }

  return (
    <div>
      <p>Números: [{numbers.join(", ")}]</p>
      <button onClick={addMutating}>Añadir mutando (✘)</button>
      <button onClick={addImmutable}>Añadir sin mutar (✔)</button>
      <button onClick={() => setNumbers([1, 2, 3])}>Reset</button>
    </div>
  );
}

Cómo probarlo:

  1. Pulsa «Añadir mutando (✘)» tres veces: la pantalla NO cambia… pero el array SÍ se está corrompiendo en silencio.
  2. Pulsa «Añadir sin mutar (✔)»: aparecen DE GOLPE los números ocultos que el botón malo había metido. Ese es el bug clásico.
  3. Conclusión: mutar no rompe React, pero crea un estado «fantasma» que aparece cuando menos lo esperas.

4 · Ejemplo real

Un mini tablero Kanban (estilo Trello): columnas con tareas, y la operación de mover una tarea de una columna a otra. Es el caso real más complejo de inmutabilidad: estado anidado (columnas → tareas) y actualización en dos sitios a la vez.

src/components/MiniKanban.jsx
import { useState } from "react";

const INITIAL_BOARD = {
  todo: {
    title: "Por hacer",
    tasks: [
      { id: 1, text: "Diseñar la base de datos" },
      { id: 2, text: "Implementar el login" },
    ],
  },
  doing: {
    title: "En progreso",
    tasks: [{ id: 3, text: "Escribir tests" }],
  },
  done: {
    title: "Completado",
    tasks: [],
  },
};

export default function MiniKanban() {
  const [board, setBoard] = useState(INITIAL_BOARD);

  // Mover una tarea de una columna a otra (inmutable en 3 niveles)
  function moveTask(taskId, fromColumn, toColumn) {
    // 1. Encontrar la tarea en la columna origen
    const task = board[fromColumn].tasks.find((t) => t.id === taskId);
    if (!task) return;

    setBoard({
      ...board,  // nivel 1: copiar el board
      [fromColumn]: {
        ...board[fromColumn],  // nivel 2: copiar la columna origen
        tasks: board[fromColumn].tasks.filter((t) => t.id !== taskId),  // quitar la tarea
      },
      [toColumn]: {
        ...board[toColumn],  // nivel 2: copiar la columna destino
        tasks: [...board[toColumn].tasks, task],  // añadir la tarea
      },
    });
  }

  return (
    <div className="kanban">
      {Object.entries(board).map(([columnKey, column]) => (
        <div key={columnKey} className="column">
          <h3>{column.title}</h3>
          <ul>
            {column.tasks.map((task) => (
              <li key={task.id}>
                {task.text}
                <div>
                  {/* Botones para mover a otras columnas */}
                  {columnKey !== "todo" && (
                    <button onClick={() => moveTask(task.id, columnKey, "todo")}>
                      ← Todo
                    </button>
                  )}
                  {columnKey !== "doing" && (
                    <button onClick={() => moveTask(task.id, columnKey, "doing")}>
                      → Doing
                    </button>
                  )}
                  {columnKey !== "done" && (
                    <button onClick={() => moveTask(task.id, columnKey, "done")}>
                      → Done
                    </button>
                  )}
                </div>
              </li>
            ))}
          </ul>
        </div>
      ))}
    </div>
  );
}

Decisiones explicadas:

  • Estado anidado en 3 niveles: board → columnas → tareas. Cada nivel necesita spread para ser inmutable.
  • moveTask actualiza DOS columnas a la vez: quita la tarea de fromColumn y la añade a toColumn. Ambas actualizaciones en UN solo setBoard (batching automático).
  • Computed property names: [fromColumn] y [toColumn] permiten usar variables como keys del objeto. Es ES6, y es idiomático en React.
  • Object.entries(board): convierte el objeto en array de [key, value] para poder usar map. Patrón común para renderizar objetos.
  • Keys por columnKey y taskId: ambos son estables y únicos. Si usáramos índices, reordenar columnas rompería la reconciliación.
📌 Conexión con el proyecto final

Este mini Kanban es una versión simplificada de TaskFlow, la app que construiremos en el Módulo 13. Allí usaremos un backend .NET 8, pero el frontend manejará el estado del tablero exactamente así: inmutable, con spread en múltiples niveles.

5 · Buenas prácticas

HazEvitaPor qué
Tratar el estado como read-only: nunca asignar a sus propiedades state.items.push(x), state.user.name = "nuevo" Cualquier mutación es invisible para React. Siempre crear copias.
Usar const para el estado (ya lo hace useState) let [items, setItems] = useState([]) Refuerza mentalmente que el estado no se reasigna, solo se reemplaza con el setter.
Aplanar el estado si tiene más de 2-3 niveles de anidación Objetos profundamente anidados con spread manual El spread profundo es verboso y propenso a errores. Estado plano = más simple.
Considerar useReducer + Immer para estado complejo (Módulo 10) Spread manual en 4+ niveles Immer te deja escribir código «como si mutaras» y produce objetos inmutables.
Keys estables por id, no por índice key={index} si el array se reordena React usa la key para reconciliar. Índices inestables = bugs de UI.

6 · Errores habituales

Error 1: sort() directo sobre el array del estado

✘ Incorrecto 
function sortTasks() {
  tasks.sort((a, b) => a.text.localeCompare(b.text));  // ✘ muta in-place
  setTasks(tasks);  // misma referencia → React no repinta
}
✔ Correcto 
function sortTasks() {
  setTasks([...tasks].sort((a, b) => a.text.localeCompare(b.text)));  // ✔ copia primero
  // o en ES2023: setTasks(tasks.toSorted((a, b) => a.text.localeCompare(b.text)));
}

Error 2: push + set con la misma referencia

✘ Incorrecto 
function addItem() {
  items.push(newItem);  // ✘ muta
  setItems(items);      // misma referencia → no repinta
}
✔ Correcto 
function addItem() {
  setItems([...items, newItem]);  // ✔ array nuevo
}

Error 3: shallow copy + mutar anidado

✘ Incorrecto 
// state = { user: { name, address: { city } } }
function updateCity(newCity) {
  const copy = { ...state };  // copia superficial
  copy.user.address.city = newCity;  // ✘ muta el objeto anidado (compartido)
  setState(copy);
}
✔ Correcto 
function updateCity(newCity) {
  setState({
    ...state,
    user: {
      ...state.user,
      address: { ...state.user.address, city: newCity },  // ✔ spread en cada nivel
    },
  });
}

Error 4: mutar dentro de map

✘ Incorrecto 
function toggleDone(id) {
  setTasks(
    tasks.map((task) => {
      if (task.id === id) {
        task.done = !task.done;  // ✘ muta el objeto task
      }
      return task;  // devuelve el mismo objeto mutado
    })
  );
}
✔ Correcto 
function toggleDone(id) {
  setTasks(
    tasks.map((task) =>
      task.id === id
        ? { ...task, done: !task.done }  // ✔ objeto nuevo con spread
        : task
    )
  );
}

Error 5: pensar que spread copia profundo

✘ Incorrecto 
const original = { a: { b: { c: 1 } } };
const copy = { ...original };
copy.a.b.c = 2;  // ✘ también cambia original.a.b.c (spread es superficial)
console.log(original.a.b.c);  // 2 (¡sorpresa!)
✔ Correcto 
const original = { a: { b: { c: 1 } } };
const copy = {
  ...original,
  a: {
    ...original.a,
    b: { ...original.a.b, c: 2 },  // ✔ spread en cada nivel
  },
};
console.log(original.a.b.c);  // 1 (independiente)

7 · Ejercicio guiado

El código roto: te doy un componente de tareas con bugs de mutación. Tu trabajo es arreglarlo paso a paso.

src/components/BrokenTodo.jsx (con bugs)
import { useState } from "react";

export default function BrokenTodo() {
  const [tasks, setTasks] = useState([
    { id: 1, text: "Aprender React", done: false },
    { id: 2, text: "Construir un proyecto", done: false },
  ]);

  function addTask(text) {
    tasks.push({ id: Date.now(), text, done: false });  // BUG 1: muta
    setTasks(tasks);  // misma referencia
  }

  function toggleTask(id) {
    const task = tasks.find((t) => t.id === id);
    task.done = !task.done;  // BUG 2: muta el objeto
    setTasks([...tasks]);  // array nuevo, pero el objeto interno es el mismo mutado
  }

  function sortTasks() {
    tasks.sort((a, b) => a.text.localeCompare(b.text));  // BUG 3: muta in-place
    setTasks(tasks);
  }

  return (
    <div>
      <button onClick={() => addTask("Nueva tarea")}>Añadir</button>
      <button onClick={sortTasks}>Ordenar</button>
      <ul>
        {tasks.map((task) => (
          <li key={task.id} onClick={() => toggleTask(task.id)}>
            {task.done ? "✔" : "○"} {task.text}
          </li>
        ))}
      </ul>
    </div>
  );
}

  1. Identifica los 3 bugs: addTask usa push, toggleTask muta task.done, sortTasks usa sort directo.

  2. Arregla addTask: reemplaza tasks.push(...) + setTasks(tasks) por setTasks([...tasks, newTask]).

  3. Arregla toggleTask: usa map con spread: tasks.map(t => t.id === id ? { ...t, done: !t.done } : t).

  4. Arregla sortTasks: copia primero con [...tasks].sort(...) o usa tasks.toSorted(...).

  5. Prueba: añade 3 tareas, ordénalas, marca una como completada. Verifica que todo funciona sin bugs de UI congelada.

8 · Reto

🎯 Historial de deshacer (undo)

Crea un componente UndoableCounter con un contador y un historial de los últimos 5 valores. Cada vez que el contador cambia, guarda el valor anterior en el historial (inmutable: [...history, previousValue]). Botones:

  1. +1 / −1: cambian el contador y añaden al historial.
  2. Deshacer: restaura el último valor del historial y lo quita del array (history.slice(0, -1)).
  3. Limitar a 5: si el historial supera 5 elementos, quita el más antiguo (history.slice(-5) o [...history.slice(1), newValue]).

Bonus: muestra el historial como una lista de botones clicables que restauran ese valor específico (no solo el último).

9 · Resumen

  • La inmutabilidad es sagrada en React porque detecta cambios comparando referencias (Object.is), no contenido.
  • Mutar el estado es invisible para React: la referencia no cambia, aunque el contenido sí. Resultado: UI congelada, estado corrupto en silencio.
  • Toolkit inmutable: spread para copiar, filter para borrar, map para actualizar, [...arr].sort() para ordenar.
  • Spread es superficial: copia solo el primer nivel. Para objetos anidados, necesitas spread en cada nivel.
  • «Copiar no es caro»: structural sharing hace que solo se creen nuevas referencias, no copias profundas de los objetos.
  • Si el estado es muy anidado (3+ niveles), considera aplanarlo o usar useReducer + Immer (Módulo 10).
  • Comparación con otros lenguajes: C# tiene record + with; Rust tiene inmutabilidad por defecto; Java tiene String inmutable.

10 · Preguntas frecuentes

¿Por qué React no inspecciona el contenido del array para ver si cambió?

Sería caro. Comparar dos arrays de 10.000 elementos elemento-por-elemento cuesta mucho más que comparar dos referencias (que es O(1)). React apuesta por «re-ejecutar funciones baratas + diffing» en vez de «inspeccionar contenido profundo». Es un trade-off consciente.

¿Puedo usar structuredClone para copiar profundo?

Sí, structuredClone(obj) hace una copia profunda real (incluyendo fechas, maps, sets). Pero es más caro que spread y no siempre necesario. Úsalo solo si necesitas clonar objetos muy anidados y no quieres spread manual en 5 niveles.

¿Vue no tiene este problema? ¿Por qué?

Vue usa reactividad profunda con proxies: cuando haces state.items.push(x), el proxy intercepta la mutación y notifica a Vue. React no usa proxies (por simplicidad y rendimiento); prefiere que le des un objeto nuevo. Ambos enfoques son válidos; React es más explícito.

¿Immer es «hacer trampa»?

No: Immer es una librería profesional que te deja escribir código «como si mutaras» y produce objetos inmutables por detrás (usando proxies y structural sharing). Redux Toolkit la incluye por defecto. Para useState puro, el spread es suficiente; para estado complejo, Immer es una herramienta legítima.

¿Por qué en .NET (Blazor) no necesito inmutabilidad?

Blazor usa StateHasChanged() explícito: tú decides cuándo re-renderizar, no hay detección automática de cambios. Puedes mutar listas y llamar a StateHasChanged(), y Blazor re-renderiza. React es más automático (los setters disparan renders), pero a cambio exige inmutabilidad para detectar cambios.
