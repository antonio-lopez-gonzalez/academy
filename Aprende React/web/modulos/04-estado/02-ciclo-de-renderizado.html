El ciclo de renderizado y el batching

Módulo 4 · Estado ⏱ 35 minutos

1 · Introducción

En la lección anterior aprendiste que setCount(count + 1) «cambia el estado y repinta». Hoy abrimos el capó: qué ocurre exactamente entre que llamas al setter y el usuario ve el nuevo número. Es la lección que separa a quien «escribe React» de quien entiende React.

Y resolveremos el acertijo más famoso de React. Mira este manejador y di en voz alta cuánto vale el contador tras un click (empieza en 0): 

function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}

¿3? No: 1. Las tres llamadas leen la misma fotografía del estado (la de este render, donde count vale 0) y las tres piden lo mismo: «que sea 1». Este comportamiento —y su solución, la actualización funcional— es el corazón de la lección. Además descubrirás el batching: esas tres llamadas provocan UN solo re-render, no tres, porque React espera a que tu manejador termine.

📌 Por qué te importa

Casi todos los bugs «de estado raro» en React —contadores que no cuentan, formularios que se comen letras, datos que llegan tarde— son en realidad malentendidos del ciclo de renderizado. Entenderlo ahora te ahorra cientos de horas de depuración.

2 · Teoría

Render = ejecutar tu función

Primero, precisemos el vocabulario. Renderizar es que React llame a tu función componente y obtenga el JSX que describe la pantalla. Nada más: es una llamada a una función de JavaScript. Lo que devuelve es una descripción de la UI (elementos React), no píxeles.

Solo hay DOS situaciones que disparan un render:

  1. El render inicial: cuando el componente aparece por primera vez en el árbol.
  2. Un setter de estado (de este componente o de un padre que le pasa props nuevas). Ninguna otra cosa re-renderiza.

Las dos fases: render y commit

Internamente, cada actualización tiene dos fases muy distintas:

SETTER LLAMADO (en un evento) │ ▼ ┌────────────────────────────────────────────────┐ │ FASE 1 · RENDER (pura, en memoria) │ │ · React ejecuta tu componente con el estado │ │ NUEVO y obtiene el JSX resultante │ │ · Lo compara con el JSX anterior (diffing) │ │ · Calcula la lista MÍNIMA de cambios │ │ · Aquí NO se toca el DOM todavía │ └──────────────────────┬─────────────────────────┘ ▼ ┌────────────────────────────────────────────────┐ │ FASE 2 · COMMIT (imperativa, sobre el DOM) │ │ · React aplica al DOM real SOLO las │ │ diferencias encontradas │ │ · Solo si NO hay diferencias, el commit │ │ no ocurre (el navegador ni se entera) │ └──────────────────────┬─────────────────────────┘ ▼ El navegador PINTA (paint)

Fíjate en la consecuencia práctica: render no es sinónimo de repintar. Si un re-render produce el mismo JSX que antes (por ejemplo, haces setCount(0) cuando ya valía 0), React ejecuta tu función, compara, ve que nada cambió y no toca el DOM. Por eso los re-renders «de más» son mucho más baratos de lo que la intuición dice — y por eso en el Módulo 11 insistiremos en no optimizar hasta medir.

El estado es una instantánea (snapshot) del render

Este es el modelo mental correcto. En cada render, tus variables de estado son constantes congeladas con el valor de ESE render. No son «cajas» que miran al valor vivo; son fotos. Cuando llamas a setCount(1) no estás editando la foto actual: estás encargando un nuevo render en el que count valdrá 1. 

function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    // "count" aquí dentro es la FOTO de este render: 0.
    // Las tres líneas piden lo mismo: "próximo render con 0 + 1".
    // Resultado tras el click: 1.
  }

  return <button onClick={handleClick}>{count}</button>;
}

Una analogía: tu componente es un pintor, cada render es un cuadro y el estado es el modelo que posa. setCount no retoca el cuadro terminado: le dice al modelo «cambia de pose para el siguiente cuadro». El cuadro actual (este render) queda como está hasta el final.

Batching: React espera a que termines

Si cada setter provocara un render inmediato, tres setters serían tres renders (y tres commits). React es más listo: acumula todas las actualizaciones de estado que ocurren en el mismo manejador y las procesa juntas, en UN solo render, cuando la función termina. A eso lo llamamos batching (procesamiento por lotes). 

function handleSave() {
  setName(input.value);      // ┐
  setEmail(input.value);     // ├─ Tres setters…
  setIsEditing(false);       // ┘
  // …pero UN solo re-render al terminar handleSave.
}
SIN BATCHING (hipotético, lento) CON BATCHING (React real) ───────────────────────────────── ────────────────────────── setName → render + commit setName ─┐ setEmail → render + commit setEmail ─┼→ 1 render → 1 commit setIsEditing → render + commit setIsEditing ─┘ (3 renders, 3 commits) (1 render, 1 commit)

Desde React 18 el batching es automático y universal: también dentro de setTimeout, promesas (.then) o manejadores de eventos nativos. Antes solo se aplicaba a eventos de React; ya no hay que pensar en ello.

La solución: actualizaciones funcionales set(c => c + 1)

¿Y si de verdad quiero sumar 3 en el mismo click? El setter acepta dos formas:

  • setCount(count + 1) — le pasas el valor que quieres (calculado con la foto de este render).
  • setCount(c => c + 1) — le pasas una función: React la ejecutará durante el próximo render dándole el valor pendiente más reciente de la cola de actualizaciones.
function handleClick() {
  setCount((c) => c + 1);   // c = 0  → 1
  setCount((c) => c + 1);   // c = 1  → 2  (recibe el resultado pendiente)
  setCount((c) => c + 1);   // c = 2  → 3
  // Resultado: 3. Y sigue siendo UN solo re-render.
}
LA COLA DE ACTUALIZACIONES DE UN MISMO EVENTO ────────────────────────────────────────────── setCount(0 + 1) setCount(0 + 1) setCount(0 + 1) └────► valor final: 1 (todas leen la foto: 0) setCount(c => c+1) setCount(c => c+1) setCount(c => c+1) c=0 → 1 ──► c=1 → 2 ──► c=2 → 3 └────► valor final: 3 (cada una recibe lo pendiente)

Regla profesional: si el nuevo valor depende del anterior (incrementos, toggles, añadir a un array…), usa siempre la forma funcional. Es inmune a las fotos antiguas y funciona igual dentro de timeouts o promesas, donde la foto del render puede estar muy desfasada.

Comparación con lo que ya conoces

  • JavaScript vanilla: tú escribes los cambios en el DOM a mano, uno a uno, en cuanto ocurren. No hay batching: si cambias tres nodos, el navegador puede re-layout tres veces.
  • .NET (Blazor): el modelo es casi idéntico: StateHasChanged() marca el componente como «sucio» y Blazor agrupa renders. La «instantánea» equivale a que las propiedades del componente no cambian hasta el próximo render.
  • Angular: Zone.js parchea los eventos y dispara detección de cambios al final de cada uno — un batching implícito. React lo hace explícito con setters.
  • Vue / Solid: usan reactividad de grano fino (signals): no re-ejecutan el componente, actualizan directamente los nodos suscritos. React prefiere re-ejecutar funciones baratas + diffing: un modelo más simple a cambio de más trabajo en memoria.

3 · Ejemplo mínimo

El experimento mínimo que demuestra TODO lo anterior. Ejecutable en ejemplos/m04-estado (sección 2):

src/components/BatchingDemo.jsx (extracto)
import { useState } from "react";

export default function BatchingDemo() {
  const [count, setCount] = useState(0);

  // Se ejecuta en CADA render: nuestra «cámara» para contar renders
  console.log("RENDER con count =", count);

  function handleTripleNaive() {
    // Tres llamadas, la MISMA foto: sube 1, no 3
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  function handleTripleFunctional() {
    // Cada función recibe el valor PENDIENTE: sube 3
    setCount((c) => c + 1);
    setCount((c) => c + 1);
    setCount((c) => c + 1);
  }

  return (
    <>
      <p>Contador: {count}</p>
      <button onClick={handleTripleNaive}>+3 ingenuo</button>
      <button onClick={handleTripleFunctional}>+3 funcional</button>
    </>
  );
}

Línea por línea (lo que debes observar):

  1. console.log("RENDER…") está en el cuerpo del componente: se ejecuta en cada render. Abre la consola del navegador antes de pulsar.
  2. Pulsa «+3 ingenuo»: aparece UN «RENDER con count = 1». Tres setters → un render (batching) → y el valor sube solo 1 (misma foto).
  3. Pulsa «+3 funcional»: aparece UN «RENDER con count = 4». Un render de nuevo, pero esta vez la cola de funciones sumó 3.
  4. Conclusión visible: un render por click, nunca uno por setter. Y la diferencia entre «pasar valor» y «pasar función» queda demostrada con números.

4 · Ejemplo real

Un cuestionario paso a paso (quiz): responder bien suma puntos Y avanza de pregunta; el botón «Reiniciar» toca tres estados a la vez. Es el caso real del batching: varios estados que deben cambiar juntos en un solo evento.

src/components/Quiz.jsx
import { useState } from "react";

const QUESTIONS = [
  { text: "¿Qué hook guarda estado?", options: ["useState", "useFetch"], answer: 0 },
  { text: "¿setState es inmediato?", options: ["Sí", "No, programa un render"], answer: 1 },
];

export default function Quiz() {
  const [step, setStep] = useState(0);        // índice de la pregunta actual
  const [score, setScore] = useState(0);      // aciertos
  const [finished, setFinished] = useState(false);

  // Derivados: NO son estado, se calculan en cada render
  const question = QUESTIONS[step];
  const isLast = step === QUESTIONS.length - 1;

  function handleAnswer(optionIndex) {
    // DOS setters en el mismo evento → UN solo re-render (batching).
    // La forma funcional: el nuevo valor depende del anterior.
    if (optionIndex === question.answer) {
      setScore((s) => s + 1);
    }
    if (isLast) {
      setFinished(true);
    } else {
      setStep((s) => s + 1);
    }
  }

  function handleRestart() {
    // TRES setters, UN render: la pantalla cambia «de golpe»,
    // nunca muestra estados intermedios a medias.
    setStep(0);
    setScore(0);
    setFinished(false);
  }

  if (finished) {
    return (
      <div>
        <h2>Resultado: {score} / {QUESTIONS.length}</h2>
        <button onClick={handleRestart}>Reiniciar</button>
      </div>
    );
  }

  return (
    <div>
      <p>Pregunta {step + 1} de {QUESTIONS.length} · Puntos: {score}</p>
      <h2>{question.text}</h2>
      {question.options.map((option, index) => (
        <button key={option} onClick={() => handleAnswer(index)}>
          {option}
        </button>
      ))}
    </div>
  );
}

Decisiones explicadas:

  • Tres estados pequeños y separados (step, score, finished) en vez de un objeto quiz gigante: cada uno responde a eventos distintos y se lee de un vistazo. (Cuándo agrupar: próxima lección.)
  • El batching garantiza atomicidad visual: en handleRestart, la UI jamás muestra «pregunta 1 con puntos viejos»: los tres cambios llegan en el mismo render. Sin batching podrías ver parpadeos intermedios.
  • question e isLast son derivados: se calculan del estado en cada render. Crear const [question, setQuestion] = useState(...) sería duplicar verdad: habría que mantenerla sincronizada a mano con step.
  • key={option}: el texto de la opción es único y estable en este quiz; si pudiera repetirse, usaríamos ids (Módulo 2).
  • Guard clauses y condicionales dentro del manejador, nunca en los hooks: los tres useState están siempre en el nivel superior, se cumplan o no las condiciones.

5 · Buenas prácticas

HazEvitaPor qué
set(c => c + 1) cuando el nuevo valor depende del anterior set(count + 1) en esos casos La forma funcional siempre recibe el valor pendiente real: es inmune a fotos antiguas y a setters encadenados.
Agrupar en un evento todos los setters de un «cambio lógico» Repartir cambios relacionados entre varios eventos «para que se vea el proceso» El batching los hace atómicos: la UI nunca muestra estados intermedios inconsistentes.
Pensar en renders como fotos: «en este render, ¿qué vale esto?» Imaginar el estado como una caja que lees en vivo El modelo de instantáneas explica el 100 % de los comportamientos «raros» de useState.
Un console.log temporal en el cuerpo para contar renders al depurar Entrar en pánico de rendimiento al ver renders extra Render ≠ repaint: renders baratos y sin cambios de DOM son normales. Optimiza solo con el Profiler (Módulo 11).
Nombre del parámetro funcional corto y claro: c, prev, current Reusar el mismo nombre que la variable de estado (setCount(count => …)) si confunde Ambas funcionan, pero un nombre distinto deja claro que es el valor pendiente, no la foto.

6 · Errores habituales

Error 1: encadenar setters leyendo la foto

✘ Incorrecto 
// "Sube 3 por click"… pero sube 1
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);
✔ Correcto 
setCount((c) => c + 1);   // cada función recibe lo pendiente
setCount((c) => c + 1);
setCount((c) => c + 1);

Error 2: leer el estado justo después de cambiarlo

✘ Incorrecto 
function handleSubmit() {
  setStatus("saving");
  if (status === "saving") { … }   // status sigue siendo el VIEJO
                                   // en todo este render/manejador
}
✔ Correcto 
function handleSubmit() {
  const nextStatus = "saving";   // tu propia variable SÍ vale ya
  setStatus(nextStatus);
  if (nextStatus === "saving") { … }
}

Error 3: llamar al setter DURANTE el render

✘ Incorrecto 
function Profile({ user }) {
  const [name, setName] = useState(user.name);
  if (user.name !== name) {
    setName(user.name);   // 💥 render → setter → render → … (bucle)
  }
}
✔ Correcto 
// Los setters van en EVENTOS (o efectos, M6).
// Si el valor se puede calcular de las props… ¡ni siquiera es estado:
function Profile({ user }) {
  return <h1>{user.name}</h1>;   // derivado directo, cero estado
}

Error 4: tratar setState como si fuera await-able

✘ Incorrecto 
await setCount(5);         // setCount NO devuelve promesa: el await
console.log("ya vale 5");  // no espera a nada. El render llegará
                           // cuando React lo programe.
✔ Correcto 
setCount(5);
// ¿Necesitas reaccionar CUANDO el valor cambie?
// Eso es un EFECTO: useEffect(() => { … }, [count]) → Módulo 6.

7 · Ejercicio guiado

Construimos un dado con estadísticas: cada tirada actualiza el dado Y el contador de tiradas (dos setters, un render — lo comprobaremos en consola).

  1. Crea Dice.jsx con dos estados: const [value, setValue] = useState(1) y const [rolls, setRolls] = useState(0). Añade el log console.log("RENDER", value, rolls) en el cuerpo.

  2. Manejador de tirada: setValue(1 + Math.floor(Math.random() * 6)) y setRolls((r) => r + 1). Pregunta clave: ¿por qué rolls usa forma funcional y value no? (Porque el nuevo valor del dado NO depende del anterior; el de tiradas, sí.)

  3. Pinta el dado ({value} en grande), el botón «Tirar» y el texto derivado Tiradas: {rolls}.

  4. Botón «Reiniciar estadísticas»: solo setRolls(0). Fíjate: un solo setter, un solo render, y el dado no cambia (su celda de estado queda intacta).

  5. Abre la consola y tira 5 veces: debes ver exactamente 5 líneas «RENDER», una por click, con AMBOS valores ya actualizados a la vez. Ahí está el batching, en vivo.

  6. Experimento final: añade otro setRolls((r) => r + 1) dentro del manejador de tirada. Predice antes de probar: ¿cuántas tiradas suma por click? ¿cuántos renders? (Respuesta: suma 2; sigue siendo 1 render.)

9 · Resumen

  • Solo dos cosas disparan un render: el montaje inicial y un setter de estado.
  • Render = ejecutar tu función y comparar el JSX (fase en memoria). Commit = tocar el DOM solo con las diferencias. Render ≠ repaint.
  • El estado de cada render es una instantánea congelada: dentro de un manejador, la variable no cambia por muchos setters que llames.
  • Batching: todos los setters de un mismo evento se procesan juntos en UN render al terminar la función. Es automático en React 19, también en promesas y timeouts.
  • Si el nuevo valor depende del anterior, usa la forma funcional: set(c => c + 1). Recibe el valor pendiente, no la foto.
  • Los setters no son await-ables ni se leen «en el acto»: para reaccionar a un cambio de estado existe useEffect (Módulo 6).

10 · Preguntas frecuentes

Entonces, ¿setState es asíncrono?

No exactamente, y esa palabra confunde. El setter actualiza una estructura interna y programa un render para cuando termine tu código (batching). No es «asíncrono» como una promesa: es «diferido hasta el final del evento». El modelo mental correcto: encargas un render, no «cambias una variable y esperas».

¿Un setter siempre provoca re-render?

Casi. Si el nuevo valor es idéntico al actual (Object.is), React «fianza» (bails out): puede ejecutar tu componente una vez más para confirmar que nada cambió, pero no toca el DOM ni re-renderiza a los hijos. Por eso setCount(0) en bucle no es un desastre… aunque tampoco es gratis.

¿Puedo forzar que algo se actualice YA, sin batching?

Existe flushSync de react-dom para casos muy concretos (medir el DOM justo tras un cambio, integraciones con librerías externas). Rompe el batching y es más caro: en todo el curso no lo necesitaremos. Saber que existe basta por ahora.

Si el render re-ejecuta TODA la función, ¿no es lentísimo?

Tu función componente suele ser baratísima: crear objetos JSX cuesta nanosegundos (son objetos planos de JS, no nodos DOM). Lo caro —tocar el DOM— solo ocurre en el commit y solo con las diferencias. React apuesta por «re-ejecutar mucho y barato» en vez de «vigilar cada variable» como hacen Vue o Solid.

¿Por qué en desarrollo veo DOS logs de render por cada click?

Es <StrictMode> (lo pusimos en main.jsx): en desarrollo ejecuta tu componente dos veces para destapar efectos secundarios impuros. Solo en desarrollo; en producción, uno. Si tus handlers son puros, el doble render no rompe nada — y es tu primer entrenamiento de cara al Módulo 6.
