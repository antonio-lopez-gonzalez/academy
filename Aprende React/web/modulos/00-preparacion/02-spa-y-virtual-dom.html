SPA y Virtual DOM

Módulo 0 · Preparación ⏱ 30 minutos

1 · Introducción

En la lección anterior vimos qué es React. Ahora vamos a entender las dos ideas técnicas que lo hacen posible: el modelo de aplicación SPA (Single Page Application) y el Virtual DOM.

Son los dos conceptos más malentendidos de React. Casi todo el mundo «sabe» que React usa un Virtual DOM, pero pocos pueden explicar qué es exactamente, por qué existe y qué NO es. Y como el Virtual DOM explica las keys, el renderizado y la mitad de las reglas de React, entenderlo bien ahora te ahorrará cientos de dudas después.

Qué aprenderás:

  • Qué es una SPA y en qué se diferencia de una web tradicional (MPA).
  • Qué es el Virtual DOM y cómo funciona el proceso de reconciliación.
  • Qué es Fiber y el renderizado concurrente (React 18+).
  • Errores típicos: «el Virtual DOM es siempre más rápido», «es lo mismo que el Shadow DOM»…

2 · Teoría

Parte 1 — De las webs tradicionales (MPA) a las SPA

Una web tradicional (MPA, Multi Page Application) funciona como un libro: cada página es un documento HTML completo que vive en el servidor. Haces clic en un enlace → el navegador pide otra página completa → el servidor la genera (con PHP, ASP.NET, etc.) → el navegador tira todo lo que tenía y pinta la nueva desde cero.

NAVEGACIÓN EN UNA MPA (web tradicional) ───────────────────────────────────────── Usuario clic en "Perfil" │ ▼ Petición HTTP ──────► Servidor │ genera perfil.html COMPLETO ◄──────────────────┘ Navegador DESTRUYE la página actual y pinta la nueva desde cero (parpadeo blanco)

Una SPA funciona como una aplicación de escritorio: se descarga una única página HTML (casi vacía) junto con el JavaScript de la aplicación, y a partir de ahí JavaScript construye y cambia la interfaz dentro de esa misma página. Navegar entre «pantallas» no recarga nada: JavaScript reescribe el contenido y actualiza la URL con la History API.

NAVEGACIÓN EN UNA SPA (React) ───────────────────────────────────────── Usuario clic en "Perfil" │ ▼ React Router cambia la URL (History API, sin recargar) │ ▼ React renderiza la pantalla "Perfil" EN LA MISMA PÁGINA │ ▼ Si faltan datos → fetch() al servidor (solo JSON, no HTML)
MPA (tradicional)SPA (React)
Quién genera el HTMLEl servidor, en cada navegaciónJavaScript, en el navegador
NavegaciónRecarga completa de páginaInstantánea, sin recarga
Primera cargaRápida (HTML ya listo)Más pesada (descargar el JS)

Si vienes de .NET: una SPA con React sustituye a las vistas Razor como generadoras de UI. El backend (.NET 8, en nuestro caso) pasa a ser una API que solo devuelve datos JSON — exactamente la arquitectura del proyecto final del curso.

Parte 2 — El DOM es lento (y peligroso) de manipular

El DOM (Document Object Model) es la representación en memoria que el navegador hace de tu HTML: un árbol de objetos vivos. Dos problemas:

  1. Tocarlo es caro: cambiar el DOM puede disparar reflow (el navegador recalcula geometría de la página) y repaint (vuelve a pintar píxeles). Cien cambios individuales pueden significar cien recálculos.
  2. Es imperativo y frágil: como vimos en la lección 1, sincronizar a mano «qué partes del árbol cambian cuando cambian los datos» es la fuente clásica de bugs.

Parte 3 — El Virtual DOM: un borrador de la interfaz

🏗 Analogía de la obra y el plano

Imagina que reformas una casa (el DOM real). Tirar un tabique y reconstruirlo cada vez que cambias de idea sería carísimo. En su lugar trabajas sobre el plano (el Virtual DOM): dibujas la nueva distribución, comparas el plano nuevo con el anterior, y solo entonces mandas a los obreros cambiar exactamente lo que es diferente: «mover esta puerta 30 cm». Un cambio mínimo en la obra real.

El Virtual DOM (VDOM) es una representación ligera de la interfaz como objetos de JavaScript. No es una copia del DOM del navegador ni algo que se pinte: son simples objetos { type, props, children } que React crea a enorme velocidad (crear objetos en memoria es baratísimo).

El ciclo completo, llamado reconciliación, funciona así:

EL CICLO DE RECONCILIACIÓN DE REACT ───────────────────────────────────────── 1. Cambia el estado (setState, nuevas props…) │ ▼ 2. RENDER: React ejecuta tus componentes y genera un NUEVO árbol Virtual DOM │ ▼ 3. DIFFING: compara el árbol nuevo con el anterior (algoritmo O(n), muy optimizado) → calcula la lista MÍNIMA de cambios │ ▼ 4. COMMIT: aplica esos cambios al DOM real, en lote, una sola vez │ ▼ El navegador repinta solo lo que cambió

Detalles clave que casi nadie explica:

  • El render no toca el DOM. Cuando dices «React se re-renderiza», significa que React volvió a ejecutar tus funciones componente para generar el nuevo VDOM. El DOM real solo se toca en la fase commit, y solo si hubo diferencias.
  • El diffing tiene reglas propias: compara por tipo de elemento y posición. Por eso existen las keys en las listas (Módulo 2): son la forma de decirle a React «este elemento de la lista nueva es el mismo que este otro de la lista vieja». Sin keys, React adivina por posición y a veces adivina mal.
  • Si el tipo cambia, se destruye el subárbol: pasar de <div> a <section> en la misma posición hace que React deseche todo lo que colgaba ahí y lo recree. Por eso importa la estabilidad de la estructura.

Parte 4 — Fiber y el renderizado concurrente (React 18/19)

Desde React 16, el motor interno se llama Fiber. Antes, la reconciliación era un trabajo único e ininterrumpible: si el árbol era grande, el navegador se quedaba «congelado» hasta terminar (no podía ni responder a un clic).

Fiber divide el trabajo de renderizado en unidades pequeñas pausables. React puede renderizar un rato, comprobar si hay algo más urgente (el usuario está escribiendo), pausar, atender lo urgente y retomar después. Desde React 18 esto se expone con las transiciones (startTransition): marcas una actualización como «no urgente» y React mantiene la interfaz respondiendo mientras la calcula en segundo plano.

RENDERIZADO ANTIGUO (síncrono) RENDERIZADO CONCURRENTE (Fiber) ────────────────────────────── ──────────────────────────────── [===render bloqueante===] [render][pausa][tecla][render]… UI congelada UI siempre responde

3 · Ejemplo mínimo

El Virtual DOM suena abstracto, así que vamos a construir uno de juguete en 20 líneas. Ejecútalo en la consola del navegador: verás que un «elemento virtual» no es más que un objeto de JavaScript que describe la UI.

consola del navegador — mini Virtual DOM de juguete
// 1. Un ELEMENTO VIRTUAL: solo un objeto plano que DESCRIBE la UI
const elementoVirtual = {
  type: "h1",
  props: { className: "titulo", children: "Hola, Virtual DOM" },
};

// 2. Un "render" casero: convierte la descripción en DOM REAL
function render(elemento) {
  const nodo = document.createElement(elemento.type);
  nodo.className = elemento.props.className;
  nodo.textContent = elemento.props.children;
  return nodo;
}

// 3. Lo montamos en la página
document.body.appendChild(render(elementoVirtual));

Línea por línea:

  1. elementoVirtual — esto ES lo que tus componentes devuelven en React (React lo crea por ti a partir del JSX). Nótese: es un objeto inofensivo, no toca nada.
  2. render() — el equivalente simplificado de lo que React hace internamente en la fase commit.
  3. React añade lo que nuestro juguete no tiene: guardar el árbol anterior, compararlo y tocar el DOM real solo donde difiera.
La idea que debes llevarte

Cuando escribes <h1 className="titulo">Hola</h1> en React, no estás creando HTML: estás creando un objeto que describe lo que quieres. React decide cuándo y cómo materializarlo en el DOM real.

4 · Ejemplo real

Veamos la reconciliación con lupa. Tenemos este componente y el usuario hace clic en «+1»:

Contador.jsx
function Contador({ count }) {
  return (
    <div className="contador">
      <h1>Contador</h1>
      <p>
        Valor: <strong>{count}</strong>
      </p>
      <button>+1</button>
    </div>
  );
}

Paso 1 — VDOM antes del clic (count = 3):

div.contador ├── h1 → "Contador" ├── p │ ├── texto → "Valor: " │ └── strong → "3" ◄── el único nodo con el dato └── button → "+1"

Paso 2 — El clic cambia el estado a 4. React vuelve a ejecutar el componente y genera un VDOM nuevo:

div.contador ├── h1 → "Contador" (igual) ├── p │ ├── texto → "Valor: " (igual) │ └── strong → "4" ◄── ¡DIFERENTE! └── button → "+1" (igual)

Paso 3 — Diffing: React recorre ambos árboles. Los tipos coinciden en todas partes; los textos coinciden en todas partes… excepto dentro de <strong>.

Paso 4 — Commit: React ejecuta exactamente UNA operación en el DOM real:

lo único que React hace en el DOM real
strong.textContent = "4"; // un único cambio, en lote

Ni el <h1>, ni el botón, ni el párrafo se tocan. En una app real con miles de nodos, este ahorro es el que permite interfaces complejas fluidas sin que tú optimices nada a mano.

🔍 Verlo con tus ojos (DevTools)

En el navegador: F12 → pestaña Elements → menú ⋮ de la esquina → More tools → Rendering → activa Paint flashing. Cada vez que algo cambie, verás un resplandor verde SOLO sobre lo que se repintó. Es la reconciliación hecha visible.

6 · Errores habituales

Error 1: «El Virtual DOM es siempre más rápido que el DOM»

Por qué está mal: el VDOM añade trabajo (crear árboles y compararlos). Para cambios triviales, un textContent = … bien colocado a mano es más rápido. La promesa real del VDOM es otra: rendimiento bueno y predecible sin esfuerzo manual, incluso cuando la app crece y nadie recuerda qué parte de la pantalla depende de qué dato.

Versión correcta: el VDOM no es una tecnología de velocidad máxima, es una tecnología de velocidad suficiente con cero mantenimiento manual. Frameworks como Solid (sin VDOM) ganan en benchmarks finos; React gana en ecosistema y modelo mental.

Error 2: confundir Virtual DOM con Shadow DOM

Por qué está mal: son cosas totalmente distintas que solo comparten la palabra «DOM».

Virtual DOMShadow DOM
Objetos JS que describen la UI (invención de React) Encapsulación nativa del navegador (Web Components)
Sirve para calcular cambios mínimos Sirve para aislar estilos y marcado
No lo ves en las DevTools Aparece como #shadow-root en Elements

Error 3: «En React nunca se toca el DOM»

Por qué está mal: React sí toca el DOM (fase commit) y tú a veces necesitarás hacerlo: enfocar un input, medir un elemento, integrar una librería de mapas… Para eso existe useRef (Módulo 6).

Versión correcta: el DOM se toca a través de los mecanismos oficiales de React (refs), nunca con document.querySelector sobre elementos que React controla.

7 · Ejercicio guiado

Entrena la reconciliación a mano. Tienes este árbol antes y después de un cambio de estado. Anota qué operaciones mínimas haría React en el DOM real.

ANTES (VDOM viejo) DESPUÉS (VDOM nuevo) ───────────────── ─────────────────── ul ul ├── li → "Leche" ├── li → "Leche" ├── li → "Pan" ├── li → "Pan integral" ← cambió texto └── li → "Huevos" ├── li → "Huevos" └── li → "Café" ← nodo nuevo

  1. Compara los tipos de la raíz: ul === ul → se conserva el nodo y se comparan hijos.

  2. Recorre los hijos por posición: posición 0 igual; posición 1 mismo tipo (li) pero distinto texto → operación 1: li[1].textContent = "Pan integral".

  3. Posición 2: igual, sin cambios. Posición 3: existe en el árbol nuevo y no en el viejo → operación 2: ul.appendChild(nuevoLi) con «Café».

  4. Resultado: 2 operaciones de DOM para un cambio que a mano habría requerido buscar la lista, encontrar el item, cambiarlo, crear otro e insertarlo. React lo deduce solo.

Pista que anticipa el Módulo 2

¿Y si en lugar de añadir «Café» al final lo insertáramos al principio? Por posiciones, React creería que cambiaron los 4 textos (4 operaciones en vez de 1). La solución son las keys: identificar cada elemento de forma estable.

9 · Resumen

  • MPA: el servidor genera cada página; navegar recarga todo. SPA: una sola página; JavaScript (React) construye la UI dentro.
  • El Virtual DOM es una descripción de la UI como objetos de JavaScript: un «borrador» barato de crear y comparar.
  • La reconciliación tiene 3 fases: render (ejecutar componentes → nuevo VDOM), diffing (comparar con el anterior), commit (aplicar cambios mínimos al DOM real).
  • Re-renderizar no es repintar: ejecutar componentes es barato; React solo toca el DOM si hay diferencias.
  • Fiber hace el renderizado pausable y por prioridades: la UI sigue respondiendo mientras React trabaja (base de las transiciones de React 18/19).
  • El VDOM no es «siempre más rápido»: es predecible y sin mantenimiento manual. Y no tiene nada que ver con el Shadow DOM.

10 · Preguntas frecuentes

¿Las SPA tienen mal SEO?

Google ejecuta JavaScript y puede indexar SPAs, pero el SEO suele ser peor y más lento que con HTML renderizado en servidor. Si el SEO es crítico (tienda, blog, marketing), usa SSR/SSG (Next.js, Astro). Si es una app tras login (un dashboard), la SPA es perfecta.

¿Cada cambio de estado repinta toda la app?

React vuelve a ejecutar los componentes afectados (render), pero el diffing garantiza que el DOM real solo se toca donde hay diferencias. El render «en vano» (que no cambia nada) es barato y habitual.

¿Puedo usar React sin hacer una SPA?

Sí: puedes montar React en una isla de una página tradicional (un widget) o usar frameworks con SSR (Next.js) que generan HTML en el servidor. En este curso nos centramos en la SPA con Vite, el caso más común del mercado.

¿Qué son los «Server Components» que oigo por ahí?

Componentes que se ejecutan solo en el servidor y envían su resultado ya renderizado (reduciendo el JS que se descarga). Son una característica avanzada ligada a frameworks (Next.js). Primero domina el modelo cliente de este curso; los Server Components serán un complemento fácil de asimilar después.

¿Por qué el diffing es O(n) si comparar árboles en general es O(n³)?

Porque React hace dos suposiciones que se cumplen casi siempre en UIs reales: (1) elementos de tipos distintos producen árboles distintos (no se comparan en profundidad, se sustituyen) y (2) las keys identifican qué elementos persisten entre renders. Con esas reglas, basta un recorrido lineal.
