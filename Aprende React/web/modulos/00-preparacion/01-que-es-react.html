Qué es React e historia

Módulo 0 · Preparación ⏱ 25 minutos

1 · Introducción

En esta primera lección vas a entender qué es React exactamente, por qué se creó y qué problema resuelve. Puede parecer tentador saltarse la historia y la teoría para ir directo al código, pero te aseguro algo: la mayoría de desarrolladores que «usan React» sin entenderlo arrastran durante años confusiones que nacen precisamente aquí, en los fundamentos que nadie les explicó.

El problema que React resuelve:

Las aplicaciones web modernas tienen interfaces enormemente complejas: un contador de notificaciones que cambia mientras escribes un comentario que actualiza una lista que modifica un contador… Mantener la interfaz sincronizada con los datos escribiendo código JavaScript a mano (buscar elementos, cambiarlos, eliminarlos, crearlos) se convierte rápidamente en un caos frágil. React existe para que tú describas cómo debe verse la interfaz y sea React quien se ocupe de hacerlo realidad en el navegador.

Cuándo se utiliza React:

  • Aplicaciones web interactivas (dashboards, editores, gestores de tareas, redes sociales).
  • Interfaces con mucho estado que cambia constantemente.
  • Proyectos de equipo que necesitan una arquitectura por componentes reutilizables.
  • Apps móviles (React Native comparte el mismo modelo mental).

Errores típicos de los que empiezan (los veremos en detalle):

  • Creer que React es un «framework completo» que lo resuelve todo.
  • Aprender React sin tener soltura con JavaScript moderno.
  • Pensar que React es rápido «por magia del Virtual DOM».

2 · Teoría

La definición oficial, desmontada

React se define a sí mismo como «una biblioteca de JavaScript para construir interfaces de usuario». Cada palabra de esa frase está elegida con cuidado:

  • Biblioteca (library), no framework: React se ocupa de una sola cosa: pintar la interfaz a partir de tus datos. No incluye router, ni gestión de peticiones HTTP, ni un sistema de formularios. Esas piezas las eliges tú (y en este curso elegiremos React Router, fetch, Redux Toolkit…). Un framework como Angular, en cambio, te da todas las respuestas de fábrica. La analogía: un framework es una casa prefabricada; una biblioteca es un excelente sistema de fontanería que instalas en la casa que tú diseñas.
  • De JavaScript: React no es un lenguaje nuevo. Todo lo que escribes es JavaScript (con una extensión de sintaxis llamada JSX que veremos en el Módulo 1). Por eso quien domina JavaScript domina React; y quien no, sufre React.
  • Para construir interfaces de usuario: su única responsabilidad es la capa de presentación: lo que el usuario ve y toca.

La idea revolucionaria: declarativo en lugar de imperativo

Aquí está el corazón de todo. Presta atención porque este concepto reaparecerá en cada módulo del curso.

🍽 Analogía del restaurante

Imperativo es cocinar tú mismo: picar la cebolla, calentar la sartén, añadir el aceite, remover durante 5 minutos… Describes cada paso del proceso.

Declarativo es pedir al camarero: «una tortilla española, por favor». Describes el resultado que quieres y alguien (la cocina) se encarga del proceso.

JavaScript «a pelo» (vanilla) es imperativo: document.createElement, appendChild, textContent = …. React es declarativo: describes la UI como una función de tus datos y React cocina.

La fórmula más importante de React, la que debes tatuarte mentalmente:

┌──────────────────────────────────────────┐ │ │ │ UI = f(estado) │ │ │ │ La interfaz es una FUNCIÓN del estado. │ │ Datos cambian → React repinta. │ │ │ └──────────────────────────────────────────┘

Tu trabajo como desarrollador React se reduce a dos cosas:

  1. Modelar bien tus datos (qué información tiene tu aplicación en cada momento).
  2. Describir cómo se ven esos datos (qué interfaz corresponde a cada valor del estado).

Cuando los datos cambian (el usuario escribe, llega una respuesta del servidor, pasa un temporizador…), tú no tocas el DOM: cambias el estado y React recalcula la interfaz.

Historia: por qué nació React (y por qué parecía una locura)

  • 2011 — El problema en Facebook: Jordan Walke, ingeniero de Facebook, sufría con el newsfeed: contadores de mensajes, notificaciones y publicaciones que se actualizaban en tiempo real con jQuery. El código era una maraña de $('#contador').text(n) repartida por todas partes. Cualquier cambio rompía otra cosa. Creó un prototipo llamado FaxJS.
  • 2012 — Instagram: Facebook compra Instagram y React se usa para reescribir su web. Primera prueba de fuego real.
  • Mayo 2013 — Open source: se presenta en la JSConf US. La comunidad reaccionó con escepticismo: JSX (mezclar «HTML dentro de JavaScript») parecía violar la sagrada «separación de responsabilidades». La historia dio la vuelta al veredicto: separar por tecnología (HTML aquí, JS allá) tenía menos sentido que separar por funcionalidad (todo lo del botón, junto).
  • 2015 — React Native: el mismo modelo sirve para apps móviles nativas.
  • 2019 — Hooks (React 16.8): useState, useEffect… Los componentes de función, antes limitados, se vuelven la forma estándar de escribir React. Las clases quedan como legado.
  • 2022 — React 18: renderizado concurrente (React puede pausar y priorizar actualizaciones urgentes, como lo que escribes, sobre las no urgentes).
  • Diciembre 2024 — React 19: la versión de este curso. Añade las Actions para formularios, el hook use, useOptimistic, mejoras en la hidratación y el soporte de componentes de servidor. Además, el React Compiler (opcional) empieza a automatizar las memoizaciones. Todo lo aprenderemos a su debido tiempo.

¿Quién usa React?

Meta (Facebook, Instagram, WhatsApp Web), Netflix, Airbnb, Uber, Discord, Notion, Microsoft (partes de Office y Teams), Shopify… No es una moda: es el estándar industrial de facto, con el mayor ecosistema y el mayor mercado laboral del frontend.

3 · Ejemplo mínimo

Todavía no hemos instalado nada (llega en la lección 5), así que el ejemplo mínimo será un contraste que puedes ejecutar ya mismo en la consola de tu navegador (F12 → pestaña «Consola»). Es la semilla de todo el curso.

Versión imperativa (JavaScript vanilla):

consola del navegador
// IMPERATIVO: describimos CADA PASO para construir un saludo

// 1. Creamos el elemento de forma manual
const titulo = document.createElement("h1");

// 2. Le ponemos el contenido
titulo.textContent = "Hola, React";

// 3. Lo insertamos en la página buscando dónde
document.body.appendChild(titulo);

// Si el nombre cambia... tenemos que REPETIR el proceso:
titulo.textContent = "Hola, Ada"; // buscar el elemento y tocarlo de nuevo

Versión declarativa (la idea de React):

idea conceptual — la ejecutaremos de verdad en la lección 6
// DECLARATIVO: describimos QUÉ QUEREMOS VER, no los pasos

// Definimos los datos...
const nombre = "Ada";

// ...y describimos la interfaz como una FUNCIÓN de esos datos
function Saludo({ nombre }) {
  return <h1>Hola, {nombre}</h1>;
}

// Cuando "nombre" cambie, React actualizará el <h1> por nosotros.
// Nunca buscamos elementos ni los tocamos a mano.

Línea por línea:

  1. const nombre = "Ada"; — en React todo empieza por los datos (el «estado»).
  2. function Saludo(...)… — un componente no es más que una función de JavaScript.
  3. return <h1>Hola, {nombre}</h1>; — parece HTML, pero es JSX: una descripción de la UI. Las llaves { } insertan valores de JavaScript. Lo aprenderemos en el Módulo 1.
  4. No hay createElement, appendChild ni búsquedas: React traducirá esa descripción al DOM real.

4 · Ejemplo real

Imagina que construyes el panel de notificaciones de una red social con JavaScript vanilla. Requisitos: una lista de notificaciones, un contador de «sin leer» y un botón «marcar todas como leídas».

El enfoque imperativo se complica así de rápido:

notifications.js (vanilla — el dolor que React evita)
// Cada cambio de datos obliga a sincronizar la UI A MANO
function marcarTodasLeidas() {
  // 1. Actualizamos los datos
  notificaciones.forEach((n) => (n.leida = true));

  // 2. Buscamos TODOS los sitios de la pantalla afectados...
  document.querySelectorAll(".notification").forEach((el) => {
    el.classList.remove("unread");           // quitar el estilo
    el.querySelector(".dot").remove();        // quitar el punto azul
  });

  // 3. Actualizamos el contador de la cabecera
  document.querySelector("#badge").textContent = "0";
  document.querySelector("#badge").hidden = true;

  // 4. ¿Y el contador del menú lateral? ¿Y el título de la pestaña?
  //    Cada sitio nuevo que muestre este dato es un punto de fallo.
}

Este código funciona… hasta que añades un tercer lugar donde aparece el contador y te olvidas de actualizarlo. Los datos dicen una cosa y la pantalla muestra otra. Ese es el bug clásico de las aplicaciones imperativas: la UI se desincroniza del estado.

La misma funcionalidad, pensada en React:

NotificationPanel.jsx (React — describimos, no ordenamos)
// En React SOLO cambiamos los datos; la UI se deriva sola
function NotificationPanel() {
  const [notificaciones, setNotificaciones] = useState(datosIniciales);

  // Dato DERIVADO: se calcula, no se guarda ni se sincroniza a mano
  const sinLeer = notificaciones.filter((n) => !n.leida).length;

  function marcarTodasLeidas() {
    // Un único cambio de estado...
    setNotificaciones(notificaciones.map((n) => ({ ...n, leida: true })));
  }

  // ...y TODA la interfaz que depende de él se actualiza sola:
  return (
    <div>
      {sinLeer > 0 && <span className="badge">{sinLeer}</span>}
      <button onClick={marcarTodasLeidas}>Marcar todas leídas</button>
      <NotificationList items={notificaciones} />
    </div>
  );
}

No entendemos aún toda la sintaxis (useState, map, onClick…) — eso es exactamente lo que enseñan los Módulos 2, 3 y 4. Lo importante ahora es la diferencia de mentalidad:

  • En vanilla sincronizas tú cada rincón de la pantalla (y se te olvidará alguno).
  • En React la pantalla es una proyección de los datos: imposible que se desincronicen, porque la UI se regenera a partir del estado.

6 · Errores habituales

Error 1: «React es un framework»

Por qué está mal: un framework (Angular, .NET MVC, Rails) define la estructura completa de tu aplicación. React solo pinta UI. Por eso no existe «la carpeta oficial de servicios» ni «el router de React»: son decisiones tuyas.

Versión correcta del concepto: React es una biblioteca de UI que se combina con otras bibliotecas. En este curso: React + Vite (herramientas) + React Router (rutas) + Redux Toolkit/Zustand (estado global) + Vitest (tests).

Error 2: «React es rápido por el Virtual DOM, automáticamente»

Por qué está mal: el Virtual DOM no hace tu aplicación rápida por arte de magia; hace que las actualizaciones sean predecibles y razonablemente rápidas. Una app React mal diseñada puede ser lenta (re-renderizados innecesarios), y una app vanilla bien escrita puede ser rapidísima. El Módulo 11 entero trata de esto.

Versión correcta del concepto: React te da un modelo donde el rendimiento bueno es el camino por defecto, no el objetivo en sí. El beneficio principal es la predecibilidad, no la velocidad bruta.

Error 3: «Necesito memorizar React como si fuera un lenguaje aparte»

Por qué está mal: lleva a «aprender recetas» sin entender. Cuando la receta no encaja, el desarrollador se bloquea.

Versión correcta: React son ~15 conceptos bien entendidos + JavaScript. Si entiendes funciones, arrays y objetos de JavaScript, React se deduce.

7 · Ejercicio guiado

Vamos a entrenar el ojo para distinguir código imperativo de declarativo. Para cada API, decide de qué tipo es:

  1. document.querySelector(".item").style.color = "red"

    Respuesta: imperativo. Describes el paso exacto (buscar y tocar un elemento concreto).

  2. SELECT * FROM users WHERE age > 18 (SQL)

    Respuesta: declarativo. Describes QUÉ quieres, no cómo recorrer las filas. La base de datos decide el «cómo». React es a la UI lo que SQL es a los datos.

  3. .map(n => n * 2) frente a un bucle for que rellena un array

    Respuesta: map es declarativo («transforma cada elemento»); el for es imperativo («crea un array vacío, itera, haz push…»). Por eso en React renderizamos listas con map (Módulo 2).

  4. CSS: .card { display: flex; }

    Respuesta: declarativo. Describes el resultado visual, no los píxeles que hay que mover. La web ya es declarativa en dos de sus tres patas (HTML y CSS); React lo hace también en JavaScript.

8 · Reto

🎯 Tu primer reto (sin código React)

Abre la consola del navegador en cualquier página web (F12) y haz estas dos cosas:

  1. Crea imperativamente una tarjeta con un título, un párrafo y un botón (createElement, appendChild…).
  2. Escribe en un comentario cómo la describirías declarativamente: qué datos necesitaría y qué estructura tendría, como si fuera la fórmula UI = f(datos). Puedes usar pseudocódigo.

No busques la solución en internet: el objetivo es sentir la diferencia de mentalidad. La volverás a necesitar en cada módulo.

9 · Resumen

  • React es una biblioteca de JavaScript para construir interfaces de usuario. No es un framework: las demás piezas se eligen aparte.
  • Nació en Facebook (2011-2013) para resolver la desincronización entre datos e interfaz en aplicaciones complejas.
  • El cambio fundamental: de código imperativo («cómo hacer cada paso») a declarativo («qué quiero ver»).
  • La fórmula sagrada: UI = f(estado). Cambian los datos → React repinta.
  • React 19 es la versión actual (estable desde diciembre de 2024) y la que usa todo este curso.
  • El mayor favor que puedes hacerte: dominar JavaScript moderno. React se apoya en él constantemente.

10 · Preguntas frecuentes

¿Necesito saber JavaScript muy bien antes de empezar?

Necesitas estar cómodo con: variables, funciones (incluidas arrow functions), arrays y sus métodos (map, filter, find), objetos, desestructuración, spread (...), módulos (import/export) y promesas/async. Si alguno te suena flojo, repásalo primero: multiplicará tu velocidad en este curso.

¿Qué diferencia hay entre React y Next.js?

React es la biblioteca de UI. Next.js es un framework construido encima de React que añade routing, renderizado en servidor, SEO, etc. Este curso enseña React puro con Vite: es la base que necesitas para luego entender Next.js sin magia.

¿Sigue teniendo sentido aprender React con la IA escribiendo código?

Más que nunca. La IA genera código React rápidamente, pero revisar, corregir y diseñar ese código exige entender el modelo mental (estado, renderizado, composición). Quien no lo entiende no puede detectar cuándo la IA se equivoca.

¿React es difícil de aprender?

React tiene pocos conceptos, pero exige cambiar de mentalidad (de imperativo a declarativo). Ese cambio cuesta unas semanas; después, todo encaja. Este curso está diseñado para que el cambio sea progresivo.

¿Por qué este curso no usa TypeScript?

Para separar dificultades: primero se entiende React en profundidad (ya es bastante), y TypeScript se añade después como capa de tipos. Todo lo que aprenderás se traslada directamente a React + TypeScript cuando lo necesites.
