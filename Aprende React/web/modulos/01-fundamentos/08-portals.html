Portals (createPortal)

Módulo 1 · Fundamentos ⏱ 30 minutos

1 · Introducción

Hasta ahora todos los componentes que hemos creado renderizan su contenido como parte del árbol DOM de su componente padre: el div raíz de Card vive dentro del div de App, que a su vez vive dentro de #root. Es la jerarquía natural de React y funciona para el 95 % de los casos.

Pero hay situaciones en las que necesitas que un hijo se renderice en otro lugar del DOM, fuera de la jerarquía de su padre. Los ejemplos clásicos son modales, tooltips, dropdowns y notificaciones toast. Si renderizas un modal dentro de un componente que tiene overflow: hidden o un z-index bajo, el modal aparecerá recortado o detrás de otros elementos. El problema no es de lógica, es de posicionamiento CSS: el modal está atrapado en el contexto de apilamiento y el clipping de su padre.

Para eso existe createPortal: una API de React que permite renderizar un subárbol de React en un nodo DOM diferente, fuera del contenedor del componente que lo crea, pero manteniendo el flujo de eventos y el contexto de React intactos. Es como si el hijo se «teletransportara» a otra parte del DOM sin que React deje de considerarlo parte de la familia.

2 · Teoría

¿Qué es createPortal exactamente?

createPortal es una función que exporta react-dom y tiene esta firma: 

import { createPortal } from "react-dom";

createPortal(children, domNode, key?)
  • children: cualquier JSX que React pueda renderizar (elementos, textos, arrays, componentes…).
  • domNode: un nodo DOM real (document.getElementById('modal-root'), por ejemplo) donde se insertarán los hijos.
  • key: opcional, igual que la prop key de los elementos, para identificar el portal durante la reconciliación.
🚪 Analogía: el teletransporte de React

Imagina que estás en una habitación (el componente padre) y necesitas que algo aparezca en la azotea (otra parte del DOM). No puedes sacarlo por la puerta porque la escalera está en obras (CSS overflow). createPortal es un teletransporte: el hijo sale de la habitación y aparece en la azotea. Pero sigue comunicándose contigo por walkie-talkie (eventos y contexto intactos).

¿Cómo funciona internamente?

Cuando React encuentra un createPortal durante el renderizado, hace esto:

  1. El portal se representa en el árbol virtual (React tree) donde el componente padre lo colocó.
  2. En el paso de reconciliación, React sabe que ese fragmento debe montarse en domNode en lugar del padre natural.
  3. El resultado DOM del portal se inserta como hijo de domNode, no del contenedor del padre.
ÁRBOL REACT (lógico) ÁRBOL DOM (físico) ───────────────────────── ──────────────────── App #root └─ Layout └─ div#app └─ TaskBoard └─ div.task-board └─ Modal (portal) └─ div.task-card └─── createPortal ────────► div#modal-root └─ div.modal-overlay └─ div.modal El Modal ES HIJO de TaskBoard El Modal APARECE en #modal-root en el React tree (sin herencia de overflow/z-index)

Lo más importante: aunque el DOM del portal esté fuera del padre, los eventos burbujean a través del árbol React, no del DOM. Es decir, si haces clic dentro del modal, el evento recorre el árbol virtual (Modal → TaskBoard → App) y puedes interceptarlo en el padre aunque DOM-estén separados.

¿Cuándo se necesita un portal?

ComponenteProblema sin portalSolución
Modal / DiálogoRecortado por overflow: hidden del padrePortal a #modal-root
TooltipAparece detrás de un z-index superiorPortal a #tooltip-root
DropdownRecortado por el scroll del contenedorPortal a body
Toast / NotificaciónAnidado en layouts que desplazan su posiciónPortal a #toast-root
Popover / DatepickerContexto de apilamiento impide solapamientoPortal a un contenedor raíz

3 · Ejemplo mínimo

Necesitamos un nodo destino en el HTML, fuera de #root:

index.html
<body>
  <div id="root"></div>         <!-- la app normal -->
  <div id="modal-root"></div>   <!-- destino del portal -->
</body>
src/components/PortalExample.jsx
import { createPortal } from "react-dom";

export default function PortalExample() {
  // createPortal recibe el JSX y el nodo DOM destino
  return createPortal(
    <div className="portal-box">
      <p>¡Estoy fuera de #root!</p>
    </div>,
    document.getElementById("modal-root")
  );
}
src/App.jsx
import PortalExample from "./components/PortalExample.jsx";

export default function App() {
  return (
    <div className="app">
      <h1>App normal dentro de #root</h1>
      <PortalExample />
      {/* el div.portal-box acaba en #modal-root, no aquí */}
    </div>
  );
}

Línea por línea:

  1. document.getElementById("modal-root") — obtenemos el nodo DOM real donde se renderizará el contenido. No es un componente React, es un nodo HTML nativo.
  2. createPortal(<div className="portal-box">…</div>, destino) — el primer argumento es el JSX a renderizar, el segundo es el nodo DOM de destino.
  3. El div.portal-box aparece como hijo de #modal-root en el DOM real, NO dentro de div.app.
  4. En React DevTools, PortalExample sigue apareciendo como hijo de App porque el árbol lógico no cambia.

4 · Ejemplo real

Vamos a construir un Modal con portal que incluye overlay, cierre al hacer clic fuera y manejo correcto de eventos. Este es exactamente el patrón que usaremos en el proyecto final (TaskFlow).

index.html — nodo destino para el modal
<body>
  <div id="root"></div>
  <div id="modal-root"></div>   <!-- todos los modales acaban aquí -->
</body>
src/components/Modal.jsx
import { createPortal } from "react-dom";
import { useEffect, useRef } from "react";

export default function Modal({ title, onClose, children }) {
  // Guardamos el nodo destino en una referencia para no consultar
  // el DOM en cada renderizado
  const modalRootRef = useRef(document.getElementById("modal-root"));

  // Enfoque automático al abrir y cierre con Escape
  useEffect(() => {
    function handleKeyDown(event) {
      if (event.key === "Escape") {
        onClose();
      }
    }
    document.addEventListener("keydown", handleKeyDown);
    return () => document.removeEventListener("keydown", handleKeyDown);
  }, [onClose]);

  return createPortal(
    // Overlay semitransparente que cierra al hacer clic fuera
    <div className="modal-overlay" onClick={onClose}>
      <div
        className="modal"
        onClick={(event) => event.stopPropagation()}
        role="dialog"
        aria-modal="true"
        aria-label={title}
      >
        <header className="modal__header">
          <h2 className="modal__title">{title}</h2>
          <button
            className="modal__close"
            onClick={onClose}
            aria-label="Cerrar"
          >
            ✕
          </button>
        </header>
        <div className="modal__body">{children}</div>
      </div>
    </div>,
    modalRootRef.current
  );
}
src/App.jsx — usando el modal con portal
import { useState } from "react";
import Modal from "./components/Modal.jsx";

export default function App() {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div className="app" style={{ overflow: "hidden", height: "100vh" }}>
      <h1>App con scroll oculto</h1>
      <p>Este contenedor tiene overflow:hidden pero el modal
        se renderiza FUERA, en #modal-root.</p>
      <p>Sin portal, el modal aparecería recortado.</p>
      <button onClick={() => setIsOpen(true)}>Abrir modal</button>

      {isOpen && (
        <Modal title="Confirmar acción" onClose={() => setIsOpen(false)}>
          <p>¿Estás seguro de que quieres eliminar este elemento?</p>
          <button onClick={() => { console.log("Eliminado"); setIsOpen(false); }}>
            Sí, eliminar
          </button>
          <button onClick={() => setIsOpen(false)}>Cancelar</button>
        </Modal>
      )}
    </div>
  );
}

Decisiones explicadas:

  • useRef para el nodo DOM: guardamos #modal-root en una ref para no hacer document.getElementById en cada render. La ref se calcula una vez y permanece estable.
  • Overlay + stopPropagation: el clic en el overlay (fondo oscuro) cierra el modal; el clic dentro del modal NO cierra porque detenemos la propagación en el contenedor interno.
  • Escape key: escuchamos el evento keydown en el documento y cerramos al pulsar Escape. El useEffect limpia el listener al desmontar.
  • Atributos ARIA: role="dialog", aria-modal="true" y aria-label para accesibilidad. Sin portal o con él, la accesibilidad es obligatoria.
  • overflow:hidden en el padre: probamos explícitamente que el modal no se recorta. Sin portal, el modal quedaría oculto parcialmente; con portal, aparece completo porque está en #modal-root fuera del flujo del padre.

5 · Buenas prácticas

HazEvitaPor qué
Crear nodos DOM estáticos en index.html para cada tipo de portal Crear nodos DOM dinámicamente en el cuerpo del componente Los nodos estáticos son predecibles, siempre existen y no dependen del ciclo de montaje de React.
Usar useRef para cachear la referencia al nodo destino Llamar a document.getElementById dentro del render Consultar el DOM durante el render rompe la pureza y es innecesario: el nodo no cambia.
Mantener la accesibilidad ARIA aunque el DOM esté fuera Asumir que el portal «invisible» a efectos DOM no necesita accesibilidad El lector de pantalla recorre el árbol de accesibilidad, que sigue el árbol React, no el DOM.
Gestionar el foco manualmente (trampa de foco) Dejar el foco «perdido» al abrir un modal con portal El foco no sigue automáticamente al portal; debes moverlo al primer elemento interactivo del modal.
Usar portal solo para UI que necesita salir del contexto de apilamiento Portals para todos los componentes «por si acaso» Cada portal añade complejidad de depuración (el DOM no coincide con el árbol de componentes). Úsalo solo cuando sea necesario.
Limpiar eventos globales en el useEffect de retorno Olvidar remover listeners al desmontar el portal Los listeners quedan huérfanos, fugas de memoria y comportamientos erráticos.

Patrón recomendado: un proveedor de portal

Para apps grandes, conviene crear un componente Portal genérico que abstraiga la obtención del nodo y permita cambiar el destino fácilmente: 

import { createPortal } from "react-dom";

// Componente contenedor que recibe el destino como prop
// con valor por defecto document.body
export default function Portal({ children, target = document.body }) {
  return createPortal(children, target);
}

// Uso:
// <Portal target={document.getElementById("modal-root")}>
//   <ModalContent />
// </Portal>

6 · Errores habituales

Error 1: el nodo destino aún no existe en el DOM

✘ Incorrecto 
function Modal({ children }) {
  // Si modal-root no existe aún, esto devuelve null y React lanza error
  const node = document.getElementById("modal-root");

  return createPortal(
    <div className="modal">{children}</div>,
    node   // ⚠️ node puede ser null
  );
}
✔ Correcto 
function Modal({ children }) {
  const modalRoot = document.getElementById("modal-root");

  // Si no existe el nodo, no renderizamos nada
  if (!modalRoot) return null;

  return createPortal(
    <div className="modal">{children}</div>,
    modalRoot
  );
}

Error 2: confundir el árbol React con el árbol DOM para eventos

✘ Creen errónea 
// El padre NO puede capturar eventos del portal con addEventListener
// en su propio nodo DOM porque el portal está fuera del DOM del padre
function Parent() {
  return (
    <div onClick={() => console.log("clic en padre")}>
      <Portal>
        <button>Clic aquí</button>  {/* ✔️ el click SÍ llega al padre */}
      </Portal>
    </div>
  );
}

Explicación: aunque el DOM del portal esté fuera, React hace que los eventos sintéticos burbujeen a través del árbol de componentes, NO del DOM. El clic en el botón sí llega al onClick del padre porque en el árbol React el portal sigue siendo hijo. Con addEventListener nativo no funcionaría, pero con los eventos de React sí.

Error 3: renderizar el portal en cada actualización de estado

✘ Ineficiente 
function Modal({ children }) {
  // Esto ejecuta document.getElementById en CADA render
  return createPortal(
    children,
    document.getElementById("modal-root")
  );
}
✔ Correcto 
import { useRef } from "react";

function Modal({ children }) {
  // La ref se calcula una vez y permanece estable
  const targetRef = useRef(document.getElementById("modal-root"));

  return createPortal(children, targetRef.current);
}

Error 4: modificar el nodo destino directamente (mutación del DOM)

✘ Peligroso 
useEffect(() => {
  // Mutar el nodo destino interfiere con React
  document.getElementById("modal-root").innerHTML = "";
}, []);
✔ Correcto 
// Deja que React gestione el contenido del destino del portal.
// Si necesitas limpiar, desmonta el componente que usa createPortal.
// No toques el nodo destino manualmente.

7 · Ejercicio guiado

Vamos a crear un Tooltip con portal paso a paso:

  1. Añade el nodo destino en index.html:

    <body>
  <div id="root"></div>
  <div id="tooltip-root"></div>
</body>

  2. Crea el componente Tooltip con portal:

    import { createPortal } from "react-dom";

export default function Tooltip({ text, children }) {
  return (
    <div className="tooltip-wrapper">
      {children}
      {createPortal(
        <div className="tooltip" role="tooltip">{text}</div>,
        document.getElementById("tooltip-root")
      )}
    </div>
  );
}

  3. Úsalo en App con un botón:

    import Tooltip from "./components/Tooltip.jsx";

export default function App() {
  return (
    <div className="app" style={{ overflow: "hidden" }}>
      <Tooltip text="Guardar cambios">
        <button>💾 Guardar</button>
      </Tooltip>
    </div>
  );
}

  4. Comprueba: el tooltip aparece fuera del div.app, en #tooltip-root. Sin portal, el tooltip se recortaría por el overflow: hidden del padre.

  5. Mejora: añade estilos CSS para posicionar el tooltip relativo al botón. Puedes usar getBoundingClientRect del wrapper para calcular la posición y pasar coordenadas como props o estado.

8 · Reto

🎯 Sistema de notificaciones toast con portal

Crea un sistema de notificaciones toast (mensajes emergentes que aparecen en la esquina superior derecha) usando un portal. Debe incluir:

  • Un contenedor <ToastProvider> que gestione la lista de toasts visibles.
  • Un useToast hook personalizado que permita a cualquier componente disparar un toast: showToast({ message, type: 'success' | 'error' }).
  • Los toasts deben renderizarse mediante createPortal a #toast-root.
  • Auto-destruirse después de 3 segundos con animación de salida.
  • Máximo 3 toasts visibles simultáneamente; si llega un cuarto, elimina el más antiguo.

Pistas:

  • Usa useState para la lista de toasts y useEffect con setTimeout para la auto-destrucción.
  • El portal puede renderizar un array de toasts mapeado sobre la lista de estado.
  • Los estilos CSS deben hacer que los toasts aparezcan apilados en la esquina superior derecha con position: fixed.

9 · Resumen

  • createPortal(children, domNode) renderiza un subárbol React en un nodo DOM diferente, fuera del padre natural.
  • El árbol React (lógico) se mantiene intacto: el portal sigue siendo hijo del componente que lo crea. Eventos y contexto fluyen normalmente.
  • El árbol DOM (físico) cambia: el contenido aparece en domNode, no dentro del contenedor del padre.
  • Casos de uso principales: modales, tooltips, dropdowns, popovers, toasts, datepicker.
  • Siempre crea nodos destino estáticos en index.html (uno por tipo de portal).
  • Usa useRef para cachear la referencia al nodo destino y evitar consultas al DOM en cada render.
  • Los eventos sintéticos de React burbujean a través del árbol de componentes, no del DOM.
  • No olvides la accesibilidad: role="dialog", aria-modal, gestión de foco y cierre con Escape.

10 · Preguntas frecuentes

¿createPortal crea un nuevo contexto de React?

No. El portal respeta el árbol de Context API: cualquier Provider que envuelva al componente que usa createPortal sigue siendo accesible desde dentro del portal. El contexto viaja por el árbol React (lógico), no por el DOM.

¿Puedo tener varios portales al mismo nodo destino?

Sí. Múltiples componentes pueden usar createPortal hacia el mismo domNode. React los monta como hijos hermanos en ese nodo, en el orden en que se renderizan. Es común tener varios modales o toasts en el mismo contenedor raíz.

¿Cómo hago testing de un componente que usa createPortal?

Con React Testing Library no necesitas cambiar nada: los portales se renderizan igual. El contenido del portal aparece en el screen y puedes buscarlo con screen.getByText o screen.getByRole. Asegúrate de que el nodo destino exista en tu mock del DOM (jsdom lo crea automáticamente con document.getElementById si existe en el HTML del test).

¿createPortal afecta al rendimiento?

Mínimo. React optimiza los portales como cualquier otro fragmento del árbol virtual. El impacto es despreciable comparado con el beneficio de tener modales y tooltips bien posicionados. El coste real está en las consultas al DOM (document.getElementById), que se evitan cacheando con useRef.

¿Puedo pasar un componente React como nodo destino de createPortal?

No. domNode debe ser un nodo DOM real, no un elemento React. Si necesitas renderizar dentro de otro componente, usa composición (children) en lugar de portal. El portal está diseñado para saltarse la jerarquía de componentes y anclar a un nodo DOM específico.

¿Qué pasa con el servidor-side rendering (SSR) y portales?

En SSR, createPortal devuelve null porque no existe el DOM del lado del servidor. Los componentes con portal deben detectar el entorno (con typeof window === 'undefined') y renderizar un fallback o nada durante el renderizado en servidor. Lo veremos en detalle si abordamos frameworks como Next.js más adelante.
