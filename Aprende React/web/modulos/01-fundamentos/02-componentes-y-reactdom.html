Componentes y ReactDOM

Módulo 1 · Fundamentos ⏱ 35 minutos

1 · Introducción

En la lección anterior aprendiste a escribir JSX. Ahora vamos a unir tres piezas que ya conoces por separado —componentes, Virtual DOM y el punto de entrada— para entender el ciclo de vida completo de una app React: desde que el navegador descarga index.html hasta que tu árbol de componentes aparece en pantalla.

Qué aprenderás:

  • La anatomía exacta de un componente de función (todas sus formas válidas).
  • Cómo react-dom monta tu aplicación en el DOM real (createRoot).
  • Qué significa «renderizar» (y por qué no es lo mismo que «pintar»).
  • Exportar e importar componentes entre archivos como un profesional.

Errores típicos: llamar al componente como función ({UserCard()}) en lugar de usarlo como elemento (<UserCard />), olvidar el export, y confundir react con react-dom.

2 · Teoría

Anatomía completa de un componente de función

Un componente, en su forma más honesta, es esto:

function NombreDelComponente(props) {
  // 1. Lógica: cálculos, datos, funciones auxiliares
  // 2. return: la descripción de la UI (JSX)
}

Variantes que verás en código real (todas correctas):

// a) Declaración de función (la más común y la que usamos en el curso)
function Button() {
  return <button>Guardar</button>;
}

// b) Arrow function asignada a una constante
const Button = () => {
  return <button>Guardar</button>;
};

// c) Arrow function con return implícito (para componentes de una línea)
const Button = () => <button>Guardar</button>;

¿Cuál elegir? La comunidad usa las tres. En este curso: declaración de función (a) para componentes (más legible, mejor nombre en los stack traces y en DevTools) y arrow functions para callbacks y funciones auxiliares. Lo importante es la consistencia dentro del proyecto.

react vs react-dom: los dos paquetes

PAQUETE react PAQUETE react-dom ───────────── ────────────────── • define componentes • es el RENDERER para navegadores • define hooks (useState…) • createRoot(): monta la app en #root • NO sabe nada del DOM • sabe crear/modificar nodos reales • sirve para web, móvil, VR… • solo para la web ┌────────────────────────────────┐ │ react + react-dom = web │ │ react + react-native = apps │ └────────────────────────────────┘

Por eso importamos useState de "react" pero createRoot de "react-dom/client". No es arbitrario: es la arquitectura multi-plataforma de React.

createRoot: el nacimiento de la aplicación

// src/main.jsx — sucede UNA sola vez en toda la vida de la app
const root = createRoot(document.getElementById("root"));
root.render(<App />);

Pasos internos:

  1. document.getElementById("root") localiza el div vacío de index.html.
  2. createRoot(div) crea una raíz de React: el punto donde el árbol de componentes se conecta con el DOM real.
  3. root.render(<App />) ejecuta el primer render: ejecuta App y todos sus hijos, genera el Virtual DOM y lo materializa dentro del div.
💡 ¿Por qué <App /> y no App()?

<App /> crea un elemento (la descripción: «pinta un App aquí») y se lo entrega a React, que decide CUÁNDO ejecutar la función. Si llamaras App() tú directamente, ejecutarías el componente fuera del control de React: sin hooks funcionando, sin reconciliación, sin prioridades concurrentes. React necesita ser quien llama a tus componentes. Regla de oro: tú describes, React ejecuta.

Renderizar ≠ pintar

Concepto fino pero crucial (ya lo olíamos en el Módulo 0):

  • Renderizar = React ejecuta tus componentes y calcula el nuevo Virtual DOM. Ocurre en memoria, es barato y puede pasar muchas veces sin que el usuario note nada.
  • Pintar (commit + paint) = React aplica las diferencias al DOM real y el navegador lo dibuja. Solo ocurre si el diffing encuentra cambios.

Cuando en el Módulo 4 hablemos de «re-renders», estaremos hablando de la primera fase. La segunda es la que React se encarga de minimizar.

Exportar e importar: el sistema de módulos en acción

// ── Export POR DEFECTO (default): uno por archivo ──────────────
export default function UserCard() { … }

// Se importa SIN llaves y con el nombre que TÚ elijas:
import UserCard from "./components/UserCard.jsx";
import Tarjeta from "./components/UserCard.jsx";   // también válido

// ── Export NOMBRADO (named): varios por archivo ────────────────
export function formatDate(date) { … }
export const APP_VERSION = "1.0";

// Se importa CON llaves y el nombre EXACTO:
import { formatDate, APP_VERSION } from "./utils.js";

Convención profesional: un componente por archivo, exportado como default, y utilidades/helpers como exports nombrados. Así import X from "./X.jsx" es predecible en todo el proyecto.

¿Por qué la extensión .jsx en los imports?

Con Vite puedes omitirla (import UserCard from "./UserCard" funciona), pero escribirla explícita deja claro qué archivo es y evita ambigüedades. En todo el curso la escribimos.

3 · Ejemplo mínimo

Dos archivos, un componente usado desde otro:

src/components/Badge.jsx
// Componente mínimo reutilizable
export default function Badge() {
  return <span className="badge">Nuevo</span>;
}
src/App.jsx
import Badge from "./components/Badge.jsx";

export default function App() {
  return (
    <h1>
      Panel de control <Badge />
    </h1>
  );
}

Línea por línea:

  1. import Badge from "./components/Badge.jsx" — trae el export default del otro archivo. La ruta es relativa al archivo actual.
  2. <Badge /> — se usa como etiqueta JSX con mayúscula: React ejecuta la función Badge y coloca su resultado (un <span>) dentro del <h1>.
  3. export default en ambos — un componente por archivo, exportación por defecto.

4 · Ejemplo real

La estructura de una app real (la del proyecto del módulo, en proyectos/m01-pagina-perfil): varios componentes, cada uno en su archivo, compuestos desde App.

src/ ├── main.jsx → createRoot(#root).render(<App />) ├── App.jsx → compone la página └── components/ ├── ProfileHeader.jsx → avatar + nombre + título ├── StatsBar.jsx → fila de estadísticas (usa StatItem) │ └── StatItem.jsx → un número + etiqueta └── Bio.jsx → biografía
src/App.jsx
import ProfileHeader from "./components/ProfileHeader.jsx";
import StatsBar from "./components/StatsBar.jsx";
import Bio from "./components/Bio.jsx";

// App solo COMPONE: cada pieza vive en su propio archivo
export default function App() {
  return (
    <main className="profile-page">
      <ProfileHeader />
      <StatsBar />
      <Bio />
    </main>
  );
}

Decisiones explicadas:

  • App actúa como director de orquesta: no sabe cómo se pinta el header; solo decide QUÉ piezas hay y en qué orden. Cada pieza se puede leer, probar y cambiar por separado.
  • Carpeta components/ desde el primer día: aunque tengas 3 componentes, la costumbre escala a 300.
  • ¿Cuándo no extraer a otro archivo? Cuando el subcomponente es minúsculo y solo lo usa un padre (ej: StatItem solo existe para StatsBar). Puede vivir en el mismo archivo del padre; extraerlo es opcional, no dogma.
🔍 React DevTools en esta estructura

Pestaña Components: verás App → ProfileHeader / StatsBar / Bio y dentro de StatsBar tres StatItem. Si un componente aparece como «Anonymous», es porque se exportó una arrow function anónima (export default () => …): otra razón para usar funciones con nombre.

6 · Errores habituales

Error 1: olvidar el export (o importar lo que no se exportó)

✘ Incorrecto 
// Badge.jsx — sin export!
function Badge() { return <span>Nuevo</span>; }

// App.jsx
import Badge from "./Badge.jsx";
// ✘ Error: "The requested module does not provide an export named 'default'"
✔ Correcto 
// Badge.jsx
export default function Badge() { return <span>Nuevo</span>; }

Error 2: llaves al importar un export default

✘ Incorrecto 
import { Badge } from "./Badge.jsx"; // ✘ Badge es default, no nombrado
✔ Correcto 
import Badge from "./Badge.jsx";     // default → SIN llaves

Truco mnemotécnico: llaves = «desestructuro los exports nombrados del módulo». Sin llaves = «dame el default, sea lo que sea».

Error 3: renderizar el componente llamándolo

✘ Incorrecto 
function App() {
  return <div>{Badge()}</div>;  // ✘ ejecutas la función tú,
}                                 //   fuera del control de React
✔ Correcto 
function App() {
  return <div><Badge /></div>; // ✔ describes el elemento; React lo ejecuta
}

Por qué importa tanto: cuando Badge tenga hooks (Módulos 4-6), {Badge()} lanzará el temido error «Invalid hook call». Los hooks solo funcionan cuando React es quien ejecuta el componente.

Error 4: importar createRoot de "react"

✘ Incorrecto 
import { createRoot } from "react"; // ✘ createRoot NO está en "react"
✔ Correcto 
import { createRoot } from "react-dom/client"; // ✔ vive en react-dom

8 · Reto

🎯 Página estática completa por componentes

Construye una página «Acerca de mí» con esta estructura, cada pieza en su archivo dentro de src/components/:

App ├── PageHeader (título de la página) ├── AboutMe (párrafo de presentación) ├── Hobbies (lista de 3 hobbies, hardcodeados con <li>) └── PageFooter (© tu nombre, año actual calculado con new Date().getFullYear())

9 · Resumen

  • Un componente es una función con nombre (PascalCase) que devuelve JSX. Las tres sintaxis (declaración, arrow, return implícito) son válidas; consistencia ante todo.
  • react define componentes y hooks (multiplataforma); react-dom es el renderer del navegador (createRoot).
  • createRoot(#root).render(<App />) ocurre UNA vez; después React se auto-actualiza.
  • Renderizar (ejecutar componentes, en memoria) no es pintar (tocar el DOM): React minimiza lo segundo.
  • Export default → import sin llaves y nombre libre. Exports nombrados → import con llaves y nombre exacto.
  • NUNCA llames un componente ({Badge()}): descríbelo (<Badge />) y deja que React lo ejecute.

10 · Preguntas frecuentes

¿Qué pasa si renderizo dos veces el mismo componente?

Nada malo: son dos instancias independientes (como dos objetos de la misma clase). Cada una tendrá sus props y, cuando lleguemos al estado, su propio estado.

¿Puedo tener varios createRoot?

Sí, en divs distintos: cada raíz es un árbol React independiente (widgets embebidos). Lo normal en una SPA es uno solo.

¿main.jsx puede tener otros nombres?

Sí, es convención de la plantilla. Lo único importante es que coincida con el <script src> de index.html.

¿Qué diferencia hay entre .js y .jsx?

Solo semántica: .jsx avisa de que el archivo contiene JSX. Vite compila ambos. Convención del curso: .jsx para componentes, .js para utilidades puras.

¿Es obligatorio el export default?

No, puedes usar solo exports nombrados. Pero «un componente = un archivo = un default export» es la convención dominante en el ecosistema y hace los imports predecibles.
