Fragments

Módulo 1 · Fundamentos ⏱ 20 minutos

1 · Introducción

Ya conoces la regla: un componente solo puede devolver un elemento raíz. La solución «de manual» es envolver todo en un <div>… pero eso mete en el HTML cajas vacías que no aportan nada, rompen layouts CSS y ensucian el DOM. React resuelve esto con los Fragments: un envoltorio invisible que agrupa en JSX sin existir en el HTML final.

Qué aprenderás: qué es un Fragment, sus dos sintaxis (y la diferencia crucial entre ellas: la key), y por qué los «divs de más» son un problema real en producción, no solo una cuestión estética.

2 · Teoría

El problema: el «div innecesario»

Supón un componente que debe devolver dos celdas de una tabla:

✘ Con un div: HTML roto 
function Cells() {
  return (
    <div>            {/* ← necesitamos un padre... */}
      <td>Nombre</td>
      <td>Edad</td>
    </div>
  );
}

// Se usa dentro de <tr>…</tr> y el HTML resultante es:
// <tr><div><td>…  💥 INVÁLIDO: <div> no puede ser hijo de <tr>
// El navegador lo «repara» moviendo cosas de sitio. Caos.

Otros casos donde el div extra hace daño de verdad:

  • Flexbox/Grid: un div intermedio se convierte en el «hijo flex», rompiendo la distribución que diseñaste para sus hijos.
  • Selectores CSS: .card > p deja de funcionar si metes un div entre .card y los p.
  • Accesibilidad y semántica: lectores de pantalla navegan mejor un DOM limpio; cada caja vacía es ruido.
  • Rendimiento marginal: miles de divs vacíos en una app grande son nodos que el navegador mantiene por gusto.

La solución: Fragment, el envoltorio fantasma

React.Fragment es un componente especial que agrupa a sus hijos sin generar ningún nodo en el DOM. Existe en el Virtual DOM (para que React pueda reconciliar), pero desaparece en el HTML final: 

import { Fragment } from "react";

function Cells() {
  return (
    <Fragment>
      <td>Nombre</td>
      <td>Edad</td>
    </Fragment>
  );
}

// HTML final: <tr><td>Nombre</td><td>Edad</td></tr>  ✔ VÁLIDO

Las dos sintaxis (y su diferencia crucial)

<Fragment> (larga)<> (corta)
Import necesarioimport { Fragment } from "react"Ninguno
Acepta keySÍ ✔NO ✘
Uso típicoFragments dentro de un .map()Todo lo demás (el 95 % de los casos)

La sintaxis corta <> </> (llamada «fragment shorthand») es la que usarás casi siempre. La larga solo es necesaria en listas, porque React exige una key en cada elemento de un .map() y <> no admite atributos. Lo veremos con lupa en el Módulo 2.

JSX QUE ESCRIBES VIRTUAL DOM HTML REAL ────────────────── ─────────── ───────── <> Fragment (nodo virtual) <h1>Hola</h1> ──► ├── h1 ──► <h1>Hola</h1> <p>Mundo</p> └── p <p>Mundo</p> </> (desaparece al pintar) ¡sin caja extra!

3 · Ejemplo mínimo

src/App.jsx
export default function App() {
  return (
    <>
      <h1>Título</h1>
      <p>Párrafo hermano del título, sin div envolvente.</p>
    </>
  );
}

Línea por línea:

  1. <> — abre el Fragment. No necesita import (con la sintaxis corta) y no admite atributos.
  2. Dos elementos hermanos dentro: el return sigue devolviendo una sola cosa (el Fragment), cumpliendo la regla.
  3. </> — cierra el Fragment. En el HTML final solo existirán el <h1> y el <p>.

Compruébalo: F12 → Elements. No hay ningún nodo envolvente alrededor de <h1> y <p> (más allá de #root).

4 · Ejemplo real

Caso 1 — Layout con CSS Grid donde un div extra rompería la cuadrícula:

src/components/Dashboard.jsx
// El CSS espera que .grid tenga EXACTAMENTE 3 hijos directos.
// Un div envolvente convertiría a Sidebar+Main+Footer en un solo hijo.
export default function Dashboard() {
  return (
    <div className="grid">
      <Sidebar />
      <MainPanel />
      <StatusBar />
    </div>
  );
}

// Sidebar necesita devolver dos hermanos: usa Fragment para no
// contaminar la cuadrícula con un div extra.
function Sidebar() {
  return (
    <>
      <nav className="sidebar__nav">…</nav>
      <aside className="sidebar__ads">…</aside>
    </>
  );
}

Caso 2 — Fragment con key en una lista (adelanto del Módulo 2):

Definiciones de un glosario
import { Fragment } from "react"; // ← necesario para la sintaxis larga

const terms = [
  { id: 1, name: "Props", definition: "Datos que recibe un componente." },
  { id: 2, name: "Estado", definition: "Memoria interna del componente." },
];

export default function Glossary() {
  return (
    <dl>
      {terms.map((term) => (
        // <Fragment key={…}>: agrupa dt+dd Y aporta la key que React exige.
        // Con <> no podrías poner la key. Con <div> romperías el <dl>.
        <Fragment key={term.id}>
          <dt>{term.name}</dt>
          <dd>{term.definition}</dd>
        </Fragment>
      ))}
    </dl>
  );
}

Por qué es el ejemplo perfecto: un <dl> solo admite <dt> y <dd> como hijos. Un <div> lo invalidaría; <> no admite key; <Fragment key> es la ÚNICA solución correcta. Cuando la necesitas, la necesitas de verdad.

5 · Buenas prácticas

HazEvitaPor qué
<> como envoltorio por defecto Divs «porque hay que devolver una cosa» DOM limpio: layouts predecibles, CSS sin sorpresas, mejor accesibilidad.
<Fragment key={id}> en map() que devuelven varios hermanos <> dentro de un map La sintaxis corta no acepta key → warning de React y riesgo de bugs de reconciliación.
Usar un contenedor REAL (section, article) cuando tiene sentido semántico o de estilo Fragments donde en realidad quieres una caja con clase CSS El Fragment es invisible: no puede llevar className ni estilos. Si necesitas estilizar el grupo, necesitas un elemento real.

6 · Errores habituales

Error 1: intentar poner className al Fragment

✘ Incorrecto 
return (
  <> className="card"          {/* 💥 los Fragments no aceptan props */}
    <h2>Hola</h2>
  </>
);
✔ Correcto 
return (
  <section className="card">   {/* necesitas un elemento REAL para estilos */}
    <h2>Hola</h2>
  </section>
);

Regla: Fragment solo acepta la prop key (y children). Nada más.

Error 2: <> con key dentro de un map

✘ Incorrecto 
{items.map((item) => (
  <>                       {/* ✘ aquí no puedes poner key */}
    <dt>{item.term}</dt>
    <dd>{item.def}</dd>
  </>
))}
✔ Correcto 
{items.map((item) => (
  <Fragment key={item.id}>   {/* ✔ sintaxis larga + key */}
    <dt>{item.term}</dt>
    <dd>{item.def}</dd>
  </Fragment>
))}

7 · Ejercicio guiado

  1. Crea un componente UserInfo que devuelva un <h2> y un <p> sin envoltorio, usando <>.

  2. Úsalo dentro de App entre dos hermanos. Inspecciona el HTML (F12): verifica que NO existe ningún nodo extra alrededor del h2 y el p.

  3. Cambia el <> por un <div>, vuelve a mirar el HTML y observa la diferencia. Este pequeño experimento fija el concepto para siempre.

  4. Intenta poner className al <> y lee el warning de la consola. Cambia a <section className="…"> cuando necesites la clase.

8 · Reto

🎯 La tabla imposible

Crea un componente TableRow que reciba una persona (hardcodeada) y devuelva DOS filas <tr> hermanas: una con el nombre y otra con el email. Úsalo dentro de un <tbody> en App.

  1. Comprueba que con <div> el HTML es inválido (el navegador sacará el div fuera de la tabla: míralo en Elements).

  3. Bonus: renderiza TRES personas con un .map() — ¿qué sintaxis de Fragment necesitas ahora y por qué?

9 · Resumen

  • Un componente devuelve un único elemento; el Fragment agrupa sin ensuciar el DOM.
  • Los divs innecesarios rompen tablas, Flexbox/Grid, selectores CSS y accesibilidad.
  • <>…</>: sintaxis corta, sin import, sin props. Es la opción por defecto.
  • <Fragment key={id}>: sintaxis larga, la única que acepta key — obligatoria en map() con varios hermanos.
  • El Fragment existe en el Virtual DOM pero no en el HTML real.
  • Si necesitas estilizar el grupo (className), necesitas un elemento real, no un Fragment.

10 · Preguntas frecuentes

¿Los Fragments afectan al rendimiento?

Al contrario: eliminan nodos DOM innecesarios. En el VDOM son nodos baratísimos (un objeto tipo y nada más). Úsalos sin miedo.

¿Se pueden anidar Fragments?

Sí, sin problema: <><>…</><>…</></>. Aunque si necesitas eso, probablemente estás dividiendo mal el componente: considera extraer componentes hijos.

¿Por qué <> no acepta key?

Es una limitación de la sintaxis JSX: <> no admite atributos porque el parser no tendría dónde ponerlos (no hay nombre de etiqueta). Por eso existe la forma larga.

¿React.Fragment aparece en las DevTools?

En React DevTools (Components) sí verás nodos Fragment en el árbol; en Elements (el DOM real) no existen. Es coherente con su naturaleza: viven solo en el Virtual DOM.
