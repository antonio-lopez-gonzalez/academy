Props

Módulo 1 · Fundamentos ⏱ 35 minutos

1 · Introducción

Hasta ahora nuestros componentes pintan siempre lo mismo: son piezas «de cartón». Las props (abreviatura de properties) son el mecanismo que las convierte en piezas reutilizables de verdad: datos que un componente padre pasa a su hijo para configurarlo.

Si un componente es una función, las props son sus argumentos. Esta lección es probablemente la más importante del Módulo 1: todo React se reduce a «componentes que reciben props y devuelven UI».

Errores típicos que corregiremos: intentar modificar las props dentro del componente (están prohibido), confundir props con estado, y pasar 15 props sueltas cuando deberías pasar un objeto.

2 · Teoría

Props = argumentos de la función componente

Cuando escribes:

<Avatar src="ana.png" size={48} />

React empaqueta todos los atributos en un único objeto y lo pasa como primer argumento a tu función: 

// React hace internamente algo equivalente a:
Avatar({ src: "ana.png", size: 48 });
EL VIAJE DE LAS PROPS ───────────────────── Padre escribe: <Avatar src="ana.png" size={48} /> │ ▼ React crea el objeto props { src: "ana.png", size: 48 } │ ▼ lo entrega como argumento Hijo recibe: function Avatar(props) { … } │ ▼ props.src → "ana.png" props.size → 48

Las tres reglas de oro de las props

  1. Las props son de SOLO LECTURA. Un componente JAMÁS modifica sus props. Son del padre; el hijo solo las lee. (Si necesitas cambiar un dato, necesitas estado — Módulo 4 — o pedirle al padre que lo cambie mediante un callback.)
  2. Fluyen en un solo sentido: padre → hijo. Un hijo no puede pasar props a su padre ni a sus hermanos. La comunicación «hacia arriba» se hace con funciones (callbacks) que el padre pasa como prop — lección de eventos del Módulo 3.
  3. Cualquier valor JavaScript puede ser una prop: strings, números, booleanos, arrays, objetos, funciones, elementos JSX e incluso componentes enteros.

Sintaxis: atributos JSX y desestructuración

Por convención universal, no se usa props.name todo el rato: se desestructura el objeto props directamente en la firma de la función. Es JavaScript normal (parámetros desestructurados), nada específico de React: 

// ❚ Versión sin desestructurar (válida pero verbosa)
function Avatar(props) {
  return <img src={props.src} width={props.size} alt="avatar" />;
}

// ✔ Versión idiomática: desestructurar en el parámetro
function Avatar({ src, size }) {
  return <img src={src} width={size} alt="avatar" />;
}

Valores por defecto

Si el padre no pasa una prop, su valor es undefined. Los valores por defecto se declaran en la propia desestructuración (sintaxis moderna de JavaScript; la antigua defaultProps está deprecada en componentes de función): 

// Si el padre no pasa "size", valdrá 40
function Avatar({ src, size = 40 }) {
  return <img src={src} width={size} height={size} alt="avatar" />;
}

<Avatar src="a.png" />        → size = 40 (por defecto)
<Avatar src="a.png" size={64} /> → size = 64

Tipos de props en acción

<ProductCard
  title="Teclado"                    // string: comillas
  price={89.9}                       // número: LLAVES (es una expresión JS)
  inStock={true}                     // booleano: llaves
  discount                           // booleano true abreviado (= {true})
  tags={["nuevo", "oferta"]}         // array: llaves
  product={{ id: 1, name: "…" }}     // objeto: llaves (doble llave: expr + objeto)
  onBuy={(id) => comprar(id)}        // función: llaves
  badge={<Badge type="new" />}       // elemento JSX: llaves
/>
⚠ La trampa de las comillas

price="89.9" pasa un string; price={89.9} pasa un número. Con números y booleanos, las llaves son obligatorias. Es el error de tipos más común de los primeros meses («sumo 1 + 1 y me da 11»).

3 · Ejemplo mínimo

src/components/Greeting.jsx
// Recibe UNA prop: "name"
export default function Greeting({ name }) {
  return <h2>Hola, {name}</h2>;
}
src/App.jsx
import Greeting from "./components/Greeting.jsx";

export default function App() {
  return (
    <div>
      <Greeting name="Ana" />
      <Greeting name="Carlos" />
      <Greeting name="Lucía" />
    </div>
  );
}

Línea por línea:

  1. function Greeting({ name }) — el componente declara qué props espera, desestructuradas.
  2. <Greeting name="Ana" /> — el padre pasa el valor como atributo JSX.
  3. Tres instancias, tres valores distintos: el mismo componente, tres resultados. Eso es reutilización.

4 · Ejemplo real

Un botón reutilizable de biblioteca de componentes (nivel profesional):

src/components/Button.jsx
// Botón de sistema de diseño: configurable por props, con valores
// por defecto sensatos. Fíjate en la técnica de las clases dinámicas.
export default function Button({
  children,               // el contenido interno (próxima lección)
  variant = "primary",    // "primary" | "secondary" | "danger"
  size = "md",            // "sm" | "md" | "lg"
  disabled = false,       // los booleanos tienen buen default
  onClick,                // callback: el padre decide QUÉ hace
}) {
  // Construimos la clase CSS a partir de las props (template string)
  const className = `btn btn--${variant} btn--${size}`;

  return (
    <button className={className} disabled={disabled} onClick={onClick}>
      {children}
    </button>
  );
}
uso desde cualquier padre
<Button onClick={() => alert("guardado")}>Guardar</Button>
<Button variant="secondary" size="sm">Cancelar</Button>
<Button variant="danger" disabled>Eliminar</Button>

Decisiones explicadas:

  • Defaults defensivos: variant y size tienen valores razonables, así el uso mínimo (<Button>) ya funciona bien. Un buen componente es fácil de usar bien y difícil de usar mal.
  • La lógica de clases fuera del JSX: el template string se calcula antes del return, no en medio del marcado.
  • onClick es una prop-función: el botón no sabe QUÉ hace; el padre lo decide. Así el mismo Button sirve para guardar, borrar o enviar. Es la inversión de control aplicada a la UI (como un Action/Func en C#).
  • Props «proxy»: disabled se pasa tal cual al <button> nativo: el componente añade estilo/comportamiento pero respeta la API del elemento HTML.

5 · Buenas prácticas

HazEvitaPor qué
Desestructurar props en la firma con defaults props.name, props.age… repetido por el cuerpo Legibilidad: la firma del componente documenta qué props acepta.
Pasar un objeto cuando hay muchos datos relacionados (user={user}) 12 props sueltas del mismo usuario El «prop drilling» de datos agrupados es ruido; un objeto cohesionado viaja mejor.
Nombres de props desde el punto de vista del HIJO (variant, no buttonVariant) Nombres que repiten el contexto del padre El componente debe ser independiente de quién lo usa.
Callbacks con prefijo on (onSave, onDelete) Nombres como saveFunction o handleIt Convención universal: on* = «avísame cuando ocurra esto».
Tratar las props como inmutables SIEMPRE Reasignar props.x = … o mutar props.user.name = … Rompe el flujo unidireccional y la reconciliación: el cambio no se reflejará bien y corromperás los datos del padre.

6 · Errores habituales

Error 1: modificar las props

✘ Incorrecto 
function Counter({ count }) {
  count = count + 1;   // 💥 PROHIBIDO: las props son de solo lectura
  return <p>{count}</p>;
}
✔ Correcto 
function Counter({ count }) {
  const next = count + 1;  // ✔ calcula valores NUEVOS en variables tuyas
  return <p>Siguiente: {next}</p>;
}
// Y si el dato debe CAMBIAR de verdad → useState (Módulo 4)

Error 2: strings donde van números/booleanos

✘ Incorrecto 
<Price value="19.99" />      // string, no número: 19.99 + 1 = "19.991"
<Modal open="false" />        // string "false" es TRUTHY: ¡el modal se abre!
✔ Correcto 
<Price value={19.99} />      // número real
<Modal open={false} />        // booleano real
<Modal open />                // abreviatura de open={true}

Error 3: renombrar props al azar entre padre e hijo

✘ Incorrecto 
// El padre pasa "userName":
<Greeting userName="Ana" />
// …pero el hijo espera "name":
function Greeting({ name }) {
  return <h2>Hola, {name}</h2>; // "Hola, undefined" 😶
}

Por qué pasa tanto: React no valida props en desarrollo (sin TypeScript). Cómo evitarlo: desestructura siempre en la firma (verás claro qué espera el componente) y revisa en DevTools qué props llegan realmente.

7 · Ejercicio guiado

Vamos a crear un componente SkillTag reutilizable:

  1. Crea src/components/SkillTag.jsx:

    export default function SkillTag({ name, level = 1 }) {
  // level: 1-3. Pintamos tantos puntos como nivel.
  const dots = "●".repeat(level) + "○".repeat(3 - level);
  return (
    <span className="skill-tag">
      {name} <span className="skill-tag__dots">{dots}</span>
    </span>
  );
}

  2. Úsalo en App con distintos valores:

    <SkillTag name="JavaScript" level={3} />
<SkillTag name="React" level={2} />
<SkillTag name="Kubernetes" />   {/* usa el default: level 1 */}

  3. Comprueba en DevTools (Components → SkillTag) qué props recibe cada instancia. Fíjate en que la tercera muestra level: undefined como prop recibida — el default se aplica al desestructurar.

  4. Prueba el error 2 a propósito: pasa level="3" (string) y observa que "●".repeat("3") funciona por coerción… pero 3 - level sigue siendo 0 por suerte. Ahora prueba level + 1 dentro: «31». Moraleja: llaves para números.

8 · Reto

🎯 AlertBox configurable

Crea un componente AlertBox con estas props:

  • type: "info" | "success" | "warning" | "error" (default: "info")
  • title: string obligatorio
  • children: el mensaje detallado
  • onClose: función opcional — si existe, muestra un botón «✕» que la llama

Requisitos: la clase CSS se compone como alert alert--{type}; cada tipo con su color; y usa el componente 4 veces desde App (una por tipo, una de ellas sin onClose). Pista para el botón condicional: {onClose && <button onClick={onClose}>✕</button>}.

9 · Resumen

  • Las props son los argumentos del componente: el padre las pasa como atributos JSX; React las empaqueta en un objeto.
  • Reglas de oro: solo lectura, flujo padre → hijo, cualquier valor JS es válido (incluidas funciones y JSX).
  • Desestructura en la firma: function Avatar({ src, size = 40 }) — con defaults ahí mismo.
  • Números y booleanos SIEMPRE entre llaves: price={89.9}, open={false}; un atributo sin valor equivale a true.
  • Los callbacks (onClick, onSave) son props-función: el hijo decide CUÁNDO avisar; el padre decide QUÉ pasa.
  • Si un dato debe cambiar, no es una prop: es estado (Módulo 4).

10 · Preguntas frecuentes

¿Cuántas props son «demasiadas»?

Más de ~6-7 suele ser señal de que el componente hace demasiado o de que varias props forman un objeto natural (user, config). Agrupa o divide el componente.

¿Puedo pasar un componente como prop?

Sí: <Layout header={<Header />} /> o como tipo <Icon icon={HomeIcon} />. Es una técnica poderosa de composición (lección 7 de este módulo).

¿Qué es el spread de props ({...props})?

<Button {...rest}> reenvía todas las props restantes al hijo. Útil para componentes «envoltorio» (wrappers), pero úsalo con moderación: puede pasar props inesperadas al DOM (React avisa de atributos desconocidos en etiquetas HTML).

¿Cómo valido las props sin TypeScript?

Opción histórica: la librería prop-types (sigue funcionando). Opción moderna: JSDoc con tipos (@param {string} name) que VSCode usa para avisarte, o migrar a TypeScript cuando toque. En el día a día: defaults + desestructuración + DevTools cubren el 90 %.

¿Las props cambian y se vuelven a renderizar?

Exacto: cuando el padre se re-renderiza y pasa props distintas, el hijo se re-renderiza con los nuevos valores. Es el ciclo natural: datos nuevos entran por arriba, UI nueva sale por abajo.
