Filtros, búsqueda y paginación

Módulo 13 · Proyecto final: TaskFlow 🕐 45 minutos

1 · Introducción

Cuando un tablero crece, «ver todo» deja de ser útil. Necesitas filtrar por etiqueta, prioridad o estado, buscar por texto y, con muchos datos, paginar. Estas tres capacidades son lo que distingue una aplicación usada a diario de una demo.

Qué vamos a aprender hoy: a gestionar el estado de filtros en la URL (no en useState), a hacer búsqueda con debounce y useDeferredValue para no saturar la API, y a paginar de forma server-side.

Qué problema resuelve: filtrar «bien» tiene tres problemas clásicos. Primero, si el filtro vive en useState, al recargar o compartir el enlace se pierde. Segundo, si cada tecla dispara una petición, machacas el backend. Tercero, si filtras en el cliente, necesitas todos los datos descargados, cosa imposible con miles de tareas.

Cuándo se utiliza: en cualquier lista que pueda crecer: tareas, pedidos, usuarios, logs. El patrón «filtros en la URL + debounce + paginación server-side» es el estándar de la industria.

Errores típicos: guardar los filtros en un estado global, disparar una petición por pulsación de tecla, u ofrecer paginación en cliente con todos los datos cargados (que además bloquea la UI al filtrar arrays enormes).

2 · Teoría

La URL como estado: por qué los filtros no van en useState

Los filtros son estado compartible: el usuario quiere enviar un enlace con la búsqueda aplicada, recargar sin perderla o usar el botón «atrás». Si viven en useState, todo eso se pierde. useSearchParams de React Router sincroniza los filtros con la query string.

/projects/42?search=login&label=diseño&priority=high&page=2 └──── ruta ────┘ └────────────── query string (el estado de filtros) ────┘ useSearchParams() → leer/actualizar sin recargar (history API) │ ▼ el componente se re-renderiza │ ▼ useEffect (depende de los filtros) → GET con esos parámetros │ ▼ el servidor filtra, ordena y pagina → { items, total, page }
💡 Regla práctica: ¿es estado de UI o de datos?

¿Debe sobrevivir a una recarga y ser compartible? → URL. ¿Es efímero (un modal abierto, un tooltip)? → useState. ¿Lo necesita media app? → contexto. Los filtros son claramente del primer tipo.

Debounce vs useDeferredValue

Buscar «login» son cinco pulsaciones. Si disparas una petición por pulsación, lanzas cinco peticiones (cuatro inútiles) y, si llegan desordenadas, puedes pintar resultados viejos. Hay dos técnicas complementarias:

TécnicaQué haceResuelve
Debounce (custom hook) Retrasa la ejecución hasta que el usuario deja de escribir (p. ej. 300 ms) Menos peticiones a la API
useDeferredValue (React) Da una «versión retrasada» de un valor para que el render pesado no bloquee el input Mantener el input fluido aunque el filtrado local tarde
src/hooks/useDebouncedValue.js
import { useEffect, useState } from "react";

// Devuelve "value" pero solo después de que deje de cambiar durante "delay" ms.
export function useDebouncedValue(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    // Cleanup: si "value" cambia antes de tiempo, cancelamos el timer anterior.
    return () => clearTimeout(id);
  }, [value, delay]);

  return debounced;
}

Paginación server-side

La API devuelve una página y el total. El cliente no pide «todas» las tareas, sino ?page=2&pageSize=20. El formato estándar es { items, total, page, pageSize }.

GET /api/projects/42/tasks?page=2&pageSize=20 Servidor: SELECT … ORDER BY position LIMIT 20 OFFSET 20 Respuesta: { "items": [ …20 tareas… ], "total": 137, "page": 2, "pageSize": 20 } │ totalPages = ceil(137 / 20) = 7
⚠️ Paginación por offset tiene un enemigo: el tiempo real

Si alguien inserta una tarea mientras estás en la página 2, el OFFSET puede repetir o saltar registros. En tableros con tiempo real (lección 9) se usan cursores (paginación «desde este id»). Para nuestro volumen, offset es suficiente; conocer la limitación te hará elegir bien en cada caso.

3 · Ejemplo mínimo

El ejemplo mínimo demuestra la idea central: los filtros viven en la URL.

src/components/tasks/TaskFilters.jsx
import { useSearchParams } from "react-router-dom";

// Este componente solo LEE y ESCRIBE la query string. No tiene estado
// propio: la URL es su fuente de verdad.
export default function TaskFilters() {
  const [searchParams, setSearchParams] = useSearchParams();

  // Leemos con valores por defecto.
  const priority = searchParams.get("priority") ?? "all";
  const search = searchParams.get("search") ?? "";

  // Actualizamos un parámetro preservando los demás.
  function updateParam(key, value) {
    setSearchParams((current) => {
      const next = new URLSearchParams(current);
      if (value === "" || value === "all") {
        next.delete(key); // limpiamos: la URL no guarda ruido
      } else {
        next.set(key, value);
      }
      next.set("page", "1"); // cualquier cambio de filtro vuelve a la página 1
      return next;
    }, { replace: true }); // replace: no llenamos el historial con cada tecla
  }

  return (
    <div className="filters">
      <input
        type="search"
        value={search}
        onChange={(e) => updateParam("search", e.target.value)}
        placeholder="Buscar tareas…"
      />

      <select value={priority} onChange={(e) => updateParam("priority", e.target.value)}>
        <option value="all">Todas las prioridades</option>
        <option value="urgent">Urgente</option>
        <option value="high">Alta</option>
        <option value="medium">Media</option>
        <option value="low">Baja</option>
      </select>
    </div>
  );
}

Línea por línea:

  1. useSearchParams() — devuelve [searchParams, setSearchParams], igual que useState pero respaldado por la URL.
  2. new URLSearchParams(current) — copiamos para modificar sin perder los demás parámetros.
  3. next.delete(key) cuando el valor es el por defecto: mantiene la URL limpia (?priority= es ruido).
  4. next.set("page", "1") — filtrar debe devolverte a la primera página: si no, podrías quedar en una página vacía.
  5. { replace: true } — evita que cada pulsación de tecla cree una entrada en el historial (si no, «atrás» sería un infierno).

src/pages/ProjectPage.jsx — filtros, búsqueda y paginación
import { useDeferredValue, useEffect, useState } from "react";
import { useParams, useSearchParams } from "react-router-dom";
import { taskService } from "../services/taskService.js";
import { useDebouncedValue } from "../hooks/useDebouncedValue.js";
import Board from "../components/tasks/Board.jsx";
import TaskFilters from "../components/tasks/TaskFilters.jsx";
import Pagination from "../components/ui/Pagination.jsx";

export default function ProjectPage() {
  const { id } = useParams();
  const [searchParams, setSearchParams] = useSearchParams();

  const [tasks, setTasks] = useState([]);
  const [meta, setMeta] = useState({ total: 0, page: 1, pageSize: 20 });
  const [status, setStatus] = useState("loading");

  // Los filtros salen de la URL (única fuente de verdad).
  const search = searchParams.get("search") ?? "";
  const priority = searchParams.get("priority") ?? "";
  const label = searchParams.get("label") ?? "";
  const page = Number(searchParams.get("page") ?? "1");

  // 1) Debounce: solo buscamos 300 ms después de la última tecla.
  const debouncedSearch = useDebouncedValue(search, 300);

  // 2) useDeferredValue: el input se pinta al instante; el filtrado del
  //    tablero (más costoso) puede ir "un poco por detrás" sin bloquear.
  const deferredSearch = useDeferredValue(debouncedSearch);

  // 3) Cuando cambian los filtros, pedimos al servidor.
  useEffect(() => {
    let activo = true;
    setStatus("loading");

    taskService
      .listByProject(id, {
        search: deferredSearch,
        priority,
        label,
        page,
        pageSize: 20,
      })
      .then((data) => {
        if (!activo) return;
        setTasks(data.items);
        setMeta({ total: data.total, page: data.page, pageSize: data.pageSize });
        setStatus("ready");
      })
      .catch(() => {
        if (activo) setStatus("error");
      });

    // Cleanup: si los filtros cambian antes de que responda, ignoramos
    // la respuesta vieja (patrón clásico del Módulo 9).
    return () => {
      activo = false;
    };
  }, [id, deferredSearch, priority, label, page]);

  function goToPage(nextPage) {
    setSearchParams((current) => {
      const next = new URLSearchParams(current);
      next.set("page", String(nextPage));
      return next;
    });
    // Volvemos arriba: buena UX al cambiar de página.
    window.scrollTo({ top: 0, behavior: "smooth" });
  }

  const totalPages = Math.max(1, Math.ceil(meta.total / meta.pageSize));

  return (
    <section className="project-page">
      <header className="page-header">
        <h1>Tareas</h1>
        <span className="page-header__count">{meta.total} en total</span>
      </header>

      <TaskFilters />

      {status === "loading" ? (
        <p className="page-state">Cargando tareas…</p>
      ) : status === "error" ? (
        <p className="page-state page-state--error">No se pudieron cargar las tareas.</p>
      ) : tasks.length === 0 ? (
        <p className="page-state">No hay tareas que coincidan con los filtros.</p>
      ) : (
        <Board tasks={tasks} />
      )}

      <Pagination page={meta.page} totalPages={totalPages} onChange={goToPage} />
    </section>
  );
}
src/components/ui/Pagination.jsx
// Paginación simple con «Anterior / Siguiente» y números. Derivada de
// las props: no guarda estado.
export default function Pagination({ page, totalPages, onChange }) {
  if (totalPages <= 1) return null;

  // Generamos un rango reducido de páginas alrededor de la actual.
  const pages = [];
  const from = Math.max(1, page - 2);
  const to = Math.min(totalPages, page + 2);
  for (let n = from; n <= to; n++) pages.push(n);

  return (
    <nav className="pagination" aria-label="Paginación">
      <button onClick={() => onChange(page - 1)} disabled={page === 1}>
        ← Anterior
      </button>

      {from > 1 && <span className="pagination__ellipsis">…</span>}

      {pages.map((n) => (
        <button
          key={n}
          className={n === page ? "pagination__page is-current" : "pagination__page"}
          onClick={() => onChange(n)}
          aria-current={n === page ? "page" : undefined}
        >
          {n}
        </button>
      ))}

      {to < totalPages && <span className="pagination__ellipsis">…</span>}

      <button onClick={() => onChange(page + 1)} disabled={page === totalPages}>
        Siguiente →
      </button>
    </nav>
  );
}

Decisiones del ejemplo: (1) los filtros se leen de la URL y el useEffect depende de ellos; (2) debounce reduce las peticiones, useDeferredValue mantiene el input fluido; (3) el flag activo en el cleanup evita pintar respuestas obsoletas cuando se teclea rápido; (4) la paginación es un componente «tonto» controlado por props; (5) al cambiar de página hacemos scroll arriba.

5 · Buenas prácticas

HazEvitaPor qué
Filtros en la URL (useSearchParams) useState que se pierde al recargar Enlaces compartibles, botón «atrás» funcional y recarga estable.
replace: true al escribir en la búsqueda Una entrada de historial por tecla «Atrás» debe volver a la página anterior, no deshacer letra a letra.
Debounce (300 ms) para la búsqueda Una petición por pulsación Menos carga en el servidor y menos parpadeo.
Paginación server-side Descargar todo y paginar en cliente Escala con miles de registros y no bloquea la UI.
Volver a la página 1 al cambiar de filtro Mantener la página actual Evita páginas vacías cuando el filtro reduce los resultados.
Flag de cancelación en el useEffect Pintar la respuesta de una búsqueda ya obsoleta Evita «parpadeos» con resultados antiguos (race conditions).

6 · Errores habituales

Error 1: historia de navegación inundada al buscar

✘ Incorrecto 
// Cada tecla añade una entrada al historial: pulsar "atrás" es inútil.
setSearchParams({ search: e.target.value });
✔ Correcto 
setSearchParams((current) => {
  const next = new URLSearchParams(current);
  next.set("search", e.target.value);
  return next;
}, { replace: true });

Error 2: disparar una petición por pulsación

✘ Incorrecto 
// "login" = 5 peticiones, y pueden llegar desordenadas.
useEffect(() => {
  taskService.listByProject(id, { search });
}, [search]);
✔ Correcto 
const debounced = useDebouncedValue(search, 300);
useEffect(() => {
  taskService.listByProject(id, { search: debounced });
}, [debounced]); // solo cuando el usuario para de escribir

Error 3: race condition con búsquedas rápidas

✘ Incorrecto 
useEffect(() => {
  // Si "a" responde después de "ab", pintamos resultados de "a".
  taskService.listByProject(id, { search }).then((data) => setTasks(data.items));
}, [search]);
✔ Correcto 
useEffect(() => {
  let activo = true; // ignoramos respuestas de efectos ya superados
  taskService.listByProject(id, { search }).then((data) => {
    if (activo) setTasks(data.items);
  });
  return () => { activo = false; };
}, [search]);

Por qué: las peticiones no llegan en orden. El cleanup del efecto marca las respuestas viejas como «no válidas». Es el patrón del AbortController del Módulo 9, en su versión más simple.

8 · Reto

🎯 Búsqueda instantánea con startTransition y resaltado

Mejora la experiencia de búsqueda con dos técnicas avanzadas:

  1. Búsqueda con transición: además del debounce, marca la actualización de resultados como no urgente con useTransition, de modo que escribir siga siendo fluido aunque el render del tablero sea pesado. Muestra un indicador sutil («buscando…») mientras isPending sea true.
  2. Resaltado de coincidencias: cuando hay texto de búsqueda, resalta las coincidencias dentro del título de cada tarjeta (p. ej. envolviéndolas en <mark>). Hazlo de forma segura: nunca inyectes HTML con dangerouslySetInnerHTML; construye un array de fragmentos de React.
  3. Persistencia del scroll: al cambiar de página, en lugar de subir siempre arriba, guarda la posición de la barra lateral (tablero) y restáurala si el usuario vuelve. Piensa cómo distinguir «cambio de filtro» (subir) de «cambio de página» (conservar).

Pista: para el resaltado, divide el título con title.split(term) y reconstruye con map intercalando <mark>; cuida el case-insensitive usando índices en lugar de split.

No lo resuelvas todavía. Una búsqueda que se siente instantánea y resalta lo encontrado es uno de esos detalles que elevan mucho la percepción de calidad.

9 · Resumen

  • Los filtros viven en la URL (useSearchParams): se comparten, persisten y funcionan con «atrás».
  • replace: true evita inundar el historial al escribir.
  • Debounce reduce peticiones; useDeferredValue mantiene el input fluido.
  • Paginación server-side con { items, total }: escala y no bloquea la UI.
  • Al cambiar un filtro, vuelve a la página 1.
  • Cleanup + flag activo evita pintar respuestas obsoletas (race conditions).

10 · Preguntas frecuentes

¿Debounce o useDeferredValue? ¿Cuál uso?

Debounce cuando quieres reducir peticiones al servidor (búsqueda). useDeferredValue cuando quieres mantener fluido un render costoso con datos que ya tienes en memoria. No son excluyentes: aquí usamos ambos.

¿Filtro en el cliente o en el servidor?

Si tienes todos los datos cargados y son pocos, filtrar en cliente es instantáneo y evita peticiones. Con paginación «hay datos que no tienes», así que el filtro tiene que ser server-side. El patrón de TaskFlow (server-side) escala sin cambios.

¿Por qué hay que volver a la página 1 al filtrar?

Porque el filtro cambia el número de resultados. Si estabas en la página 3 con 30 resultados y filtras a 8, la página 3 ya no existe: verías una lista vacía sin entender por qué. Volver a la 1 es la expectativa del usuario.

¿Cómo manejo el «botón atrás» con filtros?

Como los filtros están en la URL, «atrás» restaura el estado anterior gratis. Este es precisamente uno de los grandes motivos para poner los filtros en la URL en lugar de en useState.

¿Qué significa la «race condition» de las búsquedas?

Que dos peticiones pueden resolverse en orden inverso. Si buscas «log» y luego «login», la de «log» podría llegar después y sobrescribir los resultados correctos. El flag de cancelación (o AbortController) descarta la respuesta vieja.
