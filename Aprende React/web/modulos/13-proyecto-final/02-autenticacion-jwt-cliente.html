Autenticación JWT en el cliente

Módulo 13 · Proyecto final: TaskFlow 🕐 55 minutos

1 · Introducción

TaskFlow es multiusuario: cada persona ve sus proyectos y tareas. Eso implica que la aplicación debe saber quién eres en cada petición. La respuesta profesional es un token JWT que el backend emite al iniciar sesión y que el cliente adjunta en cada llamada.

Qué vamos a aprender hoy: a integrar la autenticación en el cliente de forma completa: pantallas de login y registro, un AuthContext que guarda la sesión, un hook useAuth() para consumirla y rutas protegidas que redirigen al login cuando no hay sesión.

Por qué es un tema delicado: la autenticación es la frontera de seguridad de tu aplicación. Un error aquí expone datos ajenos. Además, hay decisiones con matices reales: ¿dónde guardo el token?, ¿cómo sé si sigue siendo válido?, ¿qué hago cuando caduca? En esta lección razonaremos cada una.

Cuándo se utiliza: siempre que haya áreas privadas. La pauta «token + endpoint me + rutas protegidas» es el patrón estándar en aplicaciones SPA.

Errores típicos: guardar el token sin caducidad y «confiar» en que sigue vivo, escribir la lógica de auth dentro de cada componente, o proteger rutas solo ocultando enlaces (la seguridad real se valida en el servidor).

🔗 Requisitos de las lecciones anteriores

Usamos services/apiClient.js y utils/storage.js de la lección 1. Si no los tienes, vuelve a crearlos: son la base de todo el módulo.

2 · Teoría

¿Qué es un JWT?

Un JSON Web Token es una cadena con tres partes separadas por puntos. No está cifrado (cualquiera puede leer su contenido), pero sí está firmado: el servidor puede verificar que él lo emitió y que nadie lo ha manipulado.

NO debe confiar en el payload para autorizar nada: eso es responsabilidad del servidor.

Los tres campos que más nos importan del payload son sub (identificador del usuario), exp (fecha de expiración, en segundos UNIX) y, en TaskFlow, role. El resto lo decide el backend.

¿Dónde guardo el token? Las tres opciones

EstrategiaVentajasInconvenientesUso típico
localStorage Sobrevive al recargar; sencillo de usar Accesible por JavaScript: vulnerable a XSS Nuestro caso didáctico y muchas SPAs reales
Memoria (variable) A prueba de XSS; se pierde al recargar Requiere refresh token guardado en cookie Apps de alta seguridad
Cookie HttpOnly JavaScript no la ve (a prueba de XSS) Requiere configurar CORS y CSRF con esmero Enfoque más seguro a día de hoy
⚠️ Decisión didáctica, no dogma

En TaskFlow usaremos localStorage por claridad didáctica y porque es lo que la mayoría de tutoriales y apps reales hacen. Sé consciente de su debilidad: si un atacante consigue inyectar JavaScript (XSS), puede robar el token. Mitiga siempre el XSS (escapa lo que renderizas, nunca uses dangerouslySetInnerHTML con datos de usuario) y, en un producto serio, valora cookies HttpOnly.

AuthContext: la sesión como estado global

El estado de «quién ha iniciado sesión» lo necesita media aplicación: la topbar (avatar), las rutas protegidas, decenas de componentes. Es el caso de uso canónico de Context API (Módulo 10). Lo centralizamos en un AuthContext que expone cuatro cosas.

Valor expuestoTipoPara qué
userobjeto | nullDatos del usuario o «sin sesión»
loadingbooleanTrue mientras verificamos el token al arrancar
login()funciónInicia sesión y guarda el token
logout()funciónBorra la sesión y limpia el estado

El flag loading es clave: al recargar, no sabemos aún si el token vale, así que no podemos decidir si mostrar el dashboard o el login. Mientras loading sea true, mostramos un indicador. Saltarse este paso produce el famoso «flash» del login antes de entrar.

3 · Ejemplo mínimo

El ejemplo mínimo de autenticación no es una pantalla: es el servicio que habla con la API y el contexto que guarda la sesión. Con esto, cualquier componente puede autenticar.

src/services/authService.js
import { request } from "./apiClient.js";

// Cada función es fina: solo describe el endpoint. La lógica de estado
// (guardar el token, actualizar el usuario) vive en el AuthContext.
export const authService = {
  // POST /api/auth/register → { token, user }
  register: (payload) =>
    request("/auth/register", { method: "POST", body: payload }),

  // POST /api/auth/login → { token, user }
  login: (credentials) =>
    request("/auth/login", { method: "POST", body: credentials }),

  // GET /api/auth/me → { user }  (requiere token)
  me: () => request("/auth/me"),
};
src/contexts/AuthContext.jsx
import { createContext, useContext, useEffect, useState } from "react";
import { authService } from "../services/authService.js";
import { getToken, saveSession, getUser, clearSession } from "../utils/storage.js";

// El contexto nace con valor null: si alguien usa useAuth fuera del
// provider, lo detectaremos y avisaremos (ver hook abajo).
const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  // Intentamos hidratar el usuario desde localStorage al arrancar, para
  // evitar un render "sin usuario" antes de verificar el token.
  const [user, setUser] = useState(() => getUser());
  const [loading, setLoading] = useState(true);

  // Al montar: si hay token, preguntamos al servidor si sigue siendo válido.
  useEffect(() => {
    const token = getToken();

    if (!token) {
      setLoading(false);
      return;
    }

    // => authService.me() usa el token que apiClient añade automáticamente.
    authService
      .me()
      .then(({ user }) => setUser(user))
      .catch(() => {
        // Token inválido o caducado: limpiamos y dejamos que el login aparezca.
        clearSession();
        setUser(null);
      })
      .finally(() => setLoading(false));
  }, []);

  async function login(credentials) {
    const { token, user: loggedUser } = await authService.login(credentials);
    saveSession({ token, user: loggedUser });
    setUser(loggedUser);
  }

  async function register(data) {
    const { token, user: newUser } = await authService.register(data);
    saveSession({ token, user: newUser });
    setUser(newUser);
  }

  function logout() {
    clearSession();
    setUser(null);
  }

  // El objeto "value" es lo que ven todos los consumidores.
  const value = { user, loading, login, register, logout };

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

// Hook de consumo. Centraliza la comprobación de "estoy dentro del provider".
export function useAuth() {
  const context = useContext(AuthContext);
  if (context === null) {
    throw new Error("useAuth debe usarse dentro de <AuthProvider>");
  }
  return context;
}

Línea por línea:

  1. useState(() => getUser()) — el inicializador lazy lee localStorage una sola vez. Así, si el usuario ya estaba logueado, lo pintamos inmediatamente.
  2. useEffect(..., []) — al montar verificamos el token contra /auth/me. Es el paso que confirma que el token no ha caducado.
  3. .finally(() => setLoading(false)) — pase lo que pase, dejamos de cargar. Sin esto, la app se quedaría en el spinner para siempre.
  4. throw new Error(...) — un error explícito es mejor que un undefined silencioso que explota tres componentes más abajo.

4 · Ejemplo real

Ahora la aplicación completa: la página de login con validación, la ruta protegida y el cableado en main.jsx / App.jsx. Usamos Form Actions de React 19 para el estado del formulario.

src/components/layout/ProtectedRoute.jsx
import { Navigate, Outlet, useLocation } from "react-router-dom";
import { useAuth } from "../../hooks/useAuth.js";

// Envoltorio de rutas privadas. Si no hay sesión, redirige a /login
// GUARDANDO la ubicación original para volver tras autenticarse.
export default function ProtectedRoute() {
  const { user, loading } = useAuth();
  const location = useLocation();

  // Mientras verificamos el token no decidimos: mostramos un spinner.
  // Sin esto, verías el login durante un instante antes del dashboard.
  if (loading) {
    return <div className="app-loading">Cargando sesión…</div>;
  }

  if (!user) {
    // state.from guarda dónde quería ir el usuario.
    return <Navigate to="/login" replace state={{ from: location }} />;
  }

  // Outlet renderiza la ruta hija protegida (Dashboard, ProjectPage…).
  return <Outlet />;
}

src/pages/LoginPage.jsx — formulario con Actions (React 19)
import { useActionState } from "react";
import { Link, useLocation, useNavigate } from "react-router-dom";
import { useAuth } from "../hooks/useAuth.js";

// useActionState gestiona { error, pending } y recibe la acción del formulario.
// Es la forma moderna (React 19) de manejar submits con estado.
export default function LoginPage() {
  const { login } = useAuth();
  const navigate = useNavigate();
  const location = useLocation();

  // Si venimos de una ruta protegida, volvemos ahí después de entrar.
  const from = location.state?.from?.pathname ?? "/";

  async function loginAction(_prevState, formData) {
    const email = formData.get("email");
    const password = formData.get("password");

    try {
      await login({ email, password });
      navigate(from, { replace: true });
      return { error: null };
    } catch (err) {
      // Mostramos el mensaje del backend (p. ej. "Credenciales inválidas").
      return { error: err.message ?? "No se pudo iniciar sesión" };
    }
  }

  const [state, formAction, isPending] = useActionState(loginAction, { error: null });

  return (
    <main className="auth-page">
      <form className="auth-card" action={formAction}>
        <h1>Iniciar sesión</h1>

        {state.error && <p className="form-error" role="alert">{state.error}</p>}

        <label>
          Email
          <input type="email" name="email" required autoComplete="email" />
        </label>

        <label>
          Contraseña
          <input
            type="password"
            name="password"
            required
            minLength={8}
            autoComplete="current-password"
          />
        </label>

        <button type="submit" disabled={isPending}>
          {isPending ? "Entrando…" : "Entrar"}
        </button>

        <p>
          ¿No tienes cuenta? <Link to="/register">Regístrate</Link>
        </p>
      </form>
    </main>
  );
}
src/pages/RegisterPage.jsx
import { useActionState } from "react";
import { Link, useNavigate } from "react-router-dom";
import { useAuth } from "../hooks/useAuth.js";

export default function RegisterPage() {
  const { register } = useAuth();
  const navigate = useNavigate();

  async function registerAction(_prevState, formData) {
    const password = formData.get("password");
    const confirm = formData.get("confirm");

    // Validación en cliente (la definitiva la hace el backend).
    if (password !== confirm) {
      return { error: "Las contraseñas no coinciden" };
    }

    try {
      await register({
        displayName: formData.get("displayName"),
        email: formData.get("email"),
        password,
      });
      navigate("/", { replace: true });
      return { error: null };
    } catch (err) {
      return { error: err.message ?? "No se pudo crear la cuenta" };
    }
  }

  const [state, formAction, isPending] = useActionState(registerAction, { error: null });

  return (
    <main className="auth-page">
      <form className="auth-card" action={formAction}>
        <h1>Crear cuenta</h1>

        {state.error && <p className="form-error" role="alert">{state.error}</p>}

        <label>
          Nombre
          <input type="text" name="displayName" required autoComplete="name" />
        </label>
        <label>
          Email
          <input type="email" name="email" required autoComplete="email" />
        </label>
        <label>
          Contraseña
          <input type="password" name="password" required minLength={8} />
        </label>
        <label>
          Repite la contraseña
          <input type="password" name="confirm" required minLength={8} />
        </label>

        <button type="submit" disabled={isPending}>
          {isPending ? "Creando…" : "Crear cuenta"}
        </button>

        <p>
          ¿Ya tienes cuenta? <Link to="/login">Inicia sesión</Link>
        </p>
      </form>
    </main>
  );
}

      </AuthProvider>
    </BrowserRouter>

Decisiones del ejemplo: (1) la sesión vive en el Context, no repartida; (2) las rutas públicas (/login, /register) van fuera de ProtectedRoute; (3) usamos useActionState en lugar de useState + onSubmit porque React 19 elimina el boilerplate de pending y errores; (4) guardamos location para volver a donde el usuario quería ir.

5 · Buenas prácticas

HazEvitaPor qué
Toda la sesión en un AuthContext Leer el token con localStorage en cada componente Una sola fuente de verdad; los componentes solo consumen useAuth().
Un flag loading mientras verificas el token Decidir «login sí/no» antes de verificar Evita el parpadeo del login y las redirecciones prematuras.
Validar siempre en el servidor Confiar en la validación del cliente El cliente es controlable por el atacante; la autoridad es el backend.
Lanzar errores explícitos en useAuth Devolver undefined si faltó el provider Un error claro ahorra una tarde de depuración.
Mensajes de error genéricos («Credenciales inválidas») «Ese email no existe» / «contraseña incorrecta» No reveles qué usuarios existen: es información para atacantes.
Guardar la ubicación de origen al redirigir Enviar siempre al / tras el login Mejor UX: el usuario termina donde quería ir.

6 · Errores habituales

Error 1: crear un contexto distinto por componente

✘ Incorrecto 
// LoginPage.jsx
const AuthContext = createContext();  // ← ¡contexto NUEVO, no el compartido!

function LoginPage() {
  const [user, setUser] = useState(null);
  // El Topbar lee OTRO contexto y nunca se entera de la sesión.
}
✔ Correcto 
// Un único AuthContext.jsx exporta el provider y el hook.
import { useAuth } from "../hooks/useAuth.js";

function LoginPage() {
  const { login } = useAuth(); // ← siempre el mismo contexto
}

Error 2: olvidar el estado de carga al arrancar

✘ Incorrecto 
function ProtectedRoute() {
  const { user } = useAuth();
  // Al recargar, user todavía es null: redirige al login aunque haya token.
  return user ? <Outlet /> : <Navigate to="/login" replace />;
}
✔ Correcto 
function ProtectedRoute() {
  const { user, loading } = useAuth();
  if (loading) return <Spinner />;       // aún no lo sabemos
  if (!user) return <Navigate to="/login" replace />;
  return <Outlet />;
}

Error 3: pasar el token a mano en cada servicio

✘ Incorrecto 
// El token se pasa como argumento en cada llamada: fácil de olvidar.
projectService.list(token);
projectService.create(token, data);
projectService.remove(token, id);
✔ Correcto 
// apiClient añade el token automáticamente en todas las peticiones.
projectService.list();
projectService.create(data);
projectService.remove(id);

Por qué: inyectar el token en un único punto (apiClient) hace imposible olvidarlo y elimina ruido en la API de los servicios.

8 · Reto

🎯 Sesión que se renueva sola (refresh token)

Los tokens de acceso deberían ser de vida corta (p. ej. 15 minutos). Añade a TaskFlow un refresh token de vida larga:

  1. Asume que el backend expone POST /api/auth/refresh que, enviando el refresh token, devuelve un nuevo token de acceso.
  2. Guarda ambos tokens en storage.js con claves distintas.
  3. En apiClient, cuando recibas un 401, intenta renovar el token una vez y reintenta la petición original; si el refresh también falla, limpia la sesión y redirige al login.
  4. Evita la «tormenta de refrescos»: si diez peticiones reciben 401 a la vez, solo una debe pedir el refresh y las otras deben esperar su resultado. Piensa cómo lograrlo (una promesa compartida en una variable).
  5. Añade un timer que renueve el token un minuto antes de que caduque, leyendo el campo exp del payload JWT.

Pista: para leer exp decodifica el payload con JSON.parse(atob(token.split(".")[1])). Y recuerda: el cliente nunca debe considerar el payload como autorización, solo como información para saber cuándo renovar.

No lo resuelvas todavía. El refresh token es una de las piezas que más preguntan en entrevistas: merece que lo pienses bien.

9 · Resumen

  • JWT = header.payload.signature. Se puede leer, pero solo el servidor puede verificarlo. El cliente lo usa para saber exp, no para autorizar.
  • Flujo: login → guardar token → GET /auth/me al arrancar → rutas protegidas.
  • Guardar el token: localStorage es cómodo pero vulnerable a XSS; las cookies HttpOnly son más seguras. Conoce el compromiso.
  • AuthContext centraliza user, loading, login, register y logout.
  • ProtectedRoute espera a loading, luego redirige o renderiza el Outlet.
  • React 19: useActionState simplifica los formularios de login/registro.
  • Seguridad real en el servidor: el cliente solo mejora la experiencia; el backend valida el token en cada petición.

10 · Preguntas frecuentes

¿Por qué no puedo confiar en un JWT que leo en el cliente?

Porque el cliente (y el usuario) puede leerlo y modificarlo. Cualquiera puede decodificar el payload y, si no se verifica la firma, falsificar datos. La firma solo la puede validar quien posee la clave secreta: el servidor. Por eso toda autorización se decide en el backend.

¿Qué hago cuando el token caduca mientras uso la app?

Dos estrategias: (1) detectar el 401 en el cliente y redirigir al login, o (2) implementar refresh tokens (el reto). El apiClient ya centraliza el manejo del 401, así que añadir refresh es un cambio localizado en un solo archivo.

¿useActionState sustituye a useState en formularios?

Para formularios con envío sí es muy cómodo: te da pending y el resultado de la acción sin manejar onSubmit a mano. Para inputs controlados que necesitas leer en vivo, useState sigue siendo lo natural. Se complementan.

¿Y si el usuario abre dos pestañas?

localStorage es compartido entre pestañas, así que el token está disponible en ambas. Sin embargo, el estado en memoria no se sincroniza: si haces logout en una pestaña, la otra sigue mostrando la sesión hasta que recargue o haga una petición. Puedes escuchar el evento storage del navegador para sincronizarlas.

¿Necesito react-router-dom solo para esto?

No, pero el routing es imprescindible para tener rutas públicas y privadas. Navigate, Outlet y useLocation son de React Router, que instalamos en la lección 1. En la lección 3 montaremos el layout completo con rutas anidadas.
