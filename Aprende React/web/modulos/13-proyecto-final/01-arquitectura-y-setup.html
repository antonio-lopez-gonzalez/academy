Arquitectura y setup del proyecto

Módulo 13 · Proyecto final: TaskFlow 🕐 45 minutos

1 · Introducción

Llegamos al módulo que da sentido a todo el curso. Durante doce módulos has aprendido piezas sueltas: JSX, estado, efectos, routing, APIs, estado global, optimización y testing. Ahora toca ensamblarlas en TaskFlow, una aplicación profesional de gestión de tareas tipo Trello con la que cerrarás el curso con algo que puedes enseñar, no con otro ejercicio de juguete.

Qué vamos a aprender hoy: antes de escribir una sola pantalla, vamos a decidir la arquitectura. Igual que un arquitecto no empieza colocando ladrillos, un desarrollador serio no empieza tirando componentes. La carpeta donde pones un archivo, y sobre todo las dependencias que permites entre capas, determinan si un proyecto sigue siendo mantenible dentro de un año o se convierte en una maraña imposible de tocar.

Qué problema resuelve una buena arquitectura: la mayoría de proyectos React no mueren por un bug, mueren por acoplamiento. Cuando un componente llama directamente a fetch, cuando el token se lee por todo el código, cuando la lógica de negocio vive dentro del JSX… cualquier cambio se propaga a diez archivos. Una arquitectura por capas concentra cada responsabilidad en un único sitio.

Cuándo se utiliza: siempre que el proyecto vaya a crecer. Para una demo de 3 componentes no necesitas nada de esto; para TaskFlow (más de 40 componentes, 15 endpoints, tiempo real, autenticación y despliegue) es imprescindible.

Errores típicos que veremos: organizar carpetas por tipo sin ninguna regla de dependencia, mezclar código y configuración en App.jsx, o duplicar la URL de la API en veinte archivos. Todos tienen arreglo si decides la arquitectura antes de empezar.

📌 Qué vas a construir en este módulo

Al terminar el Módulo 13 tendrás un frontend completo conectado a la API .NET 8 del Módulo 14:

  • Login y registro con JWT.
  • Dashboard con CRUD de proyectos y de tareas.
  • Etiquetas, prioridades, comentarios y subtareas.
  • Filtros, búsqueda y paginación.
  • Tema oscuro, responsive y actualizaciones en tiempo real por WebSockets.
  • Despliegue en producción.

2 · Teoría

Arquitectura por capas: la regla de oro

TaskFlow se organiza en capas con una regla de dependencia estricta: las capas de arriba conocen a las de abajo, nunca al revés. Es la misma idea que la arquitectura limpia de .NET que verás en el Módulo 14.

CAPAS DE TASKFLOW (la flecha = "puede importar") ┌───────────────────────────────────────────────┐ │ pages/ LoginPage, DashboardPage… │ ← orquesta └───────────────────────┬───────────────────────┘ │ ┌───────────────────────▼───────────────────────┐ │ components/ ui · layout · projects · tasks │ ← pinta └───────────────────────┬───────────────────────┘ │ ┌───────────────────────▼───────────────────────┐ │ hooks/ · contexts/ useAuth, useRealtime… │ ← estado reutilizable └───────────────────────┬───────────────────────┘ │ ┌───────────────────────▼───────────────────────┐ │ services/ apiClient, projectService… │ ← habla con la API └───────────────────────┬───────────────────────┘ │ ┌───────────────────────▼───────────────────────┐ │ utils/ format, storage, constants │ ← funciones puras └───────────────────────────────────────────────┘ REGLA: un componente NUNCA llama a fetch() directo. Siempre pasa por services/.

¿Por qué esta regla importa tanto? Porque si mañana cambias la API (añades un header, migras a otra URL, activas reintentos), tocas un solo archivo (apiClient.js) en lugar de cuarenta componentes. Es exactamente el mismo principio que separar repositorios de controladores en .NET.

Estructura de carpetas: por tipo y por feature a la vez

Hay dos escuelas para organizar un proyecto React:

EstrategiaCómo agrupaCuándo brillaProblema
Por tipo («type-based») /components, /hooks, /services Proyectos pequeños y apps de una sola pantalla Con 40 componentes, la carpeta /components es un cajón desastre
Por funcionalidad («feature-based») /projects, /tasks, /auth Apps grandes con dominios claros (TaskFlow) Duplicación si no se extrae una capa /ui común

TaskFlow usa un híbrido: una capa de presentación común (components/ui) más dominios por feature (components/projects, components/tasks). Es el equilibrio que recomienda la comunidad y el que mejor escala.

El contrato con el backend (.NET 8)

El frontend no «adivina» la API: la API es un contrato. Estos son los endpoints que consumiremos. Los definimos ahora, aunque implementemos el backend en el Módulo 14 (con el mismo contrato).

MétodoRutaQué hace
POST/api/auth/registerCrear cuenta y devolver token
POST/api/auth/loginIniciar sesión y devolver token
GET/api/auth/meUsuario autenticado actual
GET/POST/api/projectsListar / crear proyectos
GET/PUT/DELETE/api/projects/{id}Detalle / editar / borrar
GET/POST/api/projects/{id}/tasksListar / crear tareas del proyecto
PUT/DELETE/api/tasks/{id}Editar / borrar tarea
GET/POST/api/tasks/{id}/commentsComentarios de una tarea
GET/POST/api/tasks/{id}/subtasksSubtareas de una tarea
WS/hubs/boardHub SignalR (tiempo real)

Configuración por entorno: nunca hardcodees la URL

En desarrollo la API corre en http://localhost:5080; en producción, en otro dominio. Vite expone variables que empiezan por VITE_ mediante import.meta.env. Se leen en un único sitio (services/apiClient.js) y se usan en todas partes.

⚠️ Las variables de entorno NO son secretos

Todo lo que empiece por VITE_ acaba dentro del bundle y cualquiera puede leerlo. Úsalas para configuración (URLs, flags), jamás para claves de API privadas. Los secretos viven en el backend.

3 · Ejemplo mínimo

Empecemos por lo más pequeño que demuestra la arquitectura: crear el proyecto con Vite y un punto de entrada limpio.

terminal
# 1. Creamos el proyecto con el template oficial de React (JavaScript, no TS)
pnpm create vite@latest taskflow -- --template react

# 2. Entramos y arrancamos las dependencias
cd taskflow
pnpm install

# 3. (Opcional) pnpm viene de corepack; fija la versión en el repo
corepack use pnpm@latest

# 4. Arrancamos el servidor de desarrollo
pnpm dev
src/main.jsx — el punto de entrada
// main.jsx es el ÚNICO sitio donde "montamos" React en el DOM.
// A partir del Módulo 1 sabes que ReactDOM.createRoot crea la raíz.
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import App from "./App.jsx";
import "./styles/global.css"; // estilos base (los crearemos enseguida)

// StrictMode activa comprobaciones extra en desarrollo: detecta efectos
// mal limpiados y dobles renders. Se elimina del bundle en producción.
createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>
);

Línea por línea:

  1. createRoot(...) — React 19 usa createRoot desde react-dom/client. Es la API moderna (la antigua ReactDOM.render desapareció).
  2. <StrictMode> — no pinta nada, pero en desarrollo monta los componentes dos veces para que descubras los bugs de efectos. Si algo se rompe «solo en dev», probábalo aquí.
  3. import "./styles/global.css" — los estilos globales se importan una sola vez, aquí. Vite los procesa y los inyecta.

src/services/apiClient.js — la ÚNICA puerta a la API
// Este módulo concentra TODA la comunicación HTTP.
// Ningún componente debe llamar a fetch() directamente.

// La URL base viene del entorno. En dev apuntamos al proxy de Vite ("/api").
const BASE_URL = import.meta.env.VITE_API_URL ?? "/api";

// storage.js (utils) encapsula el acceso a localStorage. Lo definimos abajo.
import { getToken, clearSession } from "../utils/storage.js";

/**
 * Petición genérica. Añade el token JWT si existe y normaliza los errores.
 * @param {string} path   Ruta relativa, p. ej. "/projects"
 * @param {object} options  Opciones de fetch (method, body, headers…)
 */
export async function request(path, options = {}) {
  const token = getToken();

  const response = await fetch(`${BASE_URL}${path}`, {
    ...options,
    headers: {
      "Content-Type": "application/json",
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...options.headers,
    },
    body: options.body ? JSON.stringify(options.body) : undefined,
  });

  // 401 → la sesión caducó: limpiamos y dejamos que la app redirija a /login.
  if (response.status === 401) {
    clearSession();
    // Lanzamos el error para que la capa superior decida qué hacer.
    throw new ApiError("Sesión caducada", 401);
  }

  // 204 No Content (DELETE) no tiene cuerpo.
  if (response.status === 204) return null;

  const data = await response.json().catch(() => null);

  if (!response.ok) {
    // El backend .NET devuelve { title, detail, status } en errores del problema.
    const message = data?.detail ?? data?.title ?? "Error inesperado";
    throw new ApiError(message, response.status, data);
  }

  return data;
}

// Error propio para distinguir errores de API de errores de programación.
export class ApiError extends Error {
  constructor(message, status, payload) {
    super(message);
    this.name = "ApiError";
    this.status = status;
    this.payload = payload;
  }
}
src/utils/storage.js — encapsula localStorage
// Centralizar las claves evita "strings mágicos" repartidos por el código
// y facilita cambiar de estrategia (p. ej. a cookies) sin tocar componentes.
const TOKEN_KEY = "taskflow.token";
const USER_KEY = "taskflow.user";

export function getToken() {
  return localStorage.getItem(TOKEN_KEY);
}

export function saveSession({ token, user }) {
  localStorage.setItem(TOKEN_KEY, token);
  localStorage.setItem(USER_KEY, JSON.stringify(user));
}

export function getUser() {
  const raw = localStorage.getItem(USER_KEY);
  return raw ? JSON.parse(raw) : null;
}

export function clearSession() {
  localStorage.removeItem(TOKEN_KEY);
  localStorage.removeItem(USER_KEY);
}
vite.config.js — proxy de desarrollo
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

// El proxy evita problemas de CORS en desarrollo: el navegador habla con
// Vite (mismo origen) y Vite reenvía a la API .NET.
export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    proxy: {
      "/api": {
        target: "http://localhost:5080", // API .NET 8 (Módulo 14)
        changeOrigin: true,
      },
      "/hubs": {
        target: "http://localhost:5080", // SignalR (WebSockets)
        ws: true, // habilita el upgrade a WebSocket
      },
    },
  },
});
.env.development
# En desarrollo usamos el proxy: el cliente pide "/api" y Vite reenvía.
VITE_API_URL=/api
.env.production
# En producción, la URL real de la API (ajústala al desplegar).
VITE_API_URL=https://api.taskflow.example.com/api

Decisiones del ejemplo: el apiClient es una fachada única con request(); los servicios concretos (authService, projectService…) se construirán encima sin repetir cabeceras ni manejo de errores. El token se lee siempre desde storage.js, nunca con localStorage.getItem("token") suelto.

5 · Buenas prácticas

HazEvitaPor qué
Una capa services/ como única puerta a la API Llamar a fetch desde dentro de un componente Si cambia la API, tocas un archivo, no cuarenta componentes.
Leer la URL de import.meta.env.VITE_* Escribir http://localhost:5080 hardcodeado El mismo código debe funcionar en dev, staging y producción.
Encapsular localStorage en utils/storage.js Leer el token con strings sueltos por todo el proyecto Una sola fuente de verdad de las claves; migración trivial a cookies.
Definir el contrato de la API ANTES de programar Descubrir los endpoints sobre la marcha Permite trabajar frontend y backend en paralelo (mismo contrato).
Carpetas por feature dentro de components/ Un único components/ con 60 archivos sueltos Encuentras lo que buscas mirando el dominio, no la extensión.
Archivos .env fuera de git (.gitignore) Commitear .env.local con datos del entorno Evitas filtrar configuración y conflictos entre máquinas.

6 · Errores habituales

Error 1: fetch repartido por los componentes

✘ Incorrecto 
// ProjectList.jsx — cada componente construye su propia URL y cabeceras
function ProjectList() {
  useState(() => {});
  const [items, setItems] = useState([]);
  useEffect(() => {
    fetch("http://localhost:5080/api/projects", {
      headers: { Authorization: "Bearer " + localStorage.getItem("token") },
    })
      .then((r) => r.json())
      .then(setItems);
  }, []);
  // Si mañana cambia el host o el header, hay que editar TODOS los componentes.
}
✔ Correcto 
// services/projectService.js — una única capa habla con la API
import { request } from "./apiClient.js";

export const projectService = {
  list: () => request("/projects"),
  get: (id) => request(`/projects/${id}`),
};

Error 2: leer import.meta.env sin el prefijo VITE_

✘ Incorrecto 
# .env.development
API_URL=/api          # ← sin VITE_: Vite lo IGNORA
// En el código vale undefined y las peticiones van a "undefined/projects".
const BASE_URL = import.meta.env.API_URL;
✔ Correcto 
# .env.development
VITE_API_URL=/api
const BASE_URL = import.meta.env.VITE_API_URL ?? "/api";

Error 3: confundir una variable VITE_ con un secreto

✘ Incorrecto 
# .env.production — ¡mal! Esta clave termina en el bundle público
VITE_STRIPE_SECRET_KEY=sk_live_123
✔ Correcto 
# El cliente solo conoce la clave PÚBLICA; la secreta vive en el backend
VITE_STRIPE_PUBLIC_KEY=pk_live_123

Por qué: Vite incrusta las variables VITE_* en el JavaScript que descarga cualquiera. Un secreto expuesto ahí es un secreto filtrado.

8 · Reto

🎯 Un cliente HTTP a prueba de balas

Amplía apiClient.js para que sea robusto en producción. Debe soportar, sin cambiar la firma de request(path, options):

  1. Timeout: si la API no responde en 10 segundos, aborta la petición con AbortController (Módulo 9) y lanza un ApiError legible.
  2. Reintentos con backoff: reintenta automáticamente hasta 2 veces los errores de red o los 5xx, esperando 300 ms y luego 900 ms (backoff exponencial). No reintentes un 4xx: si la petición está mal, repetirla no ayuda.
  3. Cancelación externa: permite que quien llama pase su propia signal y respétala.
  4. Errores tipados: distingue ApiError con status (respuesta con error) de un NetworkError (no hubo respuesta).

Pista: combina la señal externa con la interna usando AbortSignal.any() o creando tu propio AbortController y escuchando la señal externa. Documenta cada decisión con un comentario; un cliente HTTP bien escrito es infraestructura, y la infraestructura se comenta.

No lo resuelvas todavía: inténtalo y compáralo con la solución de la siguiente lección.

9 · Resumen

  • Arquitectura por capas con regla de dependencia estricta: pages → components → hooks/contexts → services → utils. Nunca al revés.
  • Carpetas híbridas: components/ui común + dominios por feature (projects, tasks).
  • services/apiClient.js es la única puerta a la API: concentra la URL base, el token y el manejo de errores.
  • Configuración por entorno con import.meta.env.VITE_*: jamás hardcodear URLs ni guardar secretos en el cliente.
  • Proxy de Vite para desarrollo: elimina CORS y centraliza /api y /hubs.
  • El contrato de la API se define antes de programar; el backend .NET 8 del Módulo 14 lo implementará tal cual.

10 · Preguntas frecuentes

¿Por qué react-router-dom@^7 y no otra versión?

React Router 7 es la versión estable actual y la que usaremos para rutas anidadas, Outlet y rutas protegidas. El paquete sigue llamándose react-router-dom. En la lección 3 montaremos el layout con rutas anidadas.

¿De verdad hace falta separar services de hooks?

Sí, aunque al principio parezca una indirección de más. Los services saben hablar con la API; los hooks saben gestionar estado de React (loading, error, caché). Separarlos permite testear los servicios sin renderizar componentes y reutilizar la gestión de estado en varias pantallas.

¿Uso http://localhost:5080 directo o el proxy?

En desarrollo, el proxy. Así el navegador cree que la API está en el mismo origen y desaparecen los problemas de CORS. En producción, o bien sirves la API bajo el mismo dominio, o configuras CORS correctamente en el backend. En ambos casos el código del cliente es idéntico: pide /api/….

¿Por qué no uso TypeScript si un proyecto real lo agradecería?

El curso enseña React con JavaScript puro por decisión pedagógica: separar la dificultad de React de la de los tipos. Todo lo que aprendas aquí se traslada directamente a React + TypeScript. Si quieres tipar los modelos (Project, Task…), puedes añadir tipos después sin cambiar la arquitectura.

¿Puedo empezar el frontend antes de tener el backend?

Sí, y es lo recomendable. Al definir el contrato primero, puedes desarrollar el frontend contra mocks o un servidor mínimo, y el backend real (Módulo 14) encajará sin cambios. Este desacoplamiento es una de las grandes ventajas de tener una capa services.
