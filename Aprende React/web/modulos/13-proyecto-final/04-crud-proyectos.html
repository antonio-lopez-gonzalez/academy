CRUD de proyectos

Módulo 13 · Proyecto final: TaskFlow 🕐 50 minutos

1 · Introducción

Un CRUD (Create, Read, Update, Delete) es el pan de cada día de cualquier aplicación de negocio. TaskFlow no es una excepción: los usuarios crean proyectos, los listan, los editan y los borran. Dominar el CRUD «bien» —con estados de carga, errores, confirmaciones y actualizaciones optimistas— es lo que separa una demo de una aplicación profesional.

Qué vamos a aprender hoy: a construir el CRUD de proyectos de principio a fin: el servicio que habla con la API, la página de listado, el formulario de creación/edición reutilizable y el borrado con confirmación.

Qué problema resuelve: escribir un CRUD «que funcione» es fácil; el reto es que se sienta bien. Un botón que no da feedback, una lista que no se actualiza tras crear o un borrado sin confirmación son fuente constante de bugs y de frustración. Vamos a resolver todos esos detalles con criterio.

Cuándo se utiliza: siempre. Ventas, tareas, usuarios, facturas… todo dominio tiene su CRUD. El patrón que aprendas aquí lo reutilizarás en cada nueva entidad.

Errores típicos: recargar la página entera tras cada operación, no manejar los estados loading/error, o asumir que el servidor asignará el id sin esperar su respuesta (falsa actualización optimista).

2 · Teoría

El ciclo de vida de los datos: «fuente de verdad» y copia local

El servidor es la fuente de verdad; el estado de React es una copia que sincronizamos. Toda operación sigue el mismo esquema: llamamos a la API, y según la respuesta actualizamos la copia local. La pregunta clave es: ¿actualizo mi copia con lo que el servidor me devuelve, o vuelvo a pedir la lista completa?

EstrategiaCómoVentajasInconvenientes
Refetch tras escribir create() → list() Siempre consistente con el servidor Dos peticiones; parpadeo si no se gestiona
Merge con la respuesta Usar el objeto que devuelve el POST/PUT Una sola petición; rápido Requiere que la API devuelva la entidad creada
Optimista Actualizar la UI antes de la respuesta Sensación instantánea (móvil, mala red) Hay que «deshacer» si el servidor falla

En TaskFlow usaremos merge con la respuesta para crear y editar (la API devuelve el recurso), y optimista con rollback para operaciones frecuentes y de bajo riesgo, como marcar una tarea. Lo veremos con detalle en la lección 5.

Endpoints del CRUD de proyectos

GET /api/projects?search=&page=&pageSize= → { items[], total } POST /api/projects body {name,description,color} → { project } GET /api/projects/{id} → { project } PUT /api/projects/{id} body {name,description,color} → { project } DELETE /api/projects/{id} → 204 No Content

El formulario como estado local, no global

Un error conceptual habitual es meter en el estado global el borrador del formulario (lo que el usuario está escribiendo). El borrador es efímero y solo interesa a ese formulario: vive en su propio useState. Cuando enviás correctamente, avisas al padre (que actualiza la lista). Flujo unidireccional puro.

ProjectDialog (estado local: borrador + errores) │ onSubmit → PASO 2: avisa al padre con los datos ▼ ProjectsPage (estado: lista de proyectos) │ llama a projectService.create(...) ▼ API .NET 8 ──► devuelve { project } │ ▼ ProjectsPage añade el proyecto a la lista → re-render

¿Modal o página propia?

Ambos son válidos. Un modal es ideal para crear/editar entidades simples sin perder el contexto de la lista; una página dedicada (/projects/new) es mejor si el formulario es largo o el usuario necesita un enlace directo. Para proyectos usaremos modal; para tareas, donde hay mucho más (etiquetas, subtareas, comentarios), usaremos un panel lateral.

3 · Ejemplo mínimo

El CRUD empieza por el servicio: cinco métodos, uno por operación. Sin él, nada más importa.

src/services/projectService.js
import { request } from "./apiClient.js";

// Un método por operación. Los nombres imitan el verbo del endpoint.
export const projectService = {
  // GET /api/projects?search=...&page=... → { items, total }
  list: ({ search = "", page = 1, pageSize = 20 } = {}) => {
    // URLSearchParams construye el query string de forma segura (escapa todo).
    const params = new URLSearchParams({ search, page, pageSize });
    return request(`/projects?${params}`);
  },

  // POST /api/projects → { project }
  create: (data) => request("/projects", { method: "POST", body: data }),

  // GET /api/projects/{id} → { project }
  get: (id) => request(`/projects/${id}`),

  // PUT /api/projects/{id} → { project }
  update: (id, data) =>
    request(`/projects/${id}`, { method: "PUT", body: data }),

  // DELETE /api/projects/{id} → 204
  remove: (id) => request(`/projects/${id}`, { method: "DELETE" }),
};

Línea por línea:

  1. URLSearchParams en lugar de concatenar strings: si la búsqueda lleva espacios o tildes, se codifica correctamente.
  2. Valores por defecto (search = "", page = 1) para poder llamar projectService.list() sin argumentos.
  3. remove devuelve null porque el apiClient trata el 204 sin cuerpo (lo viste en la lección 1).

4 · Ejemplo real

La página de proyectos completa: listado con estados, formulario en modal reutilizable para crear y editar, y borrado con confirmación.

src/pages/ProjectsPage.jsx — lista + orquestación
import { useEffect, useState } from "react";
import { projectService } from "../services/projectService.js";
import ProjectCard from "../components/projects/ProjectCard.jsx";
import ProjectDialog from "../components/projects/ProjectDialog.jsx";
import ConfirmDialog from "../components/feedback/ConfirmDialog.jsx";
import EmptyState from "../components/feedback/EmptyState.jsx";

export default function ProjectsPage() {
  const [projects, setProjects] = useState([]);
  const [status, setStatus] = useState("loading"); // "loading" | "ready" | "error"
  const [error, setError] = useState(null);

  // Qué modal está abierto: null | "create" | el proyecto a editar
  const [editing, setEditing] = useState(null);
  const [isFormOpen, setFormOpen] = useState(false);
  const [toDelete, setToDelete] = useState(null); // proyecto a borrar

  // ---- CARGA ----
  async function loadProjects() {
    setStatus("loading");
    try {
      const { items } = await projectService.list();
      setProjects(items);
      setStatus("ready");
    } catch (err) {
      setError(err.message);
      setStatus("error");
    }
  }

  useEffect(() => {
    loadProjects();
  }, []);

  // ---- CREATE / UPDATE ----
  // Un único handler para las dos operaciones: el formulario no sabe si
  // es una creación o una edición, solo envía datos.
  async function handleSave(data) {
    const { project } = editing
      ? await projectService.update(editing.id, data)
      : await projectService.create(data);

    setProjects((current) => {
      const exists = current.some((p) => p.id === project.id);
      // Si ya existía, lo reemplazamos; si no, lo añadimos al principio.
      return exists
        ? current.map((p) => (p.id === project.id ? project : p))
        : [project, ...current];
    });
    closeForm();
  }

  function openCreate() {
    setEditing(null);
    setFormOpen(true);
  }

  function openEdit(project) {
    setEditing(project);
    setFormOpen(true);
  }

  function closeForm() {
    setFormOpen(false);
    setEditing(null);
  }

  // ---- DELETE (optimista con rollback) ----
  async function confirmDelete() {
    const project = toDelete;
    setToDelete(null);

    // 1) Quitamos el proyecto de la UI inmediatamente.
    const previous = projects;
    setProjects((current) => current.filter((p) => p.id !== project.id));

    try {
      await projectService.remove(project.id);
    } catch (err) {
      // 2) Si falla, restauramos y avisamos.
      setProjects(previous);
      setError(`No se pudo borrar: ${err.message}`);
    }
  }

  // ---- RENDER POR ESTADO ----
  if (status === "loading") {
    return <div className="page-state">Cargando proyectos…</div>;
  }

  if (status === "error") {
    return (
      <div className="page-state page-state--error">
        <p>{error}</p>
        <button onClick={loadProjects}>Reintentar</button>
      </div>
    );
  }

  return (
    <section className="projects-page">
      <header className="page-header">
        <h1>Proyectos</h1>
        <button className="btn btn--primary" onClick={openCreate}>
          + Nuevo proyecto
        </button>
      </header>

      {error && <p className="inline-error">{error}</p>}

      {projects.length === 0 ? (
        <EmptyState
          title="Aún no tienes proyectos"
          message="Crea tu primer proyecto para empezar a organizar tareas."
          actionLabel="+ Nuevo proyecto"
          onAction={openCreate}
        />
      ) : (
        <div className="card-grid">
          {projects.map((project) => (
            <ProjectCard
              key={project.id}
              project={project}
              onEdit={() => openEdit(project)}
              onDelete={() => setToDelete(project)}
            />
          ))}
        </div>
      )}

      {isFormOpen && (
        <ProjectDialog
          project={editing}
          onSave={handleSave}
          onClose={closeForm}
        />
      )}

      {toDelete && (
        <ConfirmDialog
          title="Borrar proyecto"
          message={`¿Seguro que quieres borrar "${toDelete.name}"? Esta acción no se puede deshacer.`}
          confirmLabel="Borrar"
          onConfirm={confirmDelete}
          onCancel={() => setToDelete(null)}
        />
      )}
    </section>
  );
}
src/components/projects/ProjectDialog.jsx — formulario reutilizable
import { useState } from "react";

// El mismo componente sirve para crear y editar: si recibe "project",
// está en modo edición; si es null, en modo creación.
export default function ProjectDialog({ project, onSave, onClose }) {
  // El borrador vive aquí (estado local). Los valores iniciales salen
  // del proyecto en edición o de valores por defecto.
  const [form, setForm] = useState({
    name: project?.name ?? "",
    description: project?.description ?? "",
    color: project?.color ?? "#61dafb",
  });
  const [errors, setErrors] = useState({});
  const [saving, setSaving] = useState(false);

  // Un único handler para todos los campos, usando el atributo name.
  function handleChange(event) {
    const { name, value } = event.target;
    setForm((current) => ({ ...current, [name]: value }));
  }

  function validate() {
    const next = {};
    const name = form.name.trim();
    if (name.length === 0) next.name = "El nombre es obligatorio";
    if (name.length > 60) next.name = "Máximo 60 caracteres";
    setErrors(next);
    return Object.keys(next).length === 0;
  }

  async function handleSubmit(event) {
    event.preventDefault();
    if (!validate()) return;

    setSaving(true);
    try {
      await onSave({ ...form, name: form.name.trim() });
    } finally {
      setSaving(false);
    }
  }

  return (
    <div className="dialog-backdrop" onClick={onClose}>
      <!-- stopPropagation evita que el clic dentro cierre el modal -->
      <form
        className="dialog"
        onClick={(e) => e.stopPropagation()}
        onSubmit={handleSubmit}
      >
        <h2>{project ? "Editar proyecto" : "Nuevo proyecto"}</h2>

        <label>
          Nombre
          <input
            name="name"
            value={form.name}
            onChange={handleChange}
            autoFocus
            aria-invalid={Boolean(errors.name)}
          />
        </label>
        {errors.name && <p className="field-error">{errors.name}</p>}

        <label>
          Descripción
          <textarea
            name="description"
            value={form.description}
            onChange={handleChange}
            rows={3}
          />
        </label>

        <label>
          Color
          <input type="color" name="color" value={form.color} onChange={handleChange} />
        </label>

        <footer className="dialog__actions">
          <button type="button" onClick={onClose} disabled={saving}>
            Cancelar
          </button>
          <button type="submit" disabled={saving}>
            {saving ? "Guardando…" : "Guardar"}
          </button>
        </footer>
      </form>
    </div>
  );
}
src/components/projects/ProjectCard.jsx
import { Link } from "react-router-dom";

export default function ProjectCard({ project, onEdit, onDelete }) {
  return (
    <article className="project-card">
      <span className="project-card__color" style={{ background: project.color }} />

      <!-- El título enlaza al detalle del proyecto (ruta /projects/:id) -->

      </Link>

      </footer>
    </article>
  );

Decisiones del ejemplo: (1) handleSave unifica crear y editar: el modal no sabe en qué modo está, solo envía datos; (2) el borrado es optimista —quitamos el elemento de inmediato y restauramos si la API falla—; (3) el estado de carga de la página es un único campo status en lugar de varios booleanos, para que no puedan darse combinaciones imposibles; (4) la validación se hace en el cliente y en el servidor.

5 · Buenas prácticas

HazEvitaPor qué
Actualizar el estado con la respuesta del servidor Recargar toda la lista (o la página) tras cada operación Una petición menos y sin parpadeo; la API ya devuelve la entidad.
Un status único (loading/ready/error) isLoading + isError + data sueltos Evitas estados imposibles (loading y error a la vez).
Optimista + rollback en acciones de bajo riesgo Optimista «a lo loco» sin restaurar en error El usuario ve el efecto al instante, pero la UI nunca miente.
Confirmación para acciones destructivas Botón «Borrar» que actúa directamente Evita pérdidas accidentales; es una expectativa de UX básica.
Un modal reutilizable create/edit Dos formularios casi idénticos Menos código duplicado y validaciones coherentes.
onClick en el backdrop + stopPropagation dentro Que el modal se cierre al pulsar cualquier tecla o fuera sin querer Cierra de forma intuitiva sin cerrar por accidente al interactuar.

6 · Errores habituales

Error 1: mutar la lista tras crear

✘ Incorrecto 
// push muta el array del estado: React no detecta el cambio
const { project } = await projectService.create(data);
projects.push(project);      // ← misma referencia, no re-renderiza
setProjects(projects);
✔ Correcto 
const { project } = await projectService.create(data);
setProjects((current) => [project, ...current]); // nuevo array

Error 2: borrado optimista sin rollback

✘ Incorrecto 
setProjects((c) => c.filter((p) => p.id !== id));
await projectService.remove(id);
// Si la API falla, el proyecto desaparece de la UI pero sigue en el servidor.
✔ Correcto 
const previous = projects;                       // guardamos el estado
setProjects((c) => c.filter((p) => p.id !== id));
try {
  await projectService.remove(id);
} catch (err) {
  setProjects(previous);                         // restauramos si falla
  setError(err.message);
}

Error 3: leer state del closure en lugar del funcional

✘ Incorrecto 
// Si dos guardados ocurren seguidos, el segundo parte de una lista vieja.
setProjects([...projects, project]);
✔ Correcto 
// La forma funcional recibe SIEMPRE el estado más reciente.
setProjects((current) => [...current, project]);

Por qué: el cierre captura el valor de projects en el momento del render. Con la forma funcional, React te da el último estado en el momento de aplicar el cambio (Módulo 4).

8 · Reto

🎯 Actualización optimista al crear, con id temporal

Crear un proyecto hoy espera la respuesta del servidor para mostrarlo (merge). Cambia ese comportamiento a optimista real, igual que hacen Trello o Linear:

  1. Al guardar, genera un id temporal (p. ej. `temp-${crypto.randomUUID()}`) y añade el proyecto a la lista antes de que responda la API.
  2. Marca ese proyecto como «pendiente» (un campo _pending: true) y píntalo con una opacidad o un spinner para indicar que se está guardando.
  3. Cuando llegue la respuesta, reemplaza el proyecto temporal por el real (con su id definitivo del servidor).
  4. Si la API falla, elimina el temporal y muestra el error.
  5. Impide editar o borrar un proyecto mientras _pending sea true (no tendría id real).

Pista: cuida la función de merge: al sustituir por id debes buscar el temp-… correspondiente, no el id real. Piensa también qué pasa si el usuario crea dos proyectos seguidos en mala red.

No lo resuelvas todavía. La actualización optimista bien hecha —con ids temporales y reconciliación— es una de las técnicas que más se valoran en un desarrollador frontend senior.

9 · Resumen

  • Un CRUD completo tiene cinco operaciones y cada una con estados de carga y error.
  • El servidor es la fuente de verdad; el estado de React es una copia que sincronizamos con la respuesta de la API.
  • Tres estrategias de sincronización: refetch, merge con la respuesta y optimista (con rollback).
  • URLSearchParams para query strings seguros.
  • Un modal reutilizable create/edit evita duplicar formularios.
  • Estado funcional (setX(current => …)) siempre que el nuevo valor dependa del anterior.
  • Confirmación obligatoria en operaciones destructivas.

10 · Preguntas frecuentes

¿Refetch o merge con la respuesta del servidor?

Si la API devuelve la entidad creada/actualizada, el merge es más rápido y no parpadea. El refetch es más seguro cuando la operación altera otros elementos (por ejemplo, reordenar posiciones). En TaskFlow la API devuelve siempre la entidad, así que usamos merge; reservamos el refetch para casos como la paginación.

¿Guardo el formulario en un contexto global?

No. El borrador es estado efímero local: solo interesa al formulario. Meterlo en un contexto global añade complejidad y acopla una parte de la app con otra. Regla: eleva el estado solo cuando un ancestro común lo necesita.

¿Por qué el borrado es optimista y la creación no?

El borrado es de bajo riesgo (si falla, «desaparece» algo que el usuario quería quitar; restaurarlo es transparente). La creación necesita el id del servidor para muchas acciones posteriores, así que esperar la respuesta evita tener que inventar ids temporales (el reto te reta a hacerlo bien).

¿Cómo evito el «doble submit» si el usuario hace clic dos veces?

Deshabilita el botón mientras saving es true (ya lo hacemos) y, como defensa extra en el backend, usa un idempotency key en la cabecera. En el cliente, el disabled resuelve el 99 % de los casos.

¿Debo validar en el cliente si el servidor ya valida?

Sí: en el cliente por UX (feedback inmediato, sin ida y vuelta), en el servidor por seguridad (el cliente es manipulable). El servidor siempre manda; la validación del cliente es solo un atajo amable.
