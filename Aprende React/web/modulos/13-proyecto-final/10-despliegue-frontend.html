Despliegue del frontend

Módulo 13 · Proyecto final: TaskFlow 🕐 35 minutos

1 · Introducción

Una aplicación que solo corre en tu portátil no existe para nadie más. Hoy publicamos TaskFlow en internet. Y, aunque una SPA es «solo HTML, CSS y JavaScript», desplegarla bien tiene sus trampas: variables de entorno que solo se aplican al construir, rutas que el servidor debe redirigir, caché que hay que saber invalidar y CORS que hay que configurar.

Qué vamos a aprender hoy: a generar el build de producción con Vite, a entender qué se lleva al hosting, a configurar el fallback de SPA, a gestionar las variables de entorno por entorno y a automatizar el despliegue.

Qué problema resuelve: a diferencia de un sitio estático simple, una SPA maneja sus rutas en el cliente. Si un usuario entra directamente a /projects/42 y el servidor no conoce esa ruta, devuelve un 404. Hay que enseñar al hosting a servir index.html para cualquier ruta («SPA fallback»).

Cuándo se utiliza: cada vez que sacas una versión a producción. Con un pipeline decente, desplegar es automático al hacer merge.

Errores típicos: desplegar sin variables de producción (la app apunta a localhost y no carga nada), olvidar el fallback de SPA (404 al recargar), o meter secretos en variables VITE_ (terminan en el bundle).

2 · Teoría

Qué es un build y por qué no despliegas el código fuente

En desarrollo, Vite sirve tus módulos ES tal cual y los transforma al vuelo. En producción, construye: agrupa (bundling), minifica, elimina código muerto (tree-shaking), divide en chunks y versiona los nombres de archivo para la caché. El resultado va a dist/.

src/ (módulos ES, comentado, sin minificar) │ │ pnpm build (esbuild + Rollup, dentro de Vite) ▼ dist/ ├── index.html ← un solo HTML, con <script> y <link> inyectados └── assets/ ├── index-a1b2c3.js ← bundle minificado (hash para caché) ├── index-d4e5f6.css └── vendor-7g8h9i.js ← dependencias separadas (code splitting) El hash del nombre cambia cuando cambia el contenido → caché inmutable segura.
terminal — construir y previsualizar
# Build de producción (la salida es dist/)
pnpm build

# Previsualizar el build tal cual se servirá (¡no es el servidor de dev!)
pnpm preview
⚠️ pnpm dev y pnpm preview NO son lo mismo

preview sirve los archivos reales de dist/, sin el proxy de desarrollo. Si tu app funciona en dev pero no en preview, casi siempre es un problema de variables de entorno o de rutas absolutas: adelántate y pruébalo siempre antes de desplegar.

Las variables VITE_* se «conhielan» en el build

Vite sustituye import.meta.env.VITE_* por su valor en tiempo de build, no en tiempo de ejecución. Esto significa:

  • Cambiar una variable exige volver a construir (no basta con reiniciar).
  • El valor queda impreso en el JavaScript que descarga cualquiera.
  • Por eso solo van aquí datos públicos (URLs, flags), nunca secretos.

SPA fallback: la regla que todo hosting debe cumplir

El servidor debe servir index.html para cualquier ruta que no sea un archivo estático. Ejemplo en Netlify (public/_redirects) o Vercel (vercel.json):

public/_redirects (Netlify)
# Cualquier ruta que no sea un archivo existente → index.html
/*    /index.html   200
vercel.json (Vercel)
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
nginx.conf (servidor propio)
server {
  listen 80;
  root /usr/share/nginx/html;

  # Archivos estáticos con caché larga (los nombres llevan hash)
  location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
  }

  # SPA fallback: todo lo demás sirve index.html
  location / {
    try_files $uri $uri/ /index.html;
  }
}
Petición: GET /projects/42 │ ▼ ¿Existe un archivo "projects/42"? ── no ──► sirve index.html (200) │ │ sí React Router lee la URL │ y monta <ProjectPage /> ▼ sirve el archivo estático

3 · Ejemplo mínimo

El mínimo para tener un build desplegable: la configuración de vite.config.js adaptada a producción y la variable de la API.

vite.config.js — versión producción
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig(({ command }) => ({
  plugins: [react()],

  // "base" es la ruta pública desde la que se sirve la app.
  // "./" funciona en cualquier subcarpeta (GitHub Pages incluido).
  base: "./",

  build: {
    outDir: "dist",
    sourcemap: true,            // mapas para depurar errores en producción (Sentry)
    // Divide el bundle: separar las dependencias del código de la app
    // mejora la caché (cambiar tu código no invalida el vendor).
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["react", "react-dom", "react-router-dom"],
        },
      },
    },
  },

  // El proxy SOLO se aplica en desarrollo.
  server:
    command === "serve"
      ? {
          proxy: {
            "/api": { target: "http://localhost:5080", changeOrigin: true },
            "/hubs": { target: "http://localhost:5080", ws: true },
          },
        }
      : undefined,
}));
.env.production
# URL PÚBLICA de la API en producción (queda impresa en el bundle).
VITE_API_URL=https://api.taskflow.example.com/api

Línea por línea:

  1. base: "./" — la app usa rutas relativas para sus assets: funciona igual en la raíz de un dominio o en una subcarpeta.
  2. sourcemap: true — genera .map para que un servicio como Sentry traduzca el stack minificado a tu código.
  3. manualChunks — separa las librerías (vendor) del código propio: si cambias un componente, el usuario no vuelve a descargar React.
  4. El proxy vive solo cuando command === "serve": en producción no existe (y no debe existir).

4 · Ejemplo real

Un pipeline completo de GitHub Actions que prueba, construye y despliega a Netlify en cada push a main.

.github/workflows/deploy.yml
name: Deploy TaskFlow

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # pnpm viene con Node via corepack; lo activamos.
      - uses: pnpm/action-setup@v4
        with:
          version: 11

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: "pnpm"

      - run: pnpm install --frozen-lockfile

      # La puerta de calidad: si los tests fallan, NO se despliega.
      - run: pnpm test -- --run

      # Las variables de entorno del build vienen de los "secrets"/"vars"
      # del repositorio. Vite las imprime en el bundle: aquí solo van las públicas.
      - run: pnpm build
        env:
          VITE_API_URL: ${{ vars.VITE_API_URL }}

      # Publicamos el contenido de dist/ (solo en push a main).
      - name: Deploy to Netlify
        if: github.ref == 'refs/heads/main'
        uses: nwtgck/actions-netlify@v3
        with:
          publish-dir: ./dist
          production-deploy: true
        env:
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}

// Misma línea que en la lección 1, pero ahora el valor viene del
// .env.production que inyecta el CI. Cero cambios en el código.
const BASE_URL = import.meta.env.VITE_API_URL ?? "/api";

export async function request(path, options = {}) {
  const token = localStorage.getItem("taskflow.token");

  const response = await fetch(`${BASE_URL}${path}`, {
    ...options,
    headers: {
      "Content-Type": "application/json",
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...options.headers,
    },
    body: options.body ? JSON.stringify(options.body) : undefined,
  });

  if (!response.ok) {
    throw new Error(`Error ${response.status}`);
  }
  return response.status === 204 ? null : response.json();
}
🔗 CORS: no lo olvides en el backend

Si sirves el frontend en https://taskflow.app y la API en https://api.taskflow.example.com, son orígenes distintos: el backend debe autorizar explícitamente ese origen en su configuración de CORS (Módulo 14). Debe incluir los métodos y las cabeceras (Authorization, Content-Type) y, si usas SignalR, AllowCredentials.

Decisiones del ejemplo: (1) los tests son una puerta: si fallan, no se despliega; (2) --frozen-lockfile garantiza que el CI instala exactamente las versiones del pnpm-lock.yaml; (3) las variables de build vienen de vars (públicas) y los secretos de secrets; (4) desplegamos solo desde main; las pull requests generan una preview.

6 · Errores habituales

Error 1: olvidar el SPA fallback

✘ Incorrecto 
# Servidor que solo sirve archivos existentes
# GET /projects/42 → 404 Not Found (aunque la ruta exista en React)
✔ Correcto 
# SPA fallback: cualquier ruta desconocida sirve index.html
try_files $uri $uri/ /index.html;

Error 2: desplegar con la URL de desarrollo

✘ Incorrecto 
# .env.production (mal copiado del de desarrollo)
VITE_API_URL=http://localhost:5080/api
# En producción, los usuarios intentan llamar a SU localhost → todo falla.
✔ Correcto 
# .env.production
VITE_API_URL=https://api.taskflow.example.com/api

Error 3: cachear el index.html

✘ Incorrecto 
# index.html cacheado 1 año → los usuarios siguen con la app vieja
location = /index.html { expires 1y; }
✔ Correcto 
# El HTML SIEMPRE se revalida; los assets (con hash) sí se cachean
location = /index.html { add_header Cache-Control "no-cache"; }
location /assets/ { add_header Cache-Control "public, immutable"; expires 1y; }

Por qué: el index.html es el que referencia los nombres con hash del bundle nuevo. Si lo cacheas, el navegador sigue pidiendo el bundle viejo. Los assets, al llevar el hash en el nombre, pueden cachearse «para siempre» sin riesgo.

7 · Ejercicio guiado

  1. Actualiza vite.config.js con base: "./", sourcemap y manualChunks. Crea .env.production con la URL real.

  2. Genera el build y analízalo:

    pnpm build
# Observa el tamaño de cada chunk en la salida
ls dist/assets

  3. Previsualiza el build: pnpm preview. Navega a una ruta profunda (p. ej. /projects/1) y recarga. En el servidor de preview debería funcionar (Vite ya aplica el fallback).

  4. Crea public/_redirects (Netlify) o vercel.json con la regla de SPA fallback.

  5. Crea el workflow .github/workflows/deploy.yml de GitHub Actions con los pasos: install → test → build → deploy.

  6. Verifica en producción: abre la URL desplegada, recarga en una ruta profunda, abre la consola y confirma que no hay errores de CORS ni peticiones a localhost. Revisa en Network que el index.html responde no-cache y los assets immutable.

✅ Solución esperada

La app desplegada carga desde su dominio, recargar en cualquier ruta no da 404, los tests corren en el pipeline antes del despliegue y cada push a main publica una versión nueva automáticamente.

8 · Reto

🎯 Despliegue sin caídas y con marcha atrás

Lleva el despliegue a nivel profesional. Debe cumplir estas condiciones:

  1. Previsualizaciones por pull request: cada PR genera una URL temporal con su build, para que cualquiera pueda revisar el cambio antes del merge.
  2. Versionado y rollback: guarda cada build publicado (por etiqueta/git tag) y permita volver a la versión anterior con un solo comando o clic si algo sale mal.
  3. Detección de errores: integra Sentry (con los sourcemaps del build) para recibir los errores reales de producción agrupados y con stack legible.
  4. Sin downtime: explica por qué el modelo de archivos con hash + index.html sin caché hace que el despliegue sea atómico con Cloudflare/CDN, y qué hacer con los usuarios que tienen la pestaña abierta durante el cambio de versión (¿recargar? ¿avisar?).
  5. Meta de rendimiento: usa Lighthouse o PageSpeed para llegar a una puntuación alta, y explica cómo lo lograste (code splitting, lazy de rutas, tamaño del vendor).

Pista: para el punto 4, investiga el patrón «stale-while-revalidate» y el manejo de chunks que ya no existen (un usuario con el HTML viejo pide un /assets/index-viejo.js que fue borrado → error de carga). La solución típica es detectar el fallo y forzar una recarga.

No lo resuelvas todavía. Desplegar «sin caídas» es una de las habilidades que más separa a un junior de un senior.

9 · Resumen

  • pnpm build genera dist/: bundling, minificación, tree-shaking y nombres con hash.
  • pnpm preview sirve el build real: pruébalo siempre antes de desplegar.
  • Las variables VITE_* se congelan en el build y quedan públicas: nunca secretos.
  • SPA fallback obligatorio: cualquier ruta desconocida sirve index.html.
  • Caché correcta: index.html sin caché, assets con hash immutable.
  • CI/CD: tests → build → deploy automático; variables desde vars/secrets.
  • No olvides CORS en el backend cuando frontend y API tienen dominios distintos.

10 · Preguntas frecuentes

¿Puedo desplegar en GitHub Pages?

Sí, con matices: GitHub Pages no soporta rewrites reales, así que el fallback se emula copiando index.html a 404.html (el servidor sirve ese archivo en rutas desconocidas con código 200 según configuración). Además, si sirves en usuario.github.io/repo, configura base: "/repo/".

¿Por qué mi app funciona en local pero no en producción?

Las tres causas más comunes: (1) falta la variable VITE_API_URL de producción; (2) falta el SPA fallback; (3) falta el CORS en el backend. La cuarta, menos frecuente, es un base mal configurado si sirves en subcarpeta. Revisa la consola del navegador: casi siempre te lo dice.

¿Necesito un servidor Node en producción?

No. Una SPA construida es contenido estático: HTML, CSS y JS que cualquier servidor (o CDN) puede servir. Tu backend .NET 8 es el único servidor «de verdad». Esto abarata muchísimo el hosting del frontend.

¿Los sourcemaps exponen mi código?

Si los sirves junto al sitio, sí (recuperan tu código fuente legible). Lo profesional es generarlos y subirlos al servicio de errores (Sentry), pero no publicarlos en el hosting, o protegerlos con autenticación.

¿Cómo gestiono varias versiones o entornos (staging, prod)?

Con ramas y variables por entorno: main → producción, develop o PRs → staging, cada una con su VITE_API_URL. Como el valor se congela en el build, cada entorno genera su propio dist/. Los previews por PR de Netlify/Vercel automatizan esto.
