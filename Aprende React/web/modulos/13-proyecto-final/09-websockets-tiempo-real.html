WebSockets: tiempo real

Módulo 13 · Proyecto final: TaskFlow 🕐 50 minutos

1 · Introducción

Imagina que Ana mueve una tarea y Luis, en otra pestaña, sigue viendo la tarea en la columna antigua. Hasta ahora nuestra app solo «escucha» cuando el usuario actúa. El tiempo real resuelve esto: cuando algo cambia en el servidor, todos los clientes conectados se enteran al instante.

Qué vamos a aprender hoy: a conectar el frontend con el hub SignalR del backend .NET 8, a gestionar el ciclo de vida de la conexión (conectar, reconectar, cerrar) y a integrar los eventos remotos con nuestro estado local sin que la UI parpadee ni se dupliquen datos.

Qué problema resuelve: sin tiempo real, la única forma de ver cambios de otros es recargar o hacer polling (preguntar cada X segundos). El polling malgasta peticiones y aun así llega tarde. Un WebSocket mantiene una conexión abierta bidireccional: el servidor empuja los cambios en cuanto ocurren.

Cuándo se utiliza: tableros colaborativos (Trello), chats, editores en vivo, notificaciones, cotizaciones bursátiles. Siempre que «enterarse tarde» sea un problema.

Errores típicos: crear la conexión dentro de un componente que se re-monta (y multiplicar conexiones), olvidar cerrarla al desmontar (conexiones zombis), o aplicar eventos remotos que pisan al usuario y duplican datos.

2 · Teoría

¿Qué es un WebSocket y qué añade SignalR?

Un WebSocket es una conexión TCP persistente entre cliente y servidor, con dos direcciones. A diferencia de HTTP (petición → respuesta), el servidor puede enviar mensajes sin que el cliente los pida.

SignalR es una capa de .NET sobre WebSockets que se encarga de los detalles molestos: reconexión, fallback a otras técnicas (long polling) si el WebSocket no está disponible, llamadas a métodos con nombre y grupos. Del lado del cliente usamos la librería @microsoft/signalr.

📌 No sustituye al REST: lo complementa

Seguimos haciendo el CRUD por HTTP (es fiable, cacheable y fácil). Los WebSockets solo notifican a los demás clientes lo que ya pasó. El POST sigue siendo la fuente de verdad; el socket es la «campana» que avisa.

El flujo completo

Ana (cliente A) Servidor (SignalR Hub) Luis (cliente B) │ │ │ │ POST /tasks/123/status │ │ ├─────────────────────────────►│ │ │ 200 { task } │ persiste en PostgreSQL │ │◄─────────────────────────────┤ │ │ (actualiza su UI) │ Clients.Group(project) │ │ │ .SendAsync("TaskUpdated",t) │ │ ├─────────────────────────────►│ │ │ TaskUpdated│ │ │◄────(handler React)──────────┤ │ │ reconcilia su lista local │ │ │ (re-render, sin parpadeo) │

Fíjate en las dos cosas que hace el cliente B: primero recibe el evento (React ejecuta un handler) y luego reconcilia su estado (busca la tarea por id y la reemplaza). El servidor no manda «el tablero entero»: manda la entidad que cambió.

Grupos: cada cliente escucha lo suyo

Si un usuario tiene cinco proyectos, no tiene sentido recibir eventos de todos. El backend usa grupos de SignalR: al abrir un proyecto, el cliente se une al grupo de ese proyecto (JoinProject(projectId)) y solo recibe sus eventos.

Hub "board" ├── Grupo "project:a7c2" ← Ana y Luis (viendo el proyecto a7c2) └── Grupo "project:9f1e" ← Pedro (viendo otro proyecto) Clients.Group("project:a7c2").SendAsync("TaskUpdated", task) │ └── solo Ana y Luis lo reciben

Eventos que emite el backend

EventoPayloadQué hace el cliente
TaskCreated{ task }Añade la tarea a la lista (si no la tiene)
TaskUpdated{ task }Reemplaza la tarea por id
TaskDeleted{ taskId }Quita la tarea de la lista
CommentAdded{ taskId, comment }Añade el comentario si la tarea está abierta
ProjectUpdated{ project }Actualiza el nombre/color en la sidebar

El problema difícil: tu propio evento

Cuando tú cambias una tarea, actualizas la UI de forma optimista y haces el POST. El servidor emite TaskUpdated… y te lo manda a ti también (estás en el grupo). Si lo aplicas a ciegas, podrías pisar un cambio que el usuario hizo mientras tanto. La solución habitual: los eventos llevan un updatedAt/version y aplicamos el remoto solo si es más nuevo que el local (Last-Write-Wins con versión).

⚠️ Tiempo real ≠ resolución de conflictos

Que dos usuarios editen «a la vez» es un problema de concurrencia, no de WebSockets. En esta lección resolvemos el caso común con «gana el más reciente». Los conflictos reales (edición simultánea del mismo campo) se abordan con bloqueos optimistas (If-Match/ETag) o CRDTs, fuera del alcance de este curso.

3 · Ejemplo mínimo

El ejemplo más pequeño: conectar al hub y escuchar un evento. Ni reconexión ni grupos; solo la mecánica.

terminal — instalar el cliente
pnpm add @microsoft/signalr
src/services/signalClient.js — conexión mínima
import { HubConnectionBuilder, HubConnectionState } from "@microsoft/signalr";

// Una única conexión compartida por toda la app (patrón singleton).
let connection = null;

export function getConnection() {
  if (connection) return connection;

  connection = new HubConnectionBuilder()
    // En dev, "/hubs/board" pasa por el proxy de Vite (lección 1).
    .withUrl("/hubs/board", {
      // SignalR necesita el token en la query string para el handshake.
      accessTokenFactory: () => localStorage.getItem("taskflow.token") ?? "",
    })
    // Reintenta con backoff: 0s, 2s, 10s, 30s… y luego cada 30s.
    .withAutomaticReconnect([0, 2000, 10000, 30000])
    .build();

  return connection;
}

export async function startConnection() {
  const conn = getConnection();
  // Solo arrancamos si está detenida: evita el error
  // "Cannot start a connection that is not in the 'Disconnected' state".
  if (conn.state === HubConnectionState.Disconnected) {
    await conn.start();
  }
  return conn;
}

Línea por línea:

  1. HubConnectionBuilder — crea la conexión. Todos los ajustes se encadenan antes de .build().
  2. accessTokenFactory — el token JWT se envía al negociar. Sin él, el hub rechaza la conexión (401).
  3. withAutomaticReconnect([0, 2000, 10000, 30000]) — la librería reintenta sola con esos retardos. Sin esto, una caída de red mataría la conexión para siempre.
  4. El singleton evita crear una conexión nueva por cada componente que la use: sería un desastre de rendimiento.
  5. conn.state === Disconnected — arrancar una conexión ya activa lanza una excepción; comprobamos antes.

4 · Ejemplo real

La integración completa: un hook useRealtime que gestiona el ciclo de vida (conectar, unirse al proyecto, escuchar eventos, limpiar) y los handlers que reconcilian el estado local.

src/services/signalClient.js — versión completa
import { HubConnectionBuilder, HubConnectionState, LogLevel } from "@microsoft/signalr";

let connection = null;

export function getConnection() {
  if (connection) return connection;

  connection = new HubConnectionBuilder()
    .withUrl("/hubs/board", {
      accessTokenFactory: () => localStorage.getItem("taskflow.token") ?? "",
    })
    .withAutomaticReconnect([0, 2000, 10000, 30000])
    .configureLogging(LogLevel.Warning) // menos ruido que Information
    .build();

  return connection;
}

export async function startConnection() {
  const conn = getConnection();
  if (conn.state === HubConnectionState.Disconnected) await conn.start();
  return conn;
}

export async function stopConnection() {
  if (connection && connection.state !== HubConnectionState.Disconnected) {
    await connection.stop();
  }
}
src/hooks/useRealtime.js
import { useEffect } from "react";
import { getConnection, startConnection } from "../services/signalClient.js";

// Hook que se suscribe a los eventos del tablero de un proyecto.
// "handlers" es un objeto { TaskCreated, TaskUpdated, TaskDeleted, … }.
export function useRealtime(projectId, handlers) {
  useEffect(() => {
    // Si no hay proyecto, no hay nada que escuchar.
    if (!projectId) return;

    const conn = getConnection();
    let cancelled = false;

    // on/off de SignalR: guardamos las referencias para poder desuscribir.
    const registrations = Object.entries(handlers).map(([event, handler]) => {
      conn.on(event, handler);
      return [event, handler];
    });

    async function connect() {
      await startConnection();
      if (cancelled) return;
      // Nos unimos al grupo del proyecto: solo recibimos SUS eventos.
      await conn.invoke("JoinProject", projectId);
    }

    connect();

    // Reconexión: al recuperar, hay que volver a unirse al grupo.
    function handleReconnected() {
      conn.invoke("JoinProject", projectId).catch(() => {});
    }
    conn.onreconnected(handleReconnected);

    // ---- CLEANUP: se ejecuta al desmontar o al cambiar de proyecto ----
    return () => {
      cancelled = true;
      // 1) Salimos del grupo y desuscribimos los handlers.
      conn.invoke("LeaveProject", projectId).catch(() => {});
      registrations.forEach(([event, handler]) => conn.off(event, handler));
      conn.off("Reconnected", handleReconnected);
    };
  }, [projectId, handlers]);
}
src/pages/ProjectPage.jsx — integración con el estado local
import { useCallback, useState } from "react";
import { useParams } from "react-router-dom";
import { useRealtime } from "../hooks/useRealtime.js";
import Board from "../components/tasks/Board.jsx";

export default function ProjectPage() {
  const { id } = useParams();
  const [tasks, setTasks] = useState([]);

  // Handlers memoizados con useCallback: identidad estable entre renders
  // (si cambiaran en cada render, el useEffect de useRealtime se re-ejecutaría
  // sin parar y reconectaría el socket en bucle).
  const handleTaskCreated = useCallback((task) => {
    setTasks((current) => (current.some((t) => t.id === task.id) ? current : [...current, task]));
  }, []);

  const handleTaskUpdated = useCallback((task) => {
    setTasks((current) =>
      current.map((t) => {
        if (t.id !== task.id) return t;
        // Gana el más reciente: si mi copia local es más nueva, la conservo.
        const mine = new Date(t.updatedAt ?? 0).getTime();
        const theirs = new Date(task.updatedAt ?? 0).getTime();
        return theirs >= mine ? task : t;
      })
    );
  }, []);

  const handleTaskDeleted = useCallback(({ taskId }) => {
    setTasks((current) => current.filter((t) => t.id !== taskId));
  }, []);

  // Un único objeto de handlers, memoizado.
  const handlers = useCallback(
    () => ({
      TaskCreated: handleTaskCreated,
      TaskUpdated: handleTaskUpdated,
      TaskDeleted: handleTaskDeleted,
    }),
    [handleTaskCreated, handleTaskUpdated, handleTaskDeleted]
  );

  useRealtime(id, handlers);

  return <Board tasks={tasks} />;
}
src/components/layout/ConnectionStatus.jsx
import { useEffect, useState } from "react";
import { getConnection } from "../../services/signalClient.js";

// Indicador visual del estado del socket. Muy útil para depurar y para
// que el usuario sepa si está "en vivo" o desconectado.
export default function ConnectionStatus() {
  const [status, setStatus] = useState("Connecting");

  useEffect(() => {
    const conn = getConnection();
    setStatus(conn.state);

    // SignalR emite eventos de ciclo de vida que podemos observar.
    conn.onreconnecting(() => setStatus("Reconnecting"));
    conn.onreconnected(() => setStatus("Connected"));
    conn.onclose(() => setStatus("Disconnected"));

    return () => {
      conn.off("reconnecting");
      conn.off("reconnected");
      conn.off("close");
    };
  }, []);

  const labels = {
    Connected: "🟢 En vivo",
    Connecting: "🟡 Conectando…",
    Reconnecting: "🟡 Reconectando…",
    Disconnected: "🔴 Sin conexión",
  };

  return <span className="connection-status">{labels[status] ?? status}</span>;
}

Decisiones del ejemplo: (1) la conexión es un singleton: una para toda la app; (2) el hook une el cliente al grupo del proyecto y se desuscribe al salir; (3) los handlers van con useCallback para que la identidad sea estable (si no, el efecto reconectaría en bucle); (4) la reconciliación compara updatedAt (gana el más reciente); (5) creamos tareas solo si no existen (evita duplicados si el evento llega dos veces); (6) un indicador de conexión visible.

5 · Buenas prácticas

HazEvitaPor qué
Una conexión singleton compartida Crear una conexión por componente Multiplicar conexiones satura el servidor y el navegador.
Cleanup completo (off + LeaveProject) Dejar handlers y grupos «colgados» Evitas fugas de memoria y eventos que llegan a componentes muertos.
withAutomaticReconnect Confiar en que la red nunca falla Móviles, túneles y suspensión del portátil cortan la conexión a diario.
Reconciliar por id (merge) Reemplazar la lista entera con el evento Evitas parpadeos y perder cambios locales de otros campos.
Ganar el evento más reciente (updatedAt) Aplicar todo evento a ciegas Tu propio evento puede llegar tarde y pisar un cambio posterior.
Handlers con useCallback Funciones nuevas en cada render Identidad estable = el efecto no reconecta en bucle.

6 · Errores habituales

Error 1: conectar dentro de un componente que se re-monta

✘ Incorrecto 
function Board() {
  useEffect(() => {
    // ¡Nueva conexión cada vez que el Board se monta!
    const conn = new HubConnectionBuilder().withUrl("/hubs/board").build();
    conn.start();
    return () => conn.stop();
  }, []);
}
✔ Correcto 
function Board() {
  useEffect(() => {
    // Usamos la conexión compartida (singleton) y solo gestionamos
    // suscripciones y grupos.
    const conn = getConnection();
    conn.on("TaskUpdated", handler);
    conn.invoke("JoinProject", projectId);
    return () => conn.off("TaskUpdated", handler);
  }, [projectId]);
}

Error 2: no desuscribir y duplicar handlers

✘ Incorrecto 
// Cada navegación al proyecto añade OTRO handler del mismo evento.
conn.on("TaskUpdated", handleTaskUpdated);
// Al tercer cambio de proyecto, el handler se ejecuta tres veces
// por cada evento → duplicados y trabajo triple.
✔ Correcto 
conn.on("TaskUpdated", handleTaskUpdated);
return () => conn.off("TaskUpdated", handleTaskUpdated); // ← limpieza

Error 3: recrear los handlers en cada render

✘ Incorrecto 
// handlers es un objeto NUEVO en cada render → el useEffect de
// useRealtime se re-ejecuta siempre → conexión/desconexión en bucle.
const handlers = { TaskUpdated: (t) => setTasks(...) };
useRealtime(id, handlers);
✔ Correcto 
const handlers = useCallback(
  () => ({ TaskUpdated: handleTaskUpdated }),
  [handleTaskUpdated]
);
useRealtime(id, handlers);

Por qué: un objeto o función literal es una referencia nueva en cada render. Como useEffect compara dependencias por identidad, se dispararía siempre. useCallback estabiliza la referencia (Módulo 6).

8 · Reto

🎯 Presencia: quién está viendo el proyecto

Añade un indicador de presencia en tiempo real, como el «3 personas viendo» de Notion/Linear:

  1. El hub expone un método IAmHere(projectId, user) y emite un evento PresenceChanged con la lista de usuarios conectados a ese proyecto.
  2. Muestra avatares (o iniciales superpuestas) de quién está en el proyecto ahora.
  3. Al desmontar la página y salir del grupo, el servidor debe eliminar al usuario de la presencia. Si el cliente se cae sin avisar, el hub lo detecta por el timeout del socket.
  4. Añade un indicador «escribiendo…» que se active cuando alguien tiene el panel de una tarea abierto, y se apague tras 3 segundos de inactividad (como los chats).

Pista: la presencia suele gestionarse mejor en el servidor con un heartbeat: cada cliente envía «sigo aquí» cada 15 s y el servidor elimina a quien lleve más de 30 s sin señales. En el cliente, el «escribiendo…» es un debounce al revés: emite al empezar y expira solo.

No lo resuelvas todavía. La presencia es el paso natural siguiente al tiempo real y requiere pensar en el ciclo de vida del socket con cuidado.

9 · Resumen

  • Los WebSockets dan comunicación bidireccional persistente; SignalR añade reconexión, grupos y llamadas con nombre.
  • Complementan al REST: el CRUD sigue por HTTP; el socket solo notifica los cambios a los demás.
  • Conexión singleton + withAutomaticReconnect + token en accessTokenFactory.
  • Grupos por proyecto: cada cliente recibe solo los eventos que le importan.
  • Cleanup obligatorio: off de handlers y LeaveProject al desmontar.
  • Reconciliación por id y «gana el más reciente» (updatedAt) para evitar pisar cambios y duplicados.
  • Handlers con useCallback para una identidad estable y evitar reconexiones en bucle.

10 · Preguntas frecuentes

¿Por qué SignalR y no WebSocket nativo?

Podrías usar new WebSocket(url) directamente, pero tendrías que implementar a mano la reconexión, el fallback, el enrutado de mensajes por nombre y los grupos. SignalR te lo da hecho y se integra con el backend .NET 8 del Módulo 14. Como toda abstracción, esconde detalle; por eso esta lección explica qué hay debajo.

¿Cómo paso el token JWT al WebSocket?

Los navegadores no permiten cabeceras personalizadas en el handshake del WebSocket, así que SignalR envía el token por accessTokenFactory (lo añade a la negociación). Del lado .NET, el hub lo valida igual que un endpoint REST normal.

¿Por qué se duplican mis elementos tras reconectar?

Casi siempre por una de dos razones: (1) no desuscribiste los handlers y se ejecutan varias veces; (2) aplicas TaskCreated sin comprobar si la tarea ya existe. La solución: cleanup correcto en el useEffect y merge por id (solo añadir si no está).

¿Y mi propia acción? ¿Recibo mi evento?

Sí, porque estás en el grupo. Por eso comparamos updatedAt: si tu copia local ya refleja ese cambio, el evento se ignora. Otra opción es que el servidor no envíe al ConnectionId que originó el cambio (Clients.GroupExcept(...)), pero es más frágil (¿y si el mismo usuario tiene dos pestañas?).

¿Los WebSockets funcionan detrás de un proxy o CDN?

Normalmente sí, si el proxy admite el upgrade a WebSocket (por eso configuramos ws: true en el proxy de Vite de la lección 1). Algunos proxies corporativos los bloquean; SignalR cae entonces a long polling automáticamente, más lento pero funcional.
