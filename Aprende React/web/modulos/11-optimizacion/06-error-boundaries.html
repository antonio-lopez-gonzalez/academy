Error Boundaries

Módulo 11 · Optimización ⏱ 40 minutos

1 · Introducción

Un Error Boundary (frontera de error) es un componente de React que captura los errores de JavaScript lanzados en su árbol de hijos, los registra y muestra una interfaz alternativa (fallback) en lugar del componente que falló.

Sin él, un error durante el renderizado desmonta todo el árbol de React: la aplicación desaparece y el usuario ve una pantalla en blanco. Un fallo en un widget minúsculo (un reloj, un gráfico) puede tumbar toda la app. Los Error Boundaries evitan ese efecto dominó.

¿Por qué existe?

Porque un try/catch normal no captura errores de render. React renderiza de forma declarativa y en fases, así que necesitaba un mecanismo propio: componentes que declaran "si algo de lo que hay debajo falla, yo me ocupo". Ese mecanismo son los Error Boundaries.

Qué problema resuelve: aísla los fallos de renderizado en una sección de la UI, manteniendo el resto de la aplicación operativa y mostrando un mensaje útil.

Cuándo se usa: en puntos de integración de la UI: layouts, paneles del dashboard, widgets de terceros, cualquier sección que pueda fallar sin arrastrar al resto.

Errores típicos: creer que capturan errores de eventos o de setTimeout; envolver toda la app en uno solo; y no ofrecer al usuario forma de reintentar.

2 · Teoría

Los dos métodos que lo definen

Un Error Boundary es un componente de clase que implementa uno o ambos de estos métodos (en React 19 siguen siendo la única forma nativa):

  • static getDerivedStateFromError(error) — se ejecuta durante la fase de render. Debe ser puro y devolver el nuevo estado que hará que se muestre el fallback. No tiene acceso a la instancia (this).
  • componentDidCatch(error, info) — se ejecuta tras el commit. Aquí sí puedes hacer efectos: registrar el error, enviarlo a un servicio de monitoreo, etc. info.componentStack contiene la traza del árbol de componentes.
¿Cómo encuentra React la frontera?

React renderiza el árbol; si un componente lanza una excepción, React "sube" buscando el Error Boundary más cercano. Si lo encuentra, llama a getDerivedStateFromError, luego a componentDidCatch y renderiza su fallback. Si no hay ninguno, desmonta la app entera.

CÓMO SE PROPAGA UN ERROR DE RENDER ────────────────────────────────── Un componente hijo lanza una excepción │ ▼ React detiene el render e inspecciona hacia arriba │ ├── Encuentra un Error Boundary │ │ │ ▼ │ getDerivedStateFromError(error) → nuevo estado │ │ │ ▼ │ componentDidCatch(error, info) → logging │ │ │ ▼ │ renderiza el fallback (el resto de la app sigue viva) │ └── No encuentra ninguno │ ▼ desmonta todo el árbol · error en la consola

React 19 y Suspense

En React 19, los Error Boundaries también capturan los errores lanzados por una promesa rechazada dentro de <Suspense>. Esto cierra el círculo con la lección 03: un chunk de lazy que no se descarga puede atraparse con un Error Boundary adecuado.

3 · Ejemplo mínimo

src/components/ErrorBoundary.jsx
import { Component } from "react";

export default class ErrorBoundary extends Component {
  // Estado inicial: todavía no hay error.
  state = { hasError: false };

  // Fase de render: React pide el estado que muestra el fallback.
  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  // Fase de commit: aquí sí se pueden hacer efectos (logging, monitoreo).
  componentDidCatch(error, info) {
    console.error("Error capturado:", error, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return <h2>Algo salió mal.</h2>;
    }
    // Sin error, se renderiza el árbol normal.
    return this.props.children;
  }
}

Línea por línea:

  1. state = { hasError: false }: el estado que conmuta entre "normal" y "fallback". Se inicializa en el nivel de clase (sintaxis de campos públicos).
  2. getDerivedStateFromError: estático y puro; recibe el error y devuelve el estado que activa el fallback.
  3. componentDidCatch: recibe el error y info; ideal para reportar a Sentry, Datadog, etc.
  4. render: decide entre fallback y this.props.children.

4 · Ejemplo real

Un dashboard con varios widgets independientes. Cada widget va en su propia frontera: si el del clima falla, el reloj y el resto del panel siguen funcionando.

src/components/WidgetErrorBoundary.jsx
import { Component } from "react";

// Frontera reutilizable, configurable por props y con reintento.
export default class WidgetErrorBoundary extends Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, info) {
    // Punto de integración con el sistema de monitoreo.
    console.error("Widget falló:", error.message, info.componentStack);
  }

  // Resetea el estado para volver a intentar renderizar los hijos.
  handleRetry = () => this.setState({ hasError: false, error: null });

  render() {
    if (this.state.hasError) {
      return (
        <div className="widget-error">
          <h3>{this.props.fallbackTitle ?? "Widget no disponible"}</h3>
          <p>{this.props.fallbackMessage ?? "Ocurrió un error al cargar este widget."}</p>
          <button onClick={this.handleRetry}>Reintentar</button>
        </div>
      );
    }
    return this.props.children;
  }
}
src/Dashboard.jsx
import WidgetErrorBoundary from "./components/WidgetErrorBoundary.jsx";

function WeatherWidget({ city }) {
  // Un dato inválido provoca un error durante el render.
  if (!city) throw new Error("Ciudad no especificada");
  return <p>Clima en {city}: 22 °C, soleado</p>;
}

function ClockWidget() {
  return <p>{new Date().toLocaleTimeString()}</p>;
}

export default function Dashboard() {
  return (
    <section>
      <h1>Mi Dashboard</h1>
      <div className="grid">
        <WidgetErrorBoundary fallbackTitle="Error en el clima">
          <WeatherWidget city="" />
        </WidgetErrorBoundary>

        <WidgetErrorBoundary>
          <ClockWidget />
        </WidgetErrorBoundary>
      </div>
    </section>
  );
}

Decisiones explicadas:

  • Una frontera por widget: el fallo de uno no oculta a los demás. Envolver todo el dashboard en una sola frontera perdería el propósito.
  • Fallback configurable por props: el mismo componente sirve para cualquier sección con mensajes específicos.
  • Botón de reintento: el usuario puede recuperarse sin recargar la página; al resetear el estado, React vuelve a intentar el render.

5 · Buenas prácticas

HazEvitaPor qué
Coloca fronteras en secciones independientes Una sola frontera para toda la app Aísla el fallo: si cae un widget, el resto sigue vivo.
Ofrece un botón de reintento Un mensaje muerto sin salida Permite recuperarse sin recargar la página.
Reporta errores en componentDidCatch Silenciarlos con un console.log En producción necesitas saber que algo falla y dónde.
Personaliza el fallback Mostrar siempre "Algo salió mal" Un mensaje útil reduce la frustración del usuario.
Combínalas con Suspense y lazy Asumir que la red nunca falla En React 19 capturan también errores asíncronos de datos/chunks.
Trátalas como red de seguridad Usarlas como manejo de flujo normal No sustituyen a try/catch de eventos ni a la validación.
El "porqué" de fondo

Un buen diseño de componentes minimiza los errores de render. Las fronteras existen para lo inesperado, no para tapar validaciones que deberías hacer antes. Si tu app depende de que la frontera capture errores "habituales", el problema está en el diseño, no en la frontera.

6 · Errores habituales

Error 1: usarlas para capturar errores de eventos

✘ Incorrecto 
function Boton() {
  function handleClick() {
    // 💥 Un Error Boundary NO captura errores de manejadores de eventos.
    throw new Error("Error en el clic");
  }
  return <button onClick={handleClick}>Clic</button>;
}
✔ Correcto 
function Boton() {
  function handleClick() {
    try {
      // código que puede fallar
      throw new Error("Error en el clic");
    } catch (error) {
      // ✅ El error de un evento se maneja con try/catch.
      console.error("Error en el evento:", error);
    }
  }
  return <button onClick={handleClick}>Clic</button>;
}

Error 2: envolver toda la aplicación en una sola frontera

✘ Incorrecto 
// 💥 Un error en cualquier widget oculta TODA la aplicación.
<ErrorBoundary>
  <App />
</ErrorBoundary>
✔ Correcto 
// ✅ Fronteras por sección: el fallo de una no afecta a las demás.
<div>
  <ErrorBoundary><Sidebar /></ErrorBoundary>
  <ErrorBoundary><MainContent /></ErrorBoundary>
  <ErrorBoundary><WidgetPanel /></ErrorBoundary>
</div>

Error 3: implementarlo como componente funcional

✘ Incorrecto 
// 💥 No existe equivalente a getDerivedStateFromError con hooks.
function ErrorBoundary({ children }) {
  // Esto NO captura errores de render.
  return children;
}
✔ Correcto 
// ✅ Debe ser una clase. Alternativa: la librería `react-error-boundary`.
class ErrorBoundary extends Component {
  state = { hasError: false };
  static getDerivedStateFromError() {
    return { hasError: true };
  }
  render() {
    return this.state.hasError ? <Fallback /> : this.props.children;
  }
}

Error 4: no permitir la recuperación

✘ Incorrecto 
class ErrorBoundary extends Component {
  state = { hasError: false };
  static getDerivedStateFromError() {
    return { hasError: true };
  }
  render() {
    // 💥 Una vez en error, no hay forma de volver atrás.
    return this.state.hasError ? <h1>Error</h1> : this.props.children;
  }
}
✔ Correcto 
class ErrorBoundary extends Component {
  state = { hasError: false };
  static getDerivedStateFromError() {
    return { hasError: true };
  }
  handleRetry = () => this.setState({ hasError: false });
  render() {
    if (!this.state.hasError) return this.props.children;
    // ✅ El botón resetea el estado y React reintenta el render.
    return (
      <div>
        <h1>Error</h1>
        <button onClick={this.handleRetry}>Reintentar</button>
      </div>
    );
  }
}

7 · Ejercicio guiado

Vamos a proteger un perfil de usuario que carga datos "de una API" que puede fallar.

  1. Crea la frontera.
    src/components/ProfileErrorBoundary.jsx
    import { Component } from "react";

export default class ProfileErrorBoundary extends Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, info) {
    console.error("Error en perfil:", error.message, info.componentStack);
  }

  render() {
    if (!this.state.hasError) return this.props.children;
    return (
      <div className="profile-error">
        <h2>No pudimos cargar el perfil</h2>
        <p>{this.state.error.message}</p>
        <button onClick={() => this.setState({ hasError: false, error: null })}>
          Reintentar
        </button>
      </div>
    );
  }
}
  2. Crea el componente que puede fallar. 
    function UserProfile({ userId }) {
  // Simula una validación/API que falla con un id inválido.
  if (!userId || userId < 0) {
    throw new Error("ID de usuario inválido: " + userId);
  }
  const user = { id: userId, name: "Ana García", role: "Desarrolladora" };
  return <h2>{user.name} · {user.role}</h2>;
}
  3. Úsalo aislando la sección. 
    export default function App() {
  return (
    <main>
      <ProfileErrorBoundary>
        <UserProfile userId={-1} />
      </ProfileErrorBoundary>

      <section>
        <h2>Otra sección</h2>
        <p>Este contenido no se ve afectado por el error del perfil.</p>
      </section>
    </main>
  );
}
  4. Prueba. Al renderizar verás el fallback del perfil y la otra sección intacta. Pulsa "Reintentar": React resetea el estado, vuelve a renderizar UserProfile y este fallará otra vez (el userId sigue siendo -1). Cambia userId a 1 y comprueba que ahora se muestra el perfil.
Verificación

El objetivo es comprobar dos cosas: (1) que la sección hermana sigue funcionando aunque el perfil falle, y (2) que el botón de reintento vuelve a intentar el render en lugar de dejar la UI congelada.

8 · Reto

🎯 Una frontera de error reutilizable y con Suspense

Crea un componente ApiErrorBoundary genérico pensado para producción:

  1. Props flexibles: recibe fallback (un componente React), onReset (callback opcional) y onError (para reportar el error).
  2. Fallback con contexto: renderiza el fallback recibido pasándole el error y una función onRetry.
  3. Reset doble: al pulsar reintentar, llama a onReset si existe y resetea el estado. Restaura también el estado de la sección que falló.
  4. Integración con Suspense: úsala junto a un componente lazy que falle intencionadamente (simula un chunk que no se carga). Comprueba que en React 19 la frontera captura el error asíncrono.
  5. Prueba de fugas: verifica que, tras varios ciclos de fallo/reintento, no quedan listeners ni temporizadores colgando (usa el panel Performance).

Pista: para forzar el reset de un hijo cuando cambia la situación, pásale un key distinto; React remonta el subárbol desde cero.

9 · Resumen

  • Un Error Boundary es un componente de clase que captura errores de render de su árbol hijo y muestra un fallback.
  • Métodos clave: static getDerivedStateFromError(error) (estado) y componentDidCatch(error, info) (logging).
  • Captura errores de render, constructor, ciclos de vida y, en React 19, de datos asíncronos bajo Suspense.
  • No captura errores de eventos ni de código asíncrono normal: eso es try/catch.
  • Colócalas por secciones independientes, con fallback útil y botón de reintento.
  • Debe ser una clase; para componentes funcionales existe la librería react-error-boundary.

10 · Preguntas frecuentes

¿Captura errores de onClick o de fetch?

No. Solo captura errores del renderizado, del constructor y de los ciclos de vida (y, en React 19, de promesas rechazadas dentro de Suspense). Los errores de eventos y de código asíncrono se manejan con try/catch o .catch().

¿Por qué tiene que ser una clase?

Porque React expone getDerivedStateFromError y componentDidCatch solo en el API de clases; no hay hooks equivalentes estables. Si quieres uno funcional, usa react-error-boundary, que envuelve una clase por ti.

¿Cuántas fronteras debería tener mi app?

Depende del tamaño. Como regla: una por layout, una por sección independiente y, opcionalmente, una global como red de seguridad. En una app mediana suele haber entre 3 y 10.

¿Puede capturar sus propios errores?

No. Solo captura errores de sus hijos. Si la propia frontera lanza, el error sube a la frontera superior (o rompe la app si no hay ninguna).

¿Debo enviar todos los errores a un servicio externo?

Es una buena práctica en producción. Usa componentDidCatch para enviar el error y el componentStack a herramientas como Sentry, Datadog o LogRocket. Combínalo con source maps para descifrar los nombres en la build minificada.
