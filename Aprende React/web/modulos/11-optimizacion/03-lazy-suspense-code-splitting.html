lazy, Suspense y code splitting

Módulo 11 · Optimización ⏱ 35 minutos

1 · Introducción

Hay una optimización que no tiene nada que ver con re-renders: el tamaño del JavaScript que el navegador debe descargar antes de mostrar la primera pantalla. Cuando la app crece, el bundle crece con ella, y todo ese código —incluidas las páginas que el usuario quizá nunca visite— bloquea la carga inicial.

Code splitting es la técnica de partir ese bundle en trozos (chunks) que se descargan bajo demanda. React lo hace declarativo con dos piezas que trabajan juntas: lazy() (carga diferida de un componente) y <Suspense> (qué mostrar mientras llega).

¿Por qué existe?

Porque el tiempo hasta ver la primera pantalla es lo que más percibe el usuario. Enviar 800 KB de JavaScript cuando la pantalla de inicio necesita 120 KB es un desperdicio que se paga en cada visita. El code splitting convierte "descarga todo" en "descarga lo que vas a usar ahora".

Qué problema resuelve: reduce el bundle inicial dividiéndolo en chunks que se cargan solo cuando se necesitan (al navegar, al abrir un panel, al pulsar un botón).

Cuándo se usa: rutas que no todos visitan, componentes pesados (gráficos, editores, mapas), funciones detrás de un clic.

Errores típicos: declarar lazy dentro de un componente; usar lazy sin <Suspense>; intentar cargar un named export sin mapearlo; y trocear tanto que se generan decenas de peticiones minúsculas.

2 · Teoría

El bundle y el import() dinámico

Con un import estático, el bundler (Vite) mete ese módulo en el paquete principal. Con un import() dinámico —que devuelve una promesa— el bundler entiende que ese módulo puede vivir en un archivo aparte y lo genera como chunk independiente. 

// import estático → va en el bundle principal
import Panel from "./Panel.jsx";

// import() dinámico → Vite lo extrae a su propio chunk
const cargador = () => import("./Panel.jsx");
// `cargador()` devuelve una Promesa que resuelve al módulo.
React.lazy encapsula ese import()

lazy(cargador) toma una función que devuelve una promesa y te da un componente normal. React sigue el patrón Suspense de la promesa: cuando el import se resuelve, obtiene la propiedad .default del módulo y la usa como componente.

Cómo actúan lazy y Suspense juntos

FLUJO DE CARGA DIFERIDA ──────────────────────── El árbol intenta renderizar <Perfil /> │ ▼ Perfil es perezoso y su chunk aún no está descargado │ ▼ React "suspende" el render de esa rama │ ▼ Se muestra el `fallback` del <Suspense> más cercano │ ▼ El navegador descarga el chunk en segundo plano │ ▼ Cuando resuelve, React reintenta el render y muestra el componente real (React conserva el estado y revela el contenido sin parpadeo)

Suspense no "ve" cualquier cosa: solo se activa con lazy, con la lectura de una promesa vía use(), con hojas de estilo de precedence y durante el streaming del servidor. En particular, un fetch dentro de un useEffect NO activa Suspense.

Dónde poner la frontera de Suspense

Regla práctica: una frontera por cada "secuencia de carga" que el usuario percibe. Una frontera muy alta (cerca de la raíz) hará que al navegar parpadee toda la página; demasiadas fronteras pequeñas fragmentan el contenido en muchas pantallas de carga.

EstrategiaQué se difiereCuándo
Por rutaCada página de la appLo más habitual y de mayor impacto.
Por componente pesadoGráficos, editores, mapasPiezas de la UI que no todos los usuarios usan.
Bajo interacciónPanel que abre un botónCarga al primer clic, con su propio fallback.
Por vendorLibrerías grandes de tercerosEl bundler suele hacerlo solo; revísalo en el build.
Evitar esconder contenido ya visible

Si al navegar una ruta nueva suspende, React puede reemplazar por el fallback incluso el contenido que ya estaba en pantalla. Envuelve la actualización de navegación en startTransition (React Router ya lo hace) para que React espere y no esconda lo que el usuario ya está viendo.

3 · Ejemplo mínimo

src/App.jsx
import { lazy, Suspense, useState } from "react";

// lazy: el módulo ./Chart.jsx NO entra en el bundle inicial.
// Se descarga la primera vez que se renderiza <Chart />.
const Chart = lazy(() => import("./Chart.jsx"));

export default function App() {
  const [show, setShow] = useState(false);

  return (
    <div>
      <button onClick={() => setShow(true)}>Mostrar gráfico</button>

      {show && (
        <Suspense fallback={<p>Cargando gráfico…</p>}>
          <Chart />
        </Suspense>
      )}
    </div>
  );
}

Línea por línea:

  1. lazy(() => import("./Chart.jsx")): declara un componente perezoso. Es importante que sea una expresión import() literal para que Vite sepa crear el chunk.
  2. <Suspense fallback={…}>: sin esta frontera, renderizar un componente perezoso lanza un error en tiempo de ejecución.
  3. {show && …}: el chunk no se descarga hasta que el usuario pulsa el botón. Abre la pestaña Network y compruébalo.

4 · Ejemplo real

El caso profesional por excelencia: code splitting por ruta con React Router, un layout que permanece visible y un boundary de error para el caso de que un chunk falle al descargarse.

src/App.jsx
import { lazy, Suspense } from "react";
import { BrowserRouter, Routes, Route, Link } from "react-router-dom";
import Layout from "./components/Layout.jsx";
import ErrorBoundary from "./components/ErrorBoundary.jsx";

// Cada página es su propio chunk: solo se descarga al visitarla.
const Home = lazy(() => import("./pages/Home.jsx"));
const Productos = lazy(() => import("./pages/Productos.jsx"));
const Informes = lazy(() => import("./pages/Informes.jsx"));

export default function App() {
  return (
    <BrowserRouter>
      {/* El layout NO es perezoso: es el marco que siempre está visible. */}
      <Layout>
        {/* Boundary de error por si un chunk no carga (red, deploy). */}
        <ErrorBoundary fallback={<p>No se pudo cargar esta página.</p>}>
          {/* Un único Suspense: al navegar, solo cambia el contenido del layout. */}
          <Suspense fallback={<p>Cargando página…</p>}>
            <Routes>
              <Route path="/" element={<Home />} />
              <Route path="/productos" element={<Productos />} />
              <Route path="/informes" element={<Informes />} />
            </Routes>
          </Suspense>
        </ErrorBoundary>
      </Layout>
    </BrowserRouter>
  );
}

Y este es el boundary de error que captura los fallos de un chunk (la lección 06 lo estudia a fondo):

src/components/ErrorBoundary.jsx
import { Component } from "react";

export default class ErrorBoundary extends Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  render() {
    if (this.state.hasError) {
      // El fallback se recibe por props: reutilizable en toda la app.
      return this.props.fallback ?? <p>Algo salió mal.</p>;
    }
    return this.props.children;
  }
}

Decisiones explicadas:

  • Layout no perezoso: la cabecera y el menú aparecen al instante; solo el contenido espera.
  • Un solo Suspense alrededor de Routes: evita que se reemplace el layout completo durante una navegación.
  • ErrorBoundary: si el usuario tenía la app abierta y se despliega una versión nueva, el hash del chunk viejo desaparece y el import falla. El boundary muestra un mensaje en lugar de una pantalla rota.

5 · Buenas prácticas

HazEvitaPor qué
Declara lazy en el nivel superior del módulo Declararlo dentro de un componente Cada render crearía un componente nuevo y se perdería todo su estado.
Trocea por ruta primero Empezar troceando componentes diminutos Las rutas dan el mayor beneficio con la menor fragmentación.
Carga una librería pesada al usarla Importarla estáticamente "por si acaso" Gana todo el peso solo el usuario que realmente la usa.
Da un fallback con la forma del contenido (skeleton) Fallback genérico que salta y mueve el layout Reduce el layout shift y la sensación de parpadeo.
Envuelve los chunks en un boundary de error Asumir que la red siempre funciona Un chunk borrado tras un deploy rompería la app sin él.

6 · Errores habituales

Error 1: declarar lazy dentro del componente

✘ Incorrecto 
function Editor() {
  // 💥 Cada render crea un componente NUEVO: el estado del hijo se resetea.
  const Preview = lazy(() => import("./Preview.jsx"));
  return <Preview />;
}
✔ Correcto 
import { lazy } from "react";

// ✅ Declarado una sola vez, fuera del componente.
const Preview = lazy(() => import("./Preview.jsx"));

function Editor() {
  return <Preview />;
}

Error 2: lazy sin Suspense

✘ Incorrecto 
// 💥 "A component suspended while responding to synchronous input" → error.
return <Preview />;
✔ Correcto 
return (
  <Suspense fallback={<p>Cargando…</p>}>
    <Preview />
  </Suspense>
);

Error 3: intentar cargar un named export

✘ Incorrecto 
// 💥 lazy espera un `.default`; si el módulo solo tiene export nombrado, falla.
const Preview = lazy(() => import("./Preview.jsx"));
✔ Correcto 
// ✅ Mapea el export nombrado a un objeto con `.default`.
const Preview = lazy(() =>
  import("./Preview.jsx").then((mod) => ({ default: mod.Preview }))
);

8 · Reto

🎯 Precarga al hover y reintento de chunk

Mejora la app del ejercicio para que la navegación se sienta instantánea:

  1. Precarga predictiva: cuando el cursor pasa por encima de un <Link>, dispara import() del chunk de esa ruta (sin renderizarlo) para que ya esté en caché cuando el usuario haga clic.
  2. Reintento de chunk: si un chunk falla al cargar (simúlalo lanzando un error en el import), muestra un botón "Reintentar" que vuelva a montar el árbol y reintente la descarga.
  3. Suspense anidado: dentro de Informes, difiere un gráfico pesado con su propio Suspense y un skeleton que respete la forma del contenido.
  4. Mide: compara el tiempo desde el clic hasta contenido visible con y sin precarga al hover. Adjunta los números.

Pista: guarda la promesa del import() en un Map a nivel de módulo para no lanzar dos descargas del mismo chunk.

9 · Resumen

  • Code splitting = dividir el bundle en chunks que se cargan bajo demanda.
  • React.lazy(() => import(...)) declara un componente perezoso; debe ir en el nivel superior del módulo.
  • <Suspense fallback> es obligatorio alrededor de un componente perezoso y define la UI de carga.
  • La estrategia de mayor impacto es por ruta; también por componente pesado o tras una interacción.
  • Un fetch en useEffect no activa Suspense; sí lo hace use() con una promesa cacheada.
  • Envuelve los chunks en un Error Boundary y, si quieres, precarga al hover.

10 · Preguntas frecuentes

¿lazy funciona con named exports?

lazy espera que el módulo resuelto tenga un .default (export por defecto). Para un export nombrado, mapea con .then((mod) => ({'{'} default: mod.MiComponente {'}'})).

¿Por qué no aparece mi fallback durante un fetch?

Porque Suspense no detecta datos que se cargan dentro de un useEffect. Se activa con lazy, con use() sobre una promesa cacheada, o en el streaming del servidor. El data-fetching asíncrono "clásico" se gestiona con estados de loading/error (lo viste en el Módulo 9).

¿Cuántos Suspense debo tener?

Los que correspondan a las "secuencias de carga" que quieras mostrar. Ni uno gigante en la raíz (parpadea toda la página) ni uno por componente (fragmenta demasiado). Empieza con uno por ruta y refina según lo que veas.

¿Tengo que trocear todas las páginas?

No. Si una ruta es la de entrada y pesa poco, no ganas nada troceándola. El code splitting brilla en rutas secundarias, componentes pesados y librerías que no todos usan.

¿Esto sustituye al preloading de la lección 07?

Se complementan. Aquí descargamos el código de un componente bajo demanda; en la lección 07 verás preload / preinit para adelantar recursos (fuentes, imágenes, CSS) antes de que se necesiten.
