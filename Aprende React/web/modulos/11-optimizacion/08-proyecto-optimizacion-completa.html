Proyecto: optimización completa

Módulo 11 · Optimización ⏱ 60 minutos

1 · Introducción

Es la hora de juntar todo lo aprendido en el módulo. Vas a partir de un panel de productos deliberadamente lento y lo optimizarás paso a paso, midiendo cada cambio: memo, useMemo, useCallback, code splitting con lazy y Suspense, y el diagnóstico con el Profiler.

El proyecto vive en proyectos/m11-optimizacion/ y es una app Vite con React 19 y JavaScript. La regla del juego es simple: ninguna optimización vale si no se mide antes y después.

Objetivos del proyecto
  • Diagnosticar cuellos de botella reales con el Profiler (lecciones 01 y 04).
  • Estabilizar props y callbacks para que memo funcione (lección 02).
  • Trocear la app por ruta y por componente pesado (lección 03).
  • Proteger las secciones y los chunks con Error Boundaries (lección 06).
  • Documentar el antes y el después con números verificables.

La aplicación: un dashboard con una lista de 1.000 productos, filtros por categoría y precio, búsqueda en tiempo real, un gráfico de ventas pesado y varias rutas (Inicio, Productos, Informes, Ajustes).

SíntomaCausa técnicaTécnica que lo arregla

El método: medir, optimizar, volver a medir

Este proyecto no es "aplicar memo a todo". Es un ciclo disciplinado que repetiremos en cada paso:

CICLO DE OPTIMIZACIÓN DEL PROYECTO ────────────────────────────────── 1. MEDIR → Profiler + console/nº de renders + tamaño de bundle │ ▼ 2. DIAGNOSTICAR → ¿quién renderiza de más? ¿por qué (props/estado/cálculo)? │ ▼ 3. OPTIMIZAR → la técnica mínima que resuelve ESA causa │ ▼ 4. VERIFICAR → misma grabación, mismos números · ¿mejoró? │ ├── sí → documentar el antes/después y seguir └── no → revertir (no añadir complejidad gratis)

3 · Ejemplo mínimo

La optimización más pequeña con impacto real: estabilizar un valor derivado y una fila repetida. Es el ladrillo con el que se construye todo el proyecto.

src/components/ProductRow.jsx
import { memo } from "react";

// Se renderiza 1.000 veces: memorizarlo es el mayor ahorro del proyecto.
const ProductRow = memo(function ProductRow({ product, onSelect }) {
  return (
    <tr onClick={() => onSelect(product.id)}>
      <td>{product.name}</td>
      <td>{product.price} €</td>
    </tr>
  );
});

export default ProductRow;
src/components/ProductTable.jsx
import { memo, useMemo } from "react";
import ProductRow from "./ProductRow.jsx";

const ProductTable = memo(function ProductTable({ products, filters, onSelect }) {
  // El filtrado es caro: se recalcula SOLO si cambian sus entradas.
  const visible = useMemo(() => {
    return products
      .filter((p) => !filters.category || p.category === filters.category)
      .filter((p) => p.price <= filters.maxPrice)
      .filter((p) => p.name.toLowerCase().includes(filters.search.toLowerCase()));
  }, [products, filters]);

  return (
    <table>
      <tbody>
        {visible.map((p) => (
          <ProductRow key={p.id} product={p} onSelect={onSelect} />
        ))}
      </tbody>
    </table>
  );
});

export default ProductTable;

Línea por línea:

  1. memo en ProductRow: evita re-renders de 1.000 filas cuando sus props no cambian.
  2. useMemo para visible: el filtrado solo se repite si cambian products o filters.
  3. onSelect debe ser estable: por eso lo recibimos ya estabilizado con useCallback desde el padre (lo verás en el ejemplo real). Si no, memo en la fila no serviría de nada.
Sin medir, esto es fe

Este código es la "receta" típica, pero en tu app quizá el cuello de botella esté en otro sitio. Aplica estos cambios y mide: si el Profiler no muestra mejora, revisa que onSelect y filters sean estables (ese es el 90 % de los memo que "no funcionan").

4 · Ejemplo real

Este es el App.jsx final del proyecto: router con code splitting por ruta, un Suspense para el marco visible y un ErrorBoundary global para los chunks.

src/App.jsx
import { lazy, Suspense } from "react";
import { BrowserRouter, Routes, Route, Link } from "react-router-dom";
import Layout from "./components/Layout.jsx";
import ErrorBoundary from "./components/ErrorBoundary.jsx";

// Code splitting por ruta: cada página es su propio chunk.
const Inicio = lazy(() => import("./pages/Inicio.jsx"));
const Productos = lazy(() => import("./pages/Productos.jsx"));
const Informes = lazy(() => import("./pages/Informes.jsx"));
const Ajustes = lazy(() => import("./pages/Ajustes.jsx"));

export default function App() {
  return (
    <BrowserRouter>
      {/* El layout no es perezoso: es el marco que siempre se ve. */}
      <Layout>
        <ErrorBoundary fallback={<p>No se pudo cargar esta sección.</p>}>
          <Suspense fallback={<p>Cargando…</p>}>
            <Routes>
              <Route path="/" element={<Inicio />} />
              <Route path="/productos" element={<Productos />} />
              <Route path="/informes" element={<Informes />} />
              <Route path="/ajustes" element={<Ajustes />} />
            </Routes>
          </Suspense>
        </ErrorBoundary>
      </Layout>
    </BrowserRouter>
  );
}

Y este es el corazón del panel: la página Productos, donde se estabilizan las props que llegan a la tabla.

src/pages/Productos.jsx
import { useCallback, useMemo, useState } from "react";
import ProductTable from "../components/ProductTable.jsx";
import Filtros from "../components/Filtros.jsx";
import { PRODUCTS } from "../data/products.js";

export default function Productos() {
  // El estado vive AQUÍ, no en la raíz: el layout no se re-renderiza.
  const [search, setSearch] = useState("");
  const [category, setCategory] = useState("");
  const [maxPrice, setMaxPrice] = useState(Infinity);

  // ✅ Objeto estable: solo cambia si cambian sus campos.
  const filters = useMemo(
    () => ({ search, category, maxPrice }),
    [search, category, maxPrice]
  );

  // ✅ Callback estable: una sola referencia para las 1.000 filas.
  const handleSelect = useCallback((id) => {
    console.log("Producto seleccionado:", id);
  }, []);

  return (
    <>
      <Filtros
        search={search}
        onSearch={setSearch}
        onCategory={setCategory}
        onMaxPrice={setMaxPrice}
      />
      <ProductTable products={PRODUCTS} filters={filters} onSelect={handleSelect} />
    </>
  );
}

El PRODUCTS es una constante de módulo (lección 02), así que su referencia es estable por construcción:

src/data/products.js
// 1.000 productos simulados. Constante de módulo: referencia estable.
export const PRODUCTS = Array.from({ length: 1000 }, (_, i) => ({
  id: i + 1,
  name: `Producto ${i + 1}`,
  price: 10 + (i % 90),
  category: ["ropa", "calzado", "accesorios"][i % 3],
}));

Decisiones explicadas:

  • Estado en la página, no en App: el layout y las demás rutas no se re-renderizan al buscar.
  • filters con useMemo: un objeto nuevo en cada render rompería el memo de la tabla.
  • handleSelect con useCallback: mantiene una sola referencia para todas las filas.
  • PRODUCTS constante de módulo: nunca cambia de referencia, ideal para memorización.

6 · Errores habituales

Error 1: memorizar con props que cambian en cada render

✘ Incorrecto 
// 💥 `filters` y `onSelect` son nuevos en cada render:
//    el memo de ProductTable no sirve absolutamente de nada.
<ProductTable
  products={PRODUCTS}
  filters={{ search, category, maxPrice }}
  onSelect={(id) => console.log(id)}
/>
✔ Correcto 
// ✅ Propiedades estables: el memo de la tabla por fin actúa.
const filters = useMemo(() => ({ search, category, maxPrice }), [search, category, maxPrice]);
const handleSelect = useCallback((id) => console.log(id), []);

<ProductTable products={PRODUCTS} filters={filters} onSelect={handleSelect} />

Error 2: sobre-optimizar lo que no se ha medido

✘ Incorrecto 
// 💥 memo + useMemo + useCallback en un componente que renderiza un título.
//    Añade ruido y una comparación por render, sin ganancia real.
const Titulo = memo(function Titulo({ texto }) {
  const upper = useMemo(() => texto.toUpperCase(), [texto]);
  return <h1>{upper}</h1>;
});
✔ Correcto 
// ✅ Sin ceremonia: es trivial y no aparece como problema en el Profiler.
function Titulo({ texto }) {
  return <h1>{texto.toUpperCase()}</h1>;
}

Error 3: cargar el gráfico pesado aunque no se vea

✘ Incorrecto 
// 💥 Import estático: el gráfico entra en el bundle inicial aunque
//    casi nadie abra la pestaña de Informes.
import SalesChart from "../components/SalesChart.jsx";
✔ Correcto 
// ✅ Carga diferida: el chunk solo se descarga al abrir Informes.
import { lazy, Suspense } from "react";
const SalesChart = lazy(() => import("../components/SalesChart.jsx"));

<Suspense fallback={<p>Cargando gráfico…</p>}>
  <SalesChart />
</Suspense>

Error 4: dar por buena una optimización sin volver a medir

✘ Incorrecto 
// "Ya he puesto memo, seguro que va mejor." → no se vuelve a grabar.
✔ Correcto 
// Repite la MISMA grabación y compara el commit más lento del ranked chart.
// Si no mejora, el diagnóstico estaba mal: vuelve al paso 2.

8 · Reto

🎯 Llevar el panel a 10.000 filas

El proyecto actual maneja 1.000 productos con comodidad. ¿Aguanta 10.000? Demuéstralo:

  1. Sube a 10.000 filas (Array.from({'{'}length: 10000{'}'})) y vuelve a medir con el Profiler. Anota dónde se rompe.
  2. Virtualización: renderiza solo las filas visibles (scroll virtual). Puedes implementarlo tú o usar una librería ligera. Explica por qué memo ya no basta cuando el DOM tiene 10.000 nodos.
  3. Búsqueda diferida: usa useDeferredValue para que el input no espere al filtrado y la UI no se congele al escribir.
  4. Precarga de rutas: precarga el chunk de Informes al pasar el cursor por su enlace (lección 03) y mide la mejora.
  5. Informe final: entrega una tabla antes/después de cada técnica (memo, virtualización, diferido, precarga) con la métrica que la justifica.

Pista: cuando el número de nodos del DOM es el cuello de botella, el commit domina sobre el render, y la solución deja de ser la memorización: es renderizar menos cosas a la vez.

9 · Resumen

  • El proyecto aplica el ciclo medir → diagnosticar → optimizar → verificar.
  • Colocar el estado cerca de su uso evita renders sin escribir un solo memo.
  • memo + useCallback + useMemo trabajan juntos: una prop inestable invalida el memo.
  • Code splitting por ruta reduce el bundle inicial; el componente pesado se carga bajo demanda.
  • Error Boundaries alrededor de Suspense protegen frente a chunks que no cargan.
  • Toda optimización se documenta con números; la que no mejora, se revierte.

10 · Preguntas frecuentes

¿En qué orden debo aplicar las optimizaciones?

Por impacto y por coste: primero colocar bien el estado; después memorizar (memo/useMemo/useCallback); después code splitting. Y siempre midiendo cada paso por separado.

¿Cómo sé si memo está funcionando?

Con el Profiler: al repetir la interacción, el componente memorizado no debe aparecer en los commits donde sus props no cambian. Si sigue apareciendo, revisa props inestables (objetos, funciones) y "Why did this render?".

¿Cuánto debe encogerse el bundle?

Depende de la app. Lo relevante no es un número absoluto, sino que el chunk de la ruta de entrada se reduzca y que las rutas secundarias pesadas (como el gráfico) salgan del bundle inicial. Compáralo con pnpm build antes y después.

¿Y si el proyecto adoptara el React Compiler?

Muchas de las memorizaciones manuales (lección 05) las añadiría el compilador automáticamente. El diagnóstico, la colocación del estado y el code splitting seguirían siendo igual de importantes: el compilador no arregla la arquitectura.

¿Dónde encuentro el código completo del proyecto?

En proyectos/m11-optimizacion/. Instálalo con pnpm install y arráncalo con pnpm dev; compila con pnpm build para comparar los chunks.
