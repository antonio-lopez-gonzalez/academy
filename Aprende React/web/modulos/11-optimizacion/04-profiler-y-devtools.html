Profiler y React DevTools

Módulo 11 · Optimización ⏱ 30 minutos

1 · Introducción

En la lección 01 aprendimos el método: medir antes de optimizar. Aquí aprendes a medir bien. React DevTools es la extensión oficial de React y su pestaña Profiler es el instrumento más completo para ver qué se re-renderiza, cuánto tarda y por qué.

Un buen diagnóstico con el Profiler convierte una intuición ("creo que la tabla va lenta") en una decision justificada ("el render de ProductTable tarda 38 ms y ocurre en cada pulsación; el 80 % del tiempo de commit es suyo"). Solo entonces merece la pena aplicar memo, useMemo o code splitting.

¿Por qué existe?

Porque el rendimiento es contraintuitivo: el componente que parece lento muchas veces no lo es, y el que lo es pasa desapercibido. El Profiler elimina la adivinación y evita optimizaciones que añaden complejidad sin mejorar nada.

Qué problema resuelve: te dice qué componentes se re-renderizaron en cada commit, cuánto costaron y por qué, para que optimices lo que realmente importa.

Cuándo se usa: antes de cualquier optimización, al sospechar de una interacción concreta y al verificar que un cambio ha mejorado algo.

Errores típicos: profilar la build de desarrollo y sacar conclusiones; mirar el tiempo de render y olvidar el de commit; y grabar sesiones larguísimas imposibles de interpretar.

2 · Teoría

Instalación

React DevTools es una extensión de navegador. Instálala desde su tienda:

  • Chrome / Edge: "React Developer Tools".
  • Firefox: "React Developer Tools".

Al abrir las DevTools verás dos pestañas nuevas: ⚛ Components y ⚛ Profiler. La primera sirve para inspeccionar el árbol y las props; la segunda, para medir rendimiento.

Components: el árbol a rayos X

La pestaña Components te muestra la jerarquía real, con las props y los hooks de cada componente. Es la forma más rápida de responder "¿qué props está recibiendo ProductTable en este momento?" o de comprobar que un objeto que creías estable no lo es.

El badge "Memo ✨"

Si tu proyecto usa el React Compiler (lección 05), los componentes que ha optimizado muestran un ✨ junto a su nombre. Es la manera más directa de comprobar que el compilador está actuando.

Profiler: grabar, leer y decidir

El Profiler graba commits. Al detenerlo, dibuja un flamegraph (o gráfico de llamas) donde cada barra es un componente y su ancho refleja el tiempo de render. Un clic en cualquier barra abre el panel derecho con las props, el estado y la razón por la que ese componente renderizó.

LECTURA DEL PROFILER ──────────────────── Interacción del usuario │ ▼ ┌─ Commit 1 ─┬─ Commit 2 ─┬─ Commit 3 ─┐ (fase de commit, en ms) │ │ │ │ │ Flamegraph por commit: │ │ ┌──────── App (2.1 ms) ────────┐ │ │ │ ┌── ProductTable (38 ms) ─┐ │ │ ← el culpable │ │ │ Fila ×500 (36 ms) │ │ │ │ │ └─────────────────────────┘ │ │ │ └───────────────────────────────┘ │ └────────────────────────────────────────┘ Colores: amarillo/rojo = lento · verde = rápido · gris = no re-renderizó

Además del flamegraph existe la vista Ranked, que ordena los componentes por tiempo consumido. Empieza siempre por ahí: te da el top de sospechosos sin perderse en el árbol.

MétricaQué mideCómo interpretarla
Render timeLo que tardaron tus funciones de componente en ejecutarse.Alto y repetido = trabajo evitable (cálculos, listas, objetos).
Commit timeLo que tardó React en aplicar los cambios al DOM.Alto = demasiados cambios reales en el DOM.
InteractionsLa acción del usuario que disparó el commit.Te ata cada commit a un gesto concreto.
Why did this render?La causa del render (props, estado, contexto, padre).Determina la técnica adecuada para evitarlo.

Highlight updates: ver los renders en vivo

En la pestaña de Settings del Profiler (o en Components) puedes activar Highlight updates when components render. Los componentes que re-renderizan se dibujan con un borde que se ilumina. Es perfecto para detectar de un vistazo re-renders que no esperabas.

Configuración recomendada
  • Highlight updates: activado (visualización en vivo).
  • Record why each component rendered: activado (causa de cada render).
  • Parse hook names: activado (nombres reales de tus hooks).

3 · Ejemplo mínimo

Un componente con un cálculo que se repite en cada render. Con el Profiler verás el coste; sin él, solo tendrías la sospecha.

src/App.jsx
import { useState } from "react";

// Cálculo caro simulado.
function calcular(items) {
  let total = 0;
  for (let i = 0; i < 3_000_000; i++) total += items.length * 0.0001;
  return total;
}

export default function App() {
  const [n, setN] = useState(0);
  const [items] = useState(["a", "b", "c"]);

  // ⚠️ Se recalcula en CADA render, incluso cuando solo cambia `n`.
  const total = calcular(items);

  return (
    <>
      <button onClick={() => setN((v) => v + 1)}>Clic {n}</button>
      <p>Total: {total.toFixed(2)}</p>
    </>
  );
}

Qué mirar en el Profiler:

  1. Abre Profiler, pulsa el círculo de grabación y haz 5 clics.
  2. Detén la grabación. En la vista Ranked, App aparecerá con un tiempo alto en cada commit.
  3. Selecciona App y comprueba en "Why did this render?" que la causa es state: n.
  4. Ahora ya sabes que el problema es un cálculo no relacionado con n. La solución (useMemo) la verás aplicada en el ejemplo real.

4 · Ejemplo real

Volvemos al panel de productos. El flujo profesional es: grabar → identificar → aplicar → volver a medir.

  1. Graba la interacción lenta. Escribe 6 letras en el buscador. En el Ranked chart verás que ProductTable domina todos los commits.
  2. Identifica la causa. Selecciona ProductTable: "Why did this render?" dice props changed: products. El array se recrea en cada render del padre.
  3. Aplica la técnica adecuada. Estabiliza el array con useMemo y envuelve la tabla con memo. 
    import { memo, useMemo, useState } from "react";

const ProductTable = memo(function ProductTable({ products }) {
  return (
    <ul>
      {products.map((p) => (
        <li key={p.id}>{p.name}</li>
      ))}
    </ul>
  );
});

export default function App() {
  const [search, setSearch] = useState("");
  const [products] = useState(() => [/* catálogo */]);

  // La referencia solo cambia si cambian products o search.
  const visible = useMemo(
    () => products.filter((p) => p.name.includes(search)),
    [products, search]
  );

  return (
    <>
      <input value={search} onChange={(e) => setSearch(e.target.value)} />
      <ProductTable products={visible} />
    </>
  );
}
  4. Vuelve a medir. Repite la misma interacción y compara el tiempo de commit del Ranked chart. Si no mejora, revierte: una optimización que no se mide es una optimización que no existe.
Profilar en producción

El Profiler solo funciona en la build de desarrollo, que es más lenta y no refleja los tiempos reales. Para medir el rendimiento como lo vive el usuario, compila con source maps y sirve la build: 

# vite.config.js: activa source maps de producción
# build: { sourcemap: true }

pnpm build
pnpm preview

6 · Errores habituales

Error 1: sacar conclusiones de la build de desarrollo

✘ Incorrecto 
# "La app tarda 400 ms por clic" medido en desarrollo con StrictMode.
pnpm dev
✔ Correcto 
# Mide el rendimiento real de producción (con source maps para leer el árbol).
pnpm build
pnpm preview

Error 2: mirar solo el tiempo de render

✘ Incorrecto 
// "El render es rápido, así que la app es rápida" → se ignora que el commit
// tarda mucho porque se toca un DOM enorme.
✔ Correcto 
// Interpreta SIEMPRE render + commit. Un render rápido que produce un DOM
// gigante sigue siendo lento: ahí la solución es trocear/virtualizar, no memo.

Error 3: optimizar sin causa identificada

✘ Incorrecto 
// "No sé por qué va lento, así que envuelvo todo en memo."
export default memo(Componente1);
export const Dos = memo(Componente2);
export const Tres = memo(Componente3);
✔ Correcto 
// Primero graba y lee "Why did this render?". Después elige la técnica:
// memo (props) · useMemo (cálculo) · colocar el estado · code splitting.

7 · Ejercicio guiado

Vas a recorrer el ciclo completo de optimización guiado por datos.

  1. Arranca la app del ejemplo mínimo en pnpm dev y abre React DevTools → Profiler.
  2. Activa "Highlight updates" y pulsa el botón: observa cómo se ilumina el componente completo en cada clic.
  3. Graba 5 clics, detén y localiza App en el Ranked chart. Anota su tiempo en el commit más lento.
  4. Aplica useMemo al cálculo calcular(items) con dependencia [items].
  5. Vuelve a grabar los mismos 5 clics y compara el tiempo. Documenta el antes y el después.
  6. Añade performance.mark. Mide el cálculo con el User Timing API y compruébalo en la pestaña Performance de Chrome. 
    function calcularMedido(items) {
  performance.mark("calculo:inicio");
  let total = 0;
  for (let i = 0; i < 3_000_000; i++) total += items.length * 0.0001;
  performance.mark("calculo:fin");
  // Crea una medida entre las dos marcas, visible en el panel Performance.
  performance.measure("calculo", "calculo:inicio", "calculo:fin");
  return total;
}

8 · Reto

🎯 Un protocolo de medición reproducible

Diseña un protocolo que cualquier persona del equipo pueda repetir para comparar versiones de la app:

  1. Guion fijo: define una secuencia exacta (por ejemplo: escribir "camiseta", borrar, filtrar por categoría) y grábala con el Profiler.
  2. Métricas extraídas: de cada grabación, anota el commit más lento, el nº de commits y el componente dominante del Ranked chart.
  3. Automatización con el User Timing API: instrumenta la app con performance.mark/measure en los puntos clave y vuelca los resultados a un JSON exportable.
  4. Comparador: escribe un pequeño script (Node, con pnpm) que reciba dos JSON y muestre la diferencia porcentual por métrica.

Pista: el panel Performance de Chrome expone las medidas de User Timing; puedes exportarlas y quedarte solo con las que instrumentes. La clave no es la herramienta, sino que el protocolo sea repetible.

9 · Resumen

  • Components inspecciona el árbol, props y hooks; Profiler mide commits.
  • Usa el Ranked chart para encontrar el componente dominante y el flamegraph para el detalle.
  • "Why did this render?" te dice si la causa son props, estado, contexto o el padre.
  • Highlight updates muestra los re-renders en vivo y ayuda a detectarlos a simple vista.
  • Mide en la build de producción con source maps; desarrollo no refleja tiempos reales.
  • Ciclo completo: grabar → identificar → optimizar → volver a medir.

10 · Preguntas frecuentes

¿Por qué mi app no aparece en React DevTools?

Comprueba que estás en una página que usa React (y en modo desarrollo o con la extensión habilitada para archivos locales) y que la extensión está activa. También ayuda usar la build de desarrollo, no una de producción minificada sin source maps.

¿Qué diferencia hay entre "render time" y "commit time"?

Render time es lo que tardaron tus funciones de componente; commit time, lo que tardó React en aplicar los cambios al DOM. Optimizar el render (con memo/useMemo) no ayuda si el cuello de botella está en el commit (demasiados nodos en el DOM).

¿El Profiler funciona con React 19?

Sí. React DevTools da soporte a React 19 y, además, muestra el badge "Memo ✨" en los componentes optimizados por el React Compiler, lo que te permite verificar su efecto sin escribir nada a mano.

¿Puedo dejar el Profiler en producción?

El Profiler siempre está disponible en desarrollo. Para medir en producción, mide sobre la build real con source maps y, si necesitas instrumentación permanente, usa el User Timing API (performance.mark/measure) en lugar del Profiler interactivo.

¿Cuánto tiempo debo grabar?

Lo mínimo para reproducir el problema: una interacción concreta, unos pocos segundos. Grabaciones largas llenan el gráfico de commits y dificultan comparar antes y después.
