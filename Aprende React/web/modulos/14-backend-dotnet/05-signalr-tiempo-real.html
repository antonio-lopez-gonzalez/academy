SignalR: WebSockets en .NET

Módulo 14 · Backend con .NET 8 🕐 45 minutos

1 · Introducción

TaskFlow es un tablero colaborativo: si dos personas trabajan en el mismo proyecto y una mueve una tarjeta, la otra debería verla moverse sin recargar. Hasta ahora nuestro modelo era petición → respuesta: el cliente pregunta y el servidor contesta. Pero el servidor no puede iniciar una conversación por HTTP: no hay forma de que diga «oye, han creado una tarea» por sorpresa.

SignalR resuelve justo eso. Es una biblioteca de ASP.NET Core que abstrae el tiempo real: mantiene una conexión permanente con cada cliente y permite que el servidor envíe mensajes cuando ocurre algo. Y lo hace sin que tengas que elegir entre WebSockets, Server-Sent Events o long polling: SignalR elige por ti el mejor transporte disponible y degrada con gracia si el entorno no soporta WebSockets.

¿Por qué existe esta lección? Porque el Módulo 13 (lección «WebSockets: tiempo real») usa exactamente este hub desde React. Si entiendes el otro lado de la conexión, sabrás por qué el cliente se une a «grupos», por qué el token viaja en la query string y por qué a veces, en desarrollo, los mensajes «no llegan». Además, dominar SignalR te servirá para notificaciones, chats, dashboards en vivo y progreso de tareas largas.

Errores típicos:

  • Confundir SignalR con WebSockets «crudos»: SignalR es una capa sobre varios transportes.
  • Olvidar que los grupos no se persisten: al reconectar hay que volver a unirse.
  • No autenticar la conexión y dejar que cualquiera escuche un proyecto ajeno.
  • Desplegar varios servidores sin un backplane: cada instancia solo conoce a sus clientes.

2 · Teoría

El problema de HTTP, explicado

HTTP es sin estado y unidireccional: el cliente abre, pregunta, el servidor responde y se cierra. Para simular tiempo real existen tres estrategias, de mejor a peor:

TransporteCómo funcionaVentaja / inconveniente
WebSockets Canal bidireccional permanente sobre una sola conexión TCP El más eficiente; requiere que proxies y firewalls lo permitan
Server-Sent Events (SSE) El servidor mantiene abierto un flujo HTTP y va enviando Simple y pasa casi cualquier firewall; solo servidor → cliente
Long polling El cliente repite GETs que «esperan» hasta que hay novedad Funciona en todos lados; gasta peticiones y añade latencia

SignalR negocia: intenta WebSockets, si no puede pasa a SSE y, como último recurso, a long polling. Tú escribes la lógica una vez; el transporte es un detalle negociado.

   ¿WebSockets disponibles?  ── sí ──►  canal WebSocket (bidireccional)
            │ no
            ▼
   ¿SSE disponibles?         ── sí ──►  flujo EventSource (servidor→cliente)
            │ no
            ▼
   Long polling  ◄── siempre funciona, aunque es el menos eficiente

El modelo de SignalR: Hubs y Grupos

El corazón de SignalR es el Hub: una clase tuya donde defines los métodos que los clientes pueden llamar y desde la que puedes enviar mensajes. Los clientes se agrupan por interés; TaskFlow usa un grupo por proyecto.

   Cliente React A ─┐
                    ├──►  TasksHub (servidor)  ──►  grupo "project-1"
   Cliente React B ─┘                                   ▲
                                                        │
   GET /api/projects/1/tasks  ──►  TasksController ──────┘
                                     (IHubContext envía al grupo)

Analogía: un grupo es una sala de videollamada. Cuando entras, te unes a la sala (empiezas a recibir todo lo que pasa ahí). Cuando sales o se cae la conexión, sales de la sala: para volver, tienes que volver a llamar a la puerta. SignalR no recuerda que ya estabas dentro; tu cliente debe volver a unirse tras cada reconexión.

Autenticación en SignalR: el caso especial del token

En HTTP, enviamos el token en la cabecera Authorization. Las conexiones WebSocket del navegador no permiten cabeceras personalizadas en el handshake. Por eso el cliente de SignalR pasa el token por query string (?access_token=…) y el servidor lo lee al validar la conexión. Es un detalle que confunde mucho: el mismo token, entregado de otra forma.

Seguridad: como el token viaja en la URL, debes servir SignalR siempre por HTTPS y no registrarlo en logs (las URLs se registran). En producción, el servidor de SignalR nunca debe aceptar conexiones anónimas si la información es privada. En esta lección exigimos autenticación y comprobamos el acceso al proyecto al unirse al grupo.

Escalado horizontal: el backplane

Con un solo servidor, los grupos viven en su memoria. Si mañana despliegas tres instancias para aguantar más carga, cada una solo conoce a sus clientes: un mensaje enviado desde la instancia 1 no llega a los conectados a la 2. La solución es un backplane: un bus (Redis, Azure SignalR) que reenvía los mensajes entre instancias.

   Sin backplane                          Con backplane (Redis)
   ┌────────┐  ┌────────┐                 ┌────────┐  ┌────────┐
   │ API 1  │  │ API 2  │                 │ API 1  │  │ API 2  │
   │ A, B   │  │ C, D   │                 └───┬────┘  └───┬────┘
   └────────┘  └────────┘                     │           │
   mensaje de API1 llega solo a A,B           └────► Redis ◄────┘
                                              reenvía a TODAS las instancias

No lo pondremos en marcha aquí (necesita Redis, tema del Módulo de Redis), pero debes saber que existe: la propia lección 7 del Módulo 13 ya menciona este límite. Con un contenedor de API en Docker, un solo proceso, no es un problema.

3 · Ejemplo mínimo

El hub más pequeño que existe: echo. Un cliente envía un mensaje y el servidor lo devuelve a todos los conectados.

TaskFlow.Api/Hubs/ChatHub.cs
using Microsoft.AspNetCore.SignalR;

namespace TaskFlow.Api.Hubs;

// Heredar de Hub da acceso a Clients, Groups y Context
public class ChatHub : Hub
{
    // Método que los clientes pueden invocar: connection.Send("SendMessage", "hola")
    public Task SendMessage(string user, string message)
    {
        // Clients.All envía a TODAS las conexiones conectadas a este hub
        return Clients.All.SendAsync("ReceiveMessage", user, message);
    }
}
TaskFlow.Api/Program.cs (fragmento)
// 1) Registra los servicios de SignalR en el contenedor
builder.Services.AddSignalR();

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

// 2) Publica el hub en una ruta. Los clientes se conectan a /hubs/chat
app.MapHub<ChatHub>("/hubs/chat");

app.MapControllers();

Cliente JavaScript, en pocas líneas:

web/signalr-demo.js
// @microsoft/signalr es el cliente oficial (pnpm add @microsoft/signalr)
import { HubConnectionBuilder, LogLevel } from '@microsoft/signalr';

const connection = new HubConnectionBuilder()
  .withUrl('https://localhost:5000/hubs/chat')   // la misma URL del MapHub
  .configureLogging(LogLevel.Information)
  .withAutomaticReconnect()                      // reintenta solo si se cae
  .build();

// El nombre 'ReceiveMessage' debe coincidir EXACTAMENTE con el del SendAsync
connection.on('ReceiveMessage', (user, message) => {
  console.log(`${user}: ${message}`);
});

await connection.start();              // abre la conexión (negocia transporte)
await connection.invoke('SendMessage', 'Ana', 'Hola TaskFlow');

Línea por línea:

  1. HubConnectionBuilder construye la conexión con la URL del hub. Es el equivalente al fetch, pero persistente.
  2. withAutomaticReconnect() reconecta con retroceso exponencial si la red falla. Sin esto, cualquier corte deja la conexión muerta en silencio.
  3. connection.on('ReceiveMessage', …) registra un handler para un evento del servidor. El nombre debe coincidir con el primer argumento de SendAsync.
  4. connection.invoke('SendMessage', …) llama a un método del hub. invoke espera respuesta; send no.

4 · Ejemplo real

El hub de TaskFlow: un grupo por proyecto, eventos con nombre claro y verificación de acceso al unirse. Este es el hub que consume el frontend del Módulo 13.

TaskFlow.Api/Hubs/TasksHub.cs
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.SignalR;
using TaskFlow.Infrastructure.Data;

namespace TaskFlow.Api.Hubs;

[Authorize]   // exige un token válido para conectar al hub
public class TasksHub : Hub
{
    private readonly TaskFlowDbContext _context;

    // Un hub se crea por invocación, así que puede recibir servicios por DI
    public TasksHub(TaskFlowDbContext context) => _context = context;

    // El cliente llama a JoinProject("1") al abrir un tablero
    public async Task JoinProject(string projectId)
    {
        // Leemos el usuario desde los claims de la CONEXIÓN (no de la petición)
        var userId = GetUserId();

        // Solo añadimos al grupo si el usuario puede ver ese proyecto.
        // Sin esta comprobación, cualquiera escucharía cualquier tablero.
        var canAccess = await _context.Projects.AnyAsync(p =>
            p.Id.ToString() == projectId &&
            (p.OwnerId == userId || p.Members.Any(m => m.UserId == userId)));

        if (!canAccess)
        {
            // Abortar la conexión es la forma de decir "no puedes escuchar esto"
            Context.Abort();
            return;
        }

        await Groups.AddToGroupAsync(Context.ConnectionId, projectId);
    }

    // El cliente llama a LeaveProject al salir del tablero
    public Task LeaveProject(string projectId) =>
        Groups.RemoveFromGroupAsync(Context.ConnectionId, projectId);

    // Cuando una conexión se cierra, SignalR la saca de sus grupos automáticamente.
    // Sobrescribimos para poder registrar el evento si quisiéramos.
    public override Task OnDisconnectedAsync(Exception? exception) =>
        base.OnDisconnectedAsync(exception);

    // Extrae el Id del usuario del claim "sub" de la conexión
    private Guid GetUserId() =>
        Guid.Parse(Context.User!.FindFirst(JwtRegisteredClaimNames.Sub)!.Value);
}

La comprobación de acceso es la clave de la seguridad. El [Authorize] garantiza que alguien autenticado se conecta; la comprobación en JoinProject garantiza que ese alguien puede ver ese proyecto. Sin lo segundo, cualquier usuario con cuenta escucharía todos los tableros.

Registrar SignalR con JWT desde la query string

Como el navegador no puede enviar la cabecera Authorization en el handshake del WebSocket, configuramos SignalR para leer el token de access_token:

TaskFlow.Api/Program.cs (fragmento)
using Microsoft.AspNetCore.Authentication.JwtBearer;
using TaskFlow.Api.Hubs;

builder.Services.AddSignalR();

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters { /* … lección 3 … */ };

        // Conexiones SignalR: el token llega por query string, no por cabecera
        options.Events = new JwtBearerEvents
        {
            OnMessageReceived = context =>
            {
                var accessToken = context.Request.Query["access_token"];
                var path = context.HttpContext.Request.Path;

                // Solo para las rutas de hubs: no aceptamos token en query para el resto
                if (!string.IsNullOrEmpty(accessToken) && path.StartsWithSegments("/hubs"))
                    context.Token = accessToken;
            }
        };
    });

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.MapHub<TasksHub>("/hubs/tasks");   // ruta del hub de TaskFlow
app.MapControllers();
app.Run();

Notificar desde el controlador

El hub no es la única fuente de eventos: cuando un controlador crea o mueve una tarea, avisa al grupo. Para eso inyectamos IHubContext<TasksHub>, que permite enviar sin formar parte de una conexión.

TaskFlow.Api/Controllers/TasksController.cs (fragmento)
using Microsoft.AspNetCore.SignalR;
using TaskFlow.Api.Hubs;

public class TasksController : ControllerBase
{
    private readonly TaskFlowDbContext _context;
    private readonly IHubContext<TasksHub> _hub;

    public TasksController(TaskFlowDbContext context, IHubContext<TasksHub> hub)
    {
        _context = context;
        _hub = hub;
    }

    [HttpPost]
    public async Task<ActionResult<TaskItem>> Create(Guid projectId, CreateTaskDto dto)
    {
        if (!await CanAccessProjectAsync(projectId)) return NotFound();

        var task = new TaskItem { ProjectId = projectId, Title = dto.Title, /* … */ };
        _context.Tasks.Add(task);
        await _context.SaveChangesAsync();

        // Avisamos al grupo del proyecto: los clientes actualizan su estado sin recargar.
        // El nombre del evento ("TaskCreated") es el que escuchará React con connection.on(...)
        await _hub.Clients
            .Group(projectId.ToString())
            .SendAsync("TaskCreated", task);

        return CreatedAtAction(nameof(GetByProject), new { projectId }, task);
    }

    [HttpPatch("{taskId:guid}/status")]
    public async Task<IActionResult> UpdateStatus(Guid projectId, Guid taskId, UpdateTaskStatusDto dto)
    {
        // … cargar la tarea y cambiar el estado …

        // Notifica el movimiento para que el tablero se actualice en vivo
        await _hub.Clients
            .Group(projectId.ToString())
            .SendAsync("TaskMoved", new { id = taskId, status = dto.Status });

        return NoContent();
    }
}

Prefijo clr. Si el nombre del método del hub empieza por mayúscula, SignalR lo expone con el prefijo clr. por compatibilidad. En nuestro caso enviamos desde el servidor con nombres como TaskCreated, sin problema. La precaución aplica a los métodos que el cliente invoca en el hub: usa joinProject o mantén el nombre exacto con el que llamas desde React.

Suscribirse desde React

Así lo consume el tablero de TaskFlow (el detalle completo está en el Módulo 13):

proyecto-final/frontend/src/services/tasksHub.js
import { HubConnectionBuilder, HubConnectionState, LogLevel } from '@microsoft/signalr';

// Crea y arranca la conexión, pasando el token por query string
export async function createTasksHub(projectId, token) {
  const connection = new HubConnectionBuilder()
    .withUrl(`/hubs/tasks?access_token=${token}`)
    .withAutomaticReconnect()
    .configureLogging(LogLevel.Warning)
    .build();

  // Un único handler por evento; el callback lo pone quien consume el hook
  connection.on('TaskCreated', (task) => window.dispatchEvent(new CustomEvent('task-created', { detail: task })));
  connection.on('TaskMoved',   (data) => window.dispatchEvent(new CustomEvent('task-moved',   { detail: data })));
  connection.on('TaskDeleted', (id)   => window.dispatchEvent(new CustomEvent('task-deleted', { detail: id })));

  // ¡Importante! Tras CADA reconexión hay que volver a unirse al grupo
  connection.onreconnected(() => connection.invoke('JoinProject', String(projectId)));

  await connection.start();
  await connection.invoke('JoinProject', String(projectId));

  return connection;   // el hook lo cierra con connection.stop() al desmontar
}

El error nº 1 de SignalR en React: olvidar onreconnected. Todo parece ir bien… hasta que el portátil se duerme, vuelve la red y los mensajes dejan de llegar. La conexión se reconecta sola, pero los grupos se pierden con cada reconexión: hay que volver a invocar JoinProject. En el hook del Módulo 13 lo resolvemos también con el cleanup de useEffect, llamando a connection.stop().

6 · Errores habituales

Los mensajes «no llegan» tras reconectar

✗ Incorrecto
// ❌ Se une solo al abrir. Tras una reconexión, el grupo se perdió
await connection.start();
await connection.invoke('JoinProject', String(projectId));
// connection.onreconnected(() => …)  ← falta
✓ Correcto
// ✅ Vuelve a unirse CADA VEZ que se reconecta
connection.onreconnected(async () => {
  await connection.invoke('JoinProject', String(projectId));
});
await connection.start();
await connection.invoke('JoinProject', String(projectId));

No exigir autenticación en el hub

✗ Incorrecto
// ❌ Hub anónimo: cualquiera con la URL escucha el proyecto que quiera
public class TasksHub : Hub { /* sin [Authorize] ni comprobación */ }
✓ Correcto
// ✅ Exige token y valida el acceso al proyecto antes de unirse al grupo
[Authorize]
public class TasksHub : Hub { /* JoinProject comprueba canAccess */ }

Enviar a Clients.All cuando el mensaje es de un proyecto

✗ Incorrecto
// ❌ Todos los conectados reciben tareas de proyectos que no son suyos
await _hub.Clients.All.SendAsync("TaskCreated", task);
✓ Correcto
// ✅ Solo el grupo del proyecto afectado
await _hub.Clients.Group(projectId.ToString()).SendAsync("TaskCreated", task);

Usar invoke cuando no esperas respuesta

✗ Incorrecto
// ❌ invoke espera respuesta del servidor: si el método no devuelve nada,
// es trabajo innecesario y puede quedar pendiente
await connection.invoke('SendMessage', user, text);
✓ Correcto
// ✅ send no espera respuesta: ideal para notificaciones de ida
await connection.send('SendMessage', user, text);

Objetivo: añadir el evento TaskDeleted —cuando se borra una tarea, el tablero de todos los miembros la quita sin recargar— y probarlo con dos conexiones.

  1. Paso 1 — registra SignalR y publica el hub.

    builder.Services.AddSignalR();
// …
app.MapHub<TasksHub>("/hubs/tasks");
  2. Paso 2 — crea el hub. Copia TasksHub del ejemplo real, con [Authorize], JoinProject con comprobación de acceso y LeaveProject.
  3. Paso 3 — emite TaskDeleted desde el controlador.
    TaskFlow.Api/Controllers/TasksController.cs (fragmento)
    [HttpDelete("{taskId:guid}")]
public async Task<IActionResult> Delete(Guid projectId, Guid taskId)
{
    if (!await CanAccessProjectAsync(projectId)) return NotFound();

    var task = await _context.Tasks
        .FirstOrDefaultAsync(t => t.Id == taskId && t.ProjectId == projectId);
    if (task is null) return NotFound();

    _context.Tasks.Remove(task);
    await _context.SaveChangesAsync();

    // Notifica al grupo SOLO el Id: el cliente quita la tarjeta de su estado
    await _hub.Clients
        .Group(projectId.ToString())
        .SendAsync("TaskDeleted", taskId);

    return NoContent();
}

8 · Reto

🎯 Presencia en vivo y hub tipado

Dos mejoras profesionales sobre el hub actual:

  1. Añade una lista de usuarios conectados por proyecto: cuando alguien entra, el grupo recibe UserJoined con su nombre; cuando sale, UserLeft. El tablero mostrará «Ana y Luis están aquí».
  2. Convierte TasksHub en un hub tipado (Hub<ITasksClient>) para que los nombres de evento se validen en compilación y no puedas equivocarte al escribirlos.

Pista: para la presencia, mantén un diccionario en memoria ConcurrentDictionary<string projectId, HashSet> de conexiones (o de usuarios). Recuerda limpiarlo en OnDisconnectedAsync, que se dispara también cuando la red se cae. Para el hub tipado, define public interface ITasksClient { Task TaskCreated(TaskItem task); Task TaskMoved(object data); Task TaskDeleted(Guid id); } y hereda de Hub<ITasksClient>: entonces Clients.Group(id).TaskCreated(task) se comprueba al compilar. Ojo: la presencia por conexión se pierde al reconectar, así que el cliente debe re-unirse y re-anunciarse.

9 · Resumen

  • SignalR abstrae el tiempo real: negocia WebSockets → SSE → long polling automáticamente.
  • El Hub define los métodos; los grupos organizan las conexiones por interés (un grupo por proyecto).
  • IHubContext<THub> permite enviar mensajes a un grupo desde un controlador.
  • La autenticación viaja por query string (?access_token=), configurada en OnMessageReceived, porque el handshake WebSocket no admite cabeceras.
  • Los grupos se pierden al reconectar: vuelve a unirte en onreconnected.
  • Verifica el acceso al proyecto antes de AddToGroupAsync; un grupo mal protegido filtra datos.
  • Para escalar en horizontal hace falta un backplane (Redis / Azure SignalR).

10 · Preguntas frecuentes

¿SignalR es lo mismo que WebSockets?

No. WebSockets es un transporte (un protocolo de canal bidireccional); SignalR es un framework de aplicación que usa WebSockets cuando puede y otros transportes cuando no. SignalR te da además hubs, grupos, invocación de métodos remotos con nombres, reconexión automática y envío tipado. Es un nivel de abstracción por encima.

¿Por qué mi conexión recibe 401 aunque tengo un token válido?

Casi siempre porque el token no está llegando al servidor. Recuerda que el navegador no permite cabeceras en el handshake del WebSocket: el token debe ir en la query string (?access_token=…) y el servidor debe leerlo en OnMessageReceived. Comprueba también que la ruta empieza por /hubs (nuestra condición) y que el token no está caducado — con una caducidad de 7 días ya habrás visto más de un 401 por expiración en desarrollo.

¿Cuántas conexiones SignalR aguanta un servidor?

Depende mucho de la máquina y del tráfico, pero una instancia modesta maneja fácilmente decenas de miles de conexiones inactivas (WebSockets ociosos son baratos). El cuello de botella no suelen ser las conexiones, sino la frecuencia de mensajes y el trabajo por mensaje. Si necesitas más capacidad, escala en horizontal con backplane, o usa un servicio gestionado como Azure SignalR Service, pensado precisamente para esto.

¿Puedo enviar mensajes a un solo usuario?

Sí, de varias formas. Si mantienes el mapeo usuario→conexiones, con Clients.Clients(connectionIds). Si usas IUserIdProvider (que por defecto toma el claim NameIdentifier), con Clients.User(userId). Es útil para notificaciones privadas («te han asignado esta tarea»), mientras que los grupos sirven para lo compartido («el tablero del proyecto ha cambiado»).

¿Qué pasa con SignalR detrás de un proxy o balanceador?

Hay que habilitar el WebSocket upgrade y no cortar conexiones largas por inactividad. Dos ajustes imprescindibles: en nginx, las cabeceras Upgrade y Connection y un proxy_read_timeout amplio; en el balanceador, sticky sessions o un backplane. Si el transporte escala a SSE o long polling, la afinidad de sesión pasa a ser obligatoria. En la lección 7 dejaremos el nginx del frontend preparado, y en la 8 damos el checklist de despliegue.
