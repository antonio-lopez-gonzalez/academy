Setup y arquitectura limpia

Módulo 14 · Backend con .NET 8 🕐 45 minutos

1 · Introducción

Hasta ahora todo nuestro TaskFlow vivía en el navegador: estado en memoria, localStorage y, en el módulo 9, una API pública que no controlábamos. Eso está bien para aprender React, pero una aplicación real necesita sus propios datos: usuarios, proyectos, tareas, comentarios… que sobrevivan a un recargado de página y sean compartidos entre personas distintas.

En este módulo construimos el backend de TaskFlow: una API REST en .NET 8 con Entity Framework Core, PostgreSQL, autenticación JWT, tiempo real con SignalR y despliegue con Docker. No es un módulo de React, pero sí es un módulo del curso de React: entenderás exactamente qué espera el frontend del servidor y cómo se comunican.

Esta primera lección responde a una sola pregunta: ¿cómo organizamos el código para que no sea un caos dentro de tres meses? La respuesta se llama arquitectura en capas (una forma concreta de Clean Architecture aplicada a una API ASP.NET Core).

¿Por qué existe esta lección? Porque el 90 % de los proyectos .NET que se vuelven inmantenibles no lo hacen por bugs, sino por estructura. Si metes consultas de base de datos, reglas de negocio y formateo de respuestas en el mismo controlador, el primer cambio de requisito te obligará a tocar quince sitios. Empezar con capas claras cuesta una hora hoy y ahorra semanas mañana.

Errores típicos que esta lección evita:

  • Poner la lógica de negocio en el controlador «porque es rápido».
  • Hacer que la capa de dominio dependa de Entity Framework.
  • Guardar secretos (la clave JWT, la contraseña de PostgreSQL) dentro de appsettings.json versionado en Git.
  • Crear un único proyecto WebAPI con todo dentro y «ya separaremos luego».
  • Confundir entidades de base de datos con los objetos que devuelve la API (DTOs).

2 · Teoría

¿Qué es la arquitectura en capas?

Es dividir el código según qué responsabilidad tiene, no según qué tecnología usa. Cada capa solo puede hablar con la capa que tiene inmediatamente debajo (o con una abstracción). Esto se conoce como la regla de la dependencia: las dependencias apuntan siempre hacia dentro, hacia el núcleo del negocio.

Analogía: piensa en un restaurante. El camarero (la API) solo habla con los clientes y toma nota; no cocina. La cocina (Infraestructura) tiene las herramientas: la nevera, los fogones, la despensa. Y la receta (Core) es lo único que no cambia si mañana el restaurante compra fogones nuevos o cambia de proveedor. Si el camarero cocinase y además llevara la contabilidad, en cuanto hubiera diez mesas el restaurante se caería.

Las tres capas de TaskFlow

Fíjate en la dirección de las flechas: Api → Infrastructure → Core. Nunca al revés. Esa restricción es la que hace que Core sea estable: aunque cambies PostgreSQL por otro motor o añadas caché, las entidades y reglas de negocio no se tocan.

¿Por qué tres proyectos y no tres carpetas?

Podríamos crear TaskFlow.Api/Core/ y TaskFlow.Api/Infrastructure/ como simples carpetas. Funcionaría, pero entonces nada impide que una clase de Core haga using Microsoft.EntityFrameworkCore. El compilador no se queja. Al separarlas en proyectos independientes con referencias explícitas, una referencia prohibida se convierte en un error de compilación. La arquitectura deja de ser un acuerdo verbal y pasa a ser una regla que la herramienta hace cumplir.

Ventaja extra: proyectar en tres ensamblados hace la suite de tests más rápida y enfocada. Puedes probar la lógica de Core sin levantar ASP.NET ni una base de datos, porque Core no sabe que existen.

DTOs: no devuelvas tus entidades

Aunque el tema se profundiza en la lección 6, aquí colocamos la idea: una entidad (User) es cómo guardamos los datos; un DTO (UserDto) es cómo viajan hacia el cliente. Nunca devuelvas una entidad directamente: tarde o temprano expondrás el PasswordHash o romperás el contrato al añadir una columna. Los DTOs viven en Core para que Api e Infrastructure los compartan sin depender entre sí.

El pipeline de ASP.NET Core, en una frase

Cuando llega una petición, ASP.NET Core la pasa por una tubería de middleware (autenticación, autorización, enrutado, tu controlador…). Cada middleware decide si responde o la deja pasar. En el módulo verás dónde encajan el error handler (lección 6), JWT (lección 3) y SignalR (lección 5): todos son piezas de esa tubería.

  HTTP  ──►  [ UseMiddleware(Errores) ]
               └─► [ UseAuthentication ]   ← ¿lleva token válido?
                     └─► [ UseAuthorization ]  ← ¿puede entrar aquí?
                           └─► [ MapControllers ] ──► Controlador
                                                      │
                                                      ▼
                                                   Respuesta

3 · Ejemplo mínimo

Antes de la arquitectura, lo más pequeño que existe: una API de una línea. Compruébala con dotnet --version (debe imprimir 8.x):

Terminal
# Crea una carpeta, entra y genera un proyecto Web API mínimo
dotnet new web -o HelloTaskFlow
cd HelloTaskFlow
dotnet run
HelloTaskFlow/Program.cs
// El objeto builder lee la configuración (appsettings, variables de entorno…)
var builder = WebApplication.CreateBuilder(args);

// Construimos la aplicación con todo lo que se ha registrado en el builder
var app = builder.Build();

// MapGet registra una ruta: GET /  ->  responde con texto plano
// La lambda devuelve un string; ASP.NET lo serializa como 200 text/plain
app.MapGet("/", () => "TaskFlow API");

// Arranca el servidor Kestrel (por defecto en http://localhost:5000)
app.Run();

Línea por línea:

  1. WebApplication.CreateBuilder(args): prepara la inyección de dependencias, la configuración y el logging. Todo lo que registres después estará disponible para los controladores.
  2. builder.Build(): «congela» el contenedor de servicios y crea la app. A partir de aquí, ya no se registran servicios: se configura el pipeline.
  3. app.MapGet("/", …): define un endpoint. La notación () => "texto" es una lambda de C#: función sin parámetros que devuelve un string.
  4. app.Run(): bloquea y deja el servidor escuchando. Nunca se cierra por sí solo.

Abre http://localhost:5000 y verás el texto. Ese es el esqueleto sobre el que crecerá TaskFlow.

4 · Ejemplo real

Ahora sí: montamos la solución real de TaskFlow con tres proyectos y sus referencias. Esta secuencia es la base para todas las lecciones del módulo.

Terminal — crear la solución
# Una solucion (.sln) agrupa varios proyectos; es la unidad que abrimos en el IDE
dotnet new sln -n TaskFlow

# webapi: lleva los controladores y Program.cs. classlib: biblioteca sin plantilla HTTP
dotnet new webapi -n TaskFlow.Api -o TaskFlow.Api
dotnet new classlib -n TaskFlow.Core -o TaskFlow.Core
dotnet new classlib -n TaskFlow.Infrastructure -o TaskFlow.Infrastructure

# Añadimos los tres proyectos a la solucion
dotnet sln add TaskFlow.Api/TaskFlow.Api.csproj
dotnet sln add TaskFlow.Core/TaskFlow.Core.csproj
dotnet sln add TaskFlow.Infrastructure/TaskFlow.Infrastructure.csproj

# Referencias: Api -> Core e Infrastructure ; Infrastructure -> Core
dotnet add TaskFlow.Api reference TaskFlow.Core TaskFlow.Infrastructure
dotnet add TaskFlow.Infrastructure reference TaskFlow.Core

Observa el orden. Core no referencia a nadie: por eso es la capa estable. Si algún día necesitas que Core referencie Infrastructure, es señal de que el diseño se te está cayendo y conviene repensarlo antes de romper la regla.

La estructura de ficheros tras estos comandos:

Instalamos los paquetes NuGet que usaremos a lo largo del módulo. Los fijamos a la línea 8.0.x para que coincida con el runtime .NET 8:

Terminal — paquetes NuGet
# Infrastructure: proveedor de PostgreSQL, herramientas de diseño de EF y BCrypt
dotnet add TaskFlow.Infrastructure package Npgsql.EntityFrameworkCore.PostgreSQL --version 8.0.11
dotnet add TaskFlow.Infrastructure package Microsoft.EntityFrameworkCore.Design --version 8.0.15
dotnet add TaskFlow.Infrastructure package BCrypt.Net-Next --version 4.0.3

# Api: middleware de validación de JWT y Swagger para documentar la API
dotnet add TaskFlow.Api package Microsoft.AspNetCore.Authentication.JwtBearer --version 8.0.15
dotnet add TaskFlow.Api package Swashbuckle.AspNetCore --version 6.6.2

El Program.cs inicial: controladores, Swagger y el esqueleto del pipeline. Fíjate en que todo se hace en el builder o antes de app.Run().

TaskFlow.Api/Program.cs
// builder: recoge configuración, logging e inyección de dependencias
var builder = WebApplication.CreateBuilder(args);

// Habilita los controladores basados en atributos ([ApiController], [HttpGet]…)
builder.Services.AddControllers();

// Genera la descripción OpenAPI que Swagger UI muestra en /swagger
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();

// Swagger solo en desarrollo: no queremos exponer la superficie de la API en producción
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();      // sirve el documento JSON de OpenAPI
    app.UseSwaggerUI();    // sirve la interfaz web interactiva
}

app.UseHttpsRedirection(); // redirige http:// a https:// automáticamente
app.UseAuthorization();    // aplica las reglas de [Authorize] (sin auth todavía)

app.MapControllers();      // conecta el enrutado con los controladores

app.Run();

Nota sobre HTTPS y Docker: en local UseHttpsRedirection() es cómodo, pero dentro de un contenedor sin certificados provocará redirecciones raras. En la lección 7 lo condicionaremos al entorno.

Arranca y comprueba el contador de endpoints:

Terminal
dotnet run --project TaskFlow.Api
# Abre http://localhost:5000/swagger : ahí aparecerán los endpoints que
# vayas añadiendo en esta carpeta. De momento, la lista está vacía.

6 · Errores habituales

Hacer todo en el controlador

✗ Incorrecto
// ❌ El controlador habla HTTP, consulta la BD, valida y formatea.
// Imposible de testear sin base de datos y con quince responsabilidades.
[HttpGet]
public async Task<IActionResult> Get(Guid id)
{
    var conn = new NpgsqlConnection("Host=localhost;…");  // acceso a datos crudo
    await conn.OpenAsync();
    var cmd = new NpgsqlCommand("SELECT * FROM projects WHERE id=@id", conn);
    cmd.Parameters.AddWithValue("id", id);
    var reader = await cmd.ExecuteReaderAsync();
    if (!await reader.ReadAsync()) return NotFound();
    return Ok(new { Name = reader.GetString(1) }); // formateo a mano
}
✓ Correcto
// ✅ El controlador delega: recibe la petición y usa el DbContext (Infra).
// La validación y el mapeo viven en sus capas (lecciones 4 y 6).
[HttpGet("{id:guid}")]
public async Task<IActionResult> GetById(Guid id)
{
    var project = await _context.Projects.FindAsync(id);
    return project is null ? NotFound() : Ok(project);
}

Invertir la regla de dependencia

✗ Incorrecto
# ❌ Core depende de Infrastructure: el núcleo del negocio
# queda atado al motor de base de datos y a ASP.NET
dotnet add TaskFlow.Core reference TaskFlow.Infrastructure
✓ Correcto
# ✅ Las dependencias apuntan hacia dentro: Api -> Infrastructure -> Core
dotnet add TaskFlow.Infrastructure reference TaskFlow.Core

Si Core necesita algo de fuera (por ejemplo «enviar un email»), se define una interfaz en Core y la implementación concreta vive en Infrastructure. Eso es inversión de dependencias.

Guardar secretos en el repositorio

✗ Incorrecto
{
  "ConnectionStrings": {
    "Default": "Host=db.prod;Username=admin;Password=SuperSecreta123"
  },
  "Jwt": { "Key": "clave-real-de-produccion-que-no-debe-verse" }
}
✓ Correcto
{
  "ConnectionStrings": {
    "Default": "Host=localhost;Port=5432;Database=taskflow;Username=taskflow;Password=dev-only"
  },
  "Jwt": { "Key": "[usa user-secrets o una variable de entorno]" }
}

En desarrollo los valores reales llegan de user-secrets; en producción, de variables de entorno (Jwt__Key, ConnectionStrings__Default). El appsettings.json versionado solo contiene valores inocuos.

Devolver la entidad tal cual

✗ Incorrecto
// ❌ Expone el hash de la contraseña y cualquier columna futura
return Ok(user); // user incluye PasswordHash
✓ Correcto
// ✅ Proyecta a un DTO con SOLO los campos públicos
return Ok(new { user.Id, user.Name, user.Email });

7 · Ejercicio guiado

Objetivo: crear desde cero la solución TaskFlow con sus tres capas, sus referencias y un endpoint de salud que responde { "status": "ok" }. Al terminar tendrás el andamio exacto de todo el módulo.

  1. Paso 1 — solución y proyectos. 
    dotnet new sln -n TaskFlow
dotnet new webapi -n TaskFlow.Api -o TaskFlow.Api
dotnet new classlib -n TaskFlow.Core -o TaskFlow.Core
dotnet new classlib -n TaskFlow.Infrastructure -o TaskFlow.Infrastructure
dotnet sln add TaskFlow.Api/TaskFlow.Api.csproj TaskFlow.Core/TaskFlow.Core.csproj TaskFlow.Infrastructure/TaskFlow.Infrastructure.csproj
  2. Paso 2 — referencias correctas. Api usa Core e Infrastructure; Infrastructure usa Core; Core no usa nada. 
    dotnet add TaskFlow.Api reference TaskFlow.Core TaskFlow.Infrastructure
dotnet add TaskFlow.Infrastructure reference TaskFlow.Core
  3. Paso 3 — borra las plantillas vacías. Class1.cs de Core e Infrastructure solo estorba. 
    rm TaskFlow.Core/Class1.cs
rm TaskFlow.Infrastructure/Class1.cs
  4. Paso 4 — un DTO en Core. Crea TaskFlow.Core/DTOs/HealthDto.cs. Los DTOs van en Core porque Api e Infrastructure los comparten.
    TaskFlow.Core/DTOs/HealthDto.cs
    namespace TaskFlow.Core.DTOs;

// record: tipo inmutable ideal para respuestas; el compilador genera el constructor
public record HealthDto(string Status, string Service, DateTime Timestamp);
  5. Paso 5 — un controlador en Api. Crea TaskFlow.Api/Controllers/HealthController.cs.
    TaskFlow.Api/Controllers/HealthController.cs
    using Microsoft.AspNetCore.Mvc;
using TaskFlow.Core.DTOs;

namespace TaskFlow.Api.Controllers;

// [ApiController] activa validación automática y enlaces de ruta por convención
// [Route] fija el prefijo; [controller] se sustituye por "health"
[ApiController]
[Route("api/[controller]")]
public class HealthController : ControllerBase
{
    // GET /api/health  ->  200 con el estado del servicio
    [HttpGet]
    public ActionResult<HealthDto> Get() =>
        new HealthDto("ok", "TaskFlow.Api", DateTime.UtcNow);
}
  6. Paso 6 — verificación. Arranca y llama al endpoint. Debes recibir un JSON con "status":"ok". 
    dotnet run --project TaskFlow.Api
# En otra terminal:
curl http://localhost:5000/api/health
# {"status":"ok","service":"TaskFlow.Api","timestamp":"2026-…Z"}

Comprueba la regla de dependencia: intenta añadir using Microsoft.EntityFrameworkCore; en una clase de Core. Verás que el proyecto ni siquiera tiene la referencia: el compilador te lo impide. Eso es exactamente lo que buscábamos con los tres proyectos.

8 · Reto

🎯 Añade una capa de contratos y un proyecto de tests

Dos objetivos sobre la solución que acabas de crear:

  1. Crea en Core la interfaz IProjectRepository con los métodos GetByIdAsync y AddAsync, y una abstacción IClock con UtcNow. Ambas deben compilar sin referenciar EF Core.
  2. Añade un proyecto TaskFlow.Tests (plantilla xunit) que referencie solo Core y demuestre, con un test, que Core se puede probar sin ASP.NET ni base de datos.

Pista: con dotnet new xunit -n TaskFlow.Tests y dotnet sln add. Para el test, implementa una IClock falsa que devuelva una fecha fija y comprueba el valor. Si tu test necesita TaskFlow.Api o PostgreSQL para pasar, la separación de capas no está bien hecha: revisa las referencias.

9 · Resumen

  • TaskFlow se organiza en tres capas: Core (núcleo), Infrastructure (detalles) y Api (presentación).
  • La regla de la dependencia apunta siempre hacia dentro: Api → Infrastructure → Core.
  • Separar en proyectos y no en carpetas convierte la arquitectura en un error de compilación, no en una recomendación.
  • Los DTOs viven en Core; las entidades se mapean a tablas con EF Core (siguiente lección).
  • El Program.cs registra servicios en el builder y configura el pipeline de middleware tras Build().
  • Los secretos nunca viajan en appsettings.json: usa user-secrets en local y variables de entorno en producción.

10 · Preguntas frecuentes

¿Por qué el curso tiene un módulo de .NET si estoy aprendiendo React?

Porque TaskFlow es el proyecto final y necesita un backend real: guardar datos, autenticar usuarios y notificar cambios en vivo. Entender cómo se construye ese servidor te convierte en desarrollador full-stack y, sobre todo, te hace mejor en el frontend: sabrás por qué una API devuelve un 401, cómo se forma un token JWT o qué implica un include en el rendimiento de las peticiones que consumes desde React.

¿Es obligatorio .NET 8 o puedo usar otra versión?

El módulo está fijado a .NET 8 porque es la versión LTS vigente en el curso y porque los paquetes de EF Core y el proveedor de PostgreSQL que usamos se alinean con la línea 8.0.x. Puedes compilar con una SDK superior si respetas el TargetFramework del proyecto, pero no mezcles versiones de paquetes: si actualizas EF Core, actualiza también Npgsql.EntityFrameworkCore.PostgreSQL.

¿Merece la pena tanto andamio para un proyecto que estoy aprendiendo?

Sí, porque el coste de mover código después es mucho mayor que el de crear tres proyectos ahora. Dicho esto, evita el exceso contrario: no crees capas que no necesitas. Tres proyectos es el mínimo razonable para separar negocio, infraestructura y presentación. Si el día de mañana el proyecto crece, quizá añadas una capa de Application con casos de uso; hoy, no la necesitas.

¿Qué diferencia hay entre dotnet new web y dotnet new webapi?

web genera una aplicación mínima con endpoints minimal API y sin controladores: perfecta para un microservicio o una prueba. webapi incluye la infraestructura de controladores, Swagger y un ejemplo, que es lo que nos interesa para una API REST grande. En la lección 4 usaremos controladores, así que partimos de webapi.

¿Dónde guardo la clave JWT en desarrollo si no puedo usar appsettings.json?

Con user secrets: dotnet user-secrets init --project TaskFlow.Api y luego dotnet user-secrets set "Jwt:Key" "…". La configuración se guarda en tu perfil de usuario, fuera del repositorio, y ASP.NET Core la carga automáticamente en entorno Development. En la lección 3 la leeremos desde builder.Configuration["Jwt:Key"] igual que cualquier otro valor.
