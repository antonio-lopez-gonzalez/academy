Keys y reconciliación

Módulo 2 · Renderizado ⏱ 35 minutos

1 · Introducción

En la lección anterior apareció key={user.id} con la promesa de «la próxima lección la explica entera». Pues bien: esta es la lección más importante sobre cómo funciona React por dentro, y la que explica bugs que parecen magia negra («el input mantiene el texto del elemento que borré», «las animaciones se comportan raro al reordenar»…).

La key es el DNI de cada elemento de una lista: le dice a React qué elemento del árbol nuevo corresponde a cuál del árbol viejo durante la reconciliación (¿la recuerdas del Módulo 0?). Sin keys buenas, React adivina por posición — y a veces adivina catastróficamente mal.

Errores típicos: usar el índice del array como key sin entender cuándo explota, usar Math.random() como key, y creer que la key es una prop que el componente puede leer.

2 · Teoría

El problema: la reconciliación sin identidades

Imagina una lista con dos tareas y llega una nueva al principio:

ÁRBOL VIEJO ÁRBOL NUEVO ─────────── ─────────── li → "Comprar pan" li → "Estudiar React" ← NUEVA al principio li → "Pasear al perro" li → "Comprar pan" li → "Pasear al perro" SIN KEYS, React compara POR POSICIÓN: posición 0: "Comprar pan" → "Estudiar React" ✎ actualiza texto posición 1: "Pasear al perro"→ "Comprar pan" ✎ actualiza texto posición 2: — → "Pasear al perro" ✚ crea nodo Resultado: 3 operaciones DOM… ¡y cualquier ESTADO INTERNO (checkbox marcado, texto de un input) queda DESPLAZADO al elemento equivocado! CON KEYS ESTABLES: key=pan: "Comprar pan" sigue siendo "Comprar pan" → MOVER (sin tocar) key=perro: igual → MOVER key=react: nuevo → CREAR 1 nodo Resultado: 1 inserción, 0 actualizaciones, estado intacto ✔

La key permite a React responder la pregunta fundamental del diffing: «¿qué elemento del árbol nuevo ES el mismo que este del árbol viejo?». Con la respuesta correcta, React mueve nodos en lugar de destruirlos y recrearlos, y el estado interno de cada elemento viaja con él.

Por qué el índice del array es una trampa

key={index} parece funcionar… en demos. El problema: el índice describe la posición, no la identidad. Si la lista se reordena, filtra o crece por el principio, todas las identidades cambian de sitio y React empareja mal.

🪑 Analogía de las sillas numeradas

Imagina un teatro donde cada espectador tiene una entrada con su nombre (key estable): si alguien llega tarde y se sienta en primera fila, el resto no cambia de entrada. Ahora imagina que las entradas fueran «silla 1, silla 2…» (índice): al sentarse el nuevo en la silla 1, TODOS deben levantarse y cambiar de asiento — y además el abrigo que dejaste en tu silla ahora «pertenece» a otro.

¿Cuándo SÍ es aceptable el índice? Solo cuando se cumplen TODAS estas condiciones: la lista es estática (no se reordena, filtra ni edita), los elementos no tienen estado interno (inputs, animaciones) y no tienen id propio. Una lista de «features» fija de una landing, por ejemplo. En cuanto una condición falle: id único.

Qué hace una buena key

Candidata¿Vale?Por qué

Índice del array⚠ Solo listas estáticasDescribe posición, no identidad.

La key NO es una prop

Detalle que confunde a muchos: la key la consume React internamente y no llega al componente. Si tu UserRow necesita el id, debes pasarlo aparte: 

<UserRow key={user.id} id={user.id} user={user} />
//        ↑ React lo usa    ↑ el componente lo recibe como prop

Bonus avanzado: key para REINICIAR un componente

Las keys también sirven fuera de las listas, con un truco muy profesional: si cambias la key de un componente, React lo destruye y lo crea desde cero (pierde todo su estado interno). Es la forma elegante de «resetear» un formulario o un widget: 

// Al cambiar de usuario, el formulario se reinicia solo:
<EditUserForm key={selectedUser.id} user={selectedUser} />

Lo usaremos en el proyecto final. Guárdalo: «cambiar la key = nuevo componente».

3 · Ejemplo mínimo

✘ Sin key: warning y riesgo de bugs 
{tasks.map((task) => (
  <li>{task.title}</li>   // ⚠ "Each child in a list should have a unique key"
))}
✔ Con key estable 
{tasks.map((task) => (
  <li key={task.id}>{task.title}</li>   // ✔ id único y estable
))}

Línea por línea:

  1. key={task.id} — se coloca en el elemento RAÍZ que devuelve el map (aquí el <li>), no en sus hijos.
  2. Si el map devuelve un componente (<TaskItem … />), la key va en el componente, no dentro de él.
  3. La key debe ser única entre hermanos (dentro de ese map). Dos listas distintas pueden repetir keys sin problema.

4 · Ejemplo real: el desastre del índice, demostrado

Vamos a reproducir el bug clásico para que lo veas con tus ojos. Lista de jugadores con un input de «apodo» por fila (estado interno del DOM):

src/components/PlayerList.jsx
const initialPlayers = [
  { id: 101, name: "Nadia" },
  { id: 102, name: "Omar" },
  { id: 103, name: "Irene" },
];

export default function PlayerList() {
  const [players, setPlayers] = useState(initialPlayers);

  function addPlayer() {
    const nuevo = { id: crypto.randomUUID(), name: "Teo" };
    // Añadimos AL PRINCIPIO: el peor enemigo de key={index}
    setPlayers([nuevo, ...players]);
  }

  return (
    <div>
      <button onClick={addPlayer}>Añadir a Teo al principio</button>
      {players.map((player) => (
        <div key={player.id} className="player-row">
          <strong>{player.name}</strong>
          <input placeholder="Apodo…" />
        </div>
      ))}
    </div>
  );
}

El experimento:

  1. Escribe «Speedy» en el input de Nadia.
  2. Pulsa «Añadir a Teo al principio».
  3. Con key={player.id}: Nadia sigue teniendo «Speedy» en su input — su nodo se MOVIÓ con ella. ✔
  4. Cambia a key={index} y repite: el texto «Speedy» aparece ahora en la fila de Teo 😱. Como React emparejó por posición, el input de la posición 0 (antes de Nadia) ahora «es» de Teo. El estado quedó corrupto visualmente.

Este experimento de 2 minutos enseña más que 10 artículos. Hazlo: está en ejemplos/m02-renderizado.

5 · Buenas prácticas

HazEvitaPor qué
Ids de base de datos o de dominio como key Índice del array salvo listas 100 % estáticas El id identifica al DATO; el índice solo a la posición.
Generar ids al CREAR el dato (crypto.randomUUID()) Generar cualquier cosa aleatoria DURANTE el render La key debe ser estable entre renders; lo aleatorio en render destruye la identidad.
Key en la raíz de lo que devuelve el map Key en un hijo interno del elemento React solo mira las keys entre hermanos directos.
Pasar el id también como prop si el componente lo necesita Intentar leer props.key La key no llega al componente: es para React.
Usar key para reiniciar componentes cuando cambia el «sujeto» Resetear estado a mano con efectos complicados key={id} nuevo = componente nuevo limpio. Elegante y declarativo.

6 · Errores habituales

Error 1: key={Math.random()}

✘ Incorrecto 
{items.map((item) => <Row key={Math.random()} item={item} />)}
// Cada render genera keys NUEVAS → React destruye y recrea TODAS las filas.
// Síntomas: inputs que pierden el foco al teclear, animaciones rotas, lag.
✔ Correcto 
// El id se genera UNA VEZ, al crear el dato:
const newItem = { id: crypto.randomUUID(), ...datos };
{items.map((item) => <Row key={item.id} item={item} />)}

Error 2: key en el lugar equivocado

✘ Incorrecto 
// a) Key dentro del componente en lugar de en la lista:
function TaskItem({ task }) {
  return <li key={task.id}>{task.title}</li>;   // ✘ aquí no sirve
}
{tasks.map((t) => <TaskItem task={t} />)}          // ✘ aquí falta

// b) Key en un Fragment de sintaxis corta:
{tasks.map((t) => <><dt /><dd /></>)}             // ✘ <> no admite key
✔ Correcto 
{tasks.map((t) => <TaskItem key={t.id} task={t} />)}

{tasks.map((t) => (
  <Fragment key={t.id}><dt /><dd /></Fragment>   // ✔ sintaxis larga
))}

Error 3: keys duplicadas

Síntoma: warning «Encountered two children with the same key» y comportamiento errático al actualizar (React no sabe cuál es cuál).

Causa típica: usar key={item.name} con nombres repetidos, o concatenar dos listas que comparten ids. Solución: garantiza unicidad (id compuesto: {`blocked-${user.id}`} vs {`friend-${user.id}`}).

9 · Resumen

  • La key es la identidad de un elemento entre renders: permite a React mover en lugar de destruir/recreate.
  • Sin keys (o con índice), React empareja por posición → estado desplazado y operaciones DOM innecesarias.
  • Buena key: id de BD, única de dominio, o randomUUID() generado al crear el dato.
  • Índice: solo listas estáticas sin estado interno. Math.random() en el render: jamás.
  • La key no es una prop: no llega al componente.
  • Bonus: cambiar la key de un componente lo reinicia desde cero — truco profesional.

10 · Preguntas frecuentes

¿Las keys hacen la app más rápida?

Sí, en listas que cambian: con keys, React mueve nodos (barato) en lugar de actualizar contenido de todos o recrearlos (caro). Pero su propósito principal es la corrección (identidad y estado), la velocidad es consecuencia.

¿Qué pasa si dos datos tienen el mismo id (API mal diseñada)?

Tendrás keys duplicadas: warning y bugs de reconciliación. Solución temporal: key compuesta ({`${item.id}-${index}`}) mientras arreglan la API… y reporta el bug al backend, porque ids duplicados rompen mucho más que React.

¿Puedo ver las keys en las DevTools?

No aparecen en el DOM (no son atributos HTML), pero React DevTools (Components) muestra la key de cada hijo al seleccionar el padre. Útil para depurar listas.

¿Necesitan key los elementos que NO están en un map?

No: solo los hijos generados dinámicamente (map o arrays de elementos). Los hermanos escritos a mano en el JSX tienen posición estable, React los distingue solo.

¿La key tiene que ser un string?

Acepta strings y números (React los convierte internamente). Lo importante es que sea única entre hermanos y estable entre renders.
