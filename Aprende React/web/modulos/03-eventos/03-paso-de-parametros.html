Paso de parámetros a manejadores

Módulo 3 · Eventos ⏱ 25 minutos

1 · Introducción

Ya sabes pasar una función a onClick… pero ¿y si el manejador necesita datos? Tienes una lista de 30 productos con 30 botones «Eliminar»: cada botón debe saber QUÉ producto borrar. No puedes escribir 30 funciones.

La respuesta es una de las técnicas más usadas en React (y más confundidas al principio): envolver la llamada en una arrow function. Parece un detalle de sintaxis, pero detrás está uno de los conceptos más potentes de JavaScript: los closures. Entender esto bien es entender cómo respira React.

2 · Teoría

El problema: onClick espera una función SIN ejecutar

Recuerda la regla de oro: onClick={handleDelete} pasa la función; React la llamará cuando haya clic, pasándole el evento. Pero si escribes:

✘ Se ejecuta en el render 
<button onClick={handleDelete(product.id)}>Eliminar</button>
// handleDelete(product.id) se EJECUTA AHORA (al renderizar).
// onClick recibe el RESULTADO (undefined), no una función.

Necesitamos «congelar» la llamada hasta el clic. La solución: una arrow function que ENVUELVA la llamada:

✔ Se ejecuta solo al hacer clic 
<button onClick={() => handleDelete(product.id)}>Eliminar</button>
// onClick recibe una NUEVA función que, cuando React la llame
// (al hacer clic), ejecutará handleDelete(product.id)
📦 Analogía del paquete con instrucciones

handleDelete(product.id) es abrir el paquete ahora. () => handleDelete(product.id) es entregar el paquete cerrado con una nota: «ábreme cuando hagan clic». React recibe el paquete cerrado y lo abre en el momento justo — y cuando lo abre, dentro están las instrucciones con el id correcto.

El closure: por qué la arrow «recuerda» el id

Aquí está la magia de JavaScript que hace posible todo esto. Cuando creas una arrow function, ella captura las variables del ámbito donde nació y las recuerda para siempre, aunque se ejecute mucho después. Eso es un closure: 

{products.map((product) => (
  <button key={product.id} onClick={() => handleDelete(product.id)}>
    Eliminar
  </button>
))}

// En cada vuelta del map se crea una arrow DISTINTA que "recuerda"
// el product.id de ESA vuelta:
//   botón 1 → () => handleDelete(1)
//   botón 2 → () => handleDelete(2)
//   botón 3 → () => handleDelete(3)
CLOSURE EN ACCIÓN ───────────────── function crear() { const secreto = 42; ← variable local return () => console.log(secreto); ← la arrow "se lleva" secreto } const fn = crear(); // crear() ya terminó… fn(); // …pero imprime 42: la arrow RECUERDA su ámbito

Este mecanismo es el que permite que cada botón de una lista recuerde SU dato sin que tú guardes nada a mano. Los closures están por todas partes en React (también en los hooks del Módulo 6).

Las tres formas de pasar parámetros (y cuándo usar cada una)

TécnicaCódigoCuándo usarla
Arrow envolvente onClick={() => fn(id)} El 90 % de los casos: listas, botones con datos.
Arrow con evento reenviado onClick={(e) => fn(id, e)} Cuando además del dato necesitas el evento (stopPropagation, target…).
Función que devuelve función (currying) onClick={handleDelete(id)} donde handleDelete devuelve otra función Manejadores compartidos/factorías; elegante pero menos directo. 
// Currying: handleDelete es una FÁBRICA de manejadores
function handleDelete(id) {
  return function (e) {           // ← ESTA es la función que recibe React
    e.stopPropagation();
    console.log("Borrando", id);
  };
}

<button onClick={handleDelete(product.id)}>Eliminar</button>
// Aquí SÍ vale llamarla: porque lo que devuelve… es otra función

El manejador en listas: el patrón definitivo

La forma profesional no crea la arrow dentro del JSX del map por componente, sino que pasa el dato hacia abajo y deja el arrow en el hijo:

// Padre: pasa el item Y el callback como props
{products.map((product) => (
  <ProductRow key={product.id} product={product} onDelete={handleDelete} />
))}

// Hijo (ProductRow): crea el arrow AQUÍ, con su propio product
function ProductRow({ product, onDelete }) {
  return (
    <button onClick={() => onDelete(product.id)}>
      Eliminar {product.name}
    </button>
  );
}

Ventajas: el padre queda limpio, el hijo es testeable por separado, y handleDelete es UNA función compartida (no 30 closures distintos en el padre… aunque en el hijo seguirá habiendo una arrow por fila, es inevitable y está bien).

3 · Ejemplo mínimo

src/App.jsx
const colors = ["crimson", "teal", "purple"];

export default function App() {
  function handlePick(color) {
    alert(`Elegiste: ${color}`);
  }

  return (
    <div>
      {colors.map((color) => (
        <button key={color} onClick={() => handlePick(color)}>
          {color}
        </button>
      ))}
    </div>
  );
}

Línea por línea:

  1. handlePick(color) — el manejador recibe un dato propio (no el evento).
  2. onClick={() => handlePick(color)} — la arrow envuelve la llamada: se ejecutará SOLO al hacer clic, recordando el color de su vuelta del map (closure).
  3. Cada botón acaba con su propia función que recuerda su propio color.

4 · Ejemplo real

Una tabla de usuarios con acciones por fila (editar, eliminar) — el patrón exacto de cualquier back-office:

src/components/UserTable.jsx
const users = [
  { id: 1, name: "Ana", role: "admin" },
  { id: 2, name: "Luis", role: "editor" },
  { id: 3, name: "Marta", role: "viewer" },
];

export default function UserTable() {
  // UN manejador por ACCIÓN, compartido por todas las filas
  function handleEdit(id) {
    console.log("Editar usuario", id);
  }

  function handleDelete(id, event) {
    event.stopPropagation(); // no burbujee al clic de la fila
    if (confirm("¿Eliminar este usuario?")) {
      console.log("Eliminado usuario", id);
    }
  }

  return (
    <table>
      <tbody>
        {users.map((user) => (
          <tr key={user.id} onClick={() => console.log("Ver ficha", user.id)}>
            <td>{user.name}</td>
            <td>{user.role}</td>
            <td>
              {/* Arrow con SOLO el dato */}
              <button onClick={() => handleEdit(user.id)}>Editar</button>

              {/* Arrow con dato Y evento (para el stopPropagation) */}
              <button onClick={(e) => handleDelete(user.id, e)}>
                Eliminar
              </button>
            </td>
          </tr>
        ))}
      </tbody>
    </table>
  );
}

Decisiones explicadas:

  • Un manejador por acción, no por fila: handleEdit existe una vez; las arrows de cada fila solo le inyectan el id.
  • La fila entera es clicable (ver ficha) y los botones llevan stopPropagation para no disparar también el clic de la fila. Patrón muy común en tablas y listas.
  • Cuando necesitas el evento, lo declaras en la arrow ((e) => …) y lo reenvías: la arrow es tu válvula de paso.

5 · Buenas prácticas

HazEvitaPor qué
() => fn(dato) para pasar parámetros fn(dato) directo en onClick Se ejecuta en el render: es EL error de este tema.
Un manejador por acción, compartido Funciones con nombre por fila (handleDeleteUser1…) El dato cambia, la acción es la misma: parametriza.
Pasar el id (o el objeto) mínimo necesario Capturar variables globales o de módulo dentro de las arrows El closure debe capturar datos del render actual, no de fuera: si la variable cambia, leerías valores viejos (stale closure, Módulo 6).
En componentes hijo: arrow en el hijo con su propio item Arrows gigantes de 10 líneas dentro del JSX del padre El JSX debe leerse como plantilla; la lógica, en funciones.

6 · Errores habituales

Error 1: llamar en lugar de envolver

✘ Incorrecto 
<button onClick={greet("Ana")}>Saludar</button>
// El saludo salta AL RENDERIZAR, no al hacer clic.
// Y si greet cambiara estado… render infinito 💥
✔ Correcto 
<button onClick={() => greet("Ana")}>Saludar</button>

Error 2: esperar el evento cuando pasas parámetros

✘ Incorrecto 
function handleSave(userId) {
  event.preventDefault(); // 💥 "event is not defined":
}                         // tú llamas con userId, el evento no llega solo

<button onClick={() => handleSave(user.id)}>Guardar</button>
✔ Correcto 
// Decláralo en la arrow y reenvíalo si lo necesitas:
<button onClick={(e) => handleSave(user.id, e)}>Guardar</button>

Error 3: confundir currying con llamada directa

✘ Incorrecto 
function handleDelete(id) {          // NO es fábrica: no devuelve función
  console.log("borrando", id);
}
<button onClick={handleDelete(5)}>X</button>  // se ejecuta YA
✔ Correcto (una de las dos) 
<button onClick={() => handleDelete(5)}>X</button>   // arrow envolvente

// o conviértelo en fábrica de verdad:
const handleDelete = (id) => () => console.log("borrando", id);
<button onClick={handleDelete(5)}>X</button>  // ahora SÍ: devuelve función

9 · Resumen

  • Para pasar parámetros a un manejador: envuélvelo en una arrow — onClick={() => fn(dato)}.
  • La arrow recuerda el dato gracias al closure: captura las variables del ámbito donde nació.
  • Si necesitas también el evento: (e) => fn(dato, e).
  • El currying (función que devuelve función) permite onClick={fn(dato)} legítimamente — la llamada devuelve la función manejadora.
  • Patrón profesional en listas: un manejador por acción en el padre; la arrow con el item en el hijo.
  • Nunca captures variables globales en las arrows: captura datos del render actual.

10 · Preguntas frecuentes

¿Crear una arrow nueva en cada render no es lento?

Crear funciones es baratísimo en JavaScript (microsegundos). Solo importa en optimizaciones finas con React.memo en hijos costosos (Módulo 11: useCallback). Nunca optimices esto antes de tiempo.

¿Puedo usar .bind() en lugar de arrow?

onClick={handleDelete.bind(null, id)} funciona (bind crea una función con argumentos prefijados), pero la arrow es más legible y universal. Verás bind en código antiguo.

¿Y pasar parámetros en onChange/onSubmit?

Igual: onChange={(e) => handleChange(fieldName, e)}. El patrón es idéntico para todos los eventos.

¿Qué es un «stale closure» que he visto mencionar?

Cuando una arrow/hook recuerda un valor VIEJO de una variable (porque se creó en un render anterior). Es un tema de useEffect y sus dependencias: lo trataremos con calma en el Módulo 6, donde tiene sentido.
