Endurecimiento y auditoría

Módulo 6 · Seguridad 🕐 35 minutos

1 · Introducción

La imagen rabbitmq:4-management está diseñada para que empieces en dos minutos: usuario guest, puerto 5672 abierto, management en 15672 y todos los plugins de management activos. Es una decisión correcta para un tutorial y una mala configuración para un broker que atiende tráfico real. Endurecer no es añadir una capa al final: es revisar cada superficie que el broker expone y decidir si debe existir.

Un broker de mensajería es un objetivo atractivo: concentra credenciales, datos de negocio y la capacidad de parar el sistema entero. El modelo de amenaza habitual no es un atacante sofisticado, sino algo más mundano:

AmenazaVector típicoConsecuencia
UI expuesta a Internet15672 publicado en 0.0.0.0 con contraseña débilLectura de mensajes, publicación, borrado de colas.
Credencial compartidaUn usuario admin en todos los servicios y personasNo se puede revocar a un empleado sin romper el sistema; sin atribución.
Usuario por defecto activoguest con acceso remoto habilitadoCualquiera que escanee el puerto entra con guest/guest.
Tráfico en claroAMQP por 5672 entre redes no confiablesCredenciales y cargas legibles en la red.
Permisos amplios".*" en las tres columnasUn bug borra la topología; una fuga destruye el vhost.
Sin auditoríaNadie revisa usuarios, políticas ni conexionesUn acceso no autorizado pasa desapercibido durante meses.

Endurecer es reducir superficie, no acumular flags

Cada puerto, plugin, usuario y permiso que no necesitas es una vía de entrada que no tienes que defender. La lista de comprobación final no es un ritual: es la lista de cosas que alguien puede usar contra ti si las dejas abiertas.

La regla es simple: los puertos de clúster solo se abren entre nodos; los de cliente, solo desde la red de aplicaciones; los de administración, solo desde la red de operación. Todo lo demás se cierra en el cortafuegos, no solo en la configuración de RabbitMQ.

Identidad: menos cuentas y mejores

  • Elimina guest. No lo desactives «temporalmente»: bórralo y crea un administrador nominativo.
  • Una cuenta por persona y por servicio. Compartir cuenta impide revocar, atribuir y rotar.
  • Contraseñas generadas de al menos 24 caracteres aleatorios, guardadas en un gestor de secretos, nunca en Git ni en una variable de compose comprometida.
  • Rotación periódica y tras la salida de una persona. La rotación se ensaya: si el procedimiento no está probado, no existe.
  • Tags mínimos: administrator solo para el equipo de plataforma; monitoring para observabilidad; nada para APIs y workers.
  • MFA en el proveedor de identidad si la UI se federó con OAuth/LDAP; RabbitMQ por sí solo no ofrece segundo factor para usuarios internos.

El export de definiciones contiene hashes de contraseñas

export_definitions incluye usuarios, hashes y permisos. Versionarlo está bien; subirlo a un repositorio público o adjuntarlo a un ticket, no. Trátalo como un secreto, o exporta solo vhosts, políticas y colas con una herramienta que filtre usuarios.

Transporte y administración

En producción, el objetivo es que no exista una vía en claro. Eso significa listeners.tcp = none, management solo en 15671, y el puerto 15671 escuchando en una interfaz privada o detrás de un proxy con autenticación. Si necesitas la UI en localhost para depurar, publica 127.0.0.1:15671:15671, no 15671:15671.

El detalle de TLS (CA, SAN, mTLS, rotación) está en TLS en el broker. Aquí basta con la decisión: sin TLS no hay endurecimiento posible, porque las credenciales viajan legibles.

Configuración: desactivar lo que no se usa

# Qué plugins están activos de verdad
docker exec rabbitmq rabbitmq-plugins list -e

# Desactivar lo que no forma parte del producto
docker exec rabbitmq rabbitmq-plugins disable rabbitmq_mqtt
docker exec rabbitmq rabbitmq-plugins disable rabbitmq_stomp
docker exec rabbitmq rabbitmq-plugins disable rabbitmq_federation
docker exec rabbitmq rabbitmq-plugins disable rabbitmq_shovel

Cada plugin activo añade endpoints, configuración y código que hay que parchear. MQTT y STOMP son útiles si los usas; si no, son superficie regalada. Lo mismo con rabbitmq_management: si solo lo usas para métricas, quizá te baste Prometheus y puedas cerrar la UI.

Fija también por escrito listeners.tcp = none, la IP privada de management, log.console.level = info y la imagen con digest: son decisiones que un despliegue reproducible no debe improvisar.

Auditoría: qué mirar y cada cuánto

RabbitMQ no trae un registro de auditoría de negocio con autor y acción listos para compliance. Lo que sí ofrece son piezas que, combinadas, cuentan la historia:

FuenteQué respondeCómo se consulta
Log del nodoFallos de login, cierres de conexión, errores de política, alarmasdocker compose logs rabbitmq o el fichero de log
Event exchangeQué conexiones, colas, usuarios y permisos se crearon o cambiaron, y cuándoPlugin rabbitmq_event_exchange, cola enlazada a amq.rabbitmq.event
Definiciones exportadasEstado declarado: usuarios, vhosts, permisos, políticas, colasrabbitmqctl export_definitions + diff en Git
Management APIConexiones, canales, consumidores y profundidad de colas en el momentoGET /api/connections, /api/queues
MétricasTendencias y alertasPrometheus + Grafana (ver observabilidad)

El plugin de eventos publica mensajes con cuerpo vacío y los atributos en cabeceras. Se puede consumir y volcar a un sistema de logs, o alertar en tiempo real:

import amqp from 'amqplib';

const conn = await amqp.connect(process.env.RABBITMQ_URL);
const ch = await conn.createChannel();

const { queue } = await ch.assertQueue('', { exclusive: true });
await ch.bindQueue(queue, 'amq.rabbitmq.event', 'user.#');
await ch.bindQueue(queue, 'amq.rabbitmq.event', 'permission.#');

await ch.consume(queue, (msg) => {
  const event = msg.fields.routingKey;
  const who = msg.properties.headers?.name ?? 'desconocido';
  console.log(JSON.stringify({ event, who, at: new Date().toISOString() }));
  ch.ack(msg);
});

Fíjate en que la cola es exclusiva y autoborrable: es un consumidor de auditoría, no un almacén. Para conservar eventos, publica en una cola durable con retención y envíalos a tu plataforma de logs.

Mínimo privilegio y revisión periódica

Los permisos se pudren: alguien añade configure para una migración y nunca lo quita; un servicio desaparece y su usuario sigue activo. Una revisión trimestral debería responder:

  • ¿Qué usuarios existen y quién es el dueño de cada uno?
  • ¿Quién tiene el tag administrator y está justificado?
  • ¿Qué identidades tienen ".*" en algún vhost?
  • ¿Hay cuentas sin conexiones en 90 días? ¿Se pueden desactivar?
  • ¿Las políticas y los límites coinciden con lo versionado?

La revisión no es un documento que se firma: es un script que produce una lista y un responsable que la revisa. Si no genera una acción concreta, no sirve.

3 · Ejemplo mínimo

Este es el mínimo endurecimiento que deberías aplicar antes de que el broker vea tráfico real. Primero, inspecciona lo que hay:

docker exec rabbitmq rabbitmq-diagnostics listeners
docker exec rabbitmq rabbitmqctl list_users
docker exec rabbitmq rabbitmqctl list_permissions -p /
Interface: [::], port: 25672, protocol: clustering, purpose: inter-node and CLI tool communication
Interface: [::], port: 5672, protocol: amqp, purpose: AMQP 0-9-1 and AMQP 1.0
Interface: [::], port: 15672, protocol: http, purpose: HTTP API
Interface: [::], port: 1883, protocol: mqtt, purpose: MQTT

Ese puerto 1883 es el plugin MQTT que nadie pidió. Ese 5672 en [::] escucha en todas las interfaces. Y guest sigue ahí.

Aplica el mínimo:

# 1. Admin nominativo y contraseña generada
docker exec rabbitmq rabbitmqctl add_user ana.admin "$(openssl rand -base64 32)"
docker exec rabbitmq rabbitmqctl set_user_tags ana.admin administrator
docker exec rabbitmq rabbitmqctl set_permissions -p / ana.admin ".*" ".*" ".*"

# 2. Fuera el usuario por defecto
docker exec rabbitmq rabbitmqctl delete_user guest

# 3. Fuera plugins que no se usan
docker exec rabbitmq rabbitmq-plugins disable rabbitmq_mqtt

# 4. Solo TLS y UI en localhost
#    (en rabbitmq.conf)
#    listeners.tcp = none
#    management.ssl.port = 15671
#    management.ssl.ip = 127.0.0.1
#    y reiniciar el contenedor

Verifica el resultado con la misma orden que usaste para inspeccionar:

docker exec rabbitmq rabbitmq-diagnostics listeners
docker exec rabbitmq rabbitmqctl list_users

Ahora no debe aparecer guest, no debe haber un listener AMQP en claro y MQTT no debe estar escuchando. Si algo sigue ahí, no es un detalle cosmético: es una puerta.

La contraseña del ejemplo no se queda en el historial

openssl rand en el shell deja la contraseña en el historial y en la lista de procesos. En producción se genera en el gestor de secretos y se inyecta como variable de entorno o fichero; el comando que ves es para el laboratorio.

El contrato de operación tiene cuatro piezas que se revisan en cada cambio:

La auditoría no vive en un wiki: vive en un job que compara el estado del broker con el declarado. Un diff inesperado abre un ticket; un cambio intencionado se aprueba y se aplica desde el repositorio. Así el broker no se convierte en una caja negra que solo una persona sabe tocar.

6 · Errores habituales

1. Publicar la management UI en Internet

Mal — UI accesible desde cualquier IP 
ports:
  - "5672:5672"
  - "15672:15672"
Bien — TLS y solo en la interfaz privada 
ports:
  - "5671:5671"
  - "127.0.0.1:15671:15671"

La UI permite publicar mensajes, purgar colas y cambiar políticas. Exponerla convierte un escaneo de puertos en una consola de administración. El cifrado no arregla la exposición: la mueve a otro puerto.

2. Reactivar guest para «poder conectarme»

Mal — acceso remoto al usuario por defecto 
loopback_users.guest = false
Bien — usuario propio y guest eliminado 
rabbitmqctl add_user ana.admin "$(openssl rand -base64 32)"
rabbitmqctl set_user_tags ana.admin administrator
rabbitmqctl delete_user guest

guest/guest es la primera credencial que prueba cualquier escáner. Si necesitas conectarte desde otra máquina, crea un usuario con permisos limitados, no abras el de por defecto.

3. Una sola cuenta para todo

Mal — el mismo admin en CI, API y portátiles 
# .env de todos los servicios y de todas las personas
RABBITMQ_URL=amqp://admin:admin123@rabbitmq:5672/
Bien — identidades separadas y permisos acotados 
CI:      taller-deploy  configure/write/read ^taller\.
API:     taller-api     write/read ^taller\.
worker:  taller-worker  read ^taller\.jobs.*, write ^taller\.
persona: ana.admin      administrator + MFA en el IdP

Con una cuenta única no puedes revocar a un empleado sin romper la API, ni saber quién borró la cola, ni rotar sin coordinar a todo el mundo.

4. Desactivar la verificación de TLS para que arranque

Mal — «ya funciona» 
amqp.connect('amqps://user:pass@broker:5671', { rejectUnauthorized: false });
Bien — corregir la CA o el hostname 
amqp.connect('amqps://user:pass@broker:5671', {
  ca: [readFileSync('/run/secrets/ca.pem')],
  servername: 'broker',
});

El error de certificado es una señal, no un obstáculo. Desactivar la verificación convierte una conexión cifrada en una conexión cifrada con quien sea. El detalle está en TLS en el broker.

7 · Ejercicio guiado

Objetivo: endurecer un broker de laboratorio, comprobar la superficie resultante y montar una auditoría mínima de eventos y de configuración.

  1. Fotografía el estado inicial: 
    docker exec rabbitmq rabbitmq-diagnostics listeners
docker exec rabbitmq rabbitmqctl list_users
docker exec rabbitmq rabbitmqctl list_permissions -p /
docker exec rabbitmq rabbitmq-plugins list -e

    Anota puertos, usuarios y plugins. Ese es tu «antes».

  2. Elimina la cuenta por defecto y crea un admin nominativo con contraseña generada. Verifica con list_users que solo queda tu cuenta y que tiene el tag administrator.
  3. Cierra la superficie: desactiva MQTT y STOMP si no los usas, pon listeners.tcp = none en rabbitmq.conf, configura TLS en 5671 y management en 15671 sobre 127.0.0.1. Reinicia y comprueba con rabbitmq-diagnostics listeners que no queda ningún listener en claro.
  4. Activa el event exchange y consume eventos de identidad: 
    docker exec rabbitmq rabbitmq-plugins enable rabbitmq_event_exchange

    Ejecuta el consumidor del ejemplo con una cola exclusiva enlazada a user.# y permission.#. En otra terminal, crea un usuario de prueba y observa el evento user.created; bórralo y observa user.deleted. Comprueba que el cuerpo del mensaje está vacío y los datos vienen en cabeceras.

  5. Provoca un fallo de autenticación con una contraseña incorrecta y búscalo en el log: 
    docker compose logs rabbitmq | grep -i "login failed\|authentication"

    Debe aparecer el usuario y el host de origen. Ese es el rastro que usarás en una investigación.

  6. Versiona y compara: exporta las definiciones a un directorio del repositorio, haz un cambio manual (por ejemplo, crea un usuario extra) y vuelve a exportar. Diff de los dos ficheros: el cambio no autorizado debe aparecer. Cierra el ejercicio decidiendo qué harías con ese diff en CI.

Comprueba el «después» con las mismas órdenes

La tentación es fiarse de la configuración escrita. Ejecuta otra vez rabbitmq-diagnostics listeners, list_users y list_permissions: el estado real es el que responde el broker, no el que dice el fichero.

8 · Reto

🎯 Auditoría con atribución y break-glass

Diseña un sistema de auditoría que detecte en menos de cinco minutos un cambio de privilegios no autorizado en producción, y que permita a una persona de guardia obtener acceso de emergencia sin usar una cuenta compartida.

Debe cubrir: consumo de user.#, permission.#, policy.# y vhost.#; correlación con el cambio aprobado en Git; alerta si el cambio ocurre fuera de una ventana o sin PR; y un procedimiento break-glass con credenciales efímeras, registro de quién las usó y caducidad automática. Explica qué eventos no te dan atribución suficiente y cómo la obtendrías.

Pista: el event exchange te dice qué y cuándo, pero no siempre quién ni desde dónde; y los eventos de autenticación exitosa pueden ser muy ruidosos. Piensa en qué eventos son señal y cuáles son línea base.

9 · Resumen

  • Endurecer es reducir superficie: puertos, plugins, usuarios y permisos que no necesitas.
  • Solo 5671 y 15671 deben ser accesibles, y solo desde redes privadas; 4369 y 25672, solo entre nodos.
  • Borra guest, usa identidades nominativas y por servicio, y guarda los secretos fuera de Git.
  • Los tags no son permisos: limita administrator y revisa quién lo tiene.
  • Audita con logs, event exchange y diff de definiciones; una auditoría sin responsable no cambia nada.
  • La revisión de accesos es periódica y produce acciones: revocar, rotar, justificar o eliminar.

10 · Preguntas frecuentes

¿Basta con cerrar los puertos para considerar el broker seguro?

No. El cortafuegos reduce la superficie, pero un cliente comprometido dentro de la red sigue necesitando permisos acotados y TLS. La seguridad es la combinación de red, identidad, autorización, transporte y auditoría; quitar una capa no compensa las demás. Un broker solo accesible por VPN pero con ".*" para todos sigue siendo frágil.

Si uso TLS y mTLS, ¿puedo simplificar los permisos?

No. mTLS autentica la máquina, no autoriza operaciones. Un worker con certificado válido y permisos amplios puede borrar la topología igual. De hecho, mTLS facilita tener identidades por servicio, lo que hace más fácil aplicar mínimo privilegio, no menos necesario.

¿Puedo saber quién publicó un mensaje concreto?

AMQP no transporta una identidad de autor firmada por el broker. Puedes propagar un identificador de usuario o de traza en las cabeceras del mensaje, pero es responsabilidad del productor y se puede falsificar. Para atribución real, combina identidades por servicio, el evento connection.created y logs de aplicación con el mismo jobId o traceId.

¿Qué hago si sospecho que una credencial se ha filtrado?

Primero revoca: cambia la contraseña o elimina el usuario, lo que cierra sus conexiones. Después revisa el event exchange y los logs para ver qué conexiones y operaciones hubo, y las colas para detectar mensajes inesperados. Finalmente rota los secretos relacionados y añade la detección que faltaba. La rotación de emergencia debe estar escrita y probada antes del incidente.
