Fanout: publicar a todos

Módulo 2 · Exchanges y routing 🕐 30 minutos

1 · Introducción

Hay mensajes que no van dirigidos a nadie en concreto: «el catálogo cambió», «la configuración se recargó», «empieza la ronda». Todos los interesados deben enterarse ahora, y ninguno debe impedir que los demás se enteren. Ese es el trabajo de un exchange fanout: copia cada mensaje a todas las colas bindeadas e ignora por completo la routing key.

Es el exchange más simple de entender y el más fácil de usar mal. Su promesa es broadcast, no «entrega garantizada a quien no está mirando». Un fanout no almacena nada: si no hay ninguna cola bindeada en el momento de publicar, el mensaje se descarta. Y si la cola de un suscriptor es efímera, cuando ese suscriptor se desconecta deja de existir y los mensajes que lleguen mientras tanto no le esperan.

Aquí verás cuándo fanout es la respuesta correcta (invalidación de caché, eventos globales, abanico a servicios independientes), cómo construir suscriptores temporales sin filtrar colas huérfanas y por qué «fanout con routing key» no es una forma de filtrar. También la comparación incómoda: fanout y un topic bindeado con # se parecen mucho, pero no son lo mismo.

Por qué existe esta lección

El patrón pub/sub se suele explicar con fanout y se suele implementar con topic. Saber qué garantiza cada uno —y qué no— evita dos fallos clásicos: suscriptores que se pierden eventos por tener una cola temporal, y exchanges fanout usados para filtrar cuando el receptor solo quería una parte.

2 · Teoría

La regla: una copia por cola, routing key ignorada

Fanout no compara nada. Por cada mensaje publicado, el broker enumera las colas bindeadas al exchange y deja una copia en cada una. La routing key puede ser '', pedido.creado o lo-que-sea: da igual. La binding key tampoco se evalúa, aunque la API exija pasar una cadena (usa '').

                 publish("taller.eventos", "cualquier.key")
                                  |
                                  v
                        +-------------------+
                        | taller.eventos    |
                        | (fanout)          |
                        +-------------------+
                          |       |       |
              +-----------+       |       +-------------+
              v                   v                     v
      +---------------+   +---------------+     +---------------+
      | cache.productos|  | auditoria     |     | dashboard-7f3 |
      | (durable)      |  | (durable)     |     | (exclusiva)   |
      +---------------+   +---------------+     +---------------+
        1 copia              1 copia              1 copia

Dos matices que se confunden con frecuencia:

  • Una copia por cola, no por consumidor. Si dos procesos consumen la misma cola, se reparten los mensajes (competing consumers); no reciben ambos la misma copia. Para que dos instancias reciban todo, cada una necesita su propia cola.
  • Sin colas bindeadas, no hay destino. El mensaje se descarta en silencio, igual que en direct. Un alternate exchange o mandatory pueden dar señal; lo verás en headers y alternate exchange.

El problema del suscriptor temporal

Si declaras una cola con un nombre fijo para cada dashboard, en cuanto haya despliegues y réplicas tendrás colas huérfanas acumulando mensajes que nadie lee. La solución canónica son las colas exclusivas con nombre generado por el broker:

const { queue } = await ch.assertQueue('', { exclusive: true });
// queue ≈ "amq.gen-JzTY20BRgKO-HjmUJj0wLg"
await ch.bindQueue(queue, 'taller.eventos', '');
await ch.consume(queue, onEvento, { noAck: false });

La cadena vacía pide al broker un nombre único. exclusive: true ata la cola a la conexión que la declaró: solo esa conexión puede usarla y se borra al cerrarse. Es exactamente lo que quieres para una suscripción que vive mientras vive el proceso.

PropiedadQué garantizaCuándo usarla
exclusive: trueSolo la conexión declarante puede consumir; se borra al cerrar la conexión.Suscriptores efímeros, RPC replies, demos.
autoDelete: trueSe borra cuando el último consumidor se da de baja (si tuvo al menos uno).Colas con nombre estable que no deben sobrevivir al consumidor.
x-expires: msSe borra tras un periodo sin consumidores, sin redeclaración y sin basic.get.Colas temporales no exclusivas con nombre propio.
Durable, sin autoDeleteSobrevive a reinicios y guarda mensajes mientras el consumidor está caído.Suscriptores de negocio que no pueden perder eventos.

Exclusiva no significa «con buffer»

Una cola exclusiva se destruye con la conexión, y con ella sus mensajes listos. Si el suscriptor se cae, los eventos publicados durante la caída no se guardan «para cuando vuelva»: se pierden para él. Si eso no es aceptable, la cola debe ser durable y con nombre estable, y el consumidor debe reconectar y volver a consumir.

Reconexión: la cola temporal se recrea

Al reconectar, el nombre generado anterior no sirve. El suscriptor debe volver a declarar, bindear y consumir. Ese ciclo es parte del diseño, no un parche:

conectar → assertQueue('', { exclusive: true })
        → bindQueue(queue, exchange, '')
        → consume(queue)
        → ... si cae la conexión, repetir desde el principio

Si usas una librería de reconexión, comprueba que vuelve a ejecutar la topología. Una conexión recuperada con un canal nuevo pero sin consume es un suscriptor zombie: parece vivo y no recibe nada.

Fanout frente a topic con #

Un binding # en un topic coincide con cualquier routing key, así que un topic con un único binding # se comporta como un fanout para esa cola. Pero no son intercambiables:

CriterioFanoutTopic con #
IntenciónBroadcast explícitoPatrón que, en este caso, coincide con todo
Coste de routingNo evalúa nadaEvalúa el patrón en cada publicación
Mezclar selectivosNo: todos los bindings reciben todoSí: en el mismo exchange conviven # y pedido.*
RiesgoRuido si alguien bindea una cola de másCreer que # es gratis y multiplicar patrones
Lectura del diseño«Esto es un evento global»«Esto es una taxonomía con una suscripción total»

Regla práctica: si todos los receptores deben recibir todo, fanout. Si conviven receptores totales y parciales, topic y un binding # para el total. No uses fanout y luego intentes filtrar en el consumidor: estarás moviendo el filtro al sitio equivocado y pagando tráfico por mensajes que se descartan.

3 · Ejemplo mínimo

Garantía de este ejemplo: at-most-once y sin persistencia real. Las colas son exclusivas y efímeras, y los mensajes se publican sin confirms. Sirve para ver el fanout; no como plantilla de producción. En producción: colas durables para suscriptores de negocio, ack manual y confirms (ver publisher confirms).

Dos suscriptores, dos colas, un exchange. Publica una vez y observa dos entregas:

import amqp from 'amqplib';

const conn = await amqp.connect('amqp://taller:taller@localhost:5672');
const ch = await conn.createChannel();

await ch.assertExchange('demo.fanout', 'fanout', { durable: true });

// Dos colas exclusivas: una por suscriptor, con nombre generado.
const a = await ch.assertQueue('', { exclusive: true });
const b = await ch.assertQueue('', { exclusive: true });
await ch.bindQueue(a.queue, 'demo.fanout', '');
await ch.bindQueue(b.queue, 'demo.fanout', '');

// noAck solo para la demo: en producción, ack manual tras procesar.
await ch.consume(a.queue, (msg) => {
  console.log('A recibió:', msg.content.toString());
}, { noAck: true });
await ch.consume(b.queue, (msg) => {
  console.log('B recibió:', msg.content.toString());
}, { noAck: true });

// La routing key es irrelevante: fanout la ignora.
ch.publish('demo.fanout', 'lo.que.sea', Buffer.from('pedido.creado'));

await new Promise((resolve) => setTimeout(resolve, 200));
await ch.close();
await conn.close();

Salida esperada (el orden entre A y B no está garantizado):

A recibió: pedido.creado
B recibió: pedido.creado

Qué hace cada pieza:

  • assertExchange(..., 'fanout', { durable: true }): el exchange sobrevive reinicios; las colas de este ejemplo no.
  • assertQueue('', { exclusive: true }): nombre generado y cola ligada a la conexión. Al cerrar, ambas desaparecen.
  • bindQueue(cola, exchange, ''): en fanout la clave no filtra; se pasa vacía por convención.
  • publish(exchange, routingKey, Buffer): una sola llamada; el broker copia a las dos colas.

Cambia la routing key por otra.cosa y repite: verás las mismas dos entregas. Ese es el experimento que demuestra que fanout no enruta por clave.

4 · Ejemplo real

El catálogo del taller cambia de precios varias veces al día. La API publica catalogo.actualizado y deben reaccionar: la caché de productos (no puede servir precios viejos), el buscador (reindexa), y los dashboards de la oficina (solo mientras están abiertos). Los dos primeros no pueden perder eventos; el tercero sí puede.

                   catalogo.eventos (fanout)
                    /          |           \
                   v           v            v
        cache.productos   buscador.index   dashboard-<uuid>
        (durable)         (durable)        (exclusiva, efímera)
        siempre            siempre          solo mientras vive
        ack manual         ack manual        la pestaña

El publicador no conoce a ninguno de los tres. Solo declara el exchange y publica:

// publicador.js
import amqp from 'amqplib';

const conn = await amqp.connect('amqp://taller:taller@localhost:5672');
const ch = await conn.createConfirmChannel();
await ch.assertExchange('catalogo.eventos', 'fanout', { durable: true });

const evento = {
  tipo: 'catalogo.actualizado',
  sku: 'SKU-42',
  precio: 19.9,
  version: 7,
};

ch.publish('catalogo.eventos', '', Buffer.from(JSON.stringify(evento)), {
  persistent: true,
  contentType: 'application/json',
  messageId: 'catalogo-SKU-42-v7',
}, (err) => {
  if (err) console.error('nack:', err.message);
});

La cola durable del buscador se declara una vez, con su binding, y su consumidor hace ack después de reindexar:

// buscador.js
await ch.assertExchange('catalogo.eventos', 'fanout', { durable: true });
await ch.assertQueue('buscador.index', { durable: true });
await ch.bindQueue('buscador.index', 'catalogo.eventos', '');
await ch.prefetch(20);

await ch.consume('buscador.index', async (msg) => {
  if (!msg) return;
  try {
    await indexar(JSON.parse(msg.content.toString()));
    ch.ack(msg);
  } catch (err) {
    // Sin requeue infinito: a la DLQ o a una cola de reintentos.
    ch.nack(msg, false, false);
  }
});

El dashboard, en cambio, se suscribe con una cola exclusiva y la vuelve a crear si se cae la conexión:

// dashboard.js — llamado también desde el evento 'connect' tras reconectar
async function suscribir(ch) {
  await ch.assertExchange('catalogo.eventos', 'fanout', { durable: true });
  const { queue } = await ch.assertQueue('', { exclusive: true });
  await ch.bindQueue(queue, 'catalogo.eventos', '');
  await ch.consume(queue, (msg) => {
    enviarAlNavegador(JSON.parse(msg.content.toString()));
    ch.ack(msg);
  });
}
SuscriptorTipo de colaQué pasa si está caído 5 minutos
Caché de productosDurable + persistenteLos eventos se acumulan y se procesan al volver.
BuscadorDurable + persistenteSe acumulan; al arrancar reindexa el backlog.
Dashboard abiertoExclusivaPierde esos eventos; al reconectar solo ve los nuevos.
Dashboard cerradoNo existeNo hay cola ni acumulación: no los necesita.

Esa tabla es la decisión de diseño importante. Fanout no elige por ti: solo copia a quien tenga cola. La durabilidad y la persistencia son las que convierten una copia en una obligación.

6 · Errores habituales

1. Usar fanout y filtrar en el consumidor

Mal — todo el mundo recibe todo 
// Un fanout para «eventos» y cada servicio descarta lo que no le interesa.
if (evento.tipo !== 'pedido.creado') return ch.ack(msg); // ruido y CPU
Bien — topic si hay selección 
await ch.assertExchange('pedidos', 'topic', { durable: true });
await ch.bindQueue('facturacion', 'pedidos', 'pedido.creado');
// Solo llega lo que coincide; el filtro vive en el binding.

Fanout no tiene semántica de filtro. Si un receptor descarta mensajes, el exchange equivocado está en el diseño.

2. Cola temporal sin exclusividad ni autoDelete

Mal — cola con nombre fijo que nadie limpia 
await ch.assertQueue(`dashboard-${process.pid}`); // queda para siempre
await ch.bindQueue(`dashboard-${process.pid}`, 'catalogo.eventos', '');
Bien — nombre generado y vida ligada a la conexión 
const { queue } = await ch.assertQueue('', { exclusive: true });
await ch.bindQueue(queue, 'catalogo.eventos', '');

El pid cambia en cada despliegue y la cola vieja se queda con su backlog. Con miles de réplicas, el broker se llena de colas muertas.

3. Esperar que una cola exclusiva guarde el backlog

Mal — «cuando vuelva, lo procesa» 
servicio caído 10 min
→ su cola exclusiva se borró al cerrar la conexión
→ los eventos de esos 10 min no existen para él
Bien — cola durable si el evento es obligatorio 
await ch.assertQueue('facturacion.eventos', { durable: true });
await ch.bindQueue('facturacion.eventos', 'catalogo.eventos', '');
// Mensajes persistentes + ack manual = backlog recuperable.

Fanout garantiza la copia a las colas que existen en ese instante, no la entrega futura a un suscriptor ausente.

4. Publicar antes de que exista el binding

Mal — carrera de arranque 
ch.publish('catalogo.eventos', '', body); // aún no hay colas bindeadas
await ch.assertQueue('buscador.index', { durable: true }); // tarde
Bien — topología primero, publicación después 
await declararTopologia(ch);   // exchange + colas + bindings
ch.publish('catalogo.eventos', '', body, { persistent: true });

Los exchanges no almacenan. Un mensaje publicado antes del binding se descarta aunque el consumidor arranque un segundo después.

7 · Ejercicio guiado

Objetivo: ver una copia por cola, comprobar que la routing key se ignora y entender el ciclo de vida de una cola exclusiva.

  1. Declara el exchange y dos colas exclusivas con el ejemplo mínimo. Antes de publicar, imprime los nombres generados: 
    console.log('cola A:', a.queue, '| cola B:', b.queue);

    Esperado: dos nombres distintos con prefijo amq.gen-.

  2. Publica tres mensajes con keys distintas (a, pedido.creado, '') y comprueba que A y B reciben los tres. La key no cambia el resultado.
  3. Comprueba el reparto dentro de una cola: añade un segundo consumidor a la cola A y publica seis mensajes. Verás que se reparten entre los dos consumidores de A, mientras B sigue recibiendo los seis. 
    A1: 3 mensajes   A2: 3 mensajes   B: 6 mensajes
  4. Demuestra que la cola es efímera: cierra la conexión y ejecuta: 
    docker exec rabbitmq rabbitmqctl list_queues name messages consumers

    Las dos colas amq.gen-* ya no aparecen. Si el exchange era durable, sigue existiendo sin bindings.

  5. Sustituye una cola por una durable: declara demo.permanente, bíndala, publica con el consumidor desconectado y reconéctalo. Verás el backlog. Compara con lo que ocurrió con la exclusiva.

Comprobación final

En la management UI, la pestaña Exchanges muestra cuántos bindings tiene demo.fanout. Si borras una cola y el número no baja, revisa si estás mirando un exchange cacheado por la UI: recarga antes de concluir.

8 · Reto

🎯 Broadcast sin perder el evento crítico

El taller quiere que catalogo.actualizado llegue a (a) un servicio de caché que no puede perder ningún evento, (b) un índice de búsqueda que puede reconstruirse entero al arrancar, y (c) cualquier número de dashboards efímeros. Además, durante un despliegue convivirán dos versiones del servicio de caché y ninguna debe procesar el evento dos veces.

Diseña la topología con fanout, decide qué colas son durables y cuáles exclusivas, y explica qué ocurre si el publicador arranca antes que los consumidores. Después mide: publica 100 eventos con un dashboard desconectado y calcula cuántos procesa al volver.

Pista: «no perder» y «no duplicar» son problemas distintos. Para lo segundo necesitarás una clave estable y una tabla de idempotencia; el módulo 3 lo cubre.

9 · Resumen

  • Fanout copia cada mensaje a todas las colas bindeadas e ignora la routing key.
  • Una copia por cola: los consumidores de una misma cola se reparten los mensajes.
  • Sin colas bindeadas, el mensaje se descarta; fanout no almacena.
  • Las colas exclusivas con nombre generado son el patrón correcto para suscriptores efímeros; se borran al cerrar la conexión.
  • Si un suscriptor no puede perder eventos, su cola debe ser durable y el mensaje persistente.
  • Fanout y topic con # se parecen, pero topic permite mezclar suscripciones totales y parciales en el mismo exchange.

10 · Preguntas frecuentes

¿Puedo usar la routing key para filtrar en un fanout?

No. Fanout la ignora por completo, tanto al publicar como al bindear. Si necesitas filtro, usa topic (patrones) o direct (igualdad). La única forma de «filtrar» con fanout es no bindear la cola, lo que equivale a no suscribirse.

¿Qué diferencia hay entre exclusive y autoDelete?

exclusive ata la cola a la conexión que la declaró: solo esa conexión puede consumirla y se borra al cerrarse. autoDelete la borra cuando se va el último consumidor, aunque la conexión siga viva. Para un suscriptor por proceso, exclusive es lo habitual; autoDelete encaja con colas de nombre estable compartidas por consumidores que van y vienen.

Si tengo dos instancias del mismo servicio, ¿ambas reciben cada evento?

Solo si cada instancia tiene su propia cola. Si ambas consumen la misma cola, compiten y cada mensaje va a una de las dos. Para un servicio con réplicas que deben repartirse el trabajo, una cola compartida es lo correcto; para un evento que cada instancia debe ver (por ejemplo, invalidar una caché local), una cola por instancia.

¿Fanout es más rápido que topic?

Su routing es más barato porque no evalúa patrones, pero el coste dominante suele ser el número de copias y la persistencia, no el matching. La razón para elegir fanout no es el rendimiento: es que el diseño quiere broadcast sin selección.

¿Cómo evito que un dashboard que se reconecta pierda eventos?

Con una cola durable y un mensaje persistente, el dashboard puede recuperar el backlog al volver. Si aceptas perder lo ocurrido mientras estaba cerrado, la cola exclusiva es más limpia. No hay una respuesta única: es una decisión de producto sobre qué significa «perderse un evento».
