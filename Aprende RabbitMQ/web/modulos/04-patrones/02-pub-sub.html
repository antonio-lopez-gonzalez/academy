Pub/sub

Módulo 4 · Patrones 🕐 30 minutos

1 · Introducción

El taller acaba de confirmar un pedido. A partir de ese hecho, tres áreas tienen trabajo: facturación emite la factura, inventario reserva el stock y auditoría registra la traza. Si publicas pedido.creado en una sola cola, el broker entrega el evento a uno de los tres consumidores: los otros dos nunca se enteran. No es un fallo de RabbitMQ; es el contrato de una cola.

El patrón pub/sub resuelve esto con un exchange fanout y una cola por consumidor. El productor publica una vez y no sabe quién escucha; cada servicio tiene su propia cola, su propio ritmo, su propio backlog y su propio dead-letter exchange. Añadir un cuarto interesado (por ejemplo, notificaciones) es declarar una cola y un binding: no se toca al productor ni a los demás consumidores.

La diferencia con una work queue es conceptual, no de API. En una work queue los consumidores comparten el trabajo y cada mensaje se procesa una vez. En pub/sub cada consumidor recibe su propia copia del evento y lo procesa para sí. Confundir ambos patrones produce el error más caro de esta lección: una única cola para varios servicios.

Por qué existe esta lección

Los eventos de dominio son la forma habitual de desacoplar servicios, pero «desacoplar» no significa «publicar y olvidar». Hay que decidir qué pasa si un consumidor está caído, si la cola es durable, cuánto se retiene un evento y quién es dueño de cada cola. Esas decisiones son el contenido real del patrón.

2 · Teoría

Fanout: el exchange copia, no elige

Un exchange fanout ignora la routing key y entrega una copia a cada cola vinculada. El desacoplamiento está en el binding: el productor solo conoce el nombre del exchange.

                          pedido.creado
                                |
                                v
                   +----------------------------+
                   | exchange taller.eventos    |
                   | type: fanout               |
                   +---+----------+----------+--+
                       |          |          |
          binding ---- +          |          + ---- binding
                       |          |          |
                       v          v          v
             +--------------+ +-----------+ +--------------+
             | facturacion. | | inventario.| | auditoria.   |
             | pedido-creado| | pedido-... | | pedido-...   |
             | (quorum)     | | (quorum)   | | (quorum)     |
             +------+-------+ +-----+-----+ +------+-------+
                    |               |              |
                    v               v              v
              facturación      inventario       auditoría
              (su ritmo)       (su ritmo)       (su ritmo)

  Un publish -> tres copias independientes. Cada cola falla o se retrasa por su cuenta.

Cada cola es un buffer independiente. Si auditoría está en mantenimiento, su backlog crece y nadie más se entera; facturación sigue procesando. Esa independencia es la ventaja y también la responsabilidad: nadie va a avisarte de que la cola de auditoría lleva tres días creciendo salvo que la monitorices.

Fanout no es topic

FanoutTopic
Routing keySe ignoraSe compara con el patrón del binding
Casos de usoEventos que interesan a todos; difusión simpleFiltrar por tipo o área (pedido.*, #.creado)
AcoplamientoMáximo: todos reciben todoEl consumidor elige qué le importa
CosteUna copia por cola vinculadaUna copia por cola que case

Si los tres consumidores necesitan todos los pedidos, fanout es correcto. Si auditoría solo quiere pedido.cancelado, un topic exchange evita copias inútiles. La lección Topic: rutas con comodines cubre el filtrado.

Cola durable frente a cola efímera

«Suscribirse» no es una bandera del consumidor: es declarar una cola y vincularla. La durabilidad de esa cola decide qué ocurre cuando el servicio está caído.

ConfiguraciónDeclaraciónComportamiento
Durable { durable: true, arguments: { 'x-queue-type': 'quorum' } } Sobrevive a reinicios del broker; acumula eventos mientras el consumidor está caído. Es la opción para eventos de negocio.
Temporal exclusiva { exclusive: true, autoDelete: true } Vive mientras viva la conexión que la declaró. Al desconectarse, se borra con todo su contenido. Para telemetría, UIs o suscripciones best-effort.
Auto-delete con nombre { durable: true, autoDelete: true } Se borra cuando se va el último consumidor. Peligrosa: si nadie se conecta nunca, la cola queda vacía pero viva; si todos se van, se pierde el backlog.

Las quorum queues no pueden ser exclusivas ni auto-delete: son durables por diseño. Si usas una quorum para eventos críticos, el ciclo de vida lo controlas tú, no la conexión del consumidor.

Dar de baja una suscripción

La baja tiene dos niveles y conviene no mezclarlos:

  1. Dejar de consumir: channel.cancel(consumerTag). La cola y sus mensajes siguen ahí. Es lo que quieres en un despliegue: el servicio para de procesar, pero no pierde lo pendiente.
  2. Eliminar la suscripción: además de cancelar, channel.deleteQueue(nombre) y eliminar el binding. Esto borra el backlog y los eventos futuros dejan de acumularse. Es una decisión de negocio, no una limpieza técnica.

Borrar la cola no «desuscribe» al consumidor que sigue vivo

Si otro proceso tiene un consumidor sobre esa cola, borrarla provoca un consumer cancel (el callback recibe null) y el cliente debe reaccionar. Cancelar consumidores y borrar colas son operaciones coordinadas, no un DELETE silencioso.

El sobre del evento

Un evento no es solo el payload. Sin metadatos no puedes depurar, deduplicar ni versionar. Un sobre mínimo:

{
  "eventId": "evt-01J9Z8K3",
  "type": "pedido.creado",
  "version": 1,
  "occurredAt": "2026-11-05T09:14:22.318Z",
  "correlationId": "req-7f3a",
  "data": { "pedidoId": "ped-8831", "clienteId": "cli-204", "total": 149.9 }
}

El eventId sirve para deduplicar en cada consumidor; correlationId permite seguir la estela desde la petición original hasta la factura; version permite evolucionar el esquema sin romper a los suscriptores antiguos. El messageId de AMQP puede llevar el eventId, pero la deduplicación debe usar el identificador del evento, no un valor que el broker pueda regenerar.

Quién sostiene la garantía

GarantíaQuiénCómo
El evento llega al exchangeProductor + brokerPublisher confirm y exchange durable
Hay una copia por suscriptorBrokerUna cola vinculada por consumidor; fanout copia al publicar
La copia sobrevive si el consumidor está caídoBrokerCola durable y mensaje persistente
El evento se procesa al menos una vezConsumidorack manual tras el efecto; redelivery si falla
No se duplica el efectoConsumidorDeduplicación por eventId

3 · Ejemplo mínimo

Un fanout y dos colas. El productor publica un evento; los dos consumidores reciben una copia. Garantía: cada cola recibe el evento si existe en el momento de publicar; las colas son durables, así que el que esté desconectado lo encontrará al volver.

Productor (emitir.mjs):

import amqp from 'amqplib';

const conn = await amqp.connect('amqp://guest:guest@localhost:5672');
const ch = await conn.createConfirmChannel();

await ch.assertExchange('taller.eventos', 'fanout', { durable: true });
ch.publish(
  'taller.eventos',
  '',                                    // fanout ignora la routing key
  Buffer.from(JSON.stringify({ pedidoId: 'ped-8831' })),
  { persistent: true, contentType: 'application/json', messageId: 'evt-001' },
);
await ch.waitForConfirms();
await ch.close();
await conn.close();

Consumidor (escuchar.mjs), con el nombre de cola como argumento:

import amqp from 'amqplib';

const cola = process.argv[2];               // facturacion.pedido-creado | inventario.pedido-creado
const conn = await amqp.connect('amqp://guest:guest@localhost:5672');
const ch = await conn.createChannel();

await ch.assertExchange('taller.eventos', 'fanout', { durable: true });
await ch.assertQueue(cola, {
  durable: true,
  arguments: { 'x-queue-type': 'quorum' },
});
await ch.bindQueue(cola, 'taller.eventos', '');   // fanout: binding sin clave
await ch.prefetch(10);

await ch.consume(cola, (msg) => {
  if (!msg) return;
  console.log(cola, '<-', msg.content.toString());
  ch.ack(msg);
}, { noAck: false });

Arranca dos consumidores con nombres distintos y publica una vez:

node escuchar.mjs facturacion.pedido-creado
node escuchar.mjs auditoria.pedido-creado
node emitir.mjs
facturacion.pedido-creado <- {"pedidoId":"ped-8831"}
auditoria.pedido-creado   <- {"pedidoId":"ped-8831"}

Dos colas, dos copias, un solo publish. Si arrancas un tercer consumidor con el mismo nombre de cola, no recibirá una copia extra: competirá con el primero por los mismos mensajes. El nombre de la cola es la identidad de la suscripción.

4 · Ejemplo real

El taller publica pedido.creado desde la API. Tres servicios se suscriben con colas propias y políticas propias:

SuscriptorColaQué haceSi se cae
Facturaciónfacturacion.pedido-creadoEmite factura y envía emailAcumula eventos; al volver, factura el backlog
Inventarioinventario.pedido-creadoReserva stock y descuenta unidadesAcumula; el stock puede quedar desfasado hasta que se recupere
Auditoríaauditoria.pedido-creadoGuarda traza inmutable durante 90 díasAcumula; la traza se escribe con retraso, pero no se pierde

La topología se declara en un módulo compartido para que productor y consumidores no discrepen. Una declaración incompatible (otro tipo de exchange, otra durabilidad, otros argumentos) cierra el canal con PRECONDITION_FAILED.

// topologia.mjs — la usan la API y los tres workers
export async function declarar(ch) {
  await ch.assertExchange('taller.eventos', 'fanout', { durable: true });
  await ch.assertExchange('taller.dlx', 'direct', { durable: true });

  await ch.assertQueue('pedidos.fallidos', {
    durable: true,
    arguments: { 'x-queue-type': 'quorum' },
  });
  await ch.bindQueue('pedidos.fallidos', 'taller.dlx', 'pedido.fallido');

  for (const cola of [
    'facturacion.pedido-creado',
    'inventario.pedido-creado',
    'auditoria.pedido-creado',
  ]) {
    await ch.assertQueue(cola, {
      durable: true,
      arguments: {
        'x-queue-type': 'quorum',
        'x-dead-letter-exchange': 'taller.dlx',
        'x-dead-letter-routing-key': 'pedido.fallido',
        'x-delivery-limit': 8,
      },
    });
    await ch.bindQueue(cola, 'taller.eventos', '');
  }
}

Cada worker consume solo su cola y decide su política de reintentos. Facturación puede usar un backoff de 30 s; auditoría, ninguno (si falla la escritura, va a su DLQ y se revisa a mano). Compartir una cola obligaría a compartir también esas decisiones, y ahí empieza el acoplamiento que el patrón pretendía evitar.

El productor publica con confirm y con un sobre completo:

const evento = {
  eventId: crypto.randomUUID(),
  type: 'pedido.creado',
  version: 1,
  occurredAt: new Date().toISOString(),
  correlationId: req.id,
  data: { pedidoId, clienteId, total },
};

ch.publish('taller.eventos', '', Buffer.from(JSON.stringify(evento)), {
  persistent: true,
  contentType: 'application/json',
  messageId: evento.eventId,
  correlationId: evento.correlationId,
  type: evento.type,
});
await ch.waitForConfirms();

Fanout sin colas vinculadas descarta el evento

Si nadie ha declarado todavía las colas, el exchange no tiene a quién entregar y el mensaje se pierde, aunque el confirm sea positivo: el broker confirma que lo recibió, no que lo enrutó. Publica mandatory: true y escucha basic.return, o usa un alternate exchange, si un evento sin suscriptores es un error de despliegue. Lo vimos en Headers y alternate exchange.

5 · Buenas prácticas

HazEvitaPor qué
Una cola durable por servicio consumidor Una sola cola compartida por varios servicios En una cola compartida los mensajes se reparten; cada servicio ve solo una parte.
Nombrar la cola con el consumidor: servicio.evento Nombres genéricos como eventos o cola1 El nombre identifica la suscripción; facilita permisos, métricas y borrado seguro.

6 · Errores habituales

1. Una cola para tres servicios

Mal — creer que todos reciben el evento 
taller.eventos (fanout) -> cola "eventos" -> facturacion | inventario | auditoria

Cada mensaje va a UNO de los tres. Los otros dos no lo ven nunca.
Bien — una cola por consumidor 
taller.eventos (fanout) -> facturacion.pedido-creado -> facturacion
                       -> inventario.pedido-creado  -> inventario
                       -> auditoria.pedido-creado   -> auditoria

El fanout copia por cola, no por consumidor. Si los tres procesos comparten cola, compiten y el evento se procesa una sola vez. Es una work queue disfrazada de pub/sub.

2. Cola efímera para eventos que no se pueden perder

Mal — suscripción atada a la conexión 
await ch.assertQueue('', { exclusive: true, autoDelete: true });
await ch.bindQueue(q.queue, 'taller.eventos', '');
Bien — cola durable con nombre estable 
await ch.assertQueue('facturacion.pedido-creado', {
  durable: true,
  arguments: { 'x-queue-type': 'quorum' },
});

La cola exclusiva desaparece al cerrar la conexión, con todo lo que tenía dentro. Un despliegue de 30 segundos borra los eventos de ese intervalo. Para negocio, siempre durable; para una vista en vivo, efímera está bien.

3. Publicar antes de que existan las colas

Mal — confiar en el confirm como entrega 
ch.publish('taller.eventos', '', body, { persistent: true });
await ch.waitForConfirms();   // ✅ el broker lo tiene… pero no había bindings
Bien — declarar topología y detectar el retorno 
await declarar(ch);           // exchange + colas + bindings
ch.publish('taller.eventos', '', body, { persistent: true, mandatory: true });
ch.on('return', (msg) => {
  console.error('sin ruta:', msg.fields.routingKey);   // alerta de despliegue
});

Un exchange sin bindings acepta y descarta. El confirm dice «recibido», no «enrutado». En un arranque en frío, el orden de despliegue importa: primero los consumidores, después el productor; o mejor, declara la topología de forma idempotente en ambos.

4. Tratar un evento como una orden

Mal — el productor decide qué debe hacer el otro 
{ "accion": "reservarStock", "pedidoId": "ped-8831" }
Bien — describir el hecho ocurrido 
{ "type": "pedido.creado", "data": { "pedidoId": "ped-8831", "lineas": [] } }

Un evento cuenta algo que ya pasó; una orden exige una acción concreta. Si el productor nombra la acción, cada cambio en los consumidores obliga a cambiar al productor y el acoplamiento vuelve por la puerta de atrás. Los comandos existen, pero van a una cola con un consumidor concreto, no a un fanout.

7 · Ejercicio guiado

Objetivo: comprobar que cada suscriptor recibe su copia, que un consumidor caído conserva su backlog y que compartir cola rompe el patrón.

  1. Declara el fanout y las tres colas. Usa topologia.mjs del ejemplo real o la management UI. Comprueba los bindings: 
    docker exec rabbitmq rabbitmqctl list_bindings source_name destination_name routing_key
    taller.eventos  facturacion.pedido-creado
taller.eventos  inventario.pedido-creado
taller.eventos  auditoria.pedido-creado
  2. Arranca facturación y auditoría, pero deja inventario sin arrancar. Publica un evento y observa los dos consumidores activos. 
    node escuchar.mjs facturacion.pedido-creado
node escuchar.mjs auditoria.pedido-creado
node emitir.mjs
  3. Comprueba el backlog del ausente: 
    docker exec rabbitmq rabbitmqctl list_queues name messages_ready consumers
    auditoria.pedido-creado    0  1
facturacion.pedido-creado  0  1
inventario.pedido-creado   1  0

    El evento está esperando a inventario; los otros dos ya lo procesaron. Esa es la independencia de consumidores.

  4. Arranca inventario y verifica que recibe el evento pendiente, no los ya procesados por los demás. Después publica dos eventos más y comprueba que cada cola tiene su propia copia.
  5. Rompe el patrón a propósito: arranca un cuarto consumidor con el nombre facturacion.pedido-creado. Publica cuatro eventos y observa cómo se reparten entre los dos procesos de facturación: cada uno recibe una parte, no todos. Ese es el síntoma de una cola compartida.
  6. Simula una baja: cancela el consumidor de auditoría con Ctrl+C y publica un evento. La cola conserva el mensaje. Vuelve a arrancarlo y confirma que lo recibe: la suscripción sobrevivió al proceso porque la cola es durable.

8 · Reto

🎯 Un suscriptor que se une tarde

El equipo de marketing quiere empezar a recibir pedido.creado a partir de hoy, pero también necesita procesar los eventos de los últimos siete días que ya fueron consumidos por los otros servicios. Con fanout y colas durables, ¿puede conseguirlo sin republicar nada?

Diseña dos alternativas: una con RabbitMQ puro y otra que introduzca un almacén de eventos. Para cada una, explica qué garantías ofrece, cuánto cuesta en disco y qué pasa si marketing se cae durante un mes. Después implementa la que consideres correcta y documenta el binding y la retención.

9 · Resumen

  • Pub/sub = exchange fanout + una cola por consumidor; el productor publica una vez y no conoce a los suscriptores.
  • Cada cola recibe su propia copia y evoluciona de forma independiente: backlog, DLQ y ritmo propios.
  • Una cola compartida por varios servicios es una work queue: los mensajes se reparten y cada servicio ve solo una parte.
  • Colas durables para eventos de negocio; exclusivas y auto-delete solo para suscripciones efímeras.
  • El sobre del evento (eventId, type, version, occurredAt, correlationId) hace posible deduplicar, trazar y evolucionar.
  • El confirm acredita la entrada al broker; si no hay bindings, el mensaje se descarta igualmente.

10 · Preguntas frecuentes

¿No es más simple usar una cola por servicio pero con el mismo nombre de binding?

El binding no tiene nombre: es la pareja exchange-cola. Lo que debe ser único es la cola. Puedes vincular varias colas al mismo fanout sin problema; lo que no puedes es que dos servicios consuman de la misma cola esperando copias distintas.

¿Cuánto tiempo guarda RabbitMQ un evento si el consumidor está caído?

Indefinidamente, mientras la cola exista y no tenga TTL ni límite de longitud. Eso puede llenar el disco. Configura x-message-ttl, x-max-length o una política y decide qué hacer con lo descartado. La retención es una decisión de negocio: «siete días de eventos» se implementa con TTL, no con una promesa.

Si un consumidor procesa el evento y cae antes del ack, ¿lo recibe otra vez?

Sí. El broker no sabe que el efecto se produjo; solo sabe que no hubo confirmación. Por eso cada consumidor debe deduplicar por eventId o por clave de negocio. Es el precio de at-least-once, y es más barato que perder eventos.

¿Puedo usar un topic exchange para pub/sub?

Sí, y suele ser mejor cuando los suscriptores solo quieren un subconjunto. La diferencia es que el topic decide por routing key; el fanout entrega todo a todos. Empieza con fanout si el evento interesa entero a cada servicio; pasa a topic cuando el filtrado sea una necesidad real, no una optimización prematura.

¿Los suscriptores deben compartir el mismo esquema de evento?

Comparten el contrato, no el código. Versiona el sobre, añade campos de forma opcional y no cambies el significado de los existentes. Si un consumidor necesita un campo que no existe, es una versión nueva del evento, no un parche silencioso en el productor.
