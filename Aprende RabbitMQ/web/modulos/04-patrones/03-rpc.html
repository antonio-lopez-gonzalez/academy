RPC sobre mensajería

Módulo 4 · Patrones 🕐 40 minutos

1 · Introducción

El worker de facturación necesita saber cuántas unidades de un SKU quedan antes de aplicar un descuento. Inventario ya existe como servicio, pero no expone HTTP: consume órdenes de una cola. La tentación es abrir un endpoint REST solo para esa llamada, con su autenticación, su cliente y su despliegue. La alternativa es RPC sobre mensajería: enviar una petición a una cola y esperar una respuesta en otra.

El patrón usa dos propiedades AMQP que ya conoces por separado: reply_to (dónde responder) y correlation_id (a qué petición corresponde la respuesta). Con ellas, un cliente puede tener varias peticiones en vuelo sobre una sola cola de respuesta y emparejar cada respuesta con su promesa. Parece sencillo, y lo es; lo difícil es el timeout, la respuesta tardía y el error.

Esta lección insiste en una idea incómoda: RPC sobre colas no es «HTTP con otro transporte». Es un patrón con garantías distintas, latencias distintas y modos de fallo distintos. Usarlo para todo produce sistemas más lentos y más frágiles que una llamada HTTP bien hecha. Usarlo donde encaja —procesos internos sin superficie HTTP, trabajos que necesitan la cola como buffer— resuelve problemas reales.

Por qué existe esta lección

Porque el tutorial clásico de RabbitMQ enseña un cliente RPC de 40 líneas y omite lo que pasa cuando el servidor tarda 30 segundos, cuando la respuesta llega después del timeout o cuando hay 200 peticiones concurrentes. Aquí construimos el cliente completo: correlación, timeout, limpieza y cancelación.

2 · Teoría

El intercambio de mensajes

El cliente publica una petición en una cola de trabajo. El servidor la consume, calcula la respuesta y la publica en la cola indicada por reply_to, copiando el correlation_id. El cliente tiene un consumidor sobre su cola de respuesta que despacha cada mensaje a la promesa correspondiente.

CLIENTE                                       SERVIDOR RPC
   |                                               |
   | 1. assertQueue('', exclusive, autoDelete)      |
   |    -> "amq.gen-Xyz"  (cola de respuesta)       |
   |                                               |
   | 2. publish a "stock.rpc"                       |
   |    reply_to: amq.gen-Xyz                       |
   |    correlation_id: 7f3a-...                    |
   |    expiration: 2000                            |
   |                        -------------------->   |
   |                                               | 3. consume
   |                                               | 4. consultar stock
   |    <--------------------                       |
   | 5. respuesta en amq.gen-Xyz                    |
   |    correlation_id: 7f3a-...                    |
   |    body: { ok: true, stock: 42 }               |
   |                                               |
   | 6. resolver promesa / descartar si expiró      |

El servidor no necesita saber quién preguntó: solo copia reply_to y correlation_id. Eso permite escalar servidores RPC con una sola cola y consumidores en competencia, sin sesiones ni afinidad.

Las cuatro piezas que hacen que funcione

PiezaQuién la ponePara qué
reply_toCliente, en cada peticiónNombre de la cola donde el servidor debe publicar la respuesta
correlation_idCliente, único por peticiónEmparejar la respuesta con la petición correcta
Cola de respuesta exclusiva y auto-deleteCliente, una por conexiónRecibir respuestas sin colisiones y borrarla al desconectar
TimeoutClienteNo esperar para siempre; liberar la promesa y la entrada pendiente

La cola de respuesta se declara una vez por conexión, no una por petición. Si creas una cola por petición, el broker acumula miles de colas efímeras y el coste de declararlas domina la latencia. El correlation_id permite multiplexar todas las peticiones de un cliente sobre esa única cola.

Timeout: el corazón del cliente

Un RPC sin timeout es una fuga de memoria con forma de promesa. Si el servidor está caído, la respuesta nunca llega y el proceso que espera queda colgado. El cliente debe:

  • Registrar la petición en un mapa correlationId -> { resolve, reject, timer } antes de publicar.
  • Arrancar un temporizador al publicar; al vencer, borrar la entrada y rechazar con un error de timeout.
  • Al recibir una respuesta, buscar la entrada; si no existe, es una respuesta tardía y se descarta sin romper nada.
  • Limpiar el temporizador al resolver para no dejar timers vivos.

La petición no se puede «desenviar»

Cuando el cliente hace timeout, el mensaje ya está en la cola o en el servidor. No hay forma de retirarlo. La cancelación es cooperativa: el cliente deja de esperar y el servidor puede mirar una cabecera de deadline antes de empezar trabajo caro. Si el servidor termina y responde, la respuesta se descarta porque ya no hay promesa. Ese trabajo perdido es el coste de no haber medido la latencia.

Respuesta única y errores

Un RPC devuelve una respuesta por petición. Si el servidor publica dos (por un reintento o un bug), la segunda se descarta: la entrada ya no está en el mapa. Para que eso sea seguro, el servidor debe ser idempotente y publicar la respuesta una sola vez por entrega.

Los errores de negocio viajan en el cuerpo, no en el canal:

{ "ok": false, "error": { "code": "SKU_DESCONOCIDO", "message": "El SKU no existe" } }

El canal AMQP solo debe fallar por errores de transporte (cola inexistente, mensaje demasiado grande, permisos). Un nack por «no hay stock» confunde un resultado de negocio con un fallo de infraestructura y acaba en la DLQ equivocada.

amq.rabbitmq.reply-to: el atajo de RabbitMQ

RabbitMQ ofrece una pseudo-cola llamada amq.rabbitmq.reply-to. El cliente la consume en modo noAck y el broker le entrega las respuestas dirigiéndolas a su canal, sin declarar una cola real. Ahorra una declaración y una conexión de retorno.

await ch.consume('amq.rabbitmq.reply-to', onReply, { noAck: true });
ch.publish('', 'stock.rpc', body, {
  replyTo: 'amq.rabbitmq.reply-to',
  correlationId,
});

Es una extensión de RabbitMQ, no parte de AMQP 0-9-1: si mañana cambias de broker o de librería, no está. Además, al ser noAck, una respuesta perdida no se reentrega (el cliente ya tiene el timeout). Para el curso usamos la cola exclusiva explícita porque enseña el mecanismo; en producción, reply-to es una optimización válida si aceptas la dependencia.

Cuándo NO usar RPC sobre colas

SituaciónMejor opciónPor qué
Petición de usuario que espera en HTTPHTTP/gRPC directoLa cola añade un salto, un timeout y un modo de fallo sin aportar nada.
Latencia de milisegundos y servicio disponibleHTTP/gRPCEl RPC por colas pasa por disco y por dos operaciones de broker.
El cliente puede estar horas sin conexiónCola de trabajo + evento de respuestaUna promesa no sobrevive a un reinicio; un mensaje sí.
Necesitas broadcast a varios respondedoresPub/sub o scatter-gatherRPC es 1 a 1; para 1 a N el patrón es otro.
El llamador es un worker sin HTTP y el servidor ya consume colasRPC sobre colasReutilizas la infraestructura y el enrutamiento existentes.

La pregunta decisiva no es «¿puedo?», sino «¿el llamador puede seguir sin la respuesta?». Si la respuesta es sí, no necesitas RPC: necesitas un evento o una tarea. Si es no, pregúntate si HTTP no es simplemente mejor.

3 · Ejemplo mínimo

Un servidor que responde con el stock de un SKU y un cliente que pregunta una vez. Garantía: la petición es at-least-once si el servidor confirma tras calcular; la respuesta es at-most-once (si se pierde, el cliente hace timeout).

Servidor (servidor.mjs):

import amqp from 'amqplib';

const conn = await amqp.connect('amqp://guest:guest@localhost:5672');
const ch = await conn.createChannel();

await ch.assertQueue('stock.rpc', {
  durable: true,
  arguments: { 'x-queue-type': 'quorum' },
});
await ch.prefetch(4);

await ch.consume('stock.rpc', async (msg) => {
  if (!msg) return;
  const { sku } = JSON.parse(msg.content.toString());
  const stock = await inventario.consultar(sku);   // lectura idempotente
  ch.sendToQueue(
    msg.properties.replyTo,
    Buffer.from(JSON.stringify({ ok: true, stock })),
    {
      correlationId: msg.properties.correlationId,
      contentType: 'application/json',
    },
  );
  ch.ack(msg);
}, { noAck: false });

Cliente (cliente.mjs):

import amqp from 'amqplib';
import { randomUUID } from 'node:crypto';

const conn = await amqp.connect('amqp://guest:guest@localhost:5672');
const ch = await conn.createChannel();

const { queue } = await ch.assertQueue('', { exclusive: true, autoDelete: true });
const pendientes = new Map();

await ch.consume(queue, (msg) => {
  if (!msg) return;
  const entrada = pendientes.get(msg.properties.correlationId);
  if (!entrada) return;                    // respuesta tardía: se descarta
  clearTimeout(entrada.timer);
  pendientes.delete(msg.properties.correlationId);
  entrada.resolve(JSON.parse(msg.content.toString()));
}, { noAck: true });

function preguntar(sku, timeoutMs = 2000) {
  const correlationId = randomUUID();
  const respuesta = new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      pendientes.delete(correlationId);
      reject(new Error('timeout de stock.rpc'));
    }, timeoutMs);
    pendientes.set(correlationId, { resolve, reject, timer });
  });

  ch.sendToQueue('stock.rpc', Buffer.from(JSON.stringify({ sku })), {
    replyTo: queue,
    correlationId,
    expiration: String(timeoutMs),        // el broker la descarta si caduca
    contentType: 'application/json',
  });
  return respuesta;
}

console.log(await preguntar('SKU-42'));

Salida: { ok: true, stock: 42 }. Detalles que importan: la cola de respuesta se declara antes de publicar; el consumidor se registra antes de la primera petición; el temporizador se cancela al resolver; y una respuesta con correlationId desconocido se ignora en silencio. Si mueves el clearTimeout fuera del consumidor, el proceso no termina nunca.

4 · Ejemplo real

El worker de facturación pregunta el stock antes de aplicar un descuento por volumen. Si inventario tarda más de 2 segundos, la factura no se bloquea: se aplica la tarifa base y se marca la factura para revisión. El RPC es un enriquecimiento opcional, no una dependencia dura.

async function stockParaFactura(sku) {
  try {
    const r = await preguntar(sku, 2000);
    if (!r.ok) throw new Error(`${r.error.code}: ${r.error.message}`);
    return r.stock;
  } catch (err) {
    logger.warn('stock no disponible; sigo con tarifa base', { sku, err: err.message });
    return null;                            // degradación explícita
  }
}

El servidor RPC comprueba una cabecera de deadline antes de empezar trabajo caro, para no gastar CPU en una respuesta que el cliente ya no espera:

const deadline = Number(msg.properties.headers?.['x-deadline'] ?? 0);
if (deadline && Date.now() > deadline) {
  logger.info('petición caducada, se descarta', { sku });
  ch.ack(msg);                              // no es un fallo: ya no interesa
  return;
}

Y devuelve errores de negocio con un código estable, para que el cliente decida sin parsear mensajes:

try {
  const stock = await inventario.consultar(sku);
  responder(msg, { ok: true, stock });
} catch (err) {
  if (err instanceof SkuDesconocido) {
    responder(msg, { ok: false, error: { code: 'SKU_DESCONOCIDO', message: err.message } });
  } else {
    ch.nack(msg, false, true);              // fallo transitorio: reintentar
    return;
  }
}
ch.ack(msg);

function responder(msg, payload) {
  ch.sendToQueue(msg.properties.replyTo, Buffer.from(JSON.stringify(payload)), {
    correlationId: msg.properties.correlationId,
    contentType: 'application/json',
  });
}

El cliente registra cada timeout y cada respuesta tardía como métrica. Un p99 de RPC que roza el timeout no se arregla subiendo el timeout: se arregla midiendo por qué el servidor tarda. Y si el servidor se satura, la cola de peticiones crece: es la señal de que el patrón está absorbiendo un pico, no de que haya que añadir más promesas.

Cuidado con el expiration en la petición

expiration hace que el broker descarte la petición si nadie la consume a tiempo. Es útil para no procesar trabajo obsoleto, pero un valor igual al timeout del cliente puede descartar peticiones que iban a responderse justo a tiempo. Deja un margen (timeout del cliente 2500 ms, expiration 5000 ms) o no lo uses y confía en la comprobación de deadline del servidor.

5 · Buenas prácticas

HazEvitaPor qué
Una cola de respuesta exclusiva por conexión Una cola por petición o un nombre fijo compartido La primera acumula colas; la segunda hace que varios clientes compitan por respuestas ajenas.
correlation_id único con randomUUID() Reutilizar un contador o el messageId del broker Es la clave del mapa de promesas; dos peticiones con el mismo id se pisan.

Descartar respuestas sin entrada pendiente Lanzar una excepción al recibir una respuesta tardía La respuesta tardía es normal; el cliente ya decidió seguir sin ella.
Errores de negocio en el cuerpo nack o cerrar el canal por «sin stock» Un resultado esperado no es un fallo de infraestructura.
Servidores RPC idempotentes Confiar en que la petición llega una sola vez El broker puede reentregar si el servidor muere antes del ack.
Medir latencia, timeouts y cola de peticiones Subir el timeout para «arreglar» los fallos El timeout alto solo tapa la causa y multiplica el trabajo desperdiciado.

6 · Errores habituales

1. Cola de respuesta compartida con nombre fijo

Mal — todos los clientes escuchan la misma cola 
await ch.assertQueue('respuestas.rpc', { durable: true });
await ch.consume('respuestas.rpc', onReply);
Bien — cola exclusiva por conexión 
const { queue } = await ch.assertQueue('', { exclusive: true, autoDelete: true });
await ch.consume(queue, onReply, { noAck: true });

Con una cola compartida, las respuestas se reparten entre clientes y cada uno recibe respuestas de peticiones ajenas. El correlationId no salva el diseño: el mensaje ya se consumió y el cliente legítimo nunca lo verá.

2. Ignorar el correlationId al responder

Mal — responder sin correlación 
ch.sendToQueue(msg.properties.replyTo, Buffer.from(JSON.stringify(res)));
Bien — copiar el identificador 
ch.sendToQueue(msg.properties.replyTo, body, {
  correlationId: msg.properties.correlationId,
});

Sin correlación, el cliente no puede saber a qué petición pertenece la respuesta. Con dos peticiones en vuelo, resolvería la promesa equivocada. El servidor debe tratar replyTo y correlationId como un contrato, no como un detalle opcional.

3. RPC sin timeout

Mal — esperar para siempre 
const res = await new Promise((resolve) => {
  pendientes.set(id, { resolve });
  ch.sendToQueue('stock.rpc', body, { replyTo: queue, correlationId: id });
});
Bien — timeout, rechazo y limpieza 
const timer = setTimeout(() => {
  pendientes.delete(id);
  reject(new Error('timeout'));
}, 2000);
pendientes.set(id, { resolve, timer });

Si el servidor está caído, la promesa nunca se resuelve, la entrada del mapa queda para siempre y el proceso acumula trabajo muerto. El timeout no es una pesimización: es parte del contrato.

4. Usar RPC para todo

Mal — consultar el catálogo desde el frontend por colas 
navegador -> API -> cola -> servicio -> cola de respuesta -> API -> navegador

Dos saltos de broker, dos timeouts y una conexión AMQP por usuario.
Bien — HTTP para lo síncrono, colas para el trabajo 
navegador -> API -> servicio (HTTP/gRPC)          consulta interactiva
API -> cola de trabajos -> worker                 factura, email, PDF

RPC sobre colas brilla entre procesos internos que ya usan el broker. Para una petición de usuario con latencia ajustada, HTTP o gRPC es más simple, más rápido y más fácil de observar. Elegir colas «porque ya tenemos RabbitMQ» es acoplar la arquitectura a una herramienta.

7 · Ejercicio guiado

Objetivo: ver la correlación, el timeout, la respuesta tardía y la cola efímera desaparecer al cerrar el cliente.

  1. Arranca el servidor y comprueba la cola de peticiones: 
    node servidor.mjs
docker exec rabbitmq rabbitmqctl list_queues name messages_ready consumers

    Salida esperada: stock.rpc 0 1.

  2. Lanza el cliente y verifica la respuesta { ok: true, stock: 42 }. En otra terminal, lista las colas mientras el cliente sigue vivo: 
    docker exec rabbitmq rabbitmqctl list_queues name messages consumers | grep amq.gen

    Verás una cola amq.gen-... con un consumidor: es la cola de respuesta exclusiva.

  3. Cierra el cliente (Ctrl+C) y vuelve a listar. La cola amq.gen-... ya no está: exclusive y autoDelete la borraron al cerrar la conexión.
  4. Simula un servidor caído: para el servidor, arranca el cliente y mide cuánto tarda en fallar. Debe rechazar con timeout de stock.rpc tras ~2 s, no quedarse colgado. Comprueba que el mensaje queda en stock.rpc si el expiration aún no venció.
  5. Prueba la respuesta tardía: añade 3 s de sleep en el servidor y deja el timeout del cliente en 2 s. El cliente falla por timeout; cuando el servidor responde, el mensaje llega a la cola de respuesta y el cliente lo descarta sin error. Repite con dos peticiones simultáneas y comprueba que cada una recibe su stock correcto.
  6. Escala servidores: arranca dos instancias de servidor.mjs. Las peticiones se reparten; cada respuesta vuelve al cliente correcto porque viaja a su cola efímera. Anota qué pasaría si ambos publicaran la respuesta sin correlationId.

Comprobación final

Durante el ejercicio, la cola de peticiones debe volver a messages_ready = 0 y messages_unacknowledged = 0 después de cada respuesta. Si unacked se queda alto, el servidor está olvidando el ack en alguna rama del try/catch.

8 · Reto

🎯 Cancelación cooperativa de verdad

El cliente hace timeout a los 2 segundos, pero el servidor sigue calculando durante 30. Implementa una cancelación cooperativa: el cliente debe enviar una señal de cancelación y el servidor debe abandonar el trabajo si aún no ha terminado. No vale con que el servidor termine y el cliente descarte la respuesta.

Diseña el protocolo: ¿una cola de cancelación por petición, un exchange de control, una cabecera con deadline? ¿Qué pasa si la cancelación llega después de que el servidor ya publicó la respuesta? ¿Cómo evitas que un cliente malicioso cancele peticiones ajenas?

Pista: el servidor puede comprobar el deadline entre pasos del cálculo, igual que un AbortSignal. Para la autorización, piensa en incluir el correlationId y el identificador del cliente en la señal, y valida ambos.

9 · Resumen

  • RPC sobre colas = petición a una cola + respuesta a reply_to, correlacionada por correlation_id.
  • La cola de respuesta es exclusiva y auto-delete, una por conexión, no una por petición.
  • El cliente necesita timeout, mapa de pendientes y descarte de respuestas tardías; sin eso, el patrón filtra memoria.
  • Una sola respuesta por petición; el servidor debe ser idempotente porque la petición puede reentregarse.
  • Los errores de negocio viajan en el cuerpo; el nack se reserva para fallos transitorios.
  • Si el llamador puede seguir sin la respuesta, no uses RPC; si la necesita ya y hay red, probablemente HTTP sea mejor.

10 · Preguntas frecuentes

¿RPC sobre colas es un antipatrón?

No por sí mismo; lo es usarlo donde no encaja. Entre procesos internos que ya hablan AMQP, con cargas variables y necesidad de desacoplar el despliegue, es razonable. Para peticiones interactivas con latencia ajustada, añade saltos y modos de fallo sin beneficio. La decisión depende del llamador, no de la moda.

¿Por qué no crear una cola de respuesta por petición?

Porque cada assertQueue y cada deleteQueue cuesta una ida y vuelta al broker, y con miles de peticiones por minuto el broker acumula colas efímeras. Una cola por conexión con correlationId multiplexa todas las peticiones y es más barata y más fácil de limpiar.

¿Qué pasa si el servidor responde después del timeout?

La respuesta llega a la cola exclusiva del cliente, el consumidor busca el correlationId, no lo encuentra y la descarta. No es un error: es el comportamiento esperado. Si esto ocurre a menudo, el problema es la latencia del servidor, no el cliente.

¿Puedo usar amq.rabbitmq.reply-to en producción?

Sí, es una extensión estable de RabbitMQ y evita declarar la cola de respuesta. A cambio, acoplas el cliente a RabbitMQ y pierdes la reentrega de la respuesta (noAck obligatorio). Si el cliente ya tiene timeout, la pérdida de una respuesta no cambia el resultado: se traduce en un timeout igual.

¿Cómo escalo servidores RPC sin que un cliente reciba la respuesta de otro?

Con una sola cola de peticiones y varios consumidores en competencia. Cada petición lleva su reply_to y su correlation_id; el servidor que la tome responde a la cola exclusiva de ese cliente. No hay estado compartido entre servidores, así que escalar es añadir procesos.
