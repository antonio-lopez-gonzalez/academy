Instalación y management UI

Módulo 0 · Fundamentos 🕐 30 minutos

1 · Introducción

RabbitMQ es un broker escrito en Erlang. Instalarlo a mano implica gestionar Erlang/OTP, el servicio, los plugins, las rutas de datos y las actualizaciones. Para aprender el protocolo no necesitas nada de eso: la imagen oficial de Docker trae el broker, Erlang y el plugin de management en una sola pieza reproducible.

En esta lección levantamos RabbitMQ 4.4 con la imagen rabbitmq:4-management, abrimos la consola web, comprobamos el estado con rabbitmqctl y hablamos con la HTTP management API. También veremos por qué la UI es una herramienta de observación y no la fuente de verdad de tu infraestructura.

Por qué Docker y no una instalación nativa

El curso asume que todos los alumnos ejecutan los mismos comandos en Windows, macOS y Linux. Docker elimina la variable «en mi máquina funciona»: misma imagen, misma versión, mismos puertos. Si ya tienes un broker corporativo, los conceptos y la API son los mismos; solo cambian las credenciales y el host.

2 · Teoría

Qué incluye la imagen

La etiqueta 4-management significa «RabbitMQ 4.x con el plugin rabbitmq_management habilitado». Sin ese sufijo tendrías el broker y el protocolo AMQP, pero no la consola ni la HTTP API en el puerto 15672.

EtiquetaQué traeCuándo usarla
rabbitmq:4-managementBroker 4.x + management UI + HTTP API.Desarrollo y operación con observabilidad. Es la del curso.
rabbitmq:4Solo broker y protocolos; sin UI.Producción mínima o cuando el plugin se habilita aparte.
rabbitmq:latestLa última versión publicada, sin garantía de compatibilidad.Nunca en un curso ni en producción: fija la versión.

La imagen escucha AMQP en 5672 y la management API/UI en 15672. Los datos viven en /var/lib/rabbitmq; si no montas un volumen ahí, un contenedor nuevo empieza vacío.

PuertoProtocoloPara qué
5672AMQP 0-9-1Productores y consumidores (amqplib).
15672HTTPManagement UI y HTTP API.
4369 / 25672EPMD / Erlang distributionDescubrimiento y comunicación entre nodos; solo en clúster.

El contenedor y el host

TU MÁQUINA                                CONTENEDOR rabbitmq
┌───────────────────────────┐             ┌──────────────────────────────┐
│ localhost:5672            │────────────▶│ amqp listener :5672          │
│ localhost:15672           │────────────▶│ http listener :15672         │
│                           │             │                              │
│ volumen rabbitmq-data     │◀───────────▶│ /var/lib/rabbitmq            │
└───────────────────────────┘             └──────────────────────────────┘

Sin volumen, el segundo bloque borra el primero.

El mapeo -p 5672:5672 publica el puerto del contenedor en el host. Si el 5672 ya está ocupado (otro RabbitMQ, un servicio local), Docker falla al arrancar; cambia el puerto del host (-p 5673:5672) y ajusta la URL de conexión.

guest/guest solo desde localhost

La imagen crea el usuario guest con contraseña guest y permisos totales sobre el vhost /. Por seguridad, RabbitMQ solo permite a guest conectarse desde loopback (127.0.0.1 o ::1). Si publicas el puerto en una interfaz remota o usas el contenedor desde otra máquina, verás ACCESS_REFUSED.

guest/guest es para tu portátil

No abras 15672 a internet con guest/guest ni lo uses en producción. En el módulo 6 crearemos usuarios, vhosts y permisos acotados; aquí usamos guest porque todo corre en localhost.

La UI es excelente para observar: ver una cola crecer, inspeccionar un mensaje, comprobar si un consumidor está conectado. Es mala para definir: un clic no queda en Git, no pasa revisión y no se reproduce en staging.

Comandos que usarás una y otra vez

# Estado general del nodo
docker exec rabbitmq rabbitmqctl status

# Colas: tipo, mensajes listos, no confirmados y consumidores
docker exec rabbitmq rabbitmqctl list_queues name type messages messages_ready messages_unacknowledged consumers

# Exchanges y bindings
docker exec rabbitmq rabbitmqctl list_exchanges name type durable
docker exec rabbitmq rabbitmqctl list_bindings source_name destination_name routing_key

# Conexiones y canales
docker exec rabbitmq rabbitmqctl list_connections name user peer_host state
docker exec rabbitmq rabbitmqctl list_channels number consumer_count messages_unacknowledged

# Vhosts
docker exec rabbitmq rabbitmqctl list_vhosts name

rabbitmqctl habla con el nodo por distribución Erlang, no por AMQP. Por eso funciona aunque el puerto 5672 esté saturado y por eso debes ejecutarlo dentro del contenedor (o en el host del nodo, no en tu portátil).

Health checks: «arrancado» no es «listo»

Un puerto abierto no garantiza que el broker pueda aceptar trabajo. El proceso puede estar arrancando, el disco lleno o una alarma activa. RabbitMQ ofrece rabbitmq-diagnostics para preguntar por el estado real:

docker exec rabbitmq rabbitmq-diagnostics -q ping
docker exec rabbitmq rabbitmq-diagnostics -q check_running
docker exec rabbitmq rabbitmq-diagnostics -q check_local_alarms

ping responde cuando el nodo está vivo y acepta comandos; check_running comprueba que la aplicación RabbitMQ está corriendo; check_local_alarms falla si hay alarmas de memoria o disco. Para un healthcheck de Docker, ping es el equilibrio razonable entre rapidez y significado.

Por qué la UI no es la fuente de verdad

ProblemaConsecuenciaAlternativa
Un clic no queda en el historial.Nadie sabe quién creó la cola ni con qué argumentos.Declarar en código o en un script versionado.
Dev, staging y prod divergen.Funciona en local y falla al desplegar.La misma topología declarativa en todos los entornos.
No hay revisión ni tests.Un cambio de tipo o de binding rompe consumidores.Pull request + verificación de topología.
Se puede borrar una cola con mensajes.Pérdida irreversible si no hay backup.Permisos acotados y operaciones destructivas fuera de la UI.

La UI sigue siendo útil: sirve para verificar que lo que declaraste existe y para investigar un incidente. La diferencia es quién manda: el código declara, la UI observa.

3 · Ejemplo mínimo

Levanta el broker con un comando, con volumen para no perder datos y con los dos puertos publicados:

docker run -d --name rabbitmq \
  -p 5672:5672 \
  -p 15672:15672 \
  -v rabbitmq-data:/var/lib/rabbitmq \
  rabbitmq:4-management

Espera a que esté listo y comprueba el estado:

docker exec rabbitmq rabbitmq-diagnostics -q ping
docker exec rabbitmq rabbitmqctl status

Abre http://localhost:15672 y entra con guest / guest. En Overview verás la versión, el nodo y los totales; en Queues no habrá nada todavía.

Si el puerto está ocupado

Docker mostrará bind: address already in use. Cambia solo el lado del host: -p 5673:5672 -p 15673:15672. La URL de AMQP será amqp://guest:guest@localhost:5673 y la UI http://localhost:15673. El puerto interno del contenedor no se toca.

4 · Ejemplo real

Para el taller usamos Compose: la configuración queda en un archivo, se levanta con un comando y el healthcheck evita que los servicios arranquen antes de que el broker esté listo.

services:
  rabbitmq:
    image: rabbitmq:4-management
    container_name: rabbitmq
    ports:
      - "5672:5672"
      - "15672:15672"
    volumes:
      - rabbitmq-data:/var/lib/rabbitmq
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 20s

volumes:
  rabbitmq-data:

docker compose up -d
docker compose ps
docker compose logs -f rabbitmq

NAME       IMAGE                   SERVICE    STATUS                   PORTS
rabbitmq   rabbitmq:4-management   rabbitmq   Up 25 seconds (healthy)  0.0.0.0:5672->5672/tcp, 0.0.0.0:15672->15672/tcp

El estado (healthy) significa que el healthcheck se ejecutó y devolvió 0. Sin él, un depends_on solo espera a que el contenedor exista, no a que el broker acepte conexiones.

curl -s -u guest:guest http://localhost:15672/api/overview
curl -s -u guest:guest http://localhost:15672/api/health/checks/alarms

Crear una cola por API es útil para probar y para automatizar. El vhost / se codifica como %2F:

curl -s -o /dev/null -w "%{http_code}\n" \

  -H "content-type: application/json" \
  -d '{"durable":true,"arguments":{}}' \

name  type     messages  consumers
demo  classic  0         0

PowerShell y curl

En PowerShell, curl es un alias de Invoke-WebRequest y no acepta los mismos flags. Usa curl.exe o Invoke-RestMethod. En macOS y Linux, curl funciona tal cual.

6 · Errores habituales

1. Olvidar el volumen y perder los datos

Mal — contenedor sin persistencia 
docker run -d --name rabbitmq -p 5672:5672 rabbitmq:4-management
docker rm -f rabbitmq
docker run -d --name rabbitmq -p 5672:5672 rabbitmq:4-management
# ❌ colas, mensajes y usuarios han desaparecido
Bien — volumen nombrado 
docker run -d --name rabbitmq \
  -p 5672:5672 -p 15672:15672 \
  -v rabbitmq-data:/var/lib/rabbitmq \
  rabbitmq:4-management

El volumen sobrevive a docker rm. Solo desaparece si lo borras explícitamente (docker volume rm o docker compose down -v).

2. Conectarse como guest desde otra máquina

Mal — creer que guest es global 
amqp://guest:guest@192.168.1.50:5672
# ❌ ACCESS_REFUSED - Login was refused using authentication mechanism PLAIN
Bien — usuario propio y permisos acotados 
docker exec rabbitmq rabbitmqctl add_user taller 'cambia-esto'
docker exec rabbitmq rabbitmqctl add_vhost taller
docker exec rabbitmq rabbitmqctl set_permissions -p taller taller ".*" ".*" ".*"

guest solo puede autenticarse desde loopback. En un contenedor remoto, «loopback» es el propio contenedor, no tu portátil. Crea un usuario y un vhost antes de exponer el broker.

3. Dar por bueno un healthcheck de puerto

Mal — solo comprobar que 15672 responde 
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:15672"]
Bien — preguntar al nodo 
healthcheck:
  test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 20s

La UI puede responder mientras el nodo está en una alarma o sincronizando metadata. ping es más específico y no depende de que el plugin management esté sano.

7 · Ejercicio guiado

Objetivo: levantar el broker con Compose, verificarlo por tres vías y comprobar que un volumen conserva una cola durable entre reinicios.

  1. Paso 1 — Crea el Compose y arráncalo: 
    docker compose up -d
docker compose ps

    Espera a ver (healthy). Si sigue en (health: starting), dale unos segundos y repite docker compose ps.

  2. Paso 2 — Comprueba el nodo por CLI: 
    docker exec rabbitmq rabbitmq-diagnostics -q ping
docker exec rabbitmq rabbitmqctl status

    Salida esperada: Ping succeeded y un bloque con RabbitMQ version: 4.4.x.

  3. Paso 3 — Abre la UI y crea una cola por API: entra en http://localhost:15672 con guest/guest. Después ejecuta: 
    curl -s -o /dev/null -w "%{http_code}\n" \
  -u guest:guest -X PUT \
  -H "content-type: application/json" \
  -d '{"durable":true,"arguments":{}}' \
  http://localhost:15672/api/queues/%2F/demo

    201

    Recarga Queues en la UI: demo aparece con 0 mensajes y 0 consumidores.

  4. Paso 4 — Verifica por CLI y por API: 
    docker exec rabbitmq rabbitmqctl list_queues name type messages consumers
curl -s -u guest:guest http://localhost:15672/api/queues

    Las dos fuentes deben coincidir. Si no coinciden, estás mirando otro vhost, otro contenedor u otro host.

  5. Paso 5 — Reinicia el broker: 
    docker compose restart rabbitmq
docker compose ps
docker exec rabbitmq rabbitmqctl list_queues name durable

    demo sigue ahí porque es durable y el volumen persiste. Los mensajes que hubiera también, si eran persistentes.

  6. Paso 6 — Destruye el volumen y comprueba la diferencia: 
    docker compose down -v
docker compose up -d
docker exec rabbitmq rabbitmqctl list_queues name

    La lista vuelve a estar vacía. down -v borra el volumen: es la forma rápida de «empezar de cero» y también la forma rápida de perder producción si te equivocas de entorno.

Comprobación final

Ejecuta docker compose logs rabbitmq | Select-String "Server startup complete" en PowerShell (o grep en macOS/Linux). Esa línea confirma que el broker terminó de arrancar; el healthcheck ya lo habrá detectado antes.

8 · Reto

🎯 Un segundo broker en el mismo portátil

Levanta una segunda instancia de RabbitMQ sin detener la primera, usando los puertos 5673 y 15673, un contenedor llamado rabbitmq-2 y un volumen propio. Conéctate a ella con amqp://guest:guest@localhost:5673 y comprueba que las colas de la primera instancia no aparecen.

Después explica qué cambiaría si en lugar de dos contenedores fueran dos vhosts del mismo broker. ¿Qué se comparte y qué queda aislado?

Pista: el puerto interno del contenedor sigue siendo 5672 y 15672; solo cambia el mapeo del host. Para el vhost, la URL lleva el nombre al final y la API lo codifica como %2F.

9 · Resumen

  • rabbitmq:4-management trae broker, Erlang, management UI y HTTP API; no instales Erlang a mano para aprender.
  • AMQP escucha en 5672; la UI y la API en 15672. Sin volumen en /var/lib/rabbitmq, los datos son efímeros.
  • guest/guest solo funciona desde loopback; en cualquier otro caso necesitas usuario, vhost y permisos.
  • rabbitmqctl sirve para estado y diagnóstico; la HTTP API, para automatizar; la UI, para observar.
  • Un healthcheck útil pregunta al nodo (rabbitmq-diagnostics -q ping), no solo si el puerto está abierto.
  • La topología se declara en código; la UI no es la fuente de verdad.

10 · Preguntas frecuentes

¿Necesito instalar Erlang en mi máquina?

No si usas Docker: la imagen ya incluye Erlang/OTP y el broker. Solo lo necesitarías para una instalación nativa, que no recomendamos para este curso porque añade una variable más al entorno.

¿Puedo usar la management UI en producción?

Sí, para observar y diagnosticar, siempre detrás de autenticación, TLS y una red restringida. Lo que no deberías es convertirla en la única forma de crear colas o usuarios: esos cambios no quedan versionados ni pasan revisión. La UI es un panel, no un pipeline de infraestructura.

¿Qué diferencia hay entre rabbitmqctl y la HTTP API?

rabbitmqctl habla con el nodo por distribución Erlang y requiere acceso al contenedor o al host; es ideal para estado y diagnóstico. La HTTP API usa el plugin management, funciona desde cualquier cliente con credenciales y es la base para automatizar y medir. Muchas operaciones existen en ambas; elige según dónde estés y qué necesites.

¿Por qué mi contenedor está «unhealthy» si la UI abre?

Porque el healthcheck no mide lo mismo que tu navegador. Puede estar fallando rabbitmq-diagnostics por una alarma de disco, por falta de memoria o porque el nodo aún sincroniza metadata. Revisa docker inspect --format '{{json .State.Health}}' rabbitmq y los logs; la UI puede responder mientras el nodo rechaza trabajo.
