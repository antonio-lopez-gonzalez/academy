El primer mensaje

Módulo 0 · Fundamentos 🕐 35 minutos

1 · Introducción

Ya tienes el broker y el mapa mental. Toca el momento que lo une todo: un proceso publica un mensaje y otro lo recibe. Vamos a hacerlo con dos scripts de Node.js, dos terminales y una cola durable. Sin frameworks, sin capas de abstracción: amqplib directo para que veas cada paso.

El primer mensaje usa el exchange por defecto, ese que no se declara y enruta por nombre de cola. Es la forma más corta de llegar de A a B y también la que menos acoplamiento ofrece. Lo usamos aquí para aislar lo importante: conexión, canal, publicación, consumo y ack.

Al terminar tendrás un productor que envía un pedido, un consumidor que lo imprime y lo confirma, y una cola que conserva los mensajes si el consumidor está apagado. También verás la primera limitación seria: publicar sin confirms no te dice si el broker llegó a recibir el mensaje.

Por qué dos terminales

Productor y consumidor son procesos independientes, como en producción. Si los ejecutas en el mismo script, el ciclo de vida se mezcla y no ves lo que pasa cuando el consumidor no está. Dos terminales hacen visible el desacoplamiento temporal desde el primer minuto.

2 · Teoría

El exchange por defecto

Todo vhost tiene un exchange sin nombre, "", de tipo direct. No se puede borrar ni declarar y tiene una regla especial: entrega a la cola cuyo nombre coincide exactamente con la routing key. Por eso:

channel.sendToQueue("pedidos.nuevos", body, options);
// es equivalente a
channel.publish("", "pedidos.nuevos", body, options);

La comodidad tiene un precio: el productor conoce el nombre de la cola. Si mañana quieres que dos colas reciban el mismo pedido, o renombrar el destino, tienes que cambiar el productor. En la lección Publicar y consumir pasaremos a un exchange con nombre y bindings.

El recorrido de un mensaje

productor.mjs                              consumidor.mjs
     │                                           │
     ├── connect ───▶ ┌─────────────┐ ◀── connect ┤
     │                │   broker    │             │
     ├── channel ────▶│             │◀── channel ─┤
     ├── assertQueue ─┤ pedidos.    │─ assertQueue┤
     │                │ nuevos      │             │
     ├── sendToQueue ─▶  (durable)  │             │
     │                │   │         │◀─ consume ──┤
     │                │   ▼         │             │
     │                │ [mensaje]   │──▶ callback │
     │                │   │         │      ├─ procesa
     │                │   └─────────│◀─ ack ──────┘
     │                │  eliminado  │
     └── close ───────▶└─────────────┘

El mensaje no va «al consumidor»: va a la cola. El consumidor es quien se suscribe a esa cola. Si hay dos consumidores en la misma cola, cada mensaje va a uno solo; si el consumidor está desconectado, el mensaje espera.

El mensaje y sus propiedades

El cuerpo debe ser un Buffer. Para JSON, Buffer.from(JSON.stringify(pedido)). Las opciones de publicación viajan como propiedades AMQP:

channel.sendToQueue(queue, Buffer.from(JSON.stringify(pedido)), {
  persistent: true,               // deliveryMode = 2
  contentType: "application/json",
  messageId: pedido.id,
  timestamp: Math.floor(Date.now() / 1000),
});

persistent: true pide al broker que escriba el mensaje en disco, pero solo tiene efecto completo si la cola es durable. Una cola no durable desaparece al reiniciar el broker, con todos sus mensajes, por muy persistentes que sean.

Publicar no es entregar

Que sendToQueue no lance una excepción no significa que el mensaje esté a salvo: solo que se escribió en el socket. Los confirms llegan en el módulo 3. Por ahora, no uses este ejemplo como plantilla de producción; úsalo para entender el flujo.

¿Qué pasa si el consumidor está apagado?

La cola retiene el mensaje. Cuando arranca el consumidor, el broker se lo entrega. Eso es el desacoplamiento temporal en acción. El límite es el disco y la memoria del broker: una cola sin consumidores durante días es un incidente, no una estrategia de alta disponibilidad.

Si el consumidor está conectado pero no confirma, el mensaje queda en messages_unacknowledged. Si el proceso muere o la conexión se corta, el broker lo devuelve a messages_ready y lo marca como redelivered en la siguiente entrega.

3 · Ejemplo mínimo

Crea el proyecto e instala amqplib. Usamos ESM (type: module) y Node.js 22:

mkdir primer-mensaje
cd primer-mensaje
npm init -y
npm pkg set type=module
npm install amqplib

Productor:

// productor.mjs
import amqp from "amqplib";

const url = process.env.AMQP_URL ?? "amqp://guest:guest@localhost:5672";
const queue = "pedidos.nuevos";

const connection = await amqp.connect(url);
const channel = await connection.createChannel();
await channel.assertQueue(queue, { durable: true });

const pedido = {
  schemaVersion: 1,
  id: "1042",
  cliente: "Ana Torres",
  total: 49.9,
  creadoEn: new Date().toISOString(),
};

channel.sendToQueue(queue, Buffer.from(JSON.stringify(pedido)), {
  persistent: true,
  contentType: "application/json",
  messageId: pedido.id,
});

console.log(`[productor] enviado pedido ${pedido.id}`);

await channel.close();
await connection.close();

Consumidor:

// consumidor.mjs
import amqp from "amqplib";

const url = process.env.AMQP_URL ?? "amqp://guest:guest@localhost:5672";
const queue = "pedidos.nuevos";

const connection = await amqp.connect(url);
const channel = await connection.createChannel();
await channel.assertQueue(queue, { durable: true });
await channel.prefetch(1);

console.log(`[consumidor] esperando en ${queue}...`);

const { consumerTag } = await channel.consume(queue, (msg) => {
  if (!msg) return;

  try {
    const pedido = JSON.parse(msg.content.toString());
    console.log(`[consumidor] pedido ${pedido.id}: ${pedido.cliente}, ${pedido.total} €`);
    channel.ack(msg);
    console.log(`[consumidor] ack deliveryTag=${msg.fields.deliveryTag}`);
  } catch (error) {
    console.error("[consumidor] mensaje inválido:", error.message);
    channel.nack(msg, false, false); // sin DLX todavía: se descarta
  }
}, { noAck: false });

const cerrar = async () => {
  await channel.cancel(consumerTag);
  await channel.close();
  await connection.close();
  process.exit(0);
};

process.on("SIGINT", cerrar);
process.on("SIGTERM", cerrar);

Línea a línea, lo importante:

  • amqp.connect(url) y createChannel(): conexión y multiplexor. Mantén ambos vivos mientras consumas.
  • assertQueue(queue, { durable: true }): productor y consumidor declaran la misma cola con los mismos atributos. Si uno usara durable: false, el segundo recibiría un 406.
  • prefetch(1): pide al broker que no entregue más de un mensaje sin confirmar a este consumidor. Evita que un worker lento acumule trabajo.
  • consume(queue, callback, { noAck: false }): noAck: false es el valor seguro; el mensaje no se elimina hasta que tú llames a ack.
  • channel.ack(msg): confirma usando el deliveryTag que trae el mensaje; el tag es por canal.
  • cancel + close: deja de recibir, cierra el canal y la conexión. El orden importa.

Ejecuta el consumidor en una terminal y el productor en otra:

# terminal 1
node consumidor.mjs

# terminal 2
node productor.mjs

# terminal 1
[consumidor] esperando en pedidos.nuevos...
[consumidor] pedido 1042: Ana Torres, 49.9 €
[consumidor] ack deliveryTag=1

# terminal 2
[productor] enviado pedido 1042

Si el consumidor no estaba arrancado, el productor termina igual y el mensaje queda en la cola. Arranca el consumidor después y lo verás llegar.

4 · Ejemplo real

En el taller, el evento se llama pedido.creado y el consumidor no solo imprime: registra el evento y marca el pedido como «en proceso». La estructura es la misma; cambia el contrato del mensaje.

// productor-taller.mjs
const evento = {
  schemaVersion: 1,
  eventId: "evt-7f3a",
  tipo: "pedido.creado",
  ocurridoEn: new Date().toISOString(),
  datos: { pedidoId: "1042", cliente: "Ana Torres", total: 49.9 },
};

channel.sendToQueue("pedidos.nuevos", Buffer.from(JSON.stringify(evento)), {
  persistent: true,
  contentType: "application/json",
  messageId: evento.eventId,
});

// consumidor-taller.mjs
await channel.consume("pedidos.nuevos", async (msg) => {
  if (!msg) return;

  try {
    const evento = JSON.parse(msg.content.toString());
    console.log(`[taller] ${evento.tipo} ${evento.datos.pedidoId}`);

    await marcarPedidoEnProceso(evento.datos.pedidoId); // efecto de negocio
    channel.ack(msg);
  } catch (error) {
    console.error("[taller] fallo:", error.message);
    channel.nack(msg, false, false); // en el módulo 3: DLQ
  }
}, { noAck: false });

Salida esperada:

[taller] pedido.creado 1042
[consumidor] ack deliveryTag=1

La diferencia con el ejemplo mínimo es dónde va el ack: después de marcarPedidoEnProceso, no antes. Si el proceso muere entre el efecto y el ack, el broker reentrega y el consumidor vuelve a ejecutar. Por eso marcarPedidoEnProceso debe ser idempotente: si el pedido ya está «en proceso», el segundo intento no debe duplicar nada.

6 · Errores habituales

1. ECONNREFUSED: el broker no está donde crees

Mal — asumir que el contenedor está levantado 
Error: connect ECONNREFUSED 127.0.0.1:5672
Bien — comprobar estado y puerto 
docker compose ps
docker exec rabbitmq rabbitmq-diagnostics -q ping
# y revisar AMQP_URL si cambiaste el puerto del host

También ocurre si mapeaste 5673:5672 y sigues conectando a 5672. El puerto interno del contenedor no cambia; el de tu URL sí.

2. ACCESS_REFUSED: credenciales o vhost incorrectos

Mal — guest contra un host remoto 
amqp://guest:guest@192.168.1.50:5672
# ❌ ACCESS_REFUSED - Login was refused
Bien — usuario propio y vhost explícito 
amqp://taller:secreto@192.168.1.50:5672/taller

guest solo se autentica desde loopback. Si el mensaje de error menciona vhost, revisa que el usuario tenga permisos sobre ese vhost concreto.

3. Confirmar antes de procesar

Mal — el ack va primero 
channel.ack(msg);
await cobrarPedido(pedido); // si falla, el mensaje ya no existe
Bien — efecto primero, ack después 
await cobrarPedido(pedido);
channel.ack(msg);

El ack es una promesa de «ya está». Si lo adelantas, conviertes at-least-once en at-most-once sin querer.

7 · Ejercicio guiado

Objetivo: ver el desacoplamiento temporal con dos procesos reales y comprobar que una cola durable conserva el trabajo.

  1. Paso 1 — Arranca el consumidor: 
    node consumidor.mjs

    [consumidor] esperando en pedidos.nuevos...
  2. Paso 2 — Publica tres pedidos desde otra terminal: cambia el id y ejecuta el productor tres veces. 
    node productor.mjs
node productor.mjs
node productor.mjs

    Salida esperada: tres líneas [productor] enviado pedido … y, en la otra terminal, tres bloques de consumo con deliveryTag=1, 2 y 3. El tag es por canal y empieza en 1 en cada conexión nueva.

  3. Paso 3 — Para el consumidor con Ctrl+C y publica dos más: 
    docker exec rabbitmq rabbitmqctl list_queues name messages messages_ready messages_unacknowledged consumers

    name            messages  messages_ready  messages_unacknowledged  consumers
pedidos.nuevos  2         2               0                        0

    Los mensajes están listos y sin consumidores. Nadie los ha perdido.

  4. Paso 4 — Vuelve a arrancar el consumidor: 
    node consumidor.mjs

    Debe recibir los dos pendientes inmediatamente, con deliveryTag=1 y 2 de la nueva conexión. La cola vuelve a 0.

  5. Paso 5 — Reinicia el broker con un mensaje pendiente: para el consumidor, publica uno, y ejecuta: 
    docker compose restart rabbitmq
docker compose ps
docker exec rabbitmq rabbitmqctl list_queues name messages messages_ready

    El mensaje sigue ahí porque la cola es durable y el mensaje persistente. Arranca el consumidor y compruébalo.

  6. Paso 6 — Ahora rompe la durabilidad: cambia durable: true por durable: false en ambos scripts, usa una cola nueva (pedidos.efimeros) y repite el reinicio. La cola desaparece con el mensaje. Anota la diferencia: durable protege la cola; persistent protege el mensaje; necesitas ambos.

Comprobación final

Mientras el consumidor está parado, la UI muestra la cola en Queues con Ready > 0 y Consumers = 0. Es la señal de «hay trabajo esperando a que alguien lo procese»; si esa cifra crece sin parar, tienes un incidente, no un buffer sano.

8 · Reto

🎯 Un productor de verdad

Convierte productor.mjs en una herramienta de línea de comandos: debe aceptar --id, --cliente y --total, validar que el total es un número positivo y generar un messageId único si no se lo pasan. Además, añade una cabecera x-origen con el nombre del servicio y muestra por pantalla el JSON exacto que publica.

Después responde: si ejecutas el productor dos veces con el mismo --id, ¿el consumidor recibe dos mensajes? ¿Debería? ¿Dónde pondrías la deduplicación?

Pista: el broker no sabe qué es un pedido duplicado; solo ve dos publicaciones. La clave de negocio vive en tu consumidor o en una restricción única de la base de datos.

9 · Resumen

  • sendToQueue publica en el exchange por defecto: la routing key es el nombre de la cola.
  • Productor y consumidor declaran la misma cola con los mismos atributos; assertQueue es idempotente pero estricto.
  • El consumidor mantiene el mensaje unacked hasta el ack; si cae, el broker lo reentrega.
  • Cola durable + mensaje persistente = el mensaje sobrevive a un reinicio ordenado del broker. Sin volumen, el contenedor puede llevarse todo.
  • Sin publisher confirms, publicar solo garantiza que el mensaje salió del cliente, no que el broker lo tenga.
  • El ack va después del efecto de negocio, y el efecto debe ser idempotente.

10 · Preguntas frecuentes

¿Qué pasa si publico antes de que exista la cola?

El exchange por defecto no encuentra ninguna cola con ese nombre y descarta el mensaje. No hay error. Por eso ambos scripts declaran la cola al arrancar; si el productor puede publicar antes de que el consumidor haya arrancado, la cola debe existir de antemano (declarada por el productor o por un script de topología).

¿sendToQueue espera a que el broker confirme?

No. Devuelve un booleano que indica si el buffer interno del cliente aceptó el mensaje (backpressure), no si el broker lo recibió. Para saberlo necesitas un confirm channel y waitForConfirms, que llegan en el módulo 3.

¿Para qué sirve el deliveryTag?

Identifica el mensaje dentro del canal para confirmarlo o rechazarlo. Es un número creciente por canal, no global. Si abres una conexión nueva, vuelve a empezar en 1. Por eso un ack debe hacerse en el mismo canal que entregó el mensaje.

¿Puedo consumir con noAck: true?

Sí, pero el broker considerará entregado el mensaje en cuanto lo envía. Si el consumidor cae, se pierde. Es at-most-once y solo tiene sentido para datos efímeros o telemetría donde perder una muestra es aceptable. En el curso, los ejemplos de trabajo usan noAck: false.
