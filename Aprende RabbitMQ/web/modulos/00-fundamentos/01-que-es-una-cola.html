Qué es una cola de mensajes

Módulo 0 · Fundamentos 🕐 30 minutos

1 · Introducción

Imagina el endpoint que crea un pedido. Hace tres cosas seguidas: guarda el pedido, genera la factura y envía el correo de confirmación. Funciona en desarrollo, con un pedido cada diez segundos. En producción, un viernes por la tarde, el proveedor de correo tarda ocho segundos y la base de datos de facturación está en mantenimiento. El cliente pulsa «Comprar», la petición se queda colgada y, cuando por fin responde con un error, el pedido ya está guardado pero la factura no. El usuario reintenta. Ahora hay dos pedidos.

El problema no es el código: es el acoplamiento temporal. La API no puede terminar hasta que terminen tres sistemas que no controla y que no necesitan participar en la respuesta. Una cola de mensajes rompe esa cadena: la API guarda el pedido, deja un mensaje y responde. El resto ocurre después, a su ritmo, con reintentos y sin arrastrar al usuario.

Una cola no es magia ni una base de datos. Es un contrato de entrega: alguien publica un mensaje, un broker lo almacena y lo enruta, y un consumidor lo procesa y confirma. Cada una de esas palabras tiene garantías distintas, y elegirlas mal es la diferencia entre «el sistema aguanta» y «hemos perdido pedidos sin saberlo».

Por qué existe esta lección

Antes de instalar RabbitMQ conviene saber qué problema estás comprando. La mensajería añade un broker que operar, latencia eventual, duplicados posibles y un modelo mental nuevo. Si no tienes claro qué acoplamiento rompe y qué garantía necesitas, acabarás usando una cola como base de datos o creyendo que resuelve problemas que no son suyos.

2 · Teoría

El problema: una cadena síncrona

En una llamada HTTP síncrona, el cliente espera a que el servidor termine todo el trabajo. Si el servidor llama a tres servicios, la latencia es la suma y la disponibilidad es el producto:

cliente ──POST /pedidos──▶ API ──▶ PostgreSQL      (20 ms)
                              ├──▶ facturación     (300 ms)
                              ├──▶ email           (800 ms, a veces 8 s)
                              └──▶ inventario      (150 ms)
                              │
                              └── respuesta al cliente: cuando todo termina

Si facturación está al 99 % y email al 99 %, la cadena completa
no está al 99 %: está al 0,99 × 0,99 = 98,01 % como máximo.

Y hay un problema peor que la latencia: el fallo en cascada. Si el proveedor de correo se cae, la API devuelve error aunque el pedido se haya guardado. El cliente reintenta, se duplica el pedido y alguien pasa la tarde cuadrando datos.

Qué añade una cola

Con mensajería, la API hace solo lo que necesita para responder: validar, persistir el pedido y publicar un evento. El resto son consumidores independientes:

cliente ──POST /pedidos──▶ API ──INSERT──▶ PostgreSQL
                              │
                              └──publish──▶ [ exchange ] ──▶ [ cola ] ──▶ worker
                                                                   │
                                                              ack / nack

La API responde 202 Accepted en cuanto el mensaje está publicado.
El worker puede estar caído: el mensaje espera en la cola.

La cola actúa como buffer y como frontera de fallo. Un pico de cien pedidos por segundo no requiere cien workers en ese instante: se encolan y se procesan a la capacidad disponible. Un worker caído no tumba la API: sus mensajes quedan pendientes hasta que vuelva otro.

Tres desacoplamientos

TipoQué significaEjemplo en el taller
Temporal Productor y consumidor no tienen que estar vivos a la vez. La API publica a las 23:00; el worker de facturación arranca a las 06:00 y encuentra los mensajes.
Espacial El productor no conoce la identidad ni la ubicación del consumidor. La API publica pedido.creado sin saber si lo lee facturación, inventario o un servicio nuevo que aún no existe.
De fallos Un consumidor lento o caído no propaga el error al productor. El correo de confirmación falla; el pedido sigue creado y el mensaje se reintenta.

Un buffer, no una base de datos

Es tentador pensar en la cola como una tabla donde «se guardan» los pedidos. No lo es: el dato de una base de datos permanece hasta que alguien lo borra y se puede consultar, filtrar y actualizar; el mensaje de una cola desaparece cuando el consumidor confirma, no se consulta y el broker no entiende su contenido. La cola transporta el «qué ha pasado»; el estado del negocio vive en la base de datos.

La cola no sustituye la persistencia del negocio

El pedido debe estar en PostgreSQL antes de publicar el evento. Si solo vive en la cola y el consumidor falla de forma definitiva, lo pierdes. El patrón habitual es guardar estado + publicar evento, y resolver la atomicidad entre ambos con un outbox o con reintentos idempotentes.

Garantías: elige una y sabe quién la sostiene

«Entrega garantizada» no significa nada si no dices cuántas veces y ante qué fallo. Las tres opciones clásicas:

GarantíaQué prometeQuién la sostieneCómo se implementa
At-most-once Como máximo una entrega. Si el consumidor cae después de recibir, el mensaje se pierde. El broker, que considera entregado en cuanto envía. autoAck: true o noAck: true. Rápido y frágil.
At-least-once Al menos una entrega. Si el consumidor no confirma, el mensaje vuelve a la cola. El consumidor, con ack manual, y el broker, con redelivery. ack después de procesar. Puede duplicar: exige idempotencia.
Exactly-once Exactamente una entrega, sin pérdidas ni duplicados. Nadie la regala de extremo a extremo. Se aproxima con at-least-once + clave de negocio única + deduplicación.

En este curso partimos de una regla: no existe entrega exactamente una vez gratis. Si alguien te la promete, pregunta qué pasa si el proceso muere entre el efecto y el ack, o si el broker confirma y la red se corta antes de que el productor se entere.

Cuándo NO usar mensajería

Una cola añade piezas y estados intermedios. No es la respuesta a todo:

  • Necesitas la respuesta ya y con consistencia fuerte. Un GET /saldo no debe pasar por una cola: el cliente espera un dato actual, no un «procesando».
  • La operación es única, barata y de bajo volumen. Un cron diario que genera un CSV no necesita un broker; un script y un log pueden bastar.
  • Necesitas consultar el histórico. Eso es una base de datos o un event store, no una cola.

Ejemplos donde sí encaja

Pedidos y facturación (la API responde rápido y la factura se genera después), emails y notificaciones (el proveedor externo es lento y conviene reintentar con backoff), procesamiento de imágenes (trabajo pesado y workers que escalan) y eventos de dominio (varios servicios reaccionan al mismo hecho sin acoplarse). En todos, la garantía razonable es at-least-once con consumidores idempotentes.

El hilo conductor: el taller de pedidos

Durante el curso construimos un sistema que crece contigo:

  1. El taller publica pedido.creado y un consumidor lo imprime.
  2. Facturación e inventario reciben el mismo evento con un fanout.
  3. Las rutas se afinan con un topic exchange: pedido.*, pedido.creado, pedido.cancelado.
  4. Añadimos confirms, ack manual, reintentos, DLQ y la job queue completa.

Todo lo que veas a partir de aquí responderá a una pregunta concreta del taller: ¿qué pasa si este paso falla?

3 · Ejemplo mínimo

Antes de instalar nada, reproduce el concepto con una cola en memoria. No es RabbitMQ, pero te obliga a ver las tres piezas: alguien publica, algo almacena y alguien consume sin bloquear al productor.

// cola.mjs — una cola en memoria para observar el desacoplamiento
const cola = [];
let procesados = 0;

function publicar(pedido) {
  cola.push(pedido);
  console.log(`[api] pedido ${pedido.id} aceptado; pendientes: ${cola.length}`);
}

async function worker() {
  while (true) {
    const pedido = cola.shift();
    if (!pedido) {
      await new Promise((resolve) => setTimeout(resolve, 100));
      continue;
    }
    await new Promise((resolve) => setTimeout(resolve, 300)); // simula facturación
    procesados += 1;
    console.log(`[worker] pedido ${pedido.id} procesado (${procesados})`);
  }
}

worker(); // no se espera: el worker corre en paralelo
publicar({ id: "1042", total: 49.9 });
publicar({ id: "1043", total: 12.0 });
publicar({ id: "1044", total: 87.5 });

Línea a línea:

  • cola es el broker: un array que guarda mensajes pendientes.
  • publicar hace push y vuelve inmediatamente. La API no espera a que se procese nada.
  • worker hace shift: saca el mensaje más antiguo (FIFO) y lo procesa.
  • await new Promise(...) simula el trabajo lento de facturación.
  • worker() no lleva await delante: se lanza y el hilo principal sigue publicando.

Salida esperada (el orden exacto de las tres primeras líneas puede variar):

[api] pedido 1042 aceptado; pendientes: 1
[api] pedido 1043 aceptado; pendientes: 2
[api] pedido 1044 aceptado; pendientes: 3
[worker] pedido 1042 procesado (1)
[worker] pedido 1043 procesado (2)
[worker] pedido 1044 procesado (3)

Fíjate en lo importante: los tres pedidos se aceptaron en milisegundos y el worker tardó casi un segundo. Ese hueco es el buffer. Ahora mata el proceso con Ctrl+C antes de que termine: los mensajes desaparecen con la memoria. Esa es la primera lección de fiabilidad: una cola en el proceso no sobrevive al proceso. RabbitMQ existe, entre otras cosas, para que la cola viva fuera de tu aplicación.

4 · Ejemplo real

En el taller, la API crea el pedido y publica un evento. No genera la factura ni envía el correo: solo deja constancia de que algo ocurrió.

async function crearPedido(datos) {
  const pedido = await db.insert("pedidos", {
    ...datos,
    estado: "pendiente",
    creadoEn: new Date().toISOString(),
  });

  await broker.publicar("pedido.creado", {
    id: pedido.id,
    cliente: pedido.cliente,
    total: pedido.total,
  });

  return { id: pedido.id, estado: "pendiente" };
}

La topología inicial tiene un exchange y tres colas independientes:

                         ┌──────────────────────────────┐
   API ──publish────────▶│  exchange pedidos (topic)    │
   routing key:          └──────────────┬───────────────┘
   pedido.creado                        │
                         ┌──────────────┼──────────────┐
                         │              │              │
                    pedido.creado  pedido.creado   pedido.#
                         ▼              ▼              ▼
                   ┌───────────┐  ┌────────────┐  ┌───────────┐
                   │facturacion│  │ inventario │  │ auditoria │
                   └─────┬─────┘  └─────┬──────┘  └─────┬─────┘
                         ▼              ▼               ▼
                    genera PDF     reserva stock    registra todo

Cada cola tiene su propio consumidor y su propio ritmo. Si facturación va lenta, inventario sigue reservando stock y auditoría sigue registrando. No hay una cadena: hay tres reacciones al mismo hecho.

Si falla…Qué ocurreQué debe hacer el sistema
El worker de facturación está caídoLos mensajes se acumulan en facturacion.Alarma por backlog; escalar workers o revisar el fallo.
El proveedor de email tarda 30 sLa API no se entera; el consumidor espera.Timeout, nack y reintento con backoff; nunca bloquear la cola.
El broker no está disponibleLa publicación falla.La API decide: error 503, outbox o reintento; no fingir que el evento salió.
El consumidor procesa dos vecesSe duplica una factura o un email.Idempotencia por clave de negocio (pedidoId).

La analogía del mostrador

Sin cola, el cliente espera mientras el dependiente va al almacén, llama al proveedor y prepara la factura. Con cola, le da un resguardo («aceptado»), deja la comanda en una bandeja y el cliente se va. La bandeja es la cola; el resguardo es el 202 Accepted.

5 · Buenas prácticas

HazEvitaPor qué
Publicar eventos de negocio con un nombre estable: pedido.creado. Nombres atados a la implementación: insert_pedido_en_bd. El evento describe un hecho, no una función interna. Varios consumidores pueden reaccionar sin acoplarse a tu código.
Hacer el consumidor idempotente por clave de negocio. Confiar en que el mensaje llegará una sola vez. At-least-once puede duplicar. Una clave única en base de datos convierte el duplicado en un no-op.
Separar colas por tipo de trabajo y definir un límite con alarma de backlog. Una sola cola gigante para facturas, emails e imágenes, creciendo sin control. Un trabajo lento bloquea a los demás y una cola que crece es un incidente silencioso.
Versionar el esquema del mensaje (schemaVersion).Cambiar campos sin avisar a los consumidores.Productor y consumidores se despliegan por separado; el contrato debe evolucionar sin romper.

6 · Errores habituales

1. Encadenar todo en la petición HTTP

Mal — el cliente espera a tres sistemas 
app.post("/pedidos", async (req, res) => {
  const pedido = await db.insert("pedidos", req.body);
  await facturar(pedido);        // 300 ms
  await enviarEmail(pedido);     // 800 ms, a veces falla
  await reservarStock(pedido);   // 150 ms
  res.status(201).json(pedido);
});
Bien — persistir, publicar y responder 
app.post("/pedidos", async (req, res) => {
  const pedido = await db.insert("pedidos", req.body);
  await broker.publicar("pedido.creado", pedido);
  res.status(202).json({ id: pedido.id, estado: "pendiente" });
});

La API sigue siendo responsable de que el pedido esté guardado; lo que delega es el trabajo posterior. Si la publicación falla, debe devolver error o dejar el evento en un outbox: lo que no puede es responder «aceptado» y perderlo.

2. Creer que la cola garantiza una sola entrega

Mal — asumir exactly-once 
// ❌ "Si el mensaje llega, llega una sola vez"
await crearFactura(pedido);
channel.ack(msg);
Bien — asumir duplicados y deduplicar 
await db.query(
  "INSERT INTO facturas (pedido_id, total) VALUES ($1, $2) ON CONFLICT (pedido_id) DO NOTHING",
  [pedido.id, pedido.total],
);
channel.ack(msg);

El ack puede perderse después de crear la factura; el broker reentrega y el consumidor vuelve a ejecutar. La restricción única convierte el segundo intento en un no-op.

3. No poner límites ni alarmas

Mal — una cola sin dueño 
// ❌ crece durante días; nadie lo mira hasta que el disco se llena
Bien — límite, DLQ y alerta 
x-max-length + dead-letter-exchange
alerta si messages_ready > 10 000 durante 5 min

Sin consumidores no hay alta disponibilidad: hay trabajo acumulándose.

7 · Ejercicio guiado

Objetivo: comprobar con tus manos que el productor no espera, que la cola absorbe un pico y que una cola en memoria muere con el proceso.

  1. Paso 1 — Crea el archivo y deja el worker comentado: 
    mkdir laboratorio-cola
cd laboratorio-cola
node --version   # debe ser v22 o superior

    Copia el ejemplo mínimo en cola.mjs, pero sustituye la última línea worker(); por // worker();.

  2. Paso 2 — Publica tres pedidos sin consumidor: 
    node cola.mjs

    [api] pedido 1042 aceptado; pendientes: 1
[api] pedido 1043 aceptado; pendientes: 2
[api] pedido 1044 aceptado; pendientes: 3

    El proceso termina de inmediato. Los mensajes se quedaron en el array y, al salir, se perdieron. Eso es una cola sin broker: at-most-once y sin persistencia.

  3. Paso 3 — Activa el worker y vuelve a ejecutar: 
    # descomenta worker();
node cola.mjs

    [api] pedido 1042 aceptado; pendientes: 1
[api] pedido 1043 aceptado; pendientes: 2
[api] pedido 1044 aceptado; pendientes: 3
[worker] pedido 1042 procesado (1)
[worker] pedido 1043 procesado (2)
[worker] pedido 1044 procesado (3)

    Los pedidos se aceptan antes de que el worker termine el primero. Ese desfase es el desacoplamiento temporal.

  4. Paso 4 — Genera un pico: añade antes de la llamada a worker() un bucle que publique 500 pedidos: 
    for (let i = 0; i < 500; i++) {
  publicar({ id: String(2000 + i), total: 10 });
}

    Ejecuta y observa: la API acepta los 500 en unos milisegundos; el worker tarda unos 150 segundos. La cola es el amortiguador entre ambas velocidades.

  5. Paso 5 — Interrumpe a mitad: pulsa Ctrl+C cuando el worker lleve unos cuantos pedidos. Vuelve a ejecutar el script. Los pedidos que quedaban en el array ya no existen: no hay nada que reanudar.
  6. Paso 6 — Anota la conclusión: escribe en un comentario qué garantía ofrece esta implementación y qué falta para que sea at-least-once. La respuesta corta: falta un broker externo que guarde los mensajes y un ack que confirme el procesamiento.

Comprobación final

Si el worker procesa más rápido de lo que publicas, la cola casi nunca crece y el ejercicio parece innecesario. Baja la velocidad del worker o sube el número de publicaciones: el buffer solo se ve cuando la entrada supera la capacidad.

8 · Reto

🎯 Dos reacciones, una decisión

El taller necesita que, al crear un pedido, facturación genere una factura y marketing envíe un email de bienvenida. Facturación no puede perder ni una factura; marketing puede tolerar un email duplicado, pero no quiere bloquearse si el proveedor de correo está lento.

Diseña la topología: ¿una cola con dos tipos de consumidores compitiendo, dos colas separadas o un exchange con dos bindings? Decide para cada una la garantía de entrega y quién la sostiene. Después responde: si marketing se cae durante una hora, ¿qué pasa con las facturas? ¿Y si facturación se cae?

Pista: una cola con dos consumidores reparte cada mensaje a uno solo; dos colas con dos consumidores independientes reciben ambas una copia. Piensa primero en el efecto de negocio, no en el código.

9 · Resumen

  • Una cola de mensajes rompe el acoplamiento temporal, espacial y de fallos entre productor y consumidor.
  • El broker actúa como buffer: absorbe picos y permite que el consumidor procese a su ritmo.
  • Una cola no es una base de datos: no se consulta, no se actualiza y el mensaje desaparece al confirmarse.
  • Toda garantía debe nombrarse: at-most-once (puede perder), at-least-once (puede duplicar) o exactly-once aproximado con idempotencia.
  • La mensajería no es para todo: respuestas inmediatas, payloads enormes y orden global estricto suelen pedir otras herramientas.
  • El taller de pedidos usará eventos de negocio, colas independientes por consumidor y un diseño explícito de fallos.

10 · Preguntas frecuentes

¿Una cola es lo mismo que una base de datos?

No. Una base de datos guarda estado y permite consultarlo; una cola transporta mensajes hacia un consumidor y los elimina al confirmarse. Si necesitas saber «cuántos pedidos pendientes hay» o «qué pasó en marzo», eso vive en la base de datos, no en el broker.

Si el consumidor está apagado, ¿se pierde el mensaje?

Con un broker y una cola durable, no: el mensaje queda almacenado hasta que haya un consumidor. Con una cola en memoria como la del ejemplo mínimo, sí. La diferencia entre ambos casos es exactamente el motivo por el que existe RabbitMQ.

¿La cola garantiza que el mensaje se procesa una sola vez?

No. La garantía habitual es at-least-once: si el consumidor cae antes de confirmar, el broker reentrega. Para acercarte a «una sola vez» necesitas una clave de negocio única y deduplicación en el consumidor. Es responsabilidad tuya, no del broker.

¿Necesito mensajería para un cron que se ejecuta una vez al día?

Probablemente no. Si la tarea es única, barata y no compite con tráfico de usuario, un cron con logs y reintentos puede ser suficiente. La mensajería aporta cuando hay picos, varios consumidores, trabajos lentos o necesidad de desacoplar fallos. Añadir un broker sin esos requisitos es coste operativo sin beneficio.
