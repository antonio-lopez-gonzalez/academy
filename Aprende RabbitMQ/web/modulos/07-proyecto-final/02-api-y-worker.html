API y worker

Módulo 7 · Proyecto final 🕐 45 minutos

1 · Introducción

La arquitectura está decidida. Ahora hay que escribir dos procesos que se comporten como el diseño promete. La API acepta peticiones HTTP y publica; el worker consume y ejecuta. Ninguno de los dos puede asumir que el otro está vivo, que el broker está disponible o que el mensaje llegará una sola vez.

La cadena de responsabilidad es la siguiente:

PasoQuiénQué garantiza
Validar y persistir el jobAPIExiste una fila con estado queued antes de publicar.
Publicar con confirmAPI + brokerEl broker ha aceptado y replicado el mensaje (quorum).
Reclamar el jobWorker + almacénUn solo worker lo ejecuta a la vez (o uno con lease vencido).
Hacer ackWorkerEl mensaje se borra solo cuando el efecto terminó.

Responder 202 es una promesa

202 Accepted significa «he aceptado el trabajo y me hago responsable de él». Si la API responde 202 antes del confirm, esa promesa puede ser falsa: el mensaje se pierde si el broker rechaza la publicación o el canal se cierra. El orden —persistir, publicar, confirmar, responder— no es un detalle de estilo.

Errores típicos: autoAck para «simplificar», responder 202 sin confirm, hacer ack antes del efecto, matar el proceso con process.exit en el primer SIGTERM o reconectar sin volver a declarar la topología.

2 · Teoría

La API: publicar de forma fiable

El canal de publicación debe ser un ConfirmChannel. Un canal normal acepta el publish y olvida: si el exchange no existe o el broker no puede persistir, el mensaje se pierde sin que el productor lo sepa. Con confirm, el broker responde ack o nack por cada publicación.

const connection = await amqp.connect(config.url);
const channel = await connection.createConfirmChannel();
await declareTopology(channel);

channel.on('return', (msg) => {
  console.error('mensaje no enrutable:', msg.fields.routingKey, msg.content.toString());
});

const accepted = channel.publish(EXCHANGE, 'job.run', body, {
  persistent: true,
  mandatory: true,
  messageId: job.jobId,
  contentType: 'application/json',
  headers: { 'x-attempt': 0, 'x-trace-id': job.traceId },
});

if (!accepted) {
  await new Promise((resolve) => channel.once('drain', resolve));
}
await channel.waitForConfirms();
  • mandatory: true hace que un mensaje sin binding vuelva con basic.return en lugar de descartarse. El handler de return es tu red de seguridad ante una topología mal declarada.
  • persistent: true pide al broker que guarde el mensaje en disco. En una quorum queue la persistencia es obligatoria; en una clásica, sin esta opción el mensaje puede perderse al reiniciar.
  • waitForConfirms() espera a todas las publicaciones pendientes del canal. Es simple y seguro; para alto rendimiento se agrupan publicaciones y se confirma por lotes, aceptando una ventana de mensajes en vuelo.
  • El valor de retorno false indica presión de buffer, no fallo. Esperar drain evita acumular memoria.

El problema de las dos escrituras

Persistir en la base de datos y publicar en RabbitMQ son dos sistemas distintos. No hay transacción que abarque ambos. Si el proceso muere entre las dos operaciones, el job existe sin mensaje; si publica antes de persistir, el mensaje existe sin job. El diseño pragmático:

1. INSERT job (status=queued, published_at=NULL)
2. publish + waitForConfirms
3. UPDATE job SET published_at=now()
4. responder 202

si el proceso muere entre 2 y 3:
   el mensaje está en la cola y el job parece no publicado
   -> el worker lo procesa igual; el sweeper debe ser idempotente
si el proceso muere entre 1 y 2:
   el job queda sin mensaje
   -> un sweeper republica los published_at IS NULL con edad > N

La alternativa canónica es el outbox pattern: el job y un registro «pendiente de publicar» se guardan en la misma transacción; un publicador independiente lee el outbox y publica con confirm. Es más robusto y más complejo. Para el proyecto, el campo published_at y un barrido periódico dan la misma garantía con menos piezas.

El worker: prefetch, concurrencia y ack

Un worker abre una conexión y, normalmente, un canal para consumir. El canal no es thread-safe: no compartas el mismo canal entre tareas concurrentes que publican y consumen sin coordinación. El patrón del proyecto es un canal de consumo y, si hace falta publicar reintentos, un canal de confirmación separado.

await channel.prefetch(config.prefetch);   // 10 por defecto
const consumer = await channel.consume(QUEUE, (msg) => {
  if (!msg) return;                        // cancelación del consumidor
  const task = handle(msg);
  inFlight.add(task);
  task.finally(() => inFlight.delete(task));
}, { noAck: false });

prefetch limita cuántos mensajes sin ack puede tener el consumidor. No es un límite de concurrencia del proceso: amqplib entrega los mensajes y tu handler asíncrono decide cuándo termina. Con prefetch 10 y un handler que tarda 2 segundos, el worker puede tener 10 trabajos en vuelo; con prefetch 1, procesa de uno en uno. Un prefetch demasiado alto multiplica memoria y conexiones al servicio externo; uno demasiado bajo desaprovecha el worker.

El handler: reclamar, ejecutar, confirmar

async function handle(msg) {
  const job = JSON.parse(msg.content.toString());
  const claimed = await store.claim(job.jobId, { leaseMs: config.leaseMs });
  if (!claimed) {
    channel.ack(msg);                 // ya lo tiene otro o ya terminó
    return;
  }

  try {
    const result = await processJob(claimed);
    await store.markSucceeded(job.jobId, result);
    channel.ack(msg);
  } catch (err) {
    await store.markFailed(job.jobId, err);   // en 07/03: retry
    channel.nack(msg, false, false);          // a la DLX
  }
}

El ack va después de markSucceeded. Si el proceso muere entre ambos, el mensaje se reentrega y el job se vuelve a ejecutar; la reclamación verá succeeded y el worker hará ack sin repetir el efecto. Si el proceso muere antes de markSucceeded pero después del efecto, el upsert por clave de negocio evita la duplicación.

Apagado ordenado

En Docker o Kubernetes, el proceso recibe SIGTERM y tiene una ventana antes de SIGKILL. Matarlo de inmediato deja mensajes sin ack que el broker reentrega; no se pierden, pero se duplica trabajo y se ensucia el estado. El apagado correcto es:

  1. Dejar de aceptar peticiones HTTP nuevas (cerrar el servidor).
  2. Cancelar el consumidor para que no lleguen mensajes nuevos.
  3. Esperar a que los handlers en vuelo terminen y hagan ack.
  4. Cerrar canal y conexión.
  5. Salir con código 0, o forzar tras un timeout.
async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log(JSON.stringify({ event: 'shutdown', signal }));

  await channel.cancel(consumerTag);
  const drained = Promise.allSettled([...inFlight]);
  await Promise.race([drained, new Promise((r) => setTimeout(r, config.shutdownTimeoutMs))]);

  await channel.close();
  await connection.close();
}

Reconexión y códigos HTTP

Si el broker se reinicia, la conexión emite close y el proceso se queda sin canal. amqplib no reconecta ni recrea consumidores: hay que esperar con backoff, reconectar, declarar topología y volver a consumir. Mientras no haya canal, la API responde 503 en POST /jobs; el resto de códigos (400 inválido, 404 inexistente, 413 demasiado grande) los decide la validación.

Existen librerías como amqp-connection-manager que encapsulan esta lógica. El proyecto usa amqplib directo para que el mecanismo sea visible; en producción, valora la librería si no quieres mantenerla.

3 · Ejemplo mínimo

El fragmento más pequeño que publica de forma fiable. No incluye HTTP ni almacén: solo la parte que distingue una publicación de verdad de una que parece funcionar.

import amqp from 'amqplib';

const conn = await amqp.connect(process.env.RABBITMQ_URL);
const ch = await conn.createConfirmChannel();

await ch.assertExchange('taller.jobs', 'direct', { durable: true });
await ch.assertQueue('taller.jobs.work', {
  durable: true,
  arguments: {
    'x-queue-type': 'quorum',
    'x-dead-letter-exchange': 'taller.dlx',
    'x-dead-letter-routing-key': 'job.dead',
  },
});
await ch.bindQueue('taller.jobs.work', 'taller.jobs', 'job.run');

const jobId = crypto.randomUUID();
ch.publish(
  'taller.jobs',
  'job.run',
  Buffer.from(JSON.stringify({ jobId, type: 'invoice.generate', payload: {} })),
  { persistent: true, messageId: jobId, contentType: 'application/json' }
);
await ch.waitForConfirms();
console.log('confirmado por el broker:', jobId);

await ch.close();
await conn.close();

Si quitas createConfirmChannel y usas createChannel, el programa termina igual y no hay forma de saber si el mensaje llegó. Si quitas persistent, el mensaje puede desaparecer en un reinicio. Si quitas la cola durable, la cola desaparece con el broker. Cada opción protege una cosa distinta.

4 · Ejemplo real

La API del taller usa node:http para no añadir dependencias. El punto interesante no es el router, sino el orden de las operaciones y la traducción de fallos a códigos HTTP.

import http from 'node:http';
import crypto from 'node:crypto';

const server = http.createServer(async (req, res) => {
  if (req.method === 'POST' && req.url === '/jobs') {
    const raw = await readBody(req, 1024 * 1024).catch(() => null);
    if (!raw) return send(res, 413, { error: 'payload_too_large' });

    const body = parseJson(raw);
    if (!body || !body.type || typeof body.payload !== 'object') {
      return send(res, 400, { error: 'invalid_job' });
    }

    const job = {
      jobId: crypto.randomUUID(),
      type: body.type,
      payload: body.payload,
      traceId: req.headers['x-trace-id'] ?? crypto.randomUUID(),
      status: 'queued',
      attempts: 0,
    };

    await store.create(job);                       // 1. persistir

    try {
      await publishJob(job);                       // 2. publicar + confirm
      await store.markPublished(job.jobId);        // 3. marcar
    } catch (err) {
      console.error(JSON.stringify({ event: 'publish_failed', jobId: job.jobId, err: err.message }));
      return send(res, 503, { error: 'broker_unavailable', jobId: job.jobId });
    }

    res.setHeader('Location', `/jobs/${job.jobId}`);
    return send(res, 202, { id: job.jobId, status: 'queued' });  // 4. responder
  }

  const match = req.url.match(/^\/jobs\/([\w-]+)$/);
  if (req.method === 'GET' && match) {
    const job = await store.get(match[1]);
    if (!job) return send(res, 404, { error: 'not_found' });
    return send(res, 200, { id: job.jobId, status: job.status, attempts: job.attempts, result: job.result });
  }

  return send(res, 404, { error: 'not_found' });
});

El 503 devuelve el jobId a propósito: el job está persistido y el sweeper lo republicará. El cliente puede consultar su estado antes de reintentar el POST. Sin una clave de idempotencia, reintentar el POST crearía otro job; ese es el reto de la lección.

El worker, por su parte, necesita una conexión separada y un canal de confirmación para publicar reintentos. Este es el esqueleto completo, con apagado ordenado:

const connection = await connectWithRetry(config.url);
const channel = await connection.createChannel();
const confirm = await connection.createConfirmChannel();
await declareTopology(channel);
await channel.prefetch(config.prefetch);

const inFlight = new Set();
const { consumerTag } = await channel.consume(config.queue, (msg) => {
  if (!msg) return;
  const task = handle(msg, confirm).catch((err) => {
    console.error(JSON.stringify({ event: 'handler_crashed', err: err.message }));
    channel.nack(msg, false, false);
  });
  inFlight.add(task);
  task.finally(() => inFlight.delete(task));
}, { noAck: false });

El handle recibe el canal de confirmación porque, en la siguiente lección, publicará el reintento antes de hacer ack. El canal de consumo solo se usa para ack/nack; mezclar publicaciones y acknowledgements en el mismo canal funciona, pero separa responsabilidades y evita que un nack de publicación cierre el canal de consumo.

No llames a process.exit() antes de drenar

process.exit() no espera promesas pendientes. Si lo llamas nada más recibir SIGTERM, los handlers en vuelo mueren sin ack y el broker reentrega: el trabajo se duplica y el estado puede quedar inconsistente. Cierra el consumidor, espera a que termine lo que está en vuelo y solo entonces sal del proceso.

6 · Errores habituales

1. autoAck para simplificar

Mal — el mensaje se borra al entregarse 
await ch.consume(QUEUE, async (msg) => {
  await processJob(msg);
}, { noAck: true });
Bien — ack manual después del efecto 
await ch.consume(QUEUE, async (msg) => {
  await processJob(msg);
  ch.ack(msg);
}, { noAck: false });

Con noAck: true, si el proceso muere a mitad del trabajo, el mensaje ya no existe. El broker no puede reentregar lo que considera entregado. Es la forma más rápida de perder trabajos sin recibir un error.

2. Responder 202 sin confirm

Mal — la promesa no está respaldada 
ch.publish(EXCHANGE, 'job.run', body);   // canal normal
return res.status(202).json({ id });
Bien — confirmar antes de responder 
ch.publish(EXCHANGE, 'job.run', body, { persistent: true });
await ch.waitForConfirms();
return res.status(202).json({ id });

Si el exchange no existe o el broker está en una partición, el publish del canal normal puede fallar en silencio. El cliente recibe 202, el job no está en ninguna cola y nadie lo sabe hasta que el usuario pregunta por su factura.

3. ack antes de terminar

Mal — el efecto puede no ocurrir 
ch.ack(msg);
await generateInvoice(job);   // si esto falla, el mensaje ya no está
Bien — el ack cierra la transacción lógica 
await generateInvoice(job);
await store.markSucceeded(job.jobId);
ch.ack(msg);

El ack no es «he recibido el mensaje»: es «he completado el trabajo». Adelantarlo convierte un fallo recuperable en una pérdida definitiva.

4. Morir sin apagado ordenado

Mal — matar el proceso en la señal 
process.on('SIGTERM', () => process.exit(0));
Bien — drenar antes de salir 
process.on('SIGTERM', async () => {
  await channel.cancel(consumerTag);
  await Promise.allSettled([...inFlight]);
  await connection.close();
  process.exit(0);
});

El broker reentrega lo que no se confirmó, así que no se pierde; pero se duplica trabajo y se puede quedar un job en running hasta que venza el lease. En un despliegue rodado, eso se multiplica por cada réplica.

7 · Ejercicio guiado

Objetivo: ejecutar API y worker, observar los estados y comprobar la reentrega cuando el worker muere a mitad de un job.

  1. Arranca el broker y comprueba la topología: 
    docker compose up -d rabbitmq
docker exec rabbitmq rabbitmq-diagnostics ping
docker exec rabbitmq rabbitmqctl list_queues -p taller-prod name type
  2. Arranca API y worker en dos terminales con RABBITMQ_URL apuntando a /taller-prod. Deben declarar la topología al arrancar sin errores de permisos. Si usas el usuario de aplicación, recuerda que no tiene configure: declara con el usuario de despliegue antes.
  3. Crea un job y sigue su estado: 
    curl -i -X POST http://localhost:3000/jobs \
  -H 'content-type: application/json' \
  -d '{"type":"invoice.generate","payload":{"orderId":"PED-1042"}}'

    Esperado: 202, cabecera Location y un id. Consulta GET /jobs/<id> varias veces: debe pasar de queued a running y a succeeded (o failed si el procesamiento simulado falla).

  4. Mata el worker a mitad de un job: configura el procesamiento con una espera de 10 segundos y envía SIGKILL al proceso mientras está en running. Reinicia el worker. El mensaje debe reentregarse y el job completarse; el jobId no cambia. Comprueba en los logs que el segundo intento ve el lease y decide correctamente.
  5. Prueba un duplicado: publica dos veces el mismo mensaje (mismo jobId) y confirma que el efecto se ejecuta una sola vez. Si tu implementación crea dos facturas, la idempotencia no está bien puesta: revisa la reclamación y el upsert.
  6. Apagado ordenado: envía SIGTERM al worker mientras hay un job en vuelo. Debe terminar el job, hacer ack y salir con código 0 dentro del timeout. Compara el log con el del paso 4: no hay reentrega forzada.

8 · Reto

🎯 Idempotencia en el POST

Añade soporte para la cabecera Idempotency-Key en POST /jobs: si el cliente repite la petición con la misma clave, debe recibir el mismo jobId y el mismo 202, sin crear un segundo trabajo ni publicar un segundo mensaje.

El diseño debe funcionar con dos réplicas de la API y con peticiones concurrentes que llegan a la vez. Define qué pasa si la primera petición falla antes de publicar, cuánto tiempo se guarda la clave, qué se devuelve si la misma clave se usa con un cuerpo distinto y cómo se limpia la tabla de claves. Incluye una prueba con node --test que lance dos peticiones simultáneas y compruebe que solo existe un job.

Pista: una restricción única sobre la clave y una transacción que inserte el job y el registro de idempotencia resuelven la carrera; la parte difícil es qué hacer cuando la segunda petición llega antes de que la primera haya publicado.

9 · Resumen

  • La API persiste, publica con confirm y solo entonces responde 202.
  • El ack va después del efecto y del cambio de estado, nunca antes.
  • amqplib no reconecta solo: hay que recrear canal, topología y consumidor.

10 · Preguntas frecuentes

¿waitForConfirms por mensaje no es demasiado lento?

Para un endpoint que acepta un job por petición, la latencia del confirm es pequeña comparada con la del trabajo real, y la corrección vale más que unos milisegundos. Para lotes grandes, publica varios mensajes y espera una sola vez; asumes una ventana de mensajes en vuelo, pero el throughput mejora. Mide antes de optimizar.

¿Puedo procesar en paralelo dentro de un mismo worker?

Sí: prefetch permite varios mensajes en vuelo y tus handlers asíncronos se ejecutan concurrentemente. Ten en cuenta el límite del servicio externo y la CPU; si el trabajo es intensivo en CPU, más concurrencia no ayuda. Si es I/O, un prefetch de 10–20 suele ser razonable, pero el número correcto se mide con la carga real.

¿Qué hago si el broker está caído cuando arranca la API?

No aceptes tráfico que no puedes prometer. La API puede arrancar el servidor HTTP y responder 503 en POST /jobs hasta que tenga canal y topología; el healthcheck de readiness debe fallar mientras tanto. Reintenta la conexión con backoff y no bloquees el arranque en un bucle infinito sin exponer estado.

¿Por qué el worker necesita un lease si RabbitMQ ya reentrega?

Porque la reentrega no te dice si el job sigue ejecutándose en otro worker o si ya terminó. Sin lease, un mensaje reentregado tras un fallo de red puede ejecutarse en paralelo con el original. El lease acota esa ventana: si está vencido, se permite reclamar; si no, el worker espera o descarta. La idempotencia sigue siendo la última línea de defensa.
