Operación y pruebas

Módulo 7 · Proyecto final 🕐 40 minutos

1 · Introducción

La job queue funciona en tu portátil. El último paso es que siga funcionando cuando el broker se reinicie, un worker se muera, la cola crezca y alguien tenga que diagnosticarlo a las tres de la mañana. Operar no es añadir un console.log: es hacer visible el estado, automatizar las pruebas y escribir qué hacer cuando algo falla. Los reintentos y la DLQ ya existen; ahora hay que demostrar que se pueden operar.

Este cierre del proyecto se apoya en cinco piezas:

PiezaPregunta que responde
Healthchecks¿El proceso está vivo y puede aceptar trabajo ahora mismo?
Métricas¿Cuánto entra, cuánto sale, cuánto se atasca y cuánto tarda?
Logs¿Qué le pasó a este jobId concreto?
Pruebas¿La política de reintentos y el contrato del mensaje siguen siendo correctos?
Runbook¿Qué hace la persona de guardia cuando la cola crece o el broker cae?

Un sistema sin runbook no está terminado

Si la única persona que sabe qué hacer cuando la DLQ crece eres tú, el proyecto tiene un bus factor de uno. El runbook convierte conocimiento tácito en pasos reproducibles; las métricas y los logs le dan las señales para saber cuál aplicar.

Errores típicos: un liveness probe que comprueba el broker y reinicia la API en bucle cuando el broker cae, tests que comparten nombres de cola y fallan de forma intermitente, esperas de 30 segundos para probar un TTL y logs sin jobId que no permiten reconstruir un caso.

2 · Teoría

Liveness y readiness no son lo mismo

El liveness responde «¿el proceso está vivo?». El readiness responde «¿puede atender tráfico ahora?». Si mezclas ambos y haces que el liveness dependa del broker, un reinicio de RabbitMQ reinicia en cascada todos los contenedores: el broker tarda en volver, los procesos entran en CrashLoopBackOff y el sistema tarda más en recuperarse de lo necesario.

ComprobaciónEndpointSi falla
Proceso HTTP respondeGET /health/liveReiniciar el contenedor (liveness).
Canal AMQP y topología listosGET /health/readySacar la instancia del balanceador (readiness), sin reiniciar.
Consumidor activoGET /health/ready del workerReconectar o reiniciar el worker; un worker vivo pero sin consumidor no sirve.
Broker responderabbitmq-diagnostics -q pingAlerta; no reinicies la API por ello.
 
// src/health.js — el readiness no lanza; informa
export function readiness({ channel, consumerTag }) {
  const broker = Boolean(channel && channel.connection);
  const consuming = Boolean(consumerTag);
  return {
    ok: broker && consuming,
    checks: { broker, consuming },
    at: new Date().toISOString(),
  };
}

En la API, el readiness debe comprobar que el canal de publicación existe y que un publish de sondeo fue confirmado. Un canal abierto puede estar roto por dentro; la única prueba fiable es intentar una operación barata y observar el resultado.

Métricas: volumen, resultado, latencia y backlog

MétricaTipoPara qué
jobs_submitted_totalCounterVolumen de entrada; detecta picos y caídas.
jobs_completed_total{outcome}CounterProporción de éxito, reintento y fallo.
job_duration_secondsHistogramLatencia p50/p95/p99 frente al SLA.
queue_depth{queue}GaugeBacklog actual; la señal más directa de que algo se atasca.

El broker ya expone sus propias métricas con el plugin rabbitmq_prometheus en el puerto 15692: profundidad, consumidores, mensajes sin confirmar, redeliveries y alarmas. No dupliques esas cifras en la aplicación; combínalas. La aplicación aporta el contexto de negocio (tipo de job, intento, resultado) que el broker no conoce.

No pongas jobId como etiqueta

Cada valor distinto de una etiqueta crea una serie temporal. Un jobId por job genera millones de series y tumba Prometheus. Las etiquetas deben ser de cardinalidad baja: type, outcome, queue. El jobId va en los logs y en las trazas, no en las métricas.

jobs_completed_total{outcome="succeeded"} 1840
jobs_completed_total{outcome="failed"} 12
jobs_completed_total{outcome="retried"} 73
job_duration_seconds_bucket{le="0.5"} 1200
job_duration_seconds_bucket{le="2"} 1750
job_duration_seconds_bucket{le="+Inf"} 1840

Logs: el hilo del jobId

Un log útil es estructurado, tiene un identificador de correlación y no contiene el payload. En el proyecto, cada línea del ciclo de un job comparte jobId y traceId:

{"level":"info","event":"job.received","jobId":"6f1c2a9e","type":"invoice.generate","attempt":0,"traceId":"b3f1c0d2"}
{"level":"info","event":"job.succeeded","jobId":"6f1c2a9e","durationMs":842,"outcome":"succeeded","traceId":"b3f1c0d2"}
{"level":"warn","event":"job.retry_scheduled","jobId":"6f1c2a9e","attempt":1,"delayMs":5000,"error":"ETIMEDOUT","traceId":"b3f1c0d2"}
{"level":"error","event":"job.failed","jobId":"6f1c2a9e","attempt":3,"reason":"attempts_exhausted","traceId":"b3f1c0d2"}

Reglas: un evento por transición importante, no uno por línea de código; el error como código corto y mensaje saneado, sin stack completo en producción; nada de cuerpos de mensajes con datos personales; durationMs para poder cruzar con el histograma. El traceId se propaga desde la cabecera HTTP y viaja en el mensaje.

Docker Compose con healthchecks

El arranque ordenado evita el error clásico: la API arranca antes que el broker, falla al conectar y el contenedor se reinicia hasta que el broker está listo. Con depends_on: condition: service_healthy, Compose espera a que el broker responda al ping.

services:
  rabbitmq:
    image: rabbitmq:4-management
    hostname: rabbitmq
    env_file: .env
    ports:
      - "5671:5671"
      - "127.0.0.1:15671:15671"
    volumes:
      - rabbitmq-data:/var/lib/rabbitmq
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  # api: mismo patrón (build, command, env_file, depends_on: service_healthy)
  worker:
    build: .
    command: ["node", "src/worker.js"]
    env_file: .env
    depends_on:
      rabbitmq:
        condition: service_healthy

volumes:
  rabbitmq-data:

start_period da margen al broker para arrancar sin contar los fallos iniciales. Sin él, los primeros pings fallidos pueden marcar el contenedor como unhealthy antes de que termine de iniciar. Para escalar workers: docker compose up -d --scale worker=3.

Pruebas: unitarias para la política, integración para el contrato

La función planRetry es pura: recibe intento y error, devuelve una acción. Se prueba sin broker, sin Docker y sin esperas. Es la prueba que más valor aporta por línea escrita porque cubre la lógica que decide si un job se pierde, se reintenta o se entierra.

CasoEntradaEsperado
Primer fallo transitorioattempt=0, error normalretry.5s, attempt=1
Intentos agotadosattempt=3, error normaldead, attempts_exhausted
Error permanenteattempt=0, err.permanentdead, permanent

La integración prueba lo que la unidad no puede: que el mensaje se publica, que la cola existe, que el ack lo borra y que un nack lo manda a la DLQ. Debe usar nombres únicos por ejecución y limpiar al terminar; si comparte nombres con el entorno de desarrollo, los tests se pisan entre sí.

Para no esperar los TTL reales, la topología de test se declara con TTL de 100–500 ms. Eso obliga a que los TTL sean configurables por entorno; es una decisión de diseño, no un truco de test.

Runbook: síntomas, diagnóstico y acción

SíntomaQué mirarAcción
La cola de trabajo crecemessages, consumers, unacked, CPU del worker¿Hay consumers? Escalar workers; si hay 0, revisar crash y permisos. Si unacked no baja, buscar un handler colgado.
La DLQ crecex-error, tipo de job, attemptsClasificar: si es un bug, corregir y reprocesar filtrado; si es un proveedor, ajustar backoff.
El broker no respondeAlarma de memoria/disco, logs del nodoLa API devuelve 503; los workers reconectan. No borres la cola para «arreglarlo».
Mensajes sin confirmar altosmessages_unacknowledged, duración del handlerReducir prefetch, revisar timeouts del servicio externo, buscar ack olvidados.
Un job nunca terminaEstado running, leaseUntil, logs del workerEsperar el lease y reintentar; si se repite, revisar la reclamación y el timeout.

El runbook debe incluir comandos copiables y el criterio para escalar. «Mirar la cola» no es un paso; rabbitmqctl list_queues -p taller-prod name messages consumers messages_unacknowledged sí lo es, junto con el umbral que decide si se actúa.

3 · Ejemplo mínimo

Una prueba unitaria de la política de reintentos, sin broker y sin dependencias externas:

// test/retry-policy.test.js
import test from 'node:test';
import assert from 'node:assert/strict';
import { planRetry } from '../src/retry-policy.js';

test('el primer fallo transitorio reintenta a los 5 segundos', () => {
  assert.deepEqual(planRetry(0, new Error('timeout')), {
    action: 'retry',
    attempt: 1,
    routingKey: 'retry.5s',
    delayMs: 5000,
  });
});

test('el tercer fallo transitorio reintenta a los 10 minutos', () => {
  assert.equal(planRetry(2, new Error('timeout')).routingKey, 'retry.10m');
});

test('los intentos agotados van a la DLQ', () => {
  assert.deepEqual(planRetry(3, new Error('timeout')), {
    action: 'dead',
    reason: 'attempts_exhausted',
  });
});

test('un error permanente no se reintenta', () => {
  const err = Object.assign(new Error('pedido inexistente'), { permanent: true });
  assert.deepEqual(planRetry(0, err), { action: 'dead', reason: 'permanent' });
});

Ejecuta node --test. La salida resume los cuatro casos y termina con código 0. Si cambias un TTL o el número de niveles, la prueba falla antes de que el cambio llegue al broker. Es la red de seguridad más barata del proyecto.

4 · Ejemplo real

La prueba de integración usa un broker real, nombres únicos y limpieza garantizada. Se salta si no hay RABBITMQ_URL, para que node --test funcione en un portátil sin Docker.

// test/integration.test.js
import test from 'node:test';
import assert from 'node:assert/strict';
import crypto from 'node:crypto';
import amqp from 'amqplib';

const URL = process.env.RABBITMQ_URL;

test('publicar y consumir con ack borra el mensaje', { skip: !URL }, async (t) => {
  const suffix = crypto.randomUUID().slice(0, 8);
  const queue = `test.jobs.${suffix}`;
  const conn = await amqp.connect(URL);
  const ch = await conn.createConfirmChannel();

  t.after(async () => {
    await ch.deleteQueue(queue).catch(() => {});
    await ch.close();
    await conn.close();
  });

  await ch.assertQueue(queue, { durable: false, autoDelete: true });
  ch.sendToQueue(queue, Buffer.from('{"jobId":"j-1"}'), { persistent: true });
  await ch.waitForConfirms();

  const msg = await ch.get(queue, { noAck: false });
  assert.ok(msg, 'el mensaje debe estar en la cola');
  assert.equal(msg.content.toString(), '{"jobId":"j-1"}');
  ch.ack(msg);

  const after = await ch.checkQueue(queue);
  assert.equal(after.messageCount, 0);
});

La cola es única por ejecución y t.after la borra aunque el test falle. Sin esa limpieza, la segunda ejecución encuentra mensajes de la primera y el fallo parece intermitente. Para probar la DLQ, declara una cola con x-dead-letter-exchange, haz nack(requeue=false) y comprueba que el mensaje aparece en la cola de muertos; para probar reintentos, usa TTL cortos configurables.

El healthcheck del compose se apoya en el comando del broker, no en un curl a la UI: la UI puede responder mientras AMQP no acepta conexiones. rabbitmq-diagnostics -q ping comprueba el nodo de verdad, y su código de salida es el que Compose entiende.

docker compose up -d
docker compose ps                     # rabbitmq debe estar "healthy"
node --test                           # unitarias siempre; integración si hay URL
RABBITMQ_URL=amqp://taller-api:...@localhost:5672/taller-prod node --test test/integration.test.js
curl -s http://localhost:3000/health/ready | jq

Prueba el fallo, no solo el camino feliz

Un test que solo publica y consume no demuestra que el sistema sobreviva. Añade casos para: mensaje duplicado (mismo jobId), nack que va a la DLQ, worker que muere antes del ack y broker que se reinicia. Son los escenarios que rompen en producción.

6 · Errores habituales

1. Liveness que depende del broker

Mal — reinicio en cascada cuando el broker cae 
healthcheck:
  test: ["CMD", "node", "src/check-broker.js"]
  # si RabbitMQ no responde, Docker reinicia la API
Bien — liveness local, readiness con broker 
/health/live   -> 200 si el proceso responde
/health/ready  -> 200 si hay canal y consumidor
                 503 si el broker no está

El orquestador debe reiniciar el proceso cuando está colgado, no cuando su dependencia está caída. Si reinicias la API en bucle, multiplicas las reconexiones y retrasas la recuperación.

2. Tests que comparten colas

Mal — nombre fijo y estado compartido 
await ch.assertQueue('test.jobs', { durable: true });
// dos ejecuciones simultáneas se roban los mensajes
Bien — nombre único y limpieza 
const queue = `test.jobs.${crypto.randomUUID().slice(0, 8)}`;
t.after(() => ch.deleteQueue(queue).catch(() => {}));

El test pasa en local y falla en CI porque otra ejecución dejó mensajes o borró la cola. La limpieza en t.after garantiza que el entorno queda como estaba aunque el test falle.

3. Esperar los TTL reales en los tests

Mal — suite de 20 minutos 
await new Promise((r) => setTimeout(r, 600_000));   // esperar 10 min
Bien — TTL inyectado por entorno 
const ttl = Number(process.env.RETRY_5S_MS ?? 5000);
await ch.assertQueue(queue, {
  arguments: { 'x-message-ttl': ttl, 'x-dead-letter-exchange': EXCHANGE },
});

Una suite lenta deja de ejecutarse en cada commit. Si los TTL son configurables, la prueba de integración usa 100 ms y sigue verificando el mismo mecanismo.

4. Logs sin jobId o con payload

Mal — imposible correlacionar y con PII 
console.log('procesando', JSON.stringify(msg.content.toString()));
Bien — evento, identificadores y resultado 
console.log(JSON.stringify({
  event: 'job.received', jobId, type, attempt, traceId,
}));

El payload puede contener direcciones, importes o datos personales; además, un log gigante cuesta dinero y esconde la señal. Con jobId y traceId puedes reconstruir el caso consultando el almacén, sin volcar el mensaje.

7 · Ejercicio guiado

Objetivo: levantar el proyecto, comprobar salud y métricas, ejecutar las pruebas y simular una caída del broker sin perder jobs.

  1. Arranca el stack y comprueba la salud: 
    docker compose up -d
docker compose ps
curl -s http://localhost:3000/health/live
curl -s http://localhost:3000/health/ready

    Esperado: rabbitmq en healthy, la API en 200 y el worker con un consumidor activo. Si el readiness falla, mira el log del worker antes de reiniciar nada.

  2. Genera carga y observa las métricas: publica 20 jobs con curl en un bucle y consulta /metrics. jobs_submitted_total debe subir a 20 y jobs_completed_total acercarse; queue_depth debe volver a 0 cuando el worker termina.
  3. Ejecuta las pruebas unitarias: 
    node --test test/retry-policy.test.js

    Esperado: 4 tests, 0 fallos, menos de un segundo. Cambia un TTL y comprueba que la prueba falla: has verificado que la red de seguridad funciona.

  4. Ejecuta la integración contra el broker: exporta RABBITMQ_URL con el usuario de test y ejecuta node --test test/integration.test.js. Debe crear una cola con sufijo único, consumir y borrarla. Repite dos veces seguidas: no debe quedar estado que haga fallar la segunda.
  5. Simula la caída del broker: docker compose stop rabbitmq. La API debe responder 503 en POST /jobs y el readiness debe pasar a 503; el liveness debe seguir en 200. Arranca de nuevo el broker y verifica que el worker reconecta, el readiness vuelve a 200 y los jobs pendientes se procesan.
  6. Ejecuta el runbook: con un job bloqueado artificialmente, comprueba messages_unacknowledged, mata el worker, observa la reentrega y documenta en el runbook el umbral y el comando que usaste. El ejercicio termina cuando otra persona podría repetir esos pasos sin ti.

Un healthcheck que miente es peor que no tenerlo

Si el readiness devuelve 200 porque el proceso HTTP responde, pero el consumidor está muerto, el balanceador sigue enviando tráfico a una instancia que no procesa. Comprueba la pieza que realmente importa: canal, topología y consumidor activo.

8 · Reto

🎯 Simulacro de caos y SLO

Diseña un simulacro que demuestre, con evidencia, que la job queue cumple su garantía: ningún job aceptado con 202 se pierde, incluso si el broker se reinicia y un worker muere a mitad de proceso.

El simulacro debe incluir: inyección de fallos (matar el broker, matar un worker, llenar la cola), un verificador que compare los jobs aceptados con los terminados o en DLQ, y un criterio de éxito medible. Define además un SLO para la latencia de los jobs y las alertas que lo protegen, explicando qué señales son síntoma y cuáles son causa.

Pista: un contador de jobs aceptados en la API y otro de jobs en estado terminal en el almacén no cuadran si hay jobs en vuelo; el verificador debe esperar a que la cola se vacíe o usar una ventana temporal. Y matar el broker con mensajes en memoria no demuestra nada: usa mensajes persistidos en quorum y comprueba el disco.

9 · Resumen

  • Liveness comprueba el proceso; readiness comprueba canal, topología y consumidor.
  • Logs estructurados con jobId y traceId; nunca el payload con datos personales.
  • Pruebas unitarias para la política, integración con nombres únicos y TTL cortos para el contrato.
  • Runbook con síntomas, comandos y umbrales; sin él, el sistema no está operado.

10 · Preguntas frecuentes

¿Debo usar Prometheus o la management API?

Prometheus para series temporales y alertas; la management API para diagnóstico puntual y para ver el estado actual de una cola concreta. La UI es excelente para investigar y mala como fuente de alertas: no tiene retención ni consultas históricas. Expón rabbitmq_prometheus en la red de métricas y deja la UI para las personas.

¿Los tests de integración deben correr en cada commit?

Sí, si el entorno de CI puede levantar un broker efímero (Docker o Testcontainers). Si no, al menos en la pipeline que despliega a staging. Una integración que solo se ejecuta a mano se rompe sin que nadie lo note. Los tests unitarios, en cambio, deben correr siempre y en segundos.

¿Cómo pruebo la reentrega sin matar procesos a mano?

Publica un mensaje, consúmelo con noAck: false y cierra el canal sin hacer ack. El broker lo marcará como no confirmado y lo reentregará al cerrarse el canal. En un test, puedes abrir una conexión, consumir, cerrarla y abrir otra para verificar que el mensaje vuelve. Es más determinista que un kill y prueba el mismo mecanismo.

¿Qué alertas son imprescindibles y cuáles son ruido?

Imprescindibles: DLQ con mensajes, cola de trabajo creciendo por encima del umbral, cero consumidores con mensajes pendientes, alarmas de memoria/disco y readiness caído. Ruido: cada mensaje fallido individual, cada reconexión o cada pico de CPU sin relación con el backlog. Alerta sobre síntomas que requieren acción, no sobre cada evento.
