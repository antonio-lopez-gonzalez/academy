Publicar y consumir

Módulo 1 · Productores y consumidores 🕐 35 minutos

1 · Introducción

El primer mensaje usó el exchange por defecto: una cola, un destino, cero reglas. Es útil para aprender, pero acopla el productor al nombre de la cola y no permite que dos consumidores reciban el mismo evento. Un sistema real publica hechos en un exchange con nombre y deja que las bindings decidan quién los recibe.

En esta lección damos el salto: publish(exchange, routingKey, body, options), consumidores con consumerTag, mensajes con deliveryTag, cancelación ordenada y la diferencia entre «la cola está vacía» y «el mensaje no se enrutó». Son dos estados que se parecen en la UI y significan cosas opuestas.

También veremos el ciclo de vida de un consumidor. Un consumidor no es un bucle infinito sagrado: se puede cancelar, el broker puede cancelarlo si borras la cola, y un despliegue debe saber esperar a los mensajes en vuelo antes de cerrar.

Publicar y consumir son dos mundos

Publicar es un acto del productor contra un exchange; consumir es una suscripción del consumidor a una cola. Entre ambos hay una tabla de rutas y un almacén. Confundir los dos lados es la causa de la mayoría de los «no llega nada»: el mensaje se publicó bien, pero no había binding; o había binding, pero el consumidor estaba cancelado.

2 · Teoría

Exchange con nombre frente a exchange por defecto

Exchange por defecto ""Exchange con nombre
Routing keyDebe ser el nombre exacto de una cola.La decide el productor según el contrato de eventos.
BindingsNo existen: la relación es implícita.Explícitas; puedes añadir o quitar destinos sin tocar al productor.
Varios consumidoresRequiere varias publicaciones o varias colas con el mismo nombre (imposible en un vhost).Una publicación puede copiar a varias colas.
AcoplamientoEl productor conoce la cola.El productor conoce un exchange y una routing key; no las colas.
Uso típicoPrimer mensaje, RPC con cola de respuesta, tareas internas.Eventos de dominio, pub/sub, routing por tipo.

La API es simétrica: sendToQueue(q, body, opts) es publish("", q, body, opts). En cuanto necesitas una segunda cola o quieres desacoplar, pasa a un exchange con nombre.

La publicación

publish(exchange, routingKey, content, options)
   │           │            │         │
   │           │            │         └─ persistent, contentType, messageId, headers…
   │           │            └─────────── Buffer (cuerpo opaco)
   │           └──────────────────────── cadena que compara el exchange
   └──────────────────────────────────── nombre del exchange ("" = default)

channel.publish no devuelve una promesa. Devuelve un booleano que indica si el buffer del cliente aceptó el mensaje. Si es false, hay backpressure: el socket está saturado y conviene esperar al evento drain antes de seguir publicando.

const aceptado = channel.publish(exchange, key, body, options);
if (!aceptado) {
  await new Promise((resolve) => channel.once("drain", resolve));
}

Ese booleano no dice si el broker recibió el mensaje ni si acabó en una cola. Para lo primero hacen falta confirms; para lo segundo, mandatory o un alternate exchange.

El consumidor y sus dos tags

channel.consume(queue, callback, options) registra un consumidor y devuelve un consumerTag. Ese tag identifica la suscripción y se usa para cancelarla. Cada mensaje entregado trae un deliveryTag distinto, que identifica el mensaje dentro del canal:

CampoDónde viveQué significa
consumerTagResultado de consumeIdentifica la suscripción; lo usas en cancel.
deliveryTagmsg.fields.deliveryTagIdentifica el mensaje en el canal; lo usas en ack/nack.
redeliveredmsg.fields.redeliveredtrue si el broker ya lo entregó antes y no se confirmó.
exchangemsg.fields.exchangeExchange por el que se publicó.
routingKeymsg.fields.routingKeyClave con la que se publicó (no la binding key).
propertiesmsg.propertiesMetadatos: messageId, contentType, headers…

El deliveryTag es por canal, no global. Un ack hecho en otro canal no significa nada y el broker cierra el canal con un error de protocolo. Si abres un canal nuevo, los tags empiezan de cero.

Cancelar un consumidor sin perder trabajo

channel.cancel(consumerTag) deja de enviar mensajes nuevos a ese consumidor. Los que ya están en vuelo siguen esperando su ack. La cola no se borra: si quedan mensajes, se acumulan hasta que otro consumidor se suscriba.

const { consumerTag } = await channel.consume(queue, onMessage, { noAck: false });

// más tarde, en un despliegue ordenado:
await channel.cancel(consumerTag); // deja de recibir
// esperar los mensajes en vuelo (tu propio contador)
await channel.close();
await connection.close();

El broker también puede cancelar: si borras la cola, emite un evento cancel en el canal. Escucharlo evita que un worker se quede creyendo que sigue suscrito:

channel.on("cancel", (fields) => {
  console.warn("consumidor cancelado por el broker:", fields.consumerTag);
});

Cola vacía no es mensaje sin enrutar

EstadoQué pasóCómo lo detectas
Cola vacíaEl mensaje se enrutó, se entregó y se confirmó (o no había mensajes).messages = 0, consumers > 0; el consumidor registró el mensaje.
Mensaje sin enrutarNinguna binding casó; el exchange lo descartó.No hay rastro en ninguna cola. Solo lo ves con mandatory + return o alternate exchange.
Mensaje en colaSe enrutó, pero no hay consumidor o va lento.messages_ready > 0, consumers = 0 o prefetch saturado.
Mensaje unackedSe entregó y el consumidor no confirmó.messages_unacknowledged > 0.

Para no perder lo no enrutado, publica con mandatory: true y escucha return:

channel.on("return", (msg) => {
  console.warn(`no enrutado: ${msg.fields.routingKey}`, msg.content.toString());
});

channel.publish(exchange, "pedido.desconocido", body, { mandatory: true });

basic.return llega de forma asíncrona, después de la publicación. No es una excepción: si no escuchas el evento, el mensaje se pierde igual. En el módulo 2 veremos el alternate exchange como red de seguridad declarativa.

Qué garantiza cada paso

3 · Ejemplo mínimo

Un exchange direct, una cola y una binding exacta. El productor publica; el consumidor imprime los metadatos y confirma.

// publicar.mjs
import amqp from "amqplib";

const connection = await amqp.connect("amqp://guest:guest@localhost:5672");
const channel = await connection.createChannel();

await channel.assertExchange("pedidos.direct", "direct", { durable: true });
await channel.assertQueue("facturacion", { durable: true });
await channel.bindQueue("facturacion", "pedidos.direct", "pedido.creado");

channel.publish(
  "pedidos.direct",
  "pedido.creado",
  Buffer.from(JSON.stringify({ id: "1042", total: 49.9 })),
  { persistent: true, contentType: "application/json", messageId: "evt-1042" },
);

console.log("publicado pedido.creado");
await channel.close();
await connection.close();

// consumir.mjs
import amqp from "amqplib";

const connection = await amqp.connect("amqp://guest:guest@localhost:5672");
const channel = await connection.createChannel();

await channel.assertExchange("pedidos.direct", "direct", { durable: true });
await channel.assertQueue("facturacion", { durable: true });
await channel.bindQueue("facturacion", "pedidos.direct", "pedido.creado");
await channel.prefetch(1);

const { consumerTag } = await channel.consume("facturacion", (msg) => {
  if (!msg) return;
  const pedido = JSON.parse(msg.content.toString());
  console.log({
    consumerTag,
    deliveryTag: msg.fields.deliveryTag,
    exchange: msg.fields.exchange,
    routingKey: msg.fields.routingKey,
    redelivered: msg.fields.redelivered,
    messageId: msg.properties.messageId,
    pedido,
  });
  channel.ack(msg);
}, { noAck: false });

console.log(`[facturacion] esperando con ${consumerTag}`);

Salida esperada al ejecutar el consumidor y luego el productor dos veces:

[facturacion] esperando con amq.ctag-3f9a...
{
  consumerTag: 'amq.ctag-3f9a...',
  deliveryTag: 1,
  exchange: 'pedidos.direct',
  routingKey: 'pedido.creado',
  redelivered: false,
  messageId: 'evt-1042',
  pedido: { id: '1042', total: 49.9 }
}

Detalles que importan:

  • El productor declara y enlaza antes de publicar. Si publicara antes, la cola no existiría y el mensaje se perdería.
  • routingKey es pedido.creado, no facturacion: el exchange usa la binding para decidir.
  • deliveryTag=1 porque es el primer mensaje de ese canal. Si el consumidor se reconecta, vuelve a 1.
  • redelivered=false indica primera entrega. Si matas el consumidor antes del ack, la siguiente será true.
  • consumerTag lo genera el broker; puedes fijarlo tú con la opción consumerTag si necesitas identificarlo.

4 · Ejemplo real

El taller publica eventos en un topic exchange. Facturación solo quiere pedidos creados; auditoría quiere todo lo que empiece por pedido.:

exchange "pedidos" (topic)
   │
   ├── binding "pedido.creado" ──▶ cola facturacion
   └── binding "pedido.#"      ──▶ cola auditoria

publish "pedido.creado"    → facturacion + auditoria
publish "pedido.cancelado" → auditoria
publish "pago.rechazado"   → nadie (sin binding)

El productor no cambia según el destino: publica el hecho con su routing key. Si mañana se añade un servicio de fraude, se crea su cola y su binding; el productor sigue igual.

EventofacturacionauditoriaCola de facturación
pedido.creadoRecibe y confirmaRecibe y confirmaSe vacía si el consumidor está activo.
pedido.canceladoNo recibeRecibe y confirmaSin cambios.
pedido.creado con facturación canceladaSin consumidorRecibe y confirmamessages_ready sube; el mensaje espera.

Cancelar facturación no borra su cola ni sus mensajes. Si el consumidor se cae, la cola sigue acumulando:

docker exec rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers

name          messages_ready  messages_unacknowledged  consumers
auditoria     0               0                        1
facturacion   1               0                        0

Cuando facturación vuelve, recibe el pendiente. Ese es el buffer funcionando; el riesgo es que nadie mire la cifra y la cola crezca durante días.

Cancelar no es borrar

channel.cancel desuscribe al consumidor. deleteQueue borra la cola y todos sus mensajes. En un despliegue normal quieres lo primero; lo segundo es una operación destructiva que exige confirmación y permisos.

6 · Errores habituales

1. Publicar antes de crear la binding

Mal — el exchange no tiene a dónde entregar 
channel.publish("pedidos.direct", "pedido.creado", body);
await channel.bindQueue("facturacion", "pedidos.direct", "pedido.creado");
Bien — topología primero 
await channel.bindQueue("facturacion", "pedidos.direct", "pedido.creado");
channel.publish("pedidos.direct", "pedido.creado", body);

La publicación no falla: se descarta. No hay evento de error si no usas mandatory. El orden de arranque es parte del contrato.

2. Creer que publish devuelve una promesa

Mal — await sobre un booleano 
await channel.publish(exchange, key, body); // await true no espera nada
Bien — tratar el booleano como backpressure 
const ok = channel.publish(exchange, key, body);
if (!ok) await new Promise((resolve) => channel.once("drain", resolve));

publish es síncrono y escribe en el buffer del cliente. Para saber si el broker lo tiene, necesitas un confirm channel; eso es otra garantía y otra API.

3. Confirmar antes de procesar

Mal — el mensaje desaparece si el efecto falla 
channel.ack(msg);
await generarFactura(pedido);
Bien — efecto, luego ack 
await generarFactura(pedido);
channel.ack(msg);

Si el proceso muere entre el ack y el efecto, el broker no reentrega: convertiste at-least-once en at-most-once.

4. Confundir cola vacía con mensaje perdido

Mal — mirar solo messages = 0 
// ❌ "La cola está vacía, luego el mensaje nunca llegó"
Bien — distinguir enrutado, listo y no confirmado 
docker exec rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers

Una cola vacía puede significar «todo procesado» o «el exchange lo descartó». Para distinguirlo, registra la publicación y usa mandatory/return. Para ver trabajo atascado, mira messages_unacknowledged, no solo messages.

7 · Ejercicio guiado

Objetivo: observar dos consumidores independientes, cancelar uno y comprobar que sus mensajes esperan en la cola.

  1. Paso 1 — Arranca dos consumidores: guarda el consumidor del ejemplo mínimo como consumidor-facturacion.mjs y crea consumidor-auditoria.mjs cambiando la cola a auditoria y la binding a pedido.#. 
    node consumidor-facturacion.mjs
node consumidor-auditoria.mjs
  2. Paso 2 — Publica tres eventos: dos pedido.creado y uno pedido.cancelado. 
    node publicar.mjs
node publicar.mjs
node publicar.mjs   # cambia la routing key a pedido.cancelado

    Esperado: facturación recibe 2; auditoría recibe 3. Los deliveryTag de cada consumidor son independientes.

  3. Paso 3 — Cancela facturación con Ctrl+C (al cerrarse la conexión, el consumidor desaparece) y publica otro pedido.creado. 
    docker exec rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers

    name          messages_ready  messages_unacknowledged  consumers
auditoria     0               0                        1
facturacion   1               0                        0

    Auditoría lo procesa; facturación lo retiene. No se ha perdido nada.

  4. Paso 4 — Vuelve a arrancar facturación: recibe el pendiente y la cola vuelve a 0. Fíjate en redelivered: será false si nunca se había entregado, no porque se haya reencolado.
  5. Paso 5 — Publica a una routing key sin binding: usa pago.rechazado con mandatory: true y escucha return. Debe aparecer un aviso no enrutado: pago.rechazado y ninguna cola debe cambiar.
  6. Paso 6 — Comprueba la diferencia: sin mandatory, repite el paso 5. No verás ningún aviso y el mensaje desaparecerá. Anota por qué la cola vacía no era prueba de entrega.

Comprobación final

En la UI, la cola facturacion con consumers = 0 y Ready = 1 es trabajo esperando. Si además Unacked crece, el consumidor está recibiendo pero no confirmando: el problema está en el código, no en el broker.

8 · Reto

🎯 Un evento de pago con red de seguridad

Añade la cola pagos y enlázala al exchange pedidos para que reciba pedido.pagado. Publica un evento con esa clave y comprueba que llega. Después publica pago.rechazado con mandatory: true y captura el return para registrar la routing key y el cuerpo.

Responde: si el productor publica 1.000 eventos por segundo y el evento return llega después, ¿dónde guardarías los no enrutados para no perderlos? ¿Qué diferencia hay entre eso y un alternate exchange?

Pista: el evento return es asíncrono y trae el mensaje original. Un alternate exchange hace la captura en el broker, sin depender de que el productor escuche.

9 · Resumen

  • Publicar es publish(exchange, routingKey, body, options); consumir es suscribirse a una cola.
  • El exchange copia a cada cola que casa; si no hay binding, descarta el mensaje.
  • consumerTag identifica la suscripción; deliveryTag identifica el mensaje dentro del canal.
  • cancel desuscribe sin borrar la cola: los mensajes pendientes esperan a otro consumidor.
  • publish devuelve un booleano de backpressure, no una promesa ni un confirm.
  • mandatory + return revela lo que no se pudo enrutar; sin ello, se pierde en silencio.
API / conceptoQué hace
assertExchange(nombre, tipo, opts)Declara el exchange; el tipo y la durabilidad son parte del contrato.
bindQueue(cola, exchange, key)Crea la regla de enrutado.
publish(exchange, key, body, opts)Publica; devuelve false si hay backpressure.
consume(cola, cb, opts)Registra el consumidor; devuelve consumerTag.
cancel(consumerTag)Desuscribe; los mensajes pendientes quedan en la cola.
mandatory: truePide al broker que devuelva lo no enrutado.
channel.on("return", cb)Recibe los mensajes no enrutados.

10 · Preguntas frecuentes

¿Puedo hacer ack desde otro canal?

No. El deliveryTag es un identificador dentro del canal que entregó el mensaje. Si haces ack en otro canal, el broker no sabe a qué mensaje te refieres y cierra el canal con un error de protocolo. Confirma siempre en el mismo canal del consumidor.

¿Qué diferencia hay entre la routing key y la binding key?

La routing key la pone el productor en cada publicación. La binding key es la que se declaró al enlazar una cola con un exchange. El exchange compara ambas según su tipo; en direct deben ser iguales, en topic la routing key se compara con el patrón de la binding.

Si cancelo un consumidor, ¿se borran sus mensajes?

No. cancel solo desuscribe; la cola y sus mensajes siguen ahí. Se borran si usas deleteQueue, si la cola es auto-delete y se queda sin consumidores, o si el broker reinicia y la cola no era durable. La diferencia entre cancelar y borrar es la diferencia entre desplegar y destruir.

¿Por qué publish no es una promesa?

Porque AMQP 0-9-1 trata la publicación como un envío asíncrono de un frame. amqplib expone un booleano para indicar backpressure, pero no espera al broker. La confirmación real llega con un confirm channel: publicas, el broker responde con basic.ack o basic.nack, y waitForConfirms resuelve cuando todas han llegado.

¿Un mensaje puede estar en dos colas a la vez?

Sí: el exchange deposita una copia independiente en cada cola que casa. Cada copia tiene su propio deliveryTag, su ack y su redelivery. No es el mismo mensaje compartido: son copias con el mismo cuerpo y propiedades.
