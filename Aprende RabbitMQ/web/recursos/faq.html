Preguntas frecuentes

FAQ ❓ Dudas comunes del curso

Antes de empezar

¿Necesito instalar RabbitMQ en mi máquina?

No. Todo el curso usa Docker: la imagen oficial rabbitmq:4-management levanta el broker y la management UI en dos puertos. También se puede instalar de forma nativa, pero no es necesario y complica la limpieza. El proyecto final incluye su propio docker-compose.yml.

¿Qué diferencia hay entre RabbitMQ y Kafka?

RabbitMQ es un broker de mensajes: enruta mensajes a colas y los entrega a consumidores, con garantías por mensaje y borrado tras el ack. Kafka es un log distribuido con retención por tiempo/tamaño y consumidores que leen por offset. RabbitMQ brilla en colas de trabajo y routing complejo; Kafka, en streaming y replay de eventos. El curso no convierte uno en el otro: explica el modelo de RabbitMQ y cuándo encaja.

¿Necesito saber Node.js para seguir el curso?

Los ejemplos usan Node.js 22 con amqplib porque es un cliente legible y multiplataforma, pero los conceptos (exchange, cola, binding, ack, confirm, DLQ) son del protocolo AMQP y se trasladan a cualquier cliente. Si vienes de .NET, Java o Python, cambia la sintaxis, no el modelo.

Garantías y fallos

¿RabbitMQ garantiza que un mensaje se entrega exactamente una vez?

No de forma mágica. Puedes elegir at-most-once (puede perderse) o at-least-once (puede duplicarse). La entrega «exactamente una vez» se consigue a nivel de negocio con un consumidor idempotente y una clave única. El curso insiste en esto desde el primer módulo.

He activado confirms y aun así he perdido mensajes. ¿Qué falta?

Un confirm solo dice que el broker aceptó la publicación. Si el exchange no tiene bindings, el mensaje se descarta salvo que uses mandatory o un alternate exchange. Y si la cola no es durable, o el mensaje no es persistente, un reinicio lo borra. Revisa las tres capas: publicación, enrutamiento y almacenamiento.

¿Por qué mi consumidor recibe el mismo mensaje varias veces?

Porque el ack no llegó a tiempo, el canal se cerró o el consumidor hizo nack(requeue=true). En at-least-once es normal. Diseña el consumidor para que repetir no duplique efectos: una tabla de idempotencia, una restricción única o una operación idempotente en el destino.

Operación y producción

¿Classic queue o quorum queue?

Para trabajo durable, quorum: replica con Raft, elige líder y sobrevive a la caída de un nodo. Las classic queues siguen existiendo para casos concretos (por ejemplo, colas efímeras o exclusivas), pero no son la opción por defecto del curso. Las mirrored classic queues fueron retiradas y no se enseñan como solución de alta disponibilidad.

¿Un clúster de RabbitMQ me da alta disponibilidad automáticamente?

No por sí solo. Un clúster reparte colas entre nodos; para que una cola sobreviva a la caída de un nodo necesitas quorum queues (réplica) y una buena configuración de red. Además, las particiones de red y las alarmas de disco/memoria pueden bloquear publicadores. El módulo 5 lo trata en detalle.

¿Cómo evito que un mensaje venenoso bloquee la cola?

Con un límite de reintentos y una DLQ. No uses nack(requeue=true) en bucle: manda el mensaje a una cola de reintento con TTL/backoff y, tras N intentos, a la DLQ. Añade métricas y una alerta cuando la DLQ crece.

El proyecto final

¿Qué construye exactamente el proyecto?

Una job queue con una API HTTP que encola trabajos, uno o varios workers que los procesan, reintentos con backoff, DLQ, apagado ordenado y pruebas con node --test. Todo se levanta con Docker Compose y se puede ejecutar en local sin servicios externos.

¿Puedo usar el proyecto con otro lenguaje?

Sí. El proyecto de referencia está en Node.js, pero el diseño (exchange, cola, ack, reintentos, DLQ) es portable. Si lo reescribes en .NET, Python o Java, mantén las garantías y las pruebas; el curso valora el modelo, no la sintaxis.
