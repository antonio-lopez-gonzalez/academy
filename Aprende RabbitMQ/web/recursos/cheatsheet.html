Cheatsheet de RabbitMQ

Referencia rápida 🧭 por intención · RabbitMQ 4.4 + amqplib

El mapa antes de los comandos

Un productor publica en un exchange; el exchange enruta a una o varias colas según sus bindings; un consumidor lee de una cola. Publicar y entregar son dos garantías distintas. Antes de escribir código, decide quién sostiene qué.

productor ──basic.publish──▶ exchange ──binding + routing key──▶ cola ──basic.consume──▶ consumidor
     │                          │                                   │                        │
     │ publisher confirm        │ alternate exchange                │ durabilidad            │ ack / nack
     └── «el broker lo tiene»   └── «si no enruta, avisa»          └── «sobrevive reinicio» └── «lo he procesado»
Si buscas…Quién lo garantizaMecanismo
Que el broker reciba la publicaciónProductor + brokerconfirmChannel + waitForConfirms
Que el mensaje no se pierda si la cola caeBrokerCola durable + mensaje persistent + quorum queue
Que el consumidor no pierda trabajo a mediasConsumidorack manual tras procesar
Que un fallo no bloquee la colaDiseñoDLX + límite de reintentos + idempotencia
Que no se acumule sin controlBrokerx-max-length, TTL, prefetch

La regla del curso: no hay entrega «exactamente una vez» gratis. Elige at-most-once (puedes perder) o at-least-once (puedes duplicar) y haz el consumidor idempotente. Ver Idempotencia y reintentos.

Publicar y consumir con amqplib

import amqp from "amqplib";

const connection = await amqp.connect(process.env.AMQP_URL);
const channel = await connection.createConfirmChannel();

// Infraestructura idempotente: declarar siempre, no crear a mano en la UI
await channel.assertExchange("pedidos", "topic", { durable: true });
await channel.assertQueue("facturacion", {
  durable: true,
  arguments: { "x-queue-type": "quorum" },
});
await channel.bindQueue("facturacion", "pedidos", "pedido.creado");

// Publicación persistente + confirm
channel.publish(
  "pedidos",
  "pedido.creado",
  Buffer.from(JSON.stringify({ id: "1042", total: 49.9 })),
  { persistent: true, contentType: "application/json", messageId: "pedido-1042" }
);
await channel.waitForConfirms();

// Consumo con ack manual y prefetch
await channel.prefetch(10);
await channel.consume("facturacion", async (msg) => {
  if (!msg) return;
  try {
    const pedido = JSON.parse(msg.content.toString());
    await facturar(pedido);          // idempotente por pedido.id
    channel.ack(msg);
  } catch (err) {
    channel.nack(msg, false, false); // a DLX, sin reencolar en bucle
  }
});
Quiero…API
Canal con confirmsconnection.createConfirmChannel()
Declarar cola durable quorumassertQueue(name, { durable: true, arguments: { "x-queue-type": "quorum" } })
Limitar mensajes en vuelochannel.prefetch(n)
Rechazar sin reencolarchannel.nack(msg, false, false)
Reencolar para otro intentochannel.nack(msg, false, true) (con cuidado)
Cancelar un consumidorchannel.cancel(consumerTag)

await channel.assertExchange("pedidos", "topic", { durable: true });
await channel.bindQueue("facturacion", "pedidos", "pedido.creado");

await channel.bindQueue("cancelaciones", "pedidos", "pedido.cancelado");

// Alternate exchange: lo que no enruta no desaparece
await channel.assertExchange("pedidos.ae", "fanout", { durable: true });
await channel.assertExchange("pedidos", "topic", {
  durable: true,
  alternateExchange: "pedidos.ae",
});

Fiabilidad: DLQ, TTL y reintentos

// Cola de trabajo con dead-letter exchange y límite de longitud
await channel.assertExchange("pedidos.dlx", "direct", { durable: true });
await channel.assertQueue("pedidos.dlq", { durable: true });
await channel.bindQueue("pedidos.dlq", "pedidos.dlx", "fallido");

await channel.assertQueue("facturacion", {
  durable: true,
  arguments: {
    "x-queue-type": "quorum",
    "x-dead-letter-exchange": "pedidos.dlx",
    "x-dead-letter-routing-key": "fallido",
    "x-message-ttl": 60_000,
    "x-max-length": 10_000,
  },
});
Quiero…Configuración
Mensajes fallidos apartex-dead-letter-exchange + cola DLQ
Reintentar con esperaTTL en cola de reintento + DLX de vuelta a la principal
Limitar intentosCabecera x-death / contador propio + DLQ final
Evitar duplicadosClave de negocio única + deduplicación en consumidor
No bloquear la colaprefetch, timeouts y nack sin requeue

Reencolar en bucle es un anti-patrón. Un mensaje venenoso con nack(requeue=true) vuelve al frente una y otra vez y consume CPU. Mándalo a una cola de reintento con backoff o a la DLQ.

Operación y seguridad

# Colas, consumidores y mensajes listos
docker exec rabbitmq rabbitmqctl list_queues name type messages messages_ready messages_unacknowledged consumers

# Políticas (aplican a colas/exchanges existentes)
docker exec rabbitmq rabbitmqctl set_policy ha-quorum '^taller\.' \
  '{"queue-mode":"default","delivery-limit":5}' --apply-to queues

# Alarmas y recursos
docker exec rabbitmq rabbitmqctl status
docker exec rabbitmq rabbitmqctl eval 'rabbit_alarm:get_alarms().'

# Métricas Prometheus (plugin)
docker exec rabbitmq rabbitmq-plugins enable rabbitmq_prometheus

# TLS: usar amqps:// y verificar el certificado; nunca desactivar la verificación

Todo como código. Declara exchanges, colas, bindings y políticas en el arranque de la aplicación o en un script versionado. La management UI sirve para observar, no para ser la única fuente de verdad.
