Bases de datos gestionadas

Módulo 3 · Almacenamiento y datos 🕐 35 minutos

1 · Introducción

El Copiloto tiene usuarios, conversaciones, mensajes y cuentas de uso. Eso es dato estructurado con relaciones y transacciones, y su sitio es una base de datos relacional. La pregunta no es «¿PostgreSQL o MySQL?», sino «¿quién la opera?».

Puedes instalar PostgreSQL en una máquina virtual y encargarte de todo: parchear el sistema operativo, configurar la replicación, montar los backups, vigilar el disco que se llena. O puedes usar una base de datos gestionada —Azure Database for PostgreSQL, Amazon RDS— y dejar que el proveedor haga ese trabajo mientras tú te centras en el esquema y las consultas. Esta lección trata exactamente de eso: qué te quitan de encima, qué sigues siendo responsable de hacer, y cómo se materializa todo en Terraform.

¿Por qué existe esta lección? Porque el error más caro de un desarrollador en la nube es tratar la base de datos como un detalle de infraestructura y desplegar una que no se puede escalar, ni respaldar, ni recuperar. Aquí aprendes a elegir el tamaño, la alta disponibilidad y la retención con criterio, no por copiar-pegar.

2 · Teoría

Gestionado frente a autogestionado: dónde está la frontera

«Gestionado» no significa «no haces nada». Significa que el proveedor opera una capa y tú operas otra. La frontera es muy concreta:

TareaEn una VM tuyaEn una base gestionada
Parchear el sistema operativoTúEl proveedor
Instalar y actualizar el motor (PostgreSQL…)TúEl proveedor (eliges la versión mayor)
Backups automáticosTú (scripts + almacenamiento)El proveedor (incluidos, retención configurable)
Alta disponibilidad y failoverTú (replicación manual)El proveedor (se activa con una opción)
Reemplazar un disco que fallaTúEl proveedor
Esquema, índices, consultas, migracionesTúTú
Elegir tamaño, retención y HATú (con más esfuerzo)Tú (con parámetros)

La frase para recordar: el proveedor se ocupa de la máquina; tú te ocupas del dato. Diseñar tablas, índices y migraciones sigue siendo tu trabajo, y es donde de verdad se gana o se pierde rendimiento.

Analogía: una base gestionada es un coche con mantenimiento incluido. No conduces igual de mal por ello, pero ya no cambias el aceite ni te preocupa la correa de distribución. Sigues siendo responsable de no estrellarte (tu esquema y tus consultas).

El modelo mental: servidor, base de datos y conexión

                  SERVICIO GESTIONADO (el proveedor lo opera)
  +-----------------------------------------------------------+
  |  SERVIDOR  (SKU, vCPU, RAM, almacenamiento, HA, backups)  |
  |                                                           |
  |   +----------------+    +----------------+               |
  |   |  database:     |    |  database:     |               |
  |   |  copiloto      |    |  copiloto_test |               |
  |   +----------------+    +----------------+               |
  |                                                           |
  |   conexiones  <-- apps se conectan por una cadena o,      |
  |                   mejor, por identidad gestionada          |
  +-----------------------------------------------------------+

Cuando creas el recurso, eliges tres cosas que determinan coste y comportamiento: el tamaño (SKU), el almacenamiento y la alta disponibilidad. El resto (backups, conexión) se configura con parámetros.

Escalado: vertical, horizontal y el cuello de botella de conexiones

  • Escalado vertical (scale up): darle al servidor más CPU y RAM (subir de SKU). Es la palanca principal en bases gestionadas y normalmente implica un reinicio breve.
  • Escalado horizontal (read replicas): añadir servidores de solo lectura que replican el principal. Sirve para repartir lecturas (informes, analítica), no para las escrituras, que siguen yendo al primario.
  • Conexiones: cada conexión a PostgreSQL consume memoria. Con muchos workers el límite de conexiones salta antes que la CPU. La solución es un pooler (PgBouncer) que multiplexa cientos de clientes sobre unas pocas conexiones reales.

Dato clave: el almacenamiento suele crecer automáticamente cuando se llena (autogrow), pero la CPU y la RAM no. Una base que escala en disco y no en cómputo acabará lenta. Y ojo: los SKU Burstable son baratos pero no soportan alta disponibilidad; no los uses para producción crítica.

Alta disponibilidad: qué pasa cuando cae la zona

La HA gestionada funciona con un servidor de reserva (standby) que recibe las mismas escrituras de forma síncrona. Si el primario falla, el proveedor conmuta al reserva automáticamente:

  • SameZone: el reserva está en la misma zona de disponibilidad. Más barato, protege contra el fallo de una máquina, no contra la caída de una zona.
  • ZoneRedundant: el reserva está en otra zona. Protege contra la caída de una zona entera; es lo recomendable para producción.

La conmutación tiene un coste real: unos segundos de indisponibilidad y un blip en las conexiones. Ese tiempo forma parte de tus objetivos de RTO (lección 04).

Backups y PITR: el detalle importa

Toda base gestionada toma copias automáticas y un registro continuo de transacciones (WAL en PostgreSQL, binlog en MySQL). Eso permite la restauración a un punto en el tiempo (PITR): «devuélveme la base tal como estaba a las 10:42 de anteayer». Los parámetros típicos:

ParámetroValor habitualQué implica
Retención de backup7 a 35 días (PostgreSQL Flexible Server)Cuánto atrás puedes viajar; más días = más coste
Backup geo-redundanteActivado / desactivadoPermite restaurar incluso si la región entera cae
Ventana de mantenimientoFranja elegibleCuándo el proveedor aplica parches

La copia automática no es «tu» backup. La retención máxima suele ser de semanas, y el backup vive en la misma cuenta. Para requisitos legales o de largo plazo (años), exporta copias a un contenedor de objetos con retención propia. Lo montamos en la lección 04.

Elegir SKU sin equivocarse

FamiliaCuándoAviso

3 · Ejemplo mínimo

El servidor más pequeño posible: un PostgreSQL gestionado con el SKU más modesto, backups de una semana y sin acceso público. Con la CLI de Azure:

terminal
# Flexible Server: la oferta actual de PostgreSQL gestionado en Azure.
# B_Standard_B1ms = Burstable, el SKU más barato. Solo para practicar.
az postgres flexible-server create \
  --resource-group rg-copiloto \
  --name copiloto-pg-lab \
  --location westeurope \
  --tier Burstable \
  --sku-name Standard_B1ms \
  --version 16 \
  --storage-size 32 \
  --admin-user copiloto \
  --admin-password "$(openssl rand -base64 24)" \
  --backup-retention 7 \
  --public-access None      # sin exposición a Internet

# Una base de datos dentro del servidor.
az postgres flexible-server db create \
  --resource-group rg-copiloto \
  --server-name copiloto-pg-lab \
  --database-name copiloto

Qué hace cada decisión, línea a línea:

  1. --tier Burstable y --sku-name Standard_B1ms: el tamaño. Barato, útil para aprender; no para producción con HA.
  2. --backup-retention 7: puedes restaurar a cualquier instante de los últimos 7 días (PITR).
  3. --public-access None: el servidor nace sin IP pública. Se accede por red privada (módulo 2).
  4. --admin-password: aquí generamos uno al vuelo, pero en producción nunca va en el comando: se usa identidad gestionada o Azure Key Vault.

4 · Ejemplo real

La base del Copiloto en producción, en Terraform: General Purpose, alta disponibilidad por zonas, backup geo-redundante con 35 días de retención y red privada. Este es el recurso que de verdad importa proteger.

database.tf
resource "azurerm_postgresql_flexible_server" "copiloto" {
  name                = "copiloto-pg-prod"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  version             = "16"

  # Producción: equilibrado y con HA. Nunca Burstable aquí.
  sku_name   = "GP_Standard_D2s_v3"
  storage_mb = 65536          # 64 GB; el disco crece solo si se llena

  # Credenciales por variables; en el repo no hay secretos (módulo 2).
  administrator_login    = "copiloto"
  administrator_password = var.postgres_admin_password

  # Alta disponibilidad: reserva en otra zona -> sobrevive a la caída de una zona.
  high_availability {
    mode                      = "ZoneRedundant"
    standby_availability_zone = "2"
  }

  # Copia automática GEO-redundante y 35 días de retención (el máximo):
  # permite restaurar a un instante concreto incluso si cae la región.
  backup_retention_days        = 35
  geo_redundant_backup_enabled = true

  # Sin IP pública: se accede por red privada y punto de conexión privado.
  public_network_access_enabled = false

  # El servidor solo es accesible desde la subred delegada del Copiloto.
  delegated_subnet_id = azurerm_subnet.postgres.id
  private_dns_zone_id = azurerm_private_dns_zone.postgres.id

  # Ventana de mantenimiento: parcheamos de madrugada, en hora valle.
  maintenance_window {
    day_of_week  = 0   # domingo
    start_hour   = 3
    start_minute = 0
  }

  tags = { project = "copiloto", env = "prod" }
}

# La base de datos que usa la API del Copiloto.
resource "azurerm_postgresql_flexible_server_database" "copiloto" {
  name      = "copiloto"
  server_id = azurerm_postgresql_flexible_server.copiloto.id
  charset   = "UTF8"
  collation = "en_US.utf8"
}

Y cuando la carga de lecturas crece (informes, métricas), añadimos una réplica de lectura sin tocar el primario:

replica.tf
resource "azurerm_postgresql_flexible_server" "replica" {
  name                = "copiloto-pg-replica"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  version             = "16"

  # create_mode = Replica convierte este servidor en copia de solo lectura.
  create_mode      = "Replica"
  source_server_id = azurerm_postgresql_flexible_server.copiloto.id

  sku_name   = "GP_Standard_D2s_v3"
  storage_mb = 65536
}

Lo que hay que entender de este ejemplo:

  • ZoneRedundant es lo que te permite dormir: si cae una zona, el proveedor conmuta al reserva en otra.
  • 35 días + geo-redundante define tu ventana de recuperación. Es un parámetro de negocio, no técnico: ¿cuánto pasado necesitas poder recuperar?
  • La réplica no es HA. La HA te protege de un fallo; la réplica reparte lecturas. Son cosas distintas que a veces se confunden.

Azure ↔ AWS: el equivalente es Amazon RDS (con MultiAZ = true para HA), Aurora para cargas exigentes, y read replicas creadas con aws_db_instance o aws_rds_cluster. La retención se controla con backup_retention_period y el PITR viene del mismo registro de transacciones. El vocabulario cambia; las ideas son idénticas.

6 · Errores habituales

Error 1: abrir la base al mundo para «probar la conexión»

Permitir todas las IPs es cómodo durante cinco minutos y un agujero permanente si se queda.

✗ Incorrecto — firewall abierto 
resource "azurerm_postgresql_flexible_server_firewall_rule" "abierto" {
  name             = "temporal"
  server_id        = azurerm_postgresql_flexible_server.copiloto.id
  start_ip_address = "0.0.0.0"
  end_ip_address   = "255.255.255.255"   # TODO INTERNET puede intentar conectar
}
✓ Correcto — sin IP pública + red privada 
resource "azurerm_postgresql_flexible_server" "copiloto" {
  # ...
  public_network_access_enabled = false        # ni siquiera hay IP pública
  delegated_subnet_id           = azurerm_subnet.postgres.id
  private_dns_zone_id           = azurerm_private_dns_zone.postgres.id
}

Error 2: la contraseña del administrador en el repositorio

El error que más veces he visto en revisiones. Un valor por defecto en variables.tf parece inofensivo hasta que llega a un repositorio público.

✗ Incorrecto — secreto versionado 
variable "postgres_admin_password" {
  type    = string
  default = "Copiloto1234!"   # en el repo. Visible para siempre en el historial.
}
✓ Correcto — secreto sin valor por defecto 
variable "postgres_admin_password" {
  type      = string
  sensitive = true
  # Sin default: se inyecta desde Key Vault o desde el entorno de CI (módulo 2).
}

Error 3: elegir Burstable para producción

Es tentador por precio, pero esos SKU comparten CPU, no admiten alta disponibilidad y su rendimiento es impredecible bajo carga.

✗ Incorrecto — barato pero frágil 
resource "azurerm_postgresql_flexible_server" "copiloto" {
  sku_name = "B_Standard_B1ms"   # producción sobre CPU "prestada": no.
  high_availability { mode = "ZoneRedundant" }
  # Este bloque FALLA: Burstable no soporta alta disponibilidad.
}
✓ Correcto — General Purpose + HA 
resource "azurerm_postgresql_flexible_server" "copiloto" {
  sku_name = "GP_Standard_D2s_v3"      # CPU dedicada y predecible
  high_availability {
    mode = "ZoneRedundant"             # conmutación automática entre zonas
  }
}

Error 4: confundir réplica de lectura con alta disponibilidad

Una réplica no conmuta sola. Si el primario cae, la réplica sigue ahí pero sin promover automáticamente: sigues caído.

✗ Incorrecto — "ya tengo réplica, tengo HA" 
resource "azurerm_postgresql_flexible_server" "replica" {
  # create_mode = Replica sirve para REPARTIR LECTURAS, no para failover.
  create_mode      = "Replica"
  source_server_id = azurerm_postgresql_flexible_server.copiloto.id
  # Sin bloque high_availability: no hay conmutación automática.
}
✓ Correcto — HA en el primario, réplica aparte 
resource "azurerm_postgresql_flexible_server" "copiloto" {
  sku_name = "GP_Standard_D2s_v3"
  high_availability {
    mode = "ZoneRedundant"   # ESTO da continuidad ante un fallo
  }
}
# La réplica es un recurso adicional SOLO para repartir lecturas.

7 · Ejercicio guiado

Objetivo: crear un PostgreSQL gestionado, conectarte, comprobar la retención de backup y ver las opciones de restauración a un punto en el tiempo (PITR). Resultado esperado: ves la lista de backups disponibles con sus ventanas de tiempo.

  1. Paso 1: crea el servidor (SKU barato, retención 7 días) y permite el acceso desde tu IP temporalmente: 
    az group create --name rg-cloud-db --location westeurope

az postgres flexible-server create \
  --resource-group rg-cloud-db \
  --name copiloto-pg-lab \
  --location westeurope \
  --tier Burstable --sku-name Standard_B1ms \
  --version 16 --storage-size 32 \
  --admin-user copiloto \
  --admin-password "$(openssl rand -base64 24)" \
  --backup-retention 7 --public-access "$(curl -s ifconfig.me)"
  2. Paso 2: crea una base y una tabla, e inserta una fila: 
    -- Conéctate con: psql "host=copiloto-pg-lab.postgres.database.azure.com
--                   port=5432 dbname=postgres user=copiloto sslmode=require"
CREATE DATABASE copiloto;
\c copiloto
CREATE TABLE conversaciones (
  id         bigserial PRIMARY KEY,
  usuario    text        NOT NULL,
  creada_en  timestamptz NOT NULL DEFAULT now()
);
INSERT INTO conversaciones (usuario) VALUES ('ana'), ('luis');
SELECT count(*) FROM conversaciones;   -- esperado: 2
  3. Paso 3: comprueba la configuración de backup del servidor: 
    az postgres flexible-server show \
  --resource-group rg-cloud-db --name copiloto-pg-lab \
  --query "{retencion:backup.backupRetentionDays, geo:backup.geoRedundantBackup}"
# Esperado: retencion = 7, geo = "Disabled" (no lo activamos para no gastar)
  4. Paso 4: lista los backups y las horas a las que podrías restaurar: 
    az postgres flexible-server backup list \
  --resource-group rg-cloud-db --server-name copiloto-pg-lab

az postgres flexible-server restore \
  --resource-group rg-cloud-db --name copiloto-pg-restored \
  --source-server copiloto-pg-lab \
  --restore-time "2026-10-11T10:00:00Z"   # PITR: un instante concreto

    La restauración crea un servidor nuevo con el estado de ese instante. No sobreescribe el original: por eso el PITR es seguro.

  5. Paso 5 (limpieza): borra el grupo completo. Las bases gestionadas se facturan mientras existen: 
    az group delete --name rg-cloud-db --yes --no-wait

Fíjate en lo que NO has hecho: en ningún momento has instalado PostgreSQL, configurado replicación ni escrito un script de backup. Solo has tomado decisiones de tamaño, red y retención. Eso es exactamente lo que compras con una base gestionada.

9 · Resumen

  • Una base gestionada deja al proveedor la máquina; tú sigues siendo dueño del dato (esquema, índices, migraciones).
  • Tres decisiones definen coste y fiabilidad: tamaño (SKU), almacenamiento y alta disponibilidad.
  • El escalado vertical (más vCPU/RAM) es la palanca principal; las réplicas reparten lecturas, no escrituras.
  • La HA ZoneRedundant conmuta automáticamente ante un fallo; una réplica no.
  • Los backups automáticos dan PITR (restauración a un instante) dentro de la retención configurada (7–35 días).
  • El backup vive en la misma cuenta y caduca: para retenciones largas o legales, exporta a almacenamiento de objetos (lección 04).
  • Reglas de oro: red privada, sin secretos (Key Vault / identidad gestionada), y pooler cuando hay muchos workers.

10 · Preguntas frecuentes

¿Gestionado sale más caro que una VM con PostgreSQL instalado?

El precio de la máquina puede ser mayor, pero el coste total casi nunca. La VM te exige tiempo de ingeniería (parcheo, backups, replicación, guardias) que no aparece en la factura de cloud pero sí en tu nómina. Salvo cargas muy concretas, gestionado gana.

Si tengo alta disponibilidad, ¿ya no necesito backups?

No. La HA protege contra el fallo de la máquina; los backups te protegen contra el fallo humano y el lógico: borrar una tabla por error, un deploy con una migración destructiva o un ransomware. Se replican esos errores al reserva al instante. Necesitas las dos cosas.

¿Cuándo elijo una réplica de lectura y cuándo subo de SKU?

Si el problema es volumen de lecturas (informes, dashboards) y el primario va sobrado en CPU, añade réplica. Si el problema es que todas las operaciones (lecturas y escrituras) van lentas, el primario necesita más recursos: sube de SKU.

¿Puedo cambiar de versión mayor del motor (16 → 17) sin recrear el servidor?

Normalmente no de forma directa: los proveedores ofrecen un proceso de upgrade de versión mayor, o bien restauras un backup en un servidor nuevo de la versión destino. Las versiones menores sí se aplican de forma transparente. Planifica el salto como un proyecto, no como un parámetro.

¿Por qué me hablas de un pooler si la base tiene un límite de conexiones alto?

Porque el límite «alto» no es infinito y cada conexión cuesta memoria. Con decenas de workers o serverless que escalan a cientos de instancias, el número de conexiones estalla. PgBouncer multiplexa muchas conexiones de cliente sobre unas pocas reales y evita el error «too many connections» en el peor momento.
