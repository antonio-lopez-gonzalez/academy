Caché y colas

Módulo 3 · Almacenamiento y datos 🕐 30 minutos

1 · Introducción

Dos problemas aparecen siempre que el Copiloto crece. El primero: la misma consulta a la base de datos se repite mil veces por segundo y la base se ahoga. El segundo: el usuario pide un informe que tarda dos minutos en generarse y no puede quedarse mirando una pantalla en blanco. Las soluciones clásicas son una caché y una cola, y en la nube se compran gestionadas.

Una caché (Azure Cache for Redis, ElastiCache) guarda resultados ya calculados en memoria para responder en microsegundos y descargar la base de datos. Una cola (Azure Service Bus, Amazon SQS) guarda mensajes para que un worker los procese en su ritmo, desacoplando al que pide del que hace. Son dos piezas distintas que resuelven dos «por qué» distintos —rapidez y desacoplamiento— y esta lección las aborda sin confundirlas.

¿Por qué existe esta lección? Porque ya viste Redis en Aprende Redis, pero allí lo entendiste como tecnología; aquí lo ves como servicio gestionado de la nube: cuándo añadirlo, cuánto cuesta y qué te aporta el proveedor. Y porque las colas son la puerta de entrada a los eventos, que serán el corazón del módulo 5.

2 · Teoría

Caché: por qué una respuesta en memoria lo cambia todo

Leer de una base de datos relacional implica disco, planes de consulta y viajes de red: milisegundos. Leer de una caché en memoria es microsegundos. Ese salto de dos órdenes de magnitud permite, con la misma base de datos, atender cien veces más tráfico. La caché no sustituye a la base: absorbe las lecturas repetidas.

El patrón canónico se llama cache-aside (o lazy loading) y se resume en tres pasos:

  Petición --> ¿Está en la CACHÉ?
                 |                     |
                SÍ -> devolver (microsegundos)  [HIT]
                 |
                NO -> leer de la BASE DE DATOS  [MISS]
                      --> guardar en la CACHÉ con un TTL
                      --> devolver
ConceptoQué esPor qué importa
TTLTiempo de vida de una claveSin TTL el dato caduca mal; con TTL, se refresca solo y el error del que olvidó invalidar duele menos
InvalidaciónBorrar/actualizar al cambiar el origenLa caché no ve tus escrituras por sí sola; si no invalida, sirve basura
Eviction (LRU)Qué se borra al llenarseLa caché tiene tope de memoria: necesita decidir a quién sacrifica
Cache stampedeMuchos MISS a la vez sobre la misma clavePuede tumbar la base; se mitiga con locking o TTL con jitter

La caché no es fuente de verdad. El dato autoritativo vive en la base de datos; la caché es una copia que puede desaparecer en cualquier momento. Trátala siempre como material regenerable. Si al borrar la caché tu sistema pierde datos, no tenías una caché: tenías una base de datos mal configurada.

Colas y eventos: desacoplar para no bloquear

Una cola invierte el flujo: en vez de que el usuario espere a que la operación termine, la API encola un mensaje y responde «recibido» al instante. Un worker lo toma cuando puede. El diagrama es siempre el mismo:

  API  --->  COLA  --->  WORKER (uno o varios)
   |                       |
   |                       +--> escribe resultado en la BASE
   +--> responde 202 Accepted al usuario inmediatamente

  Si el worker se cae, el mensaje sigue en la cola.
  Si hay más carga, se lanzan más workers: la cola absorbe el pico.

Hay dos grandes familias de servicio y conviene no confundirlas:

TipoAzureAWSIdea
ColaService Bus (Queues)SQSUn consumidor procesa cada mensaje una vez
Pub/SubService Bus (Topics/Subscriptions)SNSUn mensaje llega a varios suscriptores
Eventos/reactorEvent GridEventBridgeReaccionar a «algo pasó» (blob creado, usuario registrado)
StreamingEvent HubsKinesis (o Kafka/MSK)Flujo continuo y ordenado con muchos consumidores

Dato clave: «cola» y «streaming» no son lo mismo. Una cola reparte el trabajo (cada mensaje, un worker); un stream lo difunde y lo conserva durante días (varios consumidores leen los mismos eventos). Elige según si repartes tareas o alimentas varios sistemas con el mismo flujo.

Garantías de entrega: aquí se gana la fiabilidad

  • At-least-once (al menos una vez): el caso por defecto. Un mensaje puede entregarse dos veces (por ejemplo, si el worker cae justo tras procesarlo). Consecuencia: el consumidor debe ser idempotente.
  • At-most-once (como mucho una vez): se puede perder, no se duplica. Sirve para métricas, no para dinero.
  • Exactly-once: casi siempre es una ilusión práctica; se consigue sumando entregas at-least-once + idempotencia en el consumidor.

Y dos mecanismos que te salvan la operación:

MecanismoQué hace
Visibility timeoutEl mensaje desaparece temporalmente mientras se procesa; si el worker no confirma, vuelve a estar visible
Dead-letter queue (DLQ)Mensajes que fallaron N veces van a una cola aparte para que no bloqueen ni se pierdan silenciosamente

Su relación con lo que ya sabes

  • Con la base de datos (lección 02): la caché descarga lecturas; la cola descarga escrituras lentas. Ambas protegen la misma base que acabas de aprender a dimensionar.
  • Con el almacenamiento de objetos (lección 01): el worker de una cola suele escribir el resultado (un PDF) en un contenedor y guardar solo la referencia en la base.
  • Con la red (módulo 2): tanto la caché como la cola deben ser privadas, accedidas por identidad gestionada o claves en Key Vault, nunca con acceso público.
  • Con el módulo 5: las colas de hoy son la base de las arquitecturas serverless por eventos de mañana.

3 · Ejemplo mínimo

Dos líneas para una caché, dos para una cola. Primero, la caché: guardar un valor con TTL y recuperarlo.

terminal
# --- CACHÉ: guardar con tiempo de vida (TTL) de 60 segundos ---
# SET con el flag EX: el valor se autodestruye a los 60 s. Nunca olvides el TTL.
redis-cli SET "usuario:42:saludo" "hola copiloto" EX 60

# GET devuelve el valor si sigue vivo; si expiró, devuelve nil.
redis-cli GET "usuario:42:saludo"
# TTL dice cuántos segundos le quedan antes de desaparecer.
redis-cli TTL "usuario:42:saludo"

Y ahora la cola: crear una cola y enviar un mensaje que un worker procesará más tarde.

terminal
# --- COLA: crear una cola en Service Bus ---
az servicebus queue create \
  --resource-group rg-copiloto \
  --namespace-name copiloto-bus \
  --name informes \
  --max-delivery-count 5        # tras 5 intentos fallidos -> dead-letter

# Enviar un trabajo: "genera el informe del usuario 42".
az servicebus queue message send \
  --resource-group rg-copiloto \
  --namespace-name copiloto-bus \
  --queue-name informes \
  --body '{"user_id":42,"tipo":"informe_mensual"}'

Qué acaba de pasar:

  1. SET ... EX 60: la clave existe en memoria 60 segundos. El EX es el seguro contra datos obsoletos.
  2. TTL: no adivines cuándo caduca: pregúntalo. Un TTL que se acaba de repente explica muchos bugs fantasma.
  3. max-delivery-count 5: si el worker falla cinco veces, el mensaje va a la DLQ en lugar de reintentarse para siempre.
  4. message send: la API no genera el informe, solo deja el encargo. Volverá a responder inmediatamente al usuario.

4 · Ejemplo real

El Copiloto usa las dos piezas juntas. Redis cachea las respuestas del modelo que se repiten (una pregunta frecuente no vuelve a costar una llamada al modelo), y Service Bus encola la generación de informes para no bloquear la API. Terraform:

cache.tf
# Caché gestionada para respuestas repetidas del Copiloto.
resource "azurerm_redis_cache" "copiloto" {
  name                = "copiloto-cache"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location

  # Standard: tiene réplica para failover. Basic no lo uses en producción.
  sku_name = "Standard"
  capacity = 1                 # tamaño del nodo; ajusta tras medir

  family             = "C"
  non_ssl_port_enabled = false # forzamos TLS: nada de tráfico en claro

  # Solo accesible desde la red del Copiloto, no desde Internet.
  public_network_access_enabled = false

  redis_configuration {
    maxmemory_policy = "allkeys-lru"   # al llenarse, desaloja lo menos usado
  }

  tags = { project = "copiloto", env = "prod" }
}
queue.tf
# Espacio de nombres de mensajería.
resource "azurerm_servicebus_namespace" "copiloto" {
  name                = "copiloto-bus"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  sku                 = "Standard"
  tags                = { project = "copiloto", env = "prod" }
}

# La cola de trabajos largos (generar informes).
resource "azurerm_servicebus_queue" "informes" {
  name         = "informes"
  namespace_id = azurerm_servicebus_namespace.copiloto.id

  # Si el worker falla 5 veces, el mensaje va a la dead-letter: no se pierde ni bloquea.
  max_delivery_count = 5

  # Tiempo que un mensaje queda "invisible" mientras se procesa.
  # Si el worker tarda más, otro lo recoge: por eso el worker debe ser idempotente.
  lock_duration = "PT5M"   # formato ISO 8601: 5 minutos

  # Guardamos el mensaje 7 días si nadie lo consume.
  default_message_ttl = "P7D"
}

El flujo completo, y por qué cada pieza está donde está:

  1. La API recibe una pregunta. Antes de llamar al modelo, busca la respuesta en Redis (clave derivada de la pregunta). Si hay HIT, responde en microsegundos y no gasta ni base ni modelo.
  2. Si no hay HIT, llama al modelo y guarda el resultado en Redis con un TTL razonable (por ejemplo 1 hora). Las siguientes preguntas idénticas son gratis.
  3. Si el usuario pide un informe, la API escribe el PDF pendiente en un contenedor de blobs (lección 01) y publica un mensaje en la cola informes.
  4. El worker consume el mensaje, genera el informe, lo sube a blobs y actualiza la base. Si falla, el mensaje vuelve; tras 5 intentos, va a la DLQ para que alguien lo mire.

Azure ↔ AWS: Redis gestionado es aws_elasticache_replication_group (ElastiCache); la cola es aws_sqs_queue (con redrive_policy para la DLQ); el pub/sub es SNS y los eventos, EventBridge. El patrón —caché en memoria delante de la base, cola entre la API y el worker— es idéntico cambie el nombre que cambie.

5 · Buenas prácticas

HazEvitaPor qué
Poner siempre un TTL a las claves de caché Claves inmortales «porque nunca cambian» Todo dato cambia alguna vez; sin TTL, un fallo de invalidación deja datos obsoletos para siempre
Tratar la caché como material regenerable Guardar en ella datos que no existen en otro sitio La caché puede vaciarse o perderse; si es tu única copia, no es una caché
Consumidores idempotentes Asumir que cada mensaje llega exactamente una vez La entrega es at-least-once: tu worker recibirá duplicados tarde o temprano
Configurar max-delivery-count y DLQ Reintentos infinitos Un mensaje «venenoso» que siempre falla bloquea la cola si no hay un vertedero a donde mandarlo
Ajustar el visibility timeout al tiempo real del trabajo Timeout por defecto con trabajos largos Si el trabajo tarda más que el timeout, otro worker reprocesa el mismo mensaje
Red privada y TLS para ambos servicios Puerto sin TLS o acceso público abierto Caché y cola llevan datos sensibles; exponerlos es regalar tu información interna

6 · Errores habituales

Error 1: usar la caché como base de datos

Guardar en Redis la única copia de algo (por ejemplo, el carrito de la compra) funciona hasta que la caché se reinicia o se desaloja una clave.

✗ Incorrecto — la caché es la única copia 
# El carrito vive SOLO en Redis, sin TTL y sin respaldo.
redis-cli SET "carrito:42" '{"items":["libro"]}'
# Si el nodo se reinicia o se desaloja la clave, el carrito desaparece.
✓ Correcto — la base manda, la caché acelera 
# La base de datos es la fuente de verdad; Redis solo replica la lectura.
# Al escribir: actualiza la base  y  refresca/invalida la caché.
redis-cli SET "carrito:42" '{"items":["libro"]}' EX 900
# La caché caduca sola y, si se pierde, se reconstruye desde la base.

Error 2: un worker que no es idempotente

Con entregas at-least-once, el mismo mensaje puede llegar dos veces. Si el worker no lo tolera, cobrarás (o enviarás) dos veces.

✗ Incorrecto — procesar sin comprobar 
# El worker recibe el mensaje y suma 1 a un contador o envía un email.
# Si el mensaje se entrega dos veces -> contador mal / email duplicado.
✓ Correcto — clave de idempotencia 
-- Antes de actuar, registra el id del mensaje. Si ya existe, ignóralo.
INSERT INTO procesados (message_id)
VALUES ('a1b2c3')
ON CONFLICT (message_id) DO NOTHING;

-- Solo si esta inserción insertó una fila (affected_rows = 1),
-- el worker ejecuta el efecto de negocio. Si ya existía, no hace nada.

Error 3: olvidar la dead-letter queue

Sin DLQ, un mensaje que siempre falla se reintenta indefinidamente y esconde el problema.

✗ Incorrecto — reintentos infinitos 
resource "azurerm_servicebus_queue" "informes" {
  name         = "informes"
  namespace_id = azurerm_servicebus_namespace.copiloto.id
  # Sin max_delivery_count ajustado: el mensaje "venenoso" no tiene salida.
}
✓ Correcto — límite y DLQ 
resource "azurerm_servicebus_queue" "informes" {
  name               = "informes"
  namespace_id       = azurerm_servicebus_namespace.copiloto.id
  max_delivery_count = 5    # tras 5 fallos, el mensaje va a la dead-letter
  dead_lettering_on_message_expiration = true
}
# Alguien (una alerta del módulo 6) vigila la DLQ: si crece, hay un bug.

Error 4: cachear sin invalidar

El usuario cambia su nombre, pero la caché sigue sirviendo el viejo porque nadie la invalidó.

✗ Incorrecto — escribir y no tocar la caché 
-- El usuario actualiza su perfil y solo escribimos en la base.
UPDATE usuarios SET nombre = 'Ana Gómez' WHERE id = 42;
-- La clave usuarios:42:cached sigue con el nombre viejo hasta que caduque.
✓ Correcto — invalidar tras escribir 
# Tras el UPDATE, borra la clave: la próxima lectura la reconstruye.
redis-cli DEL "usuarios:42:cached"
# Alternativa robusta: publicar un evento de "usuario actualizado"
# y que quien cachea esa clave reaccione (módulo 5).

7 · Ejercicio guiado

Objetivo: ver en tu terminal el patrón cache-aside (con miss y hit) y el ciclo de un mensaje en una cola, incluido el paso por la dead-letter. Resultado esperado: el primer GET falla, el segundo acierta, y un mensaje que falla acaba en la DLQ.

  1. Paso 1: simula una caché con un diccionario en memoria local (no necesitas Redis gestionado para entender el patrón): 
    # Primer acceso: MISS. "base de datos" simulada con un sleep.
# Segundo acceso: HIT, sin espera.
redis-cli -u "$REDIS_URL" SET "pregunta:hola" "respuesta cacheada" EX 30
redis-cli -u "$REDIS_URL" GET "pregunta:hola"   # HIT
redis-cli -u "$REDIS_URL" TTL "pregunta:hola"   # quedan menos de 30 s
  2. Paso 2: crea un espacio de nombres y una cola de práctiva en Service Bus: 
    az servicebus namespace create \
  --resource-group rg-cloud-lab --name copiloto-bus-lab \
  --location westeurope --sku Standard

az servicebus queue create \
  --resource-group rg-cloud-lab --namespace-name copiloto-bus-lab \
  --name informes --max-delivery-count 2
  3. Paso 3: envía dos mensajes, uno bueno y uno «venenoso»: 
    az servicebus queue message send \
  --resource-group rg-cloud-lab --namespace-name copiloto-bus-lab \
  --queue-name informes --body '{"user_id":42}'

az servicebus queue message send \
  --resource-group rg-cloud-lab --namespace-name copiloto-bus-lab \
  --queue-name informes --body '{"user_id":"NO_EXISTE"}'
  4. Paso 4: inspecciona el conteo de mensajes y de la dead-letter: 
    az servicebus queue show \
  --resource-group rg-cloud-lab --namespace-name copiloto-bus-lab \
  --name informes \
  --query "{activos:countDetails.activeMessageCount, dlq:countDetails.deadLetterMessageCount}"

    Si simulas el consumo dejando fallar el mensaje malo más de max-delivery-count veces, verás cómo dlq crece. Ese contador es el que vigilarás con una alerta.

  5. Paso 5 (limpieza): borra el grupo de recursos: 
    az group delete --name rg-cloud-lab --yes --no-wait

Lo importante no son los comandos, sino los dos contadores: el de mensajes activos (trabajo pendiente) y el de la DLQ (trabajo que fracasó). Si el primero crece sin parar, faltan workers; si crece el segundo, hay un bug. Ambas cosas son candidatas a alarma en el módulo 6.

9 · Resumen

  • La caché (Redis) responde en microsegundos y descarga las lecturas repetidas; se usa con el patrón cache-aside y siempre con TTL.
  • La caché no es fuente de verdad: es material regenerable que puede desaparecer.
  • La cola desacopla al que pide del que hace: la API responde al instante y el worker procesa a su ritmo.
  • No confundas cola (reparte trabajo), pub/sub (difunde), eventos (reacciona) y streaming (conserva el flujo).
  • La entrega es at-least-once: el consumidor debe ser idempotente.
  • Visibility timeout y dead-letter queue son los dos mecanismos que evitan perder trabajos o bloquearte con un mensaje venenoso.
  • Todo esto protege la misma base de datos que dimensionaste en la lección anterior.

10 · Preguntas frecuentes

¿De verdad necesito una caché? ¿No basta con índices y una base más grande?

A veces sí basta. La caché se justifica cuando hay lecturas muy repetidas desde varias instancias, o cuando la operación es cara (una llamada a un modelo, un agregado pesado). Añadir Redis solo porque «todo el mundo lo usa» es coste y complejidad sin beneficio. Mide primero; el hit ratio bajo es la señal de que no la necesitabas.

¿La cola reemplaza a la base de datos?

No. La cola transporta órdenes de trabajo; el estado de negocio vive en la base. Un mensaje no es un registro: se procesa y se va. Lo que aprendiste en la lección 02 sigue siendo válido: la base es la fuente de verdad, la cola es el mensajero.

¿Qué diferencia hay entre Service Bus y Event Grid?

Service Bus transporta mensajes de negocio que alguien debe procesar (genera este informe), con reintentos y DLQ. Event Grid reacciona a hechos del sistema («se creó un blob», «se registró un usuario») y notifica a quien esté suscrito. A veces se combinan: un hecho dispara un mensaje en la cola.

¿Cómo evito que un mensaje se procese dos veces si la entrega es at-least-once?

Haciendo el consumidor idempotente: el efecto de procesar el mismo mensaje dos veces debe ser igual al de procesarlo una. La técnica habitual es registrar el identificador del mensaje antes de actuar (una tabla de procesados o una clave en Redis con SETNX) y no repetir el efecto si ya está.

¿Por qué mi worker reprocesa el mismo mensaje si ya lo había empezado?

Casi siempre por el visibility timeout: si el trabajo tarda más que ese tiempo, el mensaje vuelve a estar visible y otro worker lo toma. Solución: ajusta el timeout al tiempo real del trabajo, o extiende el lock mientras procesas. Y, en cualquier caso, que el worker sea idempotente para que un reproceso no haga daño.
