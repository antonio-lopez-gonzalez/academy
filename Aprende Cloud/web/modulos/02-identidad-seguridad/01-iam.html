IAM: identidades y roles

Módulo 2 · Identidad y seguridad 🕐 35 minutos

1 · Introducción

En la nube ya no hay un cable que se pueda desenchufar ni un rack que se pueda cerrar con llave. El perímetro de seguridad ha dejado de ser físico: ahora es, sobre todo, quién eres y qué puedes hacer. Cuando alguien roba credenciales en la nube, no roba un servidor: roba permisos. Y eso puede ser peor, porque con los permisos correctos puede borrar una base de datos, extraer datos de clientes o crear máquinas para minar criptomonedas a tu costa.

Esta lección explica el sistema que responde a tres preguntas que aparecen en cada despliegue del Copiloto:

  1. ¿Quién? (identidad): la persona o el programa que quiere hacer algo.
  2. ¿Qué puede hacer? (rol y permisos): las acciones concretas que le concedemos.
  3. ¿Sobre qué? (ámbito o scope): el recurso exacto sobre el que aplica esa concesión.

¿Por qué esta lección es la primera del módulo? Porque casi todos los problemas de seguridad en la nube se reducen a una de estas tres respuestas mal dada: una identidad de larga vida que nunca debería existir, un permiso más amplio de lo necesario o un ámbito que abarca toda la suscripción cuando bastaba un recurso. Sin entender este modelo, los tres temas siguientes (secretos, red privada y OIDC) se convierten en recetas que copias sin comprender.

Errores típicos que verás una y otra vez: usar la cuenta root/owner para todo, crear un usuario con contraseña para que lo use una aplicación, asignar el rol Contributor u Owner a nivel de suscripción «para que funcione», y dejar claves con años de caducidad en variables de CI. Todos tienen solución y la verás aquí.

2 · Teoría

Autenticación no es autorización

Son dos pasos distintos que mucha gente confunde:

PreguntaNombreEjemplo
¿Quién eres?Autenticación (authN)Un login con MFA, un token válido, una identidad gestionada
¿Qué puedes hacer?Autorización (authZ)Leer este almacén, escribir en aquella base de datos

En Azure la autenticación la resuelve Entra ID (el directorio de Microsoft, antes llamado Azure AD) y la autorización la resuelve Azure RBAC. En AWS ambas viven dentro de IAM: el usuario o rol se autentica obteniendo credenciales temporales, y las policies deciden qué puede hacer.

El edificio: identidad, rol y ámbito

Analogía: piensa en un edificio de oficinas con un conserje. La identidad es tu carné. El rol es la lista de puertas que tu carné abre. El ámbito es la planta concreta a la que aplica ese carné: no es lo mismo un carné que abre todas las plantas que uno que solo abre la tuya. IAM es el conserje que, en cada puerta, comprueba las tres cosas.

Suscripción (todo el "edificio")
└── Grupo de recursos: rg-copiloto
    ├── IDENTIDAD  (¿quién?)      id-copiloto-api (managed identity)
    ├── ROL        (¿qué?)        AcrPull  -> solo leer imágenes
    └── ÁMBITO     (¿sobre qué?)  el registro de contenedores
                                   -> ni borrar, ni tocar la base de datos

Tipos de identidad en Azure

Tipo¿Para quién?¿Tiene contraseña?
UsuarioUna persona real (tú, tu equipo)Sí (idealmente con MFA y passkeys)
GrupoAgrupar personas para asignar roles en bloqueNo
Service principal (app registration)Una aplicación que corre fuera de AzureSí, gestionada por ti (evitable con federación)
Identidad gestionada (system-assigned)Un recurso de Azure (una app, una VM)No: la plataforma la gestiona
Identidad gestionada (user-assigned)Varios recursos que comparten los mismos permisosNo

La identidad gestionada es la pieza clave de todo el curso: es un service principal cuyo ciclo de vida la plataforma controla y cuyas credenciales nunca ves. No hay secreto que copiar, rotar o filtrar. La diferencia entre sus dos variantes:

  • System-assigned: se crea con el recurso y muere con él. Apropiada cuando cada recurso necesita su propia identidad (el API del Copiloto).
  • User-assigned: existe por separado y se puede asignar a muchos recursos. Apropiada cuando compartes identidad entre recursos o necesitas preparar los permisos antes de crear el recurso que los usará.

Roles y ámbitos (RBAC)

En Azure, una asignación de rol (role assignment) es la unión de tres cosas: principal (identidad) + role definition (lista de permisos) + scope (dónde aplica). Los ámbitos se anidan:

Grupo de administración (management group)   <- más amplio
└── Suscripción (subscription)
    └── Grupo de recursos (resource group)
        └── Recurso individual               <- más estrecho

Un rol asignado en un nivel se hereda hacia abajo. Por eso el mínimo privilegio casi nunca se consigue en la suscripción, sino lo más abajo posible. Azure trae cientos de roles integrados (built-in); algunos que usarás en este módulo:

RolQué permiteDónde lo usaremos
ReaderVer recursos, sin cambiarlosAuditoría, desarrollo
ContributorGestionar recursos, pero no dar permisosCon cautela y en ámbito estrecho
OwnerTodo, incluido repartir permisosCasi nunca (solo administradores)
AcrPullDescargar imágenes del registroLa API del Copiloto
Key Vault Secrets UserLeer secretos de un Key VaultLección 02

IaaS, PaaS y el mismo modelo en AWS

AWS organiza lo mismo con otros nombres. La diferencia conceptual importante: en AWS el rol es la identidad (no hay «managed identity» como concepto separado; un servicio asume un rol), y las policies pueden ser de identidad (unidas al rol) o de recurso (unidas al recurso, como una política de bucket S3).

Identidad de aplicación externaService principal (app registration)IAM role + trust policy
Lista de permisosRole definitionPolicy

Quién puede asumir el rol(implica confianza del tenant)Trust policy explícita

Regla de oro: las identidades para máquinas (apps, pipelines, contenedores) nunca deberían tener contraseñas ni claves. Si algo necesita credenciales de larga vida para funcionar, el diseño está mal. Azure lo resuelve con identidades gestionadas y AWS con roles asumidos; el módulo 2 termina enseñándote la versión más limpia: OIDC.

3 · Ejemplo mínimo

Antes de crear nada, inspecciona tu propia identidad y los permisos que ya tienes. Es el «hello world» de IAM y, además, te muestra el formato de un principal id (el identificador de la identidad), que usarás constantemente.

terminal
# Si aún no has iniciado sesión en la CLI (lección 03 del módulo 0):
az login

# 1) ¿Quien soy? Muestra el usuario con el que estas autenticado.
#    --query filtra el JSON de salida; -o table lo hace legible.
az ad signed-in-user show --query "{nombre:displayName, id:id}" -o table

# 2) Guarda tu object id en una variable (es el "principal id").
ME=$(az ad signed-in-user show --query id -o tsv)

# 3) ¿Que roles tengo y en que ambitos? --all incluye los heredados.
az role assignment list --assignee "$ME" --all --output table

Qué acaba de pasar, línea por línea:

  1. az login: abre el flujo de autenticación y deja una sesión con una identidad concreta (tu usuario). Todo lo que hagas después queda registrado a nombre de esa identidad.
  2. az ad signed-in-user show: consulta el directorio (Entra ID) para saber quién eres. El id que devuelve es el identificador estable de tu usuario.
  3. az role assignment list: lista las asignaciones de rol donde apareces como principal. La columna scope es el ámbito, y ahí verás si tienes permisos a nivel de suscripción o solo de un grupo de recursos.

En AWS el equivalente es aws sts get-caller-identity, que devuelve la cuenta, el ARN de tu identidad y el ARN del rol asumido. Practica ese comando cuando trabajes con AWS: te dice si la CLI está usando un usuario de larga vida o credenciales temporales de un rol.

4 · Ejemplo real

La API del Copiloto corre en un contenedor y necesita descargar su imagen desde el registro de contenedores (lo verás en el módulo 4). No hay usuario, no hay contraseña: creamos una identidad gestionada y le damos el permiso mínimo sobre un solo recurso.

proyectos/infra-cloud/identity.tf
# ---------------------------------------------------------------------------
# Identidad del Copiloto: una identidad gestionada "user-assigned".
# Existe por separado del recurso, asi podemos darle permisos ANTES de
# crear la aplicacion y reutilizarla si manana anadimos un job programado.
# ---------------------------------------------------------------------------
resource "azurerm_user_assigned_identity" "api" {
  name                = "id-copiloto-api"
  location            = azurerm_resource_group.rg.location
  resource_group_name = azurerm_resource_group.rg.name
}

# ---------------------------------------------------------------------------
# Permiso MINIMO: solo descargar imagenes del registro (AcrPull).
# Fijate en el scope: el id del registro, NO la suscripcion entera.
# ---------------------------------------------------------------------------
resource "azurerm_role_assignment" "api_acr_pull" {
  scope                = azurerm_container_registry.acr.id
  role_definition_name = "AcrPull"
  principal_id         = azurerm_user_assigned_identity.api.principal_id
}

# ---------------------------------------------------------------------------
# La identidad se ENGANCHA a la aplicacion (Container App / App Service).
# A partir de aqui el contenedor tiene identidad propia, sin secretos.
# ---------------------------------------------------------------------------
resource "azurerm_container_app" "api" {
  name                         = "copiloto-api"
  resource_group_name          = azurerm_resource_group.rg.name
  container_app_environment_id = azurerm_container_app_environment.env.id
  revision_mode                = "Single"

  identity {
    type         = "UserAssigned"
    identity_ids = [azurerm_user_assigned_identity.api.id]
  }

  template {
    container {
      name   = "api"
      image  = "acrcopiloto.azurecr.io/copiloto-api:latest"
      cpu    = 0.5
      memory = "1Gi"
    }
  }
}

Tres decisiones que merecen explicación:

  1. User-assigned y no system-assigned. Si más adelante añadimos un segundo consumidor del mismo registro (un worker, un job), comparte esta identidad en lugar de duplicar permisos. Menos asignaciones es menos superficie de error.
  2. AcrPull, no Contributor. El contenedor solo necesita leer la imagen. Con AcrPull no puede publicar una imagen distinta (un ataque de supply chain) ni borrar el registro.
  3. scope en el registro, no en el grupo de recursos. Aunque el grupo contenga la base de datos y el almacenamiento, esta identidad no puede tocarlos. Eso es mínimo privilegio de verdad.

El mismo diseño en AWS: sería un IAM role con una trust policy que deja a ECS asumirlo, más una policy con "Action": "ecr:GetDownloadUrlForLayer" y "ecr:BatchGetImage" limitada al ARN del repositorio. La idea —identidad sin claves, permiso concreto, recurso concreto— es idéntica.

5 · Buenas prácticas

HazEvitaPor qué
Usa identidades gestionadas para todo lo que sea una máquina (app, job, contenedor) Crear un usuario de aplicación con contraseña No hay credencial que filtrar, rotar ni olvidar; el ciclo de vida lo gestiona la plataforma
Asigna roles en el ámbito más estrecho posible (normalmente el recurso) Asignar Contributor/Owner a nivel de suscripción Los permisos se heredan hacia abajo: un error arriba alcanza todos los recursos
Prefiere roles integrados y solo crea roles personalizados si de verdad faltan Inventar un rol */* para «no pelearse con los permisos» Los integrados están probados y documentados; los personalizados hay que mantenerlos
Agrupa personas en grupos de Entra ID y asigna el rol al grupo Asignar roles uno a uno a cada persona Da de alta y de baja a la gente en un solo sitio; menos asignaciones huérfanas
Revisa las asignaciones periódicamente (access review) Dejar permisos «temporales» de un incidente pasados Los permisos se acumulan; lo que hoy sobra mañana es un vector de ataque
Todo por Terraform, revisable en un pull request Crear identidades a mano en el portal Las asignaciones quedan versionadas y cualquiera puede auditarlas

Prueba mental del mínimo privilegio: para cada identidad, escribe la lista de acciones que necesita y tacha las que nunca ejecuta. Si una acción sobra, el rol es demasiado grande. Este ejercicio, hecho antes de asignar, ahorra muchos sustos.

6 · Errores habituales

Dar permisos de administrador «para que funcione»

❌ Incorrecto 
# El clasico: como no se que permiso hace falta, doy todo a nivel
# de suscripcion. Funciona... y tambien funciona un atacante.
resource "azurerm_role_assignment" "api_todo" {
  scope                = "/subscriptions/00000000-0000-0000-0000-000000000000"
  role_definition_name = "Owner" # puede leer, escribir Y borrar todo
  principal_id         = azuread_service_principal.api.object_id
}
✅ Correcto 
# Se que la API solo descarga su imagen: le doy AcrPull sobre el registro.
resource "azurerm_role_assignment" "api_acr_pull" {
  scope                = azurerm_container_registry.acr.id
  role_definition_name = "AcrPull"
  principal_id         = azurerm_user_assigned_identity.api.principal_id
}

Si de verdad no sabes qué permiso hace falta, el camino no es el rol más grande: es empezar pequeño, ver qué falla en los logs y ampliar con evidencia. Cada ampliación es una decisión que queda escrita en Terraform.

Usar la cuenta root/global admin para el día a día

❌ Incorrecto 
# Iniciar sesion con la cuenta raiz de la organizacion y desplegar.
# Si esa sesion se filtra, no hay limite: puede borrar el directorio entero.
az login --username admin@contoso.onmicrosoft.com
✅ Correcto 
# Sesion de usuario normal con MFA; la raiz queda guardada bajo llave.
az login
az account show --query "{usuario:user.name, suscripcion:name}" -o table

# Y para automatizar, una identidad dedicada (leccion 04: OIDC).

La cuenta raíz (o el usuario global admin) existe para tareas excepcionales: crear el primer administrador, recuperar accesos. En el día a día es el mayor riesgo posible porque no se puede limitar.

Conceder un rol a «todos los usuarios» del directorio

❌ Incorrecto 
# Asignar el rol a la suscripcion para todo el tenant.
# Cualquier cuenta nueva que se cree hereda el permiso automaticamente.
resource "azurerm_role_assignment" "everyone" {
  scope                = data.azurerm_subscription.current.id
  role_definition_name = "Contributor"
  principal_id         = data.azurerm_client_config.current.tenant_id
}
✅ Correcto 
# El rol va a un grupo concreto, y la pertenencia al grupo se administra
# aparte (con aprobacion). El permiso no cresce solo.
resource "azurerm_role_assignment" "devs_rg" {
  scope                = azurerm_resource_group.rg.id
  role_definition_name = "Reader"
  principal_id         = var.dev_group_object_id
}

Conceder a nivel de tenant es hipotecar el futuro: cada identidad que se cree después hereda permisos que nadie revisó. El permiso debe nacer de una decisión explícita.

Confundir el object id con el application (client) id

❌ Incorrecto 
# az role assignment create espera el object id del principal,
# no el client id de la app registration.
APP_ID="11111111-2222-3333-4444-555555555555"
az role assignment create --assignee "$APP_ID" --role Reader --scope "$RG_ID"
# -> falla o asigna a la identidad equivocada.
✅ Correcto 
# El object id se obtiene del service principal o de la managed identity.
OBJECT_ID=$(az identity show -g rg-copiloto -n id-copiloto-api --query principalId -o tsv)
az role assignment create --assignee "$OBJECT_ID" --role AcrPull --scope "$ACR_ID"

En Entra ID una aplicación tiene dos identificadores: el application id (el «client id» que usan los logins) y el object id (el identificador de la entidad en el directorio, que es lo que espera RBAC). Intercambiarlos es una fuente de errores exasperante.

7 · Ejercicio guiado

Objetivo: crear una identidad gestionada, concederle el mínimo privilegio sobre un recurso y comprobar por qué no puede hacer otra cosa.

Coste: este ejercicio usa un grupo de recursos y un Key Vault de nivel standard, que cuesta céntimos al mes. Bórralo al terminar: al final del módulo pagas por los recursos que olvidas.

  1. Paso 1 — Crea el grupo de recursos y una identidad gestionada:
    terminal
    # Un grupo de recursos con etiqueta de coste (nunca sin ella).
az group create --name rg-iam-lab --location westeurope --tags curso=cloud

# La identidad del "trabajador" del laboratorio.
az identity create --name id-iam-lab --resource-group rg-iam-lab

# Guarda su principal id: es con lo que se asigna el rol.
PRINCIPAL_ID=$(az identity show -n id-iam-lab -g rg-iam-lab --query principalId -o tsv)
echo "$PRINCIPAL_ID"
  2. Paso 2 — Crea un Key Vault (recurso objetivo) y concede solo lectura:
    terminal
    # Nombre unico global (Key Vault lo exige): usa tus iniciales.
VAULT=kv-iam-lab-$(date +%s)
az keyvault create --name "$VAULT" --resource-group rg-iam-lab --location westeurope

# Permiso MINIMO: leer secretos, y solo en ESTE vault.
az role assignment create \
  --assignee "$PRINCIPAL_ID" \
  --role "Key Vault Secrets User" \
  --scope "$(az keyvault show -n "$VAULT" --query id -o tsv)"
  3. Paso 3 — Verifica la asignación y su ámbito:
    terminal
    az role assignment list --assignee "$PRINCIPAL_ID" --all \
  --query "[].{rol:roleDefinitionName, ambito:scope}" -o table

    Resultado esperado: una única fila, con rol Key Vault Secrets User y ámbito exactamente .../providers/Microsoft.KeyVault/vaults/<tu-vault>. Si el ámbito acabara en /resourceGroups/rg-iam-lab o en la suscripción, el permiso sería mayor de lo necesario.

  4. Paso 4 — Comprueba el límite:
    terminal
    # Intenta dar un permiso EXTRA con esta identidad: debe fallar,
# porque "Key Vault Secrets User" no puede repartir permisos.
az role assignment create \
  --assignee "$PRINCIPAL_ID" --role Reader --scope "$(az group show -n rg-iam-lab --query id -o tsv)"
# Se espera: AuthorizationFailed / el permiso de escritura no existe.
  5. Paso 5 — Limpia (borra lo que no uses):
    terminal
    az group delete --name rg-iam-lab --yes --no-wait

    Recuerda: az group delete elimina todo lo que hay dentro. Ejecútalo siempre que termines un laboratorio.

8 · Reto

🎯 Un rol a medida, más pequeño que el integrado

Los roles integrados a veces conceden más de lo que queremos. Crea un rol personalizado para un «lector de la configuración del Copiloto» que pueda únicamente leer la definición de las Container Apps (sin modificarlas, sin leer secretos, sin tocar la base de datos). Después asígnalo a una identidad gestionada sobre un solo recurso.

Debes entregar: la definición en JSON (con actions y notActions explícitos), el comando de creación y una frase explicando qué operaciones quedaron fuera a propósito y por qué.

Pista: investiga az role definition create y el formato Microsoft.App/containerApps/read. El reto no está en copiar el JSON, sino en justificar qué has dejado fuera.

9 · Resumen

  • La autenticación dice quién eres; la autorización dice qué puedes hacer. Azure usa Entra ID + RBAC; AWS usa IAM.
  • Toda concesión es identidad + rol + ámbito. Los ámbitos se heredan hacia abajo.
  • Las identidades gestionadas dan identidad a programas sin contraseñas: no hay secreto que filtrar.
  • La service principal (app registration) es para aplicaciones fuera de Azure; si es posible, se federa (lección 04) en vez de usar claves.
  • Mínimo privilegio = el rol más pequeño, en el ámbito más estrecho, por el tiempo necesario.
  • Nada de cuentas root en el día a día; los permisos se conceden a grupos, no a personas ni a todo el tenant.

10 · Preguntas frecuentes

¿Identidad gestionada o service principal? ¿Cuál elijo?

Si el consumidor vive dentro de Azure (una Container App, una VM, un Function), usa una identidad gestionada: no hay credenciales que gestionar. Si vive fuera (tu portátil, GitHub Actions, un servicio de terceros), usa una service principal, pero configúrala para federar (OIDC) y evitar claves. La service principal con contraseña es el último recurso.

¿System-assigned o user-assigned?

System-assigned cuando la identidad pertenece a un recurso y muere con él: es la opción por defecto y la más limpia para un único consumidor. User-assigned cuando varios recursos comparten identidad, cuando quieres preparar los permisos antes de crear el recurso o cuando temes que borrar y recrear el recurso te obligue a rehacer las asignaciones.

¿Por qué no basta con una API key en una cabecera?

Porque una API key es un secreto de larga vida: si se filtra (logs, capturas, un repositorio), funciona hasta que alguien la revoca —y nadie la revoca nunca—. Además no identifica quién la usa ni permite auditar por usuario. Las identidades y las credenciales temporales te dan revocación, caducidad y trazabilidad gratis.

¿Qué pasa si alguien borra una asignación de rol en el portal?

Que la aplicación deja de funcionar con un error de autorización. La ventaja de tenerlo todo en Terraform es que el siguiente terraform plan detecta la deriva y vuelve a crear la asignación. Ese es el motivo real de gestionar IAM como código: la deriva deja de ser silenciosa.

¿Cuánto cuesta IAM?

El modelo de identidades, roles y asignaciones en sí no tiene coste directo en Azure ni en AWS. Lo que cuesta dinero es lo que esas identidades usan (máquinas, bases de datos, tráfico). Aun así, IAM afecta al gasto: un permiso mal dado puede crear recursos caros sin que nadie los haya aprobado.
