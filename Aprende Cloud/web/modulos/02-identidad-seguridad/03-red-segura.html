Red segura y exposición mínima

Módulo 2 · Identidad y seguridad 🕐 30 minutos

1 · Introducción

Por defecto, casi todo servicio PaaS en la nube nace con una dirección pública en internet. Tu base de datos responde en algo.postgres.database.azure.com y tu Key Vault en algo.vault.azure.net: cualquiera puede intentar conectarse, y lo único que te separa de un ataque es una contraseña o un token. Eso se llama tener superficie de exposición, y cada servicio público es una puerta que hay que vigilar.

Esta lección trata de reducir esa superficie al mínimo: que los recursos hablen entre sí por la red privada, que lo que no necesita ser público no lo sea, y que las reglas de firewall y grupos de seguridad nieguen por defecto y permitan solo lo explícitamente necesario.

¿Por qué importa tanto en la nube? Porque la red es el último muro que no depende de que un secreto se filtre. Aunque alguien robe una credencial, si el servicio no es alcanzable desde fuera de tu red, la credencial le sirve de poco. La defensa en profundidad consiste en que cada capa (identidad, secreto, red) tenga que fallar para que haya brecha.

Errores típicos: abrir el puerto 5432 (PostgreSQL) o 3389 (escritorio remoto) a 0.0.0.0/0, dejar un Key Vault con firewall en «Allow all», confiar en una IP de origen que un atacante puede falsificar, y usar endpoints públicos «porque la red privada es complicada».

2 · Teoría

Tres formas de llegar a un servicio

Cuando un recurso A (tu API) quiere hablar con un recurso B (tu Key Vault o tu base de datos), hay tres maneras de que el tráfico llegue:

Camino¿El recurso B tiene IP pública?Cómo lo consigues
Endpoint público Sí, expuesto a todo internet Es lo que viene por defecto. Solo válido para lo que debe ser público de verdad.
Service endpoint Sí, pero el firewall lo limita a tu VNet Extiende tu VNet hasta el servicio: el tráfico sale por la red de Azure y puedes permitir solo esa subred.
Private endpoint (Private Link) No: el recurso solo existe con IP privada Crea una tarjeta de red con IP privada dentro de tu subred que apunta al servicio. Nadie fuera lo ve.

Analogía: el endpoint público es una tienda con la puerta a la calle. El service endpoint es una ventanilla que solo atiende a vecinos del mismo barrio (tu VNet). El private endpoint es una puerta interior que trae la tienda a tu propia casa: ni siquiera hay dirección en la calle para esa tienda, porque solo existe dentro de tu red.

En AWS los mismos conceptos se llaman: VPC endpoint de tipo Gateway (para S3 y DynamoDB, por tabla de rutas) y VPC endpoint de tipo Interface (una tarjeta de red con IP privada en tu subred, para el resto de servicios). El private endpoint de Azure equivale al Interface endpoint con PrivateLink.

Cómo funciona el private endpoint por dentro

   Tunel IPv4 / VNet copiloto-vnet
   +-------------------------------------------------------------+
   |  Subred api              |  Subred private-endpoints         |
   |  +-----------------+     |  +-----------------------------+  |
   |  | copiloto-api    |-----|--| pe-kv (IP 10.0.2.4)          |  |
   |  | 10.0.1.4        |     |  |   apunta a Key Vault          |  |
   |  +-----------------+     |  +-----------------------------+  |
   |                          |         ^                         |
   +--------------------------|---------|-------------------------+
                              |  Azure Private Link (fibra de Azure)
                              v
                     kv-copiloto.vault.azure.net
                     (sin IP publica: solo alcanzable desde tu red)

El detalle que hace que «funcione como siempre» es el DNS privado. Cuando tu app resuelve kv-copiloto.vault.azure.net, el servicio de DNS de la VNet responde con la IP privada del endpoint (10.0.2.4) en lugar de la IP pública. Tu código no cambia ni una línea: sigue usando el mismo nombre; solo cambia lo que ese nombre resuelve.

Firewall y grupos de seguridad: negar por defecto

Un grupo de seguridad de red (NSG en Azure, security group en AWS) es una lista de reglas que decide qué tráfico entra y sale. La regla de oro es deny by default: todo se bloquea salvo lo que permites explícitamente. Y se aplica en dos planos:

  • A nivel de red: NSG/subred para el tráfico de tus máquinas.
  • A nivel de servicio: el propio Key Vault, la base de datos o el almacenamiento tienen su firewall y su opción de «red pública activada o no».
CapaQué controlaEjemplo de configuración segura
NSG de subredTráfico entre subredes e internetPermitir 443 desde la VNet; denegar todo lo demás
Firewall del servicioQuién llega al recurso por su endpointKey Vault: default_action = Deny
Acceso a red públicaSi el recurso tiene endpoint públicopublic_network_access_enabled = false

Orden de preferencia: primero intenta que el recurso no sea público (private endpoint), y solo después limita con firewall. Un firewall perfecto sobre un endpoint público sigue siendo una superficie que vigilar; un recurso sin endpoint público no tiene nada que vigilar.

3 · Ejemplo mínimo

El firewall más pequeño que tiene sentido: un grupo de seguridad que permite HTTPS solo desde tu propia red y deja el resto bloqueado por la regla implícita «deny all» que ya trae el NSG.

terminal
# 1) Crea el grupo de seguridad (aun sin reglas).
az network nsg create --resource-group rg-net-lab --name nsg-copiloto

# 2) Permite SOLO HTTPS entrante desde dentro de la red virtual.
#    --source-address-prefixes VirtualNetwork = "trafico de mi propia VNet".
az network nsg rule create \
  --resource-group rg-net-lab --nsg-name nsg-copiloto \
  --name allow-https-internal --priority 100 \
  --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes VirtualNetwork \
  --source-port-ranges '*' \
  --destination-address-prefixes '*' \
  --destination-port-ranges 443

# 3) Comprueba las reglas efectivas: la primera permite 443;
#    las siguientes son las reglas por defecto de Azure (DenyAll).
az network nsg rule list --resource-group rg-net-lab --nsg-name nsg-copiloto \
  --query "sort_by([].{nombre:name, prio:priority, dir:direction, acc:access, puertos:destinationPortRanges}, &prio)" \
  -o table

Qué acaba de pasar:

  1. nsg create: crea una lista vacía. Vacía significa «solo reglas por defecto», que ya deniegan la entrada desde internet.
  2. nsg rule create: añade una excepción concreta. El --priority 100 es bajo a propósito: las reglas se evalúan de menor a mayor número, así que lo que quieres permitir va primero.
  3. nsg rule list: el --query ordena por prioridad para que veas primero lo que permite y, abajo, lo que Azure deniega siempre. Esa parte «denegar siempre» es la que te protege de olvidos.

Fíjate en el & escapado de la consulta: en los ejemplos de Azure CLI se usa & para ordenar, y dentro de HTML hay que escribirlo como &amp;. Si copias el comando desde el portal, ajusta ese carácter.

4 · Ejemplo real

En el Copiloto, el objetivo es que la API lea sus secretos del Key Vault sin pasar por internet: el vault no tendrá endpoint público y se accederá a él por un private endpoint dentro de la VNet.

proyectos/infra-cloud/network-private-endpoint.tf
# ---------------------------------------------------------------------------
# 1) Zona DNS privada. Sin esto, el nombre del vault seguiria resolviendo
#    a la IP publica y el private endpoint no serviria de nada.
# ---------------------------------------------------------------------------
resource "azurerm_private_dns_zone" "kv" {
  name                = "privatelink.vaultcore.azure.net"
  resource_group_name = azurerm_resource_group.rg.name
}

# Enlaza la zona con la VNet: los recursos de la VNet usan este DNS.
resource "azurerm_private_dns_zone_virtual_network_link" "kv" {
  name                  = "kv-dns-link"
  resource_group_name   = azurerm_resource_group.rg.name
  private_dns_zone_name = azurerm_private_dns_zone.kv.name
  virtual_network_id    = azurerm_virtual_network.vnet.id
}

# ---------------------------------------------------------------------------
# 2) El private endpoint: una tarjeta de red con IP privada en TU subred
#    que apunta al Key Vault. Aqui no hay IP publica que atacar.
# ---------------------------------------------------------------------------
resource "azurerm_private_endpoint" "kv" {
  name                = "pe-kv-copiloto"
  location            = azurerm_resource_group.rg.location
  resource_group_name = azurerm_resource_group.rg.name
  subnet_id           = azurerm_subnet.private_endpoints.id

  private_service_connection {
    name                           = "psc-kv-copiloto"
    private_connection_resource_id = azurerm_key_vault.kv.id
    # "vault" es el tipo de conexion para un Key Vault (subresource).
    subresource_names              = ["vault"]
    is_manual_connection           = false
  }

  private_dns_zone_group {
    name                 = "kv-dns-group"
    private_dns_zone_ids = [azurerm_private_dns_zone.kv.id]
  }
}
proyectos/infra-cloud/keyvault-hardening.tf (fragmento)
resource "azurerm_key_vault" "kv" {
  name                        = "kv-copiloto-${var.suffix}"
  location                    = azurerm_resource_group.rg.location
  resource_group_name         = azurerm_resource_group.rg.name
  tenant_id                   = data.azurerm_client_config.current.tenant_id
  sku_name                    = "standard"
  rbac_authorization_enabled  = true
  purge_protection_enabled    = true

  # 3a) Nada de endpoint publico: solo se llega por el private endpoint.
  public_network_access_enabled = false

  # 3b) Aunque el endpoint publico existiera, se niega por defecto.
  #     "AzureServices" deja que servicios de confianza (backup, monitor)
  #     puedan seguir operando sin abrir la puerta a internet.
  network_acls {
    default_action = "Deny"
    bypass         = "AzureServices"
  }
}

Cuatro decisiones que merecen explicación:

  1. Zona DNS privada primero. Es el error número uno: crear el private endpoint y preguntarse por qué sigue resolviendo a la IP pública. El enlace DNS es lo que cambia la resolución.
  2. public_network_access_enabled = false: apaga el endpoint público del vault. Sin esto, el firewall sigue existiendo pero el servicio es alcanzable desde internet.
  3. default_action = "Deny": si por algún motivo el endpoint público se reactivara, la postura por defecto seguiría siendo denegar. Es defensa en profundidad.
  4. La subred de endpoints es propia. Aislarla de las subredes de aplicación facilita aplicar reglas de NSG distintas y no mezclar tráfico de datos con el de gestión.

Coste: los private endpoints se facturan por hora y por transferencia de datos, además de la zona DNS privada. No es caro, pero no es gratis: merece la pena en producción y sobra en un laboratorio de pruebas. Elige con criterio, no por reflejo.

5 · Buenas prácticas

HazEvitaPor qué
Private endpoint para bases de datos, Key Vault y almacenamiento Dejar los datos accesibles por endpoint público Sin endpoint público no hay superficie que escanear ni que parchear con urgencia
Firewall con default_action = Deny en todos los servicios que lo permitan «Allow all» y confiar en la contraseña Un firewall que permite todo es una capa que no existe
Reglas de NSG por subred, con la subred más específica posible Un NSG gigante a nivel de VNet con reglas contradictorias Reglas locales se entienden, se revisan y no se pisan entre sí
Permitir administración (SSH/RDP) solo por Bastion o VPN Abrir el 22/3389 a 0.0.0.0/0 «solo un rato» Un puerto de administración abierto es minutos u horas de exposición, siempre
Subred dedicada para private endpoints Poner los endpoints en la subred de la aplicación Separa el tráfico de datos del de gestión y permite reglas distintas
Documentar en Terraform el porqué de cada regla permitida Añadir reglas «temporales» que se quedan años Una regla sin dueño ni motivo es una regla que nadie se atreve a borrar

La pregunta que desbloquea todo: «¿este recurso necesita de verdad ser alcanzable desde internet?». Casi siempre la respuesta es no. Si empiezas por ahí, la mitad de las decisiones de red se toman solas.

6 · Errores habituales

Abrir la base de datos a todo internet

❌ Incorrecto 
# PostgreSQL alcanzable desde cualquier IP del mundo.
# Escaneres automatizados encuentran esto en minutos.
az postgres flexible-server firewall-rule create \
  --resource-group rg-copiloto --name srvs --rule-name allow-all \
  --start-ip-address 0.0.0.0 --end-ip-address 255.255.255.255
✅ Correcto 
# La base de datos NO tiene regla de firewall para internet:
# se llega a ella por un private endpoint dentro de la VNet.
# (El firewall global, si existe, queda en Deny por defecto.)
az postgres flexible-server show \
  --resource-group rg-copiloto --name srvs-copiloto \
  --query "{publico:network.publicNetworkAccess}" -o table

Abrir el rango completo es tentador «para que funcione desde casa», pero deja la base de datos expuesta permanentemente. La alternativa correcta es un private endpoint, o en su defecto una IP concreta y temporal.

Creer que service endpoint basta para ocultar el servicio

❌ Incorrecto 
# Activo el service endpoint y me relajo: el servicio SIGUE teniendo
# IP publica y su firewall podria estar permitiendo mas de lo que creo.
resource "azurerm_subnet" "app" {
  name                 = "subnet-app"
  resource_group_name  = azurerm_resource_group.rg.name
  virtual_network_name = azurerm_virtual_network.vnet.name
  address_prefixes     = ["10.0.1.0/24"]
  service_endpoints    = ["Microsoft.KeyVault"]
}
✅ Correcto 
# El private endpoint SI crea una IP privada en mi red y me permite
# apagar por completo el acceso publico del recurso.
resource "azurerm_private_endpoint" "kv" {
  name                = "pe-kv-copiloto"
  location            = azurerm_resource_group.rg.location
  resource_group_name = azurerm_resource_group.rg.name
  subnet_id           = azurerm_subnet.private_endpoints.id

  private_service_connection {
    name                           = "psc-kv-copiloto"
    private_connection_resource_id = azurerm_key_vault.kv.id
    subresource_names              = ["vault"]
    is_manual_connection           = false
  }
}

El service endpoint es útil y más barato, pero no elimina la IP pública del servicio: solo filtra quién llega. Si el objetivo es no tener nada público, la pieza correcta es el private endpoint.

Permitir por IP de origen sin entender qué IP es

❌ Incorrecto 
# "Permito la IP de mi oficina" sin fijarse en que la IP de salida
# de la oficina puede cambiar o compartirse con muchos inquilinos.
az keyvault network-rule add --name kv-copiloto --ip-address 203.0.113.10
✅ Correcto 
# En su lugar, acceso por red privada: no dependes de IPs externas
# ni de que la IP de origen sea de quien crees que es.
az keyvault network-rule list --name kv-copiloto \
  --query "{publico:properties.publicNetworkAccess, reglas:properties.networkAcls.ipRules}" -o json

Una IP de origen no identifica a un usuario: puede cambiar, compartirse tras un NAT o falsificarse en ciertos escenarios. Si necesitas restringir por IP, hazlo como mal menor y nunca como única defensa.

Fijar el NSG a la tarjeta de red y no a la subred

❌ Incorrecto 
# Reglas distintas en cada NIC: cuando escala, cada maquina
# nueva hay que recordar aplicarle las reglas a mano. Error garantizado.
resource "azurerm_network_interface_security_group_association" "vm" {
  network_interface_id      = azurerm_network_interface.vm.id
  network_security_group_id = azurerm_network_security_group.nsg.id
}
✅ Correcto 
# El NSG se asocia a la SUBNET: toda maquina que entre hereda las reglas.
resource "azurerm_subnet_network_security_group_association" "app" {
  subnet_id                 = azurerm_subnet.app.id
  network_security_group_id = azurerm_network_security_group.nsg.id
}

Aplicar el NSG a la subred hace que la política sea estructural: no depende de que alguien recuerde configurar cada máquina. Con autoscaling, una NIC sin reglas es solo cuestión de tiempo.

7 · Ejercicio guiado

Objetivo: crear una red con una subred de aplicación y un NSG que solo permita HTTPS interno, y comprobar las reglas efectivas.

Coste: las redes virtuales, subredes y NSG no tienen coste por sí mismos. Solo pagas cuando algo consume (una máquina, un balanceador, un private endpoint). Este laboratorio puro de red es gratis, aun así borra el grupo al terminar.

  1. Paso 1 — Crea grupo de recursos, VNet y subred:
    terminal
    az group create --name rg-net-lab --location westeurope --tags curso=cloud
az network vnet create --resource-group rg-net-lab --name vnet-copiloto \
  --address-prefixes 10.10.0.0/16 \
  --subnet-name snet-app --subnet-prefixes 10.10.1.0/24
  2. Paso 2 — Crea el NSG y la regla de HTTPS interno:
    terminal
    az network nsg create --resource-group rg-net-lab --name nsg-app
az network nsg rule create --resource-group rg-net-lab --nsg-name nsg-app \
  --name allow-https-internal --priority 100 \
  --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes VirtualNetwork \
  --destination-port-ranges 443
  3. Paso 3 — Asocia el NSG a la subred:
    terminal
    az network vnet subnet update --resource-group rg-net-lab \
  --vnet-name vnet-copiloto --name snet-app \
  --network-security-group nsg-app
  4. Paso 4 — Verifica las reglas efectivas:
    terminal
    az network nsg rule list --resource-group rg-net-lab --nsg-name nsg-app \
  --query "sort_by([].{nombre:name, prio:priority, accion:access, puertos:destinationPortRanges}, &prio)" \
  -o table

    Resultado esperado: tu regla allow-https-internal aparece primero (prioridad 100). Debajo siguen las reglas por defecto de Azure (AllowVnetInBound, DenyAllInBound…). Lo importante es que no existe ninguna regla que permita entrar desde Internet: solo lo que tú autorizaste.

  5. Paso 5 — Limpia:
    terminal
    az group delete --name rg-net-lab --yes --no-wait

8 · Reto

🎯 Un Key Vault invisible desde internet

Monta un Key Vault que solo sea alcanzable por un private endpoint dentro de una VNet (endpoint público desactivado y firewall en Deny). Después demuestra con un comando que, desde fuera de ese DNS privado, az keyvault secret show falla o resuelve a una dirección pública que ya no responde.

Entrega: los recursos (VNet, subred de endpoints, zona DNS privada, enlace, private endpoint, vault endurecido), el comando que prueba el aislamiento y una frase explicando por qué falla desde fuera.

Pista: recuerda crear y enlazar la zona privatelink.vaultcore.azure.net antes de crear el endpoint. Si el nombre sigue resolviendo a una IP pública, el problema casi siempre está en el DNS, no en el endpoint. Piensa también en qué rol necesita tu identidad para leer el secreto incluso por red privada (lección 02): la red no sustituye a los permisos, los complementa.

9 · Resumen

  • Por defecto, los servicios PaaS nacen con endpoint público. Reducir esa exposición es la mejor inversión de seguridad.
  • Service endpoint filtra por red pero mantiene la IP pública; private endpoint (Private Link) crea una IP privada y permite apagar el acceso público.
  • El private endpoint solo funciona «como siempre» si el DNS privado resuelve el nombre a la IP del endpoint.
  • Firewalls y grupos de seguridad deben negar por defecto y permitir solo lo explícito.
  • Los NSG se asocian a la subred, no a cada máquina: la política es así estructural.
  • Ni una sola regla a 0.0.0.0/0 en puertos de datos o administración.

10 · Preguntas frecuentes

¿Private endpoint o service endpoint? ¿Cuándo uso cada uno?

Private endpoint cuando quieras que el recurso no tenga endpoint público (lo normal para datos y secretos) o cuando necesites conectar servicios que no soportan service endpoints. Service endpoint cuando busques algo más barato y ligero y aceptes que el servicio siga teniendo IP pública, protegida por su firewall. En un proyecto serio, los datos van por private endpoint.

He creado el private endpoint y sigue resolviendo a la IP pública. ¿Qué me falta?

Casi siempre la zona DNS privada: hay que crearla con el nombre correcto (privatelink.<servicio>.azure.net o equivalente) y enlazarla a la VNet. Sin esa resolución, tu máquina pregunta al DNS público, que no conoce tu endpoint y devuelve la IP pública.

¿La red privada sustituye a los permisos?

No: la complementa. Reducir la exposición evita que un atacante remoto llegue al servicio, pero quien esté dentro de la red sigue necesitando permisos para hacer cosas. Defensa en profundidad es que ambas capas existan; quitar una porque tienes la otra es bajar la guardia.

¿Cuánto cuesta todo esto?

VNet, subredes y NSG son gratis. Los private endpoints y las zonas DNS privadas tienen un coste por hora más transferencia, bajo pero real. En un laboratorio de pruebas puedes ahorrártelos; en producción, el coste de exponer una base de datos a internet es bastante mayor que el de un endpoint privado.

¿Y si mi aplicación debe ser accesible desde internet?

Entonces esa puerta sí es pública, pero solo una: expón la web o el API Gateway y deja que todo lo de dentro (base de datos, secretos, almacenamiento) hable por red privada. El objetivo no es «cero internet», sino una única entrada controlada en lugar de diez puertas abiertas.
