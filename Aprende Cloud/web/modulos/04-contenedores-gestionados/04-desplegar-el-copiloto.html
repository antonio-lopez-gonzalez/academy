Desplegar el Copiloto

Módulo 4 · Contenedores gestionados 🕐 40 minutos

1 · Introducción

Ha llegado el momento de juntar todas las piezas del módulo y hacer lo que llevas buscando desde la portada del curso: poner la Copiloto API en producción, con una URL pública que responde. No con la consola web, no a mano: con Terraform, reproducible, versionado y sin secretos en el repositorio.

El flujo que vamos a seguir es siempre el mismo, en cualquier proveedor y para cualquier servicio:

  (1) REGISTRO            (2) SERVICIO             (3) SALUD             (4) URL PUBLICA
  -------------           ------------             ---------             ---------------
  build imagen   ==>      Container App     ==>    /health responde ==> https://copiloto...
  push a ACR              + ingress                readiness ok          con TLS gestionado
  (identidad)             (sin credenciales)       liveness ok           accesible al mundo

Cada flecha la has aprendido por separado: el registro en el módulo 1, la identidad gestionada en el módulo 2, la base de datos en el módulo 3. Aquí las unimos en un despliegue real.

¿Por qué existe esta lección? Porque «desplegar» no es subir una imagen: es encadenar registro → servicio → salud → URL pública sin secretos y con verificación. Es el momento en que el Copiloto deja de ser un proyecto local y pasa a ser una aplicación en producción. Todo lo demás del curso (observabilidad, coste, DR) se apoya en este cimiento.

2 · Teoría

El recorrido de una petición, extremo a extremo

Antes de escribir código, ten claro el camino. Cuando un usuario abre https://copiloto....azurecontainerapps.io/health, esto es lo que ocurre:

  Usuario
    |
    | HTTPS (TLS gestionado por el ingress)
    v
  [ Ingress externo ]  --target_port 8000-->  [ Réplica del contenedor ]
    |                                             |
    | balancea entre réplicas                     | ejecuta Copiloto API
    |                                             |
    +---- si /health no responde, la plataforma   |
          NO manda tráfico a esa réplica ----------+
    |
    v
  Imagen descargada del ACR usando IDENTIDAD GESTIONADA (sin credenciales)

Cuatro ideas clave que se deducen del dibujo:

  • El ingress termina el TLS. Tú no gestionas certificados: la plataforma los emite y renueva. Por eso allow_insecure_connections = false (solo HTTPS).
  • El target_port es el del contenedor, no un puerto público. El ingress llega a él por la red interna del environment.
  • La salud decide el enrutado. Mientras /health no responde bien, la plataforma considera la réplica «no lista» y no le manda tráfico.
  • El registro se lee con identidad. Nada de usuario/contraseña: la identidad gestionada de la app tiene el rol AcrPull sobre el registro.

Los tres sondeos (probes) y por qué hacen falta los tres

Aquí está el detalle que separa un despliegue amateur de uno profesional. La plataforma necesita saber tres cosas distintas sobre tu contenedor:

SondeoPregunta que respondeQué pasa si falla
startup«¿Has terminado de arrancar?»Da tiempo a apps lentas a iniciarse sin que la plataforma las mate por «no estar listas aún».
readiness«¿Puedo mandarte tráfico ya?»La plataforma deja de enviar tráfico a esa réplica (pero la deja viva). Es la clave de un despliegue sin errores 5xx.
liveness«¿Sigues vivo, o te has colgado?»La plataforma reinicia la réplica. Detecta cuelgues que un sondeo de tráfico no vería.

Analogía: un restaurante. startup = «¿ha abierto ya las puertas?» (no le exijas servir durante la obra). readiness = «¿el chef está listo para cocinar?» (si no, no le mandes clientes, pero no cierres el local). liveness = «¿sigue respirando el chef?» (si se ha desmayado, hay que reanimarlo). Confundir los tres es la causa de reinicios en bucle y 502 en producción.

Regla de oro: readiness y liveness deben apuntar a rutas distintas o, como mínimo, liveness a una más simple. Si liveness depende de la base de datos, y la base de datos cae un momento, la plataforma reiniciará todas tus réplicas a la vez —convirtiendo un problema pequeño en una caída total.

Por qué identidad gestionada y no usuario/contraseña

Podrías darle a la app el usuario y la contraseña del registro. Funciona… y es una mala idea: esas credenciales viven en el state de Terraform, en los logs, en la memoria de quien las copió. La identidad gestionada (módulo 2) resuelve esto: la app obtiene un token temporal del propio proveedor, sin secretos persistentes.

Usuario/contraseña del registroIdentidad gestionada
Dónde vive la credencialEn variables, state, CI…En ninguna parte: token temporal
RotaciónManual y olvidadaAutomática
AlcanceTodo lo que ese usuario puedeSolo el rol asignado (AcrPull)
Fuga de la imagen/repoCredencial expuestaSin credencial que exponer

El rol que necesita una Container App para leer imágenes de un ACR se llama AcrPull. Es solo lectura del registro: exactamente el mínimo privilegio. En AWS, el equivalente es dar permiso de lectura de ECR a la identidad que usa el servicio.

3 · Ejemplo mínimo

El despliegue mínimo, sin identidad ni probes, para ver el esqueleto: un registro, un environment y una app que tira de una imagen pública. Es el «hola mundo» del registro a la URL.

minimo.tf — registro + environment + app pública
# 1) El registro donde vivirán las imágenes (módulo 1).
resource "azurerm_container_registry" "acr" {
  name                = "copilotolabacr"   # nombre único, solo minúsculas/números
  resource_group_name = var.resource_group_name
  location            = var.location
  sku                 = "Basic"            # Basic basta para el laboratorio
  admin_enabled       = false              # sin usuario admin: usaremos identidad
}

# 2) El entorno que aloja la app.
resource "azurerm_container_app_environment" "env" {
  name                = "cae-copiloto"
  resource_group_name = var.resource_group_name
  location            = var.location
}

# 3) La app. Aquí usamos una imagen pública; con el ACR propio añadiríamos
#    el bloque registry + identity (lo verás en el ejemplo real).
resource "azurerm_container_app" "min" {
  name                         = "copiloto-min"
  container_app_environment_id = azurerm_container_app_environment.env.id
  resource_group_name          = var.resource_group_name
  revision_mode                = "Single"

  template {
    container {
      name   = "api"
      image  = "mcr.microsoft.com/k8se/quickstart:latest"
      cpu    = 0.5
      memory = "1Gi"
    }
  }

  ingress {
    external_enabled           = true
    target_port                = 80
    allow_insecure_connections = false   # solo HTTPS
  }
}

Qué acaba de pasar:

  1. admin_enabled = false: desactiva el usuario administrador del registro para obligarnos a usar identidad gestionada. Es una decisión de seguridad, no un descuido.
  2. El environment: la frontera donde vive la app; agrupa logs y red interna.
  3. La app con ingress externo: al aplicar, Terraform te da un FQDN en azurerm_container_app.min.ingress[0].fqdn. Esa URL responde por HTTPS en segundos.
  4. Falta la salud y la identidad: por eso es el «mínimo». En el ejemplo real añadimos ambos para que sea apto para producción.

4 · Ejemplo real

El despliegue completo de la Copiloto API, tal como lo usarías en producción: registro → servicio → salud → URL pública, con identidad gestionada y probes, y con la configuración sensible (la cadena de conexión a la base de datos) como secreto, nunca en el código.

copiloto.tf — despliegue completo
# ------------------------- REGISTRO -------------------------
resource "azurerm_container_registry" "acr" {
  name                = "copilotoacr"
  resource_group_name = var.resource_group_name
  location            = var.location
  sku                 = "Standard"      # Standard para el entorno de producción
  admin_enabled       = false
  tags                = { course = "cloud" }
}

# ------------------------- IDENTIDAD -------------------------
# Identidad gestionada POR LA APP, no compartida con nada más.
resource "azurerm_user_assigned_identity" "app" {
  name                = "id-copiloto-api"
  resource_group_name = var.resource_group_name
  location            = var.location
}

# Permiso de SOLO LECTURA de imágenes sobre el registro (mínimo privilegio).
resource "azurerm_role_assignment" "acr_pull" {
  scope                = azurerm_container_registry.acr.id
  role_definition_name = "AcrPull"
  principal_id         = azurerm_user_assigned_identity.app.principal_id
}

# ------------------------- SERVICIO -------------------------
resource "azurerm_container_app" "copiloto" {
  name                         = "copiloto-api"
  container_app_environment_id = azurerm_container_app_environment.main.id
  resource_group_name          = var.resource_group_name
  revision_mode                = "Single"

  # La app usa su identidad para autenticarse contra el ACR.
  identity {
    type         = "UserAssigned"
    identity_ids = [azurerm_user_assigned_identity.app.id]
  }

  # Y el registro se declara con esa identidad: sin usuario ni contraseña.
  registry {
    server   = azurerm_container_registry.acr.login_server
    identity = azurerm_user_assigned_identity.app.id
  }

  # La cadena de conexión a la BD vive como SECRETO en la app.
  # Su valor se pasa en tiempo de apply (nunca en el repositorio).
  secret {
    name  = "database-url"
    value = var.database_url
  }

  template {
    container {
      name   = "api"
      image  = "${azurerm_container_registry.acr.login_server}/copiloto-api:2.0.0"
      cpu    = 0.5
      memory = "1Gi"

      # El secreto se inyecta como variable de entorno: la app lee DATABASE_URL.
      env {
        name        = "DATABASE_URL"
        secret_name = "database-url"
      }

      # (3) SALUD: startup da tiempo a arrancar; readiness decide el tráfico.
      startup_probe {
        transport               = "HTTP"
        port                    = 8000
        path                    = "/health"
        initial_delay           = 5
        interval_seconds        = 5
        failure_count_threshold = 12   # ~1 min de margen para arrancar
      }
      readiness_probe {
        transport        = "HTTP"
        port             = 8000
        path             = "/health"
        interval_seconds = 10
      }
      # liveness a la MISMA ruta en este caso, pero con umbrales laxos:
      # reinicia solo si realmente se ha colgado, no por un pico puntual.
      liveness_probe {
        transport               = "HTTP"
        port                    = 8000
        path                    = "/health"
        interval_seconds        = 30
        failure_count_threshold = 3
      }
    }

    min_replicas = 1     # una réplica caliente: sin cold start
    max_replicas = 5     # techo de coste (lección 03)
  }

  # ------------------------- URL PUBLICA -------------------------
  ingress {
    external_enabled           = true       # accesible desde Internet
    target_port                = 8000       # el puerto que escucha la app
    allow_insecure_connections = false      # solo HTTPS, TLS gestionado
  }

  tags = { course = "cloud", environment = "lab" }
}
outputs.tf — la URL pública como salida
output "copiloto_url" {
  description = "URL publica HTTPS de la Copiloto API"
  value       = "https://${azurerm_container_app.copiloto.ingress[0].fqdn}"
}

output "health_url" {
  description = "Endpoint de salud para comprobar el despliegue"
  value       = "https://${azurerm_container_app.copiloto.ingress[0].fqdn}/health"
}

Ahora la parte que sube la imagen al registro. Puedes construir dentro de Azure con az acr build, que compila en la nube y evita depender de tu Docker local:

terminal — construir y publicar la imagen
# Construye la imagen usando el ACR (no hace falta Docker local) y la publica
# con el tag 2.0.0, que es el que referencia el Terraform de arriba.
az acr build \
  --registry copilotoacr \
  --image copiloto-api:2.0.0 \
  --file Dockerfile \
  .

# Y ahora, el despliegue de la infraestructura:
terraform init
terraform apply -var="database_url=$DATABASE_URL"

# Obtén la URL y comprueba la salud:
terraform output copiloto_url
curl -s "$(terraform output -raw health_url)"
# Esperado: un JSON de estado {"status":"ok"} o similar desde /health.

Lee las decisiones importantes en voz alta:

  • Registro → servicio con identidad: la app nunca guarda credenciales del registro. La identidad UserAssigned tiene solo AcrPull.
  • La base de datos entra como secreto: DATABASE_URL se pasa en el apply y queda como secret en la app. Ni en el código, ni en la imagen, ni en el repositorio. En producción real, el secreto se leería de Key Vault con identidad (módulo 2), pero el principio se ve aquí con claridad.
  • Los tres probes: startup tolera un arranque lento, readiness evita mandar tráfico antes de tiempo, liveness reinicia solo si de verdad se cuelga.
  • La URL pública es una salida del código: terraform output copiloto_url. Nada de buscar la URL a mano en la consola.

En el proyecto final (módulo 7) este mismo Terraform se orquesta con GitHub Actions + OIDC: el pipeline hace az acr build y terraform apply sin ninguna clave almacenada, cerrando el círculo del despliegue «todo como código» del curso.

6 · Errores habituales

1. Desplegar una imagen del ACR sin permiso AcrPull

Incorrecto — falta la asignación de rol 
# ❌ La app apunta al ACR pero su identidad no puede leer del registro.
# Resultado: la revisión falla con un error al bajar la imagen y no arranca.
registry { server = azurerm_container_registry.acr.login_server }
# ...pero nunca se creó el azurerm_role_assignment con rol AcrPull
Correcto — identidad + rol explícitos 
# ✅ La identidad tiene AcrPull, y el registry la usa.
resource "azurerm_role_assignment" "acr_pull" {
  scope                = azurerm_container_registry.acr.id
  role_definition_name = "AcrPull"
  principal_id         = azurerm_user_assigned_identity.app.principal_id
}

registry {
  server   = azurerm_container_registry.acr.login_server
  identity = azurerm_user_assigned_identity.app.id
}

2. Guardar la cadena de conexión a la base de datos en el código

Incorrecto — secreto en el repositorio 
# ❌ Credenciales en claro: quedan en git, en el state y en los logs.
env {
  name  = "DATABASE_URL"
  value = "postgres://copiloto:pa55word@db.postgres.database.azure.com:5432/copiloto"
}
Correcto — secreto declarado, valor en apply 
# ✅ El código declara el secreto; el valor entra en tiempo de apply.
secret {
  name  = "database-url"
  value = var.database_url   # variable sensible, marcada como sensitive
}
env {
  name        = "DATABASE_URL"
  secret_name = "database-url"
}

3. Apuntar liveness a algo que depende de otro servicio

# ❌ Si /health-db comprueba la base de datos, y la BD cae un segundo,
# la plataforma reiniciará TODAS las réplicas a la vez.
liveness_probe {
  path = "/health-db"   # depende de un servicio externo
}

# ✅ liveness a una ruta local y barata: solo comprueba que el proceso responde.
#    La comprobación de dependencias va en readiness o en métricas/alarmas.
liveness_probe {
  path = "/health"      # sin salir de la app
}

Este error convierte una degradación pequeña (la BD responde lenta) en una caída total (todas las réplicas reiniciándose). El liveness debe responder a la pregunta «¿mi proceso está vivo?», no «¿está todo el sistema perfecto?».

4. Olvidar que el contenedor escucha en 0.0.0.0

# ❌ El servidor por defecto puede escuchar solo en localhost dentro del contenedor.
# uvicorn copiloto.main:app --host 127.0.0.1 --port 8000

# ✅ Debe escuchar en todas las interfaces para que el ingress lo alcance.
CMD ["uvicorn", "copiloto.main:app", "--host", "0.0.0.0", "--port", "8000"]

Síntoma típico: el contenedor está «Running», no hay error en los logs, pero la URL devuelve 502. El target_port coincide, pero el proceso solo atiende en 127.0.0.1. Es de los fallos más frecuentes y más difíciles de ver sin saberlo.

7 · Ejercicio guiado

Objetivo: recorrer el ciclo completo (registro → servicio → salud → URL pública) desplegando la Copiloto API y verificando que la URL responde por HTTPS.

  1. Paso 1 — grupo de recursos y registro. 
    az group create --name copiloto-rg --location westeurope --tags course=cloud
az acr create \
  --name copilotoacr --resource-group copiloto-rg \
  --sku Standard --admin-enabled false
  2. Paso 2 — construye y publica la imagen en el registro. Si no tienes el código a mano, usa una etiqueta de ejemplo: 
    az acr build \
  --registry copilotoacr \
  --image copiloto-api:2.0.0 \
  --file Dockerfile .
# Verifica que la imagen está en el registro:
az acr repository show-tags --name copilotoacr --repository copiloto-api --output table
  3. Paso 3 — crea el entorno y la app con ingress externo. 
    az containerapp env create \
  --name cae-copiloto --resource-group copiloto-rg --location westeurope

az containerapp create \
  --name copiloto-api \
  --resource-group copiloto-rg \
  --environment cae-copiloto \
  --image copilotoacr.azurecr.io/copiloto-api:2.0.0 \
  --registry-server copilotoacr.azurecr.io \
  --target-port 8000 \
  --ingress external \
  --min-replicas 1 --max-replicas 5
  4. Paso 4 — configura los health checks. La ruta /health debe existir en la app: 
    az containerapp update \
  --name copiloto-api --resource-group copiloto-rg \
  --set-env-vars "DATABASE_URL=secretref:database-url"

    En producción, los probes se declaran igual que en el ejemplo real (startup/readiness/liveness hacia /health); por CLI también se pueden ajustar, pero recuerda: el objetivo es que quede en Terraform, no solo aplicado.

  5. Paso 5 (verificación) — obtén la URL y comprueba la salud. 
    FQDN=$(az containerapp show \
  --name copiloto-api --resource-group copiloto-rg \
  --query properties.configuration.ingress.fqdn --output tsv)

echo "URL:    https://$FQDN"
echo "Health: https://$FQDN/health"
curl -s "https://$FQDN/health"
# Esperado: HTTP 200 con un estado de salud de la app.
  6. Paso 6 — comprueba que hay una réplica lista. 
    az containerapp replica list \
  --name copiloto-api --resource-group copiloto-rg \
  --query "[].{name:name, runningState:properties.runningState, health:properties.healthState}" \
  --output table
# Esperado: al menos una réplica con estado Healthy y Running.
  7. Paso 7 — limpia todo (control de coste). 
    az group delete --name copiloto-rg --yes --no-wait
# El registro y el entorno también se borran con el grupo: no queda nada facturando.

Resultado esperado: una URL https://.../health que responde 200, con la imagen servida desde tu registro y una réplica en estado Healthy. Has completado el ciclo registro → servicio → salud → URL pública de punta a punta.

8 · Reto

🎯 Despliegue continuo sin claves: del commit a la URL

Automatiza el ciclo completo en un pipeline de GitHub Actions que, al hacer push a main, haga exactamente esto: (1) construya y publique la imagen en el ACR con un tag basado en el SHA del commit; (2) aplique el Terraform que actualiza la Container App a esa imagen nueva; (3) compruebe /health contra la URL pública y falle el pipeline si no responde 200.

La condición dura del reto: ninguna credencial de larga vida. La autenticación contra Azure debe ser por OIDC federado (módulo 2), sin secretos guardados en GitHub. Documenta cómo el pipeline obtiene la identidad, cómo construye la imagen y cómo verifica la salud al final.

Pista: el rol de la identidad federada necesita permiso para hacer az acr build (contributor sobre el registro) y para aplicar Terraform sobre el grupo de recursos; y el paso de verificación es simplemente un curl --fail contra el health_url que expone tu outputs.tf.

9 · Resumen

  • Desplegar = encadenar registro → servicio → salud → URL pública, todo como código.
  • La imagen se lee del registro con identidad gestionada + rol AcrPull: nunca usuario/contraseña.
  • Los tres probes tienen fines distintos: startup (arranque), readiness (recibir tráfico), liveness (reiniciar si se cuelga).
  • La configuración sensible va como secret y como variable de entorno secretref, nunca en el código ni en la imagen.
  • El ingress externo da HTTPS con TLS gestionado; allow_insecure_connections = false fuerza solo HTTPS.
  • La URL pública es una salida de Terraform (output), no algo que se busca a mano.

10 · Preguntas frecuentes

¿Dónde debe vivir la ruta /health? ¿Qué debe comprobar?

En la propia aplicación, y debe responder rápido. Para readiness y liveness, comprueba que el proceso puede atender peticiones (por ejemplo, que el servidor HTTP responde). Para comprobar dependencias como la base de datos, hazlo en una ruta distinta (/health/ready) o mejor en métricas y alertas, no en liveness: si el liveness depende de un servicio externo, una caída momentánea de ese servicio reiniciará todas tus réplicas a la vez.

¿Cómo actualizo la app a una versión nueva sin dejar de servir?

Construyes y publicas la imagen nueva con un tag distinto (por ejemplo el SHA del commit), actualizas el image en Terraform y aplicas. En modo Single, la plataforma crea una revisión nueva y retira la vieja cuando la nueva pasa su readiness. Si quieres máxima seguridad, usa Multiple con traffic weights (lección 01): la versión nueva recibe un porcentaje pequeño de tráfico antes del cambio total.

¿Por qué el despliegue tarda o se queda «atascado» al principio?

Las causas más comunes son: el target_port no coincide con el puerto del contenedor; el contenedor escucha en 127.0.0.1 en vez de 0.0.0.0; el startup_probe es demasiado estricto para lo que tarda tu app en arrancar; o la imagen no se puede descargar del registro por falta de permiso (AcrPull). Revisa esos cuatro puntos en ese orden y casi siempre encontrarás la causa.

¿Cómo paso los secretos sin ponerlos en el repositorio?

El código declara el secret y las variables, pero los valores entran en tiempo de apply: mediante una variable marcada como sensitive, o —mejor— leyéndolos de Azure Key Vault con la identidad gestionada de la app (módulo 2). En el proyecto final se añade además GitHub OIDC para que el propio pipeline no guarde ninguna credencial. El repositorio nunca contiene secretos.

¿Y si trabajo sobre AWS? ¿Cambia el flujo?

El flujo es idéntico; cambian los nombres. El registro es ECR, el servicio es aws_apprunner_service (o ECS Fargate si necesitas más control), la identidad se sustituye por un rol de IAM con permiso de lectura de ECR, y el endpoint HTTPS lo da el propio servicio. La salud se configura con los parámetros de health check del servicio. La gran diferencia a recordar: App Runner no tiene el modelo de revisiones con pesos de Container Apps.
