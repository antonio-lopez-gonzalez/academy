Despliegue y CI/CD

Módulo 7 · Proyecto final: Copiloto en la nube 🕐 40 minutos

1 · Introducción

Ya tienes el plano (lección 01) y el Terraform que lo crea (lección 02). Falta lo que convierte esto en un proyecto de verdad: que cada push a main despliegue el Copiloto solo, sin que nadie abra una terminal, y —esta es la parte que separa a un aficionado de un profesional— sin ninguna clave de larga vida guardada en GitHub.

El pipeline hace tres cosas, en este orden:

  git push  -->  GitHub Actions
                   |
                   | (1) az acr build     <-- construye la imagen y la sube al ACR
                   | (2) terraform apply  <-- crea/actualiza la infraestructura
                   | (3) curl --fail .../health  <-- verifica que la URL responde 200
                   |
                   v
              Copiloto en producción

La autenticación contra Azure no usa contraseñas: usa OIDC federado. GitHub firma un token diciendo «soy este repositorio en esta rama» y Azure lo cambia por un token de acceso temporal, tras comprobar que se lo habías autorizado de antemano. No hay secreto que robar.

¿Por qué existe esta lección? Porque «desplegar a mano» no escala: es lento, no queda registrado y depende de que la persona recuerde los pasos. El CI/CD es el que garantiza que lo que hay en producción es lo que hay en main, construido de forma reproducible. Y hacerlo con OIDC elimina el eslabón más débil de cualquier pipeline: la credencial guardada que se filtra.

2 · Teoría

El problema de las claves de larga vida

La forma tradicional de desplegar desde un pipeline es crear un service principal y guardar su client secret como secreto del repositorio. Funciona… y tiene los problemas de siempre: el secreto no caduca solo, hay que rotarlo a mano, si se filtra da acceso hasta que alguien lo note, y queda copiado en los logs de quien lo configuró.

Service principal con client secretOIDC federado (sin secreto)
Qué se guarda en GitHubUna contraseña de larga vidaNada secreto: ids que no son sensibles
CaducidadManual, fácil de olvidarEl token dura minutos y expira solo
Si se filtraAcceso hasta rotarloNo hay nada que filtrar
RotaciónUn trabajo programado en el calendarioNo existe: no hay credencial que rotar
Alcance de la confianzaEl secreto vale para todoSe limita a este repo, esta rama/entorno

Cómo funciona OIDC, paso a paso

Parece magia, pero son cinco pasos mecánicos:

  1. GitHub emite un token OIDC para el job, solo si el workflow declara permissions: id-token: write. Ese token lleva claims (afirmaciones): el repositorio, la rama, el entorno.
  2. La acción azure/login envía ese token a Entra ID pidiendo cambiarlo por un token de Azure.
  3. Azure comprueba el token contra una credencial federada que configuraste antes: «confío en tokens cuyo subject sea repo:mi-org/mi-repo:ref:refs/heads/main».
  4. Si coincide, Azure devuelve un token de acceso temporal con los permisos del rol asignado.
  5. El resto del job usa ese token como si hubieras hecho az login: ninguna contraseña ha tocado el disco.

Analogía: el secret de larga vida es una llave física que copias y guardas en un cajón (y que si pierdes, hay que cambiar la cerradura). El OIDC es un portero que solo te abre si te reconoce por la cara: llegas, comprueba tu identidad en el momento, te deja pasar un rato y se cierra solo. No hay llave que robar porque nunca hubo una.

Crear la credencial federada (una vez)

Azure necesita saber en quién confía. Se registra una identidad (una app registration o una identidad gestionada) y se le añade una credencial federada cuyo subject ata la confianza al repositorio y la rama:

ClaimValor típicoPara qué sirve
issuerhttps://token.actions.githubusercontent.comQuién emite el token (GitHub)
audienceapi://AzureADTokenExchangePara qué se emite
subjectrepo:mi-org/infra-cloud:ref:refs/heads/mainQué repo y qué rama concreta pueden usarlo

El subject es la cerradura. Si pones un comodín, cualquier rama o cualquier repo de tu organización podría pedir ese token. Ata la confianza a la rama que despliega (main) o, mejor, a un GitHub Environment (environment:production) que exija aprobación manual. Eso convierte «cualquiera con push» en «quien tú apruebes».

Qué permisos necesita el pipeline

El principio del mínimo privilegio también aplica aquí. La identidad federada necesita justo dos capacidades:

  • Empujar imágenes al ACR: AcrPush sobre el registro.
  • Gestionar la infraestructura: permiso para crear/actualizar los recursos del entorno. En el laboratorio vale Contributor sobre el grupo de recursos; en producción, un rol a medida con lo justo. Nunca Owner.

Los ids de la identidad (client-id, tenant-id, subscription-id) no son secretos: son identificadores públicos. Guárdalos como variables del repositorio (vars), no como secrets. Es la señal de que entendiste OIDC: si algo es un secreto en tu pipeline, es que el OIDC está mal montado.

3 · Ejemplo mínimo

El workflow más pequeño que demuestra que el OIDC funciona: autenticarse y listar los grupos de recursos. Nada de build ni apply todavía.

.github/workflows/login-minimo.yml
name: login-minimo

on:
  workflow_dispatch:        # solo manual, para probar

# Sin este permiso, GitHub NO emite el token OIDC y el login falla.
permissions:
  id-token: write
  contents: read

jobs:
  probar-login:
    runs-on: ubuntu-latest
    steps:
      - name: Login en Azure con OIDC (sin secreto)
        uses: azure/login@v2
        with:
          client-id:       ${{ vars.AZURE_CLIENT_ID }}
          tenant-id:       ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Comprobar que estamos dentro
        run: az group list --query "[].name" --output tsv

Fíjate en las tres cosas que hacen que esto sea seguro y no un atajo:

  1. permissions: id-token: write: habilita la emisión del token OIDC para este job. Sin esa línea, azure/login no tiene nada que intercambiar.
  2. azure/login@v2: hace el intercambio del token de GitHub por el de Azure. No se le pasa contraseña: solo los tres identificadores.
  3. vars, no secrets: los ids no son secretos. Guardarlos como secrets «por costumbre» es una señal de que no entendiste el modelo.

4 · Ejemplo real

El pipeline completo del Copiloto. Primero, configurar la confianza en Azure una sola vez (por CLI, reproducible):

terminal — registrar identidad, credencial federada y roles
# 1) Crea la identidad de la aplicación (no confundir con la app de usuario).
APP_ID=$(az ad app create --display-name "gh-infra-cloud" --query appId --output tsv)
SP_ID=$(az ad sp create --id "$APP_ID" --query id --output tsv)

# 2) Añade la credencial federada: confía SOLO en pushes a main del repo.
az ad app federated-credential create \
  --id "$APP_ID" \
  --parameters '{
    "name": "github-main",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:mi-org/infra-cloud:ref:refs/heads/main",
    "audiences": ["api://AzureADTokenExchange"]
  }'

# 3) Da permisos mínimos: empujar al ACR y gestionar el grupo de recursos.
ACR_ID=$(az acr show --name copilotoacrprod --query id --output tsv)
az role assignment create --assignee "$SP_ID" \
  --role "AcrPush" --scope "$ACR_ID"

az role assignment create --assignee "$SP_ID" \
  --role "Contributor" --scope "/subscriptions/$SUBSCRIPTION_ID/resourceGroups/rg-copiloto-prod"

Ahora el workflow. Tiene dos trabajos encadenados: build (imagen al ACR con el SHA del commit) y deploy (Terraform y verificación):

.github/workflows/deploy.yml
name: deploy-copiloto

on:
  push:
    branches: [ main ]
  workflow_dispatch:

# Un solo despliegue a la vez: si llega otro push, cancela el anterior.
concurrency:
  group: copiloto-prod
  cancel-in-progress: false

permissions:
  id-token: write        # imprescindible para OIDC
  contents: read

env:
  RESOURCE_GROUP: rg-copiloto-prod
  ACR_NAME: copilotoacrprod
  IMAGE: copiloto-api

jobs:
  # ------------------------------------------------ (1) BUILD Y PUSH
  build:
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.meta.outputs.tag }}
    steps:
      - uses: actions/checkout@v4

      - name: Login en Azure
        uses: azure/login@v2
        with:
          client-id:       ${{ vars.AZURE_CLIENT_ID }}
          tenant-id:       ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Etiqueta inmutable a partir del commit
        id: meta
        run: echo "tag=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"

      # Construye DENTRO de Azure (no hace falta Docker en el runner) y publica.
      - name: Construir y subir la imagen al ACR
        run: |
          az acr build \
            --registry "$ACR_NAME" \
            --image "$IMAGE:${{ steps.meta.outputs.tag }}" \
            --file Dockerfile \
            .

  # ------------------------------------------------ (2) APPLY
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production      # puede exigir aprobación manual en GitHub
    steps:
      - uses: actions/checkout@v4

      - name: Login en Azure
        uses: azure/login@v2
        with:
          client-id:       ${{ vars.AZURE_CLIENT_ID }}
          tenant-id:       ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Instalar Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.9.5"

      # El state vive en Blob Storage; la clave llega del entorno del runner.
      - name: terraform init
        working-directory: infra
        run: terraform init
        env:
          ARM_ACCESS_KEY: ${{ secrets.TFSTATE_ACCESS_KEY }}

      # El secreto de la base de datos viaja como TF_VAR_*, no en el repo.
      - name: terraform plan
        working-directory: infra
        run: terraform plan -var-file=prod.tfvars -out=tfplan -input=false
        env:
          ARM_ACCESS_KEY: ${{ secrets.TFSTATE_ACCESS_KEY }}
          TF_VAR_db_admin_password: ${{ secrets.DB_ADMIN_PASSWORD }}
          TF_VAR_database_url: ${{ secrets.DATABASE_URL }}
          TF_VAR_image_tag: ${{ needs.build.outputs.tag }}

      - name: terraform apply
        working-directory: infra
        run: terraform apply -input=false -auto-approve tfplan
        env:
          ARM_ACCESS_KEY: ${{ secrets.TFSTATE_ACCESS_KEY }}
          TF_VAR_db_admin_password: ${{ secrets.DB_ADMIN_PASSWORD }}
          TF_VAR_database_url: ${{ secrets.DATABASE_URL }}
          TF_VAR_image_tag: ${{ needs.build.outputs.tag }}

      # -------------------------------------------- (3) VERIFICAR
      - name: Comprobar que la URL responde
        working-directory: infra
        run: |
          HEALTH=$(terraform output -raw health_url)
          echo "Comprobando $HEALTH"
          curl --fail --retry 10 --retry-delay 5 --retry-all-errors "$HEALTH"

Merece la pena detenerse en las decisiones del workflow:

  • concurrency: impide que dos despliegues se pisen. cancel-in-progress: false deja terminar el que está en marcha en vez de cortarlo a mitad de un apply.
  • Etiqueta por SHA (${GITHUB_SHA::7}): cada commit produce una imagen inmutable y trazable. Sabes exactamente qué código corre en producción y puedes volver atrás desplegando el tag anterior.
  • needs: build: el deploy no arranca si el build falla. Nada de aplicar infraestructura apuntando a una imagen que no existe.
  • az acr build: construye la imagen en Azure, sin depender del Docker del runner y sin exponer el registro a la máquina del CI.
  • environment: production: permite exigir aprobación manual antes de tocar producción. El pipeline prepara el despliegue; un humano decide cuándo.
  • TF_VAR_* desde secrets: los secretos de verdad (contraseña de la BD, clave del state) llegan al apply como variables de entorno en el runner, sin escribir jamás en el repositorio.
  • curl --fail con reintentos: si la URL no responde 200 tras los reintentos, el paso falla y el pipeline se pone en rojo. Un despliegue sin verificación no es un despliegue: es una esperanza.

¿Y la contraseña de la base de datos? Aparece como secrets.DATABASE_URL, sí, pero solo porque el laboratorio guarda el secreto en GitHub para simplificar. El destino final (reto de la lección 02) es que la app lea ese secreto de Key Vault con su identidad y el pipeline ni lo vea. Avanzamos hacia ahí.

6 · Errores habituales

1. Olvidar id-token: write y culpar al OIDC

Incorrecto — sin permiso de token 
# ❌ Sin `permissions`, GitHub no emite token y azure/login falla con
# "no OIDC token available". No es Azure: es el workflow.
name: deploy
on: [ push ]
jobs:
  deploy: { runs-on: ubuntu-latest, steps: [...] }
Correcto — permiso explícito 
# ✅ El job pide permiso para obtener el token OIDC.
permissions:
  id-token: write
  contents: read

2. Un subject con comodín

Incorrecto — confianza demasiado amplia 
{
  "subject": "repo:mi-org/infra-cloud:*"
}
Correcto — rama o entorno concretos 
{
  "subject": "repo:mi-org/infra-cloud:environment:production"
}

Con el comodín, cualquier rama —incluida una creada por un atacante con permiso de push— podría pedir un token con los permisos de despliegue. Fijarlo a un environment con aprobación reduce aún más la superficie que atar solo a la rama.

3. Guardar el client secret «por si el OIDC falla»

# ❌ Guardas un secreto de larga vida como red de seguridad.
# Vuelves a tener el problema que OIDC venía a resolver: credencial que robar.
with:
  creds: ${{ secrets.AZURE_CREDENTIALS }}   # un JSON con un client secret dentro

# ✅ Sin secreto: solo los ids, y la confianza federada en Azure.
with:
  client-id:       ${{ vars.AZURE_CLIENT_ID }}
  tenant-id:       ${{ vars.AZURE_TENANT_ID }}
  subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

Si mantienes un secreto «por si acaso», has migrado la superficie de ataque a un sitio más difícil de ver. OIDC no es un extra: es el sustituto del secreto.

4. Ejecutar código de un PR con secretos a mano

# ❌ `pull_request_target` con acceso a secretos y checkout del código del PR
# permite a un PR malicioso exfiltrar tus secretos.
on:
  pull_request_target:
    types: [opened, synchronize]

# ✅ Para PRs, solo `pull_request` (sin secretos) y como mucho `terraform plan`,
#    que no necesita credenciales con permiso de escritura.
on:
  pull_request:
    branches: [ main ]

Esta es una de las vulnerabilidades de CI/CD más explotadas. Para un PR solo necesitas planificar, no aplicar. Deja el apply para pushes a main, tras revisión.

Objetivo: montar la confianza federada y conseguir que un workflow se autentique y despliegue sin ningún secreto de larga vida.

gh variable set AZURE_CLIENT_ID       --body "$APP_ID"

    ls .github/workflows/deploy.yml
# Revisa que la rama del `subject` coincide con la que despilega (main).
  5. Paso 5 — dispara el despliegue y observa. 
    git checkout -b ci-oidc
git add .github/workflows/deploy.yml
git commit -m "ci: despliegue con OIDC"

# Abre el PR, fusiónalo a main y mira el workflow en la pestaña Actions.
# Esperado: login OK, imagen publicada con el SHA, apply correcto y curl 200.

8 · Reto

🎯 Despliegue azul/verde con revisión previa y vuelta atrás

Lleva el pipeline al siguiente nivel de seguridad de despliegue: que nunca cambie el 100 % del tráfico a una versión nueva de golpe. Diseña un workflow que, en cada push a main: (1) publique la imagen nueva; (2) cree una revisión nueva de la Container App y le mande un porcentaje pequeño de tráfico (por ejemplo 10 %); (3) espere y compruebe salud y errores con ese porcentaje; (4) suba el tráfico al 100 % solo si la comprobación pasa; y (5) si algo falla, vuelva solo a la revisión anterior sin intervención humana.

Además, en cada pull request el pipeline debe publicar un terraform plan como comentario del PR (usando pull_request, sin secretos de escritura) para que el revisor vea exactamente qué va a cambiar antes de aprobar.

Pista: Container Apps soporta revision_mode = "Multiple" con traffic weights (módulo 4, 01-container-apps y 03-escalado). Para el paso 4–5, mira las métricas de la revisión nueva con Azure Monitor y decide en función de ellas; para el comentario del PR, el paso de plan produce una salida que puedes publicar, pero cuidado con exponer valores sensibles en el comentario.

9 · Resumen

  • El CI/CD convierte push → build → apply → verify en un proceso automático, reproducible y registrado.
  • OIDC federado sustituye al client secret: GitHub emite un token, Azure lo valida contra una credencial federada y devuelve uno temporal. No hay clave de larga vida.
  • El subject de la credencial federada es la cerradura: átalo al repo y a la rama o al environment con aprobación.
  • Los ids (client-id, tenant-id, subscription-id) son vars, no secrets.
  • Permisos mínimos: AcrPush y un rol acotado al grupo de recursos; nunca Owner sobre la suscripción.
  • concurrency, imágenes etiquetadas por SHA, needs: y environment: de producción hacen el pipeline seguro y ordenado.
  • El despliegue termina verificando con un curl --fail: en verde solo si la app responde de verdad.

10 · Preguntas frecuentes

¿Por qué el login falla con «no OIDC token available»?

Casi siempre por falta de permissions: id-token: write en el job. GitHub solo emite el token OIDC si el workflow lo pide de forma explícita. Si ya lo tienes, revisa que el subject de la credencial federada coincide exactamente con el repositorio y la rama del workflow: un solo carácter distinto (por ejemplo refs/heads/main frente a pull_request) hace que Azure rechace el token.

¿Necesito algún secreto guardado en GitHub?

Para la autenticación con Azure, ninguno: eso es justo lo que aporta OIDC. Puedes necesitar secrets para otras cosas del pipeline (la clave de acceso al backend del state, la contraseña de la BD del laboratorio), pero nunca una credencial de Azure de larga vida. Si tu pipeline tiene un AZURE_CREDENTIALS guardado, es que aún no has terminado la migración a OIDC.

¿az acr build o construyo con Docker en el runner?

az acr build construye la imagen dentro de Azure, así que el runner no necesita Docker ni exponer credenciales del registro: solo el permiso AcrPush. Es más simple, más rápido (caché en el registro) y más seguro. Usa Docker en el runner solo si necesitas algo que ACR Tasks no soporta (por ejemplo, un build multi-arquitectura muy específico).

¿Cómo despliego a dev sin tocar prod?

Con environments de GitHub Actions y ficheros de variables distintos. En vez de un único environment: production, tienes environment: dev y environment: production, cada uno con su propia credencial federada (o el mismo subject por rama) y su -var-file. El workflow elige el tfvars según el entorno. Así dev y prod nunca comparten state ni credenciales.

¿Qué hago si el apply queda a medias y el pipeline se corta?

El state remoto de Terraform es transaccional por recurso, así que un corte deja la infraestructura en un estado intermedio pero consistente con el state. Vuelve a lanzar el pipeline: el siguiente plan mostrará exactamente qué falta por crear y apply lo completará. Lo que no debes hacer nunca es borrar el state «para empezar limpio»: eso convertiría recursos reales en huérfanos invisibles para Terraform. Para eso existe concurrency con cancel-in-progress: false.
