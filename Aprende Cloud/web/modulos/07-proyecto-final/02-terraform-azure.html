Terraform para Azure

Módulo 7 · Proyecto final: Copiloto en la nube 🕐 45 minutos

1 · Introducción

La lección anterior fijó el plano. Esta lo convierte en código que crea la infraestructura entera de una sola vez: red, registro, cómputo, base de datos, secretos y observabilidad. Es el corazón del proyecto proyectos/infra-cloud/.

Pero «escribir Terraform» no es vaciar recursos en un main.tf y darle a apply. Un Terraform de proyecto real tiene tres cosas que un script de principiante no tiene:

  1. Un backend remoto y versionado, para que el state no viva en el portátil de nadie y no acabe en el repositorio.
  2. Variables y outputs, para que lo mismo sirva para dev y para prod sin copiar y pegar archivos.
  3. Etiquetas de coste y cero secretos, las dos reglas no negociables del curso.

¿Por qué existe esta lección? Porque aquí es donde se decide si tu infraestructura es repetible o artesanal. Con lo que escribas aquí, la lección 03 podrá crear y actualizar todo el Copiloto desde un pipeline sin tocar la consola, y la lección 04 podrá etiquetar, presupuestar y observar cada recurso. Si el Terraform es desordenado, todo lo que viene detrás arrastra ese desorden.

2 · Teoría

Cómo lee Terraform un proyecto

Terraform no «ejecuta» un archivo: lee toda la carpeta .tf como una sola unidad. Por eso da igual llamar a los archivos main.tf, red.tf o datos.tf: lo que importa es organizarlos por responsabilidad. La estructura que usaremos:

  infra-cloud/
  ├── versions.tf     <-- versión de Terraform + providers (azurerm)
  ├── backend.tf      <-- dónde vive el STATE (remoto, no en git)
  ├── variables.tf    <-- ENTRADAS: lo que cambia entre dev y prod
  ├── main.tf         <-- los recursos (el plano de la lección 01)
  ├── outputs.tf      <-- SALIDAS: URL, ids, nombres de recursos
  ├── dev.tfvars      <-- valores para dev  (sin secretos)
  └── prod.tfvars     <-- valores para prod (sin secretos)

Analogía: el state es el inventario de la obra. Terraform no recuerda lo que creó mirando Azure; lo recuerda leyendo ese inventario. Si lo pierdes, no sabe qué existe y qué tiene que borrar o modificar. En el portátil, ese inventario es único y frágil; por eso vive en un backend remoto (un contenedor de Blob Storage), compartido y bloqueado mientras alguien aplica.

El state remoto: por qué nunca en el repositorio

El state contiene todo lo que Terraform sabe, incluidos valores que a veces son sensibles. Las tres reglas de oro:

ReglaPor qué
Nunca en .gitEl state puede contener secretos y, además, es un archivo binario que se pisa a cada apply
Siempre en un backend remotoUn solo estado compartido: todo el equipo y el pipeline ven lo mismo
Con state lockingEvita que dos apply a la vez corrompan el inventario (Azure lo hace con un lease del blob)

El backend azurerm guarda el state en un contenedor de una cuenta de almacenamiento. Esos datos (cuenta, contenedor, clave de acceso) no son secretos: se pueden crear por CLI y se pasan con terraform init -backend-config, o como variables de entorno:

terminal — crear el backend (una sola vez)
# La cuenta y el contenedor del state se crean a mano, UNA vez, fuera del
# Terraform (el huevo y la gallina: el state no puede depender de sí mismo).
az group create --name rg-tfstate --location westeurope
az storage account create \
  --name sttfstatecopiloto --resource-group rg-tfstate \
  --sku Standard_LRS --encryption-services blob
az storage container create --name tfstate --account-name sttfstatecopiloto

El backend se configura una vez y no se toca más. Terraform puede leer la clave de la cuenta desde el entorno (ARM_ACCESS_KEY) o —mejor— usar la identidad del pipeline contra el backend. Lo importante: esa credencial no va en el repositorio.

Variables, locals y tfvars: una sola base de código

La diferencia entre dev y prod no debe ser un archivo duplicado. Debe ser un valor distinto. Para eso están tres cosas que se confunden a menudo:

PiezaQué esEjemplo
variableUna entrada que quien aplica puede cambiarvar.environment = "prod"
localUn valor calculado dentro del código, no editable desde fueralocal.tags = { project = "copiloto", … }
.tfvarsEl archivo con los valores concretos por entornoprod.tfvars

Un truco que usarás siempre: derivar los nombres de los recursos de var.environment. Así terraform apply -var-file=dev.tfvars crea el entorno de dev y prod.tfvars el de producción, sin tocar el código:

infra/main.tf — el nombre sale del entorno
resource "azurerm_virtual_network" "vnet" {
  name = "vnet-copiloto-${var.environment}"   # vnet-copiloto-dev | vnet-copiloto-prod
  # ...
}

El patrón «protegido»: lo que nunca entra en el repositorio

El curso repite una y otra vez: ningún secreto en el repositorio. En Terraform esto se traduce en una regla concreta: una variable que contiene un secreto se declara con sensitive = true y su valor nunca se escribe en un .tfvars versionado —se pasa por variable de entorno o, mejor, se guarda en Key Vault y se lee con data.

infra/variables.tf — la variable sensible
variable "db_admin_password" {
  description = "Password del administrador de PostgreSQL (llega en apply, no en git)"
  type        = string
  sensitive   = true          # Terraform la enmascara en el plan y en los logs
}

Ojo: sensitive = true oculta el valor en la salida, pero el valor sigue guardándose en el state. Por eso el state debe estar en un backend protegido y cifrado, y por eso en la lección 03 el pipeline inyecta el secreto desde el entorno, nunca desde un archivo del repositorio.

3 · Ejemplo mínimo

El esqueleto mínimo de un proyecto Terraform de Azure: fijar versiones, declarar el provider y el backend, y leer la suscripción con un data source. Sin esto, nada más funciona bien.

infra/versions.tf — versiones fijadas y provider
terraform {
  required_version = ">= 1.6.0"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"        # permite 4.x, evita un salto mayor sin revisar
    }
  }
}

provider "azurerm" {
  features {}                  # bloque obligatorio, aunque esté vacío
}

# Saber en qué suscripción y tenant trabajamos (sin escribirlos a mano).
data "azurerm_client_config" "current" {}
infra/backend.tf — el state, remoto
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstatecopiloto"
    container_name       = "tfstate"
    key                  = "copiloto.tfstate"   # un state por despliegue
  }
}

Tres decisiones que acabas de tomar:

  1. required_version y ~> 4.0: fijas la versión mayor del provider. Terraform avisa si el provider cambia de mayor; no te sorprende un apply con una API distinta.
  2. features {}: el provider azurerm exige este bloque aunque esté vacío (allí se configuran comportamientos concretos del ciclo de vida).
  3. data.azurerm_client_config: te da tenant_id y subscription_id sin hardcodearlos. Lo usarás en el Key Vault.

4 · Ejemplo real

El proyecto completo infra-cloud, pieza a pieza. Empieza por las variables y las etiquetas, que son el contrato del proyecto:

infra/variables.tf — el contrato de entrada
variable "location" {
  description = "Región de Azure"
  type        = string
  default     = "westeurope"
}

variable "environment" {
  description = "Entorno de despliegue"
  type        = string
  validation {                                 # evita typos que crean entornos fantasma
    condition     = contains(["dev", "prod"], var.environment)
    error_message = "environment debe ser 'dev' o 'prod'."
  }
}

variable "owner" {
  description = "Responsable del proyecto (para etiquetas de coste)"
  type        = string
}

variable "cost_center" {
  description = "Centro de coste al que se imputa el gasto"
  type        = string
}

variable "db_admin_password" {
  description = "Password del administrador de PostgreSQL"
  type        = string
  sensitive   = true
}
infra/main.tf — recursos, etiquetas y composición
# ---------------------------------------------------------- GRUPO Y ETIQUETAS
resource "azurerm_resource_group" "main" {
  name     = "rg-copiloto-${var.environment}"
  location = var.location
  tags     = local.tags
}

locals {
  # UN único punto de verdad de las etiquetas: si aparece una nueva,
  # se añade aquí y llega a TODOS los recursos a la vez.
  tags = {
    course      = "cloud"
    project     = "copiloto"
    environment = var.environment
    owner       = var.owner
    cost_center = var.cost_center
  }
}

# ------------------------------------------------------------------ RED
resource "azurerm_virtual_network" "vnet" {
  name                = "vnet-copiloto-${var.environment}"

  resource_group_name = azurerm_resource_group.main.name
  address_space       = ["10.20.0.0/16"]

}

resource "azurerm_subnet" "app" {
  name                 = "snet-app"
  resource_group_name  = azurerm_resource_group.main.name
  virtual_network_name = azurerm_virtual_network.vnet.name
  address_prefixes     = ["10.20.1.0/24"]
}

# --------------------------------------------------------------- REGISTRO
resource "azurerm_container_registry" "acr" {
  name                = "copilotoacr${var.environment}"   # sin guiones, único
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  sku                 = "Standard"
  admin_enabled       = false
  tags                = local.tags
}

# -------------------------------------------------- OBSERVABILIDAD (primero)
# El entorno de Container Apps necesita el workspace, así que este va antes.
resource "azurerm_log_analytics_workspace" "law" {

  location            = azurerm_resource_group.main.location
  sku                 = "PerGB2018"
  retention_in_days   = 30
  tags                = local.tags
}

# ---------------------------------------------------------------- CÓMPUTO
resource "azurerm_container_app_environment" "env" {
  name                       = "cae-copiloto-${var.environment}"
  resource_group_name        = azurerm_resource_group.main.name
  location                   = azurerm_resource_group.main.location
  infrastructure_subnet_id   = azurerm_subnet.app.id
  log_analytics_workspace_id = azurerm_log_analytics_workspace.law.id
  tags                       = local.tags
}

resource "azurerm_user_assigned_identity" "app" {
  name                = "id-copiloto-${var.environment}"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  tags                = local.tags
}

resource "azurerm_role_assignment" "acr_pull" {
  scope                = azurerm_container_registry.acr.id
  role_definition_name = "AcrPull"                     # solo lectura de imágenes
  principal_id         = azurerm_user_assigned_identity.app.principal_id
}

resource "azurerm_container_app" "api" {
  name                         = "copiloto-api"
  container_app_environment_id = azurerm_container_app_environment.env.id
  resource_group_name          = azurerm_resource_group.main.name
  revision_mode                = "Single"
  tags                         = local.tags

  identity {
    type         = "UserAssigned"
    identity_ids = [azurerm_user_assigned_identity.app.id]
  }

  registry {
    server   = azurerm_container_registry.acr.login_server
    identity = azurerm_user_assigned_identity.app.id
  }

  template {
    container {
      name   = "api"
      image  = "${azurerm_container_registry.acr.login_server}/copiloto-api:${var.image_tag}"
      cpu    = 0.5
      memory = "1Gi"

      # El secreto se inyecta como variable de entorno: la app lee DATABASE_URL.

        name        = "DATABASE_URL"
        secret_name = "database-url"
      }

    min_replicas = 1
    max_replicas = 5
  }

  secret {
    name  = "database-url"
    value = var.database_url          # variable sensible; valor solo en apply
  }

  ingress {
    external_enabled           = true
    target_port                = 8000
    allow_insecure_connections = false
  }
}

# ------------------------------------------------------------------- DATOS
resource "azurerm_private_dns_zone" "postgres" {
  name                = "private.postgres.database.azure.com"
  resource_group_name = azurerm_resource_group.main.name
  tags                = local.tags
}

resource "azurerm_postgresql_flexible_server" "db" {
  name                   = "psql-copiloto-${var.environment}"

  location               = azurerm_resource_group.main.location
  version                = "16"
  administrator_login    = "copiloto"
  administrator_password = var.db_admin_password
  storage_mb             = 32768
  sku_name               = "B_Standard_B1ms"
  backup_retention_days  = 7
  tags                   = local.tags
}

# ----------------------------------------------------------------- SECRETOS
resource "azurerm_key_vault" "kv" {
  name                       = "kv-copiloto-${var.environment}"
  resource_group_name        = azurerm_resource_group.main.name
  location                   = azurerm_resource_group.main.location
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  rbac_authorization_enabled = true
  purge_protection_enabled   = true
  tags                       = local.tags
}

Y el ciclo de trabajo de un día normal:

terminal — inicializar, planificar y aplicar
cd proyectos/infra-cloud

# init lee el backend y coloca los providers.
terraform init

# Valida sintaxis y coherencia interna (rápido, antes de tocar la nube).
terraform validate

# Plan: SIEMPRE con el archivo del entorno. El secreto llega del entorno, no del .tfvars.
export TF_VAR_db_admin_password="$DB_ADMIN_PASSWORD"
export TF_VAR_database_url="$DATABASE_URL"

terraform plan  -var-file=dev.tfvars -out=tfplan
terraform apply tfplan

terraform output copiloto_url
  • Un local.tags y nada más: las etiquetas se definen una vez y se esparcen por referencia. Añadir team = "x" es editar una línea, no treinta.
  • El nombre de cada recurso deriva de var.environment: el mismo código crea dev y prod. Nada de main-dev.tf y main-prod.tf.
  • El secreto entra por TF_VAR_* (variable de entorno): el valor de db_admin_password y database_url nunca aparece en un archivo del repositorio. El .tfvars solo lleva lo no sensible.
  • terraform validate antes de apply: detecta errores de tipo y de referencia en segundos, sin gastar dinero creando nada.

Truco de orden: en main.tf colocamos el workspace de Log Analytics antes del entorno de Container Apps porque el entorno lo referencia. Terraform resuelve el orden con el grafo de dependencias, pero agrupar los recursos por capa (grupo → red → observabilidad → cómputo → datos → secretos) hace el archivo legible y el plan fácil de revisar.

5 · Buenas prácticas

HazEvitaPor qué
Backend remoto con locking desde el primer día State local en el portátil o (peor) en git Un state local no se comparte y puede contener secretos; en git, se corrompe con cada conflicto
Fijar versiones (required_version, ~>) Dejar los providers «a la última» sin control Un salto de versión mayor puede cambiar la API de un recurso y romper el apply
Variables con validation para los valores críticos environment = "production" por error Un typo en el entorno crea un despliegue fantasma y una factura fantasma
Un local.tags único aplicado a todo Etiquetas copiadas a mano recurso a recurso Etiquetas coherentes = atribución de coste fiable y automatizable
Secretos como variables sensitive inyectadas en runtime Secretos en .tfvars versionados Regla del curso: nada de secretos en el repositorio, ni siquiera en un .tfvars
Sacar por output todo lo que otro sistema necesita Que el pipeline busque valores «a mano» con az ... show Todo como código: las salidas son el contrato con el CI/CD y con otros equipos
Formatear y validar antes de commitear Revisiones de PR llenas de cambios de sangría terraform fmt -check y validate en el pipeline detectan lo trivial automáticamente
Separar por entorno, no por tipo de recurso Un prod y un dev mezclados en la misma carpeta/state Cada entorno tiene su state: un destroy en dev no puede tocar prod

6 · Errores habituales

1. Dejar el state en el repositorio

Incorrecto — state local, versionado por accidente 
# ❌ Sin backend: terraform escribe terraform.tfstate en la carpeta del proyecto.
# git lo ve como un archivo más y, un commit despistado, lo sube al repositorio.
# Contiene valores sensibles y se corrompe en cuanto hay dos personas.
[sin bloque backend]
Correcto — backend remoto y un .gitignore a prueba de balas 
# ✅ El state vive en Blob Storage; el repo solo guarda código.
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstatecopiloto"
    container_name       = "tfstate"
    key                  = "copiloto.tfstate"
  }
}

# Y en el .gitignore del proyecto, por si acaso:
*.tfstate
*.tfstate.*
terraform.tfvars
*.auto.tfvars
.terraform/

2. Escribir el secreto en un .tfvars versionado

Incorrecto — la contraseña va en git 
# ❌ prod.tfvars — commit y a rezar. La contraseña queda en el historial para siempre.
db_admin_password = "Sup3rS3cret0!"
database_url      = "postgres://copiloto:Sup3rS3cret0!@psql.../copiloto"
Correcto — el valor entra por el entorno en apply 
# ✅ El .tfvars solo lleva lo NO sensible; los secretos llegan del entorno.
export TF_VAR_db_admin_password="$DB_ADMIN_PASSWORD"
export TF_VAR_database_url="$DATABASE_URL"
terraform apply -var-file=prod.tfvars

3. Un apply que toca el entorno equivocado

# ❌ Nadie pasó el -var-file: Terraform usa los defaults y crea/actualiza
# recursos sin el sufijo del entorno esperado. Aparecen «entornos fantasma».
terraform apply

# ✅ El archivo del entorno es obligatorio y el valor está validado.
terraform apply -var-file=prod.tfvars

La validation de environment en variables.tf evita el typo, pero la disciplina de pasar siempre -var-file evita el olvido. En el pipeline (lección 03) esto no depende de la memoria: el entorno fija el -var-file.

4. Recrear recursos que no debían recrearse

# ❌ Cambiar un atributo inmutable (como el nombre) fuerza destroy + create:
# la base de datos se borra y se vuelve a crear → pérdida de datos.
resource "azurerm_postgresql_flexible_server" "db" {
  name = "psql-copiloto-v2"     # ¡nombre nuevo = recurso nuevo!
}

# ✅ Mira el plan: si ves "must be replaced", PARA y decide.
#    Usa `terraform state mv` o `moved {}` para renombrar sin recrear.
moved {
  from = azurerm_postgresql_flexible_server.db[0]
  to   = azurerm_postgresql_flexible_server.db
}

Regla: nunca hagas apply sin leer el plan. La línea -/+ must be replaced sobre una base de datos es la diferencia entre un despliegue y un incidente.

7 · Ejercicio guiado

Objetivo: inicializar el proyecto con backend remoto, validarlo, generar un plan para dev y comprobar que no hay ningún secreto en los archivos versionados.

  1. Paso 1 — prepara el backend remoto (una vez). 
    az group create --name rg-tfstate --location westeurope
az storage account create \
  --name sttfstatecopiloto --resource-group rg-tfstate \
  --sku Standard_LRS --encryption-services blob
az storage container create --name tfstate --account-name sttfstatecopiloto
  2. Paso 2 — inicializa y valida. 
    cd proyectos/infra-cloud
terraform init
terraform fmt -check        # ¿está todo formateado?
terraform validate          # ¿hay errores de referencia o de tipo?
  3. Paso 3 — pasa los secretos por el entorno, no por archivos. 
    export TF_VAR_db_admin_password="$(openssl rand -base64 24)"
export TF_VAR_database_url="postgres://copiloto:${TF_VAR_db_admin_password}@psql-copiloto-dev.postgres.database.azure.com:5432/copiloto"
  4. Paso 4 — genera el plan de dev y revísalo. 
    terraform plan -var-file=dev.tfvars -out=tfplan
# Lee el resumen: cuántos recursos se añaden, cuántos se cambian y cuántos se destruyen.
# Esperado: ~12 recursos "to add", 0 "to change", 0 "to destroy" en el primer apply.
  5. Paso 5 — comprueba que no hay secretos versionados. 
    # Debe salir vacío: ninguna contraseña ni cadena de conexión en los archivos del repo.
grep -RInE "password|datABASE_URL.*://|secret" *.tf *.tfvars 2>/dev/null

# Y confirma que git ignora el state y los tfvars automáticos:
git status --porcelain | grep -E "tfstate|tfvars"
  6. Paso 6 — aplica el plan y lee la salida. 
    terraform apply tfplan
terraform output copiloto_url
terraform output health_url
  7. Paso 7 — limpia (solo dev). 
    terraform destroy -var-file=dev.tfvars
# El state se queda en el backend; el grupo de recursos se borra.

Resultado esperado: el proyecto se inicializa contra el backend remoto, validate pasa en limpio, el plan para dev es revisable y la búsqueda de secretos no encuentra nada. Has montado un Terraform repetible; en la lección 03 el mismo código se disparará desde GitHub Actions sin credenciales guardadas.

8 · Reto

🎯 Key Vault como única fuente de secretos

Hoy el secreto del Copiloto (database_url) entra como variable sensible de Terraform. Ese valor acaba en el state. El reto es sacar los secretos de Terraform: que el código cree el Key Vault, guarde el secreto ahí y que la Container App lo lea directamente de Key Vault con su identidad gestionada, de forma que el valor nunca transite por el state de Terraform.

Requisitos del reto: (1) el secreto se guarda en Key Vault (por az o por un recurso de Terraform, tú decides el equilibrio); (2) la identidad de la app recibe solo el rol Key Vault Secrets User sobre ese Key Vault concreto; (3) la Container App referencia el secreto desde Key Vault y no como secret plano; y (4) documentas en el código qué secreto sigue «viviendo» en el state y por qué es aceptable o cómo evitarlo del todo.

Pista: mira el módulo 2 (02-secretos). Container Apps permite declarar un secret cuyo valor es la versionless_id de un secreto de Key Vault, y la app lo lee con su identidad. La pregunta fina —la que separa un junior de un senior— es quién pone el valor en Key Vault y si ese «quién» vuelve a arrastrar un secreto consigo.

9 · Resumen

  • Terraform lee toda la carpeta .tf: organízala por responsabilidad (versions, backend, variables, main, outputs).
  • El state es el inventario: siempre en backend remoto con locking, nunca en git.
  • Variables + .tfvars + locals = una sola base de código para dev y prod; los nombres derivan del entorno.
  • Los secretos se declaran sensitive y llegan por el entorno (TF_VAR_*) o desde Key Vault; nunca en un archivo versionado.
  • local.tags único aplicado a todos los recursos: atribución de coste desde el minuto uno.
  • outputs como contrato con el CI/CD (URL, health, servidor del registro).
  • Lee siempre el plan: must be replaced sobre datos es un incidente, no una actualización.

10 · Preguntas frecuentes

¿Terraform u OpenTofu? ¿Cambia algo de lo que he escrito?

OpenTofu es el fork abierto de Terraform y usa la misma sintaxis HCL y los mismos providers, así que todo el código de esta lección funciona igual. Cambia el binario (tofu en vez de terraform) y algunos detalles del registro de providers. Para el curso usamos terraform; si tu organización migró a OpenTofu, el 95 % del trabajo es idéntico y solo cambian comandos puntuales.

¿Puedo tener varios .tfstate para el mismo proyecto?

Sí, y a menudo conviene. La regla es un state por entorno (dev y prod separados: un error en dev no puede tocar prod). Si el proyecto crece mucho, puedes separar también por «ciclo de vida» (por ejemplo, red compartida frente a aplicaciones). Lo que no se hace es tener el mismo entorno repartido en varios states sin querer: acabarías con recursos que se crean dos veces o que se destruyen por sorpresa.

¿Cómo evito escribir la contraseña a mano en cada apply?

No la escribes: la exportas una vez en el entorno (export TF_VAR_db_admin_password=...) o —mejor— dejas que el pipeline la inyecte desde su secrets store en la lección 03. La clave es no teclearla en un archivo. Si te ves copiándola a un .tfvars «solo por comodidad», ese es justo el momento en que se convierte en una fuga.

¿Cuándo uso count/for_each y cuándo recursos repetidos a mano?

Cuando el número de recursos es dinámico o depende de una lista de configuración, usa for_each (casi siempre preferible a count, porque las claves no se reordenan al quitar un elemento). Para 3–4 recursos fijos y distintos entre sí, escribirlos a mano es más legible. No conviertas el Terraform en un lenguaje de programación: si necesitas mucha lógica, probablemente quieras un módulo.

¿Debería envolver todo esto en un módulo reutilizable?

Cuando vayas a desplegar el mismo patrón varias veces (por ejemplo, un entorno por cliente o por equipo). Un módulo encapsula el conjunto «red + cómputo + datos + secretos» y expone variables y outputs, para que crear un entorno nuevo sea una llamada de veinte líneas. Para el proyecto del curso, un solo despliegue no necesita módulo; pero saber cuándo extraerlo es parte del criterio senior.
