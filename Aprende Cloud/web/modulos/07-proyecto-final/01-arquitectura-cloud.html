Arquitectura en la nube

Módulo 7 · Proyecto final: Copiloto en la nube 🕐 45 minutos

1 · Introducción

Has recorrido el curso entero pieza a pieza: la red (módulo 1), la identidad y los secretos (módulo 2), los datos (módulo 3), los contenedores gestionados (módulo 4), el serverless (módulo 5) y la operación (módulo 6). Ahora toca lo más parecido al trabajo real: dibujar la arquitectura completa del Copiloto y justificar cada decisión antes de escribir una línea de Terraform.

Una arquitectura no es una lista de servicios bonitos. Es la respuesta razonada a cinco preguntas:

  1. ¿Qué cómputo ejecuta el código? La Copiloto API, un contenedor. ¿Gestionamos un clúster o no?
  2. ¿Dónde viven los datos? PostgreSQL para lo relacional, Blob para lo que no lo es.
  3. ¿Cómo se autentica todo entre sí? Identidades gestionadas y OIDC, nunca claves de larga vida.
  4. ¿Dónde están los secretos? En Key Vault, no en el repositorio ni en la imagen.
  5. ¿Cómo nos enteramos de qué pasa? Logs, métricas y trazas en Azure Monitor.

¿Por qué existe esta lección? Porque escribir Terraform sin una arquitectura es dibujar un plano a la vez que levantas las paredes. Esta lección fija el plano: el mismo que en las lecciones 02, 03 y 04 se convertirá en HCL, se desplegará con CI/CD y se observará en producción. Y —igual de importante— fija también la alternativa AWS, porque un ingeniero de cloud elige con criterio, no por dogma.

2 · Teoría

La nube como un edificio con plantas

Para no perderte entre nombres, piensa en la nube como un edificio. La región es la ciudad; las zonas de disponibilidad son naves distintas del mismo recinto (si una se inunda, la otra sigue); la VNet es el edificio; cada subred es una planta con su normativa; y cada recurso es una habitación con un candado (grupo de seguridad) y un portero (identidad). Todo lo que construyamos vive dentro de esa jerarquía:

  Región (westeurope)
  └── Grupo de recursos (rg-copiloto-prod)   <-- unidad de coste, permisos y borrado
      └── VNet 10.20.0.0/16
          ├── Subred app       10.20.1.0/24   <-- Container Apps se integra aquí
          ├── Subred datos     10.20.2.0/24   <-- PostgreSQL (delegada)
          └── Subred privada   10.20.3.0/24   <-- endpoints privados (ACR, KV, Blob)
      └── Recursos PaaS con nombre propio: ACR, Key Vault, Log Analytics, Monitor

Analogía del conserje: la identidad gestionada es un conserje del edificio con una tarjeta que abre solo su habitación. No lleva las llaves de todo el edificio encima ni las pierde por la calle: cuando necesita entrar, el propio edificio le emite un pase temporal. Por eso preferimos identidades a contraseñas: una contraseña es una llave física que se copia, se pierde y no se rota sola.

Las cinco capas de la arquitectura del Copiloto

Esta es la arquitectura objetivo. Cada caja la has conocido en un módulo anterior; aquí se ensamblan:

Léelo capa a capa:

CapaServicio AzureDecisión y por qué
Red VNet + subredes + endpoints privados Los recursos PaaS no se exponen a Internet: se alcanzan por la red privada. Exposición mínima = superficie de ataque mínima.
Cómputo Container Apps + ACR Contenedor gestionado sin clúster: escalado a cero, TLS gestionado, revisiones. No necesitamos Kubernetes (módulo 4).
Datos PostgreSQL Flexible Server + Blob Storage PostgreSQL gestionado para lo relacional; Blob para documentos/adjuntos. Backups automáticos y zona redundante.
Identidad Entra ID + identidades gestionadas Cada componente tiene su propia identidad con el rol mínimo (AcrPull, secrets read). Sin claves compartidas.
Secretos Azure Key Vault La cadena de conexión y demás secretos viven aquí; la app los lee con su identidad. Nada en el repo.
Observabilidad Log Analytics + Azure Monitor (+ App Insights) Sin telemetría no hay operación: logs, métricas, trazas y alertas, todo en un mismo sitio.

El coste es una capa transversal, no un módulo aparte. Todas las cajas llevan tags (curso, entorno, propietario, centro de coste) y el conjunto entero tiene un presupuesto con alertas (lección 04). Sin etiquetas no puedes atribuir gasto; sin límites, el proyecto final se convierte en una sorpresa de facturación.

Las decisiones, una a una (y qué elegiría un equipo senior)

Una arquitectura se juzga por sus decisiones, no por el catálogo. Estas son las tres que más discuten los equipos:

DecisiónElegimos…Descartamos…Por qué
Cómputo Container Apps A App Service o a AKS Ya tenemos el contenedor; Container Apps da HTTPS, escalado y revisiones sin operar un clúster. AKS es potencia que no vamos a necesitar (y se paga aunque esté parado).
Base de datos PostgreSQL Flexible Server SQL Server o una VM con Postgres Es el motor que ya usa el Copiloto; gestionado significa backups, parches y alta disponibilidad sin que los hagamos nosotros.
Exposición de la BD Subred delegada + endpoint privado Regla de firewall «allow 0.0.0.0/0» El error más grave en producción: una base de datos en Internet. La BD solo escucha dentro de la VNet.

¿Y el serverless (módulo 5)? Bien planteado: la Copiloto API es un servicio con estado de conexión a base de datos y tráfico continuo, así que un contenedor caliente encaja mejor que una función con cold start. Reservaríamos Functions para tareas puntuales (por ejemplo, consumir una cola de eventos en segundo plano), no para el servicio principal. Esa es la elección informada que pide la lección 04-cuando-serverless.

La misma arquitectura en AWS

El discurso del curso es provider-neutral: cambian los nombres, no las ideas. Este es el mapa mental que debes poder recitar de memoria:

ConceptoAzureAWS
Red aisladaVNetVPC
SubredesSubnets (+ delegación)Subnets (+ route tables)
Registro de imágenesAzure Container Registry (ACR)Elastic Container Registry (ECR)
Cómputo sin clústerContainer AppsApp Runner (o ECS Fargate)
Base de datos relacionalAzure Database for PostgreSQLRDS for PostgreSQL / Aurora
SecretosAzure Key VaultAWS Secrets Manager
IdentidadEntra ID + identidad gestionadaIAM Roles (+ IRSA / task role)
ObservabilidadAzure Monitor + Log AnalyticsCloudWatch
SDK/CLIaz + provider azurermaws + provider aws

Por qué insistimos en las dos: las diferencias reales están en los detalles (App Runner no tiene el modelo de revisiones con pesos de Container Apps; Secrets Manager cobra por secreto y rotación, Key Vault por operación). Conocer ambas evita el «en Azure esto es imposible» — casi nunca lo es, solo se llama distinto.

3 · Ejemplo mínimo

Antes de la arquitectura completa, el esqueleto de red: una VNet y las subredes donde luego encajarán los recursos. Es lo primero que se escribe de cualquier arquitectura, porque todo lo demás cuelga de aquí.

infra/red-minima.tf — la VNet y sus subredes
variable "location" {
  type    = string
  default = "westeurope"
}

# El edificio: la red virtual. El rango 10.20.0.0/16 da 65 536 direcciones,
# de sobra para repartir en subredes pequeñas y no solaparse con otras VNets.
resource "azurerm_virtual_network" "vnet" {
  name                = "vnet-copiloto"
  location            = var.location
  resource_group_name = var.resource_group_name
  address_space       = ["10.20.0.0/16"]
}

# Planta de la app: aquí se integra el entorno de Container Apps.
resource "azurerm_subnet" "app" {
  name                 = "snet-app"
  resource_group_name  = var.resource_group_name
  virtual_network_name = azurerm_virtual_network.vnet.name
  address_prefixes     = ["10.20.1.0/24"]
}

Dos líneas que importan:

  • address_space planificado. Se elige antes de crear recursos: cambiar el rango de una VNet en uso es caro. Reserva espacio para crecer (subredes de datos, de endpoints, de integración).
  • Subred por propósito. No metemos todo en una sola subred. La subred de datos se delega a PostgreSQL y la de endpoints privados alojará los private endpoint. Separarlas es lo que permite aplicar reglas de red distintas a cada cosa.

4 · Ejemplo real

La arquitectura completa del Copiloto, escrita como el inventario de recursos del proyecto infra-cloud. No es aún el Terraform completo (eso es la lección 02): es el plano con los recursos, sus etiquetas de coste y las conexiones entre ellos.

infra/main.tf — inventario de la arquitectura (extracto)
# Etiquetas comunes a TODOS los recursos: coste rastreable desde el minuto uno.
locals {
  tags = {
    course      = "cloud"
    project     = "copiloto"
    environment = var.environment        # dev | prod
    owner       = var.owner              # responsable
    cost_center = var.cost_center        # centro de coste
  }
}

# ---------------------------------------------------------------- RED
resource "azurerm_virtual_network" "vnet" {
  name                = "vnet-copiloto-${var.environment}"
  address_space       = ["10.20.0.0/16"]
  location            = var.location
  resource_group_name = azurerm_resource_group.main.name
  tags                = local.tags
}

resource "azurerm_subnet" "app" {
  name                 = "snet-app"       # integración de Container Apps
  resource_group_name  = azurerm_resource_group.main.name
  virtual_network_name = azurerm_virtual_network.vnet.name
  address_prefixes     = ["10.20.1.0/24"]
}

resource "azurerm_subnet" "data" {
  name                 = "snet-data"      # delegada a PostgreSQL
  resource_group_name  = azurerm_resource_group.main.name
  virtual_network_name = azurerm_virtual_network.vnet.name
  address_prefixes     = ["10.20.2.0/24"]

  delegation {
    name = "postgres"
    service_delegation {
      name = "Microsoft.DBforPostgreSQL/flexibleServers"
    }
  }
}

resource "azurerm_subnet" "private" {
  name                 = "snet-private"   # endpoints privados (ACR, KV, Storage)
  resource_group_name  = azurerm_resource_group.main.name
  virtual_network_name = azurerm_virtual_network.vnet.name
  address_prefixes     = ["10.20.3.0/24"]
}

# ---------------------------------------------------------------- REGISTRO
resource "azurerm_container_registry" "acr" {
  name                = "copilotoacr${var.environment}"  # único, sin guiones
  resource_group_name = azurerm_resource_group.main.name
  location            = var.location
  sku                 = "Standard"
  admin_enabled       = false                            # identidad, no admin
  tags                = local.tags
}

# ---------------------------------------------------------------- CÓMPUTO
resource "azurerm_container_app_environment" "env" {
  name                       = "cae-copiloto-${var.environment}"
  resource_group_name        = azurerm_resource_group.main.name
  location                   = var.location
  infrastructure_subnet_id   = azurerm_subnet.app.id     # entra en la VNet
  log_analytics_workspace_id = azurerm_log_analytics_workspace.law.id
  tags                       = local.tags
}

resource "azurerm_container_app" "api" {
  name                         = "copiloto-api"
  container_app_environment_id = azurerm_container_app_environment.env.id
  resource_group_name          = azurerm_resource_group.main.name
  revision_mode                = "Single"
  tags                         = local.tags
  # ... template, ingress, probes e identidad (ver módulo 4 y lección 02)
}

# ---------------------------------------------------------------- DATOS
resource "azurerm_postgresql_flexible_server" "db" {
  name                   = "psql-copiloto-${var.environment}"
  resource_group_name    = azurerm_resource_group.main.name
  location               = var.location
  version                = "16"
  zone                   = "1"            # zona primaria; la HA cubre el failover
  delegated_subnet_id    = azurerm_subnet.data.id
  private_dns_zone_id    = azurerm_private_dns_zone.postgres.id
  administrator_login    = "copiloto"
  administrator_password = var.db_admin_password   # variable SENSIBLE, en apply
  storage_mb             = 32768
  sku_name               = "B_Standard_B1ms"       # barato para el laboratorio
  backup_retention_days  = 7
  tags                   = local.tags
}

resource "azurerm_storage_account" "blob" {
  name                     = "stcopiloto${var.environment}001"
  resource_group_name      = azurerm_resource_group.main.name
  location                 = var.location
  account_tier             = "Standard"
  account_replication_type = "LRS"        # laboratorio; GRS en producción seria
  min_tls_version          = "TLS1_2"
  tags                     = local.tags
}

# ---------------------------------------------------------------- SECRETOS
resource "azurerm_key_vault" "kv" {
  name                       = "kv-copiloto-${var.environment}"
  resource_group_name        = azurerm_resource_group.main.name
  location                   = var.location
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  rbac_authorization_enabled = true       # RBAC, no access policies
  purge_protection_enabled   = true
  tags                       = local.tags
}

# ---------------------------------------------------------------- OBSERVABILIDAD
resource "azurerm_log_analytics_workspace" "law" {
  name                = "log-copiloto-${var.environment}"
  resource_group_name = azurerm_resource_group.main.name
  location            = var.location
  sku                 = "PerGB2018"
  retention_in_days   = 30
  tags                = local.tags
}

Qué acabas de dibujar, en orden de dependencias:

  • Red primero: VNet y subredes. La subred data se delega a PostgreSQL, y la private alojará los endpoints privados. Sin esto, la base de datos tendría que exponerse a Internet.
  • Registro con admin_enabled = false: obliga a la identidad gestionada (módulo 4). El nombre del ACR no admite guiones y debe ser único globalmente.
  • Entorno de Container Apps atado a la VNet y al workspace: infrastructure_subnet_id lo mete en la red privada y log_analytics_workspace_id hace que todo lo que ocurra aquí aparezca en Azure Monitor.
  • PostgreSQL con subred delegada y DNS privado: la base solo habla dentro de la VNet. La contraseña del administrador entra como variable sensible en el apply, nunca en el archivo.
  • Key Vault con RBAC y purge protection: control de acceso por roles y protección frente a borrados accidentales. El Copiloto leerá de aquí sus secretos con su identidad.
  • Todo etiquetado: tags = local.tags en cada recurso. Es lo que hace posible, en la lección 04, filtrar el gasto por entorno y proyecto.

Orden de trabajo: primero el grafo de dependencias (red → datos/secretos → cómputo), luego el código. Terraform deduce el orden de las referencias (azurerm_subnet.app.id implica que la subred existe antes), pero tú debes tenerlo claro en la cabeza para no crear dependencias circulares.

5 · Buenas prácticas

HazEvitaPor qué
Diseñar la red y el rango de direcciones antes de crear recursos Cambiar el CIDR de una VNet en uso Recrear red = recrear todo lo que cuelga de ella; es una de las operaciones más caras
Una subred por propósito (app, datos, endpoints) Meter todo en la subred por defecto Permite reglas y delegaciones distintas; aísla el impacto de cada componente
Etiquetar todos los recursos con local.tags Recursos sin owner/environment Sin etiquetas no hay atribución de gasto ni autopsia posible de un recurso huérfano
Identidad gestionada por componente y rol mínimo Una identidad «compartida» con muchos permisos El fallo se contiene: si una identidad se filtra, solo abre su puerta
Recursos PaaS con endpoint privado «Firewall abierto para probar» Un PaaS en Internet es la causa nº1 de fugas de datos
Zona redundante en la base de datos de producción Una sola instancia sin HA El failover automático convierte una caída de zona en un pequeño bache, no en un desastre
Observabilidad desde el diseño (observability by design) Añadir monitorización «cuando falle» Si no existían métricas antes del incidente, no tienes línea base ni historia que investigar

6 · Errores habituales

1. Exponer la base de datos a Internet «solo para conectarse»

Incorrecto — firewall abierto al mundo 
# ❌ Cualquier IP de Internet puede intentar autenticarse contra PostgreSQL.
resource "azurerm_postgresql_flexible_server_firewall_rule" "open" {
  name             = "allow-all"
  server_id        = azurerm_postgresql_flexible_server.db.id
  start_ip_address = "0.0.0.0"
  end_ip_address   = "255.255.255.255"
}
Correcto — subred delegada, sin endpoint público 
# ✅ La base vive dentro de la VNet: solo la alcanza quien está en la red.
resource "azurerm_postgresql_flexible_server" "db" {
  # ...
  delegated_subnet_id = azurerm_subnet.data.id
  private_dns_zone_id = azurerm_private_dns_zone.postgres.id
  public_network_access_enabled = false   # sin IP pública
}

Con public_network_access_enabled = false y la subred delegada, la base de datos deja de tener una puerta a Internet. El acceso desde tu portátil, si lo necesitas, se hace por VPN o por un jump host dentro de la VNet, no abriendo el firewall a todo el planeta.

2. Una única identidad gestionada para todos los componentes

Incorrecto — identidad compartida y sobredimensionada 
# ❌ La app, el pipeline y los jobs usan la MISMA identidad con muchos roles.
# Un permiso de más en cualquier sitio es un permiso de más en todas partes.
resource "azurerm_role_assignment" "todo" {
  principal_id         = azurerm_user_assigned_identity.comun.principal_id
  role_definition_name = "Contributor"     # demasiado
  scope                = azurerm_resource_group.main.id
}
Correcto — identidad por componente y rol mínimo 
# ✅ La identidad de la app solo puede LEER imágenes del registro.
resource "azurerm_role_assignment" "app_acr_pull" {
  principal_id         = azurerm_user_assigned_identity.app.principal_id
  role_definition_name = "AcrPull"          # solo lectura, solo del ACR
  scope                = azurerm_container_registry.acr.id
}

Regla del curso: cada componente tiene su identidad y su rol mínimo sobre el recurso exacto. El alcance no es «todo el grupo de recursos» si solo hace falta un registro.

3. Arquitectura sin etiquetas ni límite de gasto

# ❌ Recursos sueltos, sin etiquetas: la factura llega y nadie sabe de quién es.
resource "azurerm_container_app" "api" {
  name = "copiloto-api"
  # ... sin tags, sin budget, sin alertas
}

# ✅ Todo etiquetado con un local común, y un presupuesto con alertas (lección 04).
resource "azurerm_container_app" "api" {
  name = "copiloto-api"
  tags = local.tags
}

Sin las etiquetas project, environment y cost_center no puedes responder «¿cuánto cuesta el entorno de dev?» ni «¿quién es el dueño de este recurso?». El presupuesto sin etiquetas es una alarma sin dirección.

4. Escalar en horizontal sin techo, en la arquitectura

# ❌ max_replicas enorme: una subida de tráfico puede multiplicar la factura.
template {
  max_replicas = 1000
}

# ✅ Techo acorde al presupuesto, con alerta cuando se acerca.
template {
  min_replicas = 1     # sin cold start
  max_replicas = 5     # techo de coste y de protección
}

El escalado automático (módulo 4) es una promesa: «si hace falta, gasto más». La arquitectura debe decidir cuánto más. Un max_replicas sin techo razonable es una factura sin techo razonable.

7 · Ejercicio guiado

Objetivo: materializar el plano en la nube y verificarlo con la CLI. Vamos a crear la red de la arquitectura y explorarla como lo haría un ingeniero antes de añadir los recursos PaaS.

  1. Paso 1 — crea el grupo de recursos con sus etiquetas. 
    az group create \
  --name rg-copiloto-dev \
  --location westeurope \
  --tags course=cloud project=copiloto environment=dev owner=tu-nombre cost_center=formacion
  2. Paso 2 — crea la VNet y las tres subredes del plano. 
    az network vnet create \
  --resource-group rg-copiloto-dev --name vnet-copiloto-dev \
  --address-prefixes 10.20.0.0/16 \
  --subnet-name snet-app --subnet-prefixes 10.20.1.0/24

az network vnet subnet create \
  --resource-group rg-copiloto-dev --vnet-name vnet-copiloto-dev \
  --name snet-private --address-prefixes 10.20.3.0/24

# La subred de datos se crea aparte porque va DELEGADA a PostgreSQL:
az network vnet subnet create \
  --resource-group rg-copiloto-dev --vnet-name vnet-copiloto-dev \
  --name snet-data --address-prefixes 10.20.2.0/24 \
  --delegations Microsoft.DBforPostgreSQL/flexibleServers
  3. Paso 3 — comprueba que la delegación quedó aplicada. 
    az network vnet subnet show \
  --resource-group rg-copiloto-dev --vnet-name vnet-copiloto-dev \
  --name snet-data \
  --query "{nombre:name, prefijo:addressPrefix, delegacion:delegations[0].serviceName}" \
  --output table
# Esperado: delegacion = Microsoft.DBforPostgreSQL/flexibleServers
  4. Paso 4 — reserva el DNS privado para PostgreSQL. Sin zona privada, el nombre de la base no resuelve dentro de la VNet: 
    az network private-dns zone create \
  --resource-group rg-copiloto-dev \
  --name "private.postgres.database.azure.com"

az network private-dns link vnet create \
  --resource-group rg-copiloto-dev --zone-name "private.postgres.database.azure.com" \
  --name link-vnet --virtual-network vnet-copiloto-dev --registration-enabled false
  5. Paso 5 (verificación) — recorre la jerarquía de arriba abajo. Comprueba que el edificio tiene las plantas que diseñaste: 
    az network vnet subnet list \
  --resource-group rg-copiloto-dev --vnet-name vnet-copiloto-dev \
  --query "[].{subred:name, prefijo:addressPrefix}" --output table
# Esperado: snet-app, snet-data y snet-private con sus prefijos 10.20.x.0/24.
  6. Paso 6 — limpia. El grupo entero se va, y con él la VNet y el DNS privado: 
    az group delete --name rg-copiloto-dev --yes --no-wait

Resultado esperado: una VNet 10.20.0.0/16 con tres subredes (snet-app, snet-data delegada a PostgreSQL, snet-private) y una zona DNS privada enlazada. Tienes el plano de la arquitectura en pie y verificable, listo para que la lección 02 lo escriba entero en Terraform.

8 · Reto

🎯 El Copiloto sobrevive a la caída de una región

Rediseña la arquitectura para que el Copiloto siga sirviendo aunque una región entera de Azure se caiga. Debes elegir y justificar un modelo: activo-pasivo (una región caliente y otra en espera, con conmutación manual o automática) o activo-activo (las dos regiones sirviendo tráfico a la vez).

Como mínimo, tu diseño debe resolver: (1) dónde vive la base de datos y cómo se replica entre regiones; (2) dónde viven los secretos y si se replican; (3) cómo llega el tráfico del usuario a la región sana; (4) cuál es el RTO (tiempo máximo de caída) y el RPO (cuántos datos puedes perder) que ofreces, y (5) cuánto cuesta esa resiliencia de más, comparado con la arquitectura de una sola región.

Pista: piensa en el módulo 6 (04-alta-disponibilidad-y-dr). La base de datos gestionada suele ofrecer réplicas de lectura entre regiones y restauración geográfica; Azure Front Door o Traffic Manager reparten el tráfico entre regiones; y Key Vault puede replicarse. La clave del reto no es «duplicar todo», sino elegir el punto del compromiso coste/resiliencia que pida el negocio y saber defenderlo.

9 · Resumen

  • La arquitectura del Copiloto tiene cinco capas: red, cómputo, datos, identidad/secretos y observabilidad; el coste es transversal (etiquetas + presupuesto).
  • Red primero: VNet, una subred por propósito, datos delegados a PostgreSQL y endpoints privados para los PaaS.
  • Cómputo: Container Apps + ACR por identidad gestionada (AcrPull), sin clúster que operar.
  • Datos: PostgreSQL Flexible Server privado y con HA; Blob para lo no relacional.
  • Secretos: Key Vault con RBAC; la app los lee con su identidad, nunca desde el repositorio.
  • Observabilidad: todo emite a Log Analytics/Azure Monitor; se diseña antes del incidente, no después.
  • La misma arquitectura en AWS cambia de nombres, no de ideas.

10 · Preguntas frecuentes

¿Por qué Container Apps y no directamente AKS?

Porque AKS es un clúster que tú operas (o al menos pagas) aunque no lo uses: nodos, actualizaciones, ingress, certificados. Container Apps te da lo que necesitas —contenedor, HTTPS, escalado y revisiones— sin clúster. La regla es sencilla: usa Container Apps salvo que necesites control fino de Kubernetes (CRDs, operadores, red avanzada). En ese caso, AKS, pero sabiendo que no es gratis en operación.

¿Necesito realmente una VNet para un proyecto pequeño?

Para el laboratorio, no: Container Apps y PostgreSQL pueden funcionar con exposición pública. Pero el objetivo de la arquitectura final es reflejar producción, y en producción la base de datos no se expone a Internet. Diseñar la VNet ahora te obliga a elegir los rangos de direcciones antes de tener recursos —que es exactamente cuando es barato— y te ahorra una migración dolorosa después.

¿Dónde debería ir la lógica de llamada al LLM del Copiloto?

Dentro de la Copiloto API, en el contenedor. La llamada al modelo es lógica de aplicación con estado (prompts, contexto, límites de tokens), no un servicio de infraestructura aparte. Si en algún momento alguna tarea es lenta y puntual (resumir un documento largo), esa sí puede ir a una función serverless que consuma de una cola, pero el camino principal se queda en la API.

¿Cuándo separo la arquitectura en varios grupos de recursos?

Cuando tengan ciclos de vida o permisos distintos. Un patrón habitual: un grupo por entorno (rg-copiloto-dev, rg-copiloto-prod) y, dentro, todo el entorno junto. Separar «red» y «app» solo tiene sentido si equipos distintos los gestionan o si la red se comparte entre aplicaciones. Para un solo Copiloto, un grupo por entorno es lo más simple y lo que mejor casa con los presupuestos y el control de coste.

¿La arquitectura en AWS sería mucho más barata o más cara?

Depende del uso, y la respuesta honesta es «hay que medirlo». Los servicios equivalentes (App Runner/ECS, RDS, Secrets Manager, CloudWatch) tienen modelos de precio distintos: App Runner cobra por vCPU/memoria de instancia aprovisionada, Secrets Manager cobra por secreto y rotación mientras Key Vault cobra por operación, etc. Lo importante no es memorizar precios, sino saber qué partida genera el gasto en cada modelo para optimizarla. Eso lo trabajamos en la lección 04.
