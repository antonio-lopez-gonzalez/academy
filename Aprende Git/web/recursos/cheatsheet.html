Cheatsheet de Git

Referencia rápida 🧭 por intención · comandos canónicos (Git 2.23+)

El mapa antes de los comandos

Esta chuleta está ordenada por lo que quieres conseguir, no por orden alfabético de comandos. Para elegir bien solo hay que recordar el modelo: Git guarda commits inmutables y cada comando mueve uno de tres punteros. Antes de teclear, pregúntate qué puntero estoy moviendo.

los tres estados — qué toca cada comando
working tree ──git add──▶ index ──git commit──▶ commit (la rama y HEAD avanzan)
     ▲                      │
     └── git restore ───────┘        sobrescribe el fichero con lo indexado
                            │
                            └── git restore --staged ──▶ vuelve a HEAD

# HEAD    → puntero a la rama actual (o a un commit, en detached HEAD)
# rama    → ref móvil que apunta a un commit; se mueve al commitear
# índice  → el árbol del PRÓXIMO commit; no es una carpeta de borradores
Si buscas…Qué cambiaComando
Mover un cambio al índiceÍndicegit add <archivo>
Crear un commitHEAD y la ramagit commit
Cambiar de ramaHEAD y el working treegit switch <rama>
Descartar un ficheroSolo el working treegit restore <archivo>
Mover la rama hacia atrásRama, HEAD e índice (según flag)git reset

Por qué importa: casi todos los «desastres» de Git son un puntero movido sin querer, no datos perdidos. Los commits siguen en la base de objetos y el reflog los recuerda; lo único que no se recupera es lo que nunca llegó a un commit. Ver Los tres estados.

Quiero ver el estado y el historial

Antes de tocar nada, mira. git status responde «¿dónde estoy y qué tengo sin guardar?»; git log, «¿cómo he llegado hasta aquí?». Acostúmbrate a la versión corta con upstream, que es la que se lee de un vistazo.

git status -sb                     # rama, upstream y ficheros en dos columnas
git status                         # versión larga, con instrucciones de qué hacer
git diff                           # working tree vs índice (lo que NO has staged)
git diff --staged                  # índice vs HEAD (lo que entraría en el commit)
git diff HEAD                      # working tree vs HEAD (staged + unstaged)
git diff --stat                    # resumen por fichero, sin el diff entero
git log --oneline --graph --decorate --all -n 20
git show --stat HEAD               # metadatos + resumen del último commit
git branch -vv                     # ramas locales, su commit y su upstream
git remote -v                      # remotos y URLs
git config --list --show-origin    # de qué fichero sale cada valor
Quiero ver…Comando
Los ficheros de un commitgit show --name-only <sha>
Qué cambió entre dos ramas (desde su ancestro común)git diff main...feature
Qué commits tengo sin publicargit log --oneline @{u}..HEAD
Qué trae el remoto que aún no tengogit fetch y luego git log --oneline HEAD..@{u}
Quién movió una rama y cuándogit reflog show <rama>
El historial de un solo ficherogit log --oneline -- <archivo>

Lee git status, no lo ignores. Git te dice literalmente el comando que resuelve el estado en el que estás: «use git restore to discard…», «use git add to mark…». Es documentación contextual gratis (diff y el índice).

Quiero crear y navegar commits

Crear el commit

git add notas.md                 # todo el fichero al índice
git add -p                       # revisar por hunks: y = sí, n = no, s = partir
git add -u                       # solo ficheros ya trackeados (sin nuevos)
git commit -m "feat(notas): añadir búsqueda"
git commit -v                    # muestra el diff dentro del editor del mensaje
git commit --amend --no-edit     # reescribe el último commit SIN cambiar mensaje
git commit --amend -m "feat(notas): buscar por título"

--amend no «edita» el commit: crea otro con distinto hash y mueve la rama. Es seguro si el commit no está publicado; si ya lo empujaste, obliga a un force push que rompe a quien lo tenga. Ver Commits atómicos.

Navegar sin miedo

git switch main                  # cambiar de rama (moderno; checkout es lo antiguo)
git switch -                     # volver a la rama anterior
git switch --detach v1.0.0       # HEAD a un commit/tag, sin rama (detached HEAD)
git restore --source=HEAD~2 notas.md   # traer una versión antigua al working tree
git show HEAD~2:notas.md         # verla sin tocar el fichero (mejor para curiosear)
git log --oneline -- notas.md    # historia de ese fichero
git log -p -- notas.md           # historia con los diffs

HEAD~1 es «el primer padre del commit actual» y HEAD~2, «el padre del padre». HEAD^ es sinónimo de HEAD~1; HEAD^2 solo tiene sentido en un merge y apunta al segundo padre.

En detached HEAD puedes mirar, compilar y probar, pero un commit nuevo no pertenece a ninguna rama. Si quieres conservarlo: git switch -c experimento antes de cambiar de rama (Ramas y HEAD).

Quiero deshacer algo

No hay un «undo» único porque hay cuatro preguntas distintas: ¿descarto un fichero?, ¿muevo mi rama?, ¿invierto algo ya publicado?, ¿aparto el trabajo a medias? Elige por pregunta, no por costumbre.

# 1) Cambios que aún no son commit
git restore notas.md              # descarta el cambio del working tree (irreversible)
git restore --staged notas.md     # lo saca del índice; el cambio sigue en el fichero
git restore --source=HEAD --staged --worktree notas.md   # las dos cosas

# 2) Commits locales: mover la rama
git reset --soft HEAD~1           # deshacer el commit conservando todo staged
git reset HEAD~1                  # --mixed: desindexa y conserva los cambios
git reset --hard HEAD~1           # borra índice y working tree (peligroso)

# 3) Commits publicados: invertir sin reescribir
git revert <sha>                  # nuevo commit que deshace <sha>
git revert --no-commit <sha>      # preparar varios y commitear una sola vez
git revert -m 1 <merge-sha>       # revertir un merge: conserva el primer padre

# 4) Trabajo a medias: aparcarlo
git stash push -u -m "wip: búsqueda"   # -u incluye ficheros sin trackear
git stash list
git stash pop                     # aplica y elimina el último (apply + drop)
git stash apply stash@{1}         # aplica sin borrar
git stash drop stash@{0}
git stash branch wip-busqueda     # crea rama desde el commit donde hiciste stash

reset --soft / --mixed / --hard

Los tres mueven HEAD y la rama actual; la diferencia es hasta dónde arrastran el índice y el working tree.

FlagHEAD y ramaÍndiceWorking treeÚsalo para…
--softSíNoNoRecomponer commits: deshacer el commit dejando todo listo para commitear de nuevo.
--mixed (por defecto)SíSíNoDeshacer el commit y desindexar, conservando los cambios en los ficheros.
--hardSíSíSíDescartar todo y dejar el directorio igual que el commit destino.

--hard no borra commits de verdad —están en el reflog y se recuperan durante ~90 días—, pero sí destruye los cambios no commiteados, que no están en ningún objeto. Antes de usarlo: git status y, si hay dudas, git stash push -u. Ver reset.

Regla de decisión: si el commit ya está en una rama compartida, git revert; si solo existe en tu máquina, git reset o git rebase. La historia publicada no se reescribe (revert).

Quiero trabajar con ramas y unir

Una rama es un puntero móvil a un commit, no una copia de la carpeta. Crear una rama es gratis; lo que cuesta es integrarla.

git switch -c feature/busqueda    # crear y cambiar en un paso
git branch                        # listar ramas locales (* = la actual)
git branch -a                     # incluir ramas remotas
git branch -d feature/busqueda    # borrar solo si está mergeada
git branch -D feature/busqueda    # forzar el borrado (recuperable por reflog)
git branch -m nombre-nuevo        # renombrar la rama actual

git merge feature/busqueda         # fast-forward si main no avanzó
git merge --no-ff feature/busqueda # forzar merge commit (preserva la rama)
git merge --ff-only origin/main    # falla si exigiría un merge commit
git merge --squash feature/busqueda # deja los cambios staged, sin merge commit
git merge --abort                  # cancelar un merge a medias

Resolver un conflicto

git status                          # "both modified": los ficheros en conflicto
git diff --name-only --diff-filter=U  # solo los conflictivos
# editar y eliminar los marcadores <<<<<<< ======= >>>>>>>
git add conflicto.md
git merge --continue                # o git commit, si el merge ya está resuelto
git merge --abort                   # volver al estado anterior al merge
los marcadores — qué es cada bloque
<<<<<<< HEAD
lo que hay en tu rama actual
=======
lo que trae la rama que estás integrando
>>>>>>> feature/busqueda

El conflicto no es un error de Git: es Git pidiendo una decisión que no puede tomar por ti. Resolver no es «elegir un lado», es escribir el resultado correcto, que a veces combina ambos. Ver Resolver conflictos.

Fast-forward vs merge commit

la misma integración, dos historias
# fast-forward: main no se movió desde que salió la rama
antes:   A ── B (main)
              \
               C ── D (feature)
después: A ── B ── C ── D (main y feature)

# merge commit: main avanzó por su cuenta
antes:   A ── B ── E (main)
              \
               C ── D (feature)
después: A ── B ── E ───── M (main)
              \          /
               C ── D ──┘   M tiene dos padres: E y D

--no-ff conserva el contexto de que hubo una rama; el fast-forward deja una historia lineal pero pierde ese rastro. Ni uno es «mejor»: depende de si quieres leer la topología o el resultado (merge).

Quiero reescribir la historia

Rebase y cherry-pick no «mueven» commits: crean commits nuevos con el mismo cambio y otro hash. Por eso solo son seguros sobre historia que nadie más ha tomado como base.

git rebase main                    # reaplicar mi rama sobre la punta de main
git rebase -i HEAD~3               # editar los últimos 3 commits
git rebase -i --autosquash main    # ordenar los fixup! automáticamente
git rebase --continue              # tras resolver un conflicto
git rebase --skip                  # descartar el commit que falla
git rebase --abort                 # volver a donde estabas antes del rebase

git cherry-pick a1b2c3d            # traer ese commit concreto a la rama actual
git cherry-pick -x a1b2c3d         # añadir "(cherry picked from ...)" al mensaje
git cherry-pick main..feature      # un rango (sin incluir main)
git cherry-pick --abort            # cancelar si hay conflicto
rebase interactivo — la lista que editas
pick   a1b2c3d feat: formulario de búsqueda
reword e4f5g6h fix: corregir tilde en el placeholder
squash 1a2b3c4 wip
fixup  b2c3d4e wip tests
drop   9f8e7d6 debug: console.log temporal

# pick = dejar · reword = cambiar mensaje · edit = parar para enmendar
# squash = unir al anterior y editar mensaje · fixup = unir y descartar mensaje
# drop = eliminar el commit

Merge vs rebase

mergerebase
Qué creaUn merge commit (o un fast-forward)Copias nuevas de tus commits, con otros hashes
Historia resultantePreserva la topología y las ramasLineal, como si hubieras trabajado al final
ConflictosSe resuelven una vezPueden reaparecer en cada commit reaplicado

La regla de oro: no reescribas commits que alguien pueda tener. Si el rebase ya ocurrió y toca publicar, --force-with-lease —nunca --force— y solo en tu rama. --force-with-lease rechaza el push si el remoto cambió desde tu último fetch. Ver Reescribir con cuidado.

¿Y si el rebase sale mal? git rebase --abort mientras está en curso; si ya terminó, git reflog y git reset --hard HEAD@{1}. El reflog es la red de seguridad local de todas estas operaciones.

Quiero colaborar con un remoto

Un remoto es un nombre para una URL (origin por convención, no por magia). fetch descarga y actualiza las ramas remotas; no toca tu working tree. pull es fetch + integrar. push envía tus objetos y mueve la ref del remoto.

git clone ../taller.git taller     # copia objetos, refs y configura origin
git remote add origin ../taller.git
git remote -v
git remote set-url origin <nueva-url>

git fetch origin                   # trae objetos y actualiza origin/*
git fetch --all --prune            # todos los remotos; borra refs que ya no existen
git log --oneline HEAD..origin/main  # qué hay en el remoto que no tengo

git pull --ff-only                 # integra solo si es fast-forward (recomendado)
git pull --rebase                  # reaplica tus commits locales encima del remoto

git switch -c feature/busqueda
git push -u origin HEAD            # publica y fija el upstream
git push                           # ya sabe a dónde ir
git push origin --delete feature/busqueda
git push --force-with-lease        # solo tu rama, tras un rebase

Tags: marcar una release

git tag -a v1.0.0 -m "release: 1.0.0"   # anotado: objeto tag con mensaje y firma
git tag v1.0.0                            # ligero: solo una ref al commit
git tag -l "v1.*"
git show v1.0.0                           # metadatos + commit apuntado
git push origin v1.0.0                    # los tags NO se empujan con push normal
git push origin --tags                    # todos (incluidos los ligeros)
git tag -d v1.0.0                         # borrar en local
git push origin :refs/tags/v1.0.0         # borrar en el remoto

Un tag anotado es la release; uno ligero es un post-it. Para versiones publicadas usa siempre -a con mensaje: guarda autor, fecha y permite firmarlo. Y recuerda: mover un tag ya publicado es reescribir historia (push y tracking).

Si el remoto rechaza tu push por non-fast-forward, no fuerces: git fetch, mira git log --oneline HEAD..@{u} y decide entre git rebase @{u} (historia lineal) o git merge @{u} (preserva el merge). Ver clone, fetch y pull.

Quiero investigar la historia

Investigar es hacer preguntas al grafo: ¿cuándo apareció este texto?, ¿quién tocó esta línea?, ¿qué commit rompió el test?, ¿dónde está el commit que borré? Cada pregunta tiene su comando y ninguno requiere adivinar.

git log --oneline --graph --decorate --all
git log --since="2 weeks ago" --author="Ana" --oneline
git log -S"fetchData" --oneline -- src/    # pickaxe: cuándo apareció/desapareció el texto
git log -G"fetch[A-Z]" --oneline           # regex sobre las líneas del diff
git log --follow --oneline -- notas.md     # sigue el fichero aunque lo renombraras
git log -L 10,25:src/api.js                # historia de esas líneas concretas

git blame -L 10,25 src/api.js              # quién tocó por última vez cada línea
git blame --ignore-rev <sha> src/api.js    # ignorar un commit de reformateo

git bisect start
git bisect bad                             # el commit actual falla
git bisect good v1.0.0                     # este tag funcionaba
git bisect run ./scripts/test.sh           # 0 = good, ≠0 = bad, 125 = saltar
git bisect reset                           # terminar y volver a donde estabas

git reflog --date=iso                      # cada movimiento de HEAD, con fecha
git reset --hard HEAD@{1}                  # volver al movimiento anterior
git branch rescate <sha>                   # dar ref a un commit huérfano
git fsck --lost-found                      # listar objetos inalcanzables

git worktree add ../taller-hotfix -b hotfix main
git worktree list
git worktree remove ../taller-hotfix

bisect es búsqueda binaria, no magia: con 1.000 commits candidatos necesitas ~10 pasos. bisect run automatiza el proceso si tienes un test que devuelva 0/1; el código 125 le dice «este commit no se puede probar, sáltalo». Al terminar, git bisect reset te devuelve a la rama original (blame y bisect).

El reflog es local y caduca. Registra los movimientos de HEAD y de las ramas durante unos 90 días por defecto; no se comparte al hacer push. Es la primera parada cuando «he perdido un commit», y casi siempre la última (reflog).

Nunca empieces por git push --force. Si ya publicaste algo que hay que deshacer, git revert es la respuesta por defecto: no borra historia, añade un commit que explica la marcha atrás. El force push se reserva para tu rama y con --force-with-lease.

Configuración recomendada

Una configuración global sensata evita la mitad de los sustos: rama por defecto explícita, pull que no inventa merges, conflictos con contexto y finales de línea bajo control. Cópiala y ajústala; no es dogma.

git config --global user.name "Tu Nombre"
git config --global user.email "tu@ejemplo.com"

git config --global init.defaultBranch main
git config --global pull.ff only            # pull solo si es fast-forward
git config --global fetch.prune true        # limpia ramas remotas borradas
git config --global rebase.autoStash true   # guarda cambios antes de rebase
git config --global rebase.autosquash true  # ordena fixup!/squash! en -i
git config --global merge.conflictStyle zdiff3  # zdiff3: Git 2.35+; antes, diff3
git config --global diff.algorithm histogram    # diffs más legibles
git config --global rerere.enabled true     # recuerda resoluciones de conflicto
git config --global core.autocrlf false     # LF manda; usa .gitattributes
git config --global commit.verbose true     # diff visible al escribir el mensaje
git config --global push.default simple
git config --global push.autoSetupRemote true   # Git 2.37+; antes, push -u
git config --global core.editor "code --wait"

git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.st "status -sb"
git config --global alias.unstage "restore --staged --"
git config --global alias.last "show --stat --oneline HEAD"

git config --global --list --show-origin    # verificar de dónde sale cada valor
ClaveQué evita

fetch.prune trueAcumular origin/feature-vieja que ya nadie tiene.

Identidad por carpeta

Si usas el mismo portátil para trabajo y proyectos personales, no cambies user.email a mano: deja que Git elija según la ruta.

~/.gitconfig — include condicional
[includeIf "gitdir:~/trabajo/"]
    path = ~/.gitconfig-trabajo

# ~/.gitconfig-trabajo
[user]
    email = tu.nombre@empresa.com

Comprueba con git config --show-origin user.email dentro de cada repositorio: debe apuntar al fichero que esperas. Y si el repo exige LF, añade un .gitattributes con * text=auto eol=lf; así la norma viaja con el código y no depende de la configuración de cada máquina (.gitignore y .gitattributes).
