Glosario de términos

Referencia 📖 El vocabulario del modelo de Git

A

add (stage, indexar)
Copia el contenido actual de un fichero del working tree al índice, dejándolo listo para el próximo commit. Si el contenido ya existe como blob, Git reutiliza el objeto: no duplica nada. git add -p permite elegir por fragmentos (diff y el índice).
amend
Reescribe el último commit: le cambia el mensaje, le añade o quita ficheros, o ambos. No «edita» el objeto —los commits son inmutables—: crea uno nuevo con otro hash y mueve la rama. Seguro solo si el commit no está publicado (Commits atómicos).
árbol de trabajo (working tree)
Los ficheros que ves y editas: el checkout de un commit más tus cambios. Es una de las tres zonas, junto con el índice y HEAD. Git no lo toca salvo que se lo pidas con restore, reset --hard, switch o merge (Los tres estados).

B

bare repository (repositorio desnudo)
Repositorio sin working tree ni índice: solo la base de objetos y las refs. Es la forma habitual de un remoto (git init --bare) y por convención termina en .git. No se trabaja dentro de él; se empuja y se hace fetch contra él (clone, fetch y pull).
bisect
Búsqueda binaria del commit que introdujo un fallo. Marcas un commit good, uno bad y Git va haciendo checkout de puntos intermedios hasta aislar el culpable. Con git bisect run <script> se automatiza: el script devuelve 0 para good, distinto de 0 para bad y 125 para saltar (blame y bisect).
blob (binary large object)
Objeto que guarda solo el contenido de un fichero: ni nombre, ni ruta, ni permisos. Su identidad es el hash de ese contenido, así que dos ficheros idénticos comparten blob. El nombre y el modo viven en el tree (El modelo interno).

C

checkout (antiguo)
Comando que hacía dos cosas distintas: cambiar de rama y restaurar ficheros. Desde Git 2.23 se prefiere switch para ramas y restore para ficheros. Aparece en tutoriales viejos y en scripts; no es la forma recomendada del curso.
cherry-pick
Reaplica el cambio que introduce un commit (su diff contra su padre) sobre la rama actual, mediante un merge a tres bandas, y crea un commit nuevo con otro hash. El autor original se conserva; el committer eres tú. Útil para un hotfix suelto; abusar de él duplica cambios y complica el merge (cherry-pick).
clone
Copia un repositorio completo —objetos, refs y configuración— y crea una rama local a partir de la remota por defecto. Configura el remoto origin, las ramas de seguimiento y el upstream de la rama principal. No es una copia de ficheros: es una copia de la base de objetos (clone, fetch y pull).
commit
Objeto inmutable que apunta a un tree (la foto del proyecto), a cero o más padres, y guarda autor, committer, fechas y mensaje. Su hash lo identifica. «Hacer un commit» es congelar el índice en un objeto y avanzar la rama (El primer repositorio).
commit-ish / tree-ish
Cualquier expresión que Git resuelve a un commit (commit-ish) o a un árbol (tree-ish): un hash, una rama, un tag, HEAD, HEAD~2, main@{yesterday}, v1.0.0^{commit}. Casi todos los comandos aceptan estos nombres en lugar de un SHA completo.
conflicto
Situación en la que dos cambios incompatibles afectan a la misma región y Git no puede elegir. Pausa la operación (merge, rebase, cherry-pick, stash pop), escribe marcadores en el fichero y guarda las tres versiones en el índice (base, ours, theirs). Se resuelve editando, git add y continuando (Resolver conflictos).

D

dangling commit / objeto inalcanzable
Objeto que existe en la base pero ya no es alcanzable desde ninguna ref: típico de un reset --hard, un amend o una rama borrada. No se borra de inmediato; git fsck --lost-found lo lista y git gc termina eliminándolo tras el periodo de gracia (≈2 semanas). El reflog lo mantiene alcanzable mientras dure (reflog).
detached HEAD
Estado en el que HEAD apunta directamente a un commit en lugar de a una rama (tras git switch --detach <sha> o al hacer checkout de un tag). Puedes leer y commitear, pero los commits nuevos no pertenecen a ninguna rama: si cambias de rama sin crear una, quedan solo en el reflog (Ramas y HEAD).
diff
Diferencia entre dos estados: working tree vs índice (git diff), índice vs HEAD (git diff --staged), o dos commits/ramas. git diff A...B compara B contra el ancestro común, que es lo que interesa al revisar una rama. No es un objeto guardado: se calcula al vuelo.

F

fast-forward
Integración en la que la rama destino es ancestro de la que se integra: basta con avanzar el puntero, sin crear commit de merge. Deja historia lineal pero pierde el rastro de que existió una rama. --no-ff lo impide; --ff-only exige que sea posible (merge).
fetch
Descarga los objetos que faltan y actualiza las ramas de seguimiento remotas (origin/main) y FETCH_HEAD. No toca tus ramas locales ni el working tree: es la forma segura de mirar qué hay antes de integrar. git fetch --prune elimina las refs remotas que ya no existen (fetch y pull).
FETCH_HEAD
Fichero/ref que registra lo último que trajo un fetch (qué ramas y hashes), para que comandos posteriores como git merge FETCH_HEAD sepan qué integrar. No es una rama y se sobrescribe en cada fetch.
fork
Copia de un repositorio en el servidor de una forja (GitHub, GitLab), con su propia URL y permisos. No es un concepto de Git: es una función de la plataforma para proponer cambios sin escribir en el repo original. Se combina con un pull request.
force-with-lease
Variante segura de push --force: solo sobrescribe el remoto si su ref sigue en el punto que tú viste en el último fetch. Si un compañero empujó mientras tanto, el push se rechaza en vez de borrar su trabajo. Aun así, solo se usa en ramas propias (Reescribir con cuidado).

H

hash (SHA-1 / SHA-256)
Huella criptográfica del contenido de un objeto: 40 caracteres hex en SHA-1, 64 en SHA-256. Es su identidad: si cambia un byte, cambia el hash y, en cascada, el de los commits que lo contienen. Se puede abreviar (a1b2c3d) si no hay ambigüedad. Que dos objetos tengan el mismo hash implica el mismo contenido.
HEAD
Ref especial que indica dónde estás: normalmente un puntero simbólico a la rama actual (refs/heads/main), que a su vez apunta a un commit. Al commitear, se mueve la rama y HEAD la sigue. En detached HEAD contiene un hash directamente. HEAD~1 es su primer padre (Ramas y HEAD).
hook
Script que Git ejecuta en un momento del ciclo de vida: pre-commit, commit-msg, pre-push, post-receive… Los de cliente viven en .git/hooks/, no se clonan y se pueden saltar con --no-verify; para compartirlos se usa core.hooksPath o una herramienta de instalación. No son una barrera de seguridad (Hooks).

I

ignorar (.gitignore)
Lista de patrones para que Git no muestre como untracked ciertos ficheros. Solo afecta a ficheros no trackeados: si uno ya está en el índice, hay que sacarlo con git rm --cached. Se admiten negaciones (!) y el orden importa (.gitignore y .gitattributes).
índice (index, staging area, cache)
Estructura binaria en .git/index que describe el próximo commit: rutas, modos, hashes de blob y metadatos de stat. git add lo escribe; git commit lo congela en un tree. Durante un conflicto guarda hasta tres versiones por ruta (base, ours, theirs). No es una carpeta de borradores ni un diff (Los tres estados).

M

merge
Integra otra rama en la actual. Si es posible, avanza el puntero (fast-forward); si no, crea un merge commit y, si hay cambios solapados, pausa con un conflicto. No reescribe la historia de ninguna de las dos ramas (merge).
merge commit
Commit con dos o más padres que materializa la unión de dos historias. El primer padre es la rama en la que estabas; el segundo, la integrada. Conserva la topología, a cambio de un grafo menos lineal. git revert sobre él necesita -m 1 para saber qué padre conservar.
merge-base (ancestro común)
El mejor ancestro común de dos commits: el punto donde sus historias se separaron. Es la base del merge a tres bandas y de git diff A...B. Se consulta con git merge-base A B.

O

objeto
Unidad inmutable de la base de datos de Git, guardada en .git/objects/ y direccionada por su hash. Hay cuatro tipos: blob, tree, commit y tag anotado. Todo lo demás —ramas, HEAD, índice— son punteros o estructuras auxiliares (El modelo interno).
origin
Nombre convencional del remoto del que clonaste. No es especial ni obligatorio: es un alias para una URL, guardado en remote.origin.url. Puedes tener varios remotos (upstream, fork) y renombrarlos sin perder nada (Remotos).
ORIG_HEAD
Ref de seguridad que Git escribe antes de operaciones que mueven la historia: merge, rebase, reset, am. Sirve para volver atrás (git reset --hard ORIG_HEAD) si el resultado no te convence. El reflog es más general.

P

packfile
Formato comprimido en el que Git agrupa objetos (.git/objects/pack/*.pack con su índice .idx), aplicando deltas entre versiones similares. Es lo que se transfiere en clone/fetch y lo que produce git gc. No cambia el modelo: los objetos siguen siendo los mismos.
pathspec
Patrón de rutas que limita un comando a ciertos ficheros: git add src/, git diff -- '*.md', git restore -- ':(glob)**/*.ts'. El -- separa rutas de revisiones y evita que un nombre se confunda con una rama.
pull
fetch + integración (merge o rebase, según configuración). Es la operación que más sorpresas causa porque mezcla dos pasos: descargar y modificar tu rama. pull --ff-only falla si no puede avanzar limpiamente, que es lo más predecible (fetch vs pull).
pull request (PR) / merge request
Propuesta de integrar una rama en otra, con revisión, comentarios y comprobaciones. Es una función de la forja (GitHub, GitLab, Bitbucket), no de Git: por debajo solo hay una rama y un merge. El curso usa un remoto local, así que no depende de ninguna plataforma (Pull requests).
push
Envía los objetos que faltan al remoto y actualiza su ref. Se rechaza si el resultado no es fast-forward, salvo que fuerces. Con -u fija el upstream de la rama para que los siguientes push/pull no necesiten argumentos (push y tracking).

R

rama (branch)
Ref móvil bajo refs/heads/ que apunta a un commit. No es una copia del proyecto: crear una rama solo escribe un nombre y un hash. Avanza al commitear en ella; borrarla no borra commits, solo elimina una referencia (Ramas y HEAD).
rebase
Reaplica los commits de una rama sobre otra base, creando commits nuevos con otros hashes (el autor se conserva, el committer y la fecha cambian). Produce historia lineal y evita el merge commit, pero reescribe: solo es seguro en commits que nadie más ha tomado como base. Durante el proceso, HEAD queda detached y la rama se mueve al final (rebase).
ref
Nombre que apunta a un objeto o a otra ref: refs/heads/main, refs/tags/v1.0.0, refs/remotes/origin/main, HEAD. Las ramas y los tags son refs; el reflog registra cómo se mueven. Se listan con git show-ref y se empaquetan en .git/packed-refs.
reflog
Registro local de los movimientos de HEAD y de las ramas (.git/logs/), con fecha y motivo. Es la red de seguridad de reset, rebase, amend y borrados de rama. Caduca (≈90 días por defecto) y no se comparte al hacer push (reflog).
refspec
Regla que mapea refs entre local y remoto, con la forma origen:destino. Un + delante permite actualizaciones no fast-forward. El refspec por defecto de un clone es +refs/heads/*:refs/remotes/origin/*; se ve en remote.origin.fetch.
remoto (remote)
Nombre y URL de otro repositorio con el que se sincroniza. Guarda además el refspec de fetch. No implica red: puede ser una ruta local o un repositorio bare en el mismo disco, como en el laboratorio del curso.
remote-tracking branch (origin/main)
Ref local bajo refs/remotes/ que actúa de espejo de una rama remota. Solo la mueven fetch y push; no es tu rama de trabajo y no se commitea en ella. Sirve para comparar (git log HEAD..origin/main) y como upstream.
reset
Mueve HEAD y la rama actual a otro commit y, según el flag, ajusta índice y working tree: --soft solo la rama; --mixed (por defecto) también el índice; --hard también los ficheros. Los commits abandonados siguen recuperables por reflog; los cambios sin commitear que borra --hard, no (reset).
restore
Restaura ficheros del working tree o del índice desde una fuente (--source, por defecto el índice para el working tree y HEAD para --staged). No mueve HEAD ni la rama: es la herramienta quirúrgica para «este fichero sí, el commit no» (restore).
revert
Crea un commit nuevo que aplica el cambio inverso de otro. No reescribe la historia, así que es la forma correcta de deshacer algo ya publicado. Para un merge hace falta -m 1 (o el número del padre que se conserva). Puede volver a introducir el cambio si luego se vuelve a fusionar la rama original (revert).

S

staging area
Otro nombre del índice. «Staged» significa que el cambio está en el índice y entrará en el próximo commit; «unstaged», que solo está en el working tree.
stash
Pila de estados guardados (working tree + índice) para dejar la rama limpia sin commitear. Internamente son commits colgados de refs/stash, no una rama. Se aplica con pop (aplica y borra) o apply (aplica y conserva); si hay conflicto, el stash no se elimina (stash).
switch
Comando moderno (Git 2.23+) para cambiar de rama o entrar en detached HEAD. Se niega a perder cambios sin commitear. switch -c crea y cambia; switch - vuelve a la rama anterior. Sustituye al uso de checkout para ramas (Ramas y HEAD).

T

tag
Ref fija que marca un commit, normalmente una release. Hay dos tipos: ligero (solo una ref a un commit) y anotado (un objeto tag con nombre, tagger, fecha y mensaje, y opcionalmente firma). Los tags no se mueven solos y no se empujan con un push normal: git push origin v1.0.0 (Releases).
tracking branch (upstream)
Rama local vinculada a una remota, configurada en branch.<nombre>.remote y branch.<nombre>.merge. Permite git pull/git push sin argumentos y referirse a @{u} o @{upstream}. Se crea con push -u, switch --track o branch -u.
tree (árbol)
Objeto que representa un directorio: una lista ordenada de entradas con modo, tipo, hash y nombre. Puede contener blobs (ficheros) y otros trees (subdirectorios). El tree de un commit es la foto completa del proyecto en ese momento; los ficheros no cambiados se comparten entre trees (El modelo interno).

U

upstream
La rama remota que una rama local «sigue». Es configuración, no un objeto: dice a dónde van push y pull por defecto y qué comparar en git status. Se consulta con git branch -vv y se cambia con git branch -u origin/main (push y tracking).

W

worktree (árbol de trabajo adicional)
Checkout extra del mismo repositorio en otro directorio, con su propio HEAD y su propia rama, compartiendo la base de objetos y las refs. Sirve para atender un hotfix sin tocar el trabajo en curso. No se puede tener la misma rama en dos worktrees a la vez (salvo --force). Se gestiona con git worktree add/list/remove/prune (worktree y config).
