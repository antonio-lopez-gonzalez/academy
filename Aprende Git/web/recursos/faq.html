Preguntas frecuentes

FAQ ❓ Dudas comunes del curso

Antes de empezar

¿Necesito GitHub (o GitLab, o una cuenta en la nube) para seguir el curso?

No. Git es el sistema de control de versiones; GitHub es una forja que lo aloja, y el curso distingue explícitamente una cosa de la otra. Para practicar remotos se usa un repositorio bare local: git init --bare ../taller.git, y luego git clone ../taller.git. Funciona sin red, sin cuenta y sin claves SSH, y reproduce lo que importa: origin, fetch, push, rechazos por divergencia y ramas de seguimiento. Las pull requests se explican como flujo de revisión, no como requisito técnico (Pull requests).

¿Qué versión de Git necesito? ¿Sirve en Windows?

Git 2.23 o superior, porque el curso usa git switch y git restore en lugar del viejo checkout. Comprueba con git --version. En Windows instala Git for Windows y usa Git Bash para los ejemplos: es el shell canónico del curso. En PowerShell, expresiones como @{u} o HEAD@{1} pueden interpretarse como sintaxis del propio PowerShell; entrecomíllalas ('HEAD@{1}') o quédate en Git Bash. En macOS y Linux, cualquier Git del sistema o del gestor de paquetes que cumpla la versión.

Ya uso add, commit y push a diario. ¿Este curso me aporta algo?

Sí, si alguna vez has hecho reset --hard rezando, has tenido miedo de un rebase o has preguntado «¿esto ya lo he publicado?». El curso no enseña más comandos: enseña el modelo de objetos para que sepas qué mueve cada uno, y convierte «deshacer» en una decisión con criterio (restore, reset, revert, stash) en vez de una receta memorizada. Si dominas el día a día, puedes ir directo a los módulos 2 (deshacer), 4 (historia) y 6 (investigar), y usar el 7 como proyecto de auditoría (El modelo interno).

Deshacer sin destrozar nada

¿reset o revert? Nunca sé cuál toca.

La pregunta que decide es una: ¿ese commit está publicado en una rama que otros usan? Si la respuesta es no, puedes reescribir tu historia local con git reset (o rebase): mueves el puntero de tu rama y, si quieres, el índice y los ficheros. Si la respuesta es sí, usa git revert: crea un commit nuevo que invierte el anterior, sin borrar nada, de modo que quien ya hizo fetch no se encuentra una historia distinta. Regla mnemotécnica: reset reescribe, revert añade. Y si el commit aún no existe pero los cambios sí, lo que buscas es git restore (reset · revert).

¿Puedo recuperar lo que borré? ¿Hasta cuándo?

Distingue dos casos. Commits «perdidos» (tras un reset --hard, un amend o borrar una rama): sí, casi siempre. Están en la base de objetos y el git reflog guarda durante unos 90 días los movimientos de HEAD y de las ramas; localiza el hash y haz git branch rescate <sha> o git reset --hard HEAD@{1}. Si el reflog ya caducó, git fsck --lost-found puede encontrar objetos inalcanzables hasta que git gc los limpie. Cambios que nunca se commitearon: no, no están en ningún objeto; un restore o un reset --hard los borra sin red. De ahí la costumbre de hacer stash antes de operaciones destructivas (reflog).

Hice un merge y quiero deshacerlo, pero ya está publicado. ¿reset?

No, si está publicado: git revert -m 1 <merge-sha>. El -m 1 le dice a Git que conserve el primer padre (la rama en la que estabas al fusionar) e invierta los cambios que trajo el segundo. Eso deja un commit de reversión limpio. Ojo con el efecto secundario: si más adelante vuelves a fusionar la misma rama, Git considerará que esos cambios ya están integrados y no los traerá; para recuperarlos hay que revertir el commit de reversión o aplicar los commits uno a uno. Si el merge aún no está publicado, git reset --hard ORIG_HEAD —o el hash anterior— es más simple (revert).

Ramas, rebase y fuerza

¿merge o rebase? Siempre me lía la respuesta «depende».

La versión corta: merge para integrar historia compartida, rebase para ordenar la tuya antes de compartirla. Si dos personas trabajan en la misma rama, un rebase les cambia los hashes y les obliga a recolocar su trabajo; un merge, en cambio, solo añade. Si tu rama es privada y quieres que el PR se lea como una secuencia limpia sobre main, rebase (o rebase -i para squash/fixup) antes de pedir revisión. Ninguna opción es «más profesional»: son historias distintas, con costes distintos. Lo que sí es mala idea es rebasar main o cualquier rama de la que otros ya parten (rebase · merge).

¿Y si ya hice push? ¿Puedo reescribir igualmente?

Depende de quién haya tomado esos commits. En tu rama personal, tras un rebase o un amend, el push normal será rechazado porque no es fast-forward; ahí se usa git push --force-with-lease, que solo sobrescribe si el remoto sigue donde tú lo viste. Nunca --force a secas, y nunca a main. En una rama compartida, no reescribas: publica un revert o pide a quien corresponda. Aunque uses --force-with-lease, avisa: quien tenga la rama antigua necesitará git fetch y git reset --hard origin/rama, y perderá cualquier commit local no publicado (Reescribir con cuidado).

¿El rebase interactivo es peligroso? Me da miedo tocar la lista.

El riesgo está mal localizado: git rebase -i sobre commits locales es bastante seguro, porque cada paso deja rastro en el reflog y puedes volver con git rebase --abort o git reset --hard ORIG_HEAD. Lo peligroso es el resultado de publicar esa historia reescrita sin coordinación. Dicho eso, hay dos trampas reales: (1) un conflicto puede repetirse en varios commits, y (2) rebasar historia con merges puede aplanarla o exigir --rebase-merges. Empieza con rebase -i HEAD~3, usa squash/fixup/reword y comprueba el grafo con git log --oneline --graph antes de empujar (rebase interactivo).

¿Puedo cambiar el mensaje de un commit que ya está publicado?

No sin reescribir la historia: el mensaje forma parte del commit y cambiarlo produce otro hash. En un commit publicado eso obliga a force push y a que todos reubiquen su rama. La alternativa sensata es dejarlo y explicarlo: un commit de seguimiento, una nota en el PR o un git revert si el mensaje indujo a error. Si el commit es local, git commit --amend -m "..." y listo. Esta es la misma razón por la que revert no «edita» nada: añade un commit que cuenta lo que pasó (Commits atómicos).

Practicar y salir de un lío

¿Cómo practico sin riesgo de cargarme un repositorio real?

Crea repositorios de usar y tirar. El curso trae proyectos/laboratorio/, que monta los escenarios con node y los comprueba con node --test: conflictos, un bug para bisect, un commit perdido y un remoto bare local. Todo ocurre en directorios temporales y sin red. Para experimentar por tu cuenta: mkdir ~/pruebas-git && cd ~/pruebas-git && git init, y rompe lo que quieras. Si quieres probar algo sobre un repo real, haz antes una copia completa de la carpeta —incluido .git— o un git clone local; es más rápido que arrepentirse (Auditoría de un repositorio).

Me he perdido: ¿por dónde empiezo a mirar?

Para. No ejecutes reset --hard, clean -fd ni push --force «a ver si arregla». El orden es: (1) git status, para saber en qué rama estás, si hay un merge/rebase en curso y qué ficheros están en cada zona; (2) git log --oneline --graph --decorate --all -n 20, para ver dónde está cada puntero; (3) git reflog, si crees que has perdido commits. Casi todos los mensajes de Git dicen qué comando sugerir; léelos enteros antes de copiar. Si el repo está muy sucio, copia la carpeta .git a otro sitio antes de tocar nada: es tu copia de seguridad. Y si el pánico es por un fichero concreto, git restore --source=HEAD -- <archivo> es reversible si antes guardas una copia (triaje rápido).
