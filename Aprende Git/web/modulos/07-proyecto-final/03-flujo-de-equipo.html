Flujo de equipo

Módulo 7 · Proyecto final 🕐 40 minutos

1 · Introducción

Un repositorio limpio (lecciones 01 y 02) no se mantiene solo: se mantiene con reglas compartidas. Esta lección convierte la buena voluntad en convención escrita y verificable: cómo se llaman las ramas, cómo se escribe un commit, cómo se integra, quién puede empujar a main y qué se automatiza con un hook.

El entregable son dos cosas concretas: un documento de flujo (CONTRIBUTING.md) que cualquiera pueda leer en cinco minutos, y una carpeta .githooks/ versionada con un hook commit-msg que da feedback inmediato. Y una lección de humildad: los hooks locales no son una barrera de seguridad.

¿Por qué escribir el flujo y no "ya nos organizamos"?

Porque las reglas no escritas se rompen a la primera incorporación. Un CONTRIBUTING.md convierte "los commits van con prefijo" en algo que se puede citar en una revisión y automatizar con un hook. Y si la regla no se puede automatizar ni citar, probablemente no era una regla: era una preferencia.

Errores típicos

Confiar la disciplina a hooks locales (cualquiera los salta con --no-verify); instalar core.hooksPath en --global y afectar a todos los repositorios de la máquina; y escribir un flujo de veinte normas que nadie recuerda. La regla de oro: pocas reglas, automatizadas y protegidas en el servidor.

2 · Teoría

El flujo mínimo que funciona

Antes de elegir "Git Flow vs GitHub Flow vs trunk-based" (módulo 3, lección 04), decide cinco cosas. Cinco decisiones bien tomadas valen más que un diagrama de colores:

DecisiónPregunta que respondeEjemplo concreto
Rama de integración ¿Cuál es la rama estable de la que todo parte? main siempre desplegable; nadie commitea directo
Ramas de trabajo ¿Corta, desde main, y se borra al integrar? feature/…, fix/… de vida corta (< 3 días)
Nombres ¿Cómo se llaman las ramas? tipo/scope-descripcion-corta en minúsculas y guiones
Integración ¿Merge, squash o rebase? ¿Quién lo hace? Squash merge vía PR; la persona autora no mergea su propio PR
Puertas de calidad ¿Qué debe pasar antes de integrar? 1 revisión + CI en verde + commits con conventional commits

El ciclo, dibujado

                     ┌───────────────────────────────────────────┐
                     │                  main                     │
                     │   (protegida · siempre desplegable)       │
                     └───────────────────────────────────────────┘
                          ▲                          │
             squash merge │                          │ branch (siempre desde main)
             + revision   │                          ▼
                     ┌───────────────────────────────────────────┐
                     │     feature/busqueda-case-insensitive     │
                     │   commits: feat · fix · test · docs       │
                     └───────────────────────────────────────────┘
                          │
                          │ push + Pull Request
                          ▼
   ┌───────────────────────────────────────────────────────────────┐
   │  CI: lint · tests · build  →  Revision humana  →  Merge       │
   │  (status checks obligatorios · 1 aprobacion · sin bypass)     │
   └───────────────────────────────────────────────────────────────┘

Nada exótico: ramas cortas, PR pequeño, revisión, CI, squash y fuera. Lo que hace que esto se sostenga no es el diagrama, sino que esté protegido en el servidor (lo verás al final de la teoría).

Convención de nombres de rama

feature/busqueda-case-insensitive      nueva funcionalidad
fix/500-al-listar-sin-texto            correccion de bug
hotfix/1.0.1                           parche urgente sobre un tag
chore/actualizar-dependencias          mantenimiento sin cambio funcional
docs/readme-instalacion                documentacion
refactor/extraer-servicio-notas        refactor sin cambio de comportamiento

Reglas: minusculas · guiones (no guiones bajos ni espacios) · prefijo de tipo ·
incluye el id del issue si existe (fix/142-...).  NO: mi-rama, Ana, prueba2, temp.
La convención sirve para automatizar, no para castigar

Si el nombre de la rama empieza siempre por un tipo conocido, puedes usarlo después en scripts: extraer el tipo para etiquetar el PR, decidir si pasa por un flujo de hotfix, o generar un changelog por rama. Una convención que no alimenta ninguna automatización es solo burocracia.

Hooks: el contrato de commit-msg

Un hook es un script que Git ejecuta en un momento concreto del ciclo. El de commit-msg recibe como primer argumento un fichero con el mensaje que estás a punto de guardar: si el script sale con código distinto de cero, el commit se cancela. Es el sitio natural para exigir Conventional Commits.

HookCuándo correUso típico
pre-commitAntes de crear el commitLint, formateo, evitar ficheros grandes
commit-msgCon el mensaje ya escritoValidar la convención del mensaje
pre-pushAntes de enviarEjecutar tests rápidos
post-mergeTras un mergeAvisar de dependencias cambiadas
post-checkoutTras cambiar de ramaPreparar el entorno
Los hooks NO son una barrera de seguridad

Viven en .git/hooks/, que no se versiona, y cualquiera los salta con git commit --no-verify. Sirven para feedback rápido y consistencia, no para impedir. La barrera de verdad está en el servidor: revisiones requeridas, status checks obligatorios y protección de rama. El hook es el cartel de "cuidado con el escalón"; la protección es la barandilla.

Versionar los hooks: core.hooksPath

Como .git/hooks/ no se versiona, la solución es guardar los hooks en una carpeta del repositorio (por ejemplo .githooks/) y decirle a Git que los busque ahí:

# En el proyecto (config LOCAL: solo este repositorio)
git config core.hooksPath .githooks
git update-index --chmod=+x .githooks/commit-msg   # en Linux/macOS: +x

A partir de ahí, .githooks/commit-msg es un archivo versionado más: viaja con el repo, se revisa en un PR y cambia igual que el código. Cada persona debe activar el core.hooksPath una vez (o el proyecto lo hace por ella, si trae un script de setup).

Git 2.9+ y las alternativas modernas

core.hooksPath existe desde Git 2.9 y es lo que usa hoy todo el mundo para hooks compartidos. Alternativas: un hook manager (husky, pre-commit, lefthook) que gestiona la instalación, o un simple script scripts/setup.sh en el README. Lo importante es que la configuración sea local y el hook versionado.

Proteger main en el servidor

Lo último, y lo único que de verdad impone algo. En una forja (GitHub, GitLab, Gitea, Bitbucket) la configuración se llama distinto pero los conceptos son los mismos:

Regla de protecciónQué impide
Prohibir push directo a mainCommits sin revisión llegando a la rama estable
Revisión obligatoria (mínimo 1, idealmente no la propia)Integrar sin que nadie lo haya leído
Status checks de CI obligatoriosQue main se rompa por un cambio no probado
Historia lineal obligatoria (squash/rebase)Merges superfluos y grafos impostables de leer
Prohibir force-push y borrado de la ramaReescrituras accidentales de lo compartido
Ramas al día antes de mergearIntegraciones que "funcionaban" contra una base vieja
Commits firmados (opcional)Suplantación de autoría
Local vs servidor: reparto de responsabilidades

Local (tuyo, tu máquina): alias, editor, hooks para feedback rápido, pull.rebase.
Servidor (compartido, no negociable): revisión, CI, protección de rama, prohibición de force-push.
Un flujo de equipo sano tiene ambos: el local para que trabajar sea cómodo y el cambio llegue bien a la primera; el del servidor para que "la primera" no dependa de la buena voluntad de nadie.

3 · Ejemplo mínimo

El hook commit-msg más pequeño que ya sirve: exigir el prefijo de Conventional Commits.

# .githooks/commit-msg
#!/usr/bin/env bash
msg_file="$1"
asunto="$(head -n1 "$msg_file")"

if [[ ! "$asunto" =~ ^(feat|fix|docs|chore|refactor|test)(\(.+\))?!?:\ .+ ]]; then
  echo "✖ Mensaje invalido: $asunto" >&2
  echo "  Usa Conventional Commits. Ejemplo: feat(busqueda): filtrar sin mayusculas" >&2
  exit 1
fi
git config --local core.hooksPath .githooks

git commit --allow-empty -m "cambios"
# ✖ Mensaje invalido: cambios
#   Usa Conventional Commits. Ejemplo: feat(busqueda): filtrar sin mayusculas
# El commit NO se ha creado.

git commit --allow-empty -m "chore: probar el hook"
# [main 3f9a1c2] chore: probar el hook

Qué esperamos ver: el primer commit se rechaza con un mensaje claro y el segundo pasa. El hook no ha necesitado nada más: un fichero, un core.hooksPath local y una salida distinta de cero.

4 · Ejemplo real

El paquete completo del proyecto final: un CONTRIBUTING.md de una página, la carpeta .githooks/ con el hook robusto y el script de instalación. Este es el entregable de la lección.

Documento de flujo: CONTRIBUTING.md

# Cómo contribuir a taller

## Ramas
Siempre desde `main`, cortas (menos de 3 días), con prefijo de tipo:

    feature/  fix/  hotfix/  chore/  docs/  refactor/

Formato: `tipo/descripcion-corta-en-minusculas` (guiones, sin espacios).
Si hay issue: `fix/142-descripcion`.

## Commits
Conventional Commits: `tipo(scope): descripcion en imperativo`.

    feat(busqueda): filtrar notas ignorando mayusculas
    fix(api): evitar 500 al listar sin texto
    docs: explicar el modelo de objetos

Tipos: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert.
Un commit = un cambio coherente. Si dudas, haz dos commits.

## Pull Requests
- Titulo = el asunto de Conventional Commits mas representativo.
- Descripcion: que cambia, por que, como probarlo, riesgos.
- Pequeno: < 400 lineas si es posible. Grande = dificil de revisar = mas bugs.
- CI en verde antes de pedir revision.
- La persona autora NO mergea su propio PR.

## Integracion
- `main` esta protegida: no se empuja directo.
- Squash merge por defecto: el PR entra como UN commit limpio.
- Borra la rama tras el merge (el remoto tambien).

## Antes de pedir revision
    git fetch --prune
    git rebase origin/main        # o merge: lo que diga este documento
    git lg --oneline -5
    # y ejecuta los tests en local

## Herramientas locales
- `scripts/setup.sh` activa los hooks versionados (`.githooks/`).
- `git config pull.rebase true` (recomendado).

El hook robusto: .githooks/commit-msg

#!/usr/bin/env bash
# .githooks/commit-msg — exige Conventional Commits en el asunto.
# Se salta con: git commit --no-verify   (es feedback, no una jaula)
set -u

msg_file="${1:?falta el fichero del mensaje}"
asunto="$(head -n1 "$msg_file")"

# Permitir automatismos y casos legitimos que no siguen la convencion:
case "$asunto" in
  Merge\ *|Revert\ *|fixup!*|squash!*|"") exit 0 ;;
esac

tipos='feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert'
regex="^(${tipos})(\([a-z0-9._/-]+\))?!?: .+"

if ! [[ "$asunto" =~ $regex ]]; then
  echo "" >&2
  echo "  ✖ Mensaje no valido:" >&2
  echo "    ${asunto}" >&2
  echo "" >&2
  echo "  Usa Conventional Commits:" >&2
  echo "    tipo(scope): descripcion en imperativo" >&2
  echo "    ej: feat(busqueda): filtrar notas ignorando mayusculas" >&2
  echo "    tipos: feat fix docs style refactor perf test build ci chore revert" >&2
  echo "" >&2
  exit 1
fi

# Aviso (no bloquea) si el asunto es largo o no esta en imperativo.
if [ "${#asunto}" -gt 72 ]; then
  echo "  ⚠ Asunto de ${#asunto} caracteres: apunta a 72 o menos." >&2
fi

exit 0

Instalación versionada: scripts/setup.sh

#!/usr/bin/env bash
# scripts/setup.sh — activar los hooks versionados y ajustes del proyecto.
set -euo pipefail

git config --local core.hooksPath .githooks
# En Linux/macOS, asegura el bit de ejecucion del hook en el indice:
git ls-files --error-unmatch .githooks/commit-msg >/dev/null 2>&1 \
  && git update-index --chmod=+x .githooks/commit-msg || true

echo "✔ Hooks activados en .githooks/  (core.hooksPath local)"
echo "  Para saltar un commit concreto: git commit --no-verify"
$ bash scripts/setup.sh
✔ Hooks activados en .githooks/  (core.hooksPath local)
  Para saltar un commit concreto: git commit --no-verify

$ git config --local --show-origin core.hooksPath
file:.git/config        core.hooksPath=.githooks

Protección de main: la parte que no se ve en el repo

Ninguno de los archivos anteriores impide nada por sí solo. La protección de main se configura en el servidor y se documenta en el CONTRIBUTING.md para que nadie se sorprenda:

Rama protegida: main
  ☑ Require a pull request before merging
  ☑ Require approvals: 1   (dismiss stale approvals on new commits)
  ☑ Require status checks to pass: lint, test, build
  ☑ Require branches to be up to date before merging
  ☑ Require linear history (squash o rebase; sin merge commits)
  ☑ Do not allow force pushes
  ☑ Do not allow deletions
  ☐ Require signed commits   (opcional, si el equipo firma)

Nota: los hooks locales (.githooks/) NO sustituyen estas reglas.
      Son feedback temprano; esto es la barandilla.
Verifica que la protección funciona

Prueba de humo: intenta git push origin main directamente tras la configuración. El servidor debe rechazarlo con un mensaje del tipo "protected branch". Si el push pasa, tu flujo es decorativo. Esta comprobación vale más que todo el documento.

6 · Errores habituales

1. Confiar la disciplina solo a los hooks locales

Mal — creer que el hook impide commits malos 
# El equipo confia en .githooks/commit-msg como unica defensa.
git commit --no-verify -m "wip"     # el hook se salta con --no-verify
# Y si no se versiona el hook: los clones nuevos ni lo tienen.
ls .git/hooks/commit-msg.sample     # .sample = INACTIVO: no hace nada.
Bien — hook para el feedback, protección en el servidor 
# 1) Feedback rapido y consistente en local:
git config --local core.hooksPath .githooks
# 2) Barrera real en el servidor: PR obligatorio + CI + revision + sin bypass.
# 3) Verificacion: git push origin main debe ser RECHAZADO.

2. core.hooksPath en global

Mal — una regla de un proyecto aplicada a todos 
git config --global core.hooksPath .githooks
# Ahora TODOS tus repos buscan .githooks en su raiz. Los que no lo tengan
# quedan sin hooks; peor aun, los que tengan su propia carpeta con OTRO
# contenido empiezan a ejecutar el hook equivocado.
Bien — configuración local (por repositorio) 
git config --local core.hooksPath .githooks
git config --local --get core.hooksPath      # .githooks
# Y si tienes varios proyectos, cada scripts/setup.sh activa el suyo.

3. Un flujo que nadie puede cumplir

Mal — reglas imposibles o contradictorias 
# CONTRIBUTING.md
- Cada commit debe pasar 40 minutos de CI antes de subirse.   # imposible
- Ramas de vida maxima: 1 dia, aunque la feature sea grande.   # inviable
- Prohibido `--force-with-lease` en las propias ramas.         # contraproducente
- Revisiones de 2 personas para cambios de una linea.         # desproporcionado
Bien — reglas proporcionadas y automatizables 
# CONTRIBUTING.md
- PR con CI en verde antes de revision (status checks obligatorios).
- Ramas cortas: si supera ~400 lineas, dividir el PR.
- Reescritura permitida en ramas propias con `--force-with-lease`.
- 1 revision; 2 solo si `main` esta congelada o es un cambio de seguridad.

4. Dejar el hook sin versionar (o sin permiso de ejecución)

Mal — un hook que solo funciona en tu máquina 
cp hook.sh .git/hooks/commit-msg     # .git/ no se versiona: muere con el clon
chmod +x commit-msg                  # ...y en Windows/Git Bash el bit no viaja
# Resultado: el resto del equipo no tiene la validacion y no lo sabe.
Bien — versionar y activar explícitamente 
mkdir -p .githooks
git add .githooks/commit-msg
git update-index --chmod=+x .githooks/commit-msg    # bit +x en el indice
git commit -m "chore(tooling): anadir hook commit-msg versionado"
# Y en el README: "ejecuta bash scripts/setup.sh una vez".

7 · Ejercicio guiado

Objetivo: dejar el taller con un flujo escrito, un hook funcional y una comprobación de que la protección es real.

  1. Paso 1 — Escribe el documento de flujo: 
    cd taller
# Crea CONTRIBUTING.md con el contenido de la seccion 4,
# adaptando nombres y política de integracion a tu proyecto.
$EDITOR CONTRIBUTING.md
head -20 CONTRIBUTING.md
  2. Paso 2 — Crea y versiona el hook: 
    mkdir -p .githooks
$EDITOR .githooks/commit-msg     # pega el script de la seccion 4
git add .githooks/commit-msg
git update-index --chmod=+x .githooks/commit-msg
git commit -m "chore(tooling): anadir hook commit-msg versionado"

    Si core.hooksPath aún no está activo, el commit de este paso pasará sin validarse: es normal, el hook todavía no está enganchado.

  3. Paso 3 — Actívalo y comprueba que rechaza: 
    git config --local core.hooksPath .githooks
git commit --allow-empty -m "cambios"
# ✖ Mensaje no valido: cambios ... y el commit NO se crea (exit 1)

git commit --allow-empty -m "feat(busqueda): probar el hook"
# [main ...] feat(busqueda): probar el hook
git log --oneline -1

    Resultado esperado: el mensaje pobre se rechaza con un texto explicativo y el conforme pasa. Verifica también la válvula: git commit --allow-empty --no-verify -m "wip" debe pasar (aunque no lo quieras en la historia).

  4. Paso 4 — Prueba los casos límite del hook: 
    git commit --allow-empty -m "Merge branch 'main'"
git commit --allow-empty -m "fixup! feat(busqueda): probar el hook"
git commit --allow-empty -m "feat: sin scope tambien vale"
git commit --allow-empty -m "feat(x)!: breaking change"
git commit --allow-empty -m "Feature: con mayuscula"
#   ↑ este debe fallar: el tipo va en minusculas

    Resultado esperado: los cuatro primeros pasan (merges y fixups están exentos), el último se rechaza. Un hook útil distingue "no es convención" de "no es un commit normal".

  5. Paso 5 — Comprueba el reparto local/servidor: 
    git config --local --show-origin core.hooksPath
git config --global --get core.hooksPath      # debe estar VACIO
git remote -v                                 # si hay remoto, prueba un push directo a main
# git push origin main   -> debe ser rechazado si la rama esta protegida

    Resultado esperado: el hooksPath vive solo en el repo (file:.git/config) y no hay valor global. Si tienes remoto con protección, el push directo a main falla: esa es la barandilla real.

  6. Paso 6 — Publica el flujo: 
    git switch -c chore/flujo-de-equipo
git add CONTRIBUTING.md scripts/setup.sh
git commit -m "docs: definir el flujo de trabajo y los hooks"
git push -u origin chore/flujo-de-equipo
# Abre el PR siguiendo TU PROPIO flujo: titulo, descripcion, CI en verde.

    Resultado esperado: el propio PR pone a prueba el documento: si algo no cuadra al abrirlo, corrige el CONTRIBUTING.md antes de mergear.

8 · Reto

🎯 Un flujo que se comprueba solo

Añade al taller un segundo hook, .githooks/pre-push, que rechace el push si se cumplen cualquiera de estas condiciones: (a) la rama destino es main; (b) algún commit del rango que se va a subir tiene un asunto que no cumple Conventional Commits; (c) alguno de esos commits modifica un fichero mayor de 5 MB. Además, escribe scripts/verificar-flujo.sh que compruebe, sin red, que (1) core.hooksPath está activo y apunta a .githooks, (2) los hooks tienen el bit de ejecución en el índice, y (3) el CONTRIBUTING.md contiene las secciones obligatorias (ramas, commits, PRs, integración). El script debe fallar con código distinto de cero si algo falta.

Pista: en pre-push recibes por stdin las líneas <local ref> <local sha> <remote ref> <remote sha>; para el punto (b) puedes recorrer $(git rev-list --no-merges "$remote_sha..$local_sha") y validar cada asunto con la misma regex del commit-msg (extrae la validación a un script común para no duplicarla). Para el tamaño, git cat-file -s <blob> o git ls-tree -lr <commit> te dan los bytes. Recuerda: también esto es feedback local, la barrera sigue estando en el servidor.

9 · Resumen

  • Un flujo se define con cinco decisiones: rama de integración, ramas de trabajo, nombres, integración y puertas de calidad.
  • Ramas cortas desde main, con prefijo de tipo (feature/, fix/, hotfix/, chore/, docs/, refactor/).
  • El hook commit-msg valida Conventional Commits y cancela el commit si el asunto no cumple.
  • Los hooks se versionan en .githooks/ y se activan con core.hooksPath local (nunca global).
  • Los hooks locales son feedback; cualquiera los salta con --no-verify.
  • La barrera real está en el servidor: PR obligatorio, revisión, CI, historia lineal, sin force-push.
  • El entregable: CONTRIBUTING.md + .githooks/commit-msg + scripts/setup.sh, y una prueba de humo que confirme que push directo a main se rechaza.

10 · Preguntas frecuentes

¿Los hooks se pueden saltar? ¿Para qué sirven entonces?

Se saltan con --no-verify (y quien no los tenga instalados tampoco los ejecuta). Sirven para feedback barato y temprano: te enteras del error de formato en tu máquina, en un segundo, en vez de en el CI cinco minutos después. La obligación la impone el servidor con status checks y revisiones obligatorias. Hook = cartel; protección = barandilla.

¿core.hooksPath o un gestor tipo husky/pre-commit?

Para un proyecto sin dependencias de Node, core.hooksPath es lo más simple: cero dependencias, un scripts/setup.sh y listo. Un gestor (husky, pre-commit, lefthook) añade instalación automática, hooks por lenguaje y ejecución en paralelo, a cambio de una dependencia más. Cualquiera de las dos es válida; lo que no es válido es no versionar los hooks.

¿Squash, merge o rebase para integrar?

Es una decisión de equipo, no una verdad absoluta. Squash deja un commit por PR en main (historia limpia y fácil de revertir; pierdes los commits intermedios). Merge commit preserva la topología y el contexto de la rama (grafo más ruidoso). Rebase integra lineal pero reescribe los hashes de la rama (solo en ramas propias). Elige una, documéntala y actívala en la protección de rama ("require linear history" para squash/rebase).

¿Cómo protejo main si no uso GitHub/GitLab?

Los conceptos son los mismos en cualquier servidor de Git. Con Git "pelado" y SSH, la barrera se hace con un hook pre-receive o update en el repositorio bare del servidor: allí sí es infranqueable, porque corre en la máquina remota y no depende de la configuración de nadie. Las forjas son, en el fondo, una interfaz cómoda sobre esos hooks del servidor más políticas.

¿Y si el equipo no quiere escribir nada de esto?

Empieza por lo mínimo que ya aporta valor sin discusión: (1) nombres de rama con prefijo, (2) un PR siempre antes de main, (3) main protegida sin push directo. Eso cabe en tres líneas de CONTRIBUTING.md y resuelve el 80% de los problemas reales. El resto (hooks, changelog, SemVer) se añade cuando duela; un flujo que no se usa no protege a nadie.
