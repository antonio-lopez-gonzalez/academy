Auditoría de un repositorio

Módulo 7 · Proyecto final 🕐 40 minutos

1 · Introducción

Empieza el proyecto final. Tienes un repositorio, el taller, que ha crecido durante todo el curso: mensajes a medio escribir, un par de binarios versionados por accidente, ramas que ya nadie recuerda, un .gitignore con agujeros. Antes de limpiar nada hay que medir. Esta lección es pura diagnosis: cómo mirar un repositorio y saber, en veinte minutos, qué tiene roto y cuánto duele.

La auditoría se hace sin escribir en el repositorio. Todos los comandos de aquí son de lectura. El entregable es un informe, no un cambio: separar "observar" de "arreglar" es lo que distingue a quien limpia de quien rompe.

¿Por qué auditar antes de tocar?

Porque casi todas las limpiezas de historia se hacen mal por el mismo motivo: alguien empieza por el comando (rebase, filter-repo, rm --cached) sin saber cuál es el problema real. La auditoría te da el orden de intervención: primero lo barato y seguro (índice, .gitignore), después lo estructural (ramas), y solo al final, si toca, lo que reescribe historia —y solo en local.

Errores típicos de una auditoría

Confundir "repo desordenado" con "repo roto" (casi nunca está roto); auditar solo main y olvidar las ramas remotas huérfanas; y proponer como remedio un push --force a una rama compartida. Verás que los arreglos de la lección 02 evitan todos ellos.

2 · Teoría

Qué es un repositorio "sucio"

"Sucio" no significa que falle: significa que estorba. Se ensucia por cuatro vías distintas, y cada una pide un diagnóstico y un remedio diferentes:

EjeSíntomaDuele en…
Historia ilegible Mensajes "fix", "wip", "cambios"; commits que mezclan cinco cosas Investigar, revertir, generar changelogs
Contenido indebido Binarios, node_modules, dist/, credenciales, ficheros generados Velocidad de clone, revisiones, seguridad
Refs muertas Ramas locales nunca mergeadas, ramas remotas ya borradas, tags viejos Claridad del grafo, "¿esta rama está viva?"
Fronteras difusas .gitignore flojo, sin .gitattributes, finales de línea mezclados Ruido en cada diff, status inmanejable

El mapa de la auditoría

                    AUDITORIA DEL REPOSITORIO
                             │
   ┌─────────────┬───────────────┬──────────────┬─────────────────┐
   │  TAMANO Y   │   HISTORIA    │   REFS Y     │   FRONTERAS     │
   │  OBJETOS    │   (GRAFO)     │   RAMAS      │  (.gitignore)   │
   └─────────────┴───────────────┴──────────────┴─────────────────┘
        │              │               │                 │

  rev-list         --stat          for-each-ref      ls-files -i
  batch-check      --grep          --merged          .gitattributes

Eje 1 — Tamaño y objetos

Primer dato: cuánto ocupa la historia. git count-objects -vH da un resumen en unidades legibles.

git count-objects -vH
count: 0
size: 0 bytes
in-pack: 4123
packs: 2
size-pack: 184.72 MiB        ← el historial comprimido: AQUI se ve el problema
prune-packable: 0
garbage: 0
size-garbage: 0 bytes

Un repositorio de código fuente de 5 000 líneas que pesa 180 MB tiene algo grande dentro. Para saber qué, se listan los blobs más pesados de toda la historia:

git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1=="blob" { print $3, $4 }' \
  | sort -n \
  | tail -15

Ese pipeline es el estándar de facto para "¿qué demonios pesa tanto?". --objects --all enumera cada objeto alcanzable; batch-check pide tipo y tamaño; awk se queda con los blobs; y sort | tail deja arriba los quince más gordos, en bytes.

El binario borrado sigue ahí

Aunque hayas borrado el .zip en un commit posterior, el blob sigue en el objeto de la historia: Git es inmutable. Por eso lo verás en esta lista aunque git ls-files ya no lo muestre. Detectar esto es exactamente el objetivo del eje 1, y arreglarlo bien (o no tocararlo) es el tema de la lección 02.

Eje 2 — Historia y mensajes

¿Se puede leer esta historia? Dos medidas rápidas: el ranking de autores y una muestra de asuntos.

git log --oneline | wc -l                     # numero total de commits
git shortlog -sn --no-merges                  # quien y cuanto
git log --no-merges --pretty=format:'%h %s' | head -40   # muestra de mensajes

# Cuantos commits NO siguen Conventional Commits (feat:, fix:, docs:...):
git log --no-merges --pretty=%s | grep -cvE '^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\(.+\))?!?: '
$ git log --no-merges --pretty=%s | grep -cE '^(feat|fix|docs)(\(.+\))?!?: '
6
$ git log --oneline | wc -l
14
# 6 de 14 asuntos son conformes: el 57% de la historia no lo es.

Para medir el tamaño de cada commit (si mezclan cosas) basta con --stat:

git log --no-merges --shortstat --pretty='%h %s' | head -30
# Commits con 30 ficheros cambiados y un asunto "cambios" = commits no atomicos.

Eje 3 — Refs y ramas

Tres preguntas: ¿qué ramas hay? ¿están vivas? ¿dónde apuntan?

git branch -a                    # locales y remotas
git branch -vv                   # con upstream y estado de seguimiento

# Ramas ordenadas por ultima actividad, con su upstream:
git for-each-ref --sort=-committerdate refs/heads \
  --format='%(committerdate:short) %(refname:short) %(upstream:short) %(upstream:track)'

# Ramas locales ya mergeadas en main (candidatas a borrar):
git branch --merged main
# Ramas que NO estan mergeadas en main (pueden tener trabajo sin integrar):
git branch --no-merged main
$ git branch -vv
  feature/busqueda  4b7e0d1 [origin/feature/busqueda: gone] feat: filtrar notas
* main              9f1c2ab [origin/main] docs: explicar el indice
  pruebas-locales   2c9a1f3 feat: campo tags al modelo

El marcador [gone] es oro: significa que la rama remota ya no existe (la borraron tras el merge) pero tu copia local sigue. Y pruebas-locales sin upstream es una rama que quizá nunca se publicó ni se va a integrar: candidata a decisión (borrar o resucitar) en la lección 02.

Distinguir tres clases de "rama muerta"

(1) Mergeada y sin remoto: trabajo ya integrado, se puede borrar sin más. (2) Mergeada pero con upstream [gone]: el remoto la limpió; borra la local y, si quieres, deja que fetch.prune haga su parte (lección 04 del módulo 6). (3) Sin mergear y sin upstream: aquí no decidas a la ligera; puede ser trabajo sin integrar. Se investiga con git log main..rama antes de tocar nada.

Eje 4 — Fronteras: .gitignore y finales de línea

El .gitignore flojo se detecta con dos comandos:

# (a) Ficheros ignorados: ¿esta bien ignorado lo que creias?
git status --short --ignored | head -30

# (b) Ficheros RASTREADOS que ademas estan ignorados: el sintoma clasico
git ls-files -i -c --exclude-standard
#    Si sale algo aqui, se anadio al repo ANTES de la regla y la regla no le afecta.

# (c) Ficheros sin rastrear y NO ignorados: lo que se colaria en el proximo add .
git ls-files -o --exclude-standard | head -30

# (d) Por que esta ignorado (o no) un fichero concreto:
git check-ignore -v node_modules/ debug.log dist/
$ git ls-files -i -c --exclude-standard
node_modules/express/package.json
dist/bundle.js
# ↑ dos directorios que se versionaron antes de crear el .gitignore.

$ git check-ignore -v node_modules/express/package.json
# (sin salida)  ← no esta ignorado: por eso sigue ensuciando el status

Y los finales de línea, que causan diffs fantasma:

test -f .gitattributes && cat .gitattributes || echo "SIN .gitattributes"
git ls-files --eol | head -20
# i/lf  w/crlf  attr/  ← "i" = indice, "w" = directorio de trabajo
Ficheros ya rastreados que deberían ignorarse

Ese es el diagnóstico estrella del eje 4: un .gitignore no "desrastrea" nada. Si un archivo ya está en el índice, la regla lo ignora para futuros avisos, pero Git sigue gestionándolo. El remedio (git rm --cached) está en la lección 02; aquí solo lo detectamos.

Comandos de diagnóstico: chuleta

PreguntaComando
¿Cuánto pesa la historia?git count-objects -vH
¿Qué objeto es el más grande?git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n | tail
¿Qué binarios están versionados?git ls-files '*.zip' '*.png' '*.jar' '*.exe' '*.pdf'
¿Hay mensajes pobres?git log --no-merges --pretty=%s | grep -cvE '^(feat|fix|…): '
¿Qué ramas hay y cuáles están muertas?git branch -vv + git branch --merged main
¿Qué ignora el repo y qué se cuela?git status --short --ignored

¿Por qué está ignorado un fichero?git check-ignore -v <ruta>

3 · Ejemplo mínimo

La foto mínima de un repositorio, en cinco comandos que no modifican nada:

git status --short --branch       # 1. ¿limpio o con trabajo suelto?
git count-objects -vH             # 2. ¿cuanto pesa?
git branch -a -vv                 # 3. ¿cuantas ramas y estan vivas?
git shortlog -sn --no-merges      # 4. ¿quien ha trabajado y cuanto?
git ls-files -o --exclude-standard | head   # 5. ¿que se colaria en el proximo add .?
$ git status --short --branch
## main...origin/main [ahead 2]
?? notas-viejas.md
?? debug.log

$ git count-objects -vH
in-pack: 4123
size-pack: 184.72 MiB

$ git ls-files -o --exclude-standard
notas-viejas.md
debug.log
node_modules/express/package.json   # ← ¡no esta ignorado!

Qué esperamos ver: con estos cinco números ya tienes la hipótesis principal de cada eje. Aquí: hay ficheros que se cuelan (node_modules no está ignorado), la historia pesa demasiado para el tamaño del código, y hay dos commits locales sin publicar. Es una auditoría de treinta segundos; el resto de la lección la completa con detalle.

4 · Ejemplo real

Una auditoría completa del taller, convertida en el entregable del proyecto: un script de diagnóstico que no escribe nada y un informe en Markdown. Primero el script:

#!/usr/bin/env bash
# scripts/auditoria.sh — diagnostico de SOLO LECTURA del repositorio.
# No modifica el arbol de trabajo, ni el indice, ni las refs.
set -u

echo "=============================================="
echo " AUDITORIA DE $(basename "$(git rev-parse --show-toplevel)")"
echo "=============================================="

echo "--- 1. TAMANO Y OBJETOS ---------------------------------"
git count-objects -vH | grep -E 'in-pack|size-pack|count|size:'
echo "commits totales: $(git rev-list --count --all)"
echo "top-5 blobs mas grandes de la HISTORIA (bytes):"
git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1=="blob" { print $3, $4 }' | sort -n | tail -5

echo "--- 2. CONTENIDO INDEBIDO -------------------------------"
echo "binarios / generados versionados:"
git ls-files '*.zip' '*.png' '*.jpg' '*.pdf' '*.jar' '*.exe' '*.dll' '*.psd' '*.mp4' | head -20
echo "node_modules o dist indexados:"
git ls-files node_modules dist | head -5

echo "--- 3. HISTORIA Y MENSAJES ------------------------------"
git shortlog -sn --no-merges
total=$(git log --no-merges --oneline | wc -l)
conformes=$(git log --no-merges --pretty=%s | grep -cE '^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\(.+\))?!?: ')
echo "asuntos conformes a Conventional Commits: $conformes / $total"

echo "--- 4. REFS Y RAMAS -------------------------------------"
git branch -vv
echo "locales mergeadas en main:"; git branch --merged main | grep -v '\*'
echo "locales NO mergeadas en main:"; git branch --no-merged main
echo "tags:"; git tag -l --sort=-creatordate | head -10

echo "--- 5. FRONTERAS (.gitignore / .gitattributes) ----------"
if [ -f .gitattributes ]; then echo ".gitattributes presente"; else echo "SIN .gitattributes"; fi
echo "ficheros RASTREADOS y ademas ignorados (deberian salir del indice):"
git ls-files -i -c --exclude-standard | head -20
echo "ficheros sin rastrear y NO ignorados (se colarian con 'git add .'):"
git ls-files -o --exclude-standard | head -20
echo
echo "Fin del diagnostico. Ningun comando ha modificado el repositorio."
Todos los comandos son de lectura — compruébalo

Antes de fiarte, ejecuta git status y git rev-parse HEAD antes y después del script: deben coincidir. Un script de auditoría que cambia el estado no es una auditoría, es una intervención a ciegas.

Segundo, el informe. Este es el entregable de la lección: un Markdown con hallazgos, evidencia y riesgo, sin proponer todavía los arreglos (eso es la lección 02).

# Informe de auditoría — taller
Fecha: 2026-02-18
Commit auditado: 9f1c2ab

## 1. Resumen ejecutivo
Repositorio pequeño (14 commits) pero con tres focos de suciedad:
historia con mensajes pobres (57% no conformes), `node_modules` versionado,
y dos ramas locales sin integrar.

## 2. Hallazgos por eje

### 2.1 Tamaño y objetos
- `size-pack`: 184.72 MiB para ~5 000 líneas de código. **Anómalo.**
- Blob más grande: `assets/video-demo.mp4` (142 MiB) en el commit `1a2b3c4`.
- Evidencia: `git rev-list --objects --all | git cat-file --batch-check=... | sort -n | tail`
- Riesgo: **alto**. Cada clon descarga 184 MB.

### 2.2 Contenido indebido
- `node_modules/` (312 ficheros) y `dist/` están **rastreados**.
- `debug.log` sin ignorar: se colará en el próximo `git add .`.
- Evidencia: `git ls-files node_modules dist`, `git ls-files -o --exclude-standard`
- Riesgo: **medio**. Ruido en diffs y en revisiones.

### 2.3 Historia y mensajes
- 8 de 14 asuntos no siguen Conventional Commits (p. ej. "fix", "wip", "cambios").
- Dos commits tocan > 20 ficheros (no atómicos).
- Evidencia: `git log --no-merges --pretty=%s | grep -cvE '...'`
- Riesgo: **medio**. Dificulta `revert`, `bisect` y changelogs.

### 2.4 Refs y ramas
- `feature/busqueda`: mergeada en `main`, upstream `[gone]`.
- `pruebas-locales`: sin upstream, 1 commit no mergeado.
- `v0.1.0`, `v0.2.0`: tags correctos. Sin tags ligeros.
- Riesgo: **bajo** (pruebas-locales requiere revisión manual, no borrado ciego).

### 2.5 Fronteras
- Sin `.gitattributes`: finales de línea mixtos (CRLF/LF en `src/`).
- `.gitignore` ignora `dist/` pero el directorio ya está indexado (regla inútil
  hasta hacer `rm --cached`).
- Riesgo: **medio**. Diffs fantasma por fin de línea.

## 3. Orden de intervención propuesto
1. `rm --cached` + `.gitignore`/`.gitattributes` (barato, reversible, sin historia).
2. Limpieza de ramas locales (decisión por rama, no en bloque).
3. Historia local de la rama propia (`rebase -i`), solo si no está publicada.
4. NO tocar el video ya publicado sin leer la sección de riesgo del informe.

## 4. Riesgos y límites
- El binario de 142 MB está en la historia: borrarlo del pasado **reescribe
  historia** y rompe a cualquiera que la tenga. Decisión de equipo, no individual.
Un informe separa el qué del cómo

Fíjate en que el informe no dice cómo se arregla: dice qué está mal, cómo lo demuestras y cuánto duele. Esa separación es profesional: el equipo decide con el informe delante; la ejecución es otra conversación (y otra lección).

5 · Buenas prácticas

PrácticaPor qué
Audita en solo lectura y dilo en el informe La confianza del equipo empieza por "no he tocado nada"; el informe prueba el estado inicial
Fija el commit auditado git rev-parse HEAD da trazabilidad: el informe vale para un estado concreto
Mide antes de opinar "Los mensajes son malos" es una opinión; "8 de 14 no cumplen la convención" es un dato que se arregla
Prioriza por riesgo, no por gusto Primero lo que rompe clones o filtra secretos; el estilo se puede esperar
Distingue "publicado" de "solo local" Determina si el arreglo puede reescribir historia o debe ir con revert/rm --cached
Anota la evidencia (comando + salida) Sin evidencia reproducible, el hallazgo es una sospecha; con ella, es un hecho
No confundas tamaño con suciedad Un binario pequeño y necesario no es un problema; un binario de 142 MB sí
Detecta secretos, no los purgues aquí

Buscar credenciales en la historia es legítimo y forma parte de la auditoría (git log -p -S"AKIA", git log -p -S"PRIVATE KEY"). Pero purgar un secreto ya publicado no se resuelve con un comando de esta lección: exige coordinar una reescritura masiva, rotar el secreto y avisar a todo el mundo. Ese procedimiento es delicado y tiene documentación oficial propia (rewriting history / removing sensitive data en la documentación de Git). Aquí, decláralo en el informe como riesgo crítico y rota la credencial: rotar es lo único que te protege de verdad.

6 · Errores habituales

1. Curiosear el historial con comandos que escriben

Mal — "mirar" con comandos que mueven cosas 
git checkout main                # estas moviendo TU HEAD para "mirar"
git reset --hard origin/main     # y esto ya borra trabajo local sin avisar
# Antes de auditar, asegura que estas en solo-lectura.
Bien — lectura pura, sin mover refs ni indice 
git status --short --branch
git log --oneline --graph --decorate --all
git branch -a -vv
git count-objects -vH
# Ninguno de estos cambia el estado del repositorio.

2. Confiar en git ls-files para detectar binarios grandes

Mal — solo mira el árbol actual 
git ls-files -z | xargs -0 du -h | sort -rh | head
# Esto lista el arbol ACTUAL: un video borrado hace 3 meses NO aparece...
# ...aunque siga pesando 142 MB en la historia y en cada clon.
Bien — mira toda la historia, no solo el presente 
git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1=="blob" { print $3, $4 }' | sort -n | tail -10
# Ahora si: incluye blobs de commits antiguos que ya no estan en el arbol.

3. Tratar todas las ramas "viejas" igual

Mal — borrar en bloque por antigüedad 
# "no se tocan hace un mes: fuera todas"
git branch | xargs git branch -D
# Puede borrar trabajo no integrado (pruebas-locales) y deja el reflog como unica
# red de rescate. Prohibido sin revisar rama por rama.
Bien — clasifica por merge y por upstream 
git branch --merged main        # candidatas seguras a borrar
git branch --no-merged main     # revisar: git log main..<rama> antes de decidir
git branch -vv                  # marca las [gone] como listas para limpiar

4. Concluir "hay que reescribir la historia" en la auditoría

Mal — el informe proponiendo push --force 
## 3. Plan
- `git filter-repo --path video.mp4 --invert-paths`
- `git push --force origin main`   ← NUNCA sobre una rama compartida
# Y menos sin avisar: cualquiera que haya hecho fetch pierde su trabajo.
Bien — el informe acota riesgo y remite a decisión 
## 3. Plan
- Limpieza sin reescritura: `rm --cached`, `.gitignore`, `.gitattributes` (seguro).
- Reescritura del binario del pasado: **requiere decisión de equipo**;
  afecta a ramas publicadas. Ver documentación oficial de "rewriting history".
- Mientras tanto: rotar cualquier credencial expuesta y avisar al equipo.

7 · Ejercicio guiado

Objetivo: auditar el taller de arriba abajo y producir el informe de auditoría con evidencia real.

  1. Paso 1 — Congela el estado y anota el punto de partida: 
    cd taller
git rev-parse HEAD > informe/commit-auditado.txt
git status --short --branch
mkdir -p informe

    Resultado esperado: dos ficheros en informe/ (el commit auditado) y el estado anotado. Nada del repositorio se ha modificado.

  2. Paso 2 — Eje 1 (tamaño y objetos): 
    git count-objects -vH | tee informe/eje1-tamano.txt
git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1=="blob" { print $3, $4 }' | sort -n | tail -10 | tee -a informe/eje1-tamano.txt

    Resultado esperado: identificas el blob más pesado y el commit donde vive. Si el taller de referencia tiene assets/video-demo.mp4, ese es el candidato.

  3. Paso 3 — Eje 2 (contenido indebido): 
    git ls-files '*.zip' '*.png' '*.jpg' '*.pdf' '*.jar' '*.exe' '*.dll' '*.psd' '*.mp4'
git ls-files node_modules dist
git ls-files -o --exclude-standard

    Resultado esperado: la lista de binarios y directorios generados que están en el índice. Anótala tal cual en el informe: es la evidencia.

  4. Paso 4 — Eje 3 (historia y mensajes): 
    git shortlog -sn --no-merges
git log --no-merges --shortstat --pretty='%h %s' | head -30
total=$(git log --no-merges --oneline | wc -l)
conformes=$(git log --no-merges --pretty=%s | grep -cE '^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\(.+\))?!?: ')
echo "conformes: $conformes de $total"

    Resultado esperado: un porcentaje de cumplimiento de Conventional Commits y la lista de commits "gordos" que no son atómicos.

  5. Paso 5 — Eje 4 (refs y fronteras): 
    git branch -vv
git branch --merged main | grep -v '\*'
git branch --no-merged main
for r in $(git branch --no-merged main --format='%(refname:short)'); do
  echo "== $r =="; git log --oneline main.."$r"
done
git ls-files -i -c --exclude-standard
git check-ignore -v node_modules dist debug.log || true
test -f .gitattributes && echo "hay .gitattributes" || echo "SIN .gitattributes"

    Resultado esperado: la clasificación de ramas (mergeadas, [gone], sin integrar) y la lista de ficheros rastreados que además están ignorados.

  6. Paso 6 — Redacta el informe: 
    # Copia la plantilla de la seccion 4 en informe/auditoria.md y rellena
# cada apartado con la evidencia que acabas de recoger.
$EDITOR informe/auditoria.md
git status --short     # el informe vive fuera del control de versiones (aun)

    Resultado esperado: un informe/auditoria.md con los cinco ejes, riesgo por eje y el orden de intervención propuesto. Ese documento es el entregable de la lección y la entrada de la lección 02.

No versiones todavía la carpeta informe/

El informe es un borrador de trabajo. Decidir si se versiona (útil para el historial de auditorías) es parte de la conversación de la lección 02, cuando ya tengas el .gitignore y las fronteras en orden.

8 · Reto

🎯 Un auditor que se pueda comparar

Convierte scripts/auditoria.sh en un auditor mecanizable: que escriba la salida en un JSON estable (informe/auditoria.json) con los indicadores clave (commits_total, asuntos_conformes, size_pack_bytes, blob_mayor, ramas_sin_mergear, rastreados_ignorados, tiene_gitattributes). Después ejecútalo sobre otro repositorio cualquiera de la Academy y produce una comparativa: qué indicadores son peores y cuáles mejores, y qué conclusiones cambian. El objetivo es que dos auditorías hechas en semanas distintas se puedan comparar sin leer prosa.

Pista: para el JSON, imprime con printf '{"commits_total": %s, ...}' desde el propio script, en vez de parsear su salida legible. Cuidado con size-pack: git count-objects -v ya da el valor en KiB, mientras que -H lo formatea para humanos. Y recuerda: el auditor sigue sin escribir en el repositorio auditado.

9 · Resumen

  • "Sucio" = estorba, en cuatro ejes: tamaño/objetos, contenido indebido, ramas muertas y fronteras difusas.
  • La auditoría es de solo lectura: se mide, no se toca, y se fija el commit auditado.
  • git count-objects -vH más el pipeline rev-list --objects --all | cat-file --batch-check | sort | tail revelan el blob que engorda la historia.
  • git ls-files -i -c --exclude-standard detecta ficheros rastreados e ignorados: el síntoma estrella de un .gitignore sin efecto.
  • git branch -vv ([gone]) y git branch --merged/--no-merged clasifican las ramas antes de decidir nada.
  • El entregable es un informe con hallazgos, evidencia, riesgo y orden de intervención — sin proponer reescrituras a la ligera.
  • Los secretos se detectan en la auditoría y se rotan siempre; purgarlos de un remoto publicado tiene procedimiento oficial propio y no se improvisa.

10 · Preguntas frecuentes

¿La auditoría puede romper algo?

No, si te ciñes a comandos de lectura. Todos los de esta lección (count-objects, ls-files, branch, log, check-ignore, rev-list, cat-file) no escriben ni en el índice ni en las refs. Evita cualquier reset, checkout, prune o gc durante la fase de diagnosis, y verifica con git status y git rev-parse HEAD antes y después.

¿Por qué git ls-files -i -c encuentra ficheros que .gitignore decía ignorar?

Porque .gitignore solo evita que Git empiece a rastrear un fichero; no deja de rastrear los que ya estaban. -c lista los cached (en el índice) y -i los filtra por las reglas de exclusión: el resultado son los archivos que están en el índice y además ignorados. Son exactamente los que hay que sacar con git rm --cached en la lección 02.

¿Cómo sé si un binario está "publicado" o solo local?

Compara con el remoto: git log --oneline origin/main..HEAD para ver qué commits son locales, y git branch -r --contains <hash> para saber si un commit concreto está en alguna rama remota. Si el binario está en un commit alcanzable desde origin/main (o desde cualquier rama publicada), su limpieza implicaría reescribir historia compartida: decisión de equipo, no individual.

¿Con qué me quedo si solo tengo cinco minutos?

Con la foto mínima: git status --short --branch, git count-objects -vH, git branch -a -vv, git shortlog -sn --no-merges y git ls-files -o --exclude-standard. Esos cinco comandos detectan las cuatro familias de problemas en cualquier repositorio y te dicen por dónde empezar.

¿Sirve esta auditoría para un repositorio ajeno (open source) antes de contribuir?

Totalmente, y es una gran costumbre: --merged/--no-merged te dice qué ramas están vivas, shortlog quién mantiene, log --pretty=%s si siguen una convención de mensajes (que deberás imitar en tu PR) y count-objects si el proyecto tiene un problema de tamaño. Contribuir bien empieza por leer el repositorio, no por abrir un PR.
