Releases y changelog

Módulo 7 · Proyecto final 🕐 40 minutos

1 · Introducción

Última parada del proyecto: convertir la historia limpia de las tres lecciones anteriores en una release. Un número de versión que signifique algo (SemVer), una etiqueta anotada que lo fije, un changelog que se pueda leer sin abrir el log y un push que no arrastre basura. Es el momento en que todo lo aprendido —modelo, commits convencionales, flujo, tags— se ve junto y por escrito.

Y una idea importante: una release no es solo etiquetar. Es un contrato con quien consume tu proyecto: "esto es lo que cambió y esto es lo que puedes esperar". Git te da las herramientas para cumplirlo sin trabajo manual repetitivo.

¿Por qué SemVer y no "v1, v2, v3"?

Porque 1.4.2 comunica tres cosas a la vez: qué generación es (1), qué se añadió (4) y qué se corrigió (2). Quien consume tu librería puede decidir si actualiza sin leer nada: un cambio de PATCH es seguro, un MINOR añade sin romper, un MAJOR puede romper. El número es la primera línea del changelog.

Errores típicos

Usar git push --tags y subir al remoto tags de experimentos; etiquetar con un tag ligero en vez de uno anotado (se pierde autor, fecha y mensaje); y reescribir un tag ya publicado con git tag -f, que es la peor idea de la lección: quien lo descargó tiene un objeto distinto bajo el mismo nombre.

2 · Teoría

Tags: la etiqueta que fija un commit

Una rama avanza; un tag no. Es un nombre que apunta a un commit y se queda ahí para siempre. Hay dos tipos, y la diferencia importa:

TipoCómoQué guarda
Anotado (recomendado) git tag -a v1.0.0 -m "…" Un objeto completo: autor, fecha, mensaje y firma opcional. Es lo que se usa para releases.
Ligero git tag v1.0.0 Solo un puntero al commit. Útil para marcar localmente ("es aquí") sin más. 
  tag LIGERO                       tag ANOTADO
  v1.0.0                           v1.0.0
     │                                │
     │                                ▼
     │                          commit <tag>            ← objeto tag
     │                                │  (autor, fecha, mensaje)
     ▼                                ▼
  commit a1b2c3                    commit a1b2c3          ← el commit marcado

  Un tag anotado es un objeto mas en el almacen: tiene hash propio,
  viaja en el push y se puede verificar con `git tag -v`.

SemVer 2.0.0 en una tabla

El formato es MAJOR.MINOR.PATCH, más dos sufijos opcionales:

   1  .  4  .  2  -  alpha.1  +  build.20260218
   │     │     │      │            │
   MAJOR MINOR PATCH  prerelease   build metadata
   rompe  añade  corrige  "aun no es final"  "solo informativo, no ordena"
   contrato sin romper sin romper
Cambio en tu API públicaSubeDe 1.4.2 pasa a
Rompe la compatibilidad (quitar/renombrar, cambiar comportamiento)MAJOR2.0.0
Añade funcionalidad sin romperMINOR1.5.0
Corrige un bug sin añadir ni romperPATCH1.4.3
Solo documentación o tooling internoNinguno (o PATCH)1.4.2 (o 1.4.3)
Los tres matices que casi todo el mundo olvida

(1) 0.y.z es desarrollo: en 0.x la API no se considera estable y cualquier MINOR puede romper. (2) Al subir MAJOR, MINOR y PATCH se ponen a cero: 1.9.7 tras un breaking pasa a 2.0.0, no a 2.9.7. (3) El orden es numérico por campos, no alfabético: 1.10.0 es posterior a 1.9.0 (por eso un sort de texto de tags miente).

De Conventional Commits a la versión

Si tus commits siguen la convención (lección 03), el salto de versión se puede deducir, y con eso el número deja de ser una opinión:

Encuentras en los commits…SubeRegla
BREAKING CHANGE: en el cuerpo o ! tras el tipoMAJORPrioridad máxima
feat:MINORFuncionalidad nueva
fix:, perf:PATCHCorrección
docs:, chore:, test:, ci:, build:, style:, refactor:Ninguno (salvo que incluyan breaking)No cambian la API pública
 
   v0.9.0 ────────────────── v1.0.0 ─────────── v1.1.0 ──────── v1.1.1
      │                         │                  │               │
      │  BREAKING CHANGE        │   feat: ...      │   fix: ...    │
      │  (o salto a la 1.0)     │   (añade)        │   (corrige)   │
      └─ 0.x → 1.0.0           └─ MINOR           └─ PATCH
Automatizar el salto: herramientas

Existen utilidades que leen tus commits convencionales y calculan versión + changelog: git-cliff, standard-version, semantic-release, commitizen. En esta lección lo haremos a mano para entender el mecanismo; en un proyecto real, adoptar una de ellas ahorra el trabajo repetitivo (y lo hace consistente). Búscalas por nombre y elige según tu ecosistema.

git describe: identificar un commit por su distancia a un tag

Muy útil para builds intermedios: dado un commit que no es un tag, describe busca el tag anotado más cercano y cuenta cuántos commits hay desde él.

git describe --tags                       # v0.2.0-5-g4b7e0d1
git describe --tags --always              # si no hay tags: solo el hash
git describe --tags --dirty               # añade "-dirty" si hay cambios sin commitear
git describe --tags --match 'v*' --long   # restringe a tags con ese patron
$ git log --oneline -8
4b7e0d1 (HEAD) feat(busqueda): filtrar notas por texto
2c9a1f3 feat: anadir campo tags al modelo
7d4f5e6 (tag: v0.2.0) chore: ignorar node_modules

$ git describe --tags
v0.2.0-2-g4b7e0d1
# │       │ │
# │       │ └─ 'g' + hash corto del commit actual
# │       └─── 2 commits por delante del tag
# └─────────── tag anotado mas cercano

Changelog: de los commits al documento

Un changelog no es git log volcado: es una selección curada de lo que le importa a quien consume el proyecto. Con el rango entre dos tags y los asuntos convencionales, se agrupa por tipo:

git log --no-merges --pretty=format:'%s (%h)' v0.2.0..v1.0.0
$ git log --no-merges --pretty=format:'%s (%h)' v0.2.0..v1.0.0
feat(busqueda): filtrar notas ignorando mayusculas (4b7e0d1)
fix(api): evitar 500 al listar sin texto (5c8d2e4)
docs: explicar el indice en notas.md (9f1c2ab)
chore(repo): dejar de versionar generados (7a1b0c9)

Agrupado queda así:

## [1.0.0] - 2026-02-18

### Añadido
- **busqueda**: filtrar notas ignorando mayusculas (4b7e0d1)

### Corregido
- **api**: evitar 500 al listar sin texto (5c8d2e4)

### Cambios internos / documentación
- explicar el indice en notas.md (9f1c2ab)
- dejar de versionar generados (7a1b0c9)
Un changelog se escribe para quien actualiza

La prueba de fuego: "¿alguien puede decidir si actualiza leyendo solo esto?". Si un cambio breaking no está en un apartado visible y marcado como tal, el changelog ha fallado. Por eso la convención agrupa: Añadido (feat), Corregido (fix), Roto (breaking), y "todo lo demás" en un apartado interno que quien consume puede saltarse.

Publicar: push --follow-tags

Un tag local no existe en el remoto hasta que lo empujas. Y aquí hay una trampa clásica:

# ❌ Sube TODOS los tags locales, incluidos los de pruebas
git push --tags

# ✅ Sube los tags ANOTADOS alcanzables desde lo que ya se empuja
git push --follow-tags

# Un tag concreto, si quieres control total
git push origin v1.0.0
Qué hace y qué no hace --follow-tags

Empuja los tags anotados que sean alcanzables desde los commits que se están enviando, y no empuja los tags ligeros. Si etiquetas una rama y aún no has subido el commit etiquetado, --follow-tags no tendrá nada que seguir: sube primero los commits (o usa git push origin v1.0.0 explícito). Actívalo por defecto con git config --global push.followTags true.

Los tags publicados no se mueven

git tag -f v1.0.0 mueve el tag en tu máquina, pero el remoto rechazará el cambio salvo con --force, y quien ya lo descargó seguirá teniendo el objeto antiguo bajo el mismo nombre: dos mundos con la misma versión y contenido distinto. Si un tag salió mal, publica uno nuevo (v1.0.1) y deja el anterior como está. Una versión publicada es historia, y la historia no se reescribe.

3 · Ejemplo mínimo

Etiquetar la release, verla y describir su commit:

cd taller
git switch main
git tag -a v1.0.0 -m "Release 1.0.0: busqueda estable y limpieza del repositorio"
git show v1.0.0 --stat
git describe --tags
$ git tag -a v1.0.0 -m "Release 1.0.0: busqueda estable y limpieza del repositorio"

$ git show v1.0.0 --stat
tag v1.0.0
Tagger: Ana Lopez <ana@example.com>
Date:   Wed Feb 18 12:04:51 2026 +0100

Release 1.0.0: busqueda estable y limpieza del repositorio

commit 9f1c2ab...

$ git describe --tags
v1.0.0

Qué esperamos ver: el tag anotado tiene su propio bloque (tag v1.0.0) con autor, fecha y mensaje, y después el commit señalado. Si solo vieras el commit, sería un tag ligero: le faltaría el objeto. Y describe devuelve exactamente v1.0.0 porque el commit es el tag.

4 · Ejemplo real

El cierre del proyecto: la release 1.0.0 del taller de punta a punta — decisión de versión, changelog generado desde los commits, tag anotado y publicación sin arrastrar nada.

Paso 1 — Decide la versión con datos, no con sensaciones

git fetch --prune
git log --oneline v0.2.0..main             # ¿que ha entrado desde la ultima release?
git log --no-merges --pretty=%s v0.2.0..main | grep -E '^[a-z]+(\(|!|:)' | head
$ git log --no-merges --pretty=%s v0.2.0..main | head
feat(busqueda): filtrar notas ignorando mayusculas
feat(api): exponer /notas/export
fix(api): evitar 500 al listar sin texto
docs: explicar el indice en notas.md
chore(repo): dejar de versionar generados

# Hay 2 'feat' y 1 'fix', y ninguna linea 'BREAKING CHANGE' ni '!':
# seria MINOR (v0.3.0) si partieramos de una 1.x estable.
# Pero el proyecto aun estaba en 0.x: pasamos a 1.0.0 (primera API estable).
El salto 0.x → 1.0.0 es una decisión, no una regla

SemVer permite cualquier MINOR en 0.x. Declarar 1.0.0 es decir: "a partir de aquí, mi API se considera estable y respetaré SemVer en serio". Es un compromiso con quien te consume, no un número más alto.

Paso 2 — Genera el changelog desde los commits

#!/usr/bin/env bash
# scripts/changelog.sh <tag-anterior> <version>
set -euo pipefail
desde="${1:?uso: changelog.sh <tag-anterior> <version>}"
version="${2:?uso: changelog.sh <tag-anterior> <version>}"

echo "## [${version#v}] - $(date +%Y-%m-%d)"
echo
# El rango contiene commits alcanzables desde HEAD y no desde el tag anterior.
rango="${desde}..HEAD"
asuntos() { git log --no-merges --pretty=%s "$rango"; }

volcar() {  # $1 = titulo · $2 = regex de tipos
  local out
  out="$(asuntos | grep -E "^($2)(\(|!|:)" || true)"
  [ -n "$out" ] || return 0
  echo "### $1"; echo
  asuntos | grep -nE "^($2)(\(|!|:)" >/dev/null   # (comprobacion)
  git log --no-merges --pretty='- **%s** (%h)' "$rango" \
    | grep -E "^- \*\*($2)(\(|!|:)" || true
  echo
}

volcar "Roto (BREAKING)"  "feat|fix|refactor|perf" # ver nota: se filtra abajo
echo "_(revisa a mano los que lleven ':' o 'BREAKING CHANGE' en el cuerpo)_"
volcar "Añadido"          "feat"
volcar "Corregido"        "fix|perf"
volcar "Interno"          "docs|chore|test|ci|build|style|refactor"
bash scripts/changelog.sh v0.2.0 v1.0.0 > CHANGELOG-nuevo.md
cat CHANGELOG-nuevo.md
## [1.0.0] - 2026-02-18

### Añadido
- **feat(busqueda): filtrar notas ignorando mayusculas** (4b7e0d1)
- **feat(api): exponer /notas/export** (6d2e3f4)

### Corregido
- **fix(api): evitar 500 al listar sin texto** (5c8d2e4)

### Interno
- **docs: explicar el indice en notas.md** (9f1c2ab)
- **chore(repo): dejar de versionar generados** (7a1b0c9)
Antepón el changelog nuevo al existente

Un CHANGELOG.md se lee de lo más reciente a lo más antiguo: la sección nueva va arriba. Y el apartado "Roto" debe revisarse a mano al principio (los BREAKING CHANGE: van en el cuerpo del commit, que el script no lee): con el rango delante, comprobar dos o tres casos es rápido.

Paso 3 — Confirma el estado y etiqueta

git status --short           # arbol limpio antes de etiquetar
git log --oneline -1
git tag -a v1.0.0 -m "Release 1.0.0

- busqueda estable (ignora mayusculas)
- /notas/export
- repositorio sin generados versionados"

git tag -l 'v*'
git show v1.0.0 --stat | head -12
$ git tag -l 'v*'
v0.1.0
v0.2.0
v1.0.0

$ git describe --tags
v1.0.0

Paso 4 — Publica commits y tags correctamente

# Asegura que los commits etiquetados estan en el remoto:
git push origin main
# Y ahora los tags anotados alcanzables, sin arrastrar ligeros ni basura:
git push --follow-tags
# Equivalente explicito si quieres control total:
# git push origin v1.0.0
$ git push --follow-tags
Enumerating objects: 24, done.
To ../taller-remoto.git
   7d4f5e6..9f1c2ab  main -> main
 * [new tag]         v1.0.0 -> v1.0.0
Ese [new tag] es el contrato publicado

Mientras el tag viva solo en tu máquina, la release no existe para nadie. --follow-tags publica exactamente los tags anotados que acompañan a los commits que subes: ni los experimentos (que serán ligeros o no alcanzables) ni los tags de ramas ajenas. Es la forma de que el remoto y tu máquina cuenten la misma historia.

Paso 5 — Verifica la release como lo haría un consumidor

git clone ../taller-remoto.git /tmp/verificacion-release   # clon limpio
cd /tmp/verificacion-release
git tag -l
git describe --tags
git log --oneline v1.0.0 -3
git archive --prefix=taller-1.0.0/ v1.0.0 -o taller-1.0.0.tar.gz

Resultado esperado: un clon nuevo ve el tag, describe da v1.0.0, y el git archive produce el código fuente exacto de la release (con export-ignore de .gitattributes aplicado, si lo configuraste). Esa es la prueba de que la release es real y reproducible.

5 · Buenas prácticas

PrácticaPor qué
Tags anotados para releases, con prefijo v Autor, fecha y mensaje quedan registrados; el prefijo hace trivial filtrar (--match 'v*')
Etiqueta en main, sobre un commit que ya está en el remoto Evita tags huérfanos que --follow-tags no puede publicar
Escribe el número leyendo los commits La versión es una consecuencia de la historia, no un capricho del día
Changelog generado y revisado a mano Lo automático captura el 90%; los breaking del cuerpo del commit necesitan ojos
Publica con push --follow-tags (o el tag explícito) Nunca --tags: subiría también los de pruebas
Un tag publicado no se mueve jamás Si algo salió mal, una versión nueva; reescribirlo rompe a quien lo descargó
Adjunta el artefacto y el changelog a la release Quien consume no debería tener que clonar para saber qué cambió
Firma los tags si tu equipo lo exige (-s) Un tag firmado prueba que la release la publicó quien dice serlo

6 · Errores habituales

1. git push --tags como reflejo

Mal — subir todos los tags locales sin mirar 
git push --tags
# Sube TODO: v0.1.0, v0.2.0, prueba-juan, temporal, wip-1.0...
# El remoto queda con tags que ni recuerdas haber creado.
Bien — solo los anotados que acompañan a tus commits 
git push origin main            # primero los commits
git push --follow-tags          # luego los tags anotados alcanzables
git tag -l 'v*'                 # (y de paso: borra los de prueba)
git tag -d prueba-juan

2. Tag ligero para una release

Mal — sin autor, sin fecha, sin mensaje 
git tag v1.0.0
git show v1.0.0
# Solo aparece el commit: no hay objeto tag, no hay quien/cuando/por que.
# git tag -v v1.0.0 no puede verificar nada.
Bien — tag anotado, con mensaje de release 
git tag -a v1.0.0 -m "Release 1.0.0

- busqueda estable (ignora mayusculas)
- /notas/export"
git show v1.0.0 --stat | head
# tag v1.0.0 / Tagger / Date / mensaje / y despues el commit.

3. Reescribir un tag ya publicado

Mal — mover la versión que otros ya descargaron 
git tag -f v1.0.0               # mueve el tag en tu maquina
git push --force origin v1.0.0  # ❌ quien ya lo tenia conserva el objeto VIEJO
# Resultado: "v1.0.0" significa dos cosas distintas en dos maquinas.
# Los lockfiles y los caches de dependencias se vuelven incoherentes.
Bien — publica una versión nueva 
git tag -a v1.0.1 -m "Release 1.0.1: corrige el export de /notas"
git push origin v1.0.1
git push --follow-tags
# El tag antiguo se queda como esta: es historia publicada.

4. Versión calculada por "sensación"

Mal — el número sin relación con los cambios 
# Se quito una funcion publica (breaking) y se subio el PATCH:
git tag -a v1.4.3 -m "quitamos exportNotas()"
# Quien actualice de 1.4.2 a 1.4.3 espera compatibilidad y le rompe el build.
Bien — lee los commits y aplica la regla 
git log --pretty=%s v1.4.2..HEAD
#   refactor!: quitar exportNotas() de la API publica
#   feat!: renombrar buscar() a filtrar()
# → MAJOR: 2.0.0 (MINOR y PATCH a cero), con seccion "Roto" en el changelog.

7 · Ejercicio guiado

Objetivo: publicar la release 1.0.0 del taller con changelog, tag anotado y verificación en un clon limpio.

  1. Paso 1 — Parte de un estado limpio y comprueba la última release: 
    cd taller
git switch main
git status --short                 # debe estar limpio
git fetch --prune
git tag -l 'v*'
git log --oneline "$(git describe --tags --abbrev=0)"..main

    Resultado esperado: el rango desde el último tag contiene los commits que formarán parte de la release. Si no ves ninguno, no hay nada que liberar.

  2. Paso 2 — Decide la versión con la tabla de la teoría: 
    git log --no-merges --pretty=%s "$(git describe --tags --abbrev=0)"..main \
  | grep -E '^[a-z]+(\(|!|:)' | sort | uniq -c | sort -rn
# Cuenta tipos: ¿hay 'feat'? ¿hay '!' o 'BREAKING CHANGE'? ¿es 0.x?
# El taller parte de 0.2.0 con 2 feat y 1 fix -> declaramos 1.0.0 (API estable).
  3. Paso 3 — Genera el changelog: 
    $EDITOR scripts/changelog.sh        # pega el script de la seccion 4
chmod +x scripts/changelog.sh
bash scripts/changelog.sh v0.2.0 v1.0.0 > /tmp/nuevo.md
cat /tmp/nuevo.md
# Revisa a mano si algun commit lleva 'BREAKING CHANGE:' en el cuerpo:
git log --no-merges --grep='BREAKING CHANGE' v0.2.0..main

    Resultado esperado: un bloque Markdown con Añadido / Corregido / Interno, cada línea con su hash corto.

  4. Paso 4 — Integra el changelog y etiqueta: 
    # Antepon el bloque nuevo al CHANGELOG.md existente
cat /tmp/nuevo.md CHANGELOG.md > /tmp/CHANGELOG.md 2>/dev/null || cp /tmp/nuevo.md CHANGELOG.md
mv /tmp/CHANGELOG.md CHANGELOG.md
git add CHANGELOG.md scripts/changelog.sh
git commit -m "docs(changelog): anadir la seccion de 1.0.0"

git tag -a v1.0.0 -m "Release 1.0.0: busqueda estable y repositorio limpio"
git show v1.0.0 --stat | head -12
git describe --tags

    Resultado esperado: el tag anotado apunta al commit del changelog y describe devuelve v1.0.0.

  5. Paso 5 — Publica y verifica en un clon limpio: 
    git push origin main
git push --follow-tags

rm -rf /tmp/verificacion-release
git clone ../taller-remoto.git /tmp/verificacion-release
cd /tmp/verificacion-release
git tag -l 'v*'

    Resultado esperado: el clon nuevo ve v1.0.0; describe coincide; y el archive produce el árbol de la release. La release es ahora un hecho verificable, no una intención.

  6. Paso 6 — Cierra el ciclo y reflexiona: 
    cd ../../taller
git log --oneline --graph --decorate --all -12
git shortlog -sn --no-merges v0.1.0..v1.0.0

    Resultado esperado: el grafo muestra los tres tags en una historia legible, con el trabajo de todo el curso reflejado. Ese grafo, limpio y etiquetado, es el resultado final del proyecto.

8 · Reto

🎯 Una release que se calcula y se comprueba sola

Escribe scripts/release.sh que, dado el tag anterior, haga toda la release en un comando: (1) calcule la próxima versión con SemVer a partir de los commits del rango (MAJOR si hay ! o BREAKING CHANGE:, si no MINOR si hay feat:, si no PATCH si hay fix:/perf:, y si no, aborte diciendo que no hay nada que liberar); (2) genere el changelog agrupado y lo anteponga al CHANGELOG.md; (3) cree el commit del changelog y el tag anotado; (4) publique con push --follow-tags. El script debe ser idempotente y seguro: si el árbol está sucio o el tag ya existe, se niega a hacer nada; y debe imprimir al final la versión publicada y el git describe resultante.

Pista: para el orden de precedencia usa if git log --grep='BREAKING CHANGE' …; then major; elif git log --grep='^feat' …; then minor; …. Para el "ya existe": git rev-parse -q --verify "refs/tags/$version" >/dev/null. Y recuerda que este script nunca debe tocar tags antiguos: si algo salió mal, la salida es una versión nueva, jamás git tag -f.

9 · Resumen

  • Un tag fija un commit; los de release son anotados (-a): guardan autor, fecha y mensaje.
  • SemVer = MAJOR.MINOR.PATCH: rompe / añade / corrige. En 0.y.z la API no es estable; al subir MAJOR, los otros dos a cero.
  • Conventional Commits permite deducir el salto: !/BREAKING CHANGE → MAJOR, feat → MINOR, fix/perf → PATCH.
  • git describe --tags identifica cualquier commit por su distancia al tag más cercano (v0.2.0-2-g4b7e0d1).
  • El changelog se genera del rango tag_anterior..HEAD sin merges y se agrupa por tipo; los breaking se revisan a mano.
  • Se publica con git push --follow-tags (o el tag explícito); nunca --tags.
  • Un tag publicado no se mueve: si salió mal, una versión nueva.
  • Verificación final: clonar el remoto y comprobar que el tag, el describe y el archive coinciden.

10 · Preguntas frecuentes

¿git push --follow-tags sube también los tags ligeros?

No. --follow-tags empuja únicamente los tags anotados que sean alcanzables desde los commits que se están enviando. Los ligeros se quedan en local (para eso está git push origin <tag> si de verdad quieres subir uno). Es justo la protección que necesitas contra subir tags de pruebas por descuido.

Ya publiqué un tag con un bug, ¿lo borro y lo vuelvo a crear?

No. Un tag publicado es un contrato: quien lo descargó tiene un objeto concreto. Borrarlo y recrearlo (o moverlo con --force) deja a cada máquina con una versión distinta bajo el mismo nombre, y rompe lockfiles y cachés. La solución correcta es publicar v1.0.1 con la corrección y dejar el anterior como está.

¿Cuándo un cambio de docs o de chore sube la versión?

Por regla general, no: no alteran la API pública. Pero puede tener sentido un PATCH si el cambio afecta al artefacto distribuido (por ejemplo, corregir un fichero que se incluye en el paquete o arreglar el build). La pregunta útil es: "¿le importa a quien consume?". Si la respuesta es sí, sube PATCH; si es "solo a nosotros", no subas nada y deja el cambio para la próxima release funcional.

¿Cómo sé en qué versión está un despliegue concreto?

Con git describe --tags --always: te da el tag más cercano, cuántos commits hay por delante y el hash, así que un build intermedio queda perfectamente identificado (v1.0.0-7-g9f1c2ab). Muchos equipos incrustan esa cadena como "versión de build" en el binario o en /version, y añaden --dirty para que un build con cambios sin commitear se delate.

¿Firmar los tags es obligatorio?

No, pero es una capa útil en proyectos distribuidos: un tag firmado (git tag -s) permite verificar con git tag -v que la release la publicó quien dice. Si tu ecosistema ya publica artefactos con checksums o firmas (npm, PyPI, contenedores), quizá no necesites además firmar el tag. Decide con el equipo y documéntalo; lo importante es que la verificación exista en algún punto entre tú y quien consume.
