Limpiar la historia

Módulo 7 · Proyecto final 🕐 45 minutos

1 · Introducción

Ya tienes el informe de la lección 01 delante. Ahora toca arreglar. Y el orden importa muchísimo, porque hay dos familias de remedios: los que no reescriben historia (seguros en cualquier repositorio) y los que sí la reescriben (seguros solo en local y en ramas que nadie más ha basado). Esta lección los separa con una raya gruesa y te enseña a no cruzar la raya sin querer.

El objetivo es que tu rama quede presentable —commits coherentes, nada raro versionado— sin tirar por la borda el trabajo de tus compañeros. Si algo se publicó, no se reescribe: se arregla hacia delante.

La regla de oro, una vez más

No reescribas historia que ya publicaste. Reescribir cambia los hashes: el main que tienes deja de ser el main que tiene el remoto. Tus compañeros, que basaron su trabajo en esos commits, quedarán con una historia incompatible. Todo lo "divertido" de rebase -i es para lo que aún no ha salido de tu máquina.

Errores típicos

Hacer rebase -i sobre una rama compartida y luego intentar "arreglarlo" con push --force; creer que borrar un binario con git rm lo elimina de la historia (no: sigue pesando); y añadir al .gitignore lo que ya está rastreado, esperando que desaparezca (tampoco: hay que sacarlo del índice).

2 · Teoría

Dos zonas, una frontera

        ZONA SEGURA (no reescribe)            │   ZONA LOCAL (reescribe)
   ──────────────────────────────────────────┼────────────────────────────────
   git rm --cached <ruta>                    │   git commit --amend
   .gitignore  /  .gitattributes             │   git rebase -i  (pick/squash/fixup)
   git revert <hash>                         │   git reset --hard / rebase
   commits nuevos hacia delante              │   git branch -d -D
                                            │
   Válido SIEMPRE, también en main publicada │   Válido SOLO si nadie lo tiene
   (nadie ve una historia distinta)          │   (si no, rompes a quien hizo fetch)

La pregunta que decide en qué zona estás no es "¿es mi rama?" sino ¿alguien más ha hecho fetch de estos commits?. Si la respuesta es sí (o "no lo sé"), estás en la zona segura: arregla hacia delante con revert y rm --cached, y deja el pasado como está.

Cómo responder a "¿está publicado?"

git log --oneline origin/main..HEAD lista tus commits locales no publicados. git branch -r --contains <hash> te dice si un commit concreto está en alguna rama remota. Si un commit aparece en origin/…, ya lo tiene alguien más: zona segura.

Arreglar el último commit: commit --amend

El caso más pequeño de reescritura: has quedado mal en el mensaje o te faltó meter un fichero. --amend no modifica el commit: crea uno nuevo con el mismo padre y el mismo árbol (más lo que hayas añadido al índice), y mueve la rama hacia él. El anterior queda en el reflog (módulo 6, lección 03).

# Solo el mensaje
git commit --amend -m "feat(busqueda): filtrar ignorando mayusculas"

# Añadir un fichero olvidado (sin crear un commit extra)
git add src/olvidado.js
git commit --amend --no-edit           # conserva el mensaje, actualiza el arbol

# Cambiar tambien la fecha del autor (rebase de tu autoria):
git commit --amend --reset-author

rebase -i: la sesión de reescritura local

Para más de un commit, git rebase -i <base> abre tu editor con la lista de commits del rango y un verbo por delante de cada uno. Al guardar, Git reaplica la lista de abajo arriba con tus instrucciones:

$ git rebase -i HEAD~3
pick   a1b2c3d feat: anadir campo tags al modelo
squash 4b7e0d1 fix: comillas sueltas
reword 9f1c2ab docs: explicar el indice en notas.md
pick   7d4f5e6 chore: ignorar node_modules
VerboQué haceCuándo usarlo
pickConserva el commit tal cualPor defecto
rewordConserva el cambio, cambia el mensajeTítulos pobres (wip, fix)
squashFusiona en el anterior y te deja editar el mensajeVarios commits que son uno solo
fixupFusiona en el anterior descartando su mensajeArreglos triviales ("faltaba un punto y coma")
drop (o borrar la línea)Elimina el commitCommit que no debía existir
editSe detiene para que lo modifiquesPartir un commit en dos, corregir contenido
execEjecuta una orden después de ese commitVerificar que cada paso compila

Puedes reordenar simplemente moviendo líneas. Y hay un atajo que automatiza el caso más repetido —"me di cuenta tarde de que este cambio iba en el commit anterior"—: --autosquash.

git commit --fixup=4b7e0d1        # crea un "fixup! <asunto del commit>"
git rebase -i --autosquash 4b7e0d1^   # los coloca y marca solos en el editor
--autosquash es el flujo diario

Actívalo por defecto (git config --global rebase.autoSquash true) y podrás trabajar así: commits sueltos durante el día + fixup!/squash! al vuelo + un rebase -i antes de publicar. Resultado: historia limpia sin esfuerzo y sin mentir sobre lo que pasó. Solo mientras no lo hayas publicado.

Conflictos en el rebase

Reescribir commits a veces choca. Git se detiene y te deja resolver: arreglas el fichero, git add <fichero>, git rebase --continue. Si te lías, git rebase --abort te devuelve exactamente al estado anterior. Ese abort es tu botón de pánico: al principio del rebase, todo lo que llevas en el índice está a salvo.

Sacar del índice: rm --cached

El arreglo estrella de la zona segura: dejas de versionar algo sin borrarlo del disco.

# Un fichero generado que llevas versionando por error
git rm --cached debug.log
git rm --cached -r node_modules dist        # directorios, recursivo

# Ahora SI tiene efecto el .gitignore (el fichero ya no esta en el indice)
printf 'node_modules/\ndist/\n*.log\n' >> .gitignore

git commit -m "chore: dejar de versionar node_modules, dist y logs"
Lo que rm --cached NO hace

No elimina el fichero de la historia. Los blobs antiguos de node_modules o del video de 142 MB siguen en los commits donde se añadieron: cualquiera que clone seguirá descargándolos. rm --cached impide que vuelvan; limpiar el pasado es harina de otro costal (reescritura, zona local) y, si ya está publicado, no se hace sin decisión de equipo.

.gitattributes: las reglas del contenido

Mientras .gitignore decide qué entra, .gitattributes decide cómo se trata lo que entra. Va versionado y afecta a todos por igual: es la forma correcta de fijar finales de línea y de decirle a Git que trate un fichero como binario para los diffs.

# .gitattributes
* text=auto eol=lf              # normaliza a LF en el indice; se aplica a todo
*.sh   text eol=lf              # scripts: siempre LF (si no, no arrancan en Linux)
*.bat  text eol=crlf            # lotes de Windows: siempre CRLF
*.png  binary                   # no normalizar, no mostrar diff de texto
*.jpg  binary
*.pdf  -diff                    # no intentar difear: se ve como binario en revisiones
*.lock -diff                    # lockfiles: ruido en PRs, mejor sin diff
package-lock.json -diff
dist/** linguist-generated=true  # marcar generado (lo leen las forjas)
docs/** export-ignore            # no incluir en el .zip de "git archive"
AtributoEfecto
text=autoNormaliza finales de línea en el índice (deposita LF)
eol=lf / eol=crlfFija el final de línea en el directorio de trabajo
binaryAtajo de -diff -merge -text: trátalo como binario
-diffNo mostrar diff de texto (útil en lockfiles o PDFs)
diff=<driver>Usar un driver propio para difear ese tipo
export-ignoreExcluir de git archive (ZIP de release)
linguist-generated=trueLas forjas lo marcan como generado (fuera de estadísticas)
.gitattributes antes que core.autocrlf

core.autocrlf es una configuración personal: cada persona la tiene como quiere y, si se equivoca, ensucia el índice. .gitattributes se versiona con el proyecto y garantiza que todos vean lo mismo. La práctica moderna: * text=auto eol=lf en el archivo y deja autocrlf en false. Añade *.bat text eol=crlf si tienes lotes de Windows.

Qué NO tocar si ya está en el remoto

Una lista corta y explícita, porque el informe de la lección 01 te tentará a hacer lo contrario:

  • No hagas rebase -i ni reset --hard sobre ramas publicadas (main, develop, cualquier rama de la que otros se hayan bajado commits).
  • No uses git push --force sobre main. Nunca. Ni "porque es un caso especial". Con --force-with-lease en ramas propias todavía, pero a main no.
  • No muevas tags ya publicados (git tag -f): quien los descargó tiene un objeto distinto con el mismo nombre.
  • No intentes purgar un secreto ya publicado con un comando suelto: la reescritura no basta (el objeto puede seguir accesible vía reflog/forjas) y hay que rotar la credencial y coordinar a todo el mundo. Es un procedimiento con documentación oficial propia ("removing sensitive data" / "rewriting history" en la doc de Git) y una decisión de equipo, no una ocurrencia de media tarde.
# ✅ Reescritura SOLO en una rama propia y no publicada, y con arrendamiento:
git rebase -i HEAD~4
git push --force-with-lease origin feature/mi-rama

# ❌ Jamas:
git push --force origin main
Por qué --force-with-lease y no --force

--force sobrescribe la rama remota pase lo que pase: si un compañero subió un commit mientras tanto, lo borras sin enterarte. --force-with-lease comprueba que la rama remota esté donde tú creías (según tu último fetch); si cambió, rechaza el push. Es la diferencia entre "empujo mi versión" y "empujo mi versión solo si nadie ha tocado nada desde que miré".

3 · Ejemplo mínimo

Los dos arreglos más pequeños, uno de cada zona. Primero, el seguro: dejar de versionar un log.

cd taller
git rm --cached debug.log
echo 'debug.log' >> .gitignore
git commit -m "chore: dejar de versionar debug.log"
$ git rm --cached debug.log
rm 'debug.log'

$ git status --short
D  debug.log
 M .gitignore
# 'D ' = borrado en el INDICE pero el fichero sigue en el disco.
# Comprueba: ls debug.log  -> sigue ahi.

Segundo, el local: arreglar el mensaje del último commit.

git commit --amend -m "docs: explicar el indice en notas.md"
git log --oneline -1
$ git log --oneline -1
9f1c2ab docs: explicar el indice en notas.md
# Mismo contenido, mensaje nuevo. El commit anterior sigue en el reflog.

Qué esperamos ver: el fichero sigue en disco pero ya no en el índice; y el commit tiene mensaje nuevo con el mismo contenido. Ninguno de los dos arreglos ha reescrito nada publicado.

4 · Ejemplo real

La limpieza completa del taller, en el orden exacto del informe: primero lo seguro, luego lo local, y el binario publicado lo dejamos documentado sin tocar.

Fase 1 — Fronteras e índice (zona segura)

# 1.1 Sacar del indice lo que nunca debio entrar (los ficheros siguen en disco)
git rm -r --cached node_modules dist
git rm --cached debug.log '*.mp4' 2>/dev/null || true

# 1.2 Cerrar las fronteras
cat >> .gitignore <<'EOF'

# --- anadido en la limpieza del proyecto final ---
node_modules/
dist/
*.log
assets/*.mp4
.DS_Store
EOF

# 1.3 Reglas de contenido, versionadas
cat > .gitattributes <<'EOF'
* text=auto eol=lf
*.sh   text eol=lf
*.bat  text eol=crlf
*.png  binary
*.jpg  binary
*.mp4  binary
*.pdf  -diff
package-lock.json -diff
EOF

# 1.4 Renormalizar los finales de linea ya versionados
git add --renormalize .

git commit -m "chore(repo): dejar de versionar generados y fijar .gitattributes"
Qué hace git add --renormalize .

Reaplica los atributos de .gitattributes a los ficheros ya rastreados y actualiza el índice con la normalización correspondiente. Es la forma correcta de arreglar CRLF/LF mezclados sin reescribir historia: un único commit "chore(repo): normalizar finales de línea" y fuera.

Fase 2 — Historia local de tu rama (zona local)

Tu rama feature/busqueda tiene cinco commits de los cuales tres son un solo cambio. Y no está publicada. Comprobémoslo y limpiemos:

git switch feature/busqueda
git log --oneline origin/main..HEAD      # ¿que commits son solo mios?
# 5 commits, todos locales: zona local confirmada.

git commit --fixup=2c9a1f3               # (si aun tuvieras algo que anadir)
git rebase -i --autosquash origin/main
# En el editor:
pick   2c9a1f3 feat(busqueda): anadir campo tags al modelo
fixup  5f6g7h8 fixup! feat(busqueda): anadir campo tags al modelo
squash 4b7e0d1 feat: filtrar notas por texto
reword 8h9i0j1 wip
drop   3c4d5e6 debug temporal que no quiero publicar

# Tras guardar, reescribes 5 commits en 2, con mensajes decentes y sin basura.
git log --oneline --graph origin/main..HEAD
# 2 commits limpios sobre origin/main

# Reescritura en rama PROPIA y no publicada: se publica con arrendamiento
git push --force-with-lease -u origin feature/busqueda
Si el rebase se lía: --abort

Conflicto, momento confuso, dudas: git rebase --abort y vuelves exactamente al estado previo. Tu rama original y el reflog siguen intactos. Repetir el rebase con más calma es siempre una opción.

Fase 3 — El binario publicado: se documenta, no se toca

El video de 142 MB está en origin/main: lo limpiaríamos reescribiendo una rama compartida, y eso rompe a todo el mundo. La decisión correcta en la auditoría fue:

## Decisión sobre assets/video-demo.mp4 (142 MiB, en origin/main)
- **No** se reescribe la historia publicada en este proyecto.
- Se deja de versionar a partir de ahora (Fase 1: `rm --cached` + `.gitignore`).
- Se abren dos caminos para el futuro, decididos por el equipo:
  1. Aceptar el coste y no hacer nada más (el repo ya se clonó; duele menos de lo que parece).
  2. Coordinar una reescritura masiva en una ventana acordada, con la doc oficial
     de "rewriting history" delante, avisando a TODOS y asumiendo que cada clon
     debe volver a clonar. NUNCA un `push --force` sorpresa.
- Sin secretos implicados. Si los hubiera: rotar la credencial YA, antes que nada.
Por qué no te damos aquí el comando de reescritura masiva

Porque en el momento en que lo tienes en la mano, la tentación de aplicarlo a un remoto compartido es enorme, y las consecuencias (historiales divergentes, trabajo perdido, PRs rotos, secretos que siguen accesibles) son graves y difíciles de revertir. La reescritura masiva de un remoto tiene su propio procedimiento oficial, sus propias salvaguardas y su propia conversación de equipo. Aquí nos quedamos con la parte que sí es segura: dejar de versionar hacia adelante, documentar el pasado y rotar lo que sea sensible.

5 · Buenas prácticas

PrácticaPor qué
Empieza siempre por la zona segura rm --cached, .gitignore y .gitattributes no rompen a nadie y arreglan la mayoría del ruido
Comprueba "¿publicado?" antes de reescribir git log origin/main..HEAD y git branch -r --contains; sin esa respuesta, no hay rebase
Trabaja los rebase -i sobre una rama propia Limita el daño: si algo se tuerce, solo afecta a tu rama; --abort siempre disponible

Publica con --force-with-lease Solo en ramas propias; nunca --force a main
Versiona .gitattributes y .gitignore Son parte del proyecto: el arreglo debe aplicarse a todos, no solo a tu máquina

Documenta lo que no arreglas Un hallazgo aplazado con justificación es una decisión; un hallazgo ignorado es una bomba de relojería

6 · Errores habituales

1. Reescribir una rama compartida y "arreglarlo" con force

Mal — rebase sobre main y push forzado 
git switch main
git rebase -i HEAD~10          # main ya esta en origin: PROHIBIDO
git push --force origin main   # ❌ y encima pisa el trabajo de los demas
# Quien haya hecho fetch tiene ahora una historia incompatible: PRs rotos,
# merges imposibles, trabajo duplicado.
Bien — lo publicado se arregla hacia delante 
# En una rama propia y no publicada, si; en main publicada, no:
git switch -c limpieza/local main
git rebase -i HEAD~10          # ahora es TU rama, nadie la tenia
git push -u origin limpieza/local
# Y para "deshacer" algo en main: git revert (historia nueva), no rebase.

2. Creer que rm --cached borra el binario de la historia

Mal — dar por resuelto el peso del repositorio 
git rm --cached assets/video-demo.mp4
git commit -m "chore: quitar video"
git count-objects -vH
# size-pack sigue en ~180 MiB: el blob vive en el commit donde se anadio.
Bien — separar "dejar de versionar" de "limpiar el pasado" 
# (a) Dejar de versionar YA (seguro, vale siempre):
git rm --cached assets/video-demo.mp4
echo 'assets/*.mp4' >> .gitignore
git commit -m "chore: dejar de versionar videos"

# (b) Limpiar el pasado: reescribe historia. Solo si NO esta publicado
#     y con decision de equipo + doc oficial. En este proyecto: se aplaza.

3. Añadir al .gitignore lo que ya está rastreado

Mal — esperar que la regla desrastree sola 
echo 'node_modules/' >> .gitignore
git status
# ... node_modules SIGUE apareciendo modificado. La regla no afecta
# a lo que ya esta en el indice.
Bien — regla + sacar del índice en el mismo commit 
git rm -r --cached node_modules      # fuera del indice
echo 'node_modules/' >> .gitignore   # la regla evita que vuelva
git commit -m "chore: dejar de versionar node_modules"
git status --short                   # limpio

4. Usar --force donde bastaba --force-with-lease

Mal — sobrescribir sin comprobar 
git rebase -i HEAD~3
git push --force origin feature/mia
# Si un companero anadio un commit a esa rama mientras tanto, lo acabas de borrar.
Bien — arrendamiento: comprueba antes de sobrescribir 
git fetch origin
git rebase -i HEAD~3
git push --force-with-lease origin feature/mia
# Si la rama remota cambio desde tu fetch, el push se RECHAZA y te avisa.
# Y si te rechaza: fetch, mira que hay, integra y vuelve a intentarlo.

7 · Ejercicio guiado

Objetivo: ejecutar las tres fases de la limpieza en el taller, dejando la rama presentable y sin tocar nada publicado.

  1. Paso 1 — Prepara un desastre controlado y anota el punto de retorno: 
    cd taller
git switch -c limpieza/ejercicio main
git rev-parse HEAD > /tmp/antes-de-limpiar.txt
mkdir -p node_modules/pkg dist
echo 'console.log(1)' > dist/bundle.js

echo 'log ruidoso' > debug.log

git commit --allow-empty -m "wip"              # otro
git commit --allow-empty -m "otro wip"
  2. Paso 2 — Diagnostica antes de tocar (recuerda la lección 01): 
    git log --oneline -4
git ls-files node_modules dist debug.log
git status --short --ignored | head

    Resultado esperado: tres commits de mensaje pobre y ficheros generados versionados.

  3. Paso 3 — Fase segura: fronteras e índice: 
    git rm -r --cached node_modules dist
git rm --cached debug.log

printf '* text=auto eol=lf\n*.png binary\n*.lock -diff\n' > .gitattributes
git add --renormalize .
git commit -m "chore(repo): dejar de versionar generados y fijar .gitattributes"
git status --short            # los ficheros siguen en disco, ya no en el indice
  4. Paso 4 — Fase local: limpiar la historia de TU rama: 
    git log --oneline origin/main..HEAD    # confirma que NADA esta publicado
git rebase -i --autosquash origin/main

    En el editor: deja pick en el commit del .gitattributes, marca fixup o drop en los wip, y reword en "cambios" para ponerle un mensaje decente. Guarda y cierra.

    git log --oneline --graph origin/main..HEAD
# Debes ver una historia corta y con mensajes decentes.

    Resultado esperado: los wip desaparecen, el mensaje pobre queda reescrito, y la rama sigue partiendo de origin/main.

  5. Paso 5 — Verifica que el pasado publicado NO se ha tocado: 
    git log --oneline origin/main -3
git diff origin/main --stat | tail -3

    Resultado esperado: la punta de origin/main es exactamente la misma que antes de limpiar. Solo ha cambiado tu rama.

  6. Paso 6 — Publica con arrendamiento y rectifica si hace falta: 
    git push -u origin limpieza/ejercicio
# (Simula una reescritura posterior y publica de forma segura)
git commit --amend --no-edit
git push --force-with-lease origin limpieza/ejercicio

    Resultado esperado: el primer push crea la rama; el segundo, tras reescribir, acepta porque nadie más la ha tocado. Si se rechazara, significaría que hay commits nuevos en el remoto: git fetch y mirar antes de reintentar.

8 · Reto

🎯 Convertir 12 commits en una historia de 4 que se lea de un tirón

Crea en el taller una rama limpieza/reto con doce commits desordenados (mensajes wip, fix, ok; cambios que se pisan entre sí; un par de ficheros que se añaden y se quitan; un commit que no debería existir). Escribe primero el plan de reescritura en informe/plan-reto.md —qué commits se combinan, cuáles se renombran, cuál se elimina y en qué orden— y solo después ejecútalo con un rebase -i (o varios, si te resulta más manejable). La historia final debe cumplir: 4 commits, todos con mensajes de Conventional Commits válidos, cada uno compilando (git rebase -i --exec "node --test" origin/main te lo verifica paso a paso), y sin ningún fichero generado versionado.

Pista: empieza por el --autosquash para los fixup! que crees ahora (git commit --fixup=<hash>), y usa edit donde necesites partir un commit en dos (git reset HEAD^ dentro del edit y vuelve a commitear por trozos). Antes de empezar, guarda git rev-parse HEAD: es tu billete de vuelta por el reflog si el plan se te va de las manos.

9 · Resumen

  • Zona segura (no reescribe, vale siempre): rm --cached, .gitignore, .gitattributes, revert, add --renormalize.
  • Zona local (reescribe, solo si no está publicado): commit --amend, rebase -i con pick/reword/squash/fixup/drop/edit.
  • --autosquash + commit --fixup es el flujo diario para limpiar antes de publicar.
  • git rm --cached saca del índice sin borrar del disco, pero no limpia la historia.
  • .gitattributes versionado (* text=auto eol=lf, *.png binary, *.lock -diff) sustituye a core.autocrlf.
  • Lo publicado no se reescribe: git push --force a main, nunca; --force-with-lease solo en ramas propias.
  • Un secreto publicado obliga a rotar y a un procedimiento oficial de reescritura con decisión de equipo; no se resuelve con un comando suelto.
  • git rebase --abort es tu botón de pánico durante cualquier reescritura.

10 · Preguntas frecuentes

¿git rm --cached borra el fichero de mi disco?

No. Solo lo quita del índice: el fichero sigue en tu directorio de trabajo (aparecerá como "sin rastrear" hasta que lo cubra el .gitignore). Si quieres borrarlo también del disco, usa git rm sin --cached. Es un matiz clave: casi siempre quieres --cached más una regla de exclusión.

Ya hice rebase -i en una rama publicada, ¿cómo lo arreglo?

No lo "arregles" con más reescritura. Si el rebase ya se subió con --force, avisa al equipo de inmediato: quienes tengan los commits antiguos deben saber qué hacer (volver a reescribir su rama sobre la nueva base, o re-clonar). Si aún no lo has subido, git rebase --abort o el reflog te devuelven al estado anterior. La lección: antes de reescribir, comprueba git log origin/main..HEAD.

¿Puedo eliminar un fichero del pasado sin reescribir historia?

No: la historia es inmutable; todo lo que se añadió sigue en los objetos. Lo que sí puedes es dejar de versionarlo hacia adelante (rm --cached) y, si te preocupa el peso, decidir en equipo una reescritura en una ventana acordada. Si es un secreto, no hay debate: rota la credencial primero, porque aunque reescribas, el valor pudo quedar cacheado o copiado en cualquier clon, fork o log de CI.

¿revert o reset para deshacer lo publicado?

revert siempre que esté publicado: crea un commit nuevo que deshace el anterior y no reescribe nada, así los demás solo tienen que hacer pull. reset --hard mueve la punta hacia atrás y reescribe; en local es reversible con el reflog, pero en una rama compartida es el camino directo a un --force y a un lío de equipo.

¿Merece la pena --force-with-lease si trabajo solo?

Merece, porque no cuesta nada y protege justo el caso que no controlas: la rama remota cambió sin que tú lo supieras (una automatización, otra máquina tuya, un revisor que añadió un commit). Además es la costumbre correcta: el día que trabajes en equipo, ya la tienes metida en los dedos. Y recuerda: siempre en ramas propias; main no se reescribe, ni con lease.
