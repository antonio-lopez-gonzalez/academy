clone, fetch y pull

Módulo 5 · Remotos 🕐 35 minutos

1 · Introducción

Hasta ahora todo ocurría en tu máquina. Un remoto es otro repositorio —normalmente en un servidor, pero puede ser una carpeta— al que Git le habla por red o por disco. No es una carpeta compartida ni un servicio mágico: es un repositorio Git más, con sus ramas y sus objetos. origin es solo el nombre que le damos al remoto principal, como «casa» es el nombre de una dirección.

Tres comandos gobiernan la relación: clone crea tu copia, fetch trae lo nuevo sin tocar tu trabajo y pull trae lo nuevo y lo integra. Confundir los dos últimos es la causa número uno de merges sorpresa.

¿Por qué existe esta lección?

Porque git pull parece inofensivo y no lo es: puede crear un merge commit que no pediste, puede fallar a mitad por un fichero modificado y puede dejar tu rama con una forma que no esperabas. Entender qué hace cada paso —y poder separarlos— te devuelve el control. fetch es la operación segura; pull es una comodidad que conviene configurar con intención.

2 · Teoría

Qué hace git clone

git clone <url> hace, en este orden:

  1. Crea un repositorio vacío en una carpeta nueva (o en la que indiques).
  2. Registra el remoto con el nombre origin y guarda su URL.
  3. Descarga todos los objetos y referencias del remoto.
  4. Crea las ramas remotas (origin/main, origin/feature/x…) como referencias de solo lectura en tu repositorio.
  5. Crea una rama local para la rama por defecto (normalmente main), la configura como upstream de origin/main y la deja activa.
git clone ../remoto.git trabajo
cd trabajo
git remote -v
git branch -a
origin  ../remoto.git (fetch)
origin  ../remoto.git (push)

* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/main
  remotes/origin/feature/busqueda
Qué puntero mueve clone

Ninguno de tu repositorio, porque aún no existe. Crea HEAD, la rama local y las referencias remotes/origin/*. A partir de ahí, tu main y origin/main son dos referencias distintas que pueden apuntar a commits distintos.

Ramas remotas: una foto, no una rama tuya

origin/main no es «la rama main del servidor» en vivo. Es tu último conocimiento de dónde estaba, guardado en refs/remotes/origin/main. Solo cambia cuando haces fetch (o pull, que lo incluye). No puedes hacer commit sobre ella ni cambiar de rama a ella con la intención de trabajar.

TU REPOSITORIO                              REMOTO

  main          →  C1                        main → C3
  origin/main   →  C2   (lo que viste         (la verdad
                         en el último fetch)    ahora mismo)

  Si el remoto avanzó de C2 a C3 y tú no has hecho fetch,
  tu origin/main sigue en C2. Git no mira el servidor
  cada vez que ejecutas git status.

De ahí sale el mensaje más útil de status:

On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

Ese «behind» compara tu main con tu origin/main. Si no has hecho fetch, puede estar desactualizado en ambos sentidos: no sabe que el remoto avanzó y tú tampoco.

Equivalente a—fetch + merge (o rebase)

git pull no es un comando primitivo: es un atajo. Ejecuta fetch y después integra la rama remota en la tuya con merge o con rebase, según la configuración y los flags:

git pull                  # fetch + merge (por defecto histórico)
git pull --rebase         # fetch + rebase: tus commits encima de los remotos
git pull --ff-only        # fetch + merge solo si es fast-forward
El merge que no pediste

Si tienes commits locales y el remoto también avanzó, git pull con merge crea un merge commit «Merge branch 'main' of …». En un repositorio con historia lineal eso ensucia el log y aparece en cada sincronización. No es un error, pero sí una decisión que conviene tomar de antemano con pull.rebase o usando --rebase explícito.

pull --rebase: qué hace exactamente

ANTES

    A───B───C   origin/main
         \
          D───E   main (tus dos commits locales)

    git pull --rebase

DESPUÉS

    A───B───C───D'───E'   main
            ↑
            origin/main

    Tus commits se reaplican SOBRE lo que bajó.
    D y E cambian de hash: es un rebase normal,
    con la misma regla de oro (solo en ramas propias).

Ventaja: historia lineal y tus commits quedan «encima», como si hubieras empezado a trabajar después. Coste: si había conflictos, los resuelves commit a commit; y si la rama es compartida, estás reescribiendo hashes que otros pueden tener. En una rama de trabajo personal, es la opción más limpia. En main compartido, muchos equipos prefieren merge o --ff-only.

Configura una vez, evita sustos
# Opción A: nunca merges automáticos; que falle si no es fast-forward
git config --global pull.ff only

# Opción B: integra siempre con rebase
git config --global pull.rebase true

# Opción C: deja que Git te avise y decidas cada vez
git config --global pull.rebase false   # merge (comportamiento clásico)

Git moderno avisa si no has configurado nada y las ramas divergen. pull.ff only es la opción más conservadora: convierte el pull en un fetch + fast-forward y te obliga a decidir cuando hay divergencia.

Anatomía de una sincronización segura

  1. git fetch origin — trae objetos y actualiza origin/main. Tu trabajo no se toca.
  2. git status y git log --oneline main..origin/main — ¿qué hay al otro lado?
  3. git diff main...origin/main — ¿qué cambia el contenido? (tres puntos: desde la base común)
  4. Decide: git merge --ff-only origin/main, git rebase origin/main o un merge explícito.
  5. Resuelve conflictos si los hay, ejecuta tests y publica.

3 · Ejemplo mínimo

Remoto local y dos clones. El compañero publica un commit; tú aún no lo sabes.

git init --bare remoto.git
git clone remoto.git trabajo
git clone remoto.git compañero

cd compañero
printf 'nota del compañero\n' >> notas.md
git commit -am "docs: nota del compañero"
git push

En trabajo, comprueba primero que fetch no toca nada:

cd ../trabajo
git status
git fetch origin
git status
On branch main
Your branch is up to date with 'origin/main'.

# ... tras el fetch:

On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

El fichero notas.md de tu directorio de trabajo sigue sin la nota: fetch solo movió origin/main. Para verla, integra:

git merge --ff-only origin/main
cat notas.md
git log --oneline --graph -3
nota del compañero

* 8b2d4e6 (HEAD -> main, origin/main) docs: nota del compañero
* 1a2b3c4 feat: notas
Fetch es tu amigo cuando hay prisa

Puedes hacer fetch con el árbol sucio, a mitad de un rebase o mientras corre un build: no toca ficheros ni índices. Es la forma de «mirar el servidor» sin consecuencias. pull, en cambio, escribe en tu working tree y puede negarse si tienes cambios que chocan.

4 · Ejemplo real

Escenario: vuelves de una reunión. Tienes dos commits locales en feature/informe y main ha recibido cinco commits, uno de ellos tocando el mismo fichero de configuración que tú. Quieres integrar sin crear un merge commit y sin perder tu trabajo.

git status
git fetch origin
git log --oneline HEAD..origin/main
git diff --stat HEAD...origin/main
On branch feature/informe
Your branch is up to date with 'origin/feature/informe'.

  (tras el fetch, main local no cambia: solo origin/main)

8b2d4e6 chore: actualizar dependencias
7a1c3e5 fix(config): validar variables de entorno
6f0b2d4 docs: guía de despliegue
5e9a1c3 feat(api): endpoint de salud
4d8f0b2 test(config): cubrir valores vacíos

 config/app.js | 18 ++++++++++++------
 1 file changed, 12 insertions(+), 6 deletions(-)

Antes de integrar, guarda lo que tengas a medias (si hubiera algo) y comprueba desde dónde vienes. Luego rebasa tus dos commits sobre origin/main:

git rebase origin/main
Auto-merging config/app.js
CONFLICT (content): Merge conflict in config/app.js
error: could not apply 2c4e6a8... feat(informe): leer configuración
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".

Resuelves conservando la validación nueva de main y tu lectura de configuración, y sigues:

git add config/app.js
git rebase --continue
[detached HEAD 9a7c1e3] feat(informe): leer configuración
 1 file changed, 9 insertions(+), 4 deletions(-)
Successfully rebased and updated refs/heads/feature/informe.

Si en vez de rebasar hubieras hecho git pull sobre main, el resultado sería un merge commit con dos padres y un grafo en zigzag. Ninguna opción es «incorrecta»; la diferencia es qué historia quieres publicar y si la rama es tuya.

Variante con pull --rebase. Si estuvieras en main con dos commits locales sin publicar, el atajo equivalente sería:

git pull --rebase origin main

Hace exactamente fetch + rebase origin/main. La diferencia con el ejemplo es que aquí main es una rama compartida: si esos dos commits ya estuvieran publicados, el rebase te obligaría a force push y estarías reescribiendo lo que otros tienen. Por eso la secuencia explícita (fetch → inspeccionar → rebase) es mejor hábito: te obliga a verlo antes.

La regla práctica

Fetch siempre; pull solo cuando sepas qué integración quieres. Si no has configurado nada, git pull elige por ti. Y si hay cambios sin commitear, el merge puede negarse o arrastrarlos a un conflicto que no era necesario. Separar los pasos cuesta dos comandos y evita un merge que luego hay que deshacer.

6 · Errores habituales

1. Creer que origin/main está siempre al día

Mal — comparar con una foto vieja 
git status
# "Your branch is up to date with 'origin/main'"
# ...pero el remoto recibió 3 commits hace una hora
Bien — actualizar la foto primero 
git fetch origin
git status
git log --oneline main..origin/main

origin/main solo se mueve cuando tú lo traes. Hasta entonces, Git te habla de tu último recuerdo, no de la realidad del servidor. En equipos activos, fetch al empezar a trabajar es barato y evita sorpresas.

2. Hacer pull con cambios sin commitear

Mal — arrastrar el árbol sucio 
# estás editando config/app.js sin commitear
git pull
# merge con cambios locales: conflicto o "Please commit your changes"
Bien — guardar o commitear antes 
git stash push -m "wip config"
git pull --ff-only
git stash pop
# o: git commit -m "wip: config" y luego limpiar la historia

El pull intenta escribir en ficheros que tú tienes modificados. Git aborta si el merge tocaría esos ficheros, pero a veces avanza y te deja un estado mezclado difícil de leer. Un stash de diez segundos lo evita.

3. Confundir pull --rebase con «siempre seguro»

Mal — rebasar una rama compartida 
git switch main              # main compartido, ya publicado
git pull --rebase            # reescribe tus commits locales de main
git push
# rechazo no-fast-forward, y si fuerzas, rompes a los demás
Bien — integrar sin reescribir lo compartido 
git switch main
git pull --ff-only           # solo avanza; falla si hay divergencia
# si divergiste tú: mueve tus commits a una rama y allí rebasa

--rebase reescribe tus commits locales. En una rama privada es ideal; en main publicado, si esos commits ya salieron, el rebase te empuja hacia un force push. La regla de oro del módulo 4 sigue vigente.

7 · Ejercicio guiado

Objetivo: comprobar con tus ojos que fetch no toca el directorio de trabajo y que pull --ff-only sí integra, sin crear merge commits.

  1. Crea el remoto y dos clones. 
    git init --bare remoto.git
git clone remoto.git trabajo
git clone remoto.git compañero
  2. Publica desde el compañero. 
    cd compañero
printf 'línea nueva\n' >> notas.md
git commit -am "docs: línea nueva"
git push
  3. En trabajo, haz fetch y demuestra que el fichero no cambia. 
    cd ../trabajo
git fetch origin
git status
cat notas.md
git log --oneline -1 origin/main

    notas.md no debe contener «línea nueva», pero origin/main sí debe apuntar al commit nuevo.

  4. Integra con fast-forward. 
    git merge --ff-only origin/main
cat notas.md
git log --oneline --graph -3
  5. Comprueba que no hay merge commit. 
    git log --merges --oneline -3

    La salida debe estar vacía: el fast-forward solo movió el puntero.

Solución resuelta

Salida esperada del paso 3:

On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

# cat notas.md → sin la línea nueva

8b2d4e6 docs: línea nueva

Y del paso 4:

Updating 1a2b3c4..8b2d4e6
Fast-forward
 notas.md | 1 +
 1 file changed, 1 insertion(+)

* 8b2d4e6 (HEAD -> main, origin/main) docs: línea nueva
* 1a2b3c4 feat: notas

El paso 5 no imprime nada porque no hay ningún commit de merge: el fast-forward no crea commits. Ese es el resultado que buscas cuando solo quieres ponerte al día sin aportar trabajo local.

8 · Reto

Reto

En el escenario del ejercicio, crea dos commits locales en trabajo y, desde compañero, publica otros dos que tocan la misma sección de notas.md. Ahora las ramas han divergido.

Integra los cambios de las dos formas y compara los grafos resultantes: una vez con git pull (merge) y otra, partiendo del mismo estado, con git pull --rebase. Documenta con git log --oneline --graph la diferencia, explica qué pasó con los hashes de tus commits en cada caso y decide cuál publicarías si main fuera una rama compartida y cuál si fuera tu rama privada.

Pista: guarda el hash de tus commits antes de cada intento y usa el reflog para volver al estado divergente. Ten en cuenta que, tras el merge, el push será un fast-forward; tras el rebase, tus commits tendrán hashes nuevos y el remoto no los conoce. Piensa qué implicaría eso si los hubieras publicado antes.

9 · Resumen

  • clone crea el repositorio local, registra origin, descarga objetos y configura la rama por defecto con su upstream.
  • origin/main es una referencia de seguimiento local: tu última foto del remoto, no la verdad en vivo.
  • fetch descarga y actualiza origin/*; no toca tu rama, tu índice ni tus ficheros.
  • pull = fetch + integración (merge por defecto, rebase con --rebase).
  • pull --rebase deja tus commits encima y la historia lineal, pero reescribe sus hashes: solo en ramas propias.
  • La secuencia segura es fetch → inspeccionar → integrar, no pull a ciegas.

10 · Preguntas frecuentes

¿origin es obligatorio o especial?

Es una convención, no una palabra reservada. clone lo usa por defecto, pero puedes renombrarlo con git remote rename origin upstream o añadir más con git remote add. Lo especial es el upstream de cada rama (qué remoto y qué rama remota sigue), no el nombre del remoto. En un fork es habitual tener origin (tu fork) y upstream (el repositorio original).

¿Cómo veo la diferencia entre mi rama y el remoto?

Para commits, git log --oneline main..origin/main (lo que tiene el remoto y tú no) y git log --oneline origin/main..main (lo tuyo que no está allí). Para contenido, git diff main...origin/main con tres puntos: compara desde la base común, así no te muestra como «cambio» lo que solo avanzó un lado. Con dos puntos, git diff main..origin/main, verías también las diferencias acumuladas por ambos.

¿Puedo hacer fetch sin conexión?

No: necesita acceder al remoto. Pero si el remoto es una carpeta local o un repositorio bare en tu disco, funciona sin red (es el escenario del laboratorio). Si no hay conexión, tus ramas y objetos locales siguen intactos: fetch no es requisito para commitear, ramificar ni consultar la historia que ya tienes.

¿Qué hace git pull si no hay commits locales?

Un fast-forward: mueve tu rama al commit remoto sin crear merge. Es el caso más común y el más seguro. El merge solo aparece cuando ambas ramas tienen commits distintos desde la base común. Por eso el «merge branch main of…» sorprende: implica que tenías trabajo local sin publicar.

¿pull --rebase puede perder mis commits?

No los pierde, pero los reescribe: si había conflicto y lo resuelves mal, el contenido puede quedar incompleto. El reflog guarda el estado anterior, así que puedes volver con git reset --hard HEAD@{1}. Y si el rebase se interrumpe, git rebase --abort te devuelve al punto de partida. Aun así, revisa el diff y ejecuta los tests antes de publicar.
