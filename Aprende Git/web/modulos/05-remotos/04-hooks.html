Hooks: automatizar en tu máquina

Módulo 5 · Remotos 🕐 40 minutos

1 · Introducción

Un hook es un script que Git ejecuta automáticamente en un momento concreto: antes de crear un commit, después de escribir el mensaje, antes de empujar. No son plugins ni extensiones: son ficheros ejecutables en una carpeta que Git mira si existen. Si el script termina con código distinto de cero, la operación se cancela.

Eso los convierte en la primera línea de defensa del equipo: un commit-msg que rechaza mensajes mal formados, un pre-commit que pasa el linter o un pre-push que ejecuta los tests. Barrera barata, feedback inmediato. Pero también son fáciles de malinterpretar: viven en tu máquina, no en el repositorio, y cualquiera puede saltárselos.

¿Por qué existe esta lección?

Porque un hook bien puesto evita cientos de commits arreglados a posteriori con rebase -i, y un hook mal entendido crea una falsa sensación de seguridad. La clave es saber qué garantiza cada uno, dónde vive, cómo compartirlo con el equipo sin versionar .git/ y por qué la CI sigue siendo la autoridad. Los hooks aceleran; la CI decide.

2 · Teoría

Dónde viven (y por qué no se clonan)

Los hooks de cliente viven en .git/hooks/. Al crear un repositorio, Git coloca ahí una colección de ejemplos con extensión .sample, que no se ejecutan hasta que quitas esa extensión y haces el fichero ejecutable.

ls .git/hooks
applypatch-msg.sample      pre-commit.sample
commit-msg.sample          pre-push.sample
fsmonitor-watchman.sample  pre-rebase.sample
post-update.sample         prepare-commit-msg.sample
pre-applypatch.sample      update.sample

La carpeta .git/ no se versiona ni se clona. Por tanto, los hooks locales no viajan con el repositorio: son configuración de cada máquina. Si quieres compartirlos, hay que versionarlos fuera de .git/ y decirle a Git dónde buscarlos (core.hooksPath, lo verás más abajo).

Qué puntero mueven (o mejor: qué impiden)

Los hooks de cliente no mueven referencias: se ejecutan alrededor de una operación. Si terminan con éxito, la operación sigue su curso normal; si fallan, Git la aborta antes de mover nada. Un pre-commit que falla no crea commit; un pre-push que falla no mueve la referencia remota.

El ciclo de vida de un commit y un push

git commit
   │
   ├─▶ pre-commit ──────────── se ejecuta primero. Lint, formato, tests rápidos.
   │
   ├─▶ prepare-commit-msg ──── (opcional) prepara el mensaje por defecto.
   │
   ├─▶ commit-msg ──────────── recibe la ruta del fichero con el mensaje.
   │                           Valida el formato. Si falla, aborta el commit.
   │
   └─▶ post-commit ─────────── se ejecuta después. No puede abortar nada.

git push
   │
   ├─▶ pre-push ────────────── recibe remoto y URL; por stdin, las refs.
   │                           Responsabilidad: no publicar algo roto.
   │
   └─▶ pre-receive ─────────── (en el servidor) política del remoto.

Los tres que más se usan en un equipo:

HookCuándoRecibeUso típico
pre-commitAntes de abrir el editor del mensajeNada (lee el índice)Linter, formateador, comprobación de ficheros prohibidos
commit-msgTras escribir el mensaje, antes de crear el commitRuta del fichero con el mensajeConventional Commits, número de ticket obligatorio

Un detalle importante: cuando Git ejecuta un hook, su directorio de trabajo es la raíz del repositorio (en un repositorio con árbol de trabajo). Por eso los scripts pueden usar rutas relativas al proyecto.

Un commit-msg en Node: Conventional Commits

El hook recibe como primer argumento la ruta del fichero que contiene el mensaje (normalmente .git/COMMIT_EDITMSG). Leerlo, validarlo y salir con 1 si no cumple es todo lo que hace falta. Este script usa CommonJS para funcionar en cualquier versión de Node sin depender del package.json:

#!/usr/bin/env node
// .git/hooks/commit-msg
const { readFileSync } = require('node:fs');

const file = process.argv[2];
if (!file) {
  console.error('commit-msg: falta la ruta del mensaje');
  process.exit(1);
}

const message = readFileSync(file, 'utf8');
const subject = message.split('\n')[0].trim();

// Los merges automáticos no se validan.
if (subject.startsWith('Merge ')) process.exit(0);

const pattern =
  /^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?!?: .{1,72}$/;

if (!pattern.test(subject)) {
  console.error('commit-msg: mensaje inválido -> "' + subject + '"');
  console.error('Formato: tipo(alcance): resumen en imperativo (<= 72 caracteres)');
  console.error('Ejemplo: feat(busqueda): filtrar por titulo');
  process.exit(1);
}

process.exit(0);

Instalación y prueba:

cp .git/hooks/commit-msg.sample .git/hooks/commit-msg   # o crea el fichero
chmod +x .git/hooks/commit-msg                          # en Git Bash / macOS / Linux
git commit -m "arreglar cosas"
commit-msg: mensaje inválido -> "arreglar cosas"
Formato: tipo(alcance): resumen en imperativo (<= 72 caracteres)
Ejemplo: feat(busqueda): filtrar por titulo

El commit no se crea. Con un mensaje válido, el hook calla y Git sigue:

git commit -m "fix(busqueda): escapar acentos"
[main 3c4d5e6] fix(busqueda): escapar acentos
 1 file changed, 2 insertions(+), 1 deletion(-)
Windows y el bit de ejecución

En Git Bash, chmod +x marca el fichero como ejecutable y Git lo respeta. Pero el bit no viaja igual por todos los sistemas de ficheros de Windows, así que tras clonar conviene comprobar que el hook se ejecuta. Una alternativa robusta y multiplataforma es que el hook sea un script de shell mínimo que llame a Node, o que todos los hooks estén en un directorio versionado más un paso de configuración (core.hooksPath).

core.hooksPath: hooks versionados

Como .git/hooks no se comparte, la práctica habitual es guardar los hooks en una carpeta versionada del proyecto (por ejemplo .githooks/) y apuntar Git allí:

git config core.hooksPath .githooks

A partir de ese momento, Git ignora .git/hooks y busca en .githooks/. La ruta relativa se resuelve desde la raíz del repositorio, así que funciona igual en cualquier clon. Lo que no se clona es el ajuste de configuración: cada persona debe ejecutarlo una vez (idealmente con un script de arranque del proyecto).

.githooks/
├── commit-msg        ← versionado, con shebang
└── pre-push
scripts/
└── check-commit.mjs  ← la lógica real, compartida con la CI

Y una idea que ahorra duplicación: que el hook sea una envoltura mínima de un script versionado, el mismo que usa la CI. Así la regla se escribe una vez:

#!/usr/bin/env bash
# .githooks/commit-msg
exec node "$(git rev-parse --show-toplevel)/scripts/check-commit.mjs" "$1"
Un script, dos consumidores

Si el hook local y la CI ejecutan node scripts/check-commit.mjs, no hay dos reglas que mantener sincronizadas. La CI puede invocarlo sobre git log base..HEAD para validar todos los commits de un PR, mientras el hook valida solo el que estás escribiendo. Una sola fuente de verdad para la convención.

pre-push: la última puerta antes del remoto

pre-push recibe dos argumentos (nombre y URL del remoto) y, por stdin, una línea por referencia con cuatro campos separados por espacios: <local ref> <local sha> <remote ref> <remote sha>. Si el local sha es todo ceros, la operación es un borrado; si lo es el remoto, es una rama nueva.

#!/usr/bin/env bash
# .githooks/pre-push
while read -r local_ref local_sha remote_ref remote_sha; do
  if [ "$remote_ref" = "refs/heads/main" ] && [ "$local_sha" != "0000000000000000000000000000000000000000" ]; then
    echo "pre-push: este repositorio no acepta push directo a main."
    echo "Abre una rama y un pull request."
    exit 1
  fi
done
exit 0

Bloquear el push directo a main desde el hook es una red local útil, pero recuerda: es local. La protección real de main se configura en el remoto (reglas de rama / pre-receive), porque nadie puede saltarse lo que ocurre en el servidor.

Los hooks no son un control de seguridad

git commit --no-verify y git push --no-verify se saltan pre-commit y commit-msg; un hook puede borrarse o no instalarse. Nunca pongas en un hook una comprobación de la que dependa la seguridad del proyecto —que no haya secretos, que no se toquen ciertas ramas, que los datos sean válidos—: ponlo también en la CI y en la protección del remoto. El hook es una conveniencia; la CI, el contrato.

Regla de reparto de responsabilidades:

  • pre-commit: formato, lint, ficheros prohibidos. Rápido y arreglable automáticamente.
  • commit-msg: convención del mensaje. Instantáneo, sin dependencias.
  • pre-push: tests, cobertura mínima, bloqueos locales. Un poco más lento, pero antes de publicar.
  • CI: todo lo anterior más lo que no puede depender de la buena voluntad: seguridad, integración, despliegue.
Hooks rápidos o hooks odiados

Un pre-commit de treinta segundos se convierte en --no-verify en una semana. Si tu linter tarda, pásalo a pre-push o ejecútalo solo sobre los ficheros que han cambiado. La utilidad de un hook es proporcional a lo poco que molesta.

3 · Ejemplo mínimo

Instala el hook commit-msg de la teoría en taller y pruébalo:

cd taller
ls .git/hooks/commit-msg.sample
chmod +x .git/hooks/commit-msg
git commit --allow-empty -m "cambios varios"
commit-msg: mensaje inválido -> "cambios varios"
Formato: tipo(alcance): resumen en imperativo (<= 72 caracteres)

Git aborta el commit: no se ha creado nada. Prueba un mensaje conforme:

git commit --allow-empty -m "chore(hooks): probar commit-msg"
[main 7d4b2e8] chore(hooks): probar commit-msg

Y comprueba que el hook no se limita a los mensajes de una línea: lo que valida es la primera línea del fichero, así que el cuerpo del commit puede ser tan largo como quieras.

Los merges también pasan por el hook

commit-msg se ejecuta también en commits de merge, con el mensaje por defecto «Merge branch …». El script de arriba los exime con la comprobación de Merge . Si tu repositorio usa squash-merge, el mensaje que se valida al fusionar puede ser otro; coordina la convención con la forja.

4 · Ejemplo real

Escenario: un equipo quiere mensajes consistentes sin depender de la memoria de cada persona, y quiere detectar errores de sintaxis antes de publicar. Monta hooks versionados que comparten la lógica con la CI.

Paso 1 · La lógica, en un script versionado.

#!/usr/bin/env node
// scripts/check-commit.mjs
import { readFileSync } from 'node:fs';

const allowed = ['feat', 'fix', 'docs', 'style', 'refactor', 'perf', 'test', 'build', 'ci', 'chore', 'revert'];

export function validate(subject) {
  if (subject.startsWith('Merge ')) return null;
  const match = subject.match(/^(\w+)(?:\(([a-z0-9-]+)\))?!?: (.+)$/);
  if (!match) return 'formato: tipo(alcance): resumen';
  const [, type, , summary] = match;
  if (!allowed.includes(type)) return 'tipo no permitido: ' + type;
  if (summary.length > 72) return 'el resumen supera 72 caracteres';
  return null;
}

const file = process.argv[2];
if (file) {
  const error = validate(readFileSync(file, 'utf8').split('\n')[0].trim());
  if (error) {
    console.error('commit-msg: ' + error);
    process.exit(1);
  }
}

Paso 2 · Los hooks, que solo delegan.

#!/usr/bin/env bash
# .githooks/commit-msg
exec node "$(git rev-parse --show-toplevel)/scripts/check-commit.mjs" "$1"
#!/usr/bin/env bash
# .githooks/pre-commit
set -e
staged=$(git diff --cached --name-only --diff-filter=ACM -- '*.js' '*.mjs')
[ -z "$staged" ] && exit 0
for f in $staged; do
  node --check "$f"
done

Paso 3 · Activarlos en cada clon.

git config core.hooksPath .githooks
chmod +x .githooks/commit-msg .githooks/pre-commit
git commit -m "chore(hooks): añadir validación de mensajes"
[main 2c8f1a0] chore(hooks): añadir validación de mensajes
 3 files changed, 34 insertions(+)
 create mode 100755 .githooks/commit-msg
 create mode 100755 .githooks/pre-commit
 create mode 100644 scripts/check-commit.mjs

Paso 4 · La CI usa el mismo script. En el workflow, sobre todos los commits del PR:

git log --format=%s origin/main..HEAD | while read -r subject; do
  node -e "import('./scripts/check-commit.mjs').then(m => { const e = m.validate(process.argv[1]); if (e) { console.error(e); process.exit(1); } })" "$subject"
done

Paso 5 · Comprobación del hook en acción. Un compañero intenta un mensaje sin tipo:

$ git commit -m "subida rápida"
commit-msg: formato: tipo(alcance): resumen

Y con un tipo no permitido:

$ git commit -m "wip(api): probando"
commit-msg: tipo no permitido: wip

Ambos commits se abortan en local, sin crear ruido en la historia remota. Y si alguien usa --no-verify, la CI del PR lo rechazará igualmente, porque ejecuta el mismo check-commit.mjs.

Lo importante del montaje

La regla vive en un solo sitio (scripts/check-commit.mjs). Los hooks son envoltorios que se activan con un comando; la CI es el árbitro que no se puede saltar. Y los tres ficheros están versionados, así que cualquier persona nueva del equipo los recibe al clonar y solo necesita ejecutar una vez git config core.hooksPath .githooks.

6 · Errores habituales

1. Creer que el hook viaja con el repositorio

Mal — asumir que todos lo tienen 
# en tu máquina, el hook está en .git/hooks/commit-msg
git push
# tu compañero clona: su .git/hooks está vacío de lógica
Bien — versionarlo y activarlo 
mkdir -p .githooks
git config core.hooksPath .githooks
git add .githooks/commit-msg
git commit -m "chore(hooks): versionar validación de mensajes"

.git/ es tu copia de la base de datos, no el proyecto. Lo que se comparte es lo que está versionado. core.hooksPath sigue sin clonarse, así que documenta el comando (o inclúyelo en un script de arranque).

2. Hook lento en pre-commit

Mal — bloquear cada commit con la suite entera 
# .git/hooks/pre-commit
npm run test:e2e        # 4 minutos por cada commit
npm run build
npm run lint
Bien — rápido en commit, completo en push o CI 
# .githooks/pre-commit
npx lint-staged          # solo lo que cambia
# la suite completa, en pre-push (o en la CI)

Un pre-commit que cuesta minutos se desactiva mentalmente y luego de verdad. Divide: formato y lint sobre los ficheros tocados en pre-commit, tests en pre-push, integración en CI.

3. Usar hooks como control de seguridad

Mal — confiar la protección a algo saltable 
# .githooks/pre-commit: "no subir secretos"
git commit --no-verify -m "feat: config"   # el hook no se ejecuta
# el secreto llega al remoto igualmente
Bien — defensa en profundidad 
# hook local (feedback rápido)
# + escaneo de secretos en CI (bloqueante)
# + revisión y reglas de rama en el remoto

Los hooks pre-commit y commit-msg se saltan con --no-verify. Si un fallo tiene consecuencias graves, la comprobación debe estar también donde no se pueda eludir. El hook evita el error honesto; la CI evita el error de todos.

7 · Ejercicio guiado

Objetivo: instalar un commit-msg en .git/hooks, comprobar el rechazo, moverlo a .githooks/ versionado y activarlo con core.hooksPath.

  1. Crea el hook en el lugar por defecto. Escribe en .git/hooks/commit-msg el script Node de la teoría y hazlo ejecutable: 
    chmod +x .git/hooks/commit-msg
  2. Prueba un mensaje inválido. 
    git commit --allow-empty -m "varios cambios"
echo "código de salida: $?"

    Debe imprimir el error y terminar con código 1.

  3. Prueba un mensaje válido. 
    git commit --allow-empty -m "docs(hooks): documentar commit-msg"
  4. Versiona el hook y cambia la ruta. 
    mkdir -p .githooks
mv .git/hooks/commit-msg .githooks/commit-msg
git config core.hooksPath .githooks
git add .githooks/commit-msg
git commit -m "chore(hooks): versionar commit-msg"
  5. Comprueba que sigue funcionando desde el clon de otra persona. Clona el repositorio en otra carpeta, ejecuta el paso de configuración y prueba: 
    git clone ../taller taller-2
cd taller-2
git config core.hooksPath .githooks
chmod +x .githooks/commit-msg
git commit --allow-empty -m "sin formato"
Solución resuelta

Salida esperada del paso 2:

commit-msg: mensaje inválido -> "varios cambios"
Formato: tipo(alcance): resumen en imperativo (<= 72 caracteres)
código de salida: 1

Y del paso 5, en el clon nuevo:

commit-msg: mensaje inválido -> "sin formato"

El commit no se crea --allow-empty aparte. La conclusión clave: el clon nuevo recibió el fichero porque está versionado, pero no recibió la configuración core.hooksPath: sin ejecutarla, Git seguiría usando .git/hooks (vacío) y no validaría nada. Ese comando es el paso que hay que documentar.

8 · Reto

Reto

Amplía el montaje del ejemplo real con tres reglas nuevas, todas usando el mismo script versionado como fuente de verdad:

1) En commit-msg, el alcance (scope) debe pertenecer a una lista permitida (api, ui, hooks, docs) y ser obligatorio para los tipos feat y fix. 2) En pre-commit, rechazar cualquier fichero preparado que se llame .env o termine en .pem. 3) En pre-push, impedir el push directo a main, pero permitir el de una rama de feature.

Después haz que la CI del PR valide los commits con la misma lógica, de forma que un --no-verify no sirva para colar un mensaje mal formado. Demuestra los tres casos (mensaje rechazado, fichero bloqueado y push a main detenido) y explica qué queda fuera del alcance de los hooks y debe vivir en el remoto.

Pista: pre-commit solo ve lo que está en el índice, así que recorre git diff --cached --name-only; pre-push lee las refs por stdin, y el borrado de una rama remota llega con local_sha a ceros. Antes de bloquear algo en un hook, pregúntate quién podría saltárselo y dónde debe estar la misma regla para que no dependa de la buena voluntad.

9 · Resumen

  • Un hook es un script que Git ejecuta en un momento concreto; si sale con código distinto de cero, la operación se aborta.
  • Viven en .git/hooks, que no se versiona ni se clona; los ejemplos llevan .sample y no se ejecutan.
  • pre-commit (rápido, sobre el índice), commit-msg (recibe el fichero del mensaje) y pre-push (recibe el remoto y las refs por stdin).
  • core.hooksPath permite tener los hooks versionados en .githooks/; el ajuste hay que ejecutarlo en cada clon.
  • Que el hook y la CI llamen al mismo script elimina la duplicación de la regla.
  • Los hooks son comodidad, no seguridad: --no-verify los salta. Lo crítico vive en la CI y en la protección del remoto.

10 · Preguntas frecuentes

¿Por qué mi hook no se ejecuta?

Tres causas habituales: el fichero tiene extensión .sample o el nombre no es exacto (commit-msg, no commit_msg); no tiene permiso de ejecución (en Git Bash, chmod +x); o tienes core.hooksPath apuntando a otra carpeta, con lo que Git ignora .git/hooks. Comprueba con git config --get core.hooksPath y con git hook run commit-msg -- <fichero> si tu versión lo soporta.

¿--no-verify salta todos los hooks?

Salta pre-commit y commit-msg en el caso de git commit --no-verify, y pre-push en el de git push --no-verify. Es una escotilla deliberada para casos de emergencia. Por eso ningún control crítico puede depender solo de un hook: la CI y la configuración del remoto no se pueden saltar desde el cliente.

¿Los hooks funcionan igual en Windows?

Los scripts de shell se ejecutan con el sh que incluye Git for Windows (Git Bash), siempre que tengan un shebang válido. El bit de ejecución no se propaga igual entre sistemas de ficheros, así que tras clonar conviene verificar que el hook corre y, si no, marcarlo como ejecutable. Escribir la lógica en Node con shebang y una envoltura de shell mínima es la opción más portable.

¿Puedo ejecutar un hook manualmente para probarlo?

Sí. commit-msg espera la ruta de un fichero con el mensaje: puedes probar con echo "feat(api): prueba" > /tmp/msg && .githooks/commit-msg /tmp/msg. pre-push lee de stdin, así que necesitas simular una línea con los cuatro campos. Prueba siempre el camino de error: es el que protege.

¿Un hook puede modificar los ficheros del commit?

pre-commit puede, por ejemplo, un formateador que reescribe ficheros. Pero Git ya ha construido el commit con el estado del índice: si el hook modifica ficheros, esos cambios quedan en el directorio de trabajo y no en el commit. El hook debe hacer git add de lo que cambió (o fallar y pedirte que lo hagas). Los post-* no pueden abortar la operación; los pre-*, sí.
