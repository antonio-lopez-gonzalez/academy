Pull requests: revisar una propuesta

Módulo 5 · Remotos 🕐 35 minutos

1 · Introducción

Un pull request (PR) no es un comando de Git. Git no sabe qué es un PR: no hay git request-pull que abra una discusión en una web. El PR es una capa que añade la forja (GitHub, GitLab, Bitbucket…) sobre dos cosas que sí son de Git: una rama y una diferencia contra otra rama.

Piensa en él como una propuesta: «estos commits, sobre esta base, producen este cambio; ¿lo aceptamos?». La forja guarda la conversación, el estado de la CI y el botón de merge. Pero revisar bien un PR es una habilidad de Git: leer el diff correcto, ejecutar el código en tu máquina si hace falta y distinguir lo que el autor dice de lo que el commit hace.

¿Por qué existe esta lección?

Porque «funciona en mi máquina» no es una revisión, y «se ve bien» tampoco. El objetivo de un PR es reducir el riesgo de integrar un cambio antes de que llegue a main. Eso exige mirar el diff con el comando adecuado, entender qué entra y qué no, y atreverse a pedir cambios. Un revisor que no entiende el diff aprueba por confianza; y la confianza no compila.

2 · Teoría

Qué hay debajo del botón «Create pull request»

Un PR conecta dos ramas:

  • base: la rama de destino, normalmente main. Es el punto de partida de la comparación.
  • head (o compare): la rama con tus commits, normalmente en tu fork o en el mismo repositorio.
        commits del PR
        ┌───────────────┐
    A───B───C───D───E───F   feature/pagos  (head)
    │
    └── base común (merge-base)

    main: A───B───X───Y     (base)

    El PR muestra: D, E y F (lo que no está en main)
    y el diff: merge-base → F

El botón de merge ejecuta, según la estrategia, un merge, un squash o un rebase sobre la base. La forja no hace magia: hace Git en el servidor y actualiza la rama de destino.

Qué puntero mueve aceptar un PR

Mueve la rama base en el remoto (main) al resultado de la integración. La rama head no se mueve; si el PR se fusiona con squash o rebase, sus commits originales quedan fuera de main y la rama puede borrarse. Tu rama local no cambia hasta que hagas fetch y actualices.

Revisar por diff, con los comandos correctos

La forja te muestra una pestaña «Files changed», pero para revisar en serio conviene traer la rama y usar Git:

git fetch origin
git switch -c review/pagos origin/feature/pagos   # rama local para revisar
git log --oneline main..feature/pagos              # commits del PR
git diff --stat main...feature/pagos               # qué ficheros toca
git diff main...feature/pagos                      # el cambio completo

La diferencia entre dos y tres puntos es la trampa clásica:

ComandoQué comparaPara qué
git log main..featureCommits alcanzables desde feature y no desde mainVer solo los commits del PR
git log main...featureDiferencia simétrica: commits de un lado y del otroVer qué ha divergido cada rama
git diff main..featureEstado actual de main contra estado actual de featurePuede incluir cambios que main recibió después de abrir el PR
git diff main...featureDesde la base común hasta featureEl diff real del PR, sin ruido de main
Dos puntos y tres puntos no significan lo mismo en log y en diff

En diff, A...B significa «desde el merge-base de A y B hasta B». En log, A...B significa «commits en A o en B pero no en ambos» (diferencia simétrica). Es una inconsistencia histórica de Git. Regla mnemotécnica: para revisar un PR, git diff main...feature (tres puntos) es casi siempre lo que quieres; para listar commits, git log main..feature (dos puntos).

Si quieres revisar el PR como si fuera una rama local y ejecutar sus tests:

git switch review/pagos
npm ci          # instala exactamente el lockfile
npm test

Y si solo quieres ver un commit concreto, git show <hash>. Para revisar una versión actualizada sin releer todo, git range-diff main review/pagos@{1} review/pagos compara la versión anterior y la nueva commit a commit.

«Funciona en mi máquina» no es evidencia

El autor ejecutó el código en su entorno. Eso no prueba que funcione en el tuyo, en el de CI ni en producción. Las diferencias típicas:

DiferenciaQué puede romperCómo lo detectas
Dependencias no fijadasUna versión distinta cambia el comportamientonpm ci, lockfile en el diff
Variables de entornoEl código asume una config que solo tú tienesBuscar process.env en el diff
Zona horaria / localeFechas y ordenaciones distintasTests con fechas fijas, no con new Date()
Sistema de ficherosRutas con \, mayúsculas, permisosCI en Linux + prueba en Windows si aplica
Estado de la base de datosMigraciones que asumen datos existentesRevisar migraciones y rollback
Caché del buildUn artefacto viejo oculta el falloClon limpio + build desde cero

Por eso la CI no es burocracia: es un entorno reproducible que no comparte tu caché ni tus variables. Un PR sin CI verde es una hipótesis, no un cambio listo.

Tres formas de fusionar

Merge commitSquash mergeRebase merge
Qué produce en mainUn commit con dos padres + todos los commits de la ramaUn solo commit con todo el cambioLos commits de la rama, reaplicados uno a uno
Hashes originalesSe conservanSe pierdenCambian
HistoriaSe ve la rama y cuándo se integróLineal, pero sin granularidadLineal y con granularidad
Revertir una partePosible por commitNo: hay que revertir todo el squashPosible por commit
Buena paraRamas grandes, releases, trazabilidadRamas con commits de proceso (wip, fix)Ramas ya limpias y atómicas

No hay una «correcta» universal: hay una convención del repositorio. Lo importante es que el equipo sepa cuál usa y que el historial resultante sea coherente. Si el repo usa squash, no abras un PR con veinte commits esperando que se conserven; si usa merge commit, no te obsesiones con limpiar cada mensaje.

Squash y la rama local

Tras un squash-merge, tus commits originales no están en main: hay uno nuevo con el mismo contenido. Si sigues trabajando en la rama y haces git pull main, Git puede ver los mismos cambios dos veces. El flujo sano es: fusionado el PR, borra la rama, actualiza main y crea una nueva para lo siguiente.

Revisar sin miedo

Revisar no es aprobar. Es una conversación técnica sobre un diff, y el revisor tiene más poder del que cree:

  • Puede ejecutarlo en una rama local sin tocar la del autor.
  • Puede pedir cambios sin bloquear el proyecto: el PR sigue abierto y el autor itera.
  • Puede preguntar «¿por qué este commit?» sin que sea un ataque. El diff es el objeto de la conversación, no la persona.
  • No puede romper nada con solo leer: el botón de merge es otra decisión.

Un PR pequeño se revisa mejor que uno grande. Si el diff tiene 2.000 líneas, la revisión será superficial aunque no quieras. Parte del trabajo del autor es hacer revisable el cambio: commits atómicos, descripción con contexto, y separar refactor de funcionalidad.

Qué mirarPregunta concreta
Alcance¿El diff hace solo lo que dice la descripción?
Pruebas¿Hay tests para el caso nuevo y para el error?
Errores¿Qué pasa si la entrada es nula, vacía, enorme o duplicada?
Compatibilidad¿Rompe una API, un formato de datos o una migración?
Seguridad¿Hay secretos, logs de datos sensibles, permisos de más?
Rendimiento¿Añade una consulta dentro de un bucle?
Mensajes¿Los commits explican el porqué o solo el qué?

3 · Ejemplo mínimo

Simula un PR con un remoto local. La rama feature/informe tiene dos commits sobre main:

git fetch origin
git log --oneline main..origin/feature/informe
9f3c1a7 test(informe): cubrir informe vacío
4b8a2f3 feat(informe): generar informe mensual
        
git diff --stat main...origin/feature/informe
 src/informe.js      | 42 ++++++++++++++++++++++++++++++++++++++++++
 test/informe.test.js | 18 ++++++++++++++++++
 2 files changed, 60 insertions(+)
        
git diff main...origin/feature/informe
diff --git a/src/informe.js b/src/informe.js
new file mode 100644
index 0000000..3f2a1c4
--- /dev/null
+++ b/src/informe.js
@@ -0,0 +1,42 @@
+export function generarInforme(filas) {
+  if (filas.length === 0) {
+    return { total: 0, lineas: [] };
+  }
+  // ...
+}

Ya tienes lo esencial de la revisión: dos commits, dos ficheros y el contenido exacto. La forja te lo muestra en HTML; estos comandos te dan la verdad sin depender de cómo la pinte.

Revisar no exige permiso de escritura

Puedes hacer git fetch y revisar el diff aunque no tengas permiso de push en el repositorio. La rama remota es de solo lectura para ti, pero sus objetos están en tu clon. Para ejecutar los tests, crea una rama local desde origin/feature/informe; para comentar, usa la forja.

4 · Ejemplo real

Escenario: un PR de siete commits titulado «Añadir autenticación por token». El autor dice que «funciona y los tests pasan». Lo traes y lo revisas:

git fetch origin
git log --oneline main..origin/feature/auth
a1b2c3d wip
9f8e7d6 fix tests
4c3b2a1 console.log del token
8d7c6b5 feat(auth): validar expiración
7a6b5c4 test(auth): token expirado
6f5e4d3 feat(auth): middleware de token
5e4d3c2 chore: renombrar helper

El título promete autenticación; el log cuenta otra cosa: un wip, un fix tests y un commit que imprime el token en consola. Antes de mirar el código, ya tienes tres preguntas legítimas. Revisas el diff neto:

git diff main...origin/feature/auth -- src/auth.js
+export function verificarToken(req, res, next) {
+  const token = req.headers.authorization?.split(' ')[1];
+  console.log('token recibido:', token);
+  if (!token) return res.status(401).json({ error: 'sin token' });
+  try {
+    const payload = jwt.verify(token, process.env.JWT_SECRET);
+    if (payload.exp * 1000 < Date.now()) {
+      return res.status(401).json({ error: 'token expirado' });
+    }
+    req.user = payload;
+    next();
+  } catch {
+    return res.status(401).json({ error: 'token inválido' });
+  }
+}

El código funciona, pero el console.log filtra un token en los logs: un problema de seguridad real. Y no hay test para el caso «sin token». Escribes la revisión:

- [bloqueante] src/auth.js:3 imprime el token en consola. Los logs se
  retienen y se comparten; hay que quitarlo antes de fusionar.
- [bloqueante] Falta test para petición sin cabecera Authorization.
- [sugerencia] El commit "wip" y "fix tests" pueden unirse antes del merge.

El autor responde: elimina el log, añade el test, limpia la historia con rebase -i y actualiza la rama. Cuando vuelve, no relees los siete commits desde cero: comparas versiones.

git fetch origin
git range-diff main review/auth@{1} origin/feature/auth
1: 5e4d3c2 = 1: 0f1e2d3 chore: renombrar helper
2: 6f5e4d3 ! 2: 2a3b4c5 feat(auth): middleware de token
    @@ src/auth.js
    -  console.log('token recibido:', token);
3: 7a6b5c4 = 3: 3b4c5d6 test(auth): token expirado
4: 8d7c6b5 = 4: 4c5d6e7 feat(auth): validar expiración
5: 4c3b2a1 < -: ------- console.log del token
6: 9f8e7d6 < -: ------- fix tests
7: a1b2c3d < -: ------- wip

El range-diff confirma que el único cambio de contenido es la eliminación del log, y que los commits de ruido desaparecieron. El autor añadió el test en el commit 3. Ahora sí: CI verde, revisión aprobada y squash-merge, porque la rama todavía tenía commits de proceso y el repositorio usa esa convención.

git switch main
git pull --ff-only
git log --oneline -3
b7e2f90 (HEAD -> main, origin/main) feat(auth): autenticación por token (#142)
9f3c1a7 docs: actualizar guía
1a2b3c4 feat: base

Un solo commit en main, con el número de PR en el mensaje. La rama feature/auth se borra. Y si meses después hay que revertir la autenticación, git revert b7e2f90 deshace todo el PR de una vez: esa es la contrapartida del squash.

Lo que hizo buena la revisión

No fue «leer todo el código». Fue comparar lo prometido con lo que el diff hacía: título, commits y contenido. El console.log estaba a la vista; nadie lo habría encontrado confiando en «funciona en mi máquina», porque en la máquina del autor efectivamente funcionaba. La revisión busca riesgo, no confirmación.

6 · Errores habituales

1. Revisar con dos puntos y ver cambios que no son del PR

Mal — mezclar main con el PR 
git diff main..origin/feature/auth
# incluye lo que main recibió después de abrir el PR:
# parece que el autor cambió cosas que nunca tocó
Bien — comparar desde la base común 
git diff main...origin/feature/auth
# solo el cambio del PR
git log --oneline main..origin/feature/auth

Si main avanzó desde que se abrió el PR, main..feature compara dos estados actuales y muestra como «eliminado» lo que main añadió. El diff de tres puntos parte del ancestro común y refleja únicamente lo que el PR propone.

2. Aprobar sin ejecutar nada

Mal — confiar en el mensaje 
"He probado en local y funciona, los tests pasan."
→ Aprobado sin abrir el diff ni mirar qué tests son.
Bien — comprobar el entorno reproducible 
git switch -c review/auth origin/feature/auth
npm ci
npm test
git diff main...HEAD --stat

«Funciona en mi máquina» describe un entorno, no un contrato. npm ci instala el lockfile exacto; la CI ejecuta en un contenedor limpio; tu clon puede tener variables o caché que oculten el fallo. La revisión verifica, no confirma.

3. Fusión con squash y seguir en la rama

Mal — duplicar el cambio 
# PR fusionado con squash en main
git switch feature/auth
git commit -am "fix(auth): ajuste posterior"
git pull main
# Git ve el cambio del squash y el de la rama como dos historias
Bien — cerrar la rama y partir de main 
git switch main
git pull --ff-only
git branch -d feature/auth
git switch -c feature/auth-ajuste

Con squash, los commits originales no están en main; el contenido sí. Si continúas la rama y la vuelves a fusionar, puedes reintroducir cambios ya integrados o generar conflictos artificiales. La rama fusionada es historia; el trabajo nuevo empieza de main.

7 · Ejercicio guiado

Objetivo: revisar un PR simulado con un remoto local, detectar un fallo en el diff, pedir el cambio y verificar la nueva versión con range-diff.

  1. Prepara el escenario. 
    git init --bare remoto.git
git clone remoto.git trabajo
cd trabajo
printf 'export const total = (xs) => xs.reduce((a, b) => a + b, 0);\n' > total.js
git add total.js
git commit -m "feat: total"
git push -u origin main
  2. Crea la rama del PR con un fallo intencionado. 
    git switch -c feature/descuento
printf 'export const descuento = (total, pct) => total - total * pct;\n' >> total.js
git commit -am "feat(descuento): aplicar porcentaje"
git push -u origin feature/descuento

    El fallo: pct se usa como fracción (0,1) pero el nombre sugiere porcentaje (10).

  3. Revisa como si fueras otra persona. 
    cd ..
git clone remoto.git revisor
cd revisor
git fetch origin
git log --oneline main..origin/feature/descuento
git diff main...origin/feature/descuento
  4. Escribe dos comentarios: uno bloqueante por la unidad de pct y uno de sugerencia para añadir un test con pct = 10.
  5. Corrige en la rama original y actualiza. 
    cd ../trabajo
git switch feature/descuento
printf 'export const descuento = (total, pct) => total - total * (pct / 100);\n' > total.js
git commit -am "fix(descuento): interpretar pct como porcentaje"
git push
  6. Verifica qué cambió desde la revisión anterior. 
    cd ../revisor
git fetch origin
git range-diff main origin/feature/descuento@{1} origin/feature/descuento
Solución resuelta

El diff del paso 3 debe mostrar una sola línea añadida y la ausencia de tests. Los comentarios correctos serían:

[bloqueante] total.js:2 — `pct` se resta como fracción, pero el nombre
indica porcentaje. Con pct = 10 el descuento es 10 veces el total.
[sugerencia] Añadir test con pct = 10 y con pct = 0.

Y el range-diff del paso 6 debe mostrar un único cambio en la línea del cálculo:

1: 4b8a2f3 ! 1: 9f3c1a7 feat(descuento): aplicar porcentaje
    @@ total.js
    -export const descuento = (total, pct) => total - total * pct;
    +export const descuento = (total, pct) => total - total * (pct / 100);

El revisor no necesita releer todo: el range-diff demuestra que el único cambio es el solicitado. Eso es una re-revisión eficiente.

8 · Reto

Reto

Recibe un PR de cinco commits que «mejora el rendimiento del listado». El autor asegura que los tests pasan. Al revisar el diff, todo parece correcto: cambia una consulta, añade un índice y actualiza un test. Pero hay un cambio de comportamiento escondido: el listado ahora ordena por fecha descendente en vez de ascendente, y un consumidor externo dependía del orden anterior.

Localiza el commit que introduce el cambio con git log -S o git log -p, demuestra con git diff main...feature qué línea lo provoca y escribe una revisión que distinga el objetivo declarado (rendimiento) del cambio funcional no anunciado (orden). Decide además si pedir un commit nuevo, un revert parcial o un cambio de contrato documentado, y justifica la decisión.

Pista: el diff de rendimiento puede ocultar un sort que cambió de dirección; busca en el historial con git log -S "sort(" --oneline main..feature y compara el test modificado con el original. Un test que se actualiza para seguir pasando es una señal de alarma, no una prueba de que nada se rompió.

9 · Resumen

  • Un PR es una propuesta de merge entre una base y una rama head; la forja añade discusión y CI, pero el merge es Git.
  • Para revisar: fetch, git log main..feature (commits) y git diff main...feature (cambio real desde la base común).
  • En diff, tres puntos = desde el merge-base; en log, tres puntos = diferencia simétrica. No son intercambiables.
  • «Funciona en mi máquina» no es evidencia: usa un clon limpio, el lockfile y la CI.
  • Merge commit, squash y rebase producen historias distintas; sigue la convención del repositorio.
  • Revisar es comparar lo prometido con lo que hace el diff, y pedir cambios sin miedo. Un PR pequeño se revisa mejor.

10 · Preguntas frecuentes

¿Un pull request y un merge son lo mismo?

No. El PR es una propuesta y una conversación; el merge es la operación de Git que la acepta. La forja puede cerrar un PR sin fusionarlo (descartado) o fusionarlo de tres formas distintas. En un flujo sin forja, el equivalente es pedir a alguien que revise tu rama y luego hacer git merge tú mismo.

¿Por qué mi PR muestra cambios de main que yo no hice?

Porque la rama está desactualizada y la comparación se hizo con dos puntos, o porque la forja compara contra el estado actual de la base. Actualiza tu rama con git rebase origin/main (si es tuya) o git merge origin/main (si es compartida) y vuelve a mirar. Con git diff main...feature en local verás solo lo tuyo.

¿Debo aprobar si la CI está verde?

La CI verde es una condición necesaria, no suficiente. Puede no cubrir el caso límite que te preocupa, puede estar ejecutando una versión antigua del workflow o puede pasar porque el test se adaptó al nuevo comportamiento. Mira qué prueba, no solo que pase. Si el diff cambia una API pública, revisa la compatibilidad aunque los tests estén en verde.

¿Squash o merge commit?

Depende de la convención y del valor de la granularidad. Squash deja main limpio y es ideal para ramas con commits de proceso; merge commit conserva la historia y permite revertir por commit. Rebase merge es el punto medio para ramas ya atómicas. Lo importante es que el equipo use la misma regla y que el mensaje final del squash sea bueno, porque será lo único que quede.

¿Cómo reviso un PR enorme sin morir en el intento?

Por capas: primero git diff --stat para ver el alcance, luego los ficheros de lógica, después los tests, y al final el ruido (formato, lockfiles). Si es imposible, pide al autor que lo parta: un PR de 2.000 líneas no se revisa, se aprueba. También ayuda revisar commit a commit con git log -p main..feature si la historia está limpia.
