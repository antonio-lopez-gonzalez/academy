push y ramas de seguimiento

Módulo 5 · Remotos 🕐 35 minutos

1 · Introducción

fetch y pull traen; push lleva. En apariencia es el comando más simple del curso: subir tus commits. Pero push es también el momento en que tu trabajo deja de ser privado, y con ello cambian las reglas: lo que publicas puede romper la build de otro, y lo que reescribes puede borrar el trabajo de otro.

Esta lección cubre tres cosas que van juntas: cómo decirle a Git a dónde empujar sin repetirlo cada vez (upstream), por qué el servidor rechaza un push cuando las historias divergen, y cómo publicar tags —esas etiquetas que marcan una release y que no se envían solas.

¿Por qué existe esta lección?

Porque el rechazo non-fast-forward es el error que más gente resuelve mal. La solución que aparece en foros es --force, y esa solución borra commits ajenos. Entender por qué Git se niega convierte el error en una conversación: «alguien publicó algo que yo no tengo; voy a integrarlo». Eso es todo.

2 · Teoría

Qué hace un push

git push origin main pide al remoto: «actualiza tu rama main para que apunte a mi commit X, y aquí tienes los objetos que te faltan». El servidor acepta si el movimiento es fast-forward: el commit actual de su rama debe ser ancestro del nuevo. Así nunca pierde historia.

TU REPOSITORIO                          REMOTO (origin)

  main → C1───C2───C3                     main → C1
                   ↑
                   push main

  Resultado: el remoto avanza C1 → C3. Fast-forward aceptado.

  PERO SI EL REMOTO TIENE ALGO QUE TÚ NO:

  main → C1───C2                          main → C1───X
                   ↑                                    ↑
                   push main                   commit de otra persona

  C3 no desciende de X → el push se rechaza.
Qué puntero mueve push

Mueve la referencia de la rama en el remoto. Tu rama local no cambia, tu HEAD tampoco. Si el push se rechaza, no se mueve nada: el remoto sigue intacto. Por eso un rechazo nunca es una pérdida de datos, es una negativa a sobrescribir.

Upstream: dejar de repetir el destino

La primera vez que publicas una rama, usa -u (--set-upstream):

git switch -c feature/informe
# ...commits...
git push -u origin feature/informe
Enumerating objects: 7, done.
Counting objects: 100% (7/7), done.
Writing objects: 100% (5/5), 612 bytes | 612.00 KiB/s, done.
Total 5 (delta 1), reused 0 (delta 0), pack-reused 0
remote: Create a pull request for 'feature/informe' on the remote.
To ../remoto.git
 * [new branch]      feature/informe -> feature/informe
branch 'feature/informe' set up to track 'origin/feature/informe'.

Ese «set up to track» es el upstream: la pareja (remoto, rama remota) que esta rama local sigue. A partir de ahí, git push y git pull sin argumentos saben qué hacer, y git status puede decirte cuántos commits vas por delante o por detrás.

git branch -vv
* feature/informe 9f3c1a7 [origin/feature/informe] feat(informe): leer configuración
  main            b2e4d68 [origin/main: ahead 2] docs: actualizar índice
Quiero…Comando
Publicar y configurar el upstreamgit push -u origin <rama>
Configurarlo despuésgit branch --set-upstream-to=origin/<rama>
Quitarlogit branch --unset-upstream
Verlogit branch -vv o git remote show origin

El upstream se guarda en .git/config, no en el repositorio versionado:

[branch "feature/informe"]
    remote = origin
    merge = refs/heads/feature/informe

Por eso cada clon lo configura a su manera y no se comparte con el equipo. Es información local sobre «de dónde viene esta rama».

El rechazo no-fast-forward

Alguien publicó un commit en la misma rama. Tu push no desciende de él, así que el servidor se niega:

git push origin main
To ../remoto.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '../remoto.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

El mensaje puede variar (fetch first, non-fast-forward), pero significa lo mismo: hay commits en el remoto que tú no tienes. La solución no es forzar; es integrar:

git fetch origin
git log --oneline HEAD..origin/main        # qué me falta
git rebase origin/main                     # o git merge origin/main
git push origin main
La tentación del --force

git push --force «resuelve» el rechazo borrando el commit ajeno de la rama. Nunca en main. En una rama propia que acabas de reescribir, la herramienta es --force-with-lease, y ya sabes por qué (módulo 4, lección 4). Si el push rechazado es en una rama compartida, la respuesta siempre es integrar, no reemplazar.

Tags: marcar un punto en la historia

Una rama se mueve; un tag no. Es un nombre fijo sobre un commit, ideal para releases. Hay dos tipos:

Cómo se creagit tag v1.0.0git tag -a v1.0.0 -m "..."
Qué esUna referencia directa al commitUn objeto tag con autor, fecha y mensaje
Guarda quién y cuándoNoSí
Se puede firmarNoSí (-s)
Recomendado paraMarcas temporales localesReleases publicadas
 
git switch main
git tag -a v1.4.0 -m "Release 1.4.0: búsqueda por título"
git show v1.4.0
tag v1.4.0
Tagger: Ana <ana@ejemplo.dev>
Date:   Fri Oct 16 18:02:11 2026 +0200

Release 1.4.0: búsqueda por título

commit 9f3c1a7d3e8b7a6f5c4d3e2f1a0b9c8d7e6f5a4b (HEAD -> main)
Author: Ana <ana@ejemplo.dev>
Date:   Fri Oct 16 17:40:02 2026 +0200

    feat(busqueda): filtrar por título

Fíjate: show imprime dos objetos, el tag y el commit. Eso es la prueba de que es anotado. Un tag ligero mostraría solo el commit.

Los tags no se empujan solos. git push envía ramas, no etiquetas. Tienes tres formas:

git push origin v1.4.0        # solo ese tag
git push --tags               # TODOS los tags locales (también ligeros)
git push --follow-tags        # tags anotados alcanzables desde lo que empujas
--follow-tags es el hábito sano

Evita olvidarte del tag de release y evita arrastrar tags personales de prueba. Si publicas un commit con git push --follow-tags, viajan los tags anotados que apuntan a commits de esa historia. --tags es más bruto: sube todo lo que tengas, incluidos v0.0.1-prueba y temporal.

Para borrar:

git tag -d v1.4.0-rc1                 # local
git push origin --delete v1.4.0-rc1   # remoto

Y para comprobar qué hay publicado sin clonar:

git ls-remote --tags origin

3 · Ejemplo mínimo

Primer push de una rama nueva, con upstream:

git switch -c feature/etiquetas
printf '## Etiquetas\n' >> notas.md
git commit -am "feat(etiquetas): nueva sección"
git push -u origin feature/etiquetas
To ../remoto.git
 * [new branch]      feature/etiquetas -> feature/etiquetas
branch 'feature/etiquetas' set up to track 'origin/feature/etiquetas'.

Añade otro commit y prueba el push sin argumentos:

printf -- '- prioritario\n' >> notas.md
git commit -am "feat(etiquetas): marcar prioritario"
git push
To ../remoto.git
   8b2d4e6..9f3c1a7  feature/etiquetas -> feature/etiquetas

Funciona porque el upstream ya está configurado. Sin -u, el primer git push a secas te habría dicho:

fatal: The current branch feature/etiquetas has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin feature/etiquetas
Qué rama empuja git push a secas

Con push.default=simple (el valor por defecto moderno), empuja la rama actual a la rama del mismo nombre en su upstream. No empuja «todas las ramas» ni «main» por sorpresa. Si no hay upstream, falla y te dice cómo configurarlo.

4 · Ejemplo real

Escenario: trabajas en feature/pagos con un compañero. Publicas tus commits, te vas a comer y al volver intentas publicar el último:

git push
To ../remoto.git
 ! [rejected]        feature/pagos -> feature/pagos (fetch first)
error: failed to push some refs to '../remoto.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.

Tu compañero publicó mientras comías. Inspecciona antes de integrar:

git fetch origin
git log --oneline HEAD..origin/feature/pagos
git diff HEAD...origin/feature/pagos
a4d9e21 fix(pagos): validar importe cero

diff --git a/src/pagos.js b/src/pagos.js
index 3f2a1c4..8b2d4e6 100644
--- a/src/pagos.js
+++ b/src/pagos.js
@@ -12,6 +12,9 @@ export function cobrar(importe) {
+  if (importe <= 0) {
+    throw new Error('importe inválido');
+  }

Es un cambio pequeño y compatible con el tuyo. Como la rama es compartida, no rebases: integra con merge para no reescribir el hash de nadie.

git merge origin/feature/pagos
git push
Merge made by the 'ort' strategy.
 src/pagos.js | 3 +++
 1 file changed, 3 insertions(+)

To ../remoto.git
   7e2b9c4..c1f8a3d  feature/pagos -> feature/pagos

Ahora la release. El equipo etiqueta el commit de main que se despliega:

git switch main
git pull --ff-only
git tag -a v1.4.1 -m "Release 1.4.1: validación de importes"
git push origin v1.4.1
To ../remoto.git
 * [new tag]         v1.4.1 -> v1.4.1

Y compruebas que el servidor lo tiene, sin depender de tu copia local:

git ls-remote --tags origin
9f3c1a7d3e8b7a6f5c4d3e2f1a0b9c8d7e6f5a4b    refs/tags/v1.3.0
c1f8a3d2b4e6f8a0c2e4f6a8b0d2e4f6a8b0c2e4    refs/tags/v1.4.0
c1f8a3d2b4e6f8a0c2e4f6a8b0d2e4f6a8b0c2e4    refs/tags/v1.4.1
El tag apunta al commit, no a la rama

Si mañana main avanza, v1.4.1 sigue en c1f8a3d. Eso es lo que hace reproducible un despliegue: git switch --detach v1.4.1 reconstruye exactamente lo que se publicó. Si el tag se moviera con la rama, no serviría para nada. Y por eso un tag publicado no se reubica: se crea otro.

Nunca reetiquetes una release publicada

git tag -f v1.4.1 <otro-commit> y luego push --force del tag cambia lo que ve todo el mundo y rompe la trazabilidad. Si la release salió mal, publica v1.4.2. Un tag es una promesa: «este commit es lo que se desplegó».

6 · Errores habituales

1. Resolver el rechazo con --force

Mal — sobrescribir el trabajo ajeno 
git push
# ! [rejected] main -> main (fetch first)
git push --force origin main
# el commit que había publicado tu compañero deja de estar en main
Bien — integrar y volver a empujar 
git fetch origin
git log --oneline HEAD..origin/main
git rebase origin/main          # rama propia
# o git merge origin/main      # rama compartida
git push origin main

El rechazo no es un obstáculo: es el servidor diciéndote «hay trabajo que no has visto». Si lo fuerzas, ese trabajo desaparece de la rama. En main, la respuesta es siempre integrar.

2. Publicar una release sin el tag

Mal — asumir que push envía tags 
git tag -a v1.4.1 -m "Release 1.4.1"
git push origin main
# el tag existe en tu máquina; en el remoto no
Bien — empujar el tag explícitamente 
git tag -a v1.4.1 -m "Release 1.4.1"
git push origin main
git push origin v1.4.1
# o directamente: git push --follow-tags origin main

Las ramas y los tags son referencias distintas, y push solo envía la rama que le pides. El CI que se dispara con tags no se enterará de nada hasta que el tag llegue al servidor.

3. Usar --tags como sinónimo de «publicar la release»

Mal — arrastrar etiquetas personales 
git tag prueba-local
git tag v1.4.1-rc1
git push --tags
# el remoto recibe también "prueba-local"
Bien — publicar solo lo que toca 
git ls-remote --tags origin        # qué hay ya
git push origin v1.4.1             # solo esta release
git push --follow-tags             # anotados de la historia empujada

Los tags publicados son difíciles de borrar con dignidad: alguien puede haber desplegado desde ellos. Publica pocos y buenos, con nombre y mensaje claros.

7 · Ejercicio guiado

Objetivo: configurar un upstream, provocar un rechazo no-fast-forward, resolverlo sin forzar y publicar un tag anotado.

  1. Prepara el escenario. 
    git init --bare remoto.git
git clone remoto.git trabajo
git clone remoto.git compañero
cd trabajo
printf 'base\n' > notas.md
git add notas.md
git commit -m "feat: base"
git push -u origin main

    Comprueba el upstream: git branch -vv debe mostrar [origin/main].

  2. Publica tú un commit y, sin bajarlo, publica otro el compañero. 
    cd ../trabajo
printf 'mío\n' >> notas.md
git commit -am "feat: mío"
git push

cd ../compañero
git pull
printf 'suyo\n' >> notas.md
git commit -am "fix: suyo"
git push
  3. Intenta publicar tu segundo commit desde trabajo. 
    cd ../trabajo
printf 'mío 2\n' >> notas.md
git commit -am "feat: mío 2"
git push

    Debe fallar con fetch first.

  4. Inspecciona e integra. 
    git fetch origin
git log --oneline HEAD..origin/main
git rebase origin/main
git push
  5. Etiqueta y publica. 
    git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0
git ls-remote --tags origin
Solución resuelta

Salida esperada del paso 3:

To ../remoto.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '../remoto.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.

Y tras el paso 4:

To ../remoto.git
   4f8a1c2..9b7e4d6  main -> main

El paso 5 confirma el tag remoto:

9b7e4d6...    refs/tags/v1.0.0

Si en el paso 4 hubieras usado --force, el commit fix: suyo habría dejado de estar en main y tu compañero habría tenido que recuperarlo desde su reflog. El rebase, en cambio, pone tus dos commits encima del suyo sin perder nada.

8 · Reto

Reto

En el remoto del ejercicio hay ahora tres tags: v1.0.0 (anotado, correcto), v1.0.1-rc1 (ligero, de prueba) y temporal (ligero, apunta a un commit viejo). Además, v1.0.1 se creó por error como ligero y ya está publicado.

Diseña un plan para dejar el remoto con solo tags anotados de release (v1.0.0 y v1.0.1), convirtiendo v1.0.1 en anotado sin cambiar el commit al que apunta. Hazlo sin tocar main y sin usar --force sobre ninguna rama. Documenta qué comandos ejecutaste, qué pasó con cada tag y qué riesgos tiene reemplazar un tag ya publicado.

Pista: borrar un tag local y remoto son dos operaciones distintas; crear un tag anotado sobre un commit existente no mueve ninguna rama; y si alguien ya desplegó desde v1.0.1, reemplazarlo cambia el significado de una referencia publicada. Piensa si el plan correcto es reemplazar o crear una versión nueva.

9 · Resumen

  • push mueve la referencia del remoto; solo se acepta si es fast-forward.
  • -u configura el upstream, que habilita push/pull sin argumentos y los «ahead/behind» de status.
  • Un rechazo no-fast-forward significa «hay commits que no tienes»: fetch, inspecciona, integra y vuelve a empujar.
  • Nunca --force a main ni a ramas compartidas; para ramas propias reescritas, --force-with-lease.
  • Tags ligeros: solo un nombre. Tags anotados: objeto con autor, fecha y mensaje; los recomendados para releases.
  • Los tags no viajan con push: usa git push origin <tag> o --follow-tags; evita --tags a ciegas.

10 · Preguntas frecuentes

¿Qué pasa si empujo una rama con otro nombre local?

Puedes mapearlas explícitamente: git push origin local:remota crea o actualiza remota en el servidor con los commits de local. Luego, con git branch --set-upstream-to=origin/remota local, dejas el seguimiento coherente. Es útil cuando el nombre local no puede coincidir (por ejemplo, porque ya existe una rama remota con ese nombre y otra historia).

¿--force-with-lease sirve también para tags?

Técnicamente puedes forzar un tag, pero no deberías: un tag publicado es una promesa de «este commit es la release». Cambiarlo rompe despliegues y auditorías. Si te equivocaste, crea una versión nueva. Borrar el tag remoto y volver a crearlo es aceptable solo si nadie lo ha consumido y el equipo lo sabe; en caso contrario, trata la etiqueta como inmutable.

¿Por qué el CI no se ha disparado al crear el tag?

Porque el tag existe solo en tu máquina hasta que lo empujas. git tag es local; el workflow del servidor no ve nada. Comprueba con git ls-remote --tags origin y publica con git push origin <tag>. Si aun así no se dispara, revisa el filtro del workflow: puede exigir un patrón concreto (v*) o que el tag sea anotado.

¿Puedo borrar una rama remota?

Sí: git push origin --delete feature/vieja. Borra la referencia en el servidor, no los commits inmediatamente (quedan inalcanzables hasta que el servidor limpie). Hazlo cuando el PR esté fusionado y nadie más la use. En local, el equivalente es git branch -d, que se niega si la rama no está fusionada; -D fuerza y puede perder trabajo.

¿Qué significa «ahead 2, behind 1» en git status?

Que tu rama y su upstream han divergido: tienes dos commits que el remoto no tiene y el remoto tiene uno que tú no tienes. No es un fast-forward en ninguna dirección. Toca integrar (merge o rebase) antes de poder publicar. Ese mensaje solo aparece si hay upstream configurado y has hecho fetch recientemente; si no, la comparación es contra tu última foto.
