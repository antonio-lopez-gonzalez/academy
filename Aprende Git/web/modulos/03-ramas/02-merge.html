merge: unir ramas

Módulo 3 · Ramas 🕐 35 minutos

1 · Introducción

Tienes una rama con trabajo terminado y quieres llevarlo a main. Eso es git merge. La sorpresa llega cuando, según el caso, Git crea un commit nuevo… o no crea ninguno. Esa diferencia —fast-forward frente a merge commit— es la que hace que dos equipos miren el mismo repositorio y vean historias distintas.

merge es un comando no destructivo: no reescribe nada de lo que ya existía. Solo combina dos líneas de desarrollo en una, y en el peor caso te pide que resuelvas a mano las zonas donde las dos tocaron lo mismo. Después de esta lección, esa petición dejará de dar miedo.

La pregunta que responde merge

«Tengo dos punteros de rama y quiero que uno de ellos incluya el trabajo del otro, sin perder nada de ninguno». Todo lo demás —fast-forward, merge commit, conflictos— son detalles de cómo Git consigue ese resultado sin reescribir historia.

2 · Teoría

El punto de partida: la base del merge

        A <-- B <-- C        main
         \
          D <-- E            feature

  merge base = A   (el ancestro común más reciente)

Para fusionar, Git busca primero el ancestro común de las dos puntas. Con ese punto como referencia puede calcular dos diferencias: lo que hizo main desde A y lo que hizo feature desde A. El merge es la combinación de ambas. 

  git merge feature   (estando en main)

     diff(A, main)     -> lo que aportó main    (B, C)
     diff(A, feature)  -> lo que aportó feature (D, E)
     resultado         -> ambos, sin perder ninguno

Fast-forward: cuando no hay nada que combinar

Si desde que creaste feature, main no ha recibido ningún commit, entonces la punta de main es un ancestro directo de la de feature. No hay dos caminos que combinar: solo hay que adelantar el puntero. Eso es un fast-forward, y no crea ningún commit. 

  ANTES                          DESPUÉS DE git merge feature

    main                           main, feature
     |                              |
     v                              v
     A <-- B                        A <-- B
           \                              \
            C <-- D                       C <-- D
                  ^
                  |
              feature

git switch main
git merge feature
# Updating 1a2b3c4..7c6b5a4
# Fast-forward
Fast-forward: la historia parece lineal

Después de un fast-forward, git log no muestra ninguna bifurcación: parece que todo se escribió en main en orden. Eso es cómodo para leer, pero oculta que hubo una rama. Si quieres conservar esa información, se pide un merge commit explícito con --no-ff.

Merge commit: cuando sí hay dos caminos

Si las dos ramas han avanzado, Git no puede limitarse a mover un puntero: necesita crear un commit que tenga dos padres, uno por cada línea. Ese es el commit de merge. 

  git merge feature   (main ha avanzado a C; feature a E)

        A <-- B <-- C -------- M      main
         \                   /
          D <------ E ------/       feature

  M tiene dos padres: C (main) y E (feature)
  El mensaje por defecto: "Merge branch 'feature'"

git merge feature
# Merge made by the 'ort' strategy.
#  src/buscador.js | 42 +++++++++++++++++++++
#  1 file changed, 42 insertions(+)

En un merge commit, HEAD~1 es el primer padre (la rama en la que estabas) y HEAD^2 es el segundo. Esa distinción vuelve a aparecer al revertir un merge, y es la razón de que git revert necesite -m.

Forzar una cosa o la otra

# Crear SIEMPRE un merge commit, aunque se pudiera hacer fast-forward
git merge --no-ff feature
# (abre el editor para el mensaje; --no-edit lo acepta tal cual)

# Rechazar el merge si NO se puede hacer fast-forward
git merge --ff-only feature
# fatal: Not possible to fast-forward, aborting.

# Preparar el merge sin commitear, para revisarlo
git merge --no-commit feature
git diff --staged

# Fusionar acumulando los cambios en el índice, sin commit ni enlace de merge
git merge --squash feature
OpciónQué haceCuándo
--ff (por defecto)Fast-forward si es posible; si no, merge commitEl comportamiento normal
--no-ffSiempre merge commitQuieres que la rama se vea en la historia
--ff-onlySolo fast-forward; aborta si no se puedeQuieres historia lineal y detectar divergencias
--no-commitDeja el resultado preparado, sin commitRevisar o combinar con otros cambios
--squashAplica los cambios al índice; no crea merge ni padreQuieres un solo commit y no conservar la topología
--squash no es un merge de verdad

Con --squash, Git deja los cambios preparados y tú haces un commit normal. No hay segundo padre, así que Git no sabrá que esa rama ya está integrada: un merge posterior intentará aplicarla otra vez. Úsalo cuando quieras aplanar una rama desechable y vayas a borrarla, no como sustituto sistemático del merge.

Conflictos: cuando las dos ramas tocan lo mismo

Si las dos líneas modificaron las mismas líneas de un fichero (o una borró un fichero que la otra editó), Git no puede decidir por ti. Se detiene, deja el merge «en curso» y marca los ficheros: 

git merge feature
# Auto-merging notas.md
# CONFLICT (content): Merge conflict in notas.md
# Automatic merge failed; fix conflicts and then commit the result.

git status --short
# UU notas.md          <- both modified

El proceso completo:

  1. git status para ver qué ficheros están en conflicto.
  2. Abrir cada uno, quedarse con la combinación correcta y borrar los marcadores.
  3. git add <rutas> para marcar como resuelto.
  4. git commit (usa el mensaje de merge preparado) o git merge --continue.
  5. Si te arrepientes: git merge --abort devuelve todo al estado previo.

Los marcadores y las estrategias de resolución tienen lección propia: la siguiente. Aquí basta con saber que el merge se puede abortar en cualquier momento antes del commit final, sin dejar rastro.

Historia lineal frente a ramificada

  LINEAL (--ff-only, o rebase)          RAMIFICADA (--no-ff)

    A --- B --- C --- D --- E             A --- B --- C --------- M
                                                           \       /
                                                            D --- E

    git log --oneline es una lista        el grafo muestra dónde nació cada cosa
LinealRamificada
Lectura de git logSimple, una filaRequiere --graph
Contexto de una funcionalidadSe pierde el agrupamientoSe ve el bloque completo
Revertir una funcionalidad enteraVarios commits sueltosUn revert -m 1 del merge
BisectDirectoFunciona igual, con un paso más por merge
Compatible con --ff-onlySíNo

Ninguna es «la correcta»: son convenciones de equipo. Lo que sí es universal es que el merge no reescribe nada, así que es seguro en ramas compartidas. La reescritura es territorio de rebase, que verás en el módulo 4.

Herramientas para mirar antes y después

# ¿Qué commits tiene feature y no tiene main?
git log --oneline main..feature

# ¿Qué commits tiene main y no feature?
git log --oneline feature..main

# Diff de feature respecto a su base común con main (los tres puntos)
git diff main...feature

# El grafo, antes y después
git log --oneline --graph --decorate --all

El diff con tres puntos (main...feature) es el que se usa para revisar un pull request: compara contra la base común, no contra la punta de main, y por eso muestra solo lo que aporta la rama.

3 · Ejemplo mínimo

Primero un fast-forward y luego un merge commit, sobre el mismo repositorio:

mkdir taller-merge && cd taller-merge
git init
printf 'base\n' > notas.md
git add notas.md && git commit -m "docs: base"
git branch -M main

# Caso A: main no avanza -> fast-forward
git switch -c feature/ff
printf 'base\nff\n' > notas.md
git commit -am "feat: cambio en ff"

git switch main
git merge feature/ff
# Updating 1a2b3c4..2b2b2b2
# Fast-forward

git log --oneline --graph --decorate --all
# * 2b2b2b2 (HEAD -> main, feature/ff) feat: cambio en ff
# * 1a2b3c4 docs: base

La rama feature/ff sigue apuntando al mismo commit que main: no se ha creado nada. Ahora el caso B, con dos caminos de verdad: 

git switch -c feature/ramificada
printf 'base\nff\nramificada\n' > notas.md
git commit -am "feat: cambio en la ramificada"

git switch main
printf 'base\nff\nmain-avanza\n' > notas.md
git commit -am "docs: main avanza por su lado"

git merge feature/ramificada
# Merge made by the 'ort' strategy.

git log --oneline --graph --decorate --all

*   4d4d4d4 (HEAD -> main) Merge branch 'feature/ramificada'
|\
| * 3c3c3c3 (feature/ramificada) feat: cambio en la ramificada
* | 2e2e2e2 docs: main avanza por su lado
|/
* 1a2b3c4 docs: base

Aquí Git sí creó un commit 4d4d4d4 con dos padres. Ese commit no añade código propio: su contenido es el resultado de combinar los dos lados. Si los dos hubieran tocado la misma línea, este es el punto donde habría aparecido un conflicto.

Compara las dos historias

Tras el fast-forward, git log --graph es una línea recta. Tras el merge commit, aparece la bifurcación y el nudo. Ejecuta git log --oneline --graph --decorate --all después de cada caso y verás el efecto de --no-ff sin cambiar nada más.

4 · Ejemplo real

Caso 1: integrar una feature con merge commit

git switch main
git pull                      # traer lo último antes de integrar (módulo 5)

git switch feature/export-csv
git log --oneline main..HEAD
# 8b7c9d2 feat: conecta el boton de exportacion
# 7a6b5c4 feat: anade exportacion CSV

# Revisar qué aporta la rama, comparando contra la base común
git diff main...HEAD

# Volver a main y fusionar conservando la topología
git switch main
git merge --no-ff feature/export-csv -m "Merge branch 'feature/export-csv'"

git log --oneline --graph -6
# *   9f8e7d6 Merge branch 'feature/export-csv'
# |\
# | * 8b7c9d2 feat: conecta el boton de exportacion
# | * 7a6b5c4 feat: anade exportacion CSV
# |/
# * 6b5a493 docs: actualiza el README

Con el merge commit, revertir toda la funcionalidad es una sola operación: git revert -m 1 9f8e7d6. Esa es la ventaja práctica de --no-ff y la razón por la que muchos equipos lo exigen para cada pull request.

Caso 2: mantener la rama al día sin ensuciar main

Una rama larga se queda atrás y acumula conflictos. La solución es traer main hacia la rama de vez en cuando: 

git switch feature/export-csv
git fetch origin
git merge origin/main            # o: git pull origin main

# Si hay conflicto, se resuelve aquí, en tu rama,
# no en el momento crítico de integrar en main.

Eso añade a tu rama un commit de merge con main. Algunos equipos prefieren rebase para mantener la rama lineal (módulo 4), pero eso reescribe los commits de la rama y solo es seguro si nadie más la está usando.

Caso 3: un conflicto de verdad, resuelto

git switch main
git merge feature/precios
# CONFLICT (content): Merge conflict in src/precios.js
# Automatic merge failed; fix conflicts and then commit the result.

git status --short
# UU src/precios.js

git diff src/precios.js
# muestra los marcadores <<<<<<< ======= >>>>>>>

# ...editar el fichero y dejar la versión final sin marcadores...

git add src/precios.js
git status --short
# M  src/precios.js

git commit
# [main 5e5e5e5] Merge branch 'feature/precios'
Nunca commitees con marcadores dentro

Un merge commiteado con <<<<<<< en el código es un fallo que se descubre tarde, a veces en producción. Antes de git add, busca los marcadores en todo el árbol: git diff --check los señala, y un grep rápido por ^<<<<<<< te da la lista completa. Después, ejecuta los tests.

Caso 4: abortar un merge a medias

git merge feature/precios
# CONFLICT...
git status -sb
## main
# UU src/precios.js
# ...te das cuenta de que la rama no estaba lista...

git merge --abort
git status -sb
## main
# (árbol limpio: como si no hubieras empezado)

--abort solo funciona mientras el merge está en curso (conflicto sin commitear). Después del commit final, para deshacerlo se usa revert del merge.

6 · Errores habituales

1. Fusionar en la dirección contraria

Mal — traer main dentro de la feature y creer que ya está integrada 
git switch feature/export-csv
git merge main            # esto NO integra la feature en main
# Solo pone main dentro de la feature.
Bien — fusionar la feature hacia main 
git switch main
git merge feature/export-csv
# Ahora sí: main contiene el trabajo de la feature.

Es un error clásico de principiante: merge siempre trae la rama que nombras dentro de la rama en la que estás. La dirección es parte del comando.

2. Commitear el merge con marcadores de conflicto

Mal — git add . sin revisar 
git merge feature/precios
# CONFLICT...
git add .
git commit -m "merge"
# El fichero lleva <<<<<<< y >>>>>>> dentro. La app no compila.
Bien — resolver, comprobar y después commitear 
# ...editar y quitar marcadores...
git diff --check          # señala marcadores olvidados
# ...ejecutar los tests...
git add src/precios.js
git commit

3. Creer que --squash deja la rama integrada

Mal — fusionar la misma rama dos veces 
git merge --squash feature/x
git commit -m "feat: x completo"
# ...más tarde, sin borrar la rama...
git merge feature/x
# Git intenta aplicar otra vez los mismos commits: conflictos absurdos.
Bien — squash y borrar, o merge normal 
git merge --squash feature/x
git commit -m "feat: x completo"
git branch -D feature/x     # ya no aporta nada: su contenido está en main

4. Fusionar sin actualizar la rama principal

Mal — integrar contra un main obsoleto 
# Hace tres días que no haces fetch; tu main local no es el de nadie más
git switch main
git merge feature/x
# El merge es correcto en tu máquina, pero integrar de verdad
# producirá conflictos que podrías haber visto antes.
Bien — traer el remoto primero 
git switch main
git fetch origin
git merge origin/main        # o git pull, si tu configuración lo permite
git merge feature/x

5. Resolver el conflicto borrando una de las dos partes sin pensar

Mal — quedarse siempre con «lo mío» 
# Quedarse con la versión de main sin leer la de la feature
# puede tirar trabajo que ya estaba probado.
git restore --ours src/precios.js
Bien — entender las dos partes y combinar 
git log --merge -p src/precios.js    # commits de los dos lados
# ...combinar a mano la intención de ambos...
git add src/precios.js

--ours y --theirs existen y a veces son la respuesta, pero son una decisión, no un atajo: úsalos solo cuando sepas que un lado sustituye al otro.

7 · Ejercicio guiado

Vas a producir las dos topologías —fast-forward y merge commit— y a provocar y resolver un conflicto real.

  1. Crea un repositorio con un commit base en main.
  2. Haz un fast-forward: rama, un commit, vuelve a main, fusiona y comprueba que no hay merge commit.
  3. Haz un merge commit: rama nueva, commit, y esta vez añade también un commit en main antes de fusionar con --no-ff.
  4. Provoca un conflicto en un tercer fichero modificado en las dos ramas y resuélvelo combinando las dos versiones.
  5. Aborta un merge a propósito y comprueba que el árbol vuelve a estar limpio.

Solución resuelta:

mkdir ejercicio-merge && cd ejercicio-merge
git init
printf 'base\n' > notas.md
git add notas.md && git commit -m "docs: base"
git branch -M main

# 2. Fast-forward
git switch -c feature/ff
printf 'base\nff\n' > notas.md
git commit -am "feat: ff"
git switch main
git merge feature/ff
# Fast-forward
git log --oneline
# 2b2b2b2 feat: ff
# 1a2b3c4 docs: base

# 3. Merge commit
git switch -c feature/ramificada
printf 'base\nff\nramificada\n' > notas.md
git commit -am "feat: ramificada"

git switch main
printf 'base\nff\nmain\n' > notas.md
git commit -am "docs: main"

git merge --no-ff feature/ramificada -m "Merge branch 'feature/ramificada'"
git log --oneline --graph -5
# *   4d4d4d4 Merge branch 'feature/ramificada'
# |\
# | * 3c3c3c3 feat: ramificada
# * | 2e2e2e2 docs: main
# |/
# * 2b2b2b2 feat: ff

# 4. Conflicto
printf 'precio base\n' > precios.md
git add precios.md && git commit -m "feat: precios base"

git switch -c feature/precios
printf 'precio base\nIVA 21\n' > precios.md
git commit -am "feat: anade IVA"

git switch main
printf 'precio base\ndescuento 10\n' > precios.md
git commit -am "feat: anade descuento"

git merge feature/precios
# CONFLICT (content): Merge conflict in precios.md

cat precios.md
# precio base
# <<<<<<< HEAD
# descuento 10
# =======
# IVA 21
# >>>>>>> feature/precios

# Combinar las dos aportaciones
printf 'precio base\ndescuento 10\nIVA 21\n' > precios.md
git add precios.md
git commit -m "Merge branch 'feature/precios'"

# 5. Abortar
git switch -c feature/rota
printf 'roto\n' > precios.md
git commit -am "feat: algo que no debe entrar"

# main tambien toca el mismo fichero: así el merge no puede ser fast-forward
git switch main
printf 'precio base\ndescuento 10\nIVA 21\nmantenido\n' > precios.md
git commit -am "docs: anota el precio final"

git merge feature/rota
# CONFLICT...
git merge --abort
git status -sb
## main
Qué observar

Que el fast-forward no creó commit, que --no-ff sí, y que el conflicto no se resolvió eligiendo un lado sino combinando los dos: descuento e IVA. Esa es la resolución que de verdad se pide en un merge de trabajo independiente.

8 · Reto

La misma funcionalidad, dos historias

Construye dos repositorios (o dos ramas de trabajo separadas) que representen la misma funcionalidad integrada de dos maneras distintas:

  1. En el primero, main recibe la funcionalidad con historia lineal: nada de merge commits, y git log --graph es una recta.
  2. En el segundo, main recibe la funcionalidad con un merge commit que agrupa todos sus commits.
  3. Provoca en ambos un conflicto y resuélvelo de forma distinta: en uno conservando las dos aportaciones, en el otro sustituyendo una por la otra con criterio justificado.
  4. Compara el coste de revertir toda la funcionalidad en cada historia: documenta cuántos comandos necesitas en cada caso y qué queda en el grafo después.

Entrega los dos grafos, los mensajes de commit y una recomendación razonada de qué política usarías en un equipo de cuatro personas que despliega a diario. No reescribas nada que ya hayas publicado en un remoto local: si necesitas rehacer, hazlo antes de publicar.

Pista: para la historia lineal necesitarás --ff-only y, si las ramas divergen, decidir si fusionas main hacia la rama antes de integrar. Para medir el coste del revert, mira el grafo: en la historia ramificada el merge commit es un único punto de entrada. Y recuerda que --squash produce una tercera variante que conviene que sepas distinguir de las dos anteriores.

9 · Resumen

  • git merge <rama> trae la rama nombrada dentro de la rama en la que estás.
  • Si la punta actual es ancestro de la otra, hay fast-forward: se mueve el puntero y no hay commit nuevo.
  • Si las dos ramas han avanzado, se crea un merge commit con dos padres.
  • --no-ff fuerza el merge commit; --ff-only exige fast-forward; --squash aplana sin crear enlace de merge.
  • Un conflicto detiene el merge: se resuelve, se hace git add y se cierra con git commit o git merge --continue.
  • git merge --abort cancela el merge en curso sin dejar rastro.
  • El merge nunca reescribe historia: es seguro en ramas compartidas.
  • git log --oneline --graph --decorate --all muestra el resultado real.

10 · Preguntas frecuentes

¿Por qué a veces el merge no crea ningún commit?

Porque la rama de destino no había avanzado desde que nació la otra: no hay dos caminos que combinar, solo un puntero que adelantar. Ese es el fast-forward. Si quieres que quede constancia de la rama en la historia, usa --no-ff.

¿El merge pierde commits o reescribe algo?

No. merge solo añade: en el peor caso un commit de merge, y nunca modifica los commits existentes ni sus hashes. Por eso es seguro en ramas que otros ya tienen. La reescritura es cosa de rebase y de reset, no del merge.

¿Qué hago si el conflicto es enorme y no entiendo nada?

Primero git merge --abort y respira: no has perdido nada. Después, mira qué aporta cada lado con git log --merge -p <fichero> y compara las versiones con git diff :1:<fichero> :3:<fichero> (base y lado de la rama). Muchas veces la mejor decisión es resolver en la rama, con calma, fusionando main hacia ella antes de integrarla.

¿Puedo fusionar solo una parte de una rama?

No con merge: el merge combina las dos puntas completas. Si quieres traer un commit concreto, eso es cherry-pick (módulo 4). Y si quieres aplanar todos los cambios en uno solo, merge --squash deja el resultado en el índice para que hagas un commit normal.

¿Qué diferencia hay entre git diff main..feature y git diff main...feature?

Con dos puntos, Git compara las puntas: incluye también los cambios que main ha hecho y que la rama no tiene. Con tres puntos, compara contra la base común: muestra solo lo que aporta la rama. Para revisar un pull request, el que quieres casi siempre es el de tres puntos.
