Flujos de equipo

Módulo 3 · Ramas 🕐 35 minutos

1 · Introducción

Ya sabes crear ramas, fusionarlas y resolver conflictos. Lo que falta es la parte que no es de Git sino de organización: cuándo se crea una rama, de dónde sale, cuánto vive, quién puede fusionarla y qué tiene que pasar antes. Eso es un flujo de trabajo.

Hay tres nombres que oirás constantemente: GitHub Flow, Git Flow y trunk-based development. No son comandos ni plugins: son convenciones. Elegir una y respetarla vale más que elegir la «mejor» y cambiarla cada mes, porque el coste real de un flujo es la previsibilidad que da al equipo.

El problema que resuelven los flujos

Sin convención, cada persona inventa su manera: uno fusiona en main los viernes, otro mantiene una rama de tres meses, un tercero publica desde su portátil. El resultado es una historia ilegible, despliegues que nadie sabe qué contienen y conflictos que se resuelven a última hora. El flujo convierte esas decisiones en un contrato repetible.

2 · Teoría

GitHub Flow: una sola rama de larga vida

Es el flujo más simple que funciona en equipo: main siempre está desplegable, cada cambio nace en una rama corta, se abre una revisión (pull request), se integra y se despliega. No hay rama develop, no hay ramas de release permanentes. 

  main      A --- B --- C ---------- M1 ---------- M2 ---->
                       \            /            /
  feature/x             D --- E ---/            /         (vive horas o días)
  fix/y                                          F --- G  (nace de main, vuelve a main)
  1. Partir de main actualizada: git switch main y git pull.
  2. Crear una rama descriptiva: git switch -c feature/export-csv.
  3. Commitear en pequeño y subir la rama pronto: git push -u origin feature/export-csv.
  4. Abrir una pull request con contexto, capturas y cómo probarlo.
  5. Pasar la integración continua y la revisión de otra persona.
  6. Fusionar (merge commit, squash o rebase-merge, según la política) y borrar la rama.
  7. Desplegar desde main. Si algo falla, revertir y arreglar hacia delante.

Funciona muy bien en productos web con despliegue continuo. Su punto débil es que asume que main se puede desplegar en cualquier momento: si tu producto se entrega en versiones instalables cada tres meses, necesitarás algo más.

Git Flow: ramas para cada fase del ciclo de release

Diseñado para software versionado con releases planificadas. Tiene dos ramas de larga vida (main y develop) y tres tipos de ramas temporales: 

  main      ●────────────────●──────────────────●
            │      release/1.0 ↑      hotfix/1.0.1 ↑
  develop   ●──●──●──●──●──●───●───●───●───●───●──●
                 │
  feature/x      ●──●──●   (nace de develop, vuelve a develop)

  main      solo releases etiquetadas y hotfixes
  develop   integración continua del próximo release
RamaNace deVuelve aPara qué
main——Código en producción, solo versiones etiquetadas
developmain—Integración de lo que vendrá en el próximo release
feature/*developdevelopUna funcionalidad
release/*developmain y developEstabilizar, congelar y preparar la versión
hotfix/*mainmain y developCorregir una urgencia en producción

El coste es alto: dos ramas que mantener sincronizadas, merges de release hacia dos sitios, y una disciplina que se rompe en cuanto alguien commitea directamente en develop. Su ventaja es que permite congelar una versión mientras el equipo sigue desarrollando la siguiente, algo necesario en software empaquetado, firmware o productos con certificación.

Git Flow no es el flujo por defecto

Durante años se presentó como «el flujo profesional». Hoy, para una aplicación web con despliegue continuo, es sobreingeniería: añade ramas y ceremonias que no resuelven ningún problema real. Úsalo si tu ciclo de release lo justifica, no porque suene más serio.

Trunk-based: una sola línea, ramas de horas

Todo el mundo integra en trunk (o main) muy a menudo. Las ramas, si existen, duran horas o un día como máximo. Lo que no está terminado se oculta detrás de un feature flag, no de una rama eterna. 

  trunk   ●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─>   siempre verde y desplegable
              ↑     ↑       ↑
          rama 2h  rama 1d  rama 4h          (se integran y se borran)

  Lo incompleto no vive en una rama: vive detrás de un flag apagado.

Exige mucho de la ingeniería: tests rápidos y fiables, integración continua que bloquee lo roto, commits pequeños, revisión ágil y capacidad de desplegar varias veces al día. A cambio, elimina casi por completo los merges dolorosos y reduce el tiempo entre escribir algo y saber si funciona.

La analogía del carril

Una rama larga es un carril que se aleja de la autopista: cuanto más tiempo pasa, más carretera hay que construir para volver a incorporarse. Trunk-based mantiene a todos en la autopista con incorporaciones cortas. Git Flow construye una vía de servicio paralela y luego la conecta en puntos concretos; funciona si el tráfico lo requiere, pero cuesta mantenerla.

Ramas cortas: la única regla universal

Los tres flujos comparten un principio: cuanto menos vive una rama, mejor. No es una preferencia estética. Una rama larga:

  • Acumula conflictos que se resuelven todos a la vez, cuando ya no recuerdas por qué cambiaste cada línea.
  • Retrasa la integración, así que los errores de diseño se descubren tarde.
  • Se convierte en una «rama zombie» que nadie se atreve a fusionar ni a borrar.
  • Hace que la revisión sea imposible: un diff de 4.000 líneas no se revisa, se aprueba.

La práctica concreta: integra al menos cada dos días, parte siempre de la rama principal actualizada, y si una funcionalidad no cabe en ese plazo, divídela en partes que sí quepan o escóndela tras un flag.

Integración continua: el guardián del flujo

La CI no es «un servidor que ejecuta tests». Es el mecanismo que hace que integrar sea seguro:

  1. Al abrir o actualizar una pull request, se ejecutan tests, linter y compilación.
  2. Si algo falla, la rama no se puede fusionar (status checks obligatorios).
  3. Al fusionar en main, se vuelve a ejecutar todo y se despliega si está verde.
  4. Si main se rompe, se arregla o se revierte antes de seguir añadiendo cambios.
  rama  --push-->  CI: lint + tests + build  --verde-->  revisión  -->  merge  -->  deploy
                          |
                       rojo = no se fusiona

Protección de main: el contrato técnico

Un flujo sin reglas es una sugerencia. La protección de rama las convierte en algo que la herramienta impone. En una forja (GitHub, GitLab, Bitbucket) suele configurarse con estas piezas:

ReglaQué impidePor qué importa
Prohibido el push directoSaltarse la revisión y la CITodo cambio pasa por una pull request
Al menos una aprobaciónFusionar tu propio trabajo sin mirada ajenaLa revisión es el control de calidad más barato
Status checks obligatoriosFusionar con tests rojosLa CI deja de ser opcional
Rama actualizada antes de fusionarIntegrar contra una base viejaLos conflictos se resuelven antes, no después
Historia lineal (opcional)Merges en marañagit log legible; facilita bisect

La protección no sustituye al acuerdo

Puedes tener main protegida y un equipo que no entiende por qué. La conversación —qué se considera «listo», quién revisa, cuánto puede vivir una rama— es la mitad del flujo. La configuración solo evita el atajo de turno.

Cómo se fusiona una pull request

EstrategiaResultadoCuándo
Merge commit Conserva todos los commits y añade uno de merge Quieres la topología y poder revertir la funcionalidad entera
Squash Un commit en main con todos los cambios La rama tenía commits de trabajo («wip», «arreglo test») que no aportan
Rebase-merge Reaplica los commits uno a uno sobre main, sin merge commit Quieres historia lineal y commits ya limpios

Squash y rebase-merge reescriben los commits de la rama (cambian sus hashes), pero eso es aceptable porque la rama es tuya y desaparece al fusionar. Nunca reescribas main.

3 · Ejemplo mínimo

No necesitas GitHub para practicar el flujo: un repositorio bare local hace de remoto. 

# El «servidor»: un repositorio sin directorio de trabajo
git init --bare taller-remoto.git

# Tu copia de trabajo
git clone taller-remoto.git taller-local
cd taller-local
git config user.name "Ana"
git config user.email "ana@ejemplo.com"

printf '# Taller\n' > README.md
git add README.md
git commit -m "docs: arranca el taller"
git branch -M main
git push -u origin main

Ahora el ciclo de GitHub Flow, en una sola rama corta:

git switch -c feature/export-csv
printf 'export\n' > export.csv
git add export.csv
git commit -m "feat: anade exportacion CSV"
git push -u origin feature/export-csv

# «Revisión»: comparar contra la base común
git fetch origin
git diff origin/main...HEAD

# «Fusionar» en main
git switch main
git pull
git merge --no-ff feature/export-csv -m "Merge branch 'feature/export-csv'"
git push

# Limpiar la rama, local y remota
git branch -d feature/export-csv
git push origin --delete feature/export-csv
Lo que este ejemplo demuestra

Que el flujo es una secuencia de comandos que ya conoces, no una herramienta nueva. La forja añade interfaz, revisión y reglas automáticas, pero por debajo todo es fetch, diff, merge y push. Entender el mecanismo te permite depurar cuando la interfaz dice «no se puede fusionar» sin explicar por qué.

4 · Ejemplo real

Caso 1: un equipo web con GitHub Flow

Cuatro personas, despliegue diario, una sola versión en producción. La convención escrita en el README:

  • Ramas feature/…, fix/…, chore/…; máximo dos días de vida.
  • Una pull request por cambio; el título sigue Conventional Commits.
  • main protegida: CI verde, una aprobación, sin push directo.
  • Se fusiona con squash para que main tenga un commit por cambio.
  • Despliegue automático al fusionar; si falla, revert inmediato.
git switch main
git pull
git switch -c fix/orden-resultados

# ...cambio pequeno y test...
git add src/busqueda.js tests/busqueda.test.js
git commit -m "fix: orden estable en los resultados"
git push -u origin fix/orden-resultados

# Tras la revision y la CI, la forja fusiona con squash:
#   main recibe UN commit con todo el cambio
git switch main
git pull
git log --oneline -3
# 9f8e7d6 fix: orden estable en los resultados (#142)
# 7c6b5a4 feat: exportacion CSV (#141)
# 6b5a493 chore: actualiza dependencias (#140)

Caso 2: un producto empaquetado con Git Flow

Software de escritorio con releases trimestrales. Mientras se estabiliza la 2.4, el equipo sigue desarrollando la 2.5: 

# Congelar la version que se va a publicar
git switch develop
git switch -c release/2.4
# ...solo correcciones, subir version, changelog...
git commit -am "chore: prepara release 2.4"

# Publicar: a main y de vuelta a develop
git switch main
git merge --no-ff release/2.4
git tag -a v2.4.0 -m "Version 2.4.0"
git switch develop
git merge --no-ff release/2.4

# Urgencia en produccion: hotfix desde main
git switch main
git switch -c hotfix/2.4.1
# ...corregir...
git commit -am "fix: evita el cierre inesperado"
git switch main
git merge --no-ff hotfix/2.4.1
git tag -a v2.4.1 -m "Version 2.4.1"

# El hotfix vuelve tambien a develop
git switch develop
git merge --no-ff hotfix/2.4.1
El punto donde Git Flow se rompe

Si el hotfix no vuelve a develop, el bug reaparece en la siguiente versión. Si la rama release/2.4 no se fusiona en los dos sitios, main y develop divergen para siempre. Git Flow no falla por Git: falla por pasos que la gente olvida en una semana de prisas.

Caso 3: trunk-based con feature flag

Una funcionalidad de tres semanas no cabe en una rama corta. En lugar de mantener la rama, se integra el código apagado: 

git switch -c feat/export-csv-etapa-1
# ...esqueleto detras de un flag desactivado...
git add src/export.js src/flags.js
git commit -m "feat: esqueleto de exportacion tras flag"

git switch main
git pull
git merge --no-ff feat/export-csv-etapa-1
git push

# Etapa 2, al dia siguiente: otra rama de horas, no una de semanas.

  if (flags.exportCsv) {
    botonExport.hidden = false;
  }

  El codigo viaja a produccion desde el primer dia, pero nadie lo ve
  hasta que el flag se activa. La rama no acumula divergencia.

Requisito: el flag debe poder apagarse sin desplegar, y hay que borrarlo cuando la funcionalidad queda estable. Un cementerio de flags viejos es deuda técnica con otro nombre.

Caso 4: elegir flujo en un equipo existente

SíntomaFlujo razonablePrimer paso
Despliegue web diario, ramas de díasGitHub FlowProteger main y exigir CI

Migrar de golpe suele fallar. Empieza por la regla que más duele: casi siempre es «main protegida + ramas cortas + CI obligatoria». El resto se puede ajustar después.

6 · Errores habituales

1. Adoptar Git Flow para una web con despliegue diario

Mal — ceremonia que no resuelve ningún problema real 
# Rama develop + release + hotfix para desplegar un cambio de copy
git switch develop
git switch -c release/1.12
# ...tres merges y dos etiquetas para un cambio de una línea...
Bien — el flujo más simple que cubre tu riesgo 
git switch main
git switch -c fix/copy-precios
# ...cambio, test, PR, CI, merge y despliegue...

2. Mantener una rama de tres meses

Mal — integrar al final y resolver todo de golpe 
git log --oneline main..feature/rediseno | wc -l
# 214 commits
git merge main
# 31 ficheros en conflicto, tres días de resolución y un bug en produccion.
Bien — trocear e integrar cada pocos días 
# Cada parte es una rama corta que vuelve a main:
# feat/rediseno-cabecera, feat/rediseno-menu, feat/rediseno-tarjetas
# Lo que aun no se usa, detras de un flag.

3. Fusionar sin CI o con la CI en rojo

Mal — «los tests fallan por algo raro, fusiono igual» 
# CI en rojo, pero la funcionalidad «funciona en mi maquina»
git merge --no-ff feature/x
git push
# main rota: nadie puede desplegar hasta que se aclare.
Bien — la CI es parte de la definición de terminado 
# Si el fallo es del entorno, se arregla la CI primero.
# Si es del cambio, se arregla el cambio.
# Mientras tanto, main sigue verde y desplegable.

4. Hacer push directo a main

Mal — saltarse revisión y checks 
git switch main
git commit -am "fix: arreglo rapido"
git push
# Sin revision, sin CI, sin contexto. Y nadie sabe que paso.
Bien — incluso la prisa pasa por una rama 
git switch -c hotfix/login-caido
git commit -am "fix: evita el cierre inesperado"
git push -u origin hotfix/login-caido
# PR express: CI + una aprobacion. Tarda minutos, no dias.

5. Olvidar devolver el hotfix a develop

Mal — el bug vuelve en la siguiente release 
git switch main
git merge --no-ff hotfix/2.4.1
git tag -a v2.4.1 -m "Version 2.4.1"
# ...y develop se queda sin la correccion...
Bien — main y develop reciben el hotfix 
git switch main
git merge --no-ff hotfix/2.4.1
git tag -a v2.4.1 -m "Version 2.4.1"

git switch develop
git merge --no-ff hotfix/2.4.1

6. Mezclar estrategias de merge sin criterio

Mal — historia impredecible 
# Lunes: merge commit. Martes: squash. Miercoles: rebase-merge.
# Nadie sabe por que main tiene la forma que tiene.
Bien — una política escrita y aplicada por la forja 
# Acuerdo: squash para toda pull request de feature.
# Excepcion documentada: merge commit para releases.
# La forja permite desactivar las otras opciones.

7 · Ejercicio guiado

Vas a montar un flujo completo tipo GitHub Flow con un remoto local: rama, push, revisión por diff, merge, etiqueta y limpieza. Sin cuenta de GitHub.

  1. Crea un remoto bare y clona una copia de trabajo.
  2. Publica un commit inicial en main.
  3. Crea una rama corta, haz dos commits y súbela con upstream.
  4. Simula la revisión: git diff origin/main...HEAD y comprueba que solo aparecen tus cambios.
  5. Fusiona con --no-ff, publica, etiqueta la versión y borra la rama local y remota.
  6. Comprueba el grafo final con --graph --all y el estado con git branch -vv.

Solución resuelta:

mkdir flujo && cd flujo
git init --bare remoto.git
git clone remoto.git trabajo
cd trabajo
git config user.name "Ana"
git config user.email "ana@ejemplo.com"

# 2. Commit inicial
printf '# Proyecto\n' > README.md
git add README.md
git commit -m "docs: arranca el proyecto"
git branch -M main
git push -u origin main

# 3. Rama corta con dos commits
git switch -c feature/export-csv
printf 'id,titulo\n1,primera\n' > export.csv
git add export.csv
git commit -m "feat: anade exportacion CSV"
printf 'id,titulo\n1,primera\n2,segunda\n' > export.csv
git commit -am "test: amplia los datos de ejemplo"
git push -u origin feature/export-csv

# 4. Revision: solo lo que aporta la rama
git fetch origin
git diff origin/main...HEAD

# 5. Integracion
git switch main
git pull
git merge --no-ff feature/export-csv -m "Merge branch 'feature/export-csv'"
git tag -a v1.1.0 -m "Version 1.1.0"
git push
git push origin v1.1.0

git branch -d feature/export-csv
git push origin --delete feature/export-csv

# 6. Comprobacion
git log --oneline --graph --decorate --all
# *   4d4d4d4 (HEAD -> main, tag: v1.1.0, origin/main) Merge branch 'feature/export-csv'
# |\
# | * 3c3c3c3 test: amplia los datos de ejemplo
# | * 2b2b2b2 feat: anade exportacion CSV
# |/
# * 1a1a1a1 docs: arranca el proyecto

git branch -vv
# * main 4d4d4d4 [origin/main] Merge branch 'feature/export-csv'
Repite el ejercicio con squash

Crea otra rama con dos commits de trabajo y fusiónala con git merge --squash más un commit. Compara el grafo: main tendrá un solo commit lineal y no habrá enlace con la rama. Es la diferencia entre «conservar la topología» y «conservar la historia legible», y la decisión que la política del equipo debe fijar.

8 · Reto

El flujo del taller

Diseña y ejecuta el flujo de trabajo completo del repositorio taller para un equipo de cuatro personas, con un remoto bare local y sin cuenta de GitHub. El flujo debe incluir, como mínimo:

  1. Una rama principal protegida por convención: nadie commitea directamente en ella.
  2. Ramas cortas con nombres feature/…, fix/… y chore/…, y una regla escrita sobre su duración máxima.
  3. Una revisión simulada: antes de cada merge, un diff contra la base común y una lista de comprobación (tests, mensaje, alcance).
  4. Una versión etiquetada con tag anotado y un changelog breve generado a partir de los commits.
  5. Un hotfix que llegue a la versión publicada y también a la línea de desarrollo.

Entrega un documento FLUJO.md con las reglas, el grafo final, los mensajes de commit y una justificación de por qué has elegido GitHub Flow, Git Flow o trunk-based para este equipo. Incluye también qué reglas configurarías en la forja si el repositorio se publicara allí.

Pista: empieza por el riesgo, no por la herramienta. ¿Necesitas varias versiones vivas a la vez? ¿Despliegas a diario? ¿Puedes permitirte una rama de una semana? La respuesta te dice el flujo. Para el hotfix, recuerda que en Git Flow debe volver a main y a develop; en GitHub Flow, basta con una rama desde main y un revert si algo falla. Y no fuerces el push en la rama principal bajo ninguna circunstancia.

9 · Resumen

  • GitHub Flow: main desplegable, ramas cortas, pull request, merge y despliegue. Simple y ideal para web.
  • Git Flow: main + develop + feature, release y hotfix. Potente para releases versionadas, caro de mantener.
  • Trunk-based: una sola troncal, ramas de horas y feature flags. Exige CI rápida y tests fiables.
  • La regla común: ramas cortas y fusiones frecuentes.
  • La CI convierte la integración en algo seguro; la protección de main la hace obligatoria.
  • Elige una estrategia de merge (merge commit, squash o rebase-merge) y sé coherente.
  • El flujo se escribe, se revisa y se aplica con herramientas, no solo con buenas intenciones.

10 · Preguntas frecuentes

¿Cuál es el mejor flujo?

El que encaja con tu ciclo de entrega y tu madurez técnica, y que el equipo cumple de verdad. Para una aplicación web con despliegue continuo, GitHub Flow o trunk-based suelen ser mejores que Git Flow. Para software empaquetado con releases planificadas, Git Flow resuelve un problema real que los otros no cubren. No hay uno universal.

¿Necesito GitHub para usar GitHub Flow?

No. El nombre viene de la forja que lo popularizó, pero el flujo es una convención: rama corta, revisión por diff, integración en la principal y despliegue. Puedes practicarlo con GitLab, Bitbucket, un servidor propio o incluso un remoto bare local, como en el ejercicio.

¿Squash o merge commit?

Squash si los commits de la rama son de trabajo y quieres una historia limpia con un commit por cambio. Merge commit si quieres conservar la topología y poder revertir la funcionalidad completa con revert -m 1. Rebase-merge si quieres linealidad conservando commits ya pulidos. Lo importante es que el equipo elija una y la forja la imponga.

¿Qué es un feature flag y cuándo sustituye a una rama?

Es una condición en el código que activa o desactiva una funcionalidad sin desplegar de nuevo. Permite integrar trabajo incompleto en la troncal desde el primer día y seguir desarrollándolo en commits pequeños. Sustituye a la rama larga cuando la funcionalidad tarda semanas, pero exige disciplina: el flag se apaga por defecto, se prueba encendido y apagado, y se elimina cuando ya no hace falta.

¿Cómo empiezo a proteger main si el equipo no lo usa?

Con una propuesta pequeña y medible: prohibir el push directo, exigir CI verde y una aprobación. Acompaña la configuración de una guía de una página con el ciclo completo (rama, PR, revisión, merge, borrado). Al principio habrá roces; si la CI tarda veinte minutos, el problema es la CI, no la regla. La mayoría de los equipos no vuelve atrás después de un mes.
