Ramas y HEAD

Módulo 3 · Ramas 🕐 30 minutos

1 · Introducción

Mucha gente evita las ramas porque le parecen copias del proyecto: «si creo una rama, ¿se duplica la carpeta? ¿se me va a llenar el disco? ¿y si la lío y pierdo main?». Nada de eso. Una rama en Git es un puntero a un commit: un fichero de texto de 41 bytes con un hash dentro. Crear una rama es instantáneo, borrarla también, y tener cincuenta no cuesta prácticamente nada.

Lo que sí importa es entender dónde está HEAD. Ese es el puntero que dice «tú estás aquí» y decide en qué rama caerá el próximo commit. Casi todos los sustos con ramas («he perdido mis commits», «estoy en un estado raro») son en realidad historias de un HEAD separado o de una rama mal interpretada.

El modelo mental que lo cambia todo

Un commit es una foto inmutable con un puntero a su padre. Una rama es una etiqueta móvil que apunta a un commit. HEAD es otra etiqueta que normalmente apunta a una rama, y solo excepcionalmente a un commit directamente. Commitear no crea una rama nueva: mueve la etiqueta de la rama actual un paso hacia delante.

2 · Teoría

Qué hay dentro de una rama

En .git/refs/heads/ hay un fichero por rama local. Su contenido es un hash de commit, nada más. Algunos repositorios empaquetan esas referencias en .git/packed-refs por eficiencia, pero el concepto es el mismo: 

cat .git/HEAD
# ref: refs/heads/main

cat .git/refs/heads/main
# 3f2a1b0c9d8e7f6a5b4c3d2e1f0a9b8c7d6e5f4a

git symbolic-ref --short HEAD
# main

git branch --show-current
# main

HEAD contiene una referencia simbólica a refs/heads/main. Cuando commiteas, Git crea el commit, mueve refs/heads/main al commit nuevo y HEAD sigue apuntando a refs/heads/main. Por eso «HEAD se mueve»: en realidad se mueve la rama a la que apunta. 

  ANTES DEL COMMIT                DESPUÉS DE git commit

        main                            main
         |                               |
         v                               v
    A <-- B <-- C                   A <-- B <-- C <-- D
                ^                                   ^
                |                                   |
              HEAD -> main                      HEAD -> main

Crear y cambiar de rama

# Crear una rama sin cambiar a ella (el puntero nace en HEAD)
git branch feature/busqueda

# Crear y cambiar en un solo paso (la forma recomendada)
git switch -c feature/busqueda

# Cambiar a una rama existente
git switch main

# Volver a la rama anterior (atajo muy útil)
git switch -

git switch -c es equivalente a git branch <nombre> seguido de git switch <nombre>. La rama nueva apunta al mismo commit en el que estabas: no hay copia de ficheros, no hay commit nuevo. Solo hay una etiqueta más. 

  git switch -c feature/busqueda      (desde main en C)

        main
         |
         v
    A <-- B <-- C
                ^
                |
          feature/busqueda  <- HEAD apunta aquí

  Los dos punteros señalan el MISMO commit. Nada se ha duplicado.

El primer commit en una rama nueva

Al commitear en feature/busqueda, solo esa etiqueta avanza. main se queda donde estaba: 

  git commit en feature/busqueda

        main
         |
         v
    A <-- B <-- C
                \
                 D <-- E
                       ^
                       |
                feature/busqueda  <- HEAD

Ese es todo el misterio de las ramas: dos etiquetas que comparten pasado y divergen cuando cada una recibe commits. La «historia lineal» y la «historia ramificada» no son más que formas distintas de volver a juntar esos caminos, y eso es el tema de la próxima lección.

Listar, renombrar y borrar

# Ramas locales; la que tiene * es la actual
git branch
# * main
#   feature/busqueda

# Con el último commit de cada una
git branch -v

# Con el upstream y si hay commits pendientes
git branch -vv

# Renombrar la rama actual
git branch -m feature/busqueda-avanzada

# Renombrar otra rama
git branch -m main produccion

# Borrar una rama ya fusionada (seguro)
git branch -d feature/busqueda

# Borrar una rama sin comprobar si está fusionada (peligroso)
git branch -D experimento/descartado
-d comprueba, -D no

git branch -d se niega si la rama tiene commits que no están fusionados en la rama actual o en su upstream. Es una protección deliberada: te avisa de que borrar la etiqueta dejaría commits sin nombre. -D fuerza el borrado y esos commits quedan solo en el reflog hasta la recolección de basura. Si no estás seguro, no uses -D: primero fusiona o compara con git log main..rama.

No puedes borrar la rama en la que estás: Git te pedirá que cambies primero. Tampoco puedes crear dos ramas con el mismo nombre; los nombres son únicos dentro de refs/heads/.

Buenos nombres de rama

PatrónEjemploCuándo
feature/<tema>feature/busqueda-titulosFuncionalidad nueva
fix/<tema>fix/orden-resultadosCorrección de un bug
chore/<tema>chore/actualiza-dependenciasMantenimiento sin cambio funcional

Las barras crean una jerarquía visual en git branch y en las herramientas, pero no cambian el comportamiento. Usa minúsculas, guiones y nombres cortos que digan qué se hace, no quién lo hace.

Detached HEAD: cuando HEAD no apunta a una rama

Normalmente HEAD es simbólico: apunta a una rama. Si haces git switch a un commit o a una etiqueta en lugar de a una rama, HEAD pasa a apuntar directamente al commit. Eso es un detached HEAD: 

git switch --detach HEAD~2
# Note: switching to 'HEAD~2'.
# You are in 'detached HEAD' state...

git status -sb
# HEAD detached at 1a2b3c4

  main:  A <-- B <-- C <-- D
                   ^
                   |
                 HEAD  (detached: apunta al commit, no a una rama)

  Si commiteas aquí:
  main:  A <-- B <-- C <-- D
                   \
                    E   <- solo lo alcanza HEAD; ninguna rama lo protege

Un detached HEAD no es un error. Es útil para mirar código antiguo, probar algo rápido o hacer una compilación de una versión concreta. El peligro llega si commiteas ahí y luego cambias de rama: el commit E se queda sin ninguna rama que lo nombre y desaparece de git log. No se borra de inmediato (el reflog lo recuerda), pero es fácil olvidarlo.

Cómo salir bien de un detached HEAD

Si solo estabas mirando: git switch main y ya está. Si has hecho commits que quieres conservar: git switch -c rescate/detached crea una rama en ese commit antes de moverte. Si ya cambiaste y crees que los perdiste: git reflog te da el hash y git switch -c rescate <hash> los recupera.

La forma antigua de hacer lo mismo era git checkout <commit>. Hoy se prefiere git switch --detach <commit>, que dice explícitamente lo que va a pasar.

Navegar por la historia desde HEAD

ReferenciaSignificado
HEADEl commit actual
HEAD~1El primer padre del commit actual (un paso atrás)
HEAD~3Tres pasos atrás por la primera línea de padres
HEAD^Igual que HEAD~1
HEAD^2El segundo padre (solo tiene sentido en un merge)

Estas referencias funcionan en cualquier comando que acepte un commit: git show, git diff, git restore --source, git switch --detach.

Ver el grafo

git log --oneline --graph --decorate --all

* 9f8e7d6 (feature/busqueda) feat: indice de titulos
* 7c6b5a4 feat: busqueda por autor
| * 5a49382 (HEAD -> main) docs: actualiza el README
|/
* 4a38271 chore: arranca el taller

--decorate añade los nombres de ramas y etiquetas; --all incluye todas las referencias, no solo la actual. Es el comando que convierte el modelo mental en una imagen.

3 · Ejemplo mínimo

Dos ramas que nacen del mismo commit y divergen con un commit cada una:

mkdir taller-ramas && cd taller-ramas
git init
printf 'base\n' > notas.md
git add notas.md && git commit -m "docs: base"
git branch -M main

# Rama nueva desde el mismo commit
git switch -c feature/busqueda
printf 'base\nbuscador\n' > notas.md
git commit -am "feat: anade buscador"

git switch main
printf 'base\nreadme\n' > notas.md
git commit -am "docs: anade readme"

git log --oneline --graph --decorate --all

* 5a49382 (HEAD -> main) docs: anade readme
| * 7c6b5a4 (feature/busqueda) feat: anade buscador
|/
* 1a2b3c4 docs: base

Cada rama tiene su propio commit y comparten la base. main no contiene el buscador, y feature/busqueda no contiene el readme. Cambiar de rama cambia los ficheros del directorio de trabajo para que coincidan con el commit apuntado: 

git switch feature/busqueda
cat notas.md
# base
# buscador

git switch main
cat notas.md
# base
# readme
Git te protege al cambiar

Si tienes cambios sin commitear que chocarían con la otra rama, git switch se niega y te lo dice. No es un fallo: es la garantía de que no pierdes trabajo. Guárdalos con git stash (lección 4 del módulo anterior) o commitealos antes de cambiar.

4 · Ejemplo real

Caso 1: una funcionalidad, una rama, commits pequeños

git switch main
git switch -c feature/export-csv

# Commits atómicos mientras se desarrolla
git add src/export.js tests/export.test.js
git commit -m "feat: anade exportacion CSV"
git add src/ui/boton-export.js
git commit -m "feat: conecta el boton de exportacion"

# Comprobar que solo esta rama tiene los commits
git log --oneline main..HEAD
# 8b7c9d2 feat: conecta el boton de exportacion
# 7a6b5c4 feat: anade exportacion CSV

# Volver a main: los ficheros desaparecen del trabajo, los commits siguen en la rama
git switch main
ls src/export.js
# ls: cannot access 'src/export.js': No such file or directory

Que los ficheros «desaparezcan» al volver a main asusta la primera vez, pero es exactamente lo que debe pasar: el directorio de trabajo refleja el commit al que apunta HEAD. Los commits no se han ido; están en feature/export-csv.

Caso 2: inspeccionar una versión antigua sin riesgo

git log --oneline -5
# 9f8e7d6 docs: actualiza el README
# 8b7c9d2 feat: exportacion CSV
# 7a6b5c4 feat: anade exportacion CSV
# 6b5a493 chore: arranca el taller

# Mirar el estado de hace dos commits
git switch --detach HEAD~2
cat notas.md
# ...

# Probar una compilación, ejecutar tests, lo que haga falta
# ...

# Volver sin dejar rastro
git switch main
git status -sb
## main

Para solo mirar un fichero no hace falta ni cambiar: git show HEAD~2:notas.md. El detached HEAD tiene sentido cuando quieres ejecutar el proyecto entero en ese estado.

Caso 3: un commit en detached HEAD que sí quieres conservar

git switch --detach HEAD~2
printf 'prueba\n' >> notas.md
git commit -am "experiment: prueba de concepto"

git log --oneline -1
# 1f2e3d4 experiment: prueba de concepto

# La forma correcta de no perderlo: crear una rama AQUÍ
git switch -c experimento/prueba-conceptual
git status -sb
## experimento/prueba-conceptual

# Ahora la rama protege el commit y puedes fusionarlo o descartarlo con criterio

Caso 4: recuperar commits de una rama borrada con -D

git branch -D experimento/descartado
# Deleted branch experimento/descartado (was 4d3c2b1).

# ¿Seguro que no lo necesitabas? El reflog todavía lo recuerda
git reflog
# 4d3c2b1 HEAD@{5}: commit: experiment: prueba de concepto
# ...

git switch -c rescate/experimento 4d3c2b1
# La rama vuelve a existir, con todos sus commits.
El reflog es local y caduca

Recuperar una rama borrada funciona porque el reflog guarda el movimiento durante un tiempo (90 días por defecto). No es eterno, no se comparte y git gc puede limpiarlo. Para algo importante, crea la rama de rescate cuanto antes y, si debe sobrevivir a tu máquina, publícala.

6 · Errores habituales

1. Creer que una rama copia los ficheros

Mal — evitar ramas por miedo al espacio o a los conflictos 
# «No creo ramas porque luego hay que fusionarlas y se lía»
# Resultado: todo el equipo commitea en main y los conflictos llegan igual,
# pero sin un sitio limpio donde resolverlos.
Bien — ramas baratas y locales 
git switch -c feature/busqueda
# La rama pesa lo que un hash. Los ficheros se comparten hasta que divergen.

2. Commitear en main por no haber cambiado

Mal — descubrirlo después del commit 
# Estabas en main sin darte cuenta
git commit -am "feat: buscador"
git log --oneline -1
# 7c6b5a4 feat: buscador   (en main)
Bien — mover el commit a una rama antes de publicar 
git switch -c feature/busqueda    # la rama nace con el commit dentro
git switch main
git reset --hard HEAD~1           # main vuelve atrás (el commit sigue en la rama)

3. Commitear en detached HEAD y cambiar de rama

Mal — el commit queda sin rama que lo nombre 
git switch --detach HEAD~2
git commit -am "experiment: prueba"
git switch main
git log --oneline          # el commit no aparece: no lo alcanza ninguna rama
Bien — crear la rama en el momento 
git switch --detach HEAD~2
git commit -am "experiment: prueba"
git switch -c experimento/prueba    # antes de moverte

4. Borrar una rama con -D sin mirar

Mal — forzar el borrado por impaciencia 
git branch -D feature/busqueda
# Deleted branch feature/busqueda (was 7c6b5a4).
# Si tenía commits sin fusionar, ahora solo los conoce el reflog.
Bien — comprobar qué se perdería 
git log --oneline main..feature/busqueda   # ¿qué commits solo están ahí?
git branch -d feature/busqueda             # borra solo si está fusionada

5. Pensar que HEAD y la rama son lo mismo

Mal — interpretar HEAD~1 como «un commit menos en la rama» 
# En detached HEAD, HEAD~1 no tiene por qué ser el padre de main
git switch --detach 1a2b3c4
git show HEAD~1        # el padre de ESE commit, no de la punta de main
Bien — distinguir el puntero de la etiqueta 
git status -sb              # ¿HEAD está en una rama o suelto?
git branch --show-current   # vacío en detached HEAD
git log --oneline -1 HEAD   # el commit al que apunta HEAD ahora

7 · Ejercicio guiado

Vas a crear dos ramas, comprobar que divergen, borrar una fusionada y rescatar un commit que quedó en detached HEAD.

  1. Crea la base con un commit en main.
  2. Crea feature/a con switch -c, añade un commit y vuelve a main.
  3. Crea feature/b desde main, añade otro commit y comprueba el grafo con --graph --all.
  4. Fusiona feature/a en main (un fast-forward basta) y bórrala con -d.
  5. Entra en detached HEAD en el commit base, crea un commit y sácalo de ahí con una rama nueva.
  6. Comprueba que main no tiene ese commit y que la rama de rescate sí.

Solución resuelta:

mkdir ejercicio-ramas && cd ejercicio-ramas
git init
printf 'base\n' > notas.md
git add notas.md && git commit -m "docs: base"
git branch -M main

# 2. feature/a
git switch -c feature/a
printf 'base\na\n' > notas.md
git commit -am "feat: a"

git switch main

# 3. feature/b
git switch -c feature/b
printf 'base\nb\n' > notas.md
git commit -am "feat: b"

git switch main
git log --oneline --graph --decorate --all
# * 2b2b2b2 (feature/b) feat: b
# | * 1a1a1a1 (feature/a) feat: a
# |/
# * 0a0a0a0 (HEAD -> main) docs: base

# 4. Fusionar feature/a y borrarla
git merge feature/a
git branch -d feature/a
# Deleted branch feature/a (was 1a1a1a1).

# 5. Detached HEAD en la base
git switch --detach 0a0a0a0
printf 'base\nexperimento\n' > notas.md
git commit -am "experiment: prueba"
git switch -c experimento/prueba

# 6. Comprobaciones
git switch main
git log --oneline
# 1a1a1a1 feat: a
# 0a0a0a0 docs: base

git log --oneline experimento/prueba
# 3c3c3c3 experiment: prueba
# 0a0a0a0 docs: base
Lo que acabas de demostrar

Que main solo contiene lo que se le fusiona, que una rama fusionada se borra sin perder nada, y que un commit en detached HEAD se conserva en cuanto una rama lo nombra. Ningún fichero se ha duplicado en todo el ejercicio.

8 · Reto

El commit huérfano

Monta un repositorio con tres ramas (main, feature/a, feature/b) y una historia en la que un commit quede sin ninguna rama que lo apunte. Después:

  1. Demuestra con git log --oneline --all que el commit ha desaparecido de la vista.
  2. Recupéralo con git reflog y deja una rama con nombre que lo proteja.
  3. Comprueba que git branch -d se niega a borrar una rama con commits no fusionados, y explica con git log main..rama qué commits son esos.
  4. Dibuja a mano el grafo final y compáralo con git log --oneline --graph --decorate --all.

Entrega los comandos, las salidas y una explicación de qué habría pasado si el git gc hubiera pasado antes del rescate. No borres ninguna rama al final: el objetivo es que todas las etiquetas queden donde tú decidas.

Pista: la forma más limpia de crear el huérfano es commitear en detached HEAD y luego cambiar a otra rama sin crear una nueva. Para el punto 3, crea una rama con un commit propio y prueba a borrarla desde main. El reflog muestra los movimientos de HEAD, no los de las ramas: busca la línea del commit, no la del checkout.

9 · Resumen

  • Una rama es un puntero a un commit; crear o borrar una es instantáneo y no duplica ficheros.
  • HEAD es una referencia simbólica a la rama actual; al commitear, se mueve la rama, no HEAD.
  • git switch -c <nombre> crea y cambia; git switch <nombre> cambia; git switch - vuelve.
  • git branch -d solo borra si está fusionada; -D fuerza y puede dejar commits sin nombre.
  • Detached HEAD significa que HEAD apunta a un commit suelto; los commits nuevos no pertenecen a ninguna rama.
  • Para conservar esos commits: git switch -c <rama> antes de moverte, o reflog después.
  • git log --oneline --graph --decorate --all es la vista canónica del grafo.

10 · Preguntas frecuentes

¿Las ramas ocupan espacio en disco?

La rama en sí es un hash: unos 41 bytes. Lo que ocupa espacio son los commits y los objetos que contienen, y esos se comparten entre ramas: un mismo blob no se guarda dos veces porque esté en dos ramas. Por eso crear cien ramas de un repositorio grande no duplica el repositorio. Lo que sí puede crecer es el número de objetos si cada rama añade commits con contenido nuevo.

¿Qué pasa si borro una rama que no está fusionada?

Con -d, Git se niega y te avisa. Con -D, la borra y los commits dejan de ser alcanzables desde ninguna rama. No se borran de inmediato: el reflog guarda el movimiento y puedes recrear la rama con git switch -c nombre <hash>. Pero esa red caduca y git gc puede limpiarla, así que no es un plan de recuperación.

¿Puedo tener una rama y una etiqueta con el mismo nombre?

Sí, porque viven en espacios de nombres distintos (refs/heads/ y refs/tags/). Pero es una mala idea: cuando escribes el nombre en un comando, Git tiene que decidir a cuál te refieres y puede sorprenderte. Usa nombres que no colisionen, sobre todo en documentación y scripts.

¿Por qué git status dice «HEAD detached at»?

Porque HEAD no apunta a una rama, sino directamente a un commit. Ocurre al hacer switch --detach, al cambiar a una etiqueta o al hacer checkout de un hash. No es un error: es un modo de trabajo. Lo importante es saber que los commits nuevos que hagas ahí no pertenecen a ninguna rama hasta que crees una.

¿Puedo cambiar de rama con cambios sin commitear?

Sí, si los cambios no chocan con las diferencias entre las dos ramas. Git los lleva consigo al nuevo directorio de trabajo. Si chocan, se niega y te pide que los guardes o los commitees. Es una comodidad, pero puede confundir: después de cambiar, git status te mostrará esos cambios como si los hubieras hecho en la rama nueva. Si tienes dudas, stash antes de cambiar.
