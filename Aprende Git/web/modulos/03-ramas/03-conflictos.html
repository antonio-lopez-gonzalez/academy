Resolver conflictos

Módulo 3 · Ramas 🕐 40 minutos

1 · Introducción

Un conflicto no es un error de Git: es Git diciéndote «las dos ramas cambiaron esta zona y no voy a adivinar qué querías». Se detiene, deja el fichero marcado y espera. Nada se ha roto, nada se ha perdido, y todo lo que ha pasado se puede cancelar con un comando.

La razón por la que los conflictos asustan no es su dificultad técnica, sino no saber qué significa cada marcador ni en qué estado ha quedado el repositorio. Esta lección desmonta las dos cosas: primero el mecanismo (base, «nuestro» lado, «su» lado), después el procedimiento, y al final las trampas donde se atasca hasta la gente con años de Git.

Conflictos como señal, no como castigo

Un conflicto te avisa de que dos personas (o tú en dos momentos) cambiaron la misma línea con intenciones distintas. Cuanto más pequeños y frecuentes sean los merges, más pequeños serán los conflictos. Ramas de tres días producen conflictos de tres líneas; ramas de tres meses producen conflictos de tres ficheros.

2 · Teoría

Por qué ocurren

Git puede combinar cambios automáticamente cuando tocan zonas distintas del fichero, o incluso el mismo fichero en líneas separadas. Solo se detiene cuando los cambios se solapan o cuando son incompatibles por su tipo: 

  * 1a2b3c4 (main) feat: cambia precios
  * 9f8e7d6 feat: anade descuento
  | * 7c6b5a4 (feature/precios) feat: anade IVA
  |/
  * 4a38271 feat: precios base

  Las dos ramas modificaron la misma linea desde 4a38271:
  el merge se detiene y deja el fichero marcado.
TipoEjemploPor qué no hay solución automática
Mismo bloque modificado Las dos ramas cambian la misma función de otra manera Git no puede elegir la intención correcta
Modificar / borrar Una rama edita precios.js, la otra lo elimina ¿Resucitarlo con los cambios o aceptar el borrado?
Añadir / añadir Las dos crean src/export.js con contenido distinto Dos ficheros con el mismo nombre no caben
Renombrar / renombrar Cada rama renombra el fichero de otra forma ¿Cuál de los dos nombres gana?
Binarios Las dos versiones de una imagen o un PDF No hay líneas que marcar: hay que elegir una
Finales de línea o formato Un fichero se reformateó entero en un lado Todo el fichero «cambió», aunque la lógica sea igual

Las tres versiones: base, nuestro, suyo

Cuando hay conflicto, Git guarda en el índice tres versiones del mismo fichero: 

  :1:  base      el ancestro común (cómo estaba antes de que nadie lo tocara)
  :2:  ours      la versión de la rama en la que estás (HEAD)
  :3:  theirs    la versión de la rama que estás integrando

# Ver las tres versiones sin tocar nada
git show :1:src/precios.js     # base
git show :2:src/precios.js     # ours
git show :3:src/precios.js     # theirs

# Listar los ficheros sin resolver (con sus tres hashes)
git ls-files -u

Poder mirar la base es lo que separa una resolución razonada de un «me quedo con uno de los dos». La base te dice qué había antes, y con eso puedes entender qué quería cada lado.

Los marcadores

Git escribe en el fichero las dos versiones enfrentadas. Con la configuración por defecto: 

precio base
<<<<<<< HEAD
descuento 10
=======
IVA 21
>>>>>>> feature/precios
  • <<<<<<< HEAD: empieza el lado nuestro (la rama actual).
  • =======: separador entre los dos lados.
  • >>>>>>> feature/precios: cierra el lado suyo (la rama que se integra).

Si activas el estilo diff3 o zdiff3, aparece también la versión base en medio, que ayuda muchísimo a entender el conflicto: 

git config --global merge.conflictstyle zdiff3

precio base
<<<<<<< HEAD
descuento 10
||||||| base
(precio base, sin descuento ni IVA)
=======
IVA 21
>>>>>>> feature/precios
Configúralo hoy y no lo desactives

zdiff3 está disponible desde Git 2.35 y muestra la base recortada al bloque en conflicto. Con la base a la vista, la pregunta deja de ser «¿cuál de las dos líneas me quedo?» y pasa a ser «¿qué quería cada uno a partir de esto?», que es una pregunta mucho más fácil de responder.

El estado del repositorio: códigos de git status

git status --short
# UU src/precios.js
# AA src/export.js
# DU src/legacy.js
CódigoSignificadoQué hacer
UUboth modified: los dos lados editaronCombinar las dos versiones
AAboth added: los dos crearon el ficheroElegir el contenido final
DUdeleted by us: tú lo borraste, el otro lo editóDecidir si vive o muere
UDdeleted by them: el otro lo borró, tú lo editasteDecidir si vive o muere
DDboth deleted: los dos lo borrarongit rm y seguir

En la vista larga, git status lo dice con palabras: both modified, deleted by them… Leer esa parte ahorra el 80 % de las dudas.

El procedimiento, paso a paso

  1. Ver qué está en conflicto: git status --short o git diff --name-only --diff-filter=U.
  2. Entender cada lado: abrir el fichero, leer los marcadores, y si hace falta mirar :1:, :2: y :3:.
  3. Escribir la versión final: combinar, sustituir o descartar, borrando todos los marcadores.
  4. Marcar como resuelto: git add <fichero>. Para los borrados, git rm.
  5. Comprobar que no queda ninguno: git diff --check y buscar marcadores restantes.
  6. Ejecutar los tests y revisar el diff del resultado.
  7. Cerrar la operación: git commit, git merge --continue, git rebase --continue o git cherry-pick --continue.
El paso 6 no es opcional

Una resolución de conflicto es código nuevo que nadie ha probado: combina dos versiones que sí lo estaban. Compila, ejecuta los tests y revisa el diff completo con git diff --staged antes de cerrar. Los conflictos mal resueltos que llegan a producción casi siempre pasaron por alto este paso.

Elegir un lado: --ours y --theirs

# Quedarse con la versión de la rama actual (HEAD)
git restore --ours src/precios.js

# Quedarse con la versión de la rama que se integra
git restore --theirs src/precios.js

# Volver a generar los marcadores si te has liado
git restore --merge src/precios.js
Contexto«ours»«theirs»
git merge feature en mainmainfeature
git rebase main en featuremain (¡la rama base!)feature (tus commits)
git cherry-pick <commit>Tu rama actualEl commit que traes
En un rebase, «ours» no eres tú

Durante un rebase, Git reproduce tus commits encima de otra base. Para Git, «ours» es la base sobre la que estás rebasando y «theirs» son los commits que estás aplicando, es decir, los tuyos. La terminología está al revés de lo intuitivo. Antes de usar --ours o --theirs, mira git status y confirma contra qué estás integrando.

Herramientas: mergetool y rerere

# Configurar una herramienta de tres paneles
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait --merge $REMOTE $LOCAL $BASE $MERGED'

# Lanzarla solo para los ficheros en conflicto
git mergetool

# Salir sin tocar nada
git mergetool --tool-help

Una herramienta de tres paneles muestra base, nuestro y suyo en columnas y deja el resultado en una cuarta. Para conflictos grandes, ahorra tiempo y errores. Para conflictos de dos líneas, un editor normal es más rápido. 

# Recordar cómo resolviste un conflicto y reaplicarlo si vuelve a aparecer
git config --global rerere.enabled true

rerere («reuse recorded resolution») guarda tus resoluciones y las aplica automáticamente cuando el mismo conflicto reaparece: muy útil en ramas largas o en rebases repetidos. La primera vez lo resuelves tú; a partir de ahí, Git lo recuerda.

Evitar conflictos: lo que de verdad funciona

  • Ramas cortas y fusiones frecuentes. El conflicto crece con el tiempo de divergencia.
  • Traer la rama principal hacia la tuya a menudo (merge o rebase), resolviendo en pequeño.
  • Commits pequeños y atómicos: si un commit hace una sola cosa, su parte del conflicto se entiende sola.
  • Formateo aparte: un commit que reformatea todo el fichero garantiza conflictos con cualquier trabajo paralelo.
  • Finales de línea coherentes con .gitattributes (módulo 1), para que Git no vea cambios donde solo hay CRLF.
  • Repartir el trabajo: dos personas editando la misma función todo el día van a chocar siempre.

3 · Ejemplo mínimo

Un conflicto de una sola línea, resuelto de principio a fin:

mkdir taller-conflictos && cd taller-conflictos
git init
printf 'precio base\n' > precios.md
git add precios.md && git commit -m "feat: precios base"
git branch -M main

git switch -c feature/iva
printf 'precio base\nIVA 21\n' > precios.md
git commit -am "feat: anade IVA"

git switch main
printf 'precio base\ndescuento 10\n' > precios.md
git commit -am "feat: anade descuento"

git merge feature/iva
# Auto-merging precios.md
# CONFLICT (content): Merge conflict in precios.md
# Automatic merge failed; fix conflicts and then commit the result.

El fichero ha quedado así:

precio base
<<<<<<< HEAD
descuento 10
=======
IVA 21
>>>>>>> feature/iva

Las dos aportaciones son válidas y no se excluyen: el resultado correcto las combina. Escribimos la versión final, marcamos y cerramos: 

printf 'precio base\ndescuento 10\nIVA 21\n' > precios.md

git diff --check              # sin marcadores olvidados
git add precios.md
git status --short
# M  precios.md

git commit -m "Merge branch 'feature/iva'"
cat precios.md
# precio base
# descuento 10
# IVA 21
La trampa del «elijo uno»

Si aquí te hubieras quedado con uno de los dos lados, habrías perdido trabajo que ya estaba probado. Antes de descartar, pregúntate si las dos líneas pueden convivir. Solo cuando un lado sustituye conscientemente al otro tiene sentido --ours o --theirs.

4 · Ejemplo real

Caso 1: dos ficheros, uno modificado y uno borrado

git merge feature/limpieza
# CONFLICT (modify/delete): src/legacy.js deleted in feature/limpieza
#   and modified in HEAD. Version HEAD of src/legacy.js left in tree.
# CONFLICT (content): Merge conflict in src/precios.js

git status --short
# UD src/legacy.js
# UU src/precios.js

UD significa: ellos lo borraron, tú lo modificaste. Hay que decidir con criterio: 

# ¿Sigue habiendo referencias al fichero en el código actual?
grep -rn "legacy" src/ || echo "sin referencias"

# Si de verdad ya no se usa: aceptar el borrado
git rm src/legacy.js

# Si tu cambio era necesario: conservarlo y deshacer el borrado
git add src/legacy.js
# (y avisar al autor de la rama de que ese fichero sigue vivo)

Caso 2: mirar la base antes de decidir

# La versión base (antes de que nadie tocara nada)
git show :1:src/precios.js
# function precio() {
#   return base;
# }

# Nuestra versión
git show :2:src/precios.js
# function precio() {
#   return base * 0.9;   // descuento
# }

# Su versión
git show :3:src/precios.js
# function precio() {
#   return base * 1.21;  // IVA
# }

Con la base a la vista, está claro que las dos versiones parten del mismo punto y aplican factores distintos. El resultado probablemente es base * 0.9 * 1.21, no ninguno de los dos. Eso no lo adivina ni Git ni una herramienta: es una decisión de negocio.

Caso 3: conflicto durante un rebase y el lío de ours/theirs

git switch feature/busqueda
git rebase main
# CONFLICT (content): Merge conflict in src/buscador.js
# error: could not apply 7c6b5a4... feat: anade buscador

git status --short
# UU src/buscador.js

  Durante un rebase, los papeles están invertidos:

    «ours»   = main        (la base sobre la que rebasa)
    «theirs» = tus commits (lo que estás reaplicando)

  git restore --theirs src/buscador.js   -> tu versión
  git restore --ours   src/buscador.js   -> la de main

# Resolver a mano (lo recomendable) y continuar
git add src/buscador.js
git rebase --continue

# O cancelar el rebase entero y volver a como estabas
git rebase --abort

Caso 4: conflicto en un fichero binario

git merge feature/logos
# CONFLICT (content): Merge conflict in assets/logo.png
# warning: Cannot merge binary files: assets/logo.png

# No hay marcadores: hay que elegir una versión completa
git restore --theirs assets/logo.png    # la de la rama que integras
# o
git restore --ours assets/logo.png      # la de tu rama

git add assets/logo.png
git commit

Para binarios no hay combinación posible: se elige una versión entera o se genera una tercera a mano (por ejemplo, abriendo el diseño en su herramienta) y se sustituye el fichero antes de git add.

Caso 5: cancelar y replantear

git merge feature/precios
# ...seis ficheros en conflicto y ninguno claro...

git merge --abort
git status -sb
## main
# Árbol limpio: como antes de empezar.

# Alternativa mejor: resolver en la rama, con calma
git switch feature/precios
git merge main
# ...resolver los conflictos aquí, con contexto y tests...
git switch main
git merge feature/precios

Abortar no es rendirse: es elegir el momento y el lugar donde resolver. Un conflicto resuelto con prisa en main es un bug esperando a desplegarse.

6 · Errores habituales

1. Commitear con los marcadores dentro

Mal — git add . sin revisar el contenido 
git merge feature/precios
git add .
git commit -m "merge"
# El código lleva <<<<<<< y >>>>>>> dentro: no compila.
Bien — comprobar antes de marcar 
git diff --check          # señala líneas con marcadores
grep -rn '^<<<<<<<\|^>>>>>>>' src/   # búsqueda explícita
git add src/precios.js

2. Usar --ours durante un rebase creyendo que es «lo mío»

Mal — aplicar la intuición de merge en un rebase 
git rebase main
# CONFLICT...
git restore --ours src/buscador.js
# En un rebase, «ours» es main: acabas de tirar TU cambio.
Bien — comprobar los papeles antes de elegir 
git status                 # ¿merge, rebase o cherry-pick?
git log --oneline -1 REBASE_HEAD   # qué commit se está aplicando
# Resolver a mano o usar --theirs para tu versión, según el caso.

3. Borrar los marcadores dejando el código a medias

Mal — quitar las marcas y dar por resuelto 
# Resultado tras borrar los marcadores sin pensar:
function precio() {
  return base * 0.9; base * 1.21;   // sintaxis rota, lógica sin sentido
}
Bien — resolver, compilar y probar 
# Resultado razonado:
#   return base * 0.9 * 1.21;
npm test
git diff --staged
git add src/precios.js

4. Abortar después de haber commiteado

Mal — esperar que --abort deshaga el merge ya cerrado 
git merge feature/x
# ...resolver...
git commit -m "Merge branch 'feature/x'"

git merge --abort
# fatal: There is no merge to abort
Bien — usar la herramienta de la fase en la que estás 
# Antes del commit: cancelar
git merge --abort

# Después del commit: deshacer con revert
git revert -m 1 HEAD

5. Resolver el mismo conflicto cinco veces

Mal — repetir a mano cada vez que reaparece 
# Rama larga que se fusiona con main cada semana:
# el mismo conflicto de formato, resuelto de cero cada vez.
Bien — que Git recuerde la resolución 
git config --global rerere.enabled true
# La primera vez resuelves; las siguientes, Git aplica tu resolución
# y solo te pide confirmar con `git add`.

  2. Provoca un conflicto de modificación en la misma función y resuélvelo combinando los dos factores.

8 · Reto

El conflicto que se repite

Crea una rama feature/formato que reformatee por completo un fichero de código (cambiar indentación, comillas y comas) y, en paralelo, una rama feature/logica que cambie la lógica de ese mismo fichero sin tocar el formato. Después:

  1. Fusiona feature/logica en main y luego intenta fusionar feature/formato. Documenta cuántos conflictos aparecen y de qué tipo.
  2. Resuélvelos de modo que se conserven los dos: el formato nuevo y la lógica nueva.
  3. Repite el escenario desde cero con git config rerere.enabled true y comprueba cuánto trabajo te ahorra la segunda vez.
  4. Explica cómo habrías evitado el conflicto por completo con una estrategia de commits (piensa en un commit de formato aislado antes del cambio de lógica).

Entrega la lista de conflictos, la resolución final, la salida de git diff --check y una reflexión breve sobre por qué los cambios de formato globales son una fuente garantizada de conflictos. No reescribas nada publicado: si quieres rehacer el escenario, borra el repositorio de práctica y créalo de nuevo.

Pista: para que el conflicto sea masivo, reformatea el fichero entero en una sola pasada. Para conservar ambos, compara con git diff :1:<fichero> :2:<fichero> (qué cambió la lógica) y con :1: contra :3: (qué cambió el formato) y aplica los dos cambios sobre la base. Y recuerda: rerere no adivina, solo recuerda lo que tú ya decidiste.

9 · Resumen

  • Un conflicto aparece cuando dos ramas cambian las mismas líneas o hacen operaciones incompatibles (modificar/borrar, añadir/añadir, binarios).
  • Git guarda tres versiones en el índice: :1: base, :2: ours, :3: theirs.
  • Los marcadores <<<<<<< ======= >>>>>>> delimitan los dos lados; zdiff3 añade la base.
  • git status describe el tipo: both modified, deleted by us, both added…
  • Resolver: editar, git diff --check, git add, probar, y cerrar con git commit o --continue.
  • git restore --ours / --theirs elige un lado completo; en un rebase los papeles están invertidos.
  • git merge --abort, rebase --abort y cherry-pick --abort cancelan mientras la operación esté en curso.
  • Ramas cortas, merges frecuentes y formato aparte son la mejor prevención.

10 · Preguntas frecuentes

¿He perdido algo al abortar un merge?

No. git merge --abort devuelve el índice y el directorio de trabajo al estado anterior a empezar el merge, y ningún commit existente se modifica. Lo único que se pierde es el trabajo que hubieras hecho durante la resolución del conflicto, así que si llevas media hora combinando ficheros y quieres parar, guárdalos antes con git stash push -u o commitea en una rama temporal.

¿Por qué Git no resuelve esto solo? Parece obvio.

Porque «obvio» es una opinión sobre la intención, y Git no conoce tu negocio. Puede combinar cambios en zonas distintas porque no hay ambigüedad, pero cuando dos versiones tocan la misma línea, elegir es una decisión humana. Cuanto más pequeños sean los cambios, más veces acertará Git solo; cuando no lo hace, el conflicto es pequeño y concreto.

¿Qué significa «both modified» y por qué a veces veo UD o AA?

UU (both modified) es el caso habitual: los dos lados editaron el fichero. AA (both added) significa que cada rama creó el mismo fichero con contenido distinto. UD y DU aparecen cuando un lado borró el fichero y el otro lo modificó. En los tres casos el procedimiento es el mismo: entender, decidir, git add o git rm, y cerrar.

¿Puedo editar los ficheros con mi editor normal o necesito una herramienta especial?

Tu editor normal es suficiente y, para conflictos pequeños, es lo más rápido. Una herramienta de tres paneles (git mergetool) ayuda cuando hay muchos bloques o ficheros grandes, porque muestra base, nuestro y suyo a la vez. Lo único indispensable es borrar todos los marcadores y probar el resultado.

¿Cómo evito que el mismo conflicto me salga en cada merge?

Tres medidas: fusiona la rama principal hacia la tuya con frecuencia (los conflictos se resuelven en pequeño), activa rerere para que Git recuerde tus resoluciones, y separa los cambios de formato de los cambios de lógica. Si el conflicto reaparece idéntico, casi siempre es porque la rama lleva demasiado tiempo divergiendo.
