restore: descartar cambios

Módulo 2 · Deshacer 🕐 30 minutos

1 · Introducción

Tienes notas.md abierto, llevas veinte minutos probando un enfoque que no funciona y quieres volver a como estaba. O has hecho git add . con prisa y has metido en el índice un fichero de configuración que no debía viajar en el commit. Son dos problemas distintos, pero los dos se resuelven con la misma familia de comandos: git restore.

La clave es que restore no toca la historia. No mueve HEAD, no mueve la rama, no crea ni borra commits. Solo copia contenido hacia uno de los dos estados que aún no están guardados: el directorio de trabajo o el índice. Si en el módulo anterior aprendiste que cada comando mueve una de tres cosas, este es el comando que mueve las dos primeras.

¿Por qué existe restore?

Antes de Git 2.23, descartar cambios y cambiar de rama compartían el mismo comando: git checkout. Un mismo verbo servía para «tráeme otra rama» y para «machaca este fichero», con flags que cambiaban de significado según el contexto. Git 2.23 separó las dos intenciones: git switch para ramas y git restore para contenido. Menos ambigüedad y menos accidentes.

Al terminar esta lección sabrás exactamente qué copia hace cada variante de restore, cuál es irreversible y en qué orden usarlas cuando tienes cambios mezclados entre el índice y el directorio de trabajo.

2 · Teoría

Los tres estados, otra vez

Un fichero modificado puede estar en dos sitios a la vez, con contenidos distintos: el directorio de trabajo guarda lo que has escrito, y el índice guarda la versión que se congelará en el próximo commit. HEAD guarda la versión del último commit de la rama actual. restore elige un origen y un destino entre esos tres. 

  DIRECTORIO DE TRABAJO           ÍNDICE (staging)              HEAD (último commit)
  lo que ves y editas             lo que irá al commit          la foto ya guardada
  +----------------------+        +----------------------+      +----------------------+
  | notas.md  "Idea 2"   | --add->| notas.md  "Idea 2"   |--commit->| notas.md "Idea 2" |
  +----------------------+        +----------------------+      +----------------------+
            ^                              ^                              ^
            |                              |                              |
       destino de restore             destino de --staged          origen de --staged

La forma general

La sintaxis completa es git restore [--source=<commit>] [--staged] [--worktree] <ruta>. Lo importante no es memorizarla, sino leerla como una flecha: origen → destino.

ComandoOrigenDestino¿Toca el índice?¿Toca el trabajo?
git restore notas.md Índice Directorio de trabajo No Sí (descarta)
git restore --staged notas.md HEAD Índice Sí No
git restore --source=HEAD~2 notas.md El commit indicado Directorio de trabajo No Sí (sobrescribe)
git restore --staged --worktree notas.md HEAD Índice y trabajo Sí Sí (descarta)
Dos orígenes por defecto, y no es un capricho

Sin --source, git restore <ruta> copia del índice al trabajo: así no destruyes lo que ya habías preparado. En cambio, git restore --staged <ruta> copia de HEAD al índice: el índice se supone que representa a HEAD más lo que tú has añadido, así que su estado «limpio» es HEAD. Es el mismo comportamiento histórico de git checkout -- <ruta> y git reset <ruta>, ahora con nombres claros.

Descartar en el trabajo: git restore <archivo>

Este es el comando peligroso de la lección. Sustituye el contenido del fichero por la versión que hay en el índice. Si el fichero estaba preparado con git add, recuperas exactamente lo que preparaste. Si no lo estaba, recuperas la versión del último commit. En ambos casos, lo que habías escrito y no habías preparado desaparece. 

  ANTES                              DESPUÉS DE git restore notas.md
  índice:    "Idea 1"                índice:    "Idea 1"
  trabajo:   "Idea 1 + prueba"       trabajo:   "Idea 1"     <-- se pierde "prueba"
Irreversible de verdad

Los cambios que nunca llegaron al índice no son objetos de Git: no hay blob, no hay commit, no hay reflog que los devuelva. git restore es la excepción a la frase «en Git todo se recupera». Antes de ejecutarlo, comprueba con git diff qué vas a tirar. Si dudas, guarda una copia con git stash push -m "por si acaso".

Sacar del índice: git restore --staged

Este es seguro: deshace el git add. El índice vuelve a coincidir con HEAD para esa ruta, pero el directorio de trabajo no se toca. Tus cambios siguen ahí, simplemente vuelven a estar «sin preparar». Por eso es el primer paso casi siempre que quieres deshacer algo a medias. 

# Deshacer el add de un solo fichero
git restore --staged config.local.json

# Deshacer el add de todo lo que está en el índice (ojo: no borra nada del trabajo)
git restore --staged .

Fíjate en el matiz: --staged sin más no borra el fichero del disco. Si el fichero era nuevo y quieres que además desaparezca del trabajo, eso ya no es trabajo de restore: es un fichero sin seguimiento y se limpia con git clean (siempre con -n antes).

Traer una versión antigua: --source

--source permite elegir cualquier commit, etiqueta o rama como origen. Es la forma quirúrgica de decir «quiero el contenido de notas.md tal y como estaba en HEAD~3, pero sin cambiar de rama ni tocar la historia». 

# Ver la versión de hace tres commits (sin escribir nada)
git show HEAD~3:notas.md

# Traerla al directorio de trabajo (queda como cambio sin preparar)
git restore --source=HEAD~3 notas.md

# Traerla y además prepararla, para commitear esa vuelta atrás
git restore --source=HEAD~3 --staged --worktree notas.md
El flujo de «recuperar una versión»

Primero git show para mirar, después git restore --source para traer, y por último git diff para revisar qué has recuperado. Restaurar una versión antigua no borra los commits intermedios: solo cambia el contenido del fichero hacia atrás. Si lo que quieres es deshacer el commit entero, eso es revert (lección 3).

Restaurar por trozos: -p

git restore -p notas.md abre el mismo selector interactivo que git add -p, pero al revés: te pregunta, trozo a trozo, si quieres descartar ese cambio. Es la forma de tirar una función experimental sin perder el resto del trabajo del fichero. 

git restore -p notas.md
# y  -> descartar este trozo
# n  -> conservarlo
# s  -> partirlo en trozos más pequeños
# q  -> salir sin tocar el resto

Qué no hace restore

  • No mueve HEAD ni la rama: la historia queda igual.
  • No cambia de rama: para eso está git switch.
  • No borra ficheros sin seguimiento: para eso está git clean.
  • No recupera un commit borrado: para eso están reflog y reset.

3 · Ejemplo mínimo

Vamos a recorrer los tres movimientos con un repositorio de dos commits. El objetivo es ver en git status --short cómo cambia la columna del índice y la del trabajo. 

mkdir taller-restore && cd taller-restore
git init
printf '# Notas\n\n- Idea uno\n' > notas.md
git add notas.md
git commit -m "docs: primera nota"

# Segundo commit, para tener un HEAD~1 al que mirar
printf '# Notas\n\n- Idea uno\n- Idea dos\n' > notas.md
git commit -am "docs: segunda nota"

Ahora ensuciamos el fichero y comprobamos el estado:

printf '# Notas\n\n- Idea uno\n- Idea dos\n- Experimento\n' > notas.md
git status --short

 M notas.md

Un espacio y una M: el cambio está solo en el trabajo. Lo descartamos. Este paso es irreversible y por eso lo miramos antes con git diff. 

git diff
git restore notas.md
git status --short

diff --git a/notas.md b/notas.md
index 8a3c1f2..51d9e77 100644
--- a/notas.md
+++ b/notas.md
@@ -1,3 +1,4 @@
 # Notas

 - Idea uno
 - Idea dos
+- Experimento

Después de git restore, git status --short no imprime nada: el trabajo vuelve a coincidir con el índice, que a su vez coincide con HEAD.

Ahora el caso contrario: preparamos el cambio y lo sacamos del índice.

printf '# Notas\n\n- Idea uno\n- Idea dos\n- Tercera\n' > notas.md
git add notas.md
git status --short

git restore --staged notas.md
git status --short

M  notas.md      <-- M en la PRIMERA columna: preparado en el índice

 M notas.md      <-- M en la SEGUNDA columna: solo en el trabajo

El contenido sigue intacto: solo ha cambiado dónde está. Para comprobarlo, cat notas.md sigue mostrando «Tercera». Y ahora sí, si quisiéramos, podríamos tirarlo con git restore notas.md.

Por último, traemos una versión antigua sin tocar la historia:

git restore --source=HEAD~1 notas.md
git diff

diff --git a/notas.md b/notas.md
index 51d9e77..8a3c1f2 100644
--- a/notas.md
+++ b/notas.md
@@ -1,4 +1,3 @@
 # Notas

 - Idea uno
-- Idea dos

El fichero ha vuelto a la versión de HEAD~1, que solo contenía «Idea uno». Respecto al índice, desaparece «Idea dos», y ese cambio aparece como modificación sin preparar. git log --oneline sigue mostrando los dos commits: la historia no se ha movido.

4 · Ejemplo real

En el repositorio taller del curso hay tres ficheros en estados distintos y una entrega a punto de cerrarse. La situación: 

 M notas.md                 cambio en el trabajo, sin preparar
M  configuracion.json       preparado por error con `git add .`
?? borrador.txt             fichero nuevo sin seguimiento

El objetivo es commitear solo notas.md, dejar configuracion.json fuera del commit pero sin perder lo editado, y no tocar borrador.txt. 

# 1. Sacar del índice lo que no debe viajar (el trabajo se conserva)
git restore --staged configuracion.json

# 2. Preparar solo la nota
git add notas.md

# 3. Revisar exactamente qué va a entrar
git diff --staged

# 4. Commitear
git commit -m "docs: cierra las notas de la reunion"

El estado final es el que buscábamos:

 M configuracion.json       sigue ahí, fuera del commit
?? borrador.txt             intacto, sin seguimiento
El orden importa

--staged primero y restore después. Si haces git restore configuracion.json antes de sacarlo del índice, Git copia la versión preparada al trabajo: no pierdes nada, pero tampoco arreglas el problema. Y si lo haces después de sacarlo del índice, esa misma orden sí destruye la edición. Pensar en la flecha origen → destino evita el accidente.

Segundo escenario real: has estado probando un cambio en notas.md durante una hora y resulta que el enfoque era malo, pero el fichero tenía además una corrección de una errata que sí quieres conservar. No tires todo: 

# Ver qué trozos hay y descartar solo el experimento
git restore -p notas.md

# Alternativa si el experimento está en un rango de líneas concreto:
git diff notas.md              # localiza el trozo
git restore -p notas.md        # responde `y` solo a ese trozo

Tercer escenario: quieres recuperar la versión de notas.md que funcionaba antes del último refactor, compararla y decidir. No cambies de rama ni reescribas nada: 

git log --oneline -- notas.md
# a1b2c3d docs: segunda nota
# 9f8e7d6 docs: primera nota

git show a1b2c3d:notas.md          # mirar sin tocar
git restore --source=a1b2c3d notas.md
git diff                            # revisar qué supone volver atrás

6 · Errores habituales

1. Creer que todo en Git se recupera

Mal — descartar sin mirar, confiando en el reflog 
# Llevas una hora probando y decides que no sirve
git restore notas.md

# ...y luego recuerdas que ahí también estaba la corrección de la errata
git reflog            # no aparece: nunca hubo commit ni add
Bien — revisar el diff o guardar antes de descartar 
git diff notas.md          # ¿qué voy a tirar exactamente?
git stash push -m "experimento notas"   # red de seguridad reversible
git restore notas.md
# Si al final no lo necesitas: git stash drop

El reflog registra movimientos de referencias y commits, no el contenido que nunca llegó a un objeto. El editor puede tener su propio historial, pero Git no.

2. Confundir --staged con «borrar los cambios»

Mal — esperar que el fichero desaparezca del trabajo 
git restore --staged configuracion.json
ls configuracion.json        # sigue ahí, y con tus cambios
Bien — dos pasos conscientes si de verdad quieres tirarlo 
git restore --staged configuracion.json   # fuera del índice
git diff configuracion.json               # comprobar qué queda
git restore configuracion.json            # ahora sí, descartar el trabajo

--staged solo mueve el índice. Es el malentendido más común de la lección y la causa de commits que «no llevaban» el cambio esperado.

3. Usar git checkout por costumbre

Mal — el comando ambiguo que hacía dos cosas 
git checkout -- notas.md      # descarta (forma antigua)
git checkout main              # cambia de rama (misma palabra, otro efecto)
Bien — una intención, un comando 
git restore notas.md           # contenido: descartar
git restore --staged notas.md  # contenido: sacar del índice
git switch main                # ramas: cambiar
git switch -c feature/busqueda # ramas: crear y cambiar

git checkout sigue existiendo y funciona, pero ya no lo necesitas para estas tareas. En un curso y en un equipo, usar el verbo específico hace que el comando se explique solo.

4. Querer borrar un fichero nuevo con restore

Mal — restaurar algo que nunca estuvo en Git 
git restore borrador.txt
# error: pathspec 'borrador.txt' did not match any file(s) known to git
Bien — clean con simulación previa 
git clean -n          # lista lo que se borraría (¡siempre primero!)
git clean -f borrador.txt

restore restaura desde el índice o desde un commit. Un fichero sin seguimiento no está en ninguno de los dos. git clean borra del disco y también es irreversible.

5. Restaurar desde el commit equivocado

Mal — usar HEAD cuando el índice tenía lo bueno 
# Habías preparado una versión buena y luego la sobrescribiste en el editor
git restore --source=HEAD notas.md
# Adiós a la versión preparada: la sustituyes por la del último commit
Bien — el índice conserva lo preparado; úsalo como origen 
git restore notas.md          # origen por defecto: el índice
git diff --staged             # comprobar qué versión había preparada

7 · Ejercicio guiado

Vas a montar un repositorio con dos commits y tres ficheros en estados distintos, y a dejarlo limpio sin perder la edición de uno de ellos.

  1. Crea el escenario. En una carpeta temporal, inicializa un repositorio con notas.md y configuracion.json, y haz dos commits.
  2. Ensucia el árbol. Modifica notas.md sin prepararlo, modifica configuracion.json y prepáralo, y crea borrador.txt sin seguimiento.
  3. Lee el estado. Ejecuta git status --short y explica qué significa cada columna antes de tocar nada.
  4. Saca la configuración del índice y comprueba que el cambio sigue en el trabajo.
  5. Descarta la nota, pero antes mira el diff. Después confirma que el árbol está limpio salvo la configuración y el borrador.
  6. Recupera una versión antigua de notas.md desde el primer commit, mírala con git diff y decide si la preparas o la descartas.

Solución resuelta:

mkdir ejercicio-restore && cd ejercicio-restore
git init

printf '# Notas\n\n- Semana 1\n' > notas.md
printf '{\n  "tema": "oscuro"\n}\n' > configuracion.json
git add .
git commit -m "chore: arranca el taller"

printf '# Notas\n\n- Semana 1\n- Semana 2\n' > notas.md
git commit -am "docs: segunda semana"

# 2. Ensuciar
printf '# Notas\n\n- Semana 1\n- Semana 2\n- PRUEBA\n' > notas.md
printf '{\n  "tema": "claro",\n  "debug": true\n}\n' > configuracion.json
git add configuracion.json
printf 'borrador\n' > borrador.txt

# 3. Leer
git status --short
#  M notas.md
# M  configuracion.json
# ?? borrador.txt

# 4. Fuera del índice (el trabajo se queda)
git restore --staged configuracion.json
git status --short
#  M configuracion.json
#  M notas.md
# ?? borrador.txt

# 5. Descartar la nota, mirando antes
git diff notas.md
git restore notas.md
git status --short
#  M configuracion.json
# ?? borrador.txt

# 6. Versión del primer commit
git log --oneline
# 2f9c1ab docs: segunda semana
# 8d4e0c3 chore: arranca el taller

git show 8d4e0c3:notas.md
# # Notas
#
# - Semana 1

git restore --source=8d4e0c3 notas.md
git diff
# muestra que desaparece "- Semana 2"

# Si la quieres dejar así:
git add notas.md
git commit -m "docs: vuelve a la nota de la semana 1"
Comprobación

Al terminar, git status --short debe mostrar solo la configuración modificada y el borrador sin seguimiento (o nada, si decidiste descartarlos también). Si aparece una M en la primera columna que no esperabas, te has dejado algo en el índice.

8 · Reto

El fichero que estaba en tres sitios

Prepara un repositorio donde notas.md tenga tres versiones distintas a la vez: una en el último commit, otra en el índice y otra en el directorio de trabajo. Sin crear commits nuevos, consigue los cuatro objetivos siguientes y demuéstralo con la salida de git status --short y git diff después de cada paso:

  1. Que el índice vuelva a coincidir con HEAD y el trabajo conserve su versión.
  2. Que el trabajo vuelva a coincidir con el índice y el índice conserve la suya.
  3. Que ambos, índice y trabajo, coincidan con la versión del commit anterior a HEAD.
  4. Que el fichero quede con la versión del trabajo original, pero preparada para el próximo commit.

Pista: cada objetivo se resuelve con una combinación distinta de --staged, --worktree y --source. Antes de escribir el comando, di en voz alta cuál es el origen y cuál el destino. Y recuerda que el paso 3 no se puede deshacer con reflog si la versión del trabajo nunca llegó al índice: guárdala antes con git stash push -m.

9 · Resumen

  • git restore <archivo> copia del índice al directorio de trabajo y descarta lo no preparado de forma irreversible.
  • git restore --staged <archivo> copia de HEAD al índice: deshace el add sin tocar el trabajo.
  • git restore --source=<commit> <archivo> trae una versión antigua al trabajo; con --staged también la prepara.
  • git restore --staged --worktree <archivo> devuelve índice y trabajo a HEAD.
  • restore nunca mueve HEAD ni la rama: no es un comando de historia.
  • No borra ficheros sin seguimiento (git clean) ni recupera commits (reflog, reset).

10 · Preguntas frecuentes

¿Puedo recuperar lo que he tirado con git restore?

Si el contenido llegó alguna vez al índice, probablemente sí: el blob existe en la base de objetos y se puede localizar con git fsck --lost-found, aunque es una operación forense, no un botón de deshacer. Si nunca se preparó, no: Git no lo conoce y reflog no guarda contenido de trabajo. Por eso la recomendación es mirar git diff o hacer un stash antes de descartar.

¿Cuál es la diferencia exacta entre restore --staged y reset?

git restore --staged <ruta> solo toca el índice de esas rutas: no mueve HEAD ni la rama. git reset <commit> mueve la rama (y con ella HEAD) y, en su modo por defecto --mixed, además resetea el índice. Para deshacer un add, restore --staged es la herramienta precisa; el reset de rutas es la forma antigua y hoy se prefiere restore.

¿Por qué git restore . es más peligroso que git restore notas.md?

Porque el pathspec . alcanza todos los ficheros con seguimiento del directorio actual y de sus subdirectorios. Un cambio a medias en otro fichero que no recordabas desaparece también. Además, . no toca los ficheros nuevos sin seguimiento, así que el árbol puede quedar en un estado que no esperabas: unos limpios y otros intactos. Sé explícito con las rutas.

¿restore funciona con directorios y con patrones?

Sí. Acepta pathspecs de Git: git restore src/ restaura todo lo que hay bajo src/, y git restore '*.md' (con comillas para que el shell no lo expanda) restaura los Markdown. También admite :(glob) y :(exclude) para afinar. Cuanto más amplio el patrón, más importante es mirar antes con git diff -- <patrón>.

Si tengo el fichero preparado y ejecuto git restore, ¿pierdo el add?

No. git restore <archivo> usa el índice como origen, así que el fichero queda exactamente con la versión preparada: el add se mantiene. Solo perderías lo que hubiera en el trabajo por encima de esa versión. Para devolver el índice a HEAD necesitas --staged.
