revert: deshacer lo publicado

Módulo 2 · Deshacer 🕐 30 minutos

1 · Introducción

El commit con el bug ya está en main, ya se ha desplegado y tres compañeros lo tienen en su clon. No puedes hacerlo desaparecer: si mueves la rama con reset, sus historias y la tuya dejan de coincidir y alguien tendrá que reparar el desastre a mano. Lo que sí puedes hacer es añadir un commit nuevo que deshaga el anterior. Eso es git revert.

La diferencia conceptual es enorme y conviene fijarla desde el principio: reset dice «esto nunca ocurrió»; revert dice «esto ocurrió y ahora lo deshago». La primera frase reescribe el pasado y solo es aceptable en privado. La segunda es un hecho nuevo, compatible con todo el mundo, y es la única correcta cuando el pasado ya es público.

La regla de oro, en una frase

Si otra persona puede haber hecho fetch de ese commit, no lo reescribas: reviértelo. Reescribir historia publicada obliga a los demás a reconciliar su trabajo con hashes que ya no existen, y la solución nunca es «fuerza el push y que se apañen».

2 · Teoría

Qué hace revert por dentro

Git calcula el parche que introdujo el commit (la diferencia entre el commit y su padre), lo aplica al revés sobre el estado actual de la rama y crea un commit nuevo con ese resultado. El commit original sigue exactamente donde estaba; lo que cambia es que ahora hay un commit más que neutraliza su efecto. 

  ANTES

    A <-- B <-- C        main, HEAD
              |
              B introduce un bug que ya está publicado

  DESPUÉS DE git revert C

    A <-- B <-- C <-- C'   main, HEAD
                       |
                       C' es el commit inverso: aplica el parche de C al revés
                       Su mensaje por defecto: Revert "mensaje de C"

Fíjate en que C no desaparece de git log. El nuevo commit tiene un hash distinto y un mensaje que cita al original, algo así: 

commit 8b7c9d2e4f1a...
Author: Ana <ana@ejemplo.com>
Date:   ...

    Revert "feat: cambia el formato de fecha"

    This reverts commit 3e8a111c2b4d....

    # Conflicts:  (solo si hubo conflicto)

revert frente a reset

Revert no «borra» el cambio del historial

El código buggy sigue siendo consultable en C y el diff de C' explica qué se deshizo. Eso es una ventaja: dentro de seis meses, cuando alguien pregunte por qué se cambió dos veces la misma línea, la respuesta estará en la historia. Un reset borra la pregunta, no solo la respuesta.

Formas de invocarlo

# Deshacer el último commit (crea un commit nuevo)
git revert HEAD

# Deshacer un commit concreto por su hash
git revert 3e8a111

# Varios commits: se revierten del más nuevo al más antiguo
git revert HEAD~3..HEAD

# Aplicar los cambios inversos sin commitear todavía
git revert --no-commit HEAD~2..HEAD
git commit -m "revert: deshace el experimento de formateo"

--no-commit es útil cuando quieres deshacer varios commits en un solo commit de vuelta atrás, o cuando quieres revisar el resultado antes de confirmarlo. Con rangos, Git procesa los commits en orden inverso (del más reciente al más antiguo) para reducir conflictos: si deshaces un cambio y luego su preparación, el parche encaja mejor en ese orden.

Conflictos al revertir

Un revert es una aplicación de parche, así que también puede chocar. Ocurre cuando commits posteriores tocaron las mismas líneas que el commit que intentas deshacer. Git se detiene, marca los conflictos y te deja el repositorio en un estado intermedio: 

git revert 3e8a111
# error: could not revert 3e8a111... feat: cambia el formato de fecha
# hint: after resolving the conflicts, mark the corrected paths
# hint: with 'git add <paths>' or 'git rm <paths>'
# hint: and commit the result with 'git commit'

git status --short
# UU src/fechas.js        <- both modified
  1. Resuelves el conflicto editando el fichero y quitando los marcadores.
  2. git add <rutas> para marcar como resuelto.
  3. git revert --continue para cerrar el commit (o git commit, que usa el mensaje preparado).
  4. Si te arrepientes: git revert --abort devuelve todo al estado anterior.

En un rango, git revert --skip descarta el commit que está causando el conflicto y sigue con el siguiente. Úsalo solo si de verdad quieres omitir ese cambio; si no, resuelve.

Revertir un merge: el flag -m

Un commit de merge tiene dos padres, así que Git no puede saber solo «respecto a qué» calcular el parche inverso. Hay que decirle cuál es la línea principal (mainline): 

        A <-- B <-- C <-- M      main
                       |    /
                       |   /
                       D <-- E         feature

  M es el merge. Sus padres, en orden:
    1) C  (la rama en la que estabas: main)
    2) E  (la rama que fusionaste: feature)

  git revert -m 1 M   -> deshace lo que aportó feature, dejando main como estaba
  git revert -m 2 M   -> deshace lo que aportó main (rara vez lo que quieres)

# Comprobar el orden de los padres antes de elegir
git show --no-patch --pretty=%P M
# c0ffee1 deadbee      <- primero main, segundo feature

git revert -m 1 M
Elegir mal el mainline no da error: da un desastre silencioso

-m 2 no falla: genera un commit que deshace el otro lado. Revisa siempre git show --stat del merge y el orden de los padres. Si el resultado del revert no es el que esperabas, git reset --hard ORIG_HEAD (aún en local) o git revert del revert.

El caso especial: revertir un revert

Supón que revertiste el merge M y dos semanas después quieres recuperar esa funcionalidad. Si vuelves a ejecutar git merge feature, Git dirá Already up to date: los commits de feature ya son ancestros de main, aunque su efecto esté neutralizado. La forma correcta es revertir el commit de revert: 

git log --oneline
# 9a8b7c6 Revert "Merge branch 'feature/busqueda'"
# 5f4e3d2 Merge branch 'feature/busqueda'

git revert 9a8b7c6
# Vuelve a aplicar lo que el merge aportaba, sin reescribir nada.

Si después del revert de merge sigues haciendo merges de feature, los commits nuevos sí se aplican; solo los antiguos, ya fusionados y luego revertidos, quedan fuera. Esa asimetría es la razón por la que conviene documentar bien el revert.

Requisitos y contexto

  • El árbol debería estar limpio: un revert con cambios a medias puede negarse o mezclar cosas.
  • Funciona igual en local y en remoto: es un commit normal, se publica con git push.
  • No necesita permisos especiales ni reescribir la rama remota.
  • Es la herramienta de los hotfix: revertir en main, desplegar, y arreglar con calma.

3 · Ejemplo mínimo

Tres commits y un revert del del medio, que es el caso más ilustrativo:

mkdir taller-revert && cd taller-revert
git init

printf 'version 1\n' > notas.md
git add notas.md && git commit -m "docs: version 1"

printf 'version 1\nlinea peligrosa\n' > notas.md
git commit -am "feat: anade linea peligrosa"

printf 'version 1\nlinea peligrosa\nlinea segura\n' > notas.md
git commit -am "feat: anade linea segura"

git log --oneline
# 3c3c3c3 feat: anade linea segura
# 2b2b2b2 feat: anade linea peligrosa
# 1a1a1a1 docs: version 1

git revert 2b2b2b2

[main 4d4d4d4] Revert "feat: anade linea peligrosa"
 1 file changed, 1 deletion(-)

cat notas.md
# version 1
# linea segura

git log --oneline
# 4d4d4d4 Revert "feat: anade linea peligrosa"
# 3c3c3c3 feat: anade linea segura
# 2b2b2b2 feat: anade linea peligrosa
# 1a1a1a1 docs: version 1

La historia tiene cuatro commits, no dos. La línea peligrosa ya no está en el fichero, pero el commit que la introdujo sigue visible. Y observa que la línea segura, añadida después, se ha conservado: el revert solo revierte el parche de 2b2b2b2, no todo lo que vino detrás.

Comprueba siempre el diff del revert

git show HEAD te muestra exactamente qué ha deshecho. En un revert con conflictos resueltos a mano, ese diff es la única forma de confirmar que no has deshecho de más. El mensaje automático ayuda, pero no sustituye a leer el parche.

4 · Ejemplo real

Caso 1: el bug que ya está en producción

Un commit cambió el formato de fecha y rompió la API. Ya está en main, desplegado y compartido. La secuencia completa, sin reescribir nada: 

git log --oneline -5
# 3e8a111 feat: cambia el formato de fecha a ISO
# ...

# 1. Revertir el commit culpable
git revert 3e8a111
# [main 8b7c9d2] Revert "feat: cambia el formato de fecha a ISO"

# 2. Revisar qué se ha deshecho
git show --stat HEAD
git show HEAD -- src/fechas.js

# 3. Publicar
git push

# 4. El arreglo de verdad va en un commit posterior, con su test
git switch -c fix/fecha-api
# ...corregir y commitear...

Los compañeros hacen git pull y reciben el revert como un commit normal. Nadie tiene que borrar su rama ni resetear nada. Ese es el valor real de revert.

Caso 2: deshacer un merge entero

git log --oneline --graph -6
# *   9f8e7d6 Merge branch 'feature/busqueda'
# |\
# | * 7c6b5a4 feat: indice de titulos
# | * 6b5a493 feat: busqueda por autor
# * | 5a49382 docs: actualiza el README
# |/
# * 4a38271 chore: arranca el taller

# El merge está en main y ha roto la busqueda:
git revert -m 1 9f8e7d6
# [main 0d1c2b3] Revert "Merge branch 'feature/busqueda'"

git show --stat HEAD
# los ficheros que aportó feature vuelven al estado anterior
El merge sigue en la historia

El revert no elimina la estructura del grafo: el merge y sus commits siguen ahí. Lo que hace es deshacer sus efectos en la punta de main. Si más adelante quieres recuperar la funcionalidad, revierte el revert, no vuelvas a fusionar la rama.

Caso 3: varios commits en un solo revert

Un experimento de tres commits que hay que deshacer de golpe, pero dejando un único commit de vuelta atrás para que la historia sea legible: 

git log --oneline -5
# e5e5e5e wip: tercer intento de cache
# d4d4d4d wip: segundo intento de cache
# c3c3c3c wip: primer intento de cache
# b2b2b2b feat: busqueda
# a1a1a1a docs: inicio

# Aplicar los tres parches inversos sin commitear
git revert --no-commit c3c3c3c..e5e5e5e

# Revisar el resultado conjunto
git status --short
git diff --staged

# Un solo commit que explica la vuelta atrás
git commit -m "revert: descarta el experimento de cache"

Nota el rango: c3c3c3c..e5e5e5e incluye d4d4d4d y e5e5e5e pero no c3c3c3c. Para incluir el primero, usa c3c3c3c^..e5e5e5e o indica los hashes uno a uno con git revert --no-commit c3c3c3c d4d4d4d e5e5e5e.

Caso 4: conflicto al revertir y salida limpia

git revert 3e8a111
# CONFLICT (content): Merge conflict in src/fechas.js

git status --short
# UU src/fechas.js

# ...editar el fichero, quitar <<<<<<< ======= >>>>>>>...

git add src/fechas.js
git revert --continue
# Se abre el editor con el mensaje preparado; guárdalo y cierra.

# Si no quieres seguir:
# git revert --abort

Un detalle importante: tras un conflicto, el revert está «en curso». No empieces otro comando que toque la historia hasta terminarlo o abortarlo; git status te recuerda en qué paso estás.

6 · Errores habituales

1. Usar reset en una rama que ya está publicada

Mal — borrar el commit y forzar el remoto 
git reset --hard HEAD~1
# ...y forzar el push para reescribir la rama remota
# Los demás tienen un commit que ya no existe.
# Cualquier trabajo basado en él se vuelve un conflicto manual.
Bien — añadir el commit inverso 
git revert HEAD
git push
# Historia hacia delante; nadie tiene que tocar su clon.

2. Revertir un merge sin -m

Mal — Git no sabe contra qué padre comparar 
git revert 9f8e7d6
# error: commit 9f8e7d6 is a merge but no -m option was given.
# fatal: revert failed
Bien — indicar el mainline correcto 
git show --no-patch --pretty=%P 9f8e7d6
# c0ffee1 deadbee   -> el primero es main
git revert -m 1 9f8e7d6

3. Creer que revert borra el commit del historial

Mal — esperar que git log deje de mostrarlo 
git revert 3e8a111
git log --oneline
# 8b7c9d2 Revert "feat: cambia el formato de fecha"
# 3e8a111 feat: cambia el formato de fecha   <- sigue ahí, y debe seguir
Bien — entenderlo como un hecho nuevo en la historia 
git log --oneline
git show 8b7c9d2      # el parche inverso
git show 3e8a111      # el cambio original, para contexto

Si necesitas que el commit desaparezca por completo (por ejemplo, porque contiene un secreto), no es un problema de revert: es una reescritura de historia coordinada. Este curso no da recetas para purgar secretos de un remoto; se documenta el riesgo y se consulta la guía oficial.

4. Revertir en un árbol sucio

Mal — mezclar trabajo a medias con el parche inverso 
# Tienes cambios sin preparar en src/fechas.js
git revert 3e8a111
# error: your local changes would be overwritten by revert
Bien — limpiar o guardar antes 
git stash push -m "trabajo antes del revert"
git revert 3e8a111
git stash pop

5. Abandonar a medias un revert con conflicto

Mal — empezar otro comando con el revert en curso 
git revert 3e8a111
# CONFLICT...
git switch otra-rama        # Git se niega o te deja un estado confuso
Bien — terminar o abortar explícitamente 
git status                 # te dice qué falta
git add <rutas> && git revert --continue
# o, si no quieres seguir:
git revert --abort

7 · Ejercicio guiado

Vas a deshacer un commit publicado, a comprobar que la historia no se ha reescrito y a recuperar después lo deshecho con un segundo revert.

  1. Crea tres commits: una base, una funcionalidad y una línea que «rompe» la salida.
  2. Revierte el commit intermedio y comprueba el contenido del fichero.
  3. Lee la historia con git log --oneline y localiza el commit de revert.
  4. Revierte el revert y comprueba que vuelve el cambio original.
  5. Aborta un revert con conflicto: provoca uno y sal con --abort.

Solución resuelta:

mkdir ejercicio-revert && cd ejercicio-revert
git init

printf 'ok\n' > salida.txt
git add salida.txt && git commit -m "feat: salida base"

printf 'ok\nERROR 500\n' > salida.txt
git commit -am "feat: anade diagnostico (rompe la salida)"

printf 'ok\nERROR 500\ndetalle\n' > salida.txt
git commit -am "docs: amplia el detalle"

# 2. Revertir el commit intermedio
git revert HEAD~1
cat salida.txt
# ok
# detalle

# 3. Historia
git log --oneline
# 5e5e5e5 Revert "feat: anade diagnostico (rompe la salida)"
# 4d4d4d4 docs: amplia el detalle
# 3c3c3c3 feat: anade diagnostico (rompe la salida)
# 2b2b2b2 feat: salida base

# 4. Revertir el revert
git revert HEAD
cat salida.txt
# ok
# ERROR 500
# detalle

# 5. Conflicto y abort
printf 'ok\nERROR 503\ndetalle\n' > salida.txt
git commit -am "fix: cambia el codigo de error"

git revert HEAD~4
# CONFLICT en salida.txt: el commit original anadia "ERROR 500",
# pero la linea ya no dice eso.
git status --short
# UU salida.txt
git revert --abort
git status --short
# (árbol limpio, como antes de intentarlo)
Qué demuestra el paso 4

Que «deshacer un deshacer» es un commit normal, no una operación especial. Git no guarda un estado mágico del pasado: guarda parches. Revertir el revert vuelve a aplicar el parche original, y por eso salida.txt recupera la línea que habíamos quitado.

8 · Reto

El merge que había que deshacer (y recuperar)

Crea un repositorio con una rama feature/export de dos commits, fusiónala en main con un merge commit y publica el resultado en un remoto local (bare). A partir de ahí, sin reescribir ninguna rama publicada:

  1. Revierte el merge completo y demuestra con git show --stat qué ficheros han vuelto atrás.
  2. Añade un commit en feature/export y fusiónalo en main. Explica por qué ese commit nuevo sí aparece y los dos antiguos no.
  3. Recupera la funcionalidad original revirtiendo el revert, y comprueba el grafo final con git log --oneline --graph --all.
  4. Provoca un conflicto al revertir y resuélvelo manteniendo la parte que sí quieres conservar.

Entrega las salidas de git log, los mensajes de commit y un párrafo que explique el orden de los padres del merge (-m 1 frente a -m 2) y qué habría pasado si hubieras elegido el otro.

Pista: antes de revertir el merge, mira el orden de los padres con git show --no-patch --pretty=%P. Para el punto 2, recuerda que Git compara contra los ancestros, no contra los efectos: un commit fusionado y revertido sigue siendo ancestro. Para el conflicto, no hace falta que lo busques: introduce a propósito una línea en el mismo sitio después del revert y vuelve a revertir.

9 · Resumen

  • git revert <commit> crea un commit nuevo que aplica el parche inverso del indicado.
  • No reescribe la historia: el commit original sigue visible y los hashes no cambian.
  • Es la herramienta correcta para deshacer algo ya publicado o desplegado.
  • Un merge necesita -m 1 (mainline = rama en la que estabas) o -m 2 para el otro lado.
  • Tras revertir un merge, volver a fusionar la rama no restaura nada: hay que revertir el revert.
  • Si hay conflicto: resolver, git add, git revert --continue; o git revert --abort.
  • --no-commit permite agrupar varios reverts en un solo commit.

10 · Preguntas frecuentes

¿Revertir un commit elimina también los commits posteriores?

No. Solo aplica el parche inverso de ese commit sobre el estado actual. Los commits posteriores se conservan, y si tocaron las mismas líneas puede haber conflicto. Si lo que quieres es deshacer todo lo que vino después de un punto, eso es un reset (en local) o una secuencia de reverts (en remoto).

¿Puedo revertir un commit que ya es un revert?

Sí, y es la forma estándar de recuperar una funcionalidad que se revirtió. Se comporta como cualquier otro commit: aplica al revés su parche. Lo verás a menudo en equipos que revierten un merge problemático y semanas después quieren la funcionalidad de vuelta.

¿Qué pasa si revierto un merge y luego mis compañeros siguen trabajando en la rama?

Sus commits nuevos se pueden volver a fusionar sin problema, porque no formaban parte del merge revertido. Los commits antiguos, en cambio, ya son ancestros y no se reaplicarán. Si quieres recuperarlos, revierte el revert. Conviene avisar en el PR y dejarlo escrito en el mensaje del commit para que nadie se sorprenda.

¿Revert necesita que el árbol esté limpio?

En la práctica, sí. Git se niega si los cambios locales se solapan con el parche que va a aplicar, y un revert con el índice a medias puede dejarte en un estado difícil de leer. La rutina segura es git status, guardar con stash si hace falta, revertir, y recuperar el stash después.

¿Cuál es el mainline correcto en un merge?

El padre que representa la rama que quieres conservar como base. Si estabas en main cuando ejecutaste git merge feature, el padre 1 es main y el 2 es feature: para deshacer lo que aportó feature, usa -m 1. Compruébalo siempre con git show --no-patch --pretty=%P <merge> antes de ejecutar.
