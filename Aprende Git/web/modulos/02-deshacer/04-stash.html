stash: trabajo a medias

Módulo 2 · Deshacer 🕐 35 minutos

1 · Introducción

Estás a mitad de una funcionalidad: el fichero no compila, hay tres ficheros tocados y una idea a medio escribir. Suena el aviso: hay que arreglar un bug urgente en main. No quieres commitear código roto, pero tampoco puedes cambiar de rama con el árbol sucio: Git te lo impedirá si los cambios chocan con la otra rama, y arrastrar los cambios a un hotfix es una receta para el desastre.

git stash resuelve exactamente eso: guarda temporalmente los cambios sin commitear, deja el árbol limpio y te permite recuperarlos después. Es una estantería, no una rama ni una copia de seguridad permanente. Entender esa diferencia evita el 90 % de los problemas con el stash.

El stash no es magia: son commits

Por debajo, git stash crea uno o varios commits con el estado del trabajo y del índice, y los cuelga de una referencia especial (refs/stash) que no pertenece a ninguna rama. Por eso no aparece en git log normal, no se publica con push y no lo ve nadie más que tú.

2 · Teoría

Qué guarda y dónde

  RAMA main

    A <-- B <-- C           HEAD -> main
                  \
                   WIP      commit especial del stash (refs/stash)
                  /   \
             index     untracked (solo con -u o -a)

  El WIP no está en main: cuelga de C pero ninguna rama lo alcanza.
  Se ve con `git stash list` y con `git log --all --oneline`.

El stash guarda por defecto:

  • Los cambios en ficheros con seguimiento (modificados o borrados), estén preparados o no.
  • No guarda los ficheros nuevos sin seguimiento salvo que uses -u.
  • No guarda los ficheros ignorados salvo que uses -a.
ComandoQué incluyeCuándo usarlo
git stash push -m "msg"Solo ficheros con seguimientoLo habitual cuando no hay ficheros nuevos
git stash push -u -m "msg"También los no seguidosCasi siempre que estés creando ficheros nuevos
git stash push -a -m "msg"También los ignoradosRaro: binarios, artefactos, configuración local
git stash push -pSolo los trozos que elijasGuardar una parte del trabajo y dejar el resto
git stash push -kGuarda todo pero deja el índice intactoProbar qué pasa con solo lo preparado
Sin -u, los ficheros nuevos se quedan fuera

Y como no están guardados, viajan contigo al cambiar de rama: siguen en el directorio de trabajo y pueden aparecer en el commit equivocado o estorbar en el hotfix. Si has creado ficheros nuevos, usa -u. Es el error número uno con el stash.

Las cuatro operaciones básicas

# 1. Guardar (push es el nombre moderno; `git stash` a secas equivale)
git stash push -u -m "buscador: a medias"

# 2. Ver qué hay guardado
git stash list
# stash@{0}: On main: buscador: a medias

# 3. Aplicar y borrar de la lista si no hay conflicto
git stash pop

# 3b. Aplicar y conservar en la lista
git stash apply

# 4. Borrar una entrada concreta
git stash drop stash@{0}
ComandoAplicaBorra de la listaCuándo
git stash applySíNoQuieres probar en varias ramas o tener una red
git stash popSíSí, si no hay conflictoEl caso normal: recuperar y seguir
git stash dropNoSíYa no lo necesitas
git stash clearNoTodasLimpieza total (irreversible a efectos prácticos)

pop y apply son idénticos en el resultado salvo por el borrado. Por eso, cuando hay conflicto, pop no borra la entrada: si lo hiciera, perderías el trabajo justo cuando más lo necesitas. El conflicto se resuelve y luego se hace drop a mano. 

  TRABAJO SUCIO                    ÁRBOL LIMPIO                OTRA RAMA
  +----------------+  push -m   +----------------+  switch   +----------------+
  | M notas.md     | ---------> | (sin cambios)  | ---------> | hotfix listo   |
  | ?? idea.txt    |            |                |            |                |
  +----------------+            +----------------+            +----------------+
          ^                              |
          |        pop / apply           |
          +------------------------------+

  pop   = aplicar + borrar de la pila (solo si no hay conflicto)
  apply = aplicar y conservar la entrada
  drop  = borrar la entrada sin aplicar

Índices y el flag --index

Al guardar, el stash recuerda qué estaba preparado. Pero al aplicar, por defecto, todo vuelve como cambio sin preparar. Si quieres restaurar también el estado del índice, añade --index: 

git add src/buscador.js
git stash push -m "buscador: logica preparada"

# ...otra rama, otro rato...

git stash pop --index
git status --short
# M  src/buscador.js      <- vuelve a estar preparado, como antes
--index puede fallar

Si los cambios del índice chocan con los del trabajo al reaplicar, Git aborta y te lo dice. En ese caso aplica sin --index y vuelve a preparar a mano lo que corresponda. El stash guarda la información, pero reaplicarla en el mismo orden no siempre es posible si el árbol cambió.

La pila: stash@{0}, stash@{1}…

Los stashes forman una pila: el último guardado es stash@{0}, el anterior stash@{1}, y así sucesivamente. Al hacer drop o pop de una entrada, las demás se renumeran. Por eso, si vas a operar sobre varias, hazlo de arriba abajo o usa primero git stash list para confirmar los índices. 

stash@{0}: On main: buscador: a medias
stash@{1}: On main: configuracion local
stash@{2}: WIP on feature/export: 7c6b5a4 feat: indice

Los mensajes con -m valen su peso en oro cuando tienes más de dos entradas. Sin mensaje, Git usa un texto automático que casi nunca te dice qué había dentro.

Mirar antes de aplicar

# Resumen de ficheros cambiados
git stash show stash@{0}

# Diff completo de lo guardado
git stash show -p stash@{0}

# Comparar el stash con otra rama (sin aplicar)
git diff main stash@{0}

Revisar el diff es especialmente importante cuando el stash tiene días: el código de la rama ha cambiado y lo que parecía inocente puede ser un conflicto garantizado.

Cuando aplicar produce conflicto

git stash pop
# Auto-merging notas.md
# CONFLICT (content): Merge conflict in notas.md
# The stash entry is kept in case you need it again.

git status --short
# UU notas.md

El procedimiento es el mismo que en un merge: editar, quitar marcadores, git add, y comprobar que el resultado compila. No hay git stash --continue: una vez resuelto y preparado, el stash sigue en la lista y lo borras tú: 

# Resolver el fichero...
git add notas.md

# Confirmar que ya no queda nada en conflicto
git diff --check

# El stash ya cumplió: fuera
git stash drop stash@{0}
Si el conflicto se complica: stash branch

git stash branch rescate/buscador stash@{0} crea una rama nueva en el commit donde se creó el stash, la activa y aplica allí los cambios. Así el conflicto se resuelve contra el código original, no contra una rama que ha avanzado. Si la aplicación va bien, el stash se elimina solo.

Stash no es una rama

StashRama
Aparece en git logNo (solo con --all)Sí
Se publicaNuncaCon push
Se comparteNoSí
Pensado paraMinutos u horasDías o semanas
Se puede mergearNo directamenteSí
Riesgo de perderloAlto (un clear y adiós)Bajo (tiene nombre y remoto)

Si algo va a durar más de una jornada, conviértelo en un commit en una rama temporal, aunque sea un wip:. El stash es para interrupciones, no para almacenar trabajo durante semanas.

3 · Ejemplo mínimo

Guardar, comprobar que el árbol queda limpio y recuperar:

mkdir taller-stash && cd taller-stash
git init
printf 'estable\n' > notas.md
git add notas.md && git commit -m "docs: base"
git branch -M main

# Trabajo a medias: modificación + fichero nuevo
printf 'estable\nen obras\n' > notas.md
printf 'idea nueva\n' > idea.txt

git status --short
#  M notas.md
# ?? idea.txt

Si guardamos sin -u, el fichero nuevo se queda fuera:

git stash push -m "notas en obras"
git status --short
# ?? idea.txt          <- sigue aquí
git stash list
# stash@{0}: On main: notas en obras

Lo recuperamos, esta vez guardando también el no seguido:

git stash pop
git stash push -u -m "notas en obras + idea"
git status --short
# (sin salida: árbol limpio)

git stash show -p stash@{0}
# diff de notas.md y de idea.txt

git stash pop
cat notas.md
# estable
# en obras
ls idea.txt
# idea.txt
Por qué el primer intento dejó idea.txt fuera

Porque el stash solo mira lo que Git ya conoce. Un fichero sin seguimiento no está en el índice ni en HEAD, así que no hay nada que guardar. -u le dice que incluya también esos ficheros, creando un commit extra para ellos dentro del stash.

4 · Ejemplo real

Caso 1: la interrupción del hotfix

Estás en feature/busqueda con medio buscador escrito. Llega un bug de producción que hay que arreglar en main. Secuencia completa: 

git status --short
#  M src/buscador.js
#  M tests/buscador.test.js
# ?? docs/busqueda.md

# 1. Guardar todo, incluidos los ficheros nuevos
git stash push -u -m "buscador: filtros a medias"

# 2. Árbol limpio: ahora sí se puede cambiar
git switch main
git switch -c fix/orden-resultados

# 3. Arreglar el bug con commits pequeños
# ...editar, git add, git commit...
git commit -am "fix: orden estable en los resultados"

# 4. Volver y recuperar
git switch feature/busqueda
git stash pop
git status --short
#  M src/buscador.js
#  M tests/buscador.test.js
# ?? docs/busqueda.md

Lo importante es que el hotfix quedó en su rama y el trabajo a medias volvió intacto, sin un commit «wip» en la historia de la feature.

Caso 2: aplicar el mismo stash en dos ramas para comparar

git stash push -m "prueba de enfoque"

git switch main
git stash apply          # probar aquí
# ...ejecutar tests...

git switch feature/buscador
git stash apply --index  # probar aquí, recuperando el índice

# Cuando ya no lo necesites en ninguna:
git stash drop

Con apply el stash sigue disponible hasta que lo borres. Es la forma cómoda de comparar un cambio en dos contextos sin crear ramas temporales. Eso sí: cada aplicación deja los cambios en el árbol; limpia entre una y otra con git restore o git reset --hard si hace falta (mirando antes qué hay).

Caso 3: conflicto al recuperar después de varios días

git stash list
# stash@{0}: On main: buscador: filtros a medias

git stash show -p stash@{0}
# el diff toca src/buscador.js, que ha cambiado mucho desde entonces

git stash pop
# CONFLICT (content): Merge conflict in src/buscador.js
# The stash entry is kept in case you need it again.

git status --short
# UU src/buscador.js

# Resolver a mano, comprobar y preparar
git add src/buscador.js
git diff --check
git stash drop stash@{0}

Cuando el conflicto es grande, la ruta más limpia es la rama de rescate: 

# Abortar la aplicación a medias
git restore --staged --worktree src/buscador.js
git restore src/buscador.js

# Crear una rama en el punto donde nació el stash y aplicarlo allí
git stash branch rescate/buscador stash@{0}
# Switched to a new branch 'rescate/buscador'
# On branch rescate/buscador
# Your changes have been applied and the stash was dropped.

Al crear la rama desde el commit original del stash, el parche encaja contra el código con el que se escribió. Después puedes commitear el rescate y fusionarlo o hacer cherry-pick de lo que sirva.

Caso 4: limpiar la estantería

git stash list
# stash@{0}: On main: experimento de cache
# stash@{1}: On main: configuracion local
# stash@{2}: On main: buscador: a medias

# El de configuración local ya no hace falta
git stash drop stash@{1}

# Revisar el resto antes de borrar
git stash show -p stash@{0}
git stash show -p stash@{1}     # ojo: los índices han cambiado tras el drop
La renumeración muerde

Tras borrar stash@{1}, el antiguo stash@{2} pasa a ser stash@{1}. Si tienes una lista larga, borra siempre desde el final o vuelve a listar antes de cada operación. Y no uses git stash clear como limpieza rutinaria: no hay confirmación y recuperar después requiere bucear en objetos sueltos con git fsck.

6 · Errores habituales

1. Olvidar -u y arrastrar ficheros nuevos

Mal — creer que el stash se lo ha llevado todo 
git stash
git switch main
git status --short
# ?? src/nueva-funcionalidad.js   <- te ha seguido a main
Bien — incluir los no seguidos desde el principio 
git stash push -u -m "nueva funcionalidad: a medias"
git switch main
git status --short
# (limpio)

2. Hacer pop con conflicto y luego clear

Mal — destruir la red de seguridad en pleno conflicto 
git stash pop
# CONFLICT en notas.md
git stash clear     # ¿y si la resolución sale mal? Ya no hay vuelta
Bien — resolver, comprobar y borrar solo esa entrada 
git stash pop
# CONFLICT en notas.md
# ...resolver...
git add notas.md
git diff --check
git stash drop stash@{0}

3. Esperar que el índice se restaure solo

Mal — asumir que pop recuerda qué estaba preparado 
git stash pop
git status --short
#  M src/buscador.js   <- todo sin preparar, aunque antes había un add
Bien — pedirlo explícitamente con --index 
git stash pop --index
git status --short
# M  src/buscador.js   <- preparado, como antes de guardar

4. Aplicar el stash en la rama equivocada

Mal — cambiar de rama sin comprobar dónde estás 
git stash pop
# Los cambios del buscador caen en main y se mezclan con el hotfix
Bien — verificar rama y contenido antes 
git status -sb
## feature/busqueda
git stash show -p stash@{0}
git stash pop

5. Usar el stash como copia de seguridad permanente

Mal — un stash de hace un mes como único sitio del trabajo 
git stash list
# stash@{0}: WIP on main: 3f2a1b0 (hace 5 semanas)
# Nadie lo ve, no está en el remoto, y un `git gc` agresivo o un clear lo borra.
Bien — una rama con nombre y commits de verdad 
git stash branch wip/buscador stash@{0}
git add -A
git commit -m "wip: buscador a medias"
# Ahora tiene nombre, historia y se puede publicar si hace falta.

7 · Ejercicio guiado

Vas a simular una interrupción real: trabajo a medias con un fichero nuevo, un hotfix en otra rama y la recuperación posterior con el índice intacto.

  1. Prepara el escenario en main: un commit base y una rama feature.
  2. Ensuciar feature: modifica un fichero con seguimiento, crea uno nuevo y prepara solo el primero.
  3. Guarda con -u y comprueba que el árbol queda limpio (incluido el fichero nuevo).
  4. Haz el hotfix en main con un commit propio.
  5. Vuelve a feature y recupera con pop --index; comprueba que el fichero nuevo vuelve y que el preparado sigue preparado.
  6. Borra la entrada y confirma que la lista queda vacía.

Solución resuelta:

mkdir ejercicio-stash && cd ejercicio-stash
git init
printf 'base\n' > notas.md
git add notas.md && git commit -m "docs: base"
git branch -M main

git switch -c feature/busqueda
printf 'base\nbuscador\n' > notas.md
printf 'borrador de diseno\n' > diseno.txt
git add notas.md          # solo el primero queda preparado

git status --short
# M  notas.md
# ?? diseno.txt

# 3. Guardar incluyendo el no seguido
git stash push -u -m "buscador: logica y diseno"
git status --short
# (limpio)
git stash list
# stash@{0}: On feature/busqueda: buscador: logica y diseno

# 4. Hotfix en main
git switch main
printf 'base\n' > notas.md
printf 'hotfix\n' > hotfix.txt
git add hotfix.txt
git commit -m "fix: corrige el arranque"
git log --oneline
# 7a7a7a7 fix: corrige el arranque
# 1b1b1b1 docs: base

# 5. Recuperar en feature
git switch feature/busqueda
git stash pop --index
git status --short
# M  notas.md        <- vuelve preparado
# ?? diseno.txt      <- vuelve el fichero nuevo

# 6. Limpiar
git stash list
# (vacía: pop la borró al no haber conflicto)
Compara con apply

Repite el ejercicio usando git stash apply --index en el paso 5: verás que la entrada sigue en la lista. Esa es la diferencia práctica entre apply y pop, y la razón para preferir apply cuando el stash contiene algo difícil de reconstruir.

8 · Reto

La estantería con cinco botes

Crea un repositorio y genera cinco stashes con propósitos distintos: uno solo con cambios preparados, uno con ficheros nuevos, uno con ficheros ignorados, uno parcial (solo ciertos trozos de un fichero) y uno que provoque conflicto al aplicarse. Después:

  1. Distingue cada entrada por su mensaje y documenta qué contiene cada una.
  2. Recupera el stash de los ficheros nuevos en una rama distinta de donde lo creaste, sin que se mezcle con el trabajo actual.
  3. Resuelve el conflicto del último stash conservando la parte nueva y descartando la vieja, y deja la lista con exactamente dos entradas.
  4. Convierte uno de los stashes en una rama con nombre, con commits que expliquen el trabajo.

Entrega la salida de git stash list antes y después, los diffs que justifican cada decisión y una explicación de por qué pop no borra cuando hay conflicto.

Pista: para el stash parcial, git stash push -p pregunta trozo a trozo; para el de ignorados necesitas un .gitignore con una entrada real y -a. Para provocar el conflicto, cambia después las mismas líneas que guardaste y aplica. Y recuerda que los índices de la pila se renumeran al borrar: vuelve a listar antes de cada paso.

9 · Resumen

  • git stash push -m "mensaje" guarda el trabajo con seguimiento y deja el árbol limpio.
  • -u incluye ficheros nuevos; -a incluye también los ignorados; sin ellos, se quedan fuera y viajan contigo.
  • git stash list muestra la pila; stash@{0} es el más reciente y los índices se renumeran al borrar.
  • pop aplica y borra (si no hay conflicto); apply aplica y conserva; drop borra una entrada.
  • Al aplicar, todo vuelve sin preparar salvo que uses --index.
  • Un conflicto deja el stash en la lista: se resuelve, se hace add y se borra a mano.
  • El stash es local y temporal: para algo duradero, una rama con commits.

10 · Preguntas frecuentes

¿El stash se sube al remoto?

No. refs/stash es una referencia local que git push no publica. Si necesitas compartir trabajo a medias (para una revisión temprana o para moverlo de máquina), haz un commit en una rama wip/… y súbela. Un stash no se puede recuperar desde otro clon.

¿Puedo aplicar un stash en una rama distinta de donde lo creé?

Sí, y es una práctica habitual: el stash es un parche que se aplica contra el árbol actual. Si el código base es distinto, puede haber conflictos; si es muy distinto, git stash branch te da un punto de partida más fiable. Revisa siempre el diff antes de aplicar.

¿Qué diferencia hay entre pop y apply si al final borro igual?

La red de seguridad. pop borra la entrada en cuanto el parche se aplica sin conflicto, antes de que hayas comprobado que el resultado es correcto. apply deja la entrada hasta que tú ejecutes drop. Para cambios valiosos, apply es la opción conservadora.

¿Puedo recuperar un stash que he borrado con clear?

A veces, pero no es un procedimiento fiable. Los commits del stash pueden seguir en la base de objetos como inalcanzables hasta que se ejecute una recolección de basura; se pueden localizar con git fsck --unreachable y revisar con git show. Si el gc ya pasó, no hay nada que hacer. Es la razón por la que clear no debe ser una rutina.

¿El stash guarda los cambios de ficheros ignorados?

Solo con -a (o --all). Por defecto se ignoran, igual que los no seguidos. Ten en cuenta que incluir ignorados puede meter binarios grandes o configuración local que no quieres ni en el stash; úsalo cuando sepas exactamente qué hay en esa categoría.
