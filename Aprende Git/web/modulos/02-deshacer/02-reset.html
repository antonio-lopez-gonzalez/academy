reset: mover HEAD

Módulo 2 · Deshacer 🕐 35 minutos

1 · Introducción

«Quiero deshacer el último commit». Esa frase tiene al menos tres respuestas correctas y una catastrófica, y todas empiezan por git reset. La diferencia está en cuánto quieres deshacer: solo el puntero, también el índice, o también el contenido de tus ficheros.

reset es el único comando de este módulo que mueve la rama. Cuando ejecutas git reset <commit> en main, el puntero de main retrocede a ese commit y HEAD, que es simbólico y apunta a main, se mueve con ella. Los commits que quedaban por delante dejan de ser alcanzables desde la rama. No se borran en ese instante, pero desaparecen de la vista.

La pregunta que decide el modo

Antes de escribir el comando, pregúntate: ¿quiero conservar lo que estaba en el índice? ¿Y lo que estaba en el directorio de trabajo? Si la respuesta es «todo», --soft. Si es «lo del trabajo sí, lo del índice no», --mixed. Si es «nada», --hard. Ese es todo el secreto.

Y una advertencia que repetiremos hasta el final: reset reescribe la historia. Es perfecto en commits que solo existen en tu máquina y es un problema en commits que otro ya tiene. Para lo publicado hay una herramienta distinta, git revert, que verás en la lección siguiente.

2 · Teoría

Qué mueve reset, exactamente

Partimos de una rama con cuatro commits. Queremos volver a C desde D: 

  ANTES

                 main
                  |
                  v
    A <-- B <-- C <-- D        HEAD -> main
                  ^
                  |
             objetivo: C

--soft Sí, a C Sin tocar (sigue como D) Sin tocar Todo, y además preparado
--mixed (por defecto) Sí, a C Se resetea a C Sin tocar Todo, pero sin preparar
--hard Sí, a C Se resetea a C Se resetea a C Nada de lo que había en D 
  DESPUÉS DE --soft              DESPUÉS DE --mixed             DESPUÉS DE --hard

        main                           main                           main
         |                              |                              |
         v                              v                              v
    A <-- B <-- C                  A <-- B <-- C                  A <-- B <-- C
                \                              \                              \
                 D (sin rama)                   D (sin rama)                   D (sin rama)

    índice = D                     índice = C                     índice = C
    trabajo = D                    trabajo = D                    trabajo = C
Los commits no se borran: se quedan sin nombre

Tras el reset, D sigue en la base de objetos y el reflog de la rama registra el salto. Durante un tiempo (por defecto 90 días para lo alcanzable desde reflogs) puedes volver con git reset --hard HEAD@{1} o crear una rama con git switch -c rescate HEAD@{1}. La basura se recoge con git gc, no en el momento del reset. Aun así, no lo trates como una copia de seguridad: trátalo como una red que existe y que no deberías necesitar.

--soft: deshacer el commit, conservar el trabajo preparado

Mueve el puntero y nada más. El índice se queda tal cual estaba, así que todo lo que contenía el commit D aparece ahora como preparado para el próximo commit. Es el modo de «me equivoqué en el mensaje», «quiero juntar estos dos commits» o «quiero rehacer este commit en dos trozos». 

# Deshacer el último commit y dejar sus cambios preparados
git reset --soft HEAD~1
git status --short
# M  notas.md        -> sigue en el índice, listo para recomitear

Ojo con una consecuencia: si el commit era el primero de la rama, HEAD~1 no existe. En ese caso se usa git update-ref -d HEAD, que borra la referencia de la rama sin tocar índice ni trabajo; pero es un caso raro y conviene preguntarse si de verdad quieres un repositorio sin commits.

--mixed: deshacer el commit y despreparar

Es el modo por defecto, el de git reset a secas. Mueve la rama y resetea el índice al commit destino, pero deja el directorio de trabajo intacto. El resultado es que los cambios de D siguen en los ficheros, pero aparecen como «no preparados». Es el comando para deshacer un git add masivo sin perder nada: 

# Vaciar el índice: todo vuelve a estar sin preparar, nada se pierde
git reset

# Equivalente explícito, por si quieres que se lea la intención
git reset --mixed HEAD
El equivalente moderno

Para deshacer un add ruta a ruta, git restore --staged <ruta> es más preciso y no toca la historia. Usa git reset sin commit cuando quieras vaciar el índice entero de golpe; usa git restore --staged cuando sepas qué ficheros sobran.

--hard: mover todo, incluido el disco

Mueve la rama, resetea el índice y además sobrescribe los ficheros con seguimiento para que coincidan con el commit destino. Todo lo que hubiera en el trabajo y no estuviera commiteado se pierde: modificaciones, cambios preparados y también los ficheros nuevos que ya estuvieran en el índice. Los ficheros sin seguimiento, en cambio, sobreviven (Git no los conoce, no los toca). 

# Volver el árbol entero al último commit: descarta TODO lo no commiteado
git reset --hard HEAD

# Retroceder tres commits y descartar lo que hubiera en el camino
git reset --hard HEAD~3
Por qué --hard puede perder cambios

Porque el contenido del directorio de trabajo que nunca pasó por el índice no existe como objeto de Git. El reflog puede devolverte un commit, pero no puede devolverte una línea que escribiste y no preparaste. --hard es el único modo de reset que destruye trabajo no versionado. Si hay algo a medias, git stash push -m "antes del reset" o una rama de respaldo.

Una alternativa más segura: --keep

git reset --keep <commit> mueve la rama y actualiza índice y trabajo, pero se niega a hacerlo si algún cambio local sin commitear se pisaría. Es el punto intermedio entre --mixed y --hard: conserva tus cambios y aborta en vez de destruirlos. 

git reset --keep HEAD~2
# error: Your local changes to the following files would be overwritten by reset:
#         notas.md
# Si aparece ese error, no has perdido nada: decide qué hacer con esos cambios.

Antes de un reset: dos redes de seguridad

  1. Una rama de respaldo. git branch backup/antes-del-reset crea un puntero al commit actual sin cambiar de rama. Si el reset sale mal, la rama sigue ahí.
  2. ORIG_HEAD. Los comandos que mueven la punta de la rama dejan ahí la posición anterior. git reset --hard ORIG_HEAD deshace el reset inmediatamente anterior. 
git branch backup/antes-del-reset
git reset --hard HEAD~3
# ...comprobar que todo está bien...
git branch -D backup/antes-del-reset   # cuando ya no lo necesites

Reset y lo publicado

reset cambia hashes: los commits nuevos no serán los mismos que los antiguos. Si esos commits ya están en un remoto que otros usan, tu rama y la suya divergen, y la única forma de subir el reset sería reescribir la rama remota. Eso obliga a los demás a reconciliar su trabajo a mano.

SituaciónHerramientaMotivo
Commit local, nadie lo tiene git reset Reescribir es seguro: solo te afecta a ti
Commit ya publicado en una rama compartida git revert Añade historia en vez de reescribirla; nadie tiene que hacer nada
Commit publicado en tu rama de feature, sin que nadie más la use reset + push --force-with-lease Es tuya; aun así, el --force-with-lease evita pisar trabajo ajeno
main compartida revert, nunca reset --hard Reescribir la rama principal rompe a todo el equipo y a la integración continua
Nunca fuerces el push

En este curso no enseñamos el push forzado. Si de verdad necesitas actualizar una rama propia que ya publicaste, la forma segura es --force-with-lease, que aborta si alguien subió algo que tú no has visto. Y sobre main, la respuesta es siempre revert.

3 · Ejemplo mínimo

Tres commits, un reset de cada tipo y la salida que debes esperar.

mkdir taller-reset && cd taller-reset
git init
printf 'linea 1\n' > notas.md
git add notas.md && git commit -m "docs: linea 1"
printf 'linea 1\nlinea 2\n' > notas.md
git commit -am "docs: linea 2"
printf 'linea 1\nlinea 2\nlinea 3\n' > notas.md
git commit -am "docs: linea 3"

git log --oneline
# c3c3c3c docs: linea 3
# b2b2b2b docs: linea 2
# a1a1a1a docs: linea 1

Con --soft: el commit desaparece, su contenido queda preparado.

git reset --soft HEAD~1
git status --short

M  notas.md

git log --oneline
# b2b2b2b docs: linea 2
# a1a1a1a docs: linea 1
git diff --staged
# muestra la linea 3: está en el índice

Con --mixed (el modo por defecto): el contenido sigue en el fichero, pero sin preparar.

git reset HEAD~1
git status --short

 M notas.md

cat notas.md
# linea 1
# linea 2
# linea 3
# (las tres lineas siguen en el fichero: mixed no toca el trabajo)

Con --hard: el fichero vuelve al contenido del commit destino.

git reset --hard HEAD
git status --short
# (sin salida: árbol limpio)
cat notas.md
# linea 1
Observa el patrón

Los tres comandos han movido la rama al mismo sitio. Lo único que ha cambiado es cuánto han «arrastrado» hacia el índice y hacia el disco. Si entiendes eso, ya no necesitas memorizar los flags: puedes deducirlos.

4 · Ejemplo real

Caso 1: dos commits que debían ser uno (aún locales)

Has hecho dos commits seguidos para arreglar el mismo fichero y quieres dejar uno solo antes de publicarlo. No hay remoto todavía, así que reescribir es seguro. 

git log --oneline -3
# 7c1f0aa test: arregla el test que faltaba
# 42b9d31 feat: anade busqueda por titulo
# 18e0c40 docs: arranca la busqueda

git reset --soft HEAD~1
git status --short
# M  buscador.js        <- el segundo commit, ahora preparado

git commit -m "feat: busqueda por titulo con test"
git log --oneline -2
# 9d4e2f1 feat: busqueda por titulo con test
# 42b9d31 feat: anade busqueda por titulo

Alternativa equivalente y a veces más clara: git commit --amend (lo viste en el módulo 1) cuando solo quieres retocar el último commit. --soft brilla cuando quieres fusionar varios o reordenar contenido.

Caso 2: el commit accidental de un fichero de configuración

git log --oneline -1
# 3e8a111 chore: anade debug local

git show --stat HEAD
#  configuracion.local.json | 12 ++++++++++++
#  notas.md                 |  1 +

# Todavía no lo has subido:
git reset --mixed HEAD~1
git status --short
#  M configuracion.local.json
#  M notas.md

# Ahora dejas fuera el fichero local y commiteas solo la nota
printf 'configuracion.local.json\n' >> .gitignore
git add .gitignore notas.md
git commit -m "docs: cierra la nota de la semana"

Fíjate en el detalle: el commit accidental ya está deshecho, pero el contenido de configuracion.local.json sigue en el disco, sin seguimiento. Eso es exactamente lo que quieres: la configuración es tuya, no del repositorio. Si además quieres sacarla del índice sin tocar el resto, git restore --staged configuracion.local.json habría sido más quirúrgico que el reset completo.

Caso 3: descartar un experimento con --hard, con red de seguridad

git status --short
#  M buscador.js
#  M notas.md
# ?? pruebas/

# Antes de destruir, una foto:
git stash push -u -m "experimento busqueda antes de reset"

git reset --hard HEAD~2
git log --oneline -3
# 42b9d31 feat: anade busqueda por titulo
# 18e0c40 docs: arranca la busqueda

# El experimento sigue disponible si cambias de idea:
git stash list
# stash@{0}: On main: experimento busqueda antes de reset
Un stash antes de un --hard cuesta dos segundos

No es obligatorio, pero convierte una operación irreversible en una reversible. Si el reset era correcto, git stash drop; si no, git stash pop. Es la diferencia entre «he perdido la tarde» y «he perdido dos segundos».

Caso 4: el commit ya está en el remoto

El mismo commit accidental, pero ya lo subiste y un compañero ha hecho fetch. Aquí reset es la respuesta equivocada: cambiaría el hash y obligaría a todos a reparar su rama. En su lugar se añade un commit que deshace el anterior: 

git revert 3e8a111
# [main 8b7c9d2] Revert "chore: anade debug local"

La historia crece en vez de encogerse, y eso es una virtud: todo el mundo puede hacer git pull sin conflictos artificiales. Lo desarrollamos en la lección 3.

6 · Errores habituales

1. --hard con trabajo sin commitear

Mal — usar hard como «limpiar el árbol» sin mirar 
git reset --hard HEAD
# Adiós a las modificaciones sin preparar y a lo preparado.
# Los ficheros nuevos sin seguimiento siguen ahí, pero lo demás no.
Bien — guardar primero, o usar un modo que no destruye 
git status --short
git stash push -u -m "trabajo antes de limpiar"
git reset --hard HEAD
# Si algo faltaba: git stash pop

«Limpiar el árbol» no es lo mismo que «volver a un commit». Para quitar cambios del trabajo sin mover la historia, valora git restore ruta a ruta; para guardarlos, stash.

2. Resetear una rama publicada y forzar el push

Mal — reescribir main compartida 
git reset --hard HEAD~1
# ...y forzar el push para reescribir la rama remota
# Los demás tienen hashes que ya no existen; sus pull rotos;
# la integración continua puede perder commits intermedios.
Bien — revertir y publicar la vuelta atrás 
git revert HEAD
git push
# Historia hacia delante, sin reescritura y sin romper a nadie.

3. Creer que --mixed borra los ficheros

Mal — reset y esperar que el código desaparezca 
git reset --mixed HEAD~1
cat notas.md
# El contenido sigue ahí: mixed solo resetea el índice.
Bien — elegir el modo por su efecto real 
# Quiero conservar el contenido sin preparar:
git reset --mixed HEAD~1

# Quiero que el fichero vuelva al commit:
git reset --hard HEAD~1

4. Resetear desde una rama equivocada

Mal — asumir en qué rama estás 
git reset --hard HEAD~3
# ...y resulta que estabas en feature/busqueda, no en main
Bien — comprobar el contexto primero 
git status -sb
## main...origin/main
git log --oneline -4
git reset --hard HEAD~3

git status -sb muestra la rama y el estado respecto al remoto en una sola línea. Es el chequeo más barato que existe antes de cualquier operación destructiva.

5. Confundir git reset <archivo> con git reset <commit>

Mal — mezclar las dos formas 
git reset notas.md       # no mueve HEAD: solo saca la ruta del índice
git reset HEAD~1         # mueve la rama: historia reescrita
Bien — separar las intenciones 
git restore --staged notas.md   # índice, sin tocar historia
git reset --soft HEAD~1         # historia, con intención explícita

La forma con pathspec es herencia de los primeros Git y sigue funcionando, pero hoy se expresa mejor con restore --staged. Si el comando lleva una ruta, no esperes que mueva HEAD.

7 · Ejercicio guiado

Vas a vivir los tres modos en un mismo repositorio y a comprobar, con tus propios ojos, qué se conserva en cada uno.

  1. Crea tres commits sobre notas.md con una línea nueva en cada uno.
  2. Deshaz el último con --soft y comprueba con git diff --staged que la línea sigue preparada.
  3. Rehaz el commit y deshazlo con --mixed. Comprueba que el fichero conserva la línea pero git diff --staged está vacío.
  4. Prepara el cambio y deshaz con --hard. Comprueba que la línea desaparece del fichero.
  5. Recupera el commit perdido con el reflog y decide si lo quieres de vuelta.

Solución resuelta:

mkdir ejercicio-reset && cd ejercicio-reset
git init

printf 'uno\n' > notas.md
git add notas.md && git commit -m "docs: uno"
printf 'uno\ndos\n' > notas.md
git commit -am "docs: dos"
printf 'uno\ndos\ntres\n' > notas.md
git commit -am "docs: tres"

# 2. --soft
git reset --soft HEAD~1
git status --short
# M  notas.md
git diff --staged
# +tres   (sigue en el índice)

# 3. Rehacer y --mixed
git commit -m "docs: tres"
git reset --mixed HEAD~1
git status --short
#  M notas.md
git diff --staged
# (vacío)
cat notas.md
# uno
# dos
# tres

# 4. --hard
git add notas.md
git reset --hard HEAD
cat notas.md
# uno
# dos

# 5. Reflog
git reflog
# 3f2a1b0 HEAD@{0}: reset: moving to HEAD
# 9c8d7e6 HEAD@{1}: commit: docs: tres
# ...

git reset --hard 9c8d7e6
# o bien: git reset --hard HEAD@{1}
cat notas.md
# uno
# dos
# tres
Lección del paso 5

El --hard no borró el commit: solo dejó de estar señalado por la rama. El reflog conserva el movimiento y puedes volver. Lo que no habría vuelto es una modificación del trabajo que nunca hubieras preparado.

8 · Reto

El commit que no debía existir

Monta un repositorio con esta historia y sin usar git revert: 

A  docs: arranca el taller
B  feat: anade busqueda
C  wip: prueba que no funciona
D  chore: sube configuracion.local.json
E  fix: arregla el test de busqueda

Quieres publicar una historia con solo tres commits: A, un commit que una B y E con un mensaje limpio, y nada de C ni D. Los cambios de B y E deben conservarse; los de C y D no deben aparecer. Además, configuracion.local.json debe quedar en el disco pero ignorado por Git.

Documenta cada paso con git status --short y git log --oneline --graph, y explica en un párrafo por qué has elegido --soft, --mixed o --hard en cada uno. No resuelvas el reto con un único comando mágico: el objetivo es justificar las decisiones.

Pista: no hace falta tocar la historia de golpe. Una rama de respaldo antes de empezar te permite comparar el antes y el después, y el reflog te sirve para comprobar que C y D siguen recuperables. Piensa qué modo de reset conserva los cambios de dos commits que no son consecutivos.

9 · Resumen

  • reset mueve la rama (y con ella HEAD); no es un comando para descartar un solo fichero.
  • --soft: mueve el puntero y deja índice y trabajo como estaban; lo del commit queda preparado.
  • --mixed (por defecto): mueve el puntero y resetea el índice; el trabajo se conserva sin preparar.
  • --hard: mueve el puntero, resetea índice y sobrescribe el trabajo; puede perder cambios no commiteados.
  • --keep es la alternativa conservadora: aborta si pisaría cambios locales.
  • Los commits «perdidos» siguen en el reflog durante un tiempo: git reset --hard HEAD@{1} deshace el reset.
  • Reescribir solo es seguro en commits no publicados; en lo compartido, revert.

10 · Preguntas frecuentes

¿reset --hard borra los ficheros sin seguimiento?

No. Git solo sobrescribe los ficheros que conoce (los que están en el índice o en el commit destino). Un fichero nuevo que nunca se añadió no se toca: sigue en el disco, marcado como ??. Para borrarlo hay que usar git clean, que es otra operación destructiva y conviene simular antes con git clean -n.

Si hago reset --hard, ¿puedo recuperar lo que había?

Depende de dónde estuviera. Los commits a los que apuntaba la rama se recuperan con git reflog y git reset --hard <hash>. Lo que estaba preparado en el índice probablemente también (el blob existe), aunque localizarlo requiere git fsck. Lo que solo estaba en el directorio de trabajo y nunca se preparó no se puede recuperar: Git no lo conoce.

¿Cuál es la diferencia entre git reset --hard HEAD y git restore .?

git restore . copia el índice al trabajo: no mueve la rama ni el índice, y conserva lo que estuviera preparado. git reset --hard HEAD pone índice y trabajo a la altura de HEAD: descarta también lo preparado. Si solo quieres limpiar el trabajo, restore es más preciso; si quieres un árbol idéntico al último commit, reset --hard.

¿Puedo hacer reset --soft y luego publicar sin problemas?

Sí, siempre que nadie haya basado trabajo en los commits que has eliminado. Al hacer soft y volver a commitear, el hash cambia; si la rama ya estaba publicada, tu rama local y la remota divergen. En una rama propia y no compartida se resuelve con push --force-with-lease; en main, con revert.

¿Qué es ORIG_HEAD y cuándo se actualiza?

Es una referencia que Git escribe antes de operaciones que mueven la punta de la rama: reset, merge, rebase, pull. Guarda el commit donde estabas, así que git reset --hard ORIG_HEAD deshace la última de esas operaciones. Es cómodo para un arrepentimiento inmediato; para algo más antiguo, el reflog es la herramienta.
