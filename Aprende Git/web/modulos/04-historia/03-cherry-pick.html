Cherry-pick: traer un commit concreto

Módulo 4 · Historia 🕐 35 minutos

1 · Introducción

A veces no quieres una rama entera: quieres un commit. El caso clásico es el hotfix. Descubres en main un fallo de seguridad, lo arreglas, y ese arreglo también tiene que estar en la versión release/1.4 que sigue en producción. No quieres fusionar main con la release —arrastraría tres semanas de funcionalidades sin probar— ni rebasar la release —reescribiría una rama publicada—. Quieres ese parche y solo ese.

Para eso existe git cherry-pick: toma el cambio que introduce un commit y lo aplica sobre tu HEAD actual, creando un commit nuevo con el mismo contenido. Es un trasplante, no una fusión.

¿Por qué existe esta lección?

Porque cherry-pick es tentador y tiene un precio que casi nadie explica: duplica commits. Ese precio no se paga hoy; se paga el día que las dos ramas se vuelven a encontrar y Git ve el mismo cambio dos veces. Entender cuándo el atajo es legítimo —y cuándo estás creando una deuda— es la diferencia entre resolver un incendio y provocar otro.

2 · Teoría

Qué copia exactamente

Un commit no es un diff: es una foto del árbol con un padre. Pero para trasplantarlo, Git calcula la diferencia entre ese commit y su padre (el parche) y la aplica sobre tu HEAD. El resultado es un commit nuevo, con tu identidad de committer, tu fecha y un padre distinto. El autor original se conserva.

ANTES

    A───B───C───D   main
             \
              E───F   feature      (E = el arreglo que quieres)

    git switch main
    git cherry-pick E

DESPUÉS

    A───B───C───D───E'   main
             \
              E───F      feature

    E' contiene el mismo cambio que E, pero:
      - su padre es D, no C
      - su hash es distinto
      - el committer eres tú, ahora
Qué puntero mueve

cherry-pick mueve la rama actual (y HEAD) un commit hacia delante, como un commit normal. No toca la rama de origen: feature sigue exactamente donde estaba. No hay HEAD detached ni cambio de base; es una aplicación de parche con commit.

Uno, varios o un rango

FormaQué aplicaEjemplo
Un commitSolo esegit cherry-pick 4f2a1c9
VariosEn el orden indicadogit cherry-pick 4f2a1c9 8b3d2e1
Rango A..BLos commits después de A hasta B (incluido)git cherry-pick 1a2b3c4..9d8e7f6
Rango A^..BIncluye también Agit cherry-pick 1a2b3c4^..9d8e7f6

Con procedenciaAñade «(cherry picked from commit …)» al mensajegit cherry-pick -x 4f2a1c9

El rango sigue la misma convención que git log: A..B significa «lo que está en B y no en A», así que A queda fuera. Si quieres incluirlo, usa A^..B.

Usa -x para los backports

En una rama de release, dentro de seis meses alguien preguntará «¿este arreglo vino de main?». -x graba el hash original en el mensaje. Es la diferencia entre poder auditar un backport y tener que adivinarlo con git log -S. En ramas de trabajo normales no hace falta; en mantenimiento, es casi obligatorio.

Conflictos

El parche se aplica sobre un contexto distinto, así que puede chocar. El flujo es idéntico al del rebase, con otro nombre en el estado:

git cherry-pick 4f2a1c9
Auto-merging src/version.js
CONFLICT (content): Merge conflict in src/version.js
error: could not apply 4f2a1c9... fix(version): corregir comparación
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git cherry-pick --continue".
hint: To abort and get back to the state before the cherry-pick,
hint: run "git cherry-pick --abort".
  • git cherry-pick --continue: tras editar y git add, crea el commit.
  • git cherry-pick --abort: vuelve al estado anterior a toda la secuencia, no solo al último commit.
  • git cherry-pick --skip: descarta ese commit y sigue con el siguiente del rango.

Igual que en rebase, no hagas git commit a mitad: el secuenciador lleva la cuenta y un commit manual lo descuadra.

El coste: commits duplicados

Git identifica un commit por su hash. Dos commits con el mismo cambio pero distinto padre son commits distintos. Eso significa que, para Git, el cambio está dos veces. Las consecuencias:

  • El merge posterior es más ruidoso. Cuando release/1.4 se fusione de vuelta en main, Git intentará aplicar otra vez el parche que ya está. Si el contexto cambió, conflicto; si no, un commit redundante.
  • El historial miente un poco. Dos entradas para un solo arreglo; git blame puede señalar la copia en lugar del original.
  • Revertir es peligroso. Un git revert de la copia no revierte el original; hay que deshacer los dos.
  • Los rangos se complican. git log main..release muestra commits que «no están» en main aunque su contenido sí esté.

Git ofrece herramientas para detectar duplicados por contenido (no por hash):

git cherry -v main release/1.4
git log --cherry-mark --left-right --oneline main...release/1.4
- 4f2a1c9 fix(version): corregir comparación
+ 9c1d7e2 chore(release): subir versión a 1.4.3

< 4f2a1c9 fix(version): corregir comparación
> = 4f2a1c9 fix(version): corregir comparación

git cherry marca con - los commits cuya huella (patch-id) ya existe en la otra rama y con + los que no. --cherry-mark usa = para los equivalentes. Es la forma de saber si un backport ya se hizo.

Analogía: fotocopiar una página

Fusionar es encuadernar dos cuadernos en uno; rebasar es reescribir un cuaderno con las hojas en otro orden. cherry-pick es fotocopiar una página de un cuaderno y pegarla en otro. La página es la misma, pero ahora existe dos veces. Mientras los cuadernos estén separados, nadie nota nada. El día que los encuadernes juntos, tendrás que decidir cuál de las dos copias vale.

Cuándo tiene sentido (y cuándo no)

Situación¿Cherry-pick?Alternativa
Backport de un hotfix a release/*Sí, con -x—
Copiar un arreglo a otra rama de larga vidaSí, y anotarlo—
Integrar una feature completaNomerge o rebase
Poner tu rama al día con mainNorebase
Recuperar un commit de una rama borradaPosiblereflog + switch -c (mejor: conserva el original)
Evitar un merge complicado copiando commits sueltosNoResolver el merge una vez; el cherry-pick crea más deuda
Cherry-pick no sustituye a una estrategia de ramas

Si te encuentras haciendo cherry-pick de diez commits cada semana entre las mismas dos ramas, el problema no es el comando: es que las ramas divergen demasiado. Tarde o temprano habrá que fusionarlas y los duplicados saldrán a la luz. Usa cherry-pick para excepciones puntuales, no como transporte habitual.

3 · Ejemplo mínimo

En taller, un arreglo entra en main y hay que llevarlo a la release:

git switch main
git log --oneline -1
4f2a1c9 (HEAD -> main) fix(busqueda): escapar acentos en el filtro
        
git switch release/1.4
git cherry-pick -x 4f2a1c9
[release/1.4 9b7e2d4] fix(busqueda): escapar acentos en el filtro
 Date: Mon Oct 12 10:14:03 2026 +0200
 1 file changed, 6 insertions(+), 2 deletions(-)
        
git log --oneline -1
git show --stat --oneline HEAD
9b7e2d4 (HEAD -> release/1.4) fix(busqueda): escapar acentos en el filtro

9b7e2d4 fix(busqueda): escapar acentos en el filtro

    (cherry picked from commit 4f2a1c9)

 src/busqueda.js | 8 ++++++--
 1 file changed, 6 insertions(+), 2 deletions(-)

El cambio está en la release, pero el commit es 9b7e2d4, no 4f2a1c9. main no se ha movido y la rama de origen tampoco.

El autor no eres tú (y está bien)

El campo author se conserva: el commit sigue atribuido a quien escribió el arreglo. Lo que cambia es el committer, que eres tú, y la fecha de commit. Por eso dos commits con el mismo cambio pueden tener autores iguales y hashes distintos: el padre y el committer no coinciden.

4 · Ejemplo real

Escenario: un fallo de seguridad en el parser de consultas se corrige en main con un commit que toca dos ficheros: src/parser.js y src/version.js. Hay que llevarlo a release/1.4, que lleva tres semanas congelada y tiene una versión distinta en version.js.

git fetch origin
git log --oneline origin/main -5
git switch release/1.4
git cherry-pick -x origin/main~2
Auto-merging src/version.js
CONFLICT (content): Merge conflict in src/version.js
error: could not apply 4f2a1c9... fix(parser): rechazar operadores anidados
hint: after resolving the conflicts, mark the corrected paths
hint: with 'git add <paths>' or 'git rm <paths>'
hint: and commit the result with 'git cherry-pick --continue'

El conflicto no está en el arreglo, sino en el fichero de versión: main dice 1.5.0-dev y la release dice 1.4.3. La resolución correcta es conservar la versión de la release y quedarse con el cambio del parser, que se aplicó limpio:

<<<<<<< HEAD
const VERSION = '1.4.3';
=======
const VERSION = '1.5.0-dev';
>>>>>>> 4f2a1c9 (fix(parser): rechazar operadores anidados)
        
git add src/version.js
git cherry-pick --continue
[release/1.4 2c8f1a0] fix(parser): rechazar operadores anidados
 Date: Tue Oct 13 09:02:41 2026 +0200
 2 files changed, 18 insertions(+), 3 deletions(-)

Compruebas que el contenido del arreglo es el esperado y que el mensaje lleva la procedencia:

git show --stat HEAD
git log --oneline -1 --format="%h %s%n%b"
2c8f1a0 fix(parser): rechazar operadores anidados
 src/parser.js  | 15 ++++++++++++---
 src/version.js |  6 +++---
 2 files changed, 18 insertions(+), 3 deletions(-)

2c8f1a0 fix(parser): rechazar operadores anidados
(cherry picked from commit 4f2a1c9d3e8b7a6f5c4d3e2f1a0b9c8d7e6f5a4b)

Ahora la deuda. Semanas después, la release se fusiona de vuelta en main. Git compara historias y ve dos commits distintos con el mismo parche. La auditoría lo detecta:

git switch main
git cherry -v main release/1.4
- 4f2a1c9 fix(parser): rechazar operadores anidados
- 2c8f1a0 fix(parser): rechazar operadores anidados
+ 9c1d7e2 chore(release): subir versión a 1.4.3

El - confirma que el parche de la release ya está en main. En el merge, Git probablemente resolverá sin conflicto (el contenido es idéntico), pero quedará un commit redundante y un revert futuro tendrá que ocuparse de las dos copias. Ese es el precio real del backport: no el comando, sino la contabilidad posterior.

La decisión correcta era cherry-pick

Aun con la deuda, la alternativa —fusionar main en una release congelada— habría metido tres semanas de cambios sin probar en producción. El cherry-pick acota el riesgo a un parche. La lección no es «no lo hagas»: es «hazlo a sabiendas, con -x, y lleva la cuenta».

6 · Errores habituales

1. Cherry-pick para «integrar» una feature

Mal — copiar la rama commit a commit 
git switch main
git cherry-pick 1a2b3c4 2b3c4d5 3c4d5e6 4d5e6f7
# main y feature ya no comparten los mismos commits
# y el merge posterior traerá duplicados y conflictos
Bien — fusionar la rama 
git switch main
git merge --no-ff feature/informe
# o, si la rama es privada y quieres linealidad:
git rebase feature/informe

Cherry-pick sirve para excepciones entre líneas de mantenimiento. Si quieres todo el trabajo de una rama, la herramienta es merge o rebase.

2. Commitear a mitad de un cherry-pick con conflicto

Mal — romper el secuenciador 
git add src/version.js
git commit -m "arreglo versión"     # commit manual
git cherry-pick --continue          # estado inconsistente
Bien — dejar que Git cierre el commit 
git add src/version.js
git cherry-pick --continue
# si quieres ajustar el mensaje: git commit --amend antes de continuar

Durante una secuencia, Git guarda el progreso en .git/sequencer. Un commit manual no actualiza ese estado: acabarás con commits duplicados o con un --continue que no sabe dónde está.

3. Copiar un rango y olvidar el primer commit

Mal — A..B excluye A 
git cherry-pick 1a2b3c4..9d8e7f6
# querías incluir 1a2b3c4 y no lo has hecho
Bien — incluir el extremo con ^ 
git cherry-pick 1a2b3c4^..9d8e7f6
git log --oneline 1a2b3c4^..9d8e7f6   # comprobar antes qué entra

La notación de rangos es la misma que en git log y confunde a todo el mundo la primera vez. Antes de copiar, imprime la lista con git log --oneline A^..B: si no aparece lo que esperas, no lo ejecutes.

7 · Ejercicio guiado

Objetivo: hacer un backport con conflicto, conservar la versión de la rama de destino y verificar la procedencia con -x.

Escenario: en taller, main tiene el commit 4f2a1c9 que cambia notas.md y version.txt. La rama release/1.4 tiene otra versión en version.txt.

  1. Prepara la release. 
    git switch -c release/1.4 1a2b3c4
printf '1.4.3\n' > version.txt
git add version.txt
git commit -m "chore(release): versión 1.4.3"
  2. Crea el arreglo en main. 
    git switch main
printf '1.5.0-dev\n' > version.txt
printf '## Búsqueda\n- escapar acentos\n' >> notas.md
git commit -am "fix(busqueda): escapar acentos"
  3. Copia el arreglo a la release. 
    git switch release/1.4
git cherry-pick -x main

    Debe fallar por conflicto en version.txt.

  4. Resuelve conservando 1.4.3 y quedándote con la sección nueva de notas.md. 
    git add version.txt notas.md
git cherry-pick --continue
  5. Verifica. 
    cat version.txt
git log -1 --format="%h %s%n%b"
git cherry -v main release/1.4
Solución resuelta

El commit original en main es main en el momento del cherry-pick, así que el mensaje debe llevarlo como origen. Salida esperada tras el paso 5:

1.4.3

a1c9e42 fix(busqueda): escapar acentos
(cherry picked from commit 7d4b2e8f1a3c5e7d9b0a2c4e6f8d1b3a5c7e9f0d)

- 7d4b2e8 fix(busqueda): escapar acentos
+ a1c9e42 chore(release): versión 1.4.3

El - de git cherry confirma que el parche de main ya está en la release. version.txt conserva 1.4.3: no has arrastrado el 1.5.0-dev de main. Si el conflicto se hubiera resuelto con --theirs a ciegas, la release habría quedado marcada como 1.5.0-dev.

8 · Reto

Reto

En taller, crea en main tres commits consecutivos sobre notas.md: A añade una sección, B corrige una errata de A y C añade una subsección que depende del texto de A. Necesitas llevar a release/1.4 solo B y C, pero B no se aplica sin el contexto que introdujo A.

Consigue el resultado con un solo commit en la release cuyo contenido sea exactamente el de A+B+C, sin copiar los tres hashes por separado y sin fusionar main. Después demuestra con git cherry -v main release/1.4 qué commits aparecen como equivalentes y explica en una frase por qué la release no puede «verse» como si tuviera la historia de main.

Pista: git cherry-pick -n aplica sin commitear, y el rango A^..C incluye los tres. Piensa cómo combinar ambos para obtener un único commit con el estado final; y recuerda que -n no mueve HEAD hasta que tú commiteas.

9 · Resumen

  • cherry-pick aplica el parche de un commit sobre la rama actual y crea un commit nuevo con otro hash y otro padre.
  • Mueve la rama actual como un commit normal; la rama de origen no se toca.
  • Admite un commit, varios o un rango: A..B excluye A; A^..B lo incluye.
  • -x deja la procedencia en el mensaje; -n aplica sin commitear.
  • Conflicto: editar → git add → --continue. Salidas: --abort y --skip.
  • Coste: commits duplicados, merges ruidosos y revert doble. Úsalo en backports puntuales, no como estrategia.

10 · Preguntas frecuentes

¿Cherry-pick conserva al autor original?

Sí. El campo author (nombre, correo y fecha de autoría) se mantiene; lo que cambia es el committer y la fecha de commit. Por eso es habitual ver un commit en la release atribuido a quien escribió el arreglo y con la nota «cherry picked from». Si necesitas cambiar también la autoría, tendrías que reescribir el commit con --amend --author, algo que rara vez quieres.

¿Por qué el merge posterior no elimina el duplicado?

Porque un merge no compara parches: compara historias. Git ve dos commits con hashes distintos y los conserva ambos; el contenido idéntico se resuelve como un cambio ya presente, sin generar un conflicto necesariamente, pero las dos entradas siguen en el grafo. Solo una reescritura de historia (rebase o squash) podría unificarlas, y en ramas publicadas eso no se hace sin coordinación.

¿Puedo hacer cherry-pick de un commit de merge?

Sí, pero necesitas indicar qué padre usar como base: git cherry-pick -m 1 <hash> aplica los cambios relativos al primer padre. Es útil para llevar a una release un merge entero de una feature, aunque suele ser más limpio copiar los commits individuales que te interesan. Si no indicas -m, Git se niega y te lo recuerda.

¿Qué diferencia hay entre cherry-pick y rebase?

El rebase mueve toda una rama a una base nueva: cambia el punto de partida de la rama y reaplica su secuencia. El cherry-pick copia commits concretos a donde tú estés, sin mover la rama de origen ni cambiar su base. Rebase es para poner tu rama al día; cherry-pick, para trasplantar excepciones entre líneas que no deben fusionarse todavía.

¿Cómo recupero el commit original si solo tengo la copia?

El mensaje con -x te da el hash; sin él, puedes buscar por contenido con git log -S "texto del cambio" --all o comparar patch-ids con git cherry. En el peor caso, el commit original sigue en el reflog de la rama donde se creó, si aún no ha expirado. La moraleja: si vas a hacer backports, usa -x desde el primero.
