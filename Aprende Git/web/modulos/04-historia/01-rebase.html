Rebase: rejugar commits

Módulo 4 · Historia 🕐 35 minutos

1 · Introducción

En el módulo 3 uniste ramas con merge. Merge es honesto: conserva el dibujo tal y como ocurrió, incluidos los commits de ida y vuelta y ese merge commit con dos padres. Pero cuando trabajas una semana en feature/busqueda mientras main avanza, la historia resultante parece el plano del metro: útil, sí; legible, no siempre.

git rebase responde a otra pregunta: «si hoy empezara esta rama desde el main actual, ¿cómo serían mis commits?». En lugar de unir dos líneas, coge tus commits y los reaplica uno a uno sobre la nueva base. El resultado es una línea recta.

Ese «reaplicar» tiene una consecuencia que hay que entender antes de escribir el comando: los commits son nuevos. No se mueven; se copian. Cambia el padre, cambia el hash. Un rebase no es un desplazamiento, es una reescritura.

¿Por qué existe esta lección?

Porque rebase es el comando que más miedo da y el que más se usa mal. No es «merge pero mejor»: es una herramienta para historia privada. Si entiendes qué puntero mueve y qué hashes cambia, dejas de tenerle miedo; si no, un rebase sobre una rama compartida es la forma más rápida de arruinarle el día a tres compañeros.

2 · Teoría

Qué hace rebase, paso a paso

Partimos de una rama feature que salió de main hace tres commits. Mientras trabajabas, main recibió el commit C:

ANTES

                       D───E   feature
                      /
    A───B───C   main

    git switch feature
    git rebase main

DESPUÉS

    A───B───C   main
             \
              D'───E'   feature

    D' y E' hacen lo mismo que D y E, pero son OTROS commits:
    otro padre, otro hash. Los originales quedan huérfanos
    (recuperables con el reflog durante un tiempo).

Por dentro, Git hace esto:

  1. Calcula la base común (merge base) entre feature y main: el commit B. Los commits a reaplicar son los que están en feature y no en main: D y E.
  2. Pone HEAD en modo detached sobre main (C). La rama feature todavía no se ha movido.
  3. Aplica el parche de D sobre C y crea D'. Si hay conflicto, se para y te pide ayuda.
  4. Aplica el parche de E sobre D' y crea E'.
  5. Mueve la rama feature para que apunte a E' y vuelve a enganchar HEAD a ella.
Qué puntero mueve

rebase mueve la rama actual (y con ella HEAD) al final de los commits reaplicados. No mueve main ni la base: la base se queda donde está y tus commits van a su encuentro. Y no toca el directorio de trabajo más allá de lo necesario para aplicar cada parche.

Rebase frente a merge

Los dos integran cambios. La diferencia no es de calidad, es de qué historia quieres contar:

mergerebase
Forma del grafoRamificado, con un commit de merge de dos padresLineal, sin commit de merge
Hashes de tus commitsSe conservanCambian todos
Historia realFiel: se ve cuándo se integró cada ramaReescrita: parece que trabajaste sobre el main de hoy
Resolución de conflictosUna vez, en el mergePuede repetirse en cada commit reaplicado
Seguro en ramas compartidasSí, siempreNo, nunca sin coordinar
Para qué se usaIntegrar en main, preservar contexto y autoría del mergePoner al día tu rama privada antes de un PR
Analogía: el borrador y el acta

merge es el acta de una reunión: recoge lo que pasó, incluso si hubo dos reuniones paralelas. rebase es reescribir el borrador antes de entregarlo: nadie necesita ver las tres versiones intermedias, solo el documento final bien ordenado. Reescribir un borrador propio es normal; reescribir el acta que ya se repartió a todo el mundo, no.

Conflictos durante el rebase

Un rebase se detiene en el primer commit que no se puede aplicar limpio. git status te lo dice con un estado especial:

git status
interactive rebase in progress; onto a1b2c3d
You are currently rebasing branch 'feature' on 'a1b2c3d'.
  (fix conflicts and then run "git rebase --continue")
  (use "git rebase --skip" to skip this patch)
  (use "git rebase --abort" to check out the original branch)

Unmerged paths:
  (use "git restore --staged <file>..." to unstage)
  (use "git add <file>..." to mark resolution)
        both modified:   notas.md

El flujo es siempre el mismo:

  1. Edita el fichero y deja el contenido correcto, sin marcadores <<<<<<<, ======= ni >>>>>>>.
  2. Marca la resolución con git add notas.md. No hagas git commit: el rebase necesita controlar el commit.
  3. Continúa con git rebase --continue. Git crea el commit con el mensaje original y sigue con el siguiente parche.

Y las dos salidas de emergencia:

  • git rebase --abort: vuelve exactamente al estado anterior a empezar. Tu rama, tu índice y tus ficheros, como estaban. Es el botón de pánico y casi siempre es la decisión correcta si te has perdido.
  • git rebase --skip: descarta ese commit y sigue. Úsalo solo cuando el parche ya está aplicado en la base y no aporta nada; si lo usas para «quitarte el conflicto de encima», estás borrando trabajo sin querer.
Cuidado: «ours» y «theirs» están invertidos

En un merge, --ours es tu rama y --theirs la que entra. En un rebase, Git está construyendo la base, así que --ours es la rama sobre la que rebasas (main) y --theirs es tu commit reaplicado. Si resuelves a base de git checkout --ours de memoria, puedes quedarte con el lado contrario. En caso de duda, abre el fichero y lee.

La regla de oro

Rebase reescribe. Por tanto:

Regla de oro

No rebases commits que ya están fuera de tu repositorio y sobre los que alguien puede haber construido. Si tu rama está publicada y un compañero ha hecho pull, tu rebase le cambia los hashes: su rama y la tuya dejan de compartir historia. Rebase solo lo tuyo, lo local, lo que aún no has publicado. Si de verdad hay que reescribir una rama compartida, se avisa, se coordina y se hace con --force-with-lease —lo verás en la lección 4.

Cuándo rebase y cuándo no

SituaciónHerramientaPor qué
Tu rama local se quedó atrás y quieres un PR limpiogit rebase mainHistoria lineal, sin merge commits de sincronización
Integrar una rama terminada en maingit merge --no-ffPreserva el contexto y no reescribe lo publicado
Una rama publicada que otros usanmerge (o nada)Reescribirla rompe a todo el que la tenga
Quieres arreglar el orden o los mensajes de tus commitsrebase -iEs exactamente para eso: lección 2
Necesitas un solo commit concreto de otra ramacherry-pickNo quieres arrastrar toda la rama: lección 3
Truco de revisión: range-diff

Después de rebasar, git range-diff main feature@{1} feature compara la versión antigua y la nueva de la rama commit a commit. Es la forma de comprobar que un rebase no cambió el contenido, solo la base. feature@{1} es el reflog: «donde estaba feature hace un movimiento».

3 · Ejemplo mínimo

En el repositorio taller, crea una rama, añade un commit y adelanta main en paralelo:

git switch main
git switch -c feature/busqueda

echo "búsqueda por título" >> notas.md
git commit -am "feat(busqueda): filtrar por título"

git switch main
echo "índice actualizado" >> notas.md
git commit -am "docs: actualizar índice"

git log --oneline --graph --all
* 7c9d0e1 (main) docs: actualizar índice
| * 4b8a2f3 (HEAD -> feature/busqueda) feat(busqueda): filtrar por título
|/
* 1a2b3c4 feat: crear notas iniciales

La rama está «desfasada»: su base es 1a2b3c4, no 7c9d0e1. Ahora rebasa:

git switch feature/busqueda
git rebase main
Successfully rebased and updated refs/heads/feature/busqueda.
        
git log --oneline --graph --all
* 9f3c1a7 (HEAD -> feature/busqueda) feat(busqueda): filtrar por título
* 7c9d0e1 (main) docs: actualizar índice
* 1a2b3c4 feat: crear notas iniciales

Fíjate en lo importante: el commit de la feature ya no es 4b8a2f3, es 9f3c1a7. Mismo cambio, distinto padre (7c9d0e1 en vez de 1a2b3c4), distinto hash. El grafo es una línea y main no se ha movido.

Si algo sale mal

git rebase --abort te devuelve al punto de partida. Y si ya terminó y no te gusta el resultado, el reflog aún recuerda el commit viejo: git reset --hard feature@{1}. Nada de esto funciona si ya habías publicado y forzado el push; en local, sí.

4 · Ejemplo real

Escenario: llevas cuatro días con feature/busqueda, ya la habías subido a origin para que te la revisaran, y main ha recibido cinco commits, uno de ellos tocando notas.md —el mismo fichero que tú. Quieres dejarla presentable antes de pedir la revisión definitiva.

git switch feature/busqueda
git fetch origin
git log --oneline HEAD..origin/main        # qué hay en main que no tengo
git rebase origin/main
Auto-merging notas.md
CONFLICT (content): Merge conflict in notas.md
error: could not apply 4b8a2f3... feat(busqueda): filtrar por título
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
Could not apply 4b8a2f3... feat(busqueda): filtrar por título

Abres notas.md y ves los marcadores. El conflicto es real: main añadió una sección de índice y tú añadiste una de búsqueda en el mismo sitio. Decides conservar las dos, en este orden: índice primero, búsqueda después.

<<<<<<< HEAD
## Índice
- Introducción
- Búsqueda
=======
## Búsqueda
- Por título
- Por etiqueta
>>>>>>> 4b8a2f3 (feat(busqueda): filtrar por título)

Editas, quitas los marcadores y continúas:

git add notas.md
git rebase --continue
[detached HEAD 9f3c1a7] feat(busqueda): filtrar por título
 1 file changed, 4 insertions(+)
Successfully rebased and updated refs/heads/feature/busqueda.

Si el siguiente commit también choca, el proceso se repite. Cuando terminas, compruebas dos cosas: que el contenido es el de antes y que la historia es lineal.

git log --oneline --graph main..HEAD
git range-diff origin/main feature@{1} feature
* 9f3c1a7 (HEAD -> feature/busqueda) feat(busqueda): filtrar por título
* b2e4d68 feat(busqueda): ordenar resultados

1: 4b8a2f3 ! 1: 9f3c1a7 feat(busqueda): filtrar por título
    @@ Metadata
     Author: Ana <ana@ejemplo.dev>
    @@ notas.md
    -## Búsqueda
    +## Índice
    +- Introducción
    +- Búsqueda
    +## Búsqueda

El range-diff confirma que el único cambio es el contexto heredado de main; el parche sigue siendo el mismo.

Ahora la rama está publicada con hashes viejos. Para actualizarla hay que reescribir el remoto, pero solo esta rama y solo con protección:

git push --force-with-lease origin feature/busqueda
+ 9f3c1a7...b2e4d68 feature/busqueda -> feature/busqueda (forced update)
Lo que acabas de hacer y lo que no

Has reescrito tu rama, que nadie más usa como base, y lo has hecho con --force-with-lease, que aborta si el remoto cambió desde tu último fetch. Eso es legítimo. Lo que nunca harías es git rebase main estando en main con commits ya publicados, ni git push --force sobre main. La diferencia entre un profesional y un susto no es el flag: es saber sobre qué rama se aplica.

6 · Errores habituales

1. Rebasear una rama que ya usa alguien

Mal — reescribir lo compartido 
git switch feature/pagos        # publicada, dos personas trabajando
git rebase main
git push --force                # los commits de tu compañero desaparecen
Bien — integrar sin reescribir 
git switch feature/pagos
git merge main                  # conserva hashes e historia de todos
git push

La regla no es «rebase malo»: es «lo que otros ya bajaron no se reescribe». Si la rama es compartida, se integra con merge; si es tuya y aún no la ha tocado nadie, rebase es perfectamente sano.

2. Commitear a mitad del rebase

Mal — romper el secuenciador 
git add notas.md
git commit -m "conflicto resuelto"   # commit extra que Git no esperaba
git rebase --continue
Bien — dejar que Git cree el commit 
git add notas.md
git rebase --continue                # usa el mensaje del commit original
# si quieres cambiar el mensaje: git commit --amend antes de continuar

El rebase mantiene su propio estado (qué parche toca, dónde está HEAD). Un commit manual lo descoloca y suele acabar en commits duplicados o mensajes absurdos.

3. Usar --skip como botón de «no quiero ver el conflicto»

Mal — borrar trabajo sin mirar 
git rebase main
# conflicto en notas.md
git rebase --skip          # "total, ya lo arreglaré luego"
git push --force-with-lease
Bien — resolver o abortar 
git rebase main
# conflicto en notas.md
# opción A: editar + git add + git rebase --continue
# opción B: git rebase --abort   (vuelves al estado inicial, sin pérdida)

--skip descarta el parche entero. A veces es lo correcto (el cambio ya está en la base), pero como reflejo automático es una pérdida de código silenciosa: no hay conflicto, no hay error, simplemente falta una funcionalidad.

7 · Ejercicio guiado

Objetivo: provocar un conflicto durante un rebase, resolverlo sin commitear a mano y comprobar que la historia queda lineal y el contenido intacto.

Escenario: en taller, dos ramas tocan la misma línea de notas.md.

  1. Prepara el escenario. 
    git switch main
git switch -c feature/etiquetas
printf '## Etiquetas\n- prioritario\n' >> notas.md
git commit -am "feat(etiquetas): añadir sección"

git switch main
printf '## Etiquetas\n- urgente\n' >> notas.md
git commit -am "feat(etiquetas): sección desde main"
  2. Lanza el rebase y observa el estado. 
    git switch feature/etiquetas
git rebase main
git status

    Debe aparecer interactive rebase in progress (aunque no sea interactivo) y both modified: notas.md.

  3. Resuelve el conflicto. Deja el fichero así, sin marcadores: 
    ## Etiquetas
- urgente
- prioritario
  4. Marca y continúa. 
    git add notas.md
git rebase --continue
  5. Verifica. 
    git log --oneline --graph --all
git status
cat notas.md
Solución resuelta

Salida esperada tras el paso 5:

* 5e7a9c1 (HEAD -> feature/etiquetas) feat(etiquetas): añadir sección
* 3d1f8b2 (main) feat(etiquetas): sección desde main
* 1a2b3c4 feat: crear notas iniciales

On branch feature/etiquetas
nothing to commit, working tree clean

## Etiquetas
- urgente
- prioritario

Hay una sola línea, el commit de la feature tiene hash nuevo (5e7a9c1, no el original) y main sigue en 3d1f8b2. Si en el paso 2 te hubieras perdido, git rebase --abort te devolvería exactamente al escenario inicial: no habrías perdido nada.

8 · Reto

Reto

En taller, crea la rama feature/export con tres commits. Mientras tanto, en main, mueve el fichero notas.md a docs/notas.md con git mv y commitea el movimiento. Ahora rebasa feature/export sobre main.

El rebase fallará con un conflicto distinto a los anteriores: el fichero que tus commits modifican ya no está donde estaba. Resuélvelo de forma que el contenido de los tres commits acabe en docs/notas.md, sin duplicar el fichero viejo, y demuestra con git log --follow --oneline -- docs/notas.md que la historia sigue el rename.

Pista: antes de tocar nada, mira qué dice git status sobre deleted by us y deleted by them; en un rebase los papeles de «us» y «them» no significan lo que crees. Piensa si te conviene resolver con git add, con git rm o con las dos cosas en commits distintos.

9 · Resumen

  • rebase reaplica tus commits sobre otra base; no los mueve, los copia con otro padre y otro hash.
  • Mueve la rama actual y HEAD; main y la base no se mueven.
  • merge conserva la historia real; rebase la deja lineal. Ninguno es «mejor»: depende de si la rama es privada o compartida.
  • Conflicto: editar → git add → git rebase --continue. Salidas: --abort (segura) y --skip (descarta el commit).
  • Durante un rebase, ours es la base y theirs es tu commit.
  • Regla de oro: nunca rebases lo que otros ya tienen. Si hay que reescribir una rama publicada, se coordina y se usa --force-with-lease.

10 · Preguntas frecuentes

¿Rebase elimina mis commits originales?

No los borra inmediatamente: los deja huérfanos. La rama apunta a las copias nuevas, pero los commits viejos siguen en la base de datos hasta que el recolector los limpia. Durante días puedes recuperarlos con el git reflog y un git reset --hard al hash antiguo. Eso sí: si nunca estuvieron referenciados o pasó el plazo de expiración, pueden desaparecer de verdad.

¿Por qué se repite el mismo conflicto en varios commits?

Porque el rebase aplica cada commit por separado. Si tres commits tocan la misma zona, puedes resolver el conflicto tres veces. Dos formas de reducirlo: commits más pequeños y con responsabilidades separadas, o activar git config rerere.enabled true, que recuerda cómo resolviste un conflicto y lo reaplica automáticamente cuando vuelve a aparecer. rerere no adivina: reutiliza tu resolución anterior.

¿Qué diferencia hay entre git rebase main y git rebase origin/main?

main es tu rama local, que puede estar desactualizada. origin/main es la referencia de lo último que bajaste del remoto. Para preparar un PR conviene git fetch origin y rebasar sobre origin/main: así te alineas con lo que de verdad hay publicado, no con tu copia de ayer. Si tu main local está al día, da igual; si no, cambia el resultado.

¿Un rebase puede perder cambios sin avisar?

Sí, en dos casos típicos: usar --skip para quitarte un conflicto de encima (descarta el commit entero) y resolver un conflicto eligiendo un lado con --ours o --theirs sin leer. Git no sabe qué querías; solo sabe qué le dijiste. Por eso el flujo sano es leer el fichero, editar y comprobar con los tests. Ante la duda, --abort y vuelves a empezar sin coste.

¿Y git rebase --onto?

Es la versión quirúrgica: git rebase --onto main vieja-base feature reaplica en main los commits de feature que están por encima de vieja-base, y descarta lo que quede por debajo. Sirve para «trasplantar» solo una parte de una rama. Es potente y fácil de usar mal: si no tienes claro cuál es la base antigua, dibuja el grafo en papel antes de ejecutarlo. En el 99 % de los casos, git rebase main es lo que necesitas.
