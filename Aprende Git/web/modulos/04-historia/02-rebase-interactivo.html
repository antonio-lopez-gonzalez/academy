Rebase interactivo: esculpir la historia

Módulo 4 · Historia 🕐 40 minutos

1 · Introducción

Ya sabes reaplicar una rama sobre otra base (lección anterior). Pero la historia de una rama de trabajo rara vez es presentable a la primera: hay un commit wip, otro que corrige una errata del primero, uno de depuración con un console.log, y dos commits que en realidad son el mismo cambio partido en dos.

git rebase -i (interactivo) abre una lista de tus commits en un editor de texto y te deja decidir qué hacer con cada uno: conservarlo, fusionarlo con el anterior, cambiarle el mensaje, reordenarlo o eliminarlo. No cambia el contenido del trabajo: cambia cómo se cuenta.

¿Por qué existe esta lección?

Porque el historial de un repositorio es documentación. Un PR con nueve commits llamados wip, fix, fix2 y ahora sí obliga al revisor a reconstruir tu proceso mental. Tres commits bien contados explican la intención, permiten revertir una parte sin tocar el resto y hacen que git blame diga algo útil. Limpiar la historia antes de publicarla es parte del trabajo, no vanity.

2 · Teoría

Qué abre exactamente git rebase -i

git rebase -i HEAD~4 significa: «toma los últimos cuatro commits y muéstramelos para editarlos». El commit HEAD~4 es la base y no se toca; los cuatro siguientes son los candidatos. Git abre tu editor configurado (core.editor) con algo así:

pick 1a2b3c4 feat(ui): añadir botón de búsqueda
pick 5d6e7f8 fix(ui): corregir padding del botón
pick 9a0b1c2 docs: nota sobre el botón
pick 3c4d5e6 wip

# Rebase 7c9d0e1..3c4d5e6 onto 7c9d0e1 (4 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup <commit> = like "squash", but discard this commit's log message
# d, drop <commit> = remove commit

El orden de las líneas es el orden en que se aplicarán los commits, del más antiguo al más nuevo. Guardar y cerrar el editor lanza el rebase.

Qué puntero mueve

Igual que un rebase normal: mueve la rama actual al final de la nueva secuencia de commits; HEAD la acompaña. La base (HEAD~4) no se mueve. Y como todo rebase, genera hashes nuevos para cada commit que toca, incluso para los que solo reordenas.

Los cinco verbos que necesitas

VerboAtajoQué haceCuándo usarlo

rewordrConserva el cambio, abre el editor para el mensajeMensaje pobre o con errata
editePara el rebase tras aplicar el commitQuieres modificar el contenido con --amend

Borrar la línea equivale a drop. Y no hace falta memorizar los atajos: el propio fichero los lista en los comentarios.

Analogía: montar el PR antes de enseñarlo

Tu rama es el montaje de una película y el PR es la proyección. Durante el montaje cortas tomas falsas, unes planos que van juntos y pones rótulos. Nadie necesita ver las tomas descartadas. El rebase interactivo es la sala de montaje; el main publicado es la proyección: una vez emitida, no se cambia la película, se emite otra cosa.

Reordenar, fusionar y eliminar

Reordenar es mover líneas. Git aplica los commits en el nuevo orden; si dos cambios dependen entre sí, aparecerá un conflicto que tendrás que resolver en ese nuevo contexto.

Fusionar (squash) convierte dos commits en uno. Si tienes esta lista:

ANTES                                   LISTA EDITADA
pick a1 feat(ui): botón                 pick   a1 feat(ui): botón
pick b2 fix(ui): padding                squash b2 fix(ui): padding
pick c3 docs: nota                      squash c3 docs: nota
                                       
RESULTADO                               Al guardar, Git abre OTRO editor
                                        con los tres mensajes juntos:
* a1' feat(ui): botón + padding + nota
  (un solo commit, hash nuevo)          # This is a combination of 3 commits.
                                        # This is the 1st commit message:
                                        feat(ui): botón
                                        # This is the commit message #2:
                                        fix(ui): padding

En ese segundo editor dejas un mensaje único y limpio; las líneas que empiezan por # se ignoran. fixup se salta ese editor porque asume que el mensaje del commit que corrige no aporta nada.

Eliminar un commit con drop no elimina los cambios del resto: solo ese parche. Si el commit borrado contenía algo que los siguientes necesitan, el rebase fallará o el resultado no compilará. Ahí es donde entran los tests.

Conflictos y paradas

Un rebase interactivo se puede parar por tres motivos:

  • Conflicto. Editas, git add, git rebase --continue. Igual que en la lección anterior.
  • edit. Git se detiene después de aplicar el commit. Puedes modificar ficheros, git commit --amend y luego git rebase --continue. Si no cambias nada, --continue sigue sin más.
  • exec. Ejecuta un comando tras cada commit; si devuelve error, se detiene. Útil para comprobar que cada commit intermedio compila o pasa los tests.

git rebase --abort sigue siendo el botón de pánico: devuelve la rama y el árbol de trabajo al estado previo a empezar. git rebase --skip descarta el commit en curso.

Limpiar una rama antes del PR

El flujo que funciona casi siempre:

  1. Ponte al día primero. git fetch origin y git rebase origin/main. Limpiar mensajes sobre una base vieja obliga a repetir el trabajo.
  2. Mira la lista completa. git log --oneline origin/main..HEAD. Decide qué commits cuentan una historia y cuáles son ruido de proceso.
  3. Diseña el resultado. Escribe en papel los 2-4 commits finales y su mensaje. Si no puedes explicar cada uno en una frase, probablemente sobra o falta.
  4. Rebasa en interactivo. git rebase -i origin/main: reordena, fusiona, reescribe mensajes, elimina.
  5. Comprueba el contenido, no solo la forma. git diff origin/main...HEAD debe ser idéntico al de antes de limpiar. Y los tests deben pasar.
  6. Publica con protección. git push --force-with-lease solo si la rama es tuya. Si alguien más la usa, no la reescribas.
Atajo para los «fixup» del día a día

Si haces un commit para corregir otro anterior, no esperes al final: git commit --fixup=<hash> marca el mensaje como fixup! .... Luego, git rebase -i --autosquash origin/main coloca ese commit justo detrás de su objetivo y lo marca como fixup automáticamente. Para commits que sí merecen mensaje propio, --squash=<hash>.

3 · Ejemplo mínimo

Tres commits, uno de ellos una errata del primero. Quieres que queden dos: el commit de funcionalidad limpio y el de documentación.

git log --oneline -3
3c4d5e6 docs(ui): documentar el botón
9a0b1c2 fix(ui): corregir "busqueda" en el botón
1a2b3c4 feat(ui): añadir botón de búsqueda

Lanzas el interactivo sobre los tres:

git rebase -i HEAD~3

En el editor cambias la segunda línea por fixup y guardas:

pick 1a2b3c4 feat(ui): añadir botón de búsqueda
fixup 9a0b1c2 fix(ui): corregir "busqueda" en el botón
pick 3c4d5e6 docs(ui): documentar el botón
        
Successfully rebased and updated refs/heads/feature/ui.
        
git log --oneline -2
b7e2f90 (HEAD -> feature/ui) docs(ui): documentar el botón
5f1c8a3 feat(ui): añadir botón de búsqueda

El commit de la errata desapareció como entidad propia, pero su cambio sigue dentro del commit 5f1c8a3. Y los dos commits que quedan tienen hashes nuevos: 3c4d5e6 ya no existe en la rama.

Un rebase interactivo sin cambios también reescribe

Si abres git rebase -i HEAD~3, no cambias nada y guardas, Git igualmente reaplica los commits y les asigna hashes nuevos. No es un no-op. Cancelar el editor sin guardar (o borrar todas las líneas y salir) sí aborta sin tocar nada.

4 · Ejemplo real

Escenario: una rama de una semana con nueve commits. El PR todavía no se ha abierto, pero la rama ya está en origin para una revisión informal. La lista:

git fetch origin
git log --oneline origin/main..HEAD
a9f1e02 (HEAD -> feature/api) wip
8d3c7b1 fix build
6b2a4c9 console.log de depuración
5e1f8d3 test(api): casos límite
4c0b7a6 fix(api): validar query vacía
3a9d2e8 feat(api): endpoint de búsqueda
2f8c1b4 docs(api): borrador
1e7a3c5 chore: renombrar variable
0d6b2a1 feat(api): endpoint de búsqueda (primera parte)

El contenido real son tres cosas: el endpoint, sus tests y la documentación. El resto es proceso. Diseñas el resultado en papel:

  • feat(api): endpoint de búsqueda — incluye el renombrado, la validación de query vacía y el arreglo del build.
  • test(api): cubrir casos límite
  • docs(api): documentar parámetros de búsqueda

Rebasas contra origin/main para no limpiar sobre una base vieja:

git rebase -i origin/main

La lista editada queda así (los fixup van detrás de su objetivo):

pick   0d6b2a1 feat(api): endpoint de búsqueda (primera parte)
fixup  1e7a3c5 chore: renombrar variable
fixup  3a9d2e8 feat(api): endpoint de búsqueda
fixup  4c0b7a6 fix(api): validar query vacía
fixup  8d3c7b1 fix build
drop   6b2a4c9 console.log de depuración
pick   5e1f8d3 test(api): casos límite
fixup  a9f1e02 wip
reword 2f8c1b4 docs(api): borrador

Al guardar, Git fusiona los cinco primeros en un commit, elimina el console.log, fusiona el wip con los tests y abre el editor para el mensaje de documentación, que reescribes:

docs(api): documentar parámetros de búsqueda

Explica `q`, `page` y `limit`, y el comportamiento con query vacía.
        
Successfully rebased and updated refs/heads/feature/api.

Verificas que el contenido neto no cambió y que todo pasa:

git log --oneline origin/main..HEAD
git diff origin/main...HEAD --stat
npm test
c4e8a12 (HEAD -> feature/api) docs(api): documentar parámetros de búsqueda
8b1d5f7 test(api): cubrir casos límite
2a7f9c0 feat(api): endpoint de búsqueda

 src/api/search.js      | 84 ++++++++++++++++++++++++
 test/search.test.js    | 46 ++++++++++++++++
 docs/api/search.md     | 31 ++++++++++++++
 3 files changed, 161 insertions(+)

Nueve commits convertidos en tres, sin perder una línea de código. Ahora sí, el PR cuenta una historia.

La rama estaba publicada

Al reescribir hashes, el push normal será rechazado. Aquí sí toca git push --force-with-lease origin feature/api, después de avisar a quien la estuviera mirando para que no base trabajo en los hashes viejos. Si alguien más tuviera commits en esa rama, el lease lo detectaría y el push se abortaría: esa es la red de seguridad, no un estorbo.

5 · Buenas prácticas

HazEvitaPor qué
Limpiar antes de abrir el PR, sobre una base fresca Limpiar después de que el revisor haya comentado línea a línea Reescribir durante la revisión invalida sus comentarios y tu tiempo
Un commit por intención: funcionalidad, tests, docs Un único commit gigante «todo el módulo» Permite revertir una parte sin deshacer el resto y facilita el blame
Usar fixup para correcciones del mismo cambio Fusionar commits que arreglan cosas distintas Un commit debe poder explicarse solo; mezclar responsabilidades lo impide
Comprobar git diff origin/main...HEAD tras limpiar Confiar solo en que el rebase terminó sin conflictos Puedes haber perdido un parche con drop o al resolver un conflicto
Hacer exec de los tests si quieres commits que compilen Asumir que cada commit intermedio funciona Un revisor o un bisect puede aterrizar en cualquiera de ellos
Reescribir solo ramas propias y con --force-with-lease rebase -i sobre main o una rama compartida Los hashes nuevos rompen a todo el que haya hecho pull

6 · Errores habituales

1. Limpiar la historia pero cambiar el contenido

Mal — resolver el conflicto «a lo rápido» 
# conflicto al reordenar dos commits que tocaban la misma función
git checkout --ours src/search.js
git add src/search.js
git rebase --continue
# ...y se perdió la validación de query vacía
Bien — verificar el diff neto 
# resolver leyendo el fichero
git diff origin/main...HEAD        # ¿es el mismo cambio que antes?
git range-diff origin/main feature@{1} feature
npm test

Un rebase interactivo es una edición de texto sobre la historia: si te equivocas, el resultado puede ser sintácticamente válido y funcionalmente incompleto. El diff neto es la prueba.

2. Fusionar commits que no tienen relación

Mal — un solo commit para todo 
pick a1 feat(api): endpoint
squash b2 fix(ui): color del botón
squash c3 chore: actualizar lockfile
→ "feat(api): endpoint + botón + dependencias"
Bien — una intención por commit 
pick a1 feat(api): endpoint
pick b2 fix(ui): color del botón
pick c3 chore: actualizar lockfile
→ tres commits que se pueden revertir por separado

El objetivo no es «menos commits»: es commits que cuentan una sola cosa. Fusionar por pereza produce un historial tan inútil como el de wip.

3. Editar la lista y salir sin querer

Mal — editor que no sabes cerrar 
# en vim: pulsas :wq sin revisar
# o :q! y el rebase no arranca
# o borras una línea por accidente y desaparece un commit
Bien — editor explícito y copia de seguridad 
git config --global core.editor "nano"   # o "code --wait"
git branch backup/feature-api            # antes de reescribir
git rebase -i origin/main

Si el rebase ya terminó y borraste algo, git reflog conserva el estado anterior: git reset --hard HEAD@{1}. La rama de respaldo es barata y convierte un desastre en un switch.

7 · Ejercicio guiado

Objetivo: convertir tres commits (funcionalidad, wip y errata) en un solo commit limpio, y comprobar que el contenido no cambió.

Escenario: en taller, rama feature/busqueda con estos commits:

3c4d5e6 fix(busqueda): corregir "busqueda" en el título
9a0b1c2 wip
1a2b3c4 feat(busqueda): añadir sección de búsqueda
  1. Guarda una red de seguridad. 
    git branch backup/busqueda
  2. Abre el interactivo. 
    git rebase -i HEAD~3
  3. Edita la lista para que quede exactamente así: 
    pick 1a2b3c4 feat(busqueda): añadir sección de búsqueda
fixup 9a0b1c2 wip
fixup 3c4d5e6 fix(busqueda): corregir "busqueda" en el título

    Guarda y cierra el editor.

  4. Comprueba el resultado. 
    git log --oneline -1
git log --oneline backup/busqueda..HEAD
  5. Verifica que el contenido es el mismo que antes de limpiar: 
    git diff backup/busqueda..HEAD

    La salida debe estar vacía: los hashes cambiaron, el contenido no.

  6. Borra el respaldo cuando estés convencido: 
    git branch -d backup/busqueda
Solución resuelta

Tras el paso 3, el rebase termina sin abrir un segundo editor porque fixup descarta los mensajes. Salida esperada de los pasos 4 y 5:

$ git log --oneline -1
a7c1e93 (HEAD -> feature/busqueda) feat(busqueda): añadir sección de búsqueda

$ git log --oneline backup/busqueda..HEAD
a7c1e93 feat(busqueda): añadir sección de búsqueda

$ git diff backup/busqueda..HEAD
(vacío)

Un solo commit, hash nuevo y cero diferencias de contenido. El wip y la errata ya no aparecen en la historia, pero sus cambios siguen ahí. Si algo hubiera salido mal, git reset --hard backup/busqueda te devuelve al punto de partida.

8 · Reto

Reto

Parte de una rama feature/informe con ocho commits desordenados: dos implementan el informe, tres son correcciones del mismo, uno es un console.log, uno toca solo el README y uno añade tests. Redúcela a exactamente tres commits —feat, test y docs— y consigue que cada commit intermedio pase los tests usando exec en la lista interactiva.

Al terminar, demuestra tres cosas: que el diff neto contra origin/main es idéntico al inicial, que los tres mensajes cumplen Conventional Commits y que no queda ningún commit que mencione wip ni console.log.

Pista: el orden importa. Si los tests necesitan la funcionalidad completa, el commit de tests no puede ir antes; y exec se ejecuta después de cada línea, así que colócalo donde de verdad quieras comprobar algo. Antes de empezar, guarda el hash del estado inicial para poder comparar con git diff <hash>..HEAD.

9 · Resumen

  • git rebase -i HEAD~n abre una lista editable de los últimos n commits; el commit HEAD~n es la base y no se toca.
  • pick conserva, reword cambia el mensaje, edit para a mitad, squash fusiona con mensaje, fixup fusiona sin mensaje, drop elimina.
  • Mover líneas reordena; el orden de la lista es el orden de aplicación.
  • Todo commit tocado cambia de hash, incluso si solo lo reordenas.
  • --autosquash + commit --fixup automatizan el caso más común.
  • Limpia antes del PR, sobre origin/main fresco, verificando el diff neto y los tests; publica con --force-with-lease y solo en ramas propias.

10 · Preguntas frecuentes

¿Puedo deshacer un rebase interactivo que ya terminó?

Sí, en local. git reflog muestra el movimiento de la rama; el estado anterior suele ser HEAD@{1}. Con git reset --hard HEAD@{1} vuelves exactamente a donde estabas. Si ya habías hecho push --force-with-lease, el reflog local sigue sirviendo, pero el remoto ya tiene la historia nueva: recuperar allí exige otro force push coordinado. Por eso conviene una rama backup/... antes de empezar.

¿Qué diferencia hay entre squash y fixup?

Los dos fusionan el commit con el anterior. squash abre el editor para que combines los mensajes; fixup descarta el mensaje del commit que se fusiona y conserva el del anterior. Regla práctica: si el mensaje del segundo aporta información (por ejemplo, «validar query vacía»), usa squash y redacta; si solo dice «fix», usa fixup.

¿Por qué mi editor es vim y cómo lo cambio?

Git usa lo que tengas en core.editor; si está vacío, cae en el EDITOR del sistema o en vi. Configúralo una vez: git config --global core.editor "nano" o "code --wait". En vim, :wq guarda y sale, :q! sale sin guardar (y aborta el rebase si no has tocado nada). Si te bloqueas, cierra la terminal y vuelve a entrar: el rebase seguirá en curso y podrás hacer --abort.

¿Puedo reescribir el primer commit del repositorio?

Sí: git rebase -i --root incluye el commit raíz en la lista. Es útil para quitar un fichero que nunca debió entrar o corregir el mensaje inicial. Cuidado: cambia todos los hashes del repositorio, así que solo tiene sentido antes de publicar. Si el repositorio ya es compartido, la respuesta honesta es «no sin coordinarlo con todo el equipo».

¿Qué pasa si la rama contiene commits de merge?

Por defecto, rebase -i aplana la historia: los merges desaparecen y los commits de las ramas laterales se reaplican en línea. Si necesitas conservar la topología, usa git rebase -i --rebase-merges origin/main: la lista incluye etiquetas y líneas merge que puedes editar. Es potente y bastante más delicado; para limpiar una rama normal de feature casi nunca lo necesitas.
