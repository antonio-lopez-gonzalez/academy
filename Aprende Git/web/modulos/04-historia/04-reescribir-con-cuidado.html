Reescribir con cuidado

Módulo 4 · Historia 🕐 35 minutos

1 · Introducción

Las tres lecciones anteriores te han dado herramientas para cambiar la historia: rebase, rebase -i y cherry-pick. Todas comparten una propiedad que hasta ahora solo hemos mencionado de pasada: crean commits nuevos. Y un commit nuevo significa un hash nuevo. Cuando esa historia ya está en un remoto, el push normal falla, y es justo el momento en que la gente busca el flag más contundente que encuentra: git push --force.

Ese flag es un martillo. Esta lección trata de por qué existe, qué rompe exactamente y cuál es la alternativa que sí protege a tus compañeros. También trata de la red de seguridad que casi nadie usa hasta que la necesita: el reflog.

¿Por qué existe esta lección?

Porque el 90 % de los incidentes graves con Git no los causa un comando difícil, sino un --force sobre una rama compartida. No hace falta memorizar más sintaxis: hace falta entender qué se pierde al sobrescribir una referencia y quién puede recuperarlo. Con eso, la decisión correcta deja de depender de la valentía.

2 · Teoría

Por qué cambia el hash

Un commit es un objeto inmutable cuyo hash se calcula a partir de su contenido completo. No del diff: del árbol y de los metadatos.

commit 4a1f2c9...
tree   7b3e8d1...            ← foto completa del proyecto
parent 1a2b3c4...            ← commit anterior
author    Ana <ana@ejemplo.dev> 1728800000 +0200
committer Ana <ana@ejemplo.dev> 1728803600 +0200
                                ↑ fecha de commit
message
    feat(busqueda): filtrar por título

hash = SHA-1 (o SHA-256) de todo lo anterior

Cambia cualquier byte —el padre, el árbol, el mensaje, el committer, la fecha— y el hash cambia. Y como el hash del commit forma parte del contenido de sus hijos, el cambio se propaga hacia delante:

ANTES                        DESPUÉS DE UN REBASE

A───B───C   main             A───B───C   main
     \
      D───E   feature              D'───E'   feature

D y E tenían padre B.               D' y E' tienen padre C.
Al cambiar el padre de D,           El hash de D' cambia, y como E'
cambia su hash.                     tiene otro padre (D'), también.
Qué puntero mueve un push forzado

push --force no toca tu repositorio local: mueve la referencia de la rama en el remoto, sin comprobar si el movimiento es seguro. Tu rama local ya estaba en el commit nuevo; lo que se reescribe es la copia del servidor.

Por qué el push normal se niega

Un push normal solo acepta fast-forward: el commit remoto actual debe ser ancestro del que envías. Así el servidor nunca pierde historia. Tras un rebase, tu commit remoto ya no es ancestro del nuevo, porque el nuevo tiene otro padre:

git push origin feature/busqueda
To ../remoto.git
 ! [rejected]        feature/busqueda -> feature/busqueda (non-fast-forward)
error: failed to push some refs to '../remoto.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. Integrate the remote changes (e.g.
hint: 'git pull ...') before pushing again.

El mensaje sugiere pull, pero en este caso un pull normal volvería a mezclar la versión vieja con la nueva y dejaría un merge de dos historias que tú querías unificar. La intención real es reemplazar la referencia remota. De ahí el force.

--force frente a --force-with-lease

--force--force-with-lease
Qué compruebaNadaQue el remoto siga en el valor que tú viste
Si un compañero empujó despuésBorra su commit sin avisarRechaza el push
Cuándo usarloCasi nuncaRamas propias reescritas
Riesgo residualAltísimoBajo, si no hay fetch de por medio

--force-with-lease funciona como un contrato: «reemplaza la rama solo si sigue donde yo la vi». Git compara el valor remoto con tu referencia de seguimiento (origin/feature/busqueda), que se actualiza cuando haces fetch. Si alguien empujó entre medias, los valores no coinciden y el push se aborta:

To ../remoto.git
 ! [rejected]        feature/busqueda -> feature/busqueda (stale info)
error: failed to push some refs to '../remoto.git'
El lease no es magia: depende de tu último fetch

Si un proceso automático (o tú) hace fetch justo antes del push, tu referencia de seguimiento ya incluye el commit ajeno, el lease lo considera «esperado» y el force lo sobrescribe. Para el caso delicado, fija el valor esperado a mano: git push --force-with-lease=feature/x:9f3c1a7 origin feature/x. En Git 2.30+ puedes añadir --force-if-includes, que exige además que el commit remoto sea alcanzable desde tu rama. Aun así, la verdadera protección es no reescribir ramas ajenas.

La regla que no se negocia

Nunca reescribas lo que otros ya bajaron

Si alguien hizo pull de tu rama y construyó trabajo encima, tu reescritura deja sus commits apuntando a padres que ya no existen en la rama. Al volver a integrar, Git verá dos historias paralelas con los mismos cambios. La persona tendrá que hacer reset --hard, perder sus merges locales o resolver un lío que no provocó. main no se reescribe jamás. Si hay que deshacer algo publicado: git revert.

El único escenario donde reescribir una rama publicada es aceptable:

  1. La rama es tuya y nadie más la usa como base (un PR abierto se puede actualizar, pero avisa).
  2. Avísalo antes: «voy a reescribir feature/x, no hagáis pull hasta que termine».
  3. Haz una copia: git branch backup/feature-x.
  4. Publica con --force-with-lease, nunca con --force.
  5. Da las instrucciones para que los demás se alineen: git fetch && git reset --hard origin/feature/x.

El reflog: la red de seguridad local

Git registra cada movimiento de HEAD y de las ramas en un registro local, el reflog. No es una copia de seguridad de ficheros: es un historial de «dónde apuntaba cada referencia y cuándo». Sobrevive a rebases, resets y amends:

git reflog
9f3c1a7 (HEAD -> feature/busqueda) HEAD@{0}: rebase (finish): returning to refs/heads/feature/busqueda
9f3c1a7 (HEAD -> feature/busqueda) HEAD@{1}: rebase (pick): feat(busqueda): filtrar por título
7c9d0e1 HEAD@{2}: rebase (start): checkout main
4b8a2f3 HEAD@{3}: commit: feat(busqueda): filtrar por título
1a2b3c4 HEAD@{4}: checkout: moving from main to feature/busqueda

El commit 4b8a2f3, que el rebase «perdió», sigue ahí. Puedes recuperarlo:

git switch -c rescate 4b8a2f3        # conserva la rama actual y crea otra
git reset --hard 4b8a2f3             # mueve la rama actual al commit antiguo
Límites del reflog

Es local: no se clona, no se empuja y no existe en el servidor. Caduca (por defecto 90 días para entradas alcanzables, 30 para las que quedaron inalcanzables) y el recolector puede borrar los objetos. Tampoco te salva de un --force si tú nunca tuviste esos commits: los que se pierden son los del compañero. Para eso están el lease y la coordinación.

Antes de reescribir, dos segundos de red

git branch backup/lo-que-sea cuesta cero y convierte «he perdido mi trabajo» en «hago switch». El reflog es la red de seguridad automática; la rama de respaldo es la red que tú controlas. Usa las dos en operaciones grandes.

3 · Ejemplo mínimo

Un --amend es la reescritura más pequeña posible. Observa el hash antes y después:

git log --oneline -1
4b8a2f3 (HEAD -> feature/busqueda) feat(busqueda): filtrar por titulo
        
git commit --amend -m "feat(busqueda): filtrar por título"
[feature/busqueda 9f3c1a7] feat(busqueda): filtrar por título
 Date: Mon Oct 12 10:14:03 2026 +0200
 1 file changed, 4 insertions(+)

Mismo cambio, una tilde distinta, otro commit. Si ya estaba publicado, el push normal se negará. Y si te arrepientes, el reflog conserva el original:

git reflog -3
git switch -c antes-del-amend 4b8a2f3
git log --oneline -1 antes-del-amend
9f3c1a7 (HEAD -> feature/busqueda) HEAD@{0}: commit (amend): feat(busqueda): filtrar por título
4b8a2f3 HEAD@{1}: commit: feat(busqueda): filtrar por titulo
1a2b3c4 HEAD@{2}: checkout: moving from main to feature/busqueda

4b8a2f3 (antes-del-amend) feat(busqueda): filtrar por titulo
Nada se ha perdido todavía

El commit viejo no está «muerto»: está inalcanzable desde las ramas, pero el reflog lo referencia. Por eso las recuperaciones funcionan días después. Lo que no existe es una copia en el remoto si nunca lo empujaste.

4 · Ejemplo real

Escenario: tienes un PR abierto con feature/pagos. Rebasas para limpiar la historia y, cuando vas a publicar, un compañero ya había empujado una corrección sobre la versión anterior de la rama. El --force-with-lease hace exactamente lo que debe: negarse.

git push --force-with-lease origin feature/pagos
To ../remoto.git
 ! [rejected]        feature/pagos -> feature/pagos (stale info)
error: failed to push some refs to '../remoto.git'

No insistas con --force. Investiga qué hay en el remoto:

git fetch origin
git log --oneline feature/pagos..origin/feature/pagos
a4d9e21 fix(pagos): validar importe cero

Tu compañero añadió un commit que tú no tienes. La solución correcta es integrarlo, no borrarlo:

git rebase origin/feature/pagos
# resuelve conflictos si los hay
git push --force-with-lease origin feature/pagos
+ 7e2b9c4...8f1a3d6 feature/pagos -> feature/pagos (forced update)

Ahora la rama contiene tu historia limpia y el trabajo del compañero. El lease volvió a comprobar que nadie más había empujado entre tu fetch y tu push.

Qué habría pasado con --force

ANTES DEL FORCE

    ...───X───Y   origin/feature/pagos   (Y = commit de tu compañero)
             \
              Z   tu rama local reescrita

    git push --force origin feature/pagos

DESPUÉS

    ...───X───Z   origin/feature/pagos

    Y ya no es alcanzable desde ninguna rama del remoto.
    Tu compañero lo tiene en su local y en su reflog,
    pero el PR y el CI ya no lo ven. Si además borra su
    clon, se pierde de verdad.

El commit Y no desaparece de la faz de la Tierra: sigue en el clon de quien lo creó y, si el servidor conserva reflogs, quizá allí también. Pero la referencia que lo hacía visible se ha movido, y recuperarlo exige que alguien lo tenga y sepa qué buscar. Ese «alguien» no siempre existe.

Lo importante no es el output, es el orden

Fíjate en la secuencia: fetch → inspeccionar → integrar → publicar con lease. El force no es el primer paso, es el último, y solo después de saber qué hay al otro lado. Cualquier flujo que empiece por --force está apostando, no decidiendo.

6 · Errores habituales

1. --force sobre main

Mal — borrar la historia compartida 
git switch main
git reset --hard HEAD~2
git push --force origin main
# dos commits publicados dejan de estar en main
Bien — revertir sin reescribir 
git switch main
git revert --no-edit HEAD~1 HEAD
git push origin main
# historia nueva que deshace, sin borrar nada

main es la referencia común de todo el equipo y de la CI. Reescribirla invalida clones, PRs y builds. Si el commit contiene un secreto, la solución no es un force: es rotar la credencial y seguir el procedimiento de la organización (la reescritura masiva se trata aparte, nunca como receta casera).

2. Confundir --force-with-lease con un seguro total

Mal — fiarse tras un fetch automático 
git fetch --all           # tu origin/feature ya incluye el commit ajeno
git rebase main
git push --force-with-lease origin feature   # el lease lo acepta y lo borra
Bien — integrar lo que acabas de bajar 
git fetch origin
git log --oneline HEAD..origin/feature
git rebase origin/feature      # integra el commit ajeno
git push --force-with-lease origin feature

El lease protege contra cambios que no has visto. Si acabas de bajar el cambio y decides ignorarlo, el lease no tiene nada que objetar: tú eres quien está borrando trabajo conscientemente. El flag no sustituye a mirar el log.

3. Recuperar «a lo bruto» después de un force

Mal — resetear sin localizar el commit 
# "he perdido mi rama, vuelvo a empezar"
git switch main
git branch -D feature/pagos
# se abandona trabajo que estaba recuperable
Bien — buscar en el reflog antes de rendirse 
git reflog --date=iso | head -20
git switch -c rescate/pagos <hash>
git log --oneline -5 rescate/pagos
# comparar, recuperar lo que valga y seguir

Un force no borra objetos de tu clon: mueve referencias. Antes de dar algo por perdido, busca el hash en el reflog, en el de la rama (git reflog show feature/pagos) o en git fsck --lost-found. Casi siempre está.

7 · Ejercicio guiado

Objetivo: reproducir un force push peligroso en un remoto local, ver cómo --force-with-lease lo impide y recuperar el commit desde el reflog.

Escenario: dos clones del mismo repositorio bare. En el clon A reescribes la rama; en el clon B tu compañero ya había empujado.

  1. Crea el remoto y dos clones. 
    git init --bare remoto.git
git clone remoto.git clon-a
git clone remoto.git clon-b

cd clon-a
printf 'uno\n' > notas.md
git add notas.md
git commit -m "feat: notas"
git push -u origin main
  2. El compañero (clon B) añade un commit y lo publica. 
    cd ../clon-b
git pull
printf 'dos\n' >> notas.md
git commit -am "fix: añadir dos"
git push
  3. Tú (clon A) reescribes sin haber bajado ese commit. 
    cd ../clon-a
git commit --amend -m "feat: notas (mensaje corregido)"
git push --force-with-lease origin main

    Debe fallar con stale info: tu origin/main no incluye el commit de B.

  4. Inspecciona e integra. 
    git fetch origin
git log --oneline HEAD..origin/main
git rebase origin/main
git push --force-with-lease origin main
  5. Comprueba en el clon B que el commit sigue ahí. 
    cd ../clon-b
git fetch
git log --oneline origin/main -3
Solución resuelta

Salida esperada del paso 3 (el lease protege):

To ../remoto.git
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to '../remoto.git'

Y del paso 5, ya con todo integrado:

* 3f9a1c2 (origin/main) feat: notas (mensaje corregido)
* 8b2d4e6 fix: añadir dos
* 1a2b3c4 feat: notas

El commit del compañero sigue en la historia: no se ha perdido nada. Si en el paso 3 hubieras usado git push --force, el push habría funcionado y 8b2d4e6 habría dejado de estar en origin/main; en el clon B aún podrías recuperarlo con git reflog, pero el PR y la CI ya no lo verían.

8 · Reto

Reto

En el escenario del ejercicio, un compañero hace git push --force origin main por error y elimina tu commit 8b2d4e6 del remoto. Tú conservas tu clon con ese commit en el reflog. No puedes usar --force ni --force-with-lease sobre main (la rama está protegida y, además, no es la solución correcta).

Diseña y ejecuta un plan que devuelva el contenido de 8b2d4e6 a origin/main sin reescribir la historia publicada, demuestra con git log --oneline --graph que la historia es lineal y que el commit original sigue siendo alcanzable, y explica qué habrías perdido si el único clon con ese commit hubiera sido el del compañero que forzó.

Pista: tu commit está en el reflog aunque la rama ya no lo alcance; hay una forma de volver a introducir su cambio como un commit nuevo sin tocar el pasado. Piensa en cherry-pick, en una rama temporal y en un merge fast-forward; y ten claro por qué el remoto bare no conserva un reflog por defecto.

9 · Resumen

  • El hash cubre árbol, padres, autor, committer, fechas y mensaje: cualquier cambio genera un commit nuevo y arrastra a sus descendientes.
  • Un push normal solo acepta fast-forward; por eso una historia reescrita es rechazada.
  • --force sobrescribe sin comprobar nada. --force-with-lease solo si el remoto sigue donde tú lo viste.
  • El lease depende de tu último fetch: fija el valor esperado o usa --force-if-includes en casos delicados.
  • Nunca reescribas lo que otros ya bajaron. main se deshace con revert, no con force.
  • El reflog es local, caduca y no se clona, pero recupera rebases, resets y amends durante días. Una rama backup/… es la red que tú controlas.

10 · Preguntas frecuentes

¿--force-with-lease es siempre seguro?

No. Protege contra cambios que no has visto, pero si acabas de hacer fetch y decides ignorar lo que hay, el lease te deja sobrescribirlo. Tampoco te protege de reescribir una rama que otros usan aunque no hayan empujado. Es una mejora enorme frente a --force, no un permiso para reescribir cualquier cosa.

¿Puedo recuperar un commit borrado del remoto con un force push?

A veces. El commit sigue en los clones que lo tuvieron (reflog local) y, si el servidor conserva reflogs o ejecuta una retención, también allí. Un repositorio bare no mantiene reflogs por defecto, así que no cuentes con el servidor como copia. La recuperación fiable es la de alguien que tenga el commit en su clon. Por eso el force sobre ramas compartidas es tan caro: la copia de seguridad eres tú.

¿Cuánto dura el reflog?

Por defecto, 90 días para entradas alcanzables y 30 para inalcanzables (gc.reflogExpire y gc.reflogExpireUnreachable). Además, el recolector puede eliminar objetos inalcanzables tras un periodo de gracia. En la práctica: si detectas la pérdida el mismo día, casi seguro que lo recuperas; si han pasado meses y has hecho limpiezas, puede que no. Actúa pronto.

¿Por qué no reescribir main aunque sea mi repositorio personal?

Si de verdad es solo tuyo y nadie lo clona, puedes hacer lo que quieras. El problema es que «personal» cambia rápido: un fork, un colaborador, una CI que cachea el repo, un despliegue que referencia un SHA. En cuanto hay un segundo consumidor, la historia es un contrato. La regla de no reescribir main es una convención prudente, no una limitación técnica de Git.

¿Qué hago si ya he forzado y alguien había trabajo encima?

Primero, parar y avisar. Localiza el commit perdido en el reflog del compañero o en tu propio reflog si lo tenías. Crea una rama de rescate desde ese hash, verifica su contenido y vuelve a integrarlo con un commit normal o un merge; después, cada persona afectada debe alinear su rama con git fetch y git reset --hard origin/<rama> solo si no tiene trabajo local sin guardar. Documenta qué pasó: el incidente se repetirá si el equipo no cambia el hábito.
