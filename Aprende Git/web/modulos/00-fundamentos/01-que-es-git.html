Qué es Git

Módulo 0 · Fundamentos 🕐 30 minutos

1 · Introducción

Has escrito git add ., git commit -m "cambios" y git push cientos de veces. Funciona… hasta que un merge se tuerce, aparece un commit que no debería estar ahí o alguien pregunta «¿por qué se borró esta línea?». En ese momento la receta deja de servir, porque no sabes qué está tocando cada comando.

Git no es una carpeta con copias ni una nube que sincroniza archivos. Es una base de datos de objetos direccionada por contenido, con un grafo de commits encima. Todo lo demás —ramas, merges, rebase, reset, reflog— son operaciones sobre ese grafo. Entender esa frase es la diferencia entre memorizar comandos y poder razonar sobre ellos.

En esta lección veremos qué problema resuelve un sistema de control de versiones distribuido, qué guarda Git exactamente, qué no es Git (aunque se lo confunda a diario) y por qué su modelo interno condiciona la forma en que se deshace y se comparte el trabajo.

Por qué existe esta lección

El resto del curso asume que un commit es una foto del proyecto y que cada rama es un puntero. Si esos dos conceptos no están claros, reset --hard parece magia peligrosa, rebase parece brujería y los conflictos parecen castigos. Con el modelo claro, cada comando se vuelve predecible.

2 · Teoría

El problema: guardar versiones a mano no escala

Antes de los VCS, la estrategia era copiar carpetas. Todos hemos hecho algo así:

proyecto/
├── notas_v1.md
├── notas_v2.md
├── notas_final.md
├── notas_final_buena.md
├── notas_final_buena_2.md
└── notas_FINAL_ahora_si.md

Funciona para una persona durante una tarde. En cuanto hay dos personas o dos semanas de trabajo, aparecen problemas que ninguna convención de nombres resuelve:

ProblemaQué pasa con copias manuales
¿Cuál es la versión buena?Nadie lo sabe; el nombre miente y el más reciente no siempre es el correcto.
¿Qué cambió y por qué?Hay que comparar archivos a mano; el motivo se perdió en una conversación.
¿Quién cambió esta línea?Imposible saberlo con certeza.
Volver a un estado anteriorHay que recordar qué carpeta era y copiarla encima.
Trabajo en paraleloDos personas pisan el mismo archivo sin aviso.
Espacio y ruidoDiez copias completas de un proyecto que apenas cambió.

Un sistema de control de versiones (VCS) resuelve esos problemas guardando el estado del proyecto en el tiempo, con autor, fecha y motivo, y permitiendo volver, comparar y fusionar de forma fiable.

Centralizado frente a distribuido

Los VCS clásicos como CVS o Subversion eran centralizados: había un servidor con el historial y cada cliente pedía archivos o confirmaba cambios contra él. Sin red no había historia ni commits, y el servidor era un punto único de fallo.

CENTRALIZADO                          DISTRIBUIDO

        +------------------+                  +--------+   +--------+   +--------+
        |    servidor      |                  | clone  |   | clone  |   | clone  |
        | historial único  |                  |  .git  |   |  .git  |   |  .git  |
        +--------+---------+                  +---+----+   +---+----+   +---+----+
                 |                                |            |            |
        +--------+--------+               cada copia tiene TODA la historia
        |        |        |
      dev1     dev2     dev3             commit offline, ramas locales, merges sin red

Git es distribuido: al clonar un repositorio te llevas todos los commits, no solo la última versión. Eso tiene consecuencias muy concretas:

  • git log, git diff, git commit y git switch funcionan sin conexión.
  • Cada clon es una copia completa del historial: no hay una copia «principal» a nivel técnico, aunque por convención se use una (origin).
  • Las ramas son baratísimas, porque no copian archivos: solo apuntan a un commit.
  • Solo necesitan red los comandos que hablan con otro repositorio: fetch, pull y push.

Distribuido no significa sin servidor

En un equipo casi siempre hay un repositorio compartido (GitHub, GitLab, un servidor propio). «Distribuido» describe el modelo de datos: tu clon tiene la historia completa y puedes trabajar sin él. El servidor es una convención de colaboración, no un requisito para hacer commits.

Qué guarda Git: fotos, no diferencias

Esta es la idea que más cuesta desaprender. Mucha gente cree que un commit guarda «las líneas que cambiaron». No es así: un commit apunta a un árbol completo con el estado de todos los archivos en ese instante. Si un archivo no cambió, el árbol reutiliza exactamente el mismo objeto.

commit A              commit B              commit C
   |                     |                     |
   v                     v                     v
 tree A                tree B                tree C
 /      \              /      \              /      \
blob1   blob2        blob1   blob3        blob1   blob4
(nuevo) (nuevo)      (reutilizado)         (reutilizado)

blob1 se guarda UNA sola vez: su contenido no cambió y su hash es el mismo.

Por eso se dice que Git guarda snapshots (fotos) y no diffs. Los diffs que ves con git diff o git show se calculan en el momento comparando dos árboles; no están almacenados como tales. Es una decisión de diseño: recuperar una versión es copiar un árbol, no reproducir una cadena de parches.

Matiz de implementación

Internamente, Git comprime objetos sueltos con zlib y puede agruparlos en packfiles usando deltas para ahorrar espacio. Eso es un detalle de almacenamiento, no del modelo: tú sigues razonando con fotos completas. Lo veremos en la lección 3.

Direccionada por contenido: el hash manda

Cada objeto de Git se identifica por el hash de su contenido (SHA-1 por defecto, con soporte opcional de SHA-256). Ese hash es a la vez nombre y verificación de integridad:

  • Mismo contenido ⇒ mismo hash ⇒ un solo objeto almacenado. Dos archivos idénticos comparten blob.
  • Un solo byte distinto ⇒ hash distinto ⇒ objeto nuevo.
  • Si alguien altera un objeto, el hash deja de cuadrar y Git lo detecta (git fsck).
  • El hash de un commit incluye su árbol, sus padres, autor, fecha y mensaje. Cambiar cualquiera de ellos cambia el hash y, en cascada, el de todos sus descendientes.

Esa última propiedad es la razón de que un commit sea inmutable: no se «edita», se crea otro. Y es la razón de que reescribir historia sea seguro solo cuando nadie ha construido trabajo encima.

Qué NO es Git

Git es un backupEs un historial local. Si borras la carpeta o se rompe el disco, se pierde todo. Un backup vive en otro medio y se prueba.

Por qué importa el modelo

Porque casi todos los comandos de Git mueven un puntero o crean un objeto. Nada más. Cuando lo ves así, dejas de memorizar:

  • git add escribe en el índice (la foto propuesta).
  • git commit crea un objeto commit y mueve la rama actual.
  • git switch mueve HEAD y actualiza el directorio de trabajo.
  • git reset mueve la rama y, según el modo, también el índice y el disco.
  • git revert crea un commit nuevo que deshace otro, sin borrar historia.
  • git rebase crea commits nuevos (hashes nuevos) sobre otra base.

Y explica por qué existen varias formas de «deshacer»: cada una responde a una pregunta distinta. No es que Git sea complicado; es que el espacio de estados tiene más de una dimensión.

Un poco de historia

Git nació en 2005. El kernel de Linux usaba BitKeeper, que dejó de ser gratuito para el proyecto; Linus Torvalds escribió su propio VCS en unas semanas, con tres objetivos: velocidad, diseño sencillo y soporte fuerte para desarrollo no lineal. En diciembre de 2005 salió Git 1.0. La arquitectura de objetos que veremos en la lección 3 viene de ese diseño original y apenas ha cambiado.

3 · Ejemplo mínimo

Vamos a comprobar con nuestras manos que Git guarda contenido, no nombres de archivo ni diferencias. Crea un repositorio con dos archivos distintos que contienen exactamente lo mismo:

mkdir experimento
cd experimento
git init -b main

printf 'hola\n' > saludo.txt
git add saludo.txt
git commit -m "feat: saludar"

printf 'hola\n' > copia.txt
git add copia.txt
git commit -m "feat: duplicar saludo"

Ahora pregunta a Git por el objeto que respalda cada archivo en el último commit:

git rev-parse HEAD:saludo.txt
git rev-parse HEAD:copia.txt

5c1b14949828006ed75a3e8858957f86a2f7e2eb
5c1b14949828006ed75a3e8858957f86a2f7e2eb

El mismo hash. Los nombres son distintos, pero el blob es el mismo objeto porque el contenido es idéntico. El nombre vive en el árbol (tree), no en el contenido. Y fíjate en el detalle importante: el segundo commit no guardó otra copia de «hola»; reutilizó el objeto existente.

Comprueba también que la historia es local y que no ha hecho falta ningún servidor:

git log --oneline

a7c9f21 (HEAD -> main) feat: duplicar saludo
3b1e8d4 feat: saludar

Dos commits, un solo blob, cero red. Ese es el corazón del modelo.

4 · Ejemplo real

El hilo conductor del curso es taller, un repositorio de notas que crecerá con nosotros: commits, un .gitignore, una rama feature/busqueda, un bug escondido y una release final. Lo creamos en la siguiente lección, pero así se verá su historia al final del módulo 1:

$ git log --oneline --graph --decorate
* 9f3c2ab (HEAD -> main) docs: documentar el flujo de trabajo
* 4d81e07 chore: ignorar artefactos de build
* 2ee7587 docs: crear notas del taller

Cada línea es una foto completa del proyecto. Entre 2ee7587 y 4d81e07 solo cambió .gitignore; el resto de blobs se reutilizan. Si mañana hay que volver a 2ee7587, Git no «desaplica» dos parches: coloca el árbol de esa foto en el directorio de trabajo.

La consecuencia práctica más útil para tu día a día:

SituaciónQué permite el modelo distribuido
Estás en un avión sin wifiCrear ramas, commits y merges locales; solo push espera.
Quieres probar una idea arriesgadaUna rama es un puntero de 41 bytes, no una copia del proyecto.
Necesitas comparar con la versión de hace un mesgit diff HEAD~20 HEAD, sin red y sin servidor.
Un compañero borró una rama por errorSu clon puede conservar los commits; el tuyo también.
El servidor se caePuedes seguir trabajando; solo se posponen los intercambios.

La analogía del cuaderno

Un VCS centralizado es un cuaderno único que vive en la biblioteca: para escribir, tienes que ir allí. Git es un cuaderno que fotocopias completo cada vez que lo tomas prestado; puedes escribir en tu copia, y al devolverlo pones en común las páginas nuevas. Nadie te quita las tuyas si la biblioteca cierra.

6 · Errores habituales

1. «Git es GitHub»

Mal — creer que sin cuenta no hay Git 
# ❌ "No puedo usar Git hasta crear una cuenta en GitHub"
# ❌ "git commit sube el código a GitHub"
Bien — Git es local; la forja es opcional 
git init -b main          # repositorio local, sin red y sin cuenta
git add .
git commit -m "feat: primer commit"
git log --oneline         # todo esto funciona offline

GitHub añade colaboración, revisión y CI, pero no es necesario para aprender ni para usar Git. En este curso el remoto de práctica será un repositorio bare local.

2. «Git guarda las diferencias»

Mal — imaginar el commit como un parche 
commit = "se añadieron 3 líneas a notas.md"   ❌
Bien — el commit apunta a un árbol completo 
git cat-file -p HEAD

tree 801e45332eddf6a31000c9c885c163b5590a9110
author Ana Torres <ana@ejemplo.com> 1792253821 +0200
committer Ana Torres <ana@ejemplo.com> 1792253821 +0200

feat: saludar

Lo que ves es un puntero al árbol, no una lista de cambios. El diff se calcula al vuelo comparando árboles.

3. «Hacer commit es publicar»

Mal — confundir guardar con compartir 
git commit -m "feat: algo"
# ❌ "Ya lo ve mi equipo"  -> nadie lo ve todavía
Bien — publicar es un paso explícito 
git commit -m "feat: algo"
git push origin main    # solo ahora sale de tu máquina

Esta distinción es la que decide si puedes reescribir un commit o no. Mientras es local, es tu borrador; cuando está publicado, es historia compartida.

4. «Una rama es una copia de la carpeta»

Mal — esperar que crear una rama duplique el proyecto 
# ❌ "Crear una rama tardará y ocupará el doble"
Bien — una rama es un puntero a un commit 
git switch -c feature/busqueda   # instantáneo: escribe una referencia

No se copian archivos. Cambiar de rama actualiza el directorio de trabajo para que coincida con el árbol del commit apuntado.

5. «Git es mi backup»

Mal — un solo disco, un solo historial 
rm -rf .git      # ❌ se va TODA la historia, no solo un archivo
Bien — historial local + copia remota + backup probado 
git push origin main    # copia en otro lugar
# y además un backup real del repositorio, con restauración probada

Git protege contra «he borrado una línea», no contra «he formateado el disco».

7 · Ejercicio guiado

Objetivo: comprobar que el contenido se guarda una sola vez, que los nombres viven en el árbol y que todo el flujo funciona sin red.

  1. Crea el repositorio y configura tu identidad solo para él: 
    mkdir laboratorio-00
cd laboratorio-00
git init -b main
git config user.name "Ana Torres"
git config user.email "ana@ejemplo.com"

    Salida esperada: Initialized empty Git repository in …/.git/.

  2. Guarda un archivo y confirma: 
    printf 'hola\n' > saludo.txt
git add saludo.txt
git commit -m "feat: saludar"

    [main (root-commit) 3b1e8d4] feat: saludar
 1 file changed, 1 insertion(+)
 create mode 100644 saludo.txt
  3. Duplica el contenido con otro nombre y confirma de nuevo: 
    printf 'hola\n' > copia.txt
git add copia.txt
git commit -m "feat: duplicar saludo"
  4. Compara los objetos que respaldan ambos archivos: 
    git rev-parse HEAD:saludo.txt
git rev-parse HEAD:copia.txt

    5c1b14949828006ed75a3e8858957f86a2f7e2eb
5c1b14949828006ed75a3e8858957f86a2f7e2eb

    El hash es idéntico: mismo contenido, mismo objeto. Los nombres distintos están en el árbol.

  5. Verifica el tipo de objeto y la historia: 
    git cat-file -t 5c1b149
git log --oneline

    blob
a7c9f21 (HEAD -> main) feat: duplicar saludo
3b1e8d4 feat: saludar
  6. Desconecta la red y crea un tercer commit: edita saludo.txt, guarda, y ejecuta git add . && git commit -m "docs: ampliar saludo". Debe funcionar igual: no hay ninguna llamada de red en el flujo local.

Comprobación final

Ejecuta git count-objects -v. Verás más objetos que archivos: hay blobs, árboles y commits. La cifra exacta depende de cuántos commits hayas hecho.

8 · Reto

🎯 Un commit que no cambia nada

Modifica un archivo, guárdalo, y después devuélvelo exactamente a su contenido anterior. Ejecuta git status y git commit -m "docs: sin cambios". Explica por qué Git se niega a crear el commit y qué diferencia hay entre esa situación y un commit creado con git commit --allow-empty.

Después, con --allow-empty, inspecciona el commit con git cat-file -p HEAD. ¿Qué apunta su árbol? ¿Tiene padre? ¿Qué crees que cambiaría si el commit tuviera el mismo árbol que su padre?

Pista: compara git rev-parse HEAD^{tree} con git rev-parse HEAD~1^{tree}. No hace falta que escribas la respuesta: compruébala con los hashes.

9 · Resumen

  • Git es un VCS distribuido: cada clon tiene la historia completa y puede trabajar sin red.
  • Un commit es una foto (un árbol completo), no un parche; los diffs se calculan al comparar.
  • Los objetos se identifican por el hash de su contenido: mismo contenido, mismo objeto; contenido distinto, objeto distinto.
  • Los nombres viven en los árboles, no en los blobs.
  • Git no es GitHub, ni un backup, ni un sistema de sincronización, ni una herramienta de despliegue.
  • Entender el modelo convierte los comandos en operaciones predecibles sobre punteros y objetos.
ComandoQué hace
git init -b mainCrea un repositorio local con la rama inicial main
git add <archivo>Copia el contenido al índice (la próxima foto)
git commit -m "…"Crea un commit a partir del índice y mueve la rama
git log --onelineMuestra la historia resumida, la más reciente primero

10 · Preguntas frecuentes

¿Puedo usar Git sin internet para siempre?

Sí, para trabajar en local: init, add, commit, switch, merge, rebase, log, diff y reset no necesitan red. Solo fetch, pull, push y clone hablan con otro repositorio. Eso sí: sin remoto, tu historial vive en un único sitio.

Si Git guarda fotos completas, ¿no ocupa un espacio enorme?

No, porque deduplica por contenido: los archivos que no cambian se comparten entre commits. Además comprime los objetos y los empaqueta en packfiles, donde sí aplica compresión por deltas. La foto es el modelo mental; el almacenamiento está optimizado.

¿Qué diferencia hay entre Git y GitHub entonces?

Git es el motor: el formato de objetos, la CLI y el protocolo. GitHub es un servicio que aloja repositorios Git y añade revisión de código, issues, permisos y automatización. Puedes cambiar de forja sin cambiar de Git; de hecho, el mismo repositorio puede tener varios remotos.

¿Por qué se dice que un commit es inmutable si puedo hacer commit --amend?

Porque --amend no modifica el commit anterior: crea uno nuevo con otro hash y mueve la rama. El antiguo sigue existiendo en .git hasta que el recolector lo elimine, y reflog te permite recuperarlo. Lo veremos en el módulo 4.

¿Necesito entender los hashes para usar Git a diario?

Para el 90 % del trabajo basta con saber que identifican contenido y que cambian cuando algo cambia. Pero cuando algo se rompe —un commit perdido, una rama que no avanza, un conflicto raro— los hashes son la forma de nombrar estados exactos. Por eso el curso insiste en ellos.
