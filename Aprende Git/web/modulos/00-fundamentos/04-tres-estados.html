Los tres estados

Módulo 0 · Fundamentos 🕐 30 minutos

1 · Introducción

¿Por qué existe git add? Parece un paso intermedio inútil: ya tengo el archivo en disco, ¿para qué «añadirlo» otra vez antes de confirmarlo? La respuesta es que Git no tiene dos zonas de trabajo, tiene tres: el directorio de trabajo, el índice y el repositorio (con HEAD señalando el último commit).

El índice —también llamado staging area— es lo que convierte a Git en una herramienta precisa: te permite preparar exactamente la foto que quieres confirmar, aunque tengas veinte cambios a medias. Esta lección explica cada zona, qué compara cada comando y cómo leer git status, tanto en su forma larga como en la corta -s, cuyas dos columnas son un idioma en sí mismo.

Por qué existe esta lección

El 90 % de los sustos con Git vienen de no saber en qué zona está un cambio. «¿Por qué mi commit no incluyó ese archivo?», «¿por qué sigue apareciendo modificado si ya lo añadí?»: las dos tienen respuesta en el índice. Y el módulo 2 completo (deshacer) es, literalmente, elegir qué zona revertir.

2 · Teoría

Las tres zonas

   DIRECTORIO DE TRABAJO         ÍNDICE (staging)            REPOSITORIO
   (los archivos que editas)     (.git/index)               (.git/objects + refs)

        editas aquí                                             HEAD apunta aquí
             |                                                       |
             |  git add                                     |
             +------------------------>  preparas la próxima foto  |
             |                                                       |
             |                              git commit               |
             +-----------------------------------------> commit nuevo (rama avanza)

             <--- git restore <archivo> ----+                            |
                                           <--- git restore --staged ---+ (módulo 2)
ZonaDónde viveQué es
Directorio de trabajo Tu carpeta del proyecto Los archivos tal como están en disco ahora mismo. Git los compara con el índice para saber qué cambió.
Índice / staging .git/index Una lista de rutas con el hash del blob y sus metadatos. Es la foto propuesta, lo que entrará en el próximo commit.
Repositorio / HEAD .git/objects y .git/refs Los commits ya confirmados. HEAD apunta a la rama actual, que apunta al último commit: la última foto confirmada.

La analogía de la cámara

El directorio de trabajo es la escena: está en movimiento. El índice es el encuadre: eliges qué entra en la foto, e incluso puedes cambiar elementos sin mover la escena. El commit es la foto revelada y archivada. git add no «guarda el archivo»: congela su contenido en el encuadre.

El índice no es un diff: es una lista de contenido

Cuando ejecutas git add archivo.txt, Git calcula el blob del archivo en ese instante y escribe su hash en el índice. Lo importante: el índice guarda una copia del contenido, no una marca de «este archivo va en el commit». Si edites el archivo después, el índice conserva la versión anterior y el archivo pasa a estar «modificado» otra vez.

git ls-files -s

100644 27a58d6f5b9c3bf2448ea43822380ef8aaca69da 0	a.txt
100644 cbfb92d8506e74c5ca59acbcd3ef3381406a4cb2 0	b.txt
100644 a1db5b3b7e6adb2b819c02762992567810cfefd3 0	c.txt

Cada línea es modo, hash del blob, número de etapa y ruta. El 0 es la etapa normal; durante un conflicto de merge aparecen las etapas 1, 2 y 3 (base, «nuestro», «suyo»). Ese comando es la mejor prueba de que el índice es contenido, no diffs.

Qué compara cada comando

Hay tres zonas, así que hay tres comparaciones posibles. Casi todos los «diffs que no aparecen» se deben a confundirlas:

ComandoComparaResponde a
git diffTrabajo ↔ índice¿Qué he cambiado y aún no he preparado?
git diff --stagedÍndice ↔ HEAD¿Qué entraría si hiciera commit ahora?
git diff HEADTrabajo ↔ HEAD¿Qué ha cambiado desde el último commit, esté preparado o no?
git statusLas tres a la vez (resumido)¿En qué zona está cada archivo?

El módulo 1 dedica una lección entera a diff. Aquí solo necesitas la correspondencia con las zonas.

Anatomía de git status

La salida larga agrupa los archivos por zona:

On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   c.txt

Changes not staged for commit:
  (use "git add/rm <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt
	deleted:    b.txt
	modified:   c.txt

Untracked files:
  (use "git add <file>" to include in what will be committed)
	nuevo.txt

Tres bloques: lo que entrará en el commit, lo que está modificado pero fuera del índice, y lo que Git ni conoce. La sección Changes to be committed es el índice frente a HEAD; la sección not staged es el trabajo frente al índice.

La versión corta: git status -s

Con -s (o --short) cada archivo ocupa una línea y muestra dos columnas: la primera es el estado en el índice, la segunda el estado en el directorio de trabajo.

 M a.txt
 D b.txt
AM c.txt
?? nuevo.txt
CódigoSignificado
??Archivo sin seguimiento (untracked): Git no lo conoce todavía.
AAñadido al índice (staged como nuevo).
MModificado. En la primera columna: preparado; en la segunda: sin preparar.
DBorrado. Misma lógica de columnas.
RRenombrado (se detecta por similitud al comparar).
CCopiado (con status.renames configurado).
USin fusionar: hay un conflicto pendiente.
!!Ignorado (solo aparece con --ignored).

Leído así, AM c.txt significa: hay una versión de c.txt preparada (A en la columna izquierda) y además la versión de disco está modificada desde entonces (M a la derecha).  M a.txt (espacio + M) significa: hay cambios sin preparar; nada en el índice. Y M  a.txt sería lo contrario: todo listo. Los dos espacios y su posición son información, no formato.

git status -sb

Con -b añade la rama actual y su relación con el remoto: ## main...origin/main [ahead 1]. Es la vista que más gente usa a diario, y la base de un buen prompt de shell.

El ciclo de vida de un archivo

 untracked ──git add──> staged ──git commit──> committed (sin cambios)
     ^                     |                        |
     |                     | git restore --staged   | editas el archivo
     |                     v                        v
     +──── git rm ────  unstaged <────────────── modified

Un archivo puede estar en varias casillas a la vez (staged en una versión y modificado en otra), y eso es exactamente lo que codifica AM.

3 · Ejemplo mínimo

El recorrido completo de un archivo por las tres zonas:

mkdir estados-demo && cd estados-demo
git init -b main
printf 'uno\n' > notas.md

git status -s          # todavía no lo conoce Git
git add notas.md
git status -s          # preparado
git commit -m "docs: crear notas"
git status -s          # limpio: no imprime nada
?? notas.md
A  notas.md

Fíjate en las dos columnas de A  notas.md: A está en la izquierda (índice) y la derecha está en blanco (el disco coincide con lo preparado). Tras el commit, git status -s no imprime nada: el disco, el índice y HEAD coinciden.

Ahora modifica el archivo y mira cómo aparece el cambio a la derecha:

printf 'uno\ndos\n' > notas.md
git status -s
git status
 M notas.md
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>" to discard changes in working directory)
	modified:   notas.md

no changes added to commit (use "git add" and/or "git commit -a")

El espacio inicial lo dice todo: hay una diferencia entre el disco y el índice, pero el índice está intacto. Nada de eso entraría en un commit todavía.

4 · Ejemplo real

Ana trabaja en el taller y toca cuatro archivos a la vez. En lugar de preparar todo a ciegas, deja que status le cuente qué hay en cada zona:

git status

On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   c.txt

Changes not staged for commit:
  (use "git add/rm <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt
	deleted:    b.txt
	modified:   c.txt

Untracked files:
  (use "git add <file>" to include in what will be committed)
	nuevo.txt

Traducción: c.txt es nuevo y está preparado; a.txt tiene cambios fuera del índice; b.txt se ha borrado del disco pero no del índice; nuevo.txt ni siquiera está bajo seguimiento. Ahora la versión corta:

git status -s
git status -sb

 M a.txt
 D b.txt
AM c.txt
?? nuevo.txt
## main
 M a.txt
 D b.txt
AM c.txt
?? nuevo.txt

Lo más interesante es AM c.txt: Ana hizo git add c.txt y después lo volvió a editar. La columna izquierda (A) es la versión preparada; la derecha (M) avisa de que el disco ya no coincide con ella. Si hiciera git commit ahora, se guardaría la primera versión, no la última. Para arreglarlo tiene dos opciones: git add c.txt otra vez (actualiza el índice con lo último) o commitear así y guardar la segunda edición en otro commit.

La foto preparada es exactamente esto:

git ls-files -s

100644 27a58d6f5b9c3bf2448ea43822380ef8aaca69da 0	a.txt
100644 cbfb92d8506e74c5ca59acbcd3ef3381406a4cb2 0	b.txt
100644 a1db5b3b7e6adb2b819c02762992567810cfefd3 0	c.txt

El índice de c.txt apunta al blob a1db5b3, y el archivo en disco ya es otro. Eso es el M de la segunda columna. Y b.txt sigue en el índice (borrarlo del disco no lo saca): para que el borrado entre en el commit hay que prepararlo con git add -A o git rm b.txt.

«¿Por qué mi commit no incluyó ese cambio?»

Porque git commit confirma el índice, no el directorio de trabajo. Si edites después de git add, esa edición queda fuera. Es la causa número uno de archivos «que faltan» en un commit.

5 · Buenas prácticas

HazEvitaPor qué
Preparar los cambios de forma intencionada (git add <ruta>) git add . por costumbre en la raíz del proyecto Evita arrastrar archivos temporales, binarios o secretos que no querías versionar.

6 · Errores habituales

1. Creer que git add sube el archivo

Mal — «ya está en el servidor» 
git add notas.md
# ❌ Nada ha salido de tu máquina: solo se ha escrito .git/index
Bien — add escribe en el índice; push publica 
git add notas.md      # trabajo -> índice
git commit -m "…"     # índice -> repositorio local
git push              # repositorio local -> remoto

Tres pasos, tres destinos distintos. add nunca toca la red.

2. Creer que el commit incluye todo lo modificado

Mal — editar después de add y esperar que entre 
git add c.txt
printf 'tres\n' >> c.txt
git commit -m "docs: actualizar c"
# ❌ En el commit va la primera versión; 'tres' sigue sin preparar
Bien — el commit usa el índice, no el disco 
git add c.txt             # vuelve a preparar la versión final
git diff --staged         # revisa lo que realmente entrará
git commit -m "docs: actualizar c"

Después del commit, git status seguirá mostrando M c.txt si quedó algo fuera. Esa es la señal.

3. Creer que el índice guarda diferencias

Mal — imaginar el índice como una lista de parches 
index = "c.txt: +3 líneas"   ❌
Bien — el índice guarda hashes de blobs completos 
git ls-files -s

100644 a1db5b3b7e6adb2b819c02762992567810cfefd3 0	c.txt

Sin contenido completo en el índice no habría forma de armar el tree del commit sin releer el disco, y el disco ya no tiene esa versión.

4. Creer que git restore --staged borra los cambios

Mal — «he perdido mi trabajo» 
git restore --staged notas.md
# ❌ Miedo a haber descartado el contenido
Bien — solo baja del índice al estado modificado 
git restore --staged notas.md   # saca del índice, conserva el disco
git status -s                   # aparece como " M notas.md"
git diff                        # el contenido sigue ahí

Para descartar el contenido del disco hay que usar git restore notas.md, y eso sí destruye cambios no confirmados (módulo 2).

5. No saber leer las dos columnas de status -s

Mal — interpretar AM como un solo estado 
AM c.txt   →  "c.txt está añadido y modificado, no sé qué va al commit"   ❌
Bien — columna izquierda = índice; derecha = disco 
AM c.txt   →  índice: A (versión nueva preparada)
              disco:  M (modificado desde el add)

Con esa lectura, M ,  M y MM dejan de ser ruido y se vuelven diagnósticos.

6. Pensar que borrar un archivo del disco lo borra del repositorio

Mal — borrar con rm y commitear 
rm b.txt
git commit -m "chore: limpiar"
# ❌ Git sigue teniendo b.txt en el índice y lo restaura en el próximo checkout
Bien — registrar el borrado 
git rm b.txt          # borra del disco Y del índice
git add -A            # alternativa: prepara todo, incluidos borrados

Git rastrea contenido, no el sistema de archivos: el borrado es un cambio más y hay que prepararlo.

7 · Ejercicio guiado

Objetivo: provocar y leer el estado AM, el más incomprendido de git status.

  1. Prepara el terreno con dos commits: 
    mkdir laboratorio-estados
cd laboratorio-estados
git init -b main
printf 'uno\n' > a.txt
printf 'dos\n' > b.txt
git add .
git commit -m "chore: base"
  2. Prepara un archivo nuevo y luego edítalo: 
    printf 'tres\n' > c.txt
git add c.txt
printf 'tres\ncuatro\n' > c.txt
git status -s

    AM c.txt

    Ya tienes el estado clave: versión preparada (A) y versión en disco distinta (M).

  3. Comprueba qué entraría en el commit: 
    git diff --staged
git diff

    --staged mostrará solo la línea tres; git diff mostrará la línea cuatro pendiente. Son las dos mitades.

  4. Commitea sin volver a añadir y verifica el resultado: 
    git commit -m "feat: añadir c"
git status -s
git show HEAD:c.txt

     M c.txt
tres

    El commit guardó solo tres. La línea cuatro sigue en el disco y ahora aparece como modificación sin preparar.

  5. Confirma la segunda versión: 
    git add c.txt
git commit -m "feat: ampliar c"
git status -s

    Sin salida: el directorio de trabajo, el índice y HEAD coinciden. Estado limpio.

  6. Comprueba el índice explícitamente: 
    git ls-files -s

    Las tres rutas aparecen con etapa 0 y un hash. Ese hash es el del contenido que respalda cada archivo en el índice.

8 · Reto

🎯 Un commit con trampa

Consigue un archivo en estado MM (preparado y además modificado) y haz un commit. Explica, sin ejecutar nada aún, qué versión quedará en el commit y dónde estará la otra. Después compruébalo de tres formas: con git show HEAD:archivo, con git status y con git diff.

Segunda parte: partiendo del mismo estado, deja el repositorio con el índice idéntico a HEAD pero sin perder el contenido del disco. ¿Qué comando usas? ¿En qué zona queda el cambio después?

Pista: para la segunda parte, piensa qué hace exactamente «sacar del índice» y comprueba el resultado con git status -s y git diff a la vez. No hace falta commitear para verificarlo.

9 · Resumen

  • Git tiene tres zonas: directorio de trabajo, índice (staging) y repositorio (con HEAD).
  • git add copia contenido al índice: congela una versión, no marca un archivo.
  • git commit confirma el índice, no el disco. Si editas después de añadir, ese cambio queda fuera.
  • Las dos columnas de status -s son índice (izquierda) y disco (derecha); AM es «preparado y vuelto a modificar».
  • git ls-files -s muestra el índice real: modo, hash del blob, etapa y ruta.
  • Borrar un archivo del disco no lo quita del índice: hay que registrar el borrado (git rm, git add -A).
ComandoQué hace / qué compara
git statusEstado de cada archivo en las tres zonas
git status -sVersión corta: dos columnas por archivo
git status -sbAdemás muestra la rama y su relación con el remoto
git diffTrabajo frente a índice (lo que aún no has preparado)
git diff --stagedÍndice frente a HEAD (lo que entraría en el commit)
git diff HEADTrabajo frente a HEAD (todo lo cambiado)

10 · Preguntas frecuentes

¿Por qué Git tiene un índice en lugar de confirmar el directorio de trabajo?

Para permitir commits precisos y revisables. Puedes preparar solo parte de tus cambios, comprobar exactamente qué va a entrar (git diff --staged) y evitar arrastrar archivos temporales. Sin índice, cada commit sería «todo lo que haya en disco ahora mismo», que rara vez es una unidad lógica.

¿Qué contiene físicamente .git/index?

Un archivo binario con una entrada por ruta: modo, hash del blob, número de etapa, tamaño y datos de estado del sistema de archivos (para saber si el disco cambió). No contiene diferencias ni copias del texto: los contenidos viven como blobs en .git/objects.

¿HEAD es lo mismo que la rama main?

No. HEAD dice dónde estás; normalmente contiene ref: refs/heads/main, así que apunta a la rama, y la rama apunta al commit. Si haces git switch <commit> quedas en detached HEAD: HEAD apunta directamente a un commit y los commits nuevos no pertenecen a ninguna rama. Lo veremos en el módulo 3.

¿git add . prepara también los borrados?

Sí, desde Git 2.0. git add . y git add -A registran adiciones, modificaciones y borrados. Lo que no hace es incluir archivos ignorados: para eso hay que forzar con git add -f, y casi siempre es mala idea.

Si hago git commit -a, ¿me salto el índice?

-a prepara automáticamente los archivos ya rastreados que estén modificados o borrados, y luego commitea. No incluye archivos nuevos sin seguimiento. Es cómodo para un cambio pequeño y peligroso como hábito: te impide revisar el índice antes de confirmar.
