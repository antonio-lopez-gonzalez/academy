El modelo interno

Módulo 0 · Fundamentos 🕐 35 minutos

1 · Introducción

Dentro de .git/ no hay carpetas de versiones ni archivos de diferencias. Hay una base de datos de cuatro tipos de objetos —blob, tree, commit y tag— guardados bajo una carpeta con el nombre de su hash. Todo lo que Git hace consiste en crear objetos y leerlos.

Esta lección abre esa caja. Verás cómo se calcula un hash, qué contiene exactamente un commit, por qué el mismo contenido en dos repositorios distintos produce el mismo identificador y por qué un commit no se puede «editar». No es arqueología: cuando un commit desaparece, cuando una rama no avanza o cuando reflog te salva el día, entender objetos y refs es la diferencia entre resolverlo y dar palos de ciego.

Por qué existe esta lección

Las dos ideas que sostienen el curso viven aquí: el contenido define el nombre (hash) y un commit es inmutable porque su hash cubre todo su contenido. Con eso entiendes por qué reescribir historia crea commits nuevos, por qué amend no borra nada y por qué el mismo cambio aplicado dos veces en sitios distintos puede compartir objetos.

2 · Teoría

Cuatro tipos de objeto

Git solo almacena cuatro clases de cosas. Cada una es un archivo comprimido dentro de .git/objects/ cuyo nombre es su hash.

TipoQué guardaQué no guarda
blob El contenido binario de un archivo. No guarda el nombre, ni la ruta, ni permisos, ni la fecha.
tree Una lista de entradas: modo, tipo, hash y nombre. Es un «directorio». No guarda el contenido de los archivos; apunta a blobs y a otros trees.
commit Un tree (la foto), el/los commits padre, autor, committer, fechas y mensaje. No guarda diferencias ni una lista de archivos modificados.
tag (anotado) Un objeto que apunta a otro objeto, con nombre de etiqueta, autor, fecha y mensaje. No es un simple alias: es un objeto con contenido propio y, opcionalmente, firma GPG.

Con esas cuatro piezas se construye todo: un proyecto completo es un árbol que cuelga de un commit, y una rama es un puntero a un commit.

El hash: nombre y dirección a la vez

Git calcula el identificador de un objeto como el SHA-1 de una cabecera más su contenido. La cabecera es "<tipo> <tamaño>\0", donde \0 es un byte nulo. Para el texto hola seguido de un salto de línea:

contenido a hashear:  "blob 5\0hola\n"
                      ^^^^^^^^  ^^^^^^
                      tipo + tamaño (5 bytes: h,o,l,a,\n)

SHA-1  ->  5c1b14949828006ed75a3e8858957f86a2f7e2eb

De ahí salen las propiedades que gobiernan todo el modelo:

  • Direccionado por contenido: el nombre es el hash de lo que hay dentro. No hay un contador ni un ID aleatorio.
  • Deduplicación: dos archivos con el mismo contenido comparten un solo objeto, aunque se llamen distinto o estén en rutas distintas.
  • Integridad: si un byte cambia, el hash deja de coincidir y Git lo detecta al leerlo.
  • Reproducibilidad: el mismo contenido produce el mismo hash en cualquier máquina y en cualquier repositorio del mundo.

SHA-1 y SHA-256

SHA-1 está considerado roto para usos adversariales (colisiones calculables desde 2017). Git compensa con detección de colisiones y ofrece repositorios con SHA-256 (git init --object-format=sha256). Para el uso normal de un equipo, SHA-1 sigue funcionando; para garantías de seguridad reales se usan commits firmados. No hace falta memorizar esto: basta con saber que el hash es un identificador, no un mecanismo de autenticación.

Dónde viven los objetos

Cada objeto suelto se guarda comprimido con zlib en una ruta formada por los dos primeros caracteres del hash como carpeta y el resto como nombre de archivo:

.git/
├── HEAD                 -> "ref: refs/heads/main" (a qué rama apunta el repo)
├── config               -> configuración LOCAL (lección 2)
├── index                -> el área de preparación (lección 4)
├── objects/
│   ├── 5c/1b14949828006ed75a3e8858957f86a2f7e2eb   <- blob "hola\n"
│   ├── 80/1e45332eddf6a31000c9c885c163b5590a9110   <- tree del commit
│   ├── e3/240b9ada8c6122b242d971f6a042155983d5bc   <- un commit
│   ├── info/            -> metadatos de empaquetado
│   └── pack/            -> objetos agrupados en packfiles
└── refs/
    ├── heads/main       -> contiene el hash del último commit de main
    └── tags/v0.1        -> contiene el hash de la etiqueta

Con muchos objetos, Git los agrupa en packfiles para ahorrar espacio (ahí sí aplica compresión por deltas). El comando git gc hace esa limpieza. Pero el modelo no cambia: sigues nombrando objetos por su hash y sigues teniendo fotos completas.

Nunca edites .git/ a mano

Los objetos están comprimidos y sus nombres dependen del contenido. Tocar un archivo de .git/objects/ no «edita una versión»: corrompe la base de datos. Para inspeccionar se usa git cat-file; para crear se usan los comandos de Git.

Anatomía de un tree

Un tree es una lista ordenada de entradas. Cada línea tiene modo, tipo, hash y nombre:

100644 blob 5c1b14949828006ed75a3e8858957f86a2f7e2eb	saludo.txt
100755 blob 9f3c2ab4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0	build.sh
040000 tree 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0	docs
ModoSignificado
100644Archivo normal, no ejecutable
100755Archivo ejecutable
120000Enlace simbólico
040000Subdirectorio (otro tree)
160000Submódulo (hash de otro commit)

Fíjate en que el nombre solo existe aquí. El blob de saludo.txt no sabe cómo se llama: si renombras el archivo, el blob no cambia, cambia el tree.

Anatomía de un commit

tree 801e45332eddf6a31000c9c885c163b5590a9110
parent 3b1e8d4c9a0b1c2d3e4f5a6b7c8d9e0f1a2b3c4d
author Ana Torres <ana@ejemplo.com> 1792253821 +0200
committer Ana Torres <ana@ejemplo.com> 1792253821 +0200

feat: saludar
  • tree: la foto del proyecto en ese instante. Obligatorio.
  • parent: cero (commit raíz), uno (commit normal) o varios (merge). Es lo que forma el grafo.
  • author: quién escribió el cambio, con fecha y zona horaria.
  • committer: quién creó este objeto commit. En un rebase o cherry-pick puede diferir del autor.
  • mensaje: tras una línea en blanco, el asunto y el cuerpo.
commit A (raíz)        commit B              commit C (merge)
parent: ninguno        parent: A             parent: B y D
   |                     |                       |
   v                     v                       v
 tree A                tree B                tree C

Un commit es inmutable: y por eso todo encaja

El hash del commit se calcula sobre todo su contenido: árbol, padres, autor, committer y mensaje. Cambiar una sola letra del mensaje produce un hash distinto, y como los commits hijos guardan el hash de su padre, el cambio se propaga en cascada a todos los descendientes.

Esto explica tres cosas que verás una y otra vez:

  1. git commit --amend no edita: crea un commit nuevo y mueve la rama. El anterior sigue existiendo hasta que el recolector lo borre.
  2. git rebase «rejuega» commits: en realidad crea commits nuevos con hashes nuevos.
  3. Si alguien basó trabajo en un commit que tú reescribiste, su rama sigue apuntando al antiguo: por eso la regla de oro prohíbe reescribir lo publicado.

Etiquetas: ligeras y anotadas

Una etiqueta ligera es solo un archivo en .git/refs/tags/ que contiene un hash. Una etiqueta anotada es un objeto tag completo, con autor, fecha, mensaje y posibilidad de firma:

object 52978460d4e4481041e440bedc7cd619cd184f2b
type commit
tag v0.1
tagger Ana Torres <ana@ejemplo.com> 1792253631 +0200

Primera version

Para releases se usan anotadas: viajan con su mensaje, se pueden firmar y git describe las reconoce de forma fiable. Lo veremos en el módulo 7.

3 · Ejemplo mínimo

Sin repositorio, sin commits: solo el cálculo de un hash y la lectura de un objeto. Podemos usar git hash-object para calcular el identificador de un contenido que pasa por la entrada estándar:

echo "hola" | git hash-object --stdin
echo "adios" | git hash-object --stdin

5c1b14949828006ed75a3e8858957f86a2f7e2eb
19c70a3e67953361e0cb365291fee552a4872e6c

Un carácter distinto, un hash completamente distinto. Ahora guarda el objeto en la base de datos con -w (write) y léelo:

echo "hola" | git hash-object -w --stdin

git cat-file -t 5c1b149   # tipo
git cat-file -s 5c1b149   # tamaño en bytes
git cat-file -p 5c1b149   # contenido

blob
5
hola

git cat-file es la llave maestra: pregunta por el tipo (-t), el tamaño (-s) o el contenido (-p, de pretty print). Cualquier estado interno de Git se inspecciona con él. En la práctica usarás hashes completos o ramas; 5c1b149 es un prefijo abreviado que Git acepta si es único.

4 · Ejemplo real

Vamos a recorrer el grafo completo de un commit real del taller hasta llegar al contenido de un archivo:

mkdir laboratorio-objetos && cd laboratorio-objetos
git init -b main
printf 'hola\n' > saludo.txt
git add saludo.txt
git commit -m "feat: saludar"

Del commit al blob, paso a paso:

# 1. El commit
git cat-file -p HEAD

tree 801e45332eddf6a31000c9c885c163b5590a9110
author Ana Torres <ana@ejemplo.com> 1792253821 +0200
committer Ana Torres <ana@ejemplo.com> 1792253821 +0200

feat: saludar
# 2. El árbol al que apunta el commit
git cat-file -p HEAD^{tree}

100644 blob 5c1b14949828006ed75a3e8858957f86a2f7e2eb	saludo.txt
# 3. El contenido del blob (la hoja)
git cat-file -p HEAD:saludo.txt

hola

La ruta HEAD:saludo.txt se lee como «el blob de saludo.txt tal como está en el commit HEAD». Y fíjate en el hash del blob: es el mismo 5c1b149… que obtuvimos en el ejemplo mínimo y el mismo que en cualquier otro repositorio con un archivo hola\n. El contenido es la identidad.

PowerShell y las llaves

HEAD^{tree} contiene llaves, que PowerShell interpreta a su manera. En Git Bash o bash va sin problema; en PowerShell escríbelo entre comillas: git cat-file -p 'HEAD^{tree}'. Es uno de los motivos por los que el curso usa bash.

Los atajos de revisión vienen del mismo grafo: HEAD^ es el primer padre, HEAD~2 es el abuelo, HEAD:v0.1 no existe (eso son ramas y etiquetas, no rutas). Comprobemos que renombrar un archivo no cambia el blob:

git mv saludo.txt bienvenida.txt
git hash-object bienvenida.txt

5c1b14949828006ed75a3e8858957f86a2f7e2eb

Mismo hash con otro nombre. Al commitear, lo que cambia es el tree: una entrada desaparece y otra aparece, pero el blob se reutiliza. Y así se ve la etiqueta anotada que crearemos en el proyecto final:

git tag -a v0.1 -m "Primera version"
git cat-file -p v0.1

object 52978460d4e4481041e440bedc7cd619cd184f2b
type commit
tag v0.1
tagger Ana Torres <ana@ejemplo.com> 1792253631 +0200

Primera version

Una etiqueta ligera (git tag v0.1) sería solo un hash en .git/refs/tags/v0.1; esta es un objeto con contenido y autor.

6 · Errores habituales

1. Creer que el blob guarda el nombre del archivo

Mal — «el hash cambia si renombro» 
mv saludo.txt bienvenida.txt
# ❌ Se espera un hash nuevo
Bien — el nombre vive en el tree 
git mv saludo.txt bienvenida.txt
git hash-object bienvenida.txt   # mismo hash que antes del rename
git ls-tree HEAD                 # aquí SÍ cambia la entrada

El blob es contenido puro. El nombre, la ruta y el modo son metadatos del tree.

2. Creer que un commit almacena el diff

Mal — «el commit dice qué líneas cambiaron» 
commit = "línea 12: -foo +bar"   ❌
Bien — el commit apunta a un árbol; el diff se calcula 
git cat-file -p HEAD          # tree + author + committer + mensaje
git diff HEAD~1 HEAD          # el diff se genera ahora, comparando árboles

Si el diff no se guardase, git diff entre dos commits de hace un año no podría ser instantáneo. Y lo es, porque compara dos árboles con deduplicación.

3. Editar .git a mano para «arreglar» algo

Mal — modifican un objeto o una ref sin usar Git 
# ❌ abrir .git/objects/5c/1b149... y cambiar bytes
# ❌ escribir un hash a mano en .git/refs/heads/main
Bien — usar la interfaz de Git 
git cat-file -p HEAD              # leer
git update-ref refs/heads/main <hash>   # mover una ref (módulo 6)
git fsck --full                   # verificar integridad

Escribir un hash inventado en una ref deja el repositorio apuntando a un objeto que no existe.

4. Pensar que el hash es un identificador secuencial

Mal — «el commit 1, el 2, el 3…» 
commit 1001, commit 1002, ...   ❌ no existe tal numeración
Bien — el hash depende del contenido completo 
git commit --amend -m "feat: saludar (revisado)"
git rev-parse HEAD    # hash distinto: mensaje distinto

Cambiar el mensaje cambia el hash del commit. El anterior sigue accesible vía git reflog hasta que gc lo elimine.

5. Confiar en un hash como prueba de autoría

Mal — «si el hash cuadra, es auténtico» 
El hash garantiza integridad del contenido, no quién lo escribió.   ❌
Bien — firmar los commits para autenticidad 
git log --show-signature
git verify-commit HEAD

Nombre y email son texto libre. La autenticidad se consigue con firmas GPG/SSH, y se verifica con git verify-commit.

7 · Ejercicio guiado

Objetivo: recorrer el grafo commit → tree → blob y comprobar que el nombre no forma parte del contenido.

  1. Crea el repositorio y un archivo conocido: 
    mkdir laboratorio-modelo
cd laboratorio-modelo
git init -b main
printf 'hola\n' > saludo.txt
git add saludo.txt
git commit -m "feat: saludar"
  2. Observa el objeto antes de commitear: 
    git hash-object saludo.txt

    5c1b14949828006ed75a3e8858957f86a2f7e2eb

    Es el mismo hash que calculamos «a mano» con echo "hola" | git hash-object --stdin. El contenido manda.

  3. Sube por el grafo: 
    git cat-file -t HEAD              # commit
git cat-file -p HEAD              # tree + author + committer + mensaje
git cat-file -p HEAD^{tree}       # la entrada del tree
git cat-file -p HEAD:saludo.txt   # el contenido: hola

    commit

100644 blob 5c1b14949828006ed75a3e8858957f86a2f7e2eb	saludo.txt
hola
  4. Comprueba que el hash del blob es el mismo dentro del tree: la tercera línea de git ls-tree HEAD debe coincidir carácter a carácter con el git hash-object del paso 2.
  5. Renombra y verifica que el blob no cambia: 
    git mv saludo.txt bienvenida.txt
git hash-object bienvenida.txt
git commit -m "refactor: renombrar saludo a bienvenida"
git ls-tree HEAD

    5c1b14949828006ed75a3e8858957f86a2f7e2eb
100644 blob 5c1b14949828006ed75a3e8858957f86a2f7e2eb	bienvenida.txt

    Mismo blob, nueva entrada en el tree. El rename no duplicó contenido.

  6. Valida la base de datos: 
    git fsck --full

    Salida esperada: ninguna, o avisos de objetos «dangling» (no alcanzables) como los que dejan los amend. fatal o error: sha1 mismatch significaría corrupción real.

8 · Reto

🎯 Un commit creado con las manos

Construye un commit sin usar git add ni git commit, solo con comandos de fontanería (plumbing): crea un blob, empaquétalo en un árbol, crea el objeto commit apuntando a ese árbol y haz que main avance hasta él. Al terminar, git log --oneline debe mostrar tu commit y git cat-file -p HEAD debe reflejar exactamente lo que montaste.

Pregunta final: si modificas el mensaje y repites el proceso, ¿puede existir el mismo hash dos veces? ¿Qué pasa con el commit antiguo?

Pista: git hash-object -w, git mktree, git commit-tree y git update-ref. Para leer el formato que espera mktree, consulta git help mktree.

9 · Resumen

  • Git guarda cuatro tipos de objeto: blob (contenido), tree (nombres y estructura), commit (foto + metadatos) y tag anotado (etiqueta con contenido propio).
  • El hash se calcula sobre "<tipo> <tamaño>\0<contenido>": mismo contenido, mismo objeto en cualquier repositorio.
  • El nombre de archivo solo vive en el tree; renombrar no cambia el blob.
  • Un commit apunta a un tree completo, no a un diff; los diffs se calculan comparando árboles.
  • Los objetos están en .git/objects/ como ab/cdef… (dos primeros caracteres como carpeta) y pueden agruparse en packfiles.
  • Un commit es inmutable: cambiar cualquier dato produce un hash nuevo y arrastra a todos los descendientes.
  • Las etiquetas son ligeras (una ref a un commit) o anotadas (un objeto tag con autor y mensaje).

10 · Preguntas frecuentes

Si SHA-1 está roto, ¿mi historial es falsificable?

En teoría, se pueden construir dos contenidos con el mismo SHA-1; en la práctica, Git incorpora detección de colisiones desde 2017 y ofrece repositorios con SHA-256. Para autenticidad real se firman los commits o las etiquetas. El hash garantiza integridad accidental, no autoría.

¿Por qué el hash de mi archivo no coincide con git hash-object?

Porque falta el salto de línea final, hay un final de línea distinto (CRLF frente a LF) o la codificación cambió. El hash es sensible al byte exacto. Compáralo con git cat-file -p <ruta del archivo en el commit> para ver qué guardó Git de verdad.

¿Puedo recuperar un objeto si conozco su hash?

Solo si el objeto sigue en .git/objects/ o en un pack. Los objetos no alcanzables se conservan un tiempo (por eso funciona reflog) y luego git gc los elimina. Si el objeto nunca llegó a escribirse, no existe y el hash no ayuda.

¿Qué es un objeto «dangling» que aparece en git fsck?

Un objeto que existe en la base pero al que no llega ninguna referencia desde ramas, etiquetas o el índice: típicamente el resultado de un amend, un reset o un rebase. No es un error; es basura recuperable hasta que se ejecuta gc.

¿Los commits guardan la fecha? ¿Y si mi reloj estaba mal?

Guardan dos: la del autor y la del committer, con zona horaria. Si el reloj estaba mal, la fecha quedará mal; se puede reescribir con --amend --date=… o con un rebase, pero solo en commits no publicados. Los hashes cambian al hacerlo.
