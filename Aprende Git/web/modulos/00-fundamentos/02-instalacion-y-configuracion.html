Instalación y configuración

Módulo 0 · Fundamentos 🕐 35 minutos

1 · Introducción

Git funciona nada más instalarlo, pero no funciona bien hasta que le dices quién eres, cómo quieres que se llamen tus ramas y cómo debe tratar los finales de línea. Esa configuración no es un trámite: queda grabada dentro de cada commit y determina si tu trabajo aparece atribuido a ti, si los diffs son legibles y si tus compañeros ven los mismos archivos que tú.

En esta lección instalarás Git en Windows, macOS o Linux, comprobarás la versión, configurarás tu identidad y aprenderás a leer la configuración efectiva con --show-origin. También entenderemos los cuatro niveles de configuración y el famoso core.autocrlf, responsable de más diffs imposibles de revisar que cualquier otra opción de Git.

Por qué existe esta lección

Un user.email equivocado hace que tus commits no cuenten en GitHub ni en tu empresa. Un core.autocrlf mal puesto convierte un cambio de una línea en un diff de 800 líneas. Y no saber de dónde sale un valor de configuración convierte cualquier problema en adivinación. Todo eso se resuelve en 35 minutos y se sufre para siempre si no se resuelve.

2 · Teoría

Instalar Git

Necesitas Git 2.23 o superior, porque el curso usa git switch y git restore, introducidos en esa versión. Cualquier versión reciente (2.40+) es perfecta.

Verifica siempre la instalación antes de seguir:

git --version

git version 2.55.0.windows.3

La tuya puede ser distinta (en macOS verás algo como git version 2.39.5 (Apple Git-154)). Lo importante es que sea ≥ 2.23. Si el comando no existe, la instalación no está en el PATH: reinstala o abre una terminal nueva.

Windows: usa Git Bash para el curso

Los ejemplos usan sintaxis bash: &&, comillas simples, printf, rutas con /. En PowerShell cambian las comillas y las redirecciones, y algunos ejemplos fallarán. Git Bash viene con Git for Windows y hace que los ejemplos sean idénticos a Linux y macOS.

Los cuatro niveles de configuración

Git lee su configuración de varios archivos, de más general a más específico. Cada nivel sobreescribe al anterior:

PRIORIDAD (el último gana)

  1. worktree   .git/config.worktree        (solo con worktrees; raro)
  2. local      .git/config                 (este repositorio)
  3. global     ~/.gitconfig                (tu usuario; en Windows C:/Users/<tú>/.gitconfig)
  4. system     /etc/gitconfig              (toda la máquina; en Windows C:/Program Files/Git/etc/gitconfig)
NivelFlagArchivoCuándo usarlo
System--system/etc/gitconfigPolíticas de la máquina; requiere administrador. Casi nunca lo tocarás.
Global--global~/.gitconfigTu identidad personal, editor, rama por defecto. Es el nivel del día a día.
Local--local (por defecto dentro de un repo).git/configExcepciones por proyecto: email del trabajo, remotos, opciones del repo.
Worktree--worktree.git/config.worktreeConfiguración distinta por checkout cuando usas git worktree.

Leer no es escribir

git config user.name lee el valor efectivo. git config user.name "Ana" escribe en el nivel local si estás dentro de un repositorio; si no lo estás, falla. Para escribir en global, --global explícito.

La identidad: user.name y user.email

Cada commit guarda dos identidades: author (quien escribió el cambio) y committer (quien lo aplicó). En el 99 % de los casos coinciden, pero Git las separa porque un parche puede aplicarse más tarde, por otra persona, con cherry-pick o rebase.

git config --global user.name "Ana Torres"
git config --global user.email "ana@ejemplo.com"

No es un nombre de usuario ni una contraseña: es la etiqueta que quedará escrita en la historia. Si usas una forja, el email debe ser uno asociado a tu cuenta o tus commits aparecerán como «autor desconocido». Para trabajo y proyectos personales, lo normal es una identidad global y una local por repositorio.

El email no se arregla solo

Cambiar user.email hoy no reescribe los commits de ayer. Corregir commits antiguos implica --amend o rebase, y eso solo es aceptable si no están publicados. Lo veremos en el módulo 4.

Otras opciones que conviene fijar desde el principio

# Nombre de la rama inicial: evita renombrar master cada vez
git config --global init.defaultBranch main

# Editor para mensajes de commit y rebase interactivo
git config --global core.editor "code --wait"

# Que Git te avise si el final de línea se va a corromper
git config --global core.safecrlf warn

core.editor acepta cualquier comando: vim, nano, "code --wait" o "notepad++ -multiInst". El --wait de VS Code es imprescindible: sin él, el editor devuelve el control antes de que guardes y Git recibe un mensaje vacío.

init.defaultBranch solo afecta a repositorios nuevos. En uno existente, la rama se renombra a mano (lo veremos en la lección 5).

Finales de línea: LF, CRLF y core.autocrlf

Windows usa CRLF (\r\n) y Unix usa LF (\n). Si un archivo se guarda con un final y se compara con el otro, Git puede creer que todas las líneas cambiaron. El síntoma es inconfundible: un diff de 800 líneas por un cambio de una palabra.

ValorAl hacer commitAl hacer checkoutCuándo se usa
falseNo convierteNo convierteRecomendado si el equipo usa .gitattributes (módulo 1).
trueCRLF → LFLF → CRLFValor típico del instalador de Git for Windows.
inputCRLF → LFNo convierteWindows que trabaja con herramientas Unix, o macOS/Linux que reciben archivos de Windows.

El problema de autocrlf es que es una preferencia de cada máquina: si un compañero lo tiene en true y otro en false, el repositorio se llena de conversiones contradictorias. La solución de equipo es declarar la política en .gitattributes, que sí viaja con el repositorio:

* text=auto eol=lf

Por eso la recomendación del curso es core.autocrlf=false en todas las plataformas y una política explícita en .gitattributes. Lo configuraremos con detalle en la lección .gitignore y .gitattributes.

¿Y si ya tengo el repo lleno de CRLF?

No se arregla cambiando la config: hay que renormalizar el índice con git add --renormalize . y commitear el resultado. Aun así, la conversión completa del directorio de trabajo ocurre en el siguiente checkout. Lo veremos paso a paso en el módulo 1.

3 · Ejemplo mínimo

Lo mínimo para que Git sepa quién eres y cómo leer su configuración:

git --version
git config --global user.name "Ana Torres"
git config --global user.email "ana@ejemplo.com"

# Leer el valor efectivo (sin escribir nada)
git config user.name
git config user.email

git version 2.55.0.windows.3
Ana Torres
ana@ejemplo.com

Y ahora la pregunta importante: ¿de dónde sale ese valor? --show-origin añade el archivo que lo define:

git config --show-origin --get user.email

file:C:/Users/ana/.gitconfig	ana@ejemplo.com

Sin --show-origin estarías adivinando si el valor viene del sistema, de tu usuario o del repositorio. Con él, el diagnóstico es inmediato.

4 · Ejemplo real

Ana trabaja en ACME durante el día y en sus proyectos por la noche. Quiere commits de trabajo con su email corporativo y commits personales con el suyo. La configuración global es la personal y el repositorio de ACME la sobreescribe:

# Una sola vez, en global
git config --global user.name "Ana Torres"
git config --global user.email "ana@personal.dev"

# Dentro del repositorio de ACME, sin --global
cd ~/trabajo/api-acme
git config user.name "Ana Torres"
git config user.email "ana.torres@acme.com"

Comprobemos qué valor gana y de dónde sale:

git config --show-origin --get user.email
git config --show-scope --list | grep user

file:.git/config	ana.torres@acme.com
global	user.name=Ana Torres
global	user.email=ana@personal.dev
local	user.name=Ana Torres
local	user.email=ana.torres@acme.com

El valor efectivo es el local: está más cerca del repositorio y por tanto tiene prioridad. Fuera de ese repositorio, git config --get user.email devolverá el personal. Esta es la forma correcta de separar identidades; cambiar --global cada mañana es una fuente garantizada de commits con el email equivocado.

Así se ve una configuración completa y sana en una máquina de desarrollo:

git config --list --show-origin

file:C:/Program Files/Git/etc/gitconfig	core.autocrlf=true
file:C:/Program Files/Git/etc/gitconfig	init.defaultBranch=master
file:C:/Users/ana/.gitconfig	user.name=Ana Torres
file:C:/Users/ana/.gitconfig	user.email=ana@personal.dev
file:C:/Users/ana/.gitconfig	init.defaultbranch=main
file:C:/Users/ana/.gitconfig	core.editor=code --wait
file:.git/config	core.repositoryformatversion=0
file:.git/config	core.bare=false
file:.git/config	core.autocrlf=false
file:.git/config	user.email=ana.torres@acme.com

Cómo leer esta salida

La primera columna es el archivo de origen, la segunda la clave y el valor. Fíjate en que core.autocrlf aparece dos veces: el sistema dice true y el repositorio dice false. Gana el repositorio. No hay contradicción: hay capas.

5 · Buenas prácticas

6 · Errores habituales

1. Commitear con el email equivocado

Mal — descubrirlo después de publicar 
git config --global user.email "ana@portatil.local"
git commit -m "feat: informe"
git push origin main
# ❌ El commit ya está publicado con una identidad que nadie reconoce
Bien — verificar antes y corregir solo lo local 
git config --show-origin --get user.email
# Si el commit aún NO está publicado:
git commit --amend --reset-author --no-edit

Si ya está en una rama compartida, no lo reescribas: asume el error o consulta al equipo. La regla de oro del curso es que la historia publicada no se toca sin acuerdo.

2. Escribir en local creyendo que era global

Mal — dentro del repo, sin --global 
git config user.email "ana@acme.com"
# ❌ Solo afecta a este repositorio
Bien — ser explícito con el nivel 
git config --global user.email "ana@acme.com"   # todos los repos
git config --local  user.email "ana@acme.com"   # solo este

Dentro de un repositorio, git config sin flag escribe en .git/config. Es cómodo, pero ambiguo si no lo sabes.

3. Mezclar finales de línea y culpar al diff

Mal — autocrlf distinto en cada máquina 
# Windows con core.autocrlf=true, Linux con false
git diff
# ❌ Aparecen 800 líneas cambiadas por un cambio real de una palabra
Bien — política explícita en el repositorio 
git config --global core.autocrlf false
# y en la raíz del repo, un .gitattributes con:
# * text=auto eol=lf
git add --renormalize .

El diff deja de mentir cuando todos aplican la misma regla. El detalle completo va en el módulo 1.

4. Confundir user.name con el usuario de la forja

Mal — poner el login en mayúsculas o el nombre de la cuenta 
git config --global user.name "ana-dev-99"
# ❌ Eso no autentica nada ni cambia tu usuario de GitHub
Bien — nombre real y email correcto; las credenciales van aparte 
git config --global user.name "Ana Torres"
git config --global user.email "ana@ejemplo.com"
# La autenticación se configura con un credential helper (módulo 5)

user.name es una etiqueta en el commit, no un mecanismo de login.

5. Editar la configuración a ciegas y no saber qué gana

Mal — adivinar entre system, global y local 
git config --list   # ❌ sin origen, no sabes de dónde sale cada valor
Bien — pedir el origen y el ámbito 
git config --list --show-origin
git config --show-scope --get user.email

Dos flags convierten la configuración en algo observable. Úsalos siempre que un valor no sea el que esperabas.

7 · Ejercicio guiado

Objetivo: dejar la máquina lista, comprobar la precedencia y ver con tus ojos de dónde sale cada valor.

  1. Comprueba la versión: 
    git --version

    git version 2.55.0.windows.3

    Debe ser ≥ 2.23. Si no, actualiza antes de continuar.

  2. Configura la identidad global y la rama por defecto: 
    git config --global user.name "Ana Torres"
git config --global user.email "ana@ejemplo.com"
git config --global init.defaultBranch main

    No hay salida: en Unix, el silencio es éxito.

  3. Lee la configuración con origen: 
    git config --list --show-origin | grep -E "user|init"

    file:C:/Users/ana/.gitconfig	user.name=Ana Torres
file:C:/Users/ana/.gitconfig	user.email=ana@ejemplo.com
file:C:/Users/ana/.gitconfig	init.defaultbranch=main
  4. Crea un repositorio y sobreescribe la identidad en local: 
    mkdir config-demo
cd config-demo
git init -b main
git config user.email "ana@acme.com"
git config --show-origin --get user.email

    file:.git/config	ana@acme.com
  5. Comprueba la precedencia completa: 
    git config --show-scope --list | grep user

    global	user.name=Ana Torres
global	user.email=ana@ejemplo.com
local	user.email=ana@acme.com

    El nombre sigue viniendo de global; el email, de local. No se copia nada: se consulta en cascada.

  6. Sal del repositorio y vuelve a leer: 
    cd ..
git config --get user.email

    ana@ejemplo.com

    Fuera del repositorio, la configuración local no existe. Esa es la prueba de que la identidad de trabajo no contamina la personal.

8 · Reto

🎯 Dos identidades sin cambiar nada a mano

Organiza tus repositorios en dos carpetas, ~/trabajo/ y ~/personal/, y consigue que Git use automáticamente el email corporativo en la primera y el personal en la segunda, sin ejecutar git config dentro de cada repositorio nuevo.

Verifica el resultado creando un repo en cada carpeta y ejecutando git config --show-origin --get user.email. Debes ver dos archivos de origen distintos.

Pista: existe una sección [includeIf "gitdir:..."] que incluye un archivo de configuración según la ruta del repositorio. La encontrarás en git help config, sección «Conditional includes».

9 · Resumen

  • Necesitas Git ≥ 2.23 para switch y restore; verifica con git --version.
  • La configuración tiene cuatro niveles: system → global → local → worktree. El más específico gana.
  • user.name y user.email quedan grabados en cada commit. El email debe ser el de tu cuenta de la forja.
  • git config --list --show-origin responde «¿de dónde sale este valor?»; --show-scope añade el nivel.
  • init.defaultBranch main evita renombrar la rama en cada repositorio nuevo.
  • core.autocrlf es una preferencia local; la política de equipo va en .gitattributes.

10 · Preguntas frecuentes

¿Qué pasa si hago commits sin configurar user.name y user.email?

Git intenta deducirlos del sistema y, si no puede, aborta con «Please tell me who you are». En versiones recientes puede crear el commit con un email inventado tipo tuusuario@maquina.local, que la forja no asociará a tu cuenta. Configúralos antes del primer commit.

¿Puedo usar un email falso para no exponer el real?

Sí. GitHub ofrece un email noreply por cuenta (ID+usuario@users.noreply.github.com) que mantiene la atribución sin publicar tu dirección. Configúralo como user.email y verifica que la forja lo reconoce.

¿Dónde está el archivo global en Windows?

En C:\Users\<tu usuario>\.gitconfig. Git Bash lo muestra como ~/.gitconfig. El archivo de sistema suele estar en C:\Program Files\Git\etc\gitconfig. Usa git config --list --show-origin para no tener que adivinarlo.

¿Debo poner core.autocrlf=true en Windows?

Solo si el proyecto no tiene política propia. Con .gitattributes en el repositorio, la respuesta recomendada es false: la conversión la dicta el archivo versionado, no la máquina. Si trabajas con un repo antiguo sin .gitattributes, true evita mezclar finales, pero cada compañero debe usar lo mismo.

¿La configuración local se sube al repositorio?

No. .git/config vive dentro de .git/, que no forma parte del árbol versionado. Cada clon tiene su propia configuración local. Lo que sí se versiona es .gitattributes en la raíz del proyecto, porque no es configuración de máquina sino una regla del contenido.
