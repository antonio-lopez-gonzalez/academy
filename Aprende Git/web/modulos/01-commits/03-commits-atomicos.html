Commits atómicos

Módulo 1 · Commits 🕐 35 minutos

1 · Introducción

Un commit no es un punto de guardado cualquiera: es la unidad de comunicación de tu trabajo. Cuando alguien lee la historia —tu yo de dentro de seis meses, un compañero en una revisión, git bisect buscando un bug— cada commit debería contar una historia pequeña y completa. Los commits «cambios varios» no cuentan nada y hacen imposible deshacer una cosa sin arrastrar otras.

En esta lección definiremos qué hace atómico a un commit, cómo se escribe un mensaje que sirva (asunto, cuerpo y el estándar Conventional Commits) y cómo enmendar el último commit mientras aún es tuyo y nadie más lo ha visto. Esa última parte trae la primera regla de oro del curso: lo publicado no se reescribe.

Por qué existe esta lección

Todo el módulo 2 (deshacer) y el módulo 4 (historia) dependen de esto. git revert, git bisect, git cherry-pick y rebase -i funcionan bien con commits atómicos y son un infierno con commits gigantes. La calidad de tu historia decide la potencia de tus herramientas.

2 · Teoría

Qué hace atómico a un commit

Atómico no significa «pequeño», sino indivisible y coherente: un solo cambio lógico que puede describirse en una frase, que deja el proyecto en un estado válido y que podría revertirse sin arrastrar cosas ajenas.

Por qué merece la pena: un commit atómico es revertible con git revert, encontrable con bisect, revisable en un diff corto y explicable en un changelog. Un commit gigante no cumple ninguna de las cuatro.

Anatomía de un mensaje

docs(api): documentar el endpoint de usuarios
^    ^      ^
|    |      +-- descripcion breve, en imperativo, minusculas, sin punto final
|    +--------- ambito (scope) opcional: que parte del proyecto
+-------------- tipo de cambio

Cuerpo opcional tras una linea en blanco: explica el POR QUE, no el que.
Se envuelve a 72 columnas para que se lea en terminales y correos.
Las lineas vacias separan parrafos.

Conventional Commits

Es una convención sobre el asunto con muchos años de recorrido y respaldo de herramientas (changelogs automáticos, semantic-release, validadores en CI). El formato es:

<tipo>[<ambito>][!]: <descripcion>

[cuerpo opcional]

[footer(s) opcionales]
TipoCuándoEjemplo
featNueva funcionalidadfeat(auth): permitir login con passkeys
fixCorrección de un bugfix(api): evitar 500 con email vacio
docsSolo documentacióndocs: explicar el flujo de despliegue
styleFormato, espacios; sin cambio de comportamientostyle: aplicar prettier a src/
refactorReorganizar código sin cambiar comportamientorefactor(core): extraer parser a su modulo
perfMejora de rendimientoperf(db): cachear consultas de usuario
testAñadir o ajustar teststest(api): cubrir el caso de sesion expirada
buildSistema de build o dependenciasbuild: subir Node a la version 22
ciIntegración continuaci: ejecutar tests en Windows tambien
choreTareas que no cambian el productochore: actualizar .gitignore
revertDeshacer un commit anteriorrevert: feat(auth): permitir login con passkeys

Un cambio incompatible se marca con ! tras el tipo o el ámbito, y con un footer BREAKING CHANGE: que lo explique:

feat(api)!: renombrar /users a /v2/users

BREAKING CHANGE: los clientes deben actualizar la ruta base.

La convención la elige el equipo

No es obligatoria y no existe un estándar universal de mayúsculas o de ámbito. Lo importante es ser consistente: si el proyecto usa Conventional Commits, úsalo; si usa otra convención, sigue esa. Una historia homogénea vale más que una bonita a medias.

git commit --amend: arreglar el último commit

--amend (enmendar) reemplaza el último commit por otro nuevo. No lo edita: como el hash cubre todo el contenido, el resultado es un commit distinto y la rama se mueve a él. Sirve para tres cosas:

  1. Añadir un archivo olvidado: git add olvidado.txt && git commit --amend --no-edit.
  2. Corregir el mensaje: git commit --amend -m "docs: mensaje corregido".
  3. Corregir la identidad: git commit --amend --reset-author --no-edit.
# Antes del amend
git rev-parse HEAD       # 11dc4885b36fbf65e9269ff69f2c13ca3e909390

git add .gitignore
git commit --amend --no-edit

# Después
git rev-parse HEAD       # 4d9960ac771932e952ca69a9b7f88e5aba5ce2dc (otro commit)
git log --oneline

4d9960a docs: notas

Un solo commit en la historia, pero ya no es el mismo. El anterior sigue vivo en el reflog:

git reflog

4d9960a HEAD@{0}: commit (amend): docs: notas
11dc488 HEAD@{1}: commit (initial): docs: notas

Esa es la red de seguridad y también la advertencia: si ya habías publicado 11dc488, tu rama y la del remoto ahora divergen. Enmendar es seguro mientras el commit sea solo tuyo.

La regla de oro

No reescribas historia que otros ya tienen. Si el commit está publicado en una rama compartida, la solución no es --amend ni forzar el push: es un commit nuevo (y, para deshacer, git revert, módulo 2). Reescribir solo se hace en ramas propias y con --force-with-lease (módulo 4). Forzar un push sobre main nunca es una solución.

Inspeccionar un commit: git show

git show                     # HEAD: metadatos + diff
git show --stat              # metadatos + resumen de archivos
git show <commit> -- <ruta>  # solo esa ruta
git show HEAD:notas.md       # el CONTENIDO del archivo en ese commit (sin diff)

commit 4d9960ac771932e952ca69a9b7f88e5aba5ce2dc
Author: Ana Torres <ana@ejemplo.com>
Date:   Sat Oct 17 18:25:35 2026 +0200

    docs: notas

 .gitignore | 1 +
 notas.md   | 1 +
 2 files changed, 2 insertions(+)

git show HEAD:ruta es la forma de ver una versión antigua de un archivo sin cambiar nada en tu directorio de trabajo. Es el comando que usarás para comparar «cómo era» con «cómo es».

Dos ayudas más al escribir el mensaje: git commit -v añade el diff completo como comentario en el editor para que escribas mirándolo, y git commit -F mensaje.txt lee el mensaje de un archivo (útil en scripts).

3 · Ejemplo mínimo

El caso más común del mundo: commiteas y te das cuenta de que falta un archivo.

printf '# Notas\n' > notas.md
git add notas.md
git commit -m "chore: crear notas"

printf 'node_modules/\ndist/\n' > .gitignore
git add .gitignore
git commit --amend --no-edit

[main (root-commit) 11dc488] chore: crear notas
 1 file changed, 1 insertion(+)
 create mode 100644 notas.md
[main 4d9960a] chore: crear notas
 2 files changed, 2 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 notas.md

Fíjate en que el segundo mensaje dice (root-commit) también: sigue siendo el primer commit, solo que ahora con dos archivos. --no-edit conserva el mensaje original. Si miras la historia, hay un único commit; lo que cambió es su contenido y su hash.

4 · Ejemplo real

Ana implementa una búsqueda en el taller. En lugar de un commit gigante, separa el trabajo en tres unidades coherentes, cada una con su mensaje:

# 1) La funcionalidad
printf 'export function buscar(notas, texto) {\n  return notas.filter((n) => n.includes(texto));\n}\n' > buscar.js
git add buscar.js
git commit -m "feat(busqueda): filtrar notas por texto"

# 2) Los tests
printf 'import { buscar } from "./buscar.js";\n// TODO: casos de prueba\n' > buscar.test.js
git add buscar.test.js
git commit -m "test(busqueda): cubrir filtro por texto"

# 3) La documentación
printf '\n## Busqueda\n\nUsa `buscar(notas, texto)` para filtrar.\n' >> README.md
git add README.md
git commit -m "docs: documentar la busqueda"

$ git log --oneline
d41f0a2 (HEAD -> main) docs: documentar la busqueda
9c2b7e1 test(busqueda): cubrir filtro por texto
e5a8c30 feat(busqueda): filtrar notas por texto

Tres commits, tres intenciones. Si mañana el test estaba mal, se revierte solo 9c2b7e1. Si la API cambia de nombre, se revierte el feat sin tocar la documentación. Y git log se puede leer como un changelog.

El mismo trabajo mal empaquetado se vería así:

$ git log --oneline        # versión mala
f00db4r (HEAD -> main) cambios

Dentro de ese commit hay feature, tests, docs y un formateo de otro archivo. Revertirlo deshace también el formateo; revisarlo obliga a leer 400 líneas; y en el changelog aparece «cambios».

Mensaje maloQué faltaVersión útil
cambiosTodofix(api): evitar 500 con email vacio
arregladoQué se arreglófix(cache): invalidar entradas al borrar usuario
wipQue no debería publicarse tal cualCommit marcado como borrador o --fixup (módulo 4)
refactor y feature de busquedaAtomicidadDos commits: refactor(busqueda): extraer normalizador y feat(busqueda): filtrar por texto

Escribe el mensaje antes de codificar

Si no puedes resumir el commit en una frase con tipo y ámbito, probablemente son dos commits. Es la forma más rápida de detectar un cambio que deberías partir con git add -p.

5 · Buenas prácticas

HazEvitaPor qué
Un cambio lógico por commit Mezclar feature, refactor y formato Permite revertir y aplicar cambios por separado sin efectos colaterales.
Asunto en imperativo y ≤ 50 caracteres Cambios hechos al módulo de usuarios y otras cosas Se lee en listas y no se trunca en la interfaz.

6 · Errores habituales

1. Enmendar un commit ya publicado

Mal — amend después de push en una rama compartida 
git commit -m "feat: busqueda"
git push origin main
git commit --amend -m "feat: busqueda por texto"
git push              # ❌ rejected: non-fast-forward (tu rama y la remota divergen)
# ❌ Y si alguien fuerza: el compañero que ya hizo pull se queda con historia rota
Bien — corregir hacia delante 
git commit -m "docs: aclarar el alcance de la busqueda"
git push             # commit nuevo; nadie necesita reescribir nada

Si de verdad hay que reescribir una rama propia ya publicada, se hace con --force-with-lease y avisando. Nunca en main.

2. Mensajes que no dicen nada

Mal — el mensaje como trámite 
git commit -m "cambios"
git commit -m "arreglos"
git commit -m "."
Bien — tipo, ámbito y motivo 
git commit -m "fix(api): devolver 404 si el usuario no existe"

Dentro de un año, el hash no te dirá nada; el mensaje sí.

3. Un commit que hace tres cosas

Mal — todo a la vez 
git add .
git commit -m "feat: busqueda + refactor + formato + deps"
Bien — separar con add -p y commits distintos 
git add buscar.js
git commit -m "feat(busqueda): filtrar notas por texto"
git add buscar.test.js
git commit -m "test(busqueda): cubrir filtro por texto"
git add README.md
git commit -m "docs: documentar la busqueda"

git revert de un commit mezclado deshace también lo que no querías.

4. Usar --amend para trabajo nuevo

Mal — esconder un cambio dentro del commit anterior 
git add otro-cambio.js
git commit --amend --no-edit
# ❌ La historia pierde la separación entre dos cambios distintos
Bien — enmendar solo lo mismo; lo demás, commit propio 
git add otro-cambio.js
git commit -m "feat(api): anadir rate limiting"

--amend es para arreglar lo que debía estar en ese commit, no para esconder trabajo posterior.

5. Escribir un Conventional Commit que no lo es

Mal — tipo genérico y descripción vaga 
git commit -m "fix: fix"
git commit -m "chore: cambios varios"
git commit -m "feat: implementar la funcionalidad solicitada por el cliente"
Bien — tipo correcto y descripción concreta 
git commit -m "fix(auth): caducar la sesion tras 30 min de inactividad"
git commit -m "chore(deps): actualizar express a 5.1.0"

El valor de la convención está en que una máquina pueda interpretarla; fix: fix no comunica nada a nadie.

7 · Ejercicio guiado

Objetivo: construir tres commits atómicos y comprobar que enmendar cambia el hash sin añadir historial.

  1. Prepara el repositorio: 
    mkdir laboratorio-commits
cd laboratorio-commits
git init -b main
git config user.name "Ana Torres"
git config user.email "ana@ejemplo.com"
  2. Primer commit atómico (la funcionalidad): 
    printf 'export function buscar(notas, texto) {\n  return notas.filter((n) => n.includes(texto));\n}\n' > buscar.js
git add buscar.js
git commit -m "feat(busqueda): filtrar notas por texto"

    [main (root-commit) e5a8c30] feat(busqueda): filtrar notas por texto

  3. Guarda el hash actual y enmienda el mensaje: 
    git rev-parse HEAD
git commit --amend -m "feat(busqueda): filtrar notas por texto y por etiqueta"
git rev-parse HEAD

    Los dos hashes deben ser distintos y git log --oneline debe seguir mostrando un solo commit.

  4. Recupera el commit anterior con el reflog: 
    git reflog

    a1f9c74 HEAD@{0}: commit (amend): feat(busqueda): filtrar notas por texto y por etiqueta
e5a8c30 HEAD@{1}: commit (initial): feat(busqueda): filtrar notas por texto

    El commit «viejo» sigue existiendo. Eso es lo que hace de reflog una red de seguridad (módulo 6).

  5. Añade test y documentación como commits separados: 
    printf 'import { buscar } from "./buscar.js";\n// TODO: casos de prueba\n' > buscar.test.js
git add buscar.test.js
git commit -m "test(busqueda): cubrir filtro por texto"

printf '# Taller\n\n## Busqueda\n\nFiltra notas por texto.\n' > README.md
git add README.md
git commit -m "docs: documentar la busqueda"
  6. Lee la historia como un changelog: 
    git log --oneline
git show --stat HEAD~1

    d41f0a2 (HEAD -> main) docs: documentar la busqueda
9c2b7e1 test(busqueda): cubrir filtro por texto
a1f9c74 feat(busqueda): filtrar notas por texto y por etiqueta

    git show --stat HEAD~1 debe mostrar solo buscar.test.js: un archivo por commit. Esa es la señal de que la separación es correcta.

8 · Reto

🎯 Partir un commit mixto sin reescribir nada publicado

Haz un commit que mezcle dos cosas: un cambio en notas.md y uno en README.md. Después, sin usar git rebase -i (que verás en el módulo 4), conviértelo en dos commits atómicos distintos, cada uno con su mensaje. Al terminar, git log --oneline debe mostrar tres commits: el original transformado en dos más cualquier otro anterior.

Pregunta final: ¿este procedimiento es seguro si el commit mixto ya estaba publicado? ¿Por qué?

Pista: existe git reset --soft HEAD~1, que mueve la rama un commit atrás dejando el índice intacto. A partir de ahí puedes preparar y commitear por partes. Compruébalo con git status después del reset.

9 · Resumen

  • Un commit atómico es un cambio lógico, coherente y revertible por sí solo.
  • El mensaje tiene asunto (≤ 50, imperativo), línea en blanco y cuerpo (el por qué, a 72 columnas).
  • Conventional Commits: <tipo>(<ámbito>): descripción, con ! y BREAKING CHANGE: para incompatibilidades.
  • git commit --amend crea un commit nuevo que reemplaza al último; el anterior queda en reflog.
  • Enmendar es seguro solo si el commit es local. Lo publicado se corrige con commits nuevos.
  • git show detalla un commit; git show HEAD:ruta devuelve el contenido de un archivo en ese commit.

10 · Preguntas frecuentes

¿Puedo corregir el mensaje de un commit antiguo?

Sí, con git rebase -i <commit>~1 y la acción reword, que verás en el módulo 4. Pero es una reescritura: cambia el hash del commit y el de todos los siguientes, así que solo se hace si no están publicados o si la rama es tuya y coordinas el cambio.

¿--amend cambia el hash? ¿Y el reflog?

Siempre cambia el hash: el contenido del commit (árbol, padres, mensaje, fechas) forma parte de él. El viejo queda registrado en el reflog como commit (amend), y se puede volver a él con git switch --detach <hash> o resucitarlo con git branch rescatado <hash>.

¿En qué idioma escribo los mensajes?

En el que use el equipo. Lo importante es la consistencia y que quien lea la historia la entienda. Si eliges Conventional Commits, los tipos (feat, fix…) van siempre en inglés porque son parte del estándar; la descripción puede ir en español.

¿Qué diferencia hay entre autor y committer?

El autor es quien escribió el cambio; el committer, quien creó el objeto commit. En un flujo normal son la misma persona. Al hacer rebase, cherry-pick o aplicar un parche, el autor se conserva y el committer cambia. Se puede forzar el autor con --author="Nombre <email>".

¿Para qué sirve un commit vacío con --allow-empty?

Para disparar un pipeline de CI cuando no hay cambios de código (por ejemplo, forzar un despliegue o probar una configuración). También lo usan algunas herramientas para marcar hitos. No es algo que se haga a diario: Git solo crea commits vacíos si se lo pides explícitamente.
