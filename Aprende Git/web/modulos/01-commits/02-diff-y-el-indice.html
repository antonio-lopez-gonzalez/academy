diff y el índice

Módulo 1 · Commits 🕐 35 minutos

1 · Introducción

git diff es probablemente el comando que más veces vas a ejecutar y el que más veces se malinterpreta. La confusión viene de que hay tres diffs distintos según qué dos zonas compares, y de que Git no guarda ninguno: los calcula en el momento. «He añadido el archivo y git diff ya no muestra nada» es la pregunta más frecuente de este módulo.

En esta lección aprenderás a leer un diff unificado línea por línea, a elegir el diff correcto para cada pregunta y a usar git add -p para preparar por trozos: la herramienta que convierte un desastre de cambios mezclados en varios commits limpios.

Por qué existe esta lección

Los commits atómicos de la lección siguiente no se pueden hacer sin add -p, y revisar tu propio trabajo antes de confirmarlo es la costumbre que más errores evita. Además, leer un diff es una habilidad que usarás en pull requests, en git show, en git log -p y al resolver conflictos.

2 · Teoría

Los tres diffs

        DIRECTORIO DE TRABAJO            ÍNDICE                    HEAD

                 |                          |                        |
                 |<-------- git diff ------->|                        |
                 |                          |<--- git diff --staged ->|
                 |                          |                        |
                 |<--------------- git diff HEAD ---------------------->|
ComandoComparaÚsalo para
git diffTrabajo ↔ índiceVer lo que has cambiado y aún no has preparado.
git diff --stagedÍndice ↔ HEADVer exactamente lo que entraría en el próximo commit.
git diff HEADTrabajo ↔ HEADVer todo lo cambiado desde el último commit, preparado o no.

--staged y --cached son sinónimos; el segundo es el nombre clásico. Y ninguno de los tres necesita red ni escribir nada: son consultas.

Anatomía de un diff unificado

Este es un diff real del taller, con cada parte señalada:

diff --git a/notas.md b/notas.md          <- cabecera: compara estas dos rutas
index b3c6754..e4ba0db 100644             <- hashes de los blobs antes y después
--- a/notas.md                            <- versión de partida (la del índice o HEAD)
+++ b/notas.md                            <- versión de llegada (la del trabajo o índice)
@@ -3,3 +3,5 @@                           <- hunk: a partir de la línea 3, 3 vs 5 líneas
 - Revisar el inventario                   <- contexto (empieza por un espacio)
 - Preparar la demo
 - Cerrar el presupuesto
+- Enviar la factura                       <- añadida (empieza por +)
+- Comprar cafe                            <- añadida (empieza por +)
ElementoSignificado
diff --git a/… b/…Comienzo de la comparación de un archivo. Los prefijos a/ y b/ permiten distinguir los dos lados.
index …..…. 100644Hashes de los blobs de cada lado y el modo del archivo.
--- / +++Nombres de las versiones comparadas; /dev/null indica archivo nuevo o borrado.
@@ -3,3 +3,5 @@Cabecera del hunk: en el lado antiguo empieza en la línea 3 y dura 3; en el nuevo, empieza en la 3 y dura 5.
(espacio)Línea de contexto: no cambió, se muestra para ubicar el cambio.
-Línea eliminada respecto al lado antiguo.
+Línea añadida.
\ No newline at end of fileEl archivo de ese lado no termina en salto de línea. Es muy común cuando se mezclan editores.

Los números del hunk son del archivo, no de pantalla

-3,3 significa «en el archivo original, desde la línea 3, tres líneas». No es la posición del cambio en un sistema de coordenadas imaginario: es la línea real del archivo. Con varias ediciones verás varios hunks (@@) separados por contexto.

Opciones que ahorran tiempo

OpciónQué hace

También puedes comparar commits y ramas, no solo zonas:

git diff HEAD~1 HEAD          # el último commit frente a su padre
git diff main..feature        # dos ramas
git diff v0.1 v0.2 -- src/    # dos etiquetas, solo una carpeta
git show 2ee7587              # metadatos + diff de un commit

git add -p: preparar por trozos

Cuando un archivo tiene cambios que pertenecen a commits distintos, git add -p (o --patch) recorre sus hunks y pregunta qué hacer con cada uno:

git add -p

@@ -5,9 +5,11 @@
 - Reservar la sala
+- Comprar cafe

 ## Lunes

 - Enviar el resumen
+- Pagar la factura
(1/1) Stage this hunk [y,n,q,a,d,s,e,p,P,?]?
TeclaAcción
yPreparar este hunk (yes).
nNo prepararlo (no).
qSalir sin preparar este ni los siguientes.
aPreparar este hunk y todos los siguientes del archivo.
dIgnorar este y todos los siguientes del archivo.
sDividir el hunk en trozos más pequeños.
eEditar el hunk a mano para preparar solo algunas líneas.
j / kDejar este hunk pendiente y saltar al siguiente / anterior hunk sin decidir (J / K para cualquier hunk, decidido o no).
g / /Ir a un hunk concreto o buscar hunks por expresión regular.
p / PVolver a imprimir el hunk actual / anterior.
?Ayuda.

El flag -e combinado con s llega a permitir preparar una sola línea de un hunk. También funciona a la inversa para sacar del índice por trozos:

git restore --staged -p    # desprepara hunks concretos (módulo 2)

El orden importa poco, el contenido mucho

Preparar hunks no reordena líneas: cada hunk preparado escribe en el índice el contenido que tenía el archivo en esa parte. Lo que sí consigues es que el índice contenga una versión intermedia coherente, y eso es exactamente lo que hace falta para un commit atómico.

3 · Ejemplo mínimo

Un archivo con una línea nueva. El diff del trabajo frente al índice:

printf '# Notas del taller\n\n- Revisar el inventario\n- Preparar la demo\n- Cerrar el presupuesto\n' > notas.md
git add notas.md
git commit -m "docs: crear notas del taller"

printf '- Enviar la factura\n' >> notas.md
git diff

diff --git a/notas.md b/notas.md
index b3c6754..e4ba0db 100644
--- a/notas.md
+++ b/notas.md
@@ -3,3 +3,5 @@
 - Revisar el inventario
 - Preparar la demo
 - Cerrar el presupuesto
+- Enviar la factura

Se lee así: en el lado antiguo (a/) hay 3 líneas desde la 3; en el nuevo (b/) hay 5 desde la 3; la única línea nueva es - Enviar la factura. Y ahora el detalle que sorprende a todo el mundo:

git add notas.md
git diff          # sin salida
git diff --staged

diff --git a/notas.md b/notas.md
index b3c6754..e4ba0db 100644
--- a/notas.md
+++ b/notas.md
@@ -3,3 +3,5 @@
 - Revisar el inventario
 - Preparar la demo
 - Cerrar el presupuesto
+- Enviar la factura

git diff está vacío porque el índice y el disco coinciden. El cambio «se ha mudado» al diff --staged. No se ha perdido nada: has cambiado la zona de comparación.

4 · Ejemplo real

Ana ha mezclado en notas.md dos cambios de tareas distintas: uno del viernes y otro del lunes. Quiere dos commits separados, así que prepara por trozos:

git diff

git diff --staged

MM: preparado el café, pendiente la factura. Los dos diffs son complementarios y ninguno se solapa. Ya puede commitear el primero y dejar el segundo para otro commit.

Revisa siempre el diff preparado

Justo antes de confirmar, git diff --staged es la única fuente de verdad sobre lo que va a entrar. Si algo sobra, git restore --staged <ruta> (o -p para un trozo) lo devuelve al directorio de trabajo sin perder contenido.

5 · Buenas prácticas

HazEvitaPor qué
git diff --staged antes de cada commit Commitear sin revisar el índice Es la última oportunidad de detectar un archivo de más, un secreto o un cambio a medias.
git add -p cuando un archivo mezcla temas Separar archivos enteros a mano o hacer commits gigantes Permite commits atómicos sin reescribir el archivo temporalmente.
git diff --stat para una visión rápida Leer 500 líneas de diff para saber qué archivos cambiaron Primero el mapa, después el detalle.
git diff --check antes de publicar Ignorar espacios al final de línea y tabuladores sueltos Evita ruido en la revisión y conflictos tontos con compañeros.
git diff -w cuando solo cambió el formato Reformatear y funcional en el mismo commit Separar «reformatear» de «cambiar comportamiento» hace revisable el cambio.
Usar -- <ruta> para acotar Buscar el archivo entre cientos de líneas Comparar solo lo que te interesa es más rápido y menos propenso a error.

6 · Errores habituales

1. Usar git diff para ver lo que vas a commitear

Mal — mirar el diff equivocado 
git add notas.md
git diff           # ❌ vacío: el índice y el disco coinciden
# "¡Se han perdido mis cambios!"
Bien — el diff del índice es --staged 
git add notas.md
git diff --staged  # lo que entrará en el commit
git diff           # lo que aún no has preparado

No se pierde nada: has preparado un cambio y git diff ya no lo ve porque su trabajo es mostrar la diferencia entre disco e índice.

2. Creer que el diff está almacenado en el commit

Mal — «el commit guarda estas líneas» 
commit = diff congelado   ❌
Bien — el diff se calcula al vuelo 
git show HEAD             # compara el árbol del commit con el de su padre
git diff HEAD~5 HEAD      # compara dos árboles cualesquiera

Por eso cualquier par de estados se puede comparar, incluso ramas que nunca se han encontrado.

3. Preparar con add -p y seguir editando

Mal — editar después de preparar el trozo 
git add -p notas.md
printf '- Otra cosa\n' >> notas.md
git commit -m "docs: tareas"
# ❌ La línea nueva no entra: el índice ya estaba escrito
Bien — revisar después del último add 
git add -p notas.md
printf '- Otra cosa\n' >> notas.md
git status -s        # AM/MM o " M": hay algo fuera del índice
git add -p notas.md  # o decide dejarlo para otro commit

El índice es una foto; no sigue al archivo.

4. Confundir git diff HEAD con --staged

Mal — asumir que son equivalentes 
git diff HEAD      # incluye preparado Y no preparado
# ❌ No es lo mismo que "lo que voy a commitear"
Bien — elegir según la pregunta 
git diff HEAD      # "¿qué ha cambiado desde el último commit?"
git diff --staged  # "¿qué entrará en el commit?"

Si tienes cambios sin preparar, los dos resultados difieren.

5. Leer mal la cabecera del hunk

Mal — creer que -3,3 es un rango del índice global 
@@ -3,3 +3,5 @@   →  "líneas 3 a 6 del proyecto"   ❌
Bien — son líneas del archivo en cada lado 
@@ -3,3 +3,5 @@   →  antiguo: 3 líneas desde la 3
                     nuevo:   5 líneas desde la 3

Son coordenadas locales al archivo que aparece en la cabecera diff --git.

7 · Ejercicio guiado

Objetivo: partir un hunk en dos y conseguir dos commits limpios desde un mismo archivo.

  1. Prepara el escenario: 
    mkdir laboratorio-diff
cd laboratorio-diff
git init -b main
printf '# Notas del taller\n\n## Viernes\n\n- Revisar el inventario\n- Preparar la demo\n- Reservar la sala\n\n## Lunes\n\n- Cerrar el presupuesto\n- Llamar al cliente\n- Enviar el resumen\n' > notas.md
git add notas.md
git commit -m "docs: crear notas del taller"
  2. Introduce dos cambios separados: 
    printf '# Notas del taller\n\n## Viernes\n\n- Revisar el inventario\n- Preparar la demo\n- Reservar la sala\n- Comprar cafe\n\n## Lunes\n\n- Cerrar el presupuesto\n- Llamar al cliente\n- Enviar el resumen\n- Pagar la factura\n' > notas.md
git diff --stat

     notas.md | 2 ++
 1 file changed, 2 insertions(+)
  3. Prepara por trozos y divide el hunk: 
    git add -p

    Responde s para dividir, y al primer trozo (el café) y n al segundo (la factura).

  4. Verifica el estado mixto: 
    git status -s

    MM notas.md

    MM es la confirmación de que hay una versión preparada y otra pendiente en el mismo archivo.

  5. Confirma lo preparado y comprueba el contenido del commit: 
    git commit -m "docs: apuntar compra de cafe"
git show HEAD -- notas.md

    El diff del commit debe mostrar solo la línea - Comprar cafe. Si aparece también - Pagar la factura, la división no salió como creías.

  6. Confirma el segundo cambio por separado: 
    git add notas.md
git commit -m "docs: anadir pago de factura"
git log --oneline

    c3d9a12 (HEAD -> main) docs: anadir pago de factura
b07e445 docs: apuntar compra de cafe
2ee7587 docs: crear notas del taller

    Dos commits atómicos a partir de un único archivo. Este es el flujo que hace posible la lección siguiente.

8 · Reto

🎯 Preparar una sola línea

Consigue que en el índice entre una única línea de un hunk que contiene tres cambios, sin acotar por ruta ni crear archivos temporales. Al terminar, git diff --staged debe mostrar esa línea y solo esa.

Segunda parte: partiendo del mismo estado, desprepara esa línea concreta dejando el resto preparado, y explica qué comando has usado y por qué no pierde contenido.

Pista: en el diálogo de git add -p, además de y/n/s existe e, que abre el hunk en tu editor para que borres las líneas que no quieras preparar. Para la segunda parte, mira la ayuda de git restore --staged.

9 · Resumen

  • Hay tres diffs: trabajo↔índice (git diff), índice↔HEAD (--staged) y trabajo↔HEAD (git diff HEAD).
  • Los diffs se calculan; no están almacenados en el commit.
  • Un diff unificado tiene cabecera, hashes, y hunks con contexto ( ), eliminadas (-) y añadidas (+).
  • La cabecera @@ -a,b +c,d @@ indica líneas del archivo antiguo y del nuevo, no del proyecto.
  • git add -p prepara por trozos; s divide, e edita y y/n deciden.
  • Después de preparar, git diff puede quedar vacío: el cambio está en --staged.

git diff --stagedÍndice frente a HEAD (lo que entrará)

10 · Preguntas frecuentes

¿Por qué git diff no muestra nada después de git add?

Porque git diff compara el directorio de trabajo con el índice, y al preparar has copiado el contenido al índice: ya coinciden. El cambio sigue ahí; míralo con git diff --staged. No se ha perdido nada.

¿Puedo despreparar solo una parte de un archivo?

Sí: git restore --staged -p <ruta> recorre los hunks del índice y permite sacar los que quieras, igual que git add -p pero al revés. También existe git reset -p, la forma clásica. El contenido del directorio de trabajo no se toca.

¿Qué significan los prefijos a/ y b/?

Son convenciones para distinguir los dos lados de la comparación dentro del mismo diff: a/ es la versión de partida y b/ la de llegada. Se pueden quitar con --no-prefix, y muchas herramientas (patch, git apply) dependen de ellos para saber a qué archivo aplicar.

¿Qué muestra Git con un archivo binario?

Una línea del tipo Binary files a/imagen.png and b/imagen.png differ. No intenta mostrar texto porque no es texto. Para imágenes existen visores externos con git difftool, y para archivos de texto detectados como binarios puede forzarse con atributos (diff en .gitattributes, módulo 1, lección 4).

¿Puedo comparar un archivo que no está en el repositorio?

Sí, con git diff --no-index archivo1 archivo2. Es útil para comparar dos copias externas sin crear un repositorio; incluso acepta directorios completos. No necesita que estés dentro de un repositorio.
