El primer repositorio

Módulo 1 · Commits 🕐 30 minutos

1 · Introducción

Ya conoces el modelo: objetos, hashes, tres zonas. Es hora de encadenar los comandos que lo usan —git init, git add, git commit— y de saber qué acaba de aparecer en .git/ cada vez que los ejecutas. Es la primera vez que escribes en el taller, el repositorio que nos acompañará hasta el proyecto final.

En esta lección también resolverás una molestia moderna: la rama por defecto. Durante años se llamó master; hoy lo estándar es main. Veremos las tres formas de conseguirlo (configuración global, init -b y renombrar la rama) y por qué git branch -m en un repositorio recién creado es un caso especial que conviene entender.

Por qué existe esta lección

Porque git init no crea un commit, git add no guarda en la historia y el primer commit es el único que no tiene padre. Son tres detalles que reaparecen todo el tiempo: al crear un repositorio vacío, al leer un grafo y al entender por qué reset sobre el primer commit es distinto.

2 · Teoría

git init: crear la base de datos

git init no copia nada ni crea carpetas de versiones: crea el directorio .git/, que es todo el repositorio. Tu carpeta de trabajo se llama el árbol de trabajo, y sin .git/ no es un repositorio, solo archivos.

mkdir taller
cd taller
git init -b main

Initialized empty Git repository in C:/Users/ana/taller/.git/

Esto es lo que acaba de crear, recién nacido y sin un solo commit:

.git/
├── HEAD          -> contiene "ref: refs/heads/main"
├── config        -> configuración LOCAL de este repositorio
├── description   -> texto para servidores Git (irrelevante aquí)
├── hooks/        -> scripts de ejemplo (módulo 5)
├── info/         -> exclude: exclusiones locales, no versionadas
├── objects/      -> la base de datos de objetos (vacía)
└── refs/
    ├── heads/    -> ramas (vacío)
    └── tags/     -> etiquetas (vacío)
ElementoPara qué sirve
HEADIndica la rama actual. Al inicio contiene ref: refs/heads/main, apuntando a una rama que aún no existe («unborn branch»).
configConfiguración local: remotos, identidad del proyecto, opciones. Lo vimos en la lección 2 del módulo 0.
objects/Blobs, trees, commits y tags comprimidos, uno por hash.
refs/heads/Un archivo por rama; su contenido es el hash del último commit de esa rama.
refs/tags/Un archivo por etiqueta.
hooks/Plantillas de scripts que Git ejecuta en momentos concretos (pre-commit, commit-msg…).
info/excludeComo un .gitignore privado que no se versiona.
indexAún no existe: aparece con el primer git add. Es el área de preparación.
logs/Aún no existe: aparece con el primer commit y guarda el reflog (módulo 6).

Borrar .git/ no «limpia el proyecto»

Elimina toda la historia, las ramas, las etiquetas y los remotos. Si alguna vez «desconfiguras» un repositorio, no borres esa carpeta como primera opción: casi todo tiene arreglo con reflog, reset o fetch.

La rama por defecto: master, main y cómo cambiarla

Históricamente la rama inicial se llamó master. Desde 2020, la convención mayoritaria es main. Tienes tres formas de fijarlo:

MétodoComandoCuándo
Configuración global (una vez) git config --global init.defaultBranch main Afecta a todos los repositorios nuevos. Es lo recomendado.
Al inicializar git init -b main Cuando quieres decidirlo por repositorio, sin tocar la configuración.
Renombrar después git branch -m main En un repositorio ya creado (con o sin commits) y rama actual master.

El tercer caso tiene una particularidad: en un repositorio recién inicializado, master aún no existe como rama (es una «unborn branch»), pero git branch -m main funciona igual y reescribe .git/HEAD:

git init -b master
cat .git/HEAD
git branch -m main
cat .git/HEAD

ref: refs/heads/master
ref: refs/heads/main

El flag -m es move/rename. La variante -M fuerza el renombrado si el destino ya existe. Y para renombrar una rama que no es la actual: git branch -m viejo nuevo.

Si el repositorio ya está publicado

Renombrar la rama local no renombra la del remoto. Habría que borrar la antigua en el remoto y publicar la nueva; mientras tanto pueden coexistir. Lo veremos en el módulo 5. En un repositorio nuevo no hay problema: hazlo antes del primer push.

Los tres comandos del primer commit

   git init                 git add archivo            git commit -m "msg"
  ───────────              ─────────────────          ──────────────────────
  crea .git/ y HEAD     →   escribe el blob y su    →  crea el tree desde el índice
  sin commits               hash en .git/index         y el objeto commit; mueve main
  1. git init -b main: crea la base de objetos vacía y deja HEAD apuntando a refs/heads/main.
  2. git add <archivo>: calcula el blob, lo guarda en .git/objects/ y anota su hash en .git/index.
  3. git commit -m "asunto": construye un tree con el contenido del índice, crea un objeto commit (sin padre, porque es el primero), escribe el hash en refs/heads/main y registra HEAD en logs/HEAD.

Ese primer commit, sin parent, es el commit raíz. Todos los demás descienden de él.

Leer la historia: log y show

git log --oneline
git log --oneline --graph --decorate --all
git show
  • --oneline: hash corto + asunto, una línea por commit.
  • --graph: dibuja el grafo con caracteres; imprescindible cuando hay ramas.
  • --decorate: muestra a dónde apuntan HEAD, las ramas y las etiquetas.
  • --all: incluye todas las referencias, no solo la rama actual.
  • git show sin argumentos muestra el commit HEAD: metadatos y el diff frente a su padre.

En un repositorio sin commits, la salida es un error explícito: fatal: your current branch 'main' does not have any commits yet. No es un fallo de instalación; simplemente aún no hay nada que mostrar.

3 · Ejemplo mínimo

De cero a historia en cuatro comandos:

mkdir taller
cd taller
git init -b main

printf '# Notas del taller\n\nProyecto de practica del curso de Git.\n' > README.md
git add README.md
git commit -m "docs: crear README inicial"

Initialized empty Git repository in C:/Users/ana/taller/.git/
[main (root-commit) b91f4c2] docs: crear README inicial
 1 file changed, 3 insertions(+)
 create mode 100644 README.md

Tres detalles en la línea entre corchetes: la rama (main), el flag root-commit (no tiene padre) y el hash corto. Después, el resumen de archivos y el modo con el que entra el archivo. Ahora mira la historia:

git log --oneline --decorate
git status

b91f4c2 (HEAD -> main) docs: crear README inicial
On branch main
nothing to commit, working tree clean

(HEAD -> main) significa que estás en main y que esa rama apunta a ese commit. «working tree clean» significa que disco, índice y HEAD coinciden. El repositorio está sano.

4 · Ejemplo real

El taller arranca de verdad con notas.md y dos commits:

printf '# Notas del taller\n\n- Revisar el inventario\n- Preparar la demo\n' > notas.md
git add notas.md
git commit -m "docs: crear notas del taller"

printf '\n- Cerrar el presupuesto\n' >> notas.md
git add notas.md
git commit -m "docs: anadir presupuesto"

$ git log --oneline --graph --decorate
* 4d81e07 (HEAD -> main) docs: anadir presupuesto
* 2ee7587 docs: crear notas del taller

Dos commits en línea recta: cada uno tiene un solo padre. Veamos los metadatos y el diff del primero:

git show 2ee7587

commit 2ee7587541447d837b26ca7e036ec2ceda983b54
Author: Ana Torres <ana@ejemplo.com>
Date:   Sat Oct 17 18:13:46 2026 +0200

    docs: crear notas del taller

diff --git a/notas.md b/notas.md
new file mode 100644
index 0000000..b3c6754
--- /dev/null
+++ b/notas.md
@@ -0,0 +1,4 @@
+# Notas del taller
+
+- Revisar el inventario
+- Preparar la demo

Ese diff no está almacenado: Git lo calcula comparando el árbol de 2ee7587 con su padre. En el caso del commit raíz, el padre es el árbol vacío, por eso aparece new file mode y todas las líneas como añadidas.

Y así, de un vistazo, se ve qué archivos tocó cada commit:

git log --oneline --stat

4d81e07 docs: anadir presupuesto
 notas.md | 1 +
 1 file changed, 1 insertion(+)
2ee7587 docs: crear notas del taller
 notas.md | 4 ++++
 1 file changed, 4 insertions(+)

El mismo contenido, otro hash de commit

Si repites estos commits en tu máquina, los hashes serán distintos: incluyen la fecha, la zona horaria y tu identidad. Los hashes de los blobs sí coincidirán si el contenido coincide. Por eso los ejemplos muestran hashes ilustrativos.

6 · Errores habituales

1. Inicializar un repositorio dentro de otro

Mal — git init en una subcarpeta 
cd proyecto/
cd src/
git init
# ❌ Desde la raíz, 'src' aparece como un repositorio incrustado y Git avisa raro
Bien — un repositorio en la raíz del proyecto 
cd proyecto/
git init -b main
git status    # cubre todo el proyecto, incluidas subcarpetas

Si necesitas proyectos independientes dentro de otro, la herramienta correcta es un submódulo o, mejor, repositorios separados.

2. Borrar .git/ como primera solución

Mal — «se me rompió el repo, lo vuelvo a clonar» 
rm -rf .git    # ❌ se pierde lo no publicado: commits, ramas y stashes
Bien — diagnosticar antes 
git status
git log --oneline --all
git reflog          # el historial de movimientos de HEAD
git fsck --full     # integridad

Casi siempre hay una salida. reflog existe precisamente para esto (módulo 6).

3. Creer que git add crea el repositorio

Mal — esperar un commit tras el add 
git add README.md
git log
# ❌ fatal: your current branch 'main' does not have any commits yet
Bien — hacen falta init, add y commit 
git init -b main
git add README.md
git commit -m "docs: crear README"

El add solo escribe en el índice. La historia empieza con el primer commit.

4. Renombrar la rama con checkout antiguo

Mal — arrastrar checkout -b para renombrar 
git checkout -b main
# ❌ Eso CREA una rama nueva desde donde estés, no renombra la actual
Bien — branch -m renombra 
git branch -m main          # renombra la rama actual
git branch -m viejo nuevo   # renombra otra

checkout se ha partido en dos comandos con roles claros: switch para moverse y crear ramas, y restore para archivos. Renombrar siempre fue branch -m.

5. Olvidar un archivo en el primer commit

Mal — crear un commit «arreglo» inmediato 
git commit -m "docs: README"
git commit -m "docs: perdona, faltaba el .gitignore"
# ❌ Ruido en la historia para algo que aún no has publicado
Bien — enmendar mientras es local 
git add .gitignore
git commit --amend --no-edit

Enmendar cambia el hash del commit y es seguro solo si nadie lo ha publicado. Lo veremos con detalle en la lección 3 de este módulo.

7 · Ejercicio guiado

Objetivo: crear el taller, hacer dos commits y verificar que la rama y HEAD apuntan donde crees.

  1. Crea el repositorio con la rama correcta: 
    mkdir taller
cd taller
git init -b main
git config user.name "Ana Torres"
git config user.email "ana@ejemplo.com"
git branch --show-current

    main
  2. Primer commit: 
    printf '# Notas del taller\n\n- Revisar el inventario\n- Preparar la demo\n' > notas.md
git add notas.md
git commit -m "docs: crear notas del taller"

    [main (root-commit) 2ee7587] docs: crear notas del taller
 1 file changed, 4 insertions(+)
 create mode 100644 notas.md
  3. Segundo commit, sobre el mismo archivo: 
    printf '\n- Cerrar el presupuesto\n' >> notas.md
git add notas.md
git commit -m "docs: anadir presupuesto"

    [main 4d81e07] docs: anadir presupuesto
 1 file changed, 1 insertion(+)
  4. Comprueba el grafo: 
    git log --oneline --graph --decorate

    * 4d81e07 (HEAD -> main) docs: anadir presupuesto
* 2ee7587 docs: crear notas del taller

    Sin ramas intermedias: dos commits en línea, y main apunta al último.

  5. Compara los objetos de ambos commits: 
    git cat-file -p HEAD | head -3
git cat-file -p HEAD~1 | head -3

    Verás que HEAD tiene un parent (el otro commit) y que HEAD~1 no lo tiene: es el commit raíz. Los trees son distintos pero comparten el blob de las líneas que no cambiaron.

  6. Deja el repositorio limpio: 
    git status

    On branch main
nothing to commit, working tree clean

8 · Reto

🎯 Renombrar sin perder nada

Crea un repositorio con git init (sin -b) en una máquina donde init.defaultBranch sea master. Haz dos commits, renombra la rama a main y verifica que HEAD, git branch --show-current y git log coinciden. Después explica en qué se diferencia renombrar una rama con commits de renombrar una rama «sin nacer» (sin commits).

Comprueba en disco qué archivos cambiaron: inspecciona .git/HEAD y el contenido de .git/refs/heads/. ¿Se movió algún commit?

Pista: cat .git/HEAD, ls .git/refs/heads/ y git rev-parse HEAD antes y después del renombrado. Compara los hashes: el commit no cambia, solo el nombre.

9 · Resumen

  • git init crea .git/: toda la base de objetos, refs y configuración local. No crea ningún commit.
  • Tras init, HEAD contiene ref: refs/heads/main aunque la rama no exista todavía.
  • El primer commit es el commit raíz: no tiene parent.
  • git add escribe en el índice; git commit construye el tree y crea el objeto commit.
  • main se fija con init.defaultBranch, con git init -b main o renombrando con git branch -m main.
  • git log --oneline --graph --decorate es la vista estándar del grafo; git show detalla un commit.

git branch --show-currentMuestra en qué rama estás

10 · Preguntas frecuentes

¿Puedo cambiar la rama por defecto de un repositorio que ya tiene commits?

Sí: git branch -m master main si master es la rama actual, o git branch -m master main explícito con el nombre viejo. Los commits no cambian, solo la referencia. Si el repositorio ya está publicado, habrá que renombrar también en el remoto y actualizar el seguimiento (módulo 5).

¿Qué diferencia hay entre git init y git clone?

init crea un repositorio vacío, sin historia. clone copia un repositorio existente completo —objetos, ramas, etiquetas y remotos— y además hace checkout de una rama. Clonar un repositorio de una sola rama sigue trayendo todo el historial.

¿Por qué git log me dice que la rama no tiene commits todavía?

Porque has inicializado y añadido archivos, pero aún no has confirmado nada. El índice no es historia. Ejecuta git commit -m "…" y log funcionará. Es el error más habitual justo después de git init.

¿Qué pasa si borro un archivo de .git/ por accidente?

Depende de cuál. Si borras refs/heads/main, pierdes el puntero de la rama pero los commits siguen ahí: git reflog o git fsck --lost-found pueden recuperarlos. Si borras objetos de objects/, esos commits se pierden de verdad. Por eso nunca se toca .git/ a mano.

¿Cuántos commits debería tener antes de publicar?

No hay un número mágico, pero sí una regla: cada commit debe ser una unidad coherente y comprensible. Publicar tres commits atómicos es mejor que publicar uno gigante con «cambios varios». En el módulo 4 aprenderás a reorganizarlos antes de compartirlos.
