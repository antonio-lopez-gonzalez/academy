.gitignore y .gitattributes

Módulo 1 · Commits 🕐 30 minutos

1 · Introducción

Sin reglas, un repositorio se llena de node_modules/, dist/, .DS_Store, logs, bases de datos locales y —lo más grave— archivos .env con secretos. .gitignore es donde se declara qué no debe versionarse nunca, y .gitattributes donde se declara cómo debe tratarse lo que sí se versiona, empezando por los finales de línea.

Ambos archivos son texto, se versionan y viajan con el repositorio, de modo que las reglas son las mismas para todo el equipo. En esta lección aprenderás la sintaxis de patrones, por qué ignorar un archivo que ya está rastreado no sirve de nada, y cómo arreglar un repositorio que ya arrastra miles de cambios de CRLF con git add --renormalize.

Por qué existe esta lección

Un repositorio limpio es un repositorio en el que los diffs dicen la verdad. Los dos problemas más comunes de cualquier equipo —«se me coló node_modules» y «todo el archivo aparece cambiado»— se resuelven aquí, y el segundo es el origen de innumerables conflictos y revisiones imposibles.

2 · Teoría

Rastreado, sin rastrear e ignorado

Para Git, un archivo está en uno de tres estados respecto al repositorio:

EstadoSignificadoAparece en git status
Rastreado (tracked)Ya está en algún commit (o en el índice). Git lo vigila.Sí, cuando cambia.
Sin rastrear (untracked)No está en ningún commit: Git lo ve pero no lo cuida.Sí, con ??.
IgnoradoUna regla le dice a Git que no lo anuncie ni lo añada.Solo con --ignored, como !!.

La regla que más se olvida

.gitignore solo afecta a archivos sin rastrear. Si un archivo ya está en la historia, añadirlo al .gitignore no cambia nada: Git sigue viéndolo. Para dejar de rastrearlo hay que sacarlo del índice con git rm --cached (y commitear el cambio de índice).

Dónde se declaran las reglas

SitioAlcance¿Se versiona?
.gitignore en la raíz o en un subdirectorioEse directorio y sus descendientesSí: es la forma de compartir reglas con el equipo.
.git/info/excludeSolo tu clonNo: para gustos locales del proyecto.
Archivo global (core.excludesFile)Todos tus repositoriosNo: para .DS_Store, .idea/, *.swp…

Precedencia, de mayor a menor prioridad:

  1. Patrones pasados por línea de comandos (pocos comandos lo permiten).
  2. .gitignore del directorio del archivo y de sus directorios padres: los más profundos ganan.
  3. .git/info/exclude.
  4. El archivo global de core.excludesFile.

Y dentro de un mismo archivo, la última regla que coincide decide. Eso es lo que hace posible la negación con !.

Sintaxis de patrones

PatrónQué ignora
*.logCualquier archivo .log en cualquier profundidad. Un patrón sin / casa por nombre en cualquier nivel.
build/Cualquier directorio llamado build, a cualquier profundidad. La barra final significa «directorio».
/build/Solo el directorio build de la raíz. La barra inicial ancla al inicio.
doc/*.txtSolo los .txt hijos directos de doc/, no los de subcarpetas.
doc/**/*.txtCualquier .txt a cualquier profundidad bajo doc/.
**/tmp/Cualquier directorio tmp en cualquier nivel.
? y [0-9]Un carácter cualquiera y rangos: informe?.[0-9].pdf.
!importante.logNegación: vuelve a incluir lo que otro patrón excluía, si es la última coincidencia.
# al inicioComentario. Para un nombre literal que empiece por #, escríbelo como \#.
\ al finalEspacio literal: los espacios finales se ignoran salvo que vayan escapados.

No se puede reintroducir un archivo si su carpeta está excluida

Git no entra en un directorio ignorado, así que !dist/keep.txt no sirve si antes escribiste dist/. La solución es excluir el contenido en lugar del directorio: dist/* más !dist/keep.txt. Sin la barra final, la carpeta no queda fuera y la negación funciona.

Dejar de rastrear sin borrar

git rm --cached archivo.env      # lo quita del índice, deja el archivo en disco
git rm -r --cached node_modules  # igual, para todo un directorio
git commit -m "chore: dejar de rastrear artefactos"

Sin --cached, git rm borra además el archivo del disco. Con él, el archivo sigue ahí pero pasa a estar sin rastrear (y, si hay una regla, ignorado). Ten en cuenta que la historia ya contiene las versiones anteriores: sacarlo ahora no las elimina de los commits antiguos.

.gitattributes: cómo se trata el contenido

Es un archivo en la raíz (o en subdirectorios) con líneas del tipo patrón atributo [valor]. Los atributos más útiles:

AtributoQué hace
text=autoDeja que Git decida si el archivo es texto y normalice los finales de línea en el repositorio.
text / -textFuerza que se trate como texto / que no se toque (binario).
eol=lf / eol=crlfQué final de línea se escribe al hacer checkout. Implica text y tiene prioridad sobre core.autocrlf.
binaryAtajo de -text -diff: no convertir ni intentar comparar como texto.
diff / -diffSi Git debe mostrarlo en los diffs de texto.
linguist-generatedLo marca como generado (GitHub lo oculta en las revisiones).
export-ignoreExcluye el archivo de git archive.
filterPara herramientas como Git LFS.

El caso estrella es la política de finales de línea, que se declara una vez y vale para todos:

# .gitattributes
* text=auto eol=lf        # todo el proyecto en LF dentro del repositorio
*.bat text eol=crlf       # los scripts de Windows necesitan CRLF
*.ps1 text eol=crlf
*.png binary              # los binarios no se tocan
*.pdf -text

Con esto, cada máquina y cada editor dejan de importar: Git normaliza en el commit y aplica la política en el checkout. Es lo que hace que «funcione igual en Windows que en Linux» deje de ser una aspiración.

Renormalizar un repositorio con líos de finales de línea

Si el repositorio ya tiene el desastre, no basta con añadir .gitattributes: hay que reescribir el índice para que el contenido almacenado se normalice.

# 1. Declara la política
printf '* text=auto eol=lf\n' > .gitattributes
git add .gitattributes
git commit -m "chore: normalizar finales de linea"

# 2. Reescribe el indice segun los atributos (Git 2.16+)
git add --renormalize .
git commit -m "chore: renormalizar finales de linea"

# 3. Audita el resultado
git ls-files --eol

warning: in the working copy of '.gitattributes', CRLF will be replaced by LF the next time Git touches it
i/lf    w/crlf  attr/text=auto eol=lf 	.gitattributes
i/lf    w/crlf  attr/text=auto eol=lf 	script.sh

La salida de git ls-files --eol se lee en tres columnas: i/ es el final de línea en el índice, w/ el del directorio de trabajo y attr/ los atributos aplicados. En el ejemplo, el índice ya está en LF (i/lf) mientras el disco sigue en CRLF (w/crlf): la conversión del árbol de trabajo ocurre en el siguiente checkout. Con el árbol limpio y todo commiteado, puedes forzarlo:

git checkout -- .     # reescribe el trabajo desde el índice (¡sin cambios sin guardar!)
git ls-files --eol    # ahora i/lf y w/lf

Para inspeccionar los atributos de un archivo concreto, git check-attr -a <archivo> responde con el valor efectivo de cada atributo.

3 · Ejemplo mínimo

Un .gitignore típico de proyecto Node y la comprobación de que hace lo que crees:

cat > .gitignore <<'EOF'
node_modules/
dist/
*.log
.env
EOF

git check-ignore -v node_modules/x.js dist/app.js app.log

.gitignore:1:node_modules/	node_modules/x.js
.gitignore:2:dist/	dist/app.js
.gitignore:3:*.log	app.log

git check-ignore -v dice, para cada ruta, el archivo, la línea y el patrón que la ignoran. Las columnas están separadas por un tabulador: archivo:línea:patrón<TAB>ruta. Es la herramienta para depurar un .gitignore que «no funciona».

Y así se ve qué está ignorado y qué no:

git status --ignored -s

?? .env
?? .gitignore
!! app.log
!! debug.log
!! dist/
!! node_modules/

Fíjate: .env aparece sin rastrear (??) porque no está en el .gitignore del ejemplo. Si contuviera secretos, sería el peor estado posible: visible y a un git add . de distancia de quedar publicado. Los ignorados son los que empiezan por !!.

4 · Ejemplo real

El taller se trabaja en Windows, macOS y Linux. Ana detecta diffs enormes en un archivo que solo cambió una palabra, así que comprueba la política de finales de línea:

git config --show-origin --get core.autocrlf
git ls-files --eol

file:C:/Program Files/Git/etc/gitconfig	true
i/crlf  w/crlf  attr/                 	script.sh
i/crlf  w/crlf  attr/                 	notas.md

El índice guarda CRLF y no hay atributos: cada máquina decide por su cuenta. La solución es declarar la política en el repositorio y renormalizar:

printf '* text=auto eol=lf\n*.bat text eol=crlf\n*.png binary\n' > .gitattributes
git add .gitattributes
git commit -m "chore: politica de finales de linea"

git add --renormalize .
git status -s

M  script.sh
M  notas.md

El --renormalize ha vuelto a escribir en el índice el contenido ya normalizado, y esos cambios están preparados para commitear. Tras el commit, la auditoría confirma la normalización en el índice:

git ls-files --eol

i/lf    w/crlf  attr/text=auto eol=lf 	script.sh
i/lf    w/crlf  attr/text=auto eol=lf 	notas.md
i/lf    w/crlf  attr/text=auto eol=lf 	.gitattributes

El índice ya está en LF. El directorio de trabajo se reescribirá en el siguiente checkout; con el árbol limpio, git checkout -- . lo hace ahora mismo. Desde este momento, un compañero en Linux y otro en Windows escriben y leen el mismo contenido, y los diffs dejan de mentir.

¿Y si el proyecto necesita CRLF en Windows?

Se declara por tipo de archivo: *.bat text eol=crlf, *.ps1 text eol=crlf. Todo lo demás va en LF. Git convierte al hacer checkout según el atributo, en cualquier plataforma; no hace falta que cada persona configure core.autocrlf.

5 · Buenas prácticas

HazEvitaPor qué
Crear el .gitignore en el primer commit Añadirlo cuando ya hay 5 000 archivos rastreados Ignorar solo funciona sobre lo no rastreado: después hay que limpiar el índice y la historia.
Ignorar dependencias, artefactos de build, logs, bases de datos locales y secretos Versionar node_modules/, dist/, *.log, .env Son reproducibles o locales; versionarlos llena el historial de ruido y riesgos.
Versionar lockfiles (package-lock.json, pnpm-lock.yaml) Ignorarlos «porque son generados» Fijan versiones exactas: son la garantía de reproducibilidad de las instalaciones.
Poner en el excludes global los archivos del editor y del sistema Meter .vscode/ o .idea/ en el .gitignore del equipo Son preferencias personales; ensucian el proyecto sin aportar nada a los demás.
Declarar la política de finales de línea en .gitattributes Depender de core.autocrlf en cada máquina Es una regla del proyecto, versionada y compartida; no un ajuste local.
Verificar con git check-ignore -v y git status --ignored Confiar en que el patrón «seguro que funciona» Un patrón mal escrito deja el archivo visible sin que te enteres.

6 · Errores habituales

1. Añadir al .gitignore un archivo ya rastreado

Mal — esperar que desaparezca del repo 
printf 'node_modules/\n' >> .gitignore
git status
# ❌ node_modules sigue apareciendo: ya está rastreado
Bien — sacarlo del índice 
git rm -r --cached node_modules
git commit -m "chore: dejar de rastrear node_modules"

La regla se aplica a partir de ahora; el historial conserva las versiones anteriores.

2. Borrar archivos con git rm sin querer

Mal — git rm cuando solo querías desrastrear 
git rm .env
# ❌ borra el archivo del disco: adiós a la configuración local
Bien — --cached deja el archivo en su sitio 
git rm --cached .env
git status -s        # D  .env  -> el archivo sigue en disco

Y si ya lo borraste, git restore .env lo recupera desde HEAD… si estaba confirmado. Si no, se perdió.

3. Intentar reintroducir un archivo dentro de una carpeta ignorada

Mal — excluir el directorio y negar un hijo 
dist/
!dist/keep.txt      # ❌ no funciona: Git no entra en dist/
Bien — excluir el contenido, no el directorio 
dist/*
!dist/keep.txt      # ✅ la negación sí se evalúa

La regla de Git es explícita: no se puede volver a incluir un archivo si su directorio padre está excluido.

4. Ignorar archivos que sí deben versionarse

Mal — ampliar el patrón sin pensar 
*.json      # ❌ ignora package.json y tsconfig.json
*.config.js # ❌ ignora la configuración del proyecto
Bien — patrones concretos y verificados 
coverage/
*.local.json
.vscode/settings.json

Antes de commitear un .gitignore nuevo, ejecuta git status --ignored -s y revisa que no se haya comido nada importante.

5. Confiar en el .gitignore para ocultar secretos ya publicados

Mal — «lo ignoro y ya está» 
printf '.env\n' >> .gitignore   # demasiado tarde: .env ya está en la historia
Bien — rotar el secreto y sacarlo del índice 
git rm --cached .env
git commit -m "chore: dejar de rastrear .env"
# Además: invalida la credencial en el proveedor. La historia puede contenerla todavía.

Sacar un secreto de la historia requiere reescribirla —un procedimiento de alto riesgo que afecta a todo el equipo y a los despliegues—. El curso no da una receta operativa para purgar remotos publicados: si te ocurre, considera el secreto comprometido, rótalo y consulta la documentación oficial.

6. Mezclar core.autocrlf y seguir culpando al diff

Mal — depender del instalador 
Windows: core.autocrlf=true   Linux: core.autocrlf=input   macOS: false
Bien — una política versionada y renormalizada 
git config --global core.autocrlf false
printf '* text=auto eol=lf\n' > .gitattributes
git add --renormalize .

La conversión pasa a definirse en el repositorio, donde todos la comparten.

7 · Ejercicio guiado

Objetivo: crear un .gitignore, colar un directorio generado por error y arreglarlo correctamente sin borrar archivos.

  1. Crea el repositorio y un artefacto generado: 
    mkdir laboratorio-ignore
cd laboratorio-ignore
git init -b main
printf '# Taller\n' > README.md
mkdir -p dist node_modules
printf 'console.log("build");\n' > dist/app.js
printf 'module.exports = {};\n' > node_modules/lib.js
git add .
git commit -m "chore: base"
  2. Declara las reglas y comprueba que no bastan: 
    printf 'node_modules/\ndist/\n*.log\n.env\n' > .gitignore
git status -s
git check-ignore -v dist/app.js

    ?? .gitignore
.gitignore:2:dist/	dist/app.js

    dist/app.js está ignorado pero sigue rastreado desde el commit anterior: ignorar no lo saca.

  3. Sácalos del índice sin tocar el disco: 
    git rm -r --cached dist node_modules
git status -s

    D  dist/app.js
D  node_modules/lib.js
?? .gitignore

    Las rutas aparecen preparadas como borrado (D): --cached registra el borrado en el índice, pero los archivos siguen intactos en el disco.

  4. Confirma el cambio y verifica: 
    git add .gitignore
git commit -m "chore: ignorar artefactos generados"
git status --ignored -s
ls dist node_modules

    !! dist/
!! node_modules/

    ls debe mostrar dist/app.js y node_modules/lib.js: se han dejado de rastrear, no se han borrado.

  5. Añade la política de finales de línea: 
    printf '* text=auto eol=lf\n*.bat text eol=crlf\n' > .gitattributes
git add .gitattributes
git commit -m "chore: politica de finales de linea"
git check-attr -a README.md

    README.md: text: auto
README.md: eol: lf
  6. Audita: 
    git ls-files --eol

    Los archivos de texto deben mostrar attr/text=auto eol=lf y un final coherente en el índice. Si ves i/crlf, ejecuta git add --renormalize . y commitea el resultado.

8 · Reto

🎯 Solo documentación

Configura un .gitignore que ignore todo el contenido del repositorio excepto los archivos Markdown (*.md) y todos los directorios necesarios para poder descender hasta ellos. Comprueba con git status --ignored -s que solo aparecen como no rastreados los .md, y con git check-ignore -v qué regla se aplica a un archivo cualquiera dentro de una subcarpeta.

Segunda parte: añade una excepción para que docs/ completo (cualquier extensión) tampoco se ignore, y explica por qué hace falta ese orden concreto de reglas.

Pista: tres reglas bastan para la primera parte: ignorar todo, volver a incluir los directorios para que Git pueda entrar en ellos, e incluir los Markdown. Recuerda que la última regla que coincide gana, así que el orden es la semántica.

9 · Resumen

  • .gitignore solo afecta a archivos sin rastrear; hay que sacar del índice los ya rastreados con git rm --cached.
  • Un patrón sin / casa por nombre en cualquier nivel; con / inicial, solo desde la raíz; con / final, solo directorios.
  • La última regla que coincide gana; ! vuelve a incluir, salvo si un directorio padre está excluido.
  • Para ignorar en todos tus repos usa el archivo global de core.excludesFile; para un proyecto concreto, .git/info/exclude.
  • git check-ignore -v muestra el patrón responsable; git status --ignored -s enseña los ignorados con !!.
  • .gitattributes define cómo se trata el contenido: * text=auto eol=lf es la política recomendada, con excepciones para .bat y binarios.
  • git add --renormalize . reescribe el índice según los nuevos atributos; git ls-files --eol audita el resultado.

git check-ignore -v <ruta>Muestra archivo, línea y patrón que ignora esa ruta
git status --ignoredIncluye los archivos ignorados (!!)
git rm --cached <ruta>Quita del índice sin borrar del disco
git add -f <ruta>Fuerza a añadir algo ignorado (excepcional)

10 · Preguntas frecuentes

¿Por qué mi .gitignore no ignora un archivo?

Las tres causas habituales: el archivo ya estaba rastreado (hay que sacarlo del índice), un patrón posterior lo vuelve a incluir con !, o estás intentando reintroducir algo cuyo directorio padre está excluido. Ejecuta git check-ignore -v <ruta>: te dirá qué regla está ganando.

¿Cómo ignoro un archivo solo en mi máquina?

Añádelo a .git/info/exclude (solo ese repositorio) o a tu archivo global de core.excludesFile (todos tus repositorios). Así no impones tus preferencias al equipo ni ensucias el .gitignore compartido.

He commiteado node_modules por error, ¿qué hago?

Primero git rm -r --cached node_modules, añade la regla al .gitignore y commitea. La historia anterior todavía contiene esos archivos: si es un problema real (por tamaño o por secretos), hay que reescribir y coordinar con el equipo; el curso no da receta de reescritura masiva del remoto.

¿Qué diferencia hay entre text=auto y core.autocrlf?

text=auto es un atributo del repositorio: viaja con el código y se aplica a todos. core.autocrlf es configuración de tu máquina y puede ser distinta en cada persona. El atributo eol además tiene prioridad sobre la configuración local, y es lo que permite trabajar en equipo sin sorpresas.

¿Puedo forzar la inclusión de un archivo ignorado?

Sí, con git add -f archivo. Es útil en casos muy concretos, como versionar un dist/ preparado para despliegues sin build. Como norma general, si has tenido que forzarlo, revisa la regla: probablemente está demasiado amplia.
