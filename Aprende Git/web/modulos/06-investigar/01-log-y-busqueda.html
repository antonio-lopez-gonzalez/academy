log: el grafo, los filtros y la búsqueda

Módulo 6 · Investigar 🕐 35 minutos

1 · Introducción

Hasta ahora has usado git log como quien mira el retrovisor: una lista de mensajes de arriba abajo. Pero log no es una lista, es una ventana al grafo: puede dibujarlo, filtrarlo por autor, fecha, mensaje o ruta, y buscar el momento exacto en que un texto apareció o desapareció del código. Esta lección convierte log en tu herramienta forense.

La pregunta que resuelve esta lección es siempre la misma: "¿cuándo cambió esto, quién y por qué?". Saber responderla rápido es la diferencia entre arreglar un bug en cinco minutos y pasar una tarde leyendo diffs al azar.

¿Por qué log y no un visor gráfico?

Porque log es composable y scripting: sus flags de filtrado son el mismo lenguaje que usan blame, bisect y cualquier pipeline de release (lo verás en el módulo 7). Un visor gráfico es cómodo, pero lo que aprendas aquí es lo que después automatizas.

Errores típicos de esta lección

Creer que git log a secas muestra "todo" (solo muestra lo alcanzable desde HEAD); confundir -S (buscar en el contenido) con --grep (buscar en el mensaje); y perder de vista que --follow es una comodidad con límites, no un detector de renombrados perfecto.

2 · Teoría

Qué muestra realmente git log

Un commit es un objeto que apunta a su padre. El historial es un grafo dirigido acíclico (DAG) que crece hacia atrás. Cuando escribes git log sin más, Git recorre el grafo desde HEAD siguiendo los punteros padre y te lista los commits en orden topológico/fecha. Nada más.

Eso significa que los commits de otras ramas que no son ancestros de HEAD no aparecen. Por eso la primera orden que hay que memorizar es:

git log --oneline --graph --decorate --all
  • --oneline: un commit por línea (hash corto + asunto).
  • --graph: dibuja el grafo ASCII con *, | y \ /.
  • --decorate: muestra a qué apuntan las refs (HEAD -> main, tag: v1.0.0, origin/main).
  • --all: recorre todas las refs, no solo HEAD.
El atajo que usarás cien veces

--graph --decorate suele ir activado por defecto con --oneline en configuraciones recientes, pero no lo asumas entre máquinas. Escríbelo explícito o defínelo como alias (lo harás en la lección 04).

El grafo, dibujado

Session real del repositorio taller con la rama feature/busqueda ya mergeada:

$ git log --oneline --graph --decorate --all
* 9f1c2ab (HEAD -> main) docs: explicar el indice en notas.md
|\
| * 4b7e0d1 (feature/busqueda) feat: filtrar notas por texto
| * 2c9a1f3 feat: anadir campo tags al modelo
|/
* 7d4f5e6 (tag: v0.2.0) chore: ignorar node_modules
* 1a2b3c4 initial commit: notas.md

Lee el dibujo de abajo hacia arriba: primero se creó 1a2b3c4, luego 7d4f5e6; ahí la rama se dividió en dos caminos (feature/busqueda a la derecha) que volvieron a unirse en 9f1c2ab. Ese * con dos padres es un commit de merge.

Rangos: A..B y A...B

Filtrar por rango es lo que permite decir "qué entró en esta release" o "qué tengo yo que no tiene el remoto". La sintaxis de dos puntos es la más importante de la lección:

              A           B
main   ●───●───●───●───●───●───●
               \         /
feature         ●───●───●
                 C     D

A..B    "está en B pero no en A"   → { B, y sus exclusivos }
A...B   "está en A o en B, pero no en ambos a la vez" → { C, D }
  • git log A..B → commits alcanzables desde B y no desde A. Es la forma de ver "lo nuevo de B".
  • git log A...B (tres puntos) → diferencia simétrica: lo que tienen A o B, pero no ambos. Es lo que compara git status para decirte cuántos commits llevas adelante/atrás.
  • git log origin/main..HEAD → tus commits sin publicar. Memorízalo: es la pregunta "¿qué voy a enviar?".

Los dos filtros que se confunden siempre

--grep mira el mensaje del commit. -S mira el contenido del diff. Si buscas "cuándo se introdujo la palabra password en el código", es -S. Si buscas "el commit cuyo mensaje dice password", es --grep. No son intercambiables.

Pickaxe: -S y -G

El "pickaxe" (-S) es la joya de log. Busca en la historia los commits donde cambió el número de apariciones de una cadena. Es decir: el commit que la introdujo y el que la eliminó (no cada commit que la contiene).

# ¿En qué commit apareció o desapareció la llamada a funcionVieja()?
git log --oneline -S"funcionVieja"

# Igual, pero mostrando el parche de cada coincidencia
git log -p -S"funcionVieja" -- src/

# -G usa una expresión regular sobre el texto del diff (no cuenta ocurrencias)
git log --oneline -G"funcion(Vieja|Nueva)"

Diferencia fina: -S da "el commit cambió el recuento de esta cadena"; -G da "el diff contiene esta regex". Para "cuándo nació X" usa -S; para "cuándo se tocó este patrón" usa -G.

--follow: la historia de un archivo que se renombró

Git no guarda renombrados como operación: los infiere comparando contenido. Por defecto, git log -- ruta se detiene en el commit donde el archivo nació con ese nombre. --follow le pide que siga el rastro hacia atrás a través de renombrados:

git log --oneline --follow -- src/auth.js
Los límites de --follow

Solo funciona con una ruta, y no se lleva bien con --graph ni con varios pathspecs. Es una heurística de conveniencia: si un archivo cambió de nombre y de contenido a la vez, Git puede no empalmar la historia. Para casos serios, el "pickaxe" (buscar un texto único del archivo) suele ser más fiable que --follow.

Cambiar el formato de salida

log es también un generador de datos para scripts y changelogs (módulo 7):

git log --pretty=format:'%h %ad %an %s' --date=short   # hash · fecha · autor · asunto
git log --no-merges --pretty=%s v0.2.0..v0.3.0         # solo asuntos, sin merges
git shortlog -sn --no-merges                            # ranking de autores

3 · Ejemplo mínimo

El comando más pequeño que ya es útil. Desde cualquier directorio del repo:

git log --oneline --graph --decorate --all -10

Qué esperamos ver: las últimas 10 entradas del grafo completo, con las refs decoradas. Si no ves ninguna rama con --all, o tu repositorio solo tiene una rama, o el gráfico no muestra bifurcaciones porque todo es lineal. Eso no es un error: la historia lineal se dibuja como una línea.

$ git log --oneline --graph --decorate --all -5
* 9f1c2ab (HEAD -> main) docs: explicar el indice en notas.md
* 7d4f5e6 (tag: v0.2.0) chore: ignorar node_modules
* 1a2b3c4 initial commit: notas.md

# Solo 3 commits: en el taller la rama aún no se ha creado.
# Cuando exista feature/busqueda, --all la hará aparecer.

4 · Ejemplo real

Estás en el taller y ha aparecido un bug: el buscador de notas devuelve resultados vacíos. No sabes cuándo se rompió. Vas a usar log como forense, en cuatro pasos.

Paso 1 — Ver el conjunto, no el detalle

git log --oneline --graph --decorate --all
$ git log --oneline --graph --decorate --all
* 9f1c2ab (HEAD -> main) docs: explicar el indice en notas.md
|\
| * 4b7e0d1 (feature/busqueda) feat: filtrar notas por texto
| * 2c9a1f3 feat: anadir campo tags al modelo
|/
* 7d4f5e6 (tag: v0.2.0) chore: ignorar node_modules
* 1a2b3c4 initial commit: notas.md

Paso 2 — Filtrar por lo que toca la zona sospechosa

# ¿Qué commits tocaron el fichero del buscador?
git log --oneline -- src/busqueda.js

# Con el parche completo, para leer qué cambió
git log -p -- src/busqueda.js
$ git log --oneline -- src/busqueda.js
4b7e0d1 feat: filtrar notas por texto
2c9a1f3 feat: anadir campo tags al modelo
1a2b3c4 initial commit: notas.md

Paso 3 — Rastrear un identificador concreto (pickaxe)

# El buscador llamaba a normalizarTexto(); ¿cuándo desapareció la llamada?
git log --oneline -S"normalizarTexto" -- src/
$ git log --oneline -S"normalizarTexto" -- src/
4b7e0d1 feat: filtrar notas por texto
1a2b3c4 initial commit: notas.md

# Aparece dos veces: en el commit inicial se introdujo y en 4b7e0d1 cambió
# el recuento (la llamada se sustituyó). Ese es el commit candidato.

Paso 4 — Confirmar el parche exacto de ese commit

git show 4b7e0d1 --stat
git show 4b7e0d1 -- src/busqueda.js
Por qué este orden funciona

Primero redujimos el espacio (--oneline --graph --all), luego acotamos por ruta (-- src/), luego por contenido (-S), y solo al final leímos el diff. Cada paso filtra el siguiente: leer el parche antes de filtrar es lo que hace perder tardes enteras.

Bonus: la historia completa de un archivo renombrado

# busca.md se renombró a notas.md; --follow enlaza ambas etapas
git log --oneline --follow -- notas.md
$ git log --oneline --follow -- notas.md
9f1c2ab docs: explicar el indice en notas.md
7d4f5e6 chore: ignorar node_modules      # aquí aún se llamaba busca.md
1a2b3c4 initial commit: notas.md

Sin --follow, la lista se habría cortado en el rename y habrías perdido los commits antiguos.

5 · Buenas prácticas

Traduce la pregunta al comando antes de escribir nada. Esta tabla es el índice mental de la lección:

PreguntaComandoQué estás mirando
¿Cómo está el grafo ahora mismo? git log --oneline --graph --decorate --all Topología: ramas, merges, refs
¿Qué voy a publicar? git log @{u}..HEAD Solo commits locales no publicados
¿Qué trae el remoto que no tengo? git log HEAD..@{u} Commits que se descargarían con pull
¿Cuándo se introdujo este texto? git log -S"texto" Nacimiento/muerte de una cadena
¿Quién trabajó esta semana? git shortlog -sn --since=mon Actividad agregada por autor
¿Qué pasó con este archivo? git log --follow -p -- archivo Historia + parches, siguiendo renombrados
  • Filtra antes de leer. Un diff sin el commit que lo explica es información a medias; un commit sin el diff es un mensaje a medias. Úsalos juntos.
  • Usa -S con una cadena lo bastante única. Buscar "return" da ruido; busca el nombre de una función o un literal raro.
  • Recuerda que --all mira refs, no reflog. Para commits "perdidos" existe reflog (lección 03 de este módulo).
  • Guarda tus filtros como alias. alias.lg y un alias.quien ahorran dedos y errores.

6 · Errores habituales

1. Creer que git log muestra "todo"

Mal — git log solo recorre lo alcanzable desde HEAD 
git log --oneline
# "no veo el trabajo de mi companero en feature/x"
# ...porque esa rama NO es ancestro de HEAD: log nunca la visita.
Bien — pregunta por todas las refs 
git log --oneline --graph --decorate --all
# Ahora si aparecen feature/x, origin/main y los tags.

2. Usar -S para buscar en el mensaje

Mal — -S busca en el contenido del diff, no en el asunto 
git log -S"fix login"     # busca esa cadena EN EL CODIGO, no en el mensaje
# Resultado: probablemente vacio, y la conclusion erronea
# "no existe ese commit".
Bien — el mensaje se busca con --grep 
git log --grep="fix login" -i         # mensaje
git log -S"fix login"                 # contenido (codigo, docs, tests...)
# Y si quieres ambos a la vez:
git log --grep=login -S"validar"      # AND implicito: coinciden los dos filtros

3. Abusar de --follow esperando magia

Mal — varios paths y --graph con --follow 
git log --follow --graph -- src/a.js src/b.js
# --follow solo admite UNA ruta; con varias, Git ignora --follow (silencio).
# Y --graph con --follow da un dibujo que no puedes fiarte.
Bien — una ruta para --follow, o pickaxe para lo demás 
git log --oneline --follow -- src/a.js
# Para varias rutas o casos dudosos, rastrea un texto unico del archivo:
git log --oneline -S"const MARGEN_LATERAL"

4. Leer el rango al revés

Mal — invertir A..B y no entender el resultado 
# "quiero ver lo que voy a publicar"
git log HEAD..origin/main      # en realidad esto es "lo que me falta por traer"
# A..B pregunta: ¿que tiene B que no tenga A?  Aqui: B = remoto.
Bien — el destino es el segundo miembro 
git log origin/main..HEAD      # lo MIO que no esta publicado
git log HEAD..origin/main      # lo que el remoto tiene y yo no
# Atajo: git log @{u}..HEAD  /  git log HEAD..@{u}

7 · Ejercicio guiado

Objetivo: reproducir el escenario forense en el repositorio taller y localizar, solo con log, el commit que sustituyó una función.

  1. Paso 1 — Sitúate y mira el grafo completo: 
    cd taller
git log --oneline --graph --decorate --all

    Anota el hash del commit que está en la punta de main. Si no ves ninguna bifurcación, aún no has creado feature/busqueda: créala y añade un commit para tener dos caminos.

  2. Paso 2 — Reduce a la zona sospechosa: 
    git log --oneline -- src/
git log --oneline -- notas.md

    Compara las dos listas: la primera es todo lo que tocó código; la segunda, solo la documentación.

  3. Paso 3 — Pickaxe sobre el identificador desaparecido: 
    git log --oneline -S"normalizarTexto" -- src/
# Debe salir el commit inicial (introduccion) y el que cambio el recuento.
  4. Paso 4 — Confirma con el parche de ese commit: 
    HASH=$(git log --format=%H -S"normalizarTexto" -- src/ | head -1)
git show "$HASH" -- src/
# Lee el diff: aqui esta exactamente que se sustituyo y por que.

    Resultado esperado: identificas un único commit que antes usaba normalizarTexto() y ahora usa otra cosa. Ese es el origen de la regresión, sin haber abierto un solo archivo a mano.

  5. Paso 5 — Bonus: filtra por autor y fecha para acotar aún más: 
    git log --oneline --since="2 weeks ago" --author="Ana" -- src/
git shortlog -sn --no-merges     # confirmar el reparto de autorias
Comprueba que has entendido el rango

Crea una rama de prueba con un commit y ejecuta git log main..prueba y git log prueba..main. Deberías ver tu commit solo en el primero. Si no lo tienes claro, vuelve al diagrama de A..B antes de seguir.

8 · Reto

🎯 Un informe de autoría generado solo con log

Escribe un script scripts/informe-autores.sh que, desde el taller, genere un informe de texto con: (a) el ranking de autores por número de commits en el rango v0.2.0..HEAD sin contar merges; (b) los 5 archivos más tocados en ese rango; (c) la fecha del primer y último commit de cada autor. Todo debe salir de comandos git log y git shortlog (nada de blame ni de herramientas externas).

Pista: --pretty=format: te da campos separables (%an, %ad, %s); --name-only imprime la lista de archivos de cada commit; y sort | uniq -c | sort -rn convierte cualquier columna en un ranking. Recuerda --no-merges donde pida "sin contar merges".

9 · Resumen

  • git log sin flags solo ve lo alcanzable desde HEAD; --all mira todas las refs.
  • --oneline --graph --decorate --all es el mapa del repositorio: memorízalo o aliasízalo.
  • A..B = "está en B y no en A"; A...B = diferencia simétrica. @{u}..HEAD = lo que vas a publicar.
  • --author, --since/--until, --grep filtran metadatos; -- ruta filtra por ficheros.
  • -S"texto" (pickaxe) encuentra el commit que cambió el recuento de una cadena; -G usa una regex sobre el diff.
  • --follow sigue renombrados, pero solo con una ruta y sin --graph.

10 · Preguntas frecuentes

¿Cuál es la diferencia exacta entre -S y -G?

-S<cadena> localiza commits donde cambia el número de apariciones de esa cadena (añadir una línea con ella o quitarla). -G<regex> localiza commits cuyo diff casa la regex, aunque el recuento global no cambie. Para "¿cuándo nació este texto?" usa -S; para "¿cuándo se tocó este patrón?" usa -G.

¿--follow detecta cualquier renombrado?

No. Git infiere renombrados por similitud de contenido, así que un archivo que cambió de nombre y de contenido a la vez puede romper el rastro. Además --follow solo admite una ruta y no se combina bien con --graph. Cuando dudes, busca un texto único del archivo con -S: es más robusto.

¿Por qué git log no muestra unos commits que sé que existen?

Porque pertenecen a una rama que no es ancestro de HEAD (o a un commit al que ya no apunta ninguna ref). Añade --all para verlos. Si el commit ya no lo referencia ninguna ref, log no puede alcanzarlo ni con --all: eso es territorio del reflog (lección 03).

¿Cómo veo el log de solo una rama o de un autor en un periodo?

Combina filtros: git log --oneline feature/busqueda --author="Ana" --since="2026-01-01". Los filtros de la revisión (autor, fecha, grep, pickaxe, ruta) se pueden apilar; se aplican todos a la vez (AND). Para el mismo --grep repetido, el comportamiento por defecto es OR; añade --all-match para exigir todos.

¿Existe un log específico para preparar un changelog?

Sí: git log --no-merges --pretty=format:'%s' v0.2.0..v0.3.0 te da los asuntos de los commits no-merge entre dos tags. Si sigues Conventional Commits, esos asuntos se agrupan fácilmente por feat:, fix:, etc. Lo montaremos a fondo en la lección 04 del módulo 7.
