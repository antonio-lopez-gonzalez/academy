reflog: recuperar lo perdido

Módulo 6 · Investigar 🕐 35 minutos

1 · Introducción

Esta es la lección que reconcilia al programador con Git. Un git reset --hard que parecía catastrófico, un rebase que salió mal, una rama borrada por error: casi todo eso es recuperable. La razón es que Git guarda un diario local de por dónde ha pasado cada referencia. Ese diario es el reflog.

Aquí no aprenderás flagcitos sueltos: aprenderás a pensar como el recolector de basura. Entender qué hace inalcanzable a un commit y cuándo se borra de verdad es lo que te da la tranquilidad de experimentar sin miedo.

La red de seguridad que casi nadie usa

La mayoría de tutoriales te dicen "no uses reset --hard, es peligroso". Eso es medio consejo. El consejo entero es: usa reset --hard sabiendo que el reflog existe. Si entiendes esta lección, explorar con ramas, rebase y resets deja de ser arriesgado.

Dos límites que debes grabarte

El reflog es local (no se clona ni se sube) y caduca. No sirve para recuperar un commit que hizo un compañero en su máquina, ni para siempre: por defecto los reflogs caducan a los 90 días (30 para entradas no alcanzables). Si haces git gc --prune=now justo después de un error, puedes destruir tu propia red de seguridad.

2 · Teoría

Qué es el reflog

Cada vez que HEAD o una rama apuntan a otro commit, Git anota una línea en un archivo dentro de .git/logs/:

.git/logs/HEAD              ← el diario de HEAD (todos tus movimientos)
.git/logs/refs/heads/main   ← el diario de la rama main
.git/logs/refs/remotes/…    ← el diario de cada rama remota

El reflog es, literalmente, la cinta de la película: cada fotograma es "estado anterior → estado nuevo, por este motivo". Los commits que ya no apunta ninguna rama siguen existiendo como objetos; el reflog conserva la referencia que te permite volver a nombrarlos.

   git log --oneline          git reflog
   (solo lo alcanzable)       (por donde ha pasado HEAD)

        ┌─● c3  HEAD->main     c3  HEAD@{0}  reset: moving to HEAD~2
        │                     c3  HEAD@{1}  commit: fix: validar texto
   main ●  c2                  c2  HEAD@{2}  commit: feat: nuevo filtro
        │                     c1  HEAD@{3}  commit: chore: config
        ● c1
        (c2 y c3 siguen en el reflog aunque main ya no los alcance)

Leer el reflog

git reflog                 # equivalen a: git reflog show HEAD
git reflog --date=iso      # con fecha absoluta en vez de relativa
git reflog show main       # el diario de SOLO la rama main
git reflog --all           # el de todas las refs
$ git reflog
9f1c2ab (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2
4b7e0d1 HEAD@{1}: commit: fix: validar texto antes de filtrar
2c9a1f3 HEAD@{2}: commit: feat: filtrar notas por texto
7d4f5e6 HEAD@{3}: commit (amend): chore: ignorar node_modules

Cada línea tiene tres partes: el hash, la referencia cualificada (HEAD@{n}) y la acción que provocó el movimiento (commit, reset, rebase, checkout, merge…). El motivo al final es oro puro: te dice en qué pensabas cuando ocurrió.

Nombrar un estado pasado: @{n} y fechas

El reflog no es solo informativo: sus entradas son nombres válidos de commit que puedes usar en cualquier comando.

git show HEAD@{1}              # el commit anterior de HEAD
git switch -c rescate HEAD@{3} # crear rama apuntando a un estado antiguo
git switch -c rescate 'HEAD@{2.days.ago}'   # ¡acepta fechas relativas!
git switch -c rescate 'main@{yesterday}'    # el estado de main ayer
El reflog es una máquina del tiempo con nombres

HEAD@{n} cuenta hacia atrás desde el presente: @{0} es ahora, @{1} el movimiento anterior. Y como acepta @{2.hours.ago} o @{yesterday}, puedes recuperar el estado de tu repositorio a una hora concreta sin recordar ningún hash. Es especialmente útil cuando el desastre ocurrió "hace un rato".

Qué hace inalcanzable a un commit, y cuándo desaparece

Un commit se borra de verdad solo cuando se cumplen dos condiciones: (1) no lo alcanza ninguna referencia (ramas, tags, HEAD, stashes…) y (2) su entrada del reflog ha caducado, y además el recolector de basura (git gc) ha pasado por encima.

ConceptoClave de configValor por defecto
Vida de una entrada de reflog alcanzablegc.reflogExpire90 días
Vida de una entrada no alcanzablegc.reflogExpireUnreachable30 días
Antigüedad para que gc pode objetos sueltosgc.pruneExpire2 semanas
 
git reflog expire --expire=now --all   # ⚠️ caduca TODO el reflog YA (no lo hagas por error)
git gc --prune=now                      # ⚠️ borra objetos inalcanzables YA
Nunca combines esas dos órdenes tras un error

Son las que usan los "limpiadores" para reducir el tamaño de un repositorio. Ejecutarlas justo después de un reset --hard accidental es la forma de convertir un accidente reversible en una pérdida real. Si dudas, no las ejecutes: el espacio que ahorran es insignificante comparado con el trabajo que pueden destruir.

El flujo de rescate

1. Identificar        git reflog                  (¿qué movimientos hice?)
2. Nombrar el estado  HEAD@{n} o <hash>          (¿a qué commit quiero volver?)
3. Anclarlo           git switch -c rescate <hash>  (una RAMA lo hace alcanzable)
4. Verificar          git log --oneline --graph rescate
5. Decidir            merge/rebase/cherry-pick al destino
NO hacer todavia:    git reflog expire / git gc --prune=now

La clave mental: mientras el commit siga en el reflog, existe. Basta con crear una rama que lo apunte para que vuelva a ser alcanzable y quede a salvo de cualquier recolección. Crear la rama es el acto de rescate; el resto (fusionar, reescribir) es decisión tuya.

3 · Ejemplo mínimo

El accidente más común del curso, reproducido en el taller: dos commits que desaparecen de main con un reset --hard.

cd taller
git log --oneline -4                 # anota el hash de la punta ANTES del reset
git reset --hard HEAD~2
git log --oneline -2                 # los dos commits ya no se ven
$ git log --oneline -4
4b7e0d1 (HEAD -> main) fix: validar texto antes de filtrar
2c9a1f3 feat: filtrar notas por texto
7d4f5e6 chore: ignorar node_modules
1a2b3c4 initial commit: notas.md

$ git reset --hard HEAD~2
HEAD is now at 7d4f5e6 chore: ignorar node_modules

$ git log --oneline -2
7d4f5e6 (HEAD -> main) chore: ignorar node_modules
1a2b3c4 initial commit: notas.md

Para git log, 4b7e0d1 y 2c9a1f3 han dejado de existir. Para el reflog, no:

$ git reflog
7d4f5e6 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2
4b7e0d1 HEAD@{1}: commit: fix: validar texto antes de filtrar
2c9a1f3 HEAD@{2}: commit: feat: filtrar notas por texto
7d4f5e6 HEAD@{3}: commit: chore: ignorar node_modules

Qué esperamos ver: los dos commits "perdidos" siguen en la lista, con su hash completo localizable. Con HEAD@{1} los recuperas:

git switch -c rescate HEAD@{1}
git log --oneline --graph -4

4 · Ejemplo real

Tres rescates en el taller, de menor a mayor dificultad. Todos empiezan igual: no toques nada y mira el reflog.

Rescate 1 — Volver tras un reset --hard

git reflog --date=iso | head -6
# Supongamos: 4b7e0d1 HEAD@{1}: commit: fix: validar texto antes de filtrar
# Anclar el estado perdido en una rama con nombre propio
git switch -c rescate/reset HEAD@{1}

# Comprobar que es lo que queria
git log --oneline --graph --decorate -5
git diff main..rescate/reset --stat
$ git log --oneline --decorate -4
4b7e0d1 (HEAD -> rescate/reset) fix: validar texto antes de filtrar
2c9a1f3 feat: filtrar notas por texto
7d4f5e6 (main) chore: ignorar node_modules
1a2b3c4 initial commit: notas.md

Ahora tienes dos ramas: main (sin los commits) y rescate/reset (con ellos). Decide: si main ya está publicado y esos commits también lo estaban, no hagas reset --hard otra vez sobre main; deja que la historia siga avanzando. Lo correcto es git switch main && git merge rescate/reset (o cherry-pick de los dos commits) y que el rescate sea un commit nuevo.

Regla de oro

Recuperar con el reflog es seguro en local. Pero no reescribas lo ya publicado: si main con esos commits ya está en el remoto, los compañeros lo tienen. Añade historia nueva (merge o cherry-pick), no la sustituyas. Volveremos a esta regla en el módulo 7.

Rescate 2 — Recuperar una rama borrada

Borrar una rama con git branch -d no borra sus commits: solo el puntero. Si los commits no eran alcanzables por ninguna otra rama, siguen vivos en el reflog de esa rama.

git branch -D feature/busqueda      # ups, la borre antes de mergear
git reflog show feature/busqueda
# 4b7e0d1 feature/busqueda@{0}: branch: Created from HEAD
# 2c9a1f3 feature/busqueda@{1}: commit: feat: filtrar notas por texto

git switch -c feature/busqueda 'feature/busqueda@{1}'
# o directamente por hash:
git switch -c feature/busqueda 2c9a1f3
El reflog por rama sigue existiendo un tiempo

Al borrar una rama, Git borra su .git/logs/refs/heads/…, pero la entrada de HEAD que apunta al último commit suele seguir ahí un tiempo. Si git reflog show <rama-borrada> no devuelve nada, busca en git reflog el momento en que estuviste en esa rama: el hash estará en el motivo.

Rescate 3 — Deshacer un rebase (o un merge) que salió mal

git reflog | head -8
# 4b7e0d1 HEAD@{0}: rebase (finish): returning to refs/heads/main
# 2c9a1f3 HEAD@{1}: rebase (pick): feat: filtrar notas por texto
# 7d4f5e6 HEAD@{5}: checkout: moving from main to main   ← el estado previo

git reset --hard HEAD@{5}      # o mejor: git switch -c rescate/rebase HEAD@{5}
git log --oneline -3

git reset --hard HEAD@{5} te devuelve exactamente al estado previo al rebase (no es una operación destructiva de verdad: el estado malo queda a su vez en el reflog). Aun así, la opción anclar en rama (switch -c) es preferible: no pierdes nada y comparas los dos estados antes de decidir.

git switch -: el atajo para volver

Cuando solo quieres volver a donde estabas (la rama anterior), hay un atajo que no requiere reflog:

git switch main
git switch -            # vuelve a la rama anterior (imprime "Switched to branch '...'")
git switch -            # y otra vez: alterna entre las dos ultimas ramas

Es el equivalente de cd -: recuerda la rama previa. Perfecto para el vaivén main ↔ rescate mientras comparas.

Último recurso: git fsck --lost-found

¿Y si el commit ya no está en el reflog? (Porque caducó, o porque gc pasó, o porque el repo se corrompió a medias.) Antes de darlo por perdido, hay un barrido de objetos del almacén completo:

git fsck --lost-found
# Comprobando objetos: 100% (145/145), hecho.
# dangling commit 5a3c9e1f8b...   ← objeto suelto (no alcanzable)

git show 5a3c9e1f8b            # ¿es lo que buscaba?
git switch -c rescate/fsck 5a3c9e1f8b
$ ls .git/lost-found/commit/     # fsck escribe ahi los objetos sueltos
5a3c9e1f8b2d4a6c8e0f...
$ cat .git/lost-found/commit/5a3c9e1f8b2d4a6c8e0f... | head
tree 8d9f... 
parent 1a2b3c4...
author Ana Lopez <ana@example.com> 1770000000 +0100
committer Ana Lopez <ana@example.com> 1770000000 +0100

feat: filtrar notas por texto
Qué son los "dangling objects"

fsck llama dangling ("colgantes") a los objetos que existen en el almacén pero a los que no llega ninguna referencia. Suelen ser commits de pruebas, amends antiguos o estados intermedios de rebase. Recuperar uno es exactamente igual que con el reflog: git switch -c <nombre> <hash>.

5 · Buenas prácticas

PrácticaPor qué
Ante un susto, para y lee git reflog Cualquier comando adicional (reset, rebase, gc) puede empeorar la situación o borrar la pista
Ancla en una rama: git switch -c rescate <hash> Nombrar el estado lo hace alcanzable y a salvo; nunca trabajes "en el aire"
Grabar el hash antes de operaciones grandes git rev-parse HEAD en un papel (o en el chat del equipo) te da un punto de retorno explícito
Usar --force-with-lease, nunca --force a main El arrendamiento comprueba que el remoto no cambió desde tu fetch: evita pisar el trabajo ajeno
Preferir git revert si ya está publicado El reflog arregla tu copia local; lo publicado se arregla con historia nueva (módulo 2, lección 3)
Ajustar los plazos de caducidad si haces trabajo crítico git config gc.reflogExpire 180.days amplía la ventana de rescate local
Haz una copia antes de experimentar

Si vas a hacer algo realmente delicado (un filter-repo, un rebase enorme, una limpieza a fondo), la red definitiva no es el reflog sino un clon de seguridad: git clone --mirror . ../taller-backup.git. El reflog te cubre lo cotidiano; la copia te cubre lo excepcional.

6 · Errores habituales

1. Entrar en pánico y "limpiar"

Mal — pedir a Git que borre justo después del error 
git reset --hard HEAD~2      # "he perdido dos commits"
git reflog expire --expire=now --all
git gc --prune=now           # ahora SI estan perdidos de verdad.
# Grep no encuentra lo que no existe: has borrado tu red de seguridad.
Bien — leer el reflog y anclar el estado 
git reflog                        # 4b7e0d1 HEAD@{1}: commit: ...
git switch -c rescate/reset HEAD@{1}
git log --oneline -3              # los commits han vuelto a una rama

2. Creer que el reflog viaja con el repositorio

Mal — fiarse del reflog para recuperar algo ajeno 
# "que Ana mire en SU reflog el commit que borro"
git push --force origin main      # NO: ni el reflog se clona, ni se sube.
# El reflog de un repo recien clonado tiene UNA linea: el clone.
Bien — lo compartido se arregla con historia nueva 
# Si algo se publicó y hay que deshacerlo:
git revert <hash>                 # commit nuevo que deshace, sin reescribir
git push origin main              # se sube historia ADICIONAL
# El reflog solo arregla TU copia local.

3. Ignorar la caducidad

Mal — confiar en el reflog meses después 
# "recuperemos ese commit de hace tres meses"
git reflog | grep "mi commit"     # probablemente ya no esta:
# gc.reflogExpireUnreachable = 30 dias por defecto.
Bien — rescatar en caliente y ampliar plazos si hace falta 
git switch -c rescate HEAD@{1}          # rescata YA, no "mañana"
git config --global gc.reflogExpire 180.days
git config --global gc.reflogExpireUnreachable 90.days
# Y si el plazo ya paso: git fsck --lost-found como ultimo recurso.

4. Recuperar con reset --hard sobre una rama publicada

Mal — "arreglar" el remoto moviendo la punta 
git switch main
git reset --hard HEAD@{5}         # reescribe main hacia atras
git push --force origin main      # ❌ prohibido: los companeros pierden trabajo
# Es el caso de manual de "no reescribas lo publicado".
Bien — anclar, revisar y solo renombrar en local 
git switch -c rescate/rebase 'main@{yesterday}'
git diff main..rescate/rebase --stat     # mira que se perdio
# En local, mover main es TU decision y aun asi es reversible por reflog:
git switch main && git reset --hard rescate/rebase
# Pero si main ya esta en el remoto: merge o cherry-pick, NUNCA --force.

7 · Ejercicio guiado

Objetivo: perder commits a propósito y recuperarlos usando cada una de las tres vías (reflog, @{n}, fsck).

  1. Paso 1 — Fabrica el desastre de forma controlada: 
    cd taller
git switch -c laboratorio/reflog
git commit --allow-empty -m "docs: commit que voy a perder (A)"
git commit --allow-empty -m "docs: commit que voy a perder (B)"
git log --oneline -3
git rev-parse HEAD > /tmp/punta-segura.txt    # apunta la punta a salvo
  2. Paso 2 — Destrúyelo y comprueba la amnesia: 
    git reset --hard HEAD~2
git log --oneline -3          # A y B ya no aparecen
git reflog -6                 # ...pero aqui SI

    Resultado esperado: los dos commits figuran como HEAD@{1} y HEAD@{2} con el motivo commit: docs: commit que voy a perder….

  3. Paso 3 — Rescata por reflog a una rama nueva: 
    git switch -c rescate/reflog HEAD@{2}
git log --oneline -4          # A y B estan de vuelta
git diff laboratorio/reflog..rescate/reflog --stat    # que diferencia hay
  4. Paso 4 — Rescata por "máquina del tiempo" (fechas): 
    git switch -c rescate/tiempo 'laboratorio/reflog@{5.minutes.ago}'
git log --oneline -3
# Si la rama era corta, usa HEAD: git switch -c x 'HEAD@{10.minutes.ago}'

    Resultado esperado: recuperas el estado de hace cinco minutos sin haber mirado un solo hash. Es la versión reflog de "deshacer el último cuarto de hora".

  5. Paso 5 — Simula que el reflog ya no sirve y usa fsck: 
    # Caduca el reflog de esta rama para forzar el caso dificil
git reflog expire --expire-unreachable=now --all   # solo en el taller de practica
git reflog | grep "voy a perder" || echo "ya no esta en el reflog"
git fsck --lost-found
git show $(git fsck --lost-found 2>/dev/null | awk '/dangling commit/{print $3}' | head -1)

    Resultado esperado: aunque el reflog ya no te lo dé, fsck encuentra commits "colgantes" y te devuelve sus hashes; uno de ellos es tu commit A o B. Recupéralo con git switch -c rescate/fsck <hash>.

  6. Paso 6 — Vuelve y limpia el laboratorio: 
    git switch -
git branch -D laboratorio/reflog rescate/reflog rescate/tiempo rescate/fsck
git reflog -4

    Resultado esperado: de vuelta en tu rama de trabajo, con el reflog mostrando todo el recorrido del ejercicio. Eso es exactamente la cinta de la película que acabas de aprender a rebobinar.

Este ejercicio caduca reflogs a propósito

El paso 5 ejecuta git reflog expire --expire-unreachable=now --all. Hazlo solo en el repositorio de práctica y sin commits importantes sin publicar. En un repositorio real, jamás: destruirías la red de seguridad que esta lección te enseña a usar.

8 · Reto

🎯 Un rescatador de última hora

Escribe scripts/rescatar.sh que, dado un texto del mensaje de un commit perdido (por ejemplo "voy a perder"), lo encuentre y te lo devuelva anclado en una rama segura. El script debe: (1) buscar primero en git reflog y en git reflog --all; (2) si no aparece, usar git fsck --lost-found y leer los mensajes de los commits dangling con git show --format=%s; (3) imprimir el hash encontrado y ejecutar git switch -c rescatado/<fecha> <hash>; (4) negarse a tocar ramas publicadas (si la rama destino ya existe o tiene upstream, pide confirmación explícita).

Pista: git fsck --lost-found sin argumentos lista objetos sueltos; combinado con git cat-file -t <hash> filtras solo los que son commit. Para leer el asunto de un commit sin comprobarlo contra el índice, usa git show -s --format=%s <hash>. Y recuerda: el objetivo del reto no es borrar nada, es nombrar lo perdido.

9 · Resumen

  • El reflog es un diario local de a dónde ha apuntado HEAD y cada rama; vive en .git/logs/.
  • No se clona ni se publica: no sirve para recuperar el trabajo de otra persona.
  • HEAD@{n} y @{fecha} son nombres de commit utilizables en cualquier comando.
  • Tras un reset --hard, el commit sigue ahí: rescátalo con git switch -c rescate <hash>.
  • git switch - vuelve a la rama anterior sin necesidad de reflog.
  • Los reflogs caducan (90/30 días por defecto); reflog expire + gc --prune=now los destruyen — nunca los ejecutes tras un error.
  • Si ya no está en el reflog: git fsck --lost-found como último recurso.
  • Recuperar es local; lo publicado se arregla con historia nueva (revert/merge), no con --force a main.

10 · Preguntas frecuentes

¿El reflog se sube al remoto o se clona?

No. El reflog es estrictamente local y por diseño: recoge tus movimientos en tu copia. Un repositorio recién clonado tiene un reflog con una sola entrada (el clone). Por eso el reflog nunca recupera el trabajo que alguien no llegó a publicar en su máquina.

¿Cuánto tiempo puedo recuperar algo con el reflog?

Por defecto, 90 días para entradas alcanzables y 30 días para inalcanzables (gc.reflogExpire y gc.reflogExpireUnreachable). Además, el gc que poda objetos sueltos no borra nada más reciente que gc.pruneExpire (2 semanas) por defecto. Si tu proyecto maneja rescates críticos, amplía esos plazos con git config.

¿Recuperar con el reflog reescribe historia?

En local, sí: mover una rama hacia atrás con reset reescribe tu historia, pero es reversible (el estado anterior queda en el reflog). El problema aparece al publicar esa reescritura: si la rama ya está en el remoto, otros la basaron en tu trabajo. Ahí no uses --force, salvo en ramas propias y con --force-with-lease.

¿Qué es un "dangling commit" y por qué fsck lo encuentra?

Es un objeto que sigue en el almacén pero al que no llega ninguna referencia. git fsck recorre el grafo completo desde todas las refs y reporta lo que queda fuera. Es el último recurso cuando el reflog ya no conserva la pista, pero no es magia: si el commit ya fue podado por gc, no hay nada que encontrar.

¿Cómo evito depender del reflog?

Trabajando con ramas y hashes explícitos: antes de un rebase o un reset grande, guarda git rev-parse HEAD; para experimentos, crea una rama (git switch -c intento) en vez de trabajar sobre main; y para lo excepcional, un clon --mirror de seguridad. El reflog es la red, no el plan.
