blame y bisect: quién y cuándo

Módulo 6 · Investigar 🕐 40 minutos

1 · Introducción

La lección anterior filtrabas el grafo por metadatos y por texto. Ahora bajas un nivel: línea a línea. git blame responde a "¿qué commit tocó por última vez esta línea?" y git bisect responde a "¿qué commit introdujo este comportamiento?" buscando en fase logarítmica en lugar de linealmente.

Son las dos herramientas de arqueología por excelencia. Una parte de una línea y sube; la otra parte del rango entero de commits y baja por bisección hasta dar con el culpable, incluso cuando el bug no está en un archivo evidente.

El nombre blame es engañoso

"Blame" (culpar) sugiere buscar un responsable, y ese NO es su propósito. La atribución te dice qué contexto leer: el commit, su mensaje, su PR. La pregunta correcta no es "¿quién escribió esto?" sino "¿por qué se tomó esta decisión?"; y para responderla vas al git show que blame te señala. Igual que log, blame es una pista, no un veredicto.

Errores típicos

Creer que blame te da "el autor original" (te da el último commit que tocó la línea, que puede ser un reformateo masivo); ejecutar bisect sin un criterio binario y determinista para decir "bueno/malo"; y olvidar git bisect reset al terminar, dejando el repositorio en HEAD desacoplado.

2 · Teoría

git blame: atribución de cada línea

blame recorre la historia de un archivo y, para cada línea del estado actual, muestra el commit que la introdujo por última vez. La salida por defecto tiene cuatro campos:

$ git blame -L 10,14 -- src/busqueda.js
4b7e0d1a (Ana Lopez     2026-02-11 10:24:31 +0100 10) export function buscar(texto) {
2c9a1f3c (Luis Rivas    2026-02-10 18:02:07 +0100 11)   const clave = texto.trim().toLowerCase();
2c9a1f3c (Luis Rivas    2026-02-10 18:02:07 +0100 12)   return notas.filter(n => n.texto.includes(clave));
7d4f5e60 (Ana Lopez     2026-02-09 09:15:44 +0100 13) }
1a2b3c40 (Ana Lopez     2026-02-08 21:40:12 +0100 14) // TODO: ordenar por relevancia
  • hash corto del commit que tocó la línea (con un ^ delante si es un commit "frontera" del rango analizado),
  • autor y fecha de ese commit,
  • número de línea en el estado actual,
  • el contenido de la línea.

El rango con -L es lo que evita ahogarse: -L inicio,fin o, en lenguajes que lo soportan, -L :nombreDeFuncion.

git blame -L 40,60 -- src/busqueda.js      # solo estas lineas
git blame -L :buscar -- src/busqueda.js    # desde el inicio de la funcion
git blame -L 40,+15 -- src/busqueda.js     # 15 lineas a partir de la 40

Los flags que hacen útil a blame

FlagPara qué
-L <inicio,fin>Limitar el análisis a un rango o a una función
-wIgnorar diferencias de espacios en blanco (no atribuir a reformateos)
-C / -MDetectar líneas copiadas / movidas entre archivos y seguir su origen real
-eMostrar el email en vez del nombre
-sSuprimir autor y fecha (dejar solo el hash)
--ignore-rev / --ignore-revs-fileSaltar commits de ruido (formateos masivos)
--color-by-ageColorear por antigüedad: líneas viejas vs recientes
-p (porcelain)Salida estable para scripts (módulo 7)
El truco del formateo masivo

Si un commit hizo prettier . o cambió los finales de línea, blame te dirá que toda la base de código es de ese commit. Solución profesional: anotar el hash de esos commits en un archivo (.git-blame-ignore-revs) y ejecutar git blame --ignore-revs-file .git-blame-ignore-revs archivo. Así la atribución salta el ruido y señala al autor real. Puedes fijarlo por defecto con git config blame.ignoreRevsFile .git-blame-ignore-revs.

git bisect: búsqueda binaria en la historia

Cuando no sabes qué archivo ni qué texto buscar, pero sí sabes que algo funcionaba antes y no funciona ahora, bisect es el arma. En vez de probar commits de uno en uno, Git te va dando puntos medios: cada prueba descarta la mitad restante.

16 commits entre "bueno" y "malo" → 4 pruebas (log2 16)
  bueno ●───────────────────────────────────────────────────● malo
        └──────────── mitad 1 ────┬──── mitad 2 ────────────┘
                                 ↑ prueba 1: ¿funciona aqui?
   malo ●───────────────────────●
        └───── mitad ───┬─── mitad ─┘
                        ↑ prueba 2: ¿funciona aqui?

$ git bisect
bisect: a good commit, then a bad commit...
Bisecting: 3 revisions left to test after this (roughly 2 steps)

El flujo completo es: start → marcar bad (la punta) → marcar good (un commit antiguo que funciona) → Git hace checkout del punto medio → tú pruebas → repites good/bad → al final Git te dice el primer commit malo → reset para volver.

El subcomando que lo cambia todo: bisect run

Si tienes un test o un script que devuelve un código de salida honesto, git bisect run automatiza todo el proceso: hace checkout, ejecuta tu comando, interpreta el código de salida y decide solo. El contrato de salida es exacto:

Código de salida del comandoSignificado
0Bueno (good)
1–127 (excepto 125) y negativosMalo (bad)
125Saltar este commit (skip) — no se puede probar
128+Error irrecuperable: abortar el bisect
 
git bisect start
git bisect bad                  # HEAD no funciona
git bisect good v0.2.0          # este tag funcionaba
git bisect run npm test -- --grep "filtrar notas"
# Git hace todo el recorrido y termina con:
# <hash> is the first bad commit
git bisect reset                # SIEMPRE: vuelve a la rama original
Por qué el código 125 salva el proceso

Un commit intermedio puede no compilar por razones ajenas al bug (una dependencia que aún no existía, un archivo que después se renombra). Si el script devuelve 125, bisect lo marca como skip y sigue con el rango equivalente, sin contaminar la conclusión. Confundir "no se puede probar" con "malo" es la forma número uno de que bisect te mienta.

Otros subcomandos de bisect

ComandoQué hace
git bisect logImprime el diario de la sesión (los good/bad marcados)
git bisect replay archivoReproduce una sesión a partir de un log guardado
git bisect visualizeMuestra el rango pendiente (usa gitk/log)
git bisect skipSalta el commit actual o un rango
git bisect termsMuestra los términos activos (good/bad u old/new)
git bisect resetTermina y vuelve a donde estabas
No solo sirve para bugs

bisect responde a cualquier pregunta binaria sobre la historia: "¿en qué commit se dejó de soportar Node 18?", "¿cuándo empezó a tardar el test más de 10 s?", "¿qué commit hizo que fallara el build en Windows?". Basta con tener un comando que devuelva 0/1.

3 · Ejemplo mínimo

Una sola línea de blame sobre un rango pequeño ya te dice quién y cuándo. Ejecuta desde el taller:

git blame -L 10,14 -- src/busqueda.js

Qué esperamos ver: cuatro líneas, cada una precedida por un hash corto, un autor, una fecha y el número de línea. Si ves muchas líneas atribuidas al commit initial commit en vez de a los commits posteriores, probablemente el archivo se reformateó o se renombró como bloque: ahí es donde entran -w y --ignore-revs-file.

$ git blame -L 10,14 -- src/busqueda.js
4b7e0d1a (Ana Lopez     2026-02-11 10:24:31 +0100 10) export function buscar(texto) {
2c9a1f3c (Luis Rivas    2026-02-10 18:02:07 +0100 11)   const clave = texto.trim().toLowerCase();
2c9a1f3c (Luis Rivas    2026-02-10 18:02:07 +0100 12)   return notas.filter(n => n.texto.includes(clave));
7d4f5e60 (Ana Lopez     2026-02-09 09:15:44 +0100 13) }
1a2b3c40 (Ana Lopez     2026-02-08 21:40:12 +0100 14) // TODO: ordenar por relevancia

Con esa lista en la mano, el siguiente paso siempre es el mismo: git show 2c9a1f3c para leer el por qué de esas dos líneas.

4 · Ejemplo real

El escenario con el que está construido el taller: alguien introdujo a propósito un bug de búsqueda (una comparación case-sensitive que rompe el filtrado). No hay mensaje de commit que lo delate. Lo vamos a cazar con bisect run.

Preparar el terreno

cd taller
# Un test que falle SOLO por el bug (debe ser determinista y rapido)
cat > test/busqueda.test.js <<'EOF'
import test from "node:test";
import assert from "node:assert/strict";
import { buscar } from "../src/busqueda.js";

test("buscar ignora mayusculas", () => {
  const notas = [{ texto: "Comprar Pan" }, { texto: "Estudiar Git" }];
  assert.deepEqual(buscar("pan", notas).map((n) => n.texto), ["Comprar Pan"]);
});
EOF

# Confirmamos el estado actual: FALLA (HEAD es malo)
node --test test/busqueda.test.js; echo "exit=$?"

Marcar los extremos y dejar que Git conduzca

git bisect start
git bisect bad                     # HEAD: el test falla
git bisect good v0.2.0             # el tag donde el test pasaba

# A partir de aqui, Git hace todo el trabajo:
git bisect run node --test test/busqueda.test.js
running  node --test test/busqueda.test.js
Bisecting: 3 revisions left to test after this (roughly 2 steps)
[...]
running  node --test test/busqueda.test.js
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[...]

2c9a1f3c8e... is the first bad commit
commit 2c9a1f3c8e...
Author: Luis Rivas <luis@example.com>
Date:   Tue Feb 10 18:02:07 2026 +0100

    feat: anadir campo tags al modelo

 src/busqueda.js | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)
Por qué el culpable es "el primer commit malo"

Git no dice "aquí está el bug": dice que 2c9a1f3c es el primer commit del rango donde el test falla, y que su padre todavía pasaba. Por tanto ese commit introdujo el fallo (o al menos es el primero observable). Inspecciónalo con git show 2c9a1f3c: verás el cambio de includes(clave) a una comparación estricta.

Cuando un commit no se puede probar: skip y 125

#!/usr/bin/env bash
# scripts/bisect-check.sh — devuelve 0 (bueno), 1 (malo) o 125 (no se puede probar)
set -u
if [ ! -f package.json ]; then
  exit 125          # commit sin el proyecto aun montado: saltar
fi
npm ci --silent || exit 125     # no se puede instalar deps: no es "malo"
npm test --silent               # 0 pasa / no-cero falla

git bisect run ./scripts/bisect-check.sh

Cerrar siempre la sesión

git bisect reset      # vuelve a main (o a donde estabas)
git status            # comprueba que no sigues en HEAD desacoplado
Olvidar reset es el error clásico

Durante el bisect estás en HEAD desacoplado (no branch). Si empiezas a trabajar y commiteas ahí, esos commits no pertenecen a ninguna rama. git bisect reset te devuelve a la rama de partida.

5 · Buenas prácticas

PrácticaPor qué
Acota blame con -L o :funcion Un archivo de 2000 líneas sin rango es ilegible; tu pregunta es siempre sobre unas pocas líneas
Usa -w y --ignore-revs-file Los reformateos masivos enmascaran al autor real; saltarlos da la atribución honesta
Trata blame como puerta, no como destino El valor está en el git show y el PR del commit señalado, no en el nombre del autor
Escribe el criterio de bisect como un comando determinista Si el test es "flaky", el bisect llega a la conclusión equivocada con total seguridad
Devuelve 125 para "no se puede probar" Evita que un commit no compilable se marque como bug y desvíe la búsqueda
Guarda git bisect log antes de reset Tienes un rastro reproducible del razonamiento, útil para el informe y para replay
Fija un rango pequeño: un good conocido Cada tag o release anterior reduce el log2(n) de pasos; mejor aún si es un tag estable
.git-blame-ignore-revs versionado

Guarda ese archivo en el repositorio y añade git config blame.ignoreRevsFile .git-blame-ignore-revs a la config del proyecto. Así todo el equipo obtiene la misma atribución útil sin tener que recordar el flag.

6 · Errores habituales

1. Atribuir a quien hizo el formateo

Mal — leer blame sin descartar el ruido 
git blame src/busqueda.js
# Todas las lineas dicen "chore: prettier" -> conclusion: "lo escribio quien formateo"
# Falso: ese commit solo cambio espacios.
Bien — ignorar espacios y commits de ruido 
git blame -w src/busqueda.js
git blame -w --ignore-revs-file .git-blame-ignore-revs src/busqueda.js
# Ahora si aparece el commit que escribio la logica.

2. Un test flaky como criterio de bisect

Mal — el criterio no es determinista 
# Un test que a veces pasa y a veces falla (timing, red, orden de ficheros)
git bisect run npm test
# Git seguira una secuencia de good/bad aleatoria y acabara senalando
# un commit inocente con total aplomo.
Bien — un script con criterio estable y honesto 
#!/usr/bin/env bash
set -u
npm ci --silent || exit 125              # no se puede preparar -> skip
node --test test/solo-este.test.js        # determinista: 0 pasa / falla
# exit 0  = bueno   |   != 0 = malo   |   125 = saltar

3. Marcar bad y good invertidos

Mal — good apuntando a la punta 
git bisect start
git bisect good          # HEAD "funciona"??  Pero HEAD es justamente el que falla
git bisect bad v0.2.0    # el tag antiguo, que funcionaba...
# Git recorrera la direccion equivocada y "encontrara" cualquier cosa.
Bien — bad es el presente roto; good, un ancestro sano 
git bisect start
git bisect bad            # por defecto, HEAD = roto ahora mismo
git bisect good v0.2.0    # un commit ANTERIOR que si funcionaba
# good debe ser ancestro de bad; si no lo es, Git avisa.

4. Quedarse dentro del bisect

Mal — trabajar o commitear en estado de bisección 
# ...tras encontrar el commit malo, sin cerrar la sesion:
git switch -c fix/bug     # sigues en HEAD desacoplado por bisect
git commit -m "fix: ..."  # commit huerfano: no cuelga de ninguna rama
Bien — cerrar y luego trabajar 
git bisect log > bisect.log      # guarda el razonamiento (opcional)
git bisect reset                 # vuelve a main
git switch -c fix/busqueda-case  # ahora si, rama normal
git commit -m "fix: ignorar mayusculas al filtrar"

7 · Ejercicio guiado

Objetivo: cazar la regresión del taller con bisect run, documentar el culpable con blame y dejar el repositorio limpio.

  1. Paso 1 — Comprueba el estado actual (debe fallar): 
    cd taller
node --test test/busqueda.test.js; echo "exit=$?"
git log --oneline -5

    Anota el hash de HEAD y confirma que el test falla. Ese es tu punto bad.

  2. Paso 2 — Encuentra el último tag bueno y arranca el bisect: 
    git tag --list 'v*'                # p.ej. v0.2.0
git bisect start
git bisect bad
git bisect good v0.2.0
git bisect log                     # comprueba que el rango tiene sentido
  3. Paso 3 — Automatiza con bisect run: 
    git bisect run node --test test/busqueda.test.js
# Espera a la linea "<hash> is the first bad commit" y apunta el hash.

    Resultado esperado: un único hash señalado como primer commit malo (2c9a1f3c en el taller de referencia).

  4. Paso 4 — Cierra la sesión y lee el parche criminal: 
    git bisect reset
git show --stat 2c9a1f3c           # sustituye por tu hash
git show 2c9a1f3c -- src/busqueda.js
  5. Paso 5 — Usa blame para ver el alcance de esa decisión: 
    git blame -L 10,14 -- src/busqueda.js
# Confirma que las lineas sospechosas apuntan al mismo commit.
git log -1 --format='%h %s%n%b' 2c9a1f3c     # mensaje completo del culpable

    Resultado esperado: las dos líneas del filtrado aparecen atribuidas al commit que bisect señaló, y su mensaje explica la intención (feat: anadir campo tags al modelo). Conclusión: el bug se coló de refilón en un commit con otro propósito — el patrón más común.

  6. Paso 6 — Arregla y verifica: 
    git switch -c fix/busqueda-case
# Corrige la comparacion (volver a toLowerCase antes de comparar)
node --test test/busqueda.test.js; echo "exit=$?"   # debe pasar
git commit -am "fix: comparar sin distinguir mayusculas al filtrar"

8 · Reto

🎯 Caza una regresión que no controlas tú

Crea en el taller una segunda regresión real de rendimiento: añade en un commit un sleep o un bucle innecesario que haga que el test tarde más de un umbral (por ejemplo 2 segundos), y en commits anteriores deja el test rápido. Escribe un script scripts/bisect-slow.sh que mida el tiempo del test y devuelva 0 si tarda menos del umbral y 1 si lo supera, devolviendo 125 si el test ni siquiera existe en ese commit. Luego localiza el commit culpable con git bisect run ./scripts/bisect-slow.sh y documenta la sesión con git bisect log > bisect-slow.log antes de hacer reset.

Pista: mide con SECONDS o con date +%s%N en bash; compara con un umbral constante. El contrato 0/1/125 es el mismo que ya conoces, y este reto lo demuestra: bisect no sabe nada de bugs, solo de preguntas binarias.

9 · Resumen

  • git blame atribuye cada línea al último commit que la tocó; el valor está en ir luego a git show de ese commit.
  • -L acota el rango (líneas o :funcion); -w y --ignore-revs-file quitan el ruido de los reformateos.
  • git bisect hace búsqueda binaria: log2(n) pruebas para hallar el primer commit malo.
  • bisect run automatiza el recorrido: 0 = bueno, 1–127 = malo, 125 = saltar, 128+ = abortar.
  • Un criterio no determinista arruina el bisect; un 125 honesto lo salva.
  • git bisect reset al terminar: durante la sesión estás en HEAD desacoplado.
ComandoQué hace
git blame -L 10,20 -- archivoAtribuye un rango de líneas
git blame -L :funcion -- archivoAtribuye la función completa
git blame -w --ignore-revs-file f archivoIgnora espacios y commits de ruido
git bisect start / bad / goodDelimita el rango sospechoso
git bisect run cmdAutomatiza la búsqueda binaria
git bisect skipSalta un commit no verificable
git bisect log / replayGuarda o reproduce la sesión
git bisect resetCierra la sesión y vuelve a la rama

10 · Preguntas frecuentes

¿blame me da al autor original de la línea?

No necesariamente: da el último commit que la modificó. Si después de escribirla alguien la reformateó, la movió de archivo o la reindentó, ese commit tan reciente es el que aparece. Con -w, -M/-C y --ignore-revs-file puedes saltarte ese ruido y acercarte al verdadero origen.

¿bisect necesita que la historia sea lineal?

No; funciona sobre el grafo. Con merges, si quieres limitar la búsqueda al camino principal puedes usar git bisect start --first-parent. Lo importante es que exista una relación de ancestro entre good y bad: good debe ser alcanzable desde bad.

¿Cuántas pruebas va a hacer bisect?

Del orden de log2(n) donde n son los commits del rango. Git te lo anticipa en cada paso con el mensaje Bisecting: N revisions left (roughly k steps). Para 1000 commits son unas 10 pruebas; por eso bisect run merece casi siempre la pena frente a hacerlo a mano.

¿Qué hago si el commit culpable no compila?

Marca ese commit con git bisect skip, o haz que tu script de bisect run devuelva 125 cuando detecte que no puede probarse. bisect seguirá bisecando el resto del rango y, si hay varios commits contiguos incomprobables, te avisará de que la conclusión puede ser imprecisa.

¿Puedo usar bisect para repartir el trabajo entre varias máquinas?

Sí, con una técnica manual: git bisect start, marca el rango, y usa git bisect log para exportar la sesión; en otra máquina puedes marcarla a mano y devolver el resultado. También existe git bisect replay archivo para reproducir exactamente la secuencia de marcados. Para equipos, lo normal es dejar que bisect run lo haga en CI, donde el entorno es reproducible.
