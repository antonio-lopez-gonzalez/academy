worktree y config: dos checkouts, alias y perfiles

Módulo 6 · Investigar 🕐 35 minutos

1 · Introducción

Cierras el módulo con dos herramientas que casi nadie explota y que, bien usadas, te ahorran horas cada semana. git worktree te permite tener varios directorios de trabajo sobre el mismo repositorio: un hotfix en marcha mientras tu feature sigue a medias, sin stash ni clone extra. Y la configuración de Git (alias, includeIf, core.editor, pull.rebase, fetch.prune) convierte órdenes largas en gestos y adapta Git a cada directorio de tu máquina.

La lección anterior era sobre recuperar; esta es sobre trabajar cómodo. Ambas comparten una idea: quien conoce el modelo deja de memorizar y empieza a configurar su entorno.

¿Por qué worktree en vez de dos clones?

Dos clones duplican el almacén de objetos y descargan dos veces lo mismo. Un worktree comparte un único .git: el historial, los objetos y la configuración son los mismos, solo cambia el directorio de trabajo y el índice. Es la forma nativa de tener "la misma película en dos pantallas".

Errores típicos

Intentar tener la misma rama en dos worktrees (Git lo impide, y con razón); borrar a mano la carpeta de un worktree y creer que se ha eliminado; y poner core.hooksPath en la configuración global, afectando a todos los repositorios de la máquina.

2 · Teoría

Qué es un worktree

En Git, el repositorio (los objetos) y el directorio de trabajo (con su índice) son cosas separadas. Históricamente solo había uno de cada, y por eso para mirar otra rama tenías que switch (moviendo el único checkout). Un worktree rompe esa atadura: puedes asociar varios directorios de trabajo al mismo repositorio, cada uno en una rama distinta.

taller/                      ← worktree principal (rama main)
├── .git/                    ← el repositorio: objetos + config (único)
│   └── worktrees/
│       ├── hotfix/          ← metadatos del segundo worktree
│       └── revision/        ← metadatos del tercero
├── src/  notas.md  ...

taller-hotfix/               ← worktree 2 (rama hotfix/1.0.1)
taller-revision/             ← worktree 3 (HEAD desacoplado, para revisar un commit)

Los tres comparten los MISMOS objetos y el MISMO historial.
Lo unico que cambia es el indice y el directorio de trabajo de cada uno.
No es un submódulo ni un clon

Ramas, tags y stashes son compartidos entre todos los worktrees (viven en el repositorio común). Lo que no se comparte: el índice y el HEAD de cada worktree. Y una regla dura: una rama solo puede estar "checkouteada" en un worktree a la vez. Si intentas abrir main en un segundo worktree, Git te lo impedirá.

Los subcomandos

Casos de uso reales

  • Hotfix urgente mientras tienes un feature roto: creas un worktree en hotfix/1.0.1 desde main, publicas el arreglo, y tu feature sigue intacto en su carpeta.
  • Comparar dos versiones en paralelo: un worktree en v1.0.0 y otro en v2.0.0, y usas tu editor para ver ambos a la vez (si no, tendrías que switch y recompilar).
  • Revisar el PR de otra persona sin ensuciar tu checkout: git worktree add --detach ../revision origin/feature/x, pruebas sus tests, y borras el worktree.
  • Correr la suite de tests en la rama limpia mientras construyes en otra: el índice de cada worktree es independiente.

La configuración: cuatro niveles

Git lee la configuración de cuatro niveles, de menos a más específico. Gana el más específico:

  --system   /etc/gitconfig (o C:\Program Files\Git\etc\gitconfig)   todos los usuarios
  --global   ~/.gitconfig (.config/git/config)                       el usuario
  --local    .git/config                                             el repositorio   ◀ el habitual
  --worktree .git/config.worktree                                    solo este worktree

  Precedencia:  worktree  >  local  >  global  >  system
git config --list --show-origin            # de dónde sale cada valor (clave para no volverse loco)
git config --show-origin user.email        # solo una clave, con su archivo de origen
git config --global user.name "Ana Lopez"
git config --local pull.rebase true        # solo este repositorio
git config --worktree fetch.prune true     # solo este worktree
--show-origin es tu depurador de configuración

Cuando un valor "no se aplica" o "¿por qué mi email es el del trabajo en este repo?", git config --show-origin --list te dice el archivo exacto. Sin él, depurar configuración es adivinar.

Alias: convertir órdenes largas en gestos

git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.st "status --short --branch"
git config --global alias.undo "reset --soft HEAD~1"
# Un alias con "!" ejecuta una orden de shell (puede usar más comandos):
git config --global alias.quien "!git shortlog -sn --no-merges HEAD | head -10"
$ git lg -5
* 9f1c2ab (HEAD -> main) docs: explicar el indice en notas.md
* 7d4f5e6 (tag: v0.2.0) chore: ignorar node_modules
* 1a2b3c4 initial commit: notas.md
Dos cuidados con los alias

(1) No pisar una orden nativa: si defines alias.log, perderás git log tal cual lo conoces. Usa nombres nuevos (lg, st). (2) Los alias con ! son potentes pero no portables: van a la shell, así que en Windows dependen de Git Bash. Para el equipo, prefiera alias sin !.

includeIf: configuración por directorio

El problema clásico: trabajas con una identidad personal y otra laboral en la misma máquina. En vez de cambiar user.email a mano, Git permite incluir un archivo de configuración condicionalmente según dónde esté el repositorio:

# ~/.gitconfig  (global)
[user]
    name = Ana Lopez
    email = ana@personal.example
[includeIf "gitdir:~/trabajo/"]
    path = ~/.gitconfig-trabajo
[includeIf "gitdir:~/Academy/"]
    path = ~/.gitconfig-academy
# ~/.gitconfig-trabajo
[user]
    email = ana.lopez@empresa.example
[core]
    editor = "code --wait"
[pull]
    rebase = true
Detalles de includeIf

La condición gitdir: lleva barra final y hace glob (~/trabajo/ cubre cualquier repo dentro de esa carpeta). Usa gitdir/i: para ignorar mayúsculas (útil en Windows y macOS). También existe hasconfig:remote.*.url: para condicionar por la URL del remoto. La regla se aplica al descubrir el repositorio: si la carpeta no está donde esperabas, el include no se activa.

Las cinco claves que deberías fijar hoy

ClaveValor recomendadoPor qué
core.editor code --wait o vim Qué editor abre Git para el mensaje de commit o un rebase interactivo
pull.rebase true (o false, pero decide) Sin esto, cada pull avisa o crea merges de sincronización indeseados
fetch.prune true Elimina las ramas remotas que ya se borraron en origin al hacer fetch/pull
push.autoSetupRemote true git push configura el upstream solo en una rama nueva (menos -u)
init.defaultBranch main Evita que los repos nuevos nazcan en master
pull.rebase: elige una política, no la dejes al azar

pull = fetch + integrar. Integrar puede ser merge (historia con merges de sincronización) o rebase (tus commits se reaplican encima). Git 2.27+ te obliga a decidir entre pull.rebase y pull.ff. Para ramas de trabajo local, true produce historias más lineales; merges rebasea solo tus commits no publicados y conserva los merges. Elige y documéntalo en el equipo: lo peor es que cada uno haga lo contrario.

fetch.prune y la regla de oro

fetch.prune=true borra tus referencias a ramas remotas ya eliminadas en origin. Es lo correcto en el 99% de los casos. No borra commits de tu máquina ni de tus ramas locales. Pero si alguien borró una rama remota por error y necesitas un commit de ella, con prune ya activo el reflog de la rama remota (lección 03) sigue siendo tu vía de rescate.

3 · Ejemplo mínimo

La operación más pequeña de worktree: ver la rama main en otra carpeta mientras trabajas en tu feature.

cd taller
git worktree add ../taller-main main      # segundo checkout de main
git worktree list
$ git worktree list
C:/Desarrollo/Academy/taller         4b7e0d1 [feature/busqueda]
C:/Desarrollo/Academy/taller-main     9f1c2ab [main]

Qué esperamos ver: dos rutas, cada una con su rama y su commit. Ahora ../taller-main es un directorio de trabajo completamente funcional (puedes editarlo, compilarlo, commitear) sin haber tocado tu feature/busqueda.

git worktree remove ../taller-main        # se acabo: fuera
git worktree list                         # solo queda el principal
La misma rama, no

Si intentas git worktree add ../x feature/busqueda (la rama que ya tienes checkouteada), Git responde fatal: 'feature/busqueda' is already checked out at '…'. Es una protección, no un fallo: dos índices sobre la misma rama serían una fuente inagotable de conflictos. Para revisar esa rama sin tocarla, usa --detach.

4 · Ejemplo real

El escenario que más he visto en equipos reales: estás a media refactorización en feature/busqueda cuando llega el aviso de un bug crítico en producción. Necesitas publicar un parche en main ya, sin romper tu trabajo a medias.

Antes (el camino del stash)

git stash  →  git switch main  →  fix  →  commit  →  push
           →  git switch feature/busqueda  →  git stash pop  →  conflictos posibles

Riesgos: el stash puede no aplicarse limpio; te olvidas de volver;
y mientras estas en main no puedes consultar tu codigo a medias.

Después (worktree)

# 1) Sigues en feature/busqueda, con tus cambios sin commitear, tan tranquilo.
# 2) Creas un worktree desde main para el hotfix:
git worktree add -b hotfix/1.0.1 ../taller-hotfix main

# 3) Trabajas ALLI (otra terminal / otra ventana del editor):
cd ../taller-hotfix
# ... arreglas el bug en el fichero ...
node --test test/regresion.test.js        # prueba en la rama limpia
git commit -am "fix: evitar 500 al listar notas sin texto"
git push -u origin hotfix/1.0.1

# 4) Vuelves a tu feature, que nunca se movio:
cd ../taller
git status          # tus cambios siguen ahi, intactos
Por qué funciona tan bien

Cada worktree tiene su propio índice. Los cambios sin commitear de feature/busqueda viven en el índice del worktree principal; los del hotfix, en el suyo. No hay stash, no hay riesgo de pop, no hay ningún momento en que tu trabajo a medias deje de estar a la vista.

Y ahora, la configuración a juego

Tres gestos que hacen que este flujo sea rápido y seguro. Primero, un alias para no escribir el log gigante:

git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.st "status --short --branch"
git lg -10

Segundo, un editor y una política de pull explícitos:

git config --global core.editor "code --wait"
git config --global pull.rebase true
git config --global fetch.prune true
git config --global push.autoSetupRemote true
git config --global init.defaultBranch main

Tercero, identidad por directorio: el correo del trabajo dentro de la carpeta de la empresa, y el personal fuera.

# ~/.gitconfig
[user]
    name  = Ana Lopez
    email = ana@personal.example
[includeIf "gitdir/i:C:/Desarrollo/trabajo/"]
    path = ~/.gitconfig-trabajo
[includeIf "gitdir/i:C:/Desarrollo/Academy/"]
    path = ~/.gitconfig-academy
# Comprobacion: desde el repo del trabajo vs el personal
cd trabajo/api && git config user.email      # ana.lopez@empresa.example
cd ../../Academy        && git config user.email   # el global personal
git config --list --show-origin | Select-String email   # PowerShell ve el origen
Cuidado con las barras en Windows

En gitdir, Git normaliza separadores, pero lo más robusto es escribirlo con barras normales (C:/Desarrollo/…) y usar gitdir/i: para no depender del uso de mayúsculas del sistema de archivos. Y recuerda la barra final: ~/trabajo/ — sin ella, la coincidencia puede no ser la que esperas.

Cuando el worktree se queda huérfano

# Borraste la carpeta a mano (sin "worktree remove")
git worktree list                 # aparece como "prunable"
git worktree prune -v             # limpia los metadatos colgantes
git worktree list                 # ahora si: solo los que existen de verdad

5 · Buenas prácticas

PrácticaPor qué
Crea los worktrees fuera del directorio principal ../taller-hotfix o un worktrees/ hermano; dentro del repo ensuciarías el árbol y el .gitignore
Elimina con worktree remove, no con rm -rf Deja los metadatos coherentes; si borras a mano, tienes que recordar worktree prune
Nombra el worktree por su propósito taller-hotfix, taller-revision-pr-142: git worktree list tiene que contarte una historia

Usa --show-origin antes de editar a ciegas Saber en qué archivo se define un valor es la mitad del arreglo

6 · Errores habituales

1. Intentar dos veces la misma rama

Mal — reusar la rama ya checkouteada 
# Estas en feature/busqueda y quieres "otra copia" de ella:
git worktree add ../taller-otra feature/busqueda
# fatal: 'feature/busqueda' is already checked out at '...'
# Y NO debe forzarse: dos indices sobre la misma rama = conflictos absurdos.
Bien — otra rama, o un checkout desacoplado 
# Opcion A: trabajo nuevo a partir de la base
git worktree add -b feature/busqueda-v2 ../taller-v2 main
# Opcion B: solo mirar el estado actual, sin rama propia
git worktree add --detach ../taller-mira feature/busqueda

2. Borrar la carpeta a mano

Mal — el worktree desaparece pero los metadatos quedan 
rm -rf ../taller-hotfix        # la carpeta ya no esta
git worktree list
# taller-hotfix  (prunable)   ← Git cree que sigue existiendo
# Y la rama hotfix/1.0.1 sigue "ocupada" por un worktree fantasma.
Bien — eliminar con Git y podar si hizo falta 
git worktree remove ../taller-hotfix    # si el arbol esta sucio: --force
git worktree prune -v                   # solo si borraste a mano o el disco externo no esta
git worktree list

3. core.hooksPath o user.email en global cuando deben ser locales

Mal — una config que se filtra a todos los repositorios 
# Los hooks del proyecto del equipo, puestos en global:
git config --global core.hooksPath .githooks
# Ahora TODOS tus repos buscan .githooks en su raiz...
# y los que no lo tengan se comportan de formas raras o fallan.
Bien — config de proyecto en local o vía includeIf 
git config --local core.hooksPath .githooks
# O fijarlo a mano en el clon (el hook es un archivo del repo):
git config --local core.hooksPath .githooks
# Y las identidades, con includeIf por carpeta, no cambiando el global a cada rato.

4. Alias que pisa un comando nativo

Mal — redefinir log, status o checkout 
git config --global alias.log "log --oneline --graph"
# A partir de ahora "git log" NUNCA sera el git log completo.
# Cualquier script o tutorial que asuma "git log" se rompe en tu maquina.
Bien — nombres nuevos y cortos 
git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.last "log -1 --stat"
# "git lg" es tuyo; "git log" sigue intacto para humanos y scripts.

7 · Ejercicio guiado

Objetivo: montar un flujo de hotfix con worktree y dejar tu configuración con alias, editor y política de pull de una vez por todas.

  1. Paso 1 — Prepara el escenario del taller: 
    cd taller
git switch -c feature/busqueda          # rama a medias
printf 'borrador de trabajo' >> notas.md
git status --short                      # cambios sin commitear (a proposito)

    Deja ese cambio sin commitear: va a demostrar que el worktree no lo toca.

  2. Paso 2 — Crea el worktree del hotfix desde main: 
    git worktree add -b hotfix/1.0.1 ../taller-hotfix main
git worktree list

    Resultado esperado: dos entradas: taller en feature/busqueda y taller-hotfix en hotfix/1.0.1.

  3. Paso 3 — Trabaja el hotfix en su carpeta: 
    cd ../taller-hotfix
git status --short              # limpio: no ve el borrador de la otra rama
# haz un cambio pequeño, por ejemplo en src/busqueda.js
git commit -am "fix: evitar error al filtrar notas sin texto"
git log --oneline -2
  4. Paso 4 — Comprueba el aislamiento y vuelve: 
    cd ../taller
git status --short              # tu borrador sigue exactamente igual
git log --oneline -1            # tu HEAD no se movio
git branch --show-current       # feature/busqueda

    Resultado esperado: el commit del hotfix no aparece en tu rama y tu trabajo a medias está intacto. Ese es el valor del worktree.

  5. Paso 5 — Configura alias, editor y políticas: 
    git config --global core.editor "code --wait"
git config --global pull.rebase true
git config --global fetch.prune true
git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.st "status --short --branch"

git lg -8          # usa el alias recien creado
git st             # version compacta del status
git config --list --show-origin | grep -i "pull.rebase\|core.editor"

    Resultado esperado: --show-origin te muestra que ambas claves vienen del ~/.gitconfig global. Si alguna viniera de un repo concreto, ya sabes por qué "no se aplica".

  6. Paso 6 — Perfil por directorio e limpieza: 
    # Anade a ~/.gitconfig un includeIf de ejemplo (adáptalo a tus rutas):
#   [includeIf "gitdir/i:C:/Desarrollo/trabajo/"]
#       path = ~/.gitconfig-trabajo
git config --global --get-all includeIf.gitdir/i:C:/Desarrollo/trabajo/.path
#   (vacio si aun no lo has creado: escribelo a mano en el archivo)

git worktree remove ../taller-hotfix
git branch -D hotfix/1.0.1
git worktree list

    Resultado esperado: de vuelta a un solo worktree, con la configuración aplicada y verificable con --show-origin.

8 · Reto

🎯 Una revisión de PR con worktree y un alias para todo

Monta el flujo completo de "revisar el trabajo de otra persona sin ensuciar mi checkout": crea una rama feature/otro en el taller con un commit ajeno simulado, y luego revisa ese cambio en un worktree desacoplado (sin rama propia) usando --detach. Dentro de ese worktree, compara con la base (git diff main...HEAD), ejecuta los tests y anota tu veredicto. Al terminar, elimina el worktree y la rama temporal. Bonus: define un alias git rev que cree el worktree de revisión, entre en él e imprima el diff contra main, todo en un solo comando.

Pista: git worktree add --detach ../revision origin/feature/x deja el worktree en HEAD desacoplado, ideal para revisar sin tocar ninguna rama. Para el alias con varios pasos necesitarás ! y --no-checkout o un cd dentro de la orden de shell; recuerda que los alias con ! no son portables a Windows más allá de Git Bash, así que valora el coste antes de adoptarlo en equipo.

9 · Resumen

  • git worktree asocia varios directorios de trabajo a un único repositorio: comparten objetos, ramas y tags; cada uno tiene su índice y su HEAD.
  • Una rama solo puede estar checkouteada en un worktree a la vez; para revisar sin rama, --detach.
  • Se crean con add [-b] [--detach] y se eliminan con remove (y prune si borraste a mano).
  • La configuración tiene cuatro niveles — --system, --global, --local, --worktree — y --show-origin te dice de cuál sale cada valor.
  • Los alias acortan órdenes largas (lg, st); no pises comandos nativos.
  • includeIf "gitdir:…" aplica configuración por carpeta: el truco para tener dos identidades (y dos políticas) en una máquina.
  • core.editor, pull.rebase, fetch.prune, push.autoSetupRemote e init.defaultBranch son las claves que conviene fijar de una vez.

10 · Preguntas frecuentes

¿Un worktree comparte los cambios sin commitear?

No. Lo compartido es el almacén de objetos, las ramas, los tags y la configuración. El índice y el directorio de trabajo son propios de cada worktree: los cambios sin commitear de uno son invisibles para el otro. Esa independencia es precisamente lo que hace de worktree una alternativa mejor que stash para interrumpir trabajo a medias.

¿Puedo compilar o ejecutar tests en dos worktrees a la vez?

Sí, y es uno de sus mejores usos: cada worktree es una carpeta normal con su propia copia de los archivos. Cuidado solo con los artefactos compartidos por ruta absoluta (cachés, node_modules enlazados, bases de datos locales): si dos ejecuciones escriben en el mismo sitio, chocarán. Mantén los artefactos dentro de cada carpeta o usa nombres distintos.

¿worktree sustituye a los submódulos?

No, resuelven problemas distintos. Un submódulo incrusta otro repositorio dentro del tuyo (otro historial, otra URL). worktree te da otro directorio de trabajo del mismo repositorio. Submódulos para dependencias de código ajenas; worktrees para trabajar varias ramas del tuyo a la vez.

¿Qué diferencia hay entre --local y --worktree al configurar?

--local guarda el valor en .git/config y afecta a todos los worktrees del repositorio. --worktree lo guarda en .git/config.worktree y afecta solo al worktree donde lo ejecutas (requiere extensions.worktreeConfig activo, que Git activa al usarlo). Útil para diferencias puntuales, como core.bare o un core.hooksPath concreto de ese checkout.

¿Es seguro poner pull.rebase=true en global?

Es una política, no un peligro, con una condición: que no rebases commits ya publicados. Rebasear al hacer pull reescribe tus commits locales no publicados por encima de los del remoto, lo cual es limpio y seguro. Si tu equipo prefiere merges o trabajáis con ramas compartidas largas, usa pull.rebase=merges (rebasea solo lo propio y conserva merges) y documéntalo. Lo que no debe pasar es dejar la decisión al azar: Git te obliga a elegir por algo.
