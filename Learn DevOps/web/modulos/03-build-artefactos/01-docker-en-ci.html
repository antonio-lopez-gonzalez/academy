Docker en CI: la imagen multi-stage con Buildx

Módulo 3 · Build y artefactos 🕐 35 minutos

1 · Introducción

En el Módulo 2 montamos un pipeline de integración continua: en cada push y cada pull request, GitHub Actions hacía checkout, instalaba dependencias, corría el lint y los tests. Eso te dice si el código está sano, pero no produce nada que puedas desplegar. Al terminar el job, el runner —una máquina temporal— se destruye, y con él todo lo que se compiló.

Esta lección da el paso que convierte «código que pasa los tests» en un artefacto: la imagen Docker de la Copiloto API. Y lo hace donde debe hacerse: en CI, no en tu portátil. El objetivo es que el binario que se despliegue más adelante (Módulo 4) sea exactamente el que se construyó aquí, a partir de un commit concreto, con la misma receta para todo el equipo.

¿Por qué construir en CI y no en local? Porque «en mi máquina funciona» deja de ser una excusa cuando la máquina deja de ser la tuya. El runner es efímero y limpio: nadie ha dejado ahí un node_modules a medias ni una variable de entorno mágica. Si el build pasa en CI, pasa con lo que hay en el repositorio, y solo con eso. Esa es la diferencia entre un artefacto reproducible y una caja negra.

Lo que verás en este módulo: aquí construimos la imagen; en la lección 2 la publicamos en un registry con etiquetas inmutables; en la 3 le añadimos SBOM y procedencia (cadena de suministro); y en la 4 afinamos la caché para que los builds vuelen. Todo gira alrededor del mismo objeto: el artefacto que se prueba es el que se despliega.

2 · Teoría

Del código fuente al artefacto

Un pipeline de release tiene dos mitades bien separadas. La primera verifica (integración continua); la segunda produce (el build). El artefacto es el eslabón que las une: es lo que viaja hacia los entornos.

commit ┌─────────────── CI (Módulo 2) ───────────────┐ ────────► │ lint ─► test ─► cobertura ─► (pasa) │ └─────────────────────────────────────────────┘ │ ▼ ┌─────────────── BUILD (esta lección) ────────────────┐ │ docker buildx build ──► IMAGEN (artefacto) │ └─────────────────────────────────────────────────────┘ │ imagen + digest (inmutable) ▼ REGISTRY (lección 2) ──► CD (Módulo 4) ──► entornos

Fíjate en la dirección del flujo: el artefacto se construye una sola vez y se promociona entre entornos sin reconstruirse. Reconstruir en cada entorno (staging, producción) es el pecado original de la entrega continua: dos builds distintos nunca son la misma imagen, aunque salgan del mismo commit.

El runner es efímero: la caché local no existe

Cuando lanzas docker build en tu portátil, Docker reutiliza las capas ya construidas y el rebuild es casi instantáneo. En GitHub Actions, cada job arranca en una máquina virtual recién creada: no hay capas anteriores, no hay node_modules, no hay nada. El primer build en CI siempre parte de cero.

Eso cambia cómo piensas el Dockerfile: el orden de las instrucciones deja de ser una preferencia estética y pasa a ser ingeniería de caché (lo veremos a fondo en la lección 4). Y explica por qué el build en CI, la primera vez, siempre «tarda más de lo que tarda en mi máquina».

Buildx: el builder que sí funciona en CI

Docker moderno trae BuildKit como motor de build, y Buildx como su interfaz. En un runner limpio conviene crear un builder propio con el driver docker-container, y para eso está la action oficial docker/setup-buildx-action:

  • Multi-plataforma: construir linux/amd64 y linux/arm64 desde un solo job.
  • Exportar/importar caché: clave para que el CLI no reconstruya todo cada vez.
  • Attestations: SBOM y procedencia (lección 3), que el exporter clásico no soporta.
  • Secrets de build: inyectar credenciales sin dejarlas en capas.

Analogía — el obrador y la vitrina: el runner es el obrador (efímero: se monta cada día y se desmonta al cerrar). Buildx es la maquinaria que traes al obrador para amasar rápido y guardar los preparados de un día para otro (la caché). La imagen final es la tarta terminada que sale a la vitrina: no la montas en cada tienda, la horneas una vez en el obrador y la distribuyes.

docker/build-push-action: el build como paso declarativo

Podrías escribir un run: docker build ... a mano, pero la comunidad usa la action oficial docker/build-push-action porque expone Buildx como entradas declarativas (with:) en lugar de una línea de shell larga y frágil. Estas son las que tocarás:

EntradaQué hace
contextCarpeta que se envía como contexto de build (por defecto, el repo clonado).
fileRuta al Dockerfile cuando no está en la raíz del contexto.
targetConstruye solo una etapa del multi-stage (por ejemplo runtime).
tagsEtiquetas de la imagen resultante.
pushtrue publica en el registry; false la deja local (útil para smoke tests).
loadCarga la imagen en el Docker del runner para poder docker run en el mismo job.
cache-from / cache-toDe dónde leer y dónde escribir la caché de build (lección 4).
platformsArquitecturas objetivo (por defecto, la del runner).

Multi-stage: una receta, dos mundos

La Copiloto API es una aplicación Python. Sus dependencias se instalan con uv (o pip), y para producir la imagen de producción no necesitas ni el gestor de paquetes, ni las dependencias de desarrollo, ni el código de tests. El multi-stage separa el taller de la vitrina en un único Dockerfile:

ETAPA "builder" (taller) ETAPA "runtime" (vitrina) = IMAGEN FINAL ───────────────────────── ──────────────────────────────────────── FROM python:3.12-slim AS builder FROM python:3.12-slim AS runtime COPY pyproject.toml uv.lock ENV PATH=/app/.venv/bin:$PATH RUN uv sync --frozen --no-dev COPY --from=builder /app/.venv /app/.venv COPY app ./app COPY --from=builder /app/app /app/app (dependencias + resolución) USER app CMD ["uvicorn", "app.main:app"] │ SOLO viaja lo copiado con COPY --from=builder └───────────────► uv, caches y dev-deps se quedan en el taller

El resultado de la etapa runtime es la imagen de producción: más pequeña, sin herramientas de construcción y con menos superficie que atacar. Es el mismo principio que viste en Learn Docker, ahora dentro de un job de CI.

3 · Ejemplo mínimo

El workflow más pequeño que construye la imagen en CI y comprueba que arranca. Todavía no publica nada (eso es la lección 2): solo demuestra que el build ocurre en el runner, no en tu portátil.

.github/workflows/build.yml
name: build

# Se dispara en cada push y en cada pull request: el artefacto debe
# poder construirse SIEMPRE, no solo cuando decidimos publicar.
on:
  push:
    branches: [main]
  pull_request:

jobs:
  docker:
    runs-on: ubuntu-latest
    steps:
      # 1. Traer el código al runner.
      - name: Checkout
        uses: actions/checkout@v7

      # 2. Crear un builder de Buildx con driver docker-container:
      #    es lo que habilita caché exportable y (más adelante) attestations.
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4

      # 3. Construir la imagen. push: false -> no sale del runner.
      #    load: true -> queda en el Docker local para poder probarla abajo.
      - name: Build image (sin publicar)
        uses: docker/build-push-action@v7
        with:
          context: .
          file: ./Dockerfile
          target: runtime        # construye SOLO la última etapa
          push: false
          load: true
          tags: copiloto-api:ci

      # 4. Verificación funcional: si la imagen no arranca, el job falla.
      - name: Smoke test
        run: |
          docker run -d --name api -p 8000:8000 copiloto-api:ci
          for i in $(seq 1 30); do
            curl -fsS http://localhost:8000/health && break
            sleep 1
          done
          docker logs api
          docker rm -f api

Línea por línea, las decisiones que importan:

  • on: push + on: pull_request: el artefacto se construye en cada cambio. Si algo rompe el Dockerfile, te enteras en la PR, no al desplegar un viernes.
  • setup-buildx-action: crea un builder con el driver docker-container. Sin él, cache-to y las attestations no están disponibles.
  • target: runtime: pedimos explícitamente la etapa final. Es la imagen que se desplegará; construirla ahora evita sorpresas después.
  • push: false + load: true: la imagen se queda en el runner y se carga en el Docker local, lo que permite el smoke test.
  • curl -fsS .../health: un build que no arranca no es un artefacto. Verificamos que responde antes de dar el job por bueno.

El -f de curl no es decoración: sin -f, curl devuelve 0 aunque el servidor responda 500. Con -f, un error HTTP hace fallar el paso, y con él el job. Un test que nunca puede fallar no es un test.

4 · Ejemplo real

El Dockerfile real de la Copiloto API y el job que lo construye en el proyecto conductor proyectos/pipeline/. Es un multi-stage con uv: la etapa builder resuelve las dependencias desde el lockfile, y la etapa runtime recibe solo el entorno virtual y el código de la aplicación.

proyectos/pipeline/Dockerfile
# syntax=docker/dockerfile:1
# ---------- Etapa 1: builder (taller) ----------
FROM python:3.12-slim AS builder

# Copiamos el binario de uv desde su imagen oficial. Fija una etiqueta
# concreta (por ejemplo la ultima 0.x estable) en lugar de "latest".
COPY --from=ghcr.io/astral-sh/uv:0.9 /uv /uvx /bin/

WORKDIR /app
# uv copia (en vez de enlazar) y compila bytecode: rutas aptas para imagen.
ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy

# 1) Manifiestos primero: si no cambian, esta capa se reutiliza (caché).
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-install-project --no-dev

# 2) Ahora el codigo de la aplicacion.
COPY app ./app
# 3) Instalamos el proyecto en si (--no-dev: sin herramientas de desarrollo).
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

# ---------- Etapa 2: runtime (vitrina) = IMAGEN FINAL ----------
FROM python:3.12-slim AS runtime

# Usuario sin privilegios: la app no necesita ser root.
RUN useradd --create-home --uid 10001 appuser
WORKDIR /app

# Copiamos SOLO el entorno virtual y el codigo, nunca el taller.
COPY --from=builder /app/.venv /app/.venv
COPY --from=builder /app/app /app/app

ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1

USER appuser
EXPOSE 8000
# Exec form: la senal llega directamente al proceso (PID 1 correcto).
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
proyectos/pipeline/.github/workflows/publish.yml
name: publish

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4

      - name: Build image (artefacto del pipeline)
        uses: docker/build-push-action@v7
        with:
          context: .
          file: ./Dockerfile
          target: runtime
          # Etiqueta provisional por commit: la publicacion real (con
          # login y push) llega en la leccion 2.
          push: false
          load: true
          tags: copiloto-api:${{ github.sha }}

      - name: Comprobar el endpoint de salud
        run: |
          docker run -d --name copiloto -p 8000:8000 \
            -e ENVIRONMENT=ci copiloto-api:${{ github.sha }}
          for i in $(seq 1 30); do
            curl -fsS http://localhost:8000/health && break
            sleep 1
          done
          docker rm -f copiloto

Por qué etiquetamos con ${{ github.sha }} ya aquí: porque cada imagen debe poder rastrearse hasta el commit que la produjo. Es la semilla de la inmutabilidad que formalizamos en la lección 2: un identificador que nunca se reutiliza. Si el artefacto de hoy y el de mañana comparten etiqueta, ya no sabes qué desplegaste.

5 · Buenas prácticas

HazEvitaPor qué
Construye el artefacto una sola vez en CI Reconstruir en cada entorno (staging, prod) Dos builds nunca son idénticos. Si pruebas una imagen y despliegas otra, tu verificación no vale nada.
Usa un multi-stage con etapa runtime mínima Terminar el Dockerfile en la etapa de build Menos tamaño, sin compiladores ni dev-deps en producción: menos superficie de ataque y escaneos más limpios.
Etiqueta con el commit: ${{ github.sha }} Depender de latest como única etiqueta Trazabilidad. Debes poder responder «¿qué commit produjo esta imagen?» sin adivinar.
Fija la versión de las imágenes base (python:3.12-slim) FROM python:latest Una base que cambia sola rompe builds sin que toques nada. El pin hace el build reproducible.
Ejecuta la app como usuario sin privilegios (USER appuser) Dejar que la imagen corra como root Un contenedor comprometido como root es mucho más peligroso. Es gratis evitarlo.
Haz un smoke test de la imagen construida en el mismo job Asumir que «compiló, luego funciona» Un build exitoso solo prueba que se construyó. Arrancar y responder es lo que valida el artefacto.

6 · Errores habituales

1. Construir en local y subir el artefacto a mano

Mal — el artefacto nace en tu portátil 
# En tu maquina: nadie sabe que paso aqui ni con que versiones
docker build -t copiloto-api:latest .
docker push copiloto-api:latest   # a un registry
Bien — el artefacto nace en el runner, desde el commit 
- name: Build image
  uses: docker/build-push-action@v7
  with:
    context: .            # exactamente lo que hay en el commit
    push: false
    tags: copiloto-api:${{ github.sha }}

2. Copiar el código antes de las dependencias (mata la caché)

Mal — cualquier cambio de código reinstala todo 
FROM python:3.12-slim AS builder
WORKDIR /app
COPY . .                       # el codigo cambia en cada commit...
RUN uv sync --frozen --no-dev  # ...y esta capa se invalida SIEMPRE
Bien — manifiestos primero, código después 
WORKDIR /app
COPY pyproject.toml uv.lock ./                 # solo cambian si tocan deps
RUN uv sync --frozen --no-install-project --no-dev
COPY app ./app                                 # el codigo va al final
RUN uv sync --frozen --no-dev

3. Un Dockerfile fuera de la raíz sin decir dónde está

Mal — la action busca ./Dockerfile y no lo encuentra 
- uses: docker/build-push-action@v7
  with:
    context: .
    # El Dockerfile vive en docker/, pero no lo indicamos ->
    # "ERROR: failed to solve: failed to read dockerfile"
Bien — indica file (y el context correcto) 
- uses: docker/build-push-action@v7
  with:
    context: .
    file: ./docker/Dockerfile

4. Creer que docker build a secas basta en CI

Funciona, pero pierdes lo que hace útil a Buildx en un runner: caché exportable, multi-plataforma y attestations. Además, mezclar run: docker build con push a mano dispersa la lógica. Usa la action declarativa.

Ojo con load: true y las attestations: el exporter docker (que es lo que hace load) no soporta SBOM ni procedencia. Cuando activemos esas attestations en la lección 3, el patrón cambiará a push: true, porque las attestations se adjuntan a la imagen en el registry.

9 · Resumen

  • El artefacto es la imagen. Se construye una vez en CI y se promociona entre entornos sin reconstruirse.
  • El runner es efímero: no hay caché local; el orden del Dockerfile pasa a ser ingeniería de caché.
  • Buildx + docker-container: habilita caché exportable, multi-plataforma, secrets y attestations. Lo crea docker/setup-buildx-action.
  • docker/build-push-action: el build como paso declarativo (context, file, target, push, load, cache-*, platforms).
  • Multi-stage: taller (builder) y vitrina (runtime) en un solo Dockerfile; solo lo copiado con COPY --from llega a producción.
  • Trazabilidad: etiqueta con ${{ github.sha }} desde el primer momento.

10 · Preguntas frecuentes

¿Por qué no basta con run: docker build en el job?

Funcionar, funciona. Pero pierdes el builder docker-container (y con él la caché exportable, el multi-plataforma y las attestations), y sustituyes un contrato declarativo por una línea de shell larga que cada persona escribe distinto. La action oficial existe justo para eso: que el build sea igual en todos los repositorios.

¿Cuándo uso load: true y cuándo push: true?

load: true cuando quieres la imagen en el runner para probarla en el mismo job (smoke tests, escaneos, multi-etapa de test). push: true cuando quieres publicarla en un registry para que otros la consuman. Y recuerda: con varias platforms no puedes usar load; necesitas push.

El build funciona en local pero falla en CI. ¿Por qué?

Casi siempre, por tres motivos: (1) falta un archivo que tu .dockerignore excluye en local pero que CI necesita; (2) el runner no tiene algo que tu máquina sí (una variable de entorno, un binario); o (3) una imagen base que en local tenías cacheada y que en CI se descarga distinta. Reproduce con un contenedor limpio: docker build --no-cache . es tu mejor simulador de runner.

¿Construir la imagen en la PR es tirar recursos?

No: es barato comparado con el coste de descubrir en producción que la imagen no construye. Si te preocupa el tiempo, la caché de la lección 4 reduce el build de la PR a segundos cuando solo cambia el código. Y puedes condicionar el push a main: construye siempre, publica solo cuando toque.

¿La imagen que pruebo en CI es la misma que se despliega?

Solo si la publicas y despliegas por digest (por ejemplo imagen@sha256:...). El smoke test de esta lección prueba la imagen del mismo job: es una garantía fuerte. La lección 2 te enseña a conservar esa garantía al cruzar el registry con etiquetas inmutables y digests.
