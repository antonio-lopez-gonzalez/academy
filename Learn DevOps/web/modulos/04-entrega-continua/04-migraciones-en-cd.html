Migraciones en CD

Módulo 4 · Entrega continua 🕐 35 minutos

1 · Introducción

La Copiloto API tiene datos: conversaciones, usuarios, embeddings. Y el código cambia; a veces, de forma que necesita una nueva forma de la base de datos —una columna, un índice, una tabla—. Ese cambio se llama migración, y es la parte del despliegue que asusta a todo el mundo, con razón: una aplicación se puede reiniciar, un esquema de base de datos no.

El problema es que la base de datos es estado. Cuando despliegas una versión nueva de la app, durante unos segundos conviven dos versiones del código (la vieja apagándose, la nueva arrancando). Si el esquema cambió de golpe, la versión vieja se rompe. Por eso una migración en CD no es «aplicar un ALTER TABLE», sino orquestar esquema y código para que todas las versiones en vuelo sean compatibles. Esta lección enseña cómo.

¿Por qué esta lección existe? Porque la mayoría de incidentes graves de despliegue no son de código, son de datos. Un DROP COLUMN en el momento equivocado, una migración que no se puede deshacer o que se ejecuta dos veces simultáneamente puede destruir información irrecuperable. Saber ordenar los cambios es lo que separa un despliegue aburrido de un desastre.

La migración nunca se ejecuta al arrancar la app. Si cada réplica aplica migraciones al iniciarse, varias se pisan a la vez y corrompen el estado. Las migraciones son un job propio, una sola vez, antes de desplegar la nueva versión.

2 · Teoría

Por qué migrar es distinto de desplegar

El código es efímero: se reemplaza y listo. Los datos son persistentes: no puedes «volver a una versión anterior» de un dato que ya transformaste. Además, durante un despliegue sin parar el servicio, la app vieja y la nueva coexisten. Mira:

   t0: [ v1 ]                    migracion aplicada
        │                              │
        ├── v2 arranca ◀────────────────┤         ┌── hay un instante con v1 Y v2 vivas ──┐
        │                                   v2   │  ambas deben saber leer el esquema     │
        │                        [ v1 ] ──────▶ [ v1 apagandose, v2 arrancando ]
        │                                          │
        └── [ v2 ] ◀───────────────────────────────┘  solo cuando v1 muere, el esquema viejo sobra

Conclusión ineludible: cada versión del código debe funcionar con el esquema de antes y con el de después. Al cambio de esquema que cumple esto se le llama compatibilidad hacia atrás (y hacia adelante).

El patrón expand/contract

La técnica estándar para lograr esa compatibilidad se llama expand/contract (expandir y contraer). Consiste en romper un cambio incompatible en una secuencia de cambios compatibles repartidos en varias releases:

FaseQué hacesCompatibilidad
1. ExpandAñadir lo nuevo sin quitar lo viejo (nueva columna opcional, nueva tabla)v1 y v2 funcionan
2. Migrar datosBackfill: rellenar lo nuevo a partir de lo viejov1 y v2 funcionan
3. Cambiar el códigov2 escribe y lee lo nuevo (y, si hace falta, aún mantiene lo viejo)v1 y v2 funcionan
4. ContractCuando ya nadie usa lo viejo, eliminarlo (otra release)solo v2+

Nunca se pasa de «renombrar una columna» a «añadir + backfill + cambiar + borrar». Se reparte en el tiempo para que cada paso sea aburrido.

Analogía: cambiar el motor de un coche en marcha. No desmontas el viejo antes de tener el nuevo montado: primero acoplas el nuevo motor (expand), trasvasa todo (backfill), empiezas a usarlo (cambio de código) y solo entonces desmontas el viejo (contract). Nunca dejas el coche sin motor.

Orden de despliegue: esquema primero, código después

El orden correcto casi siempre es migración → despliegue del código. ¿Por qué? Porque el código nuevo puede requerir la columna nueva, pero el código viejo no debe romperse si ya existe. La migración de la fase expand es aditiva (solo añade), así que la app vieja la ignora sin problema. Después se despliega el código que la usa.

Regla de oro: «añade antes de usar; elimina mucho después de dejar de usar». Si tu migración rompe el código viejo (borra, renombra, hace NOT NULL sobre datos existentes), estás mezclando fases y vas a romper el despliegue.

Migraciones reversibles… y por qué a veces no lo son

Una migración reversible tiene un up (aplicar) y un down (deshacer). En la práctica:

  • Reversible de verdad: añadir una tabla o una columna (se deshace con DROP).
  • No reversible sin pérdida: eliminar una columna con datos, o transformar valores (¿recuperas los originales?).

Por eso, cada vez más equipos prefieren forward-fix (arreglar hacia adelante con otra migración) antes que rollback del esquema. El patrón expand/contract lo hace posible: si el cambio destructivo es siempre el último paso, casi siempre hay marcha atrás. Y si no la hay, al menos el paso destructivo llega cuando ya no hay código que dependa de él.

Una migración también debe ser idempotente o, al menos, no reejecutarse sola. Las herramientas serias (Alembic, Flyway, Liquibase…) llevan una tabla de control con las migraciones ya aplicadas; aplican solo las pendientes, en orden. Confía en ese mecanismo, no en scripts improvisados.

3 · Ejemplo mínimo

Una migración aditiva (fase expand) en SQL puro: añadir una columna opcional que el código nuevo usará y el viejo ignora. Es el átomo de todo el patrón.

migrations/0007_add_conversation_summary.sql
-- Fase EXPAND: solo anade. La app v1 ignora la columna; la v2 la usara.
ALTER TABLE conversations
  ADD COLUMN summary TEXT;

-- Indice para las consultas nuevas, sin bloquear escrituras en la mayoria de motores.
CREATE INDEX CONCURRENTLY idx_conversations_summary
  ON conversations (summary);

Línea por línea:

  1. ADD COLUMN summary TEXT: columna nueva nullable (sin NOT NULL). Aditiva y compatible: el código viejo hace SELECT * y ve una columna más que puede ignorar; el nuevo la escribe.
  2. Sin DEFAULT bloqueante: en tablas grandes, añadir una columna con valor por defecto puede reescribir toda la tabla y bloquearla. Aquí no lo necesitamos.
  3. CREATE INDEX CONCURRENTLY: en PostgreSQL, construir el índice sin bloquear escrituras. En motores pequeños da igual; en tablas grandes, marca la diferencia entre un despliegue y una caída.
  4. Nombre con número 0007: las migraciones se ordenan y se registran. La herramienta sabrá que esta ya se aplicó y no la repetirá.

Este archivo no toca la aplicación: es un cambio del esquema independiente. Ese es el punto. El código v2 vendrá después, en su propio despliegue, a usar summary.

4 · Ejemplo real

El Copiloto necesita renombrar body a content en la tabla messages. Un RENAME COLUMN rompería la app vieja al instante. Aplicamos expand/contract repartido en tres releases.

Release 1 — expand: la columna nueva convive con la vieja

migrations/0011_expand_messages_content.sql
-- EXPAND: anade la columna nueva. Aun no se borra "body".
ALTER TABLE messages
  ADD COLUMN content TEXT;

-- Backfill por lotes para no bloquear la tabla en produccion.
UPDATE messages
   SET content = body
 WHERE content IS NULL
   AND id IN (
     SELECT id FROM messages WHERE content IS NULL ORDER BY id LIMIT 10000
   );

El código de la release 1 sigue leyendo y escribiendo body; y además empieza a escribir también en content (dual-write). Así la columna nueva se mantiene al día mientras la vieja sigue siendo la fuente de verdad.

migrations/0011_rollback.sql
-- Deshacer la fase expand es seguro: solo quita lo anadido.
ALTER TABLE messages DROP COLUMN content;

Release 2 — switch: el código pasa a leer lo nuevo

Cuando el backfill terminó y ya no hay content nulos, la release 2 cambia la lectura a content y sigue escribiendo en ambas columnas. Verificación previa en el pipeline:

scripts/check_backfill.sh
# Antes de permitir el switch, comprobar que no quedan filas sin migrar.
PENDIENTES=$(psql "$DATABASE_URL" -tAc \
  "SELECT count(*) FROM messages WHERE content IS NULL")

if [ "$PENDIENTES" -ne 0 ]; then
  echo "Backfill incompleto: $PENDIENTES filas pendientes" >&2
  exit 1
fi
echo "Backfill completo: se puede hacer switch a content"

Release 3 — contract: ya nadie usa la columna vieja

migrations/0012_contract_drop_body.sql
-- CONTRACT: la ejecutamos solo cuando ninguna version en vuelo usa "body".
ALTER TABLE messages DROP COLUMN body;

Y el job que aplica las migraciones, separado del despliegue de la app:

.github/workflows/cd.yml
jobs:
  migrate:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v7
      - name: Aplicar migraciones pendientes
        run: alembic upgrade head
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}

  deploy:
    needs: migrate            # el codigo se despliega DESPUES del esquema
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v7
      - run: ./scripts/deploy.sh --image "$IMAGE" --env production
      env:
        IMAGE: ghcr.io/academy/copiloto-api:${{ github.ref_name }}

Decisiones y porqués:

  • Un job migrate aparte: se ejecuta una sola vez, antes del despliegue. Nada de migrar al arrancar cada réplica.
  • needs: migrate: impone el orden esquema → código. Si la migración falla, no se despliega la app: mejor quedarse en la versión anterior que romperse.
  • Backfill por lotes (LIMIT 10000): evita un UPDATE gigantesco que bloquearía la tabla. En producción se repite por lotes hasta vaciar NULL.
  • Dual-write entre releases: mientras conviven v1 y v2, ambas columnas se mantienen coherentes; ninguna versión lee datos que la otra no escribió.
  • El DROP va al final y aparte: es el único paso destructivo y llega cuando ya no queda código que dependa de body.

Si este flujo se te antoja lento, piensa qué gana: cero downtime, cero pérdida de datos y la capacidad de revertir las fases intermedias. La lentitud es por release, no por cambio: cada release avanza un paso pequeño.

6 · Errores habituales

Renombrar o borrar en el mismo release

Mal — cambio destructivo de golpe 
-- ❌ Rompe al instante la version vieja que aun se esta apagando.
ALTER TABLE messages RENAME COLUMN body TO content;
Bien — expand primero, contract al final 
-- ✅ Release 1: anadir la nueva y backfill (la vieja sigue viva).
ALTER TABLE messages ADD COLUMN content TEXT;
-- Release 3 (semanas despues): ya nadie usa "body".
ALTER TABLE messages DROP COLUMN body;

Migrar al arrancar cada réplica

Mal — migración en el startup 
# ❌ Cada una de las N replicas aplica migraciones al arrancar: se pisan.
uvicorn app.main:app --host 0.0.0.0 --port 8000
# (y dentro del arranque de la app: alembic upgrade head)
Bien — un job de migración, una sola vez 
# ✅ Las migraciones corren una vez, antes de desplegar la app.
jobs:
  migrate:
    steps:
      - run: alembic upgrade head
  deploy:
    needs: migrate

Columna NOT NULL sin backfill previo

Mal — exigir datos que aún no existen 
-- ❌ Falla si hay filas existentes sin valor, o reescribe toda la tabla.
ALTER TABLE messages ADD COLUMN content TEXT NOT NULL;
Bien — nullable, backfill y luego la restricción 
-- ✅ 1) anadir nullable, 2) backfill, 3) en un release posterior, la restriccion.
ALTER TABLE messages ADD COLUMN content TEXT;          -- 1
UPDATE messages SET content = body WHERE content IS NULL;  -- 2 (por lotes)
ALTER TABLE messages ALTER COLUMN content SET NOT NULL;    -- 3 (cuando ya no hay nulos)

Un backfill gigantesco de una sola pasada

Mal — bloquear la tabla 
-- ❌ Un solo UPDATE de millones de filas: locks largos y riesgo de timeout.
UPDATE messages SET content = body;
Bien — por lotes, en bucle 
-- ✅ Lotes pequenos: se puede ejecutar en bucle sin bloquear el servicio.
UPDATE messages
   SET content = body
 WHERE content IS NULL
   AND id IN (SELECT id FROM messages WHERE content IS NULL ORDER BY id LIMIT 10000);

7 · Ejercicio guiado

Objetivo: planificar y ejecutar una migración aditiva para el Copiloto (añadir conversations.summary), entender el rollout por lotes y verificar que la app vieja sigue funcionando con la columna nueva presente.

  1. Paso 1: crea la migración con Alembic (la herramienta de migraciones de SQLAlchemy, que ya usa la Copiloto API): 
    alembic revision -m "add conversations.summary"

    Resultado esperado: aparece un archivo nuevo en migrations/versions/. Ábrelo y rellena upgrade() y downgrade().

  2. Paso 2: implementa la fase expand en Python (Alembic) equivalente al SQL del ejemplo: 
    # En el archivo generado:
# op.add_column("conversations", sa.Column("summary", sa.Text(), nullable=True))
# op.create_index("idx_conversations_summary", "conversations", ["summary"])

    Observa: nullable=True es la clave de la compatibilidad. La app vieja ignora la columna; la nueva la usa.

  3. Paso 3: aplica y comprueba contra staging: 
    alembic upgrade head
psql "$DATABASE_URL" -c "\d conversations"

    Resultado esperado: la tabla muestra summary y el índice. La app desplegada sigue funcionando (no la has tocado).

  4. Paso 4: escribe el backfill por lotes como script y ejecútalo en bucle hasta que no queden nulos: 
    -- Repite hasta que el numero de pendientes sea 0.
UPDATE conversations
   SET summary = left(first_message, 200)
 WHERE summary IS NULL
   AND id IN (SELECT id FROM conversations WHERE summary IS NULL ORDER BY id LIMIT 5000);

    Resultado esperado: tras varias iteraciones, SELECT count(*) FROM conversations WHERE summary IS NULL devuelve 0. Mide cuánto tarda cada lote: así dimensionas el LIMIT para producción.

  5. Paso 5 (verificación de reversibilidad): en staging, retrocede un paso con alembic downgrade -1 y comprueba que la columna desaparece y la app sigue arrancando. Confirma en el historial (alembic history) que down deshace exactamente lo que hizo up. En cambios con datos, anota por qué el down podría no ser seguro.

8 · Reto

🎯 Migración con backfill reanudable y verificación en el pipeline

Implementa un job de migración que sea reanudable: si el backfill se interrumpe a medias (timeout, cancelación), al relanzarlo continúa donde lo dejó sin repetir trabajo, y solo pasa a la fase de switch cuando verifica que no quedan filas pendientes. Añade al pipeline una comprobación que bloquee el despliegue si la migración dejó filas sin backfillear, y un mecanismo para estimar el progreso (cuántas van, cuántas faltan).

Pista: usa un identificador incremental (por id) y guarda en una tabla o en una variable el último id procesado; cada lote avanza el puntero. La verificación del pipeline puede ser un script (scripts/check_backfill.sh) que cuente los nulos y salga con error si hay alguno. Para el progreso, ejecuta un SELECT count(*) de pendientes frente al total cada cierto número de lotes. Reflexiona: ¿por qué un backfill reanudable es más seguro que uno «todo o nada» en un sistema que no debe parar?

9 · Resumen

  • La base de datos es estado; durante un despliegue sin downtime coexisten dos versiones del código, así que el esquema debe ser compatible con ambas.
  • Expand/contract: expandir (añadir), migrar datos (backfill), cambiar el código, y solo al final contraer (eliminar).
  • El orden es esquema → código: la migración aditiva primero, la versión que la usa después.
  • Las migraciones son un job propio, una sola vez, nunca al arrancar cada réplica.
  • Prefiere cambios reversibles; para los que no lo son, planifica forward-fix. El DROP siempre al final y aparte.
  • Backfill por lotes e índices CONCURRENTLY para no bloquear tablas grandes.

10 · Preguntas frecuentes

¿Por qué no puedo simplemente migrar al desplegar?

Porque «al desplegar» implica varias réplicas arrancando a la vez. Si cada una intenta aplicar la misma migración, compiten por la tabla de control, se pisan y pueden dejar el esquema a medias. Además, si la migración falla, ya has desplegado una app que espera un esquema que no existe. El job separado permite fallar antes de tocar el código.

¿Todas las migraciones deben ser reversibles?

No siempre es posible: borrar datos o transformarlos sin vuelta atrás no se deshace. Lo importante es saber cuáles no lo son y asegurarse de que llegan al final del patrón (el contract), cuando ya no hay código dependiendo de ellas. Para el resto, prefiere forward-fix: una migración nueva que corrija, en lugar de un down arriesgado.

¿Cuánto tiempo debe pasar entre expand y contract?

Todo el que tarde el código viejo en desaparecer por completo: normalmente una o dos releases. La señal de que puedes contraer es que ninguna versión en vuelo use la columna o tabla antigua. Si dudas, espera otra release: el coste de mantener una columna de más es mínimo; el de borrarla antes de tiempo puede ser un incidente.

¿Qué hago si una migración tarda mucho en una tabla enorme?

Divide en dos: primero el cambio de esquema que es rápido (añadir columna nullable), después el backfill por lotes que puedes pausar y reanudar. Para índices, usa CONCURRENTLY (PostgreSQL) o el equivalente de tu motor. Y prueba siempre contra una copia realista: en staging con datos de verdad descubrirás los bloqueos antes que en producción.

¿Qué pasa con el rollback de la aplicación si ya migré?

Gracias a expand/contract, la versión anterior sigue funcionando con el esquema nuevo (la columna añadida es opcional para ella). Así puedes revertir el código sin revertir el esquema. Solo las fases destructivas (contract) rompen esa garantía, y por eso van al final, cuando revertir el código ya no es una opción esperada.
