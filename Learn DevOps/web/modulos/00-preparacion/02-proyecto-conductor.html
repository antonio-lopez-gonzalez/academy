Publicar el Copiloto

Módulo 0 · Preparación 🕐 30 minutos

1 · Introducción

Aprender CI/CD con fragmentos sueltos de YAML es como aprender a cocinar memorizando ingredientes: sabes qué es la sal, pero no por qué plato la estás usando. Para evitarlo, todo este curso tiene un único hilo conductor: Publicar el Copiloto. El protagonista es la Copiloto API, el servicio del curso Learn FastAPI: un asistente con RAG que responde preguntas sobre los módulos de la Academy. Hoy no construiremos el pipeline; lo diseñaremos de punta a punta para saber a dónde vamos.

La meta es concreta: que un desarrollador haga git push y, sin tocar nada más, su cambio pase por verificación automática, se convierta en una imagen Docker inmutable y llegue a producción de forma segura y reversible. Cuando el curso termine, ese pipeline será real, ejecutable y lo habrás escrito tú.

¿Por qué un proyecto conductor? Porque las decisiones de un pipeline real —qué probar, cuándo construir, cómo nombrar el artefacto, quién aprueba— solo tienen sentido sobre algo concreto. La Copiloto API nos da una aplicación real, con endpoints, tests y dependencias, sobre la que cada módulo tomará una decisión defendible.

Requisito suave: si has hecho Learn FastAPI reconocerás la API; si no, basta con saber que es un servicio web con tests. No volveremos a construir la aplicación: la trataremos como un repositorio que ya existe y al que vamos a añadir el ciclo de entrega.

2 · Teoría

Qué es la Copiloto API

La Copiloto API es un servicio HTTP escrito en Python con FastAPI. Expone endpoints como el clásico /health y el endpoint de consulta /ask; por debajo usa un modelo de lenguaje y recuperación de contexto (RAG) para responder con citas de los módulos del curso. Para nosotros, lo relevante no es su lógica interna, sino que es una aplicación de verdad: tiene dependencias, tests, un Dockerfile y una configuración por entorno.

CapaQué aportaQué le exigirá el pipeline
CódigoFastAPI + Pydantic, tests con pytestLint, tipos y tests verdes antes del merge
EmpaquetadoDockerfile multi-stageUna imagen inmutable, etiquetada por commit

EjecuciónContenedor en un orquestadorDespliegue progresivo, health checks y rollback

Del commit al despliegue: las tres fases del pipeline

El pipeline que construiremos tiene tres fases bien separadas, y esa separación es intencionada: cada fase existe para que la siguiente no tenga que confiar en nada que no haya sido verificado.

  FASE 1 · CI  (cada push y cada pull request)
  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │  lint    │   │ tipos    │   │  tests   │──▶ verde = código integrable
  │  ruff    │   │ mypy     │   │ pytest   │
  └──────────┘   └──────────┘   └──────────┘

  FASE 2 · BUILD  (al fusionar en main)
  ┌───────────────────────┐   ┌──────────────────┐
  │  docker build         │──▶│ imagen + tag      │──▶ artefacto inmutable
  │  multi-stage · Buildx │   │ sha del commit    │    (+ SBOM)
  └───────────────────────┘   └──────────────────┘

  FASE 3 · CD  (sobre ese artefacto)
  ┌──────────────────┐   ┌────────────────────┐   ┌──────────────────┐
  │  deploy staging  │──▶│ aprobación (gate)   │──▶│ deploy prod      │
  │  automático      │   │ puerta protegida    │   │ blue/green/canary│
  └──────────────────┘   └────────────────────┘   └──────────────────┘

¿Por qué separar CI, build y CD en fases? Porque tienen disparadores y garantías distintos. La CI corre en cada intento y debe ser rápida; el build solo tiene sentido si la CI ya pasó, y produce un objeto que se guarda; el CD promueve ese mismo objeto. Mezclarlas en un solo job gigante hace imposible saber si algo falló por el código o por el despliegue —y es una pesadilla de caché y de tiempo.

La regla de oro: construir una vez, promover muchas

Esta es la idea que vertebra el curso entero y conviene decírsela a quien venga de despliegues manuales: el artefacto que se prueba es exactamente el que se despliega. La imagen no se recompila al llegar a producción; se promueve la misma que ya se probó en staging.

Analogía: un fármaco no se vuelve a fabricar en cada farmacia. Se produce en un lote único, con un número de lote, se ensaya ese lote y se distribuye ese mismo lote a todas partes. Si cada hospital lo fabricara por su cuenta, la garantía del ensayo no valdría para nada. Un artefacto inmutable es tu número de lote: misma imagen, misma promesa.

Etiquetas mutables = garantía rota. Si la imagen se llama siempre :latest, no puedes decir con certeza qué código corre en producción, ni volver a la versión de ayer. Por eso etiquetaremos por el SHA del commit (inmutable), no por una etiqueta que cambia (Módulo 3).

3 · Ejemplo mínimo

No vamos a construir el pipeline completo hoy, pero sí a reservar el sitio: el esqueleto del repositorio de proyecto que iremos llenando. Este árbol de carpetas es el curso en miniatura.

proyectos/pipeline/
proyectos/pipeline/
├── .github/
│   └── workflows/
│       ├── ci.yml          # Fase 1: lint + tests (Módulo 2)
│       ├── publish.yml     # Fase 2: build + push a GHCR (Módulo 3)
│       └── deploy.yml      # Fase 3: staging → prod (Módulo 4)
├── app/                    # el código de la Copiloto API
├── tests/                  # pruebas con pytest
├── Dockerfile              # empaquetado multi-stage
├── pyproject.toml          # dependencias y herramientas
└── README.md               # cómo se ejecuta y cómo se despliega

Y el primer workflow, deliberadamente humilde: solo comprueba que el entorno del proyecto responde. Los detalles de sintaxis llegan en la lección 4; aquí nos interesa ver dónde vive.

.github/workflows/ci.yml
name: ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  copiloto-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Show toolchain
        run: |
          python --version
          echo "Copiloto API: arrancando el pipeline"

Este archivo ya contiene la anatomía que estudiaremos a fondo: un nombre, uno o varios disparadores (on), uno o varios trabajos (jobs) y, dentro, pasos (steps) que pueden ser acciones (uses) o comandos (run).

Empezar por un workflow que solo imprime el entorno no es perder el tiempo: confirma que la fontanería funciona (permisos, disparador, runner) antes de añadirle pasos que puedan fallar por mil motivos distintos. Primero el camino, luego la carga.

4 · Ejemplo real

Así se verá, de un vistazo, el pipeline del Copiloto cuando esté terminado. No hace falta entender cada línea todavía; fíjate en cómo los tres workflows se encadenan por responsabilidad, no por capricho.

.github/workflows/ci.yml (borrador del objetivo final)
name: ci
on:
  pull_request:              # corre en cada PR antes de mezclar
  push:
    branches: [main]

permissions:
  contents: read             # mínimo privilegio: solo leer el código

jobs:
  lint-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - run: pip install -e ".[dev]"
      - run: ruff check .
      - run: pytest --cov=app --cov-fail-under=85
.github/workflows/publish.yml (fase build)
name: publish
on:
  push:
    branches: [main]         # solo cuando el código ya está integrado

jobs:
  image:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write        # publicar la imagen en GHCR
    steps:
      - uses: actions/checkout@v7
      - name: Build and push
        run: |
          # En el Módulo 3 lo haremos con Buildx y caché.
          docker build -t ghcr.io/acme/copiloto-api:${{ github.sha }} .
          # ...login y docker push (con permisos, nunca con contraseñas a mano)
.github/workflows/deploy.yml (fase CD)
name: deploy
on:
  workflow_run:              # se dispara cuando "publish" termina bien
    workflows: [publish]
    types: [completed]

jobs:
  staging:
    runs-on: ubuntu-latest
    environment: staging      # despliegue automático
    steps:
      - run: echo "Desplegando la MISMA imagen a staging"

  production:
    needs: staging
    runs-on: ubuntu-latest
    environment: production   # protegido: requiere aprobación humana
    steps:
      - run: echo "Promoviendo la misma imagen a producción"

Las decisiones clave de este diseño, y su porqué:

  • La CI corre en cada PR; el build solo en main. No tiene sentido construir una imagen de una rama que quizá nunca se mezcle.
  • El artefacto se etiqueta con github.sha: cada commit produce una imagen distinta y perfectamente trazable. :latest cambiaría bajo los pies de producción.
  • El despliegue usa environment: son entornos de GitHub con reglas (secretos propios, revisores obligatorios, ramas permitidas). Así staging es automático y production espera aprobación sin que el YAML haga malabares.
  • La misma imagen viaja de staging a producción: se promueve el artefacto, no se recompila. Aquí se cumple la regla de oro.

Este YAML es un objetivo, no el estado inicial. Los módulos 2, 3 y 4 lo irán reescribiendo con detalle (matrices, caché, SBOM, OIDC, gates). Tenerlo delante ahora te da un mapa: cuando cada pieza llegue, sabrás en qué caja encaja.

5 · Buenas prácticas

PrácticaPor qué
Un workflow por responsabilidad: CI, build, deploy Cada uno con su disparador y sus permisos; más fácil de leer, reutilizar y depurar
Etiquetar el artefacto con el SHA del commit Trazabilidad total: sabes qué código corre y puedes volver a una versión exacta
Aplicar mínimo privilegio con permissions El token por defecto no debería poder publicar paquetes si el job no los publica
Usar entornos de GitHub para staging y producción Secretos separados, aprobaciones y auditoría sin duplicar workflows
Mantener el proyecto ejecutable en local antes de meterlo en CI Si pytest no corre en tu portátil, depurarlo en el runner es doloroso
Documentar en el README cómo se ejecuta y se despliega El pipeline es código, pero el «cómo» también es parte del producto

6 · Errores habituales

1. Construir la imagen por separado en cada entorno

Mal — recompilar al desplegar 
deploy-production:
  steps:
    - run: docker build -t copiloto-api .   # ¡otra imagen distinta!
    - run: docker push ...
Bien — promover el mismo artefacto 
deploy-production:
  steps:
    # Se reutiliza la imagen ya construida y probada, identificada por su SHA.
    - run: echo "desplegando ghcr.io/acme/copiloto-api:${{ github.sha }}"

2. Confundir «el repositorio» con «el artefacto»

Mal — desplegar el código fuente 
# Clonar el repo en el servidor y "arrancarlo allí"
git clone git@github.com:acme/copiloto-api.git && cd copiloto-api
pip install -r requirements.txt   # otra build, otro resultado
Bien — desplegar una imagen inmutable 
# El servidor solo sabe de imágenes; nunca ve el código fuente.
docker pull ghcr.io/acme/copiloto-api:<sha>
docker run ghcr.io/acme/copiloto-api:<sha>

3. Publicar con :latest como única etiqueta

Mal — etiqueta mutable 
- run: docker push ghcr.io/acme/copiloto-api:latest
# ¿Qué código hay detrás de "latest" hoy? ¿Y ayer?
Bien — etiqueta inmutable + un alias cómodo 
- run: docker push ghcr.io/acme/copiloto-api:${{ github.sha }}
# "latest" puede existir como conveniencia, pero NUNCA como identidad.

4. Meter secretos en el workflow «para que funcione»

Mal — secreto en texto plano 
env:
  REGISTRY_PASSWORD: "s3cr3t0-super-secreto"   # queda en el historial de Git
Bien — secretos fuera del repo 
env:
  REGISTRY_PASSWORD: ${{ secrets.REGISTRY_PASSWORD }}   # definido en GitHub, no en Git

7 · Ejercicio guiado

Objetivo: preparar el repositorio conductor —proyectos/pipeline/— con su estructura y un primer workflow que arranque en GitHub. Todavía no construiremos nada pesado: queremos el esqueleto caminando.

  1. Paso 1 — siéntate en el proyecto. Dentro de la carpeta del curso, crea la estructura del proyecto conductor: 
    mkdir -p "Learn DevOps/proyectos/pipeline"
cd "Learn DevOps/proyectos/pipeline"
mkdir -p .github/workflows app tests
git init

    Resultado esperado: un repositorio Git nuevo con las carpetas .github/workflows, app y tests.

  2. Paso 2 — un código mínimo creíble. Creamos una función pequeña con su test, para que la CI tenga algo que verificar. Es un placeholder honesto que más adelante ampliaremos con la Copiloto API real. 
    # app/health.py
def status() -> dict[str, str]:
    return {"status": "ok", "service": "copiloto-api"}

    # tests/test_health.py
from app.health import status


def test_status_ok():
    assert status()["status"] == "ok"
  3. Paso 3 — una configuración mínima de proyecto. Un pyproject.toml que declare el paquete y las herramientas de prueba: 
    # pyproject.toml
[project]
name = "copiloto-api"
version = "0.1.0"
requires-python = ">=3.12"

[tool.pytest.ini_options]
pythonpath = ["."]

    Resultado esperado: python -m pytest encuentra y pasa tests/test_health.py en tu máquina. Si no pasa en local, no lo subas todavía: depurar en local es mucho más rápido que en el runner.

  4. Paso 4 — el primer workflow. Crea el archivo de CI con el ejemplo mínimo del apartado 3: 
    # ya estás dentro de proyectos/pipeline
    .github/workflows/ci.yml
    name: ci
on:
  push:
    branches: [main]
  pull_request:
jobs:
  copiloto-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - run: pip install pytest
      - run: pytest -q
  5. Paso 5 — publícalo y mira la primera ejecución. Con la CLI de GitHub (instalación en la lección 3): 
    git add .
git commit -m "chore: esqueleto del pipeline del Copiloto"
gh repo create copiloto-pipeline --public --source=. --push
gh run watch

    Resultado esperado: la pestaña Actions muestra un job copiloto-check en verde, con el log de pytest diciendo que 1 passed. Acabas de colocar la primera piedra del hilo conductor.

  6. Paso 6 — verificación de coherencia. Comprueba que el repositorio refleja el mapa que dibujamos: los tres workflows aún no existen (solo ci.yml), y está bien. Anota en un papel qué módulo escribirá cada uno de los otros dos (publish.yml → Módulo 3; deploy.yml → Módulo 4). Este gesto, «saber qué falta», es la diferencia entre seguir un tutorial y saber dónde estás.

8 · Reto

🎯 Diseña el pipeline antes de escribirlo

Toma el repositorio del ejercicio y escribe, sin implementarlo todavía, el diseño completo del pipeline del Copiloto en un archivo docs/pipeline.md: las tres fases, qué dispara cada una, qué artefacto produce, qué entornos existen y dónde está la aprobación humana. Después responde por escrito a tres preguntas incómodas: ¿qué pasa si el build falla después de que la CI pasó?, ¿qué pasa si producción se rompe tras el despliegue?, ¿cómo sabes, dentro de un mes, qué versión exacta está corriendo?

Pista: las respuestas correctas mencionan «el artefacto no se produjo» (nada que promover), «rollback a la imagen anterior» (por eso la etiqueta es inmutable) y «el tag es el SHA del commit» (trazabilidad). No busques todavía la sintaxis: dibuja primero el mapa. Volverás a este documento en el Módulo 7 para comprobar cuánto acertaste.

9 · Resumen

  • El hilo conductor es Publicar el Copiloto: llevar la Copiloto API (FastAPI, del curso Learn FastAPI) del commit a producción con un pipeline completo.
  • El pipeline tiene tres fases: CI (lint, tipos, tests), build (imagen Docker inmutable) y CD (staging automático, producción con aprobación).
  • La regla de oro: construir una vez, promover muchas. El artefacto que se prueba es exactamente el que se despliega.
  • El artefacto se etiqueta por el SHA del commit; :latest es una conveniencia, nunca una identidad.
  • Los entornos de GitHub aportan secretos separados, aprobaciones y auditoría sin duplicar workflows.
  • Cada módulo añade una pieza a este mapa; el proyectos/pipeline/ es donde todas se juntan y se ejecutan de verdad.

10 · Preguntas frecuentes

¿Tengo que tener hecha la Copiloto API de Learn FastAPI para seguir el curso?

No es obligatorio. El curso trata el proyecto como un repositorio que ya existe; si no lo tienes, el ejercicio de hoy te deja un esqueleto mínimo (una función y su test) que iremos ampliando con piezas reales a lo largo de los módulos. Lo importante es que haya algo que construir, probar y contenerizar de verdad.

¿Por qué una imagen Docker y no desplegar el código directamente?

Porque la imagen es un artefacto inmutable: incluye el código, sus dependencias exactas y el runtime, en un objeto con un identificador único. Desplegar código fuente obliga a reinstalar dependencias en cada entorno, y eso vuelve a introducir el «en mi máquina funciona». La imagen elimina la variable «entorno» de la ecuación.

¿Qué diferencia hay entre un artefacto de GitHub Actions y la imagen de GHCR?

Ambos son «cosas que produce un workflow», pero con fines distintos. Los artifacts de Actions (por ejemplo, un informe de cobertura) se guardan junto a una ejecución concreta y sirven para inspección; la imagen de un registry como GHCR es un artefacto desplegable y versionado que puede vivir y promoverse durante meses. El pipeline usa los primeros para mirar y el segundo para desplegar.

¿Este curso sirve si mi empresa usa GitLab o Azure DevOps?

Sí. La plataforma de referencia es GitHub Actions —la más usada y la que mejor ilustra los conceptos—, pero todo lo aprendido (fases, artefactos inmutables, entornos, gates, estrategias de despliegue) es transferible, y compararemos con GitLab CI y Azure DevOps allí donde difieran. El hilo conductor es el mismo en cualquier plataforma.

¿Cuándo veremos código real y no solo el mapa?

El mapa de hoy es deliberado: sin él, cada workflow posterior parecería arbitrario. En el Módulo 2 escribiremos la CI de verdad, en el 3 el build con Buildx y SBOM, en el 4 los entornos y secretos, y en el 7 lo uniremos todo. La preparación es corta; la parte práctica es la mayor parte del curso.
