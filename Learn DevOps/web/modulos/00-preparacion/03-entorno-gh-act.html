Entorno: gh, act y Docker

Módulo 0 · Preparación 🕐 35 minutos

1 · Introducción

Antes de escribir pipelines conviene tener las herramientas bien afiladas. En este curso tocaremos el pipeline desde tres sitios: la terminal (donde creas ramas y subes código), GitHub (donde se ejecutan los workflows) y tu propia máquina (donde quieres probar un workflow antes de subirlo). Para cada uno hay una herramienta que conviene dominar desde el principio: Git, la CLI gh y act, todo ello apoyado en Docker.

La estrella de esta lección es act: un pequeño programa que lee tus workflows de GitHub Actions y los ejecuta en contenedores Docker locales. Con él dejas de esperar a un runner remoto para saber si tu YAML funciona. Vamos a instalar, autenticar y ejecutar el primer workflow de prueba.

¿Por qué probar en local si GitHub ya ejecuta los workflows? Porque el ciclo remoto es lento: commit → push → esperar → leer el log puede costar minutos por intento, y un pipeline se escribe con muchos intentos. act recorta ese bucle a segundos y, además, te obliga a tener Docker a mano —que usarás constantemente en los módulos 3 y 5.

Multiplataforma: GitHub Actions, gh y act funcionan en Linux, macOS y Windows. Los runners, en cambio, casi siempre son Linux, así que el shell canónico de los workflows es bash. Cuando te toque ejecutar algo en tu máquina, marcaremos los equivalentes de PowerShell.

2 · Teoría

Las cuatro piezas del taller

Cada herramienta cubre un tramo distinto del recorrido. Juntas forman el banco de trabajo del curso.

Analogía: si GitHub Actions fuera un horno industrial, gh es el mando que enciende el horno de la fábrica, act es un horno de sobremesa para practicar recetas en casa sin gastar un lote entero, y Docker es la bandeja donde cocinas. Git es el recetario versionado; y nadie enciende el horno sin haber probado la receta en casa.

gh: GitHub sin salir de la terminal

La CLI gh evita el vaivén constante al navegador. Los comandos que más usarás:

ComandoQué hace
gh auth loginAutentica la CLI contra tu cuenta (por token o por navegador)
gh repo createCrea un repositorio en GitHub, público o privado
gh run listLista las ejecuciones de workflows recientes
gh run watchSigue una ejecución en vivo, paso a paso
gh run view --logMuestra el log completo de una ejecución
gh secret setDefine un secreto del repositorio (nunca en el código)
gh pr create / gh pr checksCrea una PR y consulta sus comprobaciones obligatorias

Dos atajos que ahorran muchísimo tiempo: gh run watch para no recargar el navegador, y gh run view --log-failed para ver solo los pasos que fallaron. El log completo de un pipeline suele ser enorme; esto te lleva directo al error.

act: el runner que vive en tu portátil

Cuando subes un workflow, GitHub lo ejecuta en una máquina virtual «limpia». act imita ese comportamiento: lee el mismo YAML de .github/workflows/, levanta un contenedor Docker que simula el runner y ejecuta los pasos dentro. La consecuencia práctica es que solo puedes usar act si tienes Docker corriendo.

   ┌──────────────────────────────┐        ┌──────────────────────────────┐
   │        GitHub (remoto)        │        │        Tu máquina (act)      │
   │  runner ubuntu-latest (VM)    │        │  contenedor Docker (runner)  │
   │  ┌────────────────────────┐   │        │  ┌────────────────────────┐  │
   │  │ .github/workflows/*.yml │◀──┼──push──┼──│ mismos archivos YAML   │  │
   │  └────────────────────────┘   │        │  └────────────────────────┘  │
   └──────────────────────────────┘        └──────────────────────────────┘
         fiel al entorno real                    rápido, sin subir nada

act no es una réplica perfecta. La imagen por defecto no trae exactamente el mismo software que un runner hospedado de GitHub, ni reproduce los secretos ni los permisos reales. Sirve para validar la sintaxis y el flujo de tus pasos, no como sustituto de una ejecución real. Cuando algo pase en act pero falle en GitHub (o al revés), la causa suele ser una diferencia de imagen o de entorno.

Docker: el sustrato

Docker aparece dos veces en el curso: como motor de act (ejecuta los runners locales) y como empaquetador del artefacto (la imagen de la Copiloto API, Módulo 3). Aquí solo necesitas tenerlo instalado y corriendo; si vienes de Learn Docker, ya sabes lo esencial.

Comprueba que el daemon está vivo antes de usar act: docker info debe responder sin error. Docker Desktop (Windows/macOS) debe estar arrancado; en Linux, el servicio docker activo.

3 · Ejemplo mínimo

Lo más pequeño que demuestra que el taller está montado: preguntar a cada herramienta su versión. Si las cuatro responden, tienes el banco listo.

terminal
git --version       # p. ej. git version 2.45.0
gh --version        # p. ej. gh version 2.60.0
docker --version    # p. ej. Docker version 27.0.0
act --version       # p. ej. act version 0.2.70

Y comprobar que Docker responde de verdad (no basta con que el binario exista):

terminal
docker info | head -n 5    # si falla, el daemon no está corriendo

En PowerShell (Windows), los mismos comandos funcionan tal cual. La diferencia está en las tuberías y variables; aquí head no existe, así que usa docker info | Select-Object -First 5. En los workflows, en cambio, escribirás siempre bash.

4 · Ejemplo real

Un workflow de prueba honesto: valida el entorno del runner y ejecuta el test del proyecto conductor. Es el tipo de archivo que subirías para saber si tu YAML es válido antes de invertir tiempo en la CI de verdad.

.github/workflows/hello.yml
name: hello

on: [push, workflow_dispatch]   # en cada push y también a mano

jobs:
  probe:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Entorno del runner
        run: |
          echo "OS: ${{ runner.os }}"
          echo "Ref: ${{ github.ref }}"
          echo "SHA: ${{ github.sha }}"
          python --version || echo "python no disponible"
      - name: Un test rápido
        run: |
          echo "echo 'pipeline ok'" > probe.txt
          cat probe.txt

El flujo completo, de la terminal a tu máquina y a GitHub:

  1. Validar sin ejecutar: act -l lista los workflows y jobs que act detecta. Si un YAML tiene la sintaxis mal, aquí lo ves.
  2. Simular en seco: act -n push hace un dry-run: muestra qué ejecutaría sin arrancar contenedores. Perfecto para comprobar el disparador.
  3. Ejecutar de verdad: act push levanta el contenedor del runner y corre el job. La primera vez descarga una imagen grande; las siguientes son rápidas.
  4. Subir y confirmar: git push y gh run watch para ver la misma ejecución en el runner real de GitHub.

Nota el || echo "..." en el paso de Python: es defensivo a propósito. En act, la imagen por defecto puede no traer python; sin ese ||, el paso fallaría y creerías que tu workflow está mal cuando en realidad solo le falta una herramienta a la imagen. Escribir workflows tolerantes al entorno es una buena costumbre.

6 · Errores habituales

1. Ejecutar act sin Docker arrancado

Mal — el daemon está apagado 
act push
# Cannot connect to the Docker daemon. Is 'docker' running?
Bien — comprobar antes 
docker info > /dev/null && act push || echo "arranca Docker primero"

2. Confundir la imagen por defecto con un runner de GitHub

Mal — asumir que todo está instalado 
steps:
  - run: node --version      # la imagen por defecto puede no traer node
Bien — elegir una imagen con lo necesario 
# Usa una imagen que imite mejor el runner real
act push -P ubuntu-latest=catthehacker/ubuntu:act-latest

3. Pegar el token de GitHub en el comando

Mal — credencial en texto plano (y en tu historial) 
git push https://usuario:ghp_XXXXXXXX@github.com/acme/repo.git
# el token queda en el historial de la shell
Bien — autenticar una vez 
gh auth login          # guarda la credencial de forma segura
git push               # usa la credencial configurada

4. Depurar el log entero cuando falla un paso

Mal — buscar la aguja en el pajar 
gh run view 12345 --log | less   # miles de líneas
Bien — solo lo que falló 
gh run view --log-failed          # directamente el paso rojo

7 · Ejercicio guiado

Objetivo: instalar las cuatro herramientas, autenticar gh, crear el workflow de prueba y ejecutarlo dos veces: primero con act en local y después en GitHub.

  1. Paso 1 — instala las herramientas. Elige tu plataforma: 
    # macOS (Homebrew)
brew install gh nektos/act/act
# Linux (Debian/Ubuntu) — gh desde el repo oficial de GitHub CLI
sudo apt install gh          # o: brew install gh  (Linuxbrew)
brew install act             # act: vía brew, o con el script de instalación de nektos
# Windows (winget)
winget install --id GitHub.cli
winget install --id nektos.act

    Y, si no lo tienes: instala Docker Desktop (o Docker Engine en Linux) y ábrelo.

  2. Paso 2 — verifica y autentica. 
    git --version && gh --version && docker --version && act --version
gh auth login       # elige GitHub.com → HTTPS → autentícate con el navegador
gh auth status      # debe decir "Logged in to github.com"

    Resultado esperado: las cuatro versiones impresas y una sesión autenticada.

  3. Paso 3 — crea el workflow de prueba. En el repositorio del Módulo 0 (o en uno nuevo con gh repo create):
    .github/workflows/hello.yml
    name: hello
on: [push, workflow_dispatch]
jobs:
  probe:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: echo "Hola desde ${{ runner.os }} · ${{ github.sha }}"
  4. Paso 4 — valida y ejecuta en local con act. 
    act -l            # lista los jobs detectados (chequeo de sintaxis)
act -n push       # dry-run: qué haría sin ejecutar
act push          # ejecuta el job en un contenedor Docker local

    Resultado esperado: act -l muestra el job probe; toda ejecución de probe termina con Success y el eco con tu SHA. La primera vez tardará más: descarga la imagen del runner.

  5. Paso 5 — súbelo y confírmalo en GitHub. 
    git add .github/workflows/hello.yml
git commit -m "ci: workflow de prueba del entorno"
git push
gh run watch      # sigue la ejecución remota en vivo

    Resultado esperado: una ejecución verde en la pestaña Actions, con el mismo eco que viste en local. Has verificado el mismo YAML en dos motores distintos.

  6. Paso 6 — provoca un fallo a propósito y usa el log filtrado. Añade un paso - run: exit 1, sube el cambio y, cuando falle, ejecuta gh run view --log-failed. Verás únicamente el paso rojo. Después quita el paso y vuelve al verde.

8 · Reto

🎯 Un job que necesita un secreto, en local y en remoto

Añade a tu workflow un job que use un secreto (por ejemplo, imprimir una variable GREETING que no debe estar en el repositorio). Consigue que funcione de las dos formas: en GitHub, definiendo el secreto con gh secret set; en local, pasándolo a act para que el job lo reciba. Después responde: ¿por qué el secreto no aparece si intentas imprimirlo a pelo, y qué deberías hacer para usarlo sin exponerlo?

Pista: act acepta secretos con -s (o desde un archivo --secret-file), y las expresiones los leen como ${{ secrets.NOMBRE }}. Sobre la segunda pregunta: GitHub oculta los secretos en los logs, pero imprimirlos sigue siendo una mala idea; piensa en qué hace un pipeline con un token (usarlo, no mostrarlo). Guarda esta idea para el Módulo 4 (secretos y OIDC).

9 · Resumen

  • Cuatro herramientas forman el taller: Git (versiones), gh (GitHub desde la terminal), act (Actions en local) y Docker (motor y empaquetado).
  • gh auth login autentica la CLI una vez; gh run watch y gh run view --log-failed ahorran el vaivén al navegador.
  • act ejecuta los mismos workflows en un contenedor Docker local: act -l valida, act -n simula, act push ejecuta.
  • act no es un runner perfecto: la imagen por defecto tiene menos software; se elige una más completa con -P.
  • Docker debe estar arrancado; el 90% de los fallos de act son el daemon apagado.
  • Los secretos nunca van en el YAML: se definen con gh secret set (remoto) o se pasan a act con -s (local).

10 · Preguntas frecuentes

¿Necesito Docker solo para act, o también en los módulos siguientes?

Para las dos cosas. act usa Docker para simular el runner local, y en el Módulo 3 construirás la imagen de la Copiloto API con docker build. Además, en el Módulo 5 desplegarás con estrategias sobre contenedores. Tener Docker bien instalado no es opcional en este curso.

¿act puede reemplazar a ejecutar los tests en GitHub?

No del todo. act es excelente para iterar rápido y detectar errores de sintaxis y de flujo, pero no reproduce los permisos reales, los secretos gestionados ni la imagen exacta del runner hospedado. La regla sensata: act para el bucle de escritura, GitHub como verificación final. Nunca declares verde un workflow que solo pasó en local si vas a confiar en él para bloquear merges.

¿Por qué los workflows usan bash si estoy en Windows?

Porque los runners hospedados (y las imágenes de act) son Linux, y ahí el shell por defecto es bash. Mantener los pasos en bash hace que el workflow sea idéntico en tu máquina y en el servidor, y que las herramientas estén siempre disponibles. Solo cambias a PowerShell cuando ejecutas algo en tu terminal local, y eso no afecta al YAML.

¿La primera ejecución de act tarda muchísimo? ¿Es normal?

Sí. La primera vez descarga una imagen Docker de varios cientos de MB que simula el runner (o incluso de GB si eliges una imagen completa con -P). Las siguientes ejecuciones reutilizan esa imagen en caché y son rápidas. Es una inversión única a cambio de un bucle de prueba de segundos.

¿Puedo usar act sin conexión a internet?

Una vez descargada la imagen del runner, muchos pasos funcionan sin red. Pero en cuanto un paso hace actions/checkout o instala dependencias, necesita acceso. En el mundo real, la mayoría de workflows descargan código y paquetes, así que considera que act requiere conexión aunque la imagen ya esté cacheada.
