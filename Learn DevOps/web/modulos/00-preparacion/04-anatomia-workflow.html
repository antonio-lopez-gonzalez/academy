Anatomía de un workflow

Módulo 0 · Preparación 🕐 35 minutos

1 · Introducción

Un workflow de GitHub Actions no es más que un archivo YAML en una carpeta concreta que describe cuándo ejecutar algo, qué ejecutar y dónde. Toda la potencia y todas las trampas del sistema vienen de entender bien esas cuatro preguntas. Hoy desmontamos el archivo pieza a pieza: on, jobs, runs-on, steps, needs, y la diferencia entre una action (uses) y un comando (run).

Al terminar serás capaz de leer cualquier workflow de GitHub —propio o ajeno— y decir qué hace sin ejecutarlo. Esa habilidad, más que memorizar sintaxis, es la que te permitirá escribir la CI del Copiloto en el Módulo 2 con criterio propio.

¿Por qué estudiar la anatomía antes de escribir pipelines? Porque la mayoría de errores de un pipeline no son de lógica, son estructurales: un needs que apunta a un job que no existe, un runs-on puesto en el sitio equivocado, una indentación que convierte un paso en otro. Conocer el esqueleto es lo que evita ese 80% de fricción.

2 · Teoría

Dónde vive un workflow

No hay libertad de sitio: GitHub solo mira los archivos .yml (o .yaml) que estén exactamente en .github/workflows/, en la raíz del repositorio. Cada archivo es un workflow independiente; su name es el que aparece en la pestaña Actions.

estructura del repositorio
mi-repo/
├── .github/
│   └── workflows/          ← GitHub SOLO lee workflows de aquí
│       ├── ci.yml          ← un workflow (nombre visible: "ci")
│       ├── publish.yml     ← otro workflow
│       └── deploy.yml      ← otro más
├── app/
└── README.md

El nombre del archivo no importa para GitHub (vale a.yml), pero sí importa para las personas. Convención del curso: ci.yml, publish.yml, deploy.yml. Un nombre que dice lo que hace ahorra abrir el archivo.

on: el disparador (trigger)

on responde a «¿cuándo se ejecuta esto?». Es lo primero que hay que leer de un workflow, porque define su propósito. Los disparadores que más usarás:

DisparadorCuándo se activaUso típico
on: pushAl subir commits (a cualquier rama, o filtrado por branches/paths)CI al integrar en main; build de la imagen
on: pull_requestAl abrir o actualizar una PRVerificar el código antes de mezclarlo
on: workflow_dispatchManualmente, desde la interfaz o ghReintentos, tareas puntuales, despliegues manuales
on: scheduleSegún una expresión cronTareas periódicas (escaneos, limpieza)
on: workflow_runCuando otro workflow terminaEncadenar publish → deploy
on: releaseAl publicar una releasePublicar artefactos versionados (SemVer)

El disparador admite filtros que afinan aún más: por rama (branches), por etiqueta (tags) o por rutas de archivos (paths). Esto último es clave para no ejecutar la CI por un cambio en el README.

.github/workflows/ci.yml (extracto de disparadores)
on:
  push:
    branches: [main]          # solo la rama principal
    paths-ignore: ["docs/**", "**.md"]   # ignora cambios de documentación
  pull_request:
    branches: [main]
  workflow_dispatch:          # y también a mano, por si acaso

jobs: los trabajos y su grafo

Un workflow contiene uno o varios jobs. Dos reglas gobiernan el orden:

  • Por defecto, los jobs se ejecutan en paralelo, cada uno en su propia máquina limpia.
  • Con needs se establece una dependencia: un job no arranca hasta que los jobs que necesita han terminado bien. Así se forma un grafo acíclico (un DAG).
  jobs SIN needs (en paralelo)          jobs CON needs (encadenados)

       ┌─────────┐                            ┌─────────┐
       │  lint   │                            │  lint   │
       └─────────┘                            └────┬────┘
       ┌─────────┐                                 │ needs: lint
       │  test   │                            ┌────▼────┐
       └─────────┘                            │  test   │
       (arrancan a la vez)                    └────┬────┘
                                                   │ needs: test
                                              ┌────▼────┐
                                              │  build  │
                                              └─────────┘

¿Por qué encadenar con needs? Por dos motivos: corrección (no tiene sentido construir la imagen si los tests fallan) y coste (no gastas minutos de runner en trabajo inútil). El paralelismo ahorra tiempo; needs ahorra trabajo equivocado. Usa cada uno donde toca.

runs-on: dónde corre el job

Cada job declara en qué tipo de máquina se ejecuta, con runs-on. Las etiquetas más comunes:

runs-onSistemaNotas
ubuntu-latestLinuxEl estándar para CI/CD; más rápido y barato
windows-latestWindowsPara software específico de Windows
macos-latestmacOSBuilds de iOS/macOS; el más caro
[self-hosted]Tu propia máquinaCuando necesitas hardware o red concretos

runs-on es propiedad del job, no del paso. Ponerlo dentro de steps es uno de los errores más frecuentes (sección 6). Y ojo: cada job arranca en una máquina nueva; lo que instales en uno no existe en el siguiente.

steps: los pasos, actions y comandos

Dentro de un job, steps es la lista ordenada de lo que se ejecuta. Cada paso es una de dos cosas:

uses: — una actionrun: — un comando
Qué esUna pieza reutilizable publicada en el marketplace o en un repoUn comando de shell que tú escribes
Ejemplouses: actions/checkout@v4run: npm ci
ParámetrosCon with:Con el propio comando y variables
CuándoCuando existe una action que hace el trabajo (y está bien mantenida)Cuando es lógica tuya y no merece una action
.github/workflows/ci.yml (extracto de pasos)
    steps:
      # ACTION: reutilizable, versionada, con parámetros via "with"
      - name: Checkout
        uses: actions/checkout@v4
      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      # COMMAND: lógica propia, shell directo
      - name: Instalar dependencias
        run: pip install -e ".[dev]"
      - name: Lint y tests
        run: |
          ruff check .
          pytest -q

Regla de decisión: si existe una action oficial (actions/*) o muy usada que hace lo que quieres, úsala y fija su versión. Si es lógica de tu proyecto (lint, tests, scripts), escríbela con run. Y fija siempre la versión (@v4, no solo el nombre): una action sin versión puede cambiar bajo tus pies.

Contextos y expresiones: ${{ }}

Dentro del YAML puedes interpolar valores con la sintaxis ${{ ... }}. Los contextos más útiles:

ExpresiónQué contiene
${{ github.sha }}El SHA del commit que disparó la ejecución (identidad del artefacto)
${{ github.ref }}La referencia (rama o etiqueta), p. ej. refs/heads/main
${{ runner.os }}El sistema del runner (Linux, Windows, macOS)
${{ secrets.NOMBRE }}Un secreto definido en el repositorio (nunca en texto plano)
${{ steps.X.outputs.Y }}La salida de un paso anterior (con id)

No interpoles datos no confiables directamente en run. Mete el valor en una variable de entorno (env:) y usa "$VAR" dentro del script. Insertar texto del evento directamente en el shell abre la puerta a script injection; lo veremos en el Módulo 7.

El esqueleto completo, de un vistazo

.github/workflows/esqueleto.yml
name: nombre-del-workflow          # 1. aparece en la pestaña Actions

on: [push, pull_request]           # 2. CUÁNDO se ejecuta

permissions:                       # 3. con qué permisos mínimos
  contents: read

jobs:                              # 4. QUÉ trabajos hay
  lint:                            #    nombre del job
    runs-on: ubuntu-latest         # 5. DÓNDE corre
    steps:                         # 6. la lista de pasos
      - uses: actions/checkout@v4  #    acción reutilizable
      - run: echo "hello"          #    comando de shell

  test:
    needs: lint                    # 7. depende de "lint"
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "tests"

3 · Ejemplo mínimo

El workflow más pequeño que hace algo útil: tres jobs encadenados que se saludan. Sin actions externas ni dependencias — solo la estructura.

.github/workflows/minimo.yml
name: minimo
on: [push]

jobs:
  primero:
    runs-on: ubuntu-latest
    steps:
      - run: echo "paso 1: preparar"

  segundo:
    needs: primero          # no arranca hasta que "primero" acaba bien
    runs-on: ubuntu-latest
    steps:
      - run: echo "paso 2: construir"

  tercero:
    needs: segundo          # ...y este, hasta que acaba "segundo"
    runs-on: ubuntu-latest
    steps:
      - run: echo "paso 3: desplegar"

Qué observar:

  1. on: [push]: cada git push lanza una ejecución. La notación entre corchetes es la forma corta de una lista de disparadores.
  2. Tres jobs, tres máquinas: cada job arranca en su propio runner limpio. El echo de uno no ve el echo del otro.
  3. needs: crea la cadena primero → segundo → tercero. Si primero falla, los otros dos ni se ejecutan: quedan en gris, no en verde.
  4. Orden real: sin los needs, los tres jobs correrían a la vez y no sabrías en qué orden. El grafo lo dibujas tú.

Pruébalo con act push: verás los tres jobs ejecutarse en cadena. Si cambias un exit 1 en el primero, comprobarás cómo los siguientes se saltan en lugar de fallar: eso es la propagación de needs.

4 · Ejemplo real

Apliquemos la anatomía al proyecto conductor. Este es el workflow de CI del Copiloto con la forma que tendrá en el Módulo 2: un job rápido de lint y otro de tests en paralelo, y un build que solo corre si ambos han pasado.

.github/workflows/ci.yml
name: ci

on:
  pull_request:            # verifica antes del merge
  push:
    branches: [main]       # y también al integrar en main

permissions:
  contents: read           # mínimo privilegio: solo leer el código

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install ruff
      - run: ruff check .

  test:
    runs-on: ubuntu-latest   # corre EN PARALELO con "lint"
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -e ".[dev]"
      - run: pytest -q --cov=app

  build:
    needs: [lint, test]      # espera a que AMBOS terminen bien
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Empaquetar artefacto
        run: echo "aquí construiríamos la imagen en el Módulo 3"

Decisiones de diseño y su porqué:

  • lint y test en paralelo: no dependen entre sí y ambos son rápidos. Correrlos a la vez devuelve el feedback antes. Es la aplicación directa de fast feedback.
  • build con needs: [lint, test]: el artefacto solo se produce si el código está limpio y probado. El needs admite una lista, no solo un job.
  • permissions: contents: read: el token del workflow no tiene por qué escribir nada. Declarar el mínimo es una buena práctica de seguridad (Módulo 7).
  • pull_request + push: verifica tanto el trabajo en curso (PR) como el resultado ya integrado (main).

Fíjate en que cada job repite actions/checkout: es obligatorio, porque cada job es una máquina nueva. Esto choca a quien viene de un script lineal, pero es la garantía de aislamiento: lo que haces en un job no contamina a otro. La repetición se elimina con reusable workflows (Módulo 2).

5 · Buenas prácticas

HazEvitaPor qué
Un name: claro y un name: por paso importante Workflows y pasos anónimos El log y la UI se leen por nombres; sin ellos, depurar es a ciegas
Fijar la versión de cada uses: (@v4) Usar actions/checkout sin versión Una action sin versión puede cambiar y romper tu pipeline sin avisar
Declarar permissions mínimos Dejar los permisos por defecto (a veces de escritura) El token es una credencial; cuanto menos pueda, mejor

Usar variables de entorno para datos de contexto Insertar ${{ github.event.* }} crudo dentro de run Evita script injection y hace el script más legible

6 · Errores habituales

1. Poner runs-on dentro de steps

Mal — runs-on es del job 
jobs:
  test:
    steps:
      - runs-on: ubuntu-latest   # ✗ no existe aquí
      - run: pytest
Bien — al nivel del job 
jobs:
  test:
    runs-on: ubuntu-latest      # ✓ hermana de "steps"
    steps:
      - run: pytest

2. Un needs que apunta a un job inexistente o con otro nombre

Mal — nombre desalineado 
jobs:
  test:
    runs-on: ubuntu-latest
  build:
    needs: tests             # ✗ el job se llama "test", no "tests"
Bien — el nombre exacto de la clave 
jobs:
  test:
    runs-on: ubuntu-latest
  build:
    needs: test              # ✓ coincide con la clave del job

3. Usar uses para un comando de shell

Mal — mezcla de sintaxis 
steps:
  - uses: pip install -e ".[dev]"   # ✗ eso no es una action
Bien — run para comandos 
steps:
  - run: pip install -e ".[dev]"    # ✓ un comando de shell

4. Confiar en que el estado de un job pasa al siguiente

Mal — asumir continuidad entre jobs 
jobs:
  install:
    runs-on: ubuntu-latest
    steps: [{ run: pip install -e ".[dev]" }]
  test:
    needs: install
    runs-on: ubuntu-latest
    steps: [{ run: pytest }]   # ✗ las deps NO están: es otra máquina
Bien — instalar donde hace falta (o cachear) 
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -e ".[dev]"   # ✓ cada job se prepara
      - run: pytest

5. Indentación inconsistente en YAML

Mal — un paso se vuelve parámetro del anterior 
steps:
  - run: pip install pytest
    - run: pytest       # ✗ indentado de más: YAML lo une al paso anterior
Bien — cada guion al mismo nivel 
steps:
  - run: pip install pytest
  - run: pytest         # ✓ dos elementos de la lista

7 · Ejercicio guiado

Objetivo: escribir desde cero un workflow con tres jobs y dependencias reales, validarlo con act y comprobar con tus ojos cómo se propaga un fallo por el grafo de needs.

  1. Paso 1 — crea el archivo. En el repositorio del Módulo 0:
    .github/workflows/dag.yml
    name: dag
on: [push]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: echo "lint ok"

  test:
    runs-on: ubuntu-latest       # paralelo con lint
    steps:
      - run: echo "test ok"

  build:
    needs: [lint, test]          # espera a los dos
    runs-on: ubuntu-latest
    steps:
      - run: echo "build ok"

  deploy:
    needs: build                 # solo si el build pasó
    runs-on: ubuntu-latest
    steps:
      - run: echo "deploy ok"
  2. Paso 2 — valida la sintaxis. 
    act -l

    Resultado esperado: la lista muestra lint, test, build y deploy con sus dependencias. Si un job no aparece, revisa indentación y nombres.

  3. Paso 3 — ejecútalo y observa el orden. 
    act push

    Resultado esperado: lint y test se ejecutan a la vez (o en cualquier orden), y solo después aparecen build y, al final, deploy. Ese es el grafo needs en marcha.

  4. Paso 4 — rompe el lint y observa la propagación. 
      lint:
    runs-on: ubuntu-latest
    steps:
      - run: exit 1        # forzamos el fallo del lint

    act push

    Resultado esperado: lint falla; test sí corre (no depende de lint), pero build y deploy quedan saltados porque su needs no se ha cumplido. Comprobar esto en local es exactamente para lo que sirve act.

  5. Paso 5 — usa un contexto en un comando. Sustituye el job test por uno que imprima el SHA del commit: 
      test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "commit ${{ github.sha }} en ${{ github.ref }}"

    Resultado esperado: el eco muestra un SHA (real en GitHub; simulado en act) y la referencia. Has conectado el YAML con los datos de la ejecución.

  6. Paso 6 — súbelo y confírmalo. 
    git add .github/workflows/dag.yml
git commit -m "ci: workflow con grafo de jobs"
git push && gh run watch

    Resultado esperado: la vista gráfica de la ejecución en GitHub dibuja el mismo DAG que viste en act: dos jobs en paralelo y dos encadenados. Quita el exit 1 antes de dejarlo verde.

8 · Reto

🎯 Un workflow que solo se ejecute cuando importa

Afina el disparador del workflow del ejercicio para que no se ejecute cuando solo cambian archivos de documentación (*.md, docs/**), y que además permita lanzarse a mano desde la interfaz. Después añade un job que corra solo cuando estemos en la rama main, usando una condición if:. Comprueba en GitHub que un cambio que toca únicamente el README genera una ejecución «skipped» y no una CI completa.

Pista: paths-ignore vive bajo on.push; workflow_dispatch habilita el botón «Run workflow»; y una condición de job se escribe if: github.ref == 'refs/heads/main'. Ojo con la trampa clásica: si filtras demasiado y main deja de ejecutar la CI, el verde puede volverse falso. Anota qué rutas no puedes ignorar nunca.

9 · Resumen

  • Un workflow es un YAML en .github/workflows/; su name aparece en la pestaña Actions.
  • on decide cuándo se ejecuta (triggers: push, pull_request, workflow_dispatch, schedule, workflow_run…), con filtros como branches y paths.
  • jobs corren en paralelo por defecto; needs crea dependencias y forma un grafo.
  • runs-on es propiedad del job y elige la máquina (ubuntu-latest…).
  • steps combina actions (uses:, con with:) y comandos (run:).
  • Los contextos ${{ }} conectan el YAML con la ejecución (github.sha, runner.os, secrets.*).

10 · Preguntas frecuentes

¿Puedo tener varios workflows en el mismo repositorio?

Sí, y es lo recomendable. Cada archivo en .github/workflows/ es un workflow independiente con su propio disparador. En el proyecto conductor tendremos tres: ci.yml (lint y tests), publish.yml (build y subida de la imagen) y deploy.yml (despliegue). Separarlos por responsabilidad los hace más fáciles de leer, reutilizar y depurar que un único archivo gigante.

¿Cuándo uso uses y cuándo run?

Usa uses cuando existe una action que hace el trabajo y está bien mantenida (por ejemplo, hacer checkout o configurar una versión de Python): te ahorra reinventarla. Usa run para la lógica de tu proyecto (instalar dependencias, lanzar el linter, ejecutar los tests): es tu código, lo controlas tú. Regla práctica: reutiliza lo ajeno, escribe lo tuyo.

¿Por qué hay que repetir actions/checkout en cada job?

Porque cada job arranca en una máquina virtual nueva y limpia que no tiene tu código ni nada de lo que hiciste en otro job. Ese aislamiento es una ventaja (evita el «en mi máquina funciona» y la contaminación entre etapas), a cambio de repetir la preparación. La forma de evitar la repetición es extraer lo común a un reusable workflow, que veremos en el Módulo 2.

¿needs solo sirve para poner jobs en orden?

Su función principal es la dependencia y el orden, pero tiene un efecto secundario importante: si un job del que dependes falla, los siguientes se saltan en lugar de ejecutarse, lo que evita trabajo inútil (no construir si los tests no pasan) y propaga el fallo de forma visible. En workflows avanzados, needs también permite leer las salidas de otro job. Aquí nos quedamos con el orden y la propagación.

¿Qué son los contextos ${{ }} y puedo usarlos en cualquier sitio?

Son valores que GitHub rellena en el momento de la ejecución: el SHA, la rama, el sistema operativo, un secreto, la salida de un paso… Se pueden usar en la mayoría de las claves del workflow y dentro de los run. Dos advertencias: no todos los contextos están disponibles en todos los sitios (por ejemplo, secrets no vale en un if que decide si corre un workflow disparado por una PR de un fork), y nunca debes interpolar datos no confiables directamente en un run. Lo veremos a fondo en el Módulo 7.
