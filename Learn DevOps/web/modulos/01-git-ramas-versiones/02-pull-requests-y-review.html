Pull requests y revisión

Módulo 1 · Git, ramas y versiones 🕐 30 minutos

1 · Introducción

Si las ramas cortas son el «cómo» de la integración continua, el pull request (PR) es el «cuándo» y el «con permiso de quién». Un PR es la propuesta formal de meter los commits de una rama en otra; en GitLab se llama merge request, pero la idea es la misma: una conversación revisable alrededor de un cambio de código, con una puerta de calidad al final.

En esta lección verás cómo se convierte esa puerta en algo que no se puede saltar: la protección de rama con required status checks y revisiones obligatorias. Y al final, la decisión que más discusiones genera: ¿el merge se hace con squash, con un merge commit o con rebase?

¿Por qué importa esto? Porque un pipeline solo sirve si bloquea de verdad. Un CI que corre y avisa pero deja mergear en rojo es decoración. La protección de rama es lo que une «tenemos tests» con «los tests importan»: el merge se desbloquea cuando los checks están en verde y alguien ha revisado. Ahí es donde CI pasa de recomendación a contrato.

Errores típicos: exigir un check que nunca se ejecuta (y bloquear todos los PR para siempre), PRs de dos mil líneas que nadie revisa de verdad, aprobar sin leer, o mezclar formats de merge y acabar con un historial que parece una autopista de circunvalación.

2 · Teoría

Qué es un pull request (y qué no)

Git, por sí solo, no sabe nada de PRs: es una función de la plataforma (GitHub, GitLab, Bitbucket). Un PR no es un commit ni una rama; es un objeto de revisión que apunta a un par de ramas —base (destino, normalmente main) y head (tu rama)— y reúne:

  • el diff entre ambas, actualizado en vivo cada vez que subes commits;
  • una conversación: comentarios, hilos, sugerencias de cambio;
  • el estado de los checks: los workflows que corren sobre el PR y reportan éxito o fallo;
  • los aprobadores y, si toca, quién ha pedido cambios.

Analogía — la puerta del laboratorio: la rama es tu mesa de trabajo; el PR es la puerta con dos guardias. Uno mira el código (la revisión humana) y el otro mira los checks automáticos (tests, lint, build). Solo se abre cuando ambos dan el visto bueno. No es burocracia: es el punto donde el cambio se hace público y estable.

El CI en el PR: primero útil, después obligatorio

Un workflow con disparador pull_request prueba la integración de tu rama con la base, no tu rama aislada. Esa es su gracia: detecta el choque antes de que ocurra. Tienes dos caminos:

ModoQué pasaConsecuencia
CI informativoLos checks corren y se ven en el PR, pero el merge está permitido aunque fallenCómodo al principio; en la práctica se ignora el rojo
CI obligatorioLa protección de rama exige checks en verde y revisión antes de mergearEl tronco no puede romperse; es el objetivo real

Protección de rama: cómo CI deja de ser opcional

La protección de rama es un conjunto de reglas sobre una rama (típicamente main). Las piezas que nos importan:

Require a pull request before merging
Prohíbe el push directo: todo entra por PR.
Require status checks to pass
Los checks listados deben estar en verde. Los nombres deben coincidir exactamente con el nombre del job (o del check) reportado.
Require branches to be up to date
La rama head debe estar al día con la base antes de integrar: evita que dos PR verdes se rompan al juntarse (semantic conflict).
Require approvals
Al menos N revisores deben aprobar; opcionalmente se descartan aprobaciones al subir nuevos commits.
Require review from Code Owners
Si un archivo lo «posee» un equipo en CODEOWNERS, su aprobación es obligatoria (útil para .github/workflows/** o migraciones).
Restrict who can push / Dismiss stale reviews
Límites extra de quién puede tocar la rama y caducidad de aprobaciones viejas.
push a main ──▶ ✗ RECHAZADO (rama protegida) feat/health ──▶ PR hacia main │ ├─▶ checks (test, lint) ──✗──▶ merge bloqueado │ ✓ └─▶ review (1 approval) ──✗──▶ merge bloqueado ✓ └──▶ MERGE permitido

Merge queue: cuando varios PR verdes se juntan y uno rompe al otro, la solución moderna es una merge queue: la plataforma agrupa y prueba los PR antes de integrarlos a main. Es el siguiente escalón sobre «require branches to be up to date», y solo merece la pena cuando el tronco recibe muchos merges por minuto.

Squash vs merge commit vs rebase

Cuando un PR se integra, hay tres formas de materializarlo en el historial. No es un detalle estético: define cómo se lee main y con qué herramientas trabajas después (por ejemplo, un changelog derivado de commits).

Rama: A ── B ── C (tres commits "wip", "arreglo", "arreglo del arreglo") │ main ─────────M SQUASH A ── C' (un solo commit en main, con el diff de B..C) MERGE COMMIT A ── M (M tiene DOS padres: A y C; conserva la forma) REBASE A ── B' ── C' (tus commits reaplicados encima de main, lineales)
MétodoHistorial resultanteCuándo elegirlo
Squash Un commit por PR, lineal Por defecto en trunk-based: un PR = una idea = un commit en main. Ideal para changelog y para git bisect.
Merge commit Un commit de fusión con dos padres Cuando quieres preservar los commits individuales y marcar dónde entró cada PR.
Rebase merge Tus commits reaplicados, lineal, sin commit extra Cuando cada commit del PR ya es limpio y quieres historia lineal conservándolos.

La regla más simple: squash por defecto. La mayoría de PRs contienen commits de trabajo («wip», «arreglo lint») que nadie quiere en el historial de main. Con squash, lo que se revisa (el conjunto) y lo que se guarda (un commit claro) coinciden. Si un PR es un trabajo fino de varios pasos que merecen vivir por separado, usa rebase merge; si además quieres registrar el evento del PR, merge commit.

3 · Ejemplo mínimo

El PR más pequeño con su check automático: un workflow que se dispara en cada PR hacia main y un comando para abrirlo.

.github/workflows/pr.yml
name: PR checks

on:
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: pip install -e .
      - run: pytest -q

# Abre el PR describiendo el cambio
gh pr create --base main --title "feat(api): add /health" \
  --body "Cierra #12. Devuelve {status: ok}. Probado en local."

# Mira el estado de los checks del PR actual
gh pr checks

# Y mergetalo con squash cuando este verde
gh pr merge --squash --delete-branch

El nombre del job (test) es justo el que debes declarar como check obligatorio en la protección de rama. Si se llaman distinto, la regla nunca se cumple y todos los PR quedan bloqueados — el error más común de esta lección.

4 · Ejemplo real

En Publicar el Copiloto protegemos main de la Copiloto API con un check obligatorio (test) y una aprobación. La forma reproducible de configurarlo es por API, para poder versionar la regla en lugar de guiarla por interfaces:

terminal
gh api -X PUT repos/:owner/:repo/branches/main/protection \
  --input - <<'JSON'
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["test"]
  },
  "enforce_admins": true,
  "required_pull_request_reviews": {
    "required_approving_review_count": 1,
    "dismiss_stale_reviews": true
  },
  "restrictions": null,
  "required_conversation_resolution": true
}
JSON

Qué hace cada bandera: strict: true exige que la rama esté al día con main antes de integrar; dismiss_stale_reviews descarta aprobaciones al subir commits nuevos (nadie aprueba algo que ya no es lo revisado); required_conversation_resolution obliga a resolver los hilos de comentarios antes de mergear.

Para proteger también los propios workflows y las migraciones de la base de datos, usamos CODEOWNERS, de modo que su aprobación sea obligatoria aunque el PR lo haya abierto otra persona:

.github/CODEOWNERS
# Rutas sensibles: exigen revision del equipo de plataforma
/.github/workflows/   @acme/platform
/infra/               @acme/platform
/app/migrations/      @acme/backend

Y el merge por defecto es squash, con borrado de la rama, para que cada PR sea un commit en main. Ese commit único y descriptivo es exactamente lo que el módulo usará después para derivar la versión y el changelog:

commit resultante en main
feat(api): add /health endpoint (#12)

Descripción del PR = contexto para tu yo del futuro. Escribe qué cambia, por qué y cómo probarlo. El mensaje que sobrevive no es el del PR (efímero), sino el del commit squash: cuida el título del PR, porque se convertirá en el mensaje del commit que quedará para siempre en main.

6 · Errores habituales

1. Exigir un check que no existe

La causa número uno de «no puedo mergear nada». El nombre de la regla debe coincidir con el reportado.

Mal — el job se llama build-and-test, pero exiges CI 
# .github/workflows/ci.yml
jobs:
  build-and-test:        # <- el check reportado sera "build-and-test"
    runs-on: ubuntu-latest
    # ...

# Proteccion de rama: contexts ["CI"]  -> nunca aparece, merge SIEMPRE bloqueado
Bien — el mismo nombre a los dos lados 
jobs:
  test:                   # check reportado: "test"
    runs-on: ubuntu-latest

# Proteccion de rama: contexts ["test"]  -> coincide y desbloquea al pasar

2. Permitir el merge en rojo «porque es urgente»

Un CI que no bloquea es un CI que se ignora. La urgencia es justo cuando más importa.

Mal — desactivar la protección para meter un fix 
# Se quita la proteccion, se pushea el fix con el test en rojo,
# y "luego se arregla". Dos semanas despues, main sigue roto.
Bien — arreglar primero, con ayuda del CI 
gh pr checks                 # que falla exactamente
gh run view --log-failed     # el log del job que fallo
# Se arregla en la MISMA rama; el check pasa a verde y el PR se desbloquea.

3. Mezclar formatos de merge sin criterio

Diez PRs con squash y dos con merge commit dejan un historial incoherente y difícil de leer.

Mal — cada cual mergea a su gusto 
main: ... ─●─ M ─●─●─ M ─ M ─●─ ...   (commits de merge y no merge mezclados)
         "Merge branch 'feat/x' into 'main'"   x3
Bien — una política y solo una en el repo 
# Deja squash como unico metodo permitido en Settings / API:
gh api -X PATCH repos/:owner/:repo -f allow_merge_commit=false -f allow_squash_merge=true

7 · Ejercicio guiado

Objetivo: montar el ciclo completo «PR con check obligatorio» de la Copiloto API: el CI corre en el PR, la rama protegida lo exige, y una vez verde se integra con squash.

  1. Paso 1 — Crea el workflow de PR.
    .github/workflows/ci.yml
    name: CI

on:
  pull_request:
    branches: [main]

jobs:
  test:                          # el nombre "test" es el que exigira la proteccion
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -e ".[dev]"
      - run: ruff check .
      - run: pytest -q
  2. Paso 2 — Sube el workflow a main. Todavía no hay protección, así que puedes hacerlo directamente una vez. 
    git add .github/workflows/ci.yml
git commit -m "ci: run tests on pull requests"
git push origin main
  3. Paso 3 — Activa la protección con el MISMO nombre de check. 
    gh api -X PUT repos/:owner/:repo/branches/main/protection \
  --input - <<'JSON'
{
  "required_status_checks": { "strict": true, "contexts": ["test"] },
  "enforce_admins": true,
  "required_pull_request_reviews": { "required_approving_review_count": 1, "dismiss_stale_reviews": true },
  "restrictions": null
}
JSON
  4. Paso 4 — Abre un PR que rompa el test (a propósito). 
    git switch -c feat/rompe-test
# ... escribe un cambio que haga fallar pytest ...
git commit -am "feat: cambio que rompe un test"
git push -u origin feat/rompe-test
gh pr create --base main --fill
gh pr checks   # -> "test" en rojo; el boton de merge esta deshabilitado

    Comprueba en la interfaz que no puedes mergear: el botón está bloqueado por el check. Eso es la protección funcionando, no un fallo.

  5. Paso 5 — Arregla en la misma rama y mergea con squash. 
    # corrige el test roto
git commit -am "fix: corrige el test roto"
git push
gh pr checks                # -> "test" en verde
gh pr merge --squash --delete-branch

    Resultado esperado: un único commit nuevo en main con el título del PR, la rama borrada y ninguna posibilidad de haber integrado en rojo. Si gh pr checks mostraba el check con otro nombre, revisa el jobs: del YAML: ahí nace el 90% de los bloqueos.

8 · Reto

🎯 Un PR que se revisa solo

Diseña el flujo de un repositorio donde ningún PR pueda integrarse sin pasar por tres puertas: (1) el check obligatorio test; (2) una aprobación de una persona distinta al autor; y (3) una aprobación de CODEOWNERS cuando el PR toca .github/workflows/** o app/migrations/**. Además, haz que el botón de merge quede deshabilitado hasta que la rama esté al día con main. Compara lo que hace falta configurar en GitHub y en GitLab (equivalentes de branch protection y merge requests approvals) y documenta las diferencias.

Pista: en GitHub casi todo esto se expresa en la protección de rama (required_status_checks, required_pull_request_reviews, codeowners dentro de reviews) y en el CODEOWNERS; el strict: true es el que obliga a estar al día. No está prohibido usar la interfaz, pero piensa cómo versionar esa configuración (por ejemplo, con la API o con Terraform) para que no viva solo en la cabeza de nadie. Intenta además justificar cuándo una merge queue aporta y cuándo es sobreingeniería.

9 · Resumen

  • Un pull request es un objeto de revisión de la plataforma (no un commit): reúne diff, conversación, checks y aprobaciones.
  • El CI sobre pull_request prueba la fusión con la base: detecta el choque antes de que ocurra.
  • La protección de rama convierte el CI en un contrato: sin checks verdes y sin aprobación, no hay merge.
  • Los nombres de los checks deben coincidir exactamente con los jobs; un nombre inexistente bloquea todo.
  • strict: true exige que la rama esté al día; evita que dos PR verdes se rompan al juntarse.
  • Squash es el valor por defecto sensato: un PR, un commit claro en main.
  • Con squash, el título del PR se convierte en el mensaje del commit: cuídalo.

10 · Preguntas frecuentes

¿Squash, merge commit o rebase? ¿Cuál es «correcto»?

No hay uno correcto en abstracto; hay uno coherente con tu flujo. Para trunk-based, squash es lo habitual: un PR = un commit, historial lineal, changelog y git bisect legibles. Elige rebase merge si cada commit del PR ya es limpio y quieres conservarlos sin commit extra. Usa merge commit si quieres registrar explícitamente la fusión. Lo importante es elegir uno y aplicarlo en todo el repositorio.

Mis PR siempre quedan bloqueados aunque los tests pasan, ¿qué pasa?

Casi siempre es el nombre del check obligatorio que no coincide con el que reporta el job (o el workflow no corre sobre pull_request). Revisa gh pr checks para ver el nombre real y compáralo con el contexts de la protección. La segunda causa frecuente es strict: true: la rama está desactualizada respecto a main y hay que actualizarla (rebase o merge de main).

¿La revisión de código retrasa demasiado?

La revisión es un cuello de botella si se hace mal: PRs enormes, revisores ausentes, discusiones de estilo. Se aligera con PRs pequeños, con criterios de revisión explícitos (corrección, claridad, seguridad, tests) y automatizando lo objetivo (formato, lint) en el CI. El tiempo invertido en revisar bien es mucho menor que el de depurar un fallo que llegó a producción sin que nadie lo mirase.

¿Puedo mergear mi propio PR si soy administrador?

Sí, y ese es justo el agujero: el permiso de administrador suele poder saltarse la protección. Por eso existe enforce_admins, que obliga a los admins a cumplir las mismas reglas. En equipos pequeños, donde nadie más puede revisar, hay que elegir conscientemente: o se acepta que el admin pueda saltarse la puerta (documentándolo), o se pide revisión externa para lo crítico. Lo que no funciona es creer que estás protegido cuando en realidad puedes puentear la regla.

¿Qué es una merge queue y cuándo la necesito?

Es una cola donde los PR aprobados y verdes esperan su turno: la plataforma los agrupa y prueba la combinación antes de integrarlos a main, de modo que dos PR que por separado pasan pero juntos rompen no lleguen al tronco. Sustituye con ventaja a «require branches to be up to date» cuando el repositorio recibe muchos merges y cada rebase provoca esperas. En un repositorio de actividad baja, es sobreingeniería: la regla de “al día + checks” ya basta.
