Terraform básico

Módulo 6 · Infraestructura como código 🕐 40 minutos

1 · Introducción

En la lección anterior decidimos que la infraestructura del Copiloto se escribe como código. Ahora toca aprender el idioma. Terraform y OpenTofu leen archivos .tf escritos en HCL (HashiCorp Configuration Language), un lenguaje declarativo pensado para describir recursos y las relaciones entre ellos.

Esta lección cubre las seis piezas que usarás el 90 % del tiempo: providers (quién sabe crear los recursos), recursos (qué quieres que exista), variables (qué parametrizas), outputs (qué publicas), la diferencia entre plan y apply, y los dos comandos que no deberías olvidar nunca: fmt y validate.

¿Por qué Terraform/OpenTofu? Porque es declarativo (describes el resultado, no los pasos), agnóstico de nube (el mismo lenguaje habla con Kubernetes, AWS, GCP, Cloudflare…) y porque su plan te deja ver los cambios antes de aplicarlos. Aprender un idioma y usarlo en cien proveedores es mejor negocio que aprender cien consolas.

A lo largo de la lección escribimos terraform. Si usas OpenTofu, el binario es tofu, pero los archivos .tf, HCL y los subcomandos son los mismos. Elige uno en tu equipo y sé coherente.

2 · Teoría

Anatomía de un proyecto Terraform

Todo proyecto es un directorio con archivos .tf. Los nombres no importan para el motor (los carga todos), pero ordenan la cabeza. La convención que usaremos con el Copiloto:

infra/
├── versions.tf    # required_version + required_providers (fuente y version)
├── providers.tf   # configuracion de cada provider (region, kubeconfig, ...)
├── variables.tf   # entradas parametrizables
├── main.tf        # recursos
└── outputs.tf     # valores que se publican hacia fuera

Providers: quien sabe crear los recursos

Un provider es el plugin que traduce HCL a llamadas de una API concreta (Kubernetes, AWS, Cloudflare…). Se declara en el bloque terraform con su fuente (un directorio del registry) y una restricción de versión:

versions.tf
terraform {
  required_version = ">= 1.6"

  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.33"
    }
  }
}

El símbolo ~> es un «pessimistic constraint»: ~> 2.33 acepta 2.33.x y 2.34.x, pero no 3.0. Así recibes correcciones sin saltos de versión mayor que rompan la sintaxis. Las versiones exactas que se resuelven quedan fijadas en .terraform.lock.hcl, que sí se sube a Git: garantiza que CI y tu portátil usan lo mismo.

terraform init es el paso que descarga los providers y prepara el directorio. Se ejecuta siempre y primero, también en el pipeline.

El directorio .terraform/ es la caché de providers y nunca se versiona (va al .gitignore). El .terraform.lock.hcl, en cambio, sí: es pequeño, legible y determinista.

Recursos: qué quieres que exista

Un recurso es un objeto gestionado por un provider. Su dirección es tipo.nombre, y dentro vienen sus argumentos:

main.tf
resource "kubernetes_namespace_v1" "copiloto" {
  metadata {
    name   = "copiloto-${var.environment}"
    labels = { app = "copiloto", env = var.environment }
  }
}

Los recursos se referencian entre sí con la sintaxis tipo.nombre.atributo. Esa referencia es una dependencia: Terraform construye un grafo y crea las cosas en el orden correcto, en paralelo cuando puede.

referencia entre recursos
resource "kubernetes_deployment_v1" "copiloto" {
  metadata {
    # El namespace se crea primero por esta referencia; no hay que ordenar a mano.
    namespace = kubernetes_namespace_v1.copiloto.metadata[0].name
    name      = "copiloto-api"
  }
  # ...
}

Analogía: el grafo de dependencias es una receta de cocina. Si una salsa usa una base que aún no has hecho, la receta deduce que la base va primero. Tú solo escribes qué lleva cada plato; el orden se calcula.

Variables: parametrizar sin copiar y pegar

Las variables convierten un .tf en una plantilla reutilizable. Se declaran con variable y se usan como var.nombre:

variables.tf
variable "environment" {
  type        = string
  description = "Entorno de despliegue (staging o prod)"

  validation {
    condition     = contains(["staging", "prod"], var.environment)
    error_message = "El entorno debe ser 'staging' o 'prod'."
  }
}

variable "image" {
  type        = string
  description = "Referencia inmutable de la imagen del Copiloto en GHCR"
}

variable "replicas" {
  type        = number
  default     = 2
  description = "Numero de replicas de la API"
}

Los valores llegan por varias vías. De menor a mayor prioridad:

OrigenEjemploCuándo
Valor por defectodefault = 2Si nadie dice lo contrario
Variables de entornoTF_VAR_environment=stagingCI y sesiones locales
terraform.tfvarsreplicas = 3Se carga automáticamente
*.auto.tfvarsstaging.auto.tfvarsCarga automática por orden alfabético
-var-file / -var-var-file=env/staging.tfvarsExplícito; lo usaremos en la lección 4

Las variables marcadas sensitive = true no se muestran en la salida de plan ni de apply. Pero atención: eso solo oculta el valor en el log, no lo guarda en un sitio seguro. Los secretos de verdad entran desde un secret manager o desde el CI (módulo 4, lección 2).

Outputs: publicar lo que otros necesitan

Un output expone un valor fuera del proyecto: la URL del servicio, el nombre del recurso, un identificador. Sirven para dos cosas: leerlos con terraform output y que otro proyecto los consuma (lo verás con los módulos en la lección 3).

outputs.tf
output "service_name" {
  value       = kubernetes_service_v1.copiloto.metadata[0].name
  description = "Nombre del Service interno del Copiloto"
}

output "namespace" {
  value = kubernetes_namespace_v1.copiloto.metadata[0].name
}

plan vs apply: mirar antes de tocar

Esta es la distinción más importante de todo el módulo. terraform plan no cambia nada: lee el estado actual, lo compara con tu código y muestra el diff. terraform apply lo ejecuta.

   codigo (.tf) ──┐
                  ├──▶  terraform plan  ──▶  "+ crear / ~ cambiar / - destruir"
   estado real ───┘            │
                               ▼  (revisado y aprobado)
                        terraform apply  ──▶  infraestructura real

La forma rigurosa de aplicar es guardar el plan en un archivo y aplicar exactamente ese archivo. Así, lo que revisaste es literalmente lo que se ejecuta, aunque entre la revisión y el apply alguien cambie el código:

terminal
terraform plan -out=tfplan     # guarda el plan en el archivo tfplan
terraform apply tfplan         # aplica ESE plan, no recalcula nada

Evita -auto-approve en producción y -target como costumbre. -target aplica solo un recurso e ignora dependencias; útil como bisturí de emergencia, peligroso como norma. Si el plan no te gusta, arregla el código; no lo recortes.

fmt y validate: el lint y el test de tu infraestructura

Igual que en el módulo 2 el CI pasaba lint y tests antes de construir, aquí pasamos dos comprobaciones antes de planificar:

ComandoQué compruebaModo CI
terraform fmtFormato canónico (indentación, alineación)terraform fmt -check -recursive (falla si hay diferencias)
terraform validateSintaxis y coherencia interna (tipos, referencias, argumentos)terraform validate (falla si hay errores)

terraform validate necesita que init haya corrido antes (los providers deben estar descargados para validar los tipos de sus recursos). El orden en CI es siempre fmt → init → validate → plan.

3 · Ejemplo mínimo

Un solo archivo con las seis piezas en su forma más pequeña: provider, variable, recurso y output. Seguimos sin nube, con el proveedor local.

infra/main.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

variable "mensaje" {
  type        = string
  description = "Mensaje que se escribira en el archivo"
  default     = "Copiloto API"
}

resource "local_file" "nota" {
  filename = "${path.module}/salida/nota.txt"
  content  = "${var.mensaje}\n"
}

output "ruta_nota" {
  value       = local_file.nota.filename
  description = "Ruta del archivo creado"
}

El ciclo completo, con las seis piezas en juego:

terminal
terraform fmt -check -recursive   # 1. formato (falla si hay diferencias)
terraform init                    # 2. descarga `local` + escribe el lock file
terraform validate                # 3. sintaxis y coherencia
terraform plan -out=tfplan        # 4. previsualiza y guarda el plan
terraform apply tfplan            # 5. aplica exactamente lo revisado
terraform output ruta_nota        # 6. lee el valor publicado

Línea por línea:

  1. required_providers.local: declara el provider y su versión. Sin esto, init no sabe qué descargar.
  2. variable "mensaje": una entrada con tipo, descripción y valor por defecto. Se usa como var.mensaje.
  3. resource "local_file" "nota": el objeto deseado. ${path.module} es la carpeta del proyecto; ${var.mensaje} interpola la variable.
  4. output "ruta_nota": publica local_file.nota.filename. Referencia el recurso, así que el output espera a que exista.
  5. terraform plan -out=tfplan: guarda el plan. apply tfplan ejecuta ese plan concreto, sin recalcular.
  6. terraform output ruta_nota: imprime el valor. Con -json obtienes formato máquina para consumirlo desde un script o el CI.

Fíjate en que fmt -check falla si el archivo no está formateado: obliga a que todos escriban igual. Ejecuta terraform fmt -recursive (sin -check) para que lo corrija solo.

4 · Ejemplo real

El Copiloto, desplegado sobre el cluster Kubernetes que ya conoces de Learn Docker. La infraestructura declara el namespace, la imagen que corre y el Service que la expone. Todo parametrizado por entorno y por versión de imagen.

infra/versions.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.33"
    }
  }
}
infra/variables.tf
variable "environment" {
  type        = string
  description = "Entorno de despliegue (staging o prod)"
  validation {
    condition     = contains(["staging", "prod"], var.environment)
    error_message = "El entorno debe ser 'staging' o 'prod'."
  }
}

variable "image" {
  type        = string
  description = "Imagen inmutable del Copiloto en GHCR (por ejemplo, con tag v1.4.0)"
}

variable "replicas" {
  type        = number
  default     = 2
  description = "Replicas de la API"
}
infra/main.tf
resource "kubernetes_namespace_v1" "copiloto" {
  metadata {
    name   = "copiloto-${var.environment}"
    labels = { app = "copiloto", env = var.environment }
  }
}

resource "kubernetes_deployment_v1" "copiloto" {
  metadata {
    name      = "copiloto-api"
    namespace = kubernetes_namespace_v1.copiloto.metadata[0].name
    labels    = { app = "copiloto-api" }
  }

  spec {
    replicas = var.replicas

    selector {
      match_labels = { app = "copiloto-api" }
    }

    template {
      metadata {
        labels = { app = "copiloto-api" }
      }

      spec {
        container {
          name  = "api"
          image = var.image

          port {
            container_port = 8000
          }

          env {
            name  = "ENV"
            value = var.environment
          }
        }
      }
    }
  }
}

resource "kubernetes_service_v1" "copiloto" {
  metadata {
    name      = "copiloto-api"
    namespace = kubernetes_namespace_v1.copiloto.metadata[0].name
  }

  spec {
    selector = { app = "copiloto-api" }

    port {
      port        = 80
      target_port = 8000
    }
  }
}
infra/env/staging.tfvars
environment = "staging"
image       = "ghcr.io/academy/copiloto-api:v1.4.0-rc.1"
replicas    = 1

Y el flujo, ya con variables por archivo:

terminal
terraform fmt -check -recursive
terraform init
terraform validate
terraform plan  -var-file=env/staging.tfvars -out=tfplan
terraform apply tfplan
terraform output namespace

El plan, antes de tocar el cluster, deja el cambio a la vista:

terraform plan (fragmento)
Terraform will perform the following actions:

  # kubernetes_namespace_v1.copiloto will be created
  + resource "kubernetes_namespace_v1" "copiloto" {
      + metadata {
          + name   = "copiloto-staging"
          + labels = { "app" = "copiloto", "env" = "staging" }
        }
    }

  # kubernetes_deployment_v1.copiloto will be created
  + resource "kubernetes_deployment_v1" "copiloto" {
      + spec {
          + replicas = 1
          + template { + spec { + container { + image = "ghcr.io/academy/copiloto-api:v1.4.0-rc.1" } } }
        }
    }

Plan: 3 to add, 0 to change, 0 to destroy.

Decisiones y porqués:

  • image como variable: la misma infraestructura sirve para cualquier versión. El pipeline (módulo 3) publica la imagen y pasa su tag aquí; la infraestructura no «sabe» qué código corre, solo cuál debe correr.
  • environment con validation: un typo como prodution se corta en la validación, no en un namespace vacío y confuso.
  • Referencias en lugar de nombres repetidos: kubernetes_namespace_v1.copiloto.metadata[0].name garantiza que el namespace se cree antes y que nadie escriba el nombre a mano en dos sitios.
  • -var-file=env/staging.tfvars: un archivo por entorno (lo explotaremos en la lección 4). El código es idéntico; cambian los valores.
  • Plan guardado y aplicado: exactamente el paso que automatizaremos en CI.

El proveedor aquí es kubernetes para no atarnos a una nube. Cambiar a hashicorp/aws o hashicorp/google no cambia el cómo: misma estructura, otras fuentes y otros recursos. Por eso IaC es una habilidad transferible.

6 · Errores habituales

Valores incrustados en lugar de variables

Mal — copiar el recurso por entorno 
# ❌ El nombre y las replicas van incrustados: para prod hay que copiar todo.
resource "kubernetes_namespace_v1" "copiloto" {
  metadata { name = "copiloto-staging" }
}
resource "kubernetes_deployment_v1" "copiloto" {
  spec { replicas = 1 }
}
Bien — parametrizar 
# ✅ Un unico recurso; el entorno entra por variable (y por -var-file).
resource "kubernetes_namespace_v1" "copiloto" {
  metadata { name = "copiloto-${var.environment}" }
}
resource "kubernetes_deployment_v1" "copiloto" {
  spec { replicas = var.replicas }
}

Versiones de provider sin fijar

Mal — «la última» 
# ❌ Sin restriccion, un lunes cualquiera entra una version mayor y cambia el recurso.
terraform {
  required_providers {
    kubernetes = { source = "hashicorp/kubernetes" }
  }
}
Bien — restricción + lock file 
# ✅ Rango explicito y .terraform.lock.hcl versionado: resultado determinista.
terraform {
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.33"
    }
  }
}

Aplicar sin guardar el plan revisado

Mal — aplicar a ciegas 
# ❌ Si el codigo cambio entre el plan y el apply, se aplica algo que nadie reviso.
$ terraform plan
$ terraform apply -auto-approve
Bien — plan guardado y aplicado 
# ✅ El archivo tfplan es la prueba: se revisa y se aplica tal cual.
$ terraform plan -out=tfplan
$ terraform apply tfplan

Usar -target como forma habitual de trabajar

Mal — aplicar «solo lo mío» 
# ❌ Ignora dependencias y deja el resto desincronizado: asi nace el drift.
$ terraform apply -target=kubernetes_deployment_v1.copiloto
Bien — aplicar el conjunto coherente 
# ✅ Se aplica todo el proyecto; para separar, se separan en modulos (leccion 3).
$ terraform apply tfplan

Marcar un output con un secreto sin sensitive

Mal — secreto en claro en los logs 
# ❌ terraform output lo imprime en claro y viaja a los logs del CI.
output "db_password" {
  value = var.db_password
}
Bien — marcarlo y no publicarlo 
# ✅ Si de verdad hay que exponerlo, se marca; mejor aun, no se expone.
output "db_password" {
  value     = var.db_password
  sensitive = true
}

7 · Ejercicio guiado

Objetivo: montar el proyecto mínimo con las seis piezas y ver fallar a fmt y validate a propósito, para entender qué atrapan.

  1. Paso 1: crea el directorio y el archivo con las seis piezas del ejemplo mínimo. 
    mkdir -p copiloto-tf && cd copiloto-tf
# crea main.tf con el contenido del ejemplo minimo de esta leccion
terraform init

    Resultado esperado: Terraform has been successfully initialized! y aparece .terraform.lock.hcl.

  2. Paso 2: rompe el formato a propósito (quita la indentación de un bloque) y comprueba que el CI lo detectaría. 
    terraform fmt -check -recursive; echo "exit: $?"

    Resultado esperado: imprime el nombre del archivo con diferencias y exit: 3 (distinto de cero = el job del CI fallaría). Corrígelo con terraform fmt -recursive.

  3. Paso 3: introduce un error semántico: referencia una variable que no declaraste (var.replicas sin variable "replicas"). 
    terraform validate

    Resultado esperado: un error del tipo Reference to undeclared input variable. validate no necesita credenciales: atrapa esto antes de intentar hablar con ninguna API.

  4. Paso 4: corrige y planifica guardando el plan. 
    terraform plan -out=tfplan
terraform apply tfplan

    Resultado esperado: Plan: 1 to add y, al aplicar, Apply complete! Resources: 1 added. El archivo salida/nota.txt contiene el mensaje.

  5. Paso 5: cambia el valor de la variable sin tocar el recurso y observa que el plan solo propone el update mínimo. 
    terraform plan -var="mensaje=Hola Copiloto" -out=tfplan
terraform apply tfplan
terraform output ruta_nota

    Resultado esperado: el plan muestra ~ update in-place del contenido (no destruye el recurso), y terraform output imprime la ruta.

  6. Paso 6 (verificación): demuestra que el lock file hace su trabajo. 
    grep -A3 "provider \"registry.terraform.io/hashicorp/local\"" .terraform.lock.hcl

    Resultado esperado: el archivo fija la versión exacta resuelta (por ejemplo version = "2.9.0"). Sube main.tf y .terraform.lock.hcl a Git; .terraform/ y *.tfstate van al .gitignore.

8 · Reto

🎯 Un módulo de infraestructura «a prueba de balas»

Refactoriza el ejemplo real del Copiloto de forma que un entorno mal escrito no pueda llegar ni al plan: valida el nombre del entorno, valida que replicas sea mayor que cero, y haz que la imagen esté obligada a ser un tag inmutable (v1.4.0, no latest). Añade un output con la URL interna del servicio y otro con un resumen legible del despliegue.

Después añade precondition al recurso de despliegue para exigir que el cluster tenga el namespace esperado, y comprueba que un plan con un valor inválido falla con tu mensaje, no con un error críptico del proveedor.

Pista: para lo inmutable, una validation con can(regex("^v\\d+\\.\\d+\\.\\d+", var.image)) o un !strcontains(var.image, ":latest"). Para el resumen, un output que construya una cadena con format(). Para la precondition, dentro de un bloque lifecycle, comprueba var.environment contra el namespace esperado. Recuerda: el reto no trae solución, pero el mensaje de error es tu mejor prueba.

9 · Resumen

  • Un proyecto Terraform es un directorio de .tf en HCL, normalmente repartido en versions, providers, variables, main y outputs.
  • Los providers se declaran con source y version; init los descarga y el .terraform.lock.hcl fija las versiones exactas.
  • Los recursos tienen dirección tipo.nombre y se referencian entre sí: Terraform ordena las dependencias solo.
  • Las variables parametrizan con type, default y validation; llegan por tfvars, TF_VAR_ o -var-file.
  • Los outputs publican valores para leerlos con terraform output o consumirlos desde otros proyectos.
  • plan mira, apply toca. Guarda el plan (-out=tfplan) y aplica ese archivo.
  • fmt formatea y validate comprueba coherencia: son el lint y el test de la infraestructura.

10 · Preguntas frecuentes

¿terraform plan puede cambiar algo?

No debería. El plan lee el estado real (refresh), lo compara con tu código y muestra el diff, pero no aplica cambios. Única matización: el refresh puede actualizar el estado local para reflejar la realidad; es decir, puede escribir el archivo de estado, nunca la infraestructura. Si dudas, plan es seguro.

¿Por qué no basta con terraform apply directamente?

Porque sin revisar el plan no ves lo que se va a destruir. Un rename inocente puede marcar un recurso como -/+ (replace) y llevarse por delante datos. En local, con recursos desechables, apply está bien; en producción, el plan es tu revisión y, como verás en la lección 4, la prueba que el CI publica en la PR.

¿Dónde pongo los valores de las variables en el CI?

Los no secretos en *.tfvars versionados por entorno (una carpeta env/). Los secretos nunca en el repo: entran como variables de entorno TF_VAR_… desde el gestor de secretos del CI, o mejor, evitas el problema autenticando por OIDC (módulo 4, lección 2). Todo esto lo montamos en la lección 4.

¿Necesito cuenta en la nube para practicar?

No. Con el proveedor local (como en esta lección) o random practicas el lenguaje sin coste. Y con kind o minikube (del curso Learn Docker) levantas un cluster local y aplicas el ejemplo real del Copiloto sin gastar un céntimo.

Terraform o OpenTofu: ¿cuál elijo?

Para aprender, cualquiera: los archivos .tf y los subcomandos son idénticos. OpenTofu (tofu) es la bifurcación libre bajo la Fundación Linux y muchos equipos la prefieren por licencia; Terraform sigue siendo el estándar corporativo con más providers gestionados. Lo importante es fijar versiones en required_version y no mezclar binarios en el mismo equipo sin pensarlo.
