Estado y módulos

Módulo 6 · Infraestructura como código 🕐 35 minutos

1 · Introducción

Terraform funciona porque sabe qué existe y dónde está. Ese conocimiento vive en un archivo: el estado (state). Si el código .tf es el plano de la casa, el estado es el inventario de muebles con su número de serie: sin él, la herramienta no sabe si un recurso ya está creado o hay que crearlo.

El estado es, con diferencia, la pieza que más duele cuando se gestiona mal: es único, es mutable, puede contener secretos y, si dos personas lo tocan a la vez, se corrompe. Esta lección explica cómo funciona, por qué debe vivir en un backend remoto con locking y cómo los módulos te dejan reutilizar infraestructura sin copiar y pegar.

¿Por qué esta lección existe? Porque el error nº 1 de quien empieza con IaC es tratar el terraform.tfstate como un archivo cualquiera del proyecto. El estado no es un artefacto de salida: es la memoria de la herramienta. Entenderlo es la frontera entre «hago demos» y «llevo infraestructura de verdad».

Adelanto de la lección: el estado se guarda en un backend remoto, se bloquea durante cada operación y nunca se sube a Git. Si te llevas solo eso, ya habrás entendido el 80 %.

2 · Teoría

Qué guarda el estado exactamente

El estado asocia cada recurso de tu código con el objeto real que creó, y guarda los atributos que la API devolvió. Simplificando, para cada recurso hay una entrada con su dirección y sus atributos. Un extracto de un terraform.tfstate real:

terraform.tfstate (fragmento, simplificado)
{
  "version": 4,
  "terraform_version": "1.9.5",
  "serial": 12,
  "lineage": "8f2c1a9e-...",
  "resources": [
    {
      "mode": "managed",
      "type": "kubernetes_namespace_v1",
      "name": "copiloto",
      "provider": "provider[\"registry.terraform.io/hashicorp/kubernetes\"]",
      "instances": [
        {
          "attributes": {
            "id": "copiloto-staging",
            "metadata": [{ "name": "copiloto-staging", "labels": { "env": "staging" } }]
          }
        }
      ]
    }
  ]
}

Dos datos clave: el tipo y nombre (kubernetes_namespace_v1.copiloto) y el id real en el proveedor. Con eso, Terraform puede preguntar «¿sigue existiendo? ¿cambió algo?» y decidir el diff. Además, el estado guarda metadatos como el orden de serialización (serial) y el lineage, que identifican su historia.

El estado no es solo el id. También guarda los outputs, las dependencias y valores de atributos que la API no te deja consultar. Por eso no se puede «reconstruir» leyendo solo la nube: Terraform necesita el archivo.

Por qué es crítico

  • Es la fuente de verdad del plan. Sin estado, Terraform cree que no existe nada y propondrá crear recursos que ya existen (duplicados o choques de nombre) o, peor, destruir y recrear.
  • Puede contener secretos. Los atributos sensibles que la API devuelve (contraseñas generadas, tokens) se guardan en claro en el estado. Por eso el estado es tan sensible como un secreto.
  • Es un recurso compartido y mutable. Todo el equipo y el CI lo leen y lo escriben. Sin bloqueo, dos apply a la vez corrompen el archivo.
  • Perderlo es caro. Recuperarlo implica importar recurso a recurso, a mano. Es una tarde perdida y un riesgo de incidente.

Analogía: el estado es la lista de la compra después de haber comprado. El código dice qué quieres tener en la despensa; la lista dice qué hay ya y de qué marca. Si tiras la lista, volverás a comprar lo que ya tienes, o tirarás lo bueno por duplicado.

Estado remoto con locking

Por defecto el estado es un archivo local: terraform.tfstate en el directorio del proyecto. Eso vale para aprender, pero en equipo y en CI es inservible: cada persona tendría su copia y la del CI otra. La solución es un backend remoto: el estado vive en un almacenamiento compartido y se bloquea durante cada operación.

   tu portatil ─┐
                ├──▶  backend remoto (S3 + lock, HCP Terraform, GCS…)
   el CI ───────┘          │
                           ├── guarda terraform.tfstate (compartido)
                           └── LOCK mientras alguien hace plan/apply
                                │
                                └── el segundo que llega espera o falla

El backend se declara en el bloque terraform y se configura con init. Los datos sensibles (bucket, región) pueden ir por -backend-config, lo que permite el mismo código con distinto backend por entorno:

infra/versions.tf
terraform {
  backend "s3" {
    bucket       = "academy-tfstate"
    key          = "copiloto/staging/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true # bloqueo por fichero en el propio bucket (Terraform 1.10+)
  }
}
terminal
# Inicializa con backend remoto y migra el estado local si ya existia:
terraform init -migrate-state

# Espera hasta 5 minutos si el estado esta bloqueado por otro run:
terraform apply -lock-timeout=5m

Sobre el bloqueo (locking). En backends como S3, el bloqueo se hacía con una tabla de DynamoDB; hoy se admite use_lockfile = true, que usa un objeto en el propio bucket. Otros backends lo traen integrado: HCP Terraform (la nube de HashiCorp) bloquea y además da historial de runs, política y aprobaciones. Los tres backends populares —S3, GCS y Azure Blob— soportan estado remoto; elige el que ya conozcas.

Comandos de estado que conviene conocer

ComandoPara qué sirveCuidado con…
terraform state listLista las direcciones gestionadas—
terraform state show DIRMuestra los atributos de un recursoPuede revelar secretos
terraform state mv A BRenombra/dirige una entradaMejor usar bloques moved
terraform state rm DIRDeja de gestionar un recurso sin destruirloEl recurso sigue existiendo por fuera
terraform import DIR IDAdopta un recurso ya existenteHay que escribir el recurso antes

Mejor moved que state mv. Un bloque moved en el código documenta el renombrado, se revisa en la PR y se aplica solo. Un terraform state mv a mano es un cambio invisible en el historial del repositorio, y se olvida.

Módulos: reutilizar sin copiar y pegar

Un módulo es un conjunto de archivos .tf que se llama desde otro punto. El proyecto que ejecutas es el módulo raíz (root); cada module que invocas es un módulo hijo (child). La interfaz es igual que la de una función: variables de entrada, outputs de salida.

infra/envs/staging/main.tf
module "service" {
  source = "../../modules/service"

  environment = "staging"
  image       = "ghcr.io/academy/copiloto-api:v1.4.0-rc.1"
  replicas    = 1
}

output "service_name" {
  value = module.service.service_name
}

El módulo define qué recibe y qué devuelve:

infra/modules/service/variables.tf
variable "environment" { type = string }
variable "image" { type = string }
variable "replicas" {
  type    = number
  default = 2
}

Cuatro reglas que evitan sorpresas:

  1. Los hijos no tienen estado propio. Todo se guarda en el estado del módulo raíz, con direcciones prefijadas por module.nombre.
  2. Los hijos solo se comunican por variables y outputs. No hay efectos globales; es lo que los hace testeables y reutilizables.
  3. La source es local o remota. Local (../../modules/service) para módulos del propio repo; remota (registry, repo de Git con ?ref=v1.2.0) para compartidos. La remota se fija a una versión.
  4. Un módulo, un propósito. «Todo lo del Copiloto» no es un módulo; «un servicio desplegable» sí.

Los módulos también reducen el tamaño del estado. Un estado gigantesco hace lento cada plan y amplifica el riesgo de un cambio. Separa por ciclo de vida: la red cambia poco, la aplicación mucho; no deberían compartir estado.

3 · Ejemplo mínimo

Sin nube: el proveedor local escribe una nota, y nosotros miramos el estado que genera. El objetivo es ver la asociación entre dirección y recurso real.

infra/main.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

resource "local_file" "nota" {
  filename = "${path.module}/salida/nota.txt"
  content  = "estado y modulos\n"
}
terminal
terraform init
terraform apply -auto-approve

terraform state list
# local_file.nota

terraform state show local_file.nota
# # local_file.nota:
# resource "local_file" "nota" {
#     content  = "estado y modulos\n"
#     filename = "./salida/nota.txt"
#     id       = "b3f1...c9"
# }

Línea por línea:

  1. terraform state list: imprime las direcciones que Terraform gestiona. Cada línea es un recurso real que existe por ahí y que el código declara.
  2. terraform state show local_file.nota: revela los atributos guardados, incluido el id real. Es la ventana al contenido del estado sin abrir el JSON a mano.
  3. El id: lo devuelve el proveedor al crear el recurso. Es lo que ata tu dirección lógica (local_file.nota) al objeto físico.

Prueba a renombrar el recurso en el código de local_file.nota a local_file.bienvenida y ejecuta terraform plan sin mover el estado: verás - destroy y + create (borra el archivo y lo crea de nuevo). Es exactamente el replace que hay que evitar. Deshazlo, o usa un moved, y el plan dirá No changes.

4 · Ejemplo real

El Copiloto crece: queremos la misma infraestructura de servicio en staging y en producción, con estados con backend remoto distintos. La estructura que lo resuelve es un módulo y un directorio raíz por entorno (cada uno con su propio estado).

infra/
infra/
├── modules/
│   └── service/            # modulo reutilizable: namespace + deployment + service
│       ├── versions.tf
│       ├── variables.tf
│       ├── main.tf
│       └── outputs.tf
└── envs/
    ├── staging/            # modulo raiz, con su backend y su estado
    │   ├── main.tf
    │   └── backend.hcl
    └── prod/
        ├── main.tf
        └── backend.hcl

El módulo encapsula la infraestructura del servicio y expone lo que hay que publicar:

infra/modules/service/main.tf (esquema)
resource "kubernetes_namespace_v1" "this" {
  metadata {
    name   = "copiloto-${var.environment}"
    labels = { app = "copiloto", env = var.environment }
  }
}

resource "kubernetes_deployment_v1" "this" {
  metadata {
    name      = "copiloto-api"
    namespace = kubernetes_namespace_v1.this.metadata[0].name
  }
  spec {
    replicas = var.replicas
    # ... selector, template y container con var.image
  }
}
infra/modules/service/outputs.tf
output "namespace" {
  value = kubernetes_namespace_v1.this.metadata[0].name
}

output "service_name" {
  value = kubernetes_deployment_v1.this.metadata[0].name
}

Cada entorno es un módulo raíz que llama al módulo y declara su backend. El código es idéntico; solo cambian los valores y la key del estado:

infra/envs/staging/main.tf
terraform {
  required_version = ">= 1.6"
  backend "s3" {
    key          = "copiloto/staging/terraform.tfstate"
    use_lockfile = true
  }
}

module "service" {
  source = "../../modules/service"

  environment = "staging"
  image       = "ghcr.io/academy/copiloto-api:v1.4.0-rc.1"
  replicas    = 1
}
infra/envs/staging/backend.hcl
bucket = "academy-tfstate"
region = "eu-west-1"
encrypt = true
terminal
cd infra/envs/staging
terraform init -backend-config=backend.hcl -migrate-state
terraform plan -out=tfplan
terraform apply tfplan

# Las direcciones del estado llevan el prefijo del modulo:
terraform state list
# module.service.kubernetes_namespace_v1.this
# module.service.kubernetes_deployment_v1.this

Decisiones y porqués:

  • Un estado por entorno (copiloto/staging/… y copiloto/prod/…): un apply en staging no puede tocar producción, ni siquiera por error. Aislamiento por diseño.
  • El módulo no declara backend. El backend pertenece al módulo raíz; un módulo hijo no decide dónde vive el estado. Por eso modules/service no tiene bloque backend.
  • -backend-config=backend.hcl: bucket y región fuera del código, para que el mismo módulo raíz sirva en otra cuenta sin editar .tf.
  • module.service.service_name: los outputs del hijo se leen con ese prefijo. Es la única superficie de comunicación hacia fuera.
  • use_lockfile = true: si dos runs coinciden (tú y el CI), el segundo espera o falla con state locked en lugar de corromper el estado.

Lee los outputs de otro estado con el data source terraform_remote_state: define su backend y su key, y accede a los valores con data.terraform_remote_state..outputs.. Sirve para que el módulo raíz de red y el de aplicación se comuniquen sin acoplarse a la misma carpeta.

5 · Buenas prácticas

HazEvitaPor qué
Backend remoto con locking desde el día uno Estado local en el portátil Compartido, bloqueado y respaldado; el local se pierde y se desincroniza
Un estado por entorno Un único estado para staging y prod Errores en staging no deben poder alcanzar producción
Tratar el estado como un secreto Subirlo a Git o a un bucket público Contiene valores sensibles en claro; fuga garantizada
Usar bloques moved para renombrar terraform state mv a mano El renombrado queda en la PR y se aplica solo, sin destruir nada
terraform import para adoptar recursos existentes Recrear lo que ya existe Adoptar evita downtime y duplicados

Fijar la source remota a una versión (?ref=v1.2.0) Apuntar a main de otro repo Un cambio ajeno no debería romper tu infra sin avisar

6 · Errores habituales

Versionar el estado en Git

Mal — el estado en el repositorio 
# ❌ El tfstate guarda secretos en claro y, ademas, provoca conflictos en cada merge.
$ git add terraform.tfstate
$ git commit -m "state"
Bien — backend remoto e ignorado en Git 
# ✅ .gitignore
.terraform/
*.tfstate
*.tfstate.*
crash.log

Dos apply a la vez sobre el mismo estado

Mal — sin locking 
# ❌ Backend local o sin bloqueo: tu apply y el del CI escriben a la vez.
# Resultado: estado corrupto, recursos duplicados o huerfanos.
Bien — estado remoto con locking 
# ✅ El backend bloquea durante la operacion; el segundo run espera o falla limpiamente.
terraform {
  backend "s3" {
    key          = "copiloto/staging/terraform.tfstate"
    use_lockfile = true
  }
}

Renombrar un recurso sin mover el estado

Mal — renombrar y esperar 
# ❌ El estado apunta a "copiloto"; el codigo ahora dice "copiloto_api" → destroy + create.
resource "kubernetes_namespace_v1" "copiloto_api" {
  metadata { name = "copiloto-staging" }
}
Bien — dirigir el cambio con moved 
# ✅ El estado sigue el renombrado sin destruir ni recrear el recurso.
moved {
  from = kubernetes_namespace_v1.copiloto
  to   = kubernetes_namespace_v1.copiloto_api
}

Compartir un solo estado entre entornos

Mal — un estado para todo 
# ❌ Staging y produccion comparten estado: un plan de staging puede listar
# cambios de produccion, y un error de dedo aplica en el entorno equivocado.
# Y como extra, cada plan tarda una eternidad.
Bien — estados separados por entorno 
# ✅ infra/envs/staging → copiloto/staging/terraform.tfstate
#    infra/envs/prod    → copiloto/prod/terraform.tfstate
# Mismo modulo, dos estados aislados.

Módulo remoto apuntando a una rama

Mal — seguir main de otro repo 
# ❌ El modulo puede cambiar sin que tu repositorio lo sepa.
module "service" {
  source = "git::https://github.com/academy/terraform-service.git"
}
Bien — fijar una versión 
# ✅ La version es explicita y subirla es un cambio revisable en tu PR.
module "service" {
  source = "git::https://github.com/academy/terraform-service.git?ref=v1.2.0"
}

7 · Ejercicio guiado

Objetivo: ver con tus ojos por qué el estado es imprescindible, cómo el prefijo module. aparece al refactorizar, y cómo un moved evita destruir. Sin nube: el módulo escribe archivos con el proveedor local.

  1. Paso 1: crea un módulo que escriba una nota por entorno. 
    mkdir -p copiloto-state/modules/nota copiloto-state/envs/staging

    # modules/nota/variables.tf
variable "environment" { type = string }

# modules/nota/main.tf
resource "local_file" "nota" {
  filename = "${path.module}/../../salida/${var.environment}.txt"
  content  = "entorno=${var.environment}\n"
}

    Resultado esperado: el directorio del módulo y su variable. Aún no hay estado.

  2. Paso 2: crea el módulo raíz que lo llama y aplica. 
    # envs/staging/main.tf
module "nota" {
  source      = "../../modules/nota"
  environment = "staging"
}

    cd copiloto-state/envs/staging
terraform init && terraform apply -auto-approve

    Resultado esperado: se crea salida/staging.txt y aparece terraform.tfstate en la carpeta del entorno.

  3. Paso 3: mira el estado y localiza el prefijo del módulo. 
    terraform state list

    Resultado esperado: module.nota.local_file.nota. Los recursos del hijo viven en el estado del raíz, con el prefijo module.nota. El módulo no tiene estado propio.

  4. Paso 4: simula que alguien pierde el estado. Aparta el archivo y planifica. 
    mv terraform.tfstate terraform.tfstate.old
terraform plan

    Resultado esperado: Plan: 1 to add — Terraform no recuerda que la nota ya existe y quiere crearla otra vez. Restaura el archivo (mv terraform.tfstate.old terraform.tfstate) y repite plan: vuelve a decir No changes. Acabas de demostrar para qué sirve el estado.

  5. Paso 5: renombra el recurso con un bloque moved y comprueba que no se destruye nada. 
    # modules/nota/main.tf
resource "local_file" "nota_copiloto" {
  filename = "${path.module}/../../salida/${var.environment}.txt"
  content  = "entorno=${var.environment}\n"
}

moved {
  from = local_file.nota
  to   = local_file.nota_copiloto
}

    terraform plan

    Resultado esperado: No changes (Terraform reconoce el moved, no hay destroy). Quita el bloque moved y repite: ahora propondría -/+ replace. Vuelve a ponerlo.

  6. Paso 6 (verificación): prepara el salto a backend remoto y comprueba el bloqueo. 
    # envs/staging/main.tf (añade)
terraform {
  backend "s3" {
    key          = "copiloto/staging/terraform.tfstate"
    use_lockfile = true
  }
}

    terraform init -migrate-state
# Si no tienes AWS, comprueba primero que el plan sigue igual tras el cambio:
terraform plan -lock-timeout=5m

    Resultado esperado: init migra el estado local al backend remoto sin recrear recursos; en un run concurrente, el segundo recibiría Error: state locked en lugar de corromper el archivo. Si no tienes bucket, deja el bloque comentado y anota el paso como pendiente de credenciales.

Añade .terraform/, *.tfstate y *.tfstate.* al .gitignore del ejercicio. Solo .tf, .tfvars y .terraform.lock.hcl van a Git.

8 · Reto

🎯 Partir el estado en dos sin recrear nada

Tienes un único estado con toda la infraestructura del Copiloto: red, base de datos y aplicación. Pártelo en dos estados independientes —infra-base (red y base de datos) y infra-app (namespace, despliegue, servicio)— de forma que no se destruya ningún recurso en el proceso. El de la aplicación debe leer lo que necesita del estado de la base con terraform_remote_state.

Documenta el proceso como una sucesión de terraform state mv o de bloques moved (justifica cuál eliges), y añade un output en infra-base que exponga lo que consume la app.

Pista: para no destruir nada, el orden importa. Primero escribe el nuevo módulo raíz con su backend y su key propia; después terraform init y terraform state mv (o moved) para trasladar las entradas del estado viejo al nuevo; por último, terraform plan en ambos y exige No changes antes de borrar el estado antiguo. En infra-app, el data source terraform_remote_state apunta al backend de infra-base y lees data.terraform_remote_state.base.outputs.…. Si algún plan dice destroy, el movimiento no está bien hecho: para y corrígelo.

9 · Resumen

  • El estado asocia cada recurso del código con su objeto real (id) y sus atributos. Es la memoria de Terraform y la fuente de verdad del plan.
  • Es crítico: sin él, Terraform cree que nada existe; además puede contener secretos en claro. Nunca va a Git.
  • Vive en un backend remoto con locking para que equipo y CI compartan un único estado sin corromperlo.
  • Un estado por entorno: aislamiento por diseño entre staging y producción.
  • Los módulos encapsulan infraestructura reutilizable y se comunican por variables y outputs; no tienen estado propio.
  • Renombrar se hace con bloques moved (revisables) en lugar de editar el estado a mano; adoptar recursos existentes, con terraform import.
  • terraform_remote_state conecta estados distintos sin acoplarlos en la misma carpeta.

10 · Preguntas frecuentes

¿Qué pasa si pierdo el estado de verdad?

Lo recuperas importando cada recurso existente: escribes el recurso en el código y ejecutas terraform import con su id. Funciona, pero es lento y delicado, y cualquier recurso que no importes o que esté mal importado puede quedar huérfano o duplicado. La mejor estrategia es no llegar ahí: backend remoto con versionado (S3 lo tiene por defecto) y, si puedes, un backend que guarde historial de versiones del estado.

¿Por qué el estado guarda secretos?

Porque el proveedor devuelve atributos sensibles (contraseñas autogeneradas, tokens, claves) y Terraform los guarda para saber si cambiaron sin tener que volver a crearlos. sensitive = true solo oculta el valor en los logs: el estado sigue conteniéndolo. Trátalo como un secreto: backend cifrado, acceso restringido, nunca en Git.

¿Los módulos tienen su propio estado?

No. Todos los recursos de todos los módulos hijos viven en el estado del módulo raíz, con direcciones prefijadas por module.. Por eso un módulo raíz = un estado, sin excepciones. Si quieres estados separados, necesitas módulos raíz separados (directorios con su propio backend), no más módulos hijos.

¿Backend remoto o workspaces?

Son ortogonales. El backend decide dónde vive el estado; los workspaces deciden cuántos estados hay bajo el mismo backend (uno por workspace). Muchos equipos prefieren un directorio por entorno con su backend explícito, porque es más legible y fácil de aislar. Comparamos las dos opciones a fondo en la lección 4.

¿Puedo editar el estado a mano para arreglar algo?

Es la última opción y suele salir mal: el formato tiene seriales y conteos que, si te equivocas, lo corrompen. Usa terraform state mv, terraform state rm, terraform import o bloques moved, que respetan el formato. Y, sobre todo: con el estado en un backend remoto, primero haz una copia antes de tocarlo.
