Cheatsheet de CI/CD

Referencia rápida ⚙️ GitHub Actions · Docker · Terraform

Disparadores (on)

on responde a «¿cuándo se ejecuta esto?» y admite filtros por rama (branches), etiqueta (tags) o rutas (paths / paths-ignore). La forma corta de una lista es on: [push, pull_request].

DisparadorSe activa cuando…Uso típico en el Copiloto
pushSe sube un commit (filtrable por branches, tags, paths)CI al integrar en main
pull_requestSe abre o actualiza una PRVerificar antes del merge
workflow_dispatchManualmente, desde la UI o ghDespliegue manual con inputs
scheduleSegún una expresión cron en UTCEscaneos nocturnos de dependencias
workflow_runOtro workflow terminaEncadenar publish → deploy
releaseSe publica una releasePublicar artefactos versionados (SemVer)
workflow_callOtro workflow lo invocaConvertir el workflow en reusable
.github/workflows/ci.yml — disparadores combinados
on:
  push:
    branches: [main]
    tags: ["v*"]                        # releases y versiones
    paths-ignore: ["docs/**", "**.md"]  # no gastes CI en documentación
  pull_request:
    branches: [main]
  workflow_dispatch:
    inputs:
      environment:
        description: "Entorno destino"
        type: choice
        options: [staging, production]
        default: staging
  schedule:
    - cron: "0 6 * * 1"                 # lunes 06:00 UTC

# Cancela ejecuciones viejas de la misma rama: ahorra minutos y evita carreras.
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

Los inputs de workflow_dispatch se leen con ${{ inputs.environment }} (o ${{ github.event.inputs.* }}). Ojo: schedule solo corre en la rama por defecto, y un fork que abre una PR no recibe tus secretos.

Esqueleto del workflow: jobs, matriz y caché

Un workflow es un YAML en .github/workflows/. Los jobs corren en paralelo por defecto; needs crea el grafo de dependencias (un DAG). Cada job arranca en una máquina limpia: lo que instales en uno no existe en el siguiente.

.github/workflows/ci.yml — estructura completa
name: ci                        # pestaña Actions

on: [push, pull_request]

permissions:
  contents: read                # mínimo privilegio, siempre explícito

env:
  PYTHON_VERSION: "3.12"        # variables del workflow

jobs:
  lint:                         # job 1
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install ruff && ruff check .

  test:                         # job 2: corre EN PARALELO con lint
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false          # no abortes las demás combinaciones
      matrix:
        python-version: ["3.11", "3.12"]
        os: [ubuntu-latest, windows-latest]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - uses: actions/cache@v4
        with:
          path: ~/.cache/pip
          key: pip-${{ runner.os }}-${{ hashFiles('**/requirements*.txt') }}
      - run: pip install -e ".[dev]"
      - run: pytest -q

  build:
    needs: [lint, test]         # espera a que AMBOS terminen bien
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "aquí se construye la imagen"
Necesitas…Escribes…
Disparadoron: [push, pull_request]
Un trabajojobs: <id>:
La máquina del jobruns-on: ubuntu-latest
Encadenar jobsneeds: [lint, test]
Paso con una action- uses: actions/checkout@v4
Parámetros de una actionwith: { python-version: "3.12" }
Paso con un comando- run: pytest -q
Ejecutar varias líneas- run: | (bloque de shell)

Publicar un archivo entre jobs- uses: actions/upload-artifact@v4
Reutilizar un workflowuses: ./.github/workflows/reusable.yml

Fija la versión de cada uses. Las majors avanzan con el tiempo (checkout pasó de v4 a v6, upload-artifact de v3 a v4): usa una etiqueta concreta y, en producción de alto riesgo, ancla por SHA (uses: actions/checkout@11bd719…). Una action sin versión puede cambiar bajo tus pies.

Contextos y expresiones ${{ }}

GitHub rellena estos valores en tiempo de ejecución. Se usan en casi cualquier clave del YAML y dentro de los run.

ExpresiónContiene
${{ github.sha }}SHA del commit que disparó la ejecución (identidad del artefacto)
${{ github.ref }}Referencia completa, p. ej. refs/heads/main
${{ github.ref_name }}Nombre corto de la rama o etiqueta (main, v1.4.0)
${{ github.event_name }}Qué disparó el run: push, pull_request…
${{ github.repository }}propietario/repo, base de la ruta en GHCR
${{ github.actor }}Usuario que ejecutó el workflow
${{ runner.os }}Sistema del runner: Linux, Windows, macOS
${{ matrix.python-version }}La combinación actual de la matriz
${{ steps.meta.outputs.tags }}Salida de un paso anterior (ese paso lleva id: meta)
${{ needs.build.outputs.digest }}Salida de otro job del que dependes
${{ secrets.REGISTRY_TOKEN }}Un secreto del repositorio/entorno (nunca en texto plano)
${{ vars.API_URL }}Una variable de configuración (no sensible)
${{ env.PYTHON_VERSION }}Una variable declarada en env:
${{ inputs.environment }}Entrada de un workflow_dispatch o workflow_call

No interpoles datos no confiables directamente en run. Pasa el valor por env: y usa "$VAR" dentro del script. Meter texto del evento (por ejemplo un título de PR) en el shell abre la puerta a script injection.

Permisos del GITHUB_TOKEN

El GITHUB_TOKEN es una credencial efímera que GitHub crea para cada ejecución. Se declara con mínimo privilegio: si no lo especificas, hereda el valor por defecto del repositorio (a veces de escritura). Declara permissions: a nivel de workflow o de job, y solo lo necesario.

PermisoQué habilitaCuándo lo necesitas
contents: readLeer el código y los metadatos del repoCasi siempre (checkout)
contents: writeCrear tags, releases y commitsChangelog automático y releases
packages: writePublicar en GHCR (ghcr.io)Subir la imagen del Copiloto
attestations: writePublicar attestations (SBOM y procedencia)Cadena de suministro
id-token: writeSolicitar un token OIDCDesplegar sin claves de larga vida
security-events: writeSubir resultados SARIF (code scanning)Escaneo de vulnerabilidades
pull-requests: writeComentar o etiquetar PRsBots de revisión y cobertura
.github/workflows/publish.yml — permisos por job
permissions:
  contents: read            # por defecto en todo el workflow: solo leer

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read        # checkout
      packages: write       # push a ghcr.io
      attestations: write   # subir SBOM/procedencia
      id-token: write       # firmar con OIDC
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

¿Por qué importa? Un token de más es una llave de más en manos de cualquier paso (incluida una action de terceros). contents: read por defecto y packages: write solo donde publicas es la diferencia entre un «fallo local» y un compromiso de la cadena de suministro.

Comandos: gh y act

gh es la CLI oficial de GitHub; act ejecuta los workflows en local dentro de Docker (sin gastar minutos y sin hacer push).

# --- gh: autenticación y contexto ---
gh auth login                      # login interactivo (token o navegador)
gh auth status                     # ¿quién soy y con qué scopes?

# --- gh: repositorio y pull requests ---
gh repo clone acme/copiloto
gh pr create --fill                # abre una PR con título/cuerpo del commit
gh pr checks                       # estado de los checks de la PR
gh pr view --web                   # abre la PR en el navegador
gh pr merge --squash --delete-branch

# --- gh: ejecuciones de workflows ---
gh run list --workflow=ci.yml --limit 10
gh run watch                       # sigue en vivo la ejecución en curso
gh run view <run-id> --log-failed  # solo el log de lo que falló
gh run rerun <run-id> --failed     # reintenta únicamente los jobs fallidos
gh workflow run publish.yml -f version=1.4.0   # dispara workflow_dispatch

# --- gh: secretos, variables, releases y paquetes ---
gh secret set REGISTRY_TOKEN       # se define fuera del repo, nunca en YAML
gh variable set API_URL --body "https://api.example.com"
gh release create v1.4.0 --generate-notes
gh release view v1.4.0
gh attestation verify oci://ghcr.io/acme/copiloto-api:sha-abc123

# --- act: prueba los workflows en local (necesita Docker) ---
act -l                             # lista los jobs y sus dependencias
act push                           # simula un evento "push"
act pull_request -j test           # solo el job "test" del evento PR
act workflow_dispatch -W .github/workflows/publish.yml
act -n                             # dry-run: valida sin ejecutar

# Atajo habitual del curso (desde "Learn DevOps/"):
npm run serve                      # sirve web/ en local

act reutiliza imágenes de runner y no siempre trae todo lo que sí tiene GitHub (secretos, services, algunas actions). Úsalo para validar sintaxis y orden del grafo rápido, no como sustituto del run real.

Docker y Buildx en CI

En CI no se construye «a lo bruto»: se prepara Buildx, se cachean capas entre ejecuciones y se publica por digest con SBOM y procedencia. Buildx es el constructor moderno (docker build con caché avanzada y multi-arquitectura).

.github/workflows/publish.yml — build y push a GHCR
permissions:
  contents: read
  packages: write
  attestations: write
  id-token: write

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-qemu-action@v4        # multi-arch (arm64): opcional
      - uses: docker/setup-buildx-action@v4       # crea el builder

      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha,format=long                    # inmutable: sha-<commit>
            type=semver,pattern={{version}}         # solo en tags vX.Y.Z

      - uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          platforms: linux/amd64,linux/arm64
          cache-from: type=gha                      # lee caché de GitHub Actions
          cache-to: type=gha,mode=max               # guarda caché
          provenance: mode=max                      # procedencia SLSA
          sbom: true                                # SBOM (SPDX/CycloneDX)
ActionPara qué
docker/setup-buildx-action@v4Crear el builder Buildx (obligatorio antes de build-push)
docker/setup-qemu-action@v4Emular otra arquitectura (multi-arch)
docker/login-action@v4Autenticarse en el registry (GHCR, Docker Hub…)
docker/metadata-action@v5Calcular tags y labels (sha, semver, rama)
docker/build-push-action@v7Construir, cachear, publicar y firmar la imagen
 
# Los mismos comandos, en local (para reproducir lo que hace el pipeline)
docker buildx create --use --name copiloto-builder
docker buildx build --platform linux/amd64 -t copiloto-api:dev --load .
docker buildx build --push -t ghcr.io/acme/copiloto-api:sha-$(git rev-parse HEAD) .
docker buildx imagetools inspect ghcr.io/acme/copiloto-api:sha-abc123
docker buildx imagetools inspect ghcr.io/acme/copiloto-api:sha-abc123 --format '{{json .Manifest.Digest}}'

La etiqueta latest no es apta para desplegar: se mueve. El despliegue se ancla al digest (image@sha256:…), que es verificable e inmutable. Etiqueta para los humanos, digest para el sistema.

Terraform / OpenTofu básico

La infraestructura se declara en HCL y se aplica en ciclos plan → revisar → apply. El estado es la memoria de Terraform: guárdalo en un backend remoto con bloqueo, nunca en el repo.

ComandoQué hace
terraform initDescarga providers y prepara el backend remoto
terraform fmt -checkComprueba el formato (falla si hay que reformatear)
terraform validateValida sintaxis y referencias sin tocar la infra
terraform plan -out=tfplanCalcula el diff y lo guarda en un archivo revisable
terraform apply tfplanAplica exactamente el plan aprobado
terraform state listLista los recursos que gestiona el estado
terraform output -jsonExporta salidas (URLs, ARNs) para el pipeline
terraform destroyElimina lo gestionado (usar con pinzas)
terraform import <addr> <id>Adopta un recurso creado a mano
infra/main.tf — declaración y estado remoto
terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  backend "s3" {                 # estado remoto, compartido y con lock
    bucket = "copiloto-tfstate"
    key    = "prod/terraform.tfstate"
    region = "eu-west-1"
  }
}

variable "environment" {
  type        = string
  description = "staging o production"
}

resource "aws_s3_bucket" "artifacts" {
  bucket = "copiloto-artifacts-${var.environment}"
}

output "bucket_arn" {
  value = aws_s3_bucket.artifacts.arn
}
.github/workflows/infra.yml — IaC como código en CI
permissions:
  contents: read
  id-token: write                     # OIDC: credenciales temporales, sin claves

jobs:
  plan:
    runs-on: ubuntu-latest
    environment: production           # las reglas de protección del entorno aplican
    steps:
      - uses: actions/checkout@v4
      # El job intercambia el token OIDC por credenciales temporales del proveedor.
      # (Sin claves de larga vida; el proveedor concreto es indiferente.)
      - run: terraform init
      - run: terraform fmt -check
      - run: terraform validate
      - run: terraform plan -out=tfplan
      - run: terraform apply -auto-approve tfplan   # solo tras aprobación

# Regla de oro: si el verificador de attestations no casa con el digest, NO se despliega.

Plan y apply, el mismo artefacto. Genera tfplan en el job de plan, guárdalo como artifact y ejecútalo tal cual tras la aprobación. Un apply que recalcula el plan puede aplicar algo distinto de lo revisado.
