Dataclasses

Módulo 5 · Programación orientada a objetos ⏱ 30 minutos

1 · Introducción

Escribe una clase que solo guarda datos y verás siempre el mismo ritual: __init__ repitiendo self.x = x, un __repr__ legible, y un __eq__ para comparar por valor. Son líneas mecánicas, propensas a olvidar un campo y a desincronizarse cuando añades uno nuevo. Las dataclasses (introducidas en Python 3.7, mejoradas cada versión) generan todo eso por ti a partir de las anotaciones de tipo.

Esta lección enseña a declarar @dataclass, valores por defecto, el imprescindible field(default_factory=…) para mutables, frozen (inmutabilidad), order (comparación) y __post_init__ para validar. Al terminar reescribirás el Item de Biblioteca como dataclass, más corto y menos propenso a errores.

¿Por qué existen las dataclasses? Porque en Python —y en cualquier lenguaje— una gran parte de las clases son portadoras de datos: un ítem, una fila de la base, un resultado. Escribir a mano su constructor, igualdad y representación es ruido. @dataclass convierte declaración en comportamiento: describes los campos y el decorador genera el código repetitivo. Menos código, menos bugs, y el foco donde importa: las reglas del dominio.

2 · Teoría

Antes y después

Comparemos la misma cosa escrita a mano y con @dataclass. El resultado funcional es idéntico (constructor, repr e igualdad), pero la dataclass no repite nada.

# --- A mano: __init__, __repr__ y __eq__ escritos por ti ---
class Item:
    def __init__(self, id, title, kind="book"):
        self.id = id
        self.title = title
        self.kind = kind

    def __repr__(self):
        return f"Item(id={self.id!r}, title={self.title!r}, kind={self.kind!r})"

    def __eq__(self, other):
        if not isinstance(other, Item):
            return NotImplemented
        return (self.id, self.title, self.kind) == (other.id, other.title, other.kind)


# --- Con dataclass: solo declaras los campos ---
from dataclasses import dataclass

@dataclass
class Item:
    id: str
    title: str
    kind: str = "book"

La dataclass genera __init__, __repr__ y __eq__ a partir de los campos anotados. Fíjate en algo clave: las anotaciones son lo que define los campos. Si un atributo no tiene anotación, no es un campo de la dataclass.

Las anotaciones no son solo documentación aquí. En Módulo 1 viste que los type hints no se comprueban al ejecutar. En una dataclass, en cambio, @dataclass lee las anotaciones del cuerpo para saber qué campos generar. Por eso id: str es obligatorio y no un simple adorno.

Valores por defecto y el problema de los mutables

Los campos con valor por defecto deben ir después de los que no lo tienen (igual que en las funciones), o Python lanza TypeError: non-default argument follows default argument.

from dataclasses import dataclass

@dataclass
class Item:
    id: str
    title: str
    kind: str = "book"        # con default
    year: int | None = None   # con default

# item = Item("1")   # TypeError: falta title (sin default)
item = Item("1", "1984")
print(item)   # Item(id='1', title='1984', kind='book', year=None)

¿Y si el campo es mutable, como una lista de etiquetas? Escribir tags: list[str] = [] es el equivalente astronáutico del def f(x=[]): el valor se crea una sola vez y se comparte entre todas las instancias. Python moderno ni siquiera te deja: lanza ValueError: mutable default <class 'list'> for field tags is not allowed. La solución es field(default_factory=list), que ejecuta list() en cada instancia para crear una lista nueva.

from dataclasses import dataclass, field

@dataclass
class Item:
    id: str
    title: str
    tags: list[str] = field(default_factory=list)   # lista NUEVA por instancia

a = Item("1", "1984")
b = Item("2", "Dune")
a.tags.append("clásico")
print(a.tags)   # ['clásico']
print(b.tags)   # []          <- independiente

¿Por qué default_factory y no un valor directo? Porque la dataclass necesita una fábrica que llame para producir un valor nuevo en cada instancia. default_factory=list significa «llama a list() cada vez»; default_factory=dict, «llama a dict()». Es exactamente la solución al bug de la lección 1, pero ahora el lenguaje te obliga a hacerlo bien.

frozen: inmutabilidad

@dataclass(frozen=True) hace que los atributos no se puedan reasignar después de crear el objeto: intentarlo lanza FrozenInstanceError. A cambio, la dataclass genera __hash__, así que los objetos congelados se pueden usar como clave de diccionario o en un set.

from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: int
    y: int

p = Point(1, 2)
# p.x = 5              # FrozenInstanceError
print(hash(p) is not None)   # True: es hashable

¿Inmutable de verdad? frozen impide reasignar atributos, pero si un campo contiene un mutable (una lista), esa lista sigue siendo mutable: p.values.append(1) funcionaría si values fuera una lista. frozen congela los enlaces, no el contenido de los objetos enlazados. Para inmutabilidad profunda harían falta tuplas y tipos inmutables.

order: comparación

Por defecto, una dataclass genera __eq__ pero no los operadores de orden (<, <=, >, >=). Con order=True los genera comparando los campos en el orden en que los declaras (como comparar tuplas).

from dataclasses import dataclass

@dataclass(order=True)
class Version:
    major: int
    minor: int

print(Version(1, 2) < Version(1, 3))   # True  (mismo major, menor minor)
print(Version(1, 9) < Version(2, 0))   # True
print(sorted([Version(2, 0), Version(1, 5)]))
# [Version(major=1, minor=5), Version(major=2, minor=0)]

Ojo con order y los campos no comparables. Si la dataclass incluye un campo que no soporta < (por ejemplo un dict) y comparas dos instancias, saltará TypeError. Solución: usar field(compare=False) en ese campo para excluirlo de las comparaciones, o definir tus propios dunders (lección 5).

__post_init__: lógica tras generar __init__

¿Dónde validamos o calculamos algo derivado? En el método __post_init__, que la dataclass ejecuta automáticamente al final del __init__ generado.

from dataclasses import dataclass

@dataclass
class Item:
    id: str
    title: str
    year: int | None = None

    def __post_init__(self):
        # Se ejecuta después del __init__ generado: aquí validamos.
        self.title = self.title.strip()
        if not self.title:
            raise ValueError("title no puede estar vacío")
        if self.year is not None and not (0 < self.year < 3000):
            raise ValueError(f"año fuera de rango: {self.year}")

# Item("1", "  ")   # ValueError: title no puede estar vacío
item = Item("1", " 1984 ", 1949)
print(item)          # Item(id='1', title='1984', year=1949)

3 · Ejemplo mínimo

La dataclass más pequeña con sentido: un punto 2D con valores por defecto.

point.py
from dataclasses import dataclass

@dataclass
class Point:
    x: int = 0
    y: int = 0

# Al no escribir __init__, la dataclass lo genera con estos defaults.
a = Point()              # usa ambos defaults
b = Point(3, 4)          # posicional
c = Point(x=3, y=4)      # por nombre (más legible)

print(repr(a))           # Point(x=0, y=0)
print(repr(b))           # Point(x=3, y=4)
print(b == c)            # True  <- __eq__ compara campo a campo
print(b == Point(3, 5))  # False

Línea por línea: @dataclass lee las anotaciones x e y y genera __init__(self, x=0, y=0), __repr__ y __eq__. Por eso b == c es True aunque sean objetos distintos: la igualdad por defecto en una dataclass es por valor (sus campos), no por identidad. Ese matiz es justo lo que en la lección anterior teníamos que escribir a mano.

4 · Ejemplo real

Reescribimos el modelo de Biblioteca con dataclasses. Gracias a frozen y order, obtenemos gratis igualdad, orden e hash; __post_init__ centraliza la validación y field(default_factory=…) resuelve las etiquetas.

biblioteca/models.py (versión de esta lección)
from dataclasses import dataclass, field


@dataclass
class Item:
    """Ítem del catálogo, como dataclass."""

    id: str
    title: str
    kind: str = "book"                 # "book" | "movie"
    year: int | None = None
    borrowed: bool = False
    # Mutable: SIEMPRE con default_factory, nunca con [] directo.
    tags: list[str] = field(default_factory=list)
    # Campo que no participa en la igualdad ni en el orden.
    internal_note: str = field(default="", compare=False, repr=False)

    def __post_init__(self):
        # Normalización + validación, tras el __init__ generado.
        self.title = self.title.strip()
        if not self.title:
            raise ValueError("title no puede estar vacío")
        if self.kind not in {"book", "movie"}:
            raise ValueError(f"kind inválido: {self.kind!r}")
        if self.year is not None and not isinstance(self.year, int):
            raise TypeError("year debe ser int o None")

    @property
    def label(self):
        year = self.year if self.year is not None else "s/a"
        return f"{self.title} ({year})"


@dataclass(frozen=True, order=True)
class CatalogEntry:
    """Vista inmutable y ordenable de un ítem para listar."""

    kind: str
    title: str
    year: int = 0


# --- Uso ---
book = Item("1", "1984", "book", 1949)
movie = Item("2", "Blade Runner", "movie", 1982, tags=["sci-fi"])

print(book)                    # Item(id='1', title='1984', kind='book', year=1949, borrowed=False, tags=[])
print(book.label)              # 1984 (1949)

# Igualdad por VALOR: dos ítems con los mismos campos son iguales.
clone = Item("1", "1984", "book", 1949)
print(book == clone)           # True
print(book is clone)           # False  (objetos distintos, mismo valor)

# Las etiquetas son independientes (default_factory).
print(movie.tags)              # ['sci-fi']
print(book.tags)               # []
book.tags.append("distopía")
print(book.tags)               # ['distopía']  <- movie no cambia

# CatalogEntry: inmutable y ordenable.
entries = [CatalogEntry("movie", "Blade Runner", 1982), CatalogEntry("book", "1984", 1949)]
print([e.title for e in sorted(entries)])
# ['1984', 'Blade Runner']   <- ordena por (kind, title, year); "book" < "movie"

# Validación temprana:
# Item("3", "   ")            # ValueError: title no puede estar vacío
# Item("4", "X", kind="cd")   # ValueError: kind inválido: 'cd'

Decisiones explicadas:

  • default_factory=list en tags garantiza una lista por instancia: es el bug de la lección 1 resuelto por el propio decorador.
  • internal_note usa compare=False, repr=False: no debe afectar a == ni aparecer en el repr. Así el repr sigue siendo limpio y la igualdad significativa.
  • __post_init__ normaliza y valida. Es el lugar natural: el __init__ ya existe (generado) y aquí podemos inspeccionar todos los campos a la vez.
  • CatalogEntry es frozen=True, order=True: una vista inmutable y ordenable. Al ser frozen, es hashable y podría ir en un set. Es un tipo distinto de Item: no compite con él.

frozen + igualdad: cuidado al mezclar. Una dataclass normal tiene __eq__ generado y, por tanto, Python la marca como no hashable (__hash__ = None) porque la igualdad por valor y el hash deben ir juntos. Si haces frozen=False (por defecto) e intentas meter un Item en un set, obtendrás TypeError: unhashable type. Con frozen=True, obtienes __hash__ automáticamente. Lo verás con más detalle en la sección de errores.

5 · Buenas prácticas

HazEvitaPor qué
field(default_factory=list) para mutables tags: list = [] El default directo se comparte (o Python directamente lo prohíbe). default_factory crea uno nuevo por instancia.
Campos con default al final Mezclar campos sin y con default Misma regla que las funciones: TypeError: non-default argument follows default argument.
Valida en __post_init__ Confiar en que nadie creará un objeto inválido La dataclass no valida tipos en ejecución; __post_init__ es tu punto único de control.
frozen=True para valores/entidades inmutables Congelar clases que necesitan cambiar de estado frozen da hash y evita mutaciones accidentales, pero reasignar falla. Úsalo cuando el valor no debe cambiar.
field(compare=False, repr=False) para campos internos Incluir todo en igualdad y repr La igualdad debe reflejar identidad de negocio; el extra interno no debe ensuciarla.
Usa dataclass para datos, clase normal para comportamiento Forzar toda clase a ser dataclass Si el objeto es sobre todo lógica y colaboradores, una clase normal (o una dataclass con métodos concretos) lee mejor.

6 · Errores habituales

Default mutable directo

# ❌ Python lo rechaza directamente.
from dataclasses import dataclass

@dataclass
class Item:
    tags: list = []
# ValueError: mutable default <class 'list'> for field tags is not allowed:
#   use default_factory

# ✅ La fábrica crea una lista nueva por instancia.
from dataclasses import dataclass, field

@dataclass
class Item:
    tags: list = field(default_factory=list)

Creer que frozen congela el contenido

# ❌ "Es frozen, luego nada puede cambiar".
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Item:
    id: str
    tags: list = field(default_factory=list)

item = Item("1")
item.tags.append("X")      # FUNCIONA: la lista interna es mutable
print(item.tags)           # ['X']
# item.id = "2"            # FrozenInstanceError: sí bloquea reasignar el campo

# ✅ Para inmutabilidad real, usa tipos inmutables (tuple/frozenset).
@dataclass(frozen=True)
class Item:
    id: str
    tags: tuple[str, ...] = ()

Esperar order por defecto… o sufrir campos no comparables

from dataclasses import dataclass

# ❌ Sin order=True, comparar con < falla.
@dataclass
class Version:
    major: int
    minor: int

# Version(1, 0) < Version(2, 0)   # TypeError: '<' not supported

# ❌ Con order=True pero un campo no comparable, falla al comparar.
@dataclass(order=True)
class Item:
    title: str
    meta: dict = None or {}

# Item("a", {}) < Item("b", {})   # TypeError: '<' not supported between dict

# ✅ Marca compare=False el campo que no debe participar.
from dataclasses import field

@dataclass(order=True)
class Item:
    title: str
    meta: dict = field(default_factory=dict, compare=False)

Frozen + no hashable al mezclar herencia

from dataclasses import dataclass

# ❌ Con eq=True (por defecto) y sin frozen, __hash__ se pone a None.
@dataclass
class Item:
    id: str

# {Item("1")}   # TypeError: unhashable type: 'Item'

# ✅ Si necesitas hash, congela (frozen=True) o declara __hash__=None conscientemente.
@dataclass(frozen=True)
class Item:
    id: str

print({Item("1"), Item("1")})   # {Item(id='1')}  <- uno solo, son iguales

Esto es la regla de Python: «si defines __eq__, normalmente __hash__ se desactiva». La dataclass lo aplica de forma coherente: igualdad por valor → necesitas inmutabilidad para que el hash sea estable. Si el objeto va a cambiar y a la vez quieres igualdad por valor, no lo metas en un set ni lo uses como clave.

Olvidar que las anotaciones crean los campos

from dataclasses import dataclass

# ❌ Sin anotación, "borrowed" no es un campo: no se inicializa.
@dataclass
class Item:
    id: str
    borrowed = False          # esto NO es un campo (es una variable de clase)

# item = Item("1")
# print(item.borrowed)       # False, pero Item.__init__ no lo acepta:
# Item("1", True)             # TypeError: __init__() takes 2 positional arguments

# ✅ Anota el campo.
@dataclass
class Item:
    id: str
    borrowed: bool = False

8 · Reto

🎯 Un catálogo inmutable y hashable

Diseña una dataclass Snapshot que represente una foto inmutable del catálogo en un momento dado: un id, una timestamp (str) y un campo item_ids que contenga los ids de los ítems. Debe ser frozen=True y poder meterse en un set y compararse con <. Después responde: ¿por qué item_ids debe ser una tuple y no una list para que el frozen sea de verdad?

Pista: con frozen=True obtienes __hash__, pero si un campo es una lista, su hash no se puede calcular y set() fallará con TypeError: unhashable type: 'list'. Usa tuple. Y recuerda que order=True compara los campos en orden de declaración: elige el orden de campos pensando en cómo quieres ordenar. No resuelto aquí: decide también si incluir timestamp en la igualdad (compare=False) o no, y justifícalo.

9 · Resumen

  • @dataclass genera __init__, __repr__ y __eq__ a partir de las anotaciones de los campos.
  • Los campos con valor por defecto van después de los obligatorios (como en las funciones).
  • Los mutables usan field(default_factory=list); [] directo se comparte o se rechaza.
  • frozen=True impide reasignar y aporta __hash__, pero no congela el contenido de un mutable.
  • order=True genera los operadores de orden comparando campos en orden de declaración.
  • __post_init__ es el punto para validar/normalizar después del __init__ automático.
  • Una dataclass con __eq__ (por defecto) no es hashable salvo que sea frozen.

field(repr=False)Excluye un campo de la representación.
@dataclass(frozen=True)Inmutable y hashable (restringido a los enlaces, no al contenido).

10 · Preguntas frecuentes

¿Cuándo uso una dataclass y cuándo una clase normal?

Cuando la razón principal del objeto es contener datos (un ítem, una fila, un resultado, un DTO), la dataclass elimina el ruido y es la opción por defecto. Cuando la clase es sobre comportamiento y colaboradores —un servicio, una conexión, un parser con estado interno— una clase normal suele leerse mejor. Nada impide combinar: puedes usar @dataclass y añadir métodos y propiedades (lo hicimos con label).

¿frozen=True hace que el objeto sea inmutable de verdad?

Congela los enlaces: no puedes reasignar item.id = …. Pero si un campo apunta a un objeto mutable (una lista, un dict), ese objeto sigue siendo modificable por dentro (item.tags.append(...)). Inmutabilidad profunda requiere usar tipos inmutables (tuple, frozenset, dataclasses frozen anidadas). Es la misma distinción entre reasignar un nombre y mutar el objeto que viste en Módulo 1.

¿Por qué una dataclass normal no se puede meter en un set?

Porque @dataclass genera __eq__ y, por la regla de Python, definir __eq__ deja __hash__ a None (no hashable). La razón es que objetos mutables no pueden tener un hash estable: si cambia un campo, su hash cambiaría y rompería las tablas hash. Con frozen=True el objeto no muta, así que la dataclass vuelve a generar __hash__. Si necesitas hash, congela; si no, no los metas en set/dict.

¿order=True puede fallar con mis campos?

Sí. Genera comparaciones que aplican < campo a campo, y si algún campo no soporta orden (un dict, un objeto sin __lt__) lanzará TypeError al comparar. Solución: field(compare=False) para excluirlo, reordenar los campos según prioridad de comparación, o definir tus propios dunders (lección 5). Recuerda que el orden es posicional: compara el primer campo y, si empatan, el siguiente, igual que las tuplas.

¿__post_init__ puede cambiar el tipo de un campo?

Puede intentarlo, pero si la dataclass es frozen=True no podrá reasignar. Además, cambiar el tipo suele ser mala idea: rompe la promesa de la anotación. Lo habitual en __post_init__ es normalizar (quitar espacios, poner un valor por defecto derivado, calcular un campo auxiliar) y validar (lanzar ValueError/TypeError). Si necesitas una conversión real, hazla mejor en un @classmethod constructor alternativo. Y para validaciones complejas con tipos, en Módulo 7 verás la librería estándar typing y mypy, que avisan de tipos sin ejecutar.
