Módulos y paquetes

Módulo 4 · Módulos, paquetes y entornos ⏱ 30 minutos

1 · Introducción

Hasta ahora has escrito programas que caben en un fichero. Funciona… hasta que no: un script de 800 líneas mezcla la lectura de datos, las reglas de negocio y la interfaz de terminal, y cualquier cambio obliga a recorrerlo entero. En cuanto un proyecto crece, necesitas repartir el código en piezas con nombre propio que se puedan importar, reutilizar y testear por separado.

En el lenguaje de Python esas piezas son módulos (un fichero .py) y paquetes (una carpeta de módulos). En esta lección aprenderás cómo Python los encuentra, las formas de import, qué hace realmente __init__.py, cómo funcionan los imports relativos y por qué existe el idiomático if __name__ == "__main__":.

¿Por qué existe esta lección? Porque import no es una línea que se copia y se pega: es el mecanismo que da forma a todo el proyecto Biblioteca. Entender sys.path y __name__ explica de golpe por qué a veces «funciona al ejecutarlo pero falla al importarlo», el error más frustrante para quien empieza con paquetes.

Al terminar sabrás por qué en un proyecto real jamás se usa from modulo import *, por qué es mala idea llamar json.py a tu fichero, y cómo se conecta la POO del Módulo 5 con la estructura que verás aquí.

2 · Teoría

Un módulo es un fichero; un import es ejecutar ese fichero una vez

Cuando escribes import math, Python busca un fichero math.py (o un módulo compilado), lo ejecuta de arriba abajo una sola vez y guarda el resultado (sus funciones, clases y variables) en un objeto módulo. A partir de ahí, cada import posterior reutiliza esa copia: no se vuelve a ejecutar. Esto se ve clarísimo con un print a nivel de módulo.

# modulo_a.py — un módulo cualquiera
print("Ejecutando modulo_a")   # esto se ejecuta AL IMPORTAR, no al definir

def saludar(nombre):
    return f"Hola, {nombre}"

# main.py
import modulo_a       # imprime "Ejecutando modulo_a"
import modulo_a       # NO imprime otra vez: ya está en sys.modules

print(modulo_a.saludar("Ada"))

# Salida esperada (recuerda: solo se ejecuta la primera vez)
Ejecutando modulo_a
Hola, Ada

El «por qué» de este diseño es el rendimiento y la coherencia de estado: como un módulo se importa una sola vez, los objetos que define son uno solo compartido por todo el programa. Si un módulo guarda un contador, todas las partes que lo importan ven el mismo contador.

Las formas de importar (y cuál usar)

FormaQué haceCuándo usarla
import mathTrae el módulo completo, accedes con math.sqrtLa más clara y recomendada; no ensucia tu namespace
import math as mIgual, con un alias cortoCuando el nombre es largo o hay convención (import numpy as np)
from math import sqrtTrae solo el nombre sqrt a tu namespacePara nombres muy usados; cuidado con colisiones
from math import sqrt as raizTrae con aliasPara evitar colisiones o acortar
from math import *Trae todos los nombres públicosCasi nunca; contamina y oculta de dónde viene cada nombre

¿Por qué import * es peligroso? Porque rompe la legibilidad (no sabes si sqrt es tuyo o importado) y puede sobrescribir sin avisar algo que ya tenías. Además from x import * en un módulo dentro de un paquete puede saltarse __all__ si no está definido. El Zen de Python lo resume: «Explícito es mejor que implícito».

¿Dónde busca Python los módulos? sys.path

import no busca en «todo el ordenador»: recorre una lista ordenada de rutas llamada sys.path. El orden importa, porque gana la primera coincidencia:

sys.path (en orden de búsqueda)
+---------------------------------------------------------------+
| 1. El directorio del script que ejecutas (o el cwd con -m)    |
| 2. Las rutas de PYTHONPATH (variable de entorno, si existe)   |
| 3. Las rutas estándar de la instalación (stdlib)              |
| 4. Las rutas de site-packages (los paquetes instalados/pip)   |
+---------------------------------------------------------------+
                    ↓ gana la primera coincidencia

Puedes inspeccionar la lista real en tu máquina con python -c "import sys; print(*sys.path, sep='\n')": el primer elemento será tu directorio de trabajo actual.

Trampa clásica: si creas un fichero random.py en tu carpeta y luego haces import random, Python cargará tu fichero, no el de la stdlib, porque el directorio del script va primero. Ese es el motivo de que jamás debas llamar a tus módulos igual que un módulo estándar (json, math, logging, typing…).

Paquetes: carpetas con __init__.py

Un paquete es un directorio que agrupa módulos. La convención clásica es que contenga un fichero __init__.py. Ese fichero, que puede estar vacío, marca la carpeta como paquete y se ejecuta al importar el paquete. Sirve para tres cosas:

  • Declarar la interfaz pública del paquete (qué se importa desde fuera).
  • Ejecutar inicialización del paquete (registrar cosas, calcular constantes).
  • Definir __all__, la lista de nombres que exporta con from paquete import *.
biblioteca/                 <- paquete
├── __init__.py             <- se ejecuta al hacer "import biblioteca"
├── models.py               <- módulo "biblioteca.models"
├── store.py                <- módulo "biblioteca.store"
└── cli.py                  <- módulo "biblioteca.cli"

# biblioteca/__init__.py
"""Interfaz pública del paquete biblioteca."""
__version__ = "0.1.0"                  # metadato accesible como biblioteca.__version__

# Reexportamos lo más útil para que los usuarios escriban:
#   from biblioteca import Item
# en lugar de la ruta larga:
#   from biblioteca.models import Item
from biblioteca.models import Item

__all__ = ["Item", "__version__"]      # controla "from biblioteca import *"

Desde Python 3.3 existen los «namespace packages»: un paquete sin __init__.py también se puede importar. Pero para un proyecto propio conviene mantenerlo: deja explícita la intención y permite reexportar.

Imports absolutos y relativos

Un import absoluto parte del nombre completo: from biblioteca.service import add. Un import relativo parte de la posición del módulo actual usando puntos, y solo funciona dentro de un paquete:

# biblioteca/service.py

# Absoluto: claro, y no depende de dónde esté service.py
from biblioteca.models import Item
from biblioteca.store import load, save

# Relativo: un punto = paquete actual (biblioteca), dos = padre
from .models import Item          # equivale a biblioteca.models
from .store import load, save

¿Cuál usar? La guía oficial (PEP 8) recomienda absolutos en casi todo el código: se leen mejor y sobreviven a mover ficheros. Los relativos brillan cuando reorganizas un paquete grande o renombras el paquete entero, porque no repites su nombre en cada import.

__name__ == "__main__": el «doble uso» de un fichero

Cada módulo tiene una variable especial __name__. Si el fichero se importa, vale su nombre cualificado ("biblioteca.cli"). Si el fichero se ejecuta directamente, vale "__main__". Gracias a eso un mismo fichero puede servir como librería y como programa sin efectos colaterales al importarlo:

# biblioteca/cli.py
def main():
    print("Arrancando la CLI de Biblioteca")

if __name__ == "__main__":   # solo se cumple si ejecutas: python cli.py
    main()

Ejecutarlo como script imprime el mensaje; importarlo desde otro módulo no lo imprime. Ese es el «por qué»: separar «lo que define» de «lo que arranca».

3 · Ejemplo mínimo

Dos ficheros en la misma carpeta: un módulo con una función y un script que lo usa.

# saludos.py — el módulo
def saludar(nombre):
    """Devuelve un saludo cordial."""          # docstring: documentación viva
    return f"Hola, {nombre}"

# main.py — el programa
import saludos                                  # importa el módulo completo

mensaje = saludos.saludar("Grace")              # accede a la función con el prefijo
print(mensaje)

Ejecuta python main.py. Qué ocurre línea a línea:

  1. import saludos: Python busca saludos.py en sys.path. El directorio de main.py está primero, así que lo encuentra, lo ejecuta y crea el objeto módulo.
  2. saludos.saludar(...): accedes a la función definida dentro. El prefijo saludos. deja claro de dónde sale.
  3. print(mensaje): muestra el resultado.
# Salida esperada
Hola, Grace

4 · Ejemplo real

En el proyecto Biblioteca vamos a separar responsabilidades en varios módulos dentro de un paquete. Observa cómo cli.py consume las otras piezas mediante imports absolutos:

proyecto/
└── biblioteca/
    ├── __init__.py      # reexporta Item y __version__
    ├── models.py        # Item (aún un dict en este módulo; será dataclass en M5)
    ├── store.py         # lectura/escritura de data/library.json
    └── cli.py           # punto de entrada; importa models y store

# biblioteca/models.py
"""Modelo de datos del catálogo."""
from dataclasses import dataclass                  # en M5 lo convertiremos en dataclass

@dataclass
class Item:
    """Un ítem del catálogo: libro o película."""
    id: str
    title: str
    kind: str            # "book" o "movie"
    year: int | None = None
    borrowed: bool = False

# biblioteca/store.py
"""Persistencia simple en memoria (en M6 será JSON real)."""
from biblioteca.models import Item                 # import ABSOLUTO: robusto

def load() -> list[Item]:
    """Devuelve el catálogo vacío listo para usar."""
    return []

# biblioteca/cli.py
"""CLI de Biblioteca (versión mínima)."""
from biblioteca.models import Item
from biblioteca.store import load

def main() -> None:
    store = load()                                  # lista vacía
    # Añadimos un ítem para demostrar que los imports funcionan en cadena
    store.append(Item(id="it_9f3a1c7b", title="1984", kind="book", year=1949))
    print(f"Catálogo: {len(store)} ítem(s)")       # len() de la lista

if __name__ == "__main__":                          # se ejecuta solo como script
    main()

# Para ejecutarlo hay que hacerlo desde la carpeta que CONTIENE el paquete
python -m biblioteca.cli

# Salida esperada
Catálogo: 1 ítem(s)

Decisión clave: import biblioteca.models usa la ruta absoluta desde la raíz del paquete. Así, da igual dónde esté el fichero cli.py: el import sigue apuntando al mismo sitio. En la lección siguiente verás cómo pyproject.toml y el layout src/ hacen que esa raíz esté siempre en sys.path.

6 · Errores habituales

Nombrar un módulo como uno de la stdlib

# ❌ Si creas un fichero "json.py" en la carpeta del script...
import json            # Python carga TU json.py, no el de la stdlib
print(json.dumps({"a": 1}))   # AttributeError: module 'json' has no attribute 'dumps'

# Salida esperada
AttributeError: module 'json' has no attribute 'dumps'

# ✅ Renombra el fichero a algo que no choque
# json_utils.py
import json            # ahora sí, el de la stdlib
print(json.dumps({"a": 1}))

Import circular

# ❌ a.py importa b.py y b.py importa a.py
# a.py
import b
def f(): return b.g()
# b.py
import a
def g(): return a.f()

Al ejecutar cualquiera, Python empieza a cargar a, intenta cargar b, que a su vez pide a… y encuentra un módulo a medio construir: ImportError: cannot import name ... from partially initialized module. La salida es romper el ciclo: extraer lo compartido a un tercer módulo (common.py) o importar dentro de la función que lo usa si de verdad es puntual.

Ejecutar un fichero de un paquete por ruta

# ❌ Ejecutar el fichero directamente rompe los imports absolutos
python biblioteca/cli.py
# ModuleNotFoundError: No module named 'biblioteca'

# ✅ Ejecuta el paquete indicando qué módulo, desde la carpeta padre
python -m biblioteca.cli

Al hacerlo por ruta, lo primero en sys.path es la carpeta biblioteca/, no su padre, así que «biblioteca» no se encuentra a sí misma. Con -m añades el directorio actual a sys.path y el paquete queda visible.

# Reexportamos para que se pueda usar "from saludos import saludar"

8 · Reto

🎯 Subpaquete y __all__

Amplía el paquete saludos con un subpaquete saludos/idiomas/ que contenga es.py, en.py y su propio __init__.py. Cada uno debe exponer una función saludar(nombre) en su idioma. Desde saludos/__init__.py, reexporta saludar en español y expón además un diccionario IDIOMAS. Define __all__ para que un from saludos import * traiga solo lo que tú decidas.

Pista: usa imports absolutos como from saludos.idiomas import es. Para comprobar __all__, en una sesión de REPL escribe from saludos import * y luego dir() para ver qué nombres llegaron.

9 · Resumen

  • Un módulo es un fichero .py; un paquete es una carpeta de módulos con __init__.py.
  • import ejecuta el módulo una sola vez y guarda el resultado en sys.modules.
  • Python busca los módulos en sys.path, en orden; el directorio del script va primero.
  • Prefiere imports absolutos; reserva import * para casos excepcionales.
  • if __name__ == "__main__": separa «definir» de «arrancar».
  • Nunca nombres un módulo igual que uno de la stdlib.
ConceptoPara qué sirve
import moduloTraer un módulo y acceder vía modulo.nombre
__init__.pyMarcar el paquete, inicializarlo y reexportar su API pública
sys.pathLista ordenada de dónde se buscan los módulos
__name__Saber si el módulo se ejecuta ("__main__") o se importa
__all__Controlar qué exporta from paquete import *

10 · Preguntas frecuentes

¿Qué diferencia hay entre un módulo y un paquete?

Un módulo es un único fichero .py. Un paquete es una carpeta que agrupa varios módulos (y subpaquetes). Un paquete es, en cierto modo, un módulo más: se importa igual y puede tener su propio __init__.py con código.

¿__init__.py puede quedar vacío?

Sí. En muchas librerías está vacío o solo tiene la versión y los reexports. Estar vacío ya cumple su función de marcar el directorio como paquete y hacerlo encontrable de la forma clásica.

¿Por qué a veces funciona al ejecutar y falla al importar?

Porque cambia el punto de entrada a sys.path. Al ejecutar un fichero, su carpeta va primera; al importar desde otro sitio, manda la raíz del proyecto. Los imports absolutos bien definidos evitan esa asimetría.

¿Qué pasa si el mismo módulo se importa desde dos sitios distintos?

Python lo ejecuta una sola vez y comparte el mismo objeto módulo. Por eso el estado a nivel de módulo (contadores, caches) es global y compartido, y por eso importar tiene efectos solo la primera vez.
