pyproject.toml y estructura de proyecto

Módulo 4 · Módulos, paquetes y entornos ⏱ 35 minutos

1 · Introducción

En la lección anterior viste que un paquete es una carpeta de módulos. Pero, ¿cómo sabe una herramienta que tu proyecto se llama biblioteca, que necesita Python 3.12 o superior, qué dependencias tiene y cómo se instala? Antiguamente eso se repartía entre setup.py, setup.cfg y requirements.txt. Hoy existe un único fichero estándar: pyproject.toml.

En esta lección entenderás por qué se adoptó este formato (PEP 518, 517 y 621), qué significa cada bloque de metadatos, por qué el layout src/ es el recomendado para librerías y cómo se ve todo aplicado al proyecto Biblioteca.

¿Por qué existe esta lección? Porque pyproject.toml es la tarjeta de identidad de tu proyecto: sin él no puedes instalarlo como paquete, ni declarar dependencias, ni publicar en PyPI. Es también donde se define el comando bib que usarás en la última lección del módulo.

2 · Teoría

¿Qué es TOML y por qué lo eligieron?

TOML («Tom's Obvious Minimal Language») es un formato de configuración legible por humanos, con secciones [entre_corchetes] y pares clave = valor. Se eligió sobre YAML o JSON porque es sencillo, no depende de la indentación (a diferencia de YAML) y tiene tipos claros: strings, enteros, booleanos, listas y tablas. Python trae soporte de lectura en la stdlib con tomllib (3.11+).

# Un mini-TOML para ver la sintaxis
name = "biblioteca"            # string
version = "0.1.0"             # string
requires-python = ">=3.12"     # comparador de versión
dependencies = [               # lista de strings
    "requests>=2.31",
]

[project.urls]                 # tabla (subsección)
Homepage = "https://example.com"

Qué problemas resuelve pyproject.toml

  • Un solo fichero: metadatos, dependencias y configuración de herramientas (pytest, ruff, mypy) en el mismo sitio.
  • Declarar el backend de construcción: quién sabe convertir tu código en un paquete instalable.
  • Reproducibilidad: cualquiera que lea el fichero sabe con qué Python y qué versiones funciona tu código.
  • Estándar: es el formato que entienden pip, uv, build y todas las herramientas modernas.

Analogía: si tu proyecto fuese un producto en una tienda, pyproject.toml es la etiqueta con ingredientes, fecha de caducidad, modo de uso y fabricante. setup.py era una etiqueta escrita a mano donde cada fabricante inventaba su formato.

Anatomía de un pyproject.toml

Hay dos bloques indispensables y varios opcionales:

BloqueQué declaraObligatorio
[build-system]El backend que construye/instala el paquete y sus requisitosSí (para instalar como paquete)
[project]Metadatos: nombre, versión, descripción, dependencias…Sí
[project.scripts]Comandos de consola que instala el paquete (p. ej. bib)No
[project.optional-dependencies]Dependencias extras agrupadas (dev, docs…)No
[dependency-groups]Grupos de dependencias de desarrollo (PEP 735, usado por uv)No
[tool.*]Configuración de herramientas: [tool.pytest.ini_options], [tool.ruff]…No

El bloque [build-system] nombra el build backend. El más extendido es hatchling; otros son setuptools (el clásico), flit_core o pdm-backend. El «por qué» de separarlo es que pyproject.toml es un formato estándar, pero construir un paquete necesita lógica concreta: ese trabajo lo delega en el backend.

Layout plano vs layout src/

Hay dos formas de colocar tu paquete dentro del proyecto:

LAYOUT PLANO                     LAYOUT src/ (recomendado)
proyecto/                        proyecto/
├── biblioteca/                  ├── src/
│   ├── __init__.py              │   └── biblioteca/
│   └── cli.py                   │       ├── __init__.py
├── tests/                       │       └── cli.py
└── pyproject.toml               ├── tests/
                                 └── pyproject.toml

¿Por qué src/? Porque evita un error silencioso muy común: con el layout plano, el directorio del proyecto está en sys.path, así que import biblioteca carga el código tal cual está en tu carpeta, sin pasar por el proceso de instalación. Puedes tener imports rotos y no notarlo hasta publicar. Con src/, la única forma de importar es tener el paquete instalado (aunque sea en modo editable), que es exactamente lo que hará un usuario final. Es la razón por la que es el estándar en librerías serias.

Instalación editable

Durante el desarrollo no quieres reinstalar cada vez que cambias una línea. Para eso existe la instalación editable (-e): crea un enlace al código fuente en lugar de copiarlo.

# Instala el proyecto en modo editable: los cambios se ven al instante
python -m pip install -e .

# Con uv (lo verás a fondo en la lección 04)
uv pip install -e .

Lee el pyproject.toml desde Python: como tomllib está en la stdlib, puedes parsear el fichero sin dependencias. Recuerda que tomllib solo lee; para escribir TOML necesitarías otra librería, y por eso las herramientas lo editan por ti.

3 · Ejemplo mínimo

El pyproject.toml más pequeño posible para un proyecto instalable. Fíjate en que cada campo responde a una pregunta sobre el paquete.

[build-system]
# Backend que sabe construir el paquete. hatchling es moderno y sin configuración extra.
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "saludos"                 # nombre del paquete en PyPI (normalmente en minúsculas)
version = "0.1.0"                # versión actual (semántica: MAYOR.MENOR.PARCHE)
description = "Paquete de ejemplo del curso"
readme = "README.md"             # fichero que se muestra en PyPI
requires-python = ">=3.12"       # versión mínima de Python
dependencies = []                # sin dependencias externas: solo stdlib

[project.scripts]
# Crea un comando de consola "saludo" que ejecuta la función main
saludo = "saludos.cli:main"

Qué significa cada pieza:

  1. [build-system]: cuando alguien instala tu proyecto, pip descarga hatchling y le pide que construya el paquete a partir de src/ o del paquete.
  2. [project]: los metadatos que verás en PyPI y que las herramientas usan para resolver dependencias.
  3. [project.scripts]: genera un ejecutable saludo en el bin/ del entorno, cuya entrada es main() del módulo saludos.cli.

4 · Ejemplo real

Así se ve el proyecto Biblioteca completo con layout src/. Este es el árbol que iremos llenando a lo largo del curso:

biblioteca/
├── pyproject.toml          # identidad, dependencias y comando "bib"
├── README.md               # cómo instalar y usar
├── src/
│   └── biblioteca/
│       ├── __init__.py     # reexporta la API pública y __version__
│       ├── models.py       # dataclasses Item/Book/Movie (M5)
│       ├── store.py        # persistencia JSON (M6)
│       ├── service.py      # reglas: add/list/search/borrow/return
│       └── cli.py          # CLI con argparse (lección 05)
├── tests/                  # pytest (M7)
├── data/library.json       # almacén de ejemplo
└── schema/library.schema.json

# pyproject.toml — proyecto Biblioteca
[build-system]
# Hatchling sabe dónde está el código y genera la distribución sin setup.py
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "biblioteca"
version = "0.1.0"
description = "Catálogo personal de libros y películas con CLI"
readme = "README.md"
requires-python = ">=3.12"          # usamos tomllib, match/case, type hints modernos
license = { text = "MIT" }
authors = [
    { name = "Ada Lovelace", email = "ada@example.com" },
]
# Dependencias de EJECUCIÓN del paquete.
# Sintaxis: "nombre" o "nombre>=version" (un comparador de versión PEP 440).
dependencies = [
    "platformdirs>=4.0",            # para localizar la carpeta de datos del usuario
]

# Comando de consola: tras instalar, "bib" llama a biblioteca.cli:main
[project.scripts]
bib = "biblioteca.cli:main"

# Extras opcionales: se instalan con  pip install "biblioteca[dev]"
[project.optional-dependencies]
dev = [
    "pytest>=8.0",
    "mypy>=1.10",
    "ruff>=0.6",
]

[project.urls]
Homepage = "https://github.com/example/biblioteca"

# Configuración de herramientas en el mismo fichero
[tool.pytest.ini_options]
testpaths = ["tests"]

Decisiones que merecen explicación:

  • requires-python = ">=3.12": el instalador rechazará el paquete en versiones antiguas en vez de fallar en tiempo de ejecución. Mejor fallar pronto y claro.
  • dependencies: solo lo que necesita el paquete para funcionar. pytest y ruff no van aquí: van en [project.optional-dependencies].dev, porque un usuario final no los necesita.
  • [project.scripts]: convierte una función Python en un comando de terminal sin que el usuario escriba python -m ....

Mira la documentación oficial en packaging.python.org para la lista completa de campos de [project]. Es la especificación que implementan todas las herramientas, así que es la fuente que nunca se queda desfasada.

6 · Errores habituales

Creer que el nombre del paquete es libre

# ❌ El nombre del proyecto NO tiene por qué ser el de la carpeta del paquete
[project]
name = "Mi Biblioteca"          # espacios y mayúsculas: problemático

El nombre del proyecto (el que se publica) admite guiones, pero el nombre del paquete importable debe ser un identificador Python válido. Convención: proyecto mi-biblioteca, paquete mi_biblioteca (guion → guion bajo). Mantén ambos coherentes.

Poner [tool.*] fuera de sitio

# ❌ Un bloque mal anidado no se aplica (ni avisa)
[project]
name = "biblioteca"
tool.pytest.ini_options = { testpaths = ["tests"] }   # mezcla inválida de estilos

# ✅ Cada herramienta en su tabla anidada
[tool.pytest.ini_options]
testpaths = ["tests"]

Usar la ruta del módulo en lugar del paquete

# ❌ La ruta incluye "src/" y el import falla
[project.scripts]
bib = "src.biblioteca.cli:main"

# ✅ La ruta es la del import real, sin src (src es solo el directorio fuente)
[project.scripts]
bib = "biblioteca.cli:main"

Confundir dependencies con requirements.txt

[project] dependencies declara qué necesita tu paquete, con rangos de versión flexibles. Un requirements.txt congelado (lo verás en la siguiente lección) fija versiones exactas de un entorno concreto. Mezclar ambos conceptos hace que el paquete sea imposible de reutilizar. Regla: rango en pyproject.toml, congelado para reproducir un entorno.

7 · Ejercicio guiado

Objetivo: crear un proyecto con layout src/, validar que el pyproject.toml es correcto, instalarlo en editable y ejecutar su comando de consola.

  1. Paso 1: crea esta estructura: 
    saludos/
├── pyproject.toml
├── README.md
└── src/
    └── saludos/
        ├── __init__.py
        └── cli.py
  2. Paso 2: escribe el comando de consola: 
    # src/saludos/cli.py
def main() -> None:
    """Punto de entrada del comando 'saludo'."""
    print("Hola desde el comando saludo")

if __name__ == "__main__":
    main()
  3. Paso 3: escribe el pyproject.toml: 
    [build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "saludos"
version = "0.1.0"
description = "Paquete de ejemplo con CLI"
readme = "README.md"
requires-python = ">=3.12"
dependencies = []

[project.scripts]
saludo = "saludos.cli:main"
  4. Paso 4: valida el TOML sin instalar nada, usando la stdlib: 
    python -c "import tomllib; print(tomllib.load(open('pyproject.toml','rb'))['project']['name'])"

    # Salida esperada
saludos
  5. Paso 5: crea un entorno virtual e instálalo en editable (en la próxima lección verás el detalle de venv): 
    python -m venv .venv            # crea el entorno (Linux/macOS)
source .venv/bin/activate       # actívalo (bash)
python -m pip install -e .      # instala el proyecto en modo editable
saludo                          # ejecuta el comando declarado
  6. Paso 6 (verificación): la salida esperada es: 
    Hola desde el comando saludo
    Si además ejecutas python -m saludos.cli, verás el mismo mensaje: el comando saludo y el módulo apuntan a la misma función main.

8 · Reto

🎯 Un comando con argumentos y metadatos completos

Amplía el proyecto saludos: añade el campo authors, un [project.urls] y una dependencia de ejecución ficticia. Después crea un segundo módulo saludos/core.py con una función saludar(nombre) y haz que cli.py la use para saludar a un nombre que reciba de sys.argv. Declara un segundo comando de consola llamado saludo-largo que apunte a una función distinta.

Pista: un módulo solo puede aportar varias entradas de consola si defines funciones separadas en [project.scripts]. Para validar que tu TOML sigue siendo correcto, vuelve a usar tomllib.load y recorre data["project"]["scripts"]. No uses ninguna librería externa: la validación es con la stdlib.

9 · Resumen

  • pyproject.toml es el estándar único para metadatos, dependencias y configuración de herramientas (PEP 621).
  • [build-system] nombra el backend (hatchling) que construye el paquete.
  • [project] declara nombre, versión, requires-python y dependencies.
  • El layout src/ obliga a probar el paquete instalado y evita imports fantasma.
  • La instalación editable (pip install -e .) enlaza el código fuente durante el desarrollo.
  • [project.scripts] crea comandos de consola como bib.
Clave / bloquePara qué sirve
[build-system]Elegir el backend que empaqueta e instala
name / versionIdentidad y versión del proyecto
requires-pythonVersión mínima/máxima de Python compatible
dependenciesPaquetes necesarios en tiempo de ejecución
[project.scripts]Comandos de terminal instalados con el paquete
[tool.*]Configuración de pytest, ruff, mypy… en el mismo fichero

10 · Preguntas frecuentes

¿pyproject.toml sustituye a requirements.txt?

No exactamente: cubren necesidades distintas. pyproject.toml declara las dependencias del proyecto con rangos. Un requirements.txt congelado fija las versiones exactas de un entorno concreto para reproducirlo. Muchos proyectos usan ambos: rangos en pyproject.toml, congelado para desplegar.

¿Tengo que usar src/ obligatoriamente?

No es obligatorio, pero es la recomendación para librerías y paquetes publicables. Para un script pequeño o un proyecto de datos, el layout plano es aceptable. En este curso usamos src/ porque Biblioteca es un paquete real y queremos detectar imports rotos antes de publicar.

¿Qué backend de construcción elijo?

Cualquiera de los modernos funciona. hatchling es una elección común y sin fricción para proyectos que siguen las convenciones. setuptools es el clásico y tiene más historia. Lo importante es declarar [build-system]; el formato de [project] es el mismo para todos.

¿Por qué tomllib solo lee y no escribe?

Por decisión de la comunidad: escribir TOML requiere conservar comentarios y formato, algo complejo de hacer bien. Para escribir se usan herramientas externas (como tomlkit) o, mejor aún, dejas que pip/uv editen las dependencias por ti.

¿Cómo indico que mi paquete necesita solo Python, sin dependencias?

Dejando dependencies = [] (una lista vacía). Es perfectamente válido y recomendable: cuanto menos dependas de terceros, menos cosas pueden romperse. En este curso priorizamos siempre la biblioteca estándar.
