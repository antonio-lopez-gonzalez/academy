Qué es Python

Módulo 0 · Preparación ⏱ 30 minutos

1 · Introducción

Si ya programas en JavaScript, C#, Java o Go, sabes qué es un lenguaje de programación. Entonces, ¿por qué una lección entera para «qué es Python»? Porque Python esconde una decisión de diseño que explica casi todo lo demás: no se compila a código máquina de antemano, sino a un formato intermedio que ejecuta una máquina virtual. Entender ese detalle es la diferencia entre memorizar sintaxis y comprender por qué Python se comporta como se comporta.

En esta lección verás qué es realmente un intérprete frente a un compilador, qué papel juega CPython (la implementación de referencia), qué es el bytecode que aparece en __pycache__, dónde se usa Python hoy y por qué merece la pena aprenderlo en su versión 3.12+. Todo con el ojo puesto en la meta del curso: escribir Python idiomático, testeado y empaquetable.

¿Por qué existe esta lección? Porque el resto del curso asume que entiendes el modelo de ejecución. Cuando en el módulo 7 depures pytest, en el módulo 8 hables del GIL o en el módulo 9 empaquetes un .whl, todo encaja antes si sabes cómo se ejecuta Python. Esta lección es el mapa del terreno.

Para quien ya programa: no vamos a explicar qué es una variable ni qué es un bucle. Vamos a explicar por qué Python tomó las decisiones que tomó y cómo se comparan con las de tu lenguaje de siempre.

2 · Teoría

Intérprete vs. compilador: la dicotomía es falsa

Solemos decir «Python es interpretado» y «C es compilado». Es una simplificación útil, pero imprecisa. Un compilador traduce el código fuente completo a otro lenguaje (normalmente código máquina) antes de ejecutarlo. Un intérprete lee el código y lo ejecuta mientras lo recorre. La verdad es que Python hace las dos cosas:

  1. Compila tu .py a un formato intermedio llamado bytecode (instrucciones para una máquina imaginaria, no para tu CPU real).
  2. Interpreta ese bytecode con la Python Virtual Machine (PVM), que sí corre en tu CPU.
   script.py          COMPILADOR              BYTECODE            PVM
   (tu código)        (fase de compilación)   (instrucciones)     (ejecuta)
  +-----------+      +--------------+        +-----------+      +-----------+
  | print(1)  | ---> |  analiza y   | ---->  | LOAD 1    | ---> | interpreta|
  | x = 1 + 1 |      |  traduce a   |        | BINARY_ADD|      | y produce |
  |           |      |  bytecode    |        | PRINT     |      | el efecto |
  +-----------+      +--------------+        +-----------+      +-----------+
                                                            (aquí ocurre tu salida)

Analogía: el bytecode es como una partitura musical. El compositor (compilador) escribe la partitura una vez; el intérprete (la orquesta) la toca. No es código máquina, pero tampoco es texto libre: es un formato que solo un contexto concreto sabe ejecutar.

CPython: la implementación de referencia

Cuando escribes python en la terminal, casi siempre ejecutas CPython: la implementación oficial del lenguaje, escrita en C, mantenida por la Python Software Foundation. Existen otras implementaciones, pero para este curso CPython = Python:

¿Qué es el bytecode y por qué existe __pycache__?

Compilar a bytecode cuesta tiempo. Como el código de un módulo no cambia entre ejecuciones, CPython guarda el bytecode en disco para reutilizarlo. Ese es el único motivo por el que aparece una carpeta __pycache__ con archivos .pyc: es caché, no código que debas versionar ni editar.

  biblioteca/
  ├── service.py          <- tu código fuente (lo que editas)
  └── __pycache__/
      └── service.cpython-312.pyc   <- bytecode cacheado (autogenerado)

La primera vez que importas service, CPython compila y escribe el .pyc. Las siguientes veces compara fechas y versiones: si nada cambió, se salta la compilación. Por eso el bytecode no es portable entre versiones de Python (el nombre incluye cpython-312).

La filosofía: import this

Python no es solo una sintaxis; es un conjunto de valores estéticos recogidos en el Zen of Python. Se lee ejecutando import this. Estas son las ideas que de verdad guían el curso:

  • «Bello es mejor que feo» y «explícito es mejor que implícito»: código que se lee como pseudocódigo, sin magia.
  • «Simple es mejor que complejo» y «legible cuenta»: la legibilidad es un requisito, no un lujo.
  • «Los errores nunca deberían pasar silenciosamente»: base de la lección de excepciones (módulo 6).
  • «Debería haber una —y preferiblemente solo una— manera obvia de hacerlo»: por eso existe lo «pythonico».

Por qué ahora y por qué 3.12+

Python moderno ya no es el «lenguaje lento de scripts». Las versiones 3.11, 3.12 y 3.13 trajeron el intérprete adaptativo especializante (más rápido), mensajes de error mucho más claros, y la posibilidad de desactivar el GIL (PEP 703, experimental). Además, el lenguaje moderno incluye f-strings, match/case, anotaciones de tipo (list[str], X | None) y tomllib. Este curso fija 3.12+ y usa todo eso desde el principio.

3 · Ejemplo mínimo

El programa más pequeño que demuestra tres cosas: que Python ejecuta, que todo es un objeto y que el lenguaje se documenta a sí mismo.

# hello.py — el clásico. Fíjate: print es una FUNCIÓN (lleva paréntesis).
print("Hola, Python")            # imprime y añade un salto de línea

# sys es un MÓDULO de la biblioteca estándar; version trae la versión del intérprete.
import sys
print(sys.version)               # p. ej. 3.12.4 (main, ...)
print(sys.implementation.name)   # 'cpython': confirma la implementación de referencia

Salida esperada (la versión y la fecha exactas dependerán de tu instalación):

Hola, Python
3.12.4 (main, Jun  6 2024, 03:00:00) [GCC 13.2.0]
cpython

Línea por línea:

  1. print("Hola, Python"): en Python 3, print es una función normal, no una sentencia como en Python 2. Ahí dentro va cualquier objeto.
  2. import sys: los módulos son la forma de organizar código; sys expone detalles del intérprete.
  3. sys.version: una cadena con la versión y la plataforma. La usarás para diagnosticar entornos.
  4. sys.implementation.name: 'cpython' te confirma que no es PyPy ni otra implementación.

4 · Ejemplo real

En este curso construiremos Biblioteca: un catálogo de libros y películas con una CLI llamada bib. Antes de tener clases o ficheros JSON (módulos 5 y 6), el modelo más primitivo es una lista de diccionarios. Así se ve un «ítem» del catálogo en Python puro:

# catalog_v0.py — primer modelo de un ítem, sin clases todavía.
# Un diccionario asocia claves (str) con valores de cualquier tipo.
item = {
    "id": "b-001",            # identificador estable y legible
    "title": "1984",          # texto
    "kind": "book",           # 'book' o 'movie' (más adelante un Enum)
    "year": 1949,             # entero o None si no se conoce
    "borrowed": False,        # booleano: ¿está prestado?
}

# Fíjate en esta línea: crea una etiqueta legible sin concatenar strings.
print(f"{item['title']} ({item['year']}) — prestado: {item['borrowed']}")
print(f"¿Es un libro? {item['kind'] == 'book'}")

Salida esperada:

1984 (1949) — prestado: False
¿Es un libro? True

Decisiones y porqués:

  • kind en vez de dos campos (is_book, is_movie): un único campo describe el tipo y evita estados imposibles («libro y película a la vez»).
  • year: int | None: no todos los ítems tienen año conocido; None representa «desconocido» de forma explícita.
  • f-string: en lugar de + entre cadenas, insertamos valores dentro del texto. Es lo idiomático en 3.12+.
  • Los identificadores van en inglés (title, borrowed); la prosa y los comentarios, en español.

Este diccionario irá creciendo: en el módulo 1 le sumaremos listas, en el 5 lo convertiremos en una @dataclass y en el 6 lo persistiremos en data/library.json. Todo apunta al mismo sistema.

6 · Errores habituales

Creer que «interpretado» significa «sin compilación»

# ❌ ERROR conceptual: "Python no compila, por eso es lento"
# Python SÍ compila: primero a bytecode, y luego el intérprete lo ejecuta.
# La lentitud (histórica) viene de interpretar el bytecode, no de la ausencia
# de compilación. Desde 3.11 el intérprete se especializa y acelera.

# ✅ Comprobación: el bytecode existe y está en disco
import dis
def add(a, b):
    return a + b
dis.dis(add)   # desensambla la función a sus instrucciones bytecode

Manejar que CPython es «el» lenguaje

# ❌ "Python" no es solo CPython; PyPy, MicroPython, etc. siguen la misma
#    especificación del lenguaje pero NO son intercambiables en todo.

# ✅ Comprueba siempre qué implementación tienes delante
python -c "import sys; print(sys.implementation.name, sys.version)"

Confundir python con python3 (y con py)

# ❌ En algunos Linux, 'python' no existe o apunta a Python 2 (antiguo).
# python --version      # puede fallar o dar 2.7

# ✅ Usa el nombre correcto según el sistema (lección 2)
python3 --version     # Linux / macOS
py --version          # Windows (Python Launcher)

Suponer que todo el código está en UTF-8 sin comprobarlo

# ❌ Guardar el archivo en Latin-1 y esperar que los acentos salgan bien
# name = "Muñoz"   # si el archivo NO está en UTF-8, dará UnicodeDecodeError

# ✅ Python 3 asume UTF-8 por defecto para el código fuente.
#    Guarda siempre tus .py en UTF-8 (lo hace VSCode) y no tendrás sorpresas.
name = "Muñoz"
print(len(name))   # 5 caracteres, no 6 bytes

Creer que Python es solo para scripts desechables

# ❌ "Python no sirve para proyectos grandes"
# Falso: tiene empaquetado (pyproject.toml), tests (pytest), tipado (mypy),
# linters (ruff) y hasta su propio gestor moderno (uv). Lo verás de M4 a M9.

# ✅ Este curso termina con un paquete instalable con entrada de consola:
# uv build && pip install dist/*.whl && bib list

7 · Ejercicio guiado

Objetivo: confirmar que tu intérprete es CPython 3.12+ y ver la filosofía del lenguaje con tus propios ojos.

  1. Paso 1: abre una terminal y comprueba la versión (usa el comando de tu sistema): 
    python3 --version     # Linux / macOS
py --version          # Windows

    Resultado esperado: Python 3.12.x o superior. Si sale una versión menor, instala 3.12+ (lección 2).

  2. Paso 2: confirma la implementación y la plataforma: 
    python3 -c "import sys; print(sys.implementation.name, sys.version_info[:3])"

    Salida esperada (ejemplo): cpython (3, 12, 4). Si el nombre no es cpython, estás ante otra implementación; el curso asume CPython.

  3. Paso 3: lee el Zen of Python: 
    python3 -c "import this"

    Salida esperada: los 19 aforismos, empezando por «Beautiful is better than ugly». Léelos despacio: cada uno justifica una regla que aplicarás en este curso.

  4. Paso 4: crea hello.py con el ejemplo mínimo y ejecútalo: 
    python3 hello.py

    Salida esperada: Hola, Python seguido de la versión y cpython.

  5. Paso 5 (verificación): tras ejecutar hello.py, comprueba que aún no hay __pycache__ en la carpeta. Es normal: el bytecode cacheado aparece al importar módulos, no al ejecutar el script principal (lo verás en la lección 3).

8 · Reto

🎯 Desensambla tu propio código

Crea un script que defina una función price_with_tax(price, rate) que devuelva price * (1 + rate). Después usa el módulo dis para volcar su bytecode (dis.dis(price_with_tax)) e identifica al menos tres instrucciones y qué crees que hacen. Explica en dos o tres frases por qué el bytecode no es código máquina.

Pista: verás instrucciones como LOAD_FAST (cargar una variable local), BINARY_OP (operar) y RETURN_VALUE (devolver). Que sean «abstractas» y no registros de CPU concretos es justo la razón por la que Python puede correr en arquitecturas distintas sin recompilar.

9 · Resumen

  • Python compila a bytecode y luego lo interpreta con su máquina virtual: no es puramente interpretado ni puramente compilado.
  • CPython es la implementación de referencia y la que usarás; sys.implementation.name lo confirma.
  • El bytecode se cachea en __pycache__/*.pyc, atado a la versión de Python; no se versiona.
  • El Zen of Python (import this) resume los valores del lenguaje: legibilidad, simplicidad, explicitud.
  • Python brilla en datos, IA, automatización, backend y herramientas; el foco del curso es escribirlo como ingeniería, no como script suelto.
  • La versión del curso es 3.12+: f-strings, match/case, hints modernos y un intérprete más rápido.

10 · Preguntas frecuentes

Si Python compila a bytecode, ¿por qué lo llamamos «interpretado»?

Por costumbre histórica y porque la compilación no produce código máquina. A diferencia de C, el resultado no se ejecuta directamente: hace falta la máquina virtual de Python para interpretarlo. Java vive una situación parecida (compila a bytecode para la JVM), pero con tipado estático y un JIT más maduro.

¿Python es lento de verdad?

Para bucles con mucha aritmética pura puede ser más lento que C o Go. Pero la mayor parte del tiempo el cuello de botella no es Python: es una librería en C (NumPy) o la red. Además, el intérprete especializante de 3.11+ mejoró bastante el rendimiento. Escribe primero claro, mide después, optimiza solo si hace falta.

¿Por qué no compilar directamente a código máquina como Go?

Porque la portabilidad y la flexibilidad importan más que la velocidad bruta en el nicho de Python. Un mismo .py corre en Windows, macOS, Linux y hasta microcontroladores (MicroPython). El bytecode es el contrato portable entre tu código y cada plataforma.

¿Qué pasa si borro la carpeta __pycache__?

Nada grave: Python la regenerará la próxima vez que importe esos módulos. Es caché. Por eso no se versiona. Solo ten cuidado de no confundir un .pyc antiguo con el comportamiento de un .py recién editado: si dudas, bórrala; Python la reconstruye.

¿Necesito instalar Anaconda/conda para aprender Python?

No. En este curso usamos Python oficial + venv/uv (módulo 4). Conda es útil en ciencia de datos con dependencias binarias complejas, pero no es requisito y añade capas que conviene entender antes de usar.
