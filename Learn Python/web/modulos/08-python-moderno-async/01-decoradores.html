Decoradores

Módulo 8 · Python moderno y asincronía ⏱ 35 minutos

1 · Introducción

Imagina que quieres medir el tiempo que tarda una función, cachear su resultado o validar sus argumentos. Si lo haces copiando el mismo bloque al principio y al final de cada función, tienes la lógica de negocio enterrada bajo ruido repetido. Los decoradores resuelven exactamente eso: envuelven una función con comportamiento extra sin tocar su cuerpo.

En esta lección entenderás por qué los decoradores existen: porque en Python las funciones son objetos de primera clase (se pasan como argumento y se devuelven como resultado, Módulo 2). Un decorador no es magia nueva, es solo una función que recibe una función y devuelve otra. Verás functools.wraps, decoradores con argumentos, y los casos reales que de verdad usarás: timing, cache y validación en la CLI bib.

¿Por qué aprenderlos a fondo? Porque ya los usas sin saberlo: @dataclass, @property, @staticmethod, @pytest.fixture, @functools.lru_cache. Si entiendes el mecanismo, dejas de memorizar decoradores ajenos y empiezas a escribir los tuyos —que es cuando se vuelven una herramienta real y no una caja negra.

2 · Teoría

Funciones que devuelven funciones

En Python una función es un objeto como cualquier otro: tiene atributos (__name__, __doc__) y se puede asignar a una variable, pasar como argumento y devolver desde otra función. Esto es la base de los decoradores:

El decorador como azúcar sintáctico

La sintaxis @decorador encima de una def es azúcar: hace exactamente esto, pero sin que tengas que reasignar el nombre a mano.

def verbose(func):
    def wrapper(*args, **kwargs):
        print(f"→ llamando a {func.__name__}")
        result = func(*args, **kwargs)
        print(f"← resultado: {result!r}")
        return result
    return wrapper

# Estas dos formas son IDÉNTICAS:
@verbose
def greet(name):
    return f"Hola, {name}"

# def greet(name): ...          # la de arriba equivale a esto:
# greet = verbose(greet)

¿Por qué *args/**kwargs en el wrapper?

El wrapper no sabe con qué argumentos se llamará a la función decorada. Si escribiera def wrapper(name), solo serviría para funciones de un argumento. Con *args, **kwargs el wrapper reexpande lo que reciba hacia la función original, y sirve para cualquier firma.

functools.wraps: no pierdas la identidad

Al decorar, el nombre greet pasa a ser el wrapper: si miras greet.__name__ verás "wrapper", y su docstring se habrá perdido. functools.wraps copia los metadatos (__name__, __doc__, __module__, __wrapped__…) de la función original al wrapper. Úsalo siempre: herramientas como pytest, los logs y los tracebacks dependen de esos nombres.

Decoradores con argumentos: una fábrica de decoradores

Si quieres configurar el decorador (@retry(3), @require_kind("book", "movie")), necesitas tres niveles: la capa exterior recibe los argumentos de configuración y devuelve el decorador de verdad.

require_kind("book", "movie") <- recibe la CONFIGURACIÓN │ └─> decorator(func) <- recibe la FUNCIÓN a decorar │ └─> wrapper(...) <- envuelve la LLAMADA real @require_kind("book", "movie") == func = require_kind("book", "movie")(func)

El orden importa cuando apilas decoradores

Si pones varios, se aplican de abajo hacia arriba (el más cercano a la def es el primero que envuelve):

@timed          # 2º: envuelve al resultado de @cache
@cache          # 1º: envuelve a la función original
def load():
    ...
# equivale a: load = timed(cache(load))

Leyendo de arriba abajo parece «timed primero», pero no: el decorador más interno (el de abajo) se aplica primero.

3 · Ejemplo mínimo

El decorador más pequeño que hace algo útil: imprimir la traza de entrada y salida. Fíjate en que no modificamos el cuerpo de greet.

import functools

# decorador: recibe func, devuelve wrapper
def verbose(func):
    @functools.wraps(func)                       # conserva __name__ y __doc__
    def wrapper(*args, **kwargs):                # cualquier firma
        print(f"→ llamando a {func.__name__}{args}")
        result = func(*args, **kwargs)           # delega la llamada real
        print(f"← {func.__name__} devolvió {result!r}")
        return result
    return wrapper

@verbose                                     # apply: greet = verbose(greet)
def greet(name):
    """Saluda a alguien."""
    return f"Hola, {name}"

print(greet("Ada"))                          # llamada «decorada»
print("nombre real:", greet.__name__)        # gracias a functools.wraps
        
→ llamando a greet('Ada',)
← greet devolvió 'Hola, Ada'
Hola, Ada
nombre real: greet

Línea por línea: @verbose sustituye greet por wrapper; al llamar greet("Ada") entramos al wrapper, que imprime la traza, llama a la función original con func(*args, **kwargs) y devuelve su resultado. Sin functools.wraps, greet.__name__ imprimiría wrapper.

4 · Ejemplo real

En Biblioteca usamos tres decoradores para operación (no para la lógica de dominio): timing, cache y validación. Lo importante no es el decorador en sí, sino que el servicio queda limpio y el «cómo» transversal vive aparte.

biblioteca/service.py
import functools
import time

# ---------- 1) TIMING: cuánto tarda una operación ----------
def timed(func):
    """Mide el tiempo de ejecución y lo imprime."""
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()            # reloj de alta resolución
        try:
            return func(*args, **kwargs)       # delegamos
        finally:
            elapsed = time.perf_counter() - start
            # finally: también mide si la función lanza excepción
            print(f"[timed] {func.__name__} tardó {elapsed:.4f}s")
    return wrapper

# ---------- 2) CACHE: no recalcular lo mismo ----------
# functools.lru_cache es el decorador de cache de la stdlib.
# En 3.9+ existe @functools.cache (equivalente con maxsize=None).
@functools.lru_cache(maxsize=None)
def normalize(text: str) -> str:
    """Normaliza para buscar: minúsculas y sin espacios sobrantes.
    Cacheado: misma entrada -> mismo resultado sin recalcular."""
    return " ".join(text.lower().split())

# ---------- 3) VALIDACIÓN con argumentos (fábrica) ----------
def require_fields(*fields):
    """Fábrica de decoradores: exige que el dict tenga ciertas claves."""
    def decorator(func):
        @functools.wraps(func)
        def wrapper(item, *args, **kwargs):
            missing = [f for f in fields if f not in item]
            if missing:                        # falla ANTES de tocar el dominio
                raise ValueError(f"faltan campos: {missing}")
            return func(item, *args, **kwargs)
        return wrapper
    return decorator

# ---------- Uso: el servicio queda limpio ----------
@timed
@require_fields("id", "title", "kind", "borrowed")
def describe(item: dict) -> str:
    """Devuelve una descripción legible de un ítem del catálogo."""
    estado = "prestado" if item["borrowed"] else "disponible"
    return f"{item['title']} ({item['kind']}) — {estado}"

# Item válido del catálogo de ejemplo
book = {"id": "b1", "title": "1984", "kind": "book",
        "year": 1949, "borrowed": False}
print(describe(book))
        
[timed] describe tardó 0.0000s
1984 (book) — disponible

Decisiones que importan aquí:

  • Los decoradores son transversales. describe solo describe; el timing y la validación se aplican desde fuera. Si mañana quieres medir otra función, reutilizas @timed.
  • try/finally en timed: el tiempo se imprime incluso si la función falla. Un decorador de operación no debe ocultar excepciones.
  • La validación es una fábrica (require_fields(...)): los campos son configuración, por eso hay tres niveles.
  • @require_fields va debajo de @timed: así la validación corre primero y el timing mide la operación ya validada. Recuerda: se aplican de abajo arriba.

¿Por qué validar con un decorador y no con un if dentro? Porque si seis funciones del servicio necesitan el mismo chequeo, con un decorador se escribe una vez y se declara en cada uso. La alternativa (copiar el if) es justo el problema que los decoradores vinieron a resolver. Ojo: para datos que llegan de un fichero JSON persistido, la validación «de verdad» vive en store.py (Módulo 6); esto es una capa de contrato para funciones internas.

5 · Buenas prácticas

Pon @functools.wraps(func) en todo wrapper Wrapper «pelado» que pierde __name__/__doc__ pytest, logging y los tracebacks se orientan por esos metadatos; sin ellos depuras a ciegas.

PEP 8 y nombres: un decorador es una función normal, así que usa lowercase_with_underscores (timed, require_fields), no Timed. Los que se exponen como API de librería sí pueden parecer «clases», pero en tu aplicación no.

6 · Errores habituales

Olvidar devolver el wrapper

# ❌ El decorador no devuelve nada: greet se convierte en None
def broken(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    # ¡falta "return wrapper"!

@broken
def greet(name):
    return f"Hola, {name}"

print(greet("Ada"))          # TypeError: 'NoneType' object is not callable

# ✅ Devuelve SIEMPRE el wrapper (o lo que quieras que sustituya a func)
def fixed(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

Confundir el orden de los decoradores apilados

def a(func):
    def w(*args, **kwargs):
        print("a-antes");  r = func(*args, **kwargs); print("a-después"); return r
    return w

def b(func):
    def w(*args, **kwargs):
        print("b-antes");  r = func(*args, **kwargs); print("b-después"); return r
    return w

# ❌ Se cree que "a" se ejecuta primero por estar arriba
@a
@b
def task():
    print("task")

task()
# En realidad: b-antes, a-antes, task, a-después, b-después
# El decorador MÁS CERCANO a def (b) envuelve primero.

7 · Ejercicio guiado

Objetivo: escribir un decorador @count_calls que cuente cuántas veces se llama una función, sin tocar su cuerpo, y probar que functools.wraps conserva el nombre y el docstring.

  1. Paso 1 — Crea el archivo.
    count_calls.py
    import functools

# El decorador guarda el contador en el propio wrapper (atributo)
def count_calls(func):
    @functools.wraps(func)                    # conserva __name__ y __doc__
    def wrapper(*args, **kwargs):
        wrapper.calls += 1                    # incrementa el contador
        return func(*args, **kwargs)
    wrapper.calls = 0                         # inicializa el contador a CERO
    return wrapper

@count_calls
def add(a, b):
    """Suma dos números."""
    return a + b

# Tres llamadas: el contador debe llegar a 3
print(add(2, 3))
print(add(10, 20))
print(add(1, 1))
print("llamadas:", add.calls)             # leemos el atributo del wrapper
print("nombre:", add.__name__, "| doc:", add.__doc__)
  2. Paso 2 — Ejecútalo y comprueba la salida esperada. 
    python count_calls.py
# Salida esperada:
# 5
# 30
# 2
# llamadas: 3
# nombre: add | doc: Suma dos números.
  3. Paso 3 — Comprueba el punto clave. Ejecuta también: 
    # ¿Por qué "nombre: add" y no "nombre: wrapper"?
# Por @functools.wraps(func): copia __name__ y __doc__ a wrapper.
print(add.__wrapped__(2, 3))   # 5  (la función original, sin contar)

    Si quitas @functools.wraps(func), la línea del nombre imprimirá wrapper y el doc será None. Ese contraste es la lección.

  4. Paso 4 — Verificación. El contador empieza en 0, suma 1 antes de delegar, y el resultado no se altera. add.__wrapped__ demuestra que la función original sigue existiendo intacta dentro del wrapper.

8 · Reto

🎯 Decorador @retry con espera exponencial

Construye un decorador configurable @retry(attempts=3, base_delay=0.1) que reintente una función que lanza excepción, esperando base_delay * 2**intento entre intentos (espera exponencial). Debe relanzar la última excepción si se agotan los intentos y no reintentar si la función tiene éxito a la primera.

Pista 1: necesitas tres niveles (config → decorador → wrapper). Pista 2: time.sleep(...) para esperar y un bucle con enumerate. Pista 3: guarda la última excepción en una variable y raise al terminar el bucle. Bonus: añade un parámetro exceptions=(ValueError,) para decidir qué excepciones reintentar.

9 · Resumen

  • Un decorador es una función que recibe una función y devuelve otra (normalmente un wrapper).
  • Existen porque las funciones son objetos de primera clase; @d equivale a func = d(func).
  • El wrapper usa *args, **kwargs para delegar cualquier firma y functools.wraps para conservar metadatos.
  • Decoradores con argumentos necesitan tres niveles (config → decorador → wrapper).
  • Apilados, se aplican de abajo hacia arriba.
  • Casos reales: timing, cache (lru_cache/cache), validación, @property, @dataclass, fixtures de pytest.
ConceptoPara qué sirve

functools.wraps(func)Copiar __name__/__doc__ al wrapper (depuración, pytest, logs).
fábrica de 3 nivelesDecoradores configurables: @retry(3), @require_fields(...).
functools.lru_cacheCachear resultados por argumentos (funciones puras).

10 · Preguntas frecuentes

¿Por qué el wrapper usa *args, **kwargs si conozco la firma?

Porque el decorador debe ser reutilizable: @timed, @verbose o @count_calls deben funcionar sobre funciones de 0, 1 o 10 parámetros. Cablear la firma convierte un decorador genérico en uno de un solo uso. Si además quieres que las herramientas de tipado vean la firma real, existen ParamSpec y functools.wraps; pero para ejecución, *args/**kwargs es lo correcto.

¿@functools.cache y @functools.lru_cache(maxsize=None) son lo mismo?

Funcionalmente sí: cache (Python 3.9+) es equivalente a lru_cache(maxsize=None), una cache sin límite de tamaño. Si te preocupa la memoria (muchas claves distintas), usa lru_cache(maxsize=N) para descartar las menos usadas. Recuerda: cachear solo tiene sentido con funciones puras y argumentos hashables.

¿Puedo decorar métodos de una clase?

Sí. El primer argumento que recibe el wrapper es self, y como usas *args lo reenvías sin problema. El detalle: el orden con @staticmethod/@classmethod importa (se aplican de abajo arriba), y para tipado fino se usan ParamSpec y Concatenate (mencionados en la documentación de typing).

¿Miden los decoradores algo por sí mismos o hay que usar time.perf_counter?

El decorador no mide nada por sí solo: es el código dentro el que mide. Para medir tiempos se usa time.perf_counter() (reloj monótono de alta resolución) mejor que time.time(), que puede saltar hacia atrás si el sistema ajusta la hora. La documentación oficial (time, functools) recomienda perf_counter para medir duraciones cortas.
