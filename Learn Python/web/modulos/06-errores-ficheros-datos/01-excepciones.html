Excepciones y errores propios

Módulo 6 · Errores, ficheros y datos ⏱ 35 minutos

1 · Introducción

Hasta ahora el catálogo de Biblioteca vive en memoria: si el programa termina, se pierde todo. Antes de escribir nada en disco necesitamos una pieza que damos por hecha en otros lenguajes: qué hacer cuando algo falla. Un fichero que no existe, un JSON corrupto, un ítem que no está en el catálogo o un año escrito con letras no son casos raros: son la vida real de un programa que toca datos.

Esta lección enseña cómo Python señala y gestiona errores mediante excepciones: la sentencia try/except/else/finally, la jerarquía de excepciones integradas, el patrón EAFP («es más fácil pedir perdón que permiso»), cómo lanzar errores con raise y cómo crear un error propio (BibliotecaError) para que la CLI distinga fallos de negocio de fallos de programación.

¿Por qué existe esta lección? Porque en Python los errores no se devuelven como códigos: se lanzan. Entender esto es la diferencia entre un programa que revienta con un Traceback críptico y uno que dice «no existe un ítem con id 'b99'» y sigue funcionando. Además, mal manejadas, las excepciones son el error nº1 de código profesional: un except: desnudo puede ocultar bugs durante meses.

Al terminar sabrás distinguir entre errores que puedes arreglar (pedir otro id, crear el fichero), errores que debes dejar propagar (un bug de tu lógica) y errores que debes reportar al usuario (de negocio). Esa distinción es exactamente el diseño del módulo de errores de Biblioteca.

2 · Teoría

Qué es una excepción (y por qué no es un «if que falla»)

En C o Go, una función que puede fallar devuelve un valor extra: -1, null o (resultado, error). En Python (igual que en Java o C#), cuando algo imposible ocurre se lanza un objeto excepción. Ese objeto viaja hacia arriba por la pila de llamadas hasta que alguien lo captura o hasta que el intérprete lo imprime y aborta el programa.

La consecuencia de diseño fundamental es esta: el camino feliz queda limpio. No llenas la lógica de comprobaciones defensivas; escribes lo que quieres que pase y, si algo excepcional ocurre, lo tratas aparte.

find("b99") ──► raise BibliotecaError
                        │
                   ¿hay un try que lo capture?
                     /            \
                   sí              no
                   │                │
            ejecuta el except    sube por la pila
            y continúa           ──► Traceback + exit 1

La anatomía del traceback

Cuando una excepción no se captura, Python imprime un traceback: la pila de llamadas que llevó al fallo. Se lee de abajo arriba: la última línea es la causa raíz (ZeroDivisionError: division by zero) y cada línea «File …» indica el archivo y número de línea de un marco. Leerlo es una habilidad central, no un castigo.

La sentencia completa: try / except / else / finally

Cada bloque tiene un papel distinto y usarlos bien es la diferencia entre código claro y código tramposo:

BloqueCuándo se ejecutaPara qué sirve
trySiempreEl código «vigilado», el que puede lanzar
except TSi se lanza una excepción de tipo TReaccionar al error (o dejarlo subir)
elseSolo si no hubo excepciónLo que debe pasar en el camino feliz, sin quedar «protegido»
finallySiempre, haya o no errorLimpiar recursos (cerrar, borrar temporales)

¿Por qué existe else? Para mantener el try mínimo: si metes el «código de después» dentro del try, un except ValueError podría capturar un error que no venía de la operación vigilada.

La jerarquía: capturar por familia, no por caso

Todas las excepciones heredan de BaseException, pero la programación normal usa Exception. Esta jerarquía (simplificada) es la clave para decidir qué capturar:

BaseException
├── SystemExit · KeyboardInterrupt     ← no las capturemos
└── Exception                          ← ★ base de lo que gestiona tu código
    ├── ArithmeticError └── ZeroDivisionError
    ├── LookupError     ├── IndexError · KeyError
    ├── OSError         ├── FileNotFoundError · PermissionError
    ├── ValueError      └── UnicodeError · json.JSONDecodeError
    └── BibliotecaError                ← ★ el nuestro

Como las excepciones son clases, capturar un tipo captura también sus subtipos: except OSError atrapa FileNotFoundError y PermissionError. Por eso conviene poner las excepciones de arriba a abajo: de la más concreta a la más general, y dejar la general al final.

EAFP vs LBYL

Python es idomático en EAFP — Easier to Ask Forgiveness than Permission: intenta la operación y trata el fallo. El estilo contrario es LBYL — Look Before You Leap: comprueba todo antes. Mira el porqué con ficheros:

from pathlib import Path

path = Path("data/library.json")

# ❌ LBYL: entre exists() y read_text() el fichero puede desaparecer
#    (otro proceso, un test, un borrado): el bug clásico "TOCTOU".
if path.exists():
    text = path.read_text(encoding="utf-8")
else:
    text = "[]"

# ✅ EAFP: intentar y capturar el error concreto. No hay ventana.
try:
    text = path.read_text(encoding="utf-8")
except FileNotFoundError:
    text = "[]"

LBYL es correcto cuando la comprobación es barata y estable (por ejemplo, validar que un año es numérico antes de usarlo). EAFP es preferible cuando la condición puede cambiar entre la comprobación y el uso, o cuando comprobar es más caro que intentar.

Lanzar errores: raise y excepciones propias

Una función señala que no puede cumplir su contrato con raise. Y una librería seria no lanza Exception genérica: define su propia clase de error para que quien la use pueda distinguir sus fallos de dominio de los de Python.

# models.py — el error de negocio de Biblioteca
class BibliotecaError(Exception):
    """Error de negocio (entrada inválida, ítem inexistente…)."""

Fíjate en el detalle de diseño: BibliotecaError cuelga directamente de Exception, así el consumidor captura except BibliotecaError para «cualquier cosa de nuestro dominio». Si más adelante necesitas distinguir no encontrado de datos inválidos, puedes crear subclases, pero el proyecto mantiene una única clase base.

Encadenar errores: raise ... from

Cuando traduces un error de bajo nivel a uno de tu dominio, quieres conservar la causa original. raise X from Y fija X.__cause__ = Y y el traceback muestra «The above exception was the direct cause…»:

import json

def parse_store(text: str):
    try:
        return json.loads(text)          # puede lanzar json.JSONDecodeError
    except json.JSONDecodeError as exc:
        # ✅ Traducimos a un error NUESTRO sin perder la causa original.
        raise BibliotecaError("El almacén no contiene JSON válido") from exc

Sin from exc, Python aún muestra el contexto implícito («During handling…»), pero from deja explícito que este error fue causado por aquel. Es documentación para quien depure a las 3 de la mañana.

3 · Ejemplo mínimo

El fragmento más pequeño que muestra capturar un error concreto y usar else y finally:

def parse_year(raw: str) -> int:
    """Convierte texto a año, con mensaje claro si es inválido."""
    try:
        year = int(raw)                    # puede lanzar ValueError
    except ValueError:
        print(f"Año inválido: {raw!r}")    # reaccionamos al error
        return 0
    else:
        print("Conversión correcta")       # solo si NO hubo excepción
        return year
    finally:
        print("Fin del intento")           # siempre

print(parse_year("1949"))
print(parse_year("mil"))

# Salida esperada:
# Conversión correcta
# Fin del intento
# 1949
# Año inválido: 'mil'
# Fin del intento
# 0

Línea por línea: int("1949") funciona y salta al else; devuelve 1949, imprime «Conversión correcta» y, antes de salir, ejecuta finally. Con "mil", int lanza ValueError, se entra al except, se devuelve 0 y aun así se pasa por finally. El porqué de finally: es el único lugar que garantiza ejecución tanto si hay return como si hay error, ideal para limpiar.

4 · Ejemplo real

En Biblioteca, la regla de negocio «no puedes prestar dos veces el mismo ítem» se expresa lanzando un error propio, y la CLI lo traduce a un mensaje y un código de salida. Ni sys.exit dentro del servicio ni print de errores: el núcleo no sabe que existe una terminal.

# src/biblioteca/service.py
from biblioteca.models import BibliotecaError, Item

def find(items: list[Item], item_id: str) -> Item:
    """Devuelve el ítem por id o lanza BibliotecaError."""
    for item in items:
        if item.id == item_id:
            return item
    # ✅ Error de negocio con contexto útil (el id buscado)
    raise BibliotecaError(f"No existe un ítem con id {item_id!r}")

def borrow(items: list[Item], item_id: str) -> Item:
    """Marca un ítem como prestado aplicando las reglas."""
    item = find(items, item_id)            # puede lanzar BibliotecaError
    if item.borrowed:
        raise BibliotecaError(f"El ítem {item_id!r} ya está prestado")
    item.borrowed = True
    return item

# src/biblioteca/cli.py — el borde del sistema traduce a UI
import sys
from biblioteca.models import BibliotecaError

def main(argv: list[str] | None = None) -> int:
    try:
        # ... aquí se llama a service.borrow(...) según los argumentos ...
        result = borrow(items, "b99")
    except BibliotecaError as exc:
        # ✅ Capturamos SOLO nuestros errores; un bug real (TypeError…)
        #    NO se captura y verás el traceback completo para arreglarlo.
        print(f"Error: {exc}", file=sys.stderr)
        return 1                            # código de salida ≠ 0
    else:
        print(f"Prestado: {result.title}")
        return 0

Decisiones clave: (1) el servicio lanza errores de dominio (BibliotecaError) con mensaje accionable; (2) la CLI captura BibliotecaError —la raíz— y no Exception, para que un fallo de programación siga siendo visible; (3) el return 1 permite que el shell detecte el error (if bib borrow b99; then …). Esta separación es lo que hace testeable el núcleo en el Módulo 7. (En Linux/macOS lanzas con python; en Windows, con el launcher py.)

Regla de oro: lanza excepciones pronto (en cuanto detectas el problema) y captúralas tarde (en el borde que sabe qué hacer: CLI, API, job). Cuanto más abajo captures, más información pierdes.

6 · Errores habituales

Silenciar todo con un except desnudo

# ❌ except: captura incluso KeyboardInterrupt y SystemExit, y oculta
#    cualquier bug. El programa "funciona" pero con datos equivocados.
try:
    year = int(raw_year)
except:
    year = 0

# ✅ Captura solo lo que sabes tratar y registra el resto.
try:
    year = int(raw_year)
except ValueError:            # el único fallo esperable aquí
    year = 0

Capturar y no hacer nada (except … : pass)

# ❌ El fallo desaparece sin rastro. Imposible depurar.
try:
    save_store(items)
except BibliotecaError:
    pass

# ✅ Deja rastro con contexto o deja subir la excepción.
import logging
try:
    save_store(items)
except BibliotecaError:
    logging.exception("No se pudo guardar el catálogo")  # traza + stack

Lanzar Exception y perder la causa

# ❌ Se pierde el error original y el mensaje no dice qué ítem falló.
except json.JSONDecodeError:
    raise Exception("error")

# ✅ Error de dominio + causa encadenada + contexto.
except json.JSONDecodeError as exc:
    raise BibliotecaError(f"JSON inválido en {path}") from exc

7 · Ejercicio guiado

Objetivo: implementar la operación return_item (devolver un libro prestado) con errores propios y comprobar que la CLI los traduce correctamente.

  1. Paso 1 — el error: define la clase BibliotecaError (en models.py, como en la teoría).
  2. Paso 2 — el modelo mínimo: una dataclass sencilla para probar sin depender del resto del paquete. 
    from dataclasses import dataclass

@dataclass
class Book:
    id: str
    title: str
    borrowed: bool = False
  3. Paso 3 — el servicio: escribe return_item con dos reglas: si no existe, BibliotecaError; si no estaba prestado, BibliotecaError. 
    def find(items, item_id):
    for item in items:
        if item.id == item_id:
            return item
    raise BibliotecaError(f"No existe un ítem con id {item_id!r}")

def return_item(items, item_id):
    item = find(items, item_id)
    if not item.borrowed:
        raise BibliotecaError(f"El ítem {item_id!r} no estaba prestado")
    item.borrowed = False
    return item
  4. Paso 4 — el borde que captura: una función que llame y reporte. 
    def run(items, item_id):
    try:
        item = return_item(items, item_id)
    except BibliotecaError as exc:      # captura toda nuestra base
        print(f"Error: {exc}")
    else:
        print(f"Devuelto: {item.title}")

books = [Book("b1", "1984", borrowed=True), Book("b2", "Dune")]
run(books, "b1")
run(books, "b1")   # ya no estaba prestado
run(books, "b9")   # no existe
  5. Paso 5 — resultado esperado: comprueba que la salida es exactamente esta. 
    Devuelto: 1984
Error: El ítem 'b1' no estaba prestado
Error: No existe un ítem con id 'b9'
    El primer run cae en el else; el segundo lanza BibliotecaError desde el servicio y lo captura el except BibliotecaError; el tercero también. Un solo except basta.

Cómo comprobarlo: ejecuta python ejercicio.py. Si ves el else del primer caso y los dos mensajes de error exactos, el error propio y el flujo funcionan. Un except Exception también daría esta salida, pero no distingue un bug real: prueba a cambiar temporalmente find por una versión con un error de sintaxis lógica y verás que except BibliotecaError no lo oculta.

8 · Reto

🎯 Errores con contexto estructurado

Amplía BibliotecaError para que lleve datos de contexto además del mensaje: guarda el item_id o el campo inválido como atributos. Añade un método to_dict() que devuelva {"error": classname, "message": str, "context": {...}}. Después, en el borde, imprime ese diccionario como JSON en la salida de error.

Pista: define BibliotecaError.__init__(self, message, **context) y guarda self.context = context; llama a super().__init__(message). Pasa los datos con nombre al lanzar (item_id=item_id). Para el JSON, json.dumps(exc.to_dict(), ensure_ascii=False) — el ensure_ascii=False evita que los acentos salgan como \u00e1 (lo verás en la lección 4).

9 · Resumen

  • Una excepción es un objeto que interrumpe el flujo normal y viaja hacia arriba hasta ser capturado o abortar el programa.
  • try vigila, except reacciona, else es el camino feliz y finally limpia siempre.
  • Captura la excepción más concreta posible; nunca un except: desnudo.
  • Todas las excepciones heredan de BaseException; tu código normal trabaja con Exception y captura de hijo a padre.
  • EAFP (intentar y capturar) es más idiomático y seguro que LBYL cuando hay condiciones que pueden cambiar.
  • Define una clase de error propia que herede de Exception (BibliotecaError, en models.py).
  • Usa raise … from exc para traducir errores sin perder la causa original.
ConceptoPara qué sirve
try/exceptVigilar código y reaccionar a errores concretos
elseEjecutar el camino feliz sin ampliar el try
finallyGarantizar la limpieza haya o no error
raise XSeñalar que una función no puede cumplir su contrato
raise X from YEncadenar la causa original al traducir un error
BibliotecaErrorBase propia para distinguir errores de dominio de los de Python

10 · Preguntas frecuentes

¿Por qué no capturar Exception a secas para que el programa no caiga?

Porque Exception incluye errores que indican bugs: AttributeError, TypeError, NameError… Si los capturas, conviertes un fallo de programación en un «todo va bien» silencioso y los datos pueden corromperse. Captura lo que sabes tratar; deja el resto subir para verlo y arreglarlo. En un borde de aplicación (CLI de nivel superior) sí puedes hacer de último recurso except Exception para volcar un error limpio, pero registrándolo siempre.

¿Qué diferencia hay entre except, except Exception y BaseException?

except: desnudo equivale a except BaseException: y atrapa también KeyboardInterrupt (Ctrl+C) y SystemExit, impidiendo cerrar el programa. except Exception: deja pasar esas dos, pero sigue siendo demasiado amplio. La opción idiomática es capturar tipos concretos o tu jerarquía propia.

¿Debo usar excepciones para validar la entrada del usuario?

Distingue la validación de frontera de la regla de negocio. Para un año escrito con letras, un if con isdigit() o intentar int() y capturar ValueError son igual de razonables. Para «el ítem ya está prestado», lanza BibliotecaError: es una regla del dominio y merece un error propio. Usar excepciones para el flujo esperado y frecuente sí es un abuso.
