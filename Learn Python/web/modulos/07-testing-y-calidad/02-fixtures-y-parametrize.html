Fixtures, tmp_path y parametrize

Módulo 7 · Testing y calidad ⏱ 35 minutos

1 · Introducción

En la lección anterior escribimos tests con datos creados dentro de cada función. Funciona hasta que aparece la duplicación: cien tests que necesitan la misma lista de items o el mismo almacén temporal. Copiar y pegar ese setup es una bomba de relojería: el día que cambie, hay que tocar cien sitios.

pytest resuelve esto con fixtures: funciones que preparan recursos y que los tests piden por nombre. Veremos también tmp_path (un directorio temporal por test para no tocar data/library.json real), @pytest.mark.parametrize (un test, muchos casos) y monkeypatch (sustituir entorno o atributos sin dejar rastro).

¿Por qué existe esta lección? Porque un test solo es de fiar si está aislado. Si un test escribe en el almacén real, el siguiente lee basura y el fallo se vuelve irreproducible. Las fixtures son el mecanismo idiomático de pytest para dar a cada test su propio mundo limpio… y desmontarlo al terminar.

2 · Teoría

¿Qué es una fixture?

Una fixture es una función decorada con @pytest.fixture que devuelve (o cede) un recurso. El test la usa declarándola como parámetro con el mismo nombre: pytest la ejecuta antes y le inyecta el valor.

import pytest

from biblioteca.models import Book


@pytest.fixture
def sample_items() -> list[Book]:
    """Recurso compartido: dos libros canónicos del catálogo (dataclasses)."""
    return [
        Book(id="it_1", title="1984", kind="book", year=1949, author="Orwell"),
        Book(id="it_2", title="Dune", kind="book", year=1965, author="Herbert"),
    ]


def test_hay_dos_items(sample_items: list[Book]) -> None:
    assert len(sample_items) == 2   # pytest inyecta la fixture aquí

La diferencia con una variable global es el ciclo de vida: por defecto cada test recibe una instancia nueva, así que los datos no se contaminan entre tests.

Alcance (scope) y conftest.py

ScopeCuándo se crea el recursoUso típico
function (por defecto)Una vez por cada testDatos y estado: lo correcto casi siempre
moduleUna vez por archivoUna conexión de solo lectura costosa
sessionUna vez por toda la ejecuciónUn recurso muy caro de montar

Cuando una fixture la usan varios archivos, se declara en conftest.py: pytest lo descubre solo, sin import ni registro manual. Si la fixture aparta algo, debe limpiarlo con yield (lo de antes es el setup; lo de después, el teardown, que corre aunque el test falle).

Regla de oro del scope: usa el más estrecho que funcione. session solo cuando montar el recurso es tan caro que el aislamiento no compensa, porque un recurso compartido puede convertirse en estado que un test ensucia para el siguiente.

tmp_path: el almacén desechable

tmp_path es una fixture que pytest ya trae: entrega un pathlib.Path único por test, dentro de un directorio temporal, que se limpia solo. Es exactamente lo que necesitamos para probar el almacén JSON sin tocar el real.

Nunca uses rutas fijas como data/library.json en un test. Escribirás en el catálogo real, borrarás datos del alumno y el test pasará o fallará según lo que hubiera antes. tmp_path elimina ese fallo por diseño.

@pytest.mark.parametrize: un test, muchos casos

Cuando la misma lógica se comprueba con varios datos, no copies el test: parametrízalo. pytest genera un caso por fila y, si uno falla, te dice cuál por su id.

import pytest

from biblioteca.models import Book, Movie, item_from_dict


@pytest.mark.parametrize(
    "data, expected_type",
    [
        ({"id": "it_1", "title": "1984", "kind": "book", "borrowed": False}, Book),
        ({"id": "it_2", "title": "Dune", "kind": "movie", "borrowed": False}, Movie),
    ],
    ids=["libro", "pelicula"],
)
def test_item_from_dict_devuelve_el_tipo(data: dict, expected_type: type) -> None:
    # `data` es JSON crudo: la forma exacta que consume item_from_dict.
    assert isinstance(item_from_dict(data), expected_type)

monkeypatch: efectos secundarios bajo control

monkeypatch es otra fixture integrada. Cambia cosas de forma temporal —variables de entorno (setenv), atributos (setattr), el directorio de trabajo (chdir)— y pytest revierte todos los cambios al terminar. Es la vía limpia para probar código que lee os.environ.

3 · Ejemplo mínimo

Una fixture para los datos y un parametrize para los casos, en un solo archivo:

# tests/test_strip.py
import pytest


@pytest.fixture
def items() -> list[str]:
    return ["1984", "Dune", "Blade Runner"]


@pytest.mark.parametrize(
    "title, expected",
    [("1984", True), ("Dune", True), ("Neuromante", False)],
)
def test_contiene(items: list[str], title: str, expected: bool) -> None:
    assert (title in items) is expected

4 · Ejemplo real

Protegemos el almacén JSON de Biblioteca. En el proyecto real store.py no tiene clases: expone dos funciones de módulo, load(path) y save(items, path), que reciben la ruta como parámetro. Ese detalle es la clave del aislamiento.

# src/biblioteca/store.py
import json
from pathlib import Path
from typing import Sequence

from .models import BibliotecaError, Item, item_from_dict

DEFAULT_STORE = Path("data/library.json")


def load(path: str | Path = DEFAULT_STORE) -> list[Item]:
    """Lee el almacén y devuelve la lista de ítems (vacía si no existe)."""
    file = Path(path)
    if not file.exists():                 # sin archivo -> catálogo vacío
        return []
    try:
        raw = json.loads(file.read_text(encoding="utf-8"))
    except json.JSONDecodeError as err:
        raise BibliotecaError(f"el almacén {file} no es JSON válido: {err}") from err
    if not isinstance(raw, list):
        raise BibliotecaError(f"el almacén {file} debe ser una lista JSON")
    return [item_from_dict(entry) for entry in raw]


def save(items: Sequence[Item], path: str | Path = DEFAULT_STORE) -> None:
    """Escribe la lista de ítems, creando el directorio si hace falta."""
    file = Path(path)
    file.parent.mkdir(parents=True, exist_ok=True)
    data = [item.to_dict() for item in items]
    file.write_text(json.dumps(data, ensure_ascii=False, indent=2) + "\n", encoding="utf-8")

En Biblioteca no hace falta conftest.py: cada test pide tmp_path y crea su propio almacén. Un conftest tendría sentido si decenas de tests compartieran la misma fixture; aquí el aislamiento se resuelve con la ruta explícita.

# tests/test_store.py
import pytest

from biblioteca import store
from biblioteca.models import BibliotecaError, Book


def test_load_inexistente_devuelve_vacio(tmp_path):
    assert store.load(tmp_path / "no-existe.json") == []


def test_save_y_load_roundtrip(tmp_path):
    path = tmp_path / "library.json"
    items = [Book(id="it_1", title="1984", kind="book", year=1949, author="Orwell")]

    store.save(items, path)

    assert path.exists()
    assert store.load(path) == items


def test_almacen_corrupto_lanza_error(tmp_path):
    path = tmp_path / "roto.json"
    path.write_text("{esto no es json", encoding="utf-8")

    with pytest.raises(BibliotecaError):
        store.load(path)


def test_almacen_que_no_es_lista_lanza_error(tmp_path):
    path = tmp_path / "objeto.json"
    path.write_text('{"no": "es una lista"}', encoding="utf-8")

    with pytest.raises(BibliotecaError):
        store.load(path)

El test es limpio porque el diseño lo permite. load/save reciben la ruta por parámetro en vez de tenerla incrustada: eso es inyección de dependencias, y es lo que hace el código testeable. tmp_path aporta el archivo desechable; la ruta explícita evita tocar data/library.json.

¿Y monkeypatch? Sirve para aislar la ruta por defecto (relativa, data/library.json) sin pasar path en cada llamada: cambiamos el directorio de trabajo al temporal y pytest lo revierte solo.

# tests/test_service.py
from biblioteca import service


def test_default_store_es_relativa(tmp_path, monkeypatch) -> None:
    monkeypatch.chdir(tmp_path)                        # el CWD pasa al temporal
    service.add("Dune", creator="Frank Herbert")       # sin `path`: usa DEFAULT_STORE
    assert (tmp_path / "data" / "library.json").exists()

Resultado esperado: el test pasa y, al terminar, pytest devuelve el directorio de trabajo a su sitio; el data/library.json del proyecto no se toca.

6 · Errores habituales

❌ Apuntar el test al almacén real

from pathlib import Path

from biblioteca import store
from biblioteca.models import Book

# ❌ DESTRUCTIVO: escribe en el catálogo real del alumno
def test_guardar() -> None:
    store.save([Book(id="it_1", title="X", kind="book")], Path("data/library.json"))

# ✅ usa tmp_path: archivo desechable y único por test
def test_guardar_ok(tmp_path) -> None:
    store.save([Book(id="it_1", title="X", kind="book")], tmp_path / "library.json")

❌ Fixture con estado mutable compartido

import pytest

from biblioteca.models import Book

# ❌ La MISMA lista se reutiliza: un test ensucia al siguiente
@pytest.fixture(scope="session")
def items() -> list[Book]:
    return [Book(id="it_1", title="1984", kind="book", author="Orwell")]

def test_a(items) -> None:
    items.append(Book(id="it_2", title="Dune", kind="book", author="Herbert"))  # muta el recurso

def test_b(items) -> None:
    assert len(items) == 1     # FALLA según el orden de ejecución

# ✅ scope function: cada test recibe una lista nueva
@pytest.fixture
def items_ok() -> list[Book]:
    return [Book(id="it_1", title="1984", kind="book", author="Orwell")]

❌ Usar monkeypatch fuera de su ámbito

monkeypatch es una fixture: solo existe dentro de la función de test (o de otra fixture). Guardarla en una variable global o usarla en el cuerpo del módulo no funciona ni se revierte. Pídesela al test que la necesita, como parámetro.

def search(term: str, path: str = store.DEFAULT_STORE) -> list[Item]:
    """Busca por título o creador, sin distinguir mayúsculas."""
    ...
  2. Escribe el test parametrizado. Sin conftest: cada caso pide tmp_path y guarda sus propios datos. 
    # tests/test_service.py
import pytest

from biblioteca import service, store
from biblioteca.models import Book


@pytest.mark.parametrize(
    "term, expected",
    [("dune", ["Dune"]), ("DUNE", ["Dune"]), ("herbert", ["Dune"]), ("1984", ["1984"])],
    ids=["minusculas", "mayusculas", "creador", "titulo"],
)
def test_search(term: str, expected: list[str], tmp_path) -> None:
    path = tmp_path / "library.json"
    store.save(
        [
            Book(id="it_1", title="1984", kind="book", author="George Orwell"),
            Book(id="it_2", title="Dune", kind="book", author="Frank Herbert"),
        ],
        path,
    )
    assert [it.title for it in service.search(term, path=path)] == expected
  3. Añade un test de integración del almacén: 
    # tests/test_store.py (añadir al final)
from biblioteca import store
from biblioteca.models import Movie


def test_roundtrip_con_anio_none(tmp_path) -> None:
    path = tmp_path / "library.json"
    items = [Movie(id="it_3", title="Blade Runner", kind="movie", year=None, director="Ridley Scott")]
    store.save(items, path)
    # year=None debe sobrevivir al viaje por JSON
    assert store.load(path)[0].year is None

    pytest -v

    Resultado esperado: verás líneas como test_search[minusculas] y test_search[creador], todas en PASSED, y un resumen N passed.

  5. Comprueba el aislamiento: abre data/library.json antes y después de los tests. Resultado esperado: idéntico byte a byte. Si cambió, algún test escribe en el almacén real y hay que redirigirlo a tmp_path.

8 · Reto

🎯 Un almacén corrupto no debe tumbar la suite

El proyecto ya envuelve los datos inválidos en BibliotecaError. Amplía la cobertura: escribe una fixture que cree en tmp_path un archivo y un parametrize con varios casos — JSON que no parsea, JSON que no es una lista y una lista cuyo ítem tiene un kind desconocido — verificando con pytest.raises(BibliotecaError) que store.load() los detecta todos.

Pista: store.load captura json.JSONDecodeError y relanza con raise BibliotecaError(...) from err; el from err conserva la causa. El tercer caso no lo detecta json, sino item_from_dict en models.py.

9 · Resumen

  • Una fixture prepara un recurso y el test la pide por nombre como parámetro.
  • El scope controla el ciclo de vida; por defecto function = una instancia por test.
  • conftest.py comparte fixtures entre archivos sin imports.
  • tmp_path da un directorio temporal único por test: la herramienta para aislar el almacén.
  • @pytest.mark.parametrize convierte N casos en un test con ids legibles.
  • monkeypatch cambia entorno o atributos temporalmente y revierte solo.

10 · Preguntas frecuentes

¿Qué diferencia hay entre tmp_path y tmpdir?

tmpdir es la versión antigua y entrega un objeto py.path.local; tmp_path es la moderna y entrega un pathlib.Path, que es lo que usamos en todo el curso. Usa siempre tmp_path.

¿Cuándo uso scope="session"?

Solo cuando montar el recurso es muy caro (p. ej. levantar un contenedor de base de datos). Con datos y archivos deja el scope por defecto function: evita el temido «pasa solo si ejecuto los tests en este orden».

¿Puedo pedir varias fixtures en un mismo test?

Sí, se declaran todas como parámetros y pytest resuelve el orden según las dependencias. Un test puede combinar tmp_path, monkeypatch y tus propias fixtures sin problema. Y una fixture puede usar otra.

¿parametrize sustituye a escribir tests separados?

Para el mismo comportamiento con distintos datos, sí. Pero no mezcles comportamientos distintos en un solo parametrize: si los casos no comparten la misma lógica de aserción, son tests separados. Un test debe contar una sola historia.
