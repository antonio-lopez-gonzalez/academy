Introducción a pytest

Módulo 7 · Testing y calidad ⏱ 35 minutos

1 · Introducción

En el Módulo 6 la Biblioteca empezó a leer y escribir de verdad en data/library.json. A partir de ese momento el programa tiene lógica de negocio (añadir, buscar, prestar, devolver) y persistencia: dos sitios donde un cambio inocente puede romper algo que ayer funcionaba. La única defensa fiable contra esa clase de rotura es tener tests automáticos que se ejecuten en segundos tantas veces como haga falta.

En esta lección aprenderás qué problema resuelven los tests, por qué pytest es el estándar de facto en Python, cómo se escriben con assert normal y cómo el framework descubre y ejecuta los tests por ti. Terminaremos escribiendo el primer test real del catálogo Biblioteca.

¿Por qué existe esta lección? Porque un test no es burocracia: es la forma de fijar por escrito lo que el código debe hacer. Cada test es una promesa verificable («buscar orwell encuentra 1984»). Cuando esa promesa se rompe en el futuro, pytest te lo dice en milisegundos, antes de que el fallo llegue a un usuario.

2 · Teoría

Qué es un test automático

Un test es código que ejercita tu código y comprueba que el resultado es el esperado. La diferencia con «probarlo a mano» es que una vez escrito se ejecuta solo, siempre y en milisegundos. La pirámide clásica distingue tests unitarios (una función aislada, milisegundos), de integración (varias piezas: servicio + almacén JSON) y end-to-end (el programa completo, lento y frágil). En este módulo priorizamos los dos primeros.

Por qué pytest y no unittest

La biblioteca estándar incluye unittest (inspirado en JUnit de Java), que obliga a heredar de TestCase y usar self.assertEqual(...). pytest es de terceros pero se ha convertido en el estándar porque reduce la ceremonia: escribes assert normal, los tests son funciones sueltas y dispone de parametrize, fixtures y monkeypatch integrados.

Instalar pytest

Es una dependencia de desarrollo: no la necesita quien ejecuta bib, solo quien programa. Con venv+pip o con uv:

# Vía clásica: dentro del entorno virtual activado
pip install pytest            # instala la última versión estable (pytest 8.x)

# Vía moderna (recomendada): añade pytest al grupo de desarrollo
uv add --dev pytest           # lo registra en pyproject.toml y actualiza el lockfile

Multiplataforma. Instalar es idéntico en Linux, macOS y Windows. Lo que cambia es activar el entorno antes:

# Linux / macOS
source .venv/bin/activate

# Windows (PowerShell)
.venv\Scripts\Activate.ps1

Cómo descubre los tests

pytest no necesita que le digas dónde están. Cuando ejecutas pytest en la raíz del proyecto, recorre los directorios y aplica estas convenciones:

ElementoPatrón que pytest reconoce
Archivostest_*.py o *_test.py
Funcionesdef test_...
Clasesclass Test... (sin __init__)
Métodosdef test_... dentro de una clase Test*

Por eso el nombre del archivo importa: si lo llamas tests_service.py (sin el prefijo test_), pytest lo ignora y verás «no tests ran». Es el error número uno de quien empieza.

El flujo Arrange – Act – Assert

Casi todo test sano sigue tres pasos: preparar los datos (Arrange), ejecutar la acción (Act) y comprobar el resultado (Assert). Un test que hace las tres cosas y una sola comprobación es fácil de leer cuando falla.

3 · Ejemplo mínimo

El test más pequeño posible. Fíjate en que assert es el assert normal de Python, no un método especial:

# tests/test_basico.py

def add(a: int, b: int) -> int:
    """Código bajo prueba: suma dos enteros."""
    return a + b


def test_add_suma_dos_positivos() -> None:
    # Arrange + Act: ejecutamos la funcion
    result = add(2, 3)
    # Assert: comprobamos la promesa
    assert result == 5

Para ejecutarlo, desde la raíz del proyecto (donde está tests/):

pytest -v

Salida esperada (-v muestra un nombre por test):

============================= test session starts =============================
platform win32 -- Python 3.12.x, pytest-8.x.x, pluggy-1.x.x
rootdir: C:\proyectos\biblioteca
collected 1 item

tests/test_basico.py::test_add_suma_dos_positivos PASSED                 [100%]

============================== 1 passed in 0.01s ==============================

¿Y por qué assert a secas es suficiente? Porque pytest reescribe el bytecode del assert para interceptar los valores. Si el test fallara, en lugar de un opaco AssertionError verías el detalle:

>       assert add(2, 2) == 5
E       assert 4 == 5
E        +  where 4 = add(2, 2)

tests/test_basico.py:9: AssertionError

Ese where 4 = add(2, 2) lo genera pytest automáticamente. En unittest tendrías que escribirlo a mano.

4 · Ejemplo real

Apliquémoslo a Biblioteca. En service.py conviven dos funciones centrales: find recorre en memoria una colección de Item (función pura) y search lee el almacén desde una ruta concreta. Con tmp_path podemos probar ambas sin tocar data/library.json.

# src/biblioteca/service.py
from typing import Iterable

from . import store
from .models import BibliotecaError, Item


def find(items: Iterable[Item], item_id: str) -> Item:
    """Devuelve el item con ese id o lanza BibliotecaError si no existe."""
    for item in items:
        if item.id == item_id:
            return item
    raise BibliotecaError(f"no existe ningún ítem con id {item_id!r}")


def search(term: str, path: str = store.DEFAULT_STORE) -> list[Item]:
    """Busca por título o creador, sin distinguir mayúsculas."""
    needle = term.strip().lower()                  # normalizamos la aguja
    if not needle:
        raise BibliotecaError("el término de búsqueda no puede estar vacío")
    results = []
    for item in store.load(path):
        haystack = f"{item.title} {item.creator or ''}".lower()
        if needle in haystack:
            results.append(item)
    return results

Ahora los tests. Usamos los datos canónicos del curso (1984, Dune, Blade Runner) como dataclasses, y un almacén desechable por test con tmp_path:

# tests/test_service.py
import pytest

from biblioteca import service, store
from biblioteca.models import BibliotecaError, Book, Item, Movie


def make_items() -> list[Item]:
    """Fabrica los datos de ejemplo para los tests (dataclasses, no dicts)."""
    return [
        Book(id="it_1", title="1984", kind="book", year=1949, author="George Orwell"),
        Book(id="it_2", title="Dune", kind="book", year=1965, author="Frank Herbert"),
        Movie(id="it_3", title="Blade Runner", kind="movie", year=1982, director="Ridley Scott"),
    ]


def test_find_encuentra_el_item() -> None:
    items = make_items()
    assert service.find(items, "it_2").title == "Dune"


def test_find_lanza_error_si_no_existe() -> None:
    items = make_items()
    with pytest.raises(BibliotecaError):
        service.find(items, "it_999")


def test_search_ignora_mayusculas(tmp_path) -> None:
    path = tmp_path / "library.json"
    store.save(make_items(), path)
    titles = [it.title for it in service.search("DUNE", path=path)]
    assert titles == ["Dune"]


def test_search_por_titulo_y_creador(tmp_path) -> None:
    path = tmp_path / "library.json"
    store.save(make_items(), path)
    assert [it.title for it in service.search("herbert", path=path)] == ["Dune"]
    assert [it.title for it in service.search("blade", path=path)] == ["Blade Runner"]

Ejecutamos:

pytest -v tests/test_service.py

Salida esperada:

tests/test_service.py::test_find_encuentra_el_item PASSED                [ 25%]
tests/test_service.py::test_find_lanza_error_si_no_existe PASSED         [ 50%]
tests/test_service.py::test_search_ignora_mayusculas PASSED              [ 75%]
tests/test_service.py::test_search_por_titulo_y_creador PASSED           [100%]

============================== 4 passed in 0.01s ==============================

Fíjate en los nombres. test_search_ignora_mayusculas describe una promesa de comportamiento, no una función. Cuando falla dentro de seis meses, el nombre te dice exactamente qué contrato se ha roto, sin abrir el archivo.

5 · Buenas prácticas

HazEvitaPor qué
Un test = una idea, con nombre descriptivo Un test gigante que comprueba diez cosas Si falla, sabes exactamente qué contrato se rompió
Tests rápidos, sin red ni disco real Llamar a servicios externos o a data/ La suite se ejecuta en cada guardado; si tarda, dejas de correrla
Usar assert y pytest.raises try/except AssertionError o assert True Un test que no puede fallar no verifica nada
Testear el comportamiento observable Testear detalles internos de implementación Puedes refactorizar sin reescribir los tests
Datos de ejemplo explícitos dentro del test Depender de un JSON en disco que cambia El test es reproducible hoy y dentro de un año

Documentación oficial: la referencia completa de descubrimiento, assert y línea de comandos está en docs.pytest.org.

6 · Errores habituales

❌ El archivo no se llama test_*.py

# ❌ 'tests/service.py' NO coincide con el patron: pytest no lo ve
pytest -v
# collected 0 items  -> "no tests ran in 0.00s"

# ✅ renómbralo: el prefijo 'test_' es el contrato de descubrimiento
# tests/test_service.py

❌ Envolver el assert en try/except

import pytest

# ❌ Si NO salta la excepcion, el test termina sin fallar: falso verde
def test_divide_by_zero() -> None:
    try:
        divide(1, 0)
    except ZeroDivisionError:
        pass          # nunca se comprueba que realmente se lanzo

# ✅ pytest.raises afirma que la excepcion se lanza
def test_divide_by_zero_ok() -> None:
    with pytest.raises(ZeroDivisionError):
        divide(1, 0)

7 · Ejercicio guiado

Objetivo: crear la carpeta de tests de Biblioteca y comprobar el modelado de un Item (la @dataclass del Módulo 5), incluyendo que rechaza un kind inválido.

  1. Confirma la estructura del proyecto (puedes verla en la lección de estructura): 
    biblioteca/
├── pyproject.toml
├── src/biblioteca/
│   ├── models.py
│   ├── store.py
│   ├── service.py
│   └── cli.py
└── tests/
    ├── test_models.py     ← lo creamos ahora
    ├── test_store.py
    ├── test_service.py
    └── test_cli.py
  2. Recuerda el modelo (src/biblioteca/models.py). El catálogo distingue libros y películas, y valida el tipo en el constructor: 
    # src/biblioteca/models.py
from dataclasses import dataclass


class BibliotecaError(Exception):
    """Error de negocio de Biblioteca (entrada inválida, ítem inexistente…)."""


@dataclass
class Item:
    id: str
    title: str
    kind: str                  # "book" | "movie"
    year: int | None = None
    borrowed: bool = False

    def __post_init__(self) -> None:
        if self.kind not in {"book", "movie"}:
            raise BibliotecaError(f"kind inválido: {self.kind!r}")


@dataclass
class Book(Item):
    """Libro: además tiene `author`."""

    author: str | None = None
  3. Escribe el archivo de tests. Fíjate en que dataclass genera __eq__, así que dos items con los mismos campos son iguales: 
    # tests/test_models.py
import pytest

from biblioteca.models import BibliotecaError, Book, Movie


def test_kind_invalido_lanza_error() -> None:
    # pytest.raises afirma que el constructor lanza BibliotecaError
    with pytest.raises(BibliotecaError):
        Book(id="it_1", title="Dune", kind="cd")


def test_titulo_vacio_lanza_error() -> None:
    with pytest.raises(BibliotecaError):
        Book(id="it_1", title="   ", kind="book")


def test_items_iguales_por_valor() -> None:
    # Arrange: dos instancias distintas con los mismos datos
    a = Book(id="it_1", title="1984", kind="book", year=1949, author="Orwell")
    b = Book(id="it_1", title="1984", kind="book", year=1949, author="Orwell")
    # Assert: dataclass compara por valor, no por identidad
    assert a == b


def test_year_es_opcional() -> None:
    # Los datos incompletos son válidos: año desconocido = None
    assert Movie(id="it_3", title="Blade Runner", kind="movie").year is None
  4. Ejecuta los tests desde la raíz del proyecto: 
    pytest -v

    Resultado esperado: los cuatro tests en PASSED y un resumen 4 passed in 0.01s. Si ves ModuleNotFoundError: No module named 'biblioteca', instala el paquete en modo editable con pip install -e . (o uv sync) para que pytest encuentre el paquete de src/.

  5. Provoca un fallo a propósito para leer la salida de error de pytest: cambia year=1949 por year=1984 en b y vuelve a ejecutar. Observa el bloque assert a == b y cómo pytest muestra la diferencia campo a campo. Después deshaz el cambio.

8 · Reto

🎯 Caza el bug con un test que falla primero

La función search actual busca por título o creador, pero no por id. Escribe un test que documente el comportamiento deseado: service.search(item.id, path=path) debería encontrar ese mismo ítem. Ejecútalo: fallará (rojo). Después amplía el haystack de search para incluir item.id y vuelve a ejecutar hasta verlo en verde.

Pista: en pytest el ciclo es «rojo → verde → refactor». Empieza siempre escribiendo el test que falla; así te aseguras de que el test realmente comprueba algo. Usa pytest -v -k por_id para ejecutar solo ese test mientras iteras.

9 · Resumen

  • Un test fija por escrito una promesa de comportamiento y se ejecuta en milisegundos.
  • pytest es el framework estándar: assert nativo, funciones sueltas y auto-descubrimiento.
  • Descubre archivos test_*.py, funciones test_* y clases Test*.
  • Estructura sana: Arrange – Act – Assert, con un solo comportamiento por test.
  • Usa pytest.raises para excepciones: nunca try/except que se traga el fallo.
ComandoQué hace
pytestDescubre y ejecuta todos los tests del proyecto
pytest -vMuestra un nombre por test (verbose)

10 · Preguntas frecuentes

¿pytest viene incluido con Python?

No. La biblioteca estándar trae unittest, pero pytest es de terceros y se instala como dependencia de desarrollo (pip install pytest o uv add --dev pytest). El curso lo usa porque reduce el código repetitivo y da mejores mensajes de error.

¿Por qué mi test no aparece? Dice «no tests ran».

Casi siempre es el nombre. pytest solo recoge archivos test_*.py o *_test.py y funciones def test_.... Revisa también que estás en la raíz del proyecto; puedes confirmar qué está viendo con pytest --collect-only -q.

¿Dónde pongo los tests?

En una carpeta tests/ en la raíz, separada de src/. Así el código de producción no incluye los tests y ambos quedan instalables por separado. No necesitas un __init__.py en tests/ para empezar.

¿Qué código de salida devuelve pytest?

0 si todo pasa, 1 si algún test falla, 2 si el usuario interrumpe y 5 si no se recogió ningún test. Ese código es lo que permite que la CI (o un pre-commit) bloquee un cambio que rompe la suite.
