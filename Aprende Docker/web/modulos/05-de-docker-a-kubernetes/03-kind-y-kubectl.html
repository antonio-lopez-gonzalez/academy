kind y kubectl: primer contacto

Módulo 5 · De Docker a Kubernetes ⏱ 35 minutos

1 · Introducción

Ya conoces la arquitectura; ahora vas a tocarla. En esta lección levantas tu primer clúster de Kubernetes real, en tu portátil, sin nube y sin máquinas virtuales, con kind (Kubernetes in Docker). Y lo haces con la herramienta que te acompañará todo el curso: kubectl, el mando a distancia que habla en inglés con el apiserver.

Hay un guiño que cierra el círculo del curso: el clúster que vas a crear es un conjunto de contenedores Docker. El «host» de tu clúster es el motor Docker que ya dominas. Todo lo que aprendiste en los módulos 1-4 (imágenes, contenedores, redes, volúmenes) te sirve ahora para entender por qué kind funciona.

¿Por qué kind y no otro? Porque kind es el único «Kubernetes local» que usa un solo runtime (Docker) y casi cero recursos: arranca en ~1 minuto, es reproducible y es el estándar de facto para desarrollo y CI de equipes profesionales. En la sección de teoría compararemos kind con minikube para que entiendas la decisión, no para que la memorices.

2 · Teoría

Qué es kind: «Kubernetes in Docker» — el círculo se cierra

kind crea un clúster de Kubernetes donde cada nodo es un contenedor Docker especial. El plan:

  1. Descarga una node image (kindest/node). Es una imagen de Linux con Docker hub + kubelet + containerd listos, el «sistema base» de tu nodo virtual.
  2. Crea un contenedor por nodo. El primero (kind-control-plane) ejecuta kubeadm y levanta dentro los Pods estáticos del control plane (apiserver, etcd, scheduler, controller-manager).
  3. Los nodos extra (kind-worker, kind-worker2…) se unen al clúster como workers normales.
  4. kind configura el kubeconfig (~/.kube/config) y crea un contexto para que kubectl sepa a qué clúster hablar.
Tu portátil (Linux, macOS o WSL2) ┌──────────────────────────────────────────────────────┐ │ Docker Engine (el «host de hosts») │ │ │ │ ┌──────────────────────────────────────────────┐ │ │ │ contenedor NODO 1: kind-control-plane │ │ │ │ ├─ kubelet + kubeadm (nodo de control) │ │ │ │ └─ Pods del control plane: │ │ │ │ kube-apiserver · etcd · scheduler · ctrl │ │ │ └──────────────────────────────────────────────┘ │ │ ┌──────────────────────────────────────────────┐ │ │ │ contenedor NODO 2: kind-worker │ │ │ │ └─ kubelet + containerd ── tus Pods │ │ │ └──────────────────────────────────────────────┘ │ └──────────────────────────────────────────────────────┘ ▲ │ kubectl habla por HTTPS con el apiserver │ → expuesto en el puerto 6443 del nodo 1 ┌────┴────┐ (un comando basta: kind create cluster) │ kubectl │ └─────────┘

El porqué de que funcione: kind delega la máquina en Docker y levanta un kubelet dentro del contenedor. El kubelet habla con containerd y este con los Pods. Es Kubernetes de verdad — no una simulación — pero el hardware es tu motor Docker.

Analogía: un clúster físico es un «edificio de oficinas»: cada nodo es una planta con sus servidores. kind es un LEGO del mismo rascacielos: las plantas son contenedores en tu escritorio. Mismos inquilinos (kubelet), mismas reglas de incendios (API de K8s), pero las puedes tirar y reciclar en un minuto.

Instalación · kind (multi-OS)

El binario de kind es único y no depende de Python ni de VMs. La instalación canónica:

# ── Linux (incluye WSL2, que es Linux) ─────────────────────────────
# Descarga la última release (v0.2x; el ejemplo usa v0.26.0, mira el tag actual)
curl -Lo ./kind "https://kind.sigs.k8s.io/dl/v0.26.0/kind-linux-amd64"
chmod +x ./kind                     # dale permiso de ejecución
mkdir -p ~/.local/bin
mv ./kind ~/.local/bin/kind         # sin sudo: tu HOME es el PATH
export PATH="$PATH:$HOME/.local/bin"  # añade la carpeta al PATH (guardar en ~/.bashrc)

# ── macOS ──────────────────────────────────────────────────────────
brew install kind                   # Homebrew hace todo por ti

# ── Windows ────────────────────────────────────────────────────────
# NO instales kind nativo en PowerShell: instálalo DENTRO de WSL2
# (es un binario Linux; además el clúster vivirá en Docker, ver callout)

Windows / WSL2 — lee esto. La vía recomendada por el curso (y por kind) es trabajar dentro de una distro Ubuntu de WSL2. Allí instalas kind y kubectl con los binarios de Linux, y Docker Desktop debe tener activa la WSL Integration de esa distro (Settings → Resources → WSL Integration). Así el kubelet de kind ve el Docker de Windows sin fricción. En Windows nativo (PowerShell), kind queda atrapado en la mezcla de filesystems y rutas; es exactamente el caso que estudiaste en la lección de WSL2 del módulo 0.

# ── Windows / WSL2: instalación dentro de la distro Ubuntu ─────────
# (idéntica a la de Linux, ya estás en un sistema de archivos ext4)
wsl --install Ubuntu                 # si no tienes distro aún (desde PowerShell)
# abre la distro y sigue el bloque Linux de arriba:
curl -Lo ./kind "https://kind.sigs.k8s.io/dl/v0.26.0/kind-linux-amd64"
chmod +x ./kind && mkdir -p ~/.local/bin && mv ./kind ~/.local/bin
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc && source ~/.bashrc
kind version                         # verificación: v0.x.x go1.xx

Instalación · kubectl

# ── Linux / WSL2 ───────────────────────────────────────────────────
# kubectl 1.31+ (la versión puede ser la última del canal estable)
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x kubectl
mkdir -p ~/.local/bin && mv kubectl ~/.local/bin/kubectl
kubectl version --client            # verificamos el cliente
kubectl version                     # (con clúster: cliente + servidor)

# ── macOS ──────────────────────────────────────────────────────────
brew install kubectl                # o: brew install kubernetes-cli

# ── Windows ────────────────────────────────────────────────────────
# De nuevo: instala el binario Linux dentro de WSL2, NUNCA el de Windows.

¿Por qué kubectl dentro de WSL y no en PowerShell? Porque kubectl lee ~/.kube/config y habla con el apiserver de kind por localhost:6443. Si el clúster vive en el mundo Linux (WSL), el cliente debe vivir en el mismo mundo para no pelearse con rutas, certificados y barra de filesystem. Es una regla que se repetirá con helm en el módulo 8.

kubectl: contexto y clúster

kubectl es un cliente HTTP con esteroides: transforma tus comandos en peticiones REST al apiserver. Para saber a qué apiserver hablar, usa el kubeconfig (~/.kube/config), un fichero con clústeres, usuarios y contextos (la combinación clúster + usuario + namespace activa). kind escribe su contexto solo al crear el clúster.

kubectl config get-contexts      # lista todos tus clústeres conocidos
kubectl config current-context   # con cuál estás hablando AHORA
kubectl config use-context kind-kind   # cambiar de clúster (kind-<nombre>)

kind vs minikube, la comparativa que importa

La regla del curso: kind siempre como clúster de aprendizaje y CI. Minikube es la alternativa de «modo desktop» cuando quieres addons tipo dashboard listos; no lo usaremos.

3 · Ejemplo mínimo

El ejemplo más pequeño del mundo de K8s son tres comandos: crear el clúster, ver los nodos y ver los Pods del sistema. Este suele ser tu primer contacto real:

# 1 · Crear el clúster (nombre por defecto: "kind")
kind create cluster
#    Creating cluster "kind" ...
#    ✓ Ensuring node image (kindest/node:v1.31.x) 🖼
#    ✓ Preparing nodes 📦
#    ✓ Installing CNI 🔌        ← red del clúster (kindnetd)
#    ✓ Installing StorageClass 💾
#    Set kubectl context to "kind-kind"   ← kubectl ya sabe con quién habla

# 2 · Los nodos (uno solo por defecto: el de control)
kubectl get nodes
#    NAME                 STATUS   ROLES           AGE   VERSION
#    kind-control-plane   Ready    control-plane   45s   v1.31.x

# 3 · Y el control plane, ahora como Pods (la lección 2, en vivo)
kubectl get pods -A
#    NAMESPACE     NAME                                         READY   STATUS
#    kube-system   coredns-…                                    1/1     Running
#    kube-system   etcd-kind-control-plane                      1/1     Running
#    kube-system   kube-apiserver-kind-control-plane            1/1     Running
#    kube-system   kube-controller-manager-kind-control-plane   1/1     Running
#    kube-system   kube-scheduler-kind-control-plane            1/1     Running

En 60 segundos tienes el diagrama completo de la lección 2 ejecutándose dentro de contenedores Docker. Verifícalo y la arquitectura cobra vida:

# El círculo se cierra: tu clúster ES un contenedor Docker
docker ps
#    CONTAINER ID   IMAGE               NAMES
#    …              kindest/node:v1.31  kind-control-plane
kubectl cluster-info     # te da la URL del apiserver (https://127.0.0.1:6443)

4 · Ejemplo real

Ya con el clúster abierto, desplegamos algo pequeño y real para ver las piezas que seguirás usando en HarborTasks. Crearemos un Deployment de nginx con 2 réplicas, lo pondremos a servir a través de un Service y abriremos un túnel local con port-forward.

# ── 1 · Herramientas de lectura -------------------------------------------------
kubectl get nodes              # ¿qué nodos hay? (uno hoy; serán 3 en el reto)
kubectl get pods -A            # Pods en TODOS los namespaces (el sistema completo)
kubectl get all                # el resumen del namespace "default":
#                                 pods, services, deployments, replicasets…

# ── 2 · Crear el primer Deployment (imperativo, solo para probar) ----------------
kubectl create deployment web --image=nginx:1.27 --replicas=2
# deployment.apps/web created
kubectl get deployment web
#    NAME   READY   UP-TO-DATE   AVAILABLE   AGE
#    web    2/2     2            2           10s
kubectl get pods -l app=web     # las 2 réplicas, etiquetadas por el Deployment
#    NAME                  READY   STATUS    RESTARTS   AGE
#    web-5fc94d6d97-abcde   1/1     Running   0          1m
#    web-5fc94d6d97-fghij   1/1     Running   0          1m

# ── 3 · Descubrir el Service y abrir el túnel a localhost ------------------------
kubectl expose deployment web --port=80 --target-port=80 --type=ClusterIP
# service/web exposed
kubectl get svc web
#    NAME   TYPE        CLUSTER-IP      PORT(S)   AGE
#    web    ClusterIP   10.96.x.x       80/TCP    5s

kubectl port-forward deployment/web 8080:80
#    Forwarding from 127.0.0.1:8080 -> 80
#    (deja el comando en ejecución y en OTRA terminal:)
curl http://localhost:8080        # → "Welcome to nginx!"

Fíjate en las decisiones:

  • ClusterIP + port-forward: el Service da una IP interna (10.96.x.x). Como el Pod nginx no expone puerto al host, port-forward crea un túnel localhost:8080 → Pod:80. Perfecto para desarrollo y para cuando quieras probar tu API sin exponerla al mundo.
  • Etiquetas automáticas: el Deployment añade app=web a sus Pods; el Service selecciona esos mismos Pods. Es el puente labels → selector que estudiarás en la lección 4.

Sobre HarborTasks: este «web» ahora es un placeholder de nginx. En el módulo 9, el mismo Deployment apuntará a tu imagen web real con el HTML de HarborTasks, con Service, Ingress y pasando por ConfigMap y Secret. Todos los mandos que acabas de ver son exactamente los que usarás.

Cuando termines la práctica, borra el clúster para no gastar recursos:

kind delete cluster   # elimina el contenedor y el contexto
#    Deleting cluster "kind" ...
docker ps             # → vacío otra vez: el círculo se cierra hacia atrás también

6 · Errores habituales

«Unable to connect to the server: dial tcp … connection refused»

# ❌ Asumir que el clúster sigue vivo solo porque se creó ayer
kubectl get nodes
#    E: Unable to connect to the server: dial tcp 127.0.0.1:6443/timeout

# ✅ Diagnosticar en este orden:
docker ps               # 1) ¿está corriendo Docker? (si no, "daemon not running")
kind get clusters       #    → qué clústeres existen (¿borré el mío?)
kubectl config current-context   # 2) ¿a qué clúster estoy hablando?
kind create cluster     # 3) o recrear: kind es desechable, créalo de nuevo

Confundir el contexto y tocar el clúster equivocado

# ❌ "Borro pods del clúster A… creyendo que en el B"
kubectl delete deployment web     # aplica al CONTEXTO ACTUAL

# ✅ Muéstrate el contexto en cada terminal y exige el tuyo:
kubectl config current-context
#    kind-curso
kubectl config use-context kind-curso
kubectl get all -n default

Usar kubectl de Windows contra un kind de WSL

# ❌ En PowerShell intentar:  kubectl get nodes
#    falla: el kubeconfig de Windows no conoce el clúster de WSL
#    (o conoce la versión equivocada del archivo de configuración).

# ✅ Todo en el mismo mundo (WSL): el clúster y el cliente conviven,
#    y el puerto 6443 se comparte con localhost automáticamente en WSL2.

Creer que `kind create cluster` es «Docker Compose de K8s»

# ❌ "kind levanta pod, service y todo lo de compose.yaml"
#    kind SOLO crea los nodos del clúster (contenedores con kubelet).
#    Los Deployments y Services los creas tú DESPUÉS con kubectl.

# ✅ Separación mental:
#    kind   → crea el clúster (el "edificio")
#    kubectl → crea la carga de trabajo dentro (Pods, Services…)

7 · Ejercicio guiado

Objetivo: poner en pie un clúster «de marca personal», desplegar tu primera app y verla respondiendo en localhost. Todo verificable al detalle.

  1. Paso 1 — Verifica el entorno. Comprueba que Docker responde y que kind/kubectl están instalados: 
    docker version --format '{{.Server.Version}}'   # ¿el daemon responde?
kind version          # kind v0.2x
kubectl version --client   # kubectl v1.3x
  2. Paso 2 — Crea un clúster con nombre propio: 
    # "kind-academy" → creará el contexto "kind-kind-academy"
kind create cluster --name academy
kubectl config current-context      # → kind-kind-academy

    Si Docker está arrancado, en 60 s tienes tu clúster listo.

  3. Paso 3 — Reconoce a los actores de la lección 2. 
    kubectl get nodes -o wide     # 1 nodo, con IP y runtime (containerd)
kubectl get pods -n kube-system   # apiserver, etcd, scheduler, controller…
docker ps                        # el contenedor kind-academy-control-plane
  4. Paso 4 — Despliega y expón: 
    kubectl create deployment echo --image=nginx:1.27 --replicas=2
kubectl rollout status deployment/echo          # "deployment "echo" succesfully rolled out"
kubectl expose deployment echo --port=80 --target-port=80 --type=ClusterIP
kubectl get svc,deploy,pods                     # el trío al completo
  5. Paso 5 — Sírvelo en tu navegador. Deja en esta terminal: 
    kubectl port-forward deployment/echo 9090:80   # ← queda en foreground
  6. Paso 6 — Verifica: en otra terminal «proba» el túnel y después observa la auto-reparación de la plataforma: 
    curl -sI http://localhost:9090 | head -1          # HTTP/1.1 200 OK

# Auto-reparación en vivo: borra un Pod…
kubectl delete pod -l app=echo
# …y mira cómo el Deployment lo recrea solo (déjalo unos segundos):
kubectl get pods -l app=echo
#    NAME                READY   STATUS    RESTARTS
#    echo-…-rxxvv       1/1     Running   0      # ← nuevo, no el borrado
  7. Paso 7 — Recoge y limpia: 
    kubectl delete deployment,service echo    # quita la carga
kind delete cluster --name academy        # apaga el clúster (y su contexto)

Verificación esperada: (1) tres versiones responden en el paso 1; (2) el contexto es kind-kind-academy; (3) ves 5+ Pods en kube-system y un contenedor en `docker ps`; (4-5) el `curl` devuelve 200 por el túnel; (6) tras `delete pod`, aparece un Pod nuevo con timestamp reciente; (7) ya no quedan clústeres. Si algo falla, vuelve a la sección de errores y al orden de diagnóstico (Docker → contexto → recrear).

8 · Reto

🎯 Un clúster de 3 nodos sin pedirlo

kind admite clústeres multi-nodo declarando nodos en un archivo de configuración. Crea el archivo kind-3nodos.yaml (¡puedes buscarte el campo nodes: en la documentación de kind, con role: control-plane y dos role: worker), lanza kind create cluster --name trio --config kind-3nodos.yaml, y responde: 1) ¿Cuántos contenedores ves en docker ps? 2) ¿Qué le ocurre al contexto de kubectl? 3) Despliega 6 réplicas de un echo… ¿en cuántos nodos quedan repartidas y con qué comando lo compruebas?

Pista: el paralelismo con la sección 4 del ejemplo real — las réplicas no eligen nodo, el scheduler decide; kubectl get pods -o wide te muestra la columna NODE.

9 · Resumen

  • kind = Kubernetes in Docker: cada nodo del clúster es un contenedor Docker del motor que ya dominas. El círculo del curso se cierra.
  • Instalación: un binario único para mac/Linux; en Windows, siempre dentro de WSL2 (Linux binaries + integración de Docker Desktop).
  • kubectl es el cliente; el kubeconfig (~/.kube/config) guarda clústeres, usuarios y contextos.
  • Primer viaje: kind create cluster → kubectl get nodes → kubectl get pods -A → docker ps.
  • Para servir algo: kubectl create deployment + kubectl expose + kubectl port-forward.
  • La auto-reparación se ve en vivo: borra un Pod y el Deployment lo recrea.
  • kind vs minikube: contenedores vs VM; kind es el clúster del curso y de CI.

10 · Preguntas frecuentes

¿kind es lo mismo que Docker Compose?

No. Compose levanta servicios sobre un host; kind levanta nodos de un clúster (máquinas con kubelet) también sobre Docker. son distintos niveles de abstracción: Compose «cocina tu stack», kind «construye la cocina» en la que un clúster real ejecutará tu stack. Dentro de kind se usan Deployments y Services (con kubectl), no servicios de Compose.

¿Por qué veo errores de conexión justo después de crear el clúster?

Normalmente porque Docker no está arrancado, o porque kind tardó en configurar el kubeconfig, o porque estás hablando al contexto equivocado. El orden de diagnóstico es: docker ps (¿motor vivo?), kubectl config current-context (¿clúster correcto?) y, si hace falta, kind delete cluster + kind create cluster para partir de cero.

¿Puedo tener varios clústeres kind a la vez?

Sí, y es uno de sus puntos fuertes: cada uno con nombre distinto, cada uno con su nodo-contenedor y su contexto (kind-a, kind-b…). Se alternan con kubectl config use-context. Ojo con los recursos: cada nodo consume CPU/RAM, así que en un portátil no levantes cinco a la vez si no los necesitas.

¿Minikube es mejor para aprender?

Depende del objetivo. Minikube es un «desktop Kubernetes» con VMs y addons (dashboard, ingress) que dan buena experiencia de usuario. kind es más espartano, más rápido y más cercano a cómo se trabaja en CI. En este curso usamos kind por reproducibilidad y por cerrar el círculo con Docker; al terminar, podrás cambiar a minikube en minutos porque los comandos de kubectl son idénticos — el clúster es transparente para el alumno.

¿Necesito Windows Terminal aunque use WSL2?

No es obligatorio, pero es altísimamente recomendable: por defecto Windows abre tu distro en una consola de Windows Terminal — que entiende WSL, colores ANSI y te da pestañas. Para el curso, cualquier terminal que hable con tu distro de WSL sirve; el punto no técnico es que todo tu trabajo de kind/kubectl ocurra dentro de la distro, no fuera.
