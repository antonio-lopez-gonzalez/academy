YAML declarativo y reconciliación

Módulo 5 · De Docker a Kubernetes ⏱ 30 minutos

1 · Introducción

En la lección anterior usaste kubectl create deployment: le ordenaste a Kubernetes qué hacer. Ese estilo imperativo funciona para probar, pero no define cómo trabajan los profesionales. En producción no se dice «crea esto»: se declara el estado deseado en un manifest — un archivo YAML — y la plataforma se encarga de que la realidad coincida con él, para siempre.

Esta lección es el corazón del modelo mental del curso. Aprenderás la anatomía de un manifest propiama (`apiVersion`, `kind`, `metadata`, `spec`), el control loop (deseo ↔ realidad), la idempotencia de `kubectl apply`, y el trío de herramientas que te salvará la vida: `get -o yaml`, `diff` y `dry-run`.

¿Por qué existe esta lección? Porque el 90% de los errores de Kubernetes vienen de dos confusiones: (1) mezclar imperativo con declarativo (gente que «arregla a mano» un Deployment que declaraba otra cosa), y (2) no entender que `kubectl apply` no crea de nuevo sino que ajusta. Esta lección te libra de ambas para el resto del curso.

2 · Teoría

Imperativo vs declarativo: dos fidelidades a un estado

  • Imperativo: dices los pasos. kubectl create deployment web --image=nginx. Si algo cambia, nadie lo vuelve a ejecutar; cada paso es un hecho irrepetible.
  • Declarativo: dices el resultado. En un archivo escribes «quiero un Deployment llamado web con 2 réplicas de nginx». Kubernetes converge hacia ello y lo mantiene.

La metáfora que nunca falla: el imperativo es dar direcciones a un taxi («gira, gira, sigue recto»); el declarativo es dar la dirección destino («llévame a la estación»). Si cierran una calle, el taxista declarativo encuentra otra ruta; el imperativo se queda atascado.

Analogía del termostato: el control loop de Kubernetes es un termostato: declaras 22 °C (estado deseado), él mide 18 °C (estado real) y enciende la calefacción (acción). Cada pocos segundos repite la medición. Nadie «le dice» a la calefacción cuándo encenderse; el bucle lo decide. Kubernetes hace exactamente esto con réplicas, imágenes, servicios y nodos… pero sobre todo el clúster.

La anatomía de un manifest: cuatro campos que se repiten

Todo objeto de Kubernetes se escribe con la misma estructura. Aprender estos cuatro campos es aprender a leer cualquier archivo YAML del ecosistema:

CampoQué esEjemplo
apiVersionEl «contrato» de la API: qué esquema valida este objetov1 (recursos núcleo) / apps/v1 (Deployment, ReplicaSet)
kindEl tipo de objeto que quieresPod, Deployment, Service, ConfigMap…
metadataLa «carné de identidad»: nombre, namespace, etiquetas, anotacionesname: api, labels: app: api
specEl deseo: qué quieres que sea ese objeto (varía según el kind)replicas: 3, containers: …

Por qué `apiVersion` es lo primero: porque es el campo que el apiserver usa para saber cómo validarte. Los `kind` núcleos (Pod, Service, ConfigMap, Secret) son v1; los Deployments se estabilizaron en apps/v1 (la era extensions/v1beta1 y apps/v1beta1 se eliminó en K8s 1.16). Si pones un contrato antiguo, el apiserver lo rechaza en seco.

El control loop: deseo vs realidad

ESTADO DESEADO ESTADO REAL (tu manifiesto YAML) (lo que existE en el clúster) ┌──────────────────────┐ ┌──────────────────────┐ │ Deployment "web" │ │ Deployment "web" │ │ replicas: 2 │ │ replicas: 2 │ │ image: nginx:1.27 │ │ image: nginx:1.26 │ │ │ │ 1 Pod Running │ │ │ │ 1 Pod CrashLoopBackOff│ └──────────┬───────────┘ └──────────┬───────────┘ │ │ └───────────────┬──────────────────┘ ▼ CONTROL LOOP (controller-manager) «compara lo que HAY con lo que PIDO» │ ├── faltan réplicas ──▶ crea Pods nuevos ├── sobran réplicas ──▶ elimina Pods extra ├── imagen distinta ──▶ nuevo ReplicaSet (rolling update) └── Pod caído ────────▶ lo reemplaza (self-healing) │ ▼ el bucle se repite cada pocos segundos

El controller-manager no es una pieza mágica: es el conjunto de bucles que leen el estado real (desde el apiserver) vs el deseado (etcd) y emiten cambios de reconciliación. La diferencia entre tu YAML y la realidad nunca queda «abandonada»: el bucle la vuelve a ver una y otra vez.

kubectl apply: no crea «de cero», reconcilia también el archivo

El nombre lo dice todo: `apply` != `create`. `kubectl create` crea un objeto y falla si existe («AlreadyExists»). `kubectl apply -f` tiene tres modos de acción sobre el objeto:

  • No existe → lo crea.
  • Existe igual → no hace nada (sale con el mensaje «unchanged»). Aquí nace la idempotencia: aplicar el mismo archivo mil veces produce el mismo resultado, sin errores ni duplicados.
  • Existe y difiere → calcula la diferencia y actualiza solo los campos que cambian (reconciliación del propio manifest).

La herramienta idempotente es condición sine qua non para el GitOps: el estado del clúster equivale al contenido de tus archivos versionados. Puedes volver a aplicar tras un fallo sin miedo a «re-crear» nada.

3 · Ejemplo mínimo

El manifest más pequeño con sentido es un Pod: la unidad mínima desplegable. Léelo línea a línea, que es la habilidad que vas a practicar:

# pod-hello.yaml — el «hello world» de Kubernetes (Pod, ~15 líneas)
apiVersion: v1            # contrato de API: los Pods son del grupo núcleo (v1)
kind: Pod                 # qué objeto quiero: UN Pod (un contenedor o varios)
metadata:                 # carné de identidad
  name: hello-pod         # nombre ÚNICO dentro del namespace
  labels:                 # etiquetas: pares clave/valor para selección
    app: hello            #   · «mi Pod se busca con app=hello»
spec:                     # el deseo: cómo es este Pod por dentro
  containers:             # lista de contenedores del Pod (aquí, uno)
    - name: hello         # nombre del contenedor (único dentro del Pod)
      image: nginx:1.27   # qué imagen correr (el runtime la descarga si falta)
      ports:              # información DECLARATIVA (documenta el puerto)
        - containerPort: 80   # no «abre» nada solo con esto: es documentación

Ahora la prueba de fuego del modelo declarativo: kubectl apply puede aplicarse una y otra vez sin romper nada:

# Aplica el manifest (el apiserver valida y persiste el deseo en etcd)
kubectl apply -f pod-hello.yaml
#    pod/hello-pod created

# Lo aplicas DE NUEVO, sin cambios: nadie lo «recrea», nada falla
kubectl apply -f pod-hello.yaml
#    pod/hello-pod unchanged        ← idempotencia en su máxima expresión

# Comprueba la realidad y observa el self-healing en un Pod:
kubectl get pods -l app=hello
kubectl delete pod hello-pod     # ⚠️ un Pod NO se auto-repara… ver teoría 4

Nota importante — por qué un Pod no se auto-repara solo: el Pod describe «quiero que este contenedor exista», pero nada vigila el Pod. La vigilancia llega con un objeto de nivel superior: el Deployment (ejemplo real de esta misma lección). Esa es una de las confusiones más caras en K8s.

4 · Ejemplo real

Manifest de producción de la API de HarborTasks como Deployment. Añade la reconciliación que el Pod solo no tenía: replicas, selección, y el bucle de auto-reparación.

# k8s/api/deployment.yaml — Deployment de la API de HarborTasks
apiVersion: apps/v1                  # contrato estable de Deployments
kind: Deployment                     # controla ReplicaSets → Pods
metadata:
  name: api                          # nombre del Deployment (único)
  namespace: harbortasks             # dónde vive (namespace de la app)
  labels:
    app: api                         # etiqueta del PROPIO Deployment
spec:                                # ← el deseo
  replicas: 3                        # quiero SIEMPRE 3 réplicas (el control
                                     #   loop lo sostiene; si se cae una, crea otra)
  selector:                          # ⚠️ el ancla del Deployment:
    matchLabels:                     #   «cuento como MÍOS los Pods con…»
      app: api                       #   … app=api. Debe coincidir con la
                                     #   etiqueta de la plantilla (abajo).
  template:                          # la «receta» de Pods que gestiona
    metadata:
      labels:                        # las etiquetas que pone a CADA Pod
        app: api                     #  ← debe encajar con matchLabels
    spec:                            # spec del Pod (igual que el Pod suelto)
      containers:
        - name: api
          image: ghcr.io/tu-usuario/harbortasks-api:1.2.0   # imagen real
          ports:
            - containerPort: 3000    # el puerto de Express (documentación)
          env:                       # config por variables (solo un ejemplo;
            - name: PORT             #   ConfigMaps y Secrets llegan en Módulo 7)
              value: "3000"
          resources:                 # peticiones/limites (el scheduler lo usa)
            requests:
              cpu: 100m              # 0.1 CPU garantizada de partida
              memory: 128Mi
            limits:
              memory: 256Mi          # cap: si se pasa, OOMKilled

Decisiones tomadas:

  • `apps/v1` y no `extensions/v1beta1`: contrato moderno y estable; el antiguo ya no se acepta.
  • `selector.matchLabels` + etiqueta de template idénticas: son el pegamento que le dice al Deployment «estos Pods los controlo yo». Si no coinciden, el apiserver rechaza el manifest (lo verás en errores).
  • `replicas: 3`: declaro el número, no «cómo lograrlo». Si borro un Pod, el ReplicaSet del Deployment crea otro con la receta de la template.
  • `resources.requests`: el scheduler elige nodo según esto; los `limits` protegen al clúster de una api hambrienta de memoria.

Posturas en la terminal:

kubectl apply -f k8s/api/deployment.yaml          # created (primera vez)
kubectl get deployment api -n harbortasks          # 3/3 READY
kubectl rollout status deployment api -n harbortasks   # espera al rollout
kubectl get pods -n harbortasks                    # los 3 Pods con sufijo aleatorio

6 · Errores habituales

El selector no coincide con las etiquetas de la template

# ❌ El Deployment busca Pods con app=API y tú etiquetas los Pods app=api
spec:
  selector:
    matchLabels:
      app: API          # ← mayúscula/distinta de la template
  template:
    metadata:
      labels:
        app: api        # ← no coincide
# Error del apiserver: selector do not match template labels

# ✅ Mismo par en los dos sitios
spec:
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api

Usar un contrato de API viejo para Deployments

# ❌ apiVersion: extensions/v1beta1    # se eliminó en K8s 1.16: error directo
apiVersion: extensions/v1beta1
kind: Deployment

# ✅ El contrato moderno de Deployments (estable desde hace años)
apiVersion: apps/v1
kind: Deployment

Creer que un Pod suelto se auto-repara (y que create es idempotente)

# ❌ "Borro el Pod y el sistema lo devolverá" → un Pod suelto NO se recrea
kubectl delete pod hello-pod     # desaparece para siempre (sin Deployment)

# ✅ Quiere que te lo vigile un nivel superior:
#    kubectl apply -f deployment.yaml  → borra uno de sus Pods y verás
#    cómo el ReplicaSet lo reemplaza solito.

# ❌ kubectl create -f hero.yaml  (segunda vez) → error AlreadyExists
# ✅ kubectl apply -f hero.yaml   (n veces)     → created / unchanged / configured

Editar «a mano» un recurso que declaraste en un archivo

# ❌ kubectl edit deployment api      # cambio in-situ que NADIE tiene en Git
# ❌ kubectl scale deployment api --replicas=5    # no reflejado en el YAML

# ✅ Punto de referencia único: el archivo. Cambia replicas en el YAML y…
kubectl apply -f k8s/api/deployment.yaml    # …el clúster converge al archivo
# (Si algo externo lo tocó, apply reconcilia: "configured")

7 · Ejercicio guiado

Objetivo: escribir un Deployment mínimo desde cero, aplicarlo, escalarlo y demostrar que la plataforma converge y se repara sola.

  1. Paso 1 — Crea el archivo deploy-echo.yaml con este contenido exacto: 
    # deploy-echo.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: echo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: echo
  template:
    metadata:
      labels:
        app: echo
    spec:
      containers:
        - name: echo
          image: nginx:1.27
          ports:
            - containerPort: 80
  2. Paso 2 — Aplica y espera a que converja: 
    # Necesitas un clúster: si no lo tienes, "kind create cluster" (lección 03)
kubectl apply -f deploy-echo.yaml          # deployment.apps/echo created
kubectl rollout status deployment/echo     # … "succesfully rolled out"
kubectl get deploy,rs,pods -l app=echo     # Deployment + ReplicaSet + 2 Pods
  3. Paso 3 — Escala editando el archivo (declarativo puro): cambia replicas: 2 → replicas: 3 y vuelve a aplicar: 
    kubectl apply -f deploy-echo.yaml          # deployment.apps/echo configured
kubectl get pods -l app=echo               # ahora 3
# 🎉 no hiciste "scale": dijiste 3 y el bucle lo sostiene
  4. Paso 4 — Prueba la auto-reparación: 
    POD=$(kubectl get pods -l app=echo -o jsonpath='{.items[0].metadata.name}')
echo "Borrando $POD" ; kubectl delete pod "$POD"
sleep 8 && kubectl get pods -l app=echo    # un Pod NUEVO (sufijo distinto)
# como el Deployment pedía 3, la réplica se reconstruye sola
  5. Paso 5 — Contrasta el mundo declarativo con diff/dry-run: 
    # Hacer UN CAMBIO pequeño en el YAML (por ejemplo image: nginx:1.26)
# y ANTES de aplicar…:
kubectl diff -f deploy-echo.yaml          # te muestra exactamente el cambio
#   ± image: nginx:1.26  (el resto «intacto»)
kubectl apply -f deploy-echo.yaml --dry-run=client -o yaml | grep -A3 'metadata:'
#   = ensayo del apply sin tocar el clúster («dry run»)
  6. Paso 6 — No olvides la salida limpia: 
    kubectl delete -f deploy-echo.yaml   # borra lo que creó el manifest
kind delete cluster --name academy   # si usaste el del reto de la lección 3

Verificación esperada: en el paso 2, un Deployment con `READY 2/2` tras el rollout; en el paso 3 pasa a 3 sin touching; en el paso 4, al borrar un Pod aparece otro con sufijo al azar distinto; en el paso 5, `diff` muestra solo la línea de imagen y el `dry-run` imprime el objeto sin cambiarlo. Todo ello demuestra el ciclo declarativo del que habla esta lección.

9 · Resumen

  • Todo manifest tiene 4 bloques: apiVersion, kind, metadata y spec.
  • Modelo declarativo: declaras el destino; la plataforma decide la ruta.
  • El control loop (controller-manager) compara deseo ↔ realidad y actúa; de ahí sale self-healing, escalado y rolling updates.
  • kubectl apply es idempotente: crear / no-op / configurar, sin efectos duplicados.
  • Los Deployments (apps/v1) vigilan ReplicaSets → Pods; un Pod suelto no se recobra solo.
  • El selector + etiqueta es el pegamento que ata Deployment a sus Pods; si no calzan, el apiserver rechaza el archivo.
  • Antes de aplicar: kubectl diff; para ensayar: --dry-run=client -o yaml.
ComandoQué hace
kubectl apply -f archivo.yamlCrea, no-op o «configured» según el estado (idempotente)
kubectl create -f archivo.yamlCreación imperativa: falla si el objeto ya existe
kubectl get deployment/api -o yamlDump del estado REAL del objeto (con campos que el apiserver añade)
kubectl get deployment/api -o jsonpath=…Extrae un campo concreto (p. ej. nombre del primer Pod)
kubectl diff -f archivo.yamlSimula la diferencia que haría apply, sin aplicar
kubectl apply -f archivo.yaml --dry-run=client -o yamlEnsayo del apply (valida y muestra el objeto) sin tocar el clúster
kubectl rollout status deployment/apiEspera a que el Deployment termine de converger

10 · Preguntas frecuentes

¿Por qué `kubectl create deployment` sigue existiendo si lo bueno es apply?

Por comodidad y enseñanza. create deployment te genera un Deployment operativo en una línea (imperativo), y hasta te guarda un registro de la orden. Pero produce estado que no está en ningún archivo, por eso la práctica profesional es: úsalo para explorar y luego kubectl get deployment web -o yaml para copiar la forma, pero mantén el archivo como única fuente de verdad con apply.

¿`apply` sobrescribe lo que hice a mano con `kubectl edit`?

Depende: apply hace reconciliación de los campos que tú declaras en el archivo (la famosa «triple fusión» con el último apply registrado en anotaciones), y respeta campos que el sistema genera. En la práctica, la regla es clara: todo lo que quieras controlar, ponlo en el archivo. Si solo haces kubectl edit, el archivo y el clúster se descuerdan y aplicas sorpresas.

¿Qué es exactamente la «triple fusión» de apply?

Cuando aplicas, Kubernetes compara tres cosas: (1) el estado declarado por tu archivo anterior (guardado en una anotación del objeto), (2) el estado actual del clúster (posiblemente editado por otra persona o el sistema), y (3) tu nuevo archivo. Solo aplica las diferencias de (3) sobre (2), sin pisar lo que no declaras. Así un `apply` no rompe campos gestionados por el propio clúster.

¿Necesito `kubectl diff` siempre antes de aplicar?

Al principio, sí: es la forma de verte actuar y de que los errores sean temas aburridos. Con experiencia, lo harás en cambios delicados (producción, configmaps, secrets, quotas) y te saltarás el ritual de ida y vuelta en demo. La recomendación firme: en cualquier acción con impacto, antes de `apply`, un `diff` y un razonamiento de «¿es exactamente esto lo que quiero?».

¿Qué pasa si aplico un YAML con un error YAML sintáctico?

Cometes un «error YAML» antes de que Kubernetes se entere: `kubectl apply` validará la sintaxis y te dirá algo como error: error validating "x.yaml": error parsing. Los errores de indentación (que en YAML son sagrados: 2 espacios, nunca tabs) son la causa número uno. Mi consejo: haz kubectl apply --dry-run=client -o yaml como mínimo, o valida con una librería antes de llegar al apiserver.
