Verificación y checklist de producción

Módulo 9 · Proyecto final ⏱ 30 minutos

1 · Introducción

Tu stack HarborTasks ya está completo en el clúster: web, API y Postgres, todos conectados tras un Ingress. Pero ¿funciona de verdad? No basta con ver Running: hay que demostrar que el sistema completo respira — que el usuario puede crear una tarea, que sobrevive a reinicios y que los datos no se esfuman.

Esta última lección tiene tres actos: (1) la verificación end-to-end del stack con pruebas reales (crear, listar, reiniciar, persistir); (2) el checklist de producción: esos detalles que separan un "demo que corre" de "algo que puede portar tráfico real"; y (3) los próximos pasos después del curso: CI/CD, GitOps, certificados y observabilidad. Y con ello, despedida: cierras el ciclo completo de Docker → Kubernetes.

¿Por qué una lección entera solo para "verificar"? Porque la mayoría de los fallos de producción NO aparecen al desplegar, sino al perder un nodo, reiniciar un pod o cambiar una variable. Verificar no es "comprobar que funciona": es intentar romperlo a propósito y comprobar que el sistema se repara solo. Es la mentalidad de un ingeniero de SRE.

Errores típicos de esta fase: confundir Running con funcional; probar solo el API y olvidar la web y el Ingress; no probar el escenario de caída (¿qué pasa si un pod muere?); y dar por buena una configuración de "desarrollo" como si fuera producción.

2 · Teoría

Verificación end-to-end: probar el viaje completo del dato

Hay tres niveles de verificación y cada uno merece su prueba:

  1. Estático — los objetos existen y su estado declarado está bien: kubectl get pods/svc/ingress/pvc.
  2. Funcional por capa — el API responde (health/ready), la web sirve HTML, Postgres acepta SQL.
  3. De extremo a extremo — un dato concreto atraviesa todo el sistema: el usuario crea una tarea (POST por el Ingress), el API la inserta en Postgres, y al listarla vuelve a salir. Ninguna prueba en capa suelta garantiza esto.

Analogía (el piloto): un piloto no dice "he despegado, todo funciona". Recorre una checklist: combustible, presurización, flaps, rumbos. Y aunque todo esté bien en tierra, el verdadero examen es un vuelo que aterriza sin incidentes. Esta lección es tu checklist previo al vuelo y tu primer vuelo de prueba.

Resiliencia: el sistema que se repara solo

El valor real de Kubernetes aparece cuando algo falla: si borras un pod, el ReplicaSet crea otro; si cambias la imagen, el Deployment hace un rolling update sin downtime. Nuestras pruebas de verificación matan pods a propósito (con kubectl delete pod) y reinician deployments (kubectl rollout restart) para observar cómo el clúster recupera el estado deseado. Y la joya final: la persistencia — matar el pod de Postgres y comprobar que las tareas siguen ahí porque viven en el PVC, no en el pod.

Desde "funciona en kind" hasta "funciona en producción"

El clúster local te dio la destreza. Producción añade profundidad: observabilidad (métricas, logs, tracing), seguridad (no-root real, NetworkPolicies, Secretos gestionados), entregabilidad (CI/CD reproducible, GitOps con ArgoCD/Flux) y continuidad (backups, snapshots, DR). No son "cosas aparte": son el mismo modelo mental que ya tienes, escalado en tamaño y exigencias.

3 · Ejemplo mínimo

La fotografía mínima del estado del sistema cabe en tres comandos. Si cualquiera de ellos no "cuadra", ya sabes por dónde mirar:

# 1) Todo lo que hay en el namespace, de un vistazo
kubectl get all -n harbortasks
# 2) La puerta de entrada y su backend
kubectl get ingress -n harbortasks
kubectl describe ingress harbortasks -n harbortasks   # "Backends" con IPs listas
# 3) El latido del API (endpoint vivo del proceso)
curl -s http://localhost:8080/api/tasks -H "Host: harbor.test" | head

Qué esperamos ver: en get all todos los pods con READY = 1/1 (o 2/2), Services con sus CLUSTER-IP y HPA estable; en el describe del Ingress, los backends api:80 y web:80 con al menos una IP; y el curl devolviendo JSON con las tareas. Tres comandos, tres capas: objetos, enrutado y datos.

4 · Ejemplo real

Este es el "traje espacial" completo: la batería de verificación de HarborTasks, comentada paso a paso. Se ejecuta con el port-forward del Ingress activo (kubectl port-forward -n ingress-nginx svc/ingress-nginx-controller 8080:80 &).

# ===============================================================
# batería-verificacion.sh — Verificación end-to-end de HarborTasks
# ===============================================================
set -euo pipefail   # "Falla si algo falla": ninguna prueba en falso silencioso

BASE="http://localhost:8080"          # entrada al Ingress vía port-forward
HOST="Host: harbor.test"              # simulamos el nombre de dominio

echo "== 1/6 Estado de los objetos =="
kubectl get pods -n harbortasks       # todo Running y READY completo
kubectl get pvc -n harbortasks        # postgres-data Bound

echo "== 2/6 Salud por capa =="
curl -sf $BASE/api/tasks -H "$HOST" >/dev/null && echo "API OK"
curl -sf $BASE/            -H "$HOST" | grep -qi "<title>" && echo "WEB OK"

echo "== 3/6 Crear una tarea por el API =="
curl -sf -X POST $BASE/api/tasks -H "$HOST" \
  -H "Content-Type: application/json" \
  -d '{"title":"Tarea creada en la verificación"}' | tee /tmp/tarea.json
# Resultado esperado: JSON con la tarea y su id nuevo (4)

echo "== 4/6 Listarla a través de todo el stack =="
curl -sf $BASE/api/tasks -H "$HOST" | grep -q "Tarea creada" && echo "PERSISTE OK"

echo "== 5/6 Reiniciar API y web (rolling update) =="
kubectl rollout restart -n harbortasks deployment/api deployment/web
kubectl rollout status -n harbortasks deployment/api      # espera a "successfully rolled out"
kubectl rollout status -n harbortasks deployment/web
curl -sf $BASE/api/tasks -H "$HOST" | grep -q "verificación" && echo "TRÁFICO RESTAURADO"

echo "== 6/6 Matar el pod de Postgres: ¿sobrevive el dato? =="
kubectl delete pod -n harbortasks -l app=postgres --wait=false
kubectl wait --for=condition=ready pod -n harbortasks -l app=postgres --timeout=90s
curl -sf $BASE/api/tasks -H "$HOST" | grep -q "verificación" && echo "PERSISTENCIA OK"

echo "✔ Batería completa: HarborTasks operativo de extremo a extremo."

Decisiones comentadas: set -euo pipefail convierte cada fallo en error y aborta el script — así no "apruebas" una verificación que falló en silencio. --wait=false mata el pod sin bloquear y luego kubectl wait espera al sustituto. La prueba final demuestra el atributo que más queremos: los datos viven en el PVC, no en el pod.

Bonus de observabilidad: instala el metrics-server y mira la telemetría real del clúster con kubectl top nodes y kubectl top pods -n harbortasks. El HPA del API (lección 2) deja de mostrar <unknown> y empieza a leer CPU de verdad.

5 · Buenas prácticas

El checklist de producción del curso. Revísalo como el piloto revisa el suyo; cada línea responde a un fallo real de los equipos:

ÁreaChecklistPor qué importa
Recursos requests y limits en TODOS los contenedores El scheduler decide con requests; los limits evitan que un pod "coma" a sus vecinos (noisy neighbor)
Probes startup + liveness + readiness con rutas separadas (/health vs /ready) Solo así Kubernetes distingue "vivo" de "listo para tráfico" y recupera sin cortes innecesarios
No-root runAsNonRoot: true, capabilities drop ALL, puertos altos Un contenedor con root explotado = host comprometido. Menos privilegios = menos superficie
Secretos Nunca en git ni en ConfigMap; gestor externo en prod (SOPS/Vault/CSI) Base64 no cifra; la permisología (RBAC) y el gestor son la protección real
Backups pg_dump periódico (CronJob) + restauración probada Un backup que nunca se restauró no es un backup; el drill mensual es el que vale
CI/CD Pipeline: build → test → scan → push → deploy. Versiones inmutables La misma imagen que pasa CI es la que despliegas: reproducible y auditable
Observabilidad Métricas (metrics-server/Prometheus), logs centralizados, alertas con SLOs No puedes arreglar lo que no ves; las alertas avisan antes que los usuarios

6 · Errores habituales

Verificar solo "que esté Running"

# ❌ Criterio de éxito pobre
kubectl get pods -n harbortasks    # todo Running → "¡está desplegado!"
# Running solo significa que el proceso existe. El API podría estar vivo
# sin poder hablar con la BD y la web devolviendo 502 a /api.

# ✅ Criterio de éxito funcional: un dato atraviesa todo el sistema
curl -sf -X POST $BASE/api/tasks -H "$HOST" \
  -H "Content-Type: application/json" -d '{"title":"prueba"}' &&
curl -sf $BASE/api/tasks -H "$HOST" | grep -q "prueba" && echo "E2E OK"

Probar por capas y no el viaje completo

# ❌ Verificar el API aislado (port-forward directo a svc/api)
kubectl port-forward svc/api 8081:80 &
curl http://localhost:8081/api/tasks        # funciona...
# ... pero NO prueba el Ingress: el navegador va por harbor.test, no por aquí.

# ✅ Probar la ruta real del usuario:
kubectl port-forward -n ingress-nginx svc/ingress-nginx-controller 8080:80 &
curl http://localhost:8080/api/tasks -H "Host: harbor.test"   # el viaje completo

Dar por buena una config "de desarrollo" en producción

# ❌ En producción no vale:
#  CORS_ORIGIN: "*"          → cualquier sitio puede llamar al API
#  air-gap de persistent store tipo "standard" local-path → muere con el nodo
#  sin NetworkPolicies       → cualquier pod del clúster alcanza la BD

# ✅ En producción (misma arquitectura, más blindaje):
#  CORS_ORIGIN: https://harbortasks.example.com
#  StorageClass tolerante (ej. gp3/ebs) + backups + snapshots
#  NetworkPolicy: solo el namespace harbortasks alcanza postgres:5432
#  Secretos desde gestor externo (secrets-store-csi, SOPS)

7 · Ejercicio guiado

Objetivo: ejecutar la batería de verificación real, probar la resiliencia a mano y comprobar que el HPA funciona con telemetría.

  1. Paso 1 — Ver el estado estático de todo el namespace: 
    kubectl get all -n harbortasks
kubectl get pvc,ingress -n harbortasks
# Lo esperado: pods READY completos, pvc Bound, ingress con las reglas
  2. Paso 2 — Crear y listar una tarea por el Ingress (flujo completo): 
    # Asegura el canal de prueba y la telemetría
kubectl port-forward -n ingress-nginx svc/ingress-nginx-controller 8080:80 &
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl -n kube-system rollout status deployment/metrics-server

# Crear la tarea
curl -X POST http://localhost:8080/api/tasks -H "Host: harbor.test" \
  -H "Content-Type: application/json" -d '{"title":"Tarea sobreviviente"}'

# Listarla y verla cruzando TODO el stack
curl http://localhost:8080/api/tasks -H "Host: harbor.test"
  3. Paso 3 — Prueba de resiliencia: reiniciar API y web sin perder el servicio: 
    kubectl rollout restart -n harbortasks deployment/api deployment/web

# En OTRA terminal, mientras se hace el rollout:
#   while true; do curl -s http://localhost:8080/api/tasks -H "Host: harbor.test" \
#     | grep -q "sobreviviente" && echo OK || echo FALLO; sleep 1; done
# Con estrategia RollingUpdate no deberías ver FALLO: los pods nuevos
# se hacen Ready antes de que se retiren los viejos.
kubectl rollout status -n harbortasks deployment/api
  4. Paso 4 — La prueba reina: matar el pod de Postgres y comprobar el dato: 
    kubectl delete pod -n harbortasks -l app=postgres --wait=false
kubectl wait --for=condition=ready pod -n harbortasks -l app=postgres --timeout=120s

# El dato sigue ahí (vive en el PVC, no en el pod):
curl -s http://localhost:8080/api/tasks -H "Host: harbor.test" | grep -o "sobreviviente"
  5. Paso 5 — Confirmar la telemetría y el HPA: 
    kubectl top pods -n harbortasks          # CPU/memoria reales por pod
kubectl get hpa api -n harbortasks       # AC = current/target, ya no <unknown>
# Opcional: kubectl describe hpa api -n harbortasks para ver los eventos de escala

    Resultado esperado: la tarea "sobreviviente" aparece listada después de reiniciar API/web Y de matar el pod de Postgres. Esa es la definición operativa de persistencia: el dato no pertenece a ningún proceso, pertenece al volumen.

Para el informe final del curso: guarda las salidas de los 5 pasos en un archivo verificacion.txt o RUNBOOK.md. Tener un runbook que un ingeniero nuevo pueda seguir (y verificar) es una habilidad profesional en sí misma, y este vale como portafolio.

8 · Reto

🎯 Empaqueta HarborTasks en un chart de Helm

Reune los 15+ manifiestos sueltos (namespace, api/*, web/*, postgres/*, ingress) en un único chart de Helm llamado harbortasks: Chart.yaml, values.yaml con image, replicas, resources y ingress.host, y un template por recurso con {{ .Values... }}. Después elimina los objetos aplicados "a mano" e instala todo con un solo helm install, verificando nuevamente la batería E2E. Bonus: crea un segundo values.prod.yaml con más réplicas, recursos mayores y el host real de tu futuro dominio.

Pista: empieza con helm create harbortasks y borra los templates que no uses; el bloque de valores que van a .Values.image.tag te permite cambiar de versión con helm upgrade --set. La lección "Chart de HarborTasks" del módulo 8 tiene la versión de referencia (templates, helpers y la sintaxis de values); el reto es hacerlo tú sin mirarla.

9 · Resumen

  • Verificar de verdad = estático + funcional por capa + end-to-end (un dato que cruza Ingress → API → Postgres y vuelve).
  • Resiliencia: reinicia deployments (rollout restart) y mata pods; el ReplicaSet y las probes lo reparan solos, sin downtime.
  • Persistencia: el dato vive en el PVC, no en el pod; se demuestra matando el pod de Postgres.
  • Checklist de producción: recursos, probes, no-root, secretos, backups, CI/CD, observabilidad.
  • En producción: CORS restringido, StorageClass tolerante, NetworkPolicies, gestor de secretos y alertas con SLOs.
  • Próximos pasos: GitHub Actions (CI/CD), ArgoCD/Flux (GitOps), cert-manager (TLS), Prometheus/Grafana (monitorización), Helm (empaquetado).

10 · Preguntas frecuentes

¿Cuánta verificación es "suficiente" antes de considerar algo listo?

Depende del riesgo: para una demo local, la batería de esta lección sobra. Para producción, se añaden tests automatizados en el pipeline (los tests que ejecutas a mano aquí se vuelven jobs de CI), pruebas de carga, y drills de caos (kill del nodo, perdida de quórum etcd) de forma periódica. Regla útil: verifica siempre lo que más valor tiene para el usuario — aquí, que un dato creado se lea después de una caída.

¿Metrics-server es "observabilidad"?

Es la base: da las métricas de CPU/memoria con las que funciona el HPA y kubectl top. Observabilidad completa añade Prometheus (métricas de la app y del cluster), Grafana (dashboards), Loki/ELK (logs centralizados) y OpenTelemetry (traces distribuidos) — con SLOs y alertas. Es el siguiente módulo profesional natural después de este curso.

¿Necesito GitOps (ArgoCD/Flux) desde ya?

No: es un paso de madurez. El pipeline mínimo sólido es "GitHub Actions construye y publica la imagen → y un despliegue automatizado al clúster". GitOps (ArgoCD/Flux) da un salto cualitativo: el git se convierte en la única fuente de verdad del cluster y el operador sincroniza continuamente. Aprende primero a hacer que una CI/CD sencilla funcione; GitOps lo hará más declarativo después.

¿Y si quiero llevar HarborTasks a la nube de verdad?

Recoge todo lo aprendido: construye las imágenes (M1 – publicar imagen), súbelas a un registry (GHCR/Docker Hub), crea un clúster gestionado (EKS/AKS/GKE), y despliega tu chart de Helm. Sustituye kind por el proveedor, standard local-path por una StorageClass tolerante, añade TLS real con cert-manager + Let's Encrypt, y una NetworkPolicy. El curso te dejó cada pieza: solo cambia el "dónde".

¿Por dónde sigo después de este curso?

Un camino equilibrado: (1) certificación o práctica con el exam de CKA (te obliga a consolidar kubectl); (2) Helm en serio y un chart propio publicado; (3) un proyecto con CI/CD + GitOps real (repositorio + clúster kind + ArgoCD); (4) observabilidad (Prometheus/Grafana) y seguridad (RBAC, NetworkPolicies, Falco). Y sobre todo: desplegar algo tuyo y hacerlo resistir — ese es el verdadero examen final.
