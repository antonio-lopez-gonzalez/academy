Deployments y rolling updates

Módulo 6 · Workloads ⏱ 40 minutos

1 · Introducción

En la lección anterior creaste Pods sueltos y descubriste su carácter efímero: si mueren, nadie los devuelve a la vida. El Deployment es el controlador que soluciona eso para aplicaciones de larga duración: mantiene un número fijo de réplicas funcionando, se auto-repara cuando una cae y te permite actualizar la versión de tu aplicación sin cortar el servicio.

En esta lección entenderás la jerarquía Deployment → ReplicaSet → Pod, por qué el Deployment existe "encima" del ReplicaSet, cómo se hacen los rolling updates (actualización gradual), qué parámetros controlan la velocidad y el riesgo (maxSurge, maxUnavailable, revisionHistoryLimit) y los comandos kubectl rollout para controlar un despliegue.

¿Por qué existe esta lección? Porque desplegar una aplicación moderna sin downtime y poder volver atrás si algo sale mal es la diferencia entre "subir código" y "operar software". El Deployment es la herramienta número 1 que usarás en cualquier clúster.

Errores típicos: aplicar un manifiesto de ReplicaSet creyendo que es un Deployment, escalar a mano en lugar de tocar replicas en el manifiesto, editar objetos vivos con kubectl edit en producción y confundir maxSurge con maxUnavailable.

2 · Teoría

Analogía: el encargado y la brigada

Imagina una flota de reparto. El Pod es un repartidor individual (efímero, puede irse, enfermarse). El ReplicaSet es la brigada: su único trabajo es garantizar que haya exactamente N repartidores trabajando. El Deployment es el encargado: decide qué tamaño debe tener la brigada (10 repartidores), qué reglas de contratación usa y, cuando llega un protocolo nuevo (una versión), organiza cómo sustituir a toda la brigada sin dejar de repartir un solo día.

La jerarquía: Deployment → ReplicaSet → Pod

DEPLOYMENT "api" (replicas: 3, estrategia rollingUpdate) │ pertenece (ownerReference) a ... ▼ REPLICASET "api-74fb9d9c6b" (nueva revisión tras cada cambio de plantilla) │ selecciona pods con matchLabels app: api + pod-template-hash ▼ POD "api-74fb9d9c6b-Xy7zc" ──► Pod "api-74fb9d9c6b-Ab9ws" ──► Pod "api-74fb9d9c6b-Qw2er" (3 réplicas vivas; si una muere, el ReplicaSet crea una nueva)

El ReplicaSet es un controlador del modelo declarativo: lee su campo spec.replicas y compara con los Pods que existen con sus etiquetas. Si hay menos, crea; si hay más, borra. Su bucle interno se llama reconciliación y se ejecuta continuamente.

El Deployment envuelve a los ReplicaSets y añade dos capacidades que el ReplicaSet no tiene:

  1. Rollouts versionados: cada cambio en la plantilla del Pod (spec.template) crea un ReplicaSet nuevo y el Deployment orquesta la transición del viejo al nuevo.
  2. Historial y rollback: guarda las N revisiones anteriores (revisionHistoryLimit, default 10) para poder volver atrás con kubectl rollout undo.

Estrategias de actualización

El campo spec.strategy decide cómo se sustituyen los Pods:

EstrategiaComportamientoCuándo usarla
RecreateBorra TODOS los Pods viejos y luego crea los nuevosSolo cuando el servicio puede tener downtime (tareas por lotes, casos sin tráfico en vivo)
RollingUpdate (default)Sustituye gradualmente: escala el ReplicaSet nuevo mientras escala el viejoCasi siempre: aplicaciones con tráfico real

RollingUpdate se controla con dos porcentajes:

  • maxUnavailable (default 25%): cuántas réplicas pueden estar caídas a la vez durante el rollout. Garantiza que nunca haya menos de replicas - maxUnavailable Pods listos.
  • maxSurge (default 25%): cuántas réplicas extra por encima del objetivo pueden existir. Garantiza que el rollout avance incluso si el nuevo ReplicaSet no escala desapareciendo al viejo.

Analogía: renovar la flota. maxUnavailable: 0 significa "no dejes ni un repartidor menos de servicio"; maxSurge: 1 dice "contrata primero un repartidor nuevo, aprende, y luego jubila a uno viejo". Con un solo activo neutro, la renovación nunca deja de repartir.

Proporcionalidad y revisiones

Desde Kubernetes 1.28+, Progressing usa scaling proporcional: al subir replicas en pleno rollout, la proporción de Pods nuevos vs viejos se mantiene. Además, cada kubectl apply que cambie la plantilla genera una revisión (REVISION 1, 2, 3…). Cambiar solo replicas NO crea revisión, porque la plantilla no cambia.

3 · Ejemplo mínimo

La vía rápida para tener un Deployment sin escribir YAML (útil para probar, no para producción), y luego todo el ciclo de rollout con comandos:

# 1. Crear un Deployment "web" con 1 réplica de nginx.
kubectl create deployment web --image=nginx:1.27-alpine

# 2. Ver la jerarquía completa: deployment, replicaset y pods con su hash.
kubectl get deploy,rs,pods -l app=web
#    NAME             READY   ...
#    deployment.apps/web   1/1
#    replicaset.apps/web-xxx   1/1      <- el replicaset que gestiona el deployment
#    pod/web-xxx-zzz   1/1     Running  <- el pod del replicaset

# 3. Escalar: el Deployment declara el objetivo; el ReplicaSet lo cumple.
kubectl scale deployment web --replicas=3
kubectl get pods -l app=web      # 3 pods

# 4. Disparar un rollout: cambiar la imagen de la plantilla = nueva revisión.
kubectl set image deployment/web web=nginx:1.27.4-alpine

# 5. Seguir el rollout en vivo (muestra "Waiting"/"Successfully rolled out").
kubectl rollout status deployment/web

# 6. Ver el historial de revisiones.
kubectl rollout history deployment/web

Observa el paso 4: kubectl set image modifica spec.template, y eso es exactamente lo que el Deployment interpreta como "nueva versión → nuevo ReplicaSet → rollout". El comando kubectl apply haría lo mismo cuando el archivo YAML cambia.

4 · Ejemplo real

Así sería el Deployment de la API de HarborTasks en producción local con kind. Nota que aquí ya no manejamos Pods sueltos: declaramos el estado deseado y el controlador hace el resto.

deployment-api.yaml
# apiVersion: grupo de API > versión. apps/v1 es el grupo estable para Deployments.
apiVersion: apps/v1
# kind: Deployment (controlador de nivel superior sobre ReplicaSets).
kind: Deployment
metadata:
  name: api
  # namespace: aislamiento del proyecto (se crea en la lección de namespaces).
  namespace: harbortasks
  # labels del propio Deployment (no confundir con las del Pod).
  labels:
    app: api
    project: harbortasks
spec:
  # replicas: estado deseado -> el ReplicaSet reconciliará hasta alcanzarlo.
  replicas: 3
  # selector: el Deployment SOLO gestiona Pods que tengan ESTAS labels.
  # Debe coincidir con las labels del template (error típico si no).
  selector:
    matchLabels:
      app: api
  # revisionHistoryLimit: cuántos ReplicaSets antiguos conserva para el rollback.
  revisionHistoryLimit: 10
  # strategy: cómo se sustituyen los Pods al cambiar la plantilla.
  strategy:
    # RollingUpdate: nunca cortar el servicio (máx 2 réplicas extra, 0 caídas). 
    type: RollingUpdate
    rollingUpdate:
      # maxUnavailable: 0 -> NUNCA hay menos réplicas de las deseadas listas.
      # Los Pods nuevos deben estar READY antes de retirar los viejos.
      maxUnavailable: 0
      # maxSurge: "25%" -> en el punto álgido pueden existir 25% de réplicas extra.
      maxSurge: 25%
  # template: "la receta del Pod". Cualquier cambio aquí dispara un rollout.
  template:
    metadata:
      # labels del POD: el ReplicaSet las usa para contar y seleccionar.
      labels:
        app: api
      # namespace se hereda de arriba (no se repite en el template).
    spec:
      # containers: idénticos a los que viste en la lección de Pods.
      containers:
        - name: api
          # image apunta a la imagen construida en Módulos 1-4. Para kind:
          # kind load docker-image harbortasks-api:1.0.0  (la carga al clúster).
          image: harbortasks-api:1.0.0
          ports:
            - containerPort: 3000
          env:
            # Las variables de entorno reales vendrán de ConfigMap/Secret (Módulo 7).
            - name: PORT
              value: "3000"
            - name: PGHOST
              value: postgres.harbortasks.svc.cluster.local

Operación del ciclo completo con este manifiesto:

# Aplicar el estado deseado (idempotente: puedes aplicarlo N veces).
kubectl apply -f deployment-api.yaml

# Esperar a que el rollout termine y ver las 3 réplicas listas.
kubectl rollout status deployment api -n harbortasks
kubectl get deploy,rs,pods -n harbortasks

# LANZAR v1.0.1: se edita la imagen en el manifiesto y se re-aplica.
# (Aquí, hipotéticamente, la imagen nueva es harbortasks-api:1.0.1)
sed -i 's/harbortasks-api:1.0.0/harbortasks-api:1.0.1/' deployment-api.yaml
kubectl apply -f deployment-api.yaml

# Cinética en vivo y estado. Consulta de las revisiones.
kubectl rollout status deployment api -n harbortasks
kubectl rollout history deployment api -n harbortasks

# Si algo salió mal en la v1.0.1: volver a la anterior al instante.
kubectl rollout undo deployment api -n harbortasks
kubectl rollout status deployment api -n harbortasks

Tip: maxUnavailable: 0 con maxSurge: 25% para 3 réplicas significa que el rollout creará primero 1 Pod nuevo (25% de 3), esperará a que esté Ready y recién entonces retirará un Pod viejo. Coste: el rollout es más lento. Con tráfico real, maxUnavailable: 25% te da velocidad a cambio de menos redundancia momentánea.

6 · Errores habituales

Selector que no coincide con las labels del template

# ❌ selector pide app: api pero el template etiqueta app: backend.
# El Deployment crea los ReplicaSets, pero su contador no encuentra PODS,
# así que escala sin parar (crear/borrar en bucle) y nunca llega a Ready.
selector:
  matchLabels:
    app: api
template:
  metadata:
    labels:
      app: backend        # ❌ NO COINCIDE con el selector

# ✅ Una misma pareja app: api en selector Y en template.
selector:
  matchLabels:
    app: api
template:
  metadata:
    labels:
      app: api

Aplicar un ReplicaSet creyendo que es un Deployment

# ❌ kind: ReplicaSet => sin rollouts, sin historial, sin rollback.
# Si cambias su plantilla, apenas actualiza los pods; no hay "version de la app".
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: harbortasks-api:1.0.0

# ✅ El mismo manifiesto con kind: Deployment da rolling updates + undo.

Confundir maxSurge y maxUnavailable

# ❌ "No quiero caídas" y se ponen ambos al revés:
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 0        # ❌ no permite réplicas extra: el rollout puede atascarse
    maxUnavailable: 1  # ❌ admite 1 réplica caída mientras arranca la nueva

# ✅ Para cero caídas: maxUnavailable 0 y maxSurge mayor que 0.
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0

Usar kubectl create deployment para producción

# ❌ Un comando "a pelo" no queda registrado en Git y pierde estrategia/labels.
kubectl create deployment api --image=harbortasks-api:1.0.0 --replicas=3

# ✅ El manifiesto versionado es la herramienta reproducible de producción.
kubectl apply -f deployment-api.yaml

7 · Ejercicio guiado

Objetivo: desplegar un Deployment de nginx en kind, escalarlo, lanzar un rollout de imagen y volver atrás con rollback.

  1. Paso 1: crea deployment-web.yaml con 3 réplicas de nginx:1.27-alpine, selector/labels app: web, estrategia RollingUpdate con maxSurge: 1 y maxUnavailable: 0: 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
  2. Paso 2: aplícalo y espera el rollout: kubectl apply -f deployment-web.yaml y kubectl rollout status deployment/web (debe imprimir algo como "deployment web successfully rolled out").
  3. Paso 3: verifica la jerarquía y las réplicas: kubectl get deploy,rs,pods -l app=web. Espera 3 Pods Running.
  4. Paso 4: lanza una nueva versión nginx:1.27.4-alpine y observa la transición: 
    # Cambiamos la imagen de forma declarativa en el archivo...
kubectl set image deployment/web web=nginx:1.27.4-alpine

# ...y vemos cómo el rollout avanza POD A POD (nunca caen las 3 a la vez).
kubectl rollout status deployment/web --watch=true
kubectl get pods -l app=web -w    # en otra terminal: verás pods nacer y morir
  5. Paso 5: comprueba el historial: kubectl rollout history deployment/web. Debes ver REVISION 1 (nginx:1.27-alpine) y REVISION 2 (nginx:1.27.4-alpine).
  6. Paso 6: haz rollback a la revisión 1 y verifica el estado final: 
    kubectl rollout undo deployment/web --to-revision=1
kubectl rollout status deployment/web
kubectl get pods -l app=web    # 3 Pods Running con la imagen anterior

Verificación final: el paso 4 es la parte mágica: con kubectl get pods -w deberías ver cómo NUNCA hay menos de 3 Pods Running (por maxUnavailable: 0) y cómo el ReplicaSet nuevo y el viejo conviven durante la transición.

8 · Reto

🎯 Rollout fallido: aprendiendo a volver atrás

Lanza deliberadamente una actualización con una imagen que no existe (nginx:no-existe-999) en tu Deployment web y observa qué pasa: kubectl rollout status, el estado del rollout en kubectl describe deployment web y los eventos de los Pods. Después, recupera la revisión anterior.

Pista: con una imagen inexistente el kubelet nunca consigue arrancar el Pod nuevo, así que el rollout se queda esperando; fíjate en progressDeadlineSeconds (default 600s) y en kubectl rollout undo deployment/web para salir del atasco. También puedes forzar la salida con kubectl rollout status deployment/web --watch=false para ver el mensaje de timeout.

9 · Resumen

  • El Deployment orquesta ReplicaSets, y el ReplicaSet orquesta Pods: tres capas con una responsabilidad clara.
  • El Deployment garantiza N réplicas vivas (reconciliación) y sobrevive a fallos de Pod.
  • Cambiar spec.template genera un nuevo ReplicaSet y una nueva REVISION; ahí arranca el rolling update.
  • rollingUpdate con maxSurge/maxUnavailable controla velocidad vs riesgo; Recreate implica downtime.
  • El historial (revisionHistoryLimit, default 10) habilita kubectl rollout undo.
  • El manifiesto (declarativo y versionado) es el patrón de producción; los comandos kubectl solo para operar.
Comando/ManifiestoQué hace
kubectl apply -f deployment.yamlCrea/actualiza el Deployment y dispara rollout si cambió la plantilla
kubectl scale deployment X --replicas=NCambia el número deseado de réplicas
kubectl set image deployment X C=IMGCambia la imagen de un contenedor y genera nueva revisión
kubectl rollout status deployment XBloquea hasta que el rollout termine (o expire)
kubectl rollout history deployment XMuestra las revisiones del Deployment

10 · Preguntas frecuentes

¿Cuál es la diferencia entre Deployment y ReplicaSet?

El ReplicaSet solo garantiza un número de réplicas. El Deployment añade rollout versionado, historial de revisiones y rollback. En la práctica siempre usarás Deployment: el ReplicaSet es un detalle interno que el Deployment gestiona por ti (aunque aparece en kubectl get rs).

Si borro a mano un Pod de un Deployment, ¿qué pasa?

El ReplicaSet lo detecta en su siguiente reconciliación (segundos) y crea un Pod nuevo desde la misma plantilla. La "población" de Pods es lo que importa, no los individuos. Exactamente el comportamiento opuesto al Pod suelto de la lección 01.

¿maxSurge y maxUnavailable se suman para saber las réplicas máximas?

Sí: durante un rollout con 3 réplicas, maxSurge y maxUnavailable definen un rango permitido: puedes llegar a tener replica count + maxSurge Pods (por exceso) y replica count − maxUnavailable (por defecto). El controlador elige el plan de escalado del ReplicaSet dentro de ese rango.

¿Puedo hacer un rollout sin downtime si la app nueva necesita migración de datos?

Sí, pero la migración debe hacerse compatible hacia atrás (backward compatible): la versión vieja debe seguir funcionando contra el esquema nuevo. Si no puede ser compatible, la alternativa profesional es blue/green o canary: dos Deployments separados con etiquetas distintas y un Service que apunta a uno u otro (tema del reto... y del Módulo 9).
