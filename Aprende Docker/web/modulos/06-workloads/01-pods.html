Pods: la unidad mínima

Módulo 6 · Workloads ⏱ 40 minutos

1 · Introducción

Hasta ahora has visto contenedores gestionados por docker run y orquestados a mano con Compose. Kubernetes introduce una abstracción nueva entre tú y el contenedor: el Pod. Es LA unidad mínima de cómputo de Kubernetes. No existe el concepto de "contenedor suelto": cuando haces kubectl run o escribes un manifiesto, siempre estás pidiendo un Pod.

En esta lección vas a entender por qué Kubernetes decidió que el contenedor no sea la unidad mínima, qué comparten los contenedores dentro de un Pod, cuál es el ciclo de vida completo de un Pod, qué son los initContainers y el patrón sidecar, y cómo inspeccionar un Pod con kubectl.

¿Por qué existe esta lección? Porque todos los workloads del resto del curso (Deployments, Jobs, CronJobs) son, en el fondo, fábricas de Pods. Si no dominas qué es un Pod, el resto de Kubernetes será un montón de YAML sin significado. Es la lección base del Módulo 6.

Errores típicos de esta pieza: pensar que Pod y contenedor son sinónimos, meter varias aplicaciones independientes en un mismo contenedor, olvidar que un Pod es efímero (se borra y sus datos con él) y usar kubectl run como si fuera un docker run de producción.

2 · Teoría

Analogía: el camarote compartido

Piensa en un barco de carga. Cada contenedor de mercancías tiene un propósito propio, pero a veces varias piezas que trabajan juntas deben viajar en el mismo camarote: comparten el espacio, los cables de alimentación y el acceso a la cubierta; suben y bajan del barco juntas. El camarote es la unidad de manipulación — never nos moveremos "una caja suelta" por el muelle. Ese camarote es el Pod y las cajas son los contenedores.

Kubernetes agrupa uno o más contenedores en una unidad de despliegue y scheduling llamada Pod. Todo lo que está dentro de un Pod se programa, arranca y muere como un bloque. Y todos sus contenedores comparten tres cosas fundamentales:

  • La misma red: una única IP de Pod y el mismo localhost. Dos contenedores de un Pod pueden hablarse por 127.0.0.1:puerto entre sí.
  • Los mismo volúmenes de storage: un volumen montado en el Pod se puede montar en todos sus contenedores (lectura/escritura o solo lectura).
  • El mismo ciclo de vida y lugar del mundo: corren en el mismo nodo (la misma máquina) de forma simultánea, con la misma política de reinicio.

Analogía: si un contenedor es una "caja de mercancías", el Pod es el "camarote" donde se estiban las cajas que deben viajar juntas. Kubernetes manipula camarotes, no cajas sueltas: nunca dice "arranca este contenedor", siempre dice "materializa este Pod".

¿Por qué Kubernetes no ejecuta contenedores "sueltos"?

El contenedor único está bien cuando tu aplicación es una pieza aislada. Pero en producción es constantísimo encontrar procesos complementarios que deben vivir pegados a la aplicación: un agente que envía logs, un proxy que cachea respuestas, un proceso que regenera contenido estático, un sidecar de malla de servicios. Si cada uno fuera un contenedor suelto, Kubernetes tendría que coordinar su co-ubicación, su red compartida y su ciclo de vida a mano. El Pod resuelve eso de raíz: todo lo que debe compartir red, storage y ciclo de vida se declara dentro del mismo Pod.

El ciclo de vida de un Pod

Un Pod nace cuando el scheduler lo asigna a un nodo, el kubelet de ese nodo materializa sus contenedores con el runtime (containerd) y el kube-apiserver registra su estado. Las fases son:

FaseQué significaCuándo termina así
PendingEl Pod fue aceptado por el API pero no se ha materializadoEsperando scheduling o descarga de imágenes
RunningAl menos un contenedor está ejecutándoseYa hay procesos vivos
SucceededTodos los contenedores terminaron con código 0Pod finito (Jobs), nunca un Deployment normal
FailedAlgún contenedor terminó con errorEl proceso principal murió con código distinto de 0
UnknownEl nodo no comunica estadoProblemas de red o kubelet caído

Dentro de un Pod, cada contenedor tiene su propio sub-estado Waiting, Running o Terminated. Y ojo, el ciclo de vida es efímero: si un Pod muere (nodo cae, se borra), Kubernetes no lo "revive" — alguien (normalmente un Deployment) crea un Pod nuevo. Nada se reutiliza.

initContainers

Dentro de un Pod puedes declarar contenedores de inicialización (initContainers): corren en orden, uno a uno, y deben completarse (terminar con código 0) antes de que arranque el primer contenedor principal. El resto de contenedores espera. Son perfectos para "esperar a que exista una dependencia", descargar un artefacto, preparar el esquema o ajustar permisos de un volumen. Y se repiten en cada arranque del Pod.

El patrón sidecar (multi-contenedor)

El sidecar es el caso clásico de Pod multi-contenedor: un contenedor auxiliar que acompaña al principal y le da logística (logs, métricas, proxy, refresh de contenido). Comparten el mismo volumen, así que el sidecar puede escribir y el principal leer.

3 · Ejemplo mínimo

El Pod más pequeño que existe: un solo contenedor nginx. Todo corre sobre el clúster de kind creado en el Módulo 5.

pod-nginx.yaml
# apiVersion: grupo/versión de la API de tipo Core (objetos base). Los Pods viven aquí.
apiVersion: v1
# kind: el tipo de objeto que declaramos. Este es un Pod.
kind: Pod
metadata:
  # name: nombre del Pod. Debe ser único dentro del namespace.
  name: pod-nginx
  # labels: etiquetas clave=valor. Son el "pegamento" de Kubernetes:
  # los Services y Deployments las usan para encontrar sus Pods.
  labels:
    app: nginx-demo
spec:
  # containers: lista de contenedores principales del Pod (uno o varios).
  containers:
    # Un elemento por contenedor. Este es el único que tiene este Pod.
    - name: web
      # image: imagen del contenedor, igual que en docker run (sin tag = :latest).
      image: nginx:1.27-alpine
      # ports: PUERTOS QUE EXPONE el contenedor. Es informativo y documenta,
      # no "abre" nada externo (eso lo hacen los Services, lección 03).
      ports:
        - containerPort: 80
          # protocol: por defecto TCP, lo dejamos explícito para que se lea bien.
          protocol: TCP

Comandos de la vida diaria de un Pod, explicados:

# 1. Declaremos el Pod: enviamos el manifiesto al clúster (modelo declarativo).
kubectl apply -f pod-nginx.yaml

# 2. Ver el estado. "-w" vigila en vivo hasta que cambie.
kubectl get pods -w

# 3. Ver qué NODO lo alberga y su IP interna.
kubectl get pods -o wide

# 4. Informe detallado: eventos, imagen, reinicios, fase.
kubectl describe pod pod-nginx

# 5. Logs del contenedor con su nombre (si hay varios, -c nombre).
kubectl logs pod-nginx -c web

# 6. Entrar DENTRO del contenedor (como docker exec).
kubectl exec -it pod-nginx -- sh

# 7. Limpiar. Ojo: un Pod borrado NO se recrea solo.
kubectl delete -f pod-nginx.yaml

Dato clave: kubectl exec -it POD -- COMANDO ejecuta COMANDO dentro del primer contenedor del Pod. Con -c NOMBRE eliges otro contenedor. Es tu llave inglesa para diagnosticar.

4 · Ejemplo real

Llevemos la API de HarborTasks a un Pod. La imagen harbortasks-api:1.0.0 se construyó en los Módulos 1–4; para kind hay que cargarla en el clúster con kind load docker-image (no hay registro remoto). El Pod incluye un initContainer que imita el depends_on de Compose: espera a que Postgres responda antes de arrancar la API.

pod-api-harbortasks.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-api-harbortasks
  # Namespace propio del proyecto (se crea en la lección de namespaces).
  namespace: harbortasks
  labels:
    app: api
    project: harbortasks
spec:
  # initContainers: corren en orden y deben terminar con código 0
  # ANTES de que arranque cualquier contenedor principal.
  initContainers:
    - name: init-wait-postgres
      image: node:20-alpine
      # command/args: sobrescriben el CMD de la imagen. Lanzamos un mini script.
      command: ["/bin/sh", "-c"]
      args:
        - |
          # Bucle de espera: la API no arrancará hasta que Postgres acepte conexión.
          echo "Esperando a postgres.harbortasks.svc.cluster.local:5432..."
          n=0
          until wget -q -O- --timeout=2 postgres.harbortasks.svc.cluster.local:5432 2>/dev/null
          do
            n=$((n+1))
            if [ "$n" -ge 30 ]; then
              echo "ERROR: postgres no respondió en 30 intentos" >&2
              exit 1   # Si sale distinto de 0, el Pod falla y nunca arranca la API.
            fi
            echo "  intento $n: aún no disponible, reintento en 2s"
            sleep 2
          done
          echo "Postgres disponible. Arrancando contenedores principales."
  containers:
    - name: api
      image: harbortasks-api:1.0.0
      ports:
        - containerPort: 3000
      # env: variables de entorno igual que -e en Docker (Módulos 7/8 con ConfigMap/Secret).
      env:
        - name: PORT
          value: "3000"
        - name: PGHOST
          value: postgres.harbortasks.svc.cluster.local   # DNS del Service (lección 03)
        - name: PGDATABASE
          value: tasks

Y ahora el patrón sidecar: un Pod donde nginx sirve contenido estático que un sidecar con Node regenerea dentro de un volumen compartido. Así aprendes el mecanismo exacto de multi-contenedor:

pod-web-sidecar.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-web-sidecar
  labels:
    app: web
spec:
  containers:
    # Contenedor principal: sirve lo que encuentre en /usr/share/nginx/html
    - name: web
      image: nginx:1.27-alpine
      ports:
        - containerPort: 80
      volumeMounts:
        - name: contenido   # nombre del volumen declarado abajo
          mountPath: /usr/share/nginx/html
          readOnly: true    # nginx solo LEE; quien escribe es el sidecar
    # Sidecar: regenera el índice cada 10 segundos en el MISMO volumen.
    - name: generador
      image: node:20-alpine
      command: ["/bin/sh", "-c"]
      args:
        - |
          # Bucle infinito: escribe index.html con la fecha actual.
          while true; do
            date "+<h1>Generado a las %H:%M:%S</h1>" > /contenido/index.html
            sleep 10
          done
  volumes:
    # emptyDir: volumen EFÍMERO (se crea con el Pod, muere con él).
    # Ideal para compartir entre contenedores; NUNCA para persistir.
    - name: contenido
      emptyDir: {}

Por qué importa: ambos contenedores ven el mismo emptyDir porque es un volumen de Pod, no de contenedor. El sidecar escribe, nginx lee. Si un contenedor vive y el otro muere, el volumen sigue mientras el Pod exista.

6 · Errores habituales

Pensar que Pod y contenedor son el mismo concepto

# ❌ Creer que cada Pod tiene exactamente UN contenedor y que "pod" y
# "container" son intercambiables en la documentación. Falso: un Pod
# puede agrupar muchos contenedores que comparten red y storage.

# ✅ Un Pod es la UNIDAD lógica; el contenedor es la unidad de proceso.
# Los Deployments y Services trabajan con Pods, nunca con "contenedores sueltos".

Un selector que no coincide con las labels del Pod

# ❌ metadata.labels dice app: web, pero un Service (lección 03) buscaría app: api
# Resultado: el Service no encuentra endpoints y no llega nadie a tu app.
metadata:
  name: pod-web
  labels:
    app: web

# ✅ La regla de oro: lo que declaras en labels, es lo que usarás para encontrarlo.
# Antes de aplicar, piensa: "¿cómo lo localizaré después?"

Usar kubectl run como si fuera docker run de producción

# ❌ Esta línea sirve para PROBAR, no para producción:
kubectl run api --image=harbortasks-api:1.0.0 --port=3000

# ✅ En producción se declara el estado deseado en un manifiesto y se aplica:
kubectl apply -f pod-api-harbortasks.yaml

# Cuando quieras replicas, autonomía, reintentos y rollback,
# pasa al Deployment de la lección 02.

Esperar que un Pod se recupere tras borrarlo

# ❌ Pensar "si borro el Pod, Kubernetes lo recrea igual que docker restart".
# Docker RESTARTA el mismo contenedor; Kubernetes crea objetos nuevos.
kubectl delete pod pod-nginx   # desaparece para siempre (si no hay ReplicaSet detrás)

# ✅ Si necesitas que el sistema recreé el Pod bajo demanda,
# usa un Deployment: él vuelve a crear el Pod.

7 · Ejercicio guiado

Objetivo: materializar, inspeccionar y entrar en un Pod usando el clúster de kind del Módulo 5.

  1. Paso 1: verifica que el clúster sigue vivo: 
    # Contexto actual y nodos del clúster kind (debe existir uno o más).
kubectl config current-context
kubectl get nodes -o wide
  2. Paso 2: crea el manifiesto pod-nginx.yaml de la sección "Ejemplo mínimo" (etiquétalo app: nginx-demo) y aplícalo: 
    kubectl apply -f pod-nginx.yaml
kubectl get pods -w       # espera a que aparezca Running 1/1
  3. Paso 3: inspecciona el detalle con kubectl describe pod pod-nginx y localiza en el informe: la fase del Pod, la IP, el nodo y los Events (deben mostrar Scheduled y Started container web).
  4. Paso 4: prueba desde DENTRO del Pod que nginx responde: 
    # Entramos a un shell dentro del contenedor "web"
kubectl exec -it pod-nginx -- sh

# Dentro del contenedor: pedimos la página local (wget existe en alpine)
wget -qO- http://localhost/ | head -5
exit   # salimos del shell del contenedor
    Salida esperada: la primera línea es <!DOCTYPE html> o "Welcome to nginx!". La IP localhost funciona porque es la red del Pod en la que vive nginx.
  5. Paso 5: mira los logs del contenedor: kubectl logs pod-nginx. Deben aparecer las peticiones HTTP que acabamos de hacer.
  6. Paso 6: borra y verifica que ya no existe: kubectl delete -f pod-nginx.yaml y kubectl get pods.

Verificación final: si en el paso 4 viste el HTML de nginx y en el paso 6 kubectl get pods ya no muestra pod-nginx, el ejercicio está correcto.

8 · Reto

🎯 Sidecar de logs con hora

Modifica el ejemplo del pod-web-sidecar para que el contenedor api escriba sus logs a un archivo compartido (/logs/app.log) y un contenedor sidecar adicional (tail-logs) haga tail -f de ese archivo en su propio stdout, de modo que kubectl logs pod -c tail-logs muestre la actividad en vivo.

Pista: haz que api escriba con un bucle echo "tarea ${i} procesada" >> /logs/app.log, monta el mismo volumen emptyDir en ambos contenedores y usa command: ["/bin/sh","-c","tail -f /logs/app.log"] en el sidecar. Luego verifícalo con kubectl logs POD -c tail-logs.

9 · Resumen

  • El Pod es la unidad mínima de cómputo de Kubernetes; nunca existen contenedores "sueltos".
  • Los contenedores de un Pod comparten red (IP y localhost), storage y ciclo de vida y se programan juntos en el mismo nodo.
  • El ciclo de vida del Pod: Pending → Running → Succeeded/Failed; los Pods son efímeros y no reutilizables.
  • initContainers: corren en orden y terminan antes que los principales (esperar dependencias, preparar storage).
  • Sidecar: contenedor auxiliar que comparte volúmenes y red con el principal (logs, proxy, refresh de contenido).
  • Comandos esenciales: kubectl apply/get/describe/logs/exec/delete.
Comando/ManifiestoQué hace

10 · Preguntas frecuentes

¿Puede un Pod tener varios contenedores? ¿Cuándo tiene sentido?

Sí. Tiene sentido cuando dos procesos deben compartir red y storage de forma inseparable (patrón sidecar: logs, proxy, proxy mTLS). En HarborTasks, la web y la API NO van en el mismo Pod, porque no necesitan compartir red local: son servicios independientes que se hablan por Service.

Si un Pod se borra, ¿Kubernetes lo vuelve a crear?

Solo si el Pod es gestionado por un controlador (ReplicaSet, DaemonSet, Job…). Un Pod creado "a mano" con kubectl run o un manifiesto kind: Pod se borra y desaparece para siempre. Para garantías de autoreparación y réplicas necesitas un Deployment (lección 02).

¿Qué diferencia hay entre la fase del Pod y el estado de un contenedor?

La fase del Pod (Pending/Running/…) es la visión del conjunto; el estado del contenedor (Waiting/Running/Terminated) es la visión individual. Un Pod puede estar Running con un contenedor en Waiting (p. ej. CrashLoopBackOff). kubectl describe pod muestra ambas capas.

¿Por qué no debería crear Pods a mano para producción?

Porque un Pod no escala, no se autorepara y no tiene despliegues versionados. Los controladores (Deployment, Job, DaemonSet) añaden: número fijo de réplicas, reinicio ante caída, actualizaciones sin downtime y rollback. El Pod es el "atomo"; el controlador es el que lo mantiene vivo.
