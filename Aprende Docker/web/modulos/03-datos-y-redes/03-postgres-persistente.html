Caso: Postgres persistente en Docker

Módulo 3 · Datos y redes Docker ⏱ 35 minutos

1 · Introducción

Llega el momento de unir las dos lecciones anteriores en un caso real, el corazón de HarborTasks: una base de datos PostgreSQL corriendo en un contenedor, con sus datos a salvo en un volumen y accesible para la API por su nombre de red.

Verás el ciclo completo: cómo arrancar la imagen oficial postgres:16-alpine, qué hacen las variables POSTGRES_USER/POSTGRES_PASSWORD/POSTGRES_DB, por qué el volumen va en /var/lib/postgresql/data (y no en otro sitio), cómo montar un healthcheck con pg_isready, cómo comprobar la base desde dentro con docker exec psql, y qué se puede — y qué no se debe — esperar de una base contenerizada (máxima honestidad: esto es un único nodo, no un clúster).

¿Por qué existe esta lección? Porque "Postgres en Docker" es probablemente el contenedor más desplegado de la historia, y el que concentra más errores de novato: sin volumen pierdes todo al hacer docker rm; con variables mal puestas acabas logueándote contra una base con otro usuario; y sin entender el punto de montaje exacto, los datos se quedan en la capa de escritura aunque "hayas montado algo". Esta lección convierte esas tres trampas en hábitos.

2 · Teoría

Por qué Postgres dentro de un contenedor

Postgres es un proceso como cualquier otro: dado un directorio de datos (el PGDATA, por defecto /var/lib/postgresql/data en la imagen oficial), puede arrancar, servir y parar. Contenerizarlo aporta un entorno idéntico en cualquier máquina (la versión de PG la controla la imagen, no tu sistema), una instalación que se docker pull en segundos, y el mismo flujo de despliegue que el resto del stack. El truco de la persistencia ya lo tienes de la lección 1: todo lo que Postgres escribe debe ir a un volumen.

Cómo funciona el arranque de la imagen oficial

La imagen postgres incluye un entrypoint que hace la magia: si el directorio de datos está vacío (primera vez), inicializa un cluster, crea el usuario y la base según las variables de entorno, y arranca. Si el directorio ya tiene datos (re-arranque con nuestro volumen), omite la inicialización y solo arranca. Esta distinción explica un comportamiento que confunde a todo el mundo: cambiar POSTGRES_PASSWORD no cambia la contraseña de una base ya inicializada.

El punto de montaje correcto (la trampa del subdirectorio)

Un error clásico es montar el volumen en /var/lib/postgresql en vez de /var/lib/postgresql/data, o en el subdirectorio pgdata de una versión nueva. La imagen moderna coloca el cluster directamente en data/: si montas el padre, Postgres ve el volumen "con contenido" pero no encuentra el cluster en el sitio esperado, y no vuelve a inicializar (recuerda: solo inicializa si está vacío). Monta siempre exactamente /var/lib/postgresql/data, y un solo volumen por base.

Límites con los que hay que ser honesto

Un docker run postgres es una instancia única (single node): no hay alta disponibilidad, no hay réplicas, no hay failover automático. Las copias de seguridad no las hace "Docker por ti": las haces tú con pg_dump. Para un entorno local, un curso o un primer productivo pequeño es perfecto; para exigir alta disponibilidad, la industria usa soluciones orquestadas (Cloud Native PG sobre Kubernetes, o servicios gestionados) — de eso hablaremos en el curso cuando lleguemos a Helm y operación.

3 · Ejemplo mínimo

Un Postgres con volumen, en una sola línea, y su comprobación inmediata desde dentro con psql.

# 1) Crear el volumen (nombrado: la buena práctica de la lección 1)
docker volume create pgdata

# 2) Arrancar la base: variables + volumen + puerto publicado
docker run -d --name harborpostgres \
  -e POSTGRES_USER=harbor \
  -e POSTGRES_PASSWORD=harborpass \
  -e POSTGRES_DB=harbortasks \
  -v pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16-alpine

# 3) Esperar a que termine el arranque (puede tardar unos segundos)
sleep 5

# 4) Comprobar la salud: pg_isready pregunta si el servidor acepta conexiones
docker exec harborpostgres pg_isready -U harbor
# Salida esperada: /var/run/postgresql:5432 - accepting connections

# 5) Entrar con psql dentro del contenedor y ver la base creada
docker exec -it harborpostgres psql -U harbor -d harbortasks -c "\l"

Desglose línea a línea: -e POSTGRES_* se usan solo en el primer arranque (volumen vacío) para crear usuario, contraseña y base; -v pgdata:… asegura que los datos salgan de la capa efímera; -p 5432:5432 nos deja conectar con psql del host durante el desarrollo; y docker exec … psql es la vía que no necesita instalar nada en el host: ejecuta el cliente psql dentro del propio contenedor de Postgres.

4 · Ejemplo real

El harborpostgres que dejará listo la capa de datos de HarborTasks: con red definida por el usuario (lección 2), healthcheck de verdad, y conectividad desde la API por nombre.

# 0) Preparación: red y volumen
docker network create harbortasks-net
docker volume create pgdata

# 1) PostgreSQL con healthcheck declarado en el propio run
docker run -d --name harborpostgres \
  --network harbortasks-net \
  -e POSTGRES_USER=harbor \
  -e POSTGRES_PASSWORD=harborpass \
  -e POSTGRES_DB=harbortasks \
  -v pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  --health-cmd "pg_isready -U harbor -d harbortasks" \
  --health-interval 5s \
  --health-retries 10 \
  --health-timeout 3s \
  postgres:16-alpine

# 2) Esperar a que el healthcheck pase de "starting" a "healthy"
docker ps --filter name=harborpostgres   # STATUS debe decir (healthy)

# 3) Datos de ejemplo (usuario de HarborTasks)
docker exec harborpostgres psql -U harbor -d harbortasks -c \
  "CREATE TABLE IF NOT EXISTS tasks (id serial PRIMARY KEY, title text NOT NULL);"

# 4) La API se conecta por NOMBRE de contenedor (DNS interno de la lección 2)
docker run -d --name harborapi \
  --network harbortasks-net \
  -e PG_HOST=harborpostgres \
  -e PG_PORT=5432 \
  -e POSTGRES_USER=harbor \
  -e POSTGRES_PASSWORD=harborpass \
  -e POSTGRES_DB=harbortasks \
  -p 3000:8080 \
  harbortasks-api:1.0.0

# 5) Verificación end-to-end: la API responde y toca la base
curl -s http://localhost:3000/api/tasks
curl -s -X POST http://localhost:3000/api/tasks -H 'Content-Type: application/json' \
  -d '{"title":"comprar leche"}'

# 6) Verificar que el dato escribió donde debe: en el volumen (pgdata)
docker exec harborpostgres psql -U harbor -d harbortasks -c "SELECT * FROM tasks;"

Decisiones tomadas: el healthcheck con pg_isready es el patrón canónico — pg_isready está instalado en la propia imagen y responde 0 (OK) cuando el servidor acepta conexiones; así otros servicios o docker ps pueden saber cuándo la base está lista (crucial en Compose, lección 04). La API usa variables de entorno, no código con credenciales, y se conecta a harborpostgres por el DNS interno de harbortasks-net, sin IPs ni localhost. El curl del host mezclado con el SELECT interno demuestra los dos planos: fuera (puerto publicado) y dentro (red privada).

⚠️ Cambio de contraseña sin efecto: si tu base ya está inicializada (el volumen tiene cluster) y modificas POSTGRES_PASSWORD en el run, no cambia nada: el entrypoint solo aplica las variables en el primer arranque. Para rotar la contraseña, ejecuta ALTER USER postgres WITH PASSWORD 'nueva'; con psql (o \password postgres). Esto es una de las preguntas del FAQ; que te sorprenda antes aquí que en producción.

6 · Errores habituales

Sin volumen: los datos mueren con el contenedor

# ❌ Postgres sin persistencia: todo lo creado se pierde al borrar el contenedor
docker run -d --name pg-tmp -e POSTGRES_PASSWORD=x postgres:16-alpine
docker exec pg-tmp psql -U harbor -c "CREATE DATABASE misdatos;"
docker rm -f pg-tmp
# …misdatos ha desaparecido para siempre

# ✅ Con volumen pgdata, el cluster completo sobrevive al contenedor
docker run -d --name pg-tmp -e POSTGRES_PASSWORD=x -v pgdata:/var/lib/postgresql/data postgres:16-alpine

Montar el directorio equivocado

# ❌ Montar el padre de data: Postgres ve un volumen "lleno" y no inicializa
docker run -d -v pgdata:/var/lib/postgresql postgres:16-alpine
# → FATAL: no hay cluster en /var/lib/postgresql/data (el volumen está montado en el padre)

# ✅ El punto exacto del cluster
docker run -d -v pgdata:/var/lib/postgresql/data postgres:16-alpine

Publicar 5432 en producción sin necesidad

# ❌ En producción se trata a la DB como si fuera una app pública
docker run -d -p 5432:5432 -v pgdata:/var/lib/postgresql/data postgres:16-alpine

# ✅ En producción la DB solo la ve la red interna (sin -p); el -p queda para desarrollo
docker run -d --network harbortasks-net -v pgdata:/var/lib/postgresql/data postgres:16-alpine

Ignorar el healthcheck y arrancar la app a ciegas

# ❌ Lanzar la API "por si acaso" sin saber si la base está lista
docker run -d --name harborapi -e PG_HOST=harborpostgres tu-registro/api:v1
# → ECONNREFUSED: la API arrancó antes de que PG aceptara conexiones

# ✅ Preguntar primero con pg_isready (y luego orquestar arranques; Módulo 4)
docker exec harborpostgres pg_isready -U harbor -d harbortasks
# accepting connections → ahora sí, lanza la API

7 · Ejercicio guiado

Objetivo: demostrar la persistencia real del caso: crear datos, matar el contenedor, recrearlo con el mismo volumen, y comprobar que los datos siguen ahí.

  1. Paso 1: crea volumen y arranca la base (si viene de la sección anterior, sáltate la creación del volumen): 
    docker volume create pgdata
docker run -d --name harborpostgres \
  -e POSTGRES_PASSWORD=harborpass -e POSTGRES_DB=harbortasks \
  -v pgdata:/var/lib/postgresql/data \
  -p 5432:5432 postgres:16-alpine
  2. Paso 2: crea una tabla y una tarea reales: 
    docker exec harborpostgres psql -U harbor -d harbortasks -c \
  "CREATE TABLE tasks (id serial PRIMARY KEY, title text);"
docker exec harborpostgres psql -U harbor -d harbortasks -c \
  "INSERT INTO tasks (title) VALUES ('comprar leche');"
  3. Paso 3 — la prueba de fuego: destruye el contenedor por completo (-f fuerza incluso en marcha): 
    docker rm -f harborpostgres
  4. Paso 4: verifica que el volumen sigue existiendo (lección 1: los volúmenes no los borra ni docker rm -f): 
    docker volume ls | grep pgdata
  5. Paso 5: recrea el contenedor con exactamente el mismo volumen. El cluster ya existe dentro de pgdata, así que el entrypoint omite la inicialización y solo arranca (las variables no se reaplican — teoría de la sección 2): 
    docker run -d --name harborpostgres \
  -e POSTGRES_PASSWORD=harborpass -e POSTGRES_DB=harbortasks \
  -v pgdata:/var/lib/postgresql/data \
  -p 5432:5432 postgres:16-alpine
  6. Paso 6 — verificación: los datos creados en el paso 2 siguen ahí: 
    docker exec harborpostgres psql -U harbor -d harbortasks -c "SELECT * FROM tasks;"
# Salida esperada: 1 | comprar leche
  7. Paso 7 — contraste: repite los pasos 1–6 pero sin -v, en una DB recién creada con otro nombre de contenedor, y observa cómo el SELECT del final devuelve tabla inexistente. Así aprende el cuerpo por qué sin volumen no hay persistencia.

8 · Reto

🎯 El backup que nadie menciona

Sin Docker, tu base necesitaría copias de seguridad. Averigua cómo hacer un dump real de tu base harbortasks usando docker exec y la herramienta pg_dump que ya vive dentro de la imagen, y déjalo en una ruta del host (piensa qué mecanismo de la lección 1 necesitas para que el archivo del dump quede fuera del contenedor). Después, simula un desastre: borra el volumen con docker volume rm pgdata (¡tras parar el contenedor!) y restaura la base desde tu dump. Verifica con un SELECT que los datos volvieron.

Pista: docker exec harborpostgres pg_dump -U harbor -d harbortasks vierte SQL por la salida estándar; redirígela a un archivo con el bind mount o con docker cp. Para restaurar en la base vacía: docker exec -i harborpostgres psql -U harbor -d harbortasks < dump.sql. Cuidado: al restaurar una base ya creada, la base harbortasks sigue existiendo aunque el volumen sea nuevo (la imagen la crea con POSTGRES_DB).

9 · Resumen

  • La imagen oficial postgres inicializa solo la primera vez (volumen vacío): las variables de entorno no se reaplican en reinicios.
  • El volumen debe montarse en /var/lib/postgresql/data exactamente; montar el padre rompe la inicialización.
  • POSTGRES_USER, POSTGRES_PASSWORD y POSTGRES_DB definen el arranque inicial; las credenciales van por variables, nunca en código.
  • El healthcheck con pg_isready convierte el contenedor en una señal lista para orquestadores y Compose.
  • La API se conecta por nombre de contenedor en la red del usuario, no por IP ni localhost.
  • docker exec … psql y docker exec … pg_dump dan la vía de administración sin instalar nada en el host.
  • Un contenedor Postgres es una instancia única: prácticо pero sin alta disponibilidad; el backup es responsabilidad tuya.

10 · Preguntas frecuentes

¿Por qué mi POSTGRES_PASSWORD nueva no "se aplica" al reiniciar?

Porque las variables de entorno solo se consumen en el primer arranque con el volumen vacío. Los datos reales del usuario y su contraseña viven en el propio cluster (en pgdata), no en variables. Para rotar la contraseña, usa SQL: docker exec harborpostgres psql -U harbor -c "ALTER USER postgres WITH PASSWORD 'nueva';".

¿Cómo conecto desde mi máquina (host) a este Postgres?

Por el puerto publicado: como lanzaste con -p 5432:5432, desde el host conectas a localhost:5432 (o 127.0.0.1) con tu cliente psql, con el usuario y contraseña de POSTGRES_USER/POSTGRES_PASSWORD. En Windows/WSL2 el localhost del host suele redirigirse bien a WSL2; si no, usa la IP de WSL (lección 04 del módulo 0). Cuidado si ya tienes un Postgres local escuchando en 5432: cambia el lado izquierdo del mapa, p. ej. -p 5433:5432.

¿Pierdo la configuración si actualizo la imagen de 16 a 17?

Los datos sobreviven (están en el volumen), pero el cluster está versionado: la versión de PostgreSQL escribe internamente con su propio formato. Subir de versión es una migración (dump + restore con pg_upgrade), no un simple cambio de tag. Regla: en desarrollo, prueba las migraciones antes; en producción, planifica el momento de mantenimiento. Por eso la buena práctica dice "una sola versión fijada en el equipo".

¿Es seguro exponer 5432 en desarrollo? ¿Y en producción?

En desarrollo es cómodo (conectar con psql desde tu IDE al localhost) y aceptable. En producción evítalo: la base no debe ser alcanzable desde el exterior, solo desde la red interna del stack. Ahí no publicas el puerto y la comunicación viaja por la red bridge privada. Además, una base expuesta a internet sin auth estricta es un objetivo típico de ransomware.

¿Este contenedor es un clúster de Postgres?

No. Es una instancia única: para alta disponibilidad (replicación, failover, backups automatizados) se usan operadores como Cloud Native PG sobre Kubernetes, o servicios gestionados en la nube. Este contenedor es la pieza ideal para tu entorno local, desarrollo y pequeños despliegues; en el Módulo 9 verás cómo trasladarlo a Kubernetes con el patrón correcto.
