Dockerfile básico: FROM, RUN, COPY, CMD

Módulo 1 · Imágenes y Dockerfile ⏱ 35 minutos

1 · Introducción

Descargar imágenes de Docker Hub está muy bien, pero tu aplicación no existe en Docker Hub. Llega el momento de construir tus propias imágenes: eso se hace con un Dockerfile, un archivo de texto que es a la vez la «receta», el contrato y la documentación ejecutable de tu entorno.

En esta lección aprenderás las instrucciones esenciales del Dockerfile —FROM, RUN, COPY, WORKDIR, EXPOSE, CMD—, por qué el orden de las instrucciones importa muchísimo (caché de build), y cómo convertir un Dockerfile en imagen con docker build. Construirás una imagen para una página estática y, como ejemplo real, el Dockerfile casi línea a línea de la API de HarborTasks.

¿Por qué existe el Dockerfile? Porque reproducir un entorno a mano es imposible («en mi máquina funciona»). El Dockerfile declara, paso a paso, exactamente cómo se construye el entorno: misma versión de base, mismas dependencias, mismo código, mismo comando de arranque. Cualquiera (o cualquier CI) con el mismo Dockerfile obtiene la misma imagen.

2 · Teoría

¿Qué es un Dockerfile?

Un Dockerfile es un archivo de texto (Dockerfile, sin extensión) que lista instrucciones, una por línea, que el builder de Docker ejecuta de arriba hacia abajo. Cuando haces docker build, el motor lee el Dockerfile, ejecuta cada instrucción y, como viste en la lección anterior, cada instrucción que toca el sistema de archivos crea una capa nueva de la imagen.

Analogía — la receta de cocina: un Dockerfile es la receta escrita en un papel: «ingredientes» (FROM: el molde/base), «cortar y añadir» (COPY: meter tus archivos), «cocinar» (RUN: instalar y preparar), «poner a qué temperatura» (EXPOSE: puerto), y «cómo servir» (CMD: comando de arranque). Dos cocineros con la misma receta y los mismos ingredientes obtienen el mismo plato: eso es reproducibilidad.

Las instrucciones esenciales

InstrucciónQué hace¿Crea capa?
FROM <imagen>:<tag>Fija la imagen base (obligatoria y primera).Sí (hereda la pila)
WORKDIR /rutaFija el directorio de trabajo para las siguientes instrucciones.No (metadato)
COPY origen destinoCopia archivos/carpetas del contexto de build hacia la imagen.Sí
RUN comandoEjecuta un comando (instalar dependencias, compilar…) y guarda el resultado.Sí
ENV clave=valorDefine variables de entorno de la imagen y del contenedor.No (metadato)
EXPOSE 80Documenta qué puerto escuchará la app (no publica nada).No (metadato)
CMD [...]Define el comando por defecto que se ejecutará al arrancar el contenedor.No (metadato)

Las instrucciones de contenido (RUN, COPY) crean capas; las de metadato (ENV, EXPOSE, CMD, WORKDIR) graban información en el manifiesto de la imagen sin añadir bytes de sistema de archivos.

El contexto de build

Cuando escribes docker build -t nombre:tag ., el . es el contexto: el directorio que se «empaca» y se envía al daemon para que las instrucciones COPY puedan leer de ahí. Todo lo que esté dentro del contexto —aunque el Dockerfile no lo use— viaja hasta el builder. De ahí surge el famoso problema de la carpeta node_modules de 300 MB: llegará a tu imagen si no la excluyes. La solución (el archivo .dockerignore) es la próxima lección.

Orden de instrucciones y caché de build

El builder procesa cada instrucción y, si encuentra una capa idéntica a una ya cacheada (mismo texto de instrucción + mismo contexto), la reutiliza sin volver a ejecutarla. Pero la caché se rompe en cadena: si una instrucción cambia, ella y todas las siguientes se reconstruyen (las anteriores se conservan).

Dockerfile (orden optimizado) Resultado del build ----------------------------------- ----------------------------- FROM node:20-alpine -> [capa base, cacheable] WORKDIR /app -> [metadato, cacheable] COPY package.json package-lock.json ./ -> [capa A: SOLO manifiesto] RUN npm ci -> [capa B: dependencias] COPY src ./src -> [capa C: mi código] ENV NODE_ENV=production -> [metadato] EXPOSE 3000 -> [metadato] CMD ["node", "src/server.js"] -> [metadato] CAMBIA src/server.js -> se reutilizan A y B (caché), se reconstruye solo C + metas. Build en SEGUNDOS, no minutos. CAMBIA package.json -> A y B se rehacen (npm ci), todo lo de debajo también.

La regla de oro del Dockerfile: lo que cambia poco, arriba; lo que cambia mucho, abajo. Dependencias primero, código después.

Forzar reconstrucción completa: si alguna vez sospechas que la caché te está ocultando un problema, usa docker build --no-cache -t ... .. También puedes invalidar solo una instrucción tocando intencionadamente una variable de build (ARG CACHE_BUST=1), aunque lo normal es vivir con la caché bien ordenada.

docker build: del Dockerfile a la imagen

# Sintaxis general: docker build [opciones] <contexto>
docker build -t harbortasks-api:1.0 .

#   -t, --tag  nombre:etiqueta con el que quedará la imagen
#   .          el contexto (directorio actual)
#   Builder moderno: por defecto usa BuildKit (más seguro, más rápido);
#   los detalles de buildx los verás en la lección 04.

3 · Ejemplo mínimo

El ejemplo más pequeño que tiene sentido: coger una página estática y servirla con nginx. El Dockerfile completo son dos instrucciones útiles — el resto ya lo heredas de la imagen oficial.

proyecto/static-app/Dockerfile
# ============ Dockerfile mínimo: sirve una página estática ============
# 1) FROM: la imagen base oficial de nginx sobre Alpine (lección 01:
#    pequeña y con las capas compartidas). Las instrucciones EXPOSE,
#    ENTRYPOINT y CMD ya vienen configuradas por la propia imagen.
FROM nginx:1.27-alpine

# 2) COPY: mete nuestra página en el sitio web por defecto de nginx.
#    El contexto es el directorio donde está index.html (el "." del build).
COPY index.html /usr/share/nginx/html/index.html

# 3) EXPOSE: documentación. nginx escucha en el 80; EXPOSE no publica
#    el puerto, solo informa a quien la use (y a docker inspect).
EXPOSE 80

Construye y ejecútala:

# Preparar la página y construir la imagen desde el directorio del proyecto
printf '<h1>Hola Docker</h1>' > index.html        # o crea index.html a mano

# Build: docker busca "Dockerfile" en el contexto (el .)
docker build -t static-app:1.0 .
# Salida clave:
#   Step 1/3 : FROM nginx:1.27-alpine        -> usa la capa cacheada
#   Step 2/3 : COPY index.html .../index.html -> crea la capa nueva
#   Step 3/3 : EXPOSE 80                     -> metadato
#   Successfully built 9c1bf53e33c8
#   Successfully tagged static-app:1.0

# Ejecutar y comprobar desde el navegador (local) o curl:
docker run -d --name mini-web -p 8080:80 static-app:1.0
curl http://localhost:8080        # --> <h1>Hola Docker</h1>
docker logs mini-web              # nginx dejó su log de acceso

# Limpieza
docker rm -f mini-web

¿Por qué no necesito definir CMD? La imagen oficial nginx ya trae su CMD ["nginx", "-g", "daemon off;"] y su ENTRYPOINT con un script de arranque. Cuando tu Dockerfile no define CMD, el de la imagen base se «hereda». Incluirlo en este ejemplo mínimo solo serviría para confundir: primero entiende la herencia, luego la sobrescritura (lección 03).

4 · Ejemplo real

Ahora el Dockerfile casi línea a línea de la API de HarborTasks: una API REST en Node.js/Express. Fíjate en cómo el orden explota la caché de build.

proyectos/harbortasks/docker/api.Dockerfile
# ============ HarborTasks API — Dockerfile de producción ============
# FROM: imagen oficial de Node en su versión LTS sobre Alpine.
#        "20" es la rama LTS activa; la etiqueta exacta la fijamos al
#        publicar (lección 05). Alpine: runtime pequeño (lección 01).
FROM node:20-alpine

# WORKDIR: crea /app en la imagen, entra en él y lo fija como directorio
#          de trabajo. Las rutas relativas de aquí en adelante parten de
#          /app, y es donde vivirá nuestro código.
WORKDIR /app

# COPY (1º): copia SOLO los manifiestos de dependencias. Importante: si
#            copiáramos todo el proyecto ahora, cualquier cambio en el
#            código invalidaría la caché de la instalación (apartado
#            "orden y caché"), y nos pasamos el npm ci cada vez.
COPY package.json package-lock.json ./

# RUN: instala SOLO dependencias de producción de forma reproducible.
#      npm ci hace una instalación limpia: respeta package-lock.json
#      borra primero node_modules; npm install haría *cualquier* cosa
#      si el lock quedara desactualizado. --omit=dev deja fuera mocha,
#      eslint, etc.: imagen más ligera y con menos superficie de ataque.
RUN npm ci --omit=dev

# COPY (2º): ahora sí, el código fuente. CAMBIA con cada commit, así que
#            va al final para que las capas de arriba sobrevivan en caché.
COPY src ./src

# ENV: variables de entorno de la imagen. NODE_ENV=production cambia el
#      modo de Express (manejo de errores, vistas, caché) y evita que
#      algunas dependencias incluyan su maquinaria de desarrollo.
ENV NODE_ENV=production

# EXPOSE: documenta el puerto 3000 (donde Express escucha). REPITE: no
#         publica nada; la publicación se decide en docker run -p.
EXPOSE 3000

# CMD: comando de arranque en FORMA EXEC (array JSON, sin shell). Node
#      arranca como PID 1 y recibe las señales del sistema directamente.
#      (La diferencia con ENTRYPOINT y con la forma shell te la da la
#      lección 03.)
CMD ["node", "src/server.js"]

Construye y ejecuta (la API es autónoma: datos en memoria para este módulo; la conexión a Postgres llega en el Módulo 3):

# En la raíz del proyecto (donde está api.Dockerfile y src/)
docker build -f docker/api.Dockerfile -t harbortasks-api:1.0 .

# -f: usa este archivo concreto (en vez del "Dockerfile" del contexto).
#     ¿Por qué -f y -t juntos? Para poder renombrar el archivo y porque
#     la imagen se llama como la etiqueta -t, no como el archivo.

docker run -d -p 3000:3000 --name api harbortasks-api:1.0
curl http://localhost:3000/api/tasks        # --> {"tasks": []}  (o similar)
docker logs api                            # Express escuchando en /app
docker exec api ls /app                    # ves /app tal cual la construiste

Windows / CRLF — el error clásico: si editas el Dockerfile (o los scripts .sh que ejecute RUN) con un editor de Windows que guarda CRLF al final de línea, verás fallos extraños: el builder puede rechazar la instrucción al parsear (errores tipo unknown instruction) y los scripts fallan con $'\r': command not found (hay un retorno de carro invisible al final de cada línea). Solución: guarda siempre con saltos de línea LF. La forma más robusta, y que funciona para todo el equipo, es comprometerlo en Git: añade un archivo .gitattributes con * text=auto eol=lf y *.sh text eol=lf — al clonar, Git normaliza a LF y nadie vuelve a romper un script. Lo retomaremos con .dockerignore en la lección 04.

5 · Buenas prácticas

HazEvitaPor qué
Ordena las instrucciones de estable a cambiante: dependencias primero, código al final COPY . . al principio del Dockerfile La caché de build se invalida en cascada; las capas de npm ci y similares solo deben reconstruirse cuando cambia el manifiesto, no con cada commit.
Usa etiquetas fijas en FROM (node:20-alpine) FROM node (sin pin, == latest) Sin etiqueta fija el build depende del día: no es reproducible y puedes «romper» en producción sin tocar código.
npm ci --omit=dev con lockfile presente npm install (o sin package-lock) npm ci instala exactamente lo que fija el lock; evita dependencias flotantes y deja fuera la maquinaria de desarrollo.
WORKDIR al inicio y rutas relativas después Rutas absolutas larguísimas o cd /app && en cada RUN Legibilidad y un único «hogar» para la app: COPY src ./src se lee solo.
CMD en forma exec (array JSON) CMD node src/server.js (forma shell) sin motivo Forma exec lanza el proceso directamente como PID 1, responde a señales y no esconde un /bin/sh -c intermedio. La lección 03 lo detalla.
Mantén la imagen base alpine/slim y solo lo necesario Instalar vim, curl, compiladores… «por si acaso» Cada RUN apk add engorda capas y amplía la superficie de ataque. Si los necesitas para depurar, úsalos con un contenedor temporal.

6 · Errores habituales

Copiar TODO el proyecto antes de instalar dependencias

# ❌ Orden clásico que arruina la caché
FROM node:20-alpine
WORKDIR /app
COPY . .            # TODO el contexto (¡incluida la caché de npm!)
RUN npm ci          # se re-ejecuta SIEMPRE que cambie cualquier archivo
CMD ["node", "src/server.js"]

# ✅ Separar lo que cambia poco de lo que cambia mucho
FROM node:20-alpine
WORKDIR /app
COPY package.json package-lock.json ./   # solo manifiestos
RUN npm ci                               # capa estable: se cachea
COPY src ./src                           # lo volátil, al final
CMD ["node", "src/server.js"]

Creer que EXPOSE publica el puerto

# ❌ "Puse EXPOSE 3000, pero no me conecto desde el navegador"
# EXPOSE solo DOCUMENTA. Sin publicar (-p), el contenedor está aislado.
docker run -d --name api harbortasks-api:1.0
curl http://localhost:3000        # connection refused

# ✅ La publicación es responsabilidad de docker run -p
docker run -d -p 3000:3000 --name api harbortasks-api:1.0
curl http://localhost:3000        # responde
# En Compose (Módulo 4) verás el equivalente con la clave "ports".

Buscar node_modules en la imagen por no usar .dockerignore

# ❌ El contexto se envía ENTERO al builder: tu carpeta node_modules
#    local (cientos de MB) viaja con cada build aunque nadie la copie,
#    y si algún día haces COPY . . termina DENTRO de la imagen.
docker build -t api:1.0 .

# ✅ (Avance) Un .dockerignore con lo obvio aminora el contexto:
# node_modules
# .git
# Dockerfile*
# (lo vemos en profundidad en la lección 04)

Build desde el directorio equivocado

# ❌ Contexto vacío o con la recetas equivocada
docker build -t api:1.0 .            # desde otra carpeta
# ERROR: unable to prepare context: unable to evaluate symlinks: ...
# (no encuentra el Dockerfile en el contexto)

# ✅ Construye desde el directorio raíz del proyecto, o indicando -f
cd /ruta/proyectos/harbortasks        # e.g. ~/proyectos/harbortasks (WSL2)
docker build -f docker/api.Dockerfile -t harbortasks-api:1.0 .

7 · Ejercicio guiado

Objetivo: construir una imagen para una página estática con nginx y ver la caché en acción al modificar solo el contenido.

  1. Paso 1 — Crea el proyecto. 
    mkdir -p ~/proyectos/harbortasks-web   # o C:\... dentro de WSL
cd ~/proyectos/harbortasks-web
printf '<h1>HarborTasks</h1><p>versión 1.0</p>' > index.html
ls -la                                  # verás SOLO index.html (aún)
  2. Paso 2 — Escribe el Dockerfile. Cualquier editor vale (code Dockerfile si usas VSCode).
    Dockerfile
    # Imagen base oficial de nginx (Alpine)
FROM nginx:1.27-alpine
# Copia la página al sitio por defecto de nginx
COPY index.html /usr/share/nginx/html/index.html
# Documentamos el puerto (la publicación la hará docker run -p)
EXPOSE 80
  3. Paso 3 — Construye y anota los pasos. 
    docker build -t harbortasks-web:1.0 .
# Step 1/3 : FROM nginx:1.27-alpine        -- (cacheado)
# Step 2/3 : COPY index.html ...           -- capa NUEVA (solo esta se
#                                              reconstruye al cambiar HTML)
# Step 3/3 : EXPOSE 80
# Successfully built <id> / tagged harbortasks-web:1.0
  4. Paso 4 — Ejecútala y compruébala. 
    docker run -d --name web -p 8080:80 harbortasks-web:1.0
curl http://localhost:8080               # --> <h1>HarborTasks</h1>...
# (en macOS/Windows localhost funciona igual gracias al mapeo de puertos;
#  en Windows/WSL2 Docker redirige localhost automáticamente)
docker ps                                # web  Up  ...  0.0.0.0:8080->80/tcp
  5. Paso 5 — Modifica el código y reconstruye: observa la caché. 
    printf '<h1>HarborTasks</h1><p>versión 1.1</p>' > index.html
docker build -t harbortasks-web:1.1 .
# fíjate: "FROM" sale como CACHED. SOLO la capa de COPY se reconstruye.
docker run -d --name web2 -p 8081:80 harbortasks-web:1.1
curl http://localhost:8081               # --> versión 1.1
  6. Paso 6 — Verificación final. 
    docker images | grep harbortasks-web     # las dos versiones en local
docker history harbortasks-web:1.1       # 2 capas de contenido: base + COPY
# Limpieza:
docker stop web web2 && docker rm web web2
docker rmi harbortasks-web:1.0 harbortasks-web:1.1

Verificación conceptual: el paso 5 demostró la propiedad de las capas de la lección 01. Reconstruir no recrea la imagen base: reutiliza la capa por digest. Por eso el build fue casi instantáneo aunque cambiara el contenido.

8 · Reto

🎯 Caché a prueba de balas

Amplía el ejercicio para que la página estática sirva además una carpeta assets/ (un style.css o una imagen). Tu reto: rediseña el Dockerfile para que cambiar únicamente index.html no vuelva a copiar assets/, es decir, que la capa de assets solo se reconstruya cuando cambie assets, no cuando cambie index.html. Pista: la solución es tan simple como usar dos instrucciones COPY con distintas rutas —pregúntate qué pasa si haces COPY assets ./assets y la capa de COPY index.html ... va DESPUÉS. Compruébalo empíricamente con docker build y observando qué líneas salen como CACHED.

Pista extra: un .dockerignore (lección 04) te evitará además que un node_modules accidental viaje en el contexto.

9 · Resumen

  • El Dockerfile es la receta declarativa de tu imagen: se ejecuta de arriba abajo instrucción a instrucción.
  • FROM fija la base (obligatoria y primera); WORKDIR fija el directorio; COPY mete archivos del contexto; RUN ejecuta comandos; ENV define variables; EXPOSE documenta el puerto; CMD define el arranque.
  • docker build -t nombre:tag . convierte el Dockerfile + contexto en imagen; -f permite usar otro nombre de archivo.
  • El orden importa: lo estable arriba (manifiestos, npm ci), lo volátil abajo (código). Así la caché sobrevive.
  • EXPOSE no publica; publica docker run -p (Módulo 2).
  • npm ci --omit=dev y etiquetas pinedas del FROM = builds reproducibles.
ComandoQué hace
docker build -t <imagen>:<tag> .Construye la imagen con el Dockerfile del contexto marcada con la etiqueta.
docker build -f <archivo> .Usa un Dockerfile con otro nombre (p. ej. docker/api.Dockerfile).
docker build --no-cache .Reconstruye todas las capas ignorando la caché.

10 · Preguntas frecuentes

¿Por qué se llama WORKDIR y por qué debería ponerlo?

WORKDIR /app establece el directorio actual de todas las instrucciones siguientes: COPY src ./src copia a /app/src, RUN se ejecuta ahí, y el contenedor arranca con la terminal ya en /app. Sin él tendrías que usar rutas absolutas (o cd ... && ... en cada RUN), que son más largas, más frágiles y menos legibles.

¿Expose es obligatorio para que funcione el puerto?

No. EXPOSE no hace nada funcional: es documentación para quien use la imagen (aparece en docker inspect y en la descripción de Docker Hub). Aunque lo omitas, docker run -p 8080:3000 funciona igual. La publicación sí depende de -p, de --network host (Módulo 3) o del campo ports de Compose (Módulo 4).

¿Qué diferencia hay entre npm install y npm ci?

npm ci instala exactamente lo que declara package-lock.json y borra primero node_modules: es determinista y reproducible, ideal para builds. npm install puede recalcular y modificar el lock. En el Dockerfile queremos reproducibilidad: usa siempre npm ci cuando exista lockfile (y si no existe, genéralo una vez con npm install en tu máquina y commítalo).

¿Por qué mi build salta «CACHED» aunque haya cambiado el código?

Porque el cambio afectó solo a las instrucciones de abajo y el builder reutilizó las capas de arriba (FROM, bebiendo del caché por digest). Si además modificaste package.json y aún así sale CACHED en npm ci, mira que el COPY package.json package-lock.json ./ viene ANTES (si copias COPY . . antes, cualquier archivo invalida la caché). Y para descartar trucos del caché: docker build --no-cache ..

¿Puedo combinar Dockerfile con bash de Windows / PowerShell?

El contenido del Dockerfile (instrucciones) es independiente del SO, pero los saltos de línea importan: LF sí, CRLF no (ver callout en la sección 4). Los comandos con los que lo construyes y ejecutas sí cambian: docker build/run son idénticos en bash, PowerShell y WSL, así que este curso usa bash como canónico (abre WSL en Windows) y da callouts PowerShell cuando la sintaxis difiere (variables con $env:, comillas…).
