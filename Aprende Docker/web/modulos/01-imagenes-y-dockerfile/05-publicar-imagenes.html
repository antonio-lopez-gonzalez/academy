Etiquetar y publicar imágenes

Módulo 1 · Imágenes y Dockerfile ⏱ 30 minutos

1 · Introducción

Hasta aquí has construido imágenes… pero solo viven en tu máquina. Tarde o temprano necesitas que existan en otro sitio: tu equipo, un CI, el servidor de producción, Kubernetes. Ese «otro sitio» es un registro (Docker Hub, GitHub Container Registry), y publicar allí tu imagen la convierte en un artefacto consumible por cualquiera con acceso.

En esta lección aprenderás las convenciones de nombres y etiquetas (user/imagen:tag), el versionado con semver, por qué los tags son mutables y los digests inmutables, el flujo completo docker login → docker tag → docker push → docker pull en Docker Hub y GHCR, y cómo publicar imágenes multi-arquitectura con Buildx (la pieza que te faltaba de la lección 04).

¿Por qué existe una lección para «publicar»? Porque un tag es un puntero que alguien puede mover, no un contenido. Si tu equipo «hace pull de latest en producción», la falta de inmutabilidad se convierte en downtime. Entender nombres, tags, digests y multi-arch es lo que separa «salí de trabajar con imágenes» de «despliego imágenes como un profesional».

2 · Teoría

El nombre completo de una imagen

Un nombre de imagen tiene esta anatomía:

[registro/]repositorio[:tag]
#     │        │        │
#     │        │        └── la "etiqueta" (versión humana del contenido)
#     │        └─────────── nombre del repositorio (imagen)
#     └──────────────────── registro (a dónde se guarda; por defecto Docker Hub)
Nombre que escribesQué significa de verdad
nginx:1.27-alpinedocker.io/library/nginx:1.27-alpine — imagen oficial (repo library) en Docker Hub.
mi-usuario/mi-app:1.0.0docker.io/mi-usuario/mi-app:1.0.0 — tu repositorio personal (sin library).
ghcr.io/mi-org/mi-app:1.0.0ghcr.io = GitHub Container Registry; repositorio de una org/usuario de GitHub.
localhost:5000/mi-app:1.0.0Un registro local (lo usaremos en el ejercicio, sin cuentas ni internet).

Regla: si no escribes registro ni library, Docker asume docker.io/library/. Las imágenes oficiales (mantenidas por el proyecto) viven en el repositorio library; las tuyas siempre llevan tu usuario/ o tu registro.

Tag ≠ contenido: mutabilidad e inmutabilidad

Un tag es una etiqueta humana que apunta a un digest (el hash SHA-256 de la lección 01). El digest es el contenido real e inmutable; el tag es un puntero mutable: puedes re-tagear la misma imagen o mover el tag a otra imagen.

# Docker Hub del autor de una librería:
#    ghcr.io/mi-org/api:1.2.3   ──> sha256:abcd...
#    ghcr.io/mi-org/api:latest  ──> sha256:ef01...  (¡el mismo tag otro día,
#                                                     otro digest!)
# Fijar por digest es la única referencia 100% inmutable:
ghcr.io/mi-org/api@sha256:abcd...       # esta y no otra, siempre.

La inmutabilidad es la base de todo lo serio: en tu compose.yaml de producción (Módulo 4), en el image de un Deployment en Kubernetes (Módulo 6) y en la cadena de suministro (reproducibilidad, auditoría) podrás fijar cosas por digest.

Versionado con semver en imágenes

Las imágenes se versionan habitualmente con semver (X.Y.Z): 1.0.0, 1.0.1, 2.3.0… Además, los proyectos suelen publicar varias etiquetas apuntando al mismo digest para dar flexibilidad de actualización:

# Todas apuntan AL MISMO digest si se hacen el mismo día:
docker tag mi-app:1.0.0 mi-usuario/mi-app:1.0.0
docker tag mi-app:1.0.0 mi-usuario/mi-app:1.0
docker tag mi-app:1.0.0 mi-usuario/mi-app:1
docker tag mi-app:1.0.0 mi-usuario/mi-app:latest
# Quien quiera "la 1" la tiene; quien quiera pin exacto, la 1.0.0.

El peligro de latest: latest es una convención, no un «modo estable»: cada autor actualiza el tag cuando quiere. En producción usa semver exacto (o digest); reserva latest para desarrollo y demos. (En la lección 02 ya proscribimos FROM node por esto mismo.)

Registros: Docker Hub y GHCR

  • Docker Hub (docker.io): el registro público por defecto. Repos públicos gratis; repos privados con límite/plan.
  • GHCR (ghcr.io): el registro de GitHub, integrado con tus repos y Packages; autenticación con tu token de GitHub (PAT); soporta immutable tags por paquete y control fino de permisos por organización.

Autenticación:

# Docker Hub: login con usuario y password (mejor: usa un "access token"
# generado en hub.docker.com, NUNCA tu password real en el CI).
docker login
# Username: tu-usuario
# Password: ********
# Login Succeeded

# GHCR: login con tu NOMBRE DE USUARIO de GitHub y un PAT con scope
# "write:packages" (para push) / "read:packages" (para pull).
# En 2026 el PAT clásico sigue existiendo junto a los fine-grained tokens.
echo $GITHUB_TOKEN | docker login ghcr.io -u TU-USUARIO --password-stdin
#   (--password-stdin evita que el token quede en el historial de shell)

# Cerrar sesión cuando termines (sobre todo en máquinas compartidas)
docker logout

Windows / WSL2 vs PowerShell: las credenciales de docker login se guardan en el config.json del usuario desde el que ejecutas. Si tu Docker vive en WSL2, haz el login dentro de WSL (bash): el daemon de Docker Desktop compartido lo verá igual, pero la sesión queda en tu distro. Y ojo con las variables: en PowerShell la del token se escribe $env:GITHUB_TOKEN, no $GITHUB_TOKEN; este curso usa bash como canónico (abre WSL en Windows).

Multi-arquitectura: manifest lists y buildx

Un mismo tag puede apuntar a varias imágenes (una por arquitectura) mediante un manifest list (o índice): el registro sirve la manifest list, el cliente elige la arch correcta y Docker descarga solo esa. Entonces docker run funciona igual en un Mac (arm64) que en un servidor x86 (amd64) sin cambiar nada.

# Ver qué plataformas sirve una imagen de múltiples arquitecturas
docker manifest inspect nginx:1.27-alpine
#  "manifests": [ {"platform":{"os":"linux","architecture":"amd64"}, ...}
#                 {"platform":{"os":"linux","architecture":"arm64"}, ...} ]

# Publicar MULTI-ARCH con buildx: un push, varias plataformas a la vez
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t mi-usuario/harbortasks-api:1.0.0 \
  --push .        # --push construye Y sube la manifest list al registro

3 · Ejemplo mínimo

El ciclo completo más pequeño: reetiquetar, publicar y volver a bajar. Usa cualquier imagen que ya tengas (p. ej. la mini-ms:1.0 de la lección 04 o alpine:3.20).

# 1) Etiquetar con tu nombre de usuario + semver
docker tag mini-ms:1.0 mi-usuario/mini-ms:1.0.0

# 2) Publicar en Docker Hub (requiere `docker login` previo)
docker push mi-usuario/mini-ms:1.0.0
# 1.0.0: digest: sha256:... size: ...
# (Hola de nuevo: push = pull al revés; SOLO se suben las capas que el
#  registro no tiene, así que un repush tras un cambio mínimo es rápido)

# 3) Comprobar en el registro que el nombre y el digest están bien:
docker manifest inspect mi-usuario/mini-ms:1.0.0

# 4) Bajar la imagen en otro sitio (o simulando): borrar local y repull
docker rmi mi-usuario/mini-ms:1.0.0
docker pull mi-usuario/mini-ms:1.0.0     # se descarga capa a capa

# 5) Ejecutar lo que acabas de bajar (si es la mini-ms, prueba el puerto)
docker run --rm -d -p 8080:80 mi-usuario/mini-ms:1.0.0 && curl localhost:8080

Analogía — el paquete y la dirección: docker tag es escribir la dirección en el paquete (usuario/repositorio:versión), push es dejarlo en la oficina de correos, pull es recibirlo en casa. Puedes reescribir la etiqueta de un paquete (tag), pero su contenido (digest) no cambia.

4 · Ejemplo real

Publicar la API de HarborTasks a GHCR como imagen multi-arquitectura, con semver y pin por digest. Este es el patrón que verás en los pipelines de CI/CD reales.

# ---- 1. Login en GHCR (PAT con write:packages) ----
echo $GITHUB_TOKEN | docker login ghcr.io -u tu-usuario --password-stdin
# Login Succeeded

# ---- 2. Build multi-arch + push en un solo paso ----
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -f docker/api.Dockerfile \
  -t ghcr.io/tu-usuario/harbortasks-api:1.0.0 \
  -t ghcr.io/tu-usuario/harbortasks-api:1.0 \
  -t ghcr.io/tu-usuario/harbortasks-api:1 \
  --push . \
  --provenance=true
# --provenance=true (BuildKit) adjunta la factura de construcción (SLSA)
#   para alimentar auditorías de cadena de suministro.

# ---- 3. Ver el índice multi-arch publicado ----
docker buildx imagetools inspect ghcr.io/tu-usuario/harbortasks-api:1.0.0
# Name: ...:1.0.0
# MediaType: application/vnd.oci.image.index.v1+json
# Platform: linux/amd64 + linux/arm64 ...
#   (aquí verás UNA entrada por arquitectura: eso es la manifest list)

# ---- 4. Comer de tu propio inventario (prueba de fuego) ----
docker image rm ghcr.io/tu-usuario/harbortasks-api:1.0.0
docker run -d -p 3000:3000 --name api-remota \
  ghcr.io/tu-usuario/harbortasks-api:1.0.0
curl http://localhost:3000/api/tasks     # --> {"tasks":[]}

# ---- 5. Fijar producción POR DIGEST (inmutabilidad real) ----
docker image inspect ghcr.io/tu-usuario/harbortasks-api:1.0.0 \
  -f '{{.RepoDigests}}'
# --> [ghcr.io/tu-usuario/harbortasks-api@ sha256:b2a9...]
# Ese @sha256:... es lo que pondrás en compose.yaml / Deployment de K8s.

Por qué 3 tags en el mismo push: 1.0.0 (pin exacto semver), 1.0 (patch libre), 1.0.0 repetido… — en realidad, el patrón sano es 1.0.0 + 1.0 + 1 + (si quieres) latest, todos al mismo digest. Quien quiera «la menor del rango» tiene facilidad; quien necesita reproducibilidad usa el digest. Publicar varios tags es barato (el repush de etiquetas es instantáneo: solo cambia el puntero) y da un árbol de versionado usable.

5 · Buenas prácticas

HazEvitaPor qué
Versiona con semver y publica varios tags (1.2.3, 1.2, 1) Solo latest, y menos aún en producción El tag es mutable: sin pin queda «a merced» del próximo push de alguien. Semver da rangos de actualización claros.
Fija por digest (imagen@sha256:...) en producción Confiar en que el tag «no cambia» El digest es la única referencia inmutable; si el registro se ve comprometido o un tag se sobrescribe, tú sigues ejecutando exactamente lo auditado.
Autentica en docker login con tokens/PAT y --password-stdin Usar el password real o -p en el historial Los tokens son revocables y no son tu contraseña; en CI los guardas como secret. -p termina en logs e historial de shell.
Publica multi-arch con Buildx (--platform+--push) Una imagen solo para tu arquitectura Es un trabajo de un solo push y permite que cualquiera (ARM/M1, amd64, …) la use sin errores exec format.
Usa GHCR para paquetes privados de tu org; Docker Hub para público Mezclar visibilidad por sorpresa Cada registro tiene política distinta (GHCR permite immutable tags y permisos finos); elige antes de la primera publicación.
Cierra sesión (docker logout) al terminar en máquinas compartidas Dejar sesión abierta eternamente Tu credencial queda viva en su config; un colega (o un atacante) podría push a tu cuenta.

6 · Errores habituales

Push sin login, o al repositorio equivocado

# ❌ Empujar imagen propia en el "namespace" de las oficiales
docker push nginx:1.27-alpine          # denied: requested access...
# (docker.io/library lo reservan oficiales; tú no puedes escribir ahí)

# ❌ Sin login en el registro
docker push mi-usuario/mini-app:1.0.0  # denied: authentication required

# ✅ Tú y tu usuario (Docker Hub) o tu registro (GHCR/otro)
docker login
docker tag mini-app:1.0.0 mi-usuario/mini-app:1.0.0
docker push mi-usuario/mini-app:1.0.0

Pelearse con los «errores de formato» al ejecutar otra arquitectura

# ❌ En tu Mac ARM / Windows ARM intentas correr una imagen GUI x86
docker run --rm --platform linux/amd64 alpine:3.20 uname -a
#   exec format error   (O raro "no matching manifest for linux/arm64")
#   (sin qemu/binfmt el kernel host no ejecuta el binario de la otra arch)

# ✅ Tres salidas honestas:
#   a) si el registro NO ofrece la plataforma, cambiar la referencia;
#   b) publicar multi-arch (nuestra lección): cada quien baja la suya, y
#   c) para construir otras arquitecturas en local, usa --platform en
#      buildx con un builder docker-container (en Docker Desktop, el
#      soporte qemu viene preinstalado para esto).
docker run --rm alpine:3.20 uname -m     # --> aarch64  (tu arch nativa)

Confiar en la etiqueta y que el digest «esté bien seguro»… hasta que muta

# ❌ Producción: "compose.yaml image: mi-app:latest" es una bomba de reloj
#      (verás en Módulo 6 cómo un Deployment parpadea al moverse latest)

# ✅ Producción: deploy de lo que AUDITASTE
#    ghcr.io/mi-org/mi-app@sha256:9f5b0d...
#    (en Compose/K8s se escribe el nombre@digest completo)

Olvidar --push en buildx

# ❌ "Ejecuté buildx con -t pero no aparece en el registro"
docker buildx build --platform linux/amd64,linux/arm64 -t mi-usuario/api:1.0.0 .
#   (sin --push solo construye para la plataforma local y NO publica)

# ✅ --push hace el build + el push de las N plataformas
docker buildx build --platform linux/amd64,linux/arm64 \
  -t mi-usuario/api:1.0.0 --push .

7 · Ejercicio guiado

Objetivo: practicar el ciclo completo tag → push → pull → run sin crear ninguna cuenta, usando un registro local (registry:2, la imagen del propio Docker). Es exactamente la misma mecánica que con Docker Hub/GHCR: cambia solo la URL del registro.

  1. Paso 1 — Levanta un registro local. 
    docker run -d -p 5000:5000 --name registry registry:2
# registry:2 sirve un registro OCI compatible en localhost:5000.
# (En Windows/WSL2 el puerto lo redirige Docker igual que siempre.)
  2. Paso 2 — Etiqueta como si fuera un registro remoto. 
    docker tag mini-ms:1.0 localhost:5000/mi-usuario/mini-app:1.0.0
docker images | grep mini-app          # aparece con el nuevo nombre
  3. Paso 3 — Publica en el registro local (push). 
    docker push localhost:5000/mi-usuario/mini-app:1.0.0
# 1.0.0: digest: sha256:... size: ...  <- exactamente igual que en Docker Hub
  4. Paso 4 — Bórralo todo y vuelve a bajar: el viaje de ida y vuelta. 
    docker rmi localhost:5000/mi-usuario/mini-app:1.0.0
docker pull localhost:5000/mi-usuario/mini-app:1.0.0
docker run --rm -d -p 8080:80 --name prueba \
  localhost:5000/mi-usuario/mini-app:1.0.0
curl http://localhost:8080             # responde: la imagen viajó por registro
  5. Paso 5 — Verificación con el navegador del registro. 
    curl http://localhost:5000/v2/_catalog
# {"repositories":["mi-usuario/mini-app"]}    <- tu repositorio ahí guardado
docker stop prueba && docker rm prueba
docker stop registry && docker rm registry   # fin del "registro de práctica"

Traducción mental: cada comando de este ejercicio es idéntico al que usarías con Docker Hub cambiando localhost:5000/ por mi-usuario/, y con GHCR por ghcr.io/mi-usuario/. Si entiendes el flujo local, entiendes el flujo real; lo único que añade el remoto es el docker login.

8 · Reto

🎯 Publica tu imagen multi-arquitectura en el registro local

Sin crear cuentas, exclusivamente con tu registro local del ejercicio: publica la API de HarborTasks (o mini-ms de la lección 04) para dos arquitecturas a la vez.

Tareas: (1) configura un builder Buildx container con docker buildx create --name mi-builder --driver docker-container y úsalo (docker buildx use mi-builder); (2) ejecuta el build multi-arch contra tu registro local: docker buildx build --platform linux/amd64,linux/arm64 -t localhost:5000/...:1.0.0 --push .; (3) comprueba el índice con docker buildx imagetools inspect localhost:5000/...:1.0.0.

Pista: cuando el driver es docker (el por defecto) Buildx construye «en el entorno de Docker» y solo sirve tu arquitectura; para MULTI-PLATAFORMA necesitas el driver docker-container que empaqueta qemu. Si al final el build «termina» pero no ves más que una plataforma, es que usaste el driver por defecto.

9 · Resumen

  • Nombre completo = [registro/]repositorio[:tag]; sin registro = docker.io, oficiales = library.
  • Tag = puntero mutable; digest = contenido inmutable.
  • Versiona con semver publicando varios tags (1.2.3, 1.2, 1) + digest para producción.
  • Flujo: docker login → docker tag → docker push → (en otro sitio) docker pull.
  • Registros: Docker Hub (docker.io) público; GHCR (ghcr.io) con PAT, immutable tags y control por org.
  • Multi-arch = manifest list: Buildx --platform + --push publica N imágenes bajo un tag.
  • Un registro local (registry:2) te deja practicar el flujo completo sin cuentas.
ComandoQué hace
docker tag <img> <nuevo-nombre>[:tag]Reetiqueta la imagen (crea otro nombre apuntando al mismo contenido).
docker push <user>/<img>:<tag>Sube las capas que falten al registro.
docker pull <user>/<img>:<tag>Baja las capas que falten en local.
docker login [registro]Autentica con tus credenciales (preferible: token/PAT).

10 · Preguntas frecuentes

¿Qué es más fiable, el tag o el digest?

Siempre el digest: es el hash del contenido y nunca cambia. El tag es comodidad humana (legible y mutable). La práctica profesional: usa semver para trabajar, y el pin por digest (@sha256:...) para todo lo que sea producción, despliegues automatizados y auditorías: si alguien sobrescribe un tag, tu referencia no se mueve.

¿Necesito cuenta en Docker Hub para publicar? ¿Y para descargar?

Para publicar en Docker Hub sí (usuario + repositorio propio, o una org). Para descargar repos públicos NO: docker pull ubuntu:24.04 funciona sin cuenta (con límites de tasa anónimos). GHCR igual: pull público sin login, push con tu usuario de GitHub y un PAT con write:packages.

¿«latest» se actualiza solo?

No. «latest» es un tag normal: no se actualiza «solo», sino cuando el autor decide anclarlo a otra imagen. Por eso no debes asumir su significado: puede ser estable, inestable o simplemente abandonado. Nunca lo uses como «la última versión»; mira los semver del repositorio.

¿Qué es exactamente una manifest list (índice)?

Es una lista de manifiestos: una entrada por plataforma (os + arquitectura) apuntando cada una a su digest. Cuando haces pull de un tag multi-arch, Docker consulta el índice, elige la entrada de tu plataforma y descarga solo esa imagen. Como ahora también se publican manifest lists nativas (arm64/amd64), macOS ARM y servidores x86 consumen el mismo tag.

¿Puedo borrar una imagen ya publicada?

Depende del registro. Docker Hub permite borrar repos/tags (desde la web) pero no por CLI; GHCR permite eliminar imágenes y activó «immutable tags» (no se pueden sobrescribir versiones concretas). Regla de oro: en producción no sobreescribas un tag semver ya publicado — publica una versión nueva; si rompes una referencia por digest destruida, rompes a quien la consume.
