Imágenes, capas y Union FS

Módulo 1 · Imágenes y Dockerfile ⏱ 30 minutos

1 · Introducción

Todo en Docker empieza por una imagen. Un contenedor no deja de ser una imagen en ejecución: sin imágenes no hay contenedores, sin imágenes no hay docker compose, y sin imágenes no hay Pods en Kubernetes. Por eso, antes de escribir un solo Dockerfile, hay que entender de qué está hecha una imagen y por qué su diseño —capas, Union FS y copy-on-write— es la clave de todo el ecosistema.

En esta lección aprenderás qué es exactamente una imagen, qué son las capas (layers), cómo las monta el Union FS (overlay2), qué significa copy-on-write y por qué las imágenes son inmutables. Además dominarás los cuatro comandos con los que vas a trabajar imágenes durante todo el curso: docker pull, docker images, docker inspect y docker history.

¿Por qué existe esta lección? Porque casi todos los errores de Docker (imágenes que «pesan demasiado», builds lentos, versiones que cambian sin avisar) se explican con una buena comprensión de las capas. El día que entiendas capas, Union FS y copy-on-write, el Dockerfile de la siguiente lección dejará de ser magia y se convertirá en lógica pura.

2 · Teoría

¿Qué es una imagen?

Una imagen Docker es un snapshot de un sistema de archivos + metadatos, solo de lectura, que contiene todo lo necesario para ejecutar una aplicación: el sistema base (por ejemplo Alpine), las librerías, el runtime (Node, nginx), el código de tu aplicación y la configuración (variables de entorno, puertos, comando de arranque).

Analogía — la receta y la tarta: una imagen es la receta y los ingredientes envasados; un contenedor es la tarta ya horneada que se está sirviendo. Puedes hornear la misma tarta mil veces a partir de la misma receta: cada vez sale una tarta nueva, con su propio plato, pero todas usan exactamente la misma receta. Y la receta no cambia mientras la estás horneando: es inmutable.

Una imagen no es un disco de máquina virtual. No contiene un kernel ni arranca un sistema operativo completo. Una imagen es solo un conjunto de archivos + metadatos que el motor Docker monta como sistema de archivos raíz (rootfs) sobre el kernel del host. Por eso los contenedores pesan megabytes y las VMs gigas, y por eso arrancan en milisegundos.

Capas (layers): la anatomía de una imagen

Una imagen no es un bloque monolítico: es una pila de capas (layers). Cada capa es un conjunto de cambios (archivos añadidos, modificados o borrados) respecto a la capa anterior, guardado de forma comprimida y con un digest (un hash SHA-256) que la identifica de forma única e inmutable.

Cuando construyas una imagen con un Dockerfile, cada instrucción que toca el sistema de archivos (RUN, COPY, ADD) crea una capa nueva. Las instrucciones de metadatos (CMD, EXPOSE, ENV, WORKDIR) no crean contenido, solo «pegatinas» en el manifiesto de la imagen.

+------------------------------------------------------------------+ | CONTENEDOR (solo él tiene escritura) | | | | capa del contenedor (fina, se crea al arrancar; aquí van | | todos los cambios en caliente: logs, caches, archivos que | | escribe tu app) . . . . . . . . . . . <- COPY-ON-WRITE | +------------------------------------------------------------------+ | IMAGEN NGINX:1.27-ALPINE (inmutable, compartida) | | +------------------------------------------------------------+ | | | capa 3 (digest D3): COPY index.html /usr/share/nginx/html | | | +------------------------------------------------------------+ | | | capa 2 (digest D2): apk add --no-cache ... (dependencias) | | | +------------------------------------------------------------+ | | | capa 1 (digest D1): Alpine base (musl, apk, su shell) | | | +------------------------------------------------------------+ | +------------------------------------------------------------------+ | MOTOR DOCKER : overlay2 (Union FS) mezcla todas las capas en | | una única vista / (diagrama simplificado: en realidad el host | | almacena cada layer en su propio directorio con su digest). | +------------------------------------------------------------------+

Al montar la imagen, el motor Docker apila las capas de abajo hacia arriba formando un solo árbol de directorios que se ve como un sistema de archivos normal. Tú ves una única raíz / con /usr, /etc, etc.; Docker ve N capas superpuestas.

Union FS: la magia de montar varias capas como una

El Union File System es una familia de técnicas que montan varios directorios en un único punto de montaje. Docker usa el driver de almacenamiento overlay2 por defecto: cada capa es un directorio «lowerdir» y el montaje resultante expone la unión de todos. Cuando dos capas tienen un archivo con el mismo nombre, gana la capa superior.

¿Por qué esta arquitectura en capas? Por tres motivos que verás durante todo el curso: (1) ahorro de espacio — dos imágenes que comparten la base Alpine no duplican esa base en disco, comparten las mismas capas; (2) velocidad de transferencia — docker pull solo descarga las capas que no tienes; (3) caché de build — al reconstruir, Docker reutiliza las capas que no cambiaron (lo explotarás en la lección 02).

Esto explica por qué descargar node:20-alpine cuando ya tienes nginx:1.27-alpine suele ser casi instantáneo: la capa de Alpine base ya está en tu disco y solo se bajan las capas nuevas.

Copy-on-write: el contenedor «copia solo cuando escribe»

Cuando arrancas un contenedor, Docker crea una capa nueva y vacía encima de las de la imagen: la capa del contenedor. Los contenedores nunca escriben sobre las capas de la imagen (son de solo lectura). Cuando tu aplicación escribe un archivo, el mecanismo copy-on-write (CoW) copia ese archivo de la capa de la imagen a la capa del contenedor y hace la escritura ahí. Si se escribe un archivo nuevo, se crea directamente en la capa del contenedor.

lectura -> se busca de arriba hacia abajo: capa contenedor, luego capa 3, 2, 1. A la primera coincidencia se para. escritura -> COW: el archivo se COPIA primero a la capa del contenedor y se modifica allí. La imagen queda intacta. borrado -> se marca un "whiteout": el archivo queda tapado pero sigue existiendo en la imagen original (por eso borrar algo de la imagen NO reduce su tamaño en el contenedor).

De ahí la regla de oro: la imagen nunca cambia. Si detienes un contenedor, su capa queda «congelada»; si lo borras, la capa del contenedor desaparece y la imagen sigue exactamente igual que antes. Para cambiar algo de la imagen no «editas» la imagen: reconstruyes una imagen nueva (próxima lección).

Imágenes inmutables y su identificador

Cada capa (y por extensión cada imagen) tiene un digest: un hash SHA-256 del contenido. El digest es lo único verdaderamente inmutable y reproducible: sha256:9f5b0d... siempre se refiere exactamente al mismo contenido. La IMAGE ID que ves en docker images es el digest de la capa superior de la imagen (en versión corta de 12 dígitos). Esta idea se vuelve crítica en la lección 05 cuando publiques imágenes y quieras garantías de que «lo que veo es lo que ejecuto».

Los cuatro comandos básicos

  • docker pull <imagen> — descarga de un registro (por defecto Docker Hub) las capas de la imagen que faltan en tu disco.
  • docker images (alias docker image ls) — lista las imágenes locales con REPOSITORY, TAG, IMAGE ID, CREATED y SIZE.
  • docker inspect <imagen> — devuelve el manifiesto JSON completo: metadatos, env, cmd, puertos y, clave aquí, las capas en RootFS.Layers.
  • docker history <imagen> — muestra instrucción a instrucción cómo se construyó la imagen y el tamaño de cada capa.

Multi-OS: los cuatro comandos son idénticos en Linux, macOS y Windows/WSL2. Lo único que cambia es dónde se guardan físicamente las capas. En Linux nativo están en /var/lib/docker/overlay2/; en macOS y Windows viven dentro de la VM/entorno de Docker Desktop (accesible en Windows vía la distro docker-desktop de WSL2 con ls /var/lib/docker/overlay2). No los necesitas tocar nunca a mano, pero saberlo evita «investigaciones» inútiles en tu disco de Windows.

3 · Ejemplo mínimo

Vamos a tocar una imagen con los cuatro ojos: pull, images, inspect e history. Usaremos alpine:3.20, la distro base mínima (~3 MB) sobre la que se construyen casi todas las imágenes «alpine» del ecosistema.

# 1) Descargamos la imagen desde Docker Hub (docker.io/library/alpine)
docker pull alpine:3.20

# Salida importante (resumida):
#   3e04d42f29cb: Pull complete      <- CAPA: cada "Pull complete" es una capa
#   digest: sha256:9f5b0d9b1c45...    <- digest de la IMAGEN completa
#   Status: Downloaded newer image for alpine:3.20

# 2) ¿Qué imágenes hay en local?
docker images

# Salida (columnas):
# REPOSITORY   TAG      IMAGE ID       CREATED        SIZE
# alpine       3.20     3e04d42f29cb   4 weeks ago    3.32MB
# "CREATED" es cuándo se construyó la imagen NO cuándo la bajaste tú.

# 3) El manifiesto JSON de la imagen (metadatos + capas)
docker inspect alpine:3.20
# Fíjate en la salida (JSON) en:
#   .RootFS.Layers      -> ["sha256:..." ]  lista de capas (aquí: 1)
#   .Config.Env         -> ["PATH=..."]
#   .Config.Cmd         -> ["/bin/sh"]      comando por defecto
#
# Para ver solo las capas sin todo el ruido:
docker inspect -f '{{.RootFS.Layers}}' alpine:3.20

# 4) ¿Cómo se construyó? Capa a capa
docker history alpine:3.20
# IMAGE          CREATED      CREATED BY       SIZE
# 3e04d42f29cb   4 weeks ago  /bin/sh -c #(nop) CMD ["/bin/sh"]   0B
# 3e04d42f29cb   4 weeks ago  /bin/sh -c #(nop) ADD file:... in /  3.32MB

Lectura de la salida: Alpine tiene una única capa de contenido (el ADD file:... in / que añade todo su sistema) y una capa de metadatos de 0 B (el CMD). Cuando veas imágenes con decenas de capas (history), será porque su Dockerfile ejecutó muchas instrucciones RUN/COPY.

4 · Ejemplo real

En HarborTasks contenerizaremos tres piezas: web (nginx), api (Node.js/Express) y postgres. Empieza por bajar las dos imágenes de aplicaciones y observa el efecto de las capas compartidas:

# Baja primero la web (nginx sobre Alpine) y luego la API (Node sobre Alpine)
docker pull nginx:1.27-alpine
docker pull node:20-alpine

# Observación clave en el pull de node:20-alpine:
#   ...: Pull complete       <- solo descarga las capas que faltan
#   ...: Already exists      <- las capas de Alpine base YA estaban:
#   Status: Downloaded newer image for node:20-alpine
# tarda MUCHO menos que la primera descarga: compartes la base.

# La vista general del almacén local
docker images
# REPOSITORY   TAG            IMAGE ID       SIZE
# node         20-alpine      e230c8b2e1f1   164MB
# nginx        1.27-alpine    9c1bf53e33c8   49.5MB
# alpine       3.20           3e04d42f29cb   3.32MB
# 164 + 49.5 + 3.32 NO es lo que ocupa tu disco: las capas de Alpine
# base se comparten y se cuentan una sola vez.

# Manifiesto de producción: qué configuran nginx de fábrica
docker inspect nginx:1.27-alpine -f 'CMD={{.Config.Cmd}}  EXPOSE={{.Config.ExposedPorts}}'
# CMD=[nginx -g daemon off;]  EXPOSE=map[80/tcp:{}]
# (El "daemon off" es para que nginx corra en primer plano como PID 1;
#  lo retomaremos en la lección 03.)

# Cómo está construida la imagen oficial de nginx: capas y tamaño real
docker history nginx:1.27-alpine
# ...  /bin/sh -c #(nop)  CMD ["nginx" "-g" "daemon off;"]      0B
# ...  /bin/sh -c #(nop)  EXPOSE 80                             0B
# ...  /bin/sh -c #(nop)  ENTRYPOINT ["/docker-entrypoint.sh"]  0B
# ...  /bin/sh -c #(nop)  STOPSIGNAL SIGQUIT                   0B
# ...  /bin/sh -c #(nop)  COPY file:... in /docker-entrypoint.sh  1.2kB
# ...  /bin/sh -c apk add --no-cache --virtual .build-deps ...   39MB <- la
# ...                     y depués elimina .build-deps: por eso la capa
# ...                     final de nginx alpine ocupa "solo" 49MB.
# Si comparas con la de Node verás capas de apk add de librerías.

El porqué de las imágenes «alpine»: alpine usa musl (en vez de glibc) y el gestor apk. Resultado: una base de ~3 MB, imágenes de aplicación decenas o cientos de veces más pequeñas que sus hermanas debian/ubuntu. Menos tamaño = pull más rápido, menos disco y menos superficie de ataque. El «coste» es que algún binario compilado para glibc puede no funcionar; por eso algunas imágenes oficiales no ofrecen variante alpine.

6 · Errores habituales

Confundir imagen con contenedor

# ❌ Pensar que "borrar un contenedor borra la imagen"
docker rm mi-contenedor      # borra el contenedor...

# ✅ La imagen sigue ahí, intacta (para eso se construyó)
docker images                # nginx:1.27-alpine sigue en la lista
docker run nginx:1.27-alpine # y puedes crear otro contenedor nuevo

# ❌ Pensar que "editar" un contenedor modifica la imagen
docker run nginx:1.27-alpine touch /tmp/reto.txt   # escribe en capa contenedor
docker run nginx:1.27-alpine ls /tmp               # /tmp/reto.txt NO existe:
# cada contenedor nuevo parte de la imagen inmutable, sin cambios.

# ✅ Para cambiar la imagen se reconstruye (próxima lección: Dockerfile)

Malinterpretar la columna SIZE de docker images

# ❌ "Estas 3 imágenes ocupan la suma de sus SIZE en mi disco"
# Eso ignora que node:20-alpine y nginx:1.27-alpine comparten la
# capa base de alpine. El almacén real es menor.

# ✅ Para ver el uso real de disco por imagen "única" usa:
docker system df
# TYPE     TOTAL   ACTIVE  SIZE       RECLAIMABLE
# Images   4       0       217.8MB    217.8MB
# (muestra el espacio de bloques ÚNICOS, ya descontadas las capas
#  compartidas; la etiqueta "Local Volumes" no aparece porque aún
#  no has creado volúmenes: eso es la lección 03 del Módulo 3.)

Ejecutar docker inspect / docker history sobre algo que no existe

# ❌ Usar una imagen que nunca se bajó ni se construyó
docker inspect mi-app:1.0
# Error: No such image: mi-app:1.0
docker history ubuntu:24.04    # → No such image (¡no está en local!)

# ✅ Primero baja la imagen (aunque exista en Docker Hub, el comando
#    anterior solo trabaja sobre el almacén LOCAL)
docker pull ubuntu:24.04
docker history ubuntu:24.04

7 · Ejercicio guiado

Objetivo: ver con tus propios ojos (y con capas reales) cómo funciona el ahorro de espacio compartiendo la base de Alpine. Contenido: pullear, inspeccionar capas y comprobar la reutilización.

  1. Paso 1 — Prepara el terreno. Si hay imágenes anteriores de otros experimentos, no pasa nada: son aparte. 
    docker pull alpine:3.20                 # base mínima: 1 capa (~3 MB)
docker pull nginx:1.27-alpine            # comparte la capa de alpine
docker pull node:20-alpine               # también comparte la capa
docker images                            # mira los SIZE y las IMAGE ID
  2. Paso 2 — Cuenta las capas de cada imagen. 
    # El truco: filtrar con --format aprovecha la plantilla de Go de Docker
docker inspect -f '{{.Name}} capas={{len .RootFS.Layers}}' alpine:3.20
docker inspect -f '{{.Name}} capas={{len .RootFS.Layers}}' nginx:1.27-alpine
docker inspect -f '{{.Name}} capas={{len .RootFS.Layers}}' node:20-alpine
# Esperado (aproximado, depende de la versión):
# alpine:3.20    capas=2     (1 contenido + 1 de metadatos)
# nginx:1.27-alpine capas=6  (base + apks + COPY entrypoint + metas)
# node:20-alpine capas=9
  3. Paso 3 — Comprueba que comparten la capa base. La primera de las capas de nginx y node debe ser la misma que la única capa de contenido de alpine. 
    docker inspect -f '{{json .RootFS.Layers}}' alpine:3.20
docker inspect -f '{{json .RootFS.Layers}}' node:20-alpine
# Los hashes sha256 de la primera entrada deben coincidir.
  4. Paso 4 — Ejecuta la imagen para confirmar qué contiene. Usa --rm para que el contenedor se borre solo al salir (la bandera se repasará en profundidad en el Módulo 2). 
    docker run --rm alpine:3.20 cat /etc/alpine-release   # 3.20.x
docker run --rm node:20-alpine node --version          # v20.x.x LTS
docker run --rm nginx:1.27-alpine nginx -v             # nginx/1.27.x
  5. Paso 5 — Verificación final. Vuelve a mirar el árbol de capas con docker history node:20-alpine e identifica: la capa de la base (ADD file...), las capas de apk add de librerías, la capa de ENV/CMD de 0 B. Cuando lo tengas, borra las imágenes sin miedo: 
    docker rmi nginx:1.27-alpine node:20-alpine alpine:3.20
# Si docker responde "image is being used by a stopped container",
# antes hay que borrar (o borrar con -f) el contenedor que la usa:
#   docker rm <id-o-nombre>      # borra el contenedor
#   docker rmi nginx:1.27-alpine # y repite el borrado de la imagen
# La limpieza es segura: una imagen no es más que sus capas; si otra
# imagen comparte la capa base de alpine, solo se borra lo que sobra.

Windows/WSL2: en PowerShell el filtro de plantilla con comillas simples '{{.Name}} capas={{len .RootFS.Layers}}' también funciona si lo ejecutas dentro de la terminal de WSL con bash. Si estás en PowerShell puro, usa comillas dobles y escapa los corchetes si tu versión lo exige (ej. --format "{{.Name}} {{len .RootFS.Layers}}"). Este curso recomienda, como siempre, trabajar dentro de WSL2.

8 · Reto

🎯 ¿Dónde está el mayor «agujero» de la imagen de Postgres?

Postgres es enorme para lo que tú usas. Arranca en tu almacén a postgres:16-alpine e investiga con docker history postgres:16-alpine qué capa ocupa más y de qué instrucción viene. Después contesta en papel (o en un comentario de tu terminal): ¿por qué una sola capa de ~180 MB suele venir de una instrucción RUN apk add con un listado enorme, y por qué Docker no puede «adelgazar» una capa ya publicada aunque luego borres archivos en la siguiente línea?

Pista: una capa es un diff en positivo — solo se añade. Lo que una capa borra se registra como whiteout en la capa de encima, y en el historial verás que detrás de un apk add gigante no hay ninguna compensación. Piensa en el diagrama de COW de la sección 2.

9 · Resumen

  • Una imagen es un snapshot solo lectura de un sistema de archivos + metadatos (sin kernel: lo usa el del host).
  • Se divide en capas: cada capa es un conjunto de cambios con un digest SHA-256 inmutable.
  • El Union FS (overlay2) monta las capas en una única vista: arriba gana.
  • Copy-on-write: el contenedor escribe solo en su capa superior, copiando antes el archivo de la imagen.
  • Las imágenes son inmutables: para cambiarlas se reconstruyen, nunca se editan.
  • Las capas se comparten entre imágenes → ahorro de disco y pulls casi instantáneos.
  • docker pull, docker images, docker inspect y docker history son tus cuatro ojos sobre el almacén local.
ComandoQué hace

docker imagesLista las imágenes locales (repo, tag, id, tamaño).
docker inspect <imagen>Devuelve el manifiesto JSON: metadatos y capas (RootFS.Layers).
docker history <imagen>Muestra las instrucciones y el tamaño de cada capa.

10 · Preguntas frecuentes

¿Dónde se guardan físicamente las imágenes en mi sistema?

En Linux, en /var/lib/docker/overlay2/ (cada capa, un directorio con su digest). En macOS y Windows viven dentro del entorno de la VM de Docker Desktop; en Windows puedes verlos desde la distro docker-desktop de WSL2 con docker system df y docker image inspect, pero nunca deberías manipularlos a mano: úsalo siempre a través de la CLI de Docker.

¿Por qué nginx:1.27-alpine pesa ~50 MB y node:20-alpine ~160 MB?

Por las herramientas y runtime que incluyen. Alpine base son ~3 MB; nginx añade su binario compilado (apk add nginx) y node añade el runtime completo de Node más sus librerías. Más funcionalidad = más bytes en capas. La misma imagen en debian pesaría bastante más todavía, de ahí el consejo de preferir las variantes alpine/slim cuando puedas.

¿Seguro que las capas se comparten entre imágenes en mi máquina?

Sí, si las capas del mismo digest ya existen en el almacén local. La prueba más barata: pullea alpine:3.20, reinicia tu terminal (o espera un momento) y pullea node:20-alpine: verás «Already exists» (no re-descarga). Eso es la capa base compartida por diseño de Union FS + deduplicación por digest.

¿Qué es realmente el «digest» y por qué importa?

Es el hash SHA-256 del contenido de una capa o imagen. Como el contenido es inmutable, el digest te identifica el contenido de forma única y reproducible. Si dos capas tienen el mismo digest, son exactamente el mismo contenido, y el motor las comparte y no las descarga dos veces. Esta propiedad es la base de la «inmutabilidad» y la volverás a usar en la lección 05 para fijar versiones exactas con image@sha256:....

¿«CREATED» de docker images es cuándo la bajé yo?

No. Es la fecha en que el autor construyó y publicó esa capa en el registro («4 weeks ago»). Para saber cuándo la trajiste tú no hay columna directa: puedes comparar docker history o consultar el campo .Created de docker inspect. Confundir ambos es un clásico al depurar «¿esta imagen es nueva?».
