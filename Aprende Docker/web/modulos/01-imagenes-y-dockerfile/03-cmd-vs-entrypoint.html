CMD vs ENTRYPOINT

Módulo 1 · Imágenes y Dockerfile ⏱ 30 minutos

1 · Introducción

Cuando haces docker run imagen, el motor ejecuta algo dentro del contenedor. Ese «algo» lo decide el Dockerfile mediante dos instrucciones que parecen gemelas y que no lo son: CMD y ENTRYPOINT. Confundirlas es el clásico tropiezo (incluso entre perfiles con experiencia) y produce imágenes que «parecen rotas» porque el usuario no puede pasarles argumentos.

En esta lección entenderás la diferencia exacta, los dos formatos de escritura —exec form (JSON) frente a shell form (string)—, cómo se combinan ambas instrucciones (el patrón que usan nginx y postgres oficiales), y cómo docker run con argumentos o --entrypoint interactúa con todo ello.

¿Por qué existen dos instrucciones para «lo mismo»? Porque necesitamos distinguir dos cosas: el programa que tu imagen siempre debe ejecutar (ENTRYPOINT) y los argumentos por defecto que el usuario debe poder cambiar sin reescribir nada (CMD). Separarlos da imágenes flexibles y componibles en vez de «cajas cerradas».

2 · Teoría

El contenedor es su proceso

Docker arranca el contenedor ejecutando un único proceso: el comando final de la imagen, que se convierte en el PID 1 dentro del namespace del contenedor. Cuando ese proceso sale, el contenedor se detiene. La imagen aporta el sistema de archivos y la configuración; el comando de arranque aporta el proceso. Por eso, diseñar bien CMD/ENTRYPOINT es diseñar qué significa «arrancar» tu aplicación y cómo se le habla desde fuera.

CMD: el comando por defecto… reemplazable

  • Define el comando por defecto que se ejecuta si docker run no recibe ningún comando.
  • Si el usuario escribe docker run imagen <algo>, ese <algo> reemplaza por completo el CMD.
  • Puede funcionar «solo» (sin ENTRYPOINT) o como argumentos por defecto del ENTRYPOINT.

Analogía — el camarero: CMD es lo que el camarero sugiere cuando no pides nada («hoy recomiendo el menú del día»). Si pides otra cosa, te sirve lo que pidas; si no, te trae lo recomendado.

ENTRYPOINT: el programa fijo

  • Define el programa fijo que se ejecuta siempre.
  • El argumento adicional de docker run imagen <args> se añade como argumentos del ENTRYPOINT (no lo reemplaza).
  • Solo se puede saltar con docker run --entrypoint <otro-comando> imagen (típico para depurar).

La combinación dorada: ENTRYPOINT fija el programa, CMD da los argumentos

# Patrón más usado en imágenes oficiales
ENTRYPOINT ["my-program"]     #  programa fijo (siempre)
CMD ["--flag-por-defecto"]    #  argumentos por defecto (reemplazables)

Resumen de cómo se forma el comando final en cada caso:

Dockerfiledocker run imagendocker run imagen --otro flag
Solo CMD ["p", "a"]ejecuta p aejecuta --otro flag (el usuario decide todo)
Solo ENTRYPOINT ["p"]ejecuta pejecuta p --otro flag (el programa se mantiene)
ENTRYPOINT ["p"] + CMD ["a"]ejecuta p aejecuta p --otro flag (a desaparece: el usuario lo reemplazó)

Exec form vs shell form

Ambas instrucciones pueden escribirse de dos formas, y no son equivalentes:

FormaSintaxisQué hace DockerConsecuencias
Exec form CMD ["node", "server.js"]
ENTRYPOINT ["nginx", "-g", "daemon off;"]		 Lanza el programa directamente, sin shell intermedio. El binario es el PID 1, recibe señales (SIGTERM), y las variables de entorno no se expanden. Es la forma recomendada.
Shell form CMD node server.js
CMD echo "hola $NOMBRE"		 Envuelve el comando en /bin/sh -c <comando>. Dispone de pipe, ${VAR}, &&… pero el PID 1 es el sh, que debe reenviar (exec) las señales; si no, tu proceso no las recibe a tiempo.

Regla mental: ¿Necesitas variables, pipes o redirecciones? Usa exec form y muévelos a un script que tú invocas (ENTRYPOINT ["/app/start.sh"]), con exec dentro del script. ¿Es un adorno rápido? La shell form te vale, con sus riesgos.

Una trampa clásica del exec form

Como el exec form no pasa por el shell, CMD ["echo", "$HOME"] imprime literalmente $HOME. Para expandir variables de entorno necesitas shell form (o que el propio programa haga la expansión). Es el error #1 de quien viene de scripts de shell.

3 · Ejemplo mínimo

Construye una imagen minúscula que «saluda» y observa cómo cambia el comportamiento al pasar de CMD a ENTRYPOINT.

saluda/Dockerfile (versión CMD)
# Imagen base mínima de Alpine (lección 01)
FROM alpine:3.20

# CMD en exec form: siempre se ejecuta si no pasan otra cosa en docker run
CMD ["echo", "hola desde CMD"]
        
cd saluda
docker build -t saluda:cmd .
docker run --rm saluda:cmd            # --> hola desde CMD
docker run --rm saluda:cmd echo adiós # --> adiós   (CMD reemplazado)
docker run --rm saluda:cmd sh         # --> shell interactivo (¡adiós echo!)

Ahora cambia el Dockerfile a ENTRYPOINT:

saluda/Dockerfile (versión ENTRYPOINT)
FROM alpine:3.20

# ENTRYPOINT en exec form: el programa es FIJo. Lo que pases en
# docker run son argumentos suyos.
ENTRYPOINT ["echo", "hola siempre"]
        
docker build -t saluda:entry .
docker run --rm saluda:entry           # --> hola siempre
docker run --rm saluda:entry amigo     # --> hola siempre amigo (se añade)
docker run --rm --entrypoint sh saluda:entry -c "echo estoy en shell"
#   --> estoy en shell   (--entrypoint salta el programa fijo)

Diferencia visible: con CMD, pasar sh te dio un shell; con ENTRYPOINT, pasar cualquier cosa se convierte en argumento de echo. Nota que usamos --rm en los cuatro «docker run»: nada sobrevive al terminar, ideal para pruebas en una línea.

4 · Ejemplo real

El patrón «ENTRYPOINT fijo + CMD como argumentos» lo usan las imágenes oficiales más famosas. Míralo en las que usarás en HarborTasks:

# ---- nginx:1.27-alpine ----
docker inspect nginx:1.27-alpine -f 'entrypoint={{json .Config.Entrypoint}}'
docker inspect nginx:1.27-alpine -f 'cmd={{json .Config.Cmd}}'
# entrypoint=["/docker-entrypoint.sh"]
# cmd=["nginx", "-g", "daemon off;"]

# ¿Qué pasa si "reemplazas" el CMD con docker run? Pruébalo:
docker run --rm nginx:1.27-alpine nginx -v
#   --> nginx version: nginx/1.27.x
# El script docker-entrypoint.sh ejecutó "nginx -v" como argumento suyo.
# Es el mismo patrón: ENTRYPOINT [script], CMD [nginx -g daemon off;].

# ---- postgres:16-alpine ----
docker inspect postgres:16-alpine -f 'entrypoint={{.Config.Entrypoint}} | cmd={{.Config.Cmd}}'
#   --> entrypoint=[docker-entrypoint.sh] cmd=[postgres]

# El entrypoint de postgres es un setup: fija permisos, inicializa el
# cluster si está vacío, y al final hace exec "$@" (es decir, ejecuta CMD).
# Gracias a esto, AÑADIR argumentos no rompe la inicialización:
docker run --rm postgres:16-alpine postgres --help | head -5
#   --> imprime la ayuda de postgres (el entrypoint pasó "--help").
# Si postgres usara solamente CMD sin entrypoint, pasar argumentos los
# reemplazaría y nadie inicializaría el cluster.

# ---- HarborTasks API (la que construimos en la lección 02) ----
docker run --rm -it harbortasks-api:1.0 node --version
#   --> v20.x.x
# Nuestro CMD ["node", "src/server.js"] se reemplaza por "node --version":
# mismo patrón: entrada de escape para depurar sin tocar la imagen.

Por qué postgres necesita ENTRYPOINT (y no CMD): el contenedor de postgres debe preparar el cluster antes de arrancar (crear el directorio de datos, levantar la base inicial…). Eso es código, no un binario. El docker-entrypoint.sh hace la preparación y luego exec "$@" cierra con el comando real. Si postgres tuviera solo CMD ["postgres"], al pasarle un argumento no se ejecutaría ni la preparación.

5 · Buenas prácticas

HazEvitaPor qué
Usa exec form (array JSON) en CMD y ENTRYPOINT Shell form por comodidad El proceso es PID 1 de verdad y recibe las señales (parada limpia); no hay /bin/sh -c interpuesto que retrase el cierre.
Si tu imagen espera argumentos, usa ENTRYPOINT + CMD (patrón oficial) ENTRYPOINT para un comando con argumentos fijos y CMD para otra cosa El patrón da la API pública de la imagen: programa fijo, argumentos por defecto reemplazables desde docker run, Compose y Kubernetes.
Para lógica previa (inicializaciones), usa un script y ENTRYPOINT ["/app/start.sh"] con exec al final Encadenar todo con ENTRYPOINT ["sh", "-c", "..."] El script con exec cmd "$@" mantiene señales y permite argumentos; la forma sh -c envuelta es un anti-patrón con pid 1 = sh.
Documenta en el README cómo se le pasan argumentos a tu imagen Asumir que «se usa tal cual» Una imagen es una pieza reusable: quien la use (tú en 3 meses, un colega, un chart de Helm) debe saber su interfaz de entrada.
Depura con docker run --entrypoint sh imagen en contenedores temporales Editar la imagen en producción para «mirar» --entrypoint no toca la imagen: es una puerta de entrada temporal, perfecta para inspeccionar sin reescribir nada.

6 · Errores habituales

Creer que exec form expande variables

# ❌ Exec form: no hay shell, $NOMBRE NO se expande
FROM alpine:3.20
ENV NOMBRE=María
CMD ["echo", "Hola, $NOMBRE"]
# docker run --rm img   -->   "Hola, $NOMBRE"   (literal, ¡falla!)

# ❌ "Saltar" a shell form para expandir sin pensar en las consecuencias
CMD echo "Hola, $NOMBRE"
# Esto SÍ expande la variable (el shell la sustituye), pero ahora el
# PID 1 es /bin/sh -c: en un servidor de verdad las señales de parada
# (SIGTERM) llegan indirectas, y el apagado puede volverse "zombie".

# ✅ Solución robusta: script dedicado, ejecutado en exec form
FROM alpine:3.20
ENV NOMBRE=María
COPY saluda.sh /saluda.sh        # #!/bin/sh ; echo "Hola, $NOMBRE"
RUN chmod +x /saluda.sh          # (o cuida los permisos en el COPY)
CMD ["/saluda.sh"]               # con exec dentro del script

Diseñar una imagen que no deja pasar argumentos

# ❌ El usuario no puede cambiar "daemon off;" ni pasar flags
FROM nginx:1.27-alpine
CMD ["nginx", "-g", "daemon off;"]
ENTRYPOINT ["nginx", "-g", "daemon off;"]
#   docker run img -s reload          --> pasa "reload" a nginx -g ...,
#                                          rompe la sintaxis. Imposible usar.

# ✅ La imagen oficial ya lo resuelve: ENTRYPOINT script + CMD args
# (heredados, no hace falta redefinirlos)
#   docker run img nginx -v          --> nginx version: nginx/1.27.x

Confundir override con append

# ❌ "Paso un comando, pero igual se ejecuta el de la imagen"
# Con solo CMD, docker run imagen <comando> REEMPLAZA por completo.
docker run --rm saluda:cmd echo adiós       # --> adiós (no "hola desde CMD adiós")

# ✅ Solo cuando hay ENTRYPOINT los argumentos se AÑADEN
docker run --rm saluda:entry amigo          # --> hola siempre amigo

Poner CMD «después» de un cmd heredado y no esperar nada malo

# ❌ Pisa el arranque correcto que heredabas de la base
FROM postgres:16-alpine
CMD ["rumbo"]            # ¡adiós inicialización de postgres!
# Cada imagen base puede tener su propio CMD/ENTRYPOINT. Sobrescribir
# sin querer es "silencioso": el contenedor arranca con tu CMD y JAMÁS
# corre la lógica del entrypoint de postgres.

# ✅ Si solo quieres documentar, no añadas CMD a menos que vayas a
#    redefinir el arranque de verdad. Típico y correcto:
FROM node:20-alpine
CMD ["node", "src/server.js"]     # aquí SÍ redefines el arranque a propósito

7 · Ejercicio guiado

Objetivo: crear una miniimagen tipo CLI que saluda por nombre, usando el patrón ENTRYPOINT + CMD, y probar sus cuatro modos de uso.

  1. Paso 1 — Crea el directorio y el Dockerfile. 
    mkdir -p ~/proyectos/saluda-cli && cd ~/proyectos/saluda-cli
    Dockerfile
    # Patrón oficial: programa fijo + argumentos por defecto
FROM alpine:3.20
# Programa fijo: echo; docker run añadirá el nombre como argumento.
ENTRYPOINT ["echo", "Hola,"]
# Argumentos por defecto: si no se pasa nombre, saludamos al mundo.
CMD ["mundo"]
  2. Paso 2 — Construye la imagen. 
    docker build -t saluda-cli:1.0 .
# Steps: FROM (cache) + ENTRYPOINT (metadato) + CMD (metadato)
  3. Paso 3 — Ejecuta los cuatro usos y anota la salida. 
    docker run --rm saluda-cli:1.0
# --> Hola, mundo                      (usa CMD por defecto)
docker run --rm saluda-cli:1.0 Antonio
# --> Hola, Antonio                    (CMD reemplazado por "Antonio")
docker run --rm saluda-cli:1.0 --piropos a María
# --> Hola, --piropos a María          (TODO es argumento del entrypoint)
docker run --rm --entrypoint sh saluda-cli:1.0
# --> shell interactivo: el --entrypoint salta el echo
  4. Paso 4 — Confirma qué guarda el manifiesto. 
    docker inspect saluda-cli:1.0 -f 'entrypoint={{json .Config.Entrypoint}}'
docker inspect saluda-cli:1.0 -f 'cmd={{json .Config.Cmd}}'
# entrypoint=["echo","Hola,"]  cmd=["mundo"]
  5. Paso 5 — Verificación. La combinación ENTRYPOINT+CMD debe reproducir exactamente la tabla de la teoría: sin args → Hola, mundo; con un arg → Hola, <arg>. Si obtienes otra cosa, vuelve al paso 2 y revisa que usas exec form (corchetes y comillas) en ambas instrucciones.

8 · Reto

🎯 Haz que tu imagen se comporte como el comando ls

Crea una imagen (p. ej. mils:1.0) con Alpine y un WORKDIR tipo /data, de forma que:

  • docker run --rm -v $PWD:/data mils:1.0 liste el directorio actual como ls.
  • docker run --rm -v $PWD:/data mils:1.0 -la liste con detalles (añade -la como argumento).
  • Extra: haz que sin argumentos no haga nada «absurdo»: pista sobre qué le pasa a ls cuando le pasas -la /data y sobre cómo encaja el patrón «programa fijo + args por defecto» con una emulación de CLI.

Pista: tu ENTRYPOINT será ["ls"] y tu CMD (si lo pones) ["/data"]; piensa por qué entonces ls -la DEBE reemplazar al CMD, y por qué el ENTRYPOINT es lo que hace que siga siendo ls con argumentos tuyos en vez de «ls con el CMD pegado».

9 · Resumen

  • CMD = comando por defecto; docker run imagen <args> lo reemplaza.
  • ENTRYPOINT = programa fijo; los args de docker run se le añaden.
  • Combinados: ENTRYPOINT ["programa"] + CMD ["args"] → programa fijo con argumentos por defecto reemplazables.
  • Exec form (JSON): lanza el binario como PID 1, recibe señales, no expande variables.
  • Shell form (string): entra /bin/sh -c, expande variables, se pierde la señal directa.
  • Las imágenes oficiales (nginx, postgres) usan el patrón ENTRYPOINT script + CMD binario; hazlo tuyo.
ComandoQué hace
docker run --rm imagenEjecuta el CMD por defecto (o ENTRYPOINT+CMD).
docker run imagen <args>Si hay ENTRYPOINT, añade args; si solo hay CMD, lo reemplaza.
docker run --entrypoint <cmd> imagenIgnora el ENTRYPOINT de la imagen (útil para depurar).
docker inspect imagen -f '{{.Config.Cmd}}'Muestra el CMD como JSON; lo mismo con .Config.Entrypoint.

10 · Preguntas frecuentes

¿Puedo tener solo ENTRYPOINT sin CMD?

Sí. ENTRYPOINT ["echo"] funciona igual: sin args imprime una línea vacía. Lo normal en imágenes tipo CLI es el patrón combinado (ENTRYPOINT + CMD) para tener un «default» sensato. En contraste, una imagen tipo servidor (Node, nginx) normalmente usa solo CMD para que puedas reemplazar el arranque por completo cuando haga falta.

¿Qué prevalece si pongo CMD y ENTRYPOINT?

No «vence» ninguno: se combinan. ENTRYPOINT es el programa y CMD aporta sus argumentos por defecto. El resultado final es básicamente lo que habrías escrito en la línea de comandos como la suma de entrypoint + los argumentos que hayas pasado (y si no pasas ninguno, los de CMD).

¿Por qué las señales (SIGTERM) dependen de exec form?

Cuando arrancas con shell form, el PID 1 es /bin/sh, no tu aplicación. Docker manda la señal de parada al PID 1; sh tiene que reenviarla a su hijo, y no siempre lo hace de inmediato. En exec form tu proceso ES el PID 1 y recibe la señal directamente, permitiendo un apagado limpio (lo vemos en detalle en el Módulo 2 con --stop-time y señales).

¿Puedo expandir variables de entorno con exec form de alguna forma?

No directamente, porque exec form no invoca un shell. Si necesitas expandir variables, usa shell form (pierdes las señales directas) o, mejor, mételas en un script arrancado por ENTRYPOINT/CMD en exec form, con #!/bin/sh y exec al final. Alternativa limpia: dejar que tu aplicación resuelva sus propias variables (Express con process.env, por ejemplo).

¿Cuándo debería usar --entrypoint?

Casi siempre para diagnóstico: entrar en una imagen que arranca un servidor (por ejemplo `docker run -it --entrypoint sh nginx:1.27-alpine`) para ver archivos, probar comandos o revisar config sin detener nada. Nunca lo uses como «arreglo» de producción de una imagen que construyes tú: ese es el trabajo del Dockerfile.
