Puertos y variables de entorno

Módulo 2 · Contenedores en ejecución ⏱ 30 minutos

1 · Introducción

En la lección anterior viste que docker ps mostraba la columna PORTS vacía aunque nginx escuchaba en el puerto 80. ¿Por qué? Porque un contenedor vive en una red privada aislada: escucha sus puertos «de puertas para adentro», pero nada de fuera puede llegarle hasta que tú lo decidas. Publicar puertos es la decisión que convierte a un contenedor en un servicio alcanzable.

Y una vez que la gente puede hablar con tu aplicación, cada entorno la quiere distinta: la misma imagen debe servir a desarrollo, staging y producción sin recompilarse. Eso se consigue con variables de entorno, el mecanismo estándar de configuración de las aplicaciones de doce-factor. En esta lección dominarás las dos llaves que conectan un contenedor con el mundo: -p/-P (red) y -e/--env-file/ENV (configuración).

¿Por qué por separado y ahora? Porque ambos conceptos comparten la idea central de Docker: la imagen es inmutable y universal, la configuración es externa a ella. Si quieres cambiar de puerto o de base de datos, nunca recompilas la imagen: cambias las variables y los puertos en el docker run. Esa separación es la que te permitirá, más adelante, desplegar el mismo artefacto en Docker y en Kubernetes sin tocar una línea de código.

2 · Teoría

Por qué los puertos hay que «publicarlos»

Cada contenedor tiene su propio namespace de red: ve su interfaz (eth0) con una IP interna del puente bridge de Docker (rango típico 172.17.0.0/16), su tráfico no sale a tu Wi-Fi. Cuando lanzas -p 8080:3000, Docker instala un redirector: todo el tráfico que llegue a localhost:8080 de tu máquina se reenvía al puerto 3000 de la red interna del contenedor. Internamente usa iptables (regla DNAT) sobre el bridge y un proceso ligero docker-proxy para el resto de plataformas.

   Tu navegador / curl                Red interna privada de Docker
  ┌─────────────────┐                ┌──────────────────────────────┐
  │ localhost:8080  │                │  contenedor "api"            │
  │  (HOST real)    │                │  eth0 = 172.17.0.2, escucha  │
  └────────┬────────┘                │  en 0.0.0.0:3000             │
           │                         └──────────────┬───────────────┘
           ▼                                         ▲
   docker-proxy + iptables (DNAT) —──────────────────┘
   redirige 8080 del host → 3000 del contenedor

   Regla de oro:  izquierda = puerto de TU máquina (host)
                  derecha   = puerto del contenedor (app)
   -p 8080:3000   →  host:8080  ──►  contenedor:3000

-P (mayúscula, «publish all») hace lo mismo pero automático: publica en puertos aleatorios del host todos los puertos que la imagen declare con EXPOSE en su Dockerfile. EXPOSE es solo documentación (no publica nada por sí solo); -P es el atajo que la respeta. Es útil al principio pero casi nunca en producción, donde quieres puertos estables y conocidos.

localhost: quién es quién según el sistema

«localhost» tiene tres personalidades distintas en el mundo contenedor. Dentro del contenedor, localhost es el propio contenedor (o la red loopback compartida, pero nunca tu máquina). Desde tu máquina, localhost:8080 llega al puerto publicado. Y según el sistema operativo, ese «puerto publicado» viaja un trecho distinto:

EscenarioCómo llega localhost a tu contenedorConsecuencia práctica
Linux nativoDocker Engine corre en el host real; los puertos publicados son del hostlocalhost:8080 funciona directo y sin capas intermedias
macOSDocker Desktop usa una VM; la VM redirige el puerto a localhost del Maclocalhost:8080 funciona; la IP 172.17.x.x del contenedor NO es alcanzable desde el Mac
Windows + WSL2Docker Desktop redirige localhost del host al puerto dentro de la VM/WSL2localhost:8080 funciona desde PowerShell y desde WSL; para «volver» al host usa host.docker.internal

Callout multi-OS: si un contenedor necesita hablar con un servicio que corre en tu máquina (p. ej. la API en su terminal apunta a PostgreSQL del host), en Linux nativo usa --add-host host.docker.internal:host-gateway y referencia host.docker.internal; en macOS/Windows ese alias host.docker.internal ya existe. En PowerShell recuerda que las variables se leen con $env:VARIABLE (no $VARIABLE) y que -p HOST:CONT tiene la misma sintaxis.

Variables de entorno: configuración que viaja con la ejecución

Una aplicación de doce-factor (la metodología popularizada por Adam Wiggins de Heroku) guarda la configuración en el entorno, no en el código. El entorno es el mecanismo que ya existe en los sistemas (todos los procesos de tu máquina tienen variables como PATH o HOME); Docker lo adopta tal cual. Las fuentes posibles, de mayor a menor precedencia:

  LAS VARIABLES LAS PONE EL QUE LANZA, NO EL QUE COMPILA
  ┌─────────────────────────────────────────────────────────┐
  │ 1. docker run -e LLAVE=valor          ← gana SIEMPRE    │
  │ 2. docker run --env-file .env         ← por archivo     │
  │ 3. ENV en el Dockerfile               ← valor "horneado"│
  │ 4. fallback por defecto en el código                    │
  └─────────────────────────────────────────────────────────┘
  El runtime (-e / --env-file) pisa a la imagen (ENV). Por eso
  la MISMA imagen sirve para dev, staging y prod: solo cambias
  lo que inyectas al ejecutarla.

Detalles importantes: -e LLAVE=valor inyecta una variable; -e LLAVE (sin =) copia el valor del entorno de tu shell; --env-file .env carga muchas de golpe. El ENV del Dockerfile deja un valor por defecto que el runtime puede pisar. Y un matiz crítico: -e y --env-file no deben usarse para secretos en producción sin gestión de secretos: cualquier proceso con acceso al contenedor (docker inspect incluido) puede leerlos. Los secretos de verdad llegan en el módulo de Kubernetes (Secret) y en Compose puedes apuntar a archivos con permisos restringidos.

3 · Ejemplo mínimo

Cuatro variantes del mismo gesto. Empieza sin publicar y comprueba cómo el puerto queda «invisible», y termina con variables de entorno:

# 1) SIN publicar: la app corre pero NADIE puede alcanzarla.
# Puede parecer un bug, pero es la seguridad por defecto de Docker.
docker run -d --name api node:24-alpine       # la imagen es solo un marcador:
# docker ps te mostrará PORTS vacío. La API escucha en su red privada.

# 2) Publicar MANUALMENTE un puerto: -p host:contenedor
docker run -d --name api -p 8080:3000 node:24-alpine
# → curl http://localhost:8080  reenvía a la API interna en el puerto 3000.

# 3) Publicación AUTOMÁTICA de todos los EXPOSE de la imagen: -P
docker run -d --name web -P nginx:1.27-alpine     # EXPOSE 80 en la imagen
docker port web    # → "80/tcp -> 0.0.0.0:49153"   (puerto AL AZAR del host)

# 4) Una variable de entorno en el arranque
docker run -d --name api -p 8080:3000 \
  -e PORT=3000 -e NODE_ENV=production node:24-alpine
# Verificación inmediata de lo que llegó de verdad al proceso:
docker exec api printenv PORT NODE_ENV   # → 3000  production

Cada una de estas variantes es la misma historia contada de otra forma: la red y la configuración se deciden en el momento de lanzar, nunca en la imagen.

4 · Ejemplo real

La API de HarborTasks recibe su configuración completa por entorno. Primero el Dockerfile marca los valores por defecto; después, en cada entorno, docker run los pisa sin tocar la imagen.

# --- Dockerfile de la API de HarborTasks (fragmento didáctico) ---
FROM node:24-alpine                       # base oficial Node sobre Alpine (minúscula)

# ENV define valores POR DEFECTO "horneados" en la imagen. No son secretos:
# son configuración pública que el runtime puede pisar con -e o --env-file.
ENV PORT=3000 \
    NODE_ENV=production \
    DATABASE_URL=""                        # vacío de fábrica: lo llena el entorno

WORKDIR /app                               # directorio de trabajo dentro de la imagen
COPY package*.json ./
RUN npm ci --omit=dev                      # dependencias de producción, reproducibles
COPY . .                                   # el código de la API

EXPOSE 3000                                # SOLO documentación: no publica nada
CMD ["node", "server.js"]                  # exec form = proceso principal (PID 1)

# Compila la imagen una vez...
docker build -t harbor-api:0.1.0 .

# ...y ejecútala en CADA entorno cambiando solo la configuración.
# -p publica: host 8080 → contenedor 3000 (definido por PORT).
# -e pisa el ENV del Dockerfile: desarrollo quiere otro NODE_ENV y su propia BD.
docker run -d --name harbortasks-api \
  -p 8080:3000 \
  -e PORT=3000 \
  -e NODE_ENV=development \
  -e DATABASE_URL=postgres://harbor:harborpass@localhost:5432/harbortasks \
  harbor-api:0.1.0

# Verificación 1: la variable que de verdad llegó al proceso
docker exec harbortasks-api printenv NODE_ENV        # → development

# Verificación 2: el entorno completo que la app ve (orden y valores)
docker inspect harbortasks-api --format '{{range .Config.Env}}{{println .}}{{end}}'
# → PATH=... PORT=3000 NODE_ENV=development DATABASE_URL=postgres://...

# --- Alternativa limpia para muchos valores: --env-file ---
# Crea un archivo .env (EN ESPAÑOL: no se sube a git, lleva credenciales locales)
#   PORT=3000
#   NODE_ENV=development
#   DATABASE_URL=postgres://harbor:harborpass@localhost:5432/harbortasks
#   LOG_LEVEL=debug
docker run -d --name harbortasks-api \
  --env-file ./.env \
  -p 8080:3000 harbor-api:0.1.0

Dato clave: --env-file solo referencia líneas CLAVE=valor (y acepta comentarios con #); no ejecuta la lógica de tu shell. Las variables se validan y se escalan al necesario. Y ojo: si un valor contiene espacios, escribirlo sin comillas en el archivo es un error habitual — el formato de .env de Compose y de --env-file difieren ligeramente; para Compose (módulo 4) las comillas sí se interpretan.

6 · Errores habituales

Invertir el orden de -p

# ❌ La app escucha en 3000 y tú publicas el 8080 del contenedor:
docker run -d -p 3000:8080 node:24-alpine
# → llega tráfico al 8080 del contenedor, donde NADIE escucha → timeout/CONN_REFUSED

# ✅ SIEMPRE host a la izquierda, contenedor a la derecha:
#    `-p HOST:CONT`  =  por el 8080 de tu máquina llegas al 3000 de la app
docker run -d --name api -p 8080:3000 node:24-alpine

Creer que «localhost» dentro del contenedor es tu máquina

# ❌ Desde dentro, localhost:5432 es el PROPIO contenedor (sin Postgres):
docker exec api curl -s http://localhost:5432        # conexión rechazada

# ✅ Para hablar con servicios de TU HOST desde un contenedor:
#   Linux: --add-host host.docker.internal:host-gateway
#   macOS/Windows (Docker Desktop): el alias ya existe
docker run -d --name api --add-host host.docker.internal:host-gateway \
  -p 8080:3000 -e DATABASE_URL=postgres://harbor:harborpass@host.docker.internal:5432/harbortasks \
  harbor-api:0.1.0

Hornear secretos en la imagen

# ❌ Un ENV con la contraseña queda en la imagen y en su historial de capas
ENV DATABASE_URL=postgres://harbor:SUPER-SECRETO@db:5432/harbortasks
# → cualquiera con la imagen (o el registry) puede `docker history` y leerla

# ✅ La configuración se inyecta al ejecutar (o se gestiona con secretos)
docker run -d --name api --env-file ./.env \
  -p 8080:3000 harbor-api:0.1.0     # el .env NO se versiona

Confundir EXPOSE (documentación) con publicación

# ❌ Poner EXPOSE 3000 en el Dockerfile NO expone nada al host:
docker run -d --name api harbor-api:0.1.0    # PORTS sigue vacío

# ✅ Para alcanzarla hay que publicar (-p) o pedir publicación total (-P)
docker run -d --name api -p 8080:3000 harbor-api:0.1.0

7 · Ejercicio guiado

Objetivo: lanzar dos instancias de la misma mini-app con configuraciones distintas y demostrar, verificando por HTTP y por entorno, que son dos servicios diferentes a partir de la misma imagen.

  1. Paso 1 — Arranca el servidor A. 
    # La "app" es Node de una línea: responde con el contenido de $MSG.
docker run -d --name serv-a -p 8081:3000 -e MSG='Soy el servidor A' \
  node:24-alpine node -e 'const http=require("http");http.createServer((q,r)=>r.end(process.env.MSG||"sin MSG")).listen(3000)'

    Docker responde con el ID; no hay build: -e se inyecta y -p publica al instante.

  2. Paso 2 — Arranca el servidor B, la MISMA imagen, otros datos. 
    docker run -d --name serv-b -p 8082:3000 -e MSG='Soy el servidor B' \
  node:24-alpine node -e 'const http=require("http");http.createServer((q,r)=>r.end(process.env.MSG||"sin MSG")).listen(3000)'
  3. Paso 3 — Verificación por HTTP (ambos responden distinto). 
    curl -s http://localhost:8081   # ESPERADO: Soy el servidor A
curl -s http://localhost:8082   # ESPERADO: Soy el servidor B
# Misma imagen `node:24-alpine`, mismo comando, MISMA lógica.
# La única diferencia es la configuración inyectada: variables y puerto.
  4. Paso 4 — Verificación del entorno con docker exec. 
    docker exec serv-a printenv MSG   # → Soy el servidor A
docker exec serv-b printenv MSG   # → Soy el servidor B
docker ps --format 'table {{.Names}}\t{{.Ports}}\t{{.Image}}'
# → serv-a  0.0.0.0:8081->3000/tcp  node:24-alpine
# → serv-b  0.0.0.0:8082->3000/tcp  node:24-alpine
  5. Paso 5 — Prueba --env-file y el orden de precedencia. 
    # Escribe un .env.local (en Bash: printf, o con tu editor)
printf 'MSG=valor del archivo env\n' > .env.local
# El mismo -e pisa al archivo: el -e gana SIEMPRE.
docker run -d --name serv-c --env-file ./.env.local -e MSG='gana el -e' \
  -p 8083:3000 node:24-alpine node -e 'const http=require("http");http.createServer((q,r)=>r.end(process.env.MSG)).listen(3000)'
curl -s http://localhost:8083    # ESPERADO: gana el -e
docker inspect serv-c --format '{{range .Config.Env}}{{println .}}{{end}}' | grep MSG
  6. Paso 6 — Limpia. 
    docker rm -f serv-a serv-b serv-c && rm -f .env.local
# Verificación final: docker ps -a ya no muestra ninguno de los tres.

8 · Reto

🎯 El entorno como «contrato» de la imagen

Toma la mini-app del ejercicio (una API en un solo node -e) y haz que deba leer tres fuentes distintas para la misma clave: (1) un valor por defecto dentro del comando, (2) un ENV «horneado» en una imagen que tú construyas con un Dockerfile mínimo, y (3) valores inyectados por --env-file y por -e. Escribe los cuatro resultados (docker inspect por medio) y explica, en los comentarios de tu propio comando, cuál gana y por qué, citando la regla «runtime > imagen > código».

Pista: construye una imagen de 6 líneas con FROM node:24-alpine + ENV MSG=desde-la-imagen + CMD [...], luego lánzala con --env-file y -e a la vez y compara con docker inspect --format '{{.Config.Env}}'. El orden de los flags también importa: el último -e gana.

9 · Resumen

  • Los contenedores viven en una red privada aislada: sus puertos solo existen «de puertas para adentro» hasta que los publicas.
  • -p HOST:CONT publica un puerto; -P publica todos los EXPOSE de la imagen en puertos aleatorios; EXPOSE solo documenta.
  • localhost dentro del contenedor es el propio contenedor; localhost de tu máquina llega vía el publicado — con matices entre Linux nativo, la VM de macOS y WSL2.
  • Las variables de entorno son la configuración de una app de doce-factor: -e, --env-file (en el momento de ejecutar) y ENV (en la imagen).
  • Precedencia: -e > --env-file > ENV del Dockerfile > fallback del código. El runtime pisa a la imagen.
  • Los secretos no van en imágenes ni en -e a la vista de cualquiera; se gestionan aparte.
Comando / instrucciónQué hace
docker run -p 8080:3000 imagenPublica el puerto 3000 del contenedor en el 8080 del host
docker run -P imagenPublica todos los EXPOSE en puertos aleatorios del host

10 · Preguntas frecuentes

¿Qué ocurre si publico un puerto del host que ya está en uso?

docker run fallará con un error tipo bind: address already in use (o port is already allocated). Docker nunca se salta un puerto ocupado: el puerto del host es un recurso exclusivo. Tienes dos opciones: usar otro puerto (-p 8081:3000) o dejar que Docker elija uno libre con -P. Los puertos del contenedor, en cambio, pueden repetirse sin problema porque viven en redes aisladas.

¿Por qué no puedo hacer `curl http://localhost:3000` estando ya dentro del contenedor?

Porque dentro del contenedor localhost y la red 172.17.x.x solo alcanzan el propio contenedor y sus vecinos del puente. El mapeo -p 3000:3000 existe en el host (tu máquina), no dentro del sandbox. Si tu app se conecta a la DB del host, usa host.docker.internal (o --add-host en Linux); si la DB vive en otro contenedor, eso se resolverá con la red interna de Docker de la lección «Redes Docker» (módulo 3).

¿`-e` es seguro para guardar contraseñas?

Depende del contexto. Para desarrollo local es la forma más simple y aceptable. Para producción no es recomendable exponerlas así: docker inspect, docker exec env y los logs de arranque del proceso las dejan visibles, y si el contenedor está comprometido, el atacante las lee. El patrón correcto pasa por gestores de secretos: en Docker Desktop puedes apuntar a archivos encriptados, en Swarm a docker secret, y en Kubernetes a objetos Secret montados como archivos o env (lección «Secrets» del módulo 7).

¿Cuál es la diferencia entre --env-file y el .env de Docker Compose?

Son formatos parecidos pero no idénticos. --env-file no interpreta las variables entre comillas y hace un sustitución simple; el .env de Compose se usa para interpolar dentro de compose.yaml (módulo 4), soporta comillas y algunas operaciones más. Además, el orden de precedencia de Compose con env_file/environment: tiene sus propias reglas. La lección de «compose.yaml» profundiza en las diferencias; de momento, para el CLI usa archivos de pares CLAVE=valor sin comillas.

¿Por qué en mi Windows con WSL2 a veces debo usar la IP en vez de localhost?

Docker Desktop con WSL2 redirige automáticamente los puertos publicados a localhost de Windows, así que lo normal es que funcione. Si usas un motor de contenedores montado dentro de WSL sin esa integración, el puerto vive dentro de la VM/distro y debes usar la IP de la distro (o la de la VM). En ese caso, desde PowerShell prueba curl http://<IP-de-la-distro>:8080. La regla general: mientras uses Docker Desktop y publicaciones por -p, localhost:PUERTO es la vía canónica en las tres plataformas.
