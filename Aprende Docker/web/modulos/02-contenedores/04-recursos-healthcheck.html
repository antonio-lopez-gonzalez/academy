Límites de recursos y HEALTHCHECK

Módulo 2 · Contenedores en ejecución ⏱ 30 minutos

1 · Introducción

Contenedores y máquinas virtuales aíslan de forma distinta (lo viste en el módulo 0): los contenedores comparten el kernel del host. Eso los hace ligeros, pero también significa que, sin control, un solo proceso puede engullir toda la RAM o todos los núcleos de la máquina — el clásico «vecino ruidoso». Docker resuelve esto con cgroups: el mecanismo del kernel que permite asignar cuota de CPU, memoria y procesos a un grupo, y que el propio kernel la haga cumplir. Un contenedor sin límites es una promesa de apagón.

Y una vez que el proceso está acotado, queda la pregunta más importante: ¿está vivo… o está sano? Un proceso «Up» puede estar bloqueado en un deadlock o devolviendo 500 en todas las peticiones. El HEALTHCHECK de Docker responde a eso: una sonda periódica que el daemon ejecuta para decidir si el contenedor está healthy o unhealthy. En esta lección dominarás --memory, --cpus, --pids-limit, docker stats, docker update y el HEALTHCHECK del Dockerfile, y verás cómo este concepto madura hasta convertirse en las probes de Kubernetes.

¿Por qué esta lección cierra el módulo? Porque recoge todo lo operativo de las tres anteriores (ejecución, red, ciclo de vida) y lo eleva de «funciona en mi máquina» a «se comporta bien en una máquina compartida y se vigila solo». Son las dos habilidades que separan a un usuario de Docker de un operador de contenedores.

2 · Teoría

cgroups: el contrato de recursos del kernel

Un control group (cgroup) es un mecanismo del kernel Linux para agrupar procesos y darles una porción (o un máximo) de un recurso. Cuando Docker crea un contenedor, mete sus procesos en su propio cgroup y en él escribe los límites que te pidan: memoria máxima, CPU máxima, número máximo de procesos (pids). El kernel — no tu aplicación — es quien hace cumplir esos límites. Esto responde al «porqué» del diseño: tu app no tiene que colaborar; el sistema la contiene igualmente.

  CONTENEDOR = procesos dentro de su propio cgroup
  ┌──────────────────────────────────────────────────────┐
  │  cgroup "docker/<id-contenedor>"                     │
  │  ┌────────────┐ ┌──────────────┐ ┌───────────────┐   │
  │  │ PID 1 node │ │ PID 17 fork  │ │ PID 42 net…  │   │
  │  └────────────┘ └──────────────┘ └───────────────┘   │
  │                                                      │
  │  límites escritos por Docker y aplicados por el      │
  │  KERNEL (cgroup v2 en todas las distros modernas):   │
  │    memory.max  = 256 MiB   → OOM-kill si se supera   │
  │    cpu.max     = 0.5 núcleo → periodos de uso        │
  │    pids.max    = 256        → no más de 256 procesos │
  └──────────────────────────────────────────────────────┘
             ▲
  El kernel aplica el límite aunque tu app lo ignore.

--memory (p. ej. 512m) fija el máximo de RAM: si el proceso conjunto la supera, el kernel invoca el OOM killer y mata el proceso del contenedor (que verás como ExitCode 137 y el flag State.OOMKilled=true). Ojo con --memory-swap: por defecto, al limitar memoria sin swap explícito, Docker pone swap del mismo tamaño. Para usar swap de verdad (devil, no recomendado en prod) --memory-swap > --memory. --cpus (p. ej. 0.5) limita el uso de CPU: Docker mapea el valor a una cuota de periodos (--cpus 0.5 ≈ 50 µs de cada 100 µs por periodo). --pids-limit limita cuántos procesos puede crear el contenedor; imprescindible contra fork bombs (apps que se multiplican sin control).

docker stats y docker update: observar y ajustar en vivo

docker stats muestra el consumo en tiempo real (CPU, memoria, net I/O, block I/O, pids) — el «top» de los contenedores. docker stats --no-stream da una foto única (ideal para piping en scripts). Y lo mejor de los límites: se pueden cambiar con el contenedor en marcha mediante docker update, sin reiniciarlo. Esto permite, por ejemplo, subir la memoria de una API saturada sin downtime. (Los healthchecks, en cambio, no se pueden añadir en caliente a un contenedor que no los traiga de su imagen.)

HEALTHCHECK: ¿el proceso respira… o está sano?

docker ps te dice el estado del motor (Up), no el de tu aplicación. El HEALTHCHECK del Dockerfile define un comando que el daemon ejecuta periódicamente dentro del contenedor; su código de salida decide el veredicto: 0 = healthy, ≠0 = unhealthy (tras --retries fallos seguidos). Docker lo registra y expone docker inspect en .State.Health, y la cuadrícula de docker ps pasa a mostrar (healthy)/(unhealthy). Puedes definir la sonda ahí (imagen) con HEALTHCHECK, o en el arranque con --health-cmd/--health-interval/…

  dockerd ejecuta, cada --interval, el comando del HEALTHCHECK
  dentro del contenedor (ej.: wget -qO- http://localhost:3000/health)
        │
        ├── exit 0 ──────────────► healthy   (estado que ve docker ps)
        └── exit ≠ 0 ──┐
                       ▼  ¿--retries seguidos? ─► unhealthy
  El HEALTHCHECK SOLO informa del estado: NO reinicia el contenedor ni
  corta/redirige tráfico. Eso es trabajo del ORQUESTADOR (K8s probes).

Adelanto a Kubernetes (módulos 5-6): en K8s las sondas son del orquestador y sí actúan. La liveness reinicia el contenedor si no responde (dejó de ser útil), la readiness decide si el Pod recibe tráfico del Service (lo «saca del juego» mientras no esté listo) y la startup protege a apps lentas. Docker solo tiene la parte «informativa»: el healthcheck no reinicia ni desconecta — y eso es una diferencia de diseño fundamental que explica por qué, para self-healing real de un solo contenedor, hay que combinarlo con --restart (lección anterior) y para múltiples hosts hay que subir de nivel a un orquestador.

Analogía: la restart policy es como un guardia de seguridad en la puerta: si el inquilino se desmaya (proceso muerto), lo despierta. El healthcheck es como un médico de cabecera: revisa periódicamente que el inquilino esté sano de verdad, pero solo informa a la familia; no le administra fármacos. En Kubernetes, la familia contrata también a un doctor-propio (kubelet) que sabe que «marearse» merece descanso (liveness) y «estar resfriado» merece no salir a trabajar (readiness).

3 · Ejemplo mínimo

Los límites más comunes, aplicados y verificados en cuatro líneas:

# Memoria tope 128 MB, medio núcleo de CPU, y máximo 128 procesos.
# La app puede pedir ser más grande… el KERNEL se lo niega.
docker run -d --name api-node \
  --memory 128m --cpus 0.5 --pids-limit 128 \
  -p 8080:3000 node:24-alpine node server.js

# Observa el consumo REAL en vivo (equivalente al "top" del sistema):
docker stats           # Ctrl+C para salir de la vista continua
docker stats --no-stream          # una sola foto (usable en scripts)
docker stats --format 'table {{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}\t{{.PIDs}}'

# Cambia un límite SIN reiniciar el contenedor (cero downtime):
docker update --memory 512m --cpus 1 api-node
# → api-node  (vuelca el nuevo límite: mem 512m, cpus 1)

# Línea de salud SIN construir imagen (imagen de nginx viene con su propio
# healthcheck… pero puedes poner el tuyo al arrancar con --health-*):
docker run -d --name web --health-cmd "wget -qO- http://localhost/ >/dev/null || exit 1" \
  --health-interval 5s --health-retries 3 -p 8080:80 nginx:1.27-alpine
sleep 6 && docker inspect web --format '{{.State.Health.Status}}'
# → healthy   (nginx responde 200 y el daemon lo certifica)

¿Por qué wget y no curl en el healthcheck? Porque las imágenes Alpine (de base muy pequeña) traen wget de busybox de serie y NO suelen traer curl. Un healthcheck con curl en Alpine fallará siempre con «curl: not found» — un clásico falso negativo. Esta es una de esas diferencias sutiles que valen oro.

4 · Ejemplo real

La API de HarborTasks con límites de producción y un healthcheck que vigila el endpoint /health real de la app. Además, el experimento del OOM-kill para que veas con tus ojos qué hace el kernel cuando un contenedor se pasa de memoria.

# --- Dockerfile de la API de HarborTasks, con HEALTHCHECK integrado ---
FROM node:24-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .

# /health NO depende de la BD: responde "ok" si el proceso HTTP vive.
# start-period: en los primeros 20 s el daemon NO penaliza fallos
# (arranque parsea configuración, abre la BD…). Sin esto, una app
# que tarda 15 s en arrancar sería marcada unhealthy en falso.
HEALTHCHECK --interval=10s --timeout=3s --start-period=20s --retries=3 \
  CMD wget -qO- http://localhost:3000/health >/dev/null 2>&1 || exit 1

EXPOSE 3000
CMD ["node", "server.js"]
# Construye y lanza con límites realistas (memoria 256m, medio core).
docker build -t harbor-api:0.1.0 .
docker run -d --name api \
  --memory 256m --cpus 0.5 --pids-limit 256 \
  -p 8080:3000 -e DATABASE_URL=postgres://harbor:harborpass@db:5432/harbortasks \
  harbor-api:0.1.0

# Tras el arranque (espera > start-period): estado de salud desde fuera
sleep 25
docker ps --filter name=api                        # STATUS: Up (healthy)
docker inspect api --format '{{.State.Health.Status}}'     # → healthy

# El detalle de la última sonda: código de salida y salida capturada
docker inspect api --format '{{range .State.Health.Log}}{{.ExitCode}} · {{.Output}}{{end}}'
# → 0 ·          (exit 0 y sin salida: el wget fue bien)

# --------------------------------------------------------------------
# EXPERIMENTO: el OOM-kill en acción (¡aplica solo el kernel!)
# --------------------------------------------------------------------
# Esta app "fuga": mete 1 MiB en un array cada 20 ms hasta morir.
docker run -d --name leak --memory 256m node:24-alpine node -e \
  'const a=[];setInterval(()=>a.push(Buffer.alloc(1024*1024)),20)'
sleep 8
docker inspect leak --format '{{.State.OOMKilled}} · exit={{.State.ExitCode}}'
# → true · 137        (137 = 128 + SIGKILL(9): lo mató el OOM killer)
docker rm -f leak

# Balance general en un solo pantallazo:
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}'

Prioridad de la verdad: el healthcheck no engaña por diseño: /health debía responder también cuando la BD está caída (health es «el proceso respira»), porque la readiness la decidirá el orquestador más adelante. Mezclar en un solo endpoint la salud del proceso y la de sus dependencias es una decisión de arquitectura que conviene tomar conscientemente: un healthcheck que devuelve 500 porque la BD está caída provocará unhealthy en cascada en todos los días de caída de la BD.

5 · Buenas prácticas

HazEvitaPor qué
Límites siempre: --memory + --cpus en producción Contenedores sin límites en hosts compartidos Sin cgroups, un contenedor puede agotar la RAM y matar procesos del HOST; los límites son la base del «vecino silencioso»
--pids-limit (p. ej. 128-256) a todo contenedor Dejarlo ilimitado siempre Una app con fork en bucle (bug o ataque) multiplica procesos hasta agotar el host; el límite de pids lo frena en seco
Valores con algo de aire; revisar con docker stats para calibrar Limitar «justo» con el pico (p. ej. --memory 128m para una app que usa 130) El OOM-kill no espera: limites ajustados convierten un pico transitorio en una caída dura (ExitCode 137) en producción
start-period generoso en healthchecks de apps que tardan en arrancar Sonar inmediatamente con --retries pequeños y sin start-period Sin ventana de arranque, una app legítimamente lenta pasa a unhealthy falso y provoca alarma y reinicios inmerecidos
Healthcheck sobre un endpoint real de la app (no «ping local») Sondas a instrucciones que siempre devuelven 0 (true, echo ok) El healthcheck vale lo que vale su comando: un «true» solo confirma que el shell vive, no que tu HTTP responde (falso confianza)
Combinar --restart + HEALTHCHECK para autovigilancia local Esperar que el healthcheck «reinicie» el contenedor él solo En Docker el healthcheck solo INFORMA; la reactividad real la dan las restart policies (y en K8s, las probes de los controladores)

6 · Errores habituales

Healthcheck con curl en una imagen Alpine

# ❌ curl no viene instalado en Alpine (busybox no lo trae):
HEALTHCHECK CMD curl -f http://localhost:3000/health || exit 1
# → /bin/sh: curl: not found → el healthcheck FALLA SIEMPRE → unhealthy crónico

# ✅ wget (busybox) es el estándar en imágenes Alpine:
HEALTHCHECK --interval=10s --timeout=3s --start-period=20s --retries=3 \
  CMD wget -qO- http://localhost:3000/health >/dev/null 2>&1 || exit 1

Un healthcheck que «siempre pasa» porque el comando siempre devuelve 0

# ❌ "true" solo comprueba que el shell está vivo, no tu app
docker run -d --name web --health-cmd "true" nginx:1.27-alpine
# → healthy pase lo que pase (incluso con nginx detenido dentro)

# ✅ La sonda comprueba la respuesta HTTP REAL del endpoint:
docker run -d --name web \
  --health-cmd "wget -qO- http://localhost/ >/dev/null 2>&1 || exit 1" \
  --health-interval 5s --health-retries 3 --health-start-period 5s \
  -p 8080:80 nginx:1.27-alpine
# → healthy SOLO si nginx responde. Esa es la información que vale.

Ignorar --memory-swap al limitar memoria

# ❌ Al usar --memory 512m, Docker por defecto crea también 512m de swap:
#    el proceso puede "colarse" en swap y pasarte desapercibido en stats.
docker run -d --memory 512m node:24-alpine node server.js

# ✅ Si no quieres swap (recomendado en prod): swap = memoria
docker run -d --memory 512m --memory-swap 512m node:24-alpine node server.js
# -> el total RAM+swap queda en 512m: no hay colchón fantasma.

Confundir healthcheck (info) con readiness de orquestador (acción)

# ❌ Esperar que `docker inspect` te "saque del juego" a un contenedor unhealthy:
#    Docker solo cambia el estado. El tráfico no se corta ni se redirige.
docker run -d --name api --health-cmd "false" -p 8080:3000 harbor-api:0.1.0
# → STATUS "(unhealthy)" … y SIGUE recibiendo tráfico en el puerto 8080.

# ✅ En Kubernetes esto SÍ lo hace la readiness probe (módulo 6-05): el
#    kubelet quita el Pod de los endpoints del Service cuando no responde.
#    Docker te pide combinar roles: healthcheck (informar) + restart (reaccionar).

  3. Paso 3 — Sube el límite sin reiniciar. 
    docker update --memory 512m --cpus 1 limite
docker inspect limite --format 'mem={{.HostConfig.Memory}} cpu={{.HostConfig.NanoCpus}}'
# ESPERADO: mem=536870912 cpu=1000000000. El contenedor siguió Up todo el rato.
  4. Paso 4 — Fuga y OOM-kill: que el kernel hable.

    docker run -d --name enfermo --health-cmd "false" \
  --health-retries 1 -p 8082:80 nginx:1.27-alpine

docker inspect enfermo --format '{{.State.Health.Status}}'   # ESPERADO: unhealthy

8 · Reto

🎯 El healthcheck que K8s no puede fingir

Construye una mini-imagen Node con un endpoint /health que devuelve 500 cuando una variable READY=false (defínela con -e) y 200 cuando es true. Con HEALTHCHECK apuntando a ese endpoint, lanza una misma imagen dos veces: una con -e READY=true (sale healthy) y otra con READY=false (unhealthy). Después, usando docker update… demuestra que no puedes cambiar el estado de salud sin reiniciar, y explica por escrito —con el experimento ya hecho— cuál es el mecanismo que en Kubernetes sí «mueve» a un Pod del healthy al ready/unready automáticamente y por qué aquí no aplica.

Pista: el healthcheck definido en la imagen se puede sustituir en el arranque con --health-cmd (y compañía) en el propio docker run; recuerda usar wget de busybox. La respuesta al «por qué» está comparando la tabla de la teoría: Docker healthcheck (informativo) vs liveness/readiness del kubelet (acciones sobre el ciclo de vida y los endpoints del Service) — la lección «Probes» del módulo 6 cierra el círculo.

9 · Resumen

  • Los contenedores comparten el kernel del host: cgroups es el mecanismo que limita RAM, CPU y procesos, y el kernel hace cumplir los límites aunque tu app los ignore.
  • --memory, --cpus y --pids-limit son los tres límites esenciales de cualquier despliegue serio.
  • Superar --memory dispara el OOM-killer: ExitCode 137, State.OOMKilled=true.
  • docker stats observa el consumo en vivo; docker update ajusta límites sin reiniciar.
  • El HEALTHCHECK ejecuta una sonda periódica; su código de salida decide healthy/unhealthy (con --start-period, --interval, --timeout, --retries).
  • El healthcheck de Docker solo informa: no reinicia ni corta tráfico. En Kubernetes, las probes (liveness/readiness/startup) de los controladores sí actúan; es el mismo concepto madurado a la escala del clúster.

10 · Preguntas frecuentes

¿Qué ocurre exactamente cuando un contenedor supera --memory?

El kernel Linux invoca el OOM killer: elige un proceso del cgroup (normalmente el que más memoria consume) y lo mata con SIGKILL. Como el proceso principal de tu contenedor muere, el contenedor pasa a exited con ExitCode 137 (= 128 + 9, la señal SIGKILL) y el flag State.OOMKilled=true. Es inmediato y sin aviso: por eso los límites se calibran con margen usando docker stats en carga real.

¿--cpus 0.5 significa que solo usará la mitad de un núcleo?

Sí, exactamente: el contenedor puede usar como mucho el equivalente a medio núcleo. Docker traduce el valor a cuota de periodos del cgroup (--cpus 0.5 ≈ 50 µs de cómputo cada 100 µs). Puedes subir hasta tantos núcleos como tenga el host, y combinarlo con --cpuset-cpus si además quieres fijar qué núcleos físicos. No es un límite «blando»: el kernel actúa por periodos, dando una garantía media muy estable.

¿Por qué docker stats a veces muestra más memoria de la que asigné?

Porque lo que ves en docker stats es el uso efectivo (o la proyección con la caché de páginas del kernel), mientras que --memory es el tope del cgroup. La memoria de página cache se puede reclamar al vuelo, así que un contenedor «a tope de stats» puede no estar en peligro. El indicador de peligro real es el OOMKilled y el exit 137. Para una cifra «sucia pero útil» de la app, mira docker inspect con Usage de MemoryStats, o duplica el límite con swap anulado.

¿Cuál es la diferencia entre el HEALTHCHECK de Docker y las probes de Kubernetes?

Es la misma idea con poderes distintos. El HEALTHCHECK docker ejecuta una sonda y solo actualiza un estado (healthy/unhealthy) que puedes ver con docker inspect/docker ps: no reinicia el contenedor ni modifica el tráfico. Las probes de K8s (módulo 6-05) son ejecutadas por el kubelet y sí actúan: la liveness reinicia el contenedor del Pod, la readiness lo quita o añade a los endpoints del Service, y la startup protege a apps con arranque lento. Docker te pide componer (healthcheck + restart policy); Kubernetes tiene el concepto nativo del orquestador.

¿Por qué mi contenedor aparece unhealthy justo después de arrancar?

El caso típico es un arranque legítimamente lento: la app necesita 15 s para estar lista y la sonda ya está fallando en el primer intervalo. La solución es el parámetro --start-period (o HEALTHCHECK --start-period en el Dockerfile): durante esa ventana inicial, Docker registra los fallos pero no cuenta para los --retries. Otras causas comunes: el comando usa curl en una imagen Alpine (no instalado), o el healthcheck apunta a un puerto que no coincide con PORT de la app. En esos casos el diagnóstico es inmediato con docker inspect -f '{{range .State.Health.Log}}{{println .}}{{end}}'.
