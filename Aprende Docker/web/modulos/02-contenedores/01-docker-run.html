docker run, ps, logs y exec

Módulo 2 · Contenedores en ejecución ⏱ 30 minutos

1 · Introducción

En el módulo anterior aprendiste a construir imágenes con un Dockerfile: recetas inmutables que contienen todas las dependencias de tu aplicación. Pero una imagen guardada en disco no sirve de nada por sí sola: hay que ponerla en marcha. Ese es el trabajo de docker run, el comando más usado de todo Docker. Sin él, todo lo demás —puertos, variables, reinicios, límites— no tiene sobre qué aplicarse.

En esta lección vas a dominar el ciclo completo de interacción con un contenedor en ejecución: lanzarlo (docker run), ver qué está vivo (docker ps/-a), leer sus logs en tiempo real (docker logs -f), meterte dentro para diagnosticar (docker exec -it), y pararlo / arrancarlo / borrarlo (docker stop, start, rm). Trabajaremos con nginx, el contenedor más habitual en el mundo de los servidores web y el que usarás como pieza web de HarborTasks.

¿Por qué esta lección abre el módulo 2? Porque «contenedores en ejecución» es exactamente la frontera entre construir imágenes (estático, determinista, del módulo 1) y operar procesos vivos (estado, logs, red, recursos, del resto del módulo). Todo lo que aprenderás después son refinamientos de esta misma interacción: «el contenedor ya corre, ahora lo configuro, lo protejo y lo vigilo».

2 · Teoría

Qué hace realmente docker run

Recuerda la arquitectura cliente-servidor (módulo 0): docker es un cliente que habla por HTTP con el daemon (dockerd). docker run es en realidad una combinación de dos operaciones: docker create (prepara el contenedor: reserva el filesystem de capas, el namespace, la configuración) y docker start (arranca el proceso principal). El daemon delega la creación del proceso a containerd y este a runc, que es quien construye el "sandbox" con namespaces y cgroups.

  docker run -d --name web nginx:1.27-alpine
     = docker create  +  docker start      (preparar + arrancar)

        TU TERMINAL (docker CLI)
            │  petición por API HTTP (socket /var/run/docker.sock)
            ▼
        dockerd  (daemon de Docker)
            │  si la imagen no está local → la descarga del registry (pull)
            ▼
        containerd   (runtime de gestión de contenedores)
            │
            ▼
        runc   (crea el "sandbox": namespaces PID/red/FS + cgroups)
            │
            ▼
        EL PROCESO DE TU APP → dentro del contenedor es el PID 1

Dos detalles clave de este flujo. Primero: si la imagen no existe localmente, la descarga automáticamente; por eso tu primer docker run nginx:1.27-alpine tarda más que los siguientes. Segundo: un contenedor no es más que un proceso aislado. Si ese proceso termina, el contenedor termina. No hay magia: si lanzas una imagen cuyo comando acaba al instante (alpine echo hola), el contenedor se crea, imprim…, y pasa a Exited.

Primer plano vs segundo plano (-d)

Por defecto, docker run queda pegado a tu terminal (modo foreground o adjuntado): ves los logs en vivo y, al cerrar la terminal o pulsar Ctrl+C, el contenedor muere. Para servicios de larga duración (un servidor web, una API) lo normal en un servidor es detached con -d: el proceso corre en segundo plano, tu terminal queda libre y los logs se guardan para leerlos con docker logs. Es el equivalente a lanzar un servicio con systemctl en lugar de una orden cualquiera en la terminal.

Analogía: la imagen es una receta de cocina; docker run es cocinar el plato. Puedes cocinar el mismo plato mil veces (mil contenedores) con la misma receta, y cada plato es independiente: se quema uno y los otros siguen perfectos. docker ps es mirar qué platos hay en la cocina y en qué estado están; docker logs es leer la libreta de anotaciones del cocinero sobre ese plato concreto.

3 · Ejemplo mínimo

El ciclo mínimo de vida de un contenedor con nginx, paso a paso. Cada comando está comentado para que sepas por qué existe. Cópialos en tu terminal (Linux, macOS o la distro de WSL2):

# Lanza nginx en segundo plano (-d). Si la imagen no está local, la descarga.
# --name web: nombre humano. Sin él tendrías que operar con un ID hexadecimal.
docker run -d --name web nginx:1.27-alpine

# Lista los contenedores EN MARCHA: CONTAINER ID, IMAGE, COMMAND, STATUS...
# Fíjate en la columna PORTS: está vacía porque aún no hemos publicado nada.
docker ps

# Lista TODOS los contenedores, incluidos los parados (de ahí la "-a").
# Aquí aparecerán también los que ya se cerraron; es tu herramienta de diagnóstico.
docker ps -a

# Lee los logs del contenedor. Añade -f para seguirlos en tiempo real,
# igual que "tail -f" en un archivo: útil para ver el arranque y las peticiones.
docker logs -f web            # Ctrl+C para dejar de seguir (no para el contenedor)

# Entra DENTRO del contenedor con una shell. "-it" = sesión interactiva con TTY.
# La imagen Alpine de nginx trae "sh" (shell mínima). Es un proceso NUEVO,
# no el proceso principal; al salir, el contenedor sigue corriendo.
docker exec -it web sh        # dentro: ls /usr/share/nginx/html  → exit

# Parada ordenada: manda SIGTERM al proceso principal (nginx) y espera a que salga.
# NO borra el contenedor: podrás arrancarlo otra vez con el mismo estado.
docker stop web

# Lo arranca de nuevo. MISMO id, MISMO nombre, MISMO filesystem (lo que hayas
# creado dentro sigue ahí).
docker start web

# Muestra cómo quedó el mapeo de puertos (aún nada publicado → salida vacía).
docker port web

# Elimina el contenedor parado definitivamente. No borra la imagen ni las capas:
# esa memoria sigue disponible para futuros "docker run". Libera el nombre.
docker rm web

Con estos ocho comandos ya puedes operar cualquier contenedor del mundo. La lógica es siempre la misma: lanzar → inspeccionar → diagnosticar → parar/arrancar → limpiar. Este ciclo es el «respirar y andar» del trabajo con Docker.

4 · Ejemplo real

Ahora encendamos nginx como se haría de verdad y demostremos el ciclo de interacción: publicar el puerto para poder navegar a él, ver sus logs de acceso, entrar a modificar un archivo y comprobar que el cambio «persiste» mientras el contenedor exista.

# --rm es práctico para pruebas: al parar, el contenedor se autodestruye.
# -p 8080:80 publica: a la derecha el puerto INTERNO de nginx (80),
# a la izquierda el puerto de TU MÁQUINA por el que lo alcanzas.
docker run -d --name web --rm -p 8080:80 nginx:1.27-alpine

# ¿El contenedor está vivo? La columna PORTS ya muestra "0.0.0.0:8080->80/tcp".
docker ps --filter name=web

# ¿Y ese "COMMAND" que aparece? El proceso real dentro del contenedor:
docker inspect web --format '{{.Config.Cmd}}'
# → [docker-entrypoint.sh nginx -g daemon off;]  (nginx "en primer plano" para
#   que el contenedor siga vivo; sin esto nginx se haría demonio y moriría el PID 1)

# Recupera la IP interna del contenedor dentro de la red bridge de Docker.
docker inspect web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
# → 172.17.0.2 (típica de la red bridge por defecto)

# Petición DESDE FUERA por el puerto publicado (como haría un navegador):
curl -s http://localhost:8080 | head -n 5
# →  ... Welcome to nginx! ...

# Los logs de acceso: la petición anterior ya está registrada (método, ruta, código).
docker logs web
# → "GET / HTTP/1.1" 200 ...  (¡ahí está tu curl!)

# Entra y modifica la página "por dentro" como haría un sysadmin:
docker exec -it web sh -c 'echo "<h1>¡Hola desde Docker!</h1>" > /usr/share/nginx/html/index.html'

# El servidor responde ahora TU HTML: el contenedor tiene su propio filesystem
# en la capa superior escribible (copy-on-write visto en el módulo 1).
curl -s http://localhost:8080
# → ¡Hola desde Docker!

# docker attach NO es "volver a entrar": conecta tu terminal al stdin/out del
# PID 1 (nginx). Sin entrada de teclado que consumir y con logs saliendo,
# la terminal puede parecer colgada. Por eso el patrón es exec, no attach.
docker attach web        # pruébalo y pulsa Ctrl+P Ctrl+Q para desadjuntar

# Procesos que hay dentro del contenedor (visto desde fuera, con su PID interno):
docker exec web ps -o pid,comm
# → PID 1 nginx (master) y sus workers. El master de nginx es el PID 1 ⇒
#   es quien recibe las señales (SIGTERM de docker stop) y reparte el trabajo.

Nota multi-OS: localhost en Linux nativo apunta directo al host. En macOS y Windows con Docker Desktop/WSL2, ese mismo localhost:8080 funciona porque la VM (o WSL2) redirige automáticamente los puertos publicados; por eso verás siempre localhost:8080 en los ejemplos canónicos. La IP 172.17.x.x del contenedor, en cambio, solo es válida dentro de la red interna de Docker.

6 · Errores habituales

Correr nginx en primer plano y perder la terminal

# ❌ Lanzar un servicio sin -d: la terminal queda "pegada" a los logs
docker run nginx:1.27-alpine
# → nginx ocupa tu terminal. Ctrl+C envía SIGINT y MUERE el contenedor.
#   Si el SSH se cae, el contenedor se va con él.

# ✅ En un servidor queremos que viva independiente de mi terminal
docker run -d --name web nginx:1.27-alpine
# → Vuelve al prompt al instante; los logs quedan en docker logs.

Olvidar --name y acabar operando con IDs ilegibles

# ❌ Sin nombre, Docker asigna un id aleatorio tipo 8f31a2b9c41d...
docker run -d nginx:1.27-alpine
docker stop 8f31a2b9c41d          # penoso y propenso a errores

# ✅ Nombre siempre: todos los demás comandos se vuelven legibles
docker run -d --name web nginx:1.27-alpine
docker stop web

Confundir docker attach con docker exec

# ❌ attach: conecta al stdio del PID 1 (nginx). No hay "prompt", solo logs
docker attach web                 # parece colgado; hay que recordar Ctrl+P Ctrl+Q

# ✅ exec: crea un proceso NUEVO (sh) con el que inspeccionar y salir
docker exec -it web sh            # estás DENTRO, trabajas, y "exit" te devuelve

Buscar logs en el contenedor equivocado

# ❌ "no me sale nada": porque el contenedor que miras ya no corre o es otro
docker logs web --since 1m        # vacío si web se reinició antes de esa marca

# ✅ Recuerda que logs es por CONTENEDOR, y usa --filter para encontrarlo
docker ps -a --filter name=web
docker logs --tail 50 web

Regla mental: si un contenedor «desaparece», el 90% de las veces siguió vivo en docker ps -a como Exited. La -a es tu primera herramienta de troubleshooting, antes que cualquier otra.

7 · Ejercicio guiado

Objetivo: poner en marcha un nginx, servirlo por HTTP y demostrar el ciclo completo run → ps → logs → exec → stop → start → rm, verificando cada paso con su salida esperada.

  1. Paso 1 — Lanza el contenedor. 
    docker run -d --name demo nginx:1.27-alpine

    Esperado: vuelves al prompt y Docker responde con el ID largo del contenedor (no la imagen). Si es la primera ejecución, verás además el progreso de la descarga.

  2. Paso 2 — Verifica que está vivo. 
    docker ps --filter name=demo
# ESPERADO: STATUS "Up X seconds", COMMAND "[docker-entrypoint.sh nginx...]",
# PORTS vacío (aún no publicado). IMAGE nginx:1.27-alpine y NAME demo.
  3. Paso 3 — Encuentra su IP interna y hazle una petición. 
    docker inspect demo --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
# → 172.17.0.2 (apunta tu IP, puede variar)
curl -s http://172.17.0.2:80 | head -n 3
# ESPERADO: "" ... "Welcome to nginx!"
  4. Paso 4 — Comprueba que el curl quedó en el access log. 
    docker logs demo
# ESPERADO: una línea con "GET / HTTP/1.1" 200 ... (tu petición del paso 3).
docker logs --tail 5 demo        # solo las 5 últimas líneas
  5. Paso 5 — Entra y cambia la página de bienvenida. 
    docker exec -it demo sh -c 'echo "Página modificada por Docker" > /usr/share/nginx/html/index.html'
curl -s http://172.17.0.2:80
# ESPERADO: ahora responde "Página modificada por Docker" (no la de nginx).
  6. Paso 6 — Para, arranca y comprueba que TODO sigue. 
    docker stop demo
docker ps -a --filter name=demo   # ESPERADO: STATUS "Exited (0)" (parada limpia)
docker start demo                 # el mismo contenedor vuelve a la vida
curl -s http://172.17.0.2:80
# ESPERADO: sigue tu página modificada. El filesystem vivió con él: no es efímero
# como un proceso; es su "disco" de capa superior.
  7. Paso 7 — Limpia. 
    docker rm -f demo
docker ps -a --filter name=demo   # ESPERADO: ya no existe (se ha limpiado)

    Verificación final: si has visto las salidas esperadas en cada paso, has operado un contenedor real de principio a fin. Eso es exactamente el día a día de un ingeniero de plataforma.

8 · Reto

🎯 Dos servidores a la vez, un solo ojo

Lanza dos contenedores de nginx simultáneos (web-a y web-b) con la misma imagen, publicando cada uno en un puerto distinto de tu máquina (-p 8081:80 y -p 8082:80). Después, dispara al menos 20 peticiones alternadas a cada puerto con un pequeño bucle de curl y responde por escrito (en los comentarios de tu comandos): ¿cómo sabes, mirando docker logs y docker stats, qué contenedor sirvió cada petición? ¿Comparten algo los dos contenedores o son mundos completamente aislados?

Pista: los logs de acceso registran la IP del cliente y la ruta; lanza docker logs --since 2m web-a y docker logs --since 2m web-b y fíjate en cuántas líneas tiene cada uno. Para las estadísticas: docker stats en vivo o docker stats --no-stream para una foto.

9 · Resumen

  • docker run = create + start: prepara el contenedor y arranca su proceso principal (el PID 1 dentro del sandbox).
  • Un contenedor es un proceso aislado (namespaces + cgroups): si su proceso principal termina, el contenedor pasa a Exited.
  • -d desacopla el contenedor de tu terminal; --name lo hace operable; -it permite sesiones interactivas.
  • ps lista lo vivo; ps -a lista todo (incluidos los Exited): tu primer diagnóstico.
  • logs (-f, --tail, --since) son los logs del proceso, no archivos que tengas que buscar en el disco.
  • exec -it <c> sh crea un proceso nuevo dentro para inspeccionar; attach se usa en contadas ocasiones.
  • stop/start/rm cierran el ciclo: parar limpiamente (SIGTERM), reanudar con el mismo estado y borrar.

10 · Preguntas frecuentes

¿Por qué mi contenedor se detiene automáticamente al lanzarlo?

Porque el contenedor es un proceso: en cuanto el proceso principal termina su trabajo, el contenedor pasa a Exited. Si lanzas alpine echo hola, el echo acaba en un instante y el contenedor también. Las imágenes de servidores (como nginx) «se quedan» en primer plano a propósito precisamente para que el PID 1 nunca termine. Mira siempre el ExitCode con docker inspect: 0 es éxito (terminó por diseño), ≠ 0 es un error de tu aplicación.

¿Cuál es la diferencia real entre docker attach y docker exec?

attach reutiliza los streams (stdin/stdout) del proceso principal (PID 1); no crea nada nuevo. Con un proceso tipo nginx, que no lee de stdin, la terminal parece colgarse. exec, en cambio, lanza un proceso nuevo (p. ej. sh) dentro de los mismos namespaces y cgroups, y ese proceso termina cuando tu comandito termina. En la práctica, exec -it es el patrón correcto para el 99% de los casos.

¿Cuándo debo usar --rm?

--rm borra el contenedor automáticamente cuando este para. Es ideal para pruebas, CI y procesos de un solo uso (no acumulas basura). Para servicios de producción en -d no suele tener sentido: cuando el contenedor se caiga querrás que siga existiendo para leer sus logs y su estado, o que la política de reinicio lo vuelva a levantar. Las políticas de reinicio se ven en la lección «Ciclo de vida y restart policies».

¿Puedo entrar a un contenedor que está parado?

docker exec exige un contenedor en marcha (necesita procesos vivos a los que unirse). Si tu contenedor está Exited, tienes dos caminos: docker start para volver a levantarlo y luego exec, o docker run --rm --entrypoint sh imagen para crear un contenedor temporal con la misma imagen que abra una shell y te deje inspeccionar el filesystem de la imagen (no el de tu contenedor parado).

¿Por qué mi `docker ps` no muestra el puerto aunque el contenedor «escucha» en 80?

Porque «escuchar» dentro del contenedor y «estar publicado» en tu máquina son dos cosas distintas. El puerto interno (80 de nginx) solo existe en la red privada de Docker. Para alcanzarlo desde tu host necesitas -p host:contenedor (-p 8080:80) recogido en el momento del docker run. Es exactamente el tema de la siguiente lección, «Puertos y variables de entorno».
