Ciclo de vida y restart policies

Módulo 2 · Contenedores en ejecución ⏱ 30 minutos

1 · Introducción

Un contenedor no es un objeto estático que «está arriba o abajo»: es un proceso con un ciclo de vida — se crea, se pone en marcha, se pausa, muere y puede renacer. Entender esos estados (y las señales del sistema operativo que los provocan) es lo que separa a quien «sabe lanzar Docker» de quien puede operarlo de verdad, porque casi todos los problemas de producción son, en el fondo, problemas de ciclo de vida: «se paró», «no responde al apagado», «se reinicia en bucle».

En esta lección aprenderás los estados por los que pasa un contenedor, qué es el PID 1 y por qué las señales (SIGTERM/SIGKILL) deciden si una parada es limpia o traumática, la diferencia entre ejecución interactiva (-it) y desacoplada (-d), las cuatro restart policies (no, on-failure, unless-stopped, always) y cómo controlar el apagado con docker stop --time.

¿Por qué importa tanto? Porque a Kubernetes (el módulo 5+) lo aprenderás como un «orquestador de ciclos de vida»: vigilando procesos muertos, reiniciándolos y gestionando señales a otra escala. Si no dominas el ciclo de vida en Docker local, toda la orquestación posterior será copiar comandos sin entenderlos.

2 · Teoría

La máquina de estados de un contenedor

Cada contenedor es un objeto persistente (con su ID, nombre y capa superior) que recorre estados. docker create y docker run producen created; el proceso en marcha produce running; puede congelarse en paused (todos sus hilos detenidos mediante SIGSTOP, conservando la memoria reservada); y cuando el proceso principal termina pasa a exited, que ya no consume CPU ni memoria pero conserva su filesystem y su configuración hasta que lo borres con docker rm (entonces dead, y desaparece).

                docker create  (o docker run sin arrancar aún)
                         │
                         ▼
     ┌────────┐  docker start / docker run   ┌─────────┐
     │ created│ ───────────────────────────► │ running │◄────┐
     └────────┘                              └────┬────┘     │ docker unpause
          ▲                                      │           │
          │                      docker pause    │  docker   │
          │                       (SIGSTOP)      │   start   │
          │                                      ▼    /      │
          │                                   ┌────────┐  restart
          │        docker stop (SIGTERM─►SIGKILL)      │
     docker rm │                       ┌─────│ exited │
          │     (borra)                │     └────────┘
          ▼        ┌───────────────────┐
         dead ────►│ se elimina: fin   │
        (removido) └───────────────────┘

El estado exited es el protagonista del troubleshooting: con docker inspect puedes leer el ExitCode (0 = terminó con éxito, 137 = matado por señal SIGKILL, 143 = SIGTERM, etc.) y el momento, igual que haces echo $? con un comando de tu shell.

PID 1 y las señales: la parada limpia vs la traumática

Dentro de cada contenedor, el proceso principal es el PID 1 de ese namespace. El daemon se comunica con él enviándole señales: docker stop envía SIGTERM (pedir cortésmente que acabe) y, si en un plazo (por defecto 10 s) no termina, envía SIGKILL (matar sin derecho a réplica). docker kill envía la señal que tú elijas de inmediato. El «porqué» del tiempo de gracia: es la oportunidad de tu app para cerrar conexiones, vaciar buffers y confirmar transacciones — exactamente lo que haría un servidor web bien educado al recibir SIGTERM.

   docker stop web
   ─────────────► 1) SIGTERM  ──► PID 1 nginx: "apaga los listeners, guarda, sal"
                     │
                     │  ¿terminó en <10 s>?  ──sí──►  exited 0  (parada limpia)
                     │
                     └── no ──► 2) SIGKILL ──► el kernel lo mata sin aviso
                                                                  (exit 137)

   PID 1 además "adopta" huérfanos: si un proceso hijo muere y nadie lo recoge,
   se convierte en zombie; un PID1 responsable (init, tini) los "reap". Por eso
   algunas imágenes añaden --init/tini como PID 1 antes que la propia app.

El overhead del proceso init que a veces verás mencionado: si tu aplicación lanza hijos (workers) que pueden morir, el PID 1 ideal no es tu app sino un mini-init (tini, integrado en Docker con --init) que (a) reenvía señales al proceso real y (b) hace reaping de zombies. Su coste es insignificante (unos pocos megabytes de RAM) y su beneficio, real en apps que hacen fork o no gestionan SIGTERM.

-it vs -d: dos estilos de ejecución

-i mantiene el stdin abierto y -t asigna una pseudo-TTY; juntos dan -it, imprescindible para usar el contenedor (una shell, un REPL). Sin TTY, las apps que colorean su salida o leen de teclado se comportan distinto. -d (detached) ejecuta sin fijarse a tu terminal; útil porque el contenedor sigue vivo aunque cierres la ventana. No son rivales: son para momentos distintos. Y recuerda que «desacoplado» no significa «sin supervisión»: para eso existen las restart policies.

Restart policies: quién devuelve la vida al contenedor

En un servidor, cuando un proceso se cae, alguien debe levantarlo. Las restart policies lo delegan en el propio daemon de Docker. Importante: restart policy ≠ reinicio manual (docker restart); y la política solo actúa sobre caídas — si tú lanzas docker stop, Docker respeta tu decisión, salvo el matiz de always al reiniciar el daemon.

Política¿Reinicia tras caída?¿Tras reiniciar el daemon?Cuándo usarla
--restart no (por defecto)NoNoProcesos de un solo uso, pruebas, jobs puntuales
--restart on-failure[:n]Sí, solo si el código de salida ≠ 0 (hasta n veces)NoJobs y workers que deben reintentar fallos puntuales
--restart unless-stoppedSíSí, pero solo si no lo paraste tú a manoServicios de aplicación en producción (API, web)
--restart alwaysSíSí, tuviera el estado que tuvieraInfraestructura crítica: agentes, registrars, reverse proxies

Matiz fino: con always también se reinicia un contenedor stop manual… al reiniciar el daemon (Docker lo levanta por diseño). Con unless-stopped, en cambio, si tú lo paraste a mano, el daemon lo deja parado. Por eso en producción el patrón recomendado para servicios es unless-stopped: te permite «apagar la máquina» manualmente sin que vuelva sola.

3 · Ejemplo mínimo

El ciclo de vida en acción con un contenedor «de un solo uso», y la política de reinicio demostrada en un comando:

# 1) El contenedor efímero: la app imprime y termina → el contenedor EXITED.
docker run --name saluda alpine echo '¡hola!'
# → "¡hola!" y, al instante, docker devuelve el prompt.
# El contenedor NO ha desaparecido: sigue existiendo, en estado exited.

# 2) Míralo en docker ps -a: sigue ahí, con STATUS "Exited (0)".
docker ps -a --filter name=saluda

# 3) Estado y código de salida con docker inspect (tu diagnóstico):
docker inspect saluda --format '{{.State.Status}} · {{.State.ExitCode}}'
# → exited · 0        (0 = terminó con éxito por diseño)

# 4) Lo puedes volver a arrancar: mismo nombre, misma capa superior.
docker start saluda            # vuelve a ejecutar el mismo `echo`

# 5) Procesos interactivos que "pisan" la terminal: -it te da una shell.
docker run -it --rm node:24-alpine sh        # dentro: node --version, luego exit

# 6) Politica de reinicio en marcha: la app "muere" y Docker la revive.
docker run -d --name worker --restart unless-stopped \
  node:24-alpine node -e 'setTimeout(()=>process.exit(3), 3000)'
# ↑ a los 3 s el proceso sale con código 3 (error)…
docker ps --filter name=worker   # …y sigue "Up": Docker lo ha reiniciado sola.
docker inspect worker --format '{{.RestartCount}} reinicios'

Fíjate en el paso 6: exit(3) no es un fallo de Docker ni un config: es la aplicación pidiendo morir, y aun así la política la levanta. Traza exactamente el contrato de una restart policy: no decide si el proceso debe morir, decide qué pasa después.

4 · Ejemplo real

La API de HarborTasks en «producción local»: política correcta, apagado con tiempo controlado y una app que responde a SIGTERM de forma elegante para no perder ninguna petición en curso.

# --- Dockerfile de la API con un manejador de señales ---
FROM node:24-alpine
ENV PORT=3000
WORKDIR /app
COPY . .
EXPOSE 3000
# El proceso principal escucha señales y CERRARÁ CON GRACIA al recibir SIGTERM:
# cierra el servidor HTTP y confirma antes de morir (ver server.js).
CMD ["node", "server.js"]
// server.js — fragmento: apagado elegante al recibir SIGTERM
const server = require('http').createServer((req, res) => res.end('ok'));
server.listen(process.env.PORT || 3000, () => console.log('API escuchando'));

function shutdown(reason) {
  console.log(`Recibido ${reason}: cerrando conexiones…`);
  server.close(() => { console.log('Cerrado limpio ✓'); process.exit(0); });
  setTimeout(() => process.exit(1), 4000); // garantía: nunca más de 4 s
}
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT',  () => shutdown('SIGINT'));

# Lanza en producción local: política unless-stopped (recomendada p/ servicios).
docker build -t harbor-api:0.1.0 .
docker run -d --name api --restart unless-stopped \
  -p 8080:3000 -e PORT=3000 harbor-api:0.1.0

# Apagado CONTROLADO: espera como máximo 10 s (por defecto) a que la app
# termine su SIGTERM. Con el manejador anterior, el stop es casi instantáneo.
time docker stop api            # → tarda milisegundos: la app cierra sola
# (sin manejador, Docker esperaría los 10 s y luego SIGKILL traumático)

# ¿Y si quieres darle tu propio plazo? La app es lenta cerrando:
docker start api
docker stop --time=20 api       # dale 20 s de margen antes del SIGKILL

# Fuerza inmediata de una señal concreta (sin espera):
docker start api
docker kill --signal=SIGINT api # equivalente a Ctrl+C dentro

# Estado detallado para el informe de incidentes:
docker inspect api --format '{{.State.Status}} · exit={{.State.ExitCode}} · restarts={{.RestartCount}}'

# "Restart en bucle": App que muere a los 2 s con código 1 y política on-failure:3.
docker run -d --name crash --restart on-failure:3 \
  node:24-alpine node -e 'setTimeout(()=>process.exit(1), 2000)'
sleep 12 && docker inspect crash --format '{{.RestartCount}} reinicios, última salida {{.State.ExitCode}}'
# → tras 3 intentos, Docker deja de intentarlo. El problema es del código, no del motor.
docker rm -f crash

Para ojo de sysadmin: puedes observar los reinicios en vivo con docker events --filter event=restart o docker events --filter container=api. Es el primer paso mental hacia kubectl get events de Kubernetes.

5 · Buenas prácticas

HazEvitaPor qué
--restart unless-stopped para servicios (API, web) en producción Contenedores críticos sin política (default no) Sin política, una caída a las 3 a.m. te baja el servicio para siempre; unless-stopped te permite pararlo a mano sin que vuelva solo
on-failure[:n] para jobs y procesos que reintentan fallos puntuales always para jobs que deben ejecutarse UNA vez Reiniciar un job en bucle infinito puede disparar efectos secundarios (pago duplicado, email repetido) cada relanzamiento

Usar docker run --init en imágenes cuyas apps lanzan procesos hijos Dejar zombie a toda una generación de workers huérfanos El mini-init (tini) hace de PID 1: reenvía señales y reap huérfanos; su coste en RAM es despreciable frente al problema que evita
Diagnosticar con docker inspect (Status, ExitCode, RestartCount) Adivinar el problema mirando docker ps a secas El estado en una línea esconde el dato que importa: qué código de salida, cuántos reinicios, cuándo empezó o si está en un ciclo de reinicio.

6 · Errores habituales

Usar --restart always para una tarea que debe correr una sola vez

# ❌ Job de migración con always: si el job termina bien (exit 0),
#    al reiniciar el daemon se volvería a ejecutar. El trabajo se duplica.
docker run -d --restart always --name migracion imagen-migracion

# ✅ Para trabajos puntuales, sin política o con on-failure limitado
docker run --rm imagen-migracion                                # una vez y se limpia
docker run -d --restart on-failure:5 --name migracion imagen-migracion
#   reintentar solo fallos puntuales, salir cuando el puente de nuevo funciona

Confundir el docker stop de 10 s con «el contenedor se quedó colgado»

# ❌ `docker stop web` tarda y "no hace nada" durante 10 s: no es un fallo
#    de Docker, es la app IGNORANDO el SIGTERM. Docker espera su turno.
docker stop web            # 10 s muertos → SIGKILL → exit 137

# ✅ Si la app no responde a señales, doy instrucciones certeras:
docker stop --time=2 web   # 2 s de margen y SIGKILL
# o, para depurar por qué no cierra: docker kill --signal=SIGQUIT web
# (SIGQUIT suele volcar el stack trace del proceso — el mejor debugging)

Mandar SIGKILL directamente «porque es más rápido»

# ❌ kill con SIGKILL de entrada: la app muere sin cerrar conexiones.
#    Postgres sin fsync, nginx con sockets a medio escribir… datos perdidos.
docker kill web

# ✅ stop es la vía educada; kill solo cuando hay urgencia real
docker stop web                     # SIGTERM + tiempo de gracia
docker kill --signal=SIGTERM web    # "stop" exprés equivalente sin espera

Elegir restart policies sin pensar en el reinicio del DAEMON

# ❌ always + daemon reinicia: TODOS los contenedores vuelven, aun los que
#    paraste a mano "para frenar el incidente".
docker run -d --restart always

# ✅ unless-stopped respeta tu decisión manual: no vuelve si tú lo paraste
docker run -d --restart unless-stopped

7 · Ejercicio guiado

Objetivo: demostrar las tres verdades del ciclo de vida — (1) la política on-failure reinicia solo fallos y se agota, (2) always jamás se rinde, (3) stop --time controla el apagado — con salidas verificables en cada paso.

  1. Paso 1 — Lanza un contenedor que «muere» siempre. 
    docker run -d --name probe --restart on-failure:3 \
  node:24-alpine node -e 'setTimeout(()=>process.exit(1), 1500)'

    La app sale con código 1 (fallo) a los 1.5 s. Recuerda: on-failure:3 reintentará hasta 3 veces.

  2. Paso 2 — Observa el bucle y el agotamiento. 
    sleep 20
docker inspect probe --format '{{.RestartCount}} reinicios · estado {{.State.Status}}'
# ESPERADO: "3 reinicios · estado exited" (la política se ha rendido).
# El ExitCode de la última salida sigue siendo 1: la app es la culpable.
docker inspect probe --format '{{.State.ExitCode}}'
  3. Paso 3 — Demuestra que always jamás se rinde. 
    docker run -d --name probe-always --restart always \
  node:24-alpine node -e 'setTimeout(()=>process.exit(1), 1200)'
sleep 8
docker inspect probe-always --format '{{.RestartCount}} reinicios · estado {{.State.Status}}'
# ESPERADO: 3+ reinicios y estado "running" (o en "restarting" el instante justo).
# La diferencia con el paso 2 es solo el flag: política = comportamiento.
  4. Paso 4 — Parada con tiempo controlado. 
    # App que NO gestiona SIGTERM: la parada forzada tarda el plazo que le des.
docker stop --time=2 probe-always
# ESPERADO: tarda ~2 s (espera el plazo) y luego SIGKILL.
time docker stop --time=2 probe-always     # observa el segundo
  5. Paso 5 — El apagado elegante, en primera persona. 
    # Node escucha SIGTERM y cierra sus conexiones antes de salir:
docker run -d --name gentle --restart unless-stopped node:24-alpine \
  node -e 'process.on("SIGTERM",()=>{console.log("cerrando conexiones ✓");process.exit(0)});setInterval(()=>{},1000)'
time docker stop gentle     # ESPERADO: ms, sin espera forzada. El "cerrando" llega a docker logs.
docker logs --tail 2 gentle # → cerrando conexiones ✓
docker rm -f probe probe-always gentle

    Verificación final: diste tres respuestas distintas al mismo problema (una app que muere) cambiando solo la política o el plazo: eso es el ciclo de vida entendido, no memorizado.

8 · Reto

🎯 Construye tu propio PID 1

Crea una imagen propia donde el PID 1 no sea tu app, sino un mini-script (bash o Node) de ~10 líneas que debe: (1) recibir SIGTERM y reenviarlo a su hijo (la app), (2) esperar a que el hijo muera y entonces morir con su mismo código de salida, y (3) recoger los posibles huérfanos (wait en bucle). Pon como ENTRYPOINT ese script y lanzalo con --restart on-failure:2 para comprobar: cuando la app falle, el exit code que ve Docker debe ser el de la app, no el del script. Pregunta para responder en un comentario: ¿por qué este patrón importa para contenedores con procesos hijos?

Pista: en bash, trap 'kill $PID_HIJO' TERM + un bucle while true; do wait; done (o wait $PID_HIJO; exit $?) es el esqueleto. Muchos proyectos usan tini (sin parámetros extra al build) precisamente para no reinventar esto — prueba docker run --init y compara la diferencia de comportamiento frente a SIGTERM.

9 · Resumen

  • Un contenedor recorre estados: created → running → paused / exited → dead. exited conserva el filesystem y la configuración hasta el docker rm.
  • El PID 1 del namespace recibe las señales del daemon: SIGTERM (cortesía) y, tras el plazo, SIGKILL. Un PID 1 responsable reapa huérfanos y reenvía señales.
  • -it es ejecución interactiva con TTY; -d es desacoplada. No son rivales: momentos distintos.
  • Restart policies: no (default), on-failure[:n], unless-stopped (recomendada p/ servicios), always (infraestructura). Actúan sobre caídas, no sobre tus stop manuales (con el matiz de always al reiniciar el daemon).
  • docker stop --time=N controla el margen antes del SIGKILL; docker kill --signal fuerza una señal concreta.
  • docker inspect expone Status, ExitCode, RestartCount y StartedAt: tu panel de diagnóstico.
Comando / flagQué hace
docker create / start / restartPrepara / arranca / reinicia un contenedor existente
docker pause / unpauseCongela / descongela el proceso (SIGSTOP del cgroup)
docker stop <c>SIGTERM al PID 1 y espera hasta 10 s antes del SIGKILL
docker stop --time=NAjusta el margen de gracia antes del SIGKILL
docker kill --signal=SIG nomeEnvía una señal concreta sin esperar

10 · Preguntas frecuentes

¿Cuál es la diferencia entre docker stop y docker kill?

docker stop sigue un protocolo: envía SIGTERM (invitación a cerrarse con elegancia) y, si en el plazo configurado (default 10 s) el proceso no ha terminado, envía SIGKILL (muerte inmediata). docker kill envía ya la señal que elijas, sin margen: por defecto SIGKILL, pero puede ser cualquier otra (--signal=SIGINT…). Esta lección les dedica un seguido: stop es la parada civilizada; kill es para urgencias o para pruebas de señal.

¿Por qué docker stop tarda exactamente unos 10 segundos algunas veces y otras no?

Porque el plazo es un tiempo de espera máximo, no un tiempo fijo. Docker manda SIGTERM y espera: si tu app responde bien (por ejemplo gestiona la señal y cierra en 200 ms), el stop es instantáneo. Si la app lo ignora, Docker aguanta el plazo por defecto (10 s, ajustable con --time) y entonces aplica SIGKILL. Un stop «lento» es tu primera señal de que la aplicación no gestiona el cierre ordenado.

¿Qué es eso del PID 1 y por qué a veces se recomienda --init?

Dentro del namespace del contenedor, el primer proceso (el CMD/ENTRYPOINT de la imagen) recibe el PID 1. El daemon le inyecta las señales a él, así que si tu app gestiona SIGTERM, todo funciona bien. El problema aparece con apps que lanzan procesos hijos: cuando un hijo muere, el PID 1 debe «recogerlo» (reaping) para que no quede zombie acumulándose. docker run --init coloca un mini-init (tini) como PID 1 que reenvía señales a la app real y barre huérfanos. Es también el motivo por el que imágenes oficiales (Postgres, Redis) traen su propio init o entrypoint.

¿Por qué mi contenedor con --restart always vuelve a arrancar cuando reinicio Docker, aunque yo lo había parado?

Porque always indica «vuelve a estar arriba pase lo que pase», incluso si tú lo detuviste manualmente. Al reiniciar el daemon, Docker aplica la política y lo levanta. Si quieres poder apagar manualmente un servicio «para frenar un incidente» y que el reinicio del daemon respete tu decisión, usa unless-stopped: la única diferencia entre ambas es exactamente ese comportamiento. Es la razón de que unless-stopped sea el patrón recomendado en producción para servicios.

¿Una restart policy sustituye a un orquestador tipo Kubernetes?

No. La restart policy es local a la máquina donde corre el daemon: se limita a reiniciar ese contenedor en esa máquina. No te da alta disponibilidad (si el host muere, el contenedor muere), ni equilibrio de carga entre réplicas, ni re-despliegues. Kubernetes lleva la idea a otra escala: si el Pod falla, el kubelet (o el controlador) lo reinicia y, si además lo gestiona un Deployment, crea de cero una réplica nueva, quizá en otro nodo. Verás todo eso a partir del módulo 5; esta lección es la semilla local de esa idea.
