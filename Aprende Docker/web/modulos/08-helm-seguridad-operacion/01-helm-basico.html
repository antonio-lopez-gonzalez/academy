Helm: charts, values y releases

Módulo 8 · Helm, seguridad y operación ⏱ 35 minutos

1 · Introducción

Si has llegado hasta aquí ya sabes lo que cuesta desplegar un solo servicio en Kubernetes: un Deployment, un Service, un ConfigMap, tal vez un Secret, un PVC, un Ingress… Y eso es un solo microservicio. HarborTasks tiene tres. Una aplicación real tiene veinte o treinta. Ahora multiplica por los entornos: dev, staging, prod.

El resultado es una selva de YAML duplicados donde el mismo Deployment aparece copiado una y otra vez con tres líneas cambiadas (la imagen, las réplicas, el host del Ingress). Cambiar una variable implica editar diez archivos, y olvidar uno produce bugs que solo aparecen en producción.

En esta lección aprenderás Helm, el gestor de paquetes de Kubernetes: qué problema resuelve (plantillas, versionado y despliegues repetibles), qué son un chart, un release y los values, y cómo instalar, actualizar, hacer rollback y desinstalar aplicaciones con unos pocos comandos.

¿Por qué Helm? Porque convierte el YAML en un programa: el mismo chart se renderiza de forma distinta según los valores que le pases. Adiós a copiar y pegar manifiestos; hola a despliegues reproducibles y con historial de versiones.

2 · Teoría

El problema: decenas de YAML con plantillas duplicadas

En el Módulo 7 desplegaste recursos "a mano" con kubectl apply -f archivo.yaml. Ese enfoque funciona, pero tiene tres grietas:

  • Duplicación: el mismo bloque metadata.labels, spec.replicas o image: se repite en cada archivo y en cada entorno.
  • Sin versionado de despliegues: ¿qué YAML se aplicó hace dos semanas? No hay historial de "este deploy era la v3".
  • Sin rollback: si el despliegue rompe, hay que reconstruir el YAML anterior a mano.

Helm: el gestor de paquetes de Kubernetes

Helm empaqueta todos los manifiestos de una aplicación (y su configuración) en una unidad reutilizable llamada chart, que puedes instalar, actualizar, versionar y compartir. La analogía exacta:

Analogía: si apt o brew son gestores de paquetes para el sistema operativo, Helm es el gestor de paquetes de tu clúster. En vez de instalar "programas", instalas aplicaciones completas de Kubernetes con todas sus piezas.

Conceptos clave: chart, values y release

ConceptoQué esAnalogía
ChartPaquete de archivos que define una aplicación: plantillas, metadatos y valores por defectoLa "receta" de cocina
ValuesConfiguración que se inyecta en las plantillas (imagen, réplicas, hosts…)Los ingredientes elegidos
ReleaseUna instancia concreta de un chart instalada en el clústerEl plato ya cocinado en tu mesa
Repo de chartsServidor HTTP con charts empaquetados (Artifact Hub, Bitnami…)La estantería de libros de recetas

Puedes instalar el mismo chart dos veces con nombres de release distintos y tendrás dos aplicaciones independientes en el mismo clúster. Esto es clave para entornos: harbortasks-dev y harbortasks-prod.

La estructura de un chart

harbortasks/ ├── Chart.yaml # metadatos: nombre, versión, apiVersion, dependencies ├── values.yaml # valores POR DEFECTO (el usuario puede sobreescribirlos) ├── values-prod.yaml # opcional: overrides por entorno ├── templates/ # plantillas Go que HELM renderiza a YAML final │ ├── _helpers.tpl # funciones reutilizables (nombres, etiquetas) │ ├── deployment.yaml # {{ .Values.replicas }} se sustituye al instalar │ ├── service.yaml │ ├── configmap.yaml │ └── NOTES.txt # mensaje que se muestra tras el install └── charts/ # sub-charts (dependencias de terceros)

Esto es un motor de plantillas: los archivos de templates/ no son YAML válido todavía, son plantillas con directivas Go entre {{ … }} que Helm sustituye por los values en el momento de instalar. El flujo de renderizado:

┌────────────┐ ┌───────────────┐ ┌──────────────┐ ┌──────────────┐ │ values.yaml │──▶│ templates/ │──▶│ YAML final │──▶│ kubectl │ │ + --set │ │ (Go template)│ │ renderizado │ │ apply (API) │ └────────────┘ └───────────────┘ └──────────────┘ └──────────────┘ overrides ──────────────────────────▶ ▲ (--values, --set) Helm actúa de cliente, igual que kubectl

El ciclo de vida de una release

Helm guarda un historial de revisiones por release (en un Secret dentro del namespace). Cada helm upgrade crea una revisión nueva; cada revisión es un "foto" del estado. Por eso puedes volver atrás:

  • helm install → crea la release (revisión 1).
  • helm upgrade → aplica un cambio (revisión 2, 3, 4…).
  • helm rollback N → revierte a la revisión N.
  • helm uninstall → elimina la release (y por defecto su historial).

Nota: Helm 3.x no necesita tiller (el componente servidor de Helm 2). Hoy Helm es solo un binario cliente que habla directamente con la API de Kubernetes. Menos piezas, menos superficie de ataque.

3 · Ejemplo mínimo

El ejemplo más pequeño posible: crear un chart con el comando oficial y desplegarlo. Primero comprueba que tienes Helm:

# Verifica la versión de Helm (debe ser 3.x)
helm version --short
# Salida esperada: v3.x.x+...

# 1. Helm crea la estructura base de un chart llamado "demo"
helm create demo

# 2. Mira qué archivos ha generado
find demo -type f        # en PowerShell: Get-ChildItem -Recurse demo

Ahora instala el chart tal cual, con sus valores por defecto:

# Instala el chart ./demo con el nombre de release "mi-app"
# El segundo argumento es SIEMPRE el nombre de la release: con él se
# identificará la instancia en helm list, history, upgrade y rollback.
helm install mi-app ./demo

# Lista las releases del clúster
helm list

# Mira qué manifiestos reales ha aplicado Helm sobre Kubernetes
helm get manifest mi-app

# Desinstala (elimina TODO lo que creó esa release)
helm uninstall mi-app

Detalle importante: release ≠ chart. helm install mi-app ./demo significa: "instala una instancia llamada mi-app a partir del chart demo". Si instalas el mismo chart con helm install otra-app ./demo, tienes una segunda aplicación completamente independiente en el clúster.

4 · Ejemplo real

Vamos a ver el patrón real con un trozo del chart de HarborTasks (la lección siguiente lo completa). El values.yaml define valores por defecto para la API:

# values.yaml — configuración por defecto del chart de HarborTasks
# Estos valores se pueden sobreescribir con --set o con un archivo -f
api:
  replicas: 2                # cuántas copias del pod de la API
  image:
    repository: harbortasks-api   # imagen de la API (registro local del curso)
    tag: "1.0.0"                # tag pinneado: reproducibilidad
    pullPolicy: IfNotPresent    # descargar solo si no está local
  config:
    logLevel: "info"            # nivel de log de la API
  service:
    port: 3000                  # puerto del Service ClusterIP

Y la plantilla del Deployment consume esos valores:

# templates/deployment-api.yaml — plantilla Go (no es YAML aún)
# --- separadores: Helm los elimina y genera UN archivo renderizado por template

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "harbortasks.fullname" . }}-api
  labels:
    app.kubernetes.io/name: {{ include "harbortasks.name" . }}
spec:
  replicas: {{ .Values.api.replicas }}              # ← valor inyectado
  selector:
    matchLabels:
      app.kubernetes.io/name: {{ include "harbortasks.name" . }}-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ include "harbortasks.name" . }}-api
    spec:
      containers:
        - name: api
          image: "{{ .Values.api.image.repository }}:{{ .Values.api.image.tag }}"
          env:
            - name: LOG_LEVEL
              value: {{ .Values.api.config.logLevel | quote }}
          ports:
            - containerPort: {{ .Values.api.service.port }}

Ahora, desplegar en dos entornos es una cuestión de valores, no de YAML duplicado:

# Dev: 1 réplica y log a nivel "debug"
helm install harbortasks-dev ./harbortasks \
  --set api.replicas=1 \
  --set api.config.logLevel=debug

# Prod: 4 réplicas, log "info" y host del Ingress, usando un archivo
helm install harbortasks-prod ./harbortasks -f values-prod.yaml

# ¿Algo sale mal en prod tras un cambio? Mira el historial y vuelve atrás
helm history harbortasks-prod          # lista las revisiones
helm rollback harbortasks-prod 3       # revierte a la revisión 3

Nota la diferencia entre los dos mecanismos: --set clave=valor para cambios puntuales desde la terminal y --values archivo.yaml cuando los cambios son muchos (común en CI/CD). Ambos fusionan el values.yaml original con tus overrides.

5 · Buenas prácticas

HazEvitaPor qué
Imperishable: fija el tag de la imagen (1.0.0) Usar latest en el values.yaml latest cambia con cada build: el mismo chart puede desplegar cosas distintas mañana. Recuerda el Módulo 1: las imágenes son inmutables, las etiquetas deben serlo también.
Usar un archivo values-<entorno>.yaml por entorno Editar a mano el chart para cada despliegue El chart es el mismo; la configuración por entorno vive fuera, versionada con Git junto al código.
Pasar por helm lint y helm template antes de instalar Instalar directo un chart sin validar lint detecta problemas de formato y template renderiza el YAML final sin tocarte el clúster: revisas lo que vas a aplicar.
Definir valores con default en las plantillas Asumir que una clave siempre viene rellena {{ default "info" .Values.api.config.logLevel }} hace que el chart funcione aunque el usuario no defina esa clave.
Versionar el chart y sus values en Git Tener el chart solo en un directorio local El chart es código: debe pasar por review, histórico y rollback como cualquier otro artefacto.

6 · Errores habituales

Confundir el nombre del chart y el de la release

# ❌ Instalar sin nombre de release explícito puede dar fallos
# helm install ./harbortasks        # ❌ falta el nombre de la release
# Salida: Error: must either provide a name or specify --generate-name

# ✅ Da un nombre de release siempre
helm install harbortasks ./harbortasks

# ✅ O deja que Helm lo genere
helm install --generate-name ./harbortasks

Omitir el namespace en reinicios del clúster

# ❌ Instalar "a pelo" lo mete en el namespace por defecto
helm install harbortasks ./harbortasks

# ✅ Namespace explícito (y crear el namespace si no existe)
kubectl create namespace harbortasks
helm install harbortasks ./harbortasks --namespace harbortasks --create-namespace

Plantilla que no valida porque falta la clave

# ❌ References directamente una clave que puede no existir
# image: "{{ .Values.api.imageRepository }}:{{ .Values.api.imageTag }}"
# Si el usuario no las define, Helm renderiza con strings vacíos (y un warning)

# ✅ Con default, el chart es robusto
image: "{{ default "harbortasks-api" .Values.api.image.repository }}:{{ default "latest" .Values.api.image.tag }}"

Perder el historial al desinstalar

# ❌ Desinstalar sin necesidad elimina las revisiones y el historial
helm uninstall harbortasks

# ✅ Puedes conservar el historial para poder reinstalar el estado exacto
helm uninstall harbortasks --keep-history

7 · Ejercicio guiado

Objetivo: instalar, actualizar y revertir un chart en tu clúster de kind, entendiendo el historial de revisiones.

  1. Paso 1: crea un chart base y limpia la plantilla de ejemplo: 
    helm create demo
# borra la plantilla del deployment "de juguete" que trae de serie
rm demo/templates/deployment.yaml
rm demo/templates/service.yaml
  2. Paso 2: añade una plantilla de ConfigMap sencilla: 
    # demo/templates/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-config
data:
  saludo: "Hola desde la release {{ .Release.Name }}"
  replicas: {{ .Values.replicaCount | quote }}
  3. Paso 3: instala la release y comprueba el ConfigMap renderizado: 
    helm install mi-app ./demo
kubectl get configmap mi-app-config -o yaml

    Verás el valor de replicaCount y el nombre de release interpolados.

  4. Paso 4: actualiza con --set y observa la nueva revisión: 
    helm upgrade mi-app ./demo --set replicaCount=5
helm history mi-app        # ahora hay 2 revisiones
kubectl get configmap mi-app-config -o yaml   # replicas: "5"
  5. Paso 5: haz rollback a la revisión 1 y verifica: 
    helm rollback mi-app 1
kubectl get configmap mi-app-config -o yaml   # replicas: "2" (valor original)
  6. Paso 6: limpia: 
    helm uninstall mi-app
rm -rf demo

Verificación: cada vez que corras kubectl get configmap… el dato replicas debe coincidir con el valor de la revisión activa. Si helm history muestra una STATUS en failed, has encontrado un caso de error real para practicar el diagnóstico.

8 · Reto

🎯 Dos releases para dos entornos

Con el chart demo del ejercicio, instala dos releases del mismo chart (app-dev y app-prod) en namespaces distintos y haz que cada una tenga un valor de replicaCount diferente usando únicamente --set. Comprueba que los ConfigMaps de ambos coexisten y que cambiar uno no afecta al otro.

Pista: revisa la diferencia entre release name y namespace, y por qué kubectl get configmaps -A te muestra ambos sin conflicto. Recuerda que cada release genera un Secret de historial propio.

9 · Resumen

  • Helm es el gestor de paquetes de Kubernetes: empaqueta manifiestos y configuración en un chart.
  • Un chart es la receta (plantillas + values por defecto); una release es una instancia instalada con su propio nombre e historial.
  • El motor de plantillas (Go templates) convierte templates/ en YAML final inyectando values.
  • Cada helm upgrade crea una revisión; helm rollback N revierte; helm history lista el historial.
  • Se parametriza con --set clave=valor (puntual) o --values archivo (masivo, típico de CI/CD).
  • Sin YAML duplicado: el mismo chart se instala en dev y prod solo cambiando valores.
ComandoQué hace
helm create demoCrea la estructura base de un chart llamado demo
helm install <release> <chart>Instala una instancia (release) del chart
helm upgrade <release> <chart>Actualiza la release y crea una revisión nueva
helm listLista las releases instaladas
helm history <release>Muestra las revisiones de una release
helm rollback <release> NRevierte a la revisión N
helm get manifest <release>Muestra el YAML final que Helm aplicó
helm uninstall <release>Elimina la release (y con --keep-history conserva el historial)
helm --set clave=valor / helm -f file.yamlOverrides de valores puntuales o por archivo

10 · Preguntas frecuentes

¿Helm es obligatorio en Kubernetes?

No. Kubernetes funciona perfectamente con kubectl apply (y de hecho es lo que hiciste en los módulos 6 y 7). Helm brilla cuando el despliegue crece: decenas de recursos, varios entornos, rollback, dependencias. Piénsalo como la diferencia entre instalar un paquete a mano y usar un gestor de paquetes.

¿Cómo se comparte un chart con otras personas o equipos?

Un chart es un directorio que puede empaquetarse (helm package) en un archivo .tgz y publicarse en un repositorio HTTP/HTTPS (GitHub Pages, ChartMuseum, OCI registry…). Después se añade al Helm local con helm repo add y se instala desde ahí, igual que harías con apt install.

¿Qué es exactamente un Secret de release?

Cuando instalas o actualizas, Helm guarda el estado del despliegue en un objeto Secret dentro del namespace de la release. Ahí vive el historial de revisiones que permite helm history y helm rollback. Por eso helm uninstall sin --keep-history borra la capacidad de rollback.

¿Puedo mezclar recursos de Helm con recursos aplicados con kubectl?

Sí pueden coexister, pero es mala idea aplicar (kubectl apply) a un recurso que Helm gestiona: el sello app.kubernetes.io/managed-by: Helm y la anotación de historial se pierden y Helm puede sobrescribir tus cambios en el siguiente upgrade. Regla de oro: cada recurso tiene un solo responsable.

¿Helm 3 necesita un componente en el clúster?

No. Helm 3 eliminó a Tiller (el servidor de Helm 2): hoy Helm es un binario cliente que habla directamente con la API de Kubernetes usando tu kubeconfig. Más simple y más seguro, porque el binario ya no tiene permisos especiales dentro del clúster.
