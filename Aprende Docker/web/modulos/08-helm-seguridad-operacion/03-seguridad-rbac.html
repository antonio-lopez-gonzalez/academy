SecurityContext, no-root y RBAC básico

Módulo 8 · Helm, seguridad y operación ⏱ 30 minutos

1 · Introducción

Hasta aquí has aprendido a desplegar contenedores. Esta lección trata de la otra cara: quién puede ejecutar qué, y con qué permisos, dentro del clúster.

El problema de seguridad número uno es que la mayoría de las imágenes ejecutan como root (UID 0). Un atacante que explote tu API correrá con los mismos privilegios que el proceso: dentro del contenedor, root es todopoderoso. Y un Pod admin comprometido puede gobernar el clúster entero.

Verás tres frentes: hardening del contenedor (SecurityContext: no-root, capabilities, filesystem de solo lectura), mínimo privilegio en el clúster (RBAC con ServiceAccounts, Roles y RoleBindings, y namespaces como límite del blast radius) y acceso a imágenes privadas (imagePullSecrets). Todo aplicado a HarborTasks.

¿Por qué esta lección? Porque el fallo clásico es desplegar bonito y olvidar los permisos: una auditoría tumba antes un contenedor root que un bug de memoria. La seguridad es propiedad del despliegue, no solo del código.

2 · Teoría

Por qué un contenedor no debería correr como root

Un contenedor no es una máquina virtual: comparte el kernel del host (recuerda el Módulo 0). El UID 0 dentro del contenedor es "root" respecto a los namespaces y capabilities, pero sigue siendo un usuario del kernel del host. Los mecanismos de aislamiento (namespaces, seccomp) reducen el daño, pero no lo eliminan: cualquier vulnerabilidad de escalada de privilegios en el kernel convierte a ese "root del contenedor" en un peligro inmediato.

Analogía: dar a tu contenedor UID 0 es como dar al conserje de un edificio la llave maestra de todos los pisos. Funciona, pero cualquier desliz suyo es un desastre para todos. Mejor: cada servicio tiene su propia llave (su propio UID) y solo abre lo suyo.

La jerarquía de defensa en Kubernetes, de adentro hacia afuera:

a) dentro del contenedor 1. imagen sin root → Dockerfile: USER app:app 2. Pod SecurityContext → runAsNonRoot, capabilities 3. políticas → Pod Security Admission b) en el clúster 4. Namespaces → frontera por app/team 5. RBAC → ServiceAccount + RoleBinding

SecurityContext: el "permiso de usuario" del Pod

Es la sección del manifiesto que configura el contexto de seguridad de un Pod o de un contenedor. Se puede declarar a nivel de spec.securityContext (todo el Pod) o en cada containers[].securityContext (solo ese contenedor). Los campos clave:

CampoQué hacePor qué importa
runAsNonRoot: trueProhíbe arrancar con UID 0El kubelet rechaza el Pod si la imagen intenta correr como root
runAsUser: 10001Fuerza el UID del procesoDeterminismo: da igual lo que diga la imagen, corre con un UID no privilegiado
runAsGroup: 10001Fuerza el GIDEvita escrituras accidentales en archivos de otros grupos
readOnlyRootFilesystem: trueSistema de archivos raíz de solo lecturaUn atacante no puede escribir binarios o scripts en la imagen en ejecución
capabilities.drop: [ALL]Elimina todas las capabilities POSIXRoot tiene ~37 capabilities; las aplicaciones web necesitan poquísimas
allowPrivilegeEscalation: falseProhíbe subir privilegios tras arrancarBloquea técnicas como setuid que escalarían tras un exploit

USER no-root en el Dockerfile: la capa 1

El securityContext protege el despliegue, pero la imagen debe ser compatible. Si una imagen Node no tiene usuario no-root, runAsNonRoot: true la hará fallar. Por eso la práctica correcta es doble: crear el usuario en el Dockerfile y reforzarlo en el manifiesto.

# Dockerfile multi-stage de la API (recuerda M1-04): etapa final
FROM node:20-alpine
WORKDIR /app
# Copia solo lo necesario de la etapa builder
COPY --from=builder /app/dist ./dist
COPY package.json ./
RUN npm ci --omit=dev
# 1) usuario no root DENTRO de la imagen:
RUN adduser -D -u 10001 appuser
USER appuser                 # CMD correrá con este usuario
EXPOSE 3000
CMD ["node", "dist/server.js"]

RBAC: quién puede hacer qué en el clúster

RBAC (Role-Based Access Control) decide qué identidad puede ejecutar qué verbos sobre qué recursos. No es del Módulo 6: los pods no hablan con la API por defecto... o sí: recuerda que un pod puede hablar con kube-apiserver. RBAC controla ese acceso. Cuatro piezas:

  • ServiceAccount: la "identidad" de un Pod frente a la API. Cada namespace tiene una por defecto (default), y todo Pod corre con alguna.
  • Role: reglas de permisos dentro de un namespace (p. ej. "puede hacer get/list en pods").
  • ClusterRole: lo mismo pero en todo el clúster (o por namespace para recursos no-namespaced como Nodes).
  • RoleBinding / ClusterRoleBinding: el "puente" que concede ese Role a un sujeto (usuario o ServiceAccount).
+----------+ +--------+ +-----------+ │ Service │ │ Role │ │ RoleBinding│ │Account A │ ─────▶│(pods, │ ◀─────│ (conecta │ +----------+ grant│ get, │ │ SA A con │ │ list) │ │ Role) │ +--------+ +-----------+ ¿Puede el Pod de la API listar pods? → Solo si su SA tiene un binding a un Role que lo permita. → deny by default.

El modelo es deny by default: si no hay binding, no hay permiso. La regla de oro profesional: cuanto menos pueda hacer la ServiceAccount de una app, más segura está.

Namespaces: el límite del blast radius

Un namespace es una frontera lógica (no de seguridad del kernel, pero organizativa): confina recursos, ServiceAccounts, quotas y políticas. Si HarborTasks vive en su propio namespace harbortasks, sus problemas no contaminan al resto de la organización. Es la primera línea para limitar el alcance de un incidente.

imagePullSecrets: imágenes privadas

Cuando la imagen no es pública, el kubelet necesita credenciales para descargarla. Se guardan en un Secret de tipo kubernetes.io/dockerconfigjson (que se referencia desde el Dockerfile de M1-05) y el Pod lo declara con imagePullSecrets: el kubelet usa esas credenciales al hacer pull.

3 · Ejemplo mínimo

El manifiesto más pequeño posible de un Pod endurecido:

# pod-seguro.yaml — un Pod con SecurityContext básico
apiVersion: v1
kind: Pod
metadata:
  name: pod-seguro
spec:
  securityContext:              # aplica a TODOS los contenedores del Pod
    runAsNonRoot: true          # rechazado si la imagen intenta ser root
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001              # grupo para los volúmenes montados
  containers:
    - name: app
      image: node:20-alpine
      command: ["node", "-e", "console.log('uid:', process.getuid())"]
      securityContext:          # contexto SOLO de este contenedor
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]         # elimina eslint capabilities del contenedor
kubectl apply -f pod-seguro.yaml
kubectl logs pod-seguro       # debe imprimir: uid: 10001
kubectl exec pod-seguro -- whoami   # "whoami" no existe en alpine; fíjate
                                    # que sin capabilities el escaneo es mínimo

4 · Ejemplo real

Reforzar los despliegues de HarborTasks. Primero el SecurityContext del Deployment de la API (nivel que ya viste; ahora con el endurecimiento):

# deployment-api-hardened.yaml — extiende el deployment del Módulo 9
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: harbortasks
  labels:
    app.kubernetes.io/name: api
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: api
    spec:
      securityContext:                # todo el Pod
        runAsNonRoot: true            # la imagen ya usa USER appuser
        runAsUser: 10001
        runAsGroup: 10001
        fsGroup: 10001                # los volúmenes montan con GID 10001
      containers:
        - name: api
          image: harbortasks-api:1.0.0
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true   # la API solo necesita escribir en tmpfs
            capabilities:
              drop: ["ALL"]                # mínimo absoluto
          # La API escribe logs/temp en /tmp → monta un emptyDir con memoria
          volumeMounts:
            - name: tmp
              mountPath: /tmp
          volumes:
            - name: tmp
              emptyDir: {}
          envFrom:
            - configMapRef:
                name: harbor-config
            - secretRef:
                name: harbor-secrets

La web (nginx) es un caso clásico: nginx escribe en /var/cache/nginx y en /var/run. Con readOnlyRootFilesystem: true hay que montar esos directorios como emptyDir:

# deployment-web-hardened.yaml — extracto del contenedor web
          securityContext:
            runAsNonRoot: true
            runAsUser: 101          # el usuario no-root estándar de nginx
            capabilities:
              drop: ["ALL"]
              add: ["NET_BIND_SERVICE"]  # nginx necesita abrir el puerto 80
            readOnlyRootFilesystem: true
          volumeMounts:
            - name: nginx-cache
              mountPath: /var/cache/nginx
            - name: nginx-run
              mountPath: /var/run
          volumes:
            - name: nginx-cache
              emptyDir: {}
            - name: nginx-run
              emptyDir: {}

ServiceAccount, Role y RoleBinding para la API

Si la API tiene que preguntar a la API de Kubernetes (leer pods para mostrar estado), usa mínimo privilegio:

# rbac.yaml — ServiceAccount + Role + RoleBinding (todo en harbortasks)
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api-sa
  namespace: harbortasks
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: api-reader
  namespace: harbortasks
rules:
  # SOLO lectura de pods en ESTE namespace: nada de secrets ni de otros
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: api-reader-binding
  namespace: harbortasks
subjects:
  - kind: ServiceAccount
    name: api-sa
    namespace: harbortasks
roleRef:
  kind: Role
  name: api-reader
  apiGroup: rbac.authorization.k8s.io
# El Deployment debe declarar su ServiceAccount: sin esto usaría "default"
spec:
  template:
    spec:
      serviceAccountName: api-sa   # el Pod corre con la identidad api-sa

imagePullSecrets para imágenes privadas

# Criar el Secret de pull desde las credenciales de GHCR (M1-05)
kubectl create secret docker-registry ghcr-pull \

5 · Buenas prácticas

HazEvitaPor qué
Usuario no-root en el Dockerfile y runAsNonRoot en el manifiesto Confiar solo en uno de los dos El Dockerfile dota a la imagen; el SecurityContext garantiza el endurecimiento en el clúster, incluso si alguien cambia la imagen.
capabilities.drop: [ALL] + añadir solo lo imprescindible Correr con capabilities de serie de la imagen Principio de mínimo privilegio: menos capabilities = menos superficie para escalar tras un exploit.
Hawking readOnlyRootFilesystem y montar empties para escritura Confiar en que "no necesito escribir" sin montar nada Los procesos escriben en temp/cache aunque no lo planees; con RO + emptyDir controlas exactamente qué se puede escribir y dónde.
Una ServiceAccount dedicada por aplicación, con Role mínimo y binding por namespace Correr todo con la ServiceAccount default o con permisos de admin default es la identidad compartida por todos los pods sin configurar; si algo la usa, el riesgo se multiplica.
Usar namespaces por equipo/aplicación Todo en el namespace default El namespace limita el blast radius y hace los quotas y políticas aplicables por frontera.
Uso de imagePullSecrets y pullSecrets rotados Imágenes privadas sin credenciales o tokens hardcodeados La credencial vive en un Secret, no en el YAML; rotarla es recrearla y volver a referenciarla.

6 · Errores habituales

Imagen root con runAsNonRoot en el manifiesto

# ❌ El Pod dice runAsNonRoot pero la imagen arranca como root
# spec:
#   securityContext:
#     runAsNonRoot: true          # ¡y la imagen no tiene USER!
# Resultado: CreateContainerConfigError / "container has runAsNonRoot and
# image has non-numeric user (root)"

# ✅ Dos opciones: o arreglas la imagen (USER en el Dockerfile)
FROM node:20-alpine
RUN adduser -D -u 10001 appuser
USER appuser
# ✅ o al menos fuerzas el UID explícito:
#     runAsUser: 10001

Dejar writable el filesystem raíz "por si acaso"

# ❌ Omitir readOnlyRootFilesystem → la imagen raíz es escribible
# spec:
#   securityContext:
#     readOnlyRootFilesystem: false    # por defecto es false

# ✅ Y montar lo necesario como emptyDir (mínimo privilegio)
#  securityContext:
#    readOnlyRootFilesystem: true
#  volumes:
#    - name: tmp
#      emptyDir: {}

Conceder permisos de más "por comodidad"

# ❌ Role con * en recursos y * en verbs: cualquiera con esa SA puede TODO
# rules:
#   - apiGroups: ["*"]
#     resources: ["*"]
#     verbs: ["*"]

# ✅ Mínimo expresado de forma explícita
rules:
  - apiGroups: [""]            # grup núcleo (pods, services...)
    resources: ["pods"]
    verbs: ["get", "list", "watch"]

Subir de un vistazo "sudo"-minded dentro del clúster

# ❌ dar ClusterRole cluster-admin a un servicio para "que funcione"
kubectl create clusterrolebinding api-admin \
  --clusterrole=cluster-admin \
  --serviceaccount=harbortasks:api-sa

# ✅ Y la forma correcta: el Role más pequeño que cumpla la función
kubectl create role api-reader -n harbortasks \
  --verb=get,list,watch --resource=pods
kubectl create rolebinding api-reader -n harbortasks \
  --role=api-reader --serviceaccount=harbortasks:api-sa

7 · Ejercicio guiado

Objetivo: desplegar un pod endurecido en tu clúster de kind y verificar los efectos de la seguridad.

  1. Paso 1: verifica que el clúster está activo: kubectl get nodes.
  2. Paso 2: crea el namespace y el Pod del ejemplo mínimo: 
    kubectl create namespace seglab
kubectl apply -f pod-seguro.yaml -n seglab
  3. Paso 3: comprueba el UID real: 
    kubectl logs pod-seguro -n seglab        # imprime "uid: 10001"
kubectl exec pod-seguro -n seglab -- id   # uid=10001 gid=10001 groups=10001
  4. Paso 4 (verificación crítica): intenta escribir en la raíz: 
    kubectl exec pod-seguro -n seglab -- sh -c "echo hola > /root.txt"
# ❌ debe fallar: read-only file system (gracias a readOnlyRootFilesystem)
  5. Paso 5: replica la comprobación con el Pod sin endurecer: 
    kubectl run pod-inseguro --image=node:20-alpine \
  --restart=Never --command -- node -e "console.log(getuid())" -n seglab
kubectl logs pod-inseguro -n seglab      # imprime "uid: 0" — root!
  6. Paso 6: limpia el laboratorio: 
    kubectl delete namespace seglab
kubectl delete -f pod-seguro.yaml

Observa: con el mismo Dockerfile (node:20-alpine), el mismo comando y la única diferencia siendo el securityContext, un Pod arranca como uid: 0 y otro como uid: 10001. La seguridad no cambia el código: protege el despliegue.

8 · Reto

🎯 Un Pod de solo lectura que sí funciona

La web de HarborTasks (nginx) falla si montas readOnlyRootFilesystem: true sin ajustes. Tu reto: desplegar un Pod con nginx harbortasks-web:1.0.0 que cumpla TODO a la vez: runAsNonRoot + drop: [ALL] + NET_BIND_SERVICE + filesystem raíz de solo lectura, y que responda HTTP. El vector: averiguar qué monta nginx para cache/temp (pista en el ejemplo real de esta lección).

Pista: monta /var/cache/nginx y /var/run como emptyDir; revisa el log de nginx con kubectl logs si algo falla — te dirá exactamente qué directorio necesita escritura.

9 · Resumen

  • Contenedor root = peligro: comparte kernel con el host; mínimo privilegio por capas.
  • SecurityContext declara runAsNonRoot, runAsUser, readOnlyRootFilesystem, capabilities y allowPrivilegeEscalation.
  • USER appuser en el Dockerfile dota la imagen; el manifiesto garantiza el endurecimiento.
  • RBAC: ServiceAccount (¿quién es), Role/ClusterRole (¿qué puede), RoleBinding/ClusterRoleBinding (¿cómo se conectan). Deny by default.
  • Namespaces limitan el blast radius de un incidente y aíslan equipos.
  • imagePullSecrets dan el pull de imágenes privadas (type dockerconfigjson).
  • Aplicación a HarborTasks: API con drop: [ALL], web con NET_BIND_SERVICE y empties, SA api-sa con Role de solo lectura.

10 · Preguntas frecuentes

¿Un contenedor con UID no-root es 100% seguro?

Nada es 100% seguro. No-root reduce de forma drástica la superficie: limita capabilities, evita escribir en el filesystem raíz y corta la escalada setuid. Pero la seguridad total exige más capas: imágenes escaneadas, seccomp/AppArmor, network policies y RBAC mínimo. El SecurityContext es la base, no la meta.

¿Qué es una capability de Linux y por qué nginx necesita NET_BIND_SERVICE?

Las capabilities dividen los privilegios de root en piezas independientes. NET_BIND_SERVICE permite abrir puertos por debajo de 1024 (como el 80). Al hacer drop: [ALL] quitas todo y luego add reincorpora la mínima capacidad que tu proceso necesita.

¿Por qué no versionar credenciales en valores o en el YAML?

Porque un repo es un documento de acceso compartido: la credencial que versionas queda en el historial de Git para siempre aunque la borres. Las credenciales van en el gestionador de secretos (CI/CD, Vault, SealedSecrets) y se inyectan en el Secret en tiempo de despliegue.

¿ServiceAccount y RBAC son lo mismo?

No. La ServiceAccount es la identidad (quiénes somos); el Role/RoleBinding define los permisos (qué podemos hacer). Para que una identidad haga algo, necesita un Role y el binding que los conecta. Sin binding, la SA no puede hacer nada — deny by default.

¿Cuándo uso ClusterRole en lugar de Role?

Cuando el permiso debe aplicarse en todo el clúster (p. ej. un operador que gestiona recursos en todos los namespaces, o acceso a recursos sin namespace como Nodes). Para el caso típico de una aplicación que vive en un namespace, un Role + RoleBinding es lo correcto.
