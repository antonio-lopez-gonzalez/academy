Chart de HarborTasks

Módulo 8 · Helm, seguridad y operación ⏱ 35 minutos

1 · Introducción

En la lección anterior viste la mecánica de Helm con un chart de juguete. Ahora toca empaquetar el stack completo de HarborTasks — web (nginx), API (Node/Express) y postgres (PostgreSQL) — en un único chart reutilizable con sus Deployments, Services, ConfigMap, Secret, PVC e Ingress: el mismo despliegue de los módulos 6 y 7, pero parametrizado y reproducible.

El porqué: un chart no es "otra forma de escribir YAML": es la diferencia entre un despliegue manual y uno repetible. Con un chart, crear HarborTasks en un clúster nuevo es un solo comando; cambiar la imagen o escalar es cambiar un valor.

2 · Teoría

El árbol del chart harbortasks

proyectos/harbortasks/helm/harbortasks/ ├── Chart.yaml # metadatos, versiones, deps ├── values.yaml # defaults: imágenes, réplicas, hosts… ├── values-prod.yaml # overrides por entorno (opcional) ├── .helmignore └── templates/ ├── _helpers.tpl # helpers reutilizables (name, fullname, labels) ├── NOTES.txt # mensaje post-install ├── deployment-api.yaml ├── deployment-web.yaml ├── deployment-postgres.yaml ├── service-{api,web,postgres}.yaml ├── configmap.yaml ├── secret.yaml ├── postgres-pvc.yaml ├── postgres-configmap.yaml └── ingress.yaml

Tres decisiones de diseño que se repiten en cualquier chart profesional:

  • Un archivo por recurso. Facilita revisar con Git y que helm template genere nombres legibles.
  • Toda la configuración vive en values.yaml. Las plantillas no contienen datos, solo lógica: si algo cambia según entorno, debe ser un valor.
  • Los helpers centralizan nombres y etiquetas. El selector/matchLabel debe coincidir; un solo helper evita typos que rompen el Service.

Las directivas de plantilla que vas a usar

# Incluir un helper dentro de otra plantilla:
#   {{ include "harbortasks.fullname" . }}
# El "." (contexto raíz) se pasa SIEMPRE: el helper necesita .Release/.Values.

# Control dentro de las plantillas (el guion recorta el whitespace):
{{- if .Values.postgres.enabled }}
  ...lo que se renderiza si está habilitado...
{{- end }}

Tres detalles de sintaxis que confunden al principio:

  • {{ .Release.Name }} inyecta el nombre de la release (recuerda: dos instancias del mismo chart pueden coexistir).
  • {{ include "x" . | nindent 4 }} mete el resultado del helper indentado 4 espacios para que anide bien en YAML.
  • {{- … -}} recorta el salto de línea adyacente: elimina líneas blancas del renderizado.

El flujo de validación: lint → template → install

helm lint ✓ helm template ✓ helm install ────────────────▸───────────────────▸──────────────────────────────── valida el chart, renderiza TODOS los aplica sobre el clúster sus archivos y la YAML finales (sin y crea la release sintaxis Go tocar el clúster) ─────────────────────────────────────────────────────────────────── puedes hacer esto las veces que quieras, sin riesgo

3 · Ejemplo mínimo

El ciclo de validación más pequeño posible con el chart recién esqueleado. Primero, Chart.yaml:

# Chart.yaml — metadatos del chart (Helm 3 usa apiVersion v2)
apiVersion: v2
name: harbortasks          # nombre corto: se usa en helpers y nombres
description: Gestor de tareas HarborTasks: web + api + postgres
type: application          # "library" sería solo para helpers reutilizables
version: 0.1.0             # versión del CHART (la cambias tú al evolucionar)
appVersion: "1.0.0"        # versión de la aplicación que despliega

Con solo esto ya puedes validar la sintaxis del esqueleto:

# 1. Valida estructura y YAML sin desplegar nada
helm lint ./harbortasks

# 2. Renderiza todo el chart a YAML final y muéstralo
helm template ./harbortasks

# 3. Renderiza Y con la salida puedes guardarla para revisarla/versionarla
helm template ./harbortasks > rendered.yaml   # PowerShell: out-file rendered.yaml

helm template es la herramienta de ensayo general: renderiza exactamente lo que Helm aplicaría, pero sin hablar con el clúster. Si tu plantilla tiene un error de sintaxis, te lo dice aquí — antes de romper nada.

4 · Ejemplo real

El chart completo. Empezamos por los values (toda la configuración del stack en un solo lugar):

# values.yaml — configuración por defecto del chart de HarborTasks
# Override en prod con values-prod.yaml o con --set en CI/CD.

api:                    # imágenes/replicas (M1: tags inmutables, no latest)
  replicas: 2
  image:
    repository: harbortasks-api
    tag: "1.0.0"
    pullPolicy: IfNotPresent
  service:
    port: 3000
  resources:
    requests: { cpu: 100m, memory: 128Mi }
    limits:   { cpu: 500m, memory: 256Mi }

web:
  replicas: 1
  image:
    repository: harbortasks-web
    tag: "1.0.0"
    pullPolicy: IfNotPresent
  service:
    port: 80

postgres:
  enabled: true            # flag para apagar postgres en dev
  image:
    repository: postgres
    tag: "16-alpine"
  service:
    port: 5432
  persistence:
    enabled: true
    size: 1Gi
  resources:
    requests: { cpu: 100m, memory: 256Mi }
    limits:   { cpu: 500m, memory: 512Mi }

secrets:                  # en un chart real llegan del CI/CD, no de Git
  postgresPassword: "harborpass"
  databaseUrl: "postgres://harbor:harborpass@postgres:5432/harbortasks"

config:                   # config común de web y api
  logLevel: "info"
  apiUrl: "/api"

ingress:                  # puerta de entrada (lección M7-04)
  enabled: true
  host: harbor.test
  className: nginx

nameOverride: ""          # helpers: sobreescrituras opcionales
fullnameOverride: ""

Ahora los helpers, la única fuente de verdad para nombres y etiquetas:

# _helpers.tpl — una única fuente de verdad para nombres y etiquetas
{{- define "harbortasks.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}

{{- define "harbortasks.fullname" -}}
# release + nombre: dos releases del mismo chart no chocan
{{- if .Values.fullnameOverride }}
{{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- $name := default .Chart.Name .Values.nameOverride }}
{{- if contains $name .Release.Name }}
{{- .Release.Name | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- printf "%s-%s" .Release.Name $name | trunc 63 | trimSuffix "-" }}
{{- end }}
{{- end }}
{{- end }}

{{- define "harbortasks.labels" -}}
# etiquetas estándar (convención app.kubernetes.io) para todos los recursos
app.kubernetes.io/name: {{ include "harbortasks.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/version: {{ .Chart.AppVersion | default .Chart.Version }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end }}

Deployment de la API: valores, helpers y variables

# templates/deployment-api.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "harbortasks.fullname" . }}-api
  labels:
    {{- include "harbortasks.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.api.replicas }}      # → 2 por defecto
  selector:
    matchLabels:
      app.kubernetes.io/name: {{ include "harbortasks.name" . }}-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ include "harbortasks.name" . }}-api
    spec:
      containers:
        - name: api
          image: "{{ .Values.api.image.repository }}:{{ .Values.api.image.tag }}"
          imagePullPolicy: {{ .Values.api.image.pullPolicy }}
          ports:
            - containerPort: {{ .Values.api.service.port }}
          env:
            - name: LOG_LEVEL          # no secreto → ConfigMap
              valueFrom:
                configMapKeyRef:
                  name: {{ include "harbortasks.fullname" . }}-config
                  key: LOG_LEVEL
            - name: DATABASE_URL       # secreto → Secret
              valueFrom:
                secretKeyRef:
                  name: {{ include "harbortasks.fullname" . }}-secret
                  key: database-url
          resources:
            limits:
              cpu: {{ .Values.api.resources.limits.cpu }}
              memory: {{ .Values.api.resources.limits.memory }}
            requests: {{- toYaml .Values.api.resources.requests | nindent 14 }}

La web (nginx) espeja el patrón de la API (hardening al detalle en la lección 3):

# templates/deployment-web.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "harbortasks.fullname" . }}-web
  labels:
    {{- include "harbortasks.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.web.replicas }}
  selector:
    matchLabels:
      app.kubernetes.io/name: {{ include "harbortasks.name" . }}-web
  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ include "harbortasks.name" . }}-web
    spec:
      securityContext:          # runAsNonRoot + UID no privilegiado (lección 3)
        runAsNonRoot: true
        runAsUser: 101
      containers:
        - name: web
          image: "{{ .Values.web.image.repository }}:{{ .Values.web.image.tag }}"
          ports:
            - containerPort: {{ .Values.web.service.port }}

Service y Secret: Modelos de plantilla con Release.Name

# templates/service-postgres.yaml — los otros services siguen el mismo patrón
apiVersion: v1
kind: Service
metadata:
  name: {{ include "harbortasks.fullname" . }}-postgres   # hostname interno
spec:
  selector:
    app.kubernetes.io/name: {{ include "harbortasks.name" . }}-postgres
  ports:
    - port: {{ .Values.postgres.service.port }}
      targetPort: 5432
# templates/secret.yaml — credenciales del stack
apiVersion: v1
kind: Secret
metadata:
  name: {{ include "harbortasks.fullname" . }}-secret
type: Opaque
data:
  # b64enc codifica; el valor real viene del CI/CD, no del values.yaml
  database-url: {{ .Values.secrets.databaseUrl | b64enc | quote }}
  postgres-password: {{ .Values.secrets.postgresPassword | b64enc | quote }}

PVC, ConfigMap e Ingress

# templates/postgres-pvc.yaml — si postgres está deshabilitado no se crea el PVC
{{- if and .Values.postgres.enabled .Values.postgres.persistence.enabled }}
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: {{ include "harbortasks.fullname" . }}-postgres-data
spec:
  accessModes:
    - ReadWriteOnce      # un solo nodo escribe a la vez (suficiente aquí)
  resources:
    requests:
      storage: {{ .Values.postgres.persistence.size | quote }}
{{- end }}
# templates/configmap.yaml — configuración compartida
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ include "harbortasks.fullname" . }}-config
data:
  LOG_LEVEL: {{ .Values.config.logLevel | quote }}
  API_URL: {{ .Values.config.apiUrl | quote }}
  # El host de postgres es el nombre del Service (DNS interno de K8s)
  POSTGRES_HOST: {{ include "harbortasks.fullname" . }}-postgres
# templates/ingress.yaml — puerta de entrada única
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ include "harbortasks.fullname" . }}-ingress
spec:
  ingressClassName: {{ .Values.ingress.className }}
  rules:
    - host: {{ .Values.ingress.host | quote }}
      http:
        paths:
          - path: /api(/|$)(.*)     # regex: todo lo que empiece por /api
            pathType: ImplementationSpecific
            backend:
              service:
                name: {{ include "harbortasks.fullname" . }}-api
                port:
                  number: {{ .Values.api.service.port }}
          - path: /                 # el resto va a la web (nginx)
            pathType: Prefix
            backend:
              service:
                name: {{ include "harbortasks.fullname" . }}-web
                port:
                  number: {{ .Values.web.service.port }}
{{- end }}

Con el chart completo, el despliegue queda en dos comandos:

# Valida y renderiza ANTES de tocar el clúster
helm lint ./harbortasks
helm template ./harbortasks | less

# Instala el stack en su namespace (kind)
kubectl create namespace harbortasks
helm install harbortasks ./harbortasks --namespace harbortasks

# Verifica: 3 deployments con sus pods en Running
kubectl -n harbortasks get pods

5 · Buenas prácticas

HazEvitaPor qué
Mantener los nombres derivados de helpers {{ .Release.Name }}-postgres a mano en cada plantilla Un solo cambio en _helpers.tpl actualiza todos los recursos y sus referencias cruzadas (Service → Deployment → ConfigMap refs).
Usar nindent para bloques anidados Interpolar un bloque multilínea a nivel de columna 0 {{- toYaml .Values.x | nindent 6 }} inserta YAML ya indentado; si no, el renderizado es YAML roto que lint no siempre detecta.
Versionar tags y valores por entorno :latest y edits directos en el clúster Reproducibilidad: el chart + sus values en Git deberían poder recrear el clúster de cero.
Separar Secret de ConfigMap Meter contraseñas en el ConfigMap Los ConfigMaps son legibles por cualquiera con acceso; los Secrets, aunque solo codifican en base64 (no cifran), se gestionan de forma separada y pueden cifrarse con SOPS/SealedSecrets.
Ejecutar lint + template en CI antes de instalar Instalar directo con helm install El ciclo falla barato: el CI valida antes de tocar un clúster compartido. El coste de un error en YAML es un despliegue roto.

6 · Errores habituales

Selector y etiquetas que no coinciden

# ❌ El selector del Service no coincide con las labels del pod
# spec.selector: { app: web }
#  template.metadata.labels: { app.kubernetes.io/name: harbortasks-web }
# Resultado: el Service no encuentra pods → sin endpoints → timeout

# ✅ La misma etiqueta en selector y en la plantilla del pod
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: {{ include "harbortasks.name" . }}-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ include "harbortasks.name" . }}-api

Olvidar el contexto en include

# ❌ include sin el contexto "." — .Release no existe dentro del helper
# name: {{ include "harbortasks.fullname" }}     ← Error: nil pointer

# ✅ El parámetro que espera la función es el contexto raíz
name: {{ include "harbortasks.fullname" . }}

No vigilar el whitespace en los condicionales

# ❌ {{ if ... }} sin guion deja líneas en blanco que rompen el YAML
# ✅ Siempre {{- if ... }} y {{- end }} en plantillas YAML
{{- if .Values.ingress.enabled }}
# ... el bloque ...
{{- end }}

Dar por hecho que Helm cifra los Secrets

# ❌ Creer que values con contraseñas son seguros en Git
# El base64 NO es cifrado: kubectl get secret -o yaml lo muestra en claro

# ✅ No versionar secretos reales; inyectarlos desde CI/CD
helm install harbortasks ./harbortasks \
  --set secrets.postgresPassword="$PG_PASSWORD" \
  --set secrets.databaseUrl="$DATABASE_URL"

7 · Ejercicio guiado

Objetivo: montar el esqueleto del chart de HarborTasks y validar el renderizado de la API durante el proceso.

  1. Paso 1: crea la base del chart y elimina los ejemplos de serie: 
    mkdir -p proyectos/harbortasks/helm
helm create proyectos/harbortasks/helm/harbortasks
rm -f proyectos/harbortasks/helm/harbortasks/templates/{deployment,service,hpa,serviceaccount}.yaml
rm -f proyectos/harbortasks/helm/harbortasks/templates/tests/test-connection.yaml
  2. Paso 2: edita Chart.yaml con name: harbortasks, description y appVersion: "1.0.0".
  3. Paso 3: sustituye los helpers generados por los tres de esta lección (name, fullname, labels).
  4. Paso 4: añade la plantilla templates/deployment-api.yaml del ejemplo real. Valida en cada paso: 
    helm lint proyectos/harbortasks/helm/harbortasks
helm template proyectos/harbortasks/helm/harbortasks | grep -A 30 "kind: Deployment"
  5. Paso 5: comprueba que el nombre incluye la release (por defecto release-name-harbortasks-api) y que las etiquetas tienen el bloque completo: 
    helm template --release-name demo proyectos/harbortasks/helm/harbortasks \
  | grep "name:" | head -5
  6. Paso 6 (verificación final): renderiza y confirma que el valor de LOG_LEVEL viene del ConfigMap y el de DATABASE_URL del Secret: 
    helm template proyectos/harbortasks/helm/harbortasks \
  | grep -E "configMapKeyRef|secretKeyRef" -A 3

8 · Reto

🎯 Un chart, dos escenarios

Haz que el chart soporte un modo "dev" sin postgres: cuando postgres.enabled: false no se deben generar el Deployment, el Service, el PVC ni el Secret de postgres, y el ConfigMap debe apuntar la variable POSTGRES_HOST a un valor configurable (por ejemplo localhost para un dev local). Renderiza con --set postgres.enabled=false y comprueba con kubectl … --dry-run=client que solo aparecen los recursos de api y web.

Pista: usa el mismo patrón condicional que viste en pvc.yaml e ingress.yaml, y recuerda que POSTGRES_HOST es un dato del ConfigMap que depende de un valor.

9 · Resumen

  • El chart de HarborTasks empaqueta web + API + postgres con todos sus recursos en helm/harbortasks/.
  • values.yaml concentra toda la configuración: réplicas, imágenes, servicios, recursos, secretos, PVC e Ingress.
  • _helpers.tpl define los nombres y etiquetas una sola vez (DRY) con include y nindent.
  • El Secret se separa del ConfigMap; las credenciales reales llegan por --set desde CI/CD, nunca versionadas.
  • helm lint y helm template validan y renderizan sin tocar el clúster.
  • helm install harbortasks ./harbortasks --namespace harbortasks despliega el stack completo.
ComandoQué hace
helm lint ./harbortasksValida el chart: estructura, YAML y sintaxis de plantillas
helm template ./harbortasksRenderiza el YAML final sin contacto con el clúster (ensayo general)
helm install harbortasks ./harbortasks -n harbortasksInstala el stack completo en el namespace indicado
helm template --release-name demo …Renderiza usando un nombre de release concreto
helm uninstall harbortasks -n harbortasksElimina la release y todos sus recursos

10 · Preguntas frecuentes

¿Por qué usar el prefijo app.kubernetes.io/… en las etiquetas?

Es la convención de etiquetas recomendada por Kubernetes (el estándar K8s Common Labels). Herramientas como Helm, Prometheus o los dashboards la entienden de inmediato: saben quién creó el recurso, a qué aplicación y a qué release pertenece, sin tener que adivinar tus etiquetas propias.

¿Qué diferencia hay entre la versión del chart y la de la app?

appVersion describe la versión de tu aplicación (por ejemplo 1.0.0); version es la versión del chart (cómo está empaquetada). Cambiarás appVersion en cada release de la app; version lo haces cuando cambias la estructura, los values o las plantillas del propio chart.

¿Puedo desplegar HarborTasks en varios entornos con un solo chart?

Sí, esa es la idea: un chart + un values-<env>.yaml por entorno (+ secretos por CI/CD). En prod subes réplicas y límites; en dev puedes apagar postgres o usar tags de imagen distintos. Todo sin tocar una sola plantilla.

Mi plantilla renderiza feo con líneas en blanco, ¿qué hago?

Es la directiva de whitespace: usa {{- … -}} (guion a la izquierda para recortar el espacio previo, a la derecha para el posterior). Es la causa número uno de "el YAML se ve raro" en Helm. Renderiza con helm template y compara antes y después.

¿Debo versionar los archivos del chart en el propio repo de la app?

Sí, en el mismo repo que la aplicación (monorepo o repo por servicio). Así el chart evoluciona con el código que despliega. Si los charts son compartidos entre muchos equipos, es mejor un repo/chart propio publicado en un registry (lecciones futuras del ecosistema Helm).
