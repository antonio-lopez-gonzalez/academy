Límites de recursos y HPA

Módulo 8 · Helm, seguridad y operación ⏱ 30 minutos

1 · Introducción

Hasta ahora has desplegado pods sin decirle a Kubernetes cuánto necesitan. Funciona… hasta que deja de funcionar: un solo pod que consuma toda la memoria del nodo puede tumbar a todos sus vecinos. En un clúster compartido, los recursos son de todos.

Esta lección tiene dos mitades que se refuerzan:

  • Requests y limits: declarar cuánto reserva tu pod (request) y cuál es su techo (limit). Es la diferencia entre un clúster caótico y uno predecible, y determina la clase de QoS de tu pod.
  • El HorizontalPodAutoscaler (HPA): automatizar cuántas réplicas necesita tu Deployment en función del uso real de CPU/memoria. Escalar a mano con kubectl scale está bien para emergencias; el HPA es para dormir tranquilo.

El porqué: un clúster es un apartamento compartido con un presupuesto de electricidad y agua. Nadie dice "nadie", todos se quedan sin. Requests = tu reserva garantizada; limits = tu tope de consumo. El scheduler decide dónde vive cada pod mirando los requests; el kubelet corta a los que superan sus limits.

2 · Teoría

Requests vs limits: la reserva y el techo

ConceptoQué significaQuién lo usa
requestsLo que el pod garantiza tener (el scheduler lo reserva)El kube-scheduler al colocar pods
limitsEl máximo que el pod puede consumir (techo duro)El kubelet al ejecutar: CPU se limita, memoria con OOMKill si se supera

Analogía: reproducir un concierto en una sala. Request de CPU es el aforo que reservas (la sala te lo garantiza: nadie más usará esas butacas). Limit es el máximo de personas que deja entrar el cuerpo de bomberos. Si los límites del clúster se llenan, el manager te echa (eviction); si tu proceso se pasa de memoria, el kubelet le dispara el "guardián" (OOM kill).

Detalle de comportamiento que marca la diferencia:

  • CPU es comprimible: si un pod supera su limit de CPU, el kubelet lo enfria (throttling). La aplicación va lenta pero sigue viva.
  • Memoria no es comprimible: superar el limit de memoria termina con el proceso OOMKilled (y el cgroup lo mata). Por eso los limits de memoria son decisiones delicadas.

Unidades: millicores y bytes

  • CPU se expresa en millicores: 100m = 0.1 core; 250m = un cuarto de core. 1 = un core completo (o 1000m).
  • Memoria en bytes con sufijos: 128Mi = 128 mebibytes (128 × 1024²); 1Gi = 1 gibibyte. Cuidado con M (decimal) vs Mi (binario): 128M ≈ 122Mi. En Kubernetes, la comunidad usa casi siempre Mi/Gi.

Las clases de QoS: quién sobrevive a una presión de recursos

Kubernetes clasifica cada pod según cómo combines requests y limits. Esta clase decide el orden de expulsión cuando el nodo se queda sin recursos (eviction) y, en parte, dónde elige el scheduler:

Pod con request == limit → QoS: Guaranteed (los últimos en expulsar) Pod con request != limit → QoS: Burstable (siguiente en la cola) Pod sin requests ni limits→ QoS: BestEffort (los primeros en sacrificar)
QoSCómo se lograRiesgo
Guaranteedrequest == limit en CPU y memoria (todos los contenedores)Mínimo: el nodo le reserva todo lo que pide
BurstableHay requests (y a veces limits) pero no coincidenMedio: puede usar extra hasta el limit; expulsado antes que Guaranteed
BestEffortSin requests ni limitsMáximo: primero en morir ante presión

La best-effort no es "gratis": cualquiera con un bug de fuga de memoria convierte el nodo en un casino. Por eso la práctica profesional marca requests siempre (y limits con criterio).

kubectl top y kubectl scale: medir y escalar a mano

# Consumo real por nodo y por pod (requiere el metrics-server instalado)
kubectl top nodes
kubectl top pods -n harbortasks

# Escalado manual: réplicas fijas, sin inteligencia
kubectl scale deployment api -n harbortasks --replicas=4

El HorizontalPodAutoscaler: escalado automático

El HPA es un controlador del plano de control que vigila métricas (memoria y CPU por defecto) y ajusta las réplicas del Deployment para acercarse a un objetivo. El bucle es sencillo:

┌──────────────── control plane ────────────────┐ │ metrics-server ──► HPA controller ──► Deployment │ │ (recoge uso) (calcula réplicas) (ReplicaSet)│ └────────────────────────────────────────────────────┘ │ ▼ fórmula (por ReplicaSet): réplicas_objetivo = ceil( réplicas_actuales × (uso_medio / target) ) ejemplo: 2 réplicas al 85% de CPU, target 70 % → ceil(2 × 85/70) = 3 réplicas → el Deployment escala a 3

Parámetros del HPA: minReplicas, maxReplicas, targetCPUUtilizationPercentage (y, en versiones modernas, behavior para suavizar el escalado con scaleUp/scaleDown). También puede usar métricas personalizadas (p. ej. longitud de la cola de la API o peticiones por segundo) vía el custom metrics API y Prometheus — lo mencionamos porque en producción real se acaba necesitando, pero aquí nos centramos en CPU.

3 · Ejemplo mínimo

Un pod con requests y limits bien declarados:

# pod-limites.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-con-limites
spec:
  containers:
    - name: app
      image: node:20-alpine
      # El proceso que va a consumir
      command: ["node", "-e", "setInterval(()=>{},1000)"]
      resources:
        requests:            # reserva garantizada
          cpu: "100m"        # 0.1 core
          memory: "128Mi"    # 128 mebibytes
        limits:              # techo duro
          cpu: "500m"        # 0.5 core (más de eso: throttling)
          memory: "256Mi"    # más de eso: OOMKilled por el kubelet
kubectl apply -f pod-limites.yaml
# Comprueba la clase QoS que Kubernetes le asignó
kubectl get pod pod-con-limites -o jsonpath='{.status.qosClass}'
# Salida: Burstable   (porque request != limit)

# Consumo real del pod (con metrics-server instalado)
kubectl top pod pod-con-limites
# NAME               CPU(cores)   MEMORY(bytes)
# pod-con-limites    8m           12Mi

4 · Ejemplo real

Aplicado a HarborTasks. Primero, declaramos recursos en el Deployment de la API (la pieza que más varía de carga):

# deployment-api.yaml — extracto con recursos
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: api
  template:
    spec:
      containers:
        - name: api
          image: harbortasks-api:1.0.0
          resources:
            # Reserva mínima para arrancar sin hambre
            requests:
              cpu: "100m"
              memory: "128Mi"
            # Techo: la API respira hasta 500m y 256Mi
            limits:
              cpu: "500m"
              memory: "256Mi"

Ahora el HPA de la API, el protagonista de la lección:

# hpa-api.yaml — HorizontalPodAutoscaler de la API
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
  namespace: harbortasks
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api           # el Deployment al que escala
  minReplicas: 2        # nunca por debajo de 2 (mantiene HA básica)
  maxReplicas: 6        # nunca por encima de 6 (no romper el presupuesto)
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # intenta mantener ~70% de CPU media
  behavior:                        # opcional: suaviza el escalado
    scaleDown:
      stabilizationWindowSeconds: 120   # espera 2 min antes de bajar
      policies:
        - type: Percent
          value: 50                      # baja como mucho un 50% por tick
kubectl apply -f deployment-api.yaml -n harbortasks
kubectl apply -f hpa-api.yaml -n harbortasks

# Estado del HPA: réplicas actuales, target y uso medio
kubectl get hpa api -n harbortasks
# NAME   REFERENCE     TARGETS   MINPODS   MAXPODS   REPLICAS   AGE
# api    Deployment/api 45%/70%   2         6         2          5m

# Escalado manual de emergencia (cuando no hay HPA)
kubectl scale deployment api -n harbortasks --replicas=4

# Historico de eventos del HPA (por qué escaló o no)
kubectl describe hpa api -n harbortasks

Requisito: el HPA necesita el metrics-server en el clúster (de la misma forma que kubectl top). En kind se instala en rutina con un par de comandos; sin él, el HPA reporta <unknown> y no escala.

5 · Buenas prácticas

HazEvitaPor qué
Declarar requests siempre Pods sin requests con la esperanza de que sean "gratis" Sin request el pod es BestEffort y el scheduler lo puede colocar donde no le corresponde; además es el primero en morir ante presión.
Poner limits con criterio, midiéndolos primero Limits al azar o límites de memoria demasiado justos Un limit de memoria bajo produce OOMKilled en baches normales. Mide con kubectl top antes de fijar el techo.
Dejar un request y un limit coherentes entre sí request=50m y limit=4 cores (misma aplicación) La brecha enorme crea QoS Burstable poco predecible y permite a un pod "robar" CPU de los vecinos, generando caos.
HPA con behavior y ventana de estabilización HPA sin estabilización que oscila arriba/abajo Sin histéresis, un pico de un minuto provoca un "baile" de scale up/down que degrada el servicio en vez de estabilizarlo.
Combinar HPA con probes y readiness Escalar réplicas que aún no están listas El HPA escala replicas, pero las réplicas solo reciben tráfico cuando pasan readiness (M6-05). Sin probes, escalas "en vacío".

6 · Errores habituales

Confundir la unidad de memoria M vs Mi

# ❌ 128M = 128 x 10^6 bytes (decimal) ≈ 122 Mi, confunde a quien lea
#  memory: "128M"

# ✅ 128Mi = 128 mebibytes, la convención del ecosistema K8s
memory: "128Mi"

Limits de memoria "justos" que matan la app

# ❌ La API usa 140Mi en su pico habitual pero le das un limit de 128Mi
# Resultado: la API en el pico muere por OOM (CrashLoopBackOff)

# ✅ 1. Mide primero con kubectl top   2. decide el techo con margen
kubectl top pods -n harbortasks
# y luego, p. ej., ajustas limits.memory a 256Mi

No instalar metrics-server y esperar top/HPA

# ❌ kubectl top falla en kind recién creado
kubectl top nodes
# Error from server: the server could not find the requested resource

# ✅ Instala metrics-server una vez en kind
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

HPA apuntando al Deployment equivocado o con target imposible

# ❌ targetCPUUtilizationPercentage=0 → "invalid value": no escala
kubectl autoscale deployment web -n harbortasks --cpu-percent=0 --min=1 --max=5

# ✅ target razonable (entre ~50% y 80%) y al Deployment correcto
kubectl autoscale deployment api -n harbortasks \
  --cpu-percent=70 --min=2 --max=6

7 · Ejercicio guiado

Objetivo: crear presión de CPU real sobre la API y ver cómo el HPA escala y luego se relaja, sin tocar el Deployment a mano.

  1. Paso 1: despliega la API con recursos y el HPA (usa los YAML del ejemplo real): 
    kubectl create namespace harbortasks
kubectl apply -f deployment-api.yaml -n harbortasks
kubectl apply -f hpa-api.yaml -n harbortasks
kubectl get hpa api -n harbortasks     # REPLICAS 2, TARGETS ~0%/70%
  2. Paso 2: abre un segundo terminal y sigue el estado: 
    kubectl get hpa api -n harbortasks -w     # watch: ves el cambio en vivo
  3. Paso 3: genera carga con un bucle de peticiones a la API (expuesta por port-forward o por el Ingress): 
    kubectl -n harbortasks port-forward svc/api 3000:3000 &
# en otro terminal:
for i in $(seq 1 300); do curl -s http://localhost:3000/api/tasks > /dev/null; done
  4. Paso 4: observa en el -w cómo el TARGETS sube por encima de 70 y REPLICAS pasa de 2 a 3 o 4.
  5. Paso 5 (verificación): deja de generar carga y, tras la ventana de estabilización, comprueba que las réplicas vuelven a bajar: 
    kubectl get hpa api -n harbortasks
kubectl get pods -n harbortasks -l app.kubernetes.io/name=api
# Comprueba que vuelven a ser 2 (minReplicas)
  6. Paso 6: limpia si no quieres seguir usando el clúster: 
    kubectl delete hpa api -n harbortasks
kubectl delete deployment api -n harbortasks

Verificación clara: la prueba de que el HPA funciona es que tú nunca ejecutaste kubectl scale. Las réplicas subieron por el controlador, no por ti.

8 · Reto

🎯 HPA que también escale por memoria

Extiende el HPA de la API para que además de CPU tenga una métrica de memory con target de utilización (p. ej. 60%), con minReplicas: 2 y maxReplicas: 6. Averigua qué comportamiento tiene cuando ambas métricas coexisten y genera un pico de memoria real (p. ej. subiendo las tareas o el tamaño de la respuesta) para comprobar que el HPA lo ve en kubectl get hpa api -o yaml.

Pista: en autoscaling/v2 el array metrics acepta varias entradas con Resource + name: memory. El HPA usa el ratio más alto de las métricas declaradas para decidir el número de réplicas.

9 · Resumen

  • Requests = reserva garantizada (la usa el scheduler); limits = techo duro (la aplica el kubelet).
  • CPU es comprimible (throttling); memoria no lo es (OOMKill sobre el limit).
  • Clases de QoS: Guaranteed (request==limit), Burstable, BestEffort (sin requests) — en ese orden a la hora de expulsar.
  • kubectl top mide, kubectl scale actúa a mano, HPA automatiza.
  • El HPA calcula ceil(réplicas × uso/target) y escala dentro de minReplicas…maxReplicas.
  • Ventana de estabilización y behavior evitan el "baile" de réplicas.
  • Métricas personalizadas (colas, RPS) existen vía custom metrics API + Prometheus.
ComandoQué hace
kubectl top nodes / kubectl top pods -n NUso real de CPU/memoria por nodo/pod (requiere metrics-server)
kubectl scale deployment api -n N --replicas=4Escalado manual de réplicas
kubectl apply -f hpa-api.yamlCrea el HPA declarado en el manifiesto
kubectl autoscale deployment api --cpu-percent=70 --min=2 --max=6Crea un HPA imperativamente desde el CLI
kubectl get hpa api -n N -wSigue el estado del HPA en vivo
kubectl describe hpa api -n NEventos y decisiones de escalado del HPA

10 · Preguntas frecuentes

¿Qué pasa si un pod supera el limit de memoria?

Depende del QoS: si el pod es BestEffort o Burstable, el kubelet puede matar el contenedor (OOM) y reiniciarlo según la política. En cenarlos Guaranteed, el kubelet prefiere no tocar el pod y expulsar a otros. El estado visible es OOMKilled en la última terminación del pod.

¿El request de CPU garantiza que el pod SIEMPRE tiene esa CPU?

Sí a efectos de programación (el scheduler solo coloca pods si quedan requests disponibles) y en términos de "peso" en el CPU manager. Pero en CPU comprimible, si hay competencia por sobresuscripción, el pod con más CPU de su request puede ver throttling. La garantía dura de verdad es la memoria y la CPU con QoS Guaranteed.

¿Con HPA me olvido de kubectl scale para siempre?

Casi. El HPA gestiona el número de réplicas automáticamente, pero situaciones como picos inminentes (Black Friday), mantenimientos o incidentes siguen exigiendo decisión humana o pipelines de CI/CD. Además, el HPA no "precalienta": responde a la métrica ya medida. Ahí entran los autoscalers predictivos o eventos programados.

¿HPA puede escalar también Web o Postgres?

En principio sí (cualquier Deployment/StatefulSet con métricas), pero tiene sentido sobre todo en stateless e intensivos en CPU (como la API y la web). Escalar Postgres automáticamente por CPU no da réplicas que escriban de forma coherente; ahí el enfoque correcto es otro (una instancia primaria + réplicas de lectura gestionadas, o un operador de bases de datos).

¿El HPA funciona en kind?

Sí, si instalas metrics-server. kind no lo trae por defecto. Con kubectl apply -f components.yaml (el manifiesto oficial releases) lo tendrás en minutos y podrás practicar toda la lección. Solo recuerda que en kind el "escalado" ocurre con uno o unos pocos nodos, así que los límites físicos llegan rápido — perfecto para ver OOM/eviction en vivo.
