Caso de estudio: HarborTasks

Módulo 0 · Preparación ⏱ 25 minutos

1 · Introducción

Un curso de contenedores se aprende de verdad cuando tienes una misma aplicación que madura contigo: primero sueltas un docker run, luego la contenerizas pieza a pieza, después la orquestas con Compose y, al final, la despliegas en un clúster Kubernetes con Helm. Esa aplicación, a lo largo de todo el curso, es HarborTasks: un gestor de tareas en miniatura.

En esta lección entenderás qué es HarborTasks, por qué sus tres piezas (web, api, base de datos) son un ejemplo realista de arquitectura moderna, y qué conseguirás exactamente al terminar cada bloque del curso.

¿Por qué existe esta lección? Para que cada módulo posterior tenga un «por qué» concreto: cuando hagas un Dockerfile multi-stage (módulo 1), sabrás que es para la imagen de la API; cuando aprendas volúmenes (módulo 3), sabrás que es porque PostgreSQL no puede perder los datos de las tareas. El hilo conductor evita aprender comandos sueltos.

2 · Teoría

Las tres piezas de HarborTasks

  • web — interfaz estática servida por nginx (HTML/CSS/JS vanilla). Sin lógica de negocio: solo sirve archivos.
  • api — API REST en Node.js (Express) que expone el CRUD de tareas (GET /tasks, POST /tasks, …). La lógica vive aquí.
  • postgres — PostgreSQL que persiste las tareas. Es el único servicio con estado.

                        │          NAVEGADOR            │
                        └──────────────┬────────────────┘
                                       │ http://localhost:8080
                                       v
                  ┌─────────────────────────────────────────┐
                  │            CONTAINER: web                │
                  │           nginx + archivos estáticos     │
                  └──────────────┬──────────────────────────┘
                                 │ /api/*  -> http://api:3000
                                 v
                  ┌─────────────────────────────────────────┐
                  │            CONTAINER: api                │
                  │          Node.js + Express               │
                  └──────────────┬──────────────────────────┘
                                 │ postgres://harbor:harborpass@postgres:5432/harbortasks
                                 v
                  ┌─────────────────────────────────────────┐
                  │          CONTAINER: postgres              │
                  │        PostgreSQL + VOLUMEN (persistente) │
                  └─────────────────────────────────────────┘

Analogía: HarborTasks es como un restaurante con tres roles bien separados: web es el comedor (la cara que ves), api es la cocina (recibe pedidos, decide las recetas) y postgres es la despensa (guarda los ingredientes que no se pueden perder). Separar los tres hace que puedas ampliar la cocina sin cambiar el comedor, o cambiar la despensa sin tocar las recetas.

¿Por qué estas tres tecnologías?

PiezaTecnologíaPor qué
webnginxServir estáticos es su trabajo nativo; ligera, ultrarrápida y de imagen oficial pequeña
apiNode.js + ExpressEl público del curso ya programa; Express expone una API REST en pocas líneas y se conteneriza en dos etapas (multi-stage)
postgresPostgreSQLBase de datos relacional de referencia, con imagen oficial madura y un caso perfecto de persistencia y configuración

Por qué la API no habla de «localhost» a la base de datos

Como viste en la lección 1, cada contenedor tiene su propio namespace network, así que su localhost es él mismo. La API se conectará a la base usando el nombre del servicio (postgres), que queda resuelto por la red interna de Docker (redes bridge del módulo 3) o por el DNS del clúster en Kubernetes. La cadena de conexión postgres://harbor:harborpass@postgres:5432/harbortasks no es magia: el nombre de host postgres es la contraparte de red del contenedor con ese nombre.

El plan del curso: del docker run al clúster con Helm

BloqueQué haces con HarborTasks
Módulos 1–3Contenerizas cada pieza: Dockerfile de la API (multi-stage), imagen nginx de la web, PostgreSQL con volumen persistente
Módulo 4Orquestas el stack completo con Docker Compose: web + api + postgres con healthchecks y perfiles dev/prod
Módulos 5–8Subes el mismo stack a Kubernetes (kind): Pods, Deployments, Services, ConfigMaps, Secrets, PVC e Ingress

La clave pedagógica del curso: es el mismo sistema evolucionando, no ejemplos nuevos cada módulo. Cuando aparece una abstracción nueva (Service, PVC, Ingress) ya conoces el dato que transporta.

3 · Ejemplo mínimo

El «minuto cero» de HarborTasks: levantar la pieza delantera (web) en un solo contenedor, aunque todavía no tenga contenido propio.

# -d       : en segundo plano
# -p 8080:80: publica el puerto 80 del contenedor en localhost:8080
# --name   : le damos identidad para referirnos a él después
# nginx:1.27-alpine : imagen oficial de nginx sobre Alpine (pequeña)
docker run -d -p 8080:80 --name harbor-web nginx:1.27-alpine

Abre http://localhost:8080 y verás la página de bienvenida de nginx. Ya tienes un servidor web corriendo aislado: es el germen del web de HarborTasks.

Tu sistema operativo: en Linux y macOS el ejemplo es idéntico. En Windows ejecútalo dentro de tu terminal WSL2 (lección 04) — Docker Desktop redirigirá el puerto a localhost de Windows igualmente.

4 · Ejemplo real

En esta lección no montamos todavía el stack completo (eso llega en el módulo 4), pero sí vamos a preparar el terreno: crear la estructura real del proyecto que usarás todo el curso y entender qué contendrá cada carpeta.

# Crea el espacio de trabajo (dentro de WSL2 en Windows, ~ en Linux/macOS)
mkdir -p proyectos/harbortasks
cd proyectos/harbortasks

# Estructura mínima del proyecto (la ampliaremos en módulos siguientes)
mkdir -p docker k8s helm/harbortasks

Decisión de diseño de la estructura — el porqué de cada carpeta:

CarpetaQué vivirá ahíCuándo se trabaja
docker/Dockerfiles y configuración de nginx (api.Dockerfile, nginx.conf)Módulos 1–3
compose.yamlOrquestación local del stack (web+api+postgres)Módulo 4
k8s/Manifiestos Kubernetes «a mano» (Deployment, Service, ConfigMap, Secret, PVC, Ingress)Módulos 5–8
helm/Chart de Helm reutilizable del despliegue finalMódulo 9

Observa que el proyecto contiene las tres piezas, pero aún no hay ni un solo Dockerfile: lo escribirás, comentado comando a comando, en el módulo 1. Esta lección solo te ubica en el mapa.

5 · Buenas prácticas

HazEvitaPor qué
Separar frontend, API y base de datos en servicios independientes Un solo contenedor monolítico que lo haga todo Cada pieza se desarrolla, escala y despliega por separado; un monolito en un contenedor no te enseña nada de arquitectura
Tratar cada contenedor como efímero y poner los datos en volúmenes Guardar las tareas dentro de PostgreSQL sin volumen Si el contenedor muere, los datos del monolito se van con él; los volúmenes sobreviven (módulo 3)
Usar versiones fijas (nginx:1.27-alpine, postgres:16-alpine) Confiar en :latest Reproducibilidad: el mismo Dockerfile en cualquier equipo produce la misma imagen
Que la UI hable con la API por una ruta /api/* Poner la lógica de negocio en la web nginx redirige /api a la api; así la web se mantiene «tonta» y el frontend/cache está limpio
Mantener config y secretos separados de la imagen Hardcodear contraseñas en el Dockerfile Con variables de entorno, Compose y más tarde ConfigMaps/Secrets (módulo 7), una imagen sirve para prod y dev

6 · Errores habituales

Querer construir el stack completo en el módulo 0

# ❌ Correr a por Compose y Kubernetes sin dominar la pieza mínima
# docker compose up  # sin saber docker run, qué es una imagen o un volumen

# ✅ El orden del curso respeta la curva: primero contenedor, luego imagen,
#    luego Compose, luego Kubernetes. Cada módulo añade UNA abstracción.
docker run -d -p 8080:80 --name harbor-web nginx:1.27-alpine

Confundir «la web» con «la app entera»

# ❌ Pensar que el contenedor web = HarborTasks al completo
# La web solo sirve archivos; la lógica vive en la API.

# ✅ Modelo correcto: web (nginx) -> api (Node) -> postgres (datos)
# Y cada adaptación del curso toca la pieza que le corresponde.

Guardar los datos de PostgreSQL sin volumen

# ❌ Ejecutar postgres y creer que los datos son eternos
# docker run -d --name harbor-db postgres:16-alpine
# Si borras el contenedor: ADIÓS a las tareas.

# ✅ Los datos van en un volumen que sobrevive al contenedor (módulo 3)
# docker run -d --name harbor-db -v pgdata:/var/lib/postgresql/data postgres:16-alpine

Pensar que «se acabó al terminar Docker»

Si te quedas en Docker Compose, tienes una máquina local muy cómoda… y exactamente nada para producción: sin escalado, sin auto-reparación, sin multi-host. Es exactamente lo que Kubernetes resuelve (módulo 5): el curso existe para que veas el salto con el mismo HarborTasks, no con teoría abstracta.

7 · Ejercicio guiado

Objetivo: construir tu primera pieza «real» de HarborTasks: una web con nginx que sirve una página que dice HarborTasks.

  1. Paso 1: crea el proyecto y una carpeta para la web: 
    mkdir -p proyectos/harbortasks/web
cd proyectos/harbortasks/web
  2. Paso 2: crea un fichero index.html mínimo (en tu editor, el HARBOR-TASKS empezará aquí): 
    <!DOCTYPE html>
<html lang="es">
  <head><meta charset="UTF-8"><title>HarborTasks</title></head>
  <body>
    <h1>HarborTasks</h1>
    <p>Mi gestor de tareas en contenedores.</p>
  </body>
</html>
  3. Paso 3: sirve esa carpeta con nginx usando un bind mount (la web en /usr/share/nginx/html): 
    # -v "$PWD":/usr/share/nginx/html:ro  -> monta la carpeta actual de solo lectura
# :ro en el bind mount hace que nginx no pueda escribir sobre tu código
docker run -d -p 8082:80 --name harbor-web -v "$PWD":/usr/share/nginx/html:ro nginx:1.27-alpine
  4. Paso 4: abre http://localhost:8082 y comprueba que ves tu página «HarborTasks».
  5. Paso 5: cambia el texto del index.html en tu editor y recarga el navegador (F5). Verás el cambio al instante, sin reconstruir nada: el bind mount comparte archivos vivos entre tu máquina y el contenedor.
  6. Verificación final: docker ps debe mostrar harbor-web en estado Up; docker rm -f harbor-web lo limpia tras probar.

Windows/WSL2: ejecuta esto dentro de la distro con el proyecto en ~/proyectos/.... Si montaras /mnt/c, el bind mount funcionaría pero sería lento y con permisos raros. En macOS, Docker Desktop comparte la carpeta automáticamente por defecto.

8 · Reto

🎯 Planifica tu versión de HarborTasks

Sin escribir Docker aún, dibuja (en texto o en un fichero plan.md) tu versión de HarborTasks respondiendo a: (1) qué ruta de la web llama a la API y qué método HTTP usará; (2) qué tabla necesitará PostgreSQL y qué columnas tendrá una tarea (id, título, estado…); (3) dónde vivirán la contraseña de la base de datos y la variable de entorno de conexión de la API. Con tu plan hecho, anota en una línea qué te impide montarlo hoy (probablemente: «no sé todavía crear la imagen de la api» → ese es exactamente el siguiente módulo).

Pista: piensa en el flujo del usuario — la web lista las tareas consumiendo GET /api/tasks; la API las lee de PostgreSQL. La contraseña no va en el código fuente: va en variables de entorno (módulo 2) y más tarde en Secrets (módulo 7).

9 · Resumen

  • HarborTasks es el hilo conductor del curso: gestor de tareas con web (nginx), api (Node/Express) y postgres (PostgreSQL).
  • Los tres servicios se comunican por la red de contenedores: la api llama a postgres:5432, la web redirige /api/* a la api.
  • El plan del curso: docker run → imágenes/Dockerfile → volúmenes/red → Compose → Kubernetes (kind) → Helm, siempre con el mismo stack.
  • Separar piezas facilita desarrollar, escalar y desplegar cada parte por separado.
  • El proyecto vive en ~/proyectos/harbortasks (filesystem Linux en Windows/WSL2) con carpetas docker/, k8s/ y helm/.
  • Al final del curso tendrás el stack local con Compose Y el mismo stack en Kubernetes vía chart de Helm reutilizable.

10 · Preguntas frecuentes

¿Por qué la web usa nginx y no Node u otro servidor?

Porque servir archivos estáticos es tarea de un servidor web web ligero y especializado: nginx es diminuto (imagen base Alpine de pocos MB), rápidísimo y hace de proxy inverso para redirigir /api/* a la API. Meter la web «dentro de Node» añadiría una dependencia más sin necesidad: separación de responsabilidades (lección de buenas prácticas).

¿Necesito saber Node.js, Express o PostgreSQL para seguir el curso?

No a fondo. Asumimos que ya programas (tu lenguaje favorito), y las piezas son tan pequeñas (API de pocas rutas, base de una tabla) que se entienden leyendo en diagonal. El foco del curso es la contenerización y orquestación, no la sintaxis de Express: todos los ficheros vendrán comentados línea a línea.

¿Cuándo podré subir la web a producción con Kubernetes?

Al llegar al módulo 9, con tu chart de Helm. En los módulos 5–8 experimentarás en local con kind (Kubernetes in Docker), que levanta un clúster real en tu máquina con los mismos manifiestos que luego aplicarías en cualquier clúster de la nube: ese es el salto de «script de producción» a «sistema que se despliega igual en todos lados».

¿Por qué no empezar el curso directamente con Compose o Kubernetes?

Porque cada abstracción se apoya en la anterior: Compose orquesta contenedores e imágenes; Kubernetes orquesta pods, volúmenes y services. Sin la base de cómo funcionan los contenedores, Compose y Kubernetes serían cajas negras: sabrías usar los comandos, pero no qué hacen. La progresión del curso baja dramáticamente la fricción de cada módulo siguiente.

¿Puedo cambiar HarborTasks por mi propio proyecto durante el curso?

Por supuesto: si tu proyecto ya tiene frontend + API + base de datos, puedes aplicarle cada lección (Dockerfile, Compose por servicio, manifiestos K8s) en paralelo. HarborTasks te da una referencia funcionando con la que comparar tus resultados; tu proyecto te da la motivación real. Solo no dejes de hacer los ejercicios de HarborTasks: son la red de seguridad del aprendizaje.
