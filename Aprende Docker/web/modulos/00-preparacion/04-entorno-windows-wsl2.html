Windows, WSL2 y Docker Desktop

Módulo 0 · Preparación ⏱ 45 minutos

1 · Introducción

Windows no puede ejecutar contenedores Linux directamente: los contenedores usan el kernel del host (lección 1) y el kernel de Windows es NT, no Linux. La solución que Microsoft construyó — y que usaremos todo el curso — se llama WSL 2: una máquina virtual ligera de Linux integrada en Windows sobre la que Docker Desktop levanta su daemon. El resultado es que tú escribes docker run dentro de tu distro Ubuntu y todo funciona como si estuvieras en Linux.

Esta es la lección dedicada a WSL del curso. Verás por qué existe WSL, qué diferencia hay entre WSL1 y WSL2, cómo se instala (con Windows Terminal), cómo se integra con Docker Desktop y por qué tu proyecto debe vivir dentro del filesystem Linux y no en C:\. Terminamos con los errores típicos: daemon caído, integración sin activar y el temido CRLF.

¿Por qué dedicar una lección entera a esto? Porque la mitad de los fallos de Docker de un desarrollador que trabaja en Windows no son de imágenes ni de contenedores: son de dónde vive el código, con qué terminal se ejecutan los comandos y cómo se montan los archivos. Resolver el entorno de una vez es la inversión más rentable del módulo.

2 · Teoría

Qué es WSL y por qué existe

WSL (Windows Subsystem for Linux) es una capa de compatibilidad que permite ejecutar un entorno de Linux dentro de Windows. Nació porque los desarrolladores y las empresas querían herramientas Linux (Docker, Kubernetes, scripts, servidores) sin tener que arrancar una máquina virtual completa o cambiar de sistema operativo.

WSL1 vs WSL2: traducción de syscalls vs kernel real

WSL 1WSL 2
Cómo funcionaTraduce las llamadas al sistema (syscalls) de Linux a llamadas de Windows, en tiempo realVM mínima con un kernel Linux real
KernelNinguno (emula en el kernel NT)Kernel Linux completo (actualizable desde Windows)
CompatibilidadParcial: falla con ciertas syscalls y con DockerCompleta: puede ejecutar Docker y casi cualquier cosa Linux
Rendimiento de I/ORápido sobre archivos Windows nativosMuy rápido sobre su propio filesystem (ext4), más lento sobre /mnt/c
Uso con Docker❌ Básicamente no soportado✅ Necesario: la VM WSL2 es el «host Linux» de los contenedores

En el curso: usa siempre WSL 2 (versión 2). WSL1 no sirve para Docker. Verificar la versión es el primer paso de cualquier diagnóstico en Windows.

Por qué los contenedores Linux no corren en Windows directamente

Un contenedor no es una máquina virtual con su propio sistema: es un grupo de procesos que usa el kernel del host (lección 1). Un contenedor Linux necesita ejecutar clone, namespace, cgroup… y eso solo lo puede hacer un kernel Linux. El kernel de Windows no lo proporciona. Por eso Windows solo puede correr «contenedores de Windows», y nosotros usamos únicamente Linux containers: Docker Desktop levanta una VM WSL2 y utiliza esa VM como host de los contenedores.

Cómo se integra: Docker Desktop + WSL2

[ Docker Desktop (Windows) ]
   |  Settings -> Resources -> WSL Integration
   v
[ WSL2  Ubuntu ]  <-- el daemon de Docker corre DENTRO de esta VM Linux
   |  docker run nginx
   v
[ Contenedor nginx ]  <-- es un proceso Linux real sobre el kernel de la VM

La integración hace que el comando docker dentro de tu distro WSL se conecte al mismo daemon que Docker Desktop. Así puedes escribir docker run en tu terminal Ubuntu y obtener contenedores de verdad, con toda la infraestructura de Docker Desktop (menú, volúmenes, compartición de archivos).

Filesystem: dos mundos conectados

RutaQué esRendimiento
\\wsl$\Ubuntu\home\tu_usuario\...Acceso desde Windows al filesystem interno de la distro WSL (visítala desde Explorer escribiendo esa ruta)✅ Rápido (ext4 real)
/mnt/c/Users/...Acceso desde WSL a los discos de Windows (tu C:)⚠️ Lento para bind mounts y compilación: cruza el puente entre filesystems

Regla de oro del curso en Windows: el proyecto HarborTasks vive en el filesystem de Linux, dentro de la distro: ~/proyectos/harbortasks, no en C:\Users\...\proyectos. Montar /mnt/c en un contenedor (bind mount) hace que las operaciones de archivos sean un orden de magnitud más lentas y provoca fallos de permisos y de watchers. Desarrollar en el FS de Windows es el «modo lento y problemático».

Red: cómo Docker publica localhost

  • Docker Desktop redirige los puertos publicados del contenedor a localhost de Windows automáticamente. Si tu contenedor publica -p 8080:80, abres http://localhost:8080 en el navegador de Windows y funciona.
  • Dentro de WSL2, el localhost de la distro comparte red con Windows gracias a la VM (red localhost compartida), así que los puertos también se ven desde la propia distro.
  • Si necesitas hablar desde Windows con un servicio que corre dentro de la distro WSL (no en un contenedor), puedes usar la IP de WSL: averíguala con hostname -I dentro de la distro.

VSCode Remote - WSL: el proyecto abre «dentro» de Linux

La extensión Remote - WSL de VSCode abre la carpeta del proyecto usando la espacio de trabajo de WSL: la terminal integrada es bash de Ubuntu, los plugins corren con binarios de Linux (incluida la extensión de Docker) y todo lo que es relativo al proyecto (git, watchers, nodemon) se comporta como en Linux real.

[ VSCode en Windows ]
   |  Remote - WSL (extensión) conecta
   v
[ WSL2 Ubuntu ]  <-- la ventana de VSCode AHORA vive dentro de la distro
   |  terminal > bash
   |  extensiones Linux (Docker, Kubernetes)
   v
[ tu/código  ~/proyectos/harbortasks ]

Recomendación del curso: haz todo el trabajo de Docker en la terminal de bash dentro de WSL. Los ejemplos del curso son bash; así copias los comandos tal cual y el comportamiento (rutas, permisos, señales) es el que se explica. PowerShell queda para las tareas de sistema de Windows.

3 · Ejemplo mínimo

El ejemplo mínimo de esta lección no es un contenedor: es comprobar que el mundo Windows está unido. Tres comandos (uno de Windows PowerShell, dos dentro de WSL):

# En PowerShell de Windows: activa WSL y comprueba la versión instalada
wsl --install
wsl --set-default-version 2
wsl --status        # muestra la versión por defecto (debe ser 2)

# Dentro de tu distro Ubuntu (terminal WSL): verifica que se habla con la VM
uname -r            # un kernel de Linux REAL: p.ej. 5.15.x-microsoft-standard-WSL2
docker version      # la CLI funciona (hay integración con el daemon de Desktop)

Si uname -r devuelve un kernel con la palabra microsoft y sin WSL, bootstrap; si docker version muestra Server, tu integración está activa. En 3 comandos has comprobado WSL2, kernel y daemon.

4 · Ejemplo real

Veamos el flujo completo de creación del entorno de HarborTasks en Windows, paso a paso, desde PowerShell:

# 1) Habilitar WSL2 (si no lo está) y lista distros instaladas
wsl --install
wsl --list --verbose      # columnas: NAME, STATE, VERSION -> comprueba "2"

# 2) Dentro de WSL (terminal Ubuntu): crea el espacio de trabajo en el filesystem Linux
cd ~
mkdir -p proyectos/harbortasks   # vive en ext4: rápido para bind mounts
cd proyectos/harbortasks
git init

# 3) Verifica Docker desde la distro (debe responder Server de Docker Desktop)
docker version
docker run --rm hello-world   # prueba de fuego

# 4) Desde Windows Explorer, escribe \\wsl$\Ubuntu\home\TU_USUARIO\proyectos
#    y verás tus archivos: es la MISMA carpeta que ~/proyectos

Nunca hagas cd /mnt/c para el proyecto del curso. La velocidad de los bind mounts de /mnt/c es un orden de magnitud inferior, y algunos watchers (nodemon, el file watcher de Docker BuildKit) fallan o se ponen lentísimos. Los archivos del proyecto viven en ~/... de la distro.

6 · Errores habituales

Error 1: «Cannot connect to the Docker daemon» desde WSL

# ❌ El daemon existe (en Docker Desktop) pero tu distro no lo ve
docker version
# -> error during connect: ... Cannot connect to the Docker daemon

# ✅ Activa la integración: Docker Desktop -> Settings -> Resources -> WSL Integration
#    Marca tu distro Ubuntu. Después cierra/reabre la terminal WSL y repite:
docker version   # ahora aparecerá la sección Server

Error 2: la distro sin integración activada

# ❌ Docker funciona en PowerShell pero NO dentro de WSL (el daemon está en la VM WSL2)
# ✅ Docker Desktop: Settings -> Resources -> WSL Integration -> ubuntu ON

# Compruébalo con: la CLI dentro de WSL debe hablar con el mismo daemon de la app
docker context ls     # 'desktop-linux' activo en WSL es señal de integración ok

Error 3: CRLF en Dockerfiles y scripts

# ❌ Si tu Dockerfile tiene saltos de línea \r\n (CRLF), el build falla o produce errores raros:
# /bin/sh: 1: Syntax error: end of file unexpected
# ✅ Solución raíz: configurar .gitattributes para forzar LF en el repo:
git config core.autocrlf input
# Añade al repositorio un .gitattributes, y cuando uses WSL:
file Dockerfile   # debe decir "ASCII text" y NO "with CRLF line terminators"

Tip URI: dentro de WSL puedes ver claramente la diferencia: cat -v Dockerfile | head -n 3 te muestra ^M al final si hay CRLF. Si lo ves, ese es tu problema.

Error 4: mezclar rutas Windows y Linux en Compose

# ❌ En compose.yaml dentro de WSL, una ruta Windows es un error de montaje
#   volumes:
#     - C:\Users\Ana\proyectos:/web   # hay que escapar y el FS es lento
# ✅ Siempre rutas y paths Linux en proyectos dentro de WSL
#   volumes:
#     - ./web:/usr/share/nginx/html:ro

Error 5: WSL 1 en lugar de WSL 2 (Docker no funciona)

# ❌ wsl --list --verbose muestra tu distro con VERSION 1
# ✅ Conviértela a WSL 2:
wsl --set-version Ubuntu 2
wsl --list --verbose     # ahora VERSION 2

7 · Ejercicio guiado

Objetivo: levantar el entorno WSL2 + Docker Desktop + VSCode y verificarlo con un contenedor real.

  1. Paso 1: en PowerShell (como administrador), habilita WSL2 e instala Ubuntu: 
    wsl --install
wsl --list --verbose    # espera ver una distro Ubuntu con VERSION 2
  2. Paso 2: abre la terminal Ubuntu (por defecto, wsl te lleva a ella). Actualiza e instala base: 
    sudo apt update && sudo apt upgrade -y
sudo apt install -y curl git
  3. Paso 3: instala Docker Desktop (Windows) desde docker.com y actívala la primera vez. En Settings → Resources → WSL Integration marca tu distro Ubuntu.
  4. Paso 4: en Docker Desktop, en Settings → General, usa el backend WSL2 (por defecto). Cierra y vuelve a abrir la terminal Ubuntu y verifica: 
    docker version     # Server presente = integración ok
docker run --rm hello-world
  5. Paso 5: instala Windows Terminal (Microsoft Store) y configúrala para abrir por defecto «Ubuntu». Desde PowerShell: wt -d ~ abre tu home Linux en Windows Terminal.
  6. Paso 6: instala en VSCode la extensión Remote - WSL. Abre el proyecto con File → Open Folder dentro de WSL (aparece como \\wsl$\Ubuntu\...\) o usa el comando «WSL: Open Folder in WSL…». La terminal integrada de VSCode debe ser bash de Ubuntu.
  7. Paso 7 (verificación final): en la terminal integrada de VSCode (dentro de WSL): 
    cd ~ && mkdir -p proyectos/harbortasks && cd proyectos/harbortasks
docker run -d --rm -p 8080:80 nginx:1.27-alpine
curl -I localhost:8080      # esperamos HTTP/1.1 200 OK
  8. Cierre: en Explorer escribe \\wsl$\Ubuntu\home\TU_USUARIO\proyectos y confirma que ves la misma carpeta donde acabas de trabajar. Ese es tu espacio de trabajo del curso.

8 · Reto

🎯 Demuestra la diferencia de rendimiento de rutas

Sin resolverlo paso a paso, investiga y responde por escrito: ¿por qué un bind mount de /mnt/c es mucho más lento que uno de ~/ o de un volumen de Docker en Windows? ¿Qué mecanismo de intercambio de archivos usa WSL2 entre \\wsl$ y /mnt/c? Intenta medir la diferencia con docker run --rm -v /mnt/c/tmp:/tmp alpine:3.20 sh -c "time dd if=/dev/zero of=/tmp/test bs=1M count=100" dentro de WSL, y repite la prueba montando ~/tmp. Escribe los dos tiempos y tu conclusión de una línea sobre dónde debe vivir el proyecto del curso.

Pista: WSL2 accede a los archivos de Windows mediante el protocolo 9P, que es mucho más lento que el acceso nativo ext4 del propio filesystem de WSL. (9P: protocolo de red para compartir filesystems).

9 · Resumen

  • WSL 1 traduce syscalls; WSL 2 es una VM con kernel Linux real. Para Docker solo sirve WSL 2.
  • Los contenedores Linux no corren en Windows porque usan el kernel del host; Docker Desktop levanta la VM WSL2 y ese es su «host».
  • El proyecto vive en el filesystem Linux (~/proyectos/harbortasks), no en C:\ ni montado desde /mnt/c.
  • Activación de integración Docker Desktop ↔ WSL en Settings → Resources → WSL Integration.
  • Red: Docker publica en localhost; la IP de WSL se obtiene con hostname -I.
  • VSCode Remote - WSL te mete dentro de la distro: terminal bash y extensiones Linux coherentes.
  • Cuidado con CRLF en Dockerfiles y scripts; fuerza LF con .gitattributes.

10 · Preguntas frecuentes

¿Puedo usar Docker solo desde PowerShell sin tocar WSL?

Puedes, pero pierdes el objetivo del curso: en Windows puro solo hay contenedores de Windows (o el daemon de Docker Desktop con la VM). Trabajando desde WSL2 con una distro Ubuntu consigues un entorno de desarrollo equivalente al de Linux/Unix: rutas, permisos, señales y las herramientas kubectl/kind/helm (lecciones del módulo 5+) funcionan con binarios Linux. Es la vía recomendada.

¿Qué diferencia hay entre abrir \\wsl$\… en Explorer y abrirlo con VSCode Remote - WSL?

Explorer te muestra los archivos de la distro, pero está corriendo con binarios y servicios de Windows, que tratan el filesystem a través de 9P. VSCode Remote - WSL arranca un servidor VSCode dentro de Linux: la terminal y las extensiones usan procesos nativos de Ubuntu. Es un cambio de «ver archivos» a «estar dentro del sistema».

¿Y si mi Windows no soporta WSL2 (requisitos de hardware)?

WSL2 necesita virtualización (Hyper-V). En equipos muy antiguos o con la virtualización desactivada en la BIOS, puedes activarla o, en última instancia, usar WSL1 (que no sirve para Docker). Si tu equipo no puede con WSL2, la alternativa realista de este curso es usar una máquina virtual Linux completa o una partición dual.

¿CRLF rompe realmente los Dockerfiles? Me parece exagerado.

Sí. El intérprete de las instrucciones de un Dockerfile (y de los scripts bash que instala) puede fallar al encontrar \r al final de línea: errores tipo /bin/sh: 1: Syntax error. Además, los entornos de Windows revertirán los saltos si no configuras .gitattributes. La regla del curso: el repositorio se guarda con LF; git en Windows lo convierte según tu configuración si no se fija explícitamente.

Necesito acceder desde Windows a la API que corre dentro de WSL (no en contenedor). ¿Cómo?

Si es un proceso de la distro, usa la IP de WSL (hostname -I); si es un contenedor publicado con -p, usa localhost en el navegador de Windows. Docker Desktop redirige los puertos publicados al localhost de Windows, porque el daemon vive en la VM WSL2 pero su puerta de entrada se comparte con el host.
