depends_on y healthchecks entre servicios

Módulo 4 · Docker Compose ⏱ 30 minutos

1 · Introducción

Cuando un sistema tiene varios contenedores, el orden de arranque importa: la API no puede vivir sin su base de datos. Compose tiene dos mecanismos para coordinar esto: depends_on (declara quién necesita a quién) y healthcheck (declara cuándo un servicio está de verdad listo).

La trampa clásica: depends_on por defecto solo espera a que el contenedor dependido haya arrancado, no a que esté listo para trabajar. Por eso las conexiones se «niegan» al levantar un stack. En esta lección aprenderás a distinguir «arranque» de «listo», a escribir healthchecks correctos y a combinar ambas piezas con condition: service_healthy.

¿Por qué importa tanto esta lección?

Es la diferencia entre un stack que «funciona a veces» y uno reproducible. El mismo concepto —liveness y readiness— reaparecerá en Kubernetes con las probes (Módulo 6). Si hoy entiendes arranque ≠ listo, las probes de Kubernetes te parecerán familiares.

2 · Teoría

Arranque ≠ listo: dos estados muy distintos

Docker conoce el estado del proceso de un contenedor (created, running, exited…). Que el proceso de Postgres esté running solo significa que el binario se lanzó y usa CPU. Pero Postgres, antes de aceptar conexiones, tiene que: leer config, abrir el pgdata, recuperar el estado del último apagado, levantar el listener de red… Eso tarda varios segundos. Durante ese intervalo, el puerto 5432 existe físicamente pero rechaza conexiones.

Analogía: el chef y la mesa preparada

depends_on sin condición es como decirle a los comensales «el chef ya ha llegado a la cocina, sentaos». El restaurante funciona cuando el chef ha servido la comida. Un healthcheck es el «¿está la mesa lista?» que preguntamos cada pocos segundos antes de dejar pasar a los siguientes.

depends_on: la forma corta (y su límite)

services:
  api:
    # FORMA CORTA: equivale a "arranca postgres antes que la api", sin más
    depends_on:
      - postgres

  postgres:
    image: postgres:16-alpine

Con la forma corta, Compose crea y arranca postgres antes, pero no espera a nada más: la api arranca «justo después», con la base aún cerrando su arranque. Resultado típico:

api-1       | Error: connect ECONNREFUSED 172.18.0.2:5432   ← conexión RECHAZADA
api-1       |     at TCPConnectWrap.afterConnect [as oncomplete] (net.js:…)
api-1 exited with code 1

Ese ECONNREFUSED es, con diferencia, el error más visto al arrancar stacks multi-contenedor. depends_on ha cumplido su parte (orden), pero nadie le dijo al orquestador cuándo puede abrir la puerta.

healthcheck: el «¿estás listo?» periódico

Un healthcheck es un comando que Docker ejecuta cada interval dentro del contenedor. Si sale 0, el contenedor está sano; si sale distinto de 0, cuenta un fallo. Claves:

ClaveSignificadoRecomendación
testEl comando de salud: ["CMD", "prog", "arg"] (directo, sin shell) o ["CMD-SHELL", "shell_prog"]Usa CMD-SHELL cuando necesites shell o tuberías
intervalFrecuencia entre comprobaciones5–10s en local; recuerda: es ruido de proceso cada X
timeoutTiempo máximo del test antes de contar como fallo5s (debe ser menor que interval)
retriesFallos consecutivos para pasar a unhealthy3–5 (evita parpadeos ante un fallo puntual)
start_periodPeriodo de gracia inicial: los fallos durante este tiempo no cuentanEn servicios lentos (bases de datos) es clave

Estados posibles: starting (dentro de start_period), healthy y unhealthy. Puedes verlos con docker compose ps (columna STATUS muestra Up (healthy)) o con docker inspect.

depends_on con condition: la forma larga

services:
  api:
    # FORMA LARGA: la api NO arranca hasta que postgres esté "healthy"
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:16-alpine
    healthcheck:
      # probamos el listener de red con -h; sin él cae al socket (falso positivo)
      test: ["CMD-SHELL", "pg_isready -h localhost -U harbor -d harbortasks"]
      interval: 5s
      timeout: 5s
      retries: 5
      start_period: 10s

condition acepta tres valores:

  • service_started: el comportamiento por defecto (solo «arrancado»).
  • service_healthy: esperar a que el healthcheck pase → el que usaremos.
  • service_completed_successfully: esperar a que un contenedor de una sola tarea termine con éxito (migraciones, seeders).
docker compose up --wait

Compose v2 añadió el flag --wait: docker compose up -d --wait no «termina» hasta que todos los servicios con healthcheck están healthy (o fallan). Perfecto para scripts de verificación.

Redes personalizadas en Compose

Si no declaras redes, Compose crea una red bridge por proyecto y conecta todos los servicios a ella. Pero cuando declaras networks: en un servicio, ese servicio sale de la red por defecto y se conecta solo a las que declares. Esto permite separar tráfico (api→postgres por una red, api→internet por otra):

networks:                 # nivel superior: se declaran una vez
  harbor-net:
    driver: bridge         # explícito (es el default, pero queda documentado)

services:
  api:
    networks:
      - harbor-net
  postgres:
    networks:
      - harbor-net

La regla práctica: todos los servicios que deban hablarse entre sí comparten la misma red con nombre; los servicios que no se hablan pueden estar en redes distintas o directamente en la red por defecto.

El healthcheck depende de la red

condition: service_healthy solo se puede aplicar entre servicios que viven en la misma red. Si la api está aislada, Compose ni siquiera puede observar la salud del otro. La red compartida no es cosmética: es el cable que permite la dependencia.

3 · Ejemplo mínimo

El stack mínimo que resuelve el ECONNREFUSED: una base con healthcheck y un servicio que espera a que esté lista. Como «cliente» de prueba usamos la propia imagen de Postgres (trae pg_isready):

compose.yaml
name: orden-de-arranque

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: harbor
      POSTGRES_PASSWORD: harborpass
      POSTGRES_DB: harbortasks
    healthcheck:
      # probamos el listener de TCP con el cliente oficial (exit 0 = listo)
      test: ["CMD-SHELL", "pg_isready -h localhost -U harbor -d harbortasks"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s   # durante 10s un fallo NO cuenta (arranque lento)

  verifier:
    image: postgres:16-alpine    # reutilizamos la imagen solo por sus clientes
    command: ["sh", "-c",
              "pg_isready -h postgres -U harbor -d harbortasks && echo '✔ postgres listo para conexiones'"]
    depends_on:
      postgres:
        condition: service_healthy   # ← la magia: esperar a "healthy", no a "running"

Línea a línea del healthcheck: test con la forma CMD-SHELL ejecuta pg_isready -h localhost -U harbor -d harbortasks; pg_isready devuelve 0 cuando Postgres acepta conexiones. El start_period da 10 segundos de gracia (Postgres tarda más en el primer arranque). El servicio verifier queda bloqueado hasta que el estado de postgres pase a healthy.

docker compose up
# El orden real que verás en pantalla:
#   postgres  | database system is ready to accept connections   ← "embrague" de PG
#   verifier  | ✔ postgres listo para conexiones                 ← SOLO al ser healthy

4 · Ejemplo real

Aplicado a HarborTasks: la api (Express) depende de postgres con condición service_healthy, en una red personalizada, y con su propio healthcheck para que dependientes futuros (worker, proxies) puedan esperarla también:

compose.yaml
name: harbortasks

networks:
  harbor-net:
    driver: bridge

volumes:
  pgdata:

services:
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: harbor
      POSTGRES_PASSWORD: harborpass
      POSTGRES_DB: harbortasks
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - harbor-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h localhost -U harbor -d harbortasks"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s

  api:
    build: ./api
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://harbor:harborpass@postgres:5432/harbortasks
      PORT: "3000"
    networks:
      - harbor-net
    ports:
      - "3000:3000"       # publicado: el navegador y tú usáis localhost:3000
    depends_on:
      postgres:
        condition: service_healthy   # la api espera a PG LISTO, no a PG "vivo"
    healthcheck:
      # Su propia salud: GET /health responde 200 → healthy
      test: ["CMD", "node", "-e",
             "fetch('http://localhost:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 15s   # la api espera a postgres; da margen a ese "embalaje"

Decisiones tomadas:

  • pg_isready sobre localhost: probamos el listener TCP real (-h localhost fuerza red, no socket). Sin él, el test podría dar positivo antes de exponer el puerto.
  • El healthcheck de la api usa ["CMD", …] (sin shell) y llama a /health: un endpoint de verdad que tu Express expone en una línea: app.get('/health', (_req,res) => res.send('ok')). Probar «lo que el negocio necesita», no solo que el proceso respira.
  • start_period en api (15s): la api arranca tarde (esperó a PG) y durante ese tiempo sus primeros «checks» no deben contarse como fallos.
  • Red explícita harbor-net: encapsula la comunicación; en una red real aislarías además la de la api pública de la de datos.

Inspección del estado de salud

docker compose up -d --build
docker compose ps                # STATUS: "Up (healthy)" en postgres y api

# Detalle del historial de salud (JSON con el último check)
docker inspect --format '{{json .State.Health}}' harbor-postgres-1

# Script de arranque seguro para tu CI: no acaba hasta que TODO esté healthy
docker compose up -d --wait

6 · Errores habituales

Confiar en depends_on sin condition

# ❌ MAL: garantiza el ORDEN, no la DISPONIBILIDAD
services:
  api:
    depends_on:
      - postgres          # postgres "arrancado", no "listo"

# ✅ BIEN: esperar al estado healthy
services:
  api:
    depends_on:
      postgres:
        condition: service_healthy

El healthcheck que da positivo antes de tiempo

# ❌ MAL: sin -h, pg_isready prueba el socket UNIX (/var/run/postgresql).
#    El socket existe ANTES de que el listener TCP acepte conexiones remotas.
test: ["CMD-SHELL", "pg_isready -U harbor"]

# ✅ BIEN: forzamos la interfaz de red (puerto 5432 típico)
test: ["CMD-SHELL", "pg_isready -h localhost -U harbor -d harbortasks"]

timeout mayor que interval (checks que se pisan)

# ❌ MAL: interval es 5s pero el timeout es 10s → el siguiente check arranca
#    mientras el anterior sigue colgado; el estado salta a unhealthy
healthcheck:
  test: ["CMD", "pg_isready", "-h", "localhost"]
  interval: 5s
  timeout: 10s

# ✅ BIEN: timeout menor que interval
healthcheck:
  test: ["CMD", "pg_isready", "-h", "localhost"]
  interval: 10s
  timeout: 5s

Retries y start_period para uno-shot vs largo plazo

# ❌ MAL: retries bajos y sin gracia de arranque: en el primer arranque una base
#    lenta acumula 2 fallos y pasa a unhealthy aunque el arranque vaya bien
healthcheck:
  retries: 2           # un solo tropiezo en arranque = unhealthy
  # (sin start_period)

# ✅ BIEN: gracia de arranque + tolerancia a tropiezos puntuales
healthcheck:
  retries: 5
  start_period: 10s

7 · Ejercicio guiado

Objetivo: montar un stack postgres + verifier con healthcheck y condition: service_healthy, y comprobar los tres estados de salud con las herramientas de Docker.

  1. Crea el proyecto con la base y su healthcheck (copia el «ejemplo mínimo» de la sección 3).
  2. Levanta solo la base y observa la máquina de estados: 
    docker compose up -d postgres
docker compose ps            # STATUS: Up (healthy) tras unos segundos
docker inspect --format '{{json .State.Health}}' $(docker compose ps -q postgres)
# devuelve el JSON con "Status": "healthy" y el "log" del último check
  3. Añade el servicio verifier y baja todo: 
    docker compose down
docker compose up            # (en primer plano): espera hasta "healthy" y corre verifier
  4. Demuestra el «arranque ≠ listo»: detén la base mientras el verifier espera: 
    docker compose up -d
docker compose stop postgres        # la base pasa a unhealthy
docker compose run verifier         # ⏳ se queda BLOQUEADO esperando a postgres…
docker compose start postgres       # …y al volver, salud a healthy → verifier corre
docker compose run verifier         # ✔ postgres listo para conexiones
    Si el verifier se queda esperando demasiado

    Es el comportamiento correcto: condition: service_healthy bloquea hasta que haya señal real de salud. Si quieres cortar, Ctrl+C. En un script real usarías timeout 60 docker compose up o --wait.

  5. Cierra el escenario: 
    docker compose down

8 · Reto

🎯 Cadena de dependencias con tres servicios

Añade a tu stack un servicio worker (imagen node:22-alpine, comando que imprima worker arrancado) que dependa de la api con condition: service_healthy. Necesitarás dar a la api su propio healthcheck (el GET /health de la sección 4) y conectar los tres servicios a la misma red harbor-net. Comprueba con docker compose up que el orden real es postgres → api → worker.

Pistas: sin un endpoint /health la api no puede volverse «healthy»; revisa qué pasa si el worker depende de la api que a su vez depende de postgres — el orden se resuelve en cascada. Y recuerda: los tres deben compartir red.

9 · Resumen

  • Arranque ≠ listo: depends_on corto solo garantiza el orden de creación; el contenedor dependiente arranca con la conexión aún rechazada (ECONNREFUSED).
  • healthcheck define el «¿estás listo?»: test, interval, timeout, retries, start_period.
  • condition: service_healthy (forma larga de depends_on) bloquea el arranque del dependiente hasta que el healthcheck pase.
  • Test que prueba lo que el negocio usa: pg_isready, GET /health… y con -h para forzar la red.
  • Las redes personalizadas organizan el tráfico; la dependencia con condición exige red compartida.
  • El mismo patrón (liveness/readiness) aparece en Kubernetes con las probes (Módulo 6).

docker compose psMuestra Up (healthy/unhealthy) de cada servicio

docker compose stop <svc>Detiene un servicio (pasa a unhealthy) sin borrarlo

10 · Preguntas frecuentes

¿Cuándo se usa service_completed_successfully?

Cuando la dependencia es una tarea de una sola pasada que debe terminar bien antes de continuar: migraciones de base de datos, seeders o jobs de inicialización. El dependiente espera a que ese contenedor salga con código 0, no a que esté «arrancado» (que nunca «está activo» porque muere al acabar).

¿Equivale depends_on con condición a healthchecks nativos de K8s?

Conceptualmente sí, pero en Kubernetes la coordinación es distinta: cada Pod declara sus propias probes (liveness/readiness) y el Service no envía tráfico a Pods que no están listos. Aquí Compose simplemente ordena el arranque; en un clúster, la orquestación es continua. Es el salto conceptual del Módulo 6.

Mi healthcheck da unhealthy pero la app responde. ¿Qué pasa?

Tres causas típicas: el test no usa el comando correcto (falta -h en pg_isready, o la url del /health es otra), el timeout es demasiado corto para el arranque, o faltaba start_period. Depura ejecutando el test a mano dentro del contenedor: docker compose exec postgres pg_isready -h localhost -U harbor.

¿Debo poner healthcheck a todos los servicios?

No todos necesitan uno. Solo tiene sentido si (a) algo depende de su «estar listo» y lo condicionas, o (b) quieres que el stack te avise en docker compose ps. Un nginx estático que no tiene dependientes no gana nada con un healthcheck. La regla: healthcheck en lo que es dependencia de otros.

¿Por qué api necesita condition service_healthy si ya reintenta conexiones?

Porque «reintentar» es imperativo, lento y opaco (logs llenos de ECONNREFUSED, tiempos a ojo). Con la condición, el arranque queda declarado y determinista: la api solo empieza cuando la base acepta conexiones. Además, la api puede ser a su vez dependencia de otros servicios: entonces su propio healthcheck cuenta doble.
