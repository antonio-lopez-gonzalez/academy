Stack Compose completo de HarborTasks

Módulo 4 · Docker Compose ⏱ 40 minutos

1 · Introducción

Este es el hito «Docker local terminado» del curso. Aquí se juntan todas las piezas de los módulos anteriores: imágenes y capas (M1), docker run y env (M2), volúmenes y redes (M3), y las claves de Compose que acabas de aprender. El resultado es el stack completo de HarborTasks — web (nginx), api (Node/Express) y postgres — orquestado con un solo compose.yaml.

Al terminar, tendrás en tu máquina una aplicación completa y verificada de punta a punta: navegador → nginx → API → Postgres, con persistencia real y con dos «modos» de entorno (desarrollo y producción local). A partir del Módulo 5, este mismo stack emigrará a un clúster Kubernetes.

¿Por qué es un hito?

Porque por primera vez un sistema completo —no un contenedor suelto— funciona, se documenta y se reproduce con código. Cada pieza que ya dominas (Dockerfile, volumen, red, healthcheck) aparece aquí en su contexto real. Este compose será la base conceptual de los manifiestos Kubernetes de HarborTasks.

2 · Teoría

La arquitectura final del stack

(tú y el navegador) http://localhost:8080 │ ▼ ┌────────────────────────── red "harbor-net" (bridge) ─────────────────────────┐ │ │ │ ┌─────────── web ───────────┐ :3000 ┌────────── api ──────────┐ │ │ │ nginx:1.27-alpine │ ───────────────► │ node:22 (Express) │ │ │ │ • estáticos ./web │ proxy_pass /api/ │ • DATABASE_URL │ │ │ │ • nginx.conf: proxy │ │ • healthcheck /health │ │ │ └───────────────────────────┘ └────────────┬────────────┘ │ │ puerto público 8080 │ :5432 │ │ ┌──────────▼─────────────┐ │ │ │ postgres:16-alpine │ │ │ │ • volumen pgdata │ │ │ │ • healthcheck │ │ │ │ pg_isready │ │ │ └───────────────────────┘ │ │ │ └───────────────────────────────────────────────────────────────────────────────┘ API también publicada en :3000 SOLO en dev (override) · postgres NUNCA al host
  • Web sirve estáticos y, además, hace de proxy reverso: el navegador solo habla con localhost:8080 y nginx reenvía /api/* a la api. Resultado: un solo origen (sin problemas de CORS) y una decisión que luego replicará el Ingress de Kubernetes.
  • API habla con postgres por el DNS interno de la red (nombre de servicio, no IP), y expone /health para su propio healthcheck.
  • Postgres vive dentro de la red, con su volumen pgdata y jamás publica puertos al host.

Variables con interpolación: la base de dev vs prod

Compose lee un archivo .env del proyecto y lo usa para interpolar el YAML: ${POSTGRES_USER:-harbor} significa «valor de la variable, y si no existe, harbor». Así el mismo compose.yaml sirve para todos los entornos sin tocar una línea:

# .env del proyecto (fuera de git; se commitea solo el .env.example)
POSTGRES_USER=harbor
POSTGRES_PASSWORD=harborpass
POSTGRES_DB=harbortasks
NODE_ENV=development

Perfiles y archivos de override

MecanismoQué haceCuándo

Esta separación mantiene un único compose.yaml «canónico» y deja que las diferencias de entorno vivan en capas por encima. Es el mismo espíritu que luego verás en Helm con values.yaml.

3 · Ejemplo mínimo

El árbol del proyecto y el arranque mínimo para «sentir» que la web funciona antes de completar el stack:

proyectos/harbortasks/
proyectos/harbortasks/
├── compose.yaml              ← stack canónico (esta lección)
├── compose.prod.yaml         ← capa de producción local
├── compose.override.yaml     ← capa de desarrollo (auto)
├── .env.example              ← plantilla de variables (commiteada)
├── .env                      ← valores reales (NO commiteada)
├── docker/
│   ├── api.Dockerfile        ← multi-stage Node (Módulo 1)
│   └── nginx.conf            ← estáticos + proxy /api
├── api/                      ← fuente de la API (context de build)
└── web/                      ← HTML/CSS/JS servidos por nginx

Arranque mínimo: solo la web (sin depender de api ni postgres) para validar que estáticos y proxy no rompen:

docker compose up -d web --build
docker compose ps
curl http://localhost:8080/            # el index.html responde
docker compose down

Fíjate en dos cosas: el archivo docker/nginx.conf está montado en /etc/nginx/conf.d/default.conf (bind mount, Módulo 3), y la web arranca sin esperar a la api: nginx sirve estáticos igualmente (los errores de proxy solo aparecen cuando se pide /api/*).

4 · Ejemplo real

El stack completo. Primero el archivo canónico, comentado línea a línea:

proyectos/harbortasks/compose.yaml
name: harbortasks                 # prefijo de contenedores, red y volúmenes

# --- Planos de infraestructura -------------------------------------------
networks:
  harbor-net:                     # red privada compartida por TODO el stack
    driver: bridge                # explícito: el driver default, documentado

volumes:
  pgdata:                         # persistencia real de Postgres (Módulo 3)

# --- Servicios ------------------------------------------------------------
services:
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:                  # valores interpolados desde .env (con default)
      POSTGRES_USER: "${POSTGRES_USER:-harbor}"
      POSTGRES_PASSWORD: "${POSTGRES_PASSWORD:-harborpass}"
      POSTGRES_DB: "${POSTGRES_DB:-harbortasks}"
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - harbor-net
    healthcheck:                  # la api esperará a que esto sea healthy
      test: ["CMD-SHELL", "pg_isready -h localhost -U ${POSTGRES_USER:-harbor} -d ${POSTGRES_DB:-harbortasks}"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s           # gracia para el primer arranque (crea pgdata)

  api:
    build: ./api                  # contexto = carpeta ./api (contiene su Dockerfile)
    image: harbortasks-api:1.0.0  # etiqueta con la que queda la imagen construida
    restart: unless-stopped
    environment:
      NODE_ENV: "${NODE_ENV:-development}"
      PORT: "3000"
      # ⚠ "postgres" = el NOMBRE DE SERVICIO; NUNCA "localhost" dentro de aqui
      DATABASE_URL: "postgres://${POSTGRES_USER:-harbor}:${POSTGRES_PASSWORD:-harborpass}@postgres:5432/${POSTGRES_DB:-harbortasks}"
    depends_on:
      postgres:
        condition: service_healthy   # ← lección 3: arranque solo cuando PG esté LISTO
    healthcheck:
      test: ["CMD", "node", "-e",
             "fetch('http://localhost:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 20s           # la api esperó a PG: los primeros checks no deben contar
    expose:
      - "3000"                    # interno: solo nginx (y la red) la ven
    networks:
      - harbor-net

  web:
    image: nginx:1.27-alpine
    restart: unless-stopped
    volumes:
      - ./web:/usr/share/nginx/html:ro             # estáticos (bind mount ro)
      - ./docker/nginx.conf:/etc/nginx/conf.d/default.conf:ro  # config del proxy
    networks:
      - harbor-net
    ports:
      - "8080:80"                 # la ÚNICA puerta pública del stack (para el navegador)

Decisiones tomadas: no publicamos la api ni postgres en el base — el único puerto al host es 8080 (navegador). La api se publica solo en dev vía override. Cada servicio con healthcheck, para que docker compose up --wait sea una señal fiable en CI. Y nginx hace de proxy para que el navegador tenga un solo origen.

docker/nginx.conf (proxy: un solo origen, sin CORS)
server {
    listen 80;
    server_name localhost;

    root /usr/share/nginx/html;      # los estáticos de la web
    index index.html;

    # Estáticos: si existe el archivo, se sirve; si no, cae al index (SPA ligera)
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Todo lo que empiece por /api lo reenvía nginx a la api, por red interna
    location /api/ {
        proxy_pass http://api:3000;                  # DNS interno: nombre de servicio
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;     # la ip real del navegador
    }
}
docker/api.Dockerfile (multi-stage, Módulo 1)
# ETAPA 1: solo dependencias (caché: cambian menos que el código)
FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev

# ETAPA 2: imagen final, limpia y sin root
FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=deps /app/node_modules ./node_modules   # copia SOLO la capa de deps
COPY . ./                                           # el código (context = ./api)
EXPOSE 3000
USER node                                           # no correr como root
CMD ["node", "src/server.js"]

Dev: compose.override.yaml (se carga solo en desarrollo)

proyectos/harbortasks/compose.override.yaml
# Fusionado automáticamente por "docker compose". Solo conveniencias de dev.
services:
  api:
    command: npm run dev            # hot reload de Node (reemplaza el CMD del base)
    environment:
      NODE_ENV: development
    volumes:
      - ./api:/app                  # el código montado → editas y se refleja
      - /app/node_modules           # volumen ANÓNIMO: conserva las deps del contenedor
    ports:
      - "3000:3000"                 # dev también publica la api (curl directo)

  # Herramienta de administración de BD: solo con --profile dev
  adminer:
    image: adminer                    # imagen oficial de Adminer (consola web de BD)
    profiles: ["dev"]
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - harbor-net
    ports:
      - "8081:8080"                 # interfaz web en http://localhost:8081

Prod local: compose.prod.yaml (capa explícita)

proyectos/harbortasks/compose.prod.yaml
# Producción local: docker compose -f compose.yaml -f compose.prod.yaml up -d --build
services:
  postgres:
    restart: always                # en "producción" se prefiere siempre arriba
  api:
    restart: always
    environment:
      NODE_ENV: production         # pisa el default del base
  web:
    restart: always
COMPOSE_FILE en vez de repetir -f

Puedes fijar los archivos una vez en el entorno: export COMPOSE_FILE=compose.yaml:compose.prod.yaml y después escribir simplemente docker compose up -d. El orden importa: los archivos de la derecha ganan.

Verificación end-to-end (el «¿funciona de verdad?»)

# 1) Arranque con señal objetiva: no retorna hasta que todo esté healthy
docker compose up -d --build --wait
docker compose ps                    # postgres y api → "Up (healthy)"

# 2) Navegador → web → nginx → api (un solo origen):
curl http://localhost:8080/               # index.html de la web
curl http://localhost:8080/api/health     # proxy: la api responde "ok"

# 3) CRUD (la api se publica en :3000 SOLO en dev, vía override):
curl -X POST http://localhost:3000/api/tasks \
  -H "Content-Type: application/json" -d '{"title":"Aprender Compose"}'
curl http://localhost:3000/api/tasks

# 4) Persistencia de verdad: reinicia Postgres… la tarea SIGUE (es el volumen pgdata)
docker compose restart postgres
curl http://localhost:3000/api/tasks
# 5) En el navegador http://localhost:8080: crear/borrar tareas y recargar la página.
Windows / WSL2: el localhost que te engaña

En WSL2 el puerto publicado se ve en localhost del Windows, pero si compartes la carpeta por /mnt/c los bind mounts irán lentísimos. Regla de oro del curso: el proyecto vive dentro de WSL2 (~/proyectos/harbortasks), nunca en la partición de Windows. Y cuidado con el CRLF: si el nginx.conf o el Dockerfile se guardaron con saltos de línea Windows, los scripts/entradas fallan — el .gitattributes con * text=auto eol=lf lo evita.

6 · Errores habituales

La API intentando conectar a localhost

# ❌ MAL: dentro del contenedor, localhost ES la api (no el host)
services:
  api:
    environment:
      DATABASE_URL: postgres://harbor:harborpass@localhost:5432/harbortasks

# ✅ BIEN: el hostname es el NOMBRE DE SERVICIO, resuelto por el DNS interno
services:
  api:
    environment:
      DATABASE_URL: postgres://harbor:harborpass@postgres:5432/harbortasks

El bridge de la web apuntando a una carpeta sin index.html

# ❌ si la ruta del bind mount no contiene index.html → nginx responde 403
#    y se tarda un rato en ver que el fallo no es el contenedor sino el path.
# ✅ Verifica SIEMPRE el path desde la raíz del proyecto:
ls web/                     # → index.html, js/, css/…
docker compose exec web ls /usr/share/nginx/html   # los mismos archivos MONTADOS

Dependencia con condición pero servicios en redes distintas

# ❌ MAL: api en harbor-net y postgres en la red por defecto → condition no aplica
services:
  api:
    depends_on:
      postgres:
        condition: service_healthy   # la api no está en la red de postgres: sin contacto útil
    networks: [harbor-net]

# ✅ BIEN: los dependientes comparten red (y hostname postgres funciona)
services:
  api:
    networks: [harbor-net]
  postgres:
    networks: [harbor-net]

Vuelve el ECONNREFUSED (falta el healthcheck en prod override)

# ❌ MAL con -f compose.prod.yaml: si el override no incluye depends_on con
#    condición, el orden vuelve a ser "a ojo". Revisar: la condición vive en el BASE.

# ✅ Comprueba el resultado fusionado antes de up:
docker compose -f compose.yaml -f compose.prod.yaml config   # lee api.depends_on
docker compose -f compose.yaml -f compose.prod.yaml up -d --wait

7 · Ejercicio guiado

Objetivo: montar el stack completo y verificarlo de punta a punta. Si algo falla, el diagnóstico está en los logs de cada servicio.

  1. Recrea el proyecto con el árbol de la sección 3 (o clona el del curso) y copia .env.example a .env.
  2. Valida y arranca el stack: 
    docker compose config        # merge + interpolación sin efectos
docker compose up -d --build --wait   # no retorna hasta que TODO sea healthy
docker compose ps             # 3 servicios: postgres y api "healthy"
  3. Verificación por red interna (el navegador→nginx→api): 
    curl http://localhost:8080/               # la web responde
curl http://localhost:8080/api/health     # nginx proxea a la api → "ok"
  4. CRUD real contra la API: 
    curl -X POST http://localhost:3000/api/tasks \
  -H "Content-Type: application/json" -d '{"title":"Aprender Compose"}'
curl http://localhost:3000/api/tasks      # la tarea creada aparece
  5. Persistencia de verdad — reinicia Postgres sin perder nada: 
    docker compose restart postgres
curl http://localhost:3000/api/tasks   # la tarea SIGUE (esto es pgdata)
docker compose exec postgres psql -U harbor -d harbortasks -c "SELECT * FROM tasks;"
  6. Navegador: abre http://localhost:8080, crea y borra una tarea desde la interfaz; recarga la página: los datos persisten.
  7. Apaga el escenario y observa que pgdata vive: 
    docker compose down        # red y contenedores fuera
docker volume ls | grep pgdata   # el volumen sigue ahí

8 · Reto

🎯 Producción local con Compose: capa y perfiles

Levanta el stack con docker compose -f compose.yaml -f compose.prod.yaml up -d --build, verifica que NODE_ENV es production (con docker compose exec api printenv NODE_ENV) y que la api no está publicada en :3000 (mira docker compose ps). Después abre la herramienta adminer: docker compose --profile dev up -d adminer y explórala en http://localhost:8081. ¿Por qué en el modo prod no arranca adminer aunque tenga depends_on?

Pista: los servicios con profiles arrancan solo cuando su perfil se activa con --profile o COMPOSE_PROFILES; el depends_on de un servicio no perfilado hacia uno perfilado tiene normas especiales — revisa la documentación de «conditional dependency» y prueba a quitar el depends_on.

9 · Resumen

  • 🎉 Hito alcanzado: HarborTasks completo y verificado en local: web + api + postgres como una sola unidad reproducible.
  • Un solo compose.yaml canónico con tres planos (services, networks → harbor-net, volumes → pgdata).
  • Healthchecks + condition: service_healthy convierten el arranque en determinista (up --wait).
  • Dev vs Prod con .env + interpolación, compose.override.yaml automático y compose.prod.yaml explícito (vía -f o COMPOSE_FILE).
  • Perfiles (profiles: ["dev"]) para herramientas opcionales como adminer.
  • nginx como proxy reverso: un solo origen sin CORS y un patrón que volverá como Ingress.

10 · Preguntas frecuentes

¿Por qué el navegador no llama a la api en :3000 directamente?

Porque tendrías dos orígenes (localhost:8080 y localhost:3000) y el navegador exigiría cabeceras CORS en cada respuesta. Hacer que nginx proxee /api/* da un solo origen, simplifica la web y oculta la topología interna. Es exactamente el mismo trabajo que luego hará el Ingress de Kubernetes con sus rutas (Módulo 7).

¿Cuál es la diferencia entre el override automático y el de producción?

compose.override.yaml se fusiona solo en docker compose up: es «la capa de desarrollo» de tu día a día. compose.prod.yaml hay que pedirlo explícitamente con -f (o COMPOSE_FILE): es la capa de producción local, sin comodidades de dev y con políticas más estrictas.

¿Dónde viven los datos de Postgres?

En el volumen pgdata, que Docker guarda en su área de volúmenes del host (docker volume inspect pgdata te da el Mountpoint real; en Docker Desktop, dentro de la VM/WSL2). Por eso sobrevive a down y a restart. También por eso conviene hacer copias: docker compose exec postgres pg_dump -U harbor harbortasks > backup.sql.

¿Esto es ya «producción de verdad»?

Es producción local: sirve para entregar, validar y CI en una sola máquina, y comparte patrones reales (healthchecks, proxy, capas por entorno). Pero una base de datos de un solo nodo sin copias ni alta disponibilidad no es un despliegue de producción real: eso es lo que Kubernetes aporta (Módulo 5 en adelante), y no se «quita» Compose, se lo reemplaza formalmente.

¿Cómo evito que las contraseñas lleguen al repositorio?

El compose.yaml solo contiene referencias (${POSTGRES_PASSWORD:-harborpass}), nunca los valores. El archivo .env con los valores reales está en .gitignore; se commitea la plantilla .env.example. Para secretos gestionados de verdad (rotación, cifrado, RBAC) verás los Secrets de Kubernetes en el Módulo 7.
