compose.yaml: services, ports, env, volumes

Módulo 4 · Docker Compose ⏱ 35 minutos

1 · Introducción

Ya sabes por qué existe Compose. Ahora toca escribir de verdad el compose.yaml: cada clave de servicio es la traducción de un flag de docker run. En esta lección verás las claves esenciales — image/build, container_name, ports, environment, env_file, volumes, restart — y los comandos del ciclo de vida de un proyecto Compose (up, down, config, ps, logs, exec).

Terminarás sabiendo montar un stack de dos o tres servicios desde cero, entender cada línea que escribes y aprovechar el archivo de override compose.override.yaml que Compose carga automáticamente.

¿Por qué dedicarle una lección entera al archivo?

El compose.yaml es el «contrato» entre tú y el motor: casi todos los fallos de Compose son errores de archivo (indentación, claves mal escritas, puertos sin comillas…). Si dominas cada clave y la inspeccionas con docker compose config, dejarás de depurar a ciegas: el YAML te dirá exactamente qué declaraste.

2 · Teoría

Estructura del archivo: el esqueleto de nivel superior

Un compose.yaml moderno (sin version:) tiene hasta cuatro bloques de nivel superior: name, services (el único obligatorio), networks y volumes. Lo que declaras arriba se referencia desde los servicios:

compose.yaml │ ├── name: harbortasks → prefijo del proyecto: contenedores, red, volúmenes │ ├── services: ← OBLIGATORIO. Cada bloque = un contenedor │ ├── web image, ports, volumes, restart… │ ├── api build, environment, depends_on… │ └── postgres image, volumes, healthcheck… │ ├── networks: → redes declaradas (aquí: harbor-net) │ └── volumes: → volúmenes con nombre (aquí: pgdata) (la declaración no necesita más que el nombre; Docker crea el objeto)

Esta separación en tres planos (servicios, redes, datos) es deliberada: los servicios son lo efímero que se levanta y se tira; las redes y los volúmenes son infraestructura que sobrevive al ciclo de vida de los contenedores.

Clave a clave: de docker run a Compose

Si recuerdas un flag de docker run, ya recuerdas su clave. Eso es lo bueno de Compose: no introduce conceptos nuevos, empaqueta los que ya sabes.

Ojo con container_name

container_name es un nombre globalmente único en todo el Docker Engine: si dos proyectos usan harbor-api, el segundo falla con Conflict. The container name ... is already in use. En un entorno local con varios proyectos es una fuente típica de sustos. La identidad real de un servicio es su nombre de servicio (la clave api:), que es el hostname que usan los demás contenedores. Solo recurre a container_name cuando necesites previsibilidad absoluta.

ports vs expose: publicar no es exponer

ports abre el puerto hacia el host (visible en localhost, y por tanto en la red local). expose solo lo declara dentro de la red de Docker. Regla mental: publicación al exterior = ports; comunicación interna entre servicios = nombre de servicio + puerto interno, sin necesidad de publicar nada.

restart: qué hace el motor si el contenedor muere

Valores: no (default), always, on-failure, unless-stopped. Para servicios largos de un stack local, unless-stopped es la opción cómoda: se reinicia ante caídas y reinicios del motor, pero respeta un stop explícito.

3 · Ejemplo mínimo

Un servicio con las claves básicas, comentado línea a línea. Es el «sujeto de laboratorio» de esta lección:

compose.yaml
name: laboratorio

services:
  web:
    image: nginx:1.27-alpine            # imagen base (no hace falta build)
    container_name: lab-web             # nombre FIJO del contenedor (opcional)
    restart: unless-stopped             # se reinicia solo; respeta un stop manual
    ports:
      - "8080:80"                       # publica host:contenedor (siempre entre comillas)
    environment:                        # variables EN LÍNEA (mapa clave: valor)
      NGINX_HOST: localhost
      NGINX_PORT: "80"
    volumes:
      - ./html:/usr/share/nginx/html:ro # bind mount SOLO LECTURA (:ro) al html
    expose:
      - "80"                            # documenta el puerto dentro de la red

Línea a línea:

  1. name: marca el proyecto; hace de prefijo de contenedores, red y volúmenes. Opcional, pero recomendado.
  2. image: nginx:1.27-alpine: usa una imagen existente (si no está local, pull automático).
  3. container_name: nombre fijo. Útil aquí para ver el efecto; en stacks reales se omite.
  4. restart: unless-stopped: política de reinicio.
  5. ports: ["8080:80"]: publica — el host recibe localhost:8080 y reenvía al puerto 80 del contenedor.
  6. environment: variables que la imagen lee en tiempo de arranque.
  7. volumes: ./html:...:ro: bind mount del directorio local al contenedor, con :ro para inmutabilidad (ver Módulo 3).
  8. expose: documenta el puerto interno; no publica nada al host.

Levántalo, compruébalo y tíralo — el ciclo completo dura segundos:

docker compose up -d          # crea contenedor lab-web y arranca
docker compose ps             # estado: "Up"
curl http://localhost:8080    # responde el html (bind mount)
docker compose exec web sh -c 'echo dentro'   # ejecutar dentro del contenedor
docker compose down           # stop + elimina contenedor y red del proyecto

4 · Ejemplo real

Un stack real: api (Node) + postgres, con claves combinadas. Este layout es el que usará HarborTasks en la lección 4:

compose.yaml
name: harbortasks             # nombre del proyecto (evita "default")

services:
  postgres:
    image: postgres:16-alpine  # versión LTS de Postgres, imagen Alpine ligera
    restart: unless-stopped
    environment:
      POSTGRES_USER: harbor          # el usuario de la base
      POSTGRES_PASSWORD: harborpass  # ⚠ solo para dev; en prod desde Secret (K8s)
      POSTGRES_DB: harbortasks       # la base que creará el entrypoint oficial
    volumes:
      - pgdata:/var/lib/postgresql/data   # volumen con NOMBRE → persistencia real
    expose:
      - "5432"                    # interna: nadie desde el host toca postgres

  api:
    build: ./api                  # construye la imagen desde ./api (Dockerfile)
    image: harbortasks-api:1.0.0   # etiqueta que recibe la imagen construida
    restart: unless-stopped
    environment:
      # La api conecta con "postgres": el NOMBRE DE SERVICIO es el hostname
      DATABASE_URL: postgres://harbor:harborpass@postgres:5432/harbortasks
      PORT: "3000"
    env_file:
      - ./secrets/api.env         # carga más variables desde un archivo (no git)
    depends_on:                   # espera a que postgres exista (orden básico)
      - postgres
    ports:
      - "3000:3000"               # publicado: el navegador/tú lo usáis
    volumes:
      - ./api:/app                # bind mount del código → editas y se refleja

networks: {}                      # vacío: Compose crea el bridge por defecto

volumes:
  pgdata:                         # rellenado por postgres; sobrevive a down

Decisiones tomadas:

  • La api habla con postgres, nunca con localhost: dentro de la red bridge, el DNS de Docker resuelve el nombre de servicio (Módulo 3).
  • build + image: construye el api/Dockerfile y etiqueta el resultado harbortasks-api:1.0.0, para inspeccionarlo o reutilizarlo.
  • Postgres no se publica (expose): el único que debe tocarlo es la api, por red interna. Menos superficie de ataque, incluso en local.
  • env_file separa lo sensible (secrets/api.env, fuera de git) de lo declarativo.

Los comandos del ciclo de vida

# Construye si falta (por el build:) y levanta en segundo plano
docker compose up -d --build

# Inspección: cómo quedó el archivo tras resolverlo (ideal antes de up)
docker compose config            # yaml resuelto: defaults, interpolación y merge
docker compose ps                # servicios, estado y puertos publicados
docker compose logs -f api       # logs de un servicio (sigue con -f)

# Lanzar un comando puntual dentro de un servicio
docker compose exec postgres psql -U harbor -d harbortasks -c "SELECT 1;"

# Bajada completa (conserva el volumen pgdata)
docker compose down              # red y contenedores fuera; el volumen sigue
docker compose down -v           # ⚠ añade la eliminación del volumen (¡adiós datos!)

compose.override.yaml: el archivo de desarrollo automático

Compose tiene una pieza muy práctica: si existe compose.override.yaml junto al compose.yaml, docker compose up lo carga y lo fusiona automáticamente, sin flags. Es el lugar natural para lo que solo quieres en desarrollo:

compose.override.yaml
# Este archivo NO necesita ser invocado: docker compose lo detecta solo
# Regla de fusión: las claves escalares del override ganan a las del base.
services:
  api:
    environment:
      NODE_ENV: development         # pisa el valor del compose.yaml
    command: npm run dev            # arranque de desarrollo (hot reload)
    volumes:
      - ./api/src:/app/src          # añade bind mounts extra para dev
Fusiona, no reemplaza

Claves escalares (como command:) se reemplazan; listas como volumes: o ports: se concatenan con las del base. Para entornos distintos puedes forzar archivos a mano: docker compose -f compose.yaml -f compose.prod.yaml up -d (lo usarás en la lección 4).

6 · Errores habituales

Indentación con tabuladores

# ❌ MAL: el tab no está permitido en YAML
services:
	web:                            
		image: nginx:1.27-alpine

# ✅ BIEN: espacios, anidados cada 2
services:
  web:
    image: nginx:1.27-alpine

Confundir expose con ports

# ❌ MAL: solo "expose" → el navegador no llega desde localhost
services:
  web:
    image: nginx:1.27-alpine
    expose:
      - "80"
    # ❌ error típico: curl http://localhost:80 → connection refused

# ✅ BIEN: "ports" publica al host
services:
  web:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"

Fijar container_name sin necesidad (y chocar con otro proyecto)

# ❌ un segundo proyecto que también quiera "harbor-api" fallará:
#    Error response: Conflict. The container name "/harbor-api" is already in use

# ✅ los demás servicios usan el NOMBRE DE SERVICIO; sin container_name
docker compose up -d
docker compose ps   # harbor-api-1  ← Compose añade "-1" solo, sin colisiones

Olvidar que down no borra volúmenes (y luego sorprenderse)

# Si "sube" con el volumen viejo y ves datos de otra época NO es un bug:
docker compose down     # conserva pgdata a propósito
docker compose up -d    # postgres monta los MISMOS datos de antes

# Si de verdad quieres empezar de cero, sé consciente:
docker compose down -v  # ⚠ elimina también el volumen pgdata

7 · Ejercicio guiado

Objetivo: montar un nginx con bind mount, editarlo «en vivo» y explotar los comandos de inspección de Compose.

  1. Prepara el proyecto: 
    mkdir -p ~/proyectos/webserver/html && cd ~/proyectos/webserver
echo '<h1>Hola desde mi volumen</h1>' > html/index.html
  2. Crea compose.yaml con el servicio web del «ejemplo mínimo» (imagen nginx:1.27-alpine, ports: ["8080:80"], bind mount ./html:/usr/share/nginx/html:ro).
  3. Valida antes de arrancar: 
    docker compose config    # fíjate en los campos "resueltos" y en el prefijo del proyecto
  4. Levanta y verifica: 
    docker compose up -d
docker compose ps
curl http://localhost:8080    # → <h1>Hola desde mi volumen</h1>
  5. Edita el html SIN tocar el contenedor y recarga: 
    echo '<h1>Cambiado en caliente</h1>' > html/index.html
curl http://localhost:8080    # → el bind mount refleja el cambio al instante
  6. Ejecuta dentro del contenedor y baja el stack: 
    docker compose exec web ls /usr/share/nginx/html  # ves tu archivo montado
docker compose down

🎯 Variables de entorno y override para dos entornos

Añade a tu compose.yaml un servicio api (imagen node:22-alpine, command: node -v) con una variable GREETING cargada desde un env_file llamado .env.api. Después crea un compose.override.yaml que ponga GREETING a hello-override cuando se levante con docker compose up, y comprueba con docker compose exec api printenv GREETING qué valor gana.

9 · Resumen

  • El compose.yaml tiene tres planos: services (obligatorio), networks y volumes, además del opcional name.
  • Cada clave de servicio traduce un flag de docker run: ports=-p, environment=-e, volumes=-v, restart=--restart, container_name=--name.
  • ports publica al host; expose solo declara el puerto interno.
  • Los servicios se hablan por nombre de servicio (DNS de la red), no por localhost ni por IP.
  • compose.override.yaml se fusiona automáticamente: ideal para cosas de desarrollo.
  • down conserva volúmenes; down -v los borra — úsalo con intención.

10 · Preguntas frecuentes

¿Por qué los puertos deben ir entre comillas en YAML?

Porque YAML interpreta 8080:80 como la sintaxis de un mapping o como un número en algunos contextos (por ejemplo rangos 8000-8010). Entre comillas queda forzado a ser un string tal cual: "8080:80". Es la convención de todos los compose reales.

¿Qué es el prefijo del proyecto que veo en docker compose ps?

Compose nombra contenedores, red y volúmenes con el nombre del proyecto como prefijo: harbortasks-api-1, red harbortasks_default u harbortasks_harbor-net, etc. El nombre del proyecto sale de name: o, si no, del nombre de la carpeta. Así varios proyectos conviven sin pisarse.

¿Cuándo uso build y cuándo image?

image: basta cuando usas una imagen ya construida (nginx, postgres, tu imagen publicada). build: cuando quieres construir desde un Dockerfile local; normalmente lo combinas con image: para etiquetar el resultado. Compose reconstruye solo cuando indicas --build.

¿Qué diferencia hay entre environment, env_file y el .env del proyecto?

environment mete variables dentro del contenedor; env_file las carga de un archivo también hacia el contenedor. El archivo .env del proyecto (en la misma carpeta) es diferente: lo usa Compose para interpolar el propio YAML (${VAR}). En la lección 4 lo usarás para dev/prod.

¿docker compose down borra las imágenes construidas?

No. down elimina contenedores y red (y volúmenes con -v), pero las imágenes quedan en el cache local: docker image ls y reutilizarlas es instantáneo. Las imágenes se limpian con docker image prune, otro tema.
