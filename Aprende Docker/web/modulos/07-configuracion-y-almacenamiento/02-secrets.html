Secrets

Módulo 7 · Configuración y almacenamiento ⏱ 35 minutos

1 · Introducción

El ConfigMap resuelve la configuración no sensible. Pero HarborTasks necesita algo más: una contraseña para PostgreSQL. En un ConfigMap esa contraseña quedaría en texto plano, visible para cualquiera con acceso al clúster. Kubernetes define un objeto hermano, el Secret (apiVersion: v1, kind: Secret), pensado para credenciales, tokens, claves TLS y conexiones a bases de datos.

En esta lección verás por qué el Base64 no es cifrado (la confusión #1 del mundo Kubernetes), los tipos de Secret, cómo crearlos con --from-literal, --from-env-file y manifiestos, cómo consumirlos (env y volúmenes) y qué mejoras usa la industria: Sealed Secrets, External Secrets Operator y KMS.

¿Por qué existe esta lección? Porque los secretos comprometidos en Git son la causa más común de brechas de seguridad en startups. Un manifiesto con una contraseña en texto plano termina en GitHub y un escáner (o un bot) la encuentra. Saber qué protege Kubernetes y qué NO, y cómo elevar la seguridad en producción, te evita el «secreto en el commit» de por vida.

2 · Teoría

Qué es un Secret y por qué Base64 NO es cifrado

Un Secret es, internamente, un mapa clave-valor muy parecido a un ConfigMap, pero con una semántica y un tratamiento distintos. Al crearlo, Kubernetes guarda los valores en Base64. Y aquí está el malentendido clásico:

Analogía: Base64 es como escribir tu contraseña en braille: cambia la forma de representarla, pero cualquiera que conozca braille (o una herramienta de decoding) la lee al instante. No es cifrado, es codificación. Cifrar requiere una clave secreta; codificar solo requiere un algoritmo público.

El Base64 existe por una razón técnica, no de seguridad: los valores de un Secret son bytes arbitrarios (un certificado, una clave privada, un token binario). YAML es texto; Base64 convierte esos bytes en texto seguro. Internamente, el API server usa la misma representación para almacenarlo en etcd.

Ojo: kubectl get secret <nombre> -o yaml devuelve los valores en Base64. «Tener un secreto» en Kubernetes no significa cifrado: significa un objeto con permisos RBAC específicos, no expuesto en describe por defecto y con la opción de cifrarse en reposo (etcd encryption).

Tipos de Secret

El campo type indica el propósito y cómo se gestiona. El más común es Opaque (datos arbitrarios clave-valor). Otros tipos predefinidos:

typePara quéClaves típicas
OpaqueCualquier par clave-valor: contraseñas, tokens, API keysPOSTGRES_PASSWORD, DATABASE_URL
kubernetes.io/tlsCertificados TLS para Ingress (ver lección 04)tls.crt, tls.key
kubernetes.io/dockerconfigjsonCredenciales para registry (pull de imágenes privadas).dockerconfigjson
kubernetes.io/basic-authAutenticación básica HTTPusername, password
kubernetes.io/ssh-authClaves SSHssh-privatekey

Cómo se consumen

Igual que los ConfigMaps, por env (con secretKeyRef) o por volumen (cada clave es un archivo). Detalle importante: cuando un Secret se monta como volumen, las claves se materializan como archivos ya decodificados (Base64 → bytes originales). Así tu aplicación lee la contraseña tal cual espera. Con env ocurre lo mismo: la variable contiene el valor decodificado.

El camino a producción: Sealed Secrets, External Secrets, KMS

  • Sealed Secrets (Bitnami): un operador que cifra tus secretos con una clave pública en Git. Commiteas un SealedSecret cifrado; el operador dentro del clúster lo descifra y crea el Secret. Soluciona «no comprometer secretos en Git» manteniendo GitOps.
  • External Secrets Operator (ESO): los secretos viven en un gestor externo (Vault, AWS Secrets Manager, GCP Secret Manager) y un operador los trae al clúster mediante CRDs. El clúster no guarda secretos: solo referencias.
  • KMS y cifrado en reposo: etcd puede cifrar todos los objetos (incluidos Secrets) con una clave gestionada por un KMS (p. ej. AWS KMS). Oculta el valor incluso a quien acceda a etcd directamente.

Para el curso local (kind) usamos Secrets nativos: suficiente para aprender. En el módulo 8 verás restricciones RBAC; aquí nos centramos en crear y consumir sin destripar el clúster de casa.

3 · Ejemplo mínimo

# Crear un Secret Opaque con dos literales
kubectl create secret generic mi-secreto \
  --from-literal=Usuario=ana \
  --from-literal=Password=P4s$$w0rd!

# Verlo codificado (Base64) — NO es el valor real, es la representación
kubectl get secret mi-secreto -o yaml

# Ver el valor real descifrado con kubectl + base64 --decode
kubectl get secret mi-secreto -o jsonpath='{.data.Password}' | base64 --decode

Manifiesto equivalente (declarativo, igual de válido):

apiVersion: v1
kind: Secret
metadata:
  name: mi-secreto
type: Opaque                        # datos arbitrarios clave-valor
data:
  # ⚠ los valores van codificados en Base64 en el manifiesto
  Usuario: YW5h
  Password: UDRzJCR3MHJkIQ==        # "P4s$$w0rd!" codificado

Claves a entender:

  • type: Opaque → el tipo general de credenciales.
  • data → versiones Base64 (requisito: texto). Existe también stringData, que permite escribir valores en texto plano YAML y el API server los codifica por ti. Muy útil en manifiestos de desarrollo.
  • La decodificación con base64 --decode demuestra que cualquiera con acceso al objeto (o al -o yaml de alguien) puede leer el secreto. La protección real es RBAC + buen hábito, no el formato.

4 · Ejemplo real

La contraseña de PostgreSQL de HarborTasks. Vamos a crear un Secret pg-secret con las credenciales y a consumirlo desde el Deployment de postgres y desde el de la API (que necesita la contraseña para construir su DATABASE_URL).

secret-pg.yaml
apiVersion: v1
kind: Secret
metadata:
  name: pg-secret
  namespace: harbortasks
type: Opaque
stringData:                  # stringData: texto plano, el API lo codifica solo
  POSTGRES_USER: api         # usuario de la BBDD
  POSTGRES_PASSWORD: S3cr3t!DePrueba   # contraseña (en kind, es local)
  # NOTA PARA PRODUCCIÓN: un manifiesto con la contraseña NO debe ir a Git.
  # Si usas GitOps, cambia a SealedSecret o External Secret (ver teoría).
deployment-postgres.yaml (fragmento)
spec:
  template:
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          env:
            - name: POSTGRES_USER          # el entrypoint de la imagen espera estas vars
              valueFrom:
                secretKeyRef:
                  name: pg-secret          # del Secret pg-secret
                  key: POSTGRES_USER       # toma la clave POSTGRES_USER
                  optional: false          # si falta, el Pod no arranca
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: pg-secret
                  key: POSTGRES_PASSWORD
deployment-api.yaml (fragmento) — pasando la clave como archivo
spec:
  template:
    spec:
      containers:
        - name: api
          image: harbortasks-api:1.0.0
          # La app lee /run/secrets/db_password como archivo (patrón 12-factor)
          volumeMounts:
            - name: pg-creds
              mountPath: /run/secrets/db_password   # directorio que expondrá la clave
              readOnly: true
          env:
            - name: PGDATABASE_USER
              valueFrom:
                secretKeyRef:
                  name: pg-secret
                  key: POSTGRES_USER
      volumes:
        - name: pg-creds
          secret:
            secretName: pg-secret           # cada clave del Secret = un archivo
            defaultMode: 0400               # solo lectura para el owner (mejora seguridad)

Env vs volumen: con env la variable se fija al crear el contenedor (no cambia aunque rotes el Secret). Con volumen, el kubelet sincroniza los archivos periódicamente: aplicaciones que leen el secreto en cada petición (p. ej. un pool de conexiones nuevo) toleran la rotación sin reiniciar. Es el patrón que usan apps modernas.

5 · Buenas prácticas

HazEvitaPor qué
Crea secretos con kubectl create secret generic … --from-env-file=.env Escribir la contraseña a mano en el manifiesto --from-env-file mantiene el valor fuera del YAML; tú controlas su rotación
Usa stringData en manifiestos de desarrollo stringData en producción con Git En dev la claridad gana; en prod el secreto debe vivir fuera del repo
Añade .env y manifiestos con secretos a .gitignore Commitear .env, secret-*.yaml o archivos con tokens Los repos son históricos: borrar después no elimina el secreto del historial
Monta secretos como volumen con defaultMode: 0400 Permisos mundo-lectura (0444) en montajes secret Principio de menor privilegio: quien accede al Pod no debe leer password de otro
Limita el acceso con RBAC (scope del Secret) Secretos globales accesibles por todo el clúster El acceso al Secret debe limitarse solo a los Pods que lo necesitan
En producción: Sealed Secrets / External Secrets / KMS Confiar en que Base64 «protege» algo El cifrado real evita el «rótulo con sesgo» de tener secretos en repos y en etcd en claro

Windows (WSL2): para decodificar base64 usa los binarios Linux dentro de WSL: kubectl get secret pg-secret -o jsonpath='{.data.POSTGRES_PASSWORD}' | base64 --decode. En PowerShell, el comando base64 no existe (usa [Convert]::FromBase64String), así que trabaja dentro de la distro.

6 · Errores habituales

❌ Creer que el Base64 de un Secret lo protege

# ❌ "el secreto está cifrado, miro el YAML" — el valor codificado sale en claro
kubectl get secret pg-secret -o yaml | grep POSTGRES_PASSWORD
# → POSTGRES_PASSWORD: UzNjcjMhRGVQcnVlYmE=

# ✅ un simple decode revela todo; la protección real es RBAC + hábito
kubectl get secret pg-secret \
  -o jsonpath='{.data.POSTGRES_PASSWORD}' | base64 --decode
# → S3cr3t!DePrueba

❌ Valores con caracteres especiales en --from-literal sin escapar

# ❌ el '$' y espacios provocan expansión o cortes de shell
kubectl create secret generic pg-secret \
  --from-literal=POSTGRES_PASSWORD=S3cr3t! $DePrueba

# ✅ usa comillas simples para que el shell no expanda $ ni corte espacios
kubectl create secret generic pg-secret \
  --from-literal=POSTGRES_PASSWORD='S3cr3t! $DePrueba'

# ✅ o mejor: --from-env-file con un .env versionado fuera de Git
echo 'POSTGRES_PASSWORD=S3cr3t!$DePrueba' \
  | kubectl create secret generic pg-secret --from-env-file=/dev/stdin

❌ Enviar el manifiesto con el secreto en claro a un repo público

# ❌ secret.yaml con la password en el historial de Git
apiVersion: v1
kind: Secret
metadata:
  name: pg-secret
data:
  POSTGRES_PASSWORD: UzNjcjMhRGVQcnVlYmE=

# ✅ patrón GitOps: el manifiesto referencia a una herramienta que lo cifra
#    (SealedSecret, ExternalSecret) — el valor real nunca pisa el repo.
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: pg-secret
spec:
  encryptedData:
    POSTGRES_PASSWORD: AgBd3+KL…   # cifrado con la clave pública del clúster

❌ Redactar mal el nombre de una clave en secretKeyRef

Si la clave no existe en el Secret, el Pod falla con CreateContainerConfigError (si optional: false). Sucede mucho al renombrar claves tras una rotación. Verifica siempre con kubectl describe secret pg-secret (lista de claves) o kubectl get secret pg-secret -o jsonpath='{.data}'.

7 · Ejercicio guiado

Objetivo: crear un Secret, montarlo como volumen y como variable, y verificar ambos dentro de un Pod de pruebas.

  1. Crea el Secret con un archivo .env: 
    # contenido de .env (¡NO lo commitees!)
# API_KEY=abc-123
# TIMEOUT=30
kubectl create secret generic app-creds --from-env-file=.env
kubectl get secret app-creds
kubectl describe secret app-creds      # solo muestra "3 bytes" y las claves
  2. Lanza un Pod busybox que monte el Secret y lea una variable: 
    kubectl run secret-test --image=busybox --restart=Never --command -- sleep 3600
  3. Edita el Pod y añade: 
              env:
            - name: API_KEY
              valueFrom:
                secretKeyRef:
                  name: app-creds
                  key: API_KEY
          volumeMounts:
            - name: creds
              mountPath: /secrets
              readOnly: true
          volumes:
            - name: creds
              secret:
                secretName: app-creds
  4. Verifica dentro del Pod: 
    kubectl exec secret-test -- env | grep API_KEY
kubectl exec secret-test -- ls -la /secrets
kubectl exec secret-test -- cat /secrets/TIMEOUT

    Resultado esperado: la variable API_KEY con el valor claro, y en /secrets un archivo por clave (API_KEY, TIMEOUT) con el contenido ya decodificado. ✔ Si ves ls solo con permisos r-xr-xr-x es normal según el defaultMode.

  5. Limpia: kubectl delete pod secret-test y kubectl delete secret app-creds.

8 · Reto

🎯 Secreto como archivo con clave no válida para env

Algunos nombres de clave (con puntos, guiones o espacios) NO se pueden usar como variable de entorno, pero sí como nombre de archivo montado. Crea un Secret config-certs con una clave llamada server.crt (un certificado simulado) y monta solo esa clave en /etc/myapp/certs/server.crt, sin montar el resto del Secret. Pista: en spec.template.spec.volumes[0].secret.items se define qué claves se montan y bajo qué nombre de archivo.

Pista: items: con key: server.crt y path: server.crt; y un volumeMounts con mountPath: /etc/myapp/certs. Para la clave usada como env, recuerda que env exige nombres de variable válidos.

9 · Resumen

  • El Secret guarda credenciales como clave-valor en Base64; el Base64 es codificación, no cifrado.
  • Tipos comunes: Opaque (credenciales genéricas), kubernetes.io/tls, dockerconfigjson…
  • Creación: --from-literal, --from-env-file, o manifiesto con stringData (texto claro que el API codifica).
  • Consumo: env.secretKeyRef (variable) o volumen (archivo sincronizado, mejor para rotación).
  • No comprometer secretos en Git: Sealed Secrets, External Secrets Operator y KMS cifran lo que Kubernetes no cifra por defecto.
  • La seguridad real es RBAC + gestión de rotación + no exponer en repos.

kubectl create secret generic <n> --from-env-file=.envCrea un Secret desde archivo .env

10 · Preguntas frecuentes

¿El Secret está cifrado dentro del clúster?

No por defecto. En kind/instalaciones estándar, etcd guarda el objeto tal cual (en Base64, pero no cifrado). La seguridad viene del control de acceso (RBAC) y del cifrado en reposo que puedes activar (--encryption-provider-config + KMS) o delegar con External Secrets.

¿Puedo usar un Secret dentro de un ConfigMap o al revés?

Son objetos independientes. Un pod no puede «importar» un ConfigMap dentro de un Secret. Lo que sí puedes hacer es montar ambos en el mismo Pod: uno para config no sensible (URLs, flags) y otro para lo sensible (contraseñas). Es lo que hace HarborTasks.

¿Qué pasa si rotar la contraseña de postgres?

Aplica el nuevo Secret (por ej. stringData nuevo) y reinicia los Deployments que lo consumen por env. Con montajes por volumen, muchos clientes (pgBouncer, algunos ORMs) detectan el archivo nuevo sin reiniciar. Después, postgres debe aceptar la nueva contraseña: requiere una rotación coordinada (password en postgres + Secret), y ese es uno de los motivos por los que en producción se usan secret managers centralizados.

¿Los Secrets se borran si borro el namespace?

Sí. Los Secrets (y ConfigMaps) son namespace-scoped: al borrar el namespace se eliminan todos sus objetos, incluidos los secretos. Borra primero los Deployments o trabaja en el namespace correcto. Los PersistentVolumes (lección 03) sí son cluster-scoped y no se borran con el namespace.

¿Cuándo se usa un Secret mount en lugar de env?

Cuando quieres (a) rotación en caliente (el archivo se sincroniza), (b) archivos que no son texto (certificados, claves), o (c) claves con nombres no válidos para variables. Env es más cómodo para credenciales «solas» (password de postgres). Ninguno es «más seguro» por sí mismo: la seguridad es RBAC + no exponer en repos.
