Persistencia y auth

Módulo 7 · Proyecto final: Copiloto API 🕐 45 minutos

1 · Introducción

Copiloto API responde y registra consultas, pero hoy cualquiera puede llamarlo y el histórico lo ve todo el mundo. Esta lección cierra las dos grietas: quién pregunta y qué se guarda de esa pregunta. Añadimos un modelo User, enlazamos QueryLog con su dueño mediante una clave foránea, versionamos el cambio con Alembic y protegemos los endpoints con JWT y roles.

Son dos temas que en el curso viven en módulos distintos —persistencia (Módulo 4) y seguridad (Módulo 5)— pero que en un proyecto real van de la mano: una columna owner_id sin autenticación no sirve de nada, y un token sin un usuario en la base de datos no puede autorizar nada.

¿Por qué existe esta lección? Porque aquí se vuelve concreto el modelo de amenazas. Un endpoint público de RAG es caro (cada llamada mueve un modelo) y filtra el histórico de otros usuarios. Autenticar no es burocracia: es lo que permite facturar, limitar el abuso, auditar y aislar datos. Y hacerlo con migraciones versionadas es lo que permite aplicar el mismo cambio en tu portátil y en producción sin tocar una línea de SQL a mano.

Errores típicos que evitamos: guardar la contraseña (o su hash) con una comparación ==, desactivar la verificación del token «para que funcione», confiar en el rol que viene dentro del JWT en lugar de en la base de datos, y responder 403 a un recurso ajeno revelando que existe.

2 · Teoría

El histórico con dueño

El histórico no es una tabla suelta: es el registro de quién preguntó qué, cuándo y con qué coste. Con la autenticación, cada fila gana un owner_id. Esa clave foránea es la bisagra entre las dos mitades de la lección.

   users                          query_log
   ┌────┬───────────────┬───────┐   ┌────┬──────────────┬──────────┐
   │ id │ email         │ role  │   │ id │ question     │ owner_id │
   ├────┼───────────────┼───────┤   ├────┼──────────────┼──────────┤
   │ 1  │ ana@academy…  │ user  │◄──┤ 7  │ ¿Qué es ASGI?│ 1        │
   │ 2  │ root@academy… │ admin │◄──┤ 8  │ ¿Y SQLModel? │ 2        │
   └────┴───────────────┴───────┘   └────┴──────────────┴──────────┘
           1 : N  (un usuario tiene muchas consultas)

¿Por qué owner_id y no guardar el email en el log? Porque el email puede cambiar y porque una clave foránea garantiza la integridad referencial: no puedes tener una consulta de un usuario que no existe. Guardar datos duplicados es cómodo hasta que se desincronizan.

De modelo a tabla: el diff de Alembic

Añadir un modelo en Python no cambia la base de datos. El esquema real es un contrato persistente que solo cambia con una migración. El flujo de este módulo es siempre el mismo:

   1. editas app/models.py             (modelo nuevo: User, y owner_id en QueryLog)
              │
   2. uv run alembic revision --autogenerate -m "…"
              │                        → Alembic compara metadata vs BD real
              ▼
   3. LEES migrations/versions/xxxx.py  (y corriges lo que haga falta)
              │
   4. uv run alembic upgrade head       → aplica en tu base de datos
              │
   5. el MISMO fichero aplica el cambio en producción (mismo código, otra URL)

Añadir una columna NOT NULL a una tabla con datos falla. No hay valor para las filas existentes. El patrón en tres pasos es: añadirla nullable, rellenar (UPDATE … SET owner_id = …) y luego hacerla NOT NULL en una segunda migración. En SQLite, además, los ALTER complejos necesitan batch mode (Módulo 4, lección 3).

Contraseñas: hash, nunca cifrado reversible

Un hash es una función de un solo sentido: de la contraseña se obtiene una cadena, pero de la cadena no se vuelve a la contraseña. Al registrarte se guarda el hash; al hacer login se vuelve a calcular y se comparan. Nunca se guarda la contraseña, ni «cifrada», ni en ningún formato que se pueda descifrar.

Además, el hash debe ser lento y salado para resistir ataques por diccionario o tablas precalculadas. bcrypt es el estándar: incluye salt por contraseña y un coste configurable. passlib con el esquema bcrypt lo gestiona todo:

app/security.py (fragmento)
from passlib.context import CryptContext

_pwd = CryptContext(schemes=["bcrypt"], deprecated="auto")


def hash_password(password: str) -> str:
    return _pwd.hash(password)          # el salt va dentro del propio hash


def verify_password(password: str, hashed: str) -> bool:
    return _pwd.verify(password, hashed)   # comparación en tiempo constante

Dependencia concreta, no abstracta: este proyecto usa passlib[bcrypt], como indica la spec del curso. Con bcrypt 4.1 o superior, passlib 1.7.4 emite un aviso al leer su versión (AttributeError: module 'bcrypt' has no attribute '__about__'); es inofensivo pero ruidoso. Si te molesta, fija bcrypt<4.1 en pyproject.toml o migra a pwdlib, que es la alternativa moderna. Lo acotas y lo documentas: el hash no es donde conviene improvisar.

OAuth2 password flow y JWT

El password flow es el flujo estándar de OAuth2 para clientes de confianza (el propio front, una CLI, Swagger UI). Tiene dos pasos:

   POST /auth/token                        (form-urlencoded: username + password)
        │
        ▼
   ¿usuario existe y verify_password pasa?  ──no──►  401
        │ sí
        ▼
   firmar JWT { sub: email, role, iat, exp }  ──►  { access_token, token_type: "bearer" }
        │
        ▼
   Cliente:  Authorization: Bearer <token>
        │
        ▼
   Cada endpoint protegido:  decode + buscar usuario en BD  ──►  User

El JWT tiene tres partes (header.payload.signature). El payload no está cifrado: cualquiera puede leerlo. Su valor es la firma: si alguien modifica un byte del payload, la firma deja de validar. Los claims que usamos:

ClaimSignificadoPor qué importa
subSujeto: el identificador del usuario (aquí, su email)Es a quién pertenece el token
roleRol en el momento de emitirloCómodo, pero puede quedar obsoleto: revalida contra la BD
iatEmitido en (issued at)Permite auditar y calcular antigüedad
expCaduca en (expiration)Es la red de seguridad: un token robado no vale para siempre

¿Por qué el token caduca? Porque es un «pase» que el portador puede robar (un log, un historial, un dispositivo compartido) y no se puede revocar uno a uno. Caducarlo pronto reduce la ventana de abuso. Como eso obliga a loguearse a menudo, los sistemas reales combinan un access token corto con un refresh token largo (el reto de esta lección).

Autorización: get_current_user y roles

Autenticación («¿quién eres?») y autorización («¿puedes hacer esto?») son dos pasos encadenados de dependencias. El primero valida el token y devuelve el usuario; el segundo comprueba su rol:

   OAuth2PasswordBearer  ──token──►  get_current_user  ──User──►  require_role("admin")
        │                            (decode + BD)                    │
        └── sin cabecera → 401                                        └── rol insuficiente → 403

Revalida el usuario contra la base de datos. El JWT es una prueba de identidad pasada: fue cierto cuando se emitió. Si el usuario fue borrado, o si su rol cambió, el token sigue diciendo lo de antes hasta que caduque. Buscar al usuario en cada petición (una consulta indexada por email, muy barata) hace que la autorización refleje el estado real. Es la diferencia entre «el token dice que es admin» y «es admin».

3 · Ejemplo mínimo

El ciclo completo de la seguridad en un fichero: hashear, emitir un token y verificarlo. Sin FastAPI todavía, para ver la mecánica desnuda.

security_min.py
from datetime import datetime, timedelta, timezone

import jwt
from passlib.context import CryptContext

_pwd = CryptContext(schemes=["bcrypt"], deprecated="auto")

# En el proyecto esto viene de Settings, nunca del código.
SECRET_KEY = "una-clave-secreta-de-al-menos-32-caracteres"
ALGORITHM = "HS256"


def hash_password(password: str) -> str:
    return _pwd.hash(password)


def verify_password(password: str, hashed: str) -> bool:
    return _pwd.verify(password, hashed)


def create_token(email: str, role: str = "user") -> str:
    now = datetime.now(timezone.utc)
    payload = {"sub": email, "role": role, "iat": now,
               "exp": now + timedelta(minutes=30)}
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)


def decode_token(token: str) -> dict:
    return jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])


# --- Prueba del ciclo -------------------------------------------------------
hashed = hash_password("s3cret")
print(hashed.startswith("$2b$"))                      # True  (bcrypt)
print(verify_password("s3cret", hashed))              # True
print(verify_password("otra", hashed))                # False

token = create_token("ana@academy.dev")
print(decode_token(token)["sub"])                     # ana@academy.dev

# Un token manipulado o caducado lanza una excepción:
try:
    decode_token(token + "x")
except jwt.InvalidTokenError as exc:
    print("rechazado:", type(exc).__name__)

Salida esperada:

True
True
False
ana@academy.dev
rechazado: DecodeError

Lo esencial, línea por línea:

  1. _pwd.hash(password): genera un hash distinto cada vez (lleva salt dentro, empieza por $2b$). Dos usuarios con la misma contraseña tienen hashes distintos.
  2. _pwd.verify(password, hashed): verifica comparando en tiempo constante. Nunca compares con ==, y desde luego no compruebes la contraseña en claro.
  3. datetime.now(timezone.utc): la fecha con zona, como en el histórico. PyJWT exige que exp sea un instante válido.
  4. jwt.encode(payload, key, algorithm): firma el payload. La clave viene de Settings y nunca del código.
  5. jwt.decode(token, key, algorithms=[...]): valida la firma y la caducidad, y restringe el algoritmo aceptado. Omitir algorithms o pasar None abre la puerta a ataques de confusión de algoritmo.

app/security.py
from datetime import datetime, timedelta, timezone

import jwt
from passlib.context import CryptContext

from app.config import Settings

_pwd = CryptContext(schemes=["bcrypt"], deprecated="auto")


def hash_password(password: str) -> str:
    return _pwd.hash(password)


def verify_password(password: str, hashed: str) -> bool:
    return _pwd.verify(password, hashed)


def create_access_token(subject: str, settings: Settings, role: str = "user") -> str:
    now = datetime.now(timezone.utc)
    payload = {
        "sub": subject,
        "role": role,
        "iat": now,
        "exp": now + timedelta(minutes=settings.access_token_expire_minutes),
    }
    return jwt.encode(payload, settings.secret_key, algorithm=settings.algorithm)


def decode_token(token: str, settings: Settings) -> dict[str, object]:
    """Valida firma y caducidad. Lanza jwt.InvalidTokenError si algo falla."""
    return jwt.decode(token, settings.secret_key, algorithms=[settings.algorithm])
app/deps.py (fragmento de seguridad)
import jwt
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
from sqlmodel import select

from app.models import User
from app.security import decode_token

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/token")


def get_current_user(
    token: Annotated[str, Depends(oauth2_scheme)],
    session: SessionDep,
    settings: SettingsDep,
) -> User:
    """Autenticación: token válido → usuario real de la base de datos."""
    credentials_error = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Credenciales no válidas",
        headers={"WWW-Authenticate": "Bearer"},
    )
    try:
        payload = decode_token(token, settings)
    except jwt.InvalidTokenError:
        raise credentials_error from None

    email = payload.get("sub")
    if not isinstance(email, str):
        raise credentials_error

    user = session.exec(select(User).where(User.email == email)).first()
    if user is None:                      # usuario borrado pero token aún válido
        raise credentials_error
    return user


CurrentUserDep = Annotated[User, Depends(get_current_user)]


def require_role(role: str):
    """Autorización: fabrica una dependencia que exige un rol concreto."""
    def checker(user: CurrentUserDep) -> User:
        if user.role != role:             # rol REAL, no el del token
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="Permisos insuficientes",
            )
        return user
    return checker


AdminDep = Annotated[User, Depends(require_role("admin"))]
app/routers/auth.py
from typing import Annotated

from fastapi import APIRouter, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordRequestForm
from sqlmodel import select

from app.deps import SessionDep, SettingsDep
from app.models import User
from app.schemas import TokenResponse
from app.security import create_access_token, verify_password

router = APIRouter()


@router.post("/token", response_model=TokenResponse)
def login(
    form: Annotated[OAuth2PasswordRequestForm, Depends()],
    session: SessionDep,
    settings: SettingsDep,
) -> TokenResponse:
    """OAuth2 password flow: recibe form-urlencoded, devuelve el access token."""
    user = session.exec(select(User).where(User.email == form.username)).first()
    if user is None or not verify_password(form.password, user.hashed_password):
        # Mismo error para «no existe» y «contraseña mal»: no damos pistas.
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Usuario o contraseña incorrectos",
            headers={"WWW-Authenticate": "Bearer"},
        )

    token = create_access_token(user.email, settings, role=user.role)
    return TokenResponse(access_token=token)

@router.post("", response_model=AskResponse)
def ask(
    payload: AskRequest,
    engine: EngineDep,
    session: SessionDep,
    user: CurrentUserDep,          # ← sin token, este endpoint es 401
) -> AskResponse:
    started = time.perf_counter()
    result = engine.answer(payload.question, payload.module_slug)
    latency_ms = int((time.perf_counter() - started) * 1000)

    log = QueryLog(
        question=payload.question,
        answer=result.text,
        module_slug=payload.module_slug,
        latency_ms=latency_ms,
        owner_id=user.id,          # ← el histórico ya tiene dueño
    )
    session.add(log)
    session.commit()
    session.refresh(log)

    return AskResponse(answer=result.text, sources=result.sources,
                       latency_ms=latency_ms, log_id=log.id)
app/routers/logs.py
from fastapi import APIRouter, HTTPException, Query, status
from sqlmodel import select

from app.deps import AdminDep, CurrentUserDep, SessionDep
from app.models import QueryLog
from app.schemas import QueryLogPublic

router = APIRouter()


@router.get("", response_model=list[QueryLogPublic])
def list_my_logs(
    user: CurrentUserDep,
    session: SessionDep,
    limit: int = Query(default=20, ge=1, le=100),
) -> list[QueryLog]:
    """Solo el histórico del usuario autenticado."""
    statement = (
        select(QueryLog)
        .where(QueryLog.owner_id == user.id)
        .order_by(QueryLog.created_at.desc())
        .limit(limit)
    )
    return list(session.exec(statement).all())


@router.get("/all", response_model=list[QueryLogPublic])
def list_all_logs(
    admin: AdminDep,          # ← rol admin; si no, 403
    session: SessionDep,
    limit: int = Query(default=50, ge=1, le=200),
) -> list[QueryLog]:
    statement = select(QueryLog).order_by(QueryLog.created_at.desc()).limit(limit)
    return list(session.exec(statement).all())


@router.get("/{log_id}", response_model=QueryLogPublic)
def get_log(log_id: int, user: CurrentUserDep, session: SessionDep) -> QueryLog:
    log = session.get(QueryLog, log_id)
    # 404, no 403: no revelamos que un recurso ajeno existe.
    if log is None or log.owner_id != user.id:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Consulta no encontrada",
        )
    return log

Migrar y crear el primer usuario. Con la migración aplicada (uv run alembic upgrade head), crea el primer usuario con un script que use hash_password; nunca insertes la contraseña a mano en SQL. Lo tienes en el ejercicio guiado.

Decisiones y porqués:

  • hashed_password, no password: el nombre del campo deja claro qué se guarda. Un password con un hash dentro es una trampa para el siguiente que lea el código.
  • role como cadena: para dos roles (user, admin) un str con valores acotados basta; si crecen, un Enum de Python o una tabla de roles. El token lleva el rol, pero la autorización lee user.role de la BD.
  • Un mismo 401 para «no existe» y «contraseña mal»: no ayudamos a enumerar usuarios.
  • get_log responde 404 a un recurso ajeno: un 403 confirmaría que existe. Para datos privados, el 404 uniforme es la política habitual.
  • limit acotado con Query(ge=1, le=100): sin techo, un cliente puede pedir «todo el histórico». El límite es una barrera de coste y de memoria.
  • Migración en dos tiempos para owner_id: primero nullable. Cuando decidas cerrar la relación, una segunda migración con backfill la hará NOT NULL.

6 · Errores habituales

Comparar contraseñas a mano

✗ Incorrecto
user = session.exec(select(User).where(User.email == form.username)).first()
if user is None or user.password == form.password:      # ¿en claro? ¿con ==?
    token = create_access_token(user.email, settings)
✓ Correcto
if user is None or not verify_password(form.password, user.hashed_password):
    raise HTTPException(status_code=401, detail="Usuario o contraseña incorrectos")
token = create_access_token(user.email, settings, role=user.role)

Si guardas la contraseña en claro, una filtración de la base de datos es un desastre. Y si guardas el hash pero comparas con ==, no verificas el coste ni el salt de bcrypt, además de comparar en tiempo variable (que filtra información). Usa siempre verify_password.

Desactivar la verificación del token

✗ Incorrecto
payload = jwt.decode(
    token, settings.secret_key,
    options={"verify_signature": False},   # «el token de mi front falla, lo quito»
)
return payload["sub"]                      # cualquiera puede inventarse un sub
✓ Correcto
try:
    payload = jwt.decode(token, settings.secret_key, algorithms=[settings.algorithm])
except jwt.InvalidTokenError:
    raise credentials_error from None      # firma o exp inválidas → 401

Desactivar la firma convierte el JWT en un texto editable: todo el modelo de seguridad se cae. Si algo «no funciona» con un token, el problema suele ser que se firmó con otra clave o que ya caducó, no que la verificación estorbe.

Autorizar con el rol del token

✗ Incorrecto
def require_admin(token: Annotated[str, Depends(oauth2_scheme)], settings: SettingsDep):
    payload = decode_token(token, settings)
    if payload["role"] != "admin":        # rol congelado en el token
        raise HTTPException(403)
    return payload["sub"]                  # devuelve un string, no un User
✓ Correcto
def require_role(role: str):
    def checker(user: CurrentUserDep) -> User:
        if user.role != role:              # rol real, leído de la base de datos
            raise HTTPException(status_code=403, detail="Permisos insuficientes")
        return user
    return checker

El token dice lo que era cierto al emitirse. Si ayer era admin y hoy es usuario, o si su cuenta se desactivó, el token sigue diciendo «admin» hasta caducar. Revalidar contra la base de datos en cada petición es barato y mantiene la autorización fiel a la realidad.

Añadir una columna NOT NULL sin rellenarla

✗ Incorrecto
# Migración que fallará si query_log tiene filas:
def upgrade() -> None:
    op.add_column("query_log", sa.Column("owner_id", sa.Integer(), nullable=False))
# sqlite3.OperationalError: Cannot add a NOT NULL column with default value NULL
✓ Correcto
# 1) columna nullable  →  2) rellenar  →  3) (otra migración) cerrar a NOT NULL
def upgrade() -> None:
    op.add_column("query_log", sa.Column("owner_id", sa.Integer(), nullable=True))
    op.create_index("ix_query_log_owner_id", "query_log", ["owner_id"])
    op.execute("UPDATE query_log SET owner_id = 1 WHERE owner_id IS NULL")

Una regla de esquema se cambia en pasos porque la base de datos ya tiene datos que no pueden violar la nueva regla. El backfill es el paso intermedio: asignar un valor razonable a lo existente antes de exigir el nuevo contrato.

8 · Reto

🎯 Refresh tokens con rotación

Implementa un segundo tipo de token: un refresh token de vida larga (por ejemplo, 7 días) que permita obtener un nuevo access token corto sin volver a escribir la contraseña. Añade un endpoint POST /auth/refresh. Cuando se use, el refresh anterior debe quedar invalidado y debe emitirse uno nuevo (rotación); si alguien intenta reutilizar un refresh ya usado, toda la familia de tokens de ese usuario debe revocarse.

Pistas: el refresh no debería ser un access token reciclado; dale su propio type: "refresh" y comprueba ese campo al usarlo. Para invalidar y detectar reutilización necesitas estado: una tabla RefreshToken (con jti, user_id, expires_at, revoked y, opcionalmente, un family_id) o un almacén rápido tipo Redis. Pregúntate dónde guardar y cómo limpiar los tokens caducados, y qué código de estado devuelves cuando detectas reutilización. Documenta el modelo de amenaza: ¿a quién protege la rotación y de qué?

9 · Resumen

  • El histórico gana un dueño: QueryLog.owner_id con clave foránea a users.id, indexado.
  • Los cambios de esquema se hacen con Alembic: autogenerate, revisión manual, upgrade head. El mismo fichero aplica en todos los entornos.
  • Añadir una columna NOT NULL a una tabla con datos exige tres pasos: nullable, relleno y cierre.
  • Las contraseñas se guardan como hash bcrypt; se verifican con verify_password, nunca con ==.
  • El JWT se firma con una clave de Settings y lleva sub, role, iat y exp; su payload es público, su firma no.
  • decode valida firma y caducidad y restringe el algoritmo; desactivar la verificación es un error grave.
  • La autenticación (get_current_user) devuelve el usuario real de la base de datos; la autorización (require_role) comprueba su rol.
  • El aislamiento de datos se hace en SQL (where owner_id == user.id) y responde 404 a recursos privados ajenos.

10 · Preguntas frecuentes

¿Por qué el login usa form-urlencoded y no JSON?

Porque OAuth2PasswordRequestForm implementa el estándar OAuth2: el password flow define username y password como campos de formulario. Seguirlo tiene una ventaja inmediata: el botón Authorize de /docs funciona sin escribir una línea de frontend. Podrías aceptar JSON en un endpoint propio, pero perderías la integración con las herramientas estándar. Un matiz: el flujo exige HTTPS en producción, porque el formulario va en claro en cada login.

¿Guardo el rol en el token o lo consulto siempre?

Las dos cosas, y por razones distintas. En el token va el rol para que sea visible (depuración, UI) y para no obligar a una consulta si algún día mueves la autorización a otro servicio. Pero la decisión de autorización se toma contra el usuario cargado de la base de datos: es el único estado que no envejece. Si el rendimiento lo exigiera, guardarías en caché al usuario unos segundos, no confiarías en el token durante toda su vida.

¿Cómo revoco un token antes de que caduque?

Un JWT firmado es autocontenido: no existe una «lista de revocación» de serie. Por eso su vida es corta. Para revocar de inmediato tienes tres caminos: (1) rol o is_active en la base de datos y revalidar en cada petición —con lo que un UPDATE basta—; (2) una lista negra de jti en un almacén rápido (Redis) consultada en get_current_user; (3) cambiar la clave de firma, que invalida todos los tokens (útil ante un incidente). Cada uno tiene su coste; el curso se queda con el primero por simplicidad y porque ya revalidamos el usuario.

¿403 o 404 cuando el recurso es de otro usuario?

Para datos privados, un 404 uniforme: no confirmas que el identificador exista. Un 403 le dice a un atacante «este identificador es válido, solo te falta permiso», lo que permite enumerar recursos. Hay excepciones legítimas: si el recurso es público o el usuario necesita saber que existe pero no puede tocarlo, 403 es más honesto. Lo importante es decidirlo conscientemente y no dejarlo al azar de un if.

¿Puedo usar SQLite para el histórico en producción?

Para un proyecto de aprendizaje o un servicio con un solo proceso, sí: es rápido, no requiere servidor y el archivo es fácil de respaldar. Pero SQLite serializa las escrituras y no escala con varios procesos ni con tráfico concurrente alto. En cuanto el servicio crece, cambia COPILOTO_DATABASE_URL a PostgreSQL: el código de los modelos, las consultas y las dependencias no se toca, solo las migraciones se aplican contra la nueva URL. Esa portabilidad es, precisamente, el motivo de usar un ORM y migraciones.
