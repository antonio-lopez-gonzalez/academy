Testing y despliegue

Módulo 7 · Proyecto final: Copiloto API 🕐 45 minutos

1 · Introducción

Copiloto API responde, registra el histórico y protege las rutas. Falta lo que separa un proyecto de un ejercicio: poder demostrar que funciona y poder ponerlo en marcha en otro sitio. Eso es esta lección: una suite de tests que corre en segundos sin modelo ni red, y una imagen de Docker que arranca con una variable de entorno y ejecuta las migraciones.

Los dos temas van juntos porque se apoyan en la misma idea: reproducibilidad. Un test reproducible no depende del orden ni del estado global; un despliegue reproducible no depende de lo que tengas instalado en tu máquina. Si algo falla, sabes dónde mirar porque el entorno es el mismo en todos los sitios.

¿Por qué existe esta lección? Porque es el cierre del curso. Reúne TestClient y httpx (Módulo 6), las dependencias y dependency_overrides (Módulos 3 y 4), la configuración por entorno (Módulo 3), Alembic (Módulo 4) y la autenticación (Módulo 5). Y porque nadie despliega a mano dos veces el mismo proyecto igual: el Dockerfile es el contrato de arranque.

Errores típicos que veremos: tests que comparten una base de datos y se rompen según el orden; crear el TestClient sin el bloque with (y que el lifespan no se ejecute nunca); empaquetar el .env con la clave real dentro de la imagen; y arrancar con --reload en producción, que es un servidor de desarrollo disfrazado.

2 · Teoría

Qué merece un test (y qué no)

No se testea «todo»: se testea lo que puede romperse y lo que importa. En una API como Copiloto, la pirámide útil es corta y afilada:

                     ▲ pocos, lentos, reales
              ┌──────────────┐
              │  E2E / smoke │   la app arranca y /health responde (contenedor)
              ├──────────────┤
              │ Integración  │   TestClient + BD aislada: /ask, /auth, /logs
              ├──────────────┤
              │   Unitarios   │   security: hash y JWT; un puerto fake
              └──────────────┘
                     ▼ muchos, rápidos, aislados
Qué probamosCon quéPor qué
Contrato y códigos de estado de cada endpointTestClientEs lo que consume el cliente; romperlo es romper la API
Validación (422) y Problem DetailsTestClientLa forma del error también es contrato
Autenticación y roles (401/403/404)TestClient + token realUn fallo aquí es un agujero de seguridad
Persistencia y aislamiento por usuarioBD en memoria por testVerifica el owner_id en SQL, no en Python
Hash y JWTpytest puroRápido y sin infraestructura; son funciones puras
Que el contenedor arranca y respondeSmoke test con httpxEl despliegue es donde fallan las sorpresas

Rapidez = confianza. Una suite que tarda treinta segundos se ejecuta antes de cada commit. Una que tarda cinco minutos se ejecuta «algún día». La clave para que sea rápida es no depender del mundo exterior: sin Ollama, sin red, sin ficheros compartidos. Eso lo consiguen dependency_overrides y una base de datos en memoria.

Aislar la base de datos: una por test

El patrón de la suite es una fixture que construye un motor nuevo para cada test, crea las tablas y lo entrega envuelto en una sesión. Dos detalles importan:

  • sqlite:// (en memoria): la base de datos vive en RAM y desaparece al cerrar la conexión. Nada que limpiar entre tests.
  • poolclass=StaticPool: SQLite en memoria da una base distinta por conexión. Una pool estática reutiliza la misma conexión, así que todas las sesiones del test ven las mismas tablas.

El lifespan no corre solo. TestClient(app) construido directamente no dispara el arranque de la aplicación. Para eso hay que usarlo como context manager: with TestClient(app) as client:. Si lo olvidas, app.state.engine —creado en el lifespan— no existe y verás un AttributeError que parece no venir de ningún sitio. Como todo el código que abre recursos es el mismo que corre en producción, merece la pena que el test lo ejecute.

TestClient y httpx.AsyncClient

El TestClient usa httpx por debajo y ejecuta la app ASGI en el mismo proceso. Es lo más cómodo para el 90 % de los casos. Cuando el propio código es asíncrono (o quieres probar el comportamiento real de una app async), usas httpx.AsyncClient con ASGITransport y el plugin de anyio:

tests/test_health.py (variante async)
import pytest
from httpx import ASGITransport, AsyncClient

from app.main import app


@pytest.fixture
def anyio_backend() -> str:
    return "asyncio"


@pytest.mark.anyio
async def test_health_async() -> None:
    transport = ASGITransport(app=app)
    async with AsyncClient(transport=transport, base_url="http://test") as client:
        response = await client.get("/health")
    assert response.status_code == 200
    assert response.json()["status"] in {"ok", "degraded"}

No mezcles: no llames al TestClient síncrono desde dentro de un test async. Si vas a probar código asíncrono, usa el cliente asíncrono de principio a fin.

Empaquetar con una imagen multi-etapa

La imagen de producción tiene que ser pequeña, reproducible y sin herramientas de compilación. El patrón multi-stage separa la construcción (donde se instalan dependencias, quizá compiladas) del runtime (donde solo va el resultado):

   ┌─ etapa builder ─────────────────────┐   ┌─ etapa runtime ────────────────┐
   │ python:3.12-slim + uv               │   │ python:3.12-slim               │
   │ uv sync --frozen  (deps + venv)     │──►│ COPY --from=builder /app       │
   │ tools de compilación, caché, lock   │   │ usuario no-root, sin compilador│
   └─────────────────────────────────────┘   └────────────────────────────────┘
  • Copiar pyproject.toml y uv.lock antes que el código: si cambias una línea de app/, Docker reutiliza la capa de dependencias. Sin esto, cada cambio reinstala todo.
  • uv sync --frozen --no-dev: --frozen exige que el uv.lock esté al día (nada de resolver a ciegas en el build) y --no-dev deja fuera las herramientas de desarrollo.
  • Usuario no-root: si el proceso se compromete, el atacante no es root dentro del contenedor.
  • HEALTHCHECK: el orquestador sabe si el contenedor está sano llamando a /health, el endpoint que construimos en la lección 2.

Configuración por entorno y migraciones

El principio 12-factor del curso: la misma imagen, distintos entornos. Nada de una imagen por entorno: la diferencia va en variables de entorno. La imagen no contiene secretos; el .env no se copia (está en .dockerignore) y la clave se inyecta al ejecutar.

VariableEjemploSecreto
COPILOTO_DATABASE_URLpostgresql+psycopg://user:pass@db:5432/copilotoSí (lleva credenciales)
COPILOTO_SECRET_KEYuna cadena aleatoria de 48+ caracteresSí
COPILOTO_RAG_BACKENDlearn-ia · cannedNo
COPILOTO_ENVIRONMENTproductionNo

Y las migraciones se aplican al desplegar, no al importar la app. El comando es el de siempre:

uv run alembic upgrade head

Nunca apliques migraciones dentro del arranque de la aplicación. Si main.py llamara a alembic upgrade, cada uno de los N procesos lo intentaría a la vez y competirían por el esquema. La migración es un paso del despliegue (una tarea previa, un job), y arrancar es otro.

Uvicorn en producción

Uvicorn es el servidor ASGI. En desarrollo lo usas con --reload; en producción, no.

FlagPara qué
--host 0.0.0.0Escuchar en todas las interfaces (dentro del contenedor)
--port 8000El puerto que publica el contenedor
--proxy-headersRespetar X-Forwarded-For/X-Forwarded-Proto para IP real y esquema
--forwarded-allow-ipsQué proxies son de confianza (por defecto, solo local)
--workers NVarios procesos para aprovechar la CPU (o varios contenedores)
--no-access-logSilenciar el log por petición si tu logging estructurado ya lo cubre

¿--reload en producción? Nunca. Vigila el sistema de archivos y reinicia el proceso: consume recursos, provoca caídas al desplegar y no está probado para tráfico. Es una herramienta de desarrollo, igual que --workers sin contenedor suele ser innecesario: en plataformas con orquestación, es mejor escalar el número de contenedores que meter varios procesos en uno.

3 · Ejemplo mínimo

Dos fixtures y un test. Un motor en memoria, el motor de RAG sustituido por un doble y el endpoint comprobado sin depender de nada externo.

tests/conftest.py
from collections.abc import Iterator

import pytest
from fastapi.testclient import TestClient

from app.deps import get_engine
from app.main import app
from app.services.rag import RagAnswer


class FakeEngine:
    """Doble del motor de RAG: determinista, sin red ni índice."""

    def answer(self, question: str, module_slug: str | None = None) -> RagAnswer:
        return RagAnswer(text=f"respuesta a: {question}", sources=["learn-fastapi"])


@pytest.fixture
def client() -> Iterator[TestClient]:
    app.dependency_overrides[get_engine] = lambda: FakeEngine()
    with TestClient(app) as client:      # ★ el `with` dispara el lifespan
        yield client
    app.dependency_overrides.clear()
tests/test_ask.py
def test_ask_devuelve_respuesta(client) -> None:
    response = client.post("/ask", json={"question": "¿Qué es ASGI?"})

    assert response.status_code == 200
    body = response.json()
    assert body["answer"] == "respuesta a: ¿Qué es ASGI?"
    assert body["sources"] == ["learn-fastapi"]
    assert body["latency_ms"] >= 0

Ejecuta uv run pytest -q. Resultado esperado:

1 passed in 0.42s

Lo esencial:

  1. app.dependency_overrides[get_engine] = lambda: FakeEngine(): el endpoint cree que usa el motor real; el test le da un doble. Ni Ollama, ni índice, ni red.
  2. with TestClient(app) as client: el contexto ejecuta el lifespan; sin él, app.state.engine no existiría (aunque aquí esté sustituido, el patrón debe ser el mismo que el de producción).
  3. app.dependency_overrides.clear() al terminar: un override olvidado contaminaría los siguientes tests. Es el equivalente a limpiar la base de datos entre tests.
  4. La aserción sobre latency_ms >= 0: comprobamos que el campo existe y es un entero válido, sin fijar el valor exacto. Los tests no deben depender del tiempo real.

4 · Ejemplo real

La suite completa. Primero, las fixtures: base de datos en memoria por test, sesión inyectada y cliente. Un detalle importante: la clave de firma se define antes de importar la app, porque Settings la exige al arrancar.

tests/conftest.py
import os
from collections.abc import Iterator

# La configuración se lee al importar; define el entorno del test ANTES.
os.environ.setdefault("COPILOTO_SECRET_KEY", "test-secret-key-que-tiene-32-caracteres-ok")
os.environ.setdefault("COPILOTO_RAG_BACKEND", "canned")

import pytest
from fastapi.testclient import TestClient
from sqlmodel import Session, SQLModel, create_engine
from sqlmodel.pool import StaticPool

from app.db import get_session
from app.deps import get_engine
from app.main import app
from app.services.rag import RagAnswer


class FakeEngine:
    def answer(self, question: str, module_slug: str | None = None) -> RagAnswer:
        fuente = "Learn FastAPI · M07 · 02" if module_slug is None else module_slug
        return RagAnswer(text=f"respuesta a: {question}", sources=[fuente])


@pytest.fixture
def session() -> Iterator[Session]:
    """Base de datos nueva y en memoria para CADA test."""
    engine = create_engine(
        "sqlite://",
        connect_args={"check_same_thread": False},
        poolclass=StaticPool,      # misma conexión para todas las sesiones del test
    )
    SQLModel.metadata.create_all(engine)
    with Session(engine) as session:
        yield session


@pytest.fixture
def client(session: Session) -> Iterator[TestClient]:
    def override_session() -> Iterator[Session]:
        yield session               # el test y los endpoints comparten la MISMA sesión

    app.dependency_overrides[get_session] = override_session
    app.dependency_overrides[get_engine] = lambda: FakeEngine()
    with TestClient(app) as client:
        yield client
    app.dependency_overrides.clear()

Y los de seguridad, con autenticación de verdad (token firmado con la misma clave):

tests/test_auth.py
import pytest

from app.config import get_settings
from app.models import User
from app.security import create_access_token, hash_password


@pytest.fixture
def ana(session) -> User:
    user = User(
        email="ana@test.dev",
        hashed_password=hash_password("s3cret"),
        role="user",
    )
    session.add(user)
    session.commit()
    session.refresh(user)
    return user


def auth_headers(user: User) -> dict[str, str]:
    token = create_access_token(user.email, get_settings(), role=user.role)
    return {"Authorization": f"Bearer {token}"}


def test_ask_sin_token_es_401(client) -> None:
    response = client.post("/ask", json={"question": "¿Qué es ASGI?"})
    assert response.status_code == 401
    assert response.headers["www-authenticate"] == "Bearer"


def test_login_y_historial_propio(client, ana) -> None:
    # 1) Login real vía OAuth2 password flow
    token = client.post(
        "/auth/token",
        data={"username": "ana@test.dev", "password": "s3cret"},
    )
    assert token.status_code == 200
    headers = {"Authorization": f"Bearer {token.json()['access_token']}"}

    # 2) Pregunta protegida y consulta del propio histórico
    assert client.post("/ask", json={"question": "pregunta de ana"}, headers=headers).status_code == 200
    logs = client.get("/logs", headers=headers)
    assert logs.status_code == 200
    assert [log["question"] for log in logs.json()] == ["pregunta de ana"]

    # 3) Un usuario normal NO puede ver el histórico global
    assert client.get("/logs/all", headers=headers).status_code == 403


def test_login_con_password_mala(client, ana) -> None:
    response = client.post(
        "/auth/token",
        data={"username": "ana@test.dev", "password": "incorrecta"},
    )
    assert response.status_code == 401

Y, por último, la imagen de producción. Multi-etapa, usuario no-root y HEALTHCHECK contra /health:

Dockerfile
# ───────────────────────── Etapa 1: construcción ─────────────────────────
FROM python:3.12-slim AS builder

# uv dentro de la imagen, sin instalarlo con pip.
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy

WORKDIR /app

# 1) Solo los ficheros de dependencias → capa cacheable.
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-install-project --no-dev

# 2) Ahora el código y el proyecto.
COPY . .
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

# ───────────────────────── Etapa 2: runtime ──────────────────────────────
FROM python:3.12-slim AS runtime

# Usuario sin privilegios.
RUN useradd --create-home --uid 10001 appuser

WORKDIR /app

# Solo el resultado: venv + código, ya propiedad de appuser.
COPY --from=builder --chown=appuser:appuser /app /app

ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

USER appuser
EXPOSE 8000

# El orquestador pregunta a /health si el contenedor está listo.
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"

CMD ["uvicorn", "app.main:app", \
     "--host", "0.0.0.0", "--port", "8000", \

Decisiones y porqués del ejemplo real:

  • StaticPool + sqlite://: base de datos real en RAM por test. Prueba el SQL de verdad (incluida la clave foránea y el filtro por owner_id) sin tocar el disco ni dejar residuos.
  • La sesión se comparte entre el test y los endpoints: el test puede consultar session.get(QueryLog, log_id) y ver exactamente lo mismo que escribió la API. Es la forma de comprobar que el histórico se persiste, no solo que la respuesta lo diga.
  • os.environ.setdefault antes de importar app: Settings exige la clave al construirse. Definirla aquí hace que la app real que arranca el lifespan funcione sin secretos en el repositorio.
  • Dockerfile con uv sync --frozen: si el uv.lock y el pyproject.toml no coinciden, el build falla en vez de resolver versiones nuevas silenciosamente. La imagen es bit a bit reproducible en la medida de lo posible.
  • --proxy-headers: detrás de un reverse proxy, sin este flag la IP que registres y el esquema (http/https) serán los del proxy, no los del cliente. Con él, FastAPI respeta las cabeceras X-Forwarded-*.

6 · Errores habituales

Compartir la base de datos entre tests

✗ Incorrecto
# conftest.py a nivel de sesión: una sola BD para todos los tests
engine = create_engine("sqlite:///test.db")
SQLModel.metadata.create_all(engine)     # se ejecuta UNA vez

@pytest.fixture(scope="session")
def client():
    return TestClient(app)               # los datos de un test contaminan el siguiente
✓ Correcto
@pytest.fixture
def session() -> Iterator[Session]:
    engine = create_engine(
        "sqlite://",
        connect_args={"check_same_thread": False},
        poolclass=StaticPool,
    )
    SQLModel.metadata.create_all(engine)   # base nueva por test
    with Session(engine) as session:
        yield session

Con una base compartida, el test que comprueba «hay 1 consulta» falla cuando se ejecuta después del que dejó tres. El síntoma es traicionero: pasa en solitario y falla en la suite. Base nueva por test, sin excepciones.

TestClient sin el bloque with

✗ Incorrecto
def test_health():
    client = TestClient(app)             # el lifespan NO se ejecuta
    response = client.get("/health")
    # app.state.engine no existe → AttributeError en las rutas que lo usan
✓ Correcto
def test_health():
    with TestClient(app) as client:      # arranque y apagado reales
        response = client.get("/health")
    assert response.status_code == 200

El lifespan es código de producción: abre el motor de RAG, comprueba la conexión, cierra al final. Si el test lo salta, deja de probar la mitad del arranque y enmascara fallos que solo aparecerían en el contenedor.

Secretos dentro de la imagen

✗ Incorrecto
COPY . .                                   # incluye el .env con la clave real
ENV COPILOTO_SECRET_KEY="clave-que-he-puesto-aqui"   # queda grabada en la imagen
✓ Correcto
# .dockerignore: .env
# la clave se inyecta al EJECUTAR el contenedor, no al construir la imagen
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Una imagen se comparte en un registro, se cachea y se inspecciona con docker history. Todo lo que metas en una capa es público para quien tenga la imagen. Los secretos van por variables de entorno en runtime (o por un gestor de secretos), jamás en el Dockerfile ni en el .env copiado.

--reload (y root) en producción

✗ Incorrecto
USER root
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--reload"]
✓ Correcto
USER appuser
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--proxy-headers", "--forwarded-allow-ips=*"]

--reload vigila el sistema de archivos y reinicia el proceso: pensado para cuando editas código, no para servir tráfico. Y ejecutar como root hace que cualquier ejecución de código arbitrario en el contenedor tenga privilegios totales. Dos líneas de diferencia entre un juguete y algo desplegable.

7 · Ejercicio guiado

Objetivo: ejecutar la suite completa, construir la imagen y arrancar Copiloto API en un contenedor, aplicando la migración y comprobando el flujo autenticado.

  1. Paso 1 — Instala las dependencias de desarrollo. 
    uv add --dev pytest httpx anyio ruff mypy

    Resultado esperado: aparecen en el grupo dev de pyproject.toml. Añade el bloque [tool.pytest.ini_options] con testpaths = ["tests"].

  2. Paso 2 — Escribe las fixtures. Crea tests/conftest.py con el FakeEngine, las fixtures session y client y el os.environ.setdefault al principio del fichero, antes de importar la app.
  3. Paso 3 — Tests de contrato. Crea tests/test_ask.py con test_health, test_ask_registra_la_consulta y test_ask_pregunta_demasiado_corta.
  4. Paso 4 — Tests de seguridad. Crea tests/test_auth.py con la fixture ana, los tres tests de autenticación y roles.
  5. Paso 5 — Ejecuta la suite. 
    uv run pytest -q
uv run pytest -q --cov=app --cov-report=term-missing

    Resultado esperado: todos los tests en verde en menos de un segundo (sin el --cov). Compáralo con lo que tardaría si cada test llamara a un modelo real: esa diferencia es el valor de los overrides. Si un test falla por AttributeError sobre app.state.engine, revisa el with TestClient(...).

  6. Paso 6 — Construye la imagen. 
    docker build -t copiloto-api:1.0.0 .
docker image ls copiloto-api

    Resultado esperado: la imagen se construye sin secretos. Comprueba que el .env no está dentro:

    docker run --rm copiloto-api:1.0.0 ls -a /app | grep -c ".env" || echo "sin .env en la imagen"
  7. Paso 7 — Arranca con las variables de entorno. 
    docker run --rm -p 8000:8000 \
  -e COPILOTO_SECRET_KEY="una-clave-larga-de-al-menos-32-caracteres" \
  -e COPILOTO_RAG_BACKEND=canned \
  -e COPILOTO_DATABASE_URL="sqlite:////data/copiloto.db" \
  copiloto-api:1.0.0

    Resultado esperado: los logs de uvicorn y «Application startup complete». En otra terminal, docker ps debe mostrar el contenedor como healthy cuando pase el intervalo del HEALTHCHECK:

    curl -s http://127.0.0.1:8000/health
  8. Paso 8 — Migra y crea un usuario dentro del contenedor. El esquema no existe todavía: las tablas no las crea la app. Ejecuta la migración como un paso aparte y crea el usuario: 
    docker exec -it <container_id> alembic upgrade head

8 · Reto

🎯 Un smoke test de contenedor en CI

Monta un flujo de integración continua que construya la imagen, arranque el contenedor con variables de entorno de prueba, espere a que /health responda, ejecute la migración y haga un smoke test real con httpx contra el servicio en marcha (login, POST /ask y GET /logs). Si cualquier paso falla, el pipeline debe parar y volcar los logs del contenedor.

Pistas: necesitas un bucle de espera que consulte /health con reintentos y timeout (un contenedor no está listo en el instante en que arranca). Ejecuta la migración con docker exec y comprueba su código de salida antes de continuar. Para volcar los logs cuando algo falla, captúralos con docker logs en un bloque que también se ejecute si el paso falló (el if: always() de GitHub Actions). Pregúntate qué NO debe entrar nunca en este pipeline: secretos reales, la base de datos de producción o el índice de RAG de verdad. Documenta cómo lo evitas.

9 · Resumen

  • Se testea el contrato (códigos y forma de error), la seguridad (401/403/404) y la persistencia, no cada línea.
  • Una base de datos en memoria por test (sqlite:// + StaticPool) hace la suite rápida y sin orden.
  • dependency_overrides sustituye el motor de RAG y la sesión: tests deterministas, sin red ni índice.
  • with TestClient(app) as client ejecuta el lifespan; sin el contexto, no corre.
  • La imagen es multi-etapa: dependencias con uv sync --frozen --no-dev, runtime slim, usuario no-root y HEALTHCHECK.
  • La configuración va por variables de entorno (COPILOTO_*): la misma imagen en todos los entornos, cero secretos dentro.
  • Las migraciones (alembic upgrade head) son un paso del despliegue, no del arranque de la app.
  • En producción: uvicorn sin --reload, con --proxy-headers y --forwarded-allow-ips.

10 · Preguntas frecuentes

¿TestClient o httpx.AsyncClient?

TestClient para casi todo: es más simple, ejecuta la app en el mismo proceso y basta para probar contratos, validación, auth y persistencia. Usa httpx.AsyncClient con ASGITransport cuando pruebas código realmente asíncrono (endpoints async, clientes async, streaming) o cuando quieres el mismo cliente que usarás en el smoke test contra el contenedor. En un test, elige uno y no los mezcles.

¿Por qué SQLite en memoria y no PostgreSQL en un contenedor de test?

Velocidad y cero infraestructura: la suite corre en segundos en cualquier máquina, sin docker compose ni puertos. El riesgo es que SQLite no se comporta igual que PostgreSQL en todo (tipos, ALTER, concurrencia). La estrategia pragmática del curso: la mayoría de tests contra SQLite en memoria y unos pocos de integración contra la base de datos real (en CI), sobre todo si usas funciones específicas del motor. Así cubres el 95 % de los casos rápido y dejas los caros para donde aportan.

¿Cada cuánto se corre la suite?

En cada commit o pull request, y en local antes de subir. Con una suite de segundos no hay excusa. Un test que se ejecuta «a veces» es un test que se salta justo cuando más falta hace. Si tarda demasiado, el problema no es la costumbre: es el diseño de los tests (demasiada red, demasiadas bases compartidas).

¿Dónde pongo las migraciones en el despliegue?

En un paso anterior y separado al arranque del servicio: un job de despliegue, un docker run efímero que ejecuta alembic upgrade head, o una tarea del orquestador. Nunca en el lifespan: si arrancan N réplicas a la vez, todas intentarían migrar y competirían por el esquema. Y si la migración falla, el despliegue debe detenerse antes de sustituir la versión anterior.

¿Varios workers o varios contenedores?

Si tu plataforma orquesta contenedores (Kubernetes, un servicio gestionado), escala con réplicas: un proceso por contenedor es más fácil de observar, de limitar y de reiniciar. --workers tiene sentido cuando despliegas un único contenedor en una máquina con varios núcleos y no tienes orquestador, pero complica el logging y el apagado ordenado. En cualquiera de los dos casos, recuerda que el estado compartido (la base de datos) no vive en el proceso.
