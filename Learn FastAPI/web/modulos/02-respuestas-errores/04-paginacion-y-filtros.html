Paginación y filtros

Módulo 2 · Respuestas y errores 🕐 35 minutos

1 · Introducción

GET /modules que devuelve todos los módulos funciona hoy, con doce filas. Mañana son doce mil, y tu endpoint se convierte en una bomba: consulta gigante, JSON enorme, cliente que se queda sin memoria. Una colección sin paginación es una deuda técnica que siempre explota.

Esta lección cierra el módulo con la pieza que hace usables los listados: paginación (traer un trozo a la vez), orden (traerlo en un orden definido) y filtrado (traer solo lo que interesa). Y todo modelado con Query, con límites de seguridad para que el cliente no pueda pedir «un millón de filas».

¿Por qué es importante el orden? Sin un criterio de orden estable, una base de datos no garantiza en qué orden devuelve las filas. Con paginación eso es un desastre: la página 2 puede repetir un elemento de la página 1 y saltarse otro. Paginar exige ordenar por algo único (casi siempre el id).

Aquí lo haremos en memoria para centrarnos en el modelado del endpoint. En el módulo 4 verás el LIMIT/OFFSET de SQL y, en el módulo 7, la versión con base de datos real. Lo que aprendas hoy se traduce directamente a SQL.

2 · Teoría

limit y offset: la pareja canónica

Dos números controlan el trozo que pides:

  • limit: cuántos elementos quieres (el tamaño de la página).
  • offset: cuántos te saltas desde el principio (dónde empieza la página).
   offset=0, limit=3         offset=3, limit=3         offset=6, limit=3
   +---+---+---+             +---+---+---+             +---+---+---+
   | 1 | 2 | 3 |             | 4 | 5 | 6 |             | 7 | 8 | 9 |
   +---+---+---+             +---+---+---+             +---+---+---+
     pagina 1                  pagina 2                  pagina 3

La correspondencia con SQL es directa: SELECT … ORDER BY id LIMIT :limit OFFSET :offset. Alternativamente puedes exponer page y size (más amigable para un humano) y calcular offset = (page - 1) * size. Ambas son válidas; el curso usa limit/offset porque es lo que traduce la base de datos sin conversión.

El «sobre» de paginación

Devolver una list pelada deja al cliente sin saber cuántos elementos hay en total ni si hay más páginas. Envuelve el listado en un modelo:

app/schemas/page.py
# app/schemas/page.py — sobre generico y reutilizable.
from typing import Generic, TypeVar

from pydantic import BaseModel

T = TypeVar("T")


class Page(BaseModel, Generic[T]):
    items: list[T]
    total: int          # cuantos hay en total (sin paginar)
    limit: int          # tamano de pagina solicitado
    offset: int         # desde donde empieza esta pagina

Con Pydantic v2 el modelo es genérico: Page[ModuleOut] es un sobre cuyas items son módulos; Page[SourceOut], uno de fuentes. Un solo molde, tipado y documentado.

También puedes informar del total en una cabecera X-Total-Count (estilo GitHub) en vez de en el cuerpo. El sobre en el cuerpo es más fácil de consumir desde JavaScript y se autodocumenta en el OpenAPI; las cabeceras ahorran espacio. Elige una y sé consistente.

Orden: nunca desde un str libre

«Déjame ordenar por cualquier columna» suena bien hasta que el cliente envía ?order_by=title;DROP TABLE modules. El orden se modela con un enum: el cliente solo puede elegir entre opciones que tú defines.

from enum import Enum


class ModuleSort(str, Enum):
    title = "title"
    chunk_count = "chunk_count"
    created_at = "created_at"

Después traduces el enum a la columna real. El cliente elige de una lista cerrada; tú traduces de forma segura. El enum además aparece en el OpenAPI como un desplegable, que es documentación gratis.

Filtros: opcionales, tipados y acotados

Un filtro es un parámetro opcional con el que el cliente reduce la colección: ?tag=rag&search=embedding. Se modela con Query y Annotated para añadir límites:

from typing import Annotated

from fastapi import Query

limit: Annotated[int, Query(ge=1, le=100)] = 20
search: Annotated[str | None, Query(min_length=2, max_length=100)] = None

El le=100 del limit es una barrera de seguridad: aunque el cliente pida ?limit=1000000, la validación lo rechaza como 422 (que, gracias a la lección 2, ya sale como Problem Details).

PatrónCuándo usarloCoste
limit / offsetColecciones pequeñas o medianas, con «ir a la página N»El OFFSET alto degrada: la BD lee y descarta
page / sizeInterfaz con páginas numeradas para humanosIgual que offset, con una conversión extra
Cursor (?after=…)Feeds grandes, scroll infinito, datos que cambianNo permite «salto» arbitrario a una página

Analogía: offset es «lee las primeras 10 000 cartas, tira las 9 980 primeras y dame 20». Funciona, pero desperdicia trabajo. Un cursor es «empieza por la carta cuyo número es 9 981»: la bibliotecaria va directa al estante. Por eso los listados masivos usan cursores.

3 · Ejemplo mínimo

Un listado paginado sobre datos en memoria: el cliente pide limit, offset y un orden acotado, y recibe un sobre con total.

main.py
# main.py — listado paginado y ordenado sin base de datos.
from enum import Enum
from typing import Annotated, Generic, TypeVar

from fastapi import FastAPI, Query
from pydantic import BaseModel

app = FastAPI()

MODULES = [
    {"id": 1, "title": "Rutas y datos"},
    {"id": 2, "title": "Respuestas y errores"},
    {"id": 3, "title": "Dependencias"},
    {"id": 4, "title": "Datos y persistencia"},
    {"id": 5, "title": "Seguridad"},
]


class ModuleOut(BaseModel):
    id: int
    title: str


T = TypeVar("T")


class Page(BaseModel, Generic[T]):
    items: list[T]
    total: int
    limit: int
    offset: int


class ModuleSort(str, Enum):
    id = "id"
    title = "title"
main.py
@app.get("/modules", response_model=Page[ModuleOut])
async def list_modules(
    limit: Annotated[int, Query(ge=1, le=100)] = 2,
    offset: Annotated[int, Query(ge=0)] = 0,
    order_by: ModuleSort = ModuleSort.id,
    desc: bool = False,
):
    items = sorted(MODULES, key=lambda m: m[order_by.value], reverse=desc)
    page = items[offset : offset + limit]
    return {"items": page, "total": len(items), "limit": limit, "offset": offset}
terminal
uv run fastapi dev main.py
# Pagina 2, orden descendente por titulo:
curl -s "http://127.0.0.1:8000/modules?limit=2&offset=2&order_by=title&desc=true"

Salida esperada:

JSON
{
  "items": [
    { "id": 2, "title": "Respuestas y errores" },
    { "id": 1, "title": "Rutas y datos" }
  ],
  "total": 5,
  "limit": 2,
  "offset": 2
}

Línea por línea:

  1. limit: Annotated[int, Query(ge=1, le=100)] = 2: el le=100 impide pedir páginas gigantes; ge=1 prohíbe un límite de cero o negativo.
  2. offset: Annotated[int, Query(ge=0)] = 0: un offset negativo no tiene sentido y daría errores raros en la BD.
  3. order_by: ModuleSort: el cliente elige de un enum cerrado; m[order_by.value] es seguro porque solo acepta claves que tú definiste.
  4. items[offset : offset + limit]: el corte de la página. En SQL será .offset(offset).limit(limit).
  5. response_model=Page[ModuleOut]: el sobre se valida y se documenta; el filtrado de campos sigue vigente.

4 · Ejemplo real

El listado real de Copiloto API: GET /modules con paginación, orden seguro, búsqueda por texto y filtro por etiqueta, todo devuelto en un Page[ModuleOut].

proyectos/copiloto-api/app/schemas/module.py
# app/schemas/module.py — salida del listado y parametros de orden.
from enum import Enum

from pydantic import BaseModel, ConfigDict, Field


class ModuleOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    slug: str
    title: str
    tags: list[str] = Field(default_factory=list)


class ModuleSort(str, Enum):
    """Ordenes permitidos por el cliente (nunca una columna libre)."""

    title = "title"
    created_at = "created_at"
    chunk_count = "chunk_count"
proyectos/copiloto-api/app/routers/modules.py
# app/routers/modules.py — listado paginado, ordenado y filtrado.
from typing import Annotated

from fastapi import APIRouter, Query

from app.repos.modules_repo import modules_repo
from app.schemas.module import ModuleOut, ModuleSort
from app.schemas.page import Page

router = APIRouter(prefix="/modules", tags=["modules"])


@router.get("", response_model=Page[ModuleOut])
async def list_modules(
    limit: Annotated[int, Query(ge=1, le=100, description="Tamano de pagina")] = 20,
    offset: Annotated[int, Query(ge=0, description="Elementos a saltar")] = 0,
    order_by: ModuleSort = ModuleSort.title,
    desc: Annotated[bool, Query(description="Orden descendente")] = False,
    search: Annotated[
        str | None, Query(min_length=2, max_length=100, description="Busca en titulo y slug")
    ] = None,
    tag: Annotated[str | None, Query(max_length=40, description="Filtra por etiqueta")] = None,
) -> Page[ModuleOut]:
    rows, total = await modules_repo.list(
        limit=limit,
        offset=offset,
        order_by=order_by.value,
        desc=desc,
        search=search,
        tag=tag,
    )
    return Page[ModuleOut](items=rows, total=total, limit=limit, offset=offset)
proyectos/copiloto-api/app/repos/modules_repo.py
# app/repos/modules_repo.py — la capa que traduce el contrato a consulta.
# (Version en memoria; el modulo 4 lo sustituye por SQLModel + SQL real.)
from collections.abc import Sequence

ORDERABLE = {
    "title": lambda m: m.title,
    "created_at": lambda m: m.created_at,
    "chunk_count": lambda m: m.chunk_count,
}


class ModulesRepo:
    async def list(
        self,
        *,
        limit: int,
        offset: int,
        order_by: str,
        desc: bool,
        search: str | None,
        tag: str | None,
    ) -> tuple[Sequence, int]:
        rows = list(self._all())
        # Filtros (en SQL serian WHERE ...).
        if search:
            needle = search.lower()
            rows = [m for m in rows if needle in m.title.lower() or needle in m.slug.lower()]
        if tag:
            rows = [m for m in rows if tag in m.tags]

        total = len(rows)                       # COUNT(*) en SQL
        # Orden estable: por el criterio pedido y, como desempate, por id.
        rows.sort(key=ORDERABLE[order_by], reverse=desc)
        rows.sort(key=lambda m: m.id)           # desempate estable
        if desc:
            rows.reverse()
        return rows[offset : offset + limit], total     # LIMIT / OFFSET


modules_repo = ModulesRepo()
terminal
# Busca "rag", filtra por tag "fastapi", ordena por fecha descendente:
curl -s "http://127.0.0.1:8000/modules?search=rag&tag=fastapi&order_by=created_at&desc=true&limit=10"

Decisiones y porqués:

  • limit con le=100: el tope duro impide que un cliente (o un bot) pida toda la tabla. Es la barrera entre un listado sano y una denegación de servicio autoinfligida.
  • order_by como enum: el repositorio usa ORDERABLE[order_by], es decir, una clave ya validada. Cero inyección por orden.
  • Desempate por id: garantiza un orden total y estable. Sin él, dos módulos con el mismo title podrían intercambiarse entre páginas y perder o duplicar filas.
  • search con min_length=2: una búsqueda de un solo carácter rara vez es útil y castiga el índice. La longitud mínima es validación, no capricho.
  • Separación router/repo: el router habla HTTP (Query, tipado, sobre); el repositorio habla datos (filtros, orden, corte). El módulo 4 hará que ese repositorio emita SQL.

El coste oculto del offset alto. ?offset=1000000 obliga a la base de datos a leer y descartar un millón de filas aunque solo devuelva veinte. Si tu colección crece, migra a paginación por cursor («dame los posteriores a este id»): WHERE id > :after ORDER BY id LIMIT :limit. Verás esa técnica en el módulo 7.

6 · Errores habituales

Sin tope en limit

Mal — el cliente decide cuánto cargas 
# ❌ ?limit=500000 tumba la base de datos y llena la memoria.
@app.get("/modules")
async def list_modules(limit: int = 20, offset: int = 0):
    return await repo.list(limit=limit, offset=offset)
Bien — tope duro y validación 
# ✅ le=100 rechaza con 422 cualquier peticion abusiva.
from typing import Annotated
from fastapi import Query

@app.get("/modules")
async def list_modules(
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
    offset: Annotated[int, Query(ge=0)] = 0,
):
    return await repo.list(limit=limit, offset=offset)

Orden desde una cadena arbitraria

Mal — la columna la elige el cliente 
# ❌ order_by llega como texto libre: puerta abierta a inyeccion SQL.
@app.get("/modules")
async def list_modules(order_by: str = "title"):
    return await repo.list(f"ORDER BY {order_by}")      # ¡peligro!
Bien — enum cerrado y traducción segura 
# ✅ Solo se aceptan las opciones del enum; el valor va a una consulta parametrizada.
@app.get("/modules")
async def list_modules(order_by: ModuleSort = ModuleSort.title):
    return await repo.list(order=order_by.value)        # repositorio traduce con ORDERABLE

Devolver una lista sin total

Mal — el cliente no sabe si hay más 
# ❌ Llegan 20 elementos, ¿son todos? ¿hay pagina 2? Se queda sin saber.
@app.get("/modules")
async def list_modules(limit: int = 20, offset: int = 0) -> list[ModuleOut]:
    return await repo.list(limit=limit, offset=offset)
Bien — sobre con metadatos 
# ✅ Page[ModuleOut] lleva items, total, limit y offset.
@app.get("/modules", response_model=Page[ModuleOut])
async def list_modules(limit: int = 20, offset: int = 0) -> Page[ModuleOut]:
    rows, total = await repo.list(limit=limit, offset=offset)
    return Page[ModuleOut](items=rows, total=total, limit=limit, offset=offset)

Paginar sin orden determinista

Mal — el orden «natural» no está garantizado 
# ❌ Sin ORDER BY la BD puede devolver filas en cualquier orden y la
#    pagina 2 repite o pierde elementos respecto a la pagina 1.
rows = await db.fetch("SELECT * FROM modules LIMIT :l OFFSET :o", l=limit, o=offset)
Bien — orden total y estable 
# ✅ ORDER BY con desempate unico: cada fila tiene una posicion fija.
rows = await db.fetch(
    "SELECT * FROM modules ORDER BY title, id LIMIT :l OFFSET :o",
    l=limit, o=offset,
)

8 · Reto

🎯 Paginación por cursor y enlaces de navegación

Mejora el listado de módulos con (1) una variante de paginación por cursor: GET /modules?after=<id>&limit=20 que devuelva los siguientes por id sin usar offset, pensada para scroll infinito; y (2) un «sobre» enriquecido que incluya next_cursor (el id del último elemento, o null si no hay más) y cabeceras Link con rel="next"/rel="prev". Añade un test que pida todas las páginas con el cursor y compruebe que el conjunto de ids recibidos es exactamente el total, sin duplicados ni huecos —incluso si ordenas descendente y luego ascendente—.

Pista: el cursor debe ser un valor único y estable (el id lo es). Para descendente se invierte la comparación (WHERE id < :after). Piensa por qué un cursor sobre title (que puede repetirse) necesitaría un desempate compuesto (title, id); ese es el motivo por el que el cursor suele ir sobre una clave monótona. Documenta el endpoint con responses={422: {"model": ProblemDetail}} para completar el contrato.

9 · Resumen

  • Ninguna colección sin paginar: limit/offset es el punto de partida.
  • Pon siempre un tope máximo al limit (Query(le=100)).
  • Devuelve un sobre (Page[T]) con items, total, limit y offset.
  • El orden debe ser estable: criterio pedido + desempate único por id.
  • El orden se modela con un enum, nunca con una columna libre.
  • Filtros: opcionales, tipados y acotados con Query.
  • Con colecciones grandes, plantea paginación por cursor.

10 · Preguntas frecuentes

¿limit/offset o page/size?

Funcionalmente equivalentes; page/size se calcula como offset = (page - 1) * size. limit/offset traduce directo a SQL y es el que usan muchas APIs públicas. page/size es más cómodo para una interfaz con «página 3 de 10». Elige uno y mantenlo en toda la API; mezclarlos confunde a los clientes.

¿El total en cada página no es caro?

Requiere un COUNT(*) aparte, que en tablas enormes puede ser caro. Opciones: calcular el total solo cuando se pide explícitamente, usar una estimación, o pasarte a cursor y ofrecer solo «hay más / no hay más». Para la mayoría de APIs, un COUNT con un índice adecuado es perfectamente asumible. Mide antes de optimizar.

¿Por qué el desempate por id es necesario?

Porque el criterio principal puede repetirse: si ordenas por title y hay dos módulos con el mismo título, la base de datos puede devolverlos en cualquier orden relativo, y ese orden puede variar entre la página 1 y la 2. Añadir , id al ORDER BY rompe los empates de forma determinista: cada fila tiene una posición fija y la paginación deja de perder o duplicar elementos.

¿Cuándo merece la pena pasar a paginación por cursor?

Cuando la colección es grande o cambia mucho: el OFFSET alto es caro (leer y descartar) y, además, si se insertan filas mientras paginas, puedes duplicar o saltar elementos. El cursor («posteriores a este id») es O(1) por índice, estable ante inserciones y perfecto para scroll infinito. El precio: no puedes saltar a «página 5» y no hay número de página que mostrar.

¿Los filtros van en el router o en el repositorio?

Los parámetros (con su tipo y validación) viven en el router, que es la frontera HTTP. La consulta (dónde y cómo se filtra) vive en el repositorio, que es la capa de datos. El router traduce tag="rag" a «añade una condición WHERE»; el repositorio sabe si esa condición es un LIKE, un = o una búsqueda full-text. Esa separación es la que te permitirá cambiar de almacenamiento sin tocar el contrato del endpoint.
