Errores y Problem Details

Módulo 2 · Respuestas y errores 🕐 35 minutos

1 · Introducción

Cuando una API falla, el cliente necesita saber tres cosas: qué pasó, por qué y qué puede hacer al respecto. Una API que responde {"detail": "error"} no dice nada útil. Y una API donde cada ruta inventa su propio formato de error —unas veces {"error": ...}, otras {"message": ...}, otras texto plano— es imposible de consumir con dignidad.

En esta lección vas a aprender a lanzar errores con HTTPException, a interceptarlos con handlers de excepción, y sobre todo a darles una forma única y estándar: Problem Details (RFC 9457). El Copiloto API devolverá el mismo sobre de error para un 404, un 422 de validación o un fallo inesperado.

¿Por qué una forma consistente? Porque un cliente que consume tu API no quiere adivinar. Si todos los errores comparten el mismo esquema, el frontend escribe un manejador de errores y funciona con todo. Es la misma idea que response_model pero aplicada a lo que sale mal: modelar también el error.

Nunca devuelvas un stack trace. Un 500 con la traza de Python revela rutas, versiones, nombres de tablas y a veces secretos. El cliente recibe un mensaje genérico con un identificador; el detalle completo vive en tus logs.

2 · Teoría

El error también es parte del contrato

Un endpoint tiene un camino feliz (respuesta 2xx) y varios caminos de error (4xx para culpa del cliente, 5xx para culpa tuya). Si solo modelas el camino feliz, tu API está a medias. El error debe ser tan predecible como el éxito.

   peticion
      |
      v
  +-----------+    excepcion    +---------------------+    respuesta
  |  tu ruta  | --------------> |  exception_handler  | -------------->  cliente
  +-----------+                 |  (UN solo formato)  |   application/problem+json
      |                         +---------------------+
      | respuesta 2xx
      v
   JSON normal (response_model)

  Toda salida, feliz o no, tiene una forma declarada.

HTTPException: el error controlado

Para errores previstos —no encontrado, sin permisos, conflicto— lanzas HTTPException con un código y un detail:

from fastapi import HTTPException

raise HTTPException(status_code=404, detail="Modulo no encontrado")

FastAPI la convierte en una respuesta con ese status_code y un cuerpo {"detail": ...}. Es correcto, pero ese formato por defecto es pobre: no tiene tipo de problema, ni título, ni identificador de la ocurrencia. Por eso lo vamos a reemplazar por Problem Details.

HTTPException es control de flujo, no un fallo. Se usa para resultados esperados del negocio («este recurso no existe»). Un fallo real (una excepción de Python que no esperabas) es otra cosa: la capturas aparte y la traduces a 500 sin filtrar internals.

RFC 9457: Problem Details for HTTP APIs

Este estándar define un objeto JSON para describir errores. Sus campos:

CampoTipoSignificado
typeURIIdentificador del tipo de problema (a menudo una URL de tu documentación).
titlestringResumen humano y estable («Recurso no encontrado»).
statusintEl código HTTP, repetido en el cuerpo para comodidad del cliente.
detailstringExplicación específica de esta ocurrencia.
instanceURIIdentificador de la ocurrencia concreta (p. ej. el id de traza).

Se sirve con el media type application/problem+json, y puedes añadir extensiones: campos propios como errors (detalles de validación) o trace_id. Ejemplo del Copiloto:

application/problem+json
{
  "type": "https://copiloto.academy/problems/validation-error",
  "title": "Error de validacion",
  "status": 422,
  "detail": "La pregunta no puede estar vacia.",
  "instance": "/ask",
  "trace_id": "01J8Z0W3M4N5P6Q7R8S9T0",
  "errors": [
    { "field": "body.question", "message": "String should have at least 1 character" }
  ]
}

Analogía: Problem Details es la hoja de reclamación oficial de tu API. Todas las reclamaciones usan el mismo impreso: tipo de incidencia, resumen, número de expediente. Da igual si la reclamación es «faltaba un campo» o «no tienes permiso»: el funcionario que la recibe sabe leerla siempre igual.

Handlers: se registran una vez, cubren toda la API

Un exception handler es una función que FastAPI invoca cuando se lanza una excepción de cierto tipo. Lo registras con @app.exception_handler(Tipo). Los tres que necesitarás casi siempre:

  1. StarletteHTTPException: cubre los HTTPException que lanzas tú (y los 404/405 que genera el framework). Aquí das forma Problem Details a los 4xx.
  2. RequestValidationError: lo lanza FastAPI cuando el cuerpo o los query params no validan (el 422). Aquí conviertes la lista de errores de Pydantic en tu extensión errors.
  3. Exception (catch-all): captura cualquier fallo no previsto y responde un 500 genérico con trace_id, sin exponer la traza.

Puedes importar los handlers por defecto de FastAPI (fastapi.exception_handlers.http_exception_handler y request_validation_exception_handler) para envolverlos: logueas o enriqueces y luego delegas. Útil cuando no quieres reimplementar el comportamiento estándar.

Excepciones de dominio propias

En vez de lanzar HTTPException desde la capa de negocio, define excepciones tuyas (ModuleNotFound, QuotaExceeded) y tradúcelas a HTTP solo en el handler. Así tu lógica de negocio no sabe nada de HTTP.

class DomainError(Exception):
    """Base de los errores de negocio del Copiloto."""

class ModuleNotFound(DomainError):
    def __init__(self, slug: str) -> None:
        self.slug = slug

3 · Ejemplo mínimo

Definimos el modelo Problem Details y un handler para HTTPException. Con eso, todos los errores controlados de la app salen ya con la forma estándar.

main.py
# main.py — un unico formato para todos los errores controlados.
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

app = FastAPI()


@app.get("/modules/{slug}")
async def get_module(slug: str):
    if slug == "no-existe":
        raise HTTPException(status_code=404, detail=f"Modulo '{slug}' no encontrado")
    return {"slug": slug, "title": "Rutas"}


# --- Problem Details ---------------------------------------------------
PROBLEM_TYPES = {
    404: "https://copiloto.academy/problems/not-found",
    500: "https://copiloto.academy/problems/internal",
}


@app.exception_handler(StarletteHTTPException)
async def http_exception_handler(request: Request, exc: StarletteHTTPException):
    body = {
        "type": PROBLEM_TYPES.get(exc.status_code, "about:blank"),
        "title": "Recurso no encontrado" if exc.status_code == 404 else "Error",
        "status": exc.status_code,
        "detail": exc.detail,
        "instance": str(request.url.path),
    }
    return JSONResponse(
        status_code=exc.status_code,
        content=body,
        media_type="application/problem+json",
    )

Línea por línea:

  1. HTTPException(404, ...): la lógica solo dice qué falla; no decide el formato.
  2. @app.exception_handler(StarletteHTTPException): intercepta cualquier excepción HTTP de la app, venga de tu código o del framework (incluidos los 404 de rutas inexistentes).
  3. PROBLEM_TYPES: mapa de código de estado a URI de tipo de problema. Una sola fuente de verdad para los type.
  4. media_type="application/problem+json": el media type que manda el RFC. Los clientes que lo soportan lo detectan por la cabecera.
  5. instance=request.url.path: identifica la ocurrencia. En producción, un trace_id es aún mejor.

4 · Ejemplo real

En Copiloto API centralizamos todo: un modelo ProblemDetail, las excepciones de dominio, y tres handlers registrados en main.py. El resultado es que el /ask devuelve el mismo sobre tanto si la pregunta está vacía como si el índice no responde.

proyectos/copiloto-api/app/errors.py
# app/errors.py — el error como contrato, en un solo sitio.
from typing import Any

from pydantic import BaseModel, Field


class ProblemDetail(BaseModel):
    """RFC 9457 — Problem Details for HTTP APIs."""

    type: str = "about:blank"
    title: str
    status: int
    detail: str | None = None
    instance: str | None = None
    # Extensiones propias del Copiloto:
    trace_id: str | None = None
    errors: list[dict[str, Any]] | None = Field(
        default=None,
        description="Detalle por campo en errores de validacion",
    )


# --- Excepciones de dominio (no saben nada de HTTP) -------------------
class DomainError(Exception):
    """Base de los errores de negocio."""

class ModuleNotFound(DomainError):
    def __init__(self, slug: str) -> None:
        self.slug = slug

class IndexUnavailable(DomainError):
    """El motor de RAG no responde."""
proyectos/copiloto-api/app/error_handlers.py
# app/error_handlers.py — traduce excepciones a Problem Details.
import logging
import uuid

from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

from app.errors import IndexUnavailable, ModuleNotFound, ProblemDetail

logger = logging.getLogger("copiloto")

MEDIA_TYPE = "application/problem+json"
PROBLEM_TYPES = {
    404: "https://copiloto.academy/problems/not-found",
    422: "https://copiloto.academy/problems/validation-error",
    429: "https://copiloto.academy/problems/rate-limited",
    500: "https://copiloto.academy/problems/internal",
    503: "https://copiloto.academy/problems/service-unavailable",
}
TITLES = {
    404: "Recurso no encontrado",
    422: "Error de validacion",
    429: "Demasiadas peticiones",
    500: "Error interno",
    503: "Servicio no disponible",
}


def _problem(
    request: Request,
    *,
    status: int,
    detail: str | None,
    trace_id: str,
    errors: list[dict] | None = None,
) -> JSONResponse:
    problem = ProblemDetail(
        type=PROBLEM_TYPES.get(status, "about:blank"),
        title=TITLES.get(status, "Error"),
        status=status,
        detail=detail,
        instance=request.url.path,
        trace_id=trace_id,
        errors=errors,
    )
    return JSONResponse(
        status_code=status,
        content=problem.model_dump(exclude_none=True),
        media_type=MEDIA_TYPE,
    )
proyectos/copiloto-api/app/error_handlers.py
def register_exception_handlers(app: FastAPI) -> None:
    @app.exception_handler(StarletteHTTPException)
    async def http_error(request: Request, exc: StarletteHTTPException):
        trace_id = uuid.uuid4().hex
        logger.warning("http_error status=%s path=%s trace=%s", exc.status_code, request.url.path, trace_id)
        return _problem(request, status=exc.status_code, detail=str(exc.detail), trace_id=trace_id)

    @app.exception_handler(RequestValidationError)
    async def validation_error(request: Request, exc: RequestValidationError):
        trace_id = uuid.uuid4().hex
        errors = [
            {"field": ".".join(str(p) for p in err["loc"]), "message": err["msg"]}
            for err in exc.errors()
        ]
        return _problem(
            request,
            status=422,
            detail="La peticion no cumple el contrato.",
            trace_id=trace_id,
            errors=errors,
        )

    # --- Excepciones de dominio ---
    @app.exception_handler(ModuleNotFound)
    async def module_not_found(request: Request, exc: ModuleNotFound):
        return _problem(
            request,
            status=404,
            detail=f"Modulo '{exc.slug}' no encontrado.",
            trace_id=uuid.uuid4().hex,
        )

    @app.exception_handler(IndexUnavailable)
    async def index_unavailable(request: Request, exc: IndexUnavailable):
        return _problem(
            request,
            status=503,
            detail="El indice de busqueda no esta disponible; reintenta en unos segundos.",
            trace_id=uuid.uuid4().hex,
        )

    # --- Catch-all: sin stack traces hacia el cliente ---
    @app.exception_handler(Exception)
    async def unhandled(request: Request, exc: Exception):
        trace_id = uuid.uuid4().hex
        logger.exception("unhandled error path=%s trace=%s", request.url.path, trace_id)
        return _problem(
            request,
            status=500,
            detail="Error interno. Cita el trace_id al contactar soporte.",
            trace_id=trace_id,
        )

Y en el router, la lógica lanza errores de dominio —no HTTP—:

from fastapi import APIRouter

from app.errors import ModuleNotFound
from app.schemas.module import ModuleOut

router = APIRouter(prefix="/modules", tags=["modules"])


@router.get("/{slug}", response_model=ModuleOut)
async def get_module(slug: str) -> ModuleOut:
    module = await modules_repo.get_by_slug(slug)
    if module is None:
        raise ModuleNotFound(slug)      # el handler lo convierte en 404 Problem Details

proyectos/copiloto-api/app/main.py
# app/main.py
from fastapi import FastAPI

from app.error_handlers import register_exception_handlers
from app.routers import ask, modules

app = FastAPI(title="Copiloto API", version="0.1.0")
register_exception_handlers(app)          # UNA llamada: toda la API queda cubierta
app.include_router(modules.router)
app.include_router(ask.router)

Decisiones y porqués:

  • Un único _problem(): la forma se define una vez. Añadir un campo al error es tocar un solo sitio.
  • Errores de dominio sin HTTP: ModuleNotFound no importa nada de FastAPI. Si mañana lo usas desde un CLI o un worker, sigue teniendo sentido.
  • Un trace_id en cada error: el cliente lo cita, tú lo buscas en los logs. Une la experiencia del usuario con tu observabilidad.
  • Dos handlers para errores no previstos: el catch-all Exception loguea con logger.exception (traza completa en logs) y responde genérico. El cliente nunca ve el rastro.
  • Extensiones errors: en el 422, cada campo inválido con su mensaje. El frontend puede pintarlos junto al input correspondiente.

Cuidado con el orden y con los catch-all. Registra el handler de Exception al final y ten presente que Starlette solo aplica handlers de Exception si la app no está en modo depuración para ese error. En desarrollo, con --reload, puede que veas la traza; en producción, no. Prueba el catch-all con fastapi run antes de confiarte.

6 · Errores habituales

Filtrar la traza de Python al cliente

Mal — el cliente ve tus internals 
# ❌ Devolver la excepcion cruda revela rutas, versiones y estructura interna.
@app.get("/ask")
async def ask(q: str):
    try:
        return await engine.run(q)
    except Exception as exc:
        return JSONResponse(status_code=500, content={"detail": repr(exc)})
Bien — genérico al cliente, detalle en logs 
# ✅ El cliente recibe un 500 con trace_id; la traza completa va al log.
@app.exception_handler(Exception)
async def unhandled(request: Request, exc: Exception):
    trace_id = uuid.uuid4().hex
    logger.exception("unhandled path=%s trace=%s", request.url.path, trace_id)
    return _problem(request, status=500, detail="Error interno.", trace_id=trace_id)

Usar 200 OK con un cuerpo de error

Mal — todo responde 200 
# ❌ El cliente no puede distinguir exito de fallo sin leer el cuerpo.
@app.get("/modules/{slug}")
async def get_module(slug: str):
    module = await repo.get_by_slug(slug)
    if module is None:
        return {"ok": False, "error": "no encontrado"}     # ¡status 200!
    return {"ok": True, "data": module}
Bien — código HTTP correcto 
# ✅ 404 dice lo que pasa sin leer el cuerpo; el cuerpo explica el detalle.
@app.get("/modules/{slug}", response_model=ModuleOut)
async def get_module(slug: str) -> ModuleOut:
    module = await repo.get_by_slug(slug)
    if module is None:
        raise ModuleNotFound(slug)
    return module

Capturar Exception en cada ruta

Mal — try/except repetido y silencioso 
# ❌ Ruido, y ademas oculta el error real (except: pass).
@app.get("/ask")
async def ask(q: str):
    try:
        return await engine.run(q)
    except Exception:
        return {"detail": "error"}
Bien — un handler global hace ese trabajo 
# ✅ Sin try/except: el handler catch-all centraliza el comportamiento.
@app.get("/ask", response_model=AskOut)
async def ask(payload: AskIn) -> AskOut:
    return await engine.run(payload.question)

Inventar un formato distinto en cada ruta

Mal — tres formatos, tres maneras de fallar 
# ❌ El cliente no sabe que esperar.
raise HTTPException(404, detail={"error": "no encontrado"})   # dict
raise HTTPException(403, detail="sin permisos")               # string
raise HTTPException(429, detail=[1, 2, 3])                    # lista
Bien — un handler normaliza todo 
# ✅ Da igual lo que lances: el handler produce siempre Problem Details.
raise HTTPException(status_code=429, detail="Demasiadas peticiones")
# -> { "type": ".../rate-limited", "title": "Demasiadas peticiones",
#      "status": 429, "detail": "...", "instance": "...", "trace_id": "..." }

8 · Reto

🎯 Un catálogo de problemas documentado y testeado

Construye un catálogo de tipos de problema para Copiloto API: una única estructura (por ejemplo, un Enum o un diccionario) que asocie cada type con su title, su status sugerido y una descripción. Deriva de ella PROBLEM_TYPES y TITLES para no duplicar datos, expón el catálogo como JSON en GET /problems (público, sin autenticación) y añade un test que falle si algún handler usa un status que no está en el catálogo o un type que no respeta el prefijo https://copiloto.academy/problems/.

Pista: documenta cada problema con responses={404: {"model": ProblemDetail}} en el decorador para que aparezca en el OpenAPI. Piensa cómo modelar la extensión errors como un modelo Pydantic propio (FieldError) en lugar de una lista de dicts sin tipo.

9 · Resumen

  • El error es parte del contrato: modela también lo que sale mal.
  • HTTPException es el error controlado; los handlers le dan una forma única.
  • Problem Details (RFC 9457) es el estándar: type, title, status, detail, instance, y extensiones como trace_id y errors.
  • Se sirve como application/problem+json.
  • Registra tres handlers: StarletteHTTPException, RequestValidationError y Exception (catch-all).
  • Las excepciones de dominio no conocen HTTP; el handler las traduce.
  • Nunca devuelvas la traza: genérico al cliente, completo en los logs.

10 · Preguntas frecuentes

¿HTTPException o una excepción de dominio propia?

Depende de dónde estés. En la capa HTTP (una ruta, una dependencia de seguridad), HTTPException es directo y correcto. En la capa de negocio (servicios, repositorios), usa excepciones de dominio sin dependencia de FastAPI y tradúcelas con un handler. Ganancia: tu lógica se testea y se reutiliza sin arrastrar HTTP.

¿Por qué el 422 y no el 400 para errores de validación?

Porque históricamente FastAPI usa 422 Unprocessable Content para fallos de validación semántica (el cuerpo es válido como JSON pero no cumple el esquema). 400 Bad Request se reserva para peticiones malformadas de forma más general. Puedes cambiar el código en el handler si tu organización prefiere 400, pero sé consistente y documenta la decisión.

¿El handler de Exception captura todas las excepciones?

Captura las que se propagan por el flujo normal de la app. En modo depuración (por ejemplo --reload con debug), Starlette puede re-lanzar para mostrarte la traza en pantalla, que es justo lo que quieres en desarrollo. Verifica el comportamiento del catch-all con fastapi run (sin recarga) antes de confiar en él en producción.

¿Necesito type e instance si mi API es pequeña?

Puedes dejar type en "about:blank" (el valor por defecto del RFC) y omitir instance. Aun así, merece la pena mantener el sobre estándar: el día que añadas un frontend que distingue tipos de error, ya tienes dónde ponerlos. Es más fácil no romper tu contrato que crearlo tarde.

¿Y los errores de 429 del rate limiting del módulo 5?

Encajan aquí: lanza una excepción (o un HTTPException con 429) y deja que el handler de StarletteHTTPException lo convierta en Problem Details. Añade el tipo …/rate-limited a tu catálogo y, si quieres ser fino, una cabecera Retry-After que verás en la lección 3 sobre cabeceras.
