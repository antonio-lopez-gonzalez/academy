Sub-dependencias, clases y yield

Módulo 3 · Dependencias y configuración 🕐 30 minutos

1 · Introducción

En la lección anterior aprendiste a declarar lo que tu endpoint necesita. Pero las dependencias casi nunca viven solas: la sesión de base de datos necesita el engine, el usuario autenticado necesita el token, y el token necesita los settings. Esas piezas forman un árbol de dependencias que FastAPI resuelve por ti antes de entrar al endpoint.

Esta lección cierra tres cabos sueltos muy prácticos: cómo se anidan las dependencias, cómo escribir dependencias como clases (para agrupar parámetros relacionados) y cómo usar yield para manejar recursos que hay que cerrar (sesiones, conexiones, ficheros, locks). Y un bonus que ahorra muchísimo copia-pega: declarar dependencias a nivel de router.

¿Por qué existe esta lección? Porque un endpoint real rara vez necesita una sola cosa. Necesita «un usuario autenticado, con su sesión de base de datos, dentro de una transacción que se cierra pase lo que pase». Eso es un árbol de dependencias con yield al final. Si no lo dominas, acabarás abriendo conexiones a mano dentro del endpoint y olvidando cerrarlas cuando algo falla.

Errores típicos que verás aquí: usar yield sin try/finally (la conexión se queda abierta si hay una excepción), poner lógica de negocio dentro de una dependencia, esperar que una dependencia de router se inyecte como parámetro, y commitear una transacción después del yield sin entender cuándo se ejecuta ese código.

2 · Teoría

Sub-dependencias: el árbol se resuelve en profundidad

Una dependencia puede declarar a su vez sus propias dependencias con Depends. FastAPI inspecciona la firma del endpoint, ve qué dependencias necesita, y para cada una inspecciona su firma… y así hasta la raíz. La resolución es en profundidad: primero las hojas, luego las ramas, y por último el endpoint.

  ENDPOINT  /ask
     │  declara:  user, session, engine
     ▼
  get_current_user(request) ─────────► necesita: token
     │                                        │
     │                                        ▼
     │                                 get_token(header) ──► necesita: settings
     ▼                                                              │
  get_session(engine) ──► necesita: engine                          ▼
     │                            │                          get_settings()
     ▼                            ▼
  (Sesión lista)          (Engine listo)

  Orden de construcción:  hojas → ramas → endpoint
  Orden de limpieza:      inverso (LIFO): lo último creado, lo primero cerrado

Dentro de una misma petición, cada dependencia se ejecuta una sola vez (la caché que vimos en la lección 1). Si get_settings lo necesitan get_token y get_session, se llama una vez y ambas reciben el mismo objeto.

Nota: la caché se identifica por la pareja (función, use_cache). Dos parámetros que piden la misma dependencia comparten resultado; si necesitas uno distinto, usa use_cache=False o una función envoltorio.

Dependencias como clases

Un grupo de parámetros relacionados (paginación, filtros, orden) no merece tres parámetros sueltos en cada endpoint. Puedes encapsularlos en una clase: su __init__ es la firma de la dependencia y FastAPI construye una instancia como valor inyectado.

from typing import Annotated
from fastapi import Depends, FastAPI

app = FastAPI()


class Pagination:
    def __init__(self, skip: int = 0, limit: int = 20):
        self.skip = skip
        self.limit = limit


@app.get("/modules")
def list_modules(page: Annotated[Pagination, Depends()]):
    # Depends() sin argumentos infiere Pagination del tipo anotado
    return {"skip": page.skip, "limit": page.limit}

Fíjate en Depends() sin argumentos dentro de Annotated[Pagination, Depends()]: como el tipo ya está anotado, FastAPI usa la propia clase como dependencia. Es azúcar sintáctico de Depends(Pagination).

FormaCuándo usarla
def pagination_params(skip, limit) y Depends(pagination_params)Cuando solo necesitas valores sueltos o un dataclass simple
class Pagination y Annotated[Pagination, Depends()]Cuando quieres agrupar parámetros y quizá algún método derivado (page.offset, page.as_query())

Analogía: una dependencia-función es una máquina que te da una cosa. Una dependencia-clase es una caja de herramientas con su propio estado: los parámetros entran por la tapa (__init__) y dentro guardas también los métodos que operan sobre ellos.

yield: recursos con limpieza

Cuando la dependencia produce un recurso que hay que cerrar (sesión de BD, conexión, fichero, lock), no puedes limitarte a un return. Usas yield: el código antes del yield prepara el recurso, el valor se inyecta, y el código después del yield lo limpia.

from typing import Annotated
from fastapi import Depends


def get_session() -> "Session":
    session = SessionLocal()          # 1) ANTES del yield: preparar
    try:
        yield session                 # 2) se inyecta en el endpoint
        session.commit()              # 3) DESPUÉS: camino feliz
    except Exception:
        session.rollback()            # 3b) si algo falla
        raise                         #      re-lanza, no te lo tragues
    finally:
        session.close()               # 4) SIEMPRE: cerrar el recurso

El try/finally no es opcional. Si escribes yield session y luego session.close() sin try/finally, cualquier excepción en el endpoint o en el commit salta el cierre y dejas la conexión colgada. En una API con carga, eso agota el pool de conexiones en minutos.

Con varias dependencias con yield encadenadas, FastAPI ejecuta su limpieza en orden inverso (el último creado cierra primero). Es el mismo orden que los with anidados en Python.

¿Cuándo se ejecuta la limpieza? La pregunta del millón

Por defecto, el código después del yield se ejecuta después de enviar la respuesta al cliente (scope="request"). Eso significa que, por defecto, ya no puedes cambiar la respuesta en el cleanup: el cliente ya la recibió. Desde FastAPI 0.121.0 puedes pedir scope="function" para que el cleanup ocurra justo cuando termina la función del endpoint, antes de enviar la respuesta.

scopeCuándo corre el cleanupCuándo te interesa
"request" (por defecto)Después de enviar la respuestaCerrar sesiones/conexiones que ya no se necesitan para la respuesta
"function"Al terminar el endpoint, antes de enviar la respuestaCommitear una transacción, escribir cabeceras o hacer algo que la respuesta aún pueda reflejar
 
def get_session() -> "Session":
    session = SessionLocal()
    try:
        yield session
        session.commit()      # con scope="function" esto corre antes de responder
    except Exception:
        session.rollback()
        raise
    finally:
        session.close()


@app.post("/modules")
def create_module(
    session: Annotated[object, Depends(get_session, scope="function")],
):
    ...

Regla práctica: si tu cleanup hace commit (o algo que la respuesta deba reflejar), usa scope="function". Si solo cierra recursos, el valor por defecto ("request") está bien.

Dependencias a nivel de router

Cuando todos los endpoints de un router comparten una dependencia (autenticación, comprobación de plan, cabeceras obligatorias), no la repitas en cada firma. Declárala en el APIRouter:

from fastapi import APIRouter, Depends

router = APIRouter(
    prefix="/admin",
    tags=["admin"],
    dependencies=[Depends(require_admin)],   # se ejecuta en TODAS las rutas del router
)


@router.get("/metrics")
def metrics():
    # No necesita declarar require_admin: ya corre antes
    return {"ok": True}

Ojo con el valor devuelto: las dependencias de router se usan por su efecto (autorizar, validar, registrar), no se inyectan como parámetro. require_admin puede devolver lo que quiera, pero metrics() no lo recibe. Si necesitas el valor dentro del endpoint, declara la dependencia en la firma.

También puedes añadirlas al montar el router, lo que resulta útil para la app entera:

app.include_router(admin_router, dependencies=[Depends(verify_api_key)])

Y en el propio FastAPI(...) para que apliquen a todo:

app = FastAPI(dependencies=[Depends(log_request)])

3 · Ejemplo mínimo

Un ejemplo de 20 líneas que combina las dos ideas: una clase de paginación y un recurso gestionado con yield que imprime cuándo se abre y cuándo se cierra. Ejecútalo con uv.

main.py
from typing import Annotated

from fastapi import Depends, FastAPI

app = FastAPI()


class Pagination:
    """Dependencia-clase: agrupa y valida parámetros de paginación."""

    def __init__(self, skip: int = 0, limit: int = 20):
        self.skip = skip
        self.limit = limit


def get_connection():
    """Recurso con ciclo de vida: se abre antes del yield y se cierra al final."""
    print("[conn] abro conexión")
    try:
        yield {"open": True}
    finally:
        print("[conn] cierro conexión")


@app.get("/modules")
def list_modules(
    page: Annotated[Pagination, Depends()],
    conn: Annotated[dict, Depends(get_connection)],
):
    # El endpoint solo usa los valores; no abre ni cierra nada
    return {"skip": page.skip, "limit": page.limit, "connected": conn["open"]}

Arranca el servidor:

uv run uvicorn main:app --reload

Abre http://127.0.0.1:8000/docs, ejecuta GET /modules y mira la consola del servidor:

[conn] abro conexión
[conn] cierro conexión

Qué ha pasado, paso a paso:

  1. FastAPI inspecciona la firma y ve dos parámetros con Depends: la clase Pagination y la función get_connection.
  2. Construye Pagination: crea una instancia leyendo los query params skip y limit, y los valida (si mandas ?limit=abc responde 422).
  3. Ejecuta get_connection hasta el yield y guarda el valor gestionado.
  4. Llama al endpoint con page y conn ya listos.
  5. Serializa la respuesta y, al terminar la petición, ejecuta el bloque finally: «cierro conexión».

Fíjate: el print de cierre aparece después de que el cliente reciba el JSON. Ese es el comportamiento por defecto (scope="request").

4 · Ejemplo real

En el Copiloto API, el histórico de consultas vive en una base de datos. El endpoint que lista el histórico necesita una sesión que se abra y se cierre sola, y el engine lo crearemos una sola vez en lifespan (lección 3). Aquí montamos el árbol completo: endpoint → sesión → engine, más una dependencia de router para exigir un usuario.

app/deps.py
from collections.abc import Iterator
from typing import Annotated

from fastapi import Depends, HTTPException, Request, status
from sqlmodel import Session

from app.config import Settings, get_settings
from app.models import User


def get_settings_dep() -> Settings:
    return get_settings()


def get_session(request: Request) -> Iterator[Session]:
    """Sesión de BD con limpieza garantizada.

    El engine ya existe (lo creó lifespan); aquí solo abrimos la sesión.
    """
    engine = request.app.state.engine
    with Session(engine) as session:      # el with ya garantiza el close()
        yield session


def get_current_user(
    request: Request,
    session: Annotated[Session, Depends(get_session)],
    settings: Annotated[Settings, Depends(get_settings_dep)],
) -> User:
    """Sub-dependencia: depende de la sesión y de los settings."""
    token = request.headers.get("authorization")
    if not token:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, detail="Falta el token")
    user = decode_and_fetch_user(token, session, settings.secret_key)
    if user is None:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, detail="Token inválido")
    return user


SessionDep = Annotated[Session, Depends(get_session)]
CurrentUser = Annotated[User, Depends(get_current_user)]


def require_admin(user: CurrentUser) -> None:
    """Dependencia de router: se usa por su efecto, no por su valor."""
    if user.role != "admin":
        raise HTTPException(status.HTTP_403_FORBIDDEN, detail="Requiere rol admin")
app/routers/history.py
from fastapi import APIRouter, Depends
from sqlmodel import select

from app.deps import CurrentUser, SessionDep, require_admin
from app.models import Query


router = APIRouter(prefix="/history", tags=["history"])


@router.get("")
def list_history(user: CurrentUser, session: SessionDep):
    # user ya viene resuelto: la cadena token → settings → user corrió antes
    rows = session.exec(select(Query).where(Query.user_id == user.id)).all()
    return {"items": [r.model_dump() for r in rows]}


@router.delete("/{query_id}")
def delete_query(
    query_id: int,
    user: CurrentUser,
    session: SessionDep,
    _: None = Depends(require_admin),      # sub-dependencia de router en la firma
):
    ...

Decisiones explicadas:

  • El árbol se declara, no se construye. get_current_user pide la sesión; la sesión pide el engine. Nadie llama a nadie a mano: FastAPI resuelve las hojas primero (get_session) y luego las ramas (get_current_user).
  • El with Session(engine) ya cierra. Aun usando yield, apoyarse en el gestor de contexto de SQLModel evita olvidar el close(). El with es el try/finally que no puedes escribir mal.
  • Alias de tipos (SessionDep, CurrentUser): los endpoints quedan legibles y el contrato, visible.
  • require_admin a nivel de router o de firma: como es un efecto (autorizar), no necesita inyectarse. En el router valdría para todos; en la firma, solo para el endpoint concreto.

Y el test que sustituye toda la cadena sin tocar la base de datos ni los tokens:

tests/test_history.py
from fastapi.testclient import TestClient

from app.deps import get_current_user, get_session
from app.main import app


class FakeUser:
    id = 1
    role = "admin"


def test_list_history_sin_bd():
    app.dependency_overrides[get_session] = lambda: None
    app.dependency_overrides[get_current_user] = lambda: FakeUser()
    try:
        client = TestClient(app)
        r = client.get("/history")
        assert r.status_code == 200
    finally:
        app.dependency_overrides.clear()

Detalle clave: al sustituir get_session y get_current_user, el árbol entero se corta en esos dos nodos. FastAPI no ejecuta las sub-dependencias que quedarían por debajo porque ya no hacen falta. Sustituir una rama poda todo lo que cuelga de ella.

5 · Buenas prácticas

Re-lanza tras hacer rollback() Tragarte la excepción con un except vacío Si no re-lanzas, FastAPI cree que todo fue bien y responde 200 con datos falsos

6 · Errores habituales

1. yield sin try/finally

❌ Incorrecto 
def get_session():
    session = SessionLocal()
    yield session
    session.close()      # si el endpoint lanza, NUNCA se ejecuta
✅ Correcto 
def get_session():
    session = SessionLocal()
    try:
        yield session
    finally:
        session.close()  # se ejecuta siempre, pase lo que pase

2. Esperar que la dependencia de router se inyecte

❌ Incorrecto 
router = APIRouter(dependencies=[Depends(current_user)])

@router.get("/perfil")
def perfil(user: CurrentUser):   # user NO se inyecta: no está en la firma
    ...                          # -> FastAPI lo trata como QUERY PARAM
✅ Correcto 
router = APIRouter(dependencies=[Depends(ensure_logged_in)])

@router.get("/perfil")
def perfil(user: CurrentUser):
    ...                          # declarada en la firma -> sí se inyecta

Las dependencias de router corren por su efecto. Si necesitas el valor dentro del endpoint, tienes que declararlo en su firma (aunque corra dos veces, la caché por petición evita el trabajo extra).

3. Tragarse la excepción en el cleanup

❌ Incorrecto 
def get_session():
    session = SessionLocal()
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()   # no re-lanza: el error desaparece...
    finally:
        session.close()      # ...y el cliente recibe un 200 sin haber guardado nada
✅ Correcto 
def get_session():
    session = SessionLocal()
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()
        raise                # deja que FastAPI convierta el error en una respuesta correcta
    finally:
        session.close()

4. Lógica de negocio dentro de la dependencia-clase

❌ Incorrecto 
class ModuleService:
    def __init__(self, session: Annotated[Session, Depends(get_session)]):
        # Esta clase CREA y EJECUTA el caso de uso entero:
        self.items = session.exec(select(Module)).all()   # efecto colateral oculto
✅ Correcto 
class ModuleFilters:
    def __init__(self, status: str | None = None, q: str | None = None):
        self.status = status
        self.q = q

    def apply(self, stmt):
        if self.status:
            stmt = stmt.where(Module.status == self.status)
        return stmt

La dependencia prepara datos; el endpoint decide qué hacer. Si el __init__ ya ejecuta consultas, no puedes testear el endpoint sin base de datos.

5. Olvidar que las sub-dependencias se cachean

❌ Incorrecto 
# Esperas dos sesiones distintas y "por seguridad" abres dos
def get_session(request: Request):
    return Session(request.app.state.engine)   # sin close, y creyendo que son independientes
✅ Correcto 
# Declara la misma dependencia donde haga falta: es UNA sola por petición
def a(session: SessionDep): ...
def b(session: SessionDep): ...   # recibe la MISMA sesión, ya cacheada

No necesitas inventar un «contexto» para compartir la sesión entre sub-dependencias: la caché por petición ya te la da. Y si de verdad quieres dos independientes, usa use_cache=False.

_db_events: list[str] = []   # solo para observar el ciclo de vida

    _db_events.append("open")

class Pagination:
    def __init__(self, skip: int = 0, limit: int = 20):
        self.skip = skip
        self.limit = limit

    @property
    def page(self) -> int:
        return self.skip // self.limit + 1


def get_tenant(x_tenant: Annotated[str | None, Header()] = None) -> str:
    if not x_tenant:
        raise HTTPException(status.HTTP_400_BAD_REQUEST, detail="Falta x-tenant")

SessionDep = Annotated[dict, Depends(get_db_session)]
TenantDep = Annotated[str, Depends(get_tenant)]

8 · Reto

🎯 Un stack de dependencias con ciclo de vida completo

Diseña, para el Copiloto API, la cadena de dependencias del caso de uso «crear una consulta»: settings → engine → session → current_user, de forma que la sesión se abra y se cierre automáticamente y el usuario se valide contra el token. Debes lograr que:

  • El endpoint POST /ask no abra ni cierre nada: declara session y user con alias de tipo.
  • La sesión use yield con try/finally, haga commit en el camino feliz y rollback + re-raise si el endpoint lanza.
  • La autorización aplique a todo el router de escritura con dependencies=[...], sin repetirla en cada ruta.
  • Un test sustituya get_session y get_current_user y compruebe el 200 sin base de datos real.
  • Un segundo test compruebe que, si el endpoint lanza una excepción, el rollback se ejecuta (pista: una dependencia falsa puede registrar el orden de las llamadas).

Pista: el orden de limpieza es inverso al de creación, así que si el commit va tras el yield y quieres reflejarlo en la respuesta, declara la dependencia con Depends(get_session, scope="function"). Recuerda que las dependencias de router se usan por su efecto: para tener el user dentro del endpoint, decláralo también en la firma.

9 · Resumen

  • Las dependencias pueden declarar sus propias dependencias: FastAPI resuelve el árbol en profundidad y la caché por petición comparte los nodos comunes.
  • Una clase es una dependencia válida: su __init__ es la firma y Annotated[T, Depends()] la infiere del tipo.
  • yield separa preparación y limpieza; envuélvelo en try/finally y re-lanza tras el rollback.
  • La limpieza corre después de la respuesta (scope="request") salvo que uses scope="function", que la adelanta al final del endpoint.
  • Las dependencias de router (dependencies=[...]) aplican a todas sus rutas y se usan por su efecto, no como valor inyectado.

10 · Preguntas frecuentes

¿Puedo tener más de un yield en una dependencia?

No. FastAPI usa la dependencia como un context manager generador: un único yield. Si necesitas producir varias cosas, devuelve un objeto (o un dataclass) con varios campos, o yield una tupla y desestrúctúrala en el endpoint.

¿La misma dependencia se ejecuta una vez por endpoint o una vez por petición?

Una vez por petición. Aunque diez parámetros pidan Depends(get_session) en un árbol, se construye una sola sesión y todos los nodos la comparten. Si necesitas dos instancias distintas, marca use_cache=False.

¿Cuándo uso scope="function" en lugar del valor por defecto?

Cuando el código posterior al yield hace algo que la respuesta debe reflejar: un commit, actualizar cabeceras, medir el tiempo total. Con scope="request" (por defecto) ese código corre cuando la respuesta ya salió, así que ya no puede cambiarla.

¿Por qué mi dependencia de router no aparece como parámetro en el endpoint?

Porque dependencies=[...] ejecuta la dependencia por su efecto (autorizar, validar, registrar), pero no la inyecta. Si el endpoint necesita su valor, declárala otra vez en la firma; la caché por petición hace que no se ejecute dos veces.

¿Las dependencias-clase se pueden testear?

Sí, igual que una función: usas la clase en un Depends() y la sustituyes con app.dependency_overrides[Pagination] = FakePagination. Al ser clases, además puedes instanciarlas directamente en un test unitario para comprobar su lógica (Pagination(skip=40, limit=20).page == 3).
