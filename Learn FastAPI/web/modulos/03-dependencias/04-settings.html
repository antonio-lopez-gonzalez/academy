Configuración con pydantic-settings

Módulo 3 · Dependencias y configuración 🕐 30 minutos

1 · Introducción

Toda aplicación tiene cosas que cambian entre entornos: la URL de la base de datos, la clave secreta del JWT, el nivel de log, si el modo debug está activo. En local quieres SQLite y logs verbosos; en producción, Postgres y logs sobrios. Y sobre todo: los secretos no pueden estar en el código ni en el repositorio.

El patrón clásico —leer os.getenv y convertirlo a mano— se rompe enseguida: "false" no es False, un número mal escrito pasa desapercibido y nunca sabes qué variables requiere la aplicación hasta que falla en producción. pydantic-settings resuelve esto modelando la configuración con Pydantic: se declara una clase, se cargan los valores desde variables de entorno y .env, se validan y convierten los tipos, y se inyectan por dependencia como cualquier otra cosa.

¿Por qué existe esta lección? Porque «configuración» es donde se filtran los secretos, donde revientan los despliegues («funcionaba en mi máquina») y donde el tipado salva vidas. Settings es el punto único de verdad de tu configuración, tipado y validado al arrancar. Si falta algo o está mal, la app no arranca, y eso es una virtud: falla rápido y en tu portátil, no en producción a las 3 de la mañana.

Errores típicos que verás: claves hardcodeadas, construir Settings() en cada petición, parsear booleanos a mano, versionar el .env con secretos reales y leer variables sueltas por todo el código en lugar de una clase central.

2 · Teoría

El problema: configuración dispersa y sin tipos

Imagina leer la configuración con os.getenv repartido por diez módulos:

# ❌ Configuración dispersa y sin validar
import os

DEBUG = os.getenv("DEBUG", "false") == "true"          # conversión manual
DB_URL = os.getenv("DATABASE_URL")                      # ¿y si falta? None silencioso
SECRET = os.getenv("SECRET_KEY", "changeme")            # secreto por defecto peligroso
MAX_TOKENS = int(os.getenv("MAX_TOKENS", "512"))        # revienta con valor no numérico

Cuatro problemas: dispersión (no hay una lista de lo que necesitas), sin validación (un typo en una variable pasa como None), conversiones manuales (fáciles de equivocar) y secretos por defecto que acaban en producción.

La solución: una clase Settings

pydantic-settings extiende Pydantic con BaseSettings. Declaras los campos con su tipo y un valor por defecto opcional; la librería busca cada valor en las fuentes configuradas y lo valida.

from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",              # carga variables desde este fichero
        env_file_encoding="utf-8",
        extra="ignore",               # ignora variables de entorno desconocidas
    )

    environment: str = "dev"
    database_url: str = "sqlite:///./copiloto.db"
    debug: bool = False               # "true"/"1"/"yes" se convierten solos
    max_tokens: int = 512
    secret_key: SecretStr             # sin valor por defecto -> obligatorio

Fíjate en secret_key: SecretStr sin valor por defecto: si no hay variable SECRET_KEY en el entorno ni en el .env, construir Settings() lanza ValidationError. La app no arranca con configuración incompleta. Ese fail fast es exactamente lo que quieres.

Analogía: Settings es la checklist de pre-vuelo de un avión. Antes de despegar (arrancar la app) el piloto recorre la lista; si algo falta o está fuera de rango, el avión no despega. Leer os.getenv a vuelapluma sería despegar confiando en la memoria: tarde o temprano olvidas el tren de aterrizaje.

De dónde salen los valores y en qué orden

Cada fuente tiene una prioridad. Gana la primera que tenga el valor:

  Prioridad (de mayor a menor)

  1. Argumentos del constructor   Settings(database_url="...")   ← tests, overrides
  2. Variables de entorno         export DATABASE_URL=...        ← producción, Docker
  3. Fichero .env                 DATABASE_URL=...               ← desarrollo local
  4. Valor por defecto del campo  database_url: str = "sqlite..."← último recurso
ConceptoEjemploPara qué
Nombre de variablecampo database_url → DATABASE_URLPor defecto no distingue mayúsculas de minúsculas
env_prefixSettingsConfigDict(env_prefix="copiloto_")Evita colisiones con variables ajenas (COPILOTO_DATABASE_URL)
env_fileenv_file=".env" o una tupla (".env", ".env.local")Ficheros cargados por orden; el último gana

Un .env no sobrescribe a las variables de entorno reales. Es una decisión deliberada: si en producción un contenedor inyecta DATABASE_URL, esa gana sobre el .env que empaquetaste. Así un mismo artefacto se comporta distinto según el entorno, sin recompilar ni tocar código.

Tipos que hacen el trabajo sucio

La gracia está en que Pydantic convierte y valida. Estos tipos son los que más se usan:

from enum import Enum
from pydantic import AnyHttpUrl, PostgresDsn, SecretStr
from pydantic_settings import BaseSettings


class Env(str, Enum):
    dev = "dev"
    staging = "staging"
    prod = "prod"


class Settings(BaseSettings):
    environment: Env = Env.dev
    debug: bool = False                       # "true", "1", "yes" -> True
    database_url: PostgresDsn | None = None   # valida el formato de la URL
    rag_service_url: AnyHttpUrl               # valida que sea http(s)://
    secret_key: SecretStr                     # no se imprime al hacer print/log
    allowed_origins: list[str] = []           # desde JSON: '["https://a.com"]'

SecretStr evita fugas accidentales. Si haces print(settings) o lo vuelcas a un log, el secreto aparece como SecretStr('**********'). Para obtener el valor real, pídelo explícitamente: settings.secret_key.get_secret_value(). Solo hazlo justo donde toca (firmar un JWT), nunca al loguear.

Entornos: dev, staging y prod

El patrón habitual tiene un fichero por entorno y un selector:

.env               ← valores por defecto para desarrollo local (NO se versiona)
.env.example       ← plantilla con las claves y valores de ejemplo (SÍ se versiona)
.env.production    ← solo las diferencias de producción (normalmente no se versiona)

Y en el código se elige el fichero según una variable (por ejemplo APP_ENV):

import os
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=(".env", f".env.{os.getenv('APP_ENV', 'dev')}"),
        env_file_encoding="utf-8",
        extra="ignore",
    )

    environment: str = "dev"
    database_url: str = "sqlite:///./copiloto.db"

El .env no se versiona. Añádelo a .gitignore. Lo que sí se versiona es un .env.example con las claves necesarias y valores de mentira, para que cualquiera sepa qué configurar sin exponer secretos. Un secreto que llegó a un commit está comprometido aunque lo borres después: hay que rotarlo.

Inyectar Settings por dependencia

Aquí se junta todo con el módulo. Construir Settings() en cada petición leería el entorno una y otra vez sin necesidad: es un objeto inmutable durante la vida de la app, así que se construye una vez y se cachea. Y se expone por dependencia para que los endpoints lo declaren y los tests lo puedan sustituir.

from functools import lru_cache
from typing import Annotated

from fastapi import Depends

from app.config import Settings


@lru_cache
def get_settings() -> Settings:
    """Se construye UNA vez por proceso y se reutiliza en todas las peticiones."""
    return Settings()


SettingsDep = Annotated[Settings, Depends(get_settings)]

Un endpoint queda así de limpio:

from fastapi import APIRouter

from app.deps import SettingsDep

router = APIRouter()


@router.get("/config")
def show_config(settings: SettingsDep):
    return {
        "environment": settings.environment,
        "debug": settings.debug,
        "database_url": settings.database_url,
        # secret_key NUNCA se serializa
    }

Por qué @lru_cache y no app.state: Settings es inmutable y no necesita ciclo de vida, así que @lru_cache sobre get_settings es lo más simple: se construye la primera vez que se pide y se reutiliza. Ese objeto Settings sí conviene además cargarlo en el lifespan (lección 3) para fallar al arrancar si la configuración es inválida, antes de aceptar la primera petición.

En los tests, como es una dependencia normal, puedes sustituirla o limpiar la caché:

from app.deps import get_settings

# Opción 1: override de la dependencia (recomendado)
app.dependency_overrides[get_settings] = lambda: Settings(debug=True)

# Opción 2: limpiar la caché si construyes Settings con variables distintas
get_settings.cache_clear()

3 · Ejemplo mínimo

Una Settings con tres campos, un .env y un endpoint que muestra la configuración (sin secretos). Ejecutable con uv.

cd copiloto-settings
uv add fastapi "uvicorn[standard]" pydantic-settings
main.py
from functools import lru_cache
from typing import Annotated

from fastapi import Depends, FastAPI
from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")

    environment: str = "dev"
    debug: bool = False
    max_tokens: int = 512
    secret_key: SecretStr = SecretStr("changeme-en-dev")


@lru_cache
def get_settings() -> Settings:
    return Settings()


SettingsDep = Annotated[Settings, Depends(get_settings)]

app = FastAPI()


@app.get("/config")
def show_config(settings: SettingsDep):
    return {
        "environment": settings.environment,
        "debug": settings.debug,
        "max_tokens": settings.max_tokens,

.env
ENVIRONMENT=dev
DEBUG=true
MAX_TOKENS=1024
SECRET_KEY=una-clave-solo-para-local

Arranca el servidor:

uv run uvicorn main:app --reload

Llama a GET /config y verás:

{
  "environment": "dev",
  "debug": true,
  "max_tokens": 1024
}

Qué ha pasado, paso a paso:

  1. Se construye Settings() la primera vez que una petición pide SettingsDep. Busca cada campo: environment, debug, max_tokens, secret_key.
  2. Lee el .env y mapea DEBUG=true al campo debug: bool, convirtiendo la cadena "true" en el booleano True. Y MAX_TOKENS=1024 en el entero 1024.
  3. @lru_cache guarda el objeto: las siguientes peticiones reutilizan la misma instancia. No se vuelve a leer el entorno.
  4. El endpoint serializa los campos; secret_key no se incluye porque es un SecretStr y nunca lo tocamos. El secreto jamás sale en la respuesta.

Prueba a quitar MAX_TOKENS del .env y a escribir MAX_TOKENS=abc. Al pedir Settings(), Pydantic lanza un ValidationError claro («Input should be a valid integer»). Eso es la validación trabajando por ti.

4 · Ejemplo real

En el Copiloto API la configuración tiene secciones: base de datos, servicio de RAG y seguridad. Usamos ajustes anidados y un env_prefix, inyectamos Settings por dependencia y lo cargamos en el lifespan para fallar al arrancar si algo está mal.

app/config.py
from functools import lru_cache
from typing import Annotated, Literal

from fastapi import Depends
from pydantic import AnyHttpUrl, PostgresDsn, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class DatabaseSettings(BaseSettings):
    url: PostgresDsn | str = "sqlite:///./copiloto.db"
    echo: bool = False
    pool_size: int = 5


class RagSettings(BaseSettings):
    service_url: AnyHttpUrl = "http://127.0.0.1:9000"
    timeout_seconds: float = 10.0
    top_k: int = 4


class SecuritySettings(BaseSettings):
    secret_key: SecretStr = SecretStr("changeme-en-dev")
    algorithm: Literal["HS256", "RS256"] = "HS256"
    access_token_minutes: int = 30


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_prefix="copiloto_",
        env_file=(".env", ".env.local"),
        env_file_encoding="utf-8",
        env_nested_delimiter="__",   # COPILOTO_DB__HOST llena db.host
        extra="ignore",
    )

    environment: Literal["dev", "staging", "prod"] = "dev"
    debug: bool = False
    database: DatabaseSettings = DatabaseSettings()
    rag: RagSettings = RagSettings()
    security: SecuritySettings = SecuritySettings()


@lru_cache
def get_settings() -> Settings:
    """Construida una vez por proceso; validada al importar/arrancar."""
    return Settings()


SettingsDep = Annotated[Settings, Depends(get_settings)]
.env.example
# Copia este fichero a .env y rellena los valores. NO subas .env al repo.
COPILOTO_ENVIRONMENT=dev
COPILOTO_DEBUG=true
COPILOTO_DATABASE__URL=sqlite:///./copiloto.db
COPILOTO_RAG__SERVICE_URL=http://127.0.0.1:9000
COPILOTO_RAG__TIMEOUT_SECONDS=10
COPILOTO_SECURITY__SECRET_KEY=pon-aqui-una-clave-larga-y-aleatoria
app/main.py
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI
from sqlmodel import create_engine

from app.config import get_settings


@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = get_settings()          # falla aquí si la config es inválida: fail fast
    app.state.settings = settings
    app.state.engine = create_engine(str(settings.database.url), echo=settings.database.echo)
    app.state.http = httpx.AsyncClient(
        base_url=str(settings.rag.service_url),
        timeout=settings.rag.timeout_seconds,
    )
    try:
        yield
    finally:
        await app.state.http.aclose()
        app.state.engine.dispose()


app = FastAPI(title="Copiloto API", lifespan=lifespan)


from app.routers import ask, health   # noqa: E402

app.include_router(health.router)
app.include_router(ask.router)
app/routers/health.py
from fastapi import APIRouter

from app.config import SettingsDep

router = APIRouter()


@router.get("/health")
def health(settings: SettingsDep):
    return {
        "status": "ok",
        "environment": settings.environment,
        "top_k": settings.rag.top_k,       # acceso por secciones anidadas
    }

Decisiones explicadas:

  • Secciones anidadas (database, rag, security): la configuración se lee por bloques y el editor autocompleta. El delimitador __ permite mapear COPILOTO_RAG__TOP_K a settings.rag.top_k.
  • env_prefix="copiloto_": todas las variables quedan bajo un espacio propio y no chocan con las de otros servicios del mismo host.
  • .env + .env.local: la tupla se carga en orden; .env.local (ignorado por Git) puede sobrescribir para tu máquina sin ensuciar la plantilla.
  • get_settings() con @lru_cache: una única instancia validada por proceso; los tests la sustituyen con dependency_overrides.
  • Carga en lifespan: si falta SECRET_KEY o una URL es inválida, la app no arranca. El fail fast convierte un bug de producción en un error de arranque.
.gitignore
.env
.env.*
!.env.example

Regla de oro: .env fuera del repositorio, .env.example dentro. Cualquiera que clone el proyecto copia la plantilla, rellena sus valores y arranca. Y si un secreto llegó a un commit, se rota: borrarlo del último commit no lo borra del historial.

6 · Errores habituales

1. Secretos hardcodeados

❌ Incorrecto 
SECRET_KEY = "super-secreto-123"     # en el código, en el repo, para siempre
DATABASE_URL = "postgres://user:pass@prod:5432/db"
✅ Correcto 
class SecuritySettings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="copiloto_security_")
    secret_key: SecretStr            # obligatorio: viene del entorno

Un secreto en el código está en cada clon, en tu historial de Git y en las copias de seguridad. Se inyecta por entorno, nunca se escribe.

2. Construir Settings() por petición

❌ Incorrecto 
@app.get("/config")
def show_config():
    settings = Settings()      # relee y valida el entorno en CADA petición
    return {"env": settings.environment}
✅ Correcto 
@lru_cache
def get_settings() -> Settings:
    return Settings()

@app.get("/config")
def show_config(settings: SettingsDep):
    return {"env": settings.environment}

3. Convertir variables a mano

❌ Incorrecto 
import os

debug = os.getenv("DEBUG") == "true"        # "True"/"1"/"yes" se interpretan como False
timeout = float(os.getenv("TIMEOUT"))       # si falta -> TypeError al arrancar
✅ Correcto 
class Settings(BaseSettings):
    debug: bool = False        # Pydantic entiende "true", "1", "yes"...
    timeout: float = 10.0      # y da un error claro si el valor no es numérico

4. Versionar el .env con secretos

❌ Incorrecto 
git add .env      # con SECRET_KEY real: ya está comprometido
git commit -m "config"
✅ Correcto 
# .gitignore
.env
.env.*
!.env.example

git add .env.example   # solo la plantilla, sin valores reales

5. Configuración mutable en tiempo de ejecución

❌ Incorrecto 
@app.post("/admin/limits")
def set_limit(settings: SettingsDep):
    settings.rag.top_k = 10      # "cambio la config en caliente" -> se pierde al reiniciar
    return {"top_k": settings.rag.top_k}
✅ Correcto 
# La configuración es INMUTABLE. Lo que cambia en caliente va a la BD (o a un store):
@router.post("/admin/limits")
def set_limit(top_k: int, session: SessionDep):
    session.add(SettingValue(name="rag_top_k", value=str(top_k)))
    return {"top_k": top_k}

Settings describe el entorno, no el estado de la aplicación. Lo que un usuario pueda cambiar en caliente vive en la base de datos, no en la configuración.

8 · Reto

🎯 La configuración completa del Copiloto API

Diseña el módulo de configuración del Copiloto API con secciones anidadas, validación estricta y separación de entornos. Debes lograr que:

  • Haya tres secciones: database, rag y security, con env_nested_delimiter="__" y env_prefix="copiloto_".
  • environment sea un Literal["dev","staging","prod"] y las URLs se validen (PostgresDsn/AnyHttpUrl) con un mensaje de error legible.
  • Los secretos (secret_key) sean SecretStr y nunca aparezcan en un log: escribe un endpoint /debug/config que serialice toda la config sin filtrar secretos y compruébalo.
  • Se cargue en el lifespan y la app no arranque si falta SECRET_KEY o una URL es inválida.
  • Un test sustituya get_settings por una Settings de test con SQLite y compruebe que el endpoint que construye el engine usa la URL falsa.
  • Un .env.example documente todas las claves y un .gitignore excluya .env.

Pista: para «serializar sin filtrar secretos», usa model_dump() sobre un modelo donde el secreto esté tipado como SecretStr (se convierte en **********), o simplemente no incluyas ese campo. Comprueba en el test que la respuesta no contiene el valor real del secreto. Para el fail fast, llama a get_settings() en la primera línea del lifespan, antes de crear el engine.

9 · Resumen

  • pydantic-settings modela la configuración con BaseSettings: tipos, validación y valores por defecto.
  • Las fuentes tienen prioridad: init > variables de entorno > .env > defaults. Por eso el entorno real gana sobre el .env.
  • Usa env_prefix para aislar tus variables, env_nested_delimiter para secciones y SecretStr para secretos.
  • Separa entornos con .env + .env.<entorno>; nunca versiones el .env real, sí el .env.example.
  • get_settings() con @lru_cache da una instancia única por proceso; se inyecta con SettingsDep.
  • Valida en el lifespan para fallar al arrancar (fail fast) si la config es inválida.

10 · Preguntas frecuentes

¿pydantic-settings es lo mismo que Pydantic?

No. En Pydantic v2, BaseSettings vive en un paquete aparte, pydantic-settings, que se instala con uv add pydantic-settings. pydantic te da los modelos y la validación; pydantic-settings añade los cargadores (entorno, .env, secretos) y la clase BaseSettings.

¿Por qué el .env no sobrescribe una variable de entorno?

Por diseño. La prioridad es: argumentos del constructor > variables de entorno > .env > defaults. Así un mismo build se puede desplegar en varios entornos inyectando variables (Docker, Kubernetes) sin tocar el fichero. En desarrollo local, sin variables externas, manda el .env.

¿Cómo pruebo el arranque cuando falta un secreto?

Haz el campo obligatorio (sin valor por defecto) y construye Settings() en el lifespan o en get_settings. Sin la variable, Pydantic lanza ValidationError y la app no arranca. En un test puedes comprobarlo con pytest.raises(ValidationError) pasando _env_file=None y un entorno limpio.

¿Debo usar @lru_cache o guardar Settings en app.state?

Para una configuración inmutable, @lru_cache sobre get_settings es lo más simple: una instancia por proceso, sin ciclo de vida que gestionar. Cargarlo además en el lifespan es útil para forzar la validación al arrancar. No necesitas meterlo en app.state salvo que quieras tenerlo todo junto con los demás recursos.

¿Cómo manejo listas o valores más complejos en una variable de entorno?

Pydantic-settings parsea tipos complejos desde JSON. Por ejemplo, allowed_origins: list[str] se llena con ALLOWED_ORIGINS='["https://a.com","https://b.com"]'. Para ajustes anidados usa el doble guion bajo (DB__HOST con env_nested_delimiter="__"). Si en algún caso no encaja, un field_validator te deja parsear el valor a tu gusto.
