Tests async con httpx

Módulo 6 · Testing y calidad 🕐 35 minutos

1 · Introducción

En la lección anterior testeas con TestClient en funciones def normales. Eso cubre el 90% de los casos y es lo primero que debes dominar. Pero hay situaciones donde el test tiene que ser asíncrono: tu app usa una sesión de base de datos async (AsyncSession), llamas a un cliente HTTP async, o quieres comprobar que varias peticiones concurrentes se comportan bien (por ejemplo, el rate limiting del Módulo 5).

El problema aparece en cuanto escribes un test async def y usas TestClient dentro: TestClient es síncrono —por dentro ejecuta la app en un hilo aparte— y no se puede usar desde código async sin bloquear el bucle de eventos. FastAPI te da una salida limpia: httpx.AsyncClient con un ASGITransport, es decir, el mismo mecanismo que usa TestClient pero en versión await.

¿Por qué existe esta lección? Porque «async» no es una preferencia estética: es lo que permite testear concurrencia de verdad y recursos async. Saber cuándo usar TestClient (sync, simple) y cuándo AsyncClient (async, potente) es una decisión de ingeniería, no un detalle de sintaxis.

Errores típicos que veremos: usar la forma antigua AsyncClient(app=app) (eliminada en httpx 0.27), olvidar el marcador que hace await-able el test —y que entonces pase sin ejecutarse— y asumir que el lifespan corre solo (no corre).

2 · Teoría

Por qué TestClient no sirve dentro de un test async

Una app FastAPI es, por debajo, un objeto ASGI: una corrutina. TestClient es síncrono y resuelve el desajuste ejecutando esa corrutina en un hilo de fondo con un portal de AnyIO, y bloqueando hasta que termina. Ese truco funciona perfectamente desde una función def… pero si tu test ya está dentro de un bucle de eventos, bloquearlo para esperar otro bucle es un error.

   test def  ──► TestClient ──► [hilo AnyIO] ──► app (async)    ✔ funciona
   test async def ──► TestClient ──► bloquear loop ──✗ deadlock / error

La solución no es «hacer el test sync», sino usar un cliente que también sea async: httpx.AsyncClient con un transport que llama a la app ASGI directamente.

ASGITransport: el puente en proceso

El transport es la pieza de httpx que decide por dónde viaja la petición. En producción es TCP; en tests es ASGI en memoria. Desde httpx 0.27 la forma correcta ya no es AsyncClient(app=app): hay que construir explícitamente el transport.

✗ Forma antigua (eliminada)
from httpx import AsyncClient

client = AsyncClient(app=app, base_url="http://test")   # TypeError en httpx ≥ 0.27
✓ Forma actual
from httpx import ASGITransport, AsyncClient

transport = ASGITransport(app=app)
client = AsyncClient(transport=transport, base_url="http://test")

base_url es obligatorio: httpx lo necesita para resolver rutas relativas. El valor no importa (se usa http://test por convención), pero si lo omites verás un error de «no se puede construir la URL».

Lifespan: aquí tampoco corre solo

El ASGITransport envía peticiones HTTP a la app, pero no envía los eventos de ciclo de vida (startup/shutdown). Si tu app abre recursos en lifespan y los guarda en app.state, con AsyncClient no existirán. La solución estándar es envolver el cliente en un gestor de lifespan:

tests/conftest.py (fragmento)
from asgi_lifespan import LifespanManager
from httpx import ASGITransport, AsyncClient

from app.main import app


async def make_client() -> AsyncClient:
    async with LifespanManager(app):                     # dispara startup ... shutdown
        transport = ASGITransport(app=app)
        async with AsyncClient(transport=transport, base_url="http://test") as client:
            yield client

Instálalo con uv add --dev asgi-lifespan. Si tu app no usa lifespan para nada crítico, puedes prescindir de él; pero conviene saber por qué los recursos no aparecen cuando sí importan.

pytest-asyncio: hacer que pytest espere corrutinas

pytest, por sí solo, no sabe ejecutar una función async def: la llamaría, obtendría una corrutina y la descartaría. El plugin pytest-asyncio cierra ese hueco de dos maneras:

ModoCómo se marcaCuándo usarlo
strict (por defecto)Solo los tests con @pytest.mark.asyncio se ejecutan como asyncProyectos que mezclan varias librerías async
autoEl marcador se añade solo a toda función async defProyectos 100% asyncio, como el nuestro (recomendado)
pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
asyncio_mode = "auto"
asyncio_default_fixture_loop_scope = "session"

El fallo silencioso más peligroso. En modo strict, si olvidas @pytest.mark.asyncio en un test async def, pytest-asyncio lo salta con un aviso («async def functions are not natively supported»). Resultado: un test que aparece como skip y nunca comprueba nada. Con asyncio_mode = "auto" ese problema desaparece.

Fixtures async

Una fixture que necesita await se declara con @pytest_asyncio.fixture (no con @pytest.fixture a secas). En modo auto, las fixtures async también se gestionan solas, pero ser explícito es más claro. Mira los dos planos: el scope de caché (cuántas veces se crea) y el loop scope (en qué bucle de eventos corre).

tests/conftest.py
import pytest_asyncio
from httpx import ASGITransport, AsyncClient

from app.main import app


@pytest_asyncio.fixture
async def client() -> AsyncClient:
    async with AsyncClient(
        transport=ASGITransport(app=app),
        base_url="http://test",
    ) as async_client:
        yield async_client

La regla del loop scope: la fixture no puede cambiar de bucle de eventos a mitad. Si una fixture de scope="session" corre en el bucle de sesión, los tests que la usen deben hacerlo también. En un proyecto pequeño, deja los valores por defecto y ajusta solo si ves errores de «attached to a different loop».

Lo que AsyncClient desbloquea: concurrencia real

Con un cliente síncrono, «concurrente» es difícil de expresar. Con async, lanzas N peticiones a la vez y esperas a todas:

import asyncio


responses = await asyncio.gather(*(client.get("/health") for _ in range(20)))
assert all(r.status_code == 200 for r in responses)

Esto es exactamente lo que necesitas para probar que un rate limiter corta la petición número 21, o que el «motor RAG» no comparte estado entre consultas simultáneas. La concurrencia se testea, no se supone.

3 · Ejemplo mínimo

El mismo /health de la lección anterior, ahora en versión async.

consola
uv add --dev pytest httpx pytest-asyncio
app/main.py
from fastapi import FastAPI

app = FastAPI(title="Copiloto API")


@app.get("/health")
async def health() -> dict[str, str]:
    return {"status": "ok"}
pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
asyncio_mode = "auto"
tests/test_health_async.py
from httpx import ASGITransport, AsyncClient

from app.main import app


async def test_health_async() -> None:
    transport = ASGITransport(app=app)
    async with AsyncClient(
        transport=transport,
        base_url="http://test",
    ) as client:
        response = await client.get("/health")

    assert response.status_code == 200
    assert response.json() == {"status": "ok"}

Ejecútalo:

consola
uv run pytest -q

.                                                                    [100%]
1 passed in 0.05s

Línea por línea:

  1. async def test_health_async(): el test es una corrutina. Con asyncio_mode = "auto", pytest-asyncio la ejecuta con await sin que añadas ningún marcador.
  2. ASGITransport(app=app): el transport que llama a la app en proceso. Aquí está la magia: no hay red.
  3. AsyncClient(transport=..., base_url="http://test"): el cliente. El async with garantiza que se cierre al salir del bloque.
  4. await client.get("/health"): la petición es asíncrona; el await cede el control al bucle mientras la app la procesa.
  5. assert response.status_code == 200: idéntica comprobación que en el test sincrónico. El objeto de respuesta es el mismo httpx.Response.

Compáralo con la lección 1: el test síncrono tenía 3 líneas de cuerpo; este tiene 5 y un async with. Esa diferencia de «peso» es real. Por eso no conviertas todos tus tests a async sin motivo: usa el cliente async cuando el test lo necesite (concurrencia, recursos async), no por moda.

4 · Ejemplo real

En Copiloto API el endpoint POST /ask llama a un motor RAG asíncrono. Vamos a montar la infraestructura async completa: una fixture de cliente, un doble del motor y una prueba de concurrencia.

app/deps.py
class AsyncRagEngine:
    """Motor de RAG asíncrono: en producción consulta un vector store."""

    async def answer(self, question: str) -> str:
        raise NotImplementedError


def get_rag_engine() -> AsyncRagEngine:
    return AsyncRagEngine()
tests/conftest.py
from collections.abc import AsyncIterator

import pytest_asyncio
from httpx import ASGITransport, AsyncClient

from app.deps import get_rag_engine
from app.main import app


class FakeAsyncRagEngine:
    """Doble async: determinista y sin I/O de red."""

    def __init__(self) -> None:
        self.calls: int = 0

    async def answer(self, question: str) -> str:
        self.calls += 1
        return f"Respuesta simulada para: {question}"


@pytest_asyncio.fixture
async def client() -> AsyncIterator[AsyncClient]:
    app.dependency_overrides[get_rag_engine] = FakeAsyncRagEngine
    transport = ASGITransport(app=app)
    async with AsyncClient(transport=transport, base_url="http://test") as async_client:
        yield async_client
    app.dependency_overrides.clear()

Los tests quedan expresivos, y el último mide concurrencia de verdad:

tests/test_ask_async.py
import asyncio

from httpx import AsyncClient


async def test_ask_returns_answer(client: AsyncClient) -> None:
    response = await client.post("/ask", json={"question": "¿Qué es Depends?"})

    assert response.status_code == 200
    assert "Depends" in response.json()["answer"]


async def test_ask_rejects_empty_question(client: AsyncClient) -> None:
    response = await client.post("/ask", json={"question": ""})

    assert response.status_code == 422
    assert "detail" in response.json()


async def test_concurrent_requests_are_independent(client: AsyncClient) -> None:
    questions = [f"pregunta {i}" for i in range(20)]

    responses = await asyncio.gather(
        *(client.post("/ask", json={"question": q}) for q in questions)
    )

    assert all(r.status_code == 200 for r in responses)
    answers = [r.json()["answer"] for r in responses]
    # Cada petición recibe SU respuesta: no hay cruce de estado entre corrutinas.
    assert answers == [f"Respuesta simulada para: {q}" for q in questions]

Decisiones y porqués:

  • La fixture client es async y usa async with: el yield se ejecuta dentro del bucle de eventos, así que la limpieza (dependency_overrides.clear()) es await-able de forma implícita y siempre corre.
  • FakeAsyncRagEngine.calls: además de devolver respuestas, cuenta llamadas. Así un test puede comprobar cuántas veces se invocó al motor: útil para detectar dobles consultas al RAG.
  • asyncio.gather con 20 peticiones: lanza todas a la vez y espera. Es la forma de probar que no hay estado compartido ni condiciones de carrera en el endpoint.
  • La aserción compara la lista completa de respuestas: no basta con que cada respuesta sea válida; comprueba que cada pregunta obtiene su respuesta. Si hubiera cruce de estado, el orden se rompería.

Si tu app abre el motor de base de datos en lifespan, envuelve el bloque con LifespanManager(app) (visto en la teoría). Sin él, el test async encontrará recursos sin inicializar. TestClient lo hace por ti con el with; AsyncClient, no.

6 · Errores habituales

Pasar la app al cliente en lugar de al transport

✗ Incorrecto
from httpx import AsyncClient

# httpx < 0.27; hoy lanza: TypeError: __init__() got an unexpected keyword 'app'
client = AsyncClient(app=app, base_url="http://test")
✓ Correcto
from httpx import ASGITransport, AsyncClient

client = AsyncClient(transport=ASGITransport(app=app), base_url="http://test")

httpx separó la decisión del transport de la del cliente. El cliente ya no conoce a la app: se lo dice el transport.

Olvidar el marcador y «saltarse» el test

✗ Incorrecto
# en modo strict, sin marcador:
async def test_ask():
    ...   # se marca como SKIPPED y nunca ejecuta la aserción
✓ Correcto
# pyproject.toml — modo auto, o bien el marcador explícito
[tool.pytest.ini_options]
asyncio_mode = "auto"

Un test que se salta no protege nada, pero el resumen de pytest puede pasarte por alto con un simple «skipped». Con asyncio_mode = "auto" eliminas la causa de raíz.

Usar TestClient dentro de un test async

✗ Incorrecto
from fastapi.testclient import TestClient

async def test_health():
    client = TestClient(app)          # síncrono y bloqueante dentro de un loop async
    response = client.get("/health")
    assert response.status_code == 200
✓ Correcto
from httpx import ASGITransport, AsyncClient

async def test_health():
    async with AsyncClient(
        transport=ASGITransport(app=app), base_url="http://test"
    ) as client:
        response = await client.get("/health")
    assert response.status_code == 200

El cliente síncrono intenta bloquear el bucle de eventos que ya estás usando. Si el test es async, el cliente también debe serlo.

Fixture async declarada como @pytest.fixture

✗ Incorrecto
import pytest

@pytest.fixture          # devuelve una corrutina sin resolverse
async def client():
    ...

async def test_ask(client):
    response = await client.post("/ask", json={"question": "x"})
    # AttributeError: 'coroutine' object has no attribute 'post'
✓ Correcto
import pytest_asyncio

@pytest_asyncio.fixture
async def client():
    ...

El error «coroutine object has no attribute…» casi siempre significa lo mismo: decoraste una fixture async con la herramienta equivocada (o te faltó el plugin).

7 · Ejercicio guiado

Objetivo: dotar a Copiloto API de una suite async completa y escribir un test de concurrencia que detecte un «motor» con estado compartido.

  1. Paso 1 — Instala el plugin. 
    uv add --dev pytest-asyncio httpx

    Resultado esperado: pytest-asyncio aparece en las dependencias de desarrollo. Si no lo instalas, pytest te avisará de que no sabe ejecutar async def.

  2. Paso 2 — Configura el modo auto. Añade a pyproject.toml: 
    [tool.pytest.ini_options]
testpaths = ["tests"]
asyncio_mode = "auto"
asyncio_default_fixture_loop_scope = "session"
  3. Paso 3 — Crea la fixture async. Copia el conftest.py de la sección 4: ASGITransport, AsyncClient, dependency_overrides al FakeAsyncRagEngine y clear() tras el yield.
  4. Paso 4 — Traduce un test sync a async. Toma test_ask_returns_answer de la lección 1 y reescríbelo con await client.post(...). Comprueba que pasa: 
    uv run pytest -q

    Resultado esperado: el test pasa igual que su versión síncrona, pero ahora se ejecuta en el bucle de eventos.

  5. Paso 5 — Añade el test de concurrencia. Copia test_concurrent_requests_are_independent. Lánzalo 5 veces seguidas para descartar intermitencias. 
    for i in 1 2 3 4 5; do uv run pytest tests/test_ask_async.py::test_concurrent_requests_are_independent -q; done

    Resultado esperado: 1 passed en las cinco ejecuciones. Cualquier fallo intermitente aquí sería la señal de una condición de carrera.

  6. Paso 6 — Introduce el bug a propósito. Cambia el fake para que guarde la última pregunta en un atributo de instancia y devuelva esa, en lugar del argumento recibido: 
    class FakeAsyncRagEngine:
    def __init__(self) -> None:
        self.last_question = ""

    async def answer(self, question: str) -> str:
        self.last_question = question          # estado compartido entre corrutinas
        return f"Respuesta simulada para: {self.last_question}"

    Vuelve a lanzar el test de concurrencia. Debe fallar (algunas respuestas no coincidirán con su pregunta): acabas de demostrar que la prueba detecta un estado compartido entre peticiones simultáneas. Revertir el fake después.

  7. Paso 7 — Decora el lifespan, si aplica. Si tu app/main.py abre el motor de base de datos en lifespan, añade LifespanManager alrededor del async with AsyncClient y confirma que los tests siguen pasando. Resultado esperado: sin errores de recursos no inicializados.

8 · Reto

🎯 Concurrencia contra el rate limit

En el Módulo 5 limitaste las peticiones por IP. Escribe un test async que lance, con asyncio.gather, más peticiones de las permitidas en la misma ventana y que compruebe que exactamente las primeras N devuelven 200 y el resto devuelven 429, con la cabecera Retry-After presente.

Pista: añade client.headers["X-Forwarded-For"] o una IP fija para que todas las peticiones cuenten contra el mismo cubo; sin eso, cada petición podría caer en una clave distinta. Piensa si el límite debe testearse con un reloj real o con uno inyectado (freezegun o un fake de tiempo): ¿el test sería determinista si dependiera del reloj del sistema? Justifica tu elección.

9 · Resumen

  • TestClient es síncrono; no se puede usar dentro de un test async.
  • Para tests async: AsyncClient + ASGITransport(app=app) (no AsyncClient(app=app)).
  • pytest-asyncio ejecuta corrutinas; asyncio_mode = "auto" evita el fallo silencioso del test marcado como skip.
  • Las fixtures async usan @pytest_asyncio.fixture.
  • ASGITransport no dispara el lifespan: usa LifespanManager si dependes de él.
  • asyncio.gather permite probar concurrencia y detectar estado compartido.
  • Usa async cuando lo necesites (concurrencia, recursos async), no por defecto.

10 · Preguntas frecuentes

¿Convierto toda mi suite a async?

No. TestClient es más simple y suficiente para la mayoría de tests. Usa tests async cuando: (a) necesites await para recursos async, (b) quieras lanzar peticiones concurrentes, o (c) tu app use una sesión de base de datos async. Mezclar ambos estilos en la misma suite es perfectamente válido.

¿pytest-asyncio o anyio?

Ambos funcionan. La documentación de FastAPI muestra @pytest.mark.anyio porque FastAPI es agnóstico: funciona sobre asyncio o Trio. Si tu stack es asyncio puro (el caso habitual, y el de este curso), pytest-asyncio con asyncio_mode = "auto" es la opción más directa.

¿Por qué mi test async aparece como skipped y no como passed?

Casi siempre porque no está ejecutándose: en modo strict sin @pytest.mark.asyncio, pytest-asyncio lo salta con un aviso de que las funciones async «no están soportadas nativamente». Es un falso verde peligroso. Cambia a asyncio_mode = "auto" o añade el marcador.

¿Qué pasa si mi app abre el motor de BD en lifespan y uso AsyncClient?

Que el startup no se ejecuta y los recursos no existen: verás errores como AttributeError sobre None o «no such table». Envuelve la app con LifespanManager(app) de asgi-lifespan para que el ciclo de vida se dispare también en los tests async.

¿Puedo hacer asyncio.gather de 1000 peticiones?

Técnicamente sí, pero ten sentido común: 1000 corrutinas simultáneas contra una base de datos SQLite derivarán en errores de conexión. Un buen test de concurrencia usa un número representativo (10-50) y, si buscas detectar el límite, comprueba el comportamiento justo en el borde (N y N+1), no una cifra arbitraria.
