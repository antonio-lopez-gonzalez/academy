OpenAPI, ruff y mypy

Módulo 6 · Testing y calidad 🕐 30 minutos

1 · Introducción

Los tests que escribiste en las tres lecciones anteriores comprueban el comportamiento: que una petición devuelva el código y el cuerpo esperados. Esta lección cierra el módulo con otras tres capas de calidad que no son tests funcionales, pero protegen igual de bien tu API:

  • El contrato OpenAPI, que es la fuente de verdad de tu API y debe evolucionar de forma consciente, no por accidente.
  • ruff, que atrapa errores de estilo y bugs evidentes antes de que lleguen al revisor.
  • mypy, que verifica los tipos que ya declaras en cada firma y modelo, y pytest-cov, que te dice qué partes del código no ejecuta ningún test.

¿Por qué existe esta lección? Porque una API sin contrato verificado y sin herramientas automáticas se degrada sola: el esquema OpenAPI se «mueve» sin que nadie lo decida, el estilo vira según quién toque el archivo, y las zonas sin cubrir se convierten en los bugs de producción. Estas herramientas son baratas de montar y se pagan solas en la primera semana.

Errores típicos que veremos: un test de snapshot que se regenera automáticamente y por tanto nunca falla; perseguir el 100% de cobertura como si fuera un objetivo; y ejecutar mypy sobre un código sin anotaciones, que no comprueba nada útil.

2 · Teoría

OpenAPI: el contrato, no un adorno

Cuando arrancas FastAPI, la app genera un documento OpenAPI (JSON) que describe cada ruta, sus parámetros, los esquemas de entrada y salida y los códigos de respuesta. Ese documento alimenta /docs (Swagger UI) y /redoc, y es lo que consumen los clientes: generadores de SDK, gateways, y el frontend. Es, literalmente, el contrato público de tu API.

   modelos Pydantic + decoradores de ruta
                 │
                 ▼
        app.openapi()  →  documento OpenAPI (dict)
                 │                    │
                 ├── /openapi.json ───┤── generadores de cliente, gateways
                 ├── /docs  (Swagger) │
                 └── /redoc           └── tu test de snapshot (esta lección)

Analogía: el modelo de datos y los decoradores son el borrador; el documento OpenAPI es el contrato firmado. Si alguien renombra un campo o cambia un código de estado, el contrato cambia, y los clientes que ya lo consumen se rompen. Un test de contrato convierte ese cambio silencioso en un fallo visible.

El test de contrato: snapshot del esquema

La técnica es simple: guardas el documento OpenAPI en un archivo versionado (tests/openapi.json) y un test compara el esquema actual con el guardado. Si difieren, el test falla y te obliga a decidir: ¿es el cambio intencionado (actualizo el archivo) o un accidente (arreglo el código)?

La trampa mortal: un test que regenera el snapshot automáticamente cada vez que corre nunca falla, y entonces no protege nada. La regeneración debe ser una acción explícita y consciente, disparada por una variable de entorno o un flag, nunca el comportamiento por defecto.

La comparación debe ser determinista: serializa con sort_keys=True para que el orden de las claves no genere ruido, y compara los objetos (diccionarios) en lugar de las cadenas, para que el test se centre en el contenido y no en el formato.

Además del snapshot: aserciones sobre el contrato

El snapshot detecta cambios; las aserciones explícitas documentan intenciones. Merece la pena comprobar directamente cosas como:

Qué comprobarDónde en el documento
Todas las rutas esperadas existenschema["paths"]
Una ruta documenta sus códigos de respuestaschema["paths"]["/ask"]["post"]["responses"]
Un modelo tiene los campos requeridosschema["components"]["schemas"]["AskRequest"]
El título y la versión son los correctosschema["info"]

Estas aserciones no se rompen cuando cambia el formato, pero sí cuando cambia lo que importa. Combinadas con el snapshot, cubren los dos frentes.

ruff: linter y formateador en una herramienta

ruff sustituye a flake8, isort, pyupgrade y compañía, y además formatea el código. Es rapidísimo (está escrito en Rust), lo que lo hace viable incluso como hook al guardar. Dos comandos y una configuración:

   uv run ruff check .          → detecta problemas (sin modificar)
   uv run ruff check --fix .    → aplica las correcciones seguras
   uv run ruff format .         → formatea (equivalente a black)

Las reglas se agrupan por prefijo. Algunos de los más útiles para una API FastAPI:

PrefijoFamiliaEjemplo de lo que detecta
E, WpycodestyleLíneas largas, espacios sobrantes
FPyflakesImports sin usar, variables sin definir
IisortOrden de los imports
UPpyupgradeCódigo antiguo que puede modernizarse (p. ej. Optional[X] → X | None)
Bflake8-bugbearTrampas comunes: defaults mutables, comparaciones sospechosas
ASYNCflake8-asyncLlamadas bloqueantes dentro de async def

B006 de bugbear es el guardián del default mutable que ya te avisamos de no usar en Pydantic: detecta def f(x=[]). Y ASYNC es oro para FastAPI: te avisa si dentro de un async def usas una biblioteca síncrona que bloquea el bucle de eventos.

mypy: el tipo como test estático

FastAPI se apoya en anotaciones de tipo para generar el contrato y la validación. mypy usa esas mismas anotaciones para detectar incoherencias sin ejecutar nada: pasar un str donde se espera un int, llamar a un método que puede no existir, olvidar que algo es None | int…

   test dinámico   : ejecuta el código y comprueba el resultado
   test estático    : NO ejecuta; comprueba los TIPOS de todo el código
                      (mypy)  →  encuentra errores que ningún test cubriría

El modo strict de mypy es el objetivo, pero hay un matiz práctico: SQLModel genera los __init__ dinámicamente y mypy a veces no ve bien los kwargs de la tabla. La estrategia profesional es activar strict y, si hace falta, relajar módulos concretos con [[tool.mypy.overrides]] y una nota que explique por qué. Relajar un módulo entero sin justificarlo es deuda técnica silenciosa.

pytest-cov: qué código no ejecuta ningún test

La cobertura mide qué líneas (y ramas) de tu código pasan por algún test. No es un objetivo en sí, pero es un detector de puntos ciegos: «este manejador de error nunca se ejecuta», «esta rama del validador no está cubierta». Se activa como plugin de pytest:

uv add --dev pytest-cov
uv run pytest --cov=app --cov-report=term-missing --cov-branch

El 100% de cobertura no significa «sin bugs»: puedes cubrir todas las líneas sin comprobar ni un solo resultado. Es señal de que algo se ejecutó, no de que se comprobara. Úsala para encontrar huecos, y exige un umbral razonable (70-90%), no la perfección.

3 · Ejemplo mínimo

El snapshot más pequeño posible del contrato de una API.

app/main.py
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="Copiloto API", version="0.1.0")


class AskRequest(BaseModel):
    question: str


@app.post("/ask")
def ask(payload: AskRequest) -> dict[str, str]:
    return {"answer": payload.question}
tests/test_openapi.py
import json
import os
from pathlib import Path

from app.main import app

SNAPSHOT = Path(__file__).parent / "openapi.json"


def _serialize(schema: dict) -> str:
    return json.dumps(schema, indent=2, sort_keys=True, ensure_ascii=False) + "\n"


def test_openapi_contract() -> None:
    schema = app.openapi()

    # Regeneración EXPLÍCITA: solo si se pide con la variable de entorno.
    if os.getenv("UPDATE_OPENAPI"):
        SNAPSHOT.write_text(_serialize(schema), encoding="utf-8")

    expected = json.loads(SNAPSHOT.read_text(encoding="utf-8"))
    assert schema == expected

Primera ejecución: genera el snapshot una vez, a propósito.

consola
uv add --dev pytest httpx
UPDATE_OPENAPI=1 uv run pytest tests/test_openapi.py -q     # crea tests/openapi.json
uv run pytest tests/test_openapi.py -q                      # ahora ya compara

1 passed in 0.04s

En PowerShell, la variable se define así: $env:UPDATE_OPENAPI=1; uv run pytest. El comando es el mismo; cambia la sintaxis del shell.

Línea por línea:

  1. app.openapi(): genera (y cachea) el documento OpenAPI como un diccionario de Python. Es el mismo objeto que sirve /openapi.json.
  2. _serialize: convierte el diccionario a texto estable con sort_keys=True. Sin ordenar las claves, el archivo cambiaría de forma aleatoria y el diff sería ilegible.
  3. if os.getenv("UPDATE_OPENAPI"): la regeneración ocurre solo si la pides explícitamente. Es la diferencia entre un test útil y uno decorativo.
  4. json.loads(SNAPSHOT.read_text(...)): lees el contrato guardado. Comparas diccionarios, no cadenas: el test se centra en el contenido.
  5. assert schema == expected: si alguien añade una ruta o renombra un campo sin actualizar el contrato, este test falla y lo obliga a decidir.

4 · Ejemplo real

Llevemos las tres herramientas a Copiloto API. El objetivo: el contrato queda fijado por tests, el estilo y los tipos se comprueban en CI, y la cobertura avisa de los huecos.

1. El contrato: snapshot + aserciones

tests/test_openapi.py
import json
import os
from pathlib import Path

import pytest

from app.main import app

SNAPSHOT = Path(__file__).parent / "openapi.json"


def _serialize(schema: dict) -> str:
    return json.dumps(schema, indent=2, sort_keys=True, ensure_ascii=False) + "\n"


@pytest.fixture
def openapi_schema() -> dict:
    return app.openapi()


def test_openapi_snapshot(openapi_schema: dict) -> None:
    if os.getenv("UPDATE_OPENAPI"):
        SNAPSHOT.write_text(_serialize(openapi_schema), encoding="utf-8")
    expected = json.loads(SNAPSHOT.read_text(encoding="utf-8"))
    assert openapi_schema == expected


def test_contract_declares_copiloto_endpoints(openapi_schema: dict) -> None:
    paths = openapi_schema["paths"]
    assert set(paths) >= {"/health", "/modules", "/ask"}


def test_ask_documents_validation_error(openapi_schema: dict) -> None:
    responses = openapi_schema["paths"]["/ask"]["post"]["responses"]
    # El 422 es parte del contrato público del endpoint.
    assert "422" in responses


def test_ask_request_requires_question(openapi_schema: dict) -> None:
    schemas = openapi_schema["components"]["schemas"]
    request = schemas["AskRequest"]
    assert "question" in request["required"]


def test_contract_version_is_pinned(openapi_schema: dict) -> None:
    info = openapi_schema["info"]
    assert info["title"] == "Copiloto API"
    assert info["version"] == "1.0.0"

Decisiones y porqués:

  • El snapshot es una red de seguridad, no la especificación. Fija «lo de antes» para que cualquier cambio salte. Las aserciones explícitas dicen, además, qué nos importa.
  • "422" in responses: FastAPI documenta los errores de validación de Pydantic automáticamente. Este test fija que ese comportamiento siga existiendo: si alguien lo desactiva con una configuración rara, el test lo avisa.
  • La versión fijada (1.0.0): subir la versión es una decisión de producto. Que un test la fije evita «subidas» accidentales de la versión del contrato.
  • El archivo va al repositorio. tests/openapi.json es un artefacto versionado; su diff en un pull request es la mejor documentación posible de un cambio de contrato.

2. Calidad estática: la configuración

pyproject.toml
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
# E/W (estilo), F (errores), I (imports), UP (modernizar),
# B (bugbear), SIM (simplificaciones), ASYNC (bloqueos en async)
select = ["E", "W", "F", "I", "UP", "B", "SIM", "ASYNC"]
ignore = ["E501"]              # la longitud la gestiona el formateador

[tool.ruff.format]
quote-style = "double"

[tool.mypy]
python_version = "3.12"
strict = true
plugins = ["pydantic.mypy"]
warn_unused_ignores = true

[[tool.mypy.overrides]]
# SQLModel genera los constructores dinámicamente; relajamos solo esto.
module = ["app.models"]
disable_error_code = ["call-arg"]

[tool.coverage.run]
source = ["app"]
branch = true

[tool.coverage.report]
show_missing = true
skip_covered = true
fail_under = 85
exclude_lines = [
  "if TYPE_CHECKING:",
  "raise NotImplementedError",
  "if __name__ == .__main__.:",
]

El grupo ASYNC de ruff es especialmente valioso en FastAPI: marca llamadas síncronas y bloqueantes dentro de funciones async (por ejemplo, requests.get o time.sleep), que es el error de rendimiento número uno en APIs async. La lección de este módulo sobre sync vs async ya te avisó de ello; ahora tienes una herramienta que lo detecta sola.

6 · Errores habituales

El snapshot que se auto-regenera

✗ Incorrecto
def test_openapi():
    schema = app.openapi()
    SNAPSHOT.write_text(json.dumps(schema), encoding="utf-8")   # ¡siempre!
    assert schema == json.loads(SNAPSHOT.read_text())
    # El archivo acaba de escribirse con el valor actual: SIEMPRE pasa.
✓ Correcto
def test_openapi():
    schema = app.openapi()
    if os.getenv("UPDATE_OPENAPI"):       # solo cuando lo pides
        SNAPSHOT.write_text(_serialize(schema), encoding="utf-8")
    assert schema == json.loads(SNAPSHOT.read_text(encoding="utf-8"))

Si el archivo se escribe con el valor actual antes de compararlo, la aserción es una tautología. Es el antipatrón clásico de los snapshots: parecen un test, pero no comprueban nada.

Ignorar ruff con noqa en lugar de arreglar

✗ Incorrecto
import requests  # noqa: F401
import time      # noqa: F401

async def handler():
    time.sleep(1)  # noqa: ASYNC251   # bloquea TODO el bucle de eventos
    return requests.get("http://x")  # noqa: ASYNC && cliente sync en async
✓ Correcto
import asyncio

import httpx


async def handler() -> httpx.Response:
    await asyncio.sleep(1)                        # cede el control
    async with httpx.AsyncClient() as client:     # cliente async en async
        return await client.get("http://x")

Silenciar con noqa un aviso de bloqueo convierte un problema de rendimiento real en deuda invisible. En este caso, el aviso apunta a la lección de sync vs async: usa await y clientes async.

Perseguir el 100% de cobertura

✗ Incorrecto
# Un test que solo ejecuta la función, sin comprobar el resultado:
def test_ask_just_runs(client):
    client.post("/ask", json={"question": "x"})     # sube la cobertura...
    # ... pero no afirma NADA. Verde, y sin embargo inútil.
✓ Correcto
def test_ask_returns_answer(client):
    response = client.post("/ask", json={"question": "x"})
    assert response.status_code == 200
    assert response.json()["answer"]           # el test COMPRUEBA, no solo ejecuta

La cobertura mide ejecución, no verificación. Un umbral del 100% fomenta tests que «pasan por» el código sin comprobar nada, que es peor que no tenerlos: dan una falsa sensación de seguridad.

Confundir el snapshot con el openapi.json del servidor

✗ Incorrecto
def test_contract():
    # Descarga desde un servidor levantado a mano: no reproducible en CI.
    response = httpx.get("http://localhost:8000/openapi.json")
    assert response.status_code == 200
✓ Correcto
from app.main import app

def test_contract():
    schema = app.openapi()      # genera el esquema en proceso, sin servidor
    assert "/ask" in schema["paths"]

app.openapi() produce el mismo documento que sirve /openapi.json, pero sin necesidad de un servidor. El test de contrato no debe depender de infraestructura.

7 · Ejercicio guiado

Objetivo: dejar Copiloto API con su contrato fijado por tests y con las tres herramientas de calidad configuradas y en verde.

  1. Paso 1 — Instala las herramientas. 
    uv add --dev ruff mypy pytest-cov

    Resultado esperado: las tres aparecen en las dependencias de desarrollo.

  2. Paso 2 — Escribe el test de contrato. Copia tests/test_openapi.py de la sección 4. Genera el snapshot una vez: 
    UPDATE_OPENAPI=1 uv run pytest tests/test_openapi.py -q

    En PowerShell: $env:UPDATE_OPENAPI=1; uv run pytest tests/test_openapi.py -q. Resultado esperado: se crea tests/openapi.json y el test pasa.

  3. Paso 3 — Comprueba que el contrato detecta cambios. Añade un campo opcional a AskRequest (por ejemplo top_k: int = 3) y lanza los tests sin regenerar: 
    uv run pytest tests/test_openapi.py -q

    Resultado esperado: test_openapi_snapshot falla mostrando la diferencia. Es exactamente lo que quieres: un cambio de contrato nunca pasa desapercibido.

  4. Paso 4 — Acepta el cambio de forma consciente. Como el campo sí lo querías, regenera el snapshot y observa el diff: 
    UPDATE_OPENAPI=1 uv run pytest tests/test_openapi.py -q
git diff tests/openapi.json

    Resultado esperado: el diff muestra únicamente el campo nuevo. Ese diff es la documentación del cambio en el pull request.

  5. Paso 5 — Pasa ruff. 
    uv run ruff check .
uv run ruff format .

    Resultado esperado: All checks passed!. Si aparecen avisos, léelos uno a uno: algunos son de estilo (el formateador los arregla) y otros son bugs reales (los arreglas tú).

  6. Paso 6 — Pasa mypy. Añade la configuración de [tool.mypy] y ejecuta: 
    uv run mypy app

    Resultado esperado: Success: no issues found. Si mypy señala los constructores de SQLModel, aplica el override por módulo del ejemplo. No lo silencies sin justificación.

  7. Paso 7 — Mira la cobertura e interpreta el resultado. 
    uv run pytest

    Resultado esperado: un informe con la columna Missing. Elige una línea no cubierta, escribe un test que la cubra comprobando el resultado, y verifica que sube. Resultado esperado: un test más y una línea menos en Missing.

8 · Reto

🎯 Un gate de calidad en CI

Monta un flujo que, en cada push, ejecute en este orden: ruff check, ruff format --check, mypy app, pytest --cov=app. El trabajo debe fallar si cualquiera de los cuatro pasos falla. Añade, además, un test que compruebe que tests/openapi.json está al día sin permitir la regeneración (es decir, que la variable de entorno no esté presente).

Pista: puedes usar GitHub Actions (.github/workflows/ci.yml) o pre-commit para el ámbito local. Con uv, el paso de instalación es uv sync --dev y luego uv run …. Piensa cómo garantizar que el test de contrato no está «regenerando en silencio»: ¿qué pasa si alguien deja UPDATE_OPENAPI=1 definido en el entorno de CI? ¿Cómo lo harías imposible de configurar por accidente?

9 · Resumen

  • El documento OpenAPI (app.openapi() / /openapi.json) es el contrato público de tu API.
  • Un test de snapshot fija el contrato; regenéralo solo con una acción explícita, nunca de forma automática.
  • Completa el snapshot con aserciones explícitas sobre rutas, códigos y campos requeridos.
  • ruff hace de linter y formateador: estilo, imports, modernización y (grupo ASYNC) bloqueos en async.
  • mypy en modo strict convierte tus anotaciones en un test estático; relaja por módulo solo con justificación.
  • pytest-cov señala huecos (líneas y ramas sin ejecutar); es un detector de puntos ciegos, no un objetivo de porcentaje.
  • Todo esto se ejecuta automáticamente en CI: lo que no es automático, no es una garantía.

10 · Preguntas frecuentes

¿Qué diferencia hay entre un test de snapshot del contrato y los tests de endpoints?

Los tests de endpoints comprueban el comportamiento (una petición concreta devuelve esto). El test de contrato comprueba la forma declarada de toda la API a la vez: rutas, parámetros, esquemas y códigos documentados. Son complementarios: el primero verifica que funciona, el segundo que lo que prometes por escrito no cambió sin querer.

¿Cada cuánto regenero tests/openapi.json?

Solo cuando el cambio de contrato es intencionado y ya está claro en el pull request. La secuencia profesional es: haces el cambio, el test falla, revisas el diff del esquema, y si es correcto, regeneras con la variable de entorno y comiteas el archivo junto al código. El diff del openapi.json es entonces la documentación del cambio.

¿ruff y mypy no se solapan?

No: cubren cosas distintas. ruff mira estilo, formato y patrones peligrosos (un import sin usar, un default mutable, una llamada bloqueante en async). mypy mira la coherencia de los tipos en todo el programa. Puedes tener el estilo perfecto y aún así pasar un str donde va un int: eso lo caza mypy.

¿Qué umbral de cobertura debo exigir?

Un valor razonable y realista: entre 70% y 90% para una API, con fail_under configurado. Por debajo, dejas zonas importantes sin ejercitar. Buscar el 100% suele llevar a tests que ejecutan código sin comprobar nada, que son contraproducentes. Ajusta el umbral al punto en el que estás y súbelo cuando el equipo lo asuma.

¿Por qué excluir raise NotImplementedError de la cobertura?

Porque es código que, por definición, no debe ejecutarse en un test (es el esqueleto de una clase base que se sustituye). Contarlo bajaría la cobertura por una línea que nunca va a ejecutarse en producción. Las exclusiones deben ser legítimas y pocas: si excluyes demasiado, dejas de detectar huecos reales.
