Validación y tipos

Módulo 1 · Rutas y datos 🕐 35 minutos

1 · Introducción

En la lección anterior viste que el tipo define la validación: un campo int rechaza un texto. Pero las reglas de negocio reales van mucho más allá del tipo: «la pregunta debe tener al menos 3 caracteres», «el top_k está entre 1 y 10», «el email debe tener forma de email», «el slug solo admite minúsculas y guiones». Esta lección te enseña a expresar todo eso dentro del modelo, con Field, constraints y validadores.

Y como toda validación puede fallar, dedicamos la segunda mitad a la pieza que hace a FastAPI tan agradable de depurar: la forma del error 422. Entender su estructura (detail, loc, type, msg, input, ctx) es lo que te permite leer un error y arreglarlo sin adivinar.

¿Por qué declarar las reglas en el modelo y no en el handler? Porque así existe una sola fuente de verdad: la regla valida la petición, se documenta en /docs, alimenta el esquema OpenAPI y puede reutilizarse en tests y en otros endpoints. Una regla escrita en un if dentro del handler no documenta nada y hay que recordar mantenerla en cada sitio.

2 · Teoría

La cadena de validación de Pydantic v2

Antes de empezar, ubiquémonos. Cuando llega una petición, Pydantic v2 recorre el modelo en capas:

JSON recibido │ ▼ [1] Parseo JSON -> ¿es JSON válido? │ ▼ [2] Conversión de tipos -> "4" -> 4, "2026-01-31" -> datetime │ ▼ [3] Constraints de Field -> ge/le, min_length, pattern, ... │ ▼ [4] Validadores -> field_validator / model_validator │ ▼ Instancia del modelo (datos garantizados)

Todas las capas, al fallar, producen el mismo formato de error. Y todas se declaran de forma declarativa en la clase.

Field: restricciones y metadatos por campo

Field se usa (con Annotated) para añadir restricciones y documentación a un campo:

from typing import Annotated
from pydantic import BaseModel, Field

class AskRequest(BaseModel):
    question: Annotated[str, Field(min_length=3, max_length=2000,
                                   description="La pregunta del usuario")]
    top_k: Annotated[int, Field(ge=1, le=10)] = 4
    temperature: Annotated[float, Field(ge=0.0, le=2.0)] = 0.2
ConstraintAplica aSignificado
gt / genúmerosmayor que / mayor o igual
lt / lenúmerosmenor que / menor o igual
min_length / max_lengthstr, list, set, dictlongitud mínima/máxima

multiple_ofnúmerosdebe ser múltiplo de ese valor

Vienes de Pydantic v1: conint, constr, conlist siguen existiendo pero la forma actual es Annotated[int, Field(...)]. Además, para listas, min_items/max_items se llaman ahora min_length/max_length. Usa siempre el estilo de v2.

Validadores: reglas que no caben en un constraint

Cuando la regla es más compleja que un rango o una longitud, se escribe un validador. En v2 se declaran con decoradores:

from pydantic import BaseModel, field_validator

class AskRequest(BaseModel):
    question: str
    tags: list[str] = []

    @field_validator("question")
    @classmethod
    def question_no_vacia(cls, value: str) -> str:
        # Normaliza: quita espacios y exige longitud tras recortar.
        value = value.strip()
        if len(value) < 3:
            # Lanzar ValueError convierte esto en un 422 automáticamente.
            raise ValueError("La pregunta debe tener al menos 3 caracteres útiles")
        return value

Puntos clave de los validadores v2:

  • Decorador @field_validator("campo") (o varios campos a la vez) y @classmethod debajo.
  • Por defecto corren después de la conversión de tipo; con mode="before" corren antes (útil para limpiar el dato crudo).
  • Deben devolver el valor (posiblemente transformado).
  • Lanzar ValueError se transforma en un error de validación (422), no en un 500.

Para reglas que cruzan varios campos se usa model_validator(mode="after"), que recibe el modelo ya construido:

from pydantic import BaseModel, model_validator

class RAGConfig(BaseModel):
    top_k: int = 4
    temperature: float = 0.2

    @model_validator(mode="after")
    def coherente(self):
        if self.temperature > 1.0 and self.top_k > 5:
            raise ValueError("Con alta creatividad, reduce top_k (max 5)")
        return self

La forma del error 422

Cuando algo no valida, FastAPI responde HTTP 422 Unprocessable Entity con este cuerpo:

cuerpo de la respuesta 422
{
  "detail": [
    {
      "type": "string_too_short",
      "loc": ["body", "question"],
      "msg": "String should have at least 3 characters",
      "input": "hi",
      "ctx": { "min_length": 3 }
    },
    {
      "type": "less_than_equal",
      "loc": ["body", "top_k"],
      "msg": "Input should be less than or equal to 10",
      "input": 99,
      "ctx": { "le": 10 }
    }
  ]
}
CampoQué es
detailLista con un elemento por error; puede haber varios a la vez.
locRuta hasta el campo: primero el origen ("body", "query", "path") y luego los nombres/índices.
typeIdentificador estable del error (missing, string_too_short, greater_than_equal…). Ideal para programar contra él.
msgMensaje legible para humanos. Traducible/personalizable.
inputEl valor que llegó y falló (útil para depurar).
ctxContexto extra, p. ej. el límite incumplido (le: 10).

Programa contra type, no contra msg. Los mensajes pueden cambiar de idioma o de redacción entre versiones; el type y la loc son estables. Si en un cliente quieres traducir los errores, hazlo a partir de type + loc.

422 no es lo mismo que 400 ni que 500. 422 significa «entendí la petición pero los datos no cumplen el contrato». Un 400 es una petición mal formada en un sentido más general, y un 500 es un fallo tuyo. Volveremos sobre esto en la lección de códigos de estado y en Problem Details (Módulo 2).

3 · Ejemplo mínimo

Un modelo con una restricción (Field) y un validador que normaliza el texto. Observa cómo el ValueError del validador se convierte en 422.

main.py
# main.py — Field + field_validator en el ejemplo más pequeño
from typing import Annotated

from fastapi import FastAPI
from pydantic import BaseModel, Field, field_validator

app = FastAPI()


class Username(BaseModel):
    # Constraint declarativo: 3 a 20 caracteres.
    name: Annotated[str, Field(min_length=3, max_length=20)]

    # Validador: una regla que no se expresa con un constraint.
    @field_validator("name")
    @classmethod
    def sin_espacios(cls, value: str) -> str:
        if " " in value:
            raise ValueError("El nombre no puede contener espacios")
        return value


@app.post("/users")
def create_user(payload: Username):
    return {"name": payload.name}

uv run uvicorn main:app --reload

# Válido
curl -X POST "http://127.0.0.1:8000/users" \
  -H "Content-Type: application/json" -d '{"name": "ada"}'
# -> {"name":"ada"}

# Demasiado corto: lo corta el Field
curl -X POST "http://127.0.0.1:8000/users" \
  -H "Content-Type: application/json" -d '{"name": "ad"}'
# -> 422 type=string_too_short  loc=["body","name"]

4 · Ejemplo real

El modelo AskRequest de Copiloto API, ahora con validación de verdad: rangos en la configuración RAG, normalización de la pregunta y una coherencia cruzada entre campos. Todo declarado, nada en el handler.

app/schemas/ask.py
# app/schemas/ask.py — validación completa del cuerpo de /ask
from typing import Annotated

from pydantic import BaseModel, Field, field_validator, model_validator

# Un alias de tipo para no repetir Annotated en cada campo.
TopK = Annotated[int, Field(ge=1, le=10, description="Fragmentos a recuperar")]


class RAGConfig(BaseModel):
    top_k: TopK = 4
    temperature: Annotated[float, Field(ge=0.0, le=2.0)] = 0.2

    @model_validator(mode="after")
    def combinacion_coherente(self):
        # Regla de negocio que cruza dos campos.
        if self.temperature > 1.0 and self.top_k > 5:
            raise ValueError("Con temperature > 1.0, top_k no puede pasar de 5")
        return self


class AskRequest(BaseModel):
    question: Annotated[str, Field(min_length=3, max_length=2000)]
    module_id: Annotated[int | None, Field(ge=1)] = None
    config: RAGConfig = RAGConfig()

    @field_validator("question")
    @classmethod
    def normalizar(cls, value: str) -> str:
        # Recortamos espacios; si tras recortar queda corto, es error.
        value = value.strip()
        if len(value) < 3:
            raise ValueError("La pregunta debe tener al menos 3 caracteres")
        return value

    @model_validator(mode="after")
    def revisar_config(self):
        # Reutiliza la coherencia del submodelo: aquí ya está validada.
        return self

# Válido y con defaults
curl -X POST "http://127.0.0.1:8000/ask" \
  -H "Content-Type: application/json" \
  -d '{"question": "   Que es ASGI?   "}'
# -> la pregunta llega recortada a "Que es ASGI?"

# top_k fuera de rango
curl -X POST "http://127.0.0.1:8000/ask" \
  -H "Content-Type: application/json" \
  -d '{"question": "hola", "config": {"top_k": 99}}'
# -> 422 type=less_than_equal loc=["body","config","top_k"] ctx={"le": 10}

# Coherencia cruzada (dos campos)
curl -X POST "http://127.0.0.1:8000/ask" \
  -H "Content-Type: application/json" \
  -d '{"question": "hola", "config": {"top_k": 8, "temperature": 1.5}}'
# -> 422 type=value_error loc=["body","config"] msg="... top_k no puede pasar de 5"

Fíjate en la loc del error cruzado: ["body","config"], no un campo concreto, porque el fallo está en la combinación. Un model_validator apunta al modelo; un field_validator, al campo. Esa diferencia te dice dónde colocar la corrección.

5 · Buenas prácticas

HazEvitaPor qué
Usa Annotated[tipo, Field(...)] conint(ge=1) o constr(min_length=3) El estilo v2 es más legible y composable; los con* se mantienen por compatibilidad.
Reutiliza tipos especiales (EmailStr, HttpUrl, UUID) Expresiones regulares propias para emails/URLs Ya están probados; tu regex casi siempre será peor y menos legible.
Normaliza con validadores (strip, minúsculas) Esperar que el cliente mande los datos «limpios» La API es la última frontera: normalizar ahí evita duplicados («ada» vs « ada »).
Lanza ValueError en validadores Lanzar HTTPException dentro de un modelo El modelo no conoce HTTP; ValueError produce el 422 estándar con loc correcta.
Escribe mensajes concretos «valor inválido» El msg es lo que ve quien integra la API; sé específico (qué campo, qué regla).
Usa model_validator para reglas cruzadas Validar la combinación en el endpoint Se mantiene con el modelo, se documenta y se reutiliza donde se use el modelo.

6 · Errores habituales

Usar el decorador de Pydantic v1

# ❌ @validator es v1: en v2 genera avisos de deprecación
from pydantic import BaseModel, validator

class M(BaseModel):
    name: str

    @validator("name")
    def check(cls, v):
        return v.strip()

# ✅ En v2: @field_validator + @classmethod, y devuelve el valor
from pydantic import BaseModel, field_validator

class M(BaseModel):
    name: str

    @field_validator("name")
    @classmethod
    def check(cls, value: str) -> str:
        return value.strip()

Usar min_items en listas

# ❌ min_items/max_items eran de v1
from pydantic import BaseModel, Field
from typing import Annotated

class M(BaseModel):
    tags: Annotated[list[str], Field(min_items=1)]   # no existe en v2

# ✅ En v2 la longitud de una lista se llama min_length/max_length
class M(BaseModel):
    tags: Annotated[list[str], Field(min_length=1, max_length=5)]

Olvidar @classmethod o no devolver el valor

# ❌ Sin @classmethod, Pydantic v2 no ejecuta bien el validador;
#    y si no devuelves, el valor se pierde (queda None y falla el tipo)
from pydantic import field_validator

class M(BaseModel):
    name: str

    @field_validator("name")            # falta @classmethod
    def check(cls, value):
        value.strip()                    # no devuelve nada

# ✅
class M(BaseModel):
    name: str

    @field_validator("name")
    @classmethod
    def check(cls, value: str) -> str:
        return value.strip()

Lanzar la excepción equivocada en un validador

# ❌ Un raise genérico se convierte en 500 (error del servidor), no en 422
from fastapi import HTTPException
from pydantic import field_validator

@field_validator("question")
@classmethod
def check(cls, value):
    raise HTTPException(status_code=400, detail="pregunta inválida")  # mal

# ✅ ValueError => 422 con forma estándar y loc correcta
@field_validator("question")
@classmethod
def check(cls, value: str) -> str:
    raise ValueError("la pregunta no es válida")   # bien

Confundir EmailStr con un str y olvidar la dependencia

# ❌ ImportError: email-validator is not installed
uv run uvicorn main:app --reload

# ✅ Instala la extra que Pydantic necesita para EmailStr
uv add email-validator

Los validadores no deben hacer trabajo pesado ni I/O. No consultes la base de datos ni llames a un servicio dentro de un field_validator: se ejecuta en la fase de validación, es síncrono y debe ser rápido y puro. El acceso a datos va en el endpoint o en una dependencia (Módulo 3).

8 · Reto

🎯 Un tipo de dominio reutilizable

Crea una validación reutilizable para los slugs de Copiloto API: una cadena en minúsculas, con palabras separadas por un único guion (rutas-y-datos), sin empezar ni terminar en guion y con longitud 3..50. Tu reto: empaquétala como un tipo anotado (Slug = Annotated[str, ...]) que puedas usar en dos modelos distintos sin repetir la regla.

Pista: puedes combinar Field(pattern=..., min_length=..., max_length=...) con un field_validator para los casos que una regex deja incómodos (por ejemplo, guiones duplicados). Pregúntate qué error quieres obtener: una parte la resolverá el pattern (type=string_pattern_mismatch) y otra tu validador (type=value_error). Documenta ambos caminos y no lo resuelvas de una sola forma: experimenta.

9 · Resumen

  • Field (con Annotated) añade constraints y metadatos a un campo: ge, le, min_length, pattern…
  • Los tipos especiales (EmailStr, HttpUrl, UUID, datetime, Decimal) validan conceptos de dominio sin código propio.
  • Literal y Enum expresan conjuntos cerrados de valores.
  • @field_validator valida un campo; @model_validator(mode="after") valida reglas cruzadas.
  • En un validador se lanza ValueError (nunca HTTPException): se convierte en 422.
  • El error 422 tiene la forma {"detail": [{type, loc, msg, input, ctx}]}; loc señala dónde y type es el identificador estable.
  • Programa contra type+loc, no contra msg.

10 · Preguntas frecuentes

¿Por qué 422 y no 400 para errores de validación?

El código 422 «Unprocessable Entity» (definido en la especificación WebDAV y recogido por la práctica) describe exactamente esto: la petición está sintácticamente bien formada, pero su contenido no cumple el contrato. FastAPI lo usa por convención y porque separa «JSON mal formado» (400) de «JSON bien formado con datos inválidos» (422). Es un valor por defecto configurable, pero la comunidad lo ha adoptado así.

¿Puedo cambiar los mensajes de error para traducirlos al español?

Sí. La vía limpia es registrar un exception handler para RequestValidationError y transformar la lista detail a tu propio formato (por ejemplo, Problem Details, como haremos en el Módulo 2). Para traducir, mapea por type+loc en lugar de reemplazar por msg, porque los textos pueden cambiar entre versiones.

¿Un validador puede modificar el valor, o solo aceptarlo o rechazarlo?

Puede modificarlo: esa es una de sus grandes ventajas. Por ejemplo, recortar espacios, pasar a minúsculas o convertir "" en None. Solo recuerda devolver el valor (transformado o no); si no devuelves, se pierde.

¿Field también sirve para la respuesta, o solo para el cuerpo de entrada?

Para ambos. Cualquier modelo Pydantic puede usarse como entrada (cuerpo) o como salida (response_model). Las restricciones de Field y los validadores se aplican igual cuando el modelo valida la respuesta, lo que ayuda a detectar bugs en tus propios datos antes de enviarlos.

¿Dónde veo todas las restricciones cuando tengo muchos modelos?

En /docs y en el esquema OpenAPI (/openapi.json): cada constraint aparece como parte de la definición del campo, y el JSON Schema de Pydantic incluye los ejemplos. Ese esquema es, además, la fuente de verdad para generar clientes tipados.
