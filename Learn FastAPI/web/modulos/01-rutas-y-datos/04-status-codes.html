Códigos de estado

Módulo 1 · Rutas y datos 🕐 30 minutos

1 · Introducción

Toda respuesta HTTP lleva un código de estado: un número de tres cifras que resume el resultado de la petición. Los 200 que ya viste son solo el caso «todo fue bien». Pero una API profesional distingue entre «creé un recurso» (201), «no llevo cuerpo» (204), «no existe» (404), «no tienes permiso» (403) o «los datos no cumplen el contrato» (422). Usar el código correcto no es cosmético: tus clientes, tu documentación y las herramientas de operación deciden cosas en función de él.

En esta lección aprenderás a fijar el código con status_code, a usar las constantes de fastapi.status (que reexporta las de Starlette), a manejar los casos especiales 201 y 204 y a documentar las respuestas alternativas con el parámetro responses.

¿Por qué el código importa de verdad? Porque el código es parte del contrato. Un cliente bien hecho comprueba response.status_code antes de leer el cuerpo; un POST que siempre devuelve 200 «también cuando crea» obliga a ese cliente a leer el cuerpo para saber si algo se creó. Y un 500 que debería ser un 404 esconde bugs y salta las alertas de on-call sin motivo.

2 · Teoría

Las familias de códigos

El primer dígito indica la familia:

FamiliaSignificadoEjemplos
1xx InformativoSe usa poco; cambia el protocolo en curso.101 Switching Protocols
2xx ÉxitoLa petición se procesó correctamente.200 OK, 201 Created, 204 No Content
3xx RedirecciónHay que ir a otra parte.301, 307, 308
4xx Error del clienteLa petición tiene un problema que el cliente debe corregir.400, 401, 403, 404, 409, 422
5xx Error del servidorLa petición era correcta, pero nosotros fallamos.500, 502, 503

Analogía — el mostrador de atención: el cuerpo de la respuesta es lo que te entregan; el código de estado es el sello que el empleado pone al devolverte el papel: «tramitado» (200), «alta nueva creada» (201), «recibido, no había nada que devolver» (204), «no existe ese expediente» (404), «no tienes autorización» (403), «el formulario está mal relleno» (422). El sello permite saber qué pasó sin abrir el sobre.

El código por defecto y cómo cambiarlo

Si no dices nada, FastAPI responde 200. Para cambiarlo, pasa status_code al decorador:

from fastapi import FastAPI, status

app = FastAPI()

@app.post("/modules", status_code=status.HTTP_201_CREATED)
def create_module():
    return {"id": 1, "title": "Rutas y datos"}

FastAPI acepta un entero literal (status_code=201), pero es mejor usar las constantes de fastapi.status: status.HTTP_201_CREATED. El código leído es más claro y no memorizas números. fastapi.status reexporta starlette.status, así que ambas importaciones valen.

¿Qué cambia el código? El valor que se envía en la primera línea de la respuesta HTTP y que se refleja en OpenAPI. No cambia el cuerpo: si devuelves un dict, se serializa a JSON igual, con 200 o con 201.

201 Created y 204 No Content

Son los dos códigos que más se usan mal:

CódigoCuándoCuerpo
201 CreatedUn POST que crea un recurso nuevo.Sí: normalmente el recurso creado (con su ID).
204 No ContentLa operación tuvo éxito pero no hay nada que devolver (p. ej. un DELETE).No: 204 significa literalmente «sin cuerpo».
 
from fastapi import FastAPI, Response, status

app = FastAPI()

# 201 al crear; el cuerpo es el recurso recién creado.
@app.post("/modules", status_code=status.HTTP_201_CREATED)
def create_module():
    return {"id": 1, "title": "Rutas y datos"}

# 204 al borrar: devuelve None y NO declares cuerpo.
@app.delete("/modules/{module_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_module(module_id: int):
    return None

Opcionalmente, un 201 puede enriquecerse con la cabecera Location apuntando al recurso nuevo: response.headers["Location"] = f"/modules/{new_id}" (declarando un parámetro response: Response). No es obligatorio, pero es un detalle fino que algunos clientes aprovechan.

Documentar respuestas alternativas con responses

El status_code documenta el éxito. Pero un endpoint también devuelve errores, y esos conviene declararlos en OpenAPI con el parámetro responses:

from fastapi import FastAPI
from pydantic import BaseModel

class Message(BaseModel):
    detail: str

app = FastAPI()

@app.get(
    "/modules/{module_id}",
    responses={404: {"description": "Módulo no encontrado", "model": Message}},
)
def get_module(module_id: int):
    ...

responses es un diccionario {código: {"description", "model"}}. No causa el 404 —eso lo hace tu lógica con HTTPException—; simplemente documenta que ese endpoint puede devolverlo y con qué forma. Es la forma de que /docs cuente la verdad completa.

Errores: HTTPException con código

Los errores se lanzan con HTTPException, indicando el código y el detalle:

from fastapi import HTTPException, status

if module is None:
    raise HTTPException(
        status_code=status.HTTP_404_NOT_FOUND,
        detail="Modulo no encontrado",
    )

FastAPI ya genera solo dos códigos de error por ti: 422 cuando falla la validación y 500 cuando tu código lanza una excepción no controlada. Todo lo demás (404, 403, 409…) lo decides tú.

No devuelvas errores con código 200. Devolver {"error": "no encontrado"} con un 200 rompe a los clientes, engaña a los monitores y hace que un fallo parezca un éxito. Si algo es un error, usa el código de la familia 4xx/5xx correspondiente.

3 · Ejemplo mínimo

Dos endpoints que ilustran los códigos que más aparecen: un POST que responde 201 y un DELETE que responde 204.

main.py
# main.py — 201 al crear, 204 al borrar
from fastapi import FastAPI, status

app = FastAPI()

_items: dict[int, dict] = {}


# POST crea -> 201 Created
@app.post("/items", status_code=status.HTTP_201_CREATED)
def create_item(name: str):
    new_id = len(_items) + 1
    _items[new_id] = {"id": new_id, "name": name}
    return _items[new_id]          # cuerpo: el recurso creado


# DELETE borra -> 204 No Content (sin cuerpo)
@app.delete("/items/{item_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_item(item_id: int):
    _items.pop(item_id, None)
    return None                    # 204 no lleva cuerpo

uv run uvicorn main:app --reload

# -i muestra la cabecera con el código de estado
curl -i -X POST "http://127.0.0.1:8000/items?name=teclado"
# -> HTTP/1.1 201 Created
#    {"id":1,"name":"teclado"}

curl -i -X DELETE "http://127.0.0.1:8000/items/1"
# -> HTTP/1.1 204 No Content

El 204 no lleva cuerpo, y punto. No devuelvas un JSON de confirmación con 204: por especificación, un 204 no tiene contenido. Si quieres confirmar el borrado, hazlo con 200 y un cuerpo, o confía en el propio 204 («si no es error, funcionó»).

4 · Ejemplo real

Los endpoints de Copiloto API con sus códigos correctos y sus respuestas de error documentadas. Fíjate en el mapa completo: 200 para lecturas y consultas, 201 al crear feedback, 404 cuando el módulo no existe, 204 al borrar.

app/routers/modules.py
# app/routers/modules.py — códigos de estado de cada operación
from fastapi import APIRouter, HTTPException, status
from pydantic import BaseModel

router = APIRouter(prefix="/modules", tags=["modules"])


class Message(BaseModel):
    detail: str


_MODULES: dict[int, dict] = {
    1: {"id": 1, "title": "Que es FastAPI", "level": "basico"},
    2: {"id": 2, "title": "Rutas y datos", "level": "basico"},
}


# GET devuelve 200 por defecto. Documentamos el 404 en responses.
@router.get(
    "/{module_id}",
    responses={404: {"description": "Modulo no encontrado", "model": Message}},
)
def get_module(module_id: int):
    module = _MODULES.get(module_id)
    if module is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Modulo no encontrado",
        )
    return module


# POST crea -> 201 Created
@router.post("", status_code=status.HTTP_201_CREATED)
def create_module(title: str, level: str = "basico"):
    new_id = max(_MODULES) + 1
    module = {"id": new_id, "title": title, "level": level}
    _MODULES[new_id] = module
    return module


# DELETE borra -> 204 No Content
@router.delete("/{module_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_module(module_id: int):
    if module_id not in _MODULES:
        raise HTTPException(status_code=404, detail="Modulo no encontrado")
    del _MODULES[module_id]
    return None
app/routers/ask.py
# app/routers/ask.py — /ask devuelve 200: no crea un recurso nuevo,
# responde a una pregunta. Aunque sea POST, 200 es lo correcto aquí.
from fastapi import APIRouter

router = APIRouter(tags=["copiloto"])


@router.post("/ask")   # sin status_code -> 200 OK
def ask(question: str):
    return {"answer": f"[stub] responderia a: {question}"}

curl -i "http://127.0.0.1:8000/modules/1"      # -> 200 OK
curl -i "http://127.0.0.1:8000/modules/999"    # -> 404 Not Found

curl -i -X POST "http://127.0.0.1:8000/modules?title=Seguridad"
# -> 201 Created

curl -i -X DELETE "http://127.0.0.1:8000/modules/2"
# -> 204 No Content

POST no siempre es 201. /ask es un POST (envía un cuerpo), pero no crea un recurso persistente: responde a una pregunta y por eso devuelve 200. El código correcto depende de lo que hace la operación, no del método HTTP.

5 · Buenas prácticas

HazEvitaPor qué
Usa status.HTTP_201_CREATED y demás constantes Enteros mágicos (status_code=201, raise HTTPException(404)) La constante se lee sola y evita erratas; el número obliga a recordar qué significa.
201 con el recurso creado 201 con un mensaje «creado» sin datos Devolver el recurso (con su ID) ahorra al cliente una segunda petición para conocerlo.
204 sin cuerpo en DELETE 204 devolviendo {"ok": true} Un 204 no tiene contenido por especificación; el cliente no puede confiar en un cuerpo que no debe existir.
Documenta los errores con responses Documentar solo el 200 El consumidor necesita saber qué 404/409 puede recibir y con qué forma; /docs debe contar toda la verdad.
404 para «no existe», 403 para «no puedes», 409 para «conflicto» Usar 400 o 404 para todo Cada código guía al cliente sobre qué hacer y a los monitores sobre qué alertar.
Deja 422 para la validación automática Reusar 422 para errores de negocio 422 ya significa «contrato de datos incumplido»; para reglas de negocio usa 400/409/403.

6 · Errores habituales

Devolver 200 al crear un recurso

# ❌ El cliente no sabe si creó algo o solo lo consultó
@app.post("/modules")
def create_module(title: str):
    return {"id": 1, "title": title}    # -> 200 OK (por defecto)

# ✅
from fastapi import status

@app.post("/modules", status_code=status.HTTP_201_CREATED)
def create_module(title: str):
    return {"id": 1, "title": title}

Devolver cuerpo con un 204

# ❌ 204 significa "sin contenido"; devolver un cuerpo lo contradice
from fastapi import status

@app.delete("/modules/{module_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_module(module_id: int):
    return {"deleted": True}    # incoherente con 204

# ✅ Devuelve None y no declares cuerpo
@app.delete("/modules/{module_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_module(module_id: int):
    return None

Errores disfrazados de éxito

# ❌ Un "no encontrado" que responde 200
@app.get("/modules/{module_id}")
def get_module(module_id: int):
    module = _MODULES.get(module_id)
    if module is None:
        return {"error": "no encontrado"}   # -> 200 OK. ¡Mentira!

# ✅ El error es un error: lanza HTTPException con su código
from fastapi import HTTPException, status

@app.get("/modules/{module_id}")
def get_module(module_id: int):
    module = _MODULES.get(module_id)
    if module is None:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND,
                            detail="Modulo no encontrado")
    return module

Usar el mismo 400 para todo

# ❌ Todo es "400" y el cliente no puede reaccionar bien
raise HTTPException(status_code=400, detail="no existe")     # deberia ser 404
raise HTTPException(status_code=400, detail="sin permiso")   # deberia ser 403
raise HTTPException(status_code=400, detail="ya existe")     # deberia ser 409

# ✅ Cada situación, su código
raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="no existe")
raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="sin permiso")
raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail="ya existe")

Devolver 500 para fallos del cliente

# ❌ int() lanza ValueError y FastAPI responde 500 (parece culpa TUYA)
@app.get("/modules/{module_id}")
def get_module(module_id: int):   # <- si declaras el tipo int, esto NO pasa:
    ...                           #     un "foo" daria 422, no 500.
# El 500 aparece cuando TÚ lanzas una excepción no controlada, p. ej.:
value = int("no-es-numero")       # ValueError -> 500 (error de servidor)

500 es «culpa del servidor». Un 500 dispara alertas y rompe la confianza del cliente. Si el problema lo causó el cliente (dato malo, recurso inexistente, sin permiso), devuelve un 4xx. Deja el 500 para lo que de verdad es un fallo tuyo no previsto, y que sea ruidoso para que lo arregles.

9 · Resumen

  • El código de estado resume el resultado y forma parte del contrato de la API.
  • Familias: 2xx éxito, 3xx redirección, 4xx error del cliente, 5xx error del servidor.
  • Por defecto FastAPI responde 200; se cambia con status_code en el decorador.
  • Usa constantes de fastapi.status (reexporta starlette.status) en vez de enteros mágicos.
  • 201 al crear (con el recurso en el cuerpo), 204 cuando no hay cuerpo (p. ej. DELETE).
  • responses={404: {"description": ..., "model": ...}} documenta respuestas alternativas en OpenAPI.
  • Los errores se lanzan con HTTPException(status_code=..., detail=...).
  • FastAPI genera solo 422 (validación) y 500 (excepción no controlada); el resto lo decides tú.
CódigoCuándo usarlo
200 OKLectura, actualización o acción con resultado exitoso.
201 CreatedUn POST que crea un recurso (devuelve el recurso).
204 No ContentÉxito sin cuerpo (típico DELETE).
400 Bad RequestPetición/negocio inválido que no encaja en 422.

10 · Preguntas frecuentes

¿status_code en el decorador o un parámetro response: Response?

El decorador fija un código fijo para todas las respuestas exitosas de ese endpoint. Si necesitas decidir el código en tiempo de ejecución (a veces 200, a veces 201), declara un parámetro response: Response y asígnale response.status_code = ... dentro de la función. Para el 99% de los casos, el decorador es más claro y autodocumentado.

¿Puedo devolver 204 y aun así dar información al cliente?

No en el cuerpo (204 no lleva contenido), pero sí en las cabeceras. Por ejemplo, puedes incluir un X-Deleted-Id o reutilizar cabeceras estándar. Eso sí, si lo que quieres comunicar es relevante, quizá un 200 con un pequeño cuerpo sea más honesto que forzar un 204 con cabeceras exóticas.

¿responses hace que el endpoint devuelva ese código?

No. responses solo documenta (aparece en /docs y en /openapi.json). Quien devuelve realmente el 404 es tu código, normalmente con raise HTTPException(status_code=404, ...). Documentar y provocar son dos tareas separadas: no olvides la segunda.

¿Qué código uso para una operación que se procesará más tarde?

202 Accepted: indica que la petición se aceptó para procesarse de forma asíncrona, sin garantizar que ya haya terminado. Es el código natural para tareas en segundo plano (colas, generación de informes). Devuelve un cuerpo con un identificador de la tarea y, si quieres, una cabecera Location para consultar su estado.

¿Cómo veo todos los códigos que puede devolver mi API?

En /openapi.json (o en la sección de respuestas de /docs). Cada endpoint lista su respuesta de éxito y las que hayas declarado en responses. Si echas en falta un código, probablemente sea porque no lo documentaste: revisar el contrato OpenAPI es una buena forma de auditar una API.
