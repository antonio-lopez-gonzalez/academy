Cuerpo con Pydantic

Módulo 1 · Rutas y datos 🕐 35 minutos

1 · Introducción

Cuando un cliente crea o envía datos —preguntarle algo al Copiloto, guardar una tarea, registrar un usuario— no cabe todo en la URL. Esos datos viajan en el cuerpo (body) de la petición, normalmente como JSON. Y ahí está el reto: un JSON puede traer cualquier cosa. ¿Cómo te aseguras de que lo que llega tiene la forma que esperas?

La respuesta de FastAPI es Pydantic v2: describes el cuerpo como una clase (BaseModel) y el framework, a partir del tipo del parámetro, parsea, valida y convierte el JSON en una instancia de esa clase. Si algo no cuadra, responde un 422 con el detalle. En esta lección aprenderás modelos anidados, conversiones de tipo y por qué «el tipo define la validación».

¿Por qué no usar un dict y leer claves a mano? Porque con un dict tú te conviertes en el validador: data["top_k"] revienta con KeyError, data.get("temperature") puede ser un texto, y nadie documenta qué campos existen. Un modelo Pydantic declara una vez la forma del cuerpo; de ahí salen la validación, la conversión a los tipos correctos, el autocompletado del editor y el esquema OpenAPI.

2 · Teoría

¿Dónde vive el cuerpo de la petición?

Una petición HTTP tiene tres zonas donde puede viajar información:

POST /ask HTTP/1.1 <- método + ruta Host: api.copiloto.dev <- cabeceras Content-Type: application/json <- cabeceras (¡obligatoria con body!) <- línea en blanco { <- CUERPO (JSON) "question": "Que es ASGI?", "top_k": 4 }

Los datos del cuerpo no se pueden validar mirando la URL: hay que leer el flujo de bytes y entender JSON. FastAPI solo lo hace cuando declaras un parámetro con un tipo que no es escalar (un modelo Pydantic, una lista, un dict).

Un modelo Pydantic es la forma del cuerpo

from pydantic import BaseModel

class AskRequest(BaseModel):
    question: str        # obligatorio
    top_k: int = 4       # opcional: tiene default

Al declarar ask: AskRequest en la función de ruta, FastAPI infiere tres cosas:

InfiereQué hace
OrigenLos modelos van al cuerpo, no a la query (por eso AskRequest no aparece en la URL).
FormatoEl cuerpo se interpreta como JSON (no formularios, no texto plano).
ValidaciónSe comprueba cada campo y, si algo falla, se lanza un 422 con la lista de errores.

Analogía — el formulario con validación: el modelo Pydantic es como un formulario impreso con casillas: «pregunta (texto obligatorio)», «top_k (número, por defecto 4)». El cliente rellena el formulario (el JSON); el recepcionista (FastAPI/Pydantic) comprueba que ninguna casilla esté mal escrita y que los números sean números. Si algo no cuadra, devuelve el formulario con las tildes rojas (el 422) en lugar de pasarlo a producción a medias.

El tipo define la validación

Cada anotación es una regla. Pydantic v2, además, es estricto en la forma pero generoso en la conversión: acepta un "4" (texto) donde espera un int y lo convierte a 4; rechaza "cuatro". Estas son las reglas más usadas:

TipoEsperaConvierte desde
strCadenaNúmeros → texto (según config)
intEntero"4", 4.0 → 4; rechaza "4.5"
floatDecimal"0.7", 1 → 1.0
boolBooleanotrue, 1, "true"
list[str]Lista de textosUna lista JSON
datetimeFecha ISO 8601"2026-01-31T10:00:00"

La conversión ocurre una sola vez. Cuando tu función se ejecuta, ask.top_k ya es un int, ask.question ya es un str. Dentro del handler no hay que convertir nada: lo que te llega ya cumple el contrato, o el framework no te habría llamado.

Modelos anidados

El cuerpo real rara vez es plano. Un modelo puede contener otro modelo o una lista de modelos, y la validación baja por toda la jerarquía:

class RAGConfig(BaseModel):
    top_k: int = 4
    temperature: float = 0.2

class AskRequest(BaseModel):
    question: str
    config: RAGConfig = RAGConfig()   # objeto anidado, con default
AskRequest ├── question: str └── config: RAGConfig ├── top_k: int = 4 └── temperature: float = 0.2

Si el cliente envía {"question": "hola", "config": {"top_k": "cuatro"}}, el 422 apuntará a loc: ["body", "config", "top_k"]: la ruta exacta hasta el campo que falló.

Cuándo un modelo NO va al cuerpo: Body(embed=True)

Si declaras un único modelo Pydantic, FastAPI asume que todo el JSON es ese modelo: la petición envía las claves del modelo directamente. Para forzar la forma anidada (el modelo bajo una clave) se usa Body(embed=True):

from typing import Annotated
from fastapi import Body

@app.post("/ask")
def ask(ask: Annotated[AskRequest, Body(embed=True)]):
    ...
# Espera: {"ask": {"question": "...", "config": {...}}}

Es útil cuando un endpoint recibe body y, además, otros parámetros, y quieres desambiguar las claves. En el 99% de los casos no hace falta.

3 · Ejemplo mínimo

El cuerpo más pequeño posible: un modelo de dos campos y un POST que lo recibe y lo devuelve.

main.py
# main.py — el cuerpo más pequeño con un modelo Pydantic v2
from pydantic import BaseModel
from fastapi import FastAPI

app = FastAPI()


# 1) El modelo describe la forma del cuerpo.
class Item(BaseModel):
    name: str            # obligatorio
    price: float         # obligatorio
    in_stock: bool = True  # opcional (tiene default)


# 2) El parámetro `item` es un modelo => FastAPI lo lee del CUERPO como JSON.
@app.post("/items")
def create_item(item: Item):
    # item.name ya es str, item.price ya es float: nada que convertir.
    return {"created": item.name, "price": item.price, "in_stock": item.in_stock}

uv run uvicorn main:app --reload

# Cuerpo válido (-> 200 OK)
curl -X POST "http://127.0.0.1:8000/items" \
  -H "Content-Type: application/json" \
  -d '{"name": "teclado", "price": 49.9}'
# -> {"created":"teclado","price":49.9,"in_stock":true}

# Falta un campo obligatorio (-> 422)
curl -X POST "http://127.0.0.1:8000/items" \
  -H "Content-Type: application/json" \
  -d '{"name": "teclado"}'
# -> 422: loc ["body","price"], msg "Field required"

# Tipo incorrecto e imposible de convertir (-> 422)
curl -X POST "http://127.0.0.1:8000/items" \
  -H "Content-Type: application/json" \
  -d '{"name": "teclado", "price": "caro"}'
# -> 422: loc ["body","price"], msg "Input should be a valid number"

La cabecera Content-Type no es opcional. Sin Content-Type: application/json, FastAPI no trata el cuerpo como JSON y devuelve 422. Es una de las causas más frecuentes del «¿por qué no me valida el JSON?».

4 · Ejemplo real

El endpoint central de Copiloto API: POST /ask. La pregunta del usuario es obligatoria; la configuración del motor RAG (cuántos fragmentos recuperar, con qué temperatura) viaja como un modelo anidado con valores por defecto razonables, para que un cliente pueda preguntar sin configurar nada.

app/schemas/ask.py
# app/schemas/ask.py — contratos del endpoint /ask
from pydantic import BaseModel


class RAGConfig(BaseModel):
    """Ajustes del motor de recuperación (RAG)."""
    top_k: int = 4              # nº de fragmentos a recuperar
    temperature: float = 0.2    # creatividad del modelo generativo


class AskRequest(BaseModel):
    """Cuerpo de la petición: lo que el usuario pregunta."""
    question: str                            # obligatorio
    module_id: int | None = None             # opcional: limitar el contexto
    config: RAGConfig = RAGConfig()          # anidado, con default completo


class AskResponse(BaseModel):
    """Cuerpo de la respuesta: lo que devuelve la API."""
    answer: str
    sources: list[str]
app/routers/ask.py
# app/routers/ask.py — el endpoint del Copiloto
from fastapi import APIRouter

from app.schemas.ask import AskRequest, AskResponse

router = APIRouter(tags=["copiloto"])


@router.post("/ask", response_model=AskResponse)
def ask(payload: AskRequest) -> AskResponse:
    # payload.question ya es str; payload.config.top_k ya es int.
    # (El RAG real llega en el Módulo 7; aquí devolvemos un stub honesto.)
    context = f"modulo {payload.module_id}" if payload.module_id else "todos los modulos"
    return AskResponse(
        answer=(
            f"[stub] Buscaria en {context} los {payload.config.top_k} "
            f"fragmentos mas relevantes para: {payload.question!r}"
        ),
        sources=["01-rutas-path-query", "03-validacion-y-tipos"],
    )

# Pregunta mínima: solo el campo obligatorio. El resto usa defaults.
curl -X POST "http://127.0.0.1:8000/ask" \
  -H "Content-Type: application/json" \
  -d '{"question": "Que es ASGI?"}'
# -> {"answer":"[stub] Buscaria en todos los modulos los 4 fragmentos...", "sources":[...]}

# Pregunta con configuración anidada
curl -X POST "http://127.0.0.1:8000/ask" \
  -H "Content-Type: application/json" \
  -d '{"question": "Que es ASGI?", "module_id": 3, "config": {"top_k": 8, "temperature": 0.5}}'

# El anidamiento falla en un campo profundo (-> loc ["body","config","top_k"])
curl -X POST "http://127.0.0.1:8000/ask" \
  -H "Content-Type: application/json" \
  -d '{"question": "hola", "config": {"top_k": "ocho"}}'

Modelar la respuesta también. response_model=AskResponse hace que FastAPI valide y filtre lo que devuelves antes de serializarlo: si un campo se te cuela, se descarta. response_model es el tema de la primera lección del Módulo 2; aquí basta con saber que la forma de salida también es un contrato.

5 · Buenas prácticas

HazEvitaPor qué
Modela el cuerpo con BaseModel Recibir un dict y leer claves con .get() El modelo valida, documenta y da tipos al editor; el dict no hace nada de eso.
Nombra modelos de entrada con ...Request y de salida con ...Response Un único modelo para todo Separar entrada y salida te deja evolucionar la API sin exponer campos internos (Módulo 2).
Usa default_factory para listas/dicts por defecto tags: list[str] = [] como valor mutable por defecto Pydantic v2 ya copia los defaults mutables, pero default_factory=list expresa la intención y es inequívoco.
Modelos anidados para subestructuras reales Aplanar todo en 20 campos con prefijos (config_top_k, config_temp…) El anidamiento refleja el dominio, produce loc precisos en los errores y esquemas OpenAPI legibles.
Da defaults sensatos a lo opcional Obligar a enviar la configuración completa en cada petición Una API usable tiene «feliz camino corto»: {"question": "..."} debe bastar.
Reutiliza modelos entre endpoints Duplicar la misma clase en cada router Un solo sitio que cambiar; el resto de la API hereda la validación.

6 · Errores habituales

Usar un dict en lugar de un modelo

# ❌ Sin contrato: cualquier JSON pasa y los errores son tuyos
@app.post("/ask")
def ask(payload: dict):
    question = payload["question"]      # KeyError si falta
    top_k = payload.get("top_k", 4)     # ¿y si llega "ocho"?
    ...

# ✅ El modelo valida y convierte; el handler solo usa datos buenos
from pydantic import BaseModel

class AskRequest(BaseModel):
    question: str
    top_k: int = 4

@app.post("/ask")
def ask(payload: AskRequest):
    return {"q": payload.question, "k": payload.top_k}

Olvidar la cabecera Content-Type

# ❌ Sin Content-Type, FastAPI no interpreta el cuerpo como JSON
curl -X POST http://127.0.0.1:8000/items -d '{"name": "teclado", "price": 49.9}'
# -> 422: "Input should be a valid dictionary or object"

# ✅ Declara el tipo de contenido
curl -X POST http://127.0.0.1:8000/items \
  -H "Content-Type: application/json" \
  -d '{"name": "teclado", "price": 49.9}'

Confundir el nivel del JSON: embed

# ❌ Con un único modelo, FastAPI espera las CLAVES del modelo en la raíz,
#    no el modelo bajo una clave:
#    {"question": "...", "top_k": 4}
@app.post("/ask")
def ask(payload: AskRequest): ...

# Si el cliente envía {"ask": {"question": "..."}} obtiene un 422
# porque "question" no está en la raíz.

# ✅ Si DE VERDAD quieres el modelo anidado bajo una clave, pídelo explícito:
from typing import Annotated
from fastapi import Body

@app.post("/ask")
def ask(payload: Annotated[AskRequest, Body(embed=True)]): ...
# Ahora sí: {"ask": {"question": "...", "top_k": 4}}

Validar tipos con comprobaciones manuales dentro del handler

# ❌ Reimplementas la validación (y con una forma de error distinta)
class AskRequest(BaseModel):
    question: str
    top_k: int = 4

@app.post("/ask")
def ask(payload: AskRequest):
    if payload.top_k < 1 or payload.top_k > 20:
        return {"error": "top_k fuera de rango"}   # no es un 422 estándar
    ...

# ✅ Pon la restricción en el tipo (lo formalizas en la próxima lección)
from typing import Annotated
from pydantic import Field

class AskRequest(BaseModel):
    question: str
    top_k: Annotated[int, Field(ge=1, le=20)] = 4

No conviertas «por si acaso» dentro del handler. Si recibes un AskRequest, sus campos ya tienen el tipo declarado. Hacer int(payload.top_k) otra vez es ruido y puede enmascarar un 422 que debería haber cortado antes. La validación vive en los tipos, no en el cuerpo del endpoint.

7 · Ejercicio guiado

Objetivo: modelar un endpoint de feedback del Copiloto con un cuerpo anidado y comprobar la conversión y los 422.

  1. Paso 1 — Define los modelos. Un feedback tiene una rating (entero de 1 a 5, por ahora sin restricción), un comentario opcional y los datos del módulo valorado, que a su vez son un modelo anidado.
    app/schemas/feedback.py
    from pydantic import BaseModel


class ModuleRef(BaseModel):
    """Referencia al módulo que se valora."""
    module_id: int
    title: str


class FeedbackRequest(BaseModel):
    """Cuerpo del feedback del usuario."""
    rating: int                       # 1..5 (la restricción formal llega en la lección 03)
    comment: str | None = None        # opcional
    module: ModuleRef                 # ¡anidado y obligatorio!
  2. Paso 2 — El endpoint. Un POST /feedback que devuelve un eco con el rating convertido a int y el módulo anidado.
    app/main.py
    from fastapi import FastAPI

from app.schemas.feedback import FeedbackRequest

app = FastAPI(title="Copiloto API")


@app.post("/feedback")
def create_feedback(payload: FeedbackRequest):
    # payload.module.module_id ya es int; payload.rating ya es int.
    return {
        "accepted": True,
        "rating": payload.rating,
        "module": {"id": payload.module.module_id, "title": payload.module.title},
    }
  3. Paso 3 — Prueba un cuerpo completo y uno con conversión. 
    uv run uvicorn app.main:app --reload

# Cuerpo válido
curl -X POST "http://127.0.0.1:8000/feedback" \
  -H "Content-Type: application/json" \
  -d '{"rating": 5, "comment": "muy util", "module": {"module_id": 1, "title": "Rutas"}}'

# Pydantic convierte "5" (texto) a 5 (entero): sigue siendo 200 OK
curl -X POST "http://127.0.0.1:8000/feedback" \
  -H "Content-Type: application/json" \
  -d '{"rating": "5", "module": {"module_id": "1", "title": "Rutas"}}'
  4. Paso 4 — Fuerza errores y localízalos. 
    # Falta el modelo anidado obligatorio
curl -X POST "http://127.0.0.1:8000/feedback" \
  -H "Content-Type: application/json" \
  -d '{"rating": 5}'
# -> 422: loc ["body","module"], msg "Field required"

# Fallo en un campo profundo: la ruta del error lo señala
curl -X POST "http://127.0.0.1:8000/feedback" \
  -H "Content-Type: application/json" \
  -d '{"rating": "excelente", "module": {"module_id": 1, "title": "Rutas"}}'
# -> 422: loc ["body","rating"]
  5. Paso 5 — Verificación final. Abre /docs: el modelo FeedbackRequest aparece como esquema con module anidado y un ejemplo JSON generado. Si el schema muestra la jerarquía, has entendido Pydantic como contrato.

8 · Reto

🎯 Un cuerpo para varios endpoints

Modela el cuerpo de un endpoint de creación de módulos (POST /modules) que reutilice ModuleRef y añada campos propios: una lista de tags (por defecto vacía), una fecha de publicación opcional (datetime) y un campo level. Después diseña un PATCH /modules/{module_id} que acepte todos los campos opcionales (una actualización parcial): pista, aquí conviene un modelo distinto del de creación, con cada campo ... | None = None.

Pista: observa en /docs cómo el mismo nombre de modelo reutilizado no basta cuando los campos obligatorios cambian entre crear y actualizar. Pregúntate qué debe pasar si un PATCH llega con {} vacío (¿actualiza algo? ¿es válido?) y deja que esa pregunta guíe tu diseño. No hay una única respuesta correcta: el reto es pensar en contratos.

9 · Resumen

  • El cuerpo de la petición transporta datos que no caben en la URL; en una API moderna es JSON.
  • Declarar un parámetro de tipo BaseModel hace que FastAPI lo lea del cuerpo y lo valide.
  • El tipo define la validación: int, float, bool, datetime, listas y modelos se validan y convierten solos.
  • La conversión ocurre antes de tu función: dentro del handler los datos ya cumplen el contrato.
  • Los modelos anidados validan toda la jerarquía y producen errores con ruta exacta en loc.
  • Body(embed=True) solo cuando quieres el modelo bajo una clave concreta del JSON.
  • Separa modelos de entrada y de salida; modelar la respuesta es el tema siguiente (Módulo 2).

10 · Preguntas frecuentes

¿Pydantic convierte de verdad "4" a 4? ¿No es peligroso?

Sí lo hace, y en la práctica es cómodo: muchos clientes (formularios HTML, algunos SDKs) envían números como texto. Pydantic v2 convierte cuando la conversión es inequívoca y rechaza cuando no ("cuatro" → 422). Si quieres cero tolerancia, el modo strict de Pydantic se activa por modelo o por campo; para la mayoría de APIs la conversión por defecto es el equilibrio correcto.

¿Qué pasa si mi modelo tiene un campo que el cliente no envía y no tiene default?

Es un 422 con msg: "Field required" y la loc apuntando al campo. Si el campo puede faltar, dale un default (= None para opcional, o un valor con sentido). En un PATCH parcial todos los campos deben ser opcionales; en un POST de creación, los imprescindibles son obligatorios.

¿Cómo ignoro campos extra que mande el cliente?

Por defecto Pydantic v2 ignora las claves desconocidas (no falla). Si quieres rechazarlas con un 422, usa model_config = ConfigDict(extra="forbid"). Prohibirlas es buena idea para detectar erratas del cliente (un temperatur mal escrito); ignorarlas es más tolerante con clientes que envían metadatos de más.

¿Cuándo uso Body(embed=True)?

Solo cuando tu endpoint combina un modelo y otros parámetros (query o body escalares) y quieres desambiguar las claves del JSON, o cuando por compatibilidad necesitas el modelo bajo un nombre concreto. Con un único modelo y sin ambigüedad, FastAPI espera las claves del modelo en la raíz y no hace falta embed.

¿Dónde documento las restricciones de cada campo (rangos, longitudes)?

En el propio modelo, con Field y validadores. Ese es justo el tema de la próxima lección, Validación y tipos: Field(ge=1, le=5), min_length, pattern y field_validator — todo declarado en el modelo, visible en /docs y aplicado en cada petición.
