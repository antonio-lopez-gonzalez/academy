OAuth2 y JWT: login y token

Módulo 5 · Seguridad 🕐 40 minutos

1 · Introducción

Hasta ahora cualquiera que descubra la URL de tu API puede llamarla. Copiloto API expone POST /ask, que cuesta dinero (llama al modelo), y GET /logs, que guarda el histórico de preguntas. Si esos endpoints son públicos, cualquiera consume tu presupuesto y lee datos que no le corresponden. Es el momento de responder a una pregunta: ¿quién eres? Eso es autenticación.

Este módulo resuelve dos problemas distintos que conviene no mezclar: autenticación (identificar al usuario) y autorización (decidir qué puede hacer). Esta primera lección ataca la autenticación con el mecanismo que FastAPI trae de serie: el flujo password de OAuth2 para hacer login y un JWT (JSON Web Token) firmado como credencial de las peticiones siguientes. La autorización —roles y permisos— llega en la lección 2.

¿Por qué existe esta lección? Porque una API real no autentica en cada petición con usuario y contraseña. El cliente canjea sus credenciales una vez por un token que viaja en cada petición y caduca. Es el patrón que usan Google, GitHub y cualquier API moderna, y el que el propio /docs de FastAPI entiende sin configurar nada.

Errores típicos que veremos y evitaremos: guardar contraseñas en claro o con un hash inventado, poner la clave secreta en el repositorio, emitir tokens sin caducidad, decodificar el JWT sin fijar el algoritmo (cediendo ante el ataque alg: none), meter datos sensibles en el payload (el JWT no está cifrado) y confundir un 401 (no autenticado) con un 403 (autenticado pero sin permiso).

2 · Teoría

Autenticación vs. autorización

Son dos preguntas distintas y con dos códigos de estado distintos:

PreguntaConceptoSi falla
¿Quién eres?Autenticación401 Unauthorized (+ WWW-Authenticate)
¿Puedes hacer esto?Autorización403 Forbidden

En esta lección el 401 es el protagonista: no hay token, el token está caducado o la firma no cuadra. En la lección 2 aparecerá el 403.

El flujo password de OAuth2

OAuth2 define varios flujos; nosotros usamos el password flow, el adecuado para un cliente de confianza (tu propio frontend) que recoge usuario y contraseña. Tiene dos movimientos:

  1. Login. El cliente envía las credenciales a un endpoint de token (POST /auth/token) como formulario y recibe un access_token.
  2. Uso. En cada petición posterior el cliente añade la cabecera Authorization: Bearer <token>. El servidor valida el token y no vuelve a mirar la contraseña.

¿Por qué el login va en un formulario (application/x-www-form-urlencoded) y no en JSON? Porque el estándar OAuth2 lo especifica así, y FastAPI lo respeta para que el botón Authorize de /docs funcione. De ahí el formulario OAuth2PasswordRequestForm que veremos en el ejemplo.

  Cliente                        FastAPI                         BD
    │                              │                             │
    │  POST /auth/token            │                             │
    │  form: username + password   │                             │
    ├─────────────────────────────►│  buscar usuario por username│
    │                              ├────────────────────────────►│
    │                              │◄────────────────────────────┤
    │                              │  verify(password, hash)     │
    │                              │  create_access_token(sub)   │
    │  200 {access_token, bearer}  │                             │
    │◄─────────────────────────────┤                             │
    │                              │                             │
    │  GET /ask                    │                             │
    │  Authorization: Bearer eyJ...│                             │
    ├─────────────────────────────►│  decode JWT → sub, exp      │
    │  200 {answer}                │  (no consulta la tabla)     │
    │◄─────────────────────────────┤                             │

Analogía: las credenciales son tu DNI y el mostrador de recepción verifica que eres tú. El token es la pulsera del evento: la enseñas para entrar a cada sala y no vuelves a pasar por recepción. Si te la quitan o caduca a medianoche, te quedas fuera. Y como la pulsera lleva tu nombre escrito pero no va firmada por ti, quien la vea puede leer a quién pertenece: por eso el JWT no es un sitio para secretos.

Contraseñas: nunca en claro, siempre con hash lento

La base de datos guarda un hash, no la contraseña. Un hash criptográfico es una función de un solo sentido: de "s3creto" obtienes una cadena, pero de la cadena no vuelves. Para verificar, aplicas el hash a lo que teclea el usuario y comparas.

Pero un hash rápido (SHA-256) es un problema: un atacante con la base de datos robada prueba millones de contraseñas por segundo. Por eso se usan funciones deliberadamente lentas y con salt:

  • bcrypt: lento por diseño, con factor de coste y salt incluido en el propio resultado. Es el estándar clásico y el que usa este curso.
  • argon2: el ganador de la Password Hashing Competition; resistente también a ataques con GPU. Es la opción moderna (la librería pwdlib que usa la documentación actual de FastAPI lo recomienda).
app/security.py — hash de contraseñas
from passlib.context import CryptContext

# bcrypt es lento a proposito: el coste hace inviable el ataque por fuerza bruta
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")


def hash_password(plain_password: str) -> str:
    """Convierte una contrasena en un hash con salt. Irreversible."""
    return pwd_context.hash(plain_password)


def verify_password(plain_password: str, hashed_password: str) -> bool:
    """Compara una contrasena con su hash en tiempo constante."""
    return pwd_context.verify(plain_password, hashed_password)

Nunca escribas tu propio hash. Un hashlib.sha256(password + "mi_salt") casero parece seguro pero es rapidísimo y sin salt por usuario. Usa una librería probada: passlib con bcrypt (lo que usa la spec de este curso) o pwdlib con argon2 si prefieres lo más moderno. Ambas exponen hash() y verify().

El JWT: tres trozos y una firma

Un JWT (JSON Web Token) es una cadena de tres bloques separados por puntos, cada uno en base64url:

  eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI0MiIsImV4cCI6MTcyOD...} . SflKxwRJSMeKKF2QT4fwpMeJ
  └──── header ──────┘   └────────── payload ──────────┘   └────── signature ───────┘
      algoritmo (HS256)            claims (datos)            HMAC sobre las 2 partes
  • header: el algoritmo con el que se firmó (HS256 = HMAC-SHA256).
  • payload: los claims, pares clave-valor. Aquí van sub (el sujeto: quién es) y exp (cuándo expira). Es legible por cualquiera: solo está codificado, no cifrado.
  • signature: la firma, calculada con la clave secreta. Es lo que impide que alguien cambie el payload: si toca un solo carácter, la firma deja de cuadrar.

Claims habituales:

ClaimSignificadoEjemplo
subSubject: a quién representa el token (el username o el id como string)"42"
expExpiration: instante de caducidad (timestamp UTC). PyJWT lo rechaza solo si pasó1728000000
iatIssued At: cuándo se emitió1727998200
issIssuer: quién lo emitó (útil si consumes tokens de terceros)"copiloto-api"

El JWT no está cifrado. Cualquiera que intercepte el token puede leer el payload (basta un base64). Sirve para transportar datos verificables, no secretos. Y sin HTTPS, la firma no impide que alguien lo robe y lo reutilice: el token es la credencial.

3 · Ejemplo mínimo

El flujo completo con un usuario en memoria, sin base de datos. Primero las dependencias; fíjate en python-multipart, obligatorio para leer formularios:

terminal
uv add pyjwt "passlib[bcrypt]" python-multipart

Ahora el main.py mínimo. Cada pieza está comentada:

main.py
import os
from datetime import UTC, datetime, timedelta

import jwt
from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from jwt.exceptions import InvalidTokenError
from passlib.context import CryptContext

SECRET_KEY = os.environ["FAPI_SECRET_KEY"]          # nunca en el codigo
ALGORITHM = "HS256"
TOKEN_MINUTES = 30

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

# 1) El esquema declara DONDE se pide el token (tokenUrl) para /docs.
#    En cada peticion extrae la cabecera Authorization: Bearer .
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/token")

# Un unico usuario de prueba con la contrasena ya hasheada.
USERS = {
    "ana": {
        "username": "ana",
        "hashed_password": pwd_context.hash("copiloto"),
    }
}

app = FastAPI()


def authenticate(username: str, password: str) -> str | None:
    user = USERS.get(username)
    if user is None:
        return None
    if not pwd_context.verify(password, user["hashed_password"]):
        return None
    return user["username"]


def create_access_token(sub: str) -> str:
    payload = {
        "sub": sub,                                   # sujeto: quien es
        "exp": datetime.now(UTC) + timedelta(minutes=TOKEN_MINUTES),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)


@app.post("/auth/token")
def login(form: OAuth2PasswordRequestForm = Depends()) -> dict[str, str]:
    # OAuth2PasswordRequestForm trae .username y .password del formulario.
    username = authenticate(form.username, form.password)
    if username is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Usuario o contrasena incorrectos",
            headers={"WWW-Authenticate": "Bearer"},
        )
    return {"access_token": create_access_token(username), "token_type": "bearer"}


def get_current_username(token: str = Depends(oauth2_scheme)) -> str:
    # 2) Aqui se VALIDA el token en cada peticion protegida.
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    except InvalidTokenError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Credenciales invalidas",
            headers={"WWW-Authenticate": "Bearer"},
        )
    sub = payload.get("sub")
    if sub is None:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Token sin sub")
    return sub


@app.get("/me")
def read_me(username: str = Depends(get_current_username)) -> dict[str, str]:
    return {"username": username}

En Copiloto API las piezas viven separadas por capas, como en los módulos anteriores: la configuración en config.py, la criptografía en security.py, la dependencia de identidad en deps.py y el login en su router.

app/security.py
from datetime import UTC, datetime, timedelta
from typing import Any

import jwt
from passlib.context import CryptContext

from app.config import settings

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")


def hash_password(plain_password: str) -> str:
    return pwd_context.hash(plain_password)


def verify_password(plain_password: str, hashed_password: str) -> bool:
    return pwd_context.verify(plain_password, hashed_password)


def create_access_token(subject: str, extra: dict[str, Any] | None = None) -> str:
    """Emite un JWT firmado. 'extra' permite anadir claims (p. ej. roles)."""
    now = datetime.now(UTC)
    payload: dict[str, Any] = {
        "sub": subject,
        "iat": now,
        "exp": now + timedelta(minutes=settings.access_token_expire_minutes),
    }
    if extra:
        payload.update(extra)
    return jwt.encode(payload, settings.secret_key, algorithm=settings.jwt_algorithm)


def decode_access_token(token: str) -> dict[str, Any]:
    """Valida firma y caducidad. Lanza InvalidTokenError si algo falla."""
    return jwt.decode(token, settings.secret_key, algorithms=[settings.jwt_algorithm])
app/deps.py
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
from jwt.exceptions import InvalidTokenError
from sqlmodel import Session

from app.db import get_session
from app.models import User
from app.security import decode_access_token

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/token")


def get_current_user(
    token: str = Depends(oauth2_scheme),
    session: Session = Depends(get_session),
) -> User:
    """Dependencia reutilizable: traduce un token valido en un User de la BD."""
    credentials_error = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Credenciales invalidas",
        headers={"WWW-Authenticate": "Bearer"},
    )
    try:
        payload = decode_access_token(token)
    except InvalidTokenError:
        raise credentials_error

    sub = payload.get("sub")
    if sub is None:
        raise credentials_error

    user = session.get(User, int(sub))
    if user is None or user.disabled:
        raise credentials_error
    return user
app/routers/auth.py
from fastapi import APIRouter, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordRequestForm
from sqlmodel import Session, select

from app.db import get_session
from app.models import User
from app.schemas import Token
from app.security import create_access_token, verify_password

router = APIRouter(prefix="/auth", tags=["auth"])


# hash de descarte: si el usuario no existe, igual pagamos el coste de bcrypt
# para no revelar por el tiempo de respuesta que usuario existe y cual no.
DUMMY_HASH = "$2b$12$C6UzMDM.H6dfI/f/IKcEe.4Gj9XqR9sC0aB3lF7Hn5K2mQ8wP1uSe"


@router.post("/token", response_model=Token)
def login(
    form: OAuth2PasswordRequestForm = Depends(),
    session: Session = Depends(get_session),
) -> Token:
    user = session.exec(select(User).where(User.username == form.username)).first()
    if user is None:
        verify_password(form.password, DUMMY_HASH)   # mismo tiempo, sin revelar nada
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Usuario o contrasena incorrectos",
            headers={"WWW-Authenticate": "Bearer"},
        )
    if not verify_password(form.password, user.hashed_password):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Usuario o contrasena incorrectos",
            headers={"WWW-Authenticate": "Bearer"},
        )
    token = create_access_token(subject=str(user.id))   # sub como string
    return Token(access_token=token, token_type="bearer")
app/routers/ask.py
from fastapi import APIRouter, Depends

from app.deps import get_current_user
from app.models import User
from app.schemas import AskRequest, AskResponse

router = APIRouter(tags=["ask"])


@router.post("/ask", response_model=AskResponse)
def ask(
    payload: AskRequest,
    current_user: User = Depends(get_current_user),   # <- endpoint protegido
) -> AskResponse:
    # Solo llegamos aqui con un token valido. El usuario esta identificado.
    return AskResponse(answer=f"Hola {current_user.username}: {payload.question}")

Decisiones y porqués:

  • La clave secreta viene de Settings (Módulo 3), no de una constante en el código. Sin ella la app no arranca, y el .env nunca se sube al repositorio.
  • sub es el id como string. El estándar JWT define sub como una cadena; usar el id entero puede romper validadores. El token lleva el identificador mínimo, y get_current_user recupera el usuario real de la base de datos: si mañana lo deshabilitas, el token deja de valer aunque no haya caducado.
  • Un único sitio donde se valida el token (get_current_user). Cualquier endpoint protegido depende de él. No se repite el jwt.decode por ahí.
  • El DUMMY_HASH en el login: si el usuario no existe, verificamos contra un hash de descarte para tardar lo mismo. Sin eso, la diferencia de milisegundos revela qué nombres de usuario existen (user enumeration).

El contrato cambia, y eso es bueno. Si abres /docs verás que POST /ask ahora muestra el candado y, arriba, el botón Authorize. OpenAPI declara la seguridad porque OAuth2PasswordBearer es un SecurityScheme: el contrato es la fuente de verdad y ahora refleja que estos endpoints requieren token.

5 · Buenas prácticas

HazEvitaPor qué
Sacar SECRET_KEY de una variable de entorno Dejarla escrita en el código Un secreto en el repo es un secreto comprometido: queda en el historial de Git
Caducidad corta (exp de 15-60 min) Tokens eternos Un token robado es válido para siempre si no caduca; no hay forma de «anularlo» sin estado

sub como cadena estable (str(user.id)) Meter el email u objetos enteros El subject debe ser un identificador; el email cambia y contamina el token

401 con cabecera WWW-Authenticate: Bearer Devolver 400 o 500 cuando falta el token Los clientes y el propio /docs saben qué hacer ante un 401 correcto
Mensaje de error idéntico para usuario y contraseña erróneos Decir «ese usuario no existe» Revelar qué usuarios existen facilita ataques dirigidos

6 · Errores habituales

El secreto en el código

✗ Incorrecto
SECRET_KEY = "super-secreto-123"    # va al repositorio y a la imagen Docker

def create_access_token(sub: str) -> str:
    return jwt.encode({"sub": sub}, SECRET_KEY, algorithm="HS256")
✓ Correcto
from app.config import settings   # secret_key viene de FAPI_SECRET_KEY

def create_access_token(sub: str) -> str:
    return jwt.encode({"sub": sub}, settings.secret_key, algorithm=settings.jwt_algorithm)

Si el secreto está en el repositorio, cualquiera puede firmar tokens válidos: la autenticación entera deja de valer. Rótalo con openssl rand -hex 32 y guárdalo en el gestor de secretos del entorno.

Token sin caducidad (o con demasiada)

✗ Incorrecto
# Sin 'exp': el token vale para siempre
token = jwt.encode({"sub": str(user.id)}, settings.secret_key, algorithm="HS256")

# O con un año de vida "para no molestar al usuario"
{"exp": datetime.now(UTC) + timedelta(days=365)}
✓ Correcto
now = datetime.now(UTC)
payload = {"sub": str(user.id), "iat": now, "exp": now + timedelta(minutes=30)}
token = jwt.encode(payload, settings.secret_key, algorithm="HS256")

PyJWT verifica exp automáticamente al decodificar y lanza ExpiredSignatureError (subclase de InvalidTokenError) si pasó. Para sesiones largas, el patrón es un refresh token aparte, no alargar el de acceso (ver el reto).

Decodificar sin fijar el algoritmo

✗ Incorrecto
# Peligro: si no se fija el algoritmo, un atacante puede presentar
# un token con "alg": "none" y saltarse la firma por completo.
payload = jwt.decode(token, options={"verify_signature": False})
username = payload["sub"]
✓ Correcto
try:
    payload = jwt.decode(token, settings.secret_key, algorithms=[settings.jwt_algorithm])
except InvalidTokenError:
    raise HTTPException(status_code=401, detail="Credenciales invalidas")

La librería no puede adivinar con qué algoritmo esperas los tokens; si no se lo dices, acepta cualquiera. Fijar algorithms=[...] es obligatorio, no opcional.

Datos sensibles en el payload

✗ Incorrecto
payload = {
    "sub": str(user.id),
    "password": form.password,       # legible por cualquiera que vea el token
    "credit_card": user.card_pan,    # jamas
}
✓ Correcto
payload = {"sub": str(user.id), "iat": now, "exp": ...}
# El JWT transporta una AFIRMACION verificable (quien es), no datos privados.

El payload es base64, no cifrado. Cualquiera que intercepte el token —o mire en el navegador— lee todo lo que metas. El JWT lleva identidad y claims de control, nunca secretos.

Contraseña en claro o hash rápido

✗ Incorrecto
import hashlib

user.password = hashlib.sha256(form.password.encode()).hexdigest()   # rapidisimo, sin salt
✓ Correcto
user.hashed_password = pwd_context.hash(form.password)   # bcrypt: lento + salt

SHA-256 calcula miles de millones de hashes por segundo; bcrypt, con su factor de coste, decenas. Esa diferencia es la que separa una base de datos filtrada de una catástrofe, o de un contratiempo.

7 · Ejercicio guiado

Objetivo: añadir autenticación con JWT a Copiloto API y proteger POST /ask, verificando el ciclo login → token → petición protegida.

  1. Paso 1 — Dependencias. Añade las librerías (el curso ya usa uv): 
    uv add pyjwt "passlib[bcrypt]" python-multipart
uv run python -c "import jwt, passlib; print('ok')"

    Resultado esperado: imprime ok. Si OAuth2PasswordRequestForm da error en runtime, es que falta python-multipart.

  2. Paso 2 — Configuración. Añade a app/config.py secret_key: str y access_token_expire_minutes: int = 30, y crea un .env con FAPI_SECRET_KEY= y el resultado de openssl rand -hex 32. Comprueba que .env está en .gitignore.
  3. Paso 3 — Módulo de seguridad. Crea app/security.py con hash_password, verify_password, create_access_token y decode_access_token (como en el ejemplo real). Incluye iat y exp.
  4. Paso 4 — Semilla de usuario. Crea un script scripts/seed_user.py que inserte un usuario ana con hash_password("copiloto") en la base de datos (Módulo 4). Nunca guardes la contraseña en claro en la tabla.
  5. Paso 5 — Router de login. Crea app/routers/auth.py con POST /auth/token usando OAuth2PasswordRequestForm, el DUMMY_HASH para usuarios inexistentes y response_model=Token. Registra el router en app/main.py.
  6. Paso 6 — Dependencia de identidad. En app/deps.py añade get_current_user(token=Depends(oauth2_scheme), session=Depends(get_session)) que decodifique, lea sub, busque el usuario y rechace si disabled.
  7. Paso 7 — Protege y prueba. Añade current_user: User = Depends(get_current_user) a POST /ask. Arranca y ejecuta: 
    TOKEN=$(curl -s -X POST http://127.0.0.1:8000/auth/token \
  -d "username=ana&password=copiloto" | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

curl -s -o /dev/null -w "sin token: %{http_code}\n" -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" -d '{"question":"hola"}'

curl -s -X POST http://127.0.0.1:8000/ask \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"question":"hola"}'

    Resultado esperado: 401 sin token y un AskResponse con el saludo y tu usuario cuando el token es válido. Comprueba en /docs que /ask muestra el candado y que el botón Authorize funciona con ana/copiloto.

  8. Paso 8 — Verifica la caducidad. Ponte access_token_expire_minutes=0 temporalmente y repite la última llamada. Resultado esperado: 401, porque exp ya pasó. Vuelve a dejarlo en 30.

8 · Reto

🎯 Refresh tokens con rotación

Un token de acceso de 30 minutos obliga al usuario a volver a loguearse cada media hora. Implanta el patrón refresh token: un segundo token de vida larga (por ejemplo 7 días) que el cliente canjea por un access token nuevo sin volver a teclear la contraseña, con rotación (cada uso del refresh emite uno nuevo e invalida el anterior).

Pistas: añade un claim type («access» o «refresh») y rechaza los refresh en get_current_user (¡un refresh token no debe servir para llamar a /ask!). Como los JWT son sin estado, «invalidar el anterior» exige guardar el identificador del refresh (jti) en la base de datos (Módulo 4) y marcarlo como usado; si un refresh ya usado vuelve a aparecer, es señal de robo: revoca toda la cadena. Piensa también: ¿qué gana quien roba el refresh frente a quien roba el access? ¿Por qué el access token debe seguir siendo corto aunque existan refresh tokens? Pista final: el flujo estándar para clientes públicos es OAuth2PasswordRequestForm con grant_type=refresh_token.

9 · Resumen

  • Autenticar es saber quién eres (401 si falla); autorizar, qué puedes hacer (403 si falla).
  • El password flow de OAuth2 tiene dos movimientos: POST /auth/token (formulario → token) y Authorization: Bearer <token> en cada petición.
  • OAuth2PasswordBearer(tokenUrl=...) extrae el token y hace que /docs muestre el botón Authorize.
  • Las contraseñas se guardan como hash lento con salt (bcrypt/argon2), nunca en claro ni con hashes rápidos.
  • El JWT es header.payload.signature: el payload es público; la firma es lo que impide alterarlo.
  • Los claims clave son sub (quién, como string) y exp (cuándo caduca); PyJWT valida exp solo.
  • Al decodificar hay que fijar el algoritmo (algorithms=[...]) para cerrar el ataque alg: none.
  • El secreto vive en el entorno (Settings), nunca en el repositorio.
  • Una sola dependencia (get_current_user) concentra la validación; los endpoints solo declaran que la necesitan.

10 · Preguntas frecuentes

¿Por qué el login usa un formulario y no un cuerpo JSON?

Porque el flujo password de OAuth2 lo especifica como application/x-www-form-urlencoded, y FastAPI lo respeta para que el botón Authorize de /docs funcione sin configuración. OAuth2PasswordRequestForm es un Depends que lee ese formulario. Nada te impide exponer además un POST /auth/login en JSON para tu frontend, pero el endpoint que tokenUrl apunta debe ser el de formulario.

¿Puedo «cerrar sesión» invalidando el token?

No directamente: un JWT sin estado es válido hasta que exp lo mata, y el servidor no lleva registro. Opciones reales: (1) caducidades cortas + refresh tokens con estado (ver el reto); (2) una denylist de tokens revocados en Redis, consultada en get_current_user; (3) subir un token_version en el usuario y compararlo con un claim, de modo que cambiar la contraseña invalide todos sus tokens. La (3) es la más limpia para «cerrar sesión en todas partes».

¿HS256 o RS256?

HS256 (HMAC) usa un único secreto compartido para firmar y verificar: simple y perfecto cuando el mismo backend es quien emite y valida. RS256 (RSA) firma con una clave privada y verifica con la pública: imprescindible cuando otros servicios deben validar tus tokens sin poder emitirlos. Para Copiloto API, HS256 basta; si mañana un microservicio valida tokens sin compartir el secreto, cambia a RS256 y reparte solo la clave pública.

¿Dónde guardo el token en el navegador?

Es un compromiso clásico. En localStorage es cómodo pero accesible a cualquier XSS; en una cookie HttpOnly no lo lee JavaScript, pero abre la puerta a CSRF (mitigable con SameSite y tokens anti-CSRF). Para una API consumida por un frontend propio, la opción razonable es access token en memoria, refresh token en cookie HttpOnly + Secure + SameSite=Strict. Lo que nunca se hace: guardarlo en la URL o loguearlo.

¿Por qué sub debe ser una cadena si mi id es un entero?

El estándar JWT (RFC 7519) define sub como una cadena (un «StringOrURI»). PyJWT lo acepta tal cual, pero otros validadores —y otras librerías de otros lenguajes— pueden rechazar un número. Guarda str(user.id) y vuelve a convertirlo con int(sub) al consultar la base de datos. Es un detalle pequeño que evita incompatibilidades al integrarte con terceros.
