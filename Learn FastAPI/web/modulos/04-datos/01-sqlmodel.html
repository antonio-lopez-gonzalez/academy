Modelos con SQLModel

Módulo 4 · Datos y persistencia 🕐 35 minutos

1 · Introducción

Hasta aquí, tu API vive en memoria: una lista de Python guarda los datos y, al reiniciar el proceso, todo se desvanece. Para una demo basta; para una API de verdad, no. Copiloto API tiene que recordar el histórico de consultas, los módulos indexados y, más adelante, quién preguntó qué. Eso es persistencia, y en este módulo la resolvemos con SQLModel (SQLAlchemy 2.0 + Pydantic v2) y Alembic.

El problema de fondo es que, sin SQLModel, trabajar con base de datos te obliga a mantener dos mundos de modelos: los modelos Pydantic que validan la entrada y salida de la API, y los modelos SQLAlchemy que describen las tablas. Son casi idénticos, y mantenerlos sincronizados es una fuente inagotable de bugs. SQLModel es la apuesta de la misma persona que creó FastAPI: un único modelo que es a la vez tabla y modelo Pydantic.

¿Por qué existe esta lección? Porque casi todo el módulo se construye sobre ella: las sesiones (lección 2) necesitan un motor y unos modelos; Alembic (lección 3) genera migraciones comparando tu esquema con las tablas reales; el patrón repositorio (lección 4) devuelve y persiste estos modelos. Si los modelos están mal, todo lo demás lo está.

Errores típicos que verás en código real y que aquí evitamos desde el principio: usar el modelo de tabla como cuerpo de la petición y como respuesta (filtra columnas internas), olvidar declarar la clave primaria, y llamar a SQLModel.metadata.create_all() en producción como si fuera un sistema de migraciones.

2 · Teoría

Un modelo, dos sombreros

SQLModel es una clase base que tiene todo lo que ya conoces de Pydantic v2 (tipos, validación, serialización, model_validate) y, además, cuando la subclases y añades table=True, también es una tabla de SQLAlchemy 2.0: genera el CREATE TABLE, el mapeo de columnas y la relación con la sesión.

   class Hero(SQLModel, table=True)
             │          │
             │          └── SQLAlchemy: nombre de tabla, columnas, PK, índices
             └───────────── Pydantic v2: validación, tipos, serialización

Analogía: piensa en SQLModel como un formulario de admisión de un hospital que, además de validar los campos (Pydantic), sabe exactamente en qué archivador y en qué cajón va guardado (SQLAlchemy). El mismo documento sirve para pedir los datos y para almacenarlos, sin transcribirlos a mano a un segundo papel.

Modelo de tabla vs. modelo de datos

table=True es la bisagra. Sin ella, la clase es un modelo de datos puramente Pydantic: ideal para el body de una petición o para una respuesta. Con ella, es un modelo de tabla. La convención de la documentación oficial es separar responsabilidades en tres o cuatro clases:

Clase¿Tiene table=True?Para qué
QueryLogCreateNoEntrada: lo que el cliente envía (question)
QueryLogSíTabla real en la base de datos
QueryLogPublicNoSalida: lo que la API devuelve al mundo

Así, un mismo cambio de esquema no se filtra automáticamente a la respuesta pública: tú decides qué campos salen.

Field: la letra pequeña de cada columna

Field es el mismo objeto que ya usaste en Pydantic para default, max_length o validadores, extendido con parámetros de base de datos:

ParámetroQué hace
primary_key=TrueMarca la columna como clave primaria (obligatoria en cada tabla)
index=TrueCrea un índice: acelera WHERE y ordenaciones sobre esa columna
unique=TrueRestricción de unicidad (p. ej. el slug de un módulo)
foreign_key="modules.id"Clave foránea a otra tabla (lo usamos en la lección de relaciones)
max_length=200Longitud máxima; Pydantic la valida y SQLAlchemy la traduce al DDL
default=NoneValor por defecto; en la PK autogenerada, siempre None

Ojo con los defaults mutables: tags: list[str] = [] es un clásico error de Python (el mismo objeto se comparte entre instancias). En SQLModel, igual que en Pydantic, usa Field(default_factory=list).

El motor (Engine): la puerta de la base de datos

create_engine("sqlite:///database.db") construye un motor. No es una conexión: es una fábrica que gestiona un pool de conexiones, entiende el dialecto (SQLite, PostgreSQL, MySQL…) y sabe traducir tus modelos a SQL. Se crea una sola vez por proceso.

   create_engine(...)  →  Engine  →  (pool)  →  conexión 1 ─┐
                                     ├──────→  conexión 2 ─┼─→  base de datos
                                     └──────→  conexión N ─┘

La sesión (Session): la unidad de trabajo

La Session es donde ocurre el trabajo real: añades objetos, consultas, confirmas cambios. Mantiene un identity map (cada fila es un solo objeto en memoria) y agrupa operaciones en transacciones. La regla de oro: una sesión por petición, no una global. En la lección 2 la convertimos en dependencia de FastAPI con yield.

   Petición HTTP  →  get_session()  →  Session  →  session.add / exec
                                            │
                                            ├── session.commit()   (guarda)
                                            └── session.close()    (libera)

Toda consulta se hace con select() y se ejecuta con session.exec(), el atajo de SQLModel sobre la API 2.0 de SQLAlchemy. Encadenas filtros con .where() y materializas con .first(), .all() o .one().

3 · Ejemplo mínimo

El programa más pequeño que demuestra las cuatro piezas: modelo, motor, creación de tablas y sesión. Cópialo en db_min.py y ejecútalo dentro de un proyecto uv (con uv add sqlmodel).

db_min.py
from sqlmodel import Field, Session, SQLModel, create_engine, select


# 1) Modelo de tabla: hereda de SQLModel y añade table=True.
class Hero(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    name: str = Field(index=True)
    secret_name: str
    age: int | None = None


# 2) Motor: una sola vez por proceso. SQLite guarda en un archivo local.
engine = create_engine("sqlite:///database.db")

# 3) Crea las tablas a partir de los metadatos de todos los modelos importados.
SQLModel.metadata.create_all(engine)

# 4) Sesión: unidad de trabajo. Escribe, confirma y vuelve a leer.
with Session(engine) as session:
    hero = Hero(name="Deadpond", secret_name="Dive Wilson")
    session.add(hero)          # marca el objeto para INSERT
    session.commit()           # ejecuta la transacción
    session.refresh(hero)      # recupera el id autogenerado

    statement = select(Hero).where(Hero.name == "Deadpond")
    found = session.exec(statement).first()
    print(found.id, found.name, found.secret_name)

Salida esperada (el id empieza en 1 y crece en cada ejecución):

1 Deadpond Dive Wilson

Línea por línea:

  1. class Hero(SQLModel, table=True): sin table=True sería solo Pydantic; con ella, SQLModel le asigna el nombre de tabla hero (minúsculas del nombre de clase) y crea el mapeo de columnas.
  2. id: int | None = Field(default=None, primary_key=True): el | None con default=None permite dejar que la base de datos asigne el identificador. Es el patrón estándar de SQLModel.
  3. create_engine("sqlite:///database.db"): crea el motor. Tres barras apuntan a un fichero relativo; sqlite:// a memoria se usa en tests.
  4. SQLModel.metadata.create_all(engine): emite un CREATE TABLE IF NOT EXISTS por cada modelo. Perfecto para aprender y para tests; en producción mal (lo justificamos en la lección 3).
  5. session.add / commit / refresh: añade, confirma la transacción y recarga el objeto para traer campos generados por la base de datos.
  6. session.exec(select(Hero).where(...)): construye la consulta con la API 2.0 y la ejecuta; .first() devuelve el primer resultado o None.

4 · Ejemplo real

Apliquémoslo a Copiloto API. Necesitamos dos tablas: los módulos que el asistente indexa y el histórico de consultas a POST /ask. Los modelos viven en su propio módulo, app/models.py, separados de los schemas de entrada/salida.

app/models.py
from datetime import datetime, timezone

from sqlmodel import Field, SQLModel


def utcnow() -> datetime:
    """Marca de tiempo con zona (UTC). Evita el naive datetime.utcnow()."""
    return datetime.now(timezone.utc)


class Module(SQLModel, table=True):
    """Un módulo de Learn IA, expuesto por GET /modules."""

    __tablename__ = "modules"  # nombre explícito y en plural

    id: int | None = Field(default=None, primary_key=True)
    slug: str = Field(index=True, unique=True, max_length=64)
    title: str = Field(max_length=200)
    summary: str | None = None


class QueryLog(SQLModel, table=True):
    """Fila del histórico de consultas a POST /ask."""

    __tablename__ = "query_log"

    id: int | None = Field(default=None, primary_key=True)
    question: str = Field(max_length=2000)
    answer: str | None = None
    module_slug: str | None = Field(default=None, index=True, max_length=64)
    created_at: datetime = Field(default_factory=utcnow, index=True)

Decisiones y porqués:

  • __tablename__ explícito: aunque SQLModel lo deduce del nombre de clase, escribirlo evita sorpresas cuando renombres la clase y, sobre todo, deja claro el contrato con Alembic: la tabla se llama query_log.
  • slug único e indexado: es la clave natural del módulo (lo que pedirás por URL) y la unicidad es una regla de negocio, no un detalle de rendimiento.
  • module_slug indexado, no FK todavía: la relación formal con clave foránea llega en la lección de relaciones; aquí priorizamos que el índice exista para poder filtrar el histórico por módulo.
  • created_at con default_factory=utcnow y timezone.utc: guardamos siempre en UTC. Así el servidor no depende de la zona horaria de la máquina y la API puede formatear según el cliente.
  • answer: str | None: una consulta puede registrarse antes de que el RAG responda (aún None); el tipo lo dice explícitamente.

Ese utcnow() con default_factory es una función normal de Python: se llama por cada fila insertada. Es la diferencia con default=utcnow(), que calcularía la fecha una sola vez al importar el módulo. Este detalle es un bug clásico y silencioso.

app/db.py
from collections.abc import Iterator

from sqlmodel import Session, SQLModel, create_engine

from app.config import settings

# check_same_thread solo aplica a SQLite; el resto de motores no lo necesita.
connect_args = {"check_same_thread": False} if settings.database_url.startswith("sqlite") else {}

engine = create_engine(settings.database_url, echo=settings.sql_echo, connect_args=connect_args)


def init_db() -> None:
    """Crea las tablas. SOLO para desarrollo y tests; en producción, Alembic."""
    SQLModel.metadata.create_all(engine)

Fíjate en que la URL de la base de datos viene de settings (Módulo 3, lección 4), nunca escrita a mano ni en el repositorio. La misma base de código apunta a SQLite en local y a PostgreSQL en producción cambiando una variable de entorno.

5 · Buenas prácticas

HazEvitaPor qué
Separar modelos de tabla de los schemas de entrada/salida Usar el mismo modelo para body, tabla y respuesta Evita filtrar columnas internas (hashes, flags) y acopla menos tu API al esquema
Declarar siempre una primary_key Omitir la PK «porque no la necesito» SQLAlchemy no puede mapear una tabla sin clave primaria: error en el arranque
Crear el motor una sola vez y reutilizarlo Llamar a create_engine en cada función/endpoint El motor mantiene el pool de conexiones; recrearlo lo destruye y agota recursos
Guardar fechas en UTC con zona datetime.utcnow() (naive) o la hora local Un servidor en otra zona cambia silenciosamente tus datos
Indexar columnas por las que filtras (slug, created_at) Indexar todo «por si acaso» Un índice acelera las lecturas pero ralentiza las escrituras y ocupa espacio
Usar create_all solo en desarrollo y tests Usar create_all como sistema de migraciones No altera tablas existentes ni versiona el esquema; en producción se usa Alembic (lección 3)
Nombres de tabla explícitos y estables Renombrar la clase y esperar que la tabla siga igual La tabla es un contrato persistente; las migraciones dependen de su nombre

6 · Errores habituales

Usar el modelo de tabla como respuesta directa

✗ Incorrecto
class User(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    email: str
    password_hash: str        # columna interna

@app.get("/users", response_model=list[User])
def list_users(session: Session = Depends(get_session)):
    return session.exec(select(User)).all()   # ¡expone password_hash!
✓ Correcto
class UserPublic(SQLModel):        # sin table=True: solo Pydantic
    id: int
    email: str

@app.get("/users", response_model=list[UserPublic])
def list_users(session: Session = Depends(get_session)):
    return session.exec(select(User)).all()   # FastAPI filtra a UserPublic

El modelo de tabla puede tener columnas que jamás deben salir. Al modelar la salida aparte, el filtrado es automático y el contrato (OpenAPI) queda explícito. Es la misma idea de response_model que viste en el Módulo 2.

Olvidar la clave primaria

✗ Incorrecto
class QueryLog(SQLModel, table=True):
    question: str
    answer: str | None = None
# sqlalchemy.exc.ArgumentError: Mapper[QueryLog(query_log)] could not assemble
# any primary key columns from local mapped columns.
✓ Correcto
class QueryLog(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    question: str
    answer: str | None = None

El error no aparece al definir la clase, sino al mapearla (al crear el motor o al crear las tablas). Declarar la PK desde el primer momento evita depurar un ArgumentError que a priori no apunta a la causa.

Default mutable compartido y default evaluado una sola vez

✗ Incorrecto
class QueryLog(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    tags: list[str] = []                       # mismo list para todas las filas
    created_at: datetime = Field(default=utcnow())   # ¡fecha fijada al importar!
✓ Correcto
class QueryLog(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    tags: list[str] = Field(default_factory=list)
    created_at: datetime = Field(default_factory=utcnow)   # se llama por fila

default_factory=list crea una lista nueva por instancia. Y default_factory=utcnow (sin paréntesis) evalúa la fecha en el momento de insertar, no al importar el módulo.

Crear el motor dentro del endpoint

✗ Incorrecto
@app.get("/modules")
def list_modules():
    engine = create_engine("sqlite:///database.db")   # nuevo pool en cada request
    with Session(engine) as session:
        return session.exec(select(Module)).all()
✓ Correcto
# app/db.py — el motor se crea UNA vez, al importar el módulo
engine = create_engine(settings.database_url)

@app.get("/modules")
def list_modules(session: Session = Depends(get_session)):
    return session.exec(select(Module)).all()

Cada create_engine construye un pool nuevo; crear uno por petición multiplica las conexiones y arruina el rendimiento. El motor se crea al arrancar y la sesión se inyecta por dependencia.

7 · Ejercicio guiado

Objetivo: definir los modelos del histórico de Copiloto API, crear las tablas y comprobar con un script que insertar y leer funciona.

  1. Paso 1 — Prepara el proyecto. En una carpeta nueva: 
    uv init copiloto-db --python 3.12
cd copiloto-db
uv add sqlmodel

    Resultado esperado: se crea el proyecto y sqlmodel aparece como dependencia (arrastra SQLAlchemy 2.x y Pydantic v2).

  2. Paso 2 — Escribe los modelos. Crea app/models.py con el Module y el QueryLog de la sección 4. Recuerda: slug único e indexado, created_at con default_factory=utcnow.
  3. Paso 3 — Motor y creación de tablas. Crea app/db.py con engine = create_engine("sqlite:///copiloto.db") y una función init_db() que llame a SQLModel.metadata.create_all(engine).

    create_all solo ve los modelos que se han importado. Si init_db() vive en db.py pero no importa app/models.py, creará cero tablas sin avisar. Asegúrate de importar los modelos antes de llamarla.

  4. Paso 4 — Script de comprobación. Crea seed.py: 
    from sqlmodel import Session, select

from app.db import engine, init_db
from app.models import Module, QueryLog

init_db()

with Session(engine) as session:
    session.add(Module(slug="fastapi", title="FastAPI", summary="APIs modernas"))
    session.add(QueryLog(question="¿Qué es una dependencia?"))
    session.commit()

    modules = session.exec(select(Module)).all()
    logs = session.exec(select(QueryLog)).all()
    print([m.slug for m in modules])
    print([(q.id, q.created_at.tzinfo) for q in logs])

    Ejecútalo con uv run seed.py. Salida esperada (el tzinfo no es None, prueba de que guardas en UTC):

    ['fastapi']
[(1, datetime.timezone.utc)]
  5. Paso 5 — Verifica con SQL. Abre el motor desde Python y consulta el esquema para confirmar que los índices existen: 
    from sqlalchemy import text

from app.db import engine

with engine.connect() as conn:
    for row in conn.execute(text("SELECT name, sql FROM sqlite_master WHERE type='index'")):
        print(row.name)

    Resultado esperado: aparecen índices como ix_modules_slug y ix_query_log_created_at. Si no los ves, revisa que pusiste index=True.

  6. Paso 6 — Prueba el error. Comenta a propósito primary_key=True en QueryLog.id y vuelve a ejecutar uv run seed.py. Verás un ArgumentError sobre la clave primaria: ese es el error del que ya sabes salir.

9 · Resumen

  • SQLModel unifica Pydantic v2 y SQLAlchemy 2.0: la misma clase valida y se guarda.
  • table=True convierte un modelo de datos en un modelo de tabla; sin ella, es un schema normal.
  • Field amplía Pydantic con primary_key, index, unique, foreign_key, max_length…
  • El motor (create_engine) gestiona el pool y se crea una sola vez; la sesión es la unidad de trabajo por petición.
  • Separa modelos de tabla y schemas de entrada/salida para no filtrar columnas y mantener el contrato claro.
  • create_all es para desarrollo y tests; el esquema en producción se versiona con Alembic (lección 3).

10 · Preguntas frecuentes

¿SQLModel reemplaza a SQLAlchemy?

No: lo envuelve. SQLModel es una capa fina sobre SQLAlchemy 2.0 y Pydantic v2. Todo lo que SQLAlchemy sabe hacer (dialectos, transacciones, relaciones, eventos) sigue disponible. Cuando necesites algo avanzado, puede que uses sa_column=Column(...) o directamente API de SQLAlchemy.

¿Por qué el id es int | None en lugar de int?

Porque antes de insertar, el objeto no tiene identificador: lo asigna la base de datos. Con | None y default=None reflejas esa realidad y permites construir el objeto sin id. Tras commit() y refresh(), el campo se rellena.

¿create_all no basta para empezar?

Para aprender, sí. create_all solo crea tablas que no existen: no añade una columna nueva, no cambia un tipo, no deja historial de lo aplicado en cada entorno. En cuanto el esquema evoluciona (y siempre evoluciona), necesitas migraciones versionadas. La lección 3 explica Alembic en detalle.

¿Cómo hago que funcione con PostgreSQL o MySQL?

Cambiando la URL del motor: postgresql+psycopg://user:pass@host/db. El código de los modelos no cambia. Dos matices: instala el driver correspondiente y, si usas SQLite, recuerda que no aplica check_same_thread a otros motores.

¿Por qué no guardar el datetime en hora local?

Porque el servidor puede estar en otra zona (o cambiar de zona en un despliegue) y comparar fechas se vuelve ambiguo. Guardar siempre en UTC y con tzinfo hace que los datos sean comparables y portables; el formato de presentación se decide en el cliente.
