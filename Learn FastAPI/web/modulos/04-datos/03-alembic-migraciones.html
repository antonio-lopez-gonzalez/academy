Migraciones con Alembic

Módulo 4 · Datos y persistencia 🕐 40 minutos

1 · Introducción

Tu esquema no va a quedarse quieto. Hoy query_log tiene cuatro columnas; mañana le añades retried_at, la semana que viene un índice sobre module_slug, el mes que viene un user_id. En tu portátil puedes borrar el fichero SQLite y volver a ejecutar create_all. En producción no puedes borrar la base de datos: tiene datos que importan. Necesitas una forma de transformar el esquema existente sin destruirlo, de forma reproducible y auditable.

Eso es una migración, y la herramienta estándar en el ecosistema SQLAlchemy —y, por tanto, en SQLModel— es Alembic. Con ella, cada cambio de esquema es un fichero de Python versionado en tu repositorio, con su upgrade (aplicar) y su downgrade (revertir).

¿Por qué existe esta lección? Porque SQLModel.metadata.create_all() es una trampa muy común: funciona siempre en local y falla justo cuando más duele, en el servidor con datos reales. En esta lección entenderás qué hace create_all que no encaja en producción, y cómo Alembic sustituye ese hueco con historial, orden y reversibilidad.

Errores típicos que aquí cazamos: generar una migración vacía porque los modelos no estaban importados, editar a mano una migración que ya se aplicó en producción, mezclar create_all con Alembic, y olvidar el batch mode de SQLite al alterar columnas.

2 · Teoría

Qué es una migración: una lista enlazada de cambios

Cada migración es un fichero con un identificador (revision) y un puntero a la anterior (down_revision). Forman una cadena desde la base (sin nada) hasta la cabeza (head), que es la última aplicada. La base de datos guarda en una tabla especial (alembic_version) en qué eslabón está.

   base            rev a1b2          rev c3d4          rev e5f6 (head)
   (nada)  ───►   "create            "add index        "add retried_at
                   query_log"         module_slug"       to query_log"
   down_rev=None   down_rev=a1b2     down_rev=c3d4     down_rev=e5f6

Cuando ejecutas alembic upgrade head, Alembic compara el alembic_version de tu base de datos con la cadena y aplica solo los eslabones que faltan, en orden. Si otra persona del equipo tiene el esquema dos revisiones por detrás, Alembic aplica esas dos y nada más.

Anatomía del proyecto Alembic

ElementoQué es
alembic.iniConfiguración: ruta de los scripts, formato de log, y la URL de la base de datos
migrations/env.pyEl corazón: conecta Alembic con tus modelos y decide cómo ejecutar las migraciones
migrations/versions/Un fichero .py por migración (los versionas en Git)
migrations/script.py.makoPlantilla con la que se generan los ficheros nuevos
tabla alembic_versionLa crea Alembic en tu base de datos para saber qué revisión está aplicada

autogenerate: Alembic compara dos mundos

revision --autogenerate compara dos esquemas y escribe la diferencia:

   SQLModel.metadata            ──┐
   (tus modelos Python)           ├──►  DIFF  ──►  fichero de migración
   la base de datos real        ──┘                (upgrade + downgrade)

Para que funcione, env.py debe (1) apuntar al metadata correcto y (2) haber importado todos los modelos: el metadata solo conoce las tablas cuyas clases se han cargado en memoria. Si importas SQLModel pero nunca app.models, el diff ve «cero tablas» y genera una migración vacía.

Autogenerate no es magia. Detecta tablas y columnas nuevas o eliminadas, cambios de tipo básicos e índices. No detecta todo (renombres, restricciones complejas, migraciones de datos). Trata el fichero generado como un borrador que siempre se revisa antes de aplicar.

El ciclo de trabajo

ComandoQué hace
uv run alembic init migrationsCrea la carpeta migrations/, alembic.ini y la plantilla
uv run alembic revision --autogenerate -m "create query_log"Genera un fichero con el diff entre modelos y base de datos
uv run alembic upgrade headAplica todas las migraciones pendientes hasta la última
uv run alembic downgrade -1Revierte la última migración aplicada
uv run alembic currentMuestra la revisión en la que está tu base de datos
uv run alembic historyLista la cadena de revisiones
uv run alembic stamp headMarca la base de datos como «al día» sin ejecutar SQL (útil al adoptar Alembic en una base existente)

Por qué create_all no vale en producción

Necesidad realcreate_allAlembic
Añadir una columna a una tabla con datos❌ No hace ALTER TABLE✅ op.add_column(...)
Saber qué cambios están aplicados en cada entorno❌ No lleva historial✅ tabla alembic_version
Revisar el SQL antes de tocarlo❌ Se ejecuta sin más✅ El fichero es revisable en un PR
Revertir un cambio problemático❌ Imposible sin borrar datos✅ downgrade
Aplicar en el orden correcto entre equipos❌ No hay orden✅ Cadena de revisiones
Migraciones de datos (rellenar, transformar)❌ No contempla datos✅ El fichero es Python: puedes ejecutar SQL

Resumen en una frase: create_all sirve para crear tablas que no existen; Alembic sirve para evolucionar un esquema que ya está en marcha. Dev y tests pueden usar create_all; producción, siempre Alembic.

3 · Ejemplo mínimo

Primera migración desde cero, con SQLModel.

  1. Paso 1 — Instala Alembic. 
    uv add alembic
uv run alembic init migrations

    Resultado esperado: aparece alembic.ini y la carpeta migrations/ con env.py, script.py.mako y versions/ (vacía).

  2. Paso 2 — Conecta env.py con tus modelos. Edita migrations/env.py para que use tu metadata y tu URL:
    migrations/env.py
    from logging.config import fileConfig

from alembic import context
from sqlalchemy import engine_from_config, pool
from sqlmodel import SQLModel

from app.config import settings
import app.models  # noqa: F401  ← IMPORTA los modelos para registrarlos

config = context.config

# La URL sale de settings (nunca hardcodeada en alembic.ini).
config.set_main_option("sqlalchemy.url", settings.database_url)

if config.config_file_name is not None:
    fileConfig(config.config_file_name)

# ★ Alembic compara contra este metadata.
target_metadata = SQLModel.metadata
  3. Paso 3 — Genera la primera migración. Con la base de datos vacía: 
    uv run alembic revision --autogenerate -m "create modules and query_log"

    Resultado esperado en la consola:

    INFO  [alembic.autogenerate.compare] Detected added table 'modules'
INFO  [alembic.autogenerate.compare] Detected added table 'query_log'
INFO  [alembic.runtime.migration] Generating migrations/versions/a1b2....py ... done
  4. Paso 4 — Revisa el fichero. Abre migrations/versions/a1b2....py. Verás upgrade() con op.create_table(...) y downgrade() con op.drop_table(...). Lee siempre lo generado antes de aplicarlo.
  5. Paso 5 — Aplica. 
    uv run alembic upgrade head
uv run alembic current

    Resultado esperado: Running upgrade -> a1b2, create modules and query_log y luego la revisión actual. En tu base de datos ya existen modules, query_log y alembic_version.

Cada migración generada tiene esta forma (simplificada):

migrations/versions/a1b2c3d4e5f6_create_modules_and_query_log.py
from alembic import op
import sqlalchemy as sa          # noqa: F401

revision = "a1b2c3d4e5f6"
down_revision = None             # primera migración: no hay anterior
branch_labels = None
depends_on = None


def upgrade() -> None:
    op.create_table(
        "query_log",
        sa.Column("id", sa.Integer(), primary_key=True, nullable=False),
        sa.Column("question", sa.String(length=2000), nullable=False),
        sa.Column("answer", sa.String(), nullable=True),
        sa.Column("module_slug", sa.String(length=64), nullable=True),
        sa.Column("created_at", sa.DateTime(), nullable=False),
    )
    op.create_index("ix_query_log_created_at", "query_log", ["created_at"])
    op.create_index("ix_query_log_module_slug", "query_log", ["module_slug"])


def downgrade() -> None:
    op.drop_index("ix_query_log_module_slug", table_name="query_log")
    op.drop_index("ix_query_log_created_at", table_name="query_log")
    op.drop_table("query_log")

Fíjate: upgrade crea, downgrade destruye en orden inverso. Esta simetría es lo que te permite revertir sin sustos.

4 · Ejemplo real

Copiloto API va a notificar el tiempo de respuesta. Añadimos latency_ms a query_log y un índice. En local, el flujo completo:

  1. Añade la columna al modelo.
    app/models.py
    class QueryLog(SQLModel, table=True):
    __tablename__ = "query_log"

    id: int | None = Field(default=None, primary_key=True)
    question: str = Field(max_length=2000)
    answer: str | None = None
    module_slug: str | None = Field(default=None, index=True, max_length=64)
    latency_ms: int | None = None            # ← nueva columna
    created_at: datetime = Field(default_factory=utcnow, index=True)
  2. Genera el diff. 
    uv run alembic revision --autogenerate -m "add latency_ms to query_log"

    Resultado esperado: Detected added column 'query_log.latency_ms'. Revisa el fichero generado.

  3. Revisa y ajusta. El autogenerate propone:
    migrations/versions/b2c3....py
    def upgrade() -> None:
    op.add_column("query_log", sa.Column("latency_ms", sa.Integer(), nullable=True))


def downgrade() -> None:
    op.drop_column("query_log", "latency_ms")

    Si la columna fuese NOT NULL, añadirla a una tabla con filas fallaría: tendrías que dar un server_default temporal, rellenar y luego quitarlo. Aquí es nullable=True, así que no hay problema.

  4. Aplica en cada entorno. 
    uv run alembic upgrade head

    Resultado esperado: Running upgrade a1b2c3d4e5f6 -> b2c3d4e5f6a1, add latency_ms to query_log. En producción, este mismo comando —apuntando a la base de producción— aplica exactamente el mismo cambio, porque el fichero de migración está versionado.

  5. Prepara el plan de reversión. Antes de desplegar, comprueba que downgrade -1 funciona en local sobre una copia: 
    uv run alembic downgrade -1
uv run alembic upgrade head

    Resultado esperado: baja y vuelve a subir sin errores. Un downgrade roto es un seguro que has pagado y no cubre nada.

SQLite y el batch mode. SQLite no soporta ALTER COLUMN como otros motores. Cuando Alembic necesite recrear una tabla (cambiar tipo o nullable), activa el modo por lotes en env.py para que copie datos a una tabla temporal y las restituya:

migrations/env.py — parte online
def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=target_metadata,
            render_as_batch=True,   # ★ necesario en SQLite para ALTER
            compare_type=True,      # detecta cambios de tipo
        )
        with context.begin_transaction():
            context.run_migrations()

6 · Errores habituales

Migración vacía porque los modelos no se importaron

✗ Incorrecto
# migrations/env.py
from sqlmodel import SQLModel
# ...pero NUNCA importamos app.models

target_metadata = SQLModel.metadata   # metadata vacío: conoce cero tablas
✓ Correcto
# migrations/env.py
from sqlmodel import SQLModel

import app.models  # noqa: F401  ← registra Module y QueryLog en el metadata

target_metadata = SQLModel.metadata

El síntoma es un fichero de migración sin op.create_table y la sensación de que «Alembic no ve mis modelos». Alembic solo ve lo que se ha importado.

Mezclar create_all con Alembic

✗ Incorrecto
@asynccontextmanager
async def lifespan(app: FastAPI):
    SQLModel.metadata.create_all(engine)   # crea las tablas...
    yield
# ...y además aplicas migraciones de Alembic → dos fuentes de verdad
✓ Correcto
@asynccontextmanager
async def lifespan(app: FastAPI):
    if settings.environment == "development":
        SQLModel.metadata.create_all(engine)   # SOLO dev/tests
    yield
# En producción, el esquema lo aplica `alembic upgrade head` en el despliegue

Si create_all crea una tabla antes de que Alembic la migre, el upgrade puede fallar por «la tabla ya existe» o quedar desincronizado. Elige una fuente de verdad.

Editar una migración ya aplicada

✗ Incorrecto
# b2c3d4e5f6a1.py — YA se aplicó en producción; alguien lo edita
def upgrade() -> None:
    op.add_column("query_log", sa.Column("latency_ms", sa.Integer(), nullable=False))  # cambiado
✓ Correcto
# Se crea una NUEVA migración para el cambio
# uv run alembic revision -m "make latency_ms not null"
def upgrade() -> None:
    op.alter_column("query_log", "latency_ms", nullable=False)

Los entornos que ya aplicaron la revisión antigua no vuelven a ejecutarla. Si la editas, tu base de datos y el repositorio cuentan historias distintas. Los cambios se hacen hacia delante, con una migración nueva.

SQLite sin batch mode

✗ Incorrecto
uv run alembic revision --autogenerate -m "make question unique"
uv run alembic upgrade head
# sqlalchemy.exc.OperationalError: (sqlite3.OperationalError)
# Cannot add a UNIQUE column / Constraint must have a name
✓ Correcto
# migrations/env.py — dentro de run_migrations_online()
context.configure(
    connection=connection,
    target_metadata=target_metadata,
    render_as_batch=True,   # recrea la tabla por ti
)

SQLite no puede alterar columnas in situ. El modo por lotes hace que Alembic cree una tabla nueva, copie los datos y renombre; en PostgreSQL no lo necesitas, pero no estorba.

7 · Ejercicio guiado

Objetivo: añadir un campo feedback (valoración del usuario, 1–5) al histórico, con índice, de principio a fin, incluyendo la reversión.

  1. Paso 1 — Modifica el modelo. En app/models.py, añade a QueryLog: 
    feedback: int | None = Field(default=None, index=True)

    Resultado esperado: uv run python -c "import app.models" sin errores.

  2. Paso 2 — Genera la migración. 
    uv run alembic revision --autogenerate -m "add feedback to query_log"

    Resultado esperado: Detected added column 'query_log.feedback' y Detected added index 'ix_query_log_feedback'.

  3. Paso 3 — Revisa el fichero. Comprueba que upgrade() tiene op.add_column(...) y op.create_index(...), y que downgrade() hace lo inverso (drop_index y drop_column). Si el downgrade está vacío, escríbelo tú: es parte de la migración.
  4. Paso 4 — Aplica. 
    uv run alembic upgrade head
uv run alembic current

    Resultado esperado: Running upgrade ... -> ..., add feedback to query_log y la revisión actual apuntando a la nueva.

  5. Paso 5 — Verifica en la base de datos. 
    from sqlalchemy import text

from app.db import engine

with engine.connect() as conn:
    cols = conn.execute(text("PRAGMA table_info(query_log)")).all()
    print([c[1] for c in cols])   # nombres de columna

    Resultado esperado: aparece feedback en la lista, junto a id, question, answer, module_slug, latency_ms y created_at.

  6. Paso 6 — Prueba la reversión. 
    uv run alembic downgrade -1
uv run alembic current        # debe retroceder a la revisión anterior
uv run alembic upgrade head   # y volver

    Resultado esperado: el downgrade elimina feedback y upgrade lo devuelve. Acabas de probar la red de seguridad antes de necesitarla en producción.

  7. Paso 7 — Documenta el cambio. Escribe en el README del proyecto el comando de despliegue (uv run alembic upgrade head) y añade la variable de entorno de la base de datos. Los pasos de esquema se documentan, no se improvisan.

8 · Reto

🎯 Clave foránea y migración de datos

Añade una tabla users (con id y email único) y una columna user_id en query_log como clave foránea a users.id. Después escribe una segunda migración (no edites la primera) que rellene el histórico existente con un usuario «anónimo» creado en la propia migración antes de aplicar la restricción NOT NULL.

Pistas: para crear una fila desde una migración usa op.execute(...) o op.bulk_insert(...) sobre una tabla definida con sa.table(...). El orden importa: crea la columna anulable, inserta/rellena datos, y solo entonces aplícala como NOT NULL. Piensa también qué debe hacer el downgrade: ¿es reversible eliminar una columna con datos rellenados? Justifícalo y decide si merece la pena o si marcas esa revisión como no reversible usando op.get_bind() y una comprobación.

9 · Resumen

  • Una migración es un cambio de esquema versionado, con upgrade y downgrade, que forma una cadena de revisiones.
  • Alembic guarda en alembic_version qué revisión está aplicada: por eso puede aplicar solo lo que falta, en orden.
  • env.py conecta Alembic con SQLModel.metadata y debe importar los modelos.
  • --autogenerate produce un borrador: siempre se revisa y se completa el downgrade.
  • create_all es para dev y tests; producción usa Alembic porque necesita ALTER, historial y reversión.
  • Nunca edites una migración ya aplicada: los cambios van hacia delante, con una revisión nueva.
  • En SQLite activa render_as_batch=True para alterar columnas.

10 · Preguntas frecuentes

¿Puedo seguir usando create_all en desarrollo?

Sí, y es cómodo: cero fricción para arrancar. Pero en cuanto el esquema empiece a cambiar, es mejor que dev también use Alembic, para que tu entorno local refleje el mismo proceso que producción. Un buen equilibrio: create_all solo si la base de datos local no existe, y alembic upgrade head el resto del tiempo.

¿Qué hago si la migración autogenerada sale vacía?

Casi siempre es que el metadata no ve los modelos. Comprueba que env.py importa app.models (y cualquier módulo donde definas tablas). Si el import está bien, revisa que target_metadata = SQLModel.metadata apunta al mismo metadata que usan tus clases.

¿Y si la migración falla a mitad en producción?

Depende del motor. En PostgreSQL, el DDL es transaccional: la migración fallida se revierte entera. En MySQL y SQLite, no siempre: puede quedar aplicada a medias. Por eso se prueba el upgrade y el downgrade en una copia antes de tocar producción, y se evitan migraciones largas en una sola transacción.

¿Alembic detecta si cambio el tipo de una columna?

Solo si activas compare_type=True en context.configure(). Aun así, algunos cambios (por ejemplo, cadenas con distinta longitud) pueden no detectarlos todos los motores. Cuando la detección no sea fiable, escribe la migración a mano: es lo más honesto y lo más seguro.

¿Cómo adopto Alembic en una base de datos que ya existe?

Genera la primera migración con --autogenerate contra la base existente, y luego usa alembic stamp head para marcar la base como «ya al día» sin ejecutar el SQL (porque las tablas ya están). A partir de ahí, los cambios nuevos sí se aplican con upgrade. Alternativamente, empieza desde cero y usa stamp en el primer despliegue.
