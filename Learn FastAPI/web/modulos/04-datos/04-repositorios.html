El patrón repositorio

Módulo 4 · Datos y persistencia 🕐 35 minutos

1 · Introducción

Hasta ahora, tus endpoints contienen SQL: abren la sesión, escriben select(...), filtran, ordenan y devuelven. Funciona. Pero cuando la misma consulta aparece en tres endpoints, cuando quieres cambiar cómo se guarda algo y tocas diez sitios, o cuando quieres testear un endpoint sin base de datos, ese acoplamiento se convierte en un lastre. La capa HTTP está haciendo de capa de datos, y eso es mezclar responsabilidades.

El patrón repositorio es la respuesta clásica: crear un objeto cuyo único trabajo es obtener y guardar entidades de dominio, y esconder detrás de él cómo se hace. Tus endpoints piden «dame los últimos logs» y no saben (ni les importa) si eso es un SELECT en SQLite, una llamada a PostgreSQL o un diccionario en memoria.

¿Por qué existe esta lección? Porque es la costura que une todo el módulo: los modelos (lección 1) se persisten a través de una sesión (lección 2) cuyo esquema evoluciona con Alembic (lección 3), y el repositorio es quien encapsula esas consultas. Además enlaza con la inyección de dependencias del Módulo 3: el repositorio es una dependencia más, y por eso se puede sustituir por un doble en los tests (Módulo 6).

Errores típicos que veremos: repositorios que hacen commit() (robando la transacción al caso de uso), repositorios que devuelven objetos ORM con relaciones perezosas (y disparan un N+1 fuera de la sesión), repositorios que lanzan peticiones HTTP o mandan correos, y abstracciones exageradas donde cada consulta tiene su método.

2 · Teoría

Separar capas: quién hace qué

Una API sana tiene capas con responsabilidades claras. El repositorio introduce una frontera entre la lógica de aplicación y el acceso a datos.

   ┌──────────┐   Pydantic   ┌────────────┐   entidades   ┌──────────────┐
   │  Router  │ ───────────► │  Servicio  │ ────────────► │ Repositorio  │
   │ (HTTP)   │ ◄─────────── │ (casos de  │ ◄──────────── │ (consultas)  │
   └──────────┘   models     │  uso)      │   modelos     └──────┬───────┘
        ▲                     └────────────┘                      │
        │                                                          ▼
   contrato OpenAPI                                        ┌──────────────┐
                                                           │ Session / DB │
                                                           └──────────────┘
  • Router: traduce HTTP a llamadas de Python. Valida la entrada, decide el código de estado, modela la salida. No sabe SQL.
  • Servicio (opcional pero recomendable): orquesta el caso de uso, es el dueño de la transacción y del commit (lección 2).
  • Repositorio: encapsula las consultas y la persistencia. Sabe SQL; no sabe nada de HTTP ni de reglas de negocio.

El repositorio es un puerto

La idea viene de la arquitectura hexagonal: defines un puerto (una interfaz, en Python un Protocol) que describe qué operaciones necesitas, y un adaptador que las implementa con una tecnología concreta. Tu código de aplicación depende del puerto, no del adaptador.

app/repositories/queries.py — el puerto
from typing import Protocol

from app.models import QueryLog


class QueryLogRepository(Protocol):
    """Puerto: lo que la aplicación necesita, sin tecnología detrás."""

    def add(self, log: QueryLog) -> None: ...
    def get(self, log_id: int) -> QueryLog | None: ...
    def list_recent(self, limit: int = 20) -> list[QueryLog]: ...

Fíjate en que la interfaz no menciona Session, ni SQL, ni SQLite. Solo habla de QueryLog. Ese es el contrato que el resto de la aplicación conoce.

Analogía: un restaurante no dice «tráeme el plato de la cocina del fondo, en la bandeja metálica, con el cocinero de turno». Dice «tráeme la sopa». El camarero (puerto) conoce el menú; la cocina (adaptador) decide cómo se prepara. Si mañana cambian los fogones, el camarero sigue pidiendo «la sopa» igual.

El adaptador: la implementación con SQLModel

app/repositories/queries.py — el adaptador
from sqlmodel import Session, select

from app.models import QueryLog


class SqlQueryLogRepository:
    """Adaptador: implementa el puerto sobre SQLModel + SQLAlchemy."""

    def __init__(self, session: Session) -> None:
        self._session = session          # la sesión es un detalle privado

    def add(self, log: QueryLog) -> None:
        self._session.add(log)           # NO confirma: eso es del caso de uso

    def get(self, log_id: int) -> QueryLog | None:
        return self._session.get(QueryLog, log_id)

    def list_recent(self, limit: int = 20) -> list[QueryLog]:
        statement = select(QueryLog).order_by(QueryLog.created_at.desc()).limit(limit)
        return list(self._session.exec(statement).all())

El session se pasa en el constructor y se guarda como self._session: nadie de fuera lo ve. El repositorio no confirma la transacción; solo prepara cambios (add) y lee. Quién confirma lo decide la capa superior, para que una operación que toca varias tablas siga siendo atómica (lección 2).

Inyectar el repositorio por dependencia

Como es un objeto normal de Python, se construye con la sesión y se ofrece a los endpoints con Depends, exactamente igual que en el Módulo 3:

app/deps.py
from fastapi import Depends
from sqlmodel import Session

from app.db import get_session
from app.repositories.queries import QueryLogRepository, SqlQueryLogRepository


def get_query_log_repository(
    session: Session = Depends(get_session),
) -> QueryLogRepository:
    return SqlQueryLogRepository(session)   # devuelve el puerto, no el adaptador

El endpoint depende del tipo del puerto (QueryLogRepository) y FastAPI le inyecta el adaptador concreto. Esa indirección de un solo nivel es lo que hace que en los tests puedas cambiar el adaptador por un fake sin tocar el endpoint.

La recompensa: testabilidad

Con dependency_overrides de FastAPI, sustituyes la implementación real por una en memoria. El test corre sin base de datos, sin ficheros y sin limpieza:

tests/test_logs.py
from fastapi.testclient import TestClient

from app.deps import get_query_log_repository
from app.main import app
from app.models import QueryLog


class FakeQueryLogRepository:
    def __init__(self) -> None:
        self._items: list[QueryLog] = []

    def add(self, log: QueryLog) -> None:
        self._items.append(log)

    def get(self, log_id: int) -> QueryLog | None:
        return next((item for item in self._items if item.id == log_id), None)

    def list_recent(self, limit: int = 20) -> list[QueryLog]:
        return list(self._items[-limit:])


def test_list_logs_sin_base_de_datos() -> None:
    fake = FakeQueryLogRepository()
    fake.add(QueryLog(id=1, question="¿Qué es Depends?"))
    app.dependency_overrides[get_query_log_repository] = lambda: fake

    client = TestClient(app)
    response = client.get("/logs")

    assert response.status_code == 200
    assert response.json()[0]["question"] == "¿Qué es Depends?"

    app.dependency_overrides.clear()

El fake no simula la base de datos: simula el puerto. Por eso es tan corto. En el Módulo 6 verás cuándo conviene un fake (rápido, sin infraestructura) y cuándo una base de datos temporal de verdad (para probar el SQL real).

3 · Ejemplo mínimo

Un repositorio, sin interfaces ni capas, para ver la idea desnuda. Solo encapsula dos consultas:

app/repositories/queries.py
from sqlmodel import Session, select

from app.models import QueryLog


class QueryLogRepository:
    def __init__(self, session: Session) -> None:
        self._session = session

    def add(self, log: QueryLog) -> None:
        self._session.add(log)

    def list_recent(self, limit: int = 20) -> list[QueryLog]:
        statement = (
            select(QueryLog)
            .order_by(QueryLog.created_at.desc())
            .limit(limit)
        )
        return list(self._session.exec(statement).all())

Y el endpoint, ya sin SQL a la vista:

app/routers/logs.py
from fastapi import APIRouter, Depends

from app.deps import get_query_log_repository
from app.repositories.queries import QueryLogRepository

router = APIRouter()


@router.get("/logs")
def list_logs(repo: QueryLogRepository = Depends(get_query_log_repository)) -> list[QueryLog]:
    return repo.list_recent()

Compara con la versión acoplada:

✗ El endpoint sabe SQL, sesión y orden
@router.get("/logs")
def list_logs(session: Session = Depends(get_session)):
    statement = select(QueryLog).order_by(QueryLog.created_at.desc()).limit(20)
    return session.exec(statement).all()
✓ El endpoint pide el resultado, no la consulta
@router.get("/logs")
def list_logs(repo: QueryLogRepository = Depends(get_query_log_repository)):
    return repo.list_recent()

Con una sola consulta, ambos parecen iguales. La diferencia aparece cuando esa consulta se reutiliza, cuando cambia el orden por defecto, o cuando quieres testear el endpoint sin base de datos.

4 · Ejemplo real

Copiloto API, con las tres capas bien separadas. El router orquesta, el servicio decide, el repositorio consulta.

app/repositories/queries.py
from typing import Protocol

from sqlmodel import Session, select

from app.models import QueryLog


class QueryLogRepository(Protocol):
    def add(self, log: QueryLog) -> None: ...
    def get(self, log_id: int) -> QueryLog | None: ...
    def list_recent(self, limit: int = 20) -> list[QueryLog]: ...
    def list_by_module(self, module_slug: str) -> list[QueryLog]: ...


class SqlQueryLogRepository:
    def __init__(self, session: Session) -> None:
        self._session = session

    def add(self, log: QueryLog) -> None:
        self._session.add(log)

    def get(self, log_id: int) -> QueryLog | None:
        return self._session.get(QueryLog, log_id)

    def list_recent(self, limit: int = 20) -> list[QueryLog]:
        statement = select(QueryLog).order_by(QueryLog.created_at.desc()).limit(limit)
        return list(self._session.exec(statement).all())

    def list_by_module(self, module_slug: str) -> list[QueryLog]:
        statement = (
            select(QueryLog)
            .where(QueryLog.module_slug == module_slug)
            .order_by(QueryLog.created_at.desc())
        )
        return list(self._session.exec(statement).all())
app/services/ask.py
from app.models import QueryLog
from app.repositories.queries import QueryLogRepository


def register_question(repo: QueryLogRepository, question: str, module_slug: str) -> QueryLog:
    """Caso de uso: registra la pregunta. NO confirma la transacción."""
    log = QueryLog(question=question, module_slug=module_slug)
    repo.add(log)
    return log
app/routers/logs.py
from fastapi import APIRouter, Depends
from sqlmodel import Session

from app.db import get_session
from app.deps import get_query_log_repository
from app.repositories.queries import QueryLogRepository
from app.schemas import QueryLogPublic
from app.services.ask import register_question

router = APIRouter()


@router.get("/logs", response_model=list[QueryLogPublic])
def list_logs(repo: QueryLogRepository = Depends(get_query_log_repository)):
    return repo.list_recent()


@router.get("/modules/{slug}/logs", response_model=list[QueryLogPublic])
def list_module_logs(
    slug: str,
    repo: QueryLogRepository = Depends(get_query_log_repository),
):
    return repo.list_by_module(slug)


@router.post("/logs", response_model=QueryLogPublic, status_code=201)
def create_log(
    question: str,
    module_slug: str,
    repo: QueryLogRepository = Depends(get_query_log_repository),
    session: Session = Depends(get_session),      # dueño de la transacción
):
    log = register_question(repo, question, module_slug)
    session.commit()                              # un solo commit, aquí
    session.refresh(log)
    return log

Decisiones y porqués:

  • Tres capas, tres responsabilidades: el repo sabe cómo consultar (SQL, orden, límite), el servicio sabe qué operaciones componen el caso de uso, y el router sabe de HTTP.
  • La transacción vive en el router/servicio, no en el repo: register_question solo hace add; el commit está en el borde. Así el caso de uso puede componer varias escrituras atómicas.
  • El repo devuelve modelos de dominio (los QueryLog de SQLModel), no diccionarios ni filas crudas. La conversión a schema público la hace response_model.
  • El endpoint depende del Protocol, no de SqlQueryLogRepository: el tipo que ve el router es el puerto, y eso documenta la intención y habilita el override en tests.

¿Merece la pena siempre? No. Para un CRUD de tres endpoints, el repositorio puede ser ceremonia. Merece la pena cuando las consultas se repiten, cuando hay reglas que quieres testear sin base de datos, o cuando prevés cambiar de tecnología. Como toda abstracción, se paga en capas y se cobra en flexibilidad.

5 · Buenas prácticas

HazEvitaPor qué
Un repositorio por agregado/entidad (QueryLogRepository) Un «GodRepository» con métodos de todo Mantiene cada clase pequeña y con una responsabilidad clara
Operar dentro de una sesión que no es tuya Que el repositorio haga commit() La transacción pertenece al caso de uso; el repo solo prepara y lee

Dejar que las excepciones de datos suban Capturarlas y devolver None «para no romper» Ocultar errores convierte bugs en datos corruptos silenciosos
Efectos de red/correo fuera del repositorio Enviar emails o llamar APIs dentro del repo El repo accede a datos; los efectos externos son otro puerto

6 · Errores habituales

El repositorio roba la transacción

✗ Incorrecto
class SqlQueryLogRepository:
    def __init__(self, session: Session) -> None:
        self._session = session

    def add(self, log: QueryLog) -> None:
        self._session.add(log)
        self._session.commit()      # ¡confirma dentro del repo!

# El caso de uso que quería dos escrituras atómicas ya no puede
✓ Correcto
class SqlQueryLogRepository:
    def __init__(self, session: Session) -> None:
        self._session = session

    def add(self, log: QueryLog) -> None:
        self._session.add(log)      # solo prepara

# El dueño de la transacción confirma cuando terminó su unidad de trabajo
session.commit()

Con commit dentro del repo, cada llamada es una transacción y ninguna operación multi-tabla es atómica. La lección 2 lo dejó claro: un solo dueño del commit.

Devolver ORM con relaciones perezosas

✗ Incorrecto
def get_module(self, slug: str) -> Module | None:
    return self._session.exec(select(Module).where(Module.slug == slug)).first()

# Fuera del repo, la sesión ya se cerró:
# module.logs  →  DetachedInstanceError (o un N+1 si sigue abierta)
✓ Correcto
from sqlalchemy.orm import selectinload

def get_module_with_logs(self, slug: str) -> Module | None:
    statement = (
        select(Module)
        .where(Module.slug == slug)
        .options(selectinload(Module.logs))    # se carga aquí, dentro de la sesión
    )
    return self._session.exec(statement).first()

Si el repositorio entrega un objeto con relaciones sin cargar, el que lo consume intentará tocarlas cuando la sesión ya no exista. Carga lo que vayas a usar antes de devolverlo.

El repositorio hace de todo

✗ Incorrecto
class QueryLogRepository:
    def create_and_notify(self, question: str) -> QueryLog:
        log = QueryLog(question=question)
        self._session.add(log)
        self._session.commit()
        send_email("admin@copiloto.dev", question)   # efecto externo
        requests.post("https://metrics/...")         # red (y además sync en async)
        return log
✓ Correcto
class QueryLogRepository:
    def add(self, log: QueryLog) -> None:
        self._session.add(log)        # solo datos

# La notificación es otro puerto/servicio, y se hace fuera de la transacción
repo.add(log)
session.commit()
notifier.send(log)                    # efecto externo, aparte

Un repositorio que manda correos o llama a APIs deja de ser testeable, mezcla responsabilidades y complica las transacciones (¿qué pasa si el email se envía y luego falla el commit?).

Abstracción excesiva

✗ Incorrecto
def query(self, **filters) -> list[QueryLog]:
    statement = select(QueryLog)
    for key, value in filters.items():
        statement = statement.where(getattr(QueryLog, key) == value)
    return list(self._session.exec(statement).all())
# El router acaba escribiendo: repo.query(module_slug="fastapi")  → es SQL con otro nombre
✓ Correcto
def list_by_module(self, module_slug: str) -> list[QueryLog]:
    statement = select(QueryLog).where(QueryLog.module_slug == module_slug)
    return list(self._session.exec(statement).all())
# El router dice QUÉ quiere, no CÓMO filtrarlo

Un método que acepta cualquier combinación de filtros es SQL disfrazado: no esconde nada, solo lo hace menos seguro de tipos. Los métodos del repositorio se nombran por intención, no por mecánica.

7 · Ejercicio guiado

Objetivo: construir un repositorio para Module, inyectarlo como dependencia y probar el endpoint con un fake, sin base de datos.

  1. Paso 1 — Define el puerto. Crea app/repositories/modules.py: 
    from typing import Protocol

from app.models import Module


class ModuleRepository(Protocol):
    def get_by_slug(self, slug: str) -> Module | None: ...
    def list_all(self) -> list[Module]: ...
    def add(self, module: Module) -> None: ...

    Resultado esperado: el Protocol importa sin dependencia de SQLAlchemy (la interfaz es pura aplicación).

  2. Paso 2 — Implementa el adaptador. En el mismo fichero, SqlModuleRepository con Session en el constructor. get_by_slug usa select(Module).where(Module.slug == slug); list_all ordena por Module.title.
  3. Paso 3 — Dependencia. En app/deps.py, añade get_module_repository(session: Session = Depends(get_session)) -> ModuleRepository que devuelva SqlModuleRepository(session).
  4. Paso 4 — Endpoint sin SQL. Reescribe GET /modules para que use repo.list_all() y no mencione Session ni select. Comprueba en /docs que el contrato no cambió (mismo response_model).
  5. Paso 5 — El fake y el test. Crea tests/test_modules.py: 
    from fastapi.testclient import TestClient

from app.deps import get_module_repository
from app.main import app
from app.models import Module


class FakeModuleRepository:
    def __init__(self, items: list[Module]) -> None:
        self._items = items

    def get_by_slug(self, slug: str) -> Module | None:
        return next((m for m in self._items if m.slug == slug), None)

    def list_all(self) -> list[Module]:
        return sorted(self._items, key=lambda m: m.title)

    def add(self, module: Module) -> None:
        self._items.append(module)


def test_modules_sin_db():
    fake = FakeModuleRepository([Module(id=1, slug="fastapi", title="FastAPI")])
    app.dependency_overrides[get_module_repository] = lambda: fake

    client = TestClient(app)
    response = client.get("/modules")

    assert response.status_code == 200
    assert [m["slug"] for m in response.json()] == ["fastapi"]
    app.dependency_overrides.clear()

    Ejecuta uv run pytest -q. Resultado esperado: 1 passed. El test no toca ninguna base de datos: sustituye el puerto por un doble.

  6. Paso 6 — Verifica la separación. Busca en app/routers/ las apariciones de select( o Session: 
    grep -rn "select(\|Session" app/routers/ || echo "Los routers no conocen la base de datos"

    Resultado esperado: ninguna aparición (o solo la dependencia de session cuando el endpoint es dueño del commit). Los routers han dejado de saber SQL.

8 · Reto

🎯 Un repositorio base genérico

Escribe una clase BaseRepository[T] genérica (usa TypeVar y Generic) que implemente add, get, list_all y delete para cualquier modelo de SQLModel con id entero. Después haz que SqlQueryLogRepository y SqlModuleRepository la hereden y solo añadan sus métodos específicos (list_recent, get_by_slug…).

Pistas: necesitas conocer la clase del modelo en tiempo de ejecución; pasa el tipo al constructor (model: type[T]) y guárdalo en self._model, o usa los genéricos de SQLAlchemy. Para el Protocol, defínete un puerto genérico equivalente. Y respóndete a esto: ¿el BaseRepository genérico hace el código más claro o solo más corto? Un repositorio genérico que expone list_all para todo puede tentarte a saltarte consultas con nombre de dominio: si eso pasa, has perdido la principal ventaja del patrón. Documenta tu decisión.

9 · Resumen

  • El repositorio encapsula el acceso a datos detrás de métodos con nombre de dominio, y esconde cómo se consulta.
  • Separación de capas: router (HTTP) → servicio (casos de uso y transacción) → repositorio (SQL) → sesión/DB.
  • El puerto se modela con Protocol; el adaptador (SqlXRepository) lo implementa con SQLModel.
  • Se inyecta por dependencia: el endpoint depende del puerto, FastAPI entrega el adaptador.
  • El repositorio no confirma la transacción: solo prepara cambios y lee; el commit vive en el caso de uso.
  • Los métodos se nombran por intención (list_recent), no por mecánica (query(**filters)).
  • La gran recompensa es la testabilidad: dependency_overrides cambia el adaptador por un fake y el test corre sin base de datos.

10 · Preguntas frecuentes

¿No es demasiada indirección para una API pequeña?

A veces sí. Si tu API son tres endpoints y no crece, el repositorio puede ser ceremonia. El patrón se paga cuando las consultas se reutilizan, cuando quieres testear la lógica sin base de datos o cuando prevés cambiar de tecnología. Adóptalo cuando el dolor de no tenerlo sea real, no por dogma.

¿Por qué Protocol y no una clase abstracta (ABC)?

Protocol permite tipado estructural: cualquier clase que tenga los métodos correctos satisface la interfaz, sin heredar de nada. Eso hace que el fake de los tests sea trivial (no necesita importar tu jerarquía). Con ABC tendrías que heredar explícitamente. Ambos son válidos; Protocol encaja mejor con dependencias intercambiables.

¿El repositorio debe conocer los schemas de Pydantic?

No. El repositorio trabaja con modelos de dominio (los de SQLModel). La traducción a schemas de entrada/salida es responsabilidad del router y de response_model. Mantener esa frontera evita que un cambio de contrato HTTP obligue a tocar la capa de datos.

¿Quién cierra la sesión del repositorio?

La dependencia get_session con yield (lección 2). El repositorio recibe una sesión ya abierta y la usa, pero no la cierra. Como el repositorio también se construye por dependencia, FastAPI compone la cadena: abre la sesión, construye el repo, ejecuta el endpoint y cierra todo al terminar.

¿Un repositorio puede abarcar varias entidades relacionadas?

Sí, si forman un agregado (se guardan y se consultan juntas). La regla práctica es un repositorio por agregado, no por tabla. Si dos entidades siempre se usan por separado, mejor dos repositorios; si una no tiene sentido sin la otra, van juntas.
