Sesiones y transacciones

Módulo 4 · Datos y persistencia 🕐 35 minutos

1 · Introducción

En la lección anterior creaste Session(engine) dentro de un bloque with de un script. En una API eso no sirve tal cual: cada petición HTTP debe tener su propia sesión, abierta al empezar y cerrada al terminar, pase lo que pase. Si esa sesión se filtra entre peticiones, empiezas a ver datos «fantasma», bloqueos y conexiones agotadas. Aquí la convertimos en una dependencia de FastAPI con yield.

La segunda mitad del problema es la atomicidad. Muchas operaciones no son una sola escritura: cuando Copiloto API responde a una pregunta, escribe la consulta en el histórico y actualiza un contador del módulo. Si lo primero se guarda y lo segundo falla, tu base de datos queda inconsistente. Las transacciones y el rollback existen para que esas dos escrituras sean una sola: o las dos, o ninguna.

¿Por qué existe esta lección? Porque el 90% de los bugs «raros» de una API con base de datos se reducen a dos cosas: la sesión se gestiona mal (global, filtrada o nunca cerrada) o falta una transacción (una parte del cambio se aplica y la otra no). Entender el ciclo de vida de la sesión es lo que separa una demo de un sistema que no corrompe datos.

Errores típicos que verás y corregimos: una sesión global compartida entre peticiones, hacer commit() dentro de cada función auxiliar (rompiendo la atomicidad), no hacer rollback ante una excepción, y disparar una consulta por cada elemento de un bucle sin darte cuenta (el famoso N+1).

2 · Teoría

Motor, sesión y conexión: tres cosas distintas

Confundirlas es la raíz de casi todo. El motor es único y vive todo el proceso; la conexión es un canal abierto a la base de datos que sale del pool; la sesión es una unidad de trabajo que usa una conexión cuando lo necesita y lleva la cuenta de lo que has ido cambiando.

   PROCESO (toda la vida)        PETICIÓN (una sesión)      TRANSACCIÓN
   ┌────────────────────┐        ┌───────────────────┐      ┌───────────────┐
   │ Engine             │        │ Session           │      │ BEGIN         │
   │  └─ pool           │──────► │  obj A (nuevo)    │────► │ INSERT A      │
   │      ├─ conexión 1 │        │  obj B (editado)  │      │ UPDATE B      │
   │      └─ conexión 2 │        │  SELECT ...       │      │ COMMIT / ROLL │
   └────────────────────┘        └───────────────────┘      └───────────────┘

La sesión abre una transacción en cuanto toca la base de datos y la cierra con commit() (confirma) o rollback() (descarta). Mientras tanto, todo queda «pendiente»: la base de datos aún no ve tus cambios.

La dependencia de sesión con yield

Aquí enlazas con el Módulo 3: Depends y las dependencias con yield. Este es el patrón canónico de SQLModel y FastAPI:

app/db.py
def get_session():
    with Session(engine) as session:
        yield session          # FastAPI inyecta esto en el endpoint
    # al salir del 'with', la sesión se cierra: pasa SIEMPRE, haya error o no

Lo bonito del yield es el orden de ejecución. Fíjate en el diagrama de tiempos:

   ANTES del yield          →    endpoint se ejecuta    →   DESPUÉS del yield
   Session(engine).__enter__      tu lógica con session     Session.__exit__
   (sesión abierta)               (add / commit / rollback) (sesión CERRADA)

FastAPI llama a la dependencia una vez por petición: abre la sesión, la entrega a tu endpoint y, cuando el endpoint termina (incluso si lanza una excepción), reanuda la dependencia para cerrarla. Ese «incluso si lanza excepción» es justo lo que necesitas para no dejar conexiones colgadas.

Analogía: la sesión es como el carrito de una compra. Metes productos (add), los cambias (update) y solo cuando pasas por caja (commit) se cobran. Si algo se tuerce antes de pagar, vacías el carrito (rollback) y todo vuelve a como estaba. Ese carrito es tuyo y de nadie más: no lo compartes con el cliente de al lado.

commit, flush y rollback

OperaciónQué haceCuándo
session.add(obj)Marca el objeto para la transacción (aún None id)Al crear/actualizar
session.flush()Envía el SQL (INSERT/UPDATE) sin confirmar; asigna el idCuando necesitas el id antes del commit
session.commit()Confirma la transacción: los cambios se vuelven permanentesAl final de una unidad de trabajo correcta
session.refresh(obj)Recarga el objeto desde la base de datos (trae valores generados)Tras el commit, para devolver el registro actualizado
session.rollback()Descarta todos los cambios pendientes de la transacciónTras un error, antes de continuar

Una transacción, un commit. Si haces commit() dentro de una función de servicio y otra vez en el endpoint, has partido una operación atómica en dos. Decide quién es el dueño de la transacción (normalmente el caso de uso o el endpoint) y que sea el único que confirme.

AsyncSession: la misma idea, en async

Si tu endpoint es async def y tu driver lo soporta, usas el motor async y la dependencia cambia de forma, pero no de concepto:

app/db.py
from collections.abc import AsyncIterator

from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

engine = create_async_engine(settings.database_url)          # p. ej. sqlite+aiosqlite:///...
async_session = async_sessionmaker(engine, expire_on_commit=False)

async def get_session() -> AsyncIterator[AsyncSession]:
    async with async_session() as session:
        yield session

La regla sigue siendo la misma: una sesión por petición. Y una advertencia: no compartas una AsyncSession entre tareas concurrentes; no está pensada para eso.

El problema N+1

Las relaciones en SQLAlchemy se cargan de forma perezosa (lazy) por defecto: la primera vez que accedes a module.logs, se lanza una consulta. Si dentro de un bucle recorres N módulos y tocas su relación, disparas 1 consulta para la lista + N consultas, una por elemento. De ahí el nombre: N+1.

✗ N+1: una consulta por módulo
modules = session.exec(select(Module)).all()   # 1 consulta
for module in modules:                          # N consultas (una por module)
    print(module.slug, len(module.logs))        # lazy load: SELECT ... WHERE module_id = ?
✓ Carga anticipada con selectinload
from sqlalchemy.orm import selectinload

statement = select(Module).options(selectinload(Module.logs))
modules = session.exec(statement).all()         # 2 consultas en total
for module in modules:
    print(module.slug, len(module.logs))        # ya están cargados, sin consultas extra

Regla práctica: si vas a recorrer una relación de muchos objetos, cárgala anticipadamente con selectinload (una consulta extra con IN) o joinedload (un JOIN). El N+1 no se ve en desarrollo con 5 filas; se ve en producción con 5000.

3 · Ejemplo mínimo

La sesión inyectada en un endpoint. El ejemplo completo vive en dos archivos.

app/db.py
from collections.abc import Iterator

from sqlmodel import Session, SQLModel, create_engine

engine = create_engine("sqlite:///copiloto.db")


def get_session() -> Iterator[Session]:
    with Session(engine) as session:
        yield session
app/main.py
from contextlib import asynccontextmanager
from collections.abc import AsyncIterator

from fastapi import Depends, FastAPI
from sqlmodel import Session, SQLModel, select

from app.db import engine, get_session
from app.models import Module


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    SQLModel.metadata.create_all(engine)   # solo dev/tests (Módulo 3, lección 3)
    yield


app = FastAPI(lifespan=lifespan)


@app.get("/modules")
def list_modules(session: Session = Depends(get_session)) -> list[Module]:
    return session.exec(select(Module)).all()

Salida esperada al pedir GET /modules (con datos precargados):

[{"id": 1, "slug": "fastapi", "title": "FastAPI", "summary": "APIs modernas"}]

Lo esencial: el endpoint no abre ni cierra nada. Recibe una Session lista para usar, declara su intención con Depends(get_session) y FastAPI se encarga del resto. Si el endpoint lanza una excepción, el with del yield cierra la sesión igualmente.

4 · Ejemplo real

En Copiloto API, POST /ask hace dos cosas que deben ir juntas: guarda la consulta en query_log y actualiza un contador en el módulo. O las dos, o ninguna.

app/routers/ask.py
from fastapi import APIRouter, Depends, HTTPException, status
from sqlmodel import Session, select

from app.db import get_session
from app.models import Module, QueryLog
from app.schemas import AskRequest, AskResponse, QueryLogPublic

router = APIRouter()


@router.post("/ask", response_model=AskResponse, status_code=status.HTTP_201_CREATED)
def ask(payload: AskRequest, session: Session = Depends(get_session)) -> AskResponse:
    module = session.exec(select(Module).where(Module.slug == payload.module_slug)).first()
    if module is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"Módulo '{payload.module_slug}' no encontrado",
        )

    log = QueryLog(question=payload.question, module_slug=module.slug)
    answer = generate_answer(payload.question, module)   # tu función de RAG

    try:
        # Una sola transacción para ambas escrituras.
        session.add(log)
        module.queries_count += 1
        session.add(module)
        log.answer = answer
        session.commit()
    except Exception:
        session.rollback()           # deja la transacción limpia y propaga el error
        raise

    session.refresh(log)
    return AskResponse(answer=answer, log=QueryLogPublic.model_validate(log))

Decisiones y porqués:

  • Una transacción, dos escrituras: el commit() está fuera del RAG y cubre tanto el INSERT del log como el UPDATE del contador. Si el contador falla, el log tampoco se guarda.
  • rollback() ante cualquier excepción: deja la sesión reutilizable y garantiza que nada a medias se confirme. Como el objeto log ya está «sucio» en la sesión, sin el rollback el estado quedaría inconsistente.
  • raise de nuevo: no te tragas el error; lo registras o lo dejas subir para que FastAPI lo convierta en respuesta (Módulo 2) sin perder el rollback.
  • QueryLogPublic.model_validate(log): la respuesta se modela aparte del modelo de tabla, como viste en la lección 1.

Si integras el RAG de forma async (llamadas a un modelo o a un servicio HTTP), haz el endpoint async def y usa AsyncSession. Pero recuerda: la transacción debe seguir siendo una sola, y no debes mantener la sesión abierta mientras esperas a un servicio externo lento si puedes evitarlo.

El contador queries_count vive en el modelo Module. Un UPDATE ... SET queries_count = queries_count + 1 es lo correcto en producción (evita condiciones de carrera); para la lectura del curso, module.queries_count += 1 sobre la sesión es suficiente y más claro.

6 · Errores habituales

La sesión global compartida

✗ Incorrecto
# app/db.py
session = Session(engine)          # ¡una sola sesión para toda la app!

# app/main.py
def list_modules() -> list[Module]:
    return session.exec(select(Module)).all()   # carrera entre peticiones
✓ Correcto
# app/db.py
def get_session() -> Iterator[Session]:
    with Session(engine) as session:
        yield session          # cada petición recibe la suya

# app/main.py
def list_modules(session: Session = Depends(get_session)) -> list[Module]:
    return session.exec(select(Module)).all()

La Session de SQLAlchemy no es segura para hilos: dos peticiones que la usen a la vez comparten su estado interno y pueden ver filas que no les corresponden o pisarse los cambios.

Commit dentro de la función auxiliar

✗ Incorrecto
def save_log(session: Session, log: QueryLog) -> None:
    session.add(log)
    session.commit()          # ¡confirma aquí!

def bump_counter(session: Session, module: Module) -> None:
    module.queries_count += 1
    session.add(module)
    session.commit()          # operación separada: si falla, el log ya se guardó

# En el endpoint: dos commits = dos transacciones = no atómico
save_log(session, log)
bump_counter(session, module)
✓ Correcto
def save_log(session: Session, log: QueryLog) -> None:
    session.add(log)          # solo 'add': no confirma

def bump_counter(session: Session, module: Module) -> None:
    module.queries_count += 1
    session.add(module)

# El endpoint es dueño de la transacción: un solo commit para todo
save_log(session, log)
bump_counter(session, module)
session.commit()

Las funciones auxiliares preparan el cambio; el caso de uso confirma. Así puedes componer varias operaciones en una sola transacción.

No hacer rollback tras un error

✗ Incorrecto
try:
    session.add(log)
    session.commit()
except Exception:
    raise            # la transacción queda abortada y la sesión, atascada
✓ Correcto
try:
    session.add(log)
    session.commit()
except Exception:
    session.rollback()   # limpia la transacción antes de re-lanzar
    raise

Tras un fallo, la transacción queda en estado abortado: cualquier operación posterior sobre esa misma sesión fallará hasta que hagas rollback().

El N+1 disfrazado

✗ Incorrecto
modules = session.exec(select(Module)).all()
response = [{"slug": m.slug, "logs": len(m.logs)} for m in modules]   # N+1
✓ Correcto
from sqlalchemy.orm import selectinload

statement = select(Module).options(selectinload(Module.logs))
modules = session.exec(statement).all()
response = [{"slug": m.slug, "logs": len(m.logs)} for m in modules]   # 2 consultas

Una comprensible línea de Python se convierte en cientos de SELECT. Con echo=True lo ves al instante: cientos de consultas idénticas cambiando solo el parámetro.

7 · Ejercicio guiado

Objetivo: montar la sesión como dependencia, ejecutar una operación transaccional y comprobar con un test que el rollback funciona.

  1. Paso 1 — Dependencia de sesión. En tu proyecto de la lección 1, añade a app/db.py: 
    from collections.abc import Iterator
from sqlmodel import Session

def get_session() -> Iterator[Session]:
    with Session(engine) as session:
        yield session

    Resultado esperado: importa sin errores y el test de arranque no crea sesiones de más.

  2. Paso 2 — Un endpoint que solo lee. Crea GET /logs que devuelva el histórico ordenado por created_at descendente, usando Depends(get_session) y column(QueryLog.created_at).desc(). Comprueba con /docs que responde.
  3. Paso 3 — Fuerza una transacción y provoca un fallo. Crea un endpoint temporal POST /logs/_boom que añada un QueryLog y luego lance una excepción antes de confirmar: 
    @app.post("/logs/_boom")
def boom(session: Session = Depends(get_session)) -> dict:
    log = QueryLog(question="no debería guardarse")
    session.add(log)
    raise RuntimeError("fallo simulado antes del commit")

    No hagas commit: al salir el endpoint con excepción, el with del yield cierra la sesión y la transacción pendiente nunca se confirma. Llama al endpoint y luego a GET /logs.

  4. Paso 4 — Verifica con un test. Añade tests/test_tx.py: 
    from fastapi.testclient import TestClient

from app.main import app

client = TestClient(app)


def test_fallo_no_persiste():
    antes = len(client.get("/logs").json())
    client.post("/logs/_boom")                 # provoca la excepción
    despues = len(client.get("/logs").json())
    assert despues == antes                   # nada se guardó

    Ejecuta uv run pytest -q. Resultado esperado: 1 passed. Esto demuestra que, sin commit, el cambio no llega a la base de datos aunque el objeto se añadiera a la sesión.

  5. Paso 5 — Añade el rollback explícito. Modifica el endpoint para capturar la excepción, hacer session.rollback() y re-lanzarla. Vuelve a ejecutar el test: sigue pasando, y ahora la sesión queda limpia para el resto de la petición.
  6. Paso 6 — Caza un N+1. Si tienes la relación Module.logs, pon echo=True en el motor, recorre 5 módulos accediendo a .logs y cuenta las consultas. Después introduce selectinload y vuelve a contar: deberías pasar de 6 a 2.

8 · Reto

🎯 Endpoint de «reintento» transaccional

Implementa POST /ask/retry/{log_id}: si la consulta identificada por log_id tiene answer is None (quedó a medias), genera la respuesta, la guarda y —en la misma transacción— incrementa el contador del módulo y marca un campo retried_at. Si algo falla en cualquier punto, ninguno de los tres cambios debe persistir.

Pista: usa un único session.commit() al final y envuelve todo en try/except con rollback(). Piensa cómo comprobarías con un test que, al forzar el fallo, ni answer ni queries_count ni retried_at cambiaron. Añade el campo retried_at como columna nueva: ¿qué comando de Alembic necesitarás la próxima lección?

9 · Resumen

  • El motor vive todo el proceso; la sesión vive una petición. Nunca compartas la sesión.
  • La dependencia get_session con yield abre y cierra la sesión por ti, incluso si el endpoint falla.
  • La sesión agrupa cambios en una transacción: commit() la confirma, rollback() la descarta.
  • Un solo dueño de la transacción: un commit por unidad de trabajo, no uno por función.
  • Tras un error, rollback() siempre, antes de re-lanzar.
  • El problema N+1 se evita cargando relaciones con selectinload / joinedload.
  • Con drivers async, AsyncSession + async_sessionmaker: mismo concepto, async with.

10 · Preguntas frecuentes

¿Cuál es exactamente la diferencia entre flush y commit?

flush() envía el SQL a la base de datos dentro de la transacción, pero no la cierra: puedes seguir cambiando cosas y aún puedes hacer rollback(). commit() cierra la transacción y hace los cambios permanentes. Normalmente dejas que el commit haga el flush implícito; solo llamas a flush() si necesitas el id generado antes de confirmar.

¿Por qué no reutilizar una sesión para todo el proceso y ahorrar recursos?

Porque la sesión acumula estado (identity map, transacción en curso) y no es segura entre hilos. Reutilizarla mezcla objetos de distintas peticiones y puede confirmar cambios que no esperabas. Ahorras un objeto Python barato a cambio de bugs carísimos. Lo que sí se reutiliza es el motor y su pool de conexiones.

¿Dónde debe vivir el commit?

En el dueño de la unidad de trabajo: normalmente el endpoint (controlador) o la capa de servicio si la usas. Lo importante es que sea uno y que abarque todas las escrituras que deben ser atómicas. Las funciones de acceso a datos solo hacen add/select; no confirman.

¿Cómo sé si mi código tiene un N+1?

Activa echo=True en el motor (solo en desarrollo) y mira el log: si ves muchas consultas casi idénticas variando solo el WHERE id = ?, tienes un N+1. La solución suele ser selectinload para listas y joinedload para relaciones uno-a-uno. En el Módulo 6 medirás esto con tests.

¿Uso Session o AsyncSession?

Coincide con el estilo del endpoint y con el driver. Si tu ruta es async def y trabajas con aiosqlite, asyncpg o psycopg async, usa AsyncSession. Si el endpoint es síncrono, usa Session (FastAPI lo ejecuta en un hilo aparte). No mezcles: una AsyncSession no se puede usar desde código síncrono bloqueante.
