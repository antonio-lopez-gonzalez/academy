API endpoints con Astro

Módulo 5 · Datos y Endpoints 🕐 35 minutos

1 · Introducción

Traer datos de una API externa es la mitad del asunto. La otra mitad es exponer tus propios datos: un formulario que se envía, un buscador que filtra, un webhook que recibe pagos, un contador de visitas. Astro cubre esto con los endpoints: ficheros en src/pages/api/ que, en vez de devolver HTML, devuelven datos (normalmente JSON).

Un endpoint de Astro es la misma idea que una página: el sistema de ficheros define la URL. Pero en lugar de escribir marcado, escribes una función que devuelve un Response. La firma se llama APIRoute y maneja peticiones Request/Response estándar del navegador (¡las mismas que ya conoces del fetch!).

¿Por qué existe esta lección? Porque hasta ahora tus formularios simulaban el envío. Con endpoints, Astro cierra el círculo: la isla React recolecta los datos en el cliente y el endpoint los recibe, valida y responde. Es la pieza que convierte una web estática en una pequeña aplicación sin salir del modelo de Astro. Además, entender Request/Response aquí te servirá en cualquier framework y en Edge/Serverless.

2 · Teoría

La URL sale del sistema de ficheros

Igual que src/pages/blog.astro produce /blog, un fichero src/pages/api/posts.ts produce la ruta /api/posts. La diferencia es la extensión: .ts/.js (o cualquier .astro sin HTML) indica que es un endpoint, no una página.

src/pages/api/posts.ts        ->  /api/posts
src/pages/api/users/[id].ts   ->  /api/users/42
src/pages/rss.xml.ts          ->  /rss.xml

APIRoute: el contrato de un endpoint

Un endpoint exporta funciones nombradas según el método HTTP: GET, POST, PUT, DELETE, PATCH, OPTIONS… Cada una recibe un contexto (con request, params, cookies…) y devuelve un Response.

src/pages/api/ping.ts
// Importamos el tipo para tener autocompletado y comprobacion.
import type { APIRoute } from 'astro';

// GET se ejecuta cuando alguien hace una peticion GET a /api/ping.
export const GET: APIRoute = ({ request }) => {
  // Devolvemos un objeto Response: cuerpo + cabeceras + estado.
  return new Response(
    JSON.stringify({ ok: true, message: 'pong' }),
    {
      status: 200,                                   // codigo HTTP
      headers: { 'Content-Type': 'application/json' }, // tipo de contenido
    }
  );
};

Atajo útil: Response.json() crea una respuesta JSON en una sola llamada: return Response.json({ ok: true }). Es más corto y pone la cabecera Content-Type por ti. Los ejemplos del curso suelen usar la forma explícita para que veas todas las piezas, pero en producción usa Response.json.

import type { APIRoute } from 'astro';

// Los segmentos dinamicos (carpeta [id]) llegan en el objeto params.
export const GET: APIRoute = ({ params }) => {
  const { id } = params; // string | undefined
  if (!id) {
    return new Response('Falta el id', { status: 400 }); // 400 Bad Request
  }
  return Response.json({ id, name: `Usuario ${id}` });
};

POST: recibir datos y validarlos

El caso más importante: un formulario envía datos y esperamos una respuesta. El endpoint debe revalidar todo (recordabas en el Módulo 4 que la validación de cliente no es seguridad) y devolver códigos de estado correctos.

src/pages/api/contact.ts
import type { APIRoute } from 'astro';

// Recibir datos = leer el cuerpo. Aqui viene el POST del formulario.
export const POST: APIRoute = async ({ request }) => {
  // 1) Comprobamos que el cliente manda JSON (no cualquier cosa).
  const contentType = request.headers.get('content-type') ?? '';
  if (!contentType.includes('application/json')) {
    return Response.json({ error: 'Se esperaba JSON' }, { status: 415 });
  }

  // 2) Parseamos el cuerpo. request.json() puede lanzar si el JSON es invalido.
  let body: { name?: string; email?: string; message?: string };
  try {
    body = await request.json();
  } catch {
    return Response.json({ error: 'JSON invalido' }, { status: 400 });
  }

  // 3) Revalidamos SIEMPRE en el servidor. Mismas reglas que en el cliente.
  const errors: Record<string, string> = {};
  if (!body.name?.trim()) errors.name = 'El nombre es obligatorio';
  if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(body.email ?? ''))
    errors.email = 'Email invalido';
  if ((body.message ?? '').trim().length < 10)
    errors.message = 'Mensaje demasiado corto';

  // 4) Si hay errores, respondemos 422 (Unprocessable Entity) con el detalle.
  if (Object.keys(errors).length > 0) {
    return Response.json({ error: 'Validacion fallida', errors }, { status: 422 });
  }

  // 5) Aqui guardariamos/envariamos el mensaje (email, base de datos...).
  //    Simulamos el trabajo y respondemos 201 (Created).
  return Response.json({ ok: true, received: body.name }, { status: 201 });
};

Aviso crítico sobre modo estático: en un sitio puramente estático (output: 'static'), los endpoints GET se pre-renderizan a ficheros en el build (útiles para RSS, sitemaps, JSON fijos). Pero un POST necesita un servidor que lo ejecute en el momento: eso es SSR, que verás en la siguiente lección. Si pruebas un POST en estático y no funciona, ese es el motivo.

3 · Ejemplo mínimo

El endpoint más pequeño: responde «pong» a un GET /api/ping. Después lo consultamos desde el navegador y desde una isla.

src/pages/api/ping.ts
import type { APIRoute } from 'astro';

export const GET: APIRoute = async () => {
  // Response.json serializa y fija el Content-Type por nosotros.
  return Response.json({ pong: true, at: new Date().toISOString() });
};

Consúmelo desde la terminal:

Terminal
# Levanta el servidor de desarrollo.
pnpm dev
# En otra terminal, prueba el endpoint.
curl http://localhost:4321/api/ping
# -> {"pong":true,"at":"..."}

Y desde una isla, con fetch normal:

src/components/PingButton.tsx
import { useState } from 'react';

export default function PingButton() {
  const [result, setResult] = useState<string>('');

  async function ping() {
    // Llamada al endpoint propio. Ruta relativa: mismo origen, sin CORS.
    const res = await fetch('/api/ping');
    if (!res.ok) {
      setResult(`Error ${res.status}`);
      return;
    }
    const data = await res.json();
    setResult(`Respuesta: ${data.at}`);
  }

  return (
    <div>
      <button onClick={ping}>Ping</button>
      {result && <p>{result}</p>}
    </div>
  );
}

Lo esencial: la ruta del fetch es relativa (/api/ping). Al ser el mismo origen, no hay CORS ni URLs absolutas que gestionar. Es una de las comodidades de tener front y API en el mismo proyecto.

4 · Ejemplo real

Una mini API de tareas en memoria, con GET (listar) y POST (crear). Es el backend mínimo de cualquier aplicación, sin base de datos todavía.

src/data/tasks.ts
// Estado en memoria: se reinicia al reiniciar el servidor.
// En un proyecto real usarias una base de datos (Módulo 8).
export interface Task {
  id: number;
  title: string;
  done: boolean;
}

export const tasks: Task[] = [
  { id: 1, title: 'Aprender islands', done: true },
];
src/pages/api/tasks.ts
import type { APIRoute } from 'astro';
import { tasks, type Task } from '../../data/tasks';

// GET /api/tasks -> devuelve la lista completa.
export const GET: APIRoute = async () => {
  return Response.json(tasks);
};

// POST /api/tasks -> crea una nueva tarea a partir del body JSON.
export const POST: APIRoute = async ({ request }) => {
  let payload: { title?: string };
  try {
    payload = await request.json();
  } catch {
    return Response.json({ error: 'JSON invalido' }, { status: 400 });
  }

  if (!payload.title?.trim()) {
    return Response.json({ error: 'El titulo es obligatorio' }, { status: 422 });
  }

  // Generamos un id simple (en produccion lo haria la base de datos).
  const task: Task = {
    id: tasks.length + 1,
    title: payload.title.trim(),
    done: false,
  };
  tasks.push(task);

  // 201 Created + el recurso recien creado en el cuerpo.
  return Response.json(task, { status: 201 });
};
src/components/TaskList.tsx
import { useEffect, useState } from 'react';

interface Task { id: number; title: string; done: boolean; }

export default function TaskList() {
  const [tasks, setTasks] = useState<Task[]>([]);
  const [title, setTitle] = useState('');

  // Cargamos las tareas al montar la isla (GET).
  useEffect(() => {
    fetch('/api/tasks')
      .then((r) => r.json())
      .then(setTasks);
  }, []);

  async function addTask(e) {
    e.preventDefault();
    // POST con cabecera JSON y body serializado.
    const res = await fetch('/api/tasks', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ title }),
    });
    if (!res.ok) {
      const err = await res.json();
      alert(err.error ?? 'Error');
      return;
    }
    const created: Task = await res.json();
    setTasks((prev) => [...prev, created]); // reflejamos el nuevo recurso
    setTitle('');
  }

  return (
    <div>
      <ul>{tasks.map((t) => <li key={t.id}>{t.title}</li>)}</ul>
      <form onSubmit={addTask}>
        <input value={title} onChange={(e) => setTitle(e.target.value)} />
        <button>Añadir</button>
      </form>
    </div>
  );
}

Decisiones explicadas:

  • Un endpoint, dos métodos: GET y POST conviven en el mismo fichero, separando responsabilidades.
  • Datos aislados en src/data/: la lógica de datos no se mezcla con el transporte HTTP. Cuando pongas una base de datos, solo cambia ese módulo.
  • Validación en el servidor: el POST no confía en la isla; revalida el título y devuelve 422 si falta.
  • La isla refleja el recurso creado con la respuesta 201: no refresca toda la lista, añade el que el servidor confirmó. Es la pauta de una API REST sana.

Estado en memoria = se reinicia. Cada vez que reinicies el servidor, las tareas vuelven al estado inicial. Es perfecto para aprender, pero la persistencia real (ficheros, SQLite, Postgres) llega con los módulos de auth y despliegue. El contrato del endpoint no cambia: solo su implementación.

5 · Buenas prácticas

HazEvitaPor qué
Revalidar todos los datos en el endpoint Confiar en la validación del cliente El cliente es hostil: cualquiera puede enviar un POST a mano con curl
Devolver códigos de estado correctos (201, 400, 422…) Responder siempre 200 con { ok: false } El estado HTTP es el canal estándar: clientes, proxies y métricas dependen de él

6 · Errores habituales

Esperar un POST en un sitio puramente estático

✗ Incorrecto

# output: 'static' (por defecto): no hay proceso vivo en produccion,
# asi que un POST no puede ejecutarse: la ruta no existe o da error.
# astro.config.mjs -> sin adapter, sin output: 'server'

✓ Correcto

// En astro.config.mjs: activa SSR con un adapter.
import node from '@astrojs/node';
export default defineConfig({
  output: 'server',                 // ahora los endpoints corren en el servidor
  adapter: node({ mode: 'standalone' }),
});

El modo estático pre-renderiza GET a ficheros, pero no puede atender POST en el momento. Para eso necesitas SSR (lección 3).

No comprobar el cuerpo antes de parsearlo

✗ Incorrecto

// Si el cuerpo no es JSON, esto lanza un 500 sin explicacion.
export const POST: APIRoute = async ({ request }) => {
  const body = await request.json();
  return Response.json({ ok: true });
};

✓ Correcto

export const POST: APIRoute = async ({ request }) => {
  let body;
  try {
    body = await request.json();
  } catch {
    return Response.json({ error: 'JSON invalido' }, { status: 400 });
  }
  return Response.json({ ok: true });
};

Un cuerpo mal formado es responsabilidad del cliente: devuelve 400, no un 500 genérico.

Devolver 200 para todo

✗ Incorrecto

// Todo 200: el cliente no distingue exito de error sin leer el cuerpo.
return Response.json({ error: 'Faltan datos' });

✓ Correcto

// El estado HTTP comunica el resultado de un vistazo.
return Response.json({ error: 'Faltan datos' }, { status: 422 });

Con 200 y { ok: false } rompes la semántica HTTP: caches, monitores y librerías cliente se equivocan al interpretarlo.

Exponer objetos internos completos

✗ Incorrecto

// Devuelve el usuario entero, con hash de contrasena y email interno.
const user = await db.getUser(id);
return Response.json(user);

✓ Correcto

// Proyeccion explicita: solo lo que el cliente necesita.
const { id, name, avatar } = await db.getUser(id);
return Response.json({ id, name, avatar });

Nunca envíes el modelo de datos crudo. Proyecta los campos públicos para no filtrar información sensible.

7 · Ejercicio guiado

Objetivo: crear un endpoint de conversión que reciba un valor por query y devuelva JSON, y consumirlo desde una isla.

  1. Crea el endpoint src/pages/api/double.ts que lea un número por query string: 
    import type { APIRoute } from 'astro';

export const GET: APIRoute = ({ url }) => {
  // url es un objeto URL: los parametros de query se leen de ahi.
  const raw = url.searchParams.get('n');

  // Validamos: sin numero valido, respondemos 400.
  const n = Number(raw);
  if (raw === null || Number.isNaN(n)) {
    return Response.json({ error: 'Falta el parametro n numerico' }, { status: 400 });
  }

  // Devolvemos el calculo junto con la entrada para trazabilidad.
  return Response.json({ input: n, result: n * 2 });
};
  2. Pruébalo por terminal antes de tocar el cliente: 
    curl "http://localhost:4321/api/double?n=21"
# -> {"input":21,"result":42}
curl "http://localhost:4321/api/double"
# -> {"error":"Falta el parametro n numerico"}   (HTTP 400)
  3. Crea una isla que llame al endpoint con un input de usuario: 
    import { useState } from 'react';

export default function DoubleTool() {
  const [value, setValue] = useState('1');
  const [result, setResult] = useState<string>('');

  async function compute() {
    // Codificamos el parametro para que no rompa la URL.
    const res = await fetch(`/api/double?n=${encodeURIComponent(value)}`);
    const data = await res.json();
    setResult(res.ok ? `Resultado: ${data.result}` : data.error);
  }

  return (
    <div>
      <input value={value} onChange={(e) => setValue(e.target.value)} />
      <button onClick={compute}>Duplicar</button>
      <p>{result}</p>
    </div>
  );
}
  4. Móntala en una página con client:visible y pruébala en el navegador.
  5. Verifica con DevTools (Network → Fetch/XHR): al pulsar el botón debe aparecer una petición a /api/double?n=… con estado 200, y al enviar algo no numérico, un 400 con el mensaje de error. Comparar el estado HTTP con la lógica de tu isla es una habilidad clave.

8 · Reto

🎯 Una API REST de notas con CRUD

Amplía el ejemplo de tareas a una API REST completa de notas en src/pages/api/notes.ts y src/pages/api/notes/[id].ts, con las cuatro operaciones:

  • GET /api/notes: listar todas.
  • POST /api/notes: crear una nueva (valida el body, responde 201).
  • PUT /api/notes/[id]: actualizar una existente (responde 404 si no existe).
  • DELETE /api/notes/[id]: borrar (responde 204 sin cuerpo).

Requisitos: validación de servidor en cada método, códigos de estado correctos, y una isla de cliente que consuma los cuatro. Bonus: no uses alert() para errores: muéstralos en la interfaz según el estado HTTP recibido.

Pista: en [id].ts exporta GET, PUT y DELETE en el mismo fichero; el id llega en params.id y hay que convertirlo a número. Para DELETE sin cuerpo usa new Response(null, { status: 204 }). Recuerda: con output: 'static' los métodos que no sean GET no corren; activa el adapter de SSR de la siguiente lección para probarlos en producción.

9 · Resumen

  • Un endpoint es un fichero en src/pages/api/ que devuelve datos en vez de HTML; la URL sale del sistema de ficheros.
  • Cada método HTTP es una exportación nombrada (GET, POST…) tipada con APIRoute.
  • Cobran y devuelven Request/Response estándar; Response.json() simplifica el caso JSON.
  • Los datos llegan por query, params, body o cabeceras.
  • El servidor siempre revalida y responde con el código de estado correcto.
  • En modo estático, GET se pre-renderiza; POST requiere SSR (siguiente lección).

10 · Preguntas frecuentes

¿Cuál es la diferencia entre una página y un endpoint en Astro?

Ambos viven en src/pages/ y la ruta sale del sistema de ficheros. Una página devuelve HTML (con .astro o .md); un endpoint devuelve datos (con .ts/.js), normalmente JSON, pero también XML, texto o ficheros binarios. El contrato del endpoint es una función que retorna un Response.

¿Por qué mi POST devuelve 404 o 405 en producción estática?

Porque en output: 'static' Astro genera el sitio entero en build time: solo existen ficheros, no un proceso vivo. Los GET se convierten en ficheros estáticos, pero un POST no tiene quién lo ejecute. La solución es SSR con un adapter (output: 'server'), que verás en la siguiente lección. En pnpm dev sí funciona porque el servidor de desarrollo ejecuta todo en el momento.

¿Cómo protejo un endpoint para que solo lo use mi web?

Añadiendo autenticación: un token en la cabecera, una cookie de sesión o un middleware que compruebe el usuario. CORS controla a qué orígenes del navegador se permite llamar, pero no protege frente a peticiones de servidor. La autenticación real es el tema del Módulo 8. Por ahora, recuerda: un endpoint público es público de verdad.

¿Puedo devolver algo que no sea JSON?

Sí. Devuelves lo que quieras en el Response: HTML, CSV, XML (típico para RSS o sitemaps), imágenes o binarios. Solo tienes que fijar el Content-Type adecuado. Una página que devuelve XML es un endpoint con extensión .xml.ts. El mismo mecanismo sirve para todo.

¿De dónde saco datos si no hay base de datos todavía?

De donde quieras: un array en memoria (como en el ejemplo), un fichero JSON del repositorio, una carpeta de Markdown leída con Content Collections, o una API externa. La ventaja de separar la capa de datos es que la fuente no afecta al contrato del endpoint. Puedes empezar en memoria y cambiar a Postgres después sin tocar el cliente.
