Fetch de datos en build time

Módulo 5 · Datos y Endpoints 🕐 30 minutos

1 · Introducción

Una web casi nunca vive sola: consume datos. Hasta ahora usabas datos de ejemplo escritos a mano. En esta lección aprenderás a traer datos de verdad desde una API, una base de datos o un CMS, y a hacerlo en el mejor momento posible: durante el build.

Astro tiene una ventaja enorme aquí: el frontmatter de un archivo .astro es código de servidor que puede usar await directamente. Escribes const datos = await fetch(...) y listo: los datos se obtienen una vez, se renderizan a HTML y se sirven como fichero estático. Sin cargas en el cliente, sin parpadeos, sin estados de carga.

¿Por qué existe esta lección? Porque «renderizar en build time» es la característica que define a Astro y a los generadores de sitios. Cambia por completo la relación con los datos: ya no piensas «¿cómo muestro un spinner mientras llega?» sino «¿cuándo construyo esta página y con qué datos?». Entender este cambio de mentalidad es más importante que memorizar la sintaxis de fetch.

2 · Teoría

El frontmatter es código de servidor con await

Todo lo que está entre las rayas --- de un archivo .astro se ejecuta en el servidor, en tiempo de build. Puede importar módulos, acceder a variables de entorno privadas y, por supuesto, esperar promesas. El bloque de plantilla (HTML) recibe ese resultado como si fueran datos locales.

src/pages/posts.astro
---
// Este codigo corre UNA VEZ, cuando construyes el sitio (node build).
// El usuario NUNCA ve este fetch: recibe el HTML ya resuelto.
const response = await fetch('https://api.example.com/posts');
const posts = await response.json();
---

<html lang="es">
  <body>
    <ul>
      {posts.map((p) => <li>{p.title}</li>)}
    </ul>
  </body>
</html>

Fíjate en la diferencia frente a un SPA: en React harías esto dentro de un useEffect, con un estado de loading, otro de error y la lista vacía hasta que llegaran los datos. En Astro el problema desaparece: la página nace con los datos dentro, ya renderizados.

El precio: los datos se «congelan» en el build

Generar en build time tiene una contrapartida clara: la página está tan actualizada como el último build. Si los datos cambian cada minuto (el precio de una acción, el stock de un producto), un sitio puramente estático se queda desfasado. Para esos casos existe el SSR (Módulo 5, lección 3) y también estrategias de reconstrucción programada (vercel, netlify, webhooks de CMS).

Analogía: un sitio en build time es como un periódico impreso: la información es sólida y la lectura es instantánea, pero si pasa algo cambia el titular hasta la siguiente edición. Un sitio SSR es un informe en directo: siempre fresco, pero más caro de servir y más lento en la primera pintura.

getStaticPaths: datos que generan rutas

El caso más potente: usar los datos para decidir qué páginas existen. Con una lista de posts de una API, Astro puede generar una página por post. Eso se hace en getStaticPaths, que también se ejecuta en build y puede hacer await.

src/pages/posts/[slug].astro
---
// Esta funcion le dice a Astro que genere UNA pagina por cada post.
export async function getStaticPaths() {
  // Fetch en build time: una sola llamada para todas las rutas.
  const res = await fetch('https://api.example.com/posts');
  const posts = await res.json();

  // Devolvemos un array con un objeto por ruta y sus props.
  return posts.map((post) => ({
    params: { slug: post.slug },   // -> /posts/mi-post
    props: { post },               // -> disponible en esta pagina
  }));
}

// Astro inyecta las props que devolvimos arriba.
const { post } = Astro.props;
---

<article>
  <h1>{post.title}</h1>
  <div set:html={post.bodyHtml} />
</article>

Detalle importante: si además usas Content Collections (Módulo 3), normalmente no necesitas getStaticPaths con fetch, porque los datos ya viven en tu repositorio. getStaticPaths brilla cuando las rutas dependen de una fuente externa.

Fallo de red: los datos externos pueden no llegar

Un fetch en build time puede fallar (la API está caída, el token caducó, hay límite de peticiones). Y un fallo en build rompe el despliegue entero. Por eso hay que manejar el error:

  • Comprueba response.ok: fetch no lanza error en respuestas 404 o 500; hay que revisarlo a mano.
  • Envuelve en try/catch si quieres degradar con elegancia (mostrar un mensaje o usar datos por defecto).
  • Decide: ¿prefieres que el build falle (para no desplegar datos rotos) o seguir con un fallback? Depende del sitio.

Antipatrón silencioso: hacer catch y devolver [] siempre. El sitio se construye «bien» pero con listas vacías y nadie se entera. Si eliges un fallback, loguea el error para que el build lo deje rastro.

3 · Ejemplo mínimo

El fetch más pequeño posible, con manejo correcto de errores. Usamos una API pública de ejemplo:

src/pages/frases.astro
---
// Definimos el tipo de lo que esperamos recibir (TypeScript).
interface Quote {
  id: number;
  quote: string;
  author: string;
}

let quotes: Quote[] = [];

try {
  // 1) Pedimos los datos. Este fetch ocurre en BUILD TIME.
  const res = await fetch('https://dummyjson.com/quotes?limit=5');

  // 2) fetch NO lanza error en 404/500: hay que comprobar ok.
  if (!res.ok) throw new Error(`HTTP ${res.status}`);

  // 3) Convertimos el cuerpo de la respuesta a JSON.
  const data = await res.json();

  // 4) Nos quedamos solo con lo que necesitamos, ya tipado.
  quotes = data.quotes;
} catch (error) {
  // 5) Si algo falla, registramos y seguimos con lista vacia.
  console.error('No se pudieron cargar las frases:', error);
}
---

<html lang="es">
  <body>
    <h1>Cinco frases</h1>
    <ul>
      {quotes.map((q) => (
        <li>«{q.quote}» — <cite>{q.author}</cite></li>
      ))}
    </ul>
  </body>
</html>

Explicado línea a línea:

  1. El tipo Quote documenta la forma de los datos. TypeScript no los valida en tiempo de ejecución (eso lo hará Zod en Content Collections), pero te da autocompletado y detección de errores.
  2. await fetch(...) en el frontmatter: se ejecuta una sola vez, en build.
  3. if (!res.ok) throw: imprescindible. fetch solo rechaza la promesa en fallos de red, no en respuestas de error HTTP.
  4. await res.json(): parsea el cuerpo a un objeto JavaScript.
  5. try/catch: evita que un fallo externo rompa todo el build, mostrando un rastro en consola.

4 · Ejemplo real

Un patrón profesional: una web que lista los issues de un repositorio de GitHub usando su API, con token privado desde variables de entorno y validación de los datos antes de usarlos.

.env
# Variable privada: solo existe en el servidor de build.
# El prefijo PUBLIC_ NO se usa: queremos que sea secreta.
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx
src/pages/issues.astro
---
// import.meta.env lee variables de entorno. Las que NO empiezan por
// PUBLIC_ solo existen en el servidor, nunca viajan al navegador.
const token = import.meta.env.GITHUB_TOKEN;

interface Issue {
  number: number;
  title: string;
  state: 'open' | 'closed';
  html_url: string;
}

// Tipamos el resultado real de la API de GitHub (subset).
interface ApiIssue {
  number: number;
  title: string;
  state: 'open' | 'closed';
  html_url: string;
  pull_request?: unknown;
}

let issues: Issue[] = [];

try {
  const res = await fetch(
    'https://api.github.com/repos/withastro/astro/issues?per_page=10',
    { headers: { Authorization: `Bearer ${token}` } } // token en el servidor
  );
  if (!res.ok) throw new Error(`GitHub respondio ${res.status}`);

  const raw: ApiIssue[] = await res.json();

  // Filtramos los pull requests (vienen marcados) y nos quedamos con issues reales.
  issues = raw
    .filter((i) => !i.pull_request)
    .map((i) => ({ number: i.number, title: i.title, state: i.state, html_url: i.html_url }));
} catch (error) {
  console.error('Fallo al cargar issues de GitHub:', error);
}
---

<html lang="es">
  <body>
    <h1>Issues abiertos</h1>
    <ul>
      {issues.map((issue) => (
        <li>
          <a href={issue.html_url}>#{issue.number} {issue.title}</a>
          <span>({issue.state})</span>
        </li>
      ))}
    </ul>
  </body>
</html>

Decisiones profesionales:

  • Token en el servidor: como el fetch corre en build, la clave GITHUB_TOKEN nunca se envía al navegador. Si esto fuera un fetch de cliente, el token estaría expuesto a cualquiera.
  • Filtrado y mapeo: no pasamos la respuesta cruda; la reducimos a lo que necesitamos para no acoplar la UI al formato exacto de la API.
  • try/catch con log: si GitHub falla, el build no se cae en silencio; deja rastro y la página muestra una lista vacía.
  • Aviso sobre límites: la API de GitHub limita peticiones sin token (rate limit). Como pedimos una vez por build, normalmente no hay problema; pero conviene saberlo.

Depurar en DevTools funciona distinto aquí. El fetch ocurre en el servidor de build, no en el navegador, así que no lo verás en la pestaña Network del navegador. Para depurarlo, mira la salida de la terminal donde corre pnpm dev / pnpm build: ahí imprimen tus console.error.

6 · Errores habituales

No comprobar res.ok

✗ Incorrecto

---
// Si la API responde 500, res.json() lanza un error confuso mas adelante.
const res = await fetch('https://api.example.com/data');
const data = await res.json();
---

✓ Correcto

---
const res = await fetch('https://api.example.com/data');
if (!res.ok) throw new Error(`HTTP ${res.status}`); // falla claro y temprano
const data = await res.json();
---

Sin la comprobación, un error del servidor se disfraza de problema de parseo y pierdes tiempo buscando donde no está.

Exponer un token con prefijo PUBLIC_

✗ Incorrecto

# PUBLIC_ hace que la variable se envie al NAVEGADOR. Token expuesto.
PUBLIC_API_TOKEN=secreto123

✓ Correcto

# Sin prefijo: solo existe en el servidor de build.
API_TOKEN=secreto123

En Astro, el prefijo PUBLIC_ marca una variable como pública. Los secretos jamás deben llevarlo; deben quedarse en el servidor.

Fetch del cliente para datos que no cambian

✗ Incorrecto

<!-- Traer los articulos con JavaScript en el navegador: spinner innecesario. -->
<script>
  fetch('/api/posts').then(r => r.json()).then(render);
</script>

✓ Correcto

---
// Los datos no cambian entre build y visita: traelos en build time.
const posts = await (await fetch('/api/posts')).json();
---
{posts.map((p) => <article>{p.title}</article>)}

Si el dato no depende del usuario ni cambia por segundo, pedirlo en el cliente solo añade latencia y estados de carga que puedes evitar por completo.

Ignorar que el build puede romperse

✗ Incorrecto

---
// Si la API esta caida, el build ENTERO falla y no despliegas.
const data = await (await fetch(apiUrl)).json();
---

✓ Correcto

---
let data = [];
try {
  const res = await fetch(apiUrl);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  data = await res.json();
} catch (e) {
  console.error('Fallo al cargar datos, uso fallback:', e);
}
---

Decide si un fallo de datos externos debe impedir el despliegue o no. Si no, envuélvelo y deja constancia en el log.

Objetivo: construir una página que consuma una API pública en build time y muestre los datos tipados, con manejo de errores.

8 · Reto

🎯 Un blog generado desde una API

Crea una sección /blog con dos páginas generadas íntegramente a partir de datos externos:

  • /blog: lista de posts (uno de ellos consumiendo el endpoint que prefieras).
  • /blog/[slug]: una página por post, usando getStaticPaths para generar las rutas a partir de los datos.

Requisitos: tipar los datos con TypeScript, comprobar res.ok, manejar el fallo con un mensaje visible, y asegurarte de que getStaticPaths hace una sola llamada a la API para todas las rutas (no una por post).

Finalmente, ejecuta pnpm build y comprueba en dist/blog/ que se ha generado un HTML por cada post: son ficheros estáticos, no rutas dinámicas.

Pista: llama al fetch una vez al principio de getStaticPaths y reutiliza el array. Dentro de la página individual, el post llega ya como prop; no vuelvas a llamar a la API. Y recuerda que aquí no puedes depurar con DevTools: usa la consola de la terminal de Astro.

9 · Resumen

  • El frontmatter de un .astro es código de servidor que corre en build time y admite await.
  • Un fetch en build se ejecuta una vez: el HTML nace con los datos dentro, sin estado de carga en el cliente.
  • Los secretos quedan seguros: los fetch de servidor nunca exponen tokens al navegador.
  • getStaticPaths usa datos para decidir qué páginas se generan (una por post, producto, etc.).
  • Siempre hay que comprobar res.ok y decidir si el build debe fallar o degradar ante un error.
  • El límite del modelo es la frescura: los datos son tan recientes como el último build (para tiempo real, SSR).

10 · Preguntas frecuentes

¿Cómo veo el fetch en DevTools si corre en el servidor?

No lo verás en la pestaña Network del navegador: ocurre en el proceso de build. Depura con la consola de la terminal donde corre pnpm dev o pnpm build. Ahí aparecen tus console.log/console.error y los errores de red. Para inspeccionar el JSON, imprime una muestra con console.log(data) o usa curl.

¿Qué pasa si la API está caída justo cuando despliego?

Depende de cómo lo manejes. Si no capturas el error, el build falla y verás el error en CI: a veces es lo deseado (mejor no publicar una web rota). Si capturas y usas un fallback, el despliegue sigue pero con datos por defecto. Elige según la criticidad del dato y deja siempre un log visible.

¿Puedo pedir datos nuevos sin volver a desplegar?

Sí, con tres estrategias habituales: (1) incremental builds o rebuild hooks: tu CMS o backend avisa a Vercel/Netlify para reconstruir el sitio; (2) tareas programadas que reconstruyen cada X tiempo; (3) SSR (Módulo 5, lección 3), donde el dato se pide en cada petición. Cada opción cambia frescura por coste.

¿Puedo usar axios u otra librería en vez de fetch?

Sí, cualquier librería funciona en el frontmatter porque es código Node. Pero fetch ya es nativo en versiones modernas de Node y no añade dependencias. Para la mayoría de casos, el fetch nativo es suficiente; reserva librerías para necesidades específicas (interceptores, reintentos complejos, streaming).

¿Los datos del fetch pueden llegar al navegador sin querer?

Solo si los incluyes en el HTML o los pasas como props a una isla hidratada. Las variables de entorno sin PUBLIC_ nunca se envían. Un cuidado adicional: si pasas objetos enormes a una isla, esos datos se serializan en la página. Mantén las props de isla pequeñas y no incluyas secretos en ellas.
