Proyecto: blog optimizado SEO y rendimiento

Módulo 7 · SEO y Rendimiento 🕐 45 minutos

1 · Introducción

Cerramos el módulo construyendo un blog optimizado: metadatos completos, imágenes de portada optimizadas con <Picture>, transiciones suaves entre lista y artículo, prefetch, y un informe de rendimiento antes/después. Es el proyecto que reúne SEO (lección 1), View Transitions (lección 2) y rendimiento (lección 3).

La meta no es «un blog bonito», sino un blog que un buscador entienda, que las redes compartan bien y que cargue rápido en un móvil real. Para eso repetiremos el bucle de las tres lecciones: estructura → SEO → medir → optimizar.

¿Por qué este proyecto? Porque un blog es el caso de uso canónico de Astro: contenido, rutas dinámicas, colecciones e imágenes. Y porque este proyecto te obliga a medir: no basta con escribir metas y prefetches; hay que demostrar con datos que la web mejoró. Ese hábito, documentar el antes y el después, es lo que distingue a un profesional.

Errores típicos que evitaremos en el proyecto: portadas sin dimensiones (CLS); metadatos duplicados en todos los artículos; activar transiciones sin re-inicializar scripts; y añadir prefetch de todo sin control.

2 · Teoría

Arquitectura del blog

  src/
  ├─ config.ts                 fuente unica: titulo, url, autor
  ├─ content/
  │   └─ blog/                 articulos en Markdown (.md / .mdx)
  │       ├─ islands.md
  │       └─ seo.md
  ├─ components/
  │   ├─ Seo.astro             metadatos + Open Graph + JSON-LD
  │   ├─ PostCard.astro        tarjeta de la lista (con transition:name)
  │   └─ Layout.astro          ClientRouter + Seo + fuentes
  └─ pages/
      ├─ index.astro           portada: lista de articulos
      ├─ blog/[slug].astro     articulo (getStaticPaths)
      ├─ rss.xml.js            feed generado de la coleccion
      └─ robots.txt / sitemap via integracion

Tres capas separadas: contenido (Markdown en la colección), presentación (componentes) y configuración (metadatos, dominio). Esta separación es lo que hace el blog mantenible: publicar un artículo es crear un archivo; cambiar el dominio es editar una línea.

El camino crítico de una página de blog

Para optimizar hay que saber qué ocurre, en orden, hasta que el usuario ve el artículo:

  Visitante pide /blog/islands
        |
        v
  HTML estatico (ya con metadatos SEO dentro)
        |
        +--> CSS (fuentes + estilos)
        |
        +--> Imagen de portada optimizada (AVIF/WebP)  <-- LCP probable
        |
        v
  Pinta el contenido (sin esperar a JS)
        |
        +--> JS: solo las islas necesarias (aqui, casi ninguna)

El objetivo es que la cadena sea corta: HTML ya listo, imagen del LCP optimizada y priorizada, y prácticamente nada de JavaScript que bloquee el hilo.

SEO como contrato de datos

Un blog sano no deja el SEO al azar. La colección define un esquema con los campos obligatorios (title, description, pubDate, portada). Si un artículo no los trae, no compila. Así, es imposible publicar un artículo sin descripción: el error salta en el build, no en producción.

Analogía: el esquema de la colección es como el control de calidad de una imprenta. Antes de imprimir, se verifica que cada libro tiene portada, título y ISBN. Si falta algo, se para la tirada. En Astro, ese control es Zod, y el build es la tirada.

Un solo lugar para el SEO, un solo lugar para el rendimiento

  • SEO: el componente <Seo> es la única fuente de metadatos. Ninguna página escribe <meta> a mano.
  • Rendimiento: una sola estrategia de islas y prefetch definida en el layout y el config; no decisiones dispersas por cada página.

Centralizar es lo que hace que el blog escale sin degradarse. Añadir la página 100 no debería empeorar nada, porque no toca ninguna regla.

3 · Ejemplo mínimo

La pieza mínima que hace funcionar el blog: una colección con esquema y una página que la lista con SEO.

src/content.config.ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

// Coleccion "blog" con esquema obligatorio: el SEO deja de
// depender de que el autor se acuerde.
const blog = defineCollection({
  loader: glob({ pattern: '**/*.md', base: './src/content/blog' }),
  schema: z.object({
    title: z.string(),
    description: z.string(),       // obligatoria
    pubDate: z.coerce.date(),
    draft: z.boolean().default(false),
    cover: z.string().optional(),  // ruta a la imagen de portada
  }),
});

export const collections = { blog };
src/pages/index.astro
---
import { getCollection } from 'astro:content';
import Layout from '../layouts/Layout.astro';

// Solo articulos publicados, los mas recientes primero.
const posts = (await getCollection('blog', ({ data }) => !data.draft))
  .sort((a, b) => b.data.pubDate.valueOf() - a.data.pubDate.valueOf());
---
<Layout title="Blog" description="Articulos sobre Astro y desarrollo web.">
  <h1>Blog</h1>
  <ul>
    {posts.map((post) => (
      <li>
        <a href={`/blog/${post.id}/`}>
          <h2>{post.data.title}</h2>
          <p>{post.data.description}</p>
        </a>
      </li>
    ))}
  </ul>
</Layout>

Explicado línea a línea:

  1. defineCollection + glob: la colección blog lee todos los .md de src/content/blog. El content layer de Astro 5 usa un loader.
  2. schema con Zod: title y description son obligatorios. Un artículo sin descripción falla en el build: es imposible saltarse el SEO.
  3. getCollection('blog', filtro): recupera las entradas publicadas (!draft) y las ordena por fecha. La fuente de verdad es el contenido.
  4. <Layout> con props: la portada pasa su SEO al layout, que delega en <Seo>.

4 · Ejemplo real

El blog completo. Empezamos por la base (config y colección), seguimos con los componentes y terminamos con las páginas y la verificación.

Paso 2 — Metadatos: el componente <Seo>

interface Props {

  author: { '@type': 'Person', name: SITE.author },

  inLanguage: 'es',

Paso 5 — El artículo (portada optimizada + datos estructurados)

src/pages/blog/[slug].astro
---
import { getCollection } from 'astro:content';
import { Image } from 'astro:assets';
import Layout from '../../layouts/Layout.astro';
import coverDefault from '../../assets/cover-default.jpg';

// Una ruta por articulo, generada en build.
export async function getStaticPaths() {
  const posts = await getCollection('blog', ({ data }) => !data.draft);
  return posts.map((post) => ({
    params: { slug: post.id },
    props: { post },
  }));
}

const { post } = Astro.props;
const { Content } = await post.render();
---
<Layout
  title={post.data.title}
  description={post.data.description}
  type="article"
  publishedTime={post.data.pubDate.toISOString()}
>
  <article>
    <!-- LCP: prioridad alta + dimensiones (sin CLS). -->
    <Image
      src={coverDefault}
      alt=""
      loading="eager"
      fetchpriority="high"
      transition:name={`cover-${post.id}`}
    />
    <h1>{post.data.title}</h1>
    <time datetime={post.data.pubDate.toISOString()}>
      {post.data.pubDate.toLocaleDateString('es-ES')}
    </time>
    <Content />
  </article>
</Layout>

Paso 6 — Verificar y medir

  1. Build y preview: 
    pnpm build
pnpm preview
  2. Comprueba el SEO: inspecciona el <head> de un artículo. canonical, og:image y og:url deben ser absolutas. Valida el JSON-LD en el Rich Results Test.
  3. Comprueba las transiciones: navega de la lista a un artículo y observa la portada viajar. Luego activa «prefers-reduced-motion» y confirma que desaparecen.
  4. Mide con Lighthouse en modo Mobile y anota LCP, TBT y CLS. Compara con una versión sin optimizar (por ejemplo, quitando fetchpriority y el prefetch).

Decisiones profesionales detrás del proyecto:

  • Esquema obligatorio: el SEO está garantizado por tipos, no por disciplina. Un artículo mal formado no compila.
  • Un solo <Seo>: metadatos, Open Graph, Twitter y JSON-LD en un componente reutilizable.
  • Portada con dimensiones y prioridad: la imagen del LCP va eager + fetchpriority="high"; las de la lista, con srcset.
  • transition:name coherente: la portada viaja de la tarjeta al artículo, dando continuidad visual.
  • Cero islas innecesarias: el blog es contenido puro; no se hidrata nada.
  • Prefetch por viewport: navegación fluida sin gastar ancho de banda de más.

Verifica en DevTools: en Network, comprueba que la imagen de portada es AVIF/WebP y que las de la lista traen srcset. En Coverage, el JavaScript del blog debería ser casi inexistente (solo el runtime del router). En Lighthouse, el LCP debería ser la propia imagen, no un bloque de texto.

6 · Errores habituales

Portada sin dimensiones ni prioridad

✗ Incorrecto

<!-- img crudo: sin dimensiones (CLS) y sin prioridad (LCP lento). -->
<img src={post.data.cover} alt="" class="w-full" />

✓ Correcto

---
import { Image } from 'astro:assets';
import cover from '../../assets/cover-default.jpg';
---
<Image src={cover} alt="" loading="eager" fetchpriority="high" />

La imagen del artículo es, casi siempre, el elemento más grande de la primera pantalla: es el LCP. Sin dimensiones, además, provoca layout shift.

Activar transiciones y romper los scripts

✗ Incorrecto

// Con ClientRouter, esto corre UNA sola vez: el menu deja de
// funcionar al navegar a otra pagina.
document.querySelector('.menu')?.addEventListener('click', toggleMenu);

✓ Correcto

// Se re-inicializa en la carga inicial y tras cada navegacion.
document.addEventListener('astro:page-load', () => {
  document.querySelector('.menu')?.addEventListener('click', toggleMenu);
});

El error más común al usar <ClientRouter />. Cualquier inicialización debe vivir dentro de astro:page-load.

Metadatos duplicados en el artículo

✗ Incorrecto

<!-- El layout ya pone <title> y og:*. Aqui se duplican. -->
<Layout>
  <title>{post.data.title}</title>
  <meta property="og:title" content={post.data.title} />
</Layout>

✓ Correcto

<!-- Un solo origen: se pasan como props al layout. -->
<Layout title={post.data.title} description={post.data.description} type="article">

Dos orígenes de metadatos producen etiquetas duplicadas y conflictos. El SEO debe tener un único dueño: el componente <Seo>.

Prefetch indiscriminado del pie de página

✗ Incorrecto

// Prefetch de TODOS los enlaces al cargar: descarga decenas
// de paginas que el usuario no visitara.
export default defineConfig({ prefetch: { prefetchAll: true, defaultStrategy: 'load' } });

✓ Correcto

// Prudente: prepara lo que el usuario ve.
export default defineConfig({ prefetch: { defaultStrategy: 'viewport' } });

Prefetchear todo con load puede gastar muchísimo ancho de banda, sobre todo en móvil. viewport es el equilibrio sensato.

8 · Reto

🎯 Feed RSS, imágenes OG dinámicas y blog por categorías

Amplía el blog hasta un nivel de producción:

  • RSS y sitemap: genera /rss.xml desde la colección y confirma que el sitemap-index.xml incluye todos los artículos.
  • Imágenes Open Graph por artículo: genera una imagen social distinta por entrada con el título sobre un fondo de marca. Puedes usar un endpoint de imagen o una librería que componga el PNG en build.
  • Páginas de categoría: añade un campo category al esquema y crea /categoria/[cat] con getStaticPaths, con su propio SEO y su propio RSS filtrado.
  • Búsqueda bajo demanda: un buscador de artículos cuyo índice se descargue solo con import() dinámico al abrir el buscador (o al pulsar el botón).
  • Sitemap, RSS y categorías con JSON-LD correcto en cada tipo de página.

Exige que el build falle si un artículo no tiene categoría (esquema obligatorio) y documenta el informe de rendimiento final, con el presupuesto de JS que te hayas fijado.

Pista: para las imágenes OG dinámicas, hay guías que combinan generación en build con librerías de renderizado; recuerda que puedes aprovechar la API de fuentes de Astro para cargar la tipografía dentro de la imagen. Para el RSS por categoría, reutiliza el mismo endpoint cambiando el filtro de la colección. Y no olvides: cada página nueva debe seguir pasando por el mismo <Seo>.

9 · Resumen

  • Un blog Astro separa contenido (colección), presentación (componentes) y config (metadatos).
  • El esquema de la colección convierte el SEO en un contrato: un artículo mal formado no compila.
  • Un único <Seo> centraliza metadatos, Open Graph, Twitter y JSON-LD.
  • La imagen de portada es el LCP: dimensiones, formato moderno y fetchpriority="high".
  • <ClientRouter /> aporta transiciones y elementos que viajan; exige re-inicializar scripts en astro:page-load.
  • astro:prefetch por viewport da navegación fluida sin malgastar datos.
  • El trabajo se cierra midiendo antes y después con Lighthouse.

10 · Preguntas frecuentes

¿Necesito TypeScript para el esquema de la colección?

Puedes usar Zod en JavaScript, pero TypeScript te da el máximo beneficio: el esquema genera tipos que alimentan tus props y componentes. El curso fomenta TS para props y colecciones justamente por eso. No es obligatorio, pero sí recomendable en un blog que crezca.

¿Las transiciones afectan al SEO?

No de forma negativa si cada página sigue siendo HTML con sus metadatos. De hecho, cada ruta sigue existiendo como documento indexable. Lo que hay que cuidar es que ninguna página quede sin <title> (por el anuncio de ruta y por SEO) y que el contenido no dependa de JavaScript para mostrarse.

¿Cómo sé cuál es mi LCP real?

Lighthouse te lo marca en el informe: señala el elemento concreto. En un blog suele ser la imagen de portada o el <h1>. Si es la imagen, optimízala y priorízala; si es texto, suele bastar con cargar rápido las fuentes y no bloquear el render.

¿Qué diferencia hay entre el esquema obligatorio y la validación en runtime?

El esquema de Zod se valida en build time: si el contenido no cumple, el build falla y no se despliega. No hay validación en runtime del navegador porque el navegador solo recibe HTML ya construido. Esto es una ventaja: los errores de datos se detectan antes de publicar.

¿Puedo añadir interactividad (por ejemplo, comentarios) sin arruinar el rendimiento?

Sí: como una isla con client:visible o client:idle, para que su JavaScript no compita con la carga inicial. Si los comentarios se cargan desde una API, que el fetch ocurra cuando la isla se hidrata, no en el HTML. Y si el formulario de comentarios es lo único interactivo, mantenlo aislado del resto del contenido estático.
