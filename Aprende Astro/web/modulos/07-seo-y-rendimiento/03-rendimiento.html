Core Web Vitals y optimización

Módulo 7 · SEO y Rendimiento 🕐 30 minutos

1 · Introducción

Rendimiento no es «que cargue rápido» en abstracto: Google lo mide con tres métricas concretas, las Core Web Vitals. Y no son una moda: influyen en el posicionamiento y, sobre todo, en si el usuario se queda o se va. En esta lección aprenderás qué miden, por qué Astro parte con ventaja y qué palancas concretas (menos JavaScript, imports de assets, splitting, prefetch) mueven la aguja.

La buena noticia: ya has hecho lo más difícil en módulos anteriores. Al usar HTML estático, imágenes optimizadas y pocas islas, tu web ya está en buena forma. Aquí afinamos y, sobre todo, aprendemos a medir.

¿Por qué existe esta lección? Porque «optimizar» sin medir es adivinar. La diferencia entre un desarrollador que mejora un sitio y uno que lo empeora es que el primero mira Lighthouse y las métricas reales antes de tocar nada. El rendimiento es una disciplina empírica: se mide, se cambia una cosa, se vuelve a medir.

Errores típicos que veremos: optimizar a ciegas; cargar JavaScript de un framework para cosas que no lo necesitan; usar ?raw o ?url cuando no hace falta (saltándose el pipeline de Astro sin motivo); y confundir «el sitio me carga rápido en mi máquina» con «el sitio carga rápido para un móvil en 4G».

2 · Teoría

Las tres Core Web Vitals

MétricaQué mideObjetivoQué la empeora
LCP (Largest Contentful Paint) Tiempo hasta pintar el mayor elemento visible (imagen, titular) < 2,5 s Imágenes enormes, recursos que bloquean, JavaScript que retrasa la pintura
INP (Interaction to Next Paint) Latencia de las interacciones del usuario < 200 ms JavaScript pesado que satura el hilo principal
CLS (Cumulative Layout Shift) Cuánto «salta» la maquetación mientras carga < 0,1 Imágenes sin dimensiones, fuentes sin respaldo ajustado, anuncios inyectados

Analogía: el LCP es «cuánto tardas en ver el plato». El INP es «cuánto tarda el camarero en reaccionar cuando levantas la mano». El CLS es «si la mesa se mueve de sitio justo cuando vas a coger el tenedor». Las tres cosas juntas definen la sensación de calidad.

Por qué Astro parte con ventaja

Recuerda la arquitectura islands (Módulo 4): el HTML se sirve completo y solo los trozos interactivos hidratan. Traducido a métricas:

  • LCP bajo: el contenido principal ya está en el HTML; no hay que esperar a JavaScript para pintarlo.
  • INP bajo: si hay poco JavaScript, el hilo principal está libre para responder a los clics.
  • CLS bajo: con <Image>/<Picture> las dimensiones están puestas, y las fuentes con respaldos optimizados no provocan saltos.

En una SPA, el mismo contenido exige descargar, parsear y ejecutar el framework antes de pintar nada. Ese coste se paga en las tres métricas a la vez.

Menos JavaScript: la palanca principal

El JavaScript es el recurso más caro: se descarga, se parsea y se ejecuta, y bloquea el hilo principal. Cada isla que añades cuesta. La estrategia no es «cero JavaScript», sino solo el necesario, cuando se necesita:

DirectivaCoste para el LCP/INP
client:loadAlto: hidrata ya, compite con la primera pintura
client:idleMedio: espera a que el navegador esté libre
client:visibleBajo: solo hidrata al entrar en pantalla
client:mediaBajo: solo en el tamaño que lo necesita
client:onlyVariable: no hay HTML de servidor (puede empeorar el LCP)

Regla: empieza por client:visible y sube solo si la experiencia lo exige. La mayoría de las islas de un sitio bien hecho no necesitan client:load.

Imports de assets: ?url y ?raw

Vite (el motor de Astro) permite importar un archivo de dos formas especiales:

  • ?url: obtienes la URL del archivo, no su contenido. Útil para referenciarlo desde JavaScript o desde un atributo.
  • ?raw: obtienes el contenido del archivo como texto. Útil para inyectar un fragmento tal cual.
src/lib/assets.ts
// ?url devuelve la URL publica del recurso tras el build.
import logoUrl from '../assets/logo.svg?url';

// ?raw devuelve el CONTENIDO del archivo como string.
import snippetCss from '../styles/snippet.css?raw';

export { logoUrl, snippetCss };

Cuidado: ?raw y ?url saltan el procesado normal de Astro. Un CSS importado con ?url no se optimiza ni se combina con el resto; un CSS con ?raw no pasa por Tailwind ni por PostCSS. Son herramientas para casos concretos, no para lo cotidiano. Normalmente basta con un import './styles.css' a secas.

Splitting: cada página, su propio JavaScript

Astro (vía Vite) hace code splitting automático: el JavaScript común se agrupa en trozos compartidos y cada página carga solo lo que usa. Además, controlas manualmente el trozo cargando código bajo demanda con import() dinámico:

src/components/Search.astro
<button id="open-search">Buscar</button>
<script>
  // La libreria de busqueda solo se descarga cuando el usuario la abre.
  document.getElementById('open-search')?.addEventListener('click', async () => {
    const { openSearchModal } = await import('../lib/search.js');
    openSearchModal();
  });
</script>

Este patrón es oro para el INP: el código de una función que casi nadie usa no se descarga hasta que alguien la usa.

astro:prefetch: sentir la navegación como instantánea

Prefetch significa «descarga la siguiente página antes de que el usuario haga clic en el enlace», para que al pulsar ya esté lista. Astro lo integra de forma opt-in:

astro.config.mjs
export default defineConfig({
  // Activa un script de prefetch en todas las paginas.
  prefetch: true,
});

Y en los enlaces, la estrategia (por defecto hover):

src/components/Nav.astro
<!-- Se prefetchea cuando el raton pasa por encima (hover). -->
<a href="/blog" data-astro-prefetch>Blog</a>

<!-- Prefetch cuando el enlace entra en pantalla. -->
<a href="/precios" data-astro-prefetch="viewport">Precios</a>

<!-- Excluir un enlace concreto. -->
<a href="/pesado" data-astro-prefetch="false">Panel pesado</a>

Estrategias disponibles: hover (por defecto), tap, viewport y load. Astro detecta conexiones lentas y modo ahorro de datos y, en esos casos, degrada el prefetch para no gastar el ancho de banda del usuario.

Si usas <ClientRouter /> (lección anterior), el prefetch se activa por defecto con prefetchAll: todos los enlaces internos se prefetchean. Puedes ajustarlo o desactivarlo en el config.

3 · Ejemplo mínimo

El ejemplo más pequeño con impacto real: una isla que solo se hidrata al entrar en pantalla, y un enlace con prefetch.

src/pages/index.astro
---
import SearchBox from '../components/SearchBox.jsx';
---
<main>
  <h1>Inicio</h1>

  <!-- El buscador esta abajo: solo hidrata cuando el usuario
       hace scroll hasta el. No pesa en el LCP. -->
  <SearchBox client:visible />

  <!-- El enlace prefetchea su destino al pasar el raton. -->
  <a href="/blog" data-astro-prefetch>Ir al blog</a>
</main>
astro.config.mjs
import { defineConfig } from 'astro/config';

export default defineConfig({
  // Habilita el script de prefetch en todas las paginas.
  prefetch: true,
});

Explicado línea a línea:

  1. client:visible: la isla SearchBox solo descarga su JavaScript cuando entra en el viewport. Si el usuario nunca baja, nunca se descarga: LCP e INP mejoran.
  2. data-astro-prefetch: al pasar el ratón por el enlace, Astro descarga /blog en segundo plano. Al hacer clic, la página aparece casi al instante.
  3. prefetch: true: sin esto, el atributo no hace nada. Es la configuración global que habilita el script.

Esto es todo lo necesario para una mejora perceptible. Recuerda: primero mide con Lighthouse sin estos cambios, luego añádelos y vuelve a medir. La diferencia en «navegación percibida» debería notarse.

4 · Ejemplo real

Un blog optimizado: portada ligera, islas diferidas, código bajo demanda, prefetch por viewport y assets referenciados con ?url.

Config: prefetch y ajuste de inlining de CSS

astro.config.mjs
import { defineConfig } from 'astro/config';

export default defineConfig({
  site: 'https://mi-blog.example.com',

  // Prefetch para todos los enlaces internos, por viewport.
  prefetch: {
    prefetchAll: true,
    defaultStrategy: 'viewport',
  },

  build: {
    // CSS pequeno se incrusta en el HTML (menos peticiones);
    // el grande queda como archivo cacheable.
    inlineStylesheets: 'auto',
  },
});

Portada: islas diferidas y código bajo demanda

src/pages/index.astro
---
import Hero from '../components/Hero.astro';       // estatico, cero JS
import Newsletter from '../components/Newsletter.jsx'; // isla
import Comments from '../components/Comments.jsx';     // isla pesada
---
<Hero />

<!-- Esta abajo del todo: hidratar solo al verla. -->
<Newsletter client:visible />

<!-- Isla cara y secundaria: hidrata cuando el navegador este libre. -->
<Comments client:idle />

Y un buscador que se carga bajo demanda (no en el bundle inicial):

src/components/SearchButton.astro
<button data-search>Buscar</button>
<script>
  document.addEventListener('astro:page-load', () => {
    const btn = document.querySelector('[data-search]');
    btn?.addEventListener('click', async () => {
      // El motor de busqueda (potencialmente pesado) solo se
      // descarga cuando el usuario pulsa el boton.
      const { openSearch } = await import('../lib/search.js');
      openSearch();
    });
  });
</script>

Referenciar un asset por URL y otro por contenido

src/pages/kit.astro
---
// ?url -> nos da la URL final del asset tras el build.
import logoUrl from '../assets/logo.svg?url';
// ?raw -> nos da el contenido del archivo como texto.
import resetCss from '../styles/reset-snippet.css?raw';
---
<img src={logoUrl} alt="Logo" width="120" height="32" />

<!-- Inyectamos el fragmento CSS tal cual (caso avanzado). -->
<style is:inline set:html={resetCss}></style>

Medir: el bucle de Lighthouse

  1. Construye y sirve la versión de producción (Lighthouse debe medir el build real, no el dev server): 
    pnpm build
pnpm preview
  2. Mide la línea base: abre DevTools → Lighthouse, modo Mobile, y genera el informe. Anota LCP, INP/TBT y CLS.
  3. Cambia una sola cosa: por ejemplo, mueve una isla de client:load a client:visible.
  4. Vuelve a medir y compara. Anota el antes y el después.

Decisiones profesionales detrás de este ejemplo:

  • Islas con la directiva más barata posible: client:visible para lo de abajo, client:idle para lo secundario. Nada de client:load sin motivo.
  • import() dinámico: el buscador no engorda el bundle inicial. Solo se descarga al usarlo.
  • Prefetch por viewport: los enlaces que el usuario ve se preparan; los que no, no gastan ancho de banda.
  • ?url y ?raw con criterio: se usan solo donde aportan (URL de un asset, inyección de un fragmento), no como sustituto del import normal.
  • Medir el build de producción: el dev server no representa el rendimiento real (no minifica igual, no agrupa igual).

Verifica en DevTools: en la pestaña Coverage (con Ctrl+Shift+P → «Show Coverage») ves qué porcentaje del JavaScript/CSS descargado se usa de verdad. Un sitio sano tiene una cobertura alta. En Network, comprueba que las islas con client:visible no se descargan hasta que haces scroll.

6 · Errores habituales

Hidratar todo con client:load

✗ Incorrecto

<!-- Todo hidrata ya, compitiendo con la primera pintura. -->
<SearchBox client:load />
<Comments client:load />
<Newsletter client:load />

✓ Correcto

<!-- Cada una con la directiva que corresponde a su urgencia. -->
<SearchBox client:visible />
<Comments client:idle />
<Newsletter client:visible />

Hidratar de más es el error de rendimiento más común en Astro. La primera pantalla solo debería hidratar lo imprescindible; lo de abajo, al verse.

Importar el asset con la forma equivocada

✗ Incorrecto

// ?raw para el logo: obtenemos el texto SVG, no la URL.
// Y el CSS con ?url no se optimiza.
import logo from '../assets/logo.svg?raw';
import styles from '../styles/main.css?url';

✓ Correcto

// Elige la forma segun lo que necesites.
import logoUrl from '../assets/logo.svg?url'; // URL del asset
import '../styles/main.css';                  // import normal: optimizado

?raw devuelve contenido (texto), no URL. Y un CSS con ?url se salta la optimización de Astro. Usa cada forma para lo que sirve.

Prefetchear todo sin medida

✗ Incorrecto

// Prefetch de TODOS los enlaces, incluidos los que nadie visita.
export default defineConfig({ prefetch: { prefetchAll: true, defaultStrategy: 'load' } });

✓ Correcto

// Prefetch prudente: por viewport, o solo en los enlaces marcados.
export default defineConfig({ prefetch: { defaultStrategy: 'viewport' } });

Prefetchear con load todos los enlaces puede descargar decenas de páginas que el usuario no visitará, gastando su ancho de banda. viewport o hover son más respetuosos.

Medir con el servidor de desarrollo

✗ Incorrecto

# Lighthouse sobre `pnpm dev`: numeros que no representan nada.
pnpm dev

✓ Correcto

# Mide el build real: minificado y agrupado.
pnpm build
pnpm preview

El dev server no minifica ni agrupa igual. Un informe de Lighthouse sobre dev te da una imagen falsa (normalmente peor y a veces mejor). Mide siempre el preview.

7 · Ejercicio guiado

Objetivo: medir una página con Lighthouse, aplicar una optimización y cuantificar la mejora.

  1. Construye y sirve la versión de producción: 
    pnpm build
pnpm preview
  2. Mide la línea base: DevTools → Lighthouse → modo Mobile → Analyze page load. Anota LCP, TBT (proxy del INP) y CLS.
  3. Identifica la isla más pesada en Coverage y cámbiale la directiva: 
    <!-- Antes -->
<Widget client:load />
<!-- Despues -->
<Widget client:visible />
  4. Añade prefetch a los enlaces de navegación principal: 
    // astro.config.mjs
export default defineConfig({ prefetch: { defaultStrategy: 'viewport' } });
  5. Vuelve a medir y compara con la línea base. Anota la diferencia en LCP y TBT. Documenta el cambio y el resultado en el README.

Interpretación: si el LCP no mejora pero el TBT sí, tu isla no afectaba a la primera pintura (quizá ya estaba abajo), pero sí al hilo principal. Si nada mejora, quizá el cuello de botella sea una imagen: revisa en Network cuál es el recurso más pesado.

8 · Reto

🎯 Presupuesto de rendimiento y auditoría

Optimiza una página del curso hasta cumplir un presupuesto explícito y audítala:

  • Define un presupuesto: por ejemplo, menos de 100 KB de JavaScript inicial, LCP < 2 s en móvil y CLS < 0,05.
  • Portada optimizada: cero JavaScript en la primera pantalla; todas las islas, si hay, con client:visible o client:idle.
  • Código bajo demanda: al menos una funcionalidad cargada con import() dinámico (un buscador, un modal, un reproductor).
  • Prefetch medido: activa prefetch y demuestra con Network que las páginas se preparan al ver los enlaces, no todas al cargar.
  • Informe antes/después: tabla con LCP, INP/TBT y CLS de la línea base y del resultado.

Documenta cada decisión con la métrica que mejoró. Si algo no mejoró, dilo: un informe honesto vale más que uno bonito.

Pista: usa la pestaña Performance para ver qué tarea bloquea el hilo principal. Si el presupuesto de JS se pasa, busca qué componente importa una librería grande y considera cargarla con import(). Y recuerda medir siempre sobre pnpm preview, nunca sobre dev.

9 · Resumen

  • Las Core Web Vitals son LCP (pintar lo grande), INP (reactividad) y CLS (estabilidad visual).
  • Astro parte con ventaja: HTML completo, poca hidratación, imágenes y fuentes dimensionadas.
  • La palanca principal es menos JavaScript: usa la directiva de isla más barata.
  • ?url da la URL de un asset; ?raw da su contenido. Ambos saltan el pipeline: úsalos con criterio.
  • import() dinámico carga código bajo demanda y protege el INP.
  • astro:prefetch prepara las páginas al ver los enlaces; degrada solo en conexiones lentas.
  • Mide siempre sobre el build de producción, cambiando una cosa a la vez.

10 · Preguntas frecuentes

¿Cero JavaScript es el objetivo?

No. El objetivo es el JavaScript necesario, cuando se necesita. Hay interacciones que requieren cliente (un editor, un reproductor). Astro te deja añadirlas con precisión. «Cero» es un ideal; «el mínimo bien colocado» es la meta real.

¿Cuándo uso ?url y cuándo ?raw?

Usa ?url cuando necesites la ruta del archivo (para un atributo o para pasarla a JS). Usa ?raw cuando necesites su contenido como texto (inyectar un fragmento CSS/JS literal). Si solo quieres «usar» el archivo normalmente, importa a secas: es lo óptimo.

¿El prefetch no gasta el ancho de banda del usuario?

Puede, por eso existe el control por estrategia. hover (por defecto) solo prefetchea cuando el usuario muestra interés; viewport cuando ve el enlace. Además, Astro detecta conexiones lentas o modo ahorro de datos y degrada a tap. Con load se prefetchea todo: evítalo salvo en sitios muy pequeños.

¿Cómo sé rápido qué recurso pesa más?

En DevTools → Network, ordena por tamaño y por tiempo. En Coverage, mira qué JS/CSS se descarga y no se usa. En Performance, busca las tareas largas que bloquean el hilo principal. Lighthouse resume todo en métricas accionables.

¿Lighthouse es suficiente para medir el rendimiento real?

Lighthouse da una foto de laboratorio: reproducible y buena para comparar antes/después. No sustituye a los datos de campo (CrUX / RUM), que reflejan usuarios reales en dispositivos y redes reales. Empieza por Lighthouse para iterar; confirma con datos reales en producción.
