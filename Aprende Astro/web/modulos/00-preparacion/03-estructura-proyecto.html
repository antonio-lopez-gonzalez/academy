Estructura del proyecto

Módulo 0 · Preparación 🕐 25 minutos

1 · Introducción

Acabas de crear un proyecto Astro y te encuentras con una carpeta con subcarpetas llamadas src, public, y archivos como astro.config.mjs y tsconfig.json. Antes de escribir código conviene entender qué vive dónde y, sobre todo, por qué Astro lo organiza así.

La idea central de esta lección es una filosofía de diseño que Astro comparte con frameworks como Next.js o Ruby on Rails: convención sobre configuración. Es decir, en lugar de obligarte a declarar en un archivo dónde está cada cosa, Astro asume que las páginas están en src/pages/, los componentes en src/components/, etc. Menos decisiones, menos código de pegamento, menos errores.

🎯 Por qué existe esta lección

Porque en Astro la ubicación de un archivo define su comportamiento. Un archivo en src/pages/ se convierte en una ruta; el mismo archivo en src/components/ no. Entender esta frontera es la diferencia entre que tu web «funcione por casualidad» o sepas exactamente por qué funciona.

2 · Teoría

El árbol de un proyecto Astro

Este es el mapa completo de lo que genera el asistente. Algunas carpetas las crearás tú; las marcadas como reservadas tienen un significado especial.

mi-primer-astro/
├── public/                 ── assets SIN procesar (se copian tal cual al build)
│   └── favicon.svg
├── src/                    ── TU código fuente (Astro lo compila y optimiza)
│   ├── components/         ── componentes reutilizables (.astro, .tsx…)
│   ├── layouts/            ── plantillas de página compartidas
│   ├── pages/              ★ RESERVADA: cada archivo = una URL
│   │   └── index.astro     →  /
│   └── styles/             ── CSS global (convención habitual)
├── astro.config.mjs        ── configuración del proyecto (integraciones…)
├── tsconfig.json           ── configuración de TypeScript
├── package.json            ── dependencias y scripts (dev, build, preview)
├── pnpm-lock.yaml          ── versiones exactas (se versiona en git)
└── .gitignore              ── ignora node_modules/, dist/, .astro/…

📌 La única carpeta reservada es src/pages/

Astro solo reserva src/pages/ para el enrutado. components/, layouts/ y styles/ son convenciones recomendadas, no obligaciones: si prefieres src/ui/ o src/bricks/, funciona. Pero pages/ debe llamarse así y contener las rutas.

src/pages/: el enrutado por sistema de archivos

No hay un archivo de rutas como en Express o React Router. La URL de una página se deduce de dónde está el archivo dentro de src/pages/:

Archivo en src/pages/URL generada
index.astro/
about.astro/about
blog/index.astro/blog
blog/[slug].astro/blog/<lo-que-sea> (ruta dinámica)
rss.xml.js/rss.xml (endpoint, no página)

Fíjate en dos detalles clave desde ya: los corchetes [slug] indican rutas dinámicas y los archivos .js/.ts en pages/ generan endpoints (datos, no HTML). Ambos son el corazón del Módulo 2.

src/components/ y src/layouts/: reutilizar

Componentes son piezas de UI reutilizables: un botón, una tarjeta, un menú. Layouts son componentes especiales que envuelven una página entera y definen su esqueleto común (<html>, <head>, cabecera, pie, menú). La diferencia es de intención, no técnica: ambos son componentes .astro; los layouts se colocan por costumbre en layouts/ porque representan «la forma de una página».

Un layout suele apoyarse en un slot para insertar el contenido específico de cada página. Es el concepto del Módulo 1 que usarás en cada proyecto a partir de ahora.

public/: lo que no se toca

Todo lo que pongas en public/ se copia tal cual a la raíz del build, sin optimizar ni renombrar: public/favicon.svg acaba en dist/favicon.svg y se referencia como /favicon.svg. Es el lugar de robots.txt, manifest.webmanifest, favicons y PDFs.

La contrapartida: como no se procesa, tampoco se optimiza ni se hashea para caché. Por eso Astro recomienda dejar en public/ solo lo que debe mantener su nombre fijo, y meter imágenes y CSS propios en src/ para que se optimicen.

Va en public/Va en src/
favicon.svg, robots.txt, sitemap.xml estáticoImágenes de contenido, iconos SVG usados como componentes
Documentos descargables (cv.pdf)Hojas de estilo (global.css)
Fuentes auto-hospedadas que quieras servir tal cualComponentes, layouts, scripts de servidor

astro.config.mjs: el panel de control

Es el único sitio donde se configura Astro: integraciones (React, Tailwind, sitemap), opciones de build, el site para SEO, adaptadores de SSR, etc. Usa defineConfig para tener autocompletado y validación de tipos.

astro.config.mjs
// defineConfig: helper que aporta tipos y autocompletado a la configuración.
import { defineConfig } from 'astro/config';
import react from '@astrojs/react'; // integración de React (islas)
import tailwind from '@tailwindcss/vite'; // Tailwind v4 como plugin de Vite

export default defineConfig({
  // URL pública del sitio; imprescindible para sitemaps y URLs canónicas.
  site: 'https://mi-portfolio.dev',

  // Cada integración se "enchufa" en el array. El orden importa poco,
  // salvo cuando dos integraciones compiten por lo mismo.
  integrations: [react()],

  // Los plugins de Vite se configuran aquí:
  vite: {
    plugins: [tailwind()],
  },
});

📌 ¿Y no hay config para las rutas?

Correcto: no. No existe una sección donde declares «la ruta /about usa tal componente», porque el sistema de archivos ya es esa declaración. Ese es el espíritu de convención sobre configuración: astro.config.mjs existe para lo global (integraciones, build, SSR), no para el día a día de tu contenido.

tsconfig.json: TypeScript sin dolor

Astro trae TypeScript integrado y un tsconfig.json que suele bastar con extender una configuración oficial. Los tres niveles son:

PlantillaNivel de rigorCuándo usarla
astro/tsconfigs/baseSolo lo mínimo para que funcioneSitios pequeños o migraciones rápidas
astro/tsconfigs/strictstrict de TS activadoRecomendada en este curso
astro/tsconfigs/strictestAún más chequeosEquipos que quieren máxima seguridad
tsconfig.json
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}

Ese extends es la clave: no reinventamos opciones de TypeScript; heredamos las que Astro ha probado como correctas. El include mete también los tipos que Astro genera en .astro/ (por ejemplo, para Content Collections).

3 · Ejemplo mínimo

El proyecto más pequeño que Astro reconoce tiene una sola carpeta y un solo archivo. Basta con src/pages/index.astro para que exista una web funcionando en /.

Estructura mínima
proyecto/
└── src/
    └── pages/
        └── index.astro   # → genera la ruta "/"

Y este es el archivo que la hace funcionar:

src/pages/index.astro
---
// Sin configuración: el mero hecho de estar en src/pages/
// ya convierte este archivo en la página de la ruta "/".
const mensaje = 'El sistema de archivos ES el router';
---

<html lang="es">
  <body>
    <h1>{mensaje}</h1>
  </body>
</html>

Observa lo que no hay: ningún archivo de rutas, ninguna entrada de configuración, ningún registro de página. La convención («todo lo de pages/ es una ruta») hace el trabajo. Si renombras el archivo a about.astro, la página pasa a estar en /about sin tocar nada más.

💡 Compruébalo

Crea src/pages/test.astro con un <h1>Hola</h1>. Guarda y visita http://localhost:4321/test: existe. Borra el archivo: la ruta desaparece (404). Así de directo es el enrutado por archivos.

4 · Ejemplo real

Un proyecto profesional no tiene un solo archivo: tiene páginas que comparten estructura mediante un layout, componentes reutilizables, estilos globales y assets estáticos. Este árbol es el esqueleto que usarás en el proyecto del Módulo 1.

Estructura de un portfolio real
portfolio/
├── public/
│   ├── favicon.svg          # se sirve como /favicon.svg
│   └── cv.pdf               # descargable, sin procesar
├── src/
│   ├── components/
│   │   ├── Header.astro     # cabecera reutilizable
│   │   ├── ProjectCard.astro
│   │   └── Footer.astro
│   ├── layouts/
│   │   └── BaseLayout.astro # esqueleto común de todas las páginas
│   ├── pages/
│   │   ├── index.astro      # → /
│   │   ├── proyectos.astro  # → /proyectos
│   │   └── contacto.astro   # → /contacto
│   └── styles/
│       └── global.css       # importado una vez, aplicado a todo
├── astro.config.mjs
└── tsconfig.json

El layout es la pieza que ata todo. Recibe por slot el contenido de cada página:

src/layouts/BaseLayout.astro
---
// Este layout define el HTML común. Cada página mete SU contenido
// donde está el <slot />, sin repetir head, header ni footer.
import Header from '../components/Header.astro';
import Footer from '../components/Footer.astro';
import '../styles/global.css'; // importar aquí = cargar en todas las páginas
---
<!DOCTYPE html>
<html lang="es">
  <head>
    <meta charset="UTF-8" />
    <title>Mi portfolio</title>
  </head>
  <body>
    <Header />
    <main>
      <slot />  <!-- aquí aparece el contenido de cada página -->
    </main>
    <Footer />
  </body>
</html>
src/pages/index.astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
import ProjectCard from '../components/ProjectCard.astro';
// Los datos pueden vivir aquí o en una colección (Módulo 3).
const proyectos = [
  { title: 'Tienda online', url: 'https://ejemplo.dev' },
  { title: 'App de notas', url: 'https://notas.dev' },
];
---
<BaseLayout>
  <h1>Bienvenido a mi portfolio</h1>
  <ul>
    {proyectos.map((p) => (
      <ProjectCard title={p.title} url={p.url} />
    ))}
  </ul>
</BaseLayout>

Decisiones y por qué:

  • El layout está en layouts/ porque define «la forma» común; técnicamente es un componente, la carpeta es semántica.
  • global.css se importa en el layout, no en cada página: al ser el ancestro común, una sola importación aplica a todo el sitio.
  • Las páginas solo declaran su contenido, envuelto en <BaseLayout>. Cambiar la cabecera una vez la cambia en todas las páginas.
  • Los assets «fijos» van a public/ (favicon, PDF); los datos y estilos van a src/ para que Astro los procese.

🏗️ Analogía: el plano del edificio

src/pages/ son las distintas viviendas (una por URL); layouts/ es la estructura de forjados y fachada que comparten; components/ son los muebles que puedes colocar en varias viviendas; public/ es el buzón y la placa con el nombre, que se ve tal cual desde la calle; y astro.config.mjs son las licencias y acometidas del edificio.

6 · Errores habituales

1. Poner una página en el sitio equivocado

Mal — la «página» no está en pages/, así que no es una ruta 
src/components/Contacto.astro
# ❌ Visitar /contacto da 404: estar en components/ no crea ninguna URL.
#    Ese archivo solo sirve para importarlo desde otra parte.
Bien — las rutas viven en src/pages/ 
src/pages/contacto.astro
# ✅ Ahora sí: el archivo crea la ruta /contacto.
# Si además quieres reutilizarlo como componente, impórtalo desde aquí.

2. Confundir public/ con src/

Mal — meter en PUBLIC lo que debe procesarse 
<!-- archivo colocado en public/hero.jpg -->
<img src="/hero.jpg" />
<!-- ❌ Astro NO lo optimiza, no lo redimensiona ni lo convierte a WebP.
      Se copia gigante y tal cual al build. -->
Bien — importar desde src/ para que se optimice 
---
import hero from '../assets/hero.jpg'; // se procesa y optimiza
---
<img src={hero.src} width={hero.width} height={hero.height} alt="Hero" />
<!-- ✅ Optimizado, con dimensiones y hash de caché (Módulo 6). -->

3. Duplicar el tsconfig.json sin extenderlo

Mal — config de TS a mano, desincronizada de Astro 
{
  "compilerOptions": { "target": "ESNext", "module": "ESNext" }
}
// ❌ Falta lo específico de Astro (tipos .astro, jsx, resolución de módulos)
Bien — heredar la plantilla oficial 
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}

Si necesitas un ajuste puntual, añade compilerOptions propios encima del extends; no reinventes la base.

7 · Ejercicio guiado

Objetivo: montar el esqueleto de un mini-sitio de tres rutas con un layout compartido, demostrando que la ubicación de cada archivo es lo que crea la estructura.

  1. Paso 1 — parte del proyecto de la lección anterior. Sitúate dentro de mi-primer-astro/ y arranca pnpm dev.
  2. Paso 2 — crea las carpetas. Dentro de src/ tendrás que crear layouts/ y components/ si no existen (algunas plantillas no las generan).
  3. Paso 3 — crea el layout base. Añade src/layouts/BaseLayout.astro con el esqueleto HTML y un <slot /> en el <main>.
  4. Paso 4 — crea dos páginas. Añade src/pages/blog.astro y src/pages/contacto.astro, cada una envolviendo su contenido en <BaseLayout>.
  5. Paso 5 — enlaza y navega. Añade una lista de enlaces <a href="/blog"> y <a href="/contacto"> en el layout. Comprueba en el navegador que las tres rutas cargan y comparten cabecera.
  6. Paso 6 — verifica el enrutado por archivos. Renombra contacto.astro a contacto-nuevo.astro y visita /contacto: debe dar 404. Visita /contacto-nuevo: existe. Vuelve a dejarlo como estaba.

Solución — el layout y una página:

src/layouts/BaseLayout.astro
---
// Esqueleto común: cabecera, navegación, contenido (slot) y pie.
---
<!DOCTYPE html>
<html lang="es">
  <head><meta charset="UTF-8" /><title>Mi sitio</title></head>
  <body>
    <header>
      <nav>
        <a href="/">Inicio</a>
        <a href="/blog">Blog</a>
        <a href="/contacto-nuevo">Contacto</a>
      </nav>
    </header>
    <main><slot /></main> <!-- contenido específico de cada página -->
    <footer>© 2026 Mi sitio</footer>
  </body>
</html>
src/pages/blog.astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
---
<BaseLayout>
  <h1>Blog</h1>
  <p>Entradas próximamente.</p>
</BaseLayout>

✅ Resultado esperado

Tres rutas (/, /blog, /contacto-nuevo) que comparten la misma cabecera y pie. Al renombrar un archivo, la URL cambia: acabas de comprobar con tus manos que el sistema de archivos es el router.

8 · Reto

🎯 Reorganiza sin romper

Partiendo del mini-sitio del ejercicio, haz una refactorización de estructura: mueve el contenido de la cabecera a un componente src/components/Header.astro y el pie a src/components/Footer.astro, y haz que BaseLayout.astro los importe y los coloque. Después crea una subcarpeta src/pages/proyectos/index.astro y comprueba qué URL genera. Documenta en un comentario por qué esa URL es la que es.

Pista: piensa en la diferencia entre src/pages/proyectos.astro (una URL /proyectos) y src/pages/proyectos/index.astro (también /proyectos). ¿Cuál te conviene si prevés añadir luego /proyectos/[id]? Razónalo antes de mirar el Módulo 2.

9 · Resumen

  • src/pages/ es la única carpeta reservada: cada archivo genera una URL según su ruta. Sin acentos ni su configuración aparte.
  • src/components/ y src/layouts/ son convenciones: componentes reutilizables y plantillas de página con <slot />.
  • public/ se copia tal cual al build (favicon, robots.txt); lo que deba optimizarse va en src/.
  • astro.config.mjs configura lo global: integraciones, plugins de Vite, site, SSR. No declara rutas.
  • tsconfig.json normalmente solo extends astro/tsconfigs/strict; no hay que reinventarlo.
  • Todo esto es convención sobre configuración: la ubicación manda, el archivo de config solo existe para lo global.

10 · Preguntas frecuentes

¿De verdad puedo renombrar components/ y layouts/?

Sí. Astro solo reserva src/pages/. Las carpetas components/, layouts/ y styles/ son convenciones para que el equipo se entienda, no requisitos técnicos. Dicho esto, respetarlas te alinea con la documentación y con el resto del ecosistema; romperlas solo añade ruido sin beneficio.

Si astro.config.mjs no declara rutas, ¿dónde las defino?

En ningún sitio: las define el sistema de archivos. Un archivo src/pages/about.astro es la ruta /about. Las rutas dinámicas usan corchetes ([slug].astro) y se resuelven con getStaticPaths (Módulo 2). La configuración queda para lo global: integraciones, adaptadores, build, site.

¿Por qué no poner todas las imágenes en public/ y olvidarme?

Porque pierdes la optimización de Astro: redimensionado, conversión a formatos modernos, dimensiones automáticas y hash de caché. Lo de public/ se sirve tal cual, sin procesar. Regla práctica: assets «fijos» (favicon, robots, PDF) a public/; imágenes de contenido a src/ e impórtalas.

¿Necesito TypeScript para seguir el curso?

No es obligatorio, pero sí muy recomendable y está previsto así en el curso. Astro lo soporta de serie en los archivos .astro y en las props, y las plantillas oficiales de tsconfig te dan tipado sin configuración. Lo usaremos sobre todo para tipar props y esquemas de colecciones, donde aporta muchísimo.

¿Qué es la carpeta .astro/ que a veces aparece?

Es una carpeta generada por Astro que contiene tipos e información interna (por ejemplo, los tipos de tus Content Collections). No se edita a mano y va en .gitignore. Por eso el tsconfig.json recomienda incluir .astro/types.d.ts: son tipos que Astro mantiene por ti.
