Qué es Astro

Módulo 0 · Preparación 🕐 25 minutos

1 · Introducción

Durante la última década aprendimos a construir aplicaciones de página única (SPA): una sola página HTML que se carga vacía y va pintando la interfaz con JavaScript en el navegador. Ese modelo es maravilloso para un panel de control lleno de botones, pero es terrible para un blog, una documentación o una tienda: enviar cientos de kilobytes de JavaScript para mostrar un texto que nunca cambia es un desperdicio.

Astro nace como respuesta a ese exceso. Es un framework web moderno cuyo lema podría resumirse en una frase: renderiza en el servidor todo lo que puedas, envía JavaScript al navegador solo donde de verdad haga falta. En esta lección entenderás qué es Astro, por qué existe, qué es una MPA frente a una SPA, qué significa la filosofía islands y por qué decimos que Astro es content-driven. Cerraremos con una comparación honesta frente a Next.js, Gatsby y Hugo/11ty.

🎯 Por qué existe esta lección

Todo el curso se apoya en una decisión de arquitectura: HTML primero, JavaScript solo donde se necesita. Si no entiendes de dónde viene ese enfoque, el resto (componentes, islas, hidratación, content collections) serán recetas que memorizas sin saber cuándo aplicarlas. Veinte minutos aquí te ahorran muchas dudas después.

Cuando la gente empieza con Astro comete tres errores típicos que veremos a lo largo del curso: creer que es «otro React más» (no lo es), meter todo el JavaScript de la aplicación sin pensar (rompe su ventaja), y confundirlo con un simple generador de sitios estáticos (puede mucho más: SSR, API endpoints, islas server-side).

2 · Teoría

Qué es Astro, en una definición honesta

Astro es un framework de construcción de sitios y aplicaciones web basado en HTML que se renderiza en el servidor (o en tiempo de build). Sus tres rasgos definitorios, que verás repetidos hasta la saciedad, son:

  • Zero JavaScript por defecto. Un componente Astro es HTML + una parte de servidor; el navegador recibe HTML puro. Cero runtime de framework si no lo pides explícitamente.
  • Islands architecture. La interactividad se añade por islas aisladas (un carrito, un buscador, un formulario) que se hidratan por separado.
  • Content-driven. Está pensado para sitios con contenido (blogs, docs, landings, e-commerce) como ciudadano de primera clase: Markdown, MDX y Content Collections.

Astro no es React, ni Vue, ni Svelte: Astro es su propio lenguaje de plantillas (archivos .astro). Lo interesante es que puede usar React, Vue, Svelte, Solid, Preact o Alpine dentro de él para las partes interactivas. Es decir, Astro no compite con esos frameworks por la misma capa: los usa como piezas.

MPA frente a SPA: dos formas de entregar la misma web

Hay dos grandes modelos para servir una interfaz:

  • MPA (Multi-Page Application): cada URL es un documento HTML completo que se renderiza en el servidor. El navegador pide la página, la pinta y ejecuta el poco JavaScript que necesite. Es el modelo de la web clásica (PHP, Rails, Hugo) y el que Astro abraza por defecto.
  • SPA (Single-Page Application): el servidor entrega un HTML casi vacío y un gran bundle de JavaScript. Ese JavaScript construye toda la interfaz en el navegador y gestiona la navegación sin recargar. Es el modelo de muchas apps React/Vue sin meta-framework.
MPA (Astro por defecto)                      SPA (React puro, por ejemplo)
────────────────────────────                 ─────────────────────────────
GET /            → HTML completo             GET /            → HTML casi vacío
GET /blog/post   → HTML completo             GET /blog/post   → HTML casi vacío
                   + poco JS                                   + bundle JS grande
En el servidor:  trabajo de render           En el navegador: mount + render
En el cliente:   casi nada                   En el cliente: todo

Ventajas:  primer pintado rápido,           Ventajas:  transiciones ricas,
           SEO trivial, poco CPU cliente               estado global sencillo

(salvo con View Transitions)                           mucho JS, batería/móvil

Astro no renuncia a las ventajas de la SPA: con las View Transitions API (Módulo 7) y la hidratación de islas, consigue navegación fluida sin enviar la aplicación entera al cliente. La clave es que el modelo por defecto sea la MPA y la interactividad sea la excepción.

🏝️ La analogía de las islas

Imagina un océano de HTML estático (barato, ligero, rápido) con unas pocas islas interactivas flotando en él (carrito, filtros, un mapa). El resto del océano no ejecuta nada; las islas se hidratan solo cuando hacen falta. En una SPA, todo el océano es una isla: has convertido el mar en hormigón interactivo.

La filosofía islands, en detalle

La idea, popularizada por Astro aunque no inventada por él, es la hidratación selectiva: enviar el HTML ya renderizado y adjuntar comportamiento JavaScript solo a los trozos que lo necesitan. Cada trozo es una isla autónoma.

Astro controla esto con directivas que se añaden al componente interactivo: client:load (hidrata en cuanto carga), client:idle (cuando el navegador está libre), client:visible (cuando entra en pantalla), client:media (según media query) y client:only (solo en cliente). Lo verás a fondo en el Módulo 4; por ahora quédate con la idea: tú decides cuándo y dónde se gasta el JavaScript.

Content-driven: el contenido manda

Decimos que Astro es content-driven porque trata el contenido como algo de primera clase: archivos Markdown y MDX, Content Collections tipadas con Zod, y la capacidad de importar contenido como datos para recorrerlo. En una app SPA típica, el contenido suele vivir en una API y se pide en cliente; en Astro, buena parte del contenido es el sitio y se compila a HTML en el build. Eso da tres beneficios enormes: rendimiento, SEO y simplicidad de despliegue (un CDN de estáticos).

📌 Cuándo usar Astro

Astro brilla en blogs, documentación, landings, portfolios, e-commerce y sitios de marketing, donde el contenido domina y la interactividad es puntual. Si necesitas una aplicación 100 % interactiva con estado complejo y miles de interacciones (un editor, un dashboard en tiempo real), un framework de aplicación como Next.js puede encajar mejor en el núcleo — aunque Astro puede incrustar esa app como isla cuando quieras lo mejor de ambos.

3 · Ejemplo mínimo

El componente Astro más pequeño posible es también, probablemente, el más revelador. Fíjate en que hay dos zonas separadas por las tres rayas (---), y ninguna de las dos es JavaScript de cliente.

src/pages/index.astro
---
// ─── Component Script (frontmatter) ───
// Todo lo que escribas aquí se ejecuta en el SERVIDOR / BUILD.
// Jamás llega al navegador. Date cuenta: es el sitio perfecto para
// la lógica de datos sin preocuparte por secretos ni peso.
const title = '¡Hola, Astro!';
const year = new Date().getFullYear(); // se evalúa al construir la página
---

<!-- ─── Component Template ─── -->
<!-- Esto es HTML. Se produce en el servidor y viaja ya montado -->
<html lang="es">
  <body>
    <!-- Interpolamos datos del script con llaves -->
    <h1>{title}</h1>
    <footer>© {year} — hecho con Astro</footer>
  </body>
</html>

<style>
  /* El CSS se extrae, se optimiza y se sirve como una hoja normal. */
  h1 { color: #ff5d01; font-family: system-ui, sans-serif; }
</style>

Línea por línea, lo importante:

  • Las rayas --- delimitan el component script. Es TypeScript/JavaScript que corre en tu máquina o en el servidor, nunca en el navegador del visitante.
  • const title, const year son variables de servidor. Si pones ahí un console.log, lo verás en tu terminal, no en la consola del navegador.
  • {title} es una expresión de plantilla: Astro sustituye la llave por el valor durante el render, dejando HTML plano.
  • <style> no se envía tal cual: Astro lo extrae, lo encapsula por defecto y lo optimiza. Cero JavaScript implicado.

💡 Comprueba la promesa

Cuando tengas el proyecto montado (lección siguiente), abre esta página, pulsa Ver código fuente en el navegador y busca JavaScript de Astro. No hay. El HTML ya viene con <h1>¡Hola, Astro!</h1> escrito. Eso es zero JavaScript por defecto.

4 · Ejemplo real

Un caso cercano a producción: una tarjeta de producto que muestra datos obtenidos de una API en build time y que incluye un botón «Añadir al carrito» interactivo. La gracia didáctica: casi toda la tarjeta es HTML estático y solo el botón es una isla de JavaScript.

src/components/ProductCard.astro
---
// ─── Servidor: pedimos los datos cuando se construye la página ───
// Este fetch ocurre en build (o en SSR). El navegador no lo ve.
const res = await fetch('https://fakestoreapi.com/products/1');
const product = await res.json();

// Formateamos el precio una sola vez, en el servidor.
const price = new Intl.NumberFormat('es-ES', {
  style: 'currency',
  currency: 'EUR',
}).format(product.price);
---

<article class="card">
  <!-- La imagen y los textos son HTML puro: no ejecutan JavaScript -->
  <img src={product.image} alt={product.title} width="180" height="180" />
  <h2>{product.title}</h2>
  <p class="price">{price}</p>

  <!-- AQUÍ vive la única isla interactiva del componente.
       client:visible significa: hidrátala solo cuando entre en pantalla.
       (En el Módulo 4 veremos React a fondo; hoy basta con la idea.) -->
  <AddToCart client:visible productId={product.id} />
</article>

<style>
  .card { border: 1px solid #ddd; border-radius: 12px; padding: 16px; }
  .price { font-weight: 700; }
</style>

Las decisiones y por qué importan:

  • El fetch está en el frontmatter. Se ejecuta en build/SSR. En el HTML final viaja el dato ya resuelto; no hay petición en cliente ni spinner.
  • El formateo (Intl) es de servidor. No enviamos la librería ni el cálculo al navegador; enviamos el resultado.
  • La tarjeta es HTML. Un buscador, un lector de pantalla o un móvil lento lo ven al instante.
  • La isla es mínima. Solo AddToCart trae JavaScript, y encima diferido con client:visible.

🧱 Analogía: ladrillos y enchufes

Un sitio en una SPA es una pared donde cada ladrillo lleva un enchufe por si algún día le conectas algo. Un sitio en Astro es la misma pared con enchufes solo donde de verdad vas a enchufar. Menos cableado, menos averías, menos coste.

6 · Errores habituales

1. Creer que el frontmatter corre en el navegador

Mal — guardar un secreto o esperar ver el log en la consola del navegador 
---
const apiKey = 'sk-live-9f3c...';        // ❌ parece que va al cliente... y algunos lo creen
console.log('esto aparece en la consola'); // ❌ esperan verlo en DevTools
---
<p>La clave es {apiKey}</p> <!-- ❌ ahora SÍ acaba en el HTML -->
Bien — el frontmatter es de servidor; solo se exporta lo que interpolas 
---
// ✅ El código corre en servidor/build, nunca en el navegador.
const apiKey = import.meta.env.SECRET_KEY; // se lee en build/SSR
// ✅ El log aparece en TU TERMINAL, no en DevTools.
console.log('build time');
// ✅ Solo lo que IMPRIMES en la plantilla sale al HTML. Nunca imprimas secretos.
---
<p>La página está servida</p>

Regla de oro: el frontmatter es un lugar seguro para secretos si no los interpolas. Lo que escribes en la plantilla sí viaja al navegador.

2. Convertir todo el sitio en una isla

Mal — hidratar todo el árbol por inercia de la SPA 
<Layout client:load>      <!-- ❌ el layout entero ya no es server-only -->
  <Header client:load />   <!-- ❌ hidratas cosas que no cambian -->
  <Content />              <!-- ❌ contenido estático ejecutando JS -->
</Layout>
Bien — las partes estáticas son componentes Astro; solo la isla se hidrata 
<Layout>
  <Header />                     <!-- ✅ server-only, HTML puro -->
  <Content />                    <!-- ✅ server-only, HTML puro -->
  <NewsletterForm client:visible /> <!-- ✅ única isla, y diferida -->
</Layout>

El indicador de que algo va mal: abres DevTools, ves mucho JavaScript y ninguno de sus efectos (botones, estado) se usaba realmente.

3. Confundir Astro con un simple generador de estáticos

Mal — «es como Hugo, solo HTML» 
"Astro solo genera HTML estático,
así que no puedo tener rutas de API ni login."
# ❌ Astro tiene endpoints, SSR con adaptadores,
#    middleware, sesiones, acciones y server islands.
Bien — Astro es estático por defecto y a la carta cuando lo pides 
export default defineConfig({ output: 'static' }); // por defecto
// se puede pasar a rendimiento bajo demanda (SSR) con un adaptador,
// sin renunciar al HTML pre-renderizado del resto del sitio.
# ✅ Lo verás en los módulos 5 y 8.

7 · Ejercicio guiado

Objetivo: aprender a razonar con la mentalidad de Astro clasificando partes de una web real. No hace falta escribir código todavía; el objetivo es que decidas dónde hay isla y dónde no.

Partimos de una web ficticia de una tienda de plantas con estas partes: (a) un buscador con autocompletado, (b) el listado de productos con foto y nombre, (c) el pie con el año y enlaces, (d) un botón de «añadir al carrito» que actualiza el contador de la cabecera, (e) el texto largo de la página de «Envíos y devoluciones».

  1. Paso 1 — marca lo que cambia sin recargar. Pregúntate: ¿esto tiene que reaccionar a un clic o a la escritura del usuario? El buscador (a) y el botón del carrito (d) sí. El listado (b), el pie (c) y las políticas (e) no.
  2. Paso 2 — decide qué puede ser HTML de servidor. Todo lo que no reacciona es componente .astro normal: el listado se genera en build desde los datos, el pie es HTML, las políticas son Markdown.
  3. Paso 3 — aísla las islas. El buscador es una isla client:idle (no urge hasta que el usuario quiere buscar). El botón del carrito es una isla client:load o client:visible, porque su estado es lo más crítico de la página.
  4. Paso 4 — declara el estado compartido. El contador del carrito y el botón deben ver el mismo estado. Mientras las islas están aisladas, eso se resuelve con un pequeño store compartido (lo verás en el Módulo 4). Anótalo, no lo implementes aún.
  5. Paso 5 — escribe la tabla de decisiones con tres columnas: Elemento, Tipo (HTML / isla + directiva), Motivo. Compárala con la solución de abajo.

Solución paso a paso. Tu tabla debería parecerse a esta:

ElementoTipoMotivo
Buscador con autocompletadoIsla React, client:idleNecesita estado y eventos, pero no es lo primero que se usa
Listado de productosAstro (HTML)Datos de build, sin interacción
Pie con año y enlacesAstro (HTML)Estático puro
Botón «añadir al carrito»Isla React, client:visible + storeInteractivo; su estado lo comparte con la cabecera
Página de envíos y devolucionesMarkdown (colección)Contenido editorial, sin lógica

✅ Resultado esperado

Tres de cinco elementos son HTML puro y solo dos son islas. Ese reparto —mayoría estática, minoría interactiva— es exactamente la mentalidad Astro. Si tu tabla hidrata casi todo, vuelve al Paso 1.

8 · Reto

🎯 Audita una web que conozcas

Elige un sitio real que uses a diario (un periódico, un panel de administración, tu banco) y hazle una auditoría islands: abre DevTools, mira cuánto JavaScript descarga y qué partes de la página son de verdad interactivas. Estima qué porcentaje del sitio podría ser HTML puro si se hubiera construido con la filosofía de Astro, y justifica en cinco líneas dónde pondrías tú las islas y con qué directiva client:*.

Pista: empieza por la pestaña Network filtrando por JS y compara el peso del bundle con el del HTML. Verás que muchas veces se envía más JavaScript que contenido. Piensa en la primera interacción del usuario: ¿un client:load mejora o empeora el tiempo hasta que puede interactuar?

9 · Resumen

  • Astro es un framework web que renderiza HTML en el servidor/build y envía zero JavaScript por defecto.
  • Su modelo por defecto es MPA (cada URL es HTML completo), frente al modelo SPA (una página vacía que el cliente rellena con JS).
  • La filosofía islands añade interactividad en piezas aisladas que se hidratan a la carta con directivas client:*.
  • Es content-driven: Markdown, MDX y Content Collections son ciudadanos de primera clase, con enorme ventaja en rendimiento y SEO.
  • Frente a Next.js (SSR/hidratación completa), Gatsby (SSG React) y Hugo/11ty (SSG sin interactividad), Astro combina lo mejor: HTML ligero y la capacidad de usar React/Vue/Svelte donde haga falta.

10 · Preguntas frecuentes

Si Astro es una MPA, ¿pierdo la navegación fluida sin recargas?

No. Con las View Transitions API (que verás en el Módulo 7) Astro intercepta la navegación y anima la transición entre páginas sin recargar el documento completo, pero sin convertirlo todo en una SPA. Conservas el HTML por página y ganas fluidez. Es lo mejor de los dos mundos cuando se usa con criterio.

¿Astro sustituye a React?

No, lo usa. Astro es el framework del sitio (rutas, contenido, render, build) y React (o Vue, Svelte, Solid…) es una pieza que puedes incrustar como isla interactiva. En este curso usarás React solo como islands, nunca como la arquitectura completa del sitio.

¿Astro es solo para sitios estáticos?

No. Por defecto genera estáticos (SSG), pero con un adaptador puedes activar render bajo demanda (SSR), escribir endpoints de API, usar middleware, cookies y sesiones. Lo verás en los módulos 5 y 8. La ventaja es que eliges por ruta: unas páginas pre-renderizadas y otras dinámicas en el mismo proyecto.

¿Merece la pena si mi proyecto ya está en Next.js?

Depende del tipo de proyecto. Si es un sitio de contenido (blog, docs, marketing) y la mayor parte del JavaScript que envías no se usa, Astro puede recortar mucho peso y simplificar el despliegue. Si es una aplicación muy interactiva donde casi todo el árbol necesita estado, migrar puede no compensar. La pregunta clave es: ¿cuánto de mi página es HTML que no cambia?

¿Qué significa exactamente «content-driven»?

Que el contenido es la materia prima del sitio, no un añadido. Astro te da Markdown/MDX, colecciones tipadas con Zod y la posibilidad de importar y recorrer contenido como datos, todo renderizado a HTML en el build. Frente a un enfoque donde pides el contenido en cliente a una API, aquí el contenido es el HTML servido: más rápido, mejor indexado y más fácil de cachear en un CDN.
