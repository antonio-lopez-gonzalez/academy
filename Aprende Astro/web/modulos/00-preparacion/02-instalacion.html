Instalación: Node, pnpm, Vite y primer proyecto

Módulo 0 · Preparación 🕐 35 minutos

1 · Introducción

Antes de escribir una sola línea de Astro necesitas un entorno que funcione. En esta lección montamos la base: Node.js (el motor que ejecuta JavaScript fuera del navegador), pnpm (el gestor de paquetes que usaremos en todo el curso) y el wizard oficial de Astro para crear un proyecto. Terminaremos entendiendo qué hace exactamente cada comando (dev, build, preview) y por qué Astro lleva Vite dentro.

Parece una lección «de trámite», pero no lo es: la mitad de los problemas de quien empieza con Astro son de entorno (una versión de Node vieja, dos gestores de paquetes mezclados, un pnpm dev que en realidad no existe). Vamos a dejarlo blindado.

🎯 Por qué existe esta lección

Porque todo el curso se ejecuta con pnpm (nunca npm) y Astro 5 exige una versión reciente de Node. Si partes de un entorno bien hecho, cada ejemplo posterior simplemente funciona. Si no, perderás horas persiguiendo errores que no tienen nada que ver con Astro.

2 · Teoría

Node.js: el motor

Astro es una herramienta de línea de comandos escrita en JavaScript. Para ejecutarla necesitas Node.js instalado. No es un detalle menor: cada versión de Node trae un JavaScript distinto. Astro 5 requiere una versión moderna y par (las impares son experimentales y no se soportan). Concretamente, la documentación actual pide Node 22.12.0 o superior.

Puedes comprobar tu versión en la terminal:

Terminal
# Muestra las dos versiones instaladas en el sistema
node --version   # debe imprimir v22.12.0 o superior (v24, por ejemplo)
pnpm --version   # debe imprimir una versión 9.x o superior

💡 Tip: usa un gestor de versiones

En lugar de instalar Node «a pelo», usa fnm o nvm. Así puedes tener Node 22 para un proyecto y Node 20 para otro, y cambiar con un comando. Cuando clones un proyecto Astro, un archivo .nvmrc o un campo engines en package.json te dirá qué versión usar.

pnpm: por qué y no npm

Un gestor de paquetes descarga las dependencias de tu proyecto (Astro, React, Tailwind…) y las guarda en node_modules. Usaremos pnpm por tres motivos muy concretos:

  • Espacio: guarda cada paquete una sola vez en un almacén global y crea hard links. Si tienes diez proyectos Astro, no tendrás diez copias idénticas.
  • Velocidad: instala más rápido que npm, sobre todo en el segundo proyecto.
  • Rigor: es estricto con las dependencias fantasma (paquetes que usas sin declararlos). Esto produce proyectos más correctos y reproducibles.

En todo el curso escribiremos pnpm add, pnpm install, pnpm dev… Nunca npm. Mezclar gestores es una fuente clásica de node_modules inconsistentes.

Instalar pnpm

La forma recomendada hoy es Corepack, que viene con Node y activa el pnpm que declare tu proyecto:

Terminal
# Opción A (recomendada): activar pnpm mediante Corepack
corepack enable pnpm

# Opción B: instalar pnpm de forma global (si Corepack no está disponible)
npm install -g pnpm

# Comprobar que funciona
pnpm --version

Fíjate en el matiz: usamos npm solo para instalar la herramienta global pnpm. A partir de ahí, todos los comandos del proyecto son pnpm.

Astro y Vite: quién hace qué

Aquí conviene entender la arquitectura por dentro, porque explica el comportamiento del servidor de desarrollo. Astro no reinventa el bundler: se apoya en Vite, una herramienta de desarrollo y construcción ultrarrápida.

       TÚ                                    ASTRO                          VITE
  ┌─────────────┐                   ┌───────────────────┐         ┌──────────────────┐
  │  pnpm dev   │──── arranca ─────▶│  dev server Astro │──usa───▶│  Vite dev server │
  └─────────────┘                   │  (HMR, routing)   │         │  (esbuild, HMR)  │
                                    └─────────┬─────────┘         └──────────────────┘
                                              │ compila .astro, resuelve imports,
                                              │ inyecta datos de server
  ┌─────────────┐                   ┌─────────▼─────────┐         ┌──────────────────┐
  │ pnpm build  │──── produce ─────▶│  build de Astro   │──usa───▶│  Rollup (bundle) │
  └─────────────┘                   │  estáticos/SSR    │         │  minifica/empaqueta│
                                    └───────────────────┘         └──────────────────┘

En desarrollo, Vite transforma cada archivo a medida que el navegador lo pide (native ESM) y aplica HMR (Hot Module Replacement): al guardar un archivo, el navegador cambia solo esa parte, sin recargar entera. En el build, Vite usa Rollup para empaquetar y minificar el resultado. Tú casi nunca tocas Vite directamente… salvo en astro.config.mjs y en la carpeta src/, donde import.meta.glob, variables de entorno VITE_* y plugins de Vite están a tu disposición.

ComandoQué haceCuándo usarlo
pnpm devServidor de desarrollo con HMR en localhost:4321Mientras construyes; recarga al guardar
pnpm buildRenderiza el sitio y lo empaqueta en dist/Antes de publicar; valida errores de producción
pnpm previewSirve el contenido de dist/ localmentePara comprobar cómo quedará lo publicado
pnpm astro …Lanza la CLI de Astro directamenteComandos concretos (astro add, astro check)

3 · Ejemplo mínimo

El camino más corto desde cero hasta una web funcionando son cuatro comandos. El wizard de Astro te irá preguntando cosas; las veremos justo debajo.

Terminal
# 1. Crear el proyecto: no hace falta crear la carpeta antes.
#    El sufijo @latest garantiza que usas la última versión del asistente.
pnpm create astro@latest mi-primer-astro

# 2. Entrar en la carpeta recién creada
cd mi-primer-astro

# 3. Arrancar el servidor de desarrollo (por defecto en http://localhost:4321)
pnpm dev

# 4. (En otra terminal, cuando quieras) generar la versión de producción
pnpm build

Qué responde el asistente, y por qué:

  • «Where should we create your new project?» → la carpeta destino (aquí mi-primer-astro).
  • «How would you like to start your new project?» → plantilla. Elige Empty para empezar limpio o Basics para ver un ejemplo mínimo ya montado.
  • «Install dependencies?» → sí. Equivale a un pnpm install posterior.
  • «Initialize a new git repository?» → sí, para tener control de versiones desde el minuto uno.
  • «How strict should TypeScript be?» → Strict es un buen equilibrio; fomentaremos TypeScript en todo el curso.

📌 Puerto 4321

Astro usa el puerto 4321 por defecto. Si está ocupado, sube al 4322 automáticamente. En la terminal verás la URL exacta; cópiala tal cual.

4 · Ejemplo real

Un flujo de trabajo profesional: crear el proyecto, añadir una integración, comprobar el build y previsualizarlo. Aquí verás cómo se encadenan las piezas de verdad, incluyendo cómo añadir React (que usaremos para islas) sin escribir configuración a mano.

Terminal
# ── 1. Crear el proyecto con la plantilla "Basics" y TypeScript estricto ──
pnpm create astro@latest portafolio -- --template basics --typescript strict

# ── 2. Entrar y añadir una integración oficial ──
cd portafolio
pnpm astro add react      # añade React + su configuración al vuelo

# ── 3. Ver qué versión de Astro y de React han quedado instaladas ──
pnpm list astro react

# ── 4. Revisar tipos ANTES de construir (muy útil con TypeScript) ──
pnpm astro check

# ── 5. Construir para producción y previsualizar el resultado ──
pnpm build
pnpm preview

Decisiones y qué está pasando por debajo:

  • --template basics usa una plantilla oficial; --typescript strict responde de antemano a una pregunta del asistente, ideal para scripts no interactivos.
  • pnpm astro add react hace tres cosas: instala el paquete, añade @astrojs/react al array integrations de astro.config.mjs y ajusta el tsconfig.json si hace falta. Es la forma idiomática de integrar.
  • pnpm astro check ejecuta el chequeo de tipos sobre archivos .astro y .ts. Detecta errores de props antes del build; es el «linter» de tipos del curso.
  • pnpm build genera la carpeta dist/ con HTML listo para un CDN. pnpm preview sirve ese dist/ para verificar que nada se rompió al compilar (a veces un error solo aparece en producción).
astro.config.mjs (tras `astro add react`)
// defineConfig aporta autocompletado y validación de tipos a la config.
import { defineConfig } from 'astro/config';
// La integración de React la añadió `astro add` por nosotros.
import react from '@astrojs/react';

// https://astro.build/config
export default defineConfig({
  integrations: [react()], // cada integración se "enchufa" aquí
});

💡 DevTools: dónde mirar

Con pnpm dev en marcha, abre DevTools → pestaña Console: los errores de sintaxis de Astro aparecen ahí y en la terminal, con archivo y línea. La pestaña Network te deja comprobar el peso del HTML (peso ligero: es Astro funcionando). Y el Dev Toolbar de Astro aparece flotando en la esquina inferior de la página.

6 · Errores habituales

1. Mezclar npm y pnpm

Mal — dos gestores sobre el mismo proyecto 
pnpm install       # crea pnpm-lock.yaml y node_modules de pnpm
npm install axios  # ❌ ahora tienes package-lock.json también
# Resultado: dependencias fantasma, versiones cruzadas, build inestable.
Bien — un solo gestor, un solo lockfile 
# Si venías de npm, borra el lockfile viejo una vez:
rm -rf node_modules package-lock.json
pnpm install
# A partir de aquí, SIEMPRE pnpm:
pnpm add axios

2. Node demasiado antiguo

Mal — versión de Node no soportada 
node --version
# v16.20.0        ❌ Astro 5 no arranca: pide 22.12.0 o superior
pnpm dev
# Error: Astro requires Node v22.12.0 or higher
Bien — versión reciente y par 
# Con fnm:
fnm install 22
fnm use 22
node --version
# v22.12.0        ✅
pnpm dev

Recuerda: las versiones impares (v23, v25…) son de desarrollo y no están soportadas.

3. Confundir dev con build

Mal — medir el rendimiento en el servidor de desarrollo 
"Mi web va lenta y el bundle pesa mucho."
# ❌ Estabas mirando `pnpm dev`, que sirve módulos sin minificar
#    y con HMR: NO representa lo que verá el usuario.
Bien — medir sobre el build real 
pnpm build     # genera dist/ optimizado
pnpm preview   # sirve dist/ tal cual irá a producción
# Ahora sí: mide peso y tiempos sobre lo publicado.

7 · Ejercicio guiado

Objetivo: crear tu primer proyecto Astro, arrancarlo y comprobar con tus propios ojos la promesa de «zero JavaScript por defecto».

  1. Paso 1 — comprueba el entorno. En la terminal ejecuta node --version y pnpm --version. Anota las versiones. Si Node es inferior a 22.12.0, actualízalo antes de continuar.
  2. Paso 2 — crea el proyecto. Ejecuta: 
    pnpm create astro@latest mi-primer-astro
    Elige la plantilla Empty, acepta instalar dependencias, inicializar git y TypeScript strict.
  3. Paso 3 — explora antes de tocar. Entra en la carpeta y abre src/pages/index.astro, astro.config.mjs y tsconfig.json. Reconoce las tres piezas que verás en detalle en la lección siguiente.
  4. Paso 4 — arranca el servidor. Ejecuta pnpm dev y abre http://localhost:4321. Deja el navegador abierto con DevTools.
  5. Paso 5 — verifica el HTML y el JavaScript. Haz Ctrl+U (ver código fuente) y confirma que el <h1> ya viene escrito en el HTML. Luego abre DevTools → Network → filtra por JS y observa que no hay bundles de framework.
  6. Paso 6 — prueba el HMR. Edita el texto del <h1> en index.astro y guarda. El navegador debe reflejarlo al instante sin recargar entera la página.
  7. Paso 7 — construye y previsualiza. Para el servidor (Ctrl+C), ejecuta pnpm build y luego pnpm preview. Inspecciona la carpeta dist/: verás HTML plano.

Solución — qué deberías comprobar. Al terminar, tu proyecto debe tener:

Estructura esperada (resumen)
mi-primer-astro/
├── astro.config.mjs      # configuración (vacía o mínima al inicio)
├── tsconfig.json         # extend de "astro/tsconfigs/strict"
├── package.json          # scripts: dev, build, preview
├── pnpm-lock.yaml        # lockfile versionado
├── public/               # assets sin procesar (favicon...)
├── src/
│   └── pages/
│       └── index.astro   # tu primera página
└── dist/                 # (tras `pnpm build`) HTML listo para publicar

✅ Resultado esperado

Un proyecto que arranca con pnpm dev, cuyo index.astro se ve ya renderizado en el código fuente de la página, y cuya carpeta dist/ contiene HTML tras el build. Si el HTML del código fuente no contiene tu texto, revisa que estás mirando el puerto correcto o que no hay un error en la terminal.

8 · Reto

🎯 Un script de arranque reproducible

Crea un segundo proyecto Astro, pero esta vez sin responder al asistente a mano: usa solo banderas de la CLI (--template, --typescript, --no-git, --install, según necesites) para que el comando se pueda copiar y pegar en cualquier máquina. Después añade un archivo .nvmrc con la versión de Node que usas y un campo engines en package.json que la declare. El objetivo: que otra persona clone tu comando y obtenga exactamente el mismo entorno.

Pista: consulta pnpm create astro --help para descubrir todas las banderas disponibles. Y recuerda: un .nvmrc solo lo respetan herramientas como fnm/nvm; el campo engines es informativo para el gestor de paquetes. Investiga qué hace cada uno y por qué conviene tener los dos.

9 · Resumen

  • Node.js es el motor; Astro 5 pide Node 22.12.0 o superior (versiones pares).
  • pnpm es el gestor del curso: rápido, ahorra disco y es estricto con dependencias. Nunca mezcles gestores.
  • pnpm create astro@latest crea el proyecto con un asistente; las banderas permiten hacerlo sin interacción.
  • Los tres comandos clave: pnpm dev (desarrollo con HMR), pnpm build (genera dist/), pnpm preview (sirve el build).
  • Vite es el motor por debajo: servidor de desarrollo y HMR en dev, Rollup en el build. Los errores de entorno (Node viejo, gestores mezclados) son la causa nº 1 de frustración al empezar.

10 · Preguntas frecuentes

¿Puedo usar npm si ya lo tengo todo montado con npm?

Técnicamente sí: Astro funciona con npm, yarn o pnpm. Pero este curso usa pnpm en todos los comandos por coherencia y porque la documentación de Astro también lo soporta oficialmente. Lo importante es no mezclar: elige uno y no generes dos lockfiles en el mismo proyecto.

El puerto 4321 está ocupado, ¿qué hago?

Astro buscará otro puerto automáticamente y te mostrará la URL en la terminal; úsala. Si quieres fijar puerto, puedes arrancar con pnpm dev --port 3000 o configurarlo en astro.config.mjs con la opción server.port. Cuando veas «404» o «página en blanco», lo primero que debes comprobar es que estás abriendo la URL correcta.

¿Para qué sirve pnpm preview si ya tengo pnpm dev?

Porque son dos cosas distintas. dev sirve tus fuentes sin optimizar y con HMR: es cómodo para desarrollar, pero no representa el resultado publicado. preview sirve el contenido real de dist/, ya minificado y empaquetado. Mide rendimiento y verifica el sitio final siempre con build + preview.

¿Tengo que aprender Vite para usar Astro?

No para empezar: Astro te da una capa por encima y casi nunca tocas Vite directamente. Pero conviene saber que existe, porque algunos conceptos vienen de ahí: import.meta.glob, variables VITE_*, plugins y configuraciones de build. Cuando el curso mencione algo «de Vite», ya sabrás a qué capa pertenece.

¿Qué pasa con Corepack? A veces no está disponible

Corepack viene incluido en Node y es la forma recomendada de activar pnpm sin instalar nada global, pero algunas distribuciones lo traen desactivado o retirado. Si corepack enable pnpm no funciona, instala pnpm con npm install -g pnpm. Es el único uso legítimo de npm en este curso: instalar la herramienta global.
