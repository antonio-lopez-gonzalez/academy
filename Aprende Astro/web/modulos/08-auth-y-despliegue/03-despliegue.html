Despliegue en Vercel, Netlify y Cloudflare

Módulo 8 · Auth y Despliegue 🕐 35 minutos

1 · Introducción

Tienes la aplicación hecha: páginas, colecciones, islas, endpoints y autenticación. Llega el momento de que el mundo la vea. Desplegar en Astro es, casi siempre, conectar un repositorio a una plataforma y pulsar un botón. Pero debajo de ese botón hay una decisión que marca la diferencia: qué parte del sitio se genera en el build y qué parte se genera en el servidor, y qué adaptador le dice a Astro cómo ejecutarse en esa plataforma.

Esta lección cierra el ciclo del módulo: del import.meta.env local a las variables del panel, del HTML estático a las funciones on-demand, y del dominio de prueba al dominio real.

¿Por qué existe esta lección? Porque un proyecto que solo funciona en localhost no está terminado. Y porque elegir mal el adaptador o la estrategia de render es la causa número uno de «funciona en local pero revienta en producción». Entender el triángulo renderizado · adaptador · plataforma te permite desplegar en cualquiera sin sorpresas.

2 · Teoría

El adaptador: el traductor entre Astro y la plataforma

Cuando tu build es puramente estático, Astro produce una carpeta de ficheros (dist/) que cualquier servidor web sabe servir. No necesitas nada más. Pero en cuanto usas SSR o server islands, alguien tiene que ejecutar tu código en cada petición, y cada plataforma lo hace a su manera. El adaptador adapta la salida de Astro a esa manera.

Estático vs SSR al desplegar: dónde vive cada página

Un mismo proyecto Astro produce, tras el build, dos tipos de artefactos:

  • Ficheros estáticos → van al CDN y se sirven en milisegundos, sin coste de cómputo.
  • Funciones (una por ruta dinámica, o agrupadas) → se ejecutan bajo demanda en la plataforma.

El objetivo del despliegue profesional: empuja todo lo posible al estático y deja como función solo lo que de verdad lo requiere (auth, datos por usuario, formularios). Un blog bien hecho suele desplegarse con cerca del 100 % estático; una zona privada añade unas pocas funciones.

Qué cambia en cada plataforma, en la práctica

Cloudflare Workers no es Node. Corre sobre V8 y no tiene fs, ni sockets TCP crudos, ni algunos módulos nativos. Si tu código depende de librerías Node (bases de datos con drivers nativos, por ejemplo), Cloudflare exigirá alternativas (APIs basadas en HTTP, nodejs_compat para lo soportado). Elígelo cuando el estático y la red global son lo importante y tus funciones son sencillas.

El ciclo de despliegue

   git push  --->  plataforma detecta  --->  pnpm install
                                                |
                                                v
                                          pnpm build  (genera dist/)
                                                |
                          +---------------------+---------------------+
                          v                                           v
                  estaticos -> CDN                            funciones -> runtime
                          |                                           |
                          +---------------------+---------------------+
                                                v
                                         dominio (preview o prod)

Cada push a la rama principal suele desplegar a producción; cada pull request, a una URL de preview independiente. Esa es la razón por la que los secretos de producción viven en el panel: los previews pueden usar valores distintos.

3 · Ejemplo mínimo

Desplegar un sitio estático en Vercel. En este caso no hace falta adaptador: el resultado es una carpeta de ficheros y Vercel la sirve como CDN.

Terminal
# Genera la carpeta dist/ con el sitio completo.
pnpm build

# Se puede comprobar en local antes de subir:
pnpm preview
astro.config.mjs (sitio estático, sin adaptador)
import { defineConfig } from 'astro/config';

export default defineConfig({
  // Sin output ni adapter: 'static' por defecto.
  // Todo el sitio se genera en el build y se sirve desde el CDN.
  site: 'https://mi-blog.example', // necesario para sitemap y URLs absolutas
});

Pasos en la plataforma:

  1. Sube el proyecto a GitHub (sin node_modules ni dist).
  2. Conecta el repo en Vercel: importa el proyecto y deja el preset de Astro (framework: Astro).
  3. Push a main: Vercel ejecuta pnpm build y publica dist/. Ya tienes URL.

Fíjate en que no hubo que tocar el código. El modo estático es el camino feliz de Astro: cualquier plataforma lo sirve. La complejidad aparece solo cuando introduces SSR, y entonces entra el adaptador.

4 · Ejemplo real

Un sitio mixto: blog estático + zona privada con SSR, desplegado de tres formas. El código es el mismo; cambia el adaptador.

Opción A — Vercel

Terminal
# Instala el adaptador: actualiza astro.config.mjs por ti.
pnpm astro add vercel
astro.config.mjs
import { defineConfig } from 'astro/config';
import vercel from '@astrojs/vercel';

export default defineConfig({
  // 'static': estatico por defecto; las rutas con prerender=false
  // se convierten en funciones de Vercel automaticamente.
  output: 'static',
  adapter: vercel(),
  site: 'https://mi-blog.example',
});
src/pages/dashboard.astro (ruta que sera una funcion)
---
// Esta ruta necesita SSR: se desplegara como funcion de Vercel.
export const prerender = false;
const user = Astro.locals.user;
---
<h1>Panel de {user?.name}</h1>

Opción B — Netlify

Terminal
pnpm astro add netlify
astro.config.mjs
import { defineConfig } from 'astro/config';
import netlify from '@astrojs/netlify';

export default defineConfig({
  output: 'static',
  // Netlify Functions alojan las rutas dinamicas.
  adapter: netlify(),
  site: 'https://mi-blog.example',
});
netlify.toml (config opcional, util para fijar la version de Node)
[build]
  command = "pnpm build"
  publish = "dist"

[build.environment]
  # Fija la version de Node para que el build sea reproducible.
  NODE_VERSION = "22"

Opción C — Cloudflare

Terminal
pnpm astro add cloudflare
astro.config.mjs
import { defineConfig } from 'astro/config';
import cloudflare from '@astrojs/cloudflare';

export default defineConfig({
  output: 'static',
  // Workers sirven el estatico y ejecutan lo dinamico en el edge.
  adapter: cloudflare(),
  site: 'https://mi-blog.example',
});
wrangler.toml (config del Worker)
name = "mi-blog"
# Cloudflare Pages/Workers detecta el build de Astro.
compatibility_date = "2026-01-01"
# nodejs_compat habilita parte de las APIs de Node en el runtime V8.
compatibility_flags = ["nodejs_compat"]

Variables de entorno en cada plataforma

El .env local no se despliega. Los valores se definen en el panel y llegan al build y a las funciones:

Panel de la plataforma (ejemplo de valores)
# Publicas (llegan al cliente):
PUBLIC_SITE_NAME=Mi Blog Profesional
PUBLIC_API_URL=https://mi-blog.example

# Secretas (solo servidor):
DATABASE_URL=postgres://usuario:clave@host/db
SESSION_SECRET=un-secreto-largo-y-aleatorio

Buenas costumbres de despliegue: define los secretos también para los previews (o marca explícitamente que no los usen), separa entornos (development / preview / production) y fija la versión de Node en la plataforma. Un sitio desplegado con una versión distinta de Node a la local es una fuente clásica de «funciona en mi máquina».

Decisiones explicadas:

  • El mismo código, tres adaptadores: cambiar de plataforma es cambiar una dependencia y una línea de configuración.
  • output: 'static' con adaptador: mantiene el sitio estático por defecto y solo convierte en función las rutas con prerender = false.
  • Los secretos, en el panel: nunca en el repo ni en el build local de un PR ajeno.
  • site configurado: imprescindible para URLs absolutas, canonical, sitemap y RSS correctos.

6 · Errores habituales

Adaptador equivocado para la plataforma

✗ Incorrecto

// Desplegar esto en Vercel: genera un servidor Node que Vercel no espera.
import node from '@astrojs/node';
export default defineConfig({ output: 'server', adapter: node({ mode: 'standalone' }) });

✓ Correcto

// El adaptador de la plataforma de destino.
import vercel from '@astrojs/vercel';
export default defineConfig({ output: 'static', adapter: vercel() });

El adaptador define el formato del artefacto. Equivocarlo da errores de despliegue confusos, no de código.

Esperar SSR sin adaptador

✗ Incorrecto

// Rutas con prerender=false pero sin adapter: no hay donde ejecutarlas.
export default defineConfig({ output: 'static' }); // faltan adapter y dependencias

✓ Correcto

import vercel from '@astrojs/vercel';
export default defineConfig({ output: 'static', adapter: vercel() });

Toda ruta dinámica necesita un runtime. Sin adaptador, Astro no sabe dónde renderizarlas bajo demanda.

Meter secretos en el repositorio

✗ Incorrecto

// Commitear el .env con la clave real de produccion.
// SESSION_SECRET=...  <-- en git, visible para siempre

✓ Correcto

# En el .gitignore, y los valores en el panel:
.env
.env.local
# .env.example documenta los nombres, sin valores.

Los secretos de producción viven en el panel de la plataforma, no en el repo. Y si alguno llegó a commitearse, se rota.

Dar por hecho Node en Cloudflare

✗ Incorrecto

// Este import nativo de Node falla en el runtime V8 de Workers.
import { readFile } from 'node:fs/promises';
const data = await readFile('datos.json', 'utf8');

✓ Correcto

// Lee los datos en build (estaticos) o via fetch/API compatible.
const data = await fetch('https://datos.example/api').then((r) => r.json());

Cloudflare Workers no es Node. Antes de elegir plataforma, comprueba que tus dependencias de servidor son compatibles con su runtime.

Olvidar configurar site

✗ Incorrecto

// Sin site: canonical, sitemap y Open Graph generan URLs relativas/incorrectas.
export default defineConfig({ output: 'static' });

✓ Correcto

export default defineConfig({
  output: 'static',
  site: 'https://mi-blog.example', // URL absoluta de produccion
});

En producción, las URLs absolutas importan para SEO y para enlaces compartidos. Configurar site es parte del despliegue, no un extra.

7 · Ejercicio guiado

Objetivo: desplegar un sitio mixto (blog estático + una ruta SSR) en dos plataformas distintas sin cambiar el código de las páginas.

  1. Parte de un proyecto Astro con una página estática (index.astro) y una ruta SSR (dashboard.astro con export const prerender = false; y lectura de una cookie).
  2. Configura site en astro.config.mjs con la URL que tendrás en producción.
  3. Despliega en Vercel: 
    pnpm astro add vercel
pnpm build
    Sube el repo, conéctalo en Vercel con el preset de Astro y observa el primer deploy.
  4. Añade las variables en el panel (una pública y una secreta) y vuelve a desplegar. Comprueba que la ruta SSR las usa.
  5. Verifica la mezcla: abre DevTools → Network. La portada debe venir servida como HTML estático (cabecera de CDN), y /dashboard debe responder desde una función. Mira en el log del deploy cuántas funciones se generaron.
  6. Cambia a Netlify (o Cloudflare): instala su adaptador, ajusta astro.config.mjs y describe, sin tocar las páginas, qué cambia:
    • La dependencia del adaptador.
    • La línea adapter:.
    • Dónde defines las variables.
  7. Comprueba el dist/: tras pnpm build, inspecciona qué rutas quedaron como ficheros HTML en dist/ y cuáles como funciones. Ese mapa es tu coste de despliegue.

8 · Reto

🎯 Un despliegue con dominios, previews y rollback

Lleva el despliegue a nivel profesional sobre una de las plataformas:

  • Configura un dominio propio con HTTPS y decide si el www redirige al dominio raíz (o al revés). Comprueba el certificado y la redirección.
  • Provoca un deploy de preview desde una rama y verifica que usa variables de entorno distintas (por ejemplo, un PUBLIC_API_URL de staging).
  • Introduce a propósito un fallo (una variable que falta) y comprueba que el build de la plataforma falla y no publica nada. Luego arréglalo.
  • Haz un rollback a un deploy anterior y confirma que el sitio vuelve al estado previo sin tocar el código.
  • Añade cabeceras de seguridad desde el despliegue: Strict-Transport-Security, X-Content-Type-Options y, si procede, una Content-Security-Policy. Puedes hacerlo con un _headers (Netlify/Cloudflare) o config de Vercel.

Pista: cada plataforma tiene su fichero de configuración (vercel.json, netlify.toml, _headers, wrangler.toml). Empieza por el dominio y las previews; el rollback y las cabeceras son la guinda. Pregúntate, para cada cabecera de seguridad: ¿qué ataque concreto mitiga? Si no sabes responderte, investígalo antes de copiarla. Y recuerda: una CSP mal puesta te rompe el sitio tanto como un bug de código, así que pruébala primero en preview.

9 · Resumen

  • El adaptador traduce el build de Astro al formato de la plataforma; sin él no hay SSR.
  • Un mismo proyecto produce estático en CDN y funciones bajo demanda.
  • Empuja al estático el máximo posible; deja como función solo lo que necesita el servidor.
  • Vercel, Netlify y Cloudflare comparten flujo (push → build → deploy) pero difieren en runtime; Cloudflare Workers no es Node.
  • Las variables se definen en el panel, no en el repo; cada entorno tiene las suyas.
  • Configurar site y fijar la versión de Node forma parte de un despliegue reproducible.

10 · Preguntas frecuentes

¿Qué plataforma debería elegir?

Depende de tu tráfico y de tu equipo. Vercel tiene una experiencia de desarrollo excelente y previews muy cómodas; Netlify es muy completo en funciones y su plan gratuito es generoso; Cloudflare destaca en sitios con mucho tráfico estático por su red y su coste. Si tu proyecto es mayoritariamente estático, cualquiera funciona igual de bien: decide por ecosistema y equipo, no por benchmark. Y si necesitas control total, un servidor propio con @astrojs/node sigue siendo una opción válida.

¿Puedo desplegar en un VPS en lugar de una plataforma?

Sí. Con el adaptador de Node, tras pnpm build ejecutas node dist/server/entry.mjs detrás de un proxy inverso (Nginx, Caddy) que gestiona TLS. Es más trabajo (actualizaciones, certificados, escalado), pero te da control absoluto y suele salir más barato por volumen. Para la mayoría de proyectos, una plataforma gestionada ahorra tiempo y errores.

¿Cómo sé si mi sitio es realmente estático?

Mira la carpeta dist/ tras el build: verás ficheros .html por cada ruta estática. Las rutas con prerender = false no aparecen como HTML; se convierten en funciones. Otra señal: pide una página con curl -I y observa si responde el CDN (estático) o un runtime de función. Cuanto más contenido en dist/, más barato y rápido será tu despliegue.

¿Las variables del panel llegan al build o solo al runtime?

A ambos, según cómo se usen. El build las necesita si generas páginas estáticas que las leen en el frontmatter; las funciones las necesitan en tiempo de ejecución. En plataformas gestionadas se inyectan en ambos momentos. Ojo: una variable marcada como solo-runtime no estará disponible en el build y viceversa; conviene definirla como accesible en ambos.

¿Qué pasa con las imágenes y el dominio al migrar de plataforma?

Las imágenes optimizadas por Astro se generan en el build y se sirven desde el CDN de la plataforma, así que migran sin cambios. Lo único específico suele ser el dominio (apuntar el DNS a la nueva plataforma) y las variables de entorno, que hay que redefinir en el panel nuevo. Elegir site correctamente evita que enlaces y metadatos apunten al entorno antiguo.
