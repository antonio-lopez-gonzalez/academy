Autenticación con cookies y middleware

Módulo 8 · Auth y Despliegue 🕐 35 minutos

1 · Introducción

Hasta ahora tu sitio generaba HTML igual para todo el mundo: rápido, cacheable y sin memoria. Pero en cuanto aparece un usuario —un panel de administración, un área de clientes, un carrito— el HTML deja de ser el mismo para todos. Necesitas saber quién está pidiendo la página en cada petición, y eso obliga a dos cosas: guardar la identidad entre peticiones y comprobarla antes de renderizar.

Esa memoria la dan las cookies, la respuesta la dan las sesiones, y el control centralizado lo da el middleware de Astro. Juntos forman el esqueleto de cualquier autenticación web seria.

¿Por qué existe esta lección? Porque la autenticación es la frontera de seguridad de una aplicación y casi todo el mundo la improvisa mal: guarda la sesión en localStorage, confía en el cliente para decidir quién entra, o protege rutas una a una y se olvida de una. Aquí entenderás por qué HTTP no tiene memoria, por qué las cookies HttpOnly ganan a localStorage, y cómo el middleware convierte «proteger 20 rutas» en escribir una sola condición.

Requisito previo: la autenticación con sesión exige SSR. Una página estática se generó en el build y no puede leer la cookie del visitante. Necesitas un adaptador y output: 'server' (o prerender = false en las rutas privadas), como viste en el Módulo 5. Si eso aún no te suena, repásalo antes de seguir.

2 · Teoría

HTTP no tiene memoria: el problema del «segundo café»

El protocolo HTTP es sin estado (stateless): cada petición es independiente y el servidor no recuerda la anterior. Es una decisión de diseño brillante —permite escalar a millones de usuarios— pero incómoda para la vida real.

Analogía: imagina un camarero con amnesia que atiende cada pedido como si fuese la primera vez. Para un sitio público, perfecto. Pero si vuelves al día siguiente y quieres «lo mismo que ayer, mesa a nombre de Ana», el camarero necesita un carné de cliente que le entregues en cada visita. Ese carné es la cookie.

Cookies: el carné que viaja en cada petición

Una cookie es un pequeño par clave/valor que el servidor envía en la cabecera Set-Cookie y que el navegador devuelve automáticamente en la cabecera Cookie de cada petición a ese mismo dominio. No es una API de JavaScript: es un mecanismo del protocolo, y por eso funciona incluso antes de que tu código se ejecute.

  Navegador                                   Servidor
     |   GET /login (credenciales)               |
     |------------------------------------------>|
     |                                           | verifica usuario
     |   Set-Cookie: session=abc123; HttpOnly    |
     |<------------------------------------------|
     |                                           |
     |   GET /dashboard                          |
     |   Cookie: session=abc123                  |  <- el navegador lo pone solo
     |------------------------------------------>|
     |                                           | lee la cookie -> sabe quien eres
     |   200 OK (HTML del panel)                 |
     |<------------------------------------------|

Los atributos de una cookie no son decorativos: cada uno cierra una puerta a un ataque.

AtributoQué hacePor qué importa
HttpOnlyJavaScript no puede leerla (document.cookie no la ve)Frena el robo de sesión por XSS
SecureSolo se envía por HTTPSEvita que viaje en claro por la red
SameSite=Lax/StrictLimita el envío en peticiones entre sitiosMitiga el CSRF
PathLimita a qué rutas se envíaReduce exposición (p. ej. /admin)
Max-Age / ExpiresCuánto vive la cookieControla el cierre de sesión

Sesiones: el carné no lleva tu vida dentro

Hay dos filosofías para diseñar ese carné:

EnfoqueQué guarda la cookieVentajaInconveniente
Sesión opaca (server-side) Un id aleatorio; los datos viven en el servidor Revocable al instante; nada sensible en el cliente Requiere almacén (memoria, Redis, base de datos)
Token firmado (JWT) El propio token con los datos, firmado Sin estado en el servidor; escala fácil Difícil de revocar; más cuidado con el tamaño y la verificación

Recomendación del curso: para una aplicación web con backend propio, empieza con sesión opaca: cookie HttpOnly con un id, y los datos en el servidor. Es la opción más simple de razonar y la más segura por defecto. El JWT brilla cuando tienes servicios independientes que deben validar la identidad sin hablar entre ellos.

El middleware: la aduana entre la petición y tus páginas

En Astro, el middleware es un fichero src/middleware.ts que se ejecuta en cada petición, antes de renderizar cualquier página. Recibe un context, puede inspeccionar la petición, y decide: o llama a next() para continuar, o corta y devuelve otra cosa (por ejemplo una redirección).

  Petición
     |
     v
  +------------------+   redirige?  +-------------+
  |  middleware.ts   |------------->|  /login     |
  |  (la aduana)     |              +-------------+
  +------------------+
     | next()
     v
  +------------------+
  |  pagina .astro   |   lee context.locals.user
  +------------------+

Su superpoder es context.locals: un objeto que el middleware rellena y que todas las páginas pueden leer. Así la identidad se resuelve una vez y no en cada página.

src/middleware.ts
import { defineMiddleware } from 'astro:middleware';

// El middleware corre en CADA peticion, antes de renderizar la pagina.
export const onRequest = defineMiddleware(async (context, next) => {
  // Leemos la cookie de sesion (si existe).
  const sessionId = context.cookies.get('session')?.value;

  // Guardamos al usuario en locals: cualquier pagina lo vera como Astro.locals.user.
  context.locals.user = sessionId ? { id: sessionId, name: 'Ana' } : null;

  // Continuamos hacia la pagina o el endpoint correspondiente.
  return next();
});

El middleware no «protege» nada por sí solo. Es un sitio donde escribir las reglas. Su ventaja es que centraliza esas reglas en un único lugar, en vez de repetirlas al principio de cada página.

Proteger rutas: redirigir en el servidor, nunca ocultar en el cliente

El patrón es siempre el mismo: si la ruta es privada y no hay usuario, se redirige antes de generar el HTML. El navegador jamás recibe el contenido privado.

src/middleware.ts (guardia centralizada)
import { defineMiddleware } from 'astro:middleware';

// Rutas que exigen sesion iniciada.
const PROTECTED = ['/admin'];

export const onRequest = defineMiddleware(async (context, next) => {
  const user = context.cookies.get('session')?.value
    ? { name: 'Ana' }
    : null;
  context.locals.user = user;

  const needsAuth = PROTECTED.some((p) => context.url.pathname.startsWith(p));

  // Si la ruta es privada y no hay usuario, cortamos con una redireccion.
  if (needsAuth && !user) {
    return context.redirect('/login');
  }

  return next();
});

Nunca protejas escondiendo el enlace. Ocultar el botón «Admin» en el HTML no protege nada: cualquiera puede escribir la URL a mano. La autorización ocurre en el servidor, con la lógica del middleware y de las páginas. Todo lo que llega al navegador es público por definición.

3 · Ejemplo mínimo

El ejemplo más pequeño: una página que poner una cookie y una página que la leer. Con esto ya entiendes el mecanismo completo.

src/pages/set-cookie.astro
---
// En SSR podemos manipular cookies del servidor.
// Esta pagina inicia una sesion de mentira para ver el mecanismo.
Astro.cookies.set('demo', 'hola', {
  path: '/',       // disponible en todo el sitio
  httpOnly: true,  // JS del navegador NO puede leerla
  sameSite: 'lax', // no se envia en peticiones cruzadas raras
  maxAge: 60 * 60, // 1 hora
});

// Redirigimos tras fijar la cookie.
return Astro.redirect('/read-cookie');
---
src/pages/read-cookie.astro
---
// El servidor lee la cookie que mando el navegador.
const value = Astro.cookies.get('demo')?.value ?? '(sin cookie)';
---
<h1>El valor de la cookie es: {value}</h1>

Fíjate en la asimetría: cualquier cookie definida como HttpOnly es invisible para tu JavaScript en el navegador. Si abres DevTools → Application → Cookies, la verás; si escribes document.cookie en la consola, no aparecerá. Esa invisibilidad es exactamente lo que queremos para la sesión.

4 · Ejemplo real

Ahora, el flujo completo de una autenticación sencilla pero honesta: formulario de login, endpoint que verifica credenciales y fija la cookie, middleware que protege el panel, y cierre de sesión.

  /login  --POST-->  /api/login  --Set-Cookie-->  navegador
     ^                    | verifica credenciales
     |                    v
     |              (aqui iria la base de datos)
     |                    
  /dashboard  --middleware mira la cookie--> pasa o redirige a /login
src/pages/api/login.ts (endpoint de login)
import type { APIRoute } from 'astro';

// Este endpoint corre en el servidor: recibe las credenciales del formulario.
export const POST: APIRoute = async ({ request, cookies, redirect }) => {
  const data = await request.formData();
  const email = String(data.get('email') ?? '');
  const password = String(data.get('password') ?? '');

  // En un proyecto real compararias contra la base de datos
  // aplicando hashing (bcrypt/argon2). Aqui lo simulamos.
  const valid = email === 'ana@example.com' && password === 'secreto123';

  if (!valid) {
    // No revelamos si fallo el email o la contrasena: misma respuesta.
    return redirect('/login?error=1');
  }

  // Creamos una sesion opaca: un id aleatorio. El dato "real" (quien es)
  // estaria en el servidor; aqui lo simplificamos.
  const sessionId = crypto.randomUUID();

  cookies.set('session', sessionId, {
    path: '/',
    httpOnly: true,                 // el JS del navegador no la puede leer
    secure: true,                   // solo por HTTPS (en produccion)
    sameSite: 'lax',                // mitigacion de CSRF
    maxAge: 60 * 60 * 24 * 7,       // 7 dias
  });

  return redirect('/dashboard');
};
src/middleware.ts
import { defineMiddleware } from 'astro:middleware';

export const onRequest = defineMiddleware(async (context, next) => {
  // Resolvemos la identidad UNA vez para toda la peticion.
  const sessionId = context.cookies.get('session')?.value;
  context.locals.user = sessionId ? { id: sessionId, name: 'Ana' } : null;

  // Guardamos solo /dashboard (y sus subrutas) bajo autenticacion.
  const isPrivate = context.url.pathname.startsWith('/dashboard');
  if (isPrivate && !context.locals.user) {
    return context.redirect('/login');
  }

  return next();
});
src/env.d.ts (tipar locals sin librerias extra)
// Ampliamos App.Locals para que TypeScript sepa que existe locals.user
// en todas las paginas. Sin esto, Astro.locals.user daria error de tipos.
declare namespace App {
  interface Locals {
    user: { id: string; name: string } | null;
  }
}
src/pages/dashboard.astro (ruta protegida)
---
// Esta ruta necesita SSR: depende de la cookie del usuario.
export const prerender = false;

// El middleware ya la protegio; aqui solo leemos la identidad.
const user = Astro.locals.user;
---
<html lang="es">
  <body>
    <h1>Bienvenida, {user?.name}</h1>
    <!-- El enlace hace POST a un endpoint: las acciones que cambian
         estado nunca deberian ser un GET navegable. -->
    <form method="POST" action="/api/logout">
      <button type="submit">Cerrar sesion</button>
    </form>
  </body>
</html>
src/pages/api/logout.ts
import type { APIRoute } from 'astro';

export const POST: APIRoute = async ({ cookies, redirect }) => {
  // Borrar la cookie del navegador.
  cookies.delete('session', { path: '/' });
  // Nota: si hubiera un almacen de sesiones, aqui lo invalidarias tambien.
  return redirect('/login');
};

Decisiones explicadas:

  • La cookie es HttpOnly: el JavaScript del navegador no puede leerla, así que un XSS no puede robar la sesión directamente.
  • Secure y SameSite: viaja solo por HTTPS y no se envía en peticiones cruzadas sospechosas.
  • La identidad vive en locals: el middleware la resuelve una vez; las páginas solo la leen.
  • La redirección ocurre en el servidor: el HTML privado nunca se genera para un usuario sin sesión.
  • Mensaje de error uniforme: no distinguimos «email no existe» de «contraseña mal», para no dar pistas a quien prueba credenciales.
  • Logout por POST: una acción que cambia estado no debe poder dispararse con un simple enlace o imagen.

Astro Actions (Astro 5): para formularios podrías usar actions en vez de un endpoint a mano. Defines la acción en src/actions/index.ts con un esquema Zod y Astro genera el endpoint, la llamada tipada desde el cliente y la validación. Aquí usamos endpoints clásicos para que veas el mecanismo «a pelo»; en el proyecto del módulo los combinamos.

5 · Buenas prácticas

HazEvitaPor qué
Cookies de sesión HttpOnly + Secure + SameSite Guardar el token en localStorage localStorage es legible por JavaScript: un XSS roba la sesión al instante
Id de sesión aleatorio y opaco Guardar el email o el rol dentro de la cookie sin firmar El cliente puede editar la cookie: si lleva el rol, cualquiera se hace admin
Centralizar la guardia en middleware.ts Repetir el if (!user) redirect al inicio de cada página Una sola regla, imposible olvidarse de una ruta nueva
Redirigir en el servidor antes de renderizar Renderizar el panel y ocultarlo con CSS/JS si no hay sesión El HTML privado llegaría igualmente al navegador: no es seguridad
Hashear contraseñas (bcrypt/argon2) y revalidar en servidor Comparar contraseñas en texto plano o validar solo en el cliente Una base de datos filtrada no debe revelar las contraseñas
Mensajes de error uniformes en login Decir «ese email no existe» Confirmar qué emails existen ayuda a atacantes a enumerar usuarios
Expiración razonable (Max-Age) y renovación Sesiones eternas sin caducidad Una cookie robada debe tener una ventana de uso limitada

6 · Errores habituales

Guardar la sesión en localStorage

✗ Incorrecto

// Cualquier script inyectado (XSS) puede leer esto y exfiltrar el token.
localStorage.setItem('token', sessionToken);

✓ Correcto

// La cookie HttpOnly la gestiona el SERVIDOR: el JS del navegador ni la ve.
cookies.set('session', sessionId, {
  path: '/', httpOnly: true, secure: true, sameSite: 'lax',
});

El token no debe ser accesible desde JavaScript. Que el navegador lo envíe automáticamente por el protocolo es una ventaja, no un problema.

Intentar leer una cookie HttpOnly desde el cliente

✗ Incorrecto

// Devuelve '' siempre: document.cookie NO ve las cookies HttpOnly.
const session = document.cookie.split('session=')[1];

✓ Correcto

---
// La sesion se lee en el SERVIDOR, donde sí es accesible.
const session = Astro.cookies.get('session')?.value;
---

Si necesitas la identidad en el cliente, pásala como dato del HTML renderizado (por ejemplo Astro.locals.user), no intentando leer la cookie.

Proteger rutas una a una

✗ Incorrecto

---
// Si mañana creas /admin/usuarios y olvidas esta linea, queda abierta.
if (!Astro.cookies.get('session')) return Astro.redirect('/login');
---

✓ Correcto

// Una unica lista de rutas protegidas en el middleware.
const PROTECTED = ['/admin', '/dashboard'];
if (PROTECTED.some((p) => context.url.pathname.startsWith(p)) && !user) {
  return context.redirect('/login');
}

Centralizar evita el error clásico: añadir una ruta privada y olvidar protegerla.

Confiar en una cookie manipulable

✗ Incorrecto

// El cliente puede reescribir esta cookie y ponerse role=admin.
const role = Astro.cookies.get('role')?.value; // "admin" falsificado

✓ Correcto

// La cookie solo lleva un id opaco; el rol se busca en el servidor.
const sessionId = Astro.cookies.get('session')?.value;
const user = sessionId ? await getUserFromStore(sessionId) : null; // rol real

Todo lo que llega del navegador es input no confiable. La autoridad se consulta siempre en el servidor.

8 · Reto

🎯 Sesiones reales con almacén en servidor y expiración deslizante

El ejemplo guarda el «usuario» directamente en locals a partir del id. Llévalo a un modelo de sesión de verdad:

  • Crea un almacén de sesiones en el servidor (un Map en memoria te vale para practicar) que asocie el sessionId a un usuario y a una fecha de expiración.
  • En el login, guarda la sesión en el almacén; en el middleware, búscala y comprueba que no ha caducado. Si caducó, borra la cookie y redirige a login.
  • Implementa expiración deslizante: cada petición válida renueva la expiración de la sesión.
  • Añade roles: distingue user y admin, y protege /admin solo para administradores (403 o redirección, tú decides).
  • En el logout, invalida la sesión en el almacén, no solo la cookie.

Pista: el middleware es el lugar natural para «resolver sesión → locals → comprobar permisos». Separa en funciones pequeñas (getSession(id), touchSession(id), destroySession(id)). Recuerda que un Map en memoria se pierde al reiniciar el servidor y no se comparte entre instancias: en producción usarías Redis o una tabla de base de datos. Piensa también qué cabecera Cache-Control NO debe tener una página privada.

9 · Resumen

  • HTTP es sin estado; las cookies aportan la memoria, viajando en cada petición.
  • Los atributos HttpOnly, Secure y SameSite son seguridad, no estilo.
  • La sesión opaca (id aleatorio + datos en el servidor) es el punto de partida recomendado.
  • El middleware (src/middleware.ts) es la aduana: resuelve la identidad una vez y la deja en context.locals.
  • Proteger una ruta = redirigir en el servidor, nunca ocultar en el cliente.
  • La autenticación exige SSR: un HTML estático no puede leer la cookie del visitante.

10 · Preguntas frecuentes

¿Puedo autenticar sin SSR, con solo HTML estático?

No de forma segura para contenido privado. Una página estática se generó en el build y no puede leer tu cookie, así que o el contenido privado es el mismo para todos (no tiene sentido) o llega al navegador y lo escondes con JavaScript. Lo segundo no es seguridad: cualquiera ve el HTML. Para autenticación real necesitas output: 'server' o, al menos, prerender = false en las rutas privadas. Lo bueno de Astro 5 es que solo esas rutas dejan de ser estáticas.

¿Sesión opaca o JWT? ¿Cuál elijo?

Si tu aplicación es una web con su propio backend, empieza con sesión opaca: es más fácil de revocar y no expone datos en la cookie. El JWT es útil cuando varios servicios independientes deben validar la identidad sin consultar un almacén compartido, o cuando tienes APIs consumidas por apps móviles. En ambos casos, guárdalo igualmente en una cookie HttpOnly; nunca en localStorage.

¿El middleware también sirve para dar cabeceras de seguridad o registrar peticiones?

Sí, y es uno de sus mejores usos. En onRequest puedes añadir cabeceras como X-Frame-Options, Content-Security-Policy o Cache-Control, o registrar métricas de cada petición. Como pasa por todas las rutas, es el punto ideal para políticas transversales. Todo lo que aplicarías «a toda la app» encaja aquí.

¿Dónde ejecuto la comprobación de la contraseña?

Siempre en el servidor, en un endpoint o una acción. El cliente envía la contraseña por HTTPS; el servidor la compara contra un hash (bcrypt, argon2) almacenado en la base de datos. Nunca guardes contraseñas en texto plano ni en la cookie, y evita registrar la contraseña en logs. La validación en cliente es solo UX; la autoridad es el servidor.

¿Cómo evito el CSRF con cookies?

Tres capas que se suman: SameSite=Lax (o Strict para acciones sensibles) en la cookie, usar métodos POST para todo lo que cambia estado, y un token CSRF en el formulario que el servidor verifica. Con SameSite ya bloqueas la mayoría de ataques; el token cubre los casos restantes. Astro Actions incluye protección CSRF por defecto en los envíos.
