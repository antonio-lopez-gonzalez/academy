Proyecto: formulario con islas React

Módulo 4 · Islands e Interactividad 🕐 45 minutos

1 · Introducción

Vas a construir, de principio a fin, un formulario de contacto interactivo implementado como una isla React dentro de una página Astro estática. Es el proyecto que cierra el Módulo 4 y el patrón que más veces repetirás en tu carrera: una página con mucho contenido estático y una única pieza que necesita estado.

El formulario incluirá: campos controlados, validación en el cliente, estados de envío (idle, submitting, success, error), accesibilidad y feedback visual. Aprenderás a dividir la responsabilidad entre Astro (estructura, SEO, contenido) y React (interacción), que es justo la frontera de la que hablábamos en la teoría.

¿Por qué este proyecto? Porque un formulario mal hecho es el clásico ejemplo de todo lo que puede salir mal: validación dispersa, estados sin gestionar, recargas indeseadas, accesibilidad olvidada, estilo desincronizado. Aquí lo harás una vez, bien, y lo reutilizarás para siempre. Además prepara el terreno para el Módulo 5, donde el envío apuntará a un endpoint real.

2 · Teoría

Qué es un «campo controlado» y por qué importa

En un formulario nativo, el navegador guarda el valor del <input>. En React, preferimos que el estado del componente sea la única fuente de verdad: el valor del input se lee del estado y cada pulsación lo actualiza. Esto se llama campo controlado.

Analogía: un campo no controlado es como una pizarra en la que el alumno escribe y tú solo miras al final. Un campo controlado es un dictado: cada palabra que el alumno escribe pasa por ti y tú decides cómo queda. Es más trabajo por pulsación, pero te permite validar, transformar y mostrar errores en tiempo real.

El ciclo de vida de un envío

Un formulario serio no tiene dos estados («vacío» y «enviado»), tiene cuatro:

  idle  --submit valido-->  submitting  --ok--->  success
    ^                            |
    |                            +--fallo-->     error
    |
    +------- editar de nuevo ---- success/error
EstadoQué ve el usuarioQué debes bloquear
idleFormulario normalNada
submittingBotón deshabilitado con «Enviando…»Evitar envíos duplicados
successMensaje de confirmaciónOcultar o reiniciar el formulario
errorMensaje de error + reintentoNo perder lo escrito

La frontera Astro/React en este proyecto

Dividimos responsabilidades con nitidez:

  • Astro (build time): la página, el titular, el texto, el layout, el SEO y dónde se coloca la isla.
  • React (cliente): el formulario, el estado de los campos, la validación y el envío.

Directiva elegida: client:visible. El formulario casi siempre está al final de la página; no hay razón para hidratarlo antes de que el usuario llegue a él. Además, el HTML pre-renderizado ya muestra los campos vacíos, así que sin JavaScript la página sigue teniendo sentido.

Enviar datos: hoy simulamos, mañana conectamos

Enviar un formulario de verdad requiere un servidor que reciba el POST. En el Módulo 5 crearás ese endpoint (src/pages/api/contact.ts). Para que el proyecto funcione ya, aquí el envío se hará con una función sendToServer que simula la latencia y devuelve éxito. La estructura del código es idéntica a la real: solo cambiarás el cuerpo de esa función.

3 · Ejemplo mínimo

Antes del proyecto completo, el esqueleto mínimo: un campo controlado y un botón que muestra su valor. Es la base sobre la que crecerá todo.

src/components/TinyForm.tsx
import { useState } from 'react';

export default function TinyForm() {
  // El estado ES la fuente de verdad del campo.
  const [name, setName] = useState('');

  return (
    <form
      onSubmit={(e) => {
        // Evita que el navegador recargue la pagina (comportamiento nativo).
        e.preventDefault();
        alert(`Enviado: ${name}`);
      }}
    >
      <label htmlFor="name">Nombre</label>
      {/* value + onChange juntos = campo controlado. */}
      <input
        id="name"
        value={name}
        onChange={(e) => setName(e.target.value)}
      />
      <button type="submit">Enviar</button>
    </form>
  );
}

Las tres piezas que hacen que esto funcione:

  1. value={name}: el input refleja siempre el estado.
  2. onChange: cada tecla actualiza el estado; React re-renderiza y el input muestra el nuevo valor.
  3. e.preventDefault(): sin esto, el navegador recargaría la página y perderíamos el estado de la isla.

La isla completa, con validación, estados y accesibilidad:

src/components/ContactForm.tsx
import { useState, type FormEvent } from 'react';

// Tipo del formulario: un unico objeto de estado para los campos.
interface FormData {
  name: string;
  email: string;
  message: string;
}

// Estado de envio: un enum de cadenas evita booleanos contradictorios.
type Status = 'idle' | 'submitting' | 'success' | 'error';

// Validacion pura y reutilizable: devuelve un mapa de errores.
function validate(data: FormData): Partial<Record<keyof FormData, string>> {
  const errors: Partial<Record<keyof FormData, string>> = {};
  if (!data.name.trim()) errors.name = 'El nombre es obligatorio.';
  if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(data.email))
    errors.email = 'Introduce un email valido.';
  if (data.message.trim().length < 10)
    errors.message = 'El mensaje debe tener al menos 10 caracteres.';
  return errors;
}

// Simula el envio. En el Modulo 5 apuntara a un endpoint real con fetch.
async function sendToServer(data: FormData): Promise<void> {
  await new Promise((r) => setTimeout(r, 800)); // latencia simulada
  if (data.email.endsWith('@example.com')) throw new Error('Email rechazado'); // caso de fallo
}

export default function ContactForm() {
  // Un solo estado para todos los campos (objeto), mas el de estado de envio.
  const [form, setForm] = useState<FormData>({ name: '', email: '', message: '' });
  const [status, setStatus] = useState<Status>('idle');
  const [touched, setTouched] = useState(false); // ¿el usuario ya intento enviar?

  // Errores derivados: no es estado, se calcula del formulario actual.
  const errors = validate(form);
  const hasErrors = Object.keys(errors).length > 0;

  // Actualiza un campo concreto sin recrear el objeto entero a mano.
  function update(field: keyof FormData, value: string) {
    setForm((prev) => ({ ...prev, [field]: value }));
  }

  async function handleSubmit(e: FormEvent) {
    e.preventDefault();      // nunca recargar la pagina
    setTouched(true);        // a partir de aqui mostramos errores
    if (hasErrors) return;   // validacion en cliente antes de enviar

    setStatus('submitting');
    try {
      await sendToServer(form);
      setStatus('success');
    } catch {
      setStatus('error');
    }
  }

  // Si ya se envio con exito, mostramos confirmacion en vez del formulario.
  if (status === 'success') {
    return (
      <p role="status">¡Gracias, {form.name}! Hemos recibido tu mensaje.</p>
    );
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      {/* Cada campo: label asociado, valor controlado y error accesible. */}
      <div>
        <label htmlFor="name">Nombre</label>
        <input
          id="name"
          value={form.name}
          onChange={(e) => update('name', e.target.value)}
          aria-invalid={touched && !!errors.name}
          aria-describedby={errors.name ? 'name-error' : undefined}
        />
        {touched && errors.name && (
          <span id="name-error" role="alert">{errors.name}</span>
        )}
      </div>

      <div>
        <label htmlFor="email">Email</label>
        <input
          id="email"
          type="email"
          value={form.email}
          onChange={(e) => update('email', e.target.value)}
          aria-invalid={touched && !!errors.email}
          aria-describedby={errors.email ? 'email-error' : undefined}
        />
        {touched && errors.email && (
          <span id="email-error" role="alert">{errors.email}</span>
        )}
      </div>

      <div>
        <label htmlFor="message">Mensaje</label>
        <textarea
          id="message"
          rows={4}
          value={form.message}
          onChange={(e) => update('message', e.target.value)}
        />
        {touched && errors.message && (
          <span id="message-error" role="alert">{errors.message}</span>
        )}
      </div>

      {/* El boton refleja el estado de envio y se deshabilita mientras tanto. */}
      <button type="submit" disabled={status === 'submitting'}>
        {status === 'submitting' ? 'Enviando…' : 'Enviar'}
      </button>

      {status === 'error' && (
        <p role="alert">No se pudo enviar. Inténtalo de nuevo.</p>
      )}
    </form>
  );
}

Decisiones explicadas, una a una:

  • Validación como función pura validate: fuera del componente, fácil de testear y de reutilizar.
  • Errores derivados, no almacenados: se calculan del estado actual. Menos estado significa menos bugs de sincronización.
  • touched: no mostramos errores hasta el primer intento de envío; así no agobiamos al usuario que aún escribe.
  • status como enum: imposible tener «enviando y con éxito» a la vez. Un estado claro, una UI clara.
  • Accesibilidad: aria-invalid, aria-describedby y role="alert" hacen que el formulario sea usable con lector de pantalla.
  • sendToServer aislada: cuando conectes el endpoint real (Módulo 5), solo cambiará esa función.

5 · Buenas prácticas

HazEvitaPor qué
Un único objeto de estado para los campos Un useState por cada campo Un solo objeto se valida y se envía en bloque; escalar campos es trivial
Validación como función pura y reutilizable Mezclar la validación dentro del JSX Se testea aparte y se comparte entre cliente y servidor
Derivar errores del estado Guardar los errores en otro useState Evitas que el estado se desincronice del formulario

6 · Errores habituales

Olvidar preventDefault

✗ Incorrecto

// El navegador hace un POST nativo y RECARGA la pagina:
// se pierde el estado de la isla y no ves la validacion.
function handleSubmit(e) {
  await sendToServer(form);
}

✓ Correcto

function handleSubmit(e) {
  e.preventDefault();          // detenemos el comportamiento nativo
  await sendToServer(form);    // controlamos nosotros el envio (fetch)
}

Sin preventDefault el formulario recarga la página y toda la interactividad de la isla se reinicia.

Guardar los errores en estado redundante

✗ Incorrecto

// Dos fuentes de verdad que se desincronizan facilmente.
const [form, setForm] = useState({ name: '' });
const [errors, setErrors] = useState({ name: '' });

function update(field, value) {
  setForm({ ...form, [field]: value });
  setErrors(validate(form)); // usa el valor VIEJO: bug clasico
}

✓ Correcto

const [form, setForm] = useState({ name: '' });

// Los errores se DERIVAN del estado, no se almacenan.
const errors = validate(form);

Derivar en vez de duplicar elimina toda una clase de bugs: los errores siempre reflejan el estado real.

Validar solo en el cliente

✗ Incorrecto

// Confiar unicamente en la validacion del navegador.
// Un usuario puede desactivar JS o enviar el POST a mano.
<button disabled={hasErrors}>Enviar</button>

✓ Correcto

// El servidor SIEMPRE revalida. La validacion de cliente es UX,
// no seguridad. En el Modulo 5 el endpoint repite la validacion.
await sendToServer(form);

La validación en cliente mejora la experiencia, pero nunca es una defensa: el endpoint debe revalidar todo lo que recibe.

Usar el mismo estado para cosas distintas

✗ Incorrecto

// Un booleano no puede representar 4 estados: aparecen combinaciones imposibles.
const [isLoading, setIsLoading] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);
const [isError, setIsError] = useState(false);

✓ Correcto

// Un enum representa exactamente uno de los estados posibles.
type Status = 'idle' | 'submitting' | 'success' | 'error';
const [status, setStatus] = useState<Status>('idle');

Varios booleanos permiten estados contradictorios (isLoading && isError). Un único enum los hace imposibles.

7 · Ejercicio guiado

Objetivo: construir el formulario completo paso a paso y verificar cada estado.

  1. Crea el proyecto o entra en el tuyo de módulos anteriores: 
    pnpm create astro@latest contacto && cd contacto
pnpm astro add react
  2. Codifica la isla src/components/ContactForm.tsx copiando el componente del Ejemplo real (validación, estados y accesibilidad). Presta atención a las props: no recibe ninguna; toda su lógica vive dentro.
  3. Monta la isla en src/pages/contacto.astro con client:visible y envuélvela en un layout con <h1> y un párrafo estáticos.
  4. Prueba el estado idle: pnpm dev, abre /contacto y comprueba que sin tocar nada no se muestran errores. Escribe un nombre y mira cómo el value del input en DevTools (Elements) refleja el estado.
  5. Prueba la validación: pulsa «Enviar» vacío. Deben aparecer los tres errores (o los que correspondan). Verifica que aparece un email inválido y un mensaje corto. Corrige los campos y confirma que los errores desaparecen.
  6. Prueba submitting y success: envía un formulario válido con un email normal. El botón debe pasar a «Enviando…» y luego al mensaje de confirmación.
  7. Prueba error: repite el envío usando un email terminado en @example.com. Debe mostrarse el mensaje de error y no perderse lo escrito.
  8. Verifica la hidratación selectiva: en DevTools → Network, confirma que el chunk de React se descarga cuando el formulario entra en pantalla, no al cargar la página entera. Después desactiva JS y comprueba que el HTML del formulario sigue visible (inerte, pero visible).

8 · Reto

🎯 Puntuación de fuerza de la contraseña, en vivo

Añade al formulario un campo contraseña con un medidor de seguridad en tiempo real. Debe clasificar la contraseña en débil, media o fuerte según longitud y variedad de caracteres, mostrar una barra de progreso con color y bloquear el envío si es débil.

Requisitos:

  • La puntuación ha de derivarse de la contraseña (nada de guardarla en un estado aparte).
  • La barra debe actualizarse con cada tecla, sin saltos bruscos.
  • El resultado debe ser accesible: usa aria-live="polite" para anunciar el nivel, y no dependas solo del color.
  • Añade la validación de contraseña a la función validate para que el botón se comporte en consecuencia.

Pista: la puntuación es una función pura scorePassword(pwd) que devuelve un número o un nivel. Para accesibilidad, además del color, muestra texto («Fuerte») y un role="progressbar" con aria-valuenow. Recuerda: la contraseña nunca debe registrarse en consola ni enviarse en texto por canales inseguros; en el Módulo 8 verás cómo tratarla con servidores y HTTPS.

9 · Resumen

  • Un formulario interactivo es el caso perfecto para una isla React: la página es estática, solo el formulario necesita estado.
  • Los campos controlados hacen del estado la única fuente de verdad.
  • Un envío tiene cuatro estados: idle, submitting, success, error; represéntalos con un enum, no con booleanos.
  • La validación debe ser una función pura; los errores se derivan del estado.
  • La accesibilidad (label, aria-invalid, role="alert") no es opcional.
  • La validación de cliente es UX; el servidor siempre revalida.
  • Con client:visible hidratamos el formulario solo cuando el usuario lo ve.

10 · Preguntas frecuentes

¿El formulario funciona si el usuario tiene JavaScript desactivado?

Se ve (el HTML está pre-renderizado) pero no se envía, porque la lógica vive en la isla. Si necesitas que funcione sin JS, el enfoque correcto es un formulario HTML nativo que haga POST a un endpoint del servidor (Módulo 5) y progresivamente mejorarlo con JavaScript. Es la técnica de progressive enhancement: nativo primero, isla encima.

¿Debo validar en cliente y en servidor?

Sí, siempre ambos. La validación de cliente es experiencia de usuario (feedback inmediato). La de servidor es seguridad y corrección: el cliente es territorio hostil y cualquiera puede enviar una petición a mano. Reutiliza la misma función pura validate en ambos lados para no duplicar reglas.

¿Por qué no uso client:load si el formulario es importante?

Porque el formulario está abajo de la página y el usuario puede tardar. client:visible hidrata solo cuando llega a él, y el HTML pre-renderizado ya muestra los campos. La diferencia de experiencia es imperceptible, pero el ahorro de JavaScript en la primera carga es real. Si el formulario estuviera en la parte superior y fuera lo único importante de la página, client:load sería razonable.

¿Cómo conecto esto a un endpoint real?

Sustituye el cuerpo de sendToServer por un fetch: await fetch('/api/contact', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(data) }). Comprueba response.ok y lanza error si no lo es. Todo lo demás (estados, validación, UI) se queda igual. Lo montarás completo en el Módulo 5.

¿Qué framework debería usar en un formulario como este?

Cualquiera de los tres sirve; elige el que tu equipo domine (React en este curso). Svelte generaría menos JavaScript para un formulario así, y Vue sería igual de cómodo. La decisión correcta es por mantenibilidad del equipo, no por micro-optimización de kilobytes en una sola isla.
