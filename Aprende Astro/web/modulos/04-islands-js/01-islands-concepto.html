Arquitectura islands e hidratación

Módulo 4 · Islands e Interactividad 🕐 30 minutos

1 · Introducción

Hasta ahora has construido páginas que son HTML puro: rápidas, pero inertes. El usuario no puede abrir un desplegable, filtrar una lista ni validar un formulario sin que el navegador ejecute JavaScript. La pregunta es cuánto JavaScript y para qué.

Un SPA tradicional (React, Vue sin framework meta) responde enviando toda la página como JavaScript: el navegador descarga, ejecuta y «revive» el HTML completo antes de poder pintar nada. Astro propone lo contrario: la página se envía como HTML estático y solo los pequeños trozos que de verdad necesitan interactividad —las islands— se hidratan con JavaScript.

En esta lección aprenderás qué es exactamente una isla, qué significa hidratar, cómo elegir la directiva client:* adecuada para cada caso y por qué esto cambia por completo la ecuación de rendimiento.

¿Por qué existe esta lección? La arquitectura islands es la idea central de Astro y el motivo por el que nació el framework. Todo el resto del curso (React, Vue, Svelte, endpoints, server islands) son consecuencias de este diseño. Si no interiorizas el «por qué», las directivas client:* se convierten en magia que memorizas sin criterio. Aquí vas a poder justificar cada elección ante tu equipo.

2 · Teoría

De SPA a MPA: el coste de hidratar todo

En una SPA, el servidor manda un HTML casi vacío más un gran bundle de JavaScript. El framework arranca, ejecuta la librería al completo, reconstruye la página en memoria y la «hidrata» entera: asocia eventos, estados y efectos al DOM. Ese proceso consume CPU del dispositivo del usuario —y en un móvil de gama media se nota—. Cuanto más grande es la app, más caro.

Astro invierte el modelo: el 90 % de una página suele ser contenido (texto, imágenes, layout) que no cambia. Lo único que necesita JavaScript son piezas pequeñas y aisladas. A esas piezas las llamamos islas.

Analogía: imagina una plaza pública empedrada. No necesitas electricidad para las piedras: están quietas y ya cumplen su función. Solo unos pocos puestos —una cafetera, la caja del músico, un cartel luminoso— necesitan corriente. La hidratación es enchufar únicamente esos puestos, en lugar de electrificar cada piedra de la plaza.

Qué es una isla

Una isla es un componente interactivo (escrito en React, Vue, Svelte, Solid, Preact…) incrustado dentro de una página que, por todo lo demás, es HTML estático. Características clave:

  • Se renderiza primero en el servidor (durante el build) a HTML real, así el usuario ve el contenido al instante.
  • Más tarde, si recibe una directiva client:*, se descarga su JavaScript y se hidrata: se le «enchufa» la interactividad.
  • Cada isla es independiente: su estado y su runtime viven aislados del resto de la página.

Qué significa «hidratar» exactamente

Hidratar no es volver a dibujar la página. El HTML ya está en pantalla. Hidratar significa ejecutar el framework en el cliente y emparejar su árbol de componentes con el DOM que ya existe, para:

  1. Adjuntar los event listeners (clics, teclas, cambios).
  2. Reconstruir el estado inicial y sus efectos (useState, useEffect…).
  3. A partir de ahí, reaccionar a las interacciones y actualizar el DOM.

Coste real de hidratar: descarga + parseo + compilación (JIT) + ejecución del framework. Por eso Astro pone una directiva obligatoria: sin client:*, el componente se queda como HTML inerte, con cero JavaScript enviado. Es una decisión explícita, no un olvido.

Las directivas de hidratación

La directiva decide cuándo se carga y se hidrata la isla. Es la palanca más importante para optimizar:

DirectivaCuándo hidrataCuándo usarla
client:loadInmediatamente al cargar la páginaUI crítica que debe responder ya (menú visible, contador principal)
client:idleCuando el navegador está libre (requestIdleCallback)Interactividad secundaria que no urge (botón «me gusta», tema)
client:visibleCuando el componente entra en el viewport (IntersectionObserver)Contenido que está más abajo y quizá el usuario nunca vea
client:media="(max-width: 768px)"Cuando la media query coincideComponentes solo para móvil o solo para escritorio
client:only="react"Directamente en el cliente, sin render en servidorWidgets que dependen de window/document y no pueden pre-renderizarse

Regla mental de prioridad: visible → idle → load → only. Empieza siempre por la opción más barata (client:visible) y sube solo si la experiencia lo exige. La directiva más común en un sitio bien hecho es client:visible, no client:load.

¿Por qué client:load es la opción por defecto mental equivocada?

Porque hidrata todo aunque el usuario no lo necesite todavía. Si tienes seis islas con client:load en la portada, el navegador baja y ejecuta el runtime de todas ellas antes de que el usuario haya hecho scroll. Cambiar esas seis a client:visible puede reducir a la mitad el JavaScript ejecutado en la primera carga sin que el usuario note nada.

Ojo: client:load no significa «renderizado en cliente». El HTML ya está renderizado en el servidor. La directiva solo controla el momento de la hidratación. El único caso que salta el render de servidor es client:only.

3 · Ejemplo mínimo

El componente interactivo más pequeño posible: un contador. Primero el componente React, después su uso como isla dentro de una página Astro.

src/components/Counter.tsx
// Importamos useState del runtime de React. Este codigo NO se ejecuta
// en el servidor durante el build: se ejecuta en el navegador al hidratar.
import { useState } from 'react';

export default function Counter() {
  // Estado local de la isla: cada isla tiene su propio estado aislado.
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clics: {count}
    </button>
  );
}
src/pages/index.astro
---
// El frontmatter (entre las rayas) se ejecuta en el SERVIDOR, en build time.
import Counter from '../components/Counter.tsx';
---

<html lang="es">
  <body>
    <!-- Esto es HTML estatico puro: cero JavaScript enviado. -->
    <h1>Mi primera isla</h1>
    <p>Este texto no necesita JavaScript para existir.</p>

    <!-- client:load le dice a Astro: renderiza este componente a HTML
         durante el build y ADEMAS hidratalo en cuanto cargue la pagina. -->
    <Counter client:load />
  </body>
</html>

Qué ocurre paso a paso:

  1. En el build: Astro ejecuta el frontmatter, importa Counter y lo renderiza a HTML estático (<button>Clics: 0</button>). Ese HTML viaja al navegador.
  2. Al cargar la página: el usuario ve el botón al instante, aunque el JavaScript aún no haya llegado. Se cumple sin JS.
  3. Hidratación: como pusimos client:load, Astro carga el runtime de React y la lógica de Counter, empareja el DOM existente y enchufa el onClick.
  4. Interacción: a partir de ahí cada clic actualiza el estado y React re-renderiza solo ese botón.

Prueba a quitar client:load: verás el botón igual (viene pre-renderizado) pero al hacer clic no pasa nada. Esa es la prueba de que la hidratación es lo que aporta interactividad.

4 · Ejemplo real

Una landing profesional típica tiene mucha interactividad repartida. Así se reparte entre directivas, razonando cada elección por posición y urgencia:

src/pages/landing.astro
---
// Componentes isla, cada uno con su rol.
import ThemeToggle from '../components/ThemeToggle.tsx';   // boton de tema
import Gallery from '../components/Gallery.tsx';           // carrusel de fotos
import PriceTable from '../components/PriceTable.tsx';      // selector de plan
import NewsletterForm from '../components/NewsletterForm.tsx';
import MetricsChart from '../components/MetricsChart.tsx';  // grafico pesado
---

<html lang="es">
  <body>
    <header>
      <!-- El toggle de tema esta SIEMPRE visible y es critico:
           el usuario puede pulsarlo nada mas entrar. client:load. -->
      <ThemeToggle client:load />
    </header>

    <!-- La galeria esta a media pagina y es pesada: solo hidratamos
         cuando el usuario la ve (IntersectionObserver). client:visible. -->
    <Gallery client:visible />

    <!-- El selector de planes esta mas abajo: misma logica. -->
    <PriceTable client:visible />

    <!-- El formulario tampoco urge; al entrar en pantalla se activa. -->
    <NewsletterForm client:visible />

    <!-- El grafico usa una libreria muy grande. Al estar al fondo de la
         pagina, hidratarlo solo cuando entra en el viewport evita cargar
         el bundle a todo el que no baja hasta aqui. -->
    <MetricsChart client:visible />
  </body>
</html>

Decisiones clave:

  • Solo la cabecera usa client:load, porque es lo único visible e interactivo de inmediato. Todo lo demás espera.
  • La mayoría usa client:visible: el JavaScript de la galería, la tabla o el gráfico ni siquiera se descarga si el usuario rebota antes del scroll.
  • El gráfico pesado vive abajo a propósito: el diseño y la directiva colaboran para diferir lo caro.

Cómo comprobarlo: abre DevTools → Network, filtra por JS y haz scroll. Verás que los chunks de Gallery, PriceTable y MetricsChart aparecen solo cuando entran en pantalla. Eso es client:visible en acción.

6 · Errores habituales

Hidratar todo el árbol para una sola interacción

✗ Incorrecto

<!-- La pagina ENTERA como isla React: pagas React por un solo boton. -->
<Hero client:load />
<Features client:load />
<Pricing client:load />
<Footer client:load />

✓ Correcto

<!-- Contenido estatico en .astro (cero JS)… -->
<Hero />
<Pricing />
<Footer />

<!-- …y solo la isla que responde a eventos se hidrata. -->
<ContactButton client:visible />

El contenido no necesita estado ni eventos. Convertirlo en isla solo añade JavaScript que el usuario paga sin obtener nada a cambio.

Creer que sin directiva el componente es interactivo

✗ Incorrecto

<!-- Se ve el boton (pre-renderizado), pero NO responde al clic. -->
<Counter />

✓ Correcto

<!-- La directiva client:* es la que aporta la interactividad. -->
<Counter client:load />

Sin directiva no hay JavaScript: el componente queda como HTML inerte. Es la confusión número uno de quien empieza con Astro.

Ignorar el coste de hidratar en la primera carga

✗ Incorrecto

<!-- Seis islas pesadas hidratadas antes de que el usuario haga scroll. -->
<Carousel client:load />
<Map client:load />
<Chart client:load />
<Editor client:load />

✓ Correcto

<!-- El runtime de cada isla llega solo al hacerse visible. -->
<Carousel client:visible />
<Map client:visible />
<Chart client:visible />
<Editor client:idle />

El HTML se sigue pre-renderizando igual; lo que cambia es que la hidratación no bloquea la carga inicial. La experiencia mejora y el bundle ejecutado baja de forma drástica.

7 · Ejercicio guiado

Objetivo: auditar una página y elegir la directiva correcta para cada isla, justificándola.

Esta página tiene cuatro elementos interactivos descritos. Decide la directiva y por qué:

#ElementoPosición y urgencia
1Menú hamburguesa (móvil)Fijo arriba, siempre visible
2Botón «Añadir a favoritos»En medio del artículo
3Mapa interactivoAl final de la página, pesado
4Selector de divisaSolo tiene sentido en pantallas grandes
  1. Menú hamburguesa → client:load. Está siempre visible y el usuario puede pulsarlo inmediatamente; su JS es pequeño, así que el coste está justificado. 
    <MobileMenu client:load />
  2. Botón de favoritos → client:visible. Solo importa cuando el usuario llega a él. Si nunca baja, no pagamos su JavaScript. 
    <FavoriteButton client:visible />
  3. Mapa → client:visible. Es pesado y está al fondo. Hidratar solo al entrar en pantalla evita cargar la librería del mapa a quien no lo mira. 
    <Map client:visible />
  4. Selector de divisa → client:media="(min-width: 1024px)". Si solo se muestra en escritorio, no tiene sentido descargar su runtime en móvil. 
    <CurrencySelect client:media="(min-width: 1024px)" />
  5. Verifica: con pnpm dev y DevTools (Network → JS), confirma que el mapa y los favoritos solo descargan su código al hacer scroll, y que en móvil el selector de divisa no descarga nada.

8 · Reto

🎯 Mide el ahorro de hidratación selectiva

Crea una página con la misma isla de un gráfico (alguna librería pesada) repetida cuatro veces. Implementa dos versiones: una con client:load en todas y otra con client:visible. Con DevTools → Network (filtra JS) y Coverage, compara cuánto JavaScript se descarga y cuánto se ejecuta en la primera carga, sin hacer scroll.

Documenta los números y responde: ¿en qué porcentaje bajó el JavaScript ejecutado al cargar? ¿Cambió el HTML que recibe el usuario? Explica por qué.

Pista: abre la pestaña Coverage (Cmd/Ctrl+Shift+P → «Show Coverage»), recarga sin hacer scroll y anota «bytes used» frente a «bytes total». El HTML pre-renderizado no cambia; lo que cambia es cuándo y si se ejecuta el JS.

9 · Resumen

  • La arquitectura islands envía HTML estático y solo hidrata las piezas interactivas.
  • Hidratar = ejecutar el framework en el cliente y enganchar eventos/estado al DOM ya presente.
  • Una isla necesita una directiva client:* para ser interactiva; sin ella es HTML inerte.
  • El cuándo se hidrata lo decide la directiva, no el render (que siempre ocurre en el servidor, salvo client:only).
  • Orden de preferencia: visible → idle → load → only.
  • El contenido y el layout no deben convertirse en islas: no pagan el coste de un bundle que no necesitan.

client:idleEl navegador está libre (requestIdleCallback)
client:visibleEl componente entra en el viewport
client:media="(…)"La media query coincide
client:only="react"Siempre en cliente, sin render de servidor

10 · Preguntas frecuentes

¿La hidratación vuelve a renderizar el HTML desde cero?

No. El HTML ya está en el DOM, renderizado por el servidor durante el build. Hidratar significa ejecutar el framework en el cliente y emparejar su árbol de componentes con ese DOM existente para añadir listeners, estado y efectos. No hay un segundo pintado completo; por eso el contenido aparece al instante.

¿Puedo comunicar dos islas entre sí?

Sí, pero no compartiendo estado de forma implícita: cada isla es un árbol independiente con su propio runtime. Las soluciones habituales son: (1) subir el estado a un ancestro común y pasarlo como props; (2) usar un store externo mínimo y agnóstico de framework como nanostores; o (3) fusionar ambas piezas en una sola isla si de verdad van juntas. Lo verás en la lección de React.

¿client:visible funciona si el elemento está dentro de un contenedor con scroll propio?

Sí. client:visible usa IntersectionObserver, que detecta la intersección con el viewport o con el ancestro que hace de scroll. Es robusto en listas con scroll interno, pero si el contenedor tiene overflow: hidden con altura cero el elemento nunca será «visible» y la isla no se hidratará: revisa el layout.

¿Cuándo debería usar client:only de verdad?

Cuando el componente no puede renderizarse en el servidor porque depende de APIs del navegador desde el primer render: window, document, localStorage sin guardas, gráficos que miden el DOM, editores enriquecidos… El precio es que esa pieza pierde el HTML pre-renderizado (no aparece hasta que llega el JS) y su contenido no es visible para crawlers sin ejecución. Úsalo como excepción, no como norma.

¿Meter una isla React convierte mi sitio en una SPA?

No. Astro sigue siendo un MPA: cada página es un documento HTML completo con navegación normal. Las islas son piezas de interactividad dentro de esas páginas; no hay un router de cliente gobernando toda la aplicación. Podrás añadir View Transitions más adelante (Módulo 7) para dar fluidez, pero sin renunciar al modelo MPA.
