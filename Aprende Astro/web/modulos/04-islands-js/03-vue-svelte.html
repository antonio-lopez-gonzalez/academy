Componentes Vue y Svelte en Astro

Módulo 4 · Islands e Interactividad 🕐 30 minutos

1 · Introducción

Astro es agnóstico de framework: no te obliga a elegir uno. Puedes tener islas React, Vue, Svelte, Solid o Preact en el mismo proyecto, cada una donde mejor encaje. Esta lección se centra en Vue y Svelte, dos alternativas muy usadas que aportan modelos mentales distintos.

Verás cómo integrarlas, cómo se hidratan igual que cualquier isla y, sobre todo, cómo comparar los tres enfoques para decidir con criterio. Un buen desarrollador de Astro no defiende un framework por fe, sino que elige según el problema, el equipo y el coste de hidratación.

¿Por qué existe esta lección? Porque en proyectos reales rara vez eliges desde cero. Puede que tu equipo venga de Vue, que un componente concreto se beneficie de la ergonomía de Svelte o que quieras migrar sin reescribir todo. Astro permite mezclar sin penalizar: cada isla carga solo su runtime, así que una isla Svelte no arrastra React.

2 · Teoría

Tres integraciones, un mismo contrato

Cada framework tiene su paquete de integración, instalable con pnpm astro add:

FrameworkPaqueteInstalaciónExtensión
React@astrojs/reactpnpm astro add react.jsx, .tsx
Vue@astrojs/vuepnpm astro add vue.vue
Svelte@astrojs/sveltepnpm astro add svelte.svelte

Lo importante: para Astro, todos son lo mismo. Un componente de Vue o Svelte se importa y se usa igual que uno de React, y acepta las mismas directivas client:*. El framework solo cambia la forma de escribir el componente, no cómo Astro lo hidrata.

astro.config.mjs
import { defineConfig } from 'astro/config';
import react from '@astrojs/react';
import vue from '@astrojs/vue';
import svelte from '@astrojs/svelte';

export default defineConfig({
  // Conviven los tres: cada isla carga SOLO su runtime.
  integrations: [react(), vue(), svelte()],
});

El mismo contador en los tres lenguajes

Para comparar de verdad, mira cómo se escribe la misma isla en cada uno:

React — Counter.tsx
import { useState } from 'react';

export default function Counter() {
  // Estado declarado con un hook; se re-renderiza el componente entero.
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
Vue — Counter.vue
<script setup lang="ts">
// ref() crea una referencia reactiva. En el template se accede sin .value.
import { ref } from 'vue';
const count = ref(0);
</script>

<template>
  <!-- Vue rastrea que count se usa aqui y solo re-renderiza esta parte. -->
  <button @click="count++">{{ count }}</button>
</template>
Svelte — Counter.svelte
<script lang="ts">
  // En Svelte 5, $state() crea estado reactivo con runas.
  let count = $state(0);
</script>

<!-- Svelte compila esto a codigo imperativo muy pequeno. -->
<button onclick={() => count++}>{count}</button>

Fíjate: la API cambia (hook, ref, runas), pero el resultado es idéntico. Y el uso desde Astro es exactamente el mismo:

src/pages/demo.astro
---
import CounterReact from '../components/Counter.tsx';
import CounterVue from '../components/Counter.vue';
import CounterSvelte from '../components/Counter.svelte';
---

<html lang="es">
  <body>
    <h1>Islas poliglotas</h1>
    <!-- Tres frameworks distintos, la MISMA directiva client:* -->
    <CounterReact client:visible />
    <CounterVue client:visible />
    <CounterSvelte client:visible />
  </body>
</html>

Cómo se reparte el JavaScript entre islas

Pagina con 3 islas de 3 frameworks
+----------------------------------------------------------+
|  HTML estatico (layout, texto)                          |
|                                                          |
|  [isla React]      -> chunk del runtime React            |
|  [isla Vue]        -> chunk del runtime Vue              |
|  [isla Svelte]     -> chunk del runtime Svelte (minimo)  |
+----------------------------------------------------------+
   Cada isla hidratada descarga SOLO su runtime.
   No se descargan React, Vue y Svelte "por si acaso":
   solo el de las islas realmente presentes y activadas.

Consecuencia práctica: si tu proyecto tiene una sola isla hecha en Svelte y cien páginas estáticas, no pagas React ni Vue. Astro solo incluye el runtime de los frameworks que aparecen en islas hidratadas de esa página. Mezclar frameworks no multiplica el coste. Aun así, por mantenibilidad, mezclar sin motivo es mala idea: elige uno como principal.

Comparación honesta de enfoques

CriterioReactVueSvelte
Tamaño en runtimeMayorMedioMínimo (compila)
Ecosistema y libreríasEnormeMuy amplioBueno y creciente
Curva de aprendizajeMedia (hooks)Baja (SFC clara)Muy baja
Modelo de reactividadRe-render + hooksReactividad fina con proxiesCompilador + runas
Cuándo brilla como islaReutilizar componentes/librerías existentesEquipos con base VueWidgets pequeños y ligeros

Analogía: elegir framework como isla es como elegir un vehículo para un reparto. React es una furgoneta grande: carga de todo, pero consume más. Vue es un coche versátil: cómodo y equilibrado. Svelte es una moto: ágil y económica para trayectos cortos. No hay «mejor»: hay adecuado al tramo.

3 · Ejemplo mínimo

Una isla Vue que recibe una prop y la muestra reactivamente. Primero instala la integración:

Terminal
# Instala y configura @astrojs/vue en un paso.
pnpm astro add vue
src/components/Badge.vue
<script setup lang="ts">
// withDefaults define valores por defecto para props opcionales.
// La prop llega SERIALIZADA desde el .astro, como en React.
const props = withDefaults(
  defineProps<{ label: string; tone?: "ok" | "warn" }>(),
  { tone: "ok" }
);
</script>

<template>
  <!-- :class enlaza una clase segun la prop reactiva. -->
  <span class="badge" :class="`badge--${props.tone}`">{{ props.label }}</span>
</template>
src/pages/index.astro
---
// Se importa y se usa igual que cualquier otro componente.
import Badge from '../components/Badge.vue';
---

<html lang="es">
  <body>
    <!-- client:visible: se hidrata apenas entra en pantalla. -->
    <Badge label="Nuevo" tone="ok" client:visible />
  </body>
</html>

Observa lo esencial: la frontera es idéntica a la de React. Props serializables, una directiva client:*, render en servidor y luego hidratación. Cambia el lenguaje del componente, no el contrato con Astro.

4 · Ejemplo real

Un caso de decisión real: una página de documentación donde conviene usar lenguajes distintos para piezas distintas. El buscador (complejo) en Vue porque el equipo lo domina; el botón de «copiar código» en Svelte por ser diminuto y ligero.

src/components/SearchBox.vue
<script setup lang="ts">
import { ref, computed } from 'vue';

const props = defineProps<{ docs: { slug: string; title: string }[] }>();
const query = ref('');

// computed deriva el resultado SIN estado extra: solo recalcula al cambiar query.
const results = computed(() =>
  props.docs.filter((d) =>
    d.title.toLowerCase().includes(query.value.toLowerCase())
  )
);
</script>

<template>
  <input v-model="query" placeholder="Buscar..." aria-label="Buscar" />
  <ul v-if="query">
    <li v-for="d in results" :key="d.slug">{{ d.title }}</li>
  </ul>
</template>
src/components/CopyButton.svelte
<script lang="ts">
  // Una sola variable de estado: si se copio o no.
  let copied = $state(false);
  export let code: string; // prop pasada desde Astro

  // Funcion manejadora: usa la API del navegador (solo cliente).
  async function copy() {
    await navigator.clipboard.writeText(code);
    copied = true;
    setTimeout(() => (copied = false), 1500); // feedback temporal
  }
</script>

<button onclick={copy}>{copied ? 'Copiado' : 'Copiar'}</button>
src/pages/guia.astro
---
import SearchBox from '../components/SearchBox.vue';
import CopyButton from '../components/CopyButton.svelte';

const docs = [
  { slug: 'intro', title: 'Introduccion' },
  { slug: 'islands', title: 'Islands' },
];
const snippet = 'const total = price * quantity;';
---

<html lang="es">
  <body>
    <h1>Guia</h1>

    <!-- Buscador: isla Vue, espera a ser visible. -->
    <SearchBox docs={docs} client:visible />

    <!-- El codigo es estatico; solo el boton necesita JS. -->
    <pre><code>{snippet}</code></pre>
    <!-- clipboard depende del navegador: perfecto para client:only. -->
    <CopyButton code={snippet} client:only="svelte" />
  </body>
</html>

Decisiones explicadas:

  • Vue para el buscador: el equipo ya lo conoce, y computed + v-model expresan el filtro de forma natural.
  • Svelte para el botón de copiar: es minúsculo; el runtime de Svelte es el más ligero, ideal para un widget trivial.
  • client:only="svelte" en el botón: navigator.clipboard solo existe en el navegador, así que evitamos el render de servidor. Es el caso de uso legítimo de client:only.
  • El contenido y el bloque de código quedan estáticos: cero JavaScript para lo que no lo necesita.

Nota sobre client:only: al escribir con framework, debes indicarlo (client:only="vue", client:only="svelte"…). Es obligatorio porque, al no haber render de servidor, Astro necesita saber qué runtime cargar en el cliente.

5 · Buenas prácticas

HazEvitaPor qué
Elegir un framework principal por proyecto Mezclar React, Vue y Svelte sin motivo Aunque no se penaliza en peso (solo carga lo presente), sí se penaliza en mantenibilidad
Usar Svelte para widgets pequeños donde su tamaño brilla Reescribir en Svelte un componente React que ya funciona El coste de reescritura rara vez compensa; el criterio es la necesidad, no la moda
Reservar client:only="framework" para lo que depende del navegador Usar client:only por comodidad Pierdes el HTML pre-renderizado de esa pieza (y su valor SEO)
Mantener las props serializables y tipadas Pasar funciones o instancias entre framework y Astro La frontera siempre serializa a JSON, sea cual sea el framework

6 · Errores habituales

Usar client:only sin especificar el framework

✗ Incorrecto

<!-- Sin render de servidor, Astro no sabe que runtime cargar. -->
<CopyButton client:only />

✓ Correcto

<!-- Indicamos explicitamente el framework. -->
<CopyButton client:only="svelte" />

client:only es la única directiva que exige el nombre del framework, precisamente porque no hay HTML de servidor del que inferirlo.

Registrar integraciones que no se usan

✗ Incorrecto

// Instalar y activar Vue "por si acaso", sin ninguna isla Vue.
export default defineConfig({
  integrations: [react(), vue(), svelte()],
});

✓ Correcto

// Solo el framework que realmente usamos como isla.
export default defineConfig({
  integrations: [react()],
});

Una integración sin islas no envía runtime, pero añade dependencias, config de Vite y ruido en el build. Instala solo lo que uses.

Asumir que Vue y Svelte comparten estado entre islas

✗ Incorrecto

<!-- Dos islas Vue "hermanas" que deberian compartir un dato. -->
<Filters client:visible />
<Results client:visible />   <!-- cada una tiene su propio root -->

✓ Correcto

<!-- Fusionamos en una isla que contiene ambos, o usamos un store externo. -->
<SearchExperience client:visible />

El aislamiento entre islas es independiente del framework. Vue y Svelte también tienen roots separados; el estado compartido se diseña a propósito.

7 · Ejercicio guiado

Objetivo: añadir una isla Svelte de «me gusta» a una página que ya tiene una isla React, y comprobar que ambas conviven cargando solo su runtime.

  1. Instala Svelte (React ya lo instalamos en la lección anterior): 
    pnpm astro add svelte
  2. Crea el componente Svelte en src/components/Like.svelte: 
    <script lang="ts">
  // Estado reactivo con runas (Svelte 5).
  let count = $state(0);
  let liked = $state(false);

  function toggle() {
    // Cambia el estado y, con el, la UI. Sin re-render de toda la app.
    liked = !liked;
    count += liked ? 1 : -1;
  }
</script>

<button aria-pressed={liked} onclick={toggle}>
  {liked ? 'Te gusta' : 'Me gusta'} ({count})
</button>
  3. Úsala junto a una isla React existente en la misma página: 
    ---
import Counter from '../components/Counter.tsx';   // isla React (leccion previa)
import Like from '../components/Like.svelte';      // isla Svelte
---
<h1>Articulo</h1>
<Counter client:visible />
<Like client:visible />
  4. Arranca pnpm dev y comprueba que ambas islas funcionan a la vez, cada una con su interactividad.
  5. Verifica los runtimes con DevTools (Network → JS): verás un chunk del runtime de React y otro del de Svelte, pero ninguno de Vue. Esto confirma que solo se carga el runtime de las islas presentes.

8 · Reto

🎯 El mismo widget en los tres frameworks

Implementa un contador de carrito (botón «Añadir» + texto «x artículos») tres veces: una en React, otra en Vue y otra en Svelte, cada una como isla independiente en la misma página. Después:

  • Mide con DevTools el tamaño del chunk JavaScript de cada runtime.
  • Compara la cantidad de código fuente que tuviste que escribir en cada caso.
  • Responde por escrito: si el equipo ya domina React, ¿justifica el ahorro de tamaño migrar este widget a Svelte? ¿Y si el widget estuviera replicado 200 veces en el sitio?

Pista: el tamaño del runtime es fijo por framework (se comparte entre todas las islas de ese framework en la página). El ahorro solo se materializa si el framework es el único presente. Si ya tienes React por otras islas, añadir una isla Svelte suma un runtime extra en vez de ahorrar. Ahí está la trampa del «Svelte es más ligero».

9 · Resumen

  • Astro es agnóstico de framework: React, Vue y Svelte pueden convivir en el mismo proyecto.
  • Se instalan con pnpm astro add vue / pnpm astro add svelte, que registran la integración.
  • Todos usan las mismas directivas client:* y las mismas reglas de props serializables.
  • Cada isla carga solo su runtime: no pagas frameworks que no usas en la página.
  • client:only="framework" exige el nombre del framework (no hay render de servidor).
  • Mezclar frameworks no penaliza en peso, pero sí en mantenibilidad: elige uno principal.

10 · Preguntas frecuentes

¿Puedo mezclar React y Vue en la misma página?

Sí, sin problema. Cada isla declara su framework vía directiva y Astro carga el runtime correspondiente solo para las islas presentes. Lo que no puedes hacer es pasar props complejas vivas de una isla a otra: la comunicación entre islas se hace por props serializables desde Astro o por un store externo compartido.

¿Por qué mi componente entra en un bucle de peticiones al hidratarse?

Puede ser por un useEffect/onMounted que hace fetch en cada render por falta de dependencias correctas. Recuerda que cada isla es independiente: si tres islas montan y cada una pide datos, verás tres peticiones. Centraliza los datos en el servidor (build time) o raciona las peticiones dentro de una sola isla.

¿Svelte 5 con runas funciona bien como isla?

Sí. La integración @astrojs/svelte soporta Svelte 5 con runas ($state, $derived, $effect). El compilador genera código muy pequeño, lo que hace a Svelte especialmente atractivo para islas diminutas. Como siempre, comprueba la versión en tu package.json y consulta la documentación oficial de la integración si actualizas.

¿Puedo usar Stencil, Solid o Preact también?

Sí. Astro tiene integraciones oficiales y de la comunidad para Solid, Preact, Alpine, Lit y más, todas con el mismo modelo islands y las mismas directivas client:*. El framework es una decisión de ergonomía del equipo; la arquitectura de hidratación selectiva es la misma para todos.

¿Qué pasa con los estilos y el CSS con distintos frameworks?

Los estilos locales de un componente (scoped) se aplican durante el render de servidor, así que se ven correctamente incluso antes de hidratar. El CSS global del proyecto (por ejemplo Tailwind) funciona de forma transversal. Lo verás con más detalle en el Módulo 6; por ahora basta con saber que la isla no «trae» su CSS aparte: se renderiza en el HTML como cualquier otro elemento.
