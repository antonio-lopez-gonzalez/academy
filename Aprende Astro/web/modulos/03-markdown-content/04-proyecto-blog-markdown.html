Proyecto: blog con colecciones

Módulo 3 · Markdown y Content 🕐 45 minutos

1 · Introducción

Cerramos el módulo con el proyecto más satisfactorio: convertimos el blog de datos hardcodeados en un blog content-driven de verdad, donde cada entrada es un fichero Markdown validado por un esquema, listado y detalle se generan solos, y añadimos etiquetas, índice automático y tiempo de lectura. Es el salto definitivo: pasas de «escribir contenido en código» a «escribir contenido como contenido».

Este es el proyecto que usarás como base real para un blog profesional. A partir de aquí, los módulos siguientes añaden islas (Módulo 4), datos y API (Módulo 5), Tailwind (Módulo 6), SEO (Módulo 7)… pero la columna vertebral —colección tipada + listado + detalle— ya está aquí.

¿Por qué este es el patrón profesional? Porque separa de verdad tres responsabilidades que en los manuales suelen ir mezcladas: contenido (Markdown con frontmatter), contrato (esquema Zod) e interfaz (layouts y componentes). Cuando trabajas con un equipo, cada persona toca su capa y el build garantiza que encajan. Y cuando añadas 200 posts, no cambiarás ni una línea de las plantillas.

Qué construirás: colección blog con esquema, tres posts Markdown, tarjeta reutilizable, layouts anidados, portada, listado, detalle con <Content /> y TOC, página de etiquetas, 404 y un astro.config.mjs con los plugins de la lección anterior.

Errores típicos de este proyecto: dejar la config en src/content/config.ts (ubicación antigua), olvidar que getCollection es asíncrona, usar [...id] pero enlazar con post.slug (ya no existe; es post.id), y no filtrar borradores, publicándolos sin querer.

2 · Teoría: la arquitectura content-driven

Del contenido a la URL, sin pasos manuales

El flujo de un blog con colecciones es lineal y sin sorpresas: escribes un Markdown, el loader lo detecta, el esquema lo valida, y la ruta dinámica lo publica. Nada de tocar arrays ni de registrar posts.

Analogía: en el Módulo 2 el blog era una tienda de muebles armados: cada post venía montado en el código. Ahora es una fábrica con plantilla: entregas la madera (Markdown), un inspector comprueba que tiene las piezas exigidas (Zod) y la máquina produce el mueble (la página). Tú solo entregas madera.

1) Configuración de Astro (plugins de la lección anterior)

astro.config.mjs
import { defineConfig } from 'astro/config';
import mdx from '@astrojs/mdx';
import remarkToc from 'remark-toc';
import rehypeAutolinkHeadings from 'rehype-autolink-headings';
import rehypeExternalLinks from 'rehype-external-links';
import { remarkReadingTime } from './src/utils/remark-reading-time.mjs';

export default defineConfig({
  site: 'https://blog.ejemplo.dev',
  integrations: [mdx()],
  markdown: {
    remarkPlugins: [
      remarkReadingTime,
      [remarkToc, { heading: 'contenido', tight: true }],
    ],
    rehypePlugins: [
      [rehypeAutolinkHeadings, { behavior: 'wrap' }],
      [rehypeExternalLinks, { target: '_blank', rel: ['noopener', 'noreferrer'] }],
    ],
    shikiConfig: { theme: 'github-dark', wrap: true },
  },
});
src/utils/remark-reading-time.mjs
import { toString } from 'mdast-util-to-string';

// Enriquece el frontmatter con el tiempo de lectura estimado.
export function remarkReadingTime() {
  return (tree, file) => {
    const words = toString(tree).split(/\s+/).filter(Boolean).length;
    file.data.astro.frontmatter.readingTime = `${Math.ceil(words / 200)} min`;
  };
}

2) La colección

src/content.config.ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const blog = defineCollection({
  // Todos los .md/.mdx, incluidas subcarpetas (el id incluirá la subruta).
  loader: glob({ pattern: '**/*.{md,mdx}', base: './src/content/blog' }),
  schema: z.object({
    title: z.string(),
    description: z.string(),
    pubDate: z.coerce.date(),
    author: z.string().default('Anónimo'),
    tags: z.array(z.string()).default([]),
    draft: z.boolean().default(false),   // borrador: se oculta del sitio
  }),
});

export const collections = { blog };

import BlogLayout from '../../layouts/BlogLayout.astro';

Decisiones clave: el filtro de borradores va en la consulta con el predicado de getCollection, de modo que ni la portada, ni el listado, ni el detalle, ni las etiquetas muestran jamás un draft. El componente PostCard usa el tipo generado CollectionEntry<'blog'>: si el esquema cambia, el componente lo sabe. El detalle combina <Content /> (cuerpo), headings (TOC) y remarkPluginFrontmatter.readingTime (tiempo de lectura). Y la página de etiquetas enlaza a /tags/<tag>, que resolverás en el reto.

5 · Buenas prácticas

PrácticaPor qué
Filtrar borradores en la consulta, no en la plantillaNingún render puede «olvidarse» de filtrarlos
Usar CollectionEntry<'blog'>Tipos siempre sincronizados con el esquema
Ordenar de forma explícitaEl orden del sistema de archivos no es fiable para presentar
Guardar el id correcto para los enlaces (post.id)Evita 404 y URLs inconsistentes
Un schema con defaults razonablesLos posts pueden omitir campos opcionales y no rompen
Reutilizar PostCard en todos los listadosUna sola tarjeta que evoluciona en un sitio
Ejecutar pnpm build antes de publicarDetecta frontmatter inválido antes de producción

6 · Errores habituales

Error 1 — Configuración en la ubicación antigua

Mal 
src/content/config.ts     ← ubicación de las colecciones legacy
Bien — Content Layer (Astro 5) 
src/content.config.ts     ← raíz de src/

Error 2 — Enlazar con una propiedad que ya no existe

Mal — en Content Layer no hay slug 
<a href={`/blog/${post.slug}`}>...</a>   <!-- undefined → /blog/undefined -->
Bien 
<a href={`/blog/${post.id}`}>...</a>

Error 3 — Publicar borradores sin querer

// Sin filtro: los draft:true aparecen en el sitio
const posts = await getCollection('blog');

// El predicado excluye los borradores en TODAS las páginas
const posts = await getCollection('blog', ({ data }) => !data.draft);

Error 4 — Olvidar render() y pintar solo el frontmatter

---
const { post } = Astro.props;
---
<h1>{post.data.title}</h1>
<!-- El cuerpo no se ve: falta render + <Content /> -->

El detalle necesita const { Content } = await render(post); y colocar <Content />. Frontmatter y cuerpo son dos cosas distintas.

8 · Reto

🔥 Cierra el círculo: páginas por etiqueta

Crea la ruta dinámica /tags/[tag] que muestre solo los posts publicados con esa etiqueta, reutilizando PostCard. Debe generar una página por cada etiqueta única y, si la etiqueta no existe, no generarse (con lo que el 404 entra en acción).

Pista: en getStaticPaths, calcula las etiquetas con [...new Set(posts.flatMap((p) => p.data.tags))], genera un params: { tag } por cada una y pasa en props los posts filtrados por esa etiqueta. Dentro de la plantilla, recorre esos posts con <PostCard />. Cuida que los enlaces de PostCard y del listado de etiquetas apunten a la misma forma de URL.

9 · Resumen

  • El blog content-driven tiene una colección con loader y esquema Zod en src/content.config.ts.
  • Cada post es un fichero Markdown; añadir uno es crear un fichero, sin tocar código.
  • getCollection('blog', ({ data }) => !data.draft) lee y valida, filtrando borradores en la consulta.
  • El detalle usa [...id].astro + render(post) para obtener <Content />, headings y el frontmatter enriquecido por plugins.
  • PostCard se tipa con CollectionEntry<'blog'>: tipos siempre al día.
  • Los plugins construyen el TOC, las anclas, los enlaces externos seguros y el tiempo de lectura.
  • pnpm build valida todo el frontmatter antes de publicar.

10 · Preguntas frecuentes

¿Por qué los ids de entrada pueden llevar subcarpetas?

Con el loader glob, el id es la ruta del fichero relativa al base, sin extensión. Un post en src/content/blog/2026/hola.md tiene id 2026/hola. Por eso usamos [...id] (rest) en la ruta: admite ids con uno o varios segmentos. Si todos fueran simples, bastaría [id].

¿Cómo cambio el id de un post a mano?

Puedes usar el id del propio fichero, o reestructurar las carpetas (el id sigue la ruta). Para control total, puedes mapear ids en un loader propio. Lo habitual es dejar que la ruta del fichero determine el id: es predecible y fácil de mantener.

¿Los borradores siguen en el build?

El fichero se sigue cargando (la colección lo valida), pero al filtrar con ({ data }) => !data.draft no se genera ninguna ruta para él. Para el visitante, un borrador no existe. Es la forma segura de tener contenido en preparación dentro del repositorio sin publicarlo.

¿Puedo migrar el blog del Módulo 2 a esto sin perder trabajo?

Sí, y es justo lo que has hecho en este proyecto. Las plantillas (layouts, PostCard) apenas cambian; lo que cambia es la fuente de datos (posts.ts → colección) y el tipo de la entrada. El routing ([slug] → [...id]) es un ajuste menor. La arquitectura sobrevive a la migración: eso demuestra que estaba bien diseñada.

¿Y si algún día quiero los posts en un CMS?

La Content Layer está pensada para eso: cambias el loader (por uno que consulte el CMS) y el resto —esquema, páginas, componentes— sigue igual. El contenido deja de venir del sistema de archivos, pero la interfaz se mantiene. Es la ventaja de haber separado contenido y presentación.
