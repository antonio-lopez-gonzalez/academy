Proyecto: blog con routing

Módulo 2 · Routing y Layouts 🕐 45 minutos

1 · Introducción

Ha llegado el momento de juntar todo lo del módulo en un proyecto real y ejecutable: Bitácora Astro, un blog con portada, listado, detalle de cada artículo por ruta dinámica y página 404 propia. No es un ejercicio de laboratorio: es el esqueleto que usarías como punto de partida para un blog profesional, y sobre el que trabajarán los módulos siguientes.

El proyecto aplica las tres lecciones anteriores: routing por ficheros (lección 1), rutas dinámicas con getStaticPaths (lección 2) y layouts anidados (lección 3). Lo nuevo aquí no es una API, es la arquitectura: decidir qué vive en cada carpeta y por qué.

¿Por qué un proyecto y no más teoría? Porque el routing solo se entiende cuando lo recorres entero: datos → componente → listado → detalle. Los conceptos sueltos se olvidan; un proyecto que funciona se recuerda. Además, este es el paso previo obligatorio del Módulo 3, donde cambiarás la lista de datos por content collections y verás que la arquitectura apenas se toca.

Qué construirás: un proyecto Astro con TypeScript, datos tipados, dos layouts anidados, un componente de tarjeta y tres rutas (portada, listado, detalle), más una 404.

Errores típicos de este proyecto: duplicar la lista de posts en el listado y en el detalle (se desincronizan), meter los datos dentro de una página en lugar de en un módulo, olvidar el <slot /> del layout intermedio, y enlazar al detalle con la extensión .astro (las URLs nunca llevan la extensión).

2 · Teoría: arquitectura del blog

La forma de una app content-driven

Un blog es el ejemplo canónico de aplicación content-driven: el contenido es el protagonista y la interfaz solo lo presenta. Ese modelo impone una separación clara de responsabilidades:

      DATOS                 PLANTILLAS               RUTAS
  ┌────────────┐        ┌────────────────┐      ┌───────────────┐
  │ posts.ts   │───────▶│  PostCard      │──────▶│ /  (portada)  │
  │ (fuente de │        │  (componente)  │      │ /blog         │
  │  verdad)   │───────▶│  BaseLayout    │      │ /blog/[slug]  │
  └────────────┘        │  BlogLayout    │      │ 404           │
                        └────────────────┘      └───────────────┘

Tres capas, cada una con su papel: los datos (qué posts existen), las plantillas (cómo se ve) y las rutas (en qué URL). Si mañana los posts vienen de un CMS, solo cambia la capa de datos; si rediseñas, solo cambian las plantillas.

El árbol de carpetas

blog/
├── astro.config.mjs
├── package.json
├── tsconfig.json
└── src/
    ├── data/
    │   └── posts.ts            ← LA fuente de datos (tipada)
    ├── layouts/
    │   ├── BaseLayout.astro     ← chasis: html, head, nav, pie
    │   └── BlogLayout.astro     ← capa de artículo (usa BaseLayout)
    ├── components/
    │   └── PostCard.astro       ← tarjeta de post reutilizable
    └── pages/
        ├── index.astro          → /
        ├── 404.astro            → error 404
        └── blog/
            ├── index.astro      → /blog
            └── [slug].astro     → /blog/

Analogía: piensa en una redacción de periódico. posts.ts es la mesa de archivo donde están todos los artículos; PostCard y los layouts son los moldes de maquetación; y src/pages/ es la distribución: la portada, la sección y cada página concreta. El redactor (tú) solo escribe contenido; la maquetación es reutilizable.

Por qué los datos viven en src/data/ y no en una página

La tentación es definir el array de posts dentro de blog/index.astro. El problema aparece en cuanto el detalle necesita lo mismo: tendrías la lista dos veces y, tarde o temprano, se desincronizan (un post sin página, o una página sin post). Poniendo los datos en un módulo TypeScript, ambas rutas importan de la misma fuente. Este módulo será el que reemplaces por una content collection en el Módulo 3, sin tocar ni el listado ni el detalle.

Contrato de este proyecto: el blog tiene 3 entradas con estos slugs: hola-astro, por-que-mpa e islands. Al terminar, dist/ tendrá exactamente las rutas /, /blog/ y una carpeta por cada slug bajo /blog/.

src/pages/blog/[slug].astro
---
import BlogLayout from '../../layouts/BlogLayout.astro';
import type { Post } from '../../data/posts';
import { posts } from '../../data/posts';

// ★ getStaticPaths: una ruta por post. Sin esto no se genera ningún detalle.
export function getStaticPaths() {
  return posts.map((post) => ({
    params: { slug: post.slug },   // decide la URL
    props: { post },               // datos para la página
  }));
}

interface Props {
  post: Post;
}
const { post } = Astro.props;
---

<BlogLayout
  title={post.title}
  description={post.description}
  pubDate={post.pubDate}
  author={post.author}
>
  <p>{post.body}</p>
  <p><a href="/blog">← Todas las entradas</a></p>
</BlogLayout>
src/pages/404.astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
---

<BaseLayout title="404 · No encontrado">
  <h1>404 — Página no encontrada</h1>
  <p>Puede que el enlace esté roto o que la entrada no exista.</p>
  <p><a href="/blog">Explorar el blog</a> · <a href="/">Volver al inicio</a></p>
</BaseLayout>

Decisiones clave: un único posts.ts alimenta portada, listado y detalle; PostCard encapsula la tarjeta y recibe el post por props; BlogLayout usa BaseLayout para no duplicar el chasis; y [slug].astro genera un HTML por post con getStaticPaths. Ninguna página repite la estructura de las otras.

6 · Errores habituales

Error 1 — Duplicar la lista de posts

Mal — dos listas que se desincronizan 
<!-- En blog/index.astro -->
const posts = [{ slug: 'hola-astro', title: 'Hola, Astro' }];
<!-- Y otra lista copiada en [slug].astro -->
Bien — una fuente, dos imports 
// blog/index.astro y blog/[slug].astro
import { posts } from '../../data/posts';

Error 2 — Enlazar con la extensión del fichero

Mal — generaría un 404 
<a href={`/blog/${post.slug}.astro`}>{post.title}</a>
Bien 
<a href={`/blog/${post.slug}`}>{post.title}</a>

Error 3 — El layout intermedio pierde el contenido

<BaseLayout title={title}>
  <h1>{title}</h1>
  <!-- Falta <slot />: TODOS los posts se ven sin cuerpo -->
</BaseLayout>

En un layout anidado, cada capa debe reenviar el contenido con su propio <slot />. Si lo olvidas, el bug es silencioso: no hay error, simplemente desaparece el cuerpo del post.

Error 4 — Fichero fuera de src/pages/

Si creas src/pages/blog/[slug].astro con getStaticPaths pero luego mueves el fichero a src/components/, la ruta deja de existir y todos los enlaces al detalle dan 404. El detalle es siempre una página: vive en src/pages/.

Objetivo: crear el proyecto completo paso a paso y verificarlo con un build real.

8 · Reto

🏷️ Añade etiquetas y sus páginas

Añade a cada post un campo tags: string[]. Crea una página /tags que liste todas las etiquetas únicas, y una ruta dinámica /tags/[tag] que muestre solo los posts de esa etiqueta. Reutiliza PostCard para el listado filtrado.

Pista: para las etiquetas únicas, usa new Set(posts.flatMap((p) => p.tags)). En getStaticPaths de [tag].astro, genera un params.tag por etiqueta y pasa en props el subarray de posts filtrados. Cuidado con las etiquetas con espacios: normalízalas a kebab-case para que la URL sea limpia.

9 · Resumen

  • Un blog es una app content-driven: datos → plantillas → rutas.
  • Los datos viven en un módulo único (src/data/posts.ts) que importan todas las rutas.
  • PostCard recibe el post por props: es reutilizable en cualquier listado.
  • BlogLayout anida BaseLayout: cada capa con una responsabilidad.
  • [slug].astro + getStaticPaths generan una página de detalle por post.
  • Nunca pongas extensiones en las URLs ni dupliques la lista de datos.
  • El pnpm build es la verificación definitiva: dist/ debe contener una carpeta por slug.

10 · Preguntas frecuentes

¿Por qué no pongo los datos directamente en blog/index.astro?

Porque el detalle necesita los mismos datos. Si cada ruta tiene su propia copia, cualquier cambio (añadir un post, corregir un título) obliga a tocar dos sitios y es fácil que se desincronicen. Un módulo único en src/data/ garantiza coherencia y es justo lo que el Módulo 3 sustituirá por una content collection.

¿Cuántos layouts debo usar?

Los que necesites, pero con una responsabilidad por capa. En este blog bastan dos: uno base (chasis) y uno de artículo. Cuando añadas tipos de contenido nuevos (páginas legales, docs), añade un layout específico que use el base, en lugar de un «superlayout» con condicionales.

¿Puedo migrar este blog a content collections sin reescribirlo?

Sí, y es exactamente el plan del Módulo 3. La arquitectura (layout → componente → rutas) no cambia: solo sustituyes posts.ts por getCollection('blog') y los datos vienen de ficheros Markdown con esquema Zod. Las páginas apenas se tocan.

¿Cómo añado paginación al listado?

Dos caminos: generar rutas /blog/2, /blog/3… con una ruta dinámica /blog/[page].astro y getStaticPaths que calcule los trozos, o instalar una utilidad de paginación. Empieza por el primero: entenderás mejor qué rutas se están generando realmente.

¿Cómo despliego este blog?

Ejecuta pnpm build y sube la carpeta dist/ a cualquier hosting estático (Netlify, Vercel, Cloudflare Pages, GitHub Pages). No hay servidor que mantener porque todo es HTML estático. El despliegue a fondo se cubre en el Módulo 8.
