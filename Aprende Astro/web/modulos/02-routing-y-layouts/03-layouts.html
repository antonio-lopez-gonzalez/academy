Layouts anidados

Módulo 2 · Routing y Layouts 🕐 30 minutos

1 · Introducción

Ya tienes páginas y rutas dinámicas. Pero todas repiten lo mismo: el <head>, el <html>, la cabecera, el pie, el CSS. Si cambias el título del sitio en index.astro te toca cambiarlo también en about.astro, en blog/index.astro, en cada artículo… Es exactamente el problema que resolvimos con componentes en el Módulo 1, pero aplicado a la estructura de una página entera. La solución se llama layout.

Un layout no es más que un componente .astro con un <slot />. Nada nuevo que memorizar: es la misma caja de componentes que ya conoces, colocada alrededor del contenido. La novedad de esta lección es cómo se anidan layouts: un layout general (cabecera + pie) que envuelve a un layout más específico (artículo con fecha y autor), que a su vez envuelve a la página.

¿Por qué existen los layouts? Porque el DRY (Don't Repeat Yourself) no es estética, es mantenibilidad. Si el <title> o la etiqueta viewport viven en un solo sitio, actualizarlos cuesta un cambio, no cincuenta. Y con layouts anidados, cada capa se ocupa de una responsabilidad: la base se ocupa del HTML y el chrome; la capa intermedia, del formato de un tipo de contenido; la página, solo de su contenido único.

Cuándo usarlo: siempre que más de una página comparta estructura. En cualquier proyecto real tendrás al menos un BaseLayout. En la documentación oficial verás este mismo patrón como «nested layouts».

Errores típicos: olvidar el <slot /> (y que el contenido desaparezca sin error), poner el layout dentro de src/pages/ (¡se convierte en una ruta pública!), equivocar el nombre de un slot nombrado, y anidar layouts sin necesidad hasta tener cinco capas que solo envuelven y no aportan nada.

2 · Teoría

Un layout es un componente con un hueco

Recuerda la analogía del Módulo 1: un componente con <slot /> es como un marco de fotos. El frame (layout) pone el borde, el cristal y el soporte; el <slot /> es el hueco donde va la foto (la página). Cambia la foto y el marco sigue igual. La diferencia con un componente normal es solo dónde vive y para qué se usa: los layouts van en src/layouts/ y aportan el chasis completo del documento.

BaseLayout.astro            Page.astro
┌──────────────────────┐    ┌──────────────────┐
│ <html>               │    │ <BaseLayout>     │
│  <head>…</head>      │    │   <h1>Hola</h1>   │
│  <body>              │◀───│ </BaseLayout>    │
│    <header/>         │    └──────────────────┘
│    <slot />  ◀───────┼── el contenido de la página entra AQUÍ
│    <footer/>         │
│  </body>             │
│ </html>              │
└──────────────────────┘

Slots nombrados: varios huecos en un mismo marco

Un layout puede tener más de un hueco. El <slot /> sin nombre es el «slot por defecto»; los demás llevan un nombre con name y se rellenan desde la página con el atributo slot="...":

src/layouts/BaseLayout.astro (extracto)
<body>
  <header>
    <!-- Hueco nombrado: la página decide qué ponía aquí -->
    <slot name="header" />
  </header>

  <main>
    <!-- Slot por defecto: el contenido principal -->
    <slot />
  </main>

  <footer>
    <!-- El contenido entre las etiquetas es el FALLBACK:
         se usa si la página no rellena este slot. -->
    <slot name="footer"><p>© 2026 Mi sitio</p></slot>
  </footer>
</body>
src/pages/quien-soy.astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
---

<BaseLayout>
  <!-- Rellena el slot nombrado "header" -->
  <h1 slot="header">Quién soy</h1>

  <!-- Todo lo que NO lleva slot="" va al slot por defecto -->
  <p>Soy desarrolladora y escribo sobre Astro.</p>
  <!-- No rellenamos "footer": se usará su contenido por defecto -->
</BaseLayout>

El fallback (el contenido dentro del <slot>) es una de las mejores herramientas para layouts: permite que el layout funcione «sin instrucciones» y que la página solo especifique lo que quiere cambiar.

Astro.slots: preguntar y renderizar huecos desde el layout

Dentro del frontmatter del layout, Astro.slots te deja detectar si un slot se ha rellenado y, si quieres, renderizar su HTML programáticamente:

// ¿La página ha rellenado el slot "header"?  → true / false
const hasHeader = Astro.slots.has('header');

// Renderizar un slot a un string HTML (por ejemplo, para medir o envolver):
const html = await Astro.slots.render('header');

Esto permite layouts condicionales: mostrar una barra lateral solo si la página la rellenó, o envolver un slot en un contenedor distinto según su contenido.

Layouts anidados: capas de responsabilidad

Un layout puede usar otro layout. Así se construye la jerarquía típica de un blog: una base común, un layout intermedio para artículos y las páginas al final.

BaseLayout  (html, head, nav, footer, CSS)
   ▲
   │ usa
BlogLayout  (fecha, autor, título de artículo)  → envuelve cada post
   ▲
   │ usa
/blog/[slug].astro  (el contenido concreto del post)

Analogía: las muñecas rusas (matryoshkas). La muñeca grande (BaseLayout) contiene a la mediana (BlogLayout), que contiene a la pequeña (la página). Cada capa añade decoración propia sin romper a las de dentro. Si mañana cambias la pintura de la muñeca grande, cambia en todas a la vez.

El atajo para Markdown: layout en el frontmatter

Cuando la página es un fichero Markdown, no puedes escribir <BaseLayout> alrededor del contenido (el Markdown es el contenido). Para eso, el frontmatter acepta una clave layout con la ruta al layout:

src/pages/aviso-legal.md
---
layout: ../layouts/BaseLayout.astro
title: Aviso legal
---

Este texto es **Markdown**. Astro lo convierte a HTML y lo inyecta
en el slot por defecto del layout. Los valores del frontmatter llegan
al layout como `Astro.props.frontmatter`.

Profundizaremos en esto en el Módulo 3; aquí basta con que sepas que el concepto de layout es el mismo y que la clave layout es la forma de enchufarlo a Markdown.

3 · Ejemplo mínimo

El layout más pequeño posible, con un solo slot, y una página que lo usa.

src/layouts/BaseLayout.astro
---
// Las props que la página pasa al layout, tipadas.
interface Props {
  title: string;      // se usará en <title>
}

const { title } = Astro.props;
---

<!DOCTYPE html>
<html lang="es">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <!-- El título viene del layout, la página solo lo rellena -->
    <title>{title}</title>
  </head>
  <body>
    <header><a href="/">Mi sitio</a></header>

    <main>
      <!-- ★ El hueco. Sin esta línea, el contenido de la página desaparece. -->
      <slot />
    </main>

    <footer><small>© 2026 Mi sitio</small></footer>
  </body>
</html>
src/pages/index.astro
---
// La página importa el layout (ruta relativa desde src/pages/)
import BaseLayout from '../layouts/BaseLayout.astro';
---

<!-- La página NO repite <html>, <head> ni <body>: lo pone el layout. -->
<BaseLayout title="Inicio">
  <h1>¡Bienvenida!</h1>
  <p>Este contenido se inyecta en el <slot /> del layout.</p>
</BaseLayout>

Línea por línea: el layout define la estructura completa del documento y recibe title por props. La página se limita a importar y usar el layout, metiendo su contenido entre las etiquetas: ese contenido es lo que ocupa el <slot />. Fíjate en que la página ya no tiene <html> ni <head>: el chasis entero viene del layout. Si comentas el <slot /> del layout, verás la página vacía: esa es la comprobación de que el slot es imprescindible.

4 · Ejemplo real

El blog del módulo, ahora con dos capas: un BaseLayout con chrome general y slots nombrados, y un BlogLayout que lo envuelve para dar formato a los artículos.

src/layouts/BaseLayout.astro
---
interface Props {
  title: string;
  description?: string;   // opcional: no todas las páginas tienen descripción
}

const { title, description = 'Blog construido con Astro' } = Astro.props;
---

<!DOCTYPE html>
<html lang="es">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>{title}</title>
    <meta name="description" content={description} />
  </head>
  <body>
    <header>
      <nav>
        <a href="/">Inicio</a>
        <a href="/blog">Blog</a>
      </nav>
      <!-- Slot nombrado: la página puede añadir migas de pan o un título grande -->
      <slot name="header" />
    </header>

    <main>
      <!-- Slot por defecto: el contenido principal de la página -->
      <slot />
    </main>

    <footer>
      <!-- Fallback: si la página no define "footer", se usa esto -->
      <slot name="footer"><small>© 2026 Bitácora Astro</small></slot>
    </footer>
  </body>
</html>
src/layouts/BlogLayout.astro
---
import BaseLayout from './BaseLayout.astro';

// Este layout ENVUELVE al BaseLayout: layouts anidados.
interface Props {
  title: string;
  pubDate: Date;
  author: string;
}

const { title, pubDate, author } = Astro.props;
---

<!-- Le pasamos el título al BaseLayout; el resto lo pinta este layout -->
<BaseLayout title={title}>
  <article>
    <header>
      <h1>{title}</h1>
      <p>
        Por {author} · <time datetime={pubDate.toISOString()}>
          {pubDate.toLocaleDateString('es-ES')}
        </time>
      </p>
    </header>

    <!-- El contenido del post entra aquí (slot por defecto heredado) -->
    <slot />
  </article>
</BaseLayout>
src/pages/blog/[slug].astro (extracto del uso)
---
import BlogLayout from '../../layouts/BlogLayout.astro';
import { posts } from '../../data/posts';

export function getStaticPaths() {
  return posts.map((post) => ({
    params: { slug: post.slug },
    props: { post },
  }));
}

const { post } = Astro.props;
---

<BlogLayout title={post.title} pubDate={post.pubDate} author="Ana">
  <p>{post.body}</p>
</BlogLayout>

Decisiones: BlogLayout solo se ocupa de lo común a los artículos (título, fecha, autor) y delega el chasis en BaseLayout. La página del post solo importa BlogLayout: no necesita saber que existe un BaseLayout por debajo. Esa es la virtud del anidamiento: cada capa conoce solo a la inmediatamente inferior. Si mañana cambias el pie de página, tocas BaseLayout y ya está en todo el sitio.

Depuración con DevTools: abre un post en pnpm dev, inspecciona el DOM y verás que el HTML final es la composición de las tres capas (BaseLayout → BlogLayout → página). Si algo falta, busca el layout que se ha dejado el <slot /> en el camino.

6 · Errores habituales

Error 1 — El layout no tiene <slot />

Mal — el contenido de la página desaparece sin error 
<body>
  <header>Mi sitio</header>
  <!-- Falta <slot />: la página se renderiza VACÍA -->
  <footer>© 2026</footer>
</body>
Bien 
<body>
  <header>Mi sitio</header>
  <main><slot /></main>   <!-- el contenido entra aquí -->
  <footer>© 2026</footer>
</body>

Error 2 — El layout vive en src/pages/

Mal — acabas de crear la ruta /layouts/BaseLayout 
src/pages/layouts/BaseLayout.astro   ← ¡es una página pública!
Bien 
src/layouts/BaseLayout.astro         ← carpeta solo para layouts

Error 3 — El nombre del slot no coincide

Mal — name="header" vs slot="hedaer" 
<!-- layout -->
<slot name="header" />
<!-- página: nunca encontrará este slot y el contenido no se muestra -->
<h1 slot="hedaer">Título</h1>
Bien 
<slot name="header" />
<h1 slot="header">Título</h1>

Error 4 — Olvidar el <slot /> en un layout anidado intermedio

<BaseLayout title={title}>
  <h1>{title}</h1>
  <!-- Falta <slot />: el contenido del post se pierde aquí -->
</BaseLayout>

Cada capa de la cadena debe reenviar el contenido hacia abajo. Un BlogLayout sin <slot /> convertiría todos los artículos en solo el título.

8 · Reto

🧩 Layout con barra lateral opcional

Crea un DocsLayout.astro que tenga un slot aside para una barra lateral de navegación. Si la página no rellena ese slot, el layout debe ocupar todo el ancho con el contenido (sin dejar el hueco vacío). Usa Astro.slots.has('aside') en el frontmatter para decidir la clase CSS del contenedor.

Pista: const hasAside = Astro.slots.has('aside'); y luego <div class={hasAside ? 'con-aside' : 'sin-aside'}>. Crea dos páginas de prueba: una con contenido en slot="aside" y otra sin él, y compara el ancho en el navegador.

9 · Resumen

  • Un layout es un componente .astro con <slot /> que envuelve páginas.
  • Los layouts viven en src/layouts/, nunca en src/pages/.
  • Los slots nombrados (name / slot="...") permiten varios huecos; el contenido del <slot> es el fallback.
  • Astro.slots.has() y Astro.slots.render() permiten layouts condicionales.
  • Los layouts se anidan: cada capa conoce solo a la de dentro y debe reenviar el contenido con su propio <slot />.
  • En Markdown, el layout se enchufa con la clave layout del frontmatter.

10 · Preguntas frecuentes

¿Diferencia entre un layout y un componente normal?

Técnicamente ninguna: ambos son componentes .astro. La diferencia es de intención y ubicación. Un layout aporta el chasis de una página completa (con <html>, <head>, <body>) y vive en src/layouts/; un componente es una pieza reutilizable de interfaz y vive en src/components/. Un layout puede usar componentes; un componente rara vez es un layout.

¿Puedo pasar varios slots a un layout?

Sí: un slot por defecto más tantos nombrados como quieras. Cada uno se rellena con el atributo slot="nombre" desde la página. Los slots nombrados son perfectos para cabeceras, barras laterales o pies personalizados por página.

¿Puedo anidar layouts indefinidamente?

Sí, pero no deberías. Dos o tres capas cubren casi todo (base → tipo de contenido → página). Más capas suelen indicar que un layout está asumiendo demasiadas responsabilidades. Si necesitas más, plantéate dividir por slots en lugar de por capas.

¿El layout puede acceder al contenido que le pasa la página?

No directamente como texto, pero sí puede consultar Astro.slots.has() y renderizar el slot a HTML con await Astro.slots.render() si necesita procesarlo. Lo normal es no necesitarlo: el layout coloca el <slot /> y el navegador compone el HTML final.

¿Cómo usa un fichero Markdown un layout?

Con la clave layout en el frontmatter, apuntando a la ruta del layout. El Markdown convertido a HTML se inyecta en el slot por defecto, y los datos del frontmatter llegan al layout en Astro.props.frontmatter. Lo verás a fondo en el Módulo 3.
