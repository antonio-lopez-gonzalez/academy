Componentes .astro, frontmatter y template

Módulo 1 · Componentes Astro 🕐 30 minutos

1 · Introducción

Los componentes .astro son los ladrillos de cualquier proyecto Astro: desde un botón hasta una página completa. La buena noticia es que si sabes HTML, ya sabes el 80 %. La parte nueva es pequeña pero crucial: entender que un componente tiene dos zonas con dos vidas muy distintas —una que se ejecuta en el servidor y otra que produce el HTML final— y que no existe un runtime en el navegador para ellos.

En esta lección verás la anatomía exacta de un .astro, las reglas de la zona de frontmatter (delimitada por ---) y del template, cómo interpolar datos y cómo funcionan las expresiones. Terminaremos entendiendo por qué Astro puede prometer «cero JavaScript» y en qué casos excepcionales sí añade scripts.

🎯 Por qué existe esta lección

Porque todo lo demás —props, slots, layouts, islas— son matices de este mismo archivo. Si confundes las dos zonas (servidor y template), acabarás intentando usar APIs del navegador en el frontmatter o esperando estado reactivo donde no lo hay. Con la anatomía clara, el resto encaja.

2 · Teoría

Anatomía: dos zonas, dos mundos

Un componente Astro se compone de tres bloques opcionales, en este orden:

┌──────────────────────────────────────┐
│  ---                                 │  ◀── 1. FRONTMATTER (o "component script")
│  // JavaScript/TypeScript de SERVIDOR│      Corre en build/SSR. Nunca llega al navegador.
│  ---                                 │      Aquí van imports, fetch, variables, props.
├──────────────────────────────────────┤
│  <!-- TEMPLATE: HTML + expresiones --> │  ◀── 2. TEMPLATE
│  <h1>{titulo}</h1>                   │      Es lo que se renderiza a HTML.
│                                      │      Admite llaves {…} y componentes.
├──────────────────────────────────────┤
│  <style> … </style>                  │  ◀── 3. ESTILOS (opcional)
│                                      │      Se extraen y se aplican con scope.
└──────────────────────────────────────┘

Hay una manera de recordarlo que funciona siempre: el frontmatter es como una función; el template es su valor de retorno. Toda la lógica vive arriba; abajo solo se describe el resultado.

1. El frontmatter (entre ---)

Las tres rayas son la frontera de seguridad. Todo lo que escribas aquí es TypeScript que corre en el servidor o durante el build. Su contenido se elimina del HTML final salvo por lo que decidas imprimir en el template.

src/components/Saludo.astro (frontmatter)
---
// ─── Importaciones: entre otros componentes, datos o CSS ───
import OtroComponente from './OtroComponente.astro';
import datos from '../data/paises.json';

// ─── Lógica de servidor: variables, cálculos, fetch ───
const paises = datos.map((p) => p.nombre);
const total = paises.length;
const ahora = new Date().toISOString();

// ─── Esto se ejecuta en el servidor. Si hay un error, se ve en la terminal. ───
console.log('Renderizando Saludo en el servidor a las', ahora);
---

Propiedades del frontmatter que conviene interiorizar:

  • Es seguro para secretos (no se envía), pero solo si no los imprimes luego en el template.
  • Admite await de primer nivel: puedes hacer const data = await fetch(...) directamente, sin envolverlo en una función asíncrona.
  • Es TypeScript por defecto en archivos .astro, aunque no escribas anotaciones.
  • No puede usar APIs del navegador (window, document, localStorage) porque no existen en el servidor.

2. El template: HTML primero

Debajo de las rayas, el template es HTML. Puedes escribir cualquier etiqueta válida, anidarla y cerrarla. Lo que lo hace potente son las expresiones con llaves, igual que en JSX pero sin necesidad de className ni de reglas raras de atributos.

src/components/Saludo.astro (template)
<!-- Interpolar un valor: Astro lo convierte a texto y lo escapa -->
<h1>Buenos días desde {total} países</h1>

<!-- Listas con .map(): devolvemos HTML por cada elemento -->
<ul>
  {paises.map((nombre) => <li>{nombre}</li>)}
</ul>

<!-- Atributos dinámicos con llaves, sin comillas alrededor -->
<img src="/logo.svg" alt={`Logotipo ${total}`} width="48" height="48" />

<!-- Comentarios: se ELIMINAN del HTML final -->
{/* este comentario no llega al navegador */}

<!-- Usar un componente importado como si fuera una etiqueta -->
<OtroComponente />

Detalles que sorprenden a quien viene de React:

  • Clases normales: se usa class, no className.
  • Comentarios de plantilla: {/* … */} desaparecen del HTML; los <!-- --> sí se envían (ten cuidado).
  • HTML real: no hace falta cerrar con /> las etiquetas de componentes vacíos sí, pero las etiquetas HTML se comportan como HTML.
  • Autoescape: {variable} escapa por defecto, evitando inyección de HTML. Para HTML deliberado se usa set:html (consciente del riesgo).

3. Estilos con scope

El bloque <style> es local al componente por defecto: Astro transforma los selectores para que solo apliquen a este componente. Eso evita colisiones de CSS sin necesidad de BEM ni de una librería.

src/components/Boton.astro
<button class="btn">Pulsa</button>

<style>
  /* Este ".btn" solo afecta a botones de ESTE componente. */
  .btn {
    background: #ff5d01; /* naranja característico de Astro */
    color: white;
    border: none;
    padding: 8px 16px;
    border-radius: 8px;
  }
  /* Para estilos globales: <style is:global> o un archivo importado. */
</style>

Por qué no hay runtime en el cliente

Esta es la idea que sostiene todo Astro. En React, cada componente es una función que se re-ejecuta en el navegador cuando cambia el estado; por eso hace falta enviar el framework (decenas de kB) y el árbol entero. En Astro, el componente es una función que se ejecuta una vez, en el servidor, y cuyo resultado es texto HTML. Una vez enviado, no queda nada que ejecutar: no hay función que «volver a llamar».

React (runtime en cliente)              Astro (sin runtime)
──────────────────────────              ───────────────────
Component() ─┐                          Component() ──▶ HTML string
              │  se envía la función                  (una sola vez, en servidor)
              ▼  + el framework                        │
        navegador la re-ejecuta                          ▼
        en cada cambio de estado                   navegador muestra HTML
        (Virtual DOM diffs)                        y NO ejecuta nada más

Cuando de verdad necesitas interactividad (contador, formulario, carrito), Astro ofrece dos caminos que verás en módulos posteriores:

  • Un <script> propio en el componente: JavaScript de cliente, empaquetado y con scope, que se ejecuta en el navegador. Es la vía ligera, sin framework.
  • Una isla de framework (client:*): un componente React/Vue/Svelte que se hidrata por separado. Es la vía para interactividad compleja (Módulo 4).

🏭 Analogía: la imprenta

Un componente Astro es una imprenta: recibe datos en la fábrica, imprime una hoja y la envía. El lector recibe la hoja ya escrita y no tiene que montar ninguna máquina. React, en cambio, envía la máquina a cada lector para que componga el texto en su casa. Si el texto no cambia, la imprenta es mucho más eficiente.

3 · Ejemplo mínimo

El componente más pequeño con las tres zonas. Imprímelo en tu cabeza como el «esqueleto cero» que memorizarás sin esfuerzo.

src/components/Firma.astro
---
// 1) ZONA DE SERVIDOR: variables que el template consumirá.
const autor = 'Ada Lovelace';
const year = new Date().getFullYear();
---

<!-- 2) TEMPLATE: HTML + expresiones entre llaves -->
<p class="firma">
  Escrito por {autor} en {year}.
</p>

<style>
  /* 3) ESTILOS con scope local a este componente */
  .firma { font-style: italic; opacity: 0.8; }
</style>

Línea por línea:

  • --- … ---: el bloque de servidor. autor y year existen solo para el render.
  • {autor}, {year}: expresiones. Se resuelven en el servidor y el HTML final lo dice ya en texto plano.
  • class="firma": HTML normal; se usa class, no className.
  • <style>: se extrae a CSS con scope; no viaja JavaScript.

💡 Sin estado ni eventos

Date cuenta de que no hay useState, ni listeners, ni nada reactivo. Si quisieras que al pulsar cambiara algo, ese sería el momento de añadir un <script> o una isla. En HTML estático, no hay nada que «re-renderizar».

4 · Ejemplo real

Un componente profesional: una tarjeta de persona que recibe datos, calcula cosas en servidor, importa una imagen optimizada y define estilos con scope. Verás cómo conviven las tres zonas en un caso realista.

src/components/PersonCard.astro
---
// ─── SERVIDOR ───
// Tipamos las props con una interfaz (lo veremos a fondo en la lección 2).
interface Props {
  name: string;
  role: string;
  avatar: ImageMetadata; // tipo que Astro da a las imágenes importadas
  since: number;
}

const { name, role, avatar, since } = Astro.props;

// Cálculos de servidor: se hacen UNA vez en el build.
const yearsInTeam = new Date().getFullYear() - since;
const initials = name
  .split(' ')
  .map((part) => part[0])
  .join('')
  .toUpperCase();
---

<article class="card">
  <!-- Imagen optimizada por Astro (Módulo 6) -->
  <img src={avatar.src} width={avatar.width} height={avatar.height} alt={name} />
  <div>
    <h3>{name}</h3>
    <p class="role">{role}</p>
    <p class="meta">{initials} · {yearsInTeam} año(s) en el equipo</p>
  </div>
</article>

<style>
  .card { display: flex; gap: 12px; align-items: center; }
  .role { color: #666; margin: 0; }
  .meta { font-size: 0.85rem; opacity: 0.7; }
</style>

Y así se usa desde una página, pasándole datos reales importados:

src/pages/equipo.astro
---
import PersonCard from '../components/PersonCard.astro';
import anaAvatar from '../assets/ana.jpg';
import luisAvatar from '../assets/luis.jpg';

// Datos de servidor: podrían venir de una API o colección (Módulo 3).
const equipo = [
  { name: 'Ana Torres', role: 'Frontend', avatar: anaAvatar, since: 2022 },
  { name: 'Luis Gómez', role: 'Backend', avatar: luisAvatar, since: 2024 },
];
---

<section>
  <h1>Nuestro equipo</h1>
  {equipo.map((persona) => <PersonCard {...persona} />)}
</section>

Decisiones y por qué:

  • El tipado de props (interface Props) da autocompletado y errores si olvidas un dato; lo verás en detalle en la lección siguiente.
  • Los cálculos viven en el frontmatter: yearsInTeam y las iniciales se calculan una vez, no en cada visita del usuario.
  • {...persona} reenvía todas las propiedades del objeto como props; es el mismo spread de JavaScript.
  • ImageMetadata es el tipo que Astro asigna a un import de imagen, con src, width y height.
  • Sin estado: dos personas o doscientas, el HTML se genera en build y se sirve igual para todos.

📌 Compón con componentes

Los componentes usan componentes. PersonCard podría estar dentro de un TeamSection, dentro de un Layout. La composición es la forma de construir UI compleja sin repetir HTML: cada pieza se escribe una vez y se combina.

6 · Errores habituales

1. Usar APIs del navegador en el frontmatter

Mal — el frontmatter corre en servidor, no hay window 
---
// ❌ ReferenceError: window is not defined
const temaGuardado = window.localStorage.getItem('tema');
const ancho = document.documentElement.clientWidth;
---
Bien — esos datos se leen en el cliente, dentro de un script 
<p id="tema">Tema desconocido</p>

<script>
  // ✅ Este script SÍ corre en el navegador: aquí window y document existen.
  const tema = localStorage.getItem('tema') ?? 'claro';
  document.getElementById('tema').textContent = `Tema: ${tema}`;
</script>

Regla simple: si necesitas window, document, localStorage o eventos, estás en la zona de cliente (un <script> o una isla).

2. Confundir el template con JSX

Mal — sintaxis de React en un .astro 
<div className="card" onClick={() => alert('hola')}>
  <img src={foto} />
</div>
<!-- ❌ className no es clase en HTML puro; onClick no existe sin runtime. -->
Bien — HTML puro y eventos en un script 
<div class="card" data-accion="saludar">
  <img src={foto} alt="Foto" />
</div>

<script>
  // ✅ El listener se engancha en el cliente, no como atributo del template.
  document.querySelector('[data-accion="saludar"]')?.addEventListener('click', () => {
    alert('hola');
  });
</script>

3. Escapar los comentarios de plantilla a la ligera

Mal — usar comentarios HTML para notas internas 
<!-- TODO: preguntar a Ana por el precio -->
<p>Precio: {precio}</p>
<!-- ❌ Este comentario SÍ viaja al navegador: cualquiera lo lee en el source. -->
Bien — comentario de plantilla que se elimina 
{/* TODO interno: no llega al cliente, se elimina en el render */}

Los comentarios <!-- --> se sirven tal cual; los {/* */} se eliminan. No pongas notas privadas en comentarios HTML.

7 · Ejercicio guiado

Objetivo: escribir tu primer componente .astro con las tres zonas y usarlo desde la página de inicio calculando algo en el servidor.

  1. Paso 1 — crea el componente. En src/components/, añade Enganche.astro que muestre una fecha futura y los días que faltan hasta ella.
  2. Paso 2 — escribe el frontmatter. Declara una fecha objetivo y calcula la diferencia en días con JavaScript de servidor.
  3. Paso 3 — escribe el template. Muestra ambos valores con expresiones entre llaves. Añade una clase para estilar.
  4. Paso 4 — añade estilos con scope. Un bloque <style> que dé color y tipografía al enganche.
  5. Paso 5 — úsalo en la página. Impórtalo en src/pages/index.astro y colócalo dentro del body.
  6. Paso 6 — verifica el servidor. Añade un console.log en el frontmatter y confirma que aparece en la terminal de pnpm dev, no en la consola del navegador.

Solución paso a paso.

src/components/Enganche.astro
---
// 1) SERVIDOR: fecha objetivo y cálculo de días restantes.
const objetivo = new Date('2026-12-31');
const hoy = new Date();
// Diferencia en milisegundos → días (redondeado hacia arriba).
const MS_POR_DIA = 1000 * 60 * 60 * 24;
const dias = Math.ceil((objetivo.getTime() - hoy.getTime()) / MS_POR_DIA);

// 2) Este log aparece en la TERMINAL, no en la consola del navegador.
console.log('Enganche renderizado, faltan', dias, 'días');
---
<aside class="enganche">
  <p>Fin de año: {objetivo.toLocaleDateString('es-ES')}</p>
  <p class="contador">Faltan {dias} días</p>
</aside>

<style>
  .enganche { border: 1px solid #ff5d01; border-radius: 8px; padding: 12px; }
  .contador { font-weight: 700; color: #ff5d01; }
</style>
src/pages/index.astro
---
import Enganche from '../components/Enganche.astro';
---
<html lang="es">
  <body>
    <h1>Inicio</h1>
    <Enganche />
  </body>
</html>

✅ Resultado esperado

La página muestra la fecha y el número de días, ya «cocidos» en el HTML (míralo con «Ver código fuente»: el número está escrito, no lo calcula el navegador). Y el console.log aparece en la terminal de pnpm dev. Esa separación de mundos es el corazón de la lección.

🎯 Un componente sin JavaScript (y que lo demuestre)

Construye un componente TablaPrecios.astro que reciba en el frontmatter un array de planes (nombre, precio, características) y genere una tabla comparativa completa. Después demuéstralo: abre el código fuente de la página generada y busca cada precio en el HTML, y confirma en la pestaña Network que no se descargó ningún JavaScript para hacerlo.

9 · Resumen

  • Un componente .astro tiene tres zonas: frontmatter (---), template (HTML) y estilos (<style>).
  • El frontmatter es de servidor: corre en build/SSR, admite await de primer nivel y nunca llega al navegador (salvo lo que imprimas).
  • El template es HTML con expresiones {…}; se usa class, los comentarios {/* */} se eliminan y el HTML se auto-escapa.
  • Los estilos tienen scope por componente por defecto.
  • No hay runtime en el cliente: el componente se ejecuta una vez y produce HTML. La interactividad se añade con <script> o islas client:*, y solo donde hace falta.

10 · Preguntas frecuentes

¿Puedo usar async/await en el frontmatter sin envolverlo en una función?

Sí. El frontmatter admite top-level await: puedes escribir const res = await fetch(url) directamente. Es una comodidad enorme para pedir datos en build o en SSR sin la ceremonia de las funciones asíncronas. Recuerda que ese fetch ocurre en el servidor, no en el navegador.

Si no hay runtime, ¿cómo hago que un botón haga algo?

Añades JavaScript de cliente explícitamente, de una de estas dos formas: (1) un <script> dentro del componente, que Astro empaqueta y ejecuta en el navegador; o (2) una isla, un componente de framework (React, Vue…) marcado con client:* que se hidrata por separado. Lo verás en el Módulo 4; por ahora quédate con que la interactividad es siempre una decisión consciente.

¿Los <style> del componente se envían como parte del HTML?

No tal cual. Astro los extrae, les aplica scope (los selectores se modifican para no afectar a otros componentes), los combina y los sirve como CSS optimizado. Lo que llega al navegador es CSS, nunca JavaScript, y solo el que usa la página.

¿Por qué a veces veo class y otras className?

En un archivo .astro se usa class, porque es HTML. className es la forma de React y solo aparece si el código es un componente .jsx/.tsx (una isla). Mezclar mentalmente React y Astro es el origen de varios despistes al principio.

¿Puedo importar un componente de React dentro de un .astro y usarlo sin más?

Sí, con la integración instalada (pnpm astro add react). Pero ojo: si lo usas sin directiva client:*, se renderiza a HTML estático en el servidor y no será interactivo. La directiva es lo que decide que se convierta en isla. Ese matiz es la clave del Módulo 4.
