OIDC: desplegar sin claves

Módulo 2 · Identidad y seguridad 🕐 30 minutos

1 · Introducción

El pipeline de CI/CD es, sin querer, uno de los mayores agujeros de seguridad de un proyecto. Para que GitHub Actions despliegue en tu cuenta de cloud, alguien creó un «secreto» de despliegue: una clave de larga vida guardada en Settings → Secrets. Esa clave no caduca, sirve desde cualquier sitio y, si se filtra en un log o en un PR malicioso, da acceso a tu cuenta hasta que alguien se acuerde de revocarla.

Esta lección elimina ese secreto de raíz con OIDC (OpenID Connect): el pipeline demuestra quién es con un token que GitHub firma y que caduca en minutos, y el cloud le da credenciales temporales a cambio. No hay nada que guardar, nada que rotar y nada que robar más allá de unos minutos.

¿Por qué esta lección cierra el módulo? Porque aplica todo lo anterior a la pieza que más claves de larga vida acumula: la automatización. Identidad (lección 01) + sin secretos guardados (lección 02) + mínimo privilegio y ámbito (lecciones 01 y 03) + federación en vez de password. OIDC es el patrón que hace que tu pipeline sea igual de seguro que tu aplicación en ejecución.

Errores típicos: guardar AZURE_CREDENTIALS o las claves de AWS como secreto de GitHub, crear un usuario de CI con clave de acceso permanente, usar un subject con comodín (repo:org/*) que permite desplegar desde cualquier repositorio de la organización, y olvidar el permiso id-token: write, que hace que OIDC simplemente no funcione.

2 · Teoría

El problema de las claves de larga vida

Una clave de despliegue vive demasiado. Entre que se crea y se revoca, pasa por muchos sitios: la configuración del repositorio, portátiles de quien la copió, logs del pipeline, cachés. Y su radio de daño suele ser enorme, porque se le concede «lo que haga falta» para desplegar. OIDC invierte la lógica: en vez de un secreto que llevas contigo, demuestras tu identidad y recibes un permiso temporal.

Analogía: la clave de larga vida es una llave maestra que copias y repartes. OIDC es un portero que comprueba tu identidad en el momento y te deja pasar a la zona que te corresponde, con un pase que caduca en el mismo turno. Si alguien intercepta el pase, al minuto ya no sirve.

Cómo funciona la federación (paso a paso)

 1. El workflow pide un token OIDC a GitHub       GitHub Actions
    (necesita permiso id-token: write)           (token.actions.githubusercontent.com)
             |                                          |
             |------ "dame un token firmado" --------->|
             |<----- JWT firmado, dura ~minutos -------|
             |
 2. El workflow presenta el JWT al cloud
             |
 3. El cloud comprueba la FIRMA y las CLAIMS
    (issuer, audience, subject) contra la CONFIANZA
    que le configuraste previamente
             |
 4. Si coincide, emite credenciales TEMPORALES
    para el rol/identidad que toca
             |
 5. El workflow despliega en Azure/AWS con esas credenciales
    (sin haber guardado ninguna clave en el repositorio)

Las claims del token son las que deciden si se concede el acceso. Las que más se usan para restringir:

ClaimEjemploPor qué importa
iss (issuer)https://token.actions.githubusercontent.comIdentifica a GitHub como emisor de confianza
aud (audience)api://AzureADTokenExchange (Azure) · sts.amazonaws.com (AWS)Evita que un token emitido para otro servicio sirva aquí
sub (subject)repo:mi-org/mi-repo:ref:refs/heads/mainLa restricción más importante: saber qué repo, rama o entorno puede usarlo
environmentproductionPermite exigir aprobación humana antes de desplegar

El patrón environment: si configuras el subject como repo:org/repo:environment:production y el workflow declara environment: production, entonces el despliegue necesita pasar por las protection rules de ese entorno (aprobación, ramas permitidas, espera). Es la forma más limpia de que un despliegue a producción requiera un visto bueno humano sin añadir secretos.

Azure y AWS: mismo concepto, distinto vocabulario

Fíjate en algo importante: ninguno de los identificadores que verás en el workflow es un secreto. El client-id de Azure o el ARN del rol de AWS son datos públicos. Lo que protege el acceso es la condición de confianza, no el ocultamiento.

3 · Ejemplo mínimo

El workflow más pequeño que se autentica en Azure con OIDC: dos bloques, uno que concede el permiso para pedir el token y otro que hace el login. Nada de secrets.

.github/workflows/deploy.yml
name: deploy

on:
  push:
    branches: [main]

# 1) El permiso CLAVE: sin id-token: write, GitHub no emite el token OIDC
#    y azure/login se cae. Es la causa numero uno de "no funciona".
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 2) Login federado: NO hay password ni client secret.
      #    client-id, tenant-id y subscription-id son IDENTIFICADORES
      #    publicos, no secretos.
      - name: Azure login (OIDC)
        uses: azure/login@v2
        with:
          client-id:       ${{ vars.AZURE_CLIENT_ID }}
          tenant-id:       ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      # 3) A partir de aqui el token dura minutos: despliega lo que necesites.
      - name: Comprueba la identidad en Azure
        run: az account show --query "{cuenta:name, usuario:user.name}" -o table

Qué acaba de pasar:

  1. permissions: id-token: write: autoriza al workflow a pedir un token OIDC. Sin esta línea el resto es papel mojado.
  2. azure/login@v2 con client-id: el action pide el token a GitHub, lo presenta a Entra ID y recibe credenciales temporales para la identidad federada. Todo automático.
  3. az account show: verifica que el login funcionó. Es tu «hello world»: si muestra la cuenta correcta, la federación está bien configurada.

Los valores van en vars (variables del repositorio), no en secrets. No es un detalle estético: al ponerlos como variables dejas claro en el propio workflow que no hay ningún secreto y que la seguridad viene de la configuración de confianza.

4 · Ejemplo real

En el Copiloto, la identidad de despliegue es una identidad gestionada user-assigned con una federated identity credential que solo acepta tokens de la rama main de tu repositorio. Esa identidad recibe el mínimo permiso para desplegar la infraestructura.

proyectos/infra-cloud/oidc.tf
# ---------------------------------------------------------------------------
# Identidad dedicada al pipeline (no la del dia a dia de una persona).
# ---------------------------------------------------------------------------
resource "azurerm_user_assigned_identity" "github" {
  name                = "id-copiloto-github"
  location            = azurerm_resource_group.rg.location
  resource_group_name = azurerm_resource_group.rg.name
}

# ---------------------------------------------------------------------------
# LA CONFIANZA: aceptamos tokens de GitHub, del repo concreto y de la rama
# main. El subject es lo que impide que otro repo use esta identidad.
#  - audience: el valor que Entra ID espera para el token de intercambio.
#  - issuer:   el emisor OIDC de GitHub Actions.
# ---------------------------------------------------------------------------
resource "azurerm_federated_identity_credential" "github_main" {
  name                = "github-main"
  user_assigned_identity_id = azurerm_user_assigned_identity.github.id
  audience            = ["api://AzureADTokenExchange"]
  issuer              = "https://token.actions.githubusercontent.com"
  subject             = "repo:${var.github_org}/${var.github_repo}:ref:refs/heads/main"
}

# ---------------------------------------------------------------------------
# El rol que ese pipeline puede ejercer: Contributor sobre el grupo de
# recursos, donde vive todo lo que despliega (nunca Owner ni la suscripcion).
# ---------------------------------------------------------------------------
resource "azurerm_role_assignment" "github_deploy" {
  scope                = azurerm_resource_group.rg.id
  role_definition_name = "Contributor"
  principal_id         = azurerm_user_assigned_identity.github.principal_id
}

Y así se usa desde el workflow, sin un solo secreto guardado:

.github/workflows/terraform.yml
name: terraform

on:
  push:
    branches: [main]
    paths:
      - "proyectos/infra-cloud/**"

permissions:
  id-token: write   # pedir el token OIDC
  contents: read    # leer el repositorio

jobs:
  apply:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Azure login (OIDC)
        uses: azure/login@v2
        with:
          client-id:       ${{ vars.AZURE_CLIENT_ID }}
          tenant-id:       ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: terraform apply
        working-directory: proyectos/infra-cloud
        run: |
          terraform init
          terraform apply -auto-approve

Y el equivalente en AWS, donde la confianza vive en la trust policy del rol. En Terraform se escribe así, sin JSON a mano:

proyectos/infra-cloud/aws-oidc.tf (alternativa AWS)
# Proveedor OIDC de GitHub: AWS confia en los tokens que GitHub firma.
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  # Solo hace falta aportar thumbprints en proveedores antiguos;
  # AWS valida el certificado de GitHub para este emisor conocido.
}

# Trust policy del rol: quien puede asumirlo y con que claims.
data "aws_iam_policy_document" "github_trust" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }

    # Audiencia: el token es para AWS.
    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    # Subject: solo la rama main de ESTE repositorio.
    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:${var.github_org}/${var.github_repo}:ref:refs/heads/main"]
    }
  }
}

resource "aws_iam_role" "github_deploy" {
  name               = "copiloto-github-deploy"
  assume_role_policy = data.aws_iam_policy_document.github_trust.json
}

Y en el workflow de AWS se usa la action oficial con el ARN del rol, que es público:

.github/workflows/deploy-aws.yml (fragmento)
permissions:
  id-token: write
  contents: read

steps:
  - uses: actions/checkout@v4

  - name: Configura credenciales AWS (OIDC)
    uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
      aws-region: eu-west-1

Tres decisiones que merecen explicación:

  1. El subject fija el repositorio Y la rama. No es «cualquier repo de la organización»: es exactamente org/repo en main. Eso es mínimo privilegio aplicado a la identidad del pipeline.
  2. Contributor sobre el grupo de recursos, no Owner en la suscripción. El pipeline puede crear y cambiar recursos, pero no repartir permisos ni tocar otras suscripciones.
  3. Ningún identificador es un secreto. Si alguien ve el client-id, no puede hacer nada sin un token de ese repositorio y esa rama.

Para producción, sube el listón: usa subject = "repo:org/repo:environment:production" y declara environment: production en el workflow. Así el despliegue pasa a depender de una aprobación registrada, y el rol de producción queda separado del de staging (dos identidades federadas distintas).

5 · Buenas prácticas

HazEvitaPor qué
Federación OIDC para todo pipeline que toque el cloud Guardar claves de cloud como secretos de GitHub Sin secreto permanente no hay nada que filtrar ni que rotar
Restringe el subject al repo y a la rama (o entorno) Comodines como repo:org/* o ref:refs/heads/* Un comodín convierte cualquier repo comprometido en una vía de despliegue
Una identidad de despliegue por entorno (dev, staging, prod) Una sola identidad con permisos en todos los entornos Limita el daño de un workflow comprometido a un solo entorno
Declara id-token: write solo en el job que lo necesita Conceder id-token: write a todo el workflow por costumbre Menos permisos efectivos y más difícil que un paso ajeno abuse del token
Usa environment con reglas de protección para producción Desplegar a producción con cualquier push a cualquier rama Añade una revisión humana sin introducir credenciales nuevas
Registra en Terraform las credenciales federadas y los roles Crear la federación a mano en el portal La confianza queda revisable en un pull request y reproducible

Ojo con los pull requests de forks: un PR desde un fork no recibe permisos de escritura ni id-token por defecto, precisamente para que no pueda desplegar. No «arregles» esto concediendo id-token: write a eventos de PR: es la barandilla que te protege de un PR malicioso.

6 · Errores habituales

Guardar un JSON de credenciales como secreto de GitHub

❌ Incorrecto 
# El clasico: un client secret de larga vida en los secretos de CI.
# No caduca, se copia a forks y logs, y hay que rotarlo a mano.
- name: Azure login
  uses: azure/login@v2
  with:
    creds: ${{ secrets.AZURE_CREDENTIALS }}
✅ Correcto 
# OIDC: identificadores publicos + token efimero que GitHub firma.
- name: Azure login
  uses: azure/login@v2
  with:
    client-id:       ${{ vars.AZURE_CLIENT_ID }}
    tenant-id:       ${{ vars.AZURE_TENANT_ID }}
    subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

La diferencia no es de comodidad: es la diferencia entre un secreto que vive años y un permiso que vive minutos. OIDC no elimina el secreto, elimina la necesidad de guardarlo.

Usar comodines en el subject

❌ Incorrecto 
# Cualquier repositorio de la organizacion puede asumir esta identidad.
# Un repo de pruebas comprometido despliega en tu produccion.
resource "azurerm_federated_identity_credential" "github" {
  name                      = "github-any"
  user_assigned_identity_id = azurerm_user_assigned_identity.github.id
  audience                  = ["api://AzureADTokenExchange"]
  issuer                    = "https://token.actions.githubusercontent.com"
  subject                   = "repo:${var.github_org}/*:ref:refs/heads/main"
}
✅ Correcto 
# Repositorio exacto y rama exacta. Nada de comodines.
resource "azurerm_federated_identity_credential" "github" {
  name                      = "github-main"
  user_assigned_identity_id = azurerm_user_assigned_identity.github.id
  audience                  = ["api://AzureADTokenExchange"]
  issuer                    = "https://token.actions.githubusercontent.com"
  subject                   = "repo:${var.github_org}/${var.github_repo}:ref:refs/heads/main"
}

El subject es la frontera de seguridad. Un comodín ahí equivale a dar la llave a toda la organización para «no tener que configurarla cada vez». Es exactamente el tipo de atajo que se convierte en incidente.

Olvidar el permiso id-token: write

❌ Incorrecto 
# Sin permisos declarados, GITHUB_TOKEN no puede emitir el token OIDC.
# El login falla con un error poco descriptivo.
on: [push]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
✅ Correcto 
# id-token: write es OBLIGATORIO para que GitHub emita el token OIDC.
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}

Es el fallo más habitual al configurar OIDC por primera vez, y despista porque el error no dice «te falta el permiso». Regla mnemotécnica: si tocas el cloud sin claves, necesitas id-token: write.

Reutilizar una sola identidad para todos los entornos

❌ Incorrecto 
# Una unica identidad con permisos en TODO: si un workflow se compromete,
# el atacante puede tocar tambien produccion.
resource "azurerm_role_assignment" "github_all" {
  scope                = data.azurerm_subscription.current.id
  role_definition_name = "Contributor"
  principal_id         = azurerm_user_assigned_identity.github.principal_id
}
✅ Correcto 
# Identidad distinta por entorno, y cada una con su propio subject
# (staging: rama develop; produccion: environment production).
resource "azurerm_role_assignment" "github_staging" {
  scope                = azurerm_resource_group.staging.id
  role_definition_name = "Contributor"
  principal_id         = azurerm_user_assigned_identity.github_staging.principal_id
}

resource "azurerm_role_assignment" "github_prod" {
  scope                = azurerm_resource_group.prod.id
  role_definition_name = "Contributor"
  principal_id         = azurerm_user_assigned_identity.github_prod.principal_id
}

Cada entorno con su identidad y su condición de confianza. El radio de daño de un workflow comprometido se limita al entorno que le corresponde, no a toda la cuenta.

7 · Ejercicio guiado

Objetivo: configurar una federación OIDC real y comprobar el login desde un workflow sin haber creado ningún secreto.

Antes de empezar: necesitas permiso para crear app registrations y asignar roles. En un tenant de laboratorio lo tienes; en una empresa puede que no. Si no puedes, sigue los pasos para entender el flujo y pásalos a un compañero con permisos.

  1. Paso 1 — Crea la aplicación (identidad) y su service principal:
    terminal
    # La "app registration" es la identidad; el service principal es su
# presencia en el tenant (la entidad a la que se asignan roles).
APP_ID=$(az ad app create --display-name copiloto-gh-oidc --query appId -o tsv)
az ad sp create --id "$APP_ID"

TENANT_ID=$(az account show --query tenantId -o tsv)
SUBSCRIPTION_ID=$(az account show --query id -o tsv)
echo "APP_ID=$APP_ID"
  2. Paso 2 — Añade la credencial federada con el subject exacto:
    terminal
    # Cambia ORG/REPO por los tuyos. El subject fija repo y rama.
az ad app federated-credential create \
  --id "$APP_ID" \
  --parameters '{
    "name": "github-main",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:ORG/REPO:ref:refs/heads/main",
    "audiences": ["api://AzureADTokenExchange"]
  }'
  3. Paso 3 — Da el mínimo permiso necesario:
    terminal
    # Un grupo de recursos dedicado al despliegue, con el rol Contributor.
az group create --name rg-oidc-lab --location westeurope --tags curso=cloud
SP_OBJECT_ID=$(az ad sp show --id "$APP_ID" --query id -o tsv)

az role assignment create \
  --assignee "$SP_OBJECT_ID" --role Contributor \
  --scope "$(az group show -n rg-oidc-lab --query id -o tsv)"
  4. Paso 4 — Publica los identificadores como variables del repositorio:
    GitHub → Settings
    # En Settings > Secrets and variables > Actions > Variables:
#   AZURE_CLIENT_ID       = $APP_ID
#   AZURE_TENANT_ID       = $TENANT_ID
#   AZURE_SUBSCRIPTION_ID = $SUBSCRIPTION_ID
#
# Van en "Variables", NO en "Secrets": no son secretos.
  5. Paso 5 — Crea el workflow y comprueba el login:
    .github/workflows/oidc-check.yml
    name: oidc-check
on: workflow_dispatch

permissions:
  id-token: write
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - name: Azure login (OIDC)
        uses: azure/login@v2
        with:
          client-id:       ${{ vars.AZURE_CLIENT_ID }}
          tenant-id:       ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Quien soy
        run: az account show --query "{cuenta:name, usuario:user.name}" -o table

    Resultado esperado: el paso «Quien soy» muestra la suscripción y la identidad del service principal. Si el login falla, revisa (en este orden): el permiso id-token: write, que el subject coincida con tu ORG/REPO y rama, y que la audiencia sea api://AzureADTokenExchange.

  6. Paso 6 — Limpia:
    terminal
    az group delete --name rg-oidc-lab --yes --no-wait
az ad app delete --id "$APP_ID"

8 · Reto

🎯 Un despliegue a producción que exige aprobación humana

Configura dos identidades federadas distintas para el mismo repositorio: una para staging (push a develop) y otra para producción (entorno production). El despliegue a producción solo debe poder ejecutarse después de una aprobación manual y nunca desde una rama distinta de main.

Entrega: las dos credenciales federadas (con sus subject respectivos), los dos roles con ámbitos separados, y el workflow con la configuración de environment que activa la revisión.

Pista: el subject de producción usa environment:production en lugar de ref:refs/heads/.... La aprobación no la da OIDC, la dan las protection rules del entorno en GitHub; OIDC solo garantiza que el token que ves viene de ese entorno concreto. Piensa en qué pasaría si alguien quita la regla de protección: ¿tu configuración de confianza seguiría permitiendo el despliegue? ¿Debería?

9 · Resumen

  • OIDC sustituye los secretos de despliegue de larga vida por tokens firmados que caducan en minutos.
  • GitHub emite el token; el cloud lo valida contra la confianza que configuraste (issuer, audience y subject).
  • El subject es la frontera de seguridad: fija el repo, la rama o el entorno. Sin comodines.
  • En Azure la confianza es una federated identity credential sobre una identidad; en AWS, la trust policy de un rol.
  • El workflow necesita permissions: id-token: write; los identificadores son públicos y van como variables, no como secretos.
  • Una identidad por entorno y aprobaciones por environment limitan el radio de daño del pipeline.

10 · Preguntas frecuentes

¿OIDC no sigue necesitando un secreto para «empezar»?

No en el sentido clásico. El único elemento que se guarda en la nube es la confianza: emisor, audiencia y subject. Eso es configuración pública, no una credencial. El token que se usa para autenticar lo genera GitHub en el momento y caduca en minutos, así que no hay un «secreto inicial» que proteger entre despliegues.

El login falla con un error de autenticación. ¿Por dónde empiezo?

Por tres comprobaciones, en orden: (1) el workflow declara permissions: id-token: write; (2) el subject coincide exactamente con tu ORG/REPO y la rama o entorno desde el que disparas; (3) la audiencia es la correcta (api://AzureADTokenExchange en Azure, sts.amazonaws.com en AWS). La cuarta causa habitual es disparar desde un PR de un fork, que por diseño no tiene el permiso.

¿Puedo usar OIDC con GitLab, Jenkins o Terraform Cloud?

Sí. OIDC es un estándar: casi todas las plataformas de CI modernas emiten tokens OIDC (GitLab CI, CircleCI, Terraform Cloud, Bitbucket…). Cambian el emisor y las claims, pero el patrón —emitir, presentar, validar contra una confianza y recibir credenciales temporales— es idéntico. Lo que aprendes aquí se traslada.

¿OIDC cuesta dinero?

No. Configurar la federación no tiene coste en Azure ni en AWS. Lo único que puede tener coste es el propio pipeline (minutos de CI) y lo que despliegue. Es una de esas mejoras de seguridad que además simplifica la operación: menos secretos que rotar.

Con OIDC, ¿mi pipeline sigue necesitando permisos mínimos?

Más que nunca. OIDC resuelve cómo se autentica el pipeline, no cuánto puede hacer. Si le das Owner en la suscripción, un pipeline comprometido sigue siendo catastrófico, aunque no tenga claves. Combina OIDC con el mínimo privilegio de la lección 01: identidad federada, rol pequeño, ámbito estrecho y por entorno.
