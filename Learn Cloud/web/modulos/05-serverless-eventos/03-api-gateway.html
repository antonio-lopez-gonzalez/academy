API Gateway: la puerta de entrada

Módulo 5 · Serverless y eventos 🕐 30 minutos

1 · Introducción

La Copiloto API ya existe y funciona. Pero en cuanto la expones al mundo, empiezan las preguntas incómodas: ¿cómo sé quién llama? ¿Cómo impido que un cliente abusivo sature el servicio? ¿Cómo despliego la versión 2 sin romper a los clientes de la versión 1? ¿Cómo mido el uso por consumidor? Y todo eso, ¿lo meto a mano en cada endpoint de mi aplicación?

La respuesta madura es no meterlo en la aplicación, sino poner delante una puerta de entrada: un API gateway. Todas las llamadas pasan por él antes de llegar a tu servicio. Ahí se valida el token, se aplican cuotas y límites, se enruta la versión correcta, se transforma la petición si hace falta y se registra quién llamó, qué pidió y cuánto tardó.

¿Por qué existe esta lección? Porque exponer un servicio directamente es el atajo que parece más simple y termina costando más: copias la validación de tokens en cada código, no tienes dónde poner un límite global, y cada cambio de contrato rompe clientes. Un gateway concentra esos problemas en un solo sitio, declarativo y versionado. Es la pieza que separa «tengo un servicio» de «tengo una API que puedo ofrecer con garantías».

Idea clave: el gateway no es un proxy tonto. Es el lugar donde viven las preocupaciones transversales a todas tus APIs: autenticación, autorización, límites, cuotas, versionado, observabilidad y, a veces, transformación. Tu servicio vuelve a hacer solo su trabajo de negocio.

2 · Teoría

Qué hace un gateway que tu servicio no debería hacer

Imagina que pones una recepción en la entrada del edificio de tu API. Nadie pasa sin identificarse, hay un número máximo de visitantes por hora, cada uno deja registro, y hay una sala para visitas de prueba aparte de la operativa habitual. Eso hace un gateway:

PreocupaciónQué resuelveSin gateway
Autenticación / autorizaciónValida el token (JWT/OAuth2) y decide si la llamada pasa, antes de tocar tu códigoCada servicio valida su propio token; inconsistencia garantizada
Límites y cuotas«N peticiones por segundo» y «M por mes» por cliente o por IPUn cliente abusivo tumba el servicio; no hay control
Enrutado y versionado/v1/... y /v2/... conviven; cada uno apunta a un backend distintoCambiar el contrato rompe a quien ya integra
ObservabilidadMétricas por API, operación y consumidor; logs centralizadosCada servicio inventa su formato de log
TransformaciónAdaptar el contrato expuesto al backend (headers, payload, CORS)Se codifica dentro del servicio, mezclando capas

Analogía: el gateway es la recepción y control de acceso de un edificio corporativo. Da igual cuántas oficinas (backends) haya dentro: quien visita pasa por recepción, se identifica, se le sella un pase con caducidad y un cupo, y queda registrado. Las oficinas no repiten ese trabajo; se dedican a su negocio.

Los dos modelos: Azure API Management y AWS API Gateway

Aunque resuelven lo mismo, su granularidad y su coste son muy distintos. Conocerlos ayuda a no equivocarse:

AspectoAzure API Management (APIM)AWS API Gateway
NaturalezaPlataforma completa de gestión de APIs (gateway + plano de administración + portal de desarrolladores)Servicio de gateway puro (REST, HTTP y WebSocket), sin portal de desarrolladores
Modelo de configPolíticas en XML: conjuntos de reglas aplicadas en fases (inbound/backend/outbound)Configuración por API, etapa, autorizador y planes de uso
AutenticaciónValidación de JWT/OAuth2 por política; suscripciones con clavesAutorizadores (JWT, Lambda, Cognito) + claves de API
Límites / cuotasPolíticas rate-limit y quota globales o por suscripciónUsage plans con límites por clave; throttling por etapa
VersionadoVersiones + revisiones, con rutas o cabecerasEtapas (stages) y versiones en la ruta
CostePor hora de instancia + llamadas; el tier Consumption es por llamadaPor millón de llamadas + transferencia (HTTP API es mucho más barato que REST)

El detalle que sorprende en la factura: APIM tiene tiers clásicos (Developer, Basic, Standard, Premium) que se facturan por hora de instancia, con un suelo mensual alto. Para un proyecto pequeño eso es caro. El tier Consumption (y los nuevos v2) cambian el modelo a pago por uso. Elige conscientemente; no arranques un «Standard» para un MVP.

El camino de una petición por el gateway

  Cliente (con token JWT)
        │  GET /v1/copiloto/respuestas   Authorization: Bearer ...
        ▼
  ┌──────────────────────────── [ API GATEWAY ] ────────────────────────────┐
  │  1. Valida el JWT (firma, expiración, audience)   ──► si falla: 401/403   │
  │  2. Aplica límite y cuota (rate-limit / plan)     ──► si excede: 429      │
  │  3. Enruta según versión y ruta                   ──► /v1 → backend v1    │
  │  4. (Opcional) transforma cabeceras / payload                            │
  │  5. Registra métricas y trazas                                           │
  └───────────────────────────────┬─────────────────────────────────────────┘
                                  ▼
                        [ Copiloto API / Function ]   ← recibe solo llamadas legítimas

Fíjate en que el backend no ve tokens, ni cuotas, ni versiones. Ve peticiones ya autorizadas y con formato limpio. Esa es toda la gracia: cada capa hace una cosa.

Complementa a serverless, no lo reemplaza

Un gateway y las funciones que viste en la lección 1 encajan perfectamente: el gateway es la cara pública, la función es el cerebro. El patrón clásico es gateway → Lambda/Función. El gateway añade lo que a una función HTTP «cruda» le cuesta más: validación de token antes de invocar (ahorras ejecuciones), límites por consumidor y versiones.

Regla práctica: si tu API la consume más de un cliente, o necesitas cuotas, tokens o versiones, mete un gateway. Si es un único servicio interno sin esos requisitos, una función HTTP o un contenedor con ingress bastan. No añadas un APIM «porque suena profesional»: es coste y complejidad.

3 · Ejemplo mínimo

El gateway más pequeño posible en Azure es una instancia de APIM (tier Consumption) con una API declarada. Es el «hola mundo» de la puerta de entrada.

main.tf — APIM mínimo con una API
# 1) La instancia de APIM. Consumption: pago por llamada, sin suelo mensual alto.
resource "azurerm_api_management" "min" {
  name                = "apim-copiloto-min"
  location            = var.location
  resource_group_name = var.resource_group_name

  publisher_name  = "Copiloto"                 # obligatorio: quién publica
  publisher_email = "dev@copiloto.example"     # obligatorio: email de contacto

  sku_name = "Consumption_0"                   # pago por uso (ideal para empezar)
}

# 2) La API en sí: agrupa operaciones bajo un path (/copiloto).
resource "azurerm_api_management_api" "copiloto" {
  name                = "copiloto-api"
  resource_group_name = var.resource_group_name
  api_management_name = azurerm_api_management.min.name

  revision            = "1"
  display_name        = "Copiloto API"
  path                = "copiloto"       # prefijo público: /copiloto/...
  protocols           = ["https"]
}

# 3) Una operación: GET /copiloto/respuestas
resource "azurerm_api_management_api_operation" "respuestas" {
  operation_id        = "get-respuestas"
  api_name            = azurerm_api_management_api.copiloto.name
  api_management_name = azurerm_api_management.min.name
  resource_group_name = var.resource_group_name
  display_name        = "Obtener respuestas"
  method              = "GET"
  url_template        = "/respuestas"
}

Qué acaba de pasar, capa por capa:

  1. azurerm_api_management: la instancia del gateway. Con Consumption_0 pagas por llamada; con Developer_1/Standard_1 pagarías por hora de instancia (más potente, más caro). Es la decisión de coste principal.
  2. azurerm_api_management_api: agrupa operaciones bajo un path público (/copiloto). Aquí nace el concepto de «API» como unidad que se versiona y se expone.
  3. azurerm_api_management_api_operation: cada endpoint. Todavía no apunta a ningún backend: solo existe la puerta. En el ejemplo real conectaremos el backend y las políticas.

El apunte importante: crear APIM por Terraform es lento (la instancia tarda varios minutos, a veces más). Es normal; no es que se haya colgado. En AWS, con una HTTP API de API Gateway la creación es casi instantánea y el coste por llamada es sensiblemente menor que la REST API.

4 · Ejemplo real

Escenario del curso: la Copiloto API detrás de un APIM que valida el JWT, aplica un límite de 100 llamadas por minuto por suscriptor y apunta al backend real. Toda la seguridad transversal vive en una política.

   Cliente ──Bearer JWT──► [ APIM ]
                             │  1) validate-jwt  → 401 si el token no vale
                             │  2) rate-limit    → 429 si pasa de 100/min
                             │  3) set-backend   → reescribe la URL al backend
                             ▼
                     [ Copiloto API (Container Apps / Function) ]
copiloto-gateway.tf — backend + política de seguridad
# El backend real: la Copiloto API que ya desplegaste (módulo 4).
resource "azurerm_api_management_backend" "copiloto" {
  name                = "copiloto-backend"
  resource_group_name = var.resource_group_name
  api_management_name = azurerm_api_management.min.name
  protocol            = "http"
  url                 = "https://${azurerm_container_app.copiloto.ingress[0].fqdn}"
}

# La POLÍTICA: el corazón del gateway. Se aplica a toda la API (todas sus operaciones).
resource "azurerm_api_management_api_policy" "seguridad" {
  api_name            = azurerm_api_management_api.copiloto.name
  api_management_name = azurerm_api_management.min.name
  resource_group_name = var.resource_group_name

  xml_content = <<XML
<policies>
  <inbound>
    <!-- 1) Autenticación: valida el JWT contra el emisor (Entra ID / Cognito). -->
    <validate-jwt header-name="Authorization" failed-validation-httpcode="401"
                  failed-validation-error-message="Token no válido">
      <openid-config url="https://login.microsoftonline.com/${var.tenant_id}/v2.0/.well-known/openid-configuration" />
      <required-claims>
        <claim name="aud" match="any">
          <value>${var.api_audience}</value>
        </claim>
      </required-claims>
    </validate-jwt>

    <!-- 2) Límite: 100 llamadas por minuto y por suscriptor. -->
    <rate-limit calls="100" renewal-period="60" />

    <!-- 3) Enrutado: manda la petición al backend declarado arriba. -->
    <set-backend-service backend-id="copiloto-backend" />
  </inbound>

  <backend>
    <!-- Aquí podrías adaptar headers o credenciales hacia el backend. -->
  </backend>

  <outbound />
  <on-error />
</policies>
XML
}

Lo que has centralizado en la puerta, sin tocar el código de la API:

  • Seguridad antes de ejecutar: si el JWT no es válido, el gateway devuelve 401 y el backend ni se enteró. Ahorras cómputo y eliminas la validación duplicada en cada servicio.
  • Protección contra abuso: el rate-limit corta con 429 al cliente que pasa de 100/min. Tu servicio queda a salvo de picos y bucles del cliente.
  • Desacoplamiento del backend: el cliente llama a una URL estable de APIM; por dentro, set-backend-service apunta al servicio real. Mañana cambias de Container Apps a otro cómputo sin cambiar la URL pública.

En AWS, el equivalente sería una HTTP API con un JWT authorizer (valida el token) y un usage plan con límites por clave de API, enrutando a la Lambda. La idea es idéntica: validar, limitar, enrutar; solo cambia dónde se escribe la regla (política XML vs configuración por etapa).

5 · Buenas prácticas

HazEvitaPor qué
Validar el token en el gateway (401 antes del backend) Exponer el backend y validar en cada servicio Una sola fuente de verdad para auth; menos cómputo y menos errores
Poner límites (rate-limit) y cuotas por cliente Confiar en que «nadie abusará» Un bucle de un cliente puede tumbar tu servicio y dispararte la factura
Versionar desde el primer día (/v1) Cambiar el contrato in place Permite evolucionar sin romper a los clientes que ya integran
Elegir el tier por uso real (Consumption / HTTP API) Arrancar en un tier premium «por si acaso» El coste de APIM es, sobre todo, hora de instancia: no lo desperdicies
Mantener el gateway «tonto»: auth, límites, ruta Meter lógica de negocio en las políticas La lógica del gateway es difícil de testear y de versionar; el negocio va en el servicio
Observabilidad en el gateway (métricas por consumidor) No medir quién consume qué Sin datos no puedes defender cuotas, capacidad ni prioridades (módulo 6)

6 · Errores habituales

1. Exponer el backend directamente y «ya veremos»

Incorrecto — el servicio abierto a Internet sin puerta 
# ❌ Ingress público del backend accesible por cualquiera;
#    sin auth, sin límites, sin versiones. Cada llamada va al contenedor.
ingress {
  external_enabled = true        # URL pública directa, sin control
  target_port      = 8000
}
Correcto — el backend detrás del gateway 
# ✅ El backend deja de ser público; solo el gateway le llega.
#    (En producción, ingress INTERNO + el gateway por red privada.)
ingress {
  external_enabled = false       # solo alcanzable desde dentro / el gateway
  target_port      = 8000
}
# La cara pública es el APIM, que valida, limita y versiona.

2. Repartir claves de API a los clientes y llamarlas «auth»

Incorrecto — clave estática en el cliente 
# ❌ La clave viaja al cliente y nunca caduca; si se filtra, es una llave maestra.
curl -H "Ocp-Apim-Subscription-Key: 0123456789abcdef" \
     https://apim-copiloto.azure-api.net/copiloto/respuestas
Correcto — token de vida corta validado en el gateway 
# ✅ Token JWT de corta vida (OAuth2/OIDC); el gateway valida firma y claims.
TOKEN=$(curl -s -X POST "$TOKEN_ENDPOINT" -d "grant_type=client_credentials" ... | jq -r .access_token)
curl -H "Authorization: Bearer $TOKEN" \
     https://apim-copiloto.azure-api.net/copiloto/respuestas

La clave de API puede seguir usándose como etiqueta de suscriptor para cuotas, pero no es autenticación: identifica un plan, no a un usuario verificado.

3. Meter lógica de negocio en las políticas del gateway

Incorrecto — cálculo de negocio en la puerta 
<!-- ❌ El gateway no es el sitio para decidir reglas de negocio:
     es dificil de testear, de versionar y de depurar. -->
<choose>
  <when condition="context.Request.Headers['x-plan'] == 'premium'"> ...
</choose>
Correcto — la puerta se ocupa de lo transversal 
<!-- ✅ El gateway valida, limita y enruta; el NEGOCIO vive en el servicio. -->
<validate-jwt ... />
<rate-limit calls="100" renewal-period="60" />
<set-backend-service backend-id="copiloto-backend" />

4. No versionar y romper a los clientes

# ❌ Cambiar /respuestas para devolver otro formato "y santas pascuas":
#    los clientes ya integrados empiezan a fallar sin aviso.

# ✅ Publica /v2 junto a /v1, migra a los clientes y retira /v1 con plazo.
#    El gateway hace trivial tener las dos versiones apuntando a backends distintos.
#    Pista: versiona en la RUTA (más fácil de operar y de depurar que en cabeceras).

El versionado no es burocracia: es lo que te permite mejorar sin castigar a quien ya confía en tu API.

7 · Ejercicio guiado

Objetivo: poner un gateway delante de una función, comprobar que sin token devuelve 401 y que al pasarse del límite devuelve 429.

  1. Paso 1 — prepara el grupo y la función backend. Reutiliza una función HTTP mínima (lección 1): 
    az group create --name copiloto-gw-rg --location westeurope \
  --tags course=cloud lesson=05-03

func azure functionapp publish func-copiloto-min --python
HOST=$(az functionapp show --name func-copiloto-min \
  --resource-group copiloto-gw-rg --query defaultHostName -o tsv)
echo "https://$HOST/api/hello"
  2. Paso 2 — crea el APIM (tarda unos minutos). Ten paciencia: la instancia se aprovisiona despacio: 
    az apim create \
  --name apim-copiloto-lab --resource-group copiloto-gw-rg \
  --publisher-name Copiloto --publisher-email dev@copiloto.example \
  --sku-name Consumption
# Esperado: el comando termina tras varios minutos. No está colgado.
  3. Paso 3 — importa la API apuntando a la función. 
    az apim api import \
  --resource-group copiloto-gw-rg --service-name apim-copiloto-lab \
  --path copiloto --api-id copiloto-api \
  --specification-format OpenApi \
  --specification-url "https://$HOST/api/openapi.json" \
  --service-url "https://$HOST/api"
# Esperado: la API queda publicada bajo /copiloto.
  4. Paso 4 — prueba SIN token. Antes de añadir auth, la llamada pasa; comprueba la URL pública del gateway: 
    GW="https://apim-copiloto-lab.azure-api.net/copiloto"
curl -s -o /dev/null -w "%{http_code}\n" "$GW/hello?name=Copiloto"
# Esperado: 200 (todavía no hay política de auth aplicada).
  5. Paso 5 (verificación) — añade la política y comprueba 401 y 429. Aplica validate-jwt + rate-limit como en el ejemplo real y repite: 
    # Sin token debe dar 401:
curl -s -o /dev/null -w "%{http_code}\n" "$GW/hello"
# Esperado: 401

# Con token válido, mata el límite con un bucle y busca el 429:
for i in $(seq 1 120); do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -H "Authorization: Bearer $TOKEN" "$GW/hello"
done | sort | uniq -c
# Esperado: muchos 200 y, al superar 100/min, algunos 429.
  6. Paso 6 — limpia (control de coste). 
    az group delete --name copiloto-gw-rg --yes --no-wait

Resultado esperado: la misma URL responde de formas distintas según el gateway: 200 con token dentro del límite, 401 sin token, 429 al pasarse. Has visto las tres preocupaciones transversales funcionando antes de llegar al backend.

8 · Reto

🎯 Migrar de /v1 a /v2 sin cortar el servicio

La Copiloto API tiene clientes en /v1. Necesitas publicar /v2 con un contrato nuevo, pero sin romper a los clientes que aún usan /v1. Además quieres probar /v2 con tráfico real antes de migrar del todo.

Diseña y describe el procedimiento completo: ¿cómo conviven las dos versiones en el gateway? ¿Apunta cada una a un backend distinto? ¿Cómo das a un grupo reducido acceso a /v2 primero (¿pesos, cabecera, token, subdominio)? ¿Qué métricas miras antes de mover el resto? ¿Cuándo y cómo retiras /v1 con aviso a los clientes?

Pista: APIM tiene versiones y revisiones; los weights de una revisión permiten repartir tráfico entre la estable y la candidata. En AWS, las stages y el enrutado por pesos (o CloudFront) dan el mismo efecto. Céntrate en el porqué de cada paso y en cómo vuelves atrás si algo falla.

9 · Resumen

  • Un API gateway es la puerta de entrada única: todas las llamadas pasan por él antes de llegar al servicio.
  • Concentra las preocupaciones transversales: autenticación, autorización, límites, cuotas, versionado, transformación y observabilidad.
  • La autenticación se resuelve antes del backend: un token inválido da 401 sin consumir tu servicio. Las claves de API no son autenticación: identifican un plan, no a un usuario.
  • Limitar y acotar (rate-limit, cuotas) protege tu servicio y tu factura frente a abusos y bucles.
  • Versionar (/v1, /v2) permite evolucionar sin romper a los clientes; el gateway hace trivial tener dos versiones a la vez.
  • Azure: API Management, con políticas XML y tiers que se facturan por hora (usa Consumption para empezar). AWS: API Gateway (REST/HTTP/WebSocket), con stages, autorizadores y usage plans.
  • La puerta se queda tonta (auth, límites, ruta); el negocio vive en el servicio. No metas lógica de negocio en las políticas.

10 · Preguntas frecuentes

¿Necesito un gateway si solo tengo una función?

No siempre. Si la consume un único cliente interno y no necesitas cuotas, tokens ni versiones, una función HTTP directa basta. Mete un gateway cuando aparezcan esas necesidades: varios clientes, autenticación centralizada, límites por consumidor o varias versiones. Añadirlo «por si acaso» es coste y complejidad que no se recuperan.

¿Por qué mi APIM tarda muchísimo en crearse?

Porque las instancias de APIM (salvo Consumption) se aprovisionan como infraestructura dedicada y tardan varios minutos, a veces más de veinte. No es un error: es el precio de un gateway «de verdad». En AWS, una HTTP API de API Gateway se crea casi al instante. Si te urge iterar, empieza por Consumption o por HTTP API y sube de tier cuando lo necesites.

¿La clave de suscripción de APIM es suficiente para autenticar?

No. La clave de suscripción sirve para agrupar consumidores y aplicarles planes y cuotas, pero no verifica la identidad de un usuario ni caduca por defecto: si se filtra, cualquiera entra. Para autenticación de verdad usa OAuth2/OIDC con tokens de vida corta (validados con validate-jwt) y, si quieres, combínalo con la clave para atribuir el consumo a un plan.

¿Dónde pongo el límite: en el gateway o en el servicio?

En el gateway, salvo excepciones. El gateway conoce al consumidor (token, suscripción, plan) y está antes que el backend, así que puede cortar sin gastar cómputo. El servicio puede tener límites internos como última defensa, pero la política de cuotas y rate-limit pertenece a la puerta. Duplicar la lógica en cada servicio es justo lo que el gateway evita.

¿El gateway ralentiza las llamadas?

Añade un salto de red y el coste de validar tokens y aplicar políticas: milisegundos en la mayoría de casos. A cambio obtienes seguridad, control y observabilidad. Además, muchas validaciones ahorran latencia: si el token es inválido, la respuesta sale del gateway sin tocar el backend. Si la latencia del gateway fuera crítica, se usan planes con capacidad dedicada y caching en la puerta.
