Eventos y colas gestionadas

Módulo 5 · Serverless y eventos 🕐 30 minutos

1 · Introducción

Hasta ahora, cuando la Copiloto API necesitaba hacer algo, lo hacía ella misma: recibía la petición, ejecutaba el trabajo y devolvía la respuesta. Eso funciona hasta que el trabajo es lento (generar un informe, llamar a un servicio externo, redimensionar una imagen). En ese momento tienes dos problemas: el usuario espera, y si el proceso falla a mitad, la petición se pierde.

La solución no es hacerlo más rápido, sino desacoplar: la API acepta la petición, publica un mensaje o evento en un servicio gestionado y responde «aceptado» de inmediato. Otra pieza (una función, un contenedor, otro servicio) consume ese mensaje cuando puede y hace el trabajo real. Los dos extremos dejan de conocerse.

¿Por qué existe esta lección? Porque casi todo lo interesante en la nube —serverless incluido— se apoya en mensajería gestionada. Y porque Azure y AWS tienen tres familias de servicios de mensajería cada uno, con nombres que se confunden: una es para colas, otra para eventos, otra para streams. Elegir la equivocada te cuesta dinero, latencia y horas de depuración. Aquí aprendes a distinguirlas y a montar una arquitectura desacoplada de verdad, con reintentos y cola de mensajes fallidos.

Idea clave: «cola» y «evento» no son sinónimos. Una cola reparte trabajo entre consumidores (cada mensaje lo procesa uno). Un tema de eventos difunde hechos a muchos interesados (cada evento lo ve quien esté suscrito). Confundirlos es el error conceptual número uno.

2 · Teoría

Mensaje vs evento: la distinción que lo ordena todo

Antes de aprender nombres de servicios, fija la diferencia de intención:

Mensaje (comando / trabajo)Evento (hecho)
Qué expresa«Haz esto» (imperativo)«Esto ha pasado» (pasado, informativo)
Quién lo procesaUno de los consumidores (se reparte)Todos los suscritos interesados
AcoplamientoEl emisor sabe que hay un consumidor que debe trabajarEl emisor solo anuncia; no sabe ni quién escucha
Servicio típicoCola: Service Bus / SQSTema: Event Grid / EventBridge
Ejemplo«Genera el informe del usuario 42»«El fichero factura.pdf se ha creado»

Analogía: un mensaje es un sobre con una orden para un camarero en una cocina (reparte el trabajo). Un evento es un anuncio por megafonía del aeropuerto: «el vuelo ha cambiado de puerta». No sabe quién lo escucha; solo lo publica. Quien tenga interés, reacciona.

Las tres familias de mensajería (y sus equivalencias)

Azure y AWS ofrecen tres categorías de servicios, aunque con nombres distintos. Reconocer la categoría importa más que memorizar el producto:

FamiliaPara quéAzureAWS
Eventos discretos (reactivo, push)Reaccionar a hechos puntuales: un blob creado, un recurso cambiado, un clic. Enrutado y filtrado.Event GridEventBridge (+ SNS)
Colas de trabajo (imperativo, poll)Repartir trabajo, absorber picos, reintentos, transacciones y orden.Service Bus (colas/temas)SQS (+ SNS para fan-out)
Streams de telemetría (alto volumen, ordenado)Ingesta masiva de eventos ordenados por partición: IoT, telemetría, logs, analítica.Event HubsKinesis (+ MSK/Kafka)

El error caro: usar Event Hubs/Kinesis para repartir trabajo (no están pensados para consumidores que toman y borran mensajes) o usar Event Grid/EventBridge como cola de trabajo (no garantizan que un solo consumidor procese cada mensaje, ni el orden). La pregunta correcta es: ¿esto es un hecho que anuncio o un trabajo que encargo?

Cómo se entrega un mensaje: lo que debes asumir

Casi toda mensajería gestionada ofrece entrega al menos una vez (at-least-once): puede haber duplicados y reintentos. Eso obliga a un diseño concreto:

  • Idempotencia: procesar el mismo mensaje dos veces no debe duplicar el efecto. Técnica típica: guardar un id de mensaje ya procesado y descartar repetidos.
  • Reintentos con retroceso: ante fallo, el mensaje vuelve a la cola y se reintenta un número limitado de veces.
  • Cola de mensajes fallidos (DLQ): tras agotar los reintentos, el «mensaje venenoso» se aparca para inspección, en vez de bloquear la cola para siempre.
  • Confirmación explícita: el consumidor borra o confirma el mensaje solo cuando terminó bien (en SQS, borrar; en Service Bus, complete). Si no confirma, el mensaje reaparece.

Regla mental: «al menos una vez» significa «diseña para dos». La idempotencia no es un extra de elegancia; es un requisito para no cobrar dos veces ni enviar dos correos.

El patrón desacoplado, dibujado

Así se ve el Copiloto pasando de «todo síncrono» a «desacoplado»:

  ANTES (síncrono, frágil)                     DESPUÉS (desacoplado, resistente)

  Usuario ──HTTP──► [ Copiloto API ]           Usuario ──HTTP──► [ Copiloto API ]
                         │                                              │ publica
                         │ hace el trabajo                              ▼
                         │ (tarda, si falla                           ┌─────────┐
                         ▼  se pierde)                               │  Cola   │
                    [ informe ]                                      └────┬────┘
                                                                          │ consume (reparte)
                                                                          ▼
                                                                    [ Consumer 1 ]
                                                                    [ Consumer 2 ]  ← escala con la cola
                                                                          │
                                                        agotados los reintentos ▼
                                                                    [ Cola de fallidos ]

Fíjate en lo que se gana: la API responde rápido, el trabajo se escala por separado, los picos se absorben en la cola, y los fallos no se pierden: van a la DLQ para que alguien (tú) los mire.

Queue vs Topic dentro de Service Bus

Service Bus (y SNS/SQS en AWS) distingue dos formas de reparto que conviene tener claras:

QueueTopic + Subscription
ConsumidoresCompiten: cada mensaje lo procesa unoCada suscripción recibe una copia (fan-out)
UsoRepartir carga entre réplicasUn mismo hecho dispara varios procesos
Filtros—Cada suscripción filtra por propiedades del mensaje
Equivalente AWSSQSSNS (tema) con suscriptores SQS/Lambda

Cuánto cuesta y qué límites tiene

Aquí el matiz de coste importa porque el volumen de mensajes puede explotar:

ServicioModelo de coste (orden de magnitud)Límite a vigilar
Event Grid / EventBridgePor evento publicado (muy barato)Reintentos y retención limitados
SQS / Service BusPor millón de operaciones + tamaño de mensajeTamaño máximo por mensaje (p. ej. 256 KB en SQS)
Event Hubs / KinesisPor throughput provisionado o por unidadRendimiento y particiones; se paga aunque no fluya

Un mensaje grande (un PDF, una imagen) no va dentro del mensaje: se sube a Blob/S3 y en el mensaje viaja solo la referencia (la clave del objeto). Patrón conocido como «claim check».

3 · Ejemplo mínimo

El ejemplo más pequeño de cola de trabajo en Azure: un namespace de Service Bus y una cola. El namespace es la frontera; dentro viven colas y temas.

main.tf — Service Bus mínimo
# 1) El namespace: la unidad de despliegue y facturación. Standard es suficiente para colas.
resource "azurerm_servicebus_namespace" "min" {
  name                = "sb-copiloto-min"
  resource_group_name = var.resource_group_name
  location            = var.location
  sku                 = "Standard"   # Basic (solo colas) / Standard / Premium (aislamiento, VNet)
}

# 2) La cola: donde se encolan los mensajes de trabajo.
resource "azurerm_servicebus_queue" "informes" {
  name         = "informes"
  namespace_id = azurerm_servicebus_namespace.min.id

  # Red de seguridad: tras N intentos, el mensaje va a la cola de fallidos.
  max_delivery_count = 5

  # Cuánto puede tardar un consumidor en procesar antes de que el mensaje se libere.
  lock_duration = "PT1M"

  # Retención de mensajes y detección de duplicados (idempotencia a nivel de cola).
  message_ttl                = "P7D"
  requires_duplicate_detection = true
}

Qué acaba de pasar:

  1. azurerm_servicebus_namespace: es el contenedor lógico. La SKU decide capacidades: Basic solo colas, Standard añade temas, Premium añade aislamiento y red privada. Empieza por Standard.
  2. azurerm_servicebus_queue: la cola real. max_delivery_count = 5 significa que, si un consumidor falla cinco veces el mismo mensaje, Service Bus lo mueve a la dead-letter queue automáticamente.
  3. lock_duration: al recibir un mensaje, el consumidor lo «bloquea» ese tiempo. Si termina antes, confirma; si no, el mensaje se libera para otro. Evita que un consumidor caído retenga el mensaje indefinidamente.
  4. requires_duplicate_detection: activa una ventana en la que Service Bus descarta mensajes con el mismo id. Es una ayuda; no sustituye a la idempotencia de tu lógica.

Sin Terraform, el atajo es az servicebus queue create --namespace-name … --name informes. Útil para explorar; el recurso que quieras conservar va como código.

4 · Ejemplo real

Escenario del curso: cuando se registra un usuario, la Copiloto API debe enviar un correo de bienvenida y preparar su espacio de trabajo. Son dos tareas independientes y lentas; hacerlas en la petición HTTP castigaría al usuario. Lo montamos con un tema (fan-out) y dos funciones consumidoras.

  POST /users  ──►  [ Copiloto API ] ──publica "usuario.registrado"──►  [ Service Bus TOPIC ]
                                                                              │
                                              ┌───────────────────────────────┴──────────────────┐
                                              ▼  suscripción "email"                ▼ suscripción "workspace"
                                       [ Function email ]                    [ Function workspace ]
                                        (envía el correo)                     (prepara el espacio)
copiloto-eventos.tf — topic + suscripciones + reglas de filtro
resource "azurerm_servicebus_namespace" "copiloto" {
  name                = "sb-copiloto"
  resource_group_name = var.resource_group_name
  location            = var.location
  sku                 = "Standard"
}

# Un TEMA: publica un hecho y lo reciben todos los suscritos (fan-out).
resource "azurerm_servicebus_topic" "usuarios" {
  name         = "usuario-registrado"
  namespace_id = azurerm_servicebus_namespace.copiloto.id
}

# Suscripción 1: envía el correo. Recibe TODO lo publicado en el tema.
resource "azurerm_servicebus_subscription" "email" {
  name               = "email"
  topic_id           = azurerm_servicebus_topic.usuarios.id
  max_delivery_count = 5
}

# Suscripción 2: prepara el espacio. Aquí filtra: solo eventos "premium".
resource "azurerm_servicebus_subscription" "workspace" {
  name               = "workspace"
  topic_id           = azurerm_servicebus_topic.usuarios.id
  max_delivery_count = 5
}

# Regla de filtro: la suscripción "workspace" solo recibe plan == "premium".
resource "azurerm_servicebus_subscription_rule" "solo_premium" {
  name            = "solo-premium"
  subscription_id = azurerm_servicebus_subscription.workspace.id
  filter_type     = "SqlFilter"
  sql_filter      = "plan = 'premium'"
}

Lo que has construido, comparado con llamar directamente a los servicios:

  • La API no espera: publica el evento y devuelve 202 Accepted. El usuario percibe rapidez aunque el correo tarde segundos.
  • Fan-out desacoplado: mañana quieres, además, actualizar un CRM. Añades una suscripción y no tocas la API. Ese es el valor real de un tema.
  • Filtrado en origen: la función «workspace» no se ejecuta para usuarios gratuitos: la regla SQL descarta esos mensajes antes de consumir cómputo (ahorro y menos ruido).

En AWS el mismo patrón se monta con SNS (el tema) que hace fan-out a varias colas SQS, y cada cola dispara su Lambda. El filtrado también existe en el lado de la suscripción (filter policies). Cambian los nombres, no la idea: un hecho, muchos interesados.

6 · Errores habituales

1. Hacer el trabajo pesado dentro de la petición HTTP

Incorrecto — síncrono y frágil 
# ❌ El endpoint espera a que TODO termine; si algo falla, la petición se pierde
@app.post("/users")
def crear_usuario(u):
    guardar(u)
    enviar_email(u)        # 3 s de espera
    preparar_workspace(u)  # 5 s más, y si falla, el usuario ya está creado
    return {"ok": True}    # el usuario ha esperado 8 s y no hay reintento
Correcto — publicar y responder ya 
# ✅ La API solo publica un evento y responde; el resto lo hace otro consumidor
@app.post("/users", status_code=202)
def crear_usuario(u):
    guardar(u)
    publicar("usuario.registrado", {"id": u.id, "plan": u.plan})
    return {"status": "accepted"}   # rápido, y con reintentos aguas abajo

2. Cola sin DLQ ni límite de reintentos

Incorrecto — reintentos infinitos 
# ❌ Sin max_delivery_count, un mensaje que siempre falla
#    se reintenta sin fin y bloquea el progreso de la cola.
resource "azurerm_servicebus_queue" "mal" {
  name         = "informes"
  namespace_id = azurerm_servicebus_namespace.min.id
  # (sin max_delivery_count ni gestión de la dead-letter)
}
Correcto — límite + DLQ + alerta 
# ✅ Tras N intentos, el mensaje va a la DLQ y se puede investigar.
resource "azurerm_servicebus_queue" "bien" {
  name               = "informes"
  namespace_id       = azurerm_servicebus_namespace.min.id
  max_delivery_count = 5    # 5 intentos y a la dead-letter queue
}
# Y una alerta sobre el recuento de mensajes de la DLQ (módulo 6).

3. Consumidor no idempotente

Incorrecto — duplica efectos en cada reintento 
# ❌ Si el mensaje se reintenta, se cobra/avisa DOS veces
def procesar(msg):
    enviar_correo_bienvenida(msg["usuario_id"])   # sin comprobar si ya se envió
    msg.complete()
Correcto — deduplicar antes de actuar 
# ✅ Marca lo ya procesado; un reintento no repite el efecto
def procesar(msg):
    if ya_procesado(msg["id"]):
        msg.complete()          # ya se hizo: confirmamos y salimos
        return
    enviar_correo_bienvenida(msg["usuario_id"])
    marcar_procesado(msg["id"])  # registrar ANTES de confirmar
    msg.complete()

4. Elegir la familia equivocada

# ❌ Quiero REPARTIR trabajo entre consumidores y uso un TEMA de eventos.
#    Un tema difunde a todos: cada suscriptor haría el MISMO trabajo.
#
# ❌ Quiero ANUNCIAR un hecho a varios sistemas y uso una COLA.
#    Una cola da el mensaje a UNO solo: los demás nunca se enteran.
#
# ✅ Hecho -> tema (Event Grid / EventBridge / SNS)
# ✅ Trabajo -> cola (Service Bus / SQS)
# ✅ Stream masivo ordenado -> Event Hubs / Kinesis

Este es el error conceptual de fondo, y no se arregla con configuración: hay que volver a pensar si lo que estás enviando es un hecho o un encargo.

7 · Ejercicio guiado

Objetivo: crear una cola, enviar un mensaje, consumirlo y provocar un fallo para ver cómo el mensaje acaba en la cola de mensajes fallidos.

  1. Paso 1 — crea el grupo y el namespace. 
    az group create \
  --name copiloto-lab-rg --location westeurope \
  --tags course=cloud lesson=05-02

az servicebus namespace create \
  --name sb-copiloto-lab --resource-group copiloto-lab-rg \
  --sku Standard
  2. Paso 2 — crea la cola con reintentos acotados. 
    az servicebus queue create \
  --namespace-name sb-copiloto-lab --resource-group copiloto-lab-rg \
  --name informes --max-delivery-count 3
  3. Paso 3 — envía un mensaje. Obtén la cadena de conexión y publica: 
    CONN=$(az servicebus namespace authorization-rule keys list \
  --namespace-name sb-copiloto-lab --resource-group copiloto-lab-rg \
  --name RootManageSharedAccessKey --query primaryConnectionString -o tsv)

# Publica un mensaje de trabajo (encargo) en la cola:
az servicebus queue message send \
  --namespace-name sb-copiloto-lab --resource-group copiloto-lab-rg \
  --queue-name informes --body '{"informeId":42}'
  4. Paso 4 — observa el recuento de la cola. 
    az servicebus queue show \
  --namespace-name sb-copiloto-lab --resource-group copiloto-lab-rg \
  --name informes \
  --query "{activos:countDetails.activeMessageCount, dlq:countDetails.deadLetterMessageCount}" \
  -o table
# Esperado: activos = 1, dlq = 0.
  5. Paso 5 (verificación) — fuerza un consumidor que falle. Recibe el mensaje sin confirmarlo y deja que se agoten los 3 intentos: 
    # Recibe y ABANDONA (no completa) el mensaje, 3 veces, para agotar los intentos:
for i in 1 2 3; do
  az servicebus queue message peek \
    --namespace-name sb-copiloto-lab --resource-group copiloto-lab-rg \
    --queue-name informes -o none
  echo "intento $i"
done

az servicebus queue show \
  --namespace-name sb-copiloto-lab --resource-group copiloto-lab-rg \
  --name informes \
  --query "countDetails.deadLetterMessageCount" -o tsv
# Esperado: al agotar max-delivery-count, el mensaje aparece en la DLQ.
  6. Paso 6 — limpia (control de coste). 
    az group delete --name copiloto-lab-rg --yes --no-wait

Resultado esperado: un mensaje que empieza «activo» y termina en la dead-letter queue al agotar sus reintentos. Acabas de ver, en la práctica, por qué la DLQ existe: el trabajo que no se puede procesar se aparta, no se pierde ni bloquea a los buenos.

8 · Reto

🎯 Un hecho, tres interesados, con filtros

Diseña (y describe con precisión, sin resolverlo aquí) un flujo para el Copiloto donde un único hecho —«factura pagada»— provoque tres reacciones distintas e independientes: enviar un recibo por correo, actualizar un panel de métricas y desbloquear una funcionalidad premium. Cada reacción debe ejecutarse solo bajo una condición distinta.

Decide y justifica: ¿tema o cola? ¿cuántas suscripciones? ¿qué filtro lleva cada una? ¿qué pasa si el sistema del panel de métricas está caído un rato: se pierde el hecho o se recupera? ¿Cómo evitas que el recibo se envíe dos veces si hay un reintento?

Pista: un tema con varias suscripciones filtradas da el fan-out; el «panel caído» se resuelve con retención y reintentos en la propia suscripción; y el «recibo dos veces» se ataca con deduplicación idempotente en el consumidor. Detalla el camino del hecho, no el código entero.

9 · Resumen

  • Desacoplar = el productor no espera al consumidor ni lo conoce; se comunican por un servicio de mensajería gestionado.
  • Mensaje = encargo para un consumidor (cola). Evento = hecho que ven todos los suscritos (tema).
  • Tres familias: eventos discretos (Event Grid / EventBridge), colas de trabajo (Service Bus / SQS) y streams (Event Hubs / Kinesis).
  • La entrega es al menos una vez: diseña idempotente y confirma solo al terminar bien.
  • Reintentos + DLQ convierten un mensaje venenoso en algo inspeccionable en vez de un atasco.
  • Los temas con filtros hacen fan-out y reparten el trabajo solo a quien le interesa; añadir un interesado no toca al productor.
  • Payloads grandes van a Blob/S3; en el mensaje viaja la referencia. La longitud de cola y de la DLQ es el indicador de salud a vigilar.

10 · Preguntas frecuentes

¿Event Grid/EventBridge o Service Bus/SQS? ¿Cuál elijo?

Depende de la intención, no del volumen. Si quieres anunciar un hecho que varios sistemas observan y reaccionan → tema de eventos (Event Grid / EventBridge). Si quieres encargar un trabajo que exactamente uno debe completar, con reintentos y control → cola (Service Bus / SQS). Muchas arquitecturas usan ambos: el evento dispara, y dentro de cada reacción se usa una cola para el trabajo pesado.

¿Por qué me llega dos veces el mismo mensaje?

Porque el modelo es de al menos una vez. Si un consumidor no confirma (porque se cayó a mitad o tardó más que el lock), el mensaje se libera y otro consumidor lo recibe. No es un fallo: es el comportamiento esperado. La respuesta correcta es hacer el consumidor idempotente, no «evitar» los duplicados con trucos.

¿Qué es exactamente una dead-letter queue?

Es una subcola donde el servicio aparca los mensajes que agotaron sus reintentos (o que caducaron). Sirve para no bloquear la cola principal con un mensaje que siempre falla, y para poder inspeccionar qué iba mal. Buena práctica imprescindible: alertar cuando su tamaño crece, porque ahí se acumulan los problemas silenciosos.

¿Puedo mandar un PDF o una imagen dentro del mensaje?

Técnicamente hay un límite de tamaño (del orden de 256 KB a 1 MB según servicio) y no es buena idea. El patrón correcto (»claim check«) es subir el fichero a Blob/S3 y enviar en el mensaje solo la referencia. Así los mensajes son ligeros, baratos y rápidos, y el objeto grande vive donde le corresponde.

¿Ordenan los mensajes? Necesito que se procesen en secuencia.

Depende. SQS y Service Bus estándar no garantizan un orden global; SQS FIFO y las sesiones de Service Bus sí permiten ordenar por grupo. Pero ordenar tiene coste: menos paralelismo y más complejidad. Pregúntate si de verdad necesitas orden estricto o si basta con que cada entidad (por ejemplo, cada usuario) se procese en orden; el segundo caso es lo habitual y se resuelve agrupando por clave.
