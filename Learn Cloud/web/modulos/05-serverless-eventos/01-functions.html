Funciones serverless

Módulo 5 · Serverless y eventos 🕐 35 minutos

1 · Introducción

Hasta ahora has ejecutado la Copiloto API dentro de un contenedor: un proceso que arranca, se queda escuchando y responde. Ese modelo es perfecto para un servicio con tráfico continuo, pero es un desperdicio para el resto del sistema. ¿Por qué mantener una máquina despierta 24 h para un trabajo que solo se ejecuta cuando llega un webhook, cuando cambia un blob o cuando suena un temporizador a medianoche?

Las funciones serverless (Azure Functions en Azure, AWS Lambda en AWS) atacan exactamente ese caso: tú escribes una función —un trozo de código con una entrada y una salida— y la plataforma decide cuándo ejecutarla, la arranca, la escala y la apaga. Deja de haber un servidor «encendido»; hay una función «a la espera de un estímulo». Solo pagas por las ejecuciones y por el tiempo real de cómputo.

¿Por qué existe esta lección? Porque serverless es la categoría más malentendida de la nube. Mucha gente la aplica a todo («serverless first» sin pensar) y se topa con cold start, timeouts, agotamiento de conexiones a base de datos y facturas sorprendentes. Aquí vas a entender qué es una función por dentro, qué modelos de disparo tiene, qué límites no se pueden negociar y cómo probarla en local: las piezas sin las que no puedes decidir con criterio en la última lección del módulo.

Idea clave: una función es un unidad de despliegue atada a un disparador. No es «una app pequeña». En el momento en que necesitas estado persistente en memoria, conexiones largas o procesos de más de unos minutos, estás fuera de la zona cómoda de serverless (y lo verás de cerca en la lección 4).

Errores típicos que verás corregidos aquí: tratar la función como un mini backend con estado, dejar credenciales en la configuración, elegir el plan equivocado y culpar al cold start de todo, o creer que «serverless» significa «sin coste».

2 · Teoría

El último escalón del espectro de cómputo

En el módulo 1 viste el espectro VM → contenedor → serverless. Las funciones ocupan el extremo más gestionado: ya no das ni una imagen; das código y un disparador. La plataforma gestiona el runtime, el sistema operativo, la red y el escalado.

MÁS CONTROL  <-------------------------------------------->  MENOS CONTROL
MÁS TRABAJO                                              MENOS TRABAJO
                              MENOS TRABAJO

  VM            Contenedor        Contenedor            FUNCIÓN
  (SO)          (orquestador)     gestionado            (tú: una función
                                 (Container Apps)        + su disparador)
  +----------+  +-------------+  +----------------+  +----------------------+
  | systemd  |  | Deployment  |  | imagen, puerto |  | "cuando llegue X,     |
  | patch OS |  | Service/HPA |  | HTTPS, escalado|  |  ejecuta esto y calla"|
  +----------+  +-------------+  +----------------+  +----------------------+
  siempre on    siempre on        puede escalar a 0    SOLO corre cuando pasa algo

La diferencia esencial no es «no tener servidores» (los hay), sino cuándo se ejecuta el código. Una Container App con min_replicas = 0 también escala a cero, pero sigue siendo un servicio a la escucha. Una función, en cambio, casi siempre es reactiva a un evento. Esa naturaleza reactiva es la que trae tanto la eficiencia como la mayoría de los problemas.

Anatomía de una función: disparador, enlace y código

Toda función serverless se compone de cuatro piezas. Confundirlas es la causa número uno de malos diseños:

PiezaQué esEjemplo
Trigger (disparador)El porqué arranca la función. Exactamente uno por función; define el contrato de entrada.Una petición HTTP, un mensaje en cola, un fichero nuevo en un blob.
Input bindingDatos adicionales que la plataforma inyecta al arrancar, sin que tú abras conexiones a mano.Leer una fila de Cosmos DB / DynamoDB a partir del ID del evento.
Output bindingDestino al que escribir el resultado sin gestionar el cliente.Escribir en una cola o en una tabla tras procesar.
Code + hostTu lógica y el fichero de configuración del runtime (p. ej. host.json/function.json).La función en Python que manda un correo.

Analogía: una función es un timbre de una casa. El botón (trigger) es lo único que la hace sonar; los cables de entrada (input bindings) le llevan la corriente de otros sitios; el altavoz conectado (output binding) es donde sale el sonido; y la canción que suena es tu código. Si el timbre hiciera demasiadas cosas a la vez —sonar, encender luces, abrir la puerta y hablar— dejaría de ser un timbre y sería una instalación entera.

Modelos de disparo: no todo evento es igual

Los disparadores se agrupan en familias, y cada familia define cómo se comporta la función ante el error:

  • HTTP (síncrono): alguien llama y espera respuesta. Típico para webhooks y endpoints ligeros. Si tarda, el cliente espera; hay timeout.
  • Temporizador (timer/Cron): se ejecuta según una programación. Ideal para tareas de mantenimiento. No hay «quien llama».
  • Cola / mensajería (poll-based): la plataforma lee mensajes de una cola y llama a la función por lotes. Es el patrón del desacoplamiento (lección 2).
  • Evento (push): un servicio publica un evento y la plataforma empuja la llamada. Reactivo y de baja latencia.

Regla de oro de la entrega: casi toda mensajería serverless es at-least-once (al menos una vez). Eso significa que tu función puede ejecutarse más de una vez con el mismo evento. Diseña siempre idempotente: procesar dos veces el mismo mensaje no debe duplicar un cobro ni un correo. Volveremos a esto en la lección 2.

Planes de hosting en Azure: el frío, lo precalentado y lo fijo

En Azure Functions el «plan de hosting» decide precio, escalado, cold start y red. Es la decisión más importante al crear una función:

En AWS el equivalente se reparte entre dos ejes: Lambda (que siempre es «consumption», escala a cero y tiene cold start) y el provisioned concurrency o reserved concurrency como forma de pagar por instancias precalentadas o por aislar un cupo.

Cold start: qué es de verdad

Cuando una función no tiene instancia lista, la plataforma debe crear una antes de ejecutar tu código. Ese tiempo de arranque es el cold start y tiene dos fases:

   Llega el evento
        │
        ▼
  ┌───────────────┐   ┌──────────────────┐   ┌───────────────┐
  │ FASE "INIT"   │   │ CARGA RUNTIME +  │   │ EJECUCIÓN     │
  │ asigna host,  │──►│ tus dependencias │──►│ tu handler    │
  │ baja contenedor│  │ (imports, SQL…)  │   │ (lo que mides)│
  └───────────────┘   └──────────────────┘   └───────────────┘
      (fuera de facturación en Azure)         (esto sí se factura)

  Instancia caliente recibiendo más eventos -> NO hay cold start

Que el init sea lento depende del runtime (Java y .NET tradicional suelen arrancar más lento que Node o Python), del tamaño de las dependencias y del idioma. Un cold start de 1–3 s es habitual; con muchas dependencias o stacks pesados, más.

Cómo mitigarlo, de menos a más coste:

  1. Reducir el paquete: menos dependencias, imports perezosos. Gratis y siempre buena idea.
  2. Instancias precalentadas / provisioned concurrency: pagas por tener instancias listas. Elimina el cold start casi por completo.
  3. Mantener al menos una instancia (Premium/min 1): pagas aunque no haya tráfico, pero prácticamente no hay frío.
  4. SnapStart (AWS, algunos runtimes): restaura una instantánea de memoria ya inicializada.

No pelees contra el cold start antes de medirlo. Instrumenta la duración y la frecuencia de arranques en frío (Application Insights / CloudWatch) y decide con datos. Optimizar un cold start que ocurre dos veces al día es tiempo perdido; ignorar uno que golpea a cada usuario sí es un problema.

Límites que no se negocian

LímiteAzure Functions (Consumption)AWS Lambda
Duración máxima10 min (configurable)15 min (900 s)
Memoria1,5 GB por instancia (Consumption)128 MB – 10 240 MB (ajustable)
Almacenamiento temporalEn disco del host, efímero/tmp de 512 MB a 10 GB
Tamaño de payload HTTP~100 MB configurable por host6 MB síncrono
Estado entre invocacionesNo garantizado (puede reutilizarse, no lo asumas)Igual: reutiliza la instancia, pero no garantiza memoria
EscaladoAutomático por eventos (hasta un tope por plan)Automático por concurrencia (reservable)

La trampa clásica: la base de datos. Una función puede escalar a 200 instancias en segundos. Si cada instancia abre su propia conexión al PostgreSQL gestionado, lo tumbas («too many connections»). Por eso serverless + base de datos relacional exige un pooler (como PgBouncer) o un driver serverless. Este es el motivo práctico número uno por el que parte del Copiloto no es serverless (lección 4).

3 · Ejemplo mínimo

Lo más pequeño que se puede desplegar: un plan (que decide el modelo de hosting) y una function app con una función HTTP. En Azure, una misma Function App aloja varias funciones y comparte configuración.

main.tf — Function App mínima (Consumption, Linux)
# 1) El plan decide el modelo de hosting. "Y1" + Linux = Consumption (escala a 0).
resource "azurerm_service_plan" "func" {
  name                = "asp-copiloto-func"
  resource_group_name = var.resource_group_name
  location            = var.location
  os_type             = "Linux"
  sku_name            = "Y1"    # Y1 = Consumption; EP1.. = Premium
}

# 2) La Function App: runtime, almacenamiento interno y el plan de arriba.
resource "azurerm_linux_function_app" "min" {
  name                = "func-copiloto-min"
  resource_group_name = var.resource_group_name
  location            = var.location

  service_plan_id            = azurerm_service_plan.func.id
  storage_account_name       = azurerm_storage_account.func.name
  storage_account_access_key = azurerm_storage_account.func.primary_access_key

  site_config {
    application_stack {
      python_version = "3.11"     # el runtime que ejecutará tu código
    }
  }

  # Configuración de la app: variables de entorno que tu función lee.
  app_settings = {
    "FUNCTIONS_WORKER_RUNTIME" = "python"   # obligatorio: lenguaje del worker
    "APPINSIGHTS_INSTRUMENTATIONKEY" = azurerm_application_insights.main.instrumentation_key
  }
}

Qué acaba de pasar, pieza a pieza:

  1. azurerm_service_plan: es el modelo de hosting. Cambiar sku_name de "Y1" a un Premium cambia por completo el cold start, el timeout y la red. No es un detalle de rendimiento: es la decisión de arquitectura.
  2. storage_account_*: toda Function App necesita una cuenta de almacenamiento de apoyo (guarda el código, los checkpoints de los triggers y la coordinación del escalado). No es opcional.
  3. application_stack: fija el runtime. Aquí un python_version; en Node node_version; en .NET dotnet_version. Debe coincidir con lo que empaquetas.
  4. app_settings: variables de entorno y, muy importante, la cadena de Application Insights para ver logs y trazas.

Con la CLI, el atajo es az functionapp create, pero recuerda la regla del curso: lo que vayas a mantener, como código. La CLI sirve para explorar, no para reproducir entornos.

El contrato de la función: host.json

El runtime se configura con host.json en la raíz del proyecto. Es donde vive, por ejemplo, el timeout de las funciones de Consumption:

host.json — límites del runtime
{
  "version": "2.0",
  "functionTimeout": "00:05:00",
  "logging": {
    "applicationInsights": {
      "samplingSettings": {
        "isEnabled": true,
        "maxTelemetryItemsPerSecond": 20
      }
    }
  },
  "extensions": {
    "queues": {
      "batchSize": 16,
      "maxDequeueCount": 5
    }
  }
}

functionTimeout limita cuánto puede correr cada invocación (en Consumption, hasta 00:10:00). maxDequeueCount es el número de reintentos antes de mover un mensaje a la cola de mensajes fallidos (poison queue): un detalle pequeño con consecuencias grandes en la lección 2.

4 · Ejemplo real

Escenario del curso: la Copiloto API necesita generar un informe nocturno y preparar un resumen. Es una tarea de minutos, impredecible y no interactiva: un candidato perfecto a función. Aquí el detalle que cambia todo — nada de secretos en la configuración; la función usa su identidad gestionada para leer de Key Vault y escribir en Blob.

   Timer (00:00 UTC)                      Managed Identity
        │                                      │
        ▼                                      ▼
  ┌───────────────┐   lee secreto    ┌───────────────┐   escribe   ┌──────────┐
  │  Function     │─────────────────►│  Key Vault    │             │  Blob    │
  │  informe-diario│                  └───────────────┘             │ informe/ │
  └───────┬───────┘                                                 └──────────┘
          │ usa identity para el storage (sin claves)
          ▼
  Application Insights  ← logs, duración, fallos
copiloto-informe.tf — función con identity y Key Vault
# Plan Premium: sin cold start en una tarea con SLA y acceso a VNet.
resource "azurerm_service_plan" "copiloto" {
  name                = "asp-copiloto-jobs"
  resource_group_name = var.resource_group_name
  location            = var.location
  os_type             = "Linux"
  sku_name            = "EP1"   # Premium: instancias precalentadas, sin cold start
}

resource "azurerm_linux_function_app" "informe" {
  name                = "func-copiloto-informe"
  resource_group_name = var.resource_group_name
  location            = var.location

  service_plan_id = azurerm_service_plan.copiloto.id

  # Sin claves de storage en el repo: la app usa SU identidad.
  storage_account_name       = azurerm_storage_account.func.name
  storage_uses_managed_identity = true

  identity {
    type = "SystemAssigned"
  }

  site_config {
    application_stack {
      python_version = "3.11"
    }
  }

  app_settings = {
    "FUNCTIONS_WORKER_RUNTIME" = "python"

    # Key Vault se lee por REFERENCIA: el valor nunca aparece en Terraform.
    "DB_CONNECTION" = "@Microsoft.KeyVault(SecretUri=${azurerm_key_vault_secret.db.id})"

    # Enviar trazas a Application Insights.
    "APPLICATIONINSIGHTS_CONNECTION_STRING" = azurerm_application_insights.main.connection_string
  }
}

# La identidad de la función necesita permiso explícito para leer secretos (mínimo privilegio).
resource "azurerm_role_assignment" "kv_reader" {
  scope                = azurerm_key_vault.main.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_linux_function_app.informe.identity[0].principal_id
}

Lo que has ganado frente a escribir esto en el propio contenedor de la API:

  • Aislamiento de carga: el informe nocturno ya no compite por CPU/memoria con las peticiones de usuario. Si tarda, no degrada la API.
  • Coste proporcional: en Premium pagas por instancia, pero solo dimensionas lo que el job necesita; no engordas la API para que quepa este pico.
  • Sin credenciales: storage_uses_managed_identity y las referencias de Key Vault eliminan los secretos del repositorio (regla del curso). La identidad se autoriza con un rol explícito.

Si eligieras Consumption (sku "Y1") ahorrarías base a cambio de asumir cold start y un timeout más corto. Para un job con ventana amplia y tolerancia al arranque en frío, Consumption es totalmente razonable. La elección es una decisión informada, no una moda.

6 · Errores habituales

1. Guardar la cadena de conexión en app_settings

Incorrecto — secreto en claro en Terraform y en el state 
app_settings = {
  # ❌ Esto acaba en el repositorio y en el archivo de state
  "DATABASE_URL" = "postgresql://user:p@ss@copiloto-db.postgres.database.azure.com/app"
}
Correcto — referencia a Key Vault + identidad 
# ✅ El valor vive en Key Vault; Terraform solo guarda la REFERENCIA
identity { type = "SystemAssigned" }

app_settings = {
  "DATABASE_URL" = "@Microsoft.KeyVault(SecretUri=${azurerm_key_vault_secret.db.id})"
}
# Y se concede "Key Vault Secrets User" a la identidad de la función.

2. Creer que la instancia se reutiliza siempre

Incorrecto — guardar estado en memoria global 
# ❌ Un contador en memoria "de módulo" NO es fiable:
#   la plataforma puede reciclar la instancia (o crear otra) en cualquier momento.
contador_de_peticiones = 0   # global

def procesar(evento):
    global contador_de_peticiones
    contador_de_peticiones += 1   # puede "resetearse" sin avisar
Correcto — el estado vive fuera de la función 
# ✅ El estado persistente va a un servicio externo (Redis, tabla, blob).
# En la función solo se mantienen CACHES reconstruibles (p. ej. un cliente
# de conexión reutilizable), nunca la verdad del sistema.
def procesar(evento):
    redis_client.incr("peticiones")   # la verdad está en Redis

3. Elegir Consumption para una API interactiva con latencia crítica

Incorrecto — todo a Consumption por coste 
# ❌ Un endpoint que el usuario espera de forma síncrona,
#    servido por Consumption, con cold start de varios segundos.
sku_name = "Y1"    # frío en cada arranque de instancia
Correcto — Premium (o provisioned concurrency en AWS) 
# ✅ Si la latencia de arranque importa, paga por tener instancias listas.
sku_name = "EP1"   # Premium: instancias precalentadas, sin cold start
# AWS equivalente: provisioned concurrency en la función Lambda.

4. Ignorar el límite de tiempo y confiar en trabajos largos

# ❌ Una función que procesa un vídeo de 40 minutos en Lambda
#    => se agota a los 15 min (900 s) y el trabajo se pierde a medias.
# ❌ Lo mismo en Azure Consumption con functionTimeout de 5 min.

# ✅ Si el trabajo es largo: pártelo, muévelo a un contenedor/Job
#    (módulo 4) o usa un orquestador (Durable Functions / Step Functions).

Los límites de duración son de los más costosos de descubrir en producción. La pregunta correcta no es «¿cuánto tarda mi código?», sino «¿cuánto tarda en el percentil 99 con datos reales?».

7 · Ejercicio guiado

Objetivo: crear una función HTTP mínima, ejecutarla en local antes de desplegarla, y luego desplegarla comprobando que responde.

  1. Paso 1 — prepara el entorno local. Instala las Azure Functions Core Tools y crea el proyecto: 
    func --version            # comprueba que están las Core Tools
func init copiloto-func --worker-runtime python   # andamiaje del proyecto
cd copiloto-func
func new --name hello --template "HTTP trigger" --authlevel anonymous
  2. Paso 2 — arráncala en local. El runtime levanta un host HTTP local; no necesitas nube para probar: 
    func start
# Esperado: escucha en http://localhost:7071
#   hello: [GET,POST] http://localhost:7071/api/hello
  3. Paso 3 — invócala y observa el contrato. En otra terminal: 
    curl -s "http://localhost:7071/api/hello?name=Copiloto"
# Esperado: un JSON/texto con el saludo que devuelve tu función.
curl -s -X POST "http://localhost:7071/api/hello" -d '{"name":"Copiloto"}'
  4. Paso 4 — despliega con Terraform. Reutiliza el bloque mínimo de la sección 3 y publica el código: 
    az login
terraform init && terraform apply        # crea plan + function app

# Publica tu código en la app (zip deploy):
func azure functionapp publish func-copiloto-min --python
  5. Paso 5 (verificación) — llama a la función en la nube. Obtén la URL y comprueba la respuesta: 
    HOST=$(az functionapp show \
  --name func-copiloto-min --resource-group copiloto-lab-rg \
  --query defaultHostName --output tsv)
curl -s "https://$HOST/api/hello?name=Copiloto"
# Esperado: la MISMA respuesta que en local. Si da 404/500, revisa
# que el runtime y las dependencias subieron bien (mira los logs).
  6. Paso 6 — limpia (control de coste). 
    az group delete --name copiloto-lab-rg --yes --no-wait

Resultado esperado: la misma función responde idénticamente en local y en la nube. Este ida y vuelta —el mismo código, dos entornos— es lo que te permite iterar sin desplegar cada vez, y es la razón por la que las Core Tools existen.

8 · Reto

🎯 Medir el cold start y decidir con datos

Despliega la misma función en dos planes distintos (Consumption Y1 y Premium EP1) y mide el tiempo de respuesta en frío y en caliente por separado.

Diseña un experimento que fuerce arranques en frío (por ejemplo, dejando la función inactiva y volviendo a llamarla tras varios minutos) y registra: latencia del primer hit tras el reposo, latencia con instancia caliente, y cuántos arranques en frío ocurren en una hora de tráfico realista.

Con esos datos, decide y documenta: ¿qué función de la Copiloto merece Premium? ¿Cuál puede quedarse en Consumption? ¿Cuál es el sobrecoste mensual de eliminar el frío y qué gana el usuario a cambio?

Pista: mira métricas como FunctionExecutionCount y la duración en Application Insights; el cold start aparece como un salto de latencia tras un periodo sin ejecuciones. No busques un «número mágico» de segundos: busca tu distribución.

9 · Resumen

  • Una función serverless es una unidad reactiva: un trigger, un handler, código y configuración. No es «una app pequeña».
  • Las piezas son trigger, input/output bindings y código + host. El trigger define el contrato de entrada; solo hay uno.
  • Los modelos de disparo (HTTP, temporizador, cola, evento) definen el comportamiento ante errores. Asume siempre entrega al menos una vez e implementa idempotencia.
  • El plan de hosting decide coste, escalado, cold start y red: Consumption (barato, frío), Premium (precalentado), Dedicated (always on).
  • El cold start es el arranque de una instancia nueva; se mitiga reduciendo dependencias, con instancias precalentadas o con provisioned concurrency.
  • Hay límites duros de duración, memoria, payload y — el más traicionero — de conexiones a base de datos.
  • La función se prueba en local (Core Tools) y se despliega como código; los secretos van por identidad gestionada + Key Vault.

10 · Preguntas frecuentes

¿«Serverless» significa que no hay servidores en ninguna parte?

No. Significa que tú no los gestionas: no eliges SO, no parcheas, no dimensionas instancias. Hay servidores, pero son del proveedor, se crean y destruyen bajo demanda, y tú solo ves funciones y métricas. El valor no es «que no existan», sino que no tienes trabajo operativo sobre ellos.

¿Puedo usar la misma función para HTTP y para cola a la vez?

En Azure, una Function App aloja varias funciones, cada una con su trigger; pero una función concreta tiene un solo trigger. Si necesitas responder a HTTP y a una cola, casi siempre lo correcto no es unificar, sino desacoplar: un endpoint HTTP que publica un mensaje, y otra función con disparador de cola que lo procesa (justo lo del módulo 5, lección 2). Intentar que un handler haga de todo va contra el modelo de escalado por función.

¿Por qué mi función a veces tarda mucho aunque el código sea trivial?

Casi siempre es cold start: la plataforma creó una instancia nueva y tuvo que cargar el runtime y tus dependencias antes de ejecutar tu handler. Diagnóstico: mira la duración por invocación en Application Insights / CloudWatch y busca picos tras periodos de silencio. Mitigación: reducir dependencias, subir a Premium o usar provisioned concurrency. Verifica que no sea otra cosa antes de culpar al frío.

¿Cómo conecto la función a un PostgreSQL gestionado sin tumbar la base?

Con un pooler (p. ej. PgBouncer) entre la función y la base, o con un driver diseñado para entornos serverless. El problema es que cada instancia de la función abre conexiones propias y el escalado multiplica ese número; el motor tiene un límite de conexiones y lo agotas rápido. Es una de las razones técnicas por las que el Copiloto mantiene su API con estado de conexión en contenedores (lección 4).

¿Las funciones se pagan aunque no hagan nada?

En los planes que escalan a cero (Consumption, Flex, Lambda), cuando no hay ejecuciones no hay coste de cómputo: pagas por ejecuciones y por el tiempo de facturación. Pero ojo: si eliges Premium, min alto o provisioned concurrency, sí pagas por tener instancias calientes sin tráfico. Además hay costes asociados (storage interno, Application Insights, transferencia). La factura sorpresa viene de picos y de mínimos mal dimensionados, no del modelo en sí: míralo en el módulo 6.
