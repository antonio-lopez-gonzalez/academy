pnpm, package.json, dependencias, scripts

Módulo 7 · Módulos, tooling y testing ⏱ 25 minutos

1 · Introducción

Todo proyecto JavaScript/Node profesional tiene un archivo package.json. Es el manifiesto del proyecto: describe su nombre, versión, dependencias, scripts y metadatos. Sin él, no hay proyecto.

En este curso usamos pnpm como gestor de paquetes en lugar de npm. pnpm es hasta 3 veces más rápido que npm, ahorra gigabytes de disco porque almacena los paquetes una sola vez en un almacén global enlazado con hard links, y respeta estrictamente qué dependencias puede usar cada paquete (sin accesos fantasmas a node_modules).

¿Por qué pnpm?

npm instala cada dependencia por proyecto, duplicando paquetes en disco. yarn mejoró la velocidad pero sigue duplicando. pnpm usa un content-addressable store global: cada versión de cada paquete se almacena una sola vez en el disco. Tus proyectos referencian esos paquetes mediante hard links. Además, pnpm crea un node_modules no plano: cada paquete solo puede acceder a sus dependencias declaradas, evitando el infame "phantom dependency" bug.

2 · Teoría

package.json: anatomía completa

{
  "name": "mi-proyecto",
  "version": "1.0.0",
  "description": "Descripción del proyecto",
  "private": true,
  "type": "module",
  "main": "./src/index.js",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "test": "vitest",
    "lint": "eslint ."
  },
  "dependencies": {
    "lodash": "^4.17.21"
  },
  "devDependencies": {
    "vite": "^8.0.0",
    "vitest": "^4.0.0"
  },
  "peerDependencies": {
    "react": ">=18.0.0"
  },
  "engines": {
    "node": ">=20.19.0",
    "pnpm": ">=9.0.0"
  }
}

Campos esenciales

  • name: nombre del paquete (si publicas en npm, debe ser único). En minúsculas, sin espacios, usando guiones.
  • version: sigue SemVer (MAJOR.MINOR.PATCH). Ej: 1.2.3.
  • private: si es true, evita que publiques accidentalmente el paquete en npm.
  • type: "module" para ESM o "commonjs" (por defecto). Determina cómo se interpretan los .js.
  • main: punto de entrada cuando alguien hace require('mi-proyecto') o import 'mi-proyecto'.

Dependencias: dependencies vs devDependencies vs peerDependencies

  • dependencies: paquetes necesarios en producción. Si tu app necesita lodash para funcionar, va aquí. Se instalan con pnpm add lodash.
  • devDependencies: paquetes necesarios solo durante el desarrollo: testing, bundling, linting, tipado. pnpm add -D vitest.
  • peerDependencies: paquetes que tu librería espera que el consumidor tenga instalados. Útil para plugins: un plugin de React declara React como peer dependency para no instalar su propia copia. pnpm add --save-peer react.
En aplicaciones (no librerías), dependencies vs devDependencies no importa tanto

Si estás construyendo una aplicación (no un paquete npm reutilizable), la distinción es menos crítica porque no publicas el package.json a npm. Aun así, mantener la separación ayuda a documentar qué es esencial para producción y qué es tooling.

SemVer: versionado semántico

MAJOR.MINOR.PATCH (ej: 2.5.1):

  • MAJOR: cambios incompatibles con versiones anteriores (breaking changes).
  • MINOR: nuevas funcionalidades compatibles hacia atrás.
  • PATCH: correcciones de bugs compatibles hacia atrás.

Los prefijos en package.json controlan qué actualizaciones aceptas:

  • ^2.5.1: acepta cualquier versión compatible con 2.x.x (>=2.5.1 <3.0.0). Es la más común.
  • ~2.5.1: acepta solo patches (>=2.5.1 <2.6.0). Más conservador.
  • * o x: cualquier versión. Peligroso, evítalo.
  • >=2.5.1: mayor o igual. Útil para peer dependencies.
  • Sin prefijo (2.5.1): versión exacta. Blockea actualizaciones.

Archivos lock: package-lock.json / pnpm-lock.yaml

El archivo lock (pnpm-lock.yaml para pnpm) registra las versiones exactas de cada dependencia y sus sub-dependencias. Garantiza que todos los desarrolladores y el CI instalen exactamente las mismas versiones. Siempre se commitea al repositorio.

Scripts del package.json

Los scripts son comandos que se ejecutan con pnpm run nombre (o pnpm nombre para algunos atajos como test, start).

{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "test": "vitest run",
    "test:watch": "vitest",
    "lint": "eslint . --ext .js",
    "format": "prettier --write .",
    "prepare": "husky install"
  }
}

Pre y post hooks

Si defines un script build, puedes definir prebuild (se ejecuta antes) y postbuild (después). pnpm los ejecuta automáticamente:

{
  "scripts": {
    "prebuild": "pnpm run lint",
    "build": "vite build",
    "postbuild": "echo 'Build completado'"
  }
}

Comandos esenciales de pnpm

pnpm install           # Instalar todas las dependencias
pnpm add lodash        # Añadir a dependencies
pnpm add -D vitest     # Añadir a devDependencies
pnpm add -g typescript # Instalar globalmente
pnpm remove lodash     # Eliminar dependencia
pnpm update            # Actualizar dependencias según rangos
pnpm update --latest   # Actualizar a las últimas versiones (ignorando ^ y ~)
pnpm exec vitest       # Ejecutar un binario de node_modules (igual que npx)
pnpm run dev           # Ejecutar un script (se puede abreviar pnpm dev)
pnpm list              # Listar dependencias instaladas
pnpm why lodash        # ¿Por qué está instalado lodash? Muestra el árbol

node_modules y .gitignore

node_modules nunca se commitea a git. Es demasiado grande y se regenera con pnpm install. Tu .gitignore debe incluir:

node_modules/
dist/
.env
*.log

3 · Ejemplo mínimo

# 🧪 Crear un proyecto desde cero en 5 comandos
mkdir mi-proyecto && cd mi-proyecto

# Inicializar package.json con valores por defecto (-y)
pnpm init -y

# El package.json generado contiene lo mínimo:
# { "name": "mi-proyecto", "version": "1.0.0", ... }

# Añadir una dependencia de producción
pnpm add lodash

# Añadir una dependencia de desarrollo
pnpm add -D vitest

# Ejecutar un script (primero hay que definirlo en package.json)
pnpm run test

Tras estos comandos, tu package.json queda:

{
  "name": "mi-proyecto",
  "version": "1.0.0",
  "scripts": {
    "test": "vitest"
  },
  "dependencies": {
    "lodash": "^4.17.21"
  },
  "devDependencies": {
    "vitest": "^4.0.0"
  }
}

4 · Ejemplo real

package.json profesional para una aplicación Vite + Vitest

{
  "name": "taskflow-vanilla",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "description": "SPA de gestión de tareas sin frameworks",
  "scripts": {
    "dev": "vite --open",
    "build": "vite build",
    "preview": "vite preview",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:coverage": "vitest run --coverage",
    "lint": "eslint . --ext .js",
    "format": "prettier --write \"src/**/*.{js,css,html}\"",
    "prepare": "husky"
  },
  "dependencies": {},
  "devDependencies": {
    "vite": "^8.0.0",
    "vitest": "^4.0.0",
    "@vitest/coverage-v8": "^4.0.0",
    "eslint": "^8.57.0",
    "prettier": "^3.3.0",
    "husky": "^9.1.0"
  },
  "engines": {
    "node": ">=20.19.0",
    "pnpm": ">=9.0.0"
  }
}

Observaciones sobre este package.json profesional:

  • "private": true: evita publicación accidental a npm.
  • "type": "module": usa ESM en todo el proyecto.
  • Scripts con dos puntos (test:watch, test:coverage): convención para agrupar scripts relacionados. No tiene significado especial, es solo naming.
  • dependencies vacío: esta app no necesita runtime de terceros; todo es JS vanilla + Vite.
  • "prepare": "husky": se ejecuta automáticamente tras pnpm install para configurar git hooks.
  • engines: declara qué versiones de Node y pnpm requiere el proyecto. pnpm y muchos CI tools lo respetan.

6 · Errores habituales

Error 1: Instalar dependencias de producción como devDependencies (o viceversa)

# ❌ MAL: express es necesario en producción, -D es incorrecto
pnpm add -D express

# ✅ CORRECTO
pnpm add express

# ❌ MAL: eslint solo se usa en desarrollo, no debería ir en dependencies
pnpm add eslint

# ✅ CORRECTO
pnpm add -D eslint

Error 2: Olvidar el flag -D al instalar tooling

# ❌ MAL: vitest NO debería ir en dependencies
pnpm add vitest

# ✅ CORRECTO
pnpm add -D vitest

Error 3: Committear node_modules

# ❌ MAL: git add . incluye node_modules
git add .

# ✅ CORRECTO: asegúrate de que .gitignore incluya node_modules/
# Ejemplo de .gitignore:
# node_modules/
# dist/
# .env

Error 4: Usar npm en lugar de pnpm en un proyecto que usa pnpm

# ❌ MAL: mezclar gestores genera lock files inconsistentes
npm install

# ✅ CORRECTO: usa siempre pnpm
pnpm install

7 · Ejercicio guiado

Inicializa un proyecto desde cero con pnpm y Vite

  1. Crea el directorio e inicializa package.json. 
    mkdir mi-primera-app && cd mi-primera-app
pnpm init -y
  2. Edita package.json para añadir type module y scripts. 
    {
  "name": "mi-primera-app",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  }
}
  3. Instala Vite como dependencia de desarrollo. 
    pnpm add -D vite

    Observa cómo package.json ahora tiene devDependencies con vite y se creó pnpm-lock.yaml.

  4. Crea el entry point HTML y ejecuta el servidor. 
    # Crea index.html con el contenido mínimo
pnpm dev

    Si todo está correcto, Vite arranca un servidor en http://localhost:5173 con HMR (Hot Module Replacement).

  5. Añade un script de build y comprueba que funciona. 
    pnpm build
# Deberías ver una carpeta dist/ con los archivos optimizados
  6. Instala Vitest y añade un script de test. 
    pnpm add -D vitest

    Añade al package.json: "test": "vitest run". Ahora pnpm test ejecuta (aunque no haya tests aún).

8 · Reto

🎯 Crea un monorepo con pnpm workspaces

Crea un monorepo con pnpm workspaces que contenga dos paquetes: una librería de utilidades (packages/utils) y una aplicación que la consuma (apps/web). La app debe importar funciones de utils. Usa pnpm-workspace.yaml para definir los workspaces y pnpm add utils --filter web para añadir la dependencia local.

Requisitos:

  • Un pnpm-workspace.yaml en la raíz que defina packages/* y apps/*.
  • El paquete utils con "name": "@academy/utils" y al menos una función exportada.
  • La app web importando esa función con el nombre del paquete (@academy/utils).
  • Un script en la raíz que ejecute pnpm -r dev para arrancar todos los paquetes.

9 · Resumen

  • package.json es el manifiesto del proyecto: nombre, versión, dependencias, scripts.
  • dependencies = producción; devDependencies = desarrollo; peerDependencies = esperas que el consumidor las tenga.
  • SemVer: MAJOR.MINOR.PATCH. ^ permite minors y patches, ~ solo patches.
  • El archivo lock (pnpm-lock.yaml) registra versiones exactas. Siempre se commitea.
  • Scripts: comandos atajo (pnpm run dev = pnpm dev). Pre/post hooks automáticos.
  • pnpm: más rápido, menos disco, más estricto que npm. Usa store global con hard links.
  • node_modules nunca se commitea a git. Inclúyelo en .gitignore.
  • Comandos clave: pnpm add, pnpm add -D, pnpm remove, pnpm update, pnpm exec.

10 · Preguntas frecuentes

¿puedo usar npm en lugar de pnpm en este curso?

El curso está diseñado para pnpm y todos los comandos usan pnpm. Técnicamente puedes usar npm o yarn, pero te encontrarás con diferencias en comandos (pnpm exec vs npx) y en la estructura de node_modules. Recomiendo instalar pnpm: npm install -g pnpm. Es compatible con todos los paquetes npm.

¿Cuándo debería usar pnpm update vs editar package.json manualmente?

pnpm update actualiza dentro del rango definido (respeta ^ y ~). Si quieres la última versión absoluta ignorando el rango, usa pnpm update --latest. Editar manualmente el package.json y luego hacer pnpm install también funciona. Personalmente prefiero pnpm add lodash@latest si quiero una versión concreta; es más explícito.

¿Qué es exactamente un "phantom dependency"?

En npm y yarn clásico, node_modules es plano: todas las dependencias, incluso las de tus dependencias, están al mismo nivel. Esto permite que tu código importe un paquete que no declaraste en tu package.json porque alguna dependencia lo instaló. Si esa dependencia se actualiza y elimina el paquete, tu código se rompe misteriosamente. pnpm previene esto: solo puedes importar lo que declaraste explícitamente.

¿Por qué veo ^ en las versiones de package.json pero versiones exactas en el lock?

El ^ en package.json es tu intención (rango aceptable). El lock file registra la versión exacta que se instaló en ese momento. Cuando otro desarrollador hace pnpm install, usa las versiones exactas del lock, NO recalcula desde el rango. Si haces pnpm update, renegocia dentro del rango y actualiza el lock.
