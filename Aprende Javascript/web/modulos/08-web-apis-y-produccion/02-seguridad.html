Seguridad: XSS, CORS, CSP, sanitización

Módulo 8 · Web APIs y Producción ⏱ 35 minutos

1 · Introducción

Imagina que construyes la app perfecta: rápida, responsive, con animaciones fluidas... y un atacante consigue robar los datos de todos tus usuarios con una sola línea de texto. Suena a película de hackers, pero ocurre cada día. La seguridad en el frontend no es opcional — es parte del contrato con tus usuarios.

El frontend es la capa más expuesta de una aplicación. Todo el código JavaScript se envía al navegador del usuario, donde cualquiera puede leerlo, modificarlo y atacarlo. No puedes confiar en que el cliente "se porte bien". Debes programar como si cada input pudiera ser malicioso.

Analogía: El frontend es como la recepción de un hotel. Cualquiera puede entrar por la puerta. Tu trabajo como recepcionista no es confiar en que todos los que entran son huéspedes legítimos — tu trabajo es verificar identidades, no dejar pasar a zonas restringidas y asegurarte de que nadie pone una bomba en el buzón de sugerencias.

En esta lección cubriremos los ataques más comunes al frontend y las defensas que tienes a tu disposición:

  • XSS (Cross-Site Scripting): el ataque rey del frontend. Cómo evitarlo con sanitización.
  • CORS (Cross-Origin Resource Sharing): por qué el navegador bloquea peticiones entre dominios y cómo configurarlo.
  • CSP (Content Security Policy): el escudo definitivo contra inyección de código.
  • Cookies seguras y CSRF: cómo proteger las sesiones de tus usuarios.
  • Secretos en el frontend: por qué NUNCA debes guardar API keys en el código del cliente.

2 · Teoría

XSS (Cross-Site Scripting): el ataque más común del frontend

El XSS ocurre cuando un atacante consigue inyectar JavaScript malicioso en tu página web que luego se ejecuta en los navegadores de otros usuarios. El nombre es engañoso: no tiene nada que ver con CSS. "Cross-Site" significa que el código malicioso viene de fuera del sitio.

Hay tres tipos principales de XSS:

TipoMecanismoEjemplo
Stored XSS El atacante guarda código malicioso en la base de datos (ej: un comentario con una etiqueta <script>) Un foro que muestra comentarios sin escapar HTML. El script se ejecuta para TODOS los visitantes.
Reflected XSS El código viene en la URL y se refleja en la respuesta de la página /buscar?q=<script>robarCookies()</script>. Si la página muestra el parámetro q sin escapar, el script se ejecuta.
DOM-based XSS El ataque ocurre completamente en el navegador, manipulando el DOM con JavaScript vulnerable Un innerHTML = location.hash que inyecta un script directamente en la página.

¿Por qué existe XSS? Porque HTML, CSS y JavaScript se mezclan en el mismo documento. Cuando muestras datos que vienen del usuario (o de una API externa), el navegador no sabe distinguir entre "esto es texto que quiero mostrar" y "esto es código que quiero ejecutar". La única forma de distinguirlo es escapar o sanitizar el contenido antes de insertarlo en el DOM.

Las defensas contra XSS, por orden de preferencia:

  1. NUNCA uses innerHTML con datos que no controlas al 100%. Usa textContent (escapa HTML automáticamente) o createElement + appendChild.
  2. Si necesitas insertar HTML (ej: contenido de un editor de texto enriquecido), sanitízalo con DOMPurify — la librería estándar de la industria, mantenida por el equipo de seguridad de cure53.
  3. Usa Content Security Policy (CSP) como defensa en profundidad — incluso si un atacante logra inyectar un script, el CSP puede bloquear su ejecución.

CORS (Cross-Origin Resource Sharing)

Por defecto, los navegadores aplican la política del mismo origen: una página web solo puede hacer peticiones HTTP a su propio dominio. Si tu página está en https://miapp.com, no puede hacer un fetch a https://api.externa.com — a menos que esa API externa lo permita explícitamente.

Esta restricción es una defensa del usuario, no del servidor. Imagina que entras a malware.com y ese sitio intenta hacer fetch a tu-banco.com/tranferir usando tus cookies de sesión. Sin la política del mismo origen, el ataque funcionaría.

CORS es el mecanismo que permite relajar esta política de forma controlada. Cuando haces una petición cross-origin, el navegador:

  1. Envía una cabecera Origin con tu dominio.
  2. El servidor responde con una cabecera Access-Control-Allow-Origin (si te acepta).
  3. El navegador comprueba la respuesta y la deja pasar (o la bloquea).

Para peticiones "complejas" (todo lo que no sea GET/HEAD/POST con Content-Type simple), el navegador envía primero una petición preflight con el método OPTIONS para preguntar si el servidor acepta la petición real.

CSP (Content Security Policy)

El CSP es una capa de seguridad adicional que le dice al navegador: "solo ejecuta scripts que vengan de ESTOS orígenes". Se configura mediante una cabecera HTTP (recomendado) o una etiqueta <meta> en el HTML.

Una política CSP típica se ve así:

Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com; img-src *;

Esto significa: por defecto solo admite recursos del mismo origen. Scripts solo del mismo origen. Estilos del mismo origen y de Google Fonts. Imágenes de cualquier sitio. Cualquier intento de ejecutar un script inline (<script>alert(1)</script>) o de cargar un script de un dominio externo no autorizado será BLOQUEADO por el navegador.

CSP es defensa en profundidad. No sustituye a la sanitización — la complementa. Si por algún motivo se te escapa un XSS, el CSP puede salvarte. Pero no debes confiar en él como única defensa.

Cookies seguras y CSRF

Las cookies de sesión son el mecanismo más común de autenticación web. Si un atacante roba la cookie de sesión de un usuario, puede hacerse pasar por él. Por eso las cookies deben configurarse con tres flags críticos:

FlagQué haceContra qué protege
HttpOnlyLa cookie NO es accesible desde JavaScript (document.cookie)XSS — aunque inyecten código, no pueden leer la cookie de sesión
SecureLa cookie SOLO se envía por HTTPSMan-in-the-middle en redes WiFi públicas
SameSiteControla si la cookie se envía en peticiones cross-site (Lax, Strict, None)CSRF (Cross-Site Request Forgery)

Un ataque CSRF (Cross-Site Request Forgery) ocurre cuando un sitio malicioso hace que tu navegador realice una petición no deseada a un sitio donde tienes sesión iniciada. Por ejemplo: entras a evil.com y esa página tiene un formulario oculto que hace POST a tu-banco.com/transferir?monto=1000&destino=hacker. Si tu banco usa cookies de sesión sin SameSite, la petición se envía con tus credenciales.

Secretos en el frontend: la regla de oro

NUNCA guardes secretos en el frontend. Esto incluye: API keys, tokens de acceso a bases de datos, claves privadas, contraseñas de servicios externos. Todo lo que está en el código JavaScript del frontend es visible para cualquiera que abra las DevTools.

Si tu app necesita comunicarse con APIs de terceros (OpenAI, Stripe, Google Maps), tienes dos opciones seguras:

  1. Backend proxy: crea un endpoint en tu backend que haga la petición a la API externa. La clave API vive en el servidor, nunca llega al frontend.
  2. Variables de entorno en build time: Vite expone las variables con prefijo VITE_ al cliente. Úsalas SOLO para configuraciones no sensibles (URLs de API, flags de feature). Las claves secretas NUNCA deben tener prefijo VITE_.

3 · Ejemplo mínimo

XSS: innerHTML vs textContent

// ❌ VULNERABLE A XSS: innerHTML interpreta HTML
const userInput = '<img src=x onerror="alert(\'hackeado\')">';
document.getElementById('output').innerHTML = userInput;
// Resultado: se ejecuta el alert. El atacante acaba de ejecutar código en tu página.

// ✅ SEGURO: textContent escapa el HTML automáticamente
document.getElementById('output').textContent = userInput;
// Resultado: muestra el texto literal sin interpretar nada.

Sanitización con DOMPurify

// Si NECESITAS permitir HTML (ej: editor de texto enriquecido), sanitiza
import DOMPurify from 'dompurify';

const dirtyHTML = '<p>Hola</p><img src=x onerror="robarCookies()">';
const cleanHTML = DOMPurify.sanitize(dirtyHTML);
// Resultado: '<p>Hola</p><img src="x">'
// El onerror malicioso fue eliminado automáticamente
document.getElementById('output').innerHTML = cleanHTML;

CORS: petición cross-origin

// Petición a una API en otro dominio
fetch('https://api.externa.com/datos', {
  method: 'GET',
  headers: { 'Content-Type': 'application/json' }
})
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => {
    // Si el servidor NO envía Access-Control-Allow-Origin, el navegador bloquea la respuesta
    // y el error será de tipo TypeError (no un error HTTP)
    if (err.message.includes('CORS')) {
      console.error('CORS bloqueó la petición');
    }
  });

Cookies seguras (desde el servidor)

Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=3600

4 · Ejemplo real

Construyamos una sección de comentarios segura — el ejemplo clásico de XSS almacenado:

<!-- Formulario de comentarios -->
<form id="comment-form">
  <textarea id="comment-input" placeholder="Escribe tu comentario..."></textarea>
  <button type="submit">Enviar</button>
</form>
<div id="comments-list"></div>
<div id="error-message" style="color: red; display: none;"></div>
// Versión SEGURA del sistema de comentarios
class SafeComments {
  constructor() {
    this.comments = [];          // En producción, esto vendría del servidor
    this.form = document.getElementById('comment-form');
    this.input = document.getElementById('comment-input');
    this.list = document.getElementById('comments-list');
    this.errorDiv = document.getElementById('error-message');

    this.form.addEventListener('submit', (e) => {
      e.preventDefault();
      this.addComment(this.input.value);
      this.input.value = '';
    });
  }

  // Sanitiza un string eliminando cualquier HTML
  sanitize(input) {
    const div = document.createElement('div');
    div.textContent = input;  // textContent escapa todo el HTML
    return div.innerHTML;     // Devuelve la versión escapada (segura)
  }

  addComment(text) {
    if (!text.trim()) {
      this.showError('El comentario no puede estar vacío.');
      return;
    }

    const sanitized = this.sanitize(text);
    this.comments.push(sanitized);
    this.render();
    this.hideError();
  }

  render() {
    // Crear elementos DOM en lugar de usar innerHTML con template strings
    this.list.innerHTML = ''; // Limpiar (seguro porque no hay datos de usuario)
    this.comments.forEach((comment, index) => {
      const article = document.createElement('article');
      article.className = 'comment';

      const header = document.createElement('header');
      const span = document.createElement('span');
      span.textContent = `Comentario #${index + 1}`;
      header.appendChild(span);

      const p = document.createElement('p');
      p.textContent = comment; // textContent = seguro

      article.appendChild(header);
      article.appendChild(p);
      this.list.appendChild(article);
    });
  }

  showError(msg) {
    this.errorDiv.textContent = msg; // textContent = seguro
    this.errorDiv.style.display = 'block';
  }

  hideError() {
    this.errorDiv.style.display = 'none';
  }
}

// Inicializar
new SafeComments();

Puntos clave: (1) Usamos textContent para insertar cualquier dato que venga del usuario. (2) El método sanitize() usa un truco: mete el texto en un div con textContent (lo escapa) y luego lee innerHTML (devuelve la versión escapada). (3) Al renderizar, creamos elementos DOM manualmente para evitar cualquier inyección. (4) NUNCA concatenamos datos de usuario dentro de un template string que luego asignamos a innerHTML.

5 · Buenas prácticas

HazEvitaPor qué
Usa textContent para todo dato externo innerHTML con datos de usuario o de API innerHTML interpreta HTML. Cualquier script o event handler en el string se ejecutará. textContent lo trata como texto plano.
Sanitiza con DOMPurify si necesitas HTML Escribir tu propio sanitizador con regex Sanitizar HTML es increíblemente complejo. Los atacantes conocen miles de formas de evadir filtros. DOMPurify es una librería de batalla mantenida por expertos en seguridad.
Configura CSP en el servidor como cabecera HTTP Confiar solo en la sanitización del frontend El CSP es tu red de seguridad. Si algo se escapa del sanitizador, el navegador bloquea la ejecución de scripts no autorizados. Es defensa en profundidad.
Usa VITE_API_URL para URLs de API (configuración no sensible) Usar VITE_ para claves privadas o tokens Todo lo que empieza por VITE_ se incrusta en el bundle de producción. Cualquiera puede verlo abriendo las DevTools. Las claves deben vivir solo en el backend.
Valida y sanitiza en el servidor SIEMPRE Validar solo en el frontend Un atacante puede saltarse la validación del frontend simplemente usando curl o Postman. El frontend valida para UX. El backend valida para seguridad.
Configura HttpOnly; Secure; SameSite=Lax en cookies de sesión Cookies sin flags de seguridad HttpOnly bloquea el acceso desde JavaScript (anti-XSS). Secure fuerza HTTPS. SameSite previene CSRF en la mayoría de casos.

7 · Ejercicio guiado

Vamos a construir una función segura de búsqueda que reemplace los resultados en el DOM sin riesgo de XSS:

  1. HTML base:

    <input type="search" id="search-input" placeholder="Buscar productos..." />
<div id="search-results"></div>
<template id="result-template">
  <article class="search-result">
    <h3 class="result-title"></h3>
    <p class="result-desc"></p>
  </article>
</template>

    El <template> es clave: es HTML que el navegador no renderiza, pero podemos clonarlo con JavaScript. Así evitamos construir HTML con strings.

  2. Función segura de renderizado:

    function renderResults(products) {
  const container = document.getElementById('search-results');
  const template = document.getElementById('result-template');

  // Limpiamos resultados anteriores
  container.innerHTML = ''; // Seguro: no hay datos de usuario aquí

  products.forEach((product) => {
    // Clonar el template de forma segura (deep clone)
    const clone = template.content.cloneNode(true);

    // Usar textContent para todos los datos (nunca innerHTML)
    clone.querySelector('.result-title').textContent = product.name;
    clone.querySelector('.result-desc').textContent = product.description;

    container.appendChild(clone);
  });
}

  3. Función de búsqueda con debounce (¡próxima lección!) y escape de HTML:

    // Función de escape manual por si no podemos usar textContent
function escapeHTML(str) {
  const map = {
    '&': '&amp;',
    '<': '&lt;',
    '>': '&gt;',
    '"': '&quot;',
    "'": '&#039;'
  };
  return str.replace(/[&<>"']/g, (char) => map[char]);
}

9 · Resumen

  • XSS: el ataque más común del frontend. Evítalo usando textContent en lugar de innerHTML. Si necesitas HTML, sanitiza con DOMPurify.
  • CORS: el navegador bloquea peticiones cross-origin por defecto. El servidor debe responder con Access-Control-Allow-Origin para permitirlas.
  • CSP: política de seguridad que restringe qué scripts pueden ejecutarse. Defensa en profundidad, no reemplaza la sanitización.
  • Cookies seguras: siempre con HttpOnly (anti-XSS), Secure (solo HTTPS) y SameSite=Lax (anti-CSRF).
  • NUNCA guardes secretos en el frontend. Usa un backend proxy para APIs que requieran claves.
  • Variables Vite con prefijo VITE_: solo para configuración pública (URLs de API, flags de feature), nunca para secretos.
  • Valida en el servidor siempre. El frontend valida por UX, el backend por seguridad. Confía cero en el cliente.

10 · Preguntas frecuentes

¿DOMPurify es suficiente para prevenir todos los XSS?

DOMPurify es la mejor defensa del lado del cliente, pero no es infalible. Periódicamente se descubren bypasses (aunque el equipo de cure53 los corrige muy rápido). La estrategia correcta es defensa en profundidad: sanitizar con DOMPurify + CSP + cookies HttpOnly + validación en servidor. Cuantas más capas, más difícil para el atacante.

¿Por qué no debo guardar el token JWT en localStorage?

Porque cualquier código JavaScript que se ejecute en tu página puede leer localStorage. Si hay un XSS (y siempre puede haberlo), el atacante roba el token y puede hacer peticiones autenticadas como el usuario. Las cookies HttpOnly son inaccesibles desde JavaScript, por lo que un XSS no puede robarlas. Si necesitas acceso al token desde JS para añadirlo a cabeceras, guárdalo en una variable en memoria (se pierde al cerrar la pestaña) y usa refresh tokens HttpOnly para renovarlo.

¿Necesito HTTPS para desarrollar en local?

No es necesario para desarrollo local, pero algunas APIs (Clipboard, Geolocation, Notifications) requieren contexto seguro. localhost se considera seguro por los navegadores. Si necesitas probar en otros dispositivos de tu red local, Vite puede generar certificados autofirmados con el plugin @vitejs/plugin-basic-ssl.

¿Qué hago si una API externa no soporta CORS?

Tienes dos opciones: (1) Crear un proxy en tu backend que reenvíe las peticiones (tu servidor hace la petición a la API externa y devuelve el resultado al frontend). (2) Usar un servicio de proxy CORS público como corsproxy.io SOLO para desarrollo (nunca en producción — estarías enviando tus datos a un tercero). La opción correcta para producción es siempre un backend proxy.
