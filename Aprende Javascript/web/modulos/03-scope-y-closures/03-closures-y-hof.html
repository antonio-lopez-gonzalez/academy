Closures y funciones de orden superior

Módulo 3 · Scope, closures y PF ⏱ 35 minutos

1 · Introducción

Un closure es el mecanismo más elegante y poderoso de JavaScript. No es una característica que "usas": es una consecuencia natural de cómo funciona el scope léxico. Cada vez que una función "recuerda" las variables del scope donde fue creada, incluso después de que ese scope haya terminado de ejecutarse, tienes un closure.

Los closures son la base de los módulos, las funciones fábrica, la memoización, los hooks de React, el patrón middleware de Express, y prácticamente cualquier API moderna de JavaScript. Si no entiendes los closures, no entiendes JavaScript.

Analogía de la mochila: imagina que cada función lleva una mochila invisible. Cuando la función se crea, mete en su mochila todas las variables del scope que la rodea. Cuando la función viaja a otro lugar (se pasa como callback, se devuelve de otra función), su mochila viaja con ella. Las variables de la mochila no desaparecen aunque el lugar donde se crearon ya no exista.

2 · Teoría

Definición formal de closure

Un closure es la combinación de una función y su entorno léxico (las variables que estaban en su scope en el momento de su creación). Técnicamente, toda función en JavaScript es un closure, pero el término se usa cuando la función accede a variables de un scope exterior que ya no está activo.

function crearContador() {
  let count = 0; // variable privada en el scope de crearContador

  return function () {  // esta función interna es un closure
    count++;            // accede a 'count' del scope padre
    return count;
  };
  // Cuando crearContador termina, su scope "debería" desaparecer...
  // pero la función interna mantiene una referencia viva (closure)
}

const contador = crearContador();
console.log(contador()); // 1
console.log(contador()); // 2
console.log(contador()); // 3
// count sigue viva en la mochila del closure, privada e inaccesible desde fuera

Patrón Module (Revealing Module Pattern)

Antes de los módulos ES, el patrón módulo era la forma estándar de crear APIs públicas con estado privado. Combina IIFE + closure:

const Banco = (() => {
  // Variables privadas (scope de la IIFE)
  const cuentas = new Map();
  let totalCuentas = 0;

  // Función privada (no expuesta)
  function generarIBAN() {
    return `ES${Date.now()}${totalCuentas}`;
  }

  // API pública (lo que devolvemos)
  return {
    crearCuenta(titular, saldoInicial = 0) {
      const iban = generarIBAN(); // acceso al closure
      cuentas.set(iban, { titular, saldo: saldoInicial });
      totalCuentas++;
      return iban;
    },

    obtenerSaldo(iban) {
      return cuentas.has(iban) ? cuentas.get(iban).saldo : null;
    },

    transferir(origen, destino, cantidad) {
      const ctaOrigen = cuentas.get(origen);
      const ctaDestino = cuentas.get(destino);
      if (!ctaOrigen || !ctaDestino) return false;
      if (ctaOrigen.saldo < cantidad) return false;
      ctaOrigen.saldo -= cantidad;
      ctaDestino.saldo += cantidad;
      return true;
    },

    get total() {
      return totalCuentas;
    },
  };
})();

const ibanAna = Banco.crearCuenta("Ana", 1000);
const ibanLuis = Banco.crearCuenta("Luis", 500);
Banco.transferir(ibanAna, ibanLuis, 200);

console.log(Banco.obtenerSaldo(ibanAna));  // 800
console.log(Banco.obtenerSaldo(ibanLuis)); // 700
console.log(Banco.total);                   // 2
// cuentas, totalCuentas y generarIBAN son inaccesibles desde fuera

Funciones fábrica (Factory Functions)

Cada llamada a la fábrica crea un nuevo closure independiente. Las variables privadas de una instancia no interfieren con las de otra:

function crearJugador(nombre) {
  let puntuacion = 0; // privada, única por cada jugador
  let vidas = 3;

  return {
    nombre,
    sumarPuntos(puntos) {
      puntuacion += puntos;
      return puntuacion;
    },
    perderVida() {
      vidas--;
      return vidas > 0 ? `${vidas} vidas restantes` : "Game Over";
    },
    get estado() {
      return `${nombre}: ${puntuacion} pts, ${vidas} vidas`;
    },
  };
}

const player1 = crearJugador("Ana");
const player2 = crearJugador("Luis");

player1.sumarPuntos(100);
player1.sumarPuntos(50);
player2.sumarPuntos(200);

console.log(player1.estado); // "Ana: 150 pts, 3 vidas"
console.log(player2.estado); // "Luis: 200 pts, 3 vidas"
// Cada closure tiene su propia puntuacion y vidas, totalmente aisladas

Contadores privados con closures

El ejemplo canónico. Sin closures, necesitarías una variable global (mala idea) o una propiedad de objeto (expuesta). Con closures, la variable es verdaderamente privada:

const crearId = () => {
  let id = 0;
  return () => ++id; // el closure captura 'id'
};

const nextId = crearId();
console.log(nextId()); // 1
console.log(nextId()); // 2
console.log(nextId()); // 3
// No hay forma de acceder a 'id' desde fuera. No es una propiedad. No se puede resetear.
// Es verdaderamente privada (y no, no la ves ni con console.log en las DevTools comunes).

El clásico problema del bucle con var (y su solución)

Este es el bug más famoso de JavaScript. Ocurre porque var no crea un nuevo binding en cada iteración, y los closures capturan la variable por referencia, no por valor:

// ❌ PROBLEMA: todas las funciones comparten la misma 'i'
const funciones = [];
for (var i = 0; i < 3; i++) {
  funciones.push(() => console.log(i));
}
funciones[0](); // 3
funciones[1](); // 3
funciones[2](); // 3 — todas ven la i final

// ✅ SOLUCIÓN 1: let crea un nuevo binding por iteración
const funciones2 = [];
for (let j = 0; j < 3; j++) {
  funciones2.push(() => console.log(j));
}
funciones2[0](); // 0
funciones2[1](); // 1
funciones2[2](); // 2

// ✅ SOLUCIÓN 2: closure explícito con IIFE pre-ES6
const funciones3 = [];
for (var k = 0; k < 3; k++) {
  (function (capturada) {
    funciones3.push(() => console.log(capturada));
  })(k); // la IIFE captura el valor actual de k
}
funciones3[0](); // 0
funciones3[1](); // 1
funciones3[2](); // 2

Memoización con closures

Los closures permiten que una función "recuerde" resultados anteriores para evitar repetir cálculos costosos:

function memoizar(fn) {
  const cache = new Map(); // closure: esta variable persiste entre llamadas

  return function (...args) {
    const clave = JSON.stringify(args); // serializar argumentos como clave

    if (cache.has(clave)) {
      console.log(`Cache hit: ${clave}`);
      return cache.get(clave);
    }

    console.log(`Cache miss: ${clave} — calculando...`);
    const resultado = fn.apply(this, args); // ejecutar la función original
    cache.set(clave, resultado);           // guardar para la próxima
    return resultado;
  };
}

// Función costosa (simulada)
function fibonacci(n) {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2);
}

const fibMemo = memoizar(fibonacci);
console.log(fibMemo(40)); // cache miss — lento (primera vez)
console.log(fibMemo(40)); // cache hit  — instantáneo
// La cache del closure guarda el resultado de fib(40) para siempre

Ojo con la memoria: la cache de un closure memoizado crece indefinidamente. En producción necesitas límites (LRU cache, TTL, WeakMap para garbage collection). La memoización básica es didáctica; para producción usa librerías como lodash.memoize o implementa tu propia con límites.

Closures en APIs nativas y patrones comunes

Los closures están por todas partes en las APIs de JavaScript:

// setTimeout/setInterval capturan variables del scope
let mensaje = "Hola";
setTimeout(() => {
  console.log(mensaje); // closure sobre 'mensaje'
}, 1000);

// addEventListener crea un closure sobre el scope del handler
function setup(id) {
  const elemento = document.getElementById(id);
  let clicks = 0; // privado, encapsulado en el closure

  elemento.addEventListener("click", () => {
    clicks++;
    console.log(`Clickeado ${clicks} veces`); // closure sobre 'clicks' y 'elemento'
  });
}

// Promise callbacks también son closures
function fetchConReintentos(url, reintentos = 3) {
  return fetch(url).catch(err => {
    if (reintentos > 0) {
      return fetchConReintentos(url, reintentos - 1); // closure recursivo
    }
    throw err;
  });
}

3 · Ejemplo mínimo

// El closure más simple que demuestra persistencia de estado
function crearSaludo(saludo) {
  return function (nombre) {
    return `${saludo}, ${nombre}`; // 'saludo' viene del closure
  };
}

const saludarEnEspanol = crearSaludo("Hola");
const saludarEnIngles = crearSaludo("Hello");

console.log(saludarEnEspanol("Ana")); // "Hola, Ana"
console.log(saludarEnIngles("John"));  // "Hello, John"

// 'saludo' está en la mochila de cada función retornada
// y persiste aunque crearSaludo ya terminó de ejecutarse

4 · Ejemplo real

Un gestor de estado inspirado en React useState: estado privado con actualizador inmutable:

function crearEstado(valorInicial) {
  let estado = valorInicial;    // closure: encapsula el valor
  let listeners = [];           // closure: encapsula los suscriptores

  return {
    get() {
      return estado;            // acceso de solo lectura al estado actual
    },

    set(nuevoValor) {
      const valorAnterior = estado;
      estado = typeof nuevoValor === "function"
        ? nuevoValor(estado)    // actualizador funcional como en React
        : nuevoValor;

      if (valorAnterior !== estado) {
        // Notificar a suscriptores (pattern Observer)
        listeners.forEach(fn => fn(estado, valorAnterior));
      }
    },

    subscribe(fn) {
      listeners.push(fn);
      // Devolver función para cancelar suscripción
      return () => {
        listeners = listeners.filter(l => l !== fn);
      };
    },

    reset() {
      estado = valorInicial;    // volver al valor inicial
      listeners.forEach(fn => fn(estado));
    },
  };
}

const contadorState = crearEstado(0);

const unsubscribe = contadorState.subscribe((nuevo, anterior) => {
  console.log(`Estado cambió: ${anterior} → ${nuevo}`);
});

contadorState.set(c => c + 1); // "Estado cambió: 0 → 1"
contadorState.set(c => c + 1); // "Estado cambió: 1 → 2"
contadorState.set(100);        // "Estado cambió: 2 → 100"

unsubscribe(); // cancelar suscripción
contadorState.set(200);        // no imprime nada

console.log(contadorState.get()); // 200

Este patrón es el corazón de React, Vue, Svelte y cualquier librería de estado reactiva. El closure mantiene estado y listeners privados; la API expuesta es mínima y controlada.

6 · Errores habituales

1. Closure captura la variable, no el valor

// ❌ MAL: crees que capturas el valor en cada iteración
function crearFunciones() {
  const funcs = [];
  for (var i = 0; i < 3; i++) {
    funcs.push(() => i); // captura la variable 'i', no su valor
  }
  return funcs;
}
const fns = crearFunciones();
console.log(fns[0]()); // 3 — no 0

// ✅ BIEN: let crea un scope por iteración
function crearFunciones2() {
  const funcs = [];
  for (let i = 0; i < 3; i++) {
    funcs.push(() => i); // cada closure captura su propia 'i'
  }
  return funcs;
}

2. Fugas de memoria con closures en el DOM

// ❌ MAL: referencia circular entre DOM y closure
function setup() {
  const elemento = document.getElementById("btn");
  const datosGrandes = new Array(1000000).fill("🐘");

  elemento.addEventListener("click", function handler() {
    console.log(datosGrandes.length); // el closure mantiene vivo datosGrandes
  });
  // Si eliminas 'elemento' del DOM sin remover el listener,
  // datosGrandes (1M de strings) queda en memoria para siempre
}

// ✅ BIEN: limpiar listeners o usar referencias débiles
function setup() {
  const elemento = document.getElementById("btn");
  const datosGrandes = new Array(1000000).fill("🐘");

  function handler() {
    console.log(datosGrandes.length);
  }
  elemento.addEventListener("click", handler);

  // Cleanup
  return () => {
    elemento.removeEventListener("click", handler);
    // ahora datosGrandes puede ser recolectado por el GC
  };
}

3. Compartir closure accidentalmente

// ❌ MAL: todas las instancias comparten el mismo closure
function crearUsuario(nombre) {
  return {
    nombre,
    carrito: [],
    agregar(item) { this.carrito.push(item); }, // usa this, no closure
  };
}
// Esto está bien, pero si tu intención era un closure privado...

// ✅ BIEN: closure privado por instancia
function crearUsuarioPrivado(nombre) {
  const carrito = []; // closure privado, no accesible desde fuera
  return {
    nombre,
    agregar(item) { carrito.push(item); },
    getCarrito() { return [...carrito]; }, // devuelve copia
  };
}

7 · Ejercicio guiado

Enunciado: Crea una función crearTemporizador(limiteMs) que devuelva un objeto con métodos iniciar(), pausar(), reanudar(), y getTiempo() (en segundos). Todo el estado debe ser privado mediante closures.

Solución:

  1. Estructura base con closures:

    function crearTemporizador(limiteMs = 60000) {
  let tiempoTranscurrido = 0; // ms acumulados (closure privado)
  let inicio = null;          // timestamp de cuándo empezó
  let intervalo = null;       // referencia al setInterval
  let corriendo = false;

  2. Método iniciar con closure sobre setInterval:

      function tick() {
    const ahora = Date.now();
    tiempoTranscurrido += ahora - inicio;
    inicio = ahora;

    if (tiempoTranscurrido >= limiteMs) {
      pausar();
      console.log("¡Tiempo cumplido!");
    }
  }

  3. API pública (lo que devolvemos):

      return {
    iniciar() {
      if (corriendo) return "Ya está corriendo";
      corriendo = true;
      inicio = Date.now();
      intervalo = setInterval(tick, 100); // ~10 actualizaciones/segundo
      return "Iniciado";
    },
    pausar() {
      if (!corriendo) return;
      clearInterval(intervalo);
      tiempoTranscurrido += Date.now() - inicio;
      corriendo = false;
    },
    reanudar() {
      if (corriendo) return;
      corriendo = true;
      inicio = Date.now();
      intervalo = setInterval(tick, 100);
    },
    getTiempo() {
      return Math.round(tiempoTranscurrido / 1000); // ms → segundos
    },
  };
}

const timer = crearTemporizador(5000); // 5 segundos límite
timer.iniciar();
// Después de 2 segundos: timer.getTiempo() → 2
// Después de 5 segundos: se auto-pausa

8 · Reto

🎯 Sistema de middleware encadenable

Crea una función crearApp() que implemente un sistema de middleware como Express.js o Koa:

  • La app debe permitir registrar middlewares con app.use(middleware).
  • Cada middleware recibe (contexto, next) donde next() llama al siguiente middleware.
  • Usa closures para que cada middleware tenga su propia referencia a next (el siguiente middleware en la cadena).
  • Implementa app.handle(peticion) que ejecuta todos los middlewares en orden.
  • Añade manejo de errores: si algún middleware lanza, captura el error y pasa al siguiente middleware de error.
  • Todo el estado (cola de middlewares) debe ser privado mediante closure.

9 · Resumen

  • Closure: función que recuerda su scope léxico. La función + sus variables capturadas = closure.
  • Mochila: cada función lleva las variables de su scope. Incluso cuando el scope original desaparece.
  • Patrón módulo: IIFE + closure → API pública + estado privado. Predecesor de los módulos ES.
  • Factory functions: cada llamada crea un closure independiente con sus propias variables privadas.
  • Bug del bucle con var: todas las iteraciones comparten la misma variable. Solución: let o IIFE.
  • Memoización: closure con cache → recordar resultados previos para acelerar funciones puras costosas.
  • Cuidado con la memoria: los closures mantienen vivas las referencias. Si no limpias listeners, fugas.

10 · Preguntas frecuentes

¿Todo callback es un closure?

Técnicamente sí, porque toda función en JavaScript es un closure (tiene acceso a su scope léxico). Pero en la práctica, decimos "esto es un closure" cuando la función accede a variables de un scope que ya no está activo. Un callback que no usa variables externas no demuestra el poder del closure, aunque lo sea.

¿Los closures consumen mucha memoria?

Solo si capturas datos enormes y mantienes la referencia viva. Los motores modernos son inteligentes: si una función interna NO usa una variable del scope padre, el motor puede eliminarla (no la incluye en el closure). Pero si capturas un array de 10MB en un closure y mantienes viva la referencia, sí, ocupará 10MB.

¿Se pueden simular propiedades privadas de clase con closures?

Sí, y de hecho era la forma estándar antes de ES2022 (campos #privados). Con closures creas variables en el constructor que los métodos acceden. La diferencia es que con closures, los métodos se crean por instancia (más memoria), mientras que con clases comparten métodos en el prototipo (menos memoria). Para pocas instancias la diferencia es despreciable.

¿Por qué React usa closures en los hooks?

Porque los closures capturan el valor de las variables en el momento de renderizado. Cuando haces useEffect(() => { console.log(count) }, []), el closure captura el valor de count en ese render específico. Esto permite que React sea predecible: cada render tiene su propia "foto" del estado. El patrón se llama "closures sobre el ciclo de vida del componente".
