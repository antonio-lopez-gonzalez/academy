Inmutabilidad, pureza y composición funcional

Modulo 3 · Scope, closures y PF ⏱ 30 minutos

1 · Introduccion

La programacion funcional (PF) no es un cajon de sintaxis: es una filosofia de diseño que prioriza funciones puras, datos inmutables y composicion sobre herencia y mutacion. JavaScript es un lenguaje multiparadigma, lo que significa que puedes mezclar POO y PF, pero los proyectos que escalan bien tienden a apoyarse en los principios funcionales: son mas faciles de testear, mas faciles de razonar y mas faciles de paralelizar.

En esta leccion aprenderas los tres pilares de la PF aplicada a JavaScript: pureza (sin side effects), inmutabilidad (no modificar datos) y composicion (construir funciones complejas a partir de funciones simples).

¿Por que la PF escala mejor? Una funcion pura es una caja negra predecible: mismos inputs → mismos outputs, sin sorpresas. Puedes testearla sin mocks, ejecutarla en paralelo sin locks, y cachear sus resultados (memoizacion). Cuando tu base de codigo crece de 100 a 100,000 lineas, esa previsibilidad es la diferencia entre dormir tranquilo y arreglar bugs a las 3 AM.

2 · Teoria

Funciones puras: mismo input → mismo output, sin side effects

Una funcion es pura si cumple dos condiciones:

  1. Determinista: para los mismos argumentos, siempre devuelve el mismo resultado.
  2. Sin efectos secundarios: no modifica nada fuera de su scope (no muta argumentos, no escribe en DOM/consola/archivos, no lanza excepciones como parte de su logica normal).
// PURA: determinista, sin side effects
function sumar(a, b) {
  return a + b;
}
sumar(2, 3); // siempre 5

// PURA: crea un nuevo array, no modifica el original
function añadirElemento(arr, elemento) {
  return [...arr, elemento];
}

// IMPURA: modifica el array original (mutacion)
function añadirElementoMalo(arr, elemento) {
  arr.push(elemento); // side effect: modifica el argumento
  return arr;
}

// IMPURA: depende de Math.random() (no determinista)
function generarId() {
  return Math.random().toString(36);
}

// IMPURA: side effect (console.log)
function procesar(datos) {
  console.log("Procesando..."); // side effect
  return datos.map(x => x * 2);
}

¿Un programa sin side effects es inutil? Si. El objetivo no es eliminar los side effects, sino aislarlos en los bordes del sistema. La logica de negocio debe ser pura; la interaccion con el mundo exterior (DOM, red, disco) debe estar encapsulada y separada.

Inmutabilidad: nunca modificar, siempre crear nuevo

La inmutabilidad significa que una vez creado un valor, no lo cambias. Si necesitas "modificarlo", creas una copia con los cambios aplicados. JavaScript no es inmutable por defecto, pero tienes herramientas:

// Arrays inmutables
const original = [1, 2, 3];

const conElemento = [...original, 4];      // añadir
const sinPrimero = original.slice(1);       // quitar
const actualizado = original.map((n, i) => i === 1 ? 99 : n); // modificar
const ordenado = original.toSorted();       // ordenar (ES2023)
const invertido = original.toReversed();    // invertir (ES2023)

// Objetos inmutables
const usuario = { nombre: "Ana", rol: "editor" };

const actualizado2 = { ...usuario, rol: "admin" };  // spread
const sinRol = (({ rol, ...resto }) => resto)(usuario); // destructuring + rest

// Object.freeze — inmutabilidad superficial
const CONFIG = Object.freeze({
  api: "https://api.example.com",
  timeout: 5000,
});
// CONFIG.timeout = 3000; // Error en strict mode, silencioso sin strict

// Para inmutabilidad profunda: structuredClone o librerias como Immer
const profundo = { a: { b: { c: 1 } } };
const copiaProfunda = structuredClone(profundo);
copiaProfunda.a.b.c = 2;
console.log(profundo.a.b.c); // 1 — intacto

Analogia: la inmutabilidad es como un cuaderno de laboratorio. No tachas los resultados anteriores: escribes una nueva linea con la nueva medicion. Asi siempre puedes volver atras y saber exactamente que paso en cada paso. La mutacion es como borrar y sobrescribir: pierdes el historial y nadie puede verificar tus resultados.

Composicion de funciones

La composicion es el superpoder de la PF: construir funciones complejas combinando funciones simples. En lugar de una funcion de 50 lineas, tienes 5 funciones de 10 lineas que se componen:

// Composicion directa: f(g(x))
const quitarEspacios = str => str.trim();
const aMinusculas = str => str.toLowerCase();
const slugificar = str =>
  quitarEspacios(aMinusculas(str)).replace(/\s+/g, "-");

console.log(slugificar("  Hola MUNDO JS ")); // "hola-mundo-js"

// Funcion compose generica (de derecha a izquierda)
const compose = (...fns) => valorInicial =>
  fns.reduceRight((valor, fn) => fn(valor), valorInicial);

// Funcion pipe (de izquierda a derecha, mas natural de leer)
const pipe = (...fns) => valorInicial =>
  fns.reduce((valor, fn) => fn(valor), valorInicial);

const slug = pipe(
  str => str.trim(),
  str => str.toLowerCase(),
  str => str.replace(/\s+/g, "-"),
);

console.log(slug("  Hola MUNDO JS ")); // "hola-mundo-js"

Higher-Order Functions (HOF)

Una HOF es una funcion que recibe funciones como argumento y/o devuelve una funcion. map, filter y reduce son HOFs. Crear tus propias HOFs es la esencia de la PF:

// HOF que recibe funcion y devuelve funcion (decorator pattern)
function conLog(fn) {
  return function (...args) {
    console.log(`Llamando con args: ${args}`);
    const resultado = fn(...args);
    console.log(`Resultado: ${resultado}`);
    return resultado;
  };
}

const sumaConLog = conLog((a, b) => a + b);
sumaConLog(3, 4);
// Llamando con args: 3,4
// Resultado: 7

Currying (aplicacion parcial)

Transformar una funcion que recibe N argumentos en N funciones que reciben 1 argumento cada una. Permite aplicacion parcial y crear funciones especializadas:

// Con currying manual
const formatearCurried = prefijo => separador => texto =>
  `${prefijo}${separador} ${texto}`;

// Aplicacion parcial: crear versiones especializadas
const logError = formatearCurried("[ERROR]")("→");
const logInfo = formatearCurried("[INFO]")("→");

console.log(logError("Archivo no encontrado")); // "[ERROR]→ Archivo no encontrado"
console.log(logInfo("Servidor iniciado"));       // "[INFO]→ Servidor iniciado"

// Curry generico (para cualquier funcion)
const curry = (fn) => {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn.apply(this, args);
    }
    return (...next) => curried(...args, ...next);
  };
};

const sumar3 = (a, b, c) => a + b + c;
const sumarCurried = curry(sumar3);
console.log(sumarCurried(1)(2)(3)); // 6
console.log(sumarCurried(1, 2)(3)); // 6

Point-Free Style

Programar "sin puntos" significa escribir funciones sin mencionar explicitamente los argumentos sobre los que operan. Se consigue componiendo funciones:

// Con puntos (pointful): nombras el argumento
const procesar = arr => arr.filter(x => x > 0).map(x => x * 2);

// Point-free: extraes las funciones predicado/transformacion
const esPositivo = n => n > 0;
const doblar = n => n * 2;
const procesar2 = arr => arr.filter(esPositivo).map(doblar);

// Nota: JavaScript no es un lenguaje point-free puro (como Haskell).
// El point-free excesivo se vuelve ilegible; busca el equilibrio.

3 · Ejemplo minimo

// De imperativo a funcional en 3 pasos

// Imperativo (mutacion, side effects implicitos)
const precios = [100, 200, 300];
let total = 0;
for (let i = 0; i < precios.length; i++) {
  if (precios[i] > 150) {
    total += precios[i] * 1.21;
  }
}
console.log(total); // 605

// Funcional puro: sin mutacion, componible y declarativo
const aplicarIVA = arr => arr.map(p => p * 1.21);
const filtrarCaros = arr => arr.filter(p => p > 150);
const sumarTotal = arr => arr.reduce((a, b) => a + b, 0);

const totalFuncional = sumarTotal(aplicarIVA(filtrarCaros(precios)));
// equivalentemente con pipe:
// pipe(filtrarCaros, aplicarIVA, sumarTotal)(precios) → 544.5

console.log(totalFuncional); // 544.5 ≈ 200*1.21 + 300*1.21

4 · Ejemplo real

Tuberia de procesamiento de datos de usuarios desde una API:

const pipe = (...fns) => val => fns.reduce((v, fn) => fn(v), val);

const usuarios = [
  { nombre: "ana", email: "ana@mail.com", activo: true, edad: 25 },
  { nombre: "LUIS", email: "luis@mail.com", activo: false, edad: 17 },
  { nombre: "  eva  ", email: "eva@mail.com", activo: true, edad: 30 },
];

// Cada paso es una funcion pura, testable e independiente
const soloActivos = arr => arr.filter(u => u.activo);
const soloAdultos = arr => arr.filter(u => u.edad >= 18);
const normalizarNombre = arr =>
  arr.map(u => ({ ...u, nombre: u.nombre.trim().toLowerCase() }));
const capitalizarNombre = arr =>
  arr.map(u => ({
    ...u,
    nombre: u.nombre.charAt(0).toUpperCase() + u.nombre.slice(1),
  }));
const soloDatosPublicos = arr =>
  arr.map(({ nombre, email }) => ({ nombre, email }));

const procesarUsuarios = pipe(
  soloActivos,
  soloAdultos,
  normalizarNombre,
  capitalizarNombre,
  soloDatosPublicos,
);

const resultado = procesarUsuarios(usuarios);
console.log(resultado);
// [
//   { nombre: "Ana", email: "ana@mail.com" },
//   { nombre: "Eva", email: "eva@mail.com" }
// ]

Cada funcion hace una cosa. Puedes testear normalizarNombre sola, o soloAdultos sola. Puedes reordenar los pasos del pipeline sin romper nada. Y si manana necesitas añadir un paso extra (ej. ordenar alfabeticamente), simplemente lo añades a pipe. Esto es software mantenible.

6 · Errores habituales

1. Mutar el array original dentro de map

// ❌ MAL: modificar el objeto original es un side effect
const usuarios = [{ nombre: "Ana" }, { nombre: "Luis" }];
usuarios.map(u => {
  u.nombre = u.nombre.toUpperCase(); // muta el objeto original
  return u;
});
console.log(usuarios[0].nombre); // "ANA" — ¡el original cambio!

// ✅ BIEN: crear copia, nunca mutar
const usuarios2 = [{ nombre: "Ana" }, { nombre: "Luis" }];
const normalizados = usuarios2.map(u => ({
  ...u,
  nombre: u.nombre.toUpperCase(),
}));
console.log(usuarios2[0].nombre); // "Ana" — intacto

2. Efectos secundarios escondidos en funciones aparentemente puras

// ❌ MAL: parece pura, pero modifica el DOM
function calcularTotal(items) {
  document.getElementById("total").textContent = "..."; // side effect
  return items.reduce((a, b) => a + b, 0);
}

// ✅ BIEN: separar calculo de presentacion
function calcularTotal(items) {
  return items.reduce((a, b) => a + b, 0); // pura
}
function mostrarTotal(total) {
  document.getElementById("total").textContent = total; // side effect aislado
}

3. Usar sort mutando en un pipeline funcional

// ❌ MAL: sort muta el array que viene de filter
const resultado = datos
  .filter(x => x.activo)
  .sort((a, b) => a.nombre.localeCompare(b.nombre)) // muta el array de filter
  .map(x => x.nombre);

// ✅ BIEN: usar toSorted o copiar antes de sort
const resultado2 = datos
  .filter(x => x.activo)
  .toSorted((a, b) => a.nombre.localeCompare(b.nombre)) // inmutable (ES2023)
  .map(x => x.nombre);

7 · Ejercicio guiado

Enunciado: Convierte el siguiente codigo imperativo en una tuberia funcional pura usando pipe y funciones pequenas:

const pedidos = [
  { id: 1, total: 50, pagado: true, enviado: false },
  { id: 2, total: 150, pagado: true, enviado: true },
  { id: 3, total: 30, pagado: false, enviado: false },
  { id: 4, total: 200, pagado: true, enviado: false },
];

// Version imperativa a convertir:
let pendientesEnvio = [];
for (let i = 0; i < pedidos.length; i++) {
  if (pedidos[i].pagado && !pedidos[i].enviado) {
    pendientesEnvio.push(pedidos[i]);
  }
}
let totalPendiente = 0;
for (let i = 0; i < pendientesEnvio.length; i++) {
  totalPendiente += pendientesEnvio[i].total;
}
console.log(totalPendiente); // 250

Solucion funcional:

  1. Extraer funcion predicado: const pendienteEnvio = p => p.pagado && !p.enviado;
  2. Usar filter + map + reduce: 
    const pipe = (...fns) => val => fns.reduce((v, fn) => fn(v), val);

const soloPendientesEnvio = arr => arr.filter(p => p.pagado && !p.enviado);
const extraerTotales = arr => arr.map(p => p.total);
const sumar = arr => arr.reduce((a, b) => a + b, 0);

const calcularTotalPendiente = pipe(
  soloPendientesEnvio,
  extraerTotales,
  sumar,
);

console.log(calcularTotalPendiente(pedidos)); // 250

🎯 Procesador funcional de transacciones

Crea un sistema de procesamiento de transacciones usando exclusivamente funciones puras y composicion:

  • Cada transaccion es { tipo: "ingreso"|"gasto", monto: number, categoria: string, fecha: string }.
  • Implementa una funcion de currying para filtrar por categoria: filtrarPorCategoria(categoria)(transacciones).

9 · Resumen

  • Funcion pura: determinista (mismos inputs → mismo output) + sin side effects.
  • Inmutabilidad: nunca modificar datos existentes. Crear copias con spread, toSorted, structuredClone.
  • Composicion: pipe(f, g, h)(x) = h(g(f(x))). Construir complejidad combinando simplicidad.
  • HOF: funciones que reciben y/o devuelven funciones. Base de decorators, middleware, callbacks.
  • Currying: transformar f(a,b,c) en f(a)(b)(c). Permite aplicacion parcial y especializacion.
  • Point-free: escribir funciones sin nombrar argumentos, componiendo otras funciones.
  • PF escala: testabilidad (sin mocks), previsibilidad (sin mutacion), paralelismo (sin race conditions).

10 · Preguntas frecuentes

¿No es la inmutabilidad ineficiente? ¿Crear copias todo el rato no gasta mas memoria?

En arrays/objetos pequenos, el coste es despreciable. En estructuras grandes, los motores modernos optimizan con persistent data structures (comparten partes no modificadas en lugar de copiarlo todo). Librerias como Immutable.js o Immer usan tecnicas de structural sharing. Y el beneficio en correccion y mantenibilidad casi siempre supera el micro-coste de rendimiento. Si realmente necesitas mutar por rendimiento (ej. renderizado WebGL a 60fps), hazlo, pero aisla esa mutacion.

¿Pipe vs compose: cual usar?

pipe(f, g, h)(x) = h(g(f(x))) se lee de izquierda a derecha: primero f, luego g, luego h. compose(f, g, h)(x) = f(g(h(x))) se lee de derecha a izquierda (como en matematicas). La mayoria de desarrolladores prefiere pipe porque se lee en orden natural de ejecucion. Usa la que tu equipo entienda mejor.

¿JavaScript es un lenguaje funcional?

No puramente. JavaScript es multiparadigma: soporta POO (prototipos, clases), programacion imperativa y programacion funcional. A diferencia de Haskell o Elm (funcionales puros), JS no impone inmutabilidad ni pureza. Pero puedes escribir en estilo funcional y aprovechar sus ventajas. De hecho, la tendencia del ecosistema (React, Redux, RxJS, Node.js streams) es cada vez mas funcional.

¿Merece la pena aprender currying si casi nunca lo veo en codigo real?

El currying explicito (curry(fn)) es raro en JavaScript. Pero la aplicacion parcial con arrow functions (const fn = a => b => a + b) esta en todas partes: en Redux (connect(mapState, mapDispatch)(Component)), en Express (app.use(middleware(req, res, next))), en React (useCallback(fn, [deps])). Currying es el fundamento teorico de cualquier funcion que devuelve otra funcion.
