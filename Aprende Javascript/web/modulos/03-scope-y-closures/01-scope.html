Scope global, de función y de bloque

Módulo 3 · Scope, closures y PF ⏱ 30 minutos

1 · Introducción

El scope (ámbito o alcance) determina dónde una variable es visible y accesible. Es el mecanismo fundamental que evita que tu código sea una sopa de variables globales colisionando entre sí. Entender el scope no es opcional: es la diferencia entre un código que funciona por casualidad y uno que lo hace por diseño. Sin un modelo mental claro del scope, depurar errores como ReferenceError o variables que misteriosamente valen undefined se convierte en un juego de adivinanzas.

JavaScript tiene tres tipos de scope — global, de función y de bloque — y dos familias de declaración — var (que ignora el scope de bloque) y let/const (que lo respetan). Esta dualidad es la raíz del 90% de los bugs de scope.

2 · Teoría

Scope global

El scope más externo. Las variables declaradas aquí son accesibles desde cualquier parte del código, en cualquier archivo (si no usas módulos). En navegadores, el objeto global es window; en Node.js es global; en ambos funciona globalThis (ES2020).

var nombre = "Ana";  // ¡CUIDADO! var en el top-level crea propiedad en window
console.log(window.nombre); // "Ana"

let ciudad = "Madrid"; // let/const no se añaden a window
console.log(window.ciudad); // undefined

El scope global es tóxico en proyectos reales. Cualquier script o dependencia puede leer y modificar tus variables. Por eso los módulos ES existen: cada archivo tiene su propio scope y solo exportas lo que quieres compartir.

Scope de función

Cada función crea su propio scope. Las variables declaradas dentro (con var, let o const) no son visibles desde fuera. Este es el scope original de JavaScript desde su creación en 1995:

function exterior() {
  const mensaje = "dentro"; // solo visible aquí

  function interior() {
    console.log(mensaje); // "dentro" — acceso al scope padre (closure)
  }

  interior();
}

exterior();
console.log(typeof mensaje); // "undefined" — no existe fuera

Scope de bloque (ES6, let/const)

Un bloque es cualquier cosa entre llaves {}: un if, un for, una función, o incluso un bloque desnudo. let y const respetan este scope; var lo ignora:

{
  let bloqueLet = "visible solo aquí";
  var bloqueVar = "visible fuera";
  const bloqueConst = "también solo aquí";
}

console.log(typeof bloqueLet);   // "undefined" — let respeta el bloque
console.log(bloqueVar);           // "visible fuera" — var ignora el bloque
console.log(typeof bloqueConst);  // "undefined"

Árbol de scopes anidados

Los scopes forman un árbol jerárquico. JavaScript resuelve variables mirando hacia arriba en el árbol hasta encontrar la declaración o llegar al scope global. Si no la encuentra, lanza ReferenceError:

// Diagrama ASCII de scopes anidados:
//
//  ┌─────────────────────────────────┐
//  │  SCOPE GLOBAL                   │
//  │  let app = "MiApp";             │
//  │                                 │
//  │  ┌───────────────────────────┐  │
//  │  │  función init()           │  │
//  │  │  let config = {};         │  │
//  │  │                           │  │
//  │  │  ┌─────────────────────┐  │  │
//  │  │  │  if (cond) {        │  │  │
//  │  │  │    let temp = 42;   │  │  │
//  │  │  │  }                  │  │  │
//  │  │  └─────────────────────┘  │  │
//  │  └───────────────────────────┘  │
//  └─────────────────────────────────┘

let app = "MiApp";

function init() {
  let config = { port: 3000 };

  if (true) {
    let temp = "temporal";
    console.log(app);     // "MiApp" — busca arriba: init → global
    console.log(config);  // { port: 3000 } — busca arriba: init
    console.log(temp);    // "temporal" — está en este scope
  }

  console.log(typeof temp); // "undefined" — el bloque cerró, temp murió
}

init();

Variable shadowing

Cuando declaras una variable con el mismo nombre en un scope interior, "sombrea" la del scope exterior. El motor usa la declaración más cercana:

let x = "global";

function demo() {
  let x = "local"; // shadowing: oculta la x global dentro de esta función
  console.log(x);  // "local"

  if (true) {
    let x = "bloque"; // shadowing de nuevo
    console.log(x);   // "bloque"
  }

  console.log(x); // "local" — el shadow del bloque ya no existe
}

demo();
console.log(x); // "global" — nunca fue modificada

var ignora el scope de bloque

Este es el talón de Aquiles histórico de JavaScript. var solo respeta el scope de función y el global. Dentro de un if o for, la variable "escapa" al scope de la función contenedora:

function problemaVar() {
  if (true) {
    var x = 10; // declarado en el bloque, pero...
  }
  console.log(x); // 10 — ¡var ignora el bloque y se eleva al scope de la función!
}

function noProblemaLet() {
  if (true) {
    let x = 10;
  }
  console.log(typeof x); // "undefined" — let respeta el bloque
}

// El caso más famoso: bucles con var
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100); // 3, 3, 3 — ¡comparten la misma i!
}
// Con let, cada iteración crea un binding nuevo
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 100); // 0, 1, 2 — cada callback captura su j
}

'use strict' y cómo afecta al scope

En modo estricto, asignar a una variable no declarada lanza ReferenceError en lugar de crear una variable global implícita. El scope no cambia, pero los errores de fuga de variables se detectan:

"use strict";
function demo() {
  x = 42; // ReferenceError: x is not defined — sin strict, crearía window.x = 42
}

// Los módulos ES y las clases son strict por defecto

3 · Ejemplo mínimo

// Tres variables con el mismo nombre en tres scopes distintos
const color = "rojo"; // scope global

function pintar() {
  const color = "azul"; // scope de función — shadowing del global

  if (true) {
    const color = "verde"; // scope de bloque — shadowing del de función
    console.log(color);    // "verde" — el más cercano
  }

  console.log(color); // "azul" — el bloque ya cerró
}

pintar();
console.log(color); // "rojo" — el global nunca cambió

Ejecuta esto en la consola. Cada console.log(color) accede a una variable distinta con el mismo nombre, demostrando visualmente cómo el motor resuelve los scopes.

4 · Ejemplo real

Sistema de carga de módulos con aislamiento de scope:

// Simulamos el comportamiento de los módulos ES usando scopes de bloque
const Registry = (() => {
  // Este bloque IIFE crea un scope privado para el registro
  const modulos = new Map(); // solo accesible desde dentro

  return {
    registrar(nombre, fabrica) {
      // Cada módulo recibe su propio scope aislado
      const scope = {
        exports: {},
        console, // inyectar dependencias
      };

      // La fábrica se ejecuta en un scope controlado
      fabrica(scope);
      modulos.set(nombre, scope.exports);
    },

    obtener(nombre) {
      if (!modulos.has(nombre)) {
        throw new Error(`Módulo "${nombre}" no encontrado`);
      }
      return modulos.get(nombre);
    },
  };
})();

// Cada "módulo" tiene su propio scope, sin contaminar a los demás
Registry.registrar("logger", (scope) => {
  let nivel = "info"; // privado, solo visible aquí
  scope.exports = {
    log(msg) { scope.console.log(`[${nivel}] ${msg}`); },
    setNivel(n) { nivel = n; },
  };
});

Registry.registrar("app", (scope) => {
  const logger = Registry.obtener("logger"); // inyección de dependencia
  scope.exports = {
    iniciar() { logger.log("App iniciada"); },
  };
});

const app = Registry.obtener("app");
app.iniciar(); // [info] App iniciada

Este patrón es esencialmente cómo funcionan los módulos ES, CommonJS y los contenedores de inyección de dependencias. El scope asegura que nivel en el módulo logger y logger en el módulo app no colisionen.

6 · Errores habituales

1. Crear variables globales sin querer

// ❌ MAL: olvidar let/const crea una variable global (sin strict mode)
function procesar() {
  datos = [1, 2, 3]; // window.datos = [1, 2, 3] — ¡variable global!
}

// ✅ BIEN
function procesar() {
  const datos = [1, 2, 3]; // scope local, no contamina
}

2. Pensar que var respeta el scope de bloque

// ❌ MAL: var en un if no está aislado
function calcular() {
  if (true) {
    var resultado = 42;
  }
  return resultado; // 42 — accesible fuera del if
}

// ✅ BIEN
function calcular() {
  let resultado;
  if (true) {
    resultado = 42;
  }
  return resultado;
}

3. Shadowing accidental con el mismo nombre

// ❌ MAL: shadowing que confunde
let user = { name: "Admin" };
function login(user) { // el parámetro sombrea la variable exterior
  user = { name: "Guest" }; // solo modifica el parámetro, no la exterior
}
login(user);
console.log(user.name); // "Admin" — esperabas "Guest"

// ✅ BIEN: nombres distintos, o modificar la propiedad sin shadowing
let user2 = { name: "Admin" };
function login() {
  user2 = { name: "Guest" }; // modifica la variable del scope exterior
}
login();
console.log(user2.name); // "Guest"

7 · Ejercicio guiado

Enunciado: Crea una función contadorConScope() que demuestre los tres tipos de scope con un contador global, uno de función, y uno de bloque.

Solución:

  1. Scope global:

    let contadorGlobal = 0; // visible en todo el script

function contadorConScope() {
  // Scope de función
  let contadorFuncion = 0;

  console.log(`Global: ${++contadorGlobal}`); // accede al global

  for (let i = 0; i < 3; i++) {
    // Scope de bloque (cada iteración tiene su propio i)
    let contadorBloque = 0;
    contadorBloque++;
    contadorFuncion++;

    console.log(`  Iteración ${i}: bloque=${contadorBloque}, funcion=${contadorFuncion}`);
    // contadorBloque siempre será 1 (se reinicia en cada iteración)
    // contadorFuncion acumula (sobrevive entre iteraciones)
  }

  // console.log(contadorBloque); // ReferenceError — fuera del bloque
  console.log(`Función terminada. Funcion acumuló: ${contadorFuncion}`);
}

contadorConScope(); // Global: 1, Funcion: 3
contadorConScope(); // Global: 2, Funcion: 3 (empieza de nuevo)

Observa cómo contadorGlobal persiste entre llamadas (scope global), contadorFuncion se reinicia en cada llamada (scope de función), y contadorBloque se recrea en cada iteración (scope de bloque).

8 · Reto

🎯 Sandbox de ejecución segura

Crea una función ejecutarEnSandbox(codigo) que ejecute código JavaScript arbitrario en un entorno controlado sin acceso al scope global.

  • El código no debe poder acceder a window, document ni variables globales.
  • Solo debe tener acceso a un conjunto limitado de APIs que tú definas (console.log, Math, JSON).
  • Usa una combinación de scope de bloque, new Function() y with (o Proxy) para crear el aislamiento.
  • La función debe devolver el resultado o capturar errores sin que rompan el sandbox.
  • Pista: new Function("a","b","return a + b") solo tiene acceso al scope global, no al local. Piensa en cómo restringir también el global.

9 · Resumen

  • Scope global: accesible desde cualquier parte. Evítalo con módulos ES.
  • Scope de función: creado por cada función. var, let y const lo respetan.
  • Scope de bloque: creado por {}. Solo let y const lo respetan; var lo ignora.
  • Árbol de scopes: el motor busca variables hacia arriba hasta el global o lanza ReferenceError.
  • Shadowing: declarar el mismo nombre en scope interior oculta el exterior.
  • var ignora el bloque: sale al scope de función más cercano. Nunca lo uses en código nuevo.
  • use strict: evita que una asignación sin declaración cree globales. Los módulos ES ya son strict.

10 · Preguntas frecuentes

¿Por qué existe var si es tan problemático?

Por razones históricas. JavaScript se diseñó en 10 días en 1995 y var era la única forma de declarar variables. El scope de bloque no existía. Cuando ES6 introdujo let/const en 2015, mantuvieron var por retrocompatibilidad (romper la web no era una opción). Hoy var solo debería aparecer en código legacy.

¿Un bloque desnudo { } realmente crea un scope?

Sí. Es perfectamente válido y es una técnica útil para limitar el alcance de variables temporales sin crear una función. Por ejemplo: { const temp = calcularAlgoPesado(); usar(temp); } — temp muere al cerrar el bloque, liberando memoria.

¿Cuál es la diferencia entre scope léxico y scope dinámico?

JavaScript usa scope léxico (estático): la visibilidad de una variable se determina por dónde está escrita en el código fuente, no por dónde se ejecuta. El scope dinámico (que usa this en cierto modo en funciones tradicionales) depende de quién llama a la función. El scope léxico es predecible; el dinámico es flexible pero propenso a bugs.

¿let y const también tienen hoisting?

Sí, pero entran en la Temporal Dead Zone (TDZ). La declaración se eleva, pero no puedes acceder a la variable entre el inicio del scope y la línea donde se declara. var se inicializa a undefined; let/const lanzan ReferenceError si intentas usarlos antes de la declaración. Lo verás en detalle en la lección de hoisting y TDZ.
