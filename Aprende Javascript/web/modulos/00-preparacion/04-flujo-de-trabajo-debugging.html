Flujo de trabajo, debugging y DevTools

Módulo 0 · Preparación ⏱ 25 minutos

1 · Introducción

Escribir código es solo la mitad del trabajo. La otra mitad — y la que diferencia a un junior de un senior — es saber depurar. Un desarrollador profesional no escribe código perfecto a la primera; escribe código, lo prueba, encuentra errores y los corrige. La velocidad a la que haces ese ciclo determina tu productividad.

En esta lección dominarás las DevTools del navegador (tu herramienta más poderosa), aprenderás a leer un stack trace, usarás el debugger de Node.js y establecerás un flujo de trabajo profesional: escribir → ejecutar → depurar → iterar.

¿Por qué existe esta lección? Porque demasiados desarrolladores pasan horas poniendo console.log por todas partes cuando un breakpoint bien puesto les daría la respuesta en segundos. Las DevTools son un IDE dentro del navegador; conocerlas a fondo multiplica tu eficacia.

2 · Teoría

El ciclo de desarrollo profesional

ESCRIBIR → EJECUTAR → DEPURAR → ITERAR
   ↑                                  |
   └──────────────────────────────────┘

Este ciclo dura segundos en un entorno bien configurado. Con Vite + HMR, el ciclo se reduce a «guardar archivo → ver resultado». Ese feedback instantáneo es el secreto de la productividad en desarrollo web moderno.

El debugging no es un castigo ni una señal de que eres mal programador. Es una herramienta de investigación. Como un médico que usa un escáner para ver dentro del cuerpo, tú usas las DevTools para ver dentro de tu programa en ejecución.

DevTools: las pestañas esenciales

Console — Tu laboratorio de experimentación

La consola no solo muestra logs: es un REPL completo. Puedes declarar variables, llamar funciones, inspeccionar objetos y manipular el DOM en tiempo real. Todo el código que escribes en la consola se ejecuta en el contexto de la página actual.

Sources — El depurador visual

La pestaña Sources es donde haces debugging de verdad. Sus herramientas clave:

  • Breakpoints: marcas una línea de código y la ejecución se pausa justo antes de ejecutarla. Desde ahí puedes inspeccionar variables, el call stack y ejecutar código paso a paso.
  • Step Over (F10): ejecuta la línea actual y pasa a la siguiente dentro de la misma función.
  • Step Into (F11): si la línea actual llama a una función, entra dentro de ella.
  • Step Out (Shift+F11): ejecuta el resto de la función actual y vuelve a quien la llamó.
  • Watch: añade expresiones para monitorizar su valor en tiempo real durante la ejecución (ej: i > 5, user.name).
  • Call Stack: muestra la pila de llamadas: qué función llamó a qué función. Esencial para entender cómo llegaste hasta el punto actual.
  • Scope: muestra todas las variables accesibles en el punto de ejecución actual (local, closure, global).

Network — El inspector de peticiones

Cada petición HTTP que hace tu página (archivos JS, CSS, imágenes, API calls) aparece aquí. Puedes ver:

  • Estado HTTP (200, 404, 500...).
  • Headers de petición y respuesta.
  • Payload (datos enviados) y Response (datos recibidos).
  • Tiempo de cada petición (útil para detectar cuellos de botella).

Application — El almacén del navegador

Aquí inspeccionas y modificas:

  • Local Storage / Session Storage: datos persistentes y de sesión.
  • Cookies: pequeñas piezas de datos enviadas en cada petición.
  • IndexedDB: base de datos completa dentro del navegador.

La sentencia debugger

Puedes poner un breakpoint desde tu código con la palabra clave debugger;:

function calcularPrecio(base, descuento) {
  const precioConDescuento = base * (1 - descuento);
  debugger; // ← La ejecución se pausa aquí (si las DevTools están abiertas)
  return precioConDescuento;
}

Cuando la ejecución llega a debugger, se pausa automáticamente (si las DevTools están abiertas). Es como un breakpoint portable que viaja con tu código.

console.time y console.timeEnd

Miden el tiempo entre dos puntos del código con precisión de microsegundos:

console.time('ordenar-array');
const ordenado = [5, 3, 8, 1, 2, 9, 4, 7, 6].sort((a, b) => a - b);
console.timeEnd('ordenar-array'); // ordenar-array: 0.045ms

Cómo leer un stack trace

Cuando tu código falla, el navegador imprime un stack trace. Es una de las habilidades más infravaloradas:

function nivel3() {
  throw new Error('Algo salió mal'); // ← El error se lanza aquí
}
function nivel2() { nivel3(); }
function nivel1() { nivel2(); }
nivel1();

El stack trace mostrará algo como:

Uncaught Error: Algo salió mal
    at nivel3 (app.js:2:9)     ← el error se originó aquí
    at nivel2 (app.js:4:17)    ← nivel2 llamó a nivel3
    at nivel1 (app.js:5:17)    ← nivel1 llamó a nivel2
    at app.js:7:1              ← código global llamó a nivel1

Regla de oro: lee el stack trace de abajo hacia arriba. La última línea te dice qué disparó todo; la primera te dice exactamente dónde falló.

Debugging en Node.js

Node.js tiene un debugger integrado compatible con las DevTools de Chrome:

# Opción 1: Usar las DevTools de Chrome
node --inspect archivo.js
# Abre chrome://inspect en Chrome y conecta el debugger

# Opción 2: Pausar al inicio (útil para la primera línea)
node --inspect-brk archivo.js

# Opción 3: Debugger integrado de VSCode
# Crea un archivo .vscode/launch.json y usa "Node.js" como tipo

Con node --inspect, puedes abrir Chrome, ir a chrome://inspect, y verás tu script de Node listado. Haz clic en «inspect» y tendrás las mismas DevTools (Sources, Console, Breakpoints) que usarías para código del navegador, pero depurando tu script de Node.

3 · Ejemplo mínimo

El debugging más básico: poner un breakpoint y ejecutar paso a paso.

// Abre DevTools (F12) → Sources → selecciona este archivo
// Haz clic en el número de línea para poner un breakpoint en línea 4

function saludar(nombre) {
  const saludo = 'Hola, ' + nombre;  // ← Pon un breakpoint aquí (línea 4)
  const mayusculas = saludo.toUpperCase();
  return mayusculas;
}

const resultado = saludar('Ana');
console.log(resultado);
  1. Con el breakpoint puesto, recarga la página.
  2. La ejecución se pausa en línea 4.
  3. En el panel Scope, verás que nombre vale 'Ana' y saludo todavía no existe (aún no se ha ejecutado esa línea).
  4. Pulsa F10 (Step Over). Ahora saludo aparece en Scope con valor 'Hola, Ana'.
  5. Sigue pulsando F10 para ver cómo cambian las variables línea a línea.

4 · Ejemplo real

Escenario profesional: tienes una función que calcula totales de un carrito de compras, y los números no cuadran. En vez de poner 50 console.log, usas debugging estructurado:

// carrito.js
const CART = [
  { name: 'Libro JS', price: 29.99, quantity: 2 },
  { name: 'Curso Online', price: 49.99, quantity: 1 },
  { name: 'Taza', price: 12.50, quantity: 4 },
];

function calcularTotal(cart) {
  console.time('calculo-total'); // Mide el rendimiento

  let subtotal = 0;
  for (const item of cart) {
    const itemTotal = item.price * item.quantity;
    debugger; // Pausa en cada iteración para ver itemTotal
    subtotal += itemTotal;
  }

  const impuestos = subtotal * 0.21; // IVA 21%
  const total = subtotal + impuestos;

  console.group('Resumen del carrito');
  console.log('Subtotal:', subtotal.toFixed(2));
  console.log('Impuestos:', impuestos.toFixed(2));
  console.log('Total:', total.toFixed(2));
  console.groupEnd();

  console.timeEnd('calculo-total');
  return { subtotal, impuestos, total };
}

calcularTotal(CART);

Con este enfoque tienes: medición de rendimiento (console.time), inspección de cada iteración (debugger), salida estructurada (console.group), y puedes modificar variables en vivo desde la consola mientras el código está pausado para probar escenarios alternativos.

6 · Errores habituales

Usar solo console.log para depurar

// ❌ El anti-patrón "console.log debugging"
function procesarDatos(datos) {
  console.log('datos:', datos);         // 1
  const filtrados = datos.filter(d => d.active);
  console.log('filtrados:', filtrados); // 2
  const mapeados = filtrados.map(d => d.value * 2);
  console.log('mapeados:', mapeados);   // 3
  return mapeados;
}
// Esto es frágil: tienes que adivinar DÓNDE poner los logs,
// y cuando terminas tienes que borrarlos todos.

// ✅ Usa breakpoints en Sources
// Con un breakpoint ves TODAS las variables en Scope sin escribir nada.

No saber leer el stack trace

// ❌ Ver este error y no entender de dónde viene:
// TypeError: Cannot read properties of undefined (reading 'name')

// ✅ El stack trace te da el archivo y línea exacta:
//     at mostrarUsuario (user.js:15:25)
//     at cargarPagina (app.js:8:3)
// Ve a user.js línea 15 y encontrarás algo como:
// console.log(user.profile.name)  // ← profile es undefined

Depurar con las DevTools cerradas

// ❌ Tener un 'debugger;' en el código y no abrir las DevTools
// La sentencia debugger se ignora si las DevTools están cerradas.

// ✅ Siempre abre DevTools (F12) antes de ejecutar código con debugger;
// o usa node --inspect-brk para que Node espere al debugger.

No usar console.table para arrays de objetos

// ❌ Esto es ilegible con arrays grandes:
console.log(usuarios);
// (20) [{…}, {…}, {…}, ...]  ← tienes que expandir uno por uno

// ✅ Mucho más claro:
console.table(usuarios);
// ┌─────────┬───────────┬────────┬───────┐
// │ (index) │  nombre   │  edad  │ email │
// ├─────────┼───────────┼────────┼───────┤
// │    0    │  'Ana'    │   28   │  ...  │
// │    1    │  'Carlos' │   34   │  ...  │
// └─────────┴───────────┴────────┴───────┘

7 · Ejercicio guiado

Objetivo: Depurar una función con errores usando breakpoints y el depurador de Sources.

  1. Paso 1 — Código con bug: Crea un proyecto Vite y pon esto en src/main.js: 
    // Esta función tiene un bug: devuelve undefined en vez del resultado
function calcularEstadisticas(numeros) {
  let suma = 0;
  let maximo = numeros[0];

  for (let i = 0; i <= numeros.length; i++) { // ← Bug: <= en vez de <
    suma += numeros[i];
    if (numeros[i] > maximo) {
      maximo = numeros[i];
    }
  }

  return {
    suma,
    maximo,
    media: suma / numeros.length
  };
}

const resultado = calcularEstadisticas([10, 20, 30, 40, 50]);
console.log(resultado);
  2. Paso 2 — Reproduce el bug: Ejecuta pnpm dev y abre la consola. Verás que media es NaN.
  3. Paso 3 — Pon un breakpoint: En Sources, pon un breakpoint en la línea suma += numeros[i];. Recarga la página y avanza con F10. Observa en Scope que i llega a 5 (fuera del array) y numeros[5] es undefined. Al sumar undefined, suma se convierte en NaN.
  4. Paso 4 — Corrige el bug: Cambia i <= numeros.length por i < numeros.length.
  5. Paso 5 — Verifica: Quita el breakpoint y recarga. Ahora media debe ser 30 (correcto).

8 · Reto

🎯 Debugger de Node.js con Chrome DevTools

Crea un archivo server-stats.js que simule el procesamiento de logs de un servidor:

  1. Genera un array con 1000 registros de acceso simulados (timestamp, endpoint, statusCode).
  2. Calcula estadísticas: total de peticiones, porcentaje de errores (statusCode >= 400), endpoint más solicitado.
  3. Introduce un bug sutil (ej: índice fuera de rango, comparación incorrecta).
  4. Ejecuta con node --inspect-brk server-stats.js.
  5. Conéctate desde chrome://inspect y usa breakpoints, watch y step over para encontrar y corregir el bug.

Pista: --inspect-brk pausa en la primera línea; --inspect ejecuta hasta encontrar un debugger o un breakpoint manual.

9 · Resumen

  • El ciclo profesional es escribir → ejecutar → depurar → iterar. Con Vite + HMR, este ciclo dura segundos.
  • DevTools es tu herramienta más poderosa. Domina las pestañas Console, Sources, Network y Application.
  • Breakpoints pausan la ejecución; Step Over (F10) avanza al siguiente statement; Step Into (F11) entra en la función llamada.
  • Watch monitoriza expresiones en tiempo real; Call Stack muestra quién llamó a quién.
  • debugger; es un breakpoint portable desde código.
  • console.time/console.timeEnd miden rendimiento; console.table visualiza arrays de objetos.
  • El stack trace se lee de abajo hacia arriba: la última línea es el origen; la primera es dónde falló.
  • Node.js se depura con node --inspect conectándote desde chrome://inspect o con el debugger integrado de VSCode.

10 · Preguntas frecuentes

¿Por qué debo usar breakpoints si console.log funciona?

console.log te muestra valores en un momento concreto, pero no te deja explorar. Con un breakpoint puedes: ver TODAS las variables en Scope sin tener que adivinar cuáles loguear, ejecutar código en la consola en ese contexto exacto, modificar variables para probar escenarios, y avanzar línea por línea para ver cómo cambia el estado. Es la diferencia entre ver una foto (log) y ver una película que puedes pausar y rebobinar (breakpoint).

¿Qué hago si el código minificado hace ilegible el stack trace?

En desarrollo, nunca minifiques el código. Usa source maps: Vite los genera automáticamente en modo desarrollo. Un source map es un archivo que mapea el código minificado al código original. Si ves nombres como a, b, t en el stack trace, es que te faltan source maps o estás depurando en producción.

¿Puedo depurar código asíncrono con breakpoints?

Sí. Los breakpoints funcionan perfectamente con código asíncrono (promesas, async/await, setTimeout). El depurador pausa la ejecución en el punto exacto, esté dentro de un callback, una promesa o un await. Además, en la pestaña Sources puedes activar «Async» en el panel Call Stack para ver la cadena completa de llamadas asíncronas.

¿Cómo depuro un error que solo ocurre en producción?

Usa herramientas de monitoreo como Sentry o LogRocket que capturan errores en producción con stack traces completos y contexto. Para debugging manual, puedes añadir logs condicionales que solo se activen con un flag en localStorage o una variable de entorno. Nunca despliegues código con debugger; a producción.

¿Merece la pena configurar el debugger de VSCode para Node.js?

Sí, especialmente si trabajas en Node.js a diario. Te permite poner breakpoints directamente en VSCode (clic en el gutter), inspeccionar variables en el panel de debug de VSCode, y no tener que cambiar de ventana a Chrome. La configuración es un archivo .vscode/launch.json de 10 líneas que puedes generar automáticamente. Para scripts rápidos, node --inspect + Chrome es más que suficiente.
