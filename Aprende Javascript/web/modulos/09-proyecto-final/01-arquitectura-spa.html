2 · Teoría

¿Qué es una SPA (Single Page Application)?

Una SPA es una aplicación web que carga un único archivo HTML y luego usa JavaScript para gestionar toda la navegación, renderizado y estado sin recargar la página. Cuando el usuario "navega" a otra vista, JavaScript reemplaza el contenido del DOM sin pedir un nuevo HTML al servidor.

┌──────────────────────────────────────────────────────┐
│  APLICACIÓN TRADICIONAL (MPA)                         │
│                                                      │
│  index.html  ──click──► servidor ──recarga──► perfil.html
│  perfil.html ──click──► servidor ──recarga──► tareas.html
│                                                      │
│  ← Cada vista = una petición HTTP = recarga completa │
├──────────────────────────────────────────────────────┤
│  SINGLE PAGE APPLICATION (SPA)                        │
│                                                      │
│  index.html ──click──► JS router ──► cambia #/perfil  │
│            ◄──click──► JS router ──► cambia #/tareas  │
│                                                      │
│  ← Todo ocurre en la misma página, sin recargas      │
└──────────────────────────────────────────────────────┘

Las ventajas de una SPA:

  • Fluidez: sin recargas, las transiciones son instantáneas.
  • Estado persistente: el store de datos sobrevive entre navegaciones.
  • Menos carga del servidor: solo se piden datos (JSON), no HTML completo.

Las desventajas (que abordaremos):

  • SEO más complejo: los bots de búsqueda no ejecutan JavaScript igual que un navegador.
  • Carga inicial más pesada: todo el código JS se descarga al inicio (mitigado con code splitting).
  • Complejidad: tienes que implementar cosas que el navegador hace gratis (historial, scroll restoration).

Las tres piezas de nuestra arquitectura

1. Router hash-based

Usamos el hash de la URL (#/tareas, #/proyectos) para identificar la vista actual. ¿Por qué hash y no History API? Porque las rutas hash funcionan sin configuración del servidor: miapp.com/#/tareas siempre carga miapp.com (el hash nunca se envía al servidor). Con History API (/tareas), necesitas que el servidor devuelva index.html para cualquier ruta — requiere configuración adicional.

Nuestro router escucha el evento hashchange y, cuando cambia el hash, busca la vista correspondiente y la renderiza en el contenedor principal. Además, al iniciar, lee el hash actual y renderiza la vista correcta (soporte para URLs compartidas).

2. Store central con patrón Observer (pub/sub)

El store es el "cerebro" de la aplicación. Contiene TODOS los datos (tareas, proyectos, configuración) en un único objeto de estado. Nadie modifica el estado directamente: se modifican a través de acciones del store (store.addTask(), store.deleteTask()), que actualizan el estado y notifican a todos los suscriptores.

El patrón es pub/sub (publish/subscribe):

  • Las vistas se suscriben al store. Cuando quieren renderizarse, leen el estado actual del store.
  • Los eventos de usuario (clics, formularios) llaman a acciones del store.
  • El store ejecuta la acción, actualiza el estado, y notifica (publishes) a todos los suscriptores.
  • Cada vista suscrita (subscriber) se re-renderiza con el nuevo estado.
        ┌──────────┐
        │  VISTAS  │  (se suscriben al store)
        │  ┌─────┐ │
        │  │Lista│ │  subscribe(callback)
        │  │Form │ │  ←─────────────────┐
        │  │Stats│ │                    │
        │  └─────┘ │              ┌─────┴──────┐
        └────┬─────┘              │   STORE    │
             │ click/addTask()    │  ┌───────┐ │
             └──────────────────► │  │ state │ │
                                  │  └───────┘ │
                                  │  notify()  │
                                  └────────────┘

3. Sistema de componentes vanilla

No necesitas React para tener componentes. Un componente en JavaScript vanilla es simplemente una función que recibe datos (props) y devuelve un elemento DOM o un string de HTML. Estos componentes son "puros": dados los mismos props, producen el mismo HTML.

En nuestra arquitectura, cada vista es una función que recibe el estado del store y devuelve el HTML correspondiente. El router se encarga de llamar a la función correcta e insertar el resultado en el DOM.

¿Por qué esta estructura? Separa claramente responsabilidades: router.js solo sabe de rutas, store.js solo sabe de datos, components/ solo sabe de HTML, views/ compone componentes en páginas completas. Si quieres cambiar cómo se renderizan las tareas, solo tocas task-card.js. Si quieres añadir persistencia en API, solo tocas store.js. Esta es la esencia de la arquitectura limpia.

3 · Ejemplo mínimo

Router hash-based en 20 líneas

// router.js — El router más pequeño posible
// Registro de rutas: hash → función que devuelve HTML
const routes = {
  '#/':        () => '<h1>Home</h1>',
  '#/tareas':  () => '<h1>Tareas</h1>',
  '#/perfil':  () => '<h1>Perfil</h1>',
};

// Punto de montaje en el DOM
const outlet = document.getElementById('app');

// Función que renderiza la ruta actual
function renderRoute() {
  // Leer el hash actual (ej: '#/tareas') o usar la ruta por defecto
  const hash = location.hash || '#/';
  const renderFn = routes[hash];

  if (renderFn) {
    outlet.innerHTML = renderFn(); // Insertar HTML de la vista en el DOM
  } else {
    outlet.innerHTML = '<h1>404 - No encontrada</h1>';
  }
}

// Escuchar cambios de hash (cuando el usuario navega)
window.addEventListener('hashchange', renderRoute);

// Renderizar la ruta inicial al cargar la página
window.addEventListener('DOMContentLoaded', renderRoute);

Store con patrón pub/sub en 30 líneas

// store.js — Estado central de la aplicación
function createStore(initialState = {}) {
  let state = { ...initialState };          // Estado actual (privado, solo accesible vía getState)
  const listeners = new Set();              // Conjunto de callbacks suscritos

  return {
    // Leer el estado actual (devuelve una copia superficial para evitar mutaciones externas)
    getState() {
      return { ...state };
    },

    // Actualizar el estado y notificar a los suscriptores
    setState(partial) {
      state = { ...state, ...partial };     // Merge del estado nuevo sobre el viejo
      listeners.forEach((fn) => fn(state)); // Notificar a cada suscriptor
    },

    // Suscribirse a cambios: recibe el callback y devuelve una función para cancelar suscripción
    subscribe(fn) {
      listeners.add(fn);
      // Devolver función de limpieza (importante para evitar memory leaks)
      return () => listeners.delete(fn);
    }
  };
}

// Instanciar el store con el estado inicial de la app
const store = createStore({
  tasks: [],
  filter: 'all',         // 'all' | 'pending' | 'completed'
  currentView: '#/'
});

export default store;

Vista que se suscribe al store

// views/tasks.js — Vista que reacciona a cambios del store
import store from '../store.js';

function TaskList() {
  // Leer el estado actual
  const { tasks } = store.getState();

  // Renderizar lista de tareas
  return tasks.length === 0
    ? '<p>No hay tareas aún. ¡Crea la primera!</p>'
    : `<ul>${tasks.map((t) => `<li>${t.title}</li>`).join('')}</ul>`;
}

// Exportamos una función que renderiza y se suscribe al store
export function mountTaskList(container) {
  // Renderizar la primera vez
  container.innerHTML = TaskList();

  // Suscribirse para re-renderizar cuando el store cambie
  const unsubscribe = store.subscribe(() => {
    container.innerHTML = TaskList();
  });

  // Devolver función de limpieza (se llamará al cambiar de vista)
  return unsubscribe;
}

4 · Ejemplo real

Vamos a implementar el router completo de TaskFlow con soporte para parámetros, vistas lazy (import dinámico) y guardias de navegación:

// ===== src/router.js =====
// Router hash-based con lazy loading de vistas
class Router {
  constructor(outletSelector = '#app') {
    this.outlet = document.querySelector(outletSelector); // Contenedor donde renderizamos
    this.routes = new Map();   // Mapa de rutas: '/tareas' → { view, guard }
    this.currentView = null;   // Vista actual montada
    this.currentCleanup = null;// Función de limpieza de la vista actual
  }

  // Registrar una ruta: path, vista (función o import dinámico), guardia opcional
  on(path, viewLoader, guard = null) {
    this.routes.set(path, { viewLoader, guard });
    return this; // Permitir encadenamiento: router.on('/a', ...).on('/b', ...)
  }

  // Navegar a una ruta programáticamente
  navigate(path) {
    location.hash = path; // Esto dispara el evento hashchange
  }

  // Iniciar el router
  start() {
    // Escuchar cambios de hash
    window.addEventListener('hashchange', () => this.resolve());

    // Resolver la ruta inicial (si hay hash en la URL al cargar)
    this.resolve();
  }

  async resolve() {
    // Obtener la ruta actual del hash (sin el #)
    const path = location.hash.slice(1) || '/';
    const route = this.routes.get(path);

    // Si no hay ruta registrada, mostrar 404
    if (!route) {
      this.outlet.innerHTML = '<h1>404 — Página no encontrada</h1>';
      return;
    }

    // Ejecutar guardia de navegación si existe (ej: si no está autenticado, redirigir)
    if (route.guard) {
      const canActivate = await route.guard();
      if (!canActivate) {
        this.navigate('/'); // Redirigir a home
        return;
      }
    }

    // Limpiar la vista anterior (cancelar suscripciones, remover event listeners)
    if (this.currentCleanup) {
      this.currentCleanup();
      this.currentCleanup = null;
    }

    // Cargar la vista (puede ser import dinámico para code splitting)
    const view = await route.viewLoader();

    // Montar la vista en el outlet y guardar la función de limpieza
    this.currentCleanup = view.mount(this.outlet);
    this.currentView = path;
  }
}

// ===== src/app.js =====
// Punto de entrada: configurar rutas y arrancar
import { Router } from './router.js';
import store from './store.js';

const router = new Router('#app');

// Registrar rutas con lazy loading (cada vista se descarga solo cuando se necesita)
router
  .on('/', () => import('./views/home.js'))
  .on('/tareas', () => import('./views/tasks.js'))
  .on('/proyectos', () => import('./views/projects.js'));

// Arrancar la aplicación
router.start();

export { router, store };

Implementación del store con acciones

// ===== src/store.js =====
import { generateId } from './utils/id.js';

function createStore(initialState = {}) {
  let state = {
    tasks: [],
    filter: 'all',    // 'all' | 'pending' | 'completed'
    ...initialState
  };

  const listeners = new Set();

  // Notificar a todos los suscriptores
  function notify() {
    listeners.forEach((fn) => fn(state));
  }

  return {
    getState() {
      return { ...state };
    },

    subscribe(fn) {
      listeners.add(fn);
      return () => listeners.delete(fn);
    },

    // ===== ACCIONES (mutan el estado y notifican) =====

    addTask({ title, description = '', priority = 'medium', dueDate = null }) {
      const task = {
        id: generateId(),           // ID único
        title,                      // Título de la tarea
        description,                // Descripción opcional
        priority,                   // 'low' | 'medium' | 'high'
        dueDate,                    // Fecha límite (ISO string o null)
        completed: false,           // Estado de completado
        createdAt: new Date().toISOString() // Timestamp de creación
      };

      state = {
        ...state,
        tasks: [...state.tasks, task] // Añadir nueva tarea al array (inmutabilidad)
      };

      notify(); // Avisar a las vistas suscritas
      return task;
    },

    updateTask(taskId, updates) {
      state = {
        ...state,
        tasks: state.tasks.map((task) =>
          task.id === taskId ? { ...task, ...updates } : task
        )
      };
      notify();
    },

    deleteTask(taskId) {
      state = {
        ...state,
        tasks: state.tasks.filter((task) => task.id !== taskId)
      };
      notify();
    },

    toggleTask(taskId) {
      state = {
        ...state,
        tasks: state.tasks.map((task) =>
          task.id === taskId ? { ...task, completed: !task.completed } : task
        )
      };
      notify();
    },

    setFilter(filter) {
      state = { ...state, filter };
      notify();
    }
  };
}

const store = createStore();
export default store;

Puntos clave de este diseño: (1) El estado se trata como INMUTABLE — nunca modificamos state.tasks.push(), siempre creamos un nuevo array. Esto evita bugs difíciles de rastrear y permite comparar estados fácilmente. (2) Las acciones son el ÚNICO punto de entrada para modificar el estado. Ningún componente modifica store.state directamente. (3) Cada acción llama a notify() para que las vistas se actualicen automáticamente. (4) El store no sabe nada del DOM — es pura lógica de datos, completamente testeable.

5 · Buenas prácticas

HazEvitaPor qué
Trata el estado como inmutable (crea objetos nuevos) Mutación directa: state.tasks.push(task) La mutación directa hace imposible rastrear cambios y puede causar que las vistas no se actualicen porque el objeto es el mismo (misma referencia).
Usa rutas hash (#/tareas) para SPAs estáticas History API (/tareas) sin configuración del servidor Si el usuario recarga en /tareas, el servidor buscará ese archivo y devolverá 404. Con hash, siempre se carga index.html.
Cada vista devuelve una función mount() que limpia al desmontar Suscribir vistas al store sin cancelar la suscripción al cambiar de vista Memory leaks: si navegas 50 veces, tendrás 50 funciones suscritas al store ejecutándose cada vez que cambie el estado, aunque la vista ya no esté visible.
import() dinámico para cargar vistas bajo demanda Importar todas las vistas en app.js Si un usuario nunca visita /proyectos, no debería descargar ese código. Vite separa cada import() en un chunk independiente.
Componentes como funciones puras que devuelven HTML Componentes que dependen de variables globales o efectos secundarios Un componente puro es predecible y testeable: dado un input, siempre produce el mismo output. Sin sorpresas.

6 · Errores habituales

Error 1: No limpiar suscripciones al cambiar de vista

// ❌ MAL: la suscripción vive para siempre
function mountTaskList(container) {
  container.innerHTML = render();
  store.subscribe(() => {
    container.innerHTML = render();
  });
  // Nunca cancelamos la suscripción — memory leak garantizado
}

// ✅ BIEN: devolver función de limpieza
function mountTaskList(container) {
  container.innerHTML = render();
  const unsubscribe = store.subscribe(() => {
    container.innerHTML = render();
  });
  return unsubscribe; // El router llama a esto al cambiar de vista
}

Error 2: Mutar el estado directamente

// ❌ MAL: push muta el array original
const tasks = store.getState().tasks;
tasks.push(newTask); // ¡Modificaste el array dentro del store!

// ✅ BIEN: crear un nuevo array
store.addTask(newTask); // El store se encarga de crear el nuevo array y notificar

Error 3: Usar History API sin fallback del servidor

// ❌ MAL: con History API, al recargar en /tareas el servidor devuelve 404
history.pushState(null, '', '/tareas');

// ✅ BIEN: con hash, al recargar en #/tareas el servidor siempre devuelve index.html
location.hash = '#/tareas';

8 · Reto

🎯 Sistema de rutas anidadas con parámetros

Extiende el router para que soporte:

  1. Rutas con parámetros: /tareas/:id que renderice una vista de detalle de tarea.
  2. Un guardia de navegación que evite visitar /tareas/:id si la tarea no existe (redirigir a 404).
  3. Una vista 404 personalizada con sugerencias de rutas válidas.
  4. Transiciones CSS entre vistas (fade in/out).

Pista para parámetros: puedes usar un conversor simple de /tareas/:id a regex — new RegExp('^/tareas/([^/]+)$') — o implementar un mini path-to-regex usando split('/') y comparar segmento por segmento.

9 · Resumen

  • SPA: aplicación de una sola página. Navegación sin recargas mediante JavaScript. Más fluida pero más compleja que una MPA tradicional.
  • Router hash-based: usa location.hash y el evento hashchange. No requiere configuración del servidor. Ideal para SPAs estáticas.
  • Store con pub/sub: estado centralizado. Las vistas se suscriben a cambios. Las acciones de usuario mutan el estado → notifican → re-renderizan.
  • Estado inmutable: nunca modificar el objeto de estado directamente. Siempre crear copias con los cambios. Previene bugs y facilita la depuración.
  • Componentes como funciones: reciben datos, devuelven HTML. Puros, predecibles y testeables.
  • Lazy loading de vistas: import() dinámico para cargar vistas solo cuando se navega a ellas. Vite las separa en chunks automáticamente.
  • Limpieza al desmontar: cada vista devuelve una función de cleanup que cancela suscripciones y remueve event listeners. Previene memory leaks.
  • TaskFlow: combinación de router + store + componentes vanilla = una SPA profesional sin frameworks en < 500 líneas de código.

10 · Preguntas frecuentes

¿Por qué no usar directamente React o Vue para esto?

Si el proyecto va a crecer mucho (decenas de vistas, equipo grande, ecosistema de librerías), React o Vue son la decisión correcta. Pero este ejercicio tiene tres propósitos didácticos: (1) entender qué hacen esos frameworks por debajo, (2) saber que puedes construir una SPA sin ellos si el proyecto es pequeño o tienes restricciones de tamaño de bundle, y (3) valorar lo que los frameworks te ahorran cuando los usas. Un desarrollador que sabe hacer una SPA vanilla es mejor desarrollador con cualquier framework.

¿Este patrón de store es Redux?

Es una versión simplificada del mismo patrón (Flux/Redux). Redux añade conceptos como reducers, middleware, actions tipadas y DevTools. Nuestro store sigue el mismo principio fundamental: estado centralizado, acciones para modificarlo, suscripciones para reaccionar. Si tu app crece hasta necesitar Redux, la migración es directa porque el patrón mental es el mismo.

¿Cómo manejo la carga inicial si las vistas se importan dinámicamente?

El import() dinámico es asíncrono. Mientras la vista se descarga, puedes mostrar un spinner o skeleton en el outlet. En nuestro router, simplemente no mostramos nada hasta que la vista se resuelve. Para una UX más pulida, podrías añadir un estado loading en el router y mostrar un indicador mientras tanto: this.outlet.innerHTML = '<div class="spinner"></div>'; const view = await route.viewLoader();.

¿Cómo evito que el hash aparezca en la barra de direcciones?

Si quieres URLs limpias (sin #), debes usar History API (pushState) en lugar de hash. Pero esto requiere configurar tu servidor para que devuelva index.html ante cualquier ruta. En Vite, durante desarrollo esto funciona automáticamente. En producción, Vercel y Netlify lo soportan con un archivo de configuración. Si no puedes configurar el servidor (ej: GitHub Pages sin config), usa hash.
