Salida estructurada

Módulo 1 · Prompting de ingeniería 🕐 35 minutos

1 · Introducción

Hasta ahora el modelo devuelve texto y tú lo miras con los ojos. En cuanto quieres que una app use la respuesta —guardarla, pasarla a una tool, decidir un flujo— el texto libre es un problema: hay que parsearlo, y falla a menudo. La solución es pedir una salida estructurada: JSON con una forma conocida, validado contra un contrato.

En esta lección aprenderás el ciclo completo y honesto de la ingeniería con LLM: pedir JSON, validarlo con pydantic, y si no cumple, reintentar pasándole al modelo el error exacto como feedback. Verás también cómo el format (JSON Schema) empuja al modelo hacia la forma correcta desde la primera llamada.

¿Por qué existe esta lección? Porque aquí es donde separas de verdad inferencia de lógica determinista. El modelo propone una estructura; tu código decide si es válida. Esa frontera es el cimiento del tool calling (Módulo 2), de las tools del agente (Módulo 5) y de las evals (Módulo 7).

El error típico es hacer json.loads(respuesta) sin red de seguridad: el día que el modelo añade una frase antes del JSON, tu app se cae. Ya verás cómo evitarlo.

2 · Teoría

Por qué texto libre no basta

El modelo es un generador de tokens probabilístico. «Devuelve JSON» no es un contrato: es un deseo. Sin una comprobación, cualquier variación —una frase introductoria, una coma final, un campo que falta— rompe tu código.

   El modelo PROPONE              Tu código DECIDE
   ─────────────────              ────────────────
   texto / JSON  ──►  parsear ──►  ¿cumple el esquema?
                        │              │
                        │            no: reintentar con el error
                        └── ok ──►  objeto tipado (pydantic)

La regla de oro: nunca confíes en que la salida es válida porque se lo pediste. Trátala como entrada de usuario (lección 4): valídala siempre. La validación no es desconfianza del modelo, es ingeniería.

El parámetro format: JSON mode y JSON Schema

Los proveedores ofrecen dos niveles para empujar la salida hacia JSON:

NivelQué garantizaQué NO garantiza
JSON mode (format: "json")La salida es JSON sintácticamente válidoQue tenga tus campos ni los tipos correctos
JSON SchemaLa salida se ajusta a un esquema (campos y tipos)Que los valores sean ciertos o tengan sentido

En Ollama pasas el esquema en el campo format de la petición. El esquema es un JSON Schema, que puedes generar automáticamente desde tu modelo de pydantic con model_json_schema(). Así el contrato y la validación salen de la misma definición: no pueden divergir.

Una sola fuente de verdad: define el modelo una vez en pydantic y deriva de él (a) el JSON Schema que le pasas al modelo y (b) la validación de lo que te devuelve. Si cambias el modelo, ambas cambian juntas. Ese es el punto.

Modelar con pydantic

Un modelo de pydantic describe la forma de la respuesta como una clase con campos tipados. Al validar, obtienes un objeto, no un diccionario suelto: con tipos correctos, valores por defecto y errores claros.

from pydantic import BaseModel, Field

class Intencion(BaseModel):
    accion: str = Field(description="Una de: buscar, abrir_modulo, contar_progreso, charla")
    consulta: str = Field(description="El texto clave de la petición del usuario")
    modulo: int | None = Field(default=None, description="Número de módulo, si aplica")

Los description de cada campo viajan dentro del JSON Schema y le sirven al modelo de instrucción por campo: es documentación que también ve el LLM.

v2, no v1: en pydantic 2 el método es model_validate_json(texto) y el esquema se obtiene con model_json_schema(). Son los nombres actuales; los antiguos parse_raw/schema están obsoletos.

Validar y reintentar con el error como feedback

Cuando la validación falla, pydantic lanza ValidationError con un mensaje muy concreto («accion: Input should be a valid string…», «modulo: Input should be a valid integer»). Ese mensaje no es para ti: es exactamente el feedback que el modelo necesita para corregirse.

  1. Pide la salida (idealmente con format = JSON Schema).
  2. Intenta validar con model_validate_json().
  3. Si valida, devuelves el objeto tipado.
  4. Si falla, añades al historial la salida errónea y un mensaje de user con el error textual del validador.
  5. Repites un número acotado de veces (1–2 reintentos). Si no lo consigue, lo tratas como error de aplicación.

Reintenta con límite: los reintentos cuestan tokens y latencia, y pueden entrar en bucle. Pon un máximo (por ejemplo 2) y, si se agota, registra el caso para depurarlo —probablemente sea un prompt que puede mejorar—. Nunca un while True.

Separa el razonamiento del resultado

Si quieres que el modelo «piense» y aun así parsee fácil, incluye un campo de razonamiento dentro del esquema:

class Analisis(BaseModel):
    razonamiento: str   # aquí el modelo piensa, en texto
    resultado: str       # aquí va la respuesta final

Así el «pensamiento» no contamina la respuesta y tú decides si lo usas (por ejemplo, para mostrarlo en un modo depuración) o lo ignoras.

3 · Ejemplo mínimo

El ciclo más pequeño: definir el modelo, derivar el esquema, pedir la salida y validarla. El helper chat ahora acepta el parámetro format.

minimo_struct.py
import json
import urllib.request
from pydantic import BaseModel, Field

class Ciudad(BaseModel):
    nombre: str = Field(description="Nombre de la ciudad")
    habitantes: int = Field(description="Población aproximada, en número entero")

def chat(messages: list[dict], model: str = "llama3.2", fmt: object | None = None) -> str:
    """Igual que antes, pero puede forzar un formato JSON (esquema o 'json')."""
    body: dict[str, object] = {"model": model, "messages": messages, "stream": False}
    if fmt is not None:
        body["format"] = fmt
    payload = json.dumps(body).encode()
    request = urllib.request.Request(
        "http://localhost:11434/api/chat",
        data=payload,
        headers={"Content-Type": "application/json"},
    )
    with urllib.request.urlopen(request) as response:
        return json.load(response)["message"]["content"]

schema = Ciudad.model_json_schema()  # el contrato, derivado del modelo
messages = [
    {"role": "system", "content": "Extraes datos de ciudades y devuelves solo JSON."},
    {"role": "user", "content": "Bogotá tiene unos 11 millones de habitantes."},
]

raw = chat(messages, fmt=schema)
ciudad = Ciudad.model_validate_json(raw)  # valida y tipa de una vez

print(ciudad.nombre, ciudad.habitantes)   # Bogotá 11000000
print(type(ciudad.habitantes))            # <class 'int'> y no un str

Línea por línea:

  1. class Ciudad(BaseModel): el contrato. Dos campos tipados con su descripción.
  2. model_json_schema(): convierte el modelo en un JSON Schema; es lo que le enviamos al LLM en format.
  3. fmt=schema: Ollama restringe la generación para que encaje con el esquema: campos correctos y tipos correctos.
  4. model_validate_json(raw): parsea y valida. Si algo no cuadra, lanza ValidationError —y eso lo usaremos en el ejemplo real—.
  5. ciudad.habitantes: ya es un int; puedes sumarlo sin convertir nada. Eso es «salida estructurada» de verdad.

4 · Ejemplo real

El Copiloto necesita, de cada pregunta del usuario, una intención estructurada con la que decidir qué hacer. Y como ningún modelo es infalible, envolvemos la extracción en un bucle de validación con reintento y feedback del error.

copiloto/schema.py
from pydantic import BaseModel, Field

class Intencion(BaseModel):
    """Intención extraída de la petición del usuario."""
    accion: str = Field(description="Una de: buscar, abrir_modulo, contar_progreso, charla")
    consulta: str = Field(description="El contenido clave de la petición, sin muletillas")
    modulo: int | None = Field(default=None, description="Número de módulo del 0 al 8, si aplica")
copiloto/extract.py
from pydantic import ValidationError
from copiloto.schema import Intencion
from minimo_struct import chat

SYSTEM = (
    "Eres el enrutador del Copiloto de la Academy. Conviertes la petición del "
    "usuario en un objeto JSON que valide contra el esquema dado. No añades texto."
)

def extract(text: str, max_retries: int = 2) -> Intencion:
    """Extrae la intención del usuario, reintentando con el error como feedback."""
    schema = Intencion.model_json_schema()
    messages = [
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": f"Petición del usuario:\n{text}"},
    ]
    for _ in range(max_retries + 1):
        raw = chat(messages, fmt=schema)
        try:
            return Intencion.model_validate_json(raw)
        except ValidationError as exc:
            # Devolvemos al modelo su error exacto para que se corrija.
            messages.append({"role": "assistant", "content": raw})
            messages.append({
                "role": "user",
                "content": f"Esa salida no es válida. Corrige solo el JSON. Error: {exc}",
            })
    raise RuntimeError(f"No se pudo extraer la intención tras {max_retries + 1} intentos")

if __name__ == "__main__":
    for frase in ["ábreme el módulo 4", "¿cuántas lecciones llevo?", "hola!" ]:
        intencion = extract(frase)
        print(f"{frase!r} -> accion={intencion.accion!r} modulo={intencion.modulo}")

Decisiones, y por qué:

  • El esquema sale del modelo: Intencion.model_json_schema(). Contrato y validación, la misma fuente. Si añades una accion nueva, cambias la clase y todo lo demás se ajusta.
  • modulo: int | None: opcional y tipado. Es None cuando no aplica, en vez de un "" o un -1 ambiguos.
  • Feedback de ValidationError: el mensaje de pydantic es muy específico («esperaba un entero, recibí…»). Se lo devolvemos tal cual: el modelo casi siempre corrige al primer reintento.
  • Bucle acotado por max_retries: 3 intentos como máximo. Si fallan, excepción y registro. Nada de bucles infinitos.
  • accion como str con descripción: enumeramos los valores en la description. (Podríamos usar un Literal[...] para validación estricta; lo exploras en el reto.)

Este patrón es el corazón del tool calling: en el Módulo 2, lo que hoy es «extraer una intención» se convierte en «el modelo elige una tool y rellena sus argumentos». La validación con pydantic de esos argumentos es obligatoria. Guarda este ejemplo.

5 · Buenas prácticas

HazEvitaPor qué
Define el contrato una vez en pydantic y deriva el JSON Schema Mantener el esquema a mano en el prompt y el modelo aparte Si divergen, validas contra algo distinto de lo que pediste

6 · Errores habituales

1. Confiar en que «el modelo devuelve JSON»

Mal — parseo a ciegas 
raw = chat(messages)          # pedimos JSON, pero no lo validamos
data = json.loads(raw)        # puede estallar: texto antes del JSON, comas de más...
print(data["accion"])         # KeyError si el campo no existe
Bien — valida contra el contrato 
raw = chat(messages, fmt=Intencion.model_json_schema())
try:
    intencion = Intencion.model_validate_json(raw)
except ValidationError as exc:
    ...  # reintentar con el error como feedback

2. Reintentar sin decirle qué falló

Mal — repetir la misma petición tal cual 
for _ in range(5):
    raw = chat(messages)                 # mismo prompt exacto
    # Si falló una vez, ¿por qué iba a salir bien la siguiente? Es una tirada de dados.
Bien — el error es el feedback 
except ValidationError as exc:
    messages.append({"role": "assistant", "content": raw})
    messages.append({"role": "user", "content": f"Corrige solo el JSON. Error: {exc}"})

3. Esquema demasiado laxo

Mal — todo es str, todo vale 
class Datos(BaseModel):
    accion: str       # "buscar", "BUSCAR", "quiero buscar", "buscar..."  pasan igual
    modulo: str       # "cuatro" o "4" o "módulo 4" --- ¡todos válidos!
Bien — restringe lo que la lógica espera 
from typing import Literal
class Datos(BaseModel):
    accion: Literal["buscar", "abrir_modulo", "contar_progreso", "charla"]
    modulo: int | None = None

Cuanto más específico el tipo, antes (y con mejor mensaje) detectas una salida incorrecta.

4. Ignorar los reintentos al medir

Mal — no saber cuántas veces reintenta 
# El código reintenta, pero no cuentas cuántas veces.
# Un prompt que "funciona" con 4 reintentos de media es un generador de coste.
Bien — instrumenta la tasa de reintento 
reintentos += 1   # acumula y reporta: si es alto, mejora el esquema o el prompt

7 · Ejercicio guiado

Objetivo: modelar una salida, forzarla, validarla y observar un reintento real. Paso a paso.

  1. Paso 1: define un modelo para resumir una lección: 
    from pydantic import BaseModel, Field

class Resumen(BaseModel):
    titulo: str
    puntos: list[str] = Field(min_length=2, max_length=3, description="Entre 2 y 3 viñetas")
    nivel: str = Field(description="principiante o avanzado")
  2. Paso 2: pasa Resumen.model_json_schema() al format de chat() y pide un resumen de una lección real del curso.
  3. Paso 3: valida con Resumen.model_validate_json(raw) e imprime resumen.puntos.
  4. Paso 4: a propósito, relaja el esquema (quita min_length/max_length) y observa cuántas viñetas devuelve el modelo sin restricción. Vuelve a añadirlas.
  5. Paso 5: fuerza un fallo: pide el resumen sin format y pide al modelo «explica en prosa». Captura el ValidationError e imprime str(exc).
  6. Paso 6: reenvía ese error como feedback (el patrón del ejemplo real) y comprueba que el modelo entrega un JSON válido al reintentar. Anota cuántos intentos hicieron falta.

Resultado esperado: en el paso 6, algo como

Intento 1 falló: 1 validation error for Resumen
  puntos: List should have at least 2 items after validation, not 1
Intento 2 OK -> ['El prompt es estructura', 'Los roles separan tarea y datos', ...]

Cómo comprobarlo: si el reintento nunca falla tras el feedback, el ciclo funciona. Si necesitas más de dos reintentos de forma habitual, tu esquema o tu prompt tienen un problema que conviene arreglar (y medir).

Multiplataforma: pydantic 2 se instala con uv add pydantic. El código es idéntico en Linux, macOS y Windows; uv run minimo_struct.py arranca en los tres.

8 · Reto

Reto

Convierte la extracción de intención en un validador estricto y mide su tasa de reintento. Sustituye accion: str por un tipo restringido, añade una regla de negocio (por ejemplo, que abrir_modulo exija modulo no nulo y dentro de 0–8) y ejecuta 20 frases distintas. Reporta cuántas validaron al primer intento y cuántas necesitaron reintento.

Pista: pydantic v2 tiene model_validator(mode="after") para reglas que cruzan campos; y Literal[...] o Annotated[str, StringConstraints(...)] para restringir valores. Que un campo sea imposible de rellenar mal es mejor que una comprobación if olvidable.

9 · Resumen

  • El texto libre no sirve para una app; la salida estructurada sí.
  • El JSON Schema (campo format) empuja al modelo hacia la forma correcta; el JSON mode solo garantiza sintaxis.
  • Modela el contrato con pydantic y deriva de él el esquema y la validación: una sola fuente de verdad.
  • Valida siempre con model_validate_json(); el modelo propone, tu código decide.
  • Reintenta con el ValidationError como feedback y con un límite de intentos.
  • Separa razonamiento de resultado en campos distintos del esquema.
  • Instrumenta la tasa de reintento: es una métrica de calidad de tu prompt.

10 · Preguntas frecuentes

Si uso JSON mode, ¿ya no hace falta validar?

Falta la mitad. El JSON mode garantiza que el texto es parseable como JSON, pero no que tenga tus campos ni que los tipos sean los correctos. Un {"accion": "buscar", "modulo": "cuatro"} es JSON válido y, sin embargo, inválido para tu lógica. Valida siempre contra el modelo.

¿Reintentar no es «hacer trampa»?

No: es control de errores, como reintentar una petición de red fallida. El modelo es probabilístico; esperar un 100 % a la primera es ingenuo. Lo importante es reintentar bien (con el error como feedback), con límite, y medir la tasa. Si reintenta mucho, mejora el esquema o el prompt en lugar de tapar el problema.

¿No es más barato pedir la salida en texto y parsearla yo?

Sale más caro a la larga: escribirás y mantenerás un parser frágil que se rompe con cada variación del modelo. Con pydantic defines el contrato una vez y obtienes validación, tipos y errores claros gratis. Además, el format suele reducir reintentos porque el modelo acierta antes.

¿Cuántos reintentos dejo?

Uno o dos. Con el error como feedback, la mayoría se corrige al primer reintento; a partir de ahí, gastas tokens en una petición que probablemente está mal planteada. Si ves tasas altas de reintento, el problema no es el número: es el esquema, las descripciones o la instrucción.

¿Y si el modelo no soporta JSON Schema en format?

Muchos proveedores aceptan un esquema o, como mínimo, un modo JSON. Si el tuyo no lo soporta, pídelo por prompt («responde solo con un objeto JSON con estos campos…») y valida igual: el ciclo validar/reintentar funciona aunque no haya format. La validación es lo no negociable; el format es una ayuda.
