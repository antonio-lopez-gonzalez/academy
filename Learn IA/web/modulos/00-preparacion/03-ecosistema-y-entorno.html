Ecosistema y entorno (uv + Ollama)

Módulo 0 · Preparación 🕐 30 minutos

1 · Introducción

Ya sabes qué es un LLM y cómo se mide. Ahora toca situar las piezas en el mapa y montar un entorno de trabajo serio. Porque construir con IA no es «llamar a un modelo»: es conectar un modelo con embeddings, almacenamiento de vectores, herramientas y evaluación. Si no tienes el mapa, cada decisión técnica parece arbitraria.

Esta lección hace dos cosas:

  • Panorama: dónde encaja cada pieza (APIs frente a local, embeddings, bases vectoriales, agentes) y por qué existe cada una.
  • Entorno: instalar uv (gestor de Python) y Ollama (servidor de modelos local), descargar un modelo y dejar preparada la estructura del proyecto Copiloto.

¿Por qué esta lección existe? Porque «funciona en mi máquina» destruye proyectos. De la misma forma que un equipo web fija Node y pnpm, un equipo de IA fija el runtime (uv) y el proveedor por defecto (local con Ollama). Al final, cualquier persona reproduce tu entorno con dos comandos.

Local primero: no necesitas API key ni tarjeta para el núcleo del curso. Ollama corre modelos en tu máquina y es gratis. En el módulo 2 verás cómo conectar OpenAI o Anthropic como alternativa; pero aquí, todo local.

2 · Teoría

¿API en la nube o modelo local?

La pregunta «¿local o nube?» aparece en cada proyecto. No hay respuesta única: hay compromisos. Este curso usa local por defecto y enseña la nube como alternativa.

CriterioLocal (Ollama)Nube (API)
CosteGratis (usas tu CPU/GPU)Se paga por token
PrivacidadLos datos nunca salen de tu máquinaLos datos viajan al proveedor
CalidadBuena en modelos pequeños/medianosLos modelos más potentes
LatenciaDepende de tu hardwareDepende de la red y del proveedor
RequisitoRAM/VRAM suficienteAPI key y conexión
Ideal paraAprender, prototipar, datos sensiblesProducto a escala, máxima calidad

Analogía: la nube es como pedir comida a un restaurante excelente: rápido, cómodo, tiene de todo, pero pagas cada plato y el repartidor ve tu pedido. Local es cocinar en casa: gratis, privado, controlas los ingredientes, pero limitado por lo que tienes en la cocina.

Embeddings y bases vectoriales, en una frase cada uno

No los estudiarás a fondo hasta el módulo 3, pero necesitas saber qué son para entender el mapa:

  • Embedding: convertir un texto en un vector de números que captura su significado. Textos con sentido parecido quedan cerca en el espacio. Sirve para buscar por similitud, no por palabras exactas.
  • Base vectorial: almacén especializado en encontrar los vectores más cercanos a uno dado, a escala y con filtros por metadatos. Usaremos pgvector (PostgreSQL) y sqlite-vec (SQLite).

uv: gestor de Python y de proyectos

uv es un gestor escrito en Rust que reemplaza a pip, venv, pip-tools y poetry con un solo comando y mucha más velocidad. Tres cosas que hace por ti:

  1. Gestiona el intérprete: descarga e instala la versión de Python que pidas (por ejemplo 3.12), aunque no la tengas.
  2. Resuelve dependencias: lee tu pyproject.toml, resuelve versiones y escribe un uv.lock reproducible.
  3. Crea y ejecuta el entorno: .venv automático y uv run para ejecutar sin activar nada a mano.

uv run es la joya: sincroniza dependencias y ejecuta el script en un paso. Olvídate de «activar el entorno»; funciona igual en Windows, macOS y Linux, y siempre con la misma versión resuelta.

Ollama: el servidor de modelos local

Ollama descarga modelos y levanta un servidor HTTP en http://localhost:11434 con una API sencilla. Tú puedes hablarle de dos formas, y el curso usará las dos:

  • HTTP directo (/api/chat, /api/generate, /api/embeddings): útil para entender qué viaja de verdad por la red y para cualquier lenguaje.
  • SDK de Python (ollama): más cómodo en el código del día a día.

Ollama expone además una API compatible con OpenAI en /v1, lo cual te permitirá reutilizar clientes y comparar proveedores sin reescribir todo.

La estructura del proyecto Copiloto

Todo el curso apunta a un único proyecto real: Copiloto. Esta es su forma final; hoy creamos el esqueleto.

  proyectos/copiloto/
  ├── pyproject.toml          <- dependencias y config (uv)
  ├── uv.lock                 <- versiones congeladas (se versiona)
  ├── .env.example            <- variables de entorno de ejemplo (SIN secretos)
  ├── README.md
  └── src/
      └── copiloto/
          ├── __init__.py

          ├── tools.py          <- herramientas que el agente puede usar

3 · Ejemplo mínimo

El proyecto más pequeño posible con uv: creado, con versión de Python fijada, y ejecutando un script que se documenta a sí mismo.

terminal
# Crea un proyecto llamado "entorno-demo" y entra en él.
uv init entorno-demo
cd entorno-demo

# Fija la version de Python del proyecto (uv la descarga si hace falta).
uv python pin 3.12
main.py
# main.py — comprobar con que Python y con que dependencias cuentas.
import sys

print("Python:", sys.version.split()[0])          # p. ej. 3.12.x
print("Ruta del interprete:", sys.executable)     # debe apuntar a .venv
terminal
uv run main.py

Salida esperada:

Python: 3.12.4
Ruta del interprete: /ruta/entorno-demo/.venv/bin/python

Línea por línea:

  1. uv init entorno-demo: crea la carpeta y un pyproject.toml mínimo. No necesitas venv ni pip.
  2. uv python pin 3.12: escribe la versión de Python en .python-version. Cualquiera que clone el repo tendrá la misma.
  3. sys.executable: apunta al .venv del proyecto. Si apuntara al Python del sistema, tu entorno no estaría aislado.
  4. uv run main.py: uv comprueba el lockfile, instala lo que falte y ejecuta el script. Un solo comando, reproducible.

4 · Ejemplo real

Ahora el Copiloto de verdad: su pyproject.toml, sus primeras dependencias y el primer módulo de código, llm.py, que envuelve el cliente de Ollama para que el resto del proyecto no sepa (ni le importe) qué proveedor hay detrás.

proyectos/copiloto/pyproject.toml
[project]
name = "copiloto"
version = "0.1.0"
description = "Asistente RAG sobre los cursos de la Academy"
requires-python = ">=3.12"
dependencies = [
    "ollama>=0.4",
    "pydantic>=2.7",
    "typer>=0.12",
    "rich>=13.0",
]

[project.scripts]
copiloto = "copiloto.cli:app"     # el comando de consola que usara el alumno

[dependency-groups]
dev = ["ruff", "mypy", "pytest"]

Con eso, preparar el entorno del Copiloto es un solo comando:

terminal
cd proyectos/copiloto
uv sync          # crea .venv, instala todo y respeta uv.lock
uv run copiloto --help

Y este es el primer módulo de código, la frontera con el modelo:

proyectos/copiloto/src/copiloto/llm.py
# src/copiloto/llm.py — la UNICA puerta hacia el modelo.
# El resto del proyecto llama a generate(); no sabe si detras hay Ollama o una API.
import os
from dataclasses import dataclass

from ollama import Client

DEFAULT_MODEL = os.environ.get("COPILOTO_MODEL", "llama3.2")
OLLAMA_HOST = os.environ.get("OLLAMA_HOST", "http://localhost:11434")


@dataclass
class Reply:
    """Respuesta normalizada, independiente del proveedor."""
    text: str
    prompt_tokens: int
    output_tokens: int
    done_reason: str


def generate(prompt: str, *, temperature: float = 0.0) -> Reply:
    """Genera una respuesta a partir de un prompt de texto."""
    client = Client(host=OLLAMA_HOST)
    r = client.chat(
        model=DEFAULT_MODEL,
        messages=[{"role": "user", "content": prompt}],
        options={"temperature": temperature},
        stream=False,
    )
    return Reply(
        text=r.message.content,
        prompt_tokens=r.prompt_eval_count,
        output_tokens=r.eval_count,
        done_reason=r.done_reason,
    )

Decisiones y porqués:

  • Una sola puerta al modelo (llm.py): si mañana cambias de proveedor, solo tocas este archivo. Es el patrón adapter aplicado a la IA.
  • Variables de entorno (COPILOTO_MODEL, OLLAMA_HOST): la configuración no va en el código. Así el mismo binario funciona en tu máquina y en otro sitio.
  • Reply normalizado: el resto del proyecto no depende del formato crudo de un proveedor. Incluye tokens y motivo de parada desde el primer día: observar antes de optimizar.
  • requires-python = ">=3.12": el contrato del curso. uv lo hace cumplir.

No escribas llm.py a mano todavía si no quieres: la lección 4 hará la primera llamada de verdad. Lo importante aquí es entender por qué el proyecto se organiza así.

6 · Errores habituales

Instalar dependencias globalmente en vez de por proyecto

Mal — todo al Python global 
# ❌ Contamina el sistema y no queda registrado en ninguna parte.
pip install ollama pydantic
python app.py
Bien — proyecto reproducible con uv 
# ✅ Las dependencias viven en pyproject.toml y uv.lock; el venv es local.
uv add ollama pydantic
uv run app.py

Poner la configuración (o peor, claves) en el código

Mal — secreto cableado en el código 
# ❌ Clave y URL dentro del codigo: van al repo y a tu historial de Git.
API_KEY = "sk-1234secreto"
OLLAMA_HOST = "http://localhost:11434"
Bien — variables de entorno y .env ignorado 
# ✅ Lee del entorno; en local se carga desde un .env que NO se versiona.
import os
API_KEY = os.environ["OPENAI_API_KEY"]        # jamas en el codigo
OLLAMA_HOST = os.environ.get("OLLAMA_HOST", "http://localhost:11434")

Commitear el entorno virtual

Mal — versionar .venv 
# ❌ Miles de archivos de tu maquina en el repo: lento y sin sentido.
git add .venv/
git commit -m "add environment"
Bien — ignorarlo y versionar el lock 
# ✅ .gitignore excluye .venv/ y .env; se versiona uv.lock para reproducir.
echo ".venv/" >> .gitignore
echo ".env" >> .gitignore
git add pyproject.toml uv.lock

Suponer que Ollama está en marcha

Mal — fallo críptico 
# ❌ Si el servidor no corre, la llamada falla con un error de red poco claro.
reply = client.chat(model="llama3.2", messages=msgs)
Bien — comprobar y dar un mensaje útil 
# ✅ Comprueba el servidor y traduce el error a algo accionable.
try:
    reply = client.chat(model="llama3.2", messages=msgs)
except Exception as e:
    raise RuntimeError(f"Ollama no responde en {OLLAMA_HOST}. ¿Esta arrancado?") from e

7 · Ejercicio guiado

Objetivo: dejar listo el entorno completo —uv, Ollama y un modelo local— y crear el esqueleto del proyecto Copiloto.

  1. Paso 1: instala uv. En Linux/macOS: 
    curl -LsSf https://astral.sh/uv/install.sh | sh

    En Windows (PowerShell):

    powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

    Comprueba: uv --version debe imprimir algo como uv 0.5.x.

  2. Paso 2: instala Ollama desde https://ollama.com/download (instalador nativo en las tres plataformas) y verifica que el servidor responde: 
    ollama --version
curl http://localhost:11434/api/ps      # lista de modelos cargados en memoria

    Resultado esperado: la versión de Ollama y un JSON (aunque sea {"models":[]}).

  3. Paso 3: descarga un modelo local pequeño y compruébalo: 
    ollama pull llama3.2
ollama list

    Resultado esperado: llama3.2 aparece en la lista con su tamaño. La primera descarga tarda según tu conexión.

  4. Paso 4: crea el proyecto Copiloto con la estructura de la sección 2: 
    uv init proyectos/copiloto --package
cd proyectos/copiloto
uv python pin 3.12
mkdir -p src/copiloto

    Resultado esperado: pyproject.toml, .python-version y la carpeta src/copiloto/ listas.

  5. Paso 5: añade las dependencias y sincroniza: 
    uv add ollama pydantic typer rich
uv sync

    Resultado esperado: uv.lock generado y .venv/ creado. Abre pyproject.toml y verás las dependencias listadas.

  6. Paso 6 (verificación): crea src/copiloto/__init__.py vacío y un check.py que confirme la conexión, y ejecútalo: 
    # src/copiloto/check.py
from ollama import Client
models = [m.model for m in Client().list().models]
print("modelos disponibles:", models)
assert any("llama3.2" in (m or "") for m in models), "falta el modelo"
print("entorno OK")

    uv run python -m copiloto.check

    Resultado esperado: la lista de modelos y entorno OK. Si el assert falla, repite el paso 3.

Pista: en pyproject.toml puedes añadir [dependency-groups] con dev = ["ruff", "mypy", "pytest"] y configurar [tool.ruff] y [tool.mypy]. Para la tarea, un script scripts/arranque.py invocado con uv run basta; no necesitas makefiles. Piensa: ¿qué debería fallar primero y con qué mensaje útil?

9 · Resumen

  • El ecosistema de IA se compone de piezas encadenadas: LLM, embeddings, base vectorial, RAG, tools, agentes y evals.
  • Local (Ollama) es gratis, privado y perfecto para aprender; nube (APIs) da más calidad a cambio de coste y de enviar datos fuera.
  • uv gestiona el intérprete, las dependencias y el entorno con pyproject.toml + uv.lock, y ejecuta con uv run.
  • Ollama levanta un servidor HTTP en localhost:11434; se usa por HTTP directo o por el SDK ollama.
  • El proyecto Copiloto tiene una estructura fija en src/copiloto/ con una única puerta al modelo (llm.py).
  • Configuración por variables de entorno y .env (nunca en el repo); .venv/ ignorado, uv.lock versionado.

10 · Preguntas frecuentes

¿Necesito una GPU para Ollama?

No para aprender. Los modelos pequeños y medianos corren en CPU, con más lentitud. Con GPU (NVIDIA/AMD/Apple Silicon) la generación es notablemente más rápida. Empieza en CPU; si te aficionas, considera modelos cuantizados pequeños.

¿Por qué uv y no pip + venv?

Porque hace lo mismo pero resolviendo versiones de forma reproducible, fijando el intérprete y ejecutando con uv run en un solo paso. Y es mucho más rápido. Si ya usas pip, no pierdes nada: uv pip es compatible, pero el flujo recomendado es el de proyecto.

¿Qué diferencia hay entre modelo, embedding y vector?

El modelo genera y decide lenguaje. Un embedding transforma texto en un vector (lista de números) que representa su significado. Buscar vectores cercanos es buscar textos de sentido parecido. Los embeddings no generan texto: solo miden parecido semántico.

¿Puedo usar la nube desde el primer día?

Puedes, pero el curso está diseñado para que el núcleo funcione sin API key. En el módulo 2 verás cómo añadir OpenAI o Anthropic como alternativa detrás de la misma puerta (llm.py). Recomendación: domina local primero, luego compara.

¿Dónde guardo mis claves si algún día uso la nube?

En un archivo .env local que nunca se versiona (está en .gitignore), y lo lees con os.environ o con python-dotenv. En producción, en el gestor de secretos de tu plataforma. Regla sin excepciones: ninguna clave en el repositorio.
