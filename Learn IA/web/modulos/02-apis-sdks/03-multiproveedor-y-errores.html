Multiproveedor y errores

Módulo 2 · APIs y SDKs 🕐 30 minutos

1 · Introducción

Tu app funcionará con Ollama en local, con OpenAI o con Anthropic según el día. Cada SDK tiene sus nombres, sus errores y sus rarezas. Si escribes tu lógica pegada al SDK de turno, cambiar de proveedor será reescribir medio proyecto. La solución es una interfaz común (un contrato) y adaptadores por proveedor.

Y como la red falla, las APIs imponen rate limits y los modelos se atascan, necesitas una política seria de errores y reintentos. No basta con try/except: hay que distinguir lo transitorio de lo permanente y reintentar solo lo primero, con backoff exponencial y jitter.

¿Por qué existe esta lección? Porque el 90% de los «fallos de IA» en producción no son del modelo: son timeouts, 429, respuestas truncadas o claves mal puestas. Tratar los errores con criterio es lo que separa una demo de un servicio.

2 · Teoría

Local vs nube: no es una religión, son compromisos

Analogía: el proveedor es como la compañía eléctrica. Tu casa (tu código) no debería depender del nombre de la compañía: enchufas y ya. La interfaz común es el enchufe; los adaptadores son los distintos enchufes de cada país.

Una interfaz común: el patrón adaptador

Define un contrato pequeño (generar una respuesta, quizá con streaming y tools) y una implementación por proveedor. El resto del Copiloto habla con el contrato, no con el SDK:

  Copiloto (tu lógica)  ──depende de──►  LLMClient (Protocol)
                                                ▲
                            ┌───────────────────┼────────────────────┐
                            │                   │                    │
                      OllamaClient        OpenAIClient        AnthropicClient
                    (local, por defecto)   (rama nube)          (rama nube)

La ventaja no es «soportar 3 proveedores», sino poder cambiar y comparar sin tocar la app, y poder testear con un fake. La neutralidad de proveedor es una decisión de arquitectura, no de moda.

Taxonomía de errores: no todos se reintentan

Error¿Transitorio?Qué hacer
Conexión (sin red, host caído)SíReintentar con backoff
TimeoutSíReintentar, quizá con prompt más corto
429 / rate limitSíRespetar Retry-After y reintentar con backoff
500 / 502 / 503 / 504SíReintentar con backoff y jitter
400 / 422 (petición inválida)NoArreglar el código o los argumentos; reintentar no ayuda
401 / 403 (auth / permiso)NoRevisar clave y permisos
404 (modelo no existe)NoCorregir el nombre del modelo
Contexto excedidoNoReducir el prompt (resumir, recortar); reintentar no arregla nada

Reintentar un 401 mil veces no lo convierte en un 200. Reintentar lo permanente solo multiplica la carga y retrasa el diagnóstico. Clasifica primero, reintenta después.

Backoff exponencial con jitter

Reintentar «a piñón» satura al proveedor y empeora todo. La técnica estándar es esperar cada vez más, y añadir jitter (un pequeño aleatorio) para que muchos clientes no reintenten a la vez. La fórmula típica:

  espera(n) = min( base * 2^n , tope )  +  aleatorio(0, jitter)

  intento 0 ─► espera 0.5s ─► intento 1 ─► espera 1s ─► intento 2 ─► espera 2s ─► …
  con jitter: 0.5±0.25s, 1±0.25s, 2±0.25s…  (clientes desincronizados)

Muchos SDKs ya reintentan solos (el de Anthropic y el de OpenAI lo hacen por defecto 2 veces con backoff y respetan Retry-After). Tu capa añade las decisiones de negocio: cuántos reintentos, qué hacer si se agotan y si conviene cambiar de proveedor.

3 · Ejemplo mínimo

Un decorador de reintentos con backoff exponencial y jitter, independiente del proveedor. Es el ladrillo que envolverás alrededor de cualquier llamada.

ejemplos/retry_minimo.py
# retry_minimo.py — reintentos con backoff exponencial + jitter.
from __future__ import annotations

import random
import time
from collections.abc import Callable, Iterator
from contextlib import contextmanager
from typing import TypeVar

T = TypeVar("T")


class TransientError(Exception):
    """Error temporal: merece la pena reintentar (timeout, 429, 5xx)."""


class PermanentError(Exception):
    """Error definitivo: reintentar no ayuda (400, 401, contexto excedido)."""


@contextmanager
def retry(
    *,
    max_attempts: int = 4,
    base: float = 0.5,
    cap: float = 8.0,
    jitter: float = 0.25,
) -> Iterator[Callable[[Exception], None]]:
    """Reintenta un bloque solo si lanza TransientError."""
    def attempt() -> Iterator[None]:
        for n in range(max_attempts):
            try:
                yield
                return
            except TransientError:
                if n == max_attempts - 1:
                    raise                     # se agotaron los intentos
                wait = min(base * (2 ** n), cap) + random.uniform(0, jitter)
                print(f"  reintento {n + 1}/{max_attempts - 1}: espero {wait:.2f}s")
                time.sleep(wait)
    yield attempt().__next__


# Uso: simulamos una llamada que falla las dos primeras veces.
calls = {"n": 0}


def flaky_call() -> str:
    calls["n"] += 1
    if calls["n"] < 3:
        raise TransientError("429 rate limit simulado")
    return "respuesta del modelo"


with retry() as retrying:
    retrying(None)  # arranca el generador interno
    result = flaky_call()
    print(result)

Salida esperada:

  reintento 1/3: espero 0.61s
  reintento 2/3: espero 1.12s
respuesta del modelo

El ejemplo del contextmanager es didáctico pero enrevesado. En producción, un simple for con try/except se lee mejor (lo verás en el ejemplo real). La idea clave —solo se reintenta lo transitorio y la espera crece con jitter— es la misma.

4 · Ejemplo real

En el Copiloto definimos un contrato LLMClient y un adaptador de Ollama. El resto del código no sabe que existe Ollama. Añadimos reintentos clasificando errores y parseando el Retry-After cuando lo haya.

src/copiloto/llm.py — contrato y adaptador local
# src/copiloto/llm.py
from __future__ import annotations

import random
import time
from typing import Protocol

from ollama import Client, ResponseError


class LLMClient(Protocol):
    """Contrato mínimo: cualquier proveedor debe poder generar una respuesta."""

    def complete(self, messages: list[dict[str, str]], *, model: str) -> str: ...


class TransientError(Exception):
    def __init__(self, message: str, retry_after: float | None = None) -> None:
        super().__init__(message)
        self.retry_after = retry_after


class PermanentError(Exception):
    pass


class OllamaClient:
    """Adaptador local. Traduce errores de Ollama a nuestra taxonomía."""

    def __init__(self, host: str = "http://localhost:11434", timeout: float = 30.0) -> None:
        self._client = Client(host=host, timeout=timeout)

    def complete(self, messages: list[dict[str, str]], *, model: str) -> str:
        try:
            response = self._client.chat(model=model, messages=messages)
            return response.message.content or ""
        except (ConnectionError, TimeoutError) as exc:
            raise TransientError(f"conexión/timeout: {exc}") from exc
        except ResponseError as exc:
            status = getattr(exc, "status_code", None)
            if status is not None and (status == 429 or 500 <= status < 600):
                # No hay Retry-After en local, pero el mismo patrón aplica en la nube.
                raise TransientError(f"servidor ocupado ({status})") from exc
            raise PermanentError(f"petición inválida: {exc}") from exc


def complete_with_retry(
    client: LLMClient,
    messages: list[dict[str, str]],
    *,
    model: str,
    max_attempts: int = 4,
) -> str:
    """Reintenta SOLO errores transitorios, con backoff exponencial + jitter."""
    last: Exception | None = None
    for n in range(max_attempts):
        try:
            return client.complete(messages, model=model)
        except PermanentError:
            raise                                    # nunca reintentamos lo definitivo
        except TransientError as exc:
            last = exc
            if n == max_attempts - 1:
                break
            # Si el proveedor dijo 'espera X', lo respetamos; si no, backoff + jitter.
            wait = exc.retry_after if exc.retry_after else min(0.5 * (2 ** n), 8.0)
            wait += random.uniform(0, 0.25)
            print(f"  transitorio: {exc}. Reintento {n + 1}/{max_attempts - 1} en {wait:.2f}s")
            time.sleep(wait)
    raise TransientError(f"se agotaron los reintentos: {last}")
src/copiloto/app.py — la app no conoce el proveedor
# src/copiloto/app.py
from copiloto.llm import OllamaClient, complete_with_retry

client = OllamaClient()   # cambiar a OpenAIClient no tocaría esta línea más allá del import

answer = complete_with_retry(
    client,
    [{"role": "user", "content": "Resume en una frase qué es tool calling."}],
    model="llama3.2",
)
print(answer)

Decisiones y porqués:

  • Protocol, no herencia: cualquier clase con complete(...) cumple el contrato. Es structural typing: flexible y sin acoplar.
  • Traducir errores en el adaptador: el resto del sistema solo conoce TransientError y PermanentError. Añadir un proveedor no cambia la política de reintentos.
  • retry_after: si el proveedor indica cuándo reintentar, manda él; si no, aplicamos nuestro backoff.
  • Jitter siempre: evita que muchos procesos reintenten en el mismo instante (efecto thundering herd).
  • Reintentos acotados: al agotarlos, lanzamos TransientError hacia arriba. Quien decide el fallback es la capa de negocio (reto de hoy).

Nube como alternativa: en OpenAIClient/AnthropicClient mapearías RateLimitError→TransientError, APIConnectionError/APITimeoutError→TransientError y AuthenticationError/BadRequestError→PermanentError. El resto del Copiloto no cambia nada.

6 · Errores habituales

Reintentar todo por igual

Mal 
# ❌ Trata igual un 401 (clave mal) que un 503 (servidor caído).
try:
    response = client.chat(model=model, messages=messages)
except Exception:
    time.sleep(1)
    response = client.chat(model=model, messages=messages)
Bien 
# ✅ Solo se reintenta lo transitorio; lo permanente se eleva tal cual.
try:
    response = client.chat(model=model, messages=messages)
except PermanentError:
    raise                       # 400/401: arregla el código o la clave
except TransientError as exc:
    return retry_with_backoff(exc)

Backoff sin jitter

Mal 
# ❌ Todos los clientes esperan exactamente lo mismo y reintentan a la vez.
time.sleep(2 ** n)   # 1s, 2s, 4s… sincronizados
Bien 
# ✅ Añade ruido aleatorio: los reintentos se reparten en el tiempo.
base = min(0.5 * (2 ** n), 8.0)
time.sleep(base + random.uniform(0, 0.25))

Clave de API en el repositorio

Mal 
# ❌ La clave viaja en Git y en cada captura de pantalla. Nunca.
client = OpenAI(api_key="sk-proj-abcd1234...")
Bien 
# ✅ Variables de entorno (.env fuera de Git; p. ej. con python-dotenv).
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

Reintentos infinitos que ocultan el problema

Mal 
# ❌ 'while True' convierte un fallo en un cuelgue y una factura.
while True:
    try:
        return client.complete(messages, model=model)
    except TransientError:
        pass
Bien 
# ✅ Nº máximo de intentos y, agotados, error explícito hacia arriba.
for n in range(MAX_ATTEMPTS):
    try:
        return client.complete(messages, model=model)
    except TransientError:
        if n == MAX_ATTEMPTS - 1:
            raise

7 · Ejercicio guiado

Objetivo: clasificar errores y reintentar únicamente los transitorios, con backoff y jitter, sobre una función fake que simula el proveedor.

  1. Paso 1 — Simula el proveedor. Guarda retry_lab.py: 
    import random
import time

class TransientError(Exception):
    def __init__(self, message, retry_after=None):
        super().__init__(message)
        self.retry_after = retry_after

class PermanentError(Exception):
    pass

FAILS = {"left": 3}

def fake_provider(messages, *, model):
    """Falla las 2 primeras veces con 429, luego responde bien."""
    if FAILS["left"] > 0:
        FAILS["left"] -= 1
        raise TransientError("429 rate limit", retry_after=0.2)
    return "OK: respuesta del modelo"

def complete(client, messages, *, model, max_attempts=4):
    for n in range(max_attempts):
        try:
            return client(messages, model=model)
        except PermanentError:
            raise
        except TransientError as exc:
            if n == max_attempts - 1:
                raise
            wait = exc.retry_after if exc.retry_after else min(0.5 * (2 ** n), 8.0)
            wait += random.uniform(0, 0.25)
            print(f"reintento {n + 1} en {wait:.2f}s")
            time.sleep(wait)

print(complete(fake_provider, [{"role": "user", "content": "hola"}], model="fake"))
  2. Paso 2 — Ejecuta. 
    uv run retry_lab.py

    Resultado esperado: dos líneas de reintento con esperas cercanas a 0.2 s (se respeta el retry_after) y, al final, OK: respuesta del modelo.

  3. Paso 3 — Prueba lo permanente. Haz que fake_provider lance PermanentError("401 unauth") siempre. Comprueba que no hay reintentos: el error sube al instante.
  4. Paso 4 — Agota los intentos. Pon FAILS["left"] = 10 y max_attempts=4. Verifica que, tras el último intento, se lanza el error en vez de quedarse en bucle.
  5. Paso 5 (verificación): imprime en cada reintento cuántos intentos quedan y qué tipo de error fue. Debes poder leer la secuencia completa y saber por qué se reintentó (o no) cada vez.

8 · Reto

🎯 Cadena de proveedores con fallback

Implementa en el Copiloto una cadena de proveedores: primero intenta Ollama local; si agota los reintentos transitorios, pasa a OpenAI; si también falla, a Anthropic; y si todos fallan, lanza un error claro. La app debe seguir llamando al mismo contrato LLMClient, sin enterarse de la cadena.

Pista: crea un FallbackClient que guarde una lista de clientes y complete los pruebe en orden, capturando TransientError y pasando al siguiente. No captures PermanentError (un 401 en el primero no se arregla con el segundo salvo que sean claves distintas). Registra en un log qué proveedor sirvió cada respuesta: sin esa traza, no sabrás si el fallback funciona.

9 · Resumen

  • Local (Ollama) y nube (OpenAI/Anthropic) son compromisos de coste, privacidad, calidad y latencia, no bandos.
  • Una interfaz común (LLMClient) con adaptadores por proveedor evita acoplar tu app a un SDK.
  • Clasifica siempre: transitorio (429, 5xx, timeout, conexión) → reintenta; permanente (400, 401, 404, contexto excedido) → no reintentes.
  • Reintenta con backoff exponencial + jitter y respeta el Retry-After cuando exista.
  • Reintentos acotados: al agotarlos, error explícito o fallback de proveedor.
  • Las claves van en variables de entorno, nunca en el repositorio.

10 · Preguntas frecuentes

Si los SDKs ya reintentan solos, ¿para qué mi capa?

Los SDKs gestionan reintentos de red a bajo nivel, pero tu capa decide política de negocio: cuántos intentos como máximo, qué hacer al agotarlos, si cambiar de proveedor, si degradar a una respuesta de caché o mostrar un mensaje al usuario. Además, la capa de negocio unifica proveedores con errores distintos.

¿Local o nube?

Empieza en local: sin clave, sin coste, reproducible, y el núcleo del curso funciona así. Sube a la nube cuando necesites más calidad o cuando tu hardware no dé. Lo importante es no acoplarte: con una interfaz común, cambiar es configurar, no reescribir.

¿Cuántos reintentos pongo?

Pocos: 3-4 intentos cubren casi todos los fallos transitorios de la red y de un proveedor con hipo. Más allá, el proveedor está caído de verdad y el fallback o el error explícito son mejores que seguir insistiendo. Ajusta con datos, no por intuición.

¿Por qué el jitter importa tanto?

Sin jitter, si tienes 100 instancias y todas reciben un 429 al mismo tiempo, todas reintentan en el mismo instante y generan otro pico que vuelve a ser 429. El aleatorio desincroniza los reintentos y el sistema converge en vez de oscilar. Es un detalle barato con un efecto enorme.

¿Qué hago con un error de contexto excedido?

No reintentes: el prompt es demasiado largo. Reduce el contexto (recorta mensajes antiguos, resume, quita ejemplos) o usa un modelo con más ventana. Es un error determinista con una causa determinista: tu prompt. En el módulo 4 verás cómo gestionar el contexto de forma sistemática.
