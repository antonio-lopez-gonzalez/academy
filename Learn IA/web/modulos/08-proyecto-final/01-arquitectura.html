Arquitectura del Copiloto

Módulo 8 · Proyecto final: Copiloto 🕐 40 minutos

1 · Introducción

Llevas siete módulos aprendiendo las piezas por separado: llamadas al modelo, prompting, embeddings, RAG, tools, agentes, MCP y evals. Ahora las juntamos todas en un único programa que funciona: el Copiloto, un asistente que responde sobre los cursos de esta Academy, con RAG real, con herramientas y con evaluación.

Es tentador empezar a escribir código directamente: un script que lee HTML, embebe, busca, llama al modelo y ya está. Funciona… hasta que quieres cambiar de proveedor, añadir una tool, medir la calidad o ejecutar los tests. Entonces descubres que todo está enredado en una sola función de trescientas líneas y que cada cambio rompe otra cosa.

Esta lección hace lo contrario: diseña la estructura antes de escribir los detalles. Definimos seis capas (llm, index, rag, tools, agent, evals), decidimos qué contrato expone cada una, dónde vive la configuración y cómo se organiza src/copiloto/. En las tres lecciones siguientes llenaremos cada capa con código real.

¿Por qué existe esta lección? Porque la diferencia entre un script de demo y un producto con IA que puedes mantener está en la arquitectura, no en el prompt. Separar capas es lo que te permitirá cambiar Ollama por OpenAI sin tocar el agente, añadir una tool sin tocar el RAG y ejecutar las evals sin levantar la CLI.

2 · Teoría

La analogía: un edificio con pisos independientes

Piensa en un edificio. Cada planta tiene una función clara (garaje, oficinas, salas de reuniones, azotea) y en cada una trabajan personas distintas. Lo importante es que cada planta solo se comunica con la de al lado a través de un hueco regulado: el ascensor y las escaleras. Si la planta 3 tuviera que hablar directamente con el garaje por un conducto improvisado, cualquier reforma sería un caos. Las capas del Copiloto son esos pisos y los contratos son los ascensores: interfaces pequeñas y estables por donde pasa la información.

Seis capas, una responsabilidad cada una

El Copiloto se divide en seis capas. Cada una hace una sola cosa y expone un contrato claro al resto:

   ┌─────────────────────────────────────────────────────────┐
   │  agent   │ bucle pensar→actuar→observar + memoria         │
   ├──────────┼────────────────────────────────────────────────┤
   │  tools   │ buscar lecciones · abrir módulo · progreso     │
   ├──────────┼────────────────────────────────────────────────┤
   │  rag     │ recuperar fragmentos + construir contexto      │
   ├──────────┼────────────────────────────────────────────────┤
   │  index   │ ingesta → chunking → embeddings → vector store │
   ├──────────┼────────────────────────────────────────────────┤
   │  llm     │ un contrato, varios proveedores (local/nube)   │
   └──────────┴────────────────────────────────────────────────┘
                evals  →  mide todas las capas por encima
CapaResponsabilidadDepende de
llm.pyHablar con un modelo: completar y devolver JSON.Nada (hoja)
index.pyIngerir, trocear, embeber y guardar vectores.llm (embeddings)
rag.pyRecuperar fragmentos y montar el contexto citable.index, llm
tools.pyExponer acciones tipadas al agente.rag, index
agent.pyOrquestar el bucle y la memoria de conversación.llm, tools
evals.pyEjecutar el dataset y medir calidad.Todas

Fíjate en la dirección de las dependencias: de abajo hacia arriba. llm no sabe que existe rag; rag no sabe que existe agent. Esta regla —depender solo hacia «abajo»— es lo que evita los imports circulares y lo que hace que puedas probar cada capa por separado.

Contratos: interfaces pequeñas, implementaciones intercambiables

Un contrato es una promesa: «cualquier cosa que cumpla esto puede sustituirme». En Python se escribe con typing.Protocol: no hace falta heredar, solo tener los métodos con la firma correcta (structural typing). El contrato central del Copiloto es el del modelo:

class LLM(Protocol):
    def complete(self, messages: list[dict[str, str]], **opts) -> str: ...
    def json(self, messages: list[dict[str, str]], schema: dict) -> dict: ...

Con ese contrato, OllamaLLM (local), OpenAILLM (nube) y FakeLLM (tests) son intercambiables. El resto del código no sabe cuál está usando; solo pide «un objeto que cumpla LLM». Esta es exactamente la inversión de dependencias: las capas altas dependen de abstracciones, no de proveedores concretos.

Empieza con un Protocol y una sola implementación. No crees interfaces «por si acaso»: el Protocol se gana su sitio cuando aparece la segunda implementación (el test FakeLLM ya cuenta como la primera).

Configuración: una sola fuente de verdad

Los valores que cambian entre entornos —modelo, ruta de la base, top_k— no deben estar repartidos por el código. Van en un objeto Settings creado con pydantic-settings, que lee de variables de entorno y de un archivo .env (nunca versionado). Así el mismo código corre en tu portátil con Ollama y en el servidor con OpenAI cambiando solo el entorno.

Nunca metas claves de API en el repositorio. .env va en .gitignore; el código solo lee variables de entorno. Si una clave acaba en un commit, considérala comprometida: rótala.

De la capa al archivo: src/copiloto/

El proyecto es un paquete Python instalable con uv. La estructura layout src (el código dentro de src/) evita que importes el paquete por accidente desde la raíz y obliga a instalarlo, lo que hace los tests más honestos:

  proyectos/copiloto/
  ├── pyproject.toml          ← dependencias + entry point de la CLI
  ├── README.md
  ├── .env.example            ← plantilla SIN secretos
  └── src/copiloto/

El entry point: cómo copiloto llega a la terminal

Gracias a [project.scripts] en pyproject.toml, instalar el paquete crea un comando copiloto que apunta a una función de cli.py. Es la forma idiomática de exponer una CLI: sin if __name__ == "__main__" repartidos ni scripts sueltos.

[project.scripts]
copiloto = "copiloto.cli:app"

Y se ejecuta siempre con uv run, que garantiza el entorno correcto:

uv run copiloto index        # construye el índice
uv run copiloto ask "¿Qué es RAG?"   # una pregunta con citas

Modelo vs. código: dónde está la ingeniería

En el Copiloto, solo dos capas contienen inferencia (probabilística): llm y la parte de generación de rag/agent. Todo lo demás —ingesta, chunking, búsqueda, formato del contexto, ejecución de tools, métricas— es código determinista que puedes testear con asserts normales. Diseñar la frontera entre ambas es el objetivo de esta lección: cuanto más puedas mover hacia el lado determinista, más fácil será depurar y medir.

3 · Ejemplo mínimo

El contrato central en veinte líneas: una capa alta que depende de un Protocol, no de un proveedor. Cambiamos la implementación sin tocar el código de arriba. No hay red, no hay coste, no hay LLM de verdad: solo la forma de la arquitectura.

capas_minimo.py
# capas_minimo.py — el contrato que separa "quién responde" de "cómo se responde".
from typing import Protocol


class LLM(Protocol):
    """Cualquier proveedor de modelo debe cumplir esta firma."""
    def complete(self, messages: list[dict], **opts) -> str: ...


class FakeLLM:
    """Implementación determinista: tests rápidos y sin red."""
    def complete(self, messages, **opts) -> str:
        question = messages[-1]["content"]
        return f"(respuesta de prueba a: {question})"


def answer(llm: LLM, question: str) -> str:
    """La capa alta no sabe qué proveedor hay detrás: solo que cumple LLM."""
    return llm.complete([{"role": "user", "content": question}])


print(answer(FakeLLM(), "¿Qué es un token?"))

Salida esperada:

(respuesta de prueba a: ¿Qué es un token?)

Lo esencial: answer() recibe el proveedor por parámetro (inyección de dependencias). No importa OllamaLLM ni lo instancia dentro. Mañana pasas OllamaLLM() o OpenAILLM() y answer() no cambia ni una línea. Eso es la arquitectura.

"""Configuración única del Copiloto: nada de valores mágicos repartidos."""
from pathlib import Path

from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    # Lee de variables de entorno con prefijo COPILOTO_ o de .env (sin versionar).
    model_config = SettingsConfigDict(env_prefix="COPILOTO_", env_file=".env", extra="ignore")

    llm_provider: str = "ollama"                            # ollama | openai | anthropic
    llm_model: str = "llama3.2"
    embed_model: str = "intfloat/multilingual-e5-small"
    db_path: Path = Path(".data/copiloto.db")               # índice persistente (sqlite-vec)
    academy_root: Path = Path("../..")                      # carpeta Academy/ con los cursos
    top_k: int = 4                                          # fragmentos recuperados por consulta
    max_iterations: int = 6                                 # límite de vueltas del agente


settings = Settings()

Un único settings se importa desde cualquier capa. Cambiar COPILOTO_LLM_PROVIDER=openai en el entorno cambia todo el sistema sin tocar el código.

proyectos/copiloto/src/copiloto/llm.py
"""Capa llm: un contrato y varias implementaciones intercambiables."""
from typing import Protocol

import httpx

from copiloto.config import settings


class LLM(Protocol):
    """Contrato mínimo que todo proveedor debe cumplir."""
    def complete(self, messages: list[dict[str, str]], **opts) -> str: ...
    def json(self, messages: list[dict[str, str]], schema: dict) -> dict: ...


class OllamaLLM:
    """Proveedor local por defecto: sin API key, sin coste por token."""

    def __init__(self, model: str = settings.llm_model,
                 base_url: str = "http://localhost:11434") -> None:
        self.model = model
        self.base_url = base_url

    def complete(self, messages: list[dict[str, str]], **opts) -> str:
        resp = httpx.post(
            f"{self.base_url}/api/chat",
            json={"model": self.model, "messages": messages, "stream": False},
            timeout=120,
        )
        resp.raise_for_status()
        return resp.json()["message"]["content"]

    def json(self, messages: list[dict[str, str]], schema: dict) -> dict:
        # Ollama admite formato JSON estructurado; aquí delegamos en pydantic al validar.
        resp = httpx.post(
            f"{self.base_url}/api/chat",
            json={"model": self.model, "messages": messages,
                  "format": "json", "stream": False},
            timeout=120,
        )
        resp.raise_for_status()
        import json
        return json.loads(resp.json()["message"]["content"])


class OpenAILLM:
    """Alternativa en la nube. Misma firma: el resto del código no cambia."""

    def __init__(self, model: str = "gpt-4o-mini") -> None:
        self.model = model

    def complete(self, messages: list[dict[str, str]], **opts) -> str:
        from openai import OpenAI                       # import perezoso: solo si se usa
        client = OpenAI()                               # lee OPENAI_API_KEY del entorno
        out = client.chat.completions.create(model=self.model, messages=messages)
        return out.choices[0].message.content or ""

    def json(self, messages: list[dict[str, str]], schema: dict) -> dict:
        from openai import OpenAI
        import json
        client = OpenAI()
        out = client.chat.completions.create(
            model=self.model, messages=messages,
            response_format={"type": "json_object"},
        )
        return json.loads(out.choices[0].message.content or "{}")


def get_llm() -> LLM:
    """Fábrica: elige la implementación según la configuración."""
    providers = {"ollama": OllamaLLM, "openai": OpenAILLM}
    try:
        return providers[settings.llm_provider]()
    except KeyError as exc:
        raise ValueError(f"Proveedor desconocido: {settings.llm_provider}") from exc

Decisiones y porqués:

  • Un Protocol, no una clase base: las implementaciones no heredan de nada del Copiloto; solo cumplen la forma. Menos acoplamiento y más fácil de mockear.
  • get_llm() lee de settings: el resto del código nunca menciona «Ollama». Cambiar de proveedor es cambiar una variable de entorno.
  • Import perezoso de openai: quien corre en local no necesita el SDK instalado ni la clave; el import solo ocurre si el proveedor es openai.
  • json() separado de complete(): la capa de arriba pide «responde con este esquema» sin saber cómo lo logra cada proveedor (structured output nativo, formato JSON o prompt).

Esta lección es arquitectura: los cuerpos de index.py, rag.py, tools.py, agent.py y evals.py se implementan en las lecciones 02, 03 y 04. Aquí solo fijamos los límites entre ellos.

6 · Errores habituales

6.1. Acoplar la lógica al proveedor concreto

Si el agente conoce a Ollama, no puedes usar OpenAI ni testear sin red.

Incorrecto
# ❌ El agente decide el proveedor y construye la URL a mano.
import httpx

def ask(q: str) -> str:
    r = httpx.post("http://localhost:11434/api/chat",
                   json={"model": "llama3.2", "messages": [{"role": "user", "content": q}]})
    return r.json()["message"]["content"]
Correcto
# ✅ El agente depende del contrato; el proveedor se inyecta.
from copiloto.llm import LLM, get_llm

def ask(q: str, llm: LLM | None = None) -> str:
    llm = llm or get_llm()                  # Ollama, OpenAI o FakeLLM: da igual
    return llm.complete([{"role": "user", "content": q}])

6.2. Valores de configuración repartidos por el código

Cambiar el modelo o la base vectorial no debería ser un find & replace por todo el proyecto.

Incorrecto
# ❌ Cada módulo escribe sus propios valores.
model = "llama3.2"                          # en llm.py
db = ".data/copiloto.db"                     # en index.py
k = 4                                        # en rag.py
Correcto
# ✅ Todos leen del mismo objeto de configuración.
from copiloto.config import settings

model, db, k = settings.llm_model, settings.db_path, settings.top_k

6.3. Importar hacia «arriba» y crear ciclos

Cuando rag importa del agent y el agent del rag, Python lanza ImportError o, peor, ocurre a veces sí y a veces no.

Incorrecto
# ❌ rag.py importa agent (capa superior) -> ciclo.
from copiloto.agent import run_agent    # agent.py ya importa rag -> ImportError
Correcto
# ✅ Las capas bajas solo exponen datos; nunca llaman hacia arriba.
# rag.py no conoce al agente: devuelve fragmentos y ya.
def retrieve(question: str, k: int = 4) -> list[Fragment]: ...

7 · Ejercicio guiado

Objetivo: crear el esqueleto real de proyectos/copiloto/ con uv, la configuración y el contrato del modelo, y comprobar con un test que la inyección de dependencias funciona. Al terminar tendrás las cimientos de las tres lecciones siguientes.

  1. Paso 1 — crea el paquete con uv. 
    uv init --package copiloto
cd copiloto
uv add pydantic pydantic-settings httpx typer rich beautifulsoup4 fastembed sqlite-vec
uv add --dev pytest ruff mypy

    Esperado: uv crea pyproject.toml, src/copiloto/__init__.py y el layout src/.

  2. Paso 2 — añade el entry point. Edita pyproject.toml y añade el comando de la CLI: 
    [project.scripts]
copiloto = "copiloto.cli:app"

    Después crea cli.py con un mínimo viable:

    # src/copiloto/cli.py — esqueleto de la CLI (se completa en la lección 04).
import typer

app = typer.Typer(help="Copiloto de la Academy.")

@app.command()
def version() -> None:
    """Muestra la versión del Copiloto."""
    typer.echo("copiloto 0.1.0")

    Comprueba: uv run copiloto version debe imprimir copiloto 0.1.0.

  3. Paso 3 — crea config.py. Copia el objeto Settings del ejemplo real. Añade un .env.example con las variables: 
    # .env.example — plantilla sin secretos. Cópiala a .env y ajústala.
COPILOTO_LLM_PROVIDER=ollama
COPILOTO_LLM_MODEL=llama3.2
COPILOTO_TOP_K=4

    Añade .env y .data/ a .gitignore.

  4. Paso 4 — crea llm.py. Copia el Protocol y las implementaciones del ejemplo real. Al menos OllamaLLM y el FakeLLM para tests.

  5. Paso 5 — verifica la inyección de dependencias con un test. 
    # tests/test_llm.py — la capa alta no depende de un proveedor concreto.
from copiloto.llm import LLM


class FakeLLM:
    def complete(self, messages, **opts) -> str:
        return "eco: " + messages[-1]["content"]


def ask(llm: LLM, q: str) -> str:
    return llm.complete([{"role": "user", "content": q}])


def test_fake_llm_cumple_el_contrato():
    assert ask(FakeLLM(), "hola") == "eco: hola"

    Ejecuta uv run pytest -q. Esperado: 1 passed, sin red y sin coste.

  6. Paso 6 — el comprobador de entorno. Añade un comando que muestre la configuración activa: 
    # src/copiloto/cli.py (añadir al app)
from copiloto.config import settings

@app.command()
def doctor() -> None:
    """Muestra la configuración activa del Copiloto."""
    typer.echo(f"provider={settings.llm_provider} model={settings.llm_model}")
    typer.echo(f"db={settings.db_path} top_k={settings.top_k}")

    Resultado esperado: uv run copiloto doctor imprime los valores por defecto; si defines COPILOTO_TOP_K=8, el mismo comando muestra top_k=8 sin recompilar nada.

Ese comando doctor vale oro en producción: cuando algo raro pasa, lo primero es confirmar qué configuración está activa. Casi un tercio de los «no funciona como en local» son variables de entorno distintas.

8 · Reto

🎯 Un registro de proveedores con descubrimiento y una ADR

Haz que el Copiloto sea extensible a nuevos proveedores sin editar llm.py, y documenta la decisión como un ingeniero senior. Requisitos:

  • Implementa un registro de proveedores: un decorador @register_provider("nombre") que asocie un nombre a la clase, de modo que get_llm() busque en el registro en lugar de un dict fijo.
  • Añade un tercer proveedor (por ejemplo, un EchoLLM o un proveedor vía Anthropic) y regístralo desde otro módulo, sin tocar llm.py.
  • Escribe una ADR (Architecture Decision Record) de una página en docs/adr/0001-provider-registry.md con: contexto, decisión, alternativas y consecuencias (incluido el coste de mantener el registro frente a un dict simple).
  • Un test que compruebe que el nuevo proveedor se descubre solo con importar su módulo.

Pista: guarda el registro en un dict a nivel de módulo y que el decorador lo rellene; el «descubrimiento» en Python suele significar «importar el paquete». Reflexiona en la ADR sobre el momento correcto para introducir este patrón (¿lo necesitas con dos proveedores o con diez?) y no lo apliques por moda: justifica con datos cuántos proveedores esperas de verdad.

9 · Resumen

  • Seis capas con una responsabilidad cada una: llm, index, rag, tools, agent, evals.
  • Las dependencias van hacia abajo: las capas bajas no conocen a las altas → sin ciclos y testeables por separado.
  • Los contratos (Protocol) hacen intercambiables los proveedores: el resto del código no sabe si hay Ollama o OpenAI detrás.
  • La configuración vive en un único Settings (pydantic-settings) que lee de entorno y .env; jamás secretos en el repo.
  • El paquete usa layout src/ y se expone como CLI con [project.scripts]: comando copiloto, siempre uv run.
  • La ingeniería se concentra en la frontera entre lo probabilístico (inferencia) y lo determinista (tu código).

10 · Preguntas frecuentes

¿No es sobreingeniería separar en seis capas para un copiloto?

Seis archivos pequeños no son sobreingeniería; un archivo de mil líneas sí es deuda técnica. Cada capa se justifica porque cambia por razones distintas: el proveedor de modelos cambia, el corpus cambia, las tools cambian. Si todo vive junto, cada cambio arrastra a los demás. Y no hace falta implementarlas todas el primer día: empieza por llm, index y rag, y añade el resto cuando el código lo pida.

¿Por qué Protocol y no una clase base abstracta (ABC)?

Con Protocol las implementaciones no heredan de nada del Copiloto: solo cumplen la forma (structural typing). Eso reduce el acoplamiento y permite mocks triviales en los tests. Una ABC impone herencia y jerarquía, útil si compartes código común, pero innecesaria cuando solo quieres garantizar una firma. Regla: herencia si compartes implementación, Protocol si solo compartes contrato.

¿Dónde guardo las claves de API si el núcleo es local?

En un archivo .env que nunca se versiona (está en .gitignore), leído por pydantic-settings. El repositorio solo incluye .env.example con valores de ejemplo sin secretos. Ollama en local no necesita clave; solo los proveedores en la nube la usan, y el import perezoso garantiza que quien corre en local no la necesita.

¿Puedo saltarme la capa index y hacer RAG sin vectores?

Sí, para un corpus diminuto: prompt stuffing (meter todo el texto en el prompt) funciona con una o dos lecciones. Pero el Copiloto indexa todas las lecciones de todos los cursos, así que necesitas recuperación. La capa index es lo que hace que el sistema escale de un curso a decenas sin que el prompt crezca sin control. La decisión la formalizamos en la lección 02.

¿Tests con FakeLLM no falsean la realidad?

No: cubren la capa determinista (que el contexto se monta bien, que el bucle respeta el límite, que las tools devuelven lo esperado). La calidad de la respuesta del modelo no se testea con asserts, se mide con evals (lección 04). Separar ambas formas de verificación es justamente el motivo de tener el contrato: el test usa un FakeLLM determinista y las evals usan el modelo real.
