Evals y despliegue

Módulo 8 · Proyecto final: Copiloto 🕐 45 minutos

1 · Introducción

El Copiloto ya responde con RAG, usa tools y tiene memoria. Pero «funciona» es una opinión hasta que lo mides: ¿acierta las preguntas del corpus?, ¿se abstiene cuando debe?, ¿cuánto tarda?, ¿cuánto cuesta?, ¿sigue funcionando después de cambiar el prompt o el modelo? Esta lección cierra el curso poniendo números a esas preguntas y dejando el Copiloto listo para usar: por CLI y por una API mínima.

Dos piezas. La primera es la evaluación: un dataset de preguntas reales con respuesta esperada, una batería de comprobaciones (unas deterministas, otras con juez) y un pass rate que se convierte en puerta de calidad: si baja, la versión no sale. La segunda es el despliegue: empaquetar todo en una CLI cómoda (copiloto) y una API que un front o un script puedan llamar, con control de coste y latencia.

¿Por qué existe esta lección? Porque el curso entero ha repetido una idea: sin medir, no hay ingeniería. Esta es donde se convierte en hábito. Un Copiloto con evals es un proyecto que puedes mejorar con confianza; uno sin evals es una demo que da miedo tocar.

2 · Teoría

La analogía: la revisión técnica antes de la ITV

Un coche no sale a la carretera porque «parece que va bien», sino porque pasa una revisión con puntos concretos: frenos, luces, emisiones. Si algo falla, no pasa. Las evals son tu revisión: una lista de casos concretos con su criterio de éxito. Y como el coche cambia (ruedas nuevas, otra ECU), la revisión se repite cada vez, no una sola. Un cambio que «no rompe nada a ojo» suele romper algo en la revisión.

El dataset: preguntas reales con respuesta esperada

El dataset del Copiloto es una lista de casos, en JSONL (una línea por caso). Cada caso describe una pregunta y qué debe pasar:

proyectos/copiloto/evals/dataset.jsonl
{"id": "q001", "question": "¿Qué es la fidelidad en un RAG?", "expect_lesson": "03-citas-y-fidelidad", "expect_abstain": false, "tags": ["rag"]}
{"id": "q002", "question": "¿Cómo se trocea un documento para indexarlo?", "expect_lesson": "03-chunking", "expect_abstain": false, "tags": ["chunking"]}
{"id": "q003", "question": "¿Qué tools tiene el Copiloto?", "expect_lesson": "03-tools-y-agente", "expect_abstain": false, "tags": ["agent"]}
{"id": "q004", "question": "¿Cuánto cuesta el plan Premium de OpenAI?", "expect_lesson": null, "expect_abstain": true, "tags": ["out-of-corpus"]}
{"id": "q005", "question": "¿Quién ganó el mundial de 1998?", "expect_lesson": null, "expect_abstain": true, "tags": ["out-of-corpus"]}

Un buen dataset mezcla tres tipos de caso, y todos importan:

Tipo de casoQué compruebaEjemplo
Dentro del corpusQue recupera y cita la lección correcta«¿Qué es un embedding?»
Fuera del corpusQue se abstiene en vez de inventar«¿Capital de Australia?»
Ambiguo / multi-pasoQue el agente elige bien la tool o reformula«¿Qué lecciones tiene el módulo 5?»

El dataset no se escribe de una vez: crece. Cada vez que un alumno (o tú) hace una pregunta que el Copiloto responde mal, esa pregunta entra al dataset como caso de regresión. Así el sistema no vuelve a fallar dos veces en lo mismo.

Dos tipos de comprobación: determinista y juez

Determinista (código)Juez (LLM)
Qué mideAbstención, lección citada, citas en rango, formatoFidelidad, relevancia, corrección «blanda»
CosteCero (sin inferencia)Una llamada extra por caso
FiabilidadAlta y reproducibleMedia; hay que calibrarlo (módulo 7)
CuándoSiempre, en cada ejecución y en CIAntes de un release o al ajustar prompts

La regla: maximiza lo determinista. «¿Se abstuvo?» o «¿citó la lección esperada?» son comprobaciones exactas, gratis y sin sesgo. El juez se reserva para lo que el código no puede decidir: si una respuesta fundamentada es fiel al contexto.

Métricas que importan

  • Pass rate: fracción de casos que cumplen todas sus comprobaciones. Es la métrica de cabecera.
  • Abstention accuracy: cuántas preguntas fuera del corpus se abstienen de verdad (y cuántas del corpus se abstienen por error).
  • Citation accuracy: fracción de respuestas que citan la lección esperada.
  • Latencia p50/p95 y tokens/coste por caso.

No optimices una métrica en solitario: bajar la latencia recortando contexto suele subir la alucinación. Mira siempre el cuadro completo.

La puerta de calidad (regression gate)

El valor real de las evals aparece cuando se convierten en un umbral automático: si el pass rate cae por debajo de, digamos, 0,9, el proceso sale con código de error y el cambio no se despliega. En CI, esto es una línea:

uv run copiloto eval --dataset evals/dataset.jsonl --min-pass-rate 0.9
# → exit 0 si pasa; exit 1 si baja del umbral (bloquea el merge)

Un pass rate del 100 % en un dataset pequeño no significa que el sistema sea perfecto: significa que tu dataset aún no cubre los casos difíciles. Un dataset que crece y un pass rate del 90 % valen más que un dataset trivial con 100 %.

Despliegue: CLI y API mínima

El Copiloto se usa de dos formas. La CLI (copiloto) para uso interactivo y para las tareas internas (indexar, evaluar). La API mínima para que un front o un script lo consuman por HTTP. Ambas comparten las mismas capas; solo cambia la puerta de entrada:

   web/CLI ─┐                     ┌─ index   (construir el índice)
            ├─► copiloto (core) ─┤─ rag     (responder con citas)
   HTTP  ───┘                     ├─ tools   (acciones)
                                  └─ agent   (bucle + memoria)

   CLI  : uv run copiloto ask "…"      (typer + rich)
   API  : uv run uvicorn copiloto.api:app   (FastAPI, /ask, /health)

Coste y latencia en producción

Local con Ollama, el coste por token es cero pero la latencia depende de tu máquina. En la nube, cada token de entrada y salida se paga, y el bucle del agente multiplica las llamadas. Tres controles básicos:

  1. Cache: guarda respuestas de preguntas idénticas (o casi, con caché semántica) para no repetir inferencia.
  2. Límites: max_iterations y presupuesto de tokens (lección 03).
  3. Medición: registra tokens, latencia y coste por petición; sin registro no puedes optimizar ni presupuestar.

3 · Ejemplo mínimo

Un evaluador sin LLM y sin coste: lee un dataset y aplica solo comprobaciones deterministas sobre respuestas ya generadas (que aquí simulamos). Es la parte de las evals que siempre puedes permitirte correr.

eval_minimo.py
# eval_minimo.py — checks deterministas sobre un dataset de evaluación.
import json
from pathlib import Path

ABSTENTION = "No lo sé con el contexto disponible."

# Casos de ejemplo (en el Copiloto vienen de evals/dataset.jsonl).
CASES = [
    {"id": "q001", "expect_lesson": "03-citas-y-fidelidad", "expect_abstain": False},
    {"id": "q004", "expect_lesson": None, "expect_abstain": True},
]

# Respuestas simuladas (en el Copiloto las produce copiloto.rag.answer).
RESULTS = {
    "q001": {"text": "La fidelidad es… [1]", "sources": [{"lesson": "03-citas-y-fidelidad"}]},
    "q004": {"text": ABSTENTION, "sources": []},
}


def check(case: dict, result: dict) -> list[str]:
    """Devuelve los problemas del caso (vacío = pasa)."""
    problems: list[str] = []
    abstained = result["text"].strip() == ABSTENTION
    if case["expect_abstain"] and not abstained:
        problems.append("debería haberse abstenido")
    if not case["expect_abstain"]:
        if abstained:
            problems.append("se abstuvo pero había respuesta")
        else:
            cited = {s["lesson"] for s in result["sources"]}
            if case["expect_lesson"] not in cited:
                problems.append(f"no cita la lección esperada: {case['expect_lesson']}")
    return problems


passed = 0
for case in CASES:
    problems = check(case, RESULTS[case["id"]])
    passed += not problems
    print(f"{case['id']}  {'OK ' if not problems else 'FAIL'}  {problems}")

print(f"pass rate: {passed}/{len(CASES)} = {passed / len(CASES):.0%}")

Salida esperada:

q001  OK    []
q004  OK    []
pass rate: 2/2 = 100%

Dos comprobaciones exactas, cero coste. El juez se añade encima para lo que el código no resuelve, pero esta batería es la que nunca se apaga.

4 · Ejemplo real

El Copiloto. Primero la capa evals.py con las comprobaciones deterministas, un juez opcional y una puerta de calidad. Después la CLI completa y una API mínima para producción.

proyectos/copiloto/src/copiloto/evals.py
"""Capa evals: mide la calidad del Copiloto y bloquea regresiones."""
from __future__ import annotations

import json
import time
from dataclasses import dataclass, field
from pathlib import Path

from pydantic import BaseModel

from copiloto.answer import ask                 # responde con citas y abstención
from copiloto.llm import get_llm

ABSTENTION = "No lo sé con el contexto disponible."


class Case(BaseModel):
    id: str
    question: str
    expect_lesson: str | None = None
    expect_abstain: bool = False
    tags: list[str] = field(default_factory=list)


@dataclass
class CaseResult:
    case: Case
    passed: bool
    problems: list[str]
    latency_ms: float


def load_dataset(path: Path) -> list[Case]:
    return [Case.model_validate_json(line)
            for line in path.read_text(encoding="utf-8").splitlines() if line.strip()]


def check(case: Case, answer) -> list[str]:
    """Comprobaciones deterministas: abstención, lección citada, citas válidas."""
    problems: list[str] = []
    abstained = answer.text.strip() == ABSTENTION
    if case.expect_abstain and not abstained:
        problems.append("debería abstenerse")
    if not case.expect_abstain:
        if abstained:
            problems.append("se abstuvo habiendo respuesta")
        else:
            cited = {s.lesson for s in answer.sources}
            if case.expect_lesson and case.expect_lesson not in cited:
                problems.append(f"no cita {case.expect_lesson}")
    return problems


def judge_faithfulness(question: str, answer_text: str, context: str) -> float:
    """Juez LLM (0-1): ¿se apoya la respuesta solo en el contexto? (módulo 7)."""
    prompt = (f"Contexto:\n{context}\n\nRespuesta:\n{answer_text}\n\n"
              "Puntúa 0-1 cuánto se apoya la respuesta en el contexto. "
              'Devuelve JSON: {"score": <número>}.')
    llm = get_llm()
    return float(llm.json([{"role": "user", "content": prompt}], {}).get("score", 0.0))


def run(dataset_path: Path, use_judge: bool = False) -> list[CaseResult]:
    results: list[CaseResult] = []
    for case in load_dataset(dataset_path):
        start = time.perf_counter()
        answer = ask(case.question)             # pipeline RAG real
        latency = (time.perf_counter() - start) * 1000
        problems = check(case, answer)
        if use_judge and not problems:
            score = judge_faithfulness(case.question, answer.text,
                                       "\n".join(f.text for f in answer.fragments))
            if score < 0.7:
                problems.append(f"fidelidad baja: {score:.2f}")
        results.append(CaseResult(case, not problems, problems, latency))
    return results


def report(results: list[CaseResult]) -> dict:
    passed = sum(r.passed for r in results)
    return {
        "total": len(results),
        "passed": passed,
        "pass_rate": passed / len(results) if results else 0.0,
        "p50_ms": sorted(r.latency_ms for r in results)[len(results) // 2] if results else 0.0,
        "failures": [{"id": r.case.id, "problems": r.problems}
                     for r in results if not r.passed],
    }
proyectos/copiloto/src/copiloto/cli.py
"""CLI del Copiloto: indexar, preguntar, conversar y evaluar."""
from pathlib import Path

import typer

from copiloto import evals
from copiloto.agent import run as run_agent
from copiloto.answer import ask
from copiloto.index import build_index

app = typer.Typer(help="Copiloto de la Academy: RAG + tools + evals.")


@app.command()
def index() -> None:
    """Reindexa los cursos y construye la base vectorial."""
    typer.echo(f"Indexados {build_index()} chunks.")


@app.command()
def ask_cmd(question: str, k: int = 4) -> None:
    """Responde una pregunta con citas a las lecciones."""
    answer = ask(question, k=k)
    typer.echo(answer.text)
    for source in answer.sources:
        typer.echo(f"  [{source.n}] {source.lesson} · {source.section}")


@app.command()
def agent() -> None:
    """Conversa con el Copiloto (con memoria entre turnos)."""
    from copiloto.agent import SYSTEM_PROMPT
    memory = [{"role": "system", "content": SYSTEM_PROMPT}]
    while (question := typer.prompt("Tú")) not in {"salir", "exit"}:
        reply, memory = run_agent(question, memory=memory)
        typer.echo(f"Copiloto: {reply}")


@app.command()
def eval(dataset: Path = Path("evals/dataset.jsonl"),
         min_pass_rate: float = 0.9, judge: bool = False) -> None:
    """Corre las evals y falla (exit 1) si baja del umbral (puerta de calidad)."""
    summary = evals.report(evals.run(dataset, use_judge=judge))
    typer.echo(f"pass rate: {summary['pass_rate']:.0%} ({summary['passed']}/{summary['total']})")
    typer.echo(f"latencia p50: {summary['p50_ms']:.0f} ms")
    for failure in summary["failures"]:
        typer.echo(f"  FAIL {failure['id']}: {failure['problems']}")
    if summary["pass_rate"] < min_pass_rate:
        raise typer.Exit(code=1)                # ← bloquea el release
proyectos/copiloto/src/copiloto/api.py
"""API mínima del Copiloto (FastAPI): un endpoint para preguntar."""
from fastapi import FastAPI
from pydantic import BaseModel

from copiloto.answer import ask

app = FastAPI(title="Copiloto API")


class AskRequest(BaseModel):
    question: str


class Source(BaseModel):
    n: int
    lesson: str
    section: str


class AskResponse(BaseModel):
    text: str
    sources: list[Source]
    answered: bool


@app.get("/health")
def health() -> dict:
    return {"status": "ok"}


@app.post("/ask", response_model=AskResponse)
def ask_endpoint(req: AskRequest) -> AskResponse:
    answer = ask(req.question)
    return AskResponse(text=answer.text,
                       sources=[Source(n=s.n, lesson=s.lesson, section=s.section)
                                for s in answer.sources],
                       answered=answer.answered)

  FAIL q022: ['debería abstenerse']
# exit code 0 (92% >= 90%) → el release pasa

Decisiones y porqués:

  • Comprobaciones deterministas primero: abstención, lección citada y citas válidas son exactas y gratis; el juez es opcional (--judge).
  • Puerta de calidad con typer.Exit(1): el mismo comando sirve en local y en CI; el exit code es lo que bloquea el despliegue.
  • Mismo core para CLI y API: ask() es el mismo en ambos; no hay dos implementaciones que se desincronicen.
  • API con modelos pydantic: la respuesta se valida y se documenta sola (FastAPI genera el schema).
  • Latencia medida por caso: sin números no puedes saber si una optimización mejora o empeora.

En producción, el índice se construye una vez en el despliegue (copiloto index), los secretos llegan por variables de entorno y el modelo puede seguir siendo Ollama en una máquina con GPU o un proveedor en la nube. El código es el mismo; solo cambia el entorno.

6 · Errores habituales

6.1. Optimizar sin dataset (a ojo)

Cambiar el prompt «porque suena mejor» sin medir es cómo se rompen sistemas que funcionaban.

Incorrecto
# ❌ "Este prompt parece mejor": nadie lo comprueba.
SYSTEM_PROMPT = "Responde de forma muy clara y detallada sobre los cursos…"
# … y a producción.
Correcto
# ✅ Se cambia el prompt y se corren las evals antes de fusionar.
uv run copiloto eval --dataset evals/dataset.jsonl --min-pass-rate 0.9

6.2. Medir solo con el juez

El juez introduce coste, latencia y ruido. Lo que el código puede comprobar, que lo compruebe el código.

Incorrecto
# ❌ Todo depende del juez, incluso la abstención (que es exacta).
passed = judge_faithfulness(q, answer, ctx) > 0.7
Correcto
# ✅ Primero lo determinista; el juez solo si el código no decide.
problems = check(case, answer)
if not problems and use_judge:
    problems = [] if judge_faithfulness(...) >= 0.7 else ["fidelidad baja"]

6.3. Reimplementar la lógica en el endpoint HTTP

Copiar el pipeline dentro de la API crea dos verdades que divergen en el primer cambio.

Incorrecto
# ❌ La API vuelve a montar el contexto y a llamar al modelo.
@app.post("/ask")
def ask_endpoint(req: AskRequest):
    frags = retrieve(req.question)          # ¿y las citas? ¿y la abstención?
    return {"text": chat(build(frags))}
Correcto
# ✅ La API solo adapta la entrada/salida del mismo core.
@app.post("/ask", response_model=AskResponse)
def ask_endpoint(req: AskRequest) -> AskResponse:
    answer = ask(req.question)              # mismo pipeline que la CLI
    return AskResponse(text=answer.text, sources=answer.sources, answered=answer.answered)

7 · Ejercicio guiado

Objetivo: crear un dataset de 10 casos, correr las evals contra el Copiloto real y obtener un pass rate con su puerta de calidad. Al terminar tendrás la última pieza del curso: medir y bloquear regresiones.

  1. Paso 1 — crea el dataset. Escribe evals/dataset.jsonl con 10 casos: 6 dentro del corpus (que citen una lección concreta), 3 fuera del corpus (que deban abstenerse) y 1 ambiguo. 
    {"id": "q001", "question": "¿Qué es un token?", "expect_lesson": "02-tokens-contexto-sampling", "expect_abstain": false, "tags": ["basico"]}
{"id": "q007", "question": "¿Cuál es la capital de Portugal?", "expect_lesson": null, "expect_abstain": true, "tags": ["out-of-corpus"]}

    Guarda también tus 5 preguntas del módulo 4 (lección 03) como casos: ya conoces su respuesta esperada.

  2. Paso 2 — implementa evals.py y el comando eval. Copia los módulos del ejemplo real. Asegúrate de que check() cubre los tres tipos de caso.

  3. Paso 3 — corre las evals. Con el índice construido: 
    uv run copiloto index
uv run copiloto eval --dataset evals/dataset.jsonl --min-pass-rate 0.9

    Esperado: un pass rate y, si hay fallos, el caso y el problema concretos. Ejecuta dos veces: el pass rate debe ser estable (si fluctúa mucho, hay casos ambiguos o falta determinismo).

  4. Paso 4 — arregla un fallo y vuelve a medir. Toma una pregunta fallida. Mira la traza de recuperación (ask --no-llm): ¿el fragmento correcto estaba en el top-k? Si no, es un problema de chunking/index; si estaba, es del prompt. Cambia una sola cosa y vuelve a correr las evals. ¿Subió el pass rate? ¿Bajó otra cosa?

  5. Paso 5 — convierte las evals en puerta de calidad. Comprueba el exit code con un umbral imposible: 
    uv run copiloto eval --min-pass-rate 1.0 ; echo "exit=$?"
# → exit=1 (falla en cuanto hay un caso mal): esto es lo que bloquea un merge

    Resultado esperado: el comando devuelve exit=0 con un umbral razonable y exit=1 con uno imposible. Acabas de cerrar el bucle completo: construir, usar y medir.

Ejecuta las evals también en tu CI con Ollama en local o un proveedor de nube en un runner. La regla es simple: ningún cambio de prompt, modelo o chunking llega a main sin pasar la puerta. Ese hábito es lo que separa un proyecto de IA de un juguete.

8 · Reto

🎯 Pipeline de evaluación con juez calibrado y puerta en CI

Cierra el Copiloto con un pipeline de evaluación de nivel producción. Requisitos:

  • Amplía el dataset a 30 casos etiquetados por tags (rag, chunking, agent, out-of-corpus) y reporta el pass rate por etiqueta, no solo global: así ves qué capa falla.
  • Integra el juez (módulo 7) para fidelidad solo en los casos que pasan las comprobaciones deterministas, y calíbralo contra 10 veredictos humanos: mide la concordancia y ajusta el umbral.
  • Escribe un job de CI (GitHub Actions) que corra copiloto eval --min-pass-rate 0.9 en cada pull request y bloquee el merge si falla.
  • Publica un informe evals/report.md generado automáticamente con: pass rate por etiqueta, p50/p95 de latencia, tokens y coste estimado.

Pista: guarda el historial de resultados (un JSON por ejecución con fecha y commit) para ver tendencias: un pass rate que baja poco a poco es una regresión lenta, la más peligrosa. Para calibrar el juez, no confíes en un umbral «que suena bien»: compara sus veredictos con los humanos y elige el punto que maximice la concordancia (módulo 7). Y recuerda: un dataset de 30 casos es el inicio, no el final; el objetivo del reto es dejar el mecanismo para que crezca.

9 · Resumen

  • El dataset tiene casos dentro del corpus (citar la lección), fuera (abstenerse) y ambiguos (elegir bien la tool).
  • Prioriza comprobaciones deterministas (gratis y exactas); usa el juez solo para la fidelidad que el código no decide.
  • Métricas clave: pass rate, abstention accuracy, citation accuracy, latencia p50/p95 y coste.
  • La puerta de calidad convierte las evals en un exit code que bloquea regresiones en CI.
  • El Copiloto se expone por CLI (copiloto) y por una API mínima, compartiendo el mismo core.
  • En producción: índice persistente, secretos por entorno, límites y medición de coste y latencia.

10 · Preguntas frecuentes

¿Cuántos casos necesita el dataset para ser útil?

Empieza con 10–30 y céntrate en la cobertura, no en el número: dentro del corpus, fuera, ambiguos y multi-paso. Un dataset pequeño pero con buenos casos detecta la mayoría de las regresiones; crece solo, añadiendo cada fallo real. Perseguir «cien casos» antes de tener el mecanismo es tiempo perdido; lo importante es que el mecanismo exista y se ejecute en cada cambio.

¿Necesito un LLM-juez o me bastan los checks de código?

Depende de qué quieras medir. Para abstención, citas correctas y formato, el código es mejor: exacto, gratis y sin sesgo. El juez aporta para la fidelidad (¿la respuesta se apoya solo en el contexto?) y la relevancia, que el código no puede juzgar con precisión. Úsalo como complemento, con umbral calibrado, no como única fuente de verdad.

¿Cómo despliego el Copiloto si no tengo GPU?

Tres opciones. Con Ollama en una máquina con GPU (aunque sea modesta) para coste cero; con un proveedor en la nube (OpenAI/Anthropic) para no gestionar hardware, pagando por token; o híbrido: embeddings y búsqueda en local (baratos) y generación en la nube (la parte que más calidad aporta). Como el proveedor es una variable de entorno, puedes empezar con uno y cambiar sin tocar el core.

¿Cómo controlo el coste en la nube?

Con cuatro medidas: cache de respuestas repetidas, límites de contexto e iteraciones, medición por petición (tokens y latencia) y un presupuesto que corte antes de dispararse. Además, no envíes modelos grandes a tareas triviales: enruta lo fácil a un modelo pequeño y reserva el grande para las preguntas difíciles. El objetivo no es gastar menos a ciegas, sino saber exactamente cuánto cuesta cada respuesta.

¿Merece la pena una API si solo lo uso yo?

Si solo lo usas por terminal, la CLI basta y es más simple. La API se justifica cuando quieres integrarlo: una extensión de VSCode, un widget web, un bot, otro servicio. Como el core es compartido, añadir la API es barato (unas decenas de líneas) y no duplica lógica. Añádela cuando exista un consumidor real, no «por si acaso».
