Glosario de Spec-Driven Development

Referencia 📖 Términos clave

A

ADR (Architecture Decision Record)
Documento corto y numerado que registra una decisión: contexto, decisión y consecuencias. Se abre para lo difícil de revertir (formato de almacén, superficie pública del CLI, dependencias).
Agente de código
Programa (OpenCode, Cursor, Copilot, Claude Code…) que lee instrucciones y escribe o modifica código. En SDD implementa y propone planes; no es el product owner.
AGENTS.md
Fichero de instrucciones persistentes a la entrada de un repo: la puerta. Vive en el repo, se versiona y vale para cualquier hilo de trabajo, a diferencia del prompt del día (el pasillo).

C

Criterio de aceptación
Afirmación comprobable de “hecho” (Dado / Cuando / Entonces). Si no se puede demostrar con un comando, un fichero o una observación, hay que reescribirlo.
Contrato
La parte de la spec que una máquina puede comprobar: un JSON Schema, un OpenAPI. Se genera código contra él y se valida contra él.
Contexto (del agente)
Lo que el agente puede ver en una sesión. Meter de menos produce invención; meter de más produce ruido. La spec y los contratos son el contexto de mayor valor por token.

D

Definition of done
En SDD vive en la spec: la lista de criterios de aceptación. “Compila” o “pasa el linter” no es done.
Delta-spec
Spec de un cambio: estado actual, estado deseado, impacto/compatibilidad y migración. El 90 % del trabajo real son deltas, no greenfield.
Divergencia
Cuando el código y la spec dejan de decir lo mismo. Se resuelve actualizando la spec primero (en Git, con motivo), nunca parcheando a ciegas.

F

Fuente de verdad
El artefacto que gana las discusiones. En SDD es la spec (más sus contratos), no el historial del chat ni “lo que el código hace hoy”.

L

Lenguaje ubicuo
Vocabulario acordado del dominio, escrito en el glosario de la spec. La ambigüedad aquí se convierte en bugs allí.
Lumen
Bandeja de notas mínima que recorre todo el curso: spec + CLI en Node (lumen: add, list, close) + almacén data/notes.json validado con JSON Schema.

N

No-objetivos (non-goals)
Lo explícitamente fuera de alcance. La parte más rentable de una spec: cada no-objetivo es un malentendido que ya no ocurrirá.

P

Plan
El camino ordenado de la spec al código (pasos, ficheros, riesgos, fuera de alcance). Lo propone el agente y lo revisa el humano, antes de escribir código.
Prompt
Instrucción de un solo uso en un hilo de chat. Se evapora. Siempre debe poder trazarse a una spec; nunca la sustituye.

S

Skill (SKILL.md)
Spec reutilizable de cómo hacer una clase de trabajo. La spec de producto dice QUÉ; la skill dice CÓMO. Tiene nombre, descripción de un uso y límites.
Spec
Documento versionado que dice qué se quiere y por qué, con criterios de aceptación observables. No es un prompt, ni un ticket, ni un README.
Spec theatre
Documentos aprobados que nadie lee y nada verifican. Test de detección: “enséñame el comando que demuestra cada criterio”.
Supuesto
Lo que se da por hecho, escrito para poder impugnarlo. Un supuesto tácito es un bug futuro con buena coartada.

U

Under-spec / Over-spec
Demasiado poca spec (el agente inventa) frente a demasiada (parálisis, nadie la lee). El oficio está en calibrar: la spec más pequeña que elimine la ambigüedad.

V

Verificar (verify)
Cuarta fase del ciclo: comprobar la implementación contra la spec, criterio por criterio, con evidencia (comandos, ficheros).
Vibe-coding
Exploración rápida sin spec. Legítima como prototipo; el error es promocionarla a producción sin escribir después la spec que debería haber tenido.
