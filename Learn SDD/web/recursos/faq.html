Preguntas frecuentes

FAQ ❓ Dudas comunes

General

¿No es SDD simplemente “escribir buena documentación”?

No. La documentación describe lo que se hizo; una spec prescribe lo que debe hacerse y cómo se demuestra. La diferencia está en los criterios de aceptación verificables, los no-objetivos y el ciclo specify → plan → implement → verify. Un documento sin criterios comprobables es prosa, no spec.

¿Necesito un agente de código para seguir el curso?

No es obligatorio, pero sí recomendable haber usado uno aunque sea poco: el módulo 3 cobra mucho más sentido cuando has visto a un agente inventarse comportamiento por falta de spec. Todo lo importante del curso (escribir specs, planes, ADRs) se puede practicar con editor y terminal, sin API keys ni SaaS.

¿Cuánto tiempo tengo que dedicar por lección?

Cada lección está pensada para 25–35 minutos más el reto. El ritmo recomendado es 3–4 lecciones por semana. Los ejercicios producen artefactos reales (specs, planes, ADRs): guárdalos, porque el módulo 7 reutiliza ese músculo con Lumen.

¿Qué hago si me atasco en un reto?

Vuelve a la plantilla de la lección (casi todos los retos se resuelven aplicándola a un caso nuevo) y al ejemplo mínimo. Pregúntate: “¿cuál es el criterio de aceptación que debería escribir primero?”. Si en 24 horas no sale, pide a alguien (o a un agente) que revise tu spec, no que te dé la solución: el fallo suele estar en la intención, no en la ejecución.

Método

¿La spec la escribe el humano o el agente?

El humano es el dueño: decide el qué, el porqué y los no-objetivos. El agente puede redactar el borrador (es bueno resumiendo y estructurando), pero cada criterio lo aprueba un humano. Delegar la propiedad de la spec al agente es como delegar la firma de un contrato.

¿Cuándo NO merece la pena escribir una spec?

Cuando el coste de equivocarse es casi cero y el de escribir supera al de rehacer: un script de un solo uso, una exploración para aprender una API, un prototipo que vas a tirar hoy. La regla del curso: prototipa libremente, pero spec antes de ship.

¿SDD sustituye a TDD o a BDD?

No; los ordena. TDD y BDD producen specs ejecutables (tests, escenarios) que viven dentro del ciclo: el criterio de aceptación dice qué demostrar y el test lo demuestra de forma repetible. La lección 03 del módulo 4 detalla la relación.

¿Qué hago si el código y la spec divergen?

Actualizar la spec primero, en Git y con motivo, y después el código. Parchear el código para que “funcione” sin tocar la spec convierte la spec en ficción, y la próxima persona (o agente) volverá a implementar lo equivocado.

Herramientas

¿Tengo que usar Spec Kit / OpenSpec / Kiro?

No. El curso enseña el patrón (spec versionada + plan + verify) y usa esas herramientas como ejemplos, no como requisitos. Si alguna cambia de nombre o desaparece, el patrón sigue valiendo; eso es precisamente lo que lo hace robusto.

¿Vale mi editor con otro asistente en vez de OpenCode?

Sí. Los ejemplos se escriben para OpenCode porque es el entorno de esta Academy, pero el patrón AGENTS.md ≈ CLAUDE.md ≈ reglas de Cursor es el mismo: instrucciones persistentes en el repo + spec del trabajo actual + plan revisado.

¿Necesito Docker, nube o Windows con WSL para este curso?

No. Todo es Markdown, Git y Node. El CLI de Lumen corre con node nativo en Linux, macOS y Windows. Si un comando difiere entre PowerShell y bash, la lección lo señala.
