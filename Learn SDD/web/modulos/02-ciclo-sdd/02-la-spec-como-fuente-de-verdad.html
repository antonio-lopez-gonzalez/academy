La spec como fuente de verdad

Módulo 2 · El ciclo SDD ⏱ 30 minutos

1 · Introducción

Cuando hay una discusión — «¿esto debía hacer X o Y?», «¿quién pidió este comportamiento?» — algo tiene que desempatar. Ese algo es la fuente de verdad: el artefacto que gana los argumentos. En SDD, la fuente de verdad es la spec versionada en el repo (más sus contratos). No el chat, no la memoria del equipo, y desde luego no «lo que el código hace hoy».

En esta lección aprenderás por qué la spec gana al chat y al «el código es la spec», qué propiedades la hacen merecedora de ese papel (versionada, verificable, con dueño) y cómo se detecta la divergencia: las señales de que la spec y la realidad ya no coinciden, y qué hacer en cada caso.

¿Por qué existe esta lección? Porque sin fuente de verdad acordada, cada desacuerdo se resuelve por autoridad («lo dijo el senior»), por antigüedad («el código lleva así dos años») o por insistencia en el chat. La spec existe precisamente para que los desacuerdos se resuelvan por escrito verificable: gana lo que está en la spec y se puede demostrar, no lo que alguien recuerda.

2 · Teoría

Qué significa «fuente de verdad»

Fuente de verdad no significa «documento perfecto». Significa: cuando dos artefactos discrepan, este manda. La jerarquía SDD es explícita:

ORDEN DE AUTORIDAD (de mayor a menor)

  1. spec + contratos (spec/*.md, schema/*.json)   ← GANAN
  2. plan aprobado (plan/*.md)                     ← interpreta la spec
  3. código (src/)                                 ← obedece a 1 y 2
  4. chat / memoria / "siempre fue así"            ← NO DECIDEN NADA

Si el código contradice a la spec, el código está mal (o la spec está desactualizada: entonces se actualiza la spec primero, en Git, con motivo). Si el chat contradice a la spec, el chat pierde siempre: el chat se evapora, la spec permanece.

La spec gana al chat

El chat tiene tres defectos estructurales que lo inhabilitan como fuente de verdad: se evapora (los hilos se pierden, se compactan, se cierran), no tiene dueño ni versión (¿qué mensaje exacto era el válido? ¿quién lo aprobó?) y mezcla decisión con exploración («¿y si…?», «por cierto…», «dale»). Una spec, en cambio, vive en Git (historial, blame, PRs), tiene criterios comprobables y distingue lo decidido de lo explorado.

AspectoChatSpec versionada
Persistencia❌ Se pierde con el hilo✅ Vive en el repo, en Git
Autoridad❌ ¿Qué mensaje vale? ¿Quién lo aprobó?✅ Aprobada en PR, con dueño
Verificabilidad❌ «Creo que pedí…»✅ Criterios Dado/Cuando/Entonces demostrables
No-objetivos❌ Nunca se escriben en el chat✅ Sección explícita que frena inventos

Analogía: el chat es un apretón de manos; la spec es el contrato firmado. El apretón sirve para explorar y entenderse, pero cuando hay un desacuerdo sobre qué se acordó, gana lo que está firmado — y lo firmado se puede enseñar a un tercero (otro humano, otro agente) sin contarle toda la historia.

La spec gana a «el código es la spec»

«El código es la spec» suena pragmático («lee el código y sabrás qué hace»), pero confunde descripción con prescripción. El código te dice lo que el sistema hace hoy; nunca te dice lo que debería hacer, por qué lo hace, ni qué se decidió no hacer. Sin spec, no puedes distinguir un bug de una feature: si list no filtra por fecha, ¿es un error o una decisión? El código no lo dice. La spec sí (objetivo + no-objetivos + porqué).

Además, «lee el código» no escala con agentes: cada agente que entra al repo re-deriva la intención desde cero e inventa lo que falta. Con spec, todos los agentes (y humanos) parten de la misma intención escrita. Por eso la regla es: si el código y la spec divergen, se actualiza la spec primero — en Git, con motivo — y luego el código. Nunca al revés en silencio.

Cómo se detecta la divergencia

La divergencia es la distancia entre lo que la spec dice y lo que el sistema hace (o lo que el equipo cree). Señales típicas, ordenadas de más barata a más cara de ignorar:

  1. «Yo no pedí eso»: el agente (o un compañero) entrega comportamiento no especificado. Diagnóstico: under-spec — falta criterio o no-objetivo.
  2. Criterio que ya no se puede demostrar: ejecutas la comprobación de la spec y falla, pero «el producto funciona». Diagnóstico: la spec se quedó vieja tras un cambio no registrado.
  3. Dos lecturas honestas de la misma frase: dos personas implementan distinto a partir del mismo párrafo. Diagnóstico: ambigüedad — falta glosario o el criterio no es observable.
  4. Preguntas que la spec no responde: «¿y si el id no existe?», «¿en qué orden lista?». Diagnóstico: supuestos implícitos que hay que explicitar.

Test de un minuto: elige un criterio de tu spec y ejecuta su comprobación ahora mismo. Si pasa, spec y código convergen. Si falla, tienes divergencia declarada — y la regla dice qué hacer: ¿está mal el código (se corrige el código) o está mal la spec (se corrige la spec primero, con commit y motivo)? Lo que nunca vale es dejar ambas en desacuerdo.

3 · Ejemplo mínimo

Una divergencia de juguete, completa: spec, realidad observada y resolución correcta.

# spec/ping.md dice:
- [ ] Dado el CLI instalado, cuando ejecuto `ping`,
      entonces imprime `pong` y sale con código 0.

# Realidad observada:
$ node src/cli.js ping
PONG          ← mayúsculas. El criterio dice `pong`.
$ echo $?      ← 0. Esta parte sí cumple.

# Resolución (la spec manda, el código obedece):
# 1. El código está mal → se corrige `PONG` → `pong`.
# 2. Si el equipo prefiriera `PONG`, se corrige LA SPEC
#    primero (commit: "spec: ping responde PONG en mayúsculas,
#    motivo: coherencia con el protocolo X") y luego el código.
# Lo prohibido: cambiar el código a `pong` sin mirar, o dejar
# `PONG` funcionando y la spec diciendo `pong`.

Línea por línea: el criterio es lo bastante concreto (pong exacto, código 0) como para que la divergencia sea detectable mecánicamente; la observación muestra el hecho (mayúsculas) sin interpretarlo; y la resolución ofrece los dos caminos legítimos — con la condición de que el camino «cambiar la spec» deja constancia del motivo en Git. El tercer camino (divergencia silenciosa) es el que destruye la fuente de verdad.

4 · Ejemplo real

Divergencia real en Lumen: un agente implementa close y, con buena intención, añade borrado definitivo («también añadí --hard para borrar»). La spec no pedía eso.

# spec/lumen-close.md (fuente de verdad, extracto)
## Objetivo
# Cerrar una nota por su id sin borrarla.
## No-objetivos
- Borrar notas (ni `--hard`, ni purga; eso es otra spec).
## Criterios de aceptación
- [ ] Dado el almacén con la nota `abc123` abierta,
      cuando ejecuto `close abc123`, entonces `done` pasa a `true`
      y la nota sigue existiendo en `data/notes.json`.

Detección: el criterio 1 exige que la nota siga existiendo; la revisión del diff muestra una bandera --hard que la elimina. Hay dos divergencias a la vez: el código hace algo que la spec prohíbe (no-objetivo violado) y el chat donde «se habló» de --hard no tiene autoridad frente a la spec. Resolución: se elimina --hard del código (el código obedece), y si el borrado interesa de verdad, se abre otra spec (spec/lumen-delete.md) con su propio ciclo. El no-objetivo cumplió exactamente su función: convirtió «yo no pedí eso» en una infracción demostrable.

Por qué este ejemplo importa: sin la sección de no-objetivos, la discusión sería «a mí me parece útil» contra «a mí no» — irresoluble. Con el no-objetivo escrito, la discusión termina en 10 segundos: la spec gana. Esa es la rentabilidad de escribir no-objetivos (Módulo 1): son el escudo contra el alcance inventado.

6 · Errores habituales

❌ «Lo hablamos en el chat, vale como decisión»

# ❌ Decisión solo en el chat: se evapora con el hilo
# chat> "vale, que list ordene por fecha por defecto"
# (dos semanas después nadie encuentra ese mensaje)

# ✅ Del chat a la spec, en el repo
# spec/lumen-list.md → "## Supuestos: `list` ordena por `createdAt`
# descendente." + commit con motivo. Ahora es desempatable.

Por qué está mal: el chat no tiene versión, ni dueño, ni criterios. La versión correcta transcribe la decisión a la spec con motivo, donde sí tiene autoridad.

❌ «El código es la spec, lee el código»

# ❌ La prescripción perdida: el código no dice el "debería"
# $ grep -r "order" src/cli.js   # dice CÓMO ordena hoy,
#                                # no si DEBERÍA ordenar así ni por qué

# ✅ La spec prescribe; el código describe
# spec/lumen-list.md → criterio: "cuando ejecuto `list`,
# entonces las notas salen ordenadas por `createdAt` descendente".
# Si el código ordena distinto, el código está mal. Punto.

Por qué está mal: sin prescripción no se distingue bug de feature. La versión correcta mantiene el «debería» en la spec, demostrable con un comando.

❌ Parchear el código y dejar la spec rota

Cambiar el comportamiento en código «provisionalmente» sin tocar la spec. Por qué está mal: crea divergencia normalizada — la próxima persona (o agente) leerá una spec falsa y tomará decisiones falsas sobre ella. La versión correcta: si la spec estaba mal, commit a la spec primero y luego al código, en el mismo cambio.

7 · Ejercicio guiado

Objetivo: practicar la detección de divergencia sobre Lumen, con veredicto escrito.

  1. Paso 1: escribe una mini-spec de 6 líneas para add: objetivo («crear una nota con título») + 1 criterio («cuando ejecuto add "comprar pan", entonces data/notes.json contiene una nota con ese título y done=false»).
  2. Paso 2: provoca tres divergencias deliberadas en una copia del CLI (o en papel): (a) el título se guarda en mayúsculas; (b) add sin título no falla; (c) add además imprime estadísticas. Clasifica cada una: ¿viola el criterio, viola un supuesto implícito, o viola un no-objetivo ausente?
  3. Paso 3: escribe el veredicto para cada una en una línea: «código mal → corregir código» o «spec incompleta → corregir spec primero (motivo: …)».
  4. Paso 4: añade a tu mini-spec el no-objetivo o criterio que habría impedido la divergencia (c) de raíz.

Resultado esperado: una mini-spec de ~10 líneas (objetivo + 1 criterio + 1 no-objetivo añadido en el paso 4) y tres veredictos de una línea: (a) código mal — el criterio exige el título exacto; (b) spec incompleta — falta el criterio de error, se añade primero con motivo; (c) código mal — comportamiento no pedido, se elimina o se abre spec separada. Si tus tres veredictos dicen «código mal», revisa el (b): un caso de error no especificado es casi siempre spec incompleta, no código malicioso.

8 · Reto

🎯 Audita una «spec» que no lo es

Elige un README, un ticket o un hilo de chat de un proyecto tuyo que haya funcionado como «spec informal». Aplícale el test de fuente de verdad: ¿tiene criterios demostrables? ¿no-objetivos? ¿dueño? ¿historial? Escribe las 3 preguntas que ese documento no responde y que un agente tendría que inventar. No las respondas todavía: las usarás en el Módulo 7.

Pista: las preguntas que empiezan por «¿y si…?» o «¿en qué orden…?» son supuestos implícitos esperando a convertirse en divergencia.

9 · Resumen

  • La fuente de verdad es el artefacto que gana los argumentos: en SDD, la spec versionada + sus contratos.
  • La spec gana al chat porque persiste, tiene dueño y versión, y contiene criterios demostrables.
  • La spec gana al «código es la spec» porque prescribe (debería + porqué), no solo describe (hace hoy).
  • La divergencia se detecta con señales: «yo no pedí eso», criterios que fallan, dobles lecturas, preguntas sin respuesta.
  • Ante divergencia: o el código está mal (se corrige el código) o la spec está mal (se corrige la spec primero, con motivo). Nunca divergencia silenciosa.
ArtefactoPara qué sirve

Contratos (schema/*.json)Partes de la spec comprobables por máquina

10 · Preguntas frecuentes

¿Y si la spec está mal y el código «funciona bien»?

Entonces la spec está mal, y se corrige la spec primero — con commit y motivo — y luego se verifica el código contra la spec corregida. Lo que no vale es dejarlas en desacuerdo: una spec que no describe la realidad deja de ser fuente de verdad y todo el equipo (humanos y agentes) empieza a ignorarla.

¿La spec puede cambiar? ¿No se supone que es estable?

Cambia constantemente: cada delta del producto (Módulo 5) es un cambio de spec. «Fuente de verdad» no significa «inmutable», significa «versionada con motivos». Git es el que hace posible que cambie sin romperse: cada cambio queda registrado, fechado y explicado.

¿Qué hago si dos partes de la spec se contradicen?

Tienes una spec contradictoria, que es peor que una spec ausente (un agente obedecerá una mitad al azar). Se resuelve como cualquier divergencia: se decide cuál manda, se corrige la otra, se deja constancia del motivo. Y se añade un criterio que habría detectado la contradicción.

¿Los contratos (JSON Schema, OpenAPI) también son fuente de verdad?

Sí: son la parte de la spec comprobable por máquina. Si el esquema dice que done es booleano obligatorio y el código escribe "done": "yes", el validador falla y el código pierde — sin discusión humana. Los verás a fondo en el Módulo 4.
