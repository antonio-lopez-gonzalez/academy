Contratos de datos con JSON Schema

Módulo 4 · Contratos y specs técnicas ⏱ 35 minutos

1 · Introducción

En esta lección aprenderás qué es un contrato de datos: la parte de la spec que una máquina puede comprobar sola. Verás cómo describir la Nota de Lumen ({ id, title, done, createdAt }) con un esquema mínimo y por qué ese esquema evita que el CLI, la web y el agente inventen cada uno su propia forma de guardar notas.

Lo usarás cada vez que dos piezas compartan datos: el CLI que escribe data/notes.json y la web que lo lee, un agente que genera notas de prueba, o tu yo del futuro que añade un campo nuevo.

¿Por qué existe esta lección? Porque la prosa no valida. Puedes escribir «toda nota tiene un identificador» y el agente asentirá… y luego guardará una nota sin id. Un contrato dice lo mismo pero se ejecuta: un validador responde sí o no. Sin contrato, cada divergencia se descubre en producción; con contrato, se descubre al guardar.

Errores típicos de esta pieza: describir los datos solo en prosa («la nota tiene fecha»), validar solo «a ojo», o escribir un esquema tan estricto que bloquea cambios legítimos.

2 · Teoría

Un contrato es la parte ejecutable de la spec: no cuenta una historia, decide. Dado un dato, el contrato responde «válido» o «inválido» sin interpretar intenciones. Por eso en SDD los contratos viven dentro del repo, versionados en Git como la spec: son fuente de verdad, no documentación decorativa.

Analogía: la spec en prosa es el apretón de manos («nos pondremos de acuerdo en cómo es una nota»); el contrato es el contrato firmado con cláusulas comprobables. El apretón genera confianza; el papel resuelve discusiones. Necesitas ambos, pero solo uno gana un juicio — o un verify.

Qué es JSON Schema (el patrón, sin magia)

JSON Schema es un vocabulario para decir «un JSON válido para mí tiene esta forma». El patrón estable que usamos en este curso es mínimo y lleva años sin cambiar:

  • type: qué clase de valor esperas (object, string, boolean…).
  • properties: qué campos tiene un objeto y qué forma tiene cada uno.
  • required: qué campos son obligatorios (los que falten, invalidan).

Con solo esos tres bloques ya puedes blindar la Nota de Lumen. Todo lo demás (formatos, rangos, condicionales) existe, pero aquí no lo necesitas: el contrato más pequeño que elimina la ambigüedad es el mejor contrato.

Dónde vive en el ciclo SDD

 SPECIFY (spec/lumen.md dice "qué es una nota")
    │  + CONTRACT (schema/note.schema.json dice "cómo se comprueba")
    ▼
 PLAN → IMPLEMENT (el CLI valida al guardar) → VERIFY (el criterio apunta al esquema)

El contrato no sustituye a la spec de producto: la completa. La spec dice por qué una nota existe y qué significa cerrarla; el esquema dice qué forma exacta tiene. Cuando discrepan, se actualiza la spec primero (en Git, con motivo) y luego el esquema — nunca al revés en silencio.

Idea clave: un contrato bueno responde a «¿cómo sé que está hecho?» con un comando. En Lumen: validar data/notes.json contra schema/note.schema.json. Si ese comando no existe, el contrato es teatro.

3 · Ejemplo mínimo

El contrato más pequeño posible: una nota es un objeto con un título obligatorio. Diez líneas que ya validan algo real.

{
  // type "object": solo aceptamos objetos, nada de textos sueltos
  "type": "object",
  // properties: los campos que reconocemos y su tipo básico
  "properties": {
    "title": { "type": "string" },
    "done": { "type": "boolean" }
  },
  // required: sin título no hay nota; "done" puede omitirse al crear
  "required": ["title"]
}

Línea por línea:

  1. "type": "object": rechaza de entrada "comprar pan" suelto o 42. La nota es siempre un objeto.
  2. "properties": declara el vocabulario. title es texto, done es booleano. Nada más se promete por ahora.
  3. "required": ["title"]: la única regla dura: sin title, el dato es inválido. Es el «criterio de aceptación» del dato.

Por qué funciona: un agente que lea este esquema ya no puede «inventar» que el título se llama name o que done es el texto "sí". Si lo intenta, la validación lo delata.

4 · Ejemplo real

El contrato real de Lumen: la Nota completa { id, title, done, createdAt }, tal como vive en proyectos/lumen/schema/note.schema.json. El almacén data/notes.json es una lista de objetos con exactamente esta forma.

{
  // type "object": cada nota del almacén es un objeto JSON
  "type": "object",
  // properties: los cuatro campos estables de la Nota Lumen
  "properties": {
    // id: identificador único en texto (lo genera el CLI, no el humano)
    "id": { "type": "string" },
    // title: lo que escribió el usuario; nunca vacío según la spec
    "title": { "type": "string" },
    // done: false al crear, true al cerrar con "lumen close"
    "done": { "type": "boolean" },
    // createdAt: marca temporal de creación en texto (el CLI la escribe)
    "createdAt": { "type": "string" }
  },
  // required: los cuatro son obligatorios en el almacén guardado
  "required": ["id", "title", "done", "createdAt"]
}

Decisiones explicadas, una por una:

  • ¿Por qué id es string y no número? Porque la spec de Lumen exige ids únicos estables entre sesiones; un texto generado por el CLI (fecha + contador o similar) no colisiona al reordenar el fichero. El número secuencial se rompe al borrar notas.
  • ¿Por qué los cuatro son required? Porque el CLI y la web leen el mismo fichero. Si una nota guardada carece de createdAt, la web debe adivinar — y adivinar es el síntoma de under-spec. Al crear, el CLI rellena los cuatro antes de escribir.
  • ¿Por qué no hay campo tags? Porque las etiquetas llegan en el Módulo 5 como delta-spec. Adelantarlas aquí contaminaría la spec actual con futuro no decidido. El contrato describe el hoy, no el quizá.
  • ¿Por qué no fijamos aquí formatos estrictos? Para no afirmar banderas concretas más allá del patrón estable (type / properties / required). Endurecer el contrato es una decisión con dueño y ADR, no un adorno.

Y así se valida (el contrato se ejecuta, no se contempla):

# validar el almacén contra el esquema antes de dar la tarea por hecha
# validate: verbo observable; si falla, el VERIFY falla aunque "compile"
node scripts/validate-notes.mjs data/notes.json schema/note.schema.json

6 · Errores habituales

❌ Describir los datos solo en prosa

# ❌ prosa que ningún validador puede comprobar
## Nota
- Tiene un identificador, un título, si está hecha y cuándo se creó.
# ¿"Identificador" es número o texto? ¿Falta alguno y sigue siendo nota? Nadie lo sabe.

✅ La misma idea como contrato ejecutable

{
  // ✅ cada campo tiene tipo y la lista de obligatorios es explícita
  "type": "object",
  "properties": {
    "id": { "type": "string" },
    "title": { "type": "string" },
    "done": { "type": "boolean" },
    "createdAt": { "type": "string" }
  },
  "required": ["id", "title", "done", "createdAt"]
}

Por qué estaba mal: la prosa deja tres decisiones en el aire (nombres, tipos, obligatoriedad) y cada lector — humano o agente — las rellena a su manera. El esquema las fija una vez y las comprueba siempre.

❌ Esquema que nadie ejecuta

# ❌ el esquema existe pero el VERIFY no lo menciona: es decoración
node src/cli.js add "comprar pan"
# ¿era válida la nota guardada? nadie lo comprobó

# ✅ el criterio de aceptación cita el comando que demuestra la validez
node src/cli.js add "comprar pan" --store data/notes.json
node scripts/validate-notes.mjs data/notes.json schema/note.schema.json
# salida esperada: todas las notas válidas contra el esquema

7 · Ejercicio guiado

Objetivo: escribir el esquema de la Nota Lumen y pillar una nota rota con el validador.

  1. Paso 1: crea schema/note.schema.json con el contenido del ejemplo real (los cuatro campos en required).
  2. Paso 2: crea data/notes.json con una nota válida y una nota sin id: 
    [
  // nota válida: los cuatro campos presentes con sus tipos
  { "id": "n1", "title": "comprar pan", "done": false, "createdAt": "2026-01-01" },
  // nota rota: falta "id", el validador debe rechazar el fichero
  { "title": "sin identificador", "done": false, "createdAt": "2026-01-02" }
]
  3. Paso 3: ejecuta node scripts/validate-notes.mjs data/notes.json schema/note.schema.json y comprueba que falla señalando la segunda nota.
  4. Paso 4: añade el id que falta y vuelve a validar hasta obtener «válido».

Resultado esperado: un schema/note.schema.json con type / properties / required para los cuatro campos, y una validación que primero falla localizando la nota sin id y después pasa. Si el validador no te dice qué nota falla, tu script de validación aún no es un buen verificador.

8 · Reto

🎯 Endurece el título sin romper el almacén

Extiende el esquema para que title rechace cadenas vacías, y escribe un criterio de aceptación (Dado / Cuando / Entonces) que lo demuestre con el validador. No cambies los cuatro campos ni añadas tags: eso es trabajo del Módulo 5.

Pista: piensa solo en el patrón — «qué significa vacío» y «qué comando lo demuestra» — antes de buscar banderas concretas en la documentación oficial.

9 · Resumen

  • Un contrato de datos es la parte de la spec que una máquina puede comprobar: responde válido / inválido sin interpretar.
  • El patrón estable de JSON Schema basta para casi todo: type + properties + required.
  • La Nota Lumen es { id, title, done, createdAt }: cuatro campos obligatorios, sin tags hasta el delta del Módulo 5.
  • Contrato que no se ejecuta es teatro: cítalo en los criterios de aceptación con un comando de validación.
  • El contrato completa la spec (el qué forma), no la sustituye (el qué y por qué).

10 · Preguntas frecuentes

¿JSON Schema sustituye a la spec de la Nota?

No. El esquema dice qué forma tiene una nota válida; la spec dice qué significa crear, listar y cerrar notas y por qué existen. Un dato válido contra el esquema puede seguir violando la spec (por ejemplo, un id duplicado). Necesitas ambos.

¿Qué versión de JSON Schema debo usar?

La que traiga tu validador, y declárala en el repo. En esta lección usamos solo el patrón estable (type / properties / required), que no depende de versiones recientes. Si dudas de un campo concreto, consulta la documentación oficial antes de afirmarlo en tu spec.

¿Tan estricto debo ser con `required`?

Sé estricto con lo que el lector necesita para no adivinar. En el almacén guardado de Lumen, los cuatro campos son imprescindibles para el CLI y la web; por eso son obligatorios. En el momento de crear (argumentos del CLI), el usuario solo da el título y el programa rellena el resto. Obligatorio «en disco» no significa obligatorio «en el teclado».

¿Valido en el CLI, en un script aparte, o en ambos?

En ambos, con roles distintos: el CLI valida al escribir (no guarda basura), y el script de validación verifica el fichero entero en el VERIFY (pilla ediciones manuales o migraciones a medias). El criterio de aceptación cita el segundo.
