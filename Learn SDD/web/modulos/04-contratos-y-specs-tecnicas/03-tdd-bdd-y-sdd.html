TDD, BDD y SDD: primos, no rivales

Módulo 4 · Contratos y specs técnicas ⏱ 30 minutos

1 · Introducción

En esta lección ordenarás tres siglas que suelen pelearse sin motivo: TDD (test-driven), BDD (behavior-driven) y SDD (spec-driven). Aprenderás que los tests son specs ejecutables, que no sustituyen al qué y al porqué, y en qué orden usar cada uno cuando trabajas con un agente.

Lo usarás cada vez que alguien pregunte «¿para qué escribir specs si ya tengo tests?»: sabrás responder con el orden exacto y con un ejemplo de Lumen donde el test pasa y la spec sigue rota.

¿Por qué existe esta lección? Porque «ya tengo tests» es la excusa más elegante para no escribir specs — y es falsa. Un test dice cómo se comporta el código de hoy; una spec dice qué debería hacer el producto y por qué. Sin spec, los tests verifican que el código hace lo que hace. Sin tests, la spec es una promesa sin alarma. Necesitas la familia completa, cada primo en su silla.

Errores típicos de esta pieza: creer que TDD sustituye a la spec, escribir escenarios BDD como guiones de clicks sin criterio, o pedirle al agente «haz TDD» sin darle la spec de la que salen los tests.

2 · Teoría

Las tres prácticas responden preguntas distintas del mismo proyecto:

  • SDD responde qué construimos y por qué (spec versionada, criterios verificables). Es la fuente de verdad.
  • BDD responde cómo se comporta desde fuera, en lenguaje compartido (Dado / Cuando / Entonces). Es el puente entre negocio y código.
  • TDD responde cómo verifico cada paso mientras construyo (rojo → verde → refactoriza). Es el ritmo de implementación.

Analogía: SDD es el plano con la memoria del arquitecto (qué edificio y por qué así); BDD es la visita guiada («cuando entras por aquí, entonces ves la luz»); TDD es medir cada tabique con el metro mientras lo levantas. Medir mucho no te dice qué edificio querías; el plano sin metro se tuerce igual.

El orden entre los tres

 SPEC (qué + por qué + criterios) ──▶ ESCENARIOS (Dado/Cuando/Entonces) ──▶ TESTS (rojo→verde)
   SDD: fuente de verdad                 BDD: comportamiento observable      TDD: ritmo de código
         ▲                                        │                              │
         └────────── diverge? actualiza la SPEC primero ────────────────────────┘

El orden importa porque cada nivel hereda su autoridad del anterior: los escenarios BDD salen de los criterios de la spec (no de la imaginación del programador), y los tests TDD comprueban esos escenarios (no «lo que el código ya hace»). Invertir el orden — escribir tests y deducir la spec — produce suites verdes sobre productos equivocados.

Qué no sustituye a qué

Si solo tienes…Te falta…Síntoma
Solo tests (TDD sin spec)El qué y el porquéTodo pasa en verde pero nadie sabe si el producto es correcto
Solo escenarios (BDD sin tests)La alarma automáticaEl comportamiento se describe pero nadie lo comprueba a cada cambio
Solo spec (SDD sin tests)La verificación continuaLa spec es correcta el día 1 y miente el día 30

Regla de oro con agentes: el agente puede generar escenarios y tests, pero el humano (o la spec) fija el qué. «Escríbeme tests de close» sin spec produce tests que bendicen cualquier comportamiento; «implementa estos criterios con TDD» produce tests que protegen la intención.

Quién es dueño de cada nivel

La propiedad importa porque sin dueño no hay a quién preguntar cuando dos niveles discrepan.

  • Spec y criterios: del humano (actuando como product owner).
  • Escenarios BDD: negociados; el agente propone redacción, el humano acepta significado.
  • Tests: de quien implementa, siguiendo los escenarios aceptados.

Si el agente propone un criterio nuevo («¿y si close acepta varios ids?»), no lo codifica: lo lleva a la spec y espera dueño.

Señales de que el orden se invirtió

Detecta el flujo tests-primero-spec-después por estos síntomas:

  • Nadie sabe qué criterio protege cada test: preguntas «¿esto de dónde sale?» y la respuesta es «del código».
  • Cobertura alta, confianza baja: 90 % en verde y aun así cada release da miedo.
  • Cambiar la spec no rompe nada: si reescribes un criterio y ningún test falla, los tests no colgaban de la spec.
  • Los tests nombran implementación: hablan de funciones internas en vez de comportamiento observable.

Cada síntoma apunta a la misma cura: recuelga los tests de sus criterios madre antes de añadir ni un test más.

3 · Ejemplo mínimo

El ciclo completo en miniatura con el comando close de Lumen. Fíjate en de dónde sale cada pieza:

# 1 · SPEC (el qué, en la spec de Lumen):
# - [ ] Dado una nota abierta, cuando ejecuto "close <id>",
#   entonces "list" la muestra como cerrada.
# 2 · ESCENARIO BDD (el comportamiento, sale del criterio):
# Dado una nota abierta con id "n1",
# cuando ejecuto close "n1",
# entonces list muestra "n1" como cerrada.
# 3 · TEST (la alarma, sale del escenario; el agente lo codifica con TDD).

Línea por línea:

  1. El criterio vive en la spec: es verificable sin leer código («se puede demostrar que list la muestra cerrada»). Aquí manda el humano.
  2. El escenario traduce el criterio a Dado / Cuando / Entonces: mismo significado, lenguaje compartido con cualquiera (no exige herramientas Gherkin).
  3. El test automatiza el escenario: falla antes del código (rojo), pasa después (verde). Si el escenario estaba mal, el test verde miente — por eso el orden es spec → escenario → test.

4 · Ejemplo real

El caso que demuestra por qué los tests no bastan: un close con tests en verde y spec rota. El agente implementó «cerrar» como «borrar», y sus tests bendijeron el borrado:

# el agente implementó close como DELETE y su test lo celebra
# test: "close elimina la nota del almacén" -> VERDE (pero la spec dice otra cosa)
node src/cli.js add "comprar pan" --store data/notes.json
node src/cli.js close n1 --store data/notes.json
node src/cli.js list --store data/notes.json
# la nota ya no aparece: el test pasa, el producto miente

¿Qué decía la spec? Que cerrar marca done: true y la nota sigue listada como cerrada (así la web muestra historial). El test verificaba el comportamiento implementado, no el especificado:

# ✅ criterio real de la spec (el que el test debió automatizar)
- [ ] Dado una nota abierta con id "n1", cuando ejecuto
  "node src/cli.js close n1", entonces "node src/cli.js list"
  muestra "n1" con done en true y la nota sigue en data/notes.json.
# Moraleja: el test sin spec madre verifica "lo que el código hace";
# el escenario hijo de la spec verifica "lo que el producto debe hacer".

Decisiones explicadas: por qué se conserva la nota cerrada (historial y auditoría en Git del almacén), por qué el criterio nombra comandos exactos (para que el VERIFY no dependa de leer el código del agente) y por qué el fallo es de proceso, no de TDD (TDD funcionó: automatizó fielmente un escenario equivocado).

El test que miente es peor que no tener test: un hueco sin test genera precaución; un test verde sobre un escenario equivocado genera falsa confianza y se cita en revisiones («está probado»). Por eso la revisión humana empieza por los escenarios, no por el porcentaje de cobertura.

6 · Errores habituales

❌ «Ya tengo tests, no necesito spec»

# ❌ suite verde sobre comportamiento inventado: close borra en vez de marcar
# todos los tests pasan; la spec (cerrar = done true, nota conservada) se viola
node src/cli.js close n1 && node src/cli.js list
# la nota desapareció: verde por fuera, roto por dentro

✅ Tests hijos de la spec

# ✅ cada test cita su criterio madre: si el criterio cambia, el test cambia
- [ ] Dado nota abierta "n1", cuando close "n1", entonces list muestra
  "n1" con done en true (criterio LUMEN-CLOSE-01, spec/lumen.md).
# El test automatiza ESTO; si close borra, el test falla como debe.

Por qué estaba mal: los tests verifican coherencia interna, no corrección del producto. Sin criterio madre, «verde» significa «el código hace lo que el código hace». Con criterio madre, «verde» significa «el producto hace lo prometido».

❌ BDD como guion de clicks

# ❌ escenario acoplado a la implementación (si cambia un texto, falla todo)
# Dado que pulso el botón azul, cuando hago clic dos veces,
# entonces aparece el popup "¡Genial!".

Por qué está mal: describe la interfaz de hoy, no el comportamiento observable del producto. Un buen escenario BDD sobrevive a un rediseño; un guion de clicks, no.

7 · Ejercicio guiado

Objetivo: convertir un criterio de Lumen en escenario y en orden de TDD.

  1. Paso 1: copia este criterio madre a tu cuaderno: «Dado un almacén vacío, cuando ejecuto add "comprar pan", entonces list muestra una nota con ese título y done en false».
  2. Paso 2: reescríbelo como escenario BDD con tres líneas Dado / Cuando / Entonces, nombrando comandos exactos (node src/cli.js …).
  3. Paso 3: escribe (en prosa, no hace falta codificar) qué haría el test en rojo: qué comando ejecutaría y qué salida esperaría antes de que exista el código.
  4. Paso 4: escribe qué significa «verde» aquí: el comando exacto que demuestra que el escenario se cumple.

Resultado esperado: un escenario de tres líneas trazable al criterio («criterio LUMEN-ADD-01») más dos frases: «rojo = este comando falla así» y «verde = este comando muestra esto». Si tu escenario no nombra comandos, aún es prosa, no spec ejecutable.

Sin Gherkin también vale: lo que importa es el formato Dado / Cuando / Entonces como lenguaje compartido, no la herramienta. Si algún día adoptas Gherkin ejecutable, estos escenarios migrarán casi literalmente. Empieza por el hábito, no por el parser.

8 · Reto

🎯 Caza el test huérfano

Toma una suite de tests real tuya (o los ejemplos de este módulo) y elige tres tests: para cada uno, escribe de qué criterio de spec desciende. Si alguno no desciende de ninguno, clasifícalo: ¿protege intención real no escrita (candidata a criterio) o bendice implementación (candidata a reescribir)?

Pista: la pregunta que delata al huérfano es «si este test pasa y la spec dice lo contrario, ¿quién gana?».

9 · Resumen

  • Los tests son specs ejecutables: automatizan promesas, no las inventan.
  • SDD fija el qué y el porqué; BDD lo traduce a comportamiento observable; TDD lo construye paso a paso verificado.
  • El orden es spec → escenario → test. Invertirlo produce suites verdes sobre productos equivocados.
  • Un test verde sin criterio madre solo prueba coherencia interna; con criterio madre prueba corrección del producto.
  • Con agentes: el humano fija los criterios; el agente genera escenarios y tests a partir de ellos.
ArtefactoPara qué sirve
Spec + criterios (SDD)Decir qué debe hacer el producto y cómo se demuestra; fuente de verdad
Escenario Dado / Cuando / Entonces (BDD)Traducir cada criterio a comportamiento observable en lenguaje compartido
Test rojo → verde (TDD)Convertir cada escenario en alarma automática durante la implementación

10 · Preguntas frecuentes

¿Necesito herramientas Gherkin o Cucumber para hacer BDD?

No. BDD es una forma de pensar y escribir (Dado / Cuando / Entonces en lenguaje compartido), no una herramienta obligatoria. En este curso los escenarios viven en la spec como criterios y los tests los automatizan con el runner que ya uses. Añade herramienta solo cuando la trazabilidad manual se quede corta.

¿TDD ya no hace falta si trabajo spec-first con un agente?

Al contrario: hace más falta. El agente escribe código rápido y convincente; sin el ritmo rojo → verde, aceptas diffs que «parecen bien». La spec dice qué; TDD te obliga a demostrar cada paso hacia ese qué.

¿Cada criterio necesita su propio test?

Cada criterio verificable merece al menos un escenario automatizado, sí. Si un criterio no se puede automatizar («que quede bonito»), el problema no es la cobertura: es el criterio. Reescríbelo hasta que un comando pueda demostrarlo.

¿Qué hago si el test pasa pero la spec dice otra cosa?

Gana la spec (es la fuente de verdad). Sospecha primero del escenario: el test automatizó fielmente una lectura equivocada. Corrige la cadena desde arriba: aclara el criterio, reescribe el escenario y luego el test. Nunca retoques el test para que «pase» sin tocar la spec.

¿Dónde encajan los contratos (JSON Schema, OpenAPI) en este orden?

Al lado de los escenarios, como specs ejecutables de datos y APIs: el esquema valida qué forma tiene una nota y OpenAPI qué conversación promete la API. Nacen de la spec igual que los escenarios, y los tests los usan como oráculo. Spec → (escenarios + contratos) → tests: la misma cadena, un eslabón más.
