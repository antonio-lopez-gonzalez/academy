Entorno: Git, Markdown y un agente

Módulo 0 · Preparación ⏱ 25 minutos

1 · Introducción

SDD necesita sorprendentemente poco: Git para versionar la intención junto al código, Markdown como formato de las specs, y un agente de código que lea ambas cosas. Nada de SaaS de pago, nada de API keys, nada de frameworks. Si ya programas, casi seguro que lo tienes casi todo.

En esta lección montarás ese trío, entenderás qué pinta cada pieza (Git = memoria, Markdown = idioma, agente = lector y ejecutor) y conocerás la cuarta: AGENTS.md, el fichero-puerta que recibe al agente cuando entra en tu repo. Al terminar, tu entorno pasará una lista de verificación de cinco comandos.

¿Por qué existe esta lección? Porque las specs no viven en el vacío: viven en un repo, en un formato y frente a un lector (humano o agente). Sin Git, la spec no tiene historia; sin Markdown, no hay diffs legibles; sin AGENTS.md, cada agente que entra empieza de cero. Montar esto ahora evita fricción en las 28 lecciones restantes.

2 · Teoría

Las tres piezas (y la puerta)

  • Git — la memoria. Versiona la intención igual que el código: cada cambio de spec queda con autor, fecha y motivo. git log spec/ es la biografía de tus decisiones. Sin Git no hay «spec versionada», solo ficheros sueltos.
  • Markdown — el idioma. Texto plano con estructura mínima (títulos, listas, checkboxes). Difiere limpio en Git, lo edita cualquier editor y lo consume cualquier agente sin herramientas especiales. Es el formato canónico de spec.md, AGENTS.md, SKILL.md y los ADRs.
  • Un agente de código — el lector y ejecutor. Recibe la spec como contexto y produce código y planes. En este curso los ejemplos usan OpenCode (es el entorno de esta Academy), pero el método es agnóstico: Cursor, Copilot, Claude Code y compañía siguen el mismo patrón.
  • AGENTS.md — la puerta. Instrucciones persistentes que el agente lee al entrar en el repo (dónde está la spec, qué convenciones seguir, qué no tocar). Es «el pasillo frente a la puerta»: el hilo de hoy es efímero, la puerta permanece.

Puerta frente a pasillo

La distinción puerta/pasillo organiza todo el trabajo con agentes:

  • La puerta (AGENTS.md) dice cómo se trabaja en este repo, siempre: idioma de specs, dónde viven, convenciones, límites. Se escribe una vez y se mantiene.
  • El pasillo (el hilo de hoy) dice qué se hace ahora: prompts que referencian la spec y el plan. Se evapora sin pena porque lo importante quedó en la puerta y en spec/.

Analogía: AGENTS.md es el cartel de la puerta del taller («aquí se trabaja con planos, los planos están en spec/, no se toca data/ a mano»); el chat es la conversación de hoy junto al banco de trabajo («pásame el plano del count y ejecútalo»). Un cartel bien puesto ahorra repetir las normas a cada visitante; una conversación no puede sustituirlo.

Qué contiene un buen AGENTS.md

Corto y con punteros, no un manual: su trabajo es orientar, no especificar (eso es de spec/). Típicamente: qué es el proyecto en una línea, dónde está la fuente de verdad, convenciones innegociables y qué no hacer nunca.

El ciclo SDD sobre este entorno

┌──────────────────┐    ┌──────┐    ┌───────────┐    ┌──────────────────┐
│ SPECIFY          │───▶│ PLAN │───▶│ IMPLEMENT │───▶│ VERIFY           │
│ spec/*.md en Git │    │ hilo │    │ agente    │    │ criterios vs Git │
└──────────────────┘    └──────┘    └───────────┘    └──────────────────┘
        ▲                                                        │
        └────────── git log spec/ cuenta la historia ───────────┘
AGENTS.md (la puerta): el agente entra sabiendo dónde está todo, siempre igual

Nota multiplataforma: SDD es Markdown + Git y cambia poco entre sistemas. Dos detalles: usa rutas estilo Linux en las specs (spec/lumen.md; en el Explorador de Windows equivale a spec\lumen.md) y configura finales de línea LF (* text=auto eol=lf en .gitattributes) para que las specs no se llenen de CRLF. El CLI de Lumen corre con node en los tres sistemas.

3 · Ejemplo mínimo

El AGENTS.md más pequeño que sigue siendo útil: 13 líneas. Cada línea orienta; ninguna especifica (eso vive en spec/).

# Lumen — instrucciones para agentes  

La fuente de verdad es `spec/lumen.md`.     
Si spec y chat discrepan, gana la spec.      

## Convenciones                              
- Idioma: prosa y comentarios en español;   
  identificadores y comandos en inglés.
- La spec vive en `spec/` y se versiona     
  con el código. No edites `data/` a mano. 

## Antes de implementar                      
1. Lee la spec y el plan.                    
2. Propón el plan y espera el visto bueno.   
3. Verifica cada criterio de aceptación.

Fíjate en lo que no contiene: ni objetivos del producto, ni criterios, ni decisiones de diseño. Todo eso es spec/. Si tu AGENTS.md empieza a crecer hasta contar «qué debe hacer el producto», has metido la spec en la puerta: muévela a spec/ y deja aquí solo el puntero.

4 · Ejemplo real

Así se ve el entorno completo del proyecto Lumen que recorrerá el curso (lo conocerás en la lección 4). No es teoría: es la estructura real bajo proyectos/lumen/.

# Estructura del entorno Lumen (cada pieza tiene un porqué)
proyectos/lumen/
├── AGENTS.md              # la puerta: apunta a spec/, fija idioma y ciclo
├── spec/
│   ├── lumen.md           # la spec del producto (fuente de verdad)
│   ├── changelog.md       # historia de cambios de la spec (deltas)
│   └── adr/
│       └── 0001-almacen-json.md  # por qué JSON local y no SQLite
├── schema/
│   └── note.schema.json   # contrato de datos: la parte verificable por máquina
├── src/
│   └── cli.js             # CLI en Node vanilla: add, list, close
├── data/
│   └── notes.json         # almacén local (generado, nunca editado a mano)
└── package.json           # mínimo: sin frameworks

Las decisiones del entorno, una por una:

  • spec/ junto a src/: la intención y el código comparten repo y ritmo de commits. Un cambio de comportamiento sin cambio de spec se ve en el diff y huele mal.
  • schema/note.schema.json separado: es la parte de la spec que una máquina puede validar sola (módulo 4). El agente no discute el formato: lo valida.
  • data/ generado y protegido: el AGENTS.md prohíbe editarlo a mano porque es salida, no fuente. Si un dato está mal, se corrige el código o la spec, nunca el fichero.
  • Node vanilla, sin frameworks: el curso enseña SDD, no React. Cuantas menos capas, más claro se ve el hilo spec → plan → código → verificación.
  • OpenCode como ejemplo, patrón universal: la puerta (AGENTS.md) tiene equivalentes directos (CLAUDE.md, reglas de Cursor): mismo patrón, otro nombre de fichero.

6 · Errores habituales

El AGENTS.md que es una spec encubierta

# ❌ La puerta intenta especificar: duplica y divergirá de spec/
# El comando count debe mostrar el número de notas abiertas,
# sin filtros, en una sola línea, y responder en menos de 1s...

# ✅ La puerta apunta; la spec decide (spec/count.md)
La fuente de verdad es `spec/`. Los comportamientos, alcances
y criterios viven allí, no en este fichero.

Dos fuentes que dicen lo mismo acabarán diciendo cosas distintas. Regla: si una frase de AGENTS.md describe qué debe hacer el producto, pertenece a spec/. En la puerta solo quedan punteros, convenciones y límites.

Versionar solo el código

# ❌ La intención queda fuera del historial: nadie sabrá por qué cambió el código
git add src/                 # la spec cambió también... pero no se registra
git commit -m "cambios varios"

# ✅ Intención y código, cada uno con su mensaje: la historia se puede leer
git add spec/count.md        # primero la decisión...
git commit -m "spec: count sin filtros (ver no-objetivos)"
git add src/cli.js           # ...después la implementación que la cumple
git commit -m "feat: implementa spec de count (criterios 1-2)"

El commit de spec separada responde al «por qué» meses después; el commit «cambios varios» no responde a nada. Bonus: git log -- spec/ se convierte en el diario del producto.

Pedirle al agente sin puerta

# ❌ Cada sesión empieza de cero: el contexto se re-escribe (y se olvida)
"Hola, esto es Lumen, una app de notas en node, los specs están en spec/,
porfa no toques data/, los comentarios en español, y antes de programar
propón el plan..." (otra vez, como ayer, y como mañana)

# ✅ La puerta ya lo dice: el prompt solo trae lo de hoy
"Implementa los criterios de `spec/validation.md` según el plan acordado."

Sin puerta, cada prompt carga con contexto permanente que debería ser persistente: más tokens, más olvidos, más deriva entre sesiones. Con puerta, el prompt de hoy cabe en una línea porque lo permanente ya está escrito.

7 · Ejercicio guiado

Objetivo: montar el entorno SDD mínimo y dejarlo verificado con cinco comandos.

  1. Paso 1: verifica las tres herramientas. Necesitas Git, Node LTS y un agente (aquí OpenCode como ejemplo): 
    git --version      # memoria: necesitas Git funcionando
node --version     # ejecutor: Lumen corre con Node vanilla
opencode --version # agente de ejemplo (o abre tu Cursor / Copilot / CLI favorita)
  2. Paso 2: crea el esqueleto del repo de práctica con finales de línea sanos: 
    mkdir lumen-practica && cd lumen-practica  # tu arena de pruebas del módulo 0
git init                                  # sin repo no hay spec versionada
mkdir -p spec src data schema             # la casa de cada artefacto (ver lección 4)
printf '* text=auto eol=lf\n' > .gitattributes  # LF siempre: diffs limpios en cualquier OS
  3. Paso 3: escribe la puerta: crea AGENTS.md con el modelo mínimo de la sección 3 (qué repo es, dónde está la spec, convenciones de idioma, «no editar data/», ciclo specify → plan → implement → verify).
  4. Paso 4: registra la intención inicial y comprueba que Git la recuerda: 
    git add .gitattributes AGENTS.md   # la puerta también se versiona
git commit -m "chore: entorno inicial (puerta + LF)"
git log --oneline                    # tu primera línea de historia
git status                           # debe quedar limpio: nada pendiente
  5. Paso 5 (verificación): resultado esperado comprobable — los cinco comandos pasan: git --version y node --version responden, existe AGENTS.md con puntero a spec/, .gitattributes fija LF, y git status está limpio tras el commit. Pégale a tu agente el prompt «lee AGENTS.md y dime dónde está la fuente de verdad»: si responde spec/ sin dudar, la puerta funciona.

8 · Reto

🎯 Endurece tu puerta

Abre un proyecto real tuyo y escribe (o mejora) su AGENTS.md en 20 líneas como máximo: puntero a la fuente de verdad, 3 convenciones innegociables y 3 prohibiciones («nunca…»). Después abre una sesión nueva con tu agente, pídele que proponga un cambio pequeño y observa: ¿siguió la puerta sin que se lo repitieras? Anota qué tuviste que decirle de todos modos: eso que repetiste es lo próximo que debe entrar en la puerta.

Pista: las prohibiciones valen más que las convenciones — «no edites X», «no añadas dependencias sin ADR», «no implementes sin plan aprobado» frenan los tres desvíos más caros.

9 · Resumen

  • El entorno SDD mínimo es Git + Markdown + un agente: memoria, idioma y lector/ejecutor.
  • AGENTS.md es la puerta: instrucciones persistentes del repo, no el hilo de hoy.
  • La puerta apunta y limita; la spec (spec/) decide y verifica. No mezclarlas.
  • Intención y código comparten repo y ritmo: commits de spec separados cuentan el «por qué».
  • Detalles que pagan: rutas Linux en specs, LF en .gitattributes, Node vanilla para Lumen.

10 · Preguntas frecuentes

¿Tengo que usar OpenCode para seguir el curso?

No. Los ejemplos usan OpenCode porque es el entorno de esta Academy, pero el método es agnóstico: cualquier agente que lea ficheros del repo sirve (Cursor, Copilot, Claude Code…). El patrón es idéntico: una puerta (AGENTS.md o su equivalente), specs en Markdown y prompts que referencian. Si tu herramienta usa otro nombre de fichero-puerta, aplica lo mismo con ese nombre.

¿Por qué Markdown y no un formato más formal (YAML, una herramienta de specs)?

Porque la spec la leen humanos y agentes por igual, y Markdown es el formato que ambos leen sin fricción: difiere bien en Git, se edita en cualquier editor y no exige toolchain. Las partes que sí necesitan formalidad (el esquema de una nota) van en su formato formal (schema/note.schema.json) dentro del mismo sistema. Formato legible para decisiones, formato validable para contratos: cada uno donde rinde.

¿Cada cuánto se actualiza el AGENTS.md?

Poco: es estable por diseño. Se toca cuando cambia algo permanente (nueva convención, nuevo límite, nueva ubicación de la spec), no en cada tarea. Buen síntoma de una puerta sana: pasan semanas sin editarla y los prompts de cada día siguen siendo cortos porque referencian en vez de repetir.

¿Necesito WSL o Docker para este curso?

No. SDD es Markdown + Git y el CLI de Lumen corre con Node nativo en Linux, macOS y Windows. No hay contenedores, ni máquinas virtuales, ni servicios en la nube en ningún punto del curso. Si estás en Windows, Node nativo (o WSL si ya lo usas) basta.
