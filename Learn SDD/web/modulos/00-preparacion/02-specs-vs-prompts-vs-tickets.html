Spec vs prompt vs ticket vs README

Módulo 0 · Preparación ⏱ 30 minutos

1 · Introducción

«Spec», «prompt», «ticket» y «README» se usan como si fueran sinónimos, y no lo son. Cada uno responde a una pregunta distinta, vive en un sitio distinto y tiene un dueño distinto. Confundirlos es la causa raíz de dos fracasos clásicos: pegar un chat y llamarlo spec, y esperar que un ticket de dos líneas guíe a un agente durante dos días.

En esta lección aprenderás qué es cada artefacto, en qué se diferencian (tabla comparativa completa), cuándo basta cada uno —porque no todo merece una spec— y por qué un prompt, por bueno que sea, nunca puede ser una spec.

¿Por qué existe esta lección? Porque en la lección anterior definimos la spec por lo que es, y aquí la definimos por lo que no es. Si no distingues estos cuatro artefactos, acabarás pidiéndole a cada uno lo que no puede dar: verificabilidad a un chat, contexto persistente a un ticket, decisiones a un README.

2 · Teoría

Los cuatro artefactos, en una frase cada uno

  • Prompt: una instrucción de un solo uso en un hilo de conversación. Responde a «¿qué haces ahora?». Se evapora.
  • Ticket: una unidad de trabajo en un gestor (Jira, GitHub Issues…). Responde a «¿qué hay que hacer y quién lo hace?». Organiza, no especifica.
  • README: la puerta de entrada de un proyecto. Responde a «¿qué es esto y cómo lo uso?». Describe, no decide.
  • Spec: la fuente de verdad versionada del qué y el porqué. Responde a «¿qué debe pasar y cómo lo demostramos?». Decide y verifica.

Por qué el prompt no es una spec

Esta es la confusión que más daño hace, así que merece sus cuatro razones explícitas:

  1. El prompt no tiene memoria: depende del hilo donde se escribió. Sácalo de contexto y pierde la mitad de su significado («hazlo como el otro día»). La spec es autocontenida por diseño.
  2. El prompt no tiene no-objetivos: dice qué hacer, nunca qué no hacer. Y lo no dicho lo inventa el agente (recuerda las etiquetas «útiles» de la lección 1).
  3. El prompt no tiene criterios: «que quede bien» no se puede verificar. Un buen prompt sale de una spec («implementa el criterio 2 de spec/count.md»), pero no la sustituye.
  4. El prompt no tiene dueño ni historia: nadie lo firma, nada registra por qué cambió. La spec sí: cada cambio queda en Git con motivo.

Analogía: receta frente a «hazme la cena». El prompt es decirle a alguien «hazme la cena, algo rico»; la spec es la receta: ingredientes, cantidades, pasos y foto del resultado esperado. Con «hazme la cena» obtendrás una cena, quizá buena; con la receta obtendrás esa cena, repetible por cualquiera, verificable contra la foto. El ticket sería el pósit en la nevera («hacer la cena el viernes»); el README, el libro donde vive la receta.

Cuándo basta cada uno

No todo merece una spec, y decir lo contrario sería over-spec (módulo 6). La regla práctica:

  • Basta un prompt cuando el trabajo es trivial, reversible y de un solo paso: «renombra esta variable», «explica este error», «genera un ejemplo de uso». Si sale mal, se rehace en segundos.
  • Basta un ticket cuando hay que organizar trabajo humano (quién, cuándo, prioridad) y la decisión técnica ya está tomada o es obvia: «actualizar la dependencia X», «corregir esta errata».
  • Basta el README cuando hay que orientar a alguien que llega: instalar, ejecutar, estructura del proyecto. Describe el producto; no decide su futuro.
  • Hace falta una spec cuando un agente (u otro humano) debe implementar algo sin adivinar: hay decisiones que tomar, alcance que acotar y un «hecho» que demostrar. En la duda, pregunta: «¿podría salir mal si el implementador inventa los huecos?». Si sí, escribe la spec.

Cómo conviven: el flujo sano es ticket → spec → prompts. El ticket organiza («esta semana: comando count»), la spec decide (spec/count.md), y cada prompt al agente apunta a la spec («implementa los criterios de spec/count.md siguiendo el plan»). El README se actualiza al final, describiendo lo construido.

El ciclo SDD con estos artefactos

TICKET ("hacer count") ──▶ SPECIFY (spec/count.md) ──▶ PLAN ──▶ IMPLEMENT ──▶ VERIFY
                                   ▲                                              │
                                   │   prompt ("implementa el criterio 2...")     │
                                   └──────── ¿diverge? actualiza la SPEC ─────────┘
README (se actualiza al final: "lumen count muestra el nº de notas abiertas")

3 · Ejemplo mínimo

La misma necesidad («saber cuántas notas abiertas hay») expresada en los cuatro artefactos. Compara línea por línea qué aporta y qué le falta a cada uno.

# 1. PROMPT (hilo de chat: útil hoy, inútil mañana)
dime cuántas notas abiertas tengo, haz un comando count o algo así

# 2. TICKET (organiza el trabajo, no lo especifica)
[Tarea] Añadir comando count a Lumen | Asignado: Alex | Prioridad: media
Descripción: mostrar el número de notas abiertas.

# 3. README (describe el producto una vez existe, no decide)
## Comandos
- `lumen count`: muestra cuántas notas están abiertas.

# 4. SPEC (spec/count.md: decide, acota y verifica)  
## Objetivo                                          
El comando `count` informa cuántas notas siguen abiertas
para saber de un vistazo si la bandeja está al día.

## No-objetivos                                     
- Sin filtros por fecha ni por texto
- Sin formato decorado: salida de una sola línea legible por scripts

## Criterios de aceptación                          
- [ ] Dadas 3 notas abiertas y 2 cerradas, cuando ejecuto
  `lumen count`, entonces la salida es `3`
- [ ] Dado un almacén vacío, cuando ejecuto `lumen count`,
  entonces la salida es `0`

Lección del ejemplo: el prompt y el ticket presuponen decisiones que nadie tomó (¿cuenta también las cerradas? ¿qué formato tiene la salida?). Solo la spec las toma por escrito y da el comando que las demuestra. Por eso el prompt correcto del día de la implementación no es el de la línea 1, sino: «implementa los criterios de spec/count.md».

4 · Ejemplo real

Escenario profesional: en producción, Lumen guarda sus notas en data/notes.json. Un usuario informa de que «a veces desaparecen notas». Mira cómo cada artefacto gestiona el incidente, y por qué solo uno evita que se repita:

# TICKET (bien para organizar, insuficiente para decidir)
[Bug] Notas que desaparecen | Severidad: alta | Asignado: Sam
Descripción: dos usuarios reportan notas perdidas tras cerrar el portátil
rápido después de añadir. Reproducir y corregir.

# PROMPT al agente (ejecuta, pero no deja rastro de la decisión)
"reproduce el bug de notas perdidas y arréglalo, con cuidado con el fichero"

# README actualizado a posteriori (informa, no previene)
## Notas sobre durabilidad
Lumen escribe cada cambio en disco de forma síncrona (fsync)
para no perder notas si el equipo se apaga de golpe.

# SPEC de delta (spec/changes/0001-durable-write.md)  
## Estado actual
`saveNotes` escribe con una única llamada sin volcado a disco;
un apagado entre la escritura y el flush del SO pierde datos.
## Estado deseado
- [ ] Dada una nota recién añadida, cuando el proceso muere
  inmediatamente después de que `add` retorne, entonces la nota
  sobrevive al reinicio (escritura + fsync antes de retornar)
## Impacto y compatibilidad
- El formato de `data/notes.json` no cambia; solo el modo de escritura.

Todas las decisiones del ejemplo, explicadas:

  • El ticket hace su trabajo (priorizar, asignar) y nada más: «reproducir y corregir» no dice qué significa corregido. Sin spec, el agente elige su propia definición de hecho.
  • El prompt («con cuidado con el fichero») es preocupación sin criterio: ¿cómo verifica el agente que tuvo cuidado? No puede. La preocupación real —supervivencia al apagado— solo existe cuando se escribe como criterio.
  • El README documenta la solución una vez existe, pero nada impide que el próximo cambio la rompa: no hay ningún criterio que falle si alguien quita el fsync.
  • La spec de delta (módulo 5) es la única que convierte el susto en garantía: estado actual, estado deseado demostrable y compatibilidad declarada. El criterio «el proceso muere y la nota sobrevive» es un test que seguirá vigilando para siempre.

6 · Errores habituales

El prompt disfrazado de spec

# ❌ Prompt con formato: sigue sin no-objetivos, sin criterios, sin dueño
# system: eres un experto en node. Task: añade el comando count.
# Context: el proyecto es Lumen, una app de notas... (pega 200 líneas)
# Requirements: que funcione bien y sea robusto. Output: solo código.

# ✅ Spec de verdad: decide por escrito y se puede verificar
## Criterios de aceptación
- [ ] Dadas 3 notas abiertas y 2 cerradas, cuando ejecuto
  `lumen count`, entonces la salida es `3`

Maquillar el prompt con secciones («Context», «Requirements») no lo convierte en spec: sigue atado al hilo, sigue sin decir qué no hacer y sigue sin un comando que demuestre «robusto». La prueba es simple: ¿puede otro agente, sin acceso a tu chat, implementarlo sin preguntas? Si no, es un prompt con formato.

El ticket como spec

# ❌ Ticket que pretende especificar (pero vive fuera del repo, sin criterios)
[Tarea] Comando count
Criterios (informales): debe contar bien, rápido, y no romper list.
Story points: 3.

# ✅ Ticket + spec enlazada: cada uno hace lo suyo
[Tarea] Comando count → ver `spec/count.md` (criterios 1-2)
Cierre: `lumen count` pasa los 2 criterios en local.

«Debe contar bien» no es un criterio, es un deseo; y cuando el ticket se cierra y se archiva, el deseo se pierde. El patrón correcto: el ticket organiza y enlaza; la spec decide y permanece.

El README como promesa

# ❌ README que promete futuro (miente en cuanto el plan cambia)
## Roadmap
- Próximamente: etiquetas, búsqueda y sincronización en la nube.

# ✅ El futuro vive en specs de delta, no en el README
## Estado actual (README: solo lo que YA existe)
- `lumen add/list/close/count`: bandeja local en `data/notes.json`.
# (las etiquetas llegan como spec de cambio en el módulo 5)

El README que promete convierte cada cambio de planes en documentación falsa. Las intenciones futuras tienen su propio artefacto —la spec de delta— con estado actual, deseado, impacto y migración. El README describe el presente; nada más.

7 · Ejercicio guiado

Objetivo: clasificar cuatro artefactos reales y reescribir el que está haciendo un trabajo que no le corresponde.

  1. Paso 1: lee estos cuatro fragmentos y etiqueta cada uno (prompt, ticket, README o spec). Anota en qué te basas (dónde vive, si verifica, si acota): 
    A. "añade validación al add para que no acepte títulos vacíos, please"
B. [Bug] add acepta títulos vacíos | Asignado: Sam
C. `lumen add ""` es rechazado con mensaje de error y código distinto de 0.
D. ## Uso — `lumen add "texto"`: crea una nota abierta.
  2. Paso 2: comprueba tu clasificación: A es prompt (hilo, sin criterios), B es ticket (organiza), C es criterio de spec (demostrable: comando + salida esperada), D es README (describe uso existente).
  3. Paso 3: el fragmento C está huérfano (un criterio sin spec). Dale casa: crea spec/validation.md con objetivo, 2 no-objetivos y ese criterio más uno que cubra espacios en blanco: 
    # Validación del comando add

## Objetivo
`lumen add` rechaza títulos vacíos o en blanco para que
la bandeja no se llene de notas sin contenido.

## No-objetivos
- Sin longitud máxima de título (no hay requisito que la pida)
- Sin validación de otros comandos (solo `add` en esta spec)

## Criterios de aceptación
- [ ] Dado un almacén cualquiera, cuando ejecuto `lumen add ""`,
  entonces el comando falla con mensaje de error y no crea ninguna nota
- [ ] Dado un almacén cualquiera, cuando ejecuto `lumen add "   "`,
  entonces el comando falla igual que con cadena vacía
  4. Paso 4: escribe el prompt que usarías con el agente para implementar esto, apuntando a la spec en vez de re-describirla: 
    # Prompt correcto: referencia, no re-describe
Implementa los criterios de `spec/validation.md`.
Propón primero el plan (ficheros a tocar, casos borde) y
espera mi visto bueno antes de escribir código.
  5. Paso 5 (verificación): resultado esperado — spec/validation.md existe con las tres secciones, cada criterio incluye comando exacto y resultado exacto, y tu prompt cabe en 4 líneas porque referencia en vez de repetir. Si tu prompt necesita explicar qué validar, la spec está incompleta.

9 · Resumen

  • Cada artefacto responde a una pregunta: prompt (¿qué haces ahora?), ticket (¿qué hay que hacer?), README (¿qué es esto?), spec (¿qué debe pasar y cómo se demuestra?).
  • Solo la spec es versionada, con no-objetivos, con criterios verificables y reutilizable sin el hilo original.
  • El prompt no es una spec por cuatro razones: sin memoria, sin no-objetivos, sin criterios, sin dueño ni historia.
  • No todo merece spec: elige por el coste de adivinar mal (trivial + reversible → prompt; decisiones con huecos → spec).
  • El flujo sano: el ticket organiza y enlaza, la spec decide, los prompts referencian, el README describe al final.

PromptEjecutar un paso ahora, apuntando a la spec (nunca sustituirla)
TicketOrganizar el trabajo: quién, cuándo, prioridad; enlaza la spec
READMEOrientar a quien llega: qué es, cómo se usa (presente, no promesas)

Spec de deltaEspecificar cambios sobre lo existente (módulo 5)

10 · Preguntas frecuentes

Si escribo prompts muy detallados, ¿no equivalen a una spec?

No, por detallados que sean. Un megaprompt sigue viviendo en el hilo (sin memoria reutilizable), sigue sin versionarse en Git y sigue mezclando decisiones vigentes con intentos descartados. Además sufre el problema inverso: como hay que re-escribir el contexto en cada sesión, acaba divergiendo («la versión del martes decía otra cosa»). La spec se escribe una vez, se versiona y se referencia.

¿Desaparecen los tickets con SDD?

No: cambia su contenido. El ticket deja de intentar especificar (párrafos de requisitos que se pudren fuera del repo) y se dedica a organizar: prioridad, asignación, fechas y enlace a la spec. Un buen ticket SDD cabe en tres líneas: qué, enlace a spec/, y condición de cierre («pasan los criterios 1–3»).

¿El README no debería escribirse primero, como en el «README-driven development»?

El README-first es un primo honesto de SDD para explorar la experiencia de uso, y como prototipo funciona. Pero el README describe uso, no decide alcance ni verificación: en cuanto necesitas no-objetivos y criterios demostrables, has salido del README y entrado en la spec. Úsalo para pensar en voz alta; no lo confundas con la fuente de verdad.

¿Dónde vive cada cosa en el repo de Lumen?

Specs en spec/ (lumen.md, changes/, adr/), contratos en schema/, código en src/, y el README en la raíz describiendo lo que ya existe. Los tickets viven fuera (tu gestor favorito) enlazando a spec/; los prompts viven en tus chats y referencian los ficheros. Lo verás montado en la lección 4.
