Caso de estudio: Lumen

Módulo 0 · Preparación ⏱ 25 minutos

1 · Introducción

Todo curso necesita un ejemplo que crezca con el alumno. En este curso ese ejemplo se llama Lumen: una bandeja de notas mínima — capturar una idea en segundos desde la terminal y recuperarla después. Nada de usuarios, nada de nube, nada de frameworks: una CLI en Node.js, un fichero JSON y una spec que dice exactamente qué debe hacer.

En esta lección conocerás las tres piezas de Lumen, qué queda dentro y fuera de su alcance, y cómo lo verás evolucionar módulo a módulo hasta el proyecto final. Cuando termines, sabrás qué vamos a especificar antes de aprender cómo se especifica.

¿Por qué un caso tan pequeño? Porque la spec, no el código, es la protagonista. Con un producto diminuto, cada decisión de especificación se ve a simple vista: un no-objetivo mal puesto o un criterio vago se notan en minutos, no en sprints. Lumen es el laboratorio; el oficio que aprendas sirve para sistemas de cualquier tamaño.

Errores típicos al empezar: pedirle al agente “hazme una app de notas” sin spec (cada ejecución inventa algo distinto) y confundir el tamaño del ejemplo con la seriedad del método.

2 · Teoría

Lumen tiene tres piezas, y solo tres:

  1. spec/ — las especificaciones del producto. La fuente de verdad: lumen.md (qué y por qué), changelog.md (qué cambió) y adr/ (por qué se decidió lo difícil de revertir).
  2. cli — una CLI llamada lumen en Node.js vanilla: add, list, close. Sin dependencias.
  3. Almacén — data/notes.json: un array de notas validado contra schema/note.schema.json.

Una Nota tiene una forma estable durante casi todo el curso:

{
  "id": "muu4cl77m2t3",
  "title": "comprar pan",
  "done": false,
  "createdAt": "2026-10-04T17:52:51.283Z"
}

Solo cuatro campos: id único, title no vacío, done y createdAt en ISO 8601. Las tags no existen todavía: llegarán como delta en los módulos 5 y 7, y esa espera es deliberada (enseña a no filtrar el futuro en la spec inicial).

El mapa del viaje

Módulo 0-1 · SPECIFY ......... spec de Lumen (objetivo, no-objetivos, criterios)
Módulo 2 ... · PLAN ........... plan de implementación a partir de la spec
Módulo 3-4 · CONTRATOS ........ schema JSON + ADR del almacén
Módulo 5 ... · DELTA .......... spec de cambio: etiquetas y búsqueda
Módulo 6 ... · OFICIO ......... revisar la propia spec de Lumen
Módulo 7 ... · VERIFY ......... implementar el CLI y verificar cada criterio

El producto ya existe. En proyectos/lumen/ tienes la spec, el schema, el ADR y el CLI funcionando. No lo mires aún como código que copiar: míralo al final del curso como el examen aprobado. Cada lección te dará una pieza para entenderlo.

Qué queda fuera (y por qué se dice en voz alta)

La spec de Lumen declara sus no-objetivos desde el día uno: sin multiusuario, sin sincronización, sin web, sin cifrado. Cada uno es un malentendido que un agente habría “resuelto” inventando: sin esa lista, “añade búsqueda” podría terminar en Elasticsearch.

3 · Ejemplo mínimo

El corazón de Lumen cabe en seis líneas: un objetivo y un criterio. Léelo línea por línea:

# Lumen — bandeja de notas mínima
## Objetivo
Capturar una idea en segundos desde la terminal y recuperarla después.
## Criterios de aceptación
- [ ] Dado el almacén vacío, cuando ejecuto `add "pan"`,
      entonces `list` muestra una nota con id único y título "pan".
  • Línea 1: título que nombra el producto y su naturaleza (mínima). Nada de “plataforma”.
  • Línea 3: objetivo con verbos observables (capturar, recuperar) y restricción de contexto (desde la terminal).
  • Líneas 5-7: un criterio con contexto (Dado), acción (Cuando) y resultado demostrable (Entonces). Un agente puede implementarlo y tú puedes comprobarlo con dos comandos.

4 · Ejemplo real

Así se usa Lumen una vez implementado (esto es lo que la spec promete; el CLI real está en proyectos/lumen/):

# Crear dos notas (el almacén data/notes.json se crea solo)
node src/cli.js add "comprar pan"
# → nota creada: muu4cl77m2t3 comprar pan
node src/cli.js add "leer la spec del módulo 1"

# Ver el inbox (solo abiertas)
node src/cli.js list
# → [ ] muu4cl77m2t3 comprar pan
# → [ ] muu4cl9kq1x0 leer la spec del módulo 1

# Cerrar una y comprobar que sale del inbox pero sigue existiendo
node src/cli.js close muu4cl77m2t3
node src/cli.js list --all
# → [x] muu4cl77m2t3 comprar pan
# → [ ] muu4cl9kq1x0 leer la spec del módulo 1

Decisiones visibles aquí que vienen de la spec, no del código: close no borra (las notas cerradas se conservan con done: true); list muestra solo abiertas por defecto; todo error habla español y sale con código ≠ 0. Ninguna de estas tres cosas es “obvia”: alguien tuvo que decidirlas y escribirlas.

5 · Buenas prácticas

HazEvitaPor qué
Fijar el contrato de datos antes que el código (note.schema.json) Añadir campos “por si acaso” (tags antes del delta) El contrato estable permite implementar y verificar sin reescribir; lo futuro llega como delta con su propia spec
Escribir los no-objetivos el primer día “Ya lo acotaremos después” Cada semana sin no-objetivos es una funcionalidad inventada por alguien (humano o agente)
Mantener spec, changelog y ADR juntos en spec/ La spec en la wiki, el código en el repo, las decisiones en el chat Lo disperso diverge; lo versionado junto se revisa junto
Usar Lumen como referencia, no como plantilla ciega Copiar su spec cambiando dos palabras para otro producto El valor está en el razonamiento (qué/cómo demostrarlo), no en el texto

6 · Errores habituales

Pedir el producto sin spec

# ❌ "Hazme una app de notas con Node"
# Cada ejecución inventa algo distinto: SQLite hoy, Mongo mañana,
# con login, con colores, sin forma de saber qué está "bien".

# ✅ "Implementa spec/lumen.md con su plan. Verifica cada criterio."
# La spec fija el qué; el plan fija el cómo; la verificación decide el done.

Especificar la solución en vez del comportamiento

# ❌ "Usa un Map en memoria indexado por timestamp"
# Eso es diseño de implementación: ata las manos y no se puede demostrar
# desde fuera.

# ✅ "Dado el almacén vacío, cuando ejecuto `add "pan"`,
#     entonces `list` muestra una nota con id único y título "pan""
# Comportamiento observable: cualquier implementación válida lo cumple.

Confundir pequeño con trivial

Lumen es pequeño a propósito para que la spec sea la protagonista. Despreciar el ejemplo por su tamaño es perderse el método: los mismos artefactos (no-objetivos, criterios, deltas, ADRs) escalan a sistemas de cualquier tamaño.

7 · Ejercicio guiado

Objetivo: arrancar el almacén de tu propio Lumen y demostrar el ciclo completo add → list → close.

  1. Paso 1: abre una terminal en proyectos/lumen/ y pide ayuda: 
    node src/cli.js --help
    Resultado esperado: los comandos add, list y close descritos en español, código de salida 0.
  2. Paso 2: crea una nota en un almacén de prueba (para no ensuciar el tuyo): 
    node src/cli.js add "mi primera nota" --store data/practica.json
    Resultado esperado: nota creada: <id> mi primera nota.
  3. Paso 3: lista y cierra: 
    node src/cli.js list --store data/practica.json
node src/cli.js close <id> --store data/practica.json
node src/cli.js list --store data/practica.json
node src/cli.js list --all --store data/practica.json
    Resultado esperado: la nota aparece, desaparece del inbox tras close y reaparece marcada con [x] en --all.
  4. Paso 4: abre data/practica.json y comprueba que es un array con tu nota (done: true). Luego bórralo: era un almacén desechable.

8 · Reto

🎯 La spec de tu propia bandeja

Escribe en 15 líneas la spec de tu bandeja ideal: objetivo en una frase, 3 no-objetivos, y 2 criterios de aceptación con formato Dado/Cuando/Entonces que se puedan demostrar con comandos. No implementes nada todavía.

Pista: compara cada línea con la plantilla del cheatsheet y pregúntate “¿podría un agente implementar esto sin llamarme?”.

9 · Resumen

  • Lumen es una bandeja de notas mínima: spec/ + CLI lumen (add, list, close) + data/notes.json.
  • Una Nota son cuatro campos estables: id, title, done, createdAt. Sin tags hasta el delta.
  • Los no-objetivos (sin multiusuario, sin web, sin cifrado) se declaran el día uno.
  • El curso recorre Lumen en orden SDD: spec → plan → contratos → delta → oficio → verify.
  • El proyecto completo vive en proyectos/lumen/; al final del curso sabrás leer cada fichero como consecuencia de una decisión escrita.

10 · Preguntas frecuentes

¿Por qué Node.js y JSON y no una base de datos de verdad?

Porque el curso va de specs, no de bases de datos. JSON plano tiene cero dependencias, se lee con cualquier editor y se versiona en Git. El ADR 0001-almacen-json.md registra exactamente esa decisión y sus consecuencias, incluida la puerta de salida (migrar a SQLite sin cambiar el contrato de Nota).

¿Puedo usar Lumen para mis notas de verdad?

Puedes, pero no es su propósito: le faltan búsqueda, etiquetas y edición (llegan como deltas en los módulos 5 y 7). Úsalo como laboratorio del método; si te enamoras de él, esos deltas son tus primeros ejercicios con spec de cambio real.

¿La UI web forma parte de Lumen?

No en esta spec: es un no-objetivo explícito. Aparece como posible delta futuro precisamente para enseñar a especificar cambios sin reescribir el mundo. Si la echas de menos, buena señal: ya piensas en deltas.

¿Tengo que programar el CLI yo desde cero?

No. El CLI de referencia ya existe en proyectos/lumen/ y el módulo 7 te guía para implementarlo y verificarlo contra la spec. El objetivo del curso es que sepas especificar, planificar y verificar; el código es la consecuencia, no el examen.
