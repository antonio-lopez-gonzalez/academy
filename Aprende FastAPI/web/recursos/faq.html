FAQ general del curso

FAQ ❓ Dudas comunes del curso

General

¿Qué necesito saber antes de empezar el curso?

Saber programar en Python (el curso usa 3.12+ y uv) y manejarte con la terminal y Git. No se asume FastAPI previo: ASGI, la validación con Pydantic y la inyección de dependencias se explican desde cero y con el «por qué» delante. Si vienes de .NET o Node, los conceptos de HTTP, JSON y middleware te resultarán familiares; si vienes de Python «puro», el salto es pequeño.

¿Cuánto tiempo requiere y qué construyo?

Son 8 módulos (0-7) con 32 lecciones y 3 recursos. Cada lección está pensada para 30-45 minutos más el reto. El hilo conductor es Copiloto API: empiezas con un @app.get("/health") y acabas con una API real con base de datos, JWT, tests y despliegue en contenedor. Los ejercicios construyen piezas de ese mismo proyecto, así que conviene hacerlos, no solo leerlos.

¿Necesito Docker o una base de datos instalada para seguir el curso?

No para la mayor parte. El desarrollo usa SQLite, que es un simple archivo y no requiere servidor. Docker aparece en el módulo de despliegue como la forma de empaquetar la API, pero es opcional para entender los módulos anteriores. La config se lee de variables de entorno / .env, así que cambiar de SQLite a PostgreSQL es cuestión de una URL, no de reescribir el código.

Comparaciones y elección de framework

¿FastAPI vs Flask? ¿Y vs Django?

No compiten en la misma categoría exacta:

FrameworkCuándo encajaQué sacrificas
FastAPIAPIs HTTP (JSON), validación, docs automáticas, asyncNo trae ORM, panel de admin ni plantillas: los eliges tú
FlaskApps pequeñas, prototipos, control total y minimalistaValidación, serialización y docs son trabajo manual (o extensiones)
DjangoProducto «todo en uno»: ORM, admin, auth, plantillasMás peso y opinión; su capa de validación no es tan directa como Pydantic

Si tu entregable es una API, FastAPI gana por tipado, validación y OpenAPI desde el primer minuto. Django sigue siendo excelente cuando necesitas su ecosistema completo (admin, plantillas, tareas).

¿Puedo usar FastAPI junto a Django o una base de código existente?

Sí. FastAPI es una app ASGI y se puede montar junto a otro servicio (por ejemplo, detrás del mismo proxy) o convivir con el ORM de un proyecto existente. La parte que reutilizas es el acceso a datos (tu ORM, tus repositorios); lo que aportas con FastAPI es la capa HTTP: rutas, validación con Pydantic, dependencias y el contrato OpenAPI. No hay que reescribir la persistencia para empezar a usar FastAPI.

¿FastAPI es «solo para machine learning»?

No. Se popularizó sirviendo modelos, pero es un framework de APIs general: catálogos, CRUD, webhooks, backends de aplicaciones. En este curso la API expone el Copiloto (heredado de Aprende IA), pero la estructura que aprendes —rutas, modelos, dependencias, repositorios, JWT, tests— es la misma para cualquier dominio.

Código, validación y diseño

¿Escribo endpoints async def o def?

Depende de si el trabajo bloquea o no:

SituaciónEscribePor qué
Llamas a un servicio con cliente async (httpx)async defNo bloqueas el bucle de eventos: atiende otras peticiones mientras espera
Usas un ORM/cliente sync (SQLModel sync, requests)defFastAPI lo ejecuta en un threadpool; no congelas el bucle
E/S bloqueante dentro de un async def❌ evítaloBloquea toda la app mientras dura la llamada

La regla práctica: elige una estrategia por capa y sé coherente. El curso usa def para los endpoints que tocan la BD sync y async def para los que llaman a servicios externos con httpx.

¿Por qué Pydantic y no validar «a mano»?

Porque la validación manual es código repetido, fácil de dejar incompleto y difícil de documentar. Con Pydantic declaras el esquema una vez y obtienes tres cosas a la vez: validación al entrar (con 422 detallado), serialización al salir y el JSON Schema que alimenta el OpenAPI. Además, las descripciones de Field son documentación para quien consume tu API. En v2 el núcleo es Rust, así que validar no es un cuello de botella.

¿Cuándo uso Depends? ¿No basta con funciones normales?

Depends resuelve dos problemas que las funciones normales no: la sesión de base de datos o el usuario autenticado deben abrirse y cerrarse por petición (con yield), y deben ser fáciles de sustituir en tests (app.dependency_overrides). Además, FastAPI resuelve y cachea el grafo de dependencias, así que compartir una dependencia entre varios endpoints no la ejecuta de más. Es la diferencia entre «mi función sabe dónde está la BD» y «la BD me llega como parámetro» (Módulo 3).

¿Es obligatorio modelar la salida con response_model?

Técnicamente no, en la práctica sí. response_model cumple dos funciones: filtra lo que se envía (un campo que no declaras no sale, aunque el objeto lo tenga) y documenta la respuesta en OpenAPI. Saltarlo es la vía típica a fugas de datos: devuelves el hash de la contraseña, un dato interno o campos de otro usuario sin darte cuenta. Separa siempre el modelo de entrada (lo que aceptas) del de salida (lo que expones).

Datos, migraciones y seguridad

¿Por qué SQLModel y no SQLAlchemy o un ORM «mágico»?

SQLModel combina SQLAlchemy 2.0 (la capa de datos seria, con SQL explícito) y Pydantic (validación), así que un mismo modelo puede declarar la tabla y el esquema, reduciendo duplicación. No es «mágico»: por debajo hay SQL que puedes y debes inspeccionar. El curso te muestra las consultas que genera y el problema N+1, porque un ORM sin entender el SQL es una fuente de sorpresas de rendimiento.

¿Por qué migraciones con Alembic en vez de create_all?

create_all solo crea las tablas que faltan: no altera columnas, no gestiona índices existentes y no deja rastro de qué cambió ni cuándo. Alembic versiona cada cambio como una revisión con upgrade y downgrade, de modo que tu base local, la de CI y la de producción llegan al mismo esquema con alembic upgrade head. En el curso create_all se usa como atajo de arranque; en cuanto hay datos que preservar, se pasa a Alembic (Módulo 4).

¿JWT o sesiones con cookie para autenticar?

Para una API consumida por clientes móviles o SPA, el curso usa OAuth2 password flow + JWT: el login devuelve un token firmado y el cliente lo envía en Authorization: Bearer <token>. El servidor lo verifica sin consultar la BD, lo que escala bien. Su pega: un JWT filtrado vale hasta que expira, así que se usan expiraciones cortas y (si hace falta) revocación. Las sesiones con cookie son más cómodas para web con navegador, pero añaden CSRF y estado en servidor (Módulo 5).

¿Dónde guardo las claves y secretos?

Nunca en el repositorio. La clave de firma del JWT, la URL de la base de datos y cualquier API key van en variables de entorno, leídas con pydantic-settings desde un .env que está en .gitignore. En producción se inyectan desde el gestor de secretos de la plataforma. Además, versiona un .env.example con las claves sin valores para documentar qué hace falta.

Tests, despliegue y calidad

¿Cómo testeo la API sin levantar un servidor?

Con TestClient (basado en httpx), que ejecuta la app en memoria: haces client.get("/items/1") y compruebas status, body y cabeceras. Para pruebas async se usa httpx.AsyncClient con ASGITransport y fixtures de pytest. Para bases de datos, se levanta una base temporal y se aísla por test, sustituyendo la dependencia con app.dependency_overrides (Módulo 6).

¿Cómo despliego la API a producción?

El patrón es: un Dockerfile que instala dependencias con uv sync, arranca uvicorn y escucha en 0.0.0.0:8000; varios trabajadores detrás de un proxy inverso (Nginx, Caddy o el del proveedor); migraciones con alembic upgrade head como paso previo; y logging estructurado. En el servidor, los secretos llegan por variables de entorno y --reload desaparece: eso es solo de desarrollo (Módulo 7).

¿Cómo documento la API y la versiono?

La documentación es gratis: FastAPI genera OpenAPI desde tus tipos y lo sirve en /docs, /redoc y /openapi.json. Cuida los title, description y examples de los modelos, porque son la doc que lee el cliente. Para versionar, prefija las rutas (/api/v1) desde el principio: evolucionar el contrato sin romper a los consumidores es una decisión que se toma antes, no después.

Si una duda no está aquí, suele resolverse en la lección correspondiente: empieza por el glosario para el vocabulario y por el cheatsheet para la sintaxis exacta.
