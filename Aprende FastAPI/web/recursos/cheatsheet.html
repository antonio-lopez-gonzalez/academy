App y decoradores de ruta

Cada path operation es una función de Python con una anotación de tipo por parámetro y otra de retorno. FastAPI lee esas anotaciones para validar la entrada y serializar la salida; el @decorador solo declara método y path.

from fastapi import FastAPI, status

app = FastAPI(title="Copiloto API", version="1.0.0")

@app.get("/health", tags=["meta"])
async def health() -> dict[str, str]:
    return {"status": "ok"}

@app.get("/items/{item_id}")
async def read_item(item_id: int) -> dict[str, int]:
    return {"id": item_id}

@app.post("/items", status_code=status.HTTP_201_CREATED)
async def create_item(item: Item) -> Item:
    return item

# Varios métodos sobre el mismo path:
@app.api_route("/ping", methods=["GET", "HEAD"])
async def ping() -> dict[str, str]:
    return {"pong": "ok"}

Docs automáticas desde el propio esquema: /docs (Swagger UI), /redoc y el contrato crudo en /openapi.json. Si cambias el tipo de un parámetro, el contrato cambia solo.

Parámetros: path, query y body

FastAPI deduce el origen del dato: si el nombre está en el path de la ruta es path param; si es un tipo simple y no está en el path, es query param; si es un modelo Pydantic, es el body. Con Annotated lo declaras de forma explícita y añades validación.

from typing import Annotated
from fastapi import FastAPI, Path, Query, Body
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    name: str
    price: float

@app.put("/items/{item_id}")
async def update_item(
    item_id: Annotated[int, Path(ge=1, le=1000, title="ID del item")],
    q: Annotated[str | None, Query(max_length=50, alias="search")] = None,
    limit: Annotated[int, Query(ge=1, le=100)] = 10,
    item: Item | None = None,
    importance: Annotated[int, Body(ge=0, le=5)] = 0,
):
    return {"item_id": item_id, "q": q, "limit": limit, "item": item, "importance": importance}

Orden de argumentos en Python: los parámetros con valor por defecto van después de los que no lo tienen. Annotated evita el truco de poner * para forzar que los «obligatorios» de la query queden a la izquierda.

Pydantic v2: modelos, Field y validadores

Un BaseModel es el contrato de datos: valida al entrar (model_validate) y serializa al salir (model_dump). En v2 la validación la ejecuta el núcleo en Rust, así que es rápida; tu trabajo es declarar tipos y restricciones, no escribir if para cada campo.

from typing import Annotated
from pydantic import BaseModel, Field, EmailStr, field_validator, model_validator
from typing_extensions import Self

class UserCreate(BaseModel):
    # Configuración común del modelo (Pydantic v2): mejor ConfigDict que class Config.
    model_config = {"extra": "forbid", "str_strip_whitespace": True}

    username: Annotated[str, Field(min_length=3, max_length=20, pattern=r"^[a-z0-9_]+$")]
    email: EmailStr
    age: Annotated[int, Field(ge=18, le=120)]
    password: Annotated[str, Field(min_length=8, exclude=True)]   # exclude: no se serializa
    tags: list[str] = Field(default_factory=list)                 # nunca [] mutable por defecto

    @field_validator("username")
    @classmethod
    def lower(cls, v: str) -> str:
        return v.lower()

    @model_validator(mode="after")
    def check_password(self) -> Self:
        if self.username in self.password:
            raise ValueError("la contraseña no puede contener el usuario")
        return self
Opción de FieldQué hace
default / default_factoryValor por defecto; el segundo para mutables
ge, gt, le, ltRangos numéricos (≥, >, ≤, <)
min_length, max_lengthLongitud de cadenas y colecciones
patternExpresión regular que debe cumplir el texto
alias / validation_aliasNombre alternativo para entrada/salida
title, description, examplesDocumentación que se vuelca en el OpenAPI
excludeNo incluir el campo al serializar
 
# API de un modelo en v2 (la v1 con .dict() / .parse_obj() ya no se usa)
user = UserCreate.model_validate(payload)      # valida un dict (o desde ORM con from_attributes=True)
data = user.model_dump(exclude={"password"})   # dict serializable
raw  = user.model_dump_json()                  # JSON string
esq  = UserCreate.model_json_schema()          # JSON Schema del modelo

Los validadores de campo se declaran con @field_validator y @classmethod; los de modelo, con @model_validator(mode="after"). Si vienes de v1, esto reemplaza a @validator y @root_validator.

Dependencias: Depends

Una dependencia es una función que FastAPI ejecuta antes de tu endpoint y cuyo resultado inyecta como argumento. Es la forma de compartir sesión de BD, usuario autenticado, configuración o cliente HTTP sin variables globales. Con yield también limpia después de responder.

from typing import Annotated
from fastapi import Depends, FastAPI, HTTPException, status
from sqlmodel import Session

app = FastAPI()

def get_session():                     # dependencia con yield: abre y cierra
    with Session(engine) as session:
        yield session

SessionDep = Annotated[Session, Depends(get_session)]   # alias reutilizable

def get_current_user(token: str = Depends(oauth2_scheme), db: SessionDep = None) -> User:
    user = decode_and_load(token, db)
    if user is None:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, detail="Token inválido")
    return user

CurrentUser = Annotated[User, Depends(get_current_user)]

@app.get("/me")
async def read_me(user: CurrentUser) -> User:
    return user

Funcióndef dep(...)Lógica sync (accede a BD sync)
Córutinaasync def dep(...)Operación de E/S async (httpx)
Con limpiezadef dep(): ... yield r; ...Abrir/cerrar recursos por petición

A nivel de router/appdependencies=[Depends(verify_key)]Ejecutar sin pedir el valor de retorno

Respuestas, errores y response_model

response_model es la frontera de salida: fastapi valida y filtra lo devuelto, así que un campo que no declares no se filtra aunque exista en el objeto (por ejemplo, el hash de la contraseña). Úsalo siempre.

from fastapi import FastAPI, HTTPException, status
from fastapi.responses import JSONResponse

app = FastAPI()

class UserOut(BaseModel):
    id: int
    username: str
    # password_hash NO está: jamás sale

@app.get("/users/{user_id}", response_model=UserOut, responses={404: {"description": "No existe"}})
async def read_user(user_id: int) -> UserOut:
    user = repo.get(user_id)
    if user is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Usuario no encontrado",
        )
    return user                          # se convierte a UserOut y se filtran campos

# Problem Details (RFC 9457) para errores con forma consistente
def problem(status_code: int, title: str, detail: str) -> JSONResponse:
    return JSONResponse(
        status_code=status_code,
        media_type="application/problem+json",
        content={"type": "about:blank", "title": title, "status": status_code, "detail": detail},
    )

Modela siempre la salida con un modelo distinto del de entrada. Reutilizar el modelo de la tabla como respuesta es la vía rápida a fugas de datos (contraseñas, campos internos, datos de otros usuarios).

Códigos de estado

Usa las constantes de fastapi.status, no números mágicos: se leen solos y evitan el clásico return {"error": "..."} con un 200 OK mintiendo.

from fastapi import status

status.HTTP_200_OK                    # 200
status.HTTP_201_CREATED               # 201
status.HTTP_204_NO_CONTENT            # 204 (sin cuerpo)
status.HTTP_400_BAD_REQUEST           # 400
status.HTTP_401_UNAUTHORIZED          # 401 (falta o falla autenticación)
status.HTTP_403_FORBIDDEN             # 403 (autenticado, sin permiso)
status.HTTP_404_NOT_FOUND             # 404
status.HTTP_409_CONFLICT              # 409 (duplicado)
status.HTTP_422_UNPROCESSABLE_ENTITY  # 422 (validación; lo lanza FastAPI solo)
status.HTTP_500_INTERNAL_SERVER_ERROR # 500

Routers, lifespan y organización

Divide la API en módulos con APIRouter y monta cada uno con un prefijo; abre los recursos costosos (motor de BD, cliente HTTP) una vez en lifespan, no por petición.

from contextlib import asynccontextmanager
from fastapi import APIRouter, FastAPI
from sqlmodel import create_engine, SQLModel

# app/routers/items.py
router = APIRouter(prefix="/items", tags=["items"])

@router.get("/")
async def list_items() -> list[dict]:
    return []

# app/main.py
engine = create_engine("sqlite:///./copiloto.db")

@asynccontextmanager
async def lifespan(app: FastAPI):
    SQLModel.metadata.create_all(engine)   # o mejor: alembic upgrade head
    yield                                   # aquí atiende peticiones
    engine.dispose()                        # aquí limpia al apagar

app = FastAPI(title="Copiloto API", lifespan=lifespan)
app.include_router(router)

Comandos: uv, uvicorn y alembic

# uv: proyecto, entorno y dependencias (Python 3.12+)
uv init copiloto-api                        # crea pyproject.toml + .venv
uv add fastapi "uvicorn[standard]"          # runtime
uv add sqlmodel pydantic-settings alembic   # datos y configuración
uv add "passlib[bcrypt]" "python-jose[cryptography]"   # auth
uv add --dev pytest httpx ruff mypy          # calidad y tests
uv sync                                      # crea/sincroniza el entorno
uv run python -c "import fastapi; print(fastapi.__version__)"
# uvicorn: servidor ASGI
uv run uvicorn app.main:app --reload          # desarrollo (recarga al guardar)
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000   # accesible en red
uv run uvicorn app.main:app --workers 4       # producción tras un proxy
# alembic: migraciones versionadas (no create_all en producción)
alembic init migrations                        # estructura inicial
alembic revision --autogenerate -m "create history"   # genera la migración
alembic upgrade head                           # aplica todo lo pendiente
alembic downgrade -1                           # revierte la última
alembic current                                # revisión aplicada ahora
# Servir la web del curso (desde "Aprende FastAPI/")
npm run serve                                  # sirve web/ en local

El objetivo del servidor uvicorn es modulo:variable. Si tu app vive en app/main.py y se llama app, el objetivo es app.main:app. --reload es solo para desarrollo: en producción usa trabajadores y un proceso gestor.
