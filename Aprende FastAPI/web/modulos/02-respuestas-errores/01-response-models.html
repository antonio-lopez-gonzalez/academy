response_model y serialización segura

Módulo 2 · Respuestas y errores 🕐 30 minutos

1 · Introducción

En el módulo 1 validaste lo que entra: el cuerpo de la petición, los path params y los query params. Modelaste la entrada. Pero una API no solo recibe: devuelve. Y casi todas las fugas de datos que ves en producción no vienen de un ataque, sino de responder de más: un hash de contraseña, una clave interna, la ruta física de un archivo, el embedding de un documento.

Esta lección es la que cierra ese agujero. Vas a aprender a declarar la forma de la salida con response_model, a entender que FastAPI filtra lo que no declaras, y a serializar objetos del mundo real (modelos de base de datos, dataclasses) sin filtrar secretos.

¿Por qué existe response_model? Porque el contrato de una API tiene dos mitades: qué acepta y qué devuelve. Igual que no dejas pasar cualquier cuerpo sin validarlo, no deberías devolver cualquier diccionario sin filtrarlo. response_model convierte «lo que devuelve esta ruta» en un contrato documentado, validado y seguro.

La fuga más común de una API: devolver el objeto de base de datos tal cual. Ese objeto tiene más columnas de las que el cliente necesita —y a veces alguna que nunca debería salir de tu servidor—. response_model es la frontera que impide que «el objeto completo» llegue al cliente.

2 · Teoría

Entrada y salida son dos contratos distintos

Cuando registras una ruta con @app.post("/modules", response_model=ModuleOut), le dices a FastAPI tres cosas a la vez:

  • Validar: el objeto que devuelvas debe encajar con ese modelo. Si no encaja, es un error tuyo, no del cliente, y debe fallar ruidosamente.
  • Filtrar: los campos que no están declarados en el modelo se descartan antes de responder.
  • Documentar: el esquema de salida entra en el OpenAPI, así que /docs y los clientes generados saben exactamente qué reciben.

El filtrado es lo importante aquí. Mira qué ocurre: tú devuelves un objeto, y FastAPI lo pasa por el molde del response_model antes de serializarlo a JSON.

   lo que devuelve tu funcion            response_model            JSON que sale
   ----------------------------          --------------            --------------

   {
     "id": 7,
     "slug": "rutas",              valida y FILTRA        {
     "title": "Rutas",             los campos   ------>      "id": 7,
     "api_key": "sk-live-...",      no declarados             "slug": "rutas",
     "embedding": [0.1, 0.2, ...],                            "title": "Rutas"
     "file_path": "/srv/data/modules/rutas.md"
   }                                                       }

   ^ el objeto "gordo" de tu servicio              ^ el contrato publico y seguro

Fíjate en que api_key, embedding y file_path desaparecen sin que tú escribas ningún del. Solo se configura una vez, en el decorador.

Por qué UserIn y UserOut son modelos distintos

El error de principiante es reutilizar el modelo de entrada como modelo de salida. No comparten responsabilidades:

AspectoModelo de entrada (In)Modelo de salida (Out)
Contiene secretosSí (password, tokens)Nunca
Necesita id y fechasNo (los asigna el servidor)Sí
Lo controlaEl clienteTu servidor

Analogía: es el mostrador de un hotel. El formulario de check-in (entrada) incluye tu documento y tu contraseña del WiFi. La factura (salida) incluye tu nombre, tu habitación y el importe —jamás tu contraseña—. Mismo cliente, dos documentos con campos distintos. Confundirlos sería imprimir la contraseña en la factura.

Dónde vive model_config

En Pydantic v2, la configuración del modelo se declara en un atributo especial model_config (un ConfigDict). Las dos claves que más usarás en una API son:

  • from_attributes=True — permite construir el modelo desde un objeto con atributos (por ejemplo, una fila de SQLModel/SQLAlchemy) y no solo desde un dict. Es lo que hará que el módulo 4 pueda devolver objetos de la base de datos sin convertirlos a mano.
  • extra="forbid" — rechaza claves desconocidas. En entrada es un regalo para detectar erratas del cliente; en salida no aplica igual, porque el filtrado ya descarta lo que sobra.

Regla mental: response_model controla qué campos salen. model_config controla cómo se construye y se serializa el modelo. Son cosas distintas que se combinan.

3 · Ejemplo mínimo

El caso canónico: crear un usuario que llega con password y devolverlo sin el password. Sin response_model, el hash se filtra. Con él, desaparece.

main.py
# main.py — entrada y salida son modelos distintos.
from pydantic import BaseModel, EmailStr


class UserIn(BaseModel):
    username: str
    password: str          # llega del cliente y NUNCA se devuelve
    email: EmailStr


class UserOut(BaseModel):
    username: str          # solo lo que el cliente necesita
    email: EmailStr
main.py
from fastapi import FastAPI

app = FastAPI()


@app.post("/users", response_model=UserOut)
async def create_user(user: UserIn) -> UserOut:
    # ... aqui guardarias el usuario y hashearias el password ...
    stored = {"username": user.username, "email": user.email, "password_hash": "pbkdf2$..."}
    return stored          # FastAPI filtra: "password_hash" no esta en UserOut
terminal
uv run fastapi dev main.py
# En otra terminal:
curl -s http://127.0.0.1:8000/users \
  -H "Content-Type: application/json" \
  -d '{"username":"ana","password":"s3creto","email":"ana@example.com"}'

Salida esperada (observa que password_hash no aparece, aunque el servicio lo devolvió):

JSON
{
  "username": "ana",
  "email": "ana@example.com"
}

Línea por línea:

  1. UserIn vs UserOut: dos clases, dos contratos. UserIn puede tener secretos; UserOut es lo publicable.
  2. response_model=UserOut: le dice a FastAPI que use UserOut como molde de salida. Es el único cambio que hace magia.
  3. -> UserOut: repetir el tipo de retorno documenta la intención y satisface a mypy. FastAPI lo usa como response_model si no lo pasas en el decorador.
  4. return stored: devuelves un dict «gordo» a propósito. FastAPI valida contra UserOut y descarta password_hash.

Si un campo obligatorio de UserOut faltara en lo que devuelves, FastAPI lanzaría un error de validación de respuesta (HTTP 500). Eso es bueno: significa que tu contrato se cumple o el fallo aparece en desarrollo, no en producción.

4 · Ejemplo real

En Copiloto API, un módulo del RAG (una lección indexada) tiene montones de campos internos: el texto crudo, el embedding, la ruta del archivo fuente. El cliente solo necesita cuatro. Esa es la frontera que modelamos ahora.

proyectos/copiloto-api/app/schemas/module.py
# app/schemas/module.py — contrato de salida del Copiloto.
from datetime import datetime

from pydantic import BaseModel, ConfigDict, Field


class ModuleOut(BaseModel):
    """Lo que el cliente VE de un modulo. Nada mas."""

    # from_attributes permite construir este modelo desde una fila de BD
    # (SQLModel/SQLAlchemy) sin convertirlo a dict a mano.
    model_config = ConfigDict(from_attributes=True)

    id: int
    slug: str = Field(examples=["02-respuestas-errores"])
    title: str
    # El embedding, el texto completo y la ruta en disco NO se declaran:
    # al no estar aqui, response_model los filtra automaticamente.
proyectos/copiloto-api/app/routers/modules.py
# app/routers/modules.py — la ruta declara su contrato de salida.
from fastapi import APIRouter, HTTPException

from app.schemas.module import ModuleOut

router = APIRouter(prefix="/modules", tags=["modules"])


@router.get("/{slug}", response_model=ModuleOut)
async def get_module(slug: str) -> ModuleOut:
    module = await modules_repo.get_by_slug(slug)   # objeto completo, con embedding
    if module is None:
        raise HTTPException(status_code=404, detail=f"Modulo '{slug}' no encontrado")
    return module        # FastAPI construye ModuleOut y descarta el resto

Y aquí el otro extremo del hilo: la respuesta de POST /ask. El motor de RAG devuelve también las puntuaciones internas de similitud y el prompt completo que envió al modelo. El cliente necesita la respuesta y las fuentes citadas —nada más—.

proyectos/copiloto-api/app/schemas/ask.py
# app/schemas/ask.py — entrada y salida del endpoint /ask.
from datetime import datetime

from pydantic import BaseModel, ConfigDict, Field


class AskIn(BaseModel):
    question: str = Field(min_length=1, max_length=500, examples=["¿Que es un embedding?"])


class SourceOut(BaseModel):
    """Una cita: de que modulo salio y con que parecido."""

    model_config = ConfigDict(from_attributes=True)

    slug: str
    title: str
    score: float      # el cliente SI quiere la relevancia
    # "raw_text" y "chunk_embedding" del objeto interno quedan filtrados


class AskOut(BaseModel):
    answer: str
    sources: list[SourceOut]
    created_at: datetime
    # "prompt_sent_to_model" y "tokens_used" son telemetria interna:
    # no se declaran y por tanto no salen.

Decisiones y porqués:

  • Un esquema Out por entidad pública: el filtrado no depende de que el desarrollador recuerde borrar el secreto. Depende del contrato, que se revisa una vez.
  • from_attributes=True: prepara el terreno para el módulo 4. Cuando la fuente sea una fila de SQLModel, return module seguirá funcionando sin transformaciones.
  • score sí, chunk_embedding no: la relevancia es información útil para el usuario; el vector interno, además de enorme, revela tu implementación.
  • Los campos internos se omiten, no se documentan como secretos: el OpenAPI solo muestra answer, sources y created_at. El contrato es la verdad, y es una verdad pequeña.

Comprueba siempre en /docs: entra en GET /modules/{slug} y mira el Response. Si ves un campo que no querías publicar, no lo borres del servicio: examina tu Out. El problema casi siempre está en el molde, no en los datos.

5 · Buenas prácticas

HazEvitaPor qué
Declara response_model en toda ruta que devuelva datos Devolver dict «como salga» Sin molde no hay filtrado ni contrato en el OpenAPI

6 · Errores habituales

Devolver el objeto de base de datos sin molde

Mal — sin response_model, sale todo 
# ❌ El cliente recibe el hash del password y todos los campos internos.
@app.post("/users")
async def create_user(user: UserIn):
    stored = await repo.save(user)      # el objeto de BD tiene password_hash
    return stored
Bien — con molde, se filtra 
# ✅ Solo se expone lo declarado en UserOut; el hash nunca sale.
@app.post("/users", response_model=UserOut)
async def create_user(user: UserIn) -> UserOut:
    stored = await repo.save(user)
    return stored

Reutilizar el modelo de entrada como salida

Mal — un solo modelo con secretos dentro 
# ❌ User incluye password, asi que la respuesta lo devuelve.
class User(BaseModel):
    username: str
    password: str
    email: EmailStr

@app.post("/users", response_model=User)
async def create_user(user: User):
    return user          # el password viaja de vuelta al cliente
Bien — modelos separados 
# ✅ Entrada con password, salida sin el.
class UserIn(BaseModel):
    username: str
    password: str
    email: EmailStr

class UserOut(BaseModel):
    username: str
    email: EmailStr

@app.post("/users", response_model=UserOut)
async def create_user(user: UserIn) -> UserOut:
    return user          # UserOut descarta password

Creer que el tipo de retorno Any filtra algo

Mal — -> Any desactiva el contrato 
# ❌ Any no define forma: no hay esquema ni filtrado garantizado.
from typing import Any

@app.get("/modules/{slug}")
async def get_module(slug: str) -> Any:
    return await repo.get_full(slug)     # embedding y texto crudo incluidos
Bien — tipo concreto que filtra 
# ✅ El tipo concreto es el contrato: se publica y se respeta.
@app.get("/modules/{slug}")
async def get_module(slug: str) -> ModuleOut:
    return await repo.get_full(slug)

Convertir todo a dict a mano «para controlar»

Mal — manual y frágil 
# ❌ Si mañana anades un campo interno, olvidas excluirlo aqui.
@app.get("/modules/{slug}")
async def get_module(slug: str):
    m = await repo.get_by_slug(slug)
    return {"id": m.id, "slug": m.slug, "title": m.title}
Bien — el molde se encarga 
# ✅ from_attributes construye ModuleOut desde el objeto y filtra el resto.
@app.get("/modules/{slug}", response_model=ModuleOut)
async def get_module(slug: str) -> ModuleOut:
    return await repo.get_by_slug(slug)

8 · Reto

🎯 Un contrato de salida que sobrevive a cambios internos

Diseña los esquemas de salida de Copiloto API de forma que nunca puedas filtrar un secreto aunque añadas campos internos mañana. En concreto: (1) crea un modelo base de salida para tus entidades con ConfigDict(from_attributes=True); (2) añade una ruta GET /modules que devuelva list[ModuleOut]; (3) escribe un test de contrato que falle si algún campo no declarado aparece en la respuesta (por ejemplo, comparando las claves del JSON con las claves de ModuleOut.model_fields). El test debe romperse el día que alguien publique un campo por accidente.

Pista: Model.model_fields.keys() te da el conjunto de campos permitidos; response.json().keys() te da lo que salió. La igualdad de ambos conjuntos es tu contrato. Piensa además cómo modelar las respuestas de error del Copiloto para que encajen con la lección 2.

9 · Resumen

  • Toda salida se modela: response_model valida, filtra y documenta a la vez.
  • Los campos que no declaras en el modelo de salida no salen, aunque tu servicio los devuelva.
  • Entrada y salida son contratos distintos: XxxIn lleva secretos, XxxOut no.
  • model_config = ConfigDict(from_attributes=True) permite construir la salida desde objetos del mundo real (filas de BD, dataclasses).
  • Devolver un Response directamente salta el filtrado: úsalo con conocimiento (lección 3).
  • El OpenAPI (y /docs) refleja el contrato de salida: si un campo no debería estar ahí, el error está en el molde.

10 · Preguntas frecuentes

Si ya declaro el tipo de retorno -> ModuleOut, ¿hace falta response_model?

No: FastAPI usa el tipo de retorno como response_model si no pasas el parámetro explícito. Usa el tipo de retorno como forma por defecto (ayuda a mypy) y reserva response_model para cuando quieras algo distinto del tipo —por ejemplo, filtrar un subtipo—. Lo importante es que haya algo que defina la salida.

¿response_model cambia el objeto que devuelvo o solo lo que se envía?

Solo lo que se envía. Tu función devuelve lo que devuelve; FastAPI toma ese valor, lo valida contra el modelo de salida y serializa una copia filtrada. El objeto original nunca se modifica. Por eso puedes devolver el modelo de BD «gordo» sin miedo: no estás mutando nada, solo eligiendo qué se publica.

¿Qué pasa si lo que devuelvo no encaja con el response_model?

FastAPI lanza un ResponseValidationError que se traduce en un 500 Internal Server Error y registra el detalle en los logs. Es un error tuyo (del servidor), no del cliente: significa que tu código prometió un contrato que no cumple. Es exactamente lo que quieres detectar en desarrollo antes de que un cliente lo vea.

¿Sirve response_model si devuelvo una lista, por ejemplo un listado de módulos?

Sí. Declara response_model=list[ModuleOut] y FastAPI aplicará el filtro a cada elemento. Es la base de la lección 4 sobre paginación, donde el listado vendrá además envuelto en un sobre con metadatos (total, página, etc.).

¿Debo poner extra="forbid" también en los modelos de salida?

En salida rara vez importa: el filtrado ya descarta lo que sobra, así que no hay claves «extra» que rechazar. extra="forbid" brilla en la entrada, donde detecta erratas del cliente (enviar usernam en vez de username) y evita aceptar campos que no esperabas. Úsalo con criterio: también puede romper clientes legítimos que envían campos opcionales que ignoras a propósito.
