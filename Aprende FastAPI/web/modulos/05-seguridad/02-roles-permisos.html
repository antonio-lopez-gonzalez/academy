Roles y permisos: autorización

Módulo 5 · Seguridad 🕐 35 minutos

1 · Introducción

En la lección anterior ya sabemos quién llama: get_current_user convierte un token válido en un User. Pero saber quién es no es suficiente. Copiloto API tiene usuarios que solo preguntan, editores que administran el corpus de módulos y administradores que gestionan cuentas. Todos están autenticados; no todos deberían poder hacer lo mismo. Falta la segunda pregunta: ¿puede este usuario hacer esta acción? Eso es autorización.

Este es el error más común en APIs que empiezan: se protegen los endpoints con «¿hay token?» y punto. Así, cualquier usuario válido puede borrar registros, listar a otros usuarios o cambiar la configuración. La autorización no es un extra: es parte del contrato del API, tan importante como validar el cuerpo de la petición.

¿Por qué existe esta lección? Porque la buena autorización es declarativa y reutilizable. En vez de sembrar if user.role == "admin" por toda la aplicación, se escribe una vez una dependencia (require_role("admin")) y cada endpoint declara qué exige. El check vive en un sitio, se documenta en OpenAPI y no se puede olvidar.

Errores típicos que veremos: autorizar dentro del cuerpo del endpoint (fácil de olvidar en un endpoint nuevo), confiar en un rol que envía el cliente, usar roles y scopes como si fueran lo mismo, devolver 401 cuando lo correcto es 403, y esparcir comprobaciones de «superusuario» por todo el código.

2 · Teoría

Dos modelos: roles y scopes

Hay dos maneras habituales de expresar permisos, y conviene entender cuándo va cada una:

Roles (RBAC)Scopes (OAuth2)
Qué sonEtiquetas de identidad: reader, editor, adminPermisos granulares: ask:read, logs:write
GranularidadGruesa: un rol agrupa muchos permisosFina: cada scope describe una capacidad concreta
Cambian conLa persona (su puesto)La aplicación que actúa en su nombre
Ideal paraEquipos internos, paneles: «¿es moderador?»APIs consumidas por terceros: «¿puede leer mis datos?»
En el tokenClaim propio roles: ["editor"]Claim estándar scope: "ask:read ask:write"

El scope es el mecanismo estándar de OAuth2: un claim cuya forma es una lista de permisos separados por espacios. FastAPI lo integra en /docs y en OpenAPI mediante Security(...). Los roles son un claim propio que tú defines. Puedes usar uno u otro; este curso usa scopes para las capacidades del API (porque es lo que el estándar entiende) y menciona roles para el modelo más simple de «categorías de usuario».

Regla práctica: si un permiso se puede conceder a una aplicación tercera sin que cambie el «puesto» de la persona, es un scope. Si describe a la persona dentro de tu organización, es un rol. Muchos sistemas usan los dos: el rol decide el conjunto inicial de scopes que se ponen en el token.

Los claims viajan en el token: qué poner

El JWT de la lección 1 llevaba sub y exp. Para autorizar, añadimos claims. La pregunta de diseño: ¿los permisos se ponen en el token o se consultan en la base de datos?

  • En el token: rápido (sin consulta extra) y sin estado, pero los cambios de rol no se notan hasta que caduca. Bien para datos que cambian poco.
  • En la base de datos: siempre actualizado, pero cada petición consulta. Bien para permisos volátiles o si el token es largo.

El compromiso habitual: token corto con los scopes dentro (como roles del usuario), y revocación por caducidad corta. Aquí ponemos los roles en el token:

app/security.py — token con roles
from app.security import create_access_token

# Al hacer login conocemos los roles del usuario: los estampamos en el token.
token = create_access_token(subject=str(user.id), extra={"roles": user.roles})

Y en get_current_user se leen al decodificar (no hace falta ir a la base de datos para los roles):

app/deps.py — leer los roles del payload
@dataclass
class CurrentUser:
    id: int
    username: str
    roles: frozenset[str]


def get_current_user(token: str = Depends(oauth2_scheme)) -> CurrentUser:
    try:
        payload = decode_access_token(token)
    except InvalidTokenError:
        raise credentials_error()
    return CurrentUser(
        id=int(payload["sub"]),
        username=payload.get("username", ""),
        roles=frozenset(payload.get("roles", [])),   # conjunto inmutable
    )

Los roles se firman, no se confían. El cliente no envía su rol: lo envía el servidor dentro del token firmado. Si aceptaras un rol del cuerpo de la petición o de una cabecera, cualquiera se declararía admin. Nunca leas el rol de un sitio que no sea un token verificado (o la base de datos).

Dependencias de autorización reutilizables

Aquí está la idea central de la lección. En vez de comprobar el rol dentro del endpoint, se fabrica una dependencia que exige el rol y se declara en el endpoint. Es el patrón «fábrica de dependencias»: una función que devuelve una dependencia.

   Peticion
      │
      ▼
   ┌───────────────────────┐
   │ oauth2_scheme         │  extrae el Bearer token
   └──────────┬────────────┘
              ▼
   ┌───────────────────────┐
   │ get_current_user      │  valida firma/exp  →  CurrentUser(roles)
   └──────────┬────────────┘
              ▼
   ┌───────────────────────┐
   │ require_role("admin") │  ¿"admin" en roles?   NO → 403
   └──────────┬────────────┘
              ▼
   ┌───────────────────────┐
   │ endpoint              │  solo si paso el filtro
   └───────────────────────┘
app/deps.py — fábrica de dependencias por rol
from collections.abc import Callable


def require_role(role: str) -> Callable[[CurrentUser], CurrentUser]:
    """Devuelve una dependencia que exige 'role'. Reutilizable en toda la app."""

    def checker(current_user: CurrentUser = Depends(get_current_user)) -> CurrentUser:
        if role not in current_user.roles:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="No tienes permiso para esta accion",
            )
        return current_user

    return checker

Fíjate en el patrón: require_role("admin") no es una dependencia, devuelve una. Cada llamada crea una dependencia concreta que exige un rol. Se usa así:

app/routers/users.py
@router.delete("/users/{user_id}", status_code=204)
def delete_user(
    user_id: int,
    admin: CurrentUser = Depends(require_role("admin")),   # solo admin pasa
    session: Session = Depends(get_session),
) -> None:
    ...

Un check, un sitio. Si mañana la regla cambia («admin o owner de la cuenta»), tocas require_role y afecta a todos los endpoints que la usan. Esa es toda la ventaja del patrón, frente a los if repetidos.

Scopes: el mecanismo estándar

Cuando quieres permisos granulares y que OpenAPI los conozca, FastAPI ofrece Security y SecurityScopes. Se declaran los scopes disponibles en el esquema y cada endpoint pide los suyos:

app/deps.py — esquema con scopes
from fastapi import Security
from fastapi.security import SecurityScopes

oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="/auth/token",
    scopes={
        "ask:read": "Consultar el Copiloto",
        "ask:write": "Enviar preguntas nuevas",
        "logs:read": "Leer el historico de consultas",
        "admin": "Administrar usuarios y corpus",
    },
)


def get_current_user(
    security_scopes: SecurityScopes,
    token: str = Depends(oauth2_scheme),
) -> CurrentUser:
    # security_scopes.scopes trae lo que pide EL ENDPOINT que se esta ejecutando
    user = _decode_and_build(token)          # valida firma, exp y devuelve CurrentUser
    for needed in security_scopes.scopes:
        if needed not in user.scopes:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="Permisos insuficientes",
                headers={"WWW-Authenticate": f'Bearer scope="{security_scopes.scope_str}"'},
            )
    return user

El endpoint declara lo que necesita con Security en lugar de Depends:

app/routers/ask.py
@router.post("/ask", response_model=AskResponse)
def ask(
    payload: AskRequest,
    current_user: CurrentUser = Security(get_current_user, scopes=["ask:write"]),
) -> AskResponse:
    return AskResponse(answer="...")

Depends vs Security: Security es Depends con una lista de scopes que se reporta a OpenAPI. Si no necesitas scopes, Depends es suficiente y más corto.

Analogía: el rol es tu categoría de entrada al recinto («público», «prensa», «organización»). El scope es un permiso concreto escrito en la pulsera («acceso a la sala de prensa», «acceso a la zona de artistas»). Un fotógrafo de prensa (rol) puede tener permiso para la sala de prensa (scope) pero no para el escenario. La puerta de cada sala comprueba el permiso, no tu carné de prensa por sí solo.

3 · Ejemplo mínimo

Todo el patrón en cuatro piezas pequeñas, sin base de datos ni scopes: solo roles en el token.

roles_minimo.py
import os
from dataclasses import dataclass

import jwt
from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import OAuth2PasswordBearer

SECRET = os.environ["FAPI_SECRET_KEY"]
ALG = "HS256"

app = FastAPI()
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/token")


@dataclass
class CurrentUser:
    username: str
    roles: frozenset[str]


def get_current_user(token: str = Depends(oauth2_scheme)) -> CurrentUser:
    try:
        payload = jwt.decode(token, SECRET, algorithms=[ALG])
    except jwt.InvalidTokenError:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Credenciales invalidas")
    return CurrentUser(payload["sub"], frozenset(payload.get("roles", [])))


def require_role(role: str):
    def checker(user: CurrentUser = Depends(get_current_user)) -> CurrentUser:
        if role not in user.roles:
            raise HTTPException(status.HTTP_403_FORBIDDEN, "Permiso denegado")
        return user
    return checker


# Endpoint abierto a cualquier usuario autenticado
@app.get("/reports")
def read_reports(user: CurrentUser = Depends(get_current_user)) -> dict[str, str]:
    return {"for": user.username}


# Endpoint solo para admins
@app.delete("/reports/{report_id}")
def delete_report(
    report_id: int,
    admin: CurrentUser = Depends(require_role("admin")),
) -> dict[str, str]:
    return {"deleted": str(report_id), "by": admin.username}

Para probarlo, emite dos tokens distintos desde el mismo secreto:

terminal
# Token de un usuario normal
USER=$(uv run python -c "import os,jwt;print(jwt.encode({'sub':'ana','roles':['reader']}, os.environ['FAPI_SECRET_KEY'], algorithm='HS256'))")
# Token de un admin
ADMIN=$(uv run python -c "import os,jwt;print(jwt.encode({'sub':'root','roles':['reader','admin']}, os.environ['FAPI_SECRET_KEY'], algorithm='HS256'))")

curl -s http://127.0.0.1:8000/reports -H "Authorization: Bearer $USER"        # 200
curl -s -o /dev/null -w "%{http_code}\n" -X DELETE http://127.0.0.1:8000/reports/1 -H "Authorization: Bearer $USER"   # 403
curl -s -X DELETE http://127.0.0.1:8000/reports/1 -H "Authorization: Bearer $ADMIN"   # 200

Resultado esperado: el usuario normal lee el informe (200) pero al borrar recibe 403 — está autenticado, simplemente no tiene el rol. El admin pasa ambos.

401 vs 403, la clave. 401 = «no sé quién eres» (falta o es inválido el token). 403 = «sé quién eres, pero no puedes». Mezclarlos confunde al cliente: un frontend que recibe 401 intenta renovar el token; si le devuelves 401 cuando el problema es de permiso, entra en un bucle de refresco inútil.

4 · Ejemplo real

Copiloto API con las dos capas juntas: un rol de alto nivel que determina los scopes, y dependencias de scope para cada endpoint. Primero, el módulo de autorización:

app/security.py — de rol a scopes
from enum import StrEnum

from app.models import User


class Role(StrEnum):
    READER = "reader"
    EDITOR = "editor"
    ADMIN = "admin"


# El rol decide que scopes se estampan en el token al hacer login.
ROLE_SCOPES: dict[Role, frozenset[str]] = {
    Role.READER: frozenset({"ask:read", "logs:read"}),
    Role.EDITOR: frozenset({"ask:read", "ask:write", "logs:read"}),
    Role.ADMIN: frozenset({"ask:read", "ask:write", "logs:read", "logs:write", "admin"}),
}


def scopes_for(user: User) -> list[str]:
    granted: set[str] = set()
    for role in user.roles:
        granted |= ROLE_SCOPES[Role(role)]
    return sorted(granted)
app/deps.py — autorización reutilizable
from collections.abc import Callable
from dataclasses import dataclass

from fastapi import Depends, HTTPException, Security, status
from fastapi.security import OAuth2PasswordBearer, SecurityScopes
from jwt.exceptions import InvalidTokenError

from app.security import decode_access_token

oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="/auth/token",
    scopes={
        "ask:read": "Consultar el Copiloto",
        "ask:write": "Enviar preguntas nuevas",
        "logs:read": "Leer el historico",
        "logs:write": "Borrar el historico",
        "admin": "Administrar usuarios y corpus",
    },
)


@dataclass(frozen=True)
class CurrentUser:
    id: int
    username: str
    scopes: frozenset[str]


def get_current_user(
    security_scopes: SecurityScopes,
    token: str = Depends(oauth2_scheme),
) -> CurrentUser:
    authenticate_value = (
        f'Bearer scope="{security_scopes.scope_str}"' if security_scopes.scopes else "Bearer"
    )
    try:
        payload = decode_access_token(token)
    except InvalidTokenError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Credenciales invalidas",
            headers={"WWW-Authenticate": authenticate_value},
        )
    scopes = frozenset(payload.get("scope", "").split())
    for needed in security_scopes.scopes:
        if needed not in scopes:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="Permisos insuficientes",
                headers={"WWW-Authenticate": authenticate_value},
            )
    return CurrentUser(id=int(payload["sub"]), username=payload["username"], scopes=scopes)


def require_scopes(*needed: str) -> Callable[..., CurrentUser]:
    """Azucar: convierte require_scopes('a','b') en una dependencia lista."""

    def checker(
        current_user: CurrentUser = Security(get_current_user, scopes=list(needed)),
    ) -> CurrentUser:
        return current_user

    return checker
app/routers/ask.py — endpoints con distinto nivel
from fastapi import APIRouter, Depends, Security

from app.deps import CurrentUser, get_current_user, require_scopes
from app.schemas import AskRequest, AskResponse, LogPublic
from app.repositories.queries import QueryLogRepository
from app.deps import get_query_log_repository

router = APIRouter(tags=["copiloto"])


# Leer: cualquier usuario autenticado (sin scope concreto)
@router.get("/modules")
def list_modules(user: CurrentUser = Depends(get_current_user)) -> list[dict[str, str]]:
    return [{"slug": "fastapi", "title": "FastAPI"}]


# Preguntar: requiere permiso de escritura sobre el Copiloto
@router.post("/ask", response_model=AskResponse)
def ask(
    payload: AskRequest,
    user: CurrentUser = Security(get_current_user, scopes=["ask:write"]),
) -> AskResponse:
    return AskResponse(answer=f"Respuesta para {user.username}")


# Ver el historico: permiso de lectura de logs
@router.get("/logs", response_model=list[LogPublic])
def list_logs(
    user: CurrentUser = Security(get_current_user, scopes=["logs:read"]),
    repo: QueryLogRepository = Depends(get_query_log_repository),
):
    return repo.list_recent()


# Borrar el historico: solo admin, dos formas equivalentes
@router.delete("/logs", status_code=204)
def clear_logs(
    user: CurrentUser = Depends(require_scopes("logs:write", "admin")),
) -> None:
    ...   # el endpoint solo se alcanza si tiene AMBOS scopes

Decisiones y porqués:

  • El rol agrupa, el scope autoriza. La base de datos guarda roles («ana es editora»); al hacer login se traducen a scopes concretos. Así añadir un rol nuevo es tocar ROLE_SCOPES, no cada endpoint.
  • Los scopes se comprueban en una sola dependencia. get_current_user recibe SecurityScopes —lo que este endpoint pide— y compara. El endpoint nunca escribe el if.
  • require_scopes(*needed) como azúcar. Para el caso común de «esta ruta y nada más», evita repetir Security(get_current_user, ...).
  • El contrato lo refleja. En /docs, cada endpoint muestra el candado y los scopes que exige; el botón Authorize permite solicitarlos. Un cliente sabe exactamente qué permiso pedir.

Comprobar «ambos scopes». Security(get_current_user, scopes=["logs:write", "admin"]) exige todos: el bucle en get_current_user recorre los pedidos y falla al primero que falte. Si quisieras «cualquiera de los dos», escribirías la regla explícitamente con any(...): no hay un operador OR nativo, porque el estándar de scopes no lo contempla.

5 · Buenas prácticas

HazEvitaPor qué
Autorizar con dependencias declaradas en la firma if user.role != "admin" dentro del cuerpo La firma es el contrato: se ve en /docs y no se puede olvidar
Fábricas reutilizables (require_role, require_scopes) Repetir la misma comprobación en diez endpoints Un único check que evoluciona en un sitio
Leer los permisos de un token firmado o de la BD Aceptar el rol de una cabecera o del body Si el cliente declara su rol, cualquiera es admin

6 · Errores habituales

Autorizar dentro del endpoint

✗ Incorrecto
@router.delete("/modules/{slug}")
def delete_module(slug: str, user: CurrentUser = Depends(get_current_user)):
    if "admin" not in user.roles:           # invisible en OpenAPI
        raise HTTPException(403, "No permitido")
    ...
# Riesgo: el endpoint nuevo que copia esto y olvida el 'if'
✓ Correcto
@router.delete("/modules/{slug}")
def delete_module(
    slug: str,
    user: CurrentUser = Depends(require_role("admin")),   # en la FIRMA
):
    ...

El check en la firma es parte del contrato: aparece en /docs, se reutiliza y no se puede saltar. El if interno es invisible y fácil de olvidar al copiar el endpoint.

Confiar en el rol que envía el cliente

✗ Incorrecto
class Payload(BaseModel):
    question: str
    role: str = "reader"     # el cliente puede mandar "admin"

@router.post("/ask")
def ask(payload: Payload):
    if payload.role != "admin":
        raise HTTPException(403, "No permitido")
✓ Correcto
@router.post("/ask")
def ask(
    payload: AskRequest,                                    # sin 'role' en el modelo
    user: CurrentUser = Security(get_current_user, scopes=["ask:write"]),
):
    ...

El rol es un dato del servidor, no del cliente. Debe venir de un token firmado (que solo tú puedes firmar) o de la base de datos. Cualquier rol que llegue en el body es una sugerencia del atacante.

401 cuando corresponde 403

✗ Incorrecto
if "admin" not in user.roles:
    raise HTTPException(status_code=401, detail="No autorizado")
✓ Correcto
if "admin" not in user.roles:
    raise HTTPException(status_code=403, detail="Permisos insuficientes")

El 401 le dice al cliente «tu token no vale, consigue otro»; un frontend intentará refrescar en bucle. El 403 dice «estás autenticado, pero no puedes»: no hay nada que refrescar.

Permisos que se pudren en el token

✗ Incorrecto
# Token de 24 horas con TODOS los permisos dentro
{"sub": "42", "scope": "admin logs:write", "exp": now + timedelta(hours=24)}

# Revocas el rol de admin al usuario... y sigue siendo admin 24 horas mas.
✓ Correcto
# Token corto (minutos) + refresh; o consultar roles en la BD en get_current_user
{"sub": "42", "scope": "ask:read", "exp": now + timedelta(minutes=15)}

Cuanto más corto el token, menos dura la ventana en la que un permiso revocado sigue vigente. Para permisos volátiles, oblígate a mirar la base de datos en get_current_user en vez de fiarte del claim.

Denegar por lista negra

✗ Incorrecto
FORBIDDEN = {"banned", "suspended"}
if any(r in FORBIDDEN for r in user.roles):
    raise HTTPException(403, "Bloqueado")
# Un rol nuevo que olvidaste listar: permitido por defecto.
✓ Correcto
if "admin" not in user.roles:      # lista blanca: permiso explicito
    raise HTTPException(403, "Permisos insuficientes")

Denegar por defecto y conceder explícitamente. Así, un rol que nadie ha previsto no hereda capacidades por olvido.

7 · Ejercicio guiado

Objetivo: introducir roles y scopes en Copiloto API, proteger tres endpoints con niveles distintos y comprobar cada caso límite con curl.

  1. Paso 1 — Roles en el modelo. Añade a User (Módulo 4) un campo roles: list[str] = [] (SQLModel lo guarda como JSON). Siembra tres usuarios: lector con ["reader"], editora con ["editor"] y root con ["admin"].
  2. Paso 2 — Traduce rol a scopes. Crea el mapa ROLE_SCOPES como en el ejemplo real y la función scopes_for(user). En POST /auth/token, estampa extra={"scope": " ".join(scopes_for(user)), "username": user.username} al emitir el token.
  3. Paso 3 — Extrae los scopes. En get_current_user, lee payload.get("scope", "").split() y guárdalos como frozenset. No olvides el parámetro security_scopes: SecurityScopes y el bucle que compara lo pedido con lo concedido.
  4. Paso 4 — Protege los endpoints. GET /modules solo requiere autenticación; POST /ask pide ask:write; GET /logs pide logs:read. Declara oauth2_scheme con el diccionario de scopes para que /docs los muestre.
  5. Paso 5 — Añade un endpoint de administración. DELETE /logs exige logs:write y admin. Úsalo con require_scopes("logs:write", "admin").
  6. Paso 6 — Prueba la matriz completa. Con los tres usuarios, ejecuta: 
    for quien in lector:copiloto editora:copiloto root:copiloto; do
  U=${quien%%:*}; P=${quien##*:}
  T=$(curl -s -X POST http://127.0.0.1:8000/auth/token -d "username=$U&password=$P" \
      | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
  echo "$U  ask:$(curl -s -o /dev/null -w '%{http_code}' -X POST http://127.0.0.1:8000/ask \
        -H "Authorization: Bearer $T" -H 'Content-Type: application/json' -d '{"question":"hola"}')" \
       " logs:$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8000/logs -H "Authorization: Bearer $T")" \
       " clear:$(curl -s -o /dev/null -w '%{http_code}' -X DELETE http://127.0.0.1:8000/logs -H "Authorization: Bearer $T")"
done

    Resultado esperado (aproximado, según los scopes que concedas): lector → ask:403 logs:200 clear:403; editora → ask:200 logs:200 clear:403; root → ask:200 logs:200 clear:204. El lector puede leer el histórico pero no preguntar: es la diferencia entre estar autenticado y tener permiso.

  7. Paso 7 — Verifica en OpenAPI. Abre /openapi.json y busca security. Resultado esperado: POST /ask lista ask:write y DELETE /logs lista logs:write y admin. El contrato documenta los permisos: eso lo heredan los generadores de clientes y el portal de desarrolladores.

8 · Reto

🎯 Jerarquía de roles y propiedad del recurso

Los roles planos no cubren dos casos reales: (1) admin debería poder hacer todo lo que puede editor, que a su vez puede todo lo de reader, sin enumerar cada permiso; (2) un usuario debe poder editar sus propias preguntas aunque no sea admin — la autorización no siempre es por rol, a veces depende de quién es el dueño del recurso.

Impleta las dos cosas: una relación de jerarquía (un mapa {"admin": {"editor"}, "editor": {"reader"}, "reader": set()}) que expanda los scopes concedidos, y una dependencia require_owner_or_role(...) que permita la acción si el usuario es admin o si el recurso le pertenece. Aplícala a un endpoint DELETE /logs/{log_id}.

Pistas: la expansión de jerarquía es un recorrido en profundidad sobre el mapa (cuidado con los ciclos: un visited o un frozenset de vistos). Para la propiedad, la dependencia necesita conocer el recurso: pide el log_id por path y el repositorio por dependencia (Módulo 4), carga el log y compara log.user_id con user.id. Pregunta de diseño: ¿devolverías 403 o 404 cuando el recurso existe pero no es tuyo? (pista: un 404 no revela que el recurso existe). Y ojo con el orden: el check de autorización no debe ejecutar trabajo pesado que un usuario sin permiso pueda forzar.

9 · Resumen

  • Autenticación (401) identifica; autorización (403) decide. Son capas distintas.
  • Los roles agrupan permisos por categoría de usuario; los scopes son permisos granulares y estándar en OAuth2 (scope como lista separada por espacios).
  • Los permisos viajan en el token firmado (o se consultan en la BD); jamás se aceptan del cliente.
  • La autorización se declara con una dependencia reutilizable en la firma del endpoint, no con if internos.
  • La fábrica de dependencias (require_role("admin")) devuelve una dependencia configurada con el rol que exige.
  • Security es Depends + scopes declarados, y por eso aparecen en OpenAPI y en /docs.
  • SecurityScopes trae lo que pide el endpoint; la dependencia compara con lo concedido en el token.
  • Denegar por defecto (lista blanca) y no fiarse de permisos «eternos»: tokens cortos o consulta a la BD.

10 · Preguntas frecuentes

¿Roles o scopes? ¿Cuál uso en Copiloto API?

Usa los dos en capas: el rol es cómo la base de datos describe a la persona (lector, editor, admin) y el scope es la capacidad concreta que el token lleva estampada. Al hacer login traduces roles a scopes. Ganas lo mejor de cada uno: administras personas por rol y autorizas endpoints por scope granular, con el estándar OAuth2 y la documentación automática. Si tu API no la consumen terceros y los permisos son gruesos, un rol basta y te ahorras una capa.

¿Dónde conviene comprobar los permisos: en la dependencia o en el servicio?

En la dependencia para la autorización gruesa («puede usar esta ruta»), porque así es declarativa, visible en OpenAPI y no se olvida. Algunas reglas finas dependen del recurso («solo el dueño»), y esas no se pueden resolver sin cargarlo: van en el servicio o en una dependencia que reciba el recurso. La regla de oro: denegar antes de hacer trabajo costoso, y que el endpoint jamás contenga el if de permisos básicos. Ver el reto para el caso dueño-o-admin.

¿Por qué Security y no Depends?

Security es Depends con una lista de scopes que FastAPI reporta a OpenAPI. Si no pides scopes, Depends es suficiente y más corto. La diferencia no es funcional en la ejecución, sino documental: Security(..., scopes=[...]) hace que /docs y openapi.json declaren qué permiso necesita cada ruta, y que el botón Authorize permita solicitarlos.

Si cambio los roles de un usuario, ¿cuándo surte efecto?

Solo cuando emita un token nuevo. Los scopes van dentro del JWT y el token es sin estado: el servidor no consulta los roles en cada petición. Cuanto más corta la caducidad del token, menor la ventana de desfase. Si necesitas efecto inmediato, valida los permisos contra la base de datos en get_current_user (a cambio de una consulta por petición) o mantén una denylist de tokens revocados en Redis.

¿Un admin debería pasar todos los checks automáticamente?

No por defecto: eso es un «superusuario mágico» que suele sorprender y complica auditar quién hizo qué. Si quieres que admin herede los permisos de editor, hazlo explícito con una jerarquía (ver el reto) en lugar de un if user.is_admin: return True escondido. Explícito significa testeable, predecible y fácil de limitar. Un admin que además no puede borrarse a sí mismo es mejor que un admin omnipotente sin reglas.
