CORS y cabeceras de seguridad

Módulo 5 · Seguridad 🕐 30 minutos

1 · Introducción

Tu API funciona en curl, pero el frontend que vive en otro dominio recibe un error críptico en la consola del navegador: «blocked by CORS policy». Nada en tu servidor ha fallado; el navegador se ha negado a entregar la respuesta. Y al revés: cuando por fin consigues que funcione, descubres que CORS no ha protegido la API —curl sigue entrando—, porque CORS es una regla que el navegador se autoimpone, no un cortafuegos del servidor.

Esta lección desmonta dos confusiones muy extendidas y las convierte en práctica: qué es CORS exactamente (y qué no), cómo se configura con CORSMiddleware en FastAPI, y cómo añadir cabeceras de seguridad (las que el navegador usa para defenderse de XSS, clickjacking y sniffing de tipos).

¿Por qué existe esta lección? Porque CORS es la muralla que más frustración genera al conectar frontend y backend, y las cabeceras de seguridad son la capa que casi nadie configura hasta que un escáner las exige. Ambas son «gratis» de añadir y caras de olvidar. Además, la lección cierra el módulo explicando por qué el navegador distingue un dominio de otro: same-origin policy, la base de todo el modelo.

Errores típicos que veremos: poner allow_origins=["*"] junto a allow_credentials=True (el navegador lo rechaza), creer que CORS protege la API, usar una regex que lo permite todo, tratar el preflight OPTIONS como una petición normal, y enviar HSTS en desarrollo (donde puede dejarte el localhost inutilizable).

2 · Teoría

La same-origin policy y qué es un «origen»

Por seguridad, el navegador aísla las páginas entre sí: el JavaScript de una web no puede leer libremente las respuestas de otra. Ese es el same-origin policy (SOP), y es lo que impide que malicioso.com, usando la sesión que el usuario tiene abierta en banco.com, lea sus datos sin permiso.

Un origen es la terna esquema + host + puerto. Todo lo demás (ruta, query) da igual. La comparación es estricta:

URLMismo origen que https://app.examplePor qué
https://app.example/apiSíRuta distinta: irrelevante
http://app.exampleNoEsquema distinto (http vs https)
https://api.exampleNoHost distinto (subdominio distinto)
https://app.example:8443NoPuerto distinto

CORS (Cross-Origin Resource Sharing) es el mecanismo por el que el origen destino declara que este origen cruzado puede leer sus respuestas. Lo declara con cabeceras de respuesta; el navegador las lee y, si autorizan, entrega el cuerpo al JavaScript. Si no, lo bloquea.

CORS no es autenticación ni autorización. Es una decisión del navegador sobre qué JavaScript puede leer. Un atacante con curl, Postman o un script de servidor ignora CORS por completo. Si quieres bloquear peticiones, eso es autenticación (lecciones 1 y 2), no CORS.

Peticiones simples y preflight

No todas las peticiones cruzadas se comportan igual. El navegador distingue dos casos:

  • Petición «simple»: GET/HEAD/POST con cabeceras estándar y un Content-Type de los simples (text/plain, application/x-www-form-urlencoded, multipart/form-data). Se envía directamente y el navegador solo bloquea la lectura de la respuesta si el origen no está permitido.
  • Petición «con preflight»: cualquier otra cosa —PUT, DELETE, Content-Type: application/json, cabeceras como Authorization—. El navegador lanza antes una petición OPTIONS de sondeo (preflight) preguntando: «¿puedo hacer esto desde el origen X, con el método M y las cabeceras H?». Solo si el servidor dice que sí, manda la petición real.

Esto explica la mitad de los errores de CORS: una API que devuelve JSON y usa el header Authorization siempre dispara preflight, aunque el endpoint sea un simple POST.

  Navegador (origen https://app.example)          API (https://api.example)
      │                                                    │
      │  OPTIONS /ask            (preflight)               │
      │  Origin: https://app.example                       │
      │  Access-Control-Request-Method: POST               │
      │  Access-Control-Request-Headers: authorization     │
      ├───────────────────────────────────────────────────►│
      │                                                    │  decide si permite
      │  204 No Content                                    │
      │  Access-Control-Allow-Origin:  https://app.example │
      │  Access-Control-Allow-Methods: POST                │
      │  Access-Control-Allow-Headers: Authorization       │
      │◄───────────────────────────────────────────────────┤
      │                                                    │
      │  POST /ask               (peticion real)           │
      │  Authorization: Bearer ...                         │
      ├───────────────────────────────────────────────────►│
      │  200 {answer}                                      │
      │◄───────────────────────────────────────────────────┤

Credenciales y el wildcard prohibido

Si la petición lleva credenciales (cookies, o cabecera Authorization declarada como tal en modo credentials: "include"), el navegador aplica una regla dura: no acepta Access-Control-Allow-Origin: *. Debe ser el origen exacto, y además hay que enviar Access-Control-Allow-Credentials: true. Por eso CORSMiddleware rechaza al arrancar la combinación de allow_origins=["*"] con allow_credentials=True: es una configuración que el navegador nunca aceptaría.

  allow_origins=["*"] + allow_credentials=True   →  configuracion invalida
  allow_origins=["https://app.example"] + creds   →  OK (origen exacto)

Configurar CORSMiddleware

FastAPI trae el middleware de Starlette. Los parámetros que importan:

ParámetroQué hacePor defecto
allow_originsLista exacta de orígenes permitidos[]
allow_origin_regexRegex contra el origen (p. ej. subdominios)None
allow_methodsMétodos permitidos en preflight["GET"]
allow_headersCabeceras permitidas en preflight[]
allow_credentialsPermite cookies/credencialesFalse
expose_headersCabeceras de respuesta legibles por JS[]
max_ageSegundos que el navegador cachea el preflight600

CORS y cabeceras de seguridad son middleware. Se añaden con app.add_middleware(...) y envuelven toda la aplicación. El orden importa: el último añadido es el más externo. Añade CORSMiddleware en el borde (normalmente lo último) para que incluso las respuestas de error de otros middlewares salgan con las cabeceras CORS y el navegador pueda leerlas.

Cabeceras de seguridad: que el navegador se defienda

CORS no hace seguro tu API, pero las cabeceras de seguridad sí endurecen lo que el navegador permite hacer con tus respuestas. Las esenciales:

CabeceraQué bloqueaValor típico
X-Content-Type-Options Que el navegador «adivine» el tipo de un archivo (MIME sniffing) y ejecute como script lo que era texto nosniff
X-Frame-Options Que tu página se cargue dentro de un <iframe> ajeno (clickjacking) DENY
Strict-Transport-Security Que el navegador vuelva a usar HTTP en visitas futuras (solo tiene sentido sobre HTTPS) max-age=31536000; includeSubDomains
Referrer-Policy Que se filtre la URL completa (con datos) en la cabecera Referer hacia terceros no-referrer o strict-origin-when-cross-origin
Content-Security-Policy Qué orígenes pueden cargar scripts/estilos/imágenes: la defensa más fuerte contra XSS default-src 'self'
Cross-Origin-Opener-Policy Aislar tu documento de ventanas abiertas de otros orígenes same-origin

HSTS solo en HTTPS. Strict-Transport-Security le dice al navegador «durante un año, no me hables por HTTP, solo HTTPS». En desarrollo, sobre http://localhost, el navegador lo ignora; el peligro real es activarlo en un dominio que aún no tiene TLS válido: el navegador se negará a cargarlo y no habrá forma de volver atrás hasta que expire el max-age. Se activa en producción, con TLS ya funcionando.

Analogía: CORS es el portero de la discoteca que solo deja entrar a invitados de determinadas ciudades (el navegador solo enseña la respuesta si la ciudad está en la lista). Las cabeceras de seguridad son el resto del edificio: nosniff dice «no adivines qué es este paquete», X-Frame-Options: DENY dice «no te dejes meter en una vitrina ajena», y HSTS dice «a partir de ahora, entra siempre por la puerta blindada».

3 · Ejemplo mínimo

Permitir que un frontend de desarrollo (http://localhost:5173, el puerto típico de Vite) consuma la API. Es lo más corto que resuelve el error de consola:

main.py
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],   # el origen EXACTO del frontend
    allow_credentials=True,
    allow_methods=["*"],                        # o mejor: ["GET", "POST", "DELETE"]
    allow_headers=["Authorization", "Content-Type"],
)


@app.post("/ask")
def ask() -> dict[str, str]:
    return {"answer": "hola"}

El preflight se responde solo: CORSMiddleware intercepta el OPTIONS y contesta con las cabeceras Access-Control-* antes de llegar a tu endpoint. Compruébalo a mano:

terminal
# Simula el preflight que lanza el navegador
curl -i -X OPTIONS http://127.0.0.1:8000/ask \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: authorization,content-type"

Resultado esperado: 200 (o 204) con cabeceras access-control-allow-origin: http://localhost:5173, access-control-allow-methods y access-control-allow-headers. Cambia el Origin por http://evil.example: la cabecera access-control-allow-origin no aparece, y el navegador bloquearía la respuesta.

Por qué allow_credentials=True y no "*". Si tu frontend envía cookies o el header Authorization con credentials: "include", el navegador exige el origen exacto. Con allow_origins=["*"] la respuesta llevaría * y el navegador la descartaría. Por eso la lista explícita no es capricho: es requisito del estándar.

4 · Ejemplo real

En Copiloto API CORS se configura desde Settings (Módulo 3), de modo que desarrollo y producción cambian sin tocar el código, y las cabeceras de seguridad se añaden con un middleware propio.

app/config.py
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    secret_key: str
    cors_origins: list[str] = ["http://localhost:5173"]
    cors_allow_credentials: bool = True
    # En produccion, detras de TLS: activa HSTS.
    enable_hsts: bool = False

    model_config = SettingsConfigDict(env_prefix="fapi_", env_file=".env")


settings = Settings()
.env (producción)
# Lista separada por comas; pydantic-settings la convierte a list[str]
FAPI_CORS_ORIGINS=https://app.copiloto.dev,https://admin.copiloto.dev
FAPI_ENABLE_HSTS=true
app/middleware.py — cabeceras de seguridad
from collections.abc import Awaitable, Callable

from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
from starlette.responses import Response

from app.config import settings


class SecurityHeadersMiddleware(BaseHTTPMiddleware):
    """Anade cabeceras de seguridad a TODAS las respuestas."""

    async def dispatch(
        self,
        request: Request,
        call_next: Callable[[Request], Awaitable[Response]],
    ) -> Response:
        response = await call_next(request)
        response.headers["X-Content-Type-Options"] = "nosniff"
        response.headers["X-Frame-Options"] = "DENY"
        response.headers["Referrer-Policy"] = "strict-origin-when-cross-origin"
        response.headers["Cross-Origin-Opener-Policy"] = "same-origin"
        if settings.enable_hsts:
            # Solo tiene sentido sobre HTTPS; por eso es opt-in.
            response.headers["Strict-Transport-Security"] = "max-age=31536000; includeSubDomains"
        return response
app/main.py
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from starlette.middleware.trustedhost import TrustedHostMiddleware

from app.config import settings
from app.middleware import SecurityHeadersMiddleware

app = FastAPI(title="Copiloto API")

# 1) Cabeceras de seguridad (capa interna)
app.add_middleware(SecurityHeadersMiddleware)

# 2) CORS desde settings (capa externa, la ultima en anadirse = la mas externa)
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.cors_origins,
    allow_credentials=settings.cors_allow_credentials,
    allow_methods=["GET", "POST", "DELETE", "PATCH"],
    allow_headers=["Authorization", "Content-Type"],
    expose_headers=["X-Request-Id"],   # para que el frontend pueda leerlo
    max_age=3600,                      # cachea el preflight 1 hora
)

# 3) Solo atiende peticiones dirigidas a estos hosts (evita Host header injection)
app.add_middleware(TrustedHostMiddleware, allowed_hosts=["copiloto.dev", "*.copiloto.dev"])

Decisiones y porqués:

  • CORS desde Settings: los orígenes permitidos son configuración, no código. En desarrollo es localhost:5173; en producción, los dominios reales, sin recompilar.
  • Métodos y cabeceras explícitos, no "*": permites exactamente lo que tu frontend usa. Menos superficie, y evita la trampa del wildcard con credenciales.
  • expose_headers=["X-Request-Id"]: por defecto el JavaScript solo puede leer unas pocas cabeceras de respuesta; si quieres que el frontend vea un trace id para correlacionar errores, hay que exponerlo explícitamente.
  • max_age=3600: el navegador cachea el resultado del preflight una hora, ahorrando un OPTIONS por cada petición.
  • HSTS es opt-in vía enable_hsts: se activa solo donde hay TLS real. Evita el pie de página clásico de bloquear un dominio por accidente.
  • TrustedHostMiddleware: rechaza peticiones cuyo Host no sea de los tuyos, cerrando ataques de Host header injection y cache poisoning.

Detrás de un proxy inverso. En producción, nginx/Traefik/Caddy sirven TLS y reenvían a uvicorn. Arranca uvicorn con --proxy-headers --forwarded-allow-ips="*" (o la IP del proxy) para que scheme y client.host reflejen la petición original. Muchas cabeceras de seguridad —HSTS incluida— tienen más sentido puestas en el proxy, donde terminan todas las conexiones.

6 · Errores habituales

Wildcard con credenciales

✗ Incorrecto
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=True,   # el navegador DESCARTARA la respuesta
)
✓ Correcto
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.copiloto.dev"],   # origen exacto
    allow_credentials=True,
)

Con credenciales, el navegador exige el origen exacto; * es inaceptable por el estándar. CORSMiddleware avisa al arrancar para que no descubras el error en producción.

Creer que CORS protege el API

✗ Incorrecto
# "Solo dejo entrar a mi frontend: mi API esta protegida"
app.add_middleware(CORSMiddleware, allow_origins=["https://app.copiloto.dev"])
✓ Correcto
# CORS = que el NAVEGADOR enseñe la respuesta al JS de ese origen.
# La proteccion real es autenticacion/autorizacion:
app.add_middleware(CORSMiddleware, allow_origins=["https://app.copiloto.dev"])
# ... y ademas, en el endpoint:
def ask(user: CurrentUser = Security(get_current_user, scopes=["ask:write"])): ...

curl, Postman y cualquier servidor ignoran CORS. Limitar orígenes es higiene para el navegador; bloquear clientes no autorizados es tarea de la autenticación.

Regex que lo permite todo

✗ Incorrecto
app.add_middleware(CORSMiddleware, allow_origin_regex=".*")   # = "*"
✓ Correcto
app.add_middleware(
    CORSMiddleware,
    # solo subdominios concretos de mi dominio
    allow_origin_regex=r"https://.*\.copiloto\.dev",
)

La regex es potente para permitir todos los subdominios de un dominio propio, pero un .* suelto equivale a ["*"] y pierdes toda la restricción. Ancla el patrón al esquema y al dominio que controlas.

HSTS en desarrollo

✗ Incorrecto
# En local, sobre http://localhost, esto sobra y puede causar sorpresas
response.headers["Strict-Transport-Security"] = "max-age=63072000"
✓ Correcto
if settings.enable_hsts:   # solo en produccion, con TLS funcionando
    response.headers["Strict-Transport-Security"] = "max-age=31536000; includeSubDomains"

El navegador ignora HSTS en localhost sobre HTTP, pero activarlo en un dominio sin TLS válido puede dejarlo inaccesible hasta que expire el max-age. Es opt-in por diseño.

Tapar el preflight con otro middleware

✗ Incorrecto
class AuthMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        # Exige token ANTES de CORS: el preflight OPTIONS no lleva Authorization
        # y devuelve 401 -> el navegador nunca completa el CORS.
        if "authorization" not in request.headers:
            return Response(status_code=401)
        return await call_next(request)

app.add_middleware(AuthMiddleware)
app.add_middleware(CORSMiddleware, allow_origins=settings.cors_origins)  # interno
✓ Correcto
# CORS en el borde (ultimo en anadirse) responde el OPTIONS el solo,
# antes de que ningun middleware de autenticacion lo vea.
app.add_middleware(AuthMiddleware)
app.add_middleware(CORSMiddleware, allow_origins=settings.cors_origins)
# Y la autenticacion se hace en DEPENDENCIAS por endpoint, no en un middleware global.

El preflight OPTIONS nunca lleva tu token: si un middleware de autenticación global lo rechaza, CORS se rompe para todas las peticiones con credenciales. La autenticación va en dependencias por endpoint (lecciones 1 y 2), no en un middleware que intercepta todo.

7 · Ejercicio guiado

Objetivo: conectar un frontend cruzado a Copiloto API con CORS configurado desde Settings, añadir cabeceras de seguridad y verificar ambos con curl.

  1. Paso 1 — Configura los orígenes. Añade a Settings los campos cors_origins: list[str], cors_allow_credentials: bool = True y enable_hsts: bool = False. Pon en el .env de desarrollo FAPI_CORS_ORIGINS=http://localhost:5173.
  2. Paso 2 — Añade el middleware CORS. En app/main.py, registra CORSMiddleware con los valores de settings, métodos explícitos y expose_headers=["X-Request-Id"]. Añádelo el último para que quede en el borde.
  3. Paso 3 — Middleware de cabeceras. Crea app/middleware.py con SecurityHeadersMiddleware (como el ejemplo real) y regístralo antes que CORS. Deja HSTS detrás del flag enable_hsts.
  4. Paso 4 — Verifica el preflight. Con el servidor en marcha: 
    curl -s -D - -o /dev/null -X OPTIONS http://127.0.0.1:8000/ask \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: authorization,content-type" \
  | findstr /I "access-control"      # en Linux/macOS: | grep -i access-control

    Resultado esperado: aparecen access-control-allow-origin: http://localhost:5173, access-control-allow-methods con POST y access-control-allow-headers con authorization.

  5. Paso 5 — Prueba un origen no permitido. Repite con -H "Origin: http://evil.example". Resultado esperado: la respuesta no incluye access-control-allow-origin; el navegador bloquearía la lectura aunque el endpoint devuelva 200. Comprueba también que curl sin Origin sigue entrando: CORS no bloquea a un cliente que no es el navegador.
  6. Paso 6 — Verifica las cabeceras de seguridad. 
    curl -s -D - -o /dev/null http://127.0.0.1:8000/health \
  | findstr /I "x-content-type-options x-frame-options referrer-policy"

    Resultado esperado: x-content-type-options: nosniff, x-frame-options: DENY y referrer-policy: strict-origin-when-cross-origin. Sin Strict-Transport-Security (el flag está apagado en desarrollo).

  7. Paso 7 — Comprueba que HSTS es opt-in. Pon FAPI_ENABLE_HSTS=true, reinicia y repite el paso 6. Resultado esperado: ahora sí aparece strict-transport-security. Vuelve a ponerlo en false: en local no lo quieres.

8 · Reto

🎯 Una CSP con nonce por petición

Añade una Content-Security-Policy real a Copiloto API. La CSP es la cabecera que más protege contra XSS: declara de qué orígenes se pueden cargar scripts, estilos, imágenes y conexiones. El reto tiene una dificultad añadida: usar un nonce (un número de un solo uso) que cambie en cada petición, de modo que solo tus scripts con ese nonce puedan ejecutarse.

Necesitas también exponer el nonce al código que genera las plantillas (si sirves un HTML mínimo de bienvenida) y añadir X-Content-Type-Options: nosniff coherente. Al terminar, valida la cabecera con el validador de MDN mentalmente: ¿tapa la CSP todos los vectores de XSS conocidos o deja alguno?

Pistas: genera el nonce por petición con secrets.token_urlsafe(16) (¡no uses random!) y guárdalo en request.state.nonce dentro del middleware; luego construye script-src 'nonce-{valor}' 'strict-dynamic'. Un nonce reutilizado pierde el valor: por eso es por petición y nunca se cachea. Pregúntate: ¿qué pasa con 'unsafe-inline' (lo desactiva)? ¿Y con style-src en una app con estilos inline? Empieza en modo Content-Security-Policy-Report-Only con un endpoint que recoja los informes: es la forma sensata de desplegar una CSP sin romper la web. Pista final: no olvides default-src 'self' como red de seguridad.

9 · Resumen

  • Un origen es esquema + host + puerto; la same-origin policy aísla las páginas entre sí.
  • CORS es el permiso que el origen destino declara al navegador para que este origen cruzado pueda leer la respuesta.
  • CORS no protege la API: curl lo ignora. La protección real es autenticación y autorización.
  • Las peticiones con Authorization o Content-Type: application/json disparan preflight (OPTIONS).
  • Con credenciales, el origen debe ser exacto: allow_origins=["*"] + allow_credentials=True es inválido.
  • CORSMiddleware va en el borde (último en añadirse) para responder el preflight antes que otros middlewares.
  • Las cabeceras de seguridad se añaden una vez, en un middleware: nosniff, X-Frame-Options, Referrer-Policy, CSP y HSTS.
  • HSTS solo en producción con TLS: mal configurado, deja un dominio inaccesible.

10 · Preguntas frecuentes

¿Por qué en curl funciona y en el navegador no?

Porque CORS lo aplica el navegador, no el servidor. curl no comprueba las cabeceras Access-Control-*: recibe la respuesta y la usa. El navegador, en cambio, solo entrega el cuerpo al JavaScript si el origen destino declara que puede leerlo. Si tu API funciona en curl y falla en el navegador con un error de CORS, el servidor está bien: falta (o está mal) la configuración de CORSMiddleware.

¿Puedo permitir todos los orígenes en desarrollo y restringir en producción?

Sí, y es lo sensato: en desarrollo el frontend salta de puerto (5173, 3000…). Lo limpio es poner los orígenes en Settings (dev: ["*"] o la lista de localhost; prod: dominios exactos). Recuerda que ["*"] es imposible con allow_credentials=True: si usas cookies o Authorization en modo include, en desarrollo también necesitas orígenes explícitos.

¿Por qué el preflight devuelve 200 y no 204?

Ambos valen; el estándar recomienda 204 No Content porque el preflight no lleva cuerpo. CORSMiddleware responde según la configuración y, en la práctica, devuelve 200 con cabeceras. Lo importante no es el código, sino que la respuesta incluya Access-Control-Allow-Origin, Allow-Methods y Allow-Headers con lo que pedía el navegador.

¿Dónde pongo las cabeceras de seguridad: en la app o en nginx?

En producción, donde termina TLS suele ser el sitio natural: nginx/Traefik/Caddy las añaden a todas las respuestas, incluidas las estáticas que no pasan por FastAPI. Aun así, tenerlas también en un middleware de la app te protege si la app se expone directamente o si el proxy se reconfigura. Un buen compromiso: definirlas en el proxy y verificar en un test de integración que llegan (Módulo 6), para que un cambio de infraestructura no las borre en silencio.

¿CORS y CSRF son lo mismo?

No. CORS decide qué JavaScript puede leer respuestas cruzadas; CSRF (Cross-Site Request Forgery) es el ataque en que una web ajena provoca una petición autenticada tuya sin que lo sepas. Curiosamente, una petición CSRF puede no necesitar leer la respuesta (le basta el efecto). Por eso CORS por sí solo no protege de CSRF: si usas cookies de sesión, añade SameSite=Lax o Strict a la cookie y un token anti-CSRF. Si usas Authorization: Bearer y guardas el token fuera de las cookies, CSRF no aplica, porque el navegador no adjunta credenciales automáticamente.
