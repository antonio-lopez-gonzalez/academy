Arquitectura de la API

Módulo 7 · Proyecto final: Copiloto API 🕐 40 minutos

1 · Introducción

Durante seis módulos has aprendido las piezas por separado: rutas y validación, respuestas y errores con forma, Depends, lifespan, configuración, SQLModel, Alembic, JWT, tests. Cada lección tenía un ejemplo pequeño y autocontenido, a veces con todo en un solo main.py. Eso fue a propósito: aprender una pieza exige aislarla. Pero una API real no es una pieza: es el ensamblaje de todas, y el ensamblaje es lo que hace que el proyecto sea mantenible o un pantano.

Copiloto API —el asistente con RAG del curso Aprende IA, expuesto ahora como API HTTP— es ese ensamblaje. En este módulo dejamos de escribir ejemplos de laboratorio y construimos el proyecto que vive en proyectos/copiloto-api/: un paquete app/ con capas claras, un pyproject.toml, migraciones, tests y un Dockerfile.

¿Por qué existe esta lección? Porque la arquitectura se decide antes de escribir la primera línea de negocio y, en la práctica, se decide sin darte cuenta. Si colocas mal una pieza hoy, cada funcionalidad nueva la arrastrará. Esta lección fija las fronteras: quién conoce a quién, dónde vive la configuración, cómo se inyecta el motor de RAG y por qué main.py solo monta, no calcula.

Errores típicos que evitamos desde el principio: meter todo en main.py hasta convertirlo en un «God module»; leer os.environ a pelo dentro de los endpoints; que un router importe app.main (y provoque un import circular imposible de arrancar); y crear la instancia de Settings como variable global de módulo, lo que secuestra los tests y los entornos.

2 · Teoría

La API como un edificio por capas

Una API es un edificio con plantas especializadas. Cada planta tiene una función y solo habla con las de al lado. El router atiende al público (HTTP); los servicios orquestan los casos de uso; los repositorios y modelos hablan con la base de datos. Ninguna planta debería saber los detalles internos de la que está tres pisos más abajo.

   Petición HTTP
        │
        ▼
   ┌──────────────┐   valida entrada, decide status, modela salida
   │   routers/   │   ← HTTP: NO sabe SQL, NO sabe cómo se genera la respuesta
   └──────┬───────┘
          │  (schemas Pydantic de entrada/salida)
          ▼
   ┌──────────────┐   casos de uso, transacción, coordinación
   │  services/   │   ← lógica de aplicación: NO sabe HTTP
   └──────┬───────┘
          │  (modelos de dominio)
          ▼
   ┌──────────────┐   consultas y persistencia
   │repositories/ │   ← datos: NO sabe reglas de negocio
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │  Session/DB  │
   └──────────────┘

   Transversal a todas las plantas:  config  ·  deps  ·  models  ·  schemas  ·  errors

Analogía: piensa en un restaurante. El router es el camarero: toma tu pedido en el lenguaje del cliente y lo traduce a la cocina. El servicio es el jefe de cocina: decide el orden de los platos y cuándo se sirve todo junto (la transacción). El repositorio es la despensa: sabe dónde está cada ingrediente, pero no le importa qué receta estás preparando. Y la configuración es el local, los horarios y las llaves: presente en todas partes, pero no es «cocina».

Las piezas y su responsabilidad

El paquete app/ de Copiloto API se compone de estos módulos. Memoriza la tabla: es el mapa del proyecto entero.

ArchivoResponsabilidadQué NO debe hacer
app/main.pyCrear la app, montar routers, definir lifespanContener lógica de negocio o SQL
app/config.pyConfiguración tipada y validada (Settings)Leer variables dispersas con os.environ
app/db.pyMotor, fabricación de sesiones, dependencia get_sessionDefinir reglas de negocio
app/models.pyTablas SQLModel (Module, QueryLog, User)Ser el contrato de la API
app/schemas.pyModelos Pydantic de entrada/salidaTener table=True
app/deps.pyDependencias reutilizables (config, sesión, motor, usuario)Instanciar recursos en cada petición sin caché
app/routers/*.pyEndpoints agrupados por recursoConsultar la base de datos o importar main
app/services/*.pyCasos de uso y puertos (p. ej. el motor de RAG)Conocer Request/Response de HTTP
app/repositories/*.pyConsultas encapsuladasConfirmar transacciones
app/security.pyHash de contraseñas y firma/verificación de JWTSabe de rutas concretas

Una regla mental útil: las flechas de import van siempre «hacia dentro». routers → services → repositories → db. Nunca al revés. Si un model.py importa un router, algo va mal.

main.py: el punto de montaje

main.py es el composition root: el único lugar donde se conocen todos los routers y todos los recursos de larga vida. Su trabajo es montar, no calcular. En el arranque (vía lifespan, que ya vimos en el Módulo 3) abre el motor de RAG una sola vez y lo deja en app.state; al apagarse, lo cierra.

   uvicorn app.main:app
        │
        ▼
   lifespan.startup  →  crea recursos (motor de RAG, pools)  →  app.state
        │
        ▼
   include_router(...)  ×5  →  la app conoce las rutas
        │
        ▼
   (sirviendo peticiones)
        │
        ▼
   lifespan.shutdown  →  cierra los recursos

¿Por qué una función create_app() y no un app = FastAPI() suelto? Porque una factoría permite construir la aplicación con una configuración distinta en cada contexto: en los tests quieres una app «limpia» y con dobles inyectados; en producción, con la configuración real. Lo vemos en el reto.

config.py: la configuración tipada

La configuración es una entrada más del sistema y merece el mismo trato que un cuerpo de petición: tipo, valor por defecto y validación. pydantic-settings (Módulo 3, lección 4) construye Settings leyendo variables de entorno y, si quieres, un fichero .env. La regla de oro del curso: ningún secreto en el repositorio.

No instancies Settings() como variable global de módulo. Si escribes settings = Settings() en la primera línea, ese objeto se crea al importar el módulo. Los tests y los entornos que cambian variables después ya no pueden influir en él, y el fallo es silencioso: funciona en tu máquina y revienta en CI. Se resuelve con una función cacheada (get_settings) y con Depends, que veremos ahora.

deps.py: el pegamento

Las dependencias son el sistema nervioso del proyecto: conectan la configuración, la sesión de base de datos, el motor de RAG y el usuario autenticado con cualquier endpoint que los necesite, sin que el endpoint los construya. Ese «sin que los construya» es lo que hace el código testeable: en un test, dependency_overrides cambia una dependencia por un doble (Módulo 6).

   router  ──Depends──►  get_current_user ──Depends──►  get_session
      │                        │                            │
      └──Depends──►  get_settings          get_rag_engine ──┘
                              │                    │
                        .env / entorno      app.state (lifespan)

3 · Ejemplo mínimo

Cuatro archivos y una carpeta de routers: la arquitectura completa en miniatura. Cada archivo tiene exactamente la responsabilidad que le toca.

app/config.py
from functools import lru_cache

from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    """Configuración efectiva: se lee del entorno (y de .env si existe)."""

    model_config = SettingsConfigDict(
        env_prefix="COPILOTO_",   # COPILOTO_APP_NAME, COPILOTO_DATABASE_URL…
        env_file=".env",
        extra="ignore",           # otras variables del sistema no rompen el arranque
    )

    app_name: str = "Copiloto API"
    version: str = "0.1.0"
    database_url: str = "sqlite:///copiloto.db"


@lru_cache                       # se construye una vez, no en cada petición
def get_settings() -> Settings:
    return Settings()
app/deps.py
from typing import Annotated

from fastapi import Depends

from app.config import Settings, get_settings

# Alias reutilizable: el endpoint pide «la configuración» y FastAPI la inyecta.
SettingsDep = Annotated[Settings, Depends(get_settings)]
app/routers/health.py
from fastapi import APIRouter

from app.deps import SettingsDep

router = APIRouter(tags=["health"])


@router.get("/health")
def health(settings: SettingsDep) -> dict[str, str]:
    """Comprobación de vida: ¿la app responde?"""
    return {"status": "ok", "app": settings.app_name, "version": settings.version}
app/main.py
from fastapi import FastAPI

from app.config import get_settings
from app.routers import health


def create_app() -> FastAPI:
    """Factoría: construye la aplicación a partir de la configuración."""
    settings = get_settings()
    application = FastAPI(title=settings.app_name, version=settings.version)
    application.include_router(health.router)
    return application


app = create_app()   # uvicorn app.main:app

Para arrancarlo, dentro de un proyecto uv con uv add fastapi "uvicorn[standard]" pydantic-settings:

uv run uvicorn app.main:app --reload

Y en otras terminales:

curl -s http://127.0.0.1:8000/health
# {"status":"ok","app":"Copiloto API","version":"0.1.0"}

Línea por línea, las decisiones que importan:

  1. env_prefix="COPILOTO_": todas las variables del proyecto llevan el mismo prefijo. Un COPILOTO_DATABASE_URL en el entorno sobreescribe el valor por defecto sin tocar código.
  2. @lru_cache en get_settings: la configuración se lee una vez por proceso. Llamarla en cada endpoint sería releer el fichero y el entorno en cada petición.
  3. SettingsDep = Annotated[Settings, Depends(get_settings)]: un alias que evita repetir Depends(...) en cada firma. El endpoint declara qué necesita; FastAPI lo provee.
  4. return {"status": ..., "app": ...}: el endpoint devuelve datos, no la configuración entera. El contrato de salida lo fija el tipo (dict[str, str]) y OpenAPI.
  5. create_app() + app = create_app(): la factoría documenta la intención y deja la puerta abierta a construir varias apps (tests) con configuración distinta.

4 · Ejemplo real

Copiloto API completo. Primero, el main.py real: monta cinco routers, abre el motor de RAG en el lifespan y lo comparte por app.state.

app/main.py
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI

from app.config import get_settings
from app.routers import ask, auth, health, logs, modules
from app.services.rag import build_engine


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    """Recursos de larga vida: se abren al arrancar y se cierran al apagar."""
    app.state.engine = build_engine(get_settings())   # motor de RAG (una vez)
    try:
        yield
    finally:
        close = getattr(app.state.engine, "close", None)
        if close is not None:
            close()


def create_app() -> FastAPI:
    settings = get_settings()
    application = FastAPI(
        title=settings.app_name,
        version=settings.version,
        description="API del Copiloto (RAG) — Aprende IA como servicio.",
        lifespan=lifespan,
    )
    # El prefijo y las etiquetas se declaran UNA vez, aquí, no en cada router.
    application.include_router(health.router)
    application.include_router(modules.router, prefix="/modules", tags=["modules"])
    application.include_router(ask.router, prefix="/ask", tags=["ask"])
    application.include_router(auth.router, prefix="/auth", tags=["auth"])
    application.include_router(logs.router, prefix="/logs", tags=["logs"])
    return application


app = create_app()

Y la configuración real del proyecto, con los secretos siempre fuera del repositorio:

app/config.py
from functools import lru_cache

from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    """Toda la configuración de Copiloto API, tipada y validada."""

    model_config = SettingsConfigDict(
        env_prefix="COPILOTO_",
        env_file=".env",
        extra="ignore",
    )

    app_name: str = "Copiloto API"
    version: str = "1.0.0"
    environment: str = "development"          # development | production | test

    # Base de datos: SQLite en local, PostgreSQL en producción (misma API).
    database_url: str = "sqlite:///copiloto.db"
    sql_echo: bool = False

    # Seguridad: la clave JWT NUNCA tiene un valor por defecto utilizable.
    secret_key: str = Field(min_length=32)
    access_token_expire_minutes: int = 30
    algorithm: str = "HS256"

    # Motor de RAG: si no hay backend real, se usa un motor de eco (tests/local).
    rag_backend: str = "canned"               # canned | Aprende-ia
    rag_top_k: int = 5
    rag_min_score: float = 0.25

    # CORS
    cors_origins: list[str] = ["http://localhost:5173"]


@lru_cache
def get_settings() -> Settings:
    return Settings()

secret_key: str = Field(min_length=32) sin valor por defecto: si falta la variable de entorno, la aplicación no arranca. Es un fallo ruidoso al inicio en lugar de un fallo silencioso en producción (todos los tokens firmados con una clave vacía). Un .env.example versionado documenta qué variables existen; el .env real está en .gitignore.

Con eso, el arranque y la comprobación son idénticos a los de cualquier app FastAPI:

export COPILOTO_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')"
uv run uvicorn app.main:app --reload
curl -s http://127.0.0.1:8000/openapi.json | head -c 200

PowerShell (Windows): las variables de entorno se definen distinto. Para una sesión de terminal:

$env:COPILOTO_SECRET_KEY = (python -c "import secrets; print(secrets.token_urlsafe(48))")
$env:COPILOTO_RAG_BACKEND = "canned"
uv run uvicorn app.main:app --reload

Decisiones y porqués de la arquitectura real:

  • Un solo lifespan: el motor de RAG (que en el proyecto de Aprende IA abre un índice en disco) se construye una vez y se comparte. Si cada petición lo construyera, cargaríamos el índice entero en cada pregunta.
  • app.state.engine: es el sitio idiomático para guardar recursos de la aplicación. La dependencia request.app.state.engine los recupera (lección 2).
  • Prefijos en include_router: el router declara solo su trozo de ruta ("", "/{slug}") y el prefijo se decide en un único lugar. Cambiar /ask por /v2/ask es una línea.
  • services/rag.py con build_engine(settings): aquí vive el puerto del motor. El resto de la aplicación no sabe si detrás hay Ollama, un doble de test o un stub: solo conoce la interfaz. Ese es el corazón de la lección 2.
  • Sin lógica en main.py: no hay un solo select() ni un if de negocio. Si lo tuviera, el archivo crecería sin freno y los tests tendrían que importar la app entera para probar una regla.

5 · Buenas prácticas

HazEvitaPor qué
Un módulo por responsabilidad (config, db, routers…) Un main.py de 800 líneas Encuentras lo que buscas sin leerlo todo y los diffs son pequeños

Configuración por Settings e inyectada con Depends os.environ["X"] disperso por los endpoints Un solo contrato de configuración, tipado y sobreescribible en tests

6 · Errores habituales

Settings() global de módulo

✗ Incorrecto
# app/config.py
settings = Settings()            # se construye AL IMPORTAR el módulo


# app/main.py
from app.config import settings  # el test ya no puede cambiarla
app = FastAPI(title=settings.app_name)
✓ Correcto
# app/config.py
@lru_cache
def get_settings() -> Settings:
    return Settings()


# app/deps.py
SettingsDep = Annotated[Settings, Depends(get_settings)]


# app/main.py
def create_app() -> FastAPI:
    settings = get_settings()     # se lee al crear la app, no al importar

Con el global, la primera importación congela la configuración. Si un test define COPILOTO_DATABASE_URL antes de importar, quizá funcione; si lo hace después, ya es tarde. La función cacheada se llama cuando se construye la app, no antes.

El router importa main: import circular

✗ Incorrecto
# app/routers/ask.py
from app.main import app            # ← el router depende de la app que lo monta


@app.post("/ask")
def ask(...): ...
✓ Correcto
# app/routers/ask.py
from fastapi import APIRouter

router = APIRouter()                # el router NO conoce la app


@router.get("")
def list_ask(...): ...


# app/main.py
application.include_router(ask.router, prefix="/ask", tags=["ask"])

main importa ask para montarlo; si ask importa main, Python entra en un ciclo: ImportError o AttributeError: partially initialized module. El router es una pieza suelta que main enchufa, nunca al revés.

Leer el entorno a pelo dentro del endpoint

✗ Incorrecto
import os


@router.get("/ask")
def ask(question: str):
    top_k = int(os.environ.get("COPILOTO_TOP_K", "5"))   # sin tipo, sin validación
    secret = os.environ["SECRET_KEY"]                    # KeyError sin aviso
✓ Correcto
@router.get("/ask")
def ask(question: str, settings: SettingsDep):
    top_k = settings.rag_top_k        # tipado, validado, con valor por defecto

Leer el entorno a mano pierde el tipado ("5" es str), la validación (¿y si no es un entero?) y la documentación. Settings centraliza las conversiones y falla al arrancar, que es cuando quieres enterarte.

Lógica de negocio en main.py

✗ Incorrecto
app = FastAPI()


@app.post("/ask")
def ask(payload: AskRequest, session: Session = Depends(get_session)):
    engine = build_engine(get_settings())          # recurso caro por petición
    answer = engine.answer(payload.question)
    session.add(QueryLog(question=payload.question, answer=answer.text))
    session.commit()
    return {"answer": answer.text}
✓ Correcto
# app/routers/ask.py — el router solo orquesta
@router.post("", response_model=AskResponse)
def ask(
    payload: AskRequest,
    engine: EngineDep,
    service: AskServiceDep,
) -> AskResponse:
    return service.ask(payload.question, engine)

Cuando el negocio vive en main.py, no puedes probarlo sin levantar la app entera y el archivo se vuelve intocable. El router debe ocuparse de HTTP; el caso de uso, de la lógica. Lo verás en detalle en la lección 2.

7 · Ejercicio guiado

Objetivo: montar el esqueleto por capas de Copiloto API, arrancarlo y comprobar que el contrato (OpenAPI) ya refleja GET /health.

  1. Paso 1 — Crea el proyecto. 
    uv init copiloto-api --python 3.12
cd copiloto-api
uv add fastapi "uvicorn[standard]" pydantic-settings

    Resultado esperado: se crean pyproject.toml, uv.lock y .venv/. FastAPI, uvicorn y pydantic-settings aparecen en pyproject.toml.

  2. Paso 2 — Crea la estructura de carpetas. 
    mkdir -p app/routers app/services app/repositories tests
touch app/__init__.py app/routers/__init__.py app/services/__init__.py app/repositories/__init__.py tests/__init__.py

    En PowerShell el equivalente es New-Item -ItemType Directory app\routers, app\services, app\repositories, tests y luego crear los __init__.py. Resultado esperado: la estructura de árbol de la sección 2, todavía vacía de contenido.

  3. Paso 3 — Escribe app/config.py. Copia el Settings con env_prefix="COPILOTO_" y secret_key: str = Field(min_length=32). Deja el resto con valores por defecto razonables.
  4. Paso 4 — Escribe app/deps.py y app/routers/health.py. Define SettingsDep y el endpoint GET /health de la sección 3 que devuelve status, app y version.
  5. Paso 5 — Monta la app. Escribe app/main.py con la factoría create_app() y un único include_router(health.router).
  6. Paso 6 — Arranca y comprueba. Define la clave y levanta el servidor: 
    export COPILOTO_SECRET_KEY="una-clave-larga-de-al-menos-32-caracteres-aqui"
uv run uvicorn app.main:app --reload

    En otra terminal:

    curl -s http://127.0.0.1:8000/health
curl -s http://127.0.0.1:8000/openapi.json | python -m json.tool | head -20

    Resultado esperado: el JSON de salud y un OpenAPI con title, version y la ruta /health. Abre http://127.0.0.1:8000/docs: la documentación ya está publicada.

  7. Paso 7 — Provoca el fallo controlado. Detén el servidor, borra la variable COPILOTO_SECRET_KEY y arranca otra vez: 
    unset COPILOTO_SECRET_KEY   # PowerShell: Remove-Item Env:COPILOTO_SECRET_KEY
uv run uvicorn app.main:app

    Resultado esperado: uvicorn falla al arrancar con un error de validación de Pydantic que menciona secret_key. Eso es la configuración defendiéndose: mejor un arranque fallido ahora que tokens firmados con una clave inexistente en producción.

8 · Reto

🎯 Factoría con recursos inyectables

Refactoriza create_app() para que reciba sus recursos como parámetros opcionales: create_app(settings: Settings | None = None, engine: RagEngine | None = None) -> FastAPI. Si recibe un motor, la app lo usa; si no, lo construye en el lifespan. Después escribe un test que cree una app con una Settings hecha a mano y un motor fake, sin tocar el entorno ni el disco, y compruebe GET /health.

Pistas: define el Protocol RagEngine en app/services/rag.py (lo haces en la lección 2) y guarda en app.state lo que te pasen por parámetro. Pregúntate qué es más legible cuando el proyecto crezca: ¿inyectar todo por parámetro o dejar que el lifespan lo construya y usar dependency_overrides solo en los tests que lo necesiten? Documenta tu decisión y su coste.

9 · Resumen

  • Una API real es un ensamblaje por capas: routers → services → repositories → db. Los imports van siempre hacia dentro.
  • main.py monta la app, incluye los routers y define el lifespan; no contiene negocio ni SQL.
  • config.py centraliza la configuración como un Settings tipado de pydantic-settings, con los secretos fuera del repositorio.
  • get_settings() cacheado con @lru_cache y expuesto por Depends: nunca un Settings() global de módulo.
  • deps.py es el pegamento: configuración, sesión, motor de RAG y usuario se inyectan, no se construyen a mano.
  • Los recursos caros (motor de RAG, pool de conexiones) se abren en lifespan y se comparten por app.state.
  • create_app() como factoría hace la aplicación configurable y, por tanto, testeable.
  • La estructura del proyecto es proyectos/copiloto-api/: paquete app/ por capas, migrations/, tests/ y Dockerfile.

10 · Preguntas frecuentes

¿Por qué create_app() y no app = FastAPI() a secas?

Porque una factoría te deja construir la aplicación cuando y con qué configuración quieras. En producción, uvicorn app.main:app la crea una vez; en los tests, puedes crear apps con un Settings hecho a mano o con el motor de RAG en modo fake. Un objeto global creado en el import obliga a manipular el entorno antes de importar, que es frágil. El coste es una línea extra y merece la pena en cualquier proyecto que crezca.

¿routers/, api/ o endpoints/?

Es una convención, no una regla del framework. En este curso usamos routers/ porque el objeto que contiene es un APIRouter. Lo importante es ser consistente: elige un nombre y no mezcles. Si tu equipo ya usa api/, úsalo; lo que no vale es tener routers/ y endpoints/ a la vez.

¿Necesito services/ y repositories/ desde el primer endpoint?

No. Para dos endpoints triviales, un router que consulta la sesión es perfectamente honesto. Añade capas cuando el dolor sea real: una consulta que se repite en tres sitios, una regla que quieres probar sin base de datos, o la previsión de cambiar de tecnología. En Copiloto API las añadimos ahora porque el proyecto ya tiene histórico, roles y un motor de RAG que merece aislarse. La arquitectura es una inversión, no un peaje fijo.

¿Cómo evito que un router importe app.main?

Los routers no deben necesitar nada de la app. Si un endpoint requiere configuración, la pide con Depends; si requiere un recurso del lifespan, lo recupera de request.app.state a través de una dependencia. La app importa los routers para montarlos, y esa dirección única es la que rompe el ciclo. Si te ves escribiendo from app.main import app dentro de un router, casi siempre es que ese código pertenece a una dependencia o a un servicio.

¿Dónde guardo la clave secret_key en local y en producción?

En local, un fichero .env ignorado por Git (con un .env.example versionado que documenta las variables). En producción, variables de entorno reales inyectadas por tu plataforma (el orquestador, el sistema de secretos de tu nube, etc.). El código es idéntico: Settings las lee con el mismo prefijo. La regla es absoluta: ningún secreto en el repositorio ni dentro de la imagen de Docker.
