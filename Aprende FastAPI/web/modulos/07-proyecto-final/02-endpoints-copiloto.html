Endpoints del Copiloto

Módulo 7 · Proyecto final: Copiloto API 🕐 45 minutos

1 · Introducción

Ya tenemos el esqueleto por capas. Ahora le damos superficie pública: los tres endpoints que convierten a Copiloto API en un servicio de verdad. GET /health dice si estamos vivos y si la base de datos responde; GET /modules expone el catálogo que el asistente conoce; POST /ask es el corazón: recibe una pregunta y devuelve una respuesta fundamentada con sus fuentes citadas.

El reto no es escribir tres funciones. Es hacerlo con las reglas que llevamos seis módulos entrenando: toda entrada se valida, toda salida se modela y todo error tiene forma consistente. Y hay una decisión de diseño que lo condiciona todo: el motor de RAG no puede vivir dentro del endpoint. Si el endpoint construyera el índice, llamara a Ollama y gestionara el prompt, tendríamos un endpoint que no se puede testear sin un modelo, sin disco y sin red.

¿Por qué existe esta lección? Porque aquí se junta todo lo aprendido: response_model y filtrado (Módulo 2), Depends (Módulo 3), el puerto del motor de RAG y el histórico (Módulo 4), y la disciplina de sync vs async. Además, el POST /ask que escribas aquí es exactamente el que protegerás con JWT en la lección 3 y el que testearás en la lección 4.

Errores típicos que veremos: devolver el modelo de tabla tal cual (filtrando columnas internas por accidente), llamar a un motor bloqueante desde un endpoint async def (y congelar el servidor entero), inventar una forma distinta de error en cada endpoint, y aceptar preguntas sin límite de longitud.

2 · Teoría

El contrato primero

Antes de escribir una ruta, escribimos sus schemas: las clases Pydantic que son el contrato público. El contrato es la fuente de verdad del API (Módulo 2) y tiene dos mitades: lo que entra (validado) y lo que sale (modelado). Nada que no esté en el contrato debería viajar por el cable.

   Cliente ──JSON──►  AskRequest   (valida: min_length, max_length, tipos)
                          │
                          ▼
                      endpoint  ──►  motor de RAG  ──►  AskResponse
                          │            (puerto)          (answer, sources,
                          ▼                               latency_ms, log_id)
                   Problem Details  ◄── si algo falla (misma forma siempre)
EndpointEntradaSalidaCódigos

GET /modules/{slug}path paramModulePublic200 · 404

Lee esta tabla y ya has leído la API. Eso es exactamente lo que verá cualquiera que abra /docs: la tabla está generada a partir de los tipos. Si tu tabla mental y la de OpenAPI no coinciden, el código y el contrato se han divorciado.

El motor de RAG es un puerto, no una librería

En el curso Aprende IA, el Copiloto es un paquete Python (copiloto) con indexación, embeddings, recuperación y generación. Ese paquete funciona desde una CLI, pero una API no debe acoplarse a él directamente: si lo hiciera, cada test necesitaría un índice en disco y un modelo disponible, y cambiar de proveedor (Ollama por la nube) obligaría a tocar los endpoints.

La solución es la misma que en el patrón repositorio (Módulo 4): definimos un puerto (Protocol) que describe qué necesita la aplicación, y varios adaptadores que lo implementan.

app/services/rag.py — el puerto y los adaptadores
from dataclasses import dataclass, field
from typing import Protocol


@dataclass
class RagAnswer:
    """Respuesta del motor: texto + fuentes citadas."""
    text: str
    sources: list[str] = field(default_factory=list)


class RagEngine(Protocol):
    """Puerto: lo que Copiloto API necesita de un motor de RAG."""

    def answer(self, question: str, module_slug: str | None = None) -> RagAnswer: ...


class CannedEngine:
    """Adaptador de desarrollo/tests: respuestas deterministas, sin red ni disco."""

    def answer(self, question: str, module_slug: str | None = None) -> RagAnswer:
        where = f" en {module_slug}" if module_slug else ""
        return RagAnswer(text=f"Eco{where}: {question}", sources=[])


class LearnIAEngine:
    """Adaptador real: envuelve el paquete `copiloto` del curso Aprende IA."""

    def __init__(self, settings) -> None:
        from copiloto.config import load_settings
        from copiloto.embeddings import get_embedder
        from copiloto.llm import get_llm
        from copiloto.store import Store

        self._copiloto = load_settings()
        self._store = Store(self._copiloto.db_path)
        self._embedder = get_embedder(self._copiloto)
        self._llm = get_llm(self._copiloto)
        self._top_k = settings.rag_top_k
        self._min_score = settings.rag_min_score

    def answer(self, question: str, module_slug: str | None = None) -> RagAnswer:
        from copiloto.rag import answer as rag_answer, retrieve

        scored = retrieve(question, self._store, self._embedder, k=self._top_k)
        context = [chunk for score, chunk in scored if score >= self._min_score]
        result = rag_answer(question, context, self._llm)
        return RagAnswer(text=result.text, sources=result.sources)

    def close(self) -> None:
        self._store.close()


def build_engine(settings) -> RagEngine:
    """Elige el adaptador según la configuración (una sola vez, en el lifespan)."""
    if settings.rag_backend == "Aprende-ia":
        return LearnIAEngine(settings)
    return CannedEngine()

El adaptador es un envoltorio fino a propósito. Toda la lógica de RAG (recuperar, ponderar, prompt, abstenerse) sigue viviendo en copiloto; aquí solo la traducimos a la interfaz que la API conoce. Es la diferencia entre usar una librería y depender de ella: si mañana cambia la firma de retrieve, tocas un archivo; si el modelo pasa a ser remoto, añades otro adaptador.

De app.state a Depends

El motor se construye en el lifespan (es caro: abre el índice) y se guarda en app.state. Para que un endpoint lo use sin conocer app, lo exponemos con una dependencia:

app/deps.py
from typing import Annotated

from fastapi import Depends, Request
from sqlmodel import Session

from app.config import Settings, get_settings
from app.db import get_session
from app.services.rag import RagEngine

SettingsDep = Annotated[Settings, Depends(get_settings)]
SessionDep = Annotated[Session, Depends(get_session)]


def get_engine(request: Request) -> RagEngine:
    """Recupera el motor construido en el lifespan."""
    return request.app.state.engine


EngineDep = Annotated[RagEngine, Depends(get_engine)]

El endpoint declara engine: EngineDep y nunca sabe si detrás hay un CannedEngine, un LearnIAEngine o un doble de test. En la lección 4, un dependency_overrides[get_engine] sustituye un modelo real por una respuesta fija: tests rápidos y deterministas.

Sync vs async: el motor es bloqueante

El adaptador real usa urllib y SQLite: son llamadas bloqueantes (no devuelven el control hasta que terminan). Si declaras el endpoint como async def y llamas a un motor bloqueante dentro, congelas el event loop y, con él, todas las peticiones del servidor. La regla del curso:

SituaciónDeclaración correctaPor qué
El endpoint llama a un motor bloqueante (LLM local, requests, SQLite)def ask(...)FastAPI lo ejecuta en un threadpool: no bloquea el loop
El endpoint solo hace await de I/O asíncrona (cliente httpx async)async def ask(...)Se ejecuta en el loop, sin hilos extra
Mezcla: async def pero el motor es bloqueanteawait run_in_threadpool(engine.answer, ...)Descarga el trabajo bloqueante a un hilo explícitamente

Un endpoint async def que llama a un motor bloqueante no falla: simplemente hace que el servidor parezca lento bajo carga. Es el bug de rendimiento más caro y más difícil de diagnosticar. Si dudas, def: FastAPI es lo bastante listo para gestionar el hilo por ti.

Errores con una sola forma

El Módulo 2 enseñó a dar forma a los errores (RFC 9457, Problem Details). En un proyecto real, esa forma debe ser idéntica en todos los endpoints, incluidos los 422 que genera Pydantic. Se consigue con un manejador de excepciones global, no repitiendo diccionarios. Lo escribimos en app/errors.py y lo registramos al montar la app.

Fíjate en el detalle del 422: exc.errors() puede contener valores no serializables en ctx (por ejemplo, un objeto de excepción). Por eso el manejador proyecta solo loc, msg y type: convierte una respuesta impredecible en un contrato estable.

3 · Ejemplo mínimo

Un endpoint POST /ask con un motor inyectable. Todavía no hay RAG, ni base de datos, ni índice: solo el patrón, desnudo y ejecutable.

main.py
from typing import Protocol

from fastapi import Depends, FastAPI
from pydantic import BaseModel, Field


# --- 1) El contrato ---------------------------------------------------------
class AskRequest(BaseModel):
    question: str = Field(min_length=3, max_length=2000)


class RagAnswer(BaseModel):
    text: str
    sources: list[str] = []


# --- 2) El puerto y un adaptador -------------------------------------------
class RagEngine(Protocol):
    def answer(self, question: str) -> RagAnswer: ...


class EchoEngine:
    def answer(self, question: str) -> RagAnswer:
        return RagAnswer(text=f"Eco: {question}")


def get_engine() -> RagEngine:
    return EchoEngine()


# --- 3) El endpoint --------------------------------------------------------
app = FastAPI()


@app.post("/ask", response_model=RagAnswer)
def ask(payload: AskRequest, engine: RagEngine = Depends(get_engine)) -> RagAnswer:
    return engine.answer(payload.question)

Arranca con uv run uvicorn main:app --reload y prueba el camino feliz y el de error:

curl -s -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "¿Qué es Depends?"}'
# {"text":"Eco: ¿Qué es Depends?","sources":[]}

curl -s -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" -d '{"question": "no"}'
# 422: la pregunta tiene menos de 3 caracteres

Lo esencial, línea por línea:

  1. AskRequest con Field(min_length=3, max_length=2000): la validación vive en el contrato, no en un if dentro del endpoint. FastAPI devuelve 422 automáticamente si no se cumple.
  2. RagEngine(Protocol): describe la capacidad («responde a una pregunta»), no una tecnología. Cualquier objeto con un método answer compatible sirve.
  3. def get_engine(): la dependencia que provee el motor. En este ejemplo devuelve un eco; en el proyecto real recuperará el motor de app.state o el que inyecte el test.
  4. def ask(...) (no async def): el motor es síncrono, así que un def deja que FastAPI lo ejecute en un hilo y no toque el event loop.
  5. response_model=RagAnswer y tipo de retorno anotado: la respuesta se filtra y se documenta sola. Añade un campo interno al motor y no saldrá si no está en RagAnswer.

4 · Ejemplo real

Ahora los tres endpoints de Copiloto API, con schemas, dependencias y errores con forma. Empezamos por el contrato.

app/schemas.py
from typing import Literal

from pydantic import BaseModel, Field
from sqlmodel import SQLModel


class ModulePublic(SQLModel):
    """Salida pública de un módulo: sin columnas internas."""
    slug: str
    title: str

class HealthResponse(BaseModel):
    status: Literal["ok", "degraded"]
    database: Literal["up", "down"]
    version: str


class AskRequest(BaseModel):
    question: str = Field(
        min_length=3,
        max_length=2000,

        examples=["¿Cómo funciona la inyección de dependencias?"],
    )
    module_slug: str | None = Field(
        default=None,
        max_length=64,
        description="Limita la búsqueda a un módulo concreto.",
    )


class AskResponse(BaseModel):
    answer: str
    sources: list[str] = []
    latency_ms: int
    log_id: int | None = None


class ProblemDetail(BaseModel):
    """Forma consistente de error (RFC 9457)."""
    type: str = "about:blank"
    title: str
    status: int
    detail: str | None = None
    instance: str | None = None
app/errors.py
from fastapi import FastAPI, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse


def register_error_handlers(app: FastAPI) -> None:
    """Todos los 422 salen con forma Problem Details, iguales en toda la API."""

    @app.exception_handler(RequestValidationError)
    async def validation_problem(request: Request, exc: RequestValidationError) -> JSONResponse:
        return JSONResponse(
            status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
            media_type="application/problem+json",
            content={
                "type": "https://copiloto.dev/errors/validation",
                "title": "Petición no válida",
                "status": 422,
                "detail": "Uno o más campos no cumplen el contrato.",
                "instance": request.url.path,
                # Proyectamos: exc.errors() puede traer valores no serializables.
                "errors": [
                    {"loc": list(e["loc"]), "msg": e["msg"], "type": e["type"]}
                    for e in exc.errors()
                ],
            },
        )
app/routers/health.py
from fastapi import APIRouter
from sqlalchemy import text
from sqlalchemy.exc import SQLAlchemyError

from app.deps import SessionDep, SettingsDep
from app.schemas import HealthResponse

router = APIRouter(tags=["health"])


@router.get("", response_model=HealthResponse)
def health(settings: SettingsDep, session: SessionDep) -> HealthResponse:
    """Liveness + readiness: ¿responde la app? ¿responde la base de datos?"""
    try:
        session.connection().execute(text("SELECT 1"))
        database = "up"
    except SQLAlchemyError:
        database = "down"

    status_value = "ok" if database == "up" else "degraded"
    return HealthResponse(status=status_value, database=database, version=settings.version)

Un /health de verdad comprueba dependencias. Un endpoint que solo devuelve {"status": "ok"} dice que el proceso vive, pero no que pueda servir. Comprobar la base de datos con SELECT 1 convierte /health en la señal que usan los orquestadores (Docker, Kubernetes) para decidir si un contenedor está listo. Es el mismo endpoint que consumirá el HEALTHCHECK de la lección 4.

app/routers/modules.py
from fastapi import APIRouter, HTTPException, status
from sqlmodel import select

from app.deps import SessionDep
from app.models import Module
from app.schemas import ModulePublic

router = APIRouter()


@router.get("", response_model=list[ModulePublic])
def list_modules(session: SessionDep) -> list[Module]:
    """Catálogo de módulos que el Copiloto conoce."""
    return list(session.exec(select(Module).order_by(Module.title)).all())


@router.get("/{slug}", response_model=ModulePublic)
def get_module(slug: str, session: SessionDep) -> Module:
    module = session.exec(select(Module).where(Module.slug == slug)).first()
    if module is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"Módulo '{slug}' no encontrado",
        )
    return module

Fíjate en que los endpoints devuelven Module (el modelo de tabla) pero el response_model es ModulePublic: FastAPI filtra y serializa al schema público. El modelo de tabla puede tener columnas que no deben salir jamás; esta es la frontera que las contiene.

app/routers/ask.py
import time

from fastapi import APIRouter

from app.deps import EngineDep, SessionDep
from app.models import QueryLog
from app.schemas import AskRequest, AskResponse

router = APIRouter()


@router.post("", response_model=AskResponse)
def ask(payload: AskRequest, engine: EngineDep, session: SessionDep) -> AskResponse:
    """Responde con RAG y registra la consulta en el histórico.

    Es `def` (no `async def`) porque el motor es bloqueante: FastAPI lo
    ejecuta en un threadpool y no congela el event loop.
    """
    started = time.perf_counter()
    result = engine.answer(payload.question, payload.module_slug)
    latency_ms = int((time.perf_counter() - started) * 1000)

    log = QueryLog(
        question=payload.question,
        answer=result.text,
        module_slug=payload.module_slug,
        latency_ms=latency_ms,
    )
    session.add(log)          # el endpoint es dueño de la transacción
    session.commit()
    session.refresh(log)      # trae el id autogenerado

    return AskResponse(
        answer=result.text,
        sources=result.sources,
        latency_ms=latency_ms,
        log_id=log.id,
    )

Y el main.py que ya conoces, con una línea más para registrar los manejadores de error:

app/main.py (extracto)
from app.errors import register_error_handlers

application.include_router(health.router)
application.include_router(modules.router, prefix="/modules", tags=["modules"])
application.include_router(ask.router, prefix="/ask", tags=["ask"])
register_error_handlers(application)

Decisiones y porqués:

  • El motor entra por EngineDep: el router no importa copiloto, ni Store, ni Ollama. Si el motor cambia, este archivo no se toca.
  • def ask(...): el motor bloqueante se ejecuta en un hilo. Ver la tabla de sync vs async de la teoría.
  • El histórico se escribe en la misma petición: add + commit + refresh. El endpoint es el dueño de la transacción (Módulo 4, lección 2). El refresh es necesario porque log_id lo asigna la base de datos.
  • latency_ms calculado con time.perf_counter(): mide tiempo monótono, inmune a cambios del reloj del sistema. Guardarlo permite detectar si el motor se degrada.
  • Errores en un solo sitio: register_error_handlers garantiza que un 422 de validación y un 404 de módulo compartan forma (Problem Details).

6 · Errores habituales

Devolver el modelo de tabla sin response_model

✗ Incorrecto
@router.post("/ask")
def ask(payload: AskRequest, session: SessionDep):
    log = QueryLog(question=payload.question, answer="...", internal_flag=True)
    session.add(log)
    session.commit()
    return log              # sin response_model → sale TODO, incluido internal_flag
✓ Correcto
@router.post("/ask", response_model=AskResponse)
def ask(payload: AskRequest, session: SessionDep) -> AskResponse:
    ...
    return AskResponse(answer=..., sources=..., latency_ms=..., log_id=log.id)

Sin response_model, FastAPI serializa lo que devuelvas. Añades una columna interna al modelo y, sin querer, la publicas en la API. El contrato de salida debe ser explícito y más estrecho que la tabla.

Bloquear el event loop con async def

✗ Incorrecto
@router.post("/ask")
async def ask(payload: AskRequest, engine: EngineDep):
    # engine.answer es BLOQUEANTE (urllib + SQLite): congela el loop entero.
    return engine.answer(payload.question)
✓ Correcto
@router.post("/ask")
def ask(payload: AskRequest, engine: EngineDep):   # `def`: corre en un hilo
    return engine.answer(payload.question)


# ...o, si necesitas `async def`, descarga el trabajo a un hilo:
from starlette.concurrency import run_in_threadpool

@router.post("/ask")
async def ask_async(payload: AskRequest, engine: EngineDep):
    return await run_in_threadpool(engine.answer, payload.question)

Con un solo cliente el servidor parece ir bien; con diez simultáneos, todos esperan en fila. La regla no es «async siempre es mejor»: es «nunca bloquees el loop con trabajo bloqueante».

Errores con formas distintas

✗ Incorrecto
@router.post("/ask")
def ask(payload: AskRequest, engine: EngineDep):
    try:
        return engine.answer(payload.question)
    except RuntimeError as exc:
        return {"error": str(exc), "code": 500}      # forma A


@router.get("/modules/{slug}")
def get_module(slug: str, session: SessionDep):
    raise HTTPException(404, "no existe")             # forma B (dict de FastAPI)
    # y un 422 de Pydantic llega con su propia forma C
✓ Correcto
# app/errors.py — una forma para todos (Problem Details)
app.add_exception_handler(RequestValidationError, validation_problem)


@router.get("/modules/{slug}")
def get_module(slug: str, session: SessionDep):
    raise HTTPException(
        status_code=404,
        detail="Módulo no encontrado",
        headers={"Content-Type": "application/problem+json"},
    )

El cliente no debería tener que distinguir «error de validación», «error de negocio» y «error interno» por la forma del JSON. Con un manejador global y Problem Details, todo error es la misma estructura con distinto status y type.

Aceptar preguntas sin límite

✗ Incorrecto
class AskRequest(BaseModel):
    question: str          # sin min_length ni max_length: cabe un libro entero
✓ Correcto
class AskRequest(BaseModel):
    question: str = Field(min_length=3, max_length=2000)
    module_slug: str | None = Field(default=None, max_length=64)

Una pregunta sin límite es un vector de abuso: ocupa memoria al parsear, se envía al modelo (que cobra por tokens) y llena el histórico. Acotar los campos no es rigidez, es defensa. El mismo razonamiento aplica a module_slug.

8 · Reto

🎯 Respuesta en streaming

Añade un endpoint POST /ask/stream que emita la respuesta a medida que el modelo la genera, usando Server-Sent Events (SSE). El cliente debe recibir trozos parciales y, al final, las fuentes citadas en un evento de cierre. La consulta se debe seguir registrando en el histórico una sola vez, cuando termina.

Pistas: en SSE se usa media_type="text/event-stream" y un async generator dentro de StreamingResponse; cada evento se escribe como data: ...\n\n. El motor real (copiloto) genera texto de golpe, así que necesitarás un método nuevo en el puerto (stream) y un adaptador que trocee la respuesta. Pregúntate dónde crece el riesgo: si el cliente se desconecta a mitad, ¿cómo evitas dejar la transacción abierta o el QueryLog a medias? Documenta la decisión.

9 · Resumen

  • El contrato primero: los schemas de entrada/salida son la fuente de verdad, y OpenAPI se genera de ellos.
  • Los tres endpoints de Copiloto API son GET /health (liveness + BD), GET /modules (catálogo) y POST /ask (RAG + histórico).
  • El motor de RAG es un puerto (Protocol) con varios adaptadores: LearnIAEngine (real) y CannedEngine (tests/local).
  • El motor se construye en el lifespan, vive en app.state y se inyecta con EngineDep.
  • Sync vs async: un motor bloqueante exige def (threadpool) o run_in_threadpool si el endpoint es async.
  • Toda salida con response_model; toda entrada acotada con Field (min_length, max_length).
  • Los errores tienen una sola forma (Problem Details) gracias a un manejador global registrado en el arranque.
  • POST /ask registra la consulta en QueryLog y devuelve log_id y latency_ms.

10 · Preguntas frecuentes

¿Por qué no llamo al paquete copiloto directamente desde el endpoint?

Porque acoplarías el endpoint a una librería concreta: sus imports, su índice en disco y su cliente de modelo. Cualquier test tendría que preparar un índice real, y cambiar de proveedor te obligaría a editar la capa HTTP. Con el puerto RagEngine, el endpoint solo conoce una interfaz de tres líneas; los detalles de copiloto viven en un adaptador. Es la misma lección del patrón repositorio aplicada a un servicio externo.

¿El motor de RAG debería ser async?

Depende de la implementación. El del curso Aprende IA usa urllib y SQLite: es síncrono y bloqueante, así que el endpoint va en def. Si algún día el proveedor ofrece un cliente async (por ejemplo, httpx.AsyncClient contra un endpoint remoto), puedes declarar un puerto con async def y el endpoint en async def. Lo importante es que el puerto y la implementación coincidan: no mezcles un async def que esconde llamadas bloqueantes.

¿Por qué /health incluye el estado de la base de datos?

Porque un proceso vivo que no puede consultar su base de datos es un contenedor que no debe recibir tráfico. Los orquestadores usan liveness (¿reinicio el proceso?) y readiness (¿le mando tráfico?) leyendo este endpoint. Comprobar SELECT 1 es barato y convierte /health en una señal fiable. En producción, algunos equipos exponen /health/live y /health/ready por separado; aquí los unimos con el campo database para no complicar el proyecto.

¿Devolver sources no expone información interna?

Expone las referencias (curso, módulo, lección), que es justo lo que quieres: trazabilidad de por qué el modelo dijo lo que dijo. No expone los embeddings, ni los chunks completos, ni la configuración del índice. Si en tu caso las fuentes fueran sensibles, filtra en el adaptador y devuelve solo su etiqueta pública. El principio general: modela la salida y decide qué campos salen.

¿Qué pasa si el motor falla a mitad de la petición?

La excepción sube y se convierte en un 500. Como el commit del QueryLog ocurre después de engine.answer, no queda un registro a medias: la consulta fallida no se persiste, lo cual es coherente (no hubo respuesta). Si quisieras registrar también los fallos, envuelve la llamada en try/except, guarda el QueryLog con answer=None y commit, y vuelve a lanzar. Y no devuelvas el mensaje de la excepción al cliente: filtra y registra.
