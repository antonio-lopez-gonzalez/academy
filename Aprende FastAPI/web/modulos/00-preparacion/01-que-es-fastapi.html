Qué es FastAPI

Módulo 0 · Preparación 🕐 30 minutos

1 · Introducción

FastAPI es un framework para construir APIs HTTP con Python. Si vienes de .NET, te recordará a ASP.NET Core Minimal APIs; si vienes de Node, a Express con validación incluida; si vienes de Flask, a Flask… pero con los tipos como protagonistas. Su propuesta es sencilla de enunciar y potente de usar: escribes funciones Python con anotaciones de tipo y FastAPI hace el resto (valida la entrada, serializa la salida y genera la documentación).

En esta lección entenderás qué problema resuelve cada pieza del framework: por qué se apoya en ASGI y no en WSGI, qué aporta Pydantic y por qué la documentación interactiva no es un extra sino el contrato de tu API. No escribiremos todavía una API completa (eso empieza en la lección 3), pero saldremos sabiendo por qué FastAPI es hoy el framework de APIs más usado del ecosistema Python.

¿Por qué existe esta lección? Porque un framework se domina mejor cuando entiendes su arquitectura. Todo el curso (rutas, validación, dependencias, seguridad, despliegue) se apoya en tres decisiones que veremos aquí: ASGI, validación por tipos y OpenAPI. Si estos tres cimientos quedan claros, el resto encaja solo.

Para quien ya programa: no explicaremos qué es una función ni qué es JSON. Explicaremos por qué FastAPI toma las decisiones que toma y cómo se comparan con Flask, Django o ASP.NET Core.

2 · Teoría

La idea central: tus tipos son el contrato

En un framework clásico, la validación es código que escribes a mano: comprobar que item_id es un entero, que name es un texto, que price es positivo… FastAPI invierte ese trabajo. Declaras los tipos y él genera la validación, la conversión y la documentación:

app/main.py
from fastapi import FastAPI

app = FastAPI()


@app.get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None):
    # FastAPI ya garantizó, antes de entrar aquí, que item_id es un int.
    return {"item_id": item_id, "q": q}

Fíjate en lo que no escribimos: nada de int(request.args["item_id"]), nada de devolver un 422 a mano, nada de definir el esquema del parámetro para la documentación. Todo se deduce de item_id: int y q: str | None = None. Esa es la firma del framework: declaras qué, no cómo.

ASGI frente a WSGI: el cambio de paradigma

Un servidor web Python necesita un contrato para hablar con tu aplicación. Durante años ese contrato fue WSGI (Web Server Gateway Interface), síncrono y de una petición por hilo. FastAPI usa ASGI (Asynchronous Server Gateway Interface), asíncrono por diseño y capaz de mantener miles de conexiones concurrently con pocos recursos.

  WSGI (síncrono)                     ASGI (asíncrono)
  ---------------------------------   -----------------------------------
  petición ---> worker bloqueado      petición ---> evento en el loop
                hasta terminar                      sin bloquear el hilo
  petición ---> otro worker/hilo      petición ---> otro evento concurrente
  (un hilo por petición)              (un loop para muchas peticiones)

  Soporta: HTTP/1.1 básico            Soporta: HTTP, WebSockets, streaming,
  No soporta: WebSockets, SSE         server-sent events, HTTP/2 (según servidor)

Analogía: WSGI es un mostrador con un empleado por cliente: cada persona ocupa a alguien hasta que termina. ASGI es un mostrador con un recepcionista muy rápido que toma la comanda, la pasa a la cocina y sigue atendiendo; cuando un plato está listo, vuelve a por él. Con la misma plantilla, atiende a muchísima más gente —siempre que la cocina (tu código async) no se quede mirando la pared.

Async no es magia gratis. ASGI rinde más solo si tu código no bloquea el loop de eventos. Una llamada de red síncrona (por ejemplo requests.get(...)) dentro de una función async congela a todos los demás. Lo veremos a fondo en las lecciones de rutas; aquí quédate con la idea: ASGI es la puerta; cómo la cruces es decisión tuya.

Las tres capas que componen FastAPI

FastAPI no reinventa la rueda: ensambla tres piezas excelentes del ecosistema y les añade su propia capa de conveniencia (rutas, inyección de dependencias, OpenAPI).

Validación basada en tipos con Pydantic v2

Cuando envías datos en el cuerpo de una petición (un POST, por ejemplo), FastAPI los valida con un modelo Pydantic. Un modelo es una clase que describe la forma de los datos y las reglas de cada campo:

app/schemas.py
from pydantic import BaseModel, Field


class AskRequest(BaseModel):
    # Toda entrada se valida: si falta o no encaja, FastAPI responde 422 solo.
    question: str = Field(min_length=1, max_length=500)
    module: str | None = None
    top_k: int = Field(default=3, ge=1, le=10)  # entre 1 y 10


# Ejemplo de uso directo (lo que FastAPI hará por ti en cada request):
req = AskRequest(question="¿Qué es ASGI?", top_k=99)
# pydantic_core.ValidationError: top_k debe ser <= 10

¿Por qué tipos y no un validador ad-hoc? Porque el tipo es información que ya escribes de todas formas, y Pydantic la convierte en validación, conversión ("42" → 42), serialización y documentación. Un único punto de verdad para cuatro tareas. Esto es lo que la documentación de FastAPI llama el camino «rápido pero con esteroides».

Documentación automática: OpenAPI y Swagger UI

Como FastAPI conoce los tipos de tu API, puede generar el esquema OpenAPI (un JSON que describe todos tus endpoints, parámetros y respuestas) y, con él, dos interfaces interactivas listas para usar:

  • /docs — Swagger UI: documentación navegable y con botón «Try it out» para lanzar peticiones reales.
  • /redoc — ReDoc: una versión de lectura, más limpia para compartir.
  • /openapi.json — el contrato en crudo: la fuente de verdad que consumen clientes, generadores de SDK y tests.

El contrato OpenAPI es la fuente de verdad del API en este curso. Antes de escribir un cliente o un test, mira /openapi.json: si tu código y el contrato divergen, el contrato describe lo que de verdad sirve la API.

No hay un «ganador»: hay herramientas para problemas distintos. Django brilla cuando quieres un panel de administración y un ORM con baterías incluidas. FastAPI brilla cuando quieres una API HTTP rápida, tipada y auto-documentada, eligiendo tú el resto del stack. Este curso construye el hilo conductor Copiloto API sobre FastAPI precisamente por eso.

3 · Ejemplo mínimo

La API más pequeña posible que ya es, de verdad, una API FastAPI con documentación:

main.py
# main.py — la API mínima de FastAPI
from fastapi import FastAPI

app = FastAPI()          # 1. creamos la aplicación (un objeto ASGI)


@app.get("/")            # 2. decorador: registra una ruta GET en la raíz
def read_root():         # 3. la función que se ejecuta al llamar a "/"
    return {"message": "Hello, FastAPI"}   # 4. un dict se serializa a JSON

Levántala con uvicorn (veremos los detalles en la lección 2) y comprueba las tres URLs:

terminal
# Ejecuta el servidor de desarrollo con recarga automática
uv run uvicorn main:app --reload

# En otra terminal (o en el navegador):
#   GET http://127.0.0.1:8000/         -> {"message":"Hello, FastAPI"}
#   GET http://127.0.0.1:8000/docs     -> Swagger UI
#   GET http://127.0.0.1:8000/openapi.json -> el contrato OpenAPI

Línea por línea:

  1. from fastapi import FastAPI: FastAPI es la clase principal. Al instanciarla obtienes un objeto ASGI, algo que un servidor como uvicorn sabe invocar.
  2. app = FastAPI(): la variable se llama app por convención (uvicorn la busca así: main:app = «módulo main, atributo app»).
  3. @app.get("/"): un decorador que registra la función como manejadora de peticiones GET a /. Internamente FastAPI guarda esa ruta en su tabla de rutas.
  4. return {"message": ...}: devolver un dict es suficiente. FastAPI lo serializa a JSON y responde 200 OK con Content-Type: application/json.

Fíjate en que no hay if __name__ == "__main__": el servidor se ejecuta por fuera (uvicorn), no dentro del archivo. Esto permite usar el mismo proceso con distintos servidores y configuraciones sin tocar tu código.

4 · Ejemplo real

Nuestro hilo conductor es Copiloto API: el asistente con RAG del curso Aprende IA, ahora expuesto como servicio HTTP. Su primer endpoint en cualquier API de producción es /health, el «¿estás vivo?» que consultan balanceadores, contenedores y monitores.

app/main.py
from fastapi import FastAPI

# Metadatos: viajan al OpenAPI y se ven en /docs. Documentan el servicio, no el código.
app = FastAPI(
    title="Copiloto API",
    version="0.1.0",
    description="API del Copiloto: respuestas con RAG sobre los módulos del curso.",
)


@app.get("/health", tags=["system"])
def health() -> dict[str, str]:
    # Un health check debe ser barato y sin dependencias externas.
    return {"status": "ok", "service": "copiloto-api", "version": app.version}

Decisiones y porqués:

  • title, version, description: no son decoración. Van al esquema OpenAPI y aparecen en /docs; son la ficha de identidad del servicio para quien lo consume.
  • tags=["system"]: agrupa el endpoint bajo una categoría en la documentación. Cuando la API tenga /modules, /ask y /auth, las etiquetas evitan que /docs sea un muro de endpoints.
  • dict[str, str]: la anotación de retorno describe la forma de la respuesta. En el módulo 2 la sustituiremos por un response_model Pydantic para filtrar campos sensibles; aquí basta con el tipo.
  • Sin dependencias externas: si /health consultara la base de datos, un fallo de la BD haría fallar el propio monitor. Un health check comprueba que el proceso está vivo; para la BD se suele añadir /ready.

Este patrón — app con metadatos + endpoints agrupados por tags — es el esqueleto de toda API profesional. Copiloto API irá creciendo sobre él: en el módulo 1 añadiremos rutas con parámetros, en el 2 respuestas modeladas y errores, y así hasta el proyecto final.

6 · Errores habituales

1. Creer que FastAPI «adivina» y valida sin tipos

Mal — sin tipos, sin validación 
@app.get("/items/{item_id}")
def read_item(item_id):        # sin tipo: FastAPI lo trata como str, no valida nada
    return {"item_id": item_id}
# /items/abc devuelve 200 con "abc"; /items/42 devuelve el texto "42", no un entero.
Bien — el tipo es la validación 
@app.get("/items/{item_id}")
def read_item(item_id: int):   # FastAPI valida, convierte y documenta solo
    return {"item_id": item_id}
# /items/abc -> 422 automático; /items/42 -> item_id es el entero 42.

2. Mezclar Flask y FastAPI en la cabeza

Mal — patrones de WSGI 
from flask import Flask, request   # ¡es otro framework!

app = Flask(__name__)

@app.get("/search")
def search():
    q = request.args["q"]           # aquí el request es global e implícito
    return {"q": q}
Bien — parámetros declarados en la firma 
from fastapi import FastAPI

app = FastAPI()

@app.get("/search")
def search(q: str):                 # el query param llega como argumento, tipado
    return {"q": q}

3. Bloquear el loop de eventos

Mal — I/O bloqueante dentro de async 
import requests                   # cliente síncrono

@app.get("/weather")
async def weather():
    r = requests.get("https://api.example.com/weather")  # congela TODO el servidor
    return r.json()
Bien — cliente async (o función sync) 
import httpx

@app.get("/weather")
async def weather():
    async with httpx.AsyncClient() as client:   # cede el control al loop mientras espera
        r = await client.get("https://api.example.com/weather")
    return r.json()

4. Instalar FastAPI «a secas» y no tener servidor

Mal — falta el servidor ASGI 
uv add fastapi          # sin uvicorn: no hay nada que ejecute ASGI
uvicorn main:app        # command not found
Bien — extra standard 
uv add "fastapi[standard]"   # incluye uvicorn y el CLI de FastAPI
uv run uvicorn main:app --reload

5. Tratar /docs como una demo desechable

Mal — documentación vacía 
app = FastAPI()   # todo por defecto: /docs no dice nada del servicio
# título genérico "FastAPI", versión "0.1.0", endpoints amontonados
Bien — el contrato como producto 
app = FastAPI(title="Copiloto API", version="0.1.0",
              description="API del Copiloto con RAG.")
# /docs y /openapi.json pasan a ser un contrato legible para el equipo y los clientes.

7 · Ejercicio guiado

Objetivo: levantar la API mínima y comprobar con tus ojos que el tipo genera validación y documentación.

  1. Paso 1: crea el proyecto e instala FastAPI con el extra standard: 
    uv init copiloto-api
cd copiloto-api
uv add "fastapi[standard]"

    Resultado esperado: aparece un pyproject.toml con fastapi[standard] en dependencies (lección 2 en detalle).

  2. Paso 2: crea main.py con una ruta tipada: 
    from fastapi import FastAPI

app = FastAPI(title="Mi primera API", version="0.1.0")


@app.get("/")
def read_root():
    return {"message": "Hello, FastAPI"}


@app.get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None):
    return {"item_id": item_id, "q": q}
  3. Paso 3: arranca el servidor: 
    uv run uvicorn main:app --reload

    Resultado esperado: Uvicorn running on http://127.0.0.1:8000. Deja esta terminal abierta.

  4. Paso 4 (validación real): abre http://127.0.0.1:8000/items/abc en el navegador. Verás un error 422 Unprocessable Entity con un JSON que explica que abc no es un entero. Ahora abre /items/42?q=hola: responde {"item_id":42,"q":"hola"}. No escribiste nada de eso: lo dedujo el tipo.
  5. Paso 5 (documentación): abre /docs. Verás tus dos endpoints con «Try it out». Pulsa en /items/{item_id}, «Try it out», pon 99 y «Execute»: verás la petición curl equivalente y la respuesta. Después abre /openapi.json y localiza el tipo integer del parámetro item_id: eso es el contrato que acaba de consumir Swagger UI.
  6. Paso 6 (verificación): detén el servidor con Ctrl+C. Cambia el title de FastAPI(...), guarda y arranca de nuevo: /docs refleja el nuevo título. Acabas de ver que metadatos y código son la misma fuente de verdad.

8 · Reto

🎯 Una ruta que solo falle cuando tú quieras

Añade a la API del ejercicio una ruta GET /divide/{a}/{b} que reciba dos path params tipados como float y devuelva el cociente a / b. El reto: consigue que /divide/10/0 no se comporte como /divide/abc/2, es decir, que distingas un error de validación (422, lo genera FastAPI) de un error de negocio (división por cero, lo decides tú). Mira el esquema OpenAPI de tu ruta en /openapi.json y compáralo con el de /items/{item_id}.

Pista: el 422 de abc llega antes de tu función (FastAPI no puede convertir a número). La división por cero, en cambio, ocurre dentro: tendrás que lanzar tú un error HTTP explícito. Reserva esta idea; el módulo 2 la convierte en una forma consistente (Problem Details).

9 · Resumen

  • FastAPI es un framework de APIs HTTP que combina Starlette (ASGI), Pydantic v2 (validación) y su propia capa de rutas, dependencias y OpenAPI.
  • Usa ASGI en lugar de WSGI: asíncrono, concurrente y capaz de servir WebSockets y streaming. Rinde más si no bloqueas el loop.
  • La validación vive en los tipos: declaras int, str o un modelo Pydantic y obtienes validación, conversión, serialización y documentación de una sola vez.
  • La documentación es automática: /docs (Swagger UI), /redoc (ReDoc) y /openapi.json, el contrato que es la fuente de verdad del API.
  • Frente a Flask (WSGI, micro) y Django (todo incluido), FastAPI apuesta por APIs tipadas y asíncronas, dejando el ORM y el resto del stack a tu elección.
  • El hilo conductor del curso, Copiloto API, arranca con un /health sobre este esqueleto.

10 · Preguntas frecuentes

¿FastAPI es más rápido que Flask o Django?

FastAPI suele ser más rápido en peticiones concurrentes y con mucha espera de I/O, gracias a ASGI y a que Pydantic v2 tiene su núcleo en Rust. En cargas de pura CPU la diferencia se diluye: ahí manda tu lógica. La ventaja real no es solo el benchmark, sino que la misma declaración de tipos te da validación y documentación gratis.

¿Necesito saber async/await para empezar?

No para el primer endpoint: FastAPI acepta funciones def normales y las ejecuta en un pool de hilos, así que puedes empezar en síncrono. Pero para aprovechar ASGI (y no bloquear el servidor) conviene entenderlo, y lo veremos en profundidad en las lecciones de rutas y de I/O.

¿Puedo usar FastAPI para servir HTML en vez de JSON?

Sí, devolviendo un HTMLResponse o usando plantillas (Jinja2), pero no es su fuerte: FastAPI está pensado para APIs. Si tu proyecto es principalmente vistas de servidor, Django o Flask con plantillas encajan mejor. Aquí nos centramos en APIs JSON.

¿De dónde sale /docs? ¿Tengo que configurarlo?

Sale del esquema OpenAPI que FastAPI genera automáticamente a partir de tus rutas y tipos. No configuras nada para tenerlo; sí puedes personalizarlo (título, versión, descripción) y hasta desactivarlo. Es documentación derivada del código, así que no se queda obsoleta.

¿FastAPI reemplaza a Django para un backend completo?

Depende. FastAPI no incluye ORM, panel de administración ni sistema de plantillas: los eliges tú (en este curso, SQLModel + Alembic). Si quieres esas «baterías incluidas», Django sigue siendo una gran opción. Si quieres una API tipada, rápida y controlada, FastAPI es la elección natural.
