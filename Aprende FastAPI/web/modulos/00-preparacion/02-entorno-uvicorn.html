Entorno con uv y uvicorn

Módulo 0 · Preparación 🕐 30 minutos

1 · Introducción

Antes de escribir una sola línea de lógica, una API necesita un entorno reproducible: la versión exacta de Python, las dependencias exactas con sus versiones, y la forma de arrancar el servidor. En este curso ese trío lo resuelven uv (gestor de proyectos y paquetes) y uvicorn (servidor ASGI). El objetivo de esta lección es que dentro de veinte minutos tengas un proyecto que arranca con un comando y que puedes reconstruir idéntico en otra máquina.

Veremos por qué uv sustituye a pip + venv + pip-tools, qué es un pyproject.toml y un uv.lock, cómo funciona --reload y por qué nunca debe ir a producción, y cómo manejar variables de entorno y .env sin terminar con un secreto en Git. Todo con equivalencias Linux/macOS y Windows (PowerShell).

¿Por qué existe esta lección? Porque el 90% de los problemas de «a mí no me arranca» son de entorno: versión de Python equivocada, dependencia no instalada, servidor apuntando al módulo incorrecto. Domina esto una vez y no volverás a perder una tarde.

2 · Teoría

Por qué uv y no pip + venv

pip instala paquetes, venv crea entornos y pip-tools/poetry intentan fijar versiones. uv hace todo eso en una sola herramienta, escrita en Rust, y muy rápido. Pero la velocidad es la anécdota: lo importante es que uv trabaja con un proyecto declarativo.

Herramienta clásicaEquivalente con uvQué cambia
python -m venv .venvuv venvuv sync crea y sincroniza el entorno solo
pip install fastapiuv add "fastapi[standard]"Además de instalar, escribe la dependencia en pyproject.toml
pip install -r requirements.txtuv syncReconstruye el entorno exacto desde uv.lock
python main.pyuv run python main.pyEjecuta dentro del entorno del proyecto sin activarlo
pip freeze > requirements.txtuv.lock (automático)El bloqueo de versiones se mantiene solo

Dos archivos, dos propósitos. pyproject.toml declara lo que pides (con rangos de versión); uv.lock registra lo que se instaló (con versiones exactas y hashes). El primero se edita y se versiona a mano; el segundo lo genera uv y también se versiona, para que todo el equipo use exactamente las mismas versiones.

Anatomía de un proyecto uv

  copiloto-api/
  ├── pyproject.toml      <- declaras dependencias y metadatos (a mano)
  ├── uv.lock             <- versiones exactas resueltas (automático, sí se versiona)
  ├── .python-version     <- "3.12" (uv fija la versión de Python del proyecto)
  ├── .venv/              <- entorno virtual (NO se versiona, en .gitignore)
  ├── .env                <- variables y secretos locales (NO se versiona)
  ├── main.py             <- tu código (la app)
  └── app/                <- paquete de la aplicación (lección 4)

uvicorn: el servidor que habla ASGI

FastAPI define la aplicación, pero no la ejecuta: necesita un servidor que implemente ASGI. uvicorn es ese servidor. La forma canónica de lanzarlo es módulo:atributo:

terminal
# uvicorn  <módulo>:<objeto_app>  [opciones]
uv run uvicorn main:app --reload
#              ^^^^  ^^^
#              main.py   la variable 'app = FastAPI()' de dentro

El mapa de una petición por el servidor es:

  cliente HTTP
      |
      v
  +-----------+     evento ASGI      +---------------------+
  |  uvicorn  | -------------------> |  app (FastAPI)      |
  | (servidor)|  scope, receive,     |  -> rutas           |
  |           |  send                |  -> validación      |
  |           | <------------------- |  -> respuesta JSON  |
  +-----------+    Response ASGI     +---------------------+
      |
      v
  cliente recibe status + headers + body

--reload: recarga automática en desarrollo

Con --reload, uvicorn vigila tus archivos .py y, al detectar un cambio, reinicia el proceso. Guardas y el navegador ya sirve el código nuevo. Internamente ejecuta dos procesos: uno «vigilante» (reloader) y otro que es tu aplicación.

--reload es solo para desarrollo. Reinicia proceso, consume recursos y añade latencia. En producción se arranca sin --reload y con varios workers (o dentro de un contenedor orquestado). Lo veremos en el módulo de despliegue.

El CLI fastapi dev

Con el extra standard, FastAPI trae su propio CLI que envuelve a uvicorn con valores por defecto sensatos. Es cómodo, pero conviene conocer el comando «de verdad»:

ComandoEquivale aUso

Variables de entorno y .env

La configuración (puerto, URL de base de datos, claves de API) no vive en el código: vive en el entorno. Tu código lee variables; tú las defines por fuera. Así el mismo código corre en local, en CI y en producción con valores distintos.

.env
# .env — valores locales. NUNCA se versiona (va en .gitignore).
APP_ENV=development
DATABASE_URL=sqlite:///./copiloto.db
API_KEY=dev-no-es-un-secreto-real
app/config.py
import os

# Lectura directa de variables de entorno. En el módulo 3 las validaremos
# y tiparemos con pydantic-settings; aquí basta con ver la idea.
APP_ENV = os.getenv("APP_ENV", "development")
DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./copiloto.db")

uv puede cargar el .env por ti al ejecutar:

terminal
uv run --env-file .env uvicorn main:app --reload

Precedencia clara: si una variable existe tanto en el entorno real como en el .env, gana la del entorno. Eso permite que producción (que define variables reales) ignore cualquier .env heredado.

Windows (PowerShell) frente a Linux/macOS

Tareabash (Linux/macOS/WSL2)PowerShell (Windows)
Definir variable solo en esta sesiónexport APP_ENV=dev$env:APP_ENV = "dev"
Ver una variableecho $APP_ENV$env:APP_ENV
Borrar una variableunset APP_ENVRemove-Item Env:APP_ENV

Con uv casi nunca necesitas definir variables «a mano»: el .env y --env-file funcionan igual en los tres sistemas.

3 · Ejemplo mínimo

Del directorio vacío al «servidor corriendo» en cinco comandos:

terminal — bash (Linux/macOS/WSL2)
# 1. Crear el proyecto (genera pyproject.toml + .gitignore + hello.py)
uv init copiloto-api
cd copiloto-api

# 2. Fijar la versión de Python del proyecto (crea .python-version)
uv python pin 3.12

# 3. Añadir FastAPI con el extra que trae uvicorn y el CLI
uv add "fastapi[standard]"

# 4. Ver el entorno que uv creó y sincronizó por ti (.venv + uv.lock)
ls -a

# 5. Arrancar el servidor de desarrollo
uv run uvicorn main:app --reload

Equivalencia rápida en PowerShell (los comandos de uv son idénticos; cambian los utilitarios del sistema):

terminal — PowerShell (Windows)
uv init copiloto-api
cd copiloto-api
uv python pin 3.12
uv add "fastapi[standard]"
Get-ChildItem -Force        # equivale a: ls -a
uv run uvicorn main:app --reload

Línea por línea:

  1. uv init copiloto-api: crea la carpeta y un pyproject.toml mínimo. Si ya existe un pyproject.toml, uv aborta: no sobrescribe proyectos.
  2. uv python pin 3.12: escribe 3.12 en .python-version. A partir de aquí, todo comando del proyecto usará esa versión (y uv la instalará si falta).
  3. uv add "fastapi[standard]": resuelve dependencias, escribe el rango en pyproject.toml, genera uv.lock y sincroniza .venv. Es «instalar + declarar + bloquear» en un paso.
  4. uv run uvicorn main:app --reload: comprueba que el entorno está al día, ejecuta uvicorn dentro de él (sin activar nada) y arranca tu app con recarga automática.

Fíjate en que nunca activaste el entorno virtual: no hay source .venv/bin/activate ni .\.venv\Scripts\Activate.ps1. uv run lo hace por ti. Puedes activarlo si lo prefieres, pero no es necesario.

4 · Ejemplo real

Así queda el pyproject.toml de Copiloto API tras añadir FastAPI y, más adelante, el resto del stack del curso (SQLModel, Alembic, JWT, tests). Es la carta de presentación del proyecto:

pyproject.toml
[project]
name = "copiloto-api"
version = "0.1.0"
description = "API del Copiloto: respuestas con RAG sobre los módulos del curso."
readme = "README.md"
requires-python = ">=3.12"
dependencies = [
  "fastapi[standard]>=0.115",
  "pydantic-settings>=2.4",   # configuración tipada (módulo 3)
  "sqlmodel>=0.0.22",         # persistencia (módulo 4)
]

[dependency-groups]
dev = [
  "pytest>=8.0",
  "httpx>=0.27",              # cliente async para tests (módulo 6)
  "ruff>=0.6",                # linter + formatter
  "mypy>=1.11",               # tipado estático
]

Y así se arranca el proyecto en desarrollo y en «modo producción local»:

terminal
# Desarrollo: recarga automática al guardar y variables del .env
uv run --env-file .env uvicorn app.main:app --reload --host 127.0.0.1 --port 8000

# Producción (mismo código, sin reload, escuchando en todas las interfaces)
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4

Decisiones y porqués:

  • requires-python = ">=3.12": el curso fija 3.12+. uv se niega a resolver con una versión menor, así que el error aparece pronto y no en producción.
  • Dependencias de desarrollo en [dependency-groups] dev: pytest, ruff y mypy no viajan al contenedor de producción. uv sync --no-dev las omite.
  • app.main:app: en cuanto el proyecto crezca (lección 4), la app vivirá en el paquete app, no en un main.py suelto. Cambiar la ruta ahora evita sorpresas después.
  • --workers 4: varios procesos para aprovechar varios núcleos. Nunca combine --workers con --reload: son modos distintos.

Nada de secretos en el repositorio. El API_KEY del .env jamás se versiona (va en .gitignore). En producción, las variables se inyectan desde el orquestador o el gestor de secretos. El curso lo convierte en regla en el módulo de seguridad.

5 · Buenas prácticas

Versionar pyproject.toml y uv.lock Versionar .venv/ El lock garantiza el mismo entorno en tu máquina y en CI; el .venv es local y enorme
Añadir dependencias con uv add pip install dentro del entorno del proyecto pip instala pero no declara: la dependencia se pierde al reconstruir

Separar dependencias dev de las de producción Instalar todo en la imagen de producción Menos superficie de ataque, imágenes más pequeñas y arranque más rápido

6 · Errores habituales

1. Instalar con pip y perder las dependencias

Mal — instala pero no declara 
source .venv/bin/activate
pip install fastapi uvicorn     # funciona... hasta que otro clona el repo
# pyproject.toml NO cambió: la dependencia no existe para nadie más.
Bien — declara y bloquea 
uv add "fastapi[standard]"      # escribe pyproject.toml + uv.lock y sincroniza
# Cualquiera reconstruye tu entorno exacto con:
uv sync

2. Dejar --reload encendido en producción

Mal — modo desarrollo en producción 
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
# Reinicia el proceso por cualquier cambio de archivo, gasta CPU y
# no debe convivir con --workers.
Bien — servidor estable con workers 
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
# Sin --reload. En contenedores, un proceso por contenedor y escala el orquestador.

3. Apuntar uvicorn al objeto equivocado

Mal — módulo o atributo inexistentes 
uv run uvicorn app:app --reload
# ERROR: Error loading ASGI app. Could not import module "app".
# (app es un PAQUETE, no un módulo: falta el .main)
Bien — módulo:atributo correctos 
uv run uvicorn app.main:app --reload
# módulo app/main.py, atributo app = FastAPI()

4. Commitear el .env (o el .venv)

Mal — secretos y basura en Git 
git add .
git commit -m "setup"
# Se subieron .env (con API_KEY) y .venv/ (miles de archivos).
Bien — ignorar lo local 
printf '.venv/\n.env\n__pycache__/\n' >> .gitignore
git add .gitignore pyproject.toml uv.lock
git commit -m "setup del proyecto"

5. Leer variables de entorno que nadie definió

Mal — acceso directo que revienta 
import os

db_url = os.environ["DATABASE_URL"]   # KeyError si no está definida
Bien — valor por defecto y, luego, validación 
import os

db_url = os.getenv("DATABASE_URL", "sqlite:///./copiloto.db")
# En el módulo 3 esto lo hará pydantic-settings: tipado, validado y con errores claros.

7 · Ejercicio guiado

Objetivo: montar un proyecto reproducible, leer una variable de entorno y comprobar la recarga automática.

  1. Paso 1: crea el proyecto e instala el stack mínimo: 
    uv init copiloto-api && cd copiloto-api
uv python pin 3.12
uv add "fastapi[standard]"

    Resultado esperado: pyproject.toml, uv.lock, .python-version y .venv/ en la carpeta.

  2. Paso 2: crea el .env y un main.py que lo lea: 
    # .env
printf 'APP_NAME=Copiloto API\nAPP_ENV=development\n' > .env

    # main.py
import os

from fastapi import FastAPI

app = FastAPI(title=os.getenv("APP_NAME", "Sin nombre"))


@app.get("/")
def read_root():
    return {
        "message": "Hello, FastAPI",
        "env": os.getenv("APP_ENV", "unknown"),
    }
  3. Paso 3: arranca cargando el .env: 
    uv run --env-file .env uvicorn main:app --reload

    Resultado esperado: Uvicorn running on http://127.0.0.1:8000. Abre http://127.0.0.1:8000/: verás "env":"development" (la variable llegó desde el .env). Abre /docs: el título es «Copiloto API», también desde el .env.

  4. Paso 4 (recarga): con el servidor corriendo, cambia el mensaje de read_root a "message": "Hello, reloaded" y guarda. Mira la terminal: uvicorn detecta el cambio y reinicia. Recarga / y verás el mensaje nuevo. Eso es --reload.
  5. Paso 5 (recuperación): introduce a propósito un SyntaxError (borra un paréntesis) y guarda. El servidor se detiene y muestra el error con archivo y línea. Corrígelo y guarda: arranca solo de nuevo. No pierdes el comando: el reloader reintenta.
  6. Paso 6 (verificación): detén con Ctrl+C y comprueba que el .env está ignorado: git status no debe listar .env ni .venv/. Si aparecen, añádelos a .gitignore.

8 · Reto

🎯 Dos entornos, un solo código

Haz que tu API lea el puerto desde una variable de entorno PORT (por defecto 8000) y arranca el servidor en dos configuraciones sin tocar el código: una «development» que cargue el .env local, y una «staging» en la que definas APP_ENV=staging y PORT=9000 directamente en la terminal (sin .env). Demuestra que la variable del entorno gana sobre el .env cuando ambas existen.

Pista: uvicorn acepta --port en la línea de comandos, pero el reto es que el puerto salga de os.getenv("PORT"). Para leer el entorno real en bash usa export PORT=9000 (PowerShell: $env:PORT = "9000") y fíjate en la precedencia que vimos en la teoría.

9 · Resumen

  • uv sustituye a pip + venv + pip-tools: declara, resuelve, bloquea y ejecuta en un solo flujo.
  • pyproject.toml declara lo que pides; uv.lock fija lo que se instaló. Ambos se versionan; .venv/ no.
  • uvicorn es el servidor ASGI. Se lanza como módulo:atributo: uv run uvicorn app.main:app --reload.
  • --reload reinicia al detectar cambios: perfecto en desarrollo, prohibido en producción (allí, --workers).
  • La configuración vive en variables de entorno y .env (nunca en el código ni en Git); uv run --env-file .env las carga.
  • Separar dependencias en dev evita llevar tests y linters a producción.

10 · Preguntas frecuentes

¿Tengo que activar el entorno virtual con uv?

No. uv run ejecuta cualquier comando dentro del entorno del proyecto sin activarlo. Puedes activarlo si prefieres un shell «dentro» del entorno, pero no es necesario y muchos equipos ya no lo hacen. Para usar el intérprete directamente: uv run python -c "...".

¿Versiono uv.lock en Git?

Sí. El lock garantiza que tú, tus compañeros y el CI instalen exactamente las mismas versiones con hashes. Para aplicaciones, versionarlo siempre; para una librería publicable, es discutible, pero en una API como Copiloto API se versiona sin dudar.

¿fastapi dev o uvicorn --reload?

Para empezar, fastapi dev es cómodo: descubre main.py y activa el reload solo. Con el tiempo querrás controlar host, puerto y flags, y entonces usarás uvicorn directamente. En este curso usamos uvicorn para que veas siempre qué se está ejecutando.

¿Por qué mi cambio no se refleja con --reload?

Casi siempre por una de tres razones: el servidor no se está ejecutando con --reload; estás editando un archivo fuera del directorio que uvicorn vigila; o el cambio está dentro de un módulo que no se recarga (ajustes al propio servidor). Reinicia manualmente para descartar y revisa la ruta desde la que lanzaste el comando.

¿.env es lo mismo que --env-file de Docker?

Se parecen en intención (inyectar variables), pero son mecanismos distintos. .env local lo carga uv o pydantic-settings en tu máquina; en Docker, las variables se pasan al contenedor con --env, env_file o el orquestador. La regla no cambia: los secretos nunca van al repositorio.
