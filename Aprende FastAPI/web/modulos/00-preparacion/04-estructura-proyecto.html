Estructura del proyecto

Módulo 0 · Preparación 🕐 35 minutos

1 · Introducción

Un main.py de veinte líneas sirve para aprender, no para producir. En cuanto la API crece —rutas, validación, base de datos, autenticación, tests— un único archivo se convierte en un laberinto donde cada cambio roza todo lo demás. La solución no es «escribir más ordenado»: es separar responsabilidades en capas con una dirección de dependencia clara.

En esta lección montamos la estructura de carpetas que usaremos durante todo el curso: app/main.py como punto de composición, config.py para la configuración, routers/ para los endpoints, schemas/ para los modelos de entrada/salida, models/ para las tablas y deps.py para las dependencias compartidas. Y el pyproject.toml como manifiesto del proyecto. Es el andamio sobre el que se construye Copiloto API.

¿Por qué existe esta lección? Porque la arquitectura no se añade al final: se decide al principio. Elegir bien las capas ahora significa que añadir persistencia (módulo 4), seguridad (módulo 5) y tests (módulo 6) será rellenar huecos, no reescribir.

Nada de sobreingeniería. Esta estructura es un punto de partida sensato para una API real, no una obligación religiosa. Copiloto API la usa; si tu proyecto es de tres endpoints, adáptala. Lo que sí es no negociable: cada capa tiene una responsabilidad y las dependencias van en una sola dirección.

2 · Teoría

El principio: cada capa responde a una pregunta

El desorden nace cuando una misma pieza intenta responder a varias preguntas a la vez. Nuestra separación asigna una pregunta a cada módulo:

CapaPregunta que respondeContiene
main.py¿Cómo se ensambla todo?Creación de app, metadatos, include_router, lifespan
config.py¿Con qué valores corre?Settings tipados (pydantic-settings), lectura del entorno
routers/¿Qué endpoints existen?Rutas HTTP, traducción petición→llamada, sin lógica de negocio
schemas/¿Qué forma tienen los datos del API?Modelos Pydantic de entrada/salida (el contrato)
models/¿Cómo se guardan los datos?Tablas SQLModel/SQLAlchemy (el esquema de la base de datos)
deps.py¿Qué necesitan los endpoints para trabajar?Proveedores Depends: settings, sesión de BD, usuario actual

Analogía: piensa en un restaurante. routers/ son los camareros (toman el pedido, no cocinan); los schemas/ son el formato de comanda (qué campos lleva cada pedido); los models/ son las estanterías de la despensa (cómo se almacena todo); deps.py es el servicio que trae los ingredientes a la cocina; y main.py es quien abre el restaurante y decide qué camareros trabajan ese día. Si el camarero empieza a cocinar, el restaurante colapsa.

La regla de oro: dependencias en una sola dirección

Las capas no se llaman entre sí en cualquier orden. El flujo es de fuera hacia dentro y siempre el mismo:

  petición HTTP
      |
      v
  routers/          (endpoints: reciben y despachan)
      |  usa
      v
  deps.py           (provee settings, sesión de BD, usuario)
      |  usa
      v
  schemas/  y  models/   (formas de los datos)
      ^
      |  configurados por
  config.py
      ^
      |  ensamblados por
  main.py

Consecuencias prácticas de respetar la flecha:

  • schemas/ y models/ no importan routers/: las formas de datos no deben saber que existen endpoints. Si un schema importa un router, has invertido la flecha y, casi seguro, creado un import circular.
  • routers/ no importa main.py: los routers se declaran antes de montarse; main.py importa a los routers, nunca al revés.
  • config.py no importa nada del dominio: la configuración es una hoja del grafo, de la que todos dependen.

El síntoma #1 de mala arquitectura en FastAPI es el ImportError: cannot import name 'app' from partially initialized module. Casi siempre es una flecha invertida o un ciclo. La estructura por capas y la regla de dirección existen, en gran parte, para evitarlo.

¿Por qué models/ y schemas/ separados? Porque responden a preguntas distintas: models/ describe cómo se almacena (tabla, columnas, índices, relaciones); schemas/ describe cómo se transporta por la red (qué campos entran, qué campos salen, cuáles se ocultan). Aunque hoy se parezcan, mañana el schema de respuesta ocultará el hashed_password y el de entrada tendrá un password que el modelo de tabla nunca verá en claro. Mezclarlos es la puerta a filtrar datos sensibles.

Composición: main.py monta, no implementa

main.py es el composition root: el único lugar donde se decide qué piezas forman la API. Los routers se declaran por separado y se «montan» con include_router, aportando prefix y tags en el punto de unión:

app/main.py
from fastapi import FastAPI

from app.routers import ask, system

app = FastAPI(title="Copiloto API", version="0.1.0")

# Cada router trae sus endpoints; aquí solo decidimos cómo se montan.
app.include_router(system.router)                 # /, /health
app.include_router(ask.router, prefix="/ask", tags=["ask"])
app/routers/system.py
from fastapi import APIRouter

# Un APIRouter es un "mini-app": agrupa rutas afines en su propio módulo.
router = APIRouter()


@router.get("/health", tags=["system"])
def health() -> dict[str, str]:
    return {"status": "ok"}


@router.get("/", tags=["system"])
def read_root() -> dict[str, str]:
    return {"service": "copiloto-api"}

Ventajas de montar así:

  • Un archivo por área funcional (system, ask, y más adelante modules, auth): localizas el código por dónde vive la ruta.
  • prefix y tags en un solo sitio: si mañana /ask pasa a /v1/ask, lo cambias en un único punto.
  • Testeable por partes: puedes probar un router de forma aislada.

pyproject.toml: el manifiesto del proyecto

Ya lo conocimos en la lección 2 para las dependencias. En un proyecto por capas también declara metadatos (nombre, versión, Python mínimo) y herramientas (ruff, mypy, pytest):

pyproject.toml
[project]
name = "copiloto-api"
version = "0.1.0"
description = "API del Copiloto: respuestas con RAG sobre los módulos del curso."
requires-python = ">=3.12"
dependencies = [
  "fastapi[standard]>=0.115",
  "pydantic-settings>=2.4",
]

[dependency-groups]
dev = ["pytest>=8.0", "httpx>=0.27", "ruff>=0.6", "mypy>=1.11"]

[tool.ruff]
line-length = 100
target-version = "py312"

[tool.mypy]
python_version = "3.12"
strict = true
plugins = ["pydantic.mypy"]

Un único archivo declara qué es el proyecto y cómo se comprueba su calidad. Las herramientas leen de aquí; no hay que repetir configuración por bandera de línea de comandos.

config.py y deps.py: proveer, no improvisar

Dos piezas que veremos a fondo en el módulo 3, pero que conviene situar ya. config.py centraliza los valores de entorno en un objeto tipado:

app/config.py
from functools import lru_cache

from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    app_name: str = "Copiloto API"
    database_url: str = "sqlite:///./copiloto.db"
    top_k_default: int = 3


@lru_cache
def get_settings() -> Settings:
    # lru_cache: se construye UNA vez y se reutiliza (útil como dependencia).
    return Settings()

Y deps.py expone esos recursos como dependencias reutilizables por cualquier endpoint:

app/deps.py
from typing import Annotated

from fastapi import Depends

from app.config import Settings, get_settings

# Alias tipado: evita repetir "Depends(get_settings)" en cada firma y
# hace que el editor y mypy entiendan el tipo.
SettingsDep = Annotated[Settings, Depends(get_settings)]

Un recurso, un lugar. Si un endpoint necesita configuración, pide SettingsDep. Si necesita base de datos, pedirá SessionDep (módulo 4). La misma dependencia se resuelve igual en todo el código, y en los tests se puede sustituir con una versión falsa. Esa es la potencia de la inyección de dependencias que veremos en el módulo 3.

3 · Ejemplo mínimo

La estructura por capas más pequeña que sigue siendo válida: dos archivos y un paquete.

Estructura
mini-api/
├── app/
│   ├── __init__.py        <- vacío, pero imprescindible
│   ├── main.py
│   └── routers/
│       ├── __init__.py
│       └── system.py
└── pyproject.toml
app/routers/system.py
from fastapi import APIRouter

router = APIRouter()


@router.get("/health", tags=["system"])
def health() -> dict[str, str]:
    return {"status": "ok"}
app/main.py
from fastapi import FastAPI

from app.routers import system

app = FastAPI(title="Mini API")
app.include_router(system.router)

Arráncala desde la raíz del proyecto (donde está app/):

terminal
uv run uvicorn app.main:app --reload
# GET http://127.0.0.1:8000/health  -> {"status":"ok"}

Línea por línea, lo esencial del patrón:

  1. app/__init__.py: aunque esté vacío, convierte app/ en un paquete de Python. Sin él, from app.routers import system falla (al menos en instalaciones e imports basados en ficheros).
  2. router = APIRouter(): instancia un router. Los endpoints se declaran con @router.get(...), exactamente igual que con @app.get(...).
  3. app.include_router(system.router): une el router a la app. Aquí es donde, si quieres, añades prefix y tags sin tocar system.py.
  4. uvicorn app.main:app: nota la ruta app.main: paquete app, módulo main, atributo app. No es un archivo suelto.

Así queda la estructura completa de Copiloto API al terminar el curso. Fíjate en que cada capa existe ya desde el módulo 0, aunque algunas estén casi vacías: es el andamio que iremos rellenando.

Estructura — proyectos/copiloto-api/
copiloto-api/
├── pyproject.toml
├── uv.lock
├── .env
├── .gitignore
├── README.md
├── app/
│   ├── __init__.py
│   ├── main.py              # composition root: crea app y monta routers
│   ├── config.py            # Settings (pydantic-settings)
│   ├── deps.py              # SettingsDep, SessionDep, CurrentUserDep…
│   ├── routers/
│   │   ├── __init__.py
│   │   ├── system.py        # GET /  y  GET /health
│   │   ├── modules.py       # GET /modules (módulo 1-2)
│   │   ├── ask.py           # POST /ask (RAG)
│   │   └── auth.py          # POST /auth/token (módulo 5)
│   ├── schemas/
│   │   ├── __init__.py
│   │   ├── ask.py           # AskRequest, AskResponse
│   │   └── user.py          # UserCreate, UserRead (sin secretos)
│   └── models/
│       ├── __init__.py
│       ├── query.py         # QueryLog (histórico de consultas)
│       └── user.py          # User (tabla)
└── tests/

    ├── test_system.py
    └── test_ask.py
app/main.py
from fastapi import FastAPI

from app.config import get_settings
from app.routers import ask, modules, system

settings = get_settings()

app = FastAPI(
    title=settings.app_name,
    version="0.1.0",
    description="API del Copiloto: respuestas con RAG sobre los módulos del curso.",
)

# El "por qué" de cada router vive en su módulo; aquí solo se compone el grafo.
app.include_router(system.router)
app.include_router(modules.router, prefix="/modules", tags=["modules"])
app.include_router(ask.router, prefix="/ask", tags=["ask"])

Decisiones y porqués:

  • Prefijos por área: /modules y /ask agrupan la API por dominio. En /docs se ve una API ordenada, no una lista plana.
  • settings.app_name en los metadatos: el título se configura por entorno. En desarrollo «Copiloto API (dev)»; en producción, el nombre real. Cero código duplicado.
  • Un router por verbo de negocio: system (infra), modules (lectura), ask (RAG), auth (seguridad). Cada uno con su responsabilidad.
  • tests/ al mismo nivel que app/: los tests no viven dentro del paquete desplegado; conftest.py centraliza las fixtures.

Cuando llegues al módulo 4, añadir persistencia será crear app/models/query.py y añadir un SessionDep a deps.py. Ni un endpoint existente tiene que cambiar de sitio. Esa es la prueba de que las capas estaban bien elegidas.

5 · Buenas prácticas

HazEvitaPor qué
Un router por área funcional (system, ask, auth) Un main.py o un router con treinta endpoints Localizas el código por dominio y puedes testear cada router aparte
Separar schemas/ (transporte) de models/ (almacenamiento) Usar el mismo modelo para tabla y respuesta Evita filtrar campos sensibles (contraseñas, flags internos)
Configurar todo en config.py Repartir os.getenv por todo el código Una sola fuente de verdad; los valores se validan y se documentan solos
Exponer recursos con deps.py Instanciar la sesión de BD o el cliente dentro de cada endpoint Reutilización, testabilidad y recursos cerrados correctamente
Routers que reciben y despachan, sin lógica pesada Reglas de negocio enterradas en la función del endpoint La lógica se puede probar sin HTTP y reutilizar desde otros sitios
Respetar la dirección de las dependencias Que schemas/ importe routers/ Mantiene el grafo acíclico y evita los ImportError circulares

6 · Errores habituales

1. Olvidar los __init__.py

Mal — el paquete no se resuelve 
app/
├── main.py
└── routers/
    └── system.py        # sin app/__init__.py ni app/routers/__init__.py

# uvicorn app.main:app  ->  ModuleNotFoundError: No module named 'app'
Bien — paquetes explícitos 
app/
├── __init__.py
├── main.py
└── routers/
    ├── __init__.py
    └── system.py

# uvicorn app.main:app  ->  arranca correctamente

2. Import circular entre router y app

Mal — el router importa la app 
# app/routers/system.py
from app.main import app        # el router depende de la app...

@router.get("/health")
def health():
    return {"version": app.version}   # ...y la app importa este router -> ciclo
# ImportError: cannot import name 'app' from partially initialized module
Bien — los metadatos viven en config 
# app/config.py
class Settings(BaseSettings):
    app_version: str = "0.1.0"

# app/routers/system.py
from app.config import get_settings

@router.get("/health")
def health():
    return {"version": get_settings().app_version}

3. Usar el modelo de tabla como schema de respuesta

Mal — un campo sensible viaja al cliente 
# devuelve la TABLA tal cual: si tuviera una columna hashed_password,
# se serializaría al JSON sin querer.
@router.get("/users/{user_id}")
def read_user(user_id: int, session: SessionDep):
    return session.get(User, user_id)
Bien — schema explícito para la salida 
# app/schemas/user.py define SOLO los campos públicos
class UserRead(BaseModel):
    id: int
    email: str
    # sin hashed_password

@router.get("/users/{user_id}", response_model=UserRead)
def read_user(user_id: int, session: SessionDep):
    return session.get(User, user_id)   # response_model recorta lo sobrante

4. Dispersar la configuración por el código

Mal — os.getenv por todas partes 
# en routers/ask.py
top_k = int(os.getenv("TOP_K", "3"))       # repetido en 5 archivos distintos

# en routers/modules.py
top_k = int(os.getenv("TOP_K", "3"))       # una copia más: cambia en cinco sitios
Bien — una única Settings 
# app/config.py
class Settings(BaseSettings):
    top_k_default: int = 3

# cualquier endpoint
def ask(payload: AskRequest, settings: SettingsDep):
    top_k = payload.top_k or settings.top_k_default

5. Enterrar la lógica de negocio en el router

Mal — el endpoint cocina, sirve y friega 
@router.post("/ask")
def ask(payload: AskRequest, session: SessionDep):
    # 40 líneas mezclando RAG, validación de negocio, SQL y formato de respuesta
    ...
    return AskResponse(...)   # imposible de testear sin levantar HTTP y la BD
Bien — el router despacha a la lógica 
from app.services.rag import answer_question

@router.post("/ask", response_model=AskResponse)
def ask(payload: AskRequest, session: SessionDep, settings: SettingsDep):
    return answer_question(payload, session=session, settings=settings)
# El router traduce HTTP; la lógica vive aparte y se prueba sola.

La carpeta services/ (o core/) no aparece en la estructura mínima de esta lección, pero nace de forma natural en el módulo 3, cuando la lógica deja de caber en un router. Es una evolución, no una contradicción.

8 · Reto

🎯 Añade la capa que falta sin tocar las demás

Amplía Copiloto API con un router app/routers/modules.py que exponga GET /modules (devuelve una lista con dos o tres módulos ficticios del curso, cada uno con id y title) y GET /modules/{module_id} que devuelva uno. Además, crea app/schemas/module.py con un modelo Pydantic ModuleRead y úsalo como response_model. Móntalo en main.py con prefix="/modules" y tags=["modules"].

El reto de verdad: consíguelo sin editar system.py ni config.py, y haz que el module_id sea un int para que /modules/abc devuelva 422 automáticamente. Después mira /openapi.json y confirma que ModuleRead describe la respuesta y que el endpoint aparece bajo su tag.

Pista: el patrón es idéntico al de system.py: un APIRouter por archivo, el prefix solo en include_router, y el schema importado desde app.schemas.module. Si acabas importando algo de routers/ dentro de schemas/, la flecha va al revés: repiensa dónde vive ese dato.

9 · Resumen

  • Cada capa responde a una sola pregunta: main compone, config configura, routers exponen, schemas describen el transporte, models el almacenamiento, deps provee recursos.
  • La dependencia va en una sola dirección (routers → deps → schemas/models ← config): evita importes circulares.
  • main.py es el composition root: crea la app, monta routers con include_router(prefix=…, tags=…) y no implementa lógica.
  • __init__.py convierte app/ en paquete; uvicorn app.main:app se apoya en ello.
  • pyproject.toml es el manifiesto: metadatos, dependencias y configuración de ruff/mypy/pytest en un solo sitio.
  • La estructura es un andamio: los módulos siguientes rellenan capas en lugar de reescribir la app.

10 · Preguntas frecuentes

¿No es sobreingeniería para una API pequeña?

Puede serlo si el proyecto tiene tres endpoints y no va a crecer. Empieza simple y añade capas cuando la necesidad aparezca: la primera señal es un main.py que ya no cabe en la cabeza. Lo que no debes saltarte nunca es la regla de dirección de dependencias, porque es gratis y evita el dolor futuro.

¿schemas/ también debería llamarse models/?

Es una fuente clásica de confusión. Muchos equipos llaman models/ a los modelos Pydantic y db/ o tables/ a las tablas. En este curso usamos schemas/ para Pydantic (el contrato del API) y models/ para las tablas (SQLModel/SQLAlchemy), que es lo que espera quien lea la estructura por primera vez. Lo importante es ser consistente y saber por qué se separan.

¿Dónde va la lógica de negocio si los routers solo despachan?

En una capa de servicios (app/services/ o app/core/) que el router invoca. Así la lógica se prueba sin levantar HTTP y se reutiliza entre endpoints. Esta lección presenta la estructura mínima; el módulo 3 introduce los servicios cuando la lógica deja de caber en el router.

¿Por qué lru_cache en get_settings?

Para que Settings() se construya una sola vez y se reutilice en toda la aplicación. Leer el entorno y parsear el .env en cada petición sería un desperdicio, y además quieres un objeto coherente (si dos endpoints leyeran valores a la vez, podrían ver versiones distintas si algo cambia en caliente).

¿Necesito __init__.py si uso Python 3.12?

Depende de cómo se resuelvan los imports. Con el estilo clásico de paquetes (y el que usará el despliegue), sí: sin __init__.py los directorios no son paquetes importables de forma fiable, y uvicorn app.main:app puede fallar. Añadirlos es barato y elimina una clase entera de problemas. Este curso los incluye siempre.
