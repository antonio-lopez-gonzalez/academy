Depends: el corazón de FastAPI

Módulo 3 · Dependencias y configuración 🕐 35 minutos

1 · Introducción

Escribe cinco endpoints seguidos y verás el mismo patrón repetirse: leer la configuración, abrir una conexión, comprobar un token, parsear la paginación, construir el motor de RAG. Ese código no es la lógica del endpoint, pero está en todos y cada uno. Si copias y pegas, tarde o temprano arreglas un bug en cuatro sitios y olvidas el quinto.

FastAPI resuelve esto con un mecanismo llamado inyección de dependencias y una función que lo activa: Depends. La idea es sencilla: en lugar de que tu endpoint vaya a buscar lo que necesita, lo declara como parámetro y FastAPI se lo entrega. Tu código se centra en una cosa y el framework se encarga del resto.

¿Por qué existe esta lección? Porque Depends es la pieza que más se repite en una API real: sesiones de base de datos, usuario autenticado, configuración, paginación, clientes HTTP. Si dominas Depends, entiendes la mitad del framework. Y si no lo dominas, acabarás escribiendo un service locator disfrazado de módulo helpers, con acoplamiento oculto y tests imposibles.

Errores típicos que verás en esta lección: llamar tú mismo a la dependencia en vez de dejar que FastAPI lo haga, abrir un recurso pesado en cada petición, guardar estado mutable en variables globales y confundir el orden de los parámetros con valor por defecto.

2 · Teoría

El problema: la lógica transversal se repite

Pensemos en tres endpoints del Copiloto API. Todos necesitan la configuración, todos leen los mismos parámetros de paginación y dos de ellos necesitan el motor de RAG:

# ❌ Sin inyección: cada endpoint repite la misma preparación
@app.get("/modules")
def list_modules():
    settings = Settings()                     # ¿cuántas veces construimos esto?
    engine = build_rag_engine(settings)       # pesado: se rehace en cada petición
    ...

@app.post("/ask")
def ask(payload: AskRequest):
    settings = Settings()
    engine = build_rag_engine(settings)       # otra vez
    ...

Esto tiene cuatro problemas concretos: duplicación, coste (construir el motor en cada petición es carísimo), acoplamiento (el endpoint conoce cómo se construye todo) y testabilidad cero (no puedes sustituir el motor por un falso).

La solución: declarar, no buscar

Una dependencia es simplemente una función (o una clase) que FastAPI ejecuta por ti antes de llamar a tu endpoint. Tú declaras el tipo del parámetro y añades Depends(...). FastAPI, al inspeccionar la firma, ve qué necesita el endpoint, ejecuta cada dependencia y le pasa el resultado.

  PETICIÓN HTTP
       │
       ▼
  ┌─────────────┐   valida path/query/body (Pydantic)
  │ Validación  │
  └──────┬──────┘
         ▼
  ┌───────────────────────────────────────────┐
  │ Resolución de DEPENDENCIAS (en orden)     │
  │   get_settings()  ─┐                      │
  │   get_rag_engine()─┼─► valores listos    │
  │   pagination()    ─┘                      │
  └──────┬────────────────────────────────────┘
         ▼
  ┌───────────────┐
  │  Tu endpoint  │  recibe los valores ya construidos
  └──────┬────────┘
         ▼
     RESPUESTA (serializada por Pydantic)

Analogía: un chef no sale al mercado antes de cada plato. La cocina (FastAPI) tiene un ayudante que ya dejó sobre la mesa la mise en place: las verduras cortadas, la salsa lista, el horno encendido. El chef (tu endpoint) solo cocina. Depends es el ayudante. El service locator sería un chef que cada vez abre la despensa él mismo con su propia llave, en medio del servicio.

El service locator y por qué lo evitamos

Un service locator es cualquier módulo global desde el que pides servicios a demanda:

# ❌ Service locator: importo un objeto global y lo uso por dentro
from app.container import container

@app.post("/ask")
def ask(payload: AskRequest):
    engine = container.rag_engine()   # ¿de dónde sale? acoplamiento oculto
    return engine.answer(payload.question)

Parece limpio, pero esconde el contrato. Mirando la firma de ask no sabes qué necesita: hay que leer el cuerpo entero para descubrir que usa un contenedor global. Además, en los tests ese contenedor ya está inicializado y no puedes cambiarlo sin trucos de monkeypatch.

Cómo se escribe: el estilo moderno con Annotated

La forma recomendada hoy usa typing.Annotated. El primer argumento es el tipo del valor y el segundo, la dependencia:

from typing import Annotated
from fastapi import Depends, FastAPI

app = FastAPI()

def get_user_agent() -> str:
    return "unknown"

@app.get("/ping")
def ping(user_agent: Annotated[str, Depends(get_user_agent)]):
    return {"user_agent": user_agent}

Fíjate en dos cosas importantes. Primero, no llames a la función: pasas get_user_agent, no get_user_agent(). FastAPI la llamará. Segundo, el estilo antiguo (que aún verás mucho) usa un valor por defecto:

# Estilo clásico, equivalente. Sigue siendo válido, pero Annotated es más claro
@app.get("/ping")
def ping(user_agent: str = Depends(get_user_agent)):
    return {"user_agent": user_agent}

Nota: con el estilo clásico, un parámetro con valor por defecto no puede ir antes de uno sin valor por defecto. Ese detalle de orden desaparece con Annotated, que es una de las razones por las que se prefiere. En este curso usamos Annotated siempre.

Dependencias reutilizables

Lo potente es que una dependencia no pertenece a un endpoint: es una pieza compartida. Escribes la paginación una vez y la usas en cuantos endpoints quieras:

from dataclasses import dataclass

@dataclass
class Pagination:
    skip: int
    limit: int

def pagination_params(skip: int = 0, limit: int = 20) -> Pagination:
    return Pagination(skip=skip, limit=limit)

Cada dependencia puede tener a su vez parámetros que se documentan solos. En /docs verás skip y limit como query params, sin que el endpoint sepa nada de ellos.

Caché por petición (la parte que casi nadie conoce)

Dentro de una misma petición, si varias dependencias necesitan la misma dependencia, FastAPI la ejecuta una sola vez y reutiliza el resultado. Esto es lo que permite que tres piezas compartan la misma sesión de base de datos sin abrir tres conexiones.

import uuid
from typing import Annotated
from fastapi import Depends

def get_case_id() -> str:
    return str(uuid.uuid4())          # se ejecuta una vez por petición

@app.get("/a")
def endpoint_a(case: Annotated[str, Depends(get_case_id)]):
    return {"case": case}

@app.get("/b")
def endpoint_b(
    case_a: Annotated[str, Depends(get_case_id)],
    case_b: Annotated[str, Depends(get_case_id)],
):
    # True: es el MISMO valor; FastAPI no vuelve a llamar a get_case_id
    return {"same": case_a == case_b}

Si por el contrario quieres forzar que se ejecute de nuevo, usa use_cache=False:

fresh_a: Annotated[str, Depends(get_case_id, use_cache=False)]
fresh_b: Annotated[str, Depends(get_case_id, use_cache=False)]
# Ahora fresh_a != fresh_b: se ejecutó dos veces en la misma petición

Truco mental: la caché de dependencias es por petición, no global. Termina la petición y se olvida todo. Por eso es seguro usar dependencias que devuelven objetos «de un solo uso» como una sesión de base de datos o un identificador de correlación.

Testabilidad: dependency_overrides

Como las dependencias se declaran en la firma, sustituirlas en un test es trivial. FastAPI guarda un diccionario público donde mapeas la función original a una falsa:

from fastapi.testclient import TestClient

class FakeRagEngine:
    def answer(self, question: str) -> str:
        return "respuesta de prueba"

def fake_rag_engine() -> FakeRagEngine:
    return FakeRagEngine()

app.dependency_overrides[get_rag_engine] = fake_rag_engine   # sustituye
client = TestClient(app)
assert client.post("/ask", json={"question": "hola"}).status_code == 200
app.dependency_overrides.clear()                             # limpia siempre

Cuidado: dependency_overrides es global al objeto app. Si no lo limpias entre tests, el override se filtra y un test posterior falla de forma misteriosa. Usa una fixture de pytest que lo restaure (lo verás en el módulo 6).

3 · Ejemplo mínimo

La dependencia más pequeña que aporta algo real: parámetros de paginación compartidos y un identificador de petición. Crea el archivo y ejecútalo con uv.

main.py
import uuid
from dataclasses import dataclass
from typing import Annotated

from fastapi import Depends, FastAPI

app = FastAPI()


@dataclass
class Pagination:
    skip: int
    limit: int


def pagination_params(skip: int = 0, limit: int = 20) -> Pagination:
    """Dependencia reutilizable: valida y agrupa los parámetros de paginación."""
    return Pagination(skip=skip, limit=limit)


def request_id() -> str:
    """Un id único por petición, útil para logs y trazas."""
    return str(uuid.uuid4())


@app.get("/modules")
def list_modules(
    page: Annotated[Pagination, Depends(pagination_params)],
    rid: Annotated[str, Depends(request_id)],
):
    # El endpoint no sabe NADA de query params ni de uuid: solo usa los valores
    return {"request_id": rid, "skip": page.skip, "limit": page.limit}

Arranca el servidor:

# uv sincroniza las dependencias del pyproject y arranca uvicorn con recarga
uv run uvicorn main:app --reload

Pruébalo sin complicarte con herramientas externas: abre http://127.0.0.1:8000/docs y verás que /modules expone automáticamente los query params skip y limit, aunque el endpoint nunca los declaró. El JSON de respuesta tiene esta forma:

{
  "request_id": "0f3b2c1a-9c4e-4f1e-8a2b-6d5c1b7e0a44",
  "skip": 0,
  "limit": 20
}

Qué ha pasado, paso a paso:

  1. FastAPI inspecciona la firma de list_modules y encuentra dos parámetros con Depends.
  2. Ejecuta pagination_params: como tiene query params propios, los valida (si mandas ?limit=abc devuelve 422).
  3. Ejecuta request_id: no recibe nada, devuelve un UUID nuevo.
  4. Llama a tu endpoint con page y rid ya construidos.
  5. Serializa el dict que devolviste a JSON.

4 · Ejemplo real

En el Copiloto API, el endpoint POST /ask necesita el motor de RAG. Ese motor es pesado (carga índices, abre conexiones): no queremos construirlo en cada petición. En la lección 3 verás cómo crearlo una sola vez con lifespan. Por ahora, la dependencia se limita a entregarlo desde un sitio controlado y permitir sustituirlo.

app/deps.py
from typing import Annotated

from fastapi import Depends, Request

from app.config import Settings, get_settings
from app.rag import RagEngine


def get_rag_engine(request: Request) -> RagEngine:
    """Devuelve el motor de RAG creado en el arranque (lifespan).

    No lo construimos aquí: solo leemos lo que ya vive en app.state.
    """
    return request.app.state.rag_engine


# Alias reutilizable: los endpoints declaran esto y quedan legibles
RagEngineDep = Annotated[RagEngine, Depends(get_rag_engine)]
SettingsDep = Annotated[Settings, Depends(get_settings)]
app/routers/ask.py
from fastapi import APIRouter
from pydantic import BaseModel, Field

from app.deps import RagEngineDep, SettingsDep

router = APIRouter(prefix="/ask", tags=["ask"])


class AskRequest(BaseModel):
    question: str = Field(min_length=1, max_length=2000)


class AskResponse(BaseModel):
    answer: str
    model: str


@router.post("", response_model=AskResponse)
def ask(
    payload: AskRequest,
    engine: RagEngineDep,
    settings: SettingsDep,
) -> AskResponse:
    # El endpoint solo expresa su intención; no construye nada
    answer = engine.answer(payload.question)
    return AskResponse(answer=answer, model=settings.rag_model)

Decisiones explicadas:

  • Alias de tipo (RagEngineDep): evitan repetir Annotated[RagEngine, Depends(get_rag_engine)] en cada endpoint. Es puro azúcar de tipos, sin coste en ejecución.
  • Acceso a request.app.state: es el puente entre el arranque (lección 3) y la petición. La dependencia no crea el motor, solo lo sirve.
  • La firma es el contrato: cualquiera que lea ask sabe que necesita un RagEngine y unos Settings. Nada oculto.
  • En test, sustituyes get_rag_engine por una versión falsa y pruebas el endpoint sin tocar el RAG real.

Y el test que aprovecha todo esto:

tests/test_ask.py
from fastapi.testclient import TestClient

from app.deps import get_rag_engine
from app.main import app


class FakeEngine:
    def answer(self, question: str) -> str:
        return f"eco: {question}"


def test_ask_uses_engine():
    app.dependency_overrides[get_rag_engine] = lambda: FakeEngine()
    try:
        client = TestClient(app)
        r = client.post("/ask", json={"question": "¿qué es FastAPI?"})
        assert r.status_code == 200
        assert r.json()["answer"] == "eco: ¿qué es FastAPI?"
    finally:
        app.dependency_overrides.clear()

Fíjate en el detalle clave: el test no arranca el RAG real, no necesita embeddings ni vectores, y aun así ejercita toda la cadena del endpoint. Eso es exactamente lo que el service locator te quitaba.

6 · Errores habituales

1. Llamar a la dependencia con paréntesis

❌ Incorrecto 
# Se ejecuta UNA VEZ al importar el módulo, no por petición.
# Además FastAPI recibe un RagEngine ya creado, no la dependencia.
@app.post("/ask")
def ask(engine: Annotated[RagEngine, Depends(build_rag_engine())]):
    ...
✅ Correcto 
@app.post("/ask")
def ask(engine: Annotated[RagEngine, Depends(get_rag_engine)]):
    ...

Con paréntesis rompes las tres ventajas: no hay caché por petición, no puedes hacer override en tests y el recurso se crea una sola vez al importar (posiblemente cuando aún no hay configuración disponible).

2. Recurso pesado dentro de la dependencia

❌ Incorrecto 
def get_rag_engine() -> RagEngine:
    # Cada petición vuelve a leer todos los vectores del disco: lentísimo
    return RagEngine.load("data/index.faiss")
✅ Correcto 
def get_rag_engine(request: Request) -> RagEngine:
    # Creado una vez en lifespan y guardado en app.state (lección 3)
    return request.app.state.rag_engine

3. Estado mutable global

❌ Incorrecto 
CACHE = {}   # compartido por TODAS las peticiones y todos los usuarios

def get_result() -> dict:
    CACHE["hits"] = CACHE.get("hits", 0) + 1   # condición de carrera
    return CACHE
✅ Correcto 
from dataclasses import dataclass, field

@dataclass
class RequestScope:
    # Estado por petición: aislado y sin carreras entre usuarios
    hits: dict[str, int] = field(default_factory=dict)

def request_scope() -> RequestScope:
    return RequestScope()

4. Dependencia que «devuelve» varias cosas sin estructura

❌ Incorrecto 
def get_context() -> tuple:
    return ("db", "user", 42)   # ¿qué es 42? nadie lo sabe al leer el endpoint

@app.get("/x")
def x(ctx: Annotated[tuple, Depends(get_context)]):
    _, _, magic = ctx
✅ Correcto 
@dataclass
class Context:
    db: str
    user: str
    tenant_id: int

def get_context() -> Context:
    return Context(db="main", user="ana", tenant_id=42)

@app.get("/x")
def x(ctx: Annotated[Context, Depends(get_context)]):
    return {"tenant": ctx.tenant_id}   # accesible por nombre, autodocumentado

5. Situar Depends detrás de un parámetro sin valor por defecto (estilo clásico)

❌ Incorrecto 
# SyntaxError: parámetro con default antes de uno sin default
def bad(engine: RagEngine = Depends(get_rag_engine), q: str = ...):
    ...
✅ Correcto 
# Con Annotated el orden deja de importar
def good(q: str, engine: Annotated[RagEngine, Depends(get_rag_engine)]):
    ...

7 · Ejercicio guiado

Objetivo: construir una dependencia reutilizable, comprobar la caché por petición y sustituirla en un test sin tocar el endpoint.

  1. Crea el proyecto mínimo: 
    uv init copiloto-deps
cd copiloto-deps
uv add fastapi "uvicorn[standard]"
  2. Escribe la dependencia y dos endpoints en main.py: 
    import uuid
from typing import Annotated

from fastapi import Depends, FastAPI, Header

app = FastAPI()
SLOW_INIT_COUNTER = {"n": 0}


def get_trace_id(x_trace_id: Annotated[str | None, Header()] = None) -> str:
    # Si el cliente manda la cabecera, la respetamos; si no, generamos una
    return x_trace_id or str(uuid.uuid4())


def get_tenant(x_trace_id: Annotated[str | None, Header()] = None) -> str:
    # Otra dependencia: se usa para demostrar que la base se comparte
    return "tenant-default"


@app.get("/one")
def one(trace: Annotated[str, Depends(get_trace_id)]):
    return {"trace": trace}


@app.get("/twice")
def twice(
    a: Annotated[str, Depends(get_trace_id)],
    b: Annotated[str, Depends(get_trace_id)],
):
    # Debe ser True: misma ejecución dentro de la petición
    return {"same": a == b, "trace": a}
  3. Arranca y comprueba la caché: 
    uv run uvicorn main:app --reload

# En otra terminal:
# /twice devuelve {"same": true, ...} porque FastAPI cachea por petición
# Prueba a mandar tu propia cabecera y verás que se respeta
curl -H "x-trace-id: mi-traza" http://127.0.0.1:8000/twice

    Resultado esperado: {"same":true,"trace":"mi-traza"}.

  4. Fuerza la no-caché cambiando twice: 
    @app.get("/twice")
def twice(
    a: Annotated[str, Depends(get_trace_id, use_cache=False)],
    b: Annotated[str, Depends(get_trace_id, use_cache=False)],
):
    return {"same": a == b}   # ahora suele ser False: se ejecutó dos veces
  5. Sustituye la dependencia en un test (guarda esto como test_main.py): 
    from fastapi.testclient import TestClient

from main import app, get_trace_id


def test_override_trace():
    app.dependency_overrides[get_trace_id] = lambda: "traza-fija"
    try:
        client = TestClient(app)
        r = client.get("/one")
        assert r.status_code == 200
        assert r.json() == {"trace": "traza-fija"}
    finally:
        app.dependency_overrides.clear()

    uv run pytest -q
# 1 passed
  6. Verificación final: abre /docs. El parámetro x-trace-id aparece como cabecera del endpoint aunque one nunca lo declaró. El contrato se documenta solo.

8 · Reto

🎯 Un motor de RAG inyectable y sustituible

Diseña la frontera de dependencias del Copiloto API para que POST /ask reciba un RagEngine sin construirlo por dentro. Debes lograr que:

  • El endpoint no importe nada de app.rag: solo un alias de tipo y Depends.
  • En producción la dependencia entregue el motor real (app.state.rag_engine, que crearás en la lección 3).
  • En tests, un solo dependency_overrides sustituya el motor por uno falso que devuelva respuestas deterministas.
  • Añade además una dependencia get_query_id y demuestra con un test que, si el endpoint la pide dos veces, obtiene el mismo valor.

Pista: define el alias RagEngineDep = Annotated[RagEngine, Depends(get_rag_engine)] en app/deps.py y usa from __future__ import annotations solo si de verdad lo necesitas; el alias ya evita repetir tipos. Para la caché, recuerda que es por petición, no global: no necesitas ningún @lru_cache.

9 · Resumen

  • Depends implementa inyección de dependencias: el endpoint declara lo que necesita y FastAPI se lo entrega.
  • Reemplaza al service locator porque hace explícito el contrato en la firma y elimina el acoplamiento oculto.
  • Se escribe con Annotated[T, Depends(f)]; pasa la función sin paréntesis.
  • Las dependencias son reutilizables: paginación, trazas, configuración, motores… se declaran una vez.
  • La caché es por petición: la misma dependencia se ejecuta una vez; desactívala con use_cache=False.
  • Los tests sustituyen dependencias con app.dependency_overrides, y hay que limpiarlos siempre.

10 · Preguntas frecuentes

¿Depends sirve solo para operaciones de base de datos?

No. Sirve para cualquier cosa que puedas expresar como una función: parámetros compartidos, autenticación, cabeceras, clientes HTTP, feature flags, configuración, permission checks. La regla práctica es: si el mismo bloque de preparación aparece en dos endpoints, conviértelo en dependencia.

¿Cuál es la diferencia real entre Depends y una función normal que yo llamo?

Si la llamas tú, pierdes tres beneficios que da FastAPI: la caché por petición (executas de nuevo), la posibilidad de hacer dependency_overrides en tests y la integración con la validación y la documentación (los parámetros de la dependencia aparecen en /docs). Además, como dependencia puedes declarar que recibe path/query/header/body y FastAPI los valida.

Si la caché es por petición, ¿cómo comparto algo entre peticiones?

Con @lru_cache para objetos de configuración inmutables, o con recursos de arranque guardados en app.state desde lifespan (lecciones 3 y 4). Lo que nunca debes compartir es estado mutable que dependa del usuario: eso vive por petición o en la base de datos.

¿Las dependencias pueden recibir a su vez otras dependencias?

Sí, y es una de las ideas más útiles: las sub-dependencias. Una dependencia puede declarar sus propias dependencias y FastAPI construye el árbol completo en orden. Es el tema de la siguiente lección.

¿Por qué mi Depends se ejecuta aunque el endpoint no lo use?

Porque FastAPI resuelve todas las dependencias declaradas en la firma antes de entrar al endpoint, aunque en el cuerpo no las toques. Si el coste te preocupa, no la declares; las dependencias son contratos, no sugerencias. Los recursos pesados se resuelven una sola vez con lifespan, así que declararlas de más rara vez cuesta caro.
