TestClient y pytest

Módulo 6 · Testing y calidad 🕐 35 minutos

1 · Introducción

Ya tienes una API que valida, responde con modelos, gestiona errores con Problem Details y persiste en una base de datos. Funciona hoy. Pero cada vez que tocas una ruta, un modelo o una dependencia, ¿cómo sabes que no has roto algo que funcionaba? La respuesta profesional es tests automatizados: código que llama a tu API y comprueba que se comporta como esperas, en cada cambio, en cada commit.

El problema: probar una API «a mano» (abrir /docs, pulsar Try it out, mirar el resultado) no escala. Es lento, no es repetible y, sobre todo, no queda registrado. Un test es una especificación ejecutable: describe una expectativa concreta y la verifica sin intervención humana.

¿Por qué existe esta lección? Porque FastAPI trae TestClient, que ejecuta tu aplicación ASGI en el mismo proceso, sin abrir un puerto ni levantar uvicorn. Combinado con pytest, escribir tests de endpoints pasa de ser una tarea pesada a ser algo casi trivial, y eso es lo que hace que de verdad se escriban.

Errores típicos que verás en proyectos reales y que evitamos desde el principio: tests que dependen de una base de datos real (frágiles y lentos), comprobar solo que el código sea 200 sin mirar el cuerpo, y compartir estado entre tests de forma que pasen o fallen según el orden de ejecución.

2 · Teoría

La pirámide de tests

No todos los tests cuestan lo mismo. Cuanto más abajo en la pirámide, más rápidos y numerosos; cuanto más arriba, más realistas pero más lentos y frágiles. Este módulo se centra en la franja intermedia: tests que ejercitan una petición HTTP completa contra tu app, sin llegar a la red.

                      ▲  más lento, más real
                     ╱ ╲      E2E (navegador, servicio externo)
                    ╱───╲     Integración (API + BD real)
                   ╱─────╲    ◀── aquí: TestClient / httpx  (este módulo)
                  ╱───────╲   Unitarios (una función, un validador)
                 ╱_________╲  más rápido, más numeroso

TestClient: tu app sin red

TestClient es un cliente HTTP construido sobre httpx que, en lugar de conectarse por TCP a un servidor, llama directamente al objeto ASGI (app) en memoria. Esto significa que no necesitas uvicorn ni abrir un puerto: cada petición del test recorre el mismo camino que una petición real (middleware, dependencias, validación, ruta) y te devuelve un objeto de respuesta con status_code, json(), headers…

   TEST                          │   PRODUCCIÓN
   ──────────────────────────────┼──────────────────────────────
   client.get("/modules")        │   GET /modules HTTP/1.1
         │                       │         │
         ▼                       │         ▼
   ┌───────────────┐             │   ┌───────────────┐
   │   TestClient  │  en proceso │   │    uvicorn    │  red
   │  (httpx ASGI) │──────┐      │   │  + TCP :8000  │
   └───────────────┘      ▼      │   └───────┬───────┘
                      ┌────────┐ │           ▼
                      │  app   │ │      ┌────────┐
                      │ (ASGI) │ │      │  app   │
                      └────────┘ │      └────────┘

Analogía: probar con TestClient es como ensayar una obra en el propio escenario, con los actores y el guion reales, pero sin público ni taquilla. El montaje es el definitivo; lo único que te ahorras es el transporte.

Lifespan: el detalle que casi todos olvidan

Tu app abre recursos en lifespan (Módulo 3, lección 3): el motor de base de datos, clientes HTTP… Si creas client = TestClient(app) y haces peticiones, ese arranque no se ejecuta. Para que sí lo haga, usa TestClient como gestor de contexto:

with TestClient(app) as client:   # dispara lifespan.startup ...
    client.get("/health")
# ... y al salir del bloque, dispara lifespan.shutdown

Ojo: fuera del bloque with, el evento de startup no se ejecuta. Si tu app depende de él para crear la base de datos o preparar estado, tus tests fallarán con errores confusos («no such table», AttributeError sobre un recurso None). Cuando el ciclo de vida importa, usa siempre el with.

pytest: el runner estándar

pytest descubre y ejecuta los tests siguiendo tres reglas sencillas: busca archivos test_*.py (o *_test.py), dentro encuentra funciones test_*, y cada una es un test. Basta un assert de Python: pytest reescribe la expresión y, si falla, te muestra los valores reales en lugar de un críptico AssertionError.

Pieza de pytestQué es
assertLa aserción. Nada de assertEqual: Python puro, con introspección automática
@pytest.fixturePrepara un recurso (cliente, base de datos) y lo entrega al test por nombre de parámetro
conftest.pyArchivo donde viven las fixtures compartidas; pytest lo descubre sin importarlo
@pytest.mark.parametrizeEjecuta el mismo test con varios juegos de datos
pytest.raisesComprueba que un bloque lanza la excepción esperada

Fixtures: preparar el mundo antes del test

Una fixture es una función que devuelve (o cede) algo que el test necesita. pytest la inyecta por el nombre del parámetro. Es el mismo concepto que Depends en FastAPI, pero aplicado al mundo de los tests: inversión de control para montar el escenario.

import pytest


@pytest.fixture
def module_payload() -> dict[str, str]:
    return {"slug": "fastapi", "title": "FastAPI"}

def test_create_module(client, module_payload):
    response = client.post("/modules", json=module_payload)
    assert response.status_code == 201

module_payload se pide por nombre; client llegará de una fixture definida en conftest.py. El scope controla cuántas veces se ejecuta: function (por defecto, una vez por test), module, session…

El objeto de respuesta

Cada llamada a client.get/post/… devuelve un httpx.Response. Sus propiedades son las que usarás en los assert:

Atributo / métodoQué contiene
response.status_codeEl código HTTP, p. ej. 200, 201, 404
response.json()El cuerpo decodificado como JSON (dict o list)
response.textEl cuerpo como cadena, tal cual llegó
response.headersLas cabeceras de la respuesta (content-type, location…)
response.raise_for_status()Lanza excepción si el código es 4xx o 5xx

Un test bien escrito sigue given / when / then: prepara el estado, ejecuta una acción y comprueba una cosa. Si un test comprueba cinco cosas a la vez, cuando falle no sabrás cuál se rompió.

3 · Ejemplo mínimo

La app más pequeña posible y su test. Primero, el proyecto:

consola
uv init copiloto-tests --python 3.12
cd copiloto-tests
uv add fastapi
uv add --dev pytest httpx

httpx es necesario porque TestClient se apoya en él. Ahora la aplicación:

app/main.py
from fastapi import FastAPI

app = FastAPI(title="Copiloto API")


@app.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok"}

Y el test:

tests/test_health.py
from fastapi.testclient import TestClient

from app.main import app

client = TestClient(app)


def test_health_returns_ok():
    response = client.get("/health")

    assert response.status_code == 200
    assert response.json() == {"status": "ok"}

Ejecútalo:

consola
uv run pytest -q

.                                                                    [100%]
1 passed in 0.03s

Línea por línea:

  1. from fastapi.testclient import TestClient: importa el cliente. Está disponible sin instalar nada extra porque FastAPI ya depende de Starlette, que lo construye sobre httpx.
  2. from app.main import app: importa tu objeto ASGI. El test no arranca uvicorn: llama a app directamente.
  3. client = TestClient(app): crea el cliente. Para este ejemplo no necesitamos lifespan, así que no usamos with; en la sección 4 sí.
  4. client.get("/health"): simula la petición. Recorre validación, dependencias y la función de la ruta, y devuelve la respuesta.
  5. response.status_code == 200: comprueba el contrato HTTP. Si un cambio futuro devuelve 404, el test te lo dice al instante.
  6. response.json() == {"status": "ok"}: comprueba el cuerpo. Es una comparación de diccionarios completa: el orden de las claves no importa, pero sí el contenido.

El test se llama test_health_returns_ok: nombre en inglés (convención del código, según las reglas del curso), pero el contenido y los mensajes pueden ir en español. Un buen nombre de test describe el comportamiento esperado, no el método que llama.

4 · Ejemplo real

Pasemos a Copiloto API. Vamos a testear tres endpoints: GET /health, GET /modules (que lee de la base de datos) y POST /ask (que valida la entrada y delega en el «motor» RAG). La pieza central es una fixture compartida que monta el cliente con el lifespan ya arrancado y sustituye el motor por un fake.

app/deps.py
from collections.abc import Iterator

from fastapi import Depends
from sqlmodel import Session

from app.db import get_session
from app.models import Module, QueryLog


class RagEngine:
    """Envoltura del motor de RAG del Copiloto. La sustituimos en los tests."""

    def answer(self, question: str) -> str:
        raise NotImplementedError


def get_rag_engine() -> RagEngine:
    return RagEngine()


def get_modules(session: Session = Depends(get_session)) -> list[Module]:
    from sqlmodel import select

    return list(session.exec(select(Module)).all())

El archivo estrella es conftest.py: aquí definimos las fixtures que todos los tests comparten. pytest lo carga automáticamente, sin importarlo.

tests/conftest.py
from collections.abc import Iterator

import pytest
from fastapi.testclient import TestClient

from app.deps import get_rag_engine
from app.main import app


class FakeRagEngine:
    """Respuestas deterministas: los tests no dependen de un LLM real."""

    def answer(self, question: str) -> str:
        return f"Respuesta simulada para: {question}"


@pytest.fixture
def client() -> Iterator[TestClient]:
    """Cliente con el motor RAG sustituido por un doble."""
    app.dependency_overrides[get_rag_engine] = FakeRagEngine
    with TestClient(app) as test_client:      # el with dispara el lifespan
        yield test_client
    app.dependency_overrides.clear()          # limpia siempre, pase lo que pase

La fixture usa yield: todo lo que va antes entrega el recurso, y lo que va después es la limpieza. Aunque el test falle, pytest ejecuta el código posterior al yield. Es la misma idea que la dependencia get_session con yield que ya conoces (Módulo 3, lección 2).

Con eso, los tests de comportamiento quedan cortos y legibles:

tests/test_api.py
import pytest
from fastapi.testclient import TestClient


def test_health(client: TestClient) -> None:
    response = client.get("/health")

    assert response.status_code == 200
    assert response.json()["status"] == "ok"


def test_modules_lists_seeded_modules(client: TestClient) -> None:
    response = client.get("/modules")

    assert response.status_code == 200
    slugs = [module["slug"] for module in response.json()]
    assert "fastapi" in slugs


def test_ask_returns_answer(client: TestClient) -> None:
    response = client.post("/ask", json={"question": "¿Qué es Depends?"})

    assert response.status_code == 200
    assert "Depends" in response.json()["answer"]


@pytest.mark.parametrize(
    ("payload", "expected_status"),
    [
        ({"question": "ok"}, 200),
        ({"question": ""}, 422),          # pregunta vacía: falla la validación
        ({}, 422),                        # falta el campo obligatorio
        ({"question": "ok", "extra": 1}, 200),  # campo extra: se ignora
    ],
)
def test_ask_validation(client: TestClient, payload: dict, expected_status: int) -> None:
    response = client.post("/ask", json=payload)

    assert response.status_code == expected_status

Decisiones y porqués:

  • Una fixture client, no un cliente global. Cada test recibe un cliente limpio y con el lifespan arrancado. Evita el estado compartido entre tests, la causa número uno de tests flaky.
  • dependency_overrides en la fixture, no en cada test. El «motor RAG» real hace red (y costaría dinero); el fake devuelve algo determinista. La lógica de sustitución vive en un solo sitio. A fondo en la lección 3.
  • app.dependency_overrides.clear() tras el yield. Sin esta limpieza, una sustitución se «filtra» al siguiente test y produces falsos verdes imposibles de explicar.
  • La aserción mira el cuerpo, no solo el código. Un 200 con un JSON vacío sigue siendo un bug. Comprobar slugs o answer es lo que de verdad protege la funcionalidad.
  • @pytest.mark.parametrize: cuatro casos de validación en un solo test. Los casos de error (422) son tan parte del contrato como el caso feliz.

Fíjate en la forma del error 422: es el formato de validación de Pydantic que ya viste en el Módulo 1. Si un día cambia, estos tests lo detectan al momento. Ahí está el valor: los tests fijan el contrato que el resto del mundo consume.

5 · Buenas prácticas

6 · Errores habituales

Comprobar solo el código de estado

✗ Incorrecto
def test_ask():
    response = client.post("/ask", json={"question": "¿Qué es Depends?"})
    assert response.status_code == 200      # ¿y si el answer viene vacío?
✓ Correcto
def test_ask():
    response = client.post("/ask", json={"question": "¿Qué es Depends?"})
    assert response.status_code == 200
    assert "Depends" in response.json()["answer"]

El código de estado dice «la petición llegó y se procesó»; el cuerpo dice «se procesó bien». Un endpoint que siempre devuelve 200 con un cuerpo vacío pasaría el test incorrecto sin despeinarse.

Usar la app con red en lugar de TestClient

✗ Incorrecto
import httpx

def test_health():
    # Requiere uvicorn corriendo en localhost:8000 y hace I/O real de red
    response = httpx.get("http://localhost:8000/health")
    assert response.status_code == 200
✓ Correcto
from fastapi.testclient import TestClient

from app.main import app

def test_health():
    response = TestClient(app).get("/health")
    assert response.status_code == 200

El primer test solo pasa si has levantado el servidor a mano antes: no es reproducible en CI, y cualquier fallo de red lo vuelve intermitente. TestClient llama a la app en proceso, sin puerto ni red.

Olvidar la limpieza de dependency_overrides

✗ Incorrecto
client = TestClient(app)
app.dependency_overrides[get_rag_engine] = FakeRagEngine   # ¡a nivel de módulo!

def test_a(): ...

def test_b():
    ...   # sigue usando el fake aunque no lo quiera
✓ Correcto
@pytest.fixture
def client():
    app.dependency_overrides[get_rag_engine] = FakeRagEngine
    with TestClient(app) as test_client:
        yield test_client
    app.dependency_overrides.clear()

Dejar la sustitución «puesta» contamina todos los tests siguientes, que dejan de probar lo que creen probar. La limpieza va en la fixture, garantizada incluso si el test falla.

Un cliente global compartido con estado

✗ Incorrecto
client = TestClient(app)   # de módulo

def test_create():
    client.post("/modules", json={"slug": "x", "title": "X"})

def test_count():
    # Asume que el test anterior creó un módulo: depende del orden
    assert len(client.get("/modules").json()) == 1
✓ Correcto
def test_count(client):
    # El test prepara su propio estado; no hereda nada del vecino
    seed_modules(client, n=1)
    assert len(client.get("/modules").json()) == 1

Un test debe poder ejecutarse solo, con pytest tests/test_count.py, y dar el mismo resultado. Si depende del orden, tarde o temprano fallará en CI por una razón que no tiene nada que ver con tu cambio.

7 · Ejercicio guiado

Objetivo: montar desde cero la infraestructura de tests de Copiloto API y cubrir GET /health, GET /modules y POST /ask, incluidos los casos de validación.

  1. Paso 1 — Instala las dependencias de desarrollo. 
    uv add --dev pytest httpx

    Resultado esperado: pytest y httpx aparecen en el grupo dev-dependencies de pyproject.toml. httpx es la base de TestClient.

  2. Paso 2 — Configura pytest. Añade a pyproject.toml: 
    [tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q"

    Con testpaths, uv run pytest busca solo en tests/. Resultado esperado: al ejecutarlo sin tests aún, verás no tests ran, no un error de descubrimiento.

  3. Paso 3 — Crea la fixture client. Copia el tests/conftest.py de la sección 4. Comprueba que importa app.dependency_overrides y limpia después del yield.
  4. Paso 4 — Escribe los tres tests felices. En tests/test_api.py, añade test_health, test_modules_lists_seeded_modules y test_ask_returns_answer.

    test_modules_lists_seeded_modules asume que hay un módulo con slug="fastapi". Si tu base de datos de test está vacía, el test fallará. En la lección 3 resolvemos esto bien (base de datos temporal por test); por ahora, asegúrate de sembrar los datos en una fixture o de comprobar solo el tipo de la respuesta.

  5. Paso 5 — Añade los casos de validación. Copia el test parametrizado test_ask_validation. Ejecuta: 
    uv run pytest -q

    Resultado esperado: verás los cuatro casos del parametrize contabilizados como tests distintos:

    .....
5 passed in 0.21s
  6. Paso 6 — Rompe el contrato a propósito. Cambia en app/main.py el status_code del endpoint de creación (o el cuerpo de /health) y vuelve a lanzar los tests. Deben fallar con un mensaje que apunte al valor esperado frente al obtenido. Ese es el mecanismo que te protegerá en el futuro. 
    E   assert 200 == 201
  7. Paso 7 — Revisa el informe. Ejecuta con más detalle para ver el nombre de cada caso parametrizado: 
    uv run pytest -v

    Resultado esperado: una línea por caso, con los parámetros entre corchetes, p. ej. test_ask_validation[payload1-422]. Esa granularidad es la que hace que un fallo en CI sea fácil de diagnosticar.

8 · Reto

🎯 El contrato de los códigos de estado

Escribe un test parametrizado que recorra todos los endpoints de Copiloto API y afirme que, para entradas válidas, el código es el documentado (por ejemplo 200 en lecturas y 201 en creación) y el content-type es application/json. Después añade el caso inverso: para cada endpoint, una entrada inválida (falta un campo, tipo equivocado) debe devolver 422 y un cuerpo con la clave detail.

Pista: define una lista de tuplas (method, path, payload) y usa @pytest.mark.parametrize sobre ella. Para comprobar el content-type, mira response.headers["content-type"], que incluirá el sufijo del charset; usa startswith en lugar de igualdad. Piensa qué hacer con los endpoints protegidos por JWT: ¿los incluyes con un token válido o los dejas para la lección de seguridad?

9 · Resumen

  • TestClient ejecuta tu app ASGI en proceso, sin uvicorn ni red; está construido sobre httpx.
  • Usa with TestClient(app) as client cuando el lifespan importe: fuera del with no se ejecuta el startup.
  • pytest descubre test_*.py y funciones test_*; un assert basta.
  • Las fixtures (en conftest.py) preparan el cliente y los datos, y limpian tras el yield.
  • Comprueba código de estado y cuerpo; testea también los casos de error (422, 404, 401).
  • dependency_overrides sustituye dependencias reales por dobles; límpialo siempre al terminar.
  • Un test debe ser independiente del orden: prepara su propio estado.

10 · Preguntas frecuentes

¿TestClient levanta un servidor de verdad?

No. TestClient llama al objeto ASGI app directamente, en el mismo proceso donde corre pytest. No hay socket, ni puerto, ni uvicorn. Por eso los tests son rapidísimos: medidos en milisegundos, no en segundos.

¿Por qué necesito instalar httpx si uso TestClient?

Porque TestClient es un cliente httpx adaptado (con un transport ASGI en lugar de uno de red). Starlette lo trae, pero la dependencia de httpx debe estar disponible en tu entorno de desarrollo. En la lección 2 usamos httpx directamente.

¿Tengo que testear cada endpoint con cada combinación de datos?

No hace falta una combinatoria exhaustiva. Céntrate en: el camino feliz, los límites (vacío, máximo, tipos límite) y los errores esperados. La validación detallada de tipos ya la cubre Pydantic con sus propios tests; tú pruebas el comportamiento de tu API.

¿Los tests van en el mismo repositorio?

Sí, en una carpeta tests/ hermana de app/. Los tests son parte del código: se versionan, se revisan en los pull requests y se ejecutan en CI. Un test que no está en el repositorio, para el equipo, no existe.

¿Qué diferencia hay entre un fake, un stub y un mock?

Los tres son «dobles» de test. Un stub devuelve respuestas fijas; un fake tiene una implementación simplificada pero funcional (como nuestro FakeRagEngine); un mock registra cómo se le llamó y permite verificarlo. Para APIs, un fake sencillo suele ser más claro y robusto que un mock lleno de expectativas.
