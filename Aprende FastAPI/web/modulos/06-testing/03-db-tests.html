Tests con base de datos

Módulo 6 · Testing y calidad 🕐 35 minutos

1 · Introducción

Copiloto API guarda un histórico de consultas en SQLite (Módulo 4). Un test que ejercita POST /ask de verdad tiene que escribir en una base de datos: no basta con doblar el repositorio, porque entonces no estás probando la consulta SQL, ni la transacción, ni el mapeo de SQLModel. Necesitas una base de datos real… pero que no sea la tuya.

El problema tiene dos caras. Primero, aislamiento: cada test debe empezar con un estado conocido, sin heredar filas del test anterior. Segundo, rapidez y seguridad: jamás debes apuntar los tests a la base de datos de desarrollo —un DROP TABLE se lleva tus datos— ni a una compartida, donde los tests pisan entre sí.

¿Por qué existe esta lección? Porque aquí se une todo lo aprendido: la sesión con yield (Módulo 3), SQLModel y transacciones (Módulo 4), el patrón repositorio (Módulo 4) y dependency_overrides (lecciones 1 y 2). La pieza nueva es dónde vive esa base de datos y cómo se limpia entre tests.

Errores típicos que veremos: usar sqlite:// sin StaticPool y recibir un «no such table» desconcertante; dejar un fichero test.db por el repositorio que ensucia las ejecuciones; y olvidar limpiar la sustitución de get_session, con el que la app acaba escribiendo en la base de datos equivocada.

2 · Teoría

Qué base de datos usar en los tests

SQLite es ideal para tests: no requiere servidor, se crea en un instante y SQLAlchemy lo trata igual que a PostgreSQL. Hay dos sabores:

VarianteURLVentajasInconvenientes
En memoriasqlite:// Instantánea; desaparece al cerrar; cero ficheros Hay que forzar una sola conexión (StaticPool)
Fichero temporalsqlite:///{tmp_path}/test.db Comportamiento real de fichero; inspeccionable Más lento; hay que borrarlo (pytest lo hace con tmp_path)

Nunca uses la URL real (sqlite:///copiloto.db o tu PostgreSQL de desarrollo) en los tests. Si un test borra o modifica filas, estás destruyendo tus propios datos. La regla es tajante: entorno de test, base de datos de test.

El detalle que rompe a todo el mundo: StaticPool

Una base de datos SQLite en memoria vive dentro de la conexión. Si el pool abre una conexión nueva para el segundo uso, esa conexión ve otra base de datos… vacía. Por eso, cuando ves «no such table: modules» en un test que acaba de crear las tablas, casi siempre es esto.

   create_engine("sqlite://")                      sin StaticPool
   ├── conexión A → crea tablas, inserta filas   (su propia BD en memoria)
   └── conexión B → ¿tablas? NO EXISTEN          ← "no such table"

   create_engine("sqlite://", poolclass=StaticPool)   con StaticPool
   └── UNA sola conexión compartida → todos ven la misma BD en memoria  ✔

StaticPool obliga al motor a reutilizar siempre la misma conexión. Es exactamente lo que quieres para una base de datos en memoria durante un test. Añade además check_same_thread=False, porque TestClient ejecuta la app en otro hilo y SQLite es estricto con el hilo de la conexión.

tests/conftest.py (motor de test)
from sqlmodel import SQLModel, create_engine
from sqlalchemy.pool import StaticPool

engine = create_engine(
    "sqlite://",
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,
)
SQLModel.metadata.create_all(engine)

dependency_overrides: apuntar la app a la base de datos de test

La app no debe saber que está en un test. No cambies app/db.py; sustituye la dependencia get_session para que entregue una sesión de la base de datos de test:

   ENDPOINT  ──► Depends(get_session)
                      │
             dependency_overrides
                      ▼
        get_test_session()  →  Session(test_engine)  →  SQLite en memoria
tests/conftest.py (sustitución)
from collections.abc import Iterator

from fastapi.testclient import TestClient
from sqlmodel import Session

from app.db import get_session
from app.main import app


def get_test_session() -> Iterator[Session]:
    with Session(engine) as session:
        yield session


app.dependency_overrides[get_session] = get_test_session

El endpoint reutiliza su código de siempre; solo cambia de quién recibe la sesión. Esa indirección la preparaste en el módulo de repositorios, y ahora es la que te da tests sin trucos.

Aislamiento: dos estrategias

Con la base de datos en memoria ya tienes donde escribir. Falta que cada test empiece limpio. Hay dos caminos, y conviene conocer ambos:

Estrategia A — recrear el esquema por test. Una fixture de scope función que hace drop_all y create_all antes de cada test, o simplemente crea un motor nuevo en memoria. Simple, robusto y del todo suficiente para APIs de tamaño medio.

Estrategia B — transacción externa con rollback. Abres una transacción al principio del test y haces rollback al final: cada test escribe «de verdad», pero nada se guarda de forma permanente. Más rápido, a cambio de un poco más de ceremonia.

✓ Estrategia B — rollback por test (SQLAlchemy 2.0)
from collections.abc import Iterator

import pytest
from sqlalchemy.engine import Engine
from sqlmodel import Session


@pytest.fixture
def session(engine: Engine) -> Iterator[Session]:
    """Bindea la sesión a una transacción externa y la revierte al final."""
    connection = engine.connect()
    transaction = connection.begin()
    session = Session(bind=connection, join_transaction_mode="create_savepoint")
    try:
        yield session
    finally:
        session.close()
        transaction.rollback()      # se descarta todo lo escrito por el test
        connection.close()

join_transaction_mode="create_savepoint" hace que, cuando tu código llame a session.commit(), SQLAlchemy use un SAVEPOINT en lugar de cerrar la transacción externa. Así el commit de la app funciona «como siempre» para el test, pero el rollback final lo deshace todo. Sin este parámetro, el primer commit cerraría la transacción y el aislamiento se perdería.

¿Cuál elijo? Empieza con la estrategia A (recrear el esquema). Pásate a la B cuando la suite crezca y el coste de crear tablas se note. En este curso verás la B en el proyecto final porque demuestra el aislamiento más fino. También verás la variante «fichero con tmp_path» cuando necesites comprobar algo específico del sistema de ficheros.

Si tu sesión es async

Todo lo anterior tiene gemelo con AsyncSession y create_async_engine("sqlite+aiosqlite://"). En ese caso las fixtures son async (lección 2) y el override entrega un AsyncSession. El concepto no cambia: motor de test, sesión de test, dependencia sustituida, limpieza garantizada.

3 · Ejemplo mínimo

Una app con un endpoint que escribe y otro que lee, y un test que comprueba el ciclo completo contra SQLite en memoria.

app/main.py
from collections.abc import Iterator

from fastapi import Depends, FastAPI
from sqlmodel import Field, Session, SQLModel, create_engine, select

app = FastAPI(title="Copiloto API")
engine = create_engine("sqlite:///copiloto.db")   # la URL que sustituirá el test


class Module(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    slug: str


def get_session() -> Iterator[Session]:
    with Session(engine) as session:
        yield session


@app.post("/modules", status_code=201)
def create_module(slug: str, session: Session = Depends(get_session)) -> dict:
    module = Module(slug=slug)
    session.add(module)
    session.commit()
    session.refresh(module)
    return {"id": module.id, "slug": module.slug}


@app.get("/modules")
def list_modules(session: Session = Depends(get_session)) -> list[dict]:
    rows = session.exec(select(Module)).all()
    return [{"slug": row.slug} for row in rows]
tests/test_db_min.py
from collections.abc import Iterator

from fastapi.testclient import TestClient
from sqlalchemy.pool import StaticPool
from sqlmodel import Session, SQLModel, create_engine

from app.main import Module, app, get_session

# 1) Motor de test: en memoria, una sola conexión, compartida entre hilos.
test_engine = create_engine(
    "sqlite://",
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,
)
SQLModel.metadata.create_all(test_engine)


def get_test_session() -> Iterator[Session]:
    with Session(test_engine) as session:
        yield session


# 2) La app usa la base de datos de test.
app.dependency_overrides[get_session] = get_test_session
client = TestClient(app)


def test_create_and_list_module() -> None:
    created = client.post("/modules", params={"slug": "fastapi"})
    assert created.status_code == 201

    listed = client.get("/modules")
    assert listed.status_code == 200
    assert listed.json() == [{"slug": "fastapi"}]

Ejecútalo y verás el ciclo completo (INSERT + SELECT) sobre una base de datos que no existe en disco:

consola
uv add --dev pytest httpx
uv run pytest -q

.                                                                    [100%]
1 passed in 0.06s

Línea por línea:

  1. "sqlite://": tres barras tras sqlite: apuntan a un fichero; con dos barras y nada detrás, es memoria. El test no deja rastro en disco.
  2. poolclass=StaticPool: imprescindible. Sin él, la segunda conexión vería una base de datos vacía y el test fallaría con «no such table: module».
  3. SQLModel.metadata.create_all(test_engine): crea las tablas en el motor de test. Recuerda que los modelos deben estar importados; aquí importamos Module desde app.main.
  4. get_test_session: el mismo contrato que get_session (una sesión con yield), pero apuntando al motor de test.
  5. app.dependency_overrides[get_session] = get_test_session: la app deja de usar su motor real. El endpoint no cambia ni una línea.
  6. client.post(...) y client.get(...): dos peticiones reales que pasan por la ruta, la dependencia y SQLModel.

Este ejemplo mínimo sustituye la dependencia a nivel de módulo, sin limpiar. Funciona para un único archivo de test, pero en una suite real conviene hacerlo en una fixture con limpieza (como en la lección 1) o, mejor, con aislamiento por test (sección 4). Lo mostramos así a propósito, para que veas el mecanismo desnudo.

4 · Ejemplo real

En Copiloto API combinamos las dos piezas: la sustitución de get_session y el aislamiento por transacción. El resultado es una suite donde cada test ve una base de datos «como nueva» y donde nada se filtra de un test a otro.

tests/conftest.py
from collections.abc import Iterator

import pytest
from fastapi.testclient import TestClient
from sqlalchemy.engine import Engine
from sqlalchemy.pool import StaticPool
from sqlmodel import Session, SQLModel, create_engine

from app.db import get_session
from app.deps import get_rag_engine
from app.main import app
from app.models import Module  # noqa: F401  (importar para registrar la tabla)


@pytest.fixture(scope="session")
def engine() -> Iterator[Engine]:
    """Un único motor en memoria para toda la sesión de tests."""
    test_engine = create_engine(
        "sqlite://",
        connect_args={"check_same_thread": False},
        poolclass=StaticPool,
    )
    SQLModel.metadata.create_all(test_engine)
    yield test_engine


@pytest.fixture
def session(engine: Engine) -> Iterator[Session]:
    """Sesión envuelta en una transacción que se revierte al terminar el test."""
    connection = engine.connect()
    transaction = connection.begin()
    test_session = Session(bind=connection, join_transaction_mode="create_savepoint")
    try:
        yield test_session
    finally:
        test_session.close()
        transaction.rollback()
        connection.close()


@pytest.fixture
def client(session: Session) -> Iterator[TestClient]:
    """Cliente cuya app usa LA sesión del test (con su transacción)."""

    def override_get_session() -> Iterator[Session]:
        yield session

    app.dependency_overrides[get_session] = override_get_session
    app.dependency_overrides[get_rag_engine] = FakeRagEngine
    with TestClient(app) as test_client:
        yield test_client
    app.dependency_overrides.clear()


class FakeRagEngine:
    async def answer(self, question: str) -> str:
        return f"Respuesta simulada para: {question}"

Ahora los tests pueden sembrar datos con su propia sesión y consultarlos vía API, con la certeza de que nada sobrevive al test:

tests/test_query_log.py
from fastapi.testclient import TestClient
from sqlmodel import Session, select

from app.models import Module, QueryLog


def test_ask_persists_query_log(client: TestClient, session: Session) -> None:
    response = client.post("/ask", json={"question": "¿Qué es Depends?"})
    assert response.status_code == 200

    # El endpoint escribió en la MISMA sesión que el test:
    logs = session.exec(select(QueryLog)).all()
    assert len(logs) == 1
    assert logs[0].question == "¿Qué es Depends?"


def test_modules_reflects_seeded_rows(client: TestClient, session: Session) -> None:
    session.add(Module(slug="fastapi", title="FastAPI"))
    session.commit()          # SAVEPOINT: no cierra la transacción externa

    response = client.get("/modules")

    assert response.status_code == 200
    assert [m["slug"] for m in response.json()] == ["fastapi"]


def test_each_test_starts_clean(client: TestClient) -> None:
    # Ningún test anterior dejó filas: la transacción se revirtió.
    response = client.get("/modules")
    assert response.json() == []

Decisiones y porqués:

  • Motor de scope="session": se crea una vez y se reutiliza. Lo caro (crear el motor y las tablas) se paga una sola vez; el aislamiento lo aporta la transacción, no el motor.
  • La fixture session es el corazón de la estrategia B. El test comparte sesión con la app: puede sembrar filas y ver lo que la API ha escrito, porque ambas están en la misma transacción y la misma conexión.
  • El override devuelve esa sesión concreta (yield session), no una nueva. Es lo que permite que el test y el endpoint compartan estado dentro del test… y solo dentro del test.
  • transaction.rollback() en el finally: se ejecuta aunque el test falle, así que un test roto tampoco contamina al siguiente. El aislamiento es una garantía, no una esperanza.
  • test_each_test_starts_clean: un test que prueba el andamiaje. Si algún día el rollback se rompe, este test lo delata de inmediato.

Fíjate en el patrón de dependencia entre fixtures: engine → session → client. Así se documenta visualmente la jerarquía de recursos, igual que el grafo de Depends de la app.

6 · Errores habituales

SQLite en memoria sin StaticPool

✗ Incorrecto
engine = create_engine("sqlite://")      # cada conexión = base de datos nueva
SQLModel.metadata.create_all(engine)

def get_test_session():
    with Session(engine) as session:
        yield session
# OperationalError: no such table: module
✓ Correcto
from sqlalchemy.pool import StaticPool

engine = create_engine(
    "sqlite://",
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,                # una sola conexión compartida
)
SQLModel.metadata.create_all(engine)

El error «no such table» justo después de haber creado las tablas es la firma inconfundible de este problema: la app está usando una conexión distinta de la que creó las tablas.

Dejar ficheros de base de datos por el repositorio

✗ Incorrecto
def test_something():
    engine = create_engine("sqlite:///./test.db")   # se queda en el repo
    SQLModel.metadata.create_all(engine)
    ...   # y el siguiente test arranca con los datos del anterior
✓ Correcto
def test_something(tmp_path):
    db_file = tmp_path / "test.db"                  # carpeta única por test
    engine = create_engine(f"sqlite:///{db_file}")
    SQLModel.metadata.create_all(engine)
    ...   # pytest borra tmp_path al terminar

Un test.db en el repositorio hace que los tests dependan del estado previo (¿pasó ayer?) y obliga a añadirlo al .gitignore. tmp_path te da un fichero nuevo por test, borrado por pytest.

Olvidar limpiar la sustitución de sesión

✗ Incorrecto
app.dependency_overrides[get_session] = get_test_session   # a nivel de módulo
# Los tests de OTRO archivo siguen usando la sesión de test sin saberlo,
# o al revés: la app real acaba con la base de datos de test.
✓ Correcto
@pytest.fixture
def client(session):
    app.dependency_overrides[get_session] = lambda: session
    with TestClient(app) as test_client:
        yield test_client
    app.dependency_overrides.clear()     # siempre

Las sustituciones son globales al objeto app. Si no las limpias, el efecto se propaga a tests (y contextos) donde no las quieres.

Confundir la sesión de test con una sesión nueva

✗ Incorrecto
@pytest.fixture
def client(engine):
    def override():
        with Session(engine) as s:     # sesión NUEVA, sin la transacción del test
            yield s
    app.dependency_overrides[get_session] = override
    ...
# El test siembra con `session`, pero la app escribe en otra sesión
# y la transacción externa no la envuelve: el aislamiento se rompe.
✓ Correcto
@pytest.fixture
def client(session):
    def override_get_session():
        yield session                 # cede LA MISMA sesión del test
    app.dependency_overrides[get_session] = override_get_session
    ...

Para que el test y la app compartan la transacción, tienen que compartir la sesión. Es la sutileza de la estrategia B: el override no crea sesiones nuevas, cede la del test. Escribirlo como lambda: session también valdría aquí, porque FastAPI acepta tanto un valor como un generador con yield.

7 · Ejercicio guiado

Objetivo: escribir la suite de persistencia de Copiloto API con base de datos temporal y aislamiento por test, y comprobar con un caso deliberado que el aislamiento de verdad funciona.

  1. Paso 1 — Monta el motor de test. En tests/conftest.py, crea la fixture engine con sqlite://, StaticPool y check_same_thread=False. No olvides instalar StaticPool desde sqlalchemy.pool (viene con SQLModel).
  2. Paso 2 — Crea las tablas. Llama a SQLModel.metadata.create_all(test_engine) dentro de la fixture. Asegúrate de importar app/models.py: si no, crearás cero tablas.

    Si al correr los tests ves no such table: module, revisa en este orden: (1) ¿importaste los modelos?, (2) ¿pusiste StaticPool?, (3) ¿creaste las tablas en este motor y no en el de la app?

  3. Paso 3 — Fixture de sesión con rollback. Copia la fixture session de la sección 4. Presta atención a join_transaction_mode="create_savepoint": sin él, el primer commit de la app cerraría la transacción externa.
  4. Paso 4 — Fixture de cliente con el override. Copia la fixture client. Verifica que el override devuelve la misma session y que se hace clear() al final.
  5. Paso 5 — Escribe los tres tests. Usa test_ask_persists_query_log, test_modules_reflects_seeded_rows y test_each_test_starts_clean de la sección 4. Ejecuta: 
    uv run pytest -q

  6. Paso 6 — Demuestra el aislamiento. Crea tests/test_isolation.py con dos tests que inserten un módulo cada uno. En ambos, al final, comprueba que GET /modules devuelve un solo módulo:

8 · Reto

🎯 Esquema por migración, no por create_all

En el Módulo 4 configuraste Alembic. Cambia la preparación de la base de datos de test para que aplique las migraciones en lugar de SQLModel.metadata.create_all(). Después escribe un test que compruebe que el esquema de test y el esquema documentado por los modelos coinciden: ¿hay alguna columna en los modelos que las migraciones no crean (o al revés)?

Pista: Alembic puede ejecutarse programáticamente con alembic.config.Config y command.upgrade(cfg, "head") apuntando a la URL de test. Para comparar esquemas, sqlalchemy.inspect(engine).get_columns("module") te da las columnas reales; compáralas con las de Model.__table__.columns. Reflexiona: ¿qué ventaja tiene testear contra las migraciones y no contra los modelos? ¿Qué tipo de bug detectarías que hoy se te escapa?

9 · Resumen

  • Los tests usan una base de datos propia: SQLite en memoria o un fichero con tmp_path; nunca la de desarrollo.
  • Para SQLite en memoria: StaticPool + check_same_thread=False, o cada conexión verá una base de datos vacía.
  • dependency_overrides[get_session] apunta la app a la base de datos de test sin tocar el código de producción.
  • Aislamiento: recrear el esquema por test (simple) o envolver cada test en una transacción con rollback (rápido y fino).
  • join_transaction_mode="create_savepoint" permite que el commit de la app conviva con la transacción externa del test.
  • Limpia siempre dependency_overrides y cierra sesiones y conexiones en el finally.
  • Importa los modelos antes de create_all; si no, crea cero tablas en silencio.

10 · Preguntas frecuentes

¿No sería más simple doblar el repositorio y olvidarme de la base de datos?

Para tests unitarios de la lógica de negocio, sí: un fake del repositorio es rápido y no toca SQL. Pero entonces nadie prueba el SQL: ni el mapeo de SQLModel, ni las consultas select, ni las transacciones, ni las restricciones (unique, foreign_key). Necesitas ambos niveles: doble para la lógica, base de datos real para la persistencia.

¿Por qué usar SQLite y no PostgreSQL en los tests?

Por velocidad y por cero infraestructura: SQLite arranca en memoria al instante, sin contenedores. Para el 95% de la lógica (validación, rutas, mapeo, relaciones) SQLite y PostgreSQL se comportan igual. Cuando dependas de algo específico del motor —tipos JSONB, restricciones o funciones de PostgreSQL—, añade además un conjunto de tests contra el motor real en CI, pero no para cada cambio.

¿Cuándo uso la estrategia A (recrear esquema) y cuándo la B (rollback)?

Empieza por la A: es más fácil de entender y de depurar. Cuando la suite crezca y crear las tablas por test se note (o cuando quieras un esquema inicial compartido y caro de construir), pasa a la B. Muchos equipos usan A con scope="session" para crear el esquema y B dentro para aislar cada test: lo mejor de ambas.

Mi test se queda «colgado» y no termina. ¿Por qué?

Casi siempre por una conexión de SQLite que quedó abierta y bloquea el fichero (o la transacción en memoria). Asegúrate de cerrar la Session y la Connection en un finally, y de que no haya peticiones esperando a un recurso que un test anterior no liberó. En tests async, comprueba además que no dejaste una tarea pendiente.

¿Cómo testo endpoints protegidos por JWT contra la base de datos de test?

Necesitas un usuario sembrado en la base de datos de test y un token válido para él. Como la base de datos es la del test, puedes crear el usuario en la fixture y generar el token con la misma función que usa la app. La lección de seguridad (Módulo 5) definió el get_current_user; en el reto del Módulo 7 harás un override de esa dependencia para los tests que no quieran pasar por el flujo completo de login.
