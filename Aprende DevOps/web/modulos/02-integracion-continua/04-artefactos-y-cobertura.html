Artefactos y cobertura: gates de calidad

Módulo 2 · Integración continua 🕐 30 minutos

1 · Introducción

Un CI que solo dice «verde/rojo» se queda corto. Dos preguntas más hacen que el pipeline sea de verdad útil: ¿qué produjo este run? (el informe de cobertura, los resultados de test, el paquete construido) y ¿es eso suficiente para fusionar? (¿el 80 % de cobertura es un requisito o una cifra decorativa?).

En esta lección cerramos el Módulo 2 con las dos piezas que responden a esas preguntas: los artefactos, que son los resultados que un run deja para que otros los usen (el siguiente job, una persona revisando, o un despliegue posterior), y los gates de calidad, que son comprobaciones con umbral que convierten una métrica en una puerta que bloquea o deja pasar.

¿Por qué separar «caché» de «artefacto»? Porque se parecen (ambos guardan archivos entre runs) pero tienen contratos opuestos. La caché es un atajo de rendimiento, opcional y descartable: si desaparece, el pipeline debe seguir funcionando igual. El artefacto es un resultado con vida propia: informes, paquetes, binarios. El artefacto que pruebas es el que despliegas (trazabilidad); la caché nunca es el artefacto.

Errores típicos: subir artefactos gigantes sin retención, usar el mismo name en todos los jobs de una matriz (colisión en upload-artifact v4), poner un umbral de cobertura que nadie mira porque se puede fusionar igual, o confundir «el run terminó» con «el artefacto está listo y es el correcto».

2 · Teoría

Artefactos: la salida tangible de un run

Un artefacto es un conjunto de archivos que se adjunta a un run de workflow y queda disponible para descargar (desde la UI, la CLI gh run download, o desde otro job del mismo run). Los casos de uso canónicos:

Tipo de artefactoEjemplo en el CopilotoPara qué
Informe de coberturacoverage.xml / htmlcov/Ver qué líneas cubren los tests; subirlo a un panel o dejarlo para revisión.
Resultados de testjunit.xmlQue la UI muestre qué test falló, no solo «el job falló».
Artefacto desplegabledist/*.whl, la imagen DockerEs el producto: lo mismo que se prueba se despliega (Módulos 3 y 7).
Evidencias/logscapturas, trazas, SBOMAuditoría y depuración posterior del run.
job: test job: publish ───────────── ───────────── pytest --cov ──► coverage.xml │ │ ▼ ▼ download-artifact upload-artifact ══════► (recibe coverage.xml y el wheel) name: cobertura │ path: coverage.xml ▼ usa el MISMO artefacto ya probado

La regla de oro de la trazabilidad: el artefacto que se prueba es el que se despliega. Si el job de test genera un wheel, ese wheel es el que debe llegar al entorno, no uno reconstruido con las prisas en el job de deploy. Los artefactos son el mecanismo que hace posible esa promesa.

upload-artifact y download-artifact

Dos actions, upload y download, forman el canal. La subida declara un nombre (la identidad del artefacto), una ruta (qué archivos) y, opcionalmente, cuántos días se guarda:

.github/workflows/ci.yml (subida)
- name: Subir el informe de cobertura
  uses: actions/upload-artifact@v7
  with:
    name: cobertura            # la identidad del artefacto
    path: coverage.xml         # qué se incluye (admite patrones y exclusiones)
    # retention-days: 5        # por defecto, el límite del repositorio
    if-no-files-found: error   # falla si la ruta no genera nada (red de seguridad)

Y la bajada, en otro job con needs:

.github/workflows/ci.yml (bajada)
- name: Descargar la cobertura del job de tests
  uses: actions/download-artifact@v8
  with:
    name: cobertura            # sin name, descarga TODOS los artefactos
    path: cobertura/           # dónde dejarlos (si no, el directorio actual)

El fallo clásico de la v4: nombres duplicados. En upload-artifact@v4 el nombre del artefacto ya no admite colisiones: si dos jobs suben un artefacto con el mismo name, el segundo falla con an artifact with this name already exists. En una matriz, incluye el eje en el nombre (cobertura-3.12) o sube todo de golpe con pattern. Los artefactos tampoco se pueden sobrescribir: cada subida debe tener nombre único.

Qué es un gate de calidad y por qué un umbral no basta

Un gate (puerta de calidad) es una comprobación que bloquea el avance si no se cumple. La forma más simple de gate en CI es un paso que falla si una métrica no llega a un umbral:

.github/workflows/ci.yml (gate de cobertura)
- name: Tests con umbral de cobertura
  # --cov-fail-under=80: si la cobertura global baja de 80 %, pytest
  # sale con código ≠ 0 y el job falla ⇒ el check del PR se pone rojo.
  run: uv run --frozen pytest --cov=app --cov-report=xml --cov-fail-under=80

Pero un gate es más que un número: para que de verdad bloquee, el check debe ser obligatorio en la configuración de protección de la rama (Módulo 1, lección 02). Un umbral en un workflow no obligatorio es una recomendación, no una puerta.

MétricaGate razonableHerramienta
Cobertura de líneasNo bajar del umbral (p. ej. 80 %)pytest-cov --cov-fail-under
Tests que pasan100 % (cero fallos)Código de salida de pytest
Lint/tipos0 erroresruff, mypy
Vulnerabilidades0 críticas/altasEscáneres (Módulo 3/7)
Tiempo del pipelinePor debajo de un presupuestoMétricas del run (Módulo 7)

Cobertura: úsala como suelo, no como objetivo. La cobertura mide qué líneas se ejecutan, no qué se verifica. Un assert débil ejecuta la línea y sigue contando. El gate sirve para impedir que la cobertura caiga, no para premiar subirla a base de tests vacíos. Combínala siempre con criterio humano en la revisión del PR.

Cobertura: qué se mide y cómo se publica

pytest-cov ejecuta los tests midiendo qué líneas se recorren y puede emitir el informe en varios formatos: term (consola), xml (para herramientas, coverage.xml), html (navegable) y lcov. El flujo completo del Copiloto:

  1. El job de test ejecuta pytest --cov y genera coverage.xml y junit.xml.
  2. Sube ambos como artefactos (con nombres únicos por versión de Python).
  3. El job de build o un job coverage-gate descarga el informe y aplica el umbral, o el propio pytest --cov-fail-under ya lo aplica.
  4. Opcionalmente, un bot comenta el porcentaje en el PR para que la revisión lo vea sin abrir artefactos.

En "Aprende DevOps" no necesitamos herramientas SaaS: con artefactos y un umbral en el propio test tenemos cobertura publicada y gate real. Servicios como Codecov añaden comentarios en el PR y comparación contra la base, pero el mecanismo subyacente es exactamente este.

¿Por qué subir el XML y aplicar el umbral? Porque son cosas distintas: el umbral decide el veredicto (gate), y el artefacto deja la evidencia para quien quiera investigar un PR concreto semanas después. Un run sin artefacto es un run que no puedes auditar; un run sin gate es un run que no decide nada.

3 · Ejemplo mínimo

Dos jobs: uno produce un archivo y lo sube; el otro lo descarga y lo usa. Nada más: es el canal de artefactos en su mínima expresión.

.github/workflows/artifacts.yml
name: Artefactos mínimos

on: [push]

jobs:
  produce:
    runs-on: ubuntu-latest
    steps:
      - name: Crear un archivo de resultado
        run: echo "cobertura: 82%" > resultado.txt

      - name: Subirlo como artefacto
        uses: actions/upload-artifact@v7
        with:
          name: resultado
          path: resultado.txt
          if-no-files-found: error    # si no existe, falla: red de seguridad

  consume:
    # needs garantiza que el artefacto YA existe cuando este job empieza.
    needs: produce
    runs-on: ubuntu-latest
    steps:
      - name: Descargar el artefacto
        uses: actions/download-artifact@v8
        with:
          name: resultado

      - name: Usarlo
        run: |
          cat resultado.txt
          echo "Leído correctamente desde el artefacto"

Fíjate en lo esencial:

  • El needs no es opcional aquí: sin él, el job consume podría arrancar antes de que exista el artefacto y fallar. Los artefactos no son canales sincronizados: tú decides el orden con needs.
  • if-no-files-found: error convierte un artefacto vacío (ruta mal escrita, paso que no generó nada) en un fallo ruidoso en vez de un artefacto silenciosamente vacío.
  • download-artifact deja el archivo en el directorio de trabajo por defecto (o en path si lo indicas).

4 · Ejemplo real

El CI del Copiloto al completo: la matriz de tests genera cobertura y resultados, los sube como artefactos, y un job final calidad aplica el gate y prepara el paquete. Solo este último será obligatorio para fusionar.

proyectos/pipeline/.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  # ============================================================
  # TESTS + COBERTURA (matriz) — producen los artefactos.
  # ============================================================
  test:
    name: Test (Python ${{ matrix.python-version }})
    runs-on: ubuntu-latest
    strategy:
      fail-fast: true
      matrix:
        python-version: ['3.12', '3.13']
    steps:
      - uses: actions/checkout@v7

      - name: Instalar uv
        uses: astral-sh/setup-uv@v10
        with:
          enable-cache: true

      - run: uv sync --frozen --all-extras

      - name: Ejecutar tests con cobertura y umbral
        # Genera DOS informes:
        #   --cov-report=xml   -> coverage.xml (herramientas / artefacto)
        #   --junitxml=...     -> junit.xml (UI de tests / artefacto)
        # --cov-fail-under=80 -> el gate de cobertura más simple posible.
        run: |
          uv run --frozen pytest -q \
            --cov=app \
            --cov-report=term-missing \
            --cov-report=xml \
            --cov-fail-under=80 \
            --junitxml=junit.xml

      - name: Subir cobertura
        # El nombre incluye el eje de la matriz: en v4 los nombres
        # NO pueden repetirse entre jobs del mismo run.
        uses: actions/upload-artifact@v7
        with:
          name: cobertura-${{ matrix.python-version }}
          path: coverage.xml
          retention-days: 7
          if-no-files-found: error

      - name: Subir resultados de test
        uses: actions/upload-artifact@v7
        with:
          name: junit-${{ matrix.python-version }}
          path: junit.xml
          retention-days: 7
          if-no-files-found: error

  # ============================================================
  # LINT — un job, sin matriz.
  # ============================================================
  lint:
    name: Lint y tipos
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10
        with:
          enable-cache: true
      - run: uv sync --frozen --all-extras
      - run: uv run --frozen ruff check .
      - run: uv run --frozen ruff format --check .
      - run: uv run --frozen mypy app

  # ============================================================
  # BUILD — genera el artefacto DESPLEGABLE del Copiloto.
  # ============================================================
  build:
    name: Build del paquete
    needs: [test, lint]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10
        with:
          enable-cache: true
      - run: uv sync --frozen --all-extras

      - name: Construir el wheel y el sdist
        run: uv build

      - name: Prueba de humo del artefacto real
        run: |
          uv run --isolated --no-project --with dist/*.whl \
            python -c "import app; print(app.__version__)"

      - name: Publicar el paquete como artefacto
        # ESTE es el artefacto que en el Módulo 3 se convertirá en imagen
        # Docker y que, en el Módulo 7, se desplegará SIN reconstruir.
        uses: actions/upload-artifact@v7
        with:
          name: wheel
          path: dist/*.whl
          if-no-files-found: error

  # ============================================================
  # CALIDAD — el único check OBLIGATORIO. Consume los artefactos
  # y deja una vista del run en el "summary" del workflow.
  # ============================================================
  calidad:
    name: Calidad (gate)
    # always() para que corra aunque algún test haya fallado y podamos
    # reportar; luego decidimos con el resultado de los needs.
    if: always()
    needs: [test, lint, build]
    runs-on: ubuntu-latest
    steps:
      - name: Descargar TODOS los artefactos
        uses: actions/download-artifact@v8
        with:
          path: artefactos/         # sin name ⇒ baja todo el run

      - name: Listar lo recibido
        run: |
          find artefactos -type f | sort

      - name: Comprobar que los jobs obligatorios pasaron
        # needs.X.result puede ser success / failure / cancelled / skipped.
        run: |
          echo "test=${{ needs.test.result }}"
          echo "lint=${{ needs.lint.result }}"
          echo "build=${{ needs.build.result }}"
          test "${{ needs.test.result }}" = "success"
          test "${{ needs.lint.result }}" = "success"
          test "${{ needs.build.result }}" = "success"

      - name: Resumen en la interfaz del workflow
        # GitHub renderiza Markdown en el resumen de cada run.
        run: |
          {
            echo "## Resultado del CI"
            echo ""
            echo "| Job | Estado |"
            echo "| --- | --- |"
            echo "| test | ${{ needs.test.result }} |"
            echo "| lint | ${{ needs.lint.result }} |"
            echo "| build | ${{ needs.build.result }} |"
          } >> "$GITHUB_STEP_SUMMARY"

Las decisiones que hacen que este pipeline sea útil y no solo verde:

  • El gate de cobertura vive en el propio pytest (--cov-fail-under=80): es el gate más rápido y no necesita un job aparte. El job calidad añade la puerta «todas las dependencias pasaron».
  • Los artefactos llevan nombres únicos por matriz (cobertura-3.12): si los dos jobs de la matriz subieran cobertura, el segundo fallaría.
  • El artefacto wheel es el producto desplegable. En el Módulo 3 se convertirá en imagen Docker; en el Módulo 7 llegará al entorno sin reconstruirse. Ahí está la trazabilidad.
  • Un solo check obligatorio (calidad) simplifica la protección de rama: en lugar de exigir seis checks, exiges uno. Es una estrategia habitual para matrices grandes; su precio es que, si calidad falla, el motivo está en los logs de un job anterior.

¿Y el if: always()? Sirve para que calidad corra aunque un test haya fallado: así siempre obtienes el resumen y la lista de artefactos, y el gate decide al final. Sin always(), si el test falla, calidad se saltaría y perderías la evidencia agregada. Ojo: always() no convierte el fallo en éxito; el test sigue en rojo y el workflow también.

5 · Buenas prácticas

HazEvitaPor qué
Nombres de artefacto únicos por matriz name: cobertura en todos los jobs En upload-artifact@v4 los nombres no colisionan: el segundo falla con «artifact already exists».
retention-days ajustado a lo que necesitas Guardar todo hasta el límite del repositorio Los artefactos ocupan almacenamiento y tienen coste; un informe de test de hace un mes rara vez hace falta.
Sube lo pequeño y útil (XML, wheel) Subir node_modules, .venv, htmlcov/ entero sin motivo Los artefactos se descargan y consumen cuota; cachea lo repetible y sube solo lo que aporta evidencia.
if-no-files-found: error Dejar por defecto (warn) Un artefacto vacío por una ruta mal escrita es un fallo silencioso; mejor que reviente.
Gate de cobertura como check obligatorio Umbral en un workflow que nadie exige Un gate que no bloquea es documentación, no una puerta. La protección de rama es la que lo hace real.
El artefacto probado es el desplegado Reconstruir el paquete en el job de deploy Reconstruir introduce variabilidad: lo que pruebas deja de ser lo que despliegas. Trazabilidad rota.
Nunca artefactos con secretos Subir .env, tokens, kubeconfig Los artefactos son descargables por cualquiera con acceso al repo: puede ser una fuga de credenciales.

6 · Errores habituales

Nombres de artefacto duplicados en la matriz

Incorrecto
# ❌ Dos jobs de la matriz suben el mismo nombre.
#    El segundo muere: "an artifact with this name already exists".
uses: actions/upload-artifact@v7
with:
  name: cobertura
  path: coverage.xml
Correcto
# ✅ Un nombre por combinación.
uses: actions/upload-artifact@v7
with:
  name: cobertura-${{ matrix.python-version }}
  path: coverage.xml

Intentar usar el artefacto sin esperarlo

Incorrecto
jobs:
  publish:
    runs-on: ubuntu-latest   # ❌ sin needs: puede arrancar antes que test
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: wheel            # …y no existir todavía
Correcto
jobs:
  publish:
    needs: build             # ✅ el artefacto YA existe cuando empieza
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: wheel

Umbral de cobertura que no bloquea nada

# ❌ El umbral existe, pero el check no es obligatorio en la rama:
#    la cobertura baja, el job se pone rojo... y se fusiona igual.
- run: pytest --cov-fail-under=80

# ✅ Además del umbral, marca "Calidad (gate)" como check requerido
#    en la protección de rama (Settings → Branches). El código decide
#    el veredicto; la configuración de la rama lo hace vinculante.

Confundir caché con artefacto (y viceversa)

# ❌ Guardar el informe de cobertura en la caché para leerlo después.
- uses: actions/cache@v6
  with:
    path: coverage.xml
    key: cobertura           # puede no existir: la caché es "best effort"

# ❌ …o cachear el .venv como si fuera un artefacto reutilizable.
- uses: actions/upload-artifact@v7
  with:
    name: venv
    path: .venv              # entorno con rutas absolutas: inútil en otro run

# ✅ Caché = rendimiento (almacén de descargas). Artefacto = resultado
#    (coverage.xml, wheel). Cada uno en su sitio.

Rutas que no coinciden con donde se generó el archivo

# ❌ pytest escribió el XML en app/coverage.xml, no en la raíz.
- uses: actions/upload-artifact@v7
  with:
    name: cobertura
    path: coverage.xml          # no existe ⇒ artefacto vacío silencioso
    # (sin if-no-files-found: error, esto pasa desapercibido)

# ✅ Usa la ruta real, o un patrón; y pon la red de seguridad.
- uses: actions/upload-artifact@v7
  with:
    name: cobertura
    path: '**/coverage.xml'
    if-no-files-found: error

7 · Ejercicio guiado

Objetivo: publicar cobertura y resultados de test como artefactos, aplicar un umbral del 80 % y comprobar que el CI bloquea cuando la cobertura baja.

  1. Paso 1 — Añade cobertura y umbral en local. 
    cd ~/proyectos/copiloto-api
uv run --frozen pytest -q \
  --cov=app --cov-report=term-missing --cov-report=xml \
  --cov-fail-under=80 --junitxml=junit.xml
# Mira la tabla de cobertura: te dirá qué módulos van justos.
ls coverage.xml junit.xml      # ambos informes generados
  2. Paso 2 — Actualiza el workflow. Sustituye el job test del ejemplo real (con los upload-artifact) y añade el job calidad. Ponte en una rama corta. 
    git checkout -b ci/coverage-artifacts
git commit -am "ci: cobertura, artefactos y gate de calidad"
git push -u origin ci/coverage-artifacts
gh pr create --fill
gh pr checks --watch
  3. Paso 3 — Descarga un artefacto con la CLI. 
    # Toma el ID del último run del PR:
gh run list --limit 1
# Descarga los artefactos (los de la matriz llegarán en carpetas):
gh run download <run-id>
ls cobertura-3.12/ junit-3.12/ wheel/
  4. Paso 4 — Rompe el gate a propósito. Elige un módulo con tests y coméntalos, o crea una función nueva sin test, hasta bajar del umbral. 
    # Ejemplo: comenta los tests de /modules en tests/test_health.py
git commit -am "test: bajar la cobertura por debajo del umbral"
git push
gh pr checks --watch
# Esperado: "Test (Python 3.12)" ❌ con mensaje de --cov-fail-under.
# Y "Calidad (gate)" ❌ con "test=failure": el job obligatorio bloquea.
  5. Paso 5 — Recupera el umbral y revisa el resumen. 
    git checkout -- tests/test_health.py
git commit -am "test: restaurar los tests"
git push
gh run view --log | Select-String "Resultado del CI"
# En la web, la pestaña del run muestra el "Summary" con la tabla de
# estados generada en $GITHUB_STEP_SUMMARY.
  6. Paso 6 — Hazlo obligatorio y verifica. 
    # En GitHub: Settings → Branches → regla de proteccion de main:
#   exige el check "Calidad (gate)".
gh pr checks
# Esperado: todos ✅ y, con la rama protegida, el botón de fusionar
# deshabilitado si el gate no está verde. Fusiona:
gh pr merge --squash

Verificación conceptual: si el paso 4 pone el test en rojo pero el PR se pudiera fusionar igual, el gate no es obligatorio: ve a la protección de rama. Si el download-artifact no encuentra nada, revisa que el job consumidor tenga needs y que los nombres no colisionen. Y si coverage.xml aparece vacío, añade if-no-files-found: error para que la próxima vez falle en voz alta.

8 · Reto

🎯 Cobertura que no baje (y que se vea)

Convierte la cobertura en una señal viva del PR, sin depender de servicios externos:

  • Calcula la cobertura de la rama base (main) y la de la rama del PR. El gate no debe ser un número fijo, sino «no bajar respecto a la base»: si main tiene 86 %, el PR debe mantener al menos 86 %.
  • Publica un comentario en el PR con el porcentaje y la diferencia (por ejemplo, «cobertura: 87,2 % (+1,1 %)»), usando gh pr comment con GITHUB_TOKEN.
  • En una matriz, agrega los informes (coverage.xml de 3.12 y 3.13) en un solo resultado antes de decidir el gate.

Pistas: actions/download-artifact@v8 sin name baja todo y puedes fusionar los XML con coverage combine; el permiso pull-requests: write es necesario para comentar en el PR (y recuerda que ampliar permisos es una decisión de seguridad: Módulo 4); para comparar contra la base, un git worktree o un checkout de main en un job aparte te da la cifra de referencia.

9 · Resumen

  • Un artefacto es un resultado con vida propia (informe, wheel): se sube con upload-artifact y se consume con download-artifact + needs.
  • La caché es rendimiento descartable; el artefacto es evidencia. No los mezcles.
  • En upload-artifact@v4 los nombres son únicos: en matriz, incluye el eje en el nombre.
  • if-no-files-found: error convierte artefactos vacíos en fallos visibles.
  • Un gate es una comprobación que bloquea; un umbral se vuelve gate de verdad cuando el check es obligatorio en la rama.
  • La cobertura es un suelo, no un objetivo: mide líneas ejecutadas, no intención de verificar.
  • El artefacto que se prueba es el que se despliega: construye una vez, promueve el mismo artefacto.

10 · Preguntas frecuentes

¿Los artefactos se pueden sobrescribir?

No con upload-artifact@v4: cada subida crea un artefacto nuevo y el nombre debe ser único dentro del run. Si necesitas «actualizar» un artefacto, sube otro con nombre distinto o reconstruye el resultado. Este cambio respecto a versiones antiguas es deliberado: hace los artefactos inmutables, lo que refuerza la trazabilidad (sabes exactamente qué se subió).

¿Cuánto tiempo se guardan los artefactos por defecto?

El valor por defecto lo fija el repositorio (habitualmente 90 días), y puedes acortarlo por artefacto con retention-days. Nunca puedes excederlo. Para informes de test de una PR, 7 días suele bastar; para un SBOM o un binario que auditas, quizá quieras el máximo permitido. Recuerda que el almacenamiento de artefactos cuenta para la cuota de Actions.

¿Un umbral de cobertura global o por archivo?

Lo habitual es un umbral global (--cov-fail-under) como suelo del proyecto, más uno o dos módulos críticos con umbral propio (seguridad, pagos, lógica de dominio) — porque en esos el 80 % global puede esconder un 10 %. Empieza por el global para no bloquear al equipo, y endurece donde de verdad importa. Un umbral mal calibrado se acaba ignorando; uno razonable se respeta.

¿Por qué el mismo artefacto de test debe llegar al deploy?

Porque construir dos veces produce dos cosas potencialmente distintas: un wheel con otra dependencia transitiva, un binario con otro timestamp. La promesa del pipeline es «lo que se prueba es lo que se despliega». Si el job de CD descarga el mismo artefacto del job de CI (en lugar de reconstruir), eliminas toda la variabilidad entre el veredicto y el despliegue. Es la base del despliegue por promoción que verás en el Módulo 4.

¿Puedo usar la cobertura para bloquear un PR entero?

Sí, y es justo el mecanismo de gate: si pytest --cov-fail-under=80 falla, el job falla; si ese job es obligatorio en la protección de rama, el PR no se puede fusionar. La advertencia profesional: no lo pongas tan alto que el equipo invente tests vacíos para pasarlo, ni tan bajo que no cambie nada. Un buen gate se nota cuando no salta y molesta cuando de verdad detecta una regresión.
