Conventional Commits y changelog

Módulo 1 · Git, ramas y versiones 🕐 30 minutos

1 · Introducción

Hasta ahora el número de versión y el mensaje de commit eran decisiones humanas, tomadas a ojo. Conventional Commits cierra el círculo: si cada commit dice qué tipo de cambio es siguiendo una convención mecánica, una máquina puede leer ese historial y derivar la siguiente versión y el changelog sin que nadie lo escriba a mano.

En esta lección verás el formato (tipo(scope): descripción), los tipos habituales, cómo marcar un cambio incompatible, y cómo todo eso se traduce —mediante herramientas como semantic-release, release-please o git-cliff— en una etiqueta de versión y unas notas de release generadas automáticamente.

¿Por qué importa esto? Porque convierte el historial de Git —que ya escribes de todas formas— en datos. El changelog deja de ser un documento que se «redacta» (y se olvida) para ser un artefacto que se genera del propio código. Y el número de versión deja de elegirlo alguien a viernes por la tarde: lo decide la naturaleza objetiva de los commits que entran.

Errores típicos: usar fix: para todo (cuando en realidad es una feature disfrazada), inventar tipos a capricho, marcar mal un breaking change —o no marcarlo—, o instalar el generador de changelog después de tres años de mensajes «actualizo cosas».

2 · Teoría

El formato

Conventional Commits (spec 1.0.0) define una estructura simple sobre el mensaje de commit:

estructura
<tipo>[scope opcional][!]: descripción

[cuerpo opcional]

[footers opcionales]
  • tipo (obligatorio): una palabra que clasifica el cambio (feat, fix, …).
  • scope (opcional): entre paréntesis, la parte afectada (api, auth, db).
  • ! (opcional): marca un cambio incompatible, justo antes de los dos puntos.
  • descripción (obligatoria): una línea corta tras : (dos puntos y un espacio).
  • cuerpo y footers: contexto adicional y metadatos (BREAKING CHANGE, Closes #12), separados por líneas en blanco.
ejemplos válidos
feat(api): add /modules/{id}/lessons endpoint
fix(auth): reject expired JWTs before signature check
docs(readme): documentar el arranque local
feat(api)!: require X-Api-Key on every write endpoint

BREAKING CHANGE: los POST sin cabecera X-Api-Key ahora devuelven 401.

Analogía — el etiquetado de una caja: un commit convencional es una caja con una etiqueta legible por máquina. El tipo dice qué contiene (¿frágil? ¿perecedero?), el scope dice de qué estantería salió, y el ! es el precinto rojo de «esto no es compatible con lo de antes». Un almacén —tu pipeline— puede clasificar y distribuir las cajas sin abrir ninguna.

Los tipos que importan (y por qué)

TipoSignificaBump SemVer
featFuncionalidad nueva para quien usa el softwareMINOR
fixCorrección de un falloPATCH
BREAKING CHANGE (footer) o !Cualquier cambio incompatibleMAJOR
docs, style, refactor, test, chore, ci, build, perfCambios que no alteran el contrato públicoNinguno

La correspondencia con SemVer no es una coincidencia: la spec nació para dovetail con ella. feat → MINOR, fix → PATCH y cualquier incompatibilidad → MAJOR. Los demás tipos documentan trabajo que no debe mover el número público (salvo perf, que se debate: suele ir como PATCH si mejora sin cambiar contrato).

Tipos: nómina, no catálogo abierto. La spec permite cualquier tipo, pero un equipo funciona mejor con una lista corta y acordada. Si cada persona inventa el suyo (update, wip, cosas), ninguna herramienta podrá clasificar el historial y perderás justo lo que ibas buscando.

Marcar lo incompatible con rigor

Hay dos formas válidas de señalar un breaking change, y conviene saber cuándo usar cada una:

  • El ! en el prefijo (feat(api)!: …): rápido, útil cuando la línea de descripción ya explica el alcance.
  • El footer BREAKING CHANGE: (en mayúsculas): obligatorio para explicar el cambio y qué debe hacer quien actualiza. Puede convivir con el !.
breaking change bien marcado
feat(api)!: rename "level" to "difficulty" in /modules

BREAKING CHANGE: el campo `level` de la respuesta se llama ahora
`difficulty`. Actualiza tus clientes; el valor sigue siendo el mismo.
Refs: #482

BREAKING CHANGE va en mayúsculas. La spec es explícita: los tipos no distinguen mayúsculas, pero BREAKING CHANGE (y su sinónimo BREAKING-CHANGE) sí. Escrito en minúsculas, las herramientas no lo reconocen y tu cambio incompatible se cuela como un MINOR: el fallo más peligroso de esta lección.

Del historial al changelog

Con el historial etiquetado, generar el changelog es agrupar por tipo y formatear:

commits desde el ultimo tag ──▶ parser (tipo, scope, BREAKING) │ ├─▶ calcular la nueva version (SemVer) ├─▶ escribir CHANGELOG.md └─▶ crear tag + release

Herramientas habituales, con enfoques distintos:

HerramientaEnfoqueCuándo encaja
semantic-releaseCalcula versión y publica, sin intervenciónCI/CD que quiere cero pasos manuales
release-pleaseAbre un PR de release que tú mergeasEquipos que quieren revisar antes de publicar
git-cliffGenerador de changelog desde configCuando solo quieres el CHANGELOG, con control fino
commitlintValida el mensaje antes de aceptarloSiempre: es la puerta que garantiza el formato

El changelog se genera, no se escribe. El CHANGELOG.md debe salir de los commits, no redactarse a mano (dos fuentes de verdad divergen siempre). La excepción es la cabecera del release, donde una persona explica el «por qué» con contexto de negocio; eso lo añade el PR de release.

3 · Ejemplo mínimo

El mínimo indispensable: validar el formato con commitlint, de modo que un mensaje mal escrito no llegue a main. Sin esta puerta, todo lo demás (changelog, versionado derivado) deja de funcionar el día que alguien escribe «arreglos».

commitlint.config.js
// Lista corta y acordada de tipos. La valida commitlint.
export default {
  extends: ["@commitlint/config-conventional"],
};

# Instala commitlint y su configuracion en el repo
npm install --save-dev @commitlint/cli @commitlint/config-conventional

# Prueba manual: el mensaje debe cumplir el formato
echo "feat(api): add /health" | npx commitlint
# -> sin salida y exit 0 (valido)

echo "arreglos varios" | npx commitlint
# -> ✖ subject may not be empty  (invalido, exit 1)

Ese «exit 1» es lo que aprovecharás como check en el CI. Con la validación en marcha, cada commit de main es ya un dato fiable para el generador de changelog.

4 · Ejemplo real

En Publicar el Copiloto combinamos tres piezas: commitlint valida los mensajes en cada PR, y release-please mira los commits integrados para proponer la siguiente versión y el changelog en un PR de release. Lo bueno de release-please es que la publicación sigue siendo un acto revisable: nadie etiqueta por sorpresa.

.github/workflows/release-please.yml
name: Release Please

on:
  push:
    branches: [main]

permissions:
  contents: write
  pull-requests: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: googleapis/release-please-action@v5
        with:
          release-type: simple

El ciclo que produce ese workflow es este: cada merge a main con commits convencionales va engordando un PR de release llamado chore(main): release X.Y.Z. Ese PR lleva la versión calculada y el CHANGELOG.md generado. Cuando el equipo lo mergea, la action crea el tag y el release de GitHub — y a partir de ese tag arranca la publicación de la imagen (lección anterior).

CHANGELOG.md (generado, extracto)
## [2.4.0](https://…/compare/v2.3.1...v2.4.0) (2026-04-11)

### Features

* **api:** add /modules/{id}/lessons endpoint ([#482](…))

### Bug Fixes

* **auth:** reject expired JWTs before signature check ([#479](…))

### ⚠ BREAKING CHANGES

* **api:** rename "level" to "difficulty" in /modules

Observa la aritmética: hubo feats (MINOR) y un breaking (MAJOR)… pero la versión subió de 2.3.1 a 2.4.0, no a 3.0.0. En este ejemplo el breaking entró en el mismo PR que aún no se había publicado antes del corte; cuando un breaking llega después de una versión ya publicada, sí fuerza el MAJOR. La herramienta compara lo que existe en el historial desde el último tag: de ahí que el orden y el momento de los commits importen.

Y en el CI del PR, el check que garantiza el formato:

.github/workflows/ci.yml (extracto)
      - name: Install
        run: npm ci
      - name: Validate commit messages
        run: npx commitlint --from origin/main --to HEAD

6 · Errores habituales

1. Etiquetar una feature como fix

El tipo no describe tu esfuerzo, describe el efecto sobre quien usa el software. Una capacidad nueva es feat aunque fuera «un arreglo».

Mal — una feature disfrazada de fix 
fix: anado endpoint de exportacion a CSV
# El changelog lo esconde en "Bug Fixes" y la version solo sube PATCH:
# quien esperaba la funcionalidad no se entera.
Bien — tipo segun el efecto 
feat(api): add CSV export endpoint
# Aparece en "Features" y la version sube MINOR.

2. Escribir BREAKING CHANGE en minúsculas o en el sitio equivocado

La spec exige mayúsculas para ese footer. Si no, tu cambio incompatible pasa como compatible.

Mal — breaking mal marcado 
feat(api): rename level to difficulty

breaking change: los clientes deben actualizar su campo
# -> no se reconoce: la herramienta calcula un MINOR y rompe a los consumidores
Bien — footer en MAYÚSCULAS (y/o !) 
feat(api)!: rename level to difficulty

BREAKING CHANGE: el campo level se llama ahora difficulty.
# -> se reconoce: la herramienta calcula un MAJOR y lo lista aparte.

3. Inventar tipos o meterlo todo en un commit

«chore: cambios varios» no es un commit, es una caja negra. Ni el changelog ni el versionado sabrán qué pasó.

Mal — caja negra 
update: varias cosas
# No hay tipo reconocido, no hay scope, no hay descripcion util.
Bien — commits atómicos con tipo 
fix(api): handle empty module list
test(api): cover empty module list
docs(readme): note the empty-list case

Con squash, importa el PR, no tus commits internos. Si integras con squash, el mensaje que llega a main es el título del PR: ese es el que debe ser convencional. Los commits intermedios de tu rama pueden ser «wip» sin consecuencias; en la lección de pull requests vimos por qué.

7 · Ejercicio guiado

Objetivo: validar los mensajes con commitlint y generar un changelog con git-cliff a partir de un historial convencional, comprobando que cada tipo dispara el cambio de versión esperado.

  1. Paso 1 — Crea un historial convencional de laboratorio. 
    mkdir copiloto-commits && cd copiloto-commits
git init -b main
git commit --allow-empty -m "feat(api): add /health"
git commit --allow-empty -m "fix(api): return 200 on healthy"
git commit --allow-empty -m "docs(readme): documentar /health"
git commit --allow-empty -m "feat(api)!: rename level to difficulty" -m "BREAKING CHANGE: el campo level se llama difficulty"
git tag -a v1.0.0 -m "Release v1.0.0"
  2. Paso 2 — Configura y ejecuta commitlint. 
    npm init -y > /dev/null
npm install --save-dev @commitlint/cli @commitlint/config-conventional
echo "export default { extends: ['@commitlint/config-conventional'] };" > commitlint.config.js

git log -1 --pretty=%B | npx commitlint     # el ultimo commit debe pasar
echo "wip" | npx commitlint                 # -> ✖ debe fallar
  3. Paso 3 — Genera el changelog con git-cliff. 
    # Instala git-cliff (cargo, brew o binario de release) y genera desde el ultimo tag
git-cliff --latest --output CHANGELOG.md
cat CHANGELOG.md

    Si no tienes git-cliff a mano, cualquier generador sirve para el ejercicio: npx conventional-changelog-cli -p conventionalcommits -r 1 produce un changelog equivalente desde los mismos commits.

  4. Paso 4 — Verifica que el breaking quedó aparte. 
    # El CHANGELOG debe separar Features, Bug Fixes y avisar del BREAKING CHANGE
Select-String -Path CHANGELOG.md -Pattern "BREAKING|Features|Bug Fixes"
  5. Paso 5 — Razona el bump. Con estos commits, la siguiente versión desde 1.0.0 sería MAJOR (2.0.0) por el ! y el footer BREAKING CHANGE:. Añade un commit fix y comprueba que, sin el breaking, el bump bajaría a PATCH. 
    git commit --allow-empty -m "fix(api): correct difficulty mapping"
# (imagina el historial SIN el commit !): el bump seria 1.0.1, no 2.0.0

    Resultado esperado: commitlint rechaza los mensajes que no cumplen el formato; el CHANGELOG.md agrupa por tipo y señala el breaking change por separado; y sabes calcular a mano qué incremento SemVer produce cada combinación de commits.

8 · Reto

🎯 Un changelog a la medida del Copiloto

Monta un pipeline que, partiendo de los commits convencionales de la Copiloto API, genere un changelog adaptado a la audiencia. Requisitos: (1) los cambios visibles para quien usa la API (feat, fix, breaking) van a un CHANGELOG.md con enlaces a los PRs y un bloque de migración para los breaking changes; (2) los cambios internos (chore, ci, test) van a una sección secundaria o se omiten; (3) la versión siguiente se deriva de los commits y el pipeline abre un PR de release en lugar de publicar a ciegas; y (4) un check obligatorio impide mergear un commit que no cumpla el formato.

Pista: git-cliff se configura con un cliff.toml donde defines plantillas por tipo y grupos de «omitidos»; release-please ya separa automáticamente feat/fix y los breaking, y puedes añadir secciones extra. Para los enlaces a PRs necesitarás una plantilla que use el número de PR (incluido en el commit squash). Piensa qué debe ver un consumidor de la API y qué no: el reto no es generar un changelog, es decidir para quién se escribe. Documenta tu decisión.

9 · Resumen

  • Formato: <tipo>[scope][!]: descripción, con cuerpo y footers separados por líneas en blanco.
  • feat → MINOR; fix → PATCH; cualquier incompatibilidad → MAJOR.
  • Los BREAKING CHANGE se marcan con ! y/o un footer BREAKING CHANGE: en mayúsculas.
  • El tipo describe el efecto sobre quien usa el software, no el esfuerzo que te costó.
  • commitlint es la puerta que garantiza el formato; sin ella, todo lo demás se degrada.
  • El changelog se genera del historial (git-cliff, release-please, semantic-release), no se redacta a mano.
  • El pipeline puede derivar la versión de los commits, pero conviene revisarla en un PR de release.
CommitBump SemVer
fix(api): …PATCH
feat(api): …MINOR
feat(api)!: … + BREAKING CHANGE:MAJOR
docs: …, chore: …, ci: …ninguno

10 · Preguntas frecuentes

¿Merece la pena si el equipo es de una sola persona?

Sobre todo si es de una sola persona. La convención no es burocracia para equipos grandes: es la forma de que el generador de changelog y el cálculo de versión funcionen sin que nadie los mantenga. En un equipo de uno, escribir feat/fix cuesta segundos y te ahorra redactar notas de release a mano — y, dentro de seis meses, recordar por qué subió la versión.

¿Quién escribe el mensaje convencional si integro con squash?

El título del PR, porque squash lo convierte en el commit que llega a main. Por eso conviene configurar la plataforma para que el título por defecto del squash sea el del PR (o el único commit, si solo hay uno) y para que commitlint valide ese texto. Los commits internos de tu rama no necesitan ser convencionales, aunque ayuda que lo sean para revisar.

¿Qué hago con un breaking change que lleva años sin publicarse?

Se resuelve mejor con una política de deprecación que con un número. Lo ideal: publicar primero un minor que introduce la alternativa y avisa (log, cabecera de deprecación, nota en el changelog), mantener ambas durante una ventana acordada y, solo después, cortar la vieja como MAJOR. Así el número de versión refleja una decisión comunicada, no una sorpresa.

¿Los mensajes de merge automáticos o los de herramientas rompen el formato?

Sí, y es un problema real: dependabot, los merges automáticos y algunos bots generan mensajes que no siguen la convención. La solución tiene dos partes: excluir esos commits del commitlint (validar solo los humanos) y decidir explícitamente si sus cambios deben afectar a tu versión —normalmente, una actualización de dependencias es chore y no debería forzar un MINOR salvo que cambie tu contrato público.

¿Puedo aplicar Conventional Commits sin cambiar mi flujo de ramas?

Sí, es independiente de la estrategia de ramas. Pero se llevan de maravilla con trunk-based: ramas cortas, un PR = un commit squash, y un historial lineal de commits convencionales que el pipeline lee de corrido. Con GitFlow también funciona, solo que el changelog debe ignorar los commits de merge y de release para no duplicar entradas.
