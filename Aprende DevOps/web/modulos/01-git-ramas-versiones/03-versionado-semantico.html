Versionado semántico

Módulo 1 · Git, ramas y versiones 🕐 30 minutos

1 · Introducción

Un nombre de versión como 2.4.1 parece un detalle administrativo, pero en un pipeline es la identidad del artefacto: es lo que distingue la imagen que probaste en staging de la que está en producción, lo que permite volver atrás («vuelve a la 2.4.0») y lo que le dice a quien consume tu API si su código seguirá funcionando tras el cambio. El versionado semántico (SemVer) es el convenio que hace que ese nombre signifique algo.

En esta lección verás las reglas de SemVer —MAJOR.MINOR.PATCH— y, sobre todo, cómo se conectan con CI/CD: tags de Git, releases, etiquetado de imágenes y la idea de que el artefacto que se prueba es el que se despliega.

¿Por qué importa esto? Porque sin versiones inmutables no hay trazabilidad ni rollback posible. Si tu «versión» es mutable (la imagen latest, el tag staging que reescribes cada día), no puedes afirmar qué está corriendo ni reproducir un fallo. SemVer no es vanidad de librerías: es la base del despliegue seguro.

Errores típicos que veremos: subir el MAJOR por cambios que no rompen nada (y agotar la confianza del número), reutilizar un tag ya publicado, usar latest como identidad, o etiquetar el artefacto con un número distinto al del release de Git.

2 · Teoría

Las tres partes: MAJOR.MINOR.PATCH

SemVer (Semantic Versioning, spec en semver.org) define un número de versión con tres enteros separados por puntos, y una regla clara para cada uno. La idea de fondo: el número comunica qué espera quien consume el software.

ParteCuándo se incrementaPromesa
MAJORCambio incompatible (breaking change)«Algo puede dejar de funcionar; lee las notas»
MINORFuncionalidad nueva compatible«Puedes actualizar sin romper nada; hay cosas nuevas»
PATCHCorrección compatible«Solo arreglos; actualizar es seguro»
1 . 4 . 2 │ │ └── PATCH → correccion de bug compatible │ └──────── MINOR → feature nueva compatible └────────────── MAJOR → cambio incompatible (breaking) 1.4.2 ──fix──▶ 1.4.3 ──feat──▶ 1.5.0 ──breaking──▶ 2.0.0

Analogía — el manual de una máquina: el MAJOR es cambiar el modelo: los accesorios viejos ya no encajan. El MINOR es añadir un accesorio nuevo sin tocar los agujeros existentes: todo lo antiguo sigue encajando. El PATCH es apretar un tornillo suelto: nada cambia de forma, solo deja de fallar.

Las reglas que hacen útil el número

  • Cada incremento lleva a cero las partes a su derecha: de 1.4.9 un feat da 1.5.0, no 1.5.9.
  • Una versión publicada es inmutable: su contenido no cambia jamás. Si algo va mal, se publica 1.4.3, no se reescribe 1.4.2.
  • 0.y.z significa desarrollo inicial: cualquier cosa puede cambiar en cualquier momento. Solo cuando está estable se sube a 1.0.0.
  • Si un cambio rompe compatibilidad, MAJOR sube aunque sea un solo carácter. Es la parte que más se incumple.

Orden de precedencia: SemVer no compara como una cadena de texto. 1.10.0 es más nueva que 1.9.0, porque los números se comparan de mayor a menor, uno a uno. Herramientas como npm semver o la comparación de tags de tu registry respetan esta regla; tu script casero probablemente no.

Prereleases y metadatos

SemVer admite dos sufijos. Es tentador ignorarlos, pero en CI son muy útiles:

formas de versión
1.4.2-alpha.1      prerelease: tiene menor precedencia que 1.4.2
1.4.2-rc.2         release candidate: candidato antes del definitivo
1.4.2+build.511    metadatos de build: NO afectan a la precedencia

Precedencia:  1.4.2-alpha.1  <  1.4.2-beta  <  1.4.2-rc.1  <  1.4.2

Un prerelease (-rc.1, -beta) permite publicar artefactos para probar sin comprometer el número definitivo. Los metadatos (+…) sirven para anotar el build, pero no ordenan: 1.4.2+build.1 y 1.4.2+build.9 son la misma versión a efectos de precedencia.

Por qué esto importa a CI/CD

El pipeline convierte un commit en un artefacto y necesita poder referirse a él en varios sitios distintos. La versión es el hilo que los une:

commit ──▶ TAG de Git (v2.4.1) ──▶ imagen (ghcr.io/acme/copiloto:2.4.1) │ ├─▶ SBOM adjunto └─▶ procedencia / release notes │ └──▶ release en GitHub con changelog
  • Tag de Git: marca el commit exacto del release. Debe ser anotado (git tag -a), no ligero.
  • Artefacto etiquetado: la imagen usa el mismo número. Un solo release con un solo número en todos los sitios.
  • Promoción, no reconstrucción: lo que va a producción es el mismo artefacto que pasó staging, identificado por la misma versión (o mejor aún, por su digest inmutable).

La versión no basta como identidad por sí sola. Un tag como 2.4.1 puede en teoría reescribirse en un registry. Para trazabilidad real se despliega por digest (@sha256:…), que sí es inmutable por construcción. SemVer es el nombre legible; el digest es el DNI. Volveremos sobre esto al hablar de registries y tagging (módulo 3).

3 · Ejemplo mínimo

El ciclo más pequeño: etiquetar un commit con una versión SemVer, subir el tag y disparar un workflow que solo reacciona a tags con forma de versión.

terminal
# 1. Asegurate de estar sobre el commit que quieres publicar
git switch main
git pull --ff-only

# 2. Tag ANOTADO con la version (mensaje propio, no el del commit)
git tag -a v2.4.1 -m "Release v2.4.1"

# 3. Sube el tag (git push normal NO sube tags)
git push origin v2.4.1
.github/workflows/release.yml
name: Release

on:
  push:
    tags:
      - "v*.*.*"        # solo etiquetas tipo v2.4.1 (glob simple)

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Mostrar la version
        run: echo "Publicando ${GITHUB_REF_NAME}"   # v2.4.1

Fíjate en el glob v*.*.*: acepta v2.4.1 pero no v2.4. Para validar SemVer de verdad (y descartar v2.4.1.tmp) haría falta un filtro más fino, que es justo el tema del reto.

4 · Ejemplo real

En Publicar el Copiloto un release de la Copiloto API hace tres cosas a la vez a partir de un solo tag: publica la imagen en GHCR con el número de versión, genera un release en GitHub y deja el artefacto listo para promover.

.github/workflows/release.yml
name: Release

on:
  push:
    tags: ["v*.*.*"]

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: write    # crear el release
      packages: write    # publicar en GHCR
    steps:
      - uses: actions/checkout@v7

      # Deriva los tags de imagen a partir del semver del tag de Git.
      # v2.4.1 -> 2.4.1, 2.4, 2  (y "latest" solo si no es prerelease)
      - id: meta
        uses: docker/metadata-action@v6
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}

      - uses: docker/build-push-action@v7
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

      - name: Crear release a partir del tag
        run: gh release create "${GITHUB_REF_NAME}" --generate-notes
        env:
          GH_TOKEN: ${{ github.token }}

Un tag, dos artefactos etiquetados igual. El tag de Git v2.4.1 produce la imagen ghcr.io/acme/copiloto:2.4.1 y un release v2.4.1. Ese es el tipo de coherencia que permite decir, sin dudar, «en producción corre la 2.4.1». La derivación automática de tags la retomaremos en el módulo de registries.

Y al desplegar, la promoción reutiliza el mismo artefacto: no se reconstruye para producción, se mueve la etiqueta que ya existe (o mejor, se fija el digest probado).

promoción (extracto conceptual)
staging corre   ghcr.io/acme/copiloto:2.4.1        (ya probada)
produccion      <<el MISMO digest>>   2.4.1
NO se hace:  "docker build" otra vez para produccion

6 · Errores habituales

1. Reutilizar (mover) un tag ya publicado

Publicar la 2.4.1 y, al detectar un bug, mover el mismo tag al commit del arreglo. Parece cómodo; destruye la trazabilidad.

Mal — reescribir una versión publicada 
git tag -d v2.4.1
git tag v2.4.1                 # ahora apunta a OTRO commit
git push origin v2.4.1 --force # dos artefactos distintos con el mismo nombre
Bien — publicar una versión nueva 
git tag -a v2.4.2 -m "Release v2.4.2 (fix)"
git push origin v2.4.2         # 2.4.1 sigue siendo el mismo artefacto de ayer

Corolario: quitar un tag de un registry o de Git es una operación excepcional, no de rutina. Si tienes que hacerlo a menudo, el problema está en el proceso de release, no en el tag.

2. Usar latest como identidad

latest es una etiqueta que apunta a lo último que publicaste. Es una comodidad para experimentar, no un identificador.

Mal — desplegar por nombre móvil 
docker pull ghcr.io/acme/copiloto:latest
# Si manana cambia latest, tu "rollback" a :latest no vuelve a lo de ayer.
Bien — fijar versión/digest 
docker pull ghcr.io/acme/copiloto:2.4.1
# o, para inmutabilidad total:
docker pull ghcr.io/acme/copiloto@sha256:9f1c...   # esto no puede cambiar

3. Subir el MAJOR por todo

Rebautizar como 2.0.0 cualquier release hace que el número deje de informar.

Mal — MAJOR porque "es una version importante" 
1.4.2  ──▶  2.0.0   (solo se anadio un endpoint compatible)
# Quien consume cree que algo se rompe y posterga la actualizacion por miedo.
Bien — MAJOR solo con incompatibilidad real 
1.4.2  ──▶  1.5.0   (nuevo endpoint compatible)
1.5.0  ──▶  2.0.0   (se elimina /v1 y cambia el esquema de respuesta)

7 · Ejercicio guiado

Objetivo: publicar dos releases de la Copiloto API con SemVer, comprobar cómo la derivación de versiones se comporta y verificar la precedencia entre un prerelease y la versión final.

  1. Paso 1 — Prepara el repositorio y un cambio en main. 
    git switch main && git pull --ff-only
printf '\nGET /health -> {"status":"ok"}\n' >> README.md
git commit -am "feat(api): document /health"
git push origin main
  2. Paso 2 — Publica un prerelease v1.0.0-rc.1. 
    git tag -a v1.0.0-rc.1 -m "Release candidate v1.0.0-rc.1"
git push origin v1.0.0-rc.1
# El workflow de tags publica la imagen 1.0.0-rc.1
  3. Paso 3 — Prueba la precedencia con una herramienta de SemVer. 
    # Con Node disponible, instala el comparador oficial
npx semver 1.0.0-rc.1 1.0.0
# -> 1.0.0   (la final es MAYOR que su candidato)

npx semver -r "^1.0.0" 1.0.0-rc.1 1.0.1
# -> 1.0.1   (el prerelease NO satisface ^1.0.0; la 1.0.1 si)

    Este comportamiento es clave: un rango ^1.0.0 no incluye 1.0.0-rc.1. Los prereleases se «ven» solo si el consumidor los pide explícitamente. Así puedes probar sin que nadie reciba, por accidente, una versión inestable.

  4. Paso 4 — Publica el release final v1.0.0. 
    git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0
gh release list        # aparecen v1.0.0 y v1.0.0-rc.1, en ese orden de precedencia
  5. Paso 5 — Comprueba la coherencia entre tag de Git e imagen. 
    git tag --list "v*"                          # v1.0.0, v1.0.0-rc.1
docker image ls ghcr.io/acme/copiloto        # 1.0.0, 1.0.0-rc.1, 1, 1.0

    Resultado esperado: el mismo número aparece en el tag de Git, el release y la etiqueta de la imagen; 1.0.0 tiene mayor precedencia que 1.0.0-rc.1; y ningún artefacto quedó identificado como latest.

8 · Reto

🎯 Un guardián de versiones

Escribe un workflow que valide y proteja las versiones del repositorio de la Copiloto API. Debe: (1) rechazar cualquier tag que no cumpla estrictamente SemVer (no vale v2.4 ni v2.4.1.tmp); (2) comprobar que la versión del tag es mayor que la del tag anterior y no un retroceso ni un duplicado; y (3) fallar el release si ya existe una imagen con ese mismo número en el registry. Además, decide qué hacer con los prereleases: ¿deben poder publicarse aunque no sean mayores que la última final?

Pista: para validar la forma exacta del semver, una expresión regular o la propia herramienta npx semver dentro del job (npx semver -r "^v?…") te ahorra reinventar la precedencia. Para comparar con el tag anterior, git tag --sort=-v:refname te da el orden correcto de versiones (¡no el alfabético!). Y para detectar duplicados en el registry, gh api sobre el paquete o docker manifest inspect devuelven vacío o error si la etiqueta no existe. Cuida los permissions del workflow y no olvides que los prereleases tienen menor precedencia: tu comparación debe respetarlo.

9 · Resumen

  • MAJOR.MINOR.PATCH: incompatible / feature compatible / fix compatible.
  • Cada incremento pone a cero las partes a su derecha: 1.4.9 → 1.5.0.
  • Una versión publicada es inmutable; si algo falla, se publica una nueva, no se reescribe.
  • 0.y.z es desarrollo inicial: todo puede cambiar hasta el 1.0.0.
  • Los prereleases (-rc.1) tienen menor precedencia y no satisfacen rangos estables; los metadatos (+build) no afectan al orden.
  • La versión es el hilo conductor entre tag de Git, release y etiqueta del artefacto.
  • Para desplegar con garantías, fija el digest, no latest: nombre legible frente a identidad inmutable.

10 · Preguntas frecuentes

¿Qué es exactamente un «breaking change» si mi API solo añade endpoints?

Cualquier cambio que rompa lo que un consumidor ya daba por hecho: eliminar o renombrar un campo, cambiar el tipo de un valor, alterar el código de estado de un endpoint, volver obligatorio un parámetro que era opcional, endurecer una validación. Añadir un endpoint o un campo nuevo es compatible (MINOR); quitar o reinterpretar algo existente es incompatible (MAJOR). Cuando dudes, la prueba es: «¿algún cliente que funcionaba ayer dejará de funcionar hoy?».

¿Cuándo salgo del 0.x?

Cuando la API es lo bastante estable como para prometer que respetarás SemVer. Mientras estés en 0.y.z, formalmente cualquier versión puede romper y los consumidores no tienen garantías. Por eso los 0.x no se usan en producción ajena sin pin exacto. Si la Copiloto API va a recibir clientes reales, el 1.0.0 es una promesa, no una decoración.

¿La versión del software y la del contenedor son lo mismo?

En este curso sí, y es lo deseable: queremos que un único número identifique el release. En la práctica, la imagen base o una dependencia puede actualizarse sin que tu código cambie — eso no obliga a subir tu versión, porque SemVer describe tu contrato. Lo que no debe pasar es que la imagen tenga un nombre distinto al del release: pierdes la correspondencia y, con ella, la trazabilidad.

¿Por qué no usar la fecha como versión (calendario tipo 2026.4.1)?

El versionado por calendario (CalVer) es legítimo para productos donde la fecha comunica más que la compatibilidad. Pero no da la información clave de SemVer: si el cambio rompe compatibilidad. En una API con consumidores, eso es lo más importante que debe comunicar el número. Puedes combinar ambos mundos (por ejemplo, usar el calendario en el build metadata o en el nombre de la imagen y SemVer en la versión pública), pero elige uno como contrato.

¿Cómo evito decidir la versión a mano?

Derivándola del contenido de los commits. Si sigues Conventional Commits, cada tipo de commit implica un incremento: fix → PATCH, feat → MINOR, un BREAKING CHANGE → MAJOR. Herramientas como release-please o semantic-release calculan la siguiente versión, la etiquetan y generan el changelog. Es exactamente la lección que viene a continuación.
