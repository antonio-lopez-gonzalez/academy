Secretos, variables y OIDC

Módulo 4 · Entrega continua 🕐 35 minutos

1 · Introducción

Para desplegar el Copiloto hacen falta credenciales: la contraseña de la base de datos, el rol que la nube debe asumir, el acceso al registry. La tentación histórica fue guardarlas en variables de entorno del servidor o, peor, en el repositorio. Ambos caminos terminan igual: una clave filtrada en un log, en un fork o en el historial de Git, y una brecha.

Esta lección enseña los dos mecanismos que GitHub pone sobre la mesa: Secrets (valores cifrados) y Variables (configuración no sensible), con su alcance por repositorio, organización y entorno. Y, sobre todo, enseña el salto cualitativo del DevOps moderno: OIDC, la técnica para autenticarse en la nube sin guardar ninguna clave de larga vida, obteniendo un token efímero que se valida mediante credenciales federadas.

¿Por qué esta lección existe? Porque una clave estática es una deuda de seguridad que nunca deja de crecer: puede filtrarse, no expira y hay que rotarla a mano. OIDC la sustituye por un intercambio de confianza: GitHub firma un token de pocos minutos y la nube lo acepta si viene del repositorio correcto. Menos secretos que custodiar es menos superficie de ataque.

Nada de secretos en este archivo. Todos los ejemplos usan marcadores (${{ secrets.… }}, ${{ vars.… }}) o valores de mentira. Un secreto real en el curso sería, precisamente, el error que el curso enseña a evitar.

2 · Teoría

Secrets vs Variables: dos naturalezas distintas

La regla es sencilla: si revelarlo haría daño, es un secreto; si solo es configuración, es una variable.

SecretsVariables
Sintaxis${{ secrets.NOMBRE }}${{ vars.NOMBRE }}
AlmacenamientoCifradoTexto claro
En los logsEnmascarado (***)Visible
EjemplosToken de API, contraseña de BDURL, región, nivel de logs
Legible despuésNo (solo se sobrescribe)Sí

Elegir bien no es solo estética: usar una variable para algo sensible lo deja en claro en los logs; usar un secreto para una URL la vuelve invisible y difícil de depurar sin motivo. Y recuerda la lección 1: el nombre puede coincidir en todos los entornos; el valor se resuelve por el entorno del job.

Alcances: organización, repositorio, entorno

Los secretos y variables viven en tres niveles, y el más específico gana:

   Organizacion        ┌───────────────┐  compartido por varios repos
   (org)               │  ORG secrets  │
                       └───────┬───────┘
                               ▼
   Repositorio         ┌───────────────┐  por defecto del repo
   (repo)              │  REPO secrets │
                       └───────┬───────┘
                               ▼
   Entorno             ┌───────────────┐  solo en jobs con ese environment
   (environment)       │   ENV secrets │  ← el mas especifico
                       └───────────────┘

La ventaja de los secretos de entorno es doble: solo se exponen a los jobs que declaran ese entorno (una PR no ve el secreto de producción) y permiten que la misma variable tenga valores distintos en staging y producción.

El problema de las claves de larga vida

El patrón antiguo era crear un usuario de nube con una clave estática y guardarla como secrets.AWS_SECRET_ACCESS_KEY. Problemas:

  • No expira: si se filtra, sigue sirviendo indefinidamente.
  • Hay que rotarla a mano o automatizar rotación, y casi nadie lo hace bien.
  • Es reutilizable: cualquiera con la clave es la identidad, desde cualquier sitio.

OIDC: credenciales federadas y tokens efímeros

Con OpenID Connect, el workflow no guarda clave alguna. En su lugar:

  1. El job pide a GitHub un token OIDC firmado, de vida muy corta (minutos). Para ello necesita el permiso id-token: write.
  2. El token incluye claims como repository, ref y environment: quién es y desde dónde pide entrar.
  3. La nube (AWS, Azure, GCP, Vault…) tiene configurada una relación de confianza federada que dice: «acepto tokens de GitHub de este repo y este entorno».
  4. El paso de despliegue intercambia ese token por credenciales temporales de la nube. Nadie ha custodiado una clave estática.
   runner (job)                GitHub OIDC                 Nube (AWS/Azure/GCP)
   ────────────                ───────────                 ────────────────────
   id-token: write  ──────▶   firma un JWT corto  ──────▶   valida el issuer
                                 (claims: repo,           y comprueba los claims
                                  ref, environment)       (trust policy)
                                     │                           │
                                     └──────── credenciales temporales ◀──┘
                                                (sin claves guardadas)

Analogía: una clave estática es una llave maestra que copias y guardas; si se pierde, cualquiera entra para siempre. OIDC es una acreditación que se emite al momento, dice de qué empresa y qué sala vienes, y caduca en minutos. La nube es el portero que solo abre a quien trae la acreditación correcta y vigente.

Restringe el claim sub: la confianza no debe ser «cualquier cosa de mi repo», sino «este repo, esta rama o este entorno». Por ejemplo, repo:academy/copiloto-api:environment:production solo permite tokens de jobs que declaren el entorno de producción. Es el candado que evita que una PR use las credenciales de producción.

3 · Ejemplo mínimo

El mecanismo mínimo de OIDC: pedir el token y comprobar que existe. Sin nube de por medio, para entender el «contrato» del permiso id-token: write.

.github/workflows/oidc-minimo.yml
name: oidc-minimo

on:
  workflow_dispatch:

permissions:
  id-token: write   # permite pedir un token OIDC firmado por GitHub
  contents: read

jobs:
  probar-oidc:
    runs-on: ubuntu-latest
    steps:
      - name: Pedir un token OIDC a GitHub
        run: |
          TOKEN="$ACTIONS_ID_TOKEN_REQUEST_TOKEN"
          URL="$ACTIONS_ID_TOKEN_REQUEST_URL"
          # El token llega en estas variables de entorno que GitHub inyecta.
          curl -s -H "Authorization: bearer $TOKEN" "$URL&audience=copiloto" > token.json
          echo "Token recibido (no lo imprimas nunca completo)"

Línea por línea:

  1. permissions: id-token: write: sin este permiso, el job no puede pedir token OIDC. Es opt-in a propósito: un job que no despliega no debería poder pedirlo.
  2. contents: read: el resto de permisos se dejan al mínimo. GitHub recomienda denegar por defecto y conceder solo lo necesario.
  3. $ACTIONS_ID_TOKEN_REQUEST_URL y $ACTIONS_ID_TOKEN_REQUEST_TOKEN: variables que GitHub inyecta solo cuando el permiso está concedido. Son el punto de acceso al token.
  4. curl ... audience=...: el audience identifica para quién es el token; la nube lo valida en su trust policy.
  5. Nunca imprimas el token completo: es efímero, pero sigue siendo una credencial. Los ejemplos reales lo usan dentro de las acciones oficiales, no a mano.

En la práctica no pides el token a mano: lo hacen acciones oficiales como aws-actions/configure-aws-credentials o azure/login. Este ejemplo existe para que veas qué hay debajo cuando esas acciones «autentican sin secrets».

4 · Ejemplo real

El despliegue del Copiloto en dos partes. Primero, variables y secretos de entorno para lo que no es credencial de nube (URL, usuario de BD) y el uso del GITHUB_TOKEN para el registry. Después, OIDC para asumir un rol de nube sin claves estáticas.

.github/workflows/cd.yml (parte 1 — config y registry)
name: cd

on:
  push:
    tags: ["v*"]

permissions:
  contents: read
  packages: write

jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v7

      - name: Loguear en GHCR con el GITHUB_TOKEN
        run: echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin

      - name: Desplegar en staging
        env:
          API_BASE_URL: ${{ vars.API_BASE_URL }}     # variable de entorno, no secreta
          DB_USER: ${{ vars.DB_USER }}               # variable de entorno
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}    # secreto de entorno
        run: ./scripts/deploy.sh --env staging

Decisiones y porqués:

  • secrets.GITHUB_TOKEN: token efímero que GitHub genera por ejecución; sirve para el registry sin guardar credenciales. Sus permisos los fija permissions: (packages: write).
  • vars.DB_USER es variable y secrets.DB_PASSWORD es secreto: mismo entorno, naturalezas distintas. El usuario no hace daño si se ve; la contraseña sí.
  • Todo resuelto por entorno: el job de producción usará el mismo YAML, pero sus valores vendrán del entorno production.
.github/workflows/cd.yml (parte 2 — OIDC hacia la nube)
jobs:
  deploy-production:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      id-token: write      # imprescindible para OIDC: sin esto no hay federacion
    steps:
      - uses: actions/checkout@v7

      - name: Autenticar en AWS por OIDC (sin claves de larga vida)
        uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: arn:aws:iam::123456789012:role/copiloto-deploy
          aws-region: eu-west-1
          # No hay aws-access-key-id ni aws-secret-access-key: el rol se asume
          # con el token OIDC que GitHub firma para este job.

      - name: Desplegar en produccion
        run: ./scripts/deploy.sh --env production --image "$IMAGE"
      env:
        IMAGE: ghcr.io/academy/copiloto-api:${{ github.ref_name }}

Lo importante de este job:

  • No hay secrets.AWS_SECRET_ACCESS_KEY: no existe ninguna clave de larga vida que filtrar. La acción obtiene credenciales temporales del rol asumido.
  • id-token: write: el job (y solo este) puede pedir el token OIDC. Los jobs que no despliegan no lo tienen.
  • La confianza la define la nube: en AWS, el rol copiloto-deploy tiene una trust policy que acepta el issuer token.actions.githubusercontent.com y un sub acotado al entorno production del repo.
  • Efímero por diseño: las credenciales caducan al terminar el job. Aunque alguien las capturase, no sirven después.

El mismo patrón, con nombres distintos, existe en todas las nubes: azure/login con federated credentials, google-github-actions/auth con workload identity federation, o HashiCorp Vault con el método de autenticación JWT. Aprendido uno, los demás son traducción.

6 · Errores habituales

Guardar una clave de nube de larga vida

Mal — claves estáticas 
# ❌ Claves de larga vida en secrets: si se filtran, sirven para siempre.
- uses: aws-actions/configure-aws-credentials@v6
  with:
    aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
    aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    aws-region: eu-west-1
Bien — credenciales federadas por OIDC 
# ✅ No hay clave guardada: el rol se asume con un token OIDC efimero.
permissions:
  id-token: write
steps:
  - uses: aws-actions/configure-aws-credentials@v6
    with:
      role-to-assume: arn:aws:iam::123456789012:role/copiloto-deploy
      aws-region: eu-west-1

Imprimir un secreto «para depurar»

Mal — volcarlo en los logs 
# ❌ Los logs son permanentes y visibles para quien tenga acceso al repo.
echo "El token es: $DB_PASSWORD"
Bien — comprobar sin revelar 
# ✅ Se comprueba que existe, sin exponer su valor.
if [ -z "$DB_PASSWORD" ]; then
  echo "DB_PASSWORD no esta definido" >&2
  exit 1
fi
echo "Credenciales presentes (valor oculto)"

Usar un secreto global donde bastaba uno de entorno

Mal — un secreto para todo 
# ❌ Un secreto de repositorio lo ve cualquier job, incluido un test de PR.
- run: ./deploy.sh --env production
  env:
    DB_PASSWORD: ${{ secrets.DB_PASSWORD }}   # secreto de repositorio
Bien — secreto acotado al entorno 
# ✅ El secreto de entorno solo lo ve el job que declara ese entorno.
environment: production
steps:
  - run: ./deploy.sh --env production
    env:
      DB_PASSWORD: ${{ secrets.DB_PASSWORD }}   # secreto de entorno production

Dejar el permiso id-token abierto a todos los jobs

Mal — permiso para todo el workflow 
# ❌ Cualquier job puede pedir un token OIDC, incluso los que no despliegan.
permissions:
  id-token: write
  contents: read
Bien — permiso solo en el job que despliega 
# ✅ id-token: write se concede unicamente al job de despliegue.
jobs:
  tests:
    permissions:
      contents: read
  deploy:
    permissions:
      id-token: write

7 · Ejercicio guiado

Objetivo: dejar un job de despliegue autenticándose por OIDC, sin ninguna clave de larga vida, y comprobar que el token solo se emite cuando procede.

  1. Paso 1: prepara la confianza en la nube (aquí, en AWS). Crea un rol con una trust policy que acepte el issuer de GitHub y acote el repositorio y el entorno: 
    aws iam create-role --role-name copiloto-deploy \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:academy/copiloto-api:environment:production"
        }
      }
    }]
  }'

    Resultado esperado: solo un job que declare el entorno production en ese repositorio podrá asumir el rol. Una PR no puede.

  2. Paso 2: en el workflow, concede el permiso y usa la acción oficial: 
    permissions:
  id-token: write
  contents: read

jobs:
  deploy-production:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: arn:aws:iam::123456789012:role/copiloto-deploy
          aws-region: eu-west-1
      - name: Confirmar identidad asumida
        run: aws sts get-caller-identity

    Resultado esperado: aws sts get-caller-identity devuelve el ARN del rol, con credenciales temporales. No hay ningún secrets.AWS_* en el workflow.

  3. Paso 3 (verificación negativa): elimina id-token: write y vuelve a lanzar. El step de la acción debe fallar al no poder obtener token OIDC. Vuelve a añadirlo. Esto demuestra que el permiso es la puerta de entrada: sin él, no hay federación.

  4. Paso 4 (verificación de scope): intenta asumir el rol desde un job que declare el entorno staging (o sin entorno). Debe fallar la asunción, porque el sub de la trust policy exige environment:production. Ese fallo es la prueba de que la confianza está bien acotada.

  5. Paso 5: documenta en el README del repositorio cómo se configura la confianza federada (issuer, audiencia, sub). No incluyas identificadores sensibles reales; describe el patrón. Resultado esperado: cualquier compañero puede reproducir la configuración sin pedirte la clave, porque no hay clave.

8 · Reto

🎯 Un cliente OIDC propio y mínimo privilegio

Escribe un script que, sin acciones de terceros, pida el token OIDC a GitHub, decodifique su payload y valide los claims (repository, ref, environment) antes de usarlo. Después, define dos roles con permisos distintos —uno de solo lectura para staging, otro de escritura para producción— y demuestra con logs que un job de staging no puede realizar operaciones de producción aunque intente asumir el rol equivocado.

Pista: el payload del token es un JWT; su parte central está en base64url y se decodifica con base64 -d. Recuerda que el token se obtiene con curl a $ACTIONS_ID_TOKEN_REQUEST_URL y el Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN. Para los dos roles, la diferencia entre «no puede» y «puede» está en la trust policy y en las políticas de permisos: hazlas explícitas y documenta por qué cada claim importa.

9 · Resumen

  • Secrets = cifrados y enmascarados; Variables = configuración en claro. Si revelarlo hace daño, es un secreto.
  • Ambos se resuelven por entorno: es la forma de que una PR no vea los secretos de producción y de que el mismo nombre valga en cada destino.
  • Las claves de larga vida son deuda de seguridad: no expiran, hay que rotarlas y se reutilizan.
  • OIDC las sustituye: el job pide un token efímero (id-token: write) y la nube lo acepta si los claims encajan con su trust policy.
  • Acota siempre el claim sub a repositorio y entorno; concede id-token: write solo al job que despliega.
  • GITHUB_TOKEN cubre el registry y otras APIs sin guardar credenciales, con los permisos que declare permissions:.

10 · Preguntas frecuentes

Si OIDC no guarda clave, ¿qué guarda la nube?

Una relación de confianza, no una credencial. La nube registra que confía en el emisor OIDC de GitHub (token.actions.githubusercontent.com) bajo ciertas condiciones (repositorio, rama, entorno). No hay secreto compartido que custodiar: la prueba se genera en cada ejecución y caduca.

¿OIDC sirve para cualquier proveedor?

Casi todos los grandes lo soportan: AWS, Azure, Google Cloud, HashiCorp Vault, incluso PyPI. Cada uno tiene su acción oficial y su forma de declarar la confianza, pero el concepto es idéntico. Si un proveedor no lo soporta, aún puedes usar secretos cifrados bien acotados; pero OIDC es la opción por defecto en 2024 en adelante.

¿Puedo ver un secreto después de guardarlo?

No. GitHub solo permite sobrescribirlo; nunca muestra su valor. Por eso una buena práctica es documentar qué es cada secreto y dónde se genera, sin exponerlo. Si lo pierdes, lo regeneras y lo actualizas.

¿Por qué mi secreto aparece como *** incluso si lo construyo en partes?

GitHub intenta enmascarar los valores de los secretos en los logs, incluidas variantes construidas por concatenación. Aun así, no es infalible (por ejemplo, transformaciones con base64 pueden escaparse). La lección: no imprimas secretos nunca; el enmascaramiento es una red, no una garantía.

¿Qué pasa con pull_request_target y los secretos?

Ese evento ejecuta el workflow del código base pero con los permisos y secretos del repositorio, lo que históricamente ha filtrado credenciales desde PRs de forks maliciosos. La regla: usa id-token: write solo en jobs de despliegue protegidos por entorno, nunca en jobs que ejecutan código de una PR sin revisar. La lección 3 añade la capa de aprobación que cierra este hueco.
