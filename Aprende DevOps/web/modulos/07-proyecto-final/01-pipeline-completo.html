Pipeline completo

Módulo 7 · Proyecto final: el pipeline del Copiloto 🕐 45 minutos

1 · Introducción

Durante seis módulos has construido las piezas por separado: un CI que prueba, un build que publíca una imagen, un CD que despliega. En este módulo final las ensamblamos en un solo pipeline que va del git push a la aplicación corriendo, sin pasos manuales y sin recompilar nada por el camino. Ese es el objetivo de Publicar el Copiloto.

El problema del ensamblaje no es escribir más YAML, sino no escribir YAML de más. Lo fácil es que ci.yml tenga su copia de «lint + test + build», y que publish.yml tenga otra copia parecida, y que deploy.yml vuelva a construir la imagen «por si acaso». El resultado es un collar de workflows que se desincronizan: arreglas un test en uno y se te olvida en el otro. Esta lección trata de reutilizar y encadenar, no de copiar.

¿Por qué esta lección existe? Porque el trabajo de un ingeniero de plataforma no es escribir pipelines largos, es escribir pipelines cortos, componibles y de una sola fuente de verdad. Un pipeline que se mantiene duplicado se pudre; uno que reutiliza se mantiene barato. Aquí aprendes la mecánica que hace posible el resto del módulo.

La regla de oro que gobierna todo el módulo: el artefacto que se prueba es el mismo que se construye, es el mismo que se despliega. En cuanto un workflow reconstruye la imagen «para desplegarla», has roto la trazabilidad: ya no sabes si lo que corre en producción es lo que pasó los tests.

2 · Teoría

Las tres fases y sus fronteras

Un pipeline completo tiene tres fases con fronteras claras. Cada frontera marca dónde termina algo efímero (el código fuente, un runner) y empieza algo inmutable (un artefacto).

FaseEntradaSalidaCuándo corre
CI (integración continua)Un commit en el repositorioUn veredicto: pasa o no pasaEn cada push y cada pull_request
Build (publicar artefacto)Un commit que ya pasó CIUna imagen inmutable en un registry, identificada por digestCuando se crea una release (un tag)
CD (entrega continua)Un artefacto por digestLa aplicación corriendo en un entornoAutomático a staging; a producción tras aprobación

El flujo completo, de izquierda a derecha, con los dos hechos inmutables marcados:

  git push                CI: lint + test           build                 CD
  ────────▶  commit  ────────────────▶  ✔  ────────────────▶  📦 imagen  ──────────▶  entornos
              │          (efímero)                       (inmutable: @sha256:…)
              │                                              │
              └─ un push nuevo cancela el run viejo           └─ el MISMO digest viaja a
                 (el código cambia)                              staging y a producción
                                                                 (el artefacto NO se reconstruye)

Analogía: una cadena de montaje con control de calidad. CI es el operario que revisa las piezas al entrar; build es la máquina que estampa el producto terminado con un número de serie (el digest); CD es el camión que reparte ese producto. Nadie vuelve a fabricar el coche en la puerta del concesionario.

Tres archivos, no uno gigante

¿Por qué separar ci.yml, publish.yml y deploy.yml en vez de meterlo todo en un archivo?

  • Disparadores distintos. CI corre en pull_request; el build solo cuando hay un tag de release; el deploy cuando existe un artefacto. Un solo archivo tendría un on: con tres ramas y if: por todas partes.
  • Permisos distintos. CI no necesita escribir en el registry; el deploy «de producción» necesita un environment protegido. Aislar los permisos es seguridad (lo verás en la lección 4).
  • Reutilizable. El CI debe poder llamarse tanto desde un PR como desde el build. Si vive en su propio archivo reusable, se llama; si está embebido, se copia.
  • Fácil de razonar. Un archivo con una responsabilidad se depura leyéndolo; un archivo de 300 líneas con todo, no.

Ojo con un mito: un job de un workflow no puede depender con needs de un job de otro workflow. needs funciona dentro del mismo archivo. Para encadenar archivos hay tres mecanismos: workflows reutilizables (workflow_call, llamados con uses:), eventos como workflow_run, y compartir artefactos/artefactos del registry entre ellos.

Reutilización: workflow_call

Un workflow reutilizable es un YAML normal al que se le añade on: workflow_call y que declara sus inputs, outputs y secrets. Otro workflow lo invoca como si fuera una función, a nivel de job:

  publish.yml                          ci.yml (reusable)
  ───────────                          ────────────────
  jobs:                                on:
    ci:                                  workflow_call:
      uses: ./.github/workflows/ci.yml     inputs:
      with:                                  python-version: {…}
        python-version: "3.12"               outputs:
      secrets: inherit                         coverage: {…}
                                           jobs:
                                             lint: …
                                             test: …

Ventajas concretas: una sola definición de «qué es pasar CI»; el llamador solo aporta parámetros; y los outputs permiten pasar datos (por ejemplo, el porcentaje de cobertura o el digest de la imagen) de vuelta al flujo que llamó.

Encadenado: dos formas de «lo siguiente»

¿Cómo sabe el build que el CI ha pasado? No puede usar needs a través de archivos. Las dos soluciones honestas:

MecanismoCómo funcionaCuándo usarlo
Llamada directa (uses:) El workflow que publica llama al CI como primer job; si el CI falla, el build no arranca Cuando el build debe esperar al CI en el mismo run (lo más simple y trazable)
Evento (workflow_run o tag) El build se dispara cuando el CI termina o cuando se crea un tag; consulta si el CI fue verde Cuando quieres desacoplar: builds disparados por releases, reintentos independientes

Regla práctica: usa llamada directa para «CI → build» (mismo run, una sola verdad) y tags para «decidir qué versión publicar». En el Copiloto, un tag v1.4.2 dispara publish.yml, que llama al CI reusable y, solo si es verde, construye y publica.

Idempotencia y cancelación

Dos detalles que hacen que un pipeline se sienta profesional:

  • concurrency: si empujas tres commits seguidos, no quieres tres CIs compitiendo por los mismos recursos. Un grupo de concurrencia con cancel-in-progress: true en CI deja solo el más reciente: el código viejo ya no importa.
  • Reproducibilidad: el build no debe depender de cuándo corre. Fija versiones, usa caché correctamente y no «arregles» nada a mano dentro de un runner.

3 · Ejemplo mínimo

El átomo de la reutilización: un workflow con workflow_call que recibe un parámetro y devuelve un resultado, y otro que lo llama. Sin Docker, sin despliegue: solo la mecánica de «función».

.github/workflows/greet.yml
name: greet
on:
  workflow_call:
    inputs:
      who:
        description: A quien saludar
        required: true
        type: string
    outputs:
      greeting:
        description: El saludo generado
        value: ${{ jobs.say.outputs.message }}

jobs:
  say:
    runs-on: ubuntu-latest
    outputs:
      message: ${{ steps.build.outputs.text }}
    steps:
      - id: build
        run: echo "text=Hola, ${{ inputs.who }}" >> "$GITHUB_OUTPUT"
      - run: echo "El reusable dice: ${{ steps.build.outputs.text }}"

Y quien lo usa, como si fuera una función más:

.github/workflows/caller.yml
name: caller
on: [push]

jobs:
  greet:
    uses: ./.github/workflows/greet.yml
    with:
      who: Copiloto

  after:
    needs: greet
    runs-on: ubuntu-latest
    steps:
      - run: echo "El reusable devolvio: ${{ needs.greet.outputs.greeting }}"

Línea por línea:

  1. on: workflow_call convierte el archivo en reutilizable. No tiene push ni pull_request: solo se ejecuta cuando alguien lo llama.
  2. inputs con type y required: el contrato de la función. El llamador debe aportar who; si falta, el run falla antes de gastar minutos.
  3. outputs.value: expone un valor de vuelta al llamador. Debe apuntar a un output de job (jobs.say.outputs.message), que a su vez viene de un output de step.
  4. echo "text=..." >> "$GITHUB_OUTPUT": la forma canónica de que un step devuelva un valor. (Sin esto, steps.build.outputs.text estaría vacío.)
  5. uses: ./.github/workflows/greet.yml: la llamada. Con ./ se refiere a un workflow del mismo repositorio; con owner/repo/.github/…@ref se llama a uno de otro repositorio.
  6. needs: greet: el job after consume el output. Aquí sí funciona needs, porque ambos están en el mismo archivo llamador.

Un detalle que sorprende: los env definidos a nivel de workflow en el llamador no se propagan al reusable, y viceversa. La comunicación es explícita: inputs hacia dentro, outputs hacia fuera. Eso es una ventaja, no un estorbo: la función no depende de variables invisibles.

4 · Ejemplo real

Así queda el pipeline completo del Copiloto: ci.yml (reusable), publish.yml (build) y deploy.yml (CD). Empieza por el CI reutilizable, que es lo que ambos llaman.

1) ci.yml — la definición única de «pasar CI»

.github/workflows/ci.yml
name: CI

on:
  workflow_call:
    inputs:
      python-version:
        type: string
        default: "3.12"
    outputs:
      coverage:
        description: Cobertura alcanzada por los tests
        value: ${{ jobs.test.outputs.coverage }}

# Un push nuevo sobre el mismo ref cancela el CI obsoleto.
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7c6903cd8c0fde910a37f88322edcfb5dd907a8 # v5.0.0
      - uses: astral-sh/setup-uv@v10
        with:
          enable-cache: true
      - run: uv run ruff check .
      - run: uv run mypy app

  test:
    runs-on: ubuntu-latest
    outputs:
      coverage: ${{ steps.cov.outputs.percent }}
    steps:
      - uses: actions/checkout@v7c6903cd8c0fde910a37f88322edcfb5dd907a8 # v5.0.0
      - uses: astral-sh/setup-uv@v10
        with:
          enable-cache: true
      - run: uv run pytest --cov=app --cov-report=term --cov-report=xml
      - id: cov
        run: |
          PCT=$(uv run coverage report --format=total)
          echo "percent=$PCT" >> "$GITHUB_OUTPUT"

Qué mira cada decisión:

  • Es reusable (workflow_call): no tiene push propio. Lo llaman tanto un PR como el build.
  • concurrency con cancel-in-progress: true: empujar cinco commits no lanza cinco CIs completos, solo el último.
  • permissions: contents: read: el CI solo lee el repo. Nada de escribir en el registry ni en el entorno (mínimo privilegio).
  • outputs.coverage: el llamador podrá aplicar un gate («cobertura ≥ 80 %») sin volver a ejecutar los tests.
  • Las acciones van pinneadas por SHA (actions/checkout@v7c690… # v5.0.0): inmutables. Lo profundizamos en la lección 4.

2) publish.yml — llama al CI y, si pasa, construye

.github/workflows/publish.yml
name: Publish

on:
  push:
    tags: ["v*"]          # v1.4.2 despierta el build; un push normal no.

env:
  IMAGE: ghcr.io/academy/copiloto-api

jobs:
  # 1) Llama al MISMO CI que corre en los PRs. Si falla, no hay imagen.
  ci:
    uses: ./.github/workflows/ci.yml
    with:
      python-version: "3.12"

  build:
    needs: ci             # el artefacto solo existe si el CI fue verde
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write     # publicar en GHCR
      attestations: write
      id-token: write     # atestaciones y firma
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v7c6903cd8c0fde910a37f88322edcfb5dd907a8 # v5.0.0
      - uses: docker/setup-buildx-action@v4
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build y push
        id: push
        uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ${{ env.IMAGE }}:${{ github.ref_name }}
          provenance: mode=max
      - name: Atestacion de procedencia
        uses: actions/attest-build-provenance@v4
        with:
          subject-name: ${{ env.IMAGE }}
          subject-digest: ${{ steps.push.outputs.digest }}
          push-to-registry: true
      - name: Deja el digest a la vista
        run: |
          {
            echo "### Imagen publicada"
            echo ""
            echo "- Imagen: ${{ env.IMAGE }}"
            echo "- Digest: ${{ steps.push.outputs.digest }}"
          } >> "$GITHUB_STEP_SUMMARY"

Lo esencial: el tag v1.4.2 es la señal de release; el job ci reutiliza la definición única; y el build publica una imagen con provenance: mode=max y una atestación que la ata al workflow. El outputs.digest es el identificador canónico que usará el CD.

Por qué needs: ci y no re-ejecutar tests dentro del build: porque el build es publicar, no verificar. Y por qué no confiar «en que el tag ya venía de main»: un tag puede apuntar a cualquier commit. El CI se ejecuta sobre el commit del tag; si ese commit no era verde, la imagen no se publica.

3) deploy.yml — el CD, disparado por la misma release

.github/workflows/deploy.yml
name: Deploy

on:
  push:
    tags: ["v*"]          # la misma release que dispara el build

env:
  IMAGE: ghcr.io/academy/copiloto-api

jobs:
  staging:
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.copiloto.dev
    steps:
      - run: ./scripts/deploy.sh --image "$IMAGE" --env staging
        env:
          IMAGE_REF: ${{ env.IMAGE }}:${{ github.ref_name }}

  production:
    needs: staging
    runs-on: ubuntu-latest
    environment:
      name: production      # revisores obligatorios: el job se pausa aqui
      url: https://copiloto.dev
    steps:
      - run: ./scripts/deploy.sh --image "$IMAGE" --env production
        env:
          IMAGE_REF: ${{ env.IMAGE }}:${{ github.ref_name }}

El encadenado aquí es por evento (el tag): build y deploy corren en paralelo lanzados por la misma release, cada uno con su responsabilidad. En la lección 2 afinaremos esto para promover el mismo digest y no una etiqueta.

Fíjate en que deploy.yml no construye nada. Solo descarga y despliega. Ese «no construir» es lo que garantiza la regla de oro. Si el deploy tuviera un docker build, estaríamos desplegando un artefacto distinto del que se probó.

6 · Errores habituales

Creer que needs cruza workflows

Mal — needs apuntando a otro archivo 
# deploy.yml (❌) intenta esperar al build de publish.yml
jobs:
  deploy:
    needs: build     # FALLA: ese job no existe en ESTE workflow
Bien — llamada directa o evento 
# ✅ Opcion A: mismo archivo, se llama al CI y se espera.
jobs:
  ci:
    uses: ./.github/workflows/ci.yml
  build:
    needs: ci
# ✅ Opcion B: distinto archivo, encadenado por evento (tag).
on:
  push:
    tags: ["v*"]

Reconstruir la imagen en el despliegue

Mal — CD que vuelve a construir 
# ❌ deploy.yml: crea un artefacto NUEVO. Ya no es el que paso CI.
docker build -t copiloto:prod .
docker push copiloto:prod
Bien — desplegar el artefacto ya publicado 
# ✅ CD solo consume lo que el build ya publico, por su digest.
docker pull ghcr.io/academy/copiloto-api@sha256:9b1c…
./scripts/deploy.sh --image ghcr.io/academy/copiloto-api@sha256:9b1c… --env production

Duplicar el CI en cada workflow

Mal — dos copias que se desincronizan 
# pr.yml                        # publish.yml (❌) otra copia de lo mismo
jobs:                           jobs:
  test:                           test:
    steps:                          steps:
      - run: pytest                   - run: pytest   # se arregla en uno y no en el otro
Bien — una definición, dos llamadores 
# ✅ ci.yml define; pr.yml y publish.yml lo llaman.
on: { workflow_call: {} }        # ci.yml
# ---
jobs:
  ci:
    uses: ./.github/workflows/ci.yml   # en pr.yml y en publish.yml

No cancelar runs obsoletos

Mal — sin concurrencia 
# ❌ Cinco push seguidos = cinco CIs completos compitiendo.
# (Sin bloque concurrency)
Bien — cancela lo viejo 
# ✅ El run anterior del mismo ref se cancela; solo vive el ultimo commit.
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

7 · Ejercicio guiado

Objetivo: montar el esqueleto del pipeline completo del Copiloto en un repositorio de práctica y comprobar, en local con act, que el build se niega a publicar si el CI falla.

  1. Paso 1: crea el repositorio y los tres archivos (vacíos de momento): 
    gh repo create academy/copiloto-api --private --clone
cd copiloto-api
mkdir -p .github/workflows scripts

    Resultado esperado: el repo clonado, con las carpetas creadas. (gh ya lo configuraste en el Módulo 0.)

  2. Paso 2: copia el ci.yml reusable del ejemplo real y confirma que el YAML es válido: 
    uv run --with pyyaml python - <<'PY'
import yaml, pathlib
for f in pathlib.Path(".github/workflows").glob("*.yml"):
    yaml.safe_load(f.read_text())
    print("OK", f)
PY

    Resultado esperado: OK .github/workflows/ci.yml. Si hay un error de indentación, el analizador lo señala con la línea.

  3. Paso 3: haz que el CI «falle» a propósito para ver la barrera. Añade temporalmente un test que falla: 
    echo 'def test_deliberadamente_roto(): assert False' >> tests/test_smoke.py
git add -A && git commit -m "chore(ci): test que falla a proposito"
git push

    Resultado esperado: en la pestaña Actions, el run Publish muestra el job ci en rojo y el job build saltado (no arranca: needs: ci no se cumplió). Comprueba con:

    gh run list --workflow publish.yml --limit 5
gh run view --log-failed
  4. Paso 4: revierte el test roto y crea un tag para disparar una release real: 
    git revert --no-edit HEAD && git push
git tag v0.1.0 && git push origin v0.1.0

    Resultado esperado: el CI pasa en verde; el build publica la imagen y el paso «Deja el digest a la vista» escribe el sha256:… en el resumen del run (míralo en la pestaña del run).

  5. Paso 5 (local, con act): simula el disparador del tag sin gastar minutos de GitHub: 
    act -W .github/workflows/publish.yml push \
  --eventpath <(echo '{"ref":"refs/tags/v0.1.0","ref_name":"v0.1.0"}') \
  --dryrun

    Resultado esperado: act lista los jobs que ejecutaría (ci y build) sin ejecutarlos. Confirma que el disparador y el encadenado están bien declarados antes de gastar un run real.

Si act no reproduce el disparador de tags exactamente (su soporte de eventos es aproximado), apóyate en el --dryrun para leer el grafo de jobs y valida el resto en un repositorio de verdad. El objetivo del paso 5 es entender el evento, no sustituir a GitHub.

8 · Reto

🎯 Un solo llamador, tres entornos, cero duplicación

Refactoriza el pipeline del Copiloto para que exista un único workflow “entrada” (pipeline.yml) que, según el evento, llame a los reutilizables necesarios: en un PR llama solo al CI; al publicar un tag llama al CI, al build y al CD. El CI no debe definirse dos veces en ningún sitio, y el build debe consumir el resultado del CI (por ejemplo, abortar si la cobertura por debajo del umbral) sin repetir los tests. Además, haz que el digest de la imagen viaje como output del build hasta el job de CD, de forma que el despliegue use el digest y nunca la etiqueta del tag.

Pista: encadena archivos con uses: y propaga datos por outputs (jobs.build.outputs.digest → needs.build.outputs.digest → env del job de CD). Para el gate de cobertura, el output del CI (needs.ci.outputs.coverage) se compara en un if o en un paso de run que salga con error. Pregúntate: si mañana quieres reutilizar el CI en otro repositorio, ¿qué tendría que ser configurable — la versión de Python, el umbral, la ruta de la app — y qué debería seguir siendo fijo?

9 · Resumen

  • Un pipeline completo tiene tres fases con fronteras claras: CI (veredicto), build (artefacto inmutable) y CD (entorno).
  • La regla de oro: el artefacto que se prueba es el que se construye y el que se despliega. Nunca se reconstruye en CD.
  • Tres archivos (ci.yml, publish.yml, deploy.yml) con disparadores y permisos distintos; no un archivo gigante.
  • needs no cruza archivos: para encadenar, workflows reutilizables (workflow_call + uses) o eventos (workflow_run, tags).
  • Un reutilizable comunica por inputs y outputs; el env no se hereda.
  • concurrency con cancel-in-progress: true evita runs obsoletos; fija el último commit como el que importa.
  • El digest es la identidad inmutable del artefacto; la etiqueta del tag puede moverse.

10 · Preguntas frecuentes

¿Por qué no un solo workflow con todo dentro?

Porque tendría un on: con varios eventos y un montón de if para que cada job solo corriera cuando toca; además mezclaría permisos (leer para el CI, escribir en el registry para el build, entorno protegido para el deploy) y sería imposible reutilizarlo desde otro flujo. Tres archivos con una responsabilidad cada uno se leen, se depuran y se reutilizan mucho mejor. La regla es responsabilidad única, igual que en el código.

¿Un workflow reutilizable puede llamar a otro?

Sí. Se llama anidar workflows y se permiten hasta 10 niveles de profundidad, con un máximo de 50 workflows reutilizables distintos por run (contando todo el árbol de llamadas). Es potente —pipeline.yml → ci.yml → lint.yml— pero no lo abuses: si necesitas cinco niveles, probablemente convenga fusionar algunos. La regla práctica es que un reusable haga una cosa.

¿Puedo pasar secretos a un workflow reutilizable?

Sí, de dos formas: declarándolos explícitamente bajo on.workflow_call.secrets y pasándolos desde el llamador, o con secrets: inherit para pasar todos los del repositorio. La primera es más segura y legible (el reusable solo ve lo que necesita). Recuerda que el GITHUB_TOKEN no hace falta pasarlo: cada job tiene el suyo, con los permisos que declare. Y nunca metas secretos en inputs: los inputs quedan visibles en los logs y en la definición del workflow.

¿Debo desplegar por tag o por workflow_run?

Con tags ganas claridad: la release v1.4.2 es el disparador, y el nombre de la imagen coincide con la versión. Con workflow_run ganas automatismo (build y deploy se encadenan solos sin release), pero debes consultar si el run del que dependes acabó en verde, con github.event.workflow_run.conclusion == 'success'. En el Copiloto usamos tags porque la versión es un concepto de negocio que queremos explícito. Lo importante en ambos casos: que el CD consuma un artefacto ya construido, no uno nuevo.

¿Cómo evito que un build largo bloquee todo?

Con dos herramientas: concurrency para cancelar runs obsoletos del mismo ref, y needs / jobs paralelos para que lint y test corran a la vez y el build espere solo a lo imprescindible. También ayuda cachear dependencias (Módulo 2) y capas de Docker (Módulo 3). Un pipeline del Copiloto sano debería resolver CI en pocos minutos; si tarda veinte, mira qué se puede paralelizar antes de optimizar el build.
