Registries y tagging inmutable (GHCR)

Módulo 3 · Build y artefactos 🕐 35 minutos

1 · Introducción

En la lección anterior construimos la imagen de la Copiloto API… y se quedó dentro del runner. Cuando el job termina, la máquina se destruye y la imagen con ella. Para que ese artefacto sirva de algo tiene que salir del runner y guardarse en algún sitio donde los entornos (staging, producción, tus compañeros, el clúster) puedan descargarlo. Ese sitio es un registry.

Pero «publicar» no es solo un docker push. La pregunta que decide si tu entrega es confiable es otra: ¿con qué etiqueta? Si publicas cada commit como latest, acabas de destruir la trazabilidad: nadie sabrá qué versión está corriendo. En esta lección aprendemos a publicar en GitHub Container Registry (ghcr.io) y, sobre todo, a etiquetar de forma inmutable: una etiqueta, un commit, un artefacto.

¿Por qué existe el concepto de registry? Porque una imagen no se «envía» por correo. El registry es un servicio de almacenamiento direccionable por contenido: guarda las capas una sola vez, deduplica, y te deja referenciar cada imagen por etiqueta (cómoda pero mutable) o por digest (fea pero incorruptible). Entender esa dualidad es entender el despliegue seguro.

Antes de seguir: esta lección asume la imagen multi-stage de Docker en CI. Aquí no cambiamos el build; solo añadimos login, etiquetas y push.

2 · Teoría

Qué es un registry y qué guarda de verdad

Un registry es un catálogo de imágenes organizado en repositorios, cada uno con múltiples etiquetas (tags). Docker Hub, GitHub Container Registry, Amazon ECR o Google Artifact Registry son registries. Todos hablan el mismo protocolo (OCI/Distribution), por lo que docker push funciona igual contra cualquiera.

Lo que el registry almacena no es «una imagen» como un archivo: guarda blobs (capas y metadatos) direccionados por su hash de contenido, y un manifiesto que los referencia. Por eso dos etiquetas que apuntan a la misma imagen no duplican los datos, y por eso un digest identifica con precisión absoluta un contenido.

ghcr.io/acme/copiloto-api (repositorio de la imagen) │ ├── :main ──┐ ├── :sha-4f2a1c9 ──┼──► manifiesto ──► digest sha256:9b1c... ├── :1.4.2 ──┤ │ └── :latest ──┘ └─► capas (blobs) compartidas y deduplicadas Etiqueta = puntero MUTABLE (la puedes mover) -> comoda, peligrosa Digest = huella INMUTABLE del contenido -> fea, segura

Etiqueta frente a digest: la distinción que lo cambia todo

Una etiqueta es un alias que apunta a un manifiesto. Nada impide que mañana :latest apunte a un contenido distinto: por eso quien despliega «por latest» no sabe qué está desplegando. Un digest, en cambio, se deriva del contenido: si una sola capa cambia, el digest cambia. Es la diferencia entre «la carpeta donde guardo las cosas» y «el número de serie».

Etiqueta (:1.4.2)Digest (@sha256:9b1c…)
LegibilidadAlta (habla de versiones)Baja (parece ruido)
ReproducibleNo (puede moverse)Sí (identifica contenido exacto)
Se puede reutilizarSí, y ahí está el riesgoNo; es único por construcción
Uso recomendadoDesarrollo, búsqueda, promociónDespliegue y auditoría

Analogía — el número de serie: la etiqueta :latest es la etiqueta «Nuevo» en el escaparate: cambia sin avisar. El digest es el número de serie grabado en el chasis: identifica ese coche y solo ese. Para vender (buscar, promocionar) usas el nombre comercial; para reclamar una garantía (auditar, desplegar) usas el número de serie.

Tagging inmutable: una etiqueta, un contenido, para siempre

Tagging inmutable significa adoptar la regla de que una etiqueta de release nunca se mueve. En la práctica:

  • Por commit: sha-4f2a1c9 (o sha-4f2a1c9… largo) identifica exactamente el estado del repositorio que produjo la imagen.
  • Por versión: 1.4.2, 1.4 y 1.4.2-rc.1 desde una etiqueta Git v1.4.2, siguiendo SemVer (lo viste en el Módulo 1).
  • Por digest: el registro guarda el sha256:… y todo consumo posterior lo hace contra ese digest.

La regla de oro del módulo: el mismo artefacto que se prueba es el que se despliega. Si publicas por commit y despliegas ese mismo digest, la cadena es perfecta. Si reconstruyes por entorno, o despliegas :latest, la cadena se rompe.

GHCR y la autenticación con GITHUB_TOKEN

GitHub Container Registry (ghcr.io) vive dentro de tu propia organización de GitHub. Su ventaja para CI es enorme: no necesitas crear ni guardar credenciales. El workflow recibe un GITHUB_TOKEN efímero, generado por rodamiento y válido solo durante el job, al que concedes permisos explícitos:

permissions:
  contents: read     # leer el repositorio (checkout)
  packages: write    # publicar en ghcr.io

La ruta del paquete se construye con el propietario y el repositorio: ghcr.io/<owner>/<repo>. Ojo con un detalle que muerde a mucha gente: los nombres de imagen deben ir en minúsculas. Si tu repositorio tiene mayúsculas (AcmeAPI), ghcr.io/AcmeAPI/... es un error; hay que normalizarlo.

¿Y para empujar a otro repositorio o registry? GITHUB_TOKEN solo alcanza el repositorio del workflow. Publicar en un paquete de otra organización, en Docker Hub o en ECR requiere un secret con un PAT, una GitHub App o credenciales cloud (idealmente vía OIDC, sin claves de larga vida — llega en el Módulo 4). Regla que no te saltarás: ninguna credencial en el repositorio.

3 · Ejemplo mínimo

El workflow más pequeño que publica la imagen en GHCR con una etiqueta inmutable por commit. Tres pasos nuevos respecto de la lección 1: permisos, login y push: true.

.github/workflows/publish.yml
name: publish

on:
  push:
    branches: [main]

jobs:
  publish:
    runs-on: ubuntu-latest
    # El GITHUB_TOKEN es efimero y hereda EXACTAMENTE estos permisos:
    permissions:
      contents: read     # checkout del codigo
      packages: write    # escritura en ghcr.io
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4

      # Login contra ghcr.io usando el token del propio workflow.
      # No hay secrets que crear: github.actor es el usuario del run.
      - name: Login en GHCR
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Publicamos con DOS etiquetas: el commit (inmutable) y una
      # de referencia por rama (comoda, pero NO para desplegar).
      - name: Build y push
        id: push
        uses: docker/build-push-action@v7
        with:
          context: .
          target: runtime
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
            ghcr.io/${{ github.repository }}:main

      # El digest es la identidad real de lo publicado: lo imprimimos
      # y quedara tambien como output del step.
      - name: Resumen del artefacto
        run: |
          echo "digest publicado: ${{ steps.push.outputs.digest }}"
          docker buildx imagetools inspect \
            ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
  • permissions: packages: write: sin esto, el GITHUB_TOKEN es de solo lectura para paquetes y el push falla con denied.
  • username: github.actor + password: GITHUB_TOKEN: el patrón de autenticación para GHCR. El token lo inyecta GitHub; no lo escribes tú.
  • push: true: a diferencia de la lección 1, aquí la imagen sale del runner hacia ghcr.io.
  • sha-${{ github.sha }}: la etiqueta inmutable. Cada commit tendrá la suya y no se moverá nunca.
  • outputs.digest: el identificador canónico de lo publicado. Es lo que guardarás para desplegar por digest en el Módulo 4.

Etiquetas cortas para humanos, largas para máquinas: sha-4f2a1c9 (7 caracteres, el short SHA) es legible; el SHA completo es inequívoco. Da igual cuál elijas mientras seas coherente: lo importante es que una etiqueta nunca cambie de significado.

4 · Ejemplo real

En el proyecto conductor queremos más que una etiqueta por commit: queremos una familia completa de etiquetas generadas a partir del contexto (rama, PR, commit, versión Git) sin escribir a mano cada combinación. Para eso existe docker/metadata-action, que traduce los eventos de GitHub en etiquetas.

proyectos/pipeline/.github/workflows/publish.yml
name: publish

on:
  push:
    branches: [main]
    tags: ["v*"]        # una etiqueta Git como v1.4.2 dispara publicacion semver
  pull_request:

env:
  REGISTRY: ghcr.io
  # GHCR exige nombres en minusculas: normalizamos el repositorio.
  IMAGE_NAME: ${{ github.repository }}

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4

      # Solo hacemos login cuando vamos a publicar de verdad.
      # En una PR de un fork no hay permisos ni secrets: no publicamos.
      - name: Login en GHCR
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v4
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Genera la lista de etiquetas y labels OCI a partir del evento.
      - name: Metadata (tags y labels)
        id: meta
        uses: docker/metadata-action@v6
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            # Publicacion de una etiqueta Git v1.4.2 -> 1.4.2, 1.4, 1
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=semver,pattern={{major}}
            # Push a main -> etiqueta de rama (referencia, no release)
            type=ref,event=branch
            # Commit inmutable: sha largo, la base de la trazabilidad
            type=sha,format=long
            # PR -> pr-42 (para previews, jamas para produccion)
            type=ref,event=pr

      - name: Build y push
        id: push
        uses: docker/build-push-action@v7
        with:
          context: .
          target: runtime
          # En PR solo construimos (sin publicar): valida el Dockerfile.
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

      - name: Digest publicado
        if: github.event_name != 'pull_request'
        run: echo "image=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${{ steps.push.outputs.digest }}"

Lo que hace cada entrada de tags: según el evento, para que lo veas con datos:

EventoReferencia GitEtiquetas generadas
push a mainrefs/heads/mainmain, sha-4f2a1c9…
push de una etiquetarefs/tags/v1.4.21.4.2, 1.4, 1, sha-…
pull_request nº 42refs/pull/42/mergepr-42 (y no se publica)

Por qué separamos «etiqueta de rama» de «etiqueta de versión»: main y pr-42 son referencias móviles —útiles para desarrollo y previews—; 1.4.2 y sha-… son las que se pueden desplegar. Si producción apuntara a main, cada push cambiaría lo que corre sin que nadie lo decidiera. Las etiquetas de release son contratos; las de rama son punteros de trabajo.

5 · Buenas prácticas

HazEvitaPor qué
Etiqueta por commit (sha-…) y por versión SemVer Única etiqueta latest La trazabilidad es la base de todo lo demás: auditoría, rollback, «¿qué está corriendo?».
Autentica con GITHUB_TOKEN y permisos mínimos Crear un PAT de larga vida y guardarlo como secret El token del workflow expira al terminar; un PAT es una llave maestra que hay que rotar y proteger.
Normaliza el nombre a minúsculas ghcr.io/${{ github.repository }} con mayúsculas GHCR rechaza rutas con mayúsculas; es un fallo clásico en repos con CamelCase.
Publica solo desde main o etiquetas Publicar desde PRs de forks Los PRs de forks no reciben secrets ni packages: write; y no quieres artefactos de cualquiera en tu registry.
Guarda el digest como salida del build Anotar solo la etiqueta en el despliegue La etiqueta se puede mover; el digest no. Desplegar por digest es lo que garantiza «mismo artefacto».
Usa etiquetas de rama solo para previews/desarrollo Que producción consuma :main o :pr-N Un puntero móvil en producción significa que el contenido cambia sin cambio de versión: imposible auditar.

Nota sobre la inmutabilidad del registry: algunos registries (por ejemplo Amazon ECR) ofrecen un flag de «tag immutability» que rechaza sobrescribir una etiqueta. En GHCR la disciplina es tuya: la práctica de etiquetar por commit/digest y no sobrescribir es lo que da la garantía. La verificación real, en cualquier caso, se hace al consumir por digest.

6 · Errores habituales

1. Publicar siempre como latest

Mal — se pierde para siempre el vínculo commit → imagen 
- uses: docker/build-push-action@v7
  with:
    push: true
    tags: ghcr.io/acme/copiloto-api:latest   # cada push la sobreescribe
Bien — la etiqueta inmutable primero, latest como comodidad opcional 
- uses: docker/build-push-action@v7
  with:
    push: true
    tags: |
      ghcr.io/acme/copiloto-api:sha-${{ github.sha }}   # identidad
      ghcr.io/acme/copiloto-api:latest                  # solo comodidad

2. Olvidar el permiso packages: write

Mal — el token es de solo lectura y el push es denegado 
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
# push -> "denied: permission_denied: write_package"
Bien — concede el permiso explícitamente en el job 
jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      # ... login y push

3. Nombre de imagen con mayúsculas

Mal — GHCR rechaza rutas que no estén en minúsculas 
- uses: docker/build-push-action@v7
  with:
    push: true
    tags: ghcr.io/AcmeOrg/Copiloto-API:sha-${{ github.sha }}
# "invalid reference format: repository name must be lowercase"
Bien — normaliza el nombre a minúsculas 
- name: Normaliza el nombre de imagen
  run: echo "IMAGE_NAME=${GITHUB_REPOSITORY,,}" >> "$GITHUB_ENV"
- uses: docker/build-push-action@v7
  with:
    push: true
    tags: ghcr.io/${{ env.IMAGE_NAME }}:sha-${{ github.sha }}

4. Intentar publicar desde un PR de un fork

Los workflows disparados por PRs de forks no reciben secrets y GITHUB_TOKEN llega con permisos restringidos. Un push: true incondicional falla (o, peor, si usaras un PAT, expondrías artefactos no confiables). Condiciona la publicación: en PRs solo se construye.

Nunca hardcodees credenciales. Ni en el YAML, ni en un .env versionado, ni en un ARG. Si un secreto acaba en una capa de imagen, docker history lo revela. Los secretos de build entran por secrets de la action y, si son de runtime, llegan en el despliegue (Módulo 4).

7 · Ejercicio guiado

Objetivo: publicar la Copiloto API en GHCR con etiqueta inmutable, descargarla por digest y demostrar en la terminal que etiqueta y digest identifican lo mismo.

  1. Paso 1 — Prepara el workflow de publicación.
    .github/workflows/publish.yml
    name: publish
on:
  push:
    branches: [main]
env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}
jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v7

      - name: Normaliza el nombre a minusculas
        run: echo "IMAGE_NAME=${GITHUB_REPOSITORY,,}" >> "$GITHUB_ENV"

      - uses: docker/setup-buildx-action@v4

      - uses: docker/login-action@v4
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build y push inmutable
        id: push
        uses: docker/build-push-action@v7
        with:
          context: .
          target: runtime
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:sha-${{ github.sha }}
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
          labels: |
            org.opencontainers.image.source=https://github.com/${{ github.repository }}
            org.opencontainers.image.revision=${{ github.sha }}
            org.opencontainers.image.title=copiloto-api

      - name: Publicar resumen
        run: |
          echo "### Imagen publicada" >> "$GITHUB_STEP_SUMMARY"
          echo "- tag: \`sha-${{ github.sha }}\`" >> "$GITHUB_STEP_SUMMARY"
          echo "- digest: \`${{ steps.push.outputs.digest }}\`" >> "$GITHUB_STEP_SUMMARY"
  2. Paso 2 — Commit, push y observa el run. 
    git add .github/workflows/publish.yml
git commit -m "ci: publica la imagen en GHCR con tag inmutable"
git push origin main
gh run watch            # o mira la pestana Actions
  3. Paso 3 — Autentica el CLI local contra GHCR. 
    # Usa un PAT con permiso read:packages para tirar de un paquete privado.
echo "$GHCR_TOKEN" | docker login ghcr.io -u TU_USUARIO --password-stdin

    Si el paquete es público, el docker pull funciona sin login. Si es privado, necesitas un token con read:packages (esto es solo para tu terminal; los secrets del repo son cosa del workflow).

  4. Paso 4 — Descarga por etiqueta y por digest; compruébalo. 
    OWNER=tu-usuario
REPO=copiloto-api

# 1) Por etiqueta
docker pull ghcr.io/$OWNER/$REPO:latest

# 2) Que digest tiene esa etiqueta?
docker buildx imagetools inspect ghcr.io/$OWNER/$REPO:latest
# -> Digest: sha256:9b1c...    (copialo)

# 3) Descarga por digest (identificador EXACTO del contenido)
docker pull ghcr.io/$OWNER/$REPO@sha256:9b1c...

# 4) Comprueba que etiqueta y digest son la MISMA imagen
docker inspect --format '{{index .RepoDigests 0}}' ghcr.io/$OWNER/$REPO:latest
  5. Paso 5 — Comprueba la trazabilidad (labels OCI). 
    docker inspect --format '{{json .Config.Labels}}' \
  ghcr.io/$OWNER/$REPO@sha256:9b1c... | jq .
# Debe aparecer:
#   org.opencontainers.image.revision = <sha del commit>
#   org.opencontainers.image.source   = https://github.com/...

Resultado esperado del Paso 5: el revision de la imagen coincide con el SHA del commit que disparó el workflow. Eso es la trazabilidad hecha verificable: cualquiera puede tomar una imagen de producción y saber de dónde salió. En la lección 3 le sumaremos procedencia firmada y SBOM.

8 · Reto

🎯 Un pipeline que garantice inmutabilidad de verdad

Has publicado con etiqueta por commit. Pero nada impide que un git push --force reescriba historia y que dos imágenes distintas acaben compartiendo sha-… corto (7 caracteres), o que alguien sobrescriba una etiqueta de release a mano. Tu reto es cerrar esos agujeros:

# PISTAS
# 1) En lugar de type=sha,format=short usa el SHA COMPLETO:
#      type=sha,format=long
#    y ademas somete el artefacto a un digest en el despliegue:
#      image@${{ steps.push.outputs.digest }}
#
# 2) Anade un paso que FALLE si la etiqueta de version ya existe
#    con OTRO digest (deteccion de sobrescritura):
#      docker buildx imagetools inspect ghcr.io/OWNER/REPO:1.4.2
#    compara el digest con el recien construido; si difieren, error.
#
# 3) Investiga las politicas de retencion de paquetes de GHCR y el
#    concepto de tag immutability de otros registries (p. ej. ECR).

Preguntas para guiarte: ¿qué identificador recomendarías para desplegar y cuál para buscar? ¿Cómo detectarías que un artefacto fue sustituido por otro con la misma etiqueta? ¿Merece la pena prohibir por política el latest en producción? No dejes la solución aquí escrita: experimenta contra tu registry y decide con criterio.

9 · Resumen

  • Registry: almacén de imágenes por contenido; se direcciona por etiqueta (mutable) o digest (inmutable).
  • GHCR (ghcr.io): registry integrado en GitHub; se autentica con GITHUB_TOKEN y el permiso packages: write, sin crear credenciales.
  • Tagging inmutable: una etiqueta de release nunca se mueve; publica por commit (sha-…) y por versión SemVer.
  • Digest: identidad real del artefacto; es lo que se guarda y con lo que se despliega. «El mismo que se prueba es el que se despliega».
  • metadata-action: traduce eventos (rama, PR, commit, tag) en etiquetas y labels org.opencontainers.image.* para trazabilidad.
  • Nombres en minúsculas y nada de publicar desde forks: dos reglas que evitan los fallos más comunes.

10 · Preguntas frecuentes

¿Necesito crear un secret con un PAT para publicar en GHCR?

No, si publicas en el mismo repositorio del workflow. Para eso está GITHUB_TOKEN, que GitHub genera y revoca automáticamente por cada ejecución. Solo necesitas un PAT (o una GitHub App, o credenciales OIDC) para publicar en paquetes de otra organización o en registries externos.

¿Cuál es la diferencia real entre :1.4.2 y :latest?

Conceptual, no técnica: ambas son punteros. La diferencia es tu regla: :1.4.2 se escribe una vez y no se mueve (etiqueta de release); :latest se sobrescribe en cada publicación (comodidad). Por eso producción debe consumir versiones o digests, y latest queda para pruebas rápidas.

Si etiqueto por commit, ¿para qué quiero SemVer?

Porque resuelven cosas distintas. El commit te dice qué código es; SemVer te dice qué significa para quien lo consume (mayor/menor/parche). Un servicio que depende de tu API quiere saber si 1.4.2 → 1.5.0 rompe compatibilidad. Publica ambas etiquetas: la máquina despliega por digest, el humano consulta por versión.

¿Por qué mi docker push funciona en main pero falla en un PR?

Porque los PRs provenientes de forks se ejecutan con un GITHUB_TOKEN de solo lectura y sin acceso a tus secrets —por seguridad—. La solución no es darle permisos, sino no publicar en PRs: construye para validar y publica solo desde main o etiquetas.

¿Cómo sé que la imagen que descargo es la que se publicó y no otra?

Descargando por digest: imagen@sha256:…. El digest se deriva del contenido, así que si algo cambiara, el digest ya no sería el mismo y el pull fallaría. En la lección 3 añadiremos la procedencia firmada, que permite verificar criptográficamente quién construyó esa imagen y desde qué commit.
