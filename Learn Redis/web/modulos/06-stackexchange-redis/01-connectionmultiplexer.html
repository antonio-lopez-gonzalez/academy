ConnectionMultiplexer: conexión y reuso

Módulo 6 · StackExchange.Redis en .NET ⏱ 40 minutos

1 · Introducción

En .NET, Redis se usa mediante StackExchange.Redis y su pieza central, el ConnectionMultiplexer: una «fábrica de conexiones» que multiplexa todos tus comandos sobre pocas conexiones físicas, maneja reconexiones y te da IDatabase, ISubscriber, etc.

Esta lección te enseña a conectarlo bien: uno por proceso, registrado en DI, con configuración consciente de timeouts y pipelining.

2 · Teoría

Qué es y por qué «uno solo»

PID .NET
   │
   └─ ConnectionMultiplexer  (UNO por proceso)
        ├─ getDatabase()   → IDatabase  (strings, hashes, sets…)
        ├─ getSubscriber() → ISubscriber (pub/sub)
        └─ crear uno nuevo   → ❌ multiplica conexiones y sockets

Crear multiplexers repetidamente agota conexiones, memoria y agrava reconexiones. La regla: singleton (DI lo garantiza).

Instalación y primer uso

dotnet add src/RedisWsHub package StackExchange.Redis
using StackExchange.Redis;

var mux = ConnectionMultiplexer.Connect("localhost:6379");
IDatabase db = mux.GetDatabase();          // comando CRUD
ISubscriber sub = mux.GetSubscriber();     // pub/sub

await db.StringSetAsync("hub:conn:1", "node-1", TimeSpan.FromSeconds(30));
string? node = await db.StringGetAsync("hub:conn:1");

Registrar en DI (ASP.NET Core)

builder.Services.AddSingleton<IConnectionMultiplexer>(_ =>
{
    var opts = ConfigurationOptions.Parse(builder.Configuration.GetConnectionString("Redis")
        ?? "localhost:6379");
    opts.AbortOnConnectFail = false;      // no abras la app si Redis tarda
    opts.ConnectTimeout = 5000;           // ms
    return ConnectionMultiplexer.Connect(opts);
});
builder.Services.AddSingleton<IDatabase>(sp =>
    sp.GetRequiredService<IConnectionMultiplexer>().GetDatabase());

Con eso, en tu hub inyectas IDatabase y ISubscriber donde los necesites.

Pipelining y latencia

  • Cada await de un comando es un round-trip; agrupa con IBatch o db.Pipeline/Task.WhenAll para varios a la vez.
  • Los async (…Async) no bloquean; usa siempre la variante async bajo carga.
  • Si el multiplexer debe esperar a reconexar, tus comandos ya «esperan en cola» con timeout.

Configuración clave: AbortOnConnectFail=false evita el clásico «la app no arrancó porque Redis no estaba»; la conexión se intenta sola y se conecta cuando pueda (M6-04).

3 · Ejemplo mínimo

using StackExchange.Redis;

var mux = ConnectionMultiplexer.Connect("localhost:6379");
var db = mux.GetDatabase();

// set con TTL y get atómico
await db.StringSetAsync("demo:k", "v", TimeSpan.FromMinutes(1));
RedisValue v = await db.StringGetAsync("demo:k");   // "v"
mux.Close();    // en apps reales NO cierras: vive por todo el proceso

4 · Ejemplo real

Servicio del hub que usa dos "vistas" del multiplexer (DAL y suscripción):

public sealed class HubRegistry
{
    private readonly IDatabase _db;
    private readonly ISubscriber _sub;

    public HubRegistry(IConnectionMultiplexer mux, string nodeId)
    {
        _db = mux.GetDatabase();
        _sub = mux.GetSubscriber();
        NodeId = nodeId;
    }

    public string NodeId { get; }

    public async Task RegisterAsync(string connectionId, string userId)
    {
        var key = $"hub:conn:{connectionId}";
        await _db.HashSetAsync(key,
            [new HashEntry("node", NodeId), new HashEntry("userId", userId)]);
        await _db.KeyExpireAsync(key, TimeSpan.FromSeconds(30));
        // notificar al resto de nodos el alta
        await _sub.PublishAsync("hub:events",
            $$"""{"type":"connect","conn":"{{connectionId}}","node":"{{NodeId}}"}""");
    }
}

Un único multiplexer alimenta las dos vistas sin duplicar sockets.

6 · Errores habituales

Crear el multiplexer por request

// ❌ “Un mux por handler” → en cada request abres sockets nuevos
await using var mux = ConnectionMultiplexer.Connect(cs);

// ✅ DI singleton: uno por proceso, reutilizado
builder.Services.AddSingleton<IConnectionMultiplexer>(...)

Ignorar «Redis.TimeoutException» / «No connection is available»

Son síntoma habitual de: muchos comandos síncronos, timeouts de socket cortos o conexiones perdidas sin reconexión. Resuelve con async, timeouts y configuración robusta (M6-04).

9 · Resumen

  • ConnectionMultiplexer = singleton por proceso; multiplexa sockets.
  • GetDatabase() / GetSubscriber() = las dos vistas.
  • DI + connection string + AbortOnConnectFail=false.
  • Async + pipelines para no bloquear el pool de hilos.

10 · Preguntas frecuentes

¿Necesito una conexión distinta para pub/sub?

StackExchange.Redis puede usar una conexión dedicada para el suscriptor (recomendable) y otra para los comandos; el multiplexer te da ambas API. La conexión «dedicada» de pub/sub es la llamada mux.GetSubscriber() sobre una conexión gestionada por el propio multiplexer.

¿Y si uso Redis remoto (Upstash/Cloud)?

Configuras host/puerto/TLS en el connection string (o la URL de Upstash) y la API es idéntica. En esos servicios suele exigirse TLS; StackExchange.Redis lo soporta con ,ssl=true.
