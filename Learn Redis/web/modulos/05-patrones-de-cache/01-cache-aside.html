Cache-aside (look-aside)

Módulo 5 · Patrones de Caché ⏱ 35 minutos

1 · Introducción

El patrón de caché más común y más sano: cache-aside (o look-aside). La aplicación controla cuándo cachear, con qué TTL y cómo invalidar — sin esa «magia» que rompe la consistencia.

Es la base de «la API + Redis para tu servidor WebSocket» cuando quieres dar velocidad a datos que vienen de una fuente de verdad (perfiles, precios, config).

2 · Teoría

El flujo

GET datos
   │
   ├─► 1) ¿en caché?  GET cached:price:msft
   │        HIT  → devolver
   │        MISS
   ▼
  2) leer fuente de verdad (base de datos / API)      ← CARO
  3) guardar en caché con TTL (SET EX)
  4) devolver
  (la próxima vez el HIT evita el paso 2)

Ventajas y desventajas

VentajaContra
Fácil de razonar; la app controla todoRiesgo de datos «algo viejos» durante el TTL
Escala lecturas sin tocar la fuenteMISS catastrófico si la fuente cae (stampede → M5-02)
Se añade a un sistema existente sin refactor big-bangRequiere invalidación manual al escribir

Reglas de oro

  • TTL SIEMPRE: sin TTL, el dato viejísimo sobrevive y la caché crece.
  • Invalidar o expirar: al escribir en la fuente, o borra la key (DEL) o dejas que TTL la caduque. Borrar de inmediato da la mejor frescura.
  • Evict, no «update»: si actualizas la key con el nuevo valor, dos procesos a la vez pueden intercalar escrituras; el DEL (o un «muere pronto») es más simple y seguro.
  • Idempotencia/miss handling: si la fuente falla, decide: sirve el dato viejo (stale-while-revalidate) o error.

3 · Ejemplo mínimo

# 1) intento de HIT
GET cached:price:msft
# 2) MISS → ir a la fuente → 3) guardar:
SET cached:price:msft 415.25 EX 300
# 4) invalidar al escribir la fuente:
DEL cached:price:msft

4 · Ejemplo real

En .NET, un servicio cache-aside sobre StackExchange.Redis (el patrón IDistributedCache también lo usa por debajo):

public async Task<Profile?> GetProfileAsync(string userId)
{
    string key = $"cache:profile:{userId}";

    // 1) HIT
    var cached = await _db.StringGetAsync(key);
    if (!cached.IsNull)
        return JsonSerializer.Deserialize<Profile>(cached!);

    // 2) MISS → fuente de verdad (aquí simulada)
    var profile = await _repo.GetAsync(userId);
    if (profile is null) return null;

    // 3) guardar con TTL
    await _db.StringSetAsync(key,
        JsonSerializer.Serialize(profile),
        TimeSpan.FromMinutes(5));

    return profile;
}

public async Task InvalidateAsync(string userId)   // al escribir en la fuente
{
    await _db.KeyDeleteAsync($"cache:profile:{userId}");
}

Nota: en el hub, el «perfil de sesión» de un usuario es un buen candidato cache-aside, mientras que la presencia usa TTL-heartbeat (no cache-aside: es estado «vivo» que tú refrescas).

6 · Errores habituales

Cachear la ausencia del dato

// ❌ Si la fuente devuelve null y le pones TTL "para no volver a preguntar",
//    guardas "null" y ya no te enteras cuando exista.
await _db.StringSetAsync(key, value ?? emptySentinel, ttlFar);
// ✅ No cachees null; o usa un TTL corto y un marcador explícito "absent".

Invalidar con DEL solo en «algunas» escrituras

Si solo algunos writes invalidan, te quedan cachés zombies. Invalida en TODAS las rutas que cambian el dato (o reduce el TTL).

7 · Ejercicio guiado

  1. Paso 1: Emula cache-aside en redis-cli: «MISS» → lee fake → SET EX 120.
  2. Paso 2: Repite el GET y observa el HIT.
  3. Paso 3: Invalida con DEL y verifica el MISS.
  4. Paso 4: En tu hub, elige UN dato que cache-asides (p. ej. perfil) y escribe el par Get/Invalidate en C#.

8 · Reto

🎯 Frescura explícita

Define para tu hub una política: qué dato tolera 5 min de staleness (config, catálogo), qué dato solo 5 s (precio), y qué dato es «vivo» y NO se cachea (presencia). Justifica cada elección con un escenario de tu producto.

9 · Resumen

  • Cache-aside: HIT→devuelve; MISS→lee fuente→guarda con TTL.
  • Invalidación con DEL al escribir; TTL siempre; cuidar «cachear null».
  • El hub: perfiles/config cache-aside; presencia viva por TTL no cache-aside.

10 · Preguntas frecuentes

¿Cache-aside equivale a IDistributedCache?

No del todo: IDistributedCache te da Get/Set con TTL (una infra); tú implementas el «mira caché, luego fuente» (el cache-aside) encima, o usas librerías como OpenCaching/LazyCache que lo automatizan.

¿Y si quiero que entre varios nodos la caché sea coherente?

La invalidación con DEL/Aviso es por Redis (todos ven la misma key); si necesitas «avisar» a otros cachés locales, publica en un canal (M3-01) y que cada nodo borre.
