Invalidación, cache stampede y TTL/jitter

Módulo 5 · Patrones de Caché ⏱ 40 minutos

1 · Introducción

Cache-aside sin estrategia de invalidación es un desastre a plazos: datos viejos, «estampadas» (cache stampede) y picos de carga en la fuente cuando cae una key masiva.

Aquí verás qué es el cache stampede, por qué la invalidación con DEL + aviso es mejor que «actualizar en el aire», y cómo el TTL con jitter y un lock mitigan lo peor.

2 · Teoría

El cache stampede (thundering herd)

t0: una key muy popular expira (su TTL llega a 0)
t1: 10.000 peticiones → TODAS ven MISS
t2: TODAS llaman a la fuente de verdad a la vez (embudo de DB)
t3: la fuente colapsa → falla el sistema, aunque Redis estaba sano

El bloqueo no está en «Redis aguantando», sino en el efecto amplificador sobre la fuente. Los mitigadores:

  • TTL + jitter: que no todas las keys expiren al mismo segundo.
  • Lock (SET NX + TTL): solo un proceso recalcula y escribe; los demás esperan (o sirven stale).
  • Soft/hard TTL: cuando expira el «hard», se sigue sirviendo el dato viejo (stale-while-revalidate) mientras se refresca.

Invalidación: DEL con notificación

Al escribir en la fuente de verdad:

DEL cache:price:msft
PUBLISH cache:invalidations 'msft'     # aviso a otros cachés locales

El DEL es la señal universal; el PUBLISH informa a los demás nodos. Alternativa: «escribir el valor nuevo» (write-through) pero con cuidado (M5-03).

Dos técnicas estrella en redis-cli

# 1) Jitter: variar el TTL (5 ± 2 s)
SET cache:dd key EX 300
# (punto: en .NET usas Random.Next(240, 360))

# 2) Lock para recálculo:
SET lock:recalc:msft NX PX 5000      # solo 1 ganador
if (ok) { recalcula(); DEL lock; SET cache:... EX 300; }

3 · Ejemplo mínimo

# léeme y observa el flujo del lock
SET lock:hotkey NX PX 3000          # gané el lock
SET hotkey 'precio de verdad' EX 300   # recalculo y guardo
DEL lock:hotkey                     # libero el lock
GET hotkey                          # el resto ya tiene dato

4 · Ejemplo real

En .NET, el GetProfile “con guardia anti-stampede”:

public async Task<Profile> GetProfileGuardedAsync(string userId)
{
    string key = $"cache:profile:{userId}";
    string lockKey = $"lock:profile:{userId}";

    // 1) HIT
    var cached = await _db.StringGetAsync(key);
    if (!cached.IsNull) return Deserialize(cached!);

    // 2) MISS → lock con TTL corto (aunque el dueño muera, se libera solo)
    bool got = await _db.StringSetAsync(lockKey, Environment.MachineName,
        TimeSpan.FromMilliseconds(5000), When.NotExists);
    if (!got)
    {
        // otro proceso recalcula: espera un poco y relee (con timeout)
        await Task.Delay(50);
        return (await _db.StringGetAsync(key)).IsNull
            ? throw new TimeoutException("cache miss prolongado") : Deserialize(await _db.StringGetAsync(key));
    }

    try
    {
        var profile = await _repo.GetAsync(userId);      // SOLO 1 golpea la fuente
        await _db.StringSetAsync(key, Serialize(profile), RandomTtl());  // jitter
        return profile;
    }
    finally
    {
        await _db.KeyDeleteAsync(lockKey);   // libera el lock (modo ideal con Lua+token)
    }
}

private static TimeSpan RandomTtl() => TimeSpan.FromMinutes(Random.Shared.Next(4, 6));

Con el lock, el resto de peticiones espera un instante y relee; la fuente recibe 1 golpe en lugar de N.

6 · Errores habituales

Lock sin expiración (deadlock en vivo)

// ❌ SET NX sin TTL: si el proceso muere a mitad, el lock queda vivo
await _db.StringSetAsync(lk, "me", When.NotExists);

// ✅ Siempre con TTL (y token para liberación en Lua, M6-03)
await _db.StringSetAsync(lk, "me", TimeSpan.FromSeconds(5), When.NotExists);

Invalidar solo «a veces»

Un solo camino de escritura sin DEL deja cachés zombies. Invalida en todos los writers o acorta el TTL.

8 · Reto

🎯 Dilema del lock

El lock con TTL corto tiene un precio: puede expirar mientras el dueño sigue calculando, y otro proceso recalcula en paralelo. Valora para tu hub: ¿prefieres «duplicados ocasionales de recálculo» (lock corto) o «servir stale» (revalidate)? Argumenta con tu caso.

9 · Resumen

  • Cache stampede = MISS masivo → sobrecarga de la fuente.
  • Mitigadores: jitter, lock (SET NX + TTL), stale-while-revalidate.
  • Invalidación: DEL (y pub/sub para nodos con caché local).

10 · Preguntas frecuentes

¿Cuándo NO me preocupo por el stampede?

Cuando la fuente aguanta el pico (cache fría es rara o el MISS es raro). El stampede duele en keys popularísimas que expiran a la vez.

¿El lock debe ser Lua o basta SET NX?

SET NX + TTL basta para el caso básico. La «liberación segura solo-si-soy-el-dueño» y el refresh quieren Lua (M6-03). El curso te enseña ambos.
