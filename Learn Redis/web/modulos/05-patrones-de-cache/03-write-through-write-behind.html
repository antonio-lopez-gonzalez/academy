Write-through, write-behind y cuándo cachear

Módulo 5 · Patrones de Caché ⏱ 30 minutos

1 · Introducción

El cache-aside resuelve lecturas; pero ¿qué pasa al escribir? Ahí aparecen los patrones de write-through (escribir caché + fuente a la vez) y write-behind (escribir caché rápido y persistir en segundo plano).

Verás las diferencias, cuándo merecen la pena y cómo decidir qué se cachea y qué no en tu hub.

2 · Teoría

Los tres enfoques de escritura

PatrónQué haceRiesgo
Cache-aside + DEL (lo visto)Al escribir: fuente + borra la keyVentana de «caché viejísima» hasta el próximo GET
Write-throughAl escribir: fuente + REDIS con el mismo valor (SET)Escribir en caché por cada write (cuesta si escribe mucho y sirve poco)
Write-behindAl escribir: fuente (rápido) y en segundo plano refrescare valores calientesRiesgo de lag entre lo que ves y lo almacenado

Cuándo cada uno

  • Write-through: cuando el dato se lee mucho más de lo que se escribe, y quieres que la caché ya esté «caliente» al primer GET. Ej.: configuración que cambia raramente.
  • Write-behind: cuando el write a la fuente es caro y puedes agregar en Redis para persistirlo después. Ej.: contadores de estadísticas (acumulas e inserto en lote).
  • Cache-aside + DEL: el default; simplemente deja que el próximo GET rellene la caché.
write-through        write-behind
cliente → app        cliente → app
   ├─► fuente           ├─► Redis (rápido) ──► (background) ──► fuente
   └─► Redis (SET)      └─ COPIA DELEGADA (ack inmediato)

La regla de «dónde cachear»

  • Cachea lo que se lee mucho y cambia poco.
  • No cachees lo que cambia siempre ni lo denso y único (paginaciones innumerables).
  • La fuente de verdad sigue siendo tu DB; Redis es un acelerador que se puede reiniciar (y tu app debe seguir viva).

3 · Ejemplo mínimo

# write-through (simple): escribe fuente(no necesaria aquí) + caché
SET config:feature:X '{"enabled":true}' EX 3600

# write-behind (acumular stats): INCR contadores…
INCR stats:day:2026-08-31:orders
# …y un job cada X minutos sumariza a la DB y RESETEA (o DECRBY)

4 · Ejemplo real

En el hub conviven ambos sin dolor:

// 1) Write-through de una configuración de canal (se lee mucho, se escribe poco)
public async Task SetChannelConfigAsync(string ch, ChannelConfig cfg)
{
    await _repo.SaveAsync(ch, cfg);                      // fuente
    await _db.StringSetAsync($"cfg:chan:{ch}",
        JsonSerializer.Serialize(cfg), TimeSpan.FromHours(1));   // caché "caliente"
}

// 2) Write-behind de estadísticas (acumuladas en Redis, volcadas en lote)
await _db.StringIncrementAsync($"stats:{_nodeId}:msgs"); // este minuto
// (cada minuto, un worker lee+resetea e inserta en la DB — M3-02 stream/colas)

La configuración se sirve del caché al instante; las estadísticas se agregan sin tocar la DB en caliente.

5 · Buenas prácticas

HazEvitaPor qué
Write-through solo en datos «poco escritos, muy leídos»Write-through en contadores de alto writeDuplicarías el coste de red por escribir en caché lo que nadie lee
Write-behind para agregar y persistir en loteWrite-behind para datos que deben verse ya en la fuenteEl lag del background rompe la consistencia esperada
Mantener la fuente como única «fuente de verdad»Hacer de Redis la única copia de algo persistenteRedis es volátil por diseño; perderías historia

6 · Errores habituales

Usar write-through con datos de altísimo write

// ❌ Cada tick del precio (10/s) escribiendo en Redis aunque nadie lea
await _db.StringSetAsync("price:live", p, ttl);
// ✅ Cache-aside + TTL corto, o métricas/contador según lectura real

La «caché infinita» de tablas paginables

Cachear todas las combinaciones de filtro/página de un catálogo gigante = hay rebalse; mejor cachear los datos «verticales» (por id) y montar búsquedas por separado.

8 · Reto

🎯 Métrica de decisión

Define cómo medirías el hit ratio de una key (p. ej. instrumentando GETs/HITs con contadores en Redis). Escribe la consulta/lógica y el umbral a partir del cual aconsejarías dejar de cachear un dato (ratio < 40 %). Al final, y compárala con keyspace_hits / keyspace_misses de `INFO stats` del propio Redis.

9 · Resumen

  • Cache-aside + DEL es el default humano.
  • Write-through: poco-write/mucho-read (config).
  • Write-behind: agregar en Redis, persistir en lote (stats).
  • La fuente de verdad permanece; Redis es el acelerador.

10 · Preguntas frecuentes

¿Write-through y write-behind son excluyentes del cache-aside?

No, conviven al mismo tiempo en la app para distintos datos: unos usan cache-aside (+DEL), otros write-through, otros métricas agregadas. La clave es clasificarlos.

¿Y si escribo en Redis y falla la fuente?

Ese es el riesgo del write-behind: ack al cliente pero fallo al persistir. Diseña reintentos (streams del M3) o fondo de compensación si el dato importa.
