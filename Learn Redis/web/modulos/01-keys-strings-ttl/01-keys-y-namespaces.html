Keys: convenciones de nombres

Módulo 1 · Keys, Strings y TTL ⏱ 30 minutos

1 · Introducción

En Redis, el «nombre de la key» es tu esquema de datos: no hay tablas, así que el espacio de nombres lo decides tú en cada nombre. Una buena convención hoy evita colisiones, borrados accidentales y dashboards rotos mañana.

Verás el formato recomendado dominio:entidad:identificador, operaciones de gestión de keys y la diferencia entre KEYS y SCAN.

2 · Teoría

Por qué el nombre importa

Redis es un diccionario plano: no hay carpetas ni esquemas. El nombre de cada key actúa como namespace. Con varias apps compartiendo un servidor (o varios flujos del mismo hub), una convención centralizada es lo único que evita:

  • que «user» de servicios distintos pisen su valor;
  • que un FLUSHDB o un borrado por patrón se lleve datos de otro equipo;
  • que las monitorizaciones de memoria no se puedan leer.

El patrón de nombres

dominio:entidad:identificador[:detalle]

hub:conn:8632            # conexión concreta
hub:conn:8632:meta       # sub-detalle (p. ej. estado)
chan:gaming              # set de miembros de un canal
presence:global          # índice de presencia
stats:nodo1:msgs         # contador

Las reglas prácticas:

  • Dos puntos (:) como separadores — no espacios; legibles y filtrables.
  • Prefijo de dominio corto: hub, cache, session…
  • Tamaño razonable: nombres verbosos multiplican el coste de RAM (cada key guarda su nombre).
  • Estable y en minúsculas: cambiarlos a mitad de proyecto obliga a migrar datos.

Gestión de keys

EXISTS key1 key2 key3     # cuántas existen
DEL key1 key2             # borrar
RENAME vieja nueva          # renombrar
TTL key / PERSIST key     # vida (M1-03)
TYPE key                  # qué estructura es
DBSIZE                    # nº de keys en la DB

Analogía: piensa en las keys como nombres de variables en un programa global compartido. Nadie compilaría funciones con variables llamadas data o x para todo el sistema; aquí igual, con consecuencias en RAM y colisiones.

3 · Ejemplo mínimo

SET hub:conn:100 node-1
SET hub:conn:101 node-2
EXISTS hub:conn:100         # (integer) 1
SCAN 0 MATCH hub:conn:* COUNT 10
DEL hub:conn:100
DBSIZE

Con SCAN ... MATCH hub:conn:* inspeccionamos solo el namespace del hub sin bloquear Redis.

6 · Errores habituales

Nombres genéricos que colisionan

# ❌ No sabes de quién es "conn" ni de qué dominio
SET conn node-1

# ✅ Namespace completo
SET hub:conn:8632 node-1

Usar KEYS en producción

KEYS *                # ❌ recorre todo, pausa el single-thread
SCAN 0 MATCH hub:*    # ✅ iterativo, no bloquea demasiado

8 · Reto

🎯 Núcleo sin choque

Busca en internet tu «convención de keys Redis» preferida (o proponla) y escríbela como docstring en la clase Keys del proyecto. Debe cubrir: prefijos de dominio, separadores, mayúsculas/minúsculas y manejo de versiones dentro del nombre.

9 · Resumen

  • Las keys son el esquema de Redis: dominio:entidad:identificador.
  • SCAN > KEYS; DEL/EXISTS/TYPE/TTL para administrar.
  • Centraliza los nombres en constantes para evitar typos y colisiones.

10 · Preguntas frecuentes

¿Puedo tener espacios en una key?

Sí, técnicamente, pero rompe la legibilidad y los filtros. La convención es sin espacios.

¿Debo versionar las keys?

Cuando cambias el formato de un valor, es común llevar versión en el espacio (hub:conn:v2:<id>) para poder migrar sin borrar los antiguos de golpe.
