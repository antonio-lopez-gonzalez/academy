Strings: SET/GET/SETEX/MGET y opciones NX/XX

Módulo 1 · Keys, Strings y TTL ⏱ 35 minutos

1 · Introducción

El string es el tipo más simple y el más usado de Redis: guarda bytes, números, JSON. Es la base de la caché (guarda una respuesta cara en SET, la usas con GET).

Verás la familia de comandos, las opciones NX/XX/EX/PX (que esconden primitivas atómicas cruciales) y cómo encaja en el hub.

2 · Teoría

El comando SET

SET key value [EX seconds|PX ms] [NX|XX] [KEEPTTL] [GET]
OpciónQué haceCaso
EX nExpira en n segundossetear valor + TTL en un solo comando (atómico)
PX nExpira en n msexpiración con precisión de ms
NXSolo escribe si NO existealgoritmo de lock optimista, primera-semántica
XXSolo escribe si EXISTEactualizar solo algo ya presente
KEEPTTLAl escribir, conserva el TTLrefrescar valor sin resetear vida

La clave: SET ... NX EX ... es atómico → es un lock con expiración en un solo round-trip (M5 lo usa para el cache stampede).

Lectura

GET key                 # valor o (nil)
MGET k1 k2 k3            # varios en 1 round-trip (¡ahorra RTT!)
GETRANGE/GETSET          # slices y swap atómico
STRLEN key

SETEX y SETNX (formas clásicas)

SETEX key 60 valor      # = SET key valor EX 60
SETNX key valor         # = SET key valor NX
PSETEX key 60000 valor  # milesegundos

Los prefieres como sintaxis de un comando único, no dos (SET + EXPIRE) que podrían partirse entre líneas.

3 · Ejemplo mínimo

SET cached:price:msft 415.25 EX 300
GET cached:price:msft
# "415.25"

SET session:user:42 '{"name":"ana"}' NX EX 3600
SET session:user:42 '{"name":"ana2"}' NX    # → (nil) ya existe
MGET cached:price:msft cached:price:aapl     # uno llega, otro nil

NX hizo que la segunda escritura sea un no-op: semántica «solo si ausente» en un comando.

4 · Ejemplo real

En el hub, el string da dos usos: token/lock y caché de datos calientes.

# 1) Lock de "un solo consumidor procesa esta cola" (M5)
SET lock:queue:mail NX PX 5000      # ok=Redis op-ok; fallo=ya alguien

# 2) Caché de un recurso caro (profile del usuario activo)
SET cached:profile:42 '{"online":true,"channels":["general"]}' EX 15

# 3) Registro simple conexión→nodo con presencia (TTL en SET)
SET hub:conn:8632 node-1 EX 30

Todo «valor con caducidad» que necesite GET rápido cabe en un string.

6 · Errores habituales

Lock NO atómico (el clásico)

// ❌ Raza: dos procesos pueden pasar el GET al mismo tiempo
if (await db.StringGetAsync(lockKey).IsNull) {
    await db.StringSetAsync(lockKey, "me");
    // …otro ya lo hizo…
}

// ✅ SET NX atómico
bool ok = await db.StringSetAsync(lockKey, "me", TimeSpan.FromSeconds(5), When.NotExists);
if (ok) { /* soy el dueño */ }

GET sobre un string como si fuera número sin parsear

GET devuelve bytes; en .NET usa StringGet y parsea/decodifica tú con el encoding correcto (UTF-8).

8 · Reto

🎯 Lock con identidad

Para un lock distribuido sólido hay que «liberar solo si soy el dueño» (evitar liberar el lock de otro). Diseña el esquema: valor = token UUID del dueño; liberación = Lua «GET valida + DEL» (lo verás en M6-03). Escribe cómo lo harías hoy en redis-cli y compáralo con la solución Lua del curso.

9 · Resumen

  • Strings: SET/GET/MGET/INCR/SETEX/SETNX.
  • Opciones NX/XX/EX/PX/KEEPTTL = primitivas atómicas.
  • SET NX EX es tu lock distribuido básico.
  • MGET ahorra round-trips; evitar GET+SET en dos pasos.

10 · Preguntas frecuentes

¿Un string puede guardar números?

Sí: se guardan como texto y Redis los trata como enteros en INCR/DECR/INCRBY, manteniendo la atomicidad.

¿Cuándo NO usar string?

Cuando quieras acceder a campos por separado (usa hash), cuando quieras membrecía única (set) o cuando quieras orden/score (sorted set/list). El string es "el valor entero".
