Arquitectura: registro + backplane

Módulo 7 · El Hub de Conexiones WebSocket con Redis ⏱ 40 minutos

1 · Introducción

Es el momento de juntar todo lo aprendido en una sola arquitectura para tu servidor WebSocket. La idea central: Redis como «directorio de conexiones» (registro) + canal común (backplane). Cada nodo es igual, comparte estado y se escala solo añadiendo nodos.

Aquí defines el dibujo definitivo; en las siguientes lecciones lo llenamos de código.

2 · Teoría

Los roles

PiezaQué guardaEstructura
RegistroConexión → nodo dueño (+ detalle usuario)Hash por conexión hub:conn:<id>
PresenciaQuién está conectado y cuándoSorted set hub:presence (score = ts)
BackplaneBroadcast/eventos entre nodosPub/Sub hub:events, hub:presence
Indices«usuarios de un canal», nodos vivosSets chan:*, hub:nodes

El flujo de un nodo

Nodo .NET (node-1)                    Redis
   │  startup: se suscribe             SUBSCRIBE hub:events, hub:presence
   │  register en hub:nodes            SADD hub:nodes node-1
   │                                   (TTL de seguridad)
   │
cliente → /ws (upgrade)
   │  conn = conexión local (socket)    ← vive en la RAM del nodo
   │  registra:                        HSET hub:conn:<id> node node-1 userId u
   │                                   EXPIRE … 30
   │                                   ZADD hub:presence <ts> user:u
   │  publica evento                   PUBLISH hub:presence {"type":"connect"...}
   │
   │  recibe mensaje "broadcast"       PUBLISH hub:events {...}
   ▼
(cliente) ─────────────────────────────► (los otros nodos reciben y reenvían)

Decisiones de diseño

  • El socket vive en su nodo; Redis solo guarda «dónde está» y las señales. (M0-04: no guardamos el WebSocket en Redis.)
  • Todo evento relevante se publica para que cada nodo decida si le toca.
  • Nodos idénticos: sin nodo «especial»; redescubrimiento por Redis.
  • Caída de Redis: modo local degradado (M6-04) y reconciliación al volver.

3 · Ejemplo mínimo

# El patrón mínimo del registro en redis-cli
SADD hub:nodes node-1            # anuncia el nodo
EXPIRE hub:nodes 30             # (con renovación en el heartbeat)
HSET hub:conn:8632 node node-1 userId 42 EXPIRE hub:conn:8632 30
ZADD hub:presence 1750000000 user:42
PUBLISH hub:presence '{"type":"connect","conn":"8632","node":"node-1"}'

Con esto, «otro nodo» ya puede averiguar dónde está 8632 y anunciar su nacimiento.

                 |  hub:conn:* (hash)  hub:presence (zset)  chan:* (sets)    |
                 |  hub:events (pub/sub)  hub:presence (pub/sub)             |
                 +----------------------------▲------------------------------+
                                              │ subscribe + publish
   +----------------+        +---------------+│+---------------+          │
   |  Nodo A        |        |  Nodo B       │               ...          │
   | /ws (sockets)  |        | /ws (sockets) │                             │
   | /api/*         |        | /api/*        |                             │
   +----------------+        +---------------+-----------------------------+

Pilares que ya dominas: hash+TTL (M1/M2/M6), zset de presencia (M2), pub/sub (M3), multiplexer (M6). Aquí solo se ensamblan.

6 · Errores habituales

Broadcast solo a las conexiones del proceso local

// ❌ Envía solo a "mis" sockets; los del otro nodo nunca lo ven
foreach (var c in _localSockets) await c.SendAsync(msg);

// ✅ Publica (todos los nodos lo reenvían a sus sockets)
await _sub.PublishAsync("hub:events", msg);
// + el suscriptor local reenvía también (o confía en cada nodo)

Usar el ID de nodo «hardcodeado» que choca entre réplicas

Si dos réplicas usan el mismo node-1 como suyos, el registro se pisa. Usa un identificador único (guid por proceso, o nombre de pod con sufijo).

8 · Reto

🎯 ¿Quién reenvía el broadcast?

Decide y justifica: cuando un nodo publica «broadcast», ¿debe reenviar a sus propias sockets además de publicar (doble trabajo) o confiar solo en el suscriptor? Analiza las dos opciones (latencia, duplicación) y elige para tu caso.

9 · Resumen

  • Registro (hash/TTL) + presencia (zset) + backplane (pub/sub).
  • El socket vive en su nodo; Redis guarda «dónde está».
  • Eventos de ciclo de vida para que los nodos se enteren.
  • Nodo con identidad única y modo sin Redis definido.

10 · Preguntas frecuentes

¿Necesito Sentinel si solo tengo 1 nodo de Redis?

Para desarrollo, no. Para producción real (aunque tu hub funcione degradado), un par con Sentinel te ahorra rescates manuales. M4 tienes el criterio.

¿Este diseño vale para SignalR?

Sí: SignalR + Redis backplane hace exactamente «publica en Redis y cada hub reenvía». Con StackExchange.Redis lo implementas tú y ves qué ocurre debajo.
