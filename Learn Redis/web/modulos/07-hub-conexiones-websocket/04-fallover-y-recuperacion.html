Desconexiones, heartbeats y fallover

Módulo 7 · El Hub de Conexiones WebSocket con Redis ⏱ 30 minutos

1 · Introducción

El hub vive de estados frágiles: sockets que se caen, nodos que mueren, Redis que parpadea. Aquí cierras el círculo con las tres «redes de seguridad»: heartbeat (quién sigue vivo), expiración (limpieza automática) y fallover/re-registro (recuperación).

2 · Teoría

Heartbeat del socket (cliente ↔ servidor ↔ Redis)

Cliente ──ping──────────────► Nodo ──KeyExpire/ScoreRefresh──► Redis
         ◄────────────pong───   (lease 30s)                     (presencia+)
muerto: no responde pong ──► unregister                        (expira sola)
  • El servidor refresca el lease y el score en cada mensaje/heartbeat del cliente.
  • Si no llega nada y el renewal no mantiene, la expiración «borra» la presencia.

Re-registro del nodo al arrancar / reconectar

// Al arrancar un nodo (o al restaurarse Redis):
mux.ConnectionRestored += async (_, _) =>
{
    _logger.LogInformation("Redis restablecido: repito registro y suscripciones");
    await _registry.RegisterNodeAsync(_nodeId);     // SADD hub:nodes
    await _sub.SubscribeAsync("hub:events", OnEvent);   // re-subscribir
    await _sub.SubscribeAsync("hub:direct", OnDirect);
};

Fallover de un nodo

  1. El cliente pierde la conexión → lo detecta (Frames) y reintenta a otro nodo (load balancer).
  2. Su presencia expira por los TTL (lease) si nadie la refresca.
  3. El nuevo nodo RegisterAsync de nuevo (el DB ya no tiene «dónde estaba»).
  4. Un «barrido» ocasional limpia hashes huérfanos (SCAN MATCH hub:conn:*) si hiciera falta.

3 · Ejemplo mínimo

# simulación: nodo muere
# 1) no refresca:
#    (el cliente se fue → EXPIRE del registro expira a los 30 s)
# 2) nuevo nodo registra:
HSET hub:conn:200 node node-2 userId 7 EXPIRE hub:conn:200 30
ZADD hub:presence 1750000000 user:7

4 · Ejemplo real

El «recovery» completo del proyecto final:

public sealed class HubRecovery
{
    public static void Wire(IConnectionMultiplexer mux, ConnectionRegistry reg,
        ConnectionHub hub, ILogger logger, string nodeId)
    {
        mux.ConnectionFailed += (_, e) =>
            logger.LogWarning("Redis caído: {Msg}", e.Exception?.Message);

        mux.ConnectionRestored += async (_, _) =>
        {
            logger.LogInformation("Redis restaurado: re-registro y re-suscripción");
            await reg.RegisterNodeAsync(nodeId);
            await hub.ReSubscribeAsync();         // re-inscribir canales
        };
    }
}

// Heartbeat: en el loop del socket, refresca lease + score
//   (ConnectionRegistry.HeartbeatAsync que viste en M7-02)

Y una limpieza periódica opcional (job de mantenimiento):

// Cada X minutos: SCAN MATCH hub:conn:* y borrar las que ya no tienen TTL sano
// (o confiar en la expiración; el barrido es contingencia de bugs)

6 · Errores habituales

Heartbeat que refresca la presencia pero no el registro

// ❌ Solo KeyExpire del hash, olvidando el zset (o al revés)
// ✅ HeartbeatAsync refresca AMBOS (visto en M7-02)

Evitar la reconexión del cliente creyendo que «solo» la posee el servidor

El fallover del hub depende de que el cliente reintente: sin reconnect del lado cliente, la caída de un nodo tumba al usuario. Es contrato de diseño.

7 · Ejercicio guiado

  1. Paso 1: Añade el heartbeat al loop de tu socket (refresh de lease + presencia).
  2. Paso 2: Implementa re-subscribe + re-registro en ConnectionRestored.
  3. Paso 3: Simula la caída de un nodo: detén el proceso, espera la expiración y verifica que «presencia» y «registro» quedan limpios sin intervención.
  4. Paso 4: Escribe en README tu plan de «nodo muerto → cliente reconecta → nuevo nodo registra».

8 · Reto

🎯 El escenario difícil

Diseña qué pasa si Redis cae 2 minutos EN MEDIO de un flujo de broadcast dirigido: ¿mensajes perdidos? ¿cómo lo notas? Propón 2 mitigaciones (p. ej. cola de pendientes local, o aviso al cliente de «retardo») y decide cuál es aceptable para tu producto.

9 · Resumen

  • Heartbeat + lease: la presencia se limpia sola (~30 s).
  • ConnectionRestored: re-registro + re-suscripción.
  • Cliente reconectar = parte del diseño; barrido SCAN como contingencia.

10 · Preguntas frecuentes

¿Cuánto tiempo de «hueco» ve el resto si un nodo muere?

Lo que marque el TTL (lease) del registro/presencia tras el último heartbeat: ~30 s. Los clientes reconocen el corte y en ese tiempo el nuevo registro está limpio.

¿La limpieza SCAN es obligatoria?

No en el flujo feliz (la expiración ya limpia), pero sí es una red de seguridad ante bugs (un nodo sin unregister + sin TTL). Hazla con cuidado (pocas keys, sin bloquear).
