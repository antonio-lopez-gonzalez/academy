Broadcast vía pub/sub y envío dirigido

Módulo 7 · El Hub de Conexiones WebSocket con Redis ⏱ 40 minutos

1 · Introducción

Ya registramos conexiones. Ahora el propósito: enviar mensajes. Dos caminos por Redis: broadcast (a todos, vía pub/sub que cada nodo reenvía) y dirigido (a un cliente concreto, buscando su nodo en el registro).

Aquí ves el código exacto del proyecto final y cómo evitar el «bucle» de broadcasts.

2 · Teoría

Broadcast

Nodo A tiene el mensaje
  PUBLISH hub:events {"type":"broadcast","payload":...,"from":"node-1"}

Cada nodo (incl. A) recibe y reenvía a SUS sockets.
  nodo A → a los suyos
  nodo B → a los suyos
  (si no quieres duplicar, A reenvía local + publica; B solo reenvía)

Reenvío dirigido local: guardas tu diccionario local id→WebSocket y haces SendAsync a los que te tocan.

Envío dirigido

Quiero mandar al cliente conn 8632 (está en node-2)
  1) HGET hub:conn:8632 node  → "node-2"
  2) ¿soy node-2?  → sí: mi diccionario local, SendAsync
                   → no: PUBLISH hub:direct {"to":"8632","payload":...}
  3) el nodo dueño recibe y reenvía a su socket

hub:direct puede ser un canal aparte (o prefijo de mensaje). Así un mensaje «uno-a-uno» llega solo al nodo que tiene el socket.

Evitar loops

  • Publica con un from y verifica que no te lo reenvíes a ti (o publica solo, sin reenviar local, y deja que el suscriptor lo haga).
  • Para envíos dirigidos: solo el dueño (según registro) responde.

3 · Ejemplo mínimo

# broadcast
PUBLISH hub:events '{"type":"broadcast","payload":"hola","from":"node-1"}'
# dirigido
HGET hub:conn:8632 node
PUBLISH hub:direct '{"to":"8632","payload":"privado"}'

4 · Ejemplo real

El ConnectionHub que ensambla registro + backplane:

public sealed class ConnectionHub
{
    private readonly ConcurrentDictionary<string, WebSocket> _local = new();
    private readonly ConnectionRegistry _registry;
    private readonly ISubscriber _sub;
    private readonly ILogger<ConnectionHub> _logger;
    private readonly string _nodeId;

    public ConnectionHub(IConnectionMultiplexer mux, ConnectionRegistry registry,
        string nodeId, ILogger<ConnectionHub> logger)
    {
        _sub = mux.GetSubscriber();
        _registry = registry; _logger = logger; _nodeId = nodeId;

        // suscripción del backplane (se re-inscribe tras reconexión — M6-04)
        _sub.SubscribeAsync("hub:events", OnEvent);
        _sub.SubscribeAsync("hub:direct", OnDirect);
    }

    private async void OnEvent(RedisChannel ch, RedisValue value)
    {
        var evt = JsonSerializer.Deserialize<HubEvent>(value!);
        if (evt is null || evt.From == _nodeId) return;         // no loop auto

        if (evt.Type == "broadcast")
            await SendToAllAsync(JsonSerializer.Serialize(evt.Payload));
    }

    private async void OnDirect(RedisChannel ch, RedisValue value)
    {
        var req = JsonSerializer.Deserialize<DirectRequest>(value!);
        if (req is null) return;
        if (_local.TryGetValue(req.To, out var ws))
            await ws.SendAsync(JsonSerializer.Serialize(req.Payload));   // yo lo tengo
    }

    public async Task BroadcastAsync(object payload)
    {
        // Reenvío local + publicar (o solo publicar y dejar que el
        // suscriptor local reenvíe también). Elegimos: publicar + reenviar local.
        await SendToAllAsync(JsonSerializer.Serialize(payload));        // a los míos
        await _sub.PublishAsync("hub:events",
            JsonSerializer.Serialize(new HubEvent("broadcast", payload, _nodeId)));
    }

    public async Task SendToAsync(string connectionId, object payload)
    {
        // dirigido: si soy el dueño, envío local; si no, publico
        if (_local.ContainsKey(connectionId))
            await _local[connectionId].SendAsync(JsonSerializer.Serialize(payload));
        else
            await _sub.PublishAsync("hub:direct",
                JsonSerializer.Serialize(new DirectRequest(connectionId, payload, _nodeId)));
    }

    private async Task SendToAllAsync(string json)
    {
        foreach (var ws in _local.Values)
            await ws.SendAsync(json);
    }
}

Broadcast: un suscriptor por nodo reenvía; dirigido: el dueño (del diccionario local) responde solo.

6 · Errores habituales

Broadcast doble local (reenvías tú + el suscriptor)

// ❌ en OnEvent reenvías a TODOS, y BroadcastAsync también lo hizo local
// ✅ usa un patrón coherente:
//    (A) publish + reenviar local, y en el suscriptor NO reenviar si from == tú
//    (B) publish solo, y el suscriptor siempre reenvía a sus sockets

Ignorar errores al reenviar (socket muerto)

Si SendAsync falla (cliente se desconectó), captura y llama a UnregisterAsync para que el registro no quede sucio.

7 · Ejercicio guiado

  1. Paso 1: Implementa ConnectionHub (o una versión reducida) en tu proyecto.
  2. Paso 2: Levanta 2 clientes WebSocket en «nodos» distintos (aunque en una sola máquina, con GUID de nodo distinto).
  3. Paso 3: Prueba broadcast: los 2 reciben. Prueba dirigido: solo el target.
  4. Paso 4: Añade el filtro from == _nodeId y verifica que no hay duplicados.

8 · Reto

🎯 ¿A quién le toca?

Diseña «broadcast a los participantes de un canal» (no a todos): el remitente consulta el set chan:<name>, y… ¿publica una lista? ¿o cada nodo filtra por su diccionario? Justifica la elección y escríbelo como flujo con la estructura de datos que usarías (M2-03).

9 · Resumen

  • Broadcast = publica en hub:events; cada nodo reenvía a sus sockets.
  • Dirigido = consulta registro → dueño envia (o publica en hub:direct).
  • Anti-loop: from + filtro; el callback de suscripción hace poco trabajo.

10 · Preguntas frecuentes

¿Cuántos nodos puede aguantar este backplane?

Decenas con facilidad si el volumen de mensajes es moderado y el payload es pequeño: el cuello suele estar en el reenvío local y en el volumen global de pub/sub, no en Redis.

¿Y si un nodo muere mid-reenvío?

Algunos sockets se pierden; la expiración del registro y el re-registro de clientes al reconectar lo reconcilian (M7-04). Diseña reconexión en el cliente.
