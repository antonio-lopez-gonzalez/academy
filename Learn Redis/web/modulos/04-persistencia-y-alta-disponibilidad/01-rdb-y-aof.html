Persistencia: RDB vs AOF

Módulo 4 · Persistencia y Alta Disponibilidad ⏱ 35 minutos

1 · Introducción

«Redis es volátil» es un mito a medias: puede persistir en disco con dos estrategias — RDB (snapshots) y AOF (log de escrituras). Entender su diferencia define cuánto «toleras perder» al reiniciar.

Para tu hub: la mayoría de datos son presencia efímera (da igual perderlos), pero si metes sesiones o streams de auditoría, la persistencia importa.

2 · Teoría

RDB (Redis Database File)

  • Qué: un snapshot binario del keyspace completo en un momento dado.
  • Cómo: SAVE (bloquea, no usar) o BGSAVE (fork en background).
  • Config: «save 900 1 300 10 60 10000» → guarda si hay ≥N cambios en X s.
  • Pro: compacto, restauración rapidísima, ideal para backups.
  • Contra: puedes perder lo escrito desde el último snapshot.

AOF (Append Only File)

  • Qué: log de cada operación de escritura, reproducido al arrancar.
  • Config: appendfsync always|everysec|no — cuánto toleras perder.
  • Pro: pierdes ≤1 s (everysec) o nada (always).
  • Contra: más pesado; puede reescribirse (BGREWRITEAOF) para compactarlo.

En la práctica moderna: Redis 7+ recomienda combinar (RDB base + AOF incremental (AAOF híbrido)) o directamente aof-use-rdb-preamble yes. Para muchos casos, AOF «everysec» es el equilibrio.

Persistencia y TTL

Las keys con TTL se restauran con su vida restante (no «reviven»). Snapshot y log incluyen el TTL — tu presencia sigue caducando tras un reinicio.

3 · Ejemplo mínimo

CONFIG GET save
CONFIG GET appendonly
CONFIG SET appendonly yes
CONFIG SET appendfsync everysec
SAVE                  # (cuando puedas) snapshot ahora
BGSAVE                # snapshot en background (recomendado)
LASTSAVE              # timestamp del último snapshot

Tras BGSAVE, basta con un docker restart redis para ver los datos con persistencia.

4 · Ejemplo real

Docker Compose del proyecto con volúmenes y AOF encendido:

services:
  redis:
    image: redis:7.4-alpine
    command: ["redis-server", "--appendonly", "yes", "--appendfsync", "everysec"]
    volumes:
      - redis-data:/data      # ← la clave: volumen persistente
    ports:
      - "6379:6379"
volumes:
  redis-data:

Si el contenedor se destruye, los datos siguen en el volumen. Para tu hub, decide si la presencia necesita persistir (probablemente no: se regenera con heartbeats) o si los streams/sesiones sí (sí: AOF + volumen).

6 · Errores habituales

Usar SAVE en producción (bloquea)

# ❌ SAVE → pausa del servidor hasta terminar el snapshot
# ✅ BGSAVE / lastsave / snapshots programados

Pensar que «con volumen Docker ya estoy salvado»

El volumen guarda lo que Redis escribió: sin AOF/snapshots «activos», Redis no escribe casi nada en /data y al reiniciar vuelves a vacío según config.

7 · Ejercicio guiado

  1. Paso 1: Crea una key, hace BGSAVE y docker restart redis: debe seguir existiendo.
  2. Paso 2: Conecta INFO persistence y anota rdb_last_bgsave_status y aof_enabled.
  3. Paso 3: Cambia a AOF (CONFIG SET appendonly yes), escribe dos keys y reinicia: compruébalas.
  4. Paso 4: Borra las clave de prueba antes de seguir.

8 · Reto

🎯 Estrategia de backup

Define la política de persistencia de tu hub: ¿qué keys son «descartables» (presencia) y cuáles «deben sobrevivir» (si guardas algo)? Escribe la config de docker-compose que aplicarías (RDB para backups + AOF everysec) y cuándo harías un snapshot manual.

9 · Resumen

  • RDB: snapshot compacto, pierde lo posterior al último.
  • AOF: log de escrituras, pierde según fsync (everysec típico).
  • Volumen Docker + política de persistencia por tipo de dato.

10 · Preguntas frecuentes

¿Puedo tener RDB y AOF a la vez?

Sí, es lo habitual: AOF con prefijo RDB (aof-use-rdb-preamble yes) para cargar rápido y no perder mucho. Redis lo gestiona solo al arrancar.

¿Cuánta RAM ocupa el fork por BGSAVE?

Temporalmente dobla RAM (copy-on-write). En máquinas justas, programa los snapshots en horas de menor pico.
