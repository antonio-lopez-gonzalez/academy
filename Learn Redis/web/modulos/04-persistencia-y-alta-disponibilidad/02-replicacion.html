Replicación: primary/replica

Módulo 4 · Persistencia y Alta Disponibilidad ⏱ 35 minutos

1 · Introducción

La replicación es la base de toda alta disponibilidad: un servidor primary escribe y una replica copia en tiempo real. Ahí nace todo lo demás (Sentinel, Cluster).

Para tu hub, replica = tener una copia que no pierde datos si el nodo principal cae, y a la que puedas pivotar lecturas.

2 · Teoría

El modelo

PRIMARY (escribe/lee)
   │  stream de replicación (comandos aplicados)
   ▼
REPLICA (solo lectura, replica del primary)
   │
   └─ (opcional) sirve lecturas a algunas apps

- La replica arranca desde un RDB inicial + aplica comandos en vivo.
- SIEMPRE es read-only (config).
- Un error en la replica NO detiene al primary.

Asegurar las réplicas

# En la replica:
REPLICAOF host-ip port      # (o SLAVEOF en Redis viejos)
# Comprobar:
INFO replication             # role, master_link_status, offset
ROLE                        # role / replicas conectadas / offset

master_link_status:up y el offset al día = réplica sana (con lag 0).

Consideraciones importantes

  • Seguridad de datos: min-replicas-to-write / min-replicas-max-lag te dejan escribir solo si hay réplica sana (reduce lo que se puede perder).
  • Failover: réplica NO promociona sola (para eso Sentinel en M4-03).
  • No balances: en «un solo primary + una replica», NO repartas lecturas buscando escala — la réplica suele quedar reservada para HA. Balancear lecturas con réplicas es válido en algunos setups, no es el objetivo principal aquí.
  • Pub/Sub: los mensajes publicados se replican; los suscriptores de cada servidor reciben (cada nodo tiene sus suscriptores).

3 · Ejemplo mínimo

docker run -d --name redis-pri -p 6380:6379 redis:7.4-alpine
docker run -d --name redis-rep -p 6381:6379 redis:7.4-alpine

# En la replica:
docker exec -it redis-rep redis-cli REPLICAOF 127.0.0.1 6380

# Verificar:
docker exec -it redis-rep redis-cli INFO replication | Select-String role,master_link_status

Escribe SET k v en el primary y léelo en la replica: en ms ya estará.

4 · Ejemplo real

En docker-compose, un par con persistencia y sanidad:

services:
  redis:
    image: redis:7.4-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes: [redis-data:/data]
  redis-replica:
    image: redis:7.4-alpine
    command: ["redis-server", "--appendonly", "yes", "--replicaof", "redis", "6379"]
    volumes: [redis-replica-data:/data]
    depends_on: [redis]
volumes:
  redis-data:
  redis-replica-data:

Tu app escribe en redis; si cae, la réplica conserva el estado (hasta el failover automático del M4-03).

6 · Errores habituales

Leer de la réplica «por escalar» sin entender el lag

# ❌ Leer de réplica para "mejorar" sin tolerar lag: verás datos viejos
#    o estados inconsistentes en presencia ("¿está online?" con lag = sí)
# ✅ Reserva la réplica para HA/failover, o acepta el lag explícitamente
INFO replication   # mira master_repl_offset vs replica_repl_offset

Olvidar que la réplica es read-only

Intentar escribir en la réplica da «READONLY You can't write against a read only replica.» — no lo «arregles» escribiendo ahí.

7 · Ejercicio guiado

  1. Paso 1: Levanta primary (6380) y replica (6381) con Docker.
  2. Paso 2: Conecta la réplica (REPLICAOF 127.0.0.1 6380) y verifica INFO replication.
  3. Paso 3: Escribe en primary y leé en réplica; anota el lag observado.
  4. Paso 4: Añade min-replicas-to-write en el primary (config) y observa el comportamiento.

8 · Reto

🎯 Pivote manual

Simula una caída: detén el primary con datos y «promociona» la réplica a primary tú mismo (REPLICAOF NO ONE). Verifica que tus datos sobreviven y que la app podría re-apuntar. Anota los pasos exactos de ese runbook: lo reutilizarás con Sentinel en M4-03.

9 · Resumen

  • Primary escribe; replica copia en vivo y es read-only.
  • INFO replication: role, master_link_status, offsets.
  • min-replicas-to-write reduce pérdidas; la réplica no escala escrituras.
  • El failover automático lo aporta Sentinel (M4-03).

10 · Preguntas frecuentes

¿Las réplicas sirven para escalar lecturas?

Pueden, si tus lecturas toleran lag y son idempotentes. Para presencia/timing, el lag es fatal; lo habitual es reservarlas para HA.

¿Puede haber réplicas de réplicas?

Sí (cascada), útil en topologías grandes. Aquí basta el par simple.
