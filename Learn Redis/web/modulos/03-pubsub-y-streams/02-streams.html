Streams: XADD/XREAD/XREADGROUP y XACK

Módulo 3 · Pub/Sub y Streams ⏱ 40 minutos

1 · Introducción

Un stream es un log de mensajes persistido con IDs progresivos, que se puede leer hacia atrás o en vivo, y que soporta grupos de consumidores con confirmación (ack). Es la respuesta de Redis a «tengo mensajes que no deben perderse y varios workers que los procesan».

Verás el modelo (ID, entradas, grupos, PEL), los comandos clave y cómo encaja en el hub para, por ejemplo, el registro de eventos o el reprocesamiento.

2 · Teoría

El modelo de un stream

stream:trades  (append-only, acotable)
┌─────────────┬───────────────────────────────┬──────────────────────┐
│ ID (ms-seq) │  campos del mensaje           │  estado de consumo   │
├─────────────┼───────────────────────────────┼──────────────────────┤
│ 1723600000123-0 │ type=trade id=887        │  → grupo workers      │
│ 1723600000123-1 │ type=trade id=888        │    (XREADGROUP)       │
│ …                                             │    pending (PEL) ack │
└─────────────┴───────────────────────────────┴──────────────────────┘
  • ID: milisegundos-secuencia (auto hasta 2040; se puede personalizar a partir de 2040).
  • Entradas: pares campo/valor (como un hash plano por mensaje).
  • Grupos: varios consumidores leen particiones distintas del mismo stream.
  • PEL: Pending Entries List — mensajes entregados pero sin XACK.

Comandos

XADD stream:trades * type trade id 887      # añade (ID auto)
XLEN stream:trades
XRANGE stream:trades - + COUNT 10           # leer primeros N
XREAD COUNT 5 BLOCK 5000 STREAMS trades $   # en vivo (los nuevos, bloqueante)
XGROUP CREATE trades workers 0 MKSTREAM     # crea grupo de consumo
XREADGROUP GROUP workers consumidor-1 COUNT 5 STREAMS trades >   # tomar "no entregados"
XACK trades workers 1723600000123-0         # confirmar procesado
XGROUP DELCONSUMER trades workers c1     # quitar un consumidor
XGROUP DESTROY trades workers             # borrar el grupo
XTRIM trades MAXLEN ~ 1000                  # acotar tamaño (≈1000)
XDEL trades ID

> en XREADGROUP significa «los que aún no he entregado a este grupo»; luego los confirmas con XACK. Si un consumidor muere sin ack, los mensajes quedan pendientes (PEL) y otro puede retomarlos (XCLAIM/XPENDING).

3 · Ejemplo mínimo

XADD t '{"raw":"..."}'                       # ❌ el valor debe ser "campo valor"
XADD t * msg '{"type":"trade","id":1}'       # ✅ hash de entradas
XLEN t
XRANGE t - +

# grupos
XGROUP CREATE t workers 0 MKSTREAM
XREADGROUP GROUP workers w0 COUNT 1 STREAMS t >    # toma 1
XACK t workers 0-1                                 # confirma

Fíjate: XADD recibe pares campo valor, no un JSON plano.

4 · Ejemplo real

En el hub: persistir eventos «para auditoría/reproceso» mientras el backplane pub/sub atiende el tiempo real. Un stream como fuente de verdad de eventos:

// Productor (cualquier nodo)
var id = await db.StreamAddAsync("stream:trades", new NameValueEntry[]
{
    new("type", "trade"),
    new("id", "887"),
    new("node", _nodeId),
});

// Consumidores en grupo (workers)
await db.StreamCreateConsumerGroupAsync("stream:trades", "workers", "0", true);

while (true)
{
    var entries = await db.StreamReadGroupAsync("stream:trades", "workers", _consumerName, count: 10);
    foreach (var e in entries)
    {
        await ProcessAsync(e.Values.ToDictionary(v => v.Name!, v => v.Value));
        await db.StreamAcknowledgeAsync("stream:trades", "workers", e.Id);   // ack
    }
}
// Reintentos de mensajes huérfanos (murió sin ack):
var pending = await db.StreamPendingAsync("stream:trades", "workers");

Nada se pierde: si tu worker muere, los pendientes quedan en PEL y se reasignan.

5 · Buenas prácticas

HazEvitaPor qué
XACK tras procesar (idempotencia aparte)Saltarse el ackEl PEL crece y reenvía lo ya hecho (sé idempotente)
XTRIM MAXLEN para acotar la retenciónStreams que crecen sin finEl log «ilimitado» llena la RAM
Grupo = «uno consume»; XREAD solo = «todos leen»Mezclar XREAD y XREADGROUP a la vezLos grupos dividen el trabajo; el simple emite a todos
Reintentos con XCLAIM/XPENDINGMensajes que «se olvidan» si el worker muereEl PEL + XCLAIM permite reintentar sin perder

6 · Errores habituales

Pasar un JSON como «un solo valor» a XADD

XADD t '{"x":1}'          # ❌ error: espera "campo valor"
XADD t msg '{"x":1}'      # ✅ guarda un campo 'msg' con ese string
or
XADD t x 1                # ✅ varios campos planos

Faltar el ack → reenvíos infinitos al procesar sin idempotencia

Si procesas y NO confirmas, el mensaje sigue pendiente y puede reentregarse; diseña handlers idempotentes.

7 · Ejercicio guiado

  1. Paso 1: Crea un stream y añade 5 mensajes con type e id.
  2. Paso 2: Lee con XREAD desde el principio (XRANGE) y luego en vivo con BLOCK.
  3. Paso 3: Crea el grupo workers, lee con XREADGROUP y haz XACK de 2.
  4. Paso 4: Consulta XPENDING: los 3 sin ack siguen ahí. XCLAIM uno para «otro consumidor».

9 · Resumen

  • Stream = log persistido con IDs; XADD/XLEN/XRANGE/XREAD.
  • Grupos: XREADGROUP divide trabajo; XACK confirma; PEL permite reintentar.
  • Acota con XTRIM; sé idempotente en el procesado.

10 · Preguntas frecuentes

¿Los streams son «Redis» o un broker aparte?

Son una estructura de Redis. Por debajo, usan listpack/rax optimizados; para cargas moderadas reemplazan a RabbitMQ básico. Dicho esto, un broker dedicado da más garantías a escalas extremas.

¿Cómo evito el «efecto del reenvío»?

Confirmando (XACK) y siendo idempotente: procesar dos veces el mismo ID no debe duplicar efectos (any key/ID único en tu fuente).
