Cuándo usar pub/sub, streams o lists

Módulo 3 · Pub/Sub y Streams ⏱ 30 minutos

1 · Introducción

Redis te da tres herramientas de mensajería y saber cuál usar ahorra arquitecturas dolorosas: pub/sub (broadcast push, sin cola), lists (cola FIFO simple) y streams (log persistente con grupos y ack).

Esta lección es la «tabla que lo decide» y su aplicación a los flujos del hub.

2 · Teoría

La tabla de decisión

Necesitas…UsaMejor solución
Un mensaje llega a TODOS los suscriptores, en vivo, sin persistirPub/Subbackplane del hub (broadcast entre nodos)
Una cola FIFO simple, cero garantías extraListtareas ligeras por nodo
Cola con persistencia, grupos, ack, resetStreamtrades para auditoría/reproceso
Necesito leer historia / reprocesarStreampub/sub y lists lo pierden
Many-to-many con fan-out y confirmaciónStream + gruposcada grupo su «cola»

Comparación de garantías

CaracterísticaPub/SubListStream
PersistenciaNoEn memoria (persiste si RDB/AOF)Sí (log)
EntregaBroadcast (todos)FIFO (uno se lo lleva)Grupos: uno por consumidor
Confirmación (ack)NoNo (BRPOPLPUSH como truco)Sí (XACK)
Releer/historiaNoLRANGE parcialXRANGE / XREAD desde ID
CompatibilidadIdeal para broadcastColas cortasColas robustas

Regla mental para el hub

  • Broadcast entre nodos (mensajes a todos los clientes): pub/sub.
  • Trabajo «uno lo procesa» (auditoría, notificaciones): list (simple) o stream (robusto).
  • No uses pub/sub para «entregar una vez»: no hay ack ni cola.

El caso que más se equivoca: usar pub/sub para «tareas» pensando que funciona como cola. Un único consumidor, sin ack, con mensajes que se pierden → el peor sitio de pub/sub. Si alimentas un worker, list o stream.

3 · Ejemplo mínimo

Misma petición, tres semánticas distintas:

# 1) Broadcast (2 suscriptores lo reciben)
SUBSCRIBE ch                                                # A
PUBLISH ch hello        # A y B reciben; si no hay B, se pierde

# 2) FIFO (uno se lo lleva)
LPUSH q t1 t2
RPOP q                  # t1; el siguiente RPOP lo lleva t2

# 3) Stream con grupo (persistido + ack)
XADD s * type job id 1
XGROUP CREATE s workers 0 MKSTREAM
XREADGROUP GROUP workers w STREAMS s >    # entrega a w
XACK s workers 0-1                         # confirmado

4 · Ejemplo real

En el hub, conviven los tres:

FlujoNecesitoEstructura
Broadcast de un mensaje por todos los nodosTodos lo reciban, en vivo, sin historialPub/Sub hub:events
Conectar/desconectar (rollout de presencia)Señal push a todosPub/Sub hub:presence
Enviar emails/notificaciones (tareas ligeras)FIFO simple por nodoList queue:notify
Auditoría de trades + reprocesoLog persistido, grupos, ackStream stream:trades

Así, cada flujo usa la herramienta con las garantías que de verdad necesita.

6 · Errores habituales

«Quiero que el mensaje NO se pierda» usando pub/sub

# ❌ PUBLISH sin suscriptor = mensaje perdido
PUBLISH job '{"id":1}'

# ✅ XADD + XREADGROUP con ack
XADD job * id 1
XREADGROUP GROUP w c STREAMS job >

Mezclar la semántica en el mismo canal

Publicar «tareas» y «broadcasts» en el mismo canal obliga a cada suscriptor a distinguir por tipo; mantén dominios separados.

9 · Resumen

  • Pub/Sub: broadcast push, sin persistencia, sin ack.
  • List: FIFO simple, sin ack nativo, sin historial.
  • Stream: log persistido con grupos y ack (el robusto).
  • Regla: broadcast→pub/sub; one-shot simple→list; robusto/historia→stream.

10 · Preguntas frecuentes

¿Puedo usar streams como broker de "muchos a muchos"?

Sí: múltiples grupos (cada grupo = una audiencia) con su propio avance; el stream es el log compartido. Es más potente que una lista y más ordenado que pub/sub cuando hace falta re-jugar.

¿Cuándo una lista es "suficiente"?

Cuando el mensaje no necesita sobrevivir a un worker muerto (un cache de tareas de baja criticalidad, o el búfer de un worker de segundo plano).
