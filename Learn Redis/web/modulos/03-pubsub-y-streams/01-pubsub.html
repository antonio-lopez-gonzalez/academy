Pub/Sub: SUBSCRIBE/PUBLISH y el backplane del hub

Módulo 3 · Pub/Sub y Streams ⏱ 35 minutos

1 · Introducción

El pub/sub es el mecanismo push de Redis: un proceso publica en un canal y todos los procesos suscritos a ese canal reciben el mensaje al instante. Sin polling, sin cola intermedia.

Es la pieza que convierte tu hub en distribuido: cuando el nodo A recibe un broadcast, lo publica y el nodo B lo reenvía a sus clientes. Aquí verás el mecanismo exacto.

2 · Teoría

El flujo

PUBLISH  hub:events {"type":"trade",...}
   │
   ├────────────────────────►  Subscriptor A (nodo-1)    → reenvía a sus sockets
   └────────────────────────►  Subscriptor B (nodo-2)    → reenvía a los suyos
   (los que no están suscritos NO reciben nada; el mensaje NO se guarda)

Comandos

SUBSCRIBE hub:events            # suscribirse (quedarte en modo listener)
UNSUBSCRIBE hub:events
PSUBSCRIBE hub:*                # patrón (múltiples canales)
PUNSUBSCRIBE hub:*
PUBLISH hub:events '{"type":"trade"}'
PUBSUB CHANNELS                 # canales activos
PUBSUB NUMSUB hub:events        # nº de subscriptores del canal

Características (y límites) que debes conocer

PropiedadImplicación
Fire-and-forgetSi el mensaje llega a un canal sin suscriptores, se pierde. No hay persistencia
No es una colaTodos los suscritores reciben el mensaje (broadcast), no compiten por él
En memoria de la conexiónLa suscripción se pierde si la conexión a Redis se cae (re-suscribirse al reconectar)
Bloqueante para esa conexiónLa conexión que usa SUBSCRIBE queda dedicada a recibir; no la reuses para comandos normales
LatenciaMuy baja (event-loop); sirve para backplanes de tiempo real

¿Por qué para el hub? Necesitamos que «un mensaje llegue a todos los nodos» (broadcast), no que «uno solo lo consuma». El pub/sub modela exactamente eso. Para «que uno lo procese y confirme» usaríamos streams (M3-02).

3 · Ejemplo mínimo

# Terminal 1
docker exec -it redis redis-cli
SUBSCRIBE hub:events

# Terminal 2
docker exec -it redis redis-cli
PUBLISH hub:events '{"type":"connect","id":887}'
# → Terminal 1 imprime: message hub:events {"type":"connect","id":887}

4 · Ejemplo real

En .NET (StackExchange.Redis), el hub se suscribe una vez al arrancar y publica en cada evento:

// Al arrancar el nodo: suscribirse (ISubscriber) — nunca reutilizar esta
// conexión para operaciones normales del IDatabase
ISubscriber sub = mux.GetSubscriber();
await sub.SubscribeAsync("hub:events", (channel, payload) =>
{
    // Llega a TODOS los nodos; este nodo reenvía a sus sockets
    var evt = JsonSerializer.Deserialize<HubEvent>(payload!);
    if (evt?.Node == _nodeId) return;              // originó este nodo

    var connection = _connections.FirstOrDefault(c => c.UserId == evt!.UserId);
    if (connection is not null)
        await connection.SendAsync(payload);
});

// Al hacer un broadcast
await sub.PublishAsync("hub:events",
    JsonSerializer.Serialize(new HubEvent("broadcast", payloadJson, _nodeId)));

El filtro evt.Node == _nodeId evita reenvíos en bucle del mismo nodo.

6 · Errores habituales

Esperar que el mensaje «dure» para un cliente que no estaba

# ❌ Cliente se conecta DESPUÉS del publish → no recibe nada
# ✅ Para «mensajes que no deben perderse» → streams (M3-02)

Reusar la conexión suscrita

// ❌ Mismo ISubscriber + IDatabase sobre UNA sola conexión (bloqueo)
// ✅ Conexión/es independientes; si solo tienes una, usa multiplexer
//    y mantén la suscripción sin hacer llamadas normales en ese canal.

7 · Ejercicio guiado

  1. Paso 1: Reproduce el ejemplo mínimo con dos terminales.
  2. Paso 2: Prueba PSUBSCRIBE con hub:* y publica en hub:events y hub:presence.
  3. Paso 3: Con PUBSUB CHANNELS verifica qué canales están activos.
  4. Paso 4: Publica SIN subscriptores y confirma que no queda nada guardado (no hay «cola»).

8 · Reto

🎯 Desconexión limpia

Cuando un nodo muere, sus suscripciones desaparecen con la conexión. Diseña el protocolo «disconnect» del hub: ¿qué publica el nodo moribundo (o su health-check) para que los demás limpien sus referencias? Pruébalo publicando {"type":"node-down","node":"node-1"} y procesando en tus suscriptores.

9 · Resumen

  • Pub/Sub = broadcast push en tiempo real (SUBSCRIBE/PUBLISH/PSUBSCRIBE).
  • Fire-and-forget: no persiste, no compite (todos reciben).
  • Conexión dedicada y re-suscripción al reconectar.
  • Es el backplane del hub; para «uno consume y confirma», streams.

10 · Preguntas frecuentes

¿Qué pasa si Redis se reinicia estando suscrito?

La suscripción vive en la conexión; al reconectar, el cliente debe re-SUBSCRIBE. El código resiliente lo re-inscribe (lo aseguramos en M6-04).

¿Puedo suscribirme a miles de canales?

Sí (patrones PSUBSCRIBE lo resuelven), pero vigila el volumen: cada mensaje de cada canal que te toca se procesa en tu proceso de suscriptor.
