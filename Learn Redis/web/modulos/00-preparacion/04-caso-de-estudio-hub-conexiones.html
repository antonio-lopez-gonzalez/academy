Caso de estudio: hub de conexiones WebSocket

Módulo 0 · Qué es Redis y el caso de uso ⏱ 30 minutos

1 · Introducción

Todo el curso lo aplicamos a un solo sistema real: el hub de conexiones de tu servidor WebSocket. Hoy defines con precisión qué problema resuelve Redis ahí, y por qué una solución «en memoria del proceso» deja de servir cuando escalas.

Esta lección es la brújula del curso: si entiendes el problema del hub, cada estructura de datos que verás luego tendrá dónde aterrizar.

2 · Teoría

El problema de un solo proceso

Con un nodo, guardas las conexiones en un ConcurrentDictionary<guid, WebSocket>: rápido y suficiente. El problema aparece con 2+ nodos:

Sin Redis:
Nodo A guarda conn 1..5000   ·   Nodo B guarda conn 5001..10000
   Pregunta "¿dónde está el usuario 42?"  →  A no lo sabe, B no lo sabe
   Broadcast a "todos"        →  A solo a sus 5000, B solo a los suyos
   Reinicio de A              →  se pierde su registro de conexiones

Con Redis (registro + backplane):
Redis guarda el "directorio" y los mensajes comunes:
   hub:conn:<id> = nodo  →  cualquier nodo sabe dónde vive el cliente
   hub:events     = canal  →  A publica, B recibe y reenvía a sus clientes

Las responsabilidades del hub con Redis

ResponsabilidadDónde viveEstructura
¿A qué nodo pertenece la conexión X?RedisHash hub:conn:<id> (o string)
¿Quién está conectado (presencia)?RedisSorted set con timestamp + TTL/limpieza
¿Quién lee el canal gaming?RedisSet chan:gaming
Broadcast de un mensaje a todos los nodosRedisPub/Sub hub:events
Enviar a un cliente concretoEl nodo dueñoBuscar en Redis el nodo y hacer SendAsync
Mensajes que no pueden perderseRedisStream stream:<type> con grupos

Un recorrido típico sin dolor

usuario 42 conecta a Nodo A
  A: HSET hub:conn:8632 node A userId 42
     ZADD hub:presence <ts> user:42
     SADD chan:general user:42
     PUBLISH hub:events {"type":"connect","user":42}

usuario 7 conecta a Nodo B
  ... ídem con B ...

"Nodo A" quiere enviar a TODOS (incluye los del B)
  A: PUBLISH hub:events {"type":"broadcast","payload":...}
  B: (suscrito) recibe → reenvía a sus clientes

Decisión clave: nada del estado del hub vive «solo en RAM del proceso». Incluso en un solo nodo, usar Redis desde el principio normaliza el modelo y facilita escalar mañana sin refactor.

3 · Ejemplo mínimo

El latido de un hub con Redis, todo en redis-cli:

# conectar a un nodo
HSET hub:conn:8632 node node-1 state open
EXPIRE hub:conn:8632 30        # presencia temporal

# otro nodo consulta "¿dónde está 8632?"
HGET hub:conn:8632 node        # → "node-1"

# desconexión o expiración
DEL hub:conn:8632

4 · Ejemplo real

La versión «de verdad» añade la atomicidad y el pub/sub. Un fragmento del proyecto final (adelanto, M6/M7 lo detalla):

// ConnectionHub (el proyecto redis-ws-hub hará esto)
var db = mux.GetDatabase();
var sub = mux.GetSubscriber();

// Registrar conexión en el nodo local
var key = $"hub:conn:{connectionId}";
await db.HashSetAsync(key,
    [new HashEntry("node", _nodeId), new HashEntry("userId", userId)]);
await db.KeyExpireAsync(key, TimeSpan.FromSeconds(30));   // TTL = presencia

// Publicar el evento al resto de nodos
await sub.PublishAsync("hub:events",
    JsonSerializer.Serialize(new { type = "connect", userId, node = _nodeId }));

Fíjate: hash + TTL + pub/sub. Son las tres piezas que el resto del curso enseña una a una.

6 · Errores habituales

Guardar el WebSocket en Redis

// ❌ Intento (imposible): Redis no guarda sockets ni objetos live
_ = db.StringSetAsync("conn:1", socket);   // no funciona así

// ✅ Redis guarda el DIRECTORIO (¿en qué nodo está?) y
//    el socket vive en la RAM de su nodo
await db.StringSetAsync("conn:1", "node-1", TimeSpan.FromSeconds(30));

Broadcast solo local (se le olvidan los demás nodos)

Dar «broadcast» reenviando solo a las conexiones del proceso actual deja sin mensaje a los clientes de otros nodos. Siempre publica en el canal común y que cada nodo reenvíe a sus sockets.

8 · Reto

🎯 El mapa del hub

Diseña el plano de keys de tu hub: qué keys crearás para el registro (por conexión y por nodo), la presencia, los canales y las métricas. Incluye el TTL de cada una. Al terminar el curso, valida tu plano contra el proyecto final.

9 · Resumen

  • El hub necesita estado compartido que no vive en la RAM de un proceso.
  • Trío de piezas: string/hash (directorio), TTL (presencia), pub/sub (backplane).
  • Redis guarda «dónde está» y «quién lo sabrá», no el socket.

10 · Preguntas frecuentes

¿Y si solo tengo UN nodo? ¿Merece la pena Redis?

Sí como diseño: modelo igual, y cuando crezca no reescribes. Pero si tu hub es pequeño y no planeas escalar, un Dictionary + reintentos en cache es aceptable. El criterio es escala y disponibilidad.

¿No vale SignalR + backplane para esto?

SignalR con Redis backplane te da un hub gestionado; nuestro curso te da el «por qué» y el control de bajo nivel con StackExchange.Redis para que entiendas qué ocurre debajo (y puedas implementarlo sin SignalR).
