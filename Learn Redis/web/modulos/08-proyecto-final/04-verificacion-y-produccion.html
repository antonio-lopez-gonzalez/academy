Verificación, docker-compose y puesta en marcha

Módulo 8 · Proyecto Final ⏱ 45 minutos 🟢 proyecto

1 · Introducción

Cierre: un checklist de verificación, el docker-compose «listo para producción dev» y el runbook. Cuando lo taches todo, tu servidor WebSocket ya escala con Redis.

2 · Teoría

Checklist end-to-end

  1. Redis levanta (Docker) y /health/redis responde (PING, hitRatio, clients).
  2. 2-3 instancias del hub con NODE_ID únicos corriendo.
  3. Clientes en distintos nodos: broadcast global, envío dirigido al dueño.
  4. Registro: HGET hub:conn:<id> node coincide con el nodo real.
  5. Presencia: ZRANGEBYSCORE lista a los online de la ventana.
  6. Desconexión limpia: unregister borra hash y zset al instante.
  7. Caída de un nodo: en ~TTL la presencia/registro expiran solos.
  8. Caída de Redis: la app degrada (modo local) y al volver re-registra y re-suscribe.

docker-compose para desplegar (añadir réplica es opcional)

services:
  redis:
    image: redis:7.4-alpine
    command: ["redis-server", "--appendonly", "yes"]
    ports: ["6379:6379"]
    volumes: [redis-data:/data]
  hub-a:
    build: ./src/RedisWsHub
    environment:
      - ConnectionStrings__Redis=redis:6379
      - NODE_ID=hub-a
    ports: ["5210:80"]
    depends_on: [redis]
  hub-b:
    build: ./src/RedisWsHub
    environment:
      - ConnectionStrings__Redis=redis:6379
      - NODE_ID=hub-b
    ports: ["5211:80"]
    depends_on: [redis]
volumes:
  redis-data:

Sustituye el puerto interno por el que use tu imagen (80 vs 5210) según tu Dockerfile; lo importante es el patrón: DB compartida + N servicios idénticos con id único.

Puesta en marcha (runbook corto)

  • Escalar: añade otra instancia con NODE_ID nuevo + puerto; no toques código.
  • Tokens/secret: connection string de Redis por secreto del entorno.
  • Monitorizar: health/redis + métricas INCR de mensajes (stats:*) + RedisInsight de la memoria.

4 · Ejemplo real

El «cierra y abre» con Docker que harás en tu máquina:

cd proyectos/redis-ws-hub
docker compose up -d
# Redis arriba + RedisInsight en http://localhost:8001

dotnet run --project src/RedisWsHub --urls http://localhost:5210
# en otra terminal:
NODE_ID=node-2 dotnet run --project src/RedisWsHub --urls http://localhost:5211

# prueba rápida con un cliente (red de browsers): conectar a ambas, broadcast, observar ambos.

Si todo responde, tu hub es distribuido. Felicidades: caché + registro + backplane en Redis funcionando con StackExchange.Redis.

6 · Errores habituales

Olvidar que en producción el puerto del contenedor ≠ 80

# ❌ El health apunta a host:5210 pero la imagen escucha otra interna
# ✅ Depende de tu Dockerfile: EXPOSE 8080 → ports ["5210:8080"]

«Puesta en marcha» sin test de fallover

Desplegar un hub distribuido y no probar la muerte de un nodo/Redis es cómputo de sorpresas; el checklist lo incluye.
