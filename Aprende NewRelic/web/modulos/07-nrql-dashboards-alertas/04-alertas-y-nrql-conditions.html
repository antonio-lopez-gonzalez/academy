Alert policies y NRQL conditions

Módulo 7 · NRQL, Dashboards y Alertas ⏱ 35 minutos

1 · Introducción

Un dashboard te avisa «cuando lo miras»; una alerta te avisa «cuando pasa». En New Relic defines alert policies que agrupan conditions; las condiciones NRQL vigilan un resultado de query y, al cruzar un umbral durante un tiempo, abren un incidente y notifican.

Verás la anatomía de una condición NRQL y tres alertas útiles para tu WebSocket.

2 · Teoría

La estructura

Alert policy (p. ej. "Operaciones WebSocket")
 └── Condition A: NRQL "Error rate > 2% durante 10 min"
 └── Condition B: NRQL "p95 latencia > 2 s durante 5 min"
 └── Condition C: NRQL "mensajes/min < N" (ausencia de señal)
 └── Notification channels (email, Slack, PagerDuty...)

En la UI: one.newrelic.com → Alerts & AI → Alert policies (AIP).

Anatomía de una condición NRQL

ParámetroQué controla
Query NRQLQué mides (debe devolver un único valor)
Window (evaluación)Cada cuánto y sobre qué duración (1-60 min) se evalúa
Threshold & durationUmbral y cuánto tiempo debe sostenerse para abrir incidente
Operator>, <, =, baseline…
Alert severityCritical / Warning

Qué NO debería ser una alerta

Alerta no es «todo lo que se me ocurrió». Una buena condición: señal clara, umbral con base histórica y consecuencia accionable (abrir incidente, notificar al turno). Alerta ruidosa → la ignoran.

3 · Ejemplo mínimo

Condiciones NRQL para tu WebSocket:

-- A) Tasa de error de transacciones del WebSocket
SELECT count(*) * 100.0 / (SELECT count(*) FROM Transaction WHERE name LIKE 'OtherTransaction/%')
FROM TransactionError
WHERE error.expected != true   -- TODO: + filtro app
-- Threshold: > 2 % durante 10 min → Critical

-- B) p95 de duración por tipo trade
SELECT percentile(duration, 95) FROM Transaction
WHERE name LIKE '%ProcessTrade%'
-- Threshold: > 2000 ms durante 5 min → Warning

La condición B te avisa cuando los trades se degradan sin que nadie mire.

4 · Ejemplo real

Política «Operaciones WebSocket»:

CondiciónQuery/filtroUmbral
Error rateTransactionError no esperados / Transaction del WS> 2% · 10 min · Critical
Latencia p95percentile(duration,95) de ProcessTrade> 2 s · 5 min · Warning
Cola retrasadapercentile(metricTimeslice.value,95) QueueLatencyMs> 1000 ms · 5 min · Warning
Mensajes en caídaSELECT rate(count(*),1 minute) FROM Transaction ... messageType='ping'< 10/min · 15 min (señal de nodo caído)

La «ausencia de señal» (última fila) es la clásica invisible: si tu servidor de pings se va, no hay dato que cruce un umbral alto — hay que alertar lo que deja de existir.

6 · Errores habituales

La query devuelve varias filas

-- ❌ FACET rompe la condición (más de un valor)
SELECT count(*) FROM Transaction FACET messageType

-- ✅ Devuelve UN valor para comparar con el umbral
SELECT count(*) FROM Transaction WHERE name LIKE 'OtherTransaction/%'

Olvidar el appName / el entorno en el filtro

-- ❌ WHERE name LIKE 'OtherTransaction/%'  (sin app: cuenta todo el account)
-- ✅ WHERE appName = 'NotificadorWebSocket' AND name LIKE ...

7 · Ejercicio guiado

  1. Paso 1: Ejecuta en Query Builder la query del p95 de ProcessTrade para ver su valor típico.
  2. Paso 2: Crea una alert policy «Operaciones WebSocket» y una condición NRQL para el p95 con umbral por encima de tu valor típico (p. ej. 2×).
  3. Paso 3: Espera un par de evaluaciones y verifica que aparece como «green/pending» (no dispara hoy).
  4. Paso 4: (Opcional) baja el umbral temporal para ver el incidente y vuelve a subirlo.

8 · Reto

🎯 La alerta que escribe el día

Diseña tu política de alertas definitiva (máx. 5 condiciones) con umbrales razonados a partir de tus percentiles históricos, y decide cuál es Critical y cuál Warning. Explica por qué no pusiste 15 alertas.

9 · Resumen

  • Política agrupa condiciones; condición NRQL = query de un valor + umbral + duración.
  • Alert de lo que deja de existir (ausencia de señal) además de los picos.
  • Umbrales con base histórica y severidad por fases.

10 · Preguntas frecuentes

¿Puedo usar una condición NRQL sobre una métrica custom?

Sí: FROM Metric WHERE metricName = 'Custom/QueueLatencyMs' con average(metricTimeslice.value) y el umbral.

¿Y si quiero que un grupo avise pero no abra incidente?

Las condiciones tienen severidades; o separas channels. La política controla quién se notifica; el incidente se abre con condición activa.
