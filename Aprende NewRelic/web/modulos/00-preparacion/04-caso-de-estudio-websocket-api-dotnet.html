Caso de estudio: servidor WebSocket + API en .NET

Módulo 0 · Observabilidad y New Relic ⏱ 30 minutos

1 · Introducción

Toda la teoría del curso se aplica sobre un solo sistema real: un servidor WebSocket + Minimal API en .NET 8 que recibe mensajes JSON con tipo de mensaje, fecha y hora y traceId. Es el mismo tipo de app que describes: conexiones persistentes, streaming de mensajes y algunos endpoints de API para consultas o administración.

El objetivo de esta lección: conocer la anatomía de ese sistema y entender por qué es exactamente el caso en el que el agente APM automático se queda corto — y por tanto donde más valor tiene la instrumentación custom que aprenderás.

2 · Teoría

El protocolo WebSocket

WebSocket arranca con un handshake HTTP (un GET común que pide upgrade) y luego deja abierto un canal full-duplex: cliente y servidor se envían frames en ambos sentidos sin rehacer la conexión. Para el agente de New Relic, ese handshake inicial sí se ve (es una transacción HTTP), pero los mensajes posteriores no.

La anatomía de un mensaje

Una buena práctica de diseño es un envoltorio JSON común para todo el tráfico de negocio:

{
  "type": "trade",
  "timestamp": "2026-08-31T10:15:00.123Z",
  "traceId": "8f6b2c1a9d4e7f3a2b1c9d8e7f6a5b4c",
  "messageId": "887",
  "payload": {
    "symbol": "EURUSDD",
    "price": 1.0842,
    "amount": 1000
  }
}
  • type: el tipo de mensaje (ping, trade, disconnect…) → perfecto para FACET.
  • timestamp: fecha y hora en ISO-8601 → sirve para latencias y para ordenar lo que llega tarde.
  • traceId: deja sitio en el protocolo para sembrar trazas distribuidas (Módulos 3-4).
  • messageId + payload: identidad y datos de negocio.

Qué hará el agente automáticamente y qué no

Parte del sistema¿La ve el agente solo?
Handshake/Upgrade del WebSocketSí (transacción HTTP)
Endpoints de la Minimal API (GET /api/status, POST /api/broadcast)Sí (transacciones web automáticas)
Procesamiento de cada mensaje del WebSocketNo → lo instrumentas tú
Llamadas a bases de datos / HTTP outbound conocidasSí (datastores y external services)

En una frase: el agente ve los bordes HTTP, no el corazón del mensaje. Traer el volumen de mensajes, sus latencias, errores y tipos a New Relic es exactamente lo que vas a aprender a hacer.

3 · Ejemplo mínimo

El modelo que usarás en el proyecto:

// El payload común de todos los mensajes del WebSocket
public sealed record MessageEnvelope(
    string Type,                 // tipo de mensaje: "ping", "trade", ...
    DateTimeOffset Timestamp,    // fecha y hora (ISO-8601) en la que se emitió
    string TraceId,              // traceId: identificador de la traza (32 hex)
    string MessageId,            // identidad del mensaje
    JsonElement Payload);        // el contenido de negocio sin tipar

6 · Errores habituales

Asumir que el WebSocket queda monitorizado por instalar el agente

// ❌ Instalar el agente y NO tocar el handler: los mensajes son invisibles
// ✅ Añadir instrumentación custom en el punto de recepción (Módulo 4)

El timestamp como mero decorado

Si el servidor procesa con retraso mensajes con su timestamp original, sin medir la latencia (diferencia con el reloj del servidor) pierdes la señal de «cola llena» o «red lenta». Mide DateTimeOffset.UtcNow - msg.Timestamp como atributo.

Usar el traceId del cliente como trust boundary

El valor llega del cliente. Sánalo (longitud/hex) antes de usarlo, o un cliente malicioso puede fabricar trazas falsas.

9 · Resumen

  • Caso de estudio = servidor WebSocket + Minimal API en .NET 8 con mensajes JSON.
  • Envoltorio común: type, timestamp, traceId, messageId, payload.
  • El agente ve los bordes HTTP; el procesamiento de mensajes requiere instrumentación custom.
  • El timestamp habilitó medir latencias end-to-end de la cola de mensajes.

10 · Preguntas frecuentes

¿Mi app no usa WebSocket; puedo continuar?

Sí. Todo lo que se enseña para «el corazón del mensaje» aplica a cualquier canal no instrumentado: colas (RabbitMQ, Azure Service Bus), gRPC, workers. Fíjate en los patrones, no en el transporte.

¿Por qué poner traceId en el payload en vez de solo en headers?

En HTTP usas headers (traceparent); en WebSocket no hay headers por mensaje, así que el propio mensaje es el carrier. Es la misma idea que almacenar los headers en las propiedades de un mensaje de cola.

¿Vale SignalR?

SignalR es WebSocket con caperuza. El agente instrumenta el ASP.NET Core subyacente; los húb y mensajes concretos siguen necesitando instrumentación custom con los mismos patrones del curso.
