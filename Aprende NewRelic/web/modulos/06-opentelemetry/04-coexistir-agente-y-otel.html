Coexistencia del agente APM con OTel

Módulo 6 · OpenTelemetry (OTLP a New Relic) ⏱ 30 minutos

1 · Introducción

No tienes que elegir entre agente y OTel en «o/o». En sistemas reales conviven: el agente aporta su APM rico, y OTel añade instrumentación que él no cubre. Lo que hay que ordenar es qué instrumento habla de qué, o duplicarás trazas y te confundirán los números.

Verás un patrón de coexistencia sensato para tu WebSocket y qué evitar a toda costa.

2 · Teoría

El principio de no-duplicación

Cada span de cada operación debe ser emitido por una fuente. Si el agente ya instrumenta el HttpClient (external span) y tú además creas un Activity OTel para la misma llamada, tendrás spans duplicados en el trace y en las métricas.

Regla práctica: reparto por capas

Capa                               Instrumento
──────────────────────────────────────────────────────
HTTP entrante (ASP.NET Core)  →    Agente (WebTransaction)
   ├─ HttpClient saliente     →    Agente (External) 
   └─ DB / Redis              →    Agente (Datastore)
Lógica del mensaje (WebSocket)→    OTel (ActivitySource custom)
   ├─ Parse/Validate          →    OTel (Activities hijos)
   └─ Llamadas HTTP           →    Agente (External, ya automat.)
Datos de negocio (OrderPlaced)→    Agente (RecordCustomEvent)

Es decir: el agente «caza» lo automático; OTel aporta lo custom que el agente no hace por diseño (spans de negocio bien anidados).

Cómo quedaría en trazas

Trace único (traceId común):
├─ Span (agente): WebTransaction/.../POST /api/broadcast
│   └─ Span (agente): http externo a precios
└─ Span (OTel): ProcessTrade          ← el custom (tu WebSocket)
    └─ Span (OTel): Validate
       └─ Span (OTel): Persist

Con el W3C de por medio, agente y OTel hablan el mismo traceparent: se unen en una sola traza aunque cada uno haya emitido spans de distinta capa.

3 · Ejemplo mínimo

La «frontera» en el código: el WebSocket usa OTel para la lógica; el agente sigue con su instrumentación automática. No te metas en el código de HttpClient del otro:

// OTel: la capa de negocio
using var act = Telemetry.Source.StartActivity("ProcessTrade");
act?.SetTag("messageType", msg.Type);

await _priceApi.GetAsync(symbol);   // ← esto lo mide el AGENTE (External), no OTel

// el Activity de OTel sigue abierto: contiene la duración total,
// y el span HTTP del agente aparece como hijo/externo

4 · Ejemplo real

Configuración híbrida en Program.cs:

// 1. AGENTE: lo tienes con NewRelic.Agent + env (guarda su APM)
//    NEW_RELIC_APP_NAME=NotificadorWebSocket (agente)

// 2. OTEL: SDK + exporter para la capa custom
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddSource("NotificadorWs")       // SOLO nuestro source custom
        // NO AddAspNetCoreInstrumentation ni HttpClient: eso ya lo hace el agente
        .AddOtlpExporter())
    .WithMetrics(m => m.AddMeter("NotificadorWs.Meters").AddOtlpExporter());

Clave: no actives instrumentaciones automáticas de OTel que ya cubre el agente para no duplicar. Lo custom, en tu Source; lo automático, al agente.

6 · Errores habituales

Activar instrumentaciones duplicadas en OTel

// ❌ Duplicas el HTTP: el agente ya emite el external span de HttpClient
.WithTracing(t => t
    .AddAspNetCoreInstrumentation()
    .AddHttpClientInstrumentation()   // ¡el agente ya hace esto!
    .AddSource("NotificadorWs"))

// ✅ Solo el source custom
.WithTracing(t => t.AddSource("NotificadorWs"))

Mezclar conceptos en el análisis

No compares «Transaction del agente» (duración de la petición) con «Activity de OTel» (duración de tu fase) sin saber que miran cosas distintas. Normaliza en tu dashboard qué cada uno significa.

7 · Ejercicio guiado

  1. Paso 1: En tu app con agente activo, añade OTel SOLO con tu Source (sin instrumentaciones duplicadas).
  2. Paso 2: Genera tráfico y consulta SELECT count(*) FROM Span FACET service.name.
  3. Paso 3: Revisa si algún SPAN aparece contado dos veces (traceId repetido en el mismo trace): señal de duplicidad.
  4. Paso 4: Ajusta el mapa de instrumentación hasta que no se duplique.

9 · Resumen

  • Agente y OTel coexisten: reparto por capas evita duplicados.
  • W3C los une en el mismo traceId.
  • No actives instrumentaciones OTel que ya cubre el agente.

10 · Preguntas frecuentes

¿El agente y OTel se "pisan" la propagación de context?

Pueden, si ambos injectan headers en la misma llamada. La regla: deja que solo uno haga la inyección automática (normalmente el agente), y OTel solo para tu lógica custom.

¿Merece la pena el híbrido para un WebSocket pequeño?

Si tu app es pequeña y el agente cubre todo lo que necesitas, no añadas OTel. El híbrido paga cuando necesitas instrumentación custom muy especializada o si buscas portabilidad futura.
