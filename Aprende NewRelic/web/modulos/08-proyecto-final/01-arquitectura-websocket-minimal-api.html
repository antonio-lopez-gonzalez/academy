Arquitectura: WebSocket + Minimal API

Módulo 8 · Proyecto Final ⏱ 40 minutos 🟢 proyecto

1 · Introducción

Llega el momento de unirlo todo. El proyecto final es proyectos/newrelic-ws-demo: un servidor WebSocket + Minimal API de .NET 8, instrumentado de punta a punta, que funciona sin licencia y revela todo su potencial cuando conectas el agente de New Relic.

En esta primera lección construimos la arquitectura limpia: separación transporte/negocio, el envelope JSON y el arranque del servidor. Es la base sobre la que cuelga toda la instrumentación de las lecciones 2-4.

2 · Teoría

La separación que hace observable

src/NewRelicWsDemo/
├── Program.cs                  ← endpoints API + /ws + DI
├── WsServer.cs                 ← transporte (socket): espera FUERA de la txn
├── Messages/MessageEnvelope.cs ← envelope JSON común + parse tolerante
├── Handlers/
│   ├── MessageDispatcher.cs    ← 1 transacción por mensaje + W3C + errores
│   ├── TradeProcessor.cs       ← span de trade + custom event "OrderPlaced"
│   └── PingProcessor.cs        ← span de ping + métrica
└── Services/PriceSimulator.cs  ← “servicio externo” simulado

Por qué así:

  • Transporte separado del negocio: el socket no sabe de New Relic; el negocio no depende del socket. (Testeable.)
  • Transacción en el sitio que importa: la crea MessageDispatcher.OnMessage, no el loop de receive.
  • Fases como spans: TradeProcessor con [Trace] da el árbol del trace.

El envelope JSON

// Messages/MessageEnvelope.cs (resumen)
public sealed record MessageEnvelope(
    string Type, DateTimeOffset Timestamp, string MessageId,
    Dictionary<string, string> TraceContext, JsonElement Payload)
{
    public static MessageEnvelope Parse(string json) { ... }
}

Clave: TraceContext es el carrier del W3C (traceparent/tracestate) que viaja dentro del mensaje — exactamente el pattern del M3-04 (Adaptación: TransportType.Other porque el enum no tiene WebSocket).

Envía un mensaje «trade» por WebSocket (aquí el detalle del payload que el MessageDispatcher interpreta):

{
  "type": "trade",
  "timestamp": "2026-08-31T10:15:00.123Z",
  "messageId": "887",

El servidor lo procesa (transacción + spans + evento + logs). En la lección 2 de este módulo verás la traza; en la 3 los datos de negocio; en la 4 el dashboard y la alerta.

6 · Errores habituales

Devolver una respuesta HTTP después del upgrade

// ❌ Devuelves Results.OK tras AcceptWebSocketAsync: la respuesta ya no
//    es HTTP y el patrón es confuso
// ✅ El endpoint mapea el WebSocket completo: upgrade → handle → return
app.Map("/ws", async (HttpContext ctx, MessageDispatcher dispatcher) =>
{
    if (!ctx.WebSockets.IsWebSocketRequest) return Results.BadRequest();
    using var socket = await ctx.WebSockets.AcceptWebSocketAsync();
    await WsServer.HandleAsync(socket, dispatcher);
    return Results.Empty;
});

8 · Reto

🎯 Añade un tipo de mensaje

Añade un tipo status al proyecto: crea un StatusProcessor con [Trace], y una métrica Custom/StatusLatencyMs. Mantén el switch del dispatcher y el log de negocio coherentes. Verifica que compila y testea que el envelope lo parsea.

9 · Resumen

  • Arquitectura: transporte (WsServer) ↔ negocio (Dispatchers) ↔ envelope (JSON).
  • La transacción del mensaje vive en MessageDispatcher; el receive, fuera.
  • El proyecto compila y funciona sin licencia en modo no-op.

10 · Preguntas frecuentes

¿Para qué sirve el endpoint /agent?

Para debug de configuración: te dice si tienes la licencia y el app_name puestos (y un hint de cómo adjuntar el profiler). No es el «check de carga»: eso se lee en el log del agente.

¿Puedo usar SignalR en lugar del WebSocket puro?

Sí. La arquitectura (transporte → negocio → envelope) lo permite; cambias solo WsServer por el Hub y delegas igual en MessageDispatcher.
