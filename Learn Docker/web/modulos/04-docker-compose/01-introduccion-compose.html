Qué es Compose y por qué existe

Módulo 4 · Docker Compose ⏱ 30 minutos

1 · Introducción

Hasta ahora has lanzado contenedores de uno en uno con docker run. Eso funciona muy bien para un solo servicio, pero el caso de estudio HarborTasks necesita tres: web (nginx), api (Node/Express) y postgres. Y una aplicación real de producción necesita muchos más: API, base de datos, caché, cola de mensajes, worker, migraciones…

En este módulo aprenderás Docker Compose: la herramienta oficial de Docker para definir y ejecutar aplicaciones multi-contenedor como una sola unidad. En lugar de memorizar diez comandos docker run con sus flags, declaras el sistema completo en un archivo compose.yaml y lo levantas con un único comando: docker compose up.

¿Por qué existe esta lección?

Antes de escribir YAML hay que entender el problema: por qué orquestar contenedores a mano se rompe, por qué «declarar» es mejor que «scriptear», y qué cambió entre la v1 (docker-compose) y la v2 (docker compose). Si entiendes esto, cada clave del compose.yaml de las próximas lecciones tendrá sentido por sí sola.

2 · Teoría

El problema: múltiples contenedores enlazados

Un contenedor aislado casi no sirve en una aplicación real. La API necesita hablar con Postgres, la web necesita servir archivos al navegador, y el navegador necesita llamar a la API. Eso significa varios contenedores en la misma red, con variables de entorno, volúmenes y puertos coordinados. Mira lo que cuesta arrancar dos servicios «a mano»:

# Base de datos (Módulo 3: volumen + env + red)
docker network create harbor-net
docker run -d --name harbor-postgres --network harbor-net \
  -e POSTGRES_USER=harbor -e POSTGRES_PASSWORD=harborpass -e POSTGRES_DB=harbortasks \
  -v pgdata:/var/lib/postgresql/data postgres:16-alpine

# API: depende de la base, de la red y de la pwd correcta
sleep 10                             # adivinar el tiempo de arranque de Postgres…
docker run -d --name harbor-api --network harbor-net \
  -e DATABASE_URL=postgres://harbor:harborpass@postgres:5432/harbortasks \
  -p 3000:3000 harbortasks-api:1.0.0

# Código de "limpieza" que hay que recordar
docker rm -f harbor-api harbor-postgres
docker network rm harbor-net

Esto solo son dos servicios. Ahora multiplica por cinco, añade un worker, una cola, y dos o tres entornos (dev, staging, prod). Cada contenedor es un comando interminable, el orden de arranque importa, un flag mal escrito se descubre a los veinte minutos, y nada de esto queda documentado salvo en tu historial de terminal.

Analogía: cocinar para muchos invitados

Cocinar diciéndole a una persona a la vez «hierve el agua, ahora corta la cebolla, ahora enciende el horno, repite…» es lento, frágil y nadie más puede repetirlo igual. Una receta es declarativa: lista todos los ingredientes y los pasos, cualquiera puede seguirla y el resultado es reproducible. Pasar comandos uno a uno es cocinar sin receta; escribir compose.yaml es escribir la receta completa del sistema.

Declarar en vez de scripts

Hay dos filosofías para automatizar, y conviene distinguirlas porque el mismo principio reaparece en Kubernetes (Módulo 5):

Imperativo (script)Declarativo (Compose)
Describes cómo llegar al estado: «crea red, crea contenedor A, espera, crea B»Describes qué estado quieres: «existen los servicios web, api y postgres conectados por harbor-net»
El orden y el estado actual importan (si ya existe, falla o se duplica)Compose calcula qué falta: solo actúa sobre lo que ha cambiado
Difícil de revisar en git (¿qué cambió en el despliegue?)El diff del compose.yaml ES el cambio de infraestructura
Una condición especial = reescribir el scriptReconfigurar = editar una línea del YAML

Es el mismo giro que darás en Kubernetes con kubectl apply: declaras el estado deseado y la herramienta se encarga de alcanzarlo. Aprenderlo aquí te prepara para el Módulo 5.

Compose v2: docker compose (no docker-compose)

Históricamente Compose fue una herramienta Python separada, instalada aparte, invocada con guion: docker-compose up. Desde la v2, Compose vive integrado en el propio CLI de Docker como subcomando oficial:

docker compose version
# Docker Compose version v2.x  ← versión moderna (sin guion)
  • docker compose — subcomando del Docker CLI (Compose v2, Go). Es el que usaremos en todo el curso.
  • docker-compose — binario legacy (Compose v1, Python). Obsoleto y desaconsejado; si aparece en un tutorial, mejor buscar una versión actualizada.
¿Trae Docker Desktop Compose v2?

Sí. Docker Desktop incluye el plugin compose de serie. En Linux con Engine instalado «a mano», se instala como plugin con apt install docker-compose-plugin (o se descarga el binario de GitHub). Verifícalo siempre con docker compose version.

compose.yaml: «código de infraestructura local»

Un compose.yaml convierte tu stack en algo que se guarda en el repositorio, se revisa en un pull request, se comenta, se diffea y se replica en la máquina de cualquiera. Es el inicio de la filosofía Infraestructura como Código (IaC) aplicada al entorno local: la infraestructura deja de ser «cosas que hice en una terminal» y pasa a ser código versionado, como el resto de tu aplicación.

El stack multi-contenedor que declararemos

(navegador → http://localhost:8080) │ ▼ ┌──────────────────── red privada "harbor-net" (bridge) ────────────────────┐ │ │ │ ┌────────────────┐ :3000 ┌────────────────┐ :5432 ┌──────────┐ │ │ │ web │──────────► │ api │──────────► │ postgres │ │ │ │ nginx:1.27 │ hostname │ node:22 │ hostname │16-alpine │ │ │ │ alpine │ = servicio │ alpine │ = servicio│ + pgdata│ │ │ └────────────────┘ └────────────────┘ └──────────┘ │ │ │ │ │ │ bind mount de la web expone :3000 (interno) │ │ │ └────────────────────────────────────────────────────────────────────────────┘ Los contenedores se hablan por su NOMBRE de servicio ("postgres", "api"), no por IP: Docker gestiona el DNS interno de la red (Módulo 3, "Redes").

Con Compose, ese diagrama entero se escribe en un archivo y se levanta con un comando. Empieza a verlo con el ejemplo mínimo.

3 · Ejemplo mínimo

El Compose más pequeño posible: un archivo compose.yaml con un solo servicio (reutilizamos Postgres del Módulo 3):

compose.yaml
# compose.yaml — ejemplo mínimo: un contenedor solo, gestionado por Compose
# La clave de nivel superior "services" es OBLIGATORIA: ahí se definen los
# contenedores que forman la aplicación.
services:
  postgres:
    # Imagen oficial de PostgreSQL 16 sobre Alpine (ligera)
    image: postgres:16-alpine
    # Variables de entorno = los mismos "-e" que usabas en docker run
    environment:
      POSTGRES_USER: harbor
      POSTGRES_PASSWORD: harborpass
      POSTGRES_DB: harbortasks
    # Volumen "pgdata": persistencia de datos (equivalente a -v pgdata:...)
    volumes:
      - pgdata:/var/lib/postgresql/data
    restart: unless-stopped

# Un Compose también puede declarar sus propios volúmenes con nombre
volumes:
  pgdata:

Levántalo con un solo comando:

# Hace "pull", crea el contenedor, crea el volumen y lo arranca en segundo plano
docker compose up -d

# ¿Qué ha creado Compose? Todos los objetos se etiquetan con el proyecto
docker compose ps          # estado de los servicios del proyecto
docker volume ls           # aparece pgdata_ (volumen gestionado)

# Cuando termines: lo apaga Y lo elimina (contenedores + red del proyecto)
docker compose down

Línea a línea del comando: docker compose busca un archivo llamado compose.yaml (también acepta compose.yml y docker-compose.yml) en el directorio actual. up -d crea todo lo que falta y arranca en segundo plano (igual que -d de docker run). down hace lo contrario y elimina la red del proyecto. Nota importante: por defecto down no borra los volúmenes — así tus datos sobreviven.

4 · Ejemplo real

Compara ahora el «antes» y el «después» para el servicio web de HarborTasks, el mismo que lanzaste con docker run en los módulos anteriores:

Antes: un docker run largo a recordar

# Cada flag es un riesgo de error; y esto es UNA sola pieza del stack…
docker run -d --name harbor-web --restart unless-stopped \
  -p 8080:80 \
  -v "$PWD/web:/usr/share/nginx/html:ro" \
  -v "$PWD/docker/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  nginx:1.27-alpine

Después: la misma pieza, declarada

compose.yaml
name: harbortasks   # nombre del proyecto: prefijo de contenedores, red y volúmenes

services:
  web:
    image: nginx:1.27-alpine                # ← el mismo "nginx:1.27-alpine" del docker run
    restart: unless-stopped                 # ← el mismo "--restart"       del docker run
    ports:
      - "8080:80"                           # ← el mismo "-p 8080:80"      del docker run
    volumes:
      - ./web:/usr/share/nginx/html:ro               # ← el primer  "-v"
      - ./docker/nginx.conf:/etc/nginx/conf.d/default.conf:ro  # ← el segundo "-v"

Mismo resultado, pero ahora: el comando correcto está en el repo, cualquiera lo levanta con docker compose up -d, y si alguien cambia el puerto o añade un volumen, ese cambio aparece en el historial de git. Cuando en la lección 4 declaras web + api + postgres juntos, la ventaja se multiplica: red, orden y entorno se gestionan solos.

docker run no desaparece

Compose no reemplaza a docker run para tareas puntuales (docker run --rm -it node:22-alpine node -v para probar algo rápido sigue siendo perfecto). Compose es para aplicaciones de varios contenedores con ciclo de vida largo. La regla práctica: ¿lo vas a levantar más de una vez o tiene dependencias? → Compose.

6 · Errores habituales

Seguir usando docker-compose (v1)

# ❌ Comando legacy: puede no estar instalado o quedar obsoleto
docker-compose up -d
#  docker-compose: command not found   ← error típico

# ✅ Compose v2, integrado en el Docker CLI
docker compose up -d

Añadir version: al archivo (ya no hace falta)

# ❌ "version:" era un requisito de la v1 y hoy es ignorado (o genera warning)
version: "3.8"
services:
  web:
    image: nginx:1.27-alpine

# ✅ En Compose v2 se omite: el motor ya conoce la especificación
services:
  web:
    image: nginx:1.27-alpine

Orquestar con un script imperativo en vez de declarar

# ❌ La api se lanza "a ojo" esperando que postgres ya esté listo
docker run -d postgres:16-alpine
sleep 10 && docker run -d -e DATABASE_URL=... api
# → si postgres tarda 12s, la api arranca con la conexión rota

# ✅ (Próxima lección) el compose declara la relación y el orden
# depends_on: postgres  → Compose calcula el arranque por ti

7 · Ejercicio guiado

Objetivo: crear tu primer proyecto Compose (un servicio de Postgres) y comprobar que Compose orquesta el ciclo de vida completo: up, inspección, ejecución interna y down.

  1. Crea una carpeta de trabajo y entra en ella. 
    mkdir -p ~/proyectos/mi-stack && cd ~/proyectos/mi-stack
    Windows / macOS

    En Windows trabaja dentro de WSL2 (la carpeta en el FS de Linux, ~/proyectos/…). En macOS/Linux, cualquier ruta de tu home vale.

  2. Crea compose.yaml con un solo servicio (copia el «ejemplo mínimo» de la sección 3). Verifica que el archivo es válido: 
    docker compose config
# Imprime el compose "resuelto" (con defaults aplicados). Sin errores = YAML bien formado
  3. Levanta el stack y observa lo que Compose crea: 
    docker compose up -d
docker compose ps     # STATUS: Up (healthy cuando haya healthcheck) o Up
  4. Entra en el contenedor y comprueba que Postgres responde (DNS interno y variables que declaraste): 
    docker compose exec postgres psql -U harbor -d harbortasks -c "SELECT 1 as ok;"
#  ok
# ---- 
#   1
  5. Apaga todo y confirma el estado limpio: 
    docker compose down
docker compose ps        # sin servicios (lista vacía)
docker volume ls | grep pgdata   # el volumen SIGUE existiendo (down no borra datos)

8 · Reto

🎯 Convierte tu propio docker run en Compose

Recupera el comando docker run del servicio api del Módulo 3 (o el del ejemplo de la sección 2) y tradúcelo a un servicio dentro de tu compose.yaml: imagen node:22-alpine, variable DATABASE_URL apuntando a postgres (el nombre de servicio, no localhost), puerto 3000:3000 y red compartida con el servicio postgres.

Pista: un servicio puede declarar la red a la que se conecta con la clave networks:, y la red hay que declararla a nivel superior. Recuerda que la API NO sabe nada del nombre de contenedor: usa el nombre de servicio como hostname.

9 · Resumen

  • Compose resuelve el problema de orquestar aplicaciones multi-contenedor que docker run vuelve ingobernable.
  • Es declarativo: describes el estado deseado (services:, networks:, volumes:) y Compose crea, actualiza o elimina solo lo que falta.
  • La v2 es docker compose (integrada en el CLI); la v1 (docker-compose, Python) está obsoleta.
  • El compose.yaml es código de infraestructura: se versiona, se revisa y se reproduce en cualquier máquina.
  • El mismo giro declarativo aparecerá en Kubernetes (Módulo 5) con kubectl apply.
ComandoQué hace
docker compose versionMuestra la versión de Compose v2 (verificas que el plugin existe)

docker compose exec <svc> <cmd>Ejecuta un comando dentro del contenedor de un servicio (como docker exec)

10 · Preguntas frecuentes

¿Qué diferencia hay entre docker-compose.yml y compose.yaml?

Ninguna funcional: Compose acepta compose.yaml, compose.yml y el legacy docker-compose.yml, en ese orden de prioridad. La convención actual es compose.yaml, así que úsala para no arrastrar el nombre de la v1.

¿Compose funciona en producción?

Compose es ideal para desarrollo local, entornos de prueba y CI. En servidores de producción pequeños puede funcionar, pero no ofrece alta disponibilidad, escalado entre máquinas ni auto-reparación: eso es exactamente lo que Kubernetes añade (Módulo 5). Compose es el paso natural antes de dar el salto.

¿Qué pasa si no tengo Docker Compose instalado?

Con Docker Desktop ya viene activado. En Linux, instala el plugin con sudo apt install docker-compose-plugin (Debian/Ubuntu) y verifica con docker compose version. Sin sudo como requisito del curso: tu usuario ya debe estar en el grupo docker.

¿Por qué la api debe conectar con «postgres» y no con «localhost»?

Porque cada contenedor tiene su propio namespace de red: localhost dentro del contenedor de la api es ese contenedor, no el host. Dentro de una red Docker, los servicios se resuelven por su nombre (el DNS del bridge lo gestiona Docker). Es el mismo mecanismo que viste en «Redes Docker» (Módulo 3).
