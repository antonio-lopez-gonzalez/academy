Redes bridge, host y DNS interno

Módulo 3 · Datos y redes Docker ⏱ 30 minutos

1 · Introducción

En el Módulo 2 viste cómo exponer un puerto del contenedor hacia el host con -p. Pero un contenedor casi nunca viaja solo: la API de HarborTasks necesita hablar con Postgres, la web con la API. Y aquí aparece la gran confusión de quien empieza: ¿cómo se comunican dos contenedores entre sí?

Esta lección responde a esa pregunta. Verás cómo Docker conecta contenedores por defecto en una red bridge, por qué esa red de fábrica no tiene DNS por nombre y cómo una red bridge definida por el usuario añade resolución por nombre de servicio. También verás los modos host y none, por qué localhost no llega a otro contenedor, y por qué la red host se comporta distinto en macOS y Windows.

¿Por qué existe esta lección? Porque el aislamiento de red es una de las bases de seguridad de Docker, y porque en cuanto tienes más de un contenedor (esto es, en cuanto tu app es real) necesitas nombres estables para hablar entre servicios. Entender la topología de red te evita el comando docker inspect buscando IPs que cambian en cada recreación.

2 · Teoría

Cada contenedor vive en su propio "edificio"

Cada contenedor recibe su propio network namespace: una caja de red aislada con su propia interfaz, su propia tabla de rutas y su propia pila TCP/IP. Imagina un edificio de oficinas donde cada despacho (contenedor) tiene su propio teléfono e interfaz, y solo una centralita (el bridge) los conecta entre sí y con el exterior.

                ┌─────────────── HOST (tu máquina) ───────────────┐
                │                                                 │
                │     Contenedor A        Contenedor B            │
                │   ┌─────────────┐     ┌─────────────┐           │
                │   │  eth0: 172. │     │  eth0: 172. │           │
                │   └──────┬──────┘     └──────┬──────┘           │
                │          │  veth             │  veth             │
                │   ┌──────┴───────────────────┴──────┐           │
                │   │        bridge  (docker0)        │           │
                │   └──────┬────────────────────┬─────┘           │
                │          │   (NAT / iptables)  │                 │
                │          ▼                     ▼                 │
                │   eth0 del host: 192.168.x.x   puerto -p 8080   │
                └──────────┴─────────────────────┴─────────────────┘
                       a internet / tu red local

Lo importante de este diagrama: los contenedores no comparten la interfaz del host. Para salir a internet usan NAT (el host traduce sus direcciones privadas a la suya propia), y para entrar desde fuera usan la publicación de puertos (-p): el host hace de portero escuchando en un puerto suyo y redirigiendo al contenedor.

La red bridge por defecto (bridge "default")

Se crea al instalar Docker y se llama bridge (el interfaz se llama docker0). Todo contenedor lanzado sin --network se une a ella, y recibe una IP del rango privado 172.17.0.x. Los contenedores de la misma red sí pueden verse entre sí por IP, pero aquí está el truco: en esta red por defecto NO hay resolución DNS por nombre.

Analogía: la red bridge por defecto es un edificio de oficinas donde cada despacho tiene número de planta-asiento (la IP) pero las puertas no tienen nombre. Puedes ir por número (por IP), pero nadie te dice "ve al despacho de Contabilidad": para eso hace falta un directorio, y ese directorio (el DNS interno) solo existe en las redes definidas por el usuario.

Red bridge definida por el usuario: DNS por nombre de servicio

Cuando creas tu propia red con docker network create nombre y lanzas contenedores con --network nombre, Docker levanta un DNS interno automático por red. Desde dentro de la red, cada contenedor es resoluble por su nombre de contenedor (el --name) y por sus aliases. ¿La consecuencia práctica? La API puede conectarse a la base de datos usando harborpostgres:5432 en vez de una IP que cambia cada vez que recreas el contenedor.

Además, las redes definidas por el usuario aportan aislamiento por defecto: un contenedor solo ve los contenedores de su misma red (a menos que lo conectes explícitamente a varias). Esto te permite separar zonas: red pública para la web, red privada para la base de datos.

Modo host: compartir la pila del host

Con --network host el contenedor no recibe su propio namespace: usa directamente la interfaz y las rutas del host. Escucha en localhost del host sin necesidad de -p, y es la opción de máxima velocidad y menor sobrecarga (no hay NAT, no hay veth). Pero pierdes el aislamiento de red y el puerto queda "ocupado" por el contenedor en todo el host.

⚠️ network_mode: host en macOS y Windows no es lo que parece. Tanto Docker Desktop (macOS y Windows) como WSL2 ejecutan los contenedores Linux dentro de una VM ligera: el "host" que ve el contenedor es esa VM, no tu máquina real. Resultado: el modo host no te da localhost real ni el acceso directo a la red del portátil, y su comportamiento varía. Regla práctica: usa bridge + publicación de puertos (-p) en macOS/Windows; reserva host para Linux nativo o para casos muy concretos (monitoreo, VPN) donde la velocidad de baja latencia importa.

Modo none: puro aislamiento

--network none deja al contenedor sin interfaz de red alguna, solo loopback. Es el grado máximo de aislamiento: úsalo para procesos de cómputo que no deben tocar red (procesar un batch, firmar datos, ejecutar untrusted code con red desactivada).

La clave del malentendido: localhost dentro de cada contenedor

Dentro de un contenedor, localhost/127.0.0.1 siempre apunta a sí mismo (a su propio namespace). Por eso, si la API intenta conectarse a localhost:5432 buscando a Postgres, falla: estás mirando dentro de tu propio edificio, no en el vecino. La comunicación entre contenedores usa siempre el nombre o la IP dentro de la misma red, y la comunicación desde fuera (tu navegador) usa el localhost del host con el puerto publicado.

3 · Ejemplo mínimo

Dos contenedores que se saludan por nombre gracias a una red definida por el usuario.

# 1) Crear una red bridge personalizada
docker network create demo-net

# 2) Lanzar un "servidor" que escucha y guarda lo que recibe
docker run -d --name servidor --network demo-net alpine sleep 3600

# 3) Lanzar un "cliente" en la MISMA red que resuelve por nombre
docker run --rm --network demo-net alpine ping -c 2 servidor
# ... esperado: "servidor" se resuelve a 172.18.0.2 y hace ping con éxito

# 4) Comprobar la topología de la red
docker network inspect demo-net

Desglose: al crear demo-net y lanzar servidor con --network demo-net, Docker registra el nombre servidor en el DNS interno de esa red. Por eso, sin conocer ninguna IP, el cliente pinga por nombre. Prueba a cambiar el --name o a lanzar el cliente en la red por defecto y verás fallar la resolución: el DNS interno no existe ahí.

4 · Ejemplo real

En HarborTasks, la API (Node/Express) debe hablar con la base de datos (Postgres). Voy a preparar la infraestructura que en la lección 3 completarás con el Postgres real: aquí montamos la red y la conectividad por nombre.

# 1) Red única para el stack HarborTasks: todo lo que está aquí se ve por nombre
docker network create harbortasks-net

# 2) La base de datos (en el volumen pgdata de la lección 1, red harbortasks-net)
docker run -d --name harborpostgres \
  --network harbortasks-net \
  -e POSTGRES_PASSWORD=secretito \
  -p 5432:5432 \
  postgres:16-alpine

# 3) La API, en la misma red; se conecta a la DB por NOMBRE, no por IP
docker run -d --name harborapi \
  --network harbortasks-net \
  -e PG_HOST=harborpostgres \
  -e PG_PORT=5432 \
  -p 3000:8080 \
  tu-registro/harbortasks-api:v1

# 4) Aislamiento: la WEB va en otra red de solo presentación
#    (así un contenedor comprometido no ve la DB sin más)
docker run -d --name harborweb \
  --network harbortasks-net \
  -p 80:80 \
  nginx:1.27-alpine

# 5) Diagnóstico: pedirle a la API que resuelva el nombre de la DB
docker exec harborapi sh -c "getent hosts harborpostgres"
# Salida esperada: la IP interna de harborpostgres dentro de harbortasks-net

Decisiones tomadas: nombres estables en vez de IPs — como las IPs cambian al recrear contenedores, la configuración de la API apunta a harborpostgres, que el DNS interno resuelve. Un solo -p 5432 publicado para poder usar psql desde el host durante el desarrollo, mientras que la comunicación API→DB viaja dentro de la red privada sin pasar por el host. Y la web no expone puerto de base de datos: se sirve por 80.

Nota: docker exec harborapi getent hosts harborpostgres consulta el DNS del sistema dentro del contenedor — la forma más rápida de confirmar que la resolución interna funciona. En alpine existe getent/ping; en imágenes node, puedes usar nslookup si está instalado, o simplemente dejar que tu driver de BD falle o conecte.

6 · Errores habituales

Conectarse a otro contenedor con localhost

# ❌ La API intenta llegar a Postgres vía localhost (apunta a sí misma)
docker run -d --name harborapi -e PG_HOST=localhost ...

# ✅ Misma red bridge del usuario + nombre del contenedor de la DB
docker network create harbortasks-net
docker run -d --network harbortasks-net --name harborpostgres postgres:16-alpine
docker run -d --network harbortasks-net -e PG_HOST=harborpostgres tu-registro/api:v1

Confiar en el DNS de la red por defecto (que no existe)

# ❌ En la red "bridge" por defecto NO hay resolución por nombre
docker run -d --name web1 nginx
docker run --rm alpine ping web1
# ✗ ping: bad address 'web1'  → el nombre no se resuelve

# ✅ Red definida por el usuario: DNS automático
docker network create mi-red
docker run -d --network mi-red --name web1 nginx
docker run --rm --network mi-red alpine ping -c 1 web1   # ✓ resuelve a 172.18.0.x

Recrear contenedores y que la "IP fija" cambie

# ❌ Anotar la IP de la DB con docker inspect y usarla en la config de la API
docker inspect harborpostgres | grep IPAddress   # 172.18.0.2 (cambiará al recrear)

# ✅ Configurar la API con hostname harborpostgres, no con IP
# -e PG_HOST=harborpostgres  → el DNS interno se encarga de la IP actual

Entrar a un contenedor con --network host en macOS/Windows

# ❌ Esperar que la app "en host mode" sea accesible desde localhost real del Mac
docker run -d --network host mi-servicio

# ✅ En macOS/Windows: bridge + publicación de puertos es la vía predecible
docker run -d -p 3000:3000 mi-servicio

7 · Ejercicio guiado

Objetivo: crear una red, conectar dos contenedores y demostrar la resolución DNS interna por nombre de servicio.

  1. Paso 1: crea la red ejercicio-net: 
    docker network create ejercicio-net
  2. Paso 2: lanza un contenedor db con sleep en esa red:

    docker run -d --name db --network ejercicio-net alpine sleep 3600
  3. Paso 3: desde otro contenedor de la misma red, resuelve el nombre db: 
    docker run --rm --network ejercicio-net alpine sh -c "getent hosts db"
# Salida esperada: la IP interna (172.1x.0.x) del contenedor db
  4. Paso 4 — verificación del aislamiento: lanza el mismo comando SIN --network (por defecto estará en bridge) y observa que no existe db: 
    docker run --rm alpine sh -c "getent hosts db"
# Salida esperada: nada (sacado de código 2) → el nombre solo existe dentro de ejercicio-net
  5. Paso 5: inspecciona qué contenedores forman parte de la red y sus IPs: 
    docker network inspect ejercicio-net
# en "Containers" aparecen db y los contenedores unidos con --rm (efímeros)
  6. Paso 6 — limpieza: elimínalo todo: 
    docker rm -f db
docker network rm ejercicio-net

8 · Reto

🎯 Puente entre dos redes

Crea dos redes (red-datos y red-web) y tres contenedores: db solo en red-datos, web solo en red-web, y api en ambas conectado con docker network connect. Demuestra en qué direcciones existe conectividad: ¿puede web ver a db? ¿Y api a los dos? ¿Por qué Docker permite que un solo contenedor participe en varias redes simultáneamente?

Pista: un contenedor tiene tantas interfaces como redes a las que se une (una IP por red). docker run --network red-datos --name api alpine sleep, después docker network connect red-web api. Comprueba la resolución con getent hosts desde cada contenedor contra los nombres de los otros. La respuesta a por qué es posible es la misma razón por la que tu portátil puede estar a la vez en el WiFi y en la VPN.

9 · Resumen

  • Cada contenedor tiene su namespace de red: localhost siempre es él mismo.
  • La red bridge por defecto conecta contenedores por IP pero sin DNS por nombre.
  • Las redes definidas por el usuario aportan DNS interno por nombre de contenedor y aislamiento por defecto.
  • --network host comparte la pila del host (sin -p), pero en macOS/Windows el "host" es una VM: prefiere bridge + -p.
  • --network none aísla por completo: ni siquiera hay interfaz de red.
  • La comunicación externa entra por puertos publicados; la interna viaja por la red privada, sin NAT intermedio.
ComandoQué hace
docker network create nombreCrea una red bridge con DNS interno para sus miembros
docker network lsLista las redes existentes (bridge, host, none y las del usuario)
docker network inspect nombreMuestra topología: contenedores, IPs y opciones de la red
docker run --network nombre …Une el contenedor a la red indicada en su arranque

docker network disconnect nombre contenedorQuita un contenedor de una red sin pararlo
docker network rm nombreElimina una red (debe estar sin contenedores unidos)

10 · Preguntas frecuentes

¿Por qué mi contenedor no ve internet si está en una red bridge?

Sí lo ve: el bridge hace NAT hacia el host y de ahí a internet. Lo que no existe por defecto es resolución DNS por nombre de contenedor (eso sí requiere red del usuario). Si un contenedor no sale, revisa detalles como el --dns de red, firewalls del host, o que esté unido a la red correcta con docker network inspect.

¿Qué IP debo usar para que mi host alcance un contenedor?

La IP interna del contenedor es privada y cambia: no la uses en configuraciones. Desde el host usa localhost:<puerto publicado>. Y si un contenedor quiere hablar con el host, en Linux usa la IP del bridge (172.17.0.1 típicamente) o la del host; en macOS/Windows usa el nombre especial host.docker.internal, que Docker inyecta en su DNS.

¿Puedo cambiar la red de un contenedor que ya está corriendo?

Sí, sin pararlo: docker network connect otra-red contenedor le añade una segunda interfaz (y una IP nueva). Para quitar la red original usa docker network disconnect red-original contenedor. El DNS interno se actualiza al instante y el proceso ni se entera; los sockets que ya estaban abiertos se mantienen.

¿Cuándo de verdad necesito --network host?

En Linux nativo: para servicios que deben anunciarse en la LAN como si fueran del host (mDNS, wg VPN, monitoreo), o para eliminar la sobrecarga de NAT en tráfico de muy baja latencia. En macOS/Windows el beneficio se pierde porque el contenedor igualmente vive dentro de una VM; allí usa bridge con -p y quedará claro y portable (lo verás al pasar a Kubernetes, donde el pod comparte red con sus sidecars por diseño).
