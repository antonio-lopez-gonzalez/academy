Volúmenes, bind mounts y tmpfs

Módulo 3 · Datos y redes Docker ⏱ 30 minutos

1 · Introducción

Hasta ahora has creado contenedores que corren procesos y sirven peticiones. Pero hay un problema que tarde o temprano te muerde: si un contenedor es destruido, su sistema de archivos desaparece con él. El famoso docker rm -f, un reinicio con --rm, o un simple docker compose down pueden borrar datos que jamás podrás recuperar.

Esta lección resuelve esa pregunta: ¿dónde guardo los datos si el contenedor es efímero? Verás las tres respuestas que ofrece Docker — volúmenes, bind mounts y tmpfs — cuándo usar cada una, por qué los volúmenes son la opción recomendada para datos de producción, y cómo se gestionan los permisos (uid/gid) al montar rutas del host.

¿Por qué existe esta lección? Porque sin persistencia, mongodb/postgres/redis dentro de un contenedor son inútiles: cada vez que escalees o redepliegues perderías todo. Y porque un error muy típico en Windows/WSL (montar /mnt/c) convierte un bind mount rápido en algo frustrantemente lento. Entender los tres mecanismos te ahorra horas de misterios.

2 · Teoría

Por qué los contenedores no guardan datos

Recuerda la anatomía de una imagen (Módulo 1): la imagen es una pila de capas de solo lectura. Cuando lanzas un contenedor, Docker añade encima una capa de escritura (writable layer) usando copy-on-write. Todo lo que escribe el proceso — archivos, logs, una base de datos — va a esa capa.

            CONTENEDOR (proceso aislado)
┌─────────────────────────────────────────┐
│  Capa de escritura (copy-on-write)      │ ← EFÍMERA: se borra con el contenedor
│                                         │   (docker rm, --rm, compose down…)
├─────────────────────────────────────────┤
│  Capa 3 de la imagen (solo lectura)     │ ┐
│  Capa 2 de la imagen (solo lectura)     │ ├─ INMUTABLES y compartidas
│  Capa 1 de la imagen (solo lectura)     │ ┘   entre todos los contenedores
└─────────────────────────────────────────┘

La capa de escritura vive dentro de la vida del contenedor. Al eliminarlo, Docker descarta también esa capa. Es exactamente como escribir con un rotulador borrable en una pizarra que se limpia al salir de clase. Por eso, si la aplicación genera datos que deben sobrevivir (registros de usuario, pedidos, archivos subidos), hay que sacarlos fuera del sistema de archivos del contenedor: a un volumen, a una ruta del host, o mantenerlos solo en memoria.

Los tres mecanismos de almacenamiento

Docker cuatros caminos para exponer datos a un contenedor. Tres son montajes (del inglés mounts): el contenedor ve un directorio como propio, pero el contenido vive en otro sitio.

MecanismoDónde vive el datoCiclo de vidaUso típico
Volumen (docker volume)Gestionado por Docker en su área privada (/var/lib/docker/volumes/…)Sobrevive a los contenedores; se borra solo con docker volume rmDatos de bases de datos, datos que deben persistir (recomendado)
Bind mountUna ruta cualquiera del host (tu disco: /home/tu/…, C:\… o /mnt/c/…)Sobrevive a Docker por completo (es tu archivo)Desarrollo: ver tu código sin reconstruir la imagen
tmpfsMemoria RAM del hostVive exactamente lo que el contenedorSecretos temporales o cachés que nunca se deben escribir a disco

Analogía: la capa de escritura es el cuaderno de apuntes que tiras al final del curso. Un volume es un armario de archivos que Docker guarda por ti en su trastero: siempre en el mismo sitio, fácil de mover entre contenedores. Un bind mount es prestar tu disco duro externo personal: tú decides exactamente qué carpeta comparte el contenedor, y el contenido existe aunque Docker no exista. El tmpfs es escribir en una pizarra: rapidísimo, pero al apagar las luces, se fue todo.

Volúmenes: los protagonistas

Un volumen es un directorio que Docker crea y gestiona fuera del ciclo de vida de cualquier contenedor. Sus ventajas frente al bind mount: no depende de la estructura de tu disco (Docker elige la ruta), se respalda/migra de forma trivial con docker volume, funciona igual en cualquier sistema y es la única opción recomendada por Docker para datos de producción. Los volúmenes pueden ser anónimos (Docker les asigna un nombre aleatorio) o con nombre — estos últimos son los que debes usar.

Se montan con el flag -v (forma corta) o --mount (forma larga, más explícita):

# Forma corta (-v):  nombre_del_volumen : ruta_dentro_del_contenedor
docker run -d --name web-datos -v mis-datos:/usr/share/nginx/html nginx

# Forma larga (--mount): igual pero con claves explícitas y en JSON
docker run -d --name web-datos --mount type=volume,source=mis-datos,target=/usr/share/nginx/html nginx

Bind mounts: tu disco, tus reglas

Un bind mount monta una ruta existente del host directamente en el contenedor. Es la herramienta estrella en desarrollo: editas el código en tu editor, y el contenedor ve el cambio al instante sin reconstruir la imagen.

# Linux / macOS: ruta absoluta primero, después la ruta en el contenedor
docker run -v /home/usuario/proyectos/harbortasks/api:/app -p 3000:3000 node:22

# Windows nativo (PowerShell): C:\ruta\a\api:/app  ← con la unidad C:
docker run -v C:\Users\tu\proyectos\api:/app -p 3000:3000 node:22

⚠️ En WSL2, tu proyecto debe vivir en el filesystem de Linux (~/…), nunca en /mnt/c. Montar /mnt/c/... como bind mount funciona técnicamente, pero cada acceso cruza la frontera 9P entre Windows y WSL: es un orden de magnitud más lento. Peor todavía: los permisos uid/gid se traducen mal, lo que rompe bases de datos que cambian propietarios de archivos. Repite conmigo: el proyecto vive en ~/.../harbortasks, y /mnt/c solo para copiar archivos puntuales.

tmpfs: datos en RAM

El tmpfs monta un directorio en la memoria RAM del host: lo más rápido posible y, por diseño, imposible de persistir. Es perfecto para cosas que no deben tocar el disco ni sobrevivir: ficheros de lock, tokens temporales o cachés intra-proceso.

# tmpfs en /tmp (solo existe mientras el contenedor viva)
docker run --rm --tmpfs /tmp:rw,size=64m alpine sh -c "echo hola > /tmp/x.txt && cat /tmp/x.txt"

Regla de oro: ¿Datos que deben sobrevivir? Volumen. ¿Código fuente en desarrollo? Bind mount (fuera de /mnt/c en WSL). ¿Cosas temporales sensibles? tmpfs. Y si no sabes cuál elegir, la respuesta por defecto es volumen con nombre.

Permisos: el problema del uid/gid

Dentro de un contenedor no hay cuentas de usuario de tu host: los procesos corren con un uid (usuario) y gid (grupo) numéricos. Cuando montas un bind mount, los archivos del host tienen los permisos de tu usuario real (uid 1000 típicamente), pero el proceso del contenedor puede correr como root (uid 0) o como otro uid. Si el proceso escribe y su uid no coincide, encontrarás Permission denied o archivos que no puedes tocar desde el host.

La imagen oficial de postgres, por ejemplo, corre como postgres (uid 999). Si montas un bind mount de tu ~/harbortasks/data, Postgres intentará escribir con uid 999 en una carpeta tuya. La solución limpia es preasignar el dueño: mkdir -p data && sudo chown -R 999:999 data. Con volúmenes, Docker asigna los permisos de la propia imagen automáticamente — otra razón más para preferirlos.

3 · Ejemplo mínimo

La forma más corta de ver un volumen en acción: crearlo, usarlo y comprobar que sobrevive a los contenedores.

# 1) Crear un volumen con nombre
docker volume create demo-datos

# 2) Verlo en la lista (status Driver=local, gestión por el motor Docker)
docker volume ls

# 3) Montarlo en un contenedor y escribir un archivo en él
docker run --rm -v demo-datos:/datos alpine sh -c "echo 'datos que sobreviven' > /datos/hola.txt && cat /datos/hola.txt"

# 4) Montarlo de nuevo en OTRO contenedor: el archivo sigue ahí
docker run --rm -v demo-datos:/datos alpine sh -c "cat /datos/hola.txt"

# 5) Inspeccionar el volumen: dónde guarda Docker los datos reales
docker volume inspect demo-datos

# 6) Al terminar, limpiar (borrar un volumen con contenedores lo impide: primero los contenedores)
docker volume rm demo-datos

Desglose: -v demo-datos:/datos significa "monta el volumen demo-datos en la ruta /datos del contenedor". Como el volumen no muere con el contenedor y ni siquiera depende de cuál contenedor lo usa, el paso 4 demuestra la persistencia real. El flag --rm borra el contenedor al salir… pero el volumen, y su contenido, permanecen hasta que hagas docker volume rm.

Nota: en el Resumen de la lección tienes la tabla con docker volume create / ls / inspect / rm y sus variantes. Los volúmenes anónimos (-v /ruta sin nombre) existen, pero tienes que rastrearlos con docker volume ls -f dangling=true; dales siempre nombre.

4 · Ejemplo real

En HarborTasks hay tres piezas, y cada una usa el mecanismo apropiado. La base de datos (postgres) necesita un volumen con nombre en su ruta de datos; la API en desarrollo se lanza con un bind mount de tu carpeta del código para no reconstruir la imagen en cada cambio.

# --- PostgreSQL: volumen con nombre para los datos ---
# /var/lib/postgresql/data es donde la imagen oficial escribe el cluster
docker run -d --name harborpostgres \
  -e POSTGRES_PASSWORD=secretito \
  -v pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16-alpine

# --- API (Node) en desarrollo: bind mount del código en el host ---
# editas api/server.js en tu editor y el contenedor ya ve el cambio
docker run -d --name harborapi \
  -v "$(pwd)/api":/app \
  -w /app \
  -e PG_HOST=host.docker.internal \
  -p 3000:3000 \
  node:22-alpine node server.js

# Comprobar que el volumen existe y dónde vive físicamente
docker volume ls | grep pgdata      # filtra el volumen de harborpostgres
docker volume inspect harborpostgres

Decisiones tomadas: los datos de Postgres van a volumen porque deben sobrevivir a cualquier ciclo de vida del contenedor (reinicios, rm, cambios de imagen). El código de la API va a bind mount porque es exactamente lo contrario: queremos ver cambios instantáneos mientras desarrollamos. Y fíjate: nunca montas el código de producción como bind mount, ni los datos de una DB como bind mount de una carpeta cualquiera sin controlar el uid (recuerda el uid 999 de postgres).

⚠️ En Windows nativo (PowerShell), $(pwd) no existe en bash; usa "${PWD}/api" o escribe la ruta completa con la unidad: -v "C:\Users\tu\proyectos\harbortasks\api:/app". Pero recuerda la regla del curso: desarrolla dentro de WSL2, donde $(pwd) y los permisos Linux funcionan de forma nativa.

6 · Errores habituales

Creer que el contenedor "guarda" sus datos

# ❌ Escribir en la capa de escritura y esperar que persista
docker run --rm alpine sh -c "echo 'tarea' > /tareas.txt"
# ... el contenedor se borra con --rm y /tareas.txt desaparece para siempre

# ✅ Escribir en un volumen montado: el dato sobrevive al contenedor
docker volume create tareas-datos
docker run --rm -v tareas-datos:/data alpine sh -c "echo 'tarea' > /data/tareas.txt"
docker run --rm -v tareas-datos:/data alpine cat /data/tareas.txt   # → tarea

Confundir sintaxis de bind mount en Windows

# ❌ En PowerShell no puedes usar $(pwd) de bash
docker run -v $(pwd):/app node:22-alpine

# ✅ PowerShell: ${PWD} o la ruta completa con la unidad
docker run -v "${PWD}:/app" node:22-alpine
docker run -v "C:\Users\tu\proyectos\api:/app" node:22-alpine

Montar el código en WSL desde /mnt/c (lento y con permisos rotos)

# ❌ Trabajar sobre /mnt/c: cada lectura cruza la frontera Windows↔WSL
cd /mnt/c/Users/tu/proyectos/harbortasks
docker run -v "$(pwd):/app" node:22-alpine ...

# ✅ Trabajar dentro del filesystem ext4 de WSL (~), con permisos Linux sanos
cd ~/proyectos/harbortasks
docker run -v "$(pwd):/app" node:22-alpine ...

Peor aún: mezclar ambos flag sin saber qué hacen

# ❌ Un nombre sin barra busca "volumen", una ruta con barra hace "bind mount"
docker run -v pgdata:/var/lib/postgresql/data ...   # volumen llamado pgdata ✅

# ❌ La misma intención mal escrita: ruta absoluta del host que no existe
docker run -v /pgdata:/var/lib/postgresql/data ...  # bind mount del host /pgdata ❌

# ✅ --mount no deja lugar a dudas
docker run --mount type=volume,source=pgdata,target=/var/lib/postgresql/data ...

7 · Ejercicio guiado

Objetivo: demostrar con tus propias manos que un volumen sobrevive a la destrucción del contenedor, y que un bind mount refleja cambios del host.

  1. Paso 1: Crea el volumen para las tareas: 
    docker volume create ejercicio-tareas
  2. Paso 2: Lanza un contenedor con --rm que escriba una tarea en el volumen (el --rm garantiza que el contenedor se autodestruirá): 
    docker run --rm -v ejercicio-tareas:/data alpine sh -c "echo 'comprar leche' > /data/tareas.txt"
  3. Paso 3: Verifica con docker volume ls que el volumen sigue listado aunque el contenedor ya no exista.
  4. Paso 4: Vuelve a leer el archivo desde un contenedor nuevo y comprueba que la tarea sigue ahí: 
    docker run --rm -v ejercicio-tareas:/data alpine cat /data/tareas.txt
# Salida esperada: comprar leche
  5. Paso 5 (bind mount): crea una carpeta temporal en el host y monta un archivo que crees desde el host, dentro del contenedor: 
    mkdir -p /tmp/ejercicio
echo "desde el host" > /tmp/ejercicio/nota.txt
docker run --rm -v /tmp/ejercicio:/mnt alpine cat /mnt/nota.txt
# Salida esperada: desde el host
  6. Paso 6 — verificación final: cambia el contenido desde el host y compruébalo dentro del contenedor SIN reconstruir nada: 
    echo "modificado" > /tmp/ejercicio/nota.txt
docker run --rm -v /tmp/ejercicio:/mnt alpine cat /mnt/nota.txt
# Salida esperada: modificado  → prueba de que el bind mount es en vivo

8 · Reto

🎯 Permisos de bind mount con Postgres

Monta un bind mount de una carpeta nueva ~/harbortasks/pg-bind en /var/lib/postgresql/data de una imagen postgres:16-alpine. Verás que Postgres no arranca o falla al escribir: descubre por qué (¿qué uid usa el proceso postgres en la imagen?) y arregla los permisos de la carpeta para que el contenedor funcione. Luego comprueba que puedes leer/borrar los archivos desde tu usuario del host.

Pista: docker run --rm -v ~/harbortasks/pg-bind:/var/lib/postgresql/data ... fallará por dueño. Investiga cómo consultar el uid del usuario dentro de la imagen (docker run --rm postgres:16-alpine id postgres) y ajusta con chown. En WSL2 no olvides el aviso de la teoría: nada de /mnt/c.

9 · Resumen

  • La capa de escritura del contenedor es efímera: docker rm la borra con todo su contenido.
  • Un volumen con nombre es el lugar recomendado para datos que deben persistir (sobre todo bases de datos).
  • Un bind mount monta una ruta de tu host: ideal para desarrollo en vivo, no para datos con permisos complejos.
  • El tmpfs vive en RAM: datos temporales que no deben llegar jamás al disco.
  • Los permisos uid/gid explican la mayoría de Permission denied: el proceso del contenedor corre con un uid distinto al tuyo.
  • En WSL2, los bind mounts a /mnt/c son lentos y rompen permisos: desarrolla en ~.

10 · Preguntas frecuentes

¿Cuándo uso -v y cuándo --mount?

-v es la forma corta y cómoda; --mount es la forma explícita: hay que declarar el tipo (type=volume|bind|tmpfs), el origen y el destino. Son equivalentes en la mayoría de casos. Usa --mount cuando la claridad importe (scripts compartidos, documentación), y -v para comandos rápidos en la terminal.

¿Dónde guarda Docker los volúmenes físicamente?

En el área del daemon, normalmente /var/lib/docker/volumes/<nombre>/_data en Linux, y dentro de la VM de Docker Desktop en macOS/Windows (no accesible directamente a tu filesystem). Por eso no debes tocar esa ruta a mano: gestiona volúmenes con los comandos docker volume. docker volume inspect te dice el Mountpoint.

¿Puedo copiar un archivo del host a un volumen sin entrar al contenedor?

Sí, de dos maneras: con docker cp archivo contenedor:/ruta (copia al contenedor, que está montando el volumen) o montando el volumen en un contenedor de utilidades: docker run --rm -v mivol:/dest busybox cp /origen /dest/. La segunda forma funciona incluso con el contenedor original parado, porque el volumen es independiente.

¿Un volumen consume espacio aunque no lo use ningún contenedor?

Sí: el volumen existe y ocupa disco hasta que lo docker volume rm. Por eso los volúmenes anónimos huérfanos (de docker compose o de contenedores borrados sin -v) se acumulan. Límpialos con docker volume prune cuando estés seguro de que sus datos no importan. Revisa antes con docker volume ls -f dangling=true.
