Ingress y entrada al clúster

Módulo 7 · Configuración y almacenamiento ⏱ 30 minutos

1 · Introducción

Hasta ahora tus Pods solo eran visibles dentro del clúster: los Services con ClusterIP no son accesibles desde tu navegador. Para que un usuario de HarborTasks llegue a la web y a la API necesitamos exponerlos hacia fuera.

En esta lección verás las tres formas de abrir el clúster (NodePort, LoadBalancer e Ingress), qué es un IngressController (ingress-nginx) y por qué Kubernetes no viene con uno integrado, cómo se define el objeto Ingress (rules de host/path), cómo instalarlo en kind, y los primeros pasos de TLS (cert-manager mencionado). Al final, HarborTasks se servirá por harbortasks.test con rutas / (web) y /api/ (API).

¿Por qué existe esta lección? Porque instalar y configurar el routing L7 del clúster es el momento en que «todo se conecta» y también, estadísticamente, donde más gente se atasca: el controlador no viene instalado por defecto, los paths «comen» prefijos y el puerto nunca coincide. Entender la arquitectura evita debugging a ciegas.

2 · Teoría

NodePort → LoadBalancer → Ingress

En el módulo 6 viste los tipos de Service. Recapitulemos qué ofrecen hacia fuera:

MecanismoCómo exponeLimitación importante
NodePortAbre un puerto alto (30000–32767) en todos los nodos; el tráfico llega a IP:puerto Un servicio = un puerto; puertos feos; sin routing por host/path; nada de TLS
LoadBalancerCrea un balanceador en la nube (ELB/GLB) que reparte puerto 80/443 Cada servicio con su LoadBalancer = caro; sin routing por host/path (aún)
IngressUn punto de entrada (80/443) que enruta por host y path a varios Services Requiere un controlador instalado y configurado (no viene con el clúster)

Analogía: NodePort es como darle a cada empresa una puerta de entrada numerada (puerta 7, puerta 11…). LoadBalancer es comprar un edificio con una sola puerta por empresa en la calle principal. Ingress es el conserje del edificio: una única puerta con dirección, y dentro, el portero decide «los del piso 2 van a la derecha, los del piso 3 a la izquierda», según el letrero (host) y el pasillo (path).

Dos piezas: el objeto Ingress y el IngressController

Aquí está la confusión clásica. Kubernetes define el objeto Ingress (networking.k8s.io/v1): un manifiesto declarativo que dice «el host X con el path Y va al Service Z». Pero un manifiesto YAML no enruta ni un byte: necesita un controlador que lo ejecute.

El IngressController (típicamente ingress-nginx) es un Deployment + Service que corre dentro del clúster, se registra en IngressClass, escucha la API de Kubernetes, lee tus objetos Ingress y reconfigura un nginx real (descarga el nginx.conf) para servir el routing. Sin controlador, kubectl apply -f ingress.yaml no da error: simplemente no hace nada visible.

Usuario Clúster Kubernetes (kind) ─────── ────────────────────────── navegador │ GET http://harbortasks.test/api/tasks │ ▼ ┌──────────────────────────────────────────────────────────────┐ │ NODO: puerto host 80 → ingress-nginx (Service NodePort/LB) │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ ingress-nginx controller (Deployment, en namespace │ │ │ │ ingress-nginx) │ │ │ │ lee el objeto Ingress → nginx.conf real │ │ │ └──────────────────────┬────────────────────────────────┘ │ └─────────────────────────┼────────────────────────────────────┘ │ enruta según host + path ┌─────────────┴──────────────┐ ▼ ▼ Service api-harbortasks Service web-harbortasks (ClusterIP :3000) (ClusterIP :80) │ │ ▼ ▼ Pods del API Pods de la web (nginx) → postgres → BBDD → /usr/share/nginx/html

Instalación del controlador y por qué kind necesita un cluster-config

El controlador necesita que el tráfico del host llegue a sus Pods. En kind (los nodos SON contenedores Docker), debes crear el clúster mapeando los puertos 80/443 del host a los puertos 80/443 del nodo con extraPortMappings, y marcar uno de los nodos con la etiqueta ingress-ready=true que el controlador usa para fijar dónde instalarse.

Mac / Windows: en Docker Desktop (Mac/Windows) el mapeo hostPort: 80 publica directamente localhost:80. A veces el puerto 80 está ocupado (Skype, IIS, XAMPP): si falla kubectl apply del controlador o el curl no responde, cambia el hostPort a 8080 y entra por http://localhost:8080. La versión del manifiesto de kind es la misma; solo cambia el puerto de acceso y el Host header lo sigues enviando igual.

HTTP y TLS

El Ingress, por defecto, sirve HTTP en claro. Para HTTPS se monta: un Secret de tipo TLS (visto en la lección 02) con el certificado, la sección tls: del Ingress, y el controller termina el TLS y deriva HTTP a los Pods. En producción es habitual que cert-manager cree y renueve automáticamente esos certificados (Let's Encrypt), que es un operador que observa tus Ingress y genera el Secret TLS. En kind puedes emitir certificados autofirmados; lo veremos en el reto.

3 · Ejemplo mínimo

Instalar ingress-nginx en kind y enrutar un servicio de prueba. Primero, el clúster con los puertos abiertos:

kind-config.yaml
# kind despliega el clúster con un nodo control-plane.
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"   # etiqueta que busca ingress-nginx
    extraPortMappings:                          # expone 80/443 del host→nodo
      - containerPort: 80
        hostPort: 80
        protocol: TCP
      - containerPort: 443
        hostPort: 443
        protocol: TCP

# Borra el clúster anterior si existe y crea uno nuevo con la config
kind delete cluster
kind create cluster --config kind-config.yaml

# Instala el controlador residente de kind (proyecto ingress-nginx)
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.12.0/deploy/static/provider/kind/deploy.yaml

# Espera a que el Deployment esté listo (2 réplicas)
kubectl wait --namespace=ingress-nginx \
  --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=180s

Versiones: la URL raw incluye una versión (controller-v1.12.0). Comprueba en github.com/kubernetes/ingress-nginx/releases la release estable más reciente y ajusta el número. Alternativa con Helm (módulo 8): helm install ingress-nginx ingress-nginx/ingress-nginx --namespace ingress-nginx --create-namespace.

Ahora el Ingress mínimo (asumimos un Service mi-servicio en el namespace default):

ingress-minimo.yaml
apiVersion: networking.k8s.io/v1   # API actual y estable desde K8s 1.19
kind: Ingress
metadata:
  name: ingress-minimo
spec:
  ingressClassName: nginx           # usa la clase del controlador ingress-nginx
  rules:
    - host: ejemplo.test            # el Host header que debe coincidir
      http:
        paths:
          - path: /                 # todas las rutas
            pathType: Prefix
            backend:
              service:
                name: mi-servicio   # los Pods de este Service
                port:
                  number: 80        # puerto del Service (no del Pod)

Y a probar: curl -H "Host: ejemplo.test" http://localhost/ (o http://localhost:8080/ si cambiaste el hostPort). Devuelve lo que sirve mi-servicio. Sin Host header, el controller responde 404 con su página por defecto.

4 · Ejemplo real

El Ingress de HarborTasks: un host, dos paths. / servirá la web; /api/ se reenvía a la API (cuidado: resolveremos el prefijo), y nacen los requisitos previos.

ingress-harbortasks.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: harbor-ingress
  namespace: harbortasks
  annotations:
    # Sin esta anotación, /api/proxy llega al backend como /api/proxy.
    # nginx precisa regex para reescribir: quita el prefijo '/api'.
    ingress.nginx.rewrite-target: /$2
spec:
  ingressClassName: nginx             # el controlador que lo atiende
  rules:
    - host: harbortasks.test
      http:
        paths:
          # --- API: todo lo que empiece por /api/ … -----------------
          - path: /api(/|$)(.*)        # regex: captura lo que va tras /api
            pathType: ImplementationSpecific   # necesaria para regex
            backend:
              service:
                name: api-harbortasks  # Service de la API (visto en módulo 6)
                port:
                  number: 3000
          # --- Web: el resto va a nginx (estáticos) -----------------
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-harbortasks
                port:
                  number: 80

Requisitos previos para que funcione:

  1. Los Services api-harbortasks y web-harbortasks en el namespace harbortasks (repasa el módulo 6 si falta alguno).
  2. El controlador ingress-nginx instalado (ejemplo mínimo) y el clúster creado con los extraPortMappings (si creaste el clúster antes sin ellos, kind delete cluster + recrea).
  3. El nombre harbortasks.test debe resolver a 127.0.0.1 en tu máquina.

Maqueta el DNS local (esencial en Mac y Windows) — prueba con curl primero, y solo si funciona añádelo al archivo hosts:

# ---- Linux / macOS: /etc/hosts ------------------------------------
echo "127.0.0.1 harbortasks.test" | sudo tee -a /etc/hosts

# ---- Windows (PowerShell como administrador) -----------------------
# Add-Content -Path C:\Windows\System32\drivers\etc\hosts -Value "127.0.0.1 harbortasks.test"
# En WSL2 la IP de localhost difiere: si no resuelve, usa la IP del nodo:
# kubectl get nodes -o wide   → usa la IP INTERNAL-IP

# Verificación completa del flujo
curl -i http://harbortasks.test/            # → 200, HTML estático de la web
curl -i http://harbortasks.test/api/tasks   # → 200, JSON del API
curl -i http://localhost/                   # → 404 del controller (sin Host correcto)
kubectl get ingress -n harbortasks          # estado y ADDRESS del Ingress

WSL2 y hostPort: si curl http://harbortasks.test/ falla desde dentro de WSL pero http://localhost/api/tasks funciona desde PowerShell del host de Windows, Docker Desktop publica el puerto en la IP del host y no en la de WSL. En ese caso usa la IP interna del nodo (kubectl get nodes -o wide) en WSL, o accede desde la sesión de Windows del host. El 404 sin el Host correcto es el comportamiento esperado del controller: exige harbortasks.test para enrutar.

5 · Buenas prácticas

HazEvitaPor qué
Un solo Ingress por aplicación, con paths claros (/, /api/, /web/) Un Ingress por microservicio o paths anidados al azar El routing L7 se queda en un único manifiesto; es la «config del conserje»
Define ingressClassName explícito Esparcir Ingress dependiendo de la «clase por defecto» Si mañana hay 2 controladores, la anotación explícita evita ambigüedad
Usa regex + rewrite-target solo cuando el backend espera el path limpio Reescribir paths sin tester (curl contra cada backend) La reescritura mal hecha rompe la API (404 en /api/tasks)
Monta TLS con Secret kubernetes.io/tls y cert-manager en producción Dejar el 80 abierto «por si acaso» sin redirigir HTTPS es hoy el estándar; cert-manager lo automatiza (Let's Encrypt)
Verifica con curl el Host correcto antes de tocar /etc/hosts Añadir a hosts hoy un dominio que aún no enruta El 404 del controller es la pista de debugging principal; el de tu DNS, no

Tráfico al API con CORS: la web de HarborTasks y la API comparten host (harbortasks.test), así que no hay CORS cruzado. En la versión Compose sí lo había; con Ingress lo resuelves de gratis. Si algún día separas hosts (api.example.com), recuerda que CORS vuelve a ser problema.

6 · Errores habituales

❌ «Apliqué el Ingress y no pasa nada» — olvidé el controlador

# ❌ Un cluster kind recién creado NO trae ingress-nginx.
kubectl apply -f ingress-harbortasks.yaml   # "created" pero nada responde

# ✅ Verifica el controlador:
kubectl get ingresses -A                    # lista los Ingress atendidos
kubectl get pods -n ingress-nginx           # los Pods del controller deben estar Running
kubectl get ingressclass                   # debe existir una clase 'nginx'
# Si no existe 'nginx', instala el controlador (paso del ejemplo mínimo).

❌ El path no se reescribe: 404 en /api/tasks

# ❌ sin rewrite-target, el backend ve '/api/tasks' y Express no tiene esa ruta
#    → la API responde 404 (o 404 del controller)

# ✅ añade la anotación y path regex (vista en el ejemplo real)
#    ingress.nginx.rewrite-target: /$2    que traduce /api/tasks → /tasks

❌ Host header ausente o distinto

# ❌ acceso con localhost sin Host → 404 genérico del controller
curl http://localhost/

# ✅ enruta con el dominio declarado en rules.host
curl -H "Host: harbortasks.test" http://localhost/
curl http://harbortasks.test/

❌ Puerto del Service frente al puerto del Pod

# ❌ aquí va el puerto que el Service expone, no el containerPort del Pod
backend:
  service:
    name: api-harbortasks
    port:
      number: 3000             # ✅ puerto publicado por el Service (ClusterIP)
                               #   si el Service hace 80→3000, aquí escribirías 80.

Mac/Windows: el puerto 80 del host puede estar ocupado (Skype, IIS, XAMPP, AirPlay). Antes de asumir «el Ingress no funciona», prueba: netstat -ano | findstr :80 en PowerShell, o libera el puerto. Si no puedes usar 80, cambia hostPort: 80 a hostPort: 8080 en el kind-config.yaml y accede por http://harbortasks.test:8080/ (ajustando /etc/hosts igual).

7 · Ejercicio guiado

Objetivo: enrutar una aplicación de prueba con el controlador ya instalado, por host y por path, y verificar el flujo completo.

  1. Crea un Deployment + Service de prueba (usa la imagen nginx): 
    kubectl create deployment demo-web --image=nginx:1.27-alpine
kubectl expose deployment demo-web --port=80 --target-port=80
kubectl get svc demo-web       # debe tener ClusterIP 10.96.0.x:80
  2. Crea el Ingress para demo.test (aplica el ingress-minimo.yaml del ejemplo mínimo, pero con name: demo-web y host: demo.test): 
    kubectl apply -f ingress-minimo.yaml   # o el tuyo con demo.test
sleep 5    # da tiempo al controller a reconfigurar nginx
  3. Verifica el estado del Ingress: 
    kubectl get ingress
# NAME     CLASS   HOSTS       ADDRESS        PORTS
# ingres…  nginx   demo.test       80

    Si CLASS está vacío (no nginx) o ADDRESS vacío, revisa el paso del controlador.

  4. Prueba el flujo real (sin tocar /etc/hosts todavía): 
    # Con Host header correcto → respuesta del nginx (200, HTML "Welcome to nginx")
curl -i -H "Host: demo.test" http://localhost/

# Sin Host → 404 del controller (no llega a tu app)
curl -i http://localhost/

    Resultado esperado: con Host: demo.test recibes el HTML de nginx; sin él, el 404 del ingress-nginx.

  5. Ponlo en /etc/hosts y comprueba con el nombre directo: 
    echo "127.0.0.1 demo.test" | sudo tee -a /etc/hosts   # Linux/macOS
curl http://demo.test/                                 # → 200, "Welcome to nginx" ✔
  6. Limpia: kubectl delete ingress ingress-minimo, kubectl delete svc demo-web, kubectl delete deployment demo-web, y quita la línea de /etc/hosts.

8 · Reto

🎯 HTTPS con un certificado autofirmado

Eleva el Ingress de HarborTasks a HTTPS. Crea un Secret de tipo kubernetes.io/tls con un certificado autofirmado para harbortasks.test (para generarlo en Linux puedes usar el binario openssl), añade la sección spec.tls: al Ingress y verifica que curl -k https://harbortasks.test/ devuelve la web. Además, haz que el HTTP redirija al HTTPS: pista, en ingress-nginx se logra con la anotación nginx.ingress.kubernetes.io/ssl-redirect: "true", aunque el tráfico no esté cifrado con un CA público (con cert-manager + Let's Encrypt la redirección es total).

Pista: kubernetes.io/tls exige las claves tls.crt y tls.key; crea el Secret con kubectl create secret tls harbor-tls --cert=cert.pem --key=key.pem. El navegador marcará el certificado como no confiable (autofirmado): esa advertencia es esperada, la comprobación con curl -k debe devolver el HTML igualmente.

9 · Resumen

  • Tres formas de exponer: NodePort (puerto alto en nodos), LoadBalancer (un LB por servicio en la nube), Ingress (un punto de entrada con routing L7 por host/path).
  • El objeto Ingress (networking.k8s.io/v1) es declaración; el IngressController (ingress-nginx) es quien ejecuta el routing y NO viene instalado por defecto.
  • kind requiere clúster con extraPortMappings (80/443) y la etiqueta ingress-ready=true.
  • Rules de host + path: el path con regex y rewrite-target para tareas de prefijo como /api/.
  • HTTPS: Secret kubernetes.io/tls + sección spec.tls; en producción cert-manager automatiza Let's Encrypt.

10 · Preguntas frecuentes

¿Por qué Kubernetes no incluye un controlador Ingress por defecto?

Por diseño: el «reverse proxy» puede ser nginx, HAProxy, Traefik, Istio… y cada uno tiene reglas, anotaciones y operadores propios. Kubernetes define solo la API (el objetos de routing) y deja el cómo a cada implementación. Por eso «instalar el controlador» es un paso explícito que tú decides, no un componente oculto del control plane.

¿NodePort sigue sirviendo para algo si tengo Ingress?

Sí: dentro de un clúster en la nube el controlador ingress-nginx se publica habitualmente como Service LoadBalancer (o bien NodePort en kind). Y NodePort sigue siendo útil para exponer servicios no HTTP (gRPC, TCP, bases de datos) o en clústeres sin Ingress. Para tráfico HTTP/HTTPS público, Ingress es la norma.

Mi Ingress responde 404 default backend. ¿Qué significa?

Que el controlador recibió la petición pero no encontró ninguna regla que encajara: o el Host no coincide con rules.host, o el path/backend están mal, o la combinación host+path no está aplicada. Revisa kubectl get ingress -n harbortasks -o yaml y el curl -H "Host: …" adecuado.

¿Y el TLS cómo queda con host local?

En local puedes emitir un certificado autofirmado para harbortasks.test junto con un CA propio o usar mkcert (instala la CA en tu sistema y los certificados dejan de marcar error). En producción, cert-manager + cluster issuer de Let's Encrypt hace la renovación automática y el Ingress solo declara tls:.

¿Puedo tener dos hosts sobre el mismo Ingress?

Sí, añade más objetos en rules (por ejemplo api.harbortasks.test que aterrice en /api/* y web.harbortasks.test en /), o usa host con wildcard. En HarborTasks preferimos un host y routing por path (más simple, mejor DNS local).
