ConfigMaps

Módulo 7 · Configuración y almacenamiento ⏱ 30 minutos

1 · Introducción

En el modelo declarativo de Kubernetes una imagen Docker es una única entidad que debería servir igual en desarrollo, staging y producción. Si metes dentro de la imagen la URL de la base de datos o el límite de tareas, estás creando una imagen distinta por entorno: un desastre operativo. Por eso existe el ConfigMap: un objeto de Kubernetes que guarda configuración fuera de la imagen y la inyecta en los Pods.

En esta lección verás qué problema exacto resuelve (la regla de 12-factor «config in environment»), cómo se define, sus dos campos (data y binaryData), las tres formas de consumirla (variables de entorno, envFrom y volúmenes), y la inmutabilidad. Lo aplicaremos a HarborTasks: la web (nginx) y la API leerán su configuración desde un ConfigMap.

¿Por qué existe esta lección? Porque casi todos los fallos en producción con Kubernetes no son de código, sino de configuración: una URL mal apuntada, un límite distinto, un flag desactivado. Separar la config del binario es lo que permite promocionar la misma imagen por entornos y revertir cambios sin reconstruir nada.

2 · Teoría

La regla III de 12-factor: «config in environment»

Las aplicaciones de 12-factor establecen que toda configuración que cambia entre despliegues (URLs, credenciales, flags, límites) debe vivir en el entorno, no en el código ni en los archivos de la imagen. La URL de la API en tu máquina no es la misma que en producción; si esa URL está escrita dentro de la imagen, la imagen deja de ser reproducible.

Analogía: una imagen es como una pizza congelada: la receta y los ingredientes son siempre iguales. El ConfigMap son las instrucciones de horneado que escribes en el envoltorio: temperatura y minutos. Puedes cambiar las instrucciones sin volver a fabricar la pizza.

En Docker Compose ya usabas environment: para esto (módulo 4). Kubernetes da un paso más: en vez de variables sueltas en el manifiesto, crea un objeto declarativo llamado ConfigMap (apiVersion: v1, kind: ConfigMap). Es config versionada en Git, auditada por el API server y compartida por muchos Pods.

Qué contiene un ConfigMap

Es un mapa simple clave → valor, parecido a un diccionario o a un archivo .env. Tiene dos secciones:

  • data — valores de texto plano UTF-8 (cadenas, YAML, una URL, un bloque de nginx…). Los valores pueden ser multilínea usando bloque | de YAML.
  • binaryData — valores binarios codificados en Base64 (un certificado, un par de claves, un config de formato binario). Rara vez la necesitarás; es mejor montar estos ficheros como Secret o como imagen separada.

El tamaño máximo de un ConfigMap es 1 MiB (por defecto). Si necesitas más, ese dato no debería ir en un ConfigMap (piensa en un objeto propio, en un volumen o en un Secret con cifrado). Los ConfigMap son namespace-scoped: solo existen dentro de su namespace.

Cómo se consume: tres vías, tres consecuencias

kubectl apply -f configmap.yaml │ v ┌───────────────────────┐ │ ConfigMap api-config │ │ DATABASE_URL=… │ │ TASKS_LIMIT=10 │ │ LOG_LEVEL=info │ └───────────┬───────────┘ │ el kubelet las inyecta según cómo las pidas ┌───────────────┼────────────────┐ │ │ │ envFrom (todas) configMapKeyRef volume mount │ (una a una) (como archivos) │ │ │ ┌─────┴────┐ ┌──────┴─────┐ ┌─────┴─────┐ │ api Pod │ │ api Pod │ │ web Pod │ │ variables│ │ variables │ │ /etc/nginx│ │ (set de │ │ específicas│ │ /conf.d │ │ claves) │ │ │ │ default.conf └──────────┘ └────────────┘ └───────────┘
  1. env + valueFrom.configMapKeyRef: pides una clave concreta y la conviertes en una variable de entorno con el nombre que tú quieras. Útil cuando el nombre de la clave no es un nombre de variable válido (p. ej. config.url) o cuando solo quieres 2 de las 10 claves.
  2. envFrom: vuelca todas las claves del ConfigMap como variables. Cómodo, pero si una clave choca con una variable ya definida el comportamiento es sutil (más abajo en errores).
  3. Volumen montado: cada clave se convierte en un archivo cuyo nombre es la clave, contenido en un directorio que montas dentro del Pod. Perfecto para config en forma de fichero (un nginx.conf, un .env, un settings.json).

Inmutabilidad (Kubernetes 1.21+)

Si marcas immutable: true, el ConfigMap no se puede modificar ni borrar hasta que lo borres explícitamente. ¿Por qué existe? Por un problema real: cambiar la config de un sistema en marcha puede ser catastrófico (y los secretos heredados provocan «supply chain»). Hacerla inmutable garantiza que ninguna cuenta o pipeline pueda alterarla por accidente. Ganas rendimiento además: el kubelet deja de escuchar cambios en ese objeto.

Cambiar un ConfigMap no reinicia los Pods. Las variables de entorno se leen una vez al crear el contenedor. Si editas un ConfigMap de tipo env, necesitas kubectl rollout restart deployment <nombre> para aplicar los cambios. Con volúmenes, el kubelet sincroniza el archivo sin reiniciar (pero tu aplicación debe recargarlo).

3 · Ejemplo mínimo

La forma más rápida de crear un ConfigMap es con kubectl create desde la línea de comandos:

# --from-literal inyecta una clave=valor directa en el objeto
kubectl create configmap demo-cm \
  --from-literal=saludo=hola-mundo \
  --from-literal=nivel=debug

# Ver el objeto en YAML (la única fuente de verdad del clúster)
kubectl get configmap demo-cm -o yaml

# Ver un resumen legible: cuántas claves y su tamaño
kubectl describe configmap demo-cm

Salida del -o yaml (comentada):

apiVersion: v1            # API de objetos básicos (configmaps viven aquí)
kind: ConfigMap           # el tipo de objeto
metadata:
  name: demo-cm           # nombre del objeto (único en el namespace)
  namespace: default      # scope: este ConfigMap solo existe en 'default'
data:
  nivel: debug            # data = texto plano UTF-8
  saludo: hola-mundo

Puntos clave: data guarda texto, el nombre vive en metadata, y el namespace delimita dónde es visible. No hay «instalación» ni imágenes: es solo un objeto en etcd del clúster, listo para que los Pods lo consuman.

4 · Ejemplo real

Apliquémoslo a HarborTasks. Dos piezas, dos configuras:

  • API (Node/Express): necesita la URL de la base de datos, el límite de tareas por página y el nivel de log. Lo inyectamos como variables de entorno con envFrom + un par de configMapKeyRef.
  • Web (nginx): necesita saber a qué servicio enviar el tráfico /api/*. En Kubernetes nginx no expande variables de entorno por sí solo, así que la solución idiomática es montar su configuración (un fichero) como volumen.
configmaps.yaml
# --- ConfigMap de la API: variables de entorno en texto plano ---
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config                  # lo consumirán los Pods con label app=api
  namespace: harbortasks
data:
  # URL interna del servicio de postgres (DNS del clúster).
  # El puerto 5432 es el estándar de PostgreSQL.
  DATABASE_URL: postgres://harbor:harborpass@postgres:5432/harbortasks
  TASKS_LIMIT: "10"                # YAML lo interpretaría como número; lo forzamos a texto
  LOG_LEVEL: info                  # nivel de log para desarrollo local
  # NOTA: la contraseña 'harborpass' está aquí SOLO para aprender.
  # En producción va en un Secret (próxima lección), no en un ConfigMap.

---
# --- ConfigMap de la web: un fichero de configuración de nginx ---
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
  namespace: harbortasks
data:
  # El nombre de la clave (default.conf) será EL NOMBRE DEL ARCHIVO montado.
  default.conf: |
    server {
      listen 80;
      server_name _;                       # cualquier host → esta web

      # Cualquier petición /api/* se reenvía al servicio api
      location /api/ {
        proxy_pass http://api.harbortasks.svc:3000;
        proxy_set_header Host $host;
      }

      # El resto (estáticos HTML/CSS/JS) se sirve desde /usr/share/nginx/html
      location / {
        root /usr/share/nginx/html;
      }
    }
deployment-api.yaml (fragmento)
spec:
  template:
    spec:
      containers:
        - name: api
          image: harbortasks-api:1.0.0
          # 1) envFrom: vierte TODAS las claves de api-config como variables.
          envFrom:
            - configMapRef:
                name: api-config
          # 2) configMapKeyRef: pide una clave concreta y la expone con el
          #    nombre de variable que tú elijas (clave 'TASKS_LIMIT' de api-config).
          env:
            - name: MAX_TASKS_PER_PAGE       # la app espera este nombre
              valueFrom:
                configMapKeyRef:
                  name: api-config           # del ConfigMap api-config
                  key: TASKS_LIMIT           # toma la clave TASKS_LIMIT
                  optional: false            # si falta la clave, falla el arranque
deployment-web.yaml (fragmento)
spec:
  template:
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
          volumeMounts:
            - name: nginx-conf              # mismo nombre que el volumen de abajo
              mountPath: /etc/nginx/conf.d  # reemplaza el contenido de este dir
              readOnly: true                # nginx solo lee su config
      volumes:
        - name: nginx-conf
          configMap:
            name: web-config                # clave default.conf → archivo default.conf

Ojo con el mountPath: al montar un volumen en /etc/nginx/conf.d estás reemplazando la carpeta completa de la imagen (se oculta su contenido previo). Por eso el fichero se llama default.conf: sustituye al default.conf de la imagen sin dejar versiones huérfanas. Es el patrón estándar con nginx en Kubernetes.

6 · Errores habituales

❌ Claves con puntos o guiones usadas como variables de entorno

# ❌ La clave 'DATABASE.URL' no es un nombre de variable válido.
#    Docker/shell aceptarían fallos de mapeo; Kubernetes ignora la clave
#    o directamente falla al validar el Pod.
data:
  DATABASE.URL: postgres://…

# ✅ soluciones: (a) renombrar la clave, o (b) usar configMapKeyRef con re-naming
env:
  - name: DATABASE_URL                     # nombre de variable válido
    valueFrom:
      configMapKeyRef:
        name: api-config
        key: DATABASE.URL                  # clave rara… pero con nombre limpio fuera

❌ Confundir ConfigMap con el lugar para secretos

# ❌ La contraseña de postgres en texto plano dentro de un ConfigMap
kubectl create configmap credenciales \
  --from-literal=PASSWORD=hunter2          # visible para cualquiera con RBAC

# ✅ Los secretos van en un objeto Secret (core/v1) que además soporta
#    cifrado en reposo: se verá en la lección 02-secrets.
kubectl create secret generic pg-secret \
  --from-literal=POSTGRES_PASSWORD=hunter2

❌ Montar un archivo y olvidar que sustituye la carpeta

Si montas un volumen ConfigMap en /etc/nginx/conf.d y la imagen ya tenía su propio default.conf, este queda oculto. Si además añades otra clave llamada como un archivo que esperabas conservar, también se pierde. La solución idiomática: que el ConfigMap sea el contenido completo de esa carpeta (como hicimos en el ejemplo real).

❌ Esperar que un kubectl edit configmap actualice los Pods al instante

# ❌ No funciona así: los Pods siguen con las variables viejas
kubectl edit configmap api-config

# ✅ Debes reiniciar el Deployment para que sus Pods re-lean la config
kubectl rollout restart deployment api
kubectl rollout status deployment api     # esperar a que termine el rollout

7 · Ejercicio guiado

Objetivo: crear un ConfigMap que se inyecte en un Pod de pruebas (busybox) por las tres vías y verificar el resultado dentro del Pod.

  1. Crea el ConfigMap con 3 claves: 
    kubectl create configmap app-config \
  --from-literal=APP_NAME=harbortasks \
  --from-literal=APP_COLOR=blue \
  --from-literal=APP_PAGINA=principal
kubectl get configmap app-config
  2. Lanza un Pod de prueba que use envFrom y un configMapKeyRef: 
    kubectl run test-pod --image=busybox --restart=Never --command -- sleep 3600
  3. Edita el Pod para añadir las variables (kubectl edit pod test-pod) y añade bajo containers[0]: 
              env:
            - name: NOMBRE_RENOMBRADO        # renombramos la clave
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: APP_PAGINA
          envFrom:
            - configMapRef:
                name: app-config             # vuelca APP_NAME y APP_COLOR
  4. Verifica dentro del Pod: 
    kubectl exec test-pod -- env | grep -E 'APP_NAME|APP_COLOR|NOMBRE_RENOMBRADO'

    Resultado esperado: seis líneas, una por variable, con los valores harbortasks, blue y principal (renombrada). Si no ves alguna, vuelve al paso 3 y confirma el YAML.

  5. Limpia: kubectl delete pod test-pod y kubectl delete configmap app-config.

Windows (PowerShell): en cmd/PowerShell evita las barras inversas \ de continuación; escribe el comando en una sola línea. Y los acentos en los literales pueden dar problemas de codificación: usa valores ASCII para los ejemplos.

8 · Reto

🎯 Recarga en caliente de un fichero de config

Modifica el ejemplo real de la web: añade una cabecera de respuesta (proxy_set_header X-Env "prod";) al bloque /api/ editando el ConfigMap web-config con kubectl edit. Después comprueba que nginx sirve la versión nueva de default.conf sin reiniciar el Deployment (las configuraciones montadas como volumen se sincronizan). ¿Qué comando de nginx ejecutarías dentro del Pod para forzar la recarga? Pista: existe un binario de señalización llamado nginx -s y la recarga se hace con kubectl exec.

Pista: kubectl exec deployment/web -- nginx -s reload y antes verifica el estado con kubectl exec deployment/web -- nginx -t. El fichero montado se actualiza en pocos segundos tras el kubectl edit.

9 · Resumen

  • El ConfigMap separa la configuración de la imagen: misma imagen, distintos entornos (12-factor).
  • Es un objeto core/v1 del namespace, con data (texto) y binaryData (Base64), máximo 1 MiB.
  • Tres vías de consumo: env.configMapKeyRef (una clave), envFrom (todas) y volumen (clave → archivo).
  • La config sensible NO va en un ConfigMap: va en un Secret (siguiente lección).
  • immutable: true evita cambios accidentales y mejora el rendimiento del kubelet.
  • Cambiar un ConfigMap no reinicia Pods: las variables requieren kubectl rollout restart.

10 · Preguntas frecuentes

¿Un ConfigMap puede tener más de 1 MiB?

Por defecto el API server limita los objetos a 1 MiB (apiserver etcd request size). Superarlo hace fallar el kubectl apply. Es una señal de diseño: si necesitas más, ese dato no pertenece al ConfigMap; piensa en un volumen (archivo grande ya empaquetado) o en otro objeto.

¿Qué pasa si un Pod referencia un ConfigMap que no existe?

Depende: si usas env/configMapKeyRef con optional: false (por defecto), el Pod falla con CreateContainerConfigError. Marcando optional: true el Pod arranca sin esa variable. Con volúmenes, si el ConfigMap no existe el Pod permanece Pending.

¿Por qué las variables de entorno no se actualizan al editar el ConfigMap?

El kubelet inyecta las variables de entorno en el momento de crear el contenedor, como si fueran argumentos del proceso. Son inmutables durante la vida del contenedor. Por eso hace falta kubectl rollout restart (recrea contenedores). Los volúmenes, en cambio, se sincronizan periódicamente sin reiniciar.

¿ConfigMap y Secret son lo mismo?

Mismo mecanismo (mapa clave-valor), distinta semántica y distinto tratamiento. Los Secrets no se exponen en kubectl describe (por defecto), soportan cifrado en reposo y gestionan la rotación de otra forma. Regla sencilla en HarborTasks: la URL de la BBDD puede ser ConfigMap; la contraseña, siempre Secret.

¿Debo versionar los ConfigMap en Git?

Sí: los manifiestos YAML de ConfigMap deben estar en Git junto al resto del código (los valores habitualmente referenciando secretos por nombre, no con el valor). Eso te da historial, revisión y aplicado reproducible. Basta con kubectl apply -f configmaps.yaml tras el despliegue de la aplicación.
