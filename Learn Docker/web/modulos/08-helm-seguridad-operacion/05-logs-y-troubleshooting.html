Logs, kubectl debug y troubleshooting

Módulo 8 · Helm, seguridad y operación ⏱ 35 minutos

1 · Introducción

Has desplegado HarborTasks en Kubernetes. Ahora toca la parte que nadie te enseña y todo el mundo necesita: cuando un pod falla, ¿qué haces? Kubernetes no falla "en silencio": cada estado raro tiene una huella concreta que puedes leer si sabes dónde mirar.

Esta lección te da el método: los cuatro comandos que configuran el 90% del troubleshooting (kubectl logs, kubectl describe pod, kubectl get events y kubectl debug), el significado de los estados problemáticos más comunes (Pending, ImagePullBackOff, CrashLoopBackOff, CreateContainerConfigError, OOMKilled) y un proceso sistemático para diagnosticar, no para tirar a ciegas.

El porqué: la diferencia entre un operador junior y uno senior no es "saber el comando", es saber qué comando cuando. Los logs te dicen qué pasó dentro del contenedor; los eventos te dicen qué pasó alrededor del pod. El diagnóstico es leer ambas capas en orden.

2 · Teoría

Las capas de un problema: contenedor vs pod vs nodo

┌──────────────────────────────────────────────┐ │ Qué pasó DENTRO del contenedor → kubectl logs │ │ Qué pasó ALREDEDOR del pod → describe/events│ │ Qué pasó en el NODO → describe node │ └──────────────────────────────────────────────┘ Lee en este orden exacto cuando algo falla.
  • Logs: lo que el proceso imprimió por stdout/stderr (el contenedor ya arrancó y ejecutó código).
  • Events: lo que el kubelet y el scheduler decidieron (pull de imagen, fallos de arranque, reinicios). A menudo el evento es más informativo que el log cuando el contenedor ni siquiera llegó a arrancar.
  • Describe node: presión de recursos, taints, condiciones que impiden colocar pods.

Estados problemáticos y su significado

kubectl logs en sus tres variantes

# Logs actuales (desde que el contenedor está vivo)
kubectl logs api-5d8f4f9d7f-xk2p4 -n harbortasks

# Logs en streaming: la mejor herramienta durante un incidente
kubectl logs -f api-5d8f4f9d7f-xk2p4 -n harbortasks

# Logs ANTERIORES: la pieza clave del CrashLoopBackOff
# El contenedor actual ya murió; la vida pasada está en --previous
kubectl logs --previous api-5d8f4f9d7f-xk2p4 -n harbortasks

# Combo: los últimos 50 del proceso anterior (evita spam)
kubectl logs --previous --tail=50 api-5d8f4f9d7f-xk2p4 -n harbortasks

Los events: la crónica del kubelet

# Eventos del cluster ordenados por tiempo (invirtiendo lo reciente)
kubectl get events --sort-by=.lastTimestamp -n harbortasks

# Con nombres de objetos implicados (Time / Reason / Message)
kubectl get events --sort-by=.lastTimestamp -n harbortasks -w

Un detalle: los eventos son efímeros — se limpian solos con el tiempo. Si el pod falló hace horas, el evento ya no está. Por eso muchos equipos envían eventos a un agregador de logs (Módulo 9 verás CI/CD y observabilidad).

kubectl debug: meter una sonda en el pod

Hay problemas que no se ven ni con logs ni con eventos: "¿el DNS del clúster funciona?", "¿ese archivo existe en la imagen?". Para eso existe kubectl debug, que crea un ephemeral container: un contenedor temporal de inspección dentro del pod en ejecución (debug container). Comparte el network namespace y el filesystem del pod, así que puedes probar la red, montar herramientas y mirar procesos, sin tocar el código de la app:

# Añade un contenedor temporal "debugger" (imagen con herramientas)
kubectl debug api-5d8f4f9d7f-xk2p4 -n harbortasks \
  --image=nicolaka/netshoot               # imagen clásica de red + shell
  --target=api                            # comparte namespace del contenedor api

# Ya dentro del debugger: mira la red, DNS, procesos y archivos
ping web                                  # ¿resuelve el Service web?
curl http://web/                          # ¿responde nginx?
ps aux                                    # ¿qué procesos viven en el pod?
ls /app/dist                              # ¿existe el artefacto que buscamos?

Alternativa clásica: si la imagen tiene shell y herramientas, kubectl exec basta. El debug container es el refuerzo para cuando la imagen es mínima (alpine distroless) o el contenedor no arranca y necesitas inspeccionar el entorno.

3 · Ejemplo mínimo

El ciclo completo de diagnóstico en un solo ejemplo. Crea un pod deliberadamente roto y léelo con el método:

# pod-roto.yaml — el pod fallará a propósito en el próximo paso
apiVersion: v1
kind: Pod
metadata:
  name: pod-roto
spec:
  containers:
    - name: app
      # Imagen REAL pero con tag inventado → ImagePullBackOff
      image: node:999
# 1. Aplica y mira el estado
kubectl apply -f pod-roto.yaml
kubectl get pod pod-roto          # STATUS: ImagePullBackOff

# 2. Lee el reportaje del kubelet (¿por qué?): eventos
kubectl describe pod pod-roto | tail -20
# Events:
#   Failed to pull image "node:999": ... manifest unknown
#   Back-off pulling image "node:999"   ← aquí está la causa raíz

# 3. Limpia
kubectl delete pod pod-roto

Observa el orden: primero el estado (get), luego el porqué (describe), sin saltar a los logs — que aquí no existen, porque el contenedor nunca llegó a arrancar.

4 · Ejemplo real

Diagnóstico real de un pod de HarborTasks. Escenario: la API entra en CrashLoopBackOff justo después de un despliegue con Helm.

# 0. El síntoma: el deployment no se estabiliza
kubectl get pods -n harbortasks
# NAME                   READY   STATUS             RESTARTS   AGE
# api-7b5f8d9f5c-abc12   0/1     CrashLoopBackOff   5          3m
# 1. Describe: capa del pod, eventos (puede pedir "Por qué se reinicia") 
kubectl describe pod api-7b5f8d9f5c-abc12 -n harbortasks
# ...
# State:          Waiting
#   Reason:       CrashLoopBackOff
# Last State:     Terminated
#   Reason:       Error
#   Exit Code:    1          ← el proceso murió con error
# Events:
#   Back-off restarting failed container
# 2. Logs del contenedor ANTES de morir: el mensaje real del proceso
kubectl logs api-7b5f8d9f5c-abc12 -n harbortasks --previous --tail=30
# ← Port 3000 is not listening?  No: aquí lo que imprime node/express
# Error: Cannot find module '/app/dist/server.js'
#     at Module._resolveFilename (node:internal/modules/...)
# ← la API no puede encontrar su ejecutable

# 3. ¿Dónde está el archivo? El pod construye la imagen desde el stage
kubectl exec api-7b5f8d9f5c-abc12 -n harbortasks -- ls /app
# ❌ exec failed: container is restarting ... (no da tiempo a entrar)
# 4. Como no arranca, usamos un debug container temporal
kubectl debug api-7b5f8d9f5c-abc12 -n harbortasks \
  --image=alpine --target=app -- rm 2>/dev/null
# Crea un pod clon: api-7b5f8d9f5c-abc12-debug-XXXX (mismos volumenes)
kubectl exec -it api-7b5f8d9f5c-abc12-debug-XXXX -n harbortasks -- sh
# dentro del clon:
ls /app          # ¿existe dist?
# /app/dist NO existe → el Dockerfile multi-stage no copió la etapa builder

# 5. La causa raíz: en el chart el image.tag apunta a un build que
#    llegó sin dist (nueva imagen, etapa de build rota). La SOLUCIÓN
#    correcta es arreglar el Dockerfile/build, no el pod a mano.
helm list -n harbortasks
helm history harbortasks -n harbortasks   # ¿qué revisión introdujo el bug?
helm rollback harbortasks 3 -n harbortasks  # y si no la tenemos: arreglar imagen

# 6. Tras corregir la imagen se despliega de nuevo y se verifica
kubectl rollout status deployment/api -n harbortasks
kubectl get pods -n harbortasks            # ahora sí Running y Ready

Moraleja del caso: ningún comando mágico. Fue una cadena: estado → describe → logs --previous → debug container → arreglo en el origen. El error del pod casi nunca se arregla en el pod: se arregla en la imagen, el chart o los values.

5 · Buenas prácticas

HazEvitaPor qué
Diagnosticar en orden: estado → describe → logs → debug Querer arreglar con el primer comando que revisa Cada capa responde una pregunta distinta; saltartela te hace perder la causa raíz y "arreglar" el síntoma.
Usar logs --previous en CrashLoopBackOff Mirar solo kubectl logs en un pod reiniciándose El contenedor actual ya murió; el mensaje útil está en la ejecución anterior.
Dejar los logs con -f durante un incidente Cerrar la condición de streaming y volver a lanzarla cada segundo Ahorra tiempo y ves en el momento el impacto de tus cambios.
Leer los events con --sort-by y mirar el Message Ignorar los events porque "los logs decían otra cosa" Cuando el contenedor ni arranca, solo los events tienen la verdad. Son efímeros: captúralos pronto.
Arreglar la causa raíz (imagen/chart/values) y hacer rollback con Helm Parchear el pod en marcha con edits manuales El pod es efímero por diseño: cualquier fix manual se pierde en el siguiente rollout. Repara el origen y re-despliega.

6 · Errores habituales

Mirar logs cuando el contenedor nunca arrancó

# ❌ En un ImagePullBackOff no hay logs: el contenedor no existe
kubectl logs pod-roto
# Error from server (BadRequest): container "app" in pod "pod-roto"
# is waiting to start: trying and failing to pull image

# ✅ Los events tienen la respuesta (credenciales, tag, imagen inexistente)
kubectl describe pod pod-roto | grep -A 2 "Failed to pull image"

Olvidar el --previous en CrashLoopBackOff

# ❌ El log "actual" puede estar vacío o ser el de "estoy reiniciando"
kubectl logs api-7b5f8d9f5c-abc12 -n harbortasks        # (casi vacío)

# ✅ Logs de la ejecución ANTERIOR: ahí está el error real
kubectl logs api-7b5f8d9f5c-abc12 -n harbortasks --previous

Confundir CreateContainerConfigError con un bug de la app

# ❌ Pensar que "la app no arranca" sin leer el evento
kubectl get pod api-xxx -n harbortasks
# STATUS: CreateContainerConfigError

# ✅ El evento lo dice: te falta el ConfigMap/Secret que referencia el env
kubectl describe pod api-xxx -n harbortasks | grep -i "error"
# Error: configmap "mi-config" not found → crea el ConfigMap y redeploy

Pensar que GetEvents es lo mismo que logs

# ❌ Esperar que los events muestren la salida del proceso
kubectl get events -n harbortasks    # (no está el mensaje de la app)

# ✅ Los events cuentan la vida del pod; la salida de la app va a logs
kubectl get events --sort-by=.lastTimestamp -n harbortasks
kubectl logs api-xxx -n harbortasks --previous

7 · Ejercicio guiado

Objetivo: reproducir y diagnosticar con método un CreateContainerConfigError (falla del despliegue de HarborTasks al referenciar un Secret inexistente) y dejarlo resuelto.

  1. Paso 1: crea un namespace de laboratorio y un Deployment que referencia un Secret que no existe: 
    kubectl create namespace debuglab
kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata: { name: api, namespace: debuglab }
spec:
  replicas: 1
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: api
          image: harbortasks-api:1.0.0
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: no-existe     # ← este Secret no creado
                  key: database-url
EOF
  2. Paso 2: observa el estado: kubectl get pods -n debuglab → STATUS CreateContainerConfigError.
  3. Paso 3: culpable al instante en los events: 
    kubectl get events --sort-by=.lastTimestamp -n debuglab | tail -5
# Message: secret "no-existe" not found
  4. Paso 4: crea el Secret que falta con kubectl: 
    kubectl create secret generic harbor-secrets -n debuglab \
  --from-literal=database-url='postgres://harbor:harborpass@postgres:5432/harbortasks'
kubectl rollout restart deployment api -n debuglab
kubectl get pods -n debuglab
  5. Paso 5 (verificación): el pod pasa a Running y 1/1 Ready; los events nuevos ya no mencionan el Secret: 
    kubectl get pods -n debuglab
kubectl logs deployment/api -n debuglab --tail=20   # la API arranca normal
  6. Paso 6: limpia: 
    kubectl delete namespace debuglab

Verificación que vale oro: fíjate en que para diagnosticar necesitaste exactamente dos comandos (get events y create secret). Ni logs ni describe: el evento ya te dio la página exacta del libro.

8 · Reto

🎯 El pod que "no puede oír"

Crea un Deployment del API de HarborTasks sin definir port-forward ni Service, con command: ["sh","-c","curl http://web/"] (intenta llamar al Service de la web). Verás un estado curioso de "falta de DNS/red". Tu misión: usar kubectl debug con una imagen de red (p. ej. nicolaka/netshoot), averiguar si web se resuelve por DNS del clúster y dejar documentado (en un comentario del propio manifiesto) el diagnóstico por el que la API no llega a la web desde dentro del clúster.

Pista: el DNS interno de Kubernetes crea <service>.<namespace>.svc.cluster.local. El namespace importa: desde el mismo namespace basta web; desde otro, la forma larga.

9 · Resumen

  • Un problema tiene dos capas: lo que pasó dentro del contenedor (logs) y lo que pasó alrededor del pod (events/describe).
  • Estado → describe → logs → debug: el método de diagnóstico sistemático.
  • kubectl logs --previous es la primera herramienta contra CrashLoopBackOff.
  • CreateContainerConfigError = referencia rota a Secret/ConfigMap; ImagePullBackOff = problema de imagen; OOMKilled = límite de memoria alcanzado.
  • kubectl debug crea un ephemeral container para inspeccionar un pod sin tocar la imagen de la app.
  • Los events son efímeros y se ordenan con --sort-by=.lastTimestamp.
  • El arreglo vive en la causa raíz (imagen/chart/values), no en el pod.
ComandoQué hace
kubectl logs POD -n NLogs actuales del contenedor
kubectl logs -f POD -n NLogs en streaming (incidentes en vivo)
kubectl logs --previous POD -n NLogs de la ejecución anterior (causa del reinicio)
kubectl describe pod POD -n NEstado, condiciones y events del pod
kubectl get events --sort-by=.lastTimestamp -n NCrónica del kubelet/scheduler ordenada en el tiempo
kubectl debug POD -n N --image=… --target=…Crea un contenedor temporal (ephemeral) para inspeccionar
kubectl rollout status deployment/api -n NEspera y comprueba que el rollout termina bien tras el fix

10 · Preguntas frecuentes

Mi pod está en CrashLoopBackOff pero los logs no dicen nada, ¿qué hago?

Tres frentes: (1) logs --previous por si el mensaje útil está en la corrida anterior; (2) describe para eventos de arranque (probes fallando, comandos rotos, permisos); (3) si sigue en blanco, el proceso puede estar muriendo antes de imprimir — sube temporalmente el nivel de log de la app o usa kubectl debug para inspeccionar el entorno.

¿Los eventos sirven para algo en un pod que lleva horas roto?

Sí, aunque los events se auto-purgan con el tiempo. Si ya no están se completa el diagnóstico con describe (que conserva condiciones), el historial de kubectl rollout history y los logs externos (un agregador central). Por eso en producción se persisten los logs y eventos fuera del clúster.

¿Puedo hacer kubectl exec a un pod que se está reiniciando?

No de forma fiable: entre reinicios no hay contenedor al que conectarse. Por eso el kubectl debug crea un clon del pod (mismos volúmenes y config) o un ephemeral container dentro del pod vivo; es la vía correcta para inspeccionar casos en que el contenedor objetivo no arranca.

¿Cuándo es mejor el debug container que una imagen "gorda" con shell?

El debug container es ideal para imágenes mínimas o distroless (sin shell y sin herramientas), en producción, sin cambiar la imagen de la app ni reiniciar nada. La imagen "gorda" en producción es en sí un problema de superficie de ataque; el debug container es el compromiso: herramientas solo cuando las necesitas y solo mientras dura la sesión.

¿Por qué el mensaje de un OOMKilled no aparece en los logs?

Porque el OOM no lo decide el proceso: lo decide el kernel (cgroup) cuando el contenedor cruza su límite de memoria. En logs verás la salida de la app justo hasta el corte; la razón exacta (OOMKilled) está en describe pod en Last State. Si quieres el detalle del kernel, consulta el dmesg/journaldel nodo.
