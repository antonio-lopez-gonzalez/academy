Desplegar API y web

Módulo 9 · Proyecto final ⏱ 35 minutos

1 · Introducción

En la lección anterior diseñaste el plano del clúster. Ahora toca construir los primeros edificios: el API (Node/Express) y la web (nginx). Verás con detalle los siete manifiestos que las llevan a producción-like: ConfigMap, Secret, Deployment (con probes y no-root), Service y HPA para el API; ConfigMap, Deployment y Service para la web.

El objetivo no es solo "aplicar YAML": es entender qué abstracción resuelve cada problema. Por qué un Deployment y no pods sueltos, por qué un Service da un nombre estable, por qué la configuración se separa en ConfigMap/Secret, por qué las probes deciden si un pod recibe tráfico, y por qué el HPA escala sin intervención humana.

¿Por qué esta lección primero? Porque API y web son la "cara" del sistema: lo que el usuario ve y lo que procesa sus peticiones. Postgres (lección 3) es el soporte. Desplegar en este orden también te enseña una verdad operativa muy valiosa: los servicios pueden estar Running sin estar Ready. Lo verás con tus propios ojos.

Importante: en esta lección el API arrancará y vivirá, pero su readiness fallará porque Postgres aún no existe (los pods estarán 0/1 Ready). Es esperado y didáctico: en la lección 3, al desplegar la BD, se recuperarán solos. Kubernetes ante esto simplemente no les envía tráfico: no es un error, es su sistema de salud.

2 · Teoría

El trío que sostiene cada servicio: Deployment + Service + Config

RecursoProblema que resuelveAnalogía
Deployment Declarar el estado deseado (imagen, réplicas, probes) y reconciliarlo: si un pod muere, crea otro; si cambias la imagen, hace un rolling update sin downtime. El contrato laboral del restaurante: dice cuántos cocineros y qué puesto; si uno se marcha, se contrata otro igual.
Service (ClusterIP) Un nombre DNS estable y un balanceo entre pods vivos. Los pods tienen IPs efímeras; el Service nunca cambia. El teléfono fijo del negocio: aunque cambien los empleados que lo atienden, el número es el mismo.
ConfigMap Guardar configuración no sensible (puertos, hosts, paths) fuera de la imagen. La carta de precios: se actualiza sin rehacer la cocina.
Secret Guardar credenciales (usuarios, contraseñas) separadas de la imagen y de la config legible. La llave de la caja fuerte: solo quienes la necesitan la tienen.

Probes: el "semáforo" de cada pod

  • startupProbe — ¿ha terminado de arrancar la app? Da margen a las apps lentas antes de evaluar las demás. Si falla N veces, el pod se reinicia.
  • livenessProbe — ¿sigue viva la app? Detecta deadlocks u horas muertas. Si falla, el pod se reinicia.
  • readinessProbe — ¿puede recibir tráfico ya? Por ejemplo, solo cuando la BD responde. Si falla, el pod se quita del Service (no recibe tráfico) PERO NO se reinicia.

Analogía: liveness es preguntar "¿estás despierto?": si no contestas, te despiertan (reinicio). Readiness es colgar el cartel "abierto": si la cocina no está lista, no entra gente (no recibe tráfico), pero el local sigue abierto esperando. Por eso nuestra BD inexistente dejará al API vivo pero sin cartel de abierto.

HPA: el gerente que contrata y despide solo

El HorizontalPodAutoscaler (apiVersion autoscaling/v2) observa métricas (CPU/memoria) de los pods y ajusta las réplicas del Deployment entre un mínimo y un máximo. Es la diferencia entre "escalar por miedo" y "escalar por necesidad": la aplicación se adapta al tráfico real sin que un humano esté pendiente.

3 · Ejemplo mínimo

El ejemplo mínimo de "servicio desplegado con estilo" es un único Deployment + Service de nginx. Sin ConfigMap, sin probes, sin HPA: solo el esqueleto. Es el 80% de cualquier manifiesto de trabajo:

# deployment-minimo.yaml
apiVersion: apps/v1              # API de Deployments (estable, v1)
kind: Deployment
metadata:
  name: mi-web                   # Nombre del Deployment
  namespace: harbortasks         # Dónde vive (creado en la lección 1)
spec:
  replicas: 2                    # Queremos 2 copias idénticas
  selector:
    matchLabels:
      app: mi-web                # El Deployment "gobierna" pods con esta etiqueta
  template:
    metadata:
      labels:
        app: mi-web              # La etiqueta DEBE coincidir con el selector
    spec:
      containers:
        - name: web              # Nombre del contenedor (dentro del pod)
          image: nginx:1.27-alpine   # Imagen pinned: versión exacta, nunca :latest
          ports:
            - containerPort: 80  # Puerto que escucha el contenedor (informativo)
---
apiVersion: v1                   # API estable de objetos básicos
kind: Service
metadata:
  name: mi-web
  namespace: harbortasks
spec:
  selector:
    app: mi-web                  # El Service reparte tráfico a pods con esta etiqueta
  ports:
    - port: 80                   # Puerto del Service (el "número fijo")
      targetPort: 80             # Puerto del pod al que envía

Línea por línea (lo esencial): el selector.matchLabels del Deployment y el selector del Service usan la misma etiqueta — es el pegamento del sistema. El Service se llama mi-web, así que dentro del namespace cualquier pod hablará con él usando el nombre DNS mi-web (o mi-web.harbortasks.svc.cluster.local). Aplica con kubectl apply -f deployment-minimo.yaml.

4 · Ejemplo real

Aquí están los manifiestos completos del API y la web de HarborTasks, tal como viven en proyectos/harbortasks/k8s/. Léelos como un ingeniero de plataforma: cada línea tiene una razón.

API — ConfigMap y Secret

k8s/api/configmap.yaml
# configmap.yaml — configuración NO sensible del API
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config                          # El API la referenciará por este nombre
  namespace: harbortasks
data:
  PORT: "3000"                # Puerto interno donde Express escucha
  NODE_ENV: production        # Configuración no sensible (sin credenciales)
k8s/secrets.yaml
# secrets.yaml — credenciales del stack (un único Secret compartido)
apiVersion: v1
kind: Secret
metadata:
  name: harbor-secrets
  namespace: harbortasks
type: Opaque                 # Tipo genérico de secret (clave-valor opaco)
data:                        # los valores van en base64 (echo -n '...' | base64)
  # echo -n 'postgres://harbor:harborpass@postgres:5432/harbortasks' | base64
  database-url: cG9zdGdyZXM6Ly9oYXJib3I6aGFyYm9ycGFzc0Bwb3N0Z3Jlczo1NDMyL2hhcmJvcnRhc2tz
  # echo -n 'harborpass' | base64
  postgres-password: aGFyYm9ycGFzcw==
# OJO: base64 NO es cifrado. Es solo una codificación. La protección real
# viene de los permisos (RBAC) y de no commitear el archivo. Para credenciales
# reales se usa el secret manager del proveedor (Secrets Store CSI, SOPS...).

Alternativa por CLI (igual de válida y sin archivo): kubectl create secret generic harbor-secrets -n harbortasks --from-literal=database-url='postgres://harbor:harborpass@postgres:5432/harbortasks' --from-literal=postgres-password='harborpass'. En el curso escribimos manifiestos porque son revisables y reproducibles.

API — Deployment (el corazón de la lección)

k8s/api/deployment.yaml
# deployment.yaml — pods de Express con probes, recursos y no-root
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: harbortasks
  labels:
    app: api
spec:
  replicas: 2                 # Estado deseado: 2 pods. El HPA los ajustará.
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api              # Mismo label que el selector y que el Service
    spec:
      securityContext:                    # Seguridad a nivel de POD
        runAsNonRoot: true                # Prohibido arrancar como root
        runAsUser: 1000                   # Usuario sin privilegios
        fsGroup: 1000                     # Grupo propietario de los volúmenes
      containers:
        - name: api
          image: harbortasks-api:1.0.0    # Imagen construida en módulos 1-4
          ports:
            - containerPort: 3000         # Puerto de la app (informativo)
          envFrom:                        # Importa TODO el entorno no sensible
            - configMapRef:
                name: api-config          #  1. el ConfigMap (PORT, NODE_ENV)
          env:                            # La cadena de conexión es sensible: del Secret
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: harbor-secrets
                  key: database-url
          resources:
            requests:                     # Reserva mínima garantizada
              cpu: 100m                   # 0.1 vCPU
              memory: 128Mi
            limits:                       # Techo duro (OOM-kill por encima)
              cpu: 500m
              memory: 256Mi
          startupProbe:                   # ¿Terminó de arrancar?
            httpGet:
              path: /health               # Endpoint "estoy vivo" de Express
              port: 3000
            failureThreshold: 30          # 30 intentos x 2s = 60s de margen
            periodSeconds: 2
          livenessProbe:                  # ¿Sigue vivo? Si falla → reiniciar
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
            failureThreshold: 3           # 3 fallos seguidos → reinicio
          readinessProbe:                 # ¿Recibe tráfico? Solo si la BD responde
            httpGet:
              path: /ready                # 200 solo cuando Postgres responde
              port: 3000
            periodSeconds: 5
            failureThreshold: 3
# Fíjate: /ready depende de la BD. Hasta la lección 3 los pods estarán
# Running pero con readiness en 0/1 → el Service no les envía tráfico.

API — Service y HPA

k8s/api/service.yaml
# service.yaml — número fijo y balanceo hacia los pods api
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: harbortasks
spec:
  selector:
    app: api                    # Selecciona los pods del Deployment
  ports:
    - port: 80                  # El Service escucha en 80 dentro del clúster
      targetPort: 3000          # Y reenvía al puerto del contenedor Express
# DNS interno: api.harbortasks.svc.cluster.local (o simplemente "api"
# para cualquier pod del mismo namespace).
k8s/api/hpa.yaml
# hpa.yaml — escalado automático del API según CPU
apiVersion: autoscaling/v2      # API actual del HPA (métricas múltiples)
kind: HorizontalPodAutoscaler
metadata:
  name: api
  namespace: harbortasks
spec:
  scaleTargetRef:               # A quién escala: al Deployment "api"
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 1                # Nunca por debajo de 1
  maxReplicas: 5                # Nunca por encima de 5 (protección de costes)
  metrics:
    - type: Resource
      resource:
        name: cpu               # Mide el uso de CPU de los pods
        target:
          type: Utilization
          averageUtilization: 70   # Cuando la media supere 70% → añade réplicas
# El HPA respeta los "requests" que definimos: el % se calcula sobre el request.

Web — ConfigMap con el proxy nginx

k8s/web/configmap.yaml
# configmap.yaml — config de nginx de la web
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
  namespace: harbortasks
data:
  nginx.conf: |                # Bloque multilínea: un archivo de config completo
    server {
      listen 80;               # La web escucha en el puerto 80
      server_name _;           # Acepta cualquier host

      root /usr/share/nginx/html;   # Carpeta con los estáticos del frontend
      index index.html;

      # --- Proxy a la API ---
      # El navegador llama a la MISMA origem (/api/...); esta configuración
      # reenvía esas peticiones al Service api dentro del clúster.
      location /api {
        proxy_pass http://api;            # API de balanza con el Service api
        proxy_http_version 1.1;           # HTTP/1.1 necesario para keep-alive
        proxy_set_header Host $host;      # Preserva el Host original
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
      }

      # --- App de una sola página ---
      # Si la ruta no es un archivo real, devuelve index.html (rutas del SPA).
      location / {
        try_files $uri $uri/ /index.html;
      }
    }

Web — Deployment (nginx con el ConfigMap montado) y Service

k8s/web/deployment.yaml
# deployment.yaml — pods de nginx sirviendo el frontend
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: harbortasks
  labels:
    app: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 101         # El usuario no-root estándar de nginx
        fsGroup: 101
      containers:
        - name: web
          image: harbortasks-web:1.0.0    # Imagen nginx + estáticos del frontend
          ports:
            - containerPort: 80
          volumeMounts:
            - name: nginx-config
              mountPath: /etc/nginx/conf.d/default.conf  # Sobrescribe el default
              subPath: nginx.conf          # Solo monta ESTA clave del ConfigMap
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 10
      volumes:
        - name: nginx-config
          configMap:
            name: web-config   # La config vive "fuera" de la imagen
k8s/web/service.yaml
# service.yaml — la web también necesita su número fijo
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: harbortasks
spec:
  selector:
    app: web
  ports:
    - port: 80                  # Service web:80
      targetPort: 80            # → pods nginx:80

Aplicación en orden y primeros comandos de verificación

# 0. Asegurar que kind ve las imágenes locales (si las construiste en M1-M4)
kind load docker-image harbortasks-api:1.0.0 harbortasks-web:1.0.0

# 1. Configuración (ConfigMap y Secret) ANTES que los pods
kubectl apply -f k8s/namespace.yaml       # idempotente, no pasa nada si ya existe
kubectl apply -f k8s/api/configmap.yaml
kubectl apply -f k8s/api/secret.yaml
kubectl apply -f k8s/web/configmap.yaml

# 2. Workloads y su red
kubectl apply -f k8s/api/deployment.yaml
kubectl apply -f k8s/api/service.yaml
kubectl apply -f k8s/api/hpa.yaml
kubectl apply -f k8s/web/deployment.yaml
kubectl apply -f k8s/web/service.yaml

# 3. Verificación
kubectl get pods -n harbortasks            # api 0/2 Ready (esperado), web 2/2
kubectl get svc -n harbortasks             # api:80→3000, web:80→80
kubectl get hpa -n harbortasks             # target de 70% CPU, 1→5 réplicas
kubectl logs -n harbortasks deployment/api --tail=30   # busca "db" en los logs

Resultado esperado: los pods web estarán Running y Ready (1/1 o 2/2); los pods api estarán Running pero con readiness a medias (1/2 Ready o 0/2) y en los logs verás que el API reintenta conectar con Postgres. Perfecto: es exactamente el comportamiento que diseñamos. En la lección 3, al nacer la BD, se pondrán verdes solos.

5 · Buenas prácticas

HazEvitaPor qué
Montar el ConfigMap con subPath para configs de archivo Montar conf.d entero sin subtítulo subPath monta solo el archivo que quieres y no pisa otras configs del directorio
Definir requests realistas en cada pod Solo limits, o nada El scheduler usa requests para colocar pods y el HPA calcula porcentajes sobre ellos
Separar liveness (/health) de readiness (/ready) Usar la misma ruta para ambas Una app viva sin BD no debe reiniciarse, solo dejar de recibir tráfico
Pinnear versiones de imagen y revisar los cambios con kubectl rollout status latest y kubectl apply a ciegas Reproducibilidad y saber en qué punto del rollout vas
runAsNonRoot + puerto alto (3000) Correr como root y escuchar en 80 Menos superficie de ataque; nginx (web) sí puede usar 80 con usuario non-root 101

6 · Errores habituales

Etiquetas que no cuadran: el Service "no encuentra" pods

# ❌ El Service busca app: backend pero el Deployment etiqueta app: api
# service.yaml
spec:
  selector:
    app: backend   # ¡No existe ningún pod con esta etiqueta!
# Resultado: Endpoints vacío, pero SIN ningún error visible.

# ✅ Selector y labels con el mismo valor:
# service.yaml → selector: app: api
# deployment.yaml → template.metadata.labels: app: api
# Comprobar siempre: kubectl get endpoints -n harbortasks  (debe tener IPs)

Secret mal "leído" o mal referenciado

# ❌ Crear el Secret con una clave distinta a la que consume la app
kubectl create secret generic harbor-secrets --from-literal=password=abc123
# ... pero la app espera la clave database-url → lee vacío y muere la conexión

# ✅ Coherencia clave a clave: database-url en el Secret y en el Deployment
kubectl create secret generic harbor-secrets \
  --from-literal=database-url='postgres://harbor:harborpass@postgres:5432/harbortasks'
kubectl exec -n harbortasks deploy/api -- printenv | grep DATABASE_URL   # verificar

Confundir los estados del pod

# ❌ Ver "Running" y dar por hecho que el servicio funciona
kubectl get pods -n harbortasks
# NAME   READY   STATUS
# api   0/2      Running    ← Running ≠ Ready
# Si READY es 0/2, el pod NO recibe tráfico del Service.

# ✅ Leer la columna READY (y mirar por qué con describe)
kubectl describe pod -n harbortasks -l app=api   # eventos y probes
kubectl logs -n harbortasks deployment/api --tail=50

  3. Paso 3 — Verificar con logs y endpoints: 
    # El API debe estar en CrashLoopBackOff por fail de startup? NO:
# /health no depende de la BD, así que el pod ARRANCA y VIVE (Running).
kubectl logs -n harbortasks deployment/api --tail=30
# Verás reintentos de conexión a 'postgres:5432' → es el comportamiento DSEÑADO.

    # port-forward salta la red: conecta directo al pod, sin pasar por readiness

# /health: el proceso está vivo → 200 (por eso el pod no se reinicia)
curl -i http://localhost:8080/health

# /ready: la BD no existe → 503 (por eso READY es 0/1)
curl -i http://localhost:8080/ready

# /api/tasks: responde con error de BD (SQLSTATE 08001 / ECONNREFUSED)
curl -i http://localhost:8080/api/tasks

    Resultado esperado: /health responde 200, /ready responde 503 y /api/tasks falla con error de conexión. Comprender esto es el objetivo: vivo ≠ listo. En la lección 3, tras crear Postgres, los mismos pods se pondrán Ready y /api/tasks devolverá datos. Nada se reiniciará de forma manual.

  5. Paso 5 — Limpieza del proceso en segundo plano: 
    # En bash:  kill %1   |   En PowerShell:  Stop-Process -Name kubectl
# (o cierra la terminal; el port-forward muere con ella)

8 · Reto

🎯 Escalado inteligente del API

Actualiza el HPA para que el API escale también por memoria con una métrica adicional de tipo Resource (memory, average 75%) y un comportamiento (behavior) que limite el escalado brusco (por ejemplo, máximo +1 réplica cada 2 minutos). Después, genera carga con un bucle de curl y observa cómo cambia kubectl get hpa api.

Pista: en autoscaling/v2 la métrica de memoria se escribe igual que la de CPU cambiando name por memory; la sección behavior.scaleUp acepta policies de tipo Pods y Percent. Y recuerda: kubectl top pods -n harbortasks te muestra las métricas actuales que el HPA está consultando.

9 · Resumen

  • Cada servicio = Deployment + Service + (ConfigMap | Secret); el pegamento son las etiquetas.
  • ConfigMap guarda lo no sensible; Secret las credenciales (base64 ≠ cifrado).
  • Probes: startup (arranque), liveness (¿vivo? reinicia), readiness (¿recibe tráfico? quita del Service).
  • El API usa /ready que depende de Postgres ⇒ en esta lección estará Running pero 0/1 Ready: es diseño, no bug.
  • El HPA (autoscaling/v2) escala el API entre 1 y 5 réplicas según CPU.
  • La web monta su nginx.conf desde un ConfigMap con subPath y hace de proxy a /api.
  • kind no comparte tu Docker local: kind load docker-image antes de aplicar.

10 · Preguntas frecuentes

¿Por qué el API consulta Postgres por "postgres" y no por una IP?

Por el DNS interno del clúster (kube-dns): todo Service crea un nombre <servicio>.<namespace>.svc.cluster.local. Dentro del mismo namespace basta el nombre corto (postgres). Así, aunque los pods de Postgres cambien de IP, el nombre es estable: por eso la cadena de conexión del API usa el host postgres (nunca localhost), guardada en el Secret harbor-secrets.

¿Por qué mi pod de API se reinicia continuamente (CrashLoopBackOff)?

Con los manifiestos de esta lección no debería: la startupProbe apunta a /health, que no depende de la BD. Si ves CrashLoopBackOff, mira los logs (kubectl logs deploy/api): suele ser imagen no cargada en kind (ImagePullBackOff), el Secret sin la clave esperada, o un fallo al arrancar Express. En la lección 5 del módulo 8 tienes el patrón completo de diagnóstico.

¿El Secret con base64 no se descifra con un simple decode?

Sí, exactamente: base64 es codificación, no cifrado; cualquiera con acceso de lectura a Secrets puede decodificarlo. La seguridad real está en: no commitear el archivo, restringir permisos RBAC (get secrets limitado), y en entornos reales usar un gestor externo (Secrets Store CSI, SOPS, Vault). En kind es suficiente para aprender el patrón.

¿Por qué el web (nginx) necesita ser un Deployment con 2 réplicas si es estático?

Porque "estático" no significa "sin tráfico": todo el HTML/JS/CSS y el proxy de /api pasan por él. Dos réplicas dan tolerancia a fallos (si un pod muere, el otro sigue sirviendo) y son la excusa perfecta para ver cómo el Service balancea y cómo funciona el rolling update al cambiar la imagen. El coste en un clúster local es mínimo.

¿Es normal que el HPA muestre <unknown> o <unset>?

Sí, sobre todo al principio. El HPA necesita el metrics-server instalado para leer CPU/memoria (kind no lo trae por defecto; se instala con kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml) y además los valores tardan 30-60 s en aparecer. Sin él, kubectl top pods fallará con Metrics API not available. Lo instalaremos en la verificación de la lección 4.
