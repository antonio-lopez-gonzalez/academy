Arquitectura del despliegue final

Módulo 9 · Proyecto final ⏱ 30 minutos

1 · Introducción

Llegaste al final del camino. Durante los módulos 5 a 8 aprendiste cada pieza de Kubernetes por separado: Pods, Deployments, Services, ConfigMaps, Secrets, PVCs, Ingress, Helm y seguridad. Ahora llega el momento de unirlo todo: desplegar HarborTasks completo en un clúster local de kind, igual que lo haría un equipo de plataforma en producción.

HarborTasks es el caso de estudio que ha recorrido contigo todo el curso: una API REST en Node.js/Express, una web estática servida por nginx y una base de datos PostgreSQL. En los módulos 1–3 las contenerizaste por separado; en el módulo 4 las orquestaste con Compose; hoy vas a trasladar ese mismo stack a Kubernetes.

En esta lección diseñas el plano del despliegue: qué recursos existen, cómo se relacionan, por qué están organizados así y cuál es el plan de trabajo en los próximos pasos. Es la diferencia entre "aplicar manifiestos al azar" y "desplegar con intención".

¿Por qué existe esta lección? Porque en producción el 90% de los problemas no vienen de un manifiesto incorrecto, sino de no tener un modelo mental claro de cómo fluye el tráfico y los datos. Dibujar la arquitectura antes de escribir YAML te permite anticipar fallos: ¿el API puede alcanzar a Postgres? ¿el usuario puede llegar al API a través del Ingress? ¿qué pasa si un pod muere?

Errores típicos de esta fase: desplegar piezas sin un orden lógico, olvidar cargar las imágenes en kind, dejar credenciales en ConfigMaps, lanzar Postgres sin PVC (y perder los datos al reiniciar) y no definir probes. Esta lección y las siguientes te blindan contra todos ellos.

2 · Teoría

El despliegue objetivo: siete familias de recursos

La arquitectura final del proyecto utiliza exactamente los recursos que estudiaste en los módulos 6 y 7. Cada uno resuelve un problema concreto:

  • Namespace harbortasks — un "inquilino" aislado dentro del clúster donde vive TODO el proyecto. Evita colisiones de nombres y permite aplicar políticas de acceso solo a este espacio.
  • Deployments (api, web, postgres) — declaran el estado deseado: cuántas réplicas, qué imagen, qué config, qué probes. Kubernetes lo reconcilia de forma continua.
  • Services (api, web, postgres) — dan un nombre DNS estable (api.harbortasks.svc.cluster.local) y reparten tráfico entre los pods vivos. Los pods mueren y renacen; el Service nunca cambia.
  • ConfigMaps y Secrets — separan la configuración (puertos, hosts) y lo sensible (contraseñas) del código de la imagen. La misma imagen sirve para dev y prod cambiando solo estos objetos.
  • PVC + StorageClass — persistencia declarativa para Postgres. El dato vive fuera del pod; si el pod muere, el disco y los datos sobreviven.
  • Ingress + ingress-nginx — una única puerta de entrada al clúster con enrutado por host y path: /api al API y / a la web.
  • HPA — escalado automático del API según CPU.

Analogía (el puerto que da nombre al proyecto): HarborTasks es un puerto marítimo. El Ingress es la aduana: decide qué mercancía (peticiones) va a qué muelle. Los Services son los muelles con nombre fijo: aunque el barco (pod) que atraca cambie cada día, el muelle siempre se llama igual. El PVC es el almacén en tierra: aunque el barco zarpe (pod destruido), la mercancía (datos) sigue en el almacén.

Por qué NO exponemos Postgres por el Ingress

Observa que el Ingress solo enruta a api y web. Postgres queda dentro del clúster, accesible únicamente por su Service postgres:5432. Esto es una decisión de seguridad deliberada: la base de datos es el activo más valioso y solo debe hablar con el API, nunca con el mundo exterior. En producción se aplica además la isolación por red (NetworkPolicies) entre namespaces.

El plan de trabajo en 3 movimientos

  1. Lección 2: desplegar el plano de datos de configuración (ConfigMap + Secret) y los workloads api y web con sus Services, probes y HPA.
  2. Lección 3: añadir postgres (Secret, PVC, Deployment, Service), su migración inicial y el Ingress con ingress-nginx.
  3. Lección 4: verificación end-to-end, checklist de producción y próximos pasos (CI/CD, Helm, observabilidad).

3 · Ejemplo mínimo

El despliegue completo tiene decenas de manifiestos, pero el "huevo" del que nace todo es solo dos piezas: el clúster y el namespace. Sin ellos, nada tiene dónde vivir ni con qué ordenarse.

k8s/namespace.yaml
# namespace.yaml — el contenedor lógico de todo el proyecto
apiVersion: v1                    # API estable de Kubernetes
kind: Namespace                   # Tipo de recurso: un namespace
metadata:
  name: harbortasks               # Nombre del namespace (identificador)
  labels:
    app.kubernetes.io/name: harbortasks   # Etiqueta estándar del proyecto
    app.kubernetes.io/part-of: harbortasks

# 1. Crear un clúster kind con un nombre reconfortante
kind create cluster --name harbor

# 2. Aplicar el namespace (idempotente: repetirlo no rompe nada)
kubectl apply -f k8s/namespace.yaml

# 3. Comprobar que existe
kubectl get namespaces

Línea por línea: kind create cluster --name harbor levanta un clúster completo (control plane + nodo worker) como contenedores de Docker; es la forma más ligera de tener Kubernetes real en tu máquina. kubectl apply -f es el verbo principal del despliegue declarativo: le dices a Kubernetes cómo debe quedar el mundo y él lo reconcilia. kubectl get namespaces te permite verificar: deberías ver harbortasks además de default, kube-system, kube-public y kube-node-lease.

Dato: el namespace default existe en todo clúster. Un error muy común es aplicar los manifiestos sin namespace y "contaminar" el espacio por defecto; por eso el primer manifiesto del proyecto es precisamente su propia casa.

4 · Ejemplo real

Este es el mapa completo de archivos que desplegarás en el clúster. Es exactamente la estructura de proyectos/harbortasks/k8s/:

proyectos/harbortasks/k8s/
├── namespace.yaml              # 1. La casa (namespace harbortasks)
├── secrets.yaml                # 2. Secret compartido (database-url + postgres-password)
├── api/
│   ├── configmap.yaml          #    Config no sensible del API (PORT, NODE_ENV)
│   ├── deployment.yaml         #    Pods Express + probes + recursos + no-root
│   ├── service.yaml            #    Service ClusterIP api:3000
│   └── hpa.yaml                #    Escalado automático 2→5 según CPU
├── web/
│   ├── configmap.yaml          #    nginx.conf que hace de proxy → /api
│   ├── deployment.yaml         #    Pods nginx + probes
│   └── service.yaml            #    Service ClusterIP web:80
└── postgres/
    ├── configmap.yaml          #    Migración inicial (001-init.sql)
    ├── pvc.yaml                #    Disco persistente 1Gi (StorageClass standard)
    ├── deployment.yaml         #    Pod Postgres 16 + volumen + probes pg_isready
    └── service.yaml            #    Service postgres:5432 (solo interno)

Decisiones de diseño que conviene entender ahora (no memorizar):

  • Un Secret compartido y ConfigMaps por servicio: las credenciales sensibles (usuario, contraseña, URL de conexión) viven en un único secrets.yaml que consumen tanto el API como Postgres, de modo que no puedan divergir. Lo no sensible (puerto, nivel de log, nginx.conf) va en el ConfigMap de cada servicio.
  • Imágenes de Postgres oficiales: postgres:16-alpine. El dato (las tareas) vive en el cluster, pero el binario es una imagen estándar mantenida por la comunidad.
  • El web "trabaja" de proxy: su nginx.conf usa proxy_pass para reenviar /api/* al Service api. Así el navegador habla con un solo origen (sin CORS) y el Ingress solo enruta dos paths.
  • HPA solo sobre el API: la web y Postgres son casi siempre estáticos; el API es la pieza que sufre picos de CPU al atender peticiones. Escalar lo que aporta valor, no lo que añade ruido.

Pasos siguientes (las 3 lecciones que completan el módulo): (02) aplicas API + web y los verificas con port-forward; (03) incorporas Postgres + Ingress y haces la primera prueba completa con curl; (04) ejecutas la batería de verificación y cierras el curso con el checklist de producción.

6 · Errores habituales

Desplegar sin plano, pieza a pieza

# ❌ Aplicar primero lo más "visible" y descubrir después los huecos
kubectl apply -f api-deployment.yaml   # pods que no tienen a quién hablar
kubectl apply -f web-deployment.yaml
# ... ¿y el namespace? ¿y el servicio? ¿y postgres?

# ✅ Orden lógico: base → configuración → workloads → puertas
kubectl apply -f namespace.yaml         # 1. la casa
kubectl apply -f api/configmap.yaml     # 2. la configuración
kubectl apply -f api/secret.yaml
kubectl apply -f api/deployment.yaml    # 3. los workloads
...

Poner credenciales en un ConfigMap

# ❌ La contraseña es "config", pero NO debe ir en un ConfigMap:
# api/configmap.yaml
data:
  DB_PASSWORD: harborpass          # visible para cualquiera con permiso de lectura

# ✅ La contraseña vive en un Secret (base64) y se referencian así:
# envFrom: [configMapRef, secretRef]
# Un Secret no es magia criptográfica: es una separación de responsabilidades
# y de permisos (RBAC puede restringir "get secrets" por separado).

Confundir "Running" con "funciona"

# ❌ Verificación pobre: solo miramos si el pod "está"
kubectl get pods          # Todo Running... ¿y las probes? ¿y la BD?

# ✅ Verificación real: estado + logs + tráfico real
kubectl get pods -n harbortasks
kubectl logs deploy/api -n harbortasks --tail=50
kubectl port-forward svc/api 8080:80 &   # y curl http://localhost:8080/health

Objetivo: dejar tu clúster kind y el namespace de HarborTasks listos y verificar el contexto de kubectl. Es la cimentación del módulo.

  1. Paso 1 — Arrancar el clúster: 
    # Crear el clúster (si ya existe, ignora el error o usa kind delete)
kind create cluster --name harbor
kubectl cluster-info        # confirma el endpoint del API server
  2. Paso 2 — Repasar los namespaces que trae Kubernetes de fábrica: 
    kubectl get namespaces
# Verás: default, kube-node-lease, kube-public, kube-system
# kube-system aloja los componentes del control plane (coredns, etc.)
  3. Paso 3 — Crear el namespace harbortasks y verificar el contexto: 
    kubectl create namespace harbortasks   # alternativa directa
# O declarativo: kubectl apply -f k8s/namespace.yaml (preferido en el curso)

kubectl get namespaces                 # ahora debe aparecer harbortasks
kubectl config get-contexts            # revisa el contexto "kind-harbortasks"
  4. Paso 4 — Verificación del resultado esperado: 
    # REFERENCIA: resultado correcto final
kubectl get namespace harbortasks
# NAME          STATUS   AGE
# harbortasks   Active   12s

# Y el contexto activo:
kubectl config current-context
# kind-harbortasks

Verificación: si STATUS dice Active y tu contexto es kind-harbortasks, la base está lista. En Windows usas los mismos comandos dentro de WSL2 (binarios Linux de kind/kubectl); solo cambia la instalación, nunca la sintaxis.

8 · Reto

🎯 Diseña un plano multi-entorno (dev / prod)

Dibuja en tu cuaderno (o en un archivo architecture.md) cómo sería el mismo HarborTasks en un clúster de producción real con 3 nodos: dos entornos (harbortasks-dev y harbortasks-prod), el API con 5 réplicas detrás de un Ingress con TLS, Postgres en nodos dedicados con discos gp3 y un sistema de backup cron.

Pista: piensa en qué cambia respecto a kind: las StorageClass no serán local-path, habrá NetworkPolicies, el Secret de TLS del Ingress apuntará a un certificado real (Let's Encrypt), y cada entorno tendrá su propio Secret — nunca se comparten credenciales entre entornos.

9 · Resumen

  • HarborTasks completo en K8s = namespace + 3 Deployments + 3 Services + ConfigMaps + Secrets + PVC + Ingress + HPA.
  • El tráfico fluye usuario → Ingress → Service → Pod; el dato fluye api → Service postgres → Pod postgres → PVC.
  • Postgres no se expone al exterior: es un Service interno para el API.
  • La web usa nginx como proxy de /api para evitar problemas de CORS en el navegador.
  • Orden de despliegue lógico: base → config → workloads → puertas.
  • kind no ve tu registro local de imágenes: hay que kind load docker-image.

10 · Preguntas frecuentes

¿Por qué tantos archivos para una app tan pequeña?

Porque cada archivo separa una preocupación: la config, lo sensible, el estado, el tráfico y la puerta de entrada. Separar es lo que permite cambiar una contraseña sin tocar el Deployment, o escalar sin reescribir nada. En producción real, un API con 4 servicios y 2 BDs tendría 40+ manifiestos; por eso al final aprenderás Helm para empaquetarlos.

¿Es normal que Postgres viva como un único pod?

Sí, en un clúster local es lo esperable. En producción, una BD de un solo pod con disco persistente ya es un buen comienzo; la alta disponibilidad de datos (réplicas síncronas, failover) se consigue con StatefulSets, operadores como CloudNativePG o servicios gestionados (RDS, Cloud SQL). El curso te deja la base para entender esas piezas.

¿Por qué el API tiene dos rutas de health (/health y /ready)?

Son dos preguntas distintas: /health responde "el proceso está vivo" (para liveness) y /ready responde "estoy listo para recibir tráfico", por ejemplo tras comprobar que Postgres responde (para readiness). En el módulo 6 (lección 5) viste por qué mezclarlas causa cortes de servicio innecesarios.

¿Qué pasa si aplico los manifiestos fuera de orden?

Kubernetes es tolerante: puedes aplicar un Deployment antes de su ConfigMap o Service sin error, porque la reconciliación reintenta. La diferencia está en el comportamiento observado: hasta que existan los objetos referenciados los pods estarán en Pending/CrashLoopBackOff. El orden lógico minimiza el ruido al diagnosticar y hace que aprecies que "está todo verde" desde el primer minuto.

¿Y si no tengo Docker para crear kind en Windows?

kind necesita un runtime de contenedores (Docker o containerd). En Windows la vía recomendada es WSL2 + Docker Desktop con integración de la distro habilitada: Docker corre dentro de WSL y kind crea "contenedores dentro de contenedores" sin drama de redes. El detalle paso a paso está en el módulo 0, lección 4.
