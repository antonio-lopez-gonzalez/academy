Postgres en clúster + Ingress

Módulo 9 · Proyecto final ⏱ 35 minutos

1 · Introducción

En la lección 2 desplegaste API y web, y los dejaste vivos pero no listos: el API reintentaba conectar con una base de datos que aún no existía. Esta lección es la que dota de alma al sistema: desplegarás PostgreSQL con persistencia real y, con ella, la puerta de entrada del clúster: el Ingress con el controlador ingress-nginx.

Al terminar harás la primera prueba de extremo a extremo: una petición curl entra por el Ingress, llega al API, y este lee las tareas de Postgres. Y lo mejor: el API, que llevaba una lección entera esperando, se pondrá verde solo gracias a la magia del modelo declarativo y las readiness probes.

¿Por qué una base de datos "merece su propia lección"? Porque la persistencia es el reto más delicado de Kubernetes. Un pod sin estado es efímero y barato; un pod con estado arrastra un disco, permisos, inicialización y un orden de arranque. Y el Ingress es el único componente que expone tu servicio al exterior: mal configurado, todo lo demás da igual porque nadie llega. Son dos "puntos de no retorno".

Errores típicos: PVC que se queda en Pending (storageClassName mal escrito), contraseñas de Postgres y del API distintas (fallo de auth silencioso), scripts de init que no se ejecutan porque el datadir ya existía, Ingress aplicado sin controlador instalado (404), y olvidar el header Host al probar.

2 · Teoría

¿Deployment o StatefulSet para Postgres?

A diferencia del API o la web, un servidor de bases de datos tiene identidad y orden. Las opciones:

  • Deployment + PVC (lo que usamos): suficiente para una instancia única y un clúster local. El PVC garantiza que el dato sobreviva a la muerte del pod.
  • StatefulSet: añade identidades estables (postgres-0, postgres-1), arranque y parada ordenados, y es el camino real para réplicas. Se usa con operadores (CloudNativePG, Zalando) para alta disponibilidad.

La regla práctica: si tu app necesita un solo disco y no tiene réplicas con roles, un Deployment con PVC es perfecto y más simple de razonar. Este proyecto usa ese camino; el StatefulSet queda como el siguiente escalón cuando necesites varias réplicas con identidad.

El ciclo de vida del dato: PVC y StorageClass

El pod de Postgres es un "inquilino" que cambia de IP y de disco cada vez que muere. El PersistentVolumeClaim pide almacenamiento de forma declarativa ("quiero 1Gi, lectura/escritura para un solo nodo"); el StorageClass decide cómo se materializa ese disco. En kind existe la StorageClass por defecto standard, provisionada por rancher.io/local-path: reserva una carpeta en el propio nodo (que, recuerda, es un contenedor Docker).

Analogía: el PVC es "el contrato de alquiler del almacén" y el StorageClass es "el tipo de almacén" (local estándar aquí; en la nube sería un disco rápido SSD). El pod (el barco) cambia, pero el almacén (PVC + disco) permanece firmado y con las llaves.

Límite honesto: al usar local-path en kind, el "disco" vive dentro del contenedor-nodo. Si borras el clúster con kind delete cluster, el dato desaparece con él. Para un curso local es perfecto (aprendes el flujo de la persistencia); en la nube usarías una StorageClass tolerante (EBS/gp3, etc.) que sobrevive al clúster entero.

Cómo se inicializa la base de datos

La imagen oficial de Postgres ejecuta cualquier archivo *.sql (o *.sh ejecutable) que encuentre en /docker-entrypoint-initdb.d/ solo la primera vez que se crea el data dir. Es el mecanismo perfecto para "migraciones simples": montamos un ConfigMap con nuestro SQL ahí. Detalle clave: si el volumen ya está inicializado (por ejemplo, porque reiniciaste el pod preservando el PVC), esos scripts NO se vuelven a ejecutar. Por eso el SQL debe ser idempotente (CREATE TABLE IF NOT EXISTS).

El Ingress y su controlador

El Ingress es una regla declarativa ("el host X manda /api al Service api y / al Service web"). Las reglas no se cumplen solas: necesita un controlador, un proxy real que escucha el puerto 80/443 y aplica esas reglas. En kind instalamos el oficial ingress-nginx. El navegador (o curl) llega al Ingress con un Host (el nombre harbor.test); el controlador lee el host y el path y decide el destino:

    curl http://localhost:8080/api/tasks   -H "Host: harbor.test"
                    │
                    ▼
         ┌─ ingress-nginx ────────────────────────────┐
         │  Host: harbor.test        pathType: Prefix │
         │   "/api"   ──▶ Service api:80 ──▶ Pods api │
         │   "/"      ──▶ Service web:80 ──▶ Pods web │
         └────────────────────────────────────────────┘
         nginx elige el path MÁS específico (/api gana sobre /).

Por qué probar con el header Host: el enrutado por host es parte de la regla. Con curl -H "Host: harbor.test" http://localhost:8080/ simulas exactamente lo que haría un navegador sin tocar /etc/hosts ni necesitar permisos de administrador. Para el navegador (en WSL/Windows) sí conviene añadir 127.0.0.1 harbor.test al archivo de hosts.

3 · Ejemplo mínimo

El "postgres mínimo" con persistencia son dos objetos: un PVC que pide el disco y un Deployment que lo monta. Con eso ya tienes una BD cuyo dato sobrevive a los reinicios:

# postgres-minimo.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pg-mini                      # Nombre del "contrato de alquiler"
  namespace: harbortasks
spec:
  accessModes:
    - ReadWriteOnce                  # Un solo nodo escribe (suficiente)
  storageClassName: standard         # StorageClass por defecto de kind (local-path)
  resources:
    requests:
      storage: 1Gi                   # Tamaño del disco solicitado
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pg-mini
  namespace: harbortasks
spec:
  replicas: 1                        # Una instancia de BD
  selector:
    matchLabels:
      app: pg-mini
  template:
    metadata:
      labels:
        app: pg-mini
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine   # Imagen oficial, variante ligera
          ports:
            - containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data   # RUTA INTERNA de datos
              subPath: pgdata         # Subcarpeta dentro del PVC
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: pg-mini       # Conecta el pod con el "alquiler"

Línea por línea (lo esencial): el subPath evita que el entrypoint de Postgres confunda su directorio con los archivos internos de la imagen (permite que el montaje quede "limpio"). El storageClassName: standard es quien dispara el provisionador local de kind; sin él, en algunos clústeres el PVC se queda Pending. Faltan las variables de entorno y las probes, pero la semilla de la persistencia ya está plantada.

4 · Ejemplo real

Ahora los manifiestos completos de Postgres y del Ingress de HarborTasks, tal como viven en proyectos/harbortasks/k8s/postgres/.

Postgres — Secret con la contraseña de la BD

k8s/secrets.yaml (compartido)
# secrets.yaml — el mismo Secret que consume el API (harbor-secrets)
apiVersion: v1
kind: Secret
metadata:
  name: harbor-secrets
  namespace: harbortasks
type: Opaque
data:
  # echo -n 'postgres://harbor:harborpass@postgres:5432/harbortasks' | base64
  database-url: cG9zdGdyZXM6Ly9oYXJib3I6aGFyYm9ycGFzc0Bwb3N0Z3Jlczo1NDMyL2hhcmJvcnRhc2tz
  # echo -n 'harborpass' | base64
  postgres-password: aGFyYm9ycGFzcw==
# El usuario (harbor) y la base (harbortasks) NO son secretos: van como variables
# literales en el Deployment. Solo la contraseña se guarda en el Secret.
# Coherencia crítica: el API conecta con `database-url` (harbor:harborpass) y el
# servidor arranca con la MISMA contraseña (`postgres-password`). Si no coinciden,
# el API recibe "authentication failed" sin error obvio en sus logs.

Postgres — PVC, inicialización y Deployment

k8s/postgres/pvc.yaml
# pvc.yaml — el disco persistente de las tareas
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: harbortasks
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard        # StorageClass local de kind (rancher.io/local-path)
  resources:
    requests:
      storage: 1Gi                  # Las tareas no pesan; 1Gi es generoso
k8s/postgres/configmap.yaml
# configmap.yaml — migraciones iniciales (se ejecutan SOLO al crear el datadir)
apiVersion: v1
kind: ConfigMap
metadata:
  name: postgres-init
  namespace: harbortasks
data:
  001-init.sql: |
    -- Migración inicial de HarborTasks (la "v1" de nuestro esquema)
    CREATE TABLE IF NOT EXISTS tasks (
      id         SERIAL PRIMARY KEY,            -- clave autoincremental
      title      TEXT NOT NULL,                 -- el texto de la tarea
      done       BOOLEAN NOT NULL DEFAULT FALSE,-- completada o pendiente
      created_at TIMESTAMPTZ NOT NULL DEFAULT now()  -- fecha de creación
    );

    -- Dos tareas de ejemplo para que la web y el API muestren algo
    INSERT INTO tasks (title) VALUES
      ('Desplegar HarborTasks en Kubernetes'),
      ('Completar el módulo 9');
# Todo es idempotente (IF NOT EXISTS) por si se vuelve a aplicar sin iniciar
# de cero. Los INSERT no son idempotentes: si se ejecutan dos veces duplicarían
# filas; por eso solo corren en el primer arranque del datadir.
k8s/postgres/deployment.yaml
# deployment.yaml — servidor PostgreSQL con persistencia real
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
  namespace: harbortasks
  labels:
    app: postgres
spec:
  replicas: 1                      # Una instancia: suficiente para HarborTasks
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      securityContext:
        fsGroup: 70                # GID del usuario "postgres" en la imagen alpine
        # Nota: NO ponemos runAsNonRoot como en la web/API. El entrypoint
        # oficial necesita arrancar como root para preparar PGDATA (chown) y
        # luego BAJA privilegios al usuario postgres (uid 70). Es la excepción
        # documentada; en producción se usa una imagen no-root o el operador.
      containers:
        - name: postgres
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_USER          # No es secreto: configuración literal
              value: harbor
            - name: POSTGRES_DB
              value: harbortasks
            - name: POSTGRES_PASSWORD      # Solo la contraseña viene del Secret
              valueFrom:
                secretKeyRef:
                  name: harbor-secrets
                  key: postgres-password
          volumeMounts:
            - name: pg-data
              mountPath: /var/lib/postgresql/data  # Datos persistentes
              subPath: pgdata              # Carpeta dedicada dentro del PVC
            - name: init-sql
              mountPath: /docker-entrypoint-initdb.d  # Migraciones iniciales
          readinessProbe:                  # "Acepto conexiones y la BD responde"
            exec:
              command: ["pg_isready", "-U", "harbor", "-d", "harbortasks"]
            initialDelaySeconds: 10        # initdb tarda unos segundos
            periodSeconds: 5
          livenessProbe:                   # "El servidor no está colgado"
            exec:
              command: ["pg_isready", "-U", "harbor"]
            initialDelaySeconds: 30
            periodSeconds: 10
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi
      volumes:
        - name: pg-data
          persistentVolumeClaim:
            claimName: postgres-data   # El disco del PVC
        - name: init-sql
          configMap:
            name: postgres-init       # Las migraciones en un ConfigMap
k8s/postgres/service.yaml
# service.yaml — nombre DNS estable para la BD (SOLO interno)
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: harbortasks
spec:
  selector:
    app: postgres
  ports:
    - port: 5432
      targetPort: 5432
# No se expone al exterior: lo consume únicamente el API vía "postgres:5432".

El Ingress — la puerta de entrada del clúster

k8s/ingress.yaml
# ingress.yaml — enrutado por host y path hacia api y web
apiVersion: networking.k8s.io/v1   # API estable de Ingress
kind: Ingress
metadata:
  name: harbortasks
  namespace: harbortasks
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "8m"   # Peticiones grandes OK
spec:
  ingressClassName: nginx          # Usa el controlador ingress-nginx
  rules:
    - host: harbor.test            # Nombre virtual (Host header)
      http:
        paths:
          - path: /api             # Tráfico de API
            pathType: Prefix       # /api, /api/tasks, /api/tasks/1...
            backend:
              service:
                name: api
                port:
                  number: 80       # Service api:80 → pods :3000
          - path: /                # Resto: la web
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80       # Service web:80 → pods :80
# El controlador nginx aplica la regla MÁS específica: /api gana sobre /,
# así que /api/tasks SIEMPRE va al API aunque / también coincida.

Instalación y prueba end-to-end

# 0. Instalar el controlador ingress-nginx (el manifiesto kind oficial)
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.12.0/deploy/static/provider/kind/deploy.yaml

# 1. Postgres: secret → pvc → init → deployment → service (ese orden lógico)
kubectl apply -f k8s/postgres/secret.yaml
kubectl apply -f k8s/postgres/pvc.yaml
kubectl apply -f k8s/postgres/configmap.yaml
kubectl apply -f k8s/postgres/deployment.yaml
kubectl apply -f k8s/postgres/service.yaml

# 2. El descriptor del controlador
kubectl wait --namespace ingress-nginx \
  --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=120s

# 3. El Ingress de HarborTasks
kubectl apply -f k8s/ingress.yaml

# 4. Canal de prueba hacia el controlador (sin tocar /etc/hosts)
kubectl port-forward -n ingress-nginx svc/ingress-nginx-controller 8080:80 &

# 5. Primera prueba de extremo a extremo
curl -i http://localhost:8080/api/tasks -H "Host: harbor.test"   # → 200 + JSON
curl -i http://localhost:8080/            -H "Host: harbor.test"   # → 200 + HTML

Momento clave: al arrancar Postgres, sus pods de API (creados en la lección 2) pasan de 0/2 Ready a 2/2 Ready sin que hagas nada. Las readiness probes dejan de fallar y el Service api empieza a mandarles tráfico. Es la demostración más bonita del modelo declarativo: declaras el estado deseado de cada pieza y Kubernetes encaja el puzzle.

6 · Errores habituales

PVC atascado en Pending

# Reflexiona: kubectl get pvc → STATUS Pending sin avanzar
kubectl get pvc -n harbortasks
# NAME            STATUS   VOLUME  CAPACITY  ACCESS MODES STORAGECLASS AGE
# postgres-data   Pending                     3m
# Observa STORAGECLASS <none>: ¡no hay ninguna StorageClass!

# ❌ Por qué: aplicar los manifests ANTES de que exista la StorageClass,
#    o escribir storageClassName mal (p. ej. "local" en vez de "standard").
# ✅ Solución: confirma el nombre real de la StorageClass de kind y reaplica
kubectl get storageclass                      # kind suele llamarse "standard"
kubectl apply -f k8s/postgres/pvc.yaml        # el reclamo "enlaza" el disco

El API no puede autenticarse (pero parece todo "verde")

# Síntomas: pods api Ready, pero GET /api/tasks → 500 "password authentication failed"
kubectl logs -n harbortasks deployment/api --tail=20 | grep -i password

# ❌ Postgres creó el usuario con una contraseña y el API usa otra
# ✅ Las dos piezas deben ser coherentes (esto es configuración, no magia):
kubectl get secret harbor-secrets -n harbortasks -o jsonpath="{.data.postgres-password}" | base64 -d
# Compara ambas salidas: tienen que ser idénticas.

Los scripts de init "no corren" la segunda vez

# Creas una migración nueva en postgres-init, haces rollout restart... y nada cambia.

# ❌ Por qué: /docker-entrypoint-initdb.d SOLO se ejecuta la primera vez que se
#    crea el datadir. Un PVC que ya tiene data inicializada NO vuelve a correrlos.
# ✅ Vías correctas:
#   1) Cambiar el esquema con una migración "normal" (aplicada por la app),
#   2) borrar el PVC conscientemente para "recrear de cero",
#   3) usar un initContainer que aplique SQL vía psql (migraciones versionadas).

kubectl delete pvc postgres-data -n harbortasks   # ⚠️ SOLO en desarrollo: borra TODO el dato
kubectl delete pod -n harbortasks -l app=postgres # el Deployment lo recrea e inicia de nuevo

Ingress 404: el controlador no está escuchando

curl -i http://localhost:8080/ -H "Host: harbor.test"   # → 404 not found

# ❌ Aplicaste el Ingress pero NO instalaste ingress-nginx (la regla no se cumple sola)
kubectl get pods -n ingress-nginx        # ¿Existe el namespace siquiera?

# ✅ Instala el manifiesto kind oficial y espera al controlador
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.12.0/deploy/static/provider/kind/deploy.yaml
kubectl wait -n ingress-nginx --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=120s

    # 1) La web responde HTML

# 2) El API devuelve las tareas de la BD (los datos atraviesan TODO el stack)
curl -i http://localhost:8080/api/tasks -H "Host: harbor.test"

# 3) Creamos una tarea nueva por el Ingress
curl -X POST http://localhost:8080/api/tasks \

8 · Reto

🎯 Añade TLS a harbor.test

Genera un certificado autofirmado para harbor.test, súbelo como Secret de tipo kubernetes.io/tls y completa el Ingress con una sección tls y port: 443. Prueba luego con curl -k (que ignora la firma) y con -v para ver el handshake.

Pista: usa openssl req -x509 -newkey rsa:2048 -nodes -days 365 -subj "/CN=harbor.test" -keyout tls.key -out tls.crt y luego kubectl create secret tls harbor-tls --cert=tls.crt --key=tls.key. El controlador ingress-nginx redirige HTTP→HTTPS por defecto cuando existe la sección tls. En producción real este Secret lo gestionaría cert-manager con Let's Encrypt.

9 · Resumen

  • Persistencia = PVC (contrato) + StorageClass (tipo de disco) + subPath montado en el pod. El dato sobrevive a reinicios de pod.
  • Deployment + PVC es correcto para una instancia única; StatefulSet es el escalón hacia réplicas con identidad.
  • Las migraciones iniciales viven en /docker-entrypoint-initdb.d y corren una sola vez: por eso se escriben idempotentes.
  • Las credenciales de Postgres deben coincidir con las que consume el API (harbor-secrets).
  • El Ingress declara reglas; el controlador (ingress-nginx) las ejecuta; nginx elige el path más específico.
  • Al crear Postgres, los pods del API pasan a Ready solos: el modelo declarativo "encaja" las piezas.
  • Probar con -H "Host: harbor.test" + port-forward evita tocar /etc/hosts.

10 · Preguntas frecuentes

¿Puedo usar un StatefulSet para Postgres en este proyecto?

Puedes, y es el siguiente paso natural. Un StatefulSet te da nombre estable (postgres-0), un PVC por réplica y arranque ordenado. Para una sola instancia, el Deployment con PVC que usa el proyecto es más simple y suficiente. Migrar a StatefulSet es un delta futuro: cambio de kind, volumeClaimTemplates en lugar del PVC separado, y un Service headless.

¿Por qué tengo que recordar dónde se monta el datadir de Postgres?

Porque es una ruta interna de la imagen: /var/lib/postgresql/data en las versiones modernas (antes era /var/lib/postgresql/data con otra subestructura según la variante). La imagen oficial documenta exactamente esa ruta; montar el PVC ahí es lo que hace que el "disco" y el proceso se hablen. Listo para que no lo memorices como un dogma: docker run --rm postgres:16-alpine con un docker inspect te muestra los VOLUME declarados.

Me da miedo borrar el PVC: ¿pierdo las tareas?

Sí. Borrar el PVC borra el dato persistente (en kind, la carpeta local-path). Debes hacerlo solo cuando sea tu intención: "reset del proyecto". Es justo el momento de aprender a hacer backups: con pg_dump exportas el esquema y los datos a un archivo antes de destruir nada. En la próxima lección verás el backup como parte del checklist de producción, y el reto de la lección 8 te lo hará tunear.

¿Por qué en el Ingress las reglas de /api y / no chocan?

Porque el controlador nginx usa coincidencia por prefijo más específico: /api/tasks empieza con /api y con /, pero /api es más largo y gana. Es la misma lógica de rutas en Express o Rails. Por eso el orden de las reglas no importa en nginx (a diferencia de otros controladores), y por eso también se documenta como buena práctica declarar los paths específicos.

¿El controlador ingress-nginx es lo mismo que un LoadBalancer?

No, se complementan. En kind el controlador se expone con un Service tipo NodePort: ese es el punto de entrada físico (puerto 80/443 del nodo). El Ingress añade enrutado inteligente por host y path por encima. En la nube, el Service del controlador suele ser LoadBalancer (el proveedor crea el LB real) o sea: LoadBalancer te "trae al clúster"; Ingress te dice "a qué servicio dentro".
