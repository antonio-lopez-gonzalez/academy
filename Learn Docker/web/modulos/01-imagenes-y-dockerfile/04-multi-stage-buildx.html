Multi-stage, .dockerignore y Buildx

Módulo 1 · Imágenes y Dockerfile ⏱ 35 minutos

1 · Introducción

En la lección 02 viste el Dockerfile «de una etapa»: una sola imagen que lo contiene todo. Funciona, pero cuando tu aplicación compila (TypeScript, Tailwind, un bundler, binarios), el proceso de build deja dentro de la imagen máquinas de construcción completas: compiladores, dependencias de desarrollo, código fuente, caches… y eso engorda tu imagen de producción y amplía su superficie de ataque.

En esta lección aprenderás las tres herramientas que transforman ese problema: los builds multi-stage (compilar en una etapa, producir la imagen final mínima en otra), el .dockerignore (no enviar basura al builder) y Docker Buildx (el builder moderno, con BuildKit, cache en remoto, --target y multi-plataforma).

¿Por qué existen estas tres cosas? Porque «tamaño pequeño» y «misma receta» son objetivos en tensión: quieres una imagen con solo lo que corre en runtime, pero necesitas herramientas pesadas para construirla. Multi-stage separa el «taller» (build) de la «tienda» (runtime); .dockerignore no mete la basura del contexto; Buildx hace todo eso rápido, paralelo, con caché y para varias arquitecturas.

2 · Teoría

El problema: la imagen engorda con la herramienta

Un Dockerfile clásico para una app Node con TypeScript haría algo parecido a: FROM node:20-alpine → npm ci (con dependencias de dev) → npm run build (compila TS a dist/) → CMD node dist/server.js. El resultado contiene el compilador de TypeScript, Babel, eslint, sourcemaps… y el código fuente, aunque en producción solo necesita Node y el dist/ ya compilado. En proyectos grandes eso son cientos de MB y «juguetes» dentro de la imagen que nadie pidió (y que un atacante sí sabría usar).

Multi-stage: varias etapas FROM, una imagen final

Un Dockerfile puede tener varias instrucciones FROM. Cada una abre una etapa (stage) con su propio sistema de archivos. Puedes nombrarlas (FROM node:20-alpine AS build) y, al final, de esa etapa solo viajan a la imagen final los artefactos que explícitamente copies con COPY --from=build ....

ETAPA 1 "build" (taller) ETAPA 2 "runtime" (tienda) = IMAGEN FINAL --------------------------- --------------------------------------- FROM node:20-alpine AS build FROM node:20-alpine WORKDIR /app WORKDIR /app COPY package*.json ./ ENV NODE_ENV=production RUN npm ci <- dev+prod COPY package*.json ./ COPY src ./src RUN npm ci --omit=dev RUN npm run build <- compila COPY --from=build /app/dist ./dist EXPOSE 3000 ^ CMD ["node", "dist/server.js"] | COPY --from=build /app/dist ./dist (solo el dist compilado) | ────────── Los nodos de "build" NO van a la imagen final ──────

Analogía — el taller y la tienda: la etapa build es el taller donde fabrican el mueble (sierra, barniz, serrín); la etapa runtime es la tienda que muestra el mueble terminado. A la tienda no subes la sierra ni el serrín: solo el mueble. Multi-stage hace exactamente eso con tu aplicación.

  • Beneficio 1 — Tamaño: la imagen final solo contiene lo que corre en runtime.
  • Beneficio 2 — Seguridad: sin compiladores, sin credenciales de build ni caches de dependencias en producción.
  • Beneficio 3 — Velocidad: con BuildKit, las etapas se ejecutan en paralelo cuando no dependen entre sí.

.dockerignore: qué NO enviar al builder

Recuerda la lección 02: el contexto se empaqueta completo y viaja al builder. Un .gitignore no sirve aquí — el builder no conoce tu Git—. La herramienta es .dockerignore, en la raíz del contexto, con sintaxis de patrones (parecida a los globs). Excluye:

  • node_modules/ — tu caché de dependencias local, enormemente inútil en el builder.
  • .git/ — historia completa del repo.
  • dist/, coverage/, lo que regeneraras — se regenera dentro del build.
  • Archivos locales: .env (¡secretos!), *.log, .DS_Store…

Ojo: .dockerignore no protege secretos que ya hayas metido en una capa con COPY o RUN: solo evita que viajen en el contexto. Los secretos de build se inyectan de forma segura con --secret de BuildKit (fuera del alcance de esta lección).

Docker Buildx y BuildKit

Desde hace años, el builder por defecto de Docker es BuildKit, un motor de build moderno y reescrito. La forma cómoda de usarlo es Buildx: un plugin de la CLI (docker buildx) que además permite builders remotos y multi-plataforma (dar a la misma receta imágenes para linux/amd64 y linux/arm64 con --platform). Gracias a BuildKit, además tienes:

  • Construcciones paralelas entre etapas independientes.
  • Caché efectiva (local y remota, por capa y por digest).
  • Montajes efímeros de caché (--mount=type=cache) para npm/pnpm.
  • --target: construir solo una etapa concreta. Lección 4.
  • Imágenes multi-arquitectura con un solo --platform (lección 05).
# Estado del builder (por defecto hay uno: "default", vía BuildKit)
docker buildx ls
# NAME/NODE    DRIVER/ENDPOINT     STATUS   BUILDKIT/PLATFORMS
# default *    docker             running  v0.xx  linux/amd64, linux/arm64...
#
# Cuando usas el builder por defecto, "docker build" y "docker buildx
# build" son equivalentes. En esta lección usamos ese builder; el
# multi-plataforma con un builder "docker-container" lo verás en la
# lección 05.

3 · Ejemplo mínimo

El multi-stage mínimo útil: una «app web» generada con Node que se sirve con nginx. En el proceso compilamos a dist/ en una etapa y servimos solo el resultado. El proyecto tiene solo .dockerignore, Dockerfile, package.json (con un script build) y src/.

.dockerignore
# Lo que JAMÁS debe viajar al builder (contexto pequeño y limpio)
node_modules/        # caché de dependencias local: inútil e inmensa
.git/                # historia del repositorio
dist/                # se genera dentro del build
*.log                # directorios de log locales
.env                 # secretos y configuración local
Dockerfile (multi-stage mínimo)
# ===== Etapa 1: BUILD =====
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json ./
RUN npm run build            # genera dist/index.html (script local)

# ===== Etapa 2: RUNTIME (la imagen final) =====
FROM nginx:1.27-alpine
# SOLO copiamos el artefacto compilado de la etapa build
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
        
cd proyecto
docker build -t mini-ms:1.0 .
# Con BuildKit verás algo así por cada etapa:
#  #1 [build 1/2] FROM node:20-alpine
#  #5 [runtime 1/2] FROM nginx:1.27-alpine
#  #8 [build 2/2] RUN npm run build
#  #9 [runtime 2/2] COPY --from=build /app/dist ...
#  DONE ...    ← la imagen final es SOLO la etapa "runtime"

docker run -d --rm -p 8080:80 mini-ms:1.0
curl http://localhost:8080            # --> la página generada en la etapa build

Ver el viaje completo: docker history mini-ms:1.0 te muestra que la imagen final procede entera de la etapa runtime. El tamaño «desaparecido» (compilador, src, devdeps) nunca entró en la imagen: esa es la magia del multi-stage.

4 · Ejemplo real

El Dockerfile de producción de la API de HarborTasks, refactorizado a dos etapas, con --target y comparación de tamaños. Aquí la compilación es de empaquetado: la etapa build instala todas las dependencias (dev incluidas) para poder npm run build si hiciera falta, y la etapa runtime instala solo las de producción y copia el código.

proyectos/harbortasks/docker/api.Dockerfile (multi-stage)
# ============ HarborTasks API — Dockerfile multi-stage ============

# ---- Etapa 1: integración de dependencias + posible build ----
FROM node:20-alpine AS build

WORKDIR /app

# Manifiestos primero para explotar la caché (lección 02)
COPY package.json package-lock.json ./

# En la etapa de construcción instalamos TODO (dev + prod): aquí es donde
# haríamos `npm run build` (compilar TS, bundlers, etc.)
RUN npm ci

COPY src ./src

# ---- Etapa 2: RUNTIME — esta es la imagen final ----
FROM node:20-alpine AS runtime

WORKDIR /app
ENV NODE_ENV=production

# Copiamos los manifiestos desde la etapa build (caché de la lección 02)
COPY --from=build /app/package.json /app/package-lock.json ./

# …y aquí SOLO dependencias de producción, en la imagen final.
RUN npm ci --omit=dev

COPY --from=build /app/src ./src

EXPOSE 3000
CMD ["node", "src/server.js"]
proyectos/harbortasks/.dockerignore
# Entorno de trabajo Docker/K8s: no enviar al builder nada de esto
node_modules/
.git/
.env
*.log
Dockerfile*
.dockerignore
dist/            # se regenera dentro de la etapa build (si algún día compilas)

Construye y mira la víscera:

# Construir la imagen final (por defecto, la última etapa)
docker build -f docker/api.Dockerfile -t harbortasks-api:1.0 .

# ¿Y si quieres ver solo la etapa de build? --target
docker build -f docker/api.Dockerfile --target build -t harbortasks-api:build .

# Compara tamaños: la de build incluye devdeps; la final (runtime) no.
docker images | grep harbortasks-api
# harbortasks-api   build    ...   ~350 MB   (npm ci CON dev
# harbortasks-api   1.0      ...   ~120 MB   (solo --omit=dev)

# Verificación funcional
docker run -d -p 3000:3000 --name api harbortasks-api:1.0
curl http://localhost:3000/api/tasks
docker history harbortasks-api:1.0      # la imagen final conserva solo
                                        # capas de "runtime" + COPYs

Por qué los dos npm ci (no «uno con --omit=dev solo»): la etapa build necesita devdeps para compilar y ejecutar scripts de build. La etapa runtime, al ser la imagen final, quiere la instalación mínima. Multi-stage te permite tener ambas realidades en un solo Dockerfile sin sacrificar la caché: una imagen de build «gorda» para desarrollar y una imagen de producción raquítica, con el mismo código fuente como única fuente de verdad.

5 · Buenas prácticas

HazEvitaPor qué
Nombra SIEMPRE las etapas (AS build, AS runtime) Referencias numéricas COPY --from=0 Si insertas una etapa nueva, los índices se rompen silenciosamente; los nombres hacen el Dockerfile autodocumentado.
Crea siempre .dockerignore, incluso en proyectos pequeños Solo .gitignore y el contexto «igualito» El builder ve tu carpeta completa; node_modules de 300 MB con cada build ralentiza todo y puede acabar dentro de la imagen.
La imagen final: runtime solo con lo que corre (prod deps, sin compiladores) Terminar el Dockerfile en la etapa de build Tamaño, superficie de ataque y coste de escaneo: la imagen de producción debe ser un artefacto mínimo y auditable.
Usa --target para construir etapas de desarrollo/prueba Duplicar Dockerfiles (uno dev, uno prod) Un único Dockerfile con varias etapas sirve para CI, para debug y para producción sin mantener recetas repetidas.
Aprovecha el caché de BuildKit (--mount=type=cache,target=/root/.npm) en npm/pnpm de proyectos grandes Limpiar los caches dentro de la etapa build con rm -rf en el mismo RUN El mount de caché persiste entre builds SIN engordar la imagen; el rm -rf dentro del RUN engorda una capa intermedia y ensucia el diff.

6 · Errores habituales

Olvidar .dockerignore (o borrar con la escopeta)

# ❌ Sin .dockerignore: cada build envía node_modules, .git y todo logs
# (mira el tamaño del contexto en la primera línea del build:
#  "context" tarda, sube MB, y con COPY . . acaba DENTRO de la imagen)

# ✅ Mínimo viable que ya soluciona el 90% del problema
node_modules/
.git/
.env
*.log

Pensar que un multi-stage «copia todo»

# ❌ Confundir etapas: esto NO sirve nada en runtime
FROM node:20-alpine AS build
WORKDIR /app
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
# ¡nada de COPY --from=build! La imagen final es nginx VACÍO
# (sin tu web). Compila bien, funciona mal.

# ✅ Incluir el paso del taller a la tienda
FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html

Copiar el runtime sin source de producción

# ❌ Instalar dependencias de producción DESPUÉS de copiar todo
FROM node:20-alpine AS runtime
WORKDIR /app
COPY --from=build /app /app     # trae TODA la etapa build (dev+prod)
RUN npm ci --omit=dev           # ya es demasiado tarde: la basura está dentro
CMD ["node", "src/server.js"]

# ✅ Orden correcto en runtime: manifiesto, deps prod, y SOLO el artefacto
FROM node:20-alpine AS runtime
WORKDIR /app
COPY --from=build /app/package.json /app/package-lock.json ./
RUN npm ci --omit=dev
COPY --from=build /app/src ./src
CMD ["node", "src/server.js"]

Sorpresa: --target construye la etapa y NO la final

# ❌ "¿Por qué mi imagen del --target build no tiene mi CMD?"
# Porque --target build ES la etapa de build: sin EXPOSE ni CMD finales.
# Es un artefacto de desarrollo/CI, no la imagen de producción.

# ✅ Uso correcto: usa --target para DEPURAR la etapa de construcción
docker build --target build -t api:build .
docker run --rm -it api:build sh      # -> miras qué se compiló ahí

8 · Reto

🎯 Acelera el rebuild con el caché de BuildKit

En el ejercicio has notado que npm ci de la etapa runtime se repite íntegro en cada build. Tu reto: reducir el tiempo de rebuild a «segundos» cuando no cambian las dependencias usando el cache mount de BuildKit:

# PISTA — la sintaxis exacta es un comentario "especial" de BuildKit:
# RUN --mount=type=cache,target=/root/.npm,npm ci --omit=dev
#   ^  el target apunta al directorio de la caché DE npm DENTRO del
#   contenedor (para Node: /root/.npm). El directorio persiste entre
#   builds fuera de las capas de la imagen.

Tareas: aplica el mount a ambas etapas, cronometra un build limpio (docker build --no-cache -t api:prod .) y el siguiente build modificando solo src/server.js: la descarga de npm debe saltársela. No resuelvas la «solución» aquí: experimenta, y si algo no cuadra, revisa que el builder sea BuildKit (debe parecer #1 ... con FROM inline, no el formato antiguo `Step 1/N`).

9 · Resumen

  • Multi-stage: varias FROM en un Dockerfile; se nombran (AS build) y se copia lo necesario con COPY --from=etapa. Solo la última etapa se convierte en imagen final.
  • Por qué: tamaño mínimo, sin toolchains ni código fuente en producción, y builds paralelas con BuildKit.
  • .dockerignore: filtra el contexto: node_modules/, .git/, *.log, .env…
  • Buildx/BuildKit: builder moderno, paralelo, con caché (local y remota) y multi-plataforma; docker build es un alias de docker buildx build en el builder por defecto.
  • --target: construye solo una etapa (útil para dev/CI/debug).
ComandoQué hace
docker build -t <nombre> .Build estándar (BuildKit/Buildx por defecto), última etapa = imagen.
docker build --target <etapa> -t ... .Construye SOLO la etapa indicada.
COPY --from=<etapa> /org /destCopia artefactos de una etapa a otra (el puente del multi-stage).
docker buildx lsLista builders y plataformas disponibles.
docker buildx build --platform=...Build multi-plataforma (lo usamos en la lección 05).
docker history <imagen>Muestra las capas REALES de la imagen final: confirma el multi-stage.

10 · Preguntas frecuentes

¿Multi-stage hace que el build sea más lento?

Al contrario: con BuildKit las etapas independientes se ejecutan en paralelo, y su caché por etapas (no por «pasos») hace que los rebuilds descarten solo lo que cambió. El escenario donde «parece» más lento es el primer build con muchos npm ci; compensas con diferencia en la imagen final y en los siguientes builds.

¿Qué diferencia hay entre BuildKit y Buildx?

BuildKit es el motor (el «daemon» de build, moderno, con caché y paralelismo); Buildx es el plugin de la CLI que lo expone y que además gestiona builders multi-plataforma (incluidos los remotos tipo docker-container, que verás en la lección 05). En la práctica escribes docker build y tu Docker ya usa BuildKit+Buildx por defecto.

Si mi app NO compila, ¿necesito multi-stage?

A veces sí, y por otros motivos: separar deps de dev y de prod (como hicimos con la API) es ya un caso de multi-stage sin «compilar» nada. Si tu app es JS puro sin build y sin devdeps, un solo FROM node:20-alpine te basta; guarda el multi-stage para cuando «construir» deje residuos o necesites dos lentes (build y runtime) a la vez.

¿Por qué no me llegan las variables de entorno del build a la imagen?

Porque las etapas son entornos aislados: un ENV en la etapa build no existe en la runtime. Si necesitas un valor de build en runtime, decláralo en la etapa final (o páselo como argumento de build con ARG + --build-arg); lo que COPY --from no transporta son variables de entorno. La separación por etapas es deliberada, y confundirla es un clásico del multi-stage.

¿El .dockerignore afecta al .dockerignore del contexto git?

Son dos archivos y dos mundos: .gitignore lo usa Git para no versionar; .dockerignore lo usa Docker para no empaquetar el contexto. Puede darse que quieras ignorar algo en Docker pero versionarlo en Git (p. ej. un Dockerfile* de build local), o al revés. Aplica .gitattributes con LF (lección 02) a ambos para que Git no te «arregle» saltos de línea en tu .dockerignore ni en scripts.
