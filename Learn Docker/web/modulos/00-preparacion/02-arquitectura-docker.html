Arquitectura Docker: daemon, imagen y registry

Módulo 0 · Preparación ⏱ 30 minutos

1 · Introducción

Cuando escribes docker run, quien más trabaja no es lo que escribes, sino un programa que ni ves: el daemon. Entender quién hace qué dentro de Docker no es curiosidad: te explica por qué a veces el cliente responde y el daemon no, por qué Docker necesita un contenedor extra para construcciones, y qué significa exactamente «conectar tu CLI a un contexto remoto».

En esta lección desmontarás la arquitectura en piezas: cliente (CLI), daemon, containerd y shims; y entenderás los tres objetos que usarás a diario: imagen, contenedor y registry.

¿Por qué existe esta lección? Porque Docker no es un programa monolítico; es una arquitectura cliente-servidor. Cuando un comando falla, saber qué proceso falla (la CLI, el daemon, containerd o el registry) convierte un misterio en un diagnóstico de 30 segundos.

2 · Teoría

Cliente-servidor: la CLI habla con el daemon

+----------------+      HTTP/Unix socket      +------------------------------+
|  TU TERMINAL   |  docker run -p 8080:80     |         DOCKER DAEMON         |
|  docker build  |--------------------------> |  (dockerd) gestiona todo      |
|  docker pull   |  REST API sobre el socket   |  contenedores, imagenes, red  |
+----------------+                             +--------------+---------------+
                                                              |
                                                              v
                                              +------------------------------+
                                              |   containerd (runtime)        |
                                              |   +-------------------------+ |
                                              |   | shim -> runc -> proceso  | |
                                              |   +-------------------------+ |
                                              +------------------------------+
  • Cliente (docker): es el binario que escribes en la terminal. No crea contenedores: convierte tus comandos en llamadas a una API REST y se las envía al daemon.
  • Daemon (dockerd): el cerebro. Escucha en un socket (por defecto /var/run/docker.sock en Linux), recibe las peticiones y orquesta el resto. Cuando leas «cannot connect to the Docker daemon», es que este proceso no está corriendo.
  • containerd: runtime de nivel intermedio que de verdad crea los contenedores: gestiona imágenes y ciclos de vida. Docker lo usa internamente (y también lo usa Kubernetes puro, sin Docker).
  • runc + shim: runc materializa el proceso del contenedor (aplica namespaces y cgroups, que vimos en la lección 1). El shim mantiene vivo el proceso aunque el daemon se reinicie.

Detalle: la «API REST de Docker» no es una idea abstracta: es un protocolo real (Documentación de Docker Engine API) que podrías usar con curl sobre el socket. Cuando trabajes con Kubernetes verás la misma idea de «API de control», pero mucho más grande.

Imagen: la plantilla inmutable

Una imagen es un paquete estático, inmutable y autosuficiente: sistema base + código + runtime + dependencias + metadatos. Piensa en una receta de cocina escrita en un libro: no se come, pero describe exactamente cómo hacer el plato.

  • Se construye con docker build a partir de un Dockerfile (módulo 1).
  • Es inmutable: no la «editas», produces una nueva versión con otro tag.
  • Está formada por capas (cada instrucción del Dockerfile añade una capa). Eso permite reutilizar y descargar solo lo que cambia.

Contenedor: la instancia efímera

Un contenedor es una instancia en ejecución a partir de una imagen (el plato ya cocinado). De una misma imagen puedes tener muchos contenedores, cada uno con su propia capa de escritura, su red y su estado. La capa de escritura es temporal: se va cuando el contenedor se borra (por eso los datos importantes van a volúmenes, módulo 3).

Registry: el almacén de imágenes

Un registry es un servidor que guarda y distribuye imágenes. Docker Hub es el público por defecto. Los registries no solo almacenan: controlan acceso, firmas de contenido, escaneo de vulnerabilidades y cuotas. En el curso publicarás también en GHCR (GitHub Container Registry).

PiezaQué esAnalogía
RegistryRepositorio de imágenesLa biblioteca donde viven los libros de recetas
ImagenPlantilla inmutableLa receta escrita
ContenedorProceso en ejecuciónEl plato servido en tu mesa

Docker context: conectar la CLI a cualquier daemon

Como el cliente y el daemon se comunican por HTTP, nada les obliga a vivir en la misma máquina. Un context define a qué daemon habla tu CLI. Por defecto hay uno local (default), pero puedes añadir contextos remotos (un servidor de la oficina, un entorno de pruebas) y cambiar entre ellos al instante. Es la puerta de entrada a la gestión remota de Docker.

La pila completa sobre tu sistema operativo

Linux: el daemon corre como servicio de sistema (systemctl status docker) y el socket vive en /var/run/docker.sock. Acceso por grupo docker.

macOS: Docker Desktop ejecuta la pila dentro de una VM Linux; tú solo ves la CLI y una app de menú. El socket está «dentro de la VM», así que no hay grupo docker que configurar.

Windows: igual que macOS, pero la VM es WSL2. Se nota en que el daemon se ve desde la distro WSL si activas la integración (lección 04).

3 · Ejemplo mínimo

Un solo comando para ver la arquitectura cliente/daemon con tus propios ojos:

# docker version muestra DOS partes:
#   Client: la versión de la CLI que estás escribiendo
#   Server: la versión del DAEMON con el que se conecta (dockerd)
# Si la parte Server falla, el daemon no está corriendo o el contexto apunta mal.
docker version

Salida esquemática (las versiones exactas dependerán de tu instalación):

Client: Docker Engine - Community
 Version:           28.0.1        <- tu CLI
...
Server: Docker Engine - Community
 Engine:
  Version:          28.0.1        <- el daemon: SI existe, conexión OK
 containerd:
  Version:          v2.0.4        <- el runtime intermedio
 runc:
  Version:          1.2.6         <- quien materializa los procesos

Esta separación es la prueba viva de la arquitectura cliente-servidor: el cliente y el servidor pueden tener versiones distintas e incluso vivir en equipos distintos.

4 · Ejemplo real

HarborTasks necesita tres imágenes: nginx:1.27-alpine, una imagen de Node construida por ti y postgres:16-alpine. Cuando ejecutas el flujo completo, cada paso mueve la pieza correspondiente:

[ Docker Hub: registry ]
      |  docker pull postgres:16-alpine
      v
[ Daemon (dockerd): guarda imagen, gestiona el ciclo de vida ]
      |  containerd -> shim -> runc
      v
[ Contenedor postgres: proceso aislado que guarda las tareas ]
        
# 1) Descarga: la CLI avisa al daemon para que baje la imagen al registry
docker pull postgres:16-alpine

# 2) Ejecuta: el daemon crea el contenedor vía containerd/runc
#    -e POSTGRES_PASSWORD=... es la contraseña del superusuario postgres
#    -v es un volumen: los datos sobreviven aunque borres el contenedor (módulo 3)
docker run -d --name harbor-db -e POSTGRES_PASSWORD=harborpass -v pgdata:/var/lib/postgresql/data postgres:16-alpine

# 3) Inspecciona: docker inspect devuelve el detalle técnico que el daemon guarda
docker inspect harbor-db | head -n 40

Fíjate en la decisión de diseño: docker run es solo la fachada. Por debajo, la CLI no «levanta postgres»: se lo pide al daemon, y el daemon le entrega el trabajo a containerd. Cuando quieras ver imágenes o contenedores como objetos, recuerda: docker images habla de la biblioteca local y docker ps de las ejecuciones en curso.

6 · Errores habituales

Confundir la imagen con el contenedor (otra vez, pero con las piezas de esta lección)

# ❌ Borrar solo contenedores no libera espacio: las imágenes siguen ocupando
docker ps -a          # lista solo contenedores
docker rmi nginx:1.27-alpine   # esto borra la IMAGEN (plantilla), no el contenedor

# ✅ Flujo correcto: parar/borrar contenedor y, solo entonces, la imagen
docker rm -f harbor-web   # borra el contenedor (con -f fuerza aunque esté corriendo)
docker rmi nginx:1.27-alpine   # ahora sí, borra la imagen local

Pensar que la CLI hace el trabajo por sí sola

# ❌ Instalar solo el cliente (Docker CLI) en un servidor y esperar que funcione
# docker run hello-world
# -> Cannot connect to the Docker daemon...

# ✅ Necesitas el daemon (dockerd) o usar Docker Desktop/Engine completo
# En Ubuntu el paquete correcto es:
#   sudo apt install docker.io   (o docker-ce desde el repo oficial)

Montar mal la cadena de permisos del socket

# ❌ Ejecutar todo con sudo "porque el daemon requiere root"
# Cada sudo crea permisos para root y no para tu usuario

# ✅ Añade tu usuario al grupo docker UNA vez y vuelve a iniciar sesión
#   sudo usermod -aG docker $USER
#   newgrp docker      # o cierra y abre sesión
# Después corres docker sin sudo. (Solo Linux; en macOS/Windows no hace falta)

Olvidar que el registry puede estar caído o las credenciales caducadas

# ❌ Suponer que un pull fallido es un problema de imagen
docker pull miempresa/app:1.0

# ✅ Diagnostica: ¿está caído Docker Hub? ¿caducó el token?
#   docker login    -> comprueba credenciales antes
#   docker logout   -> si quieres probar como anónimo

7 · Ejercicio guiado

Objetivo: observar las piezas de la arquitectura y recorrer el flujo imagen → registry → contenedor.

  1. Paso 1: comprueba que cliente y daemon se ven: 
    docker version        # mira las secciones Client y Server
  2. Paso 2: descarga la imagen real de nginx y confírmala: 
    docker pull nginx:1.27-alpine   # baja la plantilla a tu biblioteca local
docker images                    # la verás listada con  de repositorio
  3. Paso 3: crea un contenedor desde esa imagen: 
    docker run -d --name arquidemo -p 8088:80 nginx:1.27-alpine
docker ps                   # estado Up; el contenedor existe como objeto vivo
  4. Paso 4: explora los metadatos que guarda el daemon: 
    docker inspect arquidemo     # salida JSON enorme: config, red, mounts...
docker inspect --format '{{.Config.Image}}' arquidemo   # muestra la imagen base
  5. Paso 5: comprueba el contexto activo y la pila interna: 
    docker context ls            # verás 'default' marcado con *
docker info --format '{{.ServerVersion}}'  # versión del daemon conectado
  6. Verificación final: abre http://localhost:8088. Si ves la página de nginx, todo el recorrido CLI → daemon → containerd/runc → contenedor funcionó. No olvides limpiar: docker rm -f arquidemo.

8 · Reto

🎯 Dos contenedores, una misma imagen

Lanza dos contenedores de nginx desde la MISMA imagen nginx:1.27-alpine en dos puertos distintos (-p 8089:80 y -p 8090:80). Abre ambos en el navegador. Después borra primero un contenedor con docker rm -f y comprueba en docker images que la imagen sigue ahí. Borra también la imagen y verifica que ya no se puede crear otro contenedor. Escribe las tres conclusiones.

Pista: una imagen es plantilla inmutable; de una plantilla pueden salir N ejecuciones. El orden de borrado importa: si borras la imagen sin borrar el contenedor, Docker te lo impedirá porque hay referencias.

9 · Resumen

  • Docker es una arquitectura cliente-servidor: la CLI envía peticiones REST al daemon (dockerd).
  • El daemon delega la ejecución en containerd, runc y los shims.
  • Imagen = plantilla inmutable (receta); contenedor = instancia en ejecución (plato servido); registry = almacén de imágenes (Docker Hub, GHCR).
  • El context decide a qué daemon habla tu CLI, local o remoto.
  • docker version distingue Client y Server: el diagnóstico de casi todos los fallos empieza ahí.

10 · Preguntas frecuentes

¿Docker sigue usando Docker daemon o ya usa containerd directamente?

Ambos. Docker (dockerd) usa containerd como runtime de contenedores: por eso en docker version ves las versiones de containerd y runc. La diferencia con el Kubernetes «sin Docker» es de quién gestiona a containerd, no de containerd en sí: en Kubernetes moderno, el kubelet habla directamente con containerd; en Docker, la capa intermedia es dockerd.

¿Qué es exactamente Docker Hub?

Es el registry público de imágenes por defecto que Docker usa en docker pull. Puedes subir tus propias imágenes (con una cuenta), encontrar las oficiales (nginx, postgres, node, alpine) y también puede sustituirse por registries privados o por GHCR, que usaremos en este curso.

¿Cuándo necesito un contexto distinto de «default»?

Cuando el daemon al que quieres hablar no está en tu máquina: un servidor de staging, un runner de CI o un clúster Docker remoto. Creas el contexto con la información de conexión y cambias con docker context use NOMBRE. En este curso siempre usaremos el contexto local.

¿Por qué mi comando responde «Cannot connect to the Docker daemon»?

Porque el cliente funciona (lo escribes bien) pero no encuentra ningún daemon al que hablar: o el daemon está parado, o el socket no existe en esa ruta, o tu contexto apunta a otro equipo. En Linux prueba systemctl status docker; en macOS/Windows revisa que Docker Desktop esté iniciado.

¿Docker Desktop afecta a la arquitectura que acabo de aprender?

No en lo esencial: la pila CLI → daemon → containerd → runc es idéntica. La diferencia es dónde vive esa pila: en macOS y Windows, Docker Desktop la esconde dentro de una VM Linux (WSL2 en Windows) para que los contenedores Linux tengan un kernel Linux real. La CLI y la API siguen siendo las mismas.
