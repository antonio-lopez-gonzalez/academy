Qué es un contenedor

Módulo 0 · Preparación ⏱ 30 minutos

1 · Introducción

Si alguna vez dijiste «funciona en mi máquina», ya conoces el problema que resuelven los contenedores: el código se comporta distinto según el sistema donde corre. Cada equipo usa otra versión de Node, otro PostgreSQL, otros paquetes del sistema… y todo funciona en desarrollo y todo se rompe en producción.

Un contenedor es una forma de empaquetar una aplicación con todo lo que necesita para ejecutarse (código, runtime, librerías, configuración) de manera aislada del resto del sistema. En esta lección entenderás qué es exactamente, cómo consigue ese aislamiento por debajo (namespaces y cgroups), por qué nació la idea y en qué se diferencia de una máquina virtual.

¿Por qué existe esta lección? Porque Docker, Compose y Kubernetes son capas construidas sobre una idea central: el contenedor. Si no entiendes qué es un contenedor y por qué se diseñó así, el resto del curso serán comandos que memorizas sin comprender. Esta base te va a ahorrar horas de confusión en los módulos siguientes.

2 · Teoría

Una definición precisa

Un contenedor es un proceso (o grupo de procesos) del sistema operativo host al que se le ha aplicado un doble mecanismo de aislamiento:

  • Namespaces: le dan su propia vista «privada» del sistema (procesos, red, sistema de archivos, usuarios, hostname…).
  • Cgroups (control groups): limitan qué recursos puede usar (CPU, memoria, I/O, número de procesos) para que no ahogue al resto de la máquina.

Analogía: un contenedor no es una casa nueva construida sobre el terreno; es una habitación dentro de un edificio ya existente. Comparte los cimientos y las tuberías con las demás (el kernel), pero tiene su propia puerta, su propia vista a la calle y su propio límite de metros cuadrados. Las máquinas virtuales, en cambio, serían edificios enteros con sus propios cimientos.

La consecuencia más importante: como los contenedores usan el kernel del host, un contenedor de Linux solo puede correr sobre un host Linux. En Windows lo resolvemos con WSL2 (lo verás en la lección 4), y en macOS con una VM ligera (lección 3).

Namespaces: la ilusión de un sistema propio

Un namespace es una partición lógica del sistema. Cuando creamos un contenedor, ponemos a sus procesos en una serie de namespaces para que vean una realidad filtrada:

NamespaceQué aísla
PIDLos procesos. Dentro del contenedor solo ves los tuyos; el más antiguo es el PID 1.
NetworkInterfaces de red, sockets e IPs. Cada contenedor cree tener su propio localhost.
MountEl árbol de directorios. El contenedor ve su propio /, su propia raíz del sistema de archivos.
UTSEl hostname: cada contenedor tiene su propio nombre de máquina.
UserLos UIDs/GIDs: puedes ver al usuario root (UID 0) dentro del contenedor aunque en el host sea otro.
IPCComunicación entre procesos (colas de mensajes, semáforos).

Cgroups: el tope de recursos

Los namespaces aíslan lo que el proceso ve; los cgroups controlan lo que puede consumir. Sin límites, un bucle infinito dentro de un contenedor podría dejar sin CPU a toda la máquina. Con cgroups podemos fijar:

  • cpu: cuántas CPU o qué proporción de tiempo de CPU usa el grupo.
  • memory: cuánta memoria RAM puede usar (incluso swap).
  • pids: cuántos procesos puede crear (protección contra fork bombs).
  • blkio: ancho de banda de lectura/escritura en disco.

Dato clave: en Kubernetes, los requests y limits de cada Pod se traducen exactamente en cgroups del host. Lo que aprendes aquí sobre límites de CPU y memoria te servirá palabra por palabra en el módulo 8.

El «por qué» histórico

  1. chroot (1979): primera idea de «cambiar la raíz» de un proceso, precursora del namespace de mount.
  2. FreeBSD Jails (2000): aíslan procesos con su propio filesystem, red y usuarios.
  3. Linux VServer y Solaris Zones (2004): zona de recursos aislada sobre el mismo kernel.
  4. LXC (2008): primeros contenedores «de sistema» estables combinando namespaces y cgroups del kernel Linux. Podías «fakeear» un servidor entero dentro del host, pero usarlos era incómodo: montar los filesystems, configurar la red y gestionar el ciclo de vida era manual.
  5. Docker (2013): Solomon Hykes y su equipo en dotCloud tomaron las piezas del kernel y las empaquetaron en una herramienta usable: docker build para construir, docker run para ejecutar, y imágenes para distribuir. Ahí explotó la contenerización.

Callouts según tu sistema operativo

Linux: los contenedores corren sobre el kernel nativo; nada intermedio. Es el caso más limpio.

macOS: como el kernel es de macOS, Docker Desktop ejecuta una VM Linux ligera y ahí corren tus contenedores.

Windows: Windows tiene su propio kernel (NT) y los contenedores Linux no pueden usarlo. La vía del curso es WSL2: una VM mínima de Linux que Docker usa como host de los contenedores (lección 04).

3 · Ejemplo mínimo

El ejemplo más pequeño que existe: ejecutar un contenedor que imprima un saludo. Necesitas Docker instalado (lecciones 3 y 4).

# hello-world es una imagen mínima de PRUEBA: un binario que imprime un
# mensaje y termina. Nadie la usa en producción, pero perfecta para validar
# que toda la cadena funciona: CLI -> daemon -> runtime -> contenedor.
docker run hello-world

Qué acaba de pasar, comando por comando:

  1. Docker busca la imagen hello-world: si no está localmente, la descarga de Docker Hub (lección 2).
  2. Crea arquitectura de aislamiento: asigna un namespace PID, network, mount, UTS… para el nuevo proceso.
  3. Establece cgroups: el proceso queda dentro de un grupo con limites de recursos.
  4. Ejecuta el binario: imprime el mensaje, termina, y el contenedor queda en estado exited.

Fíjate: el contenedor hizo su trabajo y terminó. Un contenedor solo vive mientras su proceso principal está vivo. Es un proceso, no una máquina que se «apaga».

4 · Ejemplo real

En este curso construirás HarborTasks, un gestor de tareas con tres piezas: web (nginx), api (Node/Express) y postgres (PostgreSQL). Cada pieza vivirá en su propio contenedor, aislada de las demás:

+-----------------+   +-----------------+   +-----------------+
| CONTENEDOR WEB |   | CONTENEDOR API  |   | CONTENEDOR DB   |
| nginx          |-->| Node.js Express |-->| PostgreSQL      |
| sirve HTML/CSS |   | expone /tasks   |   | guarda los datas|
| puerto 80      |   | puerto 3000     |   | puerto 5432     |
+-----------------+   +-----------------+   +-----------------+

Cada contenedor ve su propio sistema de archivos, su propio localhost, su propio PID 1. Cuando nginx necesite llamar a la API escribirá http://api:3000 y no localhost:3000: porque localhost del contenedor web es él mismo, no la api. Esa idea de «red privada por contenedor» es clave en todo el curso.

Veamos un adelanto con nginx (imagen real nginx:1.27-alpine):

# -d arranca el contenedor en segundo plano (desacoplado de la terminal)
# -p 8080:80 publica el puerto 80 del contenedor en el 8080 del host
# nginx:1.27-alpine es la imagen oficial de nginx sobre Alpine Linux (ligera)
docker run -d -p 8080:80 --name harbor-web nginx:1.27-alpine

Abre http://localhost:8080 y verás la página de bienvenida de nginx. Ese nginx corre en un proceso aislado con sus propios namespaces y sus cgroups, como cualquier otro contenedor.

6 · Errores habituales

Creer que el contenedor es una mini máquina virtual

# ❌ Instalar SO dentro: los contenedores no son VMs
# No necesitas "bootear" ni un init type systemd:
# docker run -it ubuntu systemctl start nginx   # EXISTE? No existe systemd dentro
# systemctl no funciona en la mayoría de contenedores: no hay init system

# ✅ Lanzas el proceso que te interesa directamente, sin init system
docker run -d -p 8080:80 nginx:1.27-alpine

Confundir imagen con contenedor

# ❌ La imagen NO es el contenedor: es la PLANTILLA (receta)
# docker images   -> lista plantillas guardadas
# docker ps       -> lista contenedores que EXISTEN (corriendo o parados)

# ✅ Flujo correcto: de una imagen salen muchos contenedores
docker run hello-world   # crea un contenedor desde la imagen hello-world

Una imagen es el plano estático y compartido; un contenedor es una ejecución concreta de ese plano. De una sola imagen puedes lanzar 50 contenedores a la vez.

Ejecutar todo con sudo

# ❌ sudo para cada comando de Docker
# sudo docker run hello-world
# El sudo camufla un problema de permisos que debes resolver una sola vez

# ✅ Configura tu usuario en el grupo 'docker' (módulo 3) o usa Docker Desktop
# Después reinicia sesión y ejecuta sin sudo:
docker run hello-world

Olvidar que el contenedor termina cuando su proceso principal termina

# ❌ Lanzar un "servidor" que en realidad muere al instante
# docker run -d hello-world   # arranca, imprime, termina. El contenedor queda parado.
docker run -d hello-world
docker ps -a   # lo verás en estado Exited (0)

# ✅ Si quieres algo que se quede vivo, ejecuta un proceso de larga duración
docker run -d -p 8080:80 nginx:1.27-alpine
docker ps      # nginx sigue en estado Up

7 · Ejercicio guiado

Objetivo: ver el aislamiento en acción: dos procesos «vecinos» sin verse entre sí.

  1. Paso 1: ejecuta el contenedor de bienvenida y comprueba el estado: 
    docker run hello-world            # imprime y termina
docker ps -a                     # lo verás en estado "Exited (0)"
  2. Paso 2: entra en un contenedor interactivo de Alpine: 
    # -it abre una sesión interactiva con una pseudo-terminal
# --rm borra el contenedor al salir (no acumula basura)
# sh es la shell de Alpine
docker run --rm -it alpine:3.20 sh
  3. Paso 3: ya dentro de la shell aislada, mira qué procesos «existen»: 
    ps aux          # solo ves tus procesos, NO los del host
hostname        # tienes tu propio hostname, distinto del tuyo real
ls /            # un sistema de archivos propio, no el de tu PC
exit            # al salir, como usamos --rm, el contenedor se borra
  4. Paso 4: en tu terminal del host, ejecuta ps aux (en WSL/Linux) y comprueba que tu sistema sigue teniendo todos sus procesos: el namespace PID del contenedor no afectó al host.
  5. Paso 5 (verificación): ejecuta docker ps -a y comprueba que el contenedor de Alpine ya no existe (lo borró --rm) y que el de hello-world queda como Exited (0).

8 · Reto

🎯 Demuestra el aislamiento de red

Lanza un contenedor de nginx publicado en el puerto 8081, y en tu terminal del host comprueba con curl localhost:8081 que responde. Después, entra en un contenedor Alpine y comprueba que desde dentro de otro contenedor localhost:8081 NO responde (porque el namespace network de cada contenedor es privado). Explica en una frase por qué.

Pista: dentro del contenedor Alpine usa wget localhost:8081 — la red de cada contenedor es su propio localhost; el del host está en otro namespace network.

9 · Resumen

  • Un contenedor es un proceso aislado del host, no una máquina virtual.
  • Namespaces aíslan la vista (procesos, red, filesystem, hostname); cgroups limitan el consumo (CPU, RAM, procesos).
  • Comparte el kernel del host: de ahí su ligereza y la razón por la que en Windows necesitamos WSL2.
  • La idea tiene raíces antiguas (chroot 1979), se estabilizó con LXC (2008) y la hizo masiva Docker (2013).
  • Una imagen es la plantilla; un contenedor es una ejecución de esa plantilla.
  • Un contenedor vive mientras su proceso principal esté vivo.

10 · Preguntas frecuentes

¿Un contenedor es un proceso? ¿Entonces cómo puede tener «un sistema dentro»?

Sí, el contenedor son uno o varios procesos del host. Lo que ocurre es que esos procesos viven en namespaces que redefinen su realidad: ven su propio árbol de procesos, su propio sistema de archivos como raíz y su propio localhost. Es una ilusión controlada por el kernel, no una máquina real.

¿Por qué los contenedores son tan ligeros comparados con las VMs?

Porque no llevan un sistema operativo completo. Una VM incluye un kernel huésped (cientos de MB) y arranca todo un SO. Un contenedor reutiliza el kernel del host y solo monta las capas de su imagen (suele ser un sistema base pequeño tipo Alpine, de pocos MB). Resultado: arranca en milisegundos.

¿Puedo ejecutar un contenedor de Windows sobre Linux?

Viceversa tampoco. Un contenedor de Linux necesita el kernel de Linux; uno de Windows necesita el kernel NT. Por eso en este curso usamos únicamente Linux containers, que corriendo en Windows necesitan WSL2 (una VM Linux) y en macOS una VM Linux interna de Docker Desktop o un entorno alternativo como Colima.

¿Docker inventó la contenerización?

No. El kernel de Linux llevaba años con las piezas (namespaces, cgroups, chroot, LXC). Docker (2013) hizo tres cosas nuevas: empaquetó esas piezas en un flujo sencillo (build, run, pull/push), popularizó el formato de imágenes y creó una comunidad y un registro central (Docker Hub). El mérito es de producto y ecosistema, no de inventar el aislamiento.

Si el filesystem del contenedor es efímero, ¿dónde guardo los datos?

En volúmenes y bind mounts: zonas de almacenamiento gestionadas por Docker (o por el clúster en Kubernetes) que sobreviven al contenedor. Es el tema del módulo 3 y un requisito imprescindible para PostgreSQL en HarborTasks.
