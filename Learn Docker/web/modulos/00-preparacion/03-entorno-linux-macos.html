Entorno en Linux y macOS

Módulo 0 · Preparación ⏱ 35 minutos

1 · Introducción

Linux y macOS son los dos mundos «nativos» de Docker, pero se instalan de forma muy distinta: en Linux instalas el Docker Engine nativo (un servicio de sistema), mientras que en macOS instalas Docker Desktop (una aplicación que esconde una VM Linux). Entender esa diferencia te evita el error clásico de buscar systemctl en macOS o de intentar configurar un «grupo docker» que no existe.

En esta lección instalas el motor en ambos sistemas y aprendes a verificar que todo funciona con tres comandos que usarás en cada entorno del curso: docker version, docker info y docker run hello-world.

¿Por qué existe esta lección? La instalación es el primer sitio donde todo el mundo tropieza: permisos del socket en Linux, la VM de macOS, el PATH, el daemon parado. Resolver esas tres cosas ahora, con calma y comprobando, te ahorra semanas de «no me funciona» a lo largo de HarborTasks.

2 · Teoría

Docker en Linux: Engine nativo sobre el kernel

En Linux, Docker corre directamente sobre el kernel (recuerda la lección 1: los contenedores usan el kernel del host). Instalas dos piezas:

  • El daemon dockerd: gestionado como un servicio de sistema (systemd). Se inicia con el sistema y se administra con systemctl.
  • La CLI docker: el cliente que habla con el daemon (lección 2).

El daemon escucha en el socket /var/run/docker.sock. Por defecto ese socket pertenece a root, así que hay que añadir nuestro usuario al grupo docker para poder ejecutar Docker sin sudo (la spec del curso prohíbe sudo como requisito).

Docker en macOS: una VM Linux escondida

macOS tiene su propio kernel (XNU), y los contenedores Linux necesitan un kernel Linux. Docker Desktop levanta una máquina virtual ligera de Linux (mediante un framework de virtualización del propio macOS) y ejecuta dentro toda la pila de Docker. Tú no la ves: interactúas con la app y la CLI como si fuera un programa normal.

Por eso en macOS:

  • No hay systemctl: el daemon vive dentro de la VM.
  • No hay grupo docker: no necesitas permisos especiales de socket.
  • Todo se administra desde la app de menú o con docker … directamente.

Alternativas del mundo macOS

Docker Desktop es la opción estándar, pero no la única ni la más ligera:

  • Colima: CLI de código abierto que levanta la misma VM Linux (usando lima). Ligera y sin licencia comercial.
  • OrbStack: clon moderno y rapidísimo de Docker Desktop, con soporte de contenedores y máquinas Linux, pensado para desarrolladores.

En este curso: usaremos Docker Desktop como vía principal por ser la más extendida y documentada. Colima/OrbStack se mencionan como alternativas equivalentes, y los comandos docker … son idénticos en las tres, porque todas exponen la misma CLI/API.

Comandos de verificación: el «checklist de salud»

ComandoQué comprueba
docker versionQue la CLI y el daemon existen y se hablan (lección 2)
docker infoEstado del daemon: contenedores, imágenes, drivers, versiones internas
docker run hello-worldEl recorrido completo: pull → daemon → containerd → contenedor real

3 · Ejemplo mínimo

La instalación se da por buena con tres comandos. Este es tu futuro «reset mental» cada vez que algo falle:

# 1) ¿Existen cliente y servidor y se ven? (server vacío = daemon caído)
docker version

# 2) ¿El daemon está sano? muestra versión, drivers y contadores
docker info

# 3) ¿Funciona de punta a punta? descarga y ejecuta la imagen de prueba
docker run hello-world

Si los tres funcionan, tu entorno está listo para todo el curso. Si fallan, la jerarquía de diagnóstico es: primero docker version (¿daemon arriba?), después docker info (¿drivers y espacio?), y por último hello-world (¿puede descargar del registry?).

Atención en Linux: si el primer comando te da permission denied con el socket, es el problema del grupo docker del que hablaremos en la sección de ejercicios. En macOS no ocurre: Docker Desktop no usa el socket del host.

4 · Ejemplo real

Imagina que acabas de llegar a un equipo y te dan un portátil. Verificar Docker no es un gesto cosmético: es detectar antes de empezar si el motor usa el driver correcto, si quedan imágenes basura que llenan el disco y si la red está bien. Un flujo real de verificación:

# 1) Versión y salud rápida del daemon
docker version
docker info

# 2) ¿Qué hay en la biblioteca local? (imágenes de otros proyectos)
docker images

# 3) ¿Hay contenedores fantasma ocupando espacio?
docker ps -a

# 4) Prueba de fuego: un contenedor real de nginx, no solo hello-world
docker run -d --rm -p 8080:80 nginx:1.27-alpine
curl -I localhost:8080      # cabecera HTTP: esperamos HTTP/1.1 200 OK

Con --rm el contenedor se limpiará solo al pararlo. Si curl no existe en tu sistema (macOS tiene curl incluido; en Linux suele instalarse con curl), puedes abrir http://localhost:8080 en el navegador.

Linux: si curl no está, en Debian/Ubuntu: sudo apt install curl; en Fedora: sudo dnf install curl. macOS: curl viene preinstalado. Windows: en la lección 04 harás la misma prueba desde dentro de WSL2.

6 · Errores habituales

En Linux: «permission denied while trying to connect to the Docker daemon socket»

# ❌ El error típico al instalar Docker Engine sin configurar el grupo
# docker run hello-world
# -> permission denied while trying to connect to the Docker daemon socket

# ✅ Añade tu usuario al grupo docker, cierra sesión y vuelve a entrar
sudo usermod -aG docker $USER
newgrp docker      # refresca los grupos en la sesión actual
docker run hello-world   # ahora funcionará sin sudo

En macOS: creer que Docker esta «roto» cuando solo no ha arrancado

# ❌ La CLI funciona pero el daemon no: falta arrancar Docker Desktop
# docker version   -> Server: ERROR ... Cannot connect to the Docker daemon

# ✅ Levanta la app de Docker Desktop (o pide imagen arrancada con launchctl)
# En la app: Settings -> Troubleshoot -> Restart
open -a Docker          # macOS: abre la aplicación
docker info             # cuando docker info responda, ya puedes continuar

7 · Ejercicio guiado

Objetivo: dejar tu Linux o macOS verificado con los 3 comandos de salud y resolver, si aparece, el problema del socket.

  1. Paso 1 (Linux): instala Docker Engine desde el repositorio oficial de tu distro y añade tu usuario al grupo: 
    # Debian/Ubuntu (resumen; consulta docs.docker.com para la guía completa)
#   sudo apt update
#   sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin
sudo usermod -aG docker $USER   # añade tu usuario al grupo docker
newgrp docker                   # activa el grupo en la sesión actual
  2. Paso 1 (macOS): descarga Docker Desktop desde docker.com/products/docker-desktop, arrastra la app a Aplicaciones y ábrela. En la primera ejecución acepta el permiso de «privileged helper».
  3. Paso 2: comprueba que la CLI y el daemon se hablan: 
    docker version     # deben verse ambas secciones: Client y Server
  4. Paso 3: revisa el estado del daemon: 
    docker info        # mira Server Version y el warning de storage driver, si lo hay
  5. Paso 4: la prueba final: 
    docker run hello-world   # mensaje de bienvenida = todo el stack funciona
  6. Paso 5 (verificación): ejecuta docker images y deberías ver hello-world descargada; docker ps -a y verás el contenedor de hello-world con Exited (0). Si algo falla, comprueba docker context ls y que en macOS la app esté encendida (ícono de la ballena en la barra).

8 · Reto

🎯 Diagnostica tu instalación en 60 segundos

Imagina que te envían este fallo real: «Mi docker run hello-world da Cannot connect to the Docker daemon. ¿Qué comando ejecutarías primero para saber si el problema es de daemon, de socket o de permisos?» Escríbelo y razona: ¿qué cambiaría en tu diagnóstico si el sistema fuera Linux en lugar de macOS? Pista: en macOS no existe ni systemctl ni el socket del host, así que el diagnóstico empieza por la app, no por el sistema.

Pista: aplica la jerarquía docker version → docker info → hello-world, y recuerda qué mecanismo de arranque del daemon existe en cada sistema.

9 · Resumen

  • Linux: Docker Engine nativo como servicio de sistema; gestión con systemctl; grupo docker para no usar sudo.
  • macOS: Docker Desktop con una VM Linux interna; sin systemctl ni grupo docker.
  • Alternativas macOS: Colima y OrbStack; la misma CLI y API.
  • Los 3 comandos de salud son docker version, docker info y docker run hello-world, en ese orden de diagnóstico.
  • El error más común en Linux es el permiso del socket; en macOS, Docker Desktop no arrancado.

10 · Preguntas frecuentes

¿Es peligroso estar en el grupo «docker»?

Dar acceso al socket de Docker equivale, en la práctica, a acceso root del host: cualquiera dentro del grupo puede montar el disco del host en un contenedor. En un equipo personal es aceptable y lo normal; en servidores de producción se mitiga con autorizaciones y entornos aislados. Nunca pongas el socket en manos de código no confiable.

¿Por qué en macOS no necesito el grupo docker?

Porque el socket «de verdad» está dentro de la VM Linux de Docker Desktop. La CLI de macOS habla con Docker Desktop a través de su proxy, que ya gestiona los permisos. No hay un socket del host que proteger, así que no existe el mecanismo de grupo docker.

¿Docker Desktop para macOS es gratis?

Hay un plan gratuito para uso personal y otro de pago para empresas grandes (la política cambia con el tiempo, consulta la web oficial). Si el uso comercial es un problema, Colima y OrbStack (con sus propias licencias) son alternativas de terminal que usan la misma CLI.

¿Puedo tener Docker Engine (línea de comandos) en macOS sin la app?

El motor necesita un kernel Linux, que en macOS solo existe dentro de una VM. Colima es exactamente eso: levanta la VM Linux desde la terminal y da el binario docker junto a ella. Docker Desktop es la alternativa con interfaz de app. Por eso en macOS «cliente suelto + motor» no existe sin una VM intermedia.

Llevo el daemon arriba y hello-world sigue fallando por red. ¿Qué hago?

Revisa primero con docker info el espacio en disco (las imágenes de nginx llenan rápido el almacén si hay basura) y la configuración de red/proxy del daemon. Si usas un proxy corporativo, necesitas configurarlo para dockerd y la CLI. Si estás en macOS con antivirus/firewalls agresivos, pueden bloquear el tráfico a Docker Hub.
