Publicar librerias tipadas

Modulo 12 · Monorepos y produccion 🕐 40 minutos

1 · Introduccion

Publicar una libreria desde un workspace pnpm es el camino completo de "codigo util" → "paquete en el registry". La parte que mas se descuida es la entrega de tipos: una libreria sin .d.ts correctos obliga al consumidor a re-escribir los tipos o a trabajar con any. Esta leccion ensena a emitir declaraciones, declarar entradas (exports) que funcionen en ESM y CJS, y publicar desde el monorepo del Modulo 12.

El problema que resuelve: en el workspace todo funciona porque TypeScript resuelve el codigo fuente. Pero en el registry, el consumidor recibe un tarball: JavaScript transpilado + declaraciones. Si el exports no declara bien los tipos (y las dos sintaxis de modulos), la libreria "se instala pero no se tipa", y nadie te avisa hasta que el editor se queda sin IntelliSense.

Cuando se utiliza
  • Librerias reutilizables que salen del monorepo hacia el registry (npm).
  • Paquetes que deben funcionar con consumidores ESM y CJS a la vez.
  • Cuando quieres que los .d.ts se generen, no se escriban a mano.
  • CI de publicacion: build + versionado + publish con las mismas herramientas que en local.

2 · Teoria

La analogia: la estanteria de la tienda

El registry es una tienda: tu libreria es una caja (el tarball) con el producto (JavaScript). Pero el consumidor no compra a ciegas: necesita la etiqueta de especificaciones para saber que contiene y como usarla. Esa etiqueta son las declaraciones .d.ts. Si la caja llega sin etiqueta, el consumidor la abre, la usa, y descubre tarde (o nunca) que le faltan tipos.

Emitir declaraciones: declaration, declarationMap

// packages/mi-lib/tsconfig.build.json
{
  "compilerOptions": {
    "declaration": true,        // emite los .d.ts
    "declarationMap": true,     // mapas hacia el codigo fuente (editor)
    "declarationDir": "dist",   // donde caen los .d.ts
    "outDir": "dist",
    "rootDir": "src",
    "strict": true
  },
  "include": ["src"]
}
  • declaration: true genera un index.d.ts por cada fuente: la "etiqueta".
  • declarationMap: true permite al editor ir a la definicion del fuente original, incluso cuando el paquete viene del registry. Requiere declaration (o composite, que la implica).
  • El consumidor nunca ve src: ve dist/*.js + dist/*.d.ts.

El package.json tipado: types, main, exports

{
  "name": "@acme/calc",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.js",        // punto de entrada CJS clasico (legacy)
  "module": "./dist/index.js",      // pista ESM para bundlers clasicos
  "types": "./dist/index.d.ts",     // tipos top-level (consumidores antiguos)
  "exports": {
    ".": "./dist/index.js"
  }
}

main + types es el esquema de la era node10: simple, pero no distingue ESM de CJS. El esquema moderno es exports, que si distingue condiciones.

El problema dual ESM/CJS

Node distingue dos familias de modulos: ESM (import) y CommonJS (require). Un paquete que quiere servir a ambas debe declarar condiciones dentro de exports, y cada condicion puede tener su propia entrada de tipos. 

{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/esm/index.d.ts",
        "default": "./dist/esm/index.js"
      },
      "require": {
        "types": "./dist/cjs/index.d.cts",
        "default": "./dist/cjs/index.cjs"
      }
    }
  }
}
El dual package hazard

Si ESM y CJS son dos copias distintas del modulo (dos archivos, dos estados), una aplicacion puede acabar con dos instancias del mismo paquete: un singleton que no es singleton, estado compartido duplicado, identidades (instanceof) rotas. Mitigaciones: publicar solo ESM (Node moderno lo soporta, y bundlers tambien) o generar ambos desde el mismo fuente y documentar la limitacion. No es una decision de tipos: es una decision de arquitectura.

types, typesVersions y como conviven

  • types top-level: unica ruta, para herramientas que no leen exports (paquetes viejos, algunos linters).
  • Condicion "types" dentro de exports: el modo moderno (TypeScript 4.7+, resoluciones node16/nodenext/bundler). Debe ir la PRIMERA dentro de cada condicion.
  • typesVersions: el fallback de la era node10, para consumidores con TypeScript anterior a 4.7 que ignoran exports:
{
  "typesVersions": {
    "*": {
      "*": ["dist/*"]       // TODO subpath se resuelve dentro de dist/
    }
  }
}

Orden de dureza en TypeScript moderno: primero la condicion types de exports; si no hay, typesVersions; si no, types top-level. Publica los tres coherentes y tu libreria tipara en cualquier consumidor.

Publicar desde un workspace pnpm

pnpm --filter @acme/calc build      # tsc -> dist (js + d.ts)
pnpm --filter @acme/calc pack       # genera el .tgz local (inspeccion)
pnpm --filter @acme/calc publish    # sube al registry

// packages/mi-lib/package.json
{
  "name": "@acme/calc",
  "version": "1.0.0",
  "files": ["dist"],                    // SOLO lo que necesita el consumidor
  "sideEffects": false,                 // avisa para tree-shaking
  "publishConfig": { "access": "public" },
  "scripts": {
    "build": "tsc -p tsconfig.build.json",
    "prepublishOnly": "pnpm build && pnpm test"
  }
}

En un workspace, pnpm publish publica el paquete local con su workspace:* resuelto a la version real. prepublishOnly garantiza que nada se sube sin compilar y sin pruebas. files es una allowlist: si falta tu dist, publicas un paquete roto.

3 · Ejemplo minimo

suma.ts
// Fuente de la libreria (src/suma.ts)
export function suma(a: number, b: number): number {
  return a + b;
}
package.json (minimo tipado)
{
  "name": "@acme/suma",
  "version": "0.1.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    }
  },
  "files": ["dist"]
}

Linea a linea:

  • declaration: true en tsconfig genera dist/index.d.ts que describe la funcion: el consumidor ve tipos sin ver el fuente.
  • exports con condicion types primero: TypeScript moderno lo lee antes que el default.
  • default apunta al JavaScript real; files: ["dist"] impide publicar src y basura.

4 · Ejemplo real

Libreria @acme/pedido-core con build dual (ESM + CJS) y declaraciones, publicada desde el monorepo.

packages/pedido-core/src/index.ts
// Codigo fuente de la libreria: una cara publica tipada.
export interface EstadoPedido {
  id: string;
  estado: "creado" | "pagado" | "enviado";
}

export function marcarPagado(p: EstadoPedido): EstadoPedido {
  return { ...p, estado: "pagado" };
}
packages/pedido-core/tsconfig.build.json
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist",
    "strict": true
  },
  "include": ["src"]
}
packages/pedido-core/package.json
{
  "name": "@acme/pedido-core",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.ts",
        "default": "./dist/index.js"
      },
      "require": {
        "types": "./dist/index.d.cts",
        "default": "./dist/index.cjs"
      }
    },
    "./package.json": "./package.json"
  },
  "files": ["dist"],
  "sideEffects": false,
  "publishConfig": { "access": "public" },
  "scripts": {
    "build": "tsc -p tsconfig.build.json && tsc -p tsconfig.cjs.json",
    "prepublishOnly": "pnpm build && pnpm test"
  }
}
packages/pedido-core/tsconfig.cjs.json
{
  "extends": "./tsconfig.build.json",
  "compilerOptions": {
    "module": "commonjs",
    "outDir": "dist/cjs"
  }
}
Comandos
pnpm --filter @acme/pedido-core build
pnpm --filter @acme/pedido-core pack   # mira el .tgz: dist/ con .js y .d.ts
pnpm --filter @acme/pedido-core publish

Decisiones:

  • El exports entrega dos rutas: ESM (.js) y CJS (.cjs), cada una con su .d.ts (.d.cts para la version CommonJS).
  • La condicion types va primero en cada rama: el consumidor resuelve tipos antes que codigo.
  • main/types top-level quedan como red de seguridad para herramientas de la era node10; exports manda.
  • files: ["dist"] + sideEffects: false optimizan tamano y tree-shaking.
  • La build de CJS es una segunda pasada de tsc con module: commonjs: mismo fuente, dos artefactos. Ambos comparten el mismo contrato tipado.

5 · Buenas practicas

  • Genera las declaraciones (nunca a mano): declaration + declarationMap.
  • Publica exports con condiciones import/require y types primero en cada rama; manten main/types como fallback.
  • Inspecciona el tarball con pnpm pack antes de publicar: si no ves .d.ts, no publiques.
  • Moja el paquete en un consumidor de prueba (otro workspace) con moduleResolution: bundler y con nodenext: los dos caminos deben tipar.
  • Usa prepublishOnly (build + test) para que nada roto salga al registry.
  • Si el consumidor puede ser antiguo, anade typesVersions coherente con tu dist.

Que evitar

  • Publicar src entero o sin files: ensucias, inflas y expones internos.
  • Declaraciones desalineadas: .d.ts que no corresponde a la version de JavaScript publicada (build desactualizada).
  • Olvidar la condicion types en exports: el paquete tipa en local, pero no en el registry.
  • Confundir main con exports: en paquetes modernos exports es la autoridad; main es el plan B.

6 · Errores habituales

Mal — exports sin la condicion types (tipos perdidos) 
{
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
  // ✖ el consumidor no encuentra .d.ts: paquete "sin tipos"
}
Bien — types primero dentro de cada condicion 
{
  "exports": {
    ".": {
      "import": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
      "require": { "types": "./dist/index.d.cts", "default": "./dist/index.cjs" }
    }
  }
}
Mal — declarar sin emitir (falta declaration) 
tsc -p tsconfig.build.json   # ✖ sin "declaration": true no hay .d.ts
# y el pack publica solo .js -> consumidor sin tipos
Bien — declaration emitida y verificada 
tsc -p tsconfig.build.json    # con declaration: true
ls dist/*.d.ts                # ✅ existe la etiqueta de tipos
Mal — publicar sin compilar (o sin el dist en files) 
{
  "name": "@acme/calc",
  "files": ["src"],   // ✖ el consumidor recibe el fuente, no dist
  "scripts": {}
}
Bien — build previa y allowlist de dist 
{
  "files": ["dist"],
  "scripts": {
    "build": "tsc -p tsconfig.build.json",
    "prepublishOnly": "pnpm build"
  }
}

7 · Ejercicio guiado

Publica tu primera libreria tipada desde un workspace, sin soltarla al registry de verdad.

  1. Crea packages/mi-lib con un src/index.ts que exporte doble(n: number): number.
  2. Anade tsconfig.build.json con declaration: true, declarationMap: true, outDir: dist y rootDir: src.
  3. Declara en package.json: type: module, exports con types + default, files: ["dist"] y script build.
  4. Compila y comprueba que dist/ contiene index.js e index.d.ts.
  5. Inspecciona el tarball con pnpm pack y verifica que solo contiene dist.

packages/mi-lib/src/index.ts
export function doble(n: number): number {
  return n * 2;
}
packages/mi-lib/tsconfig.build.json
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist",
    "strict": true
  },
  "include": ["src"]
}
packages/mi-lib/package.json
{
  "name": "@acme/mi-lib",
  "version": "0.1.0",
  "type": "module",
  "exports": {

8 · Reto

Reto

Convierte @acme/mi-lib en un paquete dual: anade una segunda build (module: commonjs, outDir: dist/cjs) y declara en exports las condiciones import y require con sus tipos (.d.ts y .d.cts). Pruebalo en dos consumidores: uno con moduleResolution: bundler y otro con nodenext. Pista: la condicion types debe ir siempre antes que default, y el consumidor CJS debe resolver con require().

9 · Resumen

  • Las declaraciones se emiten (declaration + declarationMap), nunca se escriben a mano.
  • exports con condiciones import/require resuelven el consumo dual; types va primero en cada rama.
  • El dual package hazard (dos copias del modulo) es una decision de arquitectura, no solo de tipos.
  • Coexisten tres mecanismos: condicion types (moderno), typesVersions (fallback node10) y types top-level.
  • Publica con pnpm publish desde el workspace, previo build/prepublishOnly, inspeccionando el tarball con pnpm pack.
  • files (allowlist) + sideEffects: false + publishConfig.access completan una publicacion profesional.

10 · Preguntas frecuentes

¿Puedo publicar solo ESM y olvidarme de CJS?

Si: hoy es viable y recomendado para muchisimas librerias. Node moderno, bundlers y TypeScript soportan ESM. El coste es excluir consumidores CommonJS puros. Si necesitas ambos, la build dual de esta leccion es el camino.

¿Que diferencia hay entre d.ts y d.cts?

Son declaraciones del mismo contrato con distinta interpretacion de modulos: .d.ts es ESM (o la que marque el package.json cercano) y .d.cts es CommonJS. Publicar ambas evita que un consumidor require() reciba tipos ESM y al reves.

¿Para que sirve "typesVersions" si ya uso exports?

Para consumidores con TypeScript anterior a 4.7 (o resolucion node10) que no leen exports. Es una capa de compatibilidad: si tu publico es moderno, puedes omitirla.

¿Como pruebo el paquete sin publicarlo?

Dos metodos: pnpm pack para inspeccionar el tarball, o publicar a un registry local (verdaccio) / usar file: o workspace: a un consumidor de prueba. Tambien el CI de publicacion puede simular con npm publish --dry-run.

¿Que hace "sideEffects: false"?

Avisa a los bundlers de que tus modulos no tienen efectos colaterales al importarse, y pueden tree-shake (eliminar codigo no usado). Si tu libreria importa CSS o registra polyfills, no lo pongas a false sin cuidado.

¿Por que el CI debe publicar y no mi maquina?

Determinismo y auditoria: en CI el paquete se compila y prueba en el mismo entorno una vez mas, y el publish queda registrado. En el workspace pnpm, el comando es el mismo que en local: pnpm --filter @acme/paquete publish.
