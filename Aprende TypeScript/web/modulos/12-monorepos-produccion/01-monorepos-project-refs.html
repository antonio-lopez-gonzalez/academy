Monorepos con project references

Modulo 12 · Monorepos y produccion 🕐 40 minutos

1 · Introduccion

Un monorepo profesional organiza aplicaciones y librerias en paquetes independientes, cada uno con su propio tsconfig.json. En el Modulo 7 viste la base: pnpm workspaces y project references. Ahora lo llevamos al terreno de produccion: una estructura tipada contracts / client / server, configuraciones compartidas con extends y el orden de build garantizado con tsc -b.

El problema que resuelve: si cada paquete compila ajeno a los demas, terminas copiando tipos a mano, duplicando configuraciones (strict, module, target) y con builds que "recompilan el mundo" aunque solo haya cambiado un interface. Con references + extends, un cambio en contracts recompila solo a quien lo usa, y una sola config base gobierna a todos.

Cuando se utiliza
  • Equipos con varias apps (client, server) y librerias compartidas (contracts, ui, utils).
  • Paquetes tipados reutilizables que quieres verificar de forma incremental en CI.
  • Cuando duplicar strict y compania en 10 tsconfigs empieza a doler.
  • Cuando necesitas compilar en orden: primero las dependencias, luego los consumidores.

2 · Teoria

La analogia: la fabrica de muebles

Una fabrica de muebles no corta la madera y monta la silla en el mismo banco. Tiene talleres: el de diseno (contracts, los planos), el de montaje (client/server, que usan los planos). El capataz (el modo build) decide el orden: primero diseno, luego montaje, y solo reabre un taller si su trabajo de entrada cambio. Los planos que se pasan entre talleres son los .d.ts.

Raiz ├── tsconfig.json (files: [], solo references -> orquesta) ├── tsconfig.base.json (extends: config comun, sin codigo propio) ├── packages/contracts (composite: true -> emite planos .d.ts) ├── apps/server (composite: true, emits JS para Node) └── apps/client (composite: true, noEmit -> Vite empaqueta) ▲ │ │ └── tsc -b ordena el grafo: contracts antes que apps └── pnpm workspace enlaza @acme/contracts en node_modules

Project references: un proyecto por paquete

Un paquete que otros van a consumir debe declararse como proyecto compuesto con "composite": true. Esta opcion hace dos cosas automaticamente:

  • Activa declaration: emite .d.ts, el "contrato" que otros proyectos leen.
  • Activa incremental: escribe un fichero de build (tsconfig.tsbuildinfo) con la huella de cada archivo, clave para recompilar solo lo que cambio.
// packages/contracts/tsconfig.json
{
  "compilerOptions": {
    "composite": true,        // implica declaration + incremental (no se pueden apagar)
    "declarationMap": true,   // mapas de los .d.ts hacia el codigo fuente
    "rootDir": "src",
    "outDir": "dist",
    "strict": true
  },
  "include": ["src"]
}
Por que composite fuerza declaration e incremental

Para que un proyecto sea referenciado necesita poder entregar tipos (declaraciones) y saber si su salida sigue vigente (seguimiento incremental). Sin esos dos, el compilador no puede decidir cuando debe recompilar a los consumidores. Por eso, si intentas poner "declaration": false o "incremental": false en un proyecto composite, TypeScript da error.

El consumidor declara la dependencia en su propio tsconfig:

// apps/server/tsconfig.json
{
  "references": [
    { "path": "../../packages/contracts" }
  ]
}

references establece el grafo: "mi codigo usa tipos que vienen de packages/contracts". Este grafo es lo que el modo build explota para ordenar y cachear.

El orden de build: el grafo dirigido

tsc -b (build mode) lee las references de todos los proyectos, construye el grafo y lo recorre en orden topologico: las dependencias antes que los dependientes. Ademas reutiliza los tsbuildinfo: si contracts no cambio (misma huella), sus consumidores no se recompilan. 

tsc -b .            # compila la raiz y TODO el grafo en orden
tsc -b . --dry      # muestra el orden sin compilar (ensayo)
tsc -b . --verbose  # explica proyecto a proyecto que hace
tsc -b . --force    # ignora la cache, recompila todo
tsc -b . --clean    # borra la salida de todos los proyectos
tsc -b . --watch    # modo vigilante: recompila al guardar

Herencia de tsconfig con extends

Mantener strict, module y target copiados en 10 tsconfigs es fabricar errores. extends resuelve la duplicacion: un fichero base y los hijos heredan. 

// tsconfig.base.json (raiz del monorepo)
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  }
}

// apps/client/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "noEmit": true
  },
  "include": ["src"]
}

Reglas de herencia que debes conocer:

  • Todo lo que el hijo defina gana sobre la base (override).
  • files, include y exclude del hijo sustituyen a los de la base (no se mezclan).
  • Desde TypeScript 5.0, extends acepta un array de bases; la ultima gana en conflictos. Util para combinar @tsconfig/strictest con tu base propia.
  • Los paths relativos (include, outDir, rootDir) se resuelven respecto al fichero donde estan escritos. No pongas outDir en la base si los paquetes viven a distintas profundidades.

Composicion: la raiz que solo orquesta

El tsconfig raiz no compila codigo: solo compone el grafo. Es el patron de Vite y de la mayoria de monorepos tipados. 

// tsconfig.json (raiz)
{
  "files": [],
  "references": [
    { "path": "./packages/contracts" },
    { "path": "./apps/server" },
    { "path": "./apps/client" }
  ]
}

Ejecutar tsc -b . en la raiz dispara los tres proyectos en orden. Nota que las apps del ejemplo usan noEmit: su JavaScript lo genera Vite (client) o un runtime (server); el TypeScript solo verifica. El modo build soporta proyectos noEmit sin problema: los comprueba y emite solo cuando el proyecto produce dist.

pnpm workspaces conecta los paquetes

# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

// apps/server/package.json
{
  "name": "@acme/server",
  "dependencies": {
    "@acme/contracts": "workspace:*"
  }
}

pnpm install                         # instala y enlaza los workspaces
pnpm --filter @acme/server build     # ejecuta el script "build" solo en server
pnpm -r exec tsc -b --pretty false   # ejecuta tsc -b en todos los paquetes

workspace:* le dice a pnpm "enlaza el paquete local con ese nombre en lugar de buscar en el registry". En runtime y en el tipado, @acme/contracts se resuelve a la carpeta local del workspace.

3 · Ejemplo minimo

monorepo-minimo
// Estructura:
//   tsconfig.base.json  ~  extends global
//   packages/lib/       ~  composite, emite .d.ts
//   apps/app/           ~  references + noEmit

// tsconfig.base.json
// { "compilerOptions": { "strict": true, "module": "nodenext" } }

// packages/lib/tsconfig.json
// { "extends": "../../tsconfig.base.json",
//   "compilerOptions": { "composite": true, "rootDir": "src", "outDir": "dist" } }

// packages/lib/src/doble.ts
export function doble(n: number): number {
  return n * 2;
}

// apps/app/tsconfig.json
// { "extends": "../../tsconfig.base.json",
//   "compilerOptions": { "composite": true, "noEmit": true },
//   "references": [{ "path": "../../packages/lib" }] }

// apps/app/src/main.ts
import { doble } from "@acme/lib";
const x: number = doble(21); // ✅ el tipo fluye desde lib
console.log(x);

Linea a linea:

  • La base define lo comun (strict, module); los hijos solo anaden lo suyo.
  • lib es composite: produce los .d.ts que app consumira.
  • app referencia a lib y usa noEmit: solo chequea tipos.
  • tsc -b . desde la raiz construye lib antes que app.

4 · Ejemplo real

Monorepo tipado con tres paquetes: contratos compartidos, servidor y cliente.

tsconfig.base.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true,
    "skipLibCheck": true
  }
}
packages/contracts/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}
packages/contracts/src/index.ts
// Los "planos" compartidos: aqui solo hay tipos.
export interface Pedido {
  id: string;
  total: number;
  estado: EstadoPedido;
}

export type EstadoPedido = "creado" | "pagado" | "enviado";
apps/server/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "../../node_modules/.tmp/tsconfig.server.tsbuildinfo"
  },
  "references": [{ "path": "../../packages/contracts" }],
  "include": ["src"]
}
apps/server/src/main.ts
import type { Pedido } from "@acme/contracts";

// El servidor SI emite JavaScript (lo ejecuta Node).
function cobrar(pedido: Pedido): Pedido {
  // pedido.estado esta tipado por contracts, no duplicado aqui.
  console.log(`Cobrando ${pedido.total} (${pedido.estado})`);
  return { ...pedido, estado: "pagado" };
}
apps/client/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "noEmit": true,
    "tsBuildInfoFile": "../../node_modules/.tmp/tsconfig.client.tsbuildinfo"
  },
  "references": [{ "path": "../../packages/contracts" }],
  "include": ["src"]
}
apps/client/src/main.ts
import type { Pedido } from "@acme/contracts";

// El cliente NO emite: Vite empaqueta su JavaScript.
const p: Pedido = { id: "1", total: 99, estado: "creado" };
if (p.estado === "creado") {
  console.log("Pedido listo para pagar");
}
tsconfig.json (raiz, orquesta)
{
  "files": [],
  "references": [
    { "path": "./packages/contracts" },
    { "path": "./apps/server" },
    { "path": "./apps/client" }
  ]
}
Comandos
pnpm install
tsc -b . --verbose   # 💡 muestra el orden: contracts -> server -> client

Decisiones:

  • La raiz solo orquesta con files: []; el grafo vive en las references.
  • contracts es la unica fuente de tipos: nadie redeclara Pedido.
  • El server emite (outDir: dist) porque Node ejecuta su JavaScript; el client usa noEmit porque Vite hace el bundle.
  • tsBuildInfoFile saca los ficheros de build a node_modules/.tmp (ya ignorado por git) y evita ensuciar cada paquete.
  • Un cambio en Pedido recompila contracts y, con huella distinta, a server y client.

5 · Buenas practicas

  • Marca composite: true en TODO proyecto que vaya a ser referenciado; TypeScript dara error si lo olvidas, asi que hazlo sistematico en la base de los paquetes.
  • Centraliza strict, module y target en un tsconfig.base.json con extends; no copies opciones.
  • Comila siempre con tsc -b cuando haya references: orden + cache. tsc -p a secas ignora el grafo.
  • Usa noEmit en apps cuyo JavaScript produce otra herramienta (Vite); deja emitir a los paquetes que publican dist.
  • Saca los tsbuildinfo del arbol (tsBuildInfoFile hacia node_modules/.tmp) y add al ignore los que queden.
  • Declara los enlaces locales con workspace:* en pnpm; el tipado se resuelve contra la carpeta del workspace.
  • Manten el grafo en arbol: sin dependencias circulares entre paquetes.

Que evitar

  • Poner outDir o rootDir en la config base: los paths se resuelven respecto al fichero donde nacen y cada paquete esta a una profundidad distinta.
  • Copiar interfaces entre paquetes en lugar de referenciar el paquete comun.
  • Mezclar la config del editor con la de build sin necesidad: el editor puede ser mas laxo, el build mas estricto (o viceversa), pero la raiz de verdad es el build.
  • noEmit en un paquete que debe publicar .d.ts: las librerias necesitan emitir.

6 · Errores habituales

Mal — referenciar un proyecto que no es composite 
{
  "compilerOptions": { "strict": true }
}
// apps/app -> references a packages/lib, pero lib no tiene composite
// ✖ TS6306: Referenced project must have setting "composite": true
Bien — el referenciado es composite 
{
  "compilerOptions": {
    "composite": true,   // implica declaration + incremental
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}
Mal — compilar con tsc -p ignorando el grafo 
tsc -p apps/server   # ✖ no construye contracts primero
tsc -p packages/contracts   # ✖ no avisa a los consumidores
Bien — build mode respeta el orden 
tsc -b apps/server   # ✅ compila contracts (si hace falta) y despues server
tsc -b .              # ✅ todo el monorepo desde la raiz
Mal — outDir en la base compartida 
// tsconfig.base.json
{
  "compilerOptions": {
    "strict": true,
    "outDir": "dist"   // ✖ se resuelve relativo a la RAIZ, no a cada paquete
  }
}
Bien — el hijo decide su salida 
// packages/contracts/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "rootDir": "src",
    "outDir": "dist"   // ✅ relativo a packages/contracts
  }
}
Mal — dependencia circular entre paquetes 
// apps/client importa de packages/ui
// packages/ui importa de apps/client  (✖ cierra el ciclo)
// TypeScript no puede ordenar el grafo: error de referencia
Bien — grafo en arbol 
// packages/ui no conoce a apps; las apps dependen de packages

7 · Ejercicio guiado

Monta un mini-monorepo de dos paquetes con config compartida por extends.

  1. Crea tsconfig.base.json en la raiz con strict: true y module: "nodenext".
  2. Crea packages/lib que extienda la base, con composite: true y una funcion saludar(nombre: string): string.
  3. Crea apps/app que extienda la base, con noEmit: true y una reference a lib.
  4. Declara en el raiz un tsconfig con files: [] y references a los dos proyectos.
  5. Ejecuta tsc -b . --verbose y verifica el orden.

Solucion paso a paso:

packages/lib/src/index.ts
export function saludar(nombre: string): string {
  return `Hola, ${nombre}`;
}
apps/app/src/main.ts
import { saludar } from "@acme/lib";

const msg: string = saludar("Equipo"); // ✅ tipos desde lib
console.log(msg);
apps/app/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "noEmit": true
  },
  "references": [{ "path": "../../packages/lib" }],
  "include": ["src"]
}
tsconfig.json (raiz)
{
  "files": [],
  "references": [
    { "path": "./packages/lib" },
    { "path": "./apps/app" }
  ]
}
Comandos
pnpm install
tsc -b . --verbose   # deberias ver lib compilando antes que app

8 · Reto

Reto

Anade un tercer proyecto packages/utils que dependa SOLO de packages/lib (funcion doble), y haz que apps/app use ambos. Integra packages/utils en la raiz y verifica con tsc -b . --dry que el orden es lib → utils → app. Pista: references de cada proyecto debe reflejar exactamente sus dependencias; el grafo lo ordena TypeScript, no tu.

9 · Resumen

  • Project references convierten cada paquete en un proyecto con dependencias declaradas.
  • composite: true es obligatorio en lo referenciado e implica declaration + incremental.
  • tsc -b construye el grafo en orden topologico con cache ( --dry, --force, --clean).
  • extends hereda config (TS 5.0 permite arrays); los paths relativos se resuelven en su fichero de origen.
  • La raiz con files: [] solo orquesta; apps con noEmit chequean sin emitir.
  • pnpm workspace:* enlaza los paquetes locales.

10 · Preguntas frecuentes

¿Por que composite obliga a declaration e incremental?

Porque un proyecto referenciado debe poder entregar tipos (.d.ts) y saber si su salida sigue vigente (huella incremental). Sin eso, el modo build no puede decidir cuando recompilar a los consumidores. Son una restriccion del diseno, no un capricho.

¿Puedo comprobar tipos sin emitir en un proyecto composite?

Si: composite: true con noEmit: true esta soportado en modo build. El proyecto se comprueba y no escribe JavaScript; util en apps cuyo bundle genera Vite (o un bundler ajeno a tsc).

¿Que pasa con los ficheros tsbuildinfo?

Son caches de build: no se comitean. Puedes reubicarlos con tsBuildInfoFile (por ejemplo a node_modules/.tmp) y anadirlos al ignore. En CI determinista, suelen regenerarse en cada ejecucion o restaurarse desde cache.

¿extends acepta varias configuraciones base?

Desde TypeScript 5.0 si: "extends": ["a", "b"]. Funciona como una cadena (b extiende a a) y en conflictos gana la ultima. Muy util para combinar una base generica de la comunidad (@tsconfig/strictest) con la tuya propia.

¿Tengo que usar composite en la raiz que solo orquesta?

No: la raiz con files: [] es un "pasaporte" que no emite nada; solo apunta a los proyectos reales con references. El modo build la trata como punto de entrada del grafo.

¿Y si CI solo quiere tipos y no artefactos?

Un script typecheck con tsc -b . --pretty false desde la raiz da el chequeo completo del grafo sin tocar artefactos de build (las apps con noEmit no escriben nada; las librerias si, y eso esta bien para detectar roturas en sus .d.ts). En el modulo 12, leccion 4, veras esto desplegado en CI.
