Build de produccion y despliegue

Modulo 9 · Proyecto final 🕐 40 minutos Proyecto

1 · Introduccion

El viaje termina: pasar la app al mundo. Un build de produccion optimiza el bundle y desplegarlo lo publica en internet. Con TypeScript en el proceso, el build falla antes de salir si hay errores de tipos, y las variables de entorno se tipan para no arriesgar secretos.

El problema que resuelve: el codigo de desarrollo (HMR, source maps, modo dev) no sirve en produccion. Vite empaqueta, minifica y genera assets con hash; TypeScript garantiza que lo que entregas es consistente a nivel de tipos.

Cuando se utiliza
  • Antes de cada despliegue (CI/CD).
  • Para verificar el bundle final antes de publicar.
  • Con variables de entorno tipadas (VITE_API_URL, etc.).
  • En hosting estaticos (Netlify, Vercel, GitHub Pages, un servidor propio).

2 · Teoria

La analogia: la mudanza de la casa

Empaquetar una casa para mudarse no es "copiar todo en cajas sin mirar": revisas que no falte lo importante, compactas cajas (minificacion), etiquetas con hashes para que la camioneta (el navegador) las identifique y solo son recogidas una vez (cache long-lived). El build de Vite hace de mudanza: revisa (tsc), compacta (Rollup) y firma (hashes).

El build tipico

pnpm build

Que ejecuta dos pasos encadenados:

pnpm build │ ├─ tsc -b ──► comprueba tipos (el proyecto final: strict) │ ├─ si hay ERROR de tipos: se detiene ✗ │ └─ si va bien: continua ✓ │ └─ vite build ──► empaqueta y optimiza (Rollup) ├─ JS + CSS minificados ├─ assets con hash en el nombre └─ índice HTML resultante en dist/

Que produce: la carpeta dist

dist/
├── index.html
└── assets/
    ├── index-abc123.js     ← bundle con hash (cache infinita)
    ├── index-def456.css
    └── otros assets
  • Los nombres con hash permiten al navegador cachear para siempre: si cambia el contenido, cambia el hash.
  • La compresion la hace el hosting (gzip/brotli); puedes anadir vite-plugin-compression.
  • El build es inmutable: cada despliegue es una version distinta.

Variables de entorno tipadas

Vite expone las variables VITE_ en import.meta.env. Las tipamos en un .d.ts:

// src/vite-env.d.ts (o un env.d.ts propio)
interface ImportMetaEnv {
  readonly VITE_API_URL: string;
  readonly VITE_MODE: "dev" | "prod";
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}

// Uso tipado:
const url: string = import.meta.env.VITE_API_URL; // ✅
Precaucion con secretos

Solo las variables con prefijo VITE_ llegan al cliente y son publicas. Nunca pongas claves de servidor (tokens de pago, DB) en el frontend: cualquier secreto VITE_ queda en el bundle y es visible. Los secretos reales viven en el servidor/backend.

Ver el bundle de produccion en local

pnpm build
pnpm preview    # sirve dist/ en local para revisarlo antes de publicar

Desplegar en hosting estatico

# Ejemplos de comandos (Vercel/Netlify usan la config en su panel):
# Netlify:   build: "pnpm build",  publish: "dist"
# Vercel:    build: "pnpm build",  output: "dist"
# GitHub Pages: publica la carpeta dist/
SPA y rutas

Si usas React Router, el hosting debe reescribir las rutas a index.html (fallback). En hosting estaticos se configura un fichero (_redirects en Netlify, vercel.json, etc.) para que /pedidos/123 cargue index.html.

3 · Ejemplo minimo

comandos (scripts del proyecto)
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview"
  }
}

Linea a linea:

  • dev: servidor de desarrollo con HMR.
  • build: dos pasos — tipos primero, bundle despues.
  • preview: sirve el build de produccion para comprobarlo.
  • En CI: pnpm build es la puerta de cada despliegue.

4 · Ejemplo real

Una configuracion de build lista para el proyecto final: entorno tipado, análisis del bundle y despliegue a Vercel.

.env.production
VITE_API_URL=https://mi-api.ejemplo.dev
src/api.ts (usando la variable tipada)
import type { Tarea } from "./domain/tarea";

const API_URL: string = import.meta.env.VITE_API_URL;

export async function fetchTareas(): Promise<Tarea[]> {
  const res = await fetch(`${API_URL}/tareas`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json() as Tarea[];
}
package.json (build tipado con CI)
{
  "scripts": {
    "dev": "vite",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "build": "tsc -b && vite build",
    "preview": "vite preview"
  }
}
.github/workflows/deploy.yml (ejemplo)
on:
  push:
    branches: [main]
jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
      - run: pnpm install
      - run: pnpm test       # 1. tests
      - run: pnpm build      # 2. tipos + bundle
      - uses: actions/deploy-pages@v4  # 3. publica dist/

Decisiones:

  • typecheck y test separados: cada red por su cuenta en CI.
  • pnpm build corre tsc -b primero: un error de tipos rompe el CI.
  • La variable VITE_API_URL se tipa en env.d.ts y se usa segura.
  • El deploy solo ocurre cuando tests + tipos + bundle pasan.

5 · Buenas practicas

  • Haz pnpm test + pnpm typecheck + pnpm build en el CI, en ese orden.
  • Tipa import.meta.env en env.d.ts: nada de any.
  • Nunca pongas secretos con VITE_; todo sufijo visible va al bundle.
  • Revisa pnpm preview antes de desplegar: es lo que vera el usuario.
  • Configura el fallback de rutas del SPA en el hosting.

Que evitar

  • Desplegar sin pasar tsc -b (el build te "miente" de tipos).
  • Cometer un secreto de servidor en el frontend.
  • Publicar dist/ conflictiva con cache: los hashes lo resuelven solos.
  • Ignorar el reporte de tamano del bundle sin mirarlo.

6 · Errores habituales

Mal — build sin comprobar tipos 
{
  "scripts": {
    "build": "vite build" // ✖ no valida tipos antes de empaquetar
  }
}
Bien — tsc -b primero 
{
  "scripts": {
    "build": "tsc -b && vite build" // ✅
  }
}
Mal — secreto en VITE_ 
# ✖ esto es publico en el bundle:
VITE_DB_PASSWORD=supersecreto
Bien — secretos fuera del cliente 
# Los secretos van en el servidor/backend; solo expon lo publico:
VITE_API_URL=https://api.mi-servicio.dev
Mal — rutas del SPA sin fallback 
// /detalle/123 da 404 en hosting estatico sin rewrite
Bien — fallback a index.html 
/* /index.html 200     (Netlify _redirects)
// o vercel.json: { "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }

8 · Reto

Reto

Despliega el proyecto final en un hosting estatico gratuito (Netlify, Vercel o GitHub Pages) conectando el repo, y comprueba que el SPA con rutas (si tienes una ruta /detalle) funciona al recargar. No mires la guia del hosting: resolvelo con lo aprendido (build, dist, env, fallback).

9 · Resumen

  • pnpm build = tsc -b (tipos) + vite build (bundle optimizado).
  • Assets con hash = cache segura e inmutable.
  • Variables VITE_ tipadas en env.d.ts; nunca secretos.
  • CI: test + typecheck + build antes de desplegar.
  • Configura el fallback del SPA en el hosting.

10 · Preguntas frecuentes

¿Para que sirve tsc -b en el build si Vite transpila con esbuild?

Esbuild solo borra tipos y empaqueta; no los valida. tsc -b es la red de seguridad de tipos en el pipeline. Sin el, un error de tipos pasaria a produccion.

¿Se pueden servir los secretos del backend en el frontend?

No. Todo lo que llega al navegador es publico. Los secretos reales se gestionan en el servidor o en functions (Netlify Functions, Vercel Edge...), no en el bundle.

¿El hash de los assets se regenera en cada build?

Si, cuando el contenido cambia. Asi el navegador renueva el archivo correcto y mantiene en cache los que no cambiaron. Es cache "inmutable" y segura.

¿Que hosting elegir para este proyecto?

Para estaticos: GitHub Pages (si no tienes rutas profundas), Netlify o Vercel (con SPA fallback). Todos conectan con git y generan la preview por PR.

¿Necesito configurar el fallback de rutas siempre?

Solo si usas routing del cliente (React Router) con rutas profundas que el usuario recarga. Para una pagina sencilla sin rutas, no hace falta.

¿El despliegue es un static hosting suficiente para mi API?

Si tu logica vive en localStorage o en una API externa, si: el frontend es solo estatico. Si tu backend es propio, despliegas la API aparte y apuntas VITE_API_URL a ella.
