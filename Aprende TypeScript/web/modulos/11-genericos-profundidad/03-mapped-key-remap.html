Mapped types y remapeo de claves

Modulo 11 · Genericos en profundidad 🕐 35 minutos

1 · Introduccion

En el modulo 5 viste los mapped types: { [K in keyof T]: ... } recorre las claves de un objeto y construye otro con la misma forma. Aqui los llevamos al siguiente nivel con el remapeo de claves: ya no solo transformamos el valor, tambien podemos renombrar, filtrar o preservar cada clave usando as. Es la tecnica detras de utilidades como Patial y Pick escritas a mano, de tablas de configuracion derivadas de un as const, y de familias de metodos generadas (Getters, Setters).

  • Homomorphic mapped types: conservan la forma (y los modificadores) de T.
  • Remapeo con as: [K in keyof T as ...] para renombrar, filtrar o mantener claves.
  • Filtros por valor: excluir claves cuyo tipo no encaje (solo strings, solo funciones...).
  • Prefijos y generacion: crear getX, setX, leerX a partir de x.
  • as const + mapped: convertir un objeto de configuracion en tipos derivados y consistentes.
Cuando se utilizan
  • APIs de estado (selectores, setters) que se generan de un solo modelo.
  • Esquemas de configuracion donde quieres que el tipo "crezca" con el objeto const.
  • Tipos de etiquetas, prefijos o "metadatos de clave" para i18n, formularios o rutas.
  • Filtras claves por el tipo de su valor (solo numeros, solo booleanos...).

2 · Teoria

Homomorphic mapped types: recordar la forma

Un mapped type es homomorfico cuando recorre keyof T de un unico parametro T: { [K in keyof T]: X }. El compilador lo trata de forma especial: conserva los modificadores del original (una propiedad readonly o ? se mantiene como estaba) y si T es una union de objetos, el resultado se reparte por cada miembro. Manos a la obra: 

// Partial a mano: todas las claves opcionales, mismo tipo de valor.
type Parcial<T> = { [K in keyof T]?: T[K] };

// Pick a mano: solo un subconjunto de claves.
type MiPick<T, K extends keyof T> = { [P in K]: T[P] };

// Readonly a mano: todas las claves inmutables.
type Congelado<T> = { readonly [K in keyof T]: T[K] };

interface Perfil {
  nombre: string;
  edad: number;
}

type ParcialPerfil = Parcial<Perfil>; // { nombre?: string; edad?: number }
type SoloNombre = MiPick<Perfil, "nombre">; // { nombre: string }
Por que "homomorfico" importa

Como el mapped type "recuerda" la forma de T, al componer dos utilidades los modificadores se respetan: Parcial<Congelado<Perfil>> conserva el readonly de cada propiedad y anade el ?. Si escribieras { [K in keyof T]: ... } con dos parametros o con claves que no vienen de keyof T, ese comportamiento homomorfico desapareceria y los modificadores se perderian.

Remapeo de claves con as

La clausula as en un mapped type reescribe el nombre de la clave. Es como una cinta transportadora que pasa cada etiqueta por una maquina: lo que sale de la maquina es el nuevo nombre. Puedes prefijar, renombrar con template literals, o eliminar devolviendo never (una clave never no se incluye). 

// Prefijar: cada clave pasa a "opcional_" + clave.
type ConPrefijo<T> = { [K in keyof T as `opcional_${string & K}`]: T[K] };

// Filtrar por valor: solo quedan las claves cuyo tipo sea string.
type SoloStrings<T> = { [K in keyof T as T[K] extends string ? K : never]: T[K] };

interface Ficha {
  codigo: number;
  etiqueta: string;
  activo: boolean;
}

type Prefijada = ConPrefijo<Ficha>;  // { opcional_codigo: number; opcional_etiqueta: string; ... }
type Textual = SoloStrings<Ficha>;   // { etiqueta: string }
El truco de string & K

keyof T puede incluir number y symbol, pero los template literals solo aceptan strings. Con string & K recortas cada clave a su parte textual: las claves numericas/simbolicas se descartan en el renombrado. Sin ese recorte, el compilador rechaza la plantilla por "no asignable a string".

Generar metodos: Getters y Setters

Si podemos reescribir nombres, tambien podemos generar firmas completas. De un modelo de datos derivamos un tipo de selectores (getNombre()) y otro de actualizadores (setEdad(v)). Capitalize convierte la primera letra a mayuscula, dandonos get + Nombre. 

type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type Setters<T> = {
  [K in keyof T as `set${Capitalize<string & K>}`]: (valor: T[K]) => void;
};

interface Config {
  nombre: string;
  puerto: number;
}

type Accesos = Getters<Config>;
// { getNombre(): string; getPuerto(): number }

type Mutadores = Setters<Config>;
// { setNombre(valor: string): void; setPuerto(valor: number): void }
Capitalize y amigos

Capitalize, Uncapitalize, Uppercase y Lowercase son tipos de utilidad de template literals (TypeScript 4.1+). Se usan igual que funciones de string en el nivel de tipos: Capitalize<"nombre"> es "Nombre". Son la pieza que faltaba para "generar" nombres de metodos.

as const + mapped: tablas de configuracion

El patron mas rentable: declaras la configuracion como const ... as const (literales congelados) y derivas los tipos de ese objeto. Cambia el objeto, cambia el tipo; no puedes desincronizar el codigo de la configuracion. 

const PERMISOS = {
  lectura:  { nivel: 1, descripcion: "solo leer" },
  escritura: { nivel: 2, descripcion: "leer y escribir" },
  admin:     { nivel: 3, descripcion: "todo" },
} as const;

type ClavePermiso = keyof typeof PERMISOS; // "lectura" | "escritura" | "admin"

// Mapear cada permiso a una tupla con su nivel y su rol de acceso:
type NivelDe<K extends ClavePermiso> = (typeof PERMISOS)[K]["nivel"];
type MapaNiveles = { [K in ClavePermiso]: NivelDe<K> };
// { lectura: 1; escritura: 2; admin: 3 }

Tambien puedes prefijar y filtrar sobre el as const: por ejemplo, generar "validadores" (validarLectura, validarEscritura...) a partir de las claves, o sacar solo las que tienen nivel par con un condicional en el as.

3 · Ejemplo minimo

remapeo-minimo.ts
// 1) Homomorfico: todas las claves opcionales (mini Partial).
type Opcional<T> = { [K in keyof T]?: T[K] };

interface Boton {
  texto: string;
  ancho: number;
  deshabilitado: boolean;
}

// 2) Prefijar con as.
type ConPrefijo<T> = { [K in keyof T as `dato_${string & K}`]: T[K] };
type BotonPrefijado = ConPrefijo<Boton>; // { dato_texto: string; dato_ancho: number; ... }

// 3) Filtrar por valor: solo numeros.
type SoloNumeros<T> = { [K in keyof T as T[K] extends number ? K : never]: T[K] };
type NumerosDeBoton = SoloNumeros<Boton>; // { ancho: number }

Linea a linea:

  • { [K in keyof T]?: T[K] }: el ? en el sitio de la clave la vuelve opcional.
  • as `dato_${string & K}`: el template reescribe el nombre; las claves no textuales se descartan.
  • El as con condicional: si T[K] es number, se queda (K); si no, never la elimina.
  • Nada de esto existe en runtime: son solo tipos que guian al compilador.

4 · Ejemplo real

Una tienda tipada: parte de un modelo de estado, generamos selectores y actualizadores con mapped types, y definimos los estados de un pedido con as const + remapeo para obtener un mapa de transiciones.

tienda-generada.ts
// 1) Modelo de estado unico.
type Estado = {
  usuario: { id: number; nombre: string };
  carrito: string[];
  tema: "claro" | "oscuro";
};

// 2) Selectores generados: leerUsuario, leerCarrito, leerTema.
type Selector<T> = {
  [K in keyof T as `leer${Capitalize<string & K>}`]: () => T[K];
};

// 3) Actualizadores generados: ponerUsuario, ponerCarrito, ponerTema.
type Actualizador<T> = {
  [K in keyof T as `poner${Capitalize<string & K>}`]: (valor: T[K]) => void;
};

// Implementacion manual (los tipos derivados documentan la API):
const accesos: Selector<Estado> = {
  leerUsuario: () => ({ id: 1, nombre: "Ana" }),
  leerCarrito: () => ["botella", "taza"],
  leerTema: () => "claro",
};

const cambios: Actualizador<Estado> = {
  ponerUsuario: (usuario) => console.log("usuario:", usuario),
  ponerCarrito: (carrito) => console.log("carrito:", carrito.length),
  ponerTema: (tema) => console.log("tema:", tema),
};

// 4) Estados del pedido con as const + remapeo para transiciones.
const ESTADOS = {
  pendiente: "pendiente",
  enviado: "enviado",
  entregado: "entregado",
} as const;

type ClaveEstado = keyof typeof ESTADOS;

// Una funcion por estado: desdePendiente, desdeEnviado, desdeEntregado.
type Transiciones = {
  [K in ClaveEstado as `desde${Capitalize<K>}`]: () => string;
};

const mapaTransiciones: Transiciones = {
  desdePendiente: () => "revisando",
  desdeEnviado: () => "en reparto",
  desdeEntregado: () => "completado",
};

// 5) Solo los estados cuyo codigo tiene al menos 8 letras (filtro en el as).
type EstadosLargos = {
  [K in ClaveEstado as K extends `${string}${string}${string}${string}${string}${string}${string}${string}${infer _}`
    ? K
    : never]: (typeof ESTADOS)[K];
};
// { pendiente: "pendiente"; entregado: "entregado" } ("enviado" tiene 7 letras y se filtra)

Decisiones:

  • Un unico modelo Estado genera toda la API: nunca se desincroniza el nombre del campo con su selector/actualizador.
  • leer${Capitalize} y poner${Capitalize} producen nombres legibles y autodocumentados en el editor.
  • El as const de ESTADOS congela los literales; el remapeo crea desdePendiente sin tablas duplicadas.
  • El filtro del ultimo tipo comprueba la longitud con template literal: la parte variable (infer _) solo sirve para exigir 8+ caracteres y se descarta; "enviado" (7 letras) se filtra.
  • Si alguien anade un estado o una propiedad del modelo, los tipos derivados cambian solos y el const/implementacion que falte rompe en compilacion.

5 · Buenas practicas

  • Manten T como unico parametro para conservar el comportamiento homomorfico (modificadores, distribucion en unions).
  • Usa string & K antes de meter claves en template literals; evita errores de asignabilidad.
  • Deriva tipos de un as const central: el codigo que consume la configuracion nunca queda desactualizado.
  • Deja un comentario con el "antes y despues" de un remapeo (Ficha → ConPrefijo<Ficha>) para que el lector vea la transformacion rapido.
  • Empieza por el patron mas simple (Parcial/Pick a mano) antes de lanzarte a prefijos y filtros.

Que evitar

  • Olvidar as const en el objeto origen: sin el, los literales se ensanchan a string y el remapeo pierde precision.
  • Filtrar con any: T[K] extends any ? K : never deja pasar todo y no filtra nada.
  • Prefijos innecesarios que inflan el arbol de tipos; usa remapeo cuando el nombre aporte semantica, no por costumbre.
  • Un mapped type enorme por cada caso: mejor reutilizar parametros K extends keyof T y utilidades base (Parcial, MiPick) como piezas.

6 · Errores habituales

Mal — template literal con clave que puede ser number/symbol 
type Roto = { [K in keyof T as `x_${K}`]: T[K] }; // ✖ K no es string segun TS
Bien — recortar con string & K 
type Correcto = { [K in keyof T as `x_${string & K}`]: T[K] }; // ✅
Mal — filtrar sin condicional en el as (no elimina nada) 
type SoloFun = { [K in keyof T]: T[K] extends () => void ? T[K] : never }; // deja las claves, no las elimina
Bien — never en el as elimina la clave 
type SoloFun = {
  [K in keyof T as T[K] extends () => void ? K : never]: T[K];
}; // ✅ solo las claves con funciones
Mal — mapped tipo con dos parametros y perder homomorfismo 
type Raro<T, U> = { [K in keyof T]: U }; // U hace que T pierda su forma exacta
Bien — transformaciones sobre un solo parametro 
type Espejo<T> = { [K in keyof T]: T[K] }; // homomorfico: conserva modificadores

7 · Ejercicio guiado

Implementa Getters y Setters a mano para un registro de usuario, y verifica que los nombres generados se ven en el editor.

  1. Define interface Perfil { nombre: string; edad: number }.
  2. Crea type Getters<T> con as `get${Capitalize<string & K>}`.
  3. Crea type Setters<T> con as `set${Capitalize<string & K>}`.
  4. Declara const accesos: Getters<Perfil> y completa sus cuatro metodos.
  5. Comprueba que una clave inexistente (getApellidos) falla al escribirse.

Solucion paso a paso:

ejercicio-getters-setters.ts
interface Perfil {
  nombre: string;
  edad: number;
}

type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type Setters<T> = {
  [K in keyof T as `set${Capitalize<string & K>}`]: (valor: T[K]) => void;
};

const accesos: Getters<Perfil> = {
  getNombre: () => "Ana",
  getEdad: () => 30,
};

const cambios: Setters<Perfil> = {
  setNombre: (nombre) => console.log(nombre),
  setEdad: (edad) => console.log(edad * 2),
};

// const bug: Getters<Perfil> = { getApellidos: () => "x" }; // ✖ no existe en el tipo

8 · Reto

Reto

Escribe un OpcionalProfundo<T> que recorra objetos anidados y vuelva opcionales todas las propiedades, recursivamente. Despues, anade una variante SoloLecturaProfundo<T>. Pista: cada nivel debe comprobar si T[K] es un objeto (con T[K] extends object) antes de recursar; el caso base devuelve el mismo valor sin tocar. No resuelvas la recursion con any: perderias el objetivo.

9 · Resumen

  • Los mapped types homomorficos ({ [K in keyof T]: ... }) conservan forma y modificadores.
  • [K in keyof T as ...] remapea nombres: prefijar con template literals o eliminar con never.
  • string & K recorta claves para los template literals y evita errores.
  • Getters/Setters y demas utilidades derivadas se construyen con Capitalize + as.
  • as const + mapped convierte una configuracion en un conjunto de tipos consistente y siempre sincronizado.

10 · Preguntas frecuentes

¿Que es un mapped type homomorfico exactamente?

Es aquel que recorre keyof T con un unico parametro T. TypeScript lo trata de forma especial: conserva los modificadores readonly/? y distribuye sobre unions. Si usas dos parametros o claves foraneas, pierdes ese comportamiento.

¿Por que necesito string & K en el remapeo?

Porque keyof T puede incluir claves numericas y simbolicas, y un template literal solo acepta strings. string & K intersecciona cada clave con el tipo string: lo que no es string se descarta y el template compila.

¿Como elimino claves con as?

Devolviendo never en la reescritura: [K in keyof T as K extends algo ? K : never]. Una clave never no aparece en el tipo resultante, y el valor T[K] se conserva para las que si pasan.

¿Por que usar as const antes de un mapped sobre configuracion?

Sin as const los literales se ensanchan ("lectura" se vuelve string) y el remapeo y las claves pierden precision. Con as const cada valor queda literal y el tipo derivado refleja exactamente lo declarado.

¿Puedo remapear claves que son propiedades opcionales o readonly?

Si: el remapeo afecta al nombre, no a los modificadores. El readonly y el ? se heredan de la clave original en los tipos homomorficos, y puedes anadir mas con readonly/? en el propio mapped type.

¿Los mapped types afectan al rendimiento del compilador?

Poco en tipicos casos (objetos de docenas de claves). El coste crece con objetos enormes o con recursion profunda (como OpcionalProfundo) sobre tipos grandes. Manten los objetos de configuracion pequenos y la recursion acotada, y el impacto sera minimo.
