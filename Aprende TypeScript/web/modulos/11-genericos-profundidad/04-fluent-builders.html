Builder tipado: fluent APIs con genericos

Modulo 11 · Genericos en profundidad 🕐 35 minutos

1 · Introduccion

El patron builder encadena llamadas: builder.pasoA().pasoB().construir(). En JavaScript puro es comodo pero peligroso — nada impide llamar a construir() sin haber configurado lo obligatorio, o invocar los pasos en cualquier orden. Esta leccion muestra como los genericos convierten ese encadenamiento en una API que se verifica sola: el compilador conoce el "estado" del builder y solo deja llamar al metodo siguiente (o solo a los pasos que faltan).

  • Estados tipados: cada paso devuelve un tipo distinto, de modo que el metodo siguiente solo existe en ese momento (PasoInicio → PasoUrl → PasoListo).
  • Agotar pasos: el builder "consume" etapas; el orden queda codificado en los tipos.
  • A cumulador generico: en vez de pasos fijos, un generico T crece con cada llamada (Builder<{}> → Builder<{ url: string }>).
  • Option-object con keyof/as const: opciones tipadas desde una tabla de configuracion.
  • El orden cambia el tipo: la secuencia de llamadas se refleja en el acumulador, y un construir() puede exigir que todo lo obligatorio exista.
Cuando se utilizan
  • Consultas SQL o DSLs donde el orden importa (SELECT antes que FROM).
  • Peticiones HTTP, configuracion de pedidos, formularios con etapas.
  • API publicas de librerias donde queremos que el usuario "no pueda equivocarse".
  • Construccion de objetos con decenas de campos opcionales/obligatorios.

2 · Teoria

El problema sin estados

Un builder clasico tiene todos los metodos desde el principio. El usuario puede llamar a construir() con la mitad de la configuracion, y el error solo aparece en runtime (o nunca). Los genericos atacan ese problema: el "estado" del builder es un tipo, y cada metodo te devuelve el siguiente estado. 

// Sin tipos de estado: todos los metodos disponibles siempre.
class PedidoSinChequeo {
  marca = ""; tamano = "";
  eligeMarca(m: string) { this.marca = m; return this; }
  eligeTamano(t: string) { this.tamano = t; return this; }
  construir() { return `${this.marca} ${this.tamano}`; }
}
const roto = new PedidoSinChequeo().construir(); // " " — compila y falla en runtime

Maquina de pasos tipada

La primera cura: en vez de devolver siempre this, cada metodo devuelve un tipo de interfaz con solo los metodos del siguiente paso. El encadenamiento "agota" los pasos: al llegar al ultimo, el metodo construir() existe; antes, no. 

interface PasoMarca {
  eligeMarca(m: "nike" | "adidas" | "puma"): PasoTamano;
}
interface PasoTamano {
  eligeTamano(t: 38 | 40 | 42): PasoListo;
}
interface PasoListo {
  construir(): Zapatilla;
}

interface Zapatilla { marca: string; tamano: number }

class PedidoBuilder implements PasoMarca, PasoTamano, PasoListo {
  private marca = "";
  private tamano = 0;

  eligeMarca(m: "nike" | "adidas" | "puma"): PasoTamano {
    this.marca = m;
    return this; // el tipo de retorno es PasoTamano, no PedidoBuilder
  }
  eligeTamano(t: 38 | 40 | 42): PasoListo {
    this.tamano = t;
    return this;
  }
  construir(): Zapatilla {
    return { marca: this.marca, tamano: this.tamano };
  }
}

const ok = new PedidoBuilder().eligeMarca("nike").eligeTamano(42).construir();
// new PedidoBuilder().construir();        // ✖ construir no existe aun
// new PedidoBuilder().eligeTamano(40);    // ✖ eligeTamano no existe sin eligeMarca
Analogia: la maquina expendedora

Piensa en una maquina de cafe: primero introduces el vaso (paso 1), luego eliges el tipo (paso 2), y solo entonces aparece el boton "servir". La maquina esconde los botones hasta que toca. Un builder con estados tipados hace lo mismo: el editor de codigo solo te ofrece el metodo que corresponde al paso en el que estas.

El acumulador generico: crecer con cada llamada

La segunda cura es mas flexible: en vez de pasos fijos, un generico T acumula lo configurado. Cada metodo devuelve Builder<T & { nuevaPropiedad: ... }>. El orden de las llamadas se refleja literalmente en el tipo del acumulador, y construir() puede exigir completitud con un condicional. 

// La "forma completa" que exigimos al final.
interface Completo {
  destino: string;
  asunto: string;
}

class Correo<T extends object> {
  private constructor(private readonly datos: T) {}

  static enBlanco(): Correo<{}> {
    return new Correo({});
  }

  para(destino: string): Correo<T & { destino: string }> {
    return new Correo({ ...this.datos, destino });
  }

  conAsunto(asunto: string): Correo<T & { asunto: string }> {
    return new Correo({ ...this.datos, asunto });
  }

  // Solo compila cuando T ya contiene todo lo obligatorio.
  enviar(): T extends Completo ? string : never {
    return `${this.datos.destino} :: ${this.datos.asunto}` as T extends Completo ? string : never;
  }
}

const enviado: string = Correo.enBlanco().para("ana@mail.com").conAsunto("Hola").enviar();
// const incompleto: string = Correo.enBlanco().para("ana@mail.com").enviar();
// ✖ el retorno es never (T no es Completo): la llamada no compila al usarse como string
Por que intentersection en el acumulador

T & { destino: string } "suma" la propiedad nueva a las que ya habia. Si llamas .para(...).conAsunto(...) el acumulador es { destino: string } & { asunto: string }; si inviertes el orden, { asunto: string } & { destino: string }. Estructuralmente son equivalentes, pero el tipo del editor muestra exactamente en que orden configuraste: el estado y el generico viajan juntos.

Option-object con keyof y as const

El tercer ingrediente: opciones tipadas desde una tabla de configuracion con as const. En vez de "acepta cualquier string", el metodo solo admite claves reales de la tabla, y los valores se derivan de ella. 

const EXTRAS = {
  queso:   { precio: 1.5, vegano: false },
  champinones: { precio: 1.0, vegano: true },
  salsa:   { precio: 0.8, vegano: true },
} as const;

type ClaveExtra = keyof typeof EXTRAS;

class PedidoPizza {
  private extras: ClaveExtra[] = [];

  // Solo acepta claves existentes en EXTRAS.
  conExtra<K extends ClaveExtra>(...claves: K[]): this {
    this.extras.push(...claves);
    return this;
  }

  total(): number {
    return this.extras.reduce((acc, k) => acc + EXTRAS[k].precio, 0);
  }
}

const pedido = new PedidoPizza().conExtra("queso", "salsa");
// pedido.conExtra("anchoas"); // ✖ "anchoas" no esta en EXTRAS
console.log(pedido.total()); // 1.5 + 0.8

La firma <K extends ClaveExtra> hace que cada argumento compruebe su clave, y EXTRAS[k].precio queda tipado como numero porque el as const conserva los literales.

3 · Ejemplo minimo

builder-minimo.ts
// Cuatro pasos: tipo → tamano → ingrediente → construir.
interface Paso1 {
  eligeTipo(t: "clasica" | "integral"): Paso2;
}
interface Paso2 {
  eligeTamano(t: "pequena" | "mediana" | "grande"): Paso3;
}
interface Paso3 {
  eligeIngrediente(i: "jamon" | "queso"): Paso4;
}
interface Paso4 {
  construir(): string;
}

class SandwichBuilder implements Paso1, Paso2, Paso3, Paso4 {
  private tipo = "";
  private tamano = "";
  private ingrediente = "";

  eligeTipo(t: "clasica" | "integral"): Paso2 { this.tipo = t; return this; }
  eligeTamano(t: "pequena" | "mediana" | "grande"): Paso3 { this.tamano = t; return this; }
  eligeIngrediente(i: "jamon" | "queso"): Paso4 { this.ingrediente = i; return this; }
  construir(): string { return `${this.tipo} ${this.tamano} con ${this.ingrediente}`; }
}

const sandwich = new SandwichBuilder()
  .eligeTipo("clasica")
  .eligeTamano("mediana")
  .eligeIngrediente("jamon")
  .construir();
// new SandwichBuilder().eligeTamano("grande"); // ✖ el paso 2 no existe sin el paso 1

Linea a linea:

  • Cada interfaz solo expone el metodo del paso siguiente: al hacer return this, el tipo de retorno declarado es el de la interfaz, no el de la clase.
  • Los literales del union ("clasica" | "integral") se completan en el editor.
  • construir() solo existe en Paso4: llamarlo antes es imposible en compilacion.
  • La cadena es legible de arriba a abajo y documenta el flujo del pedido.

4 · Ejemplo real

Una peticion HTTP construida como fluent API: el orden de las etapas es obligatorio, las cabeceras se escriben con option-object, y un acumulador generico garantiza que la peticion este completa antes de enviar().

peticion-builder.ts
// Tabla de cabeceras permitidas (option-object tipado).
const CABECERAS = {
  "content-type": "application/json",
  "accept": "application/json",
  "authorization": "Bearer abc",
} as const;
type ClaveCabecera = keyof typeof CABECERAS;

// La peticion "completa" que enviar() exige.
interface PeticionCompleta {
  url: string;
  metodo: "GET" | "POST" | "PUT" | "DELETE";
}

class Peticion<T extends object> {
  private constructor(private readonly datos: T) {}

  static enBlanco(): Peticion<{}> {
    return new Peticion({});
  }

  // Cada etapa devuelve el siguiente estado de la maquina.
  conUrl<U extends string>(url: U): PasoMetodo<T & { url: U }> {
    return new PasoMetodo({ ...this.datos, url });
  }
}

class PasoMetodo<T extends object> {
  constructor(private readonly datos: T) {}

  conMetodo<M extends "GET" | "POST" | "PUT" | "DELETE">(
    metodo: M,
  ): PasoCabeceras<T & { metodo: M }> {
    return new PasoCabeceras({ ...this.datos, metodo });
  }
}

class PasoCabeceras<T extends object> {
  constructor(private readonly datos: T) {}

  conCabecera<K extends ClaveCabecera>(clave: K): PasoCabeceras<T> {
    console.log(clave, CABECERAS[clave]); // opcion tipada por keyof
    return this;
  }

  // El condicional exige completitud; el generico acumula el estado.
  enviar(): T extends PeticionCompleta ? Promise<unknown> : never {
    return fetch((this.datos as unknown as PeticionCompleta).url) as never;
  }
}

// Encadenamiento completo:
const respuesta = Peticion.enBlanco()
  .conUrl("https://api.example.com/pedidos")
  .conMetodo("POST")
  .conCabecera("content-type")
  .conCabecera("accept")
  .enviar();
// const respuesta: unknown = Peticion.enBlanco().conUrl("x").enviar();
// ✖ retorno never (falta metodo): no se puede asignar, el compilador lo marca

Decisiones:

  • Las clases PasoMetodo/PasoCabeceras implementan la maquina de pasos: cada clase devuelve la siguiente, asi el orden url → metodo → cabeceras → enviar queda en el tipo.
  • El generico T de Peticion se pasa por cada clase y se combina con & en cada etapa: al llegar a enviar(), T contiene url y metodo.
  • enviar(): T extends PeticionCompleta ? Promise<unknown> : never queda tipado cuando el acumulador es completo; si falta cualquier etapa el retorno es never y usar el resultado falla en compilacion.
  • conCabecera<K extends ClaveCabecera> limita las opciones a la tabla as const: el editor ofrece las cabeceras reales y rechaza las inventadas.
  • El flujo se lee como un documento: primero la URL, luego el metodo, luego opciones, y solo al final "enviar".

5 · Buenas practicas

  • Empieza con la maquina de pasos (interfaces por estado) si el orden debe ser estricto; usa el acumulador generico cuando el orden pueda variar pero la completitud sea obligatoria.
  • Nombra las interfaces de estado con proposito (PasoUrl, PasoMetodo) para que el editor autocomplete sea el propio diagrama del flujo.
  • Tipa las opciones con keyof + as const: menos strings sueltos y mas contratos verificables.
  • Manten el constructor privado y el punto de entrada estatico (enBlanco()): fuerza a comenzar por donde el tipo espera.
  • Documenta en el build()/enviar() la forma completa que exige, con el condicional tipado y un comentario de una linea.

Que evitar

  • Devolver this con el tipo de la clase en vez del de la interfaz: rompe la maquina de pasos (el compilador vuelve a ofrecer todo).
  • Maquinas de pasos con decenas de etapas: el arbol de interfaces se vuelve ilegible; agrupalos en 3-5 estados como maximo.
  • Acumular con any: matas el condicional de completitud y el autocompletado.
  • Option-object sin as const: las claves se ensanchan a string y se pierde el filtrado por keyof.
  • Validaciones de runtime duplicadas cuando el tipo ya las garantiza: el builder tipado te permite delegar en el compilador y validar solo el borde (API, JSON).

6 · Errores habituales

Mal — devolver this con el tipo de la clase 
class Builder {
  pasoA(): this { /* ... */ return this; } // el tipo es Builder: pasoB siempre existe
  pasoB(): this { /* ... */ return this; }
}
// new Builder().pasoB(); // ✖ pasa: no se han agotado los pasos
Bien — devolver el tipo de la interfaz del paso 
interface PasoA { pasoA(): PasoB }
interface PasoB { pasoB(): Listo }
class Builder implements PasoA, PasoB {
  pasoA(): PasoB { return this; }
  pasoB(): Listo { return this; }
}
// new Builder().pasoB(); // ✖ no existe: el compilador lo bloquea
Mal — condicional de completitud con any en el acumulador 
interface Requerido { nombre: string }
// T = any: "T extends Requerido" es verdadero siempre, el condicional no protege.
class PedidoMal<T extends any> {
  enviar(): T extends Requerido ? string : never {
    return "ok" as never;
  }
}
Bien — acumulador tipado y uso con variable tipada 
interface Requerido { nombre: string }
class Pedido<T extends object> {
  static enBlanco(): Pedido<{}> { return new Pedido(); }
  conNombre(n: string): Pedido<T & { nombre: string }> {
    return this as unknown as Pedido<T & { nombre: string }>;
  }
  enviar(): T extends Requerido ? string : never {
    return "ok" as never;
  }
}
const listo: string = Pedido.enBlanco().conNombre("Ana").enviar(); // ✅
// const roto: string = Pedido.enBlanco().enviar();
// ✖ el retorno es never (falta nombre): la llamada compila, el uso no
Mal — option-object sin as const 
const OPCIONES = { grande: 5, mediana: 3 }; // sin as const: valores number
// keyof typeof OPCIONES sigue siendo literal, pero los VALORES pierden precision
Bien — as const para valores literales 
const OPCIONES = { grande: 5, mediana: 3 } as const;
type Tamano = keyof typeof OPCIONES;              // "grande" | "mediana"
type Precio = (typeof OPCIONES)[Tamano];          // 5 | 3

7 · Ejercicio guiado

Construye un builder de confirmaciones por correo con tres pasos obligatorios y un option-object para el idioma.

  1. Declara interface PasoPara { para(email: string): PasoAsunto } y las siguientes interfaces PasoAsunto, PasoIdioma y PasoListo.
  2. Implementa la clase con implements de las cuatro interfaces.
  3. Define const IDIOMAS = { es: "es", en: "en", fr: "fr" } as const; y usa keyof typeof IDIOMAS en conIdioma.
  4. Comprueba que construir() solo aparece en PasoListo.
  5. Prueba que falla llamar conAsunto sin pasar antes por para.

Solucion paso a paso:

ejercicio-builder.ts
interface PasoPara {
  para(email: string): PasoAsunto;
}
interface PasoAsunto {
  conAsunto(asunto: string): PasoIdioma;
}
interface PasoIdioma {
  conIdioma(i: "es" | "en" | "fr"): PasoListo;
}
interface PasoListo {
  construir(): string;
}

const IDIOMAS = { es: "es", en: "en", fr: "fr" } as const;
type ClaveIdioma = keyof typeof IDIOMAS;

class Confirmacion implements PasoPara, PasoAsunto, PasoIdioma, PasoListo {
  private para = "";
  private asunto = "";
  private idioma: ClaveIdioma = "es";

  para(email: string): PasoAsunto { this.para = email; return this; }
  conAsunto(asunto: string): PasoIdioma { this.asunto = asunto; return this; }
  conIdioma(i: ClaveIdioma): PasoListo { this.idioma = i; return this; }
  construir(): string {
    return `[${IDIOMAS[this.idioma]}] ${this.para}: ${this.asunto}`;
  }
}

const mensaje = new Confirmacion()
  .para("ana@mail.com")
  .conAsunto("Bienvenida")
  .conIdioma("es")
  .construir();
// new Confirmacion().conAsunto("nada"); // ✖ conAsunto no existe sin para

8 · Reto

Reto

Combina lo aprendido: un builder de consultas SQL con orden libre entre etapas pero con ejecutar() que solo compile cuando se hayan elegido columnas (seleccionar) y tabla (desde). Usa un acumulador generico con dos marcas, por ejemplo Consulta<C extends string = never, T extends string = never>: seleccionar amplia la primera marca y desde la segunda (el encadenamiento va de Consulta<string, never> a Consulta<string, string>). La pista esta en el condicional de ejecutar(): T extends string ? ... : never comprueba que la tabla exista. No lo resuelvas con any.

9 · Resumen

  • Los estados tipados convierten el encadenamiento en una maquina de pasos: cada metodo devuelve solo las operaciones del siguiente estado.
  • Devolver this con el tipo de la interfaz (no de la clase) es la clave para "agotar" pasos.
  • El acumulador generico (Builder<T & { ... }>) crece con cada llamada y el orden de llamadas se refleja en el tipo.
  • construir()/enviar() pueden exigir completitud con un condicional tipado.
  • El option-object con keyof + as const limita las opciones a la tabla real de configuracion.

10 · Preguntas frecuentes

¿Por que devuelvo this y no la clase?

Porque el tipo de retorno declarado es el de la interfaz del paso, aunque el valor real sea this. El compilador ve la interfaz: solo los metodos de ese paso quedan visibles para la siguiente llamada. Asi se "agotan" los pasos.

¿Maquina de pasos o acumulador generico?

Maquina de pasos: orden estricto y facil de leer. Acumulador generico: orden flexible con completitud verificada. Una regla util: si el usuario puede saltarse una etapa, usa el acumulador; si no, usa la maquina.

¿Que pasa con builders que devuelven interfaz y necesitan pasar datos privados?

Las interfaces no declaran datos; la clase los guarda y las interfaces solo exponen metodos. Al devolver this, el objeto real sigue siendo el builder con sus campos, aunque su tipo publico sea el de la interfaz. No hay fuga de clases ni de privados.

¿Puedo mezclar los dos patrones en un builder?

Si, es frecuente: una maquina de pasos para las etapas obligatorias y un acumulador generico para las configuraciones opcionales que van creciendo. El ejemplo real de la peticion HTTP lo hace: estados para url/metodo y generico para la completitud final.

¿Ayuda esto al editor y al autocompletado?

Enormemente: al encadenar, el editor solo sugiere los metodos validos del paso actual, y si un parametro es un union de literales, los muestra como opciones. El autocompletado se convierte en la documentacion del flujo.

¿Cuando es excesivo?

Cuando hay un solo estado o pocas opciones: un objeto de opciones normal basta. El builder brilla con 3+ etapas o con campos obligatorios que se validan en el tipo; con menos, anade indireccion sin beneficio.
