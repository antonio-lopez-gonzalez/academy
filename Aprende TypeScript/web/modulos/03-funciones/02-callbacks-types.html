Callbacks y function types

Modulo 3 · Funciones 🕐 30 minutos

1 · Introduccion

En JavaScript las funciones son valores que se pasan, guardan y devuelven. TypeScript permite tiparlas igual que cualquier otro dato: un function type describe "que tipo de funcion" espera una firma. Esto es imprecindible para callbacks (en JS de toda la vida: arrays, eventos, fetch) y para APIs de librerias.

2 · Teoria

Function type

Un function type describe una firma como tipo, con parentesis adicionales:

type Calculadora = (a: number, b: number) => number;

const sumar: Calculadora = (a, b) => a + b;   // ✅ encaja
const restar: Calculadora = (a, b) => a - b;   // ✅ encaja
// sumar = (x: string) => x;                   // ✖ no es number

La flecha => separa parametros de retorno. Fijate: el tipo de una funcion se define por sus parametros y su retorno, no por su nombre.

Asignabilidad: compatible de dentro hacia fuera

Una funcion es asignable a otra si sus parametros y retorno son compatibles. Sorpresa util: una funcion con MENOS parametros es asignable a un tipo que espera mas (porque "ignora" los extra): 

type ConDos = (a: number, b: number) => number;
const soloUno: ConDos = (a) => a * 2; // ✅ valido: ignora b

Esto se ve en todos los callbacks de arrays: map llama al callback con 3 argumentos (elemento, indice, array) y casi nunca los usas todos. TypeScript lo permite por ser seguro (los argumentos extra se descartan).

Callbacks de funciones de orden superior

// funcion que recibe un callback tipado.
function procesar(n: number, cb: (valor: number) => number): number {
  return cb(n);
}

console.log(procesar(5, (v) => v * 2)); // 10

El parametro cb declara la forma del callback: "una funcion que recibe number y devuelve number". Quien llama decide la implementacion; el 'contrato' esta en la firma.

callbacks que devuelven void

type Evento = (detalle: { id: number }) => void;

function emitir(detalle: { id: number }, cb: Evento): void {
  cb(detalle);   // el callback hace un efecto secundario
}

Importante: para un tipo esperado que devuelve void, puedes pasar un callback que devuelve number (su retorno se ignora). Esta asimetria es intencional: nadie usa lo que un callback de eventos devuelve.

Callbacks asincronos

type OnComplete = (exito: boolean, error?: string) => void;

function cargar(url: string, onComplete: OnComplete): void {
  // Simulamos trabajo asincrono.
  setTimeout(() => onComplete(true), 100);
}

Con Promise, el idioma moderno tipa de forma distinta: la funcion devuelve Promise<T> en vez de recibir callback. Ambos existen; los callbacks se ven aun en eventos del DOM, middleware y APIs de algunos paquetes.

Function type vs interface de funcion

type Fn = (x: number) => string;
interface FnI { (x: number): string; }   // equivalente

Son intercambiables; el type es mas comun por brevedad.

3 · Ejemplo minimo

callbacks-minimo.ts
// Un tipo de callback simple.
type Transformar = (s: string) => string;

function aplicar(texto: string, t: Transformar): string {
  return t(texto);
}

// Tres callbacks que cumplen la firma:
const gritar: Transformar = (s) => s.toUpperCase();
const murmurar: Transformar = (s) => s.toLowerCase();
const duplicar: Transformar = (s) => s + s;

console.log(aplicar("hola", gritar));     // "HOLA"
console.log(aplicar("hola", duplicar));   // "holahola"

4 · Ejemplo real

Un mini-framework de suscripciones tipadas (como los que usan las librerias reales):

emitter.ts
// Un "listener" es un callback que recibe el dato del evento.
type Listener<T> = (dato: T) => void;

// Un evento con nombre y dato generico (avance del modulo 5).
interface EventoGenerico<K extends string, T> {
  nombre: K;
  /* la app registra un listener por evento */
}

// Sencillo emisor de eventos con un dict de listeners.
class Emisor<T extends string> {
  // Mapa: nombre de evento → array de listeners.
  private listeners: Record<T, Listener<unknown>[]> = {} as Record<
    T,
    Listener<unknown>[]
  >;

  // Registra un callback tipado para un evento.
  on<K extends T>(nombre: K, cb: Listener<unknown>): void {
    (this.listeners[nombre] ??= []).push(cb);
  }

  // Dispara los callbacks registrados.
  emit(nombre: T, dato: unknown): void {
    const lista = this.listeners[nombre] ?? [];
    lista.forEach((cb) => cb(dato));
  }
}

const bus = new Emisor<"usuario" | "compra">();
bus.on("usuario", (datos) => console.log("usuario:", datos));
bus.on("compra", (datos) => console.log("compra:", datos));
bus.emit("usuario", { id: 1 });

Decisiones:

  • Listener<T> como type function: define la forma de cada callback de forma reutilizable.
  • El generico T extends string limita los nombres de evento a un conjunto (avanza lo del modulo 5).
  • Los callbacks tipados hacen la API documentada: "si te suscribes, tu callback recibe unknown y decides como tratarlo".

5 · Buenas practicas

  • Tipa los callbacks con un type con nombre: type OnSuccess = (data: T) => void.
  • Usa void como retorno de callbacks "de efecto" (eventos, notificaciones).
  • Aprovecha que los callbacks pueden ignorar parametros: no declares mas de los que usas.
  • Para APIs asincronas modernas, preferi Promise<T> como retorno en vez de callbacks anidados.
  • Documenta el orden y significado de cada campo del callback.

Que evitar

  • Callbacks de tipo any o "Function": pierden todo el tipado del contenido.
  • Callback hell con muchos parametros posicionales: prefiere un objeto de opciones o un tipo estructurado.
  • Confundir parametros requeridos con opcionales en la firma: declara con ? lo que pueda faltar.

6 · Errores habituales

Mal — callback con el tipo equivocado 
type Cb = (n: number) => number;
function usa(cb: Cb) { return cb(10); }
usa((s: string) => s.length); // ✖ string no es number
Bien — callback coherente con la firma 
usa((n: number) => n * 2); // ✅
Mal — usar el retorno de un callback void 
function f(cb: () => void) {
  const r = cb(); // r es void: no puedes usarlo como numero
}
Bien — decidir el retorno en la firma o ignorarlo 
function f(cb: () => number) {
  const r = cb(); // r: number
}
Mal — alias "Function" genérico 
function f(cb: Function) { cb(1, 2); } // sin tipo de parametros: peligro
Bien — firma explicita 
function f(cb: (a: number, b: number) => number) { cb(1, 2); }

8 · Reto

Reto

Escribe una funcion encadenar(fns: readonly ((x: number) => number)[]) que devuelva una nueva funcion que aplique todas las fns en orden al argumento. Tipa correctamente el tipo de retorno (una (n: number) => number compuesta) y demuestra que puedes pasar callbacks sueltos y usar el resultado.

9 · Resumen

  • type Fn = (a: T, b: U) => R: un tipo de funcion = firma.
  • Las funciones son valores: se pasan, guardan y devuelven, y cada sitio puede exigir una firma.
  • Un callback con menos parametros es asignable (seguridad por descarte).
  • Para callbacks de efectos usa retorno void.
  • API asincrona moderna prefiere Promise<T>; callbacks siguen en eventos y middleware.

10 · Preguntas frecuentes

¿Por que puedo pasar un callback con menos parametros?

Por bivarianza de funciones en los tipos de JavaScript: el callback que recibes puede ser llamado con mas argumentos de los que usas. Como el exceso se ignora, es seguro. TypeScript lo permite por compatibilidad con JS.

¿Que diferencia de rigor hay entre retorno void y un callback que devuelve algo?

Si la firma espera void, puedes pasarle un callback que devuelva number: su retorno se ignora (escucha sin usar). El tipo void es "no mires lo que devuelvo".

¿Los callbacks pueden ser genericos?

Si. type Listener<T> = (dato: T) => void es generica. El parametro se instancia por llamada, como veremos en el modulo 5.

¿"Function" como tipo existe?

Si, pero es el tipo de "cualquier funcion" (any de funciones). Ningun tipado de contenido. Casi siempre es mejor declarar la firma explicita.

¿Puedo tipar el callback de un eventListener del DOM?

Si, los tipos DOM ya existen: addEventListener("click", (e: MouseEvent) => {}); TypeScript infiere el tipo del evento segun el nombre. Lo usaremos en el modulo 8 con React.
