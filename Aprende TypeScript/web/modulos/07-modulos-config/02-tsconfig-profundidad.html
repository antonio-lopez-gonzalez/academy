tsconfig.json en profundidad

Modulo 7 · Modulos y configuracion 🕐 30 minutos

1 · Introduccion

tsconfig.json es el cerebro de tu proyecto TypeScript: decide que archivos compila, a que estandar emite, cuan estricto es y como resuelve los imports. Entenderlo a fondo es lo que separa a quien "configura por tutorial" de quien configura con intencion.

El problema que resuelve: por defecto, tsc compila "todo lo que encuentra" con modo estricto apagado y salidas sorprendentes. El tsconfig te da el control completo para que tu codigo compile como esperas, en el formato que esperas, con las garantias que quieres.

Cuando se utilizan
  • Al crear proyectos (Vite, Node, librerias).
  • Para escalar reglas de validacion (strict, noUnusedLocals).
  • Para configurar bundlers (Vite delega el transpile a esbuild, pero TS sigue para tipos).
  • Para monorepos y project references (leccion 4).

2 · Teoria

La analogia: los paneles del coche

Un coche tiene decenas de paneles y luces. No los has de tocar a todos cada dia, pero saber que es cada uno te permite conducir mejor: el cinturon (strict), la alarma de limites (noUnusedLocals), el panel de cambio de velocidad (module/target). Configurar tsconfig es "conocer tu coche" antes de ir a maxima velocidad.

El proyecto base: extends hereda configuraciones

{
  "extends": "@tsconfig/node20/tsconfig.json",
  "compilerOptions": {
    "strict": true
  },
  "include": ["src"]
}

extends permite basarte en configuraciones compartidas (casillas de una libreria o equipo) y solo sobrescribir lo que difiere. Se resuelve en cascada y las opciones mas especificas ganan.

include, exclude y files

{
  "include": ["src/**/*"],       // que entra en el programa
  "exclude": ["node_modules", "dist", "test"], // que queda fuera
  "compilerOptions": { }
}
  • include: globs de archivos a compilar (los .ts, .tsx, .d.ts).
  • exclude: lista de excepciones sobre lo incluido.
  • files: lista explicita, para proyectos muy contenidos.

target y module

{
  "compilerOptions": {
    "target": "es2022",          // a que version de JS emite los features (async, class...)
    "module": "esnext",          // ESM
    "moduleResolution": "bundler" // resuelve imports como un bundler (Vite)
  }
}
  • target: sintaxis del JS de salida (nativamente, class properties, etc.).
  • module: sistema de modulos del artefacto (esnext, commonjs, node16...).
  • moduleResolution: como buscar los archivos de los imports.

El bloqueo estricto y sus piezas

{
  "compilerOptions": {
    "strict": true,               // activa todas las piezas siguientes
    "noImplicitAny": true,        // no dejes any implicitos
    "noImplicitReturns": true,    // toda funcion debe devolver algo explicito
    "strictNullChecks": true,     // null y undefined no se mezclan con otros tipos
    "strictFunctionTypes": true,  // invariacion/contravarianza de funciones
    "strictBindCallApply": true,
    "strictPropertyInitialization": true,
    "useUnknownInCatchVariables": true, // catch(e) es unknown
    "noUncheckedIndexedAccess": true    // T[i] da T | undefined
  }
}
Por que strict siempre

strict enciende a la vez varias comprobaciones que eliminan clases enteras de bugs (el "undefined que aparecio en runtime" es la mas famosa). En TypeScript 7 (y desde hace anos) es la recomendacion oficial. Todo el codigo del curso corre con strict.

Paths y baseUrl: los alias

{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"],
      "@utils/*": ["src/utils/*"]
    }
  }
}

Te permite importar con alias en lugar de rutas relativas interminables:

import { helper } from "@utils/helper"; // en vez de ../../../../utils/helper

Diagnosticos de cleanliness

{
  "compilerOptions": {
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true,
    "forceConsistentCasingInFileNames": true
  }
}

Emit y resolver

{
  "compilerOptions": {
    "noEmit": true,            // Vite: solo animas, no emites JS
    "outDir": "dist",          // a donde iria el JS si emitieras
    "declaration": true,       // generar .d.ts (librerias)
    "sourceMap": true          // para depurar el TS en el navegador
  }
}
  • Vite usa noEmit: true: el transpile lo hace esbuild, y TypeScript solo para tipar.
  • Una libreria usa declaration: true: los consumidores necesitan los .d.ts.
  • sourceMap apunta depurador desde el JS al TS original.

3 · Ejemplo minimo

tsconfig.json
{
  "compilerOptions": {
    "target": "es2022",
    "module": "esnext",
    "moduleResolution": "bundler",
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src"]
}

Campo a campo:

  • target y module deciden el JS de salida.
  • strict activa todas las comprobaciones duras.
  • noEmit: no genera JS (lo hacer el bundler).
  • skipLibCheck: no revisa los .d.ts de node_modules (rendimiento).

4 · Ejemplo real

Configuraciones coincidentes de un proyecto Vite (app) y de un paquete reutilizable (libreria):

app/tsconfig.json (proyecto Vite)
{
  "compilerOptions": {
    "target": "ES2022",
    "useDefineForClassFields": true,
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "skipLibCheck": true,
    "isolatedModules": true,
    "moduleDetection": "force",
    "noEmit": true,
    "jsx": "react-jsx",
    "strict": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src"]
}
libreria/tsconfig.json (emit .d.ts)
{
  "compilerOptions": {
    "target": "es2020",
    "module": "esnext",
    "moduleResolution": "bundler",
    "declaration": true,
    "declarationMap": true,
    "outDir": "dist",
    "strict": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}

Decisiones:

  • La app usa noEmit (Vite transpila) y lib DOM (web).
  • La libreria usa declaration: true para publicar los .d.ts.
  • El modo isolatedModules garantiza compatibilidad con esbuild.
  • Todas ellas con strict: true: la base de la calidad.
  • Al tocar un archivo compartido, puedes subir de nivel (p.ej. noUncheckedIndexedAccess) sin romper.

5 · Buenas practicas

  • strict: true siempre. Empieza los proyectos en estricto; nunca lo apagues por comodidad.
  • Habilita noUncheckedIndexedAccess cuando puedas asumirlo: elimina una clase enorme de "undefined" inesperado.
  • skipLibCheck: true para proyectos de app (rendimiento); las librerias pueden considerarlo con cuidado.
  • Activa forceConsistentCasingInFileNames: en Mac/Linux los casos importan.
  • Separa configs por contexto (tsconfig.app.json, tsconfig.node.json) en Vite.
  • No copies configs gigantes por costumbre: usa extends de un base compartido.

Que evitar

  • Apagar strict por un error molesto: mejor arregla la raiz.
  • Dos configs dispares en el mismo repo sin base comun (deriva a desincronizacion).
  • Dejar experimentalDecorators u opciones legacy si no las usas (afecta a resolver).
  • Redefinir lo que un extends ya configuro bien.

6 · Errores habituales

Mal — strict apagado por "rapidez" 
{
  "compilerOptions": { "strict": false } // ✖ pierde toda la red de seguridad
}
Bien — strict activo 
{
  "compilerOptions": { "strict": true } // ✅
}
Mal — include demasiado amplio (compila dist/node_modules) 
{
  "include": ["**/*"] // ✖ puede abarcar dist y node_modules
}
Bien — incluir solo src 
{
  "include": ["src"]
}
Mal — moduleResolution sin module coherente 
{
  "compilerOptions": {
    "module": "commonjs",
    "moduleResolution": "bundler" // ✖ incoherente: bundler espera ESM
  }
}
Bien — emparejarlos 
{
  "compilerOptions": {
    "module": "esnext",
    "moduleResolution": "bundler" // ✅
  }
}

7 · Ejercicio guiado

Vamos a configurar desde cero un tsconfig para un proyecto Node ESM.

  1. Escribe target: "es2022", module: "node16" (o nodenext).
  2. Pon moduleResolution: "nodenext" y strict: true.
  3. Anade noEmit: true (compilaremos con tsx/tsc --watch a dist si quieres).
  4. Define include: ["src"] y skipLibCheck: true.
  5. Comprueba tsc --noEmit.

Solucion paso a paso:

tsconfig.json (Node ESM)
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src"]
}

Con module: nodenext, los imports usan extensiones reales (./modulo.js). Si en src/ ves un "type": "module" en el package.json, el resultado es ESM puro.

9 · Resumen

  • include/exclude/files deciden que compila.
  • target/module/moduleResolution deciden el artefacto JS.
  • strict y sus piezas dan la red de seguridad.
  • paths para alias; declaration para librerias; noEmit para Vite.
  • extends para basar configs en una comun.
  • Depurar es facil: tsc --showConfig imprime el resultado final.

10 · Preguntas frecuentes

¿Por que Vite usa noEmit?

Porque la transpilacion la hace esbuild (rapidisimo) y TypeScript solo se ocupa de la comprobacion de tipos. Emitir JS con tsc seria duplicar trabajo y mas lento.

¿Que pasa si omito "target"?

Usa el default (ES3/ES5 segun version). Siempre pon uno moderno (es2020+) para no limitar el codigo generado.

¿module commonjs y moduleResolution node16 son compatibles?

Son cosas diferentes; node16/nodenext implican el comportamiento de Node segun el package.json. Para apps modernas usa nodenext o bundler segun el ecosistema.

¿Cuando añadir noUncheckedIndexedAccess?

Ya es recomendable; rompe codigo que asume indices presentes (los arrays en JS pueden tener huecos). Cuando la base sea limpia, activa y ajusta accesos con guardas.

¿extends permite cambiar todo?

Si, individualmente. Las opciones del hijo sobrescriben las del padre clave a clave, y path se fusiona con las del padre (arrays de paths se heredan y extienden).

¿Y si no hay tsconfig?

TypeScript asume una configuracion por defecto (compila todo, strict off, a veces incluye node_modules). Por eso el tsconfig es el primer paso de cualquier proyecto serio.
