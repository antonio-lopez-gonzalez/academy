Modulos ES y import type

Modulo 7 · Modulos y configuracion 🕐 30 minutos

1 · Introduccion

TypeScript sigue el sistema de modulos de ES (import/export), el estandar moderno. Pero ademas, siendo tipado, tiene una categoria propia: los exports/imports de tipos (import type, export type). Entender la diferencia entre "importo un valor" e "importo un tipo" afecta al rendimiento, al arbol de dependencias y a los errores de runtime.

El problema que resuelve: en JavaScript todo es un valor en runtime. En TypeScript, los tipos solo existen en compilacion y se borran. Si mezclas "import de tipo" como si fuera "import de valor", TypeScript podria dejar codigo muerto o fallar en isolatedModules.

Cuando se utilizan
  • Separar los contratos de tipos de la logica (archivos .ts con solo interfaces).
  • Aplicaciones grandes donde cada import cuenta en el bundle.
  • Trabajar con isolatedModules (comun en build tools como Vite).
  • Librerias que exportan sus tipos y sus valores por separado.

2 · Teoria

La analogia: el catalogo de repuestos

Un taller guarda en un almacen dos cosas distintas: las piezas (que puedes sacar y montar) y el catalogo de repuestos (solo te dice la forma de cada pieza). Las piezas son los valores; el catalogo, los tipos. Cuando pides "una pieza", la pieza real viaja en tu camioneta. Cuando pides "el catalogo", solo te llevas la informacion, que no pesa nada. import type te permite pedir "solo el catalogo".

import eliminados en compilacion ──► bundle final │ │ valor ──► import { suma } ▼ → existe como codigo JS real [codigo de suma] tipo ──► import type { Usuario } ▼ → no genera nada de JS [nada: se borra]

La base: import/export ES

// archivo: modelos.ts
export interface Usuario { id: number; nombre: string; }
export function crearUsuario(nombre: string): Usuario { return { id: 1, nombre }; }

// archivo: app.ts
import { Usuario, crearUsuario } from "./modelos.js";
import type { Usuario as SoloTipo } from "./modelos.js";

Nota la extension .js en el import aunque el archivo sea .ts: TypeScript obliga (en modulo ESM moderno) a importar con la extension real que habra en runtime. Es un detalle al que hay que acostumbrarse, pero Node y los bundlers modernos lo requieren.

import type y export type

// Solo importa el TIPO, no el valor:
import type { Usuario } from "./modelos.js";

let u: Usuario = { id: 1, nombre: "Ana" }; // ✅ solo se usa como tipo

// Tambien se puede mezclar en la misma linea con sintaxis inline:
import { crearUsuario, type Usuario } from "./modelos.js";
// crearUsuario es un valor; Usuario es solo un tipo.

// export type:
export type { Usuario };
// (o export type MiTipo = Exclude<Union, "x">;)
Por que import type importa

Cuando TypeScript compila, los tipos se borran. Al marcar import type, el compilador SABE que ese import no produce codigo, asi que puede eliminarlo del bundle. En Vite con isolatedModules es obligatorio distinguir: cada archivo se compila por separado y no puede saber si tu "import ordinario" era solo de tipos. Le estas diciendo la intencion.

Re-exports y export *

// re-export de valores y tipos:
export { crearUsuario } from "./modelos.js";
export type { Usuario } from "./modelos.js";

// re-export masivo (atento a aislar los tipos):
export * from "./modelos.js";
// (con isolatedModules puede ser necessario separar con `export * as` o marcar tipos)

CommonJS y los modulos en Node

ECMAScript (import/export) y CommonJS (require/module.exports) conviven a traves de la configuracion module del tsconfig. TypeScript puede emitir ESM ("module": "esnext"), CommonJS ("commonjs") o el nuevo bundler con Node. 

// Con moduleResolution "bundler" (tipico en Vite):
import { crearUsuario } from "./modelos"; // sin extension en bundlers

// En Node ESM estricto:
import { crearUsuario } from "./modelos.js"; // con extension

Verbatim module syntax y isolatedModules

TypeScript 5 revisa con verbatimModuleSyntax que los import/export de tipos sean explicitos. En proyecto Vite suele ir activo. La regla: si solo usas el nombre como tipo, importa con type. 

// Con verbatimModuleSyntax activo:
import { crearUsuario } from "./modelos.js"; // valor: correcto
import { type Usuario } from "./modelos.js"; // uso de tipo inline: correcto
// import { Usuario } from "./modelos.js";   // ✖ porque Usuario es solo tipo

3 · Ejemplo minimo

modulos-minimo.ts
// archivo: tipos.ts
export interface Producto { id: number; nombre: string; }

// archivo: precios.ts
import type { Producto } from "./tipos.js";

function total(producto: Producto, unidades: number): number {
  return unidades * 100;
}

// Solo necesitamos Producto como tipo; import type es suficiente.

Linea a linea:

  • export interface Producto exporta un tipo.
  • import type trae Producto sin generar codigo de runtime.
  • unidades: number usa el tipo primitivo, sin import.
  • En el bundle JS final, import type desaparece por completo.

4 · Ejemplo real

Una libreria de autentificacion con API publica y contratos de tipos separados:

auth/contratos.ts
// Solo tipos: el "catalogo" publico de la libreria.
export interface Credenciales { email: string; password: string; }
export type Sesion = { token: string; expira: Date };
export enum Rol { Administrador = "admin", Usuario = "usuario" }
auth/core.ts
import type { Credenciales, Sesion, Rol } from "./contratos.js";
// ✅ solo tipos: no arrastramos codigo del enum como valor, porque
// no usamos el enum como valor aqui.

export function iniciarSesion(c: Credenciales): Sesion {
  // (esto es un stub ilustrativo)
  return { token: "eyJ...", expira: new Date() };
}
index.ts
// Re-exportamos la API publica:
export { iniciarSesion } from "./core.js";     // valores
export type { Credenciales, Sesion } from "./contratos.js"; // tipos
export { Rol } from "./contratos.js";          // valor (enum, se usa en runtime)

Decisiones:

  • Los contratos (Credenciales, Sesion) van con export type: se borran del JS final.
  • El enum Rol es un valor en runtime, por eso se exporta normal.
  • Separacion de "tipos puros" y "valores" permite que los consumidores solo importen tipos cuando los necesitan, manteniendo el bundle limpio.
  • En core.ts usamos import type porque solo usamos los nombres como tipos.

5 · Buenas practicas

  • Usa import type cuando solo necesites un nombre como tipo: declara intencion y ayuda al bundler.
  • En sintaxis inline import { crearUsuario, type Usuario } separas valores y tipos en la misma linea.
  • Re-exporta por separado valores y tipos (export type) para API de librerias.
  • Importa con la extension .js real en ESM de Node (o configura el resolver correcto en Vite/bundler).
  • Activa verbatimModuleSyntax y isolatedModules en tus proyectos modernos.
  • Un archivo puede tener solo la capa de tipos sin valores: asi los demas saben que importar type.

Que evitar

  • Mezclar sin querer valor con tipo: cambia el bundle y puede romper en runtime (si el valor no se incluye).
  • Importar con extensiones que no existen (Node/TS estricto falla).
  • Abusar de export * con re-exports que no puedas predecir.
  • Confiar en que el bundler resolvera por nosotros: declara siempre la intencion con import type.

6 · Errores habituales

Mal — importar tipo sin type (rompe verbatimModuleSyntax) 
import { Usuario } from "./modelos.js"; // ✖ si Usuario es solo tipo
let u: Usuario; // solo se usa como tipo
Bien — import type 
import type { Usuario } from "./modelos.js"; // ✅
let u: Usuario;
Mal — usar la extension .ts en el import ESM 
import { x } from "./modelos.ts"; // ✖ en runtime no existe .ts
Bien — extension real 
import { x } from "./modelos.js"; // ✅ (en ESM estricto)
// en bundlers: import { x } from "./modelos"; // segun moduleResolution
Mal — asumir que el import global exporta los tipos 
import { InterfaceAusente } from "./noexporta.ts";
// ✖ no existe tal exporto
Bien — revisa que el modulo exporte ese nombre (valor o tipo) 
import type { LoQueExiste } from "./models.js";

7 · Ejercicio guiado

Vamos a crear una libreria pequena de utilidades con tipos y valores separados.

  1. Crea tipos.ts con export interface Punto { x: number; y: number }.
  2. Crea geo.ts con import type { Punto } y una funcion distancia.
  3. Crea index.ts que re-exporte la funcion y los tipos por separado.
  4. Habilita verbatimModuleSyntax y verifica que no falla.

Solucion paso a paso:

ejercicio-modulos.ts
// tipos.ts
export interface Punto { x: number; y: number; }

// geo.ts
import type { Punto } from "./tipos.js";

export function distancia(a: Punto, b: Punto): number {
  return Math.sqrt((a.x - b.x) ** 2 + (a.y - b.y) ** 2);
}

// index.ts
export { distancia } from "./geo.js";
export type { Punto } from "./tipos.js";

// Uso:
import { distancia, type Punto } from "./index.js";
const d: number = distancia({ x: 0, y: 0 }, { x: 3, y: 4 }); // 5
const p: Punto = { x: 1, y: 1 };

8 · Reto

Reto

En un proyecto Vite + TypeScript, crea un modulo formularios.ts que exporte una interfaz FormState y un hook sin libreria que la use. Habilita isolatedModules y verbatimModuleSyntax, y conviertelo todo a sintaxis separada (valores + tipos). Verifica que tsc --noEmit pasa sin errores y que el bundle final no contiene los nombres de los tipos.

9 · Resumen

  • Modulos ES: import/export; los tipos se borran en compilacion.
  • import type / export type: separan tipos de valores, sin codigo en runtime.
  • Extension de import: .js real en ESM; resuelta por bundlers en Vite.
  • verbatimModuleSyntax y isolatedModules exigen la distincion explicita.
  • Re-exports separados mantienen la API de tipos y valores limpia.

10 · Preguntas frecuentes

¿Necesito import type en un proyecto de Node sin bundler?

Con TypeScript moderno y verbatimModuleSyntax si quieres ser explicito. En esencia ayuda a que el compilador y la herramienta sepan que no se genera codigo por ese import, y fomenta una arquitectura de tipos/valores limpia.

¿Cuando conviene un archivo "solo tipos"?

Cuando quieras centralizar contratos (interfaces, unions) reutilizados en varias capas. Evita acoplarla a implementacion; es el patron de "API types" de muchas librerias.

¿Que es moduleResolution "bundler"?

Es el modo pensado para Vite/webpack/Rollup: permite import sin extension y con export map, porque el bundler no necesita la extension real. Node ESM estricto, en cambio, usa "node16"/"nodenext".

¿Los enums importados como tipo se borran?

Un enum es un valor real (genera JS). Solo sus tipos derivados (como el tipo de un miembro) son tipos. Si importas enum, llevalo como valor normal, no como type.

¿Puedo usar import type con librerias CommonJS?

Si: import type actua igual para tipos de CommonJS (interfaces y type aliases de los .d.ts). La diferencia esta en cómo el bundler resuelve los valores del CJS, no en el tipado.

¿Debo usar import * as para modulos con muchos exports?

Con ESM import * as es un namespace valido, pero lo ideal es importar los nombres que realmente usas (tree-shaking amistoso). En CommonJS, import * as y import = require tienen matices según la config.
