Monorepos y project references

Modulo 7 · Modulos y configuracion 🕐 30 minutos

1 · Introduccion

Un monorepo es un repositorio con multiples paquetes: una app, una libreria, tooling. TypeScript lo soporta con project references: cada paquete es un proyecto TS que declara cuales son sus dependencias, permitiendo tipos compartidos, builds incrementales y compilacion en el orden correcto.

El problema que resuelve: si tienes 20 paquetes y compilas "todo junto" un cambio en uno recompila el mundo. Con project references, TypeScript sabe que app depende de lib, compila lib primero, y (con tsBuildInfoFile) solo recompila lo afectado.

Cuando se utilizan
  • Equipos grandes con varias apps y librerias compartidas.
  • Compartir tipos entre frontend, backend y paquete commun.
  • Compilacion incremental y CI rapido.
  • Este mismo curso (web/ + ejemplos/ + proyectos/) es un mini-monorepo con pnpm.

2 · Teoria

La analogia: la obra y sus camiones

Una obra grande no tiene un solo camion que lo lleva todo: tiene muchos (arquitectura, electricidad, albanileria) y solo los que se ven afectados cuando cambia el diseno. Las project references son esa logistica: sabes que para pintar una pared ("app") antes necesitas el molde del muro ("lib"), y no re-haces los cimientos cuando solo cambia el color.

Raiz (tsconfig raiz, opcional) │ package.json (pnpm-workspace) │ ├── packages/lib ──► tsconfig (composite: true) │ ▲ reference │ │ ├── apps/app ──► tsconfig (referencias a lib) │ └── package.json (scripts orquestan builds)

Pasos 1a: definir un proyecto composite

{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}

composite: true es obligatorio para poder ser referenciado: indica que el proyecto emite .d.ts y lleva track incremental. Los proyectos referenciados deben ser composite.

Pasos 1b: la app referencia al lib

{
  "compilerOptions": {
    "composite": true,
    "outDir": "dist"
  },
  "references": [
    { "path": "../lib" }
  ]
}

references establece la dependencia: "mi codigo usa tipos procedentes de ../lib". Cuando compiles la app con tsc -b (build mode), TypeScript elige el orden y compila primero lib.

tsc -b: el build mode

pnpm dlx tsc -b packages/lib
pnpm dlx tsc -b .          # compila toda la raiz y dependencias

-b respeta las referencias, detecta proyectos desactualizados y usa caché (tsconfig.tsbuildinfo) para recompilar solo lo necesario.

pnpm workspaces: los paquetes mono-repo

// pnpm-workspace.yaml
packages:
  - "packages/*"
  - "apps/*"

# Instalar en la raiz
pnpm install

# Ejecutar script de un paquete
pnpm --filter @academy/lib build
pnpm --filter @academy/app dev

Los paquetes se declaran en su package.json (scoped name) y se enlazan como dependencias locales:

{
  "name": "@academy/app",
  "dependencies": {
    "@academy/lib": "workspace:*"
  }
}

Separacion entre tipos y build

// tsconfig.json (raiz, solo supervisa)
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}

El patron de Vite mismo: una raiz sin archivos que solo apunta a sub-proyectos. Asi tsc -b dispara ambos.

Types compartidos como paquete

// packages/types/src/index.ts
export interface Usuario { id: number; nombre: string; }
export type Rol = "admin" | "usuario";

// apps/api/src/handlers.ts
import type { Usuario } from "@academy/types";
// ✅ tipos compartidos entre frontend y backend

3 · Ejemplo minimo

monorepo-minimo
// Estructura real:
// packages/lib/tsconfig.json   ── composite: true
// apps/app/tsconfig.json       ── references: [{ path: "../lib" }]
// pnpm-workspace.yaml

// packages/lib/src/saludo.ts
export function saludo(nombre: string): string {
  return `Hola, ${nombre}`;
}

// apps/app/src/main.ts
import { saludo } from "@academy/lib";
console.log(saludo("Mundo")); // ✅ tipos compartidos

Paso a paso:

  • lib declara composite: true: emite .d.ts y seguimiento incremental.
  • app referencia a lib: TypeScript resuelve @academy/lib hasta sus .d.ts.
  • tsc -b apps/app compila lib primero.
  • pnpm enlaza los paquetes locales en node_modules.

4 · Ejemplo real

Un monorepo con paquete de tipos y API compartida, frontend y tooling:

pnpm-workspace.yaml
packages:
  - "packages/*"
  - "apps/*"
packages/types/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist",
    "strict": true
  },
  "include": ["src"]
}
packages/types/src/index.ts
export interface Pedido { id: string; total: number; estado: EstadoPedido; }
export type EstadoPedido = "creado" | "pagado" | "enviado";
apps/api/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "outDir": "dist",
    "strict": true,
    "module": "nodenext",
    "moduleResolution": "nodenext"
  },
  "references": [{ "path": "../../packages/types" }]
}
apps/api/src/estado.ts
import type { Pedido, EstadoPedido } from "@midas/types";

function puedePagar(pedido: Pedido): boolean {
  return pedido.estado === "creado"; // ✅ el tipo fluye del paquete comun
}

const estado: EstadoPedido = "pagado"; // ✅

Decisiones:

  • El paquete de tipos es composite y emite .d.ts: es la "libreria fuente de todo".
  • La API referencia a el con references: tipos enlazados, no copiados.
  • pnpm --filter @midas/api build usa tsc -b respetando el orden.
  • El frontend podria referenciar el mismo paquete: tipos compartidos en todo el monorepo.
  • Los cambios en types recompilan solo a quienes lo dependen (caché incremental).

5 · Buenas practicas

  • Configura CUALQUIER paquete referenciado (composite: true) o TypeScript dara error.
  • Usa tsc -b (build mode) para builds con orden y caché; no tsc sin -b en referencias.
  • Mantén una raiz tsconfig con files: [] solo apuntando a referencias si quieres un tsc -b . global.
  • Estructura por packages/ y apps/ con pnpm workspace; nombres scoped.
  • Separa configs de build de las de editor si difieren (patterns con Vite).
  • Declarar la dependencia workspace:* para enlaces locales.

Que evitar

  • Referenciar a paquetes que no son composite.
  • Copiar tipos a mano entre paquetes en vez de usar el paquete comun.
  • No usar -b y que todo recompile (o que los .d.ts no se actualicen).
  • Dependencias circulares entre paquetes (rompen el orden de build).
  • Compilar node_modules con include indiscriminado (rompe resoluciones).

6 · Errores habituales

Mal — referenciar un proyecto no composite 
{
  "compilerOptions": { "strict": true },
  "references": [{ "path": "../lib" }]
}
// ✖ error: referenced project must have setting "composite": true
Bien — lib es composite 
{
  "compilerOptions": { "composite": true, "declaration": true },
  "include": ["src"]
}
Mal — compilar sin -b 
tsc -p packages/lib     # ✖ solo compila lib, ignora quien lo usa
tsc -p apps/app          # ✖ no dispara la build previa de lib
Bien — build mode respeta el orden 
tsc -b apps/app          # ✅ compila lib y app en orden con caché
tsc -b .                 # ✅ toda la grafo desde la raiz
Mal — dependencia circular 
// apps/a importa de lib, y lib importa de apps/a (✖ circular)
// TypeScript no puede ordenar el build: error de referencia
Bien — dependencias en arbol 
// lib no depende de estrategia de apps; apps dependen de lib

7 · Ejercicio guiado

Vamos a montar un mini-monorepo con dos paquetes.

  1. Crea packages/lib (composite) con export function doble(n: number): number.
  2. Crea apps/app con references a lib.
  3. Enlaza con "@academy/lib": "workspace:*" y pnpm install.
  4. Desde apps/app, importa doble y comprueba tipos.
  5. Ejecuta tsc -b apps/app.

Solucion paso a paso:

packages/lib/src/index.ts
export function doble(n: number): number {
  return n * 2;
}
apps/app/src/main.ts
import { doble } from "@academy/lib";

const resultado: number = doble(21); // ✅ 42
console.log(resultado);
apps/app/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true
  },
  "references": [{ "path": "../../packages/lib" }]
}
Comandos
pnpm install
pnpm --filter @academy/app exec tsc -b --pretty

8 · Reto

Reto

Añade un tercer paquete packages/utils (con una funcion uid()) que dependa SOLO de los tipos de packages/types, e integra un tsconfig.raiz.json con files: [] y references a los tres paquetes. Verifica que tsc -b . ordena la compilacion correctamente (types antes que utils, despues app). No mires la solucion.

9 · Resumen

  • Monorepo: varios paquetes en un repo con pnpm workspaces.
  • Project references: cada paquete es un proyecto TS que declara dependencias.
  • composite: true en los referenciados; tsc -b para el orden con caché.
  • Tipos compartidos via paquete comun (frontend + backend).
  • Raiz con files: [] y references = "supervisar todo" sin compilar nada en la raiz.

10 · Preguntas frecuentes

¿Por que "composite" en el referenciado?

Porque el build mode necesita saber que ese proyecto genera .d.ts y offsets incrementales (tsbuildinfo) para poder usar luego tipos obsoletos solo cuando cambie.

¿references sirve para algo si uso Vite?

Si: aunque Vite transpile con esbuild, el tipado entre paquetes (editor + tsc) se apoya en las references. Para el bundle en runtime, pnpm workspace enlaza y Vite lo resuelve.

¿Compilar todo con tsc -b . recompila demasiado?

No: con tsbuildinfo compara la huella y solo recompila dependencias desactualizadas. Los cambios en un paquete deja intactos los demas si sus .d.ts no cambiaron.

¿Que biblioteca de workspace es mejor, pnpm o npm/yarn?

Este curso usa pnpm (por convencion). Para monorepos TypeScript, pnpm workspace es ligera y compatible con references. Hay otras herramientas (turborepo, nx) que orquestan por encima.

¿Como recalculo el orden si un paquete cambia?

Con tsc -b, no lo haces tu: el detector marca dependientes obsoletos y los recompila. Si hay ciclos, TS lo reporta claramente.

¿Debo commitear los tsbuildinfo?

Normalmente no: son cachés de build (y en CI no aportan). Añadelo a .gitignore. En local aceleran la edicion/CI privada.
