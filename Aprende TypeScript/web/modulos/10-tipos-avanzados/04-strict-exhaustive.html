Strict mode y exhaustividad en profundidad

Modulo 10 · Tipos avanzados 🕐 35 minutos

1 · Introduccion

strict: true no es una opcion, es un paquete de ocho flags que endurecen el compilador. Esta leccion separa cada pieza y luego ataca el concepto que las une: exhaustividad — programar para que el compilador grite cuando tu codigo deja de cubrir todos los casos.

Veras cuatro herramientas: strictFunctionTypes (varianza), noUncheckedIndexedAccess (accesos a indices), exactOptionalPropertyTypes (opcionales honestos) y la combinacion satisfies + switch exhaustivo con never para convertir la union en un check-list que nunca se olvida.

2 · Teoria

Que activa strict exactamente

tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true
  }
}

strict es azucar sintactico para ocho flags: alwaysStrict, strictNullChecks, strictBindCallApply, strictFunctionTypes, strictPropertyInitialization, noImplicitAny, noImplicitThis y useUnknownInCatchVariables. Las dos que veremos en detalle aqui son strictFunctionTypes, noUncheckedIndexedAccess y exactOptionalPropertyTypes (esta ultima no la activa strict; se anade aparte).

strictFunctionTypes: varianza de parametros

varianza.ts
type Listener = (e: { tipo: string }) => void;

function registrar(l: Listener): void {}

// Mal: el callback acepta un SUBTIPO (mas campos). Quien muestra el evento puede
// venir sin esos campos → llamada insegura. strictFunctionTypes lo bloquea.
// registrar((e: { tipo: string; detalle: number }) => {});  // ✖

// Bien: el callback acepta un SUPERTIPO (menos exigencias) → seguro (contravariante).
registrar((e: unknown) => {}); // ✅

Una funcion que recibe callbacks exige que el parametro del callback sea compatible al reves: si tu funcion pide un evento minimo, el callback debe aceptar como poco ese evento. strictFunctionTypes aplica esta contravariacion a las propiedades de funcion, pero no a los metodos (por compatibilidad historica): 

interface ConMetodo {
  manejar(fn: (e: { tipo: string }) => void): void;          // metodo: bivariante (legacy)
}

interface ConPropiedad {
  manejar: (fn: (e: { tipo: string }) => void) => void;      // propiedad: estricta
}

noUncheckedIndexedAccess: los indices pueden no existir

indices.ts
const dias = ["L", "M", "X"];

const primero = dias[0]; // string | undefined (con la flag)
const fuera = dias[9];   // string | undefined — ya no "explota" en silencio

function saluda(): void {
  if (primero !== undefined) {
    console.log(primero.toUpperCase()); // ✅ comprobar antes de usar
  }
  const dia = dias[1] ?? "L"; // ✅ default con ??
}
Un cajon con estantes

Acceder a dias[9] sin la flag es como meter la mano en un cajon y asumir que el estante 9 siempre existe. La flag entrena el reflejo de mirar antes de usar: todo acceso por indice devuelve | undefined hasta que lo compruebas.

exactOptionalPropertyTypes: opcional no significa undefined

opcionales.ts
interface Config {
  nombre?: string;  // la clave puede faltar; no admite undefined explicito
  color: "rojo" | "azul";
}

const ok1: Config = { color: "rojo" };                 // ✅ clave omitida
const ok2: Config = { color: "azul", nombre: "App" };  // ✅ valor explicito
// const bad: Config = { color: "rojo", nombre: undefined }; // ✖ con la flag

Sin la flag, nombre?: string acepta undefined explicito; con ella, "opcional" significa unicamente que la clave puede faltar. Diferencia sutil pero real: undefined explicito suele delatar campos que de verdad son string | undefined.

satisfies: validar la forma sin perder literales

satisfies.ts
type Claves = "usuarios" | "pedidos" | "config";

// satisfies valida la forma SIN ensanchar el tipo literal inferido.
const vistas = {
  usuarios: () => import("./usuarios"),
  pedidos: () => import("./pedidos"),
  config: () => import("./config"),
} satisfies Record<Claves, () => Promise<unknown>>;

// Si Claves crece (p.ej. "admin") y no implementas la vista → error.
// Cada clave de la union queda exigida: exhaustividad de configuracion.

as fuerza el tipo; satisfies solo verifica que el valor cuadra, sin cambiar lo que el compilador infiere. Eso lo convierte en la herramienta natural para decirle al compilador "este objeto debe implementar exactamente estas claves".

El switch exhaustivo: never como check-list

exhaustivo.ts
type Estado = "cargando" | "listo" | "error";

function agotar(nunca: never): never {
  throw new Error(`Estado sin contemplar: ${nunca}`);
}

function transicionar(estado: Estado): void {
  switch (estado) {
    case "cargando": return; // carga la vista
    case "listo": return;    // muestra el contenido
    case "error": return;    // aviso al usuario
    default:
      return agotar(estado); // ✖ hoy inalcanzable; falla si anades "pausado"
  }
}
Por que never

En el default, el narrowing deja a estado con el tipo "lo que queda": si la union esta completa, queda never. agotar exige never, asi que compila hoy. Cuando alguien anade "pausado" a la union, en el default el valor ya NO es never y la compilacion falla: el compilador te recuerda el caso que falta.

3 · Ejemplo minimo

strict-minimo.ts
// noUncheckedIndexedAccess: el indice puede fallar.
const fila = ["a", "b", "c"];
const celda = fila[1]; // string | undefined

// exactOptionalPropertyTypes: omitir es lo correcto, no undefined.
interface Prefs {
  volumen?: number;
}
const p: Prefs = {}; // ✅ clave omitida

// Exhaustividad con never: la union completa cierra el switch.
type Estado = "encendido" | "apagado";

function agotar(nunca: never): never {
  throw new Error(`Estado sin tratar: ${nunca}`);
}

function manejar(e: Estado): void {
  switch (e) {
    case "encendido": encender(); return;
    case "apagado": apagar(); return;
    default: return agotar(e); // inalcanzable mientras la union este completa
  }
}

declare function encender(): void;
declare function apagar(): void;

Linea a linea:

  • fila[1] devuelve string | undefined: el compilador ya no asume que el indice existe.
  • volumen?: number sin la flag aceptaria undefined explicito; con ella, omitir la clave es la forma correcta de "sin valor".
  • agotar(e) en el default cierra el switch: anadir un miembro a Estado rompe la compilacion ahi mismo.

4 · Ejemplo real

Un reductor de estado con union discriminada, una config de vistas que exige exhaustividad con satisfies y accesos seguros a indices.

reductor-estricto.ts
type Accion =
  | { tipo: "subir"; delta: number }
  | { tipo: "bajar"; delta: number }
  | { tipo: "resetear" };

type Contador = { valor: number };

function agotar(nunca: never): never {
  throw new Error(`Accion no contemplada: ${JSON.stringify(nunca)}`);
}

function reducer(estado: Contador, accion: Accion): Contador {
  switch (accion.tipo) {
    case "subir":
      return { valor: estado.valor + accion.delta };
    case "bajar":
      return { valor: estado.valor - accion.delta };
    case "resetear":
      return { valor: 0 };
    default:
      return agotar(accion); // nueva Accion → error de compilacion aqui
  }
}

// Exhaustividad de config: cada vista declarada debe estar implementada.
type Vistas = "inicio" | "carrito" | "perfil";

const rutas = {
  inicio: () => Promise.resolve(),
  carrito: () => Promise.resolve(),
  perfil: () => Promise.resolve(),
} satisfies Record<Vistas, () => Promise<void>>;

// Acceso seguro a indices: nunca uses un indice sin asegurar.
const pasos = [1, 2, 3];
const paso = pasos[0]; // number | undefined
if (paso !== undefined) {
  console.log(paso * 2);
}

Decisiones:

  • El reductor y la config de vistas comparten la misma filosofia: la union declara el universo de casos y el codigo no puede quedarse corto sin que tsc lo diga.
  • agotar es una funcion de una linea reutilizable en cualquier switch de la app.
  • satisfies conserva los literales: si mas abajo quieres tipar las claves de rutas, el objeto mantiene su tipo exacto.
  • Los accesos por indice van precedidos de comprobacion, el habito que la flag entrena.

5 · Buenas practicas

  • Activa strict desde el primer dia del proyecto; migrar codigo legacy a strict es un trabajo doloroso y retroactivo.
  • Anade noUncheckedIndexedAccess y exactOptionalPropertyTypes conscientemente: moldean el estilo (comprobar indices, omitir claves) antes de acostumbrarte a lo laxo.
  • Declara callbacks como propiedades de funcion si quieres varianza estricta; reserva la sintaxis de metodo para clases con herencia pensada.
  • Crea un agotar(nunca: never) reutilizable y ponlo en el default de cada switch sobre unions: tu check-list del dominio.
  • Usa satisfies en lugar de as para validar formas: verifica sin destruir el tipo inferido.
  • Con useUnknownInCatchVariables (parte de strict), re-narrow el error en el catch antes de leer sus propiedades.

Que evitar

  • Aceptar undefined silencioso en accesos por indice o campos opcionales.
  • Dejar el default vacio o devolviendo null: matas el aviso de exhaustividad.
  • Usar as para silenciar un satisfies que falla: estas saltandote la comprobacion que pediste.
  • Confiar en la bivariancia de los metodos cuando la seguridad del sistema importa.

6 · Errores habituales

Mal — vivir sin strictNullChecks 
// Sin strict, null pasa como string y el crash llega en runtime:
// const nombre: string = null; // ✖ compila sin strictNullChecks
Bien — ser honesto con el dato 
const nombre: string | null = null; // ✅ el tipo dice la verdad
Mal — indice sin comprobar 
const fila = ["a", "b"];
console.log(fila[1].toUpperCase()); // ✖ fila[1] puede ser undefined
Bien — comprobar antes de usar 
const celda = fila[1]; // string | undefined
if (celda !== undefined) console.log(celda.toUpperCase());
Mal — undefined explicito en un opcional 
interface Prefs { tema?: "claro" | "oscuro"; }
// const p: Prefs = { tema: undefined }; // ✖ con exactOptionalPropertyTypes
Bien — omitir la clave 
interface Prefs { tema?: "claro" | "oscuro"; }
const p: Prefs = {};
// Si de verdad necesitas undefined: tema?: "claro" | "oscuro" | undefined
Mal — default silencioso 
switch (accion.tipo) {
  case "subir": return subir();
  default: return null; // ✖ si nace "bajar", nadie se entera
}
Bien — default que grita 
switch (accion.tipo) {
  case "subir": return subir();
  default: return agotar(accion); // nunca: la union nueva rompe la compilacion
}

7 · Ejercicio guiado

Vamos a convertir una union de colores en una funcion exhaustiva con never.

  1. Define type Color = "rojo" | "verde" | "azul".
  2. Escribe function agotar(nunca: never): never que lance un error.
  3. Crea function hex(color: Color): string con un switch de los tres colores, cada case con su return.
  4. Anade el default: con return agotar(color).
  5. Prueba: anade "amarillo" a Color y observa el error del compilador en el default.

Solucion paso a paso:

ejercicio-exhaustivo.ts
// 1) La union que declara el universo de casos.
type Color = "rojo" | "verde" | "azul";

// 2) El centinela: exige never.
function agotar(nunca: never): never {
  throw new Error(`Color sin mapear: ${nunca}`);
}

// 3 y 4) Switch completo + default exhaustivo.
function hex(color: Color): string {
  switch (color) {
    case "rojo": return "#f00";
    case "verde": return "#0f0";
    case "azul": return "#00f";
    default: return agotar(color); // inalcanzable hoy; grita si la union crece
  }
}

// 5) Descomenta "amarillo" en Color y veras el error:
// el argumento de tipo '"amarillo"' no se puede asignar al parametro de tipo 'never'.

8 · Reto

Reto

Combina las dos tecnicas de exhaustividad en un solo sistema: define type Vistas = "login" | "panel" | "admin" y un objeto rutas que con satisfies Record<Vistas, () => Promise<void>> obligue a implementar las tres vistas. Despues escribe un reducer sobre una union de acciones con el default agotar. Anade una cuarta vista y una cuarta accion: el compilador debe fallar en dos puntos distintos. No mires la solucion: piensa en que cada nueva clave de la union tiene que romper la compilacion tanto en satisfies como en el default del switch.

9 · Resumen

  • strict es un paquete de ocho flags; conocerlas te permite razonar cada error de tsc.
  • strictFunctionTypes aplica contravariencia a propiedades de funcion (no a metodos).
  • noUncheckedIndexedAccess hace que todo acceso por indice devuelva | undefined: comprobar antes de usar.
  • exactOptionalPropertyTypes separa "la clave puede faltar" de "el valor puede ser undefined".
  • satisfies valida la forma sin tocar el tipo inferido: exhaustividad de configuracion.
  • Un agotar(nunca: never) en el default convierte cada union en un check-list: un miembro nuevo rompe la compilacion.

10 · Preguntas frecuentes

¿Que opciones activa exactamente strict?

Ocho flags: alwaysStrict, strictNullChecks, strictBindCallApply, strictFunctionTypes, strictPropertyInitialization, noImplicitAny, noImplicitThis y useUnknownInCatchVariables. Sobre ellas puedes anadir noUncheckedIndexedAccess y exactOptionalPropertyTypes.

¿Por que strictFunctionTypes no afecta a los metodos?

Por compatibilidad historica con clases y herencia. Si quieres estrictez total, declara los callbacks como propiedades de funcion (manejar: (fn) => void) en lugar de metodos (manejar(fn): void).

¿noUncheckedIndexedAccess merece el ruido?

Si trabajas con arrays, mapas o registros densos: te obliga a decidir que ocurre cuando el indice no existe. Para datos siempre completos puede sentirse ruidoso; en esos casos un ?? corto documenta tu decision.

¿exactOptionalPropertyTypes rompe algo?

Cambia el habito de asignar undefined a opcionales. Si un campo de verdad acepta undefined, declara campo?: T | undefined. Los objetos mutables y algunos patrones de inicializacion requieren esa union explicita.

¿satisfies es un "as seguro"?

Es diferente: as fuerza el tipo (y puede mentir); satisfies solo verifica que el valor cuadra con lo exigido sin cambiar lo inferido. Por eso es ideal para exigir claves sin perder literales.

¿El switch exhaustivo sirve para algo mas que enums?

Si: para cualquier union literal o discriminada. El patron default: agotar(x) tambien se usa en reducers, maquinas de estado y mapeos de eventos, y funciona igual con unions de objetos discriminadas.
