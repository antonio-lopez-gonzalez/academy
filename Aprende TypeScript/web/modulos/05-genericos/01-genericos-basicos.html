Genericos basicos

Modulo 5 · Genericos 🕐 30 minutos

1 · Introduccion

Los genericos son la herramienta que permite escribir codigo que funciona con cualquier tipo pero conservando el tipo exacto con el que se usa. Resuelven el problema de la "caja que guarda algo": sin ellos, tendriamos que elegir entre any (perdemos seguridad) o duplicar codigo para cada tipo.

Es el concepto mas importante de TypeScript para el desarrollo profesional: Array<T>, Promise<T>, Record<K, V> y toda libreria moderna (React, Express, Prisma) se construye con genericos. Aprenderlos es entender la diferencia entre un desarrollador que "usa tipos" y uno que "escribe para los tipos".

Cuando se utilizan
  • Funciones que devuelven el mismo tipo que reciben (identity, wrappers).
  • Estructuras de datos: Stack<T>, Cache<K, V>, Lista<T>.
  • APIs que procesan datos de tipo desconocido de antemano.
  • Librerias y utilidades reutilizables.
Errores tipicos
  • Usar any en vez de un generico: perdemos toda la seguridad de tipos.
  • No dejar que TypeScript infiera el tipo (anotarlo a mano con un tipo ancho).
  • Olvidar el caso de las funciones flecha en .tsx (necesitan coma).

2 · Teoria

La analogia: la caja vacia

Imagina una caja para transportar cosas. La caja en si no sabe que contendra: un plato, un libro o una pastilla. Si compras "una caja", cuando llegas a casa puedes guardar lo que quieras, pero no sabes que hay dentro hasta que la abres. Eso es any.

Ahora imagina que compras una caja que promete guardar un plato. En el lateral pone "Caja de platos". Cuando la lleves de casa en casa, todos saben que dentro hay un plato, y nadie intenta sacar un martillo. Eso es Box<Plato>: el tipo del contenido queda "escrito en la etiqueta".

Un generico es exactamente eso: una variable de tipo que la caja (la funcion, la clase) declara, y que quien la use rellena con un tipo concreto. Al rellenarla, TypeScript sustituye la variable por el tipo real en todos los sitios.

Una funcion generica en tiempo de compilacion: identidad<T>(valor: T): T ▲ │ "T es una variable de tipo" │ al llamar: identidad(5) │ ▼ identidad<number>(valor: number): number

Type parameters: la sintaxis

Se declaran entre <> despues del nombre de la funcion, clase, interfaz o type alias. Por convencion se usan letras mayusculas cortas: T (Type), K (Key), V (Value), U (otro tipo), R (Return). 

// T es un "agujero" de tipo que se rellena en cada llamada.
function identidad<T>(valor: T): T {
  return valor;
}

// Al llamarla, TypeScript INFIERE T a partir del argumento:
const a = identidad(42);            // T = number, a: number
const b = identidad("hola");        // T = string, b: string
const c = identidad([1, 2, 3]);     // T = number[], c: number[]

Inferencia vs anotacion explicita

En la mayoria de los casos no escribes el tipo: TypeScript lo infiere del argumento. Pero puedes anotarlo explicitamente cuando la inferencia no pueda deducirlo (o quieras forzar un tipo concreto): 

// Inferencia: T = string
const saludo = identidad("hey");

// Explicitamente: obligamos a T = string (aunque "hey" podria ser "hey" literal
// si usamos as const).
const saludo2 = identidad<string>("hey");

// Tambien puedes anotar con un tipo ancho a proposito:
const lista: identidad<number[]> = identidad;

Varios type parameters

Puede haber varios agujeros de tipo, y TypeScript los infiere de forma independiente: 

function emparejar<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}

const par = emparejar("clave", 3);   // [string, number] (tupla, no (string|number)[])
// A = string, B = number
Por que inferir A y B por separado

Si el retorno fuera [A | B, A | B] perderiamos la relacion posicional: el primer elemento siempre es el de tipo A. Al declarar la tupla [A, B], TypeScript garantiza que la posicion y el tipo van unidos. Esto se llama preservar la relacion.

Genericos en interfaces, type aliases y clases

// Interfaz generica.
interface Caja<T> {
  contenido: T;
  etiqueta: string;
}
const cajaDeLibros: Caja<Libro> = { contenido: libro, etiqueta: "ficcion" };

// Type alias generico.
type Resultado<T> = { ok: true; datos: T } | { ok: false; error: string };

// Clase generica.
class Pila<T> {
  private items: T[] = [];
  push(item: T): void { this.items.push(item); }
  pop(): T | undefined { return this.items.pop(); }
}
const pilaDeNumeros = new Pila<number>();
pilaDeNumeros.push(1);        // ✅ solo acepta number
// pilaDeNumeros.push("x");   // ✖ error en compilacion

La trampa de las funciones flecha

En un archivo .tsx, la sintaxis <T> choca con la de los elementos JSX. La solucion es una coma de desambiguacion (o usar extends unknown): 

// En un .tsx:
const identidad = <T,>(valor: T): T => valor;
//                        ^^ la coma dice "esto es un generico, no JSX"

Arrows no usables en algunos casos

En .ts la forma normal es sin coma. En .tsx, recuerda la coma. Este pequeno detalle causa errores confusos al migrar componentes React.

3 · Ejemplo minimo

genericos-minimo.ts
// La funcion generica mas pequena posible: la identidad.
// Recibe un valor de tipo T y devuelve el mismo valor (tipo T).
function identidad<T>(valor: T): T {
  return valor; // el tipo de retorno es EXACTAMENTE el tipo de entrada
}

const numero = identidad(10);        // numero: number
const texto = identidad("hola");     // texto: string
const obj = identidad({ a: 1 });     // obj: { a: number }

Linea a linea:

  • <T> declara la variable de tipo.
  • valor: T dice "el argumento es de tipo T".
  • : T (retorno) dice "devuelvo el mismo tipo T".
  • Al llamar identidad(10), T = number. Nunca se pierde el tipo.

4 · Ejemplo real

Un cliente HTTP reutilizable. Con genericos, el mismo fetchJSON sirve para cualquier endpoint y devuelve el tipo de cada uno:

cliente-generico.ts
interface Usuario { id: number; nombre: string; }
interface Pedido { id: number; total: number; }

// Funcion generica: hace fetch y tipa la respuesta como T.
async function fetchJSON<T>(url: string): Promise<T> {
  const respuesta = await fetch(url);
  if (!respuesta.ok) {
    throw new Error(`HTTP ${respuesta.status} en ${url}`);
  }
  return respuesta.json() as T; // "as T": afirmamos la forma de la respuesta
}

// Cada llamada devuelve el tipo correcto SIN duplicar codigo:
const usuario = await fetchJSON<Usuario>("/api/usuarios/1");
usuario.nombre;  // ✅ string, con autocompletado

const pedidos = await fetchJSON<Pedido[]>("/api/pedidos");
pedidos[0].total; // ✅ number

Decisiones:

  • El generico <T> solo aparece en el retorno; el argumento es un string. La inferencia desde la URL no es posible, por eso se anota <Usuario> en cada llamada.
  • as T es una asercion controlada: la API del navegador devuelve any, y nosotros declaramos la forma. Es un punto de confianza, idealmente validado con un schema (zod) en produccion.
  • Un solo generico reutilizable reemplaza a decenas de funciones duplicadas.

5 · Buenas practicas

  • Deja que TypeScript infiera T siempre que pueda: menos ruido, menos errores.
  • Usa genericos solo cuando la relacion entre tipos importa. Si el tipo no se usa en el retorno ni en relaciones, sospecha: quizas no necesitas generico.
  • Nombra bien cuando T es poco: K, V para mapas, R para retornos. Para cosas de dominio, usa nombres descriptivos (Queue<Task>).
  • Empieza los genericos desde la firma, no desde la implementacion: primero piensa "que relacion de tipos necesito expresar".
  • No uses any como tipo de retorno generico: destruye la promesa del generico.

Que evitar

  • Anotar T manualmente cuando la inferencia lo resuelve.
  • Genericos que no se usan (sin efecto sobre el tipado).
  • Duplicar any cuando un generico expresaria mejor la intencion.
  • Olvidar que un generico en un parametro es opcional por defecto: <T = unknown> para valores por defecto.

6 · Errores habituales

Mal — any en vez de generico 
function primero(items: any[]): any {
  return items[0];
}
const x = primero([1, "dos", true]); // x: any (sin seguridad)
Bien — generico preserva el tipo 
function primero<T>(items: T[]): T | undefined {
  return items[0];
}
const x = primero([1, 2, 3]); // x: number | undefined ✅
Mal — el generico no aparece en la firma (inutil) 
function log<T>(msg: string): void {
  console.log(msg); // T no se usa: el generico no aporta nada
}
Bien — o se usa, o no es generico 
function log(msg: string): void {
  console.log(msg);
}
Mal — olvidar la coma en .tsx 
// En .tsx esto se interpreta como JSX y falla:
const id = <T>(v: T) => v; // JSX: elemento T
Bien — coma de desambiguacion 
const id = <T,>(v: T) => v; // generico real ✅

7 · Ejercicio guiado

Vamos a crear una funcion crearPar que devuelva el par ordenado de dos valores de distinto tipo.

  1. Declara la firma: function crearPar<A, B>(a: A, b: B): [A, B].
  2. Devuelve [a, b]. Comprueba que el retorno es la tupla, no el array union.
  3. Prueba: const par = crearPar("id", 7) y verifica par[0] sea string y par[1] number.
  4. Anade una propiedad nombre al resultado: extiende el generico para que el objeto resultante incluya un campo fijo.

Solucion paso a paso:

ejercicio-genericos.ts
function crearPar<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}

const par = crearPar("id", 7);
const clave: string = par[0];  // ✅ par[0] es string
const valor: number = par[1];  // ✅ par[1] es number

// Con un campo fijo anadido:
function crearParConNombre<A, B>(a: A, b: B): [A, B, string] {
  return [a, b, "par"];
}
const p2 = crearParConNombre(1, true); // [number, boolean, string]

8 · Reto

Reto

Implementa una clase generica Cache<K, V> con set(clave, valor), get(clave) (devuelve V | undefined) y un contador de accesos. No lo resuelvas aun: intenta primero que el get devuelva V | undefined y que el set acepte K y V. Pista: guarda internamente un Map<K, V>.

9 · Resumen

  • Los genericos son variables de tipo que se rellenan en el uso, conservando el tipo exacto.
  • Se usan en funciones, interfaces, type aliases y clases.
  • TypeScript infiere T del argumento; puedes anotarlo explicitamente cuando no puede.
  • Varios parametros de tipo preservan las relaciones entre argumentos y retorno.
  • En .tsx, usa <T,> para distinguir genericos de JSX.

10 · Preguntas frecuentes

¿Cuando escribo el tipo entre <> y cuando no?

Cuando la inferencia funciona (el tipo sale del argumento) no hace falta. Escribelo cuando no se pueda deducir: por ejemplo, cuando el generico solo aparece en el retorno, o cuando el argumento es any.

¿Que diferencia hay entre generico y any?

any desconecta por completo la comprobacion: no hay relacion entre lo que entra y lo que sale. Un generico enlaza los tipos: garantiza que lo que sale es del mismo tipo (o de un tipo derivado) de lo que entra.

¿Puedo poner genericos en arrow functions de .ts?

Si, sin problema: const id = <T>(v: T) => v;. El problema de JSX solo aparece en archivos .tsx, donde usas <T,>.

¿Los genericos existen en runtime?

No. TypeScript los borra en la compilacion (type erasure). Solo viven en tiempo de compilacion. Por eso no puedes hacer if (x instanceof T): T no existe en runtime.

¿Como pongo un tipo por defecto a un generico?

Con <T = unknown>. Asi, si no se infiere, T es unknown en vez de un error (util en componentes de libreria con opciones).

¿Puede una clase heredar de una clase generica?

Si: class PilaNumerica extends Pila<number>. La subclase fija el parametro de la base.
