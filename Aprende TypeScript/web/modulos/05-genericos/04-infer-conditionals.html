Infer y conditional types

Modulo 5 · Genericos 🕐 30 minutos

1 · Introduccion

Hasta aqui los tipos "describen". Con los conditional types los tipos deciden: T extends X ? A : B es el if/else a nivel de tipos. Combinado con la palabra clave infer, TypeScript puede deducir partes de un tipo (por ejemplo, el tipo de retorno de una funcion) sin que se las des tu.

Es lo avanzado de verdad: ReturnType, Parameters, Awaited (modulo 6) estan construidos exactamente con conditional types e infer. Tambien aparece en republicanas librerias como React o Prisma. Dominarlo es diferencia entre "usar tipos" y "programar con tipos".

Cuando se utilizan
  • Extraer tipos de retorno (ReturnType), de argumentos (Parameters).
  • Desempaquetar Promise, Array, genericos anidados (Awaited).
  • Tomar caminos segun la forma del tipo (condicional).
  • Implementar utilidades propias de tu libreria.

2 · Teoria

La analogia: la aduana de tipos

Imagina una aduana donde cada tipo tiene que "pasar un control". Si el tipo saca el pasaporte correcto (T extends X), va por un carril; si no, por otro. Y en el carril de "si", la aduana puede leer la etiqueta del equipaje: eso es infer, decir "extraeme lo que haya dentro de este tipo". La aduana no te dice el equipaje tu: lo lee de la estructura del tipo que llega.

Aduana: T extends Promise<infer R> ? R : T T = Promise<number> → "si", y leemos R = number T = number → "no", quedamos con T = number Resultado: desempaquetar promesas de un nivel.

Conditional types basicos

type EsArray<T> = T extends any[] ? "array" : "no-array";

type R1 = EsArray<number[]>;  // "array"
type R2 = EsArray<string>;     // "no-array"

La sintaxis completa: T extends X ? Y : Z. Es un ternario como el de JS, pero para tipos. La condicion es asignabilidad estructural: T extends X es cierto si T es asignable a X.

Infer: extraer de la estructura

// Desempaqueta el tipo de un array:
type ElementoDe<T> = T extends (infer U)[] ? U : never;

type X = ElementoDe<number[]>;  // number
type Y = ElementoDe<(string | boolean)[]>; // string | boolean

// Desempaqueta una Promise:
type AwaitedT<T> = T extends Promise<infer R> ? R : T;

type P = AwaitedT<Promise<number>>;   // number
type Plain = AwaitedT<string>;          // string (no es Promise, queda igual)
Como funciona infer

infer U en la parte izquierda del extends dice a TypeScript: "haz un hueco para deducir U de la estructura real de T, y si la deduccion es posible, dame U". Es un patron sobre la forma del tipo: (infer U)[] significa "cualquier array, y el tipo de sus elementos se llama U". Cuando no matchea, se toma la rama false (aqui never).

Multiple infer y posiciones

// T es una funcion: extraemos argumento y retorno a la vez.
type ArgsYRetorno<F> = F extends (...args: infer A) => infer R ? [A, R] : never;

type F = (id: number, nombre: string) => boolean;
type Info = ArgsYRetorno<F>;
// [[number, string], boolean]  (tupla de args + tipo de retorno)

// infer NO puede aparecer fuera de la clausula extends:
// type Mal = infer U; // ✖ error: infer solo es valido tras "extends"

Distributividad

Si la condicion se aplica sobre una union, el conditional type se distribuye: se aplica a cada miembro por separado. 

type A = "a" | "b";

// Distributivo: se evalua para "a" Y para "b" por separado.
type Distributivo<T> = T extends "a" ? 1 : 2;
type R = Distributivo<A>; // 1 | 2   (union de resultados)

// Sin distribuir mediante [ ]:
type NoDistributivo<T> = [T] extends ["a"] ? 1 : 2;
type R2 = NoDistributivo<A>; // 2 (T entera no es asignable a "a")

La distribucion es la clave de utilidades como Exclude y Extract (modulo 6).

Clausula never en la rama false

Cuando una condicion no matchea es habitual devolver never: asi el miembro "desaparece" de la union resultante (narrowing a nivel de tipos).

// Solo numeros de una union:
type SoloNumeros<T> = T extends number ? T : never;
type In = string | number | boolean;
type Out = SoloNumeros<In>; // number (los demas se convierten en never y se eliminan)

Conditional types y genericos diferidos

Si T es un generico no resuelto (por ejemplo dentro de una firma que no se instancia), lo conditional queda diferido: no se evalua hasta que el generico reciba su valor. Esto es lo que permite que el resultado "aparezca" en la llamada.

3 · Ejemplo minimo

infer-minimo.ts
// La utilidad mas clasica: ReturnType pero hecha a mano.
type MiReturnType<F extends (...args: any[]) => unknown> =
  F extends (...args: any[]) => infer R ? R : never;

function saludar(nombre: string): string {
  return `Hola ${nombre}`;
}

type R = MiReturnType<typeof saludar>; // string ✅

Linea a linea:

  • F extends (...args: any[]) => unknown restringe a "cualquier funcion".
  • En el conditional, ... => infer R dice a TS que deduzca el retorno de F.
  • Como toda funcion matchea, la rama false (never) casi nunca se usa, pero esta.
  • typeof saludar da el tipo real de la funcion; infer extrae string.

4 · Ejemplo real

Un despachador de eventos tipado que extrae los datos de cada evento segun su tipo:

eventos.ts
// Mapa de tipos de eventos reales de la app.
interface EventosMap {
  "usuario:creado": { id: number; nombre: string };
  "usuario:eliminado": { id: number };
  "pedido:pagado": { pedidoId: number; importe: number };
}

// Clave de evento: cualquiera de las claves del mapa.
type ClaveEvento = keyof EventosMap;

// Dado un evento, su payload es el tipo del valor en el mapa.
type PayloadEvento<K extends ClaveEvento> = EventosMap[K];

// Generic unico: handler generico usando conditional + indexed.
function emiteEvento<K extends ClaveEvento>(
  clave: K,
  payload: PayloadEvento<K>
): void {
  console.log(`[${clave}]`, payload);
}

// Cada evento con su payload exacto:
emiteEvento("usuario:creado", { id: 1, nombre: "Ana" });
emiteEvento("pedido:pagado", { pedidoId: 5, importe: 49.9 });

// ✖ no compila: el payload de "pedido:pagado" no tiene "nombre"
// emiteEvento("pedido:pagado", { pedidoId: 5, nombre: "x" });

Decisiones:

  • keyof EventosMap y EventosMap[K] mantienen cada evento atado a su payload (modulo 5, leccion 3).
  • El generic conditional no es estrictamente necesario aqui (basta el indexed), pero demuestra como se combinan: condicional para elegir, infer para extraer, indexed para el valor.
  • Si un dia cambia el payload de "usuario:creado", todos los emisores se actualizan en compilacion.

5 · Buenas practicas

  • Recurre a infer cuando quieras extraer un tipo de la estructura de otro (retorno, args, elemento de array, Promise resuelta).
  • Usa distributividad para filtrar unions (SoloNumeros<T>) antes de inventar loops manuales.
  • Devuelve never cuando no matchee: elimina los miembros no deseados de la union.
  • Si un conditional se enreda con genericos, encierra en [T] para evitar la distribucion accidental.
  • Prefiere utilidades del modulo 6 (ReturnType, Awaited) cuando encajen: menos codigo propio que mantener.

Que evitar

  • Colocar infer fuera de la clausula extends (no compila).
  • Condicionales sin rama never cuando quieres "filtrar".
  • Anidar conditional types sin comentarios: se vuelven ilegibles.
  • Ignorar que la distribucion cambia el resultado para unions.
  • Un uso prematuro: primero las utilidades; conditional types para casos que no existen en la stdlib.

6 · Errores habituales

Mal — usar infer fuera del extends 
// ✖ no compila: infer solo puede aparecer tras "extends"
type MiU = infer U;
Bien — infer dentro del patron del izquierda 
type MiU<T> = T extends Array<infer U> ? U : never; // ✅
Mal — olvidar la distribucion en una union 
type Cond<T> = T extends "a" ? 1 : 2;
type R = Cond<"a" | "b">; // 1 | 2 (distribuye, quizas no lo esperabas)
Bien — envolver en [] si quieres evaluar la union entera 
type CondNoDist<T> = [T] extends ["a"] ? 1 : 2;
type R = CondNoDist<"a" | "b">; // 2 (union entera)
Mal — never en mal lugar 
// Devuelve "nunca" en la rama correcta pero olvidada:
type Mal<T> = T extends string ? T : never;
// 💡 Si lo que quieres es "solo string", va bien. Solo cuidado con la rama.
Bien — pero si el limite es una union de claves, usa keyof 
type Solo

7 · Ejercicio guiado

Vamos a crear DesempaquetaPromesa que desempaquete promesas anidadas (varias capas).

  1. Define type PromesaInterna<T> = T extends Promise<infer R> ? PromesaInterna<R> : T;.
  2. Prueba PromesaInterna<Promise<Promise<number>>> — debe dar number.
  3. Recorre la recursion: si T es Promise, vuelve a aplicar sobre R.
  4. Si no es Promise, devuelve T (caso base).

Solucion paso a paso:

ejercicio-infer.ts
type PromesaInterna<T> =
  T extends Promise<infer R> ? PromesaInterna<R> : T;

// Caso base: no es una Promise, se queda igual.
// Caso recursivo: es Promise, desenrollamos una capa y seguimos.

type A = PromesaInterna<Promise<number>>;            // number
type B = PromesaInterna<Promise<Promise<boolean>>>;  // boolean
type C = PromesaInterna<string>;                      // string

// Es exactamente la miscion de Awaited (modulo 6):
type D = Awaited<Promise<Promise<number>>>; // number

8 · Reto

Reto

Implementa ExtractArgs<F> que, dada una funcion F, devuelva el tipo de sus argumentos (no la tupla, sino la union). Despues, escribe LastParam<F> que devuelva el tipo del ultimo argumento (pista: distribucion + never). No mires la solucion; intenta con infer y condicionales antes de abrir el contenido.

9 · Resumen

  • Conditional types: T extends X ? A : B, decision a nivel de tipos.
  • infer deduce parte del tipo desde la estructura (retorno, args, elemento).
  • Los conditional types se distribuyen sobre unions; [T] evita la distribucion.
  • never en la rama false "filtra" miembros de una union.
  • Son la base de ReturnType, Parameters, Awaited (modulo 6).

10 · Preguntas frecuentes

¿En que se diferencia infer de los genericos normales?

Los genericos declaras el agujero (<T>) y se rellena con el argumento que pasas. infer crea el agujero en medio del patron y TypeScript lo deduce de la estructura del tipo que matchea, sin que lo anotes.

¿Puedo usar conditional types dentro de mapped types?

Si, es la combinacion de modulos 5 y 6. Ejemplo: { [K in keyof T as ...]: T[K] extends number ? ... : ... }. Es como se filtra o transforma a la vez.

¿Cuando se evalúa realmente un conditional type?

Cuando todos sus parametros son concretos. Con genericos sin instanciar queda diferido; TypeScript lo evalua en el punto de uso (donde se resuelve T).

¿La distribucion es siempre deseable?

No. Es un comportamiento por defecto que conviene cuando filtras unions, pero molesta si quieres evaluar la union como "un solo tipo". Por eso el tip [T].

¿Puedo escribir una utilidad "ReturnType" mejor que la builtin?

La builtin ReturnType ya hace exactamente esto con infer. No reinventes ruedas: usala directamente (modulo 6). Escribir la tuya es util solo como ejercicio didactico.

¿Los conditional types afectan al rendimiento del compilador?

Si se usan con moderacion, no. Encadenar muchos across types diferidos puede ralentizar el compilador. Prefiere utilidades sencillas y evita deep recursion innecesaria (el compilador limita la profundidad de check).
