Instalacion: Vite, TypeScript y tsconfig.json

Modulo 0 · Preparacion 🕐 35 minutos

1 · Introduccion

En esta leccion montamos el entorno de desarrollo completo. Al terminar tendras: Node.js (para ejecutar JavaScript fuera del navegador), pnpm (gestor de paquetes), Vite (el dev server que compila y recarga tu codigo), TypeScript con su compilador tsc y un tsconfig.json entendido, que sera el "panel de control" de todos nuestros proyectos del curso.

No hacemos esto una vez y nos olvidamos: el tsconfig.json reaparece en todos los modulos. Por eso esta leccion te da la base conceptual para leerlo con soltura (en el modulo 7 lo desarmamos opcion a opcion).

2 · Teoria

Que es Node.js

Node.js es un runtime: un programa que ejecuta JavaScript fuera del navegador. Necesitamos Node por dos motivos: correr tsc (que es un programa JavaScript) y servir/compilar el codigo en desarrollo. Además, nuestro pnpm vive sobre el ecosistema npm de Node.

El tablero de piezas
Tu maquina ┌───────────────┬─────────────────┬──────────────────┐ │ Node.js │ pnpm │ Vite + tsc │ │ ejecuta JS │ instala pkgs │ compila TS │ └───────────────┴─────────────────┴──────────────────┘ ↑ ↑ base del sistema herramientas de proyecto

Por que pnpm y no npm

pnpm es un gestor de paquetes mas eficiente que npm: comparte dependencias entre proyectos (no las duplica), instala mas rapido y usa menos disco. Es el gestor recomendado de este curso, y su instalacion en la raiz del repositorio está declarada en package.json con la clave packageManager.

Que es Vite

Vite es el dev server moderno. Su trabajo: tomar tu codigo TypeScript (o React), compilarlo al vuelo y servirte una web con hot reload (cambias una linea y el navegador se actualiza al instante). Usa esbuild/rolldown para transformar TS a JS de forma rapidisima; no es un sustituto de tsc para comprobar tipos, por eso configuramos ambos: Vite para velocidad, tsc para seguridad.

Que es tsc y que hace el tsconfig.json

tsc es el compilador de TypeScript. Con TypeScript 7 ya no es JavaScript: es el port nativo en Go, ~10x mas rapido, pero usa exactamente la misma configuracion y sintaxis (compatible con TS 5.9+). El tsconfig.json le dice:

  • Que ficheros compilar (include/exclude).
  • Con que estrictitud (strict, noUnusedLocals, exactOptionalPropertyTypes...).
  • Hacia donde emitir el JavaScript (outDir, module, target).
  • Como resolver importaciones (moduleResolution, paths).

Es el unico fichero de configuracion que define como se comporta el lenguaje en tu proyecto.

Por que tantas herramientas

Separamos "compilar rapido" (Vite) de "revisar tipos" (tsc) porque hacen cosas distintas. Vite quita los tipos y entrega JS; tsc --noEmit solo comprueba errores de tipos sin generar nada. En produccion veremos en el modulo 8 como se combinan. Nada de esto es magia: es trabajo en cadena.

3 · Ejemplo minimo

La forma mas rapida de probar TypeScript es un fichero suelto fuera de cualquier framework.

Paso 1 — Verificar Node y pnpm

node --version    # v22.x o superior
pnpm --version    # v11.x o superior

Si pnpm no esta instalado:

corepack enable && corepack prepare pnpm@latest --activate

Paso 2 — Un fichero TypeScript suelto

hola.ts
// Declaramos una funcion tipada.
function saludo(nombre: string): string {
  return `Hola, ${nombre}`;
}

console.log(saludo("TypeScript"));

Paso 3 — Compilar con tsc

pnpm dlx tsc hola.ts       # genera hola.js
node hola.js                # ejecuta: Hola, TypeScript

pnpm dlx descarga y ejecuta tsc sin instalarlo en tu proyecto. Asi de simple: fichero TS → tsc → JavaScript que ejecuta Node.

4 · Ejemplo real

Para proyectos de verdad (incluidos los de los modulos 8 y 9) usamos Vite como base. Creamos un proyecto con Vite + TypeScript desde cero: 

# 1. Crea el proyecto con la plantilla vanilla-ts (TypeScript puro)
pnpm create vite mi-proyecto --template vanilla-ts

# 2. Entra y activa el entorno
cd mi-proyecto
pnpm install

# 3. Arranca el dev server (Vite) con recarga en caliente
pnpm dev

La estructura generada:

mi-proyecto/ ├── index.html ← punto de entrada de la web ├── package.json ← scripts y dependencias ├── tsconfig.json ← configuracion de TypeScript (la vemos abajo) ├── vite.config.ts ← configuracion de Vite └── src/ ├── main.ts ← arranque de la aplicacion ├── style.css └── vite-env.d.ts ← tipos de entorno de Vite

El tsconfig.json que genera Vite (simplificado)

tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",          // version de JavaScript para el codigo emitido
    "module": "ESNext",           // modulos ES nativos (import/export)
    "moduleResolution": "bundler", // como Vite resuelve importaciones
    "strict": true,               // activa todas las comprobaciones estrictas
    "noEmit": true,               // tsc SOLO revisa tipos, no genera JS (eso lo hace Vite)
    "isolatedModules": true,      // cada fichero se compila por separado (necesario en Vite)
    "jsx": "react-jsx",           // solo si usamos React (modulo 8)
    "skipLibCheck": true          // no revisar tipos dentro de node_modules
  },
  "include": ["src"]
}

Explicacion de las opciones clave:

OpcionQue hacePor que nos interesa
strictActiva ~10 comprobacionesEs el modo profesional; lo usamos SIEMPRE en el curso
noEmittsc no escribe JSLa emision la hace Vite; tsc solo avisa de errores
moduleResolution: bundlerResolucion moderna de importsLa que usa Vite; necesaria para exports con extensiones
isolatedModulesCompila fichero a ficheroPre-requisito para el build rapido de Vite
Consejo de depuracion

Con Vite, pnpm build lanza tsc --noEmit ANTES de generar los ficheros de produccion. Si hay un error de tipos, el build falla. Es nuestra red: comprobamos tipos (tsc) y luego generamos JS (Vite/rolldown).

5 · Buenas practicas

  • Mantener strict: true siempre. Desactivarlo "para hacer pruebas" genera deuda.
  • Un solo tsconfig.json en la raiz del proyecto, con include acotado.
  • Versionar el package.json y el lockfile (pnpm-lock.yaml) para builds reproducibles.
  • Usar pnpm dlx para herramientas ocasionales y pnpm add para dependencias de proyecto.
  • Poner Node v20+ (idealmente la LTS de tu distro): tsc 5.9/7 exige Node >= 18.

Que evitar

  • Instalar TypeScript de forma global con npm i -g: crea conflictos de version entre proyectos.
  • Copiar tsconfig de internet sin entenderlo: cada proyecto merece el suyo.
  • Mezclar gestores (npm y pnpm) en el mismo proyecto: usa uno solo, en este curso pnpm.

6 · Errores habituales

Mal — tsc no encuentra TypeScript 
tsc --version       # ✖ comando no encontrado
Bien — usar pnpm dlx o la dependencia local 
pnpm dlx tsc --version
pnpm exec tsc --version   # si pnpm add -D typescript
Mal — copiar tsconfig ajeno con "esModuleInterop" olvidado

Importar una libreria CommonJS con import x from "lib" falla si falta esModuleInterop. Es un clásico del "tsconfig copia-pega".

Bien — generarlo con la base recomendada 
{
  "compilerOptions": {
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "module": "ESNext",
    "target": "ES2022",
    "moduleResolution": "bundler"
  }
}

Por que estan mal: un comando inexistente indica que olvidaste instalar/declarar la herramienta; un tsconfig copiado arrastra opciones pensadas para otro contexto (Node, web, React...) y produce errores confusos a medio camino.

7 · Ejercicio guiado

Configura un proyecto TypeScript minimo por tu cuenta (sin Vite, para sentir tsc puro):

  1. Crea una carpeta mini-ts y dentro index.ts con una funcion tipada que devuelva la longitud de una cadena.
  2. Ejecuta pnpm init y pnpm add -D typescript.
  3. Genera el tsconfig: pnpm exec tsc --init --strict.
  4. Compila y ejecuta: pnpm exec tsc && node index.js.
Solucion

tsc --init --strict crea un tsconfig.json completo con strict activo. Al compilar, el JS emitido estara junto a index.ts. VSCode marca los errores de tipos en rojo mientras escribes incluso antes de compilar.

8 · Reto

Reto

En tu mini-ts, desactiva strict temporalmente en el tsconfig, escribe una funcion que reciba x sin tipar y asignale x a un number. Despues reactiva strict y observa las diferencias de errores. Anota TU conclusion: ¿que es lo que ganas con strict?

9 · Resumen

  • Herramientas: Node.js (ejecuta JS), pnpm (gestor), Vite (dev server + build), tsc (revisa tipos), tsconfig.json (configuracion del lenguaje).
  • tsc --init --strict activa la configuracion estricta recomendada.
  • Vite y tsc cumplen funciones distintas: transformar vs comprobar. En Vite usamos noEmit.
  • TypeScript 7 mantiene el mismo tsconfig y sintaxis que 5.9+; solo cambia la velocidad del compilador.
  • Siempre pnpm, nunca npm, en todos los comandos del curso.

10 · Preguntas frecuentes

¿Por que instalar TypeScript como dependencia del proyecto y no global?

Cada proyecto fija su version en package.json. Con un tsc global, dos proyectos podrian necesitar versiones distintas y un dia no sabras cual compila. La dependencia local es reproducible.

¿Vite revisa mis tipos? ¿Por que entonces "tsc"?

Vite/esbuild quitan los tipos sin comprobarlos (rapido pero ciego). tsc --noEmit si los comprueba. Por eso el proceso de build de Vite ejecuta tsc antes de empaquetar: velocidad + seguridad.

En TypeScript 7, ¿hay que cambiar el tsconfig?

No. El port nativo en Go acepta exactamente el mismo tsconfig.json y las mismas opciones que tsc 5.9.

¿Por que Vite y no Webpack/Babel?

Vite es muchisimo mas rapido en desarrollo (usa transformaciones nativas) y su configuracion es minima. Babel para TS quedo como alternativa legacy.

¿Que Node necesito?

Node 18+ como minimo para TS 5.9; Node 20+ o 22 LTS recomendado para todo el stack del curso. corepack te da pnpm sin instalaciones extra.
