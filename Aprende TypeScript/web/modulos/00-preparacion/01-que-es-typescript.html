Que es TypeScript y por que existe

Modulo 0 · Preparacion 🕐 25 minutos

1 · Introduccion

En esta leccion vas a entender de verdad que es TypeScript, porque existe y que problema concreto resuelve. No vamos a escribir mucho codigo todavia: primero necesitas tener el mapa mental correcto, porque la mayoria de la gente aprende TypeScript como "JavaScript con tipos" y eso te deja sin la mitad de la historia.

Si ya sabes JavaScript, ya conoces un lenguaje increiblemente flexible. Este curso te ensena la otra cara de la moneda: como hacer que esa flexibilidad no se convierta en una trampa cuando el proyecto crece.

Por que existe

JavaScript nacio en 1995 como un lenguaje para animar paginas web. Porta cualquier error a produccion: si escribes mal un nombre de propiedad, no te enteras hasta que el usuario llega a esa pantalla. TypeScript existe para adelantar esos errores al momento de escribir el codigo.

Cuando se utiliza: en cualquier proyecto JavaScript que supere las pocas lineas: apps web, APIs, herramientas de linea de comandos, librerias compartidas en un equipo.

Errores tipicos: pensar que TypeScript "impone" tipos sin dejar libertad (falso), o creer que es un lenguaje completamente nuevo que hay que aprender desde cero (tambien falso).

2 · Teoria

JavaScript es un lenguaje con tipos… sueltos

Todo valor en JavaScript tiene un tipo (string, number, object…). El problema no es que "JavaScript no tenga tipos": es que a nadie le importa cuando una funcion recibe un argumento. La pregunta clave es: 

// JavaScript puro: ¿que tipo recibe "x"? ¿Que devuelve la funcion?
function duplicar(x) {
  return x * 2;
}

console.log(duplicar("hola")); // ¿Que pasara aqui?

En JavaScript esto ejecuta sin ninguna queja. El resultado es NaN (Not a Number), y nadie se entera hasta que el codigo ya esta corriendo en un navegador real, con un usuario delante. Eso es lo que llamamos un tipo de error dinamico: el problema existe, pero solo se materializa en tiempo de ejecucion.

Analogia: el seguimiento de paquetes

JavaScript es como enviar un paquete sin etiqueta: el correo (el navegador) lo transporta igual, pero si se pierde nadie sabe de quien era. TypeScript es poner la direccion completa antes de enviarlo: una capa de revision (el compilador) comprueba que todo cuadre antes de salir, y te devuelve el paquete si algo no encaja.

TypeScript: un superconjunto de JavaScript

TypeScript es exactamente JavaScript, mas un sistema de tipos opcional. Todo codigo JavaScript valido es tambien TypeScript valido. La relacion se ve asi:

Lenguaje TypeScript ┌─────────────────────────────────────────────┐ │ ┌───────────────────────────────────────┐ │ │ │ JavaScript (todo lo que ya sabes) │ │ │ │ if, for, objetos, fetch, async... │ │ │ └───────────────────────────────────────┘ │ │ ┌───────────────────────────────────────┐ │ │ │ Tipos y herramientas extra │ │ │ │ : number, interface, genericos... │ │ │ └───────────────────────────────────────┘ │ └─────────────────────────────────────────────┘ Todo codigo JS valido → tambien es TS valido.

El compilador tsc (TypeScript Compiler) coge tu codigo con tipos, los comprueba, y despues los borra generando JavaScript limpio y estandar que cualquier navegador entiende. Por eso a TypeScript se le llama a veces "JavaScript que se revisa solo antes de salir".

Desde TypeScript 7 (la version estable mas reciente) el compilador esta escrito en Go en lugar de JavaScript, lo que lo hace unas 10 veces mas rapido. No cambia lo que escribe el compilador ni la sintaxis: cambia la velocidad. Todo el codigo de este curso compila sin cambios en TypeScript 5.9+.

Tipado estatico vs dinamico

Hay dos filosofias de tipado:

  • Tipado dinamico (JavaScript): los tipos se comprueban mientras el codigo se ejecuta. Flexibilidad maxima, errores tardios.
  • Tipado estatico (TypeScript, Java, C#, Rust): los tipos se comprueban antes de ejecutar, en "tiempo de compilacion". Mas trabajo al escribir, pero el editor y el compilador te avisan inmediatamente.

Recorda esta idea central de todo el curso:

El contrato

Escribir el tipo es firmar un contrato: "esta funcion espera un numero y devuelve una cadena". El compilador lo hace cumplir. Tu, como autora o autor, defines el contrato; el compilador es el poli que lo vigila.

La filosofia de diseno de TypeScript

Cuatro principios guian cada decision de diseno del lenguaje:

  1. JavaScript primero. Cualquier programa JS debe poder migrar sin reescribirse.
  2. Tipos opcionales y progresivos. Puedes tipar toda una app o solo una funcion; el resto se infiere.
  3. Ayudarte sin mentir. El compilador intenta adivinar tipos (inferencia) pero te avisa cuando su suposicion puede esconder un error.
  4. Estructural, no nominal. Dos objetos con la misma forma son del mismo tipo, aunque no compartan nombre de clase. Lo veras a fondo en el módulo 2.

3 · Ejemplo minimo

ejemplo-minimo.ts
// Anotamos el tipo del parametro con ":" seguido del tipo.
// Ahora "x" SOLO puede ser un numero y el compilador lo garantiza.
function duplicar(x: number): number {
  return x * 2;
}

// Llamada correcta: recibe un numero y devuelve un numero.
const resultado = duplicar(21); // resultado: number, vale 42

// Llamada INCORRECTA: el compilador la rechaza ANTES de ejecutar nada.
// duplicar("hola"); // ✖ error TS2345: string no es asignable a number

Explicacion linea por linea:

  1. x: number le dice al compilador "aqui solo puede entrar un numero".
  2. : number al final de la firma declara que la funcion devuelve un numero.
  3. La segunda llamada (comentada) provocaria el error TS2345 en el editor, antes de ejecutar el programa.
La prueba del poder

La llamada duplicar("hola") no llega ni a compilarse. En JavaScript te enterabas en produccion; en TypeScript te enteras con el subrayado rojo mientras escribes. Ese subrayado rojo es el superpoder que vas a aprender a producirlo y leerlo en todo el curso.

4 · Ejemplo real

Imagina una tienda online con descuentos. En la version JavaScript, un descuento mal calculado se propaga silenciosamente por toda la factura. Con TypeScript, el compilador nos fuerza a tomar decisiones explicitas desde el primer momento.

carrito.ts
// Modelamos el carrito con una forma concreta: un objeto de LINEAS.
// Cada linea tiene productos y una cantidad parcial.

// interface declara la FORMA de un objeto (veremos esto en el modulo 2).
interface Linea {
  producto: string;   // nombre del producto
  precio: number;     // precio unitario en euros
  cantidad: number;   // unidades compradas
}

// Recibe un array de lineas y devuelve el subtotal.
// El parametro "carrito: Linea[]" significa "array de objetos que cumplen Linea".
function subtotal(carrito: Linea[]): number {
  // reduce va sumando precio * cantidad de cada linea.
  return carrito.reduce((total, linea) => total + linea.precio * linea.cantidad, 0);
}

// Aqui construimos un carrito. El compilador valida que cumpla interface Linea.
const miCarrito: Linea[] = [
  { producto: "Teclado mecanico", precio: 89, cantidad: 1 },
  { producto: "Mouse", precio: 39, cantidad: 2 },
];

// sin "types" todavia, si escribieramos miCarrito[0].precio = "noventa"
// el compilador lo rechazaria: precio es number, no string.
console.log(`Subtotal: ${subtotal(miCarrito)} €`);

Decisiones de diseno:

  • Linea[] documenta la forma del dato: el compilador y los demas devs ven el contrato sin leer tu implementacion.
  • Si alguien añade un campo por error o cambia el nombre de cantidad, el compilador fallara en todos los usos, no solo en el sitio del cambio.
  • El refactor se vuelve seguro: cambiar el nombre de una propiedad actualiza todos los usos (VSCode lo hace automaticamente con F2).
Refactor seguridad

En JavaScript puro, renombrar linea.precio a linea.precioUnitario puede dejar coordenadas rotas que solo aparecen en ejecucion. TypeScript lo detecta al instante: "propiedad no existe en el tipo Linea". Por eso los refactors en equipos con TypeScript son mucho menos aterradores.

5 · Buenas practicas

Que hacer

  • Activa strict en tsconfig.json desde el primer dia. Es el modo correcto y lo usaremos en todo el curso.
  • Deja que el compilador infiera los tipos simples: escribir const nombre: string = "ana" es ruido. Omite lo obvio.
  • Tipa siempre los limites: firmas de funciones, forma de los datos externos (API), objetos compartidos.
  • Adopcion progresiva: si heredas un proyecto JS, tipalo por ficheros poco a poco.

Que evitar

  • No usar any como escotilla para acallar al compilador (lo veremos en el modulo 1: any, unknown, never).
  • No anotar todo en exceso: TypeScript escribe mucho por ti; no compitas con el.
  • No desactivar strict para "ir mas rapido": es exactamente el tipo de velocidad que luego pagas en bugs.

Por que

Los tipos son documentacion ejecutable que nunca se queda obsoleta. La mayor parte del valor aparece en proyectos medianos y grandes, cuando el codigo cambia constantemente y los equipos crecen. En quiza 500 lineas de codigo personal, JavaScript y TypeScript se notan poco; en 50.000 lineas con 5 personas, la diferencia es enorme.

6 · Errores habituales

Mal — tratar los tipos como si fueran "clases de Java" 
// Error: JavaScript ya tiene "string", "number"... no hagamos esto.
// (En realidad esto ni siquiera es util: typeof devuelve "string".)
const tipo = typeof miVariable === "string" ? "texto" : "otra cosa"; // con fusion pero confuso
Bien — usa inferencia, escribe solo lo necesario 
// Inferencia: el compilador ya sabe que es string.
const nombre = "ana";
Mal — acallar errores con any sin pensar 
function obtenerPrecio(item: any) { // any destruye toda la seguridad
  return item.precio;               // si NO existe, error en runtime
}
Bien — tipar la forma del dato 
interface Item { precio: number }

function obtenerPrecio(item: Item): number {
  return item.precio; // el compilador garantiza que existe
}

Por que estan mal: any desactiva el compilador exactamente en la zona que mas necesitas. Con la forma tipada, el error es imposible de producir: no hay forma de llamar a la funcion sin un objeto que tenga precio.

7 · Ejercicio guiado

Vamos a convertir una funcion JavaScript en TypeScript, paso a paso.

Punto de partida (JavaScript) 
function aplicarImpuesto(importe, porcentaje) {
  return importe + importe * (porcentaje / 100);
}
  1. Tipa los parametros como number.
  2. Añade el tipo de retorno : number.
  3. Comprueba que una llamada con una cadena da error de compilacion.
Solucion 
function aplicarImpuesto(importe: number, porcentaje: number): number {
  return importe + importe * (porcentaje / 100);
}

console.log(aplicarImpuesto(100, 21)); // 121
// aplicarImpuesto("100", 21);        // ✖ error TS2345

Fijate en que el cuerpo de la funcion no cambio en absoluto: solo se tiparon los limites.

9 · Resumen

  • TypeScript es un superconjunto de JavaScript: todo JS valido, mas un sistema de tipos opcional.
  • Resuelve el problema de los errores dinamicos tardios, adelantando el fallo al momento de escribir el codigo.
  • El compilador tsc comprueba los tipos (tiempo de compilacion) y luego los borra generando JavaScript limpio.
  • La inferencia te permite escribir pocas anotaciones y obtener mucha seguridad.
  • La ultima version estable es TypeScript 7: compilador nativo en Go, ~10x mas rapido y compatible con 5.9+.
  • Conceptos clave aprendidos: superconjunto, tipado estatico vs dinamico, contrato, strict.

10 · Preguntas frecuentes

¿TypeScript es un lenguaje de programacion distinto?

No. Es un superconjunto de JavaScript creado por Microsoft. La sintaxis es JS mas anotaciones de tipo que desaparecen en el build. Cualquier dev de JS puede leer TS al dia siguiente.

¿El navegador entiende TypeScript?

No. El navegador ejecuta JavaScript. El compilador tsc (o Vite/esbuild en el build) transforma tu TS en JS compatible antes de servirlo.

¿Debo tipar "todo de forma explicita"?

No. La inferencia ya cubre la mayoria de los casos locales. Anota las firmas publicas, los datos de entrada y lo que cruce limites del sistema. Resto: deja que el compilador trabaje.

¿Por que esta version es "7" y que cambio con el compilador Go?

TypeScript 7 (julio 2026) es el port nativo de tsc a Go. Mantiene compatibilidad de sintaxis y de tipos con las versiones 5.x/6.x, pero compila entre 8 y 12 veces mas rapido. Este curso usa la sintaxis estable 5.9+ que funciona en todas ellas.

¿Puedo usar TypeScript en el servidor con Node.js?

Si. Node ejecuta JavaScript; compilas tu TS 7 con tsc o usas un runtime que lo ejecute directo. Lo configuro en la leccion de instalacion.
