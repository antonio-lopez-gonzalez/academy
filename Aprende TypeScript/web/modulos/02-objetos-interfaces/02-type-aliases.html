Type aliases vs interfaces

Modulo 2 · Objetos e interfaces 🕐 30 minutos

1 · Introduccion

Tras usar interface, descubrimos que type tambien describe objetos. ¿Entonces cual usamos? Esta leccion resuelve la pregunta de una vez: explicamos que son, que pueden hacer cada uno y cual es la regla de oro acordada por la comunidad. El pecado de los principiantes es pensar "son casi lo mismo" y perder matices que en proyectos grandes se notan.

2 · Teoria

Type alias: un nombre para cualquier tipo

Un type alias es un alias: le pones nombre a cualquier tipo que ya describes. Puede ser un objeto, una union, una tupla, un primitivo... cualquier expresion de tipo. 

type Usuario = { nombre: string; email: string }; // objeto
type Id = number;                                   // primitivo
type Resultado = "ok" | "error";                    // union de literales
type Coordenadas = [number, number];                // tupla
type Callback = (error: Error | null) => void;      // funcion

Dentro del modulo 5 lo explotamos con genericos, pero lo importante ahora: type te da un nombre a cualquier tipo, no solo a objetos.

Interface: forma de un objeto (o clase)

Una interface declara una forma de objeto (y puede ser implementada por clases o extendida). Es magica en dos sentidos:

  • extends: hereda de otras interfaces y de tipos de objetos.
  • Declaration merging: puedes declarar una interface con el mismo nombre dos veces y se fusionan.
interface Usuario {
  nombre: string;
}

// extends: amplia la forma.
interface Admin extends Usuario {
  permisos: string[];
}

const admin: Admin = { nombre: "Ada", permisos: ["all"] }; // ✅

Declaration merging

// Fichero establece que Usuario tiene "nombre".
interface Usuario { nombre: string; }

// Otro fichero (o la misma) aporta "email" → se FUSIONAN.
interface Usuario { email: string; }

const u: Usuario = { nombre: "Ada", email: "a@d.ts" }; // ✅ ambas

Esto sirve para ampliar tipos de librerias (patches). type NO puede fusionarse: declarar el mismo alias dos veces es un error.

Lo que interface NO puede y type SI

type Mixto = string | number;                    // union → interface no puede
type Tupla = [nombre: string, valor: number];    // tupla
type Obj = { a: number } & { b: string };        // interseccion (con type)
type Recursivo = { valor: T; hijos: Recursivo[] }; // requiere interfaz CUIDADO: ver abajo

interface no puede representar uniones ni tuplas ni primitivos. Solo formas de objetos.

Regla de oro (recomendada hoy)

Cuando usar cada uno

Interface para formas de objetos publicas que quieres poder extender y fusionar (muy comun en librerias). type para todo lo demas: uniones, tuplas, alias, o cuando quieres una forma cerrada que no se extienda. Si estas dudando, la recomendacion general de la guia de estilo oficial (TypeScript Handbook y toolkits como typescript-eslint) es: usar type por defecto y interface cuando necesites los superpoderes.

Un detalle delicado: interseccion y formas redondas

Para componer objetos con type usamos & (interseccion). Para interfaces usamos extends. Con propiedades en conflicto (misma clave, tipos distintos), la interseccion produce un tipo imposible (never) mientras extends marca error claro. 

type A = { x: string };
type B = { x: number };
type AB = A & B; // x: string & number → practicamente never. PELIGRO

Por eso, para formas de objeto simples, la interface con extends es mas segura.

3 · Ejemplo minimo

alias-vs-interfaz.ts
// Interface: forma de objeto extendible.
interface Figura {
  area(): number;
}

interface Cuadrado extends Figura {
  lado: number;
}

// Type: union, mas flexible.
type Resultado = Cuadrado | { radio: number };

// Implementacion:
const cuad: Cuadrado = { lado: 4, area: () => 16 };
console.log(cuad.area()); // 16

4 · Ejemplo real

Un tipado mixto en un servicio de paginas. Combinamos ambos de forma coherente:

paginas.ts
// Estado de carga posibilidades → TYPE (union).
type EstadoCarga = "cargando" | "exito" | "error";

// Datos comunes de cualquier pagina → INTERFACE (una forma reutilizable y extendible).
interface Pagina {
  titulo: string;
  ruta: string;
}

// Una pagina de "exito" extiende la forma base → INTERFACE con extends.
interface PaginaExitosa extends Pagina {
  contenido: string[];
}

// El resultado final que devuelve un servidor → TYPE (union de estados
// con dato o mensaje). Mezclamos union + objeto.
type RespuestaPagina =
  | { estado: "cargando" }
  | { estado: "exito"; pagina: PaginaExitosa }
  | { estado: "error"; mensaje: string };

// Funcion que dado el estado devuelve el titulo a mostrar.
function tituloDe(respuesta: RespuestaPagina): string {
  switch (respuesta.estado) {
    case "exito": return respuesta.pagina.titulo;
    case "error": return `Error: ${respuesta.mensaje}`;
    default: return "Cargando..."; // el estado "cargando" cae aqui
  }
}

console.log(tituloDe({ estado: "exito", pagina: { titulo: "Inicio", ruta: "/", contenido: ["Hola"] } }));

Decisiones:

  • EstadoCarga es una union → type.
  • Pagina y PaginaExitosa son formas de objeto reutilizadas → interface con extends.
  • RespuestaPagina es una discriminated union (el campo estado discrimina): union de objetos → type.
  • El switch por estado estrecha "por ramas"; volveremos a esto en el modulo 4.

5 · Buenas practicas

  • Por defecto usa type: cubre el 90% y no da superpoderes que no quieres.
  • Usa interface cuando quieras extends, implementacion por clases, o cuando escribes una libreria donde los consumidores deban poder extender/fusionar.
  • nunca mezcles interface y type para lo mismo en el mismo proyecto sin razon: la consistencia importa.
  • Para uniones siempre type. Para formas cerradas que no deben extenderse, type.
  • Documenta la eleccion en el styleguide del equipo: es una de las pocas decisiones de "gusto" tipado.

Que evitar

  • Usar interface para uniones/tuplas/primitivos: directamente ilegal.
  • Intersecciones & con claves en conflicto: crean never silencioso.
  • Depender del declaration merging en codigo de aplicacion sin necesidad (funciona, pero hace el tipo menos predecible).

6 · Errores habituales

Mal — interface con union 
interface Estado = string | number; // ✖ no es una interface valida
Bien — type para union 
type Estado = string | number; // ✅ union con type
Mal — interseccion con conflicto silencioso 
type A = { id: string };
type B = { id: number };
type AB = A & B; // id: string & number = never → imposible de crear
Bien — detectar el conflicto con extends 
interface A { id: string }
interface B { id: number }
// interface AB extends A, B {}  // ✖ TS2312/TS2300: propiedades incompatibles (claro)
Mal — esperar que type se fusione 
type Usuario = { nombre: string };
type Usuario = { email: string }; // ✖ Duplicate identifier 'Usuario'
Bien — interface para fusionar 
interface Usuario { nombre: string }
interface Usuario { email: string } // ✅ se fusiona

9 · Resumen

  • type: alias para cualquier tipo (union, tupla, primitivo, objeto, funcion).
  • interface: forma de objeto, con extends y declaration merging.
  • Union, tupla, primitivos → solo con type.
  • Regla pragma: type por defecto, interface cuando quieras extender/fusionar o para librerias publicas.
  • La interseccion & con claves en conflicto genera never; extends da error claro.

10 · Preguntas frecuentes

¿Queda "interface" obsoleta?

No. Sigue siendo imprescindible en librerias y clases. Pero para aplicaciones, la guia de estilo ligera prefiere type. Ambas son tipos de primera clase; usalas por criterio, no por costumbre.

¿Puedo hacer un type de una union y usarlo en interface?

No directamente: la propiedad contendria la union, pero una interface no se "convierte" en union. Si necesitas union, ya es type.

¿Por que a veces veo interfaces fusionadas por librerias?

Es el declaration merging. Librerias como React lo usan para extender props o eventos desde el fichero de tipos. Es un superpoder solo disponible en interfaces.

¿Puedo implementar una interface con una clase?

Si: class Admin implements Usuario { ... }. también puedes implementar un type si es una forma de objeto. La palabra clave implements comprueba que la clase cumpla la forma.

¿Que es "excess property check"?

Cuando asignas un literal de objeto a un tipo con menos propiedades, TypeScript lo rechaza (exceso) para evitar coordenadas incompatibles. Con variables normales no: los objetos ya tipados con extras se toleran. Aparece mucho en las siguiente lecciones.
