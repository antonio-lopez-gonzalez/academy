Interfaces, opcionales y readonly

Modulo 2 · Objetos e interfaces 🕐 30 minutos

1 · Introduccion

Los objetos son la estructura de datos por excelencia en JavaScript. Aqui aprendemos a declarar la forma de un objeto con interface: que propiedades tiene, de que tipo, cuales pueden faltar (opcionales), y cuales no se pueden modificar (readonly).

Es el paso siguiente natural: si sabes tipar un numero y un array, ahora vas a tipar el mundo real — un usuario, un pedido, una configuracion — como una pieza con su molde.

2 · Teoria

El tipado estructural: la forma, no el nombre

TypeScript comprueba objetos por forma. Si dos objetos tienen las mismas propiedades con los mismos tipos, son compatibles aunque provengan de clases o nombres distintos. Esto se llama tipado estructural (o duck typing: "si nada como pato y suena como pato, es un pato"). 

interface Pato { come: () => void }
const patoReal = { come: () => console.log("como") }; // encaja: tiene "come"

En otros lenguajes tipados (Java, C#) importa la declaracion: dos clases con la misma forma pero distinto nombre NO son compatibles. En TypeScript esa compatibilidad se basa en la forma. Esto hace que TypeScript sea mucho mas compatible con el mundo JavaScript real (JSON, librerias).

Sintaxis basica de interface

interface Usuario {
  nombre: string;    // propiedad requerida
  email: string;     // propiedad requerida
}

// Objeto que cumple la interface:
const usuario: Usuario = { nombre: "Ada", email: "ada@dev.ts" };

// Faltar una propiedad es un error de compilacion:
// const mal = { nombre: "Ada" };  // ✖ falta "email"

Propiedades opcionales con ?

El ? marca que la propiedad puede no existir (o ser undefined):

interface Perfil {
  nombre: string;
  ciudad?: string;   // opcional: puede estar o no
}

const conCiudad: Perfil = { nombre: "Grace" };
const conTodo: Perfil = { nombre: "Grace", ciudad: "Madrid" };
// ambos validos
Opcional NO es "obligatoria con valor raro"

ciudad?: string significa "propiedad ausente o undefined". No significa "puede ser cualquier string raro". Al usarla debes comprobar si existe: perfil.ciudad?.toUpperCase() o un if.

readonly: propiedades de solo lectura

interface Config {
  readonly version: string;   // se puede leer, no reasignar
  puerto: number;
}

const cfg: Config = { version: "1.0", puerto: 3000 };
// cfg.version = "2.0";  // ✖ error TS2540: readonly
cfg.puerto = 4000;        // ✅ normal

readonly en objetos se aplica en el momento de crear el valor: puedes escribir la propiedad al construirlo, pero no volver a asignarla despues. Muy util para datos de configuracion o identificadores. Nota: readonly no "congela" objetos anidados; solo protege esa propiedad.

Metodos en interfaces

interface Auto {
  marca: string;
  arrancar(): void;   // metodo sin retorno
  kmRecorridos: (km: number) => number; // opción como propiedad funcion
}

Las dos notaciones son practicamente equivalentes; la primera (arrancar(): void) es la que veras con mas frecuencia en props de React y librerias.

Interfaces anidadas y reutilizacion

interface Direccion {
  calle: string;
  codigoPostal: string;
}

interface Cliente {
  nombre: string;
  direccion: Direccion;   // compone interfaces
  pedidos?: Pedido[];
}

Las interfaces se anidan en árbol como los objetos JSON. Tipa una vez la Direccion y reusala en todos los sitios. Eso es DRY aplicado a los tipos.

3 · Ejemplo minimo

interfaz-minima.ts
// La interface declara la forma: nombre y email requeridos.
interface Usuario {
  nombre: string;
  email: string;
}

function bienvenida(u: Usuario): string {
  return `Hola ${u.nombre}`;
}

// Un objeto que cumple la forma:
const u: Usuario = { nombre: "Ada", email: "ada@dev.ts" };

console.log(bienvenida(u)); // "Hola Ada"

// Metodo como propiedad funcion:
interface Saludo {
  (nombre: string): string;
}
const saluto: Saludo = (nombre) => `Hola ${nombre}`;

4 · Ejemplo real

Un sistema de productos con precios, stock y categorias opcionales:

productos.ts
// Una categoria es un objeto con id, nombre y descripcion opcional.
interface Categoria {
  id: number;               // identificador unico
  nombre: string;
  descripcion?: string;     // puede que no se defina
}

// Un producto referencia su categoria y tiene precio (float).
interface Producto {
  id: number;               // identificador readonly
  readonly sku: string;     // codigo de barras: no se reasigna
  nombre: string;
  precio: number;
  stock: number;
  categoria: Categoria;     // categoria anidada
  enOferta?: boolean;       // opcional: false por defecto
}

// Un carrito es la lista de lineas.
interface Carrito {
  productos: readonly Producto[];  // lista de solo lectura
}

function precioTotal(carrito: Carrito): number {
  // reduce suma cada precio (si enOferta, aplica 10%).
  return carrito.productos.reduce((acc, p) => {
    return acc + (p.enOferta ? p.precio * 0.9 : p.precio);
  }, 0);
}

const teclado: Producto = {
  id: 1,
  sku: "KB-001",
  nombre: "Teclado mecanico",
  precio: 89,
  stock: 10,
  categoria: { id: 3, nombre: "Perifericos" }, // descripcion opcional omitida
  enOferta: true,
};

const miCarrito: Carrito = { productos: [teclado] as const };
console.log(precioTotal(miCarrito)); // 80.1

Decisiones:

  • readonly sku: el codigo de barras de un producto no cambia; el compilador lo hace valer.
  • enOferta?: boolean: puede no venir de la API; optamos por tratarlo con ternario.
  • carrito.productos: readonly Producto[]: el carrito se lee pero no se muta directamente; quien quiera modificar crea uno nuevo.
  • Tipado estructural: el objeto teclado "es" un Producto por su forma, no porque extienda una clase.

5 · Buenas practicas

  • Nombra interfaces con sustantivo y PascalCase: Usuario, Pedido.
  • Tipa la forma completa del dato, sin dejar propiedades "por si acaso" con tipos sueltos.
  • Usa opcional ? solo para lo que de verdad puede faltar en el dato.
  • Usa readonly en identificadores y datos que no deben reasignarse.
  • Compose interfaces (una dentro de otra) antes que repetir la misma estructura.

Que evitar

  • Crear interfaces con nombres como IUsuario o UserInterface: TypeScript no precisa prefijos; son ruido.
  • Poner ? en todo "por si acaso": acabas con interfaces sin valor y con comprobaciones por todas partes.
  • Mezclar readonly con mutacion esperada sin decisión explicita.

6 · Errores habituales

Mal — olvidar una propiedad requerida 
interface Usuario { nombre: string; email: string; }
const u: Usuario = { nombre: "Ana" };  // ✖ falta "email"
Bien — cumplir la forma completa 
const u: Usuario = { nombre: "Ana", email: "ana@dev.ts" }; // ✅
Mal — reasignar una propiedad readonly 
interface Config { readonly version: string; }
const cfg: Config = { version: "1.0" };
cfg.version = "2.0"; // ✖ error TS2540
Bien — crear una nueva configuracion 
const otraCfg: Config = { version: "2.0" };
Mal — usar opcional como "excusivo de tu codigo" 
interface Perfil { nombre: string; ciudad?: string; }
// con ciudad undefined, "ciudad.toUpperCase()" fallaria en runtime
Bien — comprobar antes de usar la opcional 
const nombre = perfil.ciudad ?? "No consta"; // sin ciudad → "No consta"

Por que estan mal: la interface es un contrato; incumplirla o usarla sin respetar los opcionales es recaer en los bugs de "undefined" que TypeScript quiere eliminar.

8 · Reto

Reto

Según el tipado estructural, { id: 1, sku: "X", nombre: "N", precio: 1, stock: 1, categoria: {...} } cumple Producto aunque el objeto literal no declare la interfaz. Escribe una funcion que reciba un Producto como parametro y demuestra que un objeto literal con propiedades EXTRA (por ejemplo descuento) de tipo compatible da error TS2322 al asignarse a un Producto a menos que inicialmente se declare como otra cosa. Explica el por que en una linea.

9 · Resumen

  • interface describe la forma de un objeto: propiedades y tipos.
  • Tipado estructural: la compatibilidad depende de la forma, no del nombre de la clase.
  • Opcional ?: la propiedad puede faltar o ser undefined.
  • readonly: propiedad que no se reasigna tras la creacion.
  • Metodos y propiedades-funcion definen comportamiento en la forma.
  • Interfaces se componen en arbol (anidadas) y se reutilizan.

10 · Preguntas frecuentes

¿Que diferencia hay entre interface y type alias?

Los dos describen formas. Las interfaces pueden extender y fusionarse; los type alias sirven para mas cosas (uniones, primitivos, genericos complejos). Lo vemos con profundidad en la siguiente leccion.

¿Puedo extender una interface?

Si, con interface Admin extends Usuario { privilegios: string[] }. Las interfaces se pueden heredar y tambien fusionar si se repiten (declaration merging).

¿Puedo usar readonly en arrays dentro de interfaces?

Si: readonly items: string[] o readonly items: readonly string[], segun quieras proteger la propiedad o tambien el contenido.

¿Una interfaz obliga a que el objeto use exactamente esas propiedades?

No del todo: el exceso se rechaza solo en literales asignados directamente (excess property check). En variables y funciones, las propiedades extra de una forma compatible se toleran. Lo aclara la leccion de discriminantes.

¿se puede poner un metodo como propiedad funcion en la interfaz?

Si: saludar: (nombre: string) => string es equivalente a saludar(nombre: string): string. Las dos compilan igual; la segunda es mas legible en interfaces.
