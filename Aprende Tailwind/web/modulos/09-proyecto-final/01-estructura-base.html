Estructura base del dashboard

Módulo 9 · Proyecto Final: Dashboard ⏱ 45 minutos

1 · Introducción

Imagina que abres una aplicación como Notion, Vercel, Linear o el panel de administración de cualquier SaaS moderno. La pantalla se organiza de una forma reconocible al instante:

  • Una barra lateral a la izquierda con navegación.
  • Una barra superior con buscador y perfil de usuario.
  • Un área de contenido que ocupa todo el espacio restante.

Este patrón se llama "dashboard layout" y es el layout más común en aplicaciones web profesionales. GitHub, Stripe, Supabase — todas usan variantes de este mismo esqueleto. Dominarlo es un rito de iniciación para cualquier desarrollador frontend.

En esta lección — la primera del Módulo 9 — sentaremos los cimientos:

  • Crear el grid principal con sidebar fija + topbar sticky + contenido scrollable.
  • Elegir la paleta de colores y justificar cada decisión.
  • Definir la jerarquía de contenedores con min-h-screen.
  • Escribir la estructura HTML que sostendrá todo el proyecto durante las próximas 4 lecciones.

Al terminar tendrás el esqueleto funcional de un dashboard profesional — sin contenido aún, pero con el layout perfectamente definido. Las próximas lecciones llenarán este esqueleto con navegación, métricas, tablas y widgets.

2 · Teoría

¿Por qué un dashboard usa este layout?

Antes de escribir una sola clase de Tailwind, necesitas entender POR QUÉ este layout es universal. No es una moda — es una solución a problemas reales:

Problema Solución del layout Cómo lo implementamos
Navegación persistente Sidebar fija siempre visible (en desktop) Columna izquierda con w-64 y posicionamiento fixed/sticky
Acciones globales rápidas Topbar con buscador, notificaciones, perfil Barra superior sticky que no se desplaza al hacer scroll
Contenido largo y dinámico Área principal con scroll independiente El contenido ocupa el espacio restante y hace scroll propio
Altura completa de pantalla El layout ocupa todo el viewport sin scroll del body h-screen en el contenedor raíz + overflow:hidden en body
Responsive La sidebar se oculta en móvil y se convierte en overlay Breakpoints md: y lg: para adaptar visibilidad

El grid maestro: la anatomía del layout

Nuestro dashboard se basa en un grid CSS de dos columnas. Visualízalo así:

│          │  TOPBAR (sticky, h-16)                    │
│ SIDEBAR  ├──────────────────────────────────────────┤
│ (w-64,   │                                          │
│  fixed)  │  CONTENIDO (overflow-y-auto)              │
│          │                                          │
│          │  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│          │  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│          │  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│          │  (scroll independiente)                  │
└──────────┴──────────────────────────────────────────┘

El grid tiene dos columnas: la primera mide w-64 (256px, o 16rem) y contiene la sidebar. La segunda ocupa el resto (flex-1 o 1fr). Dentro de la segunda columna, la topbar se queda fija arriba y el contenido hace scroll.

Decisión de colores: por qué slate-900, white y slate-50

La paleta de un dashboard profesional debe cumplir tres reglas:

  1. Jerarquía visual clara: La sidebar debe ser el elemento visualmente más "pesado" (oscuro) para anclar la interfaz. El contenido debe ser claro para leer cómodamente.
  2. Contraste suficiente: Texto sobre sidebar oscura debe ser legible (blanco o gris claro). Texto sobre fondo claro debe tener contraste alto (slate-900).
  3. Neutralidad: Los colores de fondo no deben competir con los datos (gráficos, badges, indicadores de estado). Slate es la escala más neutra de Tailwind — ni cálida ni fría.
Elemento Color Razón
Sidebar bg-slate-900 Color oscuro sólido. Ancla visualmente la interfaz. Contraste máximo con contenido claro.
Topbar bg-white + borde inferior Fondo blanco puro para separar del contenido. El borde sutil (border-slate-200) marca la separación.
Fondo del contenido bg-slate-50 Gris muy claro. Diferencia sutil del blanco de las tarjetas. Reduce fatiga visual frente a blanco puro.
Tarjetas / cards bg-white Blanco puro sobre fondo gris claro. Las tarjetas "flotan" visualmente gracias a la sombra.

¿Por qué no usar slate-800 para la sidebar? Slate-900 (#0f172a) es casi negro — crea el máximo contraste con el contenido. Slate-800 (#1e293b) es más claro y compite visualmente con elementos oscuros de las tarjetas. En dashboards, la sidebar debe ser el elemento más oscuro de la página. Es una regla de diseño tácita que verás en Stripe, Vercel y GitHub.

min-h-screen vs h-screen: una decisión crucial

Aquí hay una sutileza que separa los dashboards profesionales de los amateur:

  • h-screen: Altura exacta del viewport (100vh). Si el contenido es más largo, se corta. Necesitas un scroll interno (overflow-y-auto) en el área de contenido.
  • min-h-screen: Al menos el viewport. Si el contenido es más largo, el body crece y aparece scroll del body. La sidebar SOLO ocupa el viewport — el resto de la página se queda sin sidebar.

Para un dashboard real, h-screen es la elección correcta. El motivo: la sidebar debe ser persistente incluso cuando el contenido hace scroll. Si usas min-h-screen y hay mucho contenido, el usuario hace scroll del body y la sidebar desaparece hacia arriba. Con h-screen + overflow-y-auto en el contenido, la sidebar se queda fija y solo el contenido se desplaza.

❌ min-h-screen:              ✅ h-screen + overflow-y-auto:

[sidebare][contenido largo]   [sidebar][contenido largo ↑]
[  ok  ][                   ]  [ fija ][    ↑            ]
[  ok  ][                   ]  [ fija ][    ↑ scroll     ]
[  ok  ][                   ]  [ fija ][    ↑            ]
────────[  ← sidebar se va ]  [ fija ][    ↓            ]
        [  del viewport    ]  [ fija ][    ↓            ]

La topbar: ¿sticky o fixed?

La topbar va dentro de la columna derecha del grid. Usamos sticky top-0 — NO fixed. La diferencia:

  • sticky: Se comporta como un elemento normal hasta que haces scroll. Entonces se "pega" al borde superior de su contenedor. Respeta el flujo del grid.
  • fixed: Se sale del flujo y se posiciona respecto al viewport. Tendrías que compensar su altura con padding/margin. Es más frágil.

3 · Ejemplo mínimo

Empecemos con el esqueleto más pequeño posible — un grid de dos columnas con sidebar, topbar y área de contenido. Sin estilos decorativos, solo lo esencial:

<div class="flex h-screen bg-slate-50">
  <!-- SIDEBAR -->
  <aside class="w-64 bg-slate-900 text-white flex flex-col">
    <div class="p-6 text-xl font-bold border-b border-slate-700">
      Dashboard
    </div>
    <nav class="flex-1 p-4">
      <p class="text-slate-400 text-sm">Navegación aquí</p>
    </nav>
  </aside>

  <!-- ÁREA PRINCIPAL -->
  <div class="flex-1 flex flex-col overflow-hidden">
    <!-- TOPBAR -->
    <header class="bg-white border-b border-slate-200 h-16 flex items-center px-6 sticky top-0 z-10">
      <h2 class="text-lg font-semibold text-slate-800">Panel de Control</h2>
    </header>

    <!-- CONTENIDO -->
    <main class="flex-1 overflow-y-auto p-6">
      <div class="bg-white rounded-xl border border-slate-200 p-8 text-center text-slate-400">
        Contenido del dashboard aquí
      </div>
    </main>
  </div>
</div>

Analicemos cada clase del código anterior:

  • flex h-screen en el contenedor raíz: Crea un flex container horizontal que ocupa exactamente el alto del viewport. h-screen = 100vh. Esto evita el scroll del body.
  • w-64 en el aside: Ancho fijo de 16rem (256px). Es el ancho estándar para sidebars de dashboard — suficiente para iconos + texto sin ser demasiado ancho.
  • flex-1 en el área principal: Ocupa TODO el espacio restante después de la sidebar. Es el equivalente a flex: 1 1 0% o a 1fr en grid.
  • flex flex-col overflow-hidden en el área principal: Prepara un contenedor vertical. overflow-hidden es CRÍTICO — sin él, el contenido largo haría crecer este contenedor en lugar de activar el overflow-y-auto de main.
  • sticky top-0 z-10 en la topbar: Se pega arriba al hacer scroll. z-10 la mantiene por encima del contenido que se desplaza debajo.
  • flex-1 overflow-y-auto en main: Ocupa lo que la topbar deja libre. El scroll aparece SOLO aquí, no en el body.

overflow-hidden en el padre + overflow-y-auto en el hijo: Este patrón es la clave del dashboard. El padre (flex flex-col overflow-hidden) evita que crezca más allá del viewport. El hijo (flex-1 overflow-y-auto) activa el scroll interno. Si omites overflow-hidden en el padre, el contenido largo empuja todo hacia abajo y aparece scroll del body — la sidebar se desplaza con él. Es el error más común al construir dashboards.

5 · Buenas prácticas

Haz Evita Por qué
Usa h-screen + overflow-hidden en el contenedor raíz para dashboards Usar min-h-screen y permitir scroll del body — la sidebar se desplaza y se pierde El dashboard debe comportarse como una aplicación de escritorio: navegación persistente, scroll solo en el contenido
Pon overflow-hidden en el padre flex-col y overflow-y-auto en el hijo directo Poner overflow-y-auto en el contenedor raíz — el scroll aparece en el body entero overflow-hidden en el padre crea un "bounding box"; overflow-y-auto en el hijo limita el scroll a esa caja
Define la sidebar con flex-shrink-0 además de w-64 Confiar solo en w-64 — si el contenido principal es muy ancho, la sidebar puede encogerse flex-shrink-0 garantiza que la sidebar nunca reduzca su ancho, incluso bajo presión de espacio
Coloca la topbar con sticky top-0 dentro del flujo del grid/flex Usar fixed top-0 y luego compensar con padding — frágil y propenso a errores de solapamiento sticky respeta el flujo del documento; fixed requiere cálculos manuales de offset que se rompen fácilmente
Envuelve el contenido en un max-w-7xl mx-auto para centrarlo en pantallas muy anchas Dejar el contenido sin ancho máximo — en monitores 4K las tarjetas se estiran hasta ser irreconocibles max-w-7xl (80rem / 1280px) es un ancho máximo cómodo para dashboards. Centrado con mx-auto queda bien en ultra-wide
Usa space-y-6 para separar secciones verticales dentro del contenido Poner margin-bottom manual en cada sección — inconsistente y difícil de mantener space-y-{n} aplica margin-top a todos los hijos excepto el primero. Es consistente y declarativo

6 · Errores habituales

El contenido largo hace scroll del body entero (la sidebar se mueve)

Este es el error más común al construir dashboards con Tailwind. La causa: te falta overflow-hidden en el contenedor flex-col que envuelve la topbar y el main. Sin él, el contenido empuja el contenedor hacia abajo, el body crece, y aparece scroll del viewport. La sidebar — al ser hija del flex horizontal — se desplaza con todo. Solución: <div class="flex-1 flex flex-col overflow-hidden"> en el contenedor del área principal y overflow-y-auto en <main>.

La topbar se solapa con el contenido al hacer scroll

Olvidaste sticky top-0 en la topbar. Sin sticky, la topbar es un elemento normal que se desplaza con el contenido. En cuanto el usuario baja, la topbar desaparece y no puede acceder al buscador ni a las notificaciones. Solución: sticky top-0 z-10. El z-10 evita que el contenido se renderice por encima de la topbar durante el scroll.

La sidebar es más corta que el contenido en pantallas pequeñas

La sidebar tiene h-screen pero el contenido es más largo. En pantallas pequeñas (móvil), la sidebar oculta los últimos elementos de navegación. Solución: por ahora la sidebar es fixed-width para desktop. En la lección 5 añadiremos el comportamiento mobile (overlay + toggle). Mientras tanto, asegúrate de que los enlaces de navegación caben en 100vh.

Los elementos de la topbar no se alinean correctamente

Estás usando márgenes o posicionamiento absoluto para alinear buscador, notificaciones y avatar. En su lugar, usa flex items-center justify-between en la topbar y agrupa los elementos izquierda/derecha en dos divs con flex items-center gap-4. Flexbox es la herramienta correcta para alinear elementos en una barra — no luches contra él con posicionamiento manual.

Paso 3: Hacer el breadcrumb responsive

En móvil, el breadcrumb ocupa demasiado espacio horizontal. Lo ocultamos con hidden sm:block:

<div class="hidden sm:block">
  <h1 class="text-lg font-semibold text-slate-800">Dashboard</h1>
  <div class="flex items-center gap-1.5 text-xs text-slate-500 mt-0.5">
    <a href="#" class="hover:text-slate-700 transition-colors">Inicio</a>
    <span>/</span>
    <a href="#" class="hover:text-slate-700 transition-colors">Panel</a>
    <span>/</span>
    <span class="text-slate-400">Dashboard</span>
  </div>

Ahora en pantallas pequeñas solo se ve el título "Dashboard" sin el breadcrumb, liberando espacio horizontal para el buscador y los iconos.

Analogía: La topbar es como el salpicadero de un coche. Tiene elementos fijos que siempre necesitas ver (velocidad, gasolina = título, notificaciones) y elementos secundarios que puedes ocultar cuando el espacio es limitado (radio, navegación = breadcrumb, selector de fechas). Tailwind te da hidden sm:block, hidden md:flex para decidir qué se muestra en cada tamaño de pantalla, igual que un coche compacto esconde botones secundarios detrás de menús.

8 · Reto

🎯 Construye una variante del layout con topbar de dos filas

Partiendo de la estructura base que hemos construido, modifica la topbar para que tenga dos filas:

  1. Fila 1: Logo pequeño + breadcrumb a la izquierda. Selector de fecha + notificaciones + avatar a la derecha. Altura: h-10.
  2. Fila 2: Título de la página a la izquierda. Grupo de botones de acción (Exportar, Nuevo, Filtrar) a la derecha. Altura: h-12. Con pestañas de navegación secundaria (Overview, Analytics, Reports, Settings) en el centro.

Restricciones:

  • Ambas filas deben ser sticky. Usa sticky top-0 en el contenedor de las dos filas, no en cada una por separado.
  • En móvil, la fila 2 se simplifica: solo el título y un botón de menú hamburguesa.
  • Las pestañas de la fila 2 deben tener un indicador inferior (borde azul de 2px) en la pestaña activa.

9 · Resumen

  • El dashboard layout es un patrón universal: sidebar fija izquierda + topbar sticky + contenido scrollable. Lo usan Stripe, Vercel, Linear, GitHub y prácticamente todas las aplicaciones SaaS.
  • h-screen + overflow-hidden en el contenedor raíz: Esta combinación evita el scroll del body y mantiene la sidebar siempre visible. Es la decisión de layout más importante del proyecto.
  • El patrón overflow-hidden + overflow-y-auto: El padre (flex-col + overflow-hidden) crea un bounding box. El hijo (flex-1 + overflow-y-auto) activa scroll solo en ese área. Sin overflow-hidden en el padre, todo falla.
  • Sidebar: w-64 + flex-shrink-0: 256px de ancho fijo que nunca se encoge, incluso bajo presión de espacio. Slate-900 para anclar visualmente la interfaz.
  • Topbar: sticky top-0 z-10: Sticky (no fixed) para que respete el flujo del layout. z-10 para evitar que el contenido la solape al hacer scroll.
  • Contenido centrado con max-w-7xl mx-auto: Evita que las tarjetas se estiren en monitores ultra-wide. 1280px es un máximo cómodo para dashboards.
  • Grid responsive: grid-cols-1 sm:grid-cols-2 lg:grid-cols-4 adapta el número de columnas al ancho disponible. Mobile-first: empieza con 1 columna y crece.
  • Las próximas 4 lecciones construirán sobre este esqueleto: navegación colapsable, métricas con gráficos, tabla de datos, widgets, dark mode y responsive completo. La estructura que acabas de crear es el lienzo donde pintaremos todo lo demás.

10 · Preguntas frecuentes

¿Por qué usar flex y no grid para el layout principal?

Grid también funcionaría perfectamente: grid-cols-[256px_1fr]. De hecho, para dashboards más complejos con múltiples paneles laterales, grid es superior. La razón de usar flex aquí es pedagógica: ya has estudiado Grid en el Módulo 3, y este módulo te muestra cómo Flexbox también puede resolver layouts complejos. Además, con flex tienes acceso a flex-shrink-0 que es más expresivo que grid-template-columns para garantizar anchos fijos. Ambos enfoques son válidos en producción.

¿Es h-screen realmente seguro en todos los navegadores?

En navegadores de escritorio, sí. En móviles, 100vh tiene un problema conocido: las barras de navegación del navegador (Safari iOS, Chrome Android) se superponen y reducen el viewport real. La solución moderna es usar h-dvh (dynamic viewport height) que Tailwind v4 soporta. Si tu audiencia incluye mucho tráfico móvil, considera h-dvh en lugar de h-screen. Para este curso usamos h-screen porque es el approach más compatible y porque la lección 5 añade el comportamiento mobile completo que mitiga este problema.

¿Por qué la topbar no ocupa todo el ancho de la pantalla?

La topbar está dentro de la columna derecha del grid, no en el contenedor raíz. Ocupa el espacio flex-1 — todo lo que queda después de los 256px de la sidebar. Si quisieras una topbar que cubra todo el ancho (incluyendo encima de la sidebar), tendrías que sacarla del flex horizontal y usar posicionamiento fixed con left-64 para que empiece después de la sidebar. Ese diseño es menos común porque crea una desconexión visual entre la topbar y la sidebar.

¿Cómo añado una segunda sidebar (panel derecho) al layout?

Añade un tercer hijo al flex horizontal: <aside class="w-72 bg-white border-l border-slate-200 flex-shrink-0">. El orden sería: sidebar izquierda (w-64 flex-shrink-0), área central (flex-1 min-w-0), panel derecho (w-72 flex-shrink-0). El min-w-0 en el área central es importante: sin él, el contenido podría forzar al panel central a ser más ancho de lo que permite el viewport, empujando el panel derecho fuera de la pantalla.

¿Debo usar este mismo layout para aplicaciones no-dashboard?

Este layout es óptimo para aplicaciones con navegación persistente y mucho contenido — dashboards, paneles de administración, CRMs, herramientas internas. Para sitios web de contenido (blogs, landing pages, portfolios), un layout más simple con header + contenido + footer es más apropiado. Para aplicaciones muy complejas (tipo IDE), podrías necesitar paneles redimensionables además de la sidebar. La clave es entender los principios (grid/flex + overflow controlado + sticky) y adaptarlos a cada contexto.
