Componentes Reutilizables: @apply, @layer y @utility

Módulo 7 · Formularios, Animaciones y Patrones ⏱ 30 minutos

1 · Introducción

Llevas varias lecciones escribiendo los mismos conjuntos de clases una y otra vez. Un botón azul son 15 clases. Un input de formulario son 12. Una card son 20. Si mañana cambia el diseño del botón, ¿vas a editar 47 archivos a mano?

La gran pregunta de Tailwind

Esta lección aborda el mayor punto de fricción de Tailwind: la repetición de clases. Vas a aprender cuándo y cómo extraer clases repetitivas en componentes reutilizables usando @apply, @layer y @utility. Pero también vas a entender por qué el propio Adam Wathan, creador de Tailwind, recomienda usar @apply con moderación y te explica cuándo SÍ y cuándo NO usarlo.

Al final de esta lección tendrás criterio para decidir si extraer a CSS, usar un componente de framework, o mantener las clases en el HTML — y sabrás defender tu decisión con argumentos sólidos.

2 · Teoría

El problema real: DRY vs claridad

En programación, el principio DRY (Don't Repeat Yourself) es sagrado. Pero Tailwind deliberadamente te hace repetir clases. ¿Es esto un error de diseño? No. Es una elección consciente basada en un trade-off:

OpciónVentajaDesventaja
Clases inline repetidasTodo el estilo está en el HTML. Editas un botón en su contexto. Sin saltos de archivo.Repetición. Cambiar el diseño de todos los botones requiere editar N archivos.
Clase CSS extraída (@apply)Cambias un sitio y se actualiza todo. Menos repetición.Vuelves al problema original: buscar en CSS qué hace .btn-primary. Context switching.
Componente de framework (React/Vue)Reutilización total. Props tipadas. Sin CSS global.Acoplas el estilo a un framework. No sirve para HTML plano.
Analogía: @apply es como crear una macro en Excel

Si repites la misma fórmula 50 veces, creas una macro (o función). Ganas mantenibilidad: cambias la macro una vez y se actualiza todo. Pero pierdes visibilidad: quien lee la celda ya no ve la fórmula, ve el nombre de la macro. Tiene que ir a otro sitio a entender qué hace. @apply es exactamente eso: creas una "macro" de clases Tailwind que puedes reutilizar, a costa de perder la visibilidad inmediata.

Las tres herramientas de Tailwind para reutilización

1. @apply — Extraer clases en CSS

@apply te permite inyectar clases de Tailwind dentro de una regla CSS personalizada. Es la herramienta más directa para combatir la repetición:

/* Antes: esto repetido en 20 botones */
<button class="px-5 py-2.5 bg-blue-600 text-white font-semibold
               rounded-lg hover:bg-blue-700 transition-colors">

/* Después con @apply: usas una sola clase */
.btn-primary {
  @apply px-5 py-2.5 bg-blue-600 text-white font-semibold
         rounded-lg hover:bg-blue-700 transition-colors;
}

<button class="btn-primary">Enviar</button>
Adam Wathan sobre @apply

"Use @apply for very small, highly reusable things like buttons and form inputs. Do NOT use @apply to try to recreate Bootstrap-style semantic CSS classes for everything. If you find yourself using @apply for layout, stop. Layout belongs in HTML." — Adam Wathan

2. @layer — Organizar CSS en capas

Tailwind organiza su CSS en tres capas por defecto: base (reset), components (clases extraídas), utilities (clases utilitarias). Con @layer puedes insertar tus estilos en la capa correcta para controlar la precedencia:

@import "tailwindcss";

/* Capa base: estilos globales que se aplican a elementos HTML */
@layer base {
  h1 { @apply text-3xl font-bold; }
  h2 { @apply text-2xl font-semibold; }
  a  { @apply text-blue-400 hover:text-blue-300 underline-offset-4; }
}

/* Capa components: clases reutilizables extraídas con @apply */
@layer components {
  .btn {
    @apply inline-flex items-center justify-center gap-2
           px-5 py-2.5 font-semibold rounded-lg
           transition-all duration-200
           focus-visible:ring-2 focus-visible:ring-offset-2
           active:scale-[0.97]
           disabled:opacity-50 disabled:cursor-not-allowed;
  }

  .btn-primary {
    @apply btn bg-blue-600 text-white
           hover:bg-blue-700
           focus-visible:ring-blue-500;
  }

  .btn-secondary {
    @apply btn bg-slate-700 text-slate-200 border border-slate-600
           hover:bg-slate-600
           focus-visible:ring-slate-500;
  }

  .btn-danger {
    @apply btn bg-red-600 text-white
           hover:bg-red-700
           focus-visible:ring-red-500;
  }

  .input-field {
    @apply w-full px-4 py-2.5 bg-slate-900
           border border-slate-600 rounded-lg
           text-sm text-slate-200 placeholder:text-slate-500
           focus:outline-none focus:border-blue-500
           focus:ring-2 focus:ring-blue-500/30
           transition-all duration-200;
  }

  .card {
    @apply bg-slate-800 border border-slate-700 rounded-2xl p-6;
  }
}
¿Por qué @layer importa?

Sin @layer, tus estilos CSS personalizados tienen máxima precedencia y no pueden ser sobrescritos por utilidades de Tailwind. Con @layer components, tus clases van en la capa components, por debajo de utilities. Esto significa que puedes usar Tailwind para sobrescribir partes específicas: <button class="btn-primary rounded-full"> funciona porque las utilidades (rounded-full) tienen más precedencia que los componentes.

3. @utility — Crear nuevas utilidades (Tailwind v4)

En Tailwind v4, @utility te permite definir tus propias clases utilitarias de forma nativa. Es como añadir clases al catálogo oficial de Tailwind:

@utility scrollbar-thin {
  scrollbar-width: thin;
  scrollbar-color: oklch(0.446 0.043 257.281) transparent;
}

@utility text-balance {
  text-wrap: balance;
}

@utility mask-fade-bottom {
  -webkit-mask-image: linear-gradient(to bottom,
    black 60%, transparent 100%);
  mask-image: linear-gradient(to bottom,
    black 60%, transparent 100%);
}

Una vez definidas, las usas como cualquier clase de Tailwind: scrollbar-thin, text-balance, mask-fade-bottom. La gran ventaja sobre @apply es que no creas una abstracción con nombre semántico — creas una nueva utilidad que sigue la filosofía utility-first.

📝 Ojo: algunas de estas ya son nativas en v4.1+ y v4.3

Desde text-shadow-*, mask-* y scrollbar-* ya existen como utilidades oficiales de Tailwind. Este ejemplo sigue siendo válido para aprender a crear utilidades con @utility, pero en producción usa las nativas cuando existan. Lo cubrimos a fondo en la lección Novedades de Tailwind v4.1 a v4.3.

El criterio de Adam Wathan: cuándo SÍ y cuándo NO usar @apply

SÍ usa @apply para...NO uses @apply para...
Componentes muy repetidos: botones, inputs, badges, cardsLayouts y espaciado (flex, grid, gap-4, p-6)
Estilos que cambian como conjunto (mismo aspecto en toda la app)Estilos que varían según el contexto (una card más ancha aquí, más padding allá)
Pequeños conjuntos de 5-20 clases que siempre van juntasCombinaciones únicas que solo aparecen una o dos veces
Cuando estás en HTML plano sin framework de componentesCuando usas React/Vue/Svelte — usa componentes del framework
Regla de oro

Si te encuentras copiando y pegando el mismo bloque de clases más de 3 veces, y esas clases siempre cambian juntas como una unidad, es hora de extraer. Si cada instancia es ligeramente diferente, mantener las clases inline es más claro y mantenible.

3 · Ejemplo mínimo

El caso más sencillo: un badge de estado. Aparece en 15 sitios distintos de la aplicación con las mismas clases:

/* Definición en tu CSS */
@layer components {
  .badge {
    @apply inline-flex items-center px-2.5 py-0.5 rounded-full
           text-xs font-medium;
  }

  .badge-success {
    @apply badge bg-emerald-500/20 text-emerald-400;
  }

  .badge-warning {
    @apply badge bg-amber-500/20 text-amber-400;
  }

  .badge-error {
    @apply badge bg-red-500/20 text-red-400;
  }

  .badge-info {
    @apply badge bg-blue-500/20 text-blue-400;
  }
}
<!-- Uso: una clase en vez de 5 -->
<span class="badge-success">Completado</span>
<span class="badge-warning">Pendiente</span>
<span class="badge-error">Cancelado</span>
<span class="badge-info">En revisión</span>

¿Por qué esto es un buen uso de @apply? (1) Los badges son pequeños (4 clases base). (2) Se repiten mucho en cualquier aplicación. (3) Cambian como unidad: si mañana quieres badges con borde en vez de fondo semitransparente, cambias un solo sitio. (4) El nombre badge-success es descriptivo y no requiere saltar al CSS para entender qué aspecto tiene (ya sabes que es un badge verde).

4 · Ejemplo real

1. Sistema de botones completo

Un sistema de botones profesional con variantes, tamaños y estados. Así se ve la definición CSS:

@layer components {
  /* Botón base: todas las variantes comparten esto */
  .btn {
    @apply inline-flex items-center justify-center gap-2
           font-semibold rounded-lg
           transition-all duration-200
           focus-visible:ring-2 focus-visible:ring-offset-2
           focus-visible:ring-offset-slate-900
           active:scale-[0.97]
           disabled:opacity-50 disabled:cursor-not-allowed
           select-none;
  }

  /* Tamaños */
  .btn-sm  { @apply px-3 py-1.5 text-xs; }
  .btn-md  { @apply px-5 py-2.5 text-sm; }
  .btn-lg  { @apply px-7 py-3 text-base; }

  /* Variantes de color */
  .btn-primary {
    @apply btn bg-blue-600 text-white
           hover:bg-blue-700
           focus-visible:ring-blue-500;
  }

  .btn-secondary {
    @apply btn bg-slate-700 text-slate-200
           border border-slate-600
           hover:bg-slate-600
           focus-visible:ring-slate-500;
  }

  .btn-ghost {
    @apply btn text-slate-300
           hover:bg-slate-800 hover:text-white
           focus-visible:ring-slate-500;
  }

  .btn-outline {
    @apply btn border-2 border-blue-500 text-blue-400
           hover:bg-blue-500 hover:text-white
           focus-visible:ring-blue-500;
  }

  /* Variante de icono (solo icono, sin texto) */
  .btn-icon {
    @apply btn p-2 rounded-full;
  }
}
<!-- Uso: combinar variante + tamaño -->
<button class="btn-primary btn-lg">
  <svg class="w-5 h-5">...</svg>
  Crear proyecto
</button>

<button class="btn-secondary btn-md">Cancelar</button>

<button class="btn-ghost btn-sm">Editar</button>

<button class="btn-outline btn-md">Vista previa</button>

<button class="btn-icon btn-primary" aria-label="Añadir">
  <svg class="w-5 h-5">...</svg>
</button>
La clave: componer, no anidar

Fíjate en el patrón: btn-primary btn-lg. No tienes btn-primary-lg, btn-secondary-sm, btn-outline-md (3 variantes × 3 tamaños = 9 clases). Compones: una clase para el color + una clase para el tamaño. Esto escala con el producto cartesiano: 5 variantes × 3 tamaños = 15 combinaciones con solo 5 + 3 = 8 clases definidas.

<div class="form-group">
  <label for="email" class="label">Correo electrónico</label>
  <input id="email" type="email"
         class="input focus:border-blue-500
                focus:ring-blue-500/30
                invalid:border-red-500"
         placeholder="tu@correo.com">

Observa que no se usa input-error como clase fija

En vez de class="input-error", se usa class="input invalid:border-red-500". Esto es deliberado: el estado invalid: es condicional. Si usas input-error como clase fija, el input siempre se ve rojo. La combinación de @apply para la base + utilidades para los estados condicionales es el punto dulce.

4. Cuándo NO usar @apply — el anti-patrón

Este es el error clásico que Adam Wathan advierte: intentar recrear Bootstrap con @apply:

/* ❌ MAL: intentando recrear Bootstrap. Esto es un anti-patrón */
@layer components {
  .navbar {
    @apply flex items-center justify-between px-6 py-3
           bg-slate-800 border-b border-slate-700;
  }
  .navbar-brand  { @apply text-lg font-bold text-white; }
  .navbar-nav    { @apply flex items-center gap-4; }
  .navbar-link   { @apply text-sm text-slate-400 hover:text-white
                           transition-colors; }

  .hero {
    @apply flex flex-col items-center justify-center
           text-center py-24 px-4;
  }
  .hero-title    { @apply text-5xl font-bold text-white mb-4; }
  .hero-subtitle { @apply text-xl text-slate-400 mb-8 max-w-2xl; }

  .footer {
    @apply border-t border-slate-700 py-12 px-6 mt-24;
  }
  .footer-grid   { @apply grid grid-cols-1 md:grid-cols-4 gap-8; }
  /* ... y así 50 clases más */
}

¿Por qué esto es un error?

  • Vuelves al problema original: Para saber qué hace .hero-title tienes que buscar en el CSS. Has perdido la visibilidad inmediata de Tailwind.
  • Acoplas estructura a CSS: Si cambias el layout del hero de flex a grid, tienes que editar el CSS. Con Tailwind inline, cambias el HTML directamente.
  • Especificidad en cascada: Las clases en @layer components pueden ser sobrescritas por utilidades, pero empiezan a crear una jerarquía compleja de precedencia.
  • Creas nombres de clase arbitrarios: ¿.hero-title o .hero-heading o .hero-h1? Ya estás en el problema de nombrar cosas que Tailwind resuelve.
La alternativa correcta

Si ves que una sección de layout se repite y quieres reutilizarla, la solución NO es @apply. La solución es un componente de framework (React, Vue, Svelte) o un partial/server-side include (PHP, Astro, Nunjucks). Tailwind está diseñado para convivir con sistemas de templates/componentes, no para reemplazarlos.

6 · Errores habituales

Error #1 — «Mis clases @apply no se pueden sobrescribir con utilidades»

Causa: Definiste tus clases fuera de @layer components o en un orden incorrecto en el CSS. Las reglas CSS normales (fuera de layer) tienen máxima precedencia y aplastan a las utilidades de Tailwind que están en @layer utilities. Solución: Envuelve todas tus clases en @layer components { ... } y asegúrate de que @import "tailwindcss" va antes.

Error #2 — «Creé una clase card pero en una página necesito más padding»

Causa: Tu clase .card incluye @apply p-6. Pero en la página de dashboard necesitas p-4 para que quepan más cards. Si añades class="card p-4", ¿funciona? Solo si .card está en @layer components (menor precedencia que utilities). Si está fuera de @layer, gana p-6. Solución: No incluyas padding en la clase .card base. Usa .card-body { @apply p-6; } o aplica el padding inline: <div class="card p-4">.

Error #3 — «Defino @utility pero no aparece en el autocompletado de VSCode»

Causa: Tailwind v4 con el plugin de VSCode (Tailwind CSS IntelliSense) necesita estar configurado correctamente para detectar @utility en archivos CSS. Solución: Asegúrate de que el archivo donde defines @utility está referenciado en tu @import "tailwindcss", ya sea directamente o como parte del build. En proyectos Vite, el IntelliSense escanea los archivos importados desde tu entry point CSS.

Error #4 — «Uso @apply con clases responsive y no funciona»

Causa: @apply no puede incluir variantes responsive (md:, lg:) ni de estado (hover:, focus:) — bueno, técnicamente sí puede con algunos, pero el comportamiento es impredecible y las variantes responsive en particular no funcionan dentro de @apply. Solución: Para estilos responsive, aplica las variantes directamente en el HTML. .card { @apply bg-slate-800 rounded-2xl; } y en HTML: <div class="card md:flex md:flex-row">. La base es @apply, las variaciones son utilidades inline.

7 · Ejercicio guiado

Crea un mini sistema de diseño con @apply, @layer y @utility. Define los siguientes componentes y utilidades:

  1. Badges: .badge base + .badge-{color} para success, warning, error, info, neutral.
  2. Botones: .btn base + .btn-{variant} (primary, secondary, ghost, danger) + .btn-{size} (sm, md, lg).
  3. Inputs: .input base + .label + .form-group.
  4. Utility personalizada: @utility text-balance que aplique text-wrap: balance para títulos.
  5. Card: .card base + .card-body + .card-hover.
/* === Mini sistema de diseño === */
@import "tailwindcss";

🎯 Extiende el sistema de diseño con alertas y avatares

Añade dos nuevos componentes al sistema de diseño que acabas de crear:

  • Alertas (.alert): Cuatro variantes: success (verde), warning (ámbar), error (rojo), info (azul). Cada alerta tiene un icono a la izquierda, título en negrita, mensaje descriptivo, y un botón de cerrar opcional. Las alertas ocupan el ancho completo.
  • Avatares (.avatar): Cuatro tamaños: xs (w-6 h-6), sm (w-8 h-8), md (w-10 h-10), lg (w-14 h-14). Con tres variantes: imagen (avatar-img), iniciales (avatar-initials), y placeholder genérico con icono de usuario (avatar-placeholder). Todos circulares y con un ring exterior sutil.

Pistas: Para las alertas, compón una clase base .alert + variantes .alert-success, etc. Para los avatares, compón .avatar base (rounded-full) + tamaño + variante de contenido. Usa @layer components para todo. Prueba que las utilidades inline puedan sobrescribir partes (ej: class="alert alert-error rounded-none").

9 · Resumen

  • @apply: Inyecta clases Tailwind en una regla CSS. Úsalo SOLO para componentes pequeños y muy repetidos (botones, badges, inputs). No para layouts ni combinaciones únicas.
  • @layer: Organiza tus estilos en capas (base, components, utilities) para controlar la precedencia. Las utilidades siempre pueden sobrescribir componentes. Esto es clave para la flexibilidad.
  • @utility: Crea nuevas clases utilitarias en v4. A diferencia de @apply, mantiene la filosofía utility-first: nombres descriptivos de lo que hacen, no de lo que representan.
  • Criterio de Adam Wathan: @apply para cosas pequeñas y muy repetidas. Para layouts y combinaciones únicas, mantén las clases inline. Para reutilización a gran escala, usa componentes de framework.
  • Componer, no anidar: btn-primary btn-lg es mejor que btn-primary-lg. Combina clases base + modificadores en vez de crear una clase por cada combinación.
  • Estados condicionales inline: La base del componente va con @apply. Los estados (hover:, invalid:, disabled:) van como utilidades inline en el HTML.
  • El HTML sigue siendo la fuente de verdad: Incluso con @apply, deberías poder entender el aspecto de un elemento leyendo sus clases. Si necesitas saltar al CSS para entender qué hace una clase, has extraído demasiado.

10 · Preguntas frecuentes

¿@apply no es simplemente volver a como se hacía antes con CSS?

Hay una diferencia clave. Con CSS tradicional, tus clases .btn-primary contienen CSS puro (background-color: #2563eb; padding: 10px 20px;). Con @apply, tus clases contienen referencias a utilidades Tailwind (@apply bg-blue-600 px-5 py-2.5). Esto significa que heredas todo el sistema de diseño de Tailwind: colores consistentes, escala de espaciado, breakpoints, dark mode. No estás volviendo a CSS tradicional; estás usando Tailwind como un lenguaje de más alto nivel para definir componentes.

¿Debo usar @apply si ya estoy usando React con componentes?

Generalmente no. En React, el componente ya es tu unidad de reutilización. Ejemplo: <Button variant="primary" size="md"> es un componente React que internamente usa clases Tailwind. No necesitas @apply porque el componente encapsula la repetición. @apply brilla en proyectos sin framework de componentes (HTML plano, Astro sin componentes interactivos, emails HTML, documentación estática).

¿Puedo usar @apply con variantes responsive como md: o lg:?

No de forma fiable. @apply no está diseñado para manejar variantes responsive. Si necesitas comportamiento responsive en un componente, tienes dos opciones: (1) Aplica las variantes responsive directamente en el HTML (class="card md:flex-row"). (2) Usa media queries tradicionales dentro del @layer components. La primera opción es la recomendada.

¿Cuántas clases es razonable incluir en un @apply?

Entre 5 y 20 clases. Menos de 5 no justifica la abstracción (escribir 3 clases inline no es problema). Más de 20 sugiere que estás mezclando demasiadas responsabilidades: divide en clases más pequeñas y compón. Un .btn típico tiene 8-12 clases. Un .card base tiene 4-6. Si llegas a 25, probablemente deberías dividir en .card-header, .card-body, .card-footer.

¿Tailwind v4 eliminará @apply en el futuro?

No hay planes de eliminar @apply. Adam Wathan ha dicho que, aunque él personalmente lo usa poco, reconoce que es útil en ciertos escenarios (sobre todo en proyectos sin framework). Lo que sí ha enfatizado es que no debería ser la forma principal de escribir estilos con Tailwind. La filosofía sigue siendo utility-first: las clases van en el HTML. @apply es una válvula de escape para cuando la repetición se vuelve insostenible, no el modo por defecto.
