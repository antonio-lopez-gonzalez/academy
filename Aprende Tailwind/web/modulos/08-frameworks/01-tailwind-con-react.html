Tailwind con React

Módulo 8 · Tailwind en Frameworks ⏱ 40 minutos

1 · Introducción

React y Tailwind forman una de las combinaciones más productivas del desarrollo frontend moderno. React te da componentes reutilizables; Tailwind te da estilos predecibles y colocalizados. Juntos eliminan la fricción de mantener hojas de estilo separadas y perseguir clases CSS por toda la carpeta src/.

Pero integrarlos bien no es simplemente escribir className="text-center p-4" y ya. Hay decisiones de arquitectura que marcan la diferencia entre un proyecto mantenible y un caos de clases inline interminables. En esta lección aprenderás:

  • Cómo pasar className como prop para crear componentes componibles.
  • Template literals vs clsx vs tailwind-merge: por qué necesitas ambos y cómo combinarlos en una función cn().
  • class-variance-authority (cva): el patrón definitivo para componentes con variantes (tamaño, color, estado).
  • Instalación real con Vite + pnpm.

2 · Teoría

className como prop: la clave de la componibilidad

En React, los estilos viajan por la prop className (camelCase porque JSX es JavaScript, no HTML). El patrón más importante que debes interiorizar es aceptar className en tus componentes y fusionarlo con las clases base del componente. Esto permite que quien use tu componente pueda extenderlo sin modificarlo:

// ❌ MAL: el componente es un callejón sin salida
function Card({ children }) {
  return <div className="rounded-xl bg-white p-6 shadow-lg">{children}</div>;
}
// Quien use <Card className="mt-8" /> no verá el margen aplicado.

// ✅ BIEN: aceptas className y lo fusionas
function Card({ children, className = "" }) {
  return (
    <div className={`rounded-xl bg-white p-6 shadow-lg ${className}`}>
      {children}
    </div>
  );
}
// <Card className="mt-8" /> ahora funciona.

Este patrón es ubicuo en librerías como shadcn/ui, Radix, y cualquier sistema de componentes bien diseñado.

🧩 Analogía: className como pieza de Lego

Imagina que tu componente es una pieza base de Lego (un rectángulo 2x4). Tiene sus propias características fijas (color, tamaño). La prop className es como los puntos de anclaje que permiten conectar otras piezas encima. Sin esos puntos de anclaje, tu pieza es un callejón sin salida: bonita, pero inútil para construir algo más grande.

Template literals: el problema de los conflictos

Fusionar clases con template literals (`base ${prop}`) funciona para casos sencillos, pero tiene un defecto fatal: no resuelve conflictos. Si tu componente base tiene p-4 y el usuario pasa p-6, ambas clases quedan en el HTML. CSS decide cuál gana por especificidad o por orden en la hoja de estilos, y el resultado es impredecible:

<!-- Resultado con template literals: ambas clases presentes -->
<div class="p-4 p-6">...</div>
<!-- ¿Cuál gana? Depende. En Tailwind v4, la última en el CSS generado.
     Pero como el orden de generación depende del orden de escaneo del
     content path, NO puedes confiar en ello. -->

clsx: control condicional de clases

clsx es una minilibrería (228 bytes minificada) que resuelve el problema de las clases condicionales. Convierte objetos, arrays y strings en una cadena de clases limpia:

import clsx from "clsx";

clsx("base", "extra");                         // "base extra"
clsx("base", false && "nope", "extra");        // "base extra"
clsx("base", { active: isActive, disabled });  // "base active disabled" (si ambas true)
clsx(["base", "extra"]);                       // "base extra"
clsx("p-4", "p-6");                            // "p-4 p-6" — AMBAS. clsx no resuelve conflictos

clsx es excelente para manejar condicionales, pero no resuelve conflictos entre clases de Tailwind. Para eso necesitas tailwind-merge.

tailwind-merge: el sheriff de las clases

tailwind-merge conoce las reglas de Tailwind. Sabe que p-4 y p-6 son mutuamente excluyentes (ambas afectan padding) y que en caso de conflicto debe ganar la última. También entiende modificadores como hover:, dark:, md::

import { twMerge } from "tailwind-merge";

twMerge("p-4 p-6");                     // "p-6" — p-4 eliminado
twMerge("text-red-500 text-blue-500");   // "text-blue-500"
twMerge("px-4 py-2 p-6");               // "p-6" — p-6 sobrescribe padding en todos los lados
twMerge("bg-red-500 hover:bg-red-700");  // "bg-red-500 hover:bg-red-700" — no hay conflicto
twMerge("w-1/2 w-full");                // "w-full"
📝 Nota sobre rendimiento

tailwind-merge pesa unos 7KB minificado + gzip (~2.5KB). No es despreciable, pero el ahorro en bugs de estilos y la predecibilidad que aporta justifican de sobra su inclusión. Además, si usas cn() como patrón en todo tu proyecto, el bundle solo incluye una referencia a twMerge, no una copia por componente.

cn(): la función que lo une TODO

El patrón estándar en la industria es combinar clsx + tailwind-merge en una función helper llamada cn(). Esta función acepta cualquier número de argumentos (strings, objetos condicionales, arrays), resuelve condicionales con clsx y elimina conflictos con twMerge:

// lib/utils.js
import { clsx } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs) {
  return twMerge(clsx(inputs));
}

// Uso en cualquier componente:
import { cn } from "@/lib/utils";

function Button({ className, variant = "primary", size = "md", ...props }) {
  return (
    <button
      className={cn(
        "rounded-lg font-semibold transition-colors",
        variant === "primary"   && "bg-blue-600 text-white hover:bg-blue-700",
        variant === "secondary" && "bg-gray-200 text-gray-900 hover:bg-gray-300",
        variant === "outline"   && "border-2 border-blue-600 text-blue-600 hover:bg-blue-50",
        size === "sm" && "px-3 py-1.5 text-sm",
        size === "md" && "px-5 py-2.5 text-base",
        size === "lg" && "px-7 py-3.5 text-lg",
        className // ← lo que venga de fuera (puede sobrescribir lo anterior)
      )}
      {...props}
    />
  );
}
💡 ¿Por qué className va al final?

En cn(), cuando dos clases entran en conflicto, gana la última que aparece. Al poner className (la prop externa) al final, permites que quien use tu componente pueda sobrescribir cualquier clase interna. Si invirtieras el orden, el usuario no podría personalizar el padding o el color porque las clases internas ganarían siempre.

class-variance-authority (cva): variantes tipadas y predecibles

A medida que tu componente crece, los ternarios anidados (variant === "primary" && "...") se vuelven inmanejables. cva resuelve esto definiendo las variantes de forma declarativa. Es el estándar en shadcn/ui y cada vez más proyectos profesionales:

import { cva } from "class-variance-authority";

const buttonVariants = cva(
  // Clases base (siempre presentes)
  "inline-flex items-center justify-center rounded-lg font-semibold transition-all focus:outline-none focus:ring-2 focus:ring-offset-2 disabled:opacity-50 disabled:pointer-events-none",
  {
    variants: {
      variant: {
        primary:   "bg-blue-600 text-white hover:bg-blue-700 focus:ring-blue-500",
        secondary: "bg-gray-200 text-gray-900 hover:bg-gray-300 focus:ring-gray-400",
        outline:   "border-2 border-blue-600 text-blue-600 hover:bg-blue-50 focus:ring-blue-500",
        ghost:     "text-gray-700 hover:bg-gray-100 focus:ring-gray-400",
        danger:    "bg-red-600 text-white hover:bg-red-700 focus:ring-red-500",
      },
      size: {
        sm: "px-3 py-1.5 text-sm gap-1.5",
        md: "px-5 py-2.5 text-base gap-2",
        lg: "px-7 py-3.5 text-lg gap-2.5",
        icon: "p-2", // solo icono, sin texto
      },
      fullWidth: {
        true: "w-full",
      },
    },
    defaultVariants: {
      variant: "primary",
      size: "md",
    },
  }
);

// Uso del componente:
function Button({ className, variant, size, fullWidth, ...props }) {
  return (
    <button
      className={cn(buttonVariants({ variant, size, fullWidth }), className)}
      {...props}
    />
  );
}

// Consumo:
<Button variant="outline" size="lg">Cancelar</Button>
<Button variant="danger" size="sm" fullWidth>Eliminar cuenta</Button>
<Button variant="ghost" size="icon"><SettingsIcon /></Button>

Las ventajas de cva frente a ternarios manuales son enormes: tipado automático (con TypeScript obtienes autocompletado en las variantes), valores por defecto, composición de múltiples ejes de variación (variant × size × fullWidth), y una separación nítida entre la lógica de estilos y el marcado del componente.

Instalación del stack completo

Para un proyecto React + Tailwind v4 listo para producción:

# Crear proyecto con Vite
pnpm create vite mi-app --template react
cd mi-app

# Instalar Tailwind CSS v4 y dependencias
pnpm add tailwindcss @tailwindcss/vite
pnpm add clsx tailwind-merge class-variance-authority

# Configurar Vite (vite.config.js)
# Añadir el plugin de Tailwind al array de plugins
// vite.config.js
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({
  plugins: [react(), tailwindcss()],
});

3 · Ejemplo mínimo

El componente más pequeño posible que demuestra el patrón cn() + className como prop: una Card que el consumidor puede extender.

// lib/utils.js — tu función cn() reutilizable
import { clsx } from "clsx";
import { twMerge } from "tailwind-merge";
export function cn(...inputs) { return twMerge(clsx(inputs)); }
// components/Card.jsx
import { cn } from "../lib/utils";

export function Card({ className, children, ...props }) {
  return (
    <div
      className={cn(
        "rounded-xl border border-gray-200 bg-white p-6 shadow-sm dark:border-gray-800 dark:bg-gray-900",
        className
      )}
      {...props}
    >
      {children}
    </div>
  );
}
// App.jsx — consumo del componente
import { Card } from "./components/Card";

export default function App() {
  return (
    <div className="grid grid-cols-3 gap-6 p-8">
      <Card>
        <h2 className="text-lg font-bold">Tarjeta básica</h2>
        <p className="mt-2 text-gray-600">Sin className extra.</p>
      </Card>

      <Card className="border-blue-500 bg-blue-50 ring-2 ring-blue-200">
        <h2 className="text-lg font-bold">Tarjeta destacada</h2>
        <p className="mt-2 text-gray-600">Con className sobrescribiendo estilos.</p>
      </Card>

      <Card className="p-2">
        <h2 className="text-lg font-bold">Padding mínimo</h2>
        <p className="mt-2 text-gray-600">El p-6 base fue sobrescrito por p-2.</p>
      </Card>
    </div>
  );
}

Tres usos distintos del mismo componente. Sin modificar Card.jsx. Esto es componibilidad real: el componente define unos defaults sensatos y quien lo consume los afina para cada contexto.

4 · Ejemplo real

Construyamos un sistema de botones completo con cva y un componente Card compuesto (Card + CardHeader + CardContent + CardFooter) al estilo shadcn/ui:

// components/Button.jsx
import { cva } from "class-variance-authority";
import { cn } from "../lib/utils";

const buttonVariants = cva(
  "inline-flex items-center justify-center rounded-lg font-semibold transition-all duration-200 focus:outline-none focus:ring-2 focus:ring-offset-2 disabled:opacity-50 disabled:pointer-events-none",
  {
    variants: {
      variant: {
        primary: "bg-blue-600 text-white hover:bg-blue-700 focus:ring-blue-500 shadow-sm",
        secondary: "bg-gray-100 text-gray-900 hover:bg-gray-200 focus:ring-gray-400 dark:bg-gray-800 dark:text-gray-100 dark:hover:bg-gray-700",
        outline: "border-2 border-gray-300 text-gray-700 hover:bg-gray-50 focus:ring-gray-400 dark:border-gray-600 dark:text-gray-300 dark:hover:bg-gray-800",
        ghost: "text-gray-700 hover:bg-gray-100 focus:ring-gray-400 dark:text-gray-300 dark:hover:bg-gray-800",
        danger: "bg-red-600 text-white hover:bg-red-700 focus:ring-red-500 shadow-sm",
      },
      size: {
        sm: "h-8 px-3 text-xs gap-1",
        md: "h-10 px-4 text-sm gap-2",
        lg: "h-12 px-6 text-base gap-2.5",
        xl: "h-14 px-8 text-lg gap-3",
      },
    },
    defaultVariants: { variant: "primary", size: "md" },
  }
);

export function Button({ className, variant, size, children, ...props }) {
  return (
    <button className={cn(buttonVariants({ variant, size }), className)} {...props}>
      {children}
    </button>
  );
}
// components/Card.jsx — compuesto con subcomponentes
import { cn } from "../lib/utils";

function CardRoot({ className, children, ...props }) {
  return (
    <div
      className={cn(
        "rounded-xl border border-gray-200 bg-white shadow-sm dark:border-gray-800 dark:bg-gray-900",
        className
      )}
      {...props}
    >
      {children}
    </div>
  );
}

function CardHeader({ className, children, ...props }) {
  return (
    <div
      className={cn("border-b border-gray-200 px-6 py-4 dark:border-gray-800", className)}
      {...props}
    >
      {children}
    </div>
  );
}

function CardContent({ className, children, ...props }) {
  return (
    <div className={cn("px-6 py-4", className)} {...props}>
      {children}
    </div>
  );
}

function CardFooter({ className, children, ...props }) {
  return (
    <div
      className={cn(
        "border-t border-gray-200 px-6 py-4 dark:border-gray-800",
        className
      )}
      {...props}
    >
      {children}
    </div>
  );
}

export const Card = Object.assign(CardRoot, {
  Header: CardHeader,
  Content: CardContent,
  Footer: CardFooter,
});
// App.jsx — uso compuesto
import { Card } from "./components/Card";
import { Button } from "./components/Button";

export default function App() {
  return (
    <div className="mx-auto max-w-lg p-8">
      <Card>
        <Card.Header>
          <h2 className="text-xl font-bold">Plan Profesional</h2>
          <p className="text-sm text-gray-500">Todo lo que necesitas para escalar.</p>
        </Card.Header>
        <Card.Content>
          <div className="text-4xl font-bold">29 €<span className="text-base font-normal text-gray-500">/mes</span></div>
          <ul className="mt-4 space-y-2 text-sm text-gray-600">
            <li>✅ Hasta 10 usuarios</li>
            <li>✅ 100GB de almacenamiento</li>
            <li>✅ Soporte prioritario 24/7</li>
            <li>✅ API access ilimitado</li>
          </ul>
        </Card.Content>
        <Card.Footer className="flex gap-3">
          <Button variant="primary" className="flex-1">Suscribirme</Button>
          <Button variant="outline" className="flex-1">Más info</Button>
        </Card.Footer>
      </Card>
    </div>
  );
}

Patrones importantes en este ejemplo:

  • Card compuesto con Object.assign: Permite usar <Card.Header /> sin imports adicionales. Es el mismo patrón que usa shadcn/ui.
  • Cada subcomponente acepta className: Puedes personalizar cualquier parte sin tocar el componente original.
  • Button con cva: Las variantes están declaradas en un objeto, no en ternarios. Añadir una nueva variante es añadir una línea a ese objeto.
  • className externo al final de cn(): Permite sobrescribir cualquier estilo base.

5 · Buenas prácticas

Haz Evita Por qué
Usa cn() (clsx + tailwind-merge) en todos los componentes Concatenar clases con template literals (`base ${prop}`) en componentes reutilizables Los template literals no eliminan clases conflictivas. Acumular p-4 p-6 produce resultados impredecibles
Pon className al final de cn() para que el consumidor pueda sobrescribir Poner la prop className al principio — el componente se vuelve imposible de personalizar desde fuera La última clase conflictiva gana. Poner className al final respeta la intención de quien consume el componente
Usa cva cuando tu componente tenga 2+ variantes con 2+ valores cada una Usar ternarios anidados para 4 variantes × 5 tamaños — 20 combinaciones manuales, imposible de mantener cva define las variantes de forma declarativa, con defaults y tipado automático. El código se auto-documenta
Acepta y propaga ...props (rest props) para que el HTML subyacente reciba onClick, disabled, id, etc. Definir manualmente cada prop HTML en la interfaz del componente (onClick, type, disabled...) Propagar ...props evita la duplicación infinita de props y hace que tu componente se comporte como un elemento nativo
Usa forwardRef en componentes que envuelven elementos nativos (input, button, etc.) Componentes input sin ref — quien los use no podrá hacer focus programático ni integrarlos con librerías de formularios forwardRef permite que el padre acceda al nodo DOM subyacente, igual que con un elemento nativo
Define cn() una sola vez en lib/utils.js e impórtala en cada componente Redefinir cn() o twMerge() en cada archivo de componente Una única fuente de verdad facilita cambios futuros (como añadir logs de depuración o cambiar la estrategia de merge)

6 · Errores habituales

🚫 Olvidar aceptar className en el componente

El error más común y frustrante. Creas un componente bonito, lo usas en 12 sitios, y de repente necesitas añadirle mt-4 en uno. Si no acepta className, tienes que modificar el componente (y rezar para no romper los otros 11 usos) o envolverlo en un <div> extra. Ambos caminos son malos.

Solución: Todo componente visual debe aceptar className. Es la primera prop que deberías escribir después de children.

🚫 Confundir clsx con tailwind-merge

clsx maneja condicionales (si mostrar o no una clase). twMerge resuelve conflictos (si dos clases compiten, gana la última). Son complementarias, no intercambiables. Usar solo clsx te da conflictos de estilos. Usar solo twMerge te obliga a manejar condicionales con ternarios o &&.

Solución: cn(...inputs) = twMerge(clsx(inputs)). Las dos, juntas, siempre.

🚫 Pasar clases de Tailwind dinámicas sin incluir las completas en el content scan

Tailwind escanea tu código buscando cadenas de clases completas. Si construyes clases dinámicamente (`text-${color}-500`), el escáner no las encuentra y el estilo no se genera. Esto es un error del desarrollador, no de Tailwind.

Solución: Siempre escribe las clases completas. Usa cva para mapear valores a conjuntos de clases predefinidos en lugar de construir strings dinámicos.

🚫 No instalar @tailwindcss/vite en proyectos Vite

Tailwind v4 funciona como plugin de Vite, no como plugin de PostCSS independiente. Si solo instalas tailwindcss sin @tailwindcss/vite y no lo añades a vite.config.js, Tailwind simplemente no procesará tu CSS.

Solución: pnpm add tailwindcss @tailwindcss/vite y añadir tailwindcss() al array de plugins de Vite.

7 · Ejercicio guiado

Vamos a construir paso a paso un componente Badge con variantes usando cva y el patrón cn().

  1. Crea la función cn() en lib/utils.js. 
    import { clsx } from "clsx";
import { twMerge } from "tailwind-merge";
export function cn(...inputs) { return twMerge(clsx(inputs)); }
  2. Define las variantes del Badge con cva. 
    import { cva } from "class-variance-authority";

const badgeVariants = cva(
  "inline-flex items-center rounded-full px-2.5 py-0.5 text-xs font-semibold transition-colors",
  {
    variants: {
      variant: {
        default: "bg-blue-100 text-blue-800 dark:bg-blue-900 dark:text-blue-200",
        success: "bg-green-100 text-green-800 dark:bg-green-900 dark:text-green-200",
        warning: "bg-amber-100 text-amber-800 dark:bg-amber-900 dark:text-amber-200",
        danger:  "bg-red-100 text-red-800 dark:bg-red-900 dark:text-red-200",
        neutral: "bg-gray-100 text-gray-800 dark:bg-gray-800 dark:text-gray-200",
      },
    },
    defaultVariants: { variant: "default" },
  }
);
  3. Implementa el componente Badge. 
    import { cn } from "../lib/utils";

export function Badge({ className, variant, children, ...props }) {
  return (
    <span className={cn(badgeVariants({ variant }), className)} {...props}>
      {children}
    </span>
  );
}
  4. Úsalo en la aplicación con diferentes variantes y personalizaciones. 
    import { Badge } from "./components/Badge";

export default function App() {
  return (
    <div className="flex flex-wrap gap-2 p-8">
      <Badge>Default</Badge>
      <Badge variant="success">Completado</Badge>
      <Badge variant="warning">Pendiente</Badge>
      <Badge variant="danger">Error</Badge>
      <Badge variant="neutral">Inactivo</Badge>
      {/* Sobrescribiendo padding con className externo */}

}

8 · Reto

🎯 Crea un componente Input con variantes cva y composición

Diseña un sistema de Input que incluya:

  • Input: componente base que acepta variant (default, filled), inputSize (sm, md, lg), y className. Usa forwardRef para exponer el ref del <input> nativo.
  • InputGroup: wrapper que acepta un prefix (icono o texto a la izquierda) y un suffix (icono o texto a la derecha), renderizándolos dentro del borde del input.
  • InputLabel: label estilizado que acepta required (bool) y muestra un asterisco rojo si es true.
  • InputError: mensaje de error con icono y color rojo.

Restricciones:

  • Usa cva para las variantes del Input.
  • Todos los subcomponentes deben aceptar className.
  • Usa cn() (clsx + twMerge) en todos.
  • Los estilos deben cubrir dark mode (prefijo dark:).
  • El Input debe propagar ...props al <input> nativo.

9 · Resumen

  • className como prop es el patrón fundamental de componibilidad. Todo componente visual debe aceptarlo y fusionarlo con sus clases base.
  • clsx maneja clases condicionales (objetos, arrays, booleanos). tailwind-merge resuelve conflictos entre clases Tailwind (sabe que p-4 p-6 deben colapsar a p-6). La función cn() las une: twMerge(clsx(...inputs)).
  • class-variance-authority (cva) define variantes de componente de forma declarativa. Sustituye ternarios anidados por un objeto de configuración legible y extensible.
  • En cn(), la última clase conflictiva gana. Poner className al final permite que el consumidor sobrescriba cualquier estilo base.
  • Nunca construyas clases Tailwind dinámicamente (`text-${color}-500`). Tailwind necesita ver las clases completas en tiempo de build. Usa cva para mapear valores a conjuntos predefinidos.
  • En Vite, Tailwind v4 se instala como plugin: @tailwindcss/vite + tailwindcss.
  • El patrón Object.assign (Card = Object.assign(CardRoot, { Header, Content, Footer })) crea componentes compuestos namespaceados sin imports extra.

10 · Preguntas frecuentes

¿Realmente necesito tailwind-merge? ¿No basta con clsx?

Para proyectos pequeños (1-2 personas, pocos componentes), clsx solo puede ser suficiente si eres muy disciplinado con no sobrescribir clases. Pero en cualquier proyecto que crezca, los conflictos de clases aparecen inevitablemente. Imagina un <Button variant="primary" className="p-6" />: sin twMerge, el HTML tendrá p-4 p-6 (las dos clases) y cuál gana depende del orden en el CSS generado. Con twMerge, se resuelve correctamente a p-6. La predecibilidad vale los 2.5KB extra.

¿cva es obligatorio o puedo seguir usando ternarios?

No es obligatorio. Para componentes con 1-2 variantes simples (ej: disabled sí/no), un ternario es perfectamente legible. Pero cuando tienes 3+ variantes con 3+ valores cada una, los ternarios anidados se vuelven ilegibles y propensos a errores. cva brilla en ese escenario. La regla práctica: si tu lógica de variantes ocupa más de 5 líneas, usa cva.

¿Por qué no usar CSS Modules o styled-components con Tailwind?

Puedes, pero pierdes la ventaja principal de Tailwind: la colocalización de estilos y marcado. Con CSS Modules necesitas mantener dos archivos por componente (.jsx + .module.css). Con styled-components pierdes el autocompletado de clases Tailwind y el análisis estático del linter. La combinación React + Tailwind + cn() mantiene todo en un solo archivo, con autocompletado y sin saltos de contexto.

¿Qué pasa si olvido poner className al final de cn()?

Las clases base del componente ganarán siempre a las que pase el consumidor. Si tu componente tiene cn(className, "p-4") y alguien usa <Component className="p-8" />, el resultado será p-4 porque aparece después en la lista de argumentos y twMerge le da prioridad. Regla de oro: className SIEMPRE al final.

¿Funciona tailwind-merge con clases arbitrarias (p-[13px])?

Sí. tailwind-merge entiende valores arbitrarios y los resuelve correctamente. twMerge("p-4 p-[13px]") devuelve "p-[13px]". También maneja modificadores arbitrarios como max-sm:hover:bg-red-500.
