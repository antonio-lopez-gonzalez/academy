Buenas prácticas en producción

Módulo 8 · Tailwind en Frameworks ⏱ 30 minutos

1 · Introducción

Tailwind hace que desarrollar sea rápido. Pero cuando el proyecto crece —más de 20 componentes, varias personas tocando el mismo código, requisitos de rendimiento— aparecen problemas que no veías en los tutoriales: el CSS generado empieza a crecer, las clases se duplican, el diseño se vuelve inconsistente y el equipo empieza a preguntarse si esto escala.

La buena noticia: Tailwind SÍ escala, pero requiere disciplina y conocer las herramientas adecuadas. En esta lección aprenderás:

  • Cómo organizar Tailwind en proyectos grandes: estructura de archivos, custom theme, design tokens.
  • @apply: cuándo sí, cuándo no, y por qué usarlo con moderación.
  • El motor JIT y el tamaño del CSS en producción (~10KB con Brotli).
  • Plugins de Prettier y ESLint para Tailwind: orden automático de clases y detección de errores.
  • Design tokens con @theme: cómo crear un sistema de diseño con Tailwind v4.
  • Estrategias de rendimiento: purgado, caché atómica y el mito del CSS inflado.

2 · Teoría

Organización de Tailwind en proyectos grandes

Cuando tu proyecto tiene 50+ componentes, necesitas una estructura clara:

ESTRUCTURA RECOMENDADA PARA PROYECTOS REACT/VUE CON TAILWIND:

src/
├── app.css                    ← @import "tailwindcss"; y @theme
├── lib/
│   └── utils.js               ← función cn() (clsx + tailwind-merge)
├── components/
│   ├── ui/                    ← átomos: Button, Input, Card, Badge...
│   │   ├── button.jsx
│   │   ├── input.jsx
│   │   └── card.jsx
│   └── features/              ← moléculas: UserMenu, DashboardLayout...
│       ├── user-menu.jsx
│       └── dashboard-layout.jsx
└── styles/
    ├── theme.css              ← @theme con design tokens
    └── base.css               ← @layer base { estilos globales mínimos }

Principios clave:

  • Un solo archivo de entrada CSS (app.css) que importa Tailwind y define el tema.
  • Design tokens en @theme, no en variables CSS sueltas por el código.
  • Componentes atómicos en ui/: piezas pequeñas y reutilizables.
  • Componentes compuestos en features/: combinan átomos para formar secciones de página.

@apply: la herramienta más malentendida de Tailwind

@apply permite extraer clases utilitarias repetidas en una regla CSS. Es una de las decisiones más divisivas de la comunidad. Veamos cuándo usarlo y cuándo no.

Cuándo SÍ usar @apply

1. Estilos base globales que no pueden ser componentes:

@layer base {
  h1 {
    @apply text-4xl font-extrabold tracking-tight text-gray-900 dark:text-white;
  }
  h2 {
    @apply text-3xl font-bold tracking-tight;
  }
  a {
    @apply text-blue-600 underline-offset-4 hover:underline dark:text-blue-400;
  }
}

2. Plugins de terceros que inyectan HTML que no controlas:

.toast-container .toast-success {
  @apply bg-green-50 border-green-400 text-green-800;
}

Cuándo NO usar @apply

1. Crear "clases CSS reutilizables":

/* ❌ MAL: .btn-primary en CSS cuando deberías crear <Button /> */
.btn-primary {
  @apply inline-flex items-center rounded-lg bg-blue-600 px-5 py-2.5;
}
/* El problema: fuente de verdad dividida entre CSS y JSX.
   Usa un componente React/Vue en su lugar. */

2. Para "limpiar" el HTML: la longitud de las clases es una ventaja, no un problema. Cada clase comunica exactamente qué estilo se aplica. Ocultarlas en .card te devuelve a la era de "¿qué estilos tiene esta clase?".

💡 La regla de oro de @apply

Usa @apply SOLO cuando no puedas crear un componente. En React, Vue, Svelte o cualquier framework con componentes, los componentes son la abstracción correcta. @apply es un último recurso para estilos globales y plugins de terceros.

El motor JIT: por qué tu CSS pesa ~10KB

Tailwind v4 usa un motor JIT (Just-In-Time) que genera estilos bajo demanda. Solo las clases que aparecen literalmente en tu código se incluyen en el CSS final. No hay purgado post-build porque nunca se generan las clases no usadas.

MétricaTailwind v2Tailwind v4 (JIT)
CSS en desarrollo~4 MB~50-150 KB (solo clases usadas)
CSS producción (min)~50-100 KB~10-15 KB
CSS con Brotli~15-25 KB~5-10 KB
📝 ¿Por qué comprime tan bien con Brotli?

Las clases de Tailwind son altamente repetitivas (p-4, p-6, p-8...). Brotli y Gzip detectan estos patrones y los comprimen agresivamente. Un CSS de 10KB puede pesar 3-5KB comprimido. Compáralo con Bootstrap (~20KB sin comprimir) o CSS artesanal de un proyecto mediano (~30-80KB). El mito del "CSS inflado" no se sostiene con datos reales.

prettier-plugin-tailwindcss: orden automático de clases

Cuando un componente tiene 20 clases de Tailwind, el orden importa para la legibilidad del equipo. El plugin de Prettier ordena las clases automáticamente según una convención: layout → spacing → typography → colors → borders → effects → states.

pnpm add -D prettier prettier-plugin-tailwindcss
// .prettierrc
{ "plugins": ["prettier-plugin-tailwindcss"] }

Antes y después del plugin:

<!-- ANTES: orden aleatorio, difícil de escanear -->
<button class="text-white px-5 hover:bg-blue-700 bg-blue-600
  focus:ring-2 py-2.5 rounded-lg font-semibold transition-colors">

<!-- DESPUÉS: ordenado automáticamente por Prettier al guardar -->
<button class="rounded-lg bg-blue-600 px-5 py-2.5 text-sm
  font-semibold text-white transition-colors hover:bg-blue-700
  focus:ring-2 focus:ring-blue-500">
📱 Configura formatOnSave en VSCode

Añade a .vscode/settings.json: {"editor.formatOnSave": true}. Cada vez que guardes, Prettier ordena las clases. Cero discusiones en code review sobre el orden.

ESLint plugin para Tailwind: detección de errores

El plugin de ESLint detecta clases que no existen, conflictos y malas prácticas:

pnpm add -D eslint-plugin-tailwindcss

Qué detecta:

  • Clases inexistentes: bg-blurple-500 → error.
  • Clases conflictivas: p-4 p-6 → warning.
  • Clases duplicadas: flex flex → error.
  • className vacío: className="" → warning.

Design tokens con @theme en Tailwind v4

Tailwind v4 usa @theme para definir design tokens. Esto reemplaza al antiguo tailwind.config.js:

@import "tailwindcss";

@theme {
  --color-primary-50: #eff6ff;
  --color-primary-500: #3b82f6;
  --color-primary-900: #1e3a8a;

  --color-success: #10b981;
  --color-warning: #f59e0b;
  --color-danger: #ef4444;

  --font-sans: "Inter Variable", ui-sans-serif, system-ui;
  --font-mono: "JetBrains Mono Variable", ui-monospace, monospace;

  --shadow-card: 0 1px 3px 0 rgb(0 0 0 / 0.1);
  --shadow-modal: 0 20px 25px -5px rgb(0 0 0 / 0.1);

  --radius-sm: 0.375rem;
  --radius-lg: 0.75rem;

  --animate-fade-in: fade-in 0.2s ease-out;

  @keyframes fade-in {
    from { opacity: 0; }
    to { opacity: 1; }
  }
}

Ahora puedes usar tus tokens como clases de Tailwind: bg-primary-500, text-success, font-sans, shadow-card. Las clases se generan con JIT y solo se incluyen si las usas.

💡 ¿Por qué design tokens y no valores arbitrarios?

Los valores arbitrarios (bg-[#2563eb]) son útiles para casos puntuales. Pero si el mismo color aparece en 20 componentes, al cambiarlo tienes que hacer find & replace. Los design tokens centralizan la fuente de verdad: cambias --color-primary-500 en @theme y todos los bg-primary-500 se actualizan automáticamente.

Estrategias de rendimiento

Tailwind v4 introduce una caché atómica que acelera builds incrementales. Cuando modificas un archivo, solo regenera las clases afectadas, no todo el CSS. En proyectos grandes, rebuilds pasan de segundos a milisegundos.

  • Minificación automática: Tailwind v4 minifica en producción. No necesitas cssnano.
  • Content path automático: en Vite, Tailwind escanea los archivos que Vite procesa sin configuración manual.
  • Code splitting de CSS: Vite divide el CSS por chunks. Cada página carga solo el CSS de sus componentes.
  • NO uses safelist: fuerza clases no usadas y destruye la ventaja del JIT. Si necesitas clases dinámicas, escríbelas explícitamente.

4 · Ejemplo real

Sistema de diseño completo para un SaaS usando @theme con todos los tokens centralizados:

/* src/styles/theme.css */
@theme {
  /* Colores de marca */
  --color-acme-50: #f0f9ff;
  --color-acme-500: #0ea5e9;
  --color-acme-900: #0c4a6e;

  /* Semánticos */
  --color-success-light: #dcfce7;
  --color-success: #16a34a;
  --color-warning: #d97706;
  --color-error: #dc2626;

  /* Tipografía */
  --font-sans: "Inter Variable", ui-sans-serif, system-ui;
  --font-display: "Cal Sans", "Inter Variable", ui-sans-serif;

  /* Sombras */
  --shadow-card: 0 1px 3px rgb(0 0 0 / 0.1);
  --shadow-card-hover: 0 10px 15px rgb(0 0 0 / 0.1);

  /* Animaciones */
  --animate-fade-in: fade-in 0.2s ease-out;

  @keyframes fade-in {
    from { opacity: 0; }
    to { opacity: 1; }
  }
}
/* src/app.css */
@import "tailwindcss";
@import "./styles/theme.css";

@layer base {
  body {
    @apply bg-white text-gray-900 antialiased dark:bg-gray-950 dark:text-gray-100;
  }
}
// Uso real en un componente — consistencia total
function PricingCard({ plan }) {
  return (
    <div className="rounded-xl bg-white p-8 shadow-card
      ring-1 ring-gray-200 transition-shadow hover:shadow-card-hover
      dark:bg-gray-900 dark:ring-gray-800">
      <h3 className="font-display text-2xl font-bold text-acme-500">
        {plan.name}
      </h3>
      <div className="mt-4 text-5xl font-extrabold">
        {plan.price} €
      </div>
      <button className="mt-8 w-full rounded-lg bg-acme-500 px-4 py-3
        text-sm font-semibold text-white hover:bg-acme-600
        focus:ring-2 focus:ring-acme-500 transition-colors">
        Elegir plan
      </button>
    </div>
  );
}

Puntos clave:

  • Tokens centralizados: cambiar el color de marca es editar una línea en theme.css. Todos los componentes que usan acme-* se actualizan.
  • Sombras como tokens: defines --shadow-card una vez, lo usas como shadow-card. Fin de las sombras inconsistentes.
  • Animaciones declarativas: animate-fade-in disponible en cualquier componente.
  • Tipografía de marca: font-display para headings, font-sans para body. Consistencia tipográfica total.

6 · Errores habituales

🚫 Abusar de @apply para todo

El error más común: usar @apply para recrear metodologías CSS tradicionales (BEM, Sass) dentro de Tailwind. El resultado es un archivo CSS lleno de clases .btn-primary, .card-header que envuelven utilitarias. Ahora tienes DOS sitios donde mirar los estilos (HTML + CSS), perdiste el autocompletado de Tailwind, y cada cambio requiere saltar entre archivos.

Solución: Extrae componentes de framework. <Button variant="primary" /> en lugar de .btn-primary. Guarda @apply para cuando no tengas otra opción.

🚫 No instalar prettier-plugin-tailwindcss

Cada desarrollador escribe las clases en orden distinto. Los diffs de Git mezclan cambios reales con cambios de orden. Las code reviews se alargan innecesariamente. El ojo se acostumbra a buscar ciertas clases en ciertas posiciones y la falta de consistencia ralentiza a todo el equipo.

Solución: 5 minutos de configuración en el primer commit. Ahorra horas de fricción durante toda la vida del proyecto.

🚫 Usar safelist para clases dinámicas

El safelist fuerza clases no usadas en el CSS final. Infla el CSS y anula la ventaja del JIT. Suele usarse como parche cuando alguien genera clases dinámicamente (`text-${color}-500`), que es otro error en sí mismo.

Solución: Nunca generes clases Tailwind dinámicamente. Mapea valores a clases completas con un objeto o cva. Si una clase no está escrita literalmente en tu código, no debe existir en el CSS.

🚫 No documentar los design tokens

Defines tokens pero no explicas cuándo usar cada uno. Un dev nuevo ve --color-acme-500 y --color-primary-600 y no sabe cuál usar. Acaba usando valores arbitrarios porque es más fácil que preguntar.

Solución: Comenta theme.css con el propósito de cada token. Crea una página simple con todos los colores y estilos aplicados en swatches visibles.

🚫 Ignorar eslint-plugin-tailwindcss en CI/CD

El linter detecta clases que no existen, pero solo si se ejecuta. Si no está en CI, un bg-rebeccapurple-500 llega a producción y el elemento no tiene fondo.

Solución: Añade eslint . al pipeline de CI y haz que falle el build con errores. Las clases inexistentes son bugs visuales; trátalas como tales.

8 · Reto

🎯 Auditoría de un proyecto Tailwind existente

Toma un proyecto donde hayas usado Tailwind (o imagina uno) y audítalo con esta checklist de producción:

  • [ ] ¿Tienes prettier-plugin-tailwindcss instalado y funcionando?
  • [ ] ¿Tienes eslint-plugin-tailwindcss ejecutándose en CI/CD y fallando el build si hay errores?
  • [ ] ¿Tus colores, fuentes y sombras recurrentes están definidos como design tokens en @theme?
  • [ ] ¿Evitaste @apply para crear clases CSS reutilizables (solo @layer base o plugins)?
  • [ ] ¿Tu CSS de producción pesa menos de 20KB sin comprimir?
  • [ ] ¿No hay valores arbitrarios repetidos (>3 veces) que deberían ser tokens?
  • [ ] ¿La estructura distingue entre componentes atómicos (ui/) y compuestos (features/)?
  • [ ] ¿Los cambios en design tokens pasan por code review?

Si tu respuesta es NO en 2+ puntos, tienes deuda técnica de Tailwind. Cada punto que falles hoy te costará 10x más arreglarlo cuando el proyecto tenga el doble de componentes.

9 · Resumen

  • Organiza: tokens en @theme, átomos en ui/, compuestos en features/, un solo CSS de entrada.
  • @apply con moderación: solo en @layer base y plugins de terceros. Para todo lo demás, componentes de framework.
  • JIT: solo genera clases usadas. CSS de producción ~10KB, ~5KB con Brotli. No necesitas purgeCSS ni safelist.
  • prettier-plugin-tailwindcss: ordena clases automáticamente. Instálalo el día 1.
  • eslint-plugin-tailwindcss: detecta clases erróneas. Ejecútalo en CI/CD.
  • Design tokens: centralizan la fuente de verdad del diseño. Cambia un color en @theme y se propaga a toda la app.
  • Caché atómica: builds incrementales en milisegundos. Solo regenera clases afectadas.
  • Nunca generes clases dinámicamente: usa objetos de mapeo o cva con variantes explícitas.

10 · Preguntas frecuentes

¿Realmente Tailwind en producción pesa solo ~10KB?

Sí, para una aplicación típica. El CSS contiene solo las clases que tu código usa literalmente (~300 clases = 10-15KB). Con Brotli, 5-8KB. Bootstrap son ~20KB sin comprimir; el CSS artesanal de un proyecto mediano, 30-80KB. Tailwind es consistentemente más pequeño precisamente porque solo incluye lo que usas.

¿Necesito @apply si uso componentes de React/Vue?

No. Extrae la repetición creando un componente (<Button />), no una clase CSS. Los componentes encapsulan lógica, accesibilidad y variantes (con props). @apply es para cuando no tienes componentes: HTML plano, estilos base globales, o plugins que inyectan HTML ajeno.

¿Tailwind v4 sigue siendo compatible con PostCSS?

Sí. Aunque Vite es el camino recomendado (@tailwindcss/vite), Tailwind v4 sigue siendo un plugin PostCSS compatible con Webpack, Rollup y otros bundlers. La configuración CSS-first (@theme) funciona igual en todos.

¿Cómo audito el tamaño de mi CSS en producción?

Ejecuta pnpm build y mira dist/assets/. Busca archivos .css. Si alguno supera 30KB, tienes clases no usadas o un safelist inflado. También usa las DevTools: pestaña Network, filtra por CSS, recarga y mira el tamaño transferido. Una app típica envía 3-8KB de CSS por la red.

¿Los tokens de @theme funcionan con IntelliSense de VSCode?

Sí. Tailwind CSS IntelliSense (extensión oficial) lee @theme e incluye tus tokens en el autocompletado. Si defines --color-brand-500, al escribir bg-brand- verás todas las variantes con previsualización de color.
