Persistencia: ficheros, SQLite y migraciones

Módulo 6 · Red y CLI real ⏱ 45 minutos

1 · Introducción

Hasta ahora, urlshort guarda los enlaces en un HashMap: al cerrar el proceso, todo desaparece. La persistencia parece el problema más simple del curso —«escribir un fichero»— y es donde más datos se pierden en producción. Un proceso que muere a mitad de escritura deja un JSON truncado; dos procesos que escriben a la vez se pisan; una migración a medias deja la base de datos en un estado que nadie probó.

Esta lección construye un Store con dos implementaciones intercambiables: un fichero JSON (sencillo, legible, suficiente para miles de enlaces) y SQLite (transaccional, indexado, suficiente para millones). La misma trait, el mismo contrato, los mismos tests. Cambiar de una a otra es una línea en la configuración.

¿Por qué existe esta lección?

Porque «funciona en mi máquina» deja de ser cierto en cuanto hay dos procesos, un corte de luz o una actualización de esquema. La persistencia se diseña con tres preguntas: ¿qué pasa si el proceso muere ahora?, ¿qué pasa si dos escriben a la vez?, ¿qué pasa cuando cambie el formato? JSON y SQLite responden a las tres de forma distinta, y saber cuándo usar cada uno es criterio de ingeniería.

Errores típicos: escribir directamente sobre el fichero bueno; hacer rename antes de fsync; no bloquear el fichero entre procesos; ignorar database is locked; ejecutar migraciones sin tabla de versiones; retener una conexión rusqlite a través de un .await; copiar una base SQLite en caliente con cp.

2 · Teoría

Una trait, dos motores

El dominio no debe saber si los datos viven en un fichero o en una base de datos. Esa frontera es una trait:

pub trait Store {
    fn insert(&mut self, link: Link) -> Result<(), StoreError>;
    fn get(&self, code: &str) -> Result<Option<Link>, StoreError>;
    fn list(&self, limit: usize) -> Result<Vec<Link>, StoreError>;
    fn delete(&mut self, code: &str) -> Result<bool, StoreError>;
    fn register_hit(&mut self, code: &str) -> Result<Option<Link>, StoreError>;
}

Los métodos son object-safe: Box<dyn Store> funciona y el CLI elige el motor en tiempo de ejecución. El contrato incluye el significado de los errores: insertar un código repetido devuelve Duplicate en ambos motores, aunque SQLite lo detecte como violación de clave primaria. Si las implementaciones no coinciden, la trait es una mentira.

JSON: escribir sin destruir

Un fichero JSON se reescribe entero en cada cambio. Eso es aceptable hasta unos miles de enlaces, y peligroso si se hace mal. La regla es nunca escribir sobre el fichero que estás leyendo:

  1. serializar en memoria
  2. escribir en links.json.tmp
  3. fsync del temporal      ← los bytes llegan al disco
  4. rename(tmp, links.json) ← atómico en el mismo sistema de ficheros
  5. (en Unix) fsync del directorio

  si el proceso muere en 2 o 3: queda un .tmp huérfano, el bueno sigue intacto
  si muere en 4: el rename es todo o nada

El rename sustituye el fichero de forma atómica dentro del mismo sistema de ficheros. Sin el sync_all previo, el rename puede llegar al disco antes que los datos y dejar un fichero vacío tras un corte de luz. Y como el JSON es un documento completo, dos procesos que lo editen a la vez se pisan: hace falta un bloqueo de fichero (fs2) que impida abrirlo dos veces en modo escritura.

La conclusión práctica: JSON para configuración y volúmenes pequeños; SQLite en cuanto haya escrituras concurrentes, consultas o crecimiento. No es una guerra: son herramientas distintas.

SQLite: cuatro pragmas que importan

  • PRAGMA journal_mode = WAL: escribe en un write-ahead log. Los lectores no bloquean al escritor y viceversa. Es el modo por defecto recomendable para una aplicación. No funciona igual en :memory:.
  • PRAGMA busy_timeout = 5000: si otra conexión tiene el bloqueo, espera hasta 5 s antes de devolver SQLITE_BUSY. Sin esto, dos procesos se pelean y uno falla al instante.
  • PRAGMA synchronous = NORMAL: con WAL, buen equilibrio entre durabilidad y velocidad. FULL es más seguro y más lento.
  • PRAGMA foreign_keys = ON: SQLite no aplica claves foráneas por defecto. Si el esquema las usa, hay que activarlas en cada conexión.

Con WAL sigue habiendo un solo escritor. Las transacciones de escritura deben abrirse con BEGIN IMMEDIATE (TransactionBehavior::Immediate) para tomar el bloqueo al principio y no descubrir a mitad que otro se adelantó. Un BEGIN diferido que empieza leyendo y luego quiere escribir puede fallar con SQLITE_BUSY sin poder reintentar con seguridad.

Migraciones: el esquema también es código

Una migración es un paso numerado, ordenado e irreversible en producción. Se aplica una vez, se registra en una tabla y nunca se edita después:

CREATE TABLE _migrations (
    version    TEXT PRIMARY KEY,
    applied_at TEXT NOT NULL DEFAULT (datetime('now'))
);

Al arrancar, el programa crea la tabla si no existe, recorre la lista de migraciones y aplica las que faltan, cada una dentro de su propia transacción. Reglas que evitan desastres: solo cambios aditivos (añadir columnas y tablas, no borrar), valores por defecto para las columnas nuevas, rellenar datos en lotes y hacer copia antes de migrar. Si una migración falla, el proceso no debe arrancar con el esquema a medias.

Transacciones, índices y copias

Un hit es un incremento más una lectura: si se hace en dos pasos sin transacción, dos peticiones pueden leer el mismo contador y perder uno. Con UPDATE … ; SELECT … dentro de una transacción, el resultado es consistente. Los índices aceleran las consultas que de verdad haces (ORDER BY created_at DESC, búsquedas por expires_at) y cuestan espacio y escrituras: no indexes por si acaso.

Para copias de seguridad en caliente, VACUUM INTO 'backup.db' produce una copia consistente sin parar el servidor. Copiar a mano links.db mientras hay un WAL activo puede darte una base incoherente: te falta el -wal o lo copias a medias.

3 · Ejemplo mínimo

Guardar una estructura en JSON y volver a leerla, con escritura atómica. Cargo.toml:

[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
use std::{fs, io::Write, path::Path};

#[derive(Debug, serde::Serialize, serde::Deserialize)]
struct Config {
    format: String,
    color: bool,
}

fn save(path: &Path, config: &Config) -> Result<(), Box<dyn std::error::Error>> {
    let tmp = path.with_extension("tmp");
    let bytes = serde_json::to_vec_pretty(config)?;

    {
        let mut file = fs::File::create(&tmp)?;
        file.write_all(&bytes)?;
        file.sync_all()?;          // los bytes están en disco
    }

    fs::rename(&tmp, path)?;       // sustitución atómica
    Ok(())
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = Config { format: "json".into(), color: false };
    save(Path::new("config.json"), &config)?;

    let texto = fs::read_to_string("config.json")?;
    let leido: Config = serde_json::from_str(&texto)?;
    println!("{leido:?}");
    Ok(())
}

Línea a línea:

  • with_extension("tmp") deja config.tmp junto al bueno: el rename debe ser en el mismo sistema de ficheros para ser atómico.
  • El bloque { … } cierra el fichero antes del rename. En Windows no puedes renombrar un fichero abierto.
  • sync_all() fuerza a disco. Sin él, el orden entre datos y rename no está garantizado.
  • serde_json::to_vec_pretty serializa a memoria: si falla, no has tocado el fichero bueno.
  • from_str valida el esquema: un campo que falta o un tipo distinto produce un error con línea y columna.

Esto todavía no es seguro entre procesos

La escritura atómica protege de un corte a mitad, pero no de dos procesos que leen, modifican y escriben a la vez: el último gana y pierde los cambios del otro. Para eso hace falta el bloqueo de fichero que veremos en el ejemplo real.

4 · Ejemplo real

El Store de urlshort con las dos implementaciones. Primero los tipos comunes:

// src/store.rs
use std::{
    collections::BTreeMap,
    fs::{self, File, OpenOptions},
    io::Write,
    path::{Path, PathBuf},
};

use fs2::FileExt;
use rusqlite::{params, Connection, ErrorCode, OptionalExtension, TransactionBehavior};
use serde::{Deserialize, Serialize};
use thiserror::Error;

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct Link {
    pub code: String,
    pub url: String,
    pub created_at: String,   // RFC 3339; el formato lo fija la capa que crea el enlace
    pub hits: u32,
}

#[derive(Debug, Error)]
pub enum StoreError {
    #[error("no se pudo acceder al almacén: {0}")]
    Io(#[from] std::io::Error),
    #[error("datos corruptos: {0}")]
    Json(#[from] serde_json::Error),
    #[error("error de SQLite: {0}")]
    Sqlite(#[from] rusqlite::Error),
    #[error("el almacén está bloqueado por otro proceso")]
    Locked,
    #[error("el código ya existe: {0}")]
    Duplicate(String),
    #[error("configuración inválida: {0}")]
    Setup(String),
}

pub trait Store {
    fn insert(&mut self, link: Link) -> Result<(), StoreError>;
    fn get(&self, code: &str) -> Result<Option<Link>, StoreError>;
    fn list(&self, limit: usize) -> Result<Vec<Link>, StoreError>;
    fn delete(&mut self, code: &str) -> Result<bool, StoreError>;
    fn register_hit(&mut self, code: &str) -> Result<Option<Link>, StoreError>;
}

El motor JSON mantiene el mapa en memoria y vuelca con rename. El bloqueo exclusivo se toma al abrir y se libera al cerrar (o al salir del proceso):

pub struct JsonStore {
    path: PathBuf,
    links: BTreeMap<String, Link>,
    _lock: File,
}

impl JsonStore {
    pub fn open(path: impl Into<PathBuf>) -> Result<Self, StoreError> {
        let path = path.into();
        if let Some(dir) = path.parent() {
            if !dir.as_os_str().is_empty() {
                fs::create_dir_all(dir)?;
            }
        }

        let lock = OpenOptions::new()
            .create(true)
            .truncate(false)
            .write(true)
            .open(path.with_extension("lock"))?;
        lock.try_lock_exclusive().map_err(|_| StoreError::Locked)?;

        let links = match fs::read(&path) {
            Ok(bytes) => serde_json::from_slice(&bytes)?,
            Err(err) if err.kind() == std::io::ErrorKind::NotFound => BTreeMap::new(),
            Err(err) => return Err(err.into()),
        };

        Ok(Self { path, links, _lock: lock })
    }

    fn flush(&self) -> Result<(), StoreError> {
        let tmp = self.path.with_extension("json.tmp");
        let bytes = serde_json::to_vec_pretty(&self.links)?;

        {
            let mut file = File::create(&tmp)?;
            file.write_all(&bytes)?;
            file.sync_all()?;
        }

        fs::rename(&tmp, &self.path)?;
        Ok(())
    }
}

impl Store for JsonStore {
    fn insert(&mut self, link: Link) -> Result<(), StoreError> {
        if self.links.contains_key(&link.code) {
            return Err(StoreError::Duplicate(link.code));
        }
        self.links.insert(link.code.clone(), link);
        self.flush()
    }

    fn get(&self, code: &str) -> Result<Option<Link>, StoreError> {
        Ok(self.links.get(code).cloned())
    }

    fn list(&self, limit: usize) -> Result<Vec<Link>, StoreError> {
        Ok(self.links.values().rev().take(limit).cloned().collect())
    }

    fn delete(&mut self, code: &str) -> Result<bool, StoreError> {
        let removed = self.links.remove(code).is_some();
        if removed {
            self.flush()?;
        }
        Ok(removed)
    }

    fn register_hit(&mut self, code: &str) -> Result<Option<Link>, StoreError> {
        let Some(link) = self.links.get_mut(code) else {
            return Ok(None);
        };
        link.hits += 1;
        let updated = link.clone();
        self.flush()?;      // el préstamo mutable termina aquí
        Ok(Some(updated))
    }
}

Y el motor SQLite, con esquema versionado, WAL y transacciones:

pub struct SqliteStore {
    conn: Connection,
}

const MIGRATIONS: &[(&str, &str)] = &[
    (
        "0001_init",
        "CREATE TABLE links (
             code       TEXT PRIMARY KEY,
             url        TEXT NOT NULL,
             created_at TEXT NOT NULL,
             hits       INTEGER NOT NULL DEFAULT 0
         );
         CREATE INDEX idx_links_created_at ON links(created_at DESC);",
    ),
    (
        "0002_hits_index",
        "CREATE INDEX idx_links_hits ON links(hits DESC);",
    ),
];

impl SqliteStore {
    pub fn open(path: impl AsRef<Path>) -> Result<Self, StoreError> {
        let conn = Connection::open(path)?;

        // WAL devuelve una fila: hay que leerla, no usar execute.
        let mode: String = conn.query_row("PRAGMA journal_mode = WAL", [], |row| row.get(0))?;
        if !mode.eq_ignore_ascii_case("wal") {
            return Err(StoreError::Setup(format!("no se pudo activar WAL (modo: {mode})")));
        }
        conn.pragma_update(None, "busy_timeout", 5_000)?;
        conn.pragma_update(None, "synchronous", "NORMAL")?;
        conn.pragma_update(None, "foreign_keys", "ON")?;

        migrate(&conn)?;
        Ok(Self { conn })
    }
}

fn migrate(conn: &Connection) -> Result<(), StoreError> {
    conn.execute_batch(
        "CREATE TABLE IF NOT EXISTS _migrations (
             version    TEXT PRIMARY KEY,
             applied_at TEXT NOT NULL DEFAULT (datetime('now'))
         );",
    )?;

    for &(version, sql) in MIGRATIONS {
        let applied: bool = conn.query_row(
            "SELECT EXISTS (SELECT 1 FROM _migrations WHERE version = ?1)",
            [version],
            |row| row.get(0),
        )?;
        if applied {
            continue;
        }

        // Cada migración es atómica: o entra entera o no entra.
        let tx = conn.unchecked_transaction()?;
        tx.execute_batch(sql)?;
        tx.execute("INSERT INTO _migrations (version) VALUES (?1)", [version])?;
        tx.commit()?;
    }

    Ok(())
}

fn row_to_link(row: &rusqlite::Row<'_>) -> rusqlite::Result<Link> {
    Ok(Link {
        code: row.get(0)?,
        url: row.get(1)?,
        created_at: row.get(2)?,
        hits: row.get::<_, i64>(3)? as u32,
    })
}

impl Store for SqliteStore {
    fn insert(&mut self, link: Link) -> Result<(), StoreError> {
        let result = self.conn.execute(
            "INSERT INTO links (code, url, created_at, hits) VALUES (?1, ?2, ?3, ?4)",
            params![link.code, link.url, link.created_at, link.hits as i64],
        );

        match result {
            Ok(_) => Ok(()),
            // La violación de clave primaria es el "Duplicate" de este motor.
            Err(rusqlite::Error::SqliteFailure(err, _))
                if err.code == ErrorCode::ConstraintViolation =>
            {
                Err(StoreError::Duplicate(link.code))
            }
            Err(err) => Err(err.into()),
        }
    }

    fn get(&self, code: &str) -> Result<Option<Link>, StoreError> {
        let mut stmt = self
            .conn
            .prepare_cached("SELECT code, url, created_at, hits FROM links WHERE code = ?1")?;
        Ok(stmt.query_row([code], row_to_link).optional()?)
    }

    fn list(&self, limit: usize) -> Result<Vec<Link>, StoreError> {
        let mut stmt = self.conn.prepare_cached(
            "SELECT code, url, created_at, hits FROM links ORDER BY created_at DESC LIMIT ?1",
        )?;
        let rows = stmt.query_map([limit as i64], row_to_link)?;
        Ok(rows.collect::<Result<Vec<_>, _>>()?)
    }

    fn delete(&mut self, code: &str) -> Result<bool, StoreError> {
        let affected = self.conn.execute("DELETE FROM links WHERE code = ?1", [code])?;
        Ok(affected > 0)
    }

    fn register_hit(&mut self, code: &str) -> Result<Option<Link>, StoreError> {
        // IMMEDIATE toma el bloqueo de escritura al empezar.
        let tx = self
            .conn
            .transaction_with_behavior(TransactionBehavior::Immediate)?;

        let affected = tx.execute("UPDATE links SET hits = hits + 1 WHERE code = ?1", [code])?;
        if affected == 0 {
            return Ok(None);       // el drop hace rollback: no hay nada que guardar
        }

        let mut stmt = tx.prepare("SELECT code, url, created_at, hits FROM links WHERE code = ?1")?;
        let link = stmt.query_row([code], row_to_link).optional()?;
        drop(stmt);
        tx.commit()?;
        Ok(link)
    }
}

El selector es una función y el resto del programa usa Box<dyn Store>:

pub fn open_store(backend: &str, path: &Path) -> Result<Box<dyn Store>, StoreError> {
    match backend {
        "json" => Ok(Box::new(JsonStore::open(path)?)),
        "sqlite" => Ok(Box::new(SqliteStore::open(path)?)),
        other => Err(StoreError::Setup(format!("backend desconocido: {other}"))),
    }
}

// src/main.rs — el resto del programa no sabe qué motor hay detrás
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut store = open_store("sqlite", Path::new("urlshort.db"))?;
    store.insert(Link {
        code: "rust".into(),
        url: "https://www.rust-lang.org/".into(),
        created_at: "2026-01-15T10:00:00Z".into(),
        hits: 0,
    })?;
    println!("{:?}", store.get("rust")?);
    Ok(())
}

#[cfg(test)]
mod tests {

    fn link(code: &str) -> Link {

    fn contrato(store: &mut dyn Store) {
        store.insert(link("rust")).expect("insertar");
        store.insert(link("cargo")).expect("insertar");

        assert_eq!(store.get("rust").expect("leer").expect("existe").url, "https://example.com/rust");
        assert!(store.get("nope").expect("leer").is_none());
        assert!(matches!(store.insert(link("rust")), Err(StoreError::Duplicate(_))));

        assert_eq!(store.register_hit("rust").expect("hit").expect("existe").hits, 1);
        assert_eq!(store.list(10).expect("listar").len(), 2);

        assert!(store.delete("cargo").expect("borrar"));
        assert!(!store.delete("cargo").expect("borrar"));

Analogía: el cuaderno y la caja registradora

El JSON es un cuaderno: para cambiar una línea reescribes el cuaderno entero y lo pones encima del anterior; si dos escriben a la vez, se lían. SQLite es una caja registradora: apunta operaciones en un diario, las confirma con un recibo y sabe deshacer una venta a medias. Las dos guardan datos; solo una está pensada para que varios cobren a la vez.

Empieza por JSON y migra cuando duela

No metas SQLite en un CLI que guarda veinte enlaces: el JSON es inspeccionable con cat y no añade una dependencia nativa. Cambia cuando aparezcan escrituras concurrentes, consultas o decenas de miles de registros; la trait hace que el cambio no toque el dominio.

6 · Errores habituales

1. Reescribir el fichero en su sitio

Mal:

let mut file = File::create("links.json")?;   // ya has truncado el bueno
serde_json::to_writer(&mut file, &links)?;
// si el proceso muere aquí, links.json queda vacío o a medias

Por qué está mal: File::create trunca antes de escribir. No hay recuperación. Bien: temporal, sync_all y rename.

2. Renombrar antes de sincronizar

Mal: escribir el temporal, cerrarlo y renombrarlo sin sync_all. El sistema de ficheros puede reordenar las escrituras y dejar el nombre apuntando a un fichero vacío tras un corte de luz. Bien: sync_all() antes del rename; en Unix, sincronizar también el directorio con File::open(dir)?.sync_all() si la durabilidad es crítica.

3. Ignorar el bloqueo entre procesos

Mal: dos instancias del CLI abiertas sobre el mismo JSON. Cada una leyó el mapa al arrancar; la segunda escribe y borra los enlaces que añadió la primera. Bien: try_lock_exclusive() al abrir y un error claro (StoreError::Locked) en vez de silencio.

4. database is locked

Mal: abrir la conexión sin busy_timeout y con transacciones diferidas.

Error: error de SQLite: database is locked (code 5)

Por qué está mal: dos conexiones compiten por el único escritor de SQLite; sin espera, la segunda falla al instante. Bien: busy_timeout, WAL y BEGIN IMMEDIATE para las escrituras.

5. Migrar sin versiones

Mal: ejecutar ALTER TABLE links ADD COLUMN expires_at TEXT en cada arranque.

Error: error de SQLite: duplicate column name: expires_at (code 1)

Por qué está mal: el esquema ya cambió, pero el programa no sabe que ese paso está hecho. Bien: la tabla _migrations y aplicar solo lo que falta.

6. Una conexión rusqlite a través de un .await

Mal: en un handler de Axum, guardar Connection en el estado y hacer state.conn.lock().unwrap() antes de un .await.

error[E0277]: future cannot be sent between threads safely
  = help: within `impl Future<Output = ...>`,
          the trait `Send` is not implemented for `std::sync::MutexGuard<'_, rusqlite::Connection>`

Por qué está mal: Connection no es Sync y el guard no puede cruzar un punto de await. Bien: tokio::task::spawn_blocking con la conexión movida dentro, un pool como r2d2_sqlite o tokio-rusqlite, y tareas bloqueantes fuera del runtime.

Objetivo: implementar el Store, comprobar que los dos motores cumplen el mismo contrato y ver el efecto de los índices y de una migración.

cargo add fs2

    bundled compila SQLite dentro del binario: no depende de la versión del sistema, a cambio de unos segundos más de compilación.

  2. Pega el código del ejemplo real en src/store.rs, añade pub mod store; y ejecuta cargo test. Deben pasar json_cumple_el_contrato y sqlite_cumple_el_contrato. Si uno falla, el contrato está mal definido: arréglalo en las dos implementaciones, no en el test.
  3. Provoca una corrupción controlada. Escribe echo '{roto' > links.json y ejecuta el CLI con backend JSON. Debes ver un error datos corruptos: … con línea y columna, no un panic. Decide qué hacer: renombrar el fichero a .bak y empezar vacío, o abortar. Documenta la decisión.
  4. Mira el esquema y los índices. 
    sqlite3 urlshort.db ".schema links"
sqlite3 urlshort.db "EXPLAIN QUERY PLAN
  SELECT code, url, created_at, hits FROM links
  WHERE code = 'rust';"
sqlite3 urlshort.db "EXPLAIN QUERY PLAN
  SELECT * FROM links ORDER BY created_at DESC LIMIT 20;"

    La primera consulta debe usar el índice de la clave primaria (SEARCH links USING INDEX …); la segunda, idx_links_created_at. Si ves SCAN links en la segunda, el índice no está o la consulta no lo aprovecha.

  5. Añade una migración real. Crea 0003_last_hit con ALTER TABLE links ADD COLUMN last_hit_at TEXT;, arranca dos veces y comprueba con SELECT * FROM _migrations; que hay tres filas y ningún duplicado. Actualiza register_hit para escribir last_hit_at = datetime('now') y verifica que los enlaces antiguos (con NULL) siguen funcionando. Después ejecuta EXPLAIN QUERY PLAN SELECT * FROM links ORDER BY hits DESC LIMIT 20; y comprueba que usa idx_links_hits.
  6. Prueba la concurrencia. Abre dos procesos del CLI con el mismo JSON: el segundo debe fallar con el almacén está bloqueado por otro proceso. Con SQLite, en cambio, ambos deben poder leer y uno esperar al otro para escribir: comprueba que no hay errores intermitentes.
  7. Haz una copia en caliente. 
    sqlite3 urlshort.db "VACUUM INTO 'backup-2026-01-15.db';"
ls -lh urlshort.db* backup-2026-01-15.db

    Abre la copia con sqlite3 backup-2026-01-15.db "SELECT COUNT(*) FROM links;". Debe funcionar sin el -wal original: la copia es autocontenida.

Criterio de éxito

Puedes responder con datos: qué pasa si matas el proceso a mitad de escritura, cuántos escritores admite cada motor, qué consulta usa qué índice y qué migración está aplicada. Y el mismo test pasa en JSON y en SQLite.

8 · Reto

🎯 Caducidad, limpieza y migración con relleno

Los enlaces pueden caducar. Añade al dominio expires_at: Option<String> y:

  • Resuelve un enlace caducado con un error de dominio Expired, que el servidor traducirá a 410 Gone.
  • Escribe la migración 0004_expires_at que añada la columna y rellene los enlaces existentes con NULL (sin caducidad) en la misma transacción.
  • Añade un subcomando urlshort gc --days 30 que borre en lotes los enlaces caducados hace más de N días, informando cuántos borró. Debe funcionar con los dos motores y no bloquear la base durante minutos.
  • Haz que el JSON no reescriba el fichero si el gc no borró nada.

Pista: en SQLite, DELETE FROM links WHERE expires_at < ?1 LIMIT ?2 no existe tal cual; usa una subconsulta con rowid IN (SELECT rowid … LIMIT ?2) dentro de una transacción, o borra por rangos de fecha. En JSON, retén los códigos a borrar, comprueba is_empty() y solo entonces llama a flush. Y recuerda que un ALTER TABLE con valor por defecto no puede usar funciones no constantes en SQLite.

9 · Resumen

  • La persistencia se diseña con tres preguntas: corte a mitad, concurrencia y evolución del esquema.
  • JSON se escribe con temporal + sync_all + rename; nunca sobre el fichero bueno.
  • Entre procesos, el JSON necesita un bloqueo exclusivo (fs2); sin él, el último gana.
  • SQLite aporta transacciones, índices y concurrencia; con WAL, busy_timeout y BEGIN IMMEDIATE.
  • Las migraciones son pasos numerados, registrados en _migrations y aplicados una sola vez dentro de una transacción.
  • Una trait Store con dos implementaciones permite cambiar de motor sin tocar el dominio, y un test de contrato lo garantiza.
  • Las copias se hacen con VACUUM INTO o .backup, nunca copiando el fichero con WAL activo.

10 · Preguntas frecuentes

¿rusqlite o sqlx?

rusqlite es síncrono, directo y con el SQL a la vista; ideal para CLI y para envolver en spawn_blocking dentro de un servidor. sqlx es async, soporta varios motores y verifica las consultas contra el esquema en tiempo de compilación (query!), a cambio de una configuración y una curva mayores. Para este curso, rusqlite enseña mejor lo que hay debajo.

¿Por qué no un ORM?

Porque añade una capa que oculta el SQL y las transacciones, justo lo que necesitas entender aquí. Diesel y SeaORM son buenas opciones en equipos grandes con muchas entidades; para dos tablas y cinco consultas, el SQL explícito es más corto, más rápido de leer y no te esconde un N+1.

¿Dónde guardo el fichero en una app real?

Ni en el directorio actual ni dentro del binario: usa el directorio de datos del usuario. En Linux, $XDG_DATA_HOME/urlshort (o ~/.local/share/urlshort); en macOS, ~/Library/Application Support/urlshort; en Windows, %APPDATA%\urlshort. El crate directories resuelve los tres. Y permite sobreescribirlo con --data, que ya tienes en el CLI.

¿SQLite aguanta un servidor web?

Sí, para cargas moderadas y un solo proceso escritor. Con WAL, los lectores no se bloquean. El patrón en Axum es un pool (r2d2_sqlite) y spawn_blocking para no bloquear el runtime, o tokio-rusqlite. Si necesitas varios escritores en máquinas distintas, toca PostgreSQL, no SQLite sobre NFS.

¿Puedo cambiar de JSON a SQLite sin perder datos?

Sí: escribe un subcomando migrate que abra el JsonStore, recorra list(usize::MAX) e inserte cada enlace en un SqliteStore dentro de una transacción. Como ambos implementan Store, el código es un bucle y el test de contrato ya te dice que los datos caben. Haz copia del JSON antes y verifica el recuento al terminar.
