HTTP con reqwest

Módulo 6 · Red y CLI real ⏱ 40 minutos

1 · Introducción

urlshort sabe acortar URLs, pero no sabe si la URL que le das existe. Un acortador que acepta https://ejemplo.invalido y devuelve un código bonito no está haciendo su trabajo: está guardando basura. Antes de acortar hay que comprobar el destino, y eso significa hablar HTTP desde el programa.

reqwest es el cliente HTTP de referencia del ecosistema async de Rust. Construye sobre hyper y tokio, reutiliza conexiones, gestiona TLS, sigue redirecciones, descomprime respuestas y convierte JSON a tipos de Rust con serde. Su API es de alto nivel, pero no esconde lo importante: timeouts, códigos de estado y errores de red son tuyos.

¿Por qué existe esta lección?

Porque hacer una petición es fácil y hacerla bien no tanto. La diferencia entre un cliente de juguete y uno de producción está en cinco detalles: un Client reutilizado, timeouts explícitos, error_for_status(), reintentos solo donde tienen sentido y un límite de tamaño para no comerte un gigabyte de HTML. Todo eso cabe en cien líneas.

Errores típicos: crear un Client por petición; no poner timeout y colgarse para siempre; tratar un 404 como éxito porque el cuerpo vino en JSON; parsear HTML como JSON; bloquear el runtime con std::thread::sleep; depender de OpenSSL del sistema cuando bastaba rustls.

2 · Teoría

Qué hay debajo de una petición

Cuando llamas a client.get(url).send().await ocurren varias cosas, y cada una puede fallar de forma distinta:

  Url::parse ──► DNS ──► TCP ──► TLS (si https) ──► HTTP/1.1 o h2
                  │        │        │                    │
                  ▼        ▼        ▼                    ▼
              host mal   connect  certificado       estado + cabeceras
              formado    timeout   inválido          + cuerpo (chunks)

reqwest distingue esos fallos con métodos como is_timeout(), is_connect(), is_redirect() o is_decode(). Un 404 no es un error de reqwest: es una respuesta HTTP perfectamente válida. Confundir «fallo de red» con «el servidor dijo que no» es el primer error de diseño de un cliente.

Un cliente, muchas peticiones

Client no es una petición: es un pool de conexiones más configuración compartida (TLS, proxy, cookies, timeouts). Crear uno por petición tira el pool, repite el handshake TLS y llena la tabla de conexiones del sistema con sockets en TIME_WAIT.

FormaQué implicaCuándo usarla
reqwest::get(url)Crea un Client nuevo y lo tira al terminar.Un script de una sola petición. Nunca dentro de un bucle.
Client::builder()…build()Configura timeouts, TLS, proxy y redirects; reutiliza conexiones.Siempre en una aplicación real. Se clona barato (es un Arc por dentro).
Client::new()Valores por defecto, sin timeouts.Casi nunca: un cliente sin timeout es una bomba de relojería.

Los tres timeouts

Un timeout global se queda corto en un caso y largo en otro. reqwest permite separarlos:

MétodoQué mideValor razonable
connect_timeoutSolo la conexión TCP (y el saludo TLS): detecta hosts muertos o cortafuegos que descartan paquetes.2–5 s
read_timeoutCada lectura del cuerpo; se reinicia con cada trozo recibido. Detecta conexiones que se quedan mudas.5–15 s
timeoutLa petición completa, desde que empieza a conectar hasta el último byte del cuerpo.10–30 s

Sin ninguno de los tres, una petición puede quedarse esperando indefinidamente. El sistema operativo tarda minutos en rendirse, y tu CLI parece colgado.

JSON, cabeceras y estados

La feature json añade dos métodos: .json(&valor) para enviar (serializa con serde y pone Content-Type: application/json) y .json::<T>() para recibir (deserializa el cuerpo). La respuesta solo se convierte si el estado te vale: error_for_status() convierte cualquier 4xx/5xx en Err, conservando el código.

Las cabeceras se añaden con .header(header::ACCEPT, "application/json") o con .headers(map). Para autenticación, .bearer_auth(token) y .basic_auth(usuario, Some(clave)) son atajos correctos.

TLS: nativa o rustls

reqwest usa por defecto TLS nativo del sistema (native-tls: OpenSSL en Linux, Schannel en Windows). Funciona, pero ata el binario a las bibliotecas del sistema: compilar para Alpine o para musl suele terminar en un error de openssl-sys. La alternativa es rustls, TLS en Rust puro, sin dependencias del sistema:

[dependencies]
reqwest = { version = "0.12", default-features = false, features = [
    "json", "charset", "http2", "rustls-tls",
] }

Al desactivar las features por defecto pierdes también charset y http2: si las quieres, se añaden a mano. En 0.13 la API es la misma; cambian detalles de features y algunas dependencias internas.

Proxy, reintentos y tamaño

reqwest respeta HTTP_PROXY, HTTPS_PROXY y NO_PROXY del entorno. Para forzar uno: .proxy(reqwest::Proxy::all("http://proxy.local:3128")?); para ignorarlos, .no_proxy().

Los reintentos no son gratis: solo se reintentan operaciones idempotentes (GET, HEAD, PUT, DELETE) y solo ante fallos transitorios (timeout, conexión rechazada, 502/503/504). El patrón es backoff exponencial con un tope, y respetar Retry-After si viene. Un reintento sobre un POST puede duplicar un enlace.

reqwest no impone un tamaño máximo de respuesta. Si confías en el servidor, un .text() puede materializar cientos de megas en memoria. La solución es leer por trozos con resp.chunk() y contar bytes, o comprobar content_length() antes cuando existe.

3 · Ejemplo mínimo

Una petición GET con timeout y comprobación de estado. Cargo.toml:

[dependencies]
reqwest = { version = "0.12", features = ["json"] }
tokio = { version = "1", features = ["macros", "rt-multi-thread", "time"] }
use std::time::Duration;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = reqwest::Client::builder()
        .timeout(Duration::from_secs(10))
        .build()?;

    let body = client
        .get("https://httpbin.org/uuid")
        .send()
        .await?
        .error_for_status()?
        .text()
        .await?;

    println!("{body}");
    Ok(())
}
cargo run
# {"uuid":"0f1c2a9e-..."}

Línea a línea:

  • #[tokio::main] arranca el runtime. reqwest es async: sin runtime, .await no tiene dónde ejecutarse.
  • Client::builder() permite configurar antes de construir. .build() devuelve Result: puede fallar al inicializar TLS.
  • .send() devuelve la respuesta en cuanto llegan las cabeceras. El cuerpo se descarga después, con .text() o .json().
  • error_for_status() convierte 4xx/5xx en Err sin consumir el cuerpo si no hace falta.
  • ? propaga todo con Box<dyn Error>: cómodo en un binario, insuficiente en una librería, donde querrás un error propio.
  • main devuelve Result: si algo falla, Rust imprime el error y sale con código 1.

El cuerpo no llega con send()

send() resuelve cuando las cabeceras están listas. Un servidor puede responder 200 OK y quedarse a medias del cuerpo; el fallo aparecerá en .text() o .json(). Por eso el timeout total abarca el cuerpo, y por eso read_timeout existe.

4 · Ejemplo real

El módulo check de urlshort: valida un destino con HEAD antes de acortarlo, reintenta fallos transitorios con backoff, rechaza hosts privados (un acortador no debe convertirse en un escáner de la red interna) y limita el tamaño de lo que descarga.

// src/check.rs
use std::time::Duration;

use reqwest::{header, Client, StatusCode, Url};
use thiserror::Error;

#[derive(Debug, Error)]
pub enum CheckError {
    #[error("URL inválida: {0}")]
    InvalidUrl(String),
    #[error("no se pudo contactar con el destino: {0}")]
    Transport(#[from] reqwest::Error),
    #[error("el destino respondió {status}")]
    BadStatus { status: StatusCode },
    #[error("la respuesta supera {limit} bytes")]
    TooLarge { limit: usize },
    #[error("el host es local o privado: {0}")]
    PrivateHost(String),
    #[error("agotados los reintentos")]
    RetriesExhausted,
}

#[derive(Debug, Clone)]
pub struct Checker {
    client: Client,   // clonar es barato: comparte el pool
    retries: u32,
}

impl Checker {
    pub fn new() -> Result<Self, reqwest::Error> {
        let client = Client::builder()
            .user_agent(concat!("urlshort/", env!("CARGO_PKG_VERSION")))
            .connect_timeout(Duration::from_secs(3))
            .read_timeout(Duration::from_secs(5))
            .timeout(Duration::from_secs(10))
            .redirect(reqwest::redirect::Policy::limited(5))
            .build()?;

        Ok(Self { client, retries: 3 })
    }

    /// Devuelve la URL ya validada o un error que explica qué pasó.
    pub async fn validate(&self, raw: &str) -> Result<Url, CheckError> {
        let url = Url::parse(raw)
            .map_err(|err| CheckError::InvalidUrl(err.to_string()))?;

        if !matches!(url.scheme(), "http" | "https") {
            return Err(CheckError::InvalidUrl(format!(
                "esquema no admitido: {}",
                url.scheme()
            )));
        }

        let host = url
            .host_str()
            .ok_or_else(|| CheckError::InvalidUrl("falta el host".to_string()))?;

        if is_private(host) {
            return Err(CheckError::PrivateHost(host.to_string()));
        }

        match self.probe(&url).await? {
            status if status.is_success() || status.is_redirection() => Ok(url),
            status => Err(CheckError::BadStatus { status }),
        }
    }

    // HEAD primero: no descarga cuerpo. Reintenta solo 5xx y fallos de red.
    async fn probe(&self, url: &Url) -> Result<StatusCode, CheckError> {
        let mut delay = Duration::from_millis(250);
        let mut last = CheckError::RetriesExhausted;

        for attempt in 1..=self.retries {
            match self.client.head(url.clone()).send().await {
                Ok(resp) => {
                    let status = resp.status();
                    if status.is_server_error() {
                        last = CheckError::BadStatus { status };
                    } else if status == StatusCode::METHOD_NOT_ALLOWED {
                        // Algunos servidores no implementan HEAD: pedimos un byte.
                        let resp = self
                            .client
                            .get(url.clone())
                            .header(header::RANGE, "bytes=0-0")
                            .send()
                            .await?;
                        return Ok(resp.status());
                    } else {
                        return Ok(status);
                    }
                }
                Err(err) if err.is_timeout() || err.is_connect() => {
                    last = CheckError::Transport(err);
                }
                Err(err) => return Err(CheckError::Transport(err)),
            }

            if attempt < self.retries {
                tokio::time::sleep(delay).await;
                delay = delay.saturating_mul(2);   // 250 ms, 500 ms, 1 s
            }
        }

        Err(last)
    }
}

fn is_private(host: &str) -> bool {
    match host.parse::<std::net::IpAddr>() {
        Ok(std::net::IpAddr::V4(ip)) => ip.is_loopback() || ip.is_private() || ip.is_link_local(),
        Ok(std::net::IpAddr::V6(ip)) => ip.is_loopback(),
        Err(_) => host == "localhost" || host.ends_with(".local") || host.ends_with(".internal"),
    }
}

Y el uso desde el CLI: validar, y solo entonces acortar.

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let checker = urlshort::check::Checker::new()?;
    let url = checker.validate("https://www.rust-lang.org/").await?;
    println!("ok: {url}");
    Ok(())
}

Para hablar con el servidor de urlshort (lección siguiente), el mismo cliente sirve:

#[derive(Debug, serde::Deserialize)]
pub struct LinkResponse {
    pub code: String,
    pub short_url: String,
}

pub async fn create_link(
    client: &Client,
    base: &str,
    url: &str,
) -> Result<LinkResponse, CheckError> {
    let link = client
        .post(format!("{base}/links"))
        .json(&serde_json::json!({ "url": url }))
        .send()
        .await?
        .error_for_status()?
        .json::<LinkResponse>()
        .await?;

    Ok(link)
}

Y si en algún momento descargas contenido de terceros, acota el tamaño:

pub async fn fetch_capped(
    client: &Client,
    url: &str,
    max: usize,
) -> Result<Vec<u8>, CheckError> {
    let mut resp = client.get(url).send().await?.error_for_status()?;

    if let Some(len) = resp.content_length() {
        if len > max as u64 {
            return Err(CheckError::TooLarge { limit: max });
        }
    }

    let mut body = Vec::with_capacity(8 * 1024);
    while let Some(chunk) = resp.chunk().await? {
        if body.len() + chunk.len() > max {
            return Err(CheckError::TooLarge { limit: max });
        }
        body.extend_from_slice(&chunk);
    }

    Ok(body)
}

Validar el host no basta contra SSRF

is_private mira el nombre y la IP literal, pero un dominio público puede resolver a 127.0.0.1 (DNS rebinding). En producción, resuelve el nombre, fija la IP en la conexión y vuelve a comprobarla; o valida el destino con una lista de permitidos. Aquí el objetivo es didáctico, no un cortafuegos.

6 · Errores habituales

1. Un Client por petición

Mal:

for url in urls {
    let body = reqwest::get(url).await?.text().await?;   // cliente nuevo cada vez
    println!("{body}");
}

Por qué está mal: cada iteración crea un pool, negocia TLS y abre una conexión nueva. Con cien URLs, cien handshakes y cien sockets esperando en TIME_WAIT.

Bien: crear el cliente una vez y clonarlo (o prestarlo).

let client = reqwest::Client::builder()
    .timeout(Duration::from_secs(10))
    .build()?;

for url in urls {
    let body = client.get(url).send().await?.error_for_status()?.text().await?;
    println!("{body}");
}

2. No comprobar el estado

Mal:

let link: LinkResponse = client.get(url).send().await?.json().await?;
Error: error decoding response body
  caused by: expected value at line 1 column 1

Por qué está mal: un 404 con una página HTML llega como respuesta válida; el fallo aparece al deserializar y el mensaje no dice que era un 404. Bien: .error_for_status()? antes de .json().

3. Olvidar la feature json

Mal: declarar reqwest = "0.12" sin features y llamar a .json().

error[E0599]: no method named `json` found for struct `reqwest::RequestBuilder`
in the current scope
  |
  = help: items from traits can only be used if the trait is in scope
  = note: the following trait is implemented but not in scope; perhaps add a `use` for it

Por qué está mal: los métodos de JSON viven detrás de la feature json. Bien: features = ["json"] y serde_json en las dependencias.

4. Bloquear el runtime

Mal:

async fn esperar() {
    std::thread::sleep(Duration::from_secs(1));  // bloquea el worker de tokio
}

Por qué está mal: sleep bloquea el hilo del runtime, que está compartido por todas las tareas. Con pocos workers, todo el servidor se detiene. Bien: tokio::time::sleep(delay).await.

El mismo problema aparece al retener un std::sync::MutexGuard durante un .await:

error[E0277]: future cannot be sent between threads safely
   = help: within `impl Future<Output = ...>`, the trait `Send` is not implemented
           for `std::sync::MutexGuard<'_, ...>`

Bien: usa tokio::sync::Mutex o suelta el guard antes de esperar.

5. Aceptar cualquier cuerpo

Mal: .text() sin límite sobre una URL que introduce el usuario. Una respuesta de 2 GB se convierte en un String de 2 GB y el proceso muere por OOM. Bien: fetch_capped con un máximo explícito; si el contenido no es necesario (solo validar), un HEAD ni siquiera lo descarga.

6. Reintentar sin criterio

Mal: un bucle de tres intentos alrededor de un POST /links ante cualquier error, sin espera. Si el primer POST llegó y la respuesta se perdió, el segundo crea un duplicado. Bien: reintentar solo GET/HEAD/PUT/DELETE, solo ante timeout, conexión o 5xx, con backoff y con una idempotency key si el servidor la soporta.

7 · Ejercicio guiado

Objetivo: un subcomando check que lee URLs de un fichero, las comprueba en paralelo y devuelve un código de salida distinto si alguna falla.

  1. Añade las dependencias. 
    cargo add reqwest --features json,rustls-tls --no-default-features
cargo add tokio --features macros,rt-multi-thread,time
cargo add serde --features derive
cargo add serde_json thiserror
  2. Crea src/check.rs con el Checker del ejemplo real y expórtalo desde lib.rs con pub mod check;.
  3. Prepara un fichero de prueba urls.txt: 
    https://www.rust-lang.org/
https://httpbin.org/status/404
http://10.0.0.5/admin
no-es-una-url
  4. Escribe el binario que las procesa en paralelo. 
    use tokio::task::JoinSet;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let path = std::env::args().nth(1).ok_or("uso: check <fichero>")?;
    let texto = std::fs::read_to_string(path)?;
    let checker = urlshort::check::Checker::new()?;

    let mut tareas = JoinSet::new();
    for linea in texto.lines().map(str::trim).filter(|l| !l.is_empty()) {
        let checker = checker.clone();
        let url = linea.to_string();
        tareas.spawn(async move {
            let resultado = checker.validate(&url).await;
            (url, resultado.map(|u| u.to_string()).map_err(|e| e.to_string()))
        });
    }

    let mut fallos = 0;
    while let Some(tarea) = tareas.join_next().await {
        let (url, resultado) = tarea?;
        match resultado {
            Ok(destino) => println!("ok    {url} -> {destino}"),
            Err(err) => {
                fallos += 1;
                eprintln!("fallo {url}: {err}");
            }
        }
    }

    std::process::exit(if fallos == 0 { 0 } else { 1 });
}

    Salida esperada: una línea ok para rust-lang, y fallos para el 404, el host privado y la URL mal formada. Código de salida 1.

  5. Comprueba el comportamiento sin red. Arranca un servidor local que acepte y no responda: nc -l 9999 (o ncat -l 9999). Añade http://127.0.0.1:9999 al fichero, ejecuta y mide cuánto tarda: debe fallar por PrivateHost antes de conectar. Cambia la comprobación de host privado por una variable de entorno para probar el timeout y verás el read_timeout en acción.
  6. Limita la concurrencia. JoinSet lanza todas las tareas a la vez. Con un fichero de 10 000 URLs eso son 10 000 conexiones. Añade un tokio::sync::Semaphore con 16 permisos y adquiérelo dentro de cada tarea antes de llamar a validate.
  7. Pasa clippy. 
    cargo fmt
cargo clippy --all-targets -- -D warnings

    clippy te avisará de manual_map o de closures redundantes; acéptalo, el código queda más corto.

Criterio de éxito

Puedes explicar, para cada fallo del fichero, qué capa falló (parseo, DNS/TCP, TLS, estado HTTP o deserialización) y qué timeout lo habría cortado. Si el programa se cuelga en algún caso, todavía te falta un timeout.

8 · Reto

🎯 Caché condicional y limitador de ritmo

urlshort comprueba muchas URLs del mismo dominio y no quiere abusar del servidor. Implementa un CachedChecker que:

  • Guarde la última respuesta por URL con su ETag y Last-Modified, y use If-None-Match/If-Modified-Since en la siguiente petición; un 304 Not Modified cuenta como válido y no gasta cuota.
  • Respete Cache-Control: max-age y Retry-After.
  • Limite a N peticiones por segundo y por host con un token bucket, compartido entre tareas.
  • No reintente un 429 hasta que pase el tiempo indicado.

Pista: guarda las entradas en un tokio::sync::Mutex<HashMap<String, Entrada>> o en un DashMap; el limitador puede ser un Semaphore que se rellena periódicamente con una tarea de fondo, o el crate governor. Para las cabeceras, resp.headers().get(header::ETAG).

9 · Resumen

  • Client es un pool de conexiones y configuración: uno por proceso, clonado cuando haga falta.
  • Configura connect_timeout, read_timeout y timeout. Sin ellos, la petición puede no terminar nunca.
  • send() devuelve al recibir cabeceras; el cuerpo se lee con .text(), .json() o .chunk().
  • error_for_status() separa «el servidor dijo que no» de «la red falló»; sin él, un 404 se cuela como éxito.
  • La feature json aporta .json(&valor) y .json::<T>(), construidos sobre serde.
  • Reintenta solo lo idempotente, solo ante fallos transitorios, con backoff y respetando Retry-After.
  • rustls evita depender de OpenSSL; el proxy del sistema se respeta por defecto.
  • Acota el tamaño de las respuestas de terceros: content_length() y chunk() con contador.

10 · Preguntas frecuentes

¿Y si mi programa no es async?

reqwest tiene un módulo blocking con la misma API sin .await: reqwest::blocking::Client. Por dentro arranca un runtime propio. Es cómodo en scripts, pero no lo uses dentro de un runtime async (provoca un panic por anidar runtimes); ahí ya tienes la versión async.

¿rustls o TLS nativo?

Si distribuyes un binario estático, compilas para Alpine/musl o quieres evitar OpenSSL, usa rustls-tls con default-features = false. Si necesitas certificados del almacén del sistema con reglas corporativas exóticas, el TLS nativo suele integrarse mejor. En ambos casos, rustls no valida por defecto certificados de una CA interna: hay que añadirla explícitamente.

¿Cómo cancelo una petición que tarda demasiado?

Con el timeout del cliente, que es lo normal, o envolviendo la llamada en tokio::time::timeout(Duration::from_secs(3), peticion). Al soltar el futuro, la conexión se descarta. Para cancelar varias a la vez, tokio::select! con una señal de apagado.

¿Cómo subo un fichero o un formulario?

Con la feature multipart y reqwest::multipart::Form: Form::new().text("campo", "valor").file("fichero", ruta).await?. Para cuerpos binarios grandes, .body(reqwest::Body::from_stream(stream)) evita cargarlo entero en memoria.

¿Por qué un 200 con JSON me da error de deserialización?

Porque el esquema no coincide: falta un campo obligatorio, un número viene como cadena o el servidor devolvió HTML con un login. El error de serde incluye línea y columna. Marca los campos opcionales con Option<T> y #[serde(default)], y registra el cuerpo (recortado) cuando falles, para ver qué llegó de verdad.
