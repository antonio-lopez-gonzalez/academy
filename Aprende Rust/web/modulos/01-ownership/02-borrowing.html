Borrowing: &T, &mut T y el borrow checker

Módulo 1 · Ownership y borrowing ⏱ 45 minutos

1 · Introducción

Mover la propiedad funciona, pero es incómodo: si cada función que lee un dato se lo queda, el programa se convierte en un ida y vuelta de devoluciones. Los préstamos (borrowing) resuelven eso: dejas que otro código use tu valor sin transferir la propiedad, con la garantía de que no lo va a destruir ni a modificar si no debe.

Un préstamo es una referencia: &T para leer y &mut T para leer y escribir. La regla que las gobierna es la que hace útil a Rust: muchos lectores o un solo escritor, nunca ambos a la vez. El compilador analiza cada préstamo, calcula hasta dónde se usa y rechaza cualquier solapamiento peligroso. Ese análisis es el borrow checker.

¿Por qué existe esta lección?

Porque casi todos los errores que quedan después de entender ownership son de préstamos: E0502, E0499, E0515. Y casi todos se arreglan igual: acortando la vida del préstamo o separando lo que se lee de lo que se escribe. Aprender a mirar tu código como una línea temporal de préstamos es el cambio mental más rentable del curso.

Al terminar sabrás leer un conflicto de préstamos como un intervalo de tiempo, usar &mut sin miedo, entender por qué &mut no se copia y reconocer los tres errores clásicos sin buscarlos.

Errores típicos al empezar:

  • Mantener una referencia a un elemento mientras se modifica la colección que lo contiene.
  • Pedir dos &mut del mismo valor «porque son para cosas distintas».
  • Olvidar mut en la variable y recibir un E0596, o devolver una referencia a algo creado dentro de la función.

La regla de oro

En cualquier instante, un valor puede tener muchos préstamos compartidos (&T) o exactamente un préstamo mutable (&mut T), pero nunca los dos tipos a la vez. Y un préstamo nunca puede vivir más que su dueño.

Esto se abrevia como aliasing XOR mutability: o hay alias (varias vistas del mismo dato) o hay mutación, pero no ambas. No es una limitación arbitraria; es la condición que hace imposible una categoría entera de bugs.

Por qué la regla existe: carreras de datos

Una carrera de datos ocurre cuando dos hilos acceden al mismo dato, al menos uno escribe y no hay sincronización. El resultado es un valor corrupto o un comportamiento que depende del azar del planificador. En C++ o Java el compilador no puede impedirlo; en Rust la regla de préstamos lo impide incluso dentro de un solo hilo.

   SIN LA REGLA                        CON LA REGLA
   ─────────────                       ─────────────
   hilo A: escribe  ─┐                 &mut dato   ← solo uno, y nada más
   hilo B: escribe  ─┼─► valor roto
   hilo C: lee      ─┘                 &dato &dato &dato ← muchos, todos lectura

El mismo razonamiento aplica a estructuras de datos: si tienes una referencia a un elemento de un Vec y el Vec reasigna su buffer al crecer, tu referencia apuntaría a memoria liberada. Con la regla, mientras exista esa referencia el Vec está inmóvil.

La vida de un préstamo: NLL

Desde Rust 1.31, el compilador usa NLL (non-lexical lifetimes): un préstamo no vive hasta el cierre de la llave, sino hasta su último uso. Es la diferencia entre estos dos programas:

// COMPILA: el préstamo inmutable termina en el println
fn main() {
    let mut numbers = vec![1, 2, 3];
    let first = &numbers[0];
    println!("{first}");            // último uso del préstamo
    numbers.push(4);                  // ya nadie está mirando: permitido
    println!("{numbers:?}");
}

// NO COMPILA: el préstamo sigue vivo después del push
fn broken() {
    let mut numbers = vec![1, 2, 3];
    let first = &numbers[0];
    numbers.push(4);                  // E0502: préstamo inmutable activo
    println!("{first}");              // ...y se usa aquí
}

El texto es casi idéntico; el orden de uso decide. Por eso el diagnóstico de E0502 incluye la línea «immutable borrow later used here»: el compilador te enseña el intervalo exacto.

Préstamos en funciones y reborrowing

La firma es el contrato: si solo lee, &T; si modifica, &mut T; si se queda el valor, T.

fn length(url: &str) -> usize { url.len() }
fn mark(url: &mut String) { url.push_str("#visto"); }

fn main() {
    let mut url = String::from("https://sho.rt/a");
    println!("{}", length(&url));   // compartido
    mark(&mut url);                 // exclusivo
    println!("{url}");
}

Ese &mut url es un reborrow implícito: no mueve el String, crea un préstamo temporal que dura lo que la llamada. Puedes repetirlo tantas veces como quieras, de una en una. Lo que no puedes es copiar un &mut: es exclusivo, y duplicar el permiso rompería la regla.

fn increment(n: &mut u32) { *n += 1; }

fn main() {
    let mut hits = 0;
    let r = &mut hits;
    increment(r);        // reborrow implícito: increment(&mut *r)
    increment(r);        // `r` sigue siendo válido
    println!("{hits}");    // 2
}

Campos distintos son préstamos distintos

El borrow checker distingue lugares: puedes prestar un campo en inmutable y otro en mutable a la vez, porque &link.code y &mut link.hits no se solapan. Lo que no puede demostrar es lo mismo a través de una función: si llamas a fn code(&self) -> &str, el préstamo devuelto está atado a self entero. Ese es el puente hacia las vidas.

Devolver referencias

use std::collections::HashMap;

struct Link { url: String, hits: u32 }

// El resultado vive tanto como el mapa prestado (elisión de vidas)
fn most_viewed_code(links: &HashMap<String, Link>) -> Option<&str> {
    links.iter().max_by_key(|(_, link)| link.hits).map(|(code, _)| code.as_str())
}

El Option<&str> no es una copia: apunta dentro del HashMap, y funciona porque el mapa sigue vivo en quien llama. Si la función crease el mapa dentro y devolviese una referencia a una clave, el compilador lo rechazaría con E0515.

3 · Ejemplo mínimo

Un programa corto con las dos clases de préstamo y la prueba de que los compartidos conviven:

fn length(text: &str) -> usize { text.len() }
fn bump(hits: &mut u32) {
    *hits += 1;                        // el asterisco desreferencia
}
fn main() {
    let url = String::from("https://sho.rt/k7m2qd");
    let n = length(&url);            // &String -> &str por deref coercion
    println!("{url} tiene {n} bytes"); // el dueño sigue siendo main

    let mut hits = 0;
    bump(&mut hits);
    bump(&mut hits);
    println!("{hits} hits");

    let a = &url;                      // dos compartidos a la vez: legal
    let b = &url;
    println!("{} {}", a.len(), b.len());
}
cargo run --quiet
https://sho.rt/k7m2qd tiene 23 bytes
2 hits
23 23

Línea a línea: length(&url) crea un préstamo compartido temporal que termina al volver; &String se convierte en &str por deref coercion; &mut hits presta la variable en exclusiva y *hits es el valor; y las dos últimas líneas prueban lo que &mut prohíbe: dos lectores simultáneos son legales, dos escritores no.

Si guardas un préstamo y pides otro mientras el primero sigue vivo (let r = &mut hits; bump(&mut hits); bump(r);), el error es E0499: dos permisos exclusivos sobre el mismo valor. La versión correcta usa r en las dos llamadas, que es justo lo que hace el reborrow.

4 · Ejemplo real

El registro de urlshort guarda los códigos en un HashMap. Casi todas las operaciones se hacen prestando: el CLI consulta, incrementa y lista sin mover el registro ni clonar las entradas.

use std::collections::HashMap;

#[derive(Debug)]
pub struct Link { pub url: String, pub hits: u32 }

#[derive(Default)]
pub struct Registry { links: HashMap<String, Link> }

impl Registry {
    pub fn insert(&mut self, code: &str, url: &str) {
        // El mapa necesita su propia clave: el &str no vive lo suficiente.
        self.links.insert(code.to_string(), Link { url: url.to_string(), hits: 0 });
    }

    pub fn hit(&mut self, code: &str) -> Option<u32> {
        let link = self.links.get_mut(code)?;   // un solo &mut, y sale
        link.hits += 1;
        Some(link.hits)
    }

    pub fn total_hits(&self) -> u32 {
        self.links.values().map(|link| link.hits).sum()
    }

    // &self: el resultado son préstamos a las claves, no copias
    pub fn active_codes(&self, min_hits: u32) -> Vec<&str> {
        self.links
            .iter()
            .filter(|(_, link)| link.hits >= min_hits)
            .map(|(code, _)| code.as_str())
            .collect()
    }
}

fn main() {
    let mut registry = Registry::default();
    registry.insert("k7m2qd", "https://www.rust-lang.org/learn");
    registry.insert("abc123", "https://doc.rust-lang.org/book/");

    for _ in 0..3 { let _ = registry.hit("k7m2qd"); }
    let _ = registry.hit("abc123");

    println!("total: {}", registry.total_hits());
    println!("activos: {:?}", registry.active_codes(2));
    for link in registry.links.values_mut() { link.hits = 0; }
    println!("tras reset: {}", registry.total_hits());
}
cargo run --quiet
total: 4
activos: ["k7m2qd"]
tras reset: 0

hit usa get_mut y devuelve Option<u32>: el préstamo exclusivo dura solo lo que la función y quien llama decide qué hacer si el código no existe. active_codes devuelve vistas a las claves, válidas mientras el mapa viva. values_mut permite modificar cada valor sin tocar la estructura; y el code.to_string() al insertar es una copia legítima, en el momento de crear la entrada.

Analogía: la pizarra del equipo

&T es dejar que varios compañeros lean la pizarra: pueden estar todos a la vez y nadie borra nada. &mut T es darle a uno el borrador: mientras escribe, los demás esperan fuera. Nadie prohíbe leer ni escribir; lo que se prohíbe es leer mientras otro borra. Y el dueño del aula decide cuándo se apaga la luz.

Si el error es de préstamos, dibuja la línea temporal

Escribe las líneas del conflicto en una columna y marca con [ y ] dónde empieza y acaba cada préstamo. El 90 % de las veces verás que uno de los dos se puede terminar antes. Si no se puede, el problema es de diseño: estás leyendo y escribiendo el mismo dato en el mismo instante, y ninguna cantidad de clone() lo va a hacer correcto.

6 · Errores habituales

1. Modificar una colección mientras hay una referencia a un elemento

fn main() {
    let mut numbers = vec![1, 2, 3];
    let first = &numbers[0];
    numbers.push(4);
    println!("{first}");
}
error[E0502]: cannot borrow `numbers` as mutable because it is also
              borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let first = &numbers[0];
  |                    ------- immutable borrow occurs here
4 |     numbers.push(4);
  |     ^^^^^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("{first}");
  |               ------- immutable borrow later used here

push puede reasignar el buffer del Vec; si eso pasa, first apuntaría a memoria liberada. El compilador no puede saber si habrá reasignación, así que prohíbe el escenario entero. Arreglo: terminar el préstamo antes (mover el println! antes del push) o copiar el valor si es pequeño, como let first = numbers[0]; con un i32.

2. Dos préstamos mutables del mismo valor

fn main() {
    let mut data = vec![1, 2, 3];
    let a = &mut data;
    let b = &mut data;
    a.push(4);
    b.push(5);
}
error[E0499]: cannot borrow `data` as mutable more than once at a time
 --> src/main.rs:4:13
  |
3 |     let a = &mut data;
  |             ---------- first mutable borrow occurs here
4 |     let b = &mut data;
  |             ^^^^^^^^^^ second mutable borrow occurs here
5 |     a.push(4);
  |     - first borrow later used here

Dos escritores simultáneos son la carrera de datos que la regla impide; además, si el primero reasigna el buffer, el segundo apunta a memoria vieja. Arreglo: usarlos en secuencia, o partir el contenedor con split_at_mut, que devuelve dos &mut a zonas disjuntas (let (izq, der) = data.split_at_mut(2);).

3. Devolver una referencia a un valor local

fn current_code() -> &str {
    let code = String::from("abc123");
    code.as_str()
}
error[E0515]: cannot return value referencing local variable `code`
 --> src/main.rs:3:5
  |
2 |     let code = String::from("abc123");
  |         ---- `code` is borrowed here
3 |     code.as_str()
  |     ^^^^^^^^^^^^^ returns a value referencing data owned by
  |                   the current function

Al volver, code se libera y la referencia apuntaría a memoria muerta: el use-after-free que Rust no permite ni compilar. Arreglo: devolver el String (transfiere la propiedad) o recibir el dato prestado y devolver un préstamo con su misma vida.

fn current_code() -> String { String::from("abc123") }

fn prefix(url: &str) -> &str {
    url.split('/').next().unwrap_or(url)   // vive lo que vive `url`
}

7 · Ejercicio guiado

Objetivo: reproducir E0502 y E0499, arreglarlos acortando el préstamo y comprobar que dos zonas mutables disjuntas sí se permiten.

  1. Crea el proyecto. 
    cargo new borrowing-lab --bin
cd borrowing-lab
  2. Reproduce E0502. Pega esto y ejecuta cargo build: 
    fn main() {
    let mut hits = vec![0, 0, 0];
    let first = &hits[0];
    hits.push(0);
    println!("{first}");
}

    Lee el diagnóstico entero y localiza las tres etiquetas: dónde se presta, dónde se pide el mutable y dónde se usa el préstamo por última vez.

  3. Arréglalo sin clonar. Mueve el println! antes del push y comprueba que ahora compila: el préstamo terminó en su último uso (NLL). 
    fn main() {
    let mut hits = vec![0, 0, 0];
    let first = &hits[0];
    println!("{first}");
    hits.push(0);
    println!("{hits:?}");
}
  4. Separa dos zonas mutables. 
    fn main() {
    let mut data = vec![1, 2, 3, 4];
    let (left, right) = data.split_at_mut(2);
    left[1] = 20;
    right[0] = 30;
    println!("{data:?}");
}

    Salida esperada: [1, 20, 30, 4]. Cambia split_at_mut por dos &mut data y verás volver el E0499.

  5. Itera modificando y pasa clippy. 
    use std::collections::HashMap;

fn bump_all(hits: &mut HashMap<String, u32>) {
    for value in hits.values_mut() { *value += 1; }
}

fn main() {
    let mut hits = HashMap::new();
    hits.insert(String::from("abc"), 0);
    hits.insert(String::from("def"), 2);
    bump_all(&mut hits);
    println!("{hits:?}");
}

    Salida esperada: {"abc": 1, "def": 3} (el orden puede variar). Los dos préstamos de campos distintos del paso anterior y este values_mut son la misma idea: el permiso exclusivo ya está tomado, así que no hace falta copiar. Después:

    cargo clippy -- -D warnings

Criterio de éxito

Sabes leer un E0502 como un intervalo de tiempo y proponer dos arreglos: acortar el préstamo o separar los datos. Y entiendes por qué split_at_mut es seguro aunque devuelva dos &mut: apuntan a zonas que no se solapan.

8 · Reto

🎯 El informe de códigos activos

El registro de urlshort es un HashMap<String, Link>. Escribe una función que reciba el mapa en mutable y una lista de códigos, y haga dos cosas en una sola pasada: sumar un hit a cada código que exista y devolver los códigos cuyo contador haya superado un umbral. Sin clone(), sin recolectar claves en un Vec<String> y sin dos préstamos mutables vivos a la vez.

Firma sugerida: fn bump_and_report(links: &mut HashMap<String, Link>, wanted: &[&str], threshold: u32) -> Vec<&str>. Piensa si esa firma es siquiera posible tal cual: el Vec<&str> que devuelves presta las claves del mapa, y el mapa lo tienes en mutable. Ahí está el reto.

Pista: si necesitas leer la clave mientras escribes el valor, iter_mut te da las dos cosas a la vez sin conflicto, porque el iterador ya tiene el préstamo exclusivo del mapa. Para saber si un código está en wanted, un HashSet<&str> construido antes del bucle evita búsquedas lineales. Y si el contrato de devolver &str te obliga a elegir entre devolver préstamos o mutar, decide qué importa más: quizá el informe se devuelva como Vec<String> solo con los códigos que cruzan el umbral, que son pocos.

9 · Resumen

  • &T presta para leer y se puede compartir; &mut T presta para escribir y es exclusivo.
  • La regla: muchos &T o un solo &mut T, nunca mezclados sobre el mismo valor; existe para impedir carreras de datos y referencias a memoria reasignada.
  • Con NLL un préstamo acaba en su último uso: reordenar suele resolver el conflicto.
  • &mut T no es Copy: se mueve o se reborrow con &mut *r.
  • Campos distintos y zonas disjuntas (split_at_mut) admiten préstamos simultáneos.
  • Devolver una referencia a un local es E0515; devuelve el valor o ata el préstamo al parámetro.

10 · Preguntas frecuentes

¿Por qué no puedo tener dos &mut si yo sé que no se solapan?

Porque el compilador razona sobre lo que puede demostrar, no sobre lo que tú sabes. Hay casos donde sí lo demuestra: campos distintos, split_at_mut, iteradores mutables. Si el tuyo no encaja, rediseña (índices en lugar de referencias, separar estructuras) o usa interior mutability (RefCell, Mutex), que mueve la comprobación a ejecución. Lo que nunca es una solución es unsafe para callar al compilador sin un motivo medido.

¿Un préstamo inmutable impide modificar el valor aunque no lo use?

No, desde NLL. El préstamo existe desde que se crea hasta su último uso. Si declaras let r = &v[0]; y no vuelves a tocar r, el préstamo muere ahí y puedes mutar v después. El malentendido clásico viene del Rust anterior a 1.31, donde duraba todo el bloque.

¿Qué diferencia hay entre &mut y RefCell?

&mut T comprueba la exclusividad en compilación y no cuesta nada en ejecución. RefCell<T> comprueba lo mismo en ejecución: si pides dos borrow_mut() a la vez, hace panic. Se usa cuando la estructura del código impide demostrar la exclusividad estáticamente (grafos, observers). El precio es un chequeo y un posible pánico en ejecución.

¿Devolver &str de una función siempre necesita lifetimes explícitos?

Solo si hay varias referencias en la entrada y el compilador no puede deducir de cuál viene la salida. Con un único parámetro de referencia, o con &self, la elisión resuelve el 95 % de los casos. Cuando no, se anota: fn f<'a>(x: &'a str) -> &'a str, tema de la siguiente lección.

¿Iterar con &mut y consultar otra parte del mapa es posible?

No sobre el mismo mapa: el iterador mutable ya tiene el préstamo exclusivo. Las salidas limpias son hacer la consulta antes del bucle (guardando lo necesario en una variable local), recorrer una estructura auxiliar o procesar por claves con get_mut de una en una. Si necesitas dos accesos simultáneos, el modelo de datos pide dividirse en dos.
