Lifetimes: por qué el compilador pide anotaciones

Módulo 1 · Ownership y borrowing ⏱ 40 minutos

1 · Introducción

Un lifetime (vida) es el intervalo de código durante el cual una referencia es válida. No es una duración en segundos ni un contador en ejecución: es una región del programa que el compilador calcula. Cada referencia tiene una, y el borrow checker comprueba que ninguna sobreviva al dato al que apunta.

Casi siempre ese cálculo es invisible. Pero cuando hay varias referencias en la entrada y una referencia en la salida, el compilador necesita saber de cuál viene la salida. Ahí aparecen las anotaciones <'a>, y ahí empieza la confusión: parece que estás «declarando» cuánto vive algo, cuando en realidad estás describiendo una relación que ya existe.

¿Por qué existe esta lección?

Porque la mayoría aprende lifetimes al revés: cree que son un impuesto y llena el código de 'static para que compile. Entender que son descripciones, no instrucciones —y que casi nunca hay que escribirlas en código de aplicación— ahorra semanas y evita el anti-patrón más caro.

Errores típicos al empezar:

  • Anotar 'static en todo para que el compilador calle.
  • Creer que <'a> hace que un valor viva más.
  • Poner una vida en una función que no devuelve referencias (no hace falta).
  • Guardar un &str en un struct sin parametrizarlo y toparse con E0106.

2 · Teoría

Qué es exactamente una vida

El compilador asigna a cada préstamo una región: desde que se crea hasta su último uso. Una vida no cambia el código generado; solo participa en el análisis. Dos programas con las mismas anotaciones producen el mismo binario que sin ellas.

   tiempo ────────────────────────────────────────────────►

   let a = String::from("larga");   [═══════════════════════════]
   let b = "corta";                     [═════════════]
   let r = longest(&a, b);                [════════]
   println!("{r}");                            │
                                               ▼
                                    r no puede usarse después
                                    de que muera aquello que presta

La anotación 'a en fn longest<'a>(x: &'a str, y: &'a str) -> &'a str significa: «la referencia que devuelvo es válida, como mucho, durante la intersección de las vidas de x e y». Es la vida más corta, no la más larga. Por eso el compilador puede garantizar que el resultado nunca apunta a memoria muerta. La vida existe siempre; la anotación solo cuando hay que nombrarla en una firma.

Las tres reglas de elisión

Rust no te obliga a escribir vidas siempre. Aplica estas reglas en orden; solo si al final queda una salida sin vida asignada, te pide que la anotes:

#ReglaEjemplo
1Cada parámetro de referencia recibe su propia vidafn f(x: &str, y: &str) → dos vidas distintas
2Si hay una sola vida de entrada, se asigna a todas las salidasfn f(s: &str) -> &str
3Si hay &self o &mut self, su vida va a todas las salidasfn code(&self) -> &str

Con dos referencias de entrada y una de salida, las reglas 2 y 3 no aplican: el compilador no puede adivinar de cuál viene el resultado. Ahí es donde E0106: missing lifetime specifier te pide la anotación que falta.

La firma que todo el mundo recuerda

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

<'a> declara un parámetro de vida que solo existe en esta firma. x: &'a str e y: &'a str dicen que ambas entradas deben ser válidas al menos durante 'a: no tienen que vivir lo mismo, 'a será la menor. Y -> &'a str promete que la salida no vivirá más que ese solape. Si usas dos vidas ('a e 'b) y devuelves &'a str, afirmas que el resultado solo viene de x; el compilador rechazará la rama que devuelva y salvo que 'b: 'a.

Structs con referencias

Un struct que guarda una referencia tiene que declarar la vida: el compilador necesita saber que no puede sobrevivir al dato prestado.

struct Excerpt<'a> { part: &'a str }
impl<'a> Excerpt<'a> {
    fn new(text: &'a str, up_to: usize) -> Self { Self { part: &text[..up_to] } }
    // Sin 'a la salida quedaría atada a &self; con 'a, sobrevive al struct.
    fn text(&self) -> &'a str { self.part }
}

fn main() {
    let url = String::from("https://sho.rt/k7m2qd");
    let e = Excerpt::new(&url, 8);
    println!("{} / {url}", e.text());
}

La diferencia entre fn text(&self) -> &str y fn text(&self) -> &'a str es real: la primera ata el resultado al préstamo del struct; la segunda lo ata al texto original y sobrevive al struct.

'static: la vida más larga, y casi nunca la respuesta

'static significa «válida durante todo el programa». Hay tres casos legítimos: los literales ("hola" es &'static str porque vive en el binario), los items static y los datos filtrados a propósito con Box::leak para configuración que dura lo que el proceso. Y un matiz que confunde: en un bound genérico, T: 'static no significa que el valor viva para siempre, sino que no contiene préstamos más cortos; un String o un Vec<String> cumplen T: 'static aunque se destruyan en la línea siguiente.

El anti-patrón del 'static fácil

Cuando el compilador se queja de una vida, poner 'static suele empeorar el problema: obliga a que el dato prestado viva para siempre, lo que excluye cualquier String local. La respuesta correcta casi siempre es parametrizar el struct (Config<'a>) o guardar el dato en propiedad (String).

Vidas en traits e impl

trait Summary<'a> { fn excerpt(&self) -> &'a str; }
struct Link<'a> { code: &'a str }
impl<'a> Summary<'a> for Link<'a> {
    fn excerpt(&self) -> &'a str { self.code }
}

// T: 'a significa: todo lo que contenga T vive al menos 'a
fn print_summary<'a, T: Summary<'a>>(item: &T) { println!("{}", item.excerpt()); }

fn main() {
    let code = String::from("k7m2qd");
    print_summary(&Link { code: &code });
}

Esta forma —un trait con vida— se ve en serde (Deserialize<'de>) y en parsers de zero-copy. En código de aplicación rara vez la escribirás; en bibliotecas que evitan copias, es el pan de cada día.

El consejo que ahorra meses

En código de aplicación, casi nunca hay que anotar vidas. Antes de escribir <'a>: ¿la función devuelve una referencia? Si no, no necesita vidas. ¿Cuántas referencias hay en la entrada? Si es una (o hay &self), la elisión lo resuelve. Si hay varias y no puedes decidir de cuál viene la salida, probablemente el diseño pide devolver un valor en propiedad o separar la función.

3 · Ejemplo mínimo

Dos funciones que devuelven préstamos. La primera no necesita anotación; la segunda sí.

// Una sola referencia de entrada: la elisión ata la salida a ella.
fn scheme(url: &str) -> &str {
    match url.find("://") {
        Some(i) => &url[..i],
        None => "desconocido",
    }
}

// Dos referencias de entrada: hay que decir cuál manda.
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

fn main() {
    let url = String::from("https://sho.rt/k7m2qd");
    println!("{}", scheme(&url));
    let a = String::from("urlshort");
    println!("{}", longest(&a, "rust"));
}
cargo run --quiet
https
urlshort

Línea a línea: scheme tiene una única entrada &str, así que la regla 2 asigna esa vida a la salida y el compilador la expande sola; el "desconocido" del None es &'static str, que cumple cualquier vida porque dura más que todas; longest declara que ambas entradas comparten 'a y que el resultado vive como mucho ese solape; y en main, b es un literal y a un String, así que 'a acaba siendo la vida de a, la más corta.

Quita la anotación de longest y verás el E0106 de la sección de errores. Vuelve a ponerla y comprueba que el binario es idéntico: las vidas no generan código.

4 · Ejemplo real

En urlshort hay dos sitios donde las vidas hacen trabajo real: la configuración que toma prestados los argumentos del CLI (para no copiar rutas ni URLs base) y el parser que recorre una URL devolviendo trozos sin asignar memoria.

pub struct Config<'a> {
    pub base_url: &'a str,
    pub alphabet: &'a [u8],
}
impl<'a> Config<'a> {
    pub fn new(base_url: &'a str, alphabet: &'a [u8]) -> Self { Self { base_url, alphabet } }

    pub fn short_url(&self, code: &str) -> String { format!("{}/{}", self.base_url, code) }

    // Devuelve la vida del alfabeto original, no la del préstamo a self.
    pub fn alphabet(&self) -> &'a [u8] { self.alphabet }
}

// Vistas de la URL, cero asignaciones
pub struct UrlParser<'a> { input: &'a str, cursor: usize }
impl<'a> UrlParser<'a> {
    pub fn new(input: &'a str) -> Self { Self { input, cursor: 0 } }
    pub fn next_segment(&mut self) -> Option<&'a str> {
        // Copiamos la referencia fuera de self: así el retorno no presta self
        // y podemos avanzar el cursor mientras devolvemos el trozo.
        let input: &'a str = self.input;
        let start = self.cursor;
        if start >= input.len() { return None; }
        let rest = &input[start..];
        let end = rest.find('/').map(|i| start + i).unwrap_or(input.len());
        self.cursor = if end < input.len() { end + 1 } else { end };
        Some(&input[start..end])
    }
}

fn main() {
    let base = String::from("https://sho.rt");
    let alphabet = *b"23456789abcdefghjkmnpqrstuvwxyz";
    let config = Config::new(&base, &alphabet);
    println!("{} / {} símbolos", config.short_url("k7m2qd"), config.alphabet().len());
    let raw = String::from("https://sho.rt/k7m2qd/hits");
    let mut parser = UrlParser::new(&raw);
    while let Some(segment) = parser.next_segment() {
        println!("[{segment}]");
    }
}
cargo run --quiet
https://sho.rt/k7m2qd / 31 símbolos
[https:]
[]
[sho.rt]
[k7m2qd]
[hits]

Config<'a> describe que la config no puede vivir más que base ni que alphabet. alphabet() devuelve &'a [u8] para que el slice sobreviva a la config, y next_segment devuelve vistas de raw —no de parser— para poder seguir usando el parser y los trozos a la vez. El truco clave es let input: &'a str = self.input;: se copia la referencia (es Copy) antes de tocar self.cursor; sin él, el préstamo de &mut self y el retorno chocarían.

Analogía: el préstamo con fecha de devolución

Un &'a T es un libro prestado con una fecha límite: 'a. No dice cuándo lo devuelves tú; dice hasta cuándo puedes tenerlo sin que la biblioteca lo reclame. Si dos personas prestan el mismo libro, la fecha común es la más próxima de las dos. Y 'static es un libro que la biblioteca nunca reclamará: cómodo, pero no puedes fabricar uno cada vez que abres la aplicación.

La prueba de las dos preguntas

Antes de anotar, pregúntate: «¿de dónde viene este dato?» y «¿quién garantiza que siga vivo?». Si las dos respuestas son el mismo parámetro, la elisión lo resuelve. Si son distintos, necesitas anotar. Si no hay respuesta clara, el problema no es de lifetimes: es de propiedad.

6 · Errores habituales

1. Firma ambigua sin anotación

fn longest(x: &str, y: &str) -> &str {
    if x.len() >= y.len() { x } else { y }
}
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:39
  |
1 | fn longest(x: &str, y: &str) -> &str {
  |                  ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the
          signature does not say whether it is borrowed from `x` or `y`

Hay dos candidatos para la salida y el compilador se niega a elegir: elegir mal sería un use-after-free. Si el resultado solo puede venir de x, ni siquiera necesitas darle la misma vida a y: fn prefijo<'a>(x: &'a str, _y: &str) -> &'a str.

2. Struct con referencia sin declarar la vida

struct Excerpt { part: &str }
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:24
  |
1 | struct Excerpt { part: &str }
  |                        ^ expected named lifetime parameter
  |
help: consider introducing a named lifetime parameter
  |
1 | struct Excerpt<'a> { part: &'a str }

Bien: parametrizar el struct y repetir la vida en el impl: struct Excerpt<'a> { part: &'a str } e impl<'a> Excerpt<'a>.

3. Un préstamo que sobrevive al dato

fn main() {
    let r;
    {
        let s = String::from("corto");
        r = &s;
    }
    println!("{r}");
}
error[E0597]: `s` does not live long enough
 --> src/main.rs:5:13
  |
4 |         let s = String::from("corto");
  |             - binding `s` declared here
5 |         r = &s;
  |             ^^ borrowed value does not live long enough
6 |     }
  |     - `s` dropped here while still borrowed
7 |     println!("{r}");
  |               - borrow later used here

s muere al cerrar el bloque interior y r se usa después: exactamente el use-after-free que Rust impide compilar. Arreglo: que el dueño viva tanto como el préstamo (let s = ...; let r = &s;).

4. Referencia a un temporal

fn main() {
    let r = String::from("urlshort").as_str();
    println!("{r}");
}
error[E0716]: temporary value dropped while borrowed
 --> src/main.rs:2:13
  |
2 |     let r = String::from("urlshort").as_str();
  |             ^^^^^^^^^^^^^^^^^^^^^^^^          - temporary value is freed
  |             |                                  at the end of this statement
  |             creates a temporary value which is freed while still in use
3 |     println!("{r}");
  |               - borrow later used here

Bien: nombrar el dueño: el temporal no tiene variable, así que se destruye al final de la sentencia; la referencia quedaría colgando.

fn main() {
    let owned = String::from("urlshort");
    let r = owned.as_str();
    println!("{r}");
}

7 · Ejercicio guiado

Objetivo: provocar E0106, arreglarlo con la anotación mínima, guardar un préstamo en un struct y comprobar que 'static no es la solución.

  1. Crea el proyecto. 
    cargo new lifetimes-lab --bin
cd lifetimes-lab
  2. Provoca el error. Pega esto y ejecuta cargo build: 
    fn first_word(text: &str, separator: &str) -> &str {
    match text.find(separator) {
        Some(i) => &text[..i],
        None => text,
    }
}

    Salida esperada: error[E0106]: missing lifetime specifier. Observa que el cuerpo solo usa text: el compilador no lo mira para decidir la firma.

  3. Anota solo lo necesario. El resultado viene de text, así que el separador no necesita la misma vida: 
    fn first_word<'a>(text: &'a str, separator: &str) -> &'a str {
    match text.find(separator) {
        Some(i) => &text[..i],
        None => text,
    }
}

fn main() {
    let url = String::from("sho.rt/k7m2qd");
    println!("{}", first_word(&url, "/"));
}

    Salida esperada: sho.rt. Compila también con un separador temporal: first_word(&url, &String::from("/")).

  4. Guarda una referencia en un struct. 
    struct View<'a> { text: &'a str }

impl<'a> View<'a> {
    fn new(text: &'a str) -> Self { Self { text } }
    fn len(&self) -> usize { self.text.len() }
    fn text(&self) -> &'a str { self.text }
}

fn main() {
    let owned = String::from("https://sho.rt/k7m2qd");
    let v = View::new(&owned);
    println!("{} {}", v.len(), v.text());
}

    len devuelve usize y no tiene vida en la salida; text devuelve &'a str y sobrevive al struct. Cámbialo por -> &str y comprobarás que la elisión lo ata a &self.

  5. Comprueba que 'static no sirve para un dato local. 
    fn save(list: &mut Vec<&'static str>, text: &str) {
    list.push(text);
}

fn main() {
    let mut list = Vec::new();
    let local = String::from("k7m2qd");
    save(&mut list, &local);
}

    Salida esperada: error: lifetime may not live long enough, con la nota requires that `'1` must outlive `'static`. El 'static del vector exige que el texto viva siempre. Cambia el tipo a Vec<String> y guarda text.to_string(): ahora el vector es dueño y no hay vida que atar. Cierra con cargo clippy -- -D warnings.

Criterio de éxito

Puedes explicar por qué fn first_word<'a>(text: &'a str, separator: &str) -> &'a str es mejor firma que darle la misma vida al separador, y por qué Vec<&'static str> es casi siempre un error de diseño en una aplicación.

8 · Reto

🎯 El enrutador sin copias

El servidor de urlshort recibe una línea de petición como "GET /k7m2qd HTTP/1.1". Escribe un tipo Request<'a> que guarde method, path y version como &'a str, y una función Request::parse(raw: &'a str) -> Option<Request<'a>> que la rellene sin asignar memoria: nada de to_string(), nada de Vec<String>.

Requisitos: rechaza líneas con un número de partes distinto de tres, con método o versión vacíos, y con un path que no empiece por /. Añade un método code(&self) -> &'a str que devuelva el último segmento del path y comprueba que sigue siendo usable después de mover el Request a otra variable.

Pista: split_whitespace() sobre un &'a str devuelve &'a str, no copias. Si necesitas el índice del último '/', rfind te lo da en bytes. Y ojo con la firma de code: si devuelves &str atado a &self, el resultado morirá con el Request; si lo devuelves como &'a str, sobrevive porque viene de raw. Elige a conciencia y escribe en un comentario por qué.

9 · Resumen

  • Una vida es la región en la que una referencia es válida; las anotaciones describen relaciones y no alargan ni acortan nada en ejecución.
  • Elisión: cada entrada tiene su vida; con una sola entrada (o &self), esa vida va a la salida.
  • Con varias entradas y salida prestada hay que anotar <'a> o devolver un valor en propiedad.
  • Un struct con referencias se parametriza: struct View<'a> { text: &'a str }, y el impl lleva la misma vida.
  • &'static str es válido siempre (literales, static, Box::leak); T: 'static solo significa «sin préstamos cortos».
  • En código de aplicación casi nunca hay que anotar vidas: si duele, suele ser un problema de propiedad.

Comandos y conceptos de esta lección

10 · Preguntas frecuentes

¿Por qué el compilador no deduce solo la vida y me ahorra escribirlas?

Porque en una firma pública la vida es parte del contrato: quien llama necesita saber qué garantiza la función sin leer su cuerpo. Inferirla del cuerpo haría que un cambio interno rompiera a los llamantes y que el análisis fuera mucho más caro. La elisión cubre los casos habituales; el resto se declara.

¿Cuándo debo usar 'static de verdad?

Cuando el dato vive lo que el proceso: literales, tablas de configuración compiladas, un interner de cadenas o memoria filtrada a propósito con Box::leak al arrancar. También aparece en bounds de tokio::spawn, donde una tarea no puede contener préstamos a datos que podrían morir antes que ella. Fuera de esos casos, casi siempre pide propiedad en lugar de préstamo.

Si devuelvo &'a str pero el texto lo creo dentro, ¿qué pasa?

Que no compila: E0515 o E0597. No puedes prometer que un préstamo vive más que su dueño. Las salidas son devolver el String (transfiere la propiedad), recibir el dato prestado y devolver el préstamo, o filtrar a 'static con Box::leak si de verdad debe vivir siempre.

¿Por qué Deserialize<'de> de serde tiene una vida?

Porque serde puede deserializar sin copiar: si el JSON de entrada es un &'de str, los campos &'de str del struct apuntan dentro de ese buffer. La vida 'de describe exactamente eso. Es el mismo patrón que el UrlParser del ejemplo real, aplicado a un formato de datos.
