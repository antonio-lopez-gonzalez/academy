Ownership: stack, heap, move y drop

Módulo 1 · Ownership y borrowing ⏱ 45 minutos

1 · Introducción

En cualquier lenguaje, alguien tiene que liberar la memoria que ya no se usa. Con un recolector de basura lo decide el runtime; en C y C++ lo decides tú con free y delete. Rust elige un tercer camino: cada valor tiene exactamente un dueño, y el compilador comprueba que nadie lo use cuando el dueño ya no está. Ese contrato se llama ownership, y es el mecanismo que permite prescindir del GC sin delegar la memoria al programador.

¿Por qué existe esta lección?

Porque el 80 % de los errores de tus primeras semanas (E0382, E0507, «value moved here») salen del mismo sitio: no tienes claro quién es el dueño de cada dato en cada línea. Cuando lo tienes claro, los préstamos, las vidas y los slices encajan solos.

Al terminar sabrás qué vive en el stack y qué en el heap, por qué una asignación puede invalidar la variable anterior, por qué copiar un i32 no es lo mismo que mover un String, en qué orden se libera todo y cómo devolver la propiedad sin pagar un clone().

Errores típicos al empezar:

  • Añadir clone() en cuanto el compilador se queja, en vez de preguntarse quién debería ser el dueño.
  • Creer que let b = a; copia, como en Java o Python, y usar a después.
  • Intentar marcar como Copy un tipo que contiene un String, o suponer que las variables se liberan en orden de declaración (es al revés).

2 · Teoría

Dos memorias, dos ritmos

StackHeap
Qué guardaVariables locales y valores de tamaño fijo, conocido al compilarDatos de tamaño variable o que sobreviven a la función

Quién liberaNadie: el marco desaparece al volverAlguien debe hacerlo. En Rust, el dueño
 
        STACK (LIFO, tamaño fijo)                  HEAP (libre, tamaño variable)
        ─────────────────────────                  ──────────────────────────────
   ┌──────────────────────────────┐
   │ frame de main()              │
   │   n: i32          = 42       │          ┌──────────────────────────┐
   │   s: String                  │          │  h  o  l  a              │
   │     ptr ─────────────────────┼─────────►│  (buffer de 5 bytes)     │
   │     len     = 5              │          └──────────────────────────┘
   │     cap     = 5              │
   └──────────────────────────────┘

La asimetría es la clave: el String vive en el stack (tres palabras) pero es dueño de un buffer en el heap. Cuando el marco desaparece, ese buffer quedaría huérfano; el compilador inserta la liberación exactamente donde toca.

Las tres reglas

  1. Cada valor tiene un único dueño: una variable, un campo, un elemento de un contenedor.
  2. Solo hay un dueño a la vez: asignar, pasar a una función o meter en un Vec mueve la propiedad.
  3. Al salir de ámbito, el dueño libera el valor: se ejecuta drop y la memoria vuelve al asignador.

De ahí salen las tres garantías: no hay use-after-free (nadie usa lo que no posee), ni double free (solo un dueño libera), ni fugas en el camino normal.

Anatomía de un String

fn main() {
    let mut s = String::with_capacity(16);   // reserva 16 bytes en el heap
    s.push_str("abc");                       // cabe: no reasigna
    println!("len={} cap={}", s.len(), s.capacity());
}

ptr apunta al buffer; len son los bytes escritos (s.len() devuelve bytes, no caracteres); cap son los bytes reservados. La salida es len=3 cap=16. Si push_str no cabe, el String reserva más, copia y libera el buffer viejo. Todo ocurre dentro de la biblioteca estándar: para ti sigue siendo un valor con un dueño.

Mover no es copiar

fn main() {
    let code = String::from("k7m2qd");
    let alias = code;                 // la propiedad se TRANSFIERE
    println!("{alias}");              // correcto
    // println!("{code}");            // E0382: borrow of moved value
}
   ANTES                                 DESPUÉS de `let alias = code;`
   ─────                                 ───────────────────────────────
   stack              heap               stack                heap
   code  ────────►  [k7m2qd]            code   (ya no es válido)
   alias (no existe)                    alias  ────────►  [k7m2qd]

El buffer no se ha tocado: se copian las tres palabras del stack y el origen queda marcado como movido. Por eso mover un Vec de un millón de elementos es O(1) y clonarlo es O(n). En C++ esto sería una copia superficial con delete doble si usas los dos objetos; en Java, una segunda referencia que el GC mantiene viva. Rust transfiere y anula el origen: es std::move, pero comprobado. El movimiento puede ser parcial: si mueves un campo, el struct deja de usarse entero, pero los demás campos siguen vivos.

Copy: los tipos que se copian solos

Enteros, flotantes, bool, char, tuplas y arrays de tipos Copy, y las referencias compartidas &T implementan Copy: asignar copia. No lo son &mut T, ni String, ni Vec<T>, ni HashMap, que se mueven. Un tipo solo puede ser Copy si todos sus campos lo son.

#[derive(Clone, Copy, Debug)]
struct Code { value: u32 }             // todos los campos son Copy

fn main() {
    let a = 42;
    let b = a;                         // copia: `a` sigue vivo
    let c = Code { value: 7 };
    let d = c;                         // copia: Code es Copy
    println!("{a} {b} {c:?} {d:?}");
}

drop: el final del ámbito es el final del valor

struct Label(&'static str);
impl Drop for Label {
    fn drop(&mut self) { println!("drop {}", self.0); }
}

fn main() {
    let _first = Label("primera");
    let _second = Label("segunda");
    println!("fin del cuerpo");
}
fin del cuerpo
drop segunda
drop primera

Las variables locales se liberan en orden inverso al de declaración, como una pila. Dentro de un struct, los campos se liberan en orden de declaración, después de tu Drop::drop. Y ojo: drop(x) mueve y libera en ese punto; let _ = x; libera ya; let _x = x; no libera, porque _x es un nombre normal.

Pasar por valor es transferir

fn consume(s: String) -> usize { s.len() }      // libera `s` al volver
fn hand_back(s: String) -> String { s }           // la propiedad sale

fn main() {
    let code = String::from("abc123");
    let n = consume(code);                      // movido
    let code2 = hand_back(String::from("def456")); // el dueño es code2
    println!("{n} {code2}");
}

Si la función necesita el valor para siempre (guardarlo, consumirlo), que lo reciba por valor; si solo lo lee, que lo pida prestado. Devolver la propiedad es correcto pero ruidoso, y es lo que los préstamos evitan. Y cuando el valor está detrás de un &mut, std::mem::take(&mut campo) lo saca y deja Default::default(); std::mem::replace(&mut campo, nuevo) lo saca y deja nuevo. Ambos son O(1) y evitan el clásico «no puedo mover esto porque está detrás de una referencia».

3 · Ejemplo mínimo

Los tres comportamientos en un programa mínimo. cargo new ownership-min --bin y pega esto en src/main.rs:

fn main() {
    let code = String::from("k7m2qd");   // dueño de un buffer en el heap
    let alias = code;                    // MOVE
    println!("{alias}");

    let n = 42;                          // i32 es Copy
    let m = n;                           // COPIA: `n` sigue vivo
    println!("{n} y {m}");

    let original = String::from("urlshort");
    let view = &original;               // PRÉSTAMO: no mueve
    println!("{original} / {view}");
}
cargo run --quiet
k7m2qd
42 y 42
urlshort / urlshort

Línea a línea: String::from reserva 6 bytes y devuelve las tres palabras del stack; let alias = code copia esas palabras y marca code como movida, sin tocar el texto; con i32 no hay dueño que transferir, son 4 bytes copiados; y &original crea un puntero que no transfiere la propiedad. Cambia &original por original y el compilador responderá:

error[E0382]: borrow of moved value: `original`
  |
  |     let view = original;
  |                -------- value moved here
  |     println!("{original} / {view}");
  |               ^^^^^^^^ value borrowed here after move
  |
  = note: move occurs because `original` has type `String`,
          which does not implement the `Copy` trait

Te dice dónde se movió, dónde se usó después y la causa raíz. La solución no es clonar: es decidir quién debe ser el dueño.

4 · Ejemplo real

En urlshort, cada enlace es un valor con dueño. Cuando el CLI lo crea y lo guarda, la propiedad viaja del main al almacén: nadie más lo necesita, así que se mueve en lugar de copiarse.

#[derive(Debug)]
pub struct Link {
    pub code: String,
    pub url: String,
    pub hits: u32,
}

impl Link {
    // Recibe préstamos y construye sus propios String: el Link debe
    // sobrevivir al llamante, así que aquí la copia está justificada.
    pub fn new(code: &str, url: &str) -> Self {
        Self { code: code.to_string(), url: url.to_string(), hits: 0 }
    }
}

#[derive(Default)]
pub struct Store { links: Vec<Link> }

impl Store {
    // POR VALOR: el store pasa a ser el único dueño del enlace.
    pub fn insert(&mut self, link: Link) { self.links.push(link); }

    // Se lleva todo y deja el store vacío, sin clonar.
    pub fn drain(&mut self) -> Vec<Link> { std::mem::take(&mut self.links) }
}

fn main() {
    let mut store = Store::default();
    let url = String::from("https://www.rust-lang.org/learn");
    let code = String::from("k7m2qd");
    let link = Link::new(&code, &url);   // presta: url y code siguen nuestros
    store.insert(link);                   // el Link se MUEVE al store
    println!("{url} sigue disponible");
    println!("{:?}", store.links[0]);
    let archived = store.drain();
    println!("{} enlaces archivados", archived.len());
}
cargo run --quiet
https://www.rust-lang.org/learn sigue disponible
Link { code: "k7m2qd", url: "https://www.rust-lang.org/learn", hits: 0 }
1 enlaces archivados

Link::new recibe &str porque no necesita poseer los datos del llamante; insert recibe Link por valor porque un enlace guardado pertenece al store; y drain usa mem::take para devolver el Vec en O(1) y dejar el store utilizable, sin estados a medias.

Analogía: la escritura de una casa

Poseer un valor es figurar en la escritura. Asignar es firmar el traspaso: la casa no se mueve, cambia el titular y el anterior ya no puede entrar. Prestar (&) es dejar las llaves para una visita; prestar en mutable (&mut) es dejar que alguien reforme, sin nadie más dentro. Y drop es demoler cuando el titular desaparece, sin que nadie tenga que acordarse de llamar al ayuntamiento.

La regla del bolígrafo

Hay un bolígrafo. Si lo tienes tú, nadie más escribe con él. Si lo dejas, tú ya no lo tienes. Solo puedes enseñarlo (&T) o dejarlo escribir (&mut T), y mientras lo enseñas no puedes prestarlo para escribir. Cuando interiorizas esto, dejas de pelearte con el compilador: empiezas a ver el flujo de propiedad.

6 · Errores habituales

1. Usar un valor después de moverlo

fn main() {
    let url = String::from("https://sho.rt/a");
    register(url);                    // se mueve
    println!("{url}");                 // ya no existe
}

fn register(url: String) { println!("guardada {url}"); }
error[E0382]: borrow of moved value: `url`
 --> src/main.rs:4:15
  |
2 |     let url = String::from("https://sho.rt/a");
  |         --- move occurs because `url` has type `String`,
  |             which does not implement the `Copy` trait
3 |     register(url);
  |               --- value moved here
4 |     println!("{url}");
  |               ^^^ value borrowed here after move

El compilador ofrece clone() porque es una salida válida, pero casi nunca es la mejor: si main necesita la URL después, el dueño debería seguir siendo main. Lo mismo ocurre al mover dentro de un bucle (value moved here, in previous iteration of loop). La versión correcta presta:

fn register(url: &str) { println!("guardada {url}"); }

fn main() {
    let url = String::from("https://sho.rt/a");
    register(&url);                  // presta: el dueño sigue siendo main
    println!("{url}");
}

2. Mover un elemento fuera de un índice

fn main() {
    let codes = vec![String::from("abc"), String::from("def")];
    let first = codes[0];          // ¿se lleva el String del Vec?
}
error[E0507]: cannot move out of index of `Vec<String>`
 --> src/main.rs:3:19
  |
3 |     let first = codes[0];
  |                   ^^^^^^^^^^ move occurs because value has type `String`,
  |                              which does not implement the `Copy` trait

Si el compilador lo permitiese, el Vec quedaría con un hueco inválido en la posición 0: indexar produce un lugar, no un valor. Soluciones: prestar (&codes[0]), clonar explícitamente o sacarlo con remove(0), que desplaza el resto.

3. Derivar Copy en un tipo con dueño

#[derive(Clone, Copy)]
struct Link {
    code: String,
    hits: u32,
}
error[E0204]: the trait `Copy` cannot be implemented for this type
 --> src/main.rs:2:17
  |
1 | #[derive(Clone, Copy)]
  |                 ---- in this derive macro expansion
2 | struct Link {
  |        ^^^^
3 |     code: String,
  |     ----------- this field does not implement `Copy`

Copy significa «puedo duplicar estos bytes sin consecuencias». Un String es un puntero a memoria que alguien libera: copiarlo a pelo daría dos dueños del mismo buffer y un double free garantizado. Deriva solo Clone y decide en cada llamada si el clon está justificado; si el tipo es realmente pequeño, usa campos Copy (u32, [u8; 8], &'static str).

8 · Reto

🎯 La rotación del archivo de enlaces

urlshort guarda los enlaces del día en un Store con un Vec<Link>. A medianoche hay que archivar el contenido: mover todos los enlaces al archivo histórico, dejar el store listo para el día siguiente y no copiar ni un solo Link.

Diseña dos structs, Store y Archive, con estas operaciones: crear un store vacío, insertar un enlace construido a partir de &str, rotar el store hacia el archivo y consultar cuántos enlaces hay en cada lado. El main debe seguir usando el store después de la rotación y el archivo debe conservar los enlaces rotados. Nada de clone(), nada de Rc.

Pista: el archivo puede recibir el Vec<Link> por valor, o el store puede empujar sus enlaces con extend. Para vaciar sin perder la capacidad reservada, std::mem::take deja un Vec vacío; std::mem::replace te deja elegir qué queda. Y piensa qué pasa si la rotación se llama dos veces: el segundo archivo debe quedar vacío, no con los enlaces repetidos.

9 · Resumen

  • El stack guarda valores de tamaño fijo y muere con la función; el heap guarda datos variables que necesitan dueño.
  • Tres reglas: un dueño por valor, la propiedad se transfiere, y el valor se libera al salir de ámbito.
  • Un String son tres palabras en el stack (ptr, len, capacity) y un buffer en el heap.
  • Asignar un String mueve (O(1)) y clonarlo copia el buffer (O(n)); los tipos Copy (enteros, bool, char, &T) se copian bit a bit.
  • Las variables se liberan en orden inverso; los campos de un struct, en orden de declaración.
  • mem::take y mem::replace permiten mover desde un &mut sin dejar huecos.

10 · Preguntas frecuentes

¿Por qué Rust no copia al asignar, como Java o Python?

Porque allí una variable es una referencia a un objeto que el GC mantiene vivo; copiarla es barato y seguro. Sin GC, dos referencias al mismo buffer sin control serían un double free. La solución no es copiar los datos siempre: es transferir la propiedad, que cuesta lo mismo que copiar una referencia.

Entonces, ¿cuándo está justificado un clone()?

Cuando de verdad necesitas dos copias independientes: un snapshot para un informe, un valor guardado en dos estructuras, un dato que cruza a otro hilo. No lo está cuando solo querías calmar al compilador: si la firma puede ser &T y el código sigue claro, no clones.

Si mover un Vec es O(1), ¿por qué importa el tamaño?

Porque mover solo copia las tres palabras del stack; el buffer se queda donde está y cambia de dueño. Lo que cuesta O(n) es clone(), que reserva otro buffer y copia elemento a elemento. Pasar un Vec por valor es, en la práctica, tan barato como pasar un puntero.

¿Puedo implementar Drop y Copy a la vez?

No: el compilador lo rechaza con E0184. Un tipo Copy se duplica sin avisar, y un Drop que libera un recurso se ejecutaría dos veces. Es la comprobación que impide el double free: si tu tipo necesita limpieza, no puede copiarse a la ligera.
