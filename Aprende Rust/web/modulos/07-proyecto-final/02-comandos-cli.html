Comandos: short, resolve, list y delete

Módulo 7 · Proyecto final ⏱ 45 minutos

1 · Introducción

El dominio ya existe y está probado. Ahora necesita una cara: alguien que escriba urlshort short https://… y reciba una URL corta, o urlshort resolve 9xQ2mK y reciba el destino. Ese alguien puede ser una persona en una terminal o un script en CI, y los dos tienen exigencias distintas: la persona quiere leer una línea clara; el script quiere códigos de salida estables y nada de adornos.

clap 4 resuelve el 80 % del trabajo por ti: parsea, valida tipos, genera --help, sugiere correcciones y devuelve el código 2 en los errores de uso. El 20 % restante es decisión tuya: qué se imprime, dónde se imprime y qué significa cada código de salida.

¿Por qué existe esta lección?

Porque un CLI mal terminado no se puede automatizar. Si los errores van a stdout o si todo sale con código 0, ningún script podrá distinguir un éxito de un fallo. Y si la lógica de los comandos vive dentro de main, ningún test podrá ejercitarla.

Al terminar tendrás los cinco subcomandos (short, resolve, list, delete y serve), dos flags globales, una salida pensada para leer y tests que llaman al CLI sin abrir una terminal.

  • Imprimir los errores en stdout y devolver siempre 0: el script no distingue éxito de fracaso.
  • Validar la URL con clap y luego revalidarla con reglas distintas en el servicio.
  • Llamar a std::process::exit dentro de la función que hace el trabajo: mata el proceso de test.
  • Olvidar que main async necesita #[tokio::main]: el subcomando serve no compila.

2 · Teoría

Del argv al caso de uso

Un CLI tiene tres fases que conviene no mezclar: parsear (clap convierte texto en tipos), ejecutar (el Service hace el trabajo) e informar (formatear la salida y elegir el código). Si la fase de ejecutar imprime, no se puede reutilizar; si la de informar valida, hay reglas duplicadas.

argv
  │
  ▼
clap::Parser ──► Cli { base_url, store, command }
  │                        │
  │ error de uso           │ execute(service, command)
  ▼                        ├── short   ─┐
exit 2                     ├── resolve ─┤
(--help, --version)        ├── list    ─┼──► Service ──► Arc<dyn Store>
                           ├── delete  ─┤        │
                           └── serve   ─┘        ▼
                              stdout · stderr · exit code

El contrato de los comandos, que es lo que un usuario lee en --help:

ComandoQué haceQué imprime
short <url>Valida, genera un código libre y guarda el enlaceLa URL corta
resolve <code>Busca el código, suma una visita y devuelve el destinoLa URL original
listLista los enlaces ordenados por códigoCódigo, hits y URL
delete <code>Borra el enlaceborrado 9xQ2mK
serve --port 3000Arranca el servidor HTTP (lección 03)La dirección de escucha

Flags globales: se escriban donde se escriban

#[arg(global = true)] hace que un flag valga antes o después del subcomando: urlshort --store x.json list y urlshort list --store x.json producen el mismo Cli sin duplicar definiciones. --base-url decide qué URL se enseña (local, dominio propio, tests) y --store qué fichero se usa; ninguno pertenece a un comando concreto.

Códigos de salida: el contrato con los scripts

CódigoCuándoQuién lo emite
0Todo fue bienmain
1Error de ejecución: URL inválida, código inexistente, fichero ilegibleexecute + main
2Error de uso: subcomando desconocido, falta un argumento, puerto no numéricoclap, antes de tu código

La separación es deliberada: el 2 significa «has escrito mal la orden» y no depende de tu lógica; el 1 significa «la orden era correcta y el mundo falló». Un script puede reintentar un 1 y abortar un 2 sin leer el mensaje.

Qué imprime y qué no

La regla es tajante: stdout solo lleva el resultado; los diagnósticos van a stderr. En urlshort 0.1 el CLI es para humanos: imprime una línea por enlace y no tiene flag --json. La salida legible por máquina es el servidor HTTP de la lección 03 y el propio fichero links.json; añadir --json después es un cambio compatible (nuevo flag, mismo Service).

$ urlshort --store /tmp/links.json list
CÓDIGO   HITS  URL
9xQ2mK      3  https://www.rust-lang.org/learn
A7bC1z      0  https://example.com

$ urlshort --store /tmp/links.json list > enlaces.txt
# stdout limpio: solo la tabla, sin mensajes de progreso

El nombre del subcomando también es API

Renombrar resolve por open rompe los scripts de quien ya lo usa. Los subcomandos son estables dentro de una mayor; los mensajes humanos, no. Si necesitas cambiar un nombre, añade un alias (#[command(alias = "open")]) y documenta el cambio.

3 · Ejemplo mínimo

El esqueleto más pequeño con subcomandos, sin dominio ni almacenamiento. Compila con cargo add clap --features derive.

use clap::{Parser, Subcommand};

/// Acorta URLs desde la terminal.
#[derive(Debug, Parser)]
#[command(name = "urlshort", version, about)]
struct Cli {
    /// Fichero donde se guardan los enlaces.
    #[arg(long, global = true, default_value = "links.json")]
    store: String,

    #[command(subcommand)]
    command: Command,
}

#[derive(Debug, Subcommand)]
enum Command {
    /// Crea un código corto para una URL.
    Short { url: String },
    /// Lista los enlaces guardados.
    List,
}

fn main() {
    let cli = Cli::parse();          // en error de uso: mensaje y exit 2
    match cli.command {
        Command::Short { url } => println!("(guardaría {url} en {})", cli.store),
        Command::List => println!("(sin enlaces en {})", cli.store),
    }
}

Qué hace cada pieza:

  • #[derive(Parser)] genera el parser del struct; los comentarios /// se convierten en la ayuda de --help.
  • #[command(name, version, about)] toma la versión de Cargo.toml: una sola fuente de verdad.
  • #[command(subcommand)] marca el campo con el enum; cada variante es un subcomando en kebab-case.
  • global = true permite --store antes o después del subcomando.
  • Cli::parse() imprime la ayuda y sale con 2 si algo no encaja; try_parse_from devuelve el error y es lo que usan los tests.

Prueba cargo run -- --help: verás los comandos, las opciones y la versión. Un subcomando inventado termina con código 2; --help termina con 0.

4 · Ejemplo real

El Cli de urlshort añade la configuración y los cinco comandos. Los campos son pub porque los tests los inspeccionan.

// src/cli.rs
use std::path::PathBuf;

use clap::{Parser, Subcommand};

use crate::domain::Link;
use crate::error::Error;
use crate::service::Service;

#[derive(Debug, Parser)]
#[command(name = "urlshort", version, about = "Acorta URLs desde la terminal")]
pub struct Cli {
    /// Base pública para construir la URL corta
    #[arg(long, global = true, default_value = "http://localhost:3000")]
    pub base_url: String,
    /// Fichero JSON donde se guardan los enlaces
    #[arg(long, global = true, default_value = "links.json", value_name = "PATH")]
    pub store: PathBuf,
    #[command(subcommand)]
    pub command: Command,
}

#[derive(Debug, Subcommand)]
pub enum Command {
    /// Crea un código corto para una URL
    Short { url: String },
    /// Resuelve un código y registra una visita
    Resolve { code: String },
    /// Lista los enlaces guardados
    List,
    /// Borra un enlace del store
    Delete { code: String },
    /// Arranca el servidor HTTP en 127.0.0.1
    Serve {
        #[arg(long, default_value_t = 3000)]
        port: u16,
    },
}

La ejecución delega en Service y solo se ocupa del formato. Es async porque el brazo Serve arranca el servidor; los otros cuatro no esperan nada, pero comparten la firma.

pub async fn execute(service: Service, command: Command) -> Result<(), Error> {
    match command {
        Command::Short { url } => {
            let link = service.short(&url)?;
            println!("{}", link.short_url(service.base_url()));
        }
        Command::Resolve { code } => {
            let link = service.resolve(&code)?;          // suma una visita
            println!("{}", link.url());
        }
        Command::List => print_table(&service.list()?),
        Command::Delete { code } => {
            service.delete(&code)?;
            println!("borrado {code}");
        }
        Command::Serve { port } => {
            let addr = std::net::SocketAddr::from(([127, 0, 0, 1], port));
            crate::server::serve(service, addr).await?;
        }
    }
    Ok(())
}

fn print_table(links: &[Link]) {
    if links.is_empty() {
        eprintln!("no hay enlaces guardados en este store");
        return;
    }
    println!("{:<8} {:>6}  {}", "CÓDIGO", "HITS", "URL");
    for link in links {
        println!("{:<8} {:>6}  {}", link.code(), link.hits(), link.url());
    }
}

El binario monta el store, crea el Service y traduce el resultado a código de salida. clap sale con 2 si la orden está mal; execute devuelve el error y main lo convierte en mensaje por stderr y código 1. Ningún unwrap en el camino del usuario.

// src/main.rs
use std::process::ExitCode;
use std::sync::Arc;

use clap::Parser;
use urlshort::cli::{execute, Cli};
use urlshort::service::Service;
use urlshort::store::{JsonStore, Store};

#[tokio::main]
async fn main() -> ExitCode {
    let cli = Cli::parse();
    let store: Arc<dyn Store> = match JsonStore::open(&cli.store) {
        Ok(store) => Arc::new(store),
        Err(err) => { eprintln!("error: {err}"); return ExitCode::from(1); }
    };
    let service = Service::new(store, cli.base_url);
    match execute(service, cli.command).await {
        Ok(()) => ExitCode::SUCCESS,
        Err(err) => { eprintln!("error: {err}"); ExitCode::from(1) }
    }
}

Uso real, con el store en un fichero temporal:

cargo run -- --store /tmp/links.json short "https://www.rust-lang.org/learn"
# http://localhost:3000/9xQ2mK
cargo run -- --store /tmp/links.json resolve 9xQ2mK
# https://www.rust-lang.org/learn
cargo run -- --store /tmp/links.json list
cargo run -- --store /tmp/links.json delete 9xQ2mK
# borrado 9xQ2mK

Un comando, un efecto

short escribe, resolve escribe (hits) y lee, list solo lee, delete escribe, serve no toca el store hasta que llega una petición. Si un comando hace dos cosas, el --help miente. Y si dudas de si algo debe imprimirse, pregúntate si un script lo podría parsear: si la respuesta es «da igual», probablemente va a stderr.

La salida también es una API

En cuanto alguien escribe urlshort list | awk '{print $1}', el número de columnas importa. Documenta el formato en el README y, si necesitas cambiarlo, añade una opción (--json, --quiet) en vez de romper la existente.

6 · Errores habituales

1. Mover cli.command y luego leer cli.base_url

fn run(cli: Cli) -> Result<(), Error> {
    match cli.command {                     // mueve el campo command
        Command::Short { url } => {
            let link = service.short(&url)?;
            println!("{}", link.short_url(&cli.base_url));   // movido parcialmente
        }
        _ => {}
    }
    Ok(())
}

El error real:

error[E0382]: borrow of partially moved value: `cli`
  --> src/cli.rs:12:34
   |
 6 |     match cli.command {
   |           ----------- value partially moved here
...
10 |             println!("{}", link.short_url(&cli.base_url));
   |                                         ^^^^^^^^^^^^^ value borrowed here after partial move
   |
   = note: partial move occurs because `cli.command` has type `Command`,
           which does not implement the `Copy` trait

Por qué está mal: Command contiene String y no es Copy; el match lo mueve y el resto de cli queda inutilizable. Bien: desestructura antes del match, como hace main: let Cli { base_url, store, command } = cli;.

2. Devolver siempre 0

Mal: execute imprime el error y termina con Ok(()). El mensaje se ve, pero echo $? dice 0 y el script continúa como si nada. Bien: propaga con ? y deja que main decida el código con ExitCode::from(1).

3. process::exit dentro de la biblioteca

Mal: if err { eprintln!(…); std::process::exit(1); } dentro de cli::execute. El test que llama a execute mata el proceso de test entero y no hay forma de comprobar el mensaje. Bien: Result hasta main y exit solo en el borde del binario.

4. Parsear el puerto a mano

Mal: port: String y luego port.parse().unwrap(): un valor no numérico produce un panic con traza en vez de un error de uso. Bien: port: u16. clap valida el rango y responde con código 2 antes de que tu código se ejecute.

7 · Ejercicio guiado

Objetivo: probar el parseo y el flujo completo sin abrir una terminal. Los tests de parseo viven en src/cli.rs; el de flujo, en tests/cli.rs.

  1. Añade los tests de parseo. try_parse_from recibe un iterador con el nombre del programa en la primera posición, igual que argv. 
    #[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn las_flags_globales_valen_en_cualquier_posicion() {
        let cli = Cli::try_parse_from([
            "urlshort", "--base-url", "https://s.dev", "short", "https://example.com",
        ]).unwrap();
        assert_eq!(cli.base_url, "https://s.dev");
        assert!(matches!(cli.command, Command::Short { .. }));
    }

    #[test]
    fn delete_sin_codigo_es_error_de_uso() {
        assert!(Cli::try_parse_from(["urlshort", "delete"]).is_err());
    }

    #[test]
    fn el_puerto_por_defecto_es_3000() {
        let cli = Cli::try_parse_from(["urlshort", "serve"]).unwrap();
        assert!(matches!(cli.command, Command::Serve { port: 3000 }));
    }
}
  2. Comprueba que fallan por la razón correcta. Quita global = true del flag --base-url y verás fallar el primer test: la opción deja de existir delante del subcomando. Vuelve a ponerlo.
  3. Escribe el test de flujo completo. Cada paso usa el mismo Service que el CLI; se inspecciona el estado, no la pantalla. 
    // tests/cli.rs
use std::sync::Arc;

use urlshort::cli::{execute, Command};
use urlshort::service::Service;
use urlshort::store::MemoryStore;

#[tokio::test]
async fn flujo_short_resolve_list_delete() {
    let service = Service::new(Arc::new(MemoryStore::new()), "https://s.dev");

    execute(service.clone(), Command::Short {
        url: "https://www.rust-lang.org".into(),
    }).await.unwrap();
    let code = service.list().unwrap()[0].code().to_string();

    execute(service.clone(), Command::Resolve { code: code.clone() }).await.unwrap();
    assert_eq!(service.list().unwrap()[0].hits(), 1);

    execute(service.clone(), Command::Delete { code }).await.unwrap();
    assert!(service.list().unwrap().is_empty());
}
  4. Ejecuta todo. cargo test y cargo clippy --all-targets -- -D warnings. Salida esperada: los tres tests de parseo y el de flujo en verde. Si el de flujo no compila, comprueba que Service implementa Clone: lo necesita para conservar una copia mientras execute consume la otra.

Criterio de éxito

Puedes cambiar el nombre de un subcomando y ver exactamente qué test falla. Eso significa que el contrato del CLI está cubierto: el parseo por un lado y el flujo por otro, sin procesos hijos ni sleeps.

8 · Reto

🎯 --json y --dry-run sin romper nada

Añade dos flags globales. --json hace que list imprima un array de objetos y que short/resolve impriman un objeto con code, url, short_url, hits y created_at. --dry-run hace que delete diga qué borraría sin borrar nada.

Restricciones: sin --json la salida actual no cambia ni un carácter; --dry-run no debe incrementar hits ni escribir en disco; los códigos de salida se mantienen. ¿Dónde pones el if json: en execute, en una función render o en un trait de presentación?

Pista: execute ya es el sitio donde el dominio se convierte en texto, así que es el candidato natural. Para el dry-run, mira qué operación del Service te falta: hoy delete borra y devuelve (); un método que solo consulte el enlace te da el «qué borraría» sin efectos. Y serializa con serde_json, que ya está en el árbol de dependencias.

9 · Resumen

  • clap 4 con derive convierte una estructura y un enum en un CLI completo con ayuda y validación.
  • Los flags global = true valen antes y después del subcomando; --base-url y --store son configuración.
  • execute(service, command) se testea; main solo monta el store y traduce el error a código.
  • Códigos: 0 éxito, 1 fallo de ejecución, 2 error de uso emitido por clap.
  • stdout lleva el resultado; stderr lleva diagnósticos. El CLI 0.1 es para humanos: la salida máquina es el servidor.
  • port: u16 deja que clap valide el rango antes de arrancar el servidor.
  • try_parse_from prueba el parseo sin lanzar procesos; el test de flujo usa Service + MemoryStore.

10 · Preguntas frecuentes

¿Por qué el CLI no tiene --json?

Porque en 0.1 la interfaz para máquinas es el servidor HTTP: el CLI imprime para humanos y el fichero links.json ya es JSON. Añadir --json después no rompe nada porque es un flag nuevo y el Service no cambia. Lo que sí sería un error es cambiar el formato actual sin avisar: hay scripts que leen la primera columna.

¿Dónde valido la URL: en clap o en el dominio?

En el dominio, una sola vez. clap comprueba que el argumento existe y que es un String; las reglas de qué es una URL válida viven en validate_url. Si duplicas la comprobación con un parser de clap, tendrás dos mensajes distintos para el mismo error y una de las dos reglas se quedará atrás.

¿Cómo pruebo lo que se imprime por pantalla?

Capturar stdout de tu propio proceso es incómodo. La alternativa que escala es no probar el texto: prueba el estado (los enlaces en el store) y deja el formato como decisión de presentación. Si el formato es crítico, extrae fn render(&[Link]) -> String y testea esa función pura; println! solo la imprime.

¿Por qué execute es async si cuatro comandos no esperan nada?

Porque serve sí: arranca el servidor y no termina hasta que lo paras. Una sola función con una firma uniforme evita dos caminos de despacho y dos formas de devolver errores. Si te molesta el await, el precio sería un match en main que separe Serve del resto: legítimo, pero duplica la tabla de comandos.
