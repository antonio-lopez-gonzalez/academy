Publicación en crates.io y release

Módulo 7 · Proyecto final ⏱ 40 minutos

1 · Introducción

El crate compila, pasa los tests y sirve URLs por HTTP. Falta lo que separa un repositorio de un producto: que otra persona pueda instalarlo con cargo install urlshort, leer su documentación en docs.rs y descargar un binario sin tener Rust instalado.

Publicar en crates.io es permanente. No hay «despublicar»: solo yank, que impide nuevas instalaciones de esa versión pero no borra el código. Por eso el orden importa: primero se empaqueta y se prueba el paquete, después se publica, y solo entonces se etiqueta y se generan los binarios.

¿Por qué existe esta lección?

Porque un crate sin description, sin licencia o sin README no se puede publicar, y uno con documentación vacía se publica pero nadie lo usa. Los metadatos, los doctests y el perfil de release son parte del proyecto, no burocracia: son la diferencia entre «funciona en mi máquina» y «lo instala cualquiera».

Al terminar tendrás el Cargo.toml completo, documentación que pasa #![deny(missing_docs)], un paquete verificado con cargo publish --dry-run, una estrategia de versiones, una imagen Docker de menos de 100 MB y un checklist para no publicar a ciegas.

  • Publicar sin haber ejecutado cargo package: el tarball puede no compilar aunque tu directorio sí.
  • Reutilizar el número de versión: crates.io rechaza el segundo intento y no se puede deshacer.
  • Documentar solo lo obvio y olvidar los campos públicos: missing_docs los exige todos.
  • Subir un binario de 12 MB cuando con strip y lto cabe en 1,7 MB.

2 · Teoría

La escalera de la publicación

Cada peldaño se apoya en el anterior. Saltarse uno se paga en la siguiente versión, cuando ya hay usuarios.

1. documentar     rustdoc + doctests + README        cargo doc --no-deps
2. empaquetar     lo que viaja en el .crate          cargo package --list
3. verificar      compila el tarball, no tu carpeta  cargo package
4. publicar       sube a crates.io (irreversible)    cargo publish --dry-run
5. etiquetar      versión y changelog                git tag v0.1.0
6. distribuir     binarios y contenedor              GitHub Releases · Docker

El paso 3 es el que casi nadie hace y el que evita el 90 % de los sustos: cargo package copia solo los ficheros incluidos en el paquete a target/package/ y compila desde ahí. Si te olvidaste de incluir un módulo o un fixture, falla aquí y no delante de tus usuarios.

Metadatos: lo que crates.io exige y lo que conviene

CampoObligatorioPara qué sirve
descriptionSíLa frase que aparece en la búsqueda; sin ella no se publica.
licenseSíMIT OR Apache-2.0 es la convención del ecosistema.
repository, homepageNoEnlazan desde crates.io y docs.rs al código.
readmeNocrates.io lo renderiza en la portada del crate.
keywordsNoMáximo 5; mejoran la búsqueda.
categoriesNoDeben existir en la lista oficial de crates.io.
rust-versionNoEl MSRV: la versión mínima de Rust que compila el crate.

Semver sin mentir

CambioVersión en 1.xVersión en 0.x
Arreglo compatible1.2.3 → 1.2.40.4.1 → 0.4.2
Función nueva compatible1.2.3 → 1.3.00.4.1 → 0.5.0
Cambio incompatible1.2.3 → 2.0.00.4.1 → 0.5.0

En 0.x, Cargo trata 0.4 y 0.5 como incompatibles: por eso el salto de menor es el que rompe. Mientras urlshort sea 0.x, cada cambio de API sube la segunda cifra; el día que sea 1.0.0, se compromete a no romper sin un 2.0.0.

Qué miran docs.rs y crates.io

docs.rs compila tu crate con la versión estable de Rust, por defecto con las features que declares en [package.metadata.docs.rs]. Si tu documentación tiene un doctest que falla, la build de docs falla y el crate aparece sin documentación. Un doctest no es un adorno: es un test que se ejecuta en docs.rs.

El paquete no es tu repositorio

crates.io sube un .crate (un .tar.gz) con los ficheros que diga include/exclude. Los tests de integración viajan, los target/ y los ficheros ignorados no. Todo lo que el código necesite en tiempo de compilación debe estar dentro; todo lo demás, fuera.

3 · Ejemplo mínimo

Los cuatro campos sin los que crates.io no acepta el paquete, y el comando que lo comprueba sin subir nada:

[package]
name = "urlshort"
version = "0.1.0"
edition = "2021"
description = "Acorta URLs desde la terminal y sírvelas por HTTP"
license = "MIT OR Apache-2.0"
cargo package --list
cargo package

--list enseña qué va a viajar; sin --list, Cargo crea el tarball y lo compila en target/package/urlshort-0.1.0/. Si el crate depende de otro por ruta (path = "../otro"), el empaquetado falla: hay que publicar el otro primero y declarar la versión.

Y el ensayo de publicación, que valida metadatos y tarball sin tocar el registro:

cargo publish --dry-run
warning: manifest has no documentation, homepage or repository
   Packaging urlshort v0.1.0
   Verifying urlshort v0.1.0
   Compiling urlshort v0.1.0
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 4.21s
   Packaged 18 files, 42.1KiB (9.3KiB compressed)
error: aborting due to dry run

Ese aborting due to dry run es el éxito: Cargo ha hecho todo salvo subir. El warning es la pista de que faltan repository, homepage y documentation.

4 · Ejemplo real

El manifiesto completo. include deja fuera los target/ y los ficheros de editor, y dentro lo que el crate necesita para compilar y documentarse.

[package]
name = "urlshort"
version = "0.1.0"
edition = "2021"
rust-version = "1.85"
description = "Acorta URLs desde la terminal y sírvelas por HTTP"
license = "MIT OR Apache-2.0"
repository = "https://github.com/tu-usuario/urlshort"
homepage = "https://github.com/tu-usuario/urlshort"
documentation = "https://docs.rs/urlshort"
readme = "README.md"
keywords = ["url", "shortener", "cli", "axum"]
categories = ["command-line-utilities", "web-programming::http-server"]
include = ["src/**/*", "tests/**/*", "README.md", "LICENSE-*", "Cargo.toml"]

[dependencies]
axum = "0.8"
chrono = "0.4"
clap = { version = "4.6", features = ["derive"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
thiserror = "2"
tokio = { version = "1", features = ["full"] }
tower-http = { version = "0.6", features = ["trace"] }

[dev-dependencies]
tower = { version = "0.5", features = ["util"] }
http-body-util = "0.1"

[profile.release]
strip = true          # sin tabla de símbolos
lto = "thin"          # inlining entre crates
codegen-units = 1     # menos paralelismo, más optimización
panic = "abort"       # sin desenrollado: binario más pequeño

[package.metadata.docs.rs]
all-features = true

[package.metadata.release]
sign-commit = false
tag-name = "v{{version}}"

La documentación empieza por negarse a compilar sin ella. #![deny(missing_docs)] convierte un olvido en un error de build, y el doctest del módulo se ejecuta en cargo test y en docs.rs.

// src/lib.rs
#![deny(missing_docs)]
//! urlshort — un acortador de URLs con CLI y servidor HTTP.
//!
//! El crate expone el dominio, el puerto de persistencia y el caso de uso;
//! el binario añade el CLI y el servidor.
//!
//! ```
//! use std::sync::Arc;
//!
//! use urlshort::service::Service;
//! use urlshort::store::MemoryStore;
//!
//! let service = Service::new(Arc::new(MemoryStore::new()), "https://s.dev");
//! let link = service.short("https://www.rust-lang.org")?;
//! assert!(link.short_url(service.base_url()).starts_with("https://s.dev/"));
//! # Ok::<(), urlshort::error::Error>(())
//! ```
//!
//! ## Ejemplo con fichero
//!
//! ```
//! # use std::sync::Arc;
//! use urlshort::store::{JsonStore, Store};
//! # let dir = std::env::temp_dir();
//! # let path = dir.join("doc-urlshort.json");
//! let store: Arc<dyn Store> = Arc::new(JsonStore::open(&path)?);
//! # std::fs::remove_file(&path).ok();
//! # Ok::<(), urlshort::error::Error>(())
//! ```

/// Dominio: enlaces, validación y generación de códigos.
pub mod domain;
/// El error único del proyecto.
pub mod error;
/// Persistencia: el puerto y sus adaptadores.
pub mod store;
/// Casos de uso.
pub mod service;
/// Servidor HTTP.
pub mod server;
/// Interfaz de línea de comandos.
pub mod cli;

Faltan el README y la licencia, que no son código pero sí parte del paquete. El README explica la instalación en tres líneas; las licencias MIT y Apache-2.0 se incluyen como ficheros y se referencian en license.

cargo login   # pega el token de https://crates.io/settings/tokens
cargo publish --dry-run
cargo publish

Para que el token no acabe en el historial, usa la variable de entorno que lee Cargo:

export CARGO_REGISTRY_TOKEN="$(cat ~/.secrets/crates-io)"; cargo publish

Después de publicar: etiqueta y changelog. cargo-release automatiza subir la versión, commitear, etiquetar y publicar, pero exige que el árbol esté limpio.

cargo install cargo-release
cargo release patch --execute     # 0.1.0 -> 0.1.1
cargo release minor --execute     # 0.1.1 -> 0.2.0 (rompe en 0.x)

Los binarios se distribuyen en GitHub Releases con una matriz de targets. cross compila para arquitecturas distintas de la máquina que ejecuta el job.

jobs:
  release:
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    strategy:
      matrix:
        include:
          - target: x86_64-unknown-linux-gnu
          - target: aarch64-unknown-linux-gnu
            cross: true
          - target: x86_64-pc-windows-msvc
          - target: aarch64-apple-darwin
          - target: x86_64-apple-darwin
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with: { targets: '${{ matrix.target }}' }
      - run: cargo install cross --locked
        if: matrix.cross
      - run: cross build --release --locked --target ${{ matrix.target }}
        if: matrix.cross
      - run: cargo build --release --locked --target ${{ matrix.target }}
        if: '!matrix.cross'
      - uses: softprops/action-gh-release@v2
        with:
          files: target/${{ matrix.target }}/release/urlshort*

Y el contenedor, en dos etapas: una con el toolchain para compilar y otra mínima para ejecutar. El binario enlaza glibc, así que la imagen final debe ser Debian, no Alpine.

FROM rust:1.85 AS build
WORKDIR /app
COPY Cargo.toml Cargo.lock ./
COPY src ./src
RUN cargo build --release --locked

FROM debian:bookworm-slim AS runtime
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates \
 && rm -rf /var/lib/apt/lists/*
RUN useradd --system --uid 10001 urlshort
COPY --from=build /app/target/release/urlshort /usr/local/bin/urlshort
USER urlshort
EXPOSE 3000
ENTRYPOINT ["urlshort", "serve", "--port", "3000"]
docker build -t urlshort:0.1.0 .
docker run --rm -p 3000:3000 urlshort:0.1.0
docker images urlshort --format '{{.Size}}'    # ~85 MB

De 4,2 MB a 1,7 MB

Con el perfil por defecto, un binario de axum ronda los 4 MB. strip = true quita símbolos, lto = "thin" permite inlining entre crates y codegen-units = 1 deja al optimizador ver todo. panic = "abort" recorta otro pellizco, pero rompe catch_unwind y algunos tests que esperan un panic: mide antes de aceptarlo.

El nombre es único y para siempre

Los nombres de crates.io no se liberan: si publicas urlshort y lo borras, el nombre sigue reservado. Comprueba antes con cargo search urlshort. Si está ocupado, elige un nombre con prefijo (tu-usuario-urlshort) o publica el binario solo en GitHub Releases.

6 · Errores habituales

1. Publicar dos veces la misma versión

El error real:

error: failed to publish to registry at https://crates.io
Caused by:
  the remote server responded with an error (status 400 Bad Request):
  crate version `0.1.0` is already uploaded

Por qué: no se puede reemplazar una versión publicada, ni siquiera la tuya. Bien: sube la versión (0.1.1) y publica de nuevo; si la versión está rota, cargo yank --version 0.1.0 impide instalarla sin borrar el código.

2. Metadatos incompletos

Mal: olvidar description o license. El error real: missing or empty metadata fields: description, license. Bien: rellena ambos; con licencia dual, crea LICENSE-MIT y LICENSE-APACHE y referéncialas en el README.

3. Dependencia por ruta

Mal: mi-crate = { path = "../mi-crate" } en el manifiesto que publicas. El error es all dependencies must have a version specified when packaging. Bien: publica primero la dependencia y declara { path = "../mi-crate", version = "0.2" }: la ruta sirve en local, la versión viaja.

4. Un doctest que no compila

Mal: documentar con ```rust un ejemplo que usa un ? sin función que devuelva Result. cargo test falla y docs.rs no genera documentación. Bien: cierra el doctest con # Ok::<(), urlshort::error::Error>(()) o envuelve el ejemplo en una función fn main() -> Result<(), Error>.

7 · Ejercicio guiado

Objetivo: recorrer la escalera completa sin publicar de verdad. Al final tendrás un tarball verificado y una etiqueta local.

  1. Completa los metadatos. Añade description, license, repository y readme; crea un README con instalación, uso y un ejemplo de curl.
  2. Inspecciona el paquete. 
    cargo package --list
# Cargo.toml
# README.md
# src/lib.rs
# src/main.rs
# src/domain.rs
# src/error.rs
# src/store.rs
# src/service.rs
# src/server.rs
# src/cli.rs
# tests/cli.rs
# tests/server.rs

    Si falta un fichero, revisa include/exclude y el .gitignore: Cargo respeta ambos.

  3. Compila el tarball, no tu carpeta. 
    cargo package --allow-dirty
cd target/package/urlshort-0.1.0
cargo test --all-targets

    Aquí se descubren los include mal puestos: el directorio solo contiene lo empaquetado.

  4. Ensaya la publicación. 
    cargo publish --dry-run

    Debe terminar en aborting due to dry run sin errores de metadatos ni de compilación. Si aparece un warning por campos vacíos, rellénalos.

  5. Etiqueta la versión. Con el árbol limpio y los tests en verde: 
    git tag -a v0.1.0 -m "urlshort 0.1.0"
git push origin v0.1.0
git describe --tags

    La etiqueta debe apuntar al mismo commit que se publicó; si publicas desde otro, el código descargado no coincidirá con el que crates.io tiene.

Criterio de éxito

cargo publish --dry-run termina sin errores y target/package/urlshort-0.1.0/ pasa sus propios tests. El día que ejecutes cargo publish de verdad, el único riesgo será el nombre: el resto ya lo has ensayado.

8 · Reto

🎯 Un release reproducible con cargo-dist

Automatiza los binarios: al empujar una etiqueta v*, el workflow debe compilar para Linux x86_64/aarch64, macOS Intel/ARM y Windows, generar un .tar.gz o .zip por target con su checksum, subirlos a la Release y publicar además una imagen en GHCR etiquetada con la versión y con latest.

Requisitos: el binario debe ser reproducible (misma etiqueta, mismos artefactos), la imagen no debe llevar el toolchain, y el job de publicación en crates.io solo debe correr si los tests pasan. ¿Qué orden fijas entre cargo publish, la Release de GitHub y la imagen? ¿Qué haces si crates.io falla después de haber subido los binarios?

Pista: cargo-dist genera el workflow entero a partir de Cargo.toml (dist init), pero no decide el orden. Publicar el crate primero y los binarios después evita releases que apuntan a una versión inexistente. Para GHCR, docker/metadata-action deriva las etiquetas del tag de git; y recuerda que la imagen final debe copiar el binario ya compilado, no volver a compilar dentro de la etapa de runtime.

9 · Resumen

  • El orden es documentar → empaquetar → verificar → publicar → etiquetar → distribuir; saltarse un paso se paga en la siguiente versión.
  • cargo package compila el tarball, que es lo único que verá crates.io; --list enseña qué viaja.
  • description y license son obligatorios; repository, readme, keywords y categories hacen que el crate se encuentre.
  • #![deny(missing_docs)] y un doctest convierten la documentación en parte de la build.
  • cargo publish es irreversible: --dry-run primero y yank solo como retirada, nunca como borrado.
  • En 0.x, subir la segunda cifra es el cambio incompatible; cargo-release automatiza versión, commit y etiqueta.
  • Los binarios van en GitHub Releases con matriz de targets y cross; el contenedor, en dos etapas, Debian y sin toolchain.
  • strip, lto = "thin" y codegen-units = 1 reducen el binario más de la mitad.

10 · Preguntas frecuentes

¿Puedo despublicar una versión?

No. crates.io permite yank, que impide que nuevas instalaciones resuelvan esa versión, pero el código sigue descargable para quien ya la tenía en su Cargo.lock. Es deliberado: borrar rompería builds existentes. Si publicaste algo sensible por error, rota el secreto; el código no desaparece.

¿Necesito publicar el binario y la biblioteca por separado?

No: un crate puede tener [lib] y [[bin]] a la vez, y es lo que hace urlshort. Publicas una vez y cargo install urlshort compila el binario, mientras otros crates pueden usar la biblioteca. Si el binario creciera con dependencias que la biblioteca no necesita, ahí sí separarías en un workspace.

¿Cómo evito que la documentación interna acabe en docs.rs?

Con visibilidad: lo que no es pub no se documenta. Si necesitas un módulo público solo para tests, márcalo #[doc(hidden)] o expón una API mínima. cargo doc --no-deps te enseña exactamente lo que verá el usuario, sin las dependencias.

¿La imagen Docker necesita el mismo Cargo.lock?

Sí, si compilas con --locked. Cópialo antes de src para aprovechar la caché de capas: mientras no cambien las dependencias, Docker reutiliza la capa de compilación. Y no lo generes dentro del contenedor: el lockfile es parte del repositorio y fija las versiones que probaste.
