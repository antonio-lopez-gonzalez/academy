Servidor HTTP y tests

Módulo 7 · Proyecto final ⏱ 45 minutos

1 · Introducción

El Service ya sabe acortar, resolver y borrar. El servidor es una segunda puerta al mismo mostrador: traduce HTTP a llamadas de caso de uso y traduce los errores de vuelta a códigos de estado. Nada de la lógica de urlshort se duplica aquí; si algo se duplica, está en el sitio equivocado.

Con axum 0.8 el servidor cabe en un fichero. Lo difícil no es montarlo: es demostrar que funciona. Un test que abre un puerto, espera y hace peticiones es lento y frágil; el mismo router se puede ejercitar en memoria, sin red, en milisegundos.

¿Por qué existe esta lección?

Porque la diferencia entre «funciona en mi máquina» y «funciona» son los tests de integración. Aquí aprendes a llamar al router como si fueras un cliente HTTP sin abrir un socket, a arrancar uno de verdad en un puerto efímero para probar el cableado, y a comprobar que cincuenta peticiones concurrentes cuentan cincuenta visitas y no cuarenta y nueve.

Al terminar tendrás cuatro rutas (GET /health, POST /links, GET /links/{code}, DELETE /links/{code}), errores como JSON con el estado correcto, ApiError implementando IntoResponse y una batería de tests que corre en CI.

  • Devolver 200 en todo y dejar que el cliente adivine si hubo error.
  • Escribir el error como texto plano en una ruta y como JSON en otra.
  • Testear el servidor solo con curl a mano: nadie lo repetirá en CI.
  • Compartir el store con un Mutex externo y serializar peticiones que solo leen.

2 · Teoría

Un router, cuatro rutas y un estado

Router::with_state(service) entrega una copia del Service a cada handler que lo pida con State<Service>. Como Service es Clone, la copia es un Arc más un String; el estado real (el mapa) sigue compartido dentro del adaptador.

        petición HTTP
             │
             ▼
   ┌───────────────────────┐
   │ Router                │  /health · /links · /links/{code}
   │ layer TraceLayer      │
   └──────────┬────────────┘
              │ State<Service> (copia barata)
   ┌──────────▼────────────┐
   │ handler               │  extrae Path / Json, llama al Service
   └──────────┬────────────┘
              │ Result<T, Error>
   ┌──────────▼────────────┐
   │ ApiError: IntoResponse│  InvalidUrl 400 · NotFound 404
   └───────────────────────┘  Conflict 409 · resto 500
RutaÉxitoFallo típico
GET /health200 con ok—
POST /links201 + Location + JSON del enlace400 URL inválida, 409 sin códigos libres
GET /links/{code}302 + Location a la URL original404 código desconocido
DELETE /links/{code}204 sin cuerpo404 código desconocido

El mapeo vive en impl From<Error> for ApiError: un solo sitio que mirar cuando cambia el contrato. InvalidUrl es culpa del cliente (400), NotFound es 404, Conflict es 409 —el cliente puede reintentar con otra URL— y todo lo demás es 500.

302 y no 200: la diferencia entre redirigir y contar

Un acortador existe para que el navegador vaya a otro sitio. 302 Found con Location es la respuesta clásica: el cliente vuelve a pedir la URL original y la barra de direcciones cambia. 307 conserva el método; 301/308 se cachean y harían difícil cambiar el destino. Aquí usamos StatusCode::FOUND.

Concurrencia: quién protege qué

El trait Store: Send + Sync y el Mutex interno son la única protección. Service se clona por petición; los handlers no comparten nada mutable. MemoryStore y JsonStore serializan sus accesos con std::sync::Mutex, que es correcto porque el candado no se cruza con un .await: se toma, se opera y se suelta dentro de una función síncrona.

Si algún día el adaptador hiciera E/S remota, el candado de std bloquearía un hilo del runtime. Entonces tocaría tokio::sync::Mutex o spawn_blocking. Con un fichero local, el bloqueo es de microsegundos y el diseño simple gana.

3 · Ejemplo mínimo

Un servidor con estado y una ruta, sin dominio. Compila con cargo add axum tokio --features tokio/full.

use axum::{extract::State, routing::get, Json, Router};
use serde_json::{json, Value};

#[derive(Clone)]
struct AppState {
    base_url: String,
}

#[tokio::main]
async fn main() {
    let state = AppState { base_url: "http://localhost:3000".into() };
    let app = Router::new()
        .route("/health", get(health))
        .route("/info", get(info))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

async fn health() -> &'static str {
    "ok"
}

async fn info(State(state): State<AppState>) -> Json<Value> {
    Json(json!({ "base_url": state.base_url }))
}

Las piezas que importan:

  • with_state convierte Router<AppState> en Router<()>, el único que puede servirse.
  • State<AppState> es un extractor: axum clona el estado por petición, por eso debe ser Clone.
  • Json<Value> como retorno fija el Content-Type: application/json sin escribirlo a mano.
  • axum::serve(listener, app) es la forma canónica en 0.8; ya no se usa Server::bind.

4 · Ejemplo real

El server.rs completo. La primera mitad traduce dominio a JSON; la segunda, errores a respuestas HTTP.

// src/server.rs
use std::net::SocketAddr;

use axum::{
    extract::{Path, State},
    http::{header, HeaderValue, StatusCode},
    response::{IntoResponse, Response},
    routing::{get, post},
    Json, Router,
};
use serde::{Deserialize, Serialize};
use tower_http::trace::TraceLayer;

use crate::domain::Link;
use crate::error::Error;
use crate::service::Service;

#[derive(Debug, Deserialize)]
pub struct CreateLink {
    pub url: String,
}

#[derive(Debug, Serialize)]
pub struct LinkResponse {
    pub code: String,
    pub url: String,
    pub short_url: String,
    pub hits: u64,
    pub created_at: String,
}

impl LinkResponse {
    fn new(link: &Link, short_url: String) -> Self {
        Self {
            code: link.code().to_string(),
            url: link.url().to_string(),
            short_url,
            hits: link.hits(),
            created_at: link.created_at().to_string(),
        }
    }
}

pub fn router(service: Service) -> Router {
    Router::new()
        .route("/health", get(health))
        .route("/links", post(create_link))
        .route("/links/{code}", get(resolve_link).delete(delete_link))
        .layer(TraceLayer::new_for_http())
        .with_state(service)
}

pub async fn serve(service: Service, addr: SocketAddr) -> std::io::Result<()> {
    let listener = tokio::net::TcpListener::bind(addr).await?;
    println!("urlshort escuchando en http://{addr}");
    axum::serve(listener, router(service)).await
}

Los cuatro handlers. Fíjate en que ninguno imprime ni registra: devuelven datos o un ApiError, y el middleware decide qué se anota.

async fn health() -> &'static str { "ok" }

async fn create_link(
    State(service): State<Service>,
    Json(body): Json<CreateLink>,
) -> Result<impl IntoResponse, ApiError> {
    let link = service.short(&body.url)?;
    let short_url = link.short_url(service.base_url());
    let location = HeaderValue::from_str(&short_url)
        .map_err(|_| ApiError::internal("la URL corta no es cabecera válida"))?;
    Ok((
        StatusCode::CREATED,
        [(header::LOCATION, location)],
        Json(LinkResponse::new(&link, short_url)),
    ))
}
async fn resolve_link(
    State(service): State<Service>,
    Path(code): Path<String>,
) -> Result<impl IntoResponse, ApiError> {
    let link = service.resolve(&code)?;          // suma una visita
    let location = HeaderValue::from_str(link.url())
        .map_err(|_| ApiError::internal("la URL guardada no es cabecera válida"))?;
    Ok((StatusCode::FOUND, [(header::LOCATION, location)]))
}
async fn delete_link(
    State(service): State<Service>,
    Path(code): Path<String>,
) -> Result<StatusCode, ApiError> {
    service.delete(&code)?;
    Ok(StatusCode::NO_CONTENT)
}

El error HTTP es una estructura, no un String. El mapeo desde Error es la única tabla de traducción del proyecto, y los detalles internos no salen al cliente.

pub struct ApiError {
    status: StatusCode,
    message: String,
}

impl ApiError {
    fn internal(message: impl Into<String>) -> Self {
        Self { status: StatusCode::INTERNAL_SERVER_ERROR, message: message.into() }
    }
}

impl From<Error> for ApiError {
    fn from(err: Error) -> Self {
        let status = match &err {
            Error::InvalidUrl(_) => StatusCode::BAD_REQUEST,
            Error::NotFound(_) => StatusCode::NOT_FOUND,
            Error::Conflict(_) => StatusCode::CONFLICT,
            _ => StatusCode::INTERNAL_SERVER_ERROR,
        };
        // Un 500 no cuenta al cliente si el disco falló: se registra y se dice poco.
        let message = if status == StatusCode::INTERNAL_SERVER_ERROR {
            "error interno".to_string()
        } else {
            err.to_string()
        };
        Self { status, message }
    }
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        (self.status, Json(serde_json::json!({ "error": self.message }))).into_response()
    }
}

TraceLayer no imprime por artefacto

TraceLayer::new_for_http() emite eventos de tracing. Sin un tracing-subscriber instalado no verás nada: añade tracing-subscriber con la feature env-filter y llama a fmt().with_env_filter(…).init() en main. El middleware ya está en su sitio; falta enchufar la salida.

Un 409 también es un contrato

Conflict al crear un enlace significa «no hay código libre». Es raro, pero si ocurre el cliente debe poder distinguirlo de un 500 y reintentar. Documenta cada estado en el README: los estados son parte de la API, igual que los campos del JSON.

6 · Errores habituales

1. Usar :code en axum 0.8

let app = Router::new().route("/links/:code", get(resolve_link));

El error real no es de compilación: es un panic al construir el router.

thread 'main' panicked at ...:
Invalid route: `:code` is not a valid path segment.
Path segments must be enclosed in braces, e.g. `/links/{code}`

Por qué: axum 0.8 cambió la sintaxis para alinearse con matchit 0.8. Bien: /links/{code}. El Path<String> del handler no cambia.

2. Olvidar with_state

let app = Router::new().route("/links", post(create_link));   // falta el estado
axum::serve(listener, app).await.unwrap();

El error real: error[E0277]: the trait bound `Router<Service>: Service<…>` is not satisfied, con la nota «the trait Service is implemented for Router<()>». Por qué: solo Router<()> puede servirse; mientras falte estado, el tipo lo dice. Bien: .with_state(service) al final de la cadena.

3. Devolver 200 con el error dentro

Mal: Ok(Json(json!({ "error": "no existe" }))). El cliente tiene que leer el cuerpo para saber si fue bien y los reintentos automáticos no funcionan. Bien: Err(ApiError::from(Error::NotFound(code))) y el IntoResponse pone el 404.

7 · Ejercicio guiado

Objetivo: cubrir el router con tests que no abren puerto y uno que sí, más una prueba de concurrencia. Todo en tests/server.rs.

  1. Prepara el servicio de prueba. MemoryStore detrás de un Arc; el Service es Clone, así que puedes conservar una copia para inspeccionar el estado. 
    use std::sync::Arc;

use axum::body::Body;
use axum::http::{header, Request, StatusCode};
use tower::ServiceExt;
use urlshort::server::router;
use urlshort::service::Service;
use urlshort::store::MemoryStore;

fn service() -> Service {
    Service::new(Arc::new(MemoryStore::new()), "http://localhost:3000")
}
  2. Prueba el alta y la redirección. oneshot consume el router; clónalo si necesitas otra petición. 
    #[tokio::test]
async fn post_devuelve_201_y_location() {
    let app = router(service());
    let response = app.oneshot(
        Request::post("/links")
            .header(header::CONTENT_TYPE, "application/json")
            .body(Body::from(r#"{"url":"https://www.rust-lang.org"}"#))
            .unwrap(),
    ).await.unwrap();

    assert_eq!(response.status(), StatusCode::CREATED);
    let location = response.headers()[header::LOCATION].to_str().unwrap();
    assert!(location.starts_with("http://localhost:3000/"));
}

#[tokio::test]
async fn get_redirige_y_cuenta_la_visita() {
    let service = service();
    let code = service.short("https://example.com").unwrap().code().to_string();
    let app = router(service.clone());

    let response = app
        .oneshot(Request::get(format!("/links/{code}")).body(Body::empty()).unwrap())
        .await.unwrap();

    assert_eq!(response.status(), StatusCode::FOUND);
    assert_eq!(response.headers()[header::LOCATION].to_str().unwrap(), "https://example.com");
    assert_eq!(service.list().unwrap()[0].hits(), 1);
}
  3. Arranca un puerto real, una vez. Puerto 0: el sistema elige uno libre y lo lees con local_addr. 
    #[tokio::test]
async fn responde_en_un_puerto_efimero() {
    use tokio::io::{AsyncReadExt, AsyncWriteExt};

    let listener = tokio::net::TcpListener::bind("127.0.0.1:0").await.unwrap();
    let addr = listener.local_addr().unwrap();
    tokio::spawn(async move { axum::serve(listener, router(service())).await.unwrap() });

    let mut stream = tokio::net::TcpStream::connect(addr).await.unwrap();
    stream.write_all(b"GET /health HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n")
        .await.unwrap();
    let mut raw = String::new();
    stream.read_to_string(&mut raw).await.unwrap();
    assert!(raw.starts_with("HTTP/1.1 200"));
}
  4. Prueba la concurrencia. Cincuenta tareas resuelven el mismo código; el contador debe sumar exactamente cincuenta, sin incrementos perdidos. 
    #[tokio::test(flavor = "multi_thread", worker_threads = 4)]
async fn cincuenta_visitas_suman_cincuenta() {
    let service = service();
    let code = service.short("https://example.com").unwrap().code().to_string();

    let mut handles = Vec::new();
    for _ in 0..50 {
        let service = service.clone();
        let code = code.clone();
        handles.push(tokio::spawn(async move { service.resolve(&code).unwrap() }));
    }
    for handle in handles { handle.await.unwrap(); }

    assert_eq!(service.list().unwrap()[0].hits(), 50);
}
  5. Pasa todo y añade CI. cargo test --all-targets y cargo clippy --all-targets -- -D warnings en local; después, el mismo contrato en GitHub Actions.

Criterio de éxito

Puedes romper una ruta (/links/{code} por /link/{code}) y ver fallar exactamente los tests que la usan, mientras el resto sigue en verde. Eso es una suite que localiza el fallo, no una que se cae entera.

8 · Reto

🎯 Enlaces caducados que responden 410

Con la caducidad del reto anterior, un código vencido ya no existe para el dominio, pero un cliente HTTP merece saber que existía y ya no: 410 Gone. Añade GET /links/{code} con esa distinción y un test que lo demuestre.

Restricciones: el dominio no debe importar axum; el mapeo vive en server.rs; el 410 debe incluir el mismo cuerpo JSON de error que el 404; y list no debe mostrar los caducados. ¿Creas una variante nueva en Error o reutilizas NotFound con un mensaje distinto? ¿Qué pasa con los hits de un enlace caducado?

Pista: si el dominio devuelve NotFound para ambos casos, la capa HTTP no puede distinguirlos sin mirar el mensaje, y eso es frágil. Una variante explícita (Error::Expired) mantiene el match exhaustivo: el compilador te obligará a mapearla en todos los adaptadores. Y no olvides que el reto de la lección 01 ya tocó el reloj: reutiliza esa decisión.

9 · Resumen

  • router(service) monta cuatro rutas y entrega el estado con with_state; los handlers reciben State<Service>.
  • En axum 0.8 los parámetros van con llaves: /links/{code}, nunca :code.
  • POST /links responde 201 con Location y el enlace; GET responde 302 o 404; DELETE, 204 o 404.
  • ApiError implementa IntoResponse y traduce Error a 400/404/409/500 en un solo sitio.
  • oneshot prueba el router sin red; un puerto efímero (:0) prueba el cableado real.
  • Un test multi-hilo con cincuenta tareas demuestra que el Mutex del adaptador no pierde incrementos.
  • CI repite fmt, clippy -D warnings y test --all-targets en cada PR.

10 · Preguntas frecuentes

¿Por qué 302 y no 301?

Porque un 301 es permanente y los navegadores lo cachean: si mañana cambias el destino del mismo código, algunos clientes seguirán yendo al viejo. El 302 (y el 307, que conserva el método) se consultan cada vez. Para un acortador, la flexibilidad vale más que ahorrar una petición.

¿El Service debería ser un Arc<Service> en el estado?

No hace falta: Service ya es Clone y clonarlo copia un Arc<dyn Store>, no el store. State<Service> es más simple y el router no acumula genéricos. Si el servicio tuviera un campo caro de clonar (un pool sin Arc), entonces sí envolverías en Arc.

¿Cómo pruebo que el cuerpo del error es JSON?

Con http_body_util::BodyExt: response.into_body().collect().await?.to_bytes() y luego serde_json::from_slice. Merece la pena en uno o dos tests, no en todos: el contrato importante es el estado y el Content-Type; el texto exacto del mensaje cambia más a menudo.

¿Y si quiero HTTPS?

En producción lo normal es terminar TLS en un proxy (nginx, Caddy, el balanceador del cloud) y servir HTTP en la red interna. Hacer TLS en el proceso exige axum-server con rustls y gestionar certificados; para urlshort es complejidad que no demuestra nada del lenguaje. Documenta que el binario escucha en 127.0.0.1 por defecto.
