Enums, Option, Result y pattern matching

Módulo 2 · Tipos y abstracciones ⏱ 45 minutos

1 · Introducción

Un struct dice «esto tiene todas estas piezas». Un enum dice «esto es una de estas variantes». La diferencia parece académica hasta que modelas estados: un código de urlshort está activo, caducado o borrado, y nunca dos cosas a la vez. Un struct con tres booleanos permite 8 combinaciones, de las cuales 5 no significan nada. Un enum permite exactamente 3. Y los dos enums más importantes de Rust no los escribes tú: Option<T> sustituye a null y Result<T, E> a las excepciones; ambos son enums normales y el compilador te obliga a tratar todas sus variantes. Esa obligación es la razón por la que en Rust no existe el «null pointer exception».

¿Por qué existe esta lección?

Porque el patrón que vas a usar en todo el curso es hacer imposible el estado inválido. En urlshort, un código no puede estar «borrado y activo»; una resolución no puede devolver «URL o nada» sin decir por qué. Los enums con datos y match convierten esas reglas de negocio en algo que el compilador verifica por ti.

Errores típicos al empezar: modelar estados con bool y String y olvidar combinaciones; usar unwrap() en vez de decidir qué hacer con la ausencia; añadir _ al match por pereza; y comparar un Option<T> con un T como si el envoltorio no existiera.

2 · Teoría

Una suma de variantes, no una jerarquía

Cada variante puede llevar datos, y cada una puede llevar datos distintos. No hay herencia: hay una lista cerrada de formas posibles, y el compilador la conoce para comprobar el match.

#[derive(Debug, Clone, PartialEq, Eq)]
enum Event {
    Created(Link),                              // variante de tupla: un dato
    Resolved { code: String, at: u64 },         // variante con campos
    Deleted,                                    // variante unitaria
}

En memoria, un enum es una etiqueta (discriminante) más el espacio de la variante más grande. Solo una variante está activa; las demás no existen en ese valor. Rust optimiza el espacio cuando un tipo tiene valores imposibles, como verás con Option<&T>.

  Event (la variante más grande es Resolved)
  ┌──────────┬──────────────────────────────────────┐
  │ tag = 0  │ Created(Link)                        │
  ├──────────┼──────────────────────────────────────┤
  │ tag = 1  │ Resolved { code: String, at: u64 }   │
  ├──────────┼──────────────────────────────────────┤
  │ tag = 2  │ Deleted  (sin carga útil)            │
  └──────────┴──────────────────────────────────────┘
  tamaño = discriminante + max(variantes), con alineación

Option<T>: la ausencia es un dato

Option<T> es Some(T) o None. No hay null, ni valores «vacíos» por convención, ni un 0 que significa «no hay». Si una función puede no devolver nada, su firma lo dice: fn find_link(links: &[Link], code: &str) -> Option<&Link>. El compilador no te deja usar el &Link sin abrir el envoltorio. Y Option<&T> ocupa lo mismo que un puntero: el valor «puntero nulo», imposible en un &T válido, representa None. Cero coste.

CombinadorQué haceCuándo
unwrap_or(0)Extrae o usa un defecto constanteEl defecto es barato
unwrap_or_else(|| ...)Extrae o calcula el defecto con una closureEl defecto es caro o depende del contexto

and_then(|v| ...)Encadena otra operación que también devuelve OptionVarios pasos que pueden faltar

Option no es un error: es información. Un 404 no es un fallo del programa; es un resultado posible del dominio.

Result<T, E>: el fallo también se tipa

Result es Ok(T) o Err(E). La diferencia con Option es que el fallo lleva datos: qué código no se encontró, por qué caducó, qué línea está corrupta. Frente a las excepciones, el error es parte de la firma y no puede escapar sin que alguien lo trate: nada de unwinding oculto, solo un valor de retorno normal, como en fn resolve<'a>(links: &'a [Link], code: &str) -> Result<&'a Link, ResolveError>.

match: exhaustivo por contrato

match state {
    CodeState::Active => 200,
    CodeState::Expired { .. } => 410,
    CodeState::Deleted => 404,
}

// Patrones o y rangos también valen:
match code.chars().next() {
    Some('2'..='9') | Some('a'..='z') => println!("válido"),
    _ => println!("inválido"),
}

Los patrones se prueban de arriba abajo y deben cubrir todos los casos. Puedes enlazar datos (Some(at)), añadir guardas con if y combinar con |. El comodín _ cubre lo que falte, pero apaga la protección: si mañana añades una variante, el match con _ compilará y hará lo incorrecto.

Las formas cortas del match

// if let: solo me interesa una variante
if let Some(at) = link.expires_at {
    println!("caduca en {at}");
}

// let else: la variante feliz o salgo de la función (Rust 1.65+)
let Some(link) = find_link(&links, code) else {
    return Err(ResolveError::NotFound { code: code.to_owned() });
};

// while let: consumir mientras haya
let mut pending = vec![1, 2, 3];
while let Some(top) = pending.pop() {
    println!("{top}");
}

// matches!: un booleano sin desenvolver el valor
if matches!(state, CodeState::Expired { .. }) {
    println!("hay que pedir una URL nueva");
}

#[non_exhaustive]: pensar en el futuro

Añadir una variante a un enum público rompe a todos los que hicieron un match exhaustivo. #[non_exhaustive] (por ejemplo, sobre pub enum StoreError { Io(String), Duplicate(String) }) obliga a los consumidores a incluir _ y te deja crecer sin romper semver. Solo se aplica en el crate que define el tipo.

3 · Ejemplo mínimo

Tres variantes, un match exhaustivo y un Option. Compila tal cual:

#[derive(Debug, Clone, PartialEq, Eq)]
enum CodeState {
    Active,
    Expired { since: u64 },
    Deleted,
}

fn http_status(state: &CodeState) -> u16 {
    match state {
        CodeState::Active => 200,
        CodeState::Expired { .. } => 410,
        CodeState::Deleted => 404,
    }
}

fn main() {
    let states = [
        CodeState::Active,
        CodeState::Expired { since: 1_699_999_000 },
        CodeState::Deleted,
    ];
    for state in &states {
        println!("{state:?} -> {}", http_status(state));
    }

    let expires: Option<u64> = None;
    if let Some(at) = expires {
        println!("caduca en {at}");
    } else {
        println!("sin caducidad");
    }
}

Qué mirar:

  • CodeState::Expired { .. } ignora since cuando no hace falta: los puntos suspensivos son de campos, no de variante. Y expires es Copy porque Option<u64> lo es; con Option<Link> el if let lo movería.

4 · Ejemplo real

Resolver un código en urlshort puede acabar en URL, en «no existe» o en «existió pero ya no sirve». El tipo de retorno lo dice todo y el match obliga a tratar cada caso:

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Link {
    pub code: String,
    pub url: String,
    pub created_at: u64,
    pub expires_at: Option<u64>,
    pub hits: u64,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum CodeState {
    Active,
    Expired { since: u64 },
    Deleted,
}

impl CodeState {
    pub fn http_status(&self) -> u16 {
        match self {
            CodeState::Active => 200,
            CodeState::Expired { .. } => 410,   // Gone
            CodeState::Deleted => 404,           // Not Found
        }
    }
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum ResolveError {
    NotFound { code: String },
    Gone { code: String, state: CodeState },
}

/// Calcula el estado sin tocar el almacenamiento.
pub fn state_of(link: &Link, now: u64, deleted: &[&str]) -> CodeState {
    if deleted.contains(&link.code.as_str()) {
        CodeState::Deleted
    } else {
        match link.expires_at {
            Some(at) if at <= now => CodeState::Expired { since: at },
            _ => CodeState::Active,
        }
    }
}

pub fn resolve<'a>(links: &'a [Link], code: &str, now: u64, deleted: &[&str])
    -> Result<&'a Link, ResolveError> {
    let link = links.iter().find(|l| l.code == code)
        .ok_or_else(|| ResolveError::NotFound { code: code.to_owned() })?;

    match state_of(link, now, deleted) {
        CodeState::Active => Ok(link),
        state => Err(ResolveError::Gone { code: code.to_owned(), state }),
    }
}

fn main() {
    let now = 1_700_000_000;
    let links = vec![
        Link { code: "abc234".into(), url: "https://rust-lang.org".into(),
               created_at: now - 60, expires_at: None, hits: 3 },
        Link { code: "old999".into(), url: "https://example.com/viejo".into(),
               created_at: now - 86_400, expires_at: Some(now - 10), hits: 7 },
        Link { code: "del000".into(), url: "https://example.com/borrado".into(),
               created_at: now - 100, expires_at: None, hits: 1 },
    ];

    for code in ["abc234", "old999", "del000", "noexis"] {
        match resolve(&links, code, now, &["del000"]) {
            Ok(link) => println!("/{code} 200 -> {}", link.url),
            Err(ResolveError::NotFound { .. }) => println!("/{code} 404"),
            Err(ResolveError::Gone { state, .. }) => {
                println!("/{code} {} ({state:?})", state.http_status())
            }
        }
    }
}

Salida:

/abc234 200 -> https://rust-lang.org
/old999 410 (Expired { since: 1699999990 })
/del000 404 (Deleted)
/noexis 404
DecisiónPor qué
expires_at: Option<u64>«Sin caducidad» es distinto de «caduca en 1970». Un 0 centinela sería una bomba.
ResolveError con datosEl llamador puede mostrar el código y el motivo; un String genérico perdería estructura.
state => Err(...) en el último brazoAgrupa los estados no activos sin renunciar a la exhaustividad: solo hay tres variantes; y ok_or_else + ? convierte la ausencia en error (módulo 3).

Regla de oro

Si te ves escribiendo un comentario que dice «si deleted es true, ignora expires_at», ese comentario es un enum que aún no has escrito. Las reglas de precedencia entre campos son síntoma de un tipo mal modelado.

6 · Errores habituales

1. Olvidar una variante en el match

match state {
    CodeState::Active => 200,
    CodeState::Expired { .. } => 410,
}
error[E0004]: non-exhaustive patterns: `CodeState::Deleted` not covered
  --> src/main.rs:15:11
   |
15 |     match state {
   |           ^^^^^ pattern `CodeState::Deleted` not covered
   |
   = note: `CodeState` defined here; the matched value is of type `&CodeState`

Por qué: un match no es un switch con default opcional. Si el valor puede ser Deleted, el código debe decir qué hacer. Bien: añade el brazo, o cubre el resto con un patrón concreto como state => ....

2. Comparar un Option con el valor interior

if link.expires_at < now {
    println!("caducado");
}
error[E0308]: mismatched types
  --> src/main.rs:20:26
   |
20 |     if link.expires_at < now {
   |        ---------------   ^^^ expected `Option<u64>`, found `u64`
   |        |
   |        expected because of this

Por qué: Option<u64> no se compara con u64: el envoltorio es parte del tipo. Bien: link.expires_at.is_some_and(|at| at < now) o un match con guarda. Cuidado también con el else de let ... else: debe divergir (return, break, continue o panic!); si no, el compilador rechaza el bloque.

7 · Ejercicio guiado

Objetivo: modelar el estado de un código con un enum, calcularlo con precedencia explícita y probarlo con matches!. Criterio: tres tests en verde.

  1. Crea el proyecto. 
    cargo new urlshort-state --lib
cd urlshort-state
  2. Modela el dominio en src/lib.rs. deleted y expires_at son datos; el estado es un enum calculado: una sola fuente de verdad. 
    #[derive(Debug, Clone, PartialEq, Eq)]
pub struct Link {
    pub code: String,
    pub expires_at: Option<u64>,
    pub deleted: bool,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum CodeState {
    Active,
    Expired { since: u64 },
    Deleted,
}

pub fn state_of(link: &Link, now: u64) -> CodeState {
    if link.deleted {
        return CodeState::Deleted;
    }
    match link.expires_at {
        Some(at) if at <= now => CodeState::Expired { since: at },
        _ => CodeState::Active,
    }
}
  3. Añade los tests. El tercero comprueba la precedencia: borrado gana a caducado. 
    #[cfg(test)]
mod tests {
    use super::*;

    fn link(expires_at: Option<u64>) -> Link {
        Link { code: "abc234".into(), expires_at, deleted: false }
    }

    #[test]
    fn sin_caducidad_esta_activo() {
        assert_eq!(state_of(&link(None), 1_000), CodeState::Active);
    }

    #[test]
    fn caducado_guarda_el_instante() {
        let state = state_of(&link(Some(900)), 1_000);
        assert_eq!(state, CodeState::Expired { since: 900 });
        assert!(matches!(state, CodeState::Expired { .. }));
    }

    #[test]
    fn borrado_gana_a_caducado() {
        let mut l = link(Some(900));
        l.deleted = true;
        assert_eq!(state_of(&l, 1_000), CodeState::Deleted);
    }
}
  4. Ejecuta. 
    cargo test
    running 3 tests
test result: ok. 3 passed; 0 failed; 0 ignored
  5. Añade una variante y observa. Agrega CodeState::Pending al enum y compila. Verás un E0004 en state_of y otro en cada match que no la contemple. Ese dolor es la característica: el compilador te obliga a decidir qué significa el estado nuevo en cada sitio.

8 · Reto

🎯 Replay de eventos

El estado de un enlace no se guarda: se deriva de los eventos que le han ocurrido. Es el patrón event sourcing en miniatura.

Define enum Event { Created { code: String, url: String, at: u64, expires_at: Option<u64> }, Resolved { code: String, at: u64 }, Deleted { code: String, at: u64 } } y fn apply(links: &mut Vec<Link>, event: Event) -> Result<(), DomainError> que:

  • Cree el enlace en Created y falle con DomainError::Duplicate si el código ya existe.
  • Incremente hits en Resolved y falle con DomainError::NotFound si no existe.
  • Marque como borrado en Deleted (sin eliminar el registro) y falle con DomainError::AlreadyDeleted si se repite.
  • Rechace Resolved sobre un enlace caducado con DomainError::Expired { since }.

Después, escribe un test que aplique cinco eventos y compruebe el estado final con assert_eq! y matches!.

Pista: un solo match sobre event dentro de apply mantiene la lógica junta. Y si un estado es imposible de alcanzar, pregúntate si el enum Event debería impedirlo en lugar de devolver un error en ejecución.

9 · Resumen

  • Un enum es una de varias variantes, cada una con sus propios datos; el compilador conoce la lista completa.
  • Option<T> sustituye a null y Result<T, E> a las excepciones: ausencia y fallo pasan a ser valores tipados.
  • match es exhaustivo; _ compila pero apaga la protección ante variantes nuevas.
  • if let, let else, while let y matches! son las formas cortas del match.
  • Modela estados con enums, no con booleanos: el estado inválido deja de existir.

Comandos y conceptos de esta lección

ComandoQué hace

10 · Preguntas frecuentes

¿Cuándo devuelvo Option y cuándo Result?

Option cuando la ausencia es una respuesta normal y no hay nada más que contar: buscar un código que no está, un campo opcional, un get de un mapa. Result cuando hay un fallo con causa o el llamador necesita distinguir motivos: caducado, borrado, fichero corrupto. Si te ves devolviendo Option<String> donde el texto es un mensaje de error, en realidad querías Result.

¿Por qué Rust no tiene null?

Porque un null es un valor de cualquier tipo que no es de ese tipo, y el compilador no puede impedir que lo uses. Option<T> mete la ausencia en el sistema de tipos: para llegar al T hay que abrir el envoltorio, y abrirlo obliga a considerar None. En Option<&T> ni siquiera hay coste de memoria.

¿_ en un match es mala práctica?

Depende del tipo. En un enum de tu dominio, _ esconde el día en que añadas una variante: el código seguirá compilando con un comportamiento quizá incorrecto. En un valor ajeno y muy amplio (u8, un enum de una librería con #[non_exhaustive]) es la única opción razonable. Regla: sin _ en lo tuyo, con _ en lo ajeno.

¿unwrap() está prohibido?

En producción, casi siempre. Un unwrap es un panic! con la entrada equivocada, y en un servidor eso puede tumbar una tarea o el proceso. Está bien en tests, en prototipos y cuando acabas de demostrar con una comprobación previa que el valor existe. Si la ausencia es un bug, expect("mensaje") al menos explica qué se esperaba.
