Traits, generics y trait bounds

Módulo 2 · Tipos y abstracciones ⏱ 45 minutos

1 · Introducción

Ya tienes datos con comportamiento (impl Link) y estados imposibles de representar mal (enums). Falta la pieza que permite escribir código una vez y usarlo con muchos tipos: los traits. Un trait es un contrato: una lista de métodos que un tipo promete cumplir. No hay herencia; hay implementaciones explícitas.

Los genéricos son la otra cara: una función fn top<T: Clone + Ord>(items: &[T]) sirve para enteros, cadenas o fechas sin duplicar código, y el compilador genera una versión especializada por tipo. Es abstracción con coste cero: en el binario no queda ninguna comprobación dinámica.

¿Por qué existe esta lección?

Porque urlshort necesita guardar enlaces y no quieres que el resto del código sepa si están en memoria, en un fichero JSON o mañana en SQLite. El trait Store es esa frontera: el dominio define qué necesita y cada implementación decide cómo. Es la diferencia entre un programa que crece y uno que hay que reescribir al cambiar el almacenamiento.

Errores típicos al empezar: usar dyn Trait para todo y pagar una llamada indirecta cuando un genérico bastaba; olvidar el use del trait y encontrarse un E0599; chocar con la orphan rule; y poner cinco bounds en la firma cuando el where lo haría legible.

2 · Teoría

Un trait es un contrato, no una clase base

El trait declara métodos y cada tipo decide cómo cumplirlos. Puede haber métodos por defecto que usan los demás y que el implementador sobrescribe si quiere. Self es el tipo que implementa.

trait Saludar {
    fn nombre(&self) -> &str;
    fn saludo(&self) -> String {
        format!("Hola, {}", self.nombre())
    }
}

impl Saludar for Link {
    fn nombre(&self) -> &str { &self.code }
}

Genéricos: el mismo código, tipos distintos

fn top<T: Clone + Ord>(items: &[T], n: usize) -> Vec<T> {
    let mut sorted = items.to_vec();
    sorted.sort();
    sorted.truncate(n);
    sorted
}

Los bounds son lo que permite llamar a sort o format! dentro del cuerpo: sin Ord el compilador no sabe ordenar, sin Display no sabe imprimir. where hace lo mismo que los : de la firma, pero deja leerla cuando hay tres bounds o vidas.

impl Trait: azúcar para genéricos

Como parámetro, &impl Saludar equivale a <S: Saludar>(item: &S). Como retorno, -> impl Iterator<Item = &str> significa «devuelvo un tipo concreto que cumple esto, pero no revelo cuál»: el compilador lo conoce y monomorfiza igual. Es la forma cómoda de devolver iteradores y closures sin nombrar sus tipos infinitos.

dyn Trait: despacho dinámico

Para una colección de tipos distintos que comparten trait, o un campo cuyo tipo exacto se decide en ejecución, usas un objeto trait: &dyn Trait o Box<dyn Trait>. El valor lleva un puntero a los datos y otro a la tabla de métodos (vtable); cada llamada es un salto indirecto.

Genérico T: TraitObjeto dyn Trait
ResoluciónEn compilación (estática)En ejecución (vtable)
RendimientoIgual que el código especializadoUn salto indirecto por llamada
RequisitoEl tipo se conoce al compilarEl trait debe ser object safe

Un trait no es object safe si tiene métodos genéricos o devuelve Self sin Sized. Regla práctica: genérico por defecto, dyn cuando necesites heterogeneidad o menos binario.

Box<dyn Error> y los traits de la std

Box<dyn Error> acepta cualquier error y permite ? con conversión automática; es cómodo en el borde del programa, no en la API de una librería. De la std implementarás sobre todo Display (formato de usuario), From<T> (conversión de ?), Iterator (recorrer tu estructura) y Default (valor neutro).

Coherencia y monomorfización

La orphan rule exige que el trait o el tipo sean locales: impl Display for Vec<Link> no compila porque ambos son ajenos; un newtype local lo resuelve. Y la monomorfización es lo que hace real el coste cero: el compilador genera una copia del genérico por cada tipo usado.

  fn print_all<T: Display>(items: &[T])
        ├──► print_all::<Link>     código especializado
        ├──► print_all::<String>   código especializado
        └──► print_all::<u64>      código especializado
  mismas instrucciones que a mano · más tamaño de binario

3 · Ejemplo mínimo

Un trait con método por defecto, dos implementaciones y los dos despachos en el mismo programa:

trait Saludar {
    fn nombre(&self) -> &str;
    fn saludo(&self) -> String { format!("Hola, {}", self.nombre()) }
}

struct Persona { nombre: String }
struct Robot { id: u32 }

impl Saludar for Persona {
    fn nombre(&self) -> &str { &self.nombre }
}

impl Saludar for Robot {
    fn nombre(&self) -> &str { "unidad" }
    fn saludo(&self) -> String { format!("PING {}", self.id) }
}

fn presentar(item: &impl Saludar) {
    println!("{}", item.saludo());
}

fn main() {
    let gente: Vec<Box<dyn Saludar>> = vec![
        Box::new(Persona { nombre: String::from("Ana") }),
        Box::new(Robot { id: 7 }),
    ];
    for item in &gente {
        presentar(&**item);
    }
}

&**item convierte &Box<dyn Saludar> en &dyn Saludar: presentar usa despacho estático y la colección, dinámico.

4 · Ejemplo real

El trait Store es la frontera de urlshort. JsonFileStore usa un fichero JSONL (un objeto por línea) para no adelantar dependencias del módulo 4:

use std::error::Error;
use std::fmt;
use std::fs;
use std::path::{Path, PathBuf};

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Link {
    pub code: String,
    pub url: String,
    pub created_at: u64,
    pub hits: u64,
}

#[derive(Debug)]
pub enum StoreError { Io(String), Duplicate(String), Corrupt(String) }

impl fmt::Display for StoreError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            StoreError::Io(msg) => write!(f, "E/S: {msg}"),
            StoreError::Duplicate(code) => write!(f, "el código /{code} ya existe"),
            StoreError::Corrupt(line) => write!(f, "línea corrupta: {line}"),
        }
    }
}

fn io_err(err: std::io::Error) -> StoreError { StoreError::Io(err.to_string()) }

impl Error for StoreError {}

pub trait Store {
    fn insert(&mut self, link: Link) -> Result<(), StoreError>;
    fn get(&self, code: &str) -> Option<&Link>;
    fn list(&self) -> Vec<&Link>;

    /// Método por defecto: cuenta sin que cada implementación lo escriba.
    fn count(&self) -> usize { self.list().len() }
}

#[derive(Default)]
pub struct MemoryStore { links: Vec<Link> }

impl Store for MemoryStore {
    fn insert(&mut self, link: Link) -> Result<(), StoreError> {
        if self.get(&link.code).is_some() {
            return Err(StoreError::Duplicate(link.code));
        }
        self.links.push(link);
        Ok(())
    }
    fn get(&self, code: &str) -> Option<&Link> {
        self.links.iter().find(|l| l.code == code)
    }
    fn list(&self) -> Vec<&Link> { self.links.iter().collect() }
}

pub struct JsonFileStore { path: PathBuf, links: Vec<Link> }

impl JsonFileStore {
    pub fn open(path: impl AsRef<Path>) -> Result<Self, StoreError> {
        let path = path.as_ref().to_path_buf();
        let mut store = Self { path, links: Vec::new() };
        if store.path.exists() {
            store.links = store.load()?;
        }
        Ok(store)
    }
    fn load(&self) -> Result<Vec<Link>, StoreError> {
        let raw = fs::read_to_string(&self.path).map_err(io_err)?;
        raw.lines().filter(|l| !l.trim().is_empty()).map(parse_line).collect()
    }
    fn flush(&self) -> Result<(), StoreError> {
        let body: String = self.links.iter().map(|l| to_line(l) + "\n").collect();
        fs::write(&self.path, body).map_err(io_err)?;
        Ok(())
    }
}

impl Store for JsonFileStore {
    fn insert(&mut self, link: Link) -> Result<(), StoreError> {
        if self.links.iter().any(|l| l.code == link.code) {
            return Err(StoreError::Duplicate(link.code));
        }
        self.links.push(link);
        self.flush()
    }
    fn get(&self, code: &str) -> Option<&Link> {
        self.links.iter().find(|l| l.code == code)
    }
    fn list(&self) -> Vec<&Link> { self.links.iter().collect() }
}

fn to_line(link: &Link) -> String {
    format!(r#"{{"code":"{}","url":"{}","created_at":{},"hits":{}}}"#,
            link.code, link.url, link.created_at, link.hits)
}

/// Parser mínimo del formato que escribe `to_line`. Serde lo sustituirá.
fn parse_line(line: &str) -> Result<Link, StoreError> {
    let parts: Vec<&str> = line.split('"').collect();
    let bad = || StoreError::Corrupt(line.to_string());
    if parts.len() < 16 {
        return Err(bad());
    }
    let num = |raw: &str| raw.trim_matches(|c: char| !c.is_ascii_digit()).parse::<u64>();
    Ok(Link {
        code: parts[3].to_string(),
        url: parts[7].to_string(),
        created_at: num(parts[11]).map_err(|_| bad())?,
        hits: num(parts[15]).map_err(|_| bad())?,
    })
}

fn newest<S: Store>(store: &S, n: usize) -> Vec<&Link> {
    let mut all = store.list();
    all.sort_by(|a, b| b.created_at.cmp(&a.created_at));
    all.into_iter().take(n).collect()
}

fn publish(store: &mut dyn Store, link: Link) -> Result<(), StoreError> {
    store.insert(link)
}

fn run() -> Result<(), Box<dyn Error>> {
    let mut store = JsonFileStore::open("links.jsonl")?;
    let link = Link { code: "abc234".into(), url: "https://rust-lang.org".into(),
                      created_at: 3, hits: 0 };
    publish(&mut store, link)?;
    println!("memoria: {} enlaces", MemoryStore::default().count());
    for l in newest(&store, 3) {
        println!("/{} -> {}", l.code, l.url);
    }
    Ok(())
}

fn main() {
    if let Err(err) = run() { eprintln!("error: {err}"); }
}

Salida en la primera ejecución (la segunda fallará con Duplicate si no borras links.jsonl):

memoria: 0 enlaces
/abc234 -> https://rust-lang.org
DecisiónPor qué
Store devuelve Option<&Link>Presta el dato sin clonar; el trait no impone un retorno con dueño.
count por defecto y newest<S: Store>Una implementación nueva hereda count, y el genérico especializa sin indirección para cada almacén.
Box<dyn Error> en runEl borde acepta errores variados con ?; el dominio conserva StoreError tipado.

5 · Buenas prácticas

Haz estoEvita estoPor qué
Genérico con el bound mínimoT: Clone + Debug + Display «por si acaso»Cada bound restringe al llamador y promete algo que el cuerpo quizá no usa.
where con tres bounds o vidasFirmas de 200 caracteres en una líneaLa legibilidad de la firma es parte del diseño.
dyn en las fronteras (CLI, plugins, tests)Box<dyn Trait> en todas las funciones internasLa indirección se paga en cada llamada y complica el tipado.
impl Trait en retorno para iteradoresBox<dyn Iterator> por defectoEl tipo opaco evita la reserva del Box; dyn solo si necesitas heterogeneidad.
Errores propios y traits pequeñosUn trait «Dios» o Box<dyn Error> en la API públicaLos traits pequeños se mockean y se mantienen object safe; el consumidor conserva motivos de error tipados.

Regla de oro

Empieza siempre por el genérico. Cambia a dyn cuando necesites una colección heterogénea, elijas la implementación en ejecución o midas un problema real de tamaño de binario. «Por si acaso» no es una razón: la indirección también se nota.

6 · Errores habituales

1. Usar Display sin declarar el bound

fn imprimir<T>(valor: T) {
    println!("{valor}");
}
error[E0277]: `T` doesn't implement `std::fmt::Display`
 --> src/main.rs:2:15
  |
1 | fn imprimir<T>(valor: T) {
  |               - this type parameter
2 |     println!("{valor}");
  |               ^^^^^^^ `T` cannot be formatted with the default formatter
  |
  = help: consider adding a `where T: std::fmt::Display` bound

Por qué: un genérico sin bounds no promete nada. Bien: fn imprimir<T: Display>(valor: T).

2. Implementar un trait ajeno para un tipo ajeno

error[E0117]: only traits defined in the current crate can be implemented for
              types defined outside of the crate
 --> src/lib.rs:1:1
  |
1 | impl std::fmt::Display for Vec<Link> {
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ `Vec` is not defined in the current crate
  |
  = note: implement the trait for a type defined in this crate, or use a newtype

Por qué: dos crates podrían definir dos Display incompatibles. Bien: struct Links(Vec<Link>) con su Display.

3. Convertir en objeto un trait que no es object safe

error[E0038]: the trait `Repo` cannot be made into an object
 --> src/main.rs:5:15
  |
2 |     fn find<T>(&self, id: T) -> Option<Link>;
  |        ---- this method has generic type parameters
5 | fn usar(repo: &dyn Repo) {}
  |                ^^^^^^^^ `Repo` cannot be made into an object

Por qué: la vtable necesita una entrada por método y un método genérico genera infinitas versiones. Bien: quita el genérico (fn find(&self, id: u64)) o no uses dyn con ese trait.

7 · Ejercicio guiado

Objetivo: escribir un decorator genérico que envuelva cualquier Store y registre las inserciones. Es el patrón con el que añadirás métricas y caché sin tocar el dominio.

  1. Parte del crate anterior. Sobre el código del ejemplo real, añade al final de src/lib.rs: 
    pub struct AuditStore<S> { inner: S, log: Vec<String> }

impl<S: Store> AuditStore<S> {
    pub fn new(inner: S) -> Self { Self { inner, log: Vec::new() } }
    pub fn log(&self) -> &[String] { &self.log }
}

impl<S: Store> Store for AuditStore<S> {
    fn insert(&mut self, link: Link) -> Result<(), StoreError> {
        self.log.push(format!("insert /{}", link.code));
        self.inner.insert(link)
    }
    fn get(&self, code: &str) -> Option<&Link> { self.inner.get(code) }
    fn list(&self) -> Vec<&Link> { self.inner.list() }
}

    El bound S: Store es todo lo que el decorator necesita saber. Y hereda count() sin escribirlo.

  2. Pruébalo con genérico y con dyn. 
    #[cfg(test)]
mod tests {
    use super::*;

    fn link(code: &str) -> Link {
        Link { code: code.into(), url: "https://a.dev".into(), created_at: 1, hits: 0 }
    }

    #[test]
    fn audita_las_inserciones() {
        let mut store = AuditStore::new(MemoryStore::default());
        store.insert(link("abc234")).unwrap();
        assert_eq!(store.count(), 1);
        assert_eq!(store.log()[0], "insert /abc234");
    }
}
  3. Ejecuta y pasa clippy. 
    cargo test
cargo clippy --all-targets -- -D warnings

8 · Reto

🎯 Almacén con caché y respaldo

El trait Store mezcla lectura y escritura. Sepáralo en LinkReader (get, list) y LinkWriter (insert), y define trait Store: LinkReader + LinkWriter con count por defecto. Después implementa FallbackStore: lee del almacén rápido y, si no encuentra el código, delega en el lento y rellena la caché; al insertar, escribe en ambos. Restricciones: acepta cualquier combinación de implementaciones, la API pública no expone Box<dyn Error>, y acertar en caché cuesta como máximo una llamada virtual.

Pista: prueba campos genéricos (FallbackStore<F: Store, S: Store>) y trait objects, y compara las firmas. Para rellenar la caché desde &self necesitarás interior mutabilidad (RefCell) o cambiar el contrato a &mut self: elige cuál es honesto y documéntalo en el trait.

9 · Resumen

  • Un trait es un contrato de métodos; los tipos lo implementan explícitamente y heredan los métodos por defecto.
  • Los genéricos con bounds escriben el código una vez y lo especializan en compilación, sin coste en ejecución; impl Trait es su azúcar.
  • dyn Trait permite heterogeneidad y elección en ejecución a cambio de una llamada indirecta; Box<dyn Error> va en el borde y el error propio en la librería. La orphan rule exige trait o tipo local, y el newtype es la salida.
  • La monomorfización explica el coste cero y también el crecimiento del binario.

Comandos y conceptos de esta lección

10 · Preguntas frecuentes

¿Trait es lo mismo que interfaz?

Se parecen en el contrato, pero no en el resto. Un trait puede tener implementaciones por defecto y puede implementarse para tipos que ya existen (si el trait es tuyo). No hay herencia de estado ni constructores virtuales. Y hay traits que el compilador usa para decidir cosas que una interfaz no puede: Send, Sync, Copy, Sized.

¿Genérico o dyn? ¿Cuál es más rápido?

El genérico, ligeramente: la llamada es directa y el compilador puede inlinearla. dyn añade un salto por la vtable y bloquea la inlineación. Solo importa en bucles calientes. Elige por diseño: genérico si el tipo se conoce al compilar; dyn si necesitas tipos heterogéneos o elegir implementación en ejecución.

¿Puedo implementar un trait para un tipo que no es mío?

Sí, si el trait es tuyo. Es lo que hace la std contigo: define Display y tú lo implementas para tu Link. Lo que no puedes es implementar un trait ajeno para un tipo ajeno. Tampoco vale envolverlo con un alias de tipo: el newtype tiene que ser un tipo nuevo de verdad.

¿Por qué un trait con genéricos no se puede convertir en dyn?

Porque la tabla virtual necesita un conjunto fijo de métodos con firma conocida. Un método genérico se monomorfiza por cada tipo con el que se llama, así que no tiene una única dirección que meter en la vtabla. La solución habitual es mover el parámetro de tipo al trait (trait Store<T>) o usar Box<dyn Trait<T>> con un tipo concreto, aceptando el coste.
