Tests: unitarios, de integración y doc-tests

Módulo 3 · Errores y modularidad ⏱ 40 minutos

1 · Introducción

En Rust los tests no son un añadido: son parte del lenguaje y de Cargo. Se escriben en el mismo fichero que el código, se compilan con la misma herramienta y se ejecutan en paralelo. No hay framework que instalar ni describe/it que memorizar: hay un atributo #[test] y tres macros de aserción.

Eso baja tanto el coste de escribir el primero que no hay excusa para no hacerlo. Y como el compilador ya te obliga a manejar los errores, los tests se concentran en lo que de verdad importa: el comportamiento del dominio. Los tests también son documentación ejecutable: un doctest que se rompe es una página del manual que ha mentido.

¿Por qué existe esta lección?

Porque un test no comprueba que el código hace lo que dice: comprueba que sigue haciéndolo cuando lo cambias. En un lenguaje con tipos fuertes, los tests cubren exactamente lo que el compilador no puede demostrar: la intención. Y en Rust, además, te obligan a mantener la API pública usable desde fuera, que es como la usarán tus consumidores.

Errores típicos al empezar: escribir tests que dependen del orden de ejecución; usar ficheros con nombres fijos y descubrir que fallan en paralelo; probar detalles privados desde tests/; y confundir cobertura con calidad.

2 · Teoría

Cómo funciona cargo test

cargo test compila el crate en modo test (con cfg(test) activo), genera un binario de pruebas y lo ejecuta. Cada #[test] corre en su propio hilo, por defecto en paralelo, y su salida se captura: solo la ves si el test falla o si pasas --nocapture. El código marcado con #[cfg(test)] no existe en la compilación normal: no cuesta ni un byte en producción.

  cargo test
      │
      ├─ compila lib con cfg(test) ──► tests unitarios  (dentro de src/)
      ├─ compila cada tests/*.rs   ──► tests de integración (crate aparte)
      └─ extrae bloques de ///     ──► doctests (cada uno, un mini-crate)
              │
              ▼
        ejecuta en paralelo · captura stdout · resume pass/fail

Los tests unitarios viven en un módulo #[cfg(test)] mod tests dentro del propio fichero. Al ser un hijo del módulo, use super::* le da acceso a funciones y tipos privados: puedes probar detalles internos sin abrir la API. Los tests de integración, en cambio, son un crate externo y solo ven lo pub.

Aserciones y atributos

Los tests pueden devolver Result<(), E> siempre que E: Debug. Es la forma limpia de encadenar operaciones que fallan sin llenar el test de unwrap:

#[test]
fn guardar_y_recuperar() -> Result<(), Box<dyn std::error::Error>> {
    let mut store = MemoryStore::new();
    store.insert(Link::new("abc234", "https://x.dev"))?;
    assert_eq!(store.get("abc234")?.url, "https://x.dev");
    Ok(())
}

Doctests: el manual que se ejecuta

Cualquier bloque ``` en un comentario /// se compila y se ejecuta como un crate externo que usa tu librería. Si el ejemplo deja de compilar, cargo test falla. Por eso la documentación de Rust envejece mejor que la de otros ecosistemas. Se controlan con atributos: no_run (compila pero no ejecuta), ignore (ni compila) y should_panic.

/// Comprueba que un código tenga 6 caracteres del alfabeto sin ambigüedades.
///
/// ```
/// use urlshort::domain::is_valid_code;
///
/// assert!(is_valid_code("k7m2qd"));
/// assert!(!is_valid_code("k7m2q0")); // el cero no se usa
/// ```
pub fn is_valid_code(code: &str) -> bool {
    const ALPHABET: &str = "23456789abcdefghjkmnpqrstuvwxyz";
    code.len() == 6 && code.chars().all(|c| ALPHABET.contains(c))
}

Los doctests solo funcionan en crates de librería. Si tu código vive solo en main.rs, cargo test --doc dirá «0 tests»: otra razón para separar lib.rs.

Ciclo TDD y cobertura

TDD en Rust es incómodo al principio por una razón buena: el código no compila hasta que existe la función que el test llama. El ciclo se adapta así: escribe el test, deja que falle por la razón correcta (rojo), implementa lo mínimo (verde), limpia (refactor).

  ROJO                 VERDE                REFACTOR
  escribe el test  →  implementa      →   limpia sin cambiar
  cargo test falla    cargo test pasa      el comportamiento
       ▲                                          │
       └──────────────────────────────────────────┘

Para medir cobertura, cargo-llvm-cov usa la instrumentación de LLVM: cargo llvm-cov imprime el resumen, --html genera el informe navegable y --fail-under-lines 80 rompe la CI si baja del umbral. La cobertura dice qué líneas se ejecutaron, no si las aserciones son buenas: un test sin assert también cubre líneas.

3 · Ejemplo mínimo

Cinco tests sobre dos funciones. Uno de ellos comprueba un pánico esperado; fíjate en que el módulo es privado y accede a todo con super::*.

// src/lib.rs
pub fn short_code(url: &str) -> String {
    use std::collections::hash_map::DefaultHasher;
    use std::hash::{Hash, Hasher};

    let mut hasher = DefaultHasher::new();
    url.hash(&mut hasher);
    let mut n = hasher.finish();

    const ALPHABET: &[u8] = b"23456789abcdefghjkmnpqrstuvwxyz";
    let mut code = String::with_capacity(6);
    for _ in 0..6 {
        code.push(ALPHABET[(n % ALPHABET.len() as u64) as usize] as char);
        n /= ALPHABET.len() as u64;
    }
    code
}

#[cfg(test)]
fn code_from_line(line: &str) -> &str {
    line.split_once(" -> ")
        .expect("formato: <url> -> <código>")
        .1
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn el_codigo_mide_seis() {
        assert_eq!(short_code("https://www.rust-lang.org").len(), 6);
    }

    #[test]
    fn es_estable_para_la_misma_url() {
        assert_eq!(
            short_code("https://www.rust-lang.org"),
            short_code("https://www.rust-lang.org")
        );
    }

    #[test]
    fn urls_distintas_codigos_distintos() {
        assert_ne!(short_code("https://a.dev"), short_code("https://b.dev"));
    }

    #[test]
    fn extrae_el_codigo_de_la_salida() {
        assert_eq!(code_from_line("https://a.dev -> /k7m2qd"), "k7m2qd");
    }

    #[test]
    #[should_panic(expected = "formato: <url> -> <código>")]
    fn salida_sin_flecha_entra_en_panico() {
        code_from_line("sin flecha");
    }
}

Ejecución y salida resumida:

cargo test
# running 5 tests
# test tests::el_codigo_mide_seis ... ok
# test tests::salida_sin_flecha_entra_en_panico ... ok
# …
# test result: ok. 5 passed; 0 failed; 0 ignored

Línea a línea: #[cfg(test)] excluye el módulo de la compilación normal; use super::* trae al módulo de tests todo lo que hay arriba, incluido lo privado; assert_eq! imprime los dos valores si falla; #[should_panic(expected = …)] exige que el mensaje contenga ese texto, no que sea igual. Si el test dejara de entrar en pánico, fallaría con «test did not panic as expected».

4 · Ejemplo real

urlshort tiene tres capas de test: el almacén en memoria (unitarios con fixture), el binario completo (integración con CARGO_BIN_EXE_) y el contrato de is_valid_code (doctest).

Un fixture es una función que construye el dato de prueba. Evita repetir el mismo Link en cinco tests y, cuando el struct cambie, solo se toca en un sitio.

// src/store/memory.rs
#[cfg(test)]
mod tests {
    use super::*;
    use crate::error::Error;

    fn link(url: &str) -> Link {
        Link::new("abc234", url)
    }

    #[test]
    fn insertar_y_recuperar() -> std::result::Result<(), Box<dyn std::error::Error>> {
        let mut store = MemoryStore::new();
        store.insert(link("https://x.dev"))?;

        assert_eq!(store.get("abc234")?.url, "https://x.dev");
        assert_eq!(store.get("abc234")?.hits, 0);
        Ok(())
    }

    #[test]
    fn un_codigo_duplicado_es_conflict() {
        let mut store = MemoryStore::new();
        store.insert(link("https://x.dev")).expect("primer insert");
        let err = store.insert(link("https://y.dev")).expect_err("debe fallar");

        assert!(matches!(err, Error::Domain(DomainError::Conflict(c)) if c == "abc234"));
    }

    #[test]
    fn un_codigo_desconocido_es_not_found() {
        let store = MemoryStore::new();
        let err = store.get("zzzzzz").expect_err("no existe");

        assert!(matches!(err, Error::Domain(DomainError::NotFound(c)) if c == "zzzzzz"));
    }

    #[test]
    fn el_mensaje_de_error_es_estable() {
        let store = MemoryStore::new();
        let err = store.get("zzzzzz").expect_err("no existe");

        assert_eq!(
            err.to_string(),
            "no existe ningún enlace con el código `zzzzzz`"
        );
    }
}

Los tests de integración viven en tests/, se compilan como un crate aparte y solo ven lo público. Para lanzar el binario, Cargo define CARGO_BIN_EXE_<nombre> con la ruta del ejecutable compilado: nada de rutas relativas a target/debug.

// tests/cli.rs
use std::process::Command;

#[test]
fn short_imprime_el_codigo() {
    let out = Command::new(env!("CARGO_BIN_EXE_urlshort"))
        .args(["short", "https://www.rust-lang.org"])
        .output()
        .expect("no se pudo ejecutar urlshort");

    assert!(
        out.status.success(),
        "stderr: {}",
        String::from_utf8_lossy(&out.stderr)
    );
    let stdout = String::from_utf8_lossy(&out.stdout);
    assert!(stdout.contains(" -> /"), "stdout inesperado: {stdout}");
}

#[test]
fn url_sin_esquema_sale_con_codigo_1() {
    let out = Command::new(env!("CARGO_BIN_EXE_urlshort"))
        .args(["short", "example.com"])
        .output()
        .expect("no se pudo ejecutar urlshort");

    assert_eq!(out.status.code(), Some(1));
    assert!(String::from_utf8_lossy(&out.stderr).contains("URL no válida"));
}

Y el doctest, que es el que documenta la regla del alfabeto:

Comandos para ejecutar cada capa por separado:

cargo test --lib                 # solo unitarios
cargo test --test cli            # solo tests/cli.rs
cargo test --doc                 # solo doctests
cargo test duplicado             # filtra por nombre de test
cargo test -- --nocapture        # muestra los println de los tests

Un test, una razón para fallar

Si un test comprueba tres cosas y falla, no sabes cuál se rompió. Divide: uno para el camino feliz, uno por cada error relevante y uno por cada límite (vacío, cero, máximo). El nombre debe decir qué se espera: un_codigo_duplicado_es_conflict informa más que test_insert_2.

6 · Errores habituales

1. Comparar tipos que no son iguales

Mal: len() devuelve usize, no u32.

#[test]
fn longitud() {
    assert_eq!(short_code("https://x.dev").len(), 6u32);
}
error[E0308]: mismatched types
 --> src/lib.rs:20:9
  |
20 |     assert_eq!(short_code("https://x.dev").len(), 6u32);
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ expected `usize`, found `u32`
   |
   = note: this error originates in the macro `assert_eq`

Bien: usar el tipo que devuelve la expresión (6 se infiere como usize).

assert_eq!(short_code("https://x.dev").len(), 6);

2. Importar lo privado desde tests/

Mal: un test de integración intenta entrar por el módulo interno del store.

// tests/store.rs
use urlshort::store::memory::MemoryStore;
error[E0603]: module `memory` is private
 --> tests/store.rs:1:21
  |
1 | use urlshort::store::memory::MemoryStore;
  |                     ^^^^^^ private module
  |
note: the module `memory` is defined here
 --> src/store.rs:1:1
  |
1 | mod memory;
  | ^^^^^^^^^^

Bien: usar la fachada pública, que es exactamente lo que un consumidor tendría. Si el test necesita lo privado, conviértelo en unitario dentro del módulo.

// tests/store.rs
use urlshort::store::MemoryStore;

3. #[should_panic] sin pánico

Mal: el test espera un pánico que ya no ocurre porque alguien cambió el código.

#[test]
#[should_panic(expected = "división por cero")]
fn dividir_por_cero_entra_en_panico() {
    assert_eq!(10 / 2, 5); // ya no divide por cero
}
running 1 test
test tests::dividir_por_cero_entra_en_panico ... FAILED

---- tests::dividir_por_cero_entra_en_panico stdout ----
note: test did not panic as expected

failures:
    tests::dividir_por_cero_entra_en_panico

Bien: que el test ejecute la operación que de verdad debe fallar, y con expected apuntando al mensaje concreto. Un should_panic sin expected pasa con cualquier pánico y deja de proteger el contrato.

4. Tests que comparten estado y fallan «a veces»

Mal: dos tests que escriben en /tmp/urlshort-test.json. En paralelo, uno lee el fichero del otro. Falla de forma intermitente y en tu máquina no se reproduce.

Bien: cada test usa un recurso propio (un nombre único, un directorio temporal con tempfile) o serializa el acceso con -- --test-threads=1 solo mientras diagnosticas. Que un test dependa del orden es un test que no has escrito: es una ruleta.

7 · Ejercicio guiado

Objetivo: añadir is_valid_code a urlshort con TDD estricto: tests primero, implementación después. No escribas la función hasta el paso 3.

  1. Escribe los tests en rojo. Añade al final de src/domain.rs: 
    #[cfg(test)]
mod valid_code_tests {
    use super::is_valid_code;

    #[test]
    fn acepta_codigos_del_alfabeto() {
        assert!(is_valid_code("k7m2qd"));
    }

    #[test]
    fn rechaza_el_cero_y_la_ele() {
        assert!(!is_valid_code("k7m2q0"));
        assert!(!is_valid_code("k7m2ql"));
    }

    #[test]
    fn rechaza_longitudes_distintas() {
        assert!(!is_valid_code("k7m2q"));
        assert!(!is_valid_code("k7m2qdx"));
    }

    #[test]
    fn rechaza_mayusculas() {
        assert!(!is_valid_code("K7M2QD"));
    }
}

    La función aún no existe: el compilador fallará con cannot find function is_valid_code. Eso es el rojo esperado.

  2. Ejecuta solo estos tests. 
    cargo test valid_code -- --nocapture

    El filtro busca el texto en el nombre completo del test, incluido el módulo. --nocapture deja ver los dbg! o println! que añadas mientras depuras.

  3. Implementa lo mínimo. 
    pub fn is_valid_code(code: &str) -> bool {
    const ALPHABET: &str = "23456789abcdefghjkmnpqrstuvwxyz";
    code.len() == 6 && code.chars().all(|c| ALPHABET.contains(c))
}

    Verde: cargo test debe pasar los 4. Pregúntate qué caso no cubre la implementación: por ejemplo, "ábcdef" mide 7 bytes y 6 caracteres; el len() lo rechaza, que es lo correcto para este alfabeto ASCII.

  4. Refactoriza y documenta con un doctest. 
    /// Comprueba que un código tenga 6 caracteres del alfabeto sin ambigüedades.
///
/// ```
/// use urlshort::domain::is_valid_code;
///
/// assert!(is_valid_code("k7m2qd"));
/// assert!(!is_valid_code("k7m2q0"));
/// ```
pub fn is_valid_code(code: &str) -> bool { /* … */ }
    cargo test
cargo test --doc

    El doctest corre como un crate externo: comprueba que el ejemplo es copiable y que la función es pública.

  5. Mide la cobertura. 
    rustup component add llvm-tools-preview
cargo install cargo-llvm-cov
cargo llvm-cov --html

    Abre el informe y busca líneas no cubiertas de domain.rs. Añade un test solo si esa rama representa un comportamiento real; no para colorear el mapa.

Criterio de éxito

Cuatro tests que fallan por la razón correcta antes de implementar, un doctest que documenta la API y cargo test en verde con unitarios, integración y doc. Y sabes qué capa debe probar cada cosa.

8 · Reto

🎯 La suite que aguanta un refactor

Cubre el flujo completo de urlshort sin tocar la implementación. Requisitos:

  • Unitarios del store: insertar, duplicado, desconocido, contador de hits.
  • Un test con Result que use ? en vez de unwrap.
  • Un test de integración por cada código de salida (0, 1, 2) usando CARGO_BIN_EXE_urlshort.
  • Un doctest para is_valid_code y otro para validate_url.
  • Un test #[ignore] para el futuro store SQLite, documentando por qué está ignorado.
  • Toda la suite debe pasar en paralelo y dos veces seguidas sin limpiar target/.

Después, cambia a propósito el mensaje de NotFound y comprueba cuántos tests fallan. Si falla uno solo, tu suite está mirando el contrato; si fallan diez, está acoplada a detalles que deberían ser irrelevantes.

Pista: para los códigos de salida, ejecuta el binario con Command y mira status.code(); no intentes llamar a main desde el test. Para el ignore, añade el motivo en el nombre o en un comentario, porque cargo test -- --ignored no te lo va a explicar.

9 · Resumen

  • #[cfg(test)] mod tests compila solo bajo test y accede a lo privado con super::*.
  • #[test] marca la función; assert!, assert_eq! y assert_ne! comprueban.
  • #[should_panic(expected = "…")] exige el mensaje concreto; sin expected es demasiado laxo.
  • Los tests de tests/ son un crate aparte y solo ven la API pública.
  • Los doctests de /// se compilan y ejecutan; necesitan un crate de librería.
  • Los tests corren en paralelo: nada de estado compartido ni rutas fijas.
  • Un test puede devolver Result y usar ?; falla si recibe Err.
  • TDD: rojo, verde, refactor. La cobertura (cargo llvm-cov) ayuda, pero no sustituye a las aserciones.

10 · Preguntas frecuentes

¿Por qué poner los tests en el mismo fichero que el código?

Porque pueden probar lo privado y porque el test se mueve con el código: si renombras la función, el test está al lado. Los tests de integración van en tests/ precisamente para lo contrario: verificar que la API pública es suficiente desde fuera. Usa el unitario para la lógica y el de integración para el contrato.

¿assert_eq! o assert!?

assert_eq! siempre que compares dos valores: imprime izquierda, derecha y sus tipos, que es el diagnóstico que necesitas. assert! para predicados (contains, is_ok, matches!). En ambos, añade un mensaje con contexto si el fallo no es evidente: assert!(out.status.success(), "stderr: {stderr}").

¿Cómo pruebo código que lee ficheros o la red?

Inyecta la dependencia: que la función reciba un impl Read, un Path o un trait propio, y en el test pásale un buffer o un directorio temporal. Si no puedes, marca el test con #[ignore] y ejecútalo aparte. Los tests que dependen de la red o del reloj son la causa número uno de suites inestables.

¿Los doctests cuentan como tests unitarios?

No: cada bloque se compila como un crate externo que enlaza tu librería, así que solo puede usar la API pública. Cuestan tiempo de compilación (cada doctest es un binario) y por eso a veces se separan con --doc. A cambio, garantizan que los ejemplos del manual siguen siendo ciertos.

¿Qué cobertura debería exigir en CI?

Un umbral global bajo (70–80 %) que detecte caídas grandes, no una meta de 100 %. Exigir el 100 % empuja a escribir tests sin aserciones para cubrir líneas inalcanzables. Es más útil revisar la cobertura del diff: las líneas nuevas de un PR deberían estar cubiertas salvo justificación.
