Errores propios con thiserror

Módulo 3 · Errores y modularidad ⏱ 40 minutos

1 · Introducción

En la lección anterior los errores eran String. Funciona para un ejercicio, pero tiene dos problemas graves: el llamador no puede distinguir un fallo de otro sin comparar texto, y el mensaje que ve el usuario acaba mezclado con detalles internos. Cuando urlshort crezca, necesitarás saber si un enlace no existe (código 3), si ya existe (código 4) o si el disco falló (código 1) sin leer una frase.

La solución es la misma que para cualquier otro dato: un tipo. Un enum con una variante por clase de fallo, campos con la información concreta y un Display que produzca el mensaje humano. A mano son ochenta líneas de ceremonia; thiserror las genera con atributos.

¿Por qué existe esta lección?

Porque «algo falló» no es un error: es una excusa. Un error bien diseñado nombra lo que pasó, conserva la causa original y oculta lo que el usuario no debe ver. Ese triple contrato separa una herramienta depurable de una caja negra.

Errores típicos al empezar: derivar solo Debug y usar el tipo con ? hacia Box<dyn Error>; envolver dos veces el mismo io::Error con #[from]; poner la ruta absoluta del servidor en el mensaje público; y usar String como variante comodín.

2 · Teoría

Qué exige ser un error

std::error::Error exige dos supertraits: Debug (diagnóstico) y Display (mensaje humano). Además ofrece source(), que devuelve la causa original, y provide() para backtraces. La cadena de causas permite imprimir «no se pudo guardar el enlace» y, debajo, «permiso denegado».

pub trait Error: Debug + Display {
    fn source(&self) -> Option<&(dyn Error + 'static)> { None }
}

Si implementas Error a mano y te falta Display, el compilador lo dice con E0277. Y si derivas solo Debug, el tipo no es un error para nadie: no puede viajar en Box<dyn Error>.

El enum como vocabulario del dominio

Diseñar errores es diseñar el vocabulario de lo que puede salir mal. Cada variante debe responder a una pregunta que el llamador quiera hacer. Si dos variantes se tratan siempre igual, probablemente sean una; si una necesita un dato para el mensaje, lo lleva dentro.

#[derive(Debug, thiserror::Error)]
pub enum DomainError {
    #[error("URL no válida: {0}")]
    InvalidUrl(String),

    #[error("no existe ningún enlace con el código `{0}`")]
    NotFound(String),

    #[error("el código `{0}` ya está en uso")]
    Conflict(String),
}

thiserror genera impl Display con la plantilla de #[error] y impl Error con source() cuando hay causa. Debug no lo genera: se deriva aparte y es obligatorio.

AtributoQué generaCuándo usarlo

Dos formas de conservar la causa

#[from] solo puede aparecer en un campo y la variante no admite más datos (salvo un backtrace). Sirve para «adopto el error tal cual», no para «lo envuelvo con la ruta que intentaba abrir».

#[derive(Debug, thiserror::Error)]
pub enum ConfigError {
    #[error("no se pudo leer la configuración")]
    Io(#[from] std::io::Error), // From + source, sin contexto
}

#[derive(Debug, thiserror::Error)]
pub enum StoreError {
    #[error("no se pudo acceder a {path}")]
    Io {
        path: String,
        #[source] // no hay From: el contexto se añade a mano
        source: std::io::Error,
    },
}

fn save(path: &str) -> Result<(), StoreError> {
    std::fs::write(path, b"{}").map_err(|source| StoreError::Io {
        path: path.to_string(),
        source,
    })
}

Un campo llamado source ya es la causa

thiserror trata automáticamente como causa cualquier campo llamado source; #[source] hace falta si se llama cause o io. Y dos #[from] std::io::Error en el mismo enum fallan con E0119: dos From idénticos no pueden coexistir.

Jerarquía: dominio, infraestructura y borde

Un error que lo explica todo suele ser un error que no dice nada. La estructura que mejor envejece separa tres capas:

  DOMINIO                 INFRAESTRUCTURA              BORDE (CLI / HTTP)
  ───────                 ────────────────              ──────────────────
  InvalidUrl              Io { path, source }           main / handler
  NotFound                Serde { path, source }        │
  Conflict                Db { … }                      ├─ mensaje al usuario
        │                        │                      ├─ log con la cadena
        └────────┬───────────────┘                      └─ código de salida
                 ▼
          Error (envoltorio)
          ├── Domain(#[from] DomainError)
          └── Store(#[from] StoreError)

El dominio no sabe que existe el disco; la infraestructura no sabe qué es un código duplicado. El envoltorio Error, con #[error(transparent)], agrupa ambos y permite que ? convierta sin map_err en cada capa. El borde —main o un handler de Axum— decide qué se imprime y qué código se devuelve.

No exponer las tripas

Un mensaje de error es una interfaz pública: se lee en terminales, logs y respuestas HTTP. La ruta /srv/datos/enlaces.json, el usuario de la base de datos o el SQL que falló no deben aparecer en la respuesta al cliente; sí en el log. La regla: el mensaje público describe la intención («no se pudo guardar el enlace») y la causa viaja en source() para quien tenga permiso de verla. Box<dyn Error> es útil en prototipos, tests y binarios pequeños, pero inútil en una API pública: el llamador no puede hacer match sobre variantes.

3 · Ejemplo mínimo

Tres variantes, tres mensajes y una dependencia. check devuelve el enum concreto, no una caja.

// Cargo.toml → thiserror = "2"
use thiserror::Error;

#[derive(Debug, Error)]
enum UrlError {
    #[error("la URL está vacía")]
    Empty,

    #[error("falta el esquema en `{0}`")]
    MissingScheme(String),

    #[error("esquema no permitido: `{0}`")]
    Scheme(String),
}

fn check(raw: &str) -> Result<(), UrlError> {
    let url = raw.trim();
    let (scheme, rest) = url
        .split_once("://")
        .ok_or_else(|| UrlError::MissingScheme(url.to_string()))?;
    if scheme != "http" && scheme != "https" {
        return Err(UrlError::Scheme(scheme.to_string()));
    }
    if rest.is_empty() {
        return Err(UrlError::Empty);
    }
    Ok(())
}

fn main() {
    for raw in ["https://www.rust-lang.org", "www.rust-lang.org", "ftp://x.dev"] {
        match check(raw) {
            Ok(()) => println!("ok   {raw}"),
            Err(e) => println!("err  {raw}: {e}"),
        }
    }
}

Salida: ok https://www.rust-lang.org, err www.rust-lang.org: falta el esquema en `www.rust-lang.org` y err ftp://x.dev: esquema no permitido: `ftp`.

#[derive(Debug, Error)] combina el Debug que exige el trait con el Display y el Error que genera el derive; {0} usa el primer campo posicional; ok_or_else convierte la ausencia de esquema en el error con el texto original dentro. En println!, {e} llama a Display; {e:?} llamaría a Debug e imprimiría Scheme("ftp").

El mensaje empieza en minúscula y sin punto final

Es la convención de std, porque los mensajes se encadenan: error al guardar: no se pudo acceder a enlaces.json se lee bien; Error al guardar. No se pudo acceder… se lee como dos frases peleadas. Las variantes, en cambio, van en CamelCase y en inglés, como el resto de identificadores.

4 · Ejemplo real

urlshort ya distingue cinco clases de fallo: InvalidUrl, NotFound, Conflict, Io y Serde. Dominio y almacén tienen su enum; un envoltorio los une y el borde traduce a códigos. (Cargo.toml: thiserror = "2" y serde_json = "1"; la persistencia real llega en el módulo 6.)

// src/error.rs
use thiserror::Error;

pub type Result<T> = std::result::Result<T, Error>;

#[derive(Debug, Error)]
pub enum DomainError {
    #[error("URL no válida: {0}")]
    InvalidUrl(String),

    #[error("no existe ningún enlace con el código `{0}`")]
    NotFound(String),

    #[error("el código `{0}` ya está en uso")]
    Conflict(String),
}

#[derive(Debug, Error)]
pub enum StoreError {
    #[error("no se pudo acceder a {path}")]
    Io {
        path: String,
        #[source]
        source: std::io::Error,
    },

    #[error("JSON inválido en {path}")]
    Serde {
        path: String,
        #[source]
        source: serde_json::Error,
    },
}

#[derive(Debug, Error)]
pub enum Error {
    #[error(transparent)]
    Domain(#[from] DomainError),

    #[error(transparent)]
    Store(#[from] StoreError),
}

impl Error {
    pub fn exit_code(&self) -> i32 {
        match self {
            Error::Domain(DomainError::InvalidUrl(_)) => 1,
            Error::Domain(DomainError::NotFound(_)) => 3,
            Error::Domain(DomainError::Conflict(_)) => 4,
            Error::Store(_) => 1,
        }
    }
}

El almacén construye los errores donde tiene el dato que falta: el path y la causa.

// src/store.rs (extracto)
impl MemoryStore {
    pub fn insert(&mut self, link: Link) -> Result<()> {
        if self.links.contains_key(&link.code) {
            return Err(DomainError::Conflict(link.code).into());
        }
        self.links.insert(link.code.clone(), link);
        Ok(())
    }

    pub fn get(&self, code: &str) -> Result<&Link> {
        self.links
            .get(code)
            .ok_or_else(|| DomainError::NotFound(code.to_string()).into())
    }

    pub fn save(&self, path: &std::path::Path) -> Result<()> {
        let json = serde_json::to_string_pretty(&self.links).map_err(|source| {
            StoreError::Serde { path: path.display().to_string(), source }
        })?;
        std::fs::write(path, json).map_err(|source| StoreError::Io {
            path: path.display().to_string(),
            source,
        })?;
        Ok(())
    }
}

El borde imprime el mensaje público, recorre la cadena de causas y elige el código. Ese bucle es la razón de ser de source():

// src/main.rs (extracto)
use std::process::ExitCode;

fn main() -> ExitCode {
    match run() {
        Ok(line) => {
            println!("{line}");
            ExitCode::SUCCESS
        }
        Err(err) => {
            eprintln!("error: {err}");
            let mut cause = std::error::Error::source(&err);
            while let Some(c) = cause {
                eprintln!("  causa: {c}");
                cause = c.source();
            }
            ExitCode::from(err.exit_code() as u8)
        }
    }
}

Con un fichero sin permisos: error: no se pudo acceder a enlaces.json y, debajo, causa: Permission denied (os error 13). En una CLI enseñar la causa está bien; en un servidor HTTP, no: el cliente recibe «no existe el enlace» y la ruta se queda en el log.

Los mensajes se prueban. El texto es contrato: si cambia, se rompen scripts y tests de integración.

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn invalid_url_incluye_el_valor() {
        let err = DomainError::InvalidUrl(String::from("ftp://x.dev"));
        assert_eq!(err.to_string(), "URL no válida: ftp://x.dev");
    }

    #[test]
    fn io_conserva_la_causa() {
        use std::error::Error as _;
        let err = Error::Store(StoreError::Io {
            path: String::from("enlaces.json"),
            source: std::io::Error::new(std::io::ErrorKind::PermissionDenied, "sin permisos"),
        });
        assert_eq!(err.to_string(), "no se pudo acceder a enlaces.json");
        assert_eq!(err.source().unwrap().to_string(), "sin permisos");
        assert_eq!(err.exit_code(), 1);
    }
}

La prueba del llamador

Antes de añadir una variante, pregunta: «¿qué haría distinto el código que la recibe?». Si la respuesta es «nada, imprimirla», quizá no la necesitas. Si es «reintentar», «devolver 404» o «pedir otra entrada», la variante está justificada.

6 · Errores habituales

1. Implementar Error sin Display

Mal:

#[derive(Debug)]
struct MiError;

impl std::error::Error for MiError {}
error[E0277]: `MiError` doesn't implement `std::fmt::Display`
 --> src/main.rs:4:6
  |
4 | impl std::error::Error for MiError {}
  |      ^^^^^^^^^^^^^^^^^^ `MiError` cannot be formatted with the default formatter
  |
  = help: the trait `std::fmt::Display` is not implemented for `MiError`
  = note: required for `MiError` to implement `std::error::Error`

Por qué está mal: Display es supertrait de Error; sin mensaje humano no hay error, solo un tipo con Debug.

Bien: implementar Display o, mejor, derivar thiserror.

use thiserror::Error;

#[derive(Debug, Error)]
#[error("el enlace no es válido")]
struct MiError;

2. Mover un campo detrás de &self

Mal:

pub struct Fallo {
    mensaje: String,
}

impl Fallo {
    pub fn mensaje(&self) -> String {
        self.mensaje // intenta llevarse el String del struct prestado
    }
}
error[E0507]: cannot move out of `self.mensaje` which is behind a shared reference
 --> src/lib.rs:8:9
  |
7 |     pub fn mensaje(&self) -> String {
  |                             ------ expected `String` because of return type
8 |         self.mensaje
  |         ^^^^^^^^^^^^ move occurs because `self.mensaje` has type `String`,
  |                      which does not implement the `Copy` trait
  |
help: consider cloning the value if the performance cost is acceptable
  |
8 |         self.mensaje.clone()
  |                    ++++++++

Bien: prestar el texto; un accesor de error casi nunca necesita regalar el String.

impl Fallo {
    pub fn mensaje(&self) -> &str {
        &self.mensaje
    }
}

Si de verdad necesitas el valor, que el método consuma self (fn into_mensaje(self) -> String) y que el nombre lo diga. clone() es la última opción.

3. Dos #[from] del mismo tipo

Mal:

use thiserror::Error;

#[derive(Debug, Error)]
enum StoreError {
    #[error("al leer")]
    Leer(#[from] std::io::Error),
    #[error("al escribir")]
    Escribir(#[from] std::io::Error),
}
error[E0119]: conflicting implementations of trait `From<std::io::Error>` for type `StoreError`
  --> src/main.rs:6:12
   |
 4 |     Leer(#[from] std::io::Error),
   |          --------------------- first implementation here
 6 |     Escribir(#[from] std::io::Error),
   |              ^^^^^^^^^^^^^^^^^^^^^ conflicting implementation for `StoreError`

Por qué está mal: #[from] genera impl From<std::io::Error>, y solo puede haber una; además ? no sabría cuál elegir.

Bien: un #[from] y, para el otro, contexto con #[source].

use thiserror::Error;

#[derive(Debug, Error)]
enum StoreError {
    #[error("al leer")]
    Leer(#[from] std::io::Error),
    #[error("al escribir en {path}")]
    Escribir {
        path: String,
        #[source]
        source: std::io::Error,
    },
}

Y el error de diseño: #[error("no se pudo abrir /srv/app/datos/enlaces.json: {source}")] filtra la estructura del servidor. Usa mensaje de intención y deja la ruta en el log del borde.

7 · Ejercicio guiado

Objetivo: escribir un error a mano para entender qué genera thiserror, y después sustituirlo por el derive sin cambiar el comportamiento observable.

  1. Crea el proyecto y añade la dependencia. 
    cargo new errores-config --bin
cd errores-config
cargo add thiserror@2
  2. Escribe ConfigError a mano. 
    use std::fmt;

#[derive(Debug)]
enum ConfigError {
    Missing(String),
    Invalid { key: String, value: String },
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Self::Missing(k) => write!(f, "falta la clave `{k}`"),
            Self::Invalid { key, value } => write!(f, "`{key}` no es válido: {value}"),
        }
    }
}

impl std::error::Error for ConfigError {}

    Compila y comprueba que se puede imprimir con {}.

  3. Usa el error con ?. 
    fn port_from(cfg: &HashMap<String, String>) -> Result<u16, ConfigError> {
    let raw = cfg
        .get("PORT")
        .ok_or_else(|| ConfigError::Missing(String::from("PORT")))?;
    let port = raw.parse().map_err(|_| ConfigError::Invalid {
        key: String::from("PORT"),
        value: raw.clone(),
    })?;
    Ok(port)
}

    Con un mapa vacío: falta la clave `PORT`. Con PORT=ochenta: `PORT` no es válido: ochenta.

  4. Sustituye las 25 líneas por el derive. 
    #[derive(Debug, Error)]
enum ConfigError {
    #[error("falta la clave `{0}`")]
    Missing(String),

    #[error("`{key}` no es válido: {value}")]
    Invalid { key: String, value: String },

    La salida debe ser idéntica: el derive es un atajo de implementación, no un cambio de contrato.

  5. Prueba mensaje y causa. Añade Io con #[source] y un test que compruebe err.to_string() y err.source().is_some(). Ejecuta cargo test.

Criterio de éxito

Sabes qué genera cada atributo; el mensaje público es estable; la causa sigue accesible; y ningún detalle interno aparece en el texto que ve el usuario.

8 · Reto

🎯 Una taxonomía que sobreviva al servidor

Rediseña los errores de urlshort para que el mismo tipo sirva al CLI y, más adelante, a un servidor HTTP.

  • DomainError con InvalidUrl, NotFound, Conflict y Expired.
  • StoreError con Io, Serde y Db, siempre con contexto y #[source].
  • Envoltorio Error transparente y método exit_code() para el CLI.
  • public_message() que devuelva &'static str sin datos internos, listo para HTTP.
  • Dos tests por variante: mensaje público y código de salida.
  • Prohibido String como comodín y unwrap fuera de tests.

Pista: no dupliques la tabla de códigos. Define código y mensaje público en un único match por variante, y que CLI y HTTP pregunten al mismo método. Si Expired y NotFound responden distinto al usuario pero igual al shell, decide cuál es la diferencia antes de escribir el enum.

9 · Resumen

  • Un error de verdad implementa Debug + Display + std::error::Error; sin Display no hay mensaje humano.
  • thiserror deriva Display y Error desde #[error("…")]; Debug se deriva aparte.
  • #[from] genera From y marca la causa; solo una vez por tipo y sin otros campos.
  • #[source] conserva la causa cuando añades contexto con map_err.
  • #[error(transparent)] delega Display y source: ideal para enums envoltorio.
  • Separa dominio e infraestructura; el borde decide mensaje y código.
  • El mensaje público no filtra rutas; la causa vive en source() y en el log.
  • El texto del error y la cadena de causas se prueban como cualquier contrato.

10 · Preguntas frecuentes

¿thiserror o anyhow? ¿Puedo usar los dos?

Sí, y es lo habitual: la librería define sus enums con thiserror y el binario los envuelve con anyhow::Context para añadir el «mientras hacía X». anyhow no sustituye a tu enum: lo borra. Si el llamador necesita distinguir variantes, no uses anyhow en esa frontera.

¿Por qué el derive exige Debug si ya genera Error?

Porque std::error::Error declara Debug como supertrait y thiserror no genera un Debug que quizá quieras personalizar. Es una línea de ceremonia a cambio de que el tipo sirva en Box<dyn Error>, en logs y en tests.

¿Qué diferencia hay entre #[from] y #[source]?

#[from] genera From (para que ? convierta solo) y marca el campo como causa. #[source] solo marca la causa; la conversión la escribes con map_err porque necesitas añadir contexto (la ruta, el código, el identificador). Usa #[from] cuando adoptas el error sin más.

¿Debo implementar PartialEq en mis errores para los tests?

Rara vez. Compara la causa (io::Error no lo implementa) y te obliga a que todos los campos lo hagan. Es mejor comprobar con matches!(err, Error::NotFound(c) if c == "abc234") y, cuando importe, el texto con to_string(). Si necesitas igualdad exacta, suele ser señal de que el test mira demasiado dentro.

¿Cómo añado un backtrace?

Con #[backtrace] en un campo std::backtrace::Backtrace, o dejando que anyhow lo capture en el borde. Cuesta memoria y solo tiene sentido en diagnóstico; no lo pongas en todas las variantes ni lo devuelvas al usuario. En una CLI, RUST_BACKTRACE=1 sobre un panic! suele bastar para bugs, y la cadena de source() para fallos esperados.
