Result, el operador ? y panic!

Módulo 3 · Errores y modularidad ⏱ 40 minutos

1 · Introducción

Rust no tiene excepciones. No hay try, no hay catch, no hay una pila que se desenrolla sola hasta el primer manejador. Un fallo es un valor, y como todo valor tiene un tipo que el compilador comprueba. Esa decisión hace que una función que puede fallar no pueda fingir que no falla.

La biblioteca estándar trae dos tipos para dos situaciones. Option<T> dice «puede que no haya valor»: buscar en un mapa, sacar el primer elemento. Result<T, E> dice «puede que haya fallado, y aquí está el motivo»: abrir un fichero, parsear un número, validar una URL. Con Option no puedes explicar qué salió mal; con Result sí.

Para lo que no es un fallo esperado sino un bug — un índice fuera de rango, una invariante rota — existe panic!. Saber qué va en cada caja es la mitad de la lección; la otra mitad es el operador ?, que convierte el ruido de propagar errores en una línea.

¿Por qué existe esta lección?

Porque el 90 % del código de producción consiste en decidir qué hacer cuando algo falla. Quien viene de Java envuelve todo en try/catch; quien viene de Go escribe if err != nil veinte veces; quien viene de Python deja que la excepción suba. Rust te obliga a elegir en la firma y te da ? para que elegir no cueste veinte líneas.

Errores típicos al empezar: poner ? en un main que devuelve (); convertir todo a String y perder la causa; usar unwrap() con entrada del usuario y llamarlo «manejo de errores»; creer que ? «atrapa» el error (lo devuelve hacia arriba); mezclar Option y Result sin convertir.

2 · Teoría

Un enum con dos variantes

Result no es magia del compilador: es un enum de std con esta forma exacta.

pub enum Result<T, E> {
    Ok(T),   // el camino feliz: hay valor de tipo T
    Err(E),  // el camino triste: hay un error de tipo E
}

Que sea un enum significa que solo hay dos estados posibles y que match te obliga a tratar ambos (lo practicaste en el módulo 2). No existe el «se me olvidó comprobar el error»: si quieres el valor de dentro, o haces match, o usas un método que decide por ti (unwrap, unwrap_or, ?), y cada uno es una decisión visible en el código. Comparado con las excepciones, el coste está en la firma: el tipo de retorno documenta y verifica que la función puede fallar. Comparado con los códigos de error de C, no hay canal lateral: el error viaja dentro del valor y no se puede ignorar por accidente.

El operador ?: propagar sin ceremonia

El patrón «si es Err, devuélvelo; si es Ok, dame el valor» aparece cien veces al día. ? es azúcar para exactamente eso:

// A mano
let puerto = match raw.parse::<u16>() {
    Ok(v) => v,
    Err(e) => return Err(From::from(e)),
};

// Con el operador
let puerto = raw.parse::<u16>()?;
  let x = paso()?;
             │
             ├── Ok(v)  ──────────►  x = v · la función sigue
             │
             └── Err(e) ──────────►  return Err(From::from(e))
                                     fin de la función, error hacia arriba

Hay un detalle que casi nadie ve al principio: ? no devuelve el error tal cual, sino que lo pasa por From::from. Por eso una función que devuelve Result<T, MiError> puede usar ? sobre un io::Error, siempre que exista From<io::Error> for MiError. Es la pieza que permite unificar errores sin map_err en cada llamada; Box<dyn Error> ya trae esa conversión hecha para cualquier error de la biblioteca estándar.

El error no se «captura», se devuelve

? solo funciona si el tipo de retorno puede representar ese fallo: Result, Option o cualquier tipo que implemente FromResidual. Si main devuelve (), no hay dónde meter el error y el compilador responde con E0277.

main también puede fallar

main puede devolver Result. Lo define el trait Termination: con Ok(()) el proceso sale con código 0; con Err(e) se imprime Error: {e:?} en stderr y sale con código 1.

use std::{error::Error, fs};

fn main() -> Result<(), Box<dyn Error>> {
    let texto = fs::read_to_string("enlaces.json")?;
    println!("{} bytes leídos", texto.len());
    Ok(())
}

Con el fichero ausente verás Error: Os { code: 2, kind: NotFound, message: "No such file or directory" }. Es la opción rápida para un binario pequeño; en la próxima lección veremos por qué un enum propio es mejor cuando el programa crece.

Option frente a Result

Regla sencilla: si la ausencia es una respuesta normal, Option; si es un fallo que alguien debe poder explicar, Result. HashMap::get devuelve Option porque no encontrar una clave no es un error; abrir un fichero devuelve Result porque el sistema tiene un motivo concreto (permisos, ruta, disco).

PreguntaOption<T>Result<T, E>

La conversión se hace con ok_or_else, que construye el error solo si falta el valor: let palabra = texto.split_whitespace().next().ok_or_else(|| String::from("texto vacío"))?;. Es el puente idiomático de Option a Result.

panic!: para bugs, no para entradas

Un pánico es «este estado es imposible y no sé seguir». Por defecto desenrolla la pila (unwind), ejecuta destructores y termina el hilo; si llega al hilo principal, el proceso sale con código 101. En un servicio puede tumbar la tarea entera, así que se reserva para lo que nunca debería ocurrir: un índice que se sale del array por un bug, una invariante que el código anterior garantizaba. Los fallos previsibles —entrada del usuario, fichero ausente— van a Result, porque el llamador decide si son fatales o tienen un valor por defecto.

unwrap() y expect() son panic! con esteroides: imprimen el error con Debug, y expect añade tu mensaje. unwrap sin mensaje en producción es una trampa: cuando salta, no sabes qué intentabas hacer. Si de verdad quieres el pánico, escribe por qué: .expect("PORT debe ser un número entre 0 y 65535"). En tests y prototipos, en cambio, unwrap es lo correcto: si el andamio falla, quieres verlo de inmediato.

Códigos de salida y tres niveles de error

Un CLI habla también con scripts: el código de salida es parte de su API. Convención Unix: 0 éxito, distinto de 0 fallo, 2 para errores de uso. std::process::exit(n) termina el proceso de inmediato sin ejecutar destructores de la pila actual: úsalo en el borde del programa, no en medio de la lógica.

En cuanto al tipo de error, hay una escala: Result<T, String> vale para un ejercicio, pero el llamador acaba comparando cadenas; Box<dyn Error> vale para un binario pequeño, aunque pierdes el match exhaustivo; un enum propio con thiserror es lo correcto en una librería; y anyhow::Result<T>, con contexto y cadena de causas, es lo cómodo en una aplicación. Regla práctica: thiserror para lo que publicas, anyhow para lo que ejecutas. Una librería no debe imponer su error de aplicación; un binario no necesita una taxonomía de veinte variantes si solo va a imprimir el mensaje.

3 · Ejemplo mínimo

Leer un puerto del entorno, con un valor por defecto, y fallar si no es un número. main devuelve Result, así que ? tiene dónde devolver el fallo.

// src/main.rs
use std::num::ParseIntError;

fn read_port(name: &str) -> Result<u16, ParseIntError> {
    let raw = std::env::var(name).unwrap_or_else(|_| String::from("8080"));
    let port = raw.trim().parse::<u16>()?; // corta aquí si no es numérico
    Ok(port)
}

fn main() -> Result<(), ParseIntError> {
    let port = read_port("PORT")?;
    println!("escuchando en http://127.0.0.1:{port}");
    Ok(())
}

Ejecución:

cargo run
# escuchando en http://127.0.0.1:8080

PORT=abc cargo run; echo "salida: $?"
# Error: ParseIntError { kind: InvalidDigit }
# salida: 1

Línea a línea: unwrap_or_else(|_| …) aquí sí es correcto, porque la ausencia de la variable es normal y el valor por defecto está documentado; trim() quita el salto de línea que deja un .env (sin él, "3000\n" no parsea); parse::<u16>() explicita el rango 0–65535; y ? devuelve el Err al llamador sin imprimir nada: imprimir es responsabilidad de main, que muestra el Debug en stderr y sale con código 1.

Cambia el tipo de retorno de main a () y aparecerá el E0277 de la sección 6.

4 · Ejemplo real

urlshort empieza a comportarse como una herramienta de verdad: subcomando, errores por stderr y códigos de salida que un script puede comprobar. Ningún fallo previsible usa unwrap.

// src/main.rs — urlshort v3: errores con tipo y códigos de salida
use std::process;

fn main() {
    let mut args = std::env::args().skip(1); // el nombre del programa no cuenta

    let Some(command) = args.next() else {
        eprintln!("uso: urlshort short <url>");
        process::exit(2); // 2 = error de uso
    };
    let Some(url) = args.next() else {
        eprintln!("falta la URL de `{command}`");
        process::exit(2);
    };

    let outcome: Result<String, String> = match command.as_str() {
        "short" => short(&url),
        other => {
            eprintln!("subcomando desconocido: `{other}`");
            process::exit(2);
        }
    };

    match outcome {
        Ok(line) => println!("{line}"),
        Err(err) => {
            eprintln!("error: {err}");
            process::exit(1); // 1 = fallo de ejecución
        }
    }
}

fn short(raw: &str) -> Result<String, String> {
    let url = raw.trim();
    if url.is_empty() {
        return Err(String::from("la URL está vacía"));
    }
    if !(url.starts_with("http://") || url.starts_with("https://")) {
        return Err(format!("la URL debe empezar por http:// o https://: {url}"));
    }
    Ok(format!("{url} -> /{}", short_code(url)))
}

fn short_code(url: &str) -> String {
    use std::collections::hash_map::DefaultHasher;
    use std::hash::{Hash, Hasher};

    // Hash determinista y alfabeto sin caracteres ambiguos (0, 1, l, o).
    let mut hasher = DefaultHasher::new();
    url.hash(&mut hasher);
    let mut n = hasher.finish();

    const ALPHABET: &[u8] = b"23456789abcdefghjkmnpqrstuvwxyz";
    let mut code = String::with_capacity(6);
    for _ in 0..6 {
        code.push(ALPHABET[(n % ALPHABET.len() as u64) as usize] as char);
        n /= ALPHABET.len() as u64;
    }
    code
}

Comportamiento: urlshort short "ftp://example.com" escribe error: la URL debe empezar por http:// o https://: ftp://example.com en stderr y sale con 1; urlshort nada escribe subcomando desconocido: `nada` y sale con 2.

CódigoSignificadoQuién lo usa
0ÉxitoEl shell continúa; && encadena
1Fallo de ejecución (URL inválida, no encontrado, I/O)Scripts que distinguen «no pude» de «no existe»
2Error de uso: faltan argumentos o son incoherentesConvención de grep, git, cargo
101Pánico no controladoNadie debería programarlo: es un bug

Y el texto va a stderr con eprintln!, mientras que el resultado útil va a stdout con println!: si mezclas ambos, urlshort short … > codigos.txt guardará también los errores. Cuando el proyecto crezca (lección 2), Result<String, String> se sustituye por un enum con InvalidUrl, NotFound e Io; entonces main decidirá el código por tipo, no por el texto. Y en lugar de process::exit en cada rama puedes devolver ExitCode desde main y dejar la lógica en un run() -> Result<(), Error>: es el patrón que reutilizarás con Axum, traduciendo error a código HTTP en vez de a código del shell.

Cuidado con ? en bucles

Un ? dentro de un for devuelve el error y abandona la función: los elementos que faltaban no se procesan. Si quieres continuar, recoge los errores (Vec<Result<…>>, filter_map(Result::ok)) o decide explícitamente que el primero aborta todo. No es estilo: cambia la semántica.

6 · Errores habituales

1. Usar ? en un main que devuelve ()

Mal:

use std::fs::File;

fn main() {
    let f = File::open("datos.json")?;
    println!("{f:?}");
}
error[E0277]: the `?` operator can only be used in a function that returns `Result` or `Option` (or another type that implements `FromResidual`)
 --> src/main.rs:4:13
  |
3 | fn main() {
  | --------- this function should return `Result` or `Option` to accept `?`
4 |     let f = File::open("datos.json")?;
  |             ^^^^^^^^^^^^^^^^^^^^^^^^^ cannot use the `?` operator in a function that returns `()`
  |
  = help: the trait `FromResidual<Result<Infallible, std::io::Error>>` is not implemented for `()`

Por qué está mal: ? necesita un valor de retorno donde colocar el Err. El error no dice «falta un try»: dice exactamente qué trait falta.

Bien: cambiar la firma de main.

use std::{error::Error, fs::File};

fn main() -> Result<(), Box<dyn Error>> {
    let f = File::open("datos.json")?;
    println!("{f:?}");
    Ok(())
}

2. Devolver Ok(()) de una función que promete un valor

Mal:

use std::io;

fn cargar() -> Result<String, io::Error> {
    let texto = std::fs::read_to_string("datos.txt")?;
    Ok(()) // el tipo dice String, no ()
}
error[E0308]: mismatched types
 --> src/main.rs:6:5
  |
5 | fn cargar() -> Result<String, io::Error> {
  |                ------------------------- expected `Result<String, std::io::Error>` because of return type
6 |     Ok(())
  |     ^^^^^^ expected `String`, found `()`
  |
  = note: expected enum `Result<String, std::io::Error>`
             found enum `Result<(), _>`

Bien: devolver el valor que la firma promete. Por eso el tipo de retorno se escribe antes del cuerpo: es un contrato, y el compilador señala cada rama que no lo cumple.

fn cargar() -> Result<String, std::io::Error> {
    std::fs::read_to_string("datos.txt")
}

3. Mezclar Option y Result con ?

Mal:

fn primera(texto: &str) -> Result<&str, String> {
    let palabra = texto.split_whitespace().next()?;
    Ok(palabra)
}
error[E0277]: the `?` operator can only be used on `Result`s, not `Option`s, in a function that returns `Result`
 --> src/main.rs:2:45
  |
1 | fn primera(texto: &str) -> Result<&str, String> {
  | -------------------------- this function returns a `Result`
2 |     let palabra = texto.split_whitespace().next()?;
  |                                             ^ use `.ok_or(...)` to convert the `Option` to a `Result` before using `?`
  |
  = help: the trait `FromResidual<Option<Infallible>>` is not implemented for `Result<&str, String>`

Bien: explicar el motivo de la ausencia con ok_or_else.

fn primera(texto: &str) -> Result<&str, String> {
    texto
        .split_whitespace()
        .next()
        .ok_or_else(|| String::from("texto vacío"))
}

4. Confiar en unwrap con entrada del usuario

Mal: std::env::var("PORT").unwrap().parse().unwrap() compila y pasa los tests si nadie borra la variable, pero revienta en producción con un mensaje que habla de ParseIntError { kind: Empty }, no de lo que el operador debía hacer.

Bien: devolver el error con contexto: std::env::var("PORT").map_err(|_| String::from("falta PORT"))? y luego parse().map_err(|_| format!("no es un puerto: {raw}")). El fallo está en el código, pero así se descubre en el sitio correcto.

7 · Ejercicio guiado

Objetivo: convertir un programa que revienta con unwrap en uno que propaga con ?, distingue tipos de fallo y devuelve códigos correctos.

  1. Crea el proyecto, provoca el pánico y define un error propio. 
    cargo new urlshort --bin
cd urlshort

    Escribe una versión con unwrap al leer PORT y al parsear la URL; ejecútala sin variables de entorno y anota el pánico. Después introduce el enum y prohíbete unwrap:

    #[derive(Debug)]
enum AppError {
    MissingPort,
    InvalidPort(String),
    InvalidUrl(String),
}

    read_port y validate_url devuelven Result<_, AppError>: cada fallo es una variante.

  2. Propaga con ? desde la lógica. 
    fn run() -> Result<(), AppError> {
    let port = read_port()?;
    let url = std::env::args()
        .nth(1)
        .ok_or(AppError::InvalidUrl(String::from("falta la URL")))?;
    validate_url(&url)?;
    println!("acortando {url} en el puerto {port}");
    Ok(())
}
  3. Traduce error a código en main y pasa clippy. 
    fn main() -> std::process::ExitCode {
    match run() {
        Ok(()) => std::process::ExitCode::SUCCESS,
        Err(err) => {
            eprintln!("error: {err:?}");
            let code = match err {
                AppError::InvalidUrl(_) | AppError::InvalidPort(_) => 2,
                AppError::MissingPort => 1,
            };
            std::process::ExitCode::from(code)
        }
    }
}
    cargo clippy -- -D warnings

    eprintln!("{err:?}") solo presta el error, así que el match posterior puede moverlo. Si lo pasaras por valor a otra función, el match ya no podría usarlo (E0382). Clippy señalará además unwrap innecesario y comparaciones de String con literales.

  4. Comprueba los códigos. Sin PORT, con PORT=abc y con una URL sin esquema: los tres deben escribir en stderr y salir con el código esperado. 
    PORT=abc cargo run -- "https://x.dev"; echo "salida: $?"

Criterio de éxito

Ningún unwrap en el camino del usuario; ? en toda función que puede fallar; main como único sitio que decide códigos; y sabes explicar por qué Result<T, E> obliga a tratar Err mientras una excepción se puede ignorar.

8 · Reto

🎯 Un CLI que se porta bien con los scripts

Añade a urlshort un subcomando check <url> que no acorta nada: solo valida y responde con un código distinto según el problema.

  • 0 si la URL es válida y su host no está vacío.
  • 2 si falta el argumento o el subcomando no existe.
  • 3 si no tiene esquema o el esquema no es http/https.
  • 4 si es válida pero supera los 2048 caracteres.
  • --quiet como segundo argumento opcional: no imprime nada, solo devuelve el código.
  • Nada de unwrap: cada caso es una variante del enum.

Escribe además un script de shell que ejecute los cinco casos y falle si algún código no es el esperado. En la lección 4 harás lo mismo con tests de integración y assert_eq!.

Pista: modela el comando como Result<(), AppError> y deja que main traduzca variante → número. Para --quiet, separa la decisión de imprimir de la de calcular: son dos responsabilidades y mezclarlas duplica ramas.

9 · Resumen

  • Result<T, E> es un enum con Ok(T) y Err(E): el fallo es un valor que el compilador obliga a tratar.
  • ? devuelve el Err al llamador pasándolo por From; solo compila si el tipo de retorno puede representarlo.
  • main puede devolver Result: Err imprime el Debug en stderr y sale con código 1.
  • Option expresa ausencia; Result, fallo con motivo. ok_or_else convierte uno en otro.
  • panic! es para bugs e invariantes rotas; unwrap/expect solo en tests, prototipos o invariantes demostradas.
  • El código de salida es parte de la API del CLI: 0 éxito, 1 fallo, 2 uso incorrecto.
  • thiserror para librerías; anyhow para aplicaciones; String solo en ejercicios.

10 · Preguntas frecuentes

¿? es lento? ¿Hay coste en ejecución?

No. Se expande a un match y un return; no hay excepciones, ni desenrollado de pila, ni asignación en el heap. El compilador genera una rama que comprueba la variante y devuelve el error por valor. Es el mismo código que escribirías a mano, con menos ruido.

¿Cuándo está justificado un unwrap()?

En tests (un fallo debe reventar el test con el mensaje del error), en ejemplos y prototipos, y cuando el código anterior demuestra que el valor existe: tras comprobar la longitud, o un Regex::new("…") con patrón literal. Ahí expect("patrón literal válido") documenta la invariante y convierte un fallo imposible en un mensaje útil.

¿Por qué no hay try/catch? ¿No es más cómodo?

Es más cómodo de escribir y más difícil de auditar: una excepción puede saltar desde cualquier llamada y el compilador no avisa. En Rust, la firma -> Result<T, E> es la lista de fallos posibles, y el compilador obliga a manejarlos en algún punto. Para lo irrecuperable está panic!, que sí desenrolla.

¿anyhow sustituye a thiserror?

No: se complementan. thiserror genera Display y Error para tus enums; anyhow ofrece un error borrado con contexto y cadena de causas para aplicaciones. Lo habitual es que la librería use thiserror y el binario use anyhow con .context("…")? en las llamadas.
