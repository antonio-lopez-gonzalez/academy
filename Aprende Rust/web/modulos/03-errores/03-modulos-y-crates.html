Módulos, crates y workspaces

Módulo 3 · Errores y modularidad ⏱ 40 minutos

1 · Introducción

Todo lo que has escrito hasta ahora cabe en un main.rs. En cuanto el programa pasa de doscientas líneas, ese fichero se convierte en un cajón: la lógica de dominio, el almacén, la lectura de argumentos y los errores conviven sin fronteras, y cualquier cambio obliga a leerlo entero. Rust no resuelve eso con carpetas y buena voluntad: lo resuelve con módulos, que son unidades de visibilidad, y con crates, que son unidades de compilación.

La diferencia importa. Un módulo decide quién puede ver qué; un crate decide qué se compila junto y qué se puede reutilizar desde fuera. Un paquete de Cargo puede contener una librería, uno o varios binarios, o ambos, y un workspace agrupa varios paquetes que comparten Cargo.lock y target/.

¿Por qué existe esta lección?

Porque la modularidad no es cosmética: es lo que permite que un test de integración use tu código, que un binario y un servidor compartan el mismo dominio y que el compilador te impida tocar lo que no debe tocarse. Si tu proyecto crece sin fronteras, el borrow checker será el menor de tus problemas.

Errores típicos al empezar: creer que mod x; importa el fichero (solo lo declara); añadir pub a un elemento cuyo módulo padre es privado; olvidar que un binario no puede importarse desde otro binario; y meter todo en un crate gigante porque los workspaces parecen «cosa de empresas».

2 · Teoría

Tres palabras que no son sinónimos

TérminoQué esEjemplo
PaqueteUn Cargo.toml con un nombre y una versiónurlshort 0.1.0
CrateUna unidad de compilación: una librería o un binariosrc/lib.rs, src/main.rs
MóduloUn espacio de nombres con reglas de visibilidadmod domain;, mod store;

Un paquete puede tener como máximo una librería y varios binarios. Los binarios pueden usar la librería del mismo paquete, pero no al revés: la librería no sabe que existe un main. Esa asimetría es la que te obliga a poner la lógica en lib.rs si quieres testearla y reutilizarla.

El árbol de módulos

Los módulos forman un árbol cuya raíz es src/lib.rs o src/main.rs (cada crate tiene la suya). Un mod crea un hijo; dentro, otro mod crea un nieto. Las rutas se leen como en un sistema de ficheros, pero con raíces especiales.

  crate (urlshort)
  ├── domain            pub mod domain;
  │   ├── Link          pub struct Link
  │   └── validate_url  pub fn validate_url
  ├── store             pub mod store;
  │   ├── Store         pub trait Store
  │   └── memory        mod memory;          ← privado
  │       └── MemoryStore  pub struct, re-exportado
  └── cli               pub mod cli;

Las rutas empiezan por crate (la raíz del crate actual), super (el módulo padre), self (el módulo actual) o el nombre de otro crate. En 2018+ no hace falta extern crate: una dependencia del Cargo.toml es directamente visible.

Archivos: foo.rs o foo/mod.rs

Cuando escribes mod store; en la raíz, el compilador busca src/store.rs o src/store/mod.rs (en ese orden). Ambas formas son válidas; el estilo moderno prefiere la primera, porque deja el árbol de carpetas plano:

src/
├── main.rs          mod store;   → src/store.rs
└── store/
    └── memory.rs    mod memory;  → src/store/memory.rs
                    (declarado dentro de store.rs)

La regla que confunde al principio: el mod debe estar en el padre del fichero. src/store/memory.rs no se compila solo porque exista; necesita un mod memory; dentro de store.rs, porque memory es hijo de store. Si el fichero existe pero nadie lo declara, es código muerto que el compilador ni mira.

Visibilidad: privado por defecto

En Rust todo es privado salvo que lo marques. «Privado» significa visible para el módulo donde se declara y sus descendientes, no para el resto. Y hay un matiz que provoca la mitad de los E0603: un elemento pub dentro de un módulo privado sigue siendo inalcanzable desde fuera, porque el camino hasta él está cortado.

MarcaVisible desdeUso típico
(nada)El módulo y sus hijosDetalles de implementación
pub(crate)Cualquier punto del crate, no fueraHelpers compartidos entre módulos
pub(super)El módulo padreAPI interna de un submódulo
pubTodo el mundo, si el camino es públicoAPI de la librería

Los campos de un struct tienen su propia visibilidad: aunque el struct sea pub, sus campos son privados salvo que los marques. Los constructores públicos (Link::new) son la forma de mantener invariantes. Las variantes de un enum, en cambio, heredan la visibilidad del enum: si el enum es pub, todas sus variantes lo son.

use, super y re-exportaciones

use no mueve código: crea un alias para escribir menos. Un pub use es distinto: re-exporta, es decir, hace que el elemento sea alcanzable por ese camino público. Es la herramienta para esconder la estructura interna detrás de una fachada estable.

// src/store.rs
mod memory;              // el módulo es privado…
pub use memory::MemoryStore; // …pero el tipo se ofrece en crate::store

use crate::domain::Link; // ruta absoluta dentro del crate
use crate::error::Result;

// src/store/memory.rs
use super::Store;        // el padre: crate::store
use crate::domain::Link;
use crate::error::{DomainError, Result};

Con esa fachada, el consumidor escribe urlshort::store::MemoryStore y no urlshort::store::memory::MemoryStore. El día que cambies el almacén por SQLite, la ruta pública no cambia. Es el mismo patrón que usan std y casi todas las librerías grandes: módulos internos, tipos re-exportados en la raíz.

lib.rs + main.rs: el mismo paquete, dos crates

Si un paquete tiene src/lib.rs y src/main.rs, Cargo compila dos crates: una librería con el nombre del paquete y un binario que puede usarla con use urlshort::…. El main queda como un envoltorio de veinte líneas; toda la lógica vive en la librería y se puede testear sin ejecutar el binario.

El nombre del crate en código sustituye guiones por guiones bajos: un paquete url-short se importa como url_short. Y los tests de integración de tests/ solo pueden usar la API pública de la librería: si un test necesita algo privado, o es un test unitario dentro del módulo o tu API es demasiado estrecha.

Workspaces: varios paquetes, un build

Un workspace es un Cargo.toml sin [package] que lista miembros. Comparten Cargo.lock, target/ y perfiles, así que compilar uno no recompila las dependencias de otro. Es lo que quieres cuando la CLI y el servidor comparten el dominio pero no deberían compartir binario.

# Cargo.toml (raíz del workspace)
[workspace]
resolver = "2"
members = ["crates/urlshort-core", "crates/urlshort-cli"]

[workspace.package]
version = "0.1.0"
edition = "2021"

Un miembro declara la dependencia interna por ruta, no por versión de crates.io:

# crates/urlshort-cli/Cargo.toml
[dependencies]
urlshort-core = { path = "../urlshort-core" }

resolver = "2" es obligatorio en un workspace virtual (sin [package]), porque si no Cargo usa el resolver antiguo y las features de las dependencias se unifican de formas que ya no quieres. La edición 2021 de cada miembro no lo activa por sí sola: el resolver se decide en la raíz.

3 · Ejemplo mínimo

Un módulo en un fichero, declarado desde main.rs. mod declara; use abrevia.

// src/main.rs
mod geometry; // busca src/geometry.rs

use geometry::area;

fn main() {
    println!("{}", area(3, 4)); // 12
}
// src/geometry.rs
pub fn area(width: u32, height: u32) -> u32 {
    width * height
}

fn _doble(x: u32) -> u32 { // privada: solo visible dentro de geometry
    x * 2
}

Comprueba las fronteras:

mod geometry;

fn main() {
    println!("{}", geometry::area(3, 4)); // ok: area es pub
    // println!("{}", geometry::_doble(3)); // error[E0603]: function `_doble` is private
}

Detalles que importan: mod geometry; está en la raíz del crate, así que geometry es hijo de la raíz y main puede usarlo aunque el módulo no sea pub (lo privado es visible para el módulo que lo declara y sus descendientes). Para que lo vea un consumidor externo hacen falta dos cosas: pub mod geometry; y que el crate sea una librería (lib.rs); un binario no se puede importar desde otro crate.

4 · Ejemplo real

urlshort se divide en una librería (lib.rs) y un binario fino (main.rs). La librería expone cuatro módulos; el almacén esconde su implementación en un submódulo privado y re-exporta el tipo.

urlshort/
├── Cargo.toml
└── src/
    ├── main.rs        ← 30 líneas: argumentos y códigos de salida
    ├── lib.rs         ← API pública del crate
    ├── cli.rs         ← comandos short y resolve
    ├── domain.rs      ← Link, validate_url, short_code
    ├── error.rs       ← el enum de la lección 2
    └── store/
        └── memory.rs  ← implementación privada del almacén
# Cargo.toml
[package]
name = "urlshort"
version = "0.1.0"
edition = "2021"

[dependencies]
thiserror = "2"
// src/lib.rs — la fachada del crate
pub mod cli;
pub mod domain;
pub mod error;
pub mod store;

pub use domain::Link;
pub use error::{Error, Result};

pub use permite que el consumidor escriba urlshort::Link en lugar de urlshort::domain::Link. Es una decisión de API: si mañana mueves Link a model, la ruta pública puede seguir igual.

// src/store.rs — declara el hijo privado y publica el tipo
mod memory;

pub use memory::MemoryStore;

use crate::domain::Link;
use crate::error::Result;

/// Contrato común para el store en memoria y el de SQLite.
pub trait Store {
    fn insert(&mut self, link: Link) -> Result<()>;
    fn get(&self, code: &str) -> Result<&Link>;
}
// src/store/memory.rs
use std::collections::HashMap;

use super::Store; // el padre: crate::store
use crate::domain::Link;
use crate::error::{DomainError, Result};

#[derive(Debug, Default)]
pub struct MemoryStore {
    links: HashMap<String, Link>,
}

impl MemoryStore {
    pub fn new() -> Self {
        Self::default()
    }
}

impl Store for MemoryStore {
    fn insert(&mut self, link: Link) -> Result<()> {
        if self.links.contains_key(&link.code) {
            return Err(DomainError::Conflict(link.code).into());
        }
        self.links.insert(link.code.clone(), link);
        Ok(())
    }

    fn get(&self, code: &str) -> Result<&Link> {
        self.links
            .get(code)
            .ok_or_else(|| DomainError::NotFound(code.to_string()).into())
    }
}

El dominio no conoce el almacén ni el CLI; solo define qué es un enlace y qué es válido. Esa hoja del árbol es la que ambos lados comparten.

// src/domain.rs
use crate::error::{DomainError, Result};

#[derive(Debug, Clone, PartialEq)]
pub struct Link {
    pub code: String,
    pub url: String,
    pub hits: u64,
}

impl Link {
    pub fn new(code: impl Into<String>, url: impl Into<String>) -> Self {
        Self { code: code.into(), url: url.into(), hits: 0 }
    }
}

pub fn validate_url(raw: &str) -> Result<()> {
    let url = raw.trim();
    if !(url.starts_with("http://") || url.starts_with("https://")) {
        return Err(DomainError::InvalidUrl(url.to_string()).into());
    }
    Ok(())
}

pub fn short_code(url: &str) -> String {
    use std::collections::hash_map::DefaultHasher;
    use std::hash::{Hash, Hasher};

    let mut hasher = DefaultHasher::new();
    url.hash(&mut hasher);
    let mut n = hasher.finish();

    const ALPHABET: &[u8] = b"23456789abcdefghjkmnpqrstuvwxyz";
    let mut code = String::with_capacity(6);
    for _ in 0..6 {
        code.push(ALPHABET[(n % ALPHABET.len() as u64) as usize] as char);
        n /= ALPHABET.len() as u64;
    }
    code
}
// src/cli.rs — recibe el trait, no el tipo concreto
use crate::domain::{self, Link};
use crate::error::Result;
use crate::store::Store;

pub fn short(store: &mut impl Store, raw: &str) -> Result<String> {
    let url = raw.trim();
    domain::validate_url(url)?;
    let code = domain::short_code(url);
    store.insert(Link::new(code.clone(), url))?;
    Ok(format!("{url} -> /{code}"))
}

pub fn resolve(store: &impl Store, code: &str) -> Result<String> {
    Ok(store.get(code)?.url.clone())
}
// src/main.rs — usa el crate de la librería por su nombre
use std::process;

use urlshort::cli;
use urlshort::store::MemoryStore;

fn main() {
    let args: Vec<String> = std::env::args().skip(1).collect();
    let (Some(command), Some(arg)) = (args.first(), args.get(1)) else {
        eprintln!("uso: urlshort <short|resolve> <url|código>");
        process::exit(2);
    };

    let mut store = MemoryStore::new();
    let outcome = match command.as_str() {
        "short" => cli::short(&mut store, arg),
        "resolve" => cli::resolve(&store, arg),
        other => {
            eprintln!("subcomando desconocido: `{other}`");
            process::exit(2);
        }
    };

    match outcome {
        Ok(line) => println!("{line}"),
        Err(err) => {
            eprintln!("error: {err}");
            process::exit(1);
        }
    }
}

El main no sabe de lógica

Si tu main.rs tiene un match de negocio, un cálculo o una validación, está en el sitio equivocado: muévelo a la librería y deja en el binario solo el contrato con el sistema operativo (argumentos, stdout/stderr, código de salida). Así el mismo dominio sirve para el futuro servidor.

6 · Errores habituales

1. Importar un módulo que no está declarado

Mal: existe src/domain.rs, pero main.rs no lo declara.

// src/main.rs
use crate::domain::Link;

fn main() {}
error[E0432]: unresolved import `crate::domain`
 --> src/main.rs:1:12
  |
1 | use crate::domain::Link;
  |            ^^^^^^ could not find `domain` in the crate root

Bien: declarar el módulo en la raíz del crate. use no descubre ficheros; mod lo hace.

// src/main.rs
mod domain;

use crate::domain::Link;

fn main() {}

2. Usar un crate que no está en Cargo.toml

Mal: use serde_json::Value; sin dependencia declarada. El mensaje es distinto del anterior y muy explícito:

error[E0432]: unresolved import `serde_json`
 --> src/main.rs:1:5
  |
1 | use serde_json::Value;
  |     ^^^^^^^^^^ use of undeclared crate or module `serde_json`
  |
  = help: consider adding `serde_json` as a dependency in Cargo.toml

Bien: cargo add serde_json (o editarlo a mano). No hay extern crate que arregle esto en 2018+.

3. Elemento público dentro de un módulo privado

Mal: store.rs declara mod memory; sin pub, y el binario intenta entrar por ahí.

// src/main.rs
use urlshort::store::memory::MemoryStore;
error[E0603]: module `memory` is private
 --> src/main.rs:1:21
  |
1 | use urlshort::store::memory::MemoryStore;
  |                     ^^^^^^ private module
  |
note: the module `memory` is defined here
 --> src/store.rs:1:1
  |
1 | mod memory;
  | ^^^^^^^^^^

Por qué está mal: MemoryStore puede ser pub, pero el camino hasta él está cerrado. La visibilidad no es una propiedad del elemento: es una propiedad del camino.

Bien: re-exportar el tipo desde el módulo padre, que es el que sí es público.

// src/store.rs
mod memory;
pub use memory::MemoryStore;

Y el consumidor escribe use urlshort::store::MemoryStore;.

4. El fichero existe pero el módulo no

Mal: mod store; sin src/store.rs ni src/store/mod.rs.

error[E0583]: file not found for module `store`
 --> src/main.rs:1:1
  |
1 | mod store;
  | ^^^^^^^^^^
  |
  = help: to create the module `store`, create file "src/store.rs" or "src/store/mod.rs"

Bien: crear el fichero en la ruta que el compilador indica. Si el proyecto usa store.rs para el módulo y store/memory.rs para el hijo, el hijo se declara dentro de store.rs, no en main.rs.

7 · Ejercicio guiado

Objetivo: partir un main.rs de 150 líneas en lib + bin con tres módulos, comprobando con cargo check después de cada paso. Nunca des varios pasos a la vez: el compilador te dirá exactamente qué ruta se rompe.

  1. Punto de partida. 
    cargo new urlshort --bin
cd urlshort

    Pega un main.rs con el struct Link, la validación de URL y el almacén en un HashMap. Debe compilar y funcionar.

  2. Extrae el dominio a un fichero. Crea src/domain.rs, mueve allí Link y validate_url, y en main.rs escribe: 
    mod domain;

use domain::{validate_url, Link};

    Ejecuta cargo check. Si olvidaste algún pub, verás E0603; si olvidaste mod, E0432.

  3. Añade el almacén como módulo con hijo. Crea src/store.rs con mod memory; y pub use memory::MemoryStore;, y src/store/memory.rs con la implementación. Dentro de memory.rs, usa use super::… para el trait y use crate::domain::Link; para el dominio. 
    cargo check

    Comprueba que desde main.rs solo puedes llegar a store::MemoryStore, no a store::memory::….

  4. Convierte el binario en librería + borde. Crea src/lib.rs con los pub mod y cambia main.rs para usar use urlshort::…. La lógica de los comandos va a src/cli.rs. 
    cargo check
cargo run -- short "https://www.rust-lang.org"
cargo doc --no-deps --open

    La documentación debe mostrar los cuatro módulos públicos y la fachada Link/Error. Si aparece store::memory, tu mod no es privado.

  5. Inspecciona el grafo. 
    cargo tree
cargo metadata --no-deps --format-version 1

    cargo tree muestra dependencias; cargo metadata confirma que hay dos targets (lib y bin) y cuáles son sus rutas.

Criterio de éxito

main.rs no contiene lógica de dominio; cargo test --lib compila; los tests de integración pueden hacer use urlshort::…; y sabes explicar por qué store::memory no es alcanzable desde fuera.

8 · Reto

🎯 Del paquete único al workspace

Divide urlshort en un workspace con dos miembros: urlshort-core (dominio, errores y el trait Store) y urlshort-cli (el binario y la implementación en memoria). Requisitos:

  • [workspace] en la raíz con resolver = "2", versión y edición compartidas.
  • urlshort-cli depende de urlshort-core por path, nunca por versión.
  • urlshort-core no depende del CLI: el grafo no puede tener ciclos.
  • El binario se ejecuta con cargo run -p urlshort-cli -- short ….
  • La API de core se re-exporta desde su lib.rs con pub use.
  • Verifica con cargo tree -p urlshort-cli y cargo metadata.

Pista: si core necesita el store en memoria para sus tests, no lo metas en el binario: ponlo detrás de una feature o en un tercer miembro urlshort-store. Un workspace bien cortado se reconoce porque cada miembro se puede compilar y testear solo.

9 · Resumen

  • Paquete = Cargo.toml; crate = unidad de compilación; módulo = espacio de nombres con visibilidad.
  • mod x; declara el módulo y busca x.rs o x/mod.rs; no importa nada.
  • Todo es privado por defecto; pub(crate), pub(super) y pub abren la visibilidad.
  • Un pub dentro de un módulo privado sigue siendo inalcanzable: la visibilidad es del camino.
  • use abrevia; pub use re-exporta y construye una fachada estable.
  • lib.rs + main.rs producen dos crates: el binario puede usar la librería, nunca al revés.
  • Un workspace comparte Cargo.lock y target/; los miembros se enlazan por path.
  • cargo tree y cargo metadata son las herramientas para ver el grafo real.

10 · Preguntas frecuentes

¿foo.rs o foo/mod.rs? ¿Cuál es mejor?

Ambos funcionan y no puedes tener los dos a la vez. El estilo 2018+ prefiere foo.rs + foo/bar.rs porque el árbol de carpetas refleja el de módulos sin un mod.rs en cada nivel. mod.rs sigue siendo válido, y muchas bases de código antiguas lo usan; lo importante es ser consistente.

¿Por qué mi tipo pub no se ve desde otro crate?

Porque algún módulo del camino no es pub. La visibilidad se compone: para llegar a crate::store::memory::MemoryStore, store y memory deben ser públicos (o el tipo debe re-exportarse desde un módulo que sí lo sea). El error E0603 te señala exactamente qué eslabón está cerrado.

¿Puede un binario importar otro binario del mismo paquete?

No. Cada binario es un crate independiente y no expone API. Si dos binarios comparten lógica, esa lógica va a la librería (lib.rs) o a un crate aparte. Es la razón por la que el patrón «lib + bin» aparece en casi todos los proyectos Rust que crecen.

¿Cuándo merece la pena un workspace?

Cuando hay más de un artefacto que comparte código (CLI y servidor, core y plugins), cuando quieres compilar y testear un miembro sin arrastrar los demás, o cuando necesitas versionar piezas por separado. Para un único binario con su librería, el paquete con lib.rs y main.rs es suficiente; añadir un workspace solo agrega ceremonia.

¿Qué pasa si dos módulos se importan mutuamente?

A nivel de módulos, Rust lo permite: los use no crean dependencias de compilación por sí mismos. A nivel de crates, no: el grafo de dependencias de Cargo es acíclico. Si dos crates se necesitan mutuamente, la solución es extraer lo común a un tercer crate, no forzar el ciclo.
