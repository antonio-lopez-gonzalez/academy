async/await, futures y el runtime

Módulo 5 · Concurrencia y async ⏱ 45 minutos

1 · Introducción

Un hilo del sistema operativo cuesta unos 2 MiB de stack y un cambio de contexto. Para cuatro tareas va sobrado. Para diez mil conexiones que pasan el 99 % del tiempo esperando, es un desperdicio: diez mil stacks reservados para no hacer nada.

async/await propone lo contrario: escribir código que parece secuencial y bloqueante, pero que se compila a una máquina de estados que se detiene en cada espera y deja el hilo libre para otra tarea. Diez mil conexiones caben en unos pocos hilos porque ninguna ocupa un hilo mientras espera.

A diferencia de JavaScript o C#, Rust no trae runtime. La biblioteca estándar define el trait Future, pero no sabe ejecutarlo ni qué es un socket no bloqueante. Eso lo aporta un crate: Tokio, async-std o smol. Si vienes de los canales, ya sabes que mover datos evita candados; aquí cambia el medio, no la idea. Esa separación explica la mitad de los errores que verás: async fn sin runtime no hace nada, y bloquear el hilo dentro de una tarea congela a todas las demás.

¿Por qué existe esta lección?

Porque async se copia muy bien y se entiende muy mal. Aquí no vas a memorizar .await: vas a ver qué devuelve una async fn, quién la sondea, por qué existe Pin y por qué un MutexGuard atravesando un .await rompe la compilación.

Errores típicos al empezar: usar std::thread::sleep dentro de una tarea; meter código CPU-bound en async; llamar a async fn sin .await y no ver nada; retener un MutexGuard de std a través de un .await; creer que #[tokio::main] paraleliza tus await.

2 · Teoría

Un future es una máquina de estados

Una async fn no devuelve su valor: devuelve un tipo anónimo que implementa Future. Llamarla no ejecuta nada; solo construye la máquina de estados en su estado inicial. Lo que la hace avanzar es poll:

pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> { Ready(T), Pending }

Ready significa «terminé, aquí está el valor». Pending significa «ahora no puedo avanzar; cuando haya novedades, avisa a este Waker y vuelve a sondearme». El Waker conecta la máquina de estados con el mundo: el reactor de E/S lo llama cuando el socket tiene datos y el executor vuelve a hacer poll.

  async fn acortar(url: &str) -> Link {
      let ok = validar(url).await;      // punto de suspensión 1
      guardar(url, ok).await;           // punto de suspensión 2
      Link { .. }
  }

  estado 0 ──poll──► validar() ──Pending──► control al executor
      ▲                                        │
      └──────── wake() cuando la E/S está lista ┘
  estado 1 ──poll──► guardar() ──Ready──► estado 2 ──► Ready(Link)

  el compilador genera un enum con un estado por cada await

Ese enum guarda las variables locales que sobreviven a cada suspensión: por eso async no reserva memoria en cada llamada, pero sí puede tener un tamaño sorprendente.

.await no bloquea: cede

Cuando escribes fut.await, el compilador genera un bucle que sondea fut y propaga Pending hasta el executor. El hilo queda libre y el executor pasa a otra tarea. La ilusión es perfecta: tu código parece una función normal, pero cada .await es un punto donde puede pausarse y reanudarse más tarde, en el mismo hilo o en otro. De ahí que async no sea paralelismo: dos await consecutivos dentro de la misma tarea se suman siempre.

Por qué hace falta un runtime

Un future es pasivo: alguien tiene que sondearlo, y alguien tiene que avisar cuando la E/S está lista. Ese «alguien» es el runtime, con tres piezas: el executor (cola de tareas listas, las sondea y reencola), el reactor (habla con epoll, kqueue o IOCP y despierta a las tareas cuya operación terminó) y los timers (la cola de sleep, timeout e interval).

RuntimePerfilCuándo elegirlo
TokioEstándar de facto: multihilo por defecto, red, timers, sync, fsServicios y clientes de red; es lo que usan Axum y reqwest

Este curso usa Tokio 1 porque es lo que hay detrás de Axum, reqwest y la mayor parte del ecosistema. El código async que escribas no está atado al runtime salvo en el arranque y en las primitivas de sincronización.

async en traits: AFIT y async_trait

Desde Rust 1.75 un trait puede declarar async fn directamente (AFIT, async fn in trait): trait Store { async fn resolve(&self, code: &str) -> Option<String>; }. Funciona con genéricos e impl Trait, pero no con dyn Trait: cada implementación devuelve un future de tamaño distinto y el objeto trait necesita uno fijo. Para dyn se usa el crate async-trait, que transforma el método en uno que devuelve Pin<Box<dyn Future>>, a cambio de una asignación por llamada. Regla práctica: AFIT si puedes; async-trait solo si necesitas objetos trait, como inyectar el store en Axum.

Pin, a alto nivel

Los futures generados pueden guardar referencias a sus propias variables locales: son auto-referenciales. Si se movieran en memoria después de empezar, esas referencias quedarían colgando. Pin<&mut F> es la promesa de «no voy a mover este valor», y por eso poll lo pide. En la práctica solo te topas con él al escribir combinadores o cuando select! te pide fijar un future: se resuelve con Box::pin o pin!.

Cancelar es soltar

Rust no tiene cancel(): soltar el future lo cancela. Si un timeout vence o descartas el JoinHandle, el future se destruye y su estado se pierde en el punto exacto donde estaba suspendido. No hay rollback automático más allá de los Drop de sus campos. Es barato y funciona con cualquier future, pero una operación a medias puede dejar datos inconsistentes: diseña operaciones cancel-safe o protégelas con transacciones.

3 · Ejemplo mínimo

Una async fn, su .await y lo mínimo para ejecutarla. Añade Tokio a las dependencias (features = ["full"] trae runtime, timers, red y macros) y thiserror, que ya usas desde el módulo 3:

[dependencies]
tokio = { version = "1", features = ["full"] }
thiserror = "2"
// src/main.rs
use std::time::Duration;

#[tokio::main]
async fn main() {
    let inicio = std::time::Instant::now();
    let code = acortar("https://www.rust-lang.org/learn").await;
    println!("codigo = {code} en {:?}", inicio.elapsed());
}

async fn acortar(url: &str) -> String {
    // simula una llamada de red: cede el hilo en lugar de bloquearlo
    tokio::time::sleep(Duration::from_millis(50)).await;

    let mut h: u64 = 0xcbf2_9ce4_8422_2325;
    for b in url.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(0x0000_0100_0000_01b3);
    }
    format!("{:06x}", h & 0xff_ffff)
}
cargo run
codigo = 3f9c21 en 50.312ms

Línea a línea:

  • #[tokio::main] es una macro que envuelve tu async fn main en un runtime: crea el executor, monta el reactor y llama a block_on. Sin ella, async fn main no compila como punto de entrada.
  • acortar(...) devuelve un future; nada ocurre hasta el .await. Si lo quitas, el compilador avisa de que el future no se usa.
  • tokio::time::sleep registra un temporizador y devuelve Pending: el hilo queda libre para otra tarea. Ese es todo el truco.
  • El format! final es código normal: se ejecuta de una vez cuando el future se reanuda. El tiempo medido es ~50 ms, no 0: el await espera de verdad. Lo que no hace es ocupar un hilo mientras espera.

4 · Ejemplo real

Acortar una URL en urlshort implica validarla, generar el código y guardarla. En la versión asíncrona, validar y guardar son E/S y se componen con ? como cualquier otra función.

use std::collections::HashMap;
use std::sync::Arc;
use std::time::Duration;
use tokio::sync::Mutex;

#[derive(Debug)]
pub struct Link {
    pub code: String,
    pub url: String,
}

#[derive(Debug, thiserror::Error)]
pub enum ShortError {
    #[error("la url está vacía")]
    Empty,
}

pub struct Store {
    links: Mutex<HashMap<String, String>>,
}

impl Store {
    pub fn new() -> Arc<Self> {
        Arc::new(Self { links: Mutex::new(HashMap::new()) })
    }

    /// Simula una comprobación de red (en el módulo 6 será una base de datos).
    async fn validar(&self, url: &str) -> Result<(), ShortError> {
        if url.trim().is_empty() {
            return Err(ShortError::Empty);
        }
        tokio::time::sleep(Duration::from_millis(150)).await;
        Ok(())
    }

    async fn guardar(&self, code: String, url: String) -> Result<Link, ShortError> {
        tokio::time::sleep(Duration::from_millis(100)).await;
        self.links.lock().await.insert(code.clone(), url.clone());
        Ok(Link { code, url })
    }
}

async fn acortar(store: &Store, url: &str) -> Result<Link, ShortError> {
    store.validar(url).await?;            // el ? funciona igual que en síncrono

    let mut h: u64 = 0xcbf2_9ce4_8422_2325;
    for b in url.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(0x0000_0100_0000_01b3);
    }
    let code = format!("{:06x}", h & 0xff_ffff);
    store.guardar(code, url.to_string()).await
}

Y el main que lo usa, con la cuenta del tiempo:

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let store = Store::new();
    let inicio = std::time::Instant::now();

    for url in ["https://www.rust-lang.org/learn", "https://crates.io/crates/tokio"] {
        let link = acortar(&store, url).await?;
        println!("/{}  {}", link.code, link.url);
    }
    println!("2 enlaces en {:?}", inicio.elapsed());   // ~500 ms
    Ok(())
}

El detalle que importa: los dos enlaces tardan 500 ms, la suma de 250 ms por enlace. Tener un runtime multihilo no paraleliza los await de una misma tarea. La lección siguiente lo resuelve con tokio::join! y tokio::spawn; aquí basta con ver el síntoma y saber que no es un bug.

Dos decisiones que ya son de producción

tokio::sync::Mutex en vez de std::sync::Mutex porque el candado cruza un .await; y E/S simulada con sleep detrás de funciones propias, de modo que cambiar la latencia por una base de datos real no cambie ninguna firma.

5 · Buenas prácticas

La pregunta que lo detecta todo

Antes de poner async en un proyecto, pregúntate: ¿el cuello de botella es esperar o calcular? Si es esperar (red, disco, base de datos), async escala. Si es calcular, necesitas hilos o spawn_blocking, no un executor. Y si son cuatro tareas, ni te molestes: usa hilos.

6 · Errores habituales

1. Bloquear el executor con std::thread::sleep

Mal: dos tareas que esperan 200 ms, pero el hilo se duerme en la primera.

#[tokio::main]
async fn main() {
    let inicio = std::time::Instant::now();
    tokio::join!(esperar(1), esperar(2));
    println!("{:?}", inicio.elapsed());        // ~400 ms, no ~200
}

async fn esperar(id: u32) {
    std::thread::sleep(std::time::Duration::from_millis(200));   // ¡bloquea!
    println!("tarea {id}");
}

Por qué está mal: join! sí conduce ambas tareas a la vez, pero la primera que corre nunca devuelve Pending: se queda dormida dentro del hilo del executor y la segunda no empieza hasta que suelta. Con muchas tareas, el servidor deja de responder.

Bien: usa el temporizador del runtime; el total pasa a ser ~200 ms.

async fn esperar(id: u32) {
    tokio::time::sleep(std::time::Duration::from_millis(200)).await;   // cede
    println!("tarea {id}");
}

2. Cruzar un .await con un MutexGuard de std

Mal:

let store = Arc::new(Mutex::new(HashMap::new()));
let copia = Arc::clone(&store);

tokio::spawn(async move {
    let mut guard = copia.lock().expect("lock");
    guard.insert("k7m2qd".to_string(), "https://rust-lang.org".to_string());
    tokio::time::sleep(std::time::Duration::from_millis(10)).await;
    println!("{} enlaces", guard.len());     // el guard sigue vivo aquí
});
error[E0277]: `std::sync::MutexGuard<'_, HashMap<String, String>>` cannot be sent
              between threads safely
   --> src/main.rs:4:10
    |
4   |     tokio::spawn(async move {
    |           ------ ^^^^^^^^^^ future cannot be sent between threads safely
    |           |      |
    |           |      within this `{async block@src/main.rs:4:10: 4:30}`
    |           required by a bound introduced by this call
    |
    = help: the trait `Send` is not implemented for
            `MutexGuard<'_, HashMap<String, String>>`
note: future is not `Send` as this value is used across an await
    |
7   |         tokio::time::sleep(std::time::Duration::from_millis(10)).await;
    |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    |         await occurs here, with `guard` maybe used later

Por qué está mal: tokio::spawn puede mover la tarea a otro hilo, así que exige un future Send. El guard de std no lo es, y el compilador detecta que sigue vivo después del await.

Bien: acorta el ámbito si el candado no necesita cruzar el await; si debe cruzarlo, usa tokio::sync::Mutex.

{
    let mut guard = copia.lock().expect("lock");
    guard.insert("k7m2qd".to_string(), "https://rust-lang.org".to_string());
}                                             // guard liberado aquí
tokio::time::sleep(std::time::Duration::from_millis(10)).await;

// o bien: candado async, cuyo guard sí es Send
let links = tokio::sync::Mutex::new(HashMap::<String, String>::new());
let mut guard = links.lock().await;

3. Un temporal que no vive hasta el await

Mal:

async fn registrar(code: &str) {
    let mensaje = &format!("visita a {code}");     // referencia a un temporal
    tokio::time::sleep(std::time::Duration::from_millis(5)).await;
    println!("{mensaje}");
}
error[E0716]: temporary value dropped while borrowed
 --> src/main.rs:2:20
  |
2 |     let mensaje = &format!("visita a {code}");
  |                    ^^^^^^^^^^^^^^^^^^^^^^^^^ creates a temporary value which is
  |                                               freed while still in use
3 |     tokio::time::sleep(std::time::Duration::from_millis(5)).await;
  |     --------------------------------------------------------- borrow later used here
  |
  = note: consider using a `let` binding to create a longer lived value

Por qué está mal: el future debe guardar mensaje mientras está suspendido, pero mensaje apunta a un String temporal que muere al final de la sentencia. En código síncrono el temporal viviría lo suficiente; aquí el await alarga el préstamo más allá de su dueño.

Bien: sé dueño del dato, o créalo antes del await.

let mensaje = format!("visita a {code}");   // String con dueño
tokio::time::sleep(std::time::Duration::from_millis(5)).await;
println!("{mensaje}");

Y si el trabajo es caro de CPU, no lo metas en async: tokio::task::spawn_blocking lo ejecuta en el pool de hilos bloqueantes y deja el executor libre.

7 · Ejercicio guiado

Objetivo: escribir un future a mano y un block_on mínimo, para que poll, Pending y Waker dejen de ser teoría. Sin dependencias externas.

  1. Crea el proyecto. 
    cargo new futures-a-mano --bin
cd futures-a-mano
  2. Escribe un future que tarda tres sondeos y un executor mínimo. 
    use std::future::Future;
use std::pin::pin;
use std::task::{Context, Poll, Waker};

struct TerceraVez { sondeos: u8 }

impl Future for TerceraVez {
    type Output = u8;

    fn poll(self: std::pin::Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<u8> {
        let this = self.get_mut();       // el struct es Unpin
        this.sondeos += 1;
        if this.sondeos < 3 { Poll::Pending } else { Poll::Ready(this.sondeos) }
    }
}

fn block_on<F: Future>(fut: F) -> F::Output {
    let mut fut = pin!(fut);             // fija el future en el stack
    let waker = Waker::noop();           // despertador vacío: reintentamos nosotros
    let mut cx = Context::from_waker(waker);
    let mut vueltas = 0u32;

    loop {
        vueltas += 1;
        match fut.as_mut().poll(&mut cx) {
            Poll::Ready(valor) => {
                println!("listo tras {vueltas} sondeos");
                return valor;
            }
            Poll::Pending => std::thread::yield_now(),
        }
    }
}

fn main() {
    println!("sondeos = {}", block_on(TerceraVez { sondeos: 0 }));
}
  3. Ejecuta y lee la salida. 
    cargo run
    listo tras 3 sondeos
sondeos = 3

    Eso es un executor en veinte líneas: sondear, recibir Pending, reintentar. Waker::noop() es un despertador que no hace nada; por eso el bucle insiste. Un executor real, en lugar de girar, aparca el hilo hasta que el Waker lo despierta.

  4. Comprueba el coste de girar en vacío. Cambia yield_now por un contador y mira la CPU con top o el Monitor de actividad. No lo dejes así: es exactamente lo que hace un bucle mal escrito en un servidor async. Termina con: 
    cargo clippy -- -D warnings

Criterio de éxito

Sabes explicar qué devuelve una async fn (un future, no el valor) y quién la hace avanzar (el executor, con poll). Y sabes por qué .await no bloquea el hilo aunque tu código parezca lineal.

8 · Reto

🎯 Un timeout propio

Escribe un combinador Timeout<F> que implemente Future y devuelva Option<F::Output>: Some(valor) si el future interno termina antes del límite y None si vence. No puedes usar tokio::time::timeout; sí puedes usar tokio::time::Sleep y su método poll_elapsed, fijándolo con Pin<Box<Sleep>>.

Debe respetar el contrato: si el future interno devuelve Poll::Pending, también se registra el Waker del temporizador; si vence, se devuelve None y el future interno se descarta. Añade un test con #[tokio::test] y tokio::time::pause() (feature test-util) que compruebe los dos caminos.

Pista: guarda el future interno como Pin<Box<F>> y sondea con self.as_mut(). Crea el Sleep al construir el combinador, no en el primer poll: si lo creas tarde, el plazo empieza a contar cuando ya has perdido tiempo. Y pasa siempre cx.waker() a ambas mitades.

9 · Resumen

  • Una async fn devuelve un future: una máquina de estados que no se ejecuta hasta que alguien la sondea.
  • poll devuelve Ready(valor) o Pending; el Waker avisa de cuándo merece la pena volver a sondear.
  • .await cede el hilo, no lo bloquea. La concurrencia no es paralelismo: dos await seguidos se suman.
  • Rust no incluye runtime: Tokio, async-std o smol aportan executor, reactor y timers.
  • AFIT (1.75) permite async fn en traits; para dyn Trait hace falta async-trait. Pin impide mover un future auto-referencial y casi siempre se resuelve con Box::pin o pin!.
  • Soltar un future lo cancela: diseña operaciones cancel-safe.
  • Bloquear el executor (sleep, CPU, E/S de std) es el error más caro: usa tokio::time y spawn_blocking.
ComandoQué hace
#[tokio::main]Envuelve main en un runtime y lo ejecuta con block_on.
tokio::time::sleep(d).awaitEspera sin bloquear el hilo; el temporizador vive en el runtime.

tokio::task::spawn_blocking(f)Mueve trabajo bloqueante al pool de hilos, fuera del executor.

10 · Preguntas frecuentes

¿async es más rápido que los hilos?

Depende de la carga. Con pocas tareas y mucho cálculo, los hilos son igual de rápidos o más, y el código es más simple. Con miles de conexiones que esperan E/S, async gana porque no reserva un stack por conexión ni paga un cambio de contexto por espera. La pregunta correcta no es «¿qué es más rápido?» sino «¿cuántas tareas simultáneas y cuánto esperan?».

¿Por qué no hay runtime en la biblioteca estándar?

Porque el runtime ideal depende del caso: unos quieren un executor multihilo con reactor de red, otros un bucle mínimo para un microcontrolador. La biblioteca estándar define el contrato (Future, Poll, Waker) y deja la implementación al ecosistema, igual que con los asignadores.

¿Puedo mezclar Tokio con std::thread?

Sí, y a veces es lo correcto: un hilo dedicado a un cálculo largo, o spawn_blocking para E/S de fichero. Lo que no puedes es bloquear el hilo del executor con una operación lenta. La regla mental: fuera del runtime, hilos normales; dentro, solo trabajo que cede o spawn_blocking.

¿Qué es exactamente Pin y cuándo me tengo que preocupar?

Pin garantiza que un valor no se mueve de sitio en memoria. Los futures generados por async fn pueden contener referencias a sus propias variables, así que moverlos los rompería. En la práctica solo te topas con él al escribir un combinador a mano o cuando select! te pide fijar un future: se resuelve con Box::pin o pin!.

Si cancelo una tarea, ¿se ejecuta su Drop?

Sí: al soltar el future se destruyen sus campos y se ejecutan sus Drop. Lo que no hay es una «cancelación ordenada» automática: la tarea no recibe una señal ni puede terminar su trabajo antes de morir. Si necesitas cerrar una conexión o revertir algo, ponlo en un Drop o usa un mecanismo explícito como CancellationToken, que verás en la lección 4.
