Instalación: rustup, cargo y rust-analyzer

Módulo 0 · Fundamentos ⏱ 35 minutos

1 · Introducción

Instalar Rust no es descargar un compilador: es instalar tres piezas que trabajan juntas. rustup decide qué versión del lenguaje usas, cargo orquesta la compilación y las dependencias, y rustc convierte tu código en un binario. Si no entiendes qué hace cada una, el primer mensaje de error te parecerá magia negra.

La buena noticia es que Rust tiene, probablemente, la mejor historia de instalación de cualquier lenguaje de sistemas. Un instalador por usuario, componentes que se añaden bajo demanda, actualizaciones de una línea y un LSP (Language Server Protocol) de primera categoría. Nada de tocar variables de entorno a mano ni de compilar el compilador durante dos horas.

¿Por qué existe esta lección?

Porque el 80 % de los problemas del primer día son de entorno, no de lenguaje: un linker que falta en Windows, un cargo que no aparece en PowerShell, dos toolchains mezcladas o un editor que no ve la biblioteca estándar. Todos tienen una causa concreta y una solución de un minuto. Aprenderlas ahora evita horas de frustración cuando el código aún no es el problema.

Errores típicos al instalar Rust:

  • Instalar rustc desde el gestor de paquetes de la distribución y quedarse sin cargo, clippy ni rustup.
  • Instalar en Windows sin las Build Tools de C++ y descubrirlo en el primer cargo build.
  • Mezclar la toolchain nativa de Windows con la de WSL2 y depurar rutas que no existen.

2 · Teoría

Las cuatro piezas del entorno

HerramientaQué esCuándo la usas

rustcEl compilador: analiza tipos, propiedad y vidas, genera LLVM IR y llama al linker del sistema.Casi nunca a mano. Cargo lo invoca por ti.
cargoBuild system y gestor de paquetes: dependencias, perfiles, tests, docs y publicación.Todo el día: build, run, test, fmt, clippy.

  rustup                     elige QUÉ versión de Rust se usa
    │
    ├── toolchain stable-x86_64-pc-windows-msvc
    │     ├── rustc        compilador (tipos → MIR → LLVM IR → objeto)
    │     ├── cargo        build system + resolución de dependencias
    │     ├── rustfmt      formateador oficial
    │     ├── clippy       linter oficial
    │     ├── rust-src     fuentes de std (las usa rust-analyzer)
    │     └── rust-analyzer  servidor de lenguaje
    │
    └── toolchain nightly-...
          └── (mismas piezas, distinta versión del lenguaje)

La flecha vertical importa: cargo no compila. Cargo construye el grafo de dependencias, decide los flags y llama a rustc una vez por crate. Y rustc tampoco genera el ejecutable final: emite ficheros objeto y delega en el linker del sistema (link.exe en Windows-MSVC, cc en Linux y macOS). Cuando ese enlace falla, el mensaje lo dice con la palabra linker.

Toolchains, canales y targets

Una toolchain es un conjunto concreto de compilador, biblioteca estándar y herramientas, identificado por tres cosas:

  • Canal: stable (cada seis semanas), beta (la siguiente) o nightly (diaria, con features inestables). También puedes fijar una versión exacta, como 1.85.0.
  • Target triple: plataforma de destino. x86_64-pc-windows-msvc, aarch64-apple-darwin, x86_64-unknown-linux-gnu.
  • Perfil: minimal (solo rustc, cargo y std), default (añade rustfmt, clippy y rust-docs) o complete.

Las componentes se añaden o se quitan sin reinstalar nada. En este curso necesitas tres desde el principio:

rustup component add clippy rustfmt rust-src
rustup component list --installed

rust-src no es para compilar: es el código fuente de la biblioteca estándar, y es lo que permite a rust-analyzer llevarte a la definición de Vec::push en lugar de dejarte en un tipo opaco.

Instalar en Windows: nativo o WSL2

Hay dos caminos legítimos y conviene elegir uno conscientemente:

CaminoRequisitosCuándo elegirlo
Nativo (MSVC)rustup-init.exe + Visual Studio Build Tools con la carga «Desarrollo para el escritorio con C++»Herramientas de escritorio, integración con Windows, depuración con CodeLLDB o MSVC, proyectos que no van a desplegarse en Linux.
WSL2 + UbuntuWindows 10/11 con virtualización, wsl --install -d Ubuntu, toolchain instalada dentro de LinuxServicios que se despliegan en Linux, Docker, scripts de CI idénticos a producción. Es la opción recomendada en este curso si trabajas en Windows y vas a hacer el servidor HTTP.

Instalación nativa desde PowerShell:

# Opción 1: winget (Windows 10/11 con App Installer)
winget install --id Rustlang.Rustup -e

# Opción 2: descargar rustup-init.exe desde https://rustup.rs y ejecutarlo
# Acepta las opciones por defecto: toolchain stable, host x86_64-pc-windows-msvc

El instalador detecta si falta el compilador de C++ y te ofrece instalar las Build Tools. Acepta: son el linker y las cabeceras del sistema, y sin ellas Rust no puede producir un .exe. No hace falta Visual Studio completo, solo las Build Tools con el workload de C++ y el Windows SDK.

Instalación en WSL2, Linux o macOS:

# WSL2 (desde PowerShell, una sola vez)
wsl --install -d Ubuntu

# Ya dentro de Ubuntu, o en Linux/macOS:
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"      # o abre una terminal nueva
rustc --version

No mezcles toolchains entre sistemas

Si compilas desde WSL2, los binarios son de Linux y no se ejecutan en PowerShell; y si abres el proyecto con VS Code en modo Windows, el cargo que encuentra es otro. Elige un lado, abre la carpeta con «WSL: Connect to WSL» y deja que todo —editor, terminal, toolchain— viva en el mismo sistema de archivos. Además, compilar sobre /mnt/c es entre 5 y 20 veces más lento que sobre el sistema de archivos de Linux: guarda el proyecto en ~/code.

PATH: dónde vive todo y por qué «no encuentra cargo»

rustup instala por usuario, sin permisos de administrador, en dos directorios:

SistemaHerramientasToolchains
Linux / macOS / WSL2~/.cargo/bin~/.rustup/toolchains/
Windows%USERPROFILE%\.cargo\bin%USERPROFILE%\.rustup\toolchains\

El instalador añade .cargo\bin al PATH del usuario, pero las terminales ya abiertas conservan el entorno antiguo. Ese es el motivo número uno de «cargo no se reconoce». Comprobarlo:

# bash / zsh
echo $PATH
which cargo

# PowerShell
$env:Path -split ';'
Get-Command cargo

El editor: VS Code + rust-analyzer

Instala la extensión rust-analyzer (rust-lang.rust-analyzer). No necesitas nada más para empezar, aunque estas tres incorporaciones se agradecen: Even Better TOML para Cargo.toml, CodeLLDB para depurar y crates para ver la versión instalada de cada dependencia. En los ajustes del proyecto, dos líneas que cambian el día a día:

{
  "rust-analyzer.check.command": "clippy",
  "rust-analyzer.cargo.allTargets": true
}

La primera hace que los errores en vivo vengan de clippy (más útil que solo rustc); la segunda incluye tests y ejemplos en el análisis, de modo que el editor también los revisa. Si el autocompletado no encuentra la biblioteca estándar, casi siempre falta rust-src o el editor se abrió antes de instalar el toolchain: ejecuta «Rust Analyzer: Restart Server».

Anatomía de un proyecto creado por Cargo

urlshort/
├── Cargo.toml          manifiesto: nombre, versión, edición, dependencias
├── Cargo.lock          versiones exactas resueltas (se genera al compilar)
├── .gitignore          ignora /target
├── src/
│   └── main.rs         punto de entrada del binario
├── target/             artefactos de compilación (nunca se versiona)
└── rust-toolchain.toml opcional: fija la versión para todo el equipo

cargo new crea además un repositorio Git si no estás dentro de uno; si no lo quieres, añade --vcs none. Para una biblioteca, cargo new --lib genera src/lib.rs.

3 · Ejemplo mínimo

Cuatro comandos para pasar de «no tengo Rust» a «tengo un binario que se ejecuta».

# 1. Comprobar que el instalador ha hecho su trabajo
rustc --version
cargo --version

# 2. Ver qué toolchain está activa y de dónde sale
rustup show

# 3. Crear un proyecto ejecutable y entrar en él
cargo new hola-cargo --bin
cd hola-cargo

# 4. Compilar y ejecutar
cargo run

Salida esperada:

$ rustc --version
rustc 1.85.0 (...)
$ cargo --version
cargo 1.85.0 (...)

$ cargo run
   Compiling hola-cargo v0.1.0 (/home/ana/hola-cargo)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.42s
     Running `target/debug/hola-cargo`
Hello, world!

Los paréntesis de --version contienen el hash del commit y la fecha de compilación; cambian con cada versión. Lo importante es que rustc y cargo reporten la misma.

Línea a línea:

  • rustc --version confirma que el compilador está en el PATH y qué versión se usará.
  • rustup show es el comando que resuelve dudas: lista toolchains instaladas, la activa y los overrides por directorio.
  • cargo new genera el manifiesto y el src/main.rs con un «Hello, world!» que ya compila.
  • cargo run compila en modo debug si hace falta y ejecuta target/debug/hola-cargo. La línea Compiling solo aparece la primera vez o tras un cambio.

4 · Ejemplo real

Arrancamos urlshort. No basta con cargo new: un repositorio que va a compartirse necesita que todo el equipo compile con la misma versión y que el editor aplique las mismas reglas. Eso son tres ficheros pequeños.

cargo new urlshort --bin
cd urlshort
mkdir .vscode

1. El manifiesto, con la edición fijada y la versión mínima de Rust declarada:

[package]
name = "urlshort"
version = "0.1.0"
edition = "2021"
rust-version = "1.85"

[dependencies]
# vacío por ahora: el módulo 4 empieza a añadir crates

2. La toolchain del proyecto. En lugar de confiar en la versión global de cada máquina, se fija aquí. rustup la instala sola la primera vez que ejecutes cargo dentro de la carpeta:

[toolchain]
channel = "1.85.0"
components = ["rustfmt", "clippy", "rust-src"]
profile = "minimal"

3. Los ajustes del editor, versionados con el código para que nadie discuta sobre formato o lints:

{
  "rust-analyzer.check.command": "clippy",
  "rust-analyzer.cargo.allTargets": true
}

Y el primer src/main.rs, que ya hace algo útil: leer una URL de los argumentos y anunciar el código que le correspondería.

// src/main.rs — esqueleto de urlshort, sin dependencias externas
use std::collections::hash_map::DefaultHasher;
use std::hash::{Hash, Hasher};

fn main() {
    let args: Vec<String> = std::env::args().collect();

    if args.len() < 2 {
        eprintln!("uso: urlshort <url>");
        std::process::exit(2);
    }

    let url = &args[1];
    println!("{url} -> /{}", short_code(url));
}

fn short_code(url: &str) -> String {
    let mut hasher = DefaultHasher::new();
    url.hash(&mut hasher);
    let n = hasher.finish();

    const ALPHABET: &[u8] = b"23456789abcdefghjkmnpqrstuvwxyz";
    let mut code = String::with_capacity(6);
    for i in 0..6 {
        let idx = ((n >> (i * 6)) % ALPHABET.len() as u64) as usize;
        code.push(ALPHABET[idx] as char);
    }
    code
}

rustup show. Muestra la toolchain activa, las instaladas y de dónde sale el override (un fichero rust-toolchain.toml, una variable o el directorio). Si algo compila distinto de lo que esperas, empieza por ahí antes de tocar nada.

6 · Errores habituales

1. Falta el linker de MSVC en Windows

El instalador de Rust copia el compilador, pero no el enlazador de C++: ese viene con Visual Studio Build Tools. El síntoma es este, y aparece en el primer cargo build:

error: linker `link.exe` not found
  |
  = note: program not found

error: could not compile `hola-cargo` (bin "hola-cargo") due to 1 previous error

Por qué ocurre: Rust genera ficheros objeto y necesita un linker para unirlos con el runtime de C. En Windows-MSVC ese enlazador es link.exe, que solo existe si instalaste el workload de C++.

Cómo se arregla: ejecuta el instalador de las Build Tools, marca «Desarrollo para el escritorio con C++» (incluye MSVC v143 y Windows SDK), reinicia la terminal y repite cargo build. Verifica la toolchain con rustup show: debe decir stable-x86_64-pc-windows-msvc.

2. cargo no se reconoce en PowerShell

Mal: instalar Rust y ejecutar cargo run en la misma ventana de PowerShell que ya estaba abierta.

cargo : El término 'cargo' no se reconoce como nombre de un cmdlet,
función, archivo de script o programa ejecutable.
Compruebe si escribió correctamente el nombre o, si incluyó una ruta de acceso,
compruebe que la ruta de acceso es correcta e inténtelo de nuevo.

Por qué ocurre: el instalador modifica el PATH del usuario, pero los procesos ya lanzados no releen el entorno.

Bien: cierra y abre la terminal, o comprueba el PATH y ejecuta el binario por su ruta absoluta:

# PowerShell
$env:Path -split ';' | Select-String cargo
& "$env:USERPROFILE\.cargo\bin\cargo.exe" --version

3. Mezclar toolchains: el proyecto pide una versión que no está

error: toolchain '1.85.0-x86_64-unknown-linux-gnu' is not installed
help: run `rustup toolchain install 1.85.0-x86_64-unknown-linux-gnu` to install it

Por qué ocurre: el repositorio tiene un rust-toolchain.toml que fija 1.85.0, pero la máquina solo tiene stable. Normalmente rustup la instala sola al detectar el fichero; si el fichero se añadió después de abrir el editor o hay un RUSTUP_TOOLCHAIN en el entorno, el conflicto aparece.

Bien: dejar que rustup haga su trabajo y comprobar quién manda:

rustup show                    # ¿qué toolchain está activa y por qué?
rustup toolchain install 1.85.0
cargo +stable build            # forzar una toolchain solo para ese comando
rustup override unset          # quitar un override manual del directorio

4. Instalar Rust con el gestor de paquetes del sistema

$ cargo fmt
error: no such command: `fmt`
help: view all installed commands with `cargo --list`
help: find a package providing `cargo-fmt` with `cargo search cargo-fmt`

Por qué ocurre: el paquete rustc de Debian/Ubuntu o el rust de Homebrew no instalan los componentes del ecosistema. cargo fmt no es un subcomando interno: es el binario rustfmt que rustup gestiona como componente.

Bien: desinstalar el paquete del sistema e instalar por rustup; después, rustup component add rustfmt clippy.

7 · Ejercicio guiado

Objetivo: dejar el entorno listo, con componentes, editor y una toolchain fijada por proyecto, y comprobarlo con un binario real.

  1. Instala y verifica. Instala rustup según tu sistema y abre una terminal nueva. Después: 
    rustc --version
cargo --version
rustup --version
rustup show

    Criterio: rustc, cargo y rustup responden con su versión y rustup show indica una toolchain stable con su target triple.

  2. Añade los componentes del curso. 
    rustup component add clippy rustfmt rust-src
rustup component list --installed

    Deben aparecer clippy, rustfmt y rust-src para tu toolchain. Si falta alguno, cargo fmt o el autocompletado de std fallarán más adelante.

  3. Crea el proyecto de prueba y ejecútalo. 
    cargo new toolchain-check --bin
cd toolchain-check
cargo run

    Salida esperada: Hello, world!. Anota la ruta del binario que imprime Cargo en la línea Running: ahí acaba de demostrarse que el linker funciona.

  4. Fija la toolchain como en urlshort. Crea rust-toolchain.toml en la raíz del proyecto: 
    [toolchain]
channel = "1.85.0"
components = ["clippy", "rustfmt", "rust-src"]
profile = "minimal"

    Ejecuta rustup show dentro de la carpeta: debe indicar overridden by 'rust-toolchain.toml'. Esa línea es la prueba de que la versión la decide el repositorio, no la máquina.

  5. Comprueba el editor. Abre la carpeta en VS Code con la extensión rust-analyzer. En src/main.rs, escribe let x: i32 = "hola"; y observa el subrayado en vivo con expected `i32`, found `&str`. Corrígelo a let x: i32 = 42; y comprueba que el aviso desaparece sin ejecutar cargo build. Si no aparece nada, ejecuta «Rust Analyzer: Restart Server».

  6. Cierra el círculo con las herramientas. En el proyecto del paso 3: 
    cargo fmt
cargo fmt --check
cargo clippy -- -D warnings
cargo run

    Las cuatro deben terminar con código de salida 0. cargo fmt --check no imprime nada si el formato es correcto; clippy termina con Finished.

Criterio de éxito

Sabes explicar la diferencia entre rustup, cargo y rustc, tu proyecto fija su toolchain en un fichero versionado y cargo fmt --check pasa sin tocar nada. Si algo falla, rustup show es el primer comando, no el último.

8 · Reto

🎯 Onboarding en tres comandos

Tu equipo va a incorporar a dos personas: una en Windows nativo y otra en macOS. El repositorio de urlshort debe poder clonarse y arrancar con exactamente tres comandos, sin instrucciones orales y sin que nadie instale componentes a mano:

git clone <repo> && cd urlshort
cargo run -- "https://example.com"
cargo test

Diseña los ficheros de entorno del repositorio (toolchain, editor, ignores, documentación mínima) para que eso sea cierto en ambas máquinas, y escribe en el README cómo verificar el entorno en menos de un minuto. Debes cubrir también qué pasa si la persona tiene una toolchain global distinta o una versión de Rust más nueva.

Pista: rust-toolchain.toml hace que rustup instale lo que falta sin intervención; el perfil y los componentes declarados ahí son la diferencia entre «funciona en mi máquina» y «funciona al clonar». Piensa qué debe ser idéntico entre sistemas (versión, componentes, lints) y qué no puede serlo (rutas, binarios, finales de línea).

9 · Resumen

  • rustup instala y elige toolchains; cargo orquesta; rustc compila; el linker del sistema produce el ejecutable.
  • Todo se instala por usuario en ~/.cargo/bin (o %USERPROFILE%\.cargo\bin): sin administrador y sin tocar el sistema.
  • Una toolchain se define por canal + target; los componentes (clippy, rustfmt, rust-src) se añaden aparte.
  • En Windows, el camino nativo exige las Build Tools de C++; WSL2 evita esa dependencia y se parece más a producción.
  • rust-toolchain.toml fija la versión en el repositorio y elimina las diferencias entre máquinas.
  • rust-analyzer necesita la toolchain y rust-src; con check.command = "clippy" muestra los mismos lints que la CI.
  • Si algo «no existe», casi siempre es una terminal vieja con el PATH anterior.

10 · Preguntas frecuentes

¿Por qué no instalar Rust con apt o brew?

Porque esos paquetes suelen ofrecer una versión antigua y solo el compilador: sin cargo actualizado, sin clippy, sin rustfmt y sin la posibilidad de cambiar de toolchain. rustup instala en tu directorio personal, convive con el gestor del sistema y te da actualizaciones y componentes con un comando. Si ya tienes el paquete de la distribución, desinstálalo antes para evitar dos cargo en el PATH.

¿Necesito Visual Studio completo en Windows?

No. Basta con Visual Studio Build Tools y la carga de trabajo «Desarrollo para el escritorio con C++», que aporta link.exe, las cabeceras del sistema y el Windows SDK. Son varios cientos de megas, no los varios gigas del IDE completo. Si el instalador de rustup te ofrece instalarlas, acepta: te ahorra el error linker `link.exe` not found.

¿Nativo en Windows o WSL2?

Si tu destino es Linux (servidores, Docker, CI), usa WSL2: el binario, las rutas y los scripts serán los mismos que en producción. Si haces herramientas de escritorio para Windows o necesitas depurar con MSVC, usa el toolchain nativo. Lo que no funciona bien es mezclar: compilar en WSL sobre /mnt/c es lento y abrir el proyecto en VS Code desde Windows usa otro cargo. Elige un lado y sé consistente.

¿Actualizar Rust rompe mi código?

Rara vez. Rust tiene una política de compatibilidad hacia atrás muy estricta: el código que compila con una versión estable debe seguir compilando con las siguientes, salvo cambios de edición. Pueden aparecer warnings nuevos de clippy o del compilador. Ejecuta rustup update, luego cargo test y cargo clippy -- -D warnings; si algo se rompe, rust-toolchain.toml te permite volver a la versión anterior en un segundo.

rust-analyzer no autocompleta ni encuentra la biblioteca estándar

Comprueba en este orden: (1) rustup component add rust-src; (2) que VS Code esté abierto en la carpeta que contiene Cargo.toml, no en la carpeta padre; (3) que no haya otra extensión de Rust antigua activa; (4) reinicia el servidor con «Rust Analyzer: Restart Server». En WSL, abre la carpeta con «WSL: Connect to WSL» para que el servidor use el cargo correcto.
