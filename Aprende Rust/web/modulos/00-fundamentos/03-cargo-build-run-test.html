Cargo: build, run, test, fmt y clippy

Módulo 0 · Fundamentos ⏱ 35 minutos

1 · Introducción

Cargo no es «el make de Rust». Es un build system y un gestor de paquetes a la vez, con una idea central: todo lo que necesita un proyecto vive en Cargo.toml, y todo lo que produce vive en target/. No hay ficheros de build que mantener ni scripts que se desincronizan del código. Se asume el entorno de la lección Instalación: rustup, cargo y rust-analyzer; si algo falla, ese es el primer sitio donde mirar.

La consecuencia práctica es que compilar, ejecutar, probar, formatear, pasar el linter y generar documentación son subcomandos del mismo binario. Un recién llegado a un repositorio Rust no pregunta «¿cómo se compila esto?»: ejecuta cargo test. Ese es el nivel de estandarización que Cargo aporta y la razón por la que el ecosistema entero lo asume.

¿Por qué existe esta lección?

Porque el ciclo de trabajo diario en Rust es Cargo. Saber qué hace cada subcomando, cuánto cuesta y en qué perfil se ejecuta evita dos vicios caros: compilar en release para probar (lento) y no distinguir entre check y build (esperar código máquina cuando bastaba el análisis de tipos).

Errores típicos al empezar con Cargo:

  • Editar Cargo.toml a mano para añadir dependencias y equivocarse de sección o de versión.
  • Versionar target/ o, al contrario, ignorar Cargo.lock en un binario.
  • Usar cargo build --release para cada iteración y luego quejarse de los tiempos.

El manifiesto mínimo

[package]
name = "urlshort"
version = "0.1.0"
edition = "2021"
rust-version = "1.85"

[dependencies]
# serde = { version = "1", features = ["derive"] }   ← mejor con `cargo add`

[profile.release]
lto = "thin"

edition no es la versión del compilador: es el conjunto de reglas del lenguaje. rust-version sí es el mínimo de compilador. Y [profile.release] ajusta el binario final: lto = "thin" permite optimizar entre crates y strip = true elimina símbolos de depuración.

Los tests no se ejecutan igual en release

cargo test --release es válido, pero cambia el comportamiento: los enteros desbordan en silencio y debug_assert! desaparece. Si un test depende de detectar un desbordamiento, en release no lo verá. Usa release para medir rendimiento, no como sustituto de la suite normal.

Qué pasa cuando escribes cargo build

  Cargo.toml + código
        │
        ▼
  1. resolver dependencias  ──► Cargo.lock (versiones exactas)
        │
        ▼
  2. planificar targets     ──► ¿qué crates hay que compilar?
        │
        ▼
  3. rustc --emit=obj ... (uno por crate)
        │            └── error de tipos o préstamos → para aquí
        ▼
  4. linker del sistema     ──► target/debug/urlshort
        │
        ▼
  5. caché: si nada cambió, "Finished" sin recompilar

La caché es por unidad de compilación y por perfil: cambiar un comentario en main.rs no recompila tus dependencias. target/debug/incremental/ guarda estado entre compilaciones para acortar aún más el ciclo.

check no es un build más rápido: es otra cosa

cargo check ejecuta el frontend del compilador —resolución de nombres, tipos, préstamos, vidas— y se salta la generación de código y el enlazado. Para un proyecto con 200 dependencias, la diferencia son segundos frente a minutos. No produce binario; sirve para saber si el código es correcto, que es el 90 % de las iteraciones.

Comando¿Analiza?¿Genera binario?Cuándo usarlo
cargo checkSíNoMientras escribes: el bucle más rápido de errores.
cargo buildSíSí (debug)Cuando necesitas ejecutar o inspeccionar el artefacto.
cargo clippySí, con lints extraNo por defectoAntes de cada commit; en CI con -D warnings.
cargo testSíSí (binario de test)Validar comportamiento; compila con cfg(test).
cargo build --releaseSíSí (optimizado)Entrega y medición de rendimiento.

Tests: por qué cargo test compila en modo test

Al ejecutar cargo test, Cargo construye el crate con --test y con la opción cfg(test) activa. Eso hace tres cosas: incluye los módulos marcados con #[cfg(test)], enlaza el arnés de tests de la biblioteca estándar y añade las dev-dependencies. Por eso los tests pueden usar crates que el binario de producción no lleva.

El arnés ejecuta cada #[test] en un hilo distinto y captura la salida; si un test falla, imprime el stdout capturado y la aserción. Para ver la salida de los tests que pasan: cargo test -- --nocapture. Para ejecutar solo los que coinciden con un patrón: cargo test suma.

Dependencias: cargo add antes que editar a mano

cargo add serde --features derive
cargo add thiserror@2
cargo add --dev pretty_assertions

cargo add consulta el índice, elige la última versión compatible y escribe la entrada en la sección correcta. Editar Cargo.toml a mano sigue siendo válido para ajustes finos (features, path, git), pero para «añadir un crate» el subcomando evita erratas. En un binario, la versión resuelta queda fijada en Cargo.lock, que sí se versiona; en una biblioteca publicada lo habitual es no versionarlo.

La tríada de calidad

cargo fmt --all -- --check                   # ¿está formateado?
cargo clippy --all-targets -- -D warnings    # ¿hay lints?
cargo test --all-targets                     # ¿pasa la suite?

--all-targets incluye binarios, tests, ejemplos y benchmarks: sin él, clippy puede revisar solo la biblioteca y dejar sin analizar justo el código que se ejecuta. -D warnings convierte cada aviso en error: es la diferencia entre «la CI avisa» y «la CI bloquea».

3 · Ejemplo mínimo

Un proyecto con una función, dos tests y el ciclo completo. Es todo lo que necesitas para ver cómo encajan las piezas.

cargo new suma --bin
cd suma
fn sumar(a: i64, b: i64) -> i64 {
    a + b
}

fn main() {
    println!("2 + 3 = {}", sumar(2, 3));
}

// Este módulo solo existe cuando se compila con `cargo test`
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn suma_positivos() {
        assert_eq!(sumar(2, 3), 5);
    }

    #[test]
    fn suma_negativos() {
        assert_eq!(sumar(-2, -3), -5);
    }
}
$ cargo run
   Compiling suma v0.1.0 (/home/ana/suma)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.51s
     Running `target/debug/suma`
2 + 3 = 5

$ cargo test
     Running unittests src/main.rs (target/debug/deps/suma-6f1c2a9d4b7e0f13)

running 2 tests
test tests::suma_negativos ... ok
test tests::suma_positivos ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

Qué acaba de pasar:

  • cargo run compiló en perfil dev y ejecutó target/debug/suma.
  • cargo test compiló el mismo crate con otro perfil y con cfg(test) activo; por eso aparece el módulo tests, que en el binario normal no existe.
  • test result resume: 2 pasados, 0 fallidos, 0 ignorados. Ese es el contrato que leerás en CI.

4 · Ejemplo real

Aplicamos el ciclo completo a urlshort: la función que genera el código corto se prueba, se formatea, se pasa por clippy y se compila en release para entregar.

cargo new urlshort --bin
cd urlshort
use std::collections::hash_map::DefaultHasher;
use std::hash::{Hash, Hasher};

const ALPHABET: &[u8] = b"23456789abcdefghjkmnpqrstuvwxyz";
const CODE_LEN: usize = 6;

fn main() {
    let args: Vec<String> = std::env::args().collect();
    let Some(url) = args.get(1) else {
        eprintln!("uso: urlshort <url>");
        std::process::exit(2);
    };
    println!("{url} -> /{}", short_code(url));
}

fn short_code(url: &str) -> String {
    let mut hasher = DefaultHasher::new();
    url.hash(&mut hasher);
    let n = hasher.finish();

    let mut code = String::with_capacity(CODE_LEN);
    for i in 0..CODE_LEN {
        let idx = ((n >> (i * 6)) % ALPHABET.len() as u64) as usize;
        code.push(ALPHABET[idx] as char);
    }
    code
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn el_codigo_tiene_seis_caracteres() {
        assert_eq!(short_code("https://example.com").chars().count(), CODE_LEN);
    }

    #[test]
    fn el_codigo_es_estable() {
        let url = "https://www.rust-lang.org/learn";
        assert_eq!(short_code(url), short_code(url));
    }
}
# 1. Bucle rápido mientras editas: no genera binario
cargo check

# 2. Pasar la suite (compila en modo test)
cargo test

# 3. Formato y lints antes del commit
cargo fmt
cargo clippy --all-targets -- -D warnings

# 4. Artefacto optimizado para entregar
cargo build --release

Salidas que conviene saber leer:

$ cargo test
running 2 tests
test tests::el_codigo_es_estable ... ok
test tests::el_codigo_tiene_seis_caracteres ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

ObservaciónPor qué importa
check tarda una fracción de buildIteras sin pagar generación de código. En proyectos grandes, la diferencia es de minutos.
Los tests se ejecutan en paraleloEl arnés usa varios hilos: no compartas estado global mutable sin sincronización.

6 · Errores habituales

1. cargo run en un crate que solo es biblioteca

error: a bin target must be available for `cargo run`

Por qué ocurre: creaste el proyecto con cargo new --lib (o solo existe src/lib.rs). Una biblioteca no tiene fn main(): no hay nada que ejecutar.

Bien: añade un binario que use la biblioteca, sin duplicar código. Crea src/bin/urlshort.rs con un fn main() que importe el crate; después cargo run --bin urlshort funciona y cargo test sigue probando la biblioteca.

2. Un test falla y el mensaje parece otro programa

running 1 test
test tests::suma_positivos ... FAILED

---- tests::suma_positivos stdout ----
thread 'tests::suma_positivos' panicked at src/main.rs:14:9:
assertion `left == right` failed
  left: 6
 right: 5

Cómo se lee: la primera línea con left es el valor que devolvió tu código; right es el esperado. La ruta src/main.rs:14:9 apunta a la línea del assert_eq!, no a la función probada. La captura de stdout explica por qué no ves tus println! hasta que un test falla.

Bien: reproduce en aislamiento con cargo test suma_positivos -- --nocapture y coloca el fallo donde corresponde. Un test rojo es información, no un estorbo.

3. Clippy convierte un aviso en error en CI

error: this expression creates a reference which is immediately dereferenced by the compiler
 --> src/main.rs:8:17
  |
8 |     procesar(&texto);
  |              ^^^^^^ help: change this to: `texto`
  |
  = note: `-D clippy::needless_borrow` implied by `-D warnings`

Por qué ocurre: -D warnings eleva a error cada lint. Aquí el compilador ya aplica deref coercion, así que el & es ruido.

Bien: aplica la sugerencia, no silencies el lint. Si de verdad necesitas una excepción puntual, #[allow(clippy::needless_borrow)] con un comentario que explique por qué; nunca un allow global en el crate.

4. cargo fmt --check rompe la CI

Diff in /home/ci/urlshort/src/main.rs at line 3:
 fn main() {
-    let args:Vec<String>=std::env::args().collect();
+    let args: Vec<String> = std::env::args().collect();
 }

Por qué ocurre: el código local no está formateado, o el editor usa otra configuración. --check no escribe: solo compara y devuelve código de salida 1 si hay diferencias.

Bien: cargo fmt --all en local antes de subir, y un rustfmt.toml versionado si el equipo necesita opciones no estándar. En CI se ejecuta el check, nunca el formateo: la CI verifica, no reescribe el código.

7 · Ejercicio guiado

Objetivo: recorrer el ciclo completo sobre un crate pequeño, leyendo cada salida y comprobando el efecto de cada comando en target/.

  1. Crea el proyecto y mide el primer build. 
    cargo new contador --bin
cd contador
time cargo build

    Anota el tiempo y qué directorios aparecen en target/. Ejecuta cargo build otra vez: debe decir Finished sin Compiling. Esa es la caché.

  2. Escribe el código con un test. Sustituye src/main.rs por: 
    const LIMITE: u32 = 100;

fn clasificar(hits: u32) -> &'static str {
    match hits {
        0 => "sin visitas",
        n if n < LIMITE => "normal",
        _ => "popular",
    }
}

fn main() {
    for hits in [0, 42, 100, 5_000] {
        println!("{hits:>6} → {}", clasificar(hits));
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn cero_no_es_normal() {
        assert_eq!(clasificar(0), "sin visitas");
    }

    #[test]
    fn el_limite_es_popular() {
        assert_eq!(clasificar(LIMITE), "popular");
    }
}

    Fíjate en {hits:>6}: es formato alineado a la derecha, no una comparación. En el código real se escribe con >, aquí va escapado.

  3. Pasa la suite, mide perfiles y genera documentación. Ejecuta cargo test y comprueba running 2 tests y test result: ok. 2 passed; 0 failed; cargo test limite filtra por nombre. Rompe un test cambiando el valor esperado "popular" por "normal", localiza left/right y restaura el valor. Después: 
    cargo fmt
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo build --release
cargo doc --no-deps

    cargo fmt reescribe el código; después, fmt --check debe pasar sin imprimir diferencias. Release tarda más y produce un binario menor y más rápido; cargo doc genera HTML en target/doc/contador/index.html. Criterio de éxito: puedes explicar qué aparece en target/ tras cada comando y por qué cargo test encuentra un módulo que cargo run no compila.

8 · Reto

🎯 El portero automático del repositorio

Quieres que nadie pueda subir código a urlshort sin pasar el mismo control que ejecutará la CI. Escribe un script check.sh (y su equivalente check.ps1) que, en un solo comando, verifique formato, lints, tests y compilación de release, y que se detenga en el primer fallo informando qué comprobación ha fallado.

Requisitos: no debe recompilar de más, debe funcionar igual en Windows y en Linux, debe poder ejecutarse desde cualquier subdirectorio del repositorio y debe distinguir entre «fallo de formato» (arreglable con cargo fmt) y «fallo de test» (requiere mirar el código). Añade al README la línea exacta que debe ejecutar una persona antes de abrir un pull request.

Pista: cargo fmt --all -- --check devuelve 1 sin escribir nada; cargo clippy reutiliza el trabajo de cargo check, así que el orden importa menos de lo que parece, pero el mensaje de error sí. Para la ruta, en bash existe $(dirname "$0"); en PowerShell, $PSScriptRoot. Piensa qué comando debe ir primero para que el fallo más barato salga antes.

9 · Resumen

  • Cargo es build system y gestor de paquetes: un manifiesto, un directorio de salida, cero scripts.
  • check analiza sin generar código; build produce el binario; test compila con cfg(test) y dev-dependencies.
  • Los perfiles dev y release cambian optimización, tamaño y comportamiento ante desbordamientos.
  • target/ es descartable y va en .gitignore; Cargo.lock se versiona en binarios.
  • cargo add escribe la dependencia en la sección correcta; editar el TOML a mano se reserva para ajustes finos.
  • El ciclo sano: check → test → fmt → clippy → build --release, con clippy -D warnings y fmt --check como guardianes de la CI.

10 · Preguntas frecuentes

¿Por qué cargo check es tan rápido y por qué no me da el binario?

Porque se detiene antes de la generación de código: hace resolución de nombres, comprobación de tipos, de préstamos y de vidas, y termina. No invoca a LLVM ni al linker, que es donde se va la mayor parte del tiempo. Sirve para validar el código mientras escribes; cuando necesitas ejecutar, cargo run reutiliza el análisis y solo añade la parte final.

¿Debo versionar Cargo.lock?

En un binario o aplicación, sí: fija las versiones exactas de todo el árbol de dependencias y hace que CI y las máquinas del equipo compilen lo mismo. En una biblioteca publicada, normalmente no: cada consumidor resuelve sus versiones y tu lockfile no le sirve. La regla corta: si el repositorio produce algo que se ejecuta, versiona el lock.

¿Por qué los tests no ven mis funciones privadas?

Si están en un módulo #[cfg(test)] dentro del mismo fichero, sí las ven: es un módulo hijo y los hijos acceden a los elementos privados del padre con use super::*. Los tests de tests/ son distintos: se compilan como un crate externo y solo pueden usar la API pública, exactamente como un consumidor. Esa es su gracia y su límite.

¿cargo clippy sustituye a cargo check?

En la práctica, sí para el día a día: clippy ejecuta el análisis del compilador y añade sus propios lints. La diferencia es el coste (algo mayor) y la intención: check responde «¿compila?», clippy responde «¿está bien escrito?». En CI se ejecuta clippy con -D warnings; en el editor, tener clippy como check.command unifica ambas respuestas.
