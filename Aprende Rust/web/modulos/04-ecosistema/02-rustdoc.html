Documentación con rustdoc y doctests

Módulo 4 · Ecosistema y herramientas ⏱ 35 minutos

1 · Introducción

En Rust la documentación no es un fichero aparte que se queda viejo: vive dentro del código, se extrae con rustdoc y, cuando contiene ejemplos, se compila y se ejecuta con cargo test. Ese detalle cambia las reglas del juego. Un ejemplo de la documentación que deja de compilar rompe el build. La documentación se convierte en un test más.

docs.rs aloja la documentación de prácticamente todo el ecosistema. Cuando abres la página de serde o tokio, lo que ves lo ha generado rustdoc a partir de los comentarios del código fuente, con búsqueda, enlaces cruzados y los ejemplos listos para copiar.

¿Por qué existe esta lección?

Porque urlshort se publica en el módulo 7, y un crate sin documentación es un crate que nadie adopta. Pero hay una razón más urgente: los doctests son la forma más barata de comprobar que tu API pública se puede usar desde fuera. Detectan imports rotos, visibilidad insuficiente y firmas incómodas que los tests unitarios —dentro del módulo— no ven.

Errores típicos al documentar en Rust:

  • Escribir documentación en un README.md que se desincroniza del código.
  • Usar ignore en los ejemplos para que «no molesten»; en seis meses ya no compilan.
  • Documentar el qué («esta función acorta una URL») y no el porqué ni los errores.
  • Publicar con cargo publish sin haber abierto nunca cargo doc --open.

2 · Teoría

Dos tipos de comentario, dos alcances

///Doc externoJusto antes del ítemLa función, struct, enum, trait, campo o constante siguiente
//!Doc internoAl principio del módulo o del crateEl módulo que lo contiene, no el ítem siguiente

Markdown es el formato: encabezados, listas, tablas, código en línea y bloques cercados. rustdoc los convierte a HTML y sanea el resultado. La documentación de un crate se genera recorriendo la API pública: lo privado no aparece salvo que pidas --document-private-items.

  src/lib.rs  ──►  cargo doc  ──►  target/doc/urlshort/index.html
  //! crate          │             ├─ búsqueda y enlaces intra-doc
  /// ítem           │             └─ ejemplos copiables
  /// ```ejemplo```  └─►  cargo test --doc  ─►  un binario por doctest

Cada bloque ``` se extrae como un programa independiente: se le añade un fn main si no lo hay, se compila contra tu crate y, si no lleva no_run, se ejecuta. Un crate con cuarenta doctests compila cuarenta binarios pequeños: por eso conviene que sean cortos y directos.

Las secciones que rustdoc reconoce

No son decorativas: clippy y las revisiones las buscan, y # Safety es el contrato de una unsafe fn: enumera las precondiciones que el compilador no puede comprobar. Se escriben como encabezados de nivel 2 dentro del bloque de documentación.

SecciónCuándo es obligatoriaQué debe decir
# ExamplesCasi siempre en API públicaEl caso de uso normal, ejecutable.
# PanicsSi puede entrar en pánicoBajo qué condiciones exactas. Si no puede, no la escribas.
# ErrorsSi devuelve ResultQué variantes de error y cuándo se producen.
# SafetyObligatoria en unsafe fnQué invariantes debe cumplir quien llama para que no haya comportamiento indefinido.

Atributos de los bloques de código

También existen modificadores por plataforma, como ignore-x86_64 o only-linux, que se combinan con los anteriores. Y las líneas que empiezan por # se ocultan en el HTML pero se compilan: son perfectas para imports y para el main que devuelve Result.

Enlaces intra-doc

rustdoc resuelve rutas de Rust dentro de Markdown con la sintaxis [`Ruta`]: [`Link`], [`Link::new`], [`crate::store::Store`]. Cuando un nombre es ambiguo (un módulo y una función con el mismo nombre), se desambigua con prefijo: [`struct@Config`], [`fn@config`], [`mod@config`]. Los enlaces rotos son un warning, y en CI se convierten en error con RUSTDOCFLAGS="-D warnings" cargo doc --no-deps; un enlace roto es documentación que miente.

include_str!: una sola fuente para el README

El README y la portada del crate suelen contar lo mismo. En vez de duplicarlo, se incrusta con #![doc = include_str!("../README.md")]: el fichero se lee en compilación y su Markdown se convierte en la documentación del crate. Ojo: sus bloques de código también son doctests, así que el README se prueba, y no puede usar enlaces relativos a ficheros que no se empaquetan. Para un ítem concreto sirve #[doc = include_str!("../docs/store.md")].

#[doc(hidden)] y lo que no se documenta

#[doc(hidden)] mantiene un ítem público pero fuera de la documentación: reexportaciones internas, API de implementación o código generado por macros. No lo uses para esconder deuda: si es público, alguien puede usarlo. #[doc(alias = "acortar")] hace lo contrario: añade un término de búsqueda sin cambiar el nombre.

Publicar en docs.rs

docs.rs compila cada versión publicada con nightly y las features por defecto. Si tu crate tiene features, declara [package.metadata.docs.rs] con all-features = true y rustdoc-args = ["--cfg", "docsrs"]; los ítems condicionales pueden etiquetarse con #[cfg_attr(docsrs, doc(cfg(feature = "json")))], una feature inestable que no afecta a stable porque queda detrás de cfg(docsrs).

3 · Ejemplo mínimo

Una función documentada con un ejemplo que se ejecuta. Este fichero es un crate completo:

// src/lib.rs
//! Utilidades mínimas de acortamiento.
//!
//! El crate expone [`short_code`], que deriva un código estable de una URL.
use std::collections::hash_map::DefaultHasher;
use std::hash::{Hash, Hasher};
/// Deriva un código de seis caracteres a partir del contenido de `url`.
///
/// El resultado es determinista: la misma URL produce siempre el mismo
/// código, lo que permite usarlo como identificador sin almacenamiento.
///
/// # Examples
///
/// ```
/// use urlshort::short_code;
///
/// let code = short_code("https://www.rust-lang.org");
/// assert_eq!(code.len(), 6);
/// assert_eq!(code, short_code("https://www.rust-lang.org"));
/// ```
pub fn short_code(url: &str) -> String {
    let mut hasher = DefaultHasher::new();
    url.hash(&mut hasher);
    let n = hasher.finish();
    const ALPHABET: &[u8] = b"23456789abcdefghjkmnpqrstuvwxyz";
    let mut out = String::with_capacity(6);
    for i in 0..6 {
        let idx = ((n >> (i * 6)) % ALPHABET.len() as u64) as usize;
        out.push(ALPHABET[idx] as char);
    }
    out
}

Compilar la documentación y ejecutar los ejemplos son dos operaciones distintas:

cargo doc --open --no-deps   # genera HTML y abre el navegador
cargo test --doc             # compila y ejecuta SOLO los doctests
running 1 test
test src/lib.rs - short_code (line 17) ... ok
test result: ok. 1 passed; 0 failed; 0 ignored

Qué ha pasado, paso a paso:

  • //! al principio documenta el crate entero; aparece en la portada de target/doc/urlshort/.
  • /// documenta short_code y genera su página con la firma, la descripción y el ejemplo.
  • El bloque sin atributos se trata como Rust: rustdoc le añade fn main(), lo enlaza contra el crate recién compilado y lo ejecuta.
  • use urlshort::short_code; es exactamente lo que hará un usuario externo. Si la función fuera privada, el doctest no compilaría.
  • Los dos assert_eq! verifican longitud y determinismo: el ejemplo documenta y prueba a la vez.

4 · Ejemplo real

Así se documenta el núcleo de urlshort: un tipo Link, su constructor y el error propio. Fíjate en las secciones estándar y en las líneas ocultas con #.

//! # urlshort-core
//!
//! Dominio del acortador: enlaces, códigos y almacenamiento. El crate no sabe
//! nada de HTTP ni de argumentos de línea de comandos: esas capas viven fuera.
//!
//! # Ejemplo
//!
//! ```
//! use urlshort_core::{short_code, Link};
//!
//! let link = Link::new("https://www.rust-lang.org")?;
//! assert_eq!(link.code, short_code(&link.url));
//! # Ok::<(), urlshort_core::ShortError>(())
//! ```
//!
//! El trait `Store` abstrae la persistencia; `MemoryStore` es la
//! implementación de referencia para tests.
/// Un enlace acortado.
///
/// El código es la clave pública; la URL original nunca se modifica.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Link {
    /// Código corto, único en el almacén.
    pub code: String,
    /// URL de destino, ya normalizada.
    pub url: String,
    /// Número de resoluciones desde que se creó.
    pub hits: u64,
}
impl Link {
    /// Crea un enlace con un código derivado de la URL.
    ///
    /// # Errors
    ///
    /// Devuelve [`ShortError::InvalidUrl`] si la URL no empieza por
    /// `http://` o `https://`.
    ///
    /// # Examples
    ///
    /// ```
    /// # use urlshort_core::Link;
    /// let link = Link::new("https://example.com")?;
    /// assert_eq!(link.hits, 0);
    /// # Ok::<(), urlshort_core::ShortError>(())
    /// ```
    pub fn new(url: &str) -> Result<Self, ShortError> {
        if !url.starts_with("http://") && !url.starts_with("https://") {
            return Err(ShortError::InvalidUrl(url.to_string()));
        }
        Ok(Self { code: crate::short_code(url), url: url.to_string(), hits: 0 })
    }
}
// El trait Store y su implementación viven en src/store.rs.
/// Error de dominio del acortador.
#[derive(Debug, thiserror::Error)]
pub enum ShortError {
    /// La URL no es válida.
    #[error("URL inválida: {0}")]
    InvalidUrl(String),
    /// El código no existe en el almacén.
    #[error("no existe el código {0}")]
    NotFound(String),
    /// Fallo de entrada/salida.
    #[error("error de E/S: {0}")]
    Io(#[from] std::io::Error),
}

Decisiones que hacen que esta documentación sirva:

DecisiónPor qué
//! con un ejemplo completo del flujoLa portada enseña el caso de uso real: crear y comprobar.
# Ok::<(), ShortError>(())Permite usar ? sin enseñar el envoltorio: el lector ve el camino feliz.
# use ... ocultoLos imports son ruido para quien lee; el compilador los necesita.
# Errors en cada ResultEl usuario sabe qué variantes tratar sin leer el código fuente.
Campos públicos documentados uno a unorustdoc los lista en la página del struct; un campo sin doc es deuda visible.

Truco de revisión

Abre cargo doc --open y busca tu crate en la barra de búsqueda como si fueras un usuario nuevo. Si no encuentras la función que necesitas escribiendo lo que crees que se llama, el problema no es la documentación: es el nombre. #[doc(alias = "...")] es un parche; renombrar es la solución.

6 · Errores habituales

1. //! en el sitio equivocado

Mal:

pub fn acortar(url: &str) -> String {
    //! Deriva un código corto.   ← error: inner doc comment
    String::from("abc123")
}

El compilador lo rechaza:

error: inner doc comment is not allowed here
 --> src/lib.rs:2:5
  |
2 |     //! Deriva un código corto.
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^
  |
  = note: inner doc comments like this (starting with `//!` or `/*!`) can only appear before items

Por qué está mal: //! documenta el contenedor y debe ir al principio del módulo o del crate, no dentro de una función.

Bien: /// antes de la función, o //! al principio del módulo.

2. Doctest con ? sin el main adecuado

Mal:

/// ```
/// let link = Link::new("https://example.com")?;
/// ```
pub fn ejemplo() {}

El doctest se envuelve en un fn main() que devuelve (), y ? no se puede usar ahí:

error[E0277]: the `?` operator can only be used in a function that returns
              `Result` or `Option` (or another type that implements `FromResidual`)
 --> src/lib.rs:2:47
  |
1 | fn main() { let link = Link::new("https://example.com")?; }
  | ---------- this function should return `Result` or `Option` to accept `?`

Bien: cierra el ejemplo con la línea oculta que devuelve el Result:

/// ```
/// # use urlshort_core::Link;
/// let link = Link::new("https://example.com")?;
/// assert_eq!(link.hits, 0);
/// # Ok::<(), urlshort_core::ShortError>(())
/// ```

3. Enlaces intra-doc que apuntan a nombres que ya no existen

Un enlace [`Store::open`] que apunta a un método renombrado produce warning: unresolved link to `Store::open` con la nota #[warn(rustdoc::broken_intra_doc_links)] on by default. Bien: enlazar al método real o a la ruta completa: [`Store::get`], [`crate::store::FileStore::open`], y ejecutar RUSTDOCFLAGS="-D warnings" cargo doc en CI.

4. ignore como forma de silenciar

Mal: un bloque ```ignore con FileStore::open(...).unwrap(). No se compila nunca: en dos releases la firma puede cambiar y el usuario copiará código roto, además de aprender unwrap(), justo lo que el crate evita. Bien: no_run con manejo explícito del error, o un doctest completo con un fichero temporal.

/// ```no_run
/// # use urlshort_core::{FileStore, Store};
/// let mut store = FileStore::open("links.json")?;
/// store.put(urlshort_core::Link::new("https://example.com")?)?;
/// # Ok::<(), urlshort_core::ShortError>(())
/// ```

7 · Ejercicio guiado

Objetivo: documentar urlshort-core hasta que cargo doc y cargo test --doc pasen en CI, incluyendo un enlace roto que arreglarás. Necesitas los tests del módulo 3.

  1. Activa los lints de documentación. Al principio de src/lib.rs: 
    #![warn(missing_docs)]
#![deny(rustdoc::broken_intra_doc_links)]

    Ejecuta cargo doc --no-deps y cuenta los warnings. Cada uno es un ítem público sin documentar.

  2. Escribe la portada del crate. Un bloque //! con: una frase de qué es, un párrafo de para qué sirve, y un ejemplo completo con MemoryStore que cree, guarde y resuelva un enlace. Cierra con # Ok::<(), ShortError>(()).
  3. Documenta los tres ítems con Result. Añade # Errors a Link::new, Store::put y Store::get. Cada sección debe nombrar la variante (InvalidUrl, NotFound, Io) y la condición que la produce; acompáñala de un doctest que la provoque. 
    cargo test --doc    # cada variante documentada con un doctest que la provoca
  4. Rompe un enlace a propósito. Escribe [`Store::open`] en la documentación de put y ejecuta: 
    RUSTDOCFLAGS="-D warnings" cargo doc --no-deps

    Debe fallar con unresolved link. Corrígelo apuntando a [`Store::get`] y comprueba que ahora pasa.

  5. Incluye el README y genera. Crea un README.md con un ejemplo mínimo y pon #![doc = include_str!("../README.md")] al principio de lib.rs. Ejecuta cargo test --doc: los bloques del README ahora son doctests. Después abre cargo doc --open --no-deps y cargo doc --document-private-items --no-deps, y compara la vista pública con la privada.

Criterio de éxito

cargo test --doc pasa, RUSTDOCFLAGS="-D warnings" cargo doc --no-deps no imprime nada, y alguien que nunca ha visto el crate puede crear y guardar un enlace copiando el ejemplo de la portada.

8 · Reto

🎯 La documentación que no puede mentir

Escribe la documentación pública completa de urlshort-core 1.0.0 con una restricción: ningún ejemplo puede usar ignore y todos los que devuelvan Result deben demostrar al menos una variante de error real con un doctest que la provoque y la inspeccione.

Añade además tres doctests especiales: uno no_run para el almacenamiento en fichero, uno should_panic que documente una precondición de Link::from_parts, y uno compile_fail,E0382 que demuestre que un Link no se puede usar después de moverlo a un Store.

Requisitos: #![warn(missing_docs)] sin warnings, cero enlaces rotos con -D warnings, y un README incluido con include_str! cuyos ejemplos también pasen. La portada debe explicar en menos de quince líneas qué problema resuelve el crate y qué no hace.

Pista: para el compile_fail, el compilador debe fallar exactamente con E0382; puedes fijarlo en el atributo (```compile_fail,E0382) y comprobar que un cambio de diseño lo rompe. Para la sección # Safety, solo tiene sentido si expones una función unsafe: si no la tienes, no la inventes; documenta en su lugar las invariantes del trait Store.

9 · Resumen

  • /// documenta el ítem siguiente; //! documenta el módulo o crate que lo contiene.
  • Las secciones # Examples, # Panics, # Errors y # Safety son el contrato visible de la API.
  • Los bloques de código se compilan y ejecutan con cargo test: la documentación es un test.
  • no_run compila sin ejecutar; ignore ni siquiera compila y debe ser la excepción.
  • Las líneas que empiezan por # se ocultan en el HTML pero se compilan.
  • include_str! permite una sola fuente para el README y la portada del crate.
  • Los enlaces intra-doc se verifican; con -D warnings un enlace roto rompe el build.

10 · Preguntas frecuentes

¿Los doctests cuentan como tests de verdad?

Sí, y se ejecutan en cargo test junto a los unitarios y los de integración. Tienen una diferencia importante: se compilan como un consumidor externo del crate, así que solo pueden usar la API pública. Eso los hace perfectos para detectar problemas de visibilidad, imports y ergonomía, y malos para probar detalles internos. Si un doctest necesita algo privado, probablemente sea un test unitario, no un ejemplo de documentación.

¿Por qué se dice que ignore es peligroso?

Porque no se compila. Un ejemplo con ignore puede quedar obsoleto durante meses sin que nadie lo note, y el usuario que lo copie se encontrará con errores que tú nunca viste. no_run da casi todo lo que buscas cuando el problema es el efecto (no quieres abrir un puerto en CI) sin renunciar a la comprobación de tipos. Reserva ignore para pseudocódigo explícito o plataformas que no puedes compilar.

¿Cómo documento código que solo existe con una feature?

Con #[cfg(feature = "...")] en el ítem y #[cfg_attr(docsrs, doc(cfg(feature = "..."))) ] para la etiqueta. Además, configura [package.metadata.docs.rs] con all-features = true para que docs.rs compile la vista completa. Si una feature es incompatible con otra (lo cual ya es sospechoso), necesitarás documentar cada combinación y comprobarlas en CI; Cargo no lo hace por ti.

¿Puedo escribir doctests para código async?

Sí, pero necesitas un ejecutor. La forma habitual es ocultar el runtime en el ejemplo: # #[tokio::main] y # async fn main(), o usar futures::executor::block_on. Recuerda que el doctest se compila con las dependencias de tu crate, así que tokio debe estar disponible (como dependencia normal o de desarrollo). Mantén el ejemplo corto: un doctest async con timeouts reales es una fuente de fallos intermitentes en CI.
