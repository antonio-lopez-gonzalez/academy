Clippy, rustfmt, auditoría y CI

Módulo 4 · Ecosistema y herramientas ⏱ 35 minutos

1 · Introducción

Un proyecto Rust sano no se distingue por no tener warnings: se distingue por no permitirlos. La diferencia es de proceso, no de talento. rustfmt elimina las discusiones de estilo, clippy detecta errores lógicos que el compilador acepta, cargo audit vigila las dependencias y un workflow de CI ejecuta todo eso en cada push. Cuando el build está en verde, sabes exactamente qué se ha comprobado.

Rust tiene una ventaja rara aquí: las tres herramientas son oficiales, vienen con rustup y comparten la misma salida legible. No hay que ensamblar un linting casero como en otros ecosistemas. Lo que sí hay que decidir es qué se considera un fallo: un warning que nunca se corrige es ruido que oculta el siguiente.

¿Por qué existe esta lección?

Porque el módulo 7 publica urlshort en crates.io y lo despliega. Un crate publicado con warnings no se puede actualizar con confianza, y una dependencia con un advisory abierto es un incidente esperando fecha. El CI es el contrato que te obliga a ti mismo a no romper lo que ya funciona.

Errores típicos al montar calidad y CI:

  • Ejecutar cargo clippy sin --all-targets y dejar los tests sin analizar.
  • Silenciar un lint con #[allow] global en vez de arreglarlo o acotarlo.
  • Poner -D warnings con la toolchain flotante: una stable nueva rompe el build un martes.
  • Formatear todo el repositorio en el mismo commit que el cambio funcional.
  • Ignorar un advisory de seguridad sin registrar por qué ni hasta cuándo.
  • CI que solo ejecuta cargo test: el formato, los lints y la documentación nunca se comprueban.

2 · Teoría

Cuatro puertas, un solo objetivo

  CÓDIGO ──► rustfmt ──► ¿formateado?   (estilo, cero semántica)
         ──► clippy  ──► ¿idiomático?   (lógica + estilo)
         ──► tests   ──► ¿funciona?     (unitarios, integración, doctests)
         ──► doc     ──► ¿documentado?  (enlaces y warnings de rustdoc)
         ──► audit   ──► ¿seguro?       (RUSTSEC)

Ninguna puerta sustituye a otra. rustfmt no detecta un bug; clippy no sabe si tu lógica de negocio es correcta; los tests no comprueban que la documentación compile. El CI las ejecuta todas porque cada una cubre un fallo distinto.

rustfmt: el fin de las discusiones

rustfmt reescribe el código según el estilo oficial. No cambia la semántica: si el resultado se comporta distinto, es un bug de la herramienta. Se ejecuta de dos formas:

cargo fmt            # reescribe los ficheros
cargo fmt --all --check   # no escribe: sale con código 1 si algo no está formateado

La configuración vive en rustfmt.toml. Casi todo el mundo usa el estilo por defecto; si tocas algo, que sea poco y justificado, porque cada opción nueva es una fuente de diffs entre editores:

# rustfmt.toml
edition = "2021"
max_width = 100
use_field_init_shorthand = true

Las opciones marcadas como inestables requieren nightly y unstable_features = true; si tu CI usa stable, no las uses. Y un consejo de higiene: formatea en un commit separado del cambio funcional. Un diff de 2.000 líneas por formato esconde cualquier revisión.

clippy: el revisor que ya sabe Rust

clippy es el linter oficial. Analiza el AST y el árbol de tipos, así que entiende lo que tu código hace, no solo cómo se escribe. Sus lints se agrupan:

GrupoQué contieneNivel por defecto
correctnessErrores casi seguros (comparaciones absurdas, bucles infinitos)Deny
suspiciousCódigo que probablemente no querías escribirWarn
style, complexity, perfFormas no idiomáticas, complejidad y costes evitablesWarn
pedantic, nursery, restrictionEstilo estricto, lints en desarrollo y prohibiciones de equipoAllow

El comando canónico de CI es:

cargo clippy --workspace --all-targets --all-features -- -D warnings

Cada pieza importa:

  • --workspace: todos los crates, no solo el raíz.
  • --all-targets: lib, bins, tests, benches y examples. Sin esto, el código de test no se analiza.
  • --all-features: el código condicional también se revisa. Si tus features no son aditivas, este flag lo delata.
  • -- -D warnings: todo lo que pase de -- va a rustc/clippy; convierte cualquier warning en error.

--all-features no siempre es posible

Si mantienes features excluyentes (que, como viste en Cargo avanzado, no deberías), --all-features no compilará. La solución correcta es rediseñar; la provisional, ejecutar clippy una vez por combinación con --no-default-features --features x. No lo resuelvas quitando el flag: perderías la mitad de la cobertura.

Lints a nivel de crate: la política escrita

Puedes fijar la política con atributos al principio de lib.rs (#![deny(unsafe_code)], #![warn(missing_docs)]), pero es preferible Cargo.toml desde Cargo 1.74: aplica a todos los targets y no ensucia el código:

[lints.rust]
unsafe_code = "forbid"
missing_docs = "warn"
[lints.clippy]
all = { level = "deny", priority = -1 }
pedantic = { level = "warn", priority = -1 }
module_name_repetitions = "allow"
missing_errors_doc = "allow"

La priority negativa hace que el grupo se aplique antes y que los lints individuales puedan sobrescribirlo. forbid es más fuerte que deny: ni siquiera un #[allow] local puede desactivarlo, así que úsalo solo para reglas no negociables.

Cuando un lint tenga un falso positivo, acota el silencio y documenta el motivo:

#[expect(clippy::too_many_arguments, reason = "firma impuesta por la API de axum")]
fn handler(a: String, b: String, c: String, d: String, e: String,
           f: String, g: String, h: String) { /* … */ }

#[expect] (Rust 1.81) es mejor que #[allow]: si el lint deja de dispararse, avisa de que la excepción ya no hace falta. Es la diferencia entre una nota y una nota caducada.

MSRV: la versión mínima es una promesa

rust-version en Cargo.toml declara el compilador mínimo. Cargo avisa si compilas con menos, y el resolutor v3 lo tiene en cuenta al elegir dependencias. Pero declararlo no lo garantiza: hay que compilar con esa versión en CI.

rustup toolchain install 1.82.0 --profile minimal
cargo +1.82.0 check --workspace --all-features

Subir la MSRV es un cambio incompatible según semver: si publicas la 1.3.0 exigiendo 1.82 y antes exigías 1.75, has roto a quien compila con 1.75. Puede ser aceptable, pero debe ir en la versión adecuada y en el changelog. La herramienta cargo-msrv ayuda a encontrar la mínima real; a mano, la regla es probar con la declarada en CI y no usar APIs más nuevas sin darte cuenta.

Seguridad de dependencias: audit y deny

cargo audit compara tu Cargo.lock contra la base de datos RUSTSEC de vulnerabilidades y crates yanked:

cargo install cargo-audit --locked
cargo audit

Un hallazgo real tiene esta pinta:

error: 1 vulnerability found!
Crate:     time
Version:   0.1.44
Title:     Potential segfault in the time crate
ID:        RUSTSEC-2020-0071
Solution:  Upgrade to >=0.2.23
Dependency tree:
time 0.1.44
└── chrono 0.4.19
    └── urlshort 0.3.0

El árbol de dependencias es la parte importante: no arreglas time, arreglas quien lo trae. cargo update -p chrono suele resolverlo.

cargo deny va más allá: reúne advisories, licencias, crates prohibidos, duplicados y orígenes permitidos en un solo deny.toml. Es lo que usa una empresa para decir «no aceptamos GPL en producción» o «nada de OpenSSL, usamos rustls»:

[licenses]
allow = ["MIT", "Apache-2.0", "BSD-3-Clause", "Unicode-3.0"]
[bans]
multiple-versions = "warn"
deny = [
  { name = "openssl-sys", reason = "usamos rustls; openssl rompe el build multiplataforma" },
]
[sources]
unknown-registry = "deny"
unknown-git = "deny"

Genera la plantilla con cargo deny init: según la versión, el esquema puede pedir un campo version en algunas secciones, y la plantilla siempre está al día.

El workflow: rápido, cacheado y rompible

Un CI bien diseñado tarda minutos, no horas, y falla por el motivo correcto: cachea ~/.cargo y target/, ejecuta el formato antes que la compilación, fija la toolchain, separa la MSRV y la auditoría en jobs propios y convierte los warnings de rustdoc en errores. El ejemplo real de abajo lo implementa entero.

Ojo: cambiar RUSTFLAGS invalida la caché de todas las dependencias, así que muchos equipos ponen los lints en [lints] y reservan -D warnings para el paso de clippy.

Pre-commit: el CI antes del CI

El CI es la red de seguridad, no la primera línea. Un hook local evita el ciclo de «push, esperar tres minutos, ver que falta un espacio»:

#!/usr/bin/env sh
# .githooks/pre-commit
set -eu
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --quiet
# activar una vez: git config core.hooksPath .githooks

Versionar el hook en el repositorio (en .githooks/) hace que todo el equipo lo active con un comando. Si el proyecto es grande y el hook tarda demasiado, deja solo fmt y clippy; el CI completo sigue ahí.

3 · Ejemplo mínimo

Tres comandos que puedes ejecutar hoy en urlshort para ver el estado real del proyecto:

cargo fmt --all --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --workspace

Si el primero falla, la salida es un diff con lo que cambiaría. Si falla el segundo, verás el lint con su ubicación exacta:

error: unneeded `return` statement
 --> src/main.rs:6:5
  |
6 |     return link.code;
  |     ^^^^^^^^^^^^^^^^^ help: remove `return`
  |
  = note: `-D clippy::needless-return` implied by `-D warnings`
  = help: for further information visit https://rust-lang.github.io/rust-clippy/master/index.html#needless_return

La corrección es la que sugiere el propio lint:

// Antes: return explícito al final de la función
fn code_of(link: &Link) -> String {
    return link.code.clone();
}
// Después: la última expresión es el valor de retorno
fn code_of(link: &Link) -> &str {
    &link.code
}

Fíjate en que el arreglo no es solo cosmético: al quitar el return aparece un clone() innecesario. Clippy te lleva a la versión que presta en lugar de copiar, que es exactamente lo que el curso defiende desde el módulo 1. Con [lints.clippy] en deny, cualquier warning de los grupos estándar es un error incluso en local.

4 · Ejemplo real

El CI completo de urlshort. Tres jobs: calidad, MSRV y auditoría. Copiable tal cual en .github/workflows/ci.yml:

name: CI
on:
  push:
    branches: [main]
  pull_request:
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: rustfmt, clippy
      - uses: Swatinem/rust-cache@v2
      - run: cargo fmt --all --check
      - run: cargo clippy --workspace --all-targets --all-features -- -D warnings
      - run: cargo test --workspace --all-features
      - run: cargo test --workspace --doc --all-features
        env:
          RUSTDOCFLAGS: -D warnings
      - run: cargo doc --workspace --no-deps --all-features
        env:
          RUSTDOCFLAGS: -D warnings
  msrv:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        rust: ["1.82.0", stable]
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@master
        with:
          toolchain: ${{ matrix.rust }}
      - uses: Swatinem/rust-cache@v2
      - run: cargo check --workspace --all-features
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: rustsec/audit-check@v2
        with:
          token: ${{ secrets.GITHUB_TOKEN }}

Y la política de dependencias en deny.toml, ejecutable en local con cargo deny check:

[advisories]
yanked = "deny"
[licenses]
allow = ["MIT", "Apache-2.0", "BSD-3-Clause", "Unicode-3.0"]
[bans]
multiple-versions = "warn"
deny = [
  { name = "openssl-sys", reason = "usamos rustls; openssl complica el build en Windows" },
]

Decisiones que hacen que este pipeline sea útil y no teatro:

DecisiónPor qué
Formato antes que compilaciónFalla en segundos; el feedback llega antes y no consume caché.
--all-targets en clippyLos tests y ejemplos también son código que se publica en el repositorio.
Doctests y cargo doc separadosDistinguen «el ejemplo no compila» de «el enlace está roto».
MSRV en matriz con fail-fast: falseQuieres ver a la vez si falla la mínima y la stable, no una detrás de otra.
Auditoría como job independienteUn advisory nuevo se ve como check propio y no tumba la señal de los tests.

El warning que no arreglas hoy

Si un warning se queda más de una semana, o se arregla o se convierte en una excepción con motivo y fecha. Los warnings crónicos son como las pruebas desactivadas: el día que aparece uno de verdad, nadie lo distingue del ruido de fondo.

6 · Errores habituales

1. Clippy sin --all-targets

Mal:

cargo clippy -- -D warnings

Por qué está mal: solo analiza el target por defecto (la lib o el bin). El código de tests/, los ejemplos y los benches queda fuera, que es justo donde más unwrap() y comparaciones raras se acumulan.

Bien:

cargo clippy --all-targets --all-features -- -D warnings

2. Silenciar con allow en la raíz

Mal:

#![allow(clippy::all)]        // «ya lo arreglaremos»
#![allow(dead_code)]          // el módulo entero, para siempre

Por qué está mal: apaga también correctness, que es donde están los bugs. Y dead_code global oculta funciones que ya nadie llama tras un refactor.

Bien: silencio local, con motivo y con expect para que caduque:

#[expect(dead_code, reason = "se usa desde el servidor en la feature http")]
fn internal_probe() -> bool { true }

3. -D warnings con toolchain flotante

Mal:

- uses: dtolnay/rust-toolchain@stable
- run: cargo clippy -- -D warnings

Por qué está mal: cada seis semanas sale una stable con lints nuevos o más estrictos. Un martes, sin cambios en tu código, el CI se pone rojo y el equipo aprende a ignorar el rojo.

Bien: fija la versión en la que has validado, y actualízala con un pull request dedicado:

- uses: dtolnay/rust-toolchain@master
  with:
    toolchain: "1.85.0"
    components: rustfmt, clippy

4. Ignorar un advisory sin dejar rastro

Mal: cargo audit || true con el comentario «este no aplica». El día que aparezca un advisory crítico, el paso ya está neutralizado y nadie lo verá.

Bien: una excepción explícita en la configuración, con motivo, alcance y fecha de revisión: ignore = ["RUSTSEC-2020-0071"] bajo [advisories], más un issue abierto con esa fecha. Una excepción sin caducidad es una vulnerabilidad con documentación.

7 · Ejercicio guiado

Objetivo: dejar urlshort con el build en verde bajo el mismo pipeline que usarás en el módulo 7. Necesitas el crate con tests del módulo 3.

  1. Instala, mide y formatea. Añade los componentes con rustup component add rustfmt clippy, ejecuta cargo fmt --all --check y cargo clippy --all-targets --all-features -- -D warnings, y anota cuántos ficheros y lints aparecen antes de tocar nada. Después formatea en un commit aislado (style: aplicar rustfmt).
  2. Arregla los lints uno a uno. Ejecuta clippy y ve corrigiendo: needless_return, redundant_clone, single_char_pattern… Si alguno es un falso positivo, usa #[expect(..., reason = "…")] en el ítem concreto, nunca en la raíz.
  3. Convierte la política en manifiesto. Añade el bloque [lints] con unsafe_code = "forbid", missing_docs = "warn" y clippy::all en deny. Vuelve a ejecutar clippy: ahora hay más trabajo, y ese trabajo es el que el CI va a exigir.
  4. Audita las dependencias. 
    cargo install cargo-audit --locked
cargo audit

    Si aparece un advisory, localiza quién lo trae con el árbol que imprime, actualiza esa dependencia y vuelve a ejecutar. Si no hay parche, documenta la excepción con fecha.

  5. Monta el workflow y el hook. Copia el ci.yml del ejemplo real, haz push a una rama y comprueba que los tres jobs aparecen. Rompe el formato a propósito y verifica que falla en el primer paso. Después crea .githooks/pre-commit y actívalo con git config core.hooksPath .githooks.

Criterio de éxito

Un clon limpio del repositorio pasa fmt --check, clippy --all-targets --all-features -- -D warnings, test --workspace, doc y audit sin intervención manual. Y has visto el CI fallar al menos una vez por el motivo correcto.

8 · Reto

🎯 La puerta de calidad del workspace

Diseña la política de calidad completa para el workspace de urlshort (núcleo, CLI y un futuro servidor) con estas restricciones: MSRV 1.82 intocable durante seis meses; prohibido unsafe salvo en un módulo de integración con C que debe quedar aislado y auditado; licencias permitidas solo MIT, Apache-2.0 y BSD-3-Clause; nada de OpenSSL; y un presupuesto de CI de ocho minutos en un runner de dos núcleos.

Entrega: el ci.yml final, el deny.toml, el bloque [lints] de cada crate, y una tabla que explique qué comprueba cada job, cuánto tarda y qué hace fallar. Incluye la estrategia para actualizar la toolchain sin romper el build un lunes, y el procedimiento exacto para aceptar un advisory sin parche durante un máximo de 90 días.

Demuestra el diseño con un cambio real: introduce a propósito un unsafe en el núcleo, una dependencia con licencia no permitida y un enlace intra-doc roto, y explica qué job detecta cada uno y con qué mensaje.

Pista: el aislamiento de unsafe no se consigue con un allow global, sino con un crate separado o con un módulo marcado y una excepción de lint acotada a ese ítem. Para el presupuesto de tiempo, mide antes de optimizar: el orden de los pasos y la caché suelen importar más que paralelizar jobs. Y recuerda que la matriz de MSRV duplica el build: quizá no necesite --all-features ni los tests completos.

9 · Resumen

  • rustfmt elimina el debate de estilo; --check lo convierte en condición de CI.
  • clippy analiza tipos y detecta errores lógicos; --all-targets --all-features -- -D warnings es el comando canónico.
  • La política de lints vive mejor en [lints] del manifiesto que repartida en atributos.
  • #[expect(..., reason)] documenta y caduca las excepciones; allow global las esconde.
  • La MSRV se declara con rust-version y se verifica compilando con esa versión en CI.
  • cargo audit consulta RUSTSEC; cargo deny añade licencias, bans y orígenes.
  • Los warnings crónicos y las excepciones sin fecha son deuda que se paga en producción.

10 · Preguntas frecuentes

¿Clippy y rustfmt vienen con Rust o hay que instalarlos?

Se distribuyen como componentes de rustup, pero no siempre están instalados. rustup component add clippy rustfmt los añade a la toolchain activa. En CI se declaran con components: rustfmt, clippy en la acción de la toolchain. No son crates aparte ni requieren compilación, por lo que el coste de tenerlos es cero.

¿Merece la pena activar clippy::pedantic?

Depende del proyecto y del equipo. pedantic incluye lints valiosos (missing_errors_doc, must_use_candidate) y otros muy discutibles. Una estrategia que funciona: actívalo como warn, no como deny, revisa los avisos y silencia con #[expect(reason)] los que no compartas. En una librería pública, la documentación de errores que exige pedantic mejora mucho la API. En un prototipo, es ruido.

¿Cómo actualizo la toolchain sin que el CI explote?

Con un pull request dedicado: cambias la versión fijada, ejecutas cargo clippy en local, arreglas o silencias los lints nuevos con su motivo, y actualizas el changelog si la MSRV sube. Así el fallo se atribuye a la actualización y no a un cambio funcional. Si el proyecto es grande, mantén una rama next-toolchain con la stable nueva y un job informativo (sin bloquear) hasta que esté limpia.

¿Qué hago con un advisory que no tiene parche?

Primero, determina si te afecta: lee el advisory, mira qué función o feature es vulnerable y si tu código la usa. Si no te afecta, documenta la excepción con motivo y fecha de revisión en la configuración de cargo audit o cargo deny, y abre un issue con esa fecha. Si te afecta, busca alternativa (cambiar de crate, aislar la funcionalidad, parchear con un fork) y trátalo como un incidente con prioridad. Lo que nunca vale es || true.
