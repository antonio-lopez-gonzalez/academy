Serde: JSON, derive y formatos

Módulo 4 · Ecosistema y herramientas ⏱ 40 minutos

1 · Introducción

Todo programa que guarda o intercambia datos necesita convertir estructuras en texto y texto en estructuras. En Rust eso lo hace Serde, el crate más descargado del ecosistema. Su idea central es separar dos cosas que otros lenguajes mezclan: el formato (JSON, TOML, YAML, CSV, binario) y el tipo (tus structs y enums). Escribes la conversión una vez, con #[derive(Serialize, Deserialize)], y funciona con todos los formatos.

Esa separación es lo que permite que serde sea rápido: el código de serialización se genera en tiempo de compilación, sin reflexión ni mapas de tipos en ejecución. No hay un Object intermedio como en Java o Python. El JSON se escribe directamente desde tus campos.

¿Por qué existe esta lección?

Porque urlshort necesita persistir enlaces en el módulo 6 y hablar JSON en el servidor del módulo 7. Y porque el formato que elijas es un contrato de larga vida: los ficheros que escribas hoy tendrán que leerse dentro de dos años, cuando tu struct haya cambiado. Aquí aprendes a evolucionar el esquema sin romper datos existentes.

Errores típicos con Serde:

  • Añadir un campo a un struct y romper la lectura de todos los ficheros antiguos.
  • Usar serde_json::Value para todo y perder la seguridad de tipos.
  • Renombrar un campo en Rust sin rename y cambiar el JSON que ven los clientes.
  • Serializar un HashMap, obtener otro orden en cada ejecución e imprimir el error sin línea ni columna.

2 · Teoría

Cómo funciona derive por dentro

Serde define dos traits genéricos sobre el formato: Serialize recibe un Serializer y Deserialize un Deserializer, así que un mismo Link sirve para JSON, TOML o binario. #[derive(Serialize)] genera una implementación que llama a serialize_struct con los nombres de campo; el formato decide cómo se materializa.

  struct Link  ──►  #[derive(Serialize)]    ──►  serde_json  →  {"code":…}
  code, url, hits   (código generado)             toml        →  code = "…"
                    #[derive(Deserialize)]   ◄──   csv         →  code,url
                    (validación de tipos)

La deserialización es la parte delicada: el formato es texto no confiable y el tipo debe construirse con todas sus invariantes. Si un campo falta, sobra o tiene otro tipo, el error debe ser preciso y temprano.

Atributos que cambian el contrato

Los atributos de Serde son la API real de tu formato. Estos son los que usarás el 90 % del tiempo:

AtributoEfectoCuándo
rename = "created_at"Cambia el nombre en el formatoEl JSON usa snake_case y el campo Rust no, o al revés.
rename_all = "camelCase"Aplica la convención a todos los camposAPI JSON para JavaScript.
defaultUsa Default::default() si el campo faltaCampos nuevos en formatos ya guardados.
default = "funcion"Valor alternativo calculadoCuando el valor por defecto no es Default.
skip_serializing_if = "Option::is_none"Omite el campo al escribirOpcionales que no deben aparecer como null.
skipNo se serializa ni deserializaCampos derivados o cachés internas.
flattenIncrusta los campos del campo anidado en el nivel actualComposición de structs y datos extra.
tag = "type"Enum etiquetado internamenteMensajes y eventos con un discriminante.
alias = "viejo"Acepta también otro nombre al leerRenombrados compatibles.

Un ejemplo con los tres más útiles juntos:

#[derive(Debug, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct LinkDto {
    pub code: String,
    pub created_at: u64,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub expires_at: Option<u64>,
}

Eso produce {"code":"k7m2qd","createdAt":1750000000} cuando expires_at es None, y acepta el objeto sin expiresAt al leer: compatibilidad hacia atrás y salida compacta a la vez.

Enums: tres formas de representar una variante

Los enums son la estructura más rica de Rust y Serde les da tres representaciones en JSON:

#[derive(Serialize, Deserialize)]
#[serde(tag = "event", rename_all = "snake_case")]
pub enum Event {
    Created { code: String },
    Resolved { code: String, hits: u64 },
}
{"event":"created","code":"k7m2qd"}
{"event":"resolved","code":"k7m2qd","hits":3}

Esa es la forma internamente etiquetada: el discriminante convive con los campos. Es la más legible y la que deberías preferir para mensajes propios. Limitación: no admite variantes de tupla, solo struct y unitarias.

La forma adyacente separa etiqueta y contenido con #[serde(tag = "kind", content = "payload")], útil cuando el contenido es una lista o un escalar: {"kind":"short","payload":"https://example.com"}.

La forma sin etiqueta (untagged) prueba las variantes en orden hasta que una encaje. Funciona con tipos externos, pero los errores son malos («data did not match any variant») y el orden importa: una variante demasiado laxa se come a las demás. Úsala solo cuando el formato no lo controlas.

Value: potente y peligroso

serde_json::Value representa cualquier JSON (Null, Bool, Number, String, Array, Object) y sirve para reenviar payloads opacos o inspeccionar claves arbitrarias. Como modelo de dominio es un antipatrón: un campo que falta se convierte en un None que aparece tres llamadas más tarde, sin tipo ni posición. Con un struct, el error surge en la frontera, con línea y columna.

Un formato no es «JSON con otra extensión»

JSON (serde_json) es universal pero verboso y sin comentarios; TOML (toml) es la elección del ecosistema para configuración; CSV (csv) sirve para datos tabulares planos, sin anidamiento; YAML es compacto pero tiene reglas implícitas y serde_yaml quedó sin mantenimiento en 2025, con forks como serde_yml. Para configuración nueva en Rust, TOML; para red, JSON; para analistas, CSV.

Versionar el esquema: el contrato a largo plazo

Un fichero JSON guardado es una promesa a tu yo del futuro. La forma barata de cumplirla es incluir schema_version dentro del documento y rechazar cualquier versión mayor que la soportada, en lugar de interpretarla a ciegas.

{
  "schema_version": 2,
  "links": [ { "code": "k7m2qd", "url": "https://example.com", "hits": 3 } ]
}

Reglas de evolución que funcionan:

  • Añadir un campo con #[serde(default)] es compatible: los documentos viejos siguen leyéndose.
  • Renombrar exige #[serde(alias = "nombre_viejo")] y, si escribes, mantener el nombre nuevo solo cuando todos hayan migrado.
  • Cambiar el tipo (de número a string) es incompatible: nueva versión de esquema y migración explícita.

Cuidado con deny_unknown_fields

En un formato que evoluciona es lo contrario de lo que parece: un escritor nuevo añade un campo y tu lector viejo rechaza el documento entero. Úsalo solo en entradas que deban ser exactas, nunca en datos persistidos.

3 · Ejemplo mínimo

Un struct, dos derives y un viaje de ida y vuelta. Es un crate completo:

// src/main.rs
use serde::{Deserialize, Serialize};
#[derive(Debug, PartialEq, Serialize, Deserialize)]
struct Link {
    code: String,
    url: String,
    #[serde(default)]
    hits: u64,
}
fn main() -> Result<(), serde_json::Error> {
    let link = Link {
        code: "k7m2qd".to_string(),
        url: "https://example.com".to_string(),
        hits: 0,
    };
    let json = serde_json::to_string_pretty(&link)?;
    println!("{json}");
    let recovered: Link = serde_json::from_str(&json)?;
    assert_eq!(link, recovered);
    Ok(())
}
[dependencies]
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"

Salida:

{"code":"k7m2qd","url":"https://example.com","hits":0}

Línea a línea:

  • #[derive(Serialize, Deserialize)] genera ambas implementaciones. Sin features = ["derive"] en el manifiesto, la macro no existe.
  • #[serde(default)] en hits hace que un JSON sin ese campo se lea como 0. Es la pieza que permite añadir campos sin romper datos.
  • to_string_pretty devuelve Result<String, Error>: la serialización puede fallar (por ejemplo, un HashMap con claves no textuales en JSON).
  • from_str infiere el tipo del contexto (let recovered: Link). Sin anotación, no compila: Serde no adivina.
  • main devuelve Result<(), serde_json::Error>, así que ? propaga el error sin unwrap y el proceso sale con código distinto de cero.

4 · Ejemplo real

La persistencia de urlshort: un fichero JSON con versión de esquema, lectura tolerante a documentos antiguos y errores con línea y columna. La escritura atómica la implementarás en el ejercicio.

// src/store.rs
use std::fs;
use std::path::Path;
use serde::{Deserialize, Serialize};
/// Versión del formato que escribe esta build.
pub const SCHEMA_VERSION: u32 = 2;
#[derive(Debug, Serialize, Deserialize)]
pub struct StoreFile {
    pub schema_version: u32,
    pub links: Vec<Link>,
}
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct Link {
    pub code: String,
    pub url: String,
    #[serde(default)]
    pub hits: u64,
    /// Epoch en segundos. Los documentos de la versión 1 no lo tenían.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub expires_at: Option<u64>,
}
#[derive(Debug, thiserror::Error)]
pub enum StoreError {
    #[error("no se pudo leer {path}: {source}")]
    Io {
        path: String,
        #[source]
        source: std::io::Error,
    },
    #[error("JSON inválido en línea {line}, columna {column}: {source}")]
    Parse {
        line: usize,
        column: usize,
        #[source]
        source: serde_json::Error,
    },
    #[error("esquema {found} más nuevo que el soportado ({supported}); actualiza urlshort")]
    SchemaTooNew { found: u32, supported: u32 },
}
impl StoreFile {
    /// Lee y valida el fichero. Si no existe, devuelve un almacén vacío.
    pub fn load(path: &Path) -> Result<Self, StoreError> {
        let raw = match fs::read_to_string(path) {
            Ok(raw) => raw,
            Err(e) if e.kind() == std::io::ErrorKind::NotFound => {
                return Ok(Self { schema_version: SCHEMA_VERSION, links: Vec::new() });
            }
            Err(source) => return Err(StoreError::Io { path: path.display().to_string(), source }),
        };
        let file: Self = serde_json::from_str(&raw).map_err(|source| StoreError::Parse {
            line: source.line(),
            column: source.column(),
            source,
        })?;
        if file.schema_version > SCHEMA_VERSION {
            return Err(StoreError::SchemaTooNew {
                found: file.schema_version,
                supported: SCHEMA_VERSION,
            });
        }
        Ok(file)
    }
}
#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn lee_documentos_de_la_version_1() {
        // Un fichero escrito antes de que existieran hits y expires_at
        let raw = r#"{
            "schema_version": 1,
            "links": [{ "code": "k7m2qd", "url": "https://example.com" }]
        }"#;
        let file: StoreFile = serde_json::from_str(raw).expect("JSON válido");
        assert_eq!(file.links[0].hits, 0);
        assert_eq!(file.links[0].expires_at, None);
    }
}

Qué hace que este formato sea estable:

DecisiónEfecto
schema_version explícitoUn lector viejo puede rechazar datos nuevos en lugar de malinterpretarlos.
#[serde(default)] en campos nuevosLos documentos creados con la versión 1 se leen sin migración.
skip_serializing_ifEl JSON no se llena de "expires_at": null; sigue siendo válido sin el campo.
Vec<Link>, no HashMapEl orden es determinista: los diffs del fichero son legibles y los tests estables.
Error con line() y column()El usuario sabe dónde arreglar el fichero sin adivinar.

La prueba que casi nadie escribe

Guarda un JSON de ejemplo en tests/fixtures/store-v1.json y escribe un test que lo lea. Ese fichero no cambia nunca. Cuando dentro de un año refactorices el struct, el test te dirá si has roto la compatibilidad antes de que lo descubra un usuario. Es la forma más barata de mantener un formato durante años.

6 · Errores habituales

1. Olvidar Deserialize o la feature derive

Mal:

#[derive(Serialize)]   // solo serializa
struct Link { code: String }
let link: Link = serde_json::from_str("{}")?;
error[E0277]: the trait bound `Link: Deserialize<'_>` is not satisfied
 --> src/main.rs:7:22
  |
7 |     let link: Link = serde_json::from_str("{}")?;
  |                      ^^^^^^^^^^^^^^^^^^^^^^ the trait `Deserialize<'_>`
  |                                             is not implemented for `Link`

Por qué está mal: from_str necesita construir un Link y no sabe cómo. Añade Deserialize al derive y comprueba que el manifiesto tiene features = ["derive"] (el error sin la feature es distinto: «cannot find derive macro Deserialize»).

2. Campo nuevo sin default

Mal:

#[derive(Deserialize)]
struct Link {
    code: String,
    expires_at: Option<u64>,   // sin #[serde(default)]
}

Al leer un documento antiguo:

Error("missing field `expires_at`", line: 1, column: 57)

Por qué está mal: aunque el tipo sea Option, Serde exige que el campo exista salvo que le digas lo contrario. El Option describe el valor, no la presencia del campo.

Bien: #[serde(default)] (o default = "…" si el valor no es None/0).

3. Renombrar un campo y romper el formato

Mal: renombrar created a created_at y publicar; los clientes siguen enviando created y el campo falta. Bien: #[serde(rename = "created_at", alias = "created")], que lee ambos y escribe el nuevo.

4. Value como muleta

Mal:

let v: serde_json::Value = serde_json::from_str(&raw)?;
let code = v["links"][0]["code"].as_str().ok_or("sin código")?;
let hits = v["links"][0]["hits"].as_u64().unwrap_or(0);

Por qué está mal: v["..."][0]["..."] no falla con un error útil: devuelve Null y el fallo aparece disfrazado de «sin código». Además no hay autocompletado ni refactor seguro, y cada acceso paga búsquedas en el mapa.

Bien: un struct con los campos y un error de parseo que diga qué campo falta.

7 · Ejercicio guiado

Objetivo: persistir urlshort en JSON con un formato versionado y demostrar que lee datos antiguos. Necesitas el Store del módulo 3.

  1. Añade las dependencias. 
    cargo add serde --features derive
cargo add serde_json
cargo add thiserror

    Comprueba que serde aparece en [dependencies] y no en [dev-dependencies].

  2. Define el formato. Crea StoreFile { schema_version, links } y Link con code, url, hits (default) y expires_at (default + skip_serializing_if). El JSON de salida debe tener exactamente esas claves. 
    cargo test    # escribe un test que serialice y compare con el JSON esperado
  3. Escribe un fixture de la versión 1. Un fichero sin hits ni expires_at en tests/fixtures/store-v1.json. Un test debe leerlo y comprobar que los valores por defecto son 0 y None.
  4. Rechaza esquemas futuros y escribe de forma atómica. Si schema_version > 2, devuelve un error propio y pruébalo con un documento de versión 99. Al guardar, escribe en links.json.tmp y renombra; verifica que no queda el temporal y que el contenido se relee. 
    cargo test -- --nocapture    # imprime el JSON generado si añades un println!

Criterio de éxito

Tienes tres tests: uno que fija el formato actual, uno que lee un documento de la versión anterior y uno que rechaza una versión futura. El fichero se escribe de forma atómica y un error de parseo dice línea y columna. Eso es un formato listo para producción.

8 · Reto

🎯 Migración sin downtime

urlshort lleva un año guardando enlaces con "created": 1750000000, un entero de segundos, y "owner": "ana@example.com" como cadena. La nueva versión quiere created_at como objeto {"unix": 1750000000} y owner como objeto {"email": "…", "name": "…"}, con name opcional.

Diseña el esquema 3 y la migración desde el 2: los ficheros antiguos deben seguir leyéndose y, al guardar, deben quedar en el formato nuevo. Ningún dato puede perderse, y el proceso debe poder ejecutarse dos veces sin duplicar ni corromper nada. Documenta el formato con una tabla de campos, tipos y obligatoriedad, y escribe los tests de las tres rutas: leer v2, migrar y leer v3 recién escrito.

Requisitos extra: rechaza versiones futuras con un error accionable; no uses Value en el dominio; y demuestra con un test que un campo desconocido añadido por una versión posterior no rompe la lectura.

Pista: puedes aceptar ambos formatos con un enum intermedio #[serde(untagged)] y convertir a un tipo canónico, o con un DTO de lectura que tenga los dos campos como Option. La primera opción falla peor cuando el dato está mal; la segunda obliga a escribir una función de normalización. Piensa cuál de las dos quieres depurar a las tres de la mañana.

9 · Resumen

  • Serde separa tipo y formato: un Serialize sirve para JSON, TOML, CSV o binario.
  • #[derive(Serialize, Deserialize)] genera código en compilación; requiere la feature derive.
  • #[serde(default)] permite añadir campos sin romper documentos existentes.
  • rename, rename_all y alias controlan el contrato del cable sin tocar los nombres de Rust.
  • Los enums se representan internamente etiquetados (tag), adyacentes (tag + content) o sin etiqueta (untagged).
  • Un formato persistido necesita schema_version, campos nuevos con default y tests con fixtures antiguos.

10 · Preguntas frecuentes

¿Serde usa reflexión? ¿Es lento?

No usa reflexión: el derive genera código concreto en tiempo de compilación, equivalente a escribir a mano los match y las llamadas al serializador. Por eso es rápido y por eso el binario crece un poco. El coste real suele estar en el formato (parsear JSON implica validar y asignar memoria), no en Serde. Si el rendimiento es crítico, mide antes de cambiar de formato: un binario como bincode o postcard suele ganar más que cualquier microoptimización del derive.

¿Por qué no puedo serializar un HashMap a JSON?

Puedes, si las claves son strings (o tipos que serialicen como string). JSON exige claves de objeto textuales; un HashMap<u64, T> no tiene una representación directa y Serde devuelve un error en tiempo de ejecución («key must be a string»). Además, el orden de un HashMap no es determinista, así que el fichero cambia entre ejecuciones aunque los datos sean los mismos. Para persistencia usa BTreeMap (ordenado) o una Vec de pares.

¿Option<T> no implica que el campo sea opcional?

No. Option<T> describe el valor: puede ser None. Que el campo pueda faltar en el documento es otra cosa, y se declara con #[serde(default)]. Sin él, un JSON sin la clave produce «missing field». Si además quieres omitirla al escribir cuando es None, añade skip_serializing_if = "Option::is_none". Son tres conceptos que suelen confundirse: tipo opcional, campo opcional y campo omitido.

¿Cómo doy un error útil cuando falla el parseo?

Primero, no lo silencies: serde_json::Error ya trae line() y column(). Segundo, envuélvelo en tu error de dominio con el contexto que falte (ruta del fichero, operación). Tercero, si el documento es grande y el error dice «missing field» sin más, usa serde_path_to_error: deserializa con serde_path_to_error::deserialize y tendrás la ruta exacta, por ejemplo links[3].hits. Y cuarto, escribe un test con un JSON roto a propósito para fijar el mensaje.
