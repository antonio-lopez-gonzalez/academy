Arquitectura y setup del proyecto

Módulo 8 · Proyecto Final ⏱ 45 minutos 🟢 proyecto

1 · Introducción

Unimos todo en el proyecto proyectos/redis-ws-hub: un servidor WebSocket + Minimal API en .NET 8 con el hub de conexiones distribuido sobre Redis, listo para ejecutar con docker compose up y dotnet run.

Esta lección define la arquitectura de archivos, el entorno y el «esqueleto» que rellenarás en las lecciones 2-4.

2 · Teoría

Estructura

proyectos/redis-ws-hub/
├── docker-compose.yml            # redis + redis-insight (+ replicación opcional)
├── README.md                     # cómo ejecutar y probar
├── src/RedisWsHub/
│   ├── Program.cs                # WebSocket + Minimal API + DI (multiplexer)

│   │   ├── ConnectionHub.cs      # broadcast/dirigido + suscripción (M7-03)
│   │   └── HubEvents.cs          # DTOs del backplane
│   └── appsettings.json
└── tests/RedisWsHub.Tests/       # unit tests (lógica pura p. ej. Keys, eventos)

Arranque

cd proyectos/redis-ws-hub
docker compose up -d                     # redis + redis-insight
dotnet run --project src/RedisWsHub --urls http://localhost:5210
# clientes: ws://localhost:5210/ws
# health:  http://localhost:5210/health/redis

3 · Ejemplo mínimo

// Program.cs — la DI del multiplexer + health (lo esencial)
builder.Services.AddSingleton<IConnectionMultiplexer>(_ =>
{
    var opts = ConfigurationOptions.Parse(cfg.GetConnectionString("Redis") ?? "localhost:6379");
    opts.AbortOnConnectFail = false;
    opts.ReconnectRetryPolicy = new ExponentialRetry(5000);
    return ConnectionMultiplexer.Connect(opts);
});
app.MapGet("/health/redis", (IConnectionMultiplexer mux) => /*…JSON de salud…*/);

4 · Ejemplo real

Un flujo completo que tendrás al acabar la lección 3:

Cliente-1 → ws://localhost:5210/ws (nodo-1)
Cliente-2 → un segundo proceso (nodo-2) en :5211

Cliente-1 envía {"type":"broadcast","payload":"hola"}
  → Nodo-1: reenvía a sus sockets + PUBLISH hub:events
  → Nodo-2: suscriptor recibe → reenvía a Cliente-2
  → ¡Cliente-1 y Cliente-2 reciben el mismo broadcast desde nodos distintos!

Ese es el «momento eureka» del curso: dos procesos .NET que nunca se hablan directamente, coordinados por Redis.

6 · Errores habituales

Levantar dos «nodos» pero con la misma configuración

# ❌ Ambos procesos se llaman "node-1" y compiten por el mismo registro
# ✅ Arranca con una variable de entorno distinta por proceso:
NODE_ID=node-1 dotnet run --urls http://localhost:5210
NODE_ID=node-2 dotnet run --urls http://localhost:5211

7 · Ejercicio guiado

  1. Paso 1: Crea el proyecto y el docker-compose; levanta Redis.
  2. Paso 2: Ejecuta el esqueleto (solo /health/redis) y verifica el health (ping, hitRatio).
  3. Paso 3: Comprueba en RedisInsight/redis-cli que aún no hay keys (el esqueleto no registra).
  4. Paso 4: Abre Keys.cs y rellena tu convención (M1-01).

8 · Reto

10 · Preguntas frecuentes

¿Necesito 2 máquinas para probar nodos?

No: dos procesos locales con puertos distintos (o dos contenedores) bastan para ver el backplane funcionando. Redis es el que «los une».

¿Y si uso Docker Compose para levantar también la app?

Puedes añadir servicios para 2 instancias de la app (redis-ws-hub-a, -b) con NODE_ID distintos y depends_on: redis; el puerto externo se reparte. Es tu elección para el desafío de la lección 4.
