Presencia, TTL y escalado multi-nodo

Módulo 8 · Proyecto Final ⏱ 45 minutos 🟢 proyecto

1 · Introducción

Terminamos de pulir el estado vivo: presencia con TTL que se limpia sola, el heartbeat amortiguado y una prueba de escalado multi-nodo (3 instancias coordinadas) — el objetivo de negocio del curso.

2 · Teoría

Presencia autolimpiable

Heartbeat → ZADD hub:presence user <now>   (score = último latido)
Barrido/consulta → ZRANGEBYSCORE hub:presence <now-60> +inf
Limpieza lazy → ZREMRANGEBYSCORE hub:presence -inf <now-60>

Sin cron: la consulta «ignora» a los viejos, y el broadcast de desconexión
lo da el propio nodo cuando detecta la caída (o la expiración del registro).

Heartbeat amortiguado y asimétrico

// No refresques a cada mensaje si hay ráfagas: amortigua con un mínimo
private DateTime? _lastHeartbeat;
private static readonly TimeSpan HeartbeatEvery = TimeSpan.FromSeconds(10);

bool should = _lastHeartbeat is null
    || DateTime.UtcNow - _lastHeartbeat >= HeartbeatEvery;
if (should)
{
    await registry.HeartbeatAsync(connId, userId);   // refresh lease + score
    _lastHeartbeat = DateTime.UtcNow;
}

Lease (30 s) ≫ intervalo (10 s) ≫ coste de cada refresh: latencia de red nunca te descuelga.

Escalar: N nodos sin tocar el código

NODO-1 (5210)   NODO-2 (5211)   NODO-3 (5212)
     │                │                │
     └──────► REDIS (registro + backplane) ◄──────┘
        broadcast de cualquiera llega a todos.
        la presencia es global (zset), el registro por conexión (hash).

Prueba con 3 instancias: añadir un nodo no cambia ninguna línea de C#; solo cambia NODE_ID y puerto.

3 · Ejemplo mínimo

# consulta de presencia "últimos 60 s" + limpieza
ZRANGEBYSCORE hub:presence 1749913600 +inf
ZREMRANGEBYSCORE hub:presence -inf 1749913600
ZCARD hub:presence

4 · Ejemplo real

Prueba de escalado con 3 instancias (en tu máquina con puertos distintos):

# Terminal 1,2,3:
NODE_ID=node-1 dotnet run --project src/RedisWsHub --urls http://localhost:5210
NODE_ID=node-2 dotnet run --project src/RedisWsHub --urls http://localhost:5211
NODE_ID=node-3 dotnet run --project src/RedisWsHub --urls http://localhost:5212

# Clientes: conecta 1 a cada nodo.
# Comprueba:
#   - broadcast desde cualquier nodo → llega a los 3 sockets.
#   - presencia global → los 3 usuarios online (ZRANGEBYSCORE).
#   - registro → HGET hub:conn:<id> node  indica el nodo dueño.
#   - kill node-2 → en ~30 s su presencia/registro expiran solos.

¿Plantea cuántos clientes por nodo aguanta antes de añadir otro? El número lo dicta tu prueba de carga, no Redis.

6 · Errores habituales

El score «crece» para siempre sin limpieza

# ❌ La presencia crece si solo ZADD y nunca limpias
# ✅ Limpieza lazy en la consulta + ZREMRANGEBYSCORE periódico

Subir 3 nodos pero con la MISMA config (mismo puerto/nombre)

Si tres procesos escuchan el mismo puerto o usan el mismo NODE_ID, no es un clúster: es un caos. Puerto + NODE_ID únicos por instancia.

8 · Reto

🎯 100 clientes, N nodos

Diseña (no implementes aún) un mini benchmark: cuántos clientes por nodo y qué métrica de «broadcast 100% entregado» medirías (p. ej. recibidos/emitidos por nodo). Decide el cuello de tu sistema real (¿red? ¿CPU de reenvío? ¿RAM?) y cómo lo vigilarías con los healths de M6-04.

9 · Resumen

  • Presencia global (zset) autolimpiable + registro (hash) con TTL.
  • Heartbeat amortiguado con lease ≫ intervalo.
  • Escalado = más instancias idénticas; la prueba de 3 nodos lo demuestra.

10 · Preguntas frecuentes

¿Puedo tener «presencia y registro» en un solo formato?

Puedes ahorrar algo guardando userId en el hash del registro y derivando presencia de ahí con SCAN… pero sería caro y frágil. El zset es la forma O(log n) de responder «los online de la ventana».

¿El TTL de presencia hub:presence depende del número de nodos?

No: cada heartbeat refresca su score. La «ventana» la decides tú (60 s); el recuento de nodos no cambia el diseño.
