Implementar registro y pub/sub

Módulo 8 · Proyecto Final ⏱ 45 minutos 🟢 proyecto

1 · Introducción

Rellenamos la primera mitad del proyecto: ConnectionRegistry (hash + TTL + presencia + heartbeat) y ConnectionHub (suscripción/pub del backplane). Al final, dos procesos .NET «hablan» vía Redis.

2 · Teoría

ConnectionRegistry — el contrato

// Methods
RegisterAsync(connId, userId)   // hash + TTL + ZADD presencia
HeartbeatAsync(connId, userId)  // refresh lease + score
UnregisterAsync(connId, userId) // DEL hash + ZREM
FindNodeAsync(connId)           // HGET node
OnlineAsync()                   // ZRANGEBYSCORE (última ventana)

ConnectionHub — el backplane

  • Se suscribe a hub:events (broadcast) y hub:direct (dirigido).
  • Mantiene el diccionario local connId → WebSocket.
  • Filtra from == nodeId para no hacer loop.

Decisión de diseño del proyecto: el broadcast publica Y reenvía local en el propio nodo origen; el suscriptor de los demás nodos reenvía a sus sockets. El filtro evita «el origen recibe y reenvía dos veces».

3 · Ejemplo mínimo

// Registro rápido (resumen de lo que implementarás)
await db.HashSetAsync($"hub:conn:{conn}", [new("node", nodeId), new("userId", userId)]);
await db.KeyExpireAsync($"hub:conn:{conn}", TimeSpan.FromSeconds(30));
await db.SortedSetAddAsync("hub:presence", userId, DateTimeOffset.UtcNow.ToUnixTimeSeconds());

// ... y el publish del evento
await sub.PublishAsync("hub:events", JsonSerializer.Serialize(new { type = "connect", conn, node = nodeId }));

4 · Ejemplo real

Integración con el handler del socket: al conectar, registrar + publicar; en cada mensaje, heartbeat; al cerrar, unregister + publicar.

// en el loop del WebSocket (Program.cs simplificado)
await hub.AddAsync(context, socket);       // registra + guarda local + publica "connect"

while (socket.State == WebSocketState.Open)
{
    var result = await socket.ReceiveAsync(buffer, CancellationToken.None);
    if (result.MessageType == WebSocketMessageType.Close) break;

    await hub.HeartbeatAsync(connId, userId);       // refresh lease + presencia
    var envelope = JsonSerializer.Deserialize<WsEnvelope>(
        Encoding.UTF8.GetString(buffer, 0, result.Count));

    switch (envelope?.Type)
    {
        case "broadcast": await hub.BroadcastAsync(envelope!.Payload!); break;
        case "send":      await hub.SendToAsync(envelope!.To!, envelope.Payload!); break;
    }
}
await hub.RemoveAsync(connId, userId);      // unregister + publica "disconnect"

Todo lo «de Redis» está encapsulado; el loop del socket queda legible.

6 · Errores habituales

Publicar «connect» sin que otros lo sepan (no suscripción)

// ❌ Registras en Redis pero nadie se enteró (sin SUBSCRIBE en los nodos)
// ✅ ConnectionHub se suscribe al arrancar y publica connect/disconnect

Segar el loop con el heartbeat en cada mensaje

Healthbeat por mensaje está bien, pero si el cliente envía muchos mensajes, refresca «igual»; el lease y el score son baratos (una round-trip). Si quieres reducir, hazlo a intervalos mínimos (p. ej. si han pasado >5 s).

9 · Resumen

  • ConnectionRegistry: hash+TTL+presencia.
  • ConnectionHub: backplane broadcast/dirigido con filtro de origen.
  • 2 instancias coordinan broadcast vía Redis (demo central).

10 · Preguntas frecuentes

¿El diccionario local es «memoria de más»?

Es la parte «solo de este nodo» (los sockets que le tocan). Redis guarda el directorio; el diccionario contiene los sockets reales. Es el diseño correcto (no guardes sockets en Redis).

¿Puedo usar Streams en vez de pub/sub para el broadcast?

Si quieres historial/auditoría, sí (M3-02); para broadcast en vivo, pub/sub es más directo y ligero. El curso te deja los dos; el proyecto usa pub/sub por simplicidad del caso de uso.
