Qué es Redis y para qué sirve

Módulo 0 · Qué es Redis y el caso de uso ⏱ 30 minutos

1 · Introducción

Redis es una base de datos en memoria, rápida y versátil, que en un sistema como el tuyo (servidor WebSocket + API en .NET) resuelve dos problemas de golpe: caché compartida y estado distribuido para el hub de conexiones.

En esta lección verás qué es realmente Redis (no es «solo una caché»), por qué es tan rápido, en qué casos brilla y por qué encaja en un servidor WebSocket que quieres escalar.

¿Por qué existe esta lección? Porque casi todos los «errores de Redis» nacen de no entender qué es y qué no es: si esperas de él lo que da una base relacional, o lo usas como si fuera memoria volátil sin pensar en eviction, la arquitectura se rompe tarde o temprano.

2 · Teoría

El origen del nombre

REmote DIctionary Server (RDS → Redis). Lo creó Salvatore Sanfilippo en 2009. La idea central: un diccionario remoto, exponible por red, con operaciones atómicas. El truco está en que vive en memoria y por tanto es extremadamente rápido.

Características que lo definen

CaracterísticaImplicación
En memoria (in-memory)Latencia de microsegundos; la RAM limita el dataset (sale la eviction, módulo M0/M4)
Single-threadedCada comando es atómico y no hay condiciones de carrera entre clientes para un comando
Estructuras de datos ricasStrings, hashes, lists, sets, sorted sets, streams, bitmaps… no solo clave-valor plano
TTL / expiración nativaLas keys caducan solas: perfecto para presencia, sesiones, códigos temporales
Pub/Sub y streamsMensajería y colas dentro del mismo servidor
Persistencia opcionalRDB/AOF: no es «volátil de todo» si decides guardar en disco
Replicación, Sentinel, ClusterHA y escala horizontal (Módulo 4)

Casos de uso típicos

  • Caché (cache-aside): datos caros de calcular (perfiles, precios, catálogo).
  • Sesiones compartidas entre varias instancias de una web.
  • Colas: lists con bloqueo (BRPOP) o streams con grupos.
  • Presencia / ranking: sorted sets con timestamps (quiénes están conectados).
  • Rate limiting: contadores atómicos (INCR + EXPIRE).
  • Backplane de tiempo real: pub/sub para broadcast entre nodos (¡tu caso!).

Redis frente a lo que ya conoces

RedisMemcachedSQL (Postgres)
ModeloClave-valor + estructurasClave-valor planoRelacional + queries
DurabilidadOpcional (RDB/AOF)VolátilPersistente (fuente de verdad)
EstructurasRicas (listas, sets, streams…)Solo bytesTablas, índices, joins
CuándoEstado efímero y calienteCaché simpleHistorial y consultas complejas

Regla mental: SQL es la fuente de verdad; Redis da velocidad y estado compartido volátil. No compiten, se complementan.

3 · Ejemplo mínimo

Con Redis corriendo (Docker), tu primer contacto:

docker run -d --name redis -p 6379:6379 redis:7.4-alpine
docker exec -it redis redis-cli

127.0.0.1:6379> SET saludo hola
OK
127.0.0.1:6379> GET saludo
"hola"
127.0.0.1:6379> PING
PONG

Tres comandos y ya tienes un servidor clave-valor funcionando. En el resto del curso, sustituirás SET/GET por las estructuras y patrones reales del hub.

4 · Ejemplo real

Tu servidor WebSocket con 2 nodos ejecutándose. Sin Redis, cada nodo «no sabe» quién está conectado en el otro. Con Redis:

Cliente ──WS──► Nodo A (node-1)              Nodo B (node-2)
                 │   "registro" │                  │
                 ▼              ▼                  ▼
        SET hub:conn:<id> node-1 EX 30      SET hub:conn:<id> node-2 EX 30
                 │                                  │
                 └─────────────►  REDIS (hub) ◄──────┘
                                 • registro de conexiones (hash/string + TTL)
                                 • broadcast: PUBLISH hub:events  → los 2 nodos
                                 • presencia: ZADD presence <ts> user:id

Así, un mensaje «trade» publicado por el nodo A llega también a los clientes del nodo B vía pub/sub. Ese es el patrón que construirás en el proyecto final.

6 · Errores habituales

Tenerlo todo en memoria sin límites ni eviction

# ❌ La caché crece hasta llenar la RAM y Redis empieza a fallar
# ✅ POLICY definida, p. ej. para caché:
CONFIG SET maxmemory 1gb
CONFIG SET maxmemory-policy allkeys-lru

Usar Redis como si fuera una base relacional

No esperes consultas con uniones: modela pensando en las consultas (denormaliza a mano). Para histogramas complejas, deja SQL.

7 · Ejercicio guiado

  1. Paso 1: Levanta Redis con Docker (comando del ejemplo mínimo).
  2. Paso 2: Entra con redis-cli y ejecuta SET, GET, EXISTS, PING.
  3. Paso 3: Ejecuta INFO y anota: used_memory_human, connected_clients, uptime_in_seconds.
  4. Paso 4: Limpia al terminar: FLUSHDB (o docker stop redis).

9 · Resumen

  • Redis = servidor de datos en memoria, rápido, single-threaded y con estructuras ricas.
  • No es solo caché: colas, presencia, ranking, rate limiting y backplane pub/sub.
  • SQL es la fuente de verdad; Redis la velocidad y el estado compartido.
  • En tu WebSocket: registro de conexiones + broadcast entre nodos.

10 · Preguntas frecuentes

¿Redis guarda los datos al reiniciar?

Por defecto Redis 7 sí guarda snapshots RDB, pero depende de la config de persistencia (Módulo 4). Para estado efímero no te preocupes; para datos que no puedes perder, configura AOF.

¿Es gratis para producción?

El servidor es libre y puedes gestionarlo tú (Docker/k8s). Los servicios gestionados (Upstash, Redis Cloud, ElastiCache) cobran por operarlo. Para aprender y experimentar, tu Docker local es gratis.

¿Redis reemplaza a un Message Broker como RabbitMQ?

Para cargas moderadas, sus listas/streams valen. Para hard requirements de cola (durabilidad estricta, redelivery con lógica compleja, BFF), un broker dedicado es mejor. En Módulo 3 ves cuándo cada uno.
