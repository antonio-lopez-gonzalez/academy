Resiliencia, reconexión y configuración

Módulo 6 · StackExchange.Redis en .NET ⏱ 30 minutos

1 · Introducción

Redis cae, las redes parpadean y tu hub debe seguir vivo. Esta lección junta la config del cliente (ConfigurationOptions), las respuestas a caídas (degradación), y cómo monitorizar a Redis + a tu cliente para reaccionar antes de que duela.

2 · Teoría

ConfigurationOptions: el «bosque de botones»

var opts = ConfigurationOptions.Parse(conn);
opts.AbortOnConnectFail = false;        // no romper la app si Redis tarda
opts.ConnectTimeout = 5000;             // ms de intento de conexión
opts.SyncTimeout = 5000;                // timeout de comandos síncronos/async
opts.AsyncTimeout = 5000;
opts.ReconnectRetryPolicy = new ExponentialRetry(5000);  // backoff
// (opcional) opts.CommandMap para restringir comandos; evítalo si no lo necesitas
opts.EndPoints.Add("localhost:6379");

Con AbortOnConnectFail=false, los comandos se encolan y esperan a la conexión (con timeout). Así la app arranca aunque Redis aún no esté.

El modelo de conexión y reconexión

  • El multiplexer intenta (re)conectar en background; expone eventos ConnectionRestored/ConnectionFailed.
  • Al restaurarse, re-vínculas tus suscripciones (SubscribeAsync) y re-ejecutas lógica de «volver a la normalidad».
  • Tu aplicación, durante la caída: degradar, no fallar.

Degradación en el hub

try
{
    await db.HashSetAsync(key, entries, TimeSpan.FromSeconds(30));
}
catch (RedisConnectionException)
{
    _logger.LogWarning("Redis caído: presencia en memoria (temporal)");
    _localFallback[connectionId] = DateTimeOffset.UtcNow;   // modo local
    // No publiques ni registres a nivel global hasta que vuelva.
}

Monitorizar a Redis y a tu cliente

// Estado del multiplexer
bool connected = mux.IsConnected;
var server = mux.GetServer("localhost:6379");
var info = server.Info();
long hits  = (long)info.First(x => x.Key == "keyspace_hits").Value;
long misses= (long)info.First(x => x.Key == "keyspace_misses").Value;
long clients = (long)info.First(x => x.Key == "connected_clients").Value;

// PING de salud (puerto sano)
TimeSpan ping = await mux.GetDatabase().PingAsync();

Expón /health con estas métricas: verás las caídas antes de que los usuarios se quejen.

3 · Ejemplo mínimo

var opts = ConfigurationOptions.Parse("localhost:6379");
opts.AbortOnConnectFail = false;
opts.ReconnectRetryPolicy = new ExponentialRetry(2000);

var mux = ConnectionMultiplexer.Connect(opts);
mux.ConnectionRestored += (_, _) => Console.WriteLine("Redis volvió");
mux.ConnectionFailed += (_, e) =>
    Console.WriteLine($"Redis caído: {e.Exception?.Message}");

4 · Ejemplo real

Un health‑endpoint de tu API que combina ping + stats (y que tus alertas pueden leer):

app.MapGet("/health/redis", (IConnectionMultiplexer mux) =>
{
    IDatabase db = mux.GetDatabase();
    TimeSpan ping;
    try { ping = db.PingAsync().GetAwaiter().GetResult(); }
    catch (RedisConnectionException ex)
    {
        return Results.Json(new { ok = false, error = ex.Message }, statusCode: 503);
    }

    var info = mux.GetServer().Info();
    long hits = Key(info, "keyspace_hits");
    long misses = Key(info, "keyspace_misses");
    return Results.Ok(new
    {
        ok = true,
        pingMs = ping.TotalMilliseconds,
        hitRatio = (hits + misses) == 0 ? null : Math.Round(hits / (double)(hits + misses), 3),
        clients = Key(info, "connected_clients"),
    });

    static long Key(IDictionary<string, string> info, string k) =>
        info.TryGetValue(k, out var v) ? long.Parse(v) : 0;
});

No es elegante bloquear con GetAwaiter() (mejor async), pero el patrón es claro: estado en JSON para healthchecks.

6 · Errores habituales

Tirar la excepción y no degradar

// ❌ El hub "no contesta" porque Redis falló y no atrapas
// ✅ try/catch alrededor de operaciones de Redis → fallback local
try { await db...; } catch (RedisException) { _localMode = true; }

Configurar SyncTimeout demasiado corto

Un SyncTimeout pequeño causa «Redis Timeout» bajo picos; usa tiempos de red normales (5 s) y piensa en async.

7 · Ejercicio guiado

  1. Paso 1: Configura el multiplexer robusto (AbortOnConnectFail=false, backoff).
  2. Paso 2: Detén Redis y verifica: la app SEGUE andando (modo local) y el health marca 503.
  3. Paso 3: Vuelve a levantar Redis: ConnectionRestored dispara re-suscripción y re-registro.
  4. Paso 4: Anota en README cómo probarías la caída en tu CI/CD.

8 · Reto

🎯 Diseño «caída de Redis»

Redacta el plan de tu hub ante caída de Redis: qué pasa con la presencia, el broadcast (se pierde pub/sub), las escrituras encoladas y cómo se recupera al volver (re-registro + re-suscripción). Compáralo después con el proyecto final.

9 · Resumen

  • ConfigurationOptions: AbortOnConnectFail=false, timeouts, retryPolicy.
  • Degrada con gracia (modo local) y re-registra al volver.
  • Re-suscribirse en ConnectionRestored.
  • Health: ping + hitRatio + clients.

10 · Preguntas frecuentes

¿AbortOnConnectFail=false «oculta» errores?

No: los comandos se encolan y acaban con timeout si Redis no vuelve. Es solo que la app no «se niega a arrancar» por un Redis lento.

¿Necesito reiniciar la app si Redis vuelve?

No para lo esencial; el multiplexer reconecta solo. Pero vuelve a suscribirte (ISubscriber) y a limpiar el «modo local» con eventos del multiplexer.
