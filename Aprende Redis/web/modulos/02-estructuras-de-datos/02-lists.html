Lists: colas simples

Módulo 2 · Estructuras de Datos ⏱ 30 minutos

1 · Introducción

Una list es una secuencia ordenada que admite inserción/extracción eficiente por ambos extremos. Con LPUSH + RPOP construyes una cola FIFO (y con la variante bloqueante BRPOP, una cola para trabajadores sin polling).

Verás los comandos, el patrón productor-consumidor y por qué las listas son el «escalón previo» a los streams (Módulo 3).

2 · Teoría

Comandos esenciales

LPUSH cola a b c     # inserta por la izquierda → c,b,a
RPUSH cola d         # inserta por la derecha
LPOP cola            # saca por la izquierda (c)
RPOP cola            # saca por la derecha (d)
LRANGE cola 0 -1     # todos
LLEN cola            # longitud
LTRIM cola 0 99      # recorta (mantener solo los últimos 100)

FIFO y LIFO

  • FIFO (cola): LPUSH por un extremo + RPOP por el otro.
  • LIFO (pila): LPUSH + LPOP en el mismo extremo.
  • Bloqueante: BLPOP/BRPOP esperan «con timeout o infinito» hasta que haya elemento: trabajadores sin polling.

Por qué importa la atomicidad

LPUSH/RPOP son atómicos: nunca dos consumidores roban el mismo elemento de una cola compartida (como ocurriría con una «cola en memoria» del proceso). El patrón productor-consumidor queda seguro también entre procesos distintos.

3 · Ejemplo mínimo

LPUSH queue:trades '{"id":1}'
LPUSH queue:trades '{"id":2}' '{"id":3}'
RPOP queue:trades          # {"id":1} → FIFO
RPOP queue:trades          # {"id":2}
LLEN queue:trades          # 1

4 · Ejemplo real

En el hub, una cola por tarea «por nodo» para encolar trabajos ligados (p. ej. notificaciones a enviar) procesadas por un worker:

// Productor (nodo A): encola notificación
await db.ListLeftPushAsync("queue:notify", json);

// Consumidor (worker, cualquier nodo): espera bloqueante
while (true)
{
    var payload = await db.ListRightPopAsync("queue:notify");
    if (payload.IsNull) { await Task.Delay(200); continue; }   // (fallback no bloqueante)
    await ProcessAsync(payload!);
}
// Con BLPOP en .NET: ListRightPopAsync no tiene bloqueo nativo →
//    patrón recomendado: BRPOP via Execute (Lua/raw) o ListRightPop + retry.

Para carga baja es perfecto; cuando necesites confirmar por mensaje, grupos de consumidores o reprocesar, en el Módulo 3 pasamos a streams.

6 · Errores habituales

Consumir con LRANGE + LPOP (doble lectura)

# ❌ LRANGE para "ver" y luego LPOP para sacar (raza entre consumidores)
# ✅ RPOP / BRPOP directos: la extracción es atómica

Cola sin protección de trabajadores

Si una tarea se está procesando y tu worker muere a mitad, el mensaje se pierde. Para «garantía de entrega» usa streams (XACK) o la lista auxiliar de procesando.

7 · Ejercicio guiado

  1. Paso 1: Crea queue:demo con LPUSH de 5 tareas.
  2. Paso 2: Consume 3 con RPOP (FIFO) y verifica el orden.
  3. Paso 3: Prueba LTRIM a 1 elemento y observa LLEN.
  4. Paso 4: En dos terminales, lanza un consumidor con BRPOP queue:demo 0 y publica desde la otra: observa cómo recibe sin polling.

8 · Reto

🎯 Cola «con ack» con listas

Diseña con dos listas un sistema de reintentos: queue:todo y queue:processing. El worker hace RPOPLPUSH, procesa, y al terminar LREM de processing; si muere, tras un timeout se mueve de vuelta. Responde: ¿qué comando de Redis lo hace en un solo paso? Pruébalo en redis-cli.

9 · Resumen

  • Lists = secuencia ordenada con operaciones por extremos.
  • FIFO: LPUSH+RPOP; LIFO: LPUSH+LPOP; bloqueante: BRPOP/BLPOP.
  • LTRIM para búferes; BRPOPLPUSH para reintentos.
  • Para «guaranteed delivery» saltamos a streams (M3).

10 · Preguntas frecuentes

¿Qué longitud máxima puede tener una lista?

Hasta 2^64-1 elementos (la RAM manda). Eso sí: comandos como LRANGE con rangos enormes son O(N): usa rangos pequeños (paginado) o LMOVE.

¿BRPOP bloquea Redis?

No: el cliente que espera queda en espera y Redis sigue sirviendo demás comandos. Es el mecanismo para workers eficientes.
