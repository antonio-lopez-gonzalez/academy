INCR/DECR y contadores atómicos

Módulo 1 · Keys, Strings y TTL ⏱ 30 minutos

1 · Introducción

Contar cosas en un sistema distribuido es trampa: dos nodos leyendo + sumando + escribiendo pierden incrementos. Redis lo resuelve con contadores atómicos (INCR, INCRBY…), porque cada comando se ejecuta sin intercalarse con otros.

Verás los comandos, su combinación con TTL para ventanas (rate limiting del hub, contadores por minuto) y su uso en .NET (M6).

2 · Teoría

La atomicidad

Redis es single-threaded: ejecuta un comando entero sin interrupciones. INCR key es «leer, sumar 1, escribir» como una operación. Así, N procesos concurrentes incrementando una misma key nunca pierden conteo, cosa imposible con «GET + INCR local + SET» (read-modify-write).

Comandos

INCR key              # +1 (crea con 0 si no existía)
DECR key              # -1
INCRBY key 5          # +5
DECRBY key 5          # -5
INCRBYFLOAT key 1.5   # para decimales
GET key               # valor actual

Contadores + TTL = ventanas de tiempo

El patrón rey del rate limiting: una key que expira al final de la ventana y un INCR al comenzar.

# 1ª petición en la ventana de 60 s:
INCR rl:user:42:win1     # 1
EXPIRE rl:user:42:win1 60
# siguientes peticiones:
INCR rl:user:42:win1     # 2, 3, 4...
TTL rl:user:42:win1      # ¿cuánto queda para resetear?
# → cuando pasa el límite, rechaza

La raza aquí la resuelve INCR+EXPIRE de forma aceptable en la práctica (o Lua en casos estrictos, M6-03).

3 · Ejemplo mínimo

INCR stats:nodo1:msgs        # 1
INCR stats:nodo1:msgs        # 2
INCRBY stats:nodo1:msgs 8    # 10
DECR stats:nodo1:msgs        # 9
GET stats:nodo1:msgs         # "9"

Dos procesos amigos haciendo INCR nunca dan un total menor del esperado.

4 · Ejemplo real

En el hub: contadores de mensajes por nodo y rate limiting de conexiones por IP (anti «connection flood»).

// Mensajes procesados por nodo
long received = await db.StringIncrementAsync($"stats:{_nodeId}:msgs");

// Rate limiting de conexiones por IP (máx 20 en 60 s)
var window = DateTimeOffset.UtcNow.ToUnixTimeSeconds() / 60; // ventana de minuto
string rlKey = $"rl:conn:{ip}:{window}";
long count = await db.StringIncrementAsync(rlKey);
if (count == 1)
    await db.KeyExpireAsync(rlKey, TimeSpan.FromSeconds(65)); // +margen

if (count > 20) { CloseConnection(); return; }

El contador + TTL resuelve «X eventos por ventana» con dos comandos.

6 · Errores habituales

Leer-modificar-escribir en .NET

// ❌ Raza entre GET y SET
long n = (long)await db.StringGetAsync("ct");
n++;
await db.StringSetAsync("ct", n);

// ✅ Atómico en Redis
long n2 = await db.StringIncrementAsync("ct");

Contador «de hoy» sin reset

Si el contador no expira, mañana sigue sumando contra el valor de ayer: define la ventana dentro de la propia key (rl:user:42:<windowId>) y déjala expirar.

7 · Ejercicio guiado

  1. Paso 1: Con redis-cli crea un contador demo:count y haz 10 INCR.
  2. Paso 2: Añade TTL 20 y verifica que al expirar INCR empieza de nuevo en 1.
  3. Paso 3: Simula rate limiting: INCR 5 veces en «ventana» de 30 s y observa el TTL.
  4. Paso 4: (Solo si tienes 2 terminales) haz INCR concurrente y comprueba que el total final es exacto.

8 · Reto

🎯 Rate limiter sin fugas

Investiga la técnica del «fixed window counter» con INCR+EXPIRE frente a «sliding window log» con sorted sets (ZSET+ZREMRANGEBYSCORE). Escribe cuál es más justa y cuál más barata, y dónde pondrías el límite en tu hub (p. ej. 100 conexiones/min/IP).

9 · Resumen

  • INCR/DECR/INCRBY = contadores atómicos (sin raza).
  • Clave + TTL = ventana (rate limiting, contadores por minuto).
  • Margen en el TTL y nombre de key con la ventana para no «arrastrar» valores.

10 · Preguntas frecuentes

¿INCR devuelve el valor nuevo?

Sí, devuelve el valor tras el incremento; puedes rechazar directamente si pasa tu umbral.

¿Y si la key tiene un valor no numérico?

INCR sobre un valor no entero devuelve error (nil). Mantén los contadores «solo número».
