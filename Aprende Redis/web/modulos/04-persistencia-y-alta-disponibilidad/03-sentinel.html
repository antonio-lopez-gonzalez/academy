Sentinel: alta disponibilidad

Módulo 4 · Persistencia y Alta Disponibilidad ⏱ 30 minutos

1 · Introducción

La réplica no promociona sola. Sentinel es el «vigilante» que monitoriza el primary, detecta su caída y promueve a una réplica automáticamente. Es la pieza que te da real alta disponibilidad para Redis.

Verás qué hace Sentinel, cómo se configura, cómo tu app encuentra el primary y qué papel juega en el hub.

2 · Teoría

Qué hace Sentinel

  • Monitoriza primaries (y réplicas) — manda PING periódicos.
  • Detecta caídas (subjetiva a los X s / objetiva con mayoría de Sentinels).
  • Failover: promueve una réplica a primary, reconfigura el resto y notifica.
  • Notificación: tu app pregunta «¿quién es el primary ahora?» al Sentinel.
         Sentinel (3 procesos, cuórum 2)
              │  monitoriza
   PRIMARY ◄──┤  failover: /
        │     │  promueve 2ª
      replica-1  replica-2

App ──► "¿primary?" ──► Sentinel ──► "redis-2 :6379"

Configuración (sentinel.conf o env var en Docker)

sentinel monitor mymaster redis-primary 6379 2   # nombre, host, puerto, quórum
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 15000
  • Quórum (2): nº de Séntinels que deben coincidir para declarar la caída (evita falsos if un sentinel ve un parpadeo).
  • down-after-milliseconds: latencia antes de sospechar.

El cliente descubre el primary

StackExchange.Redis admite una cadena de conexión con varios puntos: puedes incluir los Séntinels y usar el «Sentinel mode» para que tu app re-apunte sola al nuevo primary. Para el curso, entender que la app no hardcodea «redis:6379» sino que descubre el nodo activo es la victoria.

3 · Ejemplo mínimo

Primeros comandos de Sentinel (desde un contenedor con sentinel):

SENTINEL master mymaster           # info del primary actual
SENTINEL replicas mymaster         # réplicas conocidas
SENTINEL get-master-addr-by-name mymaster  # host puerto del primary
SENTINEL failover mymaster         # fuerza un failover (pruebas)

Con get-master-addr-by-name tu app pide «el primary de ahora» sin saber cuál es.

4 · Ejemplo real

docker-compose del entorno HA (resumen): Redis primary+replica+3 sentinels que monitorizan mymaster:

services:
  redis-primary: { image: redis:7.4-alpine, ... }
  redis-replica:
    image: redis:7.4-alpine
    command: ["redis-server", "--replicaof", "redis-primary", "6379"]
  sentinel-1:
    image: redis:7.4-alpine
    command: ["redis-server", "--sentinel", "--sentinel-config-file", "/etc/sentinel.conf"]
    # … argumentos: monitor mymaster redis-primary 6379 2 …

Con 3 sentinels (quórum 2) tienes tolerancia a 1 caída sin querer intervenir. Tu hub puede degradar: mientras el primary no esté, no hay estado compartido — y se re-registra al volver (M7).

6 · Errores habituales

Confundir «sentinel» con «replíca»

# ❌ Poner todas las réplicas como si "una de ellas fuera el sentinel"
# ✅ Sentinel es un proceso APARTE que vigila primary+réplicas

Umbrales agresivos que matan la presencia

Con down-after-milliseconds 200, cualquier jitter de red provoca failover; tus TTL de presencia se estropean. Dale margen real.

7 · Ejercicio guiado

  1. Paso 1: Con mínimo 3 contenedores (primary, replica, sentinel), monta el trío con redis-server --sentinel.
  2. Paso 2: Pregunta al sentinel SENTINEL get-master-addr-by-name mymaster.
  3. Paso 3: Detén el primary y observa cómo el sentinel promueve la réplica.
  4. Paso 4: Vuelve a preguntar el primary: debe haber cambiado (failover hecho).

8 · Reto

🎯 Runbook del failover

Escribe el runbook de «Redis cae» para tu hub: qué observa tu app (errores de conexión), cómo degrada (modo local), cuándo re-registra y qué hace el cluster al volver. Documenta en un comentario/archivo del proyecto cómo probarías el failover sin romper nada.

9 · Resumen

  • Sentinel monitoriza, detecta y promueve réplicas automáticamente.
  • Quórum 2+ sentinels para decidir la caída con mayoría.
  • La app descubre el primary (SENTINEL get-master-addr-by-name).
  • El failover no es instantáneo: el hub debe resistir la ventana.

10 · Preguntas frecuentes

¿Sentinel o Cluster para mi hub?

Si tu dataset cabe en un solo nodo (lo normal en presencia/caché), Sentinel basta. Cluster es para datos que no caben o para muchos GB — y complica mucho la vida (M4-04).

¿Cuánto dura el failover?

Con down-after-ms 5s y redis server healthy, del orden de segundos. Planifica tu app para esa ventana de indisponibilidad.
