Redis Cluster: sharding y hash slots

Módulo 4 · Persistencia y Alta Disponibilidad ⏱ 35 minutos

1 · Introducción

Cuando los datos no caben en un solo nodo (muchos GB) o quieres escala por sharding, entra Redis Cluster: reparte las keys entre múltiples nodos usando hash slots, con réplicas incluidas.

Esta es la pieza de «scale-out». Para un hub pequeño/mediano probablemente NO la necesites; entenderla te dirá cuándo sí (y qué complica: mover keys, multi-key, pub/sub y tu mentalidad).

2 · Teoría

El modelo de hash slots

CRC16(key) % 16384 = slot

        node1: slots 0–5460
        node2: slots 5461–10922
        node3: slots 10923–16383
        (opcional) node4-6 réplicas
  • Cada key cae en UN slot a cargo de UN nodo master.
  • El cliente recibe una redirect -MOVED slot host:port si le pide a un nodo que no es el dueño → aprende el mapa.
  • Los hash tags {tag} fuerzan que varias keys caigan en el mismo slot (para operaciones multi-key dentro del mismo nodo).

Cómo se comporta la tolerancia

  • Cada master puede tener réplicas; si un master cae y hay réplica, promueve (failover automático del cluster).
  • Si un shard se queda sin master ni réplica, «cluster failed»: parte de los datos no accesibles.
  • Persistencia y eviction se configuran por nodo igual que standalone.

Impacto en el desarrollo

3 · Ejemplo mínimo

# Consulta de slots/nodes (en cualquier nodo del cluster)
CLUSTER INFO
CLUSTER SLOTS
CLUSTER NODES

# Los MOVED aparecen si preguntas al nodo equivocado:
SET key1 v        # (si no es el dueño) → -MOVED 1000 node2:6391
# Con cliente cluster, se sigue el MOVED automáticamente

4 · Ejemplo real

Con las imágenes oficiales de Redis puedes arrancar un cluster de 3 masters (+réplicas). Ejemplo con docker (mínimo para entender):

# 6 contenedores, modo cluster, puertos 7000-7005
docker run -d --name redis-7000 -p 7000:6379 redis:7.4-alpine \
  redis-server --cluster-enabled yes --port 6379
# … réplicas con --cluster-enabled yes …
# luego ejecuta:
redis-cli --cluster create 127.0.0.1:7000 ... --cluster-replicas 1

Para el hub: defiende si tus datos «no caben». Una pregunta clave: «¿es la presencia geo-distribuida o cabe en un solo nodo?». Si cabe, Cluster añade complejidad sin beneficio — Sentinel es la vía elegante.

6 · Errores habituales

Ejecutar MSET/MGET multi-key sin hash tags

# ❌ MSET user:1 a user:2 (slot distinto) → CROSSSLOT Keys in request don't hash
# ✅ Usa {tag}: MSET user{1}:name ana user{1}:age 30   (mismo slot)
#    o haz operaciones por key

Suponer que «cada nodo es una réplica completa»

En Cluster, cada nodo guarda solo SU parte (sus slots). No esperes encontrar TODAS las keys en cualquiera: es un hash-ring, no una réplica.

7 · Ejercicio guiado

  2. Paso 2: Si no cabe, escribe los 3 cambios que harías al pasar a Cluster (keys con tag, SCAN por nodo, pub/sub de trabajo).
  3. Paso 3: Consulta CLUSTER NODES de un cluster de prueba (o estudia la salida de ejemplo).

8 · Reto

🎯 El umbral de escala

Calcula cuántas conexiones simultáneas usaría tu hub y cuántos bytes gasta cada registro en Redis. Con tu estimación de RAM, decide: ¿Sentinel o Cluster? Explica el criterio (no la respuesta bonita, sino el razonamiento con números).

9 · Resumen

  • Cluster reparte keys por hash slots (CRC16 % 16384).
  • MOVED redirects; hash tags agrupan keys; SCAN por nodo; sin SELECT.
  • Usa Cluster solo si el dataset no cabe; Sentinel escala la disponibilidad, no el tamaño.

10 · Preguntas frecuentes

¿Cuándo debo plantearme Cluster de verdad?

Cuando tu dataset no quepa en el nodo más grande que puedas tener (decenas de GB), o cuando un solo servidor ya no aguante el QPS. Antes, Sentinel te da alta disponibilidad con mucha menos fricción.

¿StackExchange.Redis soporta Cluster bien?

Sí: con ConfigurationOptions apuntando a varios nodos y Cluster mode, el cliente sigue los MOVED y conoce los slots. Pero cada operación multi-key necesita tu hash tag.
